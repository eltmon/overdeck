# UAT Batch Trains

When agents land merge-ready features faster than you can review and merge them
one at a time, the bottleneck becomes the last-mile UAT. **UAT batch trains** fix
that: Overdeck keeps **one assembled, testable batch of every ready feature**
available at all times, so you can exercise the combined result and then land
exactly what you tested — in a single click.

<Note>
Batches run only while the **Merge train** switch on the Flywheel page header
(`merge_train_enabled`) is on. With it on, normal-priority PRs in a project that
does not hold for UAT merge together automatically once the batch's own CI run
is green: when `batch_size` PRs are ready (default 3) or the oldest has waited
`batch_wait_minutes` (default 30; both in **Settings → Merge Train**).
High-priority PRs (strikes, `critical`, `blocks-main`, `P0`, `urgent`, or
`substrate-improvement` plus `bug`) merge on their own. A PR only you may merge
(held for UAT, an auto-merge you cancelled, or a Deft human-merge policy) waits
in its own batch for you. With the switch off, every ready PR merges on its own
and nothing batches.

Automatic batches need batch CI: a GitHub Actions workflow named `CI` that runs
on pushes to `uat/**` branches. Without it, a batch waits at most 10 minutes for
a CI run, then dissolves, its PRs merge one at a time, and the activity feed
says batching needs a `uat/**` CI trigger. Batching is tried again a day later.
</Note>

## What you see

The merge train shows as one card per project: on the Flywheel page rail (all
projects, with filter chips) and on each project's Home (that project only).
Each card has:

- **A mode chip and a Train switch.** **Auto-merge** projects merge ready work
  on their own; **Holds for UAT** projects wait for you to test and merge a
  batch. The switch turns the train off for that project. When the train is
  off, a banner says no batches assemble and each ready PR merges on its own
  after the cooldown.
- **The current batch**, when there is one. It names its members and any
  held-out features with the reason, offers **Open UAT** (a live stack serving
  that exact branch), a per-feature **What to UAT** checklist, and **Merge
  batch (N) to main**.
- **Older batches**, one line each: "Older batch `uat/…` · superseded" or
  "· voided". **show** opens the full card and the reason it ended, for
  example "PAN-1 was merged on its own, outside the batch". Nothing is hidden.
- **Strike PRs** at the front of the train, with a pill for each: checks
  running, flagged by review (with the reviewer's summary), waits for UAT,
  merging, or approved, and a **Merge** button where a merge can start.
- **The queue**: "Waiting to merge (N)" in an auto project, "Not in a batch
  yet (N)" in a hold project. Each row has a status pill: cooling down with a
  countdown and **Cancel**, merging with the step it is on, blocked (with the
  first reason), last merge failed (with **Retry**), waiting for batch, or
  ready (with **Merge**). In an auto project with the train on, a line says
  when the next batch assembles. Expand a row for its branch, PR link, how
  long it has been ready, its merge policy, every blocker, the reviewer's UAT
  notes, and a nine-step merge tracker.
- **Recent merges**: "Last merged: PAN-… · 22m ago · show 5". The list says how
  each one landed: auto-merge, a batch, an Overdeck merge button, or outside
  the train. A PR merged outside the train is noted, never refused; when it
  beat its own scheduled auto-merge, the line says by how many minutes.

## How it works

1. **Assemble.** A 60-second reconciler builds a generation — a throwaway
   `uat/<label>-<codename>-<MMDD>` branch off `main` — merging each ready feature
   in order. When two features conflict, a timeboxed assembly agent resolves the
   conflict *inside the batch*; if it can't, that feature is held out (never the
   whole batch).
2. **Accumulate.** New ready features trigger a new, larger generation in the
   background. Generations accumulate — you can test and promote an earlier,
   smaller batch if the newest isn't what you want.
3. **Test.** Click **Open UAT frontend** to exercise the combined branch on a
   real running stack. The checklist pulls each feature's acceptance criteria,
   plus an explicit "verify the touchpoint" item wherever a conflict was resolved.
4. **Promote.** **Merge batch (N) to main** lands exactly the tree you tested —
   conflict resolutions included — in one merge. Each feature then closes out
   through the normal post-merge flow.

Unless the ready feature is held for UAT, a batch assembles only when **two or
more** features are ready. With exactly one, the page reads "1 feature ready —
merges directly; batches assemble when 2+ are ready": a one-member batch is the
PR branch itself and its CI run a duplicate, so that feature merges on its own
(Merge button or `gh pr merge`). A feature held for UAT (its issue's
`hold-for-uat` label, else the project's `auto_merge_default: hold`, else the
global require-UAT setting when the project sets no default) keeps a batch when
it is the only one ready, because that batch is the stack you test on.

**Each ready feature has one merge path.** Overdeck decides it with one rule,
first match wins:

1. A feature held for UAT (its `hold-for-uat` label, else the project's
   default, else the global setting) waits for a batch you test and merge.
   A hold always wins, even over priority. In a project that holds for UAT,
   that is every feature, so nothing reaches `main` until you merge a batch.
2. With the merge train off, every other feature merges on its own, five
   minutes after it is ready.
3. A high-priority PR (a strike, or `critical`, `blocks-main`, `P0`, `urgent`,
   or `substrate-improvement` plus `bug`) merges on its own.
4. A feature dropped from a batch because the batch's CI failed merges on its
   own.
5. Everything else, with the train on, waits for the next batch.

A feature set to **Auto** in a project that holds for UAT still waits for the
batch. Only its own **Merge** button, or **Merge alone…** on the batch, merges
it by itself, because a lone merge voids the batch you are testing.

**Merge from the row when you need to.** A **Ready** or **Waiting for batch**
row has its own **Merge** button, which merges that one feature through the
merge gate after you confirm. On a batch, **Merge alone…** on a member does the
same for a feature already in the batch; it voids that batch, and the
confirmation says so. **Rebuild** assembles a fresh batch at once, including
after a failed assembly.

**A failed assembly is named, not hidden.** After three failed attempts in a
row, the train stops retrying on its own. Failures more than six hours old no
longer count toward that limit, so the train recovers once the cause is fixed.
**Rebuild** tries again at once.

## Projects that span several repos

A polyrepo project — one where a single issue's work lands across several member
repositories — gets batch trains too, on the same terms as a single-repo
project. There is no separate setting: the merge-train flag is the only gate.

A batch there spans **one `uat/…` branch per member repo that a ready feature
actually touches**. Repos no feature touches are left alone entirely. The batch
still behaves as one unit:

- **A feature that conflicts anywhere is held out everywhere.** You never test a
  feature that landed in the API repo but not the frontend one — if it can't be
  merged cleanly in every repo it contributes to, it waits for the next batch.
- **Merging is all-or-nothing.** Overdeck first merges every repo locally,
  without publishing anything. Only once all of them succeed does it push. If
  any repo would fail, nothing is published at all and the batch stays exactly
  as it was.
- **An interrupted merge resumes instead of unwinding.** If a push fails after
  some repos already landed, Overdeck tells you which landed and which are still
  pending, and never rewrites a repo's `main` to undo one. Clicking merge again
  skips what already landed and finishes the rest.

The live UAT stack works the same way as for a single-repo project — one stack
per batch, serving all of its repos together.

## Live UAT stacks

Each generation can serve a live dashboard at
`uat-<codename>.overdeck.localhost`, spun on demand from the batch's worktree.
Overdeck runs **at most two UAT stacks at once** (Docker's network pool is
limited) and tears down the oldest when you start a third; promoting or
invalidating a batch always tears its stack down.

## Honest controls

Every action names its exact effect and confirms before anything happens —
"Merge batch (3) to main" lists the three issues and states that it lands the
tree you tested. **Merge alone…** on a batch member merges that one feature
now, which voids the batch; the confirmation names the batch, and its other
members wait for the next one. Merging a strike before its bot review asks
first too. There is no opaque "Ship batch" button: a batch builds itself,
and nothing reaches `main` until you say so.
