Overdeck is as much a tool for **managing conversations with agents** as it is a
workflow engine. Command Deck treats every agent session as a first-class
conversation: you spawn it, watch it work, talk to it mid-task, branch it to try
a different approach, and (when it nears the context wall or you want to switch
models) hand it off to a fresh conversation that inherits the context that
matters.

## The conversation surface

Each conversation has a live **Conversation** view and a **Terminal** view of the
same session. The conversation pane streams the agent's turns (reasoning, tool
calls, file reads and edits, command output) as they happen. Below it sits the
composer, where you type to steer the agent the way you'd pair-program with a
colleague.

| Control | What it does |
|:--------|:-------------|
| **Composer** | Send a message to the running agent mid-task: correct its approach, point it at a file, or tell it to stop and rethink |
| **Model picker** | Shows the conversation's model. In the dashboard, the model is fixed once a conversation starts; click the button to see why, and hand off to a new conversation to use another model |
| **Reasoning effort** | The `Thinking: <level>` button changes how hard the model thinks while the session runs (e.g. *Extra High*); see [Changing effort while a conversation runs](#changing-effort-while-a-conversation-runs) |
| **Conversation / Terminal toggle** | Switch between the rendered conversation and the raw terminal of the same session (the native CLI for OpenCode and Codex). Shown only while the session is live |
| **Copy link** | ⋯ → Copy link copies the `overdeck.localhost/conv/<id>` URL; ⋯ → Open in new window opens the conversation in its own window |
| **Context window meter** | See how much of the window is used, your cue that a handoff is coming |
| **Bookmarks** | Mark a message by clicking the icon beside it, then reopen the list from ⋯ → Bookmarks to jump back to it |
| **Citations** | Select text in a reply (or your own message), click **Cite** (or press `C`), add an optional comment, and it goes out with your next prompt |

### The header and status line

The first row of the conversation header holds the title, the Conversation /
Terminal toggle, and these buttons on the right:

- **Changes** shows how many lines the conversation added and removed (`+86 −1`)
  and opens the side panel on its Changes tab, with the **This conversation**
  chip selected. `Ctrl Shift G` (`⌘⇧G` on a Mac) shows or hides the same tab.
- **Files** opens the side panel on its Files tab. `Ctrl Shift E` (`⌘⇧E`) shows
  or hides it.
- **⋯** opens the conversation menu. A right-click on the header opens it too.
- A Pi conversation that is working also shows **Stop**, which stops the current turn.

Changes and Files open the panel for the conversation whose header you click.
They appear only when the conversation is a tab in the Command Deck; a popped-out
window, the phone app and the issue drawer have no side panel, so they do not
show them.

The second row is the status line. It says, in words and in this order: the
state (for example "Working"), the machine a linked conversation runs on, the
folder (with your home directory shortened to `~`), the branch and its pull
request, **N commits pushed**, **N commits not pushed**, **N files not
committed**, and the cost. The commit and file counts
show only in a Command Deck tab, and a count of zero is left out. In a Command
Deck tab the folder opens the Files tab, the commit counts open the Changes tab on
**This conversation**, and **N files not committed** opens it on **Not
committed**. In a detached checkout the branch reads **detached**. When the
checkout has no upstream branch, as in a detached checkout, a commit counts
as pushed when any remote branch has it.

The ⋯ menu lists, in groups:

1. **About this conversation**, **Bookmarks**, **Show tool calls** (on or off),
   and **Subagents** (with their count, only when the conversation has some)
   to show or hide the agents rail. The rail starts collapsed to a narrow
   **Agents** strip until you open it; the dashboard then remembers your
   choice in this browser. On a narrow screen, such as a phone, the rail
   opens over the conversation instead of beside it; tap outside it, or
   pick an agent, to close it.
2. **Open folder in** an editor, one item for each editor on this machine (a linked
   conversation lists the editors that work over remote SSH), **Copy
   conversation id** (the conversation's name), **Copy session id** (the agent's
   session id, shown only when it differs from the name), **Copy link**,
   **Open in new window**, and **Full diff in a new window**, which opens the
   [diff window](#reviewing-changes-in-the-diff-window) for the conversation.
   A linked conversation or a read-only vault copy does not show it.
3. **Favorite**, **Regenerate title**, and the pull request items.
4. **Hand off to new conversation**, **Create summary fork** (not for Pi),
   **Add skills…** (Claude Code and Codex), **Export transcript**, pulling the
   conversation here, **Continue on another device**, **Share**, and the
   handoff doc and target.
5. **Advanced** → **Delivery method** (Claude Code conversations only).
6. **Archive conversation** and **Stop the agent**.

`⌘⇧O` (`Ctrl Shift O`) still opens the conversation's folder in your favorite
editor while the menu is closed.

### The turn card

When a turn changes files, a card under the turn's last reply shows what
changed. A turn is everything from one message you send to the next one. The
card shows how many files changed, the lines added and removed (`+86 −1`), and
then, only when there are any: **N commits pushed**, **N commits not
pushed**, and **N not committed**. **N not committed** is the only amber tag,
because those edits are not saved in git yet. Below the header each file has
one row; the first eight show, and **Show all N files** shows the rest. A file
that the turn both committed and still has uncommitted edits shows once, as
not committed, and the `+/−` on the card adds up those rows.

Inside a Command Deck tab:

- **Review** opens the side panel's Changes tab on the turn's first file. `J`
  and `K` step through the turn's files, and the back arrow
  (**Back to the list**) shows the This conversation list.
- **Show in files** opens the Files tab with **Only what this conversation
  changed** selected.
- Click a row to open that file's diff. Hover a row for **Open the file beside
  the chat** and **Reveal in files**.

Outside a Command Deck tab (a popped-out window, a drawer or the phone app),
the card shows the same files and counts, and **Review** and the rows open the
[diff window](#reviewing-changes-in-the-diff-window). There is no side panel
there, so **Show in files** is not shown, and the row's beside and reveal
actions are greyed out.

### File paths in replies

A file path in a reply, or in a tool's output (for example "The file
/home/you/repo/src/app.ts has been updated."), shows as a chip. A path in
`code` formatting stays plain text. Inside a Command Deck tab,
when the path is inside the conversation's repository:

- a file the conversation changed opens its diff in the side panel;
- any other file opens beside the chat, at the line the path names;
- a Markdown file the conversation did not change opens where you last chose
  to open Markdown files.

Right-click a chip for **Open diff** (changed files only), **Open beside** and
**Reveal in files** at the top of the menu, followed by the usual editor,
browser, folder and copy items. Outside a Command Deck tab, and for a path
outside the repository, a click opens the file in your editor as before. The
path that a Read, Write or Edit row shows when you expand it is plain text;
the chip is in the tool's output.

### Sending to a busy agent

The composer's **Send** menu sets how your next message reaches an agent that
is busy with a turn. It reads `Send: <mode>`:

- **normally**: the message is delivered the usual way for this agent.
- **interrupt now**: the current turn stops and the message is sent at once
  (`Ctrl Enter`, or `⌘ Enter` on a Mac, does this for one message).
- **after this turn**: the message waits until the current turn ends. Pi
  conversations only.
- **when the limit resets**: the server holds the message until your usage
  limit resets. Shown only when Overdeck can tell when the limit resets.

The menu shows for harnesses that can steer (Claude Code and Pi); see
[Steering a running turn](/configuration/harnesses#steering-a-running-turn).
⋯ → **Advanced** → **Delivery method** is a different setting: it sets how
Overdeck types into a Claude Code session, not when the message arrives.

The effort button next to it reads `Thinking: <level>`, for example
`Thinking: high`. Hover it to see where the level came from.

On a conversation that has started, the model button cannot change the model.
Click it to see why: the model is fixed once a conversation starts, so hand
off to a new conversation (⋯ → **Hand off to new conversation**) to use
another model. An agent's
model is fixed when the agent starts.

A new conversation's effort is chosen with an effort picker next to the model picker, both on the Home composer and in the left column's **New conversation** caret menu. The **New conversation with options…** dialog (below) has its own effort field, which defaults to the effort the conversation would get anyway and shows where that default comes from, for example `Default: high (default)` or `Default: medium (project)`.

### Cancelling a message that is still sending

Messages you send go out one at a time, in order. While a message reads **Sending…** it has a **Cancel** link:

- A message still waiting its turn is never sent. If the composer is empty, the text goes back into it so you can edit it. If you have already typed something new, the text goes to the failed-message list below the conversation, marked **Cancelled**, with **Resend**, **Copy** and **Discard**.
- A message already on its way is stopped if the agent has not received it yet, and its text comes back the same way. If the agent already has it, the message says "Already delivered, can't cancel". If the dashboard cannot tell, it says "Couldn't confirm the cancel" and you can try again.
- A message waiting on a permission prompt, or one waiting for the server to reconnect, also has **Cancel**.

Messages sent to an agent's own session (not a conversation) can be cancelled only before they start sending.

### Changing effort while a conversation runs

Pick a level in the composer's effort picker while the session runs. For Claude
Code, Overdeck sends `/effort <level>` to the session and keeps the new level
only after Claude Code confirms it in the transcript; a session that is mid-turn
is refused, so try again when it is idle. While the change applies the picker
reads `Applying…`, and then it reads the level, such as `Thinking: high`. Hover
it to see where the level came from, such as `Source: default` or `Source: set`.
`terminal` means the session was changed with `/effort` in the native CLI. Claude Code also saves `low` through `xhigh` as the
default for your own new sessions of that model in `~/.claude/settings.json`;
Overdeck's sessions always launch with an explicit effort, so they are not
affected.

The model and harness picker spans the harness (Claude Code, Pi, Codex) and
every routed provider, each with live per-million pricing. It picks the model
for a new conversation (on the Home composer and in the **New conversation**
caret menu); once a conversation starts, the dashboard keeps its model fixed:

### Adding skills to a running conversation

To give a running conversation more pack skills, open **Add skills…** in the
conversation tab menu or the conversation header menu, or run
`pan skills add <conversation> --pack <id>`. A Claude Code conversation loads
them in place and keeps its context. A Codex conversation, and some packs on
Claude Code, must restart to load them; **Restart and load** (or `--restart`)
resumes the conversation with its history. An agent can add skills to itself
with the `add_skills` MCP tool; they arrive after its current turn. See
[Adding skills to a running conversation](/features/skill-packs#for-one-conversation)
for the outcomes and which packs need a restart.

### New conversation with options

**New conversation** in the left column is a split button:

- **The main part** is quick create. It starts a conversation at once in the
  selected project, with the model, harness and effort from the caret menu. No
  dialog opens. Press `N` anywhere outside a text field to do the same. A
  second line under the button names what it will spawn with: the model, the
  harness when it is not Claude Code, and the effort.
- **The caret beside it** opens a menu with the model and harness picker, the
  effort picker and the Retrospective button, which set the defaults for quick
  create, and **New conversation with options…**. The command palette has the
  same action.

The dialog sets options for one conversation. Nothing you choose in it changes
what the next quick create uses. Its fields are:

- **Project** and **Working directory.** The project starts as the deck's
  project. The working directory starts as the project path, and you can point
  it at any directory inside the project, such as a package in a monorepo.
- **Machine.** This machine (the default), **Auto**, a linked machine, or
  **Fly (new VM)**, which needs a project. On another machine, that machine
  picks the working directory from its copy of the project.
- **Model** and **Harness.**
- **Effort.** It lists the levels the model supports and starts at the default
  effort, with its source shown beside it. A model with no effort setting
  shows "Not supported by this model".
- **No context** starts the conversation without Overdeck's context: no
  bundled rules, no project or workspace layers, no session briefing, no memory
  injection on each prompt, and no resume message. It starts faster and costs
  fewer tokens per turn. The conversation still shows up in the dashboard with
  live activity, and resuming or forking it keeps it bare.
- **Skip CLAUDE.md** (Claude Code only) also turns off Claude Code's own
  memory: `~/.claude/CLAUDE.md`, project `CLAUDE.md` files and auto memory.
  Without it, a bare conversation still reads those files, because Claude Code
  loads them itself.
- **Skills.** Each skill shows the state it would inherit and an Inherit / On /
  Off choice. A choice applies to this conversation only, at every launch,
  resume, restart and fork. See [Skills](/features/skills).
- **Linked issue.** Search the issues the dashboard knows by identifier or
  title.
- **First message** (optional).

After **Create**, the dialog closes and the new conversation opens.

The conversation's first derived title leaves out any attached files; a first
message that only attaches files keeps the title "New conversation" until the
generated title arrives.

See [Bare conversations](https://github.com/eltmon/overdeck/blob/main/docs/CONTEXT-LAYERS.md#bare-conversations-no-overdeck-context)
for the full list of what is skipped and what keeps running.

### Starting from Home

Both Simple and Advanced Home carry a composer at the top of the page, so you
can start a conversation or a terminal without opening the Command Deck or
picking a project first:

- **Enter** asks the composer's current agent, exactly as typed, with no seed
  prompt and no project required.
- **Ctrl+Enter** (or choosing "Run in terminal:") opens the terminal drawer in
  the relevant deck and runs the typed text as a command in a fresh shell.
- **"Talk it through first:"** (Simple mode only) sends the same text through
  a discuss-then-file prompt: the agent asks clarifying questions and files an
  issue only once you say it's ready.

The composer's project chip lists every registered project, a **no project**
choice, and **Add a project…**. Choosing no project (or having none
registered yet) starts the conversation or terminal in your home folder
(`~/Projects` if it exists, otherwise your home directory) instead of blocking
you. In the Command Deck, that same no-project state is the **No project**
deck, always reachable from the **No project** item in the project switcher's
menu, and offered as
"Start without a project" when nothing else is selected. The app bar reads
**No project** when the No project deck is selected, never its internal key.

If a conversation ends up outside any project (started from Home before a
project existed, say), its pane shows a "Not in a project · Move to
project…" chip so you can attach it to a project later without losing the
conversation. To move any conversation to another project, open its row menu
in the left column and pick the project from **Move**.

### Native OpenCode CLI in Terminal

For an OpenCode conversation, **Terminal** attaches OpenCode's own interactive
CLI to the same running server and the same session, instead of showing the
Overdeck host log. What you type there and what you send from the composer land
in one session and one transcript; no second OpenCode server or session starts.
Dashboard messages still travel over the structured ACP connection, never as
keystrokes into this terminal. This works whichever terminal backend Overdeck
uses (Herdr or tmux).

Terminal has two panes for OpenCode:

| Pane | What it shows |
|:-----|:--------------|
| **Native CLI** | `opencode attach` running against the conversation's server and session. Overdeck opens it the first time you select Terminal and reuses it after that. |
| **Runtime log** | The conversation's own terminal, the Overdeck ACP host log that Terminal showed before. |

Switching back to Conversation, changing conversations, or closing the browser
tab leaves the native CLI running. **Close native CLI** stops only that
terminal; the conversation keeps running. Stopping, archiving, deleting, or
restarting the conversation also stops its native CLI.

A conversation started before Overdeck recorded the OpenCode server port shows
**Restart required for the native CLI**. Stop and resume the conversation to
attach; nothing restarts automatically. **Show runtime log** keeps the host log
available meanwhile. Codex conversations get the same two panes (next section);
other harnesses keep their existing Terminal view.

### Native Codex CLI in Terminal

For a Codex conversation, **Terminal** attaches the real interactive Codex CLI
to the conversation's own app-server and the same thread, with
`codex resume --remote`. You can type in it, run slash commands, and answer
approvals there, and the dashboard stays connected to the same thread over its
structured app-server connection. No second app-server or thread starts. This
works whichever terminal backend Overdeck uses (Herdr or tmux).

| Pane | What it shows |
|:-----|:--------------|
| **Native CLI** | The Codex TUI attached to the conversation's thread. Overdeck opens it the first time you select Terminal and reuses it after that. |
| **Runtime log** | The conversation's own terminal: the Overdeck app-server host log (`[turn] started`, `[stderr] …`) that Terminal showed before, with its line input and `y`/`n` approval shortcut. |

Both sides share one thread:

- A message typed in the native CLI is a turn in the conversation. It appears
  in the dashboard transcript and cost like any other turn, from the same
  Codex rollout.
- An approval shows in both places. Whichever side answers first wins, and the
  other side's prompt disappears.
- A model or effort you pick with `/model` in the native CLI stays in effect for
  the next dashboard message. Changing effort in the dashboard afterwards
  applies again from the next dashboard message.
- Esc in the native CLI interrupts the current turn, like the dashboard's stop
  button.

You can open Terminal while a turn is running or an approval is waiting. The
native CLI shows the running turn and the pending prompt. Switching back to
Conversation, changing conversations, or closing the browser tab leaves the
native CLI running. **Close native CLI** stops only that terminal; the
conversation and any running turn continue. Stopping, archiving, deleting, or
restarting the conversation also stops its native CLI. If the conversation's
Codex app-server stops on its own, Overdeck closes the native CLI too and says
so in Runtime log; restart the conversation to use Terminal again.

Sub-agents the conversation spawns belong to it: their approvals show in the
dashboard, and their activity and cost count toward the conversation.

`/new`, `/resume`, and `/fork` in the native CLI move only that terminal to
another Codex thread. The dashboard stays on the conversation's thread, and the
next time you open Terminal, Overdeck replaces the native CLI with one on the
conversation's thread.

When the native CLI is not available, Terminal says why and nothing restarts:

| Message | Meaning |
|:--------|:--------|
| **Restart required for the native CLI** | The conversation started before Overdeck exposed a native endpoint for it. Stop and resume the conversation. |
| **Upgrade required for the native CLI** | The installed Codex CLI is older than 0.153.4. Upgrade Codex, then stop and resume the conversation. |
| **Native CLI not available yet** | The conversation has no saved Codex turn yet. Send a first message, then select **Try again**. |
| **Native CLI unavailable** | For example, the conversation uses the legacy `codex.transport: tui`, where its own terminal already runs the Codex CLI. Terminal opens on **Runtime log** for these conversations, with Native CLI as the second tab. |

## Attachments

You can attach files to a composer message in three ways:

- **Paperclip button**: click the attach icon in the composer toolbar and select one or more files.
- **Drag and drop**: drop files directly onto the composer area.
- **Paste**: paste an image from your clipboard (screenshots, copied files, etc.).

Supported attachments include images (`png`, `jpg`, `gif`, `webp`) and text/code/PDF
files such as `md`, `json`, `ts`, `py`, `log`, `csv`, `yaml`, and `pdf`. Files are
uploaded to the conversation's private attachment folder,
`~/.overdeck/conversation-attachments/<conversation>/`, and the message the agent
receives refers to each one as `@<absolute path>`.

### Viewing images

Click an image thumbnail in the composer to open it full size, even while it is
still uploading. A sent message that includes an image shows a thumbnail under
its text; click it to open the image full size. Press Escape or click outside
the image to close it. If the file was removed, the thumbnail does not appear
and the path stays in the message.

### Vision gating

Image attachments are only sent to models that support vision. If you attach an
image while a text-only model is selected, the image is dropped with a clear
notice and any text/code/PDF attachments still go through. Switch to a
vision-capable model (for example, Claude Sonnet 5.5) to include images.

### File size and limits

- Maximum attachment size: **5 MB** per file.
- Maximum message length: **50,000** characters.
- Unsupported or binary file types are rejected at selection time with a toast.

## Citations

To push back on part of a reply, select the text (in an assistant message or
your own) and click the **Cite** button that appears over the selection (or
press `C` while nothing else has focus). Write an optional comment explaining
what's wrong or what to change, then save. The citation becomes a chip above
the composer; the quoted text stays highlighted in its row until the citation
is sent or removed.

Chips can be expanded to show the full quote and edit the comment, or removed
with the ✕. Citations persist across switching conversations and reloading the
page: they live in the browser, not the agent's transcript, so they survive
until you send or remove them.

On send, every pending citation is prepended to your prompt as a block:

```
Notes on your previous reply:
1. > First line
   > second line
   I don't agree
2. > Use X

Please revise.
```

Numbering follows add order; a quote with no comment gets no comment line. If
the send fails, the citations stay attached to the retry-outbox entry rather
than being lost; Retry resends the same block. Typing a slash command (for
example `/compact`) sends the bare command and leaves any pending citations
untouched. You can only cite settled message text, not tool output, plan
cards, choice cards, or a reply still streaming in.

Cite is offered only when the conversation has a composer: it does not appear
while the conversation shows the resume bar, is a read-only vault copy, was
cleared into another conversation, or is still forking.

### Citing a markdown file

When you open a markdown file from a file chip in a conversation, the editor
tab remembers that conversation as its origin. In the tab's **Preview**,
select text and click **Cite** (or press `C`) exactly as you would on a
reply. The citation becomes a chip in that origin conversation's composer,
labeled with the file name, and a toast confirms **Citation added** with an
**Open conversation** action that jumps back to it.

To browse and edit any file of a project, use the [file explorer](/features/file-explorer).

Cite is not offered in **Edit** (only in **Preview**), and not while the
file has unsaved changes (save first; the agent reads the file from disk, not
your draft). It is also not offered for a tab opened from somewhere other
than a conversation, since there is nowhere for the citation to go. Opening
the same file from a different conversation moves the tab's citations to
that conversation.

On send, file citations go out in their own block per file, after any reply
notes:

```
Notes on `/repo/docs/guide.md`:
1. > Step two
   > is wrong
   Swap the order
2. > Done.
```

The quote is the rendered Preview text, so markdown symbols (`**`, `#`, link
URLs) are not included.

## Bookmarks

Click the icon beside an assistant or user message to bookmark it, using its
first line as the label. The icon turns into a filled bookmark; clicking it
again opens a popover to rename or remove the bookmark. ⋯ → **Bookmarks** opens a list showing each bookmark's label and time; clicking
a label scrolls the timeline to that message and outlines it briefly.

Bookmarks survive reloads and new messages because they point at the
transcript message's stable id, not its position in the list. They are
stored by Overdeck and never written into the agent's own transcript, and
they stay with this conversation; a handoff or fork does not copy them. If
a bookmarked message is no longer in the loaded transcript, its row in the
list shows "This message is not in the loaded transcript."

## Scheduled runs

A schedule sends a stored prompt to a conversation on a recurring timetable,
for example every evening at 21:00. Overdeck keeps the schedule and fires it
from the dashboard, so it keeps working after the agent's session stops and
after the dashboard restarts. A harness's own wakeup or cron tools stop when
its process stops; a schedule does not.

```bash
pan conv schedule add self --daily 21:00 --prompt "Summarize today's merged PRs"
pan conv schedule list
pan conv schedule pause 3
pan conv schedule resume 3
pan conv schedule rm 3
```

`<conv>` is `self` (also `.`, `current` or `me`) when you run the command
inside a conversation, a conversation number (the `/conv/<n>` id), a name, or
a unique title match. Pass exactly one recurrence:

- `--hourly` runs on the hour.
- `--daily HH:MM`, `--weekdays HH:MM` (Monday to Friday) and `--weekly "mon 09:00"` use a 24-hour time.
- `--cron "<expr>"` takes a standard 5-field cron expression (`minute hour day-of-month month day-of-week`). Six- and seven-field patterns and nicknames such as `@daily` are refused.

Pass the prompt with `--prompt` or `--prompt-file`. The schedule runs in the
time zone given by `--tz` (an IANA zone such as `America/New_York`); without
it, the zone of the machine that creates the schedule is stored on the
schedule. Runs must be at least 15 minutes apart, so a frontier-model
conversation cannot be sent a prompt every minute. Add `--paused` to create a
schedule without arming it.

How a schedule fires:

- While the dashboard runs, a due schedule fires within a minute of its time. The prompt arrives with a `[Scheduled run · schedule <id> · <cron> · <zone>]` header so the agent knows why it arrived.
- If the conversation's session has stopped, Overdeck resumes it first, then delivers the prompt. The run uses the conversation's current model and effort.
- If the dashboard was down across several run times, the schedule fires once when it comes back, not once per missed time.
- A paused schedule never fires. Resuming it computes the next run from now, so it does not catch up on runs missed while paused.
- A schedule on an archived conversation is skipped and moves to its next run. Unarchiving does not trigger a catch-up run.
- A failed run (for example, the agent is waiting on a permission answer) is recorded and is not retried. `pan conv schedule list` shows the last outcome and error.

Agent conversations and Session Vault browse copies cannot be scheduled, and
a conversation can hold at most 20 schedules.

MCP clients and managed agents manage schedules with the `schedule_recurring`,
`list_scheduled`, `update_scheduled` and `delete_scheduled` tools; see
[MCP](/configuration/mcp).

Choose **Schedule…** from the row's overflow menu or the tab menu to manage a
conversation's schedules without the CLI. The dialog lists every schedule and
lets you create, edit, pause, resume, or delete one. Repeat offers Hourly,
Daily, Weekdays, Weekly, and Custom cron; Custom cron takes the same 5-field
expression `--cron` does, and editing a schedule always pre-fills Custom cron
with its stored expression so the raw cron is never lost on save. Time zone
is its own field, defaulting to the browser's zone for a new schedule;
editing a schedule keeps its stored zone instead of overwriting it with the
browser's, so an edit never silently shifts when the schedule fires.

A conversation with at least one active (non-paused) schedule shows a
next-run badge on its row, naming its active schedule count and the soonest
run time; a conversation whose schedules are all paused, or that has none,
shows no badge.

A delivered run also returns the conversation to Inbox: it clears any settle
or snooze, so a scheduled check-in is never buried in Snoozed or Settled.

## Why hand off?

A conversation accumulates context as it works: dead ends it already ruled out,
the file relationships it discovered, the half-finished approach it's mid-stride
on. When the context window fills up, that knowledge is the most expensive thing
to lose. A naive "summarize and continue" throws away the nuance.

A **handoff** is a deliberate context transfer. Instead of a passive summary, an
agent reads the conversation and writes a structured Markdown handoff document,
capturing the dead ends, the important files, and the suggested next steps, and
that document becomes the seed message for a brand-new conversation. The new
agent starts with a clean context window but inherits what mattered.

Reach for a handoff when:

- A long-running conversation is near the context wall.
- The current agent knows dead ends, hazards, or file relationships a passive summary would miss.
- You want a deliberate context transfer before switching models, harnesses, or tasks.

Use a plain **Fresh summary** when a quick passive summary is enough; use **Exact
copy** only when you need to carry the raw history verbatim within a
Claude-Code-compatible session.

## Continue: the three ways to start a new conversation

Open the dialog (titled **Continue in a new conversation**) from a
conversation's menu: **Hand off to new conversation** opens it on Agent
handoff, **Create summary fork** on Fresh summary. Or type
`/handoff` (optionally followed by focus text) in the composer to jump straight
to handoff mode. The dialog presents three intents, ordered richest to lightest:

| Intent | What it does | Best for |
|:-------|:-------------|:---------|
| **Fresh summary** *(recommended)* | An LLM distills the prior context into a seed message. For very large conversations the history is chunked, each chunk building on the previous summary. | Most cases: a clean, structured starting point |
| **Agent handoff** | An agent writes a Markdown handoff document, optionally focused on a specific next task, that becomes the seed message. | Deliberate handoffs where dead ends, key files, and next steps matter |
| **Exact copy** | Copies the raw conversation history from the last compaction point, with no summary. Only a Claude Code conversation can be copied, and the copy launches under Claude Code. | Picking up exactly where you left off, **same model only** |

The **Project** picker controls where the successor appears in the project tree,
independently of its working directory. It defaults to **Same as source**, so an
isolated handoff worktree stays associated with the source conversation's
project. Choose another registered project only when the successor belongs
somewhere else.

<Note>
**Fast summary** is an advanced toggle under *Fresh summary* that skips the LLM
and extracts a bullet list of user messages, files modified, and tools used
directly from the history. It is cheaper and instant, but rougher.
</Note>

<Warning>
**Exact copy** carries raw history that may contain model-specific data (such as
signed thinking blocks) that won't validate on a different provider. Use a
**summary** or **handoff** when switching models.
</Warning>

### Launch model vs. authoring model

Two model choices live in this dialog, and they are independent:

- **Launch model**: the model the *new conversation* will run on. Defaults to the parent conversation's model.
- **Authoring model**: the model that *writes the summary or handoff document*. Independent of the launch model; cheaper models like Haiku work well for straightforward cases, larger models for nuanced conversations.

## Progressive disclosure: Advanced options

The dialog keeps the common case to one screen. Everything else lives behind
**Advanced options**, which expands to reveal the authoring controls:

| Authored by | Behavior |
|:------------|:---------|
| **External session** *(default)* | A clean session reads the transcript from disk and writes the document. The source conversation is never touched: its context stays clean, and the source can even be ended. Pick the authoring model here; the dialog has no harness picker. |
| **Source agent** | The live source agent writes the document in-conversation. This adds the prompt and document to the source's context, and uses whatever model the source is running. Right when the source has live state (open files, recent commands, in-flight reasoning) that a transcript reader would miss. Offered only for a Claude Code source, and Continue stays disabled until the source conversation is running. |

If authoring fails (the document never arrives or fails validation, or the
authoring request errors), Overdeck falls back to a summary fork automatically,
whoever authors it. A missing authoring model is the exception: that handoff fails.

Under **Agent handoff**, a **Fresh start** checkbox sits beside Hold. Checking it skips authoring entirely: the Focus field relabels to "First message", the Authored-by controls disappear, and Continue creates a root conversation with no parent link whose first message is the focus text verbatim.

## Handing off from the CLI

`pan handoff` is the CLI form of the dialog's **Agent handoff**, including Fresh
start and Hold. Fresh summary is `pan fork <conv>`, and Exact copy is
`pan fork <conv> --plain`.

```bash
pan handoff [conv] [focus...]
```

The trailing text after the conversation reference becomes the **focus**, with no
flag required.

### Hand off the conversation you're in

If you're an agent inside a conversation and want to hand off *your own*
conversation, omit `<conv>` (or pass `self`). The command identifies your
conversation deterministically from the session you're running in, with no scanning
and no guessing.

```bash
pan handoff                               # hand off this conversation, no focus
pan handoff self wire the Stripe webhook  # hand off this conversation, with focus
```

Because focus text is positional, prefer the explicit `self` token whenever you
pass focus: a bare first word like `pan handoff continue the wiring` is read as
a *conversation reference* named "continue", not as focus. `self` removes the
ambiguity. Run `pan conv current` (alias `pan conv whoami`) to print exactly
which conversation you resolve to.

### Hand off a specific conversation

```bash
pan handoff 42
pan handoff source-conv continue the API wiring
pan handoff source-conv --model claude-sonnet-4-6
pan handoff source-conv --cwd ~/Projects/myapp/workspaces/feature-myapp-42
pan handoff source-conv --cwd ~/worktrees/isolated --project mind-your-now
pan handoff source-conv --author source uses-source-agent-and-pollutes-its-context
pan handoff source-conv --author external --author-model claude-haiku-4-5 cheap clean handoff
```

### Options

| Option | Description |
|:-------|:------------|
| `[conv]` | Conversation id or name. Omit (or pass `self`) to hand off the conversation you're in. |
| `[focus...]` | Positional focus text: what the successor should concentrate on. **≤ 10,000 characters.** |
| `--model <model>` | Model for the new (forked) conversation. Defaults to the parent's model. |
| `--effort <level>` | Reasoning effort for the new conversation (`low`, `medium`, `high`, `xhigh`, `max`). Defaults to the source conversation's effort, clamped to the new model. |
| `--harness <harness>` | Accepted and ignored with a printed notice: the new conversation's harness follows its model's provider. |
| `--cwd <path>` | An absolute path to an existing directory under your home directory and, except with `--fresh`, inside a git working tree. A project's primary checkout is refused: use a worktree, or pass `--allow-primary`. |
| `--project <key-or-name>` | Registered project for the successor. Defaults to inheriting the source conversation's project, even when `--cwd` points outside that project's directory. |
| `--allow-primary` | Operator only: allow `--cwd` to be a project's primary checkout. Refused for agent sessions. |
| `--issue <id>` | Issue ID to associate with the new conversation. Without `--cwd`, the new conversation starts in the issue's workspace when one exists. |
| `--role <role>` | Pane role for the new conversation: `conversation` (default), `work`, `review`, `test` or `plan`. With `--issue`, `review` makes the handoff the issue's Review row. |
| `--title <title>` | Title for the new conversation. Defaults to `Handoff: <focus>` (the first ~70 characters of the focus), or `Handoff: <source title>` without focus. |
| `--author <who>` | Who authors the handoff doc: `external` (default) or `source`. |
| `--author-model <model>` | Model for the external authoring session (only when `--author=external`). Falls back to `conversations.handoff_author_model` in `config.yaml` when omitted. There is no built-in default, so set one of the two or the handoff fails with a clear error. |
| `--author-harness <harness>` | Accepted and ignored with a printed notice; there is no authoring harness choice. |
| `--skill <name>` | Turn this skill on for the new conversation only (repeatable). `<name>` is a native skill name or a pack skill id `<pack>/<skill>`. Claude Code and Codex only; a Pi successor stores the values but never applies them. |
| `--pack <id>` | Turn on every non-opt-in skill of this cached skill pack, for the new conversation only (repeatable). Claude Code and Codex only; a Pi successor stores the values but never applies them. The values are a snapshot of the pack at creation. |
| `--group <name>` | Turn on every cached pack of this [pack group](/features/skill-packs#pack-groups) (for example `video`), for the new conversation only (repeatable). Each member pack that is not added or not cached is skipped with a note. |
| `--hold` | Create and launch the new conversation without sending the kickoff. Start it with Send in the dashboard composer, or `pan handoff start <conv>`. |
| `--fresh` | Start a clean conversation: no handoff document, no summary, no parent link. The focus becomes its first message. Project, cwd, model and effort still default from the source. Cannot be combined with `--author source` or `--author-model`; with `--hold` it needs focus text. |

<Note>
**Focus is hard-capped at 10,000 characters** (PAN-3737; multi-line is fine). `pan handoff` refuses a longer focus before anything is created; the dashboard API refuses it with `focus must be 10000 characters or fewer`. No
conversation is created. Keep it short and task-oriented: the detail belongs in
the transcript the author reads; the focus only steers what the author
emphasizes.
</Note>

### Holding a handoff

`--hold` creates and launches the successor's session without sending the
kickoff, so you can inspect it before it starts working:

```bash
pan handoff self --hold Read .pan/handoff-brief.md FIRST and follow it exactly.
```

The successor's dashboard composer shows a waiting notice with the kickoff
text already filled in; pressing Send there starts it. From the terminal, run
`pan handoff start <conv>` (id or name) instead; it sends the held kickoff
exactly once. A second `pan handoff start` on the same conversation, or one on
a conversation that was never held, exits 1 with "No held kickoff: the
conversation was already started or was never held".

If the held conversation's session ends before you start it, its page shows
a **Held handoff** notice that the kickoff was not sent, with the focus, the working directory, the
handoff doc and the kickoff text. **Start** there does the same as
`pan handoff start <conv>`: it relaunches the session and sends the kickoff.
Resume Session is not offered, because a resume would start the agent without
its kickoff. Held conversations, alive or ended, are listed in the **Feed**
tab on `/activity`, in the Needs you scope, under **Waiting** until you start or archive them; their **Open**
button takes you to the conversation.

### Starting fresh

`--fresh` starts a clean conversation that takes only the source's project, cwd, model and effort, not its context. No handoff document is authored, no summary is generated, the source transcript is never read, and the successor has no parent link (no `continues ← #<id>`). The focus is delivered verbatim as the successor's first message:

```bash
pan handoff self --fresh build a new Dwarf Fortress fort
```

This is the right tool for starting unrelated work from a conversation you're already in (for example, kicking off a fort-building session on a cheaper model from a research conversation) without carrying any of that context forward.

### Fallback behavior

`pan handoff <conv>` always tries to create a usable new conversation. If the
handoff can't be authored, Overdeck falls back to a summary fork and
prints the reason:

| Reason | Meaning |
|:-------|:--------|
| `source-ended` | The source conversation is already ended (source-authored handoffs only). |
| `handoff-timeout` | A source-authored handoff: the source didn't write both the document and its `.done` sentinel within 5 minutes. |
| `handoff-validation` | The document didn't satisfy the handoff contract, or the external authoring session never wrote it. |
| `handoff-request-failed` | Any other authoring failure, for example the external authoring session erroring or timing out. |
| `source-workspace-devcontainer` | The source can't write to the host handoff directory from inside a workspace container (source-authored handoffs only). |

A successful handoff prints the new conversation id, terminal session, model, effort,
harness, project (when set), issue, handoff document path and dashboard link. Fallbacks print the same
details plus a yellow fallback notice.

## Branch to explore

A handoff isn't only for the context wall. It's also how you **branch**. Fork a
conversation to try an alternative approach, keep the original intact, compare
both, and continue with the one you like. Cheaper than restarting from scratch,
and the original's context is never lost.

## What a conversation changed

The work dock's **Changes** tab lists the commits and uncommitted edits each conversation made.
Commits are tied to a conversation exactly by the `Overdeck-Conversation`
trailer that Overdeck adds to every commit a conversation makes. Older commits,
made before the trailer existed, are found from the `git commit` output in the
conversation's own shell.

Uncommitted edits are best effort. Claude Code conversations get per-line
attribution: when other sessions also changed a file, its row says how many of
its uncommitted lines came from elsewhere and names the conversations that wrote
them when those conversations were opened recently. Conversations on other
harnesses list the file only, with a note that line attribution needs edit
records, which only Claude Code writes. Edits made only through shell commands
are not shown.

A project's spend on its Home page now includes its conversations, and
"today" follows the clock of the machine the dashboard runs on.

## Pull requests on conversations

A conversation shows the pull request its work lives on. A badge next to the
branch chip, on the conversation row and in the open conversation's header,
shows the PR number, colored by state: blue
for open, amber when a review needs a human, green for merged, red for closed
without merging, and muted for drafts. A `×` marks failing checks. Hover it for
the repository, number, state, and title; click it to open the PR. `+N` means the
conversation has more than one linked PR.

Links come from **branch detection**. About 30 seconds after the dashboard starts,
and every 60 seconds after that, Overdeck reads each GitHub project's pull
requests once and links every PR whose head branch equals the branch a
conversation's working directory is on. Agent conversations whose workspace
cannot be read fall back to `feature/<issue>`. A conversation on the project's
default branch is never linked by branch. In the project's main checkout, which
every conversation there shares, an operator conversation is linked by branch
only while its terminal is running, so idle conversations never pick up the PR
of whatever branch the checkout is on. A merged PR stays linked after the
checkout goes back to the default branch. The same sweep refreshes the stored
state of linked PRs, so the badge renders without a live GitHub call. Open PRs
refresh on every sweep, closed PRs at most every 15 minutes, and merged PRs are
final and never re-read. A linked PR the project listing doesn't include (older
than the 100 most recent open and 100 most recent closed PRs it lists, in another repository, or on a conversation
outside any GitHub project) is read on its own. After three failed reads in a
row, Overdeck skips that repository for 15 minutes.

### Linking a pull request by hand

Open a conversation's actions (the row's `⋮`, the open conversation's header
`⋯`, or a right-click on the row, the header, or its tab) and choose **Link pull
request…**. Type a PR URL, a
GitLab merge request URL, `#42`, or `owner/repo#42`, then press Enter. `#42`
means PR 42 of the conversation's project repository. When the conversation
shows a PR, the same menu offers **Unlink #42**.

**Pull requests…** in the same menu opens a dialog that lists every PR linked to
the conversation. It shows why each one is linked (`manual`, `agent`, `created`,
`branch-detected`, or `unlinked`) and which one the badge shows. From there you
can link another PR, unlink or relink one, and refresh their status from the
forge.

In a transcript, right-click a pull request or merge request link and choose
**Link to conversation**. If that PR is the one the conversation shows, the menu
offers **Unlink from conversation** instead.

Agents and scripts use the CLI. `<query>` is the conversation name, or a title
fragment that matches exactly one conversation (`pan conv current` prints the
one you're in):

```bash
pan conv link-pr <query> <url|#42|owner/repo#42>   # --source agent|manual
pan conv unlink-pr <query> <url|#42|owner/repo#42>
pan conv prs <query> [--json]                      # * marks the PR shown
```

`link-pr` records the source `agent` when it runs inside an agent
(`OVERDECK_AGENT_ID` is set) and `manual` otherwise. The verbs go through the
dashboard, so every open client updates at once. With the dashboard down they
write the link directly. They exit 2 when no conversation matches or the match is ambiguous, and 1 on any
other error.

An Overdeck agent over MCP links a pull request with the `link_pull_request`
tool instead (source `agent`), and can watch it with `watch_pull_request` to
get a message here when its checks, review state, mergeability, or merged/closed
state changes. See [MCP server: Pull requests](/configuration/mcp#pull-requests).

Rules:

- Only a repository configured for the conversation's project can be linked:
  the project's `github_repo` or `gitlab_repo`, a URL-shaped
  `workspace.repos[].remote`, or the `origin` remote of the project checkout or
  of the conversation's working directory. Anything else is refused, and
  nothing is stored.
- A PR you link by hand wins over one found by branch detection.
- Unlinking hides the link, and branch detection won't add that PR back. Linking
  the same PR by hand again restores it.
- A new link fetches the PR's state within seconds, so it doesn't wait for the
  next sweep.

When the pipeline opens the pull request for an issue (`pan done`, or the review
pipeline), it links that PR to every agent conversation for the issue and every
conversation working inside the issue's workspace, with the source `created`.
Those conversations show the PR at once, without waiting for a sweep. The
pipeline never restores a PR you unlinked.

The other direction works too: an issue's **Code** card lists every conversation
linked to the issue's PR, with why it's linked (opened by the pipeline, linked
by hand, linked by an agent, or on the same branch). Click one to open it.

### Issue links

Clicking an issue link in a conversation transcript (a GitHub issue of a
registered project, or a Linear issue whose prefix belongs to a registered
project) opens that issue's drawer in the dashboard instead of leaving the
page. The drawer still opens old closed issues the dashboard no longer lists,
loading them on open. If the dashboard cannot load an issue, the drawer still
shows the Issue button that opens the link's tracker page. Ctrl/Cmd-click,
middle-click or the browser's right-click menu still open
the tracker in a new tab. Links to issues Overdeck doesn't track stay plain
links. This only applies to the main dashboard layout, which is the only place
that mounts the issue drawer; in a pop-out window (`/popout/conversation/<id>`,
`/popout/flywheel-conversation`) or the mobile app (`/m`), an issue link always
opens the tracker in a new tab.

### Conversation links

Inside a conversation transcript, text that names another conversation
renders as a link once the dashboard resolves it: a name (`20261113-6031`,
or `conv-20261113-6031`), a numbered form (`conv 3904`, `conversation 3904`,
`conv #3904`), or a `/conv/<id>` path, written as plain text, as the whole
value of an inline code span, or as a hand-written Markdown link. The link's
tooltip is the conversation's title, or its name when it has none. Fenced
code never links, and a name the dashboard can't resolve (or hasn't resolved
yet) stays plain text; archived conversations still resolve and link. The
conversation currently being viewed is never turned into a link.

A plain click opens the conversation in the dashboard, the same way clicking
its row in the left column does, with no page reload. Ctrl/Cmd-click,
middle-click and the browser's right-click menu open it in a new tab
instead. As with issue links, this in-dashboard behaviour only applies to
the main layout: in a pop-out window, the mobile app (`/m`), or the issue
drawer, a plain click opens a new tab too.

### On issue and workspace rows

The issue's row in the left column's Issues section (when you expand it), and
its row in the Workspaces section, show the same badge as a conversation's (the PR's number,
colored by state and review, with a `×` for failing checks), read from the
issue's derived state rather than a conversation's link. It appears within
seconds of `pan done` opening the PR. A PR that closed without merging is not
shown there.

**Auto-settle on merge.** When a linked PR goes from open to merged or closed,
and every PR still linked to the conversation is merged or closed, the
conversation is settled: it moves to the Settled section with the reason
`merge`. Its session keeps running, and nothing is archived or stopped. This is
on by default. Turn it on or off for every conversation with Settings →
Conversations → **Auto-settle on merge**, or with `pan conv auto-settle-on-merge`.
Override it for one conversation from the row or tab menu → **Auto-settle on
merge** (**Use global setting**, **Always**, or **Never**), or with
`pan conv auto-settle`:

```bash
pan conv auto-settle-on-merge          # prints on or off (default: on)
pan conv auto-settle-on-merge off      # or on
pan conv auto-settle <query>           # prints on, off, or inherit (global: on|off)
pan conv auto-settle <query> off       # on, off, or inherit
```

It happens once, at that change, so a conversation you unsettle stays in
Inbox. A conversation that is already settled keeps its reason, and one snoozed
until a later time keeps its snooze. Agent conversations are never
auto-settled (the pipeline owns them).

Not yet shipped (tracked in [#3822](https://github.com/eltmon/overdeck/issues/3822)):
GitLab merge request status, the Pull requests page, and search by PR number.

## Conversations from your other machines

Needs Session Vault set up on this machine
([Session Vault](/configuration/session-vault)).

Claude Code and Codex conversations that another machine saved to the vault appear in the
conversation list with a "from `<machine>`" chip. Hovering it reads "Read-only copy from
`<machine>`". Pipeline agents (work, review, test, planning and the other Overdeck agents)
saved on another machine appear there too, titled `<issue> <role> agent (<agent id>)`.

Opening one shows the transcript. The composer is replaced by "Read-only copy from
`<machine>`.", the command `pan vault resume <id>`, and a **Continue here** button.

**Continue here** opens a dialog titled `Continue "<title>"` that says "Saved on
`<machine>`." and where the conversation will continue. Cases, one sentence each:

- Code snapshot: it says which snapshot it applies here, or that the checkout has
  uncommitted changes so the snapshot goes into a new workspace.
- Drift: when branch, commit or dirty state differs, it lists the differences and offers
  **Continue**, **Continue with a note** and **Cancel**.
- No project: "No registered project matches `<slug>`." with **Clone and register
  `<slug>`**, which opens the Add project dialog.
- Another machine continued it first: "Already continued on `<machine>`." and nothing
  changes.
- A harness without native resume: the dialog shows the `pan vault resume <id>` command
  instead.

After it continues, the conversation opens on this machine as a normal conversation.

See [Session Vault: Continue on another machine](/configuration/session-vault#continue-on-another-machine)
for the CLI path instead of repeating it.

### Conversations that run on a linked machine

With a [machine link](/configuration/linked-machines), the conversations another machine
runs appear in the list live, with a chip naming the machine (tooltip "Runs on `<machine>`"), and open at
`/conv/@<environment-id>/<name>`. You control them as if they ran here; the title bar
shows which machine owns each one.

To move one to this machine, use **Pull here**, or the CLI:

```bash
pan conv pull @desk/conv-20261101-1234             # waits for a running turn
pan conv pull @desk/conv-20261101-1234 --stop-turn # stops it instead
```

It prints each step (`release`, `transfer`, `adopt`, `finish`) and then
`Pulled: /conv/<id>`; a failure prints the step, its code and the error, and exits 1. The
other machine keeps a read-only copy that says "Continued on `<this machine>`". When the
owner is offline it continues this machine's Session Vault saved copy instead.

If a conversation you released never ran on the other machine, take it back:

```bash
pan conv reclaim conv-20261101-1234          # refuses while the other machine runs it
pan conv reclaim conv-20261101-1234 --force  # even when the other machine cannot be asked
```

`reclaim` answers `still-running-there` while the other machine lists the conversation
live (pull it back instead) and `target-offline` when it cannot be asked.

## Reviewing changes in the diff window

Open ⋯ → **Full diff in a new window** to review everything a conversation
changed. The diff window opens beside the dashboard; it no longer opens as a
panel beside the chat. A turn card outside a Command Deck tab opens the same
window (see [The turn card](#the-turn-card)). Besides **All turns**, **vs
main** and the per-turn chips, the window has a **Compare…** view for any two
points in the conversation's repository. It works in a local-only repository
too: no remote and no pull request are needed.

**All turns** lists the files this conversation changed (its own commits and
the uncommitted files its edits touched, the same list as the Changes tab's
**This conversation**) and nothing other agents changed in the same
checkout; **vs main** and **Compare…** show the wider comparisons. A file
changed only through a shell command without a commit made by this
conversation is not listed under All turns. Opening a file under All turns
shows only this conversation's own changes to it, and its +/− counts are the
sum of those changes. When another agent changed the same file between this
conversation's commits, the file appears once per commit, headed by the
commit's short SHA and subject, and once more under **Uncommitted** for edits
not yet committed.

1. Click **Compare…**.
2. Pick a **base** and a **head**. Each box suggests branches, tags and recent
   commits, and accepts any ref you type, such as a SHA or `HEAD~2`.
3. Choose **A..B** to see every difference between the two, or **A...B** to see
   only the head's changes since the two diverged.
4. Click **Compare** (or press Enter), then pick a file to read its diff.

The selection is part of the window's URL, so you can bookmark it to come back
to the same comparison later.

The **ignore whitespace** toggle in the window header hides changes that only
re-indent or re-space lines, so a reformatted block no longer hides the real
change. It applies to the diff in every view, and the window remembers it in
this browser. A turn's file list can still name a file whose only change was
whitespace; opening it then shows no net changes.

When you pick a Markdown file, the bar above its diff shows a **Diff** and
**Preview** switch. Preview renders the document as text, as it is after the
change: the current file for All turns and a turn, and the committed file for
vs main. In Compare it shows the current file with the note "Showing the
current file", since Compare can point at an arbitrary ref the window cannot
read directly. A deleted file has no Preview. The bar's **Open file** action
is not available in the diff window; inside a Command Deck tab, use the turn
card's rows or a file path in the reply to open a file beside the chat.
Relative links in the preview show as plain text in the diff window, which has
no pane to open a file in; a link to a file that does not exist shows as not found.

## Settling and snoozing conversations

The conversation list groups rows into four sections, top to bottom: **Needs
you**, **Inbox**, **Snoozed**, and **Settled**. A group with any pending
question, plan-mode prompt, or approval request always shows in Needs you,
regardless of its stored settle or snooze state; the group returns to
Snoozed or Settled once the question is answered. Inbox has no header.
Snoozed and Settled each show a count and are collapsed by default; click
the header to expand.

**Settling** marks a conversation done for now without stopping it: the
session keeps running, and nothing about it changes except where it sits in
the list. This is different from [stopping or archiving](#stopping-or-archiving-a-conversation),
which end the session. Settle (and Unsettle) are available from the row's
checkbox, the row's overflow menu, and the tab menu.

**Snoozing** hides a conversation until a chosen time, after which it moves
back to Inbox on its own. There is no server timer and no dashboard restart
can lose or delay it, since the wake check runs on the client against the
stored time. Choose **Snooze** from either menu for presets (1 hour, this
evening, tomorrow morning, next week) or the date and time field under them, then **Snooze**, for any future date and
time; **Unsnooze** clears it early. A snoozed row shows when it comes back,
such as "back tomorrow 09:00".

Every settle, unsettle, snooze, and unsnooze shows a toast with an **Undo**
action, and `Cmd+Z`/`Ctrl+Z` undoes the most recent one while focus is
anywhere in the list (but not while typing in a text field).

Shift-click selects multiple rows; with a selection active, a bulk bar above
the list offers Settle, Unsettle, and Snooze for every selected conversation
in one action. In the left column, `Cmd`/`Ctrl`-click opens the conversation
beside the focused pane instead (see
[All projects and side-by-side conversations](/features/mission-control#all-projects-and-side-by-side-conversations)).

### Settling idle conversations automatically

The primary dashboard settles an operator conversation that has had no
activity for 3 days, the default. Activity is a new message in the
conversation's transcript, from you or from the agent, or a resume. Opening
or reading a conversation without resuming it does not count.

Some conversations are never settled this way: agent conversations, snoozed
conversations, conversations waiting on you (an open question, plan approval,
or permission prompt), and conversations continued on another machine. A
conversation with lanes or a successor is judged as one group, by the newest
activity anywhere in it, and only the top-level row is settled.

Unsettling or unsnoozing a conversation restarts the count, and so does the
end of a snooze. The check runs about every 15 minutes and does nothing while
the Deacon is frozen. After an upgrade, the first check settles every
conversation that has already been idle that long; **Unsettle** brings any of
them back.

Change the number of days in **Settings → Conversations → Auto-settle idle
conversations**, or with `pan conv auto-settle-idle-days <days>`. `0` turns
it off. Conversations also settle themselves when their pull requests merge
([PAN-4653](https://github.com/eltmon/overdeck/issues/4653)); see
[Pull requests on conversations](#pull-requests-on-conversations).

A [scheduled run](#scheduled-runs) delivering its prompt also clears any
settle or snooze on that conversation, so settling or snoozing never buries a
conversation past its next scheduled run.

## Stopping or archiving a conversation

Stop is the `X` on the row, "Stop agent" in the tab menu, or
"Stop the agent" in the conversation header menu; Archive is in the row menu, the tab menu, and the header menu ("Archive conversation"). After you stop
or confirm archive, the row dims and stops responding to clicks, and its
second line reads "Stopping…" or "Archiving…" (a nested row shows the label
after the title instead); the row's `X` becomes a spinner. The conversation
header shows the same status. The row stays dimmed until the conversation
list has refreshed. Then a stopped row shows its stopped (gray) dot, and an
archived row leaves the list with a toast reading `Archived "<title>"` and
its tab closes. On failure, an error toast shows the server's message and
the row returns to normal. Both end the session; settling (above) does not:
a settled conversation keeps running and can still be unsettled back to
Inbox.

## Resuming a stopped conversation

A stopped conversation keeps its row and its transcript. Resume starts its
agent session again on that transcript. Use the Resume button in the
conversation, or resume it from a shell or an agent:

```bash
pan conv resume 20261106-0913        # prints "Resumed 20261106-0913."
pan conv resume @desk/conv-a         # a conversation on a linked machine
pan conv resume 20261106-0913 --json # the resumed conversation as JSON
```

The `resume_conversation` tool of the [Overdeck MCP server](/configuration/mcp)
does the same. Both go through the dashboard's resume route and need the
`operate` scope. A conversation that still runs is reattached, not started a
second time. `pan conv resume` exits 1 on a refusal (for example, a
conversation that continues on another machine) and 2 when no conversation
has that name.

### After a terminal-backend restart

When the terminal backend restarts (a crash, an out-of-memory stop, or a
service restart), every conversation that ran in it stops. Overdeck does not
resume them by itself: relaunching many harnesses into a machine that just ran
out of memory can cause the same out-of-memory stop again.

Instead, Needs you shows one row in the System group: `<N> conversations
stopped when the terminal backend restarted`, with their names and a **Resume
all** button. Resume all resumes them one at a time. Before each one it waits
while the memory governor reports memory or CPU pressure, and the row says so
while it waits. Each resumed conversation is told that its process ended
unexpectedly, so it takes a turn to restart its timers and loops; the
flywheel resumes the way `pan flywheel resume` does. Resume all
skips a conversation that you paused with `pan pause`, that holds an unsent
`--hold` handoff kickoff, that continues on another machine, or that you
stopped or archived after the restart. When it finishes, the row lists any
conversation whose resume failed, so you can retry or resume it by hand.
**Dismiss** drops the row without resuming anything; during Resume all it
stops before the next conversation.

The offer lives in the dashboard's memory. A dashboard restart forgets it; the
conversations stay stopped and you can still resume each one. It covers
Herdr hosts, where the dashboard sees the backend's event stream drop and come
back. See [Terminal backends](https://github.com/eltmon/overdeck/blob/main/docs/TERMINAL-BACKENDS.md#after-a-session-server-restart-pan-5091) for the details.

After `pan shutdown`, the same Needs you row offers the sessions the shutdown stopped (`Resume the <N> sessions shutdown stopped`), and Resume all resumes those conversations, then the work agents.

## Search your conversations

The command palette (`⌘K` / `Ctrl+K`, or `⌘J` / `Ctrl+J` to open it on conversations; see [Command palette](/features/keyboard-shortcuts#command-palette))
searches conversation titles and transcript text. From the command line, `pan conv` searches a
separate catalog instead, built by scanning and enriching your sessions; see
[Search from the command line](#search-from-the-command-line) below.

### Find a conversation

Press `⌘J` (macOS) or `Ctrl+J` (Linux and Windows) to open the command palette with the
**Conversations** chip already selected (see
[Command palette](/features/keyboard-shortcuts#command-palette)). Each result is one row, labelled
by the conversation's title, or by the matching text when it has none, with the best-matching
excerpt highlighted. A row's chips show the project (and workspace), the issue id when the
transcript belongs to an issue workspace, where it came from (a named conversation, a Claude
session, or a subagent), the date, the role, the number of matching chunks when there is more than
one, and `archived` for archived conversations.

Results rank in three tiers, in this order:

1. **Title matches.** Every query term starts a word of the conversation's title.
2. **Text matches.** The query matched prose in the transcript.
3. **Path matches.** The query matched only inside code, inline code or a file path.

The **Newest first** button in the palette footer sorts results by date inside each tier; tiers
still come first. It is on by default, and your browser remembers the choice.

Choosing a conversation row opens it in the Command Deck and scrolls to the matching message; a
title-only match opens the conversation without one. Opening a subagent match opens its parent
conversation with that subagent selected. Results from a linked machine appear under a group headed
`On <machine label>` and open on that machine instead.

Text search covers only Claude Code transcripts, including subagent transcripts. Conversations on
other harnesses still match by title.

### Set up semantic search

Transcript text search is on by default, using OpenAI's `text-embedding-3-small` model. To set it up
or change it:

1. Add an OpenAI key under **Settings → Providers → OpenAI**, or set the `OPENAI_API_KEY`
   environment variable on the server.
2. Open **Settings → Conversations → Conversation Search** and check the key status.
3. Pick a model: `text-embedding-3-small` (recommended, &#36;0.02 per 1M tokens), `text-embedding-3-large`
   (higher quality, &#36;0.13 per 1M tokens), or `text-embedding-ada-002` (legacy, kept for existing
   indexes).
4. Run **Estimate & reindex all conversations** to index transcripts from before search was turned
   on, or after changing the model.

Without an OpenAI key, the palette returns title matches only: it finds no transcript text matches
at all, not even keyword ones, and new transcripts go unindexed. Changing the model runs a full
reindex, because vectors from one model cannot be reused with another.

Turn conversation search off with the card's switch, or in `~/.overdeck/config.yaml`:

```yaml
conversationSearch:
  enabled: true
  provider: openai
  model: text-embedding-3-small
  # apiKeyRef: OPENAI_API_KEY   # name of the env var that holds the key
```

With it off, indexing stops and conversation text hits drop out of the palette; title matches still
work.

### When search is not working

Conversation search shows a banner in the system notices row when it is enabled but cannot serve
queries, in one of three cases:

- **Missing key.** A `Conversation search needs an OpenAI API key` banner, with an `Add OpenAI key`
  button that opens Settings → Providers with the OpenAI key field ready to fill in. Until you add
  one, `⌘K` / `Ctrl+K` finds conversations by title only.
- **Recent embedding failures**, such as exhausted credits, billing or quota problems, or a network
  error. A `Conversation search is not working` banner names the reason, with an `OpenAI billing`
  link when the reason points to credits, billing or quota.
- **Transcript indexing is paused.** The watcher that indexes new transcripts has stopped. If
  restarts have also stopped, restart the dashboard or save the conversation search settings to
  bring it back; otherwise it keeps retrying on its own.

The palette has its own error states while a search is running: after 10 seconds without an answer
it shows `Search timed out after 10 s. Try again.`, and a failed request shows `Search unavailable`
with the reason, instead of an empty result list.

If none of this explains what you are seeing, ask in the
[Overdeck Discord](https://discord.gg/ZpHE2ZTv5P) or file a
[GitHub issue](https://github.com/eltmon/overdeck/issues).

### Search from the command line

`pan conv` works on a separate catalog from the palette: a **discovered sessions** table in
Overdeck's own database, built by scanning your Claude Code transcripts. Because of that,
`pan conv embed` does not change what `⌘K` / `Ctrl+K` finds, and the palette's own index does not
help `pan conv search --semantic` or `--similar`.

The usual workflow:

1. `pan conv scan` finds sessions and records them.
2. `pan conv enrich` writes an AI summary and tags for each one.
3. `pan conv search "<words>"` searches those summaries, tags and touched files.
4. `pan conv embed`, then `pan conv search --semantic "<text>"` or `--similar <id>`, for
   meaning-based search.

| Command | What it does | Main options |
| --- | --- | --- |
| `pan conv scan [dirs...]` | Scans `~/.claude/projects/` (default) and records sessions | `--watched`, `--system`, `--dry-run`, `--max-parallel <n>` |
| `pan conv enrich [ids...]` | Writes AI summaries and tags | `--tier <n>` (1 quick, 2 detailed, 3 deep), `--deep`, `--upgrade`, `--full`, `--with <model>`, `--prompt <text>`, `--limit <n>`, `--workspace <path>`, `--since <time>`, `--yes` |
| `pan conv search [query]` | Keyword search over summaries, tags and files; add `--semantic` or `--similar` for meaning-based search | `--workspace`, `--model`, `--since`/`--after`/`--before`, `--tag`, `--tool`, `--file`, `--issue`, `--semantic <query>`, `--similar <id>`, `--format table\|json\|brief\|ids` |
| `pan conv embed [ids...]` | Generates one vector per enriched session, needed for `--semantic` and `--similar` | `--status`, `--regenerate`, `--provider openai\|voyage\|ollama`, `--model <name>` |

`pan conv enrich` asks for confirmation when the estimated cost passes a threshold (&#36;1 by
default); pass `--yes` to skip the prompt.

The Settings → Conversations card also has a **Semantic embeddings** switch, off by default, with
**Embedding provider** (OpenAI, Voyage AI or Ollama), **Embedding model**, **Auto-embed after deep
enrichment** and **Test connection**. `conversations.embeddings` turns this on; with
`embedding_auto_on_deep` also on, it embeds a session right after a tier 2 or 3 `pan conv enrich`
run. The automatic embed also needs **Settings → Background AI → Session embeddings** on (off by default) and low-cost mode off. In `~/.overdeck/config.yaml` under `conversations:`, the matching keys are `embeddings`
(defaults to `false`), `embedding_provider` (`openai`, `voyage` or `ollama`), `embedding_model` and
`embedding_auto_on_deep`.

For keys: OpenAI uses the key saved in Settings → Providers → OpenAI, or the `OPENAI_API_KEY`
environment variable. Voyage has no Providers row; set `VOYAGE_API_KEY` in the environment instead.
Ollama needs no key. `pan` loads `~/.overdeck.env` before anything else, so a key stored there works
for every `pan conv` command too.

## Subagent activity and direct messages

Select a child in the conversation's agent rail to read its transcript. Active
children display “Working for …” with the same activity indicator as the main
conversation.

A bottom composer appears when the selected child supports direct messages.
For Codex, this requires a loaded child in a conversation running the structured
app-server transport. Messages go to that child's existing thread, with its
current model and permissions. Drafts are separate for each child.

Claude Code sessions, Codex terminal sessions, and unavailable children show the
transcript without a composer. Messages are never relayed through the main agent.
Existing Codex conversations need a restart after upgrading their host before
they can expose this capability. If delivery cannot be confirmed, check the
child's transcript before retrying.
