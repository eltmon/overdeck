When an xBRIEF plan splits into items that can run at once, the issue's own work agent acts as the foreman: it works a single linear chain of items itself, and dispatches parallel work only when a wave has more than one dispatchable item. There are two ways it can run that parallel work, described below. Neither is ranked over the other; which one an issue gets depends on how it was started.

## Foreman workers

### When workers are dispatched

With a single linear chain of items, the foreman works through them itself, one at a time. When a wave has more than one dispatchable item, it dispatches a worker for each one. This only serializes correctly when the plan's `files_scope` on each item is accurate, since overlapping scopes are what keeps two workers from racing the same files.

### Subagents and pan spawn panes

The foreman has two ways to dispatch a worker: a same-harness subagent running in-harness, or a separate pane started with `pan spawn` for another harness, or for work the operator should watch directly.

### Item worktrees and branches

A worker runs in its own item worktree, `<workspace>/.swarm/<item>/`, on a branch named `<feature-branch>-<item>`; an existing worktree for the same item is reused rather than recreated.

### How work comes back

Each worker commits once per item, with `Item: <id>` and one `Item: <id>.acN` line per acceptance criterion. Workers do not push, and they do not run `pan task done` or `pan done` themselves. The foreman integrates each item onto the feature branch, pushes it, runs `pan task done` for the item and its criteria, and runs `pan done` once at the end, after every item is integrated.

## Claims and overlapping files

`pan task claim` refuses to claim an item that a live agent already holds, or whose `files_scope` overlaps an item a live agent holds. An item whose `files_scope_confidence` is `low` refuses any concurrent claim at all. `--steal` overrides this, for the foreman or an operator only.

## Who can message a worker

Only the issue's own work pane, the worker's parent, or an operator conversation may send a message to a worker's pane.

## Gated slot swarm

A plan is eligible for the gated slot swarm when at least two items are slot-eligible and each one has a `files_scope`. A slot runs on its own branch, `feature/<issue>-slot-<N>`, in its own worktree.

`pan swarm <id>` starts or attaches the foreman; it does not dispatch slot work itself, and it prints that the foreman owns dispatch. The foreman is what drives slots forward, with `pan swarm dispatch`, `pan swarm wait`, `pan swarm merge` and the rest of the `pan swarm` subcommands.

Settings → Swarming holds the swarm policy for this mechanism: "Automatic selection" (Off, Auto, Always), "Maximum slots per issue", and "Advance waves automatically". A project's own "Automatic swarming" select (Inherit, Off, Auto, Always) overrides the global setting for that project.

## CLI
