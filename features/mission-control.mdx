# Mission Control

Mission Control is Overdeck's default landing view — a unified monitoring interface for all active projects, features, and AI agent activity. It includes **Shadow Engineering**, a companion mode for teams adopting AI-assisted development incrementally.

## Layout

The top bar spans the full window width. It starts with the Overdeck brand, which opens Home. Below it, Mission Control uses a two-panel layout:

- **Left column**: the project switcher, navigation, and the selected project's conversations, issues and workspaces
- **Main panel (right)**: Feature activity view, planning artifacts, and status reviews

## Left column

The left column is the same on every page. On the Flywheel page, in Settings or anywhere else, it still lists the selected project's conversations, issues and workspaces. Clicking a row opens it in the Command Deck. From top to bottom:

- **Project switcher.** It shows a colored initials mark, the project's name and its path (such as `~/Projects/overdeck`); every project row in the menu carries its own colored mark too. Its menu lists every project, grouped by owner, each with a status word: "2 working", "1 in review" or "idle". Below the projects are **No project**, projects on your other machines, **Add a project**, and **New workspace in** the selected project. With more than 8 projects, a filter box appears at the top of the menu. The dashboard remembers the last project you picked and restores it on a fresh load of a page that isn't already project-scoped (e.g. Activity).
- **Navigation.** **Project home** (shown only when a project is selected; it is the only one of the two current on a Command Deck tab, and only while the Home pane is active) and **Flywheel** (reads "running" during a run), **Order books**, and **More**. **More** holds every other view, grouped as Operations, Infrastructure, Observability and System — it no longer lists Command Deck, since Project home already opens the deck. Experimental views appear there only when experimental features are on.
- **New conversation.** The main part of the button starts a conversation in the selected project (key `N`). A second line under it names the default model, the harness when it is not Claude Code, and the effort it will spawn with. The caret opens a menu with the model and harness picker, the effort picker, the Retrospective button and **New conversation with options…**. See [Conversations](/features/conversations#new-conversation-with-options).
- **Conversations.** **Active** shows Needs you and Inbox. **All N** adds Snoozed and Settled. Each row has a meta line in words: its state, its changes (`+12 −3`, then "2 not committed"), the harness when it is not Claude Code, and its cost (never clipped mid-number). A conversation's successors and lanes are grouped under a toggle that starts collapsed unless one of them needs you; a collapsed group still shows the selected conversation's row.
- **Issues.** The header shows the issue count, the project's CI, deploy and identity chips, and a **Filter** menu: All, Alive or Failed, plus **Planned**. A collapsed issue row reads stage · model · progress, for example "Building · opus-4-6 · 3 of 7 items". Expand the row to see its badges, merge controls and sessions.
- **Workspaces.** This project's workspaces, then **Archived (N)**, and `+` for a new workspace. The section is hidden when the project has no workspaces.
- **Footer.** **Settings**, an icon-only **Machines** button (its title names the online count), the version (click it to check for updates; its tooltip says when Overdeck runs from a source checkout), **Rebuild** (only in a source checkout), the freshness indicator, and `?` for the keyboard shortcuts sheet.

With no project selected, the switcher reads "Choose a project" and the column shows "Pick a project to see its conversations and issues" instead of the lists. New conversation then starts a conversation outside any project.

The column is 264 px wide. Drag its right edge to resize it between 240 and 640 px. Press `[` to collapse it to 48 px, where it shows only icons. In a window narrower than 900 px, the column is a drawer: open it with **Open navigation** at the left of the top bar.

## Project Tree

The Issues section lists the selected project's active features. Each one shows:

| Element | Description |
|---------|-------------|
| Status indicator | Spinner if agent is running, circle if idle |
| Issue ID | PAN-123, MIN-456, etc. |
| State label | Idle, Planning, In Progress, In Review, Done, Has Context, Suspended |
| Pull request | The issue's PR number, colored by state and review; × marks failing checks; click to open |

State labels are computed from multiple signals: tmux session presence, heartbeat freshness (10-minute threshold), review/test status from the central `review-status.json`, and agent state files.

## Project home

The **Home** tab of a project deck opens with what you can do, then the facts about the project, then what needs you, then the pipeline and who changed main. The no-project deck shows only the title and the New conversation, Terminal and More actions.

**Header and metadata line.** The title is the registered project name, with a pencil to rename it and the GitHub (or GitLab) repository beside it. **Settings** opens the project settings in a dialog. Under the title, one line names the checkout path, the branch, the latest release, the default branch's CI state and, while they apply, an in-flight deploy and the GitHub identity the project acts as. The release word reads `v1.2.0 released 2h ago`, `releasing v1.2.0…`, `v1.2.0 release failed`, `no release runs yet` or `no releases`; click it to open the release detail (the workflow run, the GitHub Release, each npm package's `latest` dist-tag, and any partial failure with links to the failing jobs). The CI word reads `CI passing`, `CI failing`, `CI running 2/5` or `CI unknown`, and opens the run on GitHub.

Per-project release resolution lives in `projects.yaml` under `publish` (`npm_packages`, `release_workflow`), with inference fallbacks: the project root `package.json` name (when not `private`) and `.github/workflows/release.yml` (when present in the checkout). Projects with no publish pipeline say `no releases`. The surface is read-only — cutting a release stays in the CLI (`pan release stable`).

**Action row.** In order:

- **New conversation** (keycap `N`, the left column's shortcut) creates a conversation in this project with your default model, harness and effort. Its caret menu starts one in **Claude Code** or **Codex**, or opens **New conversation with options…**.
- **Files** (`Ctrl+Shift+E`, `⌘⇧E` on macOS) and **Changes on main** open the work dock on the project checkout.
- **Terminal** (`⌘T` on macOS) toggles the terminal drawer.
- **Open in &lt;editor&gt;** opens the checkout in your preferred editor, when one is installed.
- **Start an issue…** (projects with an issue prefix) takes an issue ID or a pick from this project's startable issues. A planned issue starts its work agent; any other issue opens the plan dialog. Guardrail warnings appear in the dialog with **Start anyway**.
- **More** holds **Web page**, **Main checkout** and **New workspace**.

**Facts.** Five numbers, each a link:

- **Agents working** counts every agent and conversation working in this project right now, by role (planning, building, reviewing, testing, conversations). It is the same number the project switcher shows. Click it for the Agents page.
- **Needs you** counts the items waiting on you in this project and shows the first one's question.
- **In review** counts the issues in the In review lane and names their pull requests.
- **Landed this week** counts first-parent commits on the default branch in the last 7 days (`500+` at the cap) and how many came through pull requests. Click it for the Changes dock.
- **Spend this week** is this project's spend for the week, conversations included, with today's spend below. It needs an issue prefix to scope the costs; without one it says so. Click it for the Costs page.

**Needs you.** When anything waits on you, an amber panel lists each item with its question and one action: **Answer** a waiting conversation, **Open** an issue, **Open Flywheel** for a parked Flywheel item, or **Decide** a decision.

**Pipeline.** One card with three lanes that always show their count, plus a fourth when needed:

- **Building** lists issues being planned or built.
- **In review** lists issues under review.
- **Ready to merge** lists approved, green issues held for your merge.
- **Stalled** (only when non-empty) lists issues with work on disk but no live agent and no activity for 14 days. A stalled issue appears in no other lane.

Backlog, queued and merged issues are not listed; **Open the board** shows them. Each row shows the issue ID, its full title, one tag (`needs you`, `blocked`, `stalled`, `planning`, `building`, `in review`, `changes requested` or `ready`), who is on it (the pull request and its checks for review rows, else the agent's model and item progress), and the time since its last activity. Hover a row for the stuck reason and the issue's spend; click it to open the issue. The project's merge train card follows the pipeline.

**Recent changes on main.** Who changed what: today's commits on the default branch when there are at least ten, else the last ten. Each row names the conversation or agent behind the commit, read from its `Overdeck-Conversation` / `Overdeck-Agent` trailers. Click a conversation row to open that conversation, or an agent row to open its issue; commits with no trailer show as `unattributed`. Click a short SHA to copy the full one.

Click a section header to view it full-screen. Press `Esc` or use the browser back button to return. The isolated view includes model display and a prominent keyboard hint.

## Decisions

Agents stop and wait for you: a question, a plan to approve, a permission
request, a rate-limit dialog, or simply a finished turn. **Decisions** is the one
place that lists all of them, whether they come from a pipeline agent, a
conversation, or the flywheel.

Anything waiting on you is marked wherever it appears. A node awaiting your reply
carries a pulsing amber indicator — click it to bring the dialog back, including
one you dismissed with `Esc` — and the whole issue row is shaded so you can spot
it without opening the tree.

The list separates **Blocking work** from **Waiting**. Blocking means the agent
has stopped until you answer, so it is burning wall-clock and nothing else will
move; waiting means work continues around your decision. Within each group the
oldest is first, since that is the one costing the most. Each row shows the
actual question rather than just its kind, so you can often decide without
opening anything. **Answer** re-opens the dialog for that subject.

Dismissing a dialog never removes its entry here — that is the point of the
surface. A dismissed question is still an open one.

The top bar's **Needs you · N** button counts the same things once each: every
question, plan, permission request, issue that needs you, Flywheel request and
system decision. The Home page's "Needs you" card shows the same number. Open
the button to see the items grouped by project, and use **Open Activity** for
system events. Each row in the menu shows how long the item has waited.

## Activity feed

The **Activity** page (`/activity`) opens on the **Feed** tab. It has three scopes:

- **Needs you**: everything waiting on you, with the same cards as Decisions.
- **Project**: activity for the selected project's issues and conversations.
- **Global**: activity across every project.

Within a scope, **All**, **Chats** and **Activity** narrow the feed. The page remembers the tab you last picked. The log streams (Activity Log, Detailed and TTS) appear as more tabs only when experimental features are on.

## Badge Bar

Quick-access badges appear below the feature header:

| Badge | What it shows |
|-------|---------------|
| Tasks | Opens beads task panel for the feature |
| STATE | Renders STATE.md from the workspace's `.planning/` directory |
| PRD | Renders PRD.md (grayed out if not generated) |
| Status | AI-generated progress review comparing code against PRD |
| Inference | Shadow Engineering inference document (only for shadow workspaces) |
| Discussions | Synced issue tracker discussions |
| Transcripts | Uploaded meeting transcripts |
| Upload | Attach transcripts or notes to the feature |
| Sync | Pull latest discussions from GitHub/Linear |

## Status Reviews

Click the **Status** badge to generate an AI-powered progress review. The review:

1. Gathers context: PRD, STATE.md, git diff, commit log, file changes, review/test status
2. Sends everything to the configured LLM (set via **Settings > Workflow Agents > Planning**)
3. Returns a structured analysis: summary, PRD coverage table, risk assessment, and recommendations

If no API key is configured, a static template with raw data is shown as fallback.

Any configured provider (Anthropic, OpenAI, Google, Kimi, Z.AI) can be used for status reviews.

## Shadow Engineering

### Concept

Shadow Engineering is for teams that want AI assistance without replacing their existing workflow. Instead of AI *doing* the work, AI *observes, documents, and assists*.

| Standard Mode | Shadow Engineering |
|--------------|-------------------|
| Planning agent creates PRD | Monitoring agent infers plan from artifacts |
| Work agent implements features | Observer watches human PRs and comments |
| AI drives the work | AI shadows the work |
| PRD.md generated | Inference Document produced |

### How It Works

1. **Enable Shadow Mode**: When creating a feature workspace, toggle "Shadow Engineering" on
2. **Monitoring Agent**: Analyzes available artifacts (issue description, tracker comments, meeting transcripts, PR descriptions) and produces an **Inference Document** — the AI's working understanding of what the team is building
3. **Inference Document**: Not a prescriptive PRD but an inferred understanding. Surfaces gaps, ambiguities, and risks. Updates as new artifacts arrive
4. **Observer Agent**: Watches the team's actual development. Comments on PRs with observations and suggestions. Only commits code when explicitly asked

### Value Proposition

> **AI that learns your team before it leads.**

Shadow Engineering lets existing engineers keep working their way while Overdeck's AI observes, documents, and assists. It learns the codebase, patterns, and team approach — so when you're ready to go further, the AI already understands how you build.

**Ideal for**:
- Teams wanting to adopt AI-assisted development gradually
- Organizations that need to maintain existing workflows during transition
- Leaders who want AI oversight and documentation without AI-driven changes
- Teams evaluating AI coding tools who need a low-risk entry point

### Shadow Workspaces in the UI

Shadow workspaces are visually distinct in Mission Control:
- Marked with a shadow indicator in the project tree
- Show the **Inference** badge instead of generating PRDs
- Inference modal includes an explanation of what the document represents

## Planning Artifacts

Each feature workspace has a `.planning/` directory:

```
feature-pan-XXX/.planning/
├── PRD.md                    # Product requirements (generated or manual)
├── STATE.md                  # Current progress notes
├── INFERENCE.md              # Shadow Engineering inference document
├── STATUS_REVIEW.md          # Latest AI-generated status review
├── transcripts/              # Uploaded meeting transcripts
├── discussions/              # Synced tracker discussions
└── notes/                    # Ad-hoc notes and documents
```

### Uploading Artifacts

Use the **Upload** badge to attach markdown or text files. Files are categorized as transcripts or notes and stored in the appropriate subdirectory.

### Syncing Discussions

Click **Sync** to pull the latest comments from GitHub Issues or Linear. Discussions are converted to markdown and stored in `.planning/discussions/`.

## Pipeline View

Where the project tree organizes work by project and feature, the **Pipeline** page reorganizes the same issues by lifecycle phase. A metric strip — Active issues, Work running, Review queue, Ship, and Spend — sits above phase-grouped rows (Ship, Review, Verifying), with a live activity feed on the right.

## Configuration

### Adding Projects

Projects are configured in `~/.overdeck/config.yaml`. Any project with active workspaces appears in Mission Control's project tree.

### Model Selection

The model used for status reviews is configured in **Settings > Workflow Agents > Planning**. See [Configuration](/configuration/projects) for details.
