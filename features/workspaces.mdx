Workspaces provide isolated development environments for each issue, enabling multiple agents to work on different features simultaneously without conflicts.

Each workspace is where an agent's conversation and its work live together: the dashboard's board surfaces every issue alongside the agent acting on it, so you manage the running conversations and the workflow from one place.

## Workspace kinds

A workspace is one directory that Overdeck tracks for a registered project. Every workspace has one of three kinds:

- **Issue**: one git worktree per tracked issue, at `workspaces/feature-<issue>` on the branch `feature/<issue>` (for example `feature/pan-123`). Planning, work and review agents run here. Overdeck's pipeline creates and removes issue workspaces, and most of this page is about them.
- **Scratch**: any number per project, not tied to an issue. A scratch workspace shares the project directory by default, or gets its own worktree on a `scratch/<name>` branch. Create one from the dashboard or with `pan workspace new`.
- **Main**: the project's primary checkout. A project has exactly one. Overdeck creates it when you add the project or the first time you open it.

Memory is kept per workspace, so a scratch or main workspace collects memory from the conversations that run in it. See [Workspace observation memory](/configuration/memory#workspace-observation-memory).

## What Are Workspaces?

**Workspaces are git worktrees** - isolated working directories for each issue/feature. Each workspace:

- Has its own feature branch, named `feature/<issue>` (e.g., `feature/min-123`)
- Shares git history with the main repo (no separate clone)
- Can run independently (separate node_modules, builds, containers)
- Is located at `{project}/workspaces/feature-<issue>/` (lowercase, e.g. `workspaces/feature-min-123/`)

This architecture allows multiple agents to work simultaneously without stepping on each other's toes.

## Why Workspaces?

**Without workspaces:**
- Only one agent can work at a time (shared working directory)
- Branch switching disrupts running agents
- Can't test multiple features simultaneously
- Risk of cross-contamination between issues

**With workspaces:**
- Multiple agents work in parallel on different issues
- Each has its own branch, dependencies, and containers
- Complete isolation - no shared state
- Clean, predictable environment per issue

## Architecture

```
project/
├── .git/                  # Shared git repository
├── src/                   # Main project (always on 'main' branch)
├── package.json
└── workspaces/
    ├── feature-min-123/   # Workspace for MIN-123
    │   ├── .git           # File pointing at the shared ../../.git
    │   ├── .overdeck/     # Workspace runtime state (plan copy, continue file, pipeline journal)
    │   ├── src/           # Feature branch code
    │   ├── node_modules/  # Independent dependencies
    │   └── docker-compose.yml
    └── feature-min-456/   # Workspace for MIN-456
        ├── .git
        ├── .overdeck/
        └── src/
```

## Git Worktrees

Git worktrees allow multiple working directories to share a single git repository. Benefits:

**Efficiency:**
- No need to clone the repo multiple times
- Shared git history and objects (saves disk space)
- Fast branch switching (just create a new worktree)

**Isolation:**
- Each worktree has its own checked-out branch
- Changes in one worktree don't affect others
- Can build/test multiple branches simultaneously

**Safety:**
- Can't accidentally checkout the same branch twice
- Main project stays on `main` branch (protected)
- Feature work isolated to dedicated worktrees

## Workspace Structure

```
workspaces/feature-min-123/
├── .overdeck/                 # Workspace runtime state
│   ├── spec.vbrief.json       # Working copy of the xBRIEF plan
│   ├── continue.json          # Item progress
│   ├── sessions.jsonl         # Agent sessions in this workspace
│   └── pipeline.jsonl         # Pipeline journal
├── .pan/                      # Committed planning artifacts (drafts/, specs/, continues/)
├── src/                       # Feature branch code
├── node_modules/              # Independent dependencies
├── package.json
└── docker-compose.yml         # Workspace-specific containers
```

### Planning artifacts

Planning writes its artifacts under `.pan/` in the project repo and commits them on the feature branch, so they travel with the branch. A polyrepo project can name one sub-repo as the plan home with `pan_records.repo` in `projects.yaml`.

- `.pan/drafts/<issue>.md`: the PRD draft
- `.pan/specs/`: the xBRIEF plan
- `.pan/continues/`: the continue files that record item progress

The workspace's `.overdeck/` directory holds runtime state: a working copy of the plan (`spec.vbrief.json`), `continue.json`, `sessions.jsonl`, `context.md`, `feedback/` and the pipeline journal `pipeline.jsonl`. Work items are xBRIEF items; agents claim and complete them with `pan task`.

## Docker Integration

Workspaces can have independent Docker environments, allowing:
- Isolated databases per feature
- Independent service configurations
- No port conflicts (unique project names)

### Starting Containers with Workspaces

```bash
# Create workspace and start Docker containers
pan workspace create MIN-123 --docker
```

**What happens:**
1. Creates the workspace (git worktree)
2. Looks for a compose file in the workspace root or `.devcontainer/`, and regenerates `.devcontainer/` from the project template when none exists
3. Runs `docker compose -f <compose file> up -d --build` without `-p`, so the compose file names the stack

**Docker Project Naming:**

`pan workspace create --docker` passes no project name, so Docker Compose picks it: the compose file's top-level `name:` field, else `COMPOSE_PROJECT_NAME`, else the name of the folder that holds the compose file. Overdeck's own stack lookups, such as stack health, read the same `name:` field or `COMPOSE_PROJECT_NAME` in the workspace's `dev` script, and fall back to `overdeck-feature-<issue>`.
- Example: a compose file with `name: myn-feature-min-123`
- Container names: `{compose-project}-{service}-1`

This prevents conflicts when running multiple workspaces simultaneously.

### Dashboard Integration

The planning dialog includes a "Start Docker containers" checkbox:
- **Default:** Off (planning agents don't need Docker)
- **Preference saved:** Your choice is remembered in browser localStorage

**Why this helps:**
- Containers start warming up while you review the issue
- Environment ready when planning agent starts
- Can test assumptions during planning without waiting

## Workspace Lifecycle

### 1. Creation

```bash
# Create workspace without Docker
pan workspace create MIN-123

# Create workspace with Docker containers
pan workspace create MIN-123 --docker
```

**What happens:**
1. Creates git worktree at `{project}/workspaces/feature-min-123/`
2. Creates and checks out the branch `feature/min-123`
3. Optionally starts Docker containers
4. Registers workspace in Overdeck registry

### 2. Usage

Agents work inside the workspace:
- **Planning agents** - Explore the codebase and write the PRD draft and the xBRIEF plan
- **Work agents** - Implement features, run tests, commit changes
- **Review and test agents** - Review the code and run the tests

All activity isolated to the workspace directory.

### 3. Cleanup

```bash
# Destroy workspace (uncommitted changes are discarded, so commit and push first)
pan workspace destroy MIN-123
```

**What happens:**
1. Stops the workspace's Docker stack (projects with a `workspace` block in `projects.yaml`)
2. Removes every worktree for the issue (base, strike and slot; limit with `--shape`) with `git worktree remove --force`, so uncommitted changes are lost
3. Deletes the local feature branch
4. Removes the workspace's record; `--purge-memory` also deletes its memory

After an issue's pull request merges, close it out with `pan close <id>` or the **Close Out** button; [Cleaning up after close-out](#cleaning-up-after-close-out) explains what that removes.

## Finding a workspace

- **Left column, Workspaces section**: the selected project's workspaces that you created, plus any you favorited. Favorites come first, then the most recently used. Issue worktrees, Session Vault workspaces and workspaces that agents created stay off this list unless you favorite them; reach issues from the **Issues** section and the Pipeline and Board views. The main checkout appears here only when you favorite it, labelled with the project's name. Archived workspaces leave the list. The section is hidden while the project has nothing to list, and in the All projects view.
- **A project's Home, More menu, Main checkout**: opens the project's main workspace and creates it the first time.
- **Cmd-K or Ctrl-K, Workspaces group**: the same workspaces for every project, plus every main checkout, shown under its project's name. Type to filter by name or project. Selecting one opens its view.

Rows in the Workspaces section show a short status. A main or scratch row shows the phase that Overdeck's memory gave it, such as `exploring`, `building` or `shipping`. A favorited issue row shows its pipeline phase and its pull request badge, colored by state and review, with `×` when checks fail.

The workspace view (`/workspace/<id>`) shows one workspace: its conversations and its memory (status headline, phase and recent observations). An issue workspace also shows the agent terminal while an agent runs, the xBRIEF plan and the verification gates.

## Creating a workspace from the dashboard

Open the **New workspace** page from any of these places. Each one opens `/workspaces/new`; the ones that belong to a project add `?project=<key>` so that project starts selected.

- The **+** in the left column's Workspaces header.
- **New workspace in** your project, in the project switcher menu.
- **New workspace…** in Cmd-K or Ctrl-K.
- **More**, then **New workspace**, on a project's Home.

The Workspaces section is hidden while a project has no workspaces to list, so use the project switcher there.

The page shows everything about the new workspace in one view:

- The **project chips** select a registered project. Recently used projects come first. The chip row can also open the **Add a project** dialog over this page (clone a repo, add an existing folder, or start a new project); a project you add there comes back selected.
- The large **workspace name** field (placeholder "Untitled workspace") is the name of the new workspace. Names allow letters, numbers and hyphens. As you type, it suggests what you probably meant:
  - An **issue reference** (`#12`, `PAN-12`, or a GitHub issue or pull request URL) offers **Open PAN-12 and start work**, which opens that issue's page. A bare `#12` or a GitHub URL uses the selected project's issue prefix; `PAN-12` works when `PAN` is a registered prefix.
  - Text that matches **branch names** in the selected project offers **Start from branch** for each match. Picking one sets it as the parent branch and opens **Advanced** so you can see it.
  - Text that cannot be a name as typed (spaces, punctuation) offers `Use "fix-login-redirect-bug" as the name`.

  The arrow keys move through the suggestions, Enter picks one, and Esc closes the list.
- **Shared directory** (the default) points the workspace at the project's primary path, another registered target, or a directory you choose with **Browse…**.
- **Isolated worktree** creates `workspaces/scratch-<name>` on a `scratch/<name>` branch, shown under the name as **Branch:**. It makes its own path, so the target controls are disabled.
- **Advanced** lets you override the parent branch. Without an override, Overdeck uses the project's current branch.

<Note>
  The status strip above the buttons shows the final path, branch, parent branch, git posture, and whether a worktree will be created, and it updates as you type. The server runs the same resolution for this preview and for the real create, so what the strip shows is what you get.
</Note>

That same resolution validates the name, the directory and the project, and shows any problem inline. With no projects registered, the page says **Add a project first.** **Start workspace** stays disabled until the problems are fixed and the status is current. When the workspace is created, Overdeck selects it and opens its view.

The page and `pan workspace new` (below) call the same code, so a workspace created either way is identical.

## Managing a scratch or main workspace

The header of a scratch or main workspace's view has three buttons:

- **Favorite** pins the workspace to the top of the Workspaces section. Press **Unfavorite** to undo it.
- **Relocate** points the workspace at a new directory after you confirm the resolved path. Relocating the main workspace also asks you to type its name, because it makes the workspace differ from the project's path in `projects.yaml`.
- **Archive** removes the workspace from the Workspaces section and Cmd-K. Its files, branch and memory stay on disk.

Issue workspaces show none of these, because Overdeck's pipeline owns their worktree. To remove an issue workspace by hand, use `pan workspace destroy <issueId>`; add `--purge-memory` to also delete its memory permanently. The workspace view has no delete button.

## Scratch and main workspaces from the CLI

`pan workspace new`, `main`, `get`, `activate`, `archive`, `relocate` and `list --kind` manage scratch and main workspaces. The older `pan workspace create` and `destroy` handle issue workspaces (see [Workspace Lifecycle](#workspace-lifecycle)).

```bash
# Create a scratch workspace that shares the project directory (the default)
pan workspace new my-scratch-notes

# --isolated creates its own git worktree on a scratch/<name> branch
pan workspace new my-experiment --isolated --parent-branch main

# --target-path points the workspace at any existing directory
pan workspace new vendor-lens --target-path ~/code/some-vendored-repo

# --dry-run prints the resolved intent as JSON and creates nothing
pan workspace new my-scratch-notes --dry-run

# Inside an Overdeck agent or conversation the default origin is agent, which
# keeps the workspace off the Workspaces section; --origin operator keeps it on
pan workspace new my-notes --origin operator

# Point a workspace (by id or name) at another existing directory
pan workspace relocate vendor-lens --path ~/code/moved-vendored-repo

# Resolve the project's main workspace, creating it if needed
pan workspace main

# Show, activate or archive a workspace by id
pan workspace get <id>
pan workspace activate <id>
pan workspace archive <id>

# List one kind; --archived includes archived workspaces and needs --kind
pan workspace list --kind scratch --archived
```

`pan workspace new` uses the project that owns your current directory, or the only registered project; pass `--project <key>` to choose another.

### Targeting and relocating

A workspace points at a directory, so more than one workspace can point at the same repository, and you can move a workspace later. The rules:

- `--target-path` and `--isolated` cannot be combined, because an isolated worktree already decides its own path.
- `pan workspace relocate` refuses issue workspaces, because the pipeline owns their path. It needs `--force` for the main workspace, because moving it makes the workspace differ from `projects.yaml`. The new path must be an existing directory.
- `pan workspace archive` refuses the main workspace.

Relocating never moves memory. A workspace's memory is stored by its id, not by its path or name.

## Cleaning up after close-out

**Settings → Close-out** controls what `pan close <id>` and the dashboard's **Close Out** button do to an issue's workspace and feature branch after its pull request has merged. The settings are saved to the `[close_out]` table in `~/.overdeck/cloister.toml`.

<ThemedImage
  light="/images/dashboard/close-out-settings-light.png"
  dark="/images/dashboard/close-out-settings-dark.png"
  alt="Settings Close-out section with the four controls, the closed-issue disk line, and the Clean up now button"
/>

| Control | Key | Default | What it does |
| --- | --- | --- | --- |
| Remove the workspace when an issue is closed out | `remove_workspace` | on | Stops the workspace's Docker stack and stray processes and removes the worktree. Branches and memory are kept. |
| Delete the feature branch at close-out | `delete_feature_branch` | off | Deletes the local and remote feature branch. |
| Close out merged issues automatically | `auto` | shown disabled | Not in effect. Automatic close-out was removed, and nothing reads this key. |
| Automatic close-out delay (minutes) | `auto_delay_minutes` | shown disabled | Not in effect, for the same reason. |

Below the first control, a line reports how many closed issues still have a workspace on disk and their total size. **Clean up now** runs `pan workspace destroy` (which also deletes the local branch) for each closed issue whose branch is merged and whose workspace has no uncommitted changes. Untracked files count as uncommitted. It lists each issue it removed, and each issue it skipped with the reason: a polyrepo project (destroy those by hand), uncommitted changes, a branch that is not merged, or a merge state it cannot read.

<Note>
  These settings apply to close-out only. Overdeck's closed-issue reaper also runs when an issue closes and on the Deacon's background patrol. For a closed issue whose branch is merged, or no longer exists, it removes the workspace and deletes the local and remote feature branch, whatever these two settings say. The patrol stops while the Deacon is paused (the dashboard then shows **Resume Deacon**), so closed-issue workspaces can pile up. The disk line and **Clean up now** cover that case. While GitHub reads are paused, the line says the count may be incomplete, and issues it cannot confirm as closed are not counted or removed.
</Note>

## Main Project Branch Convention

> **CRITICAL:** The main project directory must **ALWAYS** stay on the `main` branch. All feature work happens in workspaces.

**Why this matters:**
- **Review and test agents** need a stable reference point
- **Merge operations** require a clean target
- **Multiple agents** won't interfere with each other

**Wrong:**
```bash
# In main project directory
git checkout feature/min-123  # ❌ BAD!
```

**Right:**
```bash
# Create a workspace instead
pan workspace create MIN-123  # ✅ GOOD!
cd workspaces/feature-min-123
```

### Git Hooks for Branch Protection

Overdeck provides git hooks to enforce the main branch convention. These hooks are automatically installed:

- **On `pan project add`** - Hooks installed when registering project
- **On `pan sync`** - Hooks updated in all registered projects

**Auto-revert behavior:**
- **Agents & planning sessions**: Automatically revert to `main` if they accidentally checkout a feature branch
- **Human users**: Display prominent warning (no auto-revert by default)

To enable auto-revert for humans:
```bash
export OVERDECK_AUTO_REVERT_CHECKOUT=1  # Add to .bashrc/.zshrc
```

## Safeguards

### Planning vs Work Agent Safeguard

Planning refuses to start while a work agent (`agent-<issue>`) is running for the issue ("Cannot start planning: work agent already running"). A work agent refuses to start until the issue has a finalized xBRIEF plan with items.

To move from planning to work, accept the plan: the **Accept plan** action finalizes it (`pan plan finalize`).

To stop planning instead (neither of these finalizes the plan, so work stays blocked):
- **Abort Planning** in the planning dialog returns the issue to Todo and keeps the workspace.
- `pan kill planning-<issue>` stops the planning agent.

### Agent safeguards

Planning, work, review and test agents start with the issue workspace as their working directory, never the main project directory. The work prompt tells the agent never to check out another branch in its workspace. The post-checkout hook auto-reverts a checkout in the main project directory when it runs inside an Overdeck agent (`OVERDECK_AGENT=1` or `OVERDECK_AGENT_ID` set), a planning session, or a tmux session named `agent-*`, `planning-*` or `specialist-*`.

## Use Cases

**Feature Development:**
```bash
pan workspace create MIN-123
cd workspaces/feature-min-123
# Agent implements feature in isolation
```

**Parallel Development:**
```bash
pan workspace create MIN-123
pan workspace create MIN-456
pan workspace create MIN-789
# Three agents work simultaneously without conflicts
```

**Testing Multiple Approaches:**
```bash
pan workspace create MIN-123 --docker
pan workspace create MIN-123-alternative --docker
# Compare two implementation approaches side-by-side
```

**Emergency Hotfix:**
```bash
pan workspace create MIN-999-hotfix
# Fix doesn't interfere with ongoing feature work
```

## Best Practices

**Workspace Management:**
- Create workspace before starting work (don't checkout in main project)
- One workspace per issue (don't reuse for multiple issues)
- Clean up completed workspaces to free disk space
- Use `--docker` flag to warm up containers early

**Branch Naming:**
- Branches are named `feature/<issue>`, lowercase
- Example: `feature/min-123`
- Overdeck auto-generates appropriate names

**Docker Usage:**
- Use unique container names via project naming
- Clean up containers when destroying workspace
- Keep docker-compose.yml in workspace (not main project)

**Planning Artifacts:**
- The PRD draft and xBRIEF plan live under `.pan/` and are committed on the feature branch, so they move with the branch
- Item progress is kept in the continue file and updated with `pan task`
- The PRD is `.pan/drafts/<issue>.md`

## Remote workspaces on Fly

Overdeck supports remote workspace execution via Fly.io Machines. Remote workspaces provide cloud-hosted agent environments without local resource constraints.

### Why Remote Workspaces?

- **Resource isolation**: heavy builds and tests don't compete with your local machine.
- **On-demand provisioning**: machines spin up per workspace and are destroyed when the agent finishes and its branch is handed to review.
- **Same workflow**: the CLI and dashboard work the same for local and remote workspaces.

### Setup

```bash
# Initialize the Fly.io app for workspace machines
pan admin remote init

# Install flyctl and configure auth
pan admin remote setup

# Check Fly.io connection and machine status
pan admin remote status

# Show RAM/disk usage across VMs
pan admin remote resources
```

### Creating Remote Workspaces

Remote workspaces are created from the planning dialog (**Workspace Location**: **Remote (Fly.io)**) or the CLI:

```bash
# Create workspace with remote execution
pan workspace create MIN-123 --remote
```

The workspace is provisioned on a Fly.io Machine with your project's dependencies pre-installed. The agent runs in a tmux session on the machine.

To start the work agent on Fly directly, use `pan start` with `--remote`:

```bash
pan start MIN-123 --remote
```

On an already-planned issue this skips planning. Overdeck finds the plan in the local workspace, on the `feature/<id>` branch, or on the last-fetched `origin/feature/<id>`, and pushes the local `feature/<id>` branch before it creates the machine. On an unplanned issue, planning runs first, and the work agent that starts after planning finalizes runs on Fly, not locally. If remote workspaces are not enabled, that hand-off fails with a message that points at `pan admin remote setup`.

### When the Agent Finishes

Within about a minute of the agent writing `REMOTE_DONE`, Overdeck brings the branch into a local worktree, opens the PR, destroys the machine and starts review. You don't run any command. Ephemeral machines stop themselves about 5 minutes after Overdeck stops running. VMs never receive your SSH keys: git uses HTTPS with your synced `gh` token.

## Troubleshooting

**Workspace creation fails:**
```bash
# Check if worktree already exists
git worktree list

# Remove stale worktree
git worktree remove workspaces/feature-min-123
```

**Docker containers conflict:**
```bash
# Check running containers
docker ps | grep feature-min-123

# Stop conflicting containers
docker compose -p myn-feature-min-123 down  # the name: from the workspace's compose file
```

**Main project on wrong branch:**
```bash
# Go back to main
cd /path/to/project
git checkout main
```

**Disk space issues:**
```bash
# List all workspaces
pan workspace list

# Show merged branches still on disk, with sizes, then destroy them
pan workspace list --stale
pan workspace destroy MIN-123
pan workspace destroy MIN-456
```

Because each running workspace carries its own agents, conversations, and processes, parallel work also consumes RAM. The dashboard's Resources page (experimental: turn on **Settings → Experimental → Experimental features**) breaks down system memory by agents, conversations, and processes so you can see which workspaces are heaviest before deciding which to destroy.
