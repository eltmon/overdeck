Overdeck's skills system provides reusable workflows and best practices for AI agents.

The dashboard's **Skills** page (left column, More, System, Skills) lists every skill with its description and a global on/off switch, grouped as Core (locked on), Overdeck (`~/.overdeck/skills`) and Personal (`~/.claude/skills`, `~/.agents/skills`). Filter by name or description, or narrow the list with **All**, **Off**, **Core** and **Overridden below**. Skill packs are listed below the skills.

## What Are Skills

Skills are reusable, shareable workflows that encode best practices for common development tasks. They are:

- **Multi-harness** - `pan sync` installs them for Claude Code (`~/.claude/skills`) and for Codex and Pi (`~/.agents/skills`)
- **Shareable** - `pan sync` copies them to every harness skill directory it manages
- **Contextual** - Invoked with `/skill-name` in an agent's prompt
- **Best-practice-driven** - Encode proven workflows and checklists

Skills eliminate the need to repeatedly explain how to do common tasks. Instead of telling an agent "please review this code for security issues", you invoke `/code-review-security` and the agent follows the established workflow.

## Using Skills

Skills are invoked as slash commands, for example in Claude Code:

```
# In Claude Code:
/feature-work
/code-review-security
/bug-fix
/pan-help
```

When you invoke a skill, the harness injects the skill's prompt into the conversation, giving the agent detailed instructions on how to proceed.

## Creating Custom Skills

Skills are markdown files stored in `~/.overdeck/skills/`. Create your own with:

```bash
# Use the guided skill creator
/pan-skill-creator

# Or manually create a skill
mkdir -p ~/.overdeck/skills/my-custom-skill
cat > ~/.overdeck/skills/my-custom-skill/SKILL.md <<'EOF'
---
name: my-custom-skill
description: One line saying what the skill does and when to use it
---
# My Custom Skill

Brief description of what this skill does.

## When to Use

Describe when this skill should be invoked.

## Steps

1. Step 1 description
2. Step 2 description
3. Step 3 description

## Best Practices

- Tip 1
- Tip 2
EOF

# Install it for every harness
pan sync
```

**Skill anatomy:**

```markdown
---
name: skill-name
description: One line saying what the skill does and when to use it
---
# Skill Title

One-line description.

## When to Use

When to invoke this skill (triggers).

## Steps

1. Detailed step-by-step instructions
2. With specific commands or patterns
3. And expected outcomes

## Checklist

- [ ] Item 1
- [ ] Item 2
- [ ] Item 3

## Examples

\`\`\`bash
# Example command
\`\`\`

## Related Skills

- /other-skill - When to use instead
- /complementary-skill - Use together with this
```

Use `/pan-skill-creator` or `/claude-skill-creator` for guided creation.

## Skill Distribution

Skills can be distributed via:

1. **Project skills**: commit them to `.pan/skills/<name>/` in the project repo. See [Project skills](#project-skills).
2. **User-specific** - Store in `~/.overdeck/skills/` (installed for every harness by `pan sync`)
3. **Third-party skill repositories**: register them as a [skill pack](/features/skill-packs) with `pan skills pack add`; to publish your own, see [Authoring a skill pack](/guides/skill-pack-authoring).
4. **Overdeck's bundled skills** ship in `sync-sources/skills/` and reach every machine through `pan sync`.

### Project skills

Project skills live at `<projectRoot>/.pan/skills/<name>/` in the project's own repo. The catalog lists them last, so a project skill with the same name as a skill in `~/.overdeck/skills`, `~/.claude/skills` or `~/.agents/skills` is listed as that other skill instead. Project skills never appear on the global Skills page, only in that project's settings and its issues.

Overdeck copies `.pan/skills/<name>/` into `<workspace>/.claude/skills/<name>/` once, when the workspace manager creates an issue workspace (planning, the dashboard, swarm, or PR adoption). Two cases copy nothing:

- `pan workspace create` for a project with no `workspace:` block in `projects.yaml`: the CLI fallback does not copy project skills.
- An existing workspace: `pan workspace update`, `pan sync-main` and `pan sync` never copy project skills into it.

A target directory that already exists is never overwritten, and bundled skills are copied first, so a project skill with the same name as a bundled skill is skipped and the bundled skill wins.

Only Claude Code sessions whose working directory is the issue workspace see project skills: work agents, and a `pan handoff --issue` successor. Codex and Pi agents do not receive project skills, and a conversation started outside the issue workspace does not see them either.

### Syncing Skills

```bash
# Sync all skills to Claude Code (~/.claude/skills) and Codex/Pi (~/.agents/skills)
pan sync

# Verify sync status
pan sync --dry-run
```

The `pan sync` command:
- Copies skills from `~/.overdeck/skills/` to `~/.claude/skills` and `~/.agents/skills`
- Overwrites installed skill files you have not edited; a file you edited since Overdeck installed it is skipped and reported as user-modified (`pan sync --force` overwrites it)
- Removes manifest-managed skills from harness directories after their bundled source is removed
- Preserves files Overdeck did not install, except that in `~/.claude/skills` a file at the same path as a bundled skill file is overwritten and reported as adopted; when a bundled skill is removed, an installed copy you edited is reported instead of deleted
- Ignores empty bundled skill directories so they do not reappear in caches or harness targets

## Turning skills on and off

Every skill has an on/off state that you can set at three levels: a **global default**, a **project override**, and an **issue override**. A conversation can also carry its own values, the narrowest level of all. The narrowest level that has a value wins:

**conversation > issue > project > global > default (on)**

A skill with no value at any level is on. The global level is two-state: a skill is either on (no stored value) or off. Project and issue levels are three-state: a skill inherits the level above, or is set on, or is set off, so a project can turn on a skill that is off globally, and an issue can turn off a skill its project turned on.

Conversation values are set when the conversation is created, in the **New conversation with options…** dialog (see [Conversations](/features/conversations)), and later with [`pan skills add`](/cli/skills-commands#pan-skills-add), the `add_skills` MCP tool or **Add skills…** in the conversation menu; a running Claude Code conversation loads added packs in place. They are stored on the conversation row and applied at every launch, resume, restart and fork of that conversation. A conversation value for a pack skill (`pack/skill`) beats every level and every pack toggle, so a conversation can turn on one opt-in pack skill for itself. Core skills ignore conversation values too.

### Core skills are always on

The pipeline depends on these 11 skills, so they are always on and cannot be overridden at any level:

`pan`, `pan-done`, `pan-flywheel`, `pan-foreman`, `pan-plan`, `pan-start`, `pan-task`, `pan-tell`, `pan-worker`, `work-complete`, `write-xbrief`

### Where each level is stored

| Level | Stored in |
|-------|-----------|
| Global | `~/.overdeck/config.yaml`, under `skills.overrides` (`<skill>: false`) |
| Project | `~/.overdeck/projects.yaml`, under `projects.<key>.skill_overrides` |
| Issue | `<planHome>/.pan/skill-overrides/<ISSUE>.yaml`, committed in the plan home on its checked-out branch (normally `main`) and pushed to that branch's upstream; if the push fails, `pan skills set` prints `push pending: <reason>` and the commit stays local |
| Conversation | `conversations.skill_overrides` (JSON) in `~/.overdeck/overdeck.db`; the conversation's launcher rereads it at every launch |

Clearing the last override for an issue deletes its file and commits the deletion. Skills that exist only in a project's `.pan/skills/` directory are **project skills**: they appear in that project's settings and its issues, never on the global Skills page.

### From the CLI

```bash
# Every skill with its effective state and where it comes from
pan skills
pan skills list --project <key> --issue <id>
pan skills list --json

# Set a skill on, off, or back to inherit (global unless you pass a level)
pan skills set <skill> on|off|inherit [--project <key> | --issue <id>]
```

At the global level, `pan skills set <skill> on` clears the override, because on is the default. Setting a core skill, an unknown skill, an unregistered project, or an issue that no registered project owns fails with an error.

### From the dashboard

- **Skills page** (left column → More → System → Skills): every skill with a global on/off switch. Each row notes when projects or issues override it, and the **Overridden below** filter lists those skills.
- **Project settings → Skills**: one switch per skill, showing whether it launches in this project, with the source beside it (`on · global`, `off · this project`). Turning a switch back to the inherited value clears the override. The pin button stores the current value so a later global change does not change it here (`on · pinned here`); the reset button returns the skill to what it inherits. Skills you changed are listed first, with **Reset all**.
- **Issue view → Skills for this issue**: the same controls for one issue, in the issue view's **Skills** tab (the issue drawer and the Stage issue tab). It opens on every skill, with the skills this issue changed listed first; **Changed here** and **Off** narrow the list. The tab is hidden for an issue that no registered project owns.

### When changes apply

Overrides are resolved when Overdeck launches an agent. They apply to Overdeck-managed **Claude Code** and **Codex** sessions at their **next launch** (a fresh start or a resume). A running agent keeps the skills it launched with.

- Claude Code launches receive `--settings '{"skillOverrides":{"<skill>":"off"}}'`, which hides every copy of the skill by name.
- Codex launches get `[[skills.config]] name = "<skill>" enabled = false` entries in the agent's own `$CODEX_HOME/config.toml`.

Overrides and packs do not apply to Pi, other harnesses, remote (Fly) launches, or sessions you start outside Overdeck. A Pi conversation accepts the dialog's Skills choices and `pan handoff --skill/--pack`, but Pi never applies them. If the override step fails at launch, the agent starts with every skill and the launcher prints a warning. See the [Skill settings reference](/configuration/skills) for every config key.

`pan sync` still installs every skill everywhere; hiding happens per launch, and no skill files are copied, moved, or deleted.

## Skill packs

A **skill pack** is a third-party git repository of skills that Overdeck pins to one commit you trust and mounts into Overdeck-managed Claude Code and Codex launches. Pack skills are off until you turn them on, at the same global, project, issue and conversation levels as other skills. Overdeck never copies them into `~/.claude/skills` or `~/.agents/skills`. See [Skill Packs](/features/skill-packs) for the quickstart, the pack catalog, the trust model and each pack.

## Subagents

Overdeck ships five pipeline agent definitions, `pan-work-agent`, `pan-review-agent`, `pan-test-agent`, `pan-uat-agent` and `pan-merge-agent`, which `pan sync` installs into `~/.claude/agents/` and Cloister uses when it launches the matching specialist. It ships no general-purpose subagent templates.

### Code review

Overdeck ships no code-review subagents. A full review runs as the [review convoy](/features/convoys): four reviewers (correctness, security, performance and requirements) whose prompts live in `roles/review-*.md` and are inlined when the review starts, plus a review parent that combines their findings.

### Planning & Exploration Subagents

Overdeck ships no custom planning or exploration subagent files. Planning runs as the `plan` role (`roles/plan.md`), and any role that needs parallel read-only exploration uses Claude Code's built-in `Explore` and `general-purpose` subagent types, which inherit the parent session's model and provider routing. Custom `.claude/agents/` files with a pinned `model:` broke under CLIProxy-routed sessions; see the "Why no ambient subagents" section in `docs/ROLES.md`.

## Best Practices

**When creating skills:**
- **Be specific** - Include exact commands, not just concepts
- **Include examples** - Show concrete usage patterns
- **Add checklists** - Help agents verify completion
- **Cross-reference** - Link to related skills and guides
- **Test thoroughly** - Verify skills work end-to-end

**When using skills:**
- **Invoke early** - Start with a skill, don't switch mid-task
- **Follow fully** - Don't skip steps or customize on-the-fly
- **Report issues** - If a skill doesn't work, improve it
- **Combine wisely** - Some skills complement each other, others conflict
