# Skill Packs

## What a skill pack is

A **skill pack** is a third-party git repository of skills, such as [eltmon/skills](https://github.com/eltmon/skills), a fork of [mattpocock/skills](https://github.com/mattpocock/skills). Overdeck pins each pack to one commit you approve, caches that commit, and mounts the pack skills you turn on into each launch through the harness's own plugin system. Pack skills are never copied into `~/.claude/skills` or `~/.agents/skills`, so they cannot collide with Overdeck's own skills or leak into sessions you start outside Overdeck.

Operators also call skill packs **skill bundles**; these docs use "skill pack."

A skill pack lets you try a third-party skill collection for one project, one issue, or one conversation without installing it for every session on the machine. The pack stays pinned to one commit, so the skills inside it do not change under you until you choose to update. When you are done, `pan skills pack remove <id>` deletes the cached commit and every mount. See [Skills](/features/skills) for the native, per-skill on/off levels that pack skills share.

## Quickstart

```bash
pan skills pack add mattpocock --ref v1.2.3          # preview, then: Trust this commit? [y/N]
pan skills list --project myapp                      # pack skills show as off
pan skills set --pack mattpocock on --project myapp  # turn the pack on for one project
# start an agent or conversation in myapp, then type: /mattpocock:grilling
pan skills set --pack mattpocock inherit --project myapp   # turn it off again
pan skills pack remove mattpocock                    # unregister and delete the cache
```

Changes apply at the next launch; a running agent keeps the skills it launched with. See [When pack changes apply](#when-pack-changes-apply).

## How packs turn on and off

### Names: `pack/skill` and `pack:skill`

Overdeck names a pack skill `pack/skill`, for example `mattpocock/grilling`. You use that id in the CLI, the dashboard, and the override files. The agent sees the skill as `pack:skill` (`mattpocock:grilling`), because the harness namespaces plugin skills. Overdeck's own `grilling` and `mattpocock:grilling` can both be present in the same session.

### Turning packs and pack skills on

Pack skills are **off** until you turn them on. You can turn on a whole pack or single skills, at the same three levels as other skills:

```bash
pan skills set --pack mattpocock on                      # the whole pack, globally
pan skills set --pack mattpocock off --issue PAN-12      # off for one issue
pan skills set mattpocock/grilling on --project myapp    # one skill in one project
```

For a pack skill, Overdeck checks the levels from narrowest to widest. At each level, a value for the skill itself beats that level's pack toggle, and the first level with any value decides. With no value anywhere, the skill is off.

| Global | Project | Issue | Result |
|--------|---------|-------|--------|
| pack on | `mattpocock/tdd` off | — | `tdd` off (project) |
| pack on | — | pack off | every skill off (issue pack) |
| — | `mattpocock/grilling` on | pack off | `grilling` off (the issue level decides first) |
| `mattpocock/grilling` on | — | — | only `grilling` on |
| pack on | — | — | `setup-matt-pocock-skills` off (opt-in) |

**Opt-in skills** are skills that change files Overdeck owns, such as `setup-matt-pocock-skills`, which edits `CLAUDE.md`/`AGENTS.md` and writes tracker docs. The pack toggle never turns them on; only a value for that skill does.

## Trust and safety

### Adding a pack

```bash
pan skills pack add mattpocock https://github.com/eltmon/skills --ref v1.2.3
```

Overdeck fetches the repository, resolves the ref to a commit, reads the pack, and prints a preview before it writes anything:

```
Pack mattpocock
  Source       https://github.com/eltmon/skills @ v1.2.3 (6acc160)
  Adapter      claude-plugin
  License      MIT
  Skills       25 (1 opt-in: setup-matt-pocock-skills)
  Executables  skills/engineering/diagnosing-bugs/scripts/hitl-loop.template.sh, skills/engineering/wizard/template.sh
  Not applied  executables (2), project-mutating skills (1)
Adding a pack trusts this commit and enables nothing. Turn it on with: pan skills set --pack mattpocock on
```

Adding a pack trusts the resolved commit and turns nothing on. In a terminal, Overdeck asks `Trust this commit? [y/N]`. Without a terminal, pass `--yes`; otherwise nothing is written. The pack id must match `[a-z0-9][a-z0-9-]*` and cannot be a core skill name. Overdeck picks the adapter itself (the known-pack default, else `claude-plugin` when the repo has `.claude-plugin/plugin.json`, otherwise `plain`); pass `--adapter plain|claude-plugin|deft-readonly|gstack-runtime` to choose. A repository cannot register a pack by committing a file; only `pan skills pack add` can.

For a known pack (`mattpocock`, `pstack`, `gstack`, `deft`, `sageox`) the url is optional. Only `pstack` also has a default ref, so `pan skills pack add pstack` is enough; the others need `--ref`.

### What is not applied

Overdeck mounts skill directories only. If a pack also carries hooks, MCP servers, commands, agents, context injection, git hooks, or scripts, the preview and the dashboard list them as **Not applied**, and none of them reach the agent. Scripts inside a skill directory are copied with the skill but never run by Overdeck.

Runtime packs (gstack) are the exception: their scripts are mounted and run when you invoke a skill, after you trusted them at `add`.

### The trust model

- Adding a pack trusts one commit and turns nothing on. Without a terminal, `--yes` is required, else nothing is written. See [Adding a pack](#adding-a-pack).
- Every launch mounts exactly the trusted commit; `update` shows the preview again and moves the commit only after you confirm. See [Pinning, updates and forks](#pinning-updates-and-forks).
- A repository cannot register itself; only `pan skills pack add` can.
- Overdeck mounts skill directories only. Hooks, MCP servers, commands, agents, context injection, git hooks and scripts are **Not applied**; scripts inside a skill directory are copied but never run by Overdeck. See [What is not applied](#what-is-not-applied).
- Runtime packs are the exception: gstack runs its pack-mode setup once per trusted commit (at add, update or sync) and its scripts when you invoke a skill; the preview lists every script before you trust it. See [gstack](#gstack).
- The gstack browser runtime is a second, separate consent that lists every download and path it writes.
- Opt-in skills change files Overdeck owns or reach paid, cloud or push actions; the pack toggle never turns them on. See [How packs turn on and off](#how-packs-turn-on-and-off).
- A launch never touches the network: it mounts from the cache or skips the pack with a warning.
- Pack skills never land in `~/.claude/skills` or `~/.agents/skills`, so they cannot reach sessions you start outside Overdeck.
- Disclosures: the `sageox` and `gstack` pack rows show what leaves the machine.
  - SageOx: "SageOx records agent sessions on this machine. With uploads off (the default) Overdeck runs `ox` with the network off: nothing is sent. With uploads on for a project, redacted session transcripts and session metadata are uploaded to the SageOx cloud ledger for that repo, and `ox` may fetch team context. Requires the eltmon/ox build; see `pan doctor`."
  - gstack: "Runs gstack's bash and bun scripts from ~/.overdeck/packs/gstack; telemetry and update checks are off. Opt-in skills can send code to OpenAI (codex) or call paid or cloud APIs. The optional browser runtime downloads npm packages and Chromium into ~/.overdeck/packs/gstack/browser."
- Deft skills carry a host notice, and outside a Directive project Claude Code launches deny Deft's CLIs. See [Deft Directive](#deft-directive).
- `pan skills pack remove <id>` deletes the cache, every mount that holds the pack, dangling launch links, and Codex plugin caches.

## Pinning, updates and forks

### Pinning and updates

The registry stores the **ref** you asked for (a tag or a branch) and the **trusted commit** you approved. Every launch mounts exactly the trusted commit, even if the tag or branch moves.

```bash
pan skills pack update mattpocock            # re-resolve the ref
pan skills pack update mattpocock --ref v1.3.0
```

`update` prints the preview again with the skills added, removed, and changed since the trusted commit, plus any capabilities that are new. It moves the trusted commit only after you confirm. `pan skills pack list` shows when the ref has moved (`update available`); `--offline` skips that network check.

### Fork-first policy

Known packs come from operator-controlled forks under `github.com/eltmon/`. A fork lets the operator decide when upstream changes arrive, and it is the only place Overdeck-specific changes land (gstack pack mode, the `ox` host-managed mode). No agent opens issues, pull requests or comments on an upstream repository, or pushes to one; upstreaming fork changes is the operator's call. `eltmon/plugins` is identical to `cursor/plugins` and exists only for pinning control. `eltmon/gstack` carries pack mode and drifts from upstream quickly.

### Syncing a fork

| Fork | Upstream | Carries changes? | Sync | Then |
|---|---|---|---|---|
| `eltmon/skills` | `mattpocock/skills` | No | `gh repo sync eltmon/skills`; for a tag, push the upstream tag to the fork from a fork clone (`git fetch upstream --tags`, `git push origin <tag>`) | `pan skills pack update mattpocock --ref <tag>` |
| `eltmon/plugins` | `cursor/plugins` | No | `gh repo sync eltmon/plugins` | `pan skills pack update pstack --ref <commit>` |
| `eltmon/directive` | `deftai/directive` | No | `gh repo sync eltmon/directive` (default branch `master`) | `pan skills pack update deft --ref <ref>`, then `pan skills deft status` |
| `eltmon/gstack` | `garrytan/gstack` | Yes: pack mode | merge in a fork clone, see below | `pan skills pack update gstack` |
| `eltmon/ox` | `sageox/ox` | Yes: host-managed mode | rebase `overdeck/host-managed` in a fork clone; branch ledger in [docs/SAGEOX-FORK.md](https://github.com/eltmon/overdeck/blob/main/docs/SAGEOX-FORK.md) | rebuild `ox` at the new commit, `ox host-contract --json`, `pan skills pack update sageox --ref overdeck/host-managed`, `pan doctor` |

Never run `gh repo sync --force` on `eltmon/gstack` or `eltmon/ox`; it hard-resets the branch and deletes the fork's own commits.

### Syncing the gstack fork

1. In a clone of `eltmon/gstack` with an `upstream` remote for `garrytan/gstack` (fetch only), run `git fetch upstream` and create a branch from `origin/main`.
2. `git merge upstream/main` and resolve conflicts, keeping pack mode.
3. Run the pack-mode tests: `bun test test/pack-mode.test.ts test/pack-browser.test.ts test/pack-browser-guards.test.ts test/pack-env.test.ts test/state-root-parity.test.ts`.
4. Check that a render writes nothing to `HOME`: make three empty temporary directories (home, render, state), run `HOME=<home> bash setup --pack-root <render> --pack-state-root <state>` from the clone, then `ls -A <home>` must print nothing.
5. Push the branch and open a pull request inside the fork: `gh pr create --repo eltmon/gstack --base main`. Merge it.
6. `pan skills pack update gstack`. The preview shows added, removed and changed skills. A skill the new commit adds is not mounted until the skill map in `src/lib/skill-packs/gstack.ts` is reviewed (see [docs/SKILL-PACKS.md](https://github.com/eltmon/overdeck/blob/main/docs/SKILL-PACKS.md)).

### When upstream is fine

Any url works, and pinning already protects you: the trusted commit does not move until you confirm an update. Registering `mattpocock` from `https://github.com/mattpocock/skills` or `pstack` from `https://github.com/cursor/plugins` works the same way. gstack and SageOx need their forks: upstream gstack commits fail the pack-mode check, and the `sageox` pack needs an `ox` built from `eltmon/ox`.

## Packs

### Matt Pocock's skills from a fork

Overdeck's default source for the `mattpocock` pack is the operator-controlled fork `eltmon/skills`, pinned to the `v1.2.3` commit. A fork lets the operator decide when upstream changes arrive: sync the fork on GitHub, then run `pan skills pack update mattpocock --ref <tag>` to preview and re-pin. Any url works here; `KNOWN_PACKS` applies the `mattpocock` defaults by pack id, not by url.

`setup-matt-pocock-skills` is opt-in: turning the pack on never turns it on. Only `pan skills set mattpocock/setup-matt-pocock-skills on [--project <key>|--issue <id>]` does.

```bash
pan skills set --pack mattpocock on                              # global: on
pan skills set --pack mattpocock off                             # global: undo

pan skills set --pack mattpocock on --project <key>               # project: on
pan skills set --pack mattpocock inherit --project <key>          # project: undo

pan skills set --pack mattpocock on --issue <id>                  # issue: on
pan skills set --pack mattpocock inherit --issue <id>              # issue: undo
```

### pstack

`pstack` is poteto's (Lauren Tan's) skill pack for Cursor — `principle-*`, `unslop`, `tdd`, `architect`, `poteto-mode`, and more — mounted from the operator's fork `https://github.com/eltmon/plugins`, pinned to `ae5650f`. Overdeck mounts Cursor's generated Claude Code build at `harness/pstack/claude-code`, not the Cursor source tree; the `KNOWN_PACKS.pstack` entry carries that subfolder as its `pluginRoot`, so the manifest, skill scan, and capability probes all read from inside it. Re-pin with `pan skills pack update pstack --ref <commit-or-branch>`.


```bash
pan skills set --pack pstack on --issue <id>                  # issue: on
```

Most pstack skills set `disable-model-invocation: true`, so the agent picks them up only when you invoke them directly, e.g. `/pstack:principle-laziness-protocol`.

Seven skills are opt-in — turning the pack on never turns them on:

- `setup-pstack` — writes `~/.claude/rules/pstack-models.md`, which every Claude Code session on the host loads, including sessions outside Overdeck.
- `automate-me` — writes a personal mode skill, then commits and opens a PR.
- `reflect` — copies a skill folder into a skills dir and edits it.
- `create-verification-skill`, `create-formal-verification-skill` — write a project-local skill under `.cursor/skills/` → `.claude/skills/`, an Overdeck sync target in workspaces.
- `maintain-verification-skill` — opens at most one PR of proven corrections.
- `make-bot-ui` — builds a webhook UI for a Grok bot and exposes it on Tailscale.

The mount also copies the plugin's `docs/` and `README.md` next to `skills/` (`KnownPack.mountExtras`), so the skills' link to the Claude Code adapter doc (`docs/harness/claude-code.md`) resolves instead of dangling.

A few pstack skills name Cursor model ids (`arena`, `architect`, `setup-pstack`); the adapter doc maps e.g. `claude-opus-5-5-xhigh` to `model: "opus"` with effort `xhigh` and runs `grok-*`/`gpt-*` roles on the session model. pstack's defaults spawn subagents at `xhigh`; the opt-in `/pstack:setup-pstack` can lower the budget.

`agents/` is not applied, so `poteto-mode`'s delegations to `pstack:poteto-agent` and `pstack:comment-sicko` fall back to `general-purpose`. `poteto-mode`'s shipping and babysit playbooks open and merge PRs with `gh` and run `scripts/watch-pr/watch-pr`; Overdeck never runs these scripts, and inside an Overdeck issue the pipeline owns PRs and merges.

Codex receives the same Claude Code build; the fork has no Codex-specific build.

### gstack

[gstack](https://github.com/garrytan/gstack) is Garry Tan's skill collection. Its skills call gstack's own bash and bun scripts by absolute path and keep state in a directory of their own, so Overdeck cannot mount them like other packs, and a normal gstack install writes `~/.claude` settings, harness skill dirs and `~/.gstack`. Overdeck uses the operator's fork [eltmon/gstack](https://github.com/eltmon/gstack), which adds a **pack mode**: `bash setup --pack-root <render> --pack-state-root <state>` copies the skills and their runtime into a directory Overdeck chooses, rewrites every skill to call scripts there, keeps all gstack state in a second directory, and writes nothing else. It never runs `bun install` or a build, never writes `~/.claude` or `~/.gstack`, and never calls the network. An optional second step builds the browser runtime ([below](#browser-design-and-pdf-skills)). The `gstack-runtime` adapter runs pack mode once per trusted commit and mounts the skills from its output.

#### Adding gstack

gstack needs [bun](https://bun.sh) on `PATH`.

```bash
pan skills pack add gstack https://github.com/eltmon/gstack --ref main
```

Before it asks, Overdeck checks that the commit has `pack-mode.json` and that bun runs. The preview shows the command trusting runs, every script the mounted skills can run (one per line, never shortened), and the skills it will not mount. Shortened here with `…`:

```
  Adapter      gstack-runtime
  License      MIT
  Skills       36 (14 opt-in: autoplan, benchmark-models, captain, careful, codex, cso, document-generate, document-release, eval-plan, freeze, guard, modernize, ubicloud, unfreeze)
  Not mounted  27: benchmark (Needs the browser runtime: pan skills pack browser gstack on); …

  Not applied  hooks, agents, project-mutating skills (14), requires CLI (bun)
  Requires     bun
                bin/gstack-config

Adding a pack trusts this commit and enables nothing. Turn it on with: pan skills set --pack gstack on
```

#### Browser, design and PDF skills

The `browser` and `browser-opt-in` skills call gstack's compiled `browse`, `design` and `make-pdf` binaries and a headless Chromium. Pack mode does not build them, so they need a second, separate consent that downloads them:

```bash
pan skills pack browser gstack            # or: pan skills pack browser gstack on
pan skills pack add gstack https://github.com/eltmon/gstack --ref main --browser   # add, then the browser step, asking twice
```

Before it asks, Overdeck checks that the trusted commit is rendered, that its `pack-mode.json` has `packBrowser`, and that bun runs. The preview lists the exact command, each direct npm dependency, a summary line for their locked dependencies (`bun.lock`, from registry.npmjs.org) and one for the Playwright browsers, and every path it writes (never shortened). Shortened here with `…`:

```
  Runs         bash setup --pack-browser /home/you/.overdeck/packs/gstack/render/<commit> --pack-browser-cache /home/you/.overdeck/packs/gstack/browser
  Downloads    direct npm dependencies, then summaries of their locked dependencies and the Playwright browsers:
                @anthropic-ai/sdk@^0.78.0
                …
                playwright@^1.62.1
                …
                + their locked dependencies from bun.lock (registry.npmjs.org)
                Chromium, Chromium headless shell and ffmpeg for playwright ^1.62.1 (Playwright CDN, ~115 MiB download)
  Writes       7 paths:
                /home/you/.overdeck/packs/gstack/render/<commit>/node_modules
                …
                /home/you/.overdeck/packs/gstack/browser/playwright
  Size         about 1 GB on disk
Trusting runs the command above once now and downloads the listed packages and Chromium.
Trust this browser runtime? [y/N]
```

After you confirm, gstack's step runs `bun install --production --frozen-lockfile`, compiles the five binaries into the render, and downloads Chromium into `~/.overdeck/packs/gstack/browser/playwright`, with bun's package cache in `~/.overdeck/packs/gstack/browser/bun-cache`. Chromium's fontconfig and GPU caches go to `~/.overdeck/packs/gstack/browser/xdg-cache` instead of `~/.cache`, both during the build and when browse runs later. It never runs gstack's full build, which would rewrite the skills for `~/.claude`. Only when the build succeeds does Overdeck record your consent (`browser: true` in the pack's registry entry). If it fails, nothing is recorded and the error shows the last lines of gstack's output.

With consent recorded, `pan skills pack update gstack` adds the browser rows to its one preview and builds the new commit's runtime before it moves the trusted commit, and `pan skills pack sync gstack` builds the runtime again when it is missing. A launch never builds: if consent is recorded but the runtime is not built, the launch mounts no browser skill and prints `gstack browser runtime not built; run pan skills pack sync gstack`.

```bash
pan skills set gstack/ship on --project <key>   # a browser-opt-in skill
pan skills pack browser gstack off              # remove the runtime
```

`off` clears the consent, renders the trusted commit again without `node_modules` or binaries, and deletes `~/.overdeck/packs/gstack/browser/`. Older commits' renders that still hold a runtime are left to `pan skills pack gc`.

#### Where gstack keeps state

Each trusted commit is rendered into `~/.overdeck/packs/gstack/render/<commit>/`. gstack's state (its `config.yaml`, sessions, learnings, project reports and plans) lives in `~/.overdeck/packs/gstack/state/`, shared across commits. The render holds a marker that points gstack's scripts at that state dir, so no environment variable is needed and nothing goes to `~/.gstack`. Pack mode starts the config with `telemetry: off`, `update_check: false` and `auto_upgrade: false`. When you invoke a skill in a project, it may write `.gstack/` (temporary files and reports) in that project. Rendered skill docs name the state dir wherever gstack's prose says `~/.gstack/`.

The browser skills start a browse daemon per project. It keeps its port, token and logs in the project's `.gstack/` (`browse.json`, `browse-*.log`), writes some temporary files as `/tmp/browse-*`, and exits by itself after 30 idle minutes (or on `$B stop`).

#### Removing gstack

```bash
pan skills pack remove gstack
```

`remove` deletes `~/.overdeck/packs/gstack/` (renders, state, extractions and the git cache), every mount that contains gstack, the launch links that leaves dangling, and the gstack copy in every Codex agent's plugin cache. A running agent that used gstack loses its gstack skills until its next launch. `remove` does not delete the `.gstack/` or `.gstack-worktrees/` dirs that skills wrote in your projects; it prints each one it finds under a registered project, with the `rm -rf` command. `remove` and `pan skills pack browser gstack off` also print each live browse daemon in a registered project as `Browse daemon still running in <project>: pid <n> — stop with: kill -INT <n>` (a headless daemon ignores a plain `kill`); they never stop one. `pan skills pack gc` also removes renders of commits other than the trusted one once no linked launch uses them and they are older than `--max-age-days` (using a render resets its age), and the `render/`, `state/` and `browser/` dirs of packs that are no longer registered once all are older than `--max-age-days`. If `config.yaml` cannot be read or parsed, gc removes nothing and exits 1, because it cannot tell which packs are registered. If removing a mount or cache fails, `remove` names it and exits 1; run it again to retry.

#### Limits

- The browser step needs an eltmon/gstack commit whose `pack-mode.json` has `packBrowser`; an older commit fails that check before anything is asked.
- Chromium comes from Playwright with no system packages or fonts (`--with-deps` is not run). On Linux, emoji may render as boxes in PDFs.
- The design skills need `OPENAI_API_KEY` or `GEMINI_API_KEY`, or a key saved by `$D setup`, which goes to gstack's state dir.
- Headed mode and the `pair-agent` tunnel are excluded, so their `~/.gstack/.auth.json` and ngrok config paths are never used.
- The browse daemon writes some temporary files in `/tmp`.
- Skills that run gstack scripts with `bun <script>` (for example the QA evidence step) let bun cache transpiled code in `~/.bun/install/cache/@t@`, because the agent's shell has no gstack environment.
- On macOS, the binaries are re-signed the way gstack's own setup does it; this was verified on Linux only.
- Browser skills in Codex launches are unverified: the Codex sandbox may block Chromium or `bun run`.
- Codex launches mount the same render as Claude Code. Skills that ask Claude-only questions fall back to gstack's plain-text path in Codex.
- Pack mode does not install setup's settings hooks (question tuning, the timeline Stop hook, auto-update, the verify gate), and gstack skills cannot upgrade themselves; update through `pan skills pack update gstack`.
- Commits of upstream `garrytan/gstack` fail the pack-mode check until pack mode is merged there; use the eltmon fork.

### Deft Directive

Deft's skills depend on its engine and project files, so Overdeck mounts only a read-only subset through the `deft-readonly` adapter.

[Deft Directive](https://github.com/eltmon/directive) is a process engine. `directive init` installs it by writing tracked files into a repository: an `AGENTS.md` managed section, agent hooks that call `deft-hook`, `.githooks/` with `core.hooksPath`, a `package.json` pin of `@deftai/directive`, `deft-directive-*` pointer skills, and an `xbrief/` tree. A repository with that deposit is a **Directive project**.

Overdeck never runs a Deft CLI, never installs the engine, and never writes a tracked file in any project. It offers three levels:

| Level | What you get |
|-------|--------------|
| Off | No Deft skills. In a Directive project, an explicit off also turns the deposit's enforcement off for Overdeck launches (the kill switch below). |
| Methodology on | The read-only `deft` pack: seven Deft skills that need no engine, mounted per launch with a host notice. In a Directive project you can also turn on managed mode. |
| Full Deft | Deft owns worktrees, review, and merge. Overdeck does not target this level. |

#### Adding the deft pack

```bash
pan skills pack add deft https://github.com/eltmon/directive --ref <ref>
pan skills set --pack deft on
```

`deft` is a known pack, so Overdeck picks the `deft-readonly` adapter. The preview lists `Skills 7` and `Not applied hooks, context injection, git hooks, requires CLI (directive)`. The adapter reads `content/skills/deft-directive-<name>/SKILL.md` at the trusted commit and keeps only the read-only allowlist. Each skill is named by its stripped name, so the agent sees `deft:glossary`, never `deft:deft-directive-glossary`, and Overdeck's id is `deft/glossary`.

#### Skill map

Every Deft skill has one class. Only `compatible` and `translated` skills are mounted. A skill that appears at a newer pinned commit and is not in this map is excluded as unreviewed. The map is verified at eltmon/directive 48e8cbf (v0.119.10-16).

| Deft skill | Class | Overdeck equivalent or reason |
|------------|-------|-------------------------------|
| glossary | compatible | Conversation-only; does not write `UBIQUITOUS_LANGUAGE.md` unless asked |
| debug | translated | `task verify:investigation` is unavailable; the ledger goes to chat |
| design-critique | translated | `task issue:ingest` is unavailable; the next step is `pan issues` or the operator |
| gh-arch | translated | `task slice:record` is unavailable; file follow-ups in Overdeck's tracker |
| write-skill | translated | New skills go to `<project>/.pan/skills/<name>/SKILL.md` |
| probe | translated | Never writes `xbrief/proposed/`; results go to chat |
| cost | translated | Reads `xbrief/PROJECT-DEFINITION.xbrief.json` only when present |
| xbrief | conflicting | `write-xbrief` |
| swarm | conflicting | `pan-swarm` |
| pre-pr | conflicting | `work-complete` |
| review-cycle | conflicting | `pan-code-review` |
| refinement | conflicting | `pan-plan` |
| decompose | conflicting | `write-xbrief` |
| gh-slice | conflicting | `pan-plan` |
| build | conflicting | `pan-start` |
| setup | conflicting | `pan-new-project` (it runs `directive init`) |
| sync | conflicting | `pan-sync` (it runs an npm refresh of the deposit) |
| interview | runtime-dependent | Needs Deft interview state |
| issue-eval | runtime-dependent | Needs Deft Stage A tooling |
| portfolio-priority | runtime-dependent | Needs Deft triage and RFC state |
| product-signal | runtime-dependent | Consent and upload flow owned by Deft |
| feedback | runtime-dependent | Escalates gaps through Deft tooling |
| article-review | runtime-dependent | Feeds Deft's improvement backlog |
| release | excluded | Releases the Deft framework itself |
| triage | excluded | Withdrawn upstream |

#### Host notice and CLI deny

The mount inserts a host notice after the frontmatter of every mounted Deft `SKILL.md`. It tells the agent not to run `directive init`, `directive update`, `directive bootstrap`, or `deft session:start`; not to install packages, change git hooks or `core.hooksPath`, edit `AGENTS.md`, or write under `xbrief/`; that Overdeck owns planning (`.pan/specs`), worktrees, review, and merge; to skip a `task` or `deft` step that is not installed and report in chat; and not to write repository files unless the operator asks. It also lists the Overdeck equivalent of each conflicting Deft skill.

When a Claude Code launch mounts any `deft/*` skill in a project that is **not** a Directive project, the launch settings also deny Deft's mutating CLIs:

```
Bash(directive:*)  Bash(deft:*)  Bash(deft-hook:*)  Bash(npx @deftai/directive:*)
Bash(npm install @deftai/directive:*)  Bash(npm i @deftai/directive:*)
Bash(pnpm add @deftai/directive:*)  Bash(git config core.hooksPath:*)
```

In a Directive project no deny is added, because Deft is that project's own tool. Codex has no equivalent deny setting, so on Codex the host notice is the only boundary.

#### What a launch does in a Directive project

Each Overdeck-managed Claude Code or Codex launch detects a Directive project at the launch directory's repository root. Detection reads files only (`.deft/core/VERSION`, the `AGENTS.md` managed-section marker, or the `@deftai/directive` pin) and is never stored. **Explicit off** means the `deft` pack toggle resolves off at the issue or project level. The default (no value anywhere) is not explicit off, and the global level has no off value, so it never is.

| Directive project | `deft` toggle | Managed mode | Result |
|-------------------|---------------|--------------|--------|
| no | any | — | Nothing exported; Claude gets the CLI deny list when deft skills are mounted |
| yes | explicit off (issue or project) | any | Kill switch: `DEFT_DIRECTIVE_DISABLE=1`, the flag file in issue worktrees, and the deposit's `deft-directive-*` pointer skills hidden |
| yes | on, or default | managed | `DEFT_ORCHESTRATOR=overdeck` |
| yes | on, or default | not managed | Nothing exported; Deft runs as the project configured it |

The **kill switch** is Deft's own `.deft-directive-disable` root file, honored by engines from v0.92.0 when the file is untracked. Overdeck writes it only when the launch runs in an issue worktree (`workspaces/feature-<issue>/`). The file starts with `# overdeck:deft-directive-disable`, and Overdeck adds `/.deft-directive-disable` to the repository's `.git/info/exclude` when nothing ignores it yet, so `git status` stays clean. When the toggle goes back to on or inherit, Overdeck deletes the flag only if its first line is that marker; a flag you wrote yourself is never touched, and a tracked flag is never changed. Review agents, test agents, and conversations launched at the project root get the environment variable only.

A launch prints one provenance line to stderr, for example `[launcher] deft: pack master (48e8cbf0e781); project directive engine ^0.119.10; kill switch`. If anything in the Deft step fails, the launch prints `[launcher] WARNING: deft integration not applied: <message>`, removes the Deft env file, and continues with its other skill settings and packs.

#### Managed mode

Managed mode is a per-project decision: Deft methodology on, with Overdeck owning worktrees, review, merge, and the pipeline xBRIEF.

```bash
pan skills deft status [--project <key>] [--json]   # detection, pack, skill map, managed mode, ownership report
pan skills deft enable --project <key> [--yes]      # print the ownership plan, then store the decision
pan skills deft disable --project <key>             # remove the decision; project files untouched
```

`enable` refuses a project that is not a Directive project (Overdeck never runs `directive init`). It prints the ownership report, one owner per concern (xbrief, context, agent hooks, git hooks, worktrees, gates, task state, review, release, skills, workspace settings), and asks `Enable managed mode with this ownership plan? [y/N]`. Without a terminal, pass `--yes`; otherwise nothing is written. It stores only `projects.<key>.deft_integration: { mode: managed, plan_digest, enabled_at }` in `~/.overdeck/projects.yaml`, where `plan_digest` is the sha256 of the report text you saw. Launches in a managed project that is not off export `DEFT_ORCHESTRATOR=overdeck`.

#### Environment contract

Overdeck exports at most these two literal lines, from a per-launch env file that the launcher reads with an allowlist and never sources:

| Variable | Value | Meaning to the engine |
|----------|-------|-----------------------|
| `DEFT_DIRECTIVE_DISABLE` | `1` | Same as an untracked root `.deft-directive-disable` |
| `DEFT_ORCHESTRATOR` | `overdeck` | External-orchestrator mode: Deft enforcement defers to the host; Deft contributes methodology only |

Both variables are a no-op until your project pins an engine that reads them ([PAN-4425](https://github.com/eltmon/overdeck/issues/4425)). The flag file works on every engine from v0.92.0.

#### Limits

- **Git hooks.** The deposited `.githooks/pre-commit` runs `deft verify:branch` and does not check the kill switch; whether `verify:branch` itself reads it is unverified. Feature-branch commits pass `verify:branch`. Main-branch plan-artifact commits in a Directive plan home may be refused.
- **Workspace settings.** In a Directive project `.claude/settings.json` is a tracked Deft deposit, and Overdeck's workspace creation merges its own hooks into it, which leaves that file modified in the worktree.
- **Scope.** Detection runs at the launch directory's repository root only, not in polyrepo sub-repositories. There is no conversation-level toggle; conversations inherit global and project toggles.

### SageOx

[SageOx](https://github.com/sageox/ox) records coding-agent sessions and syncs them to a team ledger. Overdeck offers it as the `sageox` pack, built from the operator's fork [eltmon/ox](https://github.com/eltmon/ox). The fork adds a **host-managed mode**: with `OX_HOST_MANAGED=1`, `ox` writes nothing into the repository (no `AGENTS.md`/`CLAUDE.md` markers, no `.claude/settings.json` hooks), adds no attribution to commits or PRs, never asks the agent to run `ox init`, and stays offline unless Overdeck allows the network.

SageOx is **off by default**, for every project and issue. It works with **Claude Code** launches only; Codex launches never get SageOx skills or hooks, and print a warning when the pack would have been on.

**What leaves the machine:**

> SageOx records agent sessions on this machine. With uploads off (the default) Overdeck runs `ox` with the network off: nothing is sent. With uploads on for a project, redacted session transcripts and session metadata are uploaded to the SageOx cloud ledger for that repo, and `ox` may fetch team context. Requires the eltmon/ox build; see `pan doctor`.

The Skills page shows the same text on the `sageox` pack row.

#### One-time setup

1. **Build `ox` from the fork**, at the commit the pack trusts. Overdeck never installs `ox`. The fork needs Go 1.26 (the default `GOTOOLCHAIN=auto` downloads it).

   ```bash
   git clone git@github.com:eltmon/ox.git && cd ox
   git switch --detach <trusted commit>      # shown by: pan skills pack list
   go build -o ~/.local/bin/ox ./cmd/ox
   ox host-contract --json                   # must print "contract":"overdeck-host/1"
   ```

2. **Register the pack** (the ref is a branch or tag in the fork):

   ```bash
   pan skills pack add sageox https://github.com/eltmon/ox --ref overdeck/host-managed
   ```

   The repo-writing skills (`ox-cli-init`, `ox-cli-attest`, `ox-cli-skill-manager`, `ox-cli-pr-header`, `ox-cli-plan`, and the `ox-cli-cart*` skills) are opt-in: the pack toggle never turns them on.

3. **In each repository you choose**, log in and initialize SageOx yourself, once. Overdeck never runs these commands. Host-managed `ox init` writes only `.sageox/` (no `AGENTS.md`/`CLAUDE.md` markers, no hook files, no git hooks). It registers the repository with SageOx, so it needs the network:

   ```bash
   ox login
   OX_HOST_MANAGED=1 OX_HOST_NETWORK=on ox init
   ox status        # wait until it shows the project's ledger
   ```

   Session recording writes into a local clone of the project's SageOx ledger. The ox daemon that `ox init` starts clones it; wait until `ox status` shows the ledger. With uploads off, Overdeck keeps `ox` offline and no daemon runs, so without this clone SageOx records nothing.

4. **Turn the pack on** for that project (or one issue):

   ```bash
   pan skills set --pack sageox on --project myapp
   ```

#### Uploads

Uploads are a second, separate opt-in per project. They are off until you turn them on:

```bash
pan skills pack sageox upload on --project myapp    # writes sageox_upload: enabled in projects.yaml
pan skills pack sageox upload off --project myapp
pan skills pack sageox status [--project <key>] [--json]
```

`status` shows, for each project, whether the pack is on (and from which level) and whether uploads are enabled. With uploads off, Overdeck sets `OX_HOST_NETWORK=off` and `OX_SESSION_PUBLISHING=manual`, so sessions stay on this machine. With uploads on, it sets `OX_HOST_NETWORK=on` and `OX_SESSION_PUBLISHING=auto`.

#### What a launch gets

When the pack is on for a Claude Code launch, Overdeck checks two more things at launch time: the launch's git root has a `.sageox/` directory, and the `ox` on `PATH` answers `ox host-contract --json` within 2 seconds. When all hold, the launch's `--settings` JSON carries:

- the env `OX_HOST_MANAGED=1`, `OX_PROJECT_ROOT=<git root>`, `OX_HOST_NETWORK`, `OX_SESSION_PUBLISHING`, `SAGEOX_TELEMETRY=false`, `SAGEOX_FRICTION=false`, `SAGEOX_DAEMON=false`, and `OX_NO_DAEMON=1`;
- one `ox agent hook <event>` hook for each of `SessionStart`, `PreCompact`, `PostToolUse`, `Stop`, `SessionEnd`, and `UserPromptSubmit`, with the same env written inline in each hook command;
- the `sageox` pack skills you turned on.

These hooks come from Overdeck, not from the pack; the pack's own capabilities are still **Not applied**. If any check fails, or anything goes wrong, the launch continues without SageOx: no env, no hooks, no `sageox` skills, and one `[launcher] WARNING:` line naming the reason. Turning the pack off removes all of it at the next launch.

#### What `pan doctor` checks

When the `sageox` pack is registered, `pan doctor` adds a **SageOx (ox)** row. It is `ok` when `ox` answers the `overdeck-host/1` contract and was built from the pack's trusted commit. It warns, with the build command as the fix, when `ox` is missing, is upstream `ox` without the host contract, or was built from a different commit. Without the pack, there is no row.

## Where state lives and when changes apply

### Where pack state is stored

| What | Stored in |
|------|-----------|
| Registry (url, ref, trusted commit) | `~/.overdeck/config.yaml`, under `skills.packs.<id>` |
| Global pack toggle | `~/.overdeck/config.yaml`, under `skills.pack_overrides.<id>: true` |
| Project pack toggle | `~/.overdeck/projects.yaml`, under `projects.<key>.skill_pack_overrides.<id>` |
| Issue pack toggle | The issue's skill override file, under `packs.<id>` |
| Single pack skills | The same `skills.overrides`, `skill_overrides`, and issue `skills:` maps, with `pack/skill` keys |
| gstack runtime and state | `~/.overdeck/packs/gstack/render/<commit>/` and `~/.overdeck/packs/gstack/state/` |
| gstack browser runtime | `~/.overdeck/packs/gstack/browser/` (bun cache, Chromium, Chromium's fontconfig and GPU caches), and `node_modules` plus binaries inside the render |
| gstack browser consent | `~/.overdeck/config.yaml`, under `skills.packs.gstack.browser: true` |

The cache lives in `~/.overdeck/packs/` and can be rebuilt at any time, except the gstack `state/` dir, which holds gstack's own config, sessions and learnings: `pan skills pack sync [id]` re-fetches the cache, and `pan skills pack gc [--max-age-days <n>]` removes mounts no launch uses. `pan skills pack remove <id>` unregisters a pack, clears its global toggle and global skill values, and deletes its cache; project and issue values stay but do nothing until the pack is added again.

### When pack changes apply

Packs apply to Overdeck-managed **Claude Code** and **Codex** sessions at their next launch, like other skill changes. Claude Code receives the pack as `--plugin-dir`; Codex gets a local `overdeck-packs` plugin marketplace in the agent's own `$CODEX_HOME`. Remote (Fly) launches and other harnesses get no packs. A launch never touches the network: if the trusted commit is not cached, the launch skips that pack and prints `run pan skills pack sync <id>`. If Claude Code also has the same upstream plugin installed, the dashboard warns that its skills will appear twice.

In the dashboard, packs appear above the skill list on the Skills page, in project settings, and in the issue view. The dashboard can turn packs on and off but not add them; it shows the `pan skills pack add` command instead.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Launch prints `[launcher] WARNING: skill pack <id> not cached; run pan skills pack sync <id>` and the pack is missing | The trusted commit is not in the cache; launches never fetch | `pan skills pack sync <id>`, then relaunch |
| A pack skill is not visible to the agent | The pack or skill is off at the level that decides, the skill is opt-in, the harness is not Claude Code or Codex, or the launch is remote (Fly) | `pan skills list --project <key> --issue <id>`; turn on the pack (`--pack`) or the opt-in skill (`<pack>/<skill>`); packs apply only to Overdeck-managed Claude Code and Codex launches |
| A running agent did not pick up a change | Packs resolve at launch | Restart or resume the agent; the next launch applies it |
| The dashboard shows `also installed as a Claude plugin — skills will appear twice` | Claude Code also has the same upstream plugin installed | Uninstall the Claude Code plugin, or keep the pack off |
| Launch prints `[launcher] WARNING: gstack browser runtime not built; run pan skills pack sync gstack` | Browser consent is recorded but the runtime for the trusted commit is missing | `pan skills pack sync gstack` |
| `pack gstack needs bun on PATH (https://bun.sh)` | `bun` is not installed or not on `PATH` | Install bun, then repeat the command |
| An old gstack render stays after `pan skills pack gc` | A linked mount still uses it, or it is younger than `--max-age-days` (using a mount resets its age and its render's age) | Wait until no launch uses it, or run `pan skills pack gc --max-age-days <n>` with a smaller value |
| Codex launches show no SageOx skills and print `SageOx is on but supports Claude Code launches only; sageox skills and hooks not applied` | SageOx supports Claude Code launches only | Use a Claude Code launch |

## Terminology: skill packs and skill bundles

Skill packs are the built feature described on this page. [Template Conversations](/reference/template-conversations) describes a separate, unbuilt proposal (PAN-1357, `pan bundle`) that also uses the words "skill bundle." Per-conversation skill values (PAN-4486), set in the **New conversation with options…** dialog or by `pan handoff --skill/--pack`, already cover part of that proposal: a conversation can turn on pack skills for itself.
