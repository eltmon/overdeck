Work agents write the code. A **review agent** checks it before it can merge, and a **test agent** can run its tests and browser UAT. The docs call them specialists. They run on the issue's pull request and post their verdicts to it, so GitHub shows the same state the dashboard does.

## What happens after pan done

1. **Verification gate.** After `pan done`, Overdeck runs the project's quality gates. If a gate fails, the work agent gets the failure and fixes it. See [PIPELINE-GATES.md](https://github.com/eltmon/overdeck/blob/main/docs/PIPELINE-GATES.md).
2. **Review.** A review agent reads the diff, the plan and the acceptance criteria, then approves the PR or requests changes. By default one reviewer does a combined pass for correctness, security, performance and requirements (`quick` mode, see [Review commands](/cli/review-commands) "Review modes"). Set `roles.review.mode: full` to run the [review convoy](/features/convoys): four reviewers for security, correctness, performance and requirements, and a review parent that writes the verdict.
3. **Test.** Nothing starts a test agent automatically after the review approves ([#5537](https://github.com/eltmon/overdeck/issues/5537)). In a project that runs its tests on CI (`verification.tests: ci`, or a GitHub Actions workflow that runs a test job on pull requests), the CI test job must pass on the PR head before the PR can merge. Running `pan review request` on a PR that is approved at its head but whose checks are not green starts a test agent: it runs the project's test commands and, when the acceptance criteria describe UI behavior, drives a browser with Playwright and records a separate UAT verdict. There is no separate UAT agent.
4. **Merge.** When the PR is approved at its head commit, its checks are green and GitHub says it can merge, the issue is ready. Whether you click depends on whether the issue is held for UAT: its `hold-for-uat` or `auto-merge` label, else the project's `auto_merge_default`, else the global **Require UAT** switch on the Flywheel page header, which is on by default. A held issue waits for you to click **Merge** on the issue or on the Awaiting Merge page. In a GitHub single-repo project, an issue that is not held merges on its own five minutes after it is ready, or with the next batch while the [merge train](/features/merge-batches) is on; GitLab and polyrepo projects never merge on their own. To merge, the server merges a clean, up-to-date PR as it is; otherwise it rebases the branch onto `main` itself, and when that rebase fails during a merge you started, it asks the work agent to rebase and push. Overdeck then squash-merges the PR. No agent merges it.

To ship without the click, turn on [auto-merge](/configuration/auto-merge). To land several PRs together, use [merge batches](/features/merge-batches).

## When a check fails

A request for changes or a failed test goes back to the work agent as PR review comments and a direct message. Overdeck confirms the agent received it. If it cannot, the item appears in **Needs you**.

## Start or rerun a review

`pan done` starts review automatically. To start it again, run `pan review request <issue-id> -m "what changed"`, or choose **Request review** in the issue's menu. See [Review commands](/cli/review-commands).

Automatic re-review requests are capped at 25 per issue. After that, `pan review request` returns HTTP 429 and a person must start the next review from the issue's menu. The count resets when the dashboard restarts.

## Agents stay warm

Review and test sessions stay running after their verdict until the issue closes. A re-review after a fix resumes the same reviewer, which still has the context from the last pass.

## Choose their models

Each role runs on the model you set in Settings → Model Routing. See [Model routing](/configuration/model-routing).

## Check status

`pan show <issue-id>` prints the issue's derived state and its pipeline journal. `pan admin specialists list` lists specialist sessions.
