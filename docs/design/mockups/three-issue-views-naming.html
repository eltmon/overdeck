The problem, and a way out

All three answer the same question — "what is happening on this issue right now?" — but each was built separately, so each grew sections the others lack (that's why the spinner and Ship row went missing from one but not another, and why the ★ Active Agent panel lives only in the Console). The fix isn't to sync them by hand forever. It's one data model + one component family, rendered at three densities.

Rail density

= today's View 3

Compact, always-on beside the conversation. Collapsed session nodes, chips, filter. The 90%-of-the-time glance.

Cockpit density

= today's View 2 (docked tab)

Medium. Agents&Steps lane, plan-map, detail tabs. Opened when you want to work an issue.

Console density

= today's View 1 (full page)

Large. Everything cockpit has + operator gates + dated lifecycle + the ★ Active Agent panel + full activity rail. The control room.

one <IssueView density="rail | cockpit | console" /> · same store, same row component, same verdicts · a section added once shows in all three
RECOMMENDED

A. Progressive-density unify

Extract shared pieces (issue-state store, the agent/step Row, the verification node, the ★ Active Agent panel, the Ship-door row, cost) into one family; each of the 3 views becomes a thin density wrapper.

✓ One source of truth — drift becomes impossible

✓ Keeps all 3 locations you already use

— Biggest refactor of the three

B. Rail ⇄ Cockpit expand

Keep the Rail as home base; clicking an issue expands the same component in place into the cockpit rather than opening a separate tab. Console becomes "cockpit, full-screen".

✓ Matches how you actually work (rail-first)

— Still two codebases unless paired with A

C. Shared-components only

Leave the 3 shells, but force them to consume the same Row / verification / ship / Active-Agent sub-components (the PAN-2493 audit's plan).

✓ Smallest change, ships fastest

— Layout still diverges; 3 shells to maintain

The UX approach you might be missing: you reach for the Rail most because it lives next to the conversation — the real need is "never lose sight of the issue while I talk to its agent." That argues for making the Rail the primary surface and letting it grow in place (option B) rather than sending you to a separate tab/page. Density-unify (A) is what makes B safe to build. My suggestion: A as the foundation, B as the interaction model, and retire "3 separate views" as a concept — one Issue View, always beside your conversation, that expands when you need more (and carries the ★ Active Agent panel everywhere, since that's the piece you live in).
