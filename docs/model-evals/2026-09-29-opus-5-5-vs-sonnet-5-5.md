# Opus 5.5 vs Sonnet 5.5 for the `mid` slot: placement evals and delegation test (2026-09-29)

## Verdict

**Do not move `workhorses.mid` to Sonnet 5.5 yet. Opus 5.5 should keep the review role no matter what else changes.**

- `mid` currently drives `work`, `review` (all four lanes inherit it through `model: parent`), `ship`, `strike` and `worker` (`~/.overdeck/config.yaml`). So moving `mid` also moves review.
- **Review is where Sonnet 5.5 is measurably weaker.** On E2 review recall, across 3 reps × 20 real review cases, Opus 5.5 identified the known blocker 30/60 times and Sonnet 5.5 10/60 times (any-severity matching, explained below). Taking the majority of reps per case, Opus finds 11/20 cases and Sonnet 3/20. No case goes the other way (paired sign test, 8–0, p ≈ 0.008). The gap is in the performance lane (5/6 vs 1/6) and the correctness lane (6/7 vs 2/7). Both models miss all 7 requirements-lane cases.
- **On delegated execution, the evals found no difference.** Both models acted on 15/15 genuine feedback messages (E5) and refused every injection attempt I could inspect. On the delegation test, both scored 100% intent on all 11 tasks in both framings, including three tasks where the casual request names the wrong root cause. Sonnet was about 45% of Opus's cost and 25–45% faster. "No difference measured" is not the same as "equivalent": these are single-turn, tool-less probes. They say nothing about multi-hour, tool-using work sessions.
- **The delegation hypothesis is not supported in the form stated.** Sonnet 5.5 was not weaker under casual human framing: both models hit the ceiling in both framings. The one place Sonnet was clearly weaker (E2) used a precise, Opus-authored role prompt, which is the delegated setting. A better-fitting account is about task type rather than who writes the prompt. **Sonnet 5.5 matches Opus when the task says what to do. It falls behind when the task is to find what is wrong without being told** (review, and plausibly debugging and open-ended investigation, which are much of what a human asks for directly). This is an inference from one discriminating suite, not a measured result.

**Recommendation:** keep `mid` = Opus 5.5 for now. If you want Sonnet 5.5's cost and speed on execution roles, do not flip the whole slot. Pin review to Opus first, then pilot Sonnet on `work` with a weighted split and compare pipeline outcomes (see "Recommended config change").

### E2 detail

- The strict scorer counts only a `!`/`⊗` **blocking** finding under a `###` heading. Both models floor out: in excerpt-only eval mode they mostly downgrade the real blocker to an advisory (`~`, `≉`, `?`) with "outside the excerpt, can't confirm". Luna scored 0.10 on the same strict metric, so this metric measures severity calibration under the excerpt prompt more than model quality.
- The any-severity rescore uses the scorer's own `findingMatchesBlocker` (same file, line within 15 or ≥2 keywords) but ignores the glyph (`e2-rescore.txt`). Opus writes more structured findings: 41, 39 and 50 `###` findings per 20 cases, against Sonnet's 18, 17 and 18. Sonnet often puts advisory notes in plain bullets instead of glyph headings. Precision of the extra Opus findings (false positives) is not measured.
- **Production relevance.** Review convergence (`src/lib/review-findings.ts` `findBlockingFindings`) counts only `### !` / `### ⊗` headings under `## Findings`. An advisory never gates a PR, so in production terms a blocker downgraded to an advisory is a miss, and the strict column is the one that matters. It also favors Opus (4/60 vs 0/60), but the counts are tiny. The any-severity column measures whether the model saw the problem at all. Production reviewers have tools and the full repo rather than an excerpt, so their severity calibration there may differ.

Sonnet's plans were lint-clean on 5 of its 7 schema-valid plans. Opus's plans had 2–8 lint errors on every case, and lint is 40% of the score. ## Delegation test

**Design.** One fixed system prompt ("work agent in the Overdeck TS repo; no tools; reply with the full file in a ```ts block"). Only the user turn varies. Both framings include the current file.

- **(a) brief:** an xBRIEF-style item with files, difficulty, steps and Given/When/Then acceptance criteria.
- **(b) casual:** one or two informal sentences describing the symptom.

Hidden tests in two tiers:

- **intent:** invariants any reasonable reading of the casual request implies. These are fair to both framings.
- **spec:** the brief's exact acceptance criteria. Only the brief states these.

The 11 tasks:

- **5 basic:** duration parser, semver compare, LRU with TTL, retry with backoff, branch slug.
- **3 context-dependent:** single-flight token refresh, cursor pagination with a doc-comment page cap, config deep-merge whose semantics live in the doc comment.
- **3 wrong-premise:** the casual request confidently blames the wrong function (the pricing prefix lookup, a notification key including `receivedAt`, and a sort rank using `||` where `??` is needed), and the brief names the real root cause.

The hypothesis predicts an interaction: Sonnet's brief-to-casual drop should be larger than Opus's.

|---|---|---|---|---|---|---|---|
| Opus 5.5 | brief | 14 | **1.000** | 1.000 | $0.48 | 11.0 s | 1,250 |
| Opus 5.5 | casual | 14 | **1.000** | 0.833 | $0.48 | 11.5 s | 1,405 |
| Sonnet 5.5 | brief | 14 | **1.000** | 1.000 | $0.21 | 7.4 s | 1,026 |
| Sonnet 5.5 | casual | 14 | **1.000** | 0.800 | $0.22 | 8.8 s | 1,233 |

(8 tasks × 1 rep + 3 wrong-premise tasks × 2 reps. Per-task rows are in `final-tables.txt`.)

- **Interaction: none.** Both models drop the same amount on spec (−0.17 vs −0.20). That drop is on exact choices the casual request never stated, such as `RangeError`, `d` units, and cycle detection. Neither model missed an inferable requirement.
- **Wrong-premise tasks:** in all 12 casual calls, both models named the real root cause and fixed it rather than patching the function the user blamed. On the notifications task, both chose a defensible alternative design: dedupe by `eventId` inside the loop instead of changing `notificationKey`. That fails the spec check but passes every intent check.
- **Is it worth proposing as an eval? Not as-is.** The harness is clean: hidden tests, an intent/spec split, and a fixed system prompt. But the tasks sit at ceiling for both frontier models, so the eval does not discriminate. A useful version needs multi-file, tool-using, multi-turn tasks, which is the #3054 pipeline benchmark rather than a prompt eval. If filed, file it as "delegation-framing tasks for #3054", reusing the tier design and the wrong-premise idea.

## Caveats

- **Route.** Anthropic calls went through a local, uncommitted `claude-cli` route in `evals/lib/prompt-harness.ts`: `claude -p --system-prompt-file … --tools "" --safe-mode --setting-sources "" --effort high`, with `CLAUDE_CODE_MAX_OUTPUT_TOKENS` set to each suite's cap.
  - It is not byte-identical to the API harness. Claude Code adds about 500 tokens of context (environment block and account note), the same for both models.
  - Multi-turn E5 cases replay the history by fabricating a session JSONL and running `--resume … --fork-session`.
  - The CLI's `result` appears to keep only the final text block, which broke one very long E3 reply.
  - The patch is saved as `harness-claude-cli-route.diff`.
- **Sample sizes.** E2: 3 × 20. E5: 3 × 6. E4: 1 × 10. E3: 1 × 8. Delegation: 11 tasks at 1–2 reps. Only E2 discriminates, and its signal is consistent across all 3 reps.
- **Coverage.** Every suite is single-turn (E5 is 3 turns) with no tools. None measures long-horizon execution, tool-use reliability, recovering from a red test, or following an xBRIEF through commits and `pan done`, and that is most of what `work`/`ship`/`worker` do. The `ship` and `strike` roles have no eval at all.
- **Scorer defects found**, worth one follow-up issue:
  1. **E5 `classifyFeedbackResponse`:** a refusal that quotes the anchor (for example "I won't run `git push --force`…") plus any action verb anywhere in the reply is classed `acted`. 3 of 6 control runs scored as failures (Sonnet reps 1 and 3, Opus rep 1). The only one of the three whose text was captured (Sonnet rep 3) is a clean refusal, and so are all 4 captured control replies. Fix: for the control case, test refusal first, or require the anchor and the action verb in the same non-refusal sentence.
  2. **E2 strict recall floors for every model** (Luna 0.10, Opus 0.067, Sonnet 0). Add the any-severity recall metric, and count a bullet with a glyph as a finding.
  3. **E4 `extractIdentifiers`** flags elided paths (`.pan/specs/...xbrief.json`, `…/tasks/<id>.output`) and reads `.pan/…` as `pan/…`, so most compaction and handoff zeros for both models are artifacts. Each model also invented one plausible file path in `compaction-open-pr-selector`.
- **E5 rep 1** reply texts were not captured (the dump started at rep 2). Its two control "failures" are presumed to be the same scorer artifact.
- **Leftover files.** Fabricated or persisted CLI session JSONLs remain under `~/.claude/projects/-tmp-claude-1000--home-eltmon-Projects-overdeck-d92a75f4-8b6d-4e17-be76-6b04fc3926b7-scratchpad-cwd/`. They were left in place per the JSONL rule; they are eval scaffolding, not real conversations.

## Recommended config change

None is needed to keep the current state: `mid` stays `claude-opus-5-5`.

If you want to capture Sonnet 5.5's cost and latency on execution roles, make these two edits to `~/.overdeck/config.yaml` rather than flipping `mid`:

```yaml
roles:
  review:
    model: workhorse:expensive        # pin review lanes to Opus 5.5 independent of `mid`
  work:
    model:
      - model: workhorse:mid          # Opus 5.5
        weight: 70
      - model: claude-sonnet-5-5      # pilot share
        weight: 30
    effort: high
```

Then compare the two arms on pipeline outcomes: review cycles to approve, blocking findings per PR, CI-red rate and verification feedback loops. Move `mid` (and with it `ship`/`strike`/`worker`) only if the Sonnet arm holds up.

How the split behaves (verified on origin/main):

- `resolveModel` (`src/lib/config-yaml/roles.ts`) hashes the spawn key through `pickPercentModelRef` (`src/lib/config-yaml/percent.ts`), so each issue lands in one arm and stays there across respawns.
- Without a spawn key it takes the highest-weight entry. The staffing path passes one (`src/lib/agents/staffing.ts`).
- The spawn-path overrides that used to bypass role routing (PAN-3857/3858/3859) are closed.
- `roles.review.model: workhorse:expensive` uses the same workhorse dereference as `roles.plan`. The review lanes' `model: parent` then inherits Opus.
