# The Flywheel

The Flywheel is the `/pan-flywheel` loop skill running in one operator conversation, `conv-flywheel`. It ticks the backlog and order books, launches work with `pan start`, watches each PR to landing, and parks what it cannot decide. There is no daemon and no run record.

User guide: [features/flywheel.mdx](../features/flywheel.mdx).

Every agent the loop starts carries provenance `startedBy: 'flywheel:conv-flywheel'` (PAN-3634), resolved by `resolveCliStartedBy()` from `OVERDECK_CONVERSATION=conv-flywheel` on the shell the conversation runs in — there is no run id to stamp or read anymore. The planning auto-handoff and its deferred retry carry that same token to the work agent only when the planning session they hand off from was itself Flywheel-started (`planningHandoffStartedBy()`); otherwise they send `planning-auto-handoff`, an operator origin. This is what the emergency brake and the memory governor's shed key their operator-started exemption on: only a `flywheel:`-prefixed `startedBy` is ever reaped automatically.

Pipeline role agents (plan, work, review, test, strike) escalate a stall to the Flywheel with `pan tell conv-flywheel "<role> <issue>: …"`, as their role prompts' "Signal the flywheel before you stall" section says. When no Flywheel is running the tell fails with "not running", and the prompt tells the agent to post the same analysis as an issue comment, which keeps it on record (the loop has no step that reads issue comments). `messageAgent` finds the Flywheel's harness by its full row name `conv-flywheel`, so the tell reaches a Flywheel on any harness. The retired name `flywheel-orchestrator` reaches no session; `src/lib/agents/__tests__/role-escalation-target.test.ts` fails if a rendered role prompt or a `sync-sources/` file names it as a `pan tell` target (PAN-5615).

PAN-3917 cut the Flywheel page and its `pause`/`resume`/`abort`/`report`/`stats` verbs along with the stored run records. PAN-3964 brought the page and the verbs back as a **derived view**: every status the page shows is computed when it is read, from sources that already exist. Nothing new is stored in SQLite. The only files are the loop's own `.pan/flywheel/state.md` and `.pan/flywheel/report.md`.

`pan flywheel status`, `GET /api/flywheel/status`, and the page all call the same function, `deriveFlywheelStatus()` in `src/lib/flywheel/derive-status.ts`, so the CLI and the page show the same answer.

## Board layout

The Status tab reads top to bottom: the health strip, the run summary, the last tick and its freshness, the Needs-you cards, the lane board, and the Shipped-today timeline. The board's seven lanes stack vertically in pipeline order — Plan, Build, Checks, Review, Merge, Deploy, Done today — each headed `<Lane> · <count>`, with a muted `—` when empty, so nothing scrolls sideways in the 360 px rail. An in-flight card is one button that opens the issue: issue id, time in stage, cost, owner, the full title clamped to two lines, the agent line (`<role> · <model> · <state>` or `no agent`), the blocker in its severity tone (waiting muted, stuck destructive, needs-you warning), and `last: <activity> · <age>`. Deploy and Done-today cards link to their PR. Below the `md` breakpoint the rail stacks above the conversation at full width and the resize handle hides.

## Tick marker contract

The skill ends every tick by printing one line:

```text
flywheel-tick: tick=3 pick=PAN-3964 phase=watch in-flight=PAN-3964,PAN-3920 needs-you=none
```

| Key | Value |
| --- | --- |
| `tick` | A counter that starts at 1 for this conversation. A line without a numeric tick is ignored. |
| `pick` | The issue the tick picked, or `none` (parsed as `null`). |
| `phase` | One of `orient`, `pick`, `launch`, `watch`, `park`, `idle`, `stopping`. An unknown value is parsed as `watch`. |
| `in-flight` | Comma-separated issue ids, or `none` (parsed as `[]`). |
| `needs-you` | Free text for the operator, or `none` (parsed as `null`). It is always the last key and takes the rest of the line, so it may contain spaces and `=`. Separate several items with `; `; write a PR outside the flywheel's project as `owner/repo#<n>`. An item may end with a target in angle brackets, `<https://…>`; the URL may not contain spaces or `;`. Example: `needs-you=PR eltmon/overdeck-landing#7 merge; upload AAB <https://play.google.com/console/…>`. |

`formatTickMarker` and `parseTickMarker` live in `src/lib/flywheel/tick-marker.ts`. When a message contains more than one marker, the last one wins. User messages are ignored: the stop and report requests contain a marker template, and the skill's own example appears in a user turn when the slash command expands.

The marker is the only status the loop reports. There is no `POST /api/flywheel/status`.

## Watchdog

The loop wakes itself: each tick ends by running a background `sleep`, and its completion starts the next tick. When Claude Code kills that timer (it does under memory pressure), nothing inside the conversation starts another turn. The deacon-lite routine `watchFlywheelLoop` (`src/lib/cloister/flywheel-watchdog.ts`, PAN-5667) is the outside wake-up. Once a minute it reads the run state and the transcript:

- **Stalled loop.** When the run is `running`, the newest tick is `stalled` (older than 20 minutes), and the conversation is at a turn boundary (its last message is a completed assistant message and no tool call or question waits on an answer), it sends `/pan-flywheel` through the agent delivery door. So the loop gets a new turn about 21 minutes after its last tick. A mid-turn conversation, a Herdr pane that reads `working` or `blocked`, a paused run, no tick, or a `phase=stopping` tick is never nudged. One stall gets one nudge, repeated only after another 20 minutes without a new tick.
- **Host reboot.** When the run is `paused` because the host rebooted under it, it resumes the loop through `POST /api/flywheel/resume`. That needs a row created before the boot that did not end before the boot, a transcript with nothing written since the boot, at least one tick with the newest not `phase=stopping`, a boot that is not `--no-resume`, and no deliberate stop recorded by the dashboard since the boot. A pause before the reboot, or after the loop came back, is never undone. One gap remains: if the operator pauses a dead flywheel that the watchdog has not yet resumed, only the dashboard's in-memory stop mark protects that pause. A dashboard restart forgets the mark, and the next patrol then resumes the loop.

After a safe shutdown (`pan shutdown`) the watchdog never resumes the Flywheel: the drain ends the row before the boot, and turning things back on after a deliberate shutdown is the operator's call (D-9). Instead, the shutdown resume offer in Needs you lists `conv-flywheel` whenever the drain stopped it, idle between ticks or mid-turn (PAN-5671, `isOfferedAfterShutdown` in `src/lib/shutdown/drain-record.ts`); **Resume all** resumes it through `resumeFlywheel`, which re-sends `/pan-flywheel`. While the shutdown record exists the watchdog nudges and resumes nothing.

Each nudge and resume shows in the dashboard activity feed and in `~/.overdeck/logs/deacon.log`. Freezing the Deacon (`deacon.globally_paused`) stops the watchdog with the rest of the patrol. See "Deacon-lite: ten routines" in [PIPELINE-GATES.md](PIPELINE-GATES.md).

## Non-goals

- Stats criteria c3–c7 (pass rate, MTTR, intervention rate, time consistency, flake). Their inputs were the run telemetry that PAN-3917 deleted.
- A run record, a run id, a `flywheel_runs` table, a telemetry service, or `POST /api/flywheel/status`.
- Boot reconciliation, the Recover button, the orphan-test-agent surface, the VerifyingOnMain badge, and the reset/restart-from-plan buttons.
- Changing the loop's phases or the `pan start` launch path.
- Launching `roles/flywheel.md` as a role prompt. The skill is the prompt, and the role file is only the source of the text it quotes.

Known limits: `listRepoPullRequests` reads at most 200 PRs, so a 90-day window on a busy repo undercounts merged PRs, the c1 denominator. The order book's landed count reads the issue cache. The dashboard keeps that cache loaded, but a bare CLI process may not have it, so `pan flywheel status` can report fewer landed items than the page — and, since it has no issue cache to backfill, its order-book line can still name a book as active that has in fact finished (PAN-5599). `pan orders list` and the dashboard apply the skip rule with the backfilled evidence.

The elapsed time counts from the flywheel conversation's creation, not from the loop's first tick, so a conversation that sat paused and was resumed reads as one long run. A tick-only id — one the loop named but that has no `workspaces/feature-*` directory — is derived against the flywheel's own project, so an id belonging to another project derives as `backlog` with no branch or PR rather than being resolved elsewhere. The headline strip's "bugs fixed" counts only bugs *filed* inside the window that have since closed; one filed earlier and closed inside it is not counted.
