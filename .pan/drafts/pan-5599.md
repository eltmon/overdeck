# PAN-5599: Order books — the queue skips finished books

**Issue:** https://github.com/eltmon/overdeck/issues/5599
**Depends on:** PAN-5597 (Order books page rework). It merged to `main` as `768054d9928` (#5606), so `src/lib/orders/phase.ts` exists. Work can start.

## Problem

The Flywheel releases work from one order book: the running book, else the first book with status `ready`. When every issue in that book has landed, the book still holds the slot. The next queued book does not start until a person archives the finished one. The Flywheel is meant to run without a person in the loop, so a finished book must not hold the queue.

### Correction to the original problem statement (verified 2026-11-23)

The issue cites the 2026-11-22 case of a July book holding the slot. That book is `2026-07-30-hardening-20260729`, and it is **not finished**: PAN-3290, PAN-3288 and PAN-3297 are open on GitHub and carry no `parked` label. Only PAN-3295 is closed. This change therefore does **not** release that book. A stale but unfinished book still needs a person to archive it or move it back to draft. Widening the rule to "stale" books is out of scope.

The change still matters for the live queue. Read-only `GET /api/orders` on the running dashboard on 2026-11-23 showed, in queue order:

| Book | Status | Progress | Finished |
| --- | --- | --- | --- |
| `2026-07-30-hardening-20260729` | ready | 1 of 4 landed | no (3 open) |
| `2026-11-13-file-explorer-pan-5183` | ready | 8 of 8 landed | yes |
| `2026-11-14-workflow-redesign-pan-5284` | ready | 26 of 28 landed | no |
| `2026-11-17-docs-overhaul-pan-5467` | ready | 23 of 23 landed | yes |

Today, archiving the hardening book makes the finished file-explorer book active, and the two open workflow-redesign issues stay unreleased. With this change, archiving the hardening book makes workflow-redesign active.

### A second defect this change must fix: finished evidence expires after 14 days

The dashboard's issue cache keeps closed issues only while they were updated within `issues.closedWindowDays` (default 14, `src/lib/config-yaml/defaults.ts:267`). Search anchor in `src/dashboard/server/services/issue-data-service.ts`: `The GitHub poll only fetches closed issues`. An issue closed earlier than that has no row, so `computeBookProgress` counts it as open. Two consequences:

1. A book that finishes stops reading as finished 14 days later. It then takes the active slot back from the book after it.
2. A book that runs longer than 14 days never reads as finished, because its first closed issues drop out before its last one lands.

Live evidence: before 2026-11-23 05:2x UTC the hardening book read 0 of 4 although PAN-3295 closed on 2026-09-26. A read-only `GET /api/issues/PAN-3295` ran the existing backfill door (`IssueDataService.backfillIssue`, PAN-3659), and the next `GET /api/orders` read 1 of 4. So the backfill door does feed `liveOrderIssueLookup`; this PRD uses it.

## Glossary

- **Book**: an order book, type `OrderBook` in `packages/contracts/src/orders.ts`. Stored statuses: `draft`, `ready`, `running` (legacy, nothing writes it), `complete`.
- **Queued book**: a book with stored status `ready`.
- **Active book**: the book whose issues count as operator-released for automatic pickup. `currentOrderBook` in `src/lib/orders/phase.ts` returns it.
- **Terminal issue**: closed, or carrying the `parked` label (or a legacy parked label).
- **Finished book**: a book with at least one issue where every issue is terminal. `computeBookProgress(book, lookup)` in `src/lib/orders/resolver.ts` returns `{ total, drained, … }`; finished means `total > 0 && drained`.
- **Finished rule**: the predicate `isBookFinished(progress)` this change adds to `phase.ts`.
- **Positive evidence**: the issue lookup returned a state for the issue. An issue the lookup does not know is not terminal (`computeBookProgress`, search anchor `const closed = issue ? !issue.open : false;`).
- **Issue lookup**: `liveOrderIssueLookup` in `src/lib/orders/resolver.ts`. It reads the shared issue service (`getSharedIssueService().getIssues({ cycle: 'all', includeCompleted: true })`) and returns an empty map when that service is unavailable.
- **Shared issue service**: the `IssueDataService` singleton in `src/dashboard/server/services/issue-service-singleton.ts`. The dashboard server starts it; `pan orders list` starts it read-only through `ensureOrderIssueStore()`; the deacon child process never starts it.
- **Backfill door**: `IssueDataService.backfillIssue(id)`. It fetches one issue that is missing from the cache through the tracker, holds it in an in-memory bucket that survives windowed polls, and calls `pushUpdated()`. Successes are memoized for the process lifetime (`src/dashboard/server/services/issue-title-fallback.ts`).
- **Closed window**: `issues.closedWindowDays`, default 14.
- **Deacon child**: the separate Node process started by `src/dashboard/server/services/deacon-supervisor.ts` from `deacon-main.ts`. It runs the Cloister service and its reactive lifecycle scheduler (`handleCloisterDomainEvent`).

## Decisions

- **D1. Skip, do not archive.** A finished book keeps status `ready`. Nothing writes a status. The active book is derived on every read: the running book, else the first `ready` book that is not finished. This keeps the rule "Overdeck stores no status it can derive".
- **D2. Fail safe.** A book is finished only on positive evidence for every issue. When the lookup is unavailable or does not know an issue, the book is not finished and the queue behaves as it does today.
- **D3. A `running` book stays first.** A book with stored status `running` is active even when finished. This is legacy data; nothing writes `running`. FR-3 has this one exception: such a book shows as Active and Finished.
- **D4. One function and one rule.** Dispatch, the orders API, `pan orders list` and the Flywheel status summary all call `currentOrderBook` with `isBookFinished`. Each process applies the rule to the evidence it has, so the readers can differ only when their evidence differs (see D7, H-list).
- **D5. Durable evidence through the backfill door.** Before the dashboard server derives phases, it asks the backfill door for every issue of a `ready` or `running` book that has no row in the cache, and waits for the answers up to 3000 ms. The backfill runs only when the shared issue service is started and holds at least one issue, so a started-but-empty store (boot, or a non-server process) does not try to fetch every issue.
- **D6. `pan orders list` prints the server's phases.** The CLI asks the dashboard (`GET <getDashboardApiUrl()>/api/orders?project=<key>`, 3000 ms timeout). When the dashboard answers and its book ids equal the local book ids in the same order, the CLI prints the server's phase, queue position and finished flag. Otherwise it derives phases locally, as today. Reason: the Flywheel loop reads the active book from `pan orders list` every tick; a one-shot CLI keeps no backfill memo, so it would otherwise either re-fetch aged issues from the tracker on every tick or name a finished book as active after 14 days.
- **D7. Dispatch keeps the plain lookup.** `activeOrderBookIssues` uses `computeBookProgress` with the default `liveOrderIssueLookup` and no backfill. Its only production caller is the reactive scheduler in the deacon child (`service-reactive.ts` → `gatherAutonomousWorkDispatchInput`). The deacon child never starts the shared issue service, so its issue list is empty; the label gate in `gatherAutonomousWorkDispatchInput` then returns `labels: null` and refuses before the book is consulted. Adding backfill or an HTTP read to dispatch would change nothing today. The real autonomous path is the Flywheel loop: `pan orders list` (D6) → `pan start`. This replaces the old PRD's checkpoint CP-1; it is decided here.
- **D8. Queue positions.** A queued book that is finished and not active gets `queuePosition: null`. Positions 1…n number the active book first, then the unfinished queued books in index order.
- **D9. Page placement of finished queued books.** In the book list and in the page's default-selection order, a queued book with `queuePosition: null` sorts after every numbered queued book.

## Requirements

- **FR-1** `currentOrderBook` skips `ready` books that are finished, and `deriveBookPhases` gives a finished non-active queued book phase `queued`, `finished: true` and `queuePosition: null`.
- **FR-2** Dispatch (`activeOrderBookIssues`), the orders API (`deriveBookPhases` via `bookPhases`) and the Flywheel status summary (`defaultRunningBook`) call `currentOrderBook` with `isBookFinished`.

- **FR-4** The docs describe the skip rule, the fail-safe, and the backfill.
- **FR-5** The dashboard server backfills the uncached issues of `ready`/`running` books before deriving phases (D5), so a book whose issues closed more than 14 days ago still reads as finished.

- **NFR-1** When the issue lookup returns nothing, every reader returns the same active book as before this change.
- **NFR-2** The backfill adds at most 3000 ms to one orders read, and makes no tracker request when the shared issue service is not started or holds no issues.

/**

## Hazards

- **H1. The incident book stays stuck.** `2026-07-30-hardening-20260729` has three open issues; this change does not move it. Say so in the PR description.
- **H2. Deacon dispatch reads no issues.** The deacon child never starts the shared issue service, so reactive work dispatch there refuses with `labels-unavailable` before it reads any book. This is pre-existing and out of scope; report it in the PR description, do not fix it here.
- **H3. Derived flips.** Reopening or un-parking an issue in an earlier finished book makes that book active again, ahead of the later book. This is accepted: the rule is derived. Dispatch also caches the active book for `RELEASE_CONTEXT_CACHE_MS` in `autonomous-work-dispatch.ts`, so it lags the page briefly.
- **H4. First read after a server restart.** The backfill memo is in memory. The first orders read after a restart waits up to 3000 ms for it; if the tracker is slow, that one read may still show an old finished book as unfinished (fail safe).
- **H5. One early inconsistent reading.** During discovery one `GET /api/orders` showed file-explorer at 0 of 8; ten later reads over two minutes were stable at 8 of 8. If the page ever flaps, look at the issue cache refresh, not at this rule.
