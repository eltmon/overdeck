## blocks-the-design: Polyrepo CI failures cannot match the verified head

The PRD's FR-2 covers `ci` tests mode without a monorepo limit ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4531/.pan/drafts/pan-4531.md), lines 37–38). A polyrepo workspace root is a one-commit wrapper; code heads live in nested repos ([project-repos.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4531/src/lib/project-repos.ts), lines 158–165). The runner reads `git rev-parse` at that wrapper ([verification-runner.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4531/src/lib/cloister/verification-runner.ts), line 301; [verification-decided-stop.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4531/src/lib/cloister/verification-decided-stop.ts), lines 27–30), then uses that short SHA to look up a CI result (lines 47–50 and 86–90). The CI relay records the actual PR `headSha` as its `head8` ([ci-failure-feedback.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4531/src/lib/cloister/ci-failure-feedback.ts), lines 300–313). These SHAs differ, so an already-red polyrepo head still runs every local gate. The existing tests exercise polyrepo workflow *detection* ([verification-tests-on-ci.test.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4531/tests/unit/lib/cloister/verification-tests-on-ci.test.ts), lines 456–458), but the red-head tests use a single Git repository at the workspace root (lines 260–270).

Resolve the CI verdict against the relevant sub-repo PR head, with repository identity where more than one PR exists, and add a polyrepo red-head runner test. If this issue is intentionally monorepo-only, state that limit in FR-2 and the xBRIEF instead.

## blocks-the-design: Merged stop uses a stale PR cache

The PRD requires a merge during a gate to stop before the next gate ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4531/.pan/drafts/pan-4531.md), lines 43–44). The runner calls `skipMergedVerification` at startup, which calls `getPrFacts` ([verification-runner.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4531/src/lib/cloister/verification-runner.ts), line 296; [verification-escalation.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4531/src/lib/cloister/verification-escalation.ts), lines 35–41). `getPrFacts` caches that unmerged answer for 60 seconds ([pr-facts.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4531/src/lib/cloister/pr-facts.ts), lines 590–627). Every between-gate check uses the same `skipMergedVerification` path ([verification-decided-stop.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4531/src/lib/cloister/verification-decided-stop.ts), lines 79–85). If a PR merges during a gate that finishes within the cache TTL, the next gate still starts. The merged-during-gate test replaces `getPrFacts` with a mutable mock, so it cannot expose this ([verification-tests-on-ci.test.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4531/tests/unit/lib/cloister/verification-tests-on-ci.test.ts), lines 16–20, 350–358).

Give decided-stop merge checks a fresh PR read that bypasses this memo, and test a merge while an unmerged answer is cached.

## sharpens-framing: Carry the three resolved edge rules into the xBRIEF

The draft xBRIEF's `gate-stop` action and acceptance criteria mention only a check at the top of each gate. The PRD explicitly also requires checks after CPU admission and before retries ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4531/.pan/drafts/pan-4531.md), lines 34–36 and 96–102); both points already exist in [validation.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4531/src/lib/cloister/validation.ts), lines 418–440. The xBRIEF's `ci-red-stop` and `superseded-restart` criteria also omit the failed-gate precedence and the `pre_push` limit for `notRun` that the PRD settled (lines 39–41 and 104–115; implemented in [verification-runner.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4531/src/lib/cloister/verification-runner.ts), lines 582–595). An executor following only the xBRIEF could lose these decisions while still satisfying its listed criteria.

Add those stop points, failed-gate outcomes, and the `pre_push` filter to the relevant xBRIEF actions and acceptance criteria.
