## Glossary

- **CLIProxy**: the CLIProxyAPI sidecar that Overdeck installs and supervises (`src/lib/cliproxy.ts`). It listens on `127.0.0.1:8317`, holds subscription OAuth logins, and serves one API endpoint to Claude Code agents that run GPT models. Pinned version: `v7.3.16` (`CLIPROXY_RELEASE_VERSION`, `src/lib/cliproxy.ts` line 69).
- **Pool**: every account (auth file) in the CLIProxy auth dir `~/.overdeck/cliproxy/auth/` (`getCliproxyAuthDir()`).
- **Account**: one auth file. The management API identifies it by `name` (the file name, for example `codex-primary.json`) and `auth_index` (a stable hex id).
- **Provider**: the `provider` field that `GET /v0/management/auth-files` reports, for example `codex`, `claude` or `gemini`.
- **Management API**: CLIProxy's admin HTTP API under `/v0/management/`. It needs `Authorization: Bearer <management key>`. In v7.3.16 the key is set by the top-level `remote-management.secret-key` config key. An empty key turns the API off.
- **Priority**: an integer per account, stored as a top-level `priority` field in its auth JSON. CLIProxy picks from the highest-priority tier that has an available account, round-robins inside that tier, and skips accounts in cooldown. Verified at v7.3.16: `sdk/cliproxy/auth/selector.go` `highestPriorityAuths` (line 585) and `authPriority` (line 364); `sdk/cliproxy/auth/priority.go` reads `metadata["priority"]`.
- **Session affinity**: the CLIProxy setting `routing.session-affinity`. It binds a conversation to one account for `session-affinity-ttl`. A bound session keeps its account even if priorities change. Priority decides only cold bindings, requests without a session, and rebinding after failover (v7.3.16 `config.example.yaml` lines 254–271). Prompt caches belong to one account, so affinity keeps caches warm.
- **Usage window**: one quota period that a provider reports for an account. It has a used percent and a reset time.
- **Weekly window**: the usage window with the longest duration. For Codex it is the window with the largest `limit_window_seconds` (604800 on the Pro account checked 2026-11-14). For Claude it is `seven_day`.
- **Exhausted**: an account that cannot serve now. For Codex that means `rate_limit.limit_reached === true` or `rate_limit.allowed === false`, or any window at `used_percent >= 100`. For Claude it means any of `five_hour` or `seven_day` at `utilization >= 100`.
- **Reset-first ranking**: the controller's rule. Inside each provider, the non-exhausted account whose weekly window resets soonest gets the highest priority.
- **`config.extra.yaml`**: the operator-owned file `~/.overdeck/cliproxy/config.extra.yaml`. `buildCliproxyConfig` appends it verbatim to the generated `config.yaml` (`readConfigExtra`, `src/lib/cliproxy.ts` line 329).

## Background

CLIProxy round-robins requests across the accounts of a provider. When an account's window resets, any quota it has not used is gone. If account A resets tomorrow and account B resets in 4 days, the pool should use A first. Upstream CLIProxy has no reset-aware strategy (`round-robin`, `weighted-round-robin`, `fill-first` only). It does honour per-account `priority`, so Overdeck can get reset-first routing by rewriting priorities, with no fork.

T3 Code reads pooled usage through the same management API (`pingdotgg/t3code` `apps/server/src/usage/cliproxyApi.ts`): `GET auth-files`, then `POST api-call` per account to the provider's usage endpoint with the account's token. Write our own implementation from the shapes below. Do not copy theirs.

## Decisions

1. **No fork, no version bump.** Keep `v7.3.16`. Reset-first ranking goes through `priority`.
2. **Ranking rule.** Do this per provider, only for `codex` and `claude`. Ranking runs only when the provider has 2 or more eligible accounts (not disabled, usage read OK). With fewer than 2, the controller writes nothing.
   - Sort the eligible non-exhausted accounts by weekly-window reset time, soonest first. Ties go to the lower used percent, then to `auth_index` ascending.
   - With `n` non-exhausted accounts, the first gets priority `n * 10`, the next `(n - 1) * 10`, and so on down to `10`.
   - Exhausted accounts get priority `0`. CLIProxy uses them only if no other account is available.
   - Accounts with a read error or no weekly window keep their current priority. The controller does not touch them.
   - Disabled accounts are skipped and keep their current priority.
3. **The controller owns `priority`** on every eligible `codex` and `claude` account. This is documented. There is no setting to turn it off. To take an account out of rotation, the operator sets `disabled: true`, as before.
4. **Cadence.** The controller refreshes every 5 minutes, plus once 10 seconds after the dashboard starts. A refresh that starts while another is running is skipped (`tickInFlight` pattern from `startCliproxyWatchdog`).
5. **Where it runs.** Only on host dashboards. Start it next to the watchdog in `startCliproxyWatchdogForDashboard` (`src/dashboard/server/routes/cliproxy.ts`), which already returns false on peer dashboards.
6. **Reset credits are not redeemed.** Do not call `POST /v0/management/reset-quota` or any `rate-limit-reset-credits` endpoint. They spend a banked credit. Show no "Use reset" button.
7. **Gemini and other providers.** List them in the panel with provider and email only, and state "usage not read". They are never ranked.
8. **The route stays `admin`.** Do not add a `route-scopes.ts` row. Unlisted routes need `admin` (`src/dashboard/server/route-scopes.ts` header).
9. **The snapshot is in memory only.** It is not written to disk or to the read model (Overdeck stores no status it can derive).

### 3. Pool reader (FR-4, NFR-1)

New file: `src/lib/cliproxy-pool.ts`. It is a leaf module: import only from `./cliproxy.js` (for `CLIPROXY_BASE_URL`, `readManagementKey`) and Node or Effect built-ins. Use plain `fetch` with `AbortController` + `setTimeout(15_000)` for timeouts. Do not use `AbortSignal.timeout`, which ignores Vitest fake timers.

Exports:

```ts
export type PoolProvider = 'codex' | 'claude' | string;

export interface PoolWindow {
  /** 'weekly' | '5-hour' | 'primary' | 'secondary' — label for display. */
  label: string;
  usedPercent: number;
  /** ISO time, or null when the provider gave none. */
  resetsAt: string | null;
  windowSeconds: number | null;
}

export interface PoolAccount {
  name: string;          // auth file name, used for PATCH
  authIndex: string;
  provider: PoolProvider;
  email: string | null;
  plan: string | null;
  disabled: boolean;
  priority: number | null;
  windows: PoolWindow[];
  weeklyResetsAt: string | null;
  exhausted: boolean;
  /** Short reason when usage could not be read; never contains upstream body text. */
  error: string | null;
  usageRead: boolean;    // false for providers we do not read (gemini, …)
}

export interface PoolSnapshot {
  checkedAt: string;
  managementAvailable: boolean;
  accounts: PoolAccount[];
}

export async function readPool(): Promise<PoolSnapshot>;
export async function setAccountPriority(name: string, priority: number): Promise<void>;
```

Behaviour:

1. `readPool` reads the management key with `readManagementKey()`. If it is missing, it returns `{ managementAvailable: false, accounts: [] }`.
2. It calls `GET ${CLIPROXY_BASE_URL}/v0/management/auth-files` with the bearer key. On a non-2xx answer or a timeout it returns `managementAvailable: false`.
3. For each `codex` or `claude` account that is not disabled, it calls `api-call` with the request shapes from "Verified response shapes". It runs at most 4 accounts at once.
4. Codex parse: windows from `primary_window` and `secondary_window`, skipping nulls. `resetsAt` = `new Date(reset_at * 1000).toISOString()` when `reset_at` is a number. Label `weekly` when `limit_window_seconds >= 6 * 86400`, `5-hour` when it is `<= 6 * 3600`, otherwise `primary`/`secondary`. The weekly window is the one with the largest `limit_window_seconds`. `plan` = `plan_type` or `id_token.plan_type` or `id_token.chatgpt_plan_type`. `exhausted` is defined in the glossary.
5. Claude parse: windows `five_hour` → label `5-hour`, `seven_day` → label `weekly`. `resetsAt` = `resets_at`. `plan` = `'Claude subscription'`.
6. An `api-call` with `status_code` outside 200–299 sets `error: 'HTTP <code> from provider'`. A JSON decode failure sets `error: 'unreadable usage response'`.
7. `setAccountPriority` sends `PATCH /v0/management/auth-files/fields` with `{ name, priority }` and throws a `CliproxyError` (from `./cliproxy.js`) on a non-2xx answer.
8. Never log or return the management key, tokens, or upstream body text.

### 4. Reset-first controller (FR-5, NFR-3)

New file: `src/lib/cliproxy-routing.ts`.

Exports:

```ts
/** Pure. Returns the priority to set per account name, only for accounts whose priority must change. */
export function planPriorities(accounts: readonly PoolAccount[]): Map<string, number>;

export function getPoolSnapshot(): PoolSnapshot | null;
export async function refreshPool(): Promise<PoolSnapshot>;

```

Behaviour:

1. `planPriorities` applies Decision 2 per provider and returns only changes (`desired !== account.priority`).
2. `refreshPool` calls `readPool()`, then `planPriorities`, then `setAccountPriority` for each change one at a time. It updates each changed account's `priority` in the snapshot, stores the snapshot in a module variable, and returns it. A failed PATCH logs `[cliproxy-routing] priority update failed for <name>` (name only) and leaves that account unchanged.
3. `startCliproxyRoutingController` ticks 10 s after start and then every 5 minutes, with a `tickInFlight` guard. Errors are logged and never thrown. Each tick first lists accounts (`GET auth-files`, local only). It calls `refreshPool` only when some provider (`codex` or `claude`) has 2 or more enabled accounts. Otherwise it makes no upstream usage calls. With one account, ranking cannot change anything, and calling ChatGPT's usage endpoint every 5 minutes for nothing is avoidable traffic.
4. `refreshPool` is the only function that calls `setAccountPriority`. Add `export async function readPoolSnapshot(): Promise<PoolSnapshot>`. It calls `readPool()`, overlays nothing, stores the snapshot, and never PATCHes. The route uses it.
