## Glossary

Define these before reading further; every later section uses them.

- **Benchmark template** — a markdown issue body under `benchmarks/templates/<name>.md` plus a matching spec under `benchmarks/specs/<name>.md`, describing self-contained fictional work (like the existing QuantumLlama provider). Benchmark branches are **never merged**; runs exist for measurement only.
- **Variant / arm** — one configuration under test. Each variant becomes its **own GitHub issue** (created from the same template) with its own workspace and feature branch. We never run the same issue twice: an issue is 1:1 with its workspace and branch, so a second run would collide with or inherit the first run's state.
- **Runner** — the dispatch topology for an arm: `start` (one work agent executes the whole xBRIEF via `pan start`) or `swarm` (per-item dispatch across slots via `pan swarm`).
- **Standing crew** — tiered execution (`docs/TIERED-EXECUTION.md`): warm long-lived tier sessions staffed by task difficulty, a foreman owning commit boundaries, an everyone-hears-everything commit feed, and an event-driven supervisor. Only exists on the swarm path. "Crew off" in a swarm means slots are staffed from the implicit one-tier world (`roles.work` resolution, `src/lib/agents/staffing.ts`).
- **Benchmark group** — the set of arm-issues launched together for one comparison. Identified by a shared GitHub label `benchmark-group:<slug>`.
- **Plan shape** — the measurable structure of a finalized xBRIEF: item count, dependency width, independence quality, difficulty spread, kind mix. Defined precisely in "Plan shapes" below.
- **Dependency width** — the maximum number of xBRIEF items that could execute concurrently, i.e. the size of the largest antichain in the item dependency graph. A plan of 7 items where 6 depend on 1 foundation item has width 6 (after the foundation lands).
- **Critical path** — the longest dependency chain through the plan; the lower bound on serial execution regardless of parallelism.
- **Record door** — the single write path for per-issue permanent records: `updateIssueRecord` in `src/lib/pan-dir/record-update.ts`. All durable stamping in this feature goes through it (two-door rule; see `docs/API-SURFACE.md`).
- **Close-out usage** — the `closeOut` block (usage, merges, ranOn) in the per-issue permanent record; the durable cost source for reports (`docs/AGENT-STATE-PLANES.md`).

## Background

Today `/benchmark` (machine-local skill at `~/.claude/skills/benchmark/SKILL.md`) creates ONE issue per invocation from `benchmarks/templates/quantumllama.md`, labeled `benchmark`. Comparison across configurations is fully manual: the operator asks an agent to set up each arm, flip per-issue toggles by hand, and eyeball cost records afterward.

The immediate need (operator, 2026-07-25): A/B **standing crew vs normal crew vs single agent** on cost, wall-clock, and outcome quality — and, longer-term, accumulate data that grounds a mechanical start-vs-swarm recommendation (PAN-3061).

## Plan shapes — the swarm-decision insight

Swarm buys exactly one thing: it converts **parallelism already present in the plan** into wall-clock savings. It charges for that in coordination: foreman + supervisor tokens, a commit feed that scales with slots × commits, and **assembly risk** when items are not truly independent (PAN-2383: dependent beads' tests needed foundation code that lived on another slot's branch; verification failed on two slots; the issue required manual assembly). A single `pan start` agent has none of that overhead but executes the critical path serially.

Whether swarm pays is therefore a property of the plan's **shape**, readable from the xBRIEF before anything runs:

| Feature | Definition (mechanical) |
| --- | --- |
| `item_count` | Number of implementation items in the spec |
| `dependency_width` | Size of the largest set of items with no dependency relations among them (largest antichain). With no explicit dependency edges in the spec, approximate as: items whose `files_scope` sets are pairwise disjoint AND `readiness == 'ready'` |
| `independence_fraction` | Items with `readiness == 'ready'` and `files_scope_confidence == 'high'` ÷ `item_count` |
| `difficulty_spread` | Count of items per difficulty (`trivial`/`simple`/`medium`/`complex`/`expert`) |
| `kind_mix` | Count of items per kind |
| `critical_path_len` | Longest chain of items whose `files_scope` sets overlap pairwise (overlap ⇒ ordered) |

**Worked example — the two shipped shapes (Work items 6–7):**

*Wide fan-out* (`wide-fanout` template): 1 foundation item (a notifier registry interface) + 6 independent adapter items, each touching only its own new file pair (`src/lib/notifiers/<name>.ts` + test). Shape: `item_count 7`, `dependency_width 6`, `independence_fraction ~0.86`, difficulties mostly simple/medium, `critical_path_len 2` (foundation → any adapter). Prediction: swarm wall-clock ≈ foundation + max(adapter) + coordination, vs start ≈ sum of all items — swarm should win wall-clock decisively; cost verdict depends on coordination overhead vs tier savings.

*Serial chain* (`serial-chain` template): 5 items forming one pipeline (schema → parser → aggregator → cost mapper → CLI display), every item consuming the previous item's output and touching the same module. Shape: `item_count 5`, `dependency_width 1`, `independence_fraction ~0`, difficulties medium/complex, `critical_path_len 5`. Prediction: swarm ≈ start's wall-clock PLUS coordination overhead and assembly risk — start should win on every metric. If it doesn't, that itself is a finding.

The benchmark's arms are the treatments; these shape features are the predictors. One template = one shape, so quantifying the crossover **requires shape variance** — hence two new templates with deliberately opposite shapes, plus (later, PAN-3061) retrospective mining of close-out records from real issues.

## Requirements

### Functional

- **FR-1** `pan benchmark launch --template <name> --variant <spec> [--variant <spec>]...` creates one GitHub issue per variant from `benchmarks/templates/<name>.md` via the tracker client's `createIssue()`, titled `Benchmark: <TemplateTitle> — <variantName> [<group-slug>]`, labeled `benchmark` and `benchmark-group:<slug>` (slug auto-generated `bg-YYYYMMDD-<4char>`, overridable with `--group <slug>`; labels created idempotently like the existing skill does).
- **FR-2** Variant spec grammar: semicolon-separated `key=value` pairs. Keys: `name` (required, unique in group), `runner` (required, `start`|`swarm`), `crew` (`on`|`off`, only valid with `runner=swarm`, default `on`), `model` (optional model ID validated via `normalizeModelOverrideSync`). Validation errors name the offending variant and key and create **nothing** (all-or-nothing). `model` combined with `crew=on` is rejected with the message that a work-model override suspends crew routing.
- **FR-3** Stamping is mechanical and uses only existing doors, immediately after each issue is created: `runner=swarm` → `record.swarm.policy.mode='always'`; `runner=start` → `'off'` (both via the same `updateIssueRecord` write `staffing.ts` performs). `crew=off` → the per-issue tiered-execution record override set to Off through the same record-write helper the PATCH route uses (Work item 2 extracts that helper if it is currently inline in the route, so CLI and route share one door). `model=<id>` → `record.workModel`. A `benchmark` block `{ group, variant, template, launchedAt }` is written into each issue's record in the same update.
- **FR-4** Execution: `--serial` (the default) launches arm N+1 only after arm N reaches its completion boundary (`readyForMerge` true, or a terminal failure state) — completion detected by polling the review-status/read-model at a fixed interval. `--concurrent` launches all arms immediately and the report must carry the contention caveat (NFR-2). Launch invokes the explicit verb per arm: `pan swarm <id>` for `runner=swarm`, `pan start <id>` for `runner=start` (the stamped swarm policy is belt-and-suspenders for deacon behavior, but the launcher does not rely on policy-driven verb selection).
- **FR-5** `pan benchmark report <group>` renders one row per arm: variant name | runner/crew/model | total cost (close-out usage; live per-workspace cost data as fallback while the arm is unfinished) | wall-clock (first agent-spawn event → `readyForMerge` event, from the `events` table) | tokens in/out | verification attempts | review verdict | escalations/promotions (crew arms; from `tierOverrides` in workspace continue state). Sources are durable records only — no pane scraping.
- **FR-6** The report also renders the group's **plan-shape block**: the six features from "Plan shapes", extracted at report time from each arm's finalized spec via `findSpecByIssue` (arms share a template, so shapes should match; per-arm extraction catches planning nondeterminism, and a mismatch is reported, not hidden). Extraction is a pure function in `src/lib/benchmark/plan-shape.ts` so PAN-3061 can reuse it.
- **FR-7** Ship two new benchmark templates + specs with deliberately opposite shapes: `wide-fanout` and `serial-chain`, as characterized in "Plan shapes" above. Fictional, self-contained (QuantumLlama-style "What NOT to do" section included), never-merge.
- **FR-8** Ship the wrapper skill `skills/pan-benchmark/SKILL.md` per `docs/SKILLS-CONVENTION.md` (lint-skills cross-checks flags against `pan benchmark --help` — same commit as the CLI verb). Update the local `/benchmark` skill's replacement path: its SKILL.md gains a pointer that multi-arm comparisons use `pan benchmark launch`.
- **FR-9** Docs updated in the same change: `docs/TIERED-EXECUTION.md` (benchmarking section pointing here), a new `docs/BENCHMARKS.md` (template authoring + shape design guidance), and the Mintlify page if a `reference/benchmarks` page exists (if none exists, note that in the PR body rather than creating a new Mintlify page).

### Non-functional

- **NFR-1** No `execSync` anywhere server-reachable; the CLI launcher uses async exec/spawn only. Any test exercising the serial-launch polling loop MUST use `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()` (repo fake-timers rule) — no real waits.
- **NFR-2** A report over arms that ran concurrently must print a contention caveat naming the overlap. A report never blocks on live agents; unfinished arms render with partial data and an explicit `running` marker.
- **NFR-3** No hardcoded model or harness anywhere in launcher/report; variants carry models explicitly or inherit resolved routing. Missing config fails loudly (no-hardcoded-fallback rule).

## Intersecting repo rules (restated for the executor)

Fake timers for any retry/poll/delay test (never real `setTimeout`; never `maxForks: 1` to mask OOM). No `execSync` in server-reachable code. Benchmark branches are never merged. Agents never `git stash`. Work runs through the pipeline (`pan start`); commit each work item as it lands with a meaningful message. Model/harness resolution must fail loudly — no hardcoded fallbacks. When the CLI changes, the wrapper skill changes in the same commit.
