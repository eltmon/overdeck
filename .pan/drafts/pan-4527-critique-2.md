## blocks-the-design: In-flight requests bypass the head check

Evidence: `src/dashboard/server/routes/workspaces/review-pipeline.ts`, lines 243-245, returns `already-running` before a second request reaches verification. `src/lib/cloister/request-review-pipeline.ts`, lines 29-47, skips that request and continues the first run to push and review. `src/lib/cloister/verification-worker-supervisor.ts`, lines 170-182, performs the new head comparison only after the supervisor is called. Thus a re-review for commit B in the same dashboard process never exercises FR-2 while the A pipeline is active. The PRD itself acknowledges this at `.pan/drafts/pan-4527.md`, lines 94-103, and assigns the repair to a separate PR. The smallest change is to make the request guard retain a newer-head request and rerun verification before push/review, with a test that submits B while A is in flight.

## blocks-the-design: A moved head inherits stale local gates

Evidence: `src/lib/cloister/verification-runner.ts`, lines 548-584, computes the local gate results before `resolveVerifiedHeadShort` selects the current head at lines 601-606. The pass path at lines 892-955 records and pushes a success without confirming those gates ran on that selected head. `tests/unit/lib/cloister/verification-tests-on-ci.test.ts`, lines 285-296, commits B inside the mocked quality gate and expects the run to pass using B's CI verdict. A real gate could have passed on A while B introduces a type or lint failure, yet the pipeline can label B verified. The PRD acknowledges this at `.pan/drafts/pan-4527.md`, lines 114-120, but the draft's acceptance test currently endorses it. The smallest change is to stop and rerun all gates when the head changes during verification; make the test require a fresh B run before a pass.

## blocks-the-design: Merge shape cannot prove sync ownership

Evidence: `src/lib/cloister/verification-head.ts`, lines 49-57, labels any two-parent commit with first parent A and second parent on `origin/<target>` as `synced`. It does not distinguish the worker's `syncSingleRepo` merge (`src/lib/cloister/verification-runner.ts`, lines 113-124) from an agent-made merge with edited conflict resolution. The supervisor then joins A's worker (`src/lib/cloister/verification-worker-supervisor.ts`, lines 181-185), and the runner reads A's CI verdict (`src/lib/cloister/verification-runner.ts`, lines 279-281 and 601-606). That reproduces the stated old-head result for a new merge head, and the merge may contain code the worker never checked. Existing worker state is already updated during a run by `markVerificationWorkerAdmissionPhase` (`src/lib/cloister/verification-worker-supervisor.ts`, lines 119-136). The smallest change is to record the actual post-sync head in that state and classify only that recorded transition as the worker's sync; add an agent-created merge with a resolution edit to the classifier and join tests.

## sharpens-framing: CI-head requirement silently excludes polyrepos

Evidence: FR-1 explicitly covers polyrepo anchors, while FR-4 says the runner reads the verdict for the verified head (`.pan/drafts/pan-4527.md`, lines 37-43). Yet `readWorkspaceHeadShort` runs Git at `workspacePath` (`src/lib/cloister/verification-runner.ts`, lines 257-265), and `resolveVerifiedHeadShort` falls back to that same wrapper repo (`src/lib/cloister/verification-runner.ts`, lines 272-282). `snapshotWorkspaceHeads` documents that the wrapper HEAD never changes in polyrepos (`src/lib/git-utils.ts`, lines 375-385). The PRD notes the bug and defers it at lines 122-127. The smallest change is to scope FR-4 and its acceptance criterion to monorepos explicitly, or make the polyrepo CI-head fix a prerequisite before claiming FR-4 complete.
