# PAN-5020 — Stop parallel PRs from conflicting on the codebase map's `last-verified` line

**Issue:** [PAN-5020](https://github.com/eltmon/overdeck/issues/5020)

## Glossary

- **Codebase map** — the four orientation files under `.overdeck/context/codebase/`: `architecture.md`, `concerns.md`, `conventions.md`, `stack.md`. Planning agents read them first and correct them during discovery (`roles/plan.md`, item 4).
- **Footer** / **`last-verified` line** — the HTML comment at the end of each map file, canonically `<!-- last-verified: YYYY-MM-DD -->`.
- **Date-only form** — a footer that matches exactly `^<!-- last-verified: [0-9]{4}-[0-9]{2}-[0-9]{2} -->$`: no issue ids, no other text, no trailing spaces.
- **Per-touch bump** — the current rule: every agent that corrects one statement also changes the footer date.
- **Full refresh** — re-verifying a whole map file end to end, as the `/pan-map` skill workflow does ("Write or refresh all four files together").
- **Union merge** — git's built-in `merge=union` driver (`.gitattributes`). It keeps both sides' lines of a conflict hunk instead of writing conflict markers. Only `concerns.md` has it among the map files (PAN-4614).
- **Conflict-repair prompt** — the instruction text `buildConflictRepairPrompt` (`src/lib/cloister/conflict-repair.ts`) sends a work agent whose approved PR conflicts with `main`.
- **`Prompt-Change:` trailer** — a commit-message trailer that `scripts/check-prompt-change-trailer.sh` (`npm run lint:prompt-trailer`) requires on some commit of any branch that changes `roles/*.md` or `sync-sources/skills/pan-flywheel/SKILL.md`.

## Problem

On 2026-11-04, almost every parallel PR conflicted with `main` in `.overdeck/context/codebase/architecture.md`: PAN-4947 (three times), PAN-4935, PAN-4956 (twice) and PAN-4950. Each conflict cost a repair round, a fresh verification and a fresh review.

The footer of `architecture.md` (line 358) reads:

```
<!-- last-verified: 2026-11-04 (PAN-4956, PAN-4998, PAN-4935, PAN-4947, PAN-4946, ... 30+ issue ids) -->
```

Each agent prepends its own issue id. So two PRs that both touched the map always change this one line to two different values, and git cannot merge them. `concerns.md` has the same list on three footer lines (735, 742, 750); its union merge kept every differing copy, so two stray footers now sit mid-file. `conventions.md:85` and `stack.md:83` are already date-only (`2026-11-03`).

Nothing asks for the id list. These sites all describe a date-only footer:

- `roles/plan.md:49` — "correct the file and update its `<!-- last-verified: -->` date as part of this session."
- `roles/plan.md:50` — "ends with `<!-- last-verified: YYYY-MM-DD -->`"
- `sync-sources/skills/pan-map/SKILL.md:22` — "End each file with exactly one `<!-- last-verified: YYYY-MM-DD -->` line."
- `sync-sources/skills/pan-map/SKILL.md:24` — "Update stale statements and the `last-verified` date when you confirm a change."
- `src/lib/cloister/conflict-repair.ts:116` — `"   - .overdeck/context/codebase/*.md: keep both sides' statements and refresh the \`<!-- last-verified: -->\` date.",`

Agents copy the list because it is there.

### Why date-only alone is not enough (measured)

The planner tested git 2.43 merges in a scratch repo. Base footer `2026-11-03`; side A and side B each make one edit and change the footer:

| Case | Result |
| --- | --- |
| Both sides edit different mid-file lines, both stamp `2026-11-04` | CLEAN |
| Both sides edit different mid-file lines, stamps `2026-11-04` vs `2026-11-05` | CONFLICT |
| A appends a paragraph at the end of the file; B only bumps the footer date | CONFLICT |
| A appends a line right before the footer; both stamp the same date | CONFLICT |
| `concerns.md` (union), both add a bullet, same date | CLEAN, one footer |
| `concerns.md` (union), both add a bullet, different dates | CLEAN, **two** footers survive |

Date-only fixes the observed case (every 2026-11-04 conflict was a mid-file edit plus a same-day footer change: hunks at lines 230, 326, 340, 343 with the footer at 352–358). It still conflicts whenever two PRs stamp different dates, and whenever one PR appends at the end while another touches the footer. The per-touch bump is what keeps the footer in every PR's diff.

## Decisions

- **D1 — Footer is date-only.** The footer holds only the date. Issue ids and every other provenance go in commit messages.
- **D2 — No per-touch bump.** A correction to one statement leaves the footer unchanged. Only a full refresh of a file (the `/pan-map` workflow) changes its date. The date then means "last time the whole file was verified", which is what the word says, and parallel PRs no longer touch the footer at all. The issue's fix list does not forbid this; it is a one-sentence change at the same three instruction sites the issue already names.
- **D3 — Conflict repair keeps the later date.** If a footer still conflicts (two full refreshes, or a PR branched before this change), the repair keeps one footer with the later of the two dates, date-only.
- **D4 — The lint checks format, never count.** `concerns.md`'s union merge can put two date-only footers on `main` with no PR CI run in between (the merge door's server rebase produces it). `lint` is a required check on `main`, and a red `main` empties the merge gate. So the lint fails on a footer that is not date-only, and accepts two date-only footers. Removing a stray footer stays an agent instruction ("delete a stray one"), not a lint rule. Review must not "tighten" the lint to count footers.
- **D5 — The lint matches footer lines only.** A line is a footer when it starts (after optional whitespace) with `<!--` followed by optional whitespace and `last-verified`. Prose that mentions `last-verified` mid-line is not checked, so a map bullet can still describe this rule.
- **D6 — Bash lint script, unit-tested.** The guard is `scripts/lint-last-verified.sh`, wired as `npm run lint:last-verified` and appended to the `lint` chain in `package.json`. `scripts/run-lint-group.mjs` puts every step not named in `HEAVY_STEPS` in the `core` group, so it runs in CI with no change to `.github/workflows/ci.yml`. A vitest file under `tests/unit/scripts/` exercises it against temp fixtures, following `tests/unit/scripts/lint-quarantine-audit.test.ts`. A vitest test that reads the real map files was rejected: the lint covers the real files on every CI run.
- **D7 — End-of-file appends are out of scope.** Two PRs that both append a paragraph at the end of `architecture.md` conflict on content, footer or not. That is a real content conflict and stays one.

## Requirements

- **FR-1** Every footer in `.overdeck/context/codebase/*.md` is in date-only form, and each file has exactly one footer, as its last line.
- **FR-2** `roles/plan.md` tells planners: the footer holds only the date, never issue ids; provenance belongs in commit messages; a correction to one statement leaves the date unchanged; only a full refresh changes it.
- **FR-3** `sync-sources/skills/pan-map/SKILL.md` gives the same rule, and names `npm run lint:last-verified`.
- **FR-4** The conflict-repair prompt tells the agent to keep both sides' statements and, on a conflicting footer, keep one footer with the later date and no issue ids.
- **FR-5** `npm run lint:last-verified` exits non-zero and names the file and line when any map footer is not in date-only form; it exits 0 when every footer is date-only, including two date-only footers in one file, and when the map directory is absent.
- **FR-6** `npm run lint` runs `lint:last-verified`, so CI's `lint-group (core)` job runs it.
- **FR-7** `docs/PIPELINE-GATES.md` and `docs/MERGE-WORKFLOW.md` describe the new conflict-repair rule and the lint.
- **NFR-1** The commit that changes `roles/plan.md` carries a `Prompt-Change:` trailer, so `npm run lint:prompt-trailer` passes.
- **NFR-2** No new source-introspection offender: the new test reads only a `.sh` file and temp fixtures, never a `.ts` path (`scripts/lint-source-introspection.sh` counts `readFile` calls whose arguments contain a `.ts`/`.tsx` string literal).

### W5 — `lint:last-verified` guard (FR-5, FR-6, NFR-2)

New file `scripts/lint-last-verified.sh` (mode 0755), in the style of `scripts/lint-quarantine-audit.sh`:

```bash
#!/usr/bin/env bash
#
# lint-last-verified.sh — every codebase-map footer must be exactly
# `<!-- last-verified: YYYY-MM-DD -->` (PAN-5020). Agents appended issue ids to
# the footer, so every parallel PR edited the same line and conflicted.
# Provenance belongs in commit messages. A footer is a line that starts with
# `<!-- last-verified`; prose that mentions the word mid-line is not checked.
# The number of footers is NOT checked: a union merge of concerns.md can leave
# two date-only footers on main, and a red lint there would block every merge.
set -euo pipefail
cd "$(dirname "$0")/.."

MAP_DIR=".overdeck/context/codebase"
FOOTER_RE='^[[:space:]]*<!--[[:space:]]*last-verified'
VALID_RE='^<!-- last-verified: [0-9]{4}-[0-9]{2}-[0-9]{2} -->$'

shopt -s nullglob
files=("$MAP_DIR"/*.md)
if [[ ${#files[@]} -eq 0 ]]; then
  echo "✓ lint:last-verified passed (no codebase map)"
  exit 0
fi

checked=0
fail=0
for file in "${files[@]}"; do
  lineno=0
  while IFS= read -r line || [[ -n "$line" ]]; do
    lineno=$((lineno + 1))
    [[ "$line" =~ $FOOTER_RE ]] || continue
    checked=$((checked + 1))
    if [[ ! "$line" =~ $VALID_RE ]]; then
      echo "✖ $file:$lineno: ${line:0:100}" >&2
      fail=1
    fi
  done < "$file"
done

if (( fail )); then
  echo "" >&2
  echo "lint:last-verified failed. A codebase-map footer holds only the date:" >&2
  echo "  <!-- last-verified: YYYY-MM-DD -->" >&2
  echo "Put issue ids and other provenance in the commit message." >&2
  exit 1
fi

echo "✓ lint:last-verified passed ($checked footer lines checked)"
```

## Intersecting repo rules (restated)

- Edits to `roles/*.md` need a `Prompt-Change:` trailer on a branch commit (`npm run lint:prompt-trailer`).
- Tests must not read `.ts` source text (`lint:source-introspection` baseline is shrink-only).
- No `git stash`; never `git checkout` another branch inside the workspace.
- Quality gates before `pan done`: `npm run typecheck`, `npm run lint`, and `npx vitest run` on the touched test files only. Never run the full `npm test` on the host.
- File-size ratchet: no non-test `src` file may grow past its `origin/main` line count; W4 replaces one line in place.

## Acceptance criteria

1. (W1) `grep -c 'last-verified' .overdeck/context/codebase/*.md` prints 1 per file, and every footer matches the date-only regex.
2. (W2) `roles/plan.md` item 4 says the footer holds only the date, never issue ids, and that a single correction leaves the date unchanged; a branch commit carries `Prompt-Change:`.

4. (W4) `buildConflictRepairPrompt` output contains `keep one line with the later date only, never issue ids` and no longer says "refresh the … date"; the updated unit test passes.
5. (W5) `npm run lint:last-verified` exits 0 on the branch, and the five unit cases pass; `npm run lint` invokes it.
6. (W6) `docs/PIPELINE-GATES.md` and `docs/MERGE-WORKFLOW.md` carry the new rule and name the lint.

## Non-goals

- Making end-of-file appends to `architecture.md` merge cleanly (D7).
- Adding `merge=union` to `architecture.md`, `conventions.md` or `stack.md` (union would interleave prose paragraphs).
- A lint that counts footers or requires the footer to be the last line (D4).
- Changing `.gitattributes`, the merge door, or `pan sync-main`.
- Shrinking `architecture.md` or `concerns.md` to the 150-line target.
