# PAN-4680 — Serialize GitHub quota ledger appends so file order is call order

**Issue:** [PAN-4680](https://github.com/eltmon/overdeck/issues/4680)
**Status:** planned (auto mode, 2026-11-01)

## Glossary

- **Ledger** — the GitHub quota ledger owned by `src/lib/github-quota/ledger.ts`. Every metered GitHub call and every rate-limit sample appends one JSON line to `~/.overdeck/github-quota/ledger-<YYYYMMDDHH>.jsonl` (UTC hour).
- **Queued append** — `queueLedgerEntry(input)`: fire-and-forget append used on the metered call path (`run-gh.ts`, `rest-meter.ts`) so metering never delays the call it measures.
- **Direct append** — `await appendLedgerEntry(input)`: awaited append used by `sampler.ts` and `pause-gate.ts` (and many tests).
- **Flush** — `flushLedgerWrites()`: resolves once every append queued so far has landed. CLI exit (`src/cli/telemetry.ts`) and tests call it.
- **Prepare step** — the synchronous part of an append: stamp `ts`/`pid`, resolve the ledger dir and the hour file path. It must run at call time.
- **Write step** — the asynchronous part of an append: `mkdir`, `appendFile`, and the once-per-hour prune.
- **Append chain** — a module-level promise; each write step starts only after the previous one settles.
- **NFR-2 (PAN-4264)** — "metering never fails a caller": no ledger write may throw or reject into a caller.

The test (`tests/unit/lib/github-quota/run-gh.test.ts`, lines 51-60, grep anchor `takes the caller from context, else records other`) makes two `runGh` calls in sequence, flushes, and asserts the ledger lines are in call order.

### Root cause (verified at `7fc87456019`)

`src/lib/github-quota/ledger.ts`:

- Lines 114-135 (`export async function appendLedgerEntry`): stamps the entry and resolves `dir`/`file` synchronously, then `await mkdir(dir, { recursive: true })` and `await appendFile(file, …)`.
- Lines 137-148 (grep `const pendingAppends = new Set<Promise<void>>();`): `queueLedgerEntry` starts `appendLedgerEntry(input)` immediately and only tracks the promise in a `Set`. Nothing serializes the appends.
- Lines 151-153: `flushLedgerWrites` does `await Promise.all([...pendingAppends])`.

`runGh` returns before its queued append lands. The second `runGh` queues a second append while the first is still inside `mkdir`. Both go to the libuv threadpool, so the `appendFile` that finishes first is not necessarily the one queued first. `readLedgerWindow` (line 185) returns lines in file order, so the test sees completion order.

Production readers aggregate (`aggregateLedger`), so order rarely matters in production. But the module header (lines 1-15) and `docs/PIPELINE-GATES.md` describe an append log, and the race makes the test flaky on CI.

## Requirements

- **FR-1** — Every append from one process (queued or direct) reaches the ledger file in call order. Append N's write step starts only after append N-1's write step has settled.
- **FR-2** — The prepare step runs synchronously at call time: `ts` (when not supplied) is the metering time, `pid` is stamped, and the dir and hour file are resolved from the `OVERDECK_HOME` current at call time — even when the write step runs later. (This preserves the existing guarantee in the comment at `ledger.ts` lines 120-121: "Resolve both paths before the first await, so a queued append lands in the home that was current when the call was metered.")
- **FR-3** — A failed append (a rejected `mkdir`/`appendFile`, or a throwing prepare step) does not stop later appends, and does not make `flushLedgerWrites` or `appendLedgerEntry` reject.
- **FR-4** — `flushLedgerWrites()` resolves once every append started before the call has settled.
- **FR-5** — `appendLedgerEntry` still resolves only after its own entry is on disk, so `pause-gate.ts` can read its own refusal back immediately.
- **NFR-1** — No timers, no polling, no new dependencies. The chain is a plain promise.
- **NFR-2** — Metering never fails a caller (PAN-4264 NFR-2 restated).
- **NFR-3** — `ledger.ts` keeps exactly one variant per operation (repo rule "one variant per operation in src/lib"): no new exported sync/async twins. `readLedgerWindow` stays sync.
- **NFR-4** — Tests use a hand-released deferred promise to slow `mkdir`, never real `setTimeout` delays (repo rule: fake timers / no real delays in tests; memory: fake timers that gate real I/O time out on CI, so do not use fake timers here either).

## Decisions

1. **Direct appends join the same chain.** `appendLedgerEntry` enqueues onto the append chain and awaits its own link. Rationale: FR-1 is only true for the whole file if both entry points share one order. The cost is that a direct append may wait behind queued appends that are already in flight — a few milliseconds of local disk I/O. (autoDecision.)
2. **Split prepare from write.** The chain callback calls the private write step, never `appendLedgerEntry`. Calling `appendLedgerEntry` from inside a chain link would make it wait on its own tail and deadlock.
3. **Each link swallows its own failure** with `.catch(() => undefined)` even though the write step already catches internally. The chain tail therefore never rejects (FR-3), and a future edit that forgets the inner `try` cannot break the chain.
4. **The once-per-hour prune stays inside the write step.** `flushLedgerWrites` keeps waiting for it, as it does today. Because the write steps are now serial, the `lastAppendHour` check no longer races.
5. **Cross-process order is out of scope.** The dashboard, deacon, CLI, and agent shim write the same files from separate processes. `O_APPEND` keeps lines whole; their relative order stays arrival order.
6. **New test file, not `ledger.test.ts`.** The new tests mock `node:fs/promises`. A `vi.mock` is file-wide, so it goes in a new file `tests/unit/lib/github-quota/ledger-queue.test.ts` and cannot affect the prune/append tests in `ledger.test.ts`.
7. **The 50-run proof uses a bash loop.** Vitest 4 has no `--repeat` CLI flag (checked with `npx vitest --help`). Each run enters the shared CPU admission queue, so the work agent runs the loop once as proof, not repeatedly.
8. **No change to `run-gh.test.ts`.** It keeps asserting call order; the fix makes that assertion true.

```ts
let lastAppendHour: number | null = null;

/** An entry stamped and placed at call time, waiting for its turn on disk. */
interface PreparedAppend {
  entry: LedgerEntry;
  dir: string;
  file: string;
  nowMs: number;
}

/**
 * Stamp `ts` and `pid` and resolve the ledger paths synchronously, so a queued
 * append lands in the home that was current when the call was metered.
 * Returns null instead of throwing (NFR-2).
 */
function prepareLedgerAppend(input: LedgerEntryInput): PreparedAppend | null {
  try {
    const nowMs = Date.now();
    const entry: LedgerEntry = { ...input, ts: input.ts ?? new Date(nowMs).toISOString(), pid: input.pid ?? process.pid };
    const entryMs = Date.parse(entry.ts);
    const fileMs = Number.isFinite(entryMs) ? entryMs : nowMs;
    return { entry, dir: getGitHubQuotaDir(), file: ledgerFilePath(fileMs), nowMs };
  } catch {
    return null;
  }
}

/** Write one prepared entry, then prune on the first append of a new UTC hour. Never throws. */
async function writeLedgerAppend({ entry, dir, file, nowMs }: PreparedAppend): Promise<void> {
  try {
    await mkdir(dir, { recursive: true });
    await appendFile(file, `${JSON.stringify(entry)}\n`);

    const hour = Math.floor(nowMs / HOUR_MS);
    if (lastAppendHour !== hour) {
      lastAppendHour = hour;
      await pruneLedger(nowMs, dir);
    }
  } catch {
    // NFR-2: metering never fails the caller.
  }
}

/** Tail of the append chain; it never rejects. */
let appendChain: Promise<void> = Promise.resolve();

/**
 * Prepare now, write after every earlier append has settled, so the file
 * order is the call order. Returns this entry's link of the chain.
 */
function enqueueLedgerAppend(input: LedgerEntryInput): Promise<void> {
  const prepared = prepareLedgerAppend(input);
  if (!prepared) return appendChain;
  const link = appendChain.then(() => writeLedgerAppend(prepared)).catch(() => undefined);
  appendChain = link;
  return link;
}

/**
 * Append one entry to the current hour's ledger file and resolve once it has
 * landed. Shares the queued appends' order. Never throws.
 */
export async function appendLedgerEntry(input: LedgerEntryInput): Promise<void> {
  await enqueueLedgerAppend(input);
}

/**
 * Append an entry without making the caller wait for the disk. Metered GitHub
 * calls use this on their normal path, so metering never delays the call it
 * measures. Appends land in call order; `flushLedgerWrites` awaits them.
 */
export function queueLedgerEntry(input: LedgerEntryInput): void {
  void enqueueLedgerAppend(input);
}

/** Resolve once every append started so far has landed. */
export async function flushLedgerWrites(): Promise<void> {
  await appendChain;
}
```

## Critique response

### Gated mkdir never creates the ledger directory

Accepted. The draft's gate resolved the first `mkdir` with `undefined`, so the `github-quota` directory was never created and the first `appendFile` would fail with `ENOENT` (swallowed by NFR-2), dropping entry 1 and breaking tests 1-3 even with the fix in place. WI-2 now gates the real operation: the first `mkdir` waits on the deferred and then calls the actual `mkdir` from `vi.importActual('node:fs/promises')`. The notes also state why resolving with `undefined` is wrong.

### Timestamp test checks only the home

Accepted. Test 3 now spies on `Date.now` (no fake timers): it returns `queuedAt` while the entries are queued and `queuedAt + 30_000` before the gate is released, and the test asserts both entries' `ts` equal `new Date(queuedAt).toISOString()`. An implementation that stamps `ts` at write time now fails this test. The WI-2 acceptance row and `queue-order-test.ac3` name both properties.
