## 1. Glossary

Terms from the parent glossary (explorer pane, code pane, explorer root, root id, Overdeck trash) apply unchanged.

- **Write action** — any tree action that changes files: New file, New folder, Rename, Duplicate, Delete, drag move, OS drop (upload), and undo or redo of one of these.
- **Writable tree** — an explorer pane whose root is `issue:` or `workspace:` **and** whose Changed filter is off. Write actions appear and work only in a writable tree (D-E1, D-E2).
- **`runWrite` seam** — the single function in `useExplorerActions.ts` that every write RPC and upload call goes through. Today it calls the operation with the pane's root id. PAN-5191 (child F, edit workspaces) wraps it with `withEditWorkspace` to make `project` roots writable. No other code path in this issue calls a write RPC.
- **Inline name row** — the text input that the tree shows in place of a row (rename) or as a new first child of a folder (create).
- **Undo op** — one entry on a root's undo stack: one user action (for example "delete 3 items"), made of one or more **steps**. A step is one reversible server call pair, for example "restore trash id X / move path P to the trash again".
- **Refusal** — a server error that guarantees nothing was written: a `PanRpcError` (or `ExplorerHttpError`) whose code is `ALREADY_EXISTS`, `NOT_FOUND` or `INVALID_TARGET`. A refused undo can be retried.
- **Drag payload** — the two `DataTransfer` types a tree row drag carries: `application/x-overdeck-paths` (root-relative paths, one per line, for the composer) and `application/x-overdeck-explorer` (JSON `{ rootId, paths }`, for drag move).
- **Drop zone** — the element in `ExplorerPane` that wraps the tree body, including the empty-folder message, and handles drag move and OS drop.
- **Top-level paths** — a set of paths with every path removed whose ancestor folder is also in the set (`a` and `a/b` → `a`).

## 3. Decisions

- **D-E1 Project roots get no write actions in this issue.** On a `project:` root the menu shows no write items, the header shows no New buttons, the keys do nothing, drag move is refused and an OS drop shows the toast "The main checkout is read-only, so files can't be added here." Drag to composer still works, because it writes nothing. PAN-5191 lifts this by wrapping `runWrite` (D-E3) and changing the one `writable` predicate. This follows PAN-5186 D-B7 and PAN-5187 D-C12. It replaces parent WI-13 step 9 ("Every write action first goes through `withEditWorkspace`"), which cannot ship here: `withEditWorkspace` is PAN-5191's, and PAN-5191 depends on this issue.
- **D-E2 No write actions in the Changed view.** Changed-view rows are synthesized from git status. They can include deleted files and folders that were never listed. So while the Changed filter is on, the tree is not writable (same effects as D-E1, with the OS-drop toast "Turn off the Changed filter to add files."). Drag to composer still works.
- **D-E3 One write seam.** `createExplorerActions` holds `runWrite<T>(op: (rootId: string) => Promise<T>): Promise<T>`. Every create, rename, copy, delete, restore and upload call goes through it. It throws `explorerError`-shaped `Error('The main checkout is read-only.')` when the root is a `project` root, as a guard behind the hidden UI.
- **D-E4 Undo ops are step-wise.** Port Orca's stack (50 ops per root, a new op clears redo). An op is `{ label, steps }`. Undo runs the steps that are not yet undone, last to first. Redo runs them first to last. Each op remembers how many steps are undone. On an error:
  - a **refusal** (`ALREADY_EXISTS`, `NOT_FOUND`, `INVALID_TARGET`) puts the op back where it came from, with its progress kept, so a retry continues where it stopped;
  - any other error drops the op from history, because the server state is unknown and a replay could overwrite newer work.
  The error is thrown to the caller, which shows a toast.
- **D-E5 Rename and move keep open code panes.** For a rename or move from `from` to `to`, in this order:
  1. collect every draft key of this root whose path is `from` or starts with `from + '/'`, and `await codeSaveQueue.whenIdle(key)` for each;
  2. call `explorerRename`;
  3. `useCodeDrafts.getState().rekey(oldKey, newKey)` for each key;
  4. for every deck in `panesByWorkspace`, every `'code'` pane with this `explorerRootId` and an affected `explorerPath` gets `updatePane(deck, paneId, { explorerPath: newPath, label: codePaneLabel(newPath) })`;
  5. `useExplorerStore.getState().renamePaths(rootId, from, to)` rewrites the expanded set, the selection, the anchor and the focused path, and drops cached listings at or under `from`;
  6. re-list the parents of `from` and `to` and refresh git status.
  Step 3 before step 4 means the old autosave controller's dispose finds no draft at the old key and sends nothing (fact 8). A dirty draft that had an armed autosave timer stays dirty under the new key; it saves on the next edit, blur or `Ctrl/Cmd+S`. Undo and redo of a rename run the same sequence in reverse.
- **D-E6 Delete is one call per top-level path.** `remove(paths)` reduces the paths to top-level paths and calls `explorerDelete({ rootId, paths: [p] })` for each, in order, collecting `trashIds[0]`. If call *k* fails, the op is committed with the *k − 1* steps that succeeded, and the error toast names the path that failed. Each step is `{ undo: restore(trashId), redo: trashId = delete(path) }`. The trash id is mutable, because redo returns a new one.
- **D-E7 Undo of a create trashes, it never deletes.** Create, Duplicate and upload commit steps `{ undo: trashId = delete(path), redo: restore(trashId) }`. So content written into a new file after it was created survives an undo-and-redo round trip.
- **D-E8 Delete confirmation.** A single item deletes at once. Two or more items, or any item (or descendant) with an unsaved code-pane draft, first show `useConfirm` with the title "Delete N items?" (or "Delete <name>?") and a message listing the paths. With unsaved drafts the message adds the line "Unsaved edits in: <paths>". After a delete, a toast "Moved <name> to the Overdeck trash" (or "Moved N items to the Overdeck trash") shows for 8 s with an **Undo** action that undoes that op (D-E9).
- **D-E9 The toast's Undo undoes its own op.** `undoEntry(rootId, opId)`: if the op is the top of the undo stack, it behaves as `undo(rootId)`. Otherwise it runs that op's undo, removes the op from history, and does not add it to redo (redoing out of order is not defined).
- **D-E10 Where creates and drops land.**
  - The target folder of New file / New folder: the right-clicked or single selected row if it is a folder, its parent folder if it is a file, and the root when nothing is selected or the menu opened on blank space.
  - Right-clicking blank tree space clears the selection, so the menu's targets are the root.
  - Starting a create in a collapsed folder expands it first. The inline row is the first child of the target folder (index 0 for the root), whether or not the folder's listing has loaded.
  - A drop on a folder row targets that folder. A drop on a file row targets the file's parent. A drop on blank space or the empty-folder message targets the root.
- **D-E11 Name rules.** The inline row trims its value. It refuses, with a message shown under the input: an empty name ("Enter a name."), `.` or `..` ("This name is reserved."), a name with `/`, `\` or a NUL ("Names cannot contain / or \."), the name `.git` in any case ("Overdeck does not write .git folders."), and a name that already exists among the loaded siblings, compared exactly ("<name> already exists here."). The server is still the authority: an `ALREADY_EXISTS` answer shows the same message and keeps the row open.
- **D-E12 Duplicate naming** (port of Orca's loop, extended to folders). The stem is the text before the last `.` when that dot is not the first character, else the whole name. Candidates are `<stem> copy<ext>`, then `<stem> copy 2<ext>`, `<stem> copy 3<ext>`, …, skipping names among the loaded siblings. `archive.tar.gz` → `archive.tar copy.gz`; `.env` → `.env copy`; folder `src` → `src copy`. On `ALREADY_EXISTS` (a name taken after the listing loaded) it tries the next candidate, at most 10 times.
- **D-E13 Moves.** `planMoves(sources, destDir)` reduces the sources to top-level paths, skips a source already in `destDir` (no-op), and skips a source when `destDir` is the source or inside it (toast "Can't move a folder into itself."). Each remaining source moves to `destDir/<basename>`, one `explorerRename` per source, and the moves form one op. A drag whose payload `rootId` is not this pane's root is refused with the toast "Files can only be moved within the same tree."
- **D-E14 Drag behavior.** Folders expand after 600 ms of drag hover (the timer restarts when the hovered row changes). The tree scrolls when the pointer is within 24 px of its top or bottom edge, using Orca's `getDragEdgeScrollTarget` with `edgeZonePx: 24`. The drop target folder row shows `bg-accent/60` with an inset `ring-ring` outline. A root drop target outlines the drop zone instead.
- **D-E15 Drag payload.** A row drag carries the paths of the whole selection (reduced to top-level paths) when the dragged row is selected, otherwise the dragged row alone. `effectAllowed` is `'copyMove'`. No `text/plain` is set, so text fields elsewhere in the dashboard ignore the drag.
- **D-E16 OS drop.**
  - Recognize a dropped folder by `DataTransferItem.webkitGetAsEntry()?.isDirectory === true`, read synchronously inside the `drop` handler, because items become unreadable after the handler returns. The parent PRD rules out `webkitGetAsEntry` for walking folder contents; reading its `isDirectory` flag does not walk anything. When `webkitGetAsEntry` is missing, the item is treated as a file.
  - Folders are skipped with one toast "Drop files, not folders: <names>".
  - Files over 100 MiB are skipped before sending, with the toast "<name> is larger than 100 MiB."
  - Files upload one at a time through `runWrite`. An `ALREADY_EXISTS` answer gives the toast "<name> already exists in <folder or 'the root'>" and skips that file; nothing is overwritten.
  - All successful uploads of one drop form one op (D-E7 steps). When at least one file uploaded, the toast reads "Uploaded N files" ("Uploaded <name>" for one).
- **D-E17 Drag to composer inserts at the caret.** When the composer drop carries `application/x-overdeck-paths`, the paths are inserted, joined by `\n`, at the editor's range selection with `insertRawText`. With no range selection (the editor was never focused), the root's end is selected first, so the paths are appended. The editor then takes focus. The drop is ignored under the same guard as file drops (`sending || !conversation.sessionAlive`). Only `ComposerFooter` (the conversation composer) accepts the drop.
- **D-E18 Keys.** While the tree has focus: `F2` renames the single selected row; `Delete`, or `Backspace` with `Meta`, deletes the selection (with D-E8's confirmation rules); `Ctrl/Cmd+Z` undoes; `Ctrl/Cmd+Shift+Z` redoes. The inline name row stops propagation of every `keydown`, so typing in it never moves the tree's focus or opens a file. An `Enter` with `event.nativeEvent.isComposing` true does not commit (IME input).
- **D-E19 After every write** the action re-lists the affected parent folders (`reloadDirs`) and refreshes git status. It does not wait for the watcher, because ignored folders are not watched and the watcher may be in poll mode.
- **D-E20 Undo and redo toasts.** A successful undo shows "Undid <label>", a redo "Redid <label>". Nothing to undo or redo shows nothing. Labels: "new file <name>", "new folder <name>", "rename of <old name>", "duplicate of <name>", "delete of <name>" / "delete of N items", "move of <name>" / "move of N items", "upload of <name>" / "upload of N files".

### Functional

- **FR-E4** Duplicate creates the first free copy name (D-E12) next to the original and selects it.
- **FR-E5** Delete moves the entries to the Overdeck trash with D-E8's confirmation and undo toast.
- **FR-E6** Dragging rows onto a folder moves them there (D-E13, D-E14).
- **FR-E7** `Ctrl/Cmd+Z` and `Ctrl/Cmd+Shift+Z` undo and redo the root's last file actions, up to 50 (D-E4, D-E7, D-E20).
- **FR-E8** Dropping OS files onto a folder row, blank tree space or the empty-folder message uploads them (D-E16).
- **FR-E9** Dragging tree rows onto a conversation composer inserts their root-relative paths at the caret, one per line (D-E17).

### WI-E1 — Write wrappers in the RPC seam  (FR-E1–FR-E8, NFR-E1)

```ts
export function createEntry(rootId: string, path: string, kind: 'file' | 'dir'): Promise<ExplorerEntryResult> {
  return getTransport().request((client) => (client as PanRpcProtocolClient)[WS_METHODS.explorerCreate]({ rootId, path, kind }))
}
export function renameEntry(rootId: string, from: string, to: string): Promise<ExplorerEntryResult>   // explorerRename
export function copyEntry(rootId: string, from: string, to: string): Promise<ExplorerEntryResult>     // explorerCopy
/** Move one path to the Overdeck trash; returns its trash id (D-E6). */
export async function trashPath(rootId: string, path: string): Promise<string> {
  const { trashIds } = await getTransport().request((client) =>
    (client as PanRpcProtocolClient)[WS_METHODS.explorerDelete]({ rootId, paths: [path] }),
  )
  const id = trashIds[0]
  if (!id) throw new Error(`The server returned no trash id for ${path}`)
  return id
}
export function restoreEntry(rootId: string, trashId: string): Promise<ExplorerRestoreResult>          // explorerRestore
```

Import `ExplorerEntryResult` and `ExplorerRestoreResult` types from `@overdeck/contracts`.

**Tests:** in `explorer-rpc.test.ts`, with the file's existing fake transport, each wrapper sends the exact method and payload; `trashPath` returns `trashIds[0]`, and rejects when `trashIds` is empty.

**API:**

```ts
// Ported from Orca (MIT, Copyright (c) 2026 Lovecast Inc.)
// upstream: src/renderer/src/components/right-sidebar/file-explorer/mutations/fileExplorerUndoRedo.ts @ c6b9ac9549b
export const MAX_UNDO_OPS = 50
export const REFUSAL_CODES: ReadonlySet<string> = new Set(['ALREADY_EXISTS', 'NOT_FOUND', 'INVALID_TARGET'])
export interface UndoStep { undo(): Promise<void>; redo(): Promise<void> }
export interface UndoOp { label: string; steps: readonly UndoStep[] }
export function commitOp(rootId: string, op: UndoOp): string            // returns an op id; clears the root's redo list; drops the oldest past op beyond 50
export function undo(rootId: string): Promise<string | null>           // label of the undone op, or null when nothing to undo
export function redo(rootId: string): Promise<string | null>
export function undoEntry(rootId: string, opId: string): Promise<string | null>   // D-E9
export function hasUndo(rootId: string): boolean
export function hasRedo(rootId: string): boolean
export function clearUndoHistory(rootId?: string): void                // no argument: every root (tests)
```

**Behavior:** per-root `{ past, future }` in a module-level `Map`. Each stored op records `done` = how many steps are currently applied (all of them after a commit). `undo` pops the top of `past` and runs `steps[done-1].undo()` down to `steps[0]`, decrementing `done` after each success; when `done` reaches 0 the op goes on `future`. `redo` runs `steps[done].redo()` up to the last step, then pushes the op on `past`. On an error: if the error's code (read with `explorerErrorCode`, or `.code` on any error object that has a string `code`) is in `REFUSAL_CODES`, the op goes back on the stack it was popped from with its `done` count kept; otherwise it is dropped. Then the error is rethrown. An op with zero steps is never committed (`commitOp` returns `''` and stores nothing).

**Tests:** commit then undo runs the steps in reverse and returns the label; redo runs them forward; a new commit clears redo; the 51st commit drops the oldest; a refusal on step 2 of 3 during undo keeps the op on `past`, and a second undo runs only the remaining steps; a non-refusal error drops the op; `undoEntry` on a non-top op runs its undo and leaves redo unchanged; roots are independent.

- `recordCreated`: commits one op with one D-E7 step per path.
- `undo` / `redo` / `undoEntry`: call WI-E2, then toast "Undid <label>" / "Redid <label>"; on an error, `toast.error("Couldn't undo <label>: <message>")`. Undo and redo steps also run D-E19.
- Every successful write calls `reloadDirs` with the affected parent folders and `refreshGit()` (D-E19).
- When `writable` is false, every action except `undo`/`redo` returns at once without a call. `undo`/`redo` also return at once on a `project` root.
