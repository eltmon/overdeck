# PAN-4885 — Give a secure-channel open to an online link its own budget

**Issue:** [PAN-4885](https://github.com/eltmon/overdeck/issues/4885) — found during the PAN-4882 live re-run of
Anywhere AC-4 (evidence: `.pan/uat/pan-4882/ac-04-fly-worker-lanes.md`, section "Remote worker").

## Glossary

- **Link** — an outbound machine link from this dashboard to another Overdeck machine. The link supervisor
  (`src/dashboard/server/services/link-supervisor.ts`) keeps its state: `connecting`, `online`, `offline`,
  `unsupported`, `revoked`.
- **Secure channel** — one Noise IK session over a transport (`tcp://…` or `wss://…/ws/link`). Opened on the
  initiator side by `openChannel` (`src/lib/anywhere/channel/open.ts`), whose deadline logic is
  `withDeadline` in `packages/anywhere-channel/src/initiator.ts`.
- **Open budget** — the `timeoutMs` passed to `openChannel`. It bounds the whole open: transport connect
  (TLS + WebSocket upgrade for `wss://`) plus the handshake. On expiry it rejects with
  `ChannelOpenError('timeout', 'Secure channel to <url> did not open within <timeoutMs> ms')`.
- **Connecting wait** — how long `openLinkSocket` waits for a `connecting` link to become `online` before it
  fails with `LinkUnavailableError('machine-unreachable', …)`. Today `LINK_WAIT_MS` (2.5 s).
- **Public Fly route** — a link route of the form `wss://pan-workspaces.fly.dev/ws/link?fly-instance=<id>`:
  TLS to the Fly edge, the `fly-force-instance-id` header pins one machine, then the Noise handshake.
- **Work door** — an owner-side `/api/machines/work/*` route; home posts to it through `postWorkDoor`
  (`src/dashboard/server/routes/fleet-work.ts`) with its own 30 s bound (`WORK_DOOR_TIMEOUT_MS`).

## Problem

`openLinkSocket` uses one constant for two different waits. Verified in
`src/lib/anywhere/link-client.ts` (search for `export const LINK_WAIT_MS`):

```ts
// line 29
export const LINK_WAIT_MS = 2_500;
...
// lines 109-121, openLinkSocket
  if (info!.state !== 'online' || !info!.url) {
    const label = info!.label;
    const online = await routes.waitOnline(environmentId, LINK_WAIT_MS);   // connecting wait
    ...
  }
  return openChannel(info!.url, {
    mode: 'link',
    localKey: await routes.localKey(),
    remoteKeyHex: info!.machineKey,
    timeoutMs: LINK_WAIT_MS,                                              // open budget
    ...(opts.signal ? { signal: opts.signal } : {}),
  });
```

The 2.5 s connecting wait is deliberate: a user-facing call must not hang on a machine that is not
online. Reusing it as the open budget for an **already-online** link is not: over the public Fly route,
TLS to the edge plus the instance pin plus the handshake misses 2.5 s often enough that two of three
`pan worker run --machine fly-87477d7a911d28 …` starts failed on 2026-11-03 with

```
Could not start the worker on fly-87477d7a911d28: fly-87477d7a911d28: Secure channel to wss://pan-workspaces.fly.dev/ws/link?fly-instance=87477d7a911d28 did not open within 2500 ms
```

while `pan machines list --json` showed the link `online` with a heartbeat 4 s old. The third identical
command succeeded. The `secure channel` package's own default budget is 10 s
(`DEFAULT_OPEN_TIMEOUT_MS = 10_000`, `packages/anywhere-channel/src/initiator.ts` line 41).

### Request path (verified)

`pan worker run --machine <label>` → `POST /api/fleet/workers` (home) → `postWorkDoor`
(`src/dashboard/server/routes/fleet-work.ts`, `WORK_DOOR_TIMEOUT_MS = 30_000`, line 119) →
`fetchPeer` = `linkFetch` (line 149) → `http.request` with `agent: LinkAgent` →
`LinkAgent.createConnection` (link-client.ts lines 134-141) → `openLinkSocket(environmentId, { routeSource })`
→ `openChannel(…, { timeoutMs: LINK_WAIT_MS })`. The channel-open rejection becomes the request's `error`,
`postWorkDoor` turns it into `503 { code: 'machine-unreachable', error: '<label>: Secure channel … 2500 ms' }`,
and the CLI prints it (`src/cli/commands/worker-remote.ts` line 129).

Every other `openLinkSocket` caller shares the same budget: `src/dashboard/server/ws-linked.ts` (line 45,
linked `/ws/linked/<env>/rpc|terminal`), `src/dashboard/server/services/port-forwards.ts` (line 46), and every
`linkFetch`/`linkForward` through `LinkAgent`.

## Decisions

- **D-1: Separate the open budget from the connecting wait; do not retry.** Add
  `export const LINK_OPEN_MS = 10_000;` to `link-client.ts` and pass it as `openChannel`'s `timeoutMs`.
  `LINK_WAIT_MS` stays 2.5 s and stays the connecting wait. Rationale: the evidence shows two consecutive
  failures 22 s apart followed by a success — a slow window lasting tens of seconds, not an isolated drop. A
  retry fired 2.5 s into the same slow window would likely fail again; a larger budget lets the slow open
  finish. 10 s equals the package's own `DEFAULT_OPEN_TIMEOUT_MS`, so the number is not new to the codebase,
  and it fits well inside the 30 s work-door bound.
- **D-2: `LINK_OPEN_MS` is its own literal, not an import of `DEFAULT_OPEN_TIMEOUT_MS`.** The link client's
  budget is a policy of this module; tying it to the package default would silently move it if the package
  default changes. The doc comment names the package default as the reason for the value.
- **D-3: A link that was `connecting` and came online in time gets the same `LINK_OPEN_MS` budget.** After
  `waitOnline` succeeds the link is online, so the same reasoning applies. Worst case for that path is
  2.5 s + 10 s.
- **D-4: Callers keep their own shorter bounds through `signal`.** `linkFetch` passes `init.signal` to
  `http.request` (link-client.ts line 262), so fleet routes with their own 2.5 s controllers keep their bound:
  `FLEET_SEARCH_TIMEOUT_MS = 2_500` (`routes/fleet-awareness.ts` line 61), `FLEET_USAGE_TIMEOUT_MS = 2_500`
  (`routes/fleet-usage.ts` line 30), and `fetchPeer` in `routes/machines-fleet.ts` (line 240, per-call
  `timeoutMs`). No caller changes.
- **D-5: Accepted tradeoff.** Callers with no signal (`ws-linked.ts`, `port-forwards.ts`, and `linkFetch`
  calls without `signal`) now wait up to 10 s, not 2.5 s, before a channel open to an online-but-dead machine
  fails. The supervisor marks such a link `offline` within 20 s anyway (heartbeat rule in
  `docs/ANYWHERE-ARCHITECTURE.md` "The link supervisor"), after which calls fail at once.
- **D-6: The module header states the new rule.** link-client.ts lines 14-17 currently say "No user-facing call
  waits more than 2.5 s on an unreachable machine". That sentence becomes false for an online link and must be
  rewritten (see WI-1).

## Requirements

- **FR-1** `openLinkSocket` passes `timeoutMs: LINK_OPEN_MS` (10 000 ms) to `openChannel` for an `online` link.
- **FR-2** `openLinkSocket` still waits at most `LINK_WAIT_MS` (2 500 ms) for a `connecting` link, and fails with
  `LinkUnavailableError('machine-unreachable')` when the link does not come online; after it comes online the
  open uses `LINK_OPEN_MS`.
- **FR-3** An open that finishes after 2.5 s but before 10 s resolves with the channel; an open still pending at
  10 s rejects with `ChannelOpenError` code `timeout` and message `… did not open within 10000 ms`.
- **FR-4** `offline`, `revoked`, `unsupported` and missing links still fail at once, without calling `openChannel`.
- **FR-5** `docs/ANYWHERE-ARCHITECTURE.md` and `configuration/linked-machines.mdx` state the two budgets.
- **NFR-1** No change inside `packages/anywhere-channel/`; the error text still comes from `withDeadline`.
- **NFR-2** Tests use fake timers only (`vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync`); no real sockets
  under fake timers.

- No retry of a failed channel open (D-1). The stale-channel resend for `GET`/`HEAD`/`OPTIONS` stays as it is.
- No change to the link supervisor's 2.5 s probe budget (`link-supervisor.ts`); it has its own retry loop.
- No change to `LINK_WAIT_MS` or to the connecting-wait behavior.
- No change inside `packages/anywhere-channel/` (`DEFAULT_OPEN_TIMEOUT_MS`, `withDeadline`, error text).
- No change to Fly routing (`fly-force-instance-id`, `FLY_INSTANCE_PARAM`) or to `WORK_DOOR_TIMEOUT_MS`.
- No change to fleet callers' own 2.5 s signals.
- No live Fly re-run is required to merge; the behavior is proved by fake-timer tests.
