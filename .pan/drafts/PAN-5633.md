# PAN-5633: Codex auth banner never fires for app-server conversations

**Issue:** https://github.com/eltmon/overdeck/issues/5633
**Status:** planned (auto planning, 2026-11-23)
**Sibling issue (conversation UI follow-up):** [PAN-5636](https://github.com/eltmon/overdeck/issues/5636), see "Split" below.

## Summary

A Codex conversation failed every turn for 14 hours because its shared refresh token was already used. The dashboard showed nothing. The Codex auth banner stayed silent, the conversation list showed `isWorking: true`, and nothing said the context was full once sign-in was fixed.

This PRD replaces the dead "burn flag" path with a signal derived from the Codex rollout transcript, which already records every failed turn with a structured error code. The banner, the spawn gate, the conversation list and the conversation panel all read that one signal.

Overdeck stores no status it can derive. The failure is in the rollout, so this plan reads it from there and stores nothing new.

## Glossary

- **Rollout**: the Codex CLI transcript, `rollout-<timestamp>-<threadId>.jsonl`, under `<agentDir>/codex-home*/sessions/YYYY/MM/DD/`. Every Codex session (conversation or work agent, app-server or TUI) writes one. `resolveCodexRolloutPath(agentId)` (`src/lib/agents/transcript-resolver.ts`, line 155) finds it.
- **Turn event**: a rollout record `{"type":"event_msg","payload":{"type": T}}` where `T` is `task_started` (a turn began), `task_complete` (a turn ended) or `turn_aborted` (a turn was interrupted).
- **Failed turn**: a `task_complete` payload that carries an `error` object. Verified shape (rollout of `conv-20261118-427e`, 2026-11-23T17:33:20Z):
  `{"type":"task_complete","turn_id":"…","last_agent_message":null,"error":{"message":"Error running remote compact task: Your access token could not be refreshed because your refresh token was already used. Please log out and sign in again.","codex_error_info":"unauthorized"},…}`
  A successful `task_complete` has no `error` key at all (verified on the same rollout, 2026-11-18T14:30:49Z).
- **`codex_error_info`**: the structured error code. In the rollout it is snake_case (`unauthorized`, `context_window_exceeded`). In app-server notifications it is camelCase (`unauthorized`, `contextWindowExceeded`). The full enum is in `src/lib/codex/__fixtures__/app-server-schema.json` (`definitions/v2/CodexErrorInfo`): string values `contextWindowExceeded, sessionBudgetExceeded, usageLimitExceeded, serverOverloaded, cyberPolicy, internalServerError, unauthorized, badRequest, threadRollbackFailed, sandboxError, other`, plus object variants such as `{"responseStreamDisconnected":{…}}`.
- **Failure kind**: this PRD's classification of a failed turn: `auth` (the sign-in is dead), `context-window` (the context is full and compaction failed) or `other`.
- **Native auth store**: `~/.codex/auth.json` (`getNativeCodexAuthPath()`, `src/lib/codex-auth.ts`). Every managed `CODEX_HOME` symlinks its `auth.json` to it, so one `codex login` heals every session. Its mtime is the "you last signed in at" reference.
- **Active auth failure**: an auth-kind failed turn whose timestamp is at or after the native auth store's mtime. A failure older than the mtime is healed: someone signed in again after it.
- **Burn flag (dead path)**: the agent-state marker `troubled` + `lastFailureReason` prefixed `codex-auth-burned[<ISO>]`. Nothing in `src/` writes it. PAN-3917 removed the deacon pane patrol that wrote it, and the dashboard route stopped passing agent states (`src/dashboard/server/routes/codex-auth.ts` line 160: `checkCodexAuth({})`).
- **providerError**: the per-row field on `GET /api/conversations` rows that says the last turn ended in a provider error (`ConversationProviderError`, `src/lib/overdeck/conversation-provider-error.ts` line 31). Today only Claude Code rows set it. The Agents Live view already turns it into a Needs-you row with the message (`src/dashboard/frontend/src/components/Agents/live/live-model.ts` line 105).

## Root cause (verified)

1. **The burn flag has no writer.** `git grep "codex-auth-burned" -- src` finds only the readers in `src/lib/codex-auth.ts` (lines 180-268) and their tests. The route passes `{}` (`routes/codex-auth.ts` line 160), so even a written flag would not reach the banner. Conversations have no `state.json` (`~/.overdeck/agents/conv-20261118-427e/` holds none), so the issue's suggested `saveAgentStateSync` writer would need a new store.
2. **The static classifier cannot see a burned refresh token.** `classifyNativeCodexAuth` (`src/lib/codex-auth.ts` line 111) reports `valid` when an expired access token has a refresh token. That is correct: a refresh token is usable until a refresh fails, and only a failed refresh proves otherwise.
3. **The header comment is wrong.** Lines 182-186 say the failure "never lands in the rollout JSONL". For current Codex CLIs it does, as `task_complete.error` (Glossary).
4. **`isWorking` stays true after a failed turn.** The Codex conversation parser (`src/dashboard/server/services/codex-conversation-parser.ts`) sets `lastTurnCompletedAt` only from a trailing agent message (line 243, `trailingAgentMessageAt = isUser ? undefined : createdAt`). A failed turn writes the user message, then `task_complete`, and no agent message. So the last message is the user's, `lastTurnCompletedAt` is undefined, and `summarizeConversationActivity` (`src/dashboard/server/services/conversation/activity-summary.ts` line 146) reports working while the file is fresh. In the incident, viewer messages arrived about once a minute, so the file was always fresh.
5. **The frontend panel shows "working" for 4 minutes after each failure.** `isConversationWorking` (`src/dashboard/frontend/src/lib/workingPhase.ts` line 188) returns true while the last message is a user message younger than `TURN_STALL_MS` (4 minutes).
6. **The banner polls every 120 s** (`src/dashboard/frontend/src/hooks/useCodexAuthStatus.ts` line 27), so "within a minute" is impossible today.

Re-auth needs no restart. In `appserver-events.jsonl` for `conv-20261118-427e`, after `codex login` the next turn (17:44:36Z) failed with `contextWindowExceeded` instead of `unauthorized`, with no `exit` or lifecycle event in between. The running app-server re-read the shared `auth.json`.

## Decisions

- **D1. Derive, do not store.** The failure signal comes from the rollout's newest turn event. No new agent-state field, no flag writer, no database column. (Overrides the issue's agent-note suggestion to write the burn flag through `saveAgentStateSync`; see Root cause 1.)
- **D2. Only a turn-end event decides.** Walk the rollout tail newest first to the first `task_started`, `task_complete` or `turn_aborted`. `task_started` ⇒ the turn is running, no failure. `task_complete` with `error` ⇒ failed turn. `task_complete` without `error`, or `turn_aborted` ⇒ finished, no failure.
- **D3. Classify by code first.** `codex_error_info` `unauthorized` ⇒ `auth`; `context_window_exceeded` or `contextWindowExceeded` ⇒ `context-window`. Only when the code is missing or not one of those, a message matching `/refresh token|could not be refreshed|sign in again|log out and sign in/i` ⇒ `auth`. Everything else ⇒ `other`. An object-valued code reads as its first key (for example `responseStreamDisconnected`).
- **D4. Healing rule.** An auth failure is active only while `Date.parse(failure.at) >= nativeAuthMtimeMs`. A `codex login` rewrites `~/.codex/auth.json`, its mtime moves past the failure, and the banner clears. The conversation row keeps `providerError` (its last turn did fail) but marks it `authRecovered: true` and says "send a message to resume".
- **D5. Scan only live Codex sessions.** Live = conversation rows with `harness === 'codex'` and `status === 'active'` (id = `tmuxSession`, which is the agent dir name such as `conv-20261118-427e`), plus agent states with `harness === 'codex'` and `status === 'running'` (id = `state.id`). Cap at 64 sessions. Each rollout read is a fixed 128 KiB tail (the same bound `codexThreadStatus` uses), so a 1.2 GB rollout costs the same as a small one.
- **D6. Cache the scan for 15 s, single-flight.** Several dashboard tabs poll the route; the scan lists about 5,100 agent dirs via `listAgentStatesAsync`. One scan serves every caller inside the 15 s window, and concurrent callers share one in-flight promise.
- **D7. Banner poll every 30 s, stale after 15 s.** Worst case from failure to banner: 30 s poll + 15 s cache = 45 s, inside the issue's one-minute target.
- **D8. Replace the dead burn-flag readers.** Delete `CODEX_AUTH_BURNED_REASON_PREFIX`, `CodexAuthBurnFlagState`, `codexAuthBurnFlaggedAtMs`, `filterCodexAuthBurnedAgentIds`, `listCodexAuthBurnedAgentsSync`, `hasActiveBurnedCodexAgentsSync`, `probeNativeCodexAuthSync`, `nativeCodexAuthMtimeSync` and `CheckCodexAuthOptions.agentStates`, and their tests. Rewrite the header comment.
- **D9. `codex-auth.ts` stays an import leaf.** It must not import (statically or dynamically) the scan module, the agents barrel or the conversations store. The `CodexAuthFailure` type lives in the WI-1 leaf module `src/lib/conversations/codex-thread-status.ts` (which imports only `node:fs`), so both `codex-auth.ts` and the scan import it from there; callers pass failures in.
- **D10. Reuse `providerError`.** A Codex failed turn becomes a `ConversationProviderError` with `status: null`, `code` = the raw `codex_error_info` string, `usageLimit: null`, plus two new optional fields `kind` and `authRecovered`. The message is rewritten into an operator sentence (WI-3). No new row field.
- **D11. Render failed turns in the timeline as `Turn failed` error rows**, mirroring the ACP `Prompt failed` row (`acp-conversation-parser.ts` line 170) and the Prime Agent `Turn failed` row (`pi-conversation-parser.ts` line 296).
- **D12. No auto-retry and no auto-handoff.** After re-auth, the conversation shows "sign-in fixed, send a message to resume" (the issue offers this or retry; retrying would replay prompts and fail again on a full context). Context-full is flagged, not acted on.
- **D13. Split the conversation-panel UX into a sibling issue.** The Command Deck row state word, the notice above the composer and its **Hand off** button consume the `kind`/`authRecovered` fields this issue adds. They ship independently. This keeps this plan inside the 25-file finalize limit.

## Requirements

### Functional

- **FR-1** Given a Codex rollout, a reader returns the newest turn's status (`running` | `done`) and, when the newest turn-end event is a `task_complete` with `error`, a failure `{ message, at, code, kind }` classified per D3.
- **FR-2** The Codex conversation parser ends a turn on `task_complete` and `turn_aborted`, so `lastTurnCompletedAt` is set and `summarizeConversationActivity` returns `isWorking: false` after a failed turn.
- **FR-3** The Codex conversation parser emits one `tone: 'error'` work-log row labelled `Turn failed` per `task_complete` that carries `error`, with the error message as `detail` and `result`.
- **FR-4** `GET /api/conversations` rows for live Codex conversations whose newest turn failed carry `providerError` with `kind`, `authRecovered` and an operator-readable `message`.
- **FR-5** `GET /api/settings/codex-auth` returns `status: 'burned'`, `source: 'native'` and `affectedAgents` (session ids) when any live Codex session has an active auth failure.
- **FR-6** After `~/.codex/auth.json` is rewritten later than every auth failure, `GET /api/settings/codex-auth` stops returning `burned`, and the conversation row's `providerError.authRecovered` is `true`.
- **FR-7** The spawn gate (`assertCodexNativeAuthForSpawn`) and `POST` issue-spawn subscription check (`routes/agents/spawn-issue.ts`) refuse a new Codex spawn while an active auth failure exists, using the same scan.
- **FR-8** The dashboard banner polls the auth status every 30 s and names how many Codex sessions are failing on a revoked sign-in.
- **FR-9** The conversation panel stops showing the working indicator when a `Turn failed` (or any error-tone) row is newer than the last message.
- **FR-10** The dead burn-flag code and its false header comment are removed.
- **FR-11** The docs describe the derived signal, the banner timing, the `providerError` fields and the healing rule.

### Non-functional

- **NFR-1** No synchronous filesystem or child-process call is added to any server-reachable path. All new reads are async with a bounded 128 KiB tail.
- **NFR-2** No file grows past its file-size ratchet. `src/lib/agents/spawn.ts` (1,088 lines, over the 1,000 ceiling) must not gain a line.
- **NFR-3** Tests inject `now`; no test waits on a real timer (repo rule: fake timers or injected clocks for delay-based code).
- **NFR-4** `npm run lint:circular` reports no new cycle.

## Non-goals

- Changing `classifyNativeCodexAuth`'s static rules. A refreshable token cannot be judged statically.
- Auto-retrying prompts or auto-sending a message after re-auth.
- Auto-handoff of a context-full conversation.
- Blocking message delivery to a conversation while its sign-in is burned.
- The CLIProxy log-based burn check (`evaluateBurnedFromLog`): unchanged.
- A push channel (WebSocket event) for the auth status; polling stays.
- Detecting failures in stopped sessions or vault browse copies.
- Codex `usageLimitExceeded` as a `usageLimit` with a reset time (it stays `kind: 'other'`).
- The conversation-panel UX listed under Split.

## Risks

- **Rollout schema drift.** A future Codex CLI may rename `codex_error_info`. D3's message-text fallback keeps auth detection working; the WI-1 tests pin both paths.
- **`lint:circular`.** WI-5's checkpoint names the fallback.
- **Scan cost.** `listAgentStatesAsync` reads about 5,100 `state.json` files; the 15 s cache bounds it to one scan per 15 s across all tabs. `agent-directory.ts` line 212 already does the same scan.
- **ACP `Prompt stalled` rows** now also stop the panel's working indicator (WI-8). That row means five minutes with no activity, so showing idle is accurate; new activity after it restores working.
