# PAN-5211 — Bound the dashboard's memory for very large Codex transcripts

**Issue:** [PAN-5211](https://github.com/eltmon/overdeck/issues/5211) (body plus the operator's follow-up comment of
2026-11-13) · **Planned:** 2026-11-13 · **Mode:** `pan plan --auto`

## Summary

The dashboard server kept about 1.2 GB of one Codex transcript's tool output live in its JS heap, and its RSS reached
6.4 GB. The transcript (`conv-20261110-b6d6`, 1.6 GB on disk, 104,872 lines) holds about 0.98 GB of base64 PNG
screenshots and 0.55 GB of plain tool text. Four things combine:

1. The Codex accumulator stores every tool result whole, image data URLs included.
2. Every multi-MB line is decoded to a string and run through `JSON.parse` whole, so a cold open reads and parses the
   whole 1.6 GB file. Much of the RSS is this transient work.
3. The incremental reader's cache budget counts file bytes and always keeps one entry however large.
4. The output branch finds its call with `workLog.indexOf`, which is O(n²).

This plan bounds both the parse and what it keeps:

- The reader splits lines as bytes and replaces each image data URL with a short placeholder **before** decoding or
  `JSON.parse`. It skips lines that stay over 8 MiB, and it opens a transcript over 64 MiB by reading only its last
  64 MiB.
- One shared helper caps every stored tool result at 64 KiB (head and tail kept) for Codex, pi, prime-agent, ohmypi and
  kimi.
- Cache budgets count retained characters, with a 16 Mi-character hard cap per entry. The Codex accumulator keeps a
  bounded window of the newest rows.
- Codex rows are numbered by their byte offset in the transcript. Each kept tool result stores its byte location, so
  expand seeks straight to the record, and paging back past the window reads older records from disk.
- The conversation view shows a notice for a bounded conversation and pages back through disk-backed history.
- Tests prove the retained heap, the peak RSS and the cold-open time on a synthetic 200 MB transcript.
- The docs record the decision not to set `--max-old-space-size`.

## Glossary

- **Accumulator**: an object with `push(line, location?)`, `result(size, mtimeMs)` and `retainedChars()`. It consumes
  transcript JSONL records one at a time and builds a `ParseResult`. `createCodexConversationAccumulator`
  (`src/dashboard/server/services/codex-conversation-parser.ts:111`) is the only accumulator.
- **Incremental reader**: `createIncrementalTranscriptReader`
  (`src/dashboard/server/services/incremental-transcript-reader.ts:24`). It caches one accumulator per transcript file
  and feeds it only appended bytes. One module-level instance exists per JS isolate (the main thread and each
  `dashboard-db-worker` lane thread), exported as `parseCodexConversationMessages`.
- **ParseResult**: the parsed transcript shape (`src/dashboard/server/services/conversation/types.ts:11`).
- **Work-log entry**: one `WorkLogEntry` row (`packages/contracts/src/rpc.ts:209`).
- **Tool result**: the `result` string of a work-log entry.
- **Image data URL**: the text `data:image/<format>;base64,<payload>`. Codex writes screenshots as
  `{"type":"input_image","image_url":"data:image/png;base64,…","detail":"high"}` items in the `payload.output` array of
  a `custom_tool_call_output` record.
- **Image placeholder**: the text `[image: <format>, <N> KB]` that replaces an image data URL. `<N>` is the decoded
  image size in KiB, rounded, with a minimum of 1.
- **Scrub**: replacing every image data URL in a raw line `Buffer` with its image placeholder, before the line is decoded.
- **Bounded result**: a tool result that the text helper cut, or that held an image placeholder.
- **Retained characters**: an estimate of the heap a parse result keeps. It is the sum of `.length` (UTF-16 code units)
  of every string in its messages and work-log entries, plus 64 per row.
- **Record location**: `{ offset, length }`, the byte offset and byte length of one JSONL line on disk (before scrubbing).
- **Record-offset sequence**: in a reader-fed Codex accumulator, each row's `sequence` is the byte offset of the record
  that created it. Sequences are unique and ordered across the whole file, whatever byte the read started at.
- **History start offset**: `ParseResult.historyStartOffset`, the byte offset of the oldest record the result holds.
  `> 0` means older history exists only on disk.
- **Bounded conversation**: a conversation whose parse result has `historyStartOffset > 0`. Its windows carry
  `bounded: true`.
- **Tail read**: on a cold open of a transcript larger than `TRANSCRIPT_TAIL_READ_BYTES` (64 MiB), the reader starts at
  the first line boundary inside the last 64 MiB instead of byte 0.
- **Disk page**: an older page read by `readCodexRowsBefore` from the byte range just before the oldest in-memory record.
- **Tool-body route**: `GET /api/conversations/:name/tool-body/:toolUseId` and
  `GET /api/agents/:id/conversation/tool-body/:toolUseId` (PAN-4558). The frontend calls it when a user expands a row
  marked `bodyOmitted`.
- **Snapshot cache**: the main-thread `snapshots` map in `src/dashboard/server/services/shared-transcript-parser.ts`. It
  holds worker parse results for the WebSocket conversation stream.

## Decisions (made here; the executor does not re-decide them)

- **D1: Placeholders everywhere.** An image data URL is never stored or served, including on expand and in disk pages.
  The frontend has no image renderer.
- **D2: Scrub before parse.** The reader splits lines on byte `0x0A`, which never occurs inside a UTF-8 multibyte
  sequence. It scrubs each line `Buffer` and only then decodes and parses it. The scrub scans for the bytes
  `data:image/`, reads `<format>` up to `;base64,`, and takes the payload as the run of `[A-Za-z0-9+/=]` bytes. It
  replaces the whole data URL with the ASCII placeholder. The placeholder contains no `"` or `\`, so the JSON stays
  valid. JSON writers (serde_json, `JSON.stringify`) never escape `/`, so escaped slashes inside the payload need no
  handling.
- **D3: Oversized lines.** A scrubbed line over `RECORD_PARSE_MAX_BYTES` (8 MiB) is not decoded whole. The reader calls
  `pushOversized(head, location)` with the first 4,096 bytes decoded. The Codex accumulator reads `call_id` and the
  payload type from `head` with a regex:
  - For an output whose call is in the window, the entry gets `bodyOmitted: true` and `resultBytes: location.length`,
    and no `result`. Its location is recorded. `hasToolResult` is then true and `useToolBody` fetches on expand, so the
    full read (D11) serves it.
  - Otherwise it adds an `info` row "Skipped a <X.Y> MB transcript record".
- **D4: Text caps.**
  - Stored result: at most 65,536 content chars (`TOOL_RESULT_STORED_MAX_CHARS`). Keep the first and last 32,768, joined
    by `\n\n… [<N> characters omitted] …\n\n`, where `<N>` uses `toLocaleString('en-US')`.
  - Expand: at most 4,194,304 chars (`TOOL_BODY_FULL_READ_MAX_CHARS`), cut the same way.
  - Cut points never split a surrogate pair. A changed string is returned as `Buffer.from(out,'utf8').toString('utf8')`
    so no sliced string keeps the original alive (fact 11).
- **D5: Budgets.** All budgets count retained characters:
  - per-entry hard cap `TRANSCRIPT_ENTRY_MAX_RETAINED_CHARS = 16 Mi`;
  - in-memory window eviction target `TRANSCRIPT_WINDOW_TARGET_CHARS = 12 Mi`;
  - total cache budget `TRANSCRIPT_CACHE_MAX_RETAINED_CHARS = 32 Mi`;
  - `maxFiles` stays 8 in the reader and in the snapshot cache.
- **D6: Tail read.** On a cold open (fresh cache entry) of a file larger than `TRANSCRIPT_TAIL_READ_BYTES` (64 MiB), the
  reader starts at the byte after the first `\n` at or after `size − 64 MiB`. The accumulator receives
  `historyStartOffset` set to that byte. Totals stay correct (fact 4). Appends after the open are read incrementally as
  today.
- **D7: Row sequences and ids are record offsets.** A Codex accumulator that receives locations (every reader-fed
  parse: whole-file, tail read, window slide or disk page) sets each new row's `sequence` to `location.offset` and its
  id suffix to `@<offset>` (`codex-user-@<offset>`, `codex-agent-@<offset>`, `codex-tool-@<offset>`,
  `codex-tool-out-@<offset>`). Tool rows keep the `call_id` as their id, as today. So the same record has the same id
  in every parser.
  - `lastSequence` is the newest row's sequence. Resume (`afterSequence`) still works, and a client holding old
    counter sequences gets one windowed reset.
  - Without a location (`src/lib/agents/last-assistant-message.ts`), the accumulator keeps the counter form
    `codex-user-<n>`. Those ids are never persisted.
  - The accumulator still keeps the legacy counter (today's `sequence` increments). It reports `(legacyId, id)` for
    each new row through an optional `onRowCreated` callback, which the bookmark migration (D20) uses.
- **D8: In-memory window.** When `retainedChars()` exceeds 16 Mi, the accumulator drops its oldest rows (messages and work
  log, lowest `sequence` first) until it holds at most 12 Mi, keeping at least one row. It then sets
  `historyStartOffset` to the oldest kept row's sequence (record offset). With 4 Mi of hysteresis, the row prefix
  changes once per ~4 Mi of growth. So the WS delta (`transcript-delta.ts` `diffRows`) sends one windowed reset per
  slide, not one per append.
  - Dropping a row deletes its call-index and location entries.
  - An output whose call was dropped takes the existing orphan path.
- **D9: The reader's hard cap.** The reader keeps a just-read entry only while its `retainedChars()` is at most 16 Mi.
  An entry over the cap is returned and then dropped from the cache, so the old single-entry exception can never hold
  more than the cap.
- **D10: Stored call index.** `toolCallsByCallId` becomes `Map<string, number>`, holding the absolute index (rows dropped
  so far + array position). A replaced entry is a new object (`{ ...wl, result }`), so earlier snapshots keep their own
  entry.
- **D11: Expand by offset.** The Codex accumulator records `{ offset, length }` for every kept output row that has a
  non-empty `call_id`, and `result()` exposes them as `ParseResult.toolResultLocations`. The tool-body routes read those
  bytes, scrub them, `JSON.parse` the line, and check `payload.call_id === entry.id`. They then serve the full text
  under D4's expand cap. A location whose `length` exceeds `RECORD_FULL_READ_MAX_BYTES` (64 MiB) is not read; the route
  serves the stored entry. If the check fails or the read throws, they serve the stored entry.
- **D12: Disk paging.** A page request whose in-memory page comes back empty, for a bounded conversation, reads a disk
  page:
  1. The read ends at `min(cursorSequence, historyStartOffset)`.
  2. It starts at the first line boundary `OLDER_PAGE_READ_STEP_BYTES` (8 MiB) earlier, parses that range with a fresh
     accumulator, and selects rows older than the cursor.
  3. If it finds fewer than `limit` rows and the range does not reach byte 0, it doubles the span, up to
     `OLDER_PAGE_READ_MAX_BYTES` (64 MiB).
  4. `hasOlder` is true while rows remain older than the page, or while the range start is above 0.
  5. If the disk page has no rows and `rangeStart > 0`, the window cursor is the synthetic key
     `encodeTimelineCursor([before[0], rangeStart, 0, ''])` with `hasOlder: true`. The next request then reads before
     `rangeStart`, so paging never stalls on a `null` cursor.

  Pages that come from memory but reach the oldest in-memory row return `hasOlder: true`, so the next request goes to
  disk. One limitation at the range boundary is accepted and documented: a call on a disk page whose output lies after
  the range shows as open, and that output shows as a stand-alone "Tool result" row.
- **D13: UI notice.** Windows (initial, paged and WS) of a bounded conversation carry `bounded: true` and
  `hasOlder: true`. The conversation view then shows "Large conversation: the dashboard keeps recent history in memory
  and loads older history from the transcript as you scroll up." at the top of the timeline. Scrolling up pages back
  through disk pages until "Start of conversation".
- **D14: Non-Codex harnesses.** pi, prime-agent, ohmypi and kimi re-parse whole files and get no locations. A result
  over 64 KiB expands to its head and tail. ACP (500-char cap, stricter) and muse (no work log) are unchanged.
- **D15: Snapshot cache in scope, `messagesCache` not.** The snapshot cache has the identical bug. `messagesCache`
  (`conversation-reads.ts:241`) sits in a file at the ceiling, and every Codex entry it holds is now bounded, so its
  budget is a follow-up.
- **D16: No `--max-old-space-size`.** The dashboard keeps Node's default heap limit, which is about 4 GiB per isolate on
  this host (fact 13). This change bounds retained parse state by design, so a cap adds no protection against this
  bug. A cap set too low turns a transient spike (a burst of large parses on five worker lanes) into an OOM crash. That
  crash takes down every conversation view and the pipeline UI at once. Revisit the decision if the steady-state heap
  passes 1 GiB after this lands. The decision goes in `docs/DASHBOARD-ARCHITECTURE.md` and in the PR description.
- **D18: What other consumers see for a bounded conversation.** Every consumer of the Codex parse result gets only the
  in-memory rows of a bounded conversation (one over 64 MiB, or one that slid its window):
  - title generation, retitle, title refinement and the admin title backfill (`conversation-reads.ts:906`, `:958`,
    `title-refinement.ts:88`, `routes/admin.ts:64`) read the newest rows, not the conversation's first turn;
  - conversation diffs (`src/lib/overdeck/conversation-diffs.ts:216`, `:341`, `:410`) cover the in-memory rows only;
  - `readFlywheelTranscript` (`src/lib/flywheel/derive-status.ts:118`) reads the newest rows, which is what it needs;
  - the unwindowed agent body (`GET /api/agents/:id/conversation` without params) and `?window=all` exports hold the
    in-memory rows only;
  - `listCodexSubagents` (`conversation/codex-subagents.ts:127`) loses the `spawn_agent` match for calls outside the
    window and falls back to the thread's own metadata.

  All of this is accepted, because titles are generated while transcripts are small, and it is documented in WI-18.
  None of these consumers is changed.
- **D19: Expanding a disk-paged row.** A row from a disk page is not in the in-memory parse. The frontend's tool-body
  loader sends the row's `sequence` as `?seq=<n>`. For a Codex tool row, the sequence is the byte offset of its call
  record. When the entry is not in memory, the conversation is bounded and `seq < historyStartOffset`, the server
  resolves the row from disk:
  - it checks that `seq` is a line start (byte 0, or the byte before it is `0x0A`);
  - it parses forward from `seq` with a fresh located accumulator until that id's row has its output, or
    `OLDER_PAGE_READ_MAX_BYTES` is consumed;
  - it serves the row through `withFullToolResult`.

  If it does not find the row, it returns 404 as today.
- **D20: Counter-form bookmarks are migrated once.** Bookmarks persist `message_id` and look it up exactly
  (`src/lib/overdeck/conversation-bookmarks.ts:81`, `useOlderHistory.ts:78-88`).
  - When `GET /api/conversations/:name/bookmarks` lists a Codex conversation that has bookmarks matching
    `^codex-(user|agent)-\d+$`, the route first runs `migrateCodexCounterBookmarks`. It streams the transcript from
    byte 0 through the line splitter and scrub into a located accumulator with `onRowCreated`. It stops once every
    wanted legacy id is mapped, and rewrites each bookmark's `message_id` to the offset id.
  - Ids it cannot map are left alone.
  - The migration runs at most once per conversation per process (an in-memory `Set`), and afterwards no counter-form
    ids remain.
- **D21: Budget scope.** The 32 Mi-character total and the 16 Mi hard cap are limits per cache, and there are four
  caches:
  - the reader cache in the main thread;
  - the reader cache in the worker parse lane;
  - the main-thread snapshot cache;
  - `messagesCache` in `conversation-reads.ts`. It has 100 entries and no character budget (D15), so with Codex
    entries at the 16 Mi cap it could retain about 1.56 Gi characters in the worst case. In practice it holds
    references to the main reader's current results and evicts by count.

  The docs (WI-18) state each scope. They make no dashboard-wide claim. A `messagesCache` budget is a follow-up.
- **D17: Tests measure heap, RSS and time.** They do not measure result byte size alone, because a byte-size assertion
  cannot see a sliced string holding its parent alive. The tests live in a normal `.test.ts` file so CI runs them.
  `*.slow.test.ts` files are excluded from default runs.

## Requirements

### Functional

- **FR-1**: No stored or served tool result (Codex, kimi) contains an image data URL; each becomes an image placeholder.
- **FR-2**: Every stored Codex, pi, prime-agent, ohmypi and kimi tool result is at most 65,536 content chars plus one
  omitted-characters marker (head and tail kept).
- **FR-3**: One shared helper module implements the scrub, the text cap and the retained-characters estimate.
- **FR-4**: The Codex output branch finds its call in O(1) (no `indexOf`).
- **FR-5**: The incremental reader scrubs image data URLs out of each line before decoding or `JSON.parse`. It hands
  lines over 8 MiB after scrubbing to `pushOversized` instead of parsing them.
- **FR-6**: A cold open of a transcript over 64 MiB reads only its last 64 MiB (tail read).
- **FR-7**: The reader and the snapshot cache measure retained characters and never keep an entry over 16 Mi.
- **FR-8**: A Codex accumulator whose rows exceed 16 Mi keeps the newest rows down to 12 Mi and reports
  `historyStartOffset`. Cost and token totals still reflect the whole transcript.
- **FR-9**: Each kept Codex tool result stores its record location, and expand reads the full text by seeking to it.
- **FR-10**: Paging back past a bounded conversation's in-memory start returns older rows read from disk, until
  "Start of conversation".
- **FR-11**: The conversation view tells the user when a conversation is bounded.
- **FR-12**: The docs describe the caps, the tail read, the window, disk paging and the heap-limit decision, and
  `changelog.d/pan-5211.md` holds the Fixed entry.

### Non-functional

- **NFR-1**: For a synthetic 200 MB Codex image transcript, the retained heap after GC grows by less than 64 MiB.
- **NFR-2**: For the same transcript, a cold open finishes in under 5,000 ms, and the peak RSS
  (`process.resourceUsage().maxRSS`) grows by less than 256 MiB.
- **NFR-3**: The Codex parse stays linear in record count.
- **NFR-4**: No file over 1,000 lines grows past its `origin/main` line count.

`boundToolResultText` does two things:

## Critique response

The plan critic (round 1, `.pan/drafts/PAN-5211-critique.md`) raised two blocks-the-design findings and one
sharpens-framing finding.

### Paged tool rows cannot expand

Accepted. The tool-body routes searched only the in-memory parse, so a row shown from a disk page would return 404. D19
and WI-20 make the frontend loader send the row's `sequence`, which is the byte offset of its call record. For a
bounded conversation whose in-memory parse lacks the id, the server parses forward from that offset, after checking it
is a line start, and serves the row with its full output through `withFullToolResult`. WI-20's test expands a row after
it has been evicted from memory.

### Window slides invalidate existing bookmarks

Accepted. D7 now gives every reader-fed Codex row an offset-based id (`codex-user-@<offset>`), so a record has the same
id whether it came from a whole-file parse, a tail read, a window slide or a disk page. The tail-read exception in the
earlier D7 is gone. Existing counter-form bookmarks are migrated once on the first bookmark list (D20, WI-21): a
streaming pass from byte 0 maps each legacy counter id to its offset id through `onRowCreated`, and rewrites
`message_id`. WI-21 tests a bookmark made in counter form and resolved after migration. Because ids are now stable, a
bookmark made before a window slide still resolves when its row is loaded from a disk page.

### The 32 Mi cache limit is not a dashboard limit

Accepted as framing. D21 states that each budget applies per cache, that there are four caches, and that
`messagesCache` has no character budget, with its worst-case exposure. The docs item (WI-18 step 6) states the same,
with no dashboard-wide claim. A `messagesCache` budget stays a follow-up (D15).

### Unresolved after two critic rounds

- Range boundary hides a tool call
- Bookmark ordinals drift after eviction
- Tail reads can zero the cost
- Bookmark migration is not atomic or retryable
