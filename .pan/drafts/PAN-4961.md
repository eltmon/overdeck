# PAN-4961 — Workspace disk floor accounts for in-flight setups and re-checks before each disk-heavy step

**Issue:** [PAN-4961](https://github.com/eltmon/overdeck/issues/4961)
**Planned against:** `feature/pan-4961` @ `c1818d12c01` (2026-11-03)

## Glossary

- **Disk floor** — `DISK_SAFETY_FLOOR_BYTES` (10 GiB) in `src/lib/disk-floor.ts`. Below it, an
  ENOSPC write can zero-fill a file instead of failing (PAN-1674). It must stay equal to
  `DISK_PRUNE_TRIGGER_BYTES` in `src/lib/cloister/disk-pressure-patrol.ts` (asserted by
  `src/lib/__tests__/disk-floor.test.ts`, "matches the disk-pressure-patrol trigger constant").
- **Available bytes** — `statfs(path).bavail * bsize`, read by `readAvailableBytes` in
  `src/lib/disk-floor.ts`.
- **Disk-heavy phase** — one of two steps that write gigabytes after the floor check today:
  - **host phase**: `createWorkspace` makes the git worktree and runs the package install
    (`src/lib/workspace-manager/create.ts`).
  - **stack phase**: a workspace Docker stack is built with `docker compose ... up -d --build`.
    The `init` service fills the `<compose-project>_container-node-modules` volume (measured
    1.935–1.938 GB per workspace on 2026-11-03). Frontend and server `depends_on` init with
    `condition: service_completed_successfully`
    (`infra/.devcontainer-template/docker-compose.devcontainer.yml.template`, lines 47–49,
    105–107, 143–145), so `up -d` returns only after the volume is full.
- **Disk reservation** — a small JSON file under `<OVERDECK_HOME>/disk-reservations/` that says
  "process P is running a disk-heavy phase that will write about B bytes". It exists only while
  the phase runs. It is a lease, like a lock file, not stored status.
- **In-flight reserved bytes** — the sum of `bytes` over all *live* reservations. A reservation is
  live when its `pid` is a running process **and** its file's `mtimeMs` is newer than
  `DISK_RESERVATION_STALE_MS` (10 min). The holder renews the mtime every
  `DISK_RESERVATION_HEARTBEAT_MS` (60 s) while its phase runs, so a live phase never expires
  however long its install takes, and a file left by a crashed process or a previous boot (whose
  pid may now belong to another process) stops counting within 10 minutes.
- **Admission** — the decision to let a disk-heavy phase start. A phase is admitted when
  `available − inFlightReservedBytes − ownCostBytes ≥ DISK_SAFETY_FLOOR_BYTES`.
- **Re-check** — a plain floor check (`available ≥ floor`) immediately before a disk-heavy
  sub-step (package install, `docker compose up`). It catches space lost after admission.
- **Disk-low hold message** — every refusal starts with the exported constant
  `DISK_LOW_HELD_PREFIX = 'Disk low — new workspace starts are held'` and keeps the text
  `10.0 GiB` (the floor, existing test AC1).
- **Workspace disk cost** — the measured estimate `{ hostBytes, stackBytes }` for one new
  workspace of a project (see WI-2).
- **Deferred handoff** — after `pan plan finalize`, a refused work-agent spawn is journaled and
  deacon-lite retries it with backoff (`src/lib/cloister/deferred-handoff.ts`,
  `recordPlanningAutoHandoffDeferred` in `src/lib/overdeck/planning-promotion.ts`).

## Problem

`createWorkspace` checks the floor once, at `src/lib/workspace-manager/create.ts` line 203:

```ts
  const diskError = await checkDiskFloor(projectConfig.path);
```

Everything that consumes disk runs after that check: the worktree, the package install at line
475 (`await execAsync(installCmd, { cwd: workspacePath, encoding: 'utf-8' });`), and, much later,
the workspace Docker stack. On 2026-11-03 the Flywheel started six issues within a few minutes at
15–17 GB free. Each start passed the check; together they took the disk from 15 GB to 4.9 GB in
about 20 minutes.

### Where the stack cost lands (verified)

The issue says planning-only sessions already had Docker stacks. The evidence says otherwise:
planning does not build a stack.

- `PlanDialog` defaults `startDocker` to `false`
  (`src/dashboard/frontend/src/components/PlanDialog.tsx` line 83:
  `return stored !== null ? stored === 'true' : false; // Default to false — planning agents don't need Docker`).
- `pan start` posts `buildStartPlanningBody(...)` with no `startDocker`
  (`src/cli/commands/start.ts` lines 657–673), so `spawnPlanningSession` passes
  `startDocker: undefined` to `createWorkspace` (`src/lib/planning/spawn-planning-session.ts`
  lines 427–431).
- `assertWorkspaceStackHealthyForSpawn` returns at once for the plan role
  (`src/lib/agents/spawn-prep.ts` line 967:
  `if (role === 'plan' || role === 'knowledge' || role === 'worker') return;`).
- PAN-4840 timeline: its containers were created at 15:56:31 EST, `agent-pan-4840` state files
  appeared at 15:56:58, and `planning-pan-4840/auto-spawn-on-finalize.json` reads
  `"status":"spent","updatedAt":"2026-11-03T20:57:00.035Z"` (15:57:00 EST). The stack was built
  by the **work-agent spawn** that the finalize auto-handoff requested, at the stack-health gate in
  `src/dashboard/server/routes/agents/spawn-issue.ts` line 491
  (`let stackHealth = yield* getWorkspaceStackHealth(issueId, { projectConfig, workspacePath });`),
  which calls `assertWorkspaceStackHealthyForSpawn(issueId, 'work', ...)` →
  `rebuildWorkspaceStack` → `docker compose ... up -d --build`
  (`src/lib/workspace/rebuild-stack.ts` line 271).

So the stack phase is where most of the 10 GB went, and it runs in `rebuildWorkspaceStack`, not in
`createWorkspace`. The fix must hold the stack phase too, not only workspace creation.

### Measured costs on this machine (2026-11-03)

| Component | Command | Result |
| --- | --- | --- |
| Worktree (tracked files) | `git ls-tree -r -l HEAD \| awk '{s+=$4} END {print s}'` | 359,159,075 bytes |
| Worktree on disk minus node_modules | `du -sx --exclude=node_modules .` | 381,452 KiB |
| node_modules apparent size | `du -sx node_modules` | 2,192,104 KiB |
| node_modules bytes not shared with the bun cache | `find node_modules -type f -links 1 -printf '%b\n'` summed ×512 | 0 (every file is a hardlink; `stat -c %h` of `node_modules/typescript/package.json` = 26) |
| Stack volume | `docker system df -v --format '{{json .}}'` → `Volumes[].Size` for `overdeck-feature-pan-49xx_container-node-modules` | 1.935 GB – 1.938 GB each |
| Stack images | same command → `Images[].UniqueSize` for `overdeck-feature-pan-49xx-*` | 0 B (all layers shared) |

`du` overstates node_modules by about 2 GB because bun hardlinks from its cache. The estimate must
count only files with one link. `docker system df -v` took 9.5 s, so the estimate is memoized.

## Decisions

- **D-1 Cross-process file ledger, serialized by an O_EXCL lock.** Workspace creation runs in the
  dashboard process (planning, `WorkspaceService.create`), in the Deacon child process
  (`src/lib/cloister/pr-workspace-adoption.ts`), and in CLI processes (`pan workspace create`,
  `pan swarm`). An in-process counter would miss two of the three. Admission reads, decides, and
  writes the reservation while holding `withFileLock` from `src/lib/vault/file-lock.ts` (Node
  built-ins only, stale lock reclaimed after 30 s). Because admission is serialized, every admitted
  reservation is visible to every later admission. No ranking or sequence numbers are needed.
- **D-2 Two phases, two costs, released when the phase returns.** The host phase reserves
  `hostBytes` (plus `stackBytes` only when `createWorkspace` is called with `startDocker: true`).
  The stack phase reserves `stackBytes`. A reservation is released in a `finally` when its phase
  returns, success or failure, because from then on the bytes are real and `statfs` sees them.
  The `resumingSetup` path of `createWorkspace` reserves like a fresh create (it re-runs the
  install).
- **D-3 Over-counting is the safe direction.** While a phase runs, part of its reservation is
  already written and `available` already dropped by that part, so admission counts it twice.
  This can refuse a start that would have fit; it never admits one that does not. Accepted.
- **D-4 Re-checks are plain floor checks.** Before the package install and before each
  `docker compose ... up -d --build` the code calls `checkDiskFloor` (no reservations). Subtracting
  reservations again would double-count the phase's own reservation and refuse admitted work.
- **D-5 Measured estimate, memoized, with a measured machine-wide fallback.**
  `estimateWorkspaceDiskCost` measures (WI-2) and memoizes per project path for 6 h; releasing a
  reservation invalidates that project's memo, so the start after a project's first workspace
  measures the real first workspace. A project with no finished sibling stack uses the **largest
  stack of any compose project on this Docker host** (measured from the same
  `docker system df -v` output), and the seed constants (`SEED_HOST_DISK_COST_BYTES = 0.5 GiB`,
  `SEED_STACK_DISK_COST_BYTES = 2 GiB`, rounded up from the table above) are a lower bound applied
  with `max(...)`, used alone only when nothing at all can be measured (`source: 'seed'`, with a
  `console.warn`). The remaining error is bounded by the floor itself: a phase underestimated by
  up to 8 GiB still ends above the ~2 GB point where writes start failing, and the plain re-check
  before each install and compose stops the next step. A statfs-delta measurement was rejected:
  concurrent phases (the exact case this issue is about) contaminate the delta.
- **D-6 One filesystem assumed.** The host phase reads `statfs(projectConfig.path)`; the stack
  phase reads `statfs(workspacePath)`. Docker's data root is assumed to be on the same filesystem,
  as `disk-pressure-patrol.ts` already assumes for `getOverdeckHome()`. There is one global ledger;
  if the paths were on different filesystems the sum over-counts (D-3 direction). Documented, not
  handled.
- **D-7 statfs failure fails open; ledger failure fails closed.** If `statfs` throws, admission
  admits with a no-op release (matches `checkDiskFloor` returning `null`, existing test AC3;
  without a reading there is nothing to compare). If the ledger directory, its listing, a
  reservation write, or the lock fails, admission **refuses** with
  `` `${DISK_LOW_HELD_PREFIX}: the disk reservation ledger at ${ledgerDir} is unavailable (${msg}), so in-flight workspace setups cannot be counted. Fix the directory and retry.` ``
  Ignoring the ledger would let concurrent starts all pass the plain check, which is the bug this
  issue fixes. `previewDiskFloor` returns the same text on ledger failure.
- **D-8 The work-spawn hold is in the stack-health gate, not in `evaluateSpawnGuardrails`.** A
  start whose stack is already healthy adds no disk cost, so it must not be held. Only when the
  gate is about to rebuild does it ask `resolveStackDiskHold`; a hold returns HTTP 507 with
  `diskLow: true`. `evaluateSpawnGuardrails` stays unchanged (it has no disk reading and holding
  every start would over-reach).
- **D-9 A disk hold defers the auto-handoff; it does not fail it.** Both spawn-refusal classifiers
  map `body.diskLow === true` to `'guardrails'`, and the finalize auto-spawn marks it
  `workAgentDeferred: true`, so deacon-lite retries with its existing backoff once space returns.
- **D-10 Planning keeps building no stack.** No code change to planning; WI-8 pins the current
  behavior with a test and the docs say why (the observed stacks came from the auto-handoff's work
  spawn).
- **D-11 Docker doors in scope.** `createWorkspace`'s `startDocker` branch, `rebuildWorkspaceStack`,
  the `POST /api/workspaces/:issueId/containerize` route
  (`src/dashboard/server/routes/workspaces/container-ops.ts` lines 61–186: it spawns
  `infra/new-feature` and then `./dev all`, creating a whole workspace and its stack), and
  `WorkspaceService.containerize` (`src/dashboard/server/services/workspace-service.ts` line 329,
  no production caller today but still callable). The container start/restart/stop action route
  in the same file acts on an existing stack and is out of scope.
- **D-12 One workspace-path resolver for holds.** `spawn-issue.ts` line 330 hardcodes
  `join(projectPath, 'workspaces', ...)`, while `rebuild-stack.ts` lines 159–163 honour
  `workspace.workspaces_dir`. Both hold checks (HTTP route and CLI) call
  `resolveIssueStackDiskHold(issueId)`, which resolves the path exactly as `rebuild-stack.ts` does,
  so the preview reads the same filesystem the rebuild will write. The route's own hardcoded path
  is not changed (out of scope).
- **D-13 No shell in the estimator.** Every external command runs through `execFile` with an
  argument vector (`git`, `docker`). Unshared node_modules bytes are summed with a Node
  filesystem walk (`lstat`: count `blocks * 512` when `nlink === 1`, never following symlinks),
  which is also portable to macOS, where `find -printf` does not exist.

## Requirements

- **FR-1** Admission refuses a disk-heavy phase when
  `available − inFlightReservedBytes − ownCostBytes < DISK_SAFETY_FLOOR_BYTES`, with a message that
  starts with `DISK_LOW_HELD_PREFIX` and names free GiB, reserved GiB, the number of in-flight
  phases, the phase's own GiB, and `10.0 GiB`.
- **FR-2** An admitted phase holds a reservation file that later admissions count until the phase
  returns; release is idempotent and runs on success and failure.
- **FR-3** Reservations whose pid is not running, or whose heartbeat mtime is older than 10 min,
  are ignored and deleted by the next admission; a live holder renews its mtime every 60 s, so a
  live phase is never reclaimed. A ledger that cannot be read, locked or written refuses
  admission (D-7).
- **FR-4** `estimateWorkspaceDiskCost(projectConfig)` returns measured `hostBytes` and
  `stackBytes` per D-5 and WI-2.
- **FR-5** `createWorkspace` reserves the host phase (plus the stack phase when `startDocker`)
  where line 203 checks the floor today, and releases it when `createWorkspace` returns.
- **FR-6** `createWorkspace` re-checks the floor before the root package install, before **each**
  polyrepo per-repo install, and before its `docker compose ... up -d --build`; an install-time refusal returns `success: false` with the
  setup-incomplete marker kept, so a retry resumes (PAN-4171).
- **FR-7** `rebuildWorkspaceStack` reserves the stack phase after teardown and before
  `up -d --build`, and returns `{ success: false, diskLow: true, error }` when refused.
- **FR-8** The containerize route reserves host + stack cost before it spawns `infra/new-feature`
  and releases when `./dev all` exits (or when any step fails); a refusal answers HTTP 507 with
  `diskLow: true` and spawns nothing. `WorkspaceService.containerize` reserves stack cost before
  its `up -d --build` and releases after it.
- **FR-9** `POST /api/agents` (work start) answers HTTP 507 with
  `{ success: false, blocked: true, skipped: true, diskLow: true, error, hint }` when the stack
  needs a rebuild and the disk cannot take one. This is the path of the dashboard Start button and
  the finalize auto-handoff.
- **FR-12** CLI `pan start <planned-id>` spawns in-process (`src/cli/commands/start.ts` line 977
  `spawnAgent(...)` → `src/lib/agents/spawn.ts` line 201 `prepareWorkspaceForAgentSpawn` →
  `assertWorkspaceStackHealthyForSpawn` in `src/lib/agents/spawn-prep.ts`), not through
  `POST /api/agents`. When the stack needs a rebuild and the disk cannot take one, that function
  throws an `Error` whose message is the disk-low text for the work role (and falls back to the
  host for review/test/ship), without counting a rebuild attempt. `pan start` prints the message.
- **FR-10** The finalize auto-handoff and deacon-lite's retry treat `diskLow: true` as a
  retryable guardrail refusal (`workAgentDeferred: true`).
- **FR-11** A planning session creates no Docker stack unless `startDocker: true` is passed
  explicitly.
- **NFR-1** No `execSync` and no sync tmux/child-process call in server-reachable code; the
  estimator uses promisified `exec`/`execFile`.
- **NFR-2** Tests use injected readers, ledgers, locks and clocks; no test reads real `statfs`,
  runs real `docker`, or sleeps on a real timer. Any test that exercises a delay uses
  `vi.useFakeTimers()`.
- **NFR-3** `src/lib/workspace-manager/create.ts` (800 lines) and
  `src/dashboard/server/routes/agents/spawn-issue.ts` (906) stay ≤ 1000 lines;
  `src/lib/overdeck/planning-promotion.ts` (992) stays ≤ its allowlist cap 997.
- **NFR-4** `DISK_SAFETY_FLOOR_BYTES === DISK_PRUNE_TRIGGER_BYTES` still holds.

### WI-1 Reservation ledger in `src/lib/disk-floor.ts` (FR-1, FR-2, FR-3, NFR-2, NFR-4)

Files: `src/lib/disk-floor.ts`, `src/lib/__tests__/disk-floor.test.ts`.

Add to `src/lib/disk-floor.ts` (keep `readAvailableBytes`, `checkDiskFloor`,
`DISK_SAFETY_FLOOR_BYTES` exports):

```ts
export const DISK_LOW_HELD_PREFIX = 'Disk low — new workspace starts are held';
export const DISK_RESERVATION_HEARTBEAT_MS = 60_000;
export const DISK_RESERVATION_STALE_MS = 10 * 60_000;

export interface DiskReservation { release: () => Promise<void> }
export interface DiskFloorLedgerDeps {
  read?: (path: string) => Promise<number>;          // default readAvailableBytes
  ledgerDir?: string;                                 // default join(getOverdeckHome(), 'disk-reservations')
  withLock?: <T>(lockPath: string, fn: () => Promise<T>) => Promise<T>; // default withFileLock from './vault/file-lock.js'
  isPidAlive?: (pid: number) => boolean;              // default: process.kill(pid, 0); EPERM => alive, ESRCH => dead
  now?: () => number;                                 // default Date.now
  setInterval?: typeof setInterval;                   // default global; tests use vi.useFakeTimers()
}

/** Admit a disk-heavy phase or refuse it. Refusal: { ok: false, error }. */
export async function reserveDiskFloor(
  input: { path: string; bytes: number; label: string },
  deps?: DiskFloorLedgerDeps,
): Promise<{ ok: true; reservation: DiskReservation } | { ok: false; error: string }>;

/** Same arithmetic as reserveDiskFloor, writes nothing. Returns the refusal text or null. */
export async function previewDiskFloor(
  input: { path: string; bytes: number },
  deps?: DiskFloorLedgerDeps,
): Promise<string | null>;
```

Steps:

1. Reservation file `<ledgerDir>/<randomUUID()>.json` with
   `{ "pid": number, "bytes": number, "label": string, "path": string, "createdAt": number }`.
2. `reserveDiskFloor`: `mkdir(ledgerDir, { recursive: true })`, then under
   `withLock(join(ledgerDir, '.lock'), ...)`: list `*.json`, parse each (skip unparsable files and
   delete them), drop and delete entries where `!isPidAlive(pid)` or
   `now() - stat.mtimeMs > DISK_RESERVATION_STALE_MS`, sum the rest (`reservedBytes`,
   `inFlightCount`), read `available`, refuse if
   `available - reservedBytes - bytes < DISK_SAFETY_FLOOR_BYTES`, else write the file. After the
   write, start a heartbeat `setInterval(() => utimes(file, now, now).catch(() => {}), DISK_RESERVATION_HEARTBEAT_MS)`
   and `.unref()` it. Return a `release` that clears the interval, deletes the file with
   `rm(..., { force: true })`, and is safe to call twice.
3. `previewDiskFloor`: same listing and arithmetic, no lock needed, no write.
4. If `read` throws: return `{ ok: true, reservation: { release: async () => {} } }` (D-7).
   If `mkdir`, the lock, the listing or the reservation write throws: return
   `{ ok: false, error: <ledger-unavailable text from D-7> }` and `console.warn` the same text.
   `previewDiskFloor` returns that text when the listing throws.
5. Refusal text (one helper `formatDiskFloorRefusal`):
   `` `${DISK_LOW_HELD_PREFIX}: ${free} GiB free on the filesystem holding ${path}, ${reserved} GiB reserved by ${n} in-flight workspace setup(s), this step needs ${own} GiB, and the safety floor is 10.0 GiB. Free disk space (see /resources) and retry.` ``
   (each number `.toFixed(1)`).
6. Change `checkDiskFloor`'s message to start with the same prefix:
   `` `${DISK_LOW_HELD_PREFIX}: only ${availableGib} GiB free on the filesystem holding ${path}; the safety floor is 10.0 GiB. Free disk space (see /resources) and retry.` ``

Tests (`src/lib/__tests__/disk-floor.test.ts`, temp dir ledger via `mkdtempSync`, injected

### WI-2 Measured estimate in `src/lib/workspace/disk-cost.ts` (FR-4, NFR-1, NFR-2)

Files: `src/lib/workspace/disk-cost.ts` (new), `src/lib/workspace/__tests__/disk-cost.test.ts` (new).

```ts
export const SEED_HOST_DISK_COST_BYTES = 0.5 * GIB;
export const SEED_STACK_DISK_COST_BYTES = 2 * GIB;
export const DISK_COST_MEMO_TTL_MS = 6 * 60 * 60 * 1000;

export interface WorkspaceDiskCost {
  hostBytes: number;
  stackBytes: number;            // 0 when the project has no workspace.docker.compose_template
  hostSource: 'measured' | 'seed';
  stackSource: 'measured' | 'machine' | 'seed' | 'none';
}
export interface DiskCostDeps {
  exec?: (command: string, args: string[], cwd?: string) => Promise<string>; // stdout; default promisified execFile (argument vector, no shell), timeout 60 s, maxBuffer 64 MiB
  unsharedBytes?: (dir: string) => Promise<number>;                           // default: Node fs walk (D-13)
  now?: () => number;
}
/**
 * Structural input: both `ProjectConfig` types (src/lib/workspace-config.ts line 263, used by
 * createWorkspace; src/lib/projects.ts line 436, returned by getProjectSync) satisfy it.
 */
export interface DiskCostProject {
  path: string;
  workspace?: {
    type?: string;
    workspaces_dir?: string;
    progressive?: boolean;
    always_include?: string[];
    repos?: Array<{ name: string; path: string; link_type?: 'worktree' | 'symlink' }>;
    docker?: { compose_template?: string };
  };
}
export function estimateWorkspaceDiskCost(projectConfig: DiskCostProject, deps?: DiskCostDeps): Promise<WorkspaceDiskCost>;
export function parseDockerSize(size: string): number;   // '1.938GB' → 1_938_000_000; units B, kB, KB, MB, GB, TB, decimal
export function resetWorkspaceDiskCostMemo(): void;      // tests only
export function invalidateWorkspaceDiskCostMemo(projectPath: string): void; // called after a phase releases
```

Steps:

1. **Tracked bytes**: for a monorepo, `exec('git', ['-C', projectConfig.path, 'ls-tree', '-r', '-l', 'HEAD'])`; for a
   polyrepo, the same for each repo in `workspace.repos` with `link_type !== 'symlink'` (progressive
   mode: only `always_include`), at `join(projectConfig.path, repo.path)`. Sum column 4, skipping
   `-` (submodules).
2. **Unshared node_modules bytes**: pick the newest (`mtimeMs`) directory in
   `join(projectConfig.path, workspace.workspaces_dir ?? 'workspaces')` whose name starts with
   `feature-`, that has `node_modules`, and has no setup-incomplete marker
   (`isWorkspaceSetupIncomplete` from `../workspace-manager/setup-marker.js`). Fall back to
   `join(projectConfig.path, 'node_modules')`. Sum it with the default `unsharedBytes(dir)`: an
   async recursive walk (`readdir(dir, { withFileTypes: true })`, `lstat` per regular file, add
   `blocks * 512` when `nlink === 1`; never follow symlinks; at most 64 `lstat` calls in flight).
   No shell is involved (D-13). Missing directory → 0.
3. `hostBytes = tracked + unsharedNodeModules`. If step 1 fails → `SEED_HOST_DISK_COST_BYTES`,
   `hostSource: 'seed'`.
4. **Stack bytes** (only when `projectConfig.workspace?.docker?.compose_template`): run
   `docker system df -v --format '{{json .}}'` once; for each finished sibling workspace (same rule
   as step 2) compute `composeProjectNameForWorkspace(wsPath, <issue from folder name>)` from
   `./stack-health.js` (skip on throw), then sum `parseDockerSize(Size)` of `Volumes` whose `Name`
   starts with `${name}_` plus `parseDockerSize(UniqueSize)` of `Images` whose `Repository` starts
   with `${name}-`. `stackBytes` = the maximum over siblings with a non-zero sum
   (`stackSource: 'measured'`). No sibling stack: group **all** volumes in the same output by the
   text before their first `_` (the compose project), sum each group, and use
   `max(largestGroup, SEED_STACK_DISK_COST_BYTES)` (`stackSource: 'machine'`). Docker failure →
   `SEED_STACK_DISK_COST_BYTES`, `stackSource: 'seed'`. No compose template → `0`, `'none'`.
   Every parsed component that is not a finite, non-negative number counts as unmeasurable.
5. Memoize the **promise** per `projectConfig.path` for `DISK_COST_MEMO_TTL_MS` so concurrent
   callers share one measurement; a rejected measurement is not memoized.
   `invalidateWorkspaceDiskCostMemo(path)` deletes the entry; WI-3, WI-4 and WI-5 call it right
   after they release a reservation.
6. `console.warn('[disk-cost] <component> unmeasured for <project>: <reason>; using seed <GiB>')`

## Critique response

Round 1 critique: `.pan/drafts/PAN-4961-critique.md` (codex/gpt-6-sol). All seven findings were
accepted and the design above was changed; each answer names the changed section.

### Ledger failure admits competing starts

Accepted. D-7 now fails **closed** on any ledger failure (directory, listing, write, lock):
`reserveDiskFloor` refuses with the ledger-unavailable text and `previewDiskFloor` returns it.
Only a `statfs` failure still admits, because without a reading there is nothing to compare and
that matches the existing tested `checkDiskFloor` contract. WI-1 adds a test where a throwing
`withLock` makes all 6 concurrent calls refuse.

### Containerize route bypasses the planned gate

Accepted. WI-5 now covers the real `POST /api/workspaces/:issueId/containerize` route in
`container-ops.ts`: it reserves host + stack cost before spawning `infra/new-feature` and holds the
reservation until `./dev all` exits (released once on every terminal path), answering 507
`diskLow` on refusal without spawning anything. `WorkspaceService.containerize` also takes a
stack-cost reservation instead of a plain check (FR-8, D-11).

### Live reservations expire mid-install

Accepted. The 2 h age limit is gone. A reservation is live while its pid runs **and** its file mtime
is newer than 10 minutes; the holder renews the mtime every 60 s with an unref'd interval, so a
running install of any length stays counted, while a file from a crashed process or a previous boot
(reused pid) stops counting within 10 minutes (Glossary, FR-3, WI-1). WI-1 tests a holder that stays
alive across 30 fake-timer minutes and is still counted.

### Unmeasured project cost has no safe bound

Accepted in part. A project with no finished sibling stack now uses the largest stack of any compose
project on the same Docker host, measured from the same `docker system df -v` output, with the seed
only as a lower bound (`max(...)`); the seed is used alone only when Docker cannot be queried at all.
Releasing any reservation invalidates the project's memo, so the second start measures the real
first workspace (D-5, WI-2). Holding a project's first workspace until its cost is known is rejected:
it would block every new project forever, because the cost becomes measurable only after one
workspace exists. The residual error is bounded by the floor: the 10 GiB floor sits about 8 GiB
above the ~2 GB point where writes start failing, and the plain re-checks before each install and
compose stop the next step. WI-2 tests the no-sibling case with a 5 GB volume group on the host.

### Per-repo installs skip later checks

Accepted. WI-3 step 3 puts the re-check immediately before the root install **and** before each
per-repo `execAsync` inside the polyrepo loop (FR-6). WI-3's new test covers a refusal between two
repos: the first repo installs, the second is refused, and the second install command never runs.

### HTTP hold uses a different workspace path

Accepted. Both holds (HTTP route WI-6 and CLI WI-10) call `resolveIssueStackDiskHold(issueId)`, which
resolves the workspace path exactly as `rebuild-stack.ts` does, honouring `workspace.workspaces_dir`
(D-12). The route's own hardcoded path is no longer passed. WI-6 tests a project with
`workspaces_dir: 'wt'`.

### Shell command embeds project paths

Accepted. The estimator runs no shell (D-13): `git` and `docker` run through `execFile` argument
vectors, and unshared node_modules bytes come from a Node `readdir`/`lstat` walk (`nlink === 1`,
symlinks not followed), which is also portable to macOS where `find -printf` does not exist. WI-2
tests a project path containing `"$(touch pwned)"`.

### Unresolved after two critic rounds

- Docker usage command cannot supply per-volume JSON
- CLI fallback creates workspaces without admission
- Partial sibling stacks can shrink the cost estimate
