# PAN-5637: Merge train never admits a polyrepo issue that touches a member repo with no CI

**Issue:** [PAN-5637](https://github.com/eltmon/overdeck/issues/5637)
**Follow-up filed during planning:** [PAN-5640](https://github.com/eltmon/overdeck/issues/5640) (polyrepo batch promote reads MRs at the polyrepo root)
**Sibling in flight:** [PAN-5638](https://github.com/eltmon/overdeck/issues/5638) (GitHub member PRs in the ready set; edits `githubRows` in the same file)

## Glossary

- **Polyrepo project:** a project whose `projects.yaml` entry has `workspace.type: polyrepo`. Its code lives in several member repos listed under `workspace.repos[]`. The project root is not a usable git repo (no remote).
- **Member repo:** one `workspace.repos[]` entry, for example MYN's `fe`, `api`, `infra`, `docs`. A member is **writable** when it does not set `readonly: true`.
- **`ChecksVerdict`:** the CI verdict type in `src/lib/cloister/pr-facts.ts` (line 53): `'green' | 'pending' | 'red' | 'none'`. `none` means the forge reported no pipeline / no checks for the head commit.
- **Ready set:** `listReadyIssuesForProject(projectPath)` in `src/lib/overdeck/ready-set.ts`. The issues whose PRs/MRs are approved, green and mergeable. The merge train builds batches and queues only from it.
- **Merge gate:** `evaluateIssueMergeGate(issueId)` in `src/lib/cloister/merge-gate.ts`. It reads one `PrFacts` for the issue (`getPrFacts`) and judges it with the pure rule `evaluateMergeReadiness(facts, policy)` in `src/lib/cloister/pr-facts.ts`. Every merge door asks it.
- **`ci: none` (new):** an optional field on a `workspace.repos[]` entry. It is the operator's positive statement that this member repo runs no CI. It is the only value of `ci` this change recognizes.
- **CI waiver (new):** the rule "a checks verdict of `none` counts as passing **only** for an MR in a member repo that declares `ci: none`". `red` and `pending` are never waived.
- **`checksPass` (new):** the one exported predicate that implements the CI waiver. Every site this PRD changes calls it, so the rule cannot drift between sites.

## Problem

`gitlabRows` in `src/lib/overdeck/ready-set.ts` (line 164) requires `facts.checks === 'green'` on every open MR of a polyrepo issue:

```ts
      return facts.open && !facts.draft && facts.approved && facts.checks === 'green' && facts.mergeable === true;
```

A member repo with no `.gitlab-ci.yml` never has a pipeline. `gitLabChecks` (`src/lib/cloister/pr-facts.ts`, line 479) returns `'none'` when the MR view has no `head_pipeline`/`pipeline` status. So every issue that opens an MR in such a repo is never ready, never queued, and never merges through the train.

MYN's `eltmon/myn-infra` (repo key `infra`, path `infra`) and `eltmon/mind-your-now-docs` (repo key `docs`, path `docs`) have no CI. Evidence from 2026-11-23: `listReadyIssuesForProject('/home/eltmon/Projects/myn')` returned `[]` while MIN-1144 had api!108 (approved, green, mergeable) and infra!19 (approved, **checks none**, mergeable), and MIN-1146 had api!107 and infra!18 in the same shape.

The merge gate has the same rule. `evaluateMergeReadiness` (`src/lib/cloister/pr-facts.ts`, line 963) refuses `none` on purpose:

```ts
  // FR-9 is a positive test on both: `none` (no checks reported for the head
  // commit) and `null` (the forge has not computed mergeability yet) are the
  // absence of evidence, not evidence of readiness. Merging on either is how a
  // red or conflicting branch reaches main.
  ...
  if (facts.checks !== 'green') return { ready: false, reason: `no CI checks reported on PR HEAD ${head}` };
```

For a polyrepo issue, `readPrFacts` (`src/lib/cloister/pr-facts.ts`, line 671–689) returns the facts of the **first** writable GitLab member that has an MR on the issue branch, in `workspace.repos[]` order. For MIN-1144 that is `api` (listed before `infra`), so the gate never reads infra!19. But an issue that changes only `infra` or only `docs` gets facts from that CI-less repo, and the gate refuses it forever with "no CI checks reported".

**Constraint (from the issue):** the `none`-is-not-green rule must not loosen for repos that do run CI. The fix is an explicit, per-repo, positive signal.

## Decisions (made here; the executor does not re-decide them)

- **D1 — Config shape.** `workspace.repos[].ci?: 'none'` on `RepoConfig`. Only the exact string `'none'` turns the waiver on. A missing field, or any other value (`'github-actions'`, `false`, `''`), keeps today's rule. Unknown values are ignored silently: no error, no warning, no doctor check.
- **D2 — Only `none` is waived.** With `ci: none`, `red` still blocks ("CI checks failing") and `pending` still blocks ("CI checks still pending"). If a CI-less repo later gains a pipeline that fails, the merge still stops. Without `ci: none`, `none` still blocks.
- **D3 — Facts stay honest.** `PrFacts.checks` keeps reporting the forge's own verdict (`'none'`). The waiver is applied at judgment time by `checksPass`, never by rewriting `checks` to `'green'`. UI that shows the checks verdict keeps showing "none".
- **D4 — How the gate learns the member.** `readPrFacts` already holds the `ResolvedProjectRepo` it found the MR in. It stamps `ciNone: true` on the returned facts when that repo declares `ci: none` (via `withMemberCi`). `PrFacts` gains an optional `ciNone?: boolean`. No other reader sets it, so GitHub facts and GitLab monorepo facts never carry it.
- **D5 — Scope by forge.** The waiver is honored for **GitLab** members of a polyrepo project: in the ready set's `gitlabRows` and in the gate's GitLab read path. `githubRows` is **not** changed: (a) PAN-5638 is rewriting that function's approval rule right now, and (b) the GitHub listing maps an empty check rollup to `'pending'`, not `'none'` (`toChecksState`, `src/lib/overdeck/derived-issue-state.ts`, line 345), so a `none` waiver would never fire there. A GitHub member that sets `ci: none` gets no effect; the docs say so.
- **D6 — Board consistency.** The merge-train board (`src/dashboard/server/services/merge-train-board.ts`) has two `checks === 'green'` tests on the same `PrFacts` (lines 294 and 424). They switch to `checksPass`, so a car the ready set admitted is not shown as `checks-pending`.
- **D7 — Out of scope: batch promote.** Promote (`postUatGenerationPromotePayload`, `src/dashboard/server/services/uat-train.ts`, line 882) admits a member only when `getDerivedIssueState(...).state === 'ready'`. For a polyrepo issue the derived state reads MRs at the polyrepo root, where `glab` fails, so it finds no MR at all. A read-only probe on 2026-11-23 returned `pr: null` for MIN-1144 and MIN-1146. That is a separate defect, unrelated to CI, filed as PAN-5640. This issue's acceptance is "the issue enters the ready set and the gate answers ready", **not** "the issue merges".
- **D8 — Unchanged neighbours.** `mergeabilityPending` in `merge-gate.ts` (line 64), `withForgeApprovalAtHead` (GitHub only), `evaluateConflictRepairGate` (it already forces `checks: 'green'`), `blockerReasonsFor` (it never reports `none`), and `deriveState` are not changed.
- **D9 — No noisy `false` fields.** `resolveConfiguredRepos` and `memberReposForProject` add `ciNone: true` only when the repo declares `ci: none`, by conditional spread (`...(repo.ci === 'none' ? { ciNone: true } : {})`). Repos without the field produce objects identical to today's, so existing `toEqual` assertions in `tests/lib/project-repos.test.ts` and `src/lib/overdeck/__tests__/ready-set.test.ts` keep passing unchanged.
- **D10 — The MYN config edit.** The work agent edits the operator's `~/.overdeck/projects.yaml` itself: it copies the file to `~/.overdeck/projects.yaml.bak-2026-11-23-ci-none` first, then adds `ci: none` under the `mind-your-now` project's `infra` and `docs` entries only. The running code ignores unknown repo fields (`projects.yaml` has no schema validation; `RepoConfig` is a plain interface), so the edit is safe before this change deploys. Auricle's `infra` entry is **not** touched.

## Requirements

### Functional

- **FR-1:** A `workspace.repos[]` entry may set `ci: none`. `resolveConfiguredRepos` returns that repo with `ciNone: true`. A repo without the field, or with any other value, has no `ciNone` property.
- **FR-2:** `checksPass({ checks, ciNone })` returns `true` when `checks === 'green'`, or when `checks === 'none'` and `ciNone === true`. It returns `false` for every other combination, including `red` or `pending` with `ciNone: true`.
- **FR-3:** In a polyrepo project, an open GitLab member MR that is approved, mergeable, not a draft, and whose facts show `checks: 'none'` counts as ready in `listReadyIssuesForProject` when its member repo declares `ci: none`. The issue is ready when every open MR/PR for it is ready, as today.
- **FR-4:** `getPrFacts` stamps `ciNone: true` on facts read from a GitLab member repo that declares `ci: none`. `evaluateMergeReadiness` treats those facts' `checks: 'none'` as passing. Every other refusal reason (not approved, draft, red, pending, not mergeable, failed UAT) still applies in its existing order.
- **FR-5:** The merge-train board computes `inReadySet` and the strike `checks-pending` state with `checksPass`, so a waived MR is shown the same way the ready set and gate judge it.
- **FR-6:** MYN's `infra` and `docs` entries in `~/.overdeck/projects.yaml` carry `ci: none`.
- **FR-7:** The `ci` field, its exact effect, its GitLab-only scope, and "remove it when the repo gains CI" are documented in `configuration/polyrepo.mdx` and `docs/MERGE-TRAIN.md`, with a changelog entry.

### WI-2 `ci-waiver-predicate` — one predicate for the CI waiver (FR-2, FR-4 helper)

Files: new `src/lib/cloister/member-ci.ts`, new `src/lib/cloister/__tests__/member-ci.test.ts`.

Create `src/lib/cloister/member-ci.ts` with exactly these two exports and no imports:

```ts
/**
 * PAN-5637: the CI waiver for polyrepo member repos that run no CI.
 *
 * A checks verdict of `none` (the forge reported no pipeline for the head) is
 * the absence of evidence, so merge readiness refuses it (FR-9). A member repo
 * that declares `ci: none` in `projects.yaml` has no CI by the operator's own
 * statement; for an MR there, `none` passes. `red` and `pending` never pass,
 * so a repo that later gains a failing pipeline still blocks. The ready set,
 * the merge gate and the merge-train board all ask this one predicate.
 */

/** True when the checks verdict lets a merge through. */
export function checksPass(facts: { readonly checks: string; readonly ciNone?: boolean }): boolean {
  return facts.checks === 'green' || (facts.checks === 'none' && facts.ciNone === true);
}

/** The facts marked `ciNone` when the member repo they were read from declares `ci: none`. */
export function withMemberCi<T extends object>(facts: T, repo: { readonly ciNone?: boolean }): T {
  return repo.ciNone === true ? { ...facts, ciNone: true } : facts;
}
```

Tests in `src/lib/cloister/__tests__/member-ci.test.ts`:
- `'passes green with or without ciNone'`
- `'passes none only when ciNone is true'` (`none` + `ciNone: true` → true; `none` + absent → false; `none` + `ciNone: false` → false)
- `'never passes red or pending, even with ciNone'`
- `'withMemberCi stamps ciNone only for a ci: none repo'` (returns the same object reference when `repo.ciNone` is not true).
