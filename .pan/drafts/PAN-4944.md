# PAN-4944 — W-APPR1: Approvals for every harness and a fleet-wide pending list

**Status:** planned · **Revision:** 1 (2026-11-03) · **Author:** Claude Opus 5.5 (planning agent, `pan plan --auto`)
**Issue:** [PAN-4944](https://github.com/eltmon/overdeck/issues/4944) · **Epic:** [PAN-4927](https://github.com/eltmon/overdeck/issues/4927) (`.pan/drafts/pan-4927.md`, work item W-APPR1, FR-10, AC-15)
**Depends on:** W-MCP1 = [PAN-4931](https://github.com/eltmon/overdeck/issues/4931) — **merged** (`8bdce46e72a`). `OverdeckTool.scope`, `OverdeckTool.audience`, `McpToolContext.isAgent` and `visibleTools()` exist on `main`.
**Base commit verified:** `7bf5d1b118b` (2026-11-03).

**Why this exists.** The dashboard already has eight approval routes with `approve` rows in the route-scope table, but the MCP server exposes only two of them (`answer_question` for Claude Code conversations and `answer_permission`). An MCP client cannot answer a pane menu, a Pi ask, a Codex approval, a plan approval, or any work agent's prompt. `list_pending_input` also reads only this machine's conversations, so it never shows agents or linked machines. This issue adds the missing tools and makes `list_pending_input` fleet-wide.

## Glossary

- **MCP tool:** an `OverdeckTool` (`src/lib/mcp/tool.ts:21-31`): `name`, `description`, `inputSchema`, `scope`, `audience`, `run`. Every tool proxies one or more dashboard HTTP routes through `ctx.api.request(method, path, body)` with the caller's Bearer token, so the route-scope table judges each call.
- **`tools/list` visibility:** `visibleTools()` (`src/lib/mcp/server.ts:41-43`) shows a tool only when the token's scopes satisfy `tool.scope` and (`audience === 'any'` or the caller is an agent token). A hidden tool answers `Unknown tool <name>` on `tools/call`.
- **Route-scope table:** `ROUTE_SCOPES` in `src/dashboard/server/route-scopes.ts`. Unlisted routes need `admin`. `requiredScopeFor()` (line 226) strips the `@<env>` segment of a linked conversation path before matching, so `/api/conversations/@desk/conv-a/pane-choice` needs the same scope as `/api/conversations/:id/pane-choice`.
- **No-loss matrix:** `tests/unit/lib/overdeck/no-loss-matrix.ts`. Every route in a top-level file of `src/dashboard/server/routes/` needs a row; `src/dashboard/server/__tests__/route-scopes.test.ts:12` also fails when a route-scope row has no matrix row.
- **Pending input / prompt kind:** something a session waits on the operator for. Conversation rows carry the payload fields `pendingAskUserQuestion`, `pendingProposedPlan`, `pendingPaneChoice`, `pendingPermission`. Agent rows carry `pendingInputKinds` (`askUserQuestion`, `exitPlanMode`, `permissionRequest`, `sessionResume`, `rateLimit`, …).
- **Needs-You feed:** `buildNeedsYou()` (`src/dashboard/server/services/needs-you-feed.ts:66`) → `{ hash, conversations, agents }` for this machine. Its `hash` rides in the link heartbeat; linked machines cache the feed (`linked-needs-you-sync.ts`).
- **Channel permission request:** a work agent's tool-permission request that arrived through the Channels bridge. The read model holds it as a `ChannelPermissionRequestSnapshot` (`packages/contracts/src/types.ts:297-305`: `requestId, agentId, issueId?, toolName, description, inputPreview, createdAt`), apart from the agent row.
- **Linked machine:** another Overdeck this one is linked to (PAN-4645/4651). A conversation there is addressed `@<environment-id|label>/<name>`; the linked-conversation proxy (`src/dashboard/server/linked-conversation-proxy.ts`) forwards `/api/conversations/@…` requests with the token's scopes as the ceiling. **There is no proxy for `/api/agents/@…`.**
- **Agent (in this doc):** an Overdeck-managed work agent or role run addressed by its agent id (`agent-pan-123`), answered through `/api/agents/:id/*` routes. Distinct from a conversation.

## Requirements

### Functional
- **FR-1** `GET /api/needs-you` (scope `read:conversations`) answers this machine's `{ conversations, agents }`. Agent rows add `pendingAskUserQuestion` (when the read model has one) and `permissionRequests: [{ requestId, toolName, description, inputPreview, createdAt }]` (when the agent has open channel permission requests). Every agent with an open channel request is listed and has `permissionRequest` in `pendingInputKinds`. `inputPreview` is redacted with `redactPermissionInputPreview`.
- **FR-2** `list_pending_input` answers `{ machines: [ { environmentId: null, label: 'this machine', conversations, agents }, …one entry per online linked machine ], fleetError? }`. Linked conversations are renamed `@<environmentId>/<name>`; linked agents are renamed `@<environmentId>/<id>` and carry `remote: true`. A failed fleet read keeps the local entry and adds `fleetError`.
- **FR-3** `answer_pane_choice` answers a conversation's pane menu (`pane-choice`).
- **FR-4** `answer_codex_approval` answers a Codex conversation's approval (`codex-approval`).
- **FR-5** `answer_pi_ask` answers a Pi conversation's ask modal (`pi-ask-answer`).
- **FR-6** `answer_plan` answers a conversation's plan approval (`plan-action`).
- **FR-7** `answer_agent_plan` answers an agent's plan approval (`/api/agents/:id/plan-action`).
- **FR-8** `answer_agent_permission` answers an agent's channel permission request (`/api/agents/:id/permissions/:requestId/respond`).
- **FR-9** `answer_question` accepts `agentId` instead of `conversation` and then posts to `/api/agents/:id/answer-question`. For a Pi conversation it refuses and names `answer_pi_ask`; for a Codex conversation it refuses and names `answer_codex_approval`.
- **FR-10** Every answer tool that takes `conversation` accepts `@<machine>/<name>` and reaches the linked machine through the existing proxy. Every tool that takes `agentId` refuses an id starting with `@` before any request.
- **FR-11** Documentation states the new tools, their scope and arguments, the new route, and that agent answers reach this machine only.

### Non-functional
- **NFR-1 One authority.** Each new tool is a thin proxy to exactly one route (`list_pending_input`: two GETs); the route-scope table judges it. No new route-scope rows except `GET /api/needs-you`.
- **NFR-2 Validation before requests.** A tool rejects malformed arguments with a tool error and makes **zero** dashboard requests.
- **NFR-3 Module boundary.** `src/lib/mcp/*` imports no dashboard server code (F-1). Copy the plan action list as a constant; do not import `conversation-delivery.ts`.
- **NFR-4 File size.** `tools-approve.ts` stays under 600 lines (expected ≈ 380). New `routes/needs-you.ts` stays under 150 lines. `server.ts` grows by 2 lines (one import, one layer entry).
- **NFR-5 Async only.** No `execSync`/`spawnSync`/`execFileSync`, no new `*Sync` function (repo rules `no-execsync-server`, `prefer-async`).
- **NFR-6 `buildNeedsYou()` is untouched.** Its shape and hash feed the link heartbeat and every peer's cache; enrichment happens only in the new route.
- **NFR-7 Effect façades.** No new exported Effect wrapper; `npm run lint:effect-facades` does not rise.

## Decisions

- **D-1 Enrich in the route, not the feed.** `routes/needs-you.ts` calls `buildNeedsYou()`, drops `hash`, and joins read-model details onto agent rows. `needs-you-feed.ts` does not change (NFR-6).
- **D-2 Agent rows get ids (beyond the epic PRD).** The epic's step 1 said the route answers `buildNeedsYou()` without the hash. That leaves `answer_agent_permission` with no way to learn a `requestId` and `answer_question(agentId)` with no question text (F-4). So the route adds `permissionRequests` and `pendingAskUserQuestion`. Agents that have a channel request but empty kinds are added (F-4).
- **D-3 Redact previews.** `inputPreview` goes through `redactPermissionInputPreview` (F-5) because MCP output lands in bot and agent transcripts.
- **D-4 Agent tools are this-machine only.** No `/api/agents/@…` proxy exists. Tools taking `agentId` refuse an id that starts with `@` with `AGENT_ON_LINKED_MACHINE_TEXT = 'agentId names an agent on a linked machine; answer it on that machine. These tools reach agents on this machine only.'` `list_pending_input` marks linked agents `remote: true`.
- **D-5 One file.** All tools stay in `src/lib/mcp/tools-approve.ts` (≈ 380 lines < 600). No `tools-approve-agent.ts`.
- **D-6 Final tool order** (`APPROVE_TOOLS`, therefore the tail of `ALL_TOOLS`): `list_pending_input, answer_question, answer_permission, answer_pane_choice, answer_codex_approval, answer_pi_ask, answer_plan, answer_agent_plan, answer_agent_permission`. Sixteen tools in all.
- **D-7 Argument names mirror route bodies**, except `conversation`/`agentId` for the path segment. `answer_pi_ask` keeps `answers` (array, exactly one string) to match the route and `answer_question`.
- **D-8 `answer_codex_approval.toolUseId` is optional in the schema** (TUI transport ignores it) and the description says to pass `pendingAskUserQuestion.toolUseId` from `list_pending_input` (app-server transport requires it).
- **D-9 `list_pending_input` output is a breaking shape change** (array → `{ machines }`). Accepted: the epic PRD specifies it, and MCP tools are pre-1.0.
- **D-10 Agent pane menus are out of scope.** `POST /api/agents/:id/pane-choice` needs `admin` (F-2). Adding its row widens the `approve` scope and is a separate decision.
- **D-11 AC-15 proof.** "Resolves its prompt kind on a test conversation" is proven mechanically by `mcp-acceptance.test.ts`: real gate, real `/mcp`, real route-scope table, stub answer routes. Each tool must reach its route with the documented body under `approve` and be hidden without it. Live resolution of real prompts is the test role's UAT and is not required for done.

function requiredInteger(args: Record<string, unknown>, field: string, min: number, max: number): ArgResult<number> {
  const parsed = optionalInteger(args, field, min, max, undefined);
  if (!parsed.ok) return parsed;
