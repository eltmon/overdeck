# PAN-2420 — Pipeline merge robustness against GitHub App 403 permission failures

**Issue:** [PAN-2420](https://github.com/eltmon/overdeck/issues/2420) — bug(cloister): pipeline merge fails with GitHub App 403 'Resource not accessible by integration' — merge door falls back to nothing

## Glossary

- **Merge door** — the single server path that squash-merges an approved PR:
  `mergePullRequestWithAppPromise` (`src/lib/github-app.ts:549`) → its Effect wrapper
  `mergePullRequestWithApp` (`:852`) → `forge.ts mergeReviewArtifact` (`:227`) →
  `merge-ops.ts triggerMerge` step 4b (`:1136`).
- **GitHub App** — the `overdeck-agent` GitHub App installation (id 144090266) whose
  installation access token authenticates the merge door. Its `permissions` object must
  include `pull_requests: write` and `contents: write` to merge a PR.
- **Installation token** — the short-lived token minted by
  `generateInstallationTokenPromise` (`src/lib/github-app.ts:206`). GitHub's
  create-installation-token response includes a `permissions` object that the current code
  discards.
- **merge_status** — the `merge_status` column on `review_status`
  (enum `'pending' | 'queued' | 'merging' | 'verifying' | 'merged' | 'failed'`,
  `src/lib/review-status.ts:46`). Written via `setReviewStatus`; a change emits an activity
  entry (the operator-facing "needs-you" surface) with `details: mergeNotes`
  (`src/lib/review-status.ts:485-494`).
- **Reconciler** — `reconcileStaleMergeStatus` (`src/lib/cloister/deacon-merge.ts:145`), run
  every deacon patrol (`deacon.ts:2947`). Detects a feature branch merged on GitHub whose
  `merge_status` is stale and terminalizes it (`merge_status='merged'` + `postMergeLifecycle`).
- **Respawn / dispatch paths** — the sites that call `spawnRun(issueId, role, …)` to (re)dispatch
  work/review/test agents against a feature branch.
- **Out-of-band merge** — a PR merged on GitHub by something other than the merge door (the
  operator's `gh`, or the App after a scope grant) while our `merge_status` still reads `failed`.
- **verifyMergedBeforeLifecycle** — existing GitHub-authoritative "is this branch's PR merged?"
  read (`src/lib/cloister/merge-verification.ts:21`), returns `{ merged, reason }`.

## Problem

On 2026-07-06 the first merge through the unified pipeline (PAN-2402, PR #2411) reached the
final GitHub call and failed:

```
github merge failed: GitHub merge failed: 403 {"message":"Resource not accessible by integration"}
```

The App installation lacked `pull_requests:write` / `contents:write`. Three durable defects
remain even though the operator has since granted the scopes:

1. **No boot preflight.** Nothing verifies at boot that the App can actually merge. The merge
   permission gap only surfaces at the moment of the first real merge, mid-pipeline.
   `getMergeBackendStatus` (`github-app.ts:147`) checks only that credential *files exist*, not
   that the token carries merge scopes. `generateInstallationTokenPromise` (`:206`) already
   receives GitHub's `permissions` object but discards it (`:233`).

2. **Merge door does not distinguish permission failure from transient.** The 403 is not in
   `forge.ts`'s retry set (`:283-295`, matches 405/409/422/mergeable-state only), so it is
   rethrown; `merge-ops.ts triggerMerge` step 4b's transient check (`:1167-1171`, timeouts /
   ECONNRESET only) does not match it either, so it falls to the generic `else`
   (`:1183-1186`) that records `merge_status='failed'` with the raw 403 text. The operator gets
   a generic failure, not "the App is missing scope X".

3. **No auto-reconciliation after an out-of-band merge, and respawn paths dispatch against a
   merged branch.** After the 403, PAN-2402's PR was merged out-of-band but `merge_status`
   stayed `failed` for **90 minutes** while the pipeline respawned work+review+test agents
   against the already-merged branch (three live sessions killed manually; issue closed
   manually). Root cause is a **deadlock**: `reconcileStaleMergeStatus` *does* process
   `merge_status='failed'` (it skips only `'merged'`, `deacon-merge.ts:151`) and *would*
   detect the merged PR — but it **defers whenever a work/planning agent is active**
   (`deacon-merge.ts:226-235`, the PAN-1994 anti-contamination guard). The respawned work
   agent kept `hasActiveAgent` true, so the reconciler deferred every patrol. Meanwhile no
   dispatch site checks GitHub PR state before spawning (`service.ts:305` gates only on
   `merge_status==='merged'`; the orphan/re-dispatch sites — `deacon-review-status.ts:587`,
   `test-agent-queue.ts:85`, `review-agent.ts:377`, `merge-train-deps.ts:70`,
   `deacon-swarm.ts:825` — check nothing).

## Proposal

Three independent, additive slices. None removes an existing behavior; each is a superset of
today's handling.

**A. Boot preflight (asks #1).** Have `generateInstallationTokenPromise` surface GitHub's
`permissions`; add `verifyAppCanMerge()` that mints a token and reports the missing merge
scopes; add a boot service `warnIfAppCannotMerge()` (mirroring the existing
`merge-backend-health.ts` / `warnIfAutonomousMergeBackendUnavailable` pattern, called at
`main.ts:93`) that logs an actionable warning + activity entry naming the missing scope.

**B. Merge-door error classification (ask #2).** Add `isIntegrationPermissionError()`; in
`merge-ops.ts` step 4b, branch permission failures into `merge_status='failed'` with an
**actionable `mergeNotes`** that names the exact missing scopes (obtained from
`verifyAppCanMerge()`), distinct from the transient path. Because a `merge_status` change
already emits an operator-facing activity entry with `details: mergeNotes`, this *is* the
"needs-you" surface — no new enum value or UI needed.

**C. Reconcile + respawn guard (ask #3).** Add a shared, GitHub-authoritative pre-dispatch
guard `shouldSkipDispatchAsMerged(issueId)` (wrapping `verifyMergedBeforeLifecycle`) and call
it at the advancing-role respawn sites so a merged branch is never re-dispatched; and narrow
the reconciler's PAN-1994 defer so a **confirmed-merged PR** terminalizes even when a
work/advancing agent is the only thing "active" (that agent is a zombie — its work already
landed). Reserve the defer for a genuine re-plan (active `planning-` agent or a spec back in
`draft`/`proposed`). Together these close the deadlock from both ends, exactly as the operator
directed.

## Requirements

- **FR-1** `generateInstallationTokenPromise` returns the installation token's `permissions`
  map; `InstallationToken` gains a `permissions?: Record<string,string>` field.
- **FR-2** `verifyAppCanMerge()` mints a token and returns `{ canMerge, missing: string[], detail }`
  where `missing` names any of `pull_requests`/`contents` not at `write`.
- **FR-3** A boot preflight logs an actionable warning + `warn`-level activity entry naming the
  missing scope(s) when the App is configured but cannot merge; it is silent when the App can
  merge or when no App is configured (gh-CLI / no-backend cases are already covered by
  `warnIfAutonomousMergeBackendUnavailable`).
- **FR-4** `isIntegrationPermissionError(message)` returns true for a 403 whose body contains
  `Resource not accessible by integration`, false for transient/other errors.
- **FR-5** On a permission-class merge failure, the merge door records `merge_status='failed'`
  with a `mergeNotes` that names the missing scope(s) and the remedy, distinct from the raw
  transient message.
- **FR-6** A shared `shouldSkipDispatchAsMerged(issueId)` returns `{ skip, reason }` using the
  GitHub-authoritative PR-merged read, resolving the project internally.
- **FR-7** The advancing-role respawn sites skip dispatch (with a logged reason) when the
  issue's PR is already merged on GitHub, regardless of recorded `merge_status`.
- **FR-8** `reconcileStaleMergeStatus` terminalizes a confirmed-merged PR (sets
  `merge_status='merged'` + runs `postMergeLifecycle`) even when a non-planning agent is
  running, deferring only for a genuine re-plan.
- **NFR-1** No new blocking network call on the dashboard event loop; preflight is
  fire-and-forget (`void`), matching `warnIfAutonomousMergeBackendUnavailable`.
- **NFR-2** No `execSync` in server-reachable code; async exec/`spawn` only.
- **NFR-3** Retry/delay-exercising tests use fake timers.

## Planning Q&A

Auto mode (`pan plan --auto`) — no interactive questions. Inferred decisions recorded in
`plan.autoDecisions[]` (see spec). Key decisions:

- **Needs-you surface = actionable `mergeNotes` on the existing `failed` status**, not a new
  enum value. Rationale: a `merge_status` change already emits an operator-facing activity
  entry carrying `mergeNotes` as `details` (`review-status.ts:485-494`); adding an enum value
  would ripple through every `merge_status` consumer for no added signal.
- **Dispatch guard reuses `verifyMergedBeforeLifecycle`** via a thin named wrapper rather than
  editing `spawnRun` centrally. Rationale: `spawnRun` returns a run object every caller
  dereferences; making it return-null/throw on skip is a wider, riskier contract change than a
  per-site early-return that each caller's existing control flow already supports.
- **Boot preflight does not gate boot; it warns.** Rationale: the App scope is operator-fixable
  out-of-band; a hard boot failure would strand the whole dashboard over a merge-only capability.
- **`bootReconciliationSkipReason` (sync) is left unchanged** — see NonGoals. The steady-state
  reconciler terminalizes a merged branch within one patrol after boot, so a briefly-resumed
  work agent is caught by FR-8 rather than by making a sync predicate do a network call.

## NonGoals

- Not changing the GitHub App's actual installed permissions (operator already granted them).
- Not adding a new `merge_status` enum value for permission failures.
- Not making `bootReconciliationSkipReason` (`boot-reconciliation-predicates.ts:15`) do a
  network PR-state check — kept sync; FR-8 covers a briefly-resumed post-boot work agent.
- Not guarding the swarm work-slot dispatch (`deacon-swarm.ts:825`) or the merge-train conflict
  resolver (`merge-train-deps.ts:70`) — those dispatch against pre-merge branches during active
  work; guarding them adds per-slot latency for a case the incident did not involve. If needed,
  file a follow-up.
- Not weakening the PAN-328 `in-flight-guard` idempotency test or the PAN-1994 intent (defer for
  a genuine re-plan is preserved).
