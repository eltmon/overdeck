# PAN-5238 — Skills for this issue takes 37–77 s to load (`GET /api/skills/overrides?issue=`)

**Issue:** https://github.com/eltmon/overdeck/issues/5238
**Status:** draft (planning, `pan plan --auto`)

## Glossary

- **Skills for this issue** — the collapsed section in the issue drawer
  (`IssueSkillsSection`, `src/dashboard/frontend/src/components/skills/SkillOverridesSections.tsx`).
  Opening it fetches `GET /api/skills/overrides?issue=<ID>` once.
- **Skill catalog** — `listSkillCatalog()` in `src/lib/skill-overrides/catalog.ts`: every
  directory holding a `SKILL.md` under `~/.overdeck/skills`, `~/.claude/skills`,
  `~/.agents/skills` and `<projectRoot>/.pan/skills`. First root wins on a name clash,
  and that root sets the entry's `origin`.
- **Pack catalog** — `listPackCatalog()` in the same file: each registered skill pack
  (`config.yaml` `skills.packs.<id>`) with the manifest of its trusted commit, read by
  `readPackManifest()` in `src/lib/skill-packs/adapters.ts`.
- **Extract dir** — `~/.overdeck/packs/<id>/<commit>/`, written by `extractCommit()`
  (`src/lib/skill-packs/sources.ts`) into a temp dir and then renamed into place. Its
  contents are fixed for that commit. The one exception: when `pluginRoot` is given and
  missing, `extractCommit` deletes the dir and renames a fresh extraction into place,
  so the directory gets a new inode.
- **libuv threadpool** — the 4-thread pool (Node default; `UV_THREADPOOL_SIZE` is unset
  for the dashboard, verified in `/proc/<pid>/environ`) that runs every `fs/promises`
  call. When other work keeps the pool busy, each fs call waits in its queue.
- **Sequential fs chain** — a loop that `await`s one fs call per file. Its latency is
  (number of calls) × (queue wait), so a busy pool multiplies it.
- **Fs limiter** — `createPromiseConcurrencyLimiter(max)` from `src/lib/concurrency.ts`
  (exists today, line `export function createPromiseConcurrencyLimiter(max: number)`).
  Every call to the returned function shares one queue with at most `max` tasks running.

## Problem and root cause

The issue reports 57.5 s, 77.4 s and 37.0 s for `?issue=PAN-5185`, against 0.31 s
(global) and 0.19 s (project). The issue suspects `resolveProjectFromIssueSync`.

**What planning measured (2026-11-13, live dashboard on :3011, pid 1003443, started 22:57:29):**

1. **The suspected sync lookup is not the cause.** `resolveProjectFromIssueSync`
   (`src/lib/projects.ts`, `export function resolveProjectFromIssueSync(`) calls
   `loadProjectsConfigSync()`, which re-parses `projects.yaml` only when its mtime
   changes (`_projectsCache`). One request costs a `statSync` and a loop over ~25 projects.
2. **The trigger did not reproduce.** Repeated requests now take 0.26–3.3 s at every
   level, including 8 concurrent `?issue=PAN-5185` requests (3.3 s each). In one loop the
   *global* level took 3.7 s while the issue level took 0.3 s, so the level is not the
   variable. The slow runs fell inside the first ~8 minutes after a dashboard restart
   (22:57:29 start; the issue was filed 23:05:04). `dashboard.log` shows steady pool and
   loop pressure in that period and after it: repeated `parseTranscriptSnapshot` reads of
   121 MB transcripts and `costReconcileSweep` runs of 2–9 s. The log has no timestamps,
   so planning cannot isolate the exact window.
3. **The request is a ~3,900-step sequential fs chain.** Counting `fs/promises` calls
   made by `listSkillStates({ issueId: 'PAN-5185' })`: 475 for the skill catalog
   (`readRoot` awaits one `readFile` per skill dir; 466 skill dirs across the three home
   roots) and 3,408 for the pack catalog (`readPackManifest` → `listExecutables` awaits one
   `lstat` per file in each pack skill dir; impeccable alone has 4,071 files). Nearly all
   of them are awaited one at a time.
4. **A busy threadpool turns that chain into a minute.** With 16 background threadpool
   jobs running (a stand-in for the transcript reads), the real `listSkillCatalog` took
   26.0 s and the real `listPackCatalog` 40.5 s, 66 s in total, which sits in the reported
   37–77 s band. On a quiet pool they take 0.34 s and 0.16 s. A synthetic read of the
   same 466 `SKILL.md` files took 216 s sequentially against 0.65 s unbounded-concurrent
   under a heavier load. Under the lighter load (16 chained `pbkdf2` jobs of 6000
   iterations) it took 24.2 s sequentially, 1.5 s through a 16-slot limiter and 0.73 s
   through a 32-slot limiter.
5. **Nothing in front of the handler is keyed on the `issue` param.** `route-scopes.ts`
   matches on path only and has no `/api/skills/overrides` row, and no server middleware
   reads `searchParams.get('issue')` for this route. The level asymmetry in the report is
   therefore timing, not code: the issue-level runs landed in congested moments.

**Conclusion.** The measured mechanism, a sequential fs chain on a congested threadpool, reproduces 66 s
under synthetic saturation, which matches the report. The live trigger was not observed.
The route is slow whenever the threadpool is congested, at every level.
The issue level was what the operator happened to open during a congested window. The
fix shortens the sequential chain: concurrent, bounded catalog reads, and a manifest
cache keyed on the extract dir's identity. It also adds a slow-request log line to the
route, so if the trigger turns out to be something else, the next occurrence shows up
in `dashboard.log`.

`listPackCatalog()` also runs on every agent launch (`src/lib/skill-overrides/launch.ts`,
`await Promise.all([loadLaunchLayers(ctx), listPackCatalog(), isDeftPipelineLaunch(ctx)])`)
and in `conversation-flags.ts`, so launches get the same speedup.

## Requirements

- **FR-1** — `listSkillCatalog()` issues its per-skill `SKILL.md` reads concurrently
  through an fs limiter, and reads its roots concurrently. It returns output identical to
  today's: same entries, same `origin`, same first-root-wins precedence, sorted by name.
- **FR-2** — `listPackCatalog()` reuses a pack's previously read manifest when the
  extract dir is unchanged. The dir is unchanged when its inode, mtime and ctime, the adapter
  and the read options all match. A rebuilt extract dir, a changed adapter, or a changed
  `browser` readiness re-reads the manifest. A thrown or `null` read is never cached.
- **FR-3** — `readPackManifest()` reads skill `SKILL.md` files and walks executables
  concurrently through an fs limiter, and returns a manifest identical to today's:
  same skills in the same order, same `seen`-name dedupe, and the same `executables`
  list in the same order.
- **FR-4** — `GET /api/skills/overrides` logs one line,
  `[skill-overrides] slow GET level=<global|project|issue> project=<key|-> issue=<id|-> ms=<n>`,
  via `console.warn` when the request takes 2000 ms or more. Faster requests log nothing.
  The timer covers only the handler body. A request the browser sees as slow with no
  slow line means the time went elsewhere: browser connection queueing, the event loop
  before the handler ran, or the network.
- **NFR-1** — No fs limiter in this change allows more than 32 in-flight fs tasks.
  The bound is `32`, written as a named constant in each module. Planning measured
  466 `SKILL.md` reads under the same synthetic load: 24.2 s sequential, 6.2 s at 4,
  1.5 s at 16, 0.73 s at 32, 0.45 s at 64, 0.10 s unbounded. 32 halves the 16-slot time
  and still caps how much of the shared pool queue one request can hold.
- **NFR-2** — `projectForIssue()` (`src/lib/skill-overrides/issue-file.ts`) uses the async
  resolver `resolveProjectFromIssue` (Effect) instead of `resolveProjectFromIssueSync`.
  This is rule compliance, not the performance fix: `src/lib/projects.ts` says
  "Do not add new synchronous callers; server-reachable code uses the async variants."
- **NFR-3** — The response bodies of `GET`/`PUT /api/skills/overrides` stay byte-for-byte
  identical for the same files on disk. No frontend change.

## Decisions

1. **Bounded concurrency, not unbounded `Promise.all`.** An unbounded walk would put
   ~3,400 `lstat`s on the 4-thread pool at once and slow every other dashboard request.
   The limit is 32 (see NFR-1 for the measurements).
2. **Wrap leaf fs calls only.** The limiter wraps `readdir`, `readFile`, `lstat` and
   `readTextOrNull` calls. It never wraps a function that itself calls the limiter, such as
   `walk()`, `readRoot()` or `listExecutables()`. With a shared queue, a wrapped recursive
   call can hold a slot while it waits for a slot, which deadlocks once the recursion depth reaches the bound.
3. **One limiter per module, created at module load.** `catalog.ts` and `adapters.ts`
   each get `const limitFs = createPromiseConcurrencyLimiter(<NAME>_FS_CONCURRENCY)`.
   Concurrent requests share it, so the bound holds across requests.
4. **The manifest cache key is the extract dir's identity, with no invalidation hooks.**
   The key is `dir`. The stored stamp is
   `${stats.ino}:${stats.mtimeMs}:${stats.ctimeMs}:${adapter}:${JSON.stringify(readOpts)}`, where `stats`
   comes from the `lstat` that `listPackCatalog` already runs, and `readOpts` is the
   options object passed to `readPackManifest`, which includes `browser`. `extractCommit`'s
   rebuild renames a new dir into place, which gives a new inode, so the stamp misses with
   no hook in `updatePack`, `removePack`, `enablePackBrowser` or `disablePackBrowser`.
   The `cached`, `browser` and `isRenderReady`/`isBrowserReady` checks keep running on
   every call, outside the cache.
5. **The cache lives in `catalog.ts`, not `adapters.ts`.** `readPackManifest` keeps no
   state; the CLI preview paths (`sources.ts` `readPackManifest(dir, adapter, …)`) are
   unaffected.
6. **The sync-resolver swap is its own item.** It is mtime-cached and is not the cause
   (see Problem, point 1). It ships for rule compliance (NFR-2).
7. **No per-phase timing.** FR-4 logs the total only, so `listSkillStates` keeps its
   signature. If the slow line fires again after this ships, a follow-up adds phase timings.
