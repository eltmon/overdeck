# PAN-5045 — Phone app: group conversations by project, collapsed by default, with + to start a conversation in a project

**Issue:** https://github.com/eltmon/overdeck/issues/5045
**Status:** planned (auto planning, 2026-11-04)

## Summary

The phone's Conversations tab (`/m?tab=conversations`, rendered by the phone app `apps/mobile` and by the
`/m` PWA) shows one flat list, newest first. This change groups that list by project. Every project group
starts collapsed. Each project header has a **+** that creates a conversation in that project through the
existing `POST /api/conversations` route and opens it. Conversations without a project go in a
**No project** group, sorted last.

The phone cannot read the project list today: `GET /api/registered-projects` has no row in the route-scope
table, so it needs `admin`, and a phone token never has `admin`. This change adds one `read:state` row for
that route, which gives the phone the exact data the desktop groups with.

## Glossary

- **Phone app** — `apps/mobile`, the Capacitor app. `apps/mobile/src/shell/MachineView.tsx` renders the
  frontend's `MobileApp` (`src/dashboard/frontend/src/components/mobile/MobileApp.tsx`) for one linked
  machine. Its requests reach that machine over the Anywhere secure channel with a **phone token**.
- **PWA** — the same `MobileApp` served by the dashboard at `/m` in a phone browser. A paired browser
  device holds `['admin']` (`src/dashboard/server/routes/pairing.ts`, `createAccessToken({ … scopes: ['admin'], kind: 'device' })`).
- **Phone token** — an access-token record of `kind: 'phone'` carrying `PHONE_TOKEN_SCOPES`
  (`src/lib/access-tokens.ts` line 112: `read:events, read:state, read:conversations, read:costs, read:settings, tell, operate, approve`). Never `admin`.
- **Route-scope table** — `ROUTE_SCOPES` in `src/dashboard/server/route-scopes.ts`. It lists which scope a
  non-root credential needs per `METHOD path`. Anything not listed needs `admin` (fails closed).
- **Registered projects** — the machine's `projects.yaml` entries, served by `GET /api/registered-projects`
  (`src/dashboard/server/routes/misc/meta.ts` around line 124, grep `'/api/registered-projects'`) as
  `[{ key, name, path, linearTeam, membershipQueryable, githubRepo, tracker, linearProject }]`.
- **Effective project** — the project a conversation belongs to: its explicit `projectKey` override when set,
  otherwise the registered project whose `path` contains the conversation's `cwd`. One resolver decides it:
  `resolveEffectiveProjectKey` in `src/dashboard/frontend/src/components/CommandDeck/projectsData.ts`
  (line 47). The desktop Command Deck groups with it (`components/CommandDeck/index.tsx` around line 480,
  grep `Partition conversations into project-scoped vs unscoped`).
- **No project group** — the bucket for conversations whose effective project is null or not a registered
  project. Key `NO_PROJECT_KEY = '__no-project__'`, label `NO_PROJECT_LABEL = 'No project'`
  (`projectsData.ts` lines 14–15).
- **Linked row** — a conversation row with `origin: 'linked'`, owned by another machine and merged into
  `GET /api/conversations` (`src/dashboard/server/services/conversation-list-merged.ts`). Its `projectKey`
  is the owner machine's key.
- **Fallback mode** — the phone's grouping when the project list request fails (any non-2xx, for example a
  `403 insufficient_scope` from a machine that predates this change). The phone app bundles its own copy
  of the frontend, so a new app can talk to an old machine.
- **Expanded set** — the project keys the operator has expanded on this device, stored in `localStorage`.
  A key not in the set is collapsed, so every group starts collapsed.

## Decisions

- **D-1 Door: add `GET /api/registered-projects` to the route-scope table at `read:state`.** It gives the
  phone the same data and the same resolver as the desktop, so the two groupings cannot disagree.
  Disclosure delta, recorded for review.security:
  - Project root paths are already derivable by every `read:conversations` holder: `GET /api/conversations`
    returns each conversation's `cwd`, and `shared-conversations.ts` sends `cwd` to linked machines.
    `BOT_DEFAULT_SCOPES` already includes `read:conversations`.
  - `githubRepo` is already exposed as `gitOrigin` by `GET /api/machines/projects` under `read:state`.
  - New to non-admin `read:state` holders: `linearTeam`, `tracker`, `linearProject`,
    `membershipQueryable` — low-sensitivity tracker metadata. Accepted.
  - Precedent: `docs/DASHBOARD-AUTH.md` D-8 (PAN-4835) — a scope row is never phone-exclusive; it widens
    the scope for every credential holding it. D-4651-11's "no paths" is the contract of
    `/api/machines/projects` only, and that route is unchanged.
- **D-2 One resolver.** The phone calls `resolveEffectiveProjectKey(conv, registeredProjects, NO_FLEET)` with
  an explicit `NO_FLEET = { combine: false, localKeyByOrigin: new Map() }`. The phone never loads the fleet
  index (fleet routes refuse channel callers), so passing it explicitly keeps the result deterministic. A
  resolved key that is not a registered project goes to No project — the same rule as
  `isUnscopedConversation` (`projectsData.ts` line 76). A linked row whose owner key is not registered on
  this machine therefore lands in No project, as on the desktop without Combine.
- **D-3 Every registered project gets a group, even with zero conversations.** Otherwise the **+** could not
  start the first conversation in a project. An expanded empty group shows `No conversations in this project.`
- **D-4 Order.** Project groups sort by label with `a.label.localeCompare(b.label)` (the desktop's
  `groupProjects` order, `projectsData.ts`). No project is always last and appears only when it has rows.
  Rows inside a group keep the current order: `recencyAt` descending, archived rows hidden.
- **D-5 Label.** `project.name || project.key` in normal mode; the raw `projectKey` in fallback mode;
  `No project` for the bucket. The header also shows the row count.
- **D-6 Fallback mode.** When `GET /api/registered-projects` fails (any non-2xx or network error), the phone
  groups by the raw `row.projectKey` (null → No project), labels each group with the key, and shows no **+**
  on any header. This is the same resolver with an empty project list, plus "keep unregistered keys".
  Rationale: a new app against an old machine gets `403 insufficient_scope`; the list must still render.
- **D-7 + only on registered projects.** The No project group has no **+**: it is not a project, and the
  issue asks for **+** "by the project name". Fallback-mode groups have no **+** because the key cannot be
  checked against the machine's registry.
- **D-8 Create body is `{ projectKey }` only.** The phone has no model or harness picker, so the server's
  configured defaults apply (`handleConversationCreate` logs `model=default`). The phone never sends a
  hard-coded model (repo rule: no hard-coded model fallbacks). If the server answers non-2xx, the group shows
  the server's `error` text inline (`role="alert"`) and the operator stays on the list.
- **D-9 After a successful create:** invalidate the `['mobile-conversations']` query, then call
  `onOpen(conversationRouteKey(created))`, which opens the new conversation full screen.
- **D-10 Persistence.** `localStorage` key `pan-mobile-expanded-projects` holds a JSON array of expanded group
  keys. Store the expanded set, never the collapsed set, so a project that appears later starts collapsed.
  Every read and write is wrapped in `try/catch`; invalid JSON or a throwing accessor reads as an empty set.
  One key for all machines (the phone app renders every machine under one web origin); a key shared by two
  machines' projects expands on both. Accepted.
- **D-11 Desktop unchanged.** No desktop component changes. `MobileConversations.tsx` is rendered only by
  `MobileApp` (verified: no other importer).
- **D-12 Tap targets.** Header toggle and **+** are separate sibling buttons (never nested), each at least
  44×44 px (`min-h-11 min-w-11`), matching NFR-4 of PAN-2355. The toggle carries `aria-expanded` and
  `aria-controls`; the **+** has `aria-label="New conversation in <label>"`.

## Requirements

### Functional

- **FR-1** A phone token can read `GET /api/registered-projects`: the route-scope table maps it to `read:state`.
- **FR-2** The phone conversation list renders one group per registered project and a No project group for
  conversations with no registered effective project; No project sorts last.
- **FR-3** A conversation's group is decided by `resolveEffectiveProjectKey` against the registered projects
  (explicit `projectKey` first, then `cwd` inside a project `path`).
- **FR-4** Every group is collapsed on first load (no stored state); tapping a header toggles it.
- **FR-5** The expanded set persists per device in `localStorage` key `pan-mobile-expanded-projects`.
- **FR-6** Each registered project's header has a **+** that sends `POST /api/conversations` with
  `{ projectKey: <key> }` and, on success, opens the created conversation.
- **FR-7** When the project list request fails, the list still renders, grouped by raw `projectKey`, with no **+**.
- **FR-8** A failed create shows the server's error inline in that group and does not navigate.

### Non-functional

- **NFR-1** Desktop dashboard behavior is unchanged.
- **NFR-2** No new HTTP route; creation uses the existing `POST /api/conversations`.
- **NFR-3** Header buttons meet the 44×44 px tap-target floor.
- **NFR-4** `localStorage` access never throws into render.
- **NFR-5** A Playwright screenshot at 390×844 shows the collapsed and expanded states, committed under
  `apps/mobile/acceptance/` and linked from the PR.

```ts
import { NO_PROJECT_KEY, NO_PROJECT_LABEL, resolveEffectiveProjectKey, type FleetProjectIndex, type RegisteredProjectLite } from '../CommandDeck/projectsData';

export interface GroupableConversation {
  cwd?: string | null;
  projectKey?: string | null;
  origin?: string | null;
  gitOrigin?: string | null;
  createdAt: string;
  lastActivityAt?: string | null;
  lastAttachedAt?: string | null;
  archivedAt?: string | null;
}

export interface MobileConversationGroup<Row> {
  /** Project key, or NO_PROJECT_KEY. Also the expanded-set key. */
  key: string;
  label: string;
  /** True only for a project from a loaded registered list (D-7). */
  canCreate: boolean;
  /** Unarchived rows, newest activity first. */
  rows: Row[];
}

export const EXPANDED_PROJECTS_STORAGE_KEY = 'pan-mobile-expanded-projects';

export function recencyAt(row: GroupableConversation): string; // lastActivityAt ?? lastAttachedAt ?? createdAt
export function groupMobileConversations<Row extends GroupableConversation>(
  rows: readonly Row[],
  registeredProjects: readonly RegisteredProjectLite[] | null, // null = fallback mode (D-6)
): MobileConversationGroup<Row>[];
export function readExpandedProjects(): Set<string>;
export function writeExpandedProjects(keys: ReadonlySet<string>): void;
```

`FleetProjectIndex` is already exported from `projectsData.ts`; define
`const NO_FLEET: FleetProjectIndex = { combine: false, localKeyByOrigin: new Map() };` in the new module.

Rules for `groupMobileConversations`:
1. Drop rows with `archivedAt != null`.
2. **Normal mode** (`registeredProjects` is an array): create one group per registered project
   (`label = name || key`, `canCreate: true`). For each row, `key = resolveEffectiveProjectKey(row, registeredProjects, NO_FLEET)`;
   if `key` is null or not a registered key, put the row in No project.
3. **Fallback mode** (`null`): a group per distinct non-empty `row.projectKey` (`label = key`,
   `canCreate: false`); a null or empty `projectKey` goes to No project.
4. Sort each group's rows by `recencyAt` descending (`b.localeCompare(a)` on the ISO strings, as today).
5. Sort project groups by `a.label.localeCompare(b.label)`; append No project
   (`{ key: NO_PROJECT_KEY, label: NO_PROJECT_LABEL, canCreate: false }`) last, only when it has rows.

`readExpandedProjects` returns `new Set(parsed)` when `localStorage.getItem(KEY)` parses to an array of
strings, else an empty set; any thrown error → empty set. `writeExpandedProjects` calls
`localStorage.setItem(KEY, JSON.stringify([...keys]))` inside `try/catch`.
