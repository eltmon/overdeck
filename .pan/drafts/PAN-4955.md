## Glossary

- **Grok Build:** xAI's local coding agent, the `grok` CLI (installed here: `grok 1.0.34 (3736acbc8658) [stable]`). It loads plugins and attaches their stdio MCP servers.
- **Grok plugin:** a folder with `.grok-plugin/plugin.json` (manifest), optional `skills/<name>/SKILL.md`, `commands/<name>.md`, `.mcp.json`. `grok plugin install <source> --trust` **copies** the folder into `~/.grok/installed-plugins/<name>-<hash>/`; `grok plugin enable <name>` turns it on (plugins are off by default, `~/.grok/docs/user-guide/09-plugins.md`).
- **`${GROK_PLUGIN_ROOT}`:** the variable Grok expands in `.mcp.json` to the installed copy's path.
- **Plugin skill / plugin command:** Grok lists both as slash entries ("skills" in `grok inspect --json`). A skill name that also exists elsewhere is "ambiguous"; Grok then offers qualified forms such as `<plugin>:<skill>` (`invocableAs` in `grok inspect --json`).
- **The shared skill:** `integrations/shared/SKILL.md` (frontmatter `name: overdeck`), copied byte-for-byte to `integrations/<platform>/skills/overdeck/SKILL.md` by `node integrations/shared/sync-skill.mjs`; `--check` exits 1 on any difference (W-INT0, PAN-4952).
- **The Overdeck user skill `overdeck`:** a different skill, `sync-sources/skills/overdeck/SKILL.md` ("overdeck <verb> <args> — alias of /pan"). `pan sync` installs it into `~/.agents/skills/overdeck/`, which Grok also reads. Every computer with Overdeck installed has it.
- **`pan mcp serve`:** the stdio MCP server in `src/cli/commands/mcp.ts`. Its token comes from `OVERDECK_MCP_TOKEN`, else the 0600 file named by `OVERDECK_MCP_TOKEN_FILE` (`readServeToken`, lines 38-73). It verifies the token against **this computer's** registry (`verifyAccessToken(token)`, line 85) before serving.
- **Overdeck connector:** `pan mcp connector login|pair|serve|status|logout` (`src/cli/commands/mcp-connector.ts`, PAN-4950). State lives in `$OVERDECK_CONNECTOR_HOME`, default `~/.overdeck-connector` (`connectorHome`, `src/lib/mcp/connector/home.ts:69-71`); pairing writes `pairing.json` there (`PAIRING_FILE`, `home.ts:33`). `serve --stdio` serves one MCP session on stdin/stdout and sends every diagnostic to stderr (`mcp-connector.ts`, the `serve` action).
- **Reach:** how a bot reaches Overdeck in the Connect a bot dialog. For Grok Build: `this-computer` (default), `connector`, `tailscale` (`BOT_PLATFORMS`, `src/dashboard/frontend/src/components/Settings/anywhere/botSnippets.ts:20`).
- **The pin:** the exact `@overdeck/core` version `run-mcp.sh` passes to `npx` when no capable `pan` is on `PATH` (D-1).
- **Capable `pan`:** a `pan` on `PATH` whose `pan mcp --help` output lists a `connector` subcommand line.

## Decisions

- **D-1 Connector binary: capable `pan` first, then a pinned `npx`.** The epic says `npx -y @overdeck/core@<pinned version>`. No published version has the connector yet, and a user who has Overdeck installed should not download a second copy. So the script uses a capable `pan` when present, else `npx -y "@overdeck/core@${OVERDECK_CORE_VERSION}"` where `OVERDECK_CORE_VERSION` defaults to the pin `0.74.0` (the next minor release after `0.73.1`, the last release without the connector; feature releases have been minor bumps: 0.70.0 → 0.73.0). An environment override `OVERDECK_CORE_VERSION` lets a user match the version the Connect a bot dialog showed them. `@latest` was rejected: it queries the registry on every Grok session start, fails offline, and drops the epic's pinning. PUBLISHING.md makes "the pin is a published version" a pre-publish check.
- **D-2 Capability probe.** "Capable `pan`" is decided by capturing `pan mcp --help` into a variable and matching a line `^[[:space:]]+connector[[:space:]]` with `grep -Eq` on a here-string. Not `pan mcp connector --help`: Commander can print the parent's help and exit 0 for an unknown subcommand with `--help`. Not a pipe into `grep -q`: under `set -o pipefail` a pipe can report SIGPIPE.
- **D-3 `/overdeck` behavior lives in the shared skill.** Probe 1 shows Grok never loads `commands/overdeck.md` while `skills/overdeck/` exists, and the skill copy must stay byte-identical to `integrations/shared/SKILL.md`. So the `status`/`pending`/`answer` rules go into the shared skill (all four platforms get them; Hermes's native `/overdeck` command in W-INT1 uses the same three words). `commands/overdeck.md` still ships, as the epic and the MYN model do, with a body that only points at the skill section, so the two can never disagree.
- **D-4 On an Overdeck computer the plugin form is `/overdeck:overdeck`.** Probe 2. The README, the verification doc and `configuration/mcp.mdx` say so. AC-27's local check uses `/overdeck:overdeck pending` and records what bare `/overdeck pending` does. Renaming either skill is out of scope (NG-4).
- **D-5 Token-file default** (FR-3). `.mcp.json`'s `env` is static, so without a default the user must export `OVERDECK_MCP_TOKEN_FILE` in every shell that starts `grok`. The default path is the one `tokenSetup` already writes. An explicit `OVERDECK_MCP_TOKEN` or `OVERDECK_MCP_TOKEN_FILE` always wins.
- **D-6 README covers two reaches.** "This computer" and "Overdeck connector". The Tailscale reach is listed as not yet working, with the follow-up issue link (fact above, NG-3).
- **D-7 Install command.** Primary: `grok plugin install eltmon/overdeck#integrations/grok-build --trust` then `grok plugin enable overdeck` (`owner/repo#subdir` is a documented source form). Secondary: the local-path form. To pick up a change, uninstall and install again, because install copies the folder.
- **D-8 Live-check home.** The AC-27 local check runs with the operator's real `HOME` (the realistic "This computer" case: real `grok` sign-in, real `pan` skills, so the collision is present), with a temporary read-only token, and ends with `grok plugin uninstall overdeck --confirm` and `pan token revoke` of that token. The MYN plugin is not touched.
- **D-9 Tests are split by item** so items share no test file: `grok-build.test.ts` (WI-1), `grok-build-run-mcp.test.ts` (WI-2), `grok-build-readme.test.ts` (WI-4). The skill section is covered by the existing `sync-skill.test.ts`.

- **Traces:** FR-2, FR-3, NFR-1, NFR-3.

     ```bash
     #!/usr/bin/env bash
     # Overdeck MCP server for Grok Build (PAN-4927 W-INT3, PAN-4955).
     # Serves MCP on stdio by exec'ing, in order: the paired Overdeck connector
     # (a pan that has `mcp connector`, else npx with the pinned @overdeck/core),
     # then `pan mcp serve`. It never writes to stdout: stdout is the server's
     # JSON-RPC. See README.md.
     set -euo pipefail

     OVERDECK_CORE_VERSION="${OVERDECK_CORE_VERSION:-0.74.0}"
     connector_home="${OVERDECK_CONNECTOR_HOME:-$HOME/.overdeck-connector}"

     pan_has_connector() {
       command -v pan >/dev/null 2>&1 || return 1
       local help
       help="$(pan mcp --help 2>/dev/null)" || return 1
       grep -Eq '^[[:space:]]+connector[[:space:]]' <<<"$help"
     }

     if [ -f "$connector_home/pairing.json" ]; then
       if pan_has_connector; then
         exec pan mcp connector serve --stdio
       fi
       if command -v npx >/dev/null 2>&1; then
         exec npx -y "@overdeck/core@${OVERDECK_CORE_VERSION}" mcp connector serve --stdio
       fi
       echo "overdeck: a connector is paired in $connector_home, but neither pan nor npx is on PATH. Install Node 22.16 or later." >&2
       exit 1
     fi

     if command -v pan >/dev/null 2>&1; then
       default_token_file="$HOME/.overdeck/grok-build-mcp-token"
       if [ -z "${OVERDECK_MCP_TOKEN:-}" ] && [ -z "${OVERDECK_MCP_TOKEN_FILE:-}" ] && [ -f "$default_token_file" ]; then
         export OVERDECK_MCP_TOKEN_FILE="$default_token_file"
       fi
       exec pan mcp serve
     fi

     echo "Install Overdeck (npm i -g @overdeck/core) or pair a connector" >&2
     exit 1
     ```
