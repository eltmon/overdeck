# PAN-5611: Idle-settled conversations stay in Settled after the operator resumes them

**Issue:** [PAN-5611](https://github.com/eltmon/overdeck/issues/5611)
**Builds on:** PAN-4639 (settle and snooze), PAN-4655 (idle auto-settle), PAN-4657 (schedule runs clear triage).

## Summary

The idle sweep settles a conversation (reason `idle`) after `conversations.auto_settle_idle_days` days with no activity. Nothing clears that settle when activity resumes, so a conversation the operator is chatting with stays in the Command Deck's Settled section and its project group never appears. This change ends an `idle` settle in two ways:

1. **Instant path (FR-1):** an accepted message through `POST /api/conversations/:name/message` clears the `idle` settle on the messaged conversation and on its display root.
2. **Sweep path (FR-2):** each idle-settle sweep also clears an `idle` settle when a member of the group has transcript activity newer than the root's `settled_at`. This covers work typed directly into the terminal pane.

Settles with reason `manual` or `merge` are never cleared automatically (FR-3).

## Glossary

- **Settle / settled:** `conversations.settled_at` (epoch ms) is non-null. Display-only: the session keeps running. The frontend puts the conversation in the Settled section.
- **Settle reason:** `conversations.settle_reason`, one of `manual`, `merge`, `idle` (`SETTLE_REASONS`, `src/lib/overdeck/conversation-triage-store.ts`, line 4). A settled row whose stored reason is NULL or unknown reads as `manual` (`rowToTriage`, same file, line 51).
- **Idle settle:** a settle with reason `idle`, written only by the idle sweep through `settleIdleConversation` (same file, line 146).
- **Idle clock / idle reset:** `conversations.idle_reset_at` (epoch ms). Unsettle and unsnooze write it. The sweep never idle-settles a conversation whose `idle_reset_at` is newer than the cutoff (PAN-4655 D3).
- **Resurface:** clear an idle settle (set `settled_at`, `settle_reason`, `snoozed_until` to NULL) and write `idle_reset_at = now`, so the conversation returns to Inbox and the idle clock restarts.
- **Display root / group:** the Command Deck nests a conversation under its "display parent" (D27 rule): the conversation it critiques (`criticOfConversationId`) when that row is listed, else its `parentConversationId` when that row is listed. Lanes, critics, and handoff/fork successors are display children of the original conversation (a non-fresh fork or handoff is created with `parentName: conv.name`, `src/lib/overdeck/conversation-forks.ts`, line 881). A `/clear` successor nests the same way whenever it carries a parent link. The section (Needs you / Inbox / Snoozed / Settled) is decided on the root only (`sectionOf`, `src/dashboard/frontend/src/components/CommandDeck/conversation-triage.ts`, line 41). The idle sweep settles only roots.
- **Operator list:** the rows `listConversations()` returns (`src/lib/overdeck/conversations.ts`, line 553): unarchived, not `agent-%`/`planning-%`/`specialist-%`, not `origin = 'vault'`. A parent outside this list does not count as a display parent.
- **Delivery receipt:** `withConversationMessageReceipt` (`src/dashboard/server/services/conversation-message-receipts.ts`, line 172) coalesces HTTP retries that carry the same `clientMessageId`. A retry returns the stored response without calling the delivery callback again.
- **List enrichment cache:** the server cache behind `GET /api/conversations`; `invalidateConversationListEnrichmentCache()` (`src/lib/overdeck/conversation-list.ts`) drops it.
- **`conversation.schedules_changed`:** an in-memory domain event emitted by `emitConversationSchedulesChanged(name)` (`src/lib/overdeck/conversation-schedules.ts`, line 373). Its reducer bumps `conversationsListRevision` (`packages/contracts/src/event-reducers.ts`, line 1539), and `ConversationList.tsx` (line 523) refetches the list when the revision changes. The schedule service already uses it after it clears triage (PAN-4657).

## Root cause (verified against the code at 99283e4c86f)

Only two paths clear a settle today:

1. `unsettleConversation` (`conversation-triage-store.ts`, line 93), reached through `applyTriageUpdate` from `POST /api/conversations/triage`.
2. `clearConversationTriage` (`conversation-triage-store.ts`, line 116), called by the schedule sweep after a delivered fire (`src/dashboard/server/services/conversation-schedule-service.ts`, line 87 and line 165).

The message route (`src/dashboard/server/routes/conversations.ts`, line 612, `postConversationMessageRoute`) and the idle sweep (`src/lib/overdeck/conversation-idle-settle.ts`, `sweepIdleConversations`, line 125) clear nothing. The sweep's candidate filter drops settled roots (`isCandidateGroup`, line 113: `if (!clock || clock.settledAtMs !== null) return false;`).

PAN-4639 D8 ("New activity never changes stored state") and the PAN-4655 non-goal ("new activity never unsettles") made this deliberate. **This issue reverses that rule for settle reason `idle` only.** `manual` and `merge` settles keep the old rule. Do not edit the PAN-4639 or PAN-4655 drafts; this PRD supersedes them on this point.

## Requirements

### Functional

- **FR-1** When `POST /api/conversations/:name/message` returns a 2xx response from a real delivery (not a receipt replay), clear an `idle` settle on the messaged conversation and on its display root (if different), restart their idle clocks, invalidate the list enrichment cache, and emit `conversation.schedules_changed` for each conversation that changed.
- **FR-2** Each idle-settle sweep clears the `idle` settle on a display root when (a) at least one group member's terminal session is live, and (b) some group member's transcript activity (`readTranscriptLastActivityMs(path, settledAtMs)`) is strictly newer than the root's `settled_at`. The write is guarded so that a settle written after the sweep read the row wins.
- **FR-3** Settles with reason `manual` or `merge`, and settled rows whose stored reason is NULL or unknown, are never cleared by FR-1 or FR-2.
- **FR-4** The FR-2 pass runs even when `conversations.auto_settle_idle_days` is `0` and when the settle pass has no candidates.
- **FR-5** A failure while resurfacing (a thrown error from the store or the emitter) never changes the message route's response; it is logged with `console.warn`.
- **FR-6** After a sweep resurfaces at least one conversation, the idle-settle service invalidates the list enrichment cache, emits `conversation.schedules_changed` for each resurfaced name, and logs one line naming them.

### Non-functional

- **NFR-1** No schema migration. `settle_reason` and `idle_reset_at` already exist.
- **NFR-2** No new event type and no frontend change. The existing `conversation.schedules_changed` event and the 10 s list poll refresh the Command Deck.
- **NFR-3** `src/dashboard/server/routes/conversations.ts` (1039 lines; allowlist cap 1072, `scripts/file-size-allowlist.txt` line 117) grows by at most 5 lines. The FR-1 logic lives in a new module.
- **NFR-4** The FR-2 pass reads transcripts only for idle-settled groups with a live member, and `readTranscriptLastActivityMs` stats a file before it reads any bytes, so a quiet settled conversation costs one stat per sweep.
- **NFR-5** Tests that involve timers use `vi.useFakeTimers()` (the service tests already do).

## Decisions

- **D1 — FR-1 target is the display root as well as the messaged row.** Handoff and fork successors are display children of the original conversation (`conversation-forks.ts`, line 881, sets `parentName`; `displayParentId`, `src/dashboard/frontend/src/components/CommandDeck/conversation-tree.ts`, line 68, falls back to `parentConversationId`). The sweep settles only that original root. Clearing only the messaged row would leave the group in Settled in the most common case: the operator working in a successor. FR-1 therefore clears the messaged row and its display root, computed with the sweep's own rule (`groupByDisplayRoot`'s root walk) over `listConversations()`.
- **D2 — Hook placement: inside the receipt's delivery callback.** The route wraps `handleConversationMessage` in an async callback that awaits the response, calls the resurface helper when `response.status` is 2xx, then returns the response. A receipt replay never calls the callback, so it never resurfaces again.
- **D3 — Any 2xx counts, including `/pan` composer commands and native compact.** The operator typed into the conversation's composer; that is use of the conversation. Non-2xx responses (409 cancelled, 409 permission-pending, 502 not-delivered, 503, 504 delivery unknown) do not resurface; FR-2 catches a delivery that did land.
- **D4 — Guarded store door, not `clearConversationTriage`.** `clearConversationTriage` is unconditional and would clear `manual` and `merge` settles. A new function `resurfaceIdleSettledConversation(name, nowMs, settledAtMs?)` runs one `UPDATE … WHERE name = ? AND settled_at IS NOT NULL AND settle_reason = 'idle'` and, when `settledAtMs` is given, `AND settled_at = ?`. FR-1 calls it without `settledAtMs`; FR-2 passes the value it read.
- **D5 — Event reuse.** Emit `conversation.schedules_changed`, as the schedule service does after it clears triage (the issue prescribes this). Adding a dedicated triage event is out of scope.
- **D6 — FR-2 keeps the existing activity helper.** `readTranscriptLastActivityMs(path, settledAtMs)` returns the modified time when it is at or before `settledAtMs` (cheap, no read), else the last Claude-format user/assistant record time in the 512 KB tail, else the modified time. `turnRecordTimestamp` (`src/lib/agent-enrichment.ts`, line 524) parses only Claude-format records, so for pi, codex, kimi and other harnesses the activity is the modified time. Accepted assumption (not verified per harness): those transcripts change only when a record is written, so the modified time approximates the last write. A false resurface costs one row in Inbox until the next idle settle. Claude Code's touch-without-record quirk (PAN-4515) is handled by the record-time branch.
- **D7 — FR-2 requires a live member.** Work typed into a pane needs a live terminal session, and the live check bounds the steady-state cost (NFR-4). When the backend cannot list sessions (`listLiveSessions` returns null) the pass resurfaces nothing that tick and logs one line.
- **D8 — FR-2 runs before the settle pass in the same tick.** A resurfaced row gets `idle_reset_at = now`, so the settle pass (and `settleIdleConversation`'s guard) cannot re-settle it in the same tick or for the next N days.
- **D9 — Resumes count as activity.** PAN-4655 defines a resume as activity. A resume (the Resume button, or "Resume all" after a backend restart) sends a resume contract and the harness takes a turn, which writes transcript records, so FR-2 resurfaces live idle-settled conversations that were resumed. This is accepted: the operator chose to resume them. The Resume route itself is not changed.
- **D10 — Automated deliveries resurface through FR-2 only.** PR-watch notifications, trigger hooks, scheduled messages and agent `send_message`/`pan tell` deliveries that do not use the message route produce transcript activity, which FR-2 sees within one sweep (about 15 minutes). Agent deliveries that do use the message route resurface instantly through FR-1. Both match PAN-4655's definition of activity.
- **D11 — Re-settling an idle-settled row keeps reason `idle`.** `settleConversation` (line 79) keeps the existing reason when the row is already settled, so a merge or bulk manual settle over an idle settle stays `idle` and stays resurfaceable. Changing that is out of scope.
- **D12 — The service's sweep seam changes shape.** `IdleSettlePatrolDeps.sweep` returns `{ settled: string[]; resurfaced: string[] }` instead of `string[]`. The existing settle log line stays byte-identical.

## Work items

### WI-1 — Store door `resurfaceIdleSettledConversation` (FR-3, D4)

Files: `src/lib/overdeck/conversation-triage-store.ts`, `src/lib/overdeck/__tests__/conversation-triage-store.test.ts`.

Add after `clearConversationTriage` (line 121):

```ts
/**
 * PAN-5611: ends an 'idle' settle (and any snooze) and restarts the idle clock.
 * Manual, merge and unknown-reason settles stay. With settledAtMs, clears only
 * that exact settle, so a settle written after the caller read the row wins.
 */
export function resurfaceIdleSettledConversation(name: string, nowMs: number = Date.now(), settledAtMs?: number): boolean {
  const guard = settledAtMs === undefined ? '' : ' AND settled_at = ?';
  const params = settledAtMs === undefined ? [nowMs, name] : [nowMs, name, settledAtMs];
  const result = getOverdeckDatabase()
    .prepare(
      `UPDATE conversations
       SET settled_at = NULL, settle_reason = NULL, snoozed_until = NULL, idle_reset_at = ?
       WHERE name = ? AND settled_at IS NOT NULL AND settle_reason = 'idle'${guard}`,
    )
    .run(...params);
  return result.changes > 0;
}
```

Tests (append to the existing file, same temp-`OVERDECK_HOME` pattern and its `create`/`setColumn` helpers):
- `resurfaceIdleSettledConversation clears an idle settle and restarts the idle clock`: `settleIdleConversation('r-a', cutoff, 1_000)`; `resurfaceIdleSettledConversation('r-a', 9_000)` returns true; `getConversationTriage('r-a')` equals `EMPTY_CONVERSATION_TRIAGE`; `idle_reset_at` reads 9000.
- `resurfaceIdleSettledConversation leaves manual and merge settles`: `settleConversation('r-b', 'manual', 1_000)` and `settleConversation('r-c', 'merge', 1_000)`; both calls return false; reasons still `manual` and `merge`; `idle_reset_at` still NULL.
- `resurfaceIdleSettledConversation leaves a settled row with a NULL reason`: set `settled_at = 1000`, `settle_reason = NULL` directly; returns false.
- `resurfaceIdleSettledConversation with settledAtMs leaves a different settle`: idle-settled at 1000; call with `settledAtMs = 2_000` returns false and the row stays settled; call with `1_000` returns true.
- returns false for an unsettled row and for a missing name.

## Non-goals

- Resurfacing `manual` or `merge` settles, or settled rows with a NULL/unknown reason.
- Unsnoozing a snoozed conversation when it receives a message or activity.
- Changing the Resume route, the triage route, or the schedule service's unconditional `clearConversationTriage`.
- Treating opening or reading a conversation (`last_attached_at`) as activity for resurfacing.
- A new domain event type, a schema migration, or any frontend change.
- Changing `settleConversation` so that a re-settle over an idle settle replaces the reason.
- Resurfacing from inside `handleConversationMessage` for its other callers (PR-watch notifier, trigger hooks, shared-session submit queue, scheduled-message delivery); FR-2 covers them.
