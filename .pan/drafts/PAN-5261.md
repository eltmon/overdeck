# PAN-5261: GitHub GraphQL still at ~47%/hour after PAN-5224 — cut per-event cost, not the poll tier

**Issue:** [PAN-5261](https://github.com/eltmon/overdeck/issues/5261)
**Planned:** 2026-11-14, auto mode, against `main` at `0a6481e7e93`. The live dashboard (pid 1100460) runs `aa7e22e15de` (PAN-5224), started 07:06:56 UTC.
**Siblings filed during planning:** [PAN-5263](https://github.com/eltmon/overdeck/issues/5263) (the GitHub App has no `issues` permission, so membership sees zero open `eltmon/overdeck` issues) and [PAN-5264](https://github.com/eltmon/overdeck/issues/5264) (attribute the `app-rest` App-pool caller).

## Glossary

- **Pool / bucket** — GitHub's hourly allowance per credential *pool* (`user` = the operator's `gh` OAuth token, `app` = the GitHub App installation token, `pat` = the tracker PAT) and *bucket* (`graphql` points, `rest` calls; 5,000 each per hour). The ledger `~/.overdeck/github-quota/ledger-<YYYYMMDDHH>.jsonl` records every metered call (`src/lib/github-quota/ledger.ts`).
- **Caller** — the name a metered call is billed to (`runGh(..., { caller })`, `withGitHubCaller`). This issue targets `pr-cache` and `pipeline-membership`.
- **Open read / closed read** — the two `gh pr list` calls behind the PR listing cache in `src/lib/overdeck/pr-listing.ts` (`loadOpenPullRequests`, `loadClosedPullRequests`), keyed by project path, caller `pr-cache`.
- **Coalescer fire** — one run of `fire()` in `src/dashboard/server/services/pr-webhook-freshness.ts` (PAN-5224): it invalidates a repo's PR listing (open and closed) and membership PR snapshot and schedules a derived-state refresh for the named issues. It logs `[pr-webhook] <repo>: refreshed (<reasons>, <n> issue(s))`.
- **Membership gather** — `gatherProjectLensSignals(project)` in `src/lib/pipeline-membership-gather.ts`: one project's open issues, phase-labelled issues, open PRs, branch refs, specs, then GraphQL issue states (`listIssueStatesBatched`, 50 aliases per call) and merged heads (`listMergedPullRequestHeadsBatched`, 50 aliases per call).
- **Issue-state lookup** — the `listIssueStates` step of a gather: for every candidate that has a branch or open PR but is absent from the open-issue listing, ask GraphQL whether the issue is OPEN, CLOSED or not an issue (a null alias, e.g. a PR number).
- **Raw tracker rows** — the tracker issues as polled, before derived-state projection: `IssueDataService.getCachedTrackerIssues()` (`src/dashboard/server/services/issue-data-service.ts` line 911). `getIssues()` is the *projected* view, which replaces `state` with `verifying_on_main` for a merged-but-open issue (same file, lines 499–518).
- **Issue branch** — a branch that names an issue: `/(?:feature|strike|bypass)\/[a-z]+-\d+$/i` (`issueIdFromBranch`, `src/lib/webhook-handlers.ts` line 106).
- **Dry-run cost** — the GraphQL point cost GitHub reports for a query under `rateLimit(dryRun: true) { cost }`, which does not spend quota.

### Hypotheses from the issue, verified

1. **"Webhook health reads unhealthy, so the 30 s fallback stays on" — false.** `GET /api/system/health` at 07:56:37 returned `state: healthy` with the `smee-relay` row `status: running` on a sample 2 s old, which satisfies `isWebhookRelayRunningInLastSample` (`src/dashboard/server/services/system-health-service.ts` line 884). The ledger agrees: outside webhook-driven re-reads, open reads run at about 1.0–1.4/min, the healthy-tier rate (3 repos with open PRs every 5 min, 6 empty repos every 15 min). Under the unhealthy tier, `stablyai/orca`, `eltmon/lexerra` and `eltmon/overdeck` alone would be 6/min. So the issue's requirement 2 (show a webhook-delay indicator) is conditional on this cause and **is not triggered** (D-7).
2. **"Readers bypass the TTL" — partly true, through invalidation, not TTL bypass.** Open and closed reads come in pairs at about 5/min each. A closed read's TTL is 15 min across 9 repos (0.6/min), so the pairs come from invalidations: 209 coalescer fires in 55 min (3.8/min), each invalidating the open and the closed read of `eltmon/overdeck` (`fire()`, `pr-webhook-freshness.ts` lines 47–90; `invalidateRepoPullRequests`, `pr-listing.ts` line 256). Of the 209 fires, 42 (20%) named no issue and no PR (CI runs on `main`), so they could not change any PR row.
3. **"`pipeline-membership` was never moved to webhook-driven reads" — false framing; the cost is per gather.** Gathers *are* event-driven since PAN-5224. Each `eltmon/overdeck` gather costs 11 GraphQL calls plus 6 App REST calls, and about 5 gathers follow each merge: the `pull_request:closed` webhook, `merge.completed`, the telemetry stage gather (below), and one or two tracker-diff triggers. The ledger shows bursts at 07:26:02, 07:26:17, 07:26:31 (two at once) after the 07:26:00 merge of #5256.

### Root causes (verified)

- **RC-1 — The open read asks for 100 rows.** `loadOpenPullRequests` runs `gh pr list --state open --limit 100` (`pr-listing.ts` line 175). Dry-run cost of that exact field set: **3** points at `first: 100`, 2 at 50, **1** at 30. Only `stablyai/orca` has more than 30 open PRs (100); `eltmon/overdeck` has 4, `eltmon/lexerra` 2, the other 6 repos 0. The estimator `priceGhListCall` (`src/lib/github-quota/gh-cost.ts`) already prices `--limit 30` at 1 point, so the ledger will show the saving.
- **RC-2 — Status-only webhooks invalidate the closed read and the membership snapshot.** A review, check or status event can change only an open PR's `reviewDecision` / `statusCheckRollup`, yet `fire()` always calls `invalidateRepoPullRequests` (both reads) and `invalidateOpenPullRequestsSnapshot`.
- **RC-3 — Fires that cannot change a PR row.** `handleCheckRun` fires on every `created` and failing `completed`, even with no PR and a non-issue branch (`webhook-handlers.ts`, the block starting `const coalescerTrigger = payload.action === 'created'`, around line 270). `handleStatus` fires whenever `branches` is non-empty, even when no branch is an issue branch (around line 518).
- **RC-4 — The issue-state lookup re-asks the same numbers every gather.** For `eltmon/overdeck` the App's open-issue listing returns 0 rows (the App has no `issues` permission; filed as [PAN-5263](https://github.com/eltmon/overdeck/issues/5263)). So all ~492 branch and spec candidates go to `listIssueStatesBatched`: 10 calls per gather (`pipeline-membership-gather.ts` line 708). Measured with a probe gather that stubbed GraphQL: 492 issue-state numbers, 10 chunks.
- **RC-5 — The tracker trigger diffs projected state.** `read-model.ts` lines 673 and 682 seed and diff `issueService.getIssues({ cycle: 'all' })`, the projected view. When a derived refresh flips a merged-but-open issue to `verifying_on_main`, `pushSnapshot()` (`issue-data-service.ts` line 785) re-runs the trigger, and the projected `state` change reads as a tracker change, so it costs an extra full gather. The reverse case (a real tracker change hidden under `verifying_on_main`) is missed. This is the PAN-5224 round-2 critique finding "Tracker diff reads projected state" (`.pan/drafts/PAN-5224-critique-2.md`), left unresolved.
- **RC-6 — `stablyai/orca` can be pinned at 30 s.** `prListingTtlMs` (`src/lib/overdeck/pr-cache-policy.ts` line 66) keeps the 30 s TTL whenever any OPEN row has `mergeable: UNKNOWN`. `orca` is an upstream fork with 100 open PRs (24 CONFLICTING, 76 MERGEABLE at 08:05). GitHub recomputes mergeability lazily after upstream pushes, so UNKNOWN rows recur, and none of them is an Overdeck issue branch that a merge gate reads.

## Requirements

### Functional

- **FR-1** — The open read lists at most 30 rows (`--limit 30`) unless the repo's last successful open read returned 30 or more rows. A read at 30 that returns 30 rows is re-run at `--limit 100` inside the same load before it settles, so a settled open listing never holds fewer rows than today's `--limit 100` read would. A repo whose read at 100 returns fewer than 30 rows goes back to 30 on its next load.
- **FR-2** — An OPEN row with `mergeable: UNKNOWN` keeps the 30 s TTL only when its `headRefName` is an issue branch. Other UNKNOWN rows follow the normal health-dependent TTL.
- **FR-3** — Each coalescer event carries a change kind. `pr-state` (any `pull_request` action) invalidates the repo's open read, closed read and membership PR snapshot, as today. `pr-status` (`pull_request_review`, `check_suite`, `check_run`, `status`) invalidates only the open read, in flight or settled. A fire acts as `pr-state` when any event merged into *that* fire was `pr-state`; the kind resets with each window, so a later status-only fire invalidates only the open read.
- **FR-4** — A `check_run` event reaches the coalescer only when `run.pull_requests` is non-empty or `run.check_suite.head_branch` is an issue branch. A `status` event reaches it only when at least one of `branches[].name` is an issue branch. The `check_suite` rule is unchanged (it already requires a listed PR or an issue branch). Every qualifying event still reaches the coalescer; its 6 s spacing is the only merging.
- **FR-5** — *Retired (critique round 1).* It deduplicated `check_run` `created` per head SHA, which hid later distinct checks (e.g. a `needs:` job created minutes after the first) from `summarizeTestChecks` and `readySinceFromRollup`.
- **FR-6** — The tracker-change membership trigger seeds and diffs the raw tracker rows (`getCachedTrackerIssues()`), never the projected `getIssues()` view. A derived-state refresh alone never enqueues `tracker:issues-changed`.
- **FR-7** — In a process that enabled it, the gather reuses an issue-state answer (OPEN, CLOSED, or not-an-issue) for the same repo and number for up to 30 minutes. Only numbers without a fresh answer go to GraphQL. An answer whose lookup started before an invalidation of that number is never stored. With the cache not enabled (the default: CLI, deacon, tests), every gather asks GraphQL as today.
- **FR-8** — The dashboard enables the issue-state cache where it installs the tracker-change trigger, and the trigger drops the cached answer for every changed identifier (state or labels changed, new, or gone) before it enqueues the refresh.

### Non-functional

- **NFR-1** — Over a full 60-minute ledger window with no dashboard reload: (a) in an idle hour (no running agents and no merges), total user-pool GraphQL is under 750 points (15%); (b) in a busy hour, user-pool GraphQL from every caller except `agent` is under 750 points, and the total including `agent` is reported. User-pool REST is under 750 calls (15%) in both. The PR records the window's running-agent count, merge count and coalescer-fire count beside the numbers. The App and PAT pools are reported beside it, not targeted (D-3).
- **NFR-2** — While webhooks are healthy, a PR, review or check change on `eltmon/overdeck` still reaches derived issue state within the PAN-5224 bound (coalescer ≤ 6 s + one open read). No change in this issue delays the first event that changes a PR row.
- **NFR-3** — No new GitHub caller, health signal, config key or persisted state. All new state is process memory.
- **NFR-4** — Every TTL, cache-age and coalescer test uses `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()` (repo rule `fake-timers-for-retry-tests`); no real waits.
- **NFR-5** — No file grows past its line ceiling (`scripts/lint-file-size.sh`, origin/main count or allowlist cap). `src/dashboard/server/services/issue-data-service.ts` is at its 1,754-line cap: WI-5 changes one keyword there and adds no line.
- **NFR-6** — No sync exec in server-reachable code (`no-execsync-server`).

## Decisions (made here; do not re-decide)

- **D-1 — Cut per-event cost, keep the PAN-5224 tiers.** The TTL tiers already run at the healthy rate. Lengthening them saves little and widens the lag on repos without webhooks.
- **D-2 — `--limit 30` with a full re-read, not a smaller fixed limit.** 30 is the largest limit that dry-runs at 1 point (50 costs 2). The re-read at 100 keeps the auto-merge scheduler, the batch door and `lastOpenNumbers` shrink detection on a complete open set.
- **D-3 — NFR-1 binds the user pool,** as PAN-5224 D-3 did. The issue's "under 15%" refers back to PAN-5224's user-pool target, and the issue's own sample is the user pool's `gh api rate_limit`. The App pool (50.5%) is split into `close-out` ([PAN-5227](https://github.com/eltmon/overdeck/issues/5227)) and the untraced `app-rest` ([PAN-5264](https://github.com/eltmon/overdeck/issues/5264)).
- **D-4 — The App's missing `issues` permission is a sibling issue.** Fixing it changes membership semantics, and it would *raise* the gather cost (about 881 open issues → ~36 merged-head chunks per gather). [PAN-5263](https://github.com/eltmon/overdeck/issues/5263) carries that cost warning. This issue keeps the listing as it is.
- **D-5 — The issue-state cache is opt-in per process.** Only a process that diffs tracker rows can drop stale entries. The dashboard enables it next to `seedTrackerIssues`. The 30-minute age bound covers a tracker poll that fails or misses a change.
- **D-6 — No per-SHA deduplication of check events (critique round 1).** Each `created` check run adds a distinct pending row that `summarizeTestChecks` (`src/lib/cloister/pr-facts.ts`) and `readySinceFromRollup` (`src/lib/cloister/batch-window.ts`) read, so suppressing it would break NFR-2. The 6 s coalescer stays the only merging. A successful `completed` still does not fire (PAN-5224 D-8).
- **D-7 — No webhook-delay indicator.** The issue's requirement 2 applies "if webhook health is the cause". It is not, so no dashboard UI is added (recorded as a NonGoal).
- **D-8 — Telemetry gathers stay.** `readCanonicalPipelineMembership` (`src/lib/telemetry/pipeline.ts`) runs an uncached full gather per pipeline stage. In the dashboard process it shares the WI-6 cache, so its cost falls with every other gather.
- **D-9 — The issue's "healthy webhooks keep `pr-cache` on the slow fallback" test already exists:** `tests/unit/lib/overdeck/pr-listing-webhook-ttl.test.ts`, "healthy provider with an OPEN row: cached 5 min, re-reads just past it (ac1)". This issue runs it as an acceptance criterion and adds tests only for what it changes.
- **D-10 — Before/after measurement.** The work agent cannot deploy (deploys are the Flywheel's `pan reload`). The PR body carries the before table above, the budget model and an unchecked "After (post-deploy)" box with the recipe in WI-7. The after numbers are posted as a PR comment after the reload.

const issueStateGeneration = new Map<string, number>();

function issueStateKey(owner: string, repo: string, number: number): string {

Accepted.
