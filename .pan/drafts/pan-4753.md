## 0. Glossary

Read this first. Every later section uses these terms exactly as defined here.

| Term | Meaning |
| --- | --- |
| **Train** | One project's merge pipeline: everything that turns ready PRs into commits on `main`. Turned on and off by the **train flag**. |
| **Train flag (global)** | `merge_train.enabled` in `app_settings`, falling back to `flywheel.merge_train_enabled`. Read by `isMergeTrainEnabled()` (`src/lib/overdeck/merge-sync.ts:56`). After WI-2 it is the **master switch**: off means no train runs in any project. |
| **Train flag (project)** | `merge_train: enabled \| disabled` in `projects.yaml`. Read by `isMergeTrainEnabledForProject()` (`merge-sync.ts:75`). After WI-2, `disabled` turns this project's train off; `enabled` and absent both mean "on while the master switch is on". |
| **Hold project** | A project whose project-level policy holds merges for UAT: `projectHoldsForUat(config, globalRequireUat)` is true (`src/lib/cloister/auto-merge-policy.ts:36`). Its `auto_merge_default` is `hold`, or it has none and the global `require_uat_before_merge` is true. Mind Your Now is the live example. Shown in the UI with the mode chip **Holds for UAT**. |
| **Auto project** | Any project that is not a hold project. Shown with the mode chip **Auto-merge**. Overdeck (`panopticon-cli`) is the live example. |
| **Issue policy** | The per-issue override carried by tracker labels: `auto-merge` means Auto, `hold-for-uat` means Hold, neither means "follow the project" (`autoMergeFromLabels`, `src/lib/cloister/auto-merge-eligibility.ts:53`). |
| **Merge route** | Where a ready PR goes, decided by `mergeRouteFor` (new in WI-2): `auto-merge` (the scheduler merges it alone after a cooldown) or `batch` (it waits for a UAT batch). |
| **Car** | One issue on a train: an open PR that review approved at some head, or an issue with a live auto-merge row or merge run. One row in the queue list. |
| **Ready set** | The cars whose PR is approved, has green checks, and is mergeable (`listReadyIssuesForProject`, `src/lib/overdeck/derived-issue-state.ts:850`). Batches are assembled from it. |
| **Batch** (= **generation**) | A `uat/<label>-<codename>-<MMDD>-<n>` branch that merges several ready features onto `main` for joint UAT. Stored in `uat_generations` (`UatGeneration`, `src/lib/overdeck/merge-types.ts:130`). |
| **Live batch** | A batch with status `assembling`, `ready` or `superseded`. `ready` and `superseded` batches can be promoted (`PROMOTABLE`, `src/lib/cloister/uat-promote.ts:153`). |
| **Hero batch** | In a hold project's card, the newest live batch that is not `superseded`. Shown as the large card at the top. |
| **Superseded** | A batch whose base moved or whose input set changed, so a newer batch replaced it. Still testable and still promotable. |
| **Invalidated** (= **voided**) | A batch whose content can no longer be trusted: a member left the ready set or a member's branch gained commits (`isStale`, `src/lib/cloister/uat-reconciler.ts:195`). Cannot be promoted. Before this epic the UI hid these; after WI-3 and WI-10 it shows them, with a stored reason. |
| **Status reason** | New column `uat_generations.status_reason` (WI-3): one sentence saying why a batch became `superseded` or `invalidated`. |
| **Promote** | Merge a batch's branch to `main` ("Merge batch (N) to main"). `POST /api/merge-train/generations/:name/promote`. |
| **Cooldown** | The wait between scheduling an auto-merge and the executor merging it: `AUTO_MERGE_COOLDOWN_MS = 300_000` (`src/lib/cloister/auto-merge-config.ts:1`). Cancel works during it. Strikes have no cooldown. |
| **Scheduler** | `scheduleReadyAutoMerges` (`src/dashboard/server/services/auto-merge-scheduler.ts:195`). Runs on the 60 s UAT-train tick and writes `pending_auto_merges` rows. Never merges. |
| **Executor** | `tickAutoMergeExecutor` (`src/dashboard/server/services/auto-merge-executor.ts:161`). Runs every 30 s and merges due `pending` rows through `triggerMerge`. |
| **Merge gate** | `evaluateIssueMergeGate` (`src/lib/cloister/merge-gate.ts:109`). The single readiness check every merge door asks. |
| **Head approval** | Proof that a review approved the PR's exact head commit: a GitHub review whose `commit.oid` is the head (`forgeApprovalAtHead`, `src/lib/cloister/pr-facts.ts:826`) or a trusted verdict marker `<!-- overdeck-verdict: APPROVED sha=<head> -->` (`pr-facts.ts:190-194`, `:416-427`). Required by `requireApprovalAtHead: true`. |
| **Strike PR** | A PR on branch `strike/<issue-lower>` opened by a strike agent from workspace `<project>/workspaces/feature-<issue-lower>-strike` (PAN-3973). Authored with the operator's credentials, so the operator cannot approve it on GitHub. Has no xBRIEF. |
| **Strike lane** | The per-project list of open strike PRs in the train UI. Rendered above the queue: strikes go to the front of the train. |
| **Expedited review** | One quick-mode review (`roles.review.mode: quick`, a single reviewer, no convoy) of a strike PR at its current head, dispatched automatically (WI-5). Its APPROVED verdict is a GitHub APPROVE review by the GitHub App bot (`overdeck-agent[bot]`), which is a head approval. |
| **Flagged** | A strike PR whose expedited review returned CHANGES_REQUESTED. It stops; the lane shows the reviewer's summary. |
| **Operator-started strike merge** | A strike merge the operator clicked (WI-1). The only merge that does not require a head approval. |
| **Merge run** | The in-memory progress of one merge this process is executing: phase plus one of nine steps (`MergeRun`, `src/dashboard/server/services/merge-queue-service.ts:28-36`). Served by `GET /api/merge-queue` (`merge-ops.ts:1726-1740`). Dies with the process. |
| **Step tracker** | The 9-step `MergeStepTracker` UI restored from `AwaitingMergePage.tsx@a9d0942c1ed` lines 240-295. |
| **Pipeline journal** | `<workspace>/.overdeck/pipeline.jsonl`, append-only (`src/lib/cloister/pipeline-journal.ts`). Written at the moment of an action, never authority over the PR. |
| **Recent merges strip** | One line per project card: "Last merged: X · 22m ago · show 5". Lists the last five merges and how each landed, including merges made outside the train. |
| **Outside-train merge** | A PR merged on the forge directly (GitHub or GitLab UI, `gh pr merge`), not through any Overdeck merge door. Noted in the recent merges strip; never refused or reverted. |
| **Board** | The new aggregate read `GET /api/merge-train/board` (WI-7): everything one `MergeTrain` component renders, per project. |
| **TENET-10** | The rule in `sync-sources/skills/pan-flywheel/SKILL.md:326-330`: changes to the deacon, the flywheel loop, conversation live-control, the merge or review routes, or the agents runtime are never auto-started; they are marked `needs-handoff` and go through a supervised `pan handoff`. |

## 1. Problem

After The Cut (PAN-3917, merge `ca15def4bb7`, parent `a9d0942c1ed`) the merge train came back in a form the operator cannot see or steer:

1. **The scheduler voids every batch in auto projects.** The UAT reconciler assembles a batch from any 2+ ready features (`uat-reconciler.ts:295`), and the auto-merge scheduler, running on the same 60 s tick (`src/dashboard/server/main.ts:523-528`), merges members one at a time. Each merged member "left the ready queue", so `isStale` invalidates the batch (`uat-reconciler.ts:195-208`, `:241-255`). On 2026-11-01 26 `uat/pan-onyx-1101-*` batches were assembled and all 26 invalidated.
2. **Voided batches are hidden.** `visibleGenerationsOf` (`src/dashboard/frontend/src/components/merge-train/MergeTrainView.tsx:189-196`) drops `invalidated`, and nothing stores why a batch was voided.
3. **Nothing decides batch versus auto-merge.** A hold project's `auto-merge`-labelled feature is scheduled alone (`autoMergePolicyRefusal`, `src/dashboard/server/routes/merge-train.ts:588-605`, reads only the issue's own tiers), which voids its live batch.
4. **The polyrepo queue is empty (PAN-3657).** `queueEntryForProject` and `defaultOrderedIssueIdsForProject` call the monorepo builder `computeMergeQueueFromCandidates` (`merge-train.ts:132`, `:200`), which runs git at the project root. A polyrepo root is not the repo. The ready set itself reads only `gh pr list` (`derived-issue-state.ts:367-395`), so a GitLab polyrepo project (Mind Your Now) never has candidates.
5. **No strike PR can merge through Overdeck (PAN-4750).** `POST /api/issues/:issueId/merge` always calls `triggerMerge(issueId)` with `kind: 'normal'` (`src/dashboard/server/routes/workspaces/merge-ops.ts:1209`), which gates on `feature/<id>`. The `kind: 'strike'` path in `triggerMerge` (`merge-ops.ts:267-275`) has no caller: its internal route was deleted in `31cbe84577c` (#3987). Even with a caller, `evaluateIssueMergeGate` hardcodes `requireApprovalAtHead: true` (`merge-gate.ts:136`), and a strike PR authored by `eltmon` can never be approved by `eltmon`. Strikes are also excluded from the scheduler by the branch regex (`auto-merge-scheduler.ts:87-90`). Five green, mergeable strike PRs are stuck: #4698, #4701, #4707, #4678, #4679.
6. **Restored UI pieces are gone:** the 9-step tracker, "Last merge failed" with Retry, "ready N ago", reviewer UAT notes, four of six blocker types (only `failing_checks` and `merge_conflict` render, `AwaitingMergePage.tsx:455-473`), the editable per-issue Auto/Hold toggle (`AutoMergeToggle.tsx` is read-only, lines 10-11), and any train view on the project page.
7. **Merges outside the train are invisible.** PR #4749 (PAN-4296) was merged on GitHub at 23:52:42Z, four minutes before its cooldown ended; the auto-merge row then ended `blocked: PR is already merged`. Rows 269-279 on 2026-11-01 all ended that way.

## 2. Operator decisions (2026-11-02, from the issue body; binding)

- **D1 Strikes.** Strike PRs go to the front of the train with no cooldown. Each gets an expedited single-reviewer bot review. If it approves and checks are green, it merges at once. If the reviewer flags something, it stops and shows why. When the project requires UAT, strikes wait like everything else.
- **D2 Auto in a hold project.** A PR set to Auto in a hold project waits for the batch. Only its own manual Merge button merges it alone, because a lone merge voids the live batch.
- **D3 Outside merges.** Merges outside the train are noted in the project's recent merges strip. They are not refused.

## 3. Decisions made in this document

These close every judgment call. An executor applies them as written.

- **R1 Merge route rule.** `route = batch` when the project is a hold project (D2), or when the issue policy is Hold. Otherwise `route = auto-merge`. In code: `mergeRouteFor(issuePolicy, projectDefault, globalRequireUat)` (WI-2). Consequences:
  - Auto project + Auto (or default) issue: auto-merged alone after the cooldown. **Never batched.** This removes the 26-voided-batches failure.
  - Auto project + Hold issue: batched (one-member batch if alone, which is today's PAN-3965 behavior).
  - Hold project + any issue: batched. Never auto-merged. An `auto-merge` label in a hold project only keeps its existing meaning in the merge gate (a failed UAT verdict is advisory, `merge-gate.ts:75-94`).
- **R2 Live-batch guard.** Independently of R1, the scheduler and the executor never auto-merge an issue that is a member of a live batch (`assembling`, `ready`, `superseded`). This covers the window between an issue policy flip and the next reconcile.
- **R3 Manual merges stay allowed.** The per-row Merge button and a batch member's **Merge alone…** (`POST /api/merge-train/merge-next` with `issueId`), the issue page Merge button (`POST /api/issues/:issueId/merge`) and batch promotion are operator actions and are not subject to R1 or R2. In the `MergeTrain` component, merging a live-batch member alone asks for confirmation naming the batch it will void (WI-10). The issue page `MergeButton` is unchanged and does not confirm; that is out of scope.
- **R4 Strikes in batch-route projects are not batch members.** Batches stay feature-only (`flywheel-merge-order.ts:199`, `:236`, `:533` derive `feature/<id>`). A strike whose route is `batch` gets its expedited review, then waits in the strike lane with the pill **Waits for UAT** and a Merge button (the operator-started strike door). Folding strikes into batches is out of scope.
- **R5 Strike ordering.** A strike on the auto-merge route is scheduled with `scheduledMergeAt = scheduledAt` (no cooldown) and the executor takes due strike rows before due feature rows.
- **R6 The master switch.** The global train flag becomes a master switch: `isMergeTrainEnabledForProject` returns false whenever `isMergeTrainEnabled()` is false, whatever the project override says. Today an `enabled` override wins over a global off (`merge-sync.ts:75-86`), while the executor already pauses on the global flag alone (`auto-merge-executor.ts:172`). The mockup's "Merge train (all projects)" switch requires one meaning.
- **R7 Head approval exemption is narrow.** Only an operator-started strike merge skips the head-approval requirement. Every automatic merge (feature or strike) and every feature merge still needs it (PAN-4750 acceptance).
- **R8 Recent merges are derived.** From the forge listings already cached (`gh pr list --state all --limit 100`, `derived-issue-state.ts:391`; GitLab `merge_requests?state=all`, `:500`), attributed using records that already exist: `pending_auto_merges` rows, `uat_generations` rows, and pipeline journal `merge.attempted` entries. Nothing new is stored for it.
- **R9 Per-issue policy writes the tracker.** The editable Auto/Hold toggle adds or removes the `auto-merge` / `hold-for-uat` labels. Overdeck stores no copy. Trackers whose `IssueLifecycle.addLabel` is a no-op (Linear, Rally; `src/dashboard/server/services/issue-lifecycle.ts:64-82`) get a 501 and a read-only toggle.
- **R10 One component.** `MergeTrain` (new, `src/dashboard/frontend/src/components/merge-train/train/`) replaces `MergeTrainView`, `FlywheelUatBatchesCard` and `PendingAutoMergesCard`. It renders on the Flywheel rail (all projects), on the Awaiting Merge page (all projects), and on the project home (one project).
- **R11 The project page has no tabs.** The mockup's Overview / Issues / Merge train / Settings tab bar is not built. The project card renders as a section in `ProjectOverview` after `ProjectSettingsDisclosure` (`src/dashboard/frontend/src/components/CommandDeck/ProjectOverview.tsx:285`), with DOM id `merge-train`.

## 6. Requirements

### Functional

- **FR-1** An operator-started merge of a strike PR that is open, not a draft, has green checks, is mergeable, and has no changes-requested review succeeds without a head approval. (PAN-4750)
- **FR-2** Every automatic merge (feature or strike) and every feature merge still requires a head approval. (PAN-4750)
- **FR-3** `mergeRouteFor` decides the route of every ready PR per R1; the scheduler, the schedule door, the executor, the batch ready set and the queue payload all use it.
- **FR-4** The scheduler and the executor never auto-merge an issue that is a member of a live batch (R2).
- **FR-5** The global train flag is a master switch (R6).
- **FR-6** Every transition of a batch to `superseded` or `invalidated` stores a one-sentence `status_reason`. When the cause is a member merged outside the batch, the reason names the member and says so.
- **FR-7** The generations payload returns the status reason, and the UI never hides an invalidated or superseded batch: it shows it as one collapsed "Older batch … superseded/voided" row that expands to the full card and the reason.
- **FR-8** The ready set and the merge queue work for GitLab projects and polyrepo projects. A polyrepo issue is ready when every member repo's MR for it is approved, green and mergeable. (PAN-3657)
- **FR-9** Every open strike PR in a train-enabled project with green checks and no review at its current head gets exactly one expedited (quick-mode, single reviewer) review per head, dispatched automatically.
- **FR-10** `pan review request <id>` and `POST /api/review/:issueId/request` work for an issue that has only a strike workspace and a strike PR.
- **FR-11** An expedited review's APPROVED verdict is a head approval the merge gate accepts. Its CHANGES_REQUESTED verdict stops the strike, and the reviewer's summary is readable by the UI.
- **FR-12** An approved, green, mergeable strike on the auto-merge route is scheduled with no cooldown and merged before any due feature row.
- **FR-13** A strike on the batch route is never auto-merged; it waits with an operator Merge button (R4).
- **FR-14** `GET /api/merge-train/board` returns, per project: mode, effective flag, override, cars with state, step, blockers, readiness time and UAT notes, strikes with state, batches (all statuses in the chain, newest first, with status reason), and up to five recent merges with attribution.
- **FR-15** Cars carry all six blocker types: `failing_checks`, `merge_conflict`, `unresolved_conversations`, `changes_requested`, `draft_pr`, `not_mergeable`.
- **FR-16** Recent merges include merges made outside the train, attributed `outside-train`, with a warning when an auto-merge was scheduled for that PR and had not yet run. Outside merges are never refused, reverted or treated as errors.
- **FR-17** `POST /api/merge-train/policy/:issueId` sets an issue's policy to `auto`, `hold` or `default` by writing tracker labels; 501 on trackers without label writes.
- **FR-18** Batch promotion is refused when UAT is required for the batch's project and its stack is not `running`, unless the request carries `overrideStackHealth: true` with a non-empty reason; the override is journaled per member. (#3176)
- **FR-19** One `MergeTrain` component renders per-project bounded cards with mode chip, Train switch, intro line, train-off banner, hero batch (hold projects), older batch rows, queue rows with status pills that expand, the strike lane, and the recent merges strip.
- **FR-20** Expanded queue rows show the full title, branch, PR links (one per repo for polyrepo), "ready N ago", the editable policy toggle with a "default" marker, every blocker with details, reviewer UAT notes, and the 9-step tracker while merging or after a failure.
- **FR-21** The Flywheel page rail shows the all-projects `MergeTrain` with project filter chips and an idle-projects footer line; the Flywheel header carries the master switch. The project home shows that project's card.
- **FR-22** The editable policy toggle (`AutoMergeToggle`) works in every place it renders: the train rows, `IssueHeader`, `PipelineView`, and `MergePolicySection`.

### Non-functional

- **NFR-1** No `execSync`/`execFileSync`/`spawnSync` in server code (rule 1).
- **NFR-2** Every cooldown, countdown and delay test uses fake timers (rule 2).
- **NFR-3** Each new route has a no-loss matrix row and 401s for LAN peers (rule 3).
- **NFR-4** No touched file exceeds its file-size cap (rule 4).
- **NFR-5** No text below 11 px in `components/merge-train/**` (rule 6).
- **NFR-6** The board read costs no more forge calls per poll than today's queues + generations + merge-blockers reads combined: it reuses the cached listings (`listRepoPullRequestsStaleOk`) and the 60 s PR facts cache, and the one new GraphQL read (unresolved threads) is per repo, cached for `PR_CACHE_TTL_MS`.
- **NFR-7** One project's failure never blanks the board: a failed project returns its card with `error` and empty lists (same pattern as `getMergeTrainQueuesPayload`, `merge-train.ts:150-166`).
- **NFR-8** Nothing new stores derivable status. New stored facts are limited to: `uat_generations.status_reason` (why a transition happened), `pending_auto_merges.kind` (what was scheduled), and new optional fields on existing journal entries.
