## Glossary

- **Supervisor:** the small sidecar process `dist/supervisor/server.js` (`src/supervisor/server.ts`). Its **watchdog** (`src/supervisor/watchdog.ts`) polls `GET /api/health` every 10 s and, when the dashboard is down, spawns `pan restart --dashboard --resume --health-timeout 120000` (`src/supervisor/restart-spawn.ts`, `buildSupervisorRestartArgs`).
- **Supervisor unit:** the systemd user unit `overdeck-supervisor.service` that runs the supervisor (`SUPERVISOR_UNIT_NAME`, `renderSupervisorUnit`, `installSupervisorUnit` in `src/lib/systemd.ts`). `pan up` installs and starts it but never enables it.
- **Boot grace:** the watchdog does not restart a dashboard that has never been healthy until `bootGraceMs` (default 5 min, `OVERDECK_SUPERVISOR_BOOT_GRACE_MS`) has passed since the supervisor started (`src/supervisor/watchdog.ts`, search `boot grace active after supervisor startup`).
- **Enable:** `systemctl --user enable <unit>` creates the `default.target.wants` symlink so the user manager starts the unit whenever it starts. It needs an `[Install]` section in the unit.
- **Lingering:** `loginctl enable-linger <user>` makes systemd start the user's manager at boot and keep it after the last logout. Without it, every user unit (and every transient `systemd-run --user` unit) stops at logout and starts only at the next login.
- **Launch agent:** a macOS launchd job in `~/Library/LaunchAgents/<label>.plist`, loaded into the user's `gui/<uid>` domain. It starts when the user logs in. macOS has no equivalent of lingering for agents.
- **npx cache root:** when the CLI runs through `npx @overdeck/core …`, `packageRoot` (`src/lib/paths.ts:97`) is a directory under `~/.npm/_npx/<hash>/node_modules/@overdeck/core`. npm may prune this cache at any time, so nothing that must outlive the command may point into it.
- **Durable runtime:** `${OVERDECK_HOME}/runtime/node_modules/@overdeck/core`, an ordinary `npm install --prefix ${OVERDECK_HOME}/runtime` of the exact running version. Introduced by this issue.
- **Pairing link:** `<base>/#pair=odp_…` from `POST /api/pairing/credentials` (`pairingUrl`, `src/cli/commands/pair.ts`). Single use, expires after 10 minutes, held in dashboard memory (a dashboard restart drops it). `pan machines link <pairing-link>` and **Settings → Anywhere → Machines → Link a machine** consume it (`routeFromPairingUrl`, `src/lib/anywhere/routes.ts:108`).
- **Pairing base:** the `<base>` of the pairing link: an `http://<address>:<api-port>` that the other machine can reach.
- **Primary identity:** `{ repoRoot, mode: 'primary' }` from `resolvePrimaryDashboardIdentity()` (`src/cli/commands/restart.ts:217`). The watchdog evicts a dashboard on its port whose `/api/health` reports another `repoRoot` ("foreign dashboard").

## Problem

FR-25 of the parent PRD: `pan connect` (and `npx @overdeck/core connect` on a machine with no install) turns a machine reached over SSH into a lasting linked machine. It installs the server as a user service with lingering on Linux or a launch agent on macOS, starts it, prints one link that pairs it, and says plainly when the server will stop at logout. Done when: on a fresh VPS reached over SSH, `npx @overdeck/core connect` prints a link; after the operator logs out and the VPS reboots, the machine shows `online` on the laptop.

Today nothing does this:

1. `renderSupervisorUnit()` (`src/lib/systemd.ts:72`) writes no `[Install]` section, so the supervisor unit cannot be enabled, and `src/lib/__tests__/systemd.test.ts` asserts `not.toContain('[Install]')` (around line 199). This was deliberate in PAN-2253: "the unit is deliberately NOT `WantedBy` a boot target and lingering is NOT enabled, so it does not start into a stackless post-reboot environment" (`git show facf1685785:.pan/drafts/pan-2253.md`, line 48). A connected server is exactly the case where boot start is wanted.
2. No code anywhere enables lingering (`grep -rn loginctl src` finds nothing).
3. No launchd code exists (`grep -rln LaunchAgents src` finds nothing).
4. `pan serve` (`src/cli/commands/serve.ts`), the `npx @overdeck/core` entry point, runs the dashboard in the foreground from the npx cache root and dies with the SSH session.
5. `pan pair` prints a `http://localhost:3011/#pair=…` link on a VPS (`getDashboardApiUrl()`, `src/lib/config.ts:418`), which `routeFromPairingUrl` refuses on the other machine ("This link points at localhost").

## Requirements

### Functional

- **FR-1 One command.** `pan connect [--url <base>] [--label <name>] [--json]` exists, registered from `registerPairCommands`, and `npx @overdeck/core connect` runs it.
- **FR-2 Durable runtime under npx.** When `packageRoot` is an npx cache root, `pan connect` installs the exact running version into the durable runtime (skipping the install when the runtime already has that version), then re-runs itself from the durable runtime with the same arguments and exits with the child's exit code. Every path it writes into a unit, plist or spawn afterwards comes from the durable runtime.
- **FR-3 Dashboard running as the primary.** If a dashboard already answers `/api/health` on the API port with the primary identity, `pan connect` leaves it running. Otherwise it starts one through `restartDashboard` + `spawnDashboardDetached` under the restart lock, waiting up to 120 s for health. If a dashboard with another identity held the port, the output says it was replaced.
- **FR-4 Linux service.** On Linux, when `systemdUserAvailable()` and `supervisorUnitAllowed()` are both true, `pan connect` installs the supervisor unit (now carrying `[Install] WantedBy=default.target`), enables it, starts it, and writes the operator's `PATH` for the user manager.
- **FR-5 Lingering.** On the FR-4 path, `pan connect` turns lingering on: already on ⇒ nothing; else it runs `loginctl enable-linger --no-ask-password <user>`; if lingering is still off it prints `sudo loginctl enable-linger <user>` and, when stdin is a TTY and `--json` is off, waits (polling every 2 s) until lingering is on or the operator presses Enter. When lingering stays off it says plainly that the server stops at logout.
- **FR-6 macOS launch agent.** On macOS, `pan connect` writes `~/Library/LaunchAgents/ai.overdeck.supervisor.plist` (supervisor, `RunAtLoad`, `KeepAlive`), loads it, and says plainly that the agent starts when the user logs in. `pan up` on a Mac with the agent loaded does not start a second supervisor.
- **FR-7 No service manager.** On Linux without a usable systemd user manager, or with a non-default `OVERDECK_HOME` that has not opted in (`OVERDECK_SUPERVISOR_UNIT=1`), `pan connect` starts the supervisor as a plain process (`startSupervisorProcess`) and says plainly that the server stops at logout and does not start after a reboot, with the reason.
- **FR-8 One reachable link.** `pan connect` prints one pairing link whose base the other machine can reach (D-6), as a ready-to-run `pan machines link '<link>'` line, plus the paste alternative, the expiry, and a reachability hint naming the host and port.
- **FR-9 Idempotent.** Re-running `pan connect` on a connected machine installs nothing twice, never restarts a healthy primary dashboard, and prints a fresh link.
- **FR-10 Unsupported platforms.** On Windows, `pan connect` exits 1 with `pan connect supports Linux and macOS; on Windows, run it inside WSL.`

### Non-functional

- **NFR-1 Async only.** All `systemctl`, `loginctl`, `launchctl` and `npm` calls use async `execFile` with timeouts. No `execSync`, no new `*Sync` tmux calls. (Only the reused `spawnDashboardDetached` keeps its existing synchronous `systemd-run` runner.)
- **NFR-2 Fake timers.** Tests of the linger poll and every other wait use `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()`; no test waits on real time.
- **NFR-3 No secrets in units.** Units, plists and `environment.d` files carry only `OVERDECK_HOME`, `OVERDECK_SUPERVISOR_PORT` and `PATH` — never a token or API key.
- **NFR-4 index.ts does not grow.** `src/cli/index.ts` stays at or below its `origin/main` line count.
- **NFR-5 Boot bound.** After a reboot of a connected Linux machine with lingering on, its dashboard answers `/api/health` within 6 minutes (5 min boot grace + restart), so a linked laptop shows it `online` within 15 minutes (its link back-off caps at 300 s).

## Decisions

- **D-1 Reuse the supervisor unit; no dedicated dashboard unit.** The parent PRD names `installSupervisorUnit()`. A second unit that runs `dist/dashboard/server.js` with `Restart=always` would fight `pan restart`, `pan reload` and the watchdog itself: each kills the server on the port and spawns its own, and systemd would respawn the killed one into a port conflict. The supervisor unit plus its watchdog already restarts the dashboard as the primary, through the same `pan restart --dashboard` path every other restart uses.
- **D-2 `[Install]` goes into the default render; only `pan connect` enables.** `renderSupervisorUnit` always emits `[Install]\nWantedBy=default.target`, so `pan up`'s idempotent re-render keeps the text stable and keeps a connected machine enable-able. `pan up` still never calls `enable`, so PAN-2253's guarantee holds on every machine that has not run `pan connect`: a unit that is not enabled does not start at boot.
- **D-3 Accept the 5-minute boot grace.** At boot the supervisor starts, the watchdog sees the dashboard down, waits out the boot grace, then restarts it. Shortening the grace for connected machines only would need a unit setting that `pan up`'s re-render would erase. NFR-5 states the resulting bound.
- **D-4 Durable runtime is `${OVERDECK_HOME}/runtime` via `npm install --prefix`, never `npm install --global`.** A global prefix on a system Node is `/usr` and needs sudo; the per-home prefix never does. One path, no sudo. Updating a connected npx machine is `npx @overdeck/core@latest connect` (it installs the new version into the runtime and rewrites the unit). Fleet updates are #4654's.
- **D-5 Re-exec after the runtime install.** The running process's `packageRoot` decides `resolveBundledServerPath()` and `resolveSupervisorBundle()`. Re-running `connect` from the runtime is the only way every path (unit `ExecStart`, `WorkingDirectory`, dashboard bundle, primary identity) agrees; otherwise the watchdog would see the dashboard as foreign and evict it. Loop guard: the child carries `OVERDECK_CONNECT_REEXEC=1`, and a process with that variable never re-execs.
- **D-6 Pairing base, first match wins:**
  1. `--url <base>` exactly as given (trailing `/` stripped);
  2. the first tailnet IPv4 from `interfaceEndpoints` ⇒ `http://<ip>:<port>`;
  3. the server address in `SSH_CONNECTION` (its third field) when it is not loopback ⇒ `http://<addr>:<port>` (IPv6 in brackets) — the address the operator just used to reach this machine;
  4. the first non-internal, non-tailnet IPv4 on an interface not in `IGNORED_INTERFACE_PREFIXES`, public addresses before RFC 1918 ones;
  5. `http://localhost:<port>` with the existing `pan pair` loopback warning.

  `<port>` is `readPlatformConfig().dashboardApiPort`. The kind (`tailnet`, `public`, `lan`, `loopback`) is `classifyHost` of the chosen host (`routes.ts`), with `loopback` for rule 5.
- **D-7 Order of steps.** runtime → dashboard healthy → service (unit + enable + PATH + start, or agent, or process) → lingering → pairing link. The link is requested last because it expires 10 minutes after creation and the linger wait can take longer.
- **D-8 PATH for the user manager.** The systemd user manager's default `PATH` lacks `~/.local/bin` and nvm directories, where the harness CLIs live. On the FR-4 path `pan connect` writes `~/.config/environment.d/60-overdeck.conf` containing `PATH=<process.env.PATH>` (read by the user manager at every start) and runs `systemctl --user set-environment PATH=<process.env.PATH>` for the current boot. Both happen **before** `startSupervisorUnit()`: `set-environment` affects only units started afterwards, and `spawnDashboardDetached` passes the supervisor's own environment to every watchdog-restarted dashboard through `--setenv`. Path segments ending in `/git-guard` (the per-agent shim dirs from `src/lib/launcher-git-guard.ts`, line 372) are dropped before writing, so a run from an agent shell never persists a shim. It does not add `PATH` to the supervisor unit, because `pan up` re-renders that unit from whatever shell (or agent shell with a git-guard shim on `PATH`) runs it.
- **D-9 Lingering wait.** Poll `isLingerEnabled` every 2 s with no timeout. Enter skips. Non-TTY stdin or `--json` never waits. Skipping or failing is not an error: exit 0 with the plain stops-at-logout line (FR-25.3 says to say so, not to fail).
- **D-10 macOS domain.** `launchctl bootstrap gui/<uid> <plist>`; on a non-zero exit, `launchctl bootstrap user/<uid> <plist>`. Loaded and unchanged ⇒ nothing. Loaded and changed ⇒ `launchctl bootout <domain>/ai.overdeck.supervisor`, then bootstrap. "Loaded" = `launchctl print <domain>/ai.overdeck.supervisor` exits 0 for `gui/<uid>` or `user/<uid>`.
- **D-11 Traefik note.** When `readPlatformConfig().traefikEnabled`, the output adds: `Traefik is enabled here; after a reboot the dashboard starts but Traefik and CLIProxy wait for pan up.` (PAN-2253's "stackless" concern, stated rather than prevented.)
