# PAN-1224 — Surface a failed post-merge dashboard deploy ("stale code") loudly

**Issue:** https://github.com/eltmon/overdeck/issues/1224
**Planning model:** agent:claude-opus-4-8
**Status:** proposed

---

## TL;DR — the issue's premise has changed

PAN-1224 was filed (2026-05-20) asking the pipeline to **rebuild + restart the
dashboard after a PR merges**, so the operator's UAT-on-main window runs against
the merged code instead of the stale pre-merge binary.

**That core ask is already built and hardened:**

- Built under **PAN-444** — `cca2526f3 feat(pan-444): add deploy step 0 to
  postMergeLifecycle`. `postMergeLifecycle()` writes `pending-post-merge.json`
  and spawns the detached `scripts/post-merge-deploy.sh`
  (`src/lib/cloister/merge-agent.ts:363-411`).
- Hardened by **PAN-1723** (build from a pristine `origin/main` worktree),
  **PAN-1763** / **PAN-1764** (host restarts no longer kill in-container
  workspace servers).

The deploy script already answers four of the issue's six open questions the way
the issue recommended: full `npm run build` (Q1), build-then-real-restart (Q2),
dashboard-only port kills 3010–3012 with sidecars untouched (Q4), container-cgroup
PIDs skipped (Q6). Successful restarts are surfaced in the activity feed
(`dashboard.lifecycle_started`/`_completed` + the restart-announcer).

**The one genuinely-unaddressed slice is Q3 — "what if the build fails?"** This
PRD scopes *only* that slice (operator decision recorded below).

---

## Problem

When the post-merge build fails, `scripts/post-merge-deploy.sh` exits non-zero
*before* it writes the restart marker and *before* it restarts the server
(`post-merge-deploy.sh:73,82,91`). The consequence:

1. The old dashboard keeps running on **stale code** (the running
   `dist/dashboard/server.js` is behind `origin/main`), and
2. **No operator-visible signal fires.** The `dashboard.lifecycle_failed` event
   is only emitted by `processPendingLifecycle()` on a *fresh boot* that never
   happens (the server never restarts), or when its in-process lifecycle runner
   throws (`src/dashboard/server/pending-lifecycle.ts:126-142`) — neither path is
   a *build* failure. The deacon-patrol fallback
   (`src/lib/cloister/deacon.ts:5007-5033`) still runs the cleanup lifecycle with
   `skipDeploy: true` but emits no failure signal either.

Net result: a failed post-merge build silently sends the operator to UAT-on-main
against old code. The only trace is `/tmp/overdeck-deploy.log`. This is the exact
trust-eroding failure mode the issue's Q3 worried about ("would lose trust in the
pipeline").

This is rare because CI gates each PR, but **`npm run build` of the whole project
from `origin/main` can fail for reasons a single PR's CI did not catch** — most
commonly a semantic conflict between two PRs that each passed CI independently and
only collide once both are on `main`.

## Proposal

Add a **cross-process "dashboard is stale" signal** that the failing deploy script
writes and the running (old) dashboard surfaces. Because the deploy script is a
detached bash process that cannot reach the dashboard's in-process event store —
and in the worst case is failing to restart the very server that would emit — the
signal MUST be a **file marker** that a dashboard-side poller converts into
(a) an activity-feed error and (b) a persistent banner. This mirrors the existing
restart-announcer pattern (`src/dashboard/server/services/restart-announcer.ts`),
whose own header documents exactly this constraint:

> Restart writers […] run in separate processes and cannot reach the dashboard's
> in-process event store — and mid-restart the dashboard is the very thing being
> killed. So the (re)started server announces instead.

**Signal file:** `~/.overdeck/dashboard-stale.json`, written by the deploy script
on a *pre-dist-swap* failure and deleted on success / next successful `pan reload`.

**Flow:**

```
post-merge-deploy.sh build/fetch/worktree FAILS (before dist swap)
   └─ writes ~/.overdeck/dashboard-stale.json   { issueId, reason, stage, error, logFile, timestamp }
        ├─ stale-deploy-watcher (dashboard poll, dedupe by timestamp)
        │     └─ emitActivityEntrySync(level: 'error')   → Activity feed (ONE entry)
        └─ GET /api/dashboard/stale  → useDashboardStaleStatus() → <StaleDashboardBanner/>  (persistent)

post-merge-deploy.sh SUCCESS (exit 0)        → rm -f marker
pan reload SUCCESS (build + restart)         → clearDashboardStaleMarker()
   └─ banner + endpoint clear automatically
```

## Glossary

- **post-merge deploy** — `scripts/post-merge-deploy.sh`, spawned detached by
  `postMergeLifecycle()` after a merge; rebuilds `dist/` from `origin/main` and
  restarts the host dashboard.
- **dist swap** — `post-merge-deploy.sh` Step 4 (`:124-132`): the atomic
  `mv dist.incoming dist`. **Before** the swap the running code is stale; **after**
  it the fresh code is on disk (the failure mode past this point is "server didn't
  start", which is the existing backend-offline banner's job, not ours).
- **restart marker** — `~/.overdeck/dashboard-restarting.json`, written by the
  deploy script *on success* (Step 3, `:110-122`) and consumed by
  `processPendingLifecycle()` to emit `dashboard.lifecycle_started`.
- **stale marker** — NEW `~/.overdeck/dashboard-stale.json`, this PRD's signal.
- **restart-announcer** — `src/dashboard/server/services/restart-announcer.ts`;
  polls `restart-status.json`, emits one activity entry per new `ts`. The template
  for the new stale-deploy-watcher.
- **activity feed** — the dashboard Awareness panel, fed by `activity.entry`
  domain events via `emitActivityEntrySync` (`src/lib/activity-logger.ts:107`).

## Requirements

**Functional**

- **FR-1** A post-merge deploy that fails *before the dist swap* (git fetch fail,
  worktree-add fail, or `npm run build` fail) writes
  `~/.overdeck/dashboard-stale.json` identifying the issue, the failing stage, a
  short error, and the log file path.
- **FR-2** A successful post-merge deploy deletes the stale marker.
- **FR-3** The dashboard exposes the stale state via `GET /api/dashboard/stale`
  (returns the marker when present, a not-stale payload when absent).
- **FR-4** A *new* stale marker emits exactly one error-level activity-feed entry;
  re-polling the same marker (same `timestamp`) emits nothing.
- **FR-5** While stale, the dashboard shows a persistent banner naming the issue
  and the remedy (`pan reload`); the banner disappears once the marker clears.
- **FR-6** A successful `pan reload` clears the stale marker.

**Non-functional**

- **NFR-1** The signal path is cross-process and file-based — it must not depend
  on the dashboard restarting or on any in-process event reaching the failing
  deploy process.
- **NFR-2** No `execSync`/sync-fs on any server-reachable path: marker reads use
  async `fs`; the watcher uses `unref()`ed timers (matches restart-announcer).
- **NFR-3** A missing or corrupt marker is treated as not-stale; the endpoint and
  watcher never throw on it (mirror `readRestartStatus` validation,
  `src/lib/restart-status.ts:40-77`).

## The stale-marker schema (single source of truth — every consumer conforms)

```jsonc
// ~/.overdeck/dashboard-stale.json
{
  "issueId": "PAN-1234",          // optional — the merged issue, if known
  "reason": "post-merge",          // why a deploy ran
  "stage": "build",                // "fetch" | "worktree" | "build" — the failing step (pre-swap only)
  "error": "tsc exited 2 ...",     // short (≤200 char) human summary
  "logFile": "/tmp/overdeck-deploy.log",
  "timestamp": 1718900000000       // epoch ms — dedupe key for the activity emit
}
```

The bash writer (Bead 2) and the TypeScript reader (Bead 1) MUST agree on these
exact field names. Bead 1 is the canonical definition; it is the inspection
foundation for the rest.

## Work Items (beads)

### Bead 1 — `dashboard-stale-marker` lib module (FOUNDATION)

**What/why:** one server-lib module owns the marker's TypeScript type and its
read/clear/write helpers, so every other consumer (endpoint, watcher, reload,
bash writer) conforms to one shape. Single-source-of-truth tenet.

**Files:** NEW `src/lib/dashboard-stale-marker.ts` (sibling of, and modelled on,
`src/lib/restart-status.ts`); NEW `src/lib/__tests__/dashboard-stale-marker.test.ts`.

**Changes:**
- Export `interface DashboardStaleMarker` with the exact fields above.
- Export `STALE_MARKER_PATH = join(getOverdeckHome(), 'dashboard-stale.json')`
  (use `getOverdeckHome()` from `./paths.js`, as restart-status does).
- `readDashboardStaleMarker(): Promise<DashboardStaleMarker | null>` — async
  read + field validation; ENOENT → null; parse/validation failure → null
  (copy the defensive shape of `readRestartStatusPromise`).
- `clearDashboardStaleMarker(): Promise<void>` — `unlink`, ignore ENOENT.
- `writeDashboardStaleMarker(marker): Promise<void>` — atomic tmp-write+rename
  (mirror `writeRestartStatusPromise`); used by tests and available to TS callers.

**ACs:** see vBRIEF.

**requiresInspection:** true — this is the schema every downstream bead encodes
assumptions about. `inspectionDepth: fast`. `foundationFor`: stale-script,
stale-endpoint, stale-watcher, reload-clear.

### Bead 2 — Deploy script writes/clears the stale marker

**What/why:** the cross-process producer. On a pre-swap failure, write the marker;
on success, delete it.

**Files:** `scripts/post-merge-deploy.sh`.

**Changes:**
- Add `STALE_MARKER="$HOME/.overdeck/dashboard-stale.json"` next to the existing
  `RESTART_MARKER` definition (`:22`).
- Add a `write_stale_marker <stage> <msg>` shell helper that writes the JSON
  (fields per the schema; `timestamp` via `$(date +%s000)` as the restart marker
  already does at `:119`; `error` truncated).
- Call `write_stale_marker fetch ...` before the `exit 1` at `:73`,
  `write_stale_marker worktree ...` before `:82`, `write_stale_marker build ...`

- **Do NOT** write the marker on the health-check-timeout `exit 1` (`:186`): by

  failure is "server didn't start" (the backend-offline banner's job), not stale

- On the success path, before `exit 0` (`:181`), `rm -f "$STALE_MARKER"`.

## NonGoals (out of scope — review enforces these as must-not)

- Do NOT make the deacon-patrol fallback (`deacon.ts:5007-5033`) emit a failure
  signal, add a stale-build watchdog, or add a `pan doctor` check. (That was the
  rejected "broader hardening" option.)
- Do NOT write the stale marker on the health-check-timeout path
  (`post-merge-deploy.sh:186`) — post-swap, the dist is fresh; that is the
  backend-offline banner's concern.
- Do NOT change the success behavior of the post-merge deploy, the rebuild scope,
  the restart strategy, sidecar boundaries, or any Q1/Q2/Q4/Q6 behavior — those
  are already correct.
- Do NOT add a banner action button that triggers a rebuild from the browser;
  the remedy is the documented `pan reload`.
- Do NOT touch remote/multi-user dashboards (issue Q5, explicitly out of scope).
- Do NOT reuse / overload `restart-status.json` for the persistent stale state
  (it is a single-slot, overwritten-on-next-restart file; wrong lifetime).

## Decisions

- **D1** Re-scope PAN-1224 to the Q3 build-failure surfacing only (operator chose
  this over "close as done" and over "broader hardening"). Core rebuild+restart is
  already shipped (PAN-444 + PAN-1723/1763/1764).
- **D2** Signal via a dedicated file marker `~/.overdeck/dashboard-stale.json` +
  dashboard-side poller — NOT a domain event from the deploy script (it cannot
  reach the in-process store) and NOT `restart-status.json` (wrong lifetime).
- **D3** Marker is written only for *pre-dist-swap* failures (fetch/worktree/build).
  Post-swap failures (health-check timeout) are "server didn't start", surfaced by
  the existing backend-offline banner.
- **D4** Two clear paths: deploy-script success (`rm -f`) and `pan reload` success
  (`clearDashboardStaleMarker()`), funnelled through `recordReloadStatus(...,true)`.
  `pan restart` (no rebuild) intentionally does NOT clear — it doesn't fix staleness.
- **D5** Both an activity-feed error (Bead 4) and a persistent banner (Bead 5) —
  the operator explicitly asked for both.

## Repo rules that intersect this work (restated for the executor)

- **No `execSync` in server-reachable code** — marker reads/writes use async `fs`;
  watcher delays use `setTimeout` (unref'd), never `execSync('sleep')`. (PAN-70.)
- **Fake timers for the watcher test** — `vi.useFakeTimers()` +
  `vi.advanceTimersByTimeAsync()`; never real waits. Prefer driving the exported
  single-pass function directly with injected deps (as the announcer test does).
- **Dashboard = Node 22 from `dist/`** — run `npm run build` before restarting to
  observe the change; never Bun/tsx.
- **Async tmux only** — N/A here (no tmux interaction), but do not introduce sync
  primitives.
- **pan-style-guide** — banner: no pill badges, no decorative color; reuse the
  existing destructive-banner utility classes already in `App.tsx`.
