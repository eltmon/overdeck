# PAN-4546 — Two concurrent quality gates (`resources.quality_gate_slots`, default 2) with a CPU-pressure fallback to one

**Issue:** [PAN-4546](https://github.com/eltmon/overdeck/issues/4546)
**Folded in:** [PAN-4610](https://github.com/eltmon/overdeck/issues/4610) (a half-written waiter ticket is deleted by a poller and its waiter waits forever). WI-0 fixes it and lands before the N-slot change. The PR body must contain `Closes #4610`.
**Routing note (from the issue):** this is verification machinery (TENET-10). The issue asks for a supervised `pan handoff`, not an unattended `pan start`. The planner records this; it does not enforce it.

## Glossary

- **Quality gate** — one command (`typecheck`, `lint`, `test`, …) from `projects.yaml` that the verification runner executes for `pan done`. Gates run in `src/lib/cloister/validation.ts` (`runQualityGates`-style loop near line 405).
- **CPU admission** — the machine-wide queue in `src/lib/cloister/quality-gate-admission.ts` (PAN-3344, PAN-4311). A gate or a direct local Vitest run must hold an admission lease before it starts.
- **Admission root** — the directory `~/.overdeck/verification-workers/admission/` (`admissionRoot()`, line 133). All lock and waiter files live here.
- **Waiter ticket** — `waiter-<ticketId>.json`, one per pending request. The oldest live ticket is the **head**. Only the head may try to take a slot, so the queue is FIFO.
- **Slot** — one concurrent admission lease. Today there is exactly one slot, stored as `owner.json`. This issue adds N slots.
- **Slot owner file** — the JSON file whose existence means a slot is held. Slot 0 is `owner.json`; slot *i* ≥ 1 is `slot-<i>.json` (decision D1 below).
- **Breaker file** — a short-lived exclusive file that serializes stale-owner reclaim for one slot. Slot 0 uses `owner.break`; slot *i* ≥ 1 uses `slot-<i>.break`.
- **Torn file** — a ticket, owner, or breaker file that exists but does not yet hold complete JSON. Today `writeExclusive` (line 149) creates the file with `open(path, 'wx')` and writes the JSON afterwards, so every new file is briefly torn.
- **Publish** — make a file appear under its final name with its full content in one step: write a temp file in the same directory, then `link()` it to the final name and unlink the temp file (WI-0, D13).
- **Torn grace** — `QUALITY_GATE_ADMISSION_TORN_GRACE_MS` (10 s, new). An unparseable file younger than this, by file mtime against `Date.now()`, is skipped, never deleted.
- **Stale owner** — a slot owner whose `acquiredAt` is older than `QUALITY_GATE_ADMISSION_STALE_MS` (25 min, line 23) or whose `pid` is dead (`ownerIsStale`, line 180).
- **Pressured sample** — the result of `sampleQualityGatePressure()` (line 110) with `pressured: true`: CPU utilization ≥ 0.75, or CPU PSI `some avg10` ≥ 25 (`QUALITY_GATE_PSI_SOME_AVG10_START_THRESHOLD`), or, only when PSI is unavailable, load per core ≥ 1.
- **Settle re-check** — after writing a slot owner file, the request sleeps `settleMs` (1.5 s) and samples again; a pressured re-check gives the slot back (lines 322-330).
- **Runaway patrol** — the observe-only process patrol (`src/lib/cloister/runaway-process-patrol.ts`, classifier `runaway-classify.ts`) that flags long-running CPU-burning process groups. It must never flag an admitted gate.

## Problem

Quality-gate admission is one machine-wide slot: one `owner.json` lock (`ownerPath`, `src/lib/cloister/quality-gate-admission.ts:137`; acquire loop lines 260-349). On the 24-core host on 2026-10-04, 5–7 PRs waited 1–2 hours in the queue while load sat near 7 and CPU PSI `some avg10` stayed near 0. The serialized queue, not the agents, bounded overnight throughput.

**Operator decision (2026-10-04):** allow **two** concurrent heavy gates, and fall back to one whenever CPU pressure is up.

## Decisions (made here; the executor must not re-decide)

- **D1 — Slot 0 keeps the legacy filenames.** Slot 0 is `owner.json` + `owner.break`; slot *i* ≥ 1 is `slot-<i>.json` + `slot-<i>.break`. The issue text says `slot-0.json`, but unrebased workspaces run `tests/vitest-cpu-admission.ts` from their own old checkout for as long as they exist, and that code knows only `owner.json`. With slot 0 = `owner.json`, old and new processes contend on the same slot-0 file, so mixed versions never exceed N concurrent gates. With `slot-0.json`, an old checkout's Vitest run would coordinate with nothing (N+1). No acceptance criterion checks filenames.
- **D2 — Every slot uses today's exact admission path.** Pressure check → exclusive write → settle → re-check → give back on pressure. This applies to slot 0 *and* to slots ≥ 1. The issue's "takes slot 0 whenever it is free" cannot mean "skip the pressure check for slot 0", because AC3 requires `quality_gate_slots: 1` to behave identically to today, and the existing test at `tests/unit/lib/cloister/quality-gate-admission.test.ts:101` (`[high, low, low]`, three samples) proves today's slot 0 checks pressure. "Fall back to one" therefore means: while the sample is pressured, no new gate starts, so a running gate keeps the host to itself until pressure clears.
- **D3 — The head takes the lowest free slot index in `[0, N)`, and only when the total live owner count across all slot files is below N.** "All slot files" means `owner.json` and every `slot-<i>.json` present in the root, for any *i*. This keeps the cap correct when an operator lowers `quality_gate_slots` while a higher slot is still held (for example N lowered 2 → 1 while `slot-1.json` is live: the next request waits).
- **D4 — Stale reclaim is per slot.** Each slot owner file found stale is reclaimed through that slot's own breaker file with today's `clearStaleOwner` rules (dead pid or older than `staleMs`); after a reclaim attempt the loop sleeps `pollMs` and re-evaluates, exactly as today.
- **D5 — Slot count resolution (machine-wide source only).** `QualityGateAdmissionDeps` gains `slots?: number`. When it is omitted (or is not an integer ≥ 1), `acquireQualityGateAdmission` resolves the count once per call from `(await loadGlobalConfigNoMigration()).config.resources.qualityGateSlots` — a new export in `config-yaml/load.ts` that merges **only** the global `~/.overdeck/config.yaml` over defaults and never reads a project `.pan.yaml`. The admission directory is machine-wide, so its limit must be too: with `loadConfigNoMigration`, Vitest runs from different workspaces could resolve different limits for the same directory. A `quality_gate_slots` value in a project file is ignored by admission. The loader is fetched with a lazy `await import('../config-yaml/load.js')` (precedent `model-presets/plan.ts:111`; keeps the Vitest `globalSetup` import graph unchanged and avoids any new import cycle). The resolver **never throws**: any load error, or a value that is not an integer ≥ 1, resolves to `DEFAULT_QUALITY_GATE_SLOTS = 2`. Reason: `tests/vitest-cpu-admission.ts` swallows acquire errors and runs *without* admission, so a throwing resolver would silently disable the Vitest queue.
- **D6a — Canonical slot names only.** A slot file is `owner.json` (slot 0) or `slot-<i>.json` where `<i>` matches `/^[1-9]\d*$/` and `Number.isSafeInteger(i)`. Aliases such as `slot-0.json`, `slot-01.json`, or `slot-1e3.json` are not slots: admission never counts, reads, reclaims, or writes them, and `readQualityGateAdmissionOwnerPids` ignores them. Reason: with a looser matcher, `slot-0.json` would map to slot 0 while `clearStaleOwner(root, 0, …)` targets `owner.json`, so an alias could hold capacity forever or get a valid canonical owner cleared.
- **D6 — Config range.** `resources.quality_gate_slots` accepts an integer in `[1, 16]`; anything else is ignored and the default (2) stays, per the `merge-cpu.ts` ignore-not-clamp convention. 16 bounds a typo such as `200` that would effectively disable admission.
- **D7 — The handle reports its slot.** `QualityGateAdmissionHandle` gains `slot: number` (0-based). `validation.ts:420` logs `[quality-gate] Admitted (slot <slot+1>/<N>): …`-style text; to avoid a second config read in `validation.ts`, the handle also carries `slots: number` (the N it was admitted under). `release()` unlinks only the slot file it took, and only if `sameOwner` still matches.
- **D8 — Waiter ticket shape and filenames are unchanged.** Old code unlinks tickets it cannot parse (`listLiveTickets`, lines 246-249), so the ticket JSON must keep exactly today's fields.
- **D9 — The runaway patrol reads every slot owner.** `quality-gate-admission.ts` exports `readQualityGateAdmissionOwnerPids(rootDir?: string): Promise<number[]>`, which reads `owner.json` and every `slot-<i>.json` in the admission root and returns the numeric pids (malformed or missing files are skipped; never throws; waiter and breaker files are ignored). The patrol and classifier switch from one pid to a list.

- **D13 — Publish with `link()`, not `rename()`.** PAN-4610 suggests `rename`, but `rename` silently replaces an existing target, which would break the mutual exclusion that `open('wx')` gives `owner.json`, the slot files, and the breaker files. `link(tmp, final)` is atomic and fails with `EEXIST` when `final` exists, so `publishExclusive` keeps today's `EEXIST` contract for every caller. Waiter tickets use the same helper. The temp name is `.tmp-<pid>-<seq>-<final basename>`, so it never matches `waiter-*.json`, `owner.json`, or `slot-*.json`.
- **D14 — Torn grace instead of instant delete.** `listLiveTickets` skips an unparseable ticket whose mtime is younger than the torn grace and deletes it only when it is older. New code never writes torn files (D13), but old-version processes still do during the rollout, and they must not lose their tickets to a new poller. The same grace applies to unparseable slot owner files in WI-2.
- **D15 — A waiter recreates its own missing ticket.** Each loop pass checks that its own ticket is in the listing; if not, it republishes the original ticket object (same `ticketId` and `createdAt`), ignores `EEXIST`, and continues, so it keeps its FIFO place. This also covers deletion by old-version pollers.
- **D16 — Leaked temp files are swept by pid.** A process killed between write and link leaves a `.tmp-<pid>-…` file. `listLiveTickets` deletes temp files whose pid is dead; live-pid temp files are left alone.
- **D17 — No timeout is added.** `validation.ts` still passes no `maxWaitMs`; with D15 a waiter cannot lose its ticket, so the unbounded wait is again bounded by the queue ahead of it.

## Requirements
