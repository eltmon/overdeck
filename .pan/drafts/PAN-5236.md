# PAN-5236: Show a reload banner when a dashboard tab runs older frontend code than the server

**Issue:** [PAN-5236](https://github.com/eltmon/overdeck/issues/5236)
**Status:** planned (auto mode, 2026-11-14)

## Glossary

- **Bundle commit** — the git commit the tab's frontend JavaScript was built from. `vite build` compiles it into the bundle as the constant `__OVERDECK_FRONTEND_BUILD_COMMIT__`. It is `null` in the Vite dev server, in Vitest, and in the native phone app's bundle, because none of those define it.
- **Server commit** — the `buildCommit` field of `GET /api/health`. The server's tsdown build compiles it in (`src/dashboard/server/tsdown.config.ts`, `__OVERDECK_BUILD_COMMIT__`). It is `null` when the server runs from source.
- **Build drift** — both commits are non-empty strings and they differ. Only build drift shows the banner.
- **Stream rising edge** — `useConnectionState().streamLive` changes from `false` to `true`. EventRouter sets it `true` after each successful bootstrap (first connect and every reconnect) and `false` whenever the stream goes down (`src/dashboard/frontend/src/components/EventRouter.tsx`, `connection.setStreamLive(true)` after `syncSnapshot(snapshot)`; `markStreamDown()`).
- **New-build banner** — the new non-blocking row, `components/NewBuildBanner.tsx`, `data-component="new-build-banner"`.
- **Web `/m` shell** — the phone screens served by the dashboard in a phone browser (`components/mobile/MobileApp.tsx`). The **native phone app** (`apps/mobile`, `isNativeShell() === true`) renders the same `MobileApp` from its own bundle; it is not the web `/m` shell.
- **Draft** — unsent composer text, kept in localStorage under `conv-draft:<conversationName>` (`src/dashboard/frontend/src/lib/composerDraft.ts`).

## Problem

After a deploy, an open dashboard tab keeps running the frontend code it loaded earlier, and nothing tells the operator. On 2026-11-14 the operator reported the PAN-5184 composer fix as broken again; the tab predated the deploy, and a reload fixed it. Verified fixes look like regressions, and debugging time is wasted.

`src/dashboard/frontend/src/components/StaleBuildChip.tsx` ("build stale ×N") reports only that the **server** build is behind `origin/main` (`useDeployStaleness`, `GET /api/deploy/staleness`). Nothing compares the **tab's** frontend build with the server's.

## Decisions

- **D-1 Source of the server commit.** One `GET /api/health` (`cache: 'no-store'`) on every stream rising edge, plus one at watch start when the stream is already live. This satisfies "on connect and reconnect" with no new polling and no change to the server, the contracts, the snapshot, or `EventRouter`. A snapshot field was rejected: `EventRouter` syncs the cached snapshot from localStorage before bootstrap, so a freshly loaded tab would compare its new bundle against the old server's commit and flash a false banner.
- **D-2 Drift rule.** `isBuildDrift(bundle, server)` is true only when both are non-empty strings and `bundle !== server`. A `null` on either side (Vite dev server, server run from source, a failed fetch, a body without `buildCommit`) never shows the banner. A failed fetch leaves the last known server commit unchanged.
- **D-3 Dev mode.** The Vite define is set only when `command === 'build'`. Under `vite serve` (`pan dev`) the constant is `null`. Reason: `pan dev` hot-rebuilds only the server, so the commits would drift and Reload could not fix it.
- **D-4 Reload that cannot help.** When the operator clicks Reload, the banner writes the server commit to `sessionStorage` key `overdeck.build-drift.reloaded-for`. After the reload, if the bundle still differs from that same server commit, the banner stays hidden for that server commit (a server-only rebuild; reloading again changes nothing). A different server commit shows the banner again. `sessionStorage` errors are caught and treated as "not tried".
- **D-5 No auto-reload.** The banner never reloads the tab by itself. Requirement 4 ("never auto-reload a tab with unsent composer text or an open dialog") is met by never auto-reloading. The `recovery.tsx` chunk-failure reload is unchanged.
- **D-6 Draft handling.** Reload relies on the existing `pagehide` flush; no new flush plumbing. When any non-empty `conv-draft:*` key exists, the banner adds "Unsent drafts are kept." (new helper `hasSavedDraft()` in `lib/composerDraft.ts`).
- **D-7 Surfaces.** The banner mounts in the app shell (`AppChrome.tsx`), the web `/m` shell (`MobileApp.tsx`, only when `!isNativeShell()`), and the standalone conversation popout (it has a composer and is a long-lived window). The terminal, diff and Flywheel popouts are out of scope.
- **D-8 Native phone app.** The check is off when `isNativeShell()` is true. The app-store bundle never matches the machine's server, and Reload cannot update it. `apps/mobile` does not define the constant either, so the bundle commit is `null` there anyway; the explicit gate is defence in depth.
- **D-9 No dismiss button.** The tab really is stale and Reload is the fix; the issue asks for a banner with a Reload button and nothing else.
- **D-10 Copy.** "A newer Overdeck is running. Reload to update." The rollback case (server older than the tab) uses the same text; the plan does not compute commit ancestry.
- **D-11 Style.** Amber means "a human must act" (style guide: amber = human). Use the same row classes as `DegradedModeBanner`'s `delayed` state: container `flex shrink-0 items-center gap-2 border-b border-border px-4 py-1.5 text-xs bg-warning/10 text-warning-foreground`, button `shrink-0 rounded-md border border-warning/40 px-2.5 py-0.5 text-xs font-medium transition-colors hover:bg-warning/20`. No `font-semibold`/`font-bold`, no hardcoded hex, no `rounded-full`, no `bg-muted/…` opacity utilities.
- **D-12 Mobile placement.** In the web `/m` shell the banner renders once, as the first row inside the signed-in branch, above the header, so it shows in the list screens and in a full-screen conversation or issue sheet. It takes `safeAreaTop` and then replaces the top padding with `pt-[calc(env(safe-area-inset-top)+0.375rem)]` (the `py-1.5` top half plus the inset; a bare `pt-[env(…)]` would zero the top padding wherever the inset is 0). On an iPhone in standalone mode the header below also pads its inset, so the gap doubles while the banner shows; accepted (rare, only during drift).

## Requirements

- **FR-1** A `vite build` compiles the checkout's `git rev-parse HEAD` into the bundle as `__OVERDECK_FRONTEND_BUILD_COMMIT__`; `vite serve` compiles `null`; a failing `git` call compiles `null` and the build still succeeds.
- **FR-2** The tab reads its bundle commit with a `typeof` guard, so Vitest, the dev server and the native app get `null` and never throw.
- **FR-3** On each stream rising edge (and once at watch start if already live) the tab fetches `GET /api/health` with `cache: 'no-store'` and a 3 s timeout, and stores `buildCommit` when it is a string (or `null` when the field is absent or not a string). A network error, timeout or non-JSON body leaves the stored value unchanged.
- **FR-4** The new-build banner renders exactly when `isBuildDrift(bundle, server)` is true and D-4 does not suppress it, with the text "A newer Overdeck is running. Reload to update." and a **Reload** button.
- **FR-5** When any non-empty `conv-draft:*` key exists, the banner also says "Unsent drafts are kept."
- **FR-6** Reload records the server commit in `sessionStorage` (D-4) and then calls `window.location.reload()`; it never removes or rewrites `conv-draft:*` keys.
- **FR-7** Nothing in this change reloads the page automatically.
- **FR-8** The banner shows in the app shell, the web `/m` shell (including full-screen conversation and issue views) and the standalone conversation popout. It never mounts in the native phone app.
- **NFR-1** No new polling: the only new request is one `/api/health` per stream rising edge.
- **NFR-2** No server, contract or `EventRouter.tsx` change.
- **NFR-3** Timer-dependent tests use `vi.useFakeTimers()` (repo rule: fake timers for delay tests); the 3 s fetch timeout uses `AbortController` + `setTimeout`.
- **NFR-4** Every new frontend test file is appended to `scripts/frontend-test-subset.txt`.
