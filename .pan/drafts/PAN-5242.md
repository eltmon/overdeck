# PAN-5242: name the WebRTC route in channel errors, add `no-webrtc-egress`, and add a TURN relay health check

**Issue:** [PAN-5242](https://github.com/eltmon/overdeck/issues/5242)
**Status:** draft (planning, `pan plan --auto`)
**Verified against:** `feature/pan-5242` at `cbd344564b5` (2026-11-14), werift 0.25.1

## Glossary

- **Route.** The WebRTC path a dial takes. `direct` is the URL `rtc://<environmentId>` (ICE with host
  and server-reflexive candidates). `relay` is `rtc+turn://<environmentId>` (`iceTransportPolicy:
  'relay'`, TURN only). A dial knows its route from the `relay: boolean` argument.
- **Dialer / initiator.** The side that creates the peer connection and sends the offer. A bot's
  connector is always the dialer.
- **Responder.** The side that answers an offer. Here, the machine's dashboard (`RtcTransport.accept`).
- **Candidate.** An ICE candidate string such as `candidate:1 1 udp 2130706431 10.0.0.2 5000 typ host`.
  Its kind is the word after `typ`: `host`, `srflx`, `prflx` or `relay`. A **relay candidate** is
  `typ relay`. Only a TURN allocation produces one.
- **Gathered.** The candidates this side's own peer connection produced (werift `onIceCandidate`).
- **Received.** The distinct candidates this side learned from the other side, from two sources: the
  `a=candidate:` lines of the remote SDP and the trickled `candidate` signal frames. They are
  deduplicated by text after removing a leading `a=`.
- **Tally.** A count of distinct candidates by kind. Its text form is
  `<total> (host <h>, srflx <s>, relay <r>)`. It never carries candidate text.
- **No relay candidate.** A relay dial whose ICE list names a TURN URL, but which gathered zero
  `typ relay` candidates. The TURN server could not be reached, so the relay route cannot open.
- **Cause.** The `detail.cause` string of a `ChannelOpenError`
  (`packages/anywhere-channel/src/initiator.ts:54-59`). This PRD adds the cause value
  `no-relay-candidate`. It adds no new `ChannelOpenErrorCode`.
- **Status line.** The last stdout line of `pan mcp connector connect`:
  `OVERDECK_CONNECT {"v":1,"status":…}` (`src/lib/mcp/connector/connect-output.ts`). Status `retry`
  exits 4; `error` exits 1.
- **Relay check.** The new on-demand health check: this machine asks the directory for TURN
  credentials and gathers relay candidates once, without dialing anyone.

## Problem

A bot connector that cannot open a WebRTC channel reports a retryable
`"direct connection failed"` with code `machine-unreachable`, even when the relay leg failed and a
retry cannot help. On 2026-11-14 the operator's Grok Bot ran the connect command three times. Each
time it got status `retry`, code `machine-unreachable`, and the detail
`direct connection failed (direct: Secure channel to rtc://e91ffda1-… did not open within 15000 ms)`.
It told the operator to check that the machine was awake. The machine was online.

What the logs show (from the issue, verified by the reporter): all three attempts reached the
machine. Direct offers were answered but never connected. Every relay session logged `failed`
before `answered`, which means the machine's ICE gave up as soon as it read the bot's offer. The
likely cause is an offer with zero candidates: the bot's sandbox has no TLS to
`turn.cloudflare.com:443` and no UDP. This is "likely", not proven, because neither side logs how
many candidates it gathered. This PRD adds those counts.

Empirical check at planning time (werift 0.25.1 on this machine, scratchpad probe): a relay-policy
peer connection with TURN credentials and an unreachable TURN server gathers **zero** candidates,
and `setLocalDescription` resolves after the gather ends:

| ICE list | Gather time | Candidates |
| --- | --- | --- |
| `turns:127.0.0.1:1` (closed port) | 15 ms | 0 |
| `turn:127.0.0.1:1?transport=tcp` (closed port) | 4 ms | 0 |
| `turn:127.0.0.1:1` (UDP, closed) | 6387 ms | 0 |
| `turns:10.255.255.1:443` (blackhole) | 8029 ms | 0 |
| `[]` (no TURN server, relay policy) | 101 ms | 34 (20 host, 14 srflx, 0 relay) |

The last row matters: werift gathers host candidates in relay mode when it has no TURN server with
credentials (`node_modules/werift/lib/ice/src/ice.js:846-850`, `gatherRelayOnly`). So the check
must count `typ relay` candidates, not the total.

## Root cause of the misleading report (verified)

1. `src/lib/mcp/connector/pair.ts:232` dials `rtc://` (15 s, `PAIR_CHANNEL_TIMEOUT_MS`), then line
   237 dials `rtc+turn://`. Lines 239-242 build `` `Could not reach ${label}: ${relayError} (direct: ${directError})` ``
   and return `machine-unreachable` for every relay failure that is not a pairing refusal.
2. `src/lib/anywhere/channel/rtc-transport.ts:389` labels every route's failure
   `` `direct connection ${state}` ``, so the relay failure also reads "direct connection failed".
   `RtcDialAbortedError` (`rtc-transport.ts:58-63`) always says `direct connection aborted`, and
   `awaitOpen` says `data channel closed before it opened` (line 386) with no route.
3. `src/lib/mcp/connector/connect-output.ts:40` puts `machine-unreachable` in `RETRY_CODES`, and
   `CONNECT_NEXT['machine-unreachable']` (line 57) says "Run the same command again in a minute."
4. `RtcTransport` (`rtc-transport.ts:196-206` gathering, `257-261` remote SDP, `240-255` remote
   candidates) counts nothing and logs no candidate numbers.
5. The already-paired path has the same flaw: `connect.ts` `verify()` (lines 119-127) returns
   `verify-failed` (retry) for any probe failure, and `ConnectorLink`
   (`src/lib/mcp/connector/channel-api.ts:141-173`) keeps only the last error code, not its cause.

## Requirements

- **FR-1.** Every error `RtcTransport` produces for a dial names its route: `direct` or `relay`.
  The connector's pairing and link messages label each leg (`relay: …; direct: …`).
- **FR-2.** `RtcTransport` logs per-route candidate tallies on both sides: the dialer logs what it
  gathered when it sends the offer; the responder logs what it received and gathered when it
  answers; both log gathered and received tallies on every `connected`, `failed` and `closed`
  state line. No line contains SDP or candidate text.
- **FR-3.** A relay dial that gathered no relay candidate fails at once with
  `ChannelOpenError('unreachable', …, { cause: 'no-relay-candidate' })` and sends no offer.
- **FR-4.** `pan mcp connector connect` returns status `error` (exit 1), code `no-webrtc-egress`,
  when the relay leg failed with cause `no-relay-candidate`, on both the first pairing and an
  existing pairing's verify. Its `next` says the bot's environment cannot reach the TURN relay (TLS
  to `turn.cloudflare.com:443`) or send UDP in the usual case, that a retry will not help then, that a
  relay outage gives the same result (check `pan doctor` on the machine), and points to Public MCP or
  a host with WebRTC egress.
- **FR-5.** `retry` stays only for codes a retry can clear: `network`, `machine-offline`,
  `machine-unreachable`, `verify-failed` (unchanged set). `no-webrtc-egress` is not in it.
- **FR-6.** `POST /api/anywhere/relay-check` runs the relay check on this machine and answers with
  one of the five states in WI-8.
- **FR-7.** `pan doctor` shows a `TURN relay` row when this machine is signed in to the directory
  with the relay plan: `ok` with the relay candidate count, or `warn` with the reason. It is silent
  otherwise.
- **FR-8.** The docs describe `no-webrtc-egress`, the new log fields, the relay check and the
  doctor row; a changelog entry records the fix.
- **NFR-1.** No log line, error message or doctor row contains SDP, candidate text, TURN
  credentials, keys or tokens. The `never logs SDP or candidate text` test
  (`src/lib/anywhere/channel/__tests__/rtc-transport.test.ts:239-251`) rejects any line containing
  `v=0`, `a=` or `candidate:`; every new line must pass it.
- **NFR-2.** The relay check never runs inside `GET /api/anywhere/status` (the dashboard polls it).
- **NFR-3.** The CLI never opens its own directory socket for the check; it calls the dashboard,
  which owns the machine's one directory registration.
- **NFR-4.** Tests follow the repo rules restated under "Repo rules that apply".

## Decisions

- **D-1. The cause rides `ChannelOpenError.detail.cause`.** No new `ChannelOpenErrorCode`. Code stays
  `unreachable`, so every existing consumer (link supervisor, phone, LinkAgent) keeps working.
- **D-2. Fail fast in `RtcTransport.create`.** After `setLocalDescription` the gather is complete
  (werift awaits it, `peerConnection.js:919`), so the relay-candidate count is final. When the
  route is relay, the ordered ICE list contains a TURN URL, and the relay count is 0, `create`
  closes the entry and throws; no offer is sent. This applies to every `RtcTransport` user:
  the connector, the dashboard's machine-to-machine dials and approval dials
  (`src/dashboard/server/services/directory-rtc.ts`). That is intended: they now fail at the end of
  gathering (≤ about 8 s, werift's TURN connect timeout) instead of after ICE fails or the open
  times out. The dashboard's relay probe budget is 10 s (`link-supervisor.ts:64`
  `RELAY_PROBE_TIMEOUT_MS`), the connector's is 15 s, so the cause arrives before the timeout.
- **D-3. A relay list with no TURN URL is not "no egress".** If the ordered list has no TURN URL,
  `create` does not fail fast; the dial runs as today and a failure stays `machine-unreachable`.
  The directory refuses relay credentials (`turn_unavailable`) rather than send such a list, so
  this is a server fault, not the bot's network.
- **D-4. Tally helpers live in `rtc-transport.ts`** (exported `candidateKind`, `CandidateTally`,
  `firstTurnUrl`, `routeOf`), not in a new module. They are small, and `RtcTransport` is their main
  user; `relay-probe.ts` imports two of them. `rtc-transport.ts` is 403 lines and the god-file
  ceiling is 1000 (`scripts/lint-file-size.sh` `CEILING=1000`).
- **D-5. The existing `rtc session <s> answered` line keeps its exact text.** The responder adds a
  separate `answer to` line before it. Tests pin `answered` (`rtc-transport.test.ts:207,337`).
- **D-6. The relay check is on demand only**: a dashboard route plus a doctor row. No background
  timer and no UI card (see NonGoals). The route is single-flight: a second call while one runs
  awaits the same promise.
- **D-7. The doctor row is `warn`, never `error`.** The relay is optional reachability.
- **D-8. The phone dialer is out of scope.** `packages/anywhere-channel/src/dial-machine.ts` has its
  own "direct connection …" strings (lines 154, 171, 304, 381, 392), pinned by
  `dial-machine.test.ts:301`. The incident, the bot connector and every line the issue cites are
  the Node `RtcTransport`. The phone dialer is a separate browser package
  (`@overdeck/anywhere-channel/web`) that ships inside the mobile app, and no phone report is
  involved. FR-1 is read as "every error `RtcTransport` and the connector produce". Recorded as an
  `autoDecision` and a NonGoal so review checks against that reading.
- **D-9. `callDashboard` gains an optional `signal`.** The doctor needs a 3 s and a 25 s deadline;
  `src/cli/commands/dashboard-call.ts` has no way to pass one today.

   export type CandidateKind = 'host' | 'srflx' | 'prflx' | 'relay' | 'other';

   /** The `typ` of one candidate string; never logs or returns the text. */
   export function candidateKind(candidate: string): CandidateKind {
     const kind = / typ (host|srflx|prflx|relay)(?:\s|$)/.exec(candidate)?.[1];
     return (kind as CandidateKind | undefined) ?? 'other';
   }

   /** Distinct candidates by kind (deduplicated by text without a leading `a=`). */
   export class CandidateTally {
     private readonly seen = new Set<string>();
     readonly counts: Record<CandidateKind, number> = { host: 0, srflx: 0, prflx: 0, relay: 0, other: 0 };
     add(candidate: string | undefined | null): void {
       const key = (candidate ?? '').trim().replace(/^a=/, '');
       if (!key || this.seen.has(key)) return;
       this.seen.add(key);
       this.counts[candidateKind(key)] += 1;
     }
     addSdp(sdp: string): void {
       for (const line of sdp.split(/\r?\n/)) if (line.startsWith('a=candidate:')) this.add(line);
     }
     get total(): number {
       return this.seen.size;
     }
     /** `3 (host 2, srflx 0, relay 1)`. */
     format(): string {
       const { host, srflx, relay } = this.counts;
       return `${this.total} (host ${host}, srflx ${srflx}, relay ${relay})`;
     }
   }
   ```

/**
 * The relay check (PAN-5242 FR-6): can this machine gather a TURN relay candidate now? One
 * relay-policy werift peer connection, one data channel, one offer; the gather ends inside
 * `setLocalDescription`. Nothing is dialed and no offer leaves this process. No result carries
 * candidate text or credentials.
 */
export const RELAY_CHECK_TIMEOUT_MS = 12_000;

export type RelayCheckResponse =
  | { state: 'skipped'; reason: 'directory-offline'; detail: string }
  | { state: 'refused'; detail: string }
  | { state: 'unanswered'; detail: string }
  | { state: 'ok'; relayCandidates: number; turnUrl: string; elapsedMs: number }
  | { state: 'failed'; relayCandidates: 0; turnUrl: string | null; elapsedMs: number; detail: string };

export type RelayProbeResult = Extract<RelayCheckResponse, { state: 'ok' } | { state: 'failed' }>;

export interface RelayProbePeer {
  onIceCandidate: { subscribe(handler: (candidate: { toJSON(): { candidate?: string } } | undefined) => void): unknown };
  createDataChannel(label: string, opts: { ordered: boolean }): unknown;
  createOffer(): Promise<unknown>;
  setLocalDescription(description: unknown): Promise<unknown>;
  close(): Promise<void>;
}

export async function probeRelayCandidate(
  servers: readonly RTCIceServerLike[],
  deps: { createPeer?: (config: { iceServers: RTCIceServerLike[]; iceTransportPolicy: 'relay' }) => RelayProbePeer; now?: () => number; timeoutMs?: number } = {},
): Promise<RelayProbeResult>;
```

## Critique response

### zero candidates do not prove bot egress is blocked

Accepted in part. The dialer cannot tell a blocked network from a TURN outage or a refused
allocation: all of them gather zero relay candidates. Credentials come fresh from the directory
(600 s TTL) right before the dial, so stale credentials are unlikely, but they remain possible. The
issue asks for a distinct code that is not retryable, so the code stays `no-webrtc-egress` with
status `error`. Status `error` makes the bot stop and tell the user rather than loop. The design
changes so it no longer claims certainty:

- The `next` text (WI-4) now says "the usual cause is …" instead of asserting the cause. It sends
  the user to `pan doctor` on their machine. If the `TURN relay` row is ok, the block is on the
  bot's side, so use Public MCP or another host. If the row warns too, the relay is down, and the
  user can run the command again once it passes. The user decides when to retry, not a loop.
- The fail-fast message (WI-3) now says "the TURN server could not be reached from this host or
  refused the allocation". It no longer claims "this host cannot reach".
- `bots.mdx` (WI-10) says a relay outage gives the same result and must be checked first.

A connector-side check that tells egress from allocation failure (for example a plain TLS connect
to the TURN host) is not added. It would mean more network I/O in the failure path and another
classification layer, and the doctor row already gives the user that answer from the machine.
The hazard "a TURN outage looks like no egress" stays recorded.

### dial setup errors still lack a route

Accepted. WI-1 step 4 wraps the whole body of `create()` with `withRoute(route, error)`. A failed
ICE-server request (`the directory did not answer the ICE server request`) or a failed
`createOffer` / `setLocalDescription` now rejects as `relay connection: …` or `direct connection: …`.
