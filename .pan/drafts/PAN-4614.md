# PAN-4614: Shared concerns.md conflicts on every concurrent PR; mark it merge=union

**Issue:** https://github.com/eltmon/overdeck/issues/4614

## Glossary

- **concerns.md** — `.overdeck/context/codebase/concerns.md`, the shared "Concerns / hazards"
  list in the codebase map. It is a markdown bullet list; agents append bullets near the end.
  It ends with one footer line, `<!-- last-verified: YYYY-MM-DD -->`.
- **Footer** — that `<!-- last-verified: … -->` line. `roles/plan.md` (line 49) and
  `sync-sources/skills/pan-map/SKILL.md` (lines 22–24) tell agents to keep it at the end and
  to update its date when they confirm a change.
- **Union merge driver** — git's built-in `merge=union` attribute. When both sides change
  the same region, git keeps both sides' lines (ours first, then theirs) instead of writing
  conflict markers. It is built in, so it needs no `git config` entry. It does not dedupe.
- **Merge door** — the server-side merge path. Its rebase is `rebaseFeatureBranch`
  (`src/lib/cloister/merge-rebase.ts`), called from
  `src/dashboard/server/routes/workspaces/merge-strike.ts` (`rebaseWithAgentFallback`, line 518).
  It has two entry points: the in-place path (`rebaseFeatureBranchBody`, line 183, runs
  `git rebase origin/<base>` in the workspace) and the approved-head path
  (`rebaseApprovedHead`, line 70, runs `git rebase origin/<base>` in a detached temp worktree
  made by `git worktree add --detach`, line 111).
- **Conflict probe** — `probeBranchConflictPaths` (`src/lib/cloister/conflict-gate.ts`, line 80).
  It runs `git merge-tree --write-tree --name-only HEAD origin/<target>` (line 101) and
  returns `{ mergeability: 'clean' | 'conflicts' | 'unknown', paths }`. The conflict-repair
  patrol uses it for the paths in its repair prompt.
- **Merge gate's conflict signal** — `evaluateConflictRepairGate` (`src/lib/cloister/merge-gate.ts`,
  line ~156) reads the forge's `mergeable` fact (GitHub), not a local git run.
- **sync-main** — `pan sync-main <id>` (`src/cli/commands/sync-main.ts`): "Uses git merge
  (not rebase)" (line 5). It is the conflict-repair patrol's repair step.

## Problem

Concurrent PRs that each add a bullet to concerns.md conflict, because git's default 3-way
merge reports two overlapping appends as a conflict. On 2026-10-24 this blocked PAN-4595 twice
(PR #4601 went CONFLICTING after #4600 merged; after repair and re-review the merge door's
rebase failed with `Rebase conflicts in: .overdeck/context/codebase/concerns.md` after #4604
merged). Each round costs a re-verification and a re-review. `git log --since=2026-10-01`
shows 14 commits on main touching concerns.md.

## Verified behavior (experiments run during planning, git 2.43.0)

All in throwaway repos under the session scratchpad. Fixture: base file `- one\n- two`, branch
`a` adds `- A-bullet` after `- two`, branch `b` adds `- B-bullet` after `- two`.

1. **Control (no attribute):** `git merge-tree --write-tree --name-only a b` exits 1 and names
   concerns.md, in both a normal clone and a bare clone.
2. **With `merge=union`:** `git rebase main` of `b` (after `a` merged) succeeds; the file holds
   `- A-bullet` then `- B-bullet`. `git merge-tree` exits 0 in a normal clone and in a bare
   clone (git 2.43 reads `HEAD:.gitattributes` in a bare repo by default).
3. **Pre-attribute branch:** a branch created before `main` gained the attribute:
   - `git rebase main` succeeds (rebase checks out main's tree first, so main's
     `.gitattributes` is in effect).
   - `git merge main` into it **conflicts** (merge reads the current branch's working-tree
     `.gitattributes`, which lacks the line). This is what `pan sync-main` runs.
4. **Footer:** both sides append a bullet and bump the footer.
   - Same date on both sides: clean result, one footer.
   - Different dates: union keeps both hunks, giving `- A`, `<!-- last-verified: D1 -->`,
     `- B`, `<!-- last-verified: D2 -->` — a stray footer mid-file. No content is lost.
   6 of the 14 commits since 2026-10-01 bumped the footer, so this case is routine.
   Nothing in `src/` or `scripts/` parses the footer (`git grep last-verified` hits only
   prompt text in `src/lib/cloister/conflict-repair.ts:116`).

## Requirements

- **FR-1** `.gitattributes` assigns `merge=union` to `.overdeck/context/codebase/concerns.md`.
- **FR-2** The `.gitattributes` comment above that line states why union is safe here
  (line-oriented markdown bullet list; both sides' bullets should survive), names the known
  artifact (a duplicated footer when two PRs stamp different dates), and the existing WARNING
  that JSON state files under `.pan/specs/`, `.pan/continues/`, `.pan/records/` must never get
  a content-merge driver stays verbatim.
- **FR-3** A regression test proves, with real git and the repo's real `.gitattributes`, that
  two branches each adding a bullet to concerns.md rebase through both merge-door entry points
  with both bullets kept and no conflict, that the conflict probe reports `clean`, and that the
  same fixture without the attribute conflicts.
- **FR-4** `docs/MERGE-WORKFLOW.md` names the union-merged files and their limits, including that
  GitHub's mergeable check is unverified (PAN-4616); it never claims concurrent appends "never conflict".
- **FR-5** The codebase-map guidance tells agents to keep exactly one footer line at the end of
  a map file and to delete a stray one a union merge left mid-file.
- **NFR-1** No change to merge-door, conflict-gate, merge-gate, or sync-main code.
- **NFR-2** The test uses a local bare remote only — no network — and real timers are not
  involved (no retry/delay logic is exercised).

## Decisions (made here, not left to the executor)

- **D1 Only concerns.md gets union.** `architecture.md` (11 edits in the same window) conflicts
  the same way, but it is sectioned prose, not an append list; union would interleave
  paragraphs silently. `conventions.md` (1) and `stack.md` (3) rarely change. They are NonGoals.
- **D2 Keep the footer convention; make it self-healing.** Agents still bump the footer when
  they verify. The stray-footer artifact is cosmetic (nothing parses it), so the fix is one
  guidance sentence telling the next editor to collapse duplicates, not a new policy on who may
  bump the date.
- **D3 Test location and shape.** New file
  `src/lib/cloister/__tests__/merge-rebase-union-concerns.test.ts`, modeled on
  `src/lib/cloister/__tests__/merge-rebase-plan-artifacts.test.ts` (real git, `execFileSync`,
  local bare remote, `mkdtempSync` root, `rmSync` in `afterEach`). It seeds the fixture's
  `.gitattributes` from the repo's real file so the test goes red if the line is removed.
  Reading `.gitattributes` with `readFileSync` is allowed: `scripts/lint-source-introspection.sh`
  only counts `readFile*` calls whose argument is a `.ts`/`.tsx` string.
- **D4 Do not edit concerns.md in this PR.** This PR's own commit is replayed onto a base that
  does not have the attribute yet, so it gets no protection for its own hunk.
- **D5 GitHub's `mergeable` is not settled here.** Public reports (a 2016 RuboCop PR; GitLab
  and Bitbucket issues) say hosted merge checks ignore `merge=union`, but modern git honors it
  in bare repos (experiment 2). Settling it needs an outward action (a throwaway GitHub repo),
  which planning does not take. Working assumption: GitHub may still report CONFLICTING. The
  plan still pays off: the merge door's rebase never fails on concerns.md again, and a
  patrol-sent `pan sync-main` auto-resolves for any branch carrying the attribute. Post-landing
  check: see H2.
  **Scope of this issue (narrowed after critique):** PAN-4614 fixes the local-git paths — the
  merge door's two rebase entry points, `git merge-tree`, and `pan sync-main` on post-attribute
  branches. GitHub's mergeable path is tracked in [PAN-4616](https://github.com/eltmon/overdeck/issues/4616).

## Hazards

- **H1 Transitional sync-main conflict.** Branches created before W1 lands lack the attribute
  in their own `.gitattributes`; `pan sync-main` (a merge) into them still conflicts on
  concerns.md once. After that merge they carry the attribute. Expected, documented in W3.
- **H2 GitHub `mergeable`.** See D5. After landing, on the next pair of concurrent PRs that both
  touch concerns.md, the operator or Flywheel notes whether GitHub reported CONFLICTING. The
  follow-up is filed: [PAN-4616](https://github.com/eltmon/overdeck/issues/4616) records the
  observation and, if GitHub ignores union, designs the merge-gate fallback.
- **H3 Union keeps both edits of the same bullet.** If two PRs rewrite the same existing bullet
  differently, both versions survive with no conflict. Acceptable for a hazards list; the next
  map refresh collapses it.
- **H4 This PR must not touch concerns.md** (D4).

## Critique response

### GitHub conflict gate remains unverified

Accepted. The critic is right that the merge gate trusts GitHub's `mergeable` fact
(`src/lib/cloister/pr-facts.ts` maps `CONFLICTING` to `mergeable: false`, and the merge queue
refuses before the server rebase), and that the four tests exercise only local git. Changes:

- **Objective narrowed.** PAN-4614 fixes the local-git paths, matching the issue's own Fix and
  Acceptance sections: the merge door's in-place and approved-head rebases (the failure PAN-4595
  hit the second time), `git merge-tree`, and `pan sync-main` for branches carrying the
  attribute. See D5.
- **Documentation corrected.** The W3 paragraph no longer says concurrent appends "never
  conflict"; it names the local paths that stop conflicting and says GitHub's mergeable check may
  still report the PR conflicting (FR-4, AC-W3).
- **GitHub path tracked with its fallback.** Verifying GitHub needs a controlled PR pair on the
  forge, an outward action an auto-mode planner and work agent should not take unasked. Filed
  [PAN-4616](https://github.com/eltmon/overdeck/issues/4616): observe GitHub's result on the next
  concurrent pair after this lands; if GitHub ignores union, design the merge-gate fallback
  (let the server rebase run when GitHub says CONFLICTING but the local probe says clean). That
  touches the merge gate's trust boundary, so it gets its own plan rather than being folded in.

Even if GitHub ignores the attribute, this change still removes cost: a patrol-sent
`pan sync-main` repair now merges cleanly instead of needing a hand resolution, and the merge
door's rebase can no longer fail on concerns.md.
