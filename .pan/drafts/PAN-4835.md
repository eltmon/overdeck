**What this ships.** The machine side of the phone app's identity: a new access-token kind `phone`, the pairing exchange that mints it, two self-service routes the app calls, phones in the device list, the `capabilities.phoneApp` flag, and the route-scope rows the phone screens need. All work is in the dashboard server, `src/lib/access-tokens.ts`, one contract field, the Settings Devices panel and two developer docs. No phone code, no directory code.

## Glossary

- **Machine:** a computer running the Overdeck dashboard server (`pan up`).
- **Access-token registry:** `${OVERDECK_HOME}/access-tokens.json`, read and written only through `src/lib/access-tokens.ts`. Each record is one revocable credential with a `kind`: `device` (paired browser), `token` (API token) or `machine` (a linked machine, PAN-4645). This issue adds `phone`.
- **Secure channel:** the Noise-encrypted byte stream between two Overdeck endpoints (`src/lib/anywhere/channel/`, `@overdeck/anywhere-channel`). The machine hands each decrypted channel to its Node HTTP server, so requests inside a channel are ordinary HTTP/1.1. A request's channel is read with `channelOfRequest(request)` (`src/dashboard/server/channel-peer.ts`), which returns a `ChannelMarker { mode, remoteKeyHex, … }` or `null` for a plain socket.
- **Pairing mode / link mode:** two handshake modes. Pairing (`Noise_XXpsk0`) is keyed by a one-time `odp_` pairing code and is used once, to exchange credentials. Link (`Noise_IK`) is used afterwards; the responder (the machine) proves the initiator's static key and accepts it only when `isPinnedPeer(remoteKeyHex)` is true (`src/lib/anywhere/channel/accept.ts:137`).
- **Phone key (link key):** the X25519 public key the phone app uses in link mode, 64 lowercase hex. Inside a channel it is `channel.remoteKeyHex`.
- **Push key:** a second X25519 public key (64 hex) the phone uses to decrypt sealed notifications (W-MAC3 consumes it; this issue only stores it).
- **Client id:** the phone app's directory client id, a UUID v4 (epic W-CON1). One active phone record per client id.
- **Phone credential:** the `DashboardCredential` variant `{ kind: 'phone', … }` that a `phone` record resolves to. It resolves only inside a link-mode channel whose `remoteKeyHex` equals the record's `phoneKey`.
- **Route-scope table:** `ROUTE_SCOPES` and `RPC_METHOD_SCOPES` in `src/dashboard/server/route-scopes.ts`. A registry credential needs the listed scope for `METHOD path` (or RPC tag). Anything unlisted needs `admin`.
- **CSRF check:** `rejectUnsafeDashboardMutationRequest` (`src/dashboard/server/routes/dashboard-auth.ts:247-271`) requires `x-overdeck-csrf-token` for cookie-borne credentials. Header-borne credentials skip it.
- **No-chained-hops rule:** PAN-4651 D-4651-17. Three sites refuse every channel caller so a linked machine cannot use this machine as a hop to a third: `refuseFleetRequest` (`routes/machines-fleet.ts:269`), `chainedHopRefusal` (`linked-conversation-proxy.ts:163`) and the `/ws/linked` upgrade (`ws-linked.ts:132`). This issue leaves all three unchanged (see D-6).
- **Phone surface:** the requests the phone app must be able to make on its paired machine, listed in "Phone surface inventory" below. It is the fixture for the inventory test (WI-6).

## Facts this plan is built on (verified 2026-11-03 at `272f0f4018b`)

1. **The record validator lists kinds by hand.** `src/lib/access-tokens.ts:210`:
   ```ts
   (r.kind === undefined || r.kind === 'device' || r.kind === 'token' || r.kind === 'machine');
   ```
   A record with any other kind makes `parseRegistry` throw "unexpected shape", and a corrupt file accepts **zero** tokens (`failSnapshot`, line 288). So the `phone` kind and its required fields must land in the validator in the same change that first writes a phone record. A downgrade to a version without `phone` refuses every token until phones are removed; this is the same accepted hazard as `machine` (header comment lines 21-22).
2. **The link handshake refuses keys that no machine token pins.** `src/dashboard/server/server.ts:188`:
   ```ts
   isPinnedPeer: (remoteKeyHex) => findActiveMachineTokenByKey(remoteKeyHex) !== null,
   ```
   `accept.ts:137-138` throws `unknown-peer` when this is false. Without a change here, a phone's link channel never reaches HTTP, so no credential check runs. **The epic PRD's W-MAC1 does not mention this; it is the first thing to fix.** WebRTC data channels reach the same acceptor (`acceptRawChannel`, `channel-listener.ts:99`).
3. **Credential resolution inside a channel accepts only `machine`.** `dashboard-auth.ts:177-196`; line 182 returns `null` unless `record.kind === 'machine'` and `record.machineKey === channel.remoteKeyHex`.
4. **On a plain socket, an unknown kind falls through to `device`.** `dashboard-auth.ts:205-213`:
   ```ts
   if (record.kind === 'machine') return null;
   if (record.kind === 'token') { … }
   // A record with no kind is a device (PAN-2351 FR-10).
   return { kind: 'device', deviceId: record.id, scopes: record.scopes };
   ```
   Without an explicit `if (record.kind === 'phone') return null;`, a phone token presented over plain HTTP (for example over Tailscale) would authenticate as a device. This must be refused.
5. **The CSRF check resolves the credential without the channel.** `dashboard-auth.ts:260`:
   ```ts
   const credentialKind = resolveDashboardCredential(headers)?.kind;
   if (credentialKind === 'internal-token' || credentialKind === 'token') return null;
   ```
   `resolveDashboardCredential(headers)` passes `channel = null`, so a channel credential never resolves here. The fix uses `resolveRequestCredential(request)` (same file, line 217), which reads the channel marker. For plain sockets this is identical; for `machine` credentials in a channel the result is unchanged (they are not in the skip list and still reach the CSRF check).
6. **Most phone mutation routes check only Origin, not CSRF.** `POST /api/conversations/:name/message`, `…/codex-approval`, `…/pi-ask-answer`, `…/pane-choice`, `…/upload-image` call `validateOrigin(request)` (`routes/conversations.ts` around lines 530-700). `validateOriginHeaders` (`routes/origin-validation.ts:127-157`) passes a POST with no `Origin`/`Referer` when it carries `Authorization: Bearer odk_…` (line 144), and **rejects a present but untrusted `Origin`** (lines 148-153). `POST /api/agents/:id/answer-question` (`routes/agents/permissions.ts:209-218`) has no per-route guard; the global gate decides. So the phone's HTTP client must send **no** `Origin` or `Referer` header (contract for W-WEB2; see H-2).
7. **Revocation closes connections per kind.** `src/dashboard/server/device-connections.ts:49-53` `revocableCredentialId` returns an id only for `device`, `token` and `machine`; `src/dashboard/server/ws-rpc-auth.ts:160-165` `registerRevocationClosers` closes channels only for `machine` records (`closeChannelsForPeer(record.machineKey)`). Both need `phone`. The registry refreshes every 5 s (`ACCESS_TOKEN_REFRESH_MS`, `access-tokens.ts:50`), so a revoke written by another process (for example `pan devices revoke` while offline) lands within 5 s; an in-process revoke fires listeners at once (`revokeAccessToken`, line 422).
8. **The pairing-channel allowlist is fixed.** `src/dashboard/server/remote-request-gate.ts:114`:
   ```ts
   export const PAIRING_CHANNEL_ALLOWLIST: ReadonlySet<string> = new Set(['GET /api/environment', 'POST /api/machines/exchange']);
   ```
   and line 138 returns 401 for `POST /api/machines/exchange` on any non-pairing socket.
9. **The machine exchange is the model for the phone exchange.** `routes/machines-peer.ts:72-118` `handleMachinesExchange(bodyText, channel)` refuses anything but `channel?.mode === 'pairing'` (403), parses a `v: 1` body, mints the record bound to `channel.remoteKeyHex`, emits an activity entry and answers `{ v: 1, token, tokenId, descriptor }` with `descriptor = await buildEnvironmentDescriptor()`.

It closes the caller's own channel before the response flushes; the caller treats a dropped connection after the DELETE as success.
11. **The device list shows `device` records only.** `routes/pairing.ts:160-170` filters `record.kind === 'device'`; `DELETE /api/devices/:id` (lines 172-205) looks up `record.kind === 'device'` (line 187). ## Requirements

### Functional

- **FR-1 Phone record.** The registry accepts `kind: 'phone'` records that carry `phoneKey` (64 lowercase hex), `clientId` (UUID v4) and an optional `pushKey` (64 lowercase hex). A `phone` record missing `phoneKey` or `clientId`, or with a malformed one, makes the file corrupt (fail closed), exactly like a malformed `machine` record.
- **FR-2 Phone scopes.** A phone record carries exactly `PHONE_TOKEN_SCOPES` = `read:events, read:state, read:conversations, read:costs, read:settings, tell, operate, approve`. `createAccessToken` refuses a phone record with `admin` or `forward`.
- **FR-3 Channel binding.** A phone credential resolves only inside a link-mode channel whose `remoteKeyHex` equals the record's `phoneKey`. It resolves to `null` in a pairing or approval channel, in a link channel from any other key, and on a plain socket.
- **FR-4 Pinned key.** The channel listener accepts a link-mode handshake from a key that an active `phone` record holds as `phoneKey`, as it does for an active `machine` record's `machineKey`.
- **FR-5 No CSRF, no Origin.** A request with a phone credential skips the Origin and CSRF checks in `rejectUnsafeDashboardMutationRequest`.
- **FR-6 Pairing exchange.** `POST /api/phones/exchange`, reachable only through a pairing-mode channel, takes `{ v: 1, clientId, label, pushKeyHex }`. It answers 409 when an active phone record already holds `channel.remoteKeyHex` as its `phoneKey`. Otherwise it mints a phone record bound to `channel.remoteKeyHex`, then revokes every earlier active phone record with the same `clientId`, and answers `{ v: 1, token, tokenId, descriptor }`.
- **FR-7 Self-revoke.** `DELETE /api/phones/self` revokes the calling phone's own record and closes its connections and channels. Any other credential gets 403.
- **FR-8 Push-key rotation.** `PUT /api/phones/self/push-key` with `{ pushKeyHex }` replaces the calling phone's `pushKey`. Any other credential gets 403.
- **FR-9 Device list.** `GET /api/devices` returns phone records next to device records, each row with `kind: 'device' | 'phone'`. `DELETE /api/devices/:id` revokes a phone record and closes its channels. The Settings → Anywhere Devices panel labels phone rows "Phone app".
- **FR-10 Revocation closes sockets.** Revoking a phone record by any path (operator, `DELETE /api/phones/self`, another process) closes its `/ws/rpc` sockets with 4401 and destroys its channels within 5 s.
- **FR-11 Capability flag.** `GET /api/environment` reports `capabilities.phoneApp: true`.
- **FR-12 Scope rows.** The route-scope table maps `pan.getSnapshot` → `read:state`, `pan.replayEvents` → `read:events`, `GET /api/activity` → `read:state`, `GET /api/conversations/pending-input` → `read:conversations` (explicit, ahead of `/api/conversations/:id`), `POST /api/conversations/:name/delete-image` → `tell`, `PUT /api/phones/self/push-key` → `tell`, `DELETE /api/phones/self` → `tell`.
- **FR-13 Phone surface test.** A test asserts that every request in the phone surface inventory resolves to a scope that `PHONE_TOKEN_SCOPES` satisfies, and that every request in the admin-only list does not.

### Non-functional

- **NFR-1 Never admin, never forward.** No code path mints or resolves a phone credential with `admin` or `forward`.
- **NFR-2 Fail closed.** A malformed phone record makes the registry corrupt (zero tokens) rather than parsing permissively.
- **NFR-3 Async only.** New server code uses async I/O; no `execSync` and no `*Sync` call on a server-reachable path (repo rule `no-execsync-server`). The registry snapshot lookups (`findActiveChannelTokenByKey`) are in-memory and synchronous by design, like `findActiveMachineTokenByKey`.
- **NFR-4 Fake timers.** Any test that waits on the 5 s refresh uses `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`, never a real wait (repo rule `fake-timers-for-retry-tests`).
- **NFR-5 No god files.** No touched file passes its allowed line count (`scripts/lint-file-size.sh`). All are well under 1000 today.
- **NFR-6 Machine behavior unchanged.** Every existing `machine`, `device` and `token` test passes unchanged.

## Decisions

- **D-1 One lookup for pinned channel keys.** Add `findActiveChannelTokenByKey(keyHex)` to `access-tokens.ts`. It returns the active `machine` record whose `machineKey` equals the key, else the active `phone` record whose `phoneKey` equals it, else `null`. `server.ts:188` uses it for `isPinnedPeer`. `findActiveMachineTokenByKey` stays for its other callers.
- **D-2 One active phone record per client id and per phone key; a fresh link key per pairing.** Every channel from one key, pairing channels included, is tracked under that key (`channel-listener.ts:227-241`), and revoking a phone record destroys every channel from its `phoneKey` (WI-4). So if the exchange revoked an older record with the *same* key, it would destroy its own pairing channel before the response is written, and the phone would lose both its old and its new token. Rules: (a) the phone app generates a new link key pair for every pairing (contract for W-APP1; per-machine keys also stop machines correlating one phone); (b) the exchange answers **409** `{ error: 'this link key is already paired with this machine; pair again with a new key', code: 'link-key-in-use' }` when an active phone record already holds `channel.remoteKeyHex`; (c) otherwise it mints the new record **first** and then revokes every older active phone record with the same `clientId` (they hold other keys, so the pairing channel survives, and a failed mint leaves the old record working). So `findActiveChannelTokenByKey` and resolution never see two active phone records for one key.
- **D-3 Record name.** The record's `name` is the trimmed `label` from the exchange body (1-64 characters). It is what the Devices panel shows.
- **D-4 Phone credential shape.** `{ kind: 'phone'; tokenId: string; clientId: string; phoneKey: string; scopes: AccessTokenScope[] }`. The scopes are the record's scopes, unnarrowed (a phone sends no actor stamp or ceiling header).
- **D-5 CSRF skip uses the channel-aware resolver.** Line 260 becomes `resolveRequestCredential(request)?.kind`, and `'phone'` joins the skip list. A phone credential is header-borne and channel-bound, so there is no ambient cookie to abuse (epic D-4).
- **D-6 Linked machines are out of scope; filed as PAN-4887.** The epic's FR-5/D-3 ("other machines through its links") contradicts the no-chained-hops rule at three sites. Lifting it for phones is a separate security change, and it does not fit this issue's file budget. In this issue a phone reaches only its paired machine's own data: `/api/fleet/needs-you`, `@env/name` proxying and `/ws/linked/:env/rpc` keep answering 403 to a phone. The phone surface inventory lists them as "deferred to PAN-4887".
- **D-7 Rule for adding scope rows.** Add a row only when (a) the phone screens cannot do their core job (boot, Needs-you, read a conversation, send a message, answer a question or approval, stop a turn) without it and (b) the response holds no configuration secret. Everything else stays `admin`, and the app (W-APP1) hides the control or tolerates the 403 (epic NFR-4). This is why `GET /api/settings`, `GET /api/color-themes`, the model-picker reads and the long tail stay `admin`. `POST /api/conversations/:name/delete-image` gets `tell` because it is the undo of `upload-image` (`tell`) in the same composer.
- **D-8 Rows widen linked machines and tokens too.** The new rows also let a linked machine's operator token and any API token with those scopes call them. That is intended: they grant reads of state and events the token already holds as scopes, and `delete-image` pairs with `upload-image`. The docs say so.
- **D-9 Self routes need `tell` and a phone credential.** The scope row (`tell`) lets the gate admit the request; the handler then requires `credential.kind === 'phone'` (else 403). `tell` is the narrowest scope every phone holds that is not a read scope.
- **D-10 The phone routes live in a new module** `src/dashboard/server/routes/phones.ts`, exporting `phonesRouteLayer`, registered in `server.ts` next to `machinesPeerRouteLayer` (line 447). Handlers are exported functions taking the channel marker or credential, so tests call them directly (the `handleMachinesExchange` pattern).
- **D-11 The device list gains `kind`, not `platform`.** The label already says "iPhone" or "Android phone" (account-service default labels, epic W-ACC1). Adding a parsed platform field is not needed.
- **D-12 Self-revoke closes the caller's own channel.** As with `DELETE /api/machines/self`, the response may not reach the phone. The app treats a dropped connection after `DELETE /api/phones/self` as success (stated in the docs and in continue.json for W-APP1).
- **D-13 `remote-access/config.ts` is unchanged.** `require_token_mint` protects against a local reverse proxy making remote visitors look local. A phone arrives only through a secure channel, which is never a trusted local caller (`remote-request-gate.ts:150`), so phones add no auto-mint reason.

## Hazards

- **H-1 Registry downgrade.** A version without `phone` support treats a file with a phone record as corrupt and accepts no token. Same accepted trade-off as `machine` records (PAN-4645 H4). Documented in the `access-tokens.ts` header.
- **H-2 Origin headers from the phone.** `validateOriginHeaders` rejects a present, untrusted `Origin` before any credential check, on HTTP mutations and on the `/ws/rpc` upgrade. The phone's channel HTTP and WebSocket client (W-WEB2) must send no `Origin` or `Referer` header. The machine does not add `capacitor://localhost` to its trusted origins.
- **H-3 Self-revoke response.** `DELETE /api/phones/self` closes the caller's own channel, so the response may not arrive. W-APP1 treats a dropped connection after this call as success.
- **H-4 Admin-only boot calls.** `GET /api/settings`, `GET /api/color-themes` and the other inventory-B requests answer 403 to a phone. W-APP1 must tolerate these at boot (telemetry, design language, color theme reconcile) and hide the controls that need them.
- **H-5 Linked machines.** Until PAN-4887 lands, a phone sees only its paired machine's own Needs-you and conversations. Fleet Needs-you answers 403.
- **H-7 Re-pairing with the same key.** Refused with 409 by D-2, because revoking the old record would destroy the live pairing channel. W-APP1 must generate a fresh link key for each pairing. `grantMachineLink` revokes a same-environment machine record during the machine exchange and may have the same self-close effect; that is out of scope here and not changed.
- **H-6 Two phone records for one key.** Prevented by D-2. If a hand-edited file holds two, `findActiveChannelTokenByKey` returns the first active match; resolution then uses the presented token's own record, which still must match the channel key, so no privilege mix-up results.

## Acceptance criteria

- **AC-1 (WI-1):** a phone record with `phoneKey`, `clientId` and `pushKey` round-trips through the registry; `createAccessToken` rejects `admin` and `forward` on a phone; a phone record missing `clientId` makes the registry accept no token; `findActiveChannelTokenByKey` returns active machine and phone records by key and ignores revoked ones.
- **AC-2 (WI-2):** a phone token resolves to `{ kind: 'phone' }` only in a link channel from its `phoneKey`; it resolves to `null` from another key, in a pairing channel and on a plain socket; a phone POST through `rejectUnsafeDashboardMutationRequest` with no CSRF header returns `null`, and a device cookie POST without CSRF still returns 403.
- **AC-3 (WI-3):** `server.ts` passes `findActiveChannelTokenByKey` to `isPinnedPeer`; a link handshake from an active phone key completes and from a revoked phone key is refused with `unknown-peer`.
- **AC-4 (WI-4):** revoking a phone record closes its `/ws/rpc` connection with 4401 and calls `closeChannelsForPeer(phoneKey)`, both in process and after a registry refresh.
- **AC-5 (WI-5):** `requiredScopeFor` returns `read:state` for `GET /api/activity`, `read:conversations` for `GET /api/conversations/pending-input`, `tell` for `POST /api/conversations/c1/delete-image`, `PUT /api/phones/self/push-key` and `DELETE /api/phones/self`; `RPC_METHOD_SCOPES` maps `pan.getSnapshot` to `read:state` and `pan.replayEvents` to `read:events`.
- **AC-6 (WI-6):** `route-scopes-phone.test.ts` passes: every inventory-A request is satisfied by `PHONE_TOKEN_SCOPES`, the named inventory-B requests require `admin`, and `allowedRpcTags(PHONE_TOKEN_SCOPES)` includes the four boot/stream tags and none of the six named admin tags.
- **AC-7 (WI-7):** `POST /api/phones/exchange` in a pairing channel returns `{ v: 1, token, tokenId, descriptor }` and persists one active phone record bound to the channel key; it returns 403 outside a pairing channel at the handler and 401 at the gate; a repeat exchange with the same `clientId` and a new key leaves exactly one active record; a key already held by an active phone returns 409.
- **AC-8 (WI-8):** `DELETE /api/phones/self` revokes only the calling phone and closes its channels; `PUT /api/phones/self/push-key` replaces its `pushKey`; both return 403 to `machine`, `device` and missing credentials.
- **AC-9 (WI-9):** `GET /api/devices` returns phone rows with `kind: 'phone'` and no key material; `DELETE /api/devices/<phone id>` revokes the phone and closes its channels.
- **AC-10 (WI-10):** the Devices panel shows "Phone app" on phone rows and unchanged rows for devices.
- **AC-11 (WI-11):** `GET /api/environment` returns `capabilities.phoneApp: true`, and a descriptor without the field still decodes.
- **AC-12 (WI-12):** both developer docs carry a "Phone credentials (PAN-4835)" section stating the channel binding, the eight scopes, the three routes, the no-Origin rule and the PAN-4887 limit.
- **Epic AC-7 mapping:** "works only inside a link channel from its key" = AC-2, AC-3; "carries no admin" = AC-1, AC-6; "needs no CSRF" = AC-2; "reaches every request the mobile screens make" = AC-5, AC-6 for the paired machine (linked machines are PAN-4887); "revocation by the operator or by `DELETE /api/phones/self` closes its sockets within 5 s" = AC-4, AC-8, AC-9.

## Non-goals

- Phone access to linked machines (fleet routes, `@env` proxy, `/ws/linked`) — PAN-4887.
- The Settings "Set up the phone app" QR dialog (epic W-MAC2), native push delivery and use of `pushKey` (W-MAC3), any directory or contracts frame (W-CON1/2/3), the phone app itself (W-APP1), and the channel HTTP client and shims (W-WEB2).
- New scope rows for `GET /api/settings`, `GET /api/color-themes`, model-picker reads, push routes or any other inventory-B request.
- A `KIND` column in `pan devices list`, and offline (`dashboard not running`) revocation of phones in `pan devices revoke` (its fallback still finds `device` records only; with the dashboard running the route revokes phones).
- Trusting `capacitor://localhost` or any phone origin.
- Changes to `remote-access/config.ts` auto-mint reasons (D-13).
- Counting phones in `GET /api/anywhere/status` `devices.active` (`routes/anywhere.ts:116` keeps counting browser devices; the Devices panel lists both).
- User-facing Mintlify pages (`configuration/phone-app.mdx` and the others in epic W-DOC).
