# PAN-4479 — Shared Sessions v0 (slice 8): host reconnect and viewer auto-restore

**Issue:** [PAN-4479](https://github.com/eltmon/overdeck/issues/4479). **Parent PRD:** `.pan/drafts/pan-658.md` (revision 3), sections *Link Lifecycle & Disconnect/Reconnect* (FR-12), *Data Model → Host-side persistence*, *Room rules*. **Sibling PRDs read:** `.pan/drafts/PAN-4473.md` (slice 2, D-1, D-15), `.pan/drafts/PAN-4474.md` (slice 3, D-12, D-15), `.pan/drafts/PAN-4475.md` (slice 4, D-5, D-8, D-10, D-11).
**Status:** Planned (auto planning, 2026-11-03). **Depends on:** PAN-4475 (merged as `5d941630c45`).

## Glossary

| Term | Meaning |
| --- | --- |
| **Share service** | The Cloudflare Worker `services/share/` with one `ShareRoom` Durable Object per room (slice 1). It holds the room record (participants, controller, block list) in storage and ends a room 5 minutes (`HOST_RECONNECT_WINDOW_MS = 300_000`, `services/share/src/room-state.ts`) after the host socket goes away. |
| **Host socket** | The WebSocket the host's dashboard server keeps open to `GET /v1/rooms/:code/host?v=1` with `Authorization: Bearer <hostToken>`. Owned by `ShareManager` in `src/dashboard/server/services/share-host.ts`. |
| **Join socket** | The WebSocket the viewer's dashboard server keeps open to `GET /v1/rooms/:code/join?v=1` with the viewer's device token. Owned by `JoinManager` in `src/dashboard/server/services/share-join.ts`. |
| **Share record** | One entry of `${OVERDECK_HOME}/shared-sessions.json` (mode 0600), written by `src/lib/sharing/share-record.ts`: `{ scopeKind, scopeId, hostToken, joinUrl, createdAt }`, keyed by short code. It survives a dashboard restart. |
| **Re-park** | Opening the host socket again for a share record after a **dashboard process restart**, when this process has no host entry for that code. New in this slice: `ShareManager.resume()`. |
| **Reconnect** | Opening the host socket (or join socket) again **in the same process** after it closed unexpectedly. New in this slice. |
| **Backoff table** | `SHARE_RECONNECT_DELAYS_MS = [1_000, 2_000, 4_000, 8_000, 15_000, 30_000]`. Attempt *n* (0-based) waits `table[min(n, 5)]` ms, so after the fifth failure every attempt waits 30 s. The attempt counter resets to 0 when the host receives a `room` frame or the viewer receives any `status` frame. |
| **Peer hub** | `PeerHub` in `src/dashboard/server/sharing/peer-hub.ts`: one per host entry, one werift `RTCPeerConnection` per eligible viewer. |
| **Host-admitted set** | `PeerHub.hostAdmitted`: the GitHub ids the hub will serve content to (slice-3 D-12). Fed by `hub.admit(id)`; a snapshot can only remove ids. A new process starts with an empty set. |
| **Eligible viewer** | In the host-admitted set **and** listed in the latest snapshot as `state: 'admitted'` and `connected: true`. `PeerHub.reconcile()` starts a peer (a new offer) for every eligible viewer that has none. |
| **Seated join** | A join that has received at least one `status` frame (`lobby` or `admitted`) since it was created by `JoinManager.join()`. Only a seated join reconnects automatically. |
| **Peer phase** | The browser peer's phase in `webrtc-viewer.ts`: `waiting`, `connecting`, `connected`, `lost`. `lost` = the connection failed or closed on its own. |
| **Window** | The 5-minute host-reconnect window enforced by the share service alarm. Inside it, the room and its admitted list survive; after it, the room is deleted and its short code answers 404. |

## Problem

Today a host share dies on the first hiccup. `ShareManager` never reconnects the host socket and never re-parks on boot (slice-2 D-1, comment at `share-host.ts` lines 10-13: "It is never reconnected and never re-parked on boot"). A 1006 close, a socket error, a pong timeout or a 5xx upgrade marks the share `disconnected` for good (`share-host.ts` `disconnect()`, line 394), and `ShareDialog` then tells the operator "End this share and create a new link". A dashboard restart (`pan reload`) loses every live share even though the room on the share service survives 5 minutes and the record file still holds the host token.

The viewer side has the matching gap: `JoinManager` turns any unexpected join-socket close into `disconnected` and the page shows **Rejoin** (slice-4 D-8, `share-join.ts` lines 285-298). The browser peer's `lost` phase shows a manual **Reconnect** button (slice-4 D-11, `SharedConversationView.tsx` lines 173-178).

There is also a content-gate gap: after a process restart a new `PeerHub` has an empty host-admitted set, and a snapshot can never add an id (slice-3 D-12), so even a re-parked host would never offer a peer to anyone. Slice-3 D-12 says: "Re-park after a restart, which must seed the set from the snapshot, is slice 8."

## Goal

Inside the 5-minute window, a host network drop or a host dashboard restart is invisible to admitted viewers except for the "Host disconnected — reconnecting…" banner: the host comes back on its own, its admitted viewers get a new offer and a fresh history, and nobody goes through the lobby again. After the window, the host clears the record and the link is dead; re-joining means a new share and the lobby. A viewer's own network drop restores the same way.

## Requirements

- **FR-1** After an unexpected host-socket loss in the same process (close other than 4004/4008, socket `error`, 75 s pong timeout, upgrade answered with a status other than 404/401), `ShareManager` keeps the share record and the peer hub, sets the share's `connection` to `'reconnecting'`, and opens a new host socket after the backoff table's delay; it repeats until a `room` frame arrives or a terminal answer comes.
- **FR-2** Terminal answers stop the reconnect loop: upgrade 404 or 401 and close 4004 drop the host entry (closing the hub) and remove the record; close 4008 sets `connection: 'disconnected'` with `lastError.code = 'replaced'`, keeps the record, and does not retry.
- **FR-3** On dashboard boot, a primary dashboard (`hostsMachineLinks()` true) re-parks every share record that has no host entry in this process, with no user action and no account read.
- **FR-4** The first `room` frame a re-parked host receives seeds its peer hub's host-admitted set with every participant whose `state` is `'admitted'`, exactly once, before the hub reconciles; a host opened by `create()` or reconnected in the same process is never seeded.
- **FR-5** After a re-park or a reconnect, every admitted, connected viewer gets a new host offer and a fresh `history` without passing through the lobby (no `status lobby` reaches it).
- **FR-6** After the window, a re-park gets upgrade 404: the host removes the record and `GET /api/shares` no longer lists the share; a viewer that joins again joins a new share and lands in `lobby`.
- **FR-7** The host share dialog shows "Reconnecting to the share service…" while `connection` is `'reconnecting'`, and the lobby actions stay disabled.
- **FR-8** A seated join whose join socket closes unexpectedly (close code not in `CLOSE_STATES`, socket `error`, pong timeout, upgrade status other than 404/401/403) becomes `'reconnecting'` with `error` set to `connection_lost`, `unreachable` or `http_<status>`, and `JoinManager` opens a new join socket on the backoff table. The service restores an admitted viewer as `admitted` (no lobby); a lobby viewer returns to `lobby`.
- **FR-9** A join that never got a `status` frame keeps today's behaviour: an unexpected close, error or upgrade failure gives `disconnected` and the page offers **Rejoin**.
- **FR-10** The viewer page treats `'reconnecting'` as live: **Leave** stays, the browser peer is kept, and the screen shows the banner "Reconnecting to the share service…" above the kept timeline (or a panel with that text when no history arrived yet).
- **FR-11** The viewer page keeps the timeline visible while a new host offer is negotiating (`hasHistory` true), instead of falling back to "Connecting to the host…".
- **FR-13** **End share** on a share that is not `connected` (no host entry, `connecting`, `reconnecting` or `disconnected`) forgets it locally when the share service cannot be reached: an invalid `anywhere.share_url` or a failed `deleteRoom` drops the host entry, removes the record and answers 204. A `connected` share keeps today's 500 `share_url_invalid` / 502 `share_service_error` answers and its record.
- **FR-12** When the browser peer becomes `lost` while the join is `admitted`, the page opens a new event stream after 5 s without clearing its messages (which restarts the join socket per slice-4 D-5, so the host offers again), at most 3 times in a row; the count resets when the peer reaches `connected`; after the third try the manual **Reconnect** banner stays.

Non-functional:

- **NFR-1** Every delay in this slice is a `setTimeout` with `unref()`, cleared on terminal states, `end()`, `leave()` and `stop()`. Unit tests use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`; integration tests inject `reconnectDelaysMs: [0]` and never sleep (repo rule: fake timers for retry/backoff tests).
- **NFR-2** No new `execSync`, no sync file reads in server code; `resume()` never throws and never blocks boot (called with `void … .catch`).
- **NFR-3** The host token and device token never appear in a `ShareView`, `JoinView`, `JoinEvent` or log line (slice-2 NFR-1 unchanged).
- **NFR-4** `packages/contracts/src/sharing.ts` stays type-only with no `import` (D-R3-8).
- **NFR-5** `src/dashboard/server/main.ts` (986 lines on `origin/main`, ceiling 1000) grows by at most 2 lines.

## Decisions

- **D-1 Reconnect keeps the hub.** A same-process reconnect reuses the existing `ShareHost` entry and its `PeerHub` (slice-3 D-15 already keeps peers across a host-socket loss). The host-admitted set is still valid because nothing can admit while the host socket is down (D-R3-3: admission frames come only from the host socket). The next `room` frame reconciles: peers that died during the outage are re-offered, live peers are untouched.
- **D-2 Backoff table, no give-up.** `SHARE_RECONNECT_DELAYS_MS = [1_000, 2_000, 4_000, 8_000, 15_000, 30_000]`, last value repeats, counter resets on success. There is no attempt limit: the host cannot know from its own clock whether the service's 5-minute alarm has fired (the service measures from when *it* saw the close), so only the service's answer (404 or 4004) ends the loop. A share stuck reconnecting is visible in the dialog and **End share** still works. The constant lives in `share-host.ts` and `share-join.ts` imports it, the same way it already imports `PING_INTERVAL_MS` and `PONG_TIMEOUT_MS`.
- **D-3 Re-park on boot, primary dashboard only.** `main.ts` calls `getShareManager().resume()` right after `startAnywhere` at line 224, gated on `hostsMachineLinks()` (`src/lib/boot-gates.ts`). A peer dashboard that shares `~/.overdeck` must not re-park, because two processes parking the same room replace each other with close 4008. `resume()` reads the record file and `anywhere.share_url` only; it needs no account (the host token authenticates). A bad share URL or an unreadable record file skips re-park silently (the records stay; the dialog shows them `disconnected`).
- **D-4 Seed the content gate from the first post-restart snapshot.** This is the exception slice-3 D-12 reserved for this slice, and the parent PRD's data model requires it ("Participants … are not stored on the host … the host reads them from the room snapshot on every park"). It does not weaken the trust model: the service admits a viewer only on an `admit` frame from the host socket (D-R3-3), so the snapshot's admitted list is this host's own prior decisions as persisted by the service, and the service already relays the SDP that carries the DTLS fingerprints (D-R3-1), so it is a trust root either way. Seeding is exactly once per re-parked host entry (`restoring` flag), only `state === 'admitted'` participants, and implemented in `ShareManager.onFrame` with the existing `hub.admit(id)` call, so `PeerHub` code does not change (only its header comment).
- **D-5 No retry on 4008.** Close 4008 means another host socket for this room connected (another dashboard on the same home, or a second `resume()`); retrying would ping-pong. The share becomes `disconnected` with `lastError.code = 'replaced'`, as today.
- **D-6 `ShareConnection` gains `'reconnecting'`; `JoinState` gains `'reconnecting'`.** Distinct values make the state observable in the API, the UI and the tests. Both are live (`isLive` in `share-host.ts`, `LIVE_STATES` in `share-join.ts`, `LIVE_JOIN_STATES` in `useSharedJoin.ts`). `JoinState 'disconnected'` stays for joins that were never seated (FR-9).
- **D-7 Only a seated join auto-reconnects.** A first connect that fails (share service down, bad network) shows the explicit **Rejoin** screen instead of an endless spinner; a join that has been in the room or the lobby reconnects on its own.
- **D-8 The viewer's peer-lost auto-reconnect lives in the page, bounded.** `useSharedJoin` restarts the event stream (slice-4 D-5 restart, so the service flips `connected` and the host re-offers) 5 s after the peer goes `lost` while the join is `admitted`. Bound: 3 consecutive tries (`PEER_AUTO_RECONNECT_MAX = 3`, `PEER_AUTO_RECONNECT_DELAY_MS = 5_000`, exported from `useSharedJoin.ts`). It does not fire while `host-disconnected` or `reconnecting` (the host's own re-offer restores those). It keeps messages (no `resetContent()`), so the timeline does not blank. Rationale: if a host's network drop kills the peers but not the host socket, no new snapshot arrives and the hub never re-offers; this is the only automatic path back.
- **D-9 "After the window" is proven by a deleted room.** Miniflare does not fire a Durable Object alarm 5 real minutes later inside a test, and nothing may sleep. The reducer's `alarm` past the window and `DELETE` share the same `end` branch (`room-state.ts` *Room rules*: "`host-frame end`, `delete` → status ended …"; the alarm path is covered by `tests/unit/services/share/room-state.test.ts` `describe('alarm')`, line 137). The integration test ends the room with `deleteRoom()` while the host is down, then re-parks.
- **D-10 Integration delays are injected.** `ShareManagerDeps` and `JoinManagerDeps` gain an optional `reconnectDelaysMs?: readonly number[]` (default `SHARE_RECONNECT_DELAYS_MS`). Integration tests pass `[0]`.
- **D-12 End forgets an unreachable, unconnected share.** With no give-up (D-2) and `'reconnecting'` counted as live (D-6), `create()` returns a reconnecting share as `existing`, so **End share** is the operator's only way out. If **End share** failed whenever the service is unreachable, a share stuck reconnecting (service down, or `anywhere.share_url` broken after creation) could never be removed from the UI. So `end()` forgets a not-`connected` share locally when the service call fails, as slice-2 D-3 already does for stale records in `createRoomFor`. The room, if it still exists, ends itself on the service's 5-minute alarm because no host returns. A `connected` share keeps 502, because the operator can retry and the room is reachable.
- **D-11 No shutdown hook.** On SIGTERM the process exits and the OS closes the host socket; the service sees the close and starts the window, which is exactly what a restart needs. `ShareManager.stop()` is not added to `main.ts` shutdown (it would not change the service's behaviour and costs ceiling lines).

## Design

### Host: `ShareManager` (`src/dashboard/server/services/share-host.ts`)

**Before** (`share-host.ts` lines 88-99, 273-328, 393-398):

```ts
interface ShareHost {
  readonly shortCode: string;
  readonly record: ShareRecord;
  readonly socket: ShareSocket;
  connection: ShareConnection;
  // …
}
// openHost: const current = () => this.hosts.get(shortCode) === host && host.connection !== 'disconnected';
// close (not 4004): if (code === CLOSE_REPLACED) host.lastError = …; this.disconnect(host, 'none');
// error / non-404 upgrade / pong timeout: this.disconnect(host, 'terminate');
private disconnect(host: ShareHost, how: 'terminate' | 'none'): void {
  host.connection = 'disconnected';
  this.stopKeepalive(host);
  if (how === 'terminate') this.shut(host.socket, 'terminate');
}
```

**After** (shape; match the file's style):

```ts
export const SHARE_RECONNECT_DELAYS_MS: readonly number[] = [1_000, 2_000, 4_000, 8_000, 15_000, 30_000];

export interface ShareManagerDeps {
  // … existing …
  /** Reconnect backoff (D-2); tests pass [0]. Default SHARE_RECONNECT_DELAYS_MS. */
  reconnectDelaysMs?: readonly number[];
}

/** One host socket; `done` is set once the manager stops listening to it. */
interface HostConnection {
  readonly socket: ShareSocket;
  done: boolean;
}

interface ShareHost {
  readonly shortCode: string;
  readonly record: ShareRecord;
  readonly base: string;            // share service URL used for every (re)connect
  conn: HostConnection;
  connection: ShareConnection;
  snapshot: RoomSnapshot | null;
  lastError: ShareLastError | null;
  pingTimer: NodeJS.Timeout | null;
  pongTimer: NodeJS.Timeout | null;
  retryTimer: NodeJS.Timeout | null;
  /** Failed connects since the last `room` frame; indexes the backoff table. */
  attempt: number;
  /** Re-parked by resume() and no `room` frame yet: the first one seeds the hub (D-4). */
  restoring: boolean;
  hub: HostHub | null;
}
```

Rules, in order of the code:

1. `openHost(base, shortCode, record, restoring: boolean)` builds the entry (`connection: 'connecting'`, `attempt: 0`, `retryTimer: null`), creates the hub once (as today), then calls `connect(host)`.
2. `connect(host)` opens `deps.openSocket(hostSocketUrl(host.base, code), { Authorization: Bearer <hostToken> })`, stores `host.conn = { socket, done: false }`, and attaches listeners. Every listener first checks `current()` = `!conn.done && host.conn === conn && this.hosts.get(code) === host`.
   - `open` → `startKeepalive(host, conn)`.
   - `message` (text) → `onFrame(host, text)`.
   - `pong` → `armPongDeadline(host, conn)`; the pong deadline fires `lose(host, 'terminate')` only if `!conn.done && host.conn === conn`.
   - `unexpected-response` 404 or 401 → `dropHost(code, 'terminate')` + `removeRecord(code)`. Any other status → `lose(host, 'terminate')`.
   - `close` 4004 → `dropHost(code, 'none')` + `removeRecord(code)`. Close 4008 → `conn.done = true`, `stopKeepalive`, `connection = 'disconnected'`, `lastError = { code: 'replaced', at }` (no retry, D-5). Any other code → `lose(host, 'none')`.
   - `error` → `lose(host, 'terminate')`.
3. `lose(host, how)`: `conn.done = true`; `stopKeepalive(host)`; if `how === 'terminate'` shut the socket; `connection = 'reconnecting'`; delay = `delays[Math.min(host.attempt, delays.length - 1)]`; `host.attempt += 1`; `host.retryTimer = setTimeout(…, delay)` with `unref()`. The timer callback clears `retryTimer` and calls `connect(host)` only if `this.hosts.get(code) === host && host.connection === 'reconnecting'`.
4. `onFrame` `room`: set `snapshot`, `connection = 'connected'`, `attempt = 0`; if `restoring`: set it `false`, then `hub.admit(p.githubId)` for every `p` in `snapshot.participants` with `p.state === 'admitted'`; then `hub.onSnapshot(snapshot)` (as today).
5. `sendHostFrame` and `command()` use `host.conn.socket` and refuse when `host.conn.done` or `connection !== 'connected'` (`command` keeps its 409 `share_not_connected`).
6. `dropHost` also clears `retryTimer`. `stop()` (unchanged signature) therefore clears every retry timer.
7. `isLive` stays `connection !== 'disconnected'`, so a `'reconnecting'` share is returned by `create()` as `existing` and is not replaced.
8. New public method:

```ts
/**
 * Re-parks every recorded share this process does not host yet (D-3). Reads the record file and
 * anywhere.share_url only; never throws. Returns the short codes it opened.
 */
async resume(): Promise<string[]> {
  let records: Record<string, ShareRecord>;
  try {
    records = await this.deps.records.read();
  } catch {
    return [];
  }
  const codes = Object.keys(records).filter((code) => !this.hosts.has(code));
  if (codes.length === 0) return [];
  let base: ShareUrlResult;
  try {
    base = await this.deps.readShareUrl();
  } catch {
    return [];
  }
  if ('error' in base) return [];
  const opened: string[] = [];
  for (const code of codes) {
    try {
      this.openHost(base.url, code, records[code] as ShareRecord, true);
      opened.push(code);
    } catch {
      // openSocket threw synchronously (for example a malformed URL): forget this entry, keep the record.
      this.dropHost(code, 'none');
    }
  }
  return opened;
}
```

9. `end(shortCode)` (lines 197-208): read `const host = this.hosts.get(shortCode)` and `const offline = host?.connection !== 'connected'` before calling the service. When `readShareUrl` answers an error or `deleteRoom` answers `ok: false`: if `offline`, `dropHost(shortCode, 'close')`, `await records.remove(shortCode)`, return `{ status: 204 }` (D-12); otherwise return today's 500/502 unchanged.
10. Update the file header comment (lines 10-13) to: "Lifecycle: the host socket opens right after the room is created and its record written, and `resume()` re-parks every record on boot (PAN-4479). An unexpected loss reconnects on `SHARE_RECONNECT_DELAYS_MS` and keeps the hub; close 4004 or a 404/401 upgrade removes the record; close 4008 stops (another host socket holds the room)."

`ShareView` building (`viewOf`) is unchanged; `connection` now can be `'reconnecting'`.

### Viewer server: `JoinManager` (`src/dashboard/server/services/share-join.ts`)

New `Join` fields: `seated: boolean` (false in `openJoin`), `attempt: number` (0), `retryTimer: NodeJS.Timeout | null` (null). `JoinManagerDeps` gains `reconnectDelaysMs?: readonly number[]`. `LIVE_STATES` (line 87) adds `'reconnecting'`.

1. `onFrame` `status` (any value): set `join.seated = true` and `join.attempt = 0` before the existing state mapping.
2. Unexpected loss in `listen()` (lines 277-298) and the pong deadline (lines 472-480):
   - `unexpected-response`: 404 → `ended`; 401/403 → `rejected` (unchanged). Other status: `seated` → `scheduleReconnect(join, 'http_<status>')`; not seated → `disconnected` `http_<status>` (unchanged).
   - `close` after `settleIntent` returned false: a code in `CLOSE_STATES` → that state (unchanged). Any other code: `seated` → `scheduleReconnect(join, 'connection_lost')`; else `disconnected` `connection_lost`.
   - `error` after `settleIntent` returned false: `seated` → `scheduleReconnect(join, 'unreachable')`; else `disconnected` `unreachable`.
   - Pong deadline: `seated` → `scheduleReconnect(join, 'connection_lost')`; else `disconnected` `connection_lost`. (A pong deadline only runs after `open`, so in practice the join is usually seated.)
3. `scheduleReconnect(join, error)`: `finishConnection(join, 'terminate')` (no-op if already done); `resolveIce(join, [])`; `setState(join, 'reconnecting', error)`; delay = `delays[Math.min(join.attempt, delays.length - 1)]`; `join.attempt += 1`; `join.retryTimer = setTimeout(() => this.reconnectNow(join), delay)` with `unref()`.
4. Split today's `reopen()` (lines 369-378) into `openNextSocket(join)` (generation + 1, clear `pendingSignals`, `subscribedThisGeneration = subscriber !== null`, `resolveIce(join, [])`, new `conn`, `listen`) and `reopen(join)` = `restarting = false; openNextSocket(join); setState(join, 'connecting')` (behaviour unchanged). `reconnectNow(join)`: clear `retryTimer`; if `this.joins.get(code) !== join || join.state !== 'reconnecting'` return; `openNextSocket(join)` and **keep** state `'reconnecting'` (the next `status` frame sets it).
5. `clearRetry(join)` is called from `setState` when the new state is not live, from `stop()`, and from the grace path.
6. Grace timer (lines 380-404): inside the timeout, before the `join.conn.done` early return, add: if `join.state === 'reconnecting' && join.conn.done` (waiting between attempts) → `clearRetry(join)`, `setState(join, 'away')`, return. A reconnect attempt whose socket is open follows the existing close-with-`away` path.
