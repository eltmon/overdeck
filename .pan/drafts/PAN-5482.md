**`pan reload` vs `pan restart`.**
- `pan reload` (`src/cli/commands/reload.ts`): builds from `origin/main` (anchor
  `buildDashboardFromOriginMain`), not your local branch; checks the build; waits at the approval gate; then
  restarts. A failed build or health check leaves the old dashboard running. It refuses during a
  `pan shutdown` drain, refuses `--no-deacon`, and refuses while a restart hold is set. Under `pan dev` it does
  an in-place hot restart instead. It keeps the running dashboard's auto-resume setting unless `--resume` or
  `--no-resume` is given. Do not mention `--force` (no-op, PAN-5550).
- `pan restart` (`src/cli/commands/restart.ts` anchor `restartCommand`): never builds. Scopes `--dashboard`
  (default), `--cliproxy`, `--traefik`, `--full`. Only the dashboard and full scopes wait at the approval gate
  and obey the hold. `--no-resume` turns off crash auto-resume for that boot. The supervisor watchdog's own
  restart skips the gate and the hold.
- Decision rule for the page: to ship new code, use `pan reload`; to relaunch the build you already run, use
  `pan restart`. Help texts with dashes to paraphrase: `pan reload --health-timeout`, `pan restart`
  description, `--health-timeout`, `--resume`; `pan shutdown` uses an en dash in "10–3600".
- `cli/core-commands.mdx` (near lines 234 to 296) has the flag tables: link it rather than repeat them.

**Approval gate and restart hold (two mechanisms, one banner).**
- Gate (`src/dashboard/server/services/restart-gate.ts`, client `src/lib/restart-gate-client.ts`): every
  voluntary restart (`pan reload`, `pan restart` for the dashboard or full scope, the post-merge deploy) waits
  with no timeout. One approval satisfies every waiting request with a single restart. If the gate is missing
  or the dashboard health check fails for 60 seconds, the requester restarts without approval. Approve with the
  banner's `Restart now` button, `pan restart approve`, or `pan restart --now` (approves and restarts at once).
- Banner (`FE/components/RestartApprovalBanner.tsx`): "A dashboard restart is waiting for your approval" (or
  "N dashboard restarts are waiting for your approval") with `Restart now`; while a hold is set it shows
  "Restarts on hold" plus the reason and a lock icon, with no button. The other banner strings contain em
  dashes: paraphrase.
- Hold (`src/lib/restart-hold.ts`, `src/cli/commands/restart-hold.ts`): `pan restart hold --reason "<text>"
  [--until <when>]` (`--until` takes `30m`, `2h`, `1d` or an ISO time in the future; `--reason` is required);
  `pan restart hold --status`; `pan restart release`. Stored in `~/.overdeck/restart-hold.json`. An expired hold
  counts as released; an unreadable file counts as an active hold. It refuses `pan reload`, dashboard and full
  `pan restart` (including `--now`), `pan restart approve` and banner approvals, with the message
  "Refusing to ...: the operator restart hold is active" and "--now and --force do not bypass the hold." It does
  not block `--cliproxy`, `--traefik` or the watchdog. On release it prints that a reload refused during the
  hold was not queued: run `pan reload` to ship what merged meanwhile.

**Crash auto-resume (PAN-5354).**
- `src/lib/cloister/crashed-work-resume.ts` (header comment), run by the Deacon every 60 seconds. It resumes a
  **work** agent whose pane died with no recorded stop, only when: the agent was seen dead on two checks at
  least 45 seconds apart; nobody stopped it on purpose; it is not paused, troubled or in failure backoff; its
  issue is open and not merged; the Deacon is not frozen and the dashboard was not started with `--no-resume`;
  and memory pressure is normal. At most one resume every 45 seconds, oldest first, one attempt per crash.
- On failure Needs you shows "work agent X crashed and its automatic resume failed: (reason). Fix the cause,
  then run pan resume X."; when a gate blocks it: "...was not resumed automatically: (reason). Run pan resume X
  to resume it." Log: `~/.overdeck/logs/deacon.log`, lines prefixed `[deacon-lite]`.
- Turn it off: `pan up --no-resume` or `pan restart --no-resume`; the emergency-stop freeze also stops it.
- Conversations are never auto-resumed. After a terminal-backend (Herdr) restart, Needs you offers
  "N conversations stopped when the terminal backend restarted" with `Resume all` / `Dismiss` (link
  `/features/conversations`, its "After a terminal-backend restart" section). That offer is kept in memory
  only, so after a host crash or reboot there is no conversation offer. After `pan shutdown`, Needs you offers
  "Resume the N sessions shutdown stopped" (link `/features/safe-shutdown`).
- Manual tools: `pan resume <id>` and `pan recover [id]` (link `/cli/agent-commands`).

**Backups.**
- Scope: only the `~/.claude/skills`, `~/.claude/commands` and `~/.claude/agents` folders that `pan sync`
  writes. **Nothing backs up the Overdeck database or `~/.overdeck` state.** Say so plainly.
- `pan sync` makes a backup first when `backup_before_sync` (default `true`) is set under `[sync]` in
  `~/.overdeck/config.toml` (a TOML file, separate from `config.yaml`; `src/cli/commands/sync.ts` anchor
  `backupBeforeSync`), then keeps the newest `backup_keep` (default 10) (`src/lib/backup.ts` anchor
  `DEFAULT_BACKUP_KEEP`). `pan sync --backup-only` makes a backup without syncing. Backups live in
  `~/.overdeck/backups/<timestamp>`, with timestamps like `2026-11-18T21-03-10-797Z`.
- `pan backup list [--json]`; `pan backup clean [--keep <count>]` (default 10).
- `pan restore [timestamp]`: with no timestamp it lists the 10 newest to pick from; it always asks for
  confirmation (default No) and has no `--yes`; it replaces the target folder with the backup copy. Today it
  restores skills and commands only, not agents (PAN-5549, see re-check rule).

### G17: CI integrations

**CI tests mode** (`src/lib/cloister/verification-tests-mode.ts`).
- `projects.yaml`, per project: `verification: { tests: ci }` or `local` (anchor
  `export type VerificationTestsMode`). Any other value is ignored with a warning and detection runs.
- Unset: `ci` when a GitHub Actions workflow in the project (or in a polyrepo member under `workspace.repos`)
  runs a test job on pull requests to the PR base, or on pushes to a feature branch; otherwise `local`. A test
  job is one whose check name (its `name:`, else the job id) is `test`, `tests`, `test (...)`, `test-...`,
  `test:...` or `test / ...` (anchor `isCiTestCheckName`). Not evaluated: `paths` filters, most `if:`
  expressions, and the inside of reusable workflows. Re-detected when `projects.yaml` or a workflow file
  changes. No GitHub repo configured means `local`.
- In CI mode the host skips only the gate named exactly `test`; `typecheck`, `lint` and custom gates still run
  (anchor `selectLocalVerificationGates`). The commit status `overdeck/test` reads "Verification gate passed
  (typecheck+lint; tests run on CI)".
- Merge needs at least one test check concluded success on the PR head; none, or only skipped, blocks the
  merge (`docs/PIPELINE-GATES.md` near lines 233 to 240). A red test job goes back to the work agent as a
  verification failure and counts against the same 3-attempt budget; a failure that also fails on `main` does
  not count. The relayed text contains an em dash: paraphrase.
- GitLab with `tests: ci` gets the merge gate but no automatic agent feedback (`PIPELINE-GATES.md` near 483).
- A custom gate must not be named `test` or CI mode drops it (`configuration/projects.mdx` dbt section).
- There is no dashboard control for `verification.tests`.

**Dagger Cloud** (PAN-4589, v0.70.0). Recognition only. Overdeck has **no** Dagger config key, token, secret or
generated workflow. Detection never switches to `ci` because of Dagger; it only notes "dagger.toml present", so
the project must set `verification.tests: ci` itself. Overdeck treats a commit status whose link is on
`dagger.cloud` and any of whose `/`-separated name parts is a test name (for example `go-client/test`) as a CI
test check, for the merge gate and for failure feedback (`isDaggerCloudUrl`, `isDaggerCloudTestCheck`). Not
test checks: `python-client/format`, `helm/lint`. Failure feedback includes a rerun line
`dagger check dag://<name>`. This needs the GitHub `status` webhook event. `configuration/auto-merge.mdx`
(near lines 225 to 229) already says this: link it.

**CodeRabbit.**
- Advisory, never blocking: `src/lib/advisory-checks.ts` anchor `ADVISORY_CHECK_NAMES`; CodeRabbit checks are
  left out of merge checks.
- A CodeRabbit review with inline comments on a `feature/` branch PR is relayed to the issue's work agent
  (`src/lib/coderabbit-feedback.ts`, login `coderabbitai[bot]`). The agent gets a findings file and answers
  each thread with a fix or a reply giving its reason; after code changes it runs
  `pan review request <id> -m "..."`. With no agent to receive it, Needs you shows it. A review posted while the
  dashboard is down is not relayed later.
- After merge, threads nobody answered become a follow-up issue titled "CodeRabbit follow-up for ...", created
  by the GitHub App (`src/lib/cloister/advisory-followup.ts`). The App needs **Issues: Read and write** on the
  repo, or Needs you reports the failure. **Do not name an assignee** (PAN-5548).
- `features/issue-pipeline.mdx` ("Feedback the work agent receives") already summarizes this: link it.

**`uat/**` batch workflow (merge train).**
- Batching needs a GitHub Actions workflow whose `name:` is exactly `CI` and that runs on pushes to `uat/**`
  (`src/dashboard/server/services/batch-auto-promote.ts` anchor `BATCH_CI_WORKFLOW = 'CI'`). If no such run
  appears within 10 minutes, Overdeck pauses batching for that project, merges its PRs one at a time, and
  retries batching a day later. Batch branches are named `uat/<label>-<codename>-<MMDD>`.
