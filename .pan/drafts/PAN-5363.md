# PAN-5363: Merge train board Train switch flips back on after turning it off

**Issue:** [PAN-5363](https://github.com/eltmon/overdeck/issues/5363)
**Status:** planned (auto mode, 2026-11-15)

## Glossary

- **Train switch** — the per-project `ToggleSwitch` in the header of `ProjectTrainCard` (test id `merge-train-switch-<projectKey>`). Off writes the project override `merge_train: disabled` to `~/.overdeck/projects.yaml`; on clears it (`null`).
- **Project override** — `ProjectConfig.merge_train?: 'enabled' | 'disabled'` (`src/lib/projects.ts`, field near line 490). Only `disabled` has an effect: `isMergeTrainEnabledForProject` (`src/lib/overdeck/merge-sync.ts:76-79`) returns `false` when the global flag is off or the project says `disabled`.
- **Master switch** — the global `merge_train_enabled` flag (`GET /api/merge-train/config`). Not touched by this issue.
- **Board** — `GET /api/merge-train/board[?project=<key>]`, the read model behind every `MergeTrain` placement. Each project row carries `override` (the raw project override) and `enabled` (master AND project), set in `projectIdentity` (`src/dashboard/server/services/merge-train-board.ts`, lines 188-189: `enabled: master && deps.projectEnabled(config),` / `override: config.merge_train ?? null,`).
- **Server board cache** — `boardCache`, a `createSettledTtlPromiseCache` with a 5 s TTL keyed by `projectKey ?? '*'` (`merge-train-board.ts:463-464`). A pending load is returned regardless of age; a settled one is reused for 5 s (`src/lib/concurrency.ts`, `createSettledTtlPromiseCache`). `invalidateMergeTrainBoardCache()` (`merge-train-board.ts:466-469`) drops every entry including in-flight ones (`includeInFlight: true`).
- **Board query keys (client)** — `MERGE_TRAIN_BOARD_KEY = ['merge-train', 'board']`; each placement is `[...MERGE_TRAIN_BOARD_KEY, projectKey ?? 'all']` (`src/dashboard/frontend/src/components/merge-train/train/useMergeTrainBoard.ts:20-24`).
- **Settings query key (client)** — `['project-merge-train', projectKey]`, read by the project settings disclosure from `GET /api/projects/:key/merge-train` (`src/dashboard/frontend/src/components/CommandDeck/ProjectSettingsDisclosure.tsx:328-336`).
- **Project train write** — the JSON answer of `POST /api/projects/:projectKey/merge-train`: `{ value: 'enabled' | 'disabled' | null, effective: boolean }` (`src/dashboard/server/routes/projects-merge-train.ts:53-56`). `effective` is `isMergeTrainEnabledForProject` of the updated config, so it equals the board's `enabled` for that project.
- **Cancel-with-revert** — TanStack Query 5.103.2 `queryClient.cancelQueries` defaults to `revert: true`, which resets the query to the state it had when the cancelled fetch started (`node_modules/.bun/@tanstack+query-core@5.103.2/.../build/modern/queryClient.js:276-283`, `query.js` `onCancel` → `setState({ ...this.#revertState })`). A cache patch made *before* a cancel is therefore undone by the cancel.

## Problem

On 2026-11-15 the operator turned the Train switch off for `overdeck`. The switch showed off, flipped back on, then off again a few seconds later. `projects.yaml` was written correctly; only the display was wrong for one poll cycle.

Verified cause (all references checked against `52e312dd0df`):

1. The switch value is the mutation argument only while the POST is pending (`ProjectTrainCard.tsx:71-73`):
   ```tsx
   const switchOn = trainSwitch.isPending && trainSwitch.variables !== undefined
     ? trainSwitch.variables
     : project.override !== 'disabled';
   ```
   `project` is a prop that `MergeTrain` passes from the board query.
2. `onSuccess: () => invalidate()` (`ProjectTrainCard.tsx:67`) returns nothing, and `useInvalidateBoard` voids `invalidateQueries` (`useMergeTrainBoard.ts:76-81`). The mutation settles the moment the POST resolves, so the switch reads the old cached `override: null` and shows **on**.
3. The refetch hits the server board cache. A load that started before the write is still in flight (single-flight) or still within its 5 s TTL, and each load reads `projects.yaml` once at its start (`merge-train-board.ts:473`, `d.listProjects()`). The refetch therefore returns the pre-click value.
4. `POST /api/projects/:projectKey/merge-train` never drops that cache. It calls `setProjectMergeTrain` at `projects-merge-train.ts:49` and returns. The only caller of `invalidateMergeTrainBoardCache` is the issue-policy write (`src/dashboard/server/services/merge-policy-write.ts:98`, `invalidateBoard: invalidateMergeTrainBoardCache,`).
5. The next 15 s poll (`useMergeTrainBoard.ts:63`) after the TTL returns a fresh read, and the switch goes back **off**.

Secondary: the project settings disclosure writes the same field. Its mutation invalidates only `['project-merge-train', key]` (`ProjectSettingsDisclosure.tsx:348`), and the board switch invalidates only the board prefix. A change in one place leaves the other showing the old value until its own poll.

Verified non-cause: the projects config read cache does not hide the write. `updateProjectsConfigAsync` calls `invalidateProjectsConfigCache()` after writing (`src/lib/projects.ts`, lines ~669 and ~681), and `loadProjectsConfigSync` also keys its cache on the file mtime (`projects.ts:603-616`). A board load that starts after the write reads the new value.

## Requirements

- **FR-1** — After `POST /api/projects/:projectKey/merge-train` writes the override, the server drops every cached and in-flight board read, so the next board read starts after the write.
- **FR-2** — The route does not drop the board cache when it does not write (auth rejection, unknown project 404, bad value 400).
- **FR-3** — After the Train switch POST succeeds, the switch shows the clicked value without a flicker: it never falls back to the pre-click cached value between the POST resolving and the next board response.
- **FR-4** — A board read that was in flight on the client when the write succeeded is discarded; it cannot overwrite the confirmed value.
- **FR-5** — One shared client helper applies a confirmed project train write: it patches the project's `override` and `enabled` in every cached board query, sets `['project-merge-train', key]` to the write, and invalidates both the board prefix and the settings key.
- **FR-6** — The board Train switch and the project settings disclosure's Merge train control both apply their successful writes through the FR-5 helper, so each refreshes the other.
- **FR-7** — `docs/MERGE-TRAIN.md` and `changelog.d/pan-5363.md` describe the new behavior.
- **NFR-1** — No new HTTP route, no change to the POST request or response shape, no change to `projects.yaml` semantics.
- **NFR-2** — A board response fetched after the write is authoritative. The client does not hold a local value against server data (no "hold until confirmed" state that could stick).
- **NFR-3** — The switch stays disabled only for the POST plus the cancel-and-patch step; it does not wait for the board refetch (an all-projects board read takes ~11 s on the live dashboard).

## Decisions

- **D1 — Server fix as the issue proposes.** Call `invalidateMergeTrainBoardCache()` right after `setProjectMergeTrain` resolves, in the route. *After*, not before: a load that started between an early invalidate and the write would read the old value. Rejected alternative: subscribe the board cache to `subscribeProjectsConfigInvalidation` (`src/lib/projects-cache-events.ts`), which would drop it on every `projects.yaml` write. It is broader than this bug, couples the board to unrelated config writes, and still would not cover CLI writes from another process.
- **D2 — Client: patch from the server's answer in `onSuccess`, not in `onMutate`.** The POST answer `{ value, effective }` maps 1:1 onto the board row's `{ override, enabled }`, so the patch is server-confirmed and needs no rollback. While the POST is pending the switch already shows `variables`. Patching in `onMutate` would add rollback code and could be overwritten by a poll landing during the POST.
- **D3 — Order inside the helper: cancel, then patch, then invalidate.** Because of cancel-with-revert (glossary), `await cancelQueries` must run *before* `setQueriesData`. `invalidateQueries` runs last and is *not* awaited.
- **D4 — `onSuccess` returns the helper's promise.** TanStack awaits `onSuccess`, so `isPending` (and therefore `variables`) holds until the patch is in the cache. The helper resolves after cancel+patch and does not wait for the refetch (NFR-3).
- **D5 — The helper lives in `useMergeTrainBoard.ts`.** Both writers already import that module (`ProjectSettingsDisclosure.tsx:7` imports `useMergeTrainBoard`), so no new import edge and no new cycle.
- **D6 — Regression tests go through the query, not the card prop.** `ProjectTrainCard` reads `project` from a prop, so a card-level test with a fixed prop can never see a cache patch. The switch regression tests render `MergeTrain placement="project" projectKey="overdeck"` in `MergeTrain.test.tsx`. Every test file touched is already in `scripts/frontend-test-subset.txt` (lines 382, 384, 390), so CI runs them without list changes.
- **D7 — Deviation from the issue's test wording.** The issue suggests a test where "the board refetch after the POST resolves with the old override and the switch stays off". With D2/NFR-2 a board response *fetched after* the write is treated as truth (it can only be stale if another writer changed the value back), so that literal test would contradict NFR-2. The tests instead model the real race: (a) the post-write refetch is still pending, and (b) a read already in flight at click time resolves stale after the POST and is discarded.

```ts
/** The answer of `POST /api/projects/:key/merge-train`. */
export interface ProjectTrainWrite { value: 'enabled' | 'disabled' | null; effective: boolean }

/** The project settings disclosure's read of the same override. */
export function projectTrainQueryKey(projectKey: string): readonly string[] {
  return ['project-merge-train', projectKey];
}

/**
 * PAN-5363: shows a confirmed project train write in every cached read of it.
 * Cancels in-flight board and settings reads first (cancelQueries reverts a
 * query to its pre-fetch state, which would undo an earlier patch), patches
 * the project's `override`/`enabled` in every board placement, sets the
 * settings query, then invalidates both without waiting for the refetch.
 */
export function useApplyProjectTrainWrite(): (projectKey: string, write: ProjectTrainWrite) => Promise<void> {
  const queryClient = useQueryClient();
  return async (projectKey, write) => {
    const settingsKey = projectTrainQueryKey(projectKey);
    await Promise.all([
      queryClient.cancelQueries({ queryKey: MERGE_TRAIN_BOARD_KEY }),
      queryClient.cancelQueries({ queryKey: settingsKey }),
    ]);
    queryClient.setQueriesData<MergeTrainBoard>({ queryKey: MERGE_TRAIN_BOARD_KEY }, (board) => board && {
      ...board,
      projects: board.projects.map((p) => (p.projectKey === projectKey
        ? { ...p, override: write.value, enabled: write.effective }
        : p)),
    });
    queryClient.setQueryData<ProjectTrainWrite>(settingsKey, write);
    void queryClient.invalidateQueries({ queryKey: MERGE_TRAIN_BOARD_KEY });
    void queryClient.invalidateQueries({ queryKey: settingsKey });
  };
}
```

## Non-goals

- Another browser tab's in-flight board read still shows the old value until that tab's next poll.
- CLI writes (`pan` in another process) are not pushed to the dashboard; they show after the 5 s board TTL.
- The project `auto-merge-default` write has the same stale-board shape for `mode`; it is not changed here.
- No subscription of the board cache to `subscribeProjectsConfigInvalidation`.
- No "hold the clicked value until the board agrees" local state.
- No change to the master switch, `GET /api/merge-train/config`, or the POST request/response shape.
