# PAN-5054: stop parallel phone PRs from conflicting on `apps/mobile/ACCEPTANCE.md`

**Issue:** [PAN-5054](https://github.com/eltmon/overdeck/issues/5054)

## Summary

Every phone-app PR appends its acceptance evidence as a new section at the end of
`apps/mobile/ACCEPTANCE.md`, so two phone PRs in flight conflict at the end of that file. The issue
proposed marking the file `merge=union` in `.gitattributes`. A probe during planning showed that
union **silently interleaves** two realistic evidence sections, line by line, with no conflict
markers. That is worse than the conflict it removes. So this plan does not mark the file union.
Instead, each new issue writes its evidence to its own file, `apps/mobile/acceptance/PAN-<n>.md`.
Two PRs that add different files never conflict. `ACCEPTANCE.md` keeps its existing sections and
gets a note at the top that points new evidence at the per-issue files.

## Glossary

- **Acceptance evidence:** the record a phone-app issue leaves of its device or emulator run:
  date, commit, steps, results, and links to screenshots. Today it lives in
  `apps/mobile/ACCEPTANCE.md`, one `## ...` section per issue.
- **Union merge (`merge=union`):** git's built-in merge driver. When both sides change the same
  region, it keeps both sides' lines instead of writing conflict markers. It needs no git config.
- **Zealous refinement:** git's merge step that moves lines common to both sides' changes out of
  the conflict region and emits them once. With union, this is what interleaves two sections that
  share identical lines (blank lines, table delimiter rows such as `| --- | --- |`, boilerplate
  such as `**Result: PASS.**`).
- **Per-issue evidence file:** `apps/mobile/acceptance/PAN-<n>.md`, a new file that holds one
  issue's acceptance evidence. Screenshots stay in the same folder as `pan-<n>-<step>.png`.
- **Merge door:** Overdeck's server-side merge path. It rebases the approved head onto `main`
  (`rebaseFeatureBranch`, `src/lib/cloister/merge-rebase.ts`) and probes conflicts with
  `probeBranchConflictPaths` (`src/lib/cloister/conflict-gate.ts`).
- **Conflict repair:** the patrol that asks a work agent to run `pan sync-main <id>` when its PR
  conflicts with `main` (docs/MERGE-WORKFLOW.md, "Conflict repair").

### Probe result: union interleaves realistic sections

Planning built a temp repo whose `A.md` started as the last 20 lines of the real `ACCEPTANCE.md`,
marked `A.md merge=union`, and appended one evidence section on each of two branches. Each section
had the shape of the real ones: a blank line, `## PAN-<n> ...`, `**Result: PASS.**`, a
`- **Date:**` bullet, a 4-column table with the row `| --- | --- | --- | --- |`, and a 3-column
table. Both `git merge-tree --write-tree x y` and `git merge --no-edit y` exited 0, and the merged
file read:

```text
## PAN-111 section 111
## PAN-222 section 222

**Result: PASS.** All steps passed.
...
| 2 | Pair 111 | shot | pass |
- **App commit:** `222`.
...
| 1. x111 | a | pass |
| 1. x222 | a | pass |
```

The two headings sit together, PAN-111's table rows run straight into PAN-222's bullets, and the
last table mixes both issues' rows. Nothing flags it. A simpler fixture with no shared interior
lines merged in order but still lost the blank line between the sections. Conclusion: union is safe
only for one-entry-per-line lists (the `.gitattributes` comments already say "no structure to
break"); it is not safe for sectioned markdown.

## Decisions

- **D-1 No union on `ACCEPTANCE.md`.** The probe shows silent interleaving. A visible conflict is
  better than shredded evidence. The issue's proposed fix is rejected with this evidence, and the
  issue gets a comment saying so.
- **D-2 One evidence file per issue.** New phone-app evidence goes in
  `apps/mobile/acceptance/PAN-<n>.md`, with `<n>` the GitHub issue number and `PAN` upper case
  (the `.pan/drafts/PAN-<n>.md` style). Screenshots go beside it as `pan-<n>-<step>.png`. Parallel
  PRs add different files, so neither git nor GitHub reports a conflict, and the PAN-4616 question
  (whether GitHub honors union) does not arise.
- **D-3 Keep the existing sections where they are.** Moving the ten sections out of
  `ACCEPTANCE.md` would rewrite the file and conflict with #5051 and #5049. Later issues may cite
  those sections by their current headings (e.g. PAN-4841's PRD cites "PAN-4838 iOS
  notifications"). `ACCEPTANCE.md` stays as the record up to now.
- **D-4 No index of the per-issue files.** A shared index that every PR appends to would recreate
  the hot spot. The folder listing is the index.
- **D-5 No lint or test that refuses new sections in `ACCEPTANCE.md`.** #5051 and #5049 still
  append there; a guard would turn their CI red after this lands. The note and the docs steer new
  plans; a missed case costs one conflict repair, as today.
- **D-6 The test guards the decision.** It checks that `ACCEPTANCE.md` and a per-issue file carry
  no merge attribute, and it shows two branches that each add a per-issue file merge cleanly.
  It does not assert git's interleaving behavior, because a future git version could change it and
  turn CI red for no code change.
