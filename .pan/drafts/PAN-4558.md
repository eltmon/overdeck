# PAN-4558: Conversation open sends the whole transcript — bound the initial window and page older history

**Issue:** https://github.com/eltmon/overdeck/issues/4558 · **Related:** #3778 (this issue also delivers #3778 direction 1, resume on resubscribe)

## 0. Summary

Opening a conversation sends its entire parsed transcript to the browser, over HTTP and over the WebSocket (WS) subscribe, and every WS resubscribe sends it again. This PRD bounds every cold open to the newest ~75 timeline rows or ~1 MiB, adds a paged HTTP read for older history that the timeline loads when the user scrolls to the top, removes large tool bodies from the wire (loaded on expand), and makes a WS resubscribe send only rows the client does not already have.

## 1. Glossary

- **Transcript** — the harness's JSONL session file on disk. Never modified by this work.
- **Parse result** — `ParseResult` (`src/dashboard/server/services/conversation/types.ts`, `export interface ParseResult`): `messages: ChatMessage[]`, `workLog: WorkLogEntry[]`, metadata (`streaming`, `totalCost`, `totalTokens`, `proposedPlan`, `compactBoundaries`, `pendingToolUse`, …).
- **Entry** — one `ChatMessage` or one `WorkLogEntry` (schemas in `packages/contracts/src/rpc.ts`, `export const ChatMessage` ~line 149 and `export const WorkLogEntry` ~line 161).
- **Timeline order** — the order the frontend renders entries in: `deriveTimelineEntries` (`src/dashboard/frontend/src/components/chat/MessagesTimeline.logic.ts` ~:80-103) concatenates messages and workLog and sorts by `createdAt` (string compare), then `sequence`. This PRD's **timeline key** extends that to a total order: `(createdAt, sequence ?? 0, kindRank, id)` where `kindRank` is `0` for a message and `1` for a work entry.
- **Timeline row** — what the frontend draws: each message is one row; a maximal run of consecutive work entries (in timeline order) is one row (`deriveMessagesTimelineRows` groups them into a `kind:'work'` row, ~:197-202).
- **Window** — the newest contiguous slice of entries in timeline order that a response carries, plus **pinned** entries (open tool calls, see FR-3).
- **Cursor** — an opaque string that encodes the timeline key of the oldest *contiguous* entry in a window or page (pinned entries never set the cursor). `before=<cursor>` asks for entries strictly older than it.
- **`hasOlder`** — true when at least one entry older than the cursor exists.
- **Transcript id** — `"<dev>:<ino>"` of the transcript file at read time. Identifies "the same file" across reconnects.
- **Wire projection / elision** — replacing a large tool body (`result`, oversized `detail`, oversized strings inside `toolInput`) with a short preview plus a size hint before an entry goes on the wire. The full entry stays in the server's parse result.
- **Open entry** — an entry the client holds that may still change: a work entry with `tone === 'tool'` and no result yet, or an assistant message with no `completedAt`.
- **Resume** — on WS resubscribe, the client tells the server what it already has (`afterSequence`, `openIds`, `transcript`); the server replies with only newer or newly-settled entries.
- **Windowed snapshot** — a WS `messages` event with `snapshot: true` and a `window` field. It replaces the newest part of the client cache, never the paged-in older part (FR-9).

## 3. Requirements

### Functional

- **FR-1** A cold open of a conversation over HTTP (`GET /api/conversations/:name/messages` with no paging params) returns a window: at most `CONVERSATION_WINDOW_MAX_ROWS` (75) timeline rows and at most `CONVERSATION_WINDOW_MAX_BYTES` (983,040) bytes of encoded entries, always at least one entry when the transcript has any, plus a `window: { cursor, hasOlder, transcript }` field.
- **FR-2** The first event of every WS `subscribeConversationMessages` stream (Claude and full-parse harnesses, conversations and synthetic agent sessions, main and subagent transcripts) is a windowed snapshot under the same budget, unless a valid resume applies (FR-8). Every later `snapshot: true` event (file reset, full-parse reorder) is also windowed.
- **FR-3** A window always includes, in addition to the contiguous slice: the newest ≤`WINDOW_PINNED_OPEN_TOOLS_MAX` (10) open tool calls — `workLog` entries with `tone === 'tool'` and `!hasToolResult(entry)` (pinned), and full metadata — `streaming`, `totalCost`, `totalTokens` (HTTP), `proposedPlan`, all `compactBoundaries`, `compacting` (HTTP), `contextUsage`, `subagents` (HTTP). `totalCost`/`totalTokens` stay whole-transcript values.
- **FR-4** `GET /api/conversations/:name/messages?before=<cursor>&limit=<n>` returns the page of entries strictly older than the cursor (newest `n` timeline rows, same byte budget, at least one entry if any exist) with its own `window`. `limit` defaults to 75 and clamps to `[1, 200]`. A malformed cursor returns HTTP 400 `{ "error": "Invalid cursor" }`. `agentId` combines with it.
- **FR-5** `GET /api/conversations/:name/messages?window=all` returns today's full response (all entries, no elision, no `window` field). Transcript export uses it.
- **FR-6** `GET /api/agents/:id/conversation` keeps its full response when called with no new params. `?window=initial` returns a window (FR-1 shape) and `?before=<cursor>&limit=<n>` returns a page (FR-4 shape); both combine with `subagentId`.
- **FR-7** Every entry on a windowed/paged HTTP response and on every WS event is wire-projected: a `result` longer than `TOOL_BODY_INLINE_MAX_BYTES` (4096 UTF-8 bytes) is removed and replaced by `resultBytes: <byte length>`; a `detail` or any string inside `toolInput` longer than 4096 bytes is cut to its first 512 characters plus `…`; any such change sets `bodyOmitted: true`. Status (`tone`), the failure prefix in `detail` (`Error: …`) and `toolTitle`/`label` are kept.
- **FR-8** The subscribe payload accepts `resume?: { afterSequence: number; openIds: string[]; transcript: string }`. When the server's transcript id equals `resume.transcript`, every entry has a numeric `sequence`, `afterSequence` ≤ the highest sequence in the parse, and the delta fits the byte budget, the first event is `{ kind: 'messages', snapshot: false, metadataSnapshot: true, ... }` carrying only entries with `sequence > afterSequence` plus the server's current copy of every entry whose id is in `openIds` (at most 200, usually one or two). "Rows the client already has" (issue AC 3) means settled rows: open rows are re-sent because they may have changed in place. Otherwise the first event is a windowed snapshot with `reset: true`.
- **FR-9** The client keeps a `history: { cursor, hasOlder, transcript }` field in its message cache. A windowed snapshot or windowed HTTP response merges with the cache: entries older than the response's cursor that the cache already has are kept; from the cursor on, the response is authoritative. If the response's cursor is newer than the cache's newest entry (a gap), or the event has `reset: true`, the response replaces the cache.
- **FR-10** When the user scrolls within 400 px of the top of the timeline and `history.hasOlder` is true, the client fetches the next older page and prepends it without moving the visible content. It shows "Loading earlier messages…" while loading and "Start of conversation" when `hasOlder` is false and older pages were loaded. Repeating this reaches the first entry with no duplicated or missing entries.
- **FR-11** Expanding a tool row with `bodyOmitted: true` fetches the full entry from `GET /api/conversations/:name/tool-body/:toolUseId` (`?agentId=` for a subagent) or `GET /api/agents/:id/conversation/tool-body/:toolUseId` (`?subagentId=`) and renders its full result and input. A missing id returns HTTP 404 `{ "error": "Tool entry not found" }`.
- **FR-12** A tool row with `resultBytes` set counts as having a result everywhere "pending" is decided (working phase, current-tool, expandability).
- **FR-13** Jump-to-message (palette hit, `targetMessageId`) and bookmark jump load older pages until the target message id is loaded or `hasOlder` is false, then scroll to it. The index-based fallback (`targetMessageIndex`) is used only when `hasOlder` is false.
- **FR-14** The client shows compaction boundaries only when their `timestamp` is ≥ the `createdAt` of the oldest loaded entry, or when `hasOlder` is false.
- **FR-15** The simple activity feed marks a user message as the task kickoff only when `hasOlder` is false.
- **FR-16** Transcript export (conversation header and Command Deck action menu) exports the whole transcript via `?window=all` (agent panels: the agents route without params).

### Non-functional

- **NFR-1** Payload budget: for a synthetic transcript larger than 5 MB, `Buffer.byteLength(JSON.stringify(body))` of the initial HTTP body and of the first WS event is ≤ `CONVERSATION_PAYLOAD_BUDGET_BYTES` (1,048,576). A test enforces it (WI-15).
- **NFR-2** Window selection walks from the newest entry and stops at the budget: it never projects or measures entries outside the window it returns (no O(transcript) JSON encoding per open).
- **NFR-3** Paged reads reuse the existing parse caches (`getCachedMessages` for conversations; the agents route's existing parse). No new on-disk state, no new cache.
- **NFR-4** No `execSync`; no blocking I/O on the dashboard server path. Tests with delays use `vi.useFakeTimers()`.
- **NFR-5** File-size ratchet: `src/dashboard/server/ws-rpc.ts` (1220 lines, cap 1221) and `ConversationPanel.tsx` (1525 lines, cap 1531) must not grow past their caps; extraction items WI-3 and WI-10 run first. Never raise `scripts/file-size-allowlist.txt`.

## 4. Decisions (made here; do not re-decide)

1. **Window unit = timeline rows over merged order**, not per-array counts. Each array windowed separately would interleave wrongly at the old edge.
2. **Cursor = timeline key of oldest contiguous entry**, encoded as `JSON.stringify([createdAt, sequence ?? 0, kindRank, id])`. It is not a byte offset, because the Claude parser sorts entries and merges tool_use blocks, so file offsets do not map to entries. Decoding validates shape (4-tuple: string, finite number, 0|1, string) and returns `null` on anything else.
3. **Budget constants** live in `packages/contracts/src/conversation-window.ts` so client and server share them: `CONVERSATION_WINDOW_MAX_ROWS = 75`, `CONVERSATION_WINDOW_MAX_BYTES = 983_040` (960 KiB for entries, leaving 64 KiB for metadata), `CONVERSATION_PAYLOAD_BUDGET_BYTES = 1_048_576`, `CONVERSATION_PAGE_DEFAULT_LIMIT = 75`, `CONVERSATION_PAGE_MAX_LIMIT = 200`, `TOOL_BODY_INLINE_MAX_BYTES = 4096`, `TOOL_BODY_PREVIEW_CHARS = 512`, `RESUME_OPEN_IDS_MAX = 200`, `WINDOW_PINNED_OPEN_TOOLS_MAX = 10`.
4. **One server window module** (`src/dashboard/server/services/conversation/window.ts`) used by HTTP conversations, HTTP agents, the Claude WS stream and the full-parse WS stream. One **wire projection** module (`.../conversation/wire-projection.ts`) used by the window module and by every WS delta emission.
5. **Full-parse delta stays over full arrays.** `createTranscriptDelta` keeps its `previous` baseline over the full `ParseResult` rows; only the emitted event is windowed/projected. Windowing `previous` would make every diff a snapshot.
6. **Compaction boundaries are always sent whole** (they are small metadata); the client filters display (FR-14). This keeps `metadataSnapshot` semantics unchanged.
7. **Resume uses `afterSequence` + `openIds` + `transcript`**, not a byte offset. `sequence` is assigned per JSONL line from file start by every parser except prime-agent; a resume against entries without numeric `sequence` falls back to a windowed reset snapshot.
8. **`window=all` and the agents route without params stay unwindowed and unprojected** so export and the three other agent-route hosts (`TerminalPanel`, `DirectoryTranscript`, `SessionTranscript`) keep working unchanged. Only `ConversationPanel` (with `agentId`) opts into `?window=initial`.
9. **Pinned open tools** are defined once in `window.ts`: the newest 10 `workLog` entries with `tone === 'tool'` and `!hasToolResult(entry)`. This works on every path (the HTTP full parse flushes `pendingToolUse` into `workLog` and clears the map, parser.ts ~:625-631, so the map cannot be the source). Pinned entries never move the cursor; the client dedupes them by id on prepend.
10. **A single newest entry larger than the budget is still sent** (the "at least one entry" rule). Message text is never elided. This is a NonGoal to fix.
11. **OKF docs** are edited in the separate bundle repo `/home/eltmon/Projects/overdeck-knowledge` (remote `eltmon/overdeck-knowledge`) and committed there directly, as PAN-4312 did (`0641353`).

### WI-4 Server window selection module — foundation

Files: `src/dashboard/server/services/conversation/window.ts` (new), `src/dashboard/server/services/conversation/__tests__/window.test.ts` (new).

API:
```ts
export interface WindowInput {
  messages: readonly ChatMessage[];
  workLog: readonly WorkLogEntry[];
}
export interface WindowedRows { messages: ChatMessage[]; workLog: WorkLogEntry[]; window: ConversationWindow }
export function selectInitialWindow(input: WindowInput, transcript?: string, budget?: { maxRows: number; maxBytes: number }): WindowedRows
export function selectPageBefore(input: WindowInput, before: TimelineKey, limit: number, transcript?: string): WindowedRows
export function selectResumeDelta(input: WindowInput, resume: ConversationResume, transcript: string | undefined): { messages: ChatMessage[]; workLog: WorkLogEntry[] } | null
export function transcriptIdOf(stats: { dev: number; ino: number }): string // `${dev}:${ino}`
```
Algorithm (`selectInitialWindow` / `selectPageBefore`):
1. Build a merged list of `{ key, kind, entry }` (messages kindRank 0, work 1), sort by `compareTimelineKeys`. For `selectPageBefore`, keep only keys `< before`.
2. Walk from the newest. Track `rows` (increment when the entry is a message, or a work entry whose newer neighbour in the walk was not a work entry) and `bytes` (`Buffer.byteLength(JSON.stringify(projected))`, work entries projected with `projectWorkLogEntry`). Stop before an entry that would make `rows > maxRows` (initial) / `> limit` (page) or `bytes > maxBytes`, except the first entry, which is always taken.
3. `cursor` = encoded key of the oldest taken entry (null when nothing taken); `hasOlder` = an untaken older entry exists.
4. Initial window only: add pinned open tools (projected): the newest `WINDOW_PINNED_OPEN_TOOLS_MAX` work entries with `tone === 'tool'` and `!hasToolResult(entry)` that were not already taken.
5. Split back into `messages`/`workLog`, each sorted ascending by timeline key.
`selectResumeDelta` implements FR-8 (entries with `sequence > afterSequence` plus the current copy of every `openIds` entry; returns null on transcript mismatch, any entry without numeric `sequence`, `afterSequence` > max sequence, or delta bytes > `CONVERSATION_WINDOW_MAX_BYTES`); `openIds` beyond `RESUME_OPEN_IDS_MAX` are ignored.

Tests: 300 alternating message/tool entries → 75 rows, `hasOlder` true, cursor = oldest taken; byte cap stops early with 200 KB entries; single 2 MB message → exactly that entry; page before cursor returns the next older rows with no overlap and paging to the end yields every entry exactly once (concatenate all pages + window and compare ids to the input); pinned open tool older than the window is included and the cursor is unaffected; resume returns new entries plus the current copy of open entries, null on transcript mismatch, null when a row lacks sequence.

## 8. Non-goals

- A single newest entry larger than the budget (for example a 3 MB pasted user message) is still sent whole; message text is never elided.
- Ctrl+F search covers loaded rows only, and does not search omitted tool bodies.
- Turn-diff matching and reviewer round markers apply to loaded rows only; they fill in as older pages load.
- `TerminalPanel`, `DirectoryTranscript` and `SessionTranscript` keep reading the full agents-route response (no paging there).
- No change to the transcript on disk, the parsers' output, the message-locator route, or #3778 direction 3 (watchdog fairness).
- No new persistent cache or on-disk state.

## 9. Risks

- **Resume correctness**: a row that changed without a new sequence and is not "open" would be missed. Only open tool calls and incomplete assistant messages change in place in today's parsers, and the server re-sends its current copy of every open row; anything else is a new line with a new sequence.
- **Scroll anchoring under tanstack virtual**: absolutely positioned rows re-measure after prepend; the anchoring must use `scrollHeight` deltas in a layout effect, not estimated sizes.
- **ConversationPanel/ws-rpc caps**: WI-3 and WI-10 must land before items that touch those files.
- **Shared OKF checkout**: `/home/eltmon/Projects/overdeck-knowledge` is a shared primary checkout; pull before editing, commit only the three files.
