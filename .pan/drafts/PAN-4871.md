# PAN-4871: Phone web app cannot open a linked machine's conversation

**Issue:** [PAN-4871](https://github.com/eltmon/overdeck/issues/4871)
**Status:** planned (auto mode, high effort)

## Glossary

- **Phone app** — the installable web app at `/m` (`src/dashboard/frontend/src/components/mobile/`), PAN-2355. Deep links are query parameters: `/m?conversation=<key>` opens one conversation full screen.
- **Linked machine** — another Overdeck machine joined to this one through Anywhere machine links (PAN-4645/PAN-4650).
- **Linked row** — a conversation that a linked machine owns, merged into this machine's `GET /api/conversations` list by `linkedListRow` (`src/lib/overdeck/linked-conversations-merge.ts`, line 63). It carries:
  - `id: -record.id` — negative and unstable (the issue saw `-1`);
  - `name: '@<environmentId>/<ownerName>'` — the **linked name**;
  - `origin: 'linked'`, `environmentId`, `remoteName` (the owner's local name), `machineLabel`, `machineState`.
- **Linked name** — `@<target>/<name>`, parsed by `parseLinkedConversationName` (`packages/contracts/src/linked-conversations.ts`, line 75). `<target>` is an environment id or a machine label.
- **Owner row** — the owner machine's own conversation row: positive id, its local `name` (no `@` prefix), no `origin: 'linked'`.
- **Linked-conversation proxy** — `src/dashboard/server/linked-conversation-proxy.ts`. A global middleware that forwards `/api/conversations/@<target>/<ownerName>[/…]` (raw or `%40<env>%2F<name>`) to the owner's `/api/conversations/<ownerName>[/…]` and returns the owner's status and body **unchanged**.
- **Route key** — what a UI uses to address a conversation. `conversationRouteKey(conv)` in `src/dashboard/frontend/src/lib/linkedConversation.ts` (line 25) returns the linked name for a linked row and `String(conv.id)` otherwise.

## Problem

Two separate defects block the phone from reaching a linked machine's conversation.

### Defect 1 — the list opens linked rows by their negative id

`src/dashboard/frontend/src/components/mobile/MobileConversations.tsx`, line 47 (search `onClick={() => onOpen(String(c.id))}`):

```tsx
onClick={() => onOpen(String(c.id))}
```

A linked row's id is negative, so tapping it navigates to `/m?conversation=-1`. `ConversationView` then calls `GET /api/conversations/-1`, which matches no row, and renders "Couldn't load this conversation."

### Defect 2 — the view feeds `ConversationPanel` the owner's row

`MobileConversations.tsx`, `ConversationView` (search `fetchWithTimeout(\`/api/conversations/${encodeURIComponent(conversationId)}\`)`) fetches the single row by key. For `conversationId = '@env/conv-a'` the request is `/api/conversations/%40env%2Fconv-a`. The proxy parses that form (`parseLinkedConversationPath`, lines 77–82) and forwards it, so the fetch **succeeds** — but the body is the **owner row**: positive id, `name: 'conv-a'`, no `origin`.

`ConversationView` passes that row to `ConversationPanel`, which addresses everything by `conversation.name`:

1. `useConversationMessagesStream` (`src/dashboard/frontend/src/components/chat/useConversationMessagesStream.ts`, line 140 `shouldStreamConversationMessages`) enables the RPC stream, because the owner row has `id >= 0` and no `endedAt`.
2. `transportForConversation('conv-a')` (`linkedConversation.ts`, line 59) finds no `@` prefix and returns this machine's own `/ws/rpc` transport.
3. This machine's server has no conversation named `conv-a`, emits a `discovering` event and keeps polling. `ConversationPanel` renders `TranscriptLoadingSkeleton` with "Discovering conversation…" forever.

### How the desktop does it

The desktop never fetches `/api/conversations/@env/name` to get the row. It takes the **viewer-shaped linked row** from the merged list (`src/dashboard/frontend/src/components/CommandDeck/index.tsx`, line 634: `conversations.find((c) => c.name === selectedConversation)`) and passes it to `ConversationPanel`. With `name: '@env/name'` and a negative id, every call the panel makes (`/api/conversations/%40env%2Fname/messages`, `/tool-body`, `/about`, sends) goes through the proxy, and the panel's linked-row branches (`ConversationMachineBanner`, `conversationMachineState`, the `remote` open-in picker at `ConversationPanel.tsx` line 986) see `origin: 'linked'`.

## Proposal

Make the phone do what the desktop does:

1. The list opens every row by `conversationRouteKey(c)` — the linked name for a linked row, the numeric id otherwise.
2. The view resolves a linked name from the merged `GET /api/conversations` list (the page the list view already fetches; linked rows merge into page 1 only — `getMergedConversationList`, `src/dashboard/server/services/conversation-list-merged.ts`, line 36) and passes that viewer-shaped row to `ConversationPanel`. Local ids and names keep the existing single-row fetch.

`ConversationPanel.tsx` is not edited (the module header's D-14 rule: "`ConversationPanel.tsx` is never edited for the phone"). No server or proxy change is needed.

## Requirements

### Functional

- **FR-1** — Tapping a linked row in the phone conversation list calls `onOpen` with the row's linked name (`@<environmentId>/<ownerName>`), never its negative id. Local rows still open by `String(c.id)`.
- **FR-2** — `/m?conversation=@<environmentId>/<name>` round-trips through `mobilePath` / `readMobileRoute` (`MobileApp.tsx`) with `@` and `/` intact.
- **FR-3** — When `conversationId` parses as a linked name, the phone view fetches `GET /api/conversations`, picks the row whose `name` equals `conversationId`, and renders `ConversationPanel` with that row (negative id, linked name, `origin: 'linked'`). It never fetches `/api/conversations/<encoded linked name>` to build the row.
- **FR-4** — A linked key whose target is a machine label (`@<label>/<name>`) resolves to the linked row whose `origin === 'linked'`, `machineLabel === <label>` and `remoteName === <name>` when no row name matches exactly.
- **FR-5** — When no linked row matches, the view renders the existing "Couldn't load this conversation. It may have been archived or deleted." text. While the list is loading it renders "Loading conversation…".
- **FR-6** — A local `conversationId` (numeric id or local name) keeps today's behavior: `GET /api/conversations/<encoded id>`, refetched every 5 s.

### Non-functional

- **NFR-1** — `ConversationPanel.tsx`, the proxy and every server file stay unchanged.
- **NFR-2** — The linked-row lookup is a pure function in `src/dashboard/frontend/src/lib/linkedConversation.ts` with unit tests; the component only calls it.
- **NFR-3** — The linked view refetches the list every 5 s, the same cadence as the local single-row fetch, so `sessionAlive`, `machineState` and the title stay current.

## Decisions

- **D-1 — Resolve the linked row from the merged list.** Chosen because the merged row is the exact shape the desktop renders, so the panel's linked branches work unchanged. Rejected alternatives:
  - *Patch the proxied owner row* (rename `name`, negate `id`, add `origin`). It would have to rebuild merge-only fields (`machineLabel`, `machineState`, `machineLastSeenAt`, `savedCopyName`, `releasedTo`) that `ConversationMachineBanner` and `conversationMachineState` read, and would drift from `linkedListRow`.
  - *A new server route returning one merged row.* It needs a `route-scopes.ts` row, a no-loss-matrix row and server tests — more surface than the bug needs.
  The issue's "load `@<env>/<name>` through the linked-conversation proxy" still holds: every call `ConversationPanel` makes with `name = '@env/name'` goes through the proxy.
- **D-2 — Match by exact name first, then by label.** Exact `name === key` covers every row the list produces (names use the environment id). The label fallback (FR-4) covers hand-typed or shared `@<label>/<name>` links, which the proxy also accepts. Two machines with the same label are not a concern: the first matching row wins, the same rule `Array.find` gives the desktop.
- **D-3 — No fallback to the proxied single-row fetch** when the linked row is missing. The owner row would reproduce Defect 2. The error text is the honest state: the row is not in this machine's cache (machine unlinked, sharing off, or hidden).
- **D-4 — Query keys.** The linked view keeps the existing `['mobile-conversation', conversationId]` key; only its `queryFn` branches. The list view keeps `['mobile-conversations']`. No shared cache is introduced.

### WI-2 — Pure linked-row lookup (NFR-2, FR-4)

**Files:** `src/dashboard/frontend/src/lib/linkedConversation.ts`, `src/dashboard/frontend/src/lib/__tests__/linkedConversation.test.ts`.

Add, below `conversationRouteKey`:

```ts
type LinkedLookupRow = { name: string; origin?: string; machineLabel?: string; remoteName?: string };

/**
 * The merged-list row a linked key opens (PAN-4871): the row named `key`, else
 * the linked row on the machine labelled `<target>` with owner name `<name>`.
 * Null for a local key or when no linked row matches.
 */
export function findLinkedConversationRow<T extends LinkedLookupRow>(rows: readonly T[], key: string): T | null {
  const linked = parseLinkedConversationName(key);
  if (!linked) return null;
  return rows.find((row) => row.name === key)
    ?? rows.find((row) => isLinkedConversation(row) && row.machineLabel === linked.target && row.remoteName === linked.name)
    ?? null;
}
```

Unit tests in `linkedConversation.test.ts` (new `describe('findLinkedConversationRow')`):

- returns the row whose `name` is `'@env-a/conv-9'`;
- returns the linked row with `machineLabel: 'laptop'`, `remoteName: 'conv-9'` for key `'@laptop/conv-9'`;
- returns `null` for a local key `'conv-9'` even when a row named `conv-9` exists;
- returns `null` when no row matches `'@env-b/conv-9'`;
- ignores a non-linked row (`origin: 'local'`) that happens to carry `machineLabel`/`remoteName`.

Tests: `npx vitest run src/dashboard/frontend/src/lib/__tests__/linkedConversation.test.ts`.
