# PAN-5232: Herdr pane reads always return empty text

**Issue:** [PAN-5232](https://github.com/eltmon/overdeck/issues/5232)
**Planned:** 2026-11-14, against `main` at `99517e495ab`, herdr 0.9.1 (protocol 22).

## Glossary

- **Herdr**: the default terminal backend. Overdeck talks to it through NDJSON over the unix socket
  `~/.config/herdr/sessions/overdeck/herdr.sock`, one request per connection.
- **`HerdrApiClient.call()`**: `src/lib/terminal-backends/herdr-api.ts`. It sends one request and
  resolves the response's `result` object **unchanged** (`finish(() => resolve((response.result ?? {}) as T))`).
  It never unwraps per-method payloads, so each caller must read the right key inside `result`.
- **`pane.read`**: the Herdr method that returns a pane's terminal text (the Herdr equivalent of
  `tmux capture-pane`). Sources used here: `recent`, `visible`, `recent_unwrapped`.
- **Wire shape**: the JSON structure of a response's `result`. For `pane.read` on herdr 0.9.1 it is
  `{ type: "pane_read", read: { pane_id, workspace_id, tab_id, source, format, text, revision, truncated } }`.
- **Legacy shape**: `{ text }` directly on `result`. No observed Herdr version returns it. The
  issue asks the parser to accept it anyway.
- **Pane reader**: any code that sends `pane.read` and extracts text. There are three (see Root cause).
- **Schema fixture**: `src/lib/terminal-backends/__fixtures__/herdr-v0.9.1/schema.json`, the committed
  Herdr JSON schema. `schemas.success_response.$defs.ResponseResult.oneOf` lists every result variant.
- **Dormant code**: screen-parsing logic that has never run on Herdr against real text, because every
  read returned `''`. Fixing reads switches it on.

## Problem

On Herdr, every pane read returns `''`. Every decision that looks at pane text is blind: readiness
waits, crash and stall detection, resume-menu handling, submit verification, and API-error nudges.

## Decisions

- **D1. One parser in a new leaf module.** Create `src/lib/terminal-backends/herdr-pane-read.ts`
  exporting `herdrPaneReadText(result: unknown): string`. It imports nothing. `herdr-submit.ts`
  says that importing `herdr-api` from there would close an import cycle through `types.ts`, so the
  parser must not import `herdr-api.ts` or `types.ts`. Its input is `unknown` because
  `HerdrSubmitApi.call` returns `Promise<unknown>`.
- **D2. Precedence.** If `result.read` is an object with a string `text`, return it. Else if
  `result.text` is a string, return it (legacy shape). Otherwise return `''`.
- **D3. An unrecognized shape returns `''` and warns once per process.** It does not throw. All
  readers treat `''` as "nothing on screen yet", which is how the fleet has run on Herdr since
  PAN-3917. A throw would change behaviour on a future shape change in ways that are worse. For
  example, `ensureMainInputTarget` would refuse every Claude delivery and
  `prepareAutonomousAgentResumePane` would block every autonomous resume. The warning makes a shape
  change visible in logs. The contract test (D5) makes it fail CI. Warning text:
  `[herdr] pane.read response has no read.text or text; treating the pane as empty (keys: <comma-separated top-level keys>) (PAN-5232)`.
  A `null`/`undefined`/non-object result also takes this path, and its key list is empty.
- **D4. Convert every wire-level `pane.read` mock to the 0.9.1 shape** (`{ type: 'pane_read', read: { text } }`
  or at least `{ read: { text } }`). Only the parser's own unit test covers the legacy shape. This way
  no test keeps describing a wire Herdr does not speak.
- **D5. The contract test goes through the real client.** It feeds the exact 0.9.1 NDJSON line
  through `HerdrApiClient` (constructed with a `connect` factory that returns a fake socket echoing
  the request id) into `readHerdrPaneText(..., api)` and into `pasteAndSubmitHerdrPane(api, ...)`.
  This covers `call()` returning `result` unchanged plus the parser. It also loads the schema fixture
  and asserts that the `pane_read` variant's only non-`type` property is `read`, that `read` refers to
  `PaneReadResult`, and that `PaneReadResult.required` contains `text`. It does not read source files.
- **D6. `herdr.ts` line budget.** `herdr.ts` is 1006 lines and capped at 1008 in
  `scripts/file-size-allowlist.txt` (`1008 src/lib/terminal-backends/herdr.ts # PAN-4292`). Net
  growth for R1 + R2 must be **≤ 2 lines**: one import line, and in-place replacements of the two
  `.text` reads. Never raise the allowlist row.
- **D7. Live check: two parts, never touching the operator's panes with input.**
  1. **Read-only run (required).** A one-off script from the workspace calls `readHerdrPaneText`
     against a live idle Claude pane and `waitForClaudeReady(<live idle Claude conversation agent id>)`.
     Both calls only read. The planning agent already ran this against the unfixed code (see W6,
     "Before"), so the script path is proven.
  2. **Isolated launch (required attempt).** This is the only check that exercises readiness from a
     cold start, including the startup-dialog and early-exit throws. Use the PAN-5122 recipe in
     `docs/TERMINAL-BACKENDS.md` ("Live verification record — companion terminal on Herdr (PAN-5122)"):
     `npm run build:dashboard`, then
     `API_PORT=3091 HOST=127.0.0.1 OVERDECK_HOME=<scratch home> node dist/dashboard/server.js`, backed
     by `herdr --session <scratch session> server`. Launch one throwaway Claude conversation there and
     record the elapsed time to the `[conversations] Claude Code ready in` log line.
     **Implementation checkpoint, fallback:** if the isolated instance cannot be started, record in
     the live record what failed (the command and its error). Part 1 then stands as the evidence for
     requirement 4. Stop the isolated server and its scratch Herdr session afterwards.
  Never send text or keys to an operator pane. Pasting through `pasteAndSubmitHerdrPane` into a live
  operator pane is forbidden. Submit verification is proven by unit tests on the real wire shape plus
  the composer probe above.
- **D8. No screen-parser changes.** If real text exposes a bug in a dormant parser (composer,
  selector, resume gate, readiness regexes, API-error patterns), the work agent files a follow-up
  issue and does not fix it here.

```ts
/**
 * PAN-5232: the text of a Herdr `pane.read` response. Herdr 0.9.1 answers
 * `{ type: 'pane_read', read: { text, … } }`, and `HerdrApiClient.call()`
 * returns that `result` unchanged, so readers that took `result.text` saw ''
 * on every read. Accepts the legacy `{ text }` shape too. Imports nothing:
 * herdr-submit.ts must not import herdr-api (import cycle through types.ts).
 */
let warnedUnrecognized = false;

export function herdrPaneReadText(result: unknown): string {
  const record = result !== null && typeof result === 'object' ? result as Record<string, unknown> : null;
  const read = record?.read;
  if (read !== null && typeof read === 'object' && typeof (read as { text?: unknown }).text === 'string') {
    return (read as { text: string }).text;
  }
  if (typeof record?.text === 'string') return record.text;
  if (!warnedUnrecognized) {
    warnedUnrecognized = true;
    console.warn(`[herdr] pane.read response has no read.text or text; treating the pane as empty (keys: ${Object.keys(record ?? {}).join(',')}) (PAN-5232)`);
  }
  return '';
}
```

`vi.resetModules()` + dynamic import. Tests (each its own `it`):

## Critique response

The plan critic (round 1, `.pan/drafts/PAN-5232-critique.md`) raised two blocks-the-design findings
and one sharpening. All three were checked against the code and adopted.

### Enter can answer a visible permission menu

Confirmed. `herdr-submit.ts` Step 3 runs only when `presence !== 'present'`. Today reads are empty,
so presence is never `present`, and `blocked()` always runs before the first Enter. Once reads work,
a visible paste would skip `blocked()` and the menu check, and the existing tests
`'holds when the agent is blocked at the decision point'` and
`'holds when a permission menu appears on the same screen as the composer'` expect exactly that one
Enter. That contradicts the module header ("Never presses a keystroke when a permission prompt or
choice menu is on screen, or the agent is `blocked`"). W3 now runs Step 3 whatever the presence is.
Those two tests now expect `'blocked'` with zero keys, and a new test keeps `'held'` covered (AC-W3b).

### Resume treats permission menus as clear

Confirmed. `paneChoiceFromText` uses the card parser, which returns `null` for permission options
(`if (looksLikePermissionOptions(options)) return null` in `pane-choice-menu.ts`), so
`prepareAutonomousAgentResumePane` would return `{ ready: true, action: 'clear' }` and type a
continuation into a permission menu. The degraded-behaviour row claimed otherwise and has been
corrected. W7 adds a guard-mode `paneHasBlockingChoiceMenu(screen)` check in the Herdr branch, so the
answer is `ready: false`, with a permission-menu test (AC-W7). The tmux branch has the same gap.
That gap does not come from this change, so it stays a non-goal here.

### Resume capture uses recent, not visible

Adopted in W7: the Herdr resume capture reads `visible`, and the test asserts the `source`.
