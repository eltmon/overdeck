## blocks-the-design: In-flight requests bypass the head check

`startRequestReviewPipeline` returns `already-running` before verification when an issue is in flight ([review-pipeline.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4527/src/dashboard/server/routes/workspaces/review-pipeline.ts), lines 240-245). The guard skips the second task rather than queuing it ([in-flight-guard.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4527/src/lib/cloister/in-flight-guard.ts), lines 60-79), while the route tells the caller that the existing verification will lead to review (review-pipeline.ts, lines 936-942). Even a direct second call to `runSupervisedVerification` returns the issue-keyed `activeSupervisorRuns` promise before `runSupervisedVerificationInternal` compares heads ([verification-worker-supervisor.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4527/src/lib/cloister/verification-worker-supervisor.ts), lines 245-259). The proposed join test registers an existing worker on disk before its *first* call (verification-worker-supervisor-join.test.ts, lines 153-185), so it does not exercise either in-process path. A new commit during an active request can therefore inherit the old run and its later push/review continuation. Make both coalescing decisions head-aware: preserve same-head deduplication, supersede an old-head run, and prevent its continuation from pushing or dispatching review. Add a second-request-while-running acceptance test through the normal review door.

## blocks-the-design: Commit topology cannot identify the worker's sync

The classifier calls any two-parent commit with first parent equal to the launch SHA and second parent on `origin/<target>` `synced`; it similarly accepts any fast-forward onto that branch ([verification-head.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4527/src/lib/cloister/verification-head.ts), lines 46-59). `syncSingleRepo` does make such a merge (verification-runner.ts, lines 113-123), but an agent can make and push the same shaped merge after the worker launches. The supervisor will join the old worker (verification-worker-supervisor.ts, lines 181-185) and the runner can read the old head's CI verdict (verification-runner.ts, lines 267-281). The test covers only a merge made by the worker-shaped setup (verification-head.test.ts, lines 58-75). Record the actual head transition produced by this worker's sync and accept only that recorded result as `synced`; add an agent-made target merge case. A graph predicate alone cannot establish ownership.

## blocks-the-design: A moved head inherits stale local gates

The runner starts gates after capturing `launchHead` (verification-runner.ts, lines 364-368 and 554-580), then `resolveVerifiedHeadShort` selects a later HEAD for the CI lookup (lines 267-281 and 594-606). It never invalidates those gate results when HEAD moves. At pass time it snapshots the new HEAD and reports success on it (lines 892-955). The proposed test deliberately commits B during `runQualityGates` and expects a pass (verification-tests-on-ci.test.ts, lines 285-295), without proving that typecheck, lint, or the other gates ran against B. Thus A's local gates plus B's green CI can approve B. Change FR-4 and the test so a moved head makes the current run stale and triggers fresh verification of B before any pass, push, or review.

## blocks-the-design: Polyrepo CI lookup uses the wrapper head

`readWorkspaceHeadShort` runs Git in `workspacePath`, and `resolveVerifiedHeadShort` falls back to that same path after a move (verification-runner.ts, lines 257-282). In a polyrepo, `workspacePath` is the wrapper whose HEAD does not represent a member repo; `snapshotWorkspaceHeads` instead builds `repoKey@sha` values for the member roots ([git-utils.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4527/src/lib/git-utils.ts), lines 375-410). CI results are stored under the PR head SHA's first eight characters ([ci-failure-feedback.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4527/src/lib/cloister/ci-failure-feedback.ts), lines 295-313). A red CI result for a moved member head will therefore be missed by `readLatestCiTestResult`; the existing CI test uses a wrapper-only mock repo (verification-tests-on-ci.test.ts, lines 145-163). Resolve the CI verdict head from the relevant member repo or PR head, and test a real polyrepo layout with a red CI artifact for a moved member head.

## blocks-the-design: Partial snapshots can be classified as same

`snapshotWorkspaceHeads` silently omits a repo when its `git rev-parse HEAD` fails and returns the remaining heads (git-utils.ts, lines 391-410). `classifyVerificationHead` returns `same` immediately when the two anchor strings match and otherwise compares only the maps' sizes to each other ([verification-head.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4527/src/lib/cloister/verification-head.ts), lines 77-96). If the same required member is unreadable in both snapshots, the classifier says `same` despite having no evidence about that member. This contradicts the PRD's `unknown`-as-`moved` rule and can join a stale worker. Require a complete anchor for every expected repo before the equality shortcut; return `unknown` if any required repo is absent or unreadable, and test partial polyrepo snapshots.
