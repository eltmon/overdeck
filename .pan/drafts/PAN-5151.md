# PAN-5151 — New installations default to `claude.permissionMode: auto`; existing installations keep their current mode

**Issue:** [PAN-5151](https://github.com/eltmon/overdeck/issues/5151) · **Base:** `main` at `3235e7fa459` · **Planning mode:** `pan plan --auto` (no operator Q&A; defaults recorded below and in the xBRIEF `autoDecisions[]`).

This reverses the 2026-07-12 default (`c1ddd567846`, "make bypass (yolo) the recommended default permission mode"). A new installation launches Claude Code in Overdeck's `auto` mode. An installation that already exists keeps the mode it runs with today.

## Glossary

- **`claude.permissionMode`:** the key in `~/.overdeck/config.yaml` (global layer) or a project `.pan.yaml` that picks the permission flag for spawned Claude Code processes. Valid values: `auto`, `bypass`. Merged by `mergeConfigs` in `src/lib/config-yaml/merge.ts` (search `config.claude?.permissionMode !== undefined`).
- **`bypass`:** emits `--permission-mode bypassPermissions`. No tool call prompts.
- **`auto`:** Overdeck's own mode name. It emits `--permission-mode default` (`getClaudePermissionFlags` in `src/lib/claude-permissions.ts`). Overdeck's `auto-approve-hook` — a `PreToolUse` hook registered in `~/.claude/settings.json` — approves safe tool calls and blocks destructive ones. Without that hook every tool call prompts.
- **Resolved mode:** the value `resolvePermissionMode()` returns: `PAN_YOLO` env → explicit argument → merged config → (catch) fallback.
- **Global config file:** `~/.overdeck/config.yaml` = `GLOBAL_CONFIG_PATH` (`src/lib/config-yaml/defaults.ts`, last line: `export const GLOBAL_CONFIG_PATH = join(OVERDECK_HOME, 'config.yaml');`).
- **Legacy config file:** `~/.overdeck/config.toml` = `CONFIG_FILE` (`src/lib/paths.ts` line 53). `pan install` and `pan init` write this file, **not** `config.yaml` (`src/cli/commands/install.ts` line 572: `const configFile = join(OVERDECK_HOME, 'config.toml');`).
- **Pin:** the one-time decision this issue adds. On the first run of the new version it classifies the home as new or existing and, for an existing home whose `config.yaml` has no valid key, writes `claude.permissionMode: bypass` into it.
- **Pin marker:** `~/.overdeck/.claude-permission-mode-pin.json`. Its presence means the pin decision was made; the pin never runs again on that home.
- **New installation:** an Overdeck home where none of `config.yaml`, `config.toml`, `overdeck.db` exists when the pin first runs.
- **Existing installation:** an Overdeck home where at least one of those three files exists when the pin first runs.
- **Launch guard:** `ensureAutoApproveHookReady()` (new, `src/lib/agents/hook-readiness.ts`). Under resolved mode `auto` it makes sure the auto-approve hook is registered, or refuses the launch with an error that names `pan sync`.

### Which entry point runs first after an npm upgrade (the issue's implementation checkpoint)

No single existing entry point is guaranteed. `pan start` (`start.ts:977`), `pan strike` (`strike.ts:402`) and `pan knowledge` (`knowledge.ts:117`) spawn Claude Code inside the CLI process, so the first spawn after an upgrade can happen before any `pan sync` or dashboard restart. The npm postinstall (`scripts/postinstall.mjs`, run as `node scripts/postinstall.mjs || true`) is best-effort and cannot import TypeScript lib code. **Resolution:** run the pin at the two places every new-version process passes through before it can launch Claude Code: the CLI entry (`src/cli/index.ts`, before `program.parseAsync`) and dashboard server boot (`src/dashboard/server/main.ts`, before the HTTP listener binds). The dashboard covers the desktop app and supervisor restarts; the CLI covers every `pan` verb including `pan start`, `pan install`, `pan sync`, `pan up`, `pan reload`.

### Why "config.yaml exists" alone cannot classify a home, and why the pin runs once

`config.yaml` is created lazily by single-key writers (`color-themes/selection-write.ts`, `jev/settings.ts`, `model-presets/apply.ts`, `skill-packs/sources.ts`, `skill-overrides/store.ts`, `updateConversationsConfig`, the Settings page). On a new installation such a writer produces a `config.yaml` with no `claude.permissionMode`. A rule of "config.yaml without the key ⇒ bypass", applied on every run, would pin that new installation to bypass. So the pin decides **once**, stamps the marker whatever it decided, and never runs again. Because the pin runs at the very first `pan` command or dashboard boot of the new version — before `pan install` writes `config.toml`, before boot creates `overdeck.db` (`main.ts` line 172), and before any config writer — the three-file signal is reliable on the first run.

## Requirements

- **FR-1 (new installations start in auto):** with no `claude.permissionMode` in any config file and no `PAN_YOLO` / `--yolo`, a new installation resolves `auto` and launches Claude Code with `--permission-mode default`.
- **FR-2 (existing installations keep their mode):** on an existing installation, the first new-version run writes `claude.permissionMode: bypass` into `~/.overdeck/config.yaml` when the key is absent or holds an unrecognized value (the value these homes resolve today). A valid key (`auto` or `bypass`) is left unchanged. After the marker exists the pin never writes again.
- **FR-3 (one default everywhere):** `DEFAULT_CONFIG.claude.permissionMode`, the catch in `resolvePermissionMode`, `settings-api.ts` line 757 and `PermissionsSection.tsx` line 55 all fall back to `auto`.
- **FR-4 (Settings matches):** the Permissions section lists Auto first, titled `Auto (recommended)`, and titles Bypass `Bypass (yolo)`. The selected radio shows the config value, including `bypass` on a pinned existing installation.
- **FR-5 (auto never strands a user on prompts):** (a) when the resolved mode is `auto` and the auto-approve hook is not registered, `pan doctor` prints an `error` row whose fix names `pan sync`; (b) every local Claude Code launch site listed above runs the launch guard, which registers the hooks or refuses the launch with an error naming `pan sync`; (c) a remote Fly agent launch under resolved mode `auto` is refused with an error that says to choose `bypass`, because the VM has no hooks.
- **FR-6 (text matches behavior):** `docs/CONFIGURATION.md` (Permission Mode section), `configuration/mcp.mdx` (line 608), `docs/fly-provider.md` (permission-mode paragraph near line 362), the comments in `defaults.ts`, `claude-permissions.ts`, `schema.ts`, `config.ts`, `Settings/types.ts`, and `changelog.mdx` (Upcoming block) state the new default and the existing-installation rule.
- **NFR-1:** `PAN_YOLO`, `--yolo` and `--no-yolo` keep their precedence over config.
- **NFR-2:** config load (`loadConfigSync`, `loadConfigNoMigration`) still never throws, never prompts, and never writes. The pin is a separate step and never throws to its callers.
- **NFR-3:** the pin's fast path (marker present) costs one `stat` per `pan` invocation and loads no heavy modules; `src/dashboard/server/main.ts` stays at or under 1000 lines (`scripts/lint-file-size.sh` CEILING=1000, no allowlist row).

## Decisions (made here; recorded as `autoDecisions[]`)

1. **FR-2 mechanism = one-time pin + marker, run at CLI entry and dashboard boot** (the issue's proposal, corrected for the evidence above). Pin outcomes: `new-install` (marker only), `pinned-bypass` (write + marker), `already-set` (marker only), `skipped-unparseable` (no write, **no marker** — retried next run so a repaired file still gets pinned), `skipped-test-runner`.
2. **"Existing" = any of `config.yaml`, `config.toml`, `overdeck.db` exists at first run.** The glossary in the issue names only `config.yaml`, but its Why section requires every installation that exists today to keep its mode; an install that never wrote `config.yaml` (CLI users who only ran `pan install`, desktop users who never saved a setting) resolves `bypass` today. All three files are written only by Overdeck and only after the first-run pin on a fresh home.
3. **Invalid present value ⇒ pinned to `bypass`.** Today `mergeConfigs` warns and keeps the default (`bypass`) for an unrecognized value. After the flip the default is `auto`, so leaving the typo would change the mode. The pin replaces it with `bypass` and its notice names the old value.
4. **Config-load failure fallback = `auto`** (the issue's proposal: the less permissive mode). Note the realistic failure path: a YAML parse error goes `loadYamlFile → console.error → null → DEFAULT_CONFIG` (`src/lib/config-yaml/load.ts` lines 38–51), not through the catch at `claude-permissions.ts:73`. Both paths now yield `auto`; the launch guard keeps either from stranding a user.
5. **This issue does not change what `auto` emits** (`--permission-mode default`); mapping to a native Claude Code mode is [#3760](https://github.com/eltmon/overdeck/issues/3760).
6. **The claudish pin in NFR-1 of the issue does not exist in code.** `git grep -i claudish -- src` finds only two comments (`costs/reconciler.ts:345`, `model-fallback.ts:406`); `permission-mode-leak.test.ts` asserts non-Anthropic providers honor `auto`. Nothing to preserve; the stale caveat at `docs/CONFIGURATION.md:226` is removed.
7. **Remote Fly agents under `auto` are refused, not silently bypassed.** The VM has no Overdeck hooks (`fly-provider.ts:622` writes only theme + `defaultMode`), so `auto` there prompts forever on a VM nobody watches. Pinning remote to bypass would violate the trust property locked by `remote-settings-no-leak.test.ts` / `permission-mode-leak.test.ts`. A clear refusal lets the operator choose.
8. **Launch guard placement:** inside both command builders (`getAgentRuntimeBaseCommand`, `getRoleRuntimeBaseCommand`, after the non-claude early returns and after the `OVERDECK_TEST_HARNESS_COMMAND` early return), in the `spawn-prep.ts` resume branch for claude-code, at the top of `spawnConversationSession` for `launchCommandKind === 'claude-code'`, and in the planning message route. `runModelSummary` (`-p`) is exempt (see table). Double calls (e.g. spawn.ts already provisions) are harmless: the guard's fast path is one `settings.json` read.
9. **The pin uses no backup file and no settings write queue.** Every write is atomic (`writeFileAtomic` from `src/lib/model-presets/state.ts`, preserves mode, temp + rename) and edits one key with comments preserved. `runSettingsWriteSerialized` is in-process only and the pin runs before the dashboard serves requests and in separate CLI processes, so the queue protects nothing here. The config cache is mtime-keyed (`getConfigMtimes` in `load.ts`), so no `clearConfigCache()` call is needed.
10. **The pin prints one notice on stderr** (CLI) / `console.log` (dashboard) only when it writes: `Overdeck: kept this installation on claude.permissionMode: bypass (written to ~/.overdeck/config.yaml). New installations now default to auto; change it in Settings → Permissions.`

export async function ensureAutoApproveHookReady(
  opts: { settingsPath?: string; binDir?: string; mode?: ClaudePermissionMode } = {},
): Promise<void> {
  const mode = opts.mode ?? resolvePermissionMode();
  if (mode !== 'auto') return;
  if (!opts.settingsPath && process.env.VITEST) return; // same test-runner precedent as provisionClaudeHooks
  const settingsPath = opts.settingsPath ?? join(homedir(), '.claude', 'settings.json');
  const binDir = opts.binDir ?? BIN_DIR;
  if (await isRegisteredOnDisk(settingsPath, binDir)) return;          // read + JSON.parse; false on any error
  const result = await provisionClaudeHooks({ settingsPath, binDir });
  if (result.ok && await isRegisteredOnDisk(settingsPath, binDir)) return;
  throw new Error(

      + `${result.ok ? '' : ` (${result.reason})`}. Without it every tool call prompts. `
      + 'Run `pan sync` to register it (it needs jq), or set claude.permissionMode: bypass in Settings → Permissions.',
  );
}
