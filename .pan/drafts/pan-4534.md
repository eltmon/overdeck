# PAN-4534 — CI failure feedback names the failing test

**Issue:** [PAN-4534](https://github.com/eltmon/overdeck/issues/4534)
**PR:** [#4613](https://github.com/eltmon/overdeck/pull/4613)
**Status:** delivered. This PRD records the work in PR #4613.

## Glossary

- **CI failure relay**: `relayCiFailureFeedback` in `src/lib/cloister/ci-failure-feedback.ts`. It fires on a failing
  `check_run` webhook and writes `.overdeck/feedback/NNN-ci-monitor-failed.md` for the work agent.
- **Check run**: one job's result on a commit (`GET /repos/{owner}/{repo}/commits/{sha}/check-runs`). A check run
  concludes as soon as its job ends, while the workflow run that holds it may still be `in_progress`.
- **Job log**: `GET /repos/{owner}/{repo}/actions/jobs/{job_id}/logs`. For a GitHub Actions check run, the check
  run id is the job id. GitHub publishes the log a few seconds after the job ends, and until then the call returns 404.
- **Aggregate check**: a gate job such as `test` that only echoes the result of its shards (`test-shard (4/4)`).
- **Commit-status test check** (PAN-4589): a test check reported as a commit status (Dagger Cloud), not as a check
  run. The relay lists these separately.

## Root cause

`listFailingRuns` in `ci-failure-feedback.ts` looked only for workflow runs with status `failure`
(`gh run list --status failure`). The relay fires on the failing shard's check run, and at that moment the workflow
run is usually still `in_progress`. So `collectFailures` returned `[]`, and the feedback said "no failing workflow
runs were found". This was seen on PAN-4259 and PAN-4260 on 2026-10-04.

## Requirements

- **FR-1**: Failures come from the head's check runs (`conclusion == "failure"`). For a GitHub Actions check run,
  the failure carries that job's log excerpt. The workflow-run lookup stays as the fallback when no check run reports
  a failure, or when the check runs cannot be read.
- **FR-2**: The excerpt is the Vitest failure section, from the first `FAIL` line through the `Test Files … failed`
  summary, capped at about 2000 characters. When the log has no such section, the excerpt is the tail of the log.
- **FR-3**: An aggregate check is dropped when one of its shards also failed, and kept when it failed alone.
- **FR-4**: A job log that is not published yet is retried with bounded backoff (`JOB_LOG_RETRY_DELAYS_MS`, 2 minutes
  in total). When no log ever appears, the feedback lists the failing check names, their job-log commands and their
  check URLs.
- **FR-5**: `docs/PIPELINE-GATES.md` describes what the CI failure feedback contains.

## Work items

1. **check-run-failures** (FR-1, FR-2, FR-3, FR-4). New `src/lib/cloister/ci-check-run-failures.ts` exports:
   - `CheckRunFailure`.
   - `JOB_LOG_RETRY_DELAYS_MS` (`[5000, 10000, 20000, 40000, 45000]`).
   - `withoutAggregateChecks`, which drops `X` when another failing check is named `X-…`, `X (…` or `X / …`.
   - `extractTestFailureExcerpt`, which strips timestamps.
   - `collectCheckRunFailures`, which returns null when the check runs cannot be read.
   Test: new `src/lib/cloister/__tests__/ci-check-run-failures.test.ts`.
2. **relay-uses-check-runs** (FR-1, FR-4). In `ci-failure-feedback.ts`:
   - `CiFailure` gains optional `runId`, `jobId` and `url`.
   - `collectFailures` tries `collectCheckRunFailures` first and falls back to `listFailingRuns`.
   - `buildFeedbackBody` prints the `Run:`, `Job log:` and `Check:` lines only when it has each value.
   The commit-status section from PAN-4589 stays as main has it.
   Tests: `tests/unit/lib/cloister/ci-failure-feedback.test.ts`, describe "PAN-4534: failures come from the head's
   check runs, with the failing test named" (fake timers for the retries). The debounce test now counts the extra
   check-runs read.
3. **docs** (FR-5). `docs/PIPELINE-GATES.md` gets the bullet "What the CI failure feedback contains (PAN-4534)".

## Non-goals

- No change to when the relay fires, to its debounce, or to its attempt accounting.
- No GitLab change. GitLab reports one pipeline verdict.
- No new HTTP route, CLI verb or setting.

## Acceptance criteria

1. Given a failing `test-shard (4/4)` check run while the workflow run is still `in_progress`, then the feedback names
   the failing test file and test title from the job log.
2. Given only the aggregate `test` job and one failing shard job, then the feedback reports the shard's failure, not
   the aggregate echo.
3. Given the job log returns 404 at first and is available on retry, then the feedback contains the excerpt (fake
   timers).
4. Given no log is ever available, then the fallback lists the failing check names and URLs.
5. `docs/PIPELINE-GATES.md` describes what the CI failure feedback contains.
