**Issue:** [PAN-4435](https://github.com/eltmon/overdeck/issues/4435) · **Epic:** [PAN-2350](https://github.com/eltmon/overdeck/issues/2350) (Overdeck Anywhere, Phase 0) · **Split from:** [PAN-2351](https://github.com/eltmon/overdeck/issues/2351) (FR-6 and the Settings half of FR-1 of `.pan/drafts/pan-2351.md`)
**Written:** 2026-09-30 against `main` at `2889c7eed34`. PAN-2351 is merged (`9118416df74`, #4441), so the token registry, the `/api/access-tokens` routes and `pan token` exist. This issue adds only the dashboard surfaces and the config plumbing for the flag.

## Glossary

- **Access-token registry** — `~/.overdeck/access-tokens.json`, managed by `src/lib/access-tokens.ts`. Holds paired devices (`kind: 'device'`) and scoped API tokens (`kind: 'token'`). Plaintext tokens start with `odk_` and are never stored; only a SHA-256 hash is.
- **Scoped token** — a registry record with `kind: 'token'` and one or more scopes from `ACCESS_TOKEN_SCOPES` (`src/lib/access-tokens.ts:42`): `read:events`, `read:state`, `read:conversations`, `tell`, `operate`, `admin`.
- **Root credential** — the internal token or the root session cookie (`overdeck_session`). Only a root credential may create or revoke tokens (PAN-2351 D-11). A browser on this machine normally holds the root session.
- **Device session** — a browser paired with `pan pair`; it carries the `overdeck_device` cookie and `admin` scope. It can list tokens but gets **403** on create and revoke.
- **Session mint** — `POST /api/dashboard/session`. A loopback peer may mint a root session without a credential, unless `require_token_mint` is on.
- **`require_token_mint`** — `dashboard.require_token_mint` in `~/.overdeck/config.yaml` (boolean, default `false`). When `true`, being on this machine no longer mints a root session, and a loopback request carrying a proxy header counts as remote. Enforced since PAN-3762 by `rejectUnauthorizedDashboardSessionMintRequest` (`src/dashboard/server/routes/dashboard-auth.ts:359`) and the remote request gate (`src/dashboard/server/remote-request-gate.ts:72`).
- **Remote-access config cache** — `readRemoteAccessConfig()` in `src/lib/remote-access/config.ts` parses raw `config.yaml` once and caches it for the process lifetime. Today a change needs a dashboard restart.
- **Settings autosave** — the Settings page keeps the whole `/api/settings` payload in `formData`; `applySettings(next)` (`SettingsPage.tsx:440`) schedules a debounced `PUT /api/settings` with the full document.
- **File-size cap** — `scripts/lint-file-size.sh` fails any `src` file over 1000 lines unless it is at or under its last row in `scripts/file-size-allowlist.txt`. Agents may never raise a cap.

## Decisions

- **D-1 Settings GET reports the enforced value.** `loadSettingsApi()` sets `dashboard.require_token_mint` from `readRemoteAccessConfig().requireTokenMint`, not from the merged config. The merged config also folds in a project `.pan.yaml`, which enforcement never reads, so the toggle could otherwise show `true` while enforcement is `false`. The schema and normalizer entry still exist (WI-1) so `YamlConfig` types the write and `loadConfig` consumers see the key.
- **D-2 Invalid values are `false` and never throw.** The normalizer sets `requireTokenMint` to `value === true`, the same rule as `readRemoteAccessConfig()`. `mergeRemoteConfig` throws on bad input; this merger must not, because a throw fails the whole config load.
- **D-3 Preserve on absent.** `writeYamlConfigPreservingComments` touches `['dashboard']` only when the PUT carries a `dashboard` object, and then with `setBlockMergePreserving` (never `setIn`), so a client that omits the block never turns the security flag off. This differs from `remote`, which is deleted when absent.
- **D-4 Cache invalidation lives in `saveSettingsApi`.** Rename `_resetRemoteAccessConfigForTests` to `invalidateRemoteAccessConfig` (one function, no test-only twin) and call it right after `clearConfigCache()` at `settings-api.ts:1052`. `routes/settings.ts` is at its size cap and gets no new line. A hand edit of `config.yaml` still needs a restart; the docs say so.
- **D-5 Scope list in the frontend.** Add `sections/accessTokenScopes.ts` with the six scopes and one plain-words description each (copied from `configuration/remote-access.mdx:120-126`). A root-vitest parity test imports it and `ACCESS_TOKEN_SCOPES` from `src/lib/access-tokens.ts` and asserts the same ids in the same order. Moving the list to `@overdeck/contracts` would touch the security module and the contracts build for six strings.
- **D-6 One nav entry, one section.** Nav item `{ id: 'access-tokens', label: 'Access Tokens', icon: KeyRound }` goes right after `remote`. The section holds the `require_token_mint` toggle row first, then the token list and the Create button.
- **D-7 Plaintext lives in dialog state only.** The create response is kept in `CreateAccessTokenDialog` component state. Closing the dialog clears it and calls `mutation.reset()`, so react-query's retained `data` cannot show it again. It never enters the `['access-tokens']` query cache, `localStorage`, or a log line.
- **D-8 403 is an explanation, not a crash.** Any 403 from the three routes renders a notice with the server's `error` text plus: "This browser is signed in as a paired device or with a scoped token. Only this machine's own dashboard session can create or revoke access tokens; use `pan token` on this machine instead." Other failures render `error` text inline. No `window.alert`/`window.confirm`.
- **D-9 UAT evidence goes in the PR body.** No committed screenshots (an `images/` path would add a seventh subsystem to the plan-size lint).

## Requirements

- **FR-1** Settings has an "Access Tokens" nav entry and a section `id="access-tokens"` that lists every `kind: 'token'` record with name, scopes (comma-separated text), created time, last used time ("Never" when `null`) and revoked time ("—" when absent).
- **FR-2** A "Create token" dialog takes a name and one checkbox per scope. Create is disabled until the trimmed name is non-empty and at least one scope is checked. On success the dialog shows the plaintext once in a read-only field with a Copy button; after close the plaintext is gone, the list shows the new record, and reopening shows an empty form.
- **FR-3** Each non-revoked row has a Revoke button. It asks for confirmation through `useConfirm` (destructive variant); on confirm it sends `DELETE /api/access-tokens/:id` and the list then shows the revoked time. Revoked rows show no Revoke button.
- **FR-4** A 403 from list, create or revoke renders the D-8 explanation; the page keeps rendering.
- **FR-5** `YamlConfig.dashboard?.require_token_mint?: boolean` is typed in the new `src/lib/config-yaml/schema-dashboard.ts`; the merged config carries `dashboard?: { requireTokenMint: boolean }` per D-2.
- **FR-6** `GET /api/settings` includes `dashboard: { require_token_mint: boolean }` per D-1. `PUT /api/settings` accepts it, rejects a non-object `dashboard` or a non-boolean `require_token_mint` with 400, and writes it per D-3.
- **FR-7** `updateSettingsApi` merges `dashboard` like `remote`.
- **FR-8** After a Settings save changes the flag, the next session mint and gate check use the new value without a restart (D-4).
- **FR-9** The Access Tokens section's first row is a toggle "Require a token to sign in" bound to `formData.dashboard.require_token_mint` through `applySettings`. Its description says: "Turn this on when a local reverse proxy (Tailscale Serve, cloudflared) forwards outside traffic. Browsers that already have a session keep working; a new browser on this machine then needs the `#overdeck_token=` link or pairing to sign in."
- **FR-10** `configuration/remote-access.mdx` and `docs/DASHBOARD-AUTH.md` describe the Settings section and the toggle, and no longer say a restart is needed after a Settings change.
- **NFR-1** No `execSync` in server-reachable code. `routes/settings.ts` gets no new lines; `schema.ts` stays ≤ 1114 lines and `settings-api.ts` ≤ 1508 (`bash scripts/lint-file-size.sh` passes).
- **NFR-2** The plaintext token never enters the react-query cache, browser storage or a log (D-7).
- **NFR-3** Every new frontend test file is appended to `test:frontend-subset` in `package.json`, or CI never runs it.
- **NFR-4** UI follows the `pan-style-guide` skill: no pill badges, no decorative color, muted secondary text; the toggle uses `Settings/Shared/Toggle.tsx`.
- **NFR-5** Browser verification uses an isolated Playwright browser context and a throwaway `OVERDECK_HOME`; it never reuses another agent's browser or the operator's `~/.overdeck`.

## Intersecting repo rules (restated)

- No `execSync` in dashboard-server-reachable code; use async I/O.
- Never raise a `scripts/file-size-allowlist.txt` cap. If a file would pass its cap, extract a module.
- New source-reading ("grep the source") tests fail lint; test by rendering or by calling functions. Any added `skipIf`/`.only` fails the test-skip gate.

- The dashboard runs only as `node dist/dashboard/server.js` under Node 22, after `npm run build`. Never Bun, never tsx.
- No destructive HTTP requests against the operator's live dashboard. UAT uses its own server and temp home.
