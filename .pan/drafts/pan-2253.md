# PAN-2253 — Dashboard recovery guardian: make the supervisor durable via a systemd user unit

**Issue:** [PAN-2253](https://github.com/eltmon/overdeck/issues/2253)
**Mode:** `pan plan --auto` (no interactive Q&A; inferred choices recorded under Planning Q&A / autoDecisions)

---

## Glossary

- **Dashboard server** — `dist/dashboard/server.js`, Node 22, API port 3011 / UI port 3010. Hosts the Deacon (agent lifecycle watchdog) *in-process*, so it cannot restart its own host.
- **Supervisor sidecar** — `dist/supervisor/server.js`, HTTP on port 3012. An *external* process started by `pan up` (`startSupervisorProcessSync()` in `src/lib/supervisor.ts:85`) whose `SupervisorWatchdog` (`src/supervisor/watchdog.ts`) polls the dashboard `/api/health` + `/api/deacon/status` and restarts the dashboard on failure. Stopped by `pan down` (`stopSupervisorProcessSync()`).
- **SupervisorWatchdog** — the polling class inside the sidecar. Already implements dead-vs-busy failure classification, restart rate-limiting (`maxRestarts=3` / `windowMs=5min`), persistent give-up (`supervisor-watchdog.json` + `WATCHDOG GIVING UP` log), and the deacon-patrol staleness check.
- **systemd user unit** — a `~/.config/systemd/user/<name>.service` managed by `systemctl --user`. `Restart=on-failure` revives a process that exits abnormally; a clean `systemctl --user stop` is NOT auto-restarted.
- **Operator-intent latch** — a durable "stay down" signal. Here it is systemd's own clean-stopped unit state: after `systemctl --user stop`, the unit stays down until an explicit `start`.
- **Health identity** — the `{ repoRoot, mode }` fields the dashboard returns on `GET /api/health` (`getDashboardIdentity()` in `src/dashboard/server/identity.ts:16`; `mode` is `'peer'` when `OVERDECK_DISABLE_DEACON=1`, else `'primary'`). This is the #2252 field; it already exists.
- **`systemctl --user` availability** — a working per-user systemd manager + DBus session. Absent in most containers, CI, macOS, and non-systemd Linux.

## Problem

On 2026-07-02 the dashboard was dark on port 3011 for ~10 minutes with nothing attempting recovery. The Deacon lives inside the dashboard process, so it cannot restart its own host; recovery happened only because an agent conversation happened to notice.

Since then a **supervisor sidecar** was added and *is* the intended recovery guardian. But it has two structural gaps:

1. **The guardian has no guardian.** The supervisor is a detached child of the `pan up` invocation (`src/lib/supervisor.ts:112` `spawn(process.execPath, [bundle], { detached: true })`). If the supervisor process itself crashes or is killed, nothing revives it — the dashboard is then unguarded and can go dark exactly as in the incident. There is no systemd unit, cron entry, or external watchdog for the supervisor.
2. **The watchdog trusts a bare 200.** `SupervisorWatchdog.runCheck()` (`src/supervisor/watchdog.ts:204`) treats any `response.ok` on `/api/health` as healthy. A squatter process that grabbed port 3011 and answers 200 (issue #2252's scenario) would satisfy the guardian even though it is not the real primary dashboard.

The issue also lists two design requirements that are **already satisfied** and must not be duplicated:
- Distinguish down from busy + rate-limit — the watchdog already classifies hard-down (`failThreshold=3`) vs busy/timeout (`busyFailThreshold=12`) and gives up after `maxRestarts` (`watchdog.ts:256-305`).
- The 15s health-timeout that makes every watchdog restart fail — owned by **#2286 (active)**, an explicit prerequisite. Not in scope here.

## Proposal

Wrap the existing supervisor sidecar in a **systemd user unit** (`overdeck-supervisor.service`) so the guardian survives its own death, and route operator lifecycle through it:

- The unit's `ExecStart` runs the supervisor bundle under the same Node 22 binary + env the detached path uses today, in the foreground so systemd owns it. `Restart=on-failure` + `RestartSec` revive an abnormally-exited supervisor. `StartLimitIntervalSec` + `StartLimitBurst` cap a supervisor crash-loop (e.g. missing bundle) and leave the unit `failed` instead of looping forever.
- `pan up` installs (idempotently) + `systemctl --user start`s the unit when `systemctl --user` is available; otherwise it falls back to today's `startSupervisorProcessSync()` unchanged.
- `pan down` `systemctl --user stop`s the unit — a clean stop systemd will not auto-restart = the operator-intent latch; falls back to `stopSupervisorProcessSync()` otherwise.
- `pan restart --dashboard` stops fighting systemd: its manual `stopSupervisorProcessSync()/startSupervisorProcessSync()` cycle (`src/cli/commands/restart.ts:214-219`) is skipped when the unit owns the supervisor (systemd keeps it alive across the dashboard restart).
- The watchdog health probe verifies identity: `repoRoot` matches the host primary root AND `mode === 'primary'`; a foreign/squatter 200 is treated as unhealthy.
- When the unit gives up (StartLimitBurst tripped → `failed`), a loud operator notification is surfaced via the existing restart-announcer pipeline.

**Why the unit supervises the supervisor, not the dashboard directly.** Making systemd own the dashboard process would create two owners of it — systemd's `Restart=` and the watchdog's `pan restart --dashboard` — the exact dual-ownership churn class PAN-1714 documented. The supervisor is already the single owner of dashboard recovery; systemd only needs to keep *that* alive. This is additive (the dashboard launch path is untouched) and closes the identified gap minimally. Trade-off: the "kill -9 the dashboard → back in 60s" acceptance path runs through the watchdog + #2286 rather than systemd directly — which the issue already accepts by declaring #2286 the prerequisite.

## Non-Goals

- Full-stack cold-boot recovery (bringing traefik + cliproxy + dashboard up after a machine reboot from nothing). The unit is deliberately NOT `WantedBy` a boot target and lingering is NOT enabled, so it does not start into a stackless post-reboot environment. Filed as a follow-up.
- Duplicating the #2286 `pan restart --dashboard` 15s health-timeout fix. It is a prerequisite, owned elsewhere.
- Making systemd own the dashboard server process directly (rejected — PAN-1714 dual-ownership churn).
- Non-Linux service managers (launchd, Windows services). Those platforms use the existing detached-spawn fallback unchanged.
- Changing the watchdog's existing dead-vs-busy thresholds, give-up counters, or deacon-patrol logic.

## Requirements

### Functional
- **FR-1** — A systemd user unit `overdeck-supervisor.service` supervises the supervisor sidecar with `Restart=on-failure`; a supervisor that exits abnormally (crash / SIGKILL) is revived automatically by systemd.
- **FR-2** — The unit rate-limits supervisor restarts with `StartLimitIntervalSec` + `StartLimitBurst`; exceeding the burst leaves the unit in `failed` state rather than restarting forever.
- **FR-3** — `pan up` starts the supervisor through the unit (`systemctl --user start`) when `systemctl --user` is available, and falls back to `startSupervisorProcessSync()` otherwise, with no error surfaced on fallback.
- **FR-4** — `pan down` stops the supervisor through the unit (`systemctl --user stop`), which systemd will not auto-restart (operator-intent latch); falls back to `stopSupervisorProcessSync()` otherwise.
- **FR-5** — `pan restart --dashboard` skips its manual supervisor stop/start cycle when the unit owns the supervisor, so the restart does not fight systemd.
- **FR-6** — The SupervisorWatchdog health probe verifies dashboard identity (`repoRoot` == host primary root AND `mode === 'primary'`); a foreign / squatter 200 response is classified unhealthy, not healthy.
- **FR-7** — When the unit reaches `failed` (StartLimitBurst tripped), a loud operator notification is surfaced through the existing restart-announcer activity pipeline.

### Non-Functional
- **NFR-1** — Every `systemctl` interaction reachable from the dashboard event loop uses async `execAsync`/`spawn`, never `execSync` (PAN-70).
- **NFR-2** — Graceful degradation: on hosts without a working `systemctl --user` (containers with `OVERDECK_DISABLE_DEACON=1`, CI, macOS, non-systemd Linux) behavior is exactly today's — no unit written, detached spawn used, no errors.
- **NFR-3** — Unit install is idempotent; re-running `pan up` neither duplicates nor corrupts the unit and does not restart a healthy supervisor.

## Planning Q&A (auto-mode inferred decisions)

- **Unit supervises the supervisor sidecar, not the dashboard directly.** Rationale: avoids PAN-1714 dual-ownership churn; additive (dashboard launch untouched); closes the "guardian has no guardian" gap minimally. Deviates from the issue's suggested `overdeck-dashboard.service` name → named `overdeck-supervisor.service` to reflect what it guards.
- **Reboot / cold-boot recovery out of scope.** Rationale: the unit is not enabled at boot and lingering is off, so it never starts into a stackless post-reboot environment; full-stack boot bring-up is a separate, larger change. Filed as follow-up.
- **#2286 treated as a prerequisite, not duplicated.** Rationale: the issue explicitly declares it so; the dashboard-restart-under-load path is fixed there.
- **Reuse the existing restart-announcer for give-up notification** rather than adding a new CLI verb (avoids skills↔CLI lockstep churn). The dashboard checks `systemctl --user is-failed` and writes a give-up restart-status the announcer already surfaces.
- **Identity check reuses the existing `getDashboardIdentity()` `{repoRoot, mode}` contract** (#2252, already shipped) mirroring `waitForDashboardHealthPromise`'s `expectedIdentity` logic.
