# PAN-4338: Handoffs, forks and workers refuse a project's primary checkout as cwd

**Issue:** [PAN-4338](https://github.com/eltmon/overdeck/issues/4338)
**Parent PRD:** `.pan/drafts/deft-adoption.md`, "Issue 4" (line ~272).
**Related:** #2409, #3284 (work agent writes outside its workspace), #4337 (branch drift inside a workspace).
**Planning mode:** `pan plan --auto` — every decision below is made in this document and mirrored in the xBRIEF `plan.autoDecisions[]`.

## Glossary

- **Primary checkout** — the directory a project is registered at in `~/.overdeck/projects.yaml` (`projects.<key>.path`), or the directory of a polyrepo member repo (`resolve(project.path, workspace.repos[i].path)`). It is the shared checkout on the project's default branch. Commits made there bypass review and land on `main`.
- **Worktree / workspace** — a separate git worktree, for example `<root>/workspaces/feature-<issue>/` or `$HOME/Projects/hoff-<slug>`. It has its own git top level, even when it lives inside the primary directory tree.
- **Git top level** — the output of `git rev-parse --show-toplevel` run in a directory: the root of the work tree that directory belongs to.
- **Fork route** — `POST /api/conversations/:name/summary-fork`, handled by `handleConversationSummaryFork` in `src/lib/overdeck/conversation-forks.ts`. It serves `pan fork` (summary/plain) and `pan handoff` (handoff mode) and the dashboard Fork modal.
- **Explicit cwd** — the `cwd` field in the fork route's JSON body. The CLI sends it only when the user passed `--cwd`. The dashboard UI never sends it (`src/dashboard/frontend/src/components/CommandDeck/useConversationMutations.ts`, `summaryForkConversation` body has no `cwd`).
- **Caller kind** — `'operator' | 'agent'`, as computed by `verdictCallerFromEnv(process.env, readAncestorAgentIds).kind` in `src/lib/cloister/verdict-caller.ts`. A process with no `OVERDECK_AGENT_ID` (and no managed-pane markers) or with a `conv-*` id is `operator`; any other managed pane, or any ancestor with a non-`conv-` agent id, is `agent`.
- **`allowPrimary`** — a new boolean body field on the fork route. It asks the server to accept a primary checkout as the explicit cwd. It is honored only for operator callers.
- **Worker** — an agent started by `pan worker run` through `startWorker` in `src/lib/agents/worker/start.ts`.

## Problem

`validateCwdContainment` exists twice and accepts any existing directory under `$HOME`, including a project's primary checkout:

- `src/lib/overdeck/conversation-forks.ts:172` (`async function validateCwdContainment(cwd: string): Promise<boolean>`), called at `:826` (`if (cwd && !(await validateCwdContainment(cwd))) {`).
- `src/lib/overdeck/conversation-runtime.ts:224` (same name, same body), called at `:393` (model/harness switch on an existing conversation) and `:1131` (resume of an existing conversation).

So `pan handoff --cwd ~/Projects/overdeck self "..."` starts an agent in the primary checkout. The 2026-07-01 incident in `sync-sources/rules/handoff-isolate-cwd.md` is exactly this: the handoff agent branched and committed in the primary checkout, which drifted local `main`. Today only the written rule prevents it.

`pan worker run` already confines an explicit `--cwd` to the issue workspace (`src/lib/agents/worker/start.ts:118-127`), and its default read-write cwd is a fresh `.swarm/worker-<n>` worktree. The one gap is a symlink inside the workspace that resolves to a primary checkout (for example a `link_type: symlink` member repo in a polyrepo workspace). `realpath` follows it, the resolved path is "inside" nothing the worker guard checks, and a read-write worker then commits in the primary member repo.

## Decisions (made here; mirrored in `plan.autoDecisions[]`)

- **D1 — The refusal applies only to the explicit cwd of the fork route and to the explicit `--cwd` of a read-write worker.** It does not apply to the inherited cwd (`issueWorkspaceCwd || conv.cwd || process.cwd()` at `conversation-forks.ts` "effectiveCwd"). Reason: operator conversations (including `conv-flywheel`) run in the primary checkout by design, and the rule itself tells agents to run `pan handoff` from the project directory. Refusing the inherited cwd would break every `pan handoff self` from such a conversation and the existing test "keeps the parent cwd when the issue workspace does not exist".
- **D2 — Resume and model/harness switch of an existing conversation are never refused.** The two `validateCwdContainment` copies are collapsed into one shared helper (issue work item 2), but the primary-checkout check is added only at the fork route, not inside the shared containment helper. Reason: `conversation-runtime.ts:393` and `:1131` validate the `cwd` of a conversation that already exists; refusing there would make every primary-checkout conversation impossible to resume.
- **D3 — "Is the primary checkout" means: the canonical path, or its git top level, equals a registered root or member root.** A path passes the check only when neither its canonical form nor its git top level matches. So `--cwd <root>/src` is refused (its git top level is `<root>`), while `<root>/workspaces/feature-x` passes (it is its own worktree with its own top level). When `git rev-parse --show-toplevel` fails (not a git tree, e.g. a polyrepo wrapper directory), only the canonical path is compared. Reason: commits from a subdirectory land in the primary checkout just the same; plain equality would leave that hole open.
- **D4 — The resolver lives in a new leaf module `src/lib/projects/primary-checkout.ts` exporting `findPrimaryCheckout`, not in `src/lib/projects.ts`.** Reason: `projects.ts` is at 1217 lines, exactly its `scripts/file-size-allowlist.txt` ceiling (`1217 src/lib/projects.ts # PAN-4223`); the sibling `src/lib/projects/path-containment.ts` already holds the path helpers. The issue's name `isPrimaryCheckout` becomes `findPrimaryCheckout` because it returns the match (needed for the error message), not a boolean.
- **D5 — `allowPrimary` trust model copies `pan review restart` (#3853).** The CLI (`fork-client.ts`) always sends `callerKind` computed by `verdictCallerFromEnv(process.env, readAncestorAgentIds).kind`, and sends `allowPrimary: true` only when the user passes the new `--allow-primary` flag on `pan fork` or `pan handoff`. The server honors `allowPrimary` only when `callerKind` is `'operator'` or absent (the dashboard UI sends no `callerKind`). `callerKind: 'agent'` or any other value means `allowPrimary` is ignored and the request is refused. This is accident prevention: it stops an agent that uses the CLI, but it is not a security boundary against a process that crafts raw HTTP without `callerKind`.
- **D6 — Workers get no override.** A read-write worker whose explicit `--cwd` resolves to a primary checkout is always refused; `--read-only` workers are not checked (the read-only git guard already blocks commits). The issue gives workers no `allowPrimary`.
- **D7 — No frontend change.** The dashboard Fork modal sends no `cwd`, so it can never hit the refusal.
- **D8 — Error message.** `Invalid cwd: <path> is the primary checkout of <label>; use a worktree`, where `<path>` is the cwd string exactly as the caller supplied it and `<label>` is the project key for a project root, or `<key>/<repoName>` for a polyrepo member repo. The worker uses the same message with `--cwd` in place of `Invalid cwd`: `--cwd <path> is the primary checkout of <label>; use a worktree`.

## Requirements

### Functional

- **FR-1** — `findPrimaryCheckout(path, deps?)` returns `{ projectKey, repoName, root }` when the canonical path or its git top level equals a registered project root or a polyrepo member root, else `null`. `repoName` is `null` for a project root.
- **FR-2** — Both conversation files use one shared `validateCwdContainment` with unchanged semantics (absolute, no `..` segment, existing directory, under `$HOME`).
- **FR-3** — The fork route returns HTTP 400 with the D8 message when the explicit `cwd` is a primary checkout, in every fork mode (`summary`, `plain`, `handoff`), unless `allowPrimary` is honored per D5. No conversation row is created on refusal.
- **FR-4** — The fork route accepts an explicit `cwd` that is a worktree of a registered project (for example `<root>/workspaces/feature-pan-1`).
- **FR-5** — `pan fork` and `pan handoff` accept `--allow-primary`; `fork-client.ts` always sends `callerKind` and sends `allowPrimary: true` only with the flag.
- **FR-6** — `startWorker` throws the D8 worker message, before allocating a worker id, when `readOnly` is false and the realpath'd explicit `--cwd` is a primary checkout.
- **FR-7** — The rule, skills and reference docs state that the server refuses a primary checkout as `--cwd`, and name `--allow-primary` as the operator-only override.

### Non-functional

- **NFR-1** — Every new filesystem or git call on a request path is async (`fs.promises`, `execFile` promisified). No `execSync`/`*Sync` in `primary-checkout.ts` or on the fork route (repo rule: no `execSync` in server-reachable code).
- **NFR-2** — `src/lib/overdeck/conversation-runtime.ts` does not grow (it sits at its allowlist ceiling of 1248); the collapse must shrink it. `src/lib/projects.ts` is not touched.
- **NFR-3** — Tests use injected dependencies or real temp directories under the test's `$HOME`; no test touches the real `~/.overdeck/projects.yaml`.

/** Validate a caller-supplied cwd is an existing directory under the user's home. */
export async function validateCwdContainment(cwd: string): Promise<boolean> {
  if (!cwd.startsWith('/')) return false;
  const segments = cwd.split('/').filter(Boolean);
  if (segments.includes('..')) return false;
  try {
    const resolved = await realpath(cwd);
    const stats = await stat(resolved);
    if (!stats.isDirectory()) return false;
    const home = homedir();
    return resolved.startsWith(`${home}/`) || resolved === home;
  } catch {
    return false;
  }
}

- Any dashboard frontend change (D7).
- A security boundary against a process that sends raw HTTP to the fork route without `callerKind` (D5: accident prevention only).

## Repo rules that intersect this change

- **No `execSync` in server-reachable code.** `primary-checkout.ts` is called from the fork route, so its git call uses promisified `execFile` and its fs calls use `fs.promises` (`canonicalPathAsync`).
- **Fake timers for delay-based tests.** If a `fork-client.test.ts` case waits on the poll loop, use `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()`, or pass `pollMs: 0`; never a real multi-second wait.
- **File-size ratchet.** `scripts/lint-file-size.sh` compares against `origin/main`. `conversation-runtime.ts` (1248, at ceiling) must shrink; `src/cli/index.ts` (1280 vs its last allowlist row 1379) may grow by two lines; `projects.ts` is not touched.
- **Generated manifest.** Adding a CLI option changes `packages/contracts/src/composer-commands.generated.ts`; regenerate with `npm run generate:slash-commands` after `npm run build:cli` and commit it.
- **Quality gates before `pan done`:** `npm run typecheck`, `npm run lint`, and `npx vitest run <touched test files>`. `npm run typecheck` excludes `*.test.ts`, so run the touched test files explicitly.
- **Commit trailers.** Each work item lands as its own commit with an `Item: <item-id>` trailer.
