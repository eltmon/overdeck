# PAN-3931 — Peer dashboards still write shared state under the primary's OVERDECK_HOME

Issue: https://github.com/eltmon/overdeck/issues/3931
Follow-up from [PAN-3917](https://github.com/eltmon/overdeck/issues/3917) (The Overdeck Cut) — filed from the Cut's integration notes and a Codex review of the integrated diff.
Authored: 2026-09-19/20, planning session, from direct code reading on this branch (`feature/pan-3931`, based on `main` at `5eb034428ab`).
Status: implementation-ready.

## Glossary

- **Peer dashboard**: a dashboard server process (`node dist/dashboard/server.js`) launched with `OVERDECK_DISABLE_DEACON` truthy. It is a read/UI peer, never a second orchestrator — it must not poll trackers, spawn agents, or mutate state another dashboard owns (PAN-1817, PAN-3917 fix10).
- **Primary dashboard**: the operator's `pan up` dashboard — the one that owns tracker polling, merges, and agent lifecycle for a given `OVERDECK_HOME`.
- **Own-home peer**: a peer dashboard whose `OVERDECK_HOME` is its own throwaway directory (a devcontainer's home, a Playwright fixture's `mkdtempSync` home). It never touches another dashboard's data because it has no shared storage.
- **Shared-home peer**: a peer dashboard that inherits or is pointed at the *same* `OVERDECK_HOME` as a running primary — concretely, a hand-run `OVERDECK_DISABLE_DEACON=1 node dist/dashboard/server.js` on the operator's own host, with no `OVERDECK_HOME` override. This is the case this issue is about: its writes land in the primary's own SQLite database, event log, and `~/.overdeck/*.json` files.
- **`isPeerDashboardProcess()`**: the single boolean gate at `src/lib/boot-gates.ts:36`, `true` whenever `OVERDECK_DISABLE_DEACON` is a truthy value. It does not distinguish own-home from shared-home peers — by design, since a peer must behave identically either way; an own-home peer just has nothing to corrupt.
- **fix10**: the PAN-3917 commit (`6b4f2a8e25d`) that gated the boot paths which could *spawn an agent* on `isPeerDashboardProcess()` — the auto-merge executor, the backlog auto-trigger, and the boot merge-queue/post-merge-lifecycle/feedback-replay block in `main.ts`. This issue extends that same pattern to boot paths that *mutate shared state* without spawning anything.
- **Event store**: the SQLite-backed durable event log (`overdeck.db`, `events` table) every dashboard process appends into and reads from (`src/dashboard/server/event-store.ts`). A shared-home peer's appends land in the same table the primary reads.
- **`app_settings`**: a SQLite table (`src/lib/overdeck/control-settings.ts:13`) holding small durable key/value settings, including the restart announcer's last-announced timestamp.

## Problem

`OVERDECK_DISABLE_DEACON=1` now spawns nothing and runs no destructive migration (fix10 of [PAN-3917](https://github.com/eltmon/overdeck/issues/3917)), and PAN-1817 already stops a peer from polling issue trackers. But `isPeerDashboardProcess()` is not yet checked at four more boot sites in `src/dashboard/server/main.ts`, each started unconditionally regardless of `isPeerDashboard`:

1. **`startConversationLifecycleService()`** (`src/dashboard/server/services/conversation-lifecycle.ts:565`, wired at `main.ts:455`) — polls every 10s (`POLL_INTERVAL_MS`, line 44), marks the primary's `conversations` rows `ended`/`running` (`markConversationEnded`/`markConversationRunning`), inserts backfill rows for live specialist sessions (`backfillOrphanedSpecialistConversations`), inserts and links `/clear`-orphan sibling rows (`detectOrphanedClaudeCodeSessions` → `createConversation`/`setClearedToConvId`), and deletes attachment files (`cleanupUnreferencedConversationAttachments`, which calls `fs.rm`).
2. **`startAgentEnrichmentService()`** (`src/dashboard/server/services/agent-enrichment-service.ts:355`, wired at `main.ts:203`) — polls every 10s (`POLL_INTERVAL_MS`, line 346), appends durable `agent.created` and `agent.enrichment_changed` domain events into the shared event store (`saveAgentStateAndEmitEvent` / `eventStore.appendAsync`), and on state transitions emits activity-feed entries and fires text-to-speech (`emitActivityEntrySync`, `emitActivityTtsSync`).
3. **`startProjectCiRefillAfterProjectionReady()`** (`src/dashboard/server/services/project-ci-refill-startup.ts:25`, wired at `main.ts:705` with a 15-minute interval) — appends durable `project.ci_head_observed` domain events (`fillAllProjectCi` → `appendDomainEventAsync`) by paginating the GitHub Actions API per project.
4. **`startRestartAnnouncer()`** (`src/dashboard/server/services/restart-announcer.ts:215`, wired at `main.ts:678`) — polls every 15s (`POLL_MS`, line 28; 1s bootstrap poll for the first 30 ticks) and writes the *primary's* last-announced-restart marker into the shared `app_settings` table (`setSetting(RESTART_ANNOUNCER_LAST_TS_KEY, …)`), consuming the notification before the primary's own instance can announce it. On a failed systemd unit it also writes a synthetic entry to `~/.overdeck/restart-status.json` (`writeRestartStatus`, `src/lib/restart-status.ts`).

The issue's fifth named site, `restart-gate.ts`, is **not actually a writer**: since commit `d76b9b18409` ("restart gate is an in-memory request map", PAN-3917 W6 D2) the gate holds all state in an in-process `Map`/object (`RestartGateState`, `src/dashboard/server/services/restart-gate.ts:88`) with **no disk store**, and its projection publish (`emitThroughEventStore`, line 348) calls `getEventStore().emitOnly(...)` (line 354) — `emitOnly`, explicitly *not* `append` — which fans the snapshot out to live RPC subscribers without writing to the durable event log. `initRestartGate()` (`main.ts:746`) only starts an in-memory sweep timer; it writes nothing shared. This is recorded as a finding below (see Requirements, FR-6) rather than treated as a fifth gate site — the issue body is stale on this point relative to the current code, not in conflict with any other authoritative input, so this does not trigger the auto-mode contradiction halt.

**Who is actually affected.** Container and CI peers already have their own storage and are unaffected by any of the four sites above:
- The devcontainer's `server` service (`.devcontainer/docker-compose.devcontainer.yml:152-159`) explicitly does **not** mount `${HOME}/.overdeck` into the container (see the comment at line 152: "Do NOT mount... the container's dashboard server would run its own Deacon patrol against shared host agent state") — its `OVERDECK_HOME` is the container's own `/home/node`, not the primary's.
- Both Playwright isolation fixtures (`src/dashboard/frontend/tests/fixtures/isolated-dashboard.ts:94`, `health-page.spec.ts:47`, `system-health-pill.spec.ts:49`) pass an explicit throwaway `OVERDECK_HOME: home` (an `mkdtempSync` directory) alongside `OVERDECK_DISABLE_DEACON: '1'`.

So today's real hazard is a **shared-home peer**: an operator (or an agent under test/UAT) hand-running `OVERDECK_DISABLE_DEACON=1 node dist/dashboard/server.js` on the host with no `OVERDECK_HOME` override, which inherits the primary's `~/.overdeck`. This already happened: the PAN-3260 UAT run's own disclosure records an isolated peer on port 3211 that "unexpectedly picked up and executed a live durable-review verification retry... against PAN-3232's own workspace, from shared state in `~/.overdeck/verification-workers/`" despite `OVERDECK_DISABLE_DEACON=1` (`docs/audits/pan-3367/evidence/candidates.json:538` — noted here as a related, but out-of-scope, gap; see NonGoals). This issue's four sites are a second instance of the identical shared-home-corruption class: a throwaway peer boot silently mutating conversation rows, agent lifecycle events, CI projections, and the primary's own restart-announcement bookkeeping — all in tables/files the primary reads back.

Because own-home peers have nothing to act on that could actually corrupt shared state (their `conversations` table, `events` table, and `app_settings` are empty and freshly created), gating unconditionally on `isPeerDashboardProcess()` — the same test fix10 already uses, with no additional `OVERDECK_HOME`-comparison logic — is safe for every peer shape: an own-home peer's poll would have been a no-op anyway (nothing in its own empty DB to touch), and a shared-home peer is now correctly prevented from touching the primary's.

## Decisions (made in this document)

- **D1 — Gate shape matches fix10 exactly.** Each of the four services gets a boolean-returning wrapper, following `startAutoMergeExecutor(): boolean` (`src/dashboard/server/services/auto-merge-executor.ts:244`, PAN-3917 fix10): check `isPeerDashboardProcess()` first, return `false`/skip without starting the timer when true. `main.ts` branches its boot log line on the return value, exactly like the existing `if (startAutoMergeExecutor()) {...} else if (isPeerDashboard) {...}` block at `main.ts:760-766`.
- **D2 — Gate the starter, not the poll function.** `pollConversations()`, `pollOnce()` (enrichment), `fillAllProjectCi()`, and `announceNewRestart()` keep their existing signatures and are NOT touched — all four have existing unit tests (`conversation-lifecycle.test.ts`, `agent-enrichment-service.test.ts`, `project-ci-refill-startup.test.ts`, `restart-announcer.test.ts`) that call these functions directly with injected fakes/mocks and no `isPeerDashboardProcess` awareness. Gating only the `start*` entry point keeps every existing test passing unmodified and matches exactly where fix10 gated `startAutoMergeExecutor`.
- **D3 — `restart-gate.ts` is a no-op item, documented not coded.** Per the Problem section finding, `restart-gate.ts` writes no shared state today. No code change is made to it. A one-line comment is added at its `main.ts:746` call site recording why, so a future reader does not need to re-derive this.
- **D4 — `project-ci-refill-startup.ts`'s consequence is accepted, not hidden.** Gating it means a shared-home peer's dashboard UI shows an empty/stale per-project CI chip (no other code path currently fills that projection for a peer — `smee-client` webhook relay is already skipped on peers per `main.ts:585`, and this fill is presently the only other producer of `project.ci_head_observed` events). This is recorded in `plan.autoDecisions[]` as the one real trade-off this issue makes, following the PAN-1817 precedent that peers make zero forge-API calls against the shared token.
- **D5 — No new environment variable, no new module.** All four gates reuse the existing `isPeerDashboardProcess()` export from `src/lib/boot-gates.ts`; no new config surface is introduced.
- **D6 — Scope is exactly the four named sites plus their `main.ts` wiring plus docs.** The broader inventory of other unconditional `main.ts` boot writers (attachment cleanup interval, TTS summarizer/playback, `seedProjectsFromYaml`, `backfillIssueWorkspaces`/`migrateMemoryHomesToWorkspacesOnce`, the transcript poller, cost reconcile service, conversation search watcher/rescan scheduler, and `recoverStuckForks` which itself calls `markConversationEnded`) is explicitly out of scope for this issue — see NonGoals — and is left as a named follow-up recommendation rather than silently absorbed or silently dropped.

## Requirements

- **FR-1** `startConversationLifecycleService()` returns `boolean`. When `isPeerDashboardProcess()` is true, it logs `[overdeck] ConversationLifecycleService SKIPPED — peer dashboard shares no lifecycle authority` (or equivalent, avoiding the substrings `failed`/`failure` per NFR-2), starts no poll timer, and returns `false` without calling `scheduleNext()`. When false, behavior is unchanged (existing log line, `scheduleNext()` runs, returns `true`).
- **FR-2** `startAgentEnrichmentService()` returns `boolean`. When `isPeerDashboardProcess()` is true, it logs a `SKIPPED` line, starts no `setInterval`, and returns `false`. When false, behavior is unchanged and it returns `true`.
- **FR-3** `startProjectCiRefillAfterProjectionReady()` gates *before* awaiting `whenEventStoreProjectionReady()` — the boot must not block on projection readiness at all for a peer, matching how `startAutoMergeExecutor` gates before doing any other work. When `isPeerDashboardProcess()` is true, it logs a `SKIPPED` line and resolves without calling `deps.start`/`startProjectCiRefill`, returning `null`. When false, existing behavior (await readiness, then call `start`) is unchanged and it returns the interval handle as before.
- **FR-4** `startRestartAnnouncer()` returns `boolean`. When `isPeerDashboardProcess()` is true, it logs a `SKIPPED` line, does not call `pass()` (so no `readStatus`/`writeStatus`/`getLastAnnounced`/`setLastAnnounced` dependency ever runs), and returns `false`. When false, behavior is unchanged and it returns `true`.
- **FR-5** `main.ts` wires all four gated starters the same way `startAutoMergeExecutor()` is already wired at `main.ts:760-766`: `if (startX()) { console.log('... started') } else if (isPeerDashboard) { console.log('... SKIPPED — peer dashboard ...') } else { /* only reachable if a future non-peer gate is added; today omit or log a generic skip */ }`. For `startProjectCiRefillAfterProjectionReady`, since it is `await`ed and returns a value (not currently branched on), the wiring branches on the returned value being `null` vs. non-`null`.
- **FR-6** A code comment at the `initRestartGate()` call site in `main.ts` (~line 746) records: `restart-gate.ts` is in-memory-only since PAN-3917 D2 and publishes via `emitOnly` (never `append`), so it needs no peer gate; retained here as the resolution of the PAN-3931 issue body's fifth named site.
- **FR-7** `docs/DASHBOARD-ARCHITECTURE.md` gains a **"Peer dashboards"** bold-section (following the existing `**Session lifecycle rules:**` bold-section pattern at line 186) enumerating, by name, every boot path a peer dashboard (`OVERDECK_DISABLE_DEACON=1`) skips today: tracker polling (PAN-1817), CLIProxy watchdog, smee-client webhook relay, backlog auto-trigger, auto-merge executor, boot merge-queue repair/post-merge-lifecycle/feedback-replay, Cloister/Deacon auto-start (all pre-existing), plus the four newly gated in this issue (conversation lifecycle, agent enrichment, project CI refill, restart announcer), plus the restart-gate no-op finding (FR-6).

- No change to how `isPeerDashboardProcess()` distinguishes (or rather, deliberately does not distinguish) an own-home peer from a shared-home peer — both are gated identically, matching every existing fix10 site.
