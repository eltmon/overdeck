## Glossary

- **Machine:** one running Overdeck dashboard with its own `OVERDECK_HOME`. Its identity is its environment id (`${OVERDECK_HOME}/environment-id.json`).
- **Machine key:** the X25519 key pair in `${OVERDECK_HOME}/machine-key.json` (mode 0600), created by `ensureMachineKey()` (`src/lib/anywhere/machine-key.ts:151`). The public half is 64 lowercase hex; `machineKeyFingerprint()` (`machine-key.ts:109`) renders it as five dash-separated groups of four hex characters.
- **Account:** an overdeck.ai account from `services/account`. A signed-in machine holds a device token `odd_<64 hex>` in `${OVERDECK_HOME}/account.json` (mode 0600), read with `readAccount()` (`src/lib/account/store.ts:58`). The account worker verifies a token through the RPC entrypoint `AccountRpc.verifyDevice(token)` (`services/account/src/index.ts:15-19`), which returns `{ ok: true, userId, githubId, githubLogin, deviceId, entitlement }`.
- **Entitlement / plan:** `Entitlement` in `services/account/src/entitlement.ts:12-16` (`plan`, `storageBytesCap`, `maxDevices`). This issue widens `plan` to `'free' | 'tester'`. `tester` is every allowlisted account until billing (PAN-4294) ships, and it carries the paid tiers (Anywhere and the relay add-on).
- **Directory:** the `services/connect` Cloudflare Worker at `connect.overdeck.ai`, with one Durable Object per account (class `AccountDirectory`). It knows an account's machines: environment id, label, machine public key, fingerprint, presence and advertised addresses. It introduces machines to each other and steps aside. It never carries conversation bytes and never vouches for a key (D-18).
- **Directory socket:** the one hibernating WebSocket each signed-in machine keeps to its account's Durable Object (`wss://connect.overdeck.ai/v1/directory`).
- **Directory client:** the machine-side service in the dashboard that owns the directory socket (`src/dashboard/server/services/directory-client.ts`, new).
- **Route:** one way to reach a linked machine (PAN-4645). Kinds are ranked `lan < tailnet < ssh < public < direct < relay` (`ROUTE_KINDS`, `packages/contracts/src/machines.ts:19`).
- **`direct` route:** a WebRTC data channel between two machines, opened with STUN for NAT traversal after the two machines exchange WebRTC offers, answers and ICE candidates through the directory socket. Route URL form: `rtc://<environmentId>`.
- **`relay` route:** the same WebRTC data channel forced through a Cloudflare Realtime TURN server (`iceTransportPolicy: 'relay'`). Route URL form: `rtc+turn://<environmentId>`. Relay-plan accounts only.
- **Secure channel:** the Noise session between two machine keys (PAN-4645, `src/lib/anywhere/channel/*`). Every route, including `direct` and `relay`, carries it, so STUN, TURN and the directory see only ciphertext.
- **Signalling:** the WebRTC offer/answer/ICE candidate exchange. Here it travels as `signal` frames on the directory socket.
- **Dynamic route:** a route that exists only while the directory says the peer is in the account (`direct`, `relay`, and addresses the directory reports). Dynamic routes are never written to `${OVERDECK_HOME}/machine-links.json` (D-2356-7).
- **Approval:** linking two machines of one account with no pairing code. The requesting machine asks; an operator confirms on both machines that the two screens show the same six-digit code (D-2356-9).
- **Approval channel:** a secure-channel session in the new `approval` mode (Noise `XX`, mode byte `0x03`), used only to run one approval.
- **SAS:** short authentication string, the six-digit code both machines derive from the approval channel's Noise handshake hash.
- **Relay allowance:** 50 GB (50,000,000,000 bytes) of relay traffic per account per UTC calendar month (OD-3).
- **Webhook inbox / directory inbox:** a URL `https://connect.overdeck.ai/h/<id>` that accepts a webhook event, seals it to the target machine's public key and holds only the sealed copy until the machine acknowledges it or 24 hours pass (D-20).
- **Sealed box:** libsodium's `crypto_box_seal` format: `ephemeralPublicKey (32) || XSalsa20-Poly1305(message)`, nonce `= BLAKE2b-192(ephemeralPublicKey || recipientPublicKey)`. Overhead 48 bytes.
- **Trigger:** a PAN-4648 webhook trigger (`src/lib/triggers/store.ts`, `TriggerRecord` lines 40-48). Its local URL is `/hooks/<trg_id>/<urlSecret>`.

## Problem

PAN-4645 gave two machines an end-to-end encrypted link over any route that already reaches them: LAN, Tailscale, SSH, a public address. Two machines on different networks without Tailscale still cannot reach each other. The epic's answer (D-3) is a directory first and a relay last: overdeck.ai introduces the machines and lets them open a peer-to-peer WebRTC path, and only relay-plan accounts fall back to a TURN relay that forwards ciphertext. Separately, a webhook trigger today works only while the machine is online behind Tailscale Funnel; an event sent while the machine is off is lost (`configuration/triggers.mdx`, "Nothing is queued"). The directory inbox holds those events, sealed, for 24 hours.

Nothing of this exists in code (verified 2026-11-01): there is no `services/connect`, no `anywhere.directory_url`, no `werift` dependency, no inbox delivery path, and the account service has only the plan `'tester'`.

## Requirements

Requirement ids from the epic are kept where they apply; new ids are local to this issue.

### Functional

- **FR-20 Directory.** A machine signed in to an overdeck.ai account registers in the account's directory with its environment id, label, machine public key, fingerprint, server version and advertised endpoints, and keeps a presence socket open. From any signed-in machine the operator can:
  - see all of the account's machines, online or offline (with last-seen time), without sharing a network;
  - link two of them with no pairing code, through an approval confirmed on both screens (D-2356-9);
  - reach a linked machine with no Tailscale over a `direct` route.
  The directory moves only presence, labels, keys, fingerprints, advertised addresses and signalling messages.
- **FR-20a Machine limit.** A free account holds at most 3 machines in its directory. Registering a fourth environment id is refused with the exact text `The free account includes 3 machines`. **Remove from directory** (and `pan machines forget`) frees a slot.
- **FR-21 Relay fallback.** When every other route to a linked machine fails, and the account's plan includes the relay (`tester` until billing ships), the two machines connect through Cloudflare TURN, carrying the same secure channel. A non-relay account gets the link detail `No direct path; install Tailscale or use the relay plan`. Relay bytes are counted per account per UTC month. At 50 GB the relay stops until the next month and the status card shows `Relay allowance used; install Tailscale or add 50 GB` with an **Add 50 GB** button. While a relay route is current, the status card shows **Using relay** and the bytes used this month.
- **FR-26i Directory inbox.** A trigger can have a directory inbox. Its URL `https://connect.overdeck.ai/h/<id>` accepts `POST` events, seals each to the target machine's public key, stores only the sealed copy, delivers held events in arrival order when the machine is online, and deletes each on acknowledgement or after 24 hours. Signatures are checked on the machine. The inbox is available on the Anywhere tier (`tester`), not the free account.
- **FR-2356-1 Directory URL setting.** `anywhere.directory_url` in `${OVERDECK_HOME}/config.yaml` sets the directory, default `https://connect.overdeck.ai`. It must be `https:`, except `http:` to a loopback host. It is read at every directory (re)connect.
- **FR-2356-2 Signed-out behaviour.** A machine with no `account.json` runs no directory client, opens no socket and shows "Sign in with `pan account login` to find your machines through overdeck.ai" in the directory panel. Nothing else changes (NFR-8).

### Non-functional

- **NFR-8 Self-hosting has no feature gate.** Everything except the hosted directory, direct connections through it, the relay and the directory inbox works without an account. A self-hoster can run `services/connect` and point `anywhere.directory_url` at it.
- **NFR-2356-1 No content through the directory.** The Durable Object never stores or logs a frame payload. Its logs name only the frame type, the environment id and outcome. Inbox storage holds only sealed bytes.
- **NFR-2356-2 Bounded idle cost.** An idle directory socket sends one `ping` text frame every 30 s, answered by `setWebSocketAutoResponse` without waking the Durable Object.
- **NFR-2356-3 Async only.** All machine-side code is reachable from the dashboard server and uses async I/O: no `execSync`, no new `*Sync` tmux calls (repo rules `no-execsync-server`, `prefer-async`).
- **NFR-2356-4 Fake timers.** Every back-off, expiry, alarm, ping and probe-phase test uses `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()` (repo rule `fake-timers-for-retry-tests`). Real-clock tests go only in the smoke script.
- **NFR-2356-5 Throughput.** Over a loopback `direct` route, a 1 MiB HTTP response through the secure channel completes in under 5 s.

## Decisions

Decisions from the epic are binding: D-3 (directory first, relay last, Cloudflare Worker with one Durable Object per account, werift data channel, `anywhere.directory_url`), D-15 (cloud components carry transport only), D-18 (the directory never vouches for a key), D-20 (the inbox stores only sealed events). The decisions below make them concrete.

- **D-2356-1 Worker layout copies `services/share`.** `services/connect/` is a Bun workspace (`@overdeck/connect-service`, `"private": true`, `"license": "FSL-1.1-MIT"`, `"type": "module"`), with the same dev dependencies and pins as share (`@cloudflare/workers-types` `5.20261002.1`, `miniflare` `5.20261001.0-alpha`, `wrangler` `4.146.0`), the same `tsconfig.json`, `compatibility_date "2026-09-01"`, and the same "only `src/index.ts` imports `cloudflare:workers`" rule. Licence: covered by `services/LICENSE.md`; `README.md:264` names the new service. Tests live under `tests/unit/services/connect/` and `tests/integration/services/connect/`, not inside the service.
- **D-2356-2 One Durable Object per account, named by the account `userId`.** The Worker verifies the device token with `env.ACCOUNT.verifyDevice`, then routes to `env.DIRECTORY.idFromName(userId)`. Trust passes to the Durable Object in internal headers (`X-Connect-Identity`: JSON `{ userId, githubId, deviceId, plan, maxDevices }`), the same way share passes `X-Share-Identity`. The Durable Object never reads `Authorization`.
- **D-2356-3 Plans until billing.** `Entitlement.plan` becomes `'free' | 'tester'`. `entitlementFor(grant)` reads the grant's existing `entitlement` column: `'free'` gives `{ plan: 'free', maxDevices: 3 }`; anything else, and the owner, gives `{ plan: 'tester', maxDevices: null }` as today. Connect derives `relayAllowed = inboxAllowed = plan !== 'free'` and enforces `maxDevices` on directory registration. The account service stays invite-only; a free account is an allowlisted GitHub id whose grant row has `entitlement = 'free'` (set with `wrangler d1 execute`, documented in `docs/ACCOUNT-SERVICE.md`). Opening sign-up to the public is out of scope.
- **D-2356-4 Presence registry in Durable Object SQLite.** The Durable Object uses `ctx.storage.sql` (class migration `new_sqlite_classes`). A machine row persists after its socket closes, with `last_seen_at`, so offline machines stay listed. The machine count for FR-20a is the number of rows. A `hello` for a new environment id when `rows >= maxDevices` is answered with `error { code: 'machine_limit', message: 'The free account includes 3 machines' }` and close code 4009. A `hello` for an existing row updates label, key, endpoints and device id. A second socket for the same environment id replaces the first (old one closed with 4011).
- **D-2356-5 Presence carries advertised endpoints, not STUN addresses.** The machine publishes the `lan`/`tailnet` endpoints its `EndpointAdvertiser` already computes. STUN-reflexive addresses travel only inside ICE candidates during signalling. This keeps the machine from running STUN continuously; FR-20's "addresses STUN reports" is satisfied at connection time.
- **D-2356-6 Signalling rides the directory socket.** A machine sends `signal { to, session, purpose, relay, data }`. The Durable Object stamps `from` with the sender socket's environment id (never trusting a field in the frame) and forwards to the target's socket, or answers `error { code: 'peer_offline', session }`. The frame caps of share apply (frame 64 KiB, SDP 32 KiB, candidate 2 KiB). Signals with `purpose: 'approval'` are forwarded only while a pending approval between those two machines exists.
- **D-2356-7 Dynamic routes, never persisted.** The directory client offers routes for a linked machine only when the directory lists that environment id with the same public key the link pinned. The routes are `rtc://<envId>` (kind `direct`), `rtc+turn://<envId>` (kind `relay`, only when `relayAllowed`), and the peer's directory-reported endpoints (their own kinds), all with the new source `'directory'`. The supervisor reads them through a new `LinkSupervisorDeps.dynamicRoutes(link)` hook. They are never written to `machine-links.json`, because `isRoute` (`src/lib/anywhere/link-store.ts:81-89`) rejects unknown schemes and sources and a rejected file empties every link, so an older `pan` would lose every link after a downgrade.
- **D-2356-8 Phased probing.** Phase 1 probes every route whose kind is not `direct` or `relay`, in parallel, at the existing 2.5 s timeout. Phase 2 runs only when phase 1 produced no channel and no `unknown-peer` refusal: it probes `direct` routes with `DIRECT_PROBE_TIMEOUT_MS = 10_000`. Phase 3 runs only when phase 2 also failed and a `relay` route exists: it probes it with `RELAY_PROBE_TIMEOUT_MS = 10_000`. When phases 1 and 2 fail and no relay route exists because the plan has no relay, `stateDetail` is `No direct path; install Tailscale or use the relay plan`. The 60 s better-route check keeps working unchanged: on `relay` it re-probes `direct` and phase-1 routes; on `direct` it re-probes phase-1 routes.
- **D-2356-9 Approval is confirmed on both machines (tightens FR-20).** FR-20 says approving on the existing machine "creates the links with no pairing code". A one-sided approval lets a compromised directory make the new machine trust an impostor approver, which D-18 forbids. So:
  1. The requesting machine R sends `approval-request` (to one machine, or to all of the account's machines).
  2. The approving machine A's operator clicks **Review**. A opens a `direct` WebRTC path to R and runs an `approval`-mode secure channel (Noise `XX`, no pre-shared key) whose preamble carries the 16-byte request id.
  3. Both machines derive the SAS from the handshake hash and show it with the other machine's fingerprint, taken from the handshake, never from the directory.
  4. The operator clicks **Approve** on A and **Accept** on R after checking that both screens show the same code. Each side mints its machine token only after its own operator confirms. A link is created in both directions, operator-level (epic D-4), only when both confirmed.
  5. A man in the middle produces two different handshake hashes, so the two screens show different codes. **Amended 2026-11-01 after review (run `agent-pan-2356-review-65a26309`):** different hashes are not enough, because six digits collide after about 10^6 tries and the attacker can vary its own leg (for example its message-3 static key) until both codes match. D-2356-10 now adds a commit-then-reveal round after the handshake, so neither leg's code is known to the attacker when it fixes its input.
  - **Headless R** (a VPS, PAN-4656's `pan connect`): `pan machines join` prints the code and approver fingerprint and asks `Accept? [y/N]` on a TTY. Off a TTY, it prints the request id, and `pan machines accept <requestId>` confirms.
  - **Limits:** a request expires after 10 minutes. The Durable Object keeps at most 1 pending request per requesting machine and 5 per account, and refuses more with `error { code: 'approval_limit' }`. A machine accepts an approval channel only for its own live request id (single use).
- **D-2356-10 SAS derivation (amended 2026-11-01 after review).** After Noise XX completes, inside the same framing (`uint24le length` + payload): the initiator A sends `C = SHA-256("overdeck-approve-commit/1" || 0x00 || handshakeHash || n_A)` for a fresh 32-byte nonce `n_A`; the responder R answers with its fresh 32-byte nonce `n_R`; A reveals `n_A`; R refuses the channel (`handshake-failed`, "Approval nonce did not match its commitment") unless `C` matches. Then `sas = (uint32BE(SHA-256("overdeck-approve-sas/2" || 0x00 || handshakeHash || n_A || n_R)[0..4]) mod 1_000_000)`, zero-padded to 6 digits and shown as `123 456`. A man in the middle is the responder toward A, so it must send its nonce before A reveals, and the initiator toward R, so it must commit before `n_R` arrives; it cannot steer either code. Restarting the R leg for a fresh nonce needs a new channel, which `takeApproval` refuses (one channel per request id). The original `"overdeck-approve-sas/1"` derivation (handshake hash only) never shipped. The approval preamble appends the request id, which is 16 random bytes encoded as 32 lowercase hex, just as pairing mode appends its pairing id. The prologue binds it: `prologueFor('approval', requestId)`.
- **D-2356-11 WebRTC library and transport.** `werift` pinned exactly at `0.25.1` (published 2026-10-17, older than two weeks at planning time), bundled (it is pure TypeScript, unlike the externals PAN-4645 added). One `RTCPeerConnection` per (peer environment id, route kind); each `openChannel` call opens a new ordered, reliable data channel labelled `ovdl` on it, because `LinkAgent` pools up to four channels per machine (`src/lib/anywhere/link-client.ts:105`). The `Duplex` adapter splits writes into chunks of at most 16 KiB and pauses while `bufferedAmount > 1 MiB`, resuming on `bufferedamountlow` (threshold 256 KiB). Direct uses the STUN servers the directory returns; relay uses TURN credentials with `iceTransportPolicy: 'relay'` on the initiator only.
- **D-2356-12 TURN credentials and metering.** TURN credentials come from `ice-servers { relay: true }` and are minted with share's Cloudflare Realtime call (`services/share/src/turn.ts`) with `TURN_TTL_SECONDS = 600`. The Durable Object refuses with `relay_not_allowed` (plan `free`), `relay_cap_reached` (month total ≥ cap) or `turn_unavailable` (secrets unset).
  - **Reporting:** the machine that requested the credentials (the channel initiator) reports ciphertext bytes, sent plus received, from the relay channel's `ChannelSocket` counters as `relay-usage { bytes }` deltas every 60 s and when the channel closes. The responder never reports, so each channel is counted once.
  - **Trust:** counts are self-reported by the account's own machines, which is the same trust the account already has.
  - **Cut-off:** when a report pushes the month total to or past the cap, the Durable Object broadcasts `relay-status { stopped: true }`, every machine closes its relay channels, and no new credentials are issued. Over-run is therefore bounded by one report interval plus the credential TTL.
  - **Billing:** **Add 50 GB** opens `https://overdeck.ai/anywhere` in a new tab, because billing (PAN-4294) is out of scope.
- **D-2356-13 Inbox URL routes without a global index.** The inbox id is `<doId>.<secret>`: `doId` is the account Durable Object's id string (64 lowercase hex, `DIRECTORY.idFromName(userId).toString()`), `secret` is 32 lowercase hex (128 random bits). The Worker splits on the dot, rebuilds the id with `idFromString(doId)` (an invalid id answers `404 { error: "not found" }`), and the Durable Object compares `SHA-256(secret)` with stored hashes in constant time. The public inbox handle the machine stores is `ib_<16 hex>`; the secret exists only in the URL, which is returned once.
- **D-2356-14 Inbox limits.**
  - **Body:** at most 256 KiB (`INBOX_BODY_MAX_BYTES = 262_144`); larger requests get `413 { error: "event too large for the directory inbox" }`. This is below PAN-4648's 1 MiB local cap because each sealed event must fit one WebSocket message after base64.
  - **Queue:** each inbox holds at most 200 pending events, and each account at most 64 MiB of sealed bytes. A request beyond either cap gets `429 { error: "inbox full" }` with `Retry-After: 3600`.
  - **Rate:** at most 120 events per minute per inbox, through a `ratelimits` binding `INBOX_LIMIT`.
  - **Answer:** an accepted event gets `202 { queued: true }` at once. The inbox never waits for the machine.
  - **Plan:** when the account's last-seen plan is `free`, intake answers `403 { error: "the inbox needs the Anywhere plan" }`.
- **D-2356-15 What is sealed.** The sealed plaintext is UTF-8 JSON `{ v: 1, eventId, inboxId, receivedAt, headers, body }`:
  - `eventId` is a UUID made by the Durable Object.
  - `receivedAt` is Unix milliseconds.
  - `headers` keeps only `content-type`, `user-agent`, `x-github-event`, `x-github-delivery`, `x-hub-signature-256` and `stripe-signature`, lower-cased.
  - `body` is the raw request bytes in base64.
  The Durable Object stores `event_id, inbox_id, environment_id, received_at, size, next_attempt_at, sealed BLOB` and nothing else about the event. The plaintext exists only in the request handler's memory.
- **D-2356-16 Sealed-box implementation.** The Worker seals with `@noble/curves@2.4.0` (x25519), `@noble/ciphers@2.4.0` (xsalsa20poly1305) and `@noble/hashes@2.4.0` (blake2b, `dkLen: 24`), all pinned exactly in `services/connect/package.json`. The machine opens with `sodium-native`'s `crypto_box_seal_open`, the libsodium reference. `sodium-native@5.2.0` (the version already in `bun.lock` through `noise-handshake`) becomes a direct root dependency. It is already external in both tsdown configs (`tsdown.config.ts:50`, `src/dashboard/server/tsdown.config.ts:154`). A fixed test vector proves the two interoperate.
- **D-2356-17 Inbox delivery on the machine.** `deliverInboxEvent(trigger, event, deps)` is a second entry point into the trigger core. It runs every step of `runDelivery` except step 1 (the URL secret), because the inbox secret already authorised the sender. The steps it runs are: signature, rate limit, CPU hold, envelope and delivery door.
  - **Stripe:** the 300 s tolerance is measured against `receivedAt`, not the current time.
  - **Freshness:** an event whose `receivedAt` is more than 24 h 5 min old, or more than 5 min in the future, is rejected.
  - **Dedupe:** delivered event ids are kept in `${OVERDECK_HOME}/inbox-delivered.json` (0600, last 1000 ids, 48 h), so a redelivery after a lost acknowledgement does nothing and is acknowledged again.
  - **Acknowledgements:**
    - 2xx answers and the terminal 4xx answers (401, 404, 410, 413) send `inbox-ack`;
    - 503 and 429 send `inbox-nack { retryAfterSeconds }`;
    - the Durable Object re-sends at `max(retryAfter, 60 s)`.
  - **Order:** events are processed one at a time per machine, in `receivedAt` order. On every `welcome` the Durable Object sends all pending events at once, which is what meets "within 60 s of coming back".
- **D-2356-18 Expiry.** A Durable Object alarm is set for the oldest pending event's `received_at + 24 h`. When it fires, the Durable Object deletes every expired row and re-arms the alarm for the next one.
- **D-2356-19 The directory URL is a raw YAML read.** `src/lib/anywhere/directory-config.ts` reads `anywhere.directory_url` straight from `config.yaml` with `js-yaml`, the way `src/lib/remote-access/config.ts` reads `dashboard.require_token_mint`. There is no Settings UI field, because `settings-api.ts` is over the file-size ceiling. A Settings save preserves the block (see "What exists").
- **D-2356-20 One issue, not three.** W-LINK5, W-LINK8 and the inbox share one Worker, one Durable Object class, one wire protocol and one machine-side client, so separate issues would serialise on the same files. The epic's disposition table assigns all three to PAN-2356.
- **D-2356-21 Deployment is an operator checkpoint.** Agents may run `wrangler dev --local` and `wrangler deploy --dry-run`, never a real deploy (`docs/ACCOUNT-SERVICE.md`, `docs/SHARED-SESSIONS.md:144`). The account service is not deployed yet (`PAN-4330.md:9`). The two live "Done when" checks (different networks; UDP blocked) are therefore an operator checkpoint after merge, following the runbook WI-23 writes. ## Wire protocol (WI-1 defines it in `packages/contracts/src/connect.ts`)

`CONNECT_PROTOCOL_VERSION = 1`. All frames are JSON text frames. The machine sends the text `ping` every 30 s and expects `pong`; a socket with no `pong` for 75 s is closed and reconnected.

**Machine → directory**

| type | fields |
|---|---|
| `hello` | `protocol: 1`, `environmentId`, `label` (≤ 64 chars), `publicKeyHex` (64 hex), `serverVersion`, `linkProtocol`, `endpoints: AdvertisedEndpoint[]` (≤ 16) |
| `endpoints` | `endpoints: AdvertisedEndpoint[]` |
| `forget` | `environmentId` |
| `approval-request` | `requestId` (32 hex), `to: string \| null` |
| `approval-cancel` | `requestId` |

| `inbox-create` | `requestId` |
| `inbox-delete` | `inboxId` |
| `inbox-ack` | `eventId` |
| `inbox-nack` | `eventId`, `retryAfterSeconds` (60–3600) |

| type | fields |
|---|---|
| `welcome` | `protocol`, `plan`, `maxMachines: number \| null`, `relayAllowed`, `inboxAllowed`, `relay: RelayStatus`, `machines: DirectoryMachine[]` |

- **Flow (D-2356-9):**
  - **Requester side:**
    - `POST /api/directory/join` creates `requestId` (16 random bytes, hex), sends `approval-request`, and keeps the join for 10 minutes.
    - The incoming approval channel for that id is accepted once. Its SAS and the approver's fingerprint (from the handshake key) appear in `GET /api/directory` `joins[]`.
    - `POST /api/machines/approval-exchange` (body `{ environmentId, label, reverseToken }`, where `reverseToken` is the approver's machine token for R) waits up to the join's expiry for `accept` or `reject`.
    - On accept, R mints its token for A with `grantMachineLink` (reverse link stored with `reverseToken`) and answers `{ token, label, environmentId }`. On reject or expiry it answers 403 `{ error: 'approval-refused' }`.
  - **Approver side:**
    - Incoming `approval-request` frames appear in `approvals[]`.
    - `open` dials `rtc://<R>` with `purpose: 'approval'` and opens the approval channel. Its handshake key must equal the `publicKeyHex` the request carried, otherwise the open fails with `fingerprint-mismatch`. The call returns `{ sas, fingerprint }`.
    - `approve` mints A's token for R, posts the exchange over the channel, and on success stores the link A→R with R's returned token and with routes from R's advertised endpoints (fetched with `GET /api/environment` on the channel and merged with `mergeAdvertised`). On failure it revokes the token it minted.
    - `reject` closes the channel and sends `approval-cancel`.
  - **Defaults:** links created by approval are `operator` access, both ways.
  - **Route declarations:** declare every route as `HttpRouter.add('METHOD', '/path', …)` so `tests/unit/lib/overdeck/no-loss-matrix.test.ts` enumerates it (WI-9 does the same for `GET /api/directory`).
  - **Long-held exchange:** if the Effect server or `http.Agent` times out the held `approval-exchange` response, return `202 { pending: true }` and have the approver re-post every 10 s on the same channel until accept, reject or expiry.
- **Tests:** new `src/dashboard/server/services/__tests__/directory-approval.test.ts` with two in-process dashboards' services joined by an in-memory directory and transport:
  - approve plus accept creates exactly one link each way and two machine tokens;
  - approve without accept creates nothing on either side after 10 minutes of fake clock, and A's minted token is revoked;
  - a key mismatch on `open` creates nothing;
  - `machines-exchange.test.ts` still passes after the extraction.

- **Fake timers** for every back-off, ping, expiry, alarm and probe-phase test (`vi.useFakeTimers()`, `vi.advanceTimersByTimeAsync()`). Never real `setTimeout` waits in unit tests. Never lower `maxForks` to hide a leak.

- **Never deploy** a Worker, never call destructive HTTP endpoints speculatively.
