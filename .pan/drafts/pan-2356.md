## Glossary

- **Relay** — a small always-on cloud service. Overdeck instances dial OUT to it over a persistent
  authenticated WebSocket; clients (browsers, PWA, Hermes, collaborators) reach the relay's public
  HTTPS endpoint; the relay forwards frames down the already-established instance connection. The
  relay is transport only — it stores no canonical state (two-doors tenet; NFR-6 of the epic PRD).
- **Instance** — one home machine's Overdeck dashboard server (Node 22, port 3011) plus the relay
  daemon connection it owns.
- **Room** — the relay-side logical channel for one instance. All client traffic for that instance
  multiplexes through its room.
- **Relay daemon (client side)** — a service inside the existing dashboard server process (NOT a
  separate binary) that maintains the outbound connection, re-dials with backoff, and bridges relay
  frames to local HTTP/WS handlers.
- **Pairing** — the act of binding an identity (GitHub account or device key) to an instance with a
  scope set, producing a relay-recognized credential.
- **TLS passthrough (Nabu Casa model)** — the relay routes on the TLS SNI hostname and forwards
  still-encrypted bytes; the certificate lives on the instance, so the relay cannot read traffic.
- **E2E pairing (Happy model)** — client and instance share a symmetric key exchanged out-of-band
  (QR scan); the relay carries only ciphertext; used by native apps, not required for v1 browser flow.

## Problem

After PAN-2352, remote access requires each operator to own a Cloudflare-DNS domain and run
cloudflared — fine for the author, wrong for a product. PAN-658 independently requires a cloud
rendezvous (GitHub OAuth identity + room fan-out) and the epic requires a stable push origin
(Web Push VAPID today, APNs/FCM later — push credentials cannot credibly live on a home machine).
Three needs, one service.

## Decisions (locked here)

- **D-R1 Host: Fly.io machine** (`shared-cpu-1x`, ~$2/mo), same org as `hermes-eltmon`, so instances
  already 6PN-peered (PAN-2353) can reach the relay privately while the public edge serves humans.
  Cloudflare Durable Objects + hibernation was the runner-up; rejected for v1 because the daemon
  side already speaks plain WebSocket + Node, Fly gives us a boring long-lived process with no
  per-message pricing model, and we already operate Fly. Revisit if relay egress ever dominates cost.
- **D-R2 Identity: GitHub OAuth at the relay** (scope `read:user` only — same choice PAN-658 locked).
  Instance-side authorization remains scoped tokens (PAN-2351): the relay authenticates WHO, the
  instance authorizes WHAT. The relay never holds instance tokens.
- **D-R3 v1 privacy tier: authenticated TLS relay, not E2E.** v1 terminates TLS at the relay and
  forwards frames over the instance's outbound WSS connection. This matches Omnara/Codespaces tier,
  ships fastest, and is honest in docs ("the relay can technically observe traffic; it stores none").
  **v2 upgrade path (do not build in v1, do not preclude):** Nabu-Casa-style SNI passthrough for
  browsers, Happy-style QR-paired E2E for the native app. The frame protocol must therefore treat
  payloads as opaque bytes end-to-end (no relay-side parsing of payload frames).
- **D-R4 Repo layout: new top-level `relay/` workspace** in the overdeck monorepo (Bun workspace,
  own `package.json`, deployed via its own `fly.toml`). Not a separate repo — versioned protocol
  types must ship in lockstep with the daemon via `packages/contracts`.
- **D-R5 Protocol: versioned JSON control frames + binary payload frames** over WebSocket.
  Control: `hello`, `auth`, `open-channel`, `close-channel`, `ping/pong`, `error`. Payload frames
  carry `(channelId, opaque bytes)`. Version field in `hello`; relay rejects unknown majors. This is
  deliberately the same "scoped versioned wire format, not internal PanRpcGroup types" rule PAN-658
  locked for its conversation channel.
- **D-R6 The relay stores:** GitHub identity ↔ instance pairing table, per-instance room membership
  and block lists (PAN-658), push subscriptions, and nothing else. SQLite on the Fly volume;
  rebuildable; loss of relay state must never lose operator data (it can only force re-pairing).

## Requirements

- **FR-R1** An instance connects outbound to the relay with a pairing credential and maintains the
  connection (reconnect with jittered backoff; fake-timer tests).
- **FR-R2** A browser hitting `https://<relay>/i/<instance-slug>/...` gets: GitHub OAuth if no
  session → pairing check → frames proxied to that instance's room. Unpaired identities get a
  pairing-request screen, approved from the instance's dashboard (lobby pattern, reused by PAN-658).
- **FR-R3** The full dashboard works through the relay: HTTP API, `/ws/rpc`, `/ws/terminal`, SSE —
  i.e., the relay proxies arbitrary HTTP+WS to the instance, not a curated subset.
- **FR-R4** Instance-side enforcement: every proxied request arrives at the local server carrying a
  relay-asserted identity header, which the instance maps to a scoped token (PAN-2351) minted at
  pairing time. A relay compromise without a pairing grant yields no scopes.
- **FR-R5** Push origin: the relay exposes `POST /push` (instance-authenticated) and holds Web Push
  VAPID keys (v1) with APNs/FCM slots (v2); PAN-2354's bridge gains a `provider: 'relay'` option.
- **FR-R6** Rooms + presence + block lists sufficient for PAN-658 v0 (plain WSS rooms), per its
  locked lobby/admit/kick/revoke semantics.
- **FR-R7** `pan relay connect|status|pair|unpair` CLI; pairing approvals also surface in the
  dashboard Needs-You feed.
- **NFR-R1** No inbound ports on instances; relay outage degrades to local-only operation with a
  clear banner, never data loss.
- **NFR-R2** Relay is stateless-restartable; deploys must not wedge instances (daemon re-dials).
- **NFR-R3** Cost ceiling $5/mo until >3 instances; log volume capped; no payload logging ever.
- **NFR-R4** Node 22 for the daemon side (it lives inside the dashboard server); the relay service
  itself may be Bun (it has no node-pty / no circular-ESM constraint) — decide at implementation
  by which runtime the chosen WS lib is happiest under; record the decision in the vBRIEF.

## Work items (numbered; each → bead(s) at plan time)

- **W1 Protocol package.** `packages/contracts/src/relay-protocol.ts`: frame types, version const,
  encode/decode with tests. No I/O.
- **W2 Relay service** (`relay/`): WS server, room registry, GitHub OAuth (device flow for CLI,
  web flow for browsers), pairing table (SQLite), HTTP+WS proxy over rooms, `/push` endpoint,
  `fly.toml`. Vitest for room routing, pairing lifecycle, version rejection.
- **W3 Instance daemon.** New service in the dashboard server boot path — registered exactly like existing
  background services in `src/dashboard/server/main.ts`: the `startAgentEnrichmentService()` /
  `startAgentOutputService()` start block (`main.ts:151-165`), with teardown in the shutdown cleanup
  (`main.ts:498+`); the event-store subscriber block (`main.ts:459-478`) is the template for its
  event-forwarding half. Scope of the daemon:
  outbound connection, frame ↔ local-HTTP bridging (loopback fetch to `localhost:3011` with the
  pairing-mapped scoped token), reconnect, status surface. **Boot-path change ⇒ runtime-boot-test
  on a throwaway instance before live restart; `pan restart --health-timeout 120`** (repo rule).
- **W4 Pairing UX.** Dashboard approval card + `pan relay pair`; scoped-token mint on approval
  (`operate` default for the operator's own devices, narrower grants for guests).
- **W5 Push origin.** VAPID keypair on the relay, `/push` route, PAN-2354 provider option.
- **W6 Docs.** `docs/RELAY.md`: architecture, privacy tier statement (D-R3, honest), threat model,
  runbook, PAN-658 hand-off notes (what rooms/block-lists it can assume).

## Intersecting repo rules (restated)

Fake timers for reconnect/backoff tests; no `execSync` server-side; boot-path changes are
runtime-boot-tested (never hot-patched live); two-doors — the daemon bridges transport and never
reads/writes stores directly; commit early on main; work agents run through `pan`.

## Out of scope

E2E encryption tiers (v2), APNs/FCM (v2, needs paid dev accounts), multi-relay HA, billing,
PAN-658's own UI/lobby logic (it consumes rooms; it is not built here).
