# PAN-3937: OpenCode conversations stop answering when a Task subagent hits a permission ask

## Glossary

- **ACP** — Agent Client Protocol, the JSON-RPC-over-stdio transport Overdeck uses to drive OpenCode and Kimi as persistent agents (`packages/effect-acp`, `src/lib/acp/`).
- **ACP host** — the Overdeck-owned process (`dist/acp-host.js`, built from `src/lib/acp/host.ts`, class `AcpHost`) that spawns `opencode acp` (or `kimi acp`), drives the ACP session, writes the JSONL transcript, and exposes a local Unix-socket RPC (`op: "message" | "status" | "interrupt" | "set-effort"`) that the dashboard talks to.
- **ACP session** — an OpenCode session opencode's own ACP layer (`packages/opencode/src/acp/session.ts`, referenced as `ACPSession`) tracks and can relay permission asks for. A **primary session** (the one the ACP host created via `session/new`) is an ACP session. A **Task subagent session** (`mode=subagent`, spawned internally by opencode's `task` tool) is *not* registered as an ACP session.
- **Permission ask** — opencode's internal `Permission.ask()` (`packages/opencode/src/permission/index.ts`) blocking on a `Deferred` until something calls `Permission.reply()`. When the action for a requested `(permission, pattern)` pair evaluates to `"ask"`, the deferred blocks; `"allow"` and `"deny"` resolve immediately (deny throws).
- **Permission relay** — opencode's ACP layer (`packages/opencode/src/acp/permission.ts`, class `Handler`) subscribing to `permission.asked` events and forwarding them to the ACP client (Overdeck) via `session/request_permission`, then replying to opencode via `sdk.permission.reply()` once the client answers. It only relays asks whose `sessionID` resolves through `ACPSession.tryGet()` — a subagent session ID never does.
- **opencode HTTP server** — the local HTTP API opencode's `acp` command starts internally (`Server.listen()`) so its own CLI/SDK can talk to the running instance. It exposes `GET /permission` (list pending) and `POST /permission/:id/reply` (`{reply: "once"|"always"|"reject", message?}`). The ACP host does not currently know this server's port.
- **Watchdog** (this issue) — new host-side logic that polls the opencode HTTP server for permission asks the ACP relay never received, and auto-replies to unstick a deadlocked turn.

## Problem

An OpenCode conversation stops answering forever once one of its Task subagents hits a permission ask that opencode's ACP layer never relays. Every operator message queued after that point is accepted and stored, but the turn queue (`AcpHost.promptQueue`, `src/lib/acp/host.ts:83,237-286`) never advances because the prompt in flight is itself blocked on the subagent's stuck permission `Deferred`.

### Root cause, verified against opencode 1.18.31 source (`anomalyco/opencode` tag `v1.18.31`)

1. **The permission relay silently drops subagent asks.** `packages/opencode/src/acp/permission.ts`, `Handler.process()`:
   ```ts
   const session = await Effect.runPromise(this.input.session.tryGet(permission.sessionID))
   if (!session) return
   ```
   A Task subagent's session (`mode=subagent`, spawned by `packages/opencode/src/tool/task.ts`) is never registered with `ACPSession`, so `tryGet` misses and `process()` returns without ever calling `connection.requestPermission()` or `sdk.permission.reply()`. The ask's `Deferred` (`packages/opencode/src/permission/index.ts`, `ask()`) is never resolved. The subagent's tool call hangs forever; the parent's `task` tool call hangs waiting on the subagent; the parent's `session/prompt` RPC — which `AcpSessionRuntime.prompt()` (`src/lib/acp/session-runtime.ts` ~L745) awaits synchronously via `Fiber.join` — never resolves; `AcpHost.enqueuePrompt` (`src/lib/acp/host.ts:237`) never advances `promptQueue`; every subsequent `handleMessageOp` call queues behind it forever.

2. **Overdeck launches `opencode acp` with opencode's stock permission defaults**, which include several `"ask"` actions. `packages/opencode/src/agent/agent.ts` (the built-in `defaults` ruleset, lines ~118–134):
   ```ts
   const defaults = Permission.fromConfig({
     "*": "allow",
     doom_loop: "ask",
     external_directory: { "*": "ask", ...whitelistedDirs.map(d => [d, "allow"]) },
     question: "deny",
     plan_enter: "deny",
     plan_exit: "deny",
     read: { "*": "allow", "*.env": "ask", "*.env.*": "ask", "*.env.example": "allow" },
   })
   ```
   The three keys that default to `"ask"` (and therefore can deadlock a subagent per (1)) are **`external_directory`** (any path outside the session's own workspace/whitelisted dirs — this is what fired in the incident), **`doom_loop`** (opencode's own loop-detector), and **`read`** for `*.env`/`*.env.*` globs. `question`, `plan_enter`, and `plan_exit` default to `"deny"`, not `"ask"` — a denied permission throws `PermissionDeniedError` synchronously and does *not* deadlock, so those three are out of scope here.

3. **Subagents inherit the parent session's `external_directory` posture verbatim.** `packages/opencode/src/agent/subagent-permissions.ts`, `deriveSubagentSessionPermission()`:
   ```ts
   return [
     ...input.parentSessionPermission.filter(
       (rule) => rule.permission === "external_directory" || rule.action === "deny",
     ),
     ...(canTodo ? [] : [{ permission: "todowrite", pattern: "*", action: "deny" }]),
     ...(canTask ? [] : [{ permission: "task", pattern: "*", action: "deny" }]),
   ]
   ```
   Whatever `external_directory` ruleset the *parent* session was configured with flows straight into every subagent session it spawns. This is the lever Overdeck controls at launch time (work item 1): setting the parent's `external_directory` (and `doom_loop`, `read`) to `allow` removes the ask before opencode ever evaluates it for a subagent, independent of whether the relay would have worked.

### Incident evidence (conv 2834, 2026-09-19, harness `opencode`, opencode 1.18.31)

- `14:23:08` — subagent runs a bash command touching `/tmp/lexerra-rig-slot-*.lock`; `opencode.log`: `evaluated permission=external_directory ... action.action=ask` then `asking id=per_0ba0cad000013CKTpIac03yVfE permission=external_directory patterns="[\"/tmp/*\"]"`. No further activity from that run for 20+ minutes.
- `~/.overdeck/agents/conv-20260919-8174/acp-session.jsonl` has **no** `permission_request` entry for this ask — `AcpHost.handlePermissionRequest` (`src/lib/acp/host.ts:321`) appends one before doing anything else, confirming the relay never reached the host.
- Two more operator prompts (`14:21:11`, `14:35:12`) were delivered and queued behind the stuck turn (bridge log `~/.overdeck/logs/bridge-conv-20260919-8174.log`); no `turn_completed` for the original prompt.
- Unblocked live via the opencode HTTP API on the port it happened to be listening on: `curl -s 127.0.0.1:4096/permission` (listed the pending id) then `curl -s -X POST 127.0.0.1:4096/permission/per_.../reply -d '{"reply":"always"}'` — the run resumed within seconds and the queue drained. This confirms the HTTP fallback path is viable and is the mechanism the watchdog (work item 3) reuses.
- Contrast: an `external_directory /tmp/*` ask from a **primary** session on 2026-09-18 was relayed and auto-approved by the host in 12ms — the relay works correctly for primary sessions; the gap is subagent-only.

### Live-verified implementation facts

- `opencode debug config` with `OPENCODE_PERMISSION='{"external_directory":"allow","doom_loop":"allow","read":{"*.env":"allow","*.env.*":"allow"}}'` in the environment produces a merged config `"permission": {"external_directory":"allow","doom_loop":"allow","read":{"*.env":"allow","*.env.*":"allow"}}` — confirmed by running the actual installed opencode 1.18.31 binary (`~/.opencode/bin/opencode`). Env-injected values land in `cfg.permission`, which `packages/opencode/src/agent/agent.ts` folds in as the `user` ruleset positioned *after* `defaults` in the array `Permission.merge(defaults, user, ...)`; `evaluate()` (`packages/opencode/src/permission/index.ts`) picks the *last* matching rule (`Array.prototype.findLast`), so `user` rules win over `defaults`.
- `OPENCODE_PERMISSION` is parsed and deep-merged (`mergeDeep`) over `result.permission` **after** every other config source, including a user's own `opencode.jsonc` — so it also overrides an explicit `"deny"` a user configured for `external_directory`, `doom_loop`, or `.env` reads. This is a deliberate, scoped posture change (see NFR-1 and the Docs item) — not a general permission bypass, since only these three keys are touched.
- `opencode acp --help` confirms `--port` (default `0` — "prefer 4096, else any free port", per `packages/opencode/src/server/server.ts` `startWithPortFallback`) and `--hostname` (default `127.0.0.1`) flags exist and are honored (`packages/opencode/src/cli/network.ts` `resolveNetworkOptionsNoConfig` — an explicit `--hostname`/`--port` arg wins over any `server.hostname`/`server.port` value in the user's own opencode config).
- `startWithPortFallback` only retries the 4096→random fallback when the *default* `port: 0` is used; an **explicit non-zero `--port`** goes straight to `startListener(opts, opts.port)` with no fallback — a bind conflict on an explicitly-chosen port fails the whole `opencode acp` launch. The live host today already has two opencode processes running on `127.0.0.1:4096` and `127.0.0.1:45907` (confirmed via `ss -ltnp`), i.e. 4096 is already contended by a second concurrent conversation in normal operation — the port-selection design (work item 2) must not assume 4096 is free.

## Proposal

Two independent layers, matching the issue's own framing, plus a visible stall signal:

1. **Prevent the deadlock at the source.** Launch `opencode acp` with `external_directory`, `doom_loop`, and `read` (`*.env`, `*.env.*`) pre-set to `allow` via the `OPENCODE_PERMISSION` env var, so opencode never evaluates these as `"ask"` for any session, including subagents. This alone should make the incident's exact reproduction (a Task subagent touching `/tmp`) never ask.
2. **Catch anything pre-allow misses.** Give the ACP host a deterministic, known port for the opencode HTTP server it already spawns, and add a watchdog inside `AcpHost` that — only while a prompt is in flight for an opencode/opencode-go session, and only after the transcript has gone quiet for longer than a threshold — polls `GET /permission` on that port and auto-replies `{"reply":"always"}` to anything pending, logging a `permission_outcome` transcript entry with `source: "watchdog"` so the fallback is visible and distinguishable from the normal ACP-relayed auto-approve path.
3. **Surface a stuck turn to the operator** even if the watchdog itself somehow fails to unstick things (a different opencode bug, a network hiccup) — the dashboard conversation list already derives `isWorking`/`currentTool` from the ACP transcript; extend that derivation with a `stalledSince` signal and render a muted "waiting on agent — no activity since HH:MM" label in the conversation row.
4. **Document** the policy, the watchdog's exact behavior, and a manual unstick recipe (generalized from the incident's live `curl` commands to use the discovered port instead of the incident's coincidental `4096`).
5. **File upstream** (operator's call, not an xBRIEF item — see NonGoals) against `anomalyco/opencode`: ACP's `session/request_permission` is never emitted for `mode=subagent` sessions, so any ACP client relying on the relay (not just Overdeck) can deadlock on a Task subagent hitting an `"ask"` permission.

## Requirements

- **FR-1.** `buildOpenCodeAcpSpawnInput` (`src/lib/acp/opencode.ts`) sets `OPENCODE_PERMISSION` in the spawned `opencode acp` process's environment to `{"external_directory":"allow","doom_loop":"allow","read":{"*.env":"allow","*.env.*":"allow"}}` (as a JSON string), for the `opencode`/`opencode-go` providers only.
- **FR-2.** The ACP host reserves a TCP port before spawning `opencode acp` and passes it explicitly via `--hostname 127.0.0.1 --port <N>`, and both the spawn path and the `AcpHost` instance know that port.
- **FR-3.** While a prompt is in flight for an opencode/opencode-go session, `AcpHost` polls for staleness; once no runtime event has been observed for the trigger threshold, it calls `GET /permission` on the reserved port, and for every entry returned calls `POST /permission/:id/reply` with `{"reply":"always"}`, then appends one `permission_outcome` transcript entry per reply with `source: "watchdog"` and the entry's own `sessionID`.
- **FR-4.** `ConversationActivitySummary` (ACP branch) computes a `stalledSince` timestamp when the transcript file has not been modified for longer than the stall threshold while the turn is still open (`isWorking` true, no `turn_completed`/`prompt_failed` since the last prompt); this threads through `conversation-list.ts` into the enriched conversation row.
- **FR-5.** `ConversationRow` renders a muted "waiting on agent — no activity since HH:MM" label when `stalledSince` is set, following `pan-style-guide` (no decorative color, muted status text, `aria-label` matching the existing `AwaitingInputIndicator` pattern).
- **FR-6.** `configuration/harnesses.mdx`'s OpenCode section documents the pre-allow policy (exact keys and JSON), the deny-override caveat, the watchdog's port-discovery/cadence/reply policy, and the manual unstick recipe using the discovered port.
- **FR-7.** `sync-sources/skills/pan-diagnose/SKILL.md` gains a troubleshooting section for "OpenCode conversation stuck after a permission ask" with the same manual unstick recipe and how to recognize a watchdog-authored fix (`source":"watchdog"` in the transcript) versus one that needs manual intervention.
- **NFR-1.** The pre-allow policy touches only `external_directory`, `doom_loop`, and `read` (`*.env`/`*.env.*`) — `question`, `plan_enter`, `plan_exit`, and every other permission key are left exactly as opencode defaults or the user's own config sets them.
- **NFR-2.** The watchdog polls only for `provider === 'opencode' || provider === 'opencode-go'` sessions, only while a prompt is in flight, never at idle, and never for `kimi` (which shares the `acp` runtime name but a different binary and no opencode HTTP server).
- **NFR-3.** All timer/interval logic in the watchdog is tested with `vi.useFakeTimers()` / `vi.advanceTimersByTimeAsync()` — no real waits (`sync-sources/rules/fake-timers-for-retry-tests.md`).
- **NFR-4.** The host watchdog's own poll cadence (60s) and trigger threshold (180s of no runtime event while a prompt is in flight) are independent of, and tighter than, the dashboard's stall-banner threshold (300s), so the banner only appears once the host's own internal recovery attempt has already had a full cycle to fire — a row is never shown "working" and "stalled" as contradictory simultaneous signals for longer than that gap.

## Decisions made in this document

- **D1 — Pre-allow key set.** Only the three keys that opencode defaults to `"ask"` (`external_directory`, `doom_loop`, `read` for `.env` globs) are set via `OPENCODE_PERMISSION`. `question`/`plan_enter`/`plan_exit` default to `"deny"` (fail fast, no deadlock risk) and are left untouched — widening the pre-allow set to them would change behavior with no deadlock-prevention benefit.
- **D2 — Deterministic port, not `ss -ltnp` discovery.** The issue text suggests discovering the port opencode picked via `ss -ltnp` against the ACP process's PID. This plan instead has the host **choose** the port up front (reserve a free TCP port via a short-lived `net.createServer().listen(0)` call, close it, then pass that number as `opencode acp`'s explicit `--port`) and pass `--hostname 127.0.0.1` explicitly too (which — per `resolveNetworkOptionsNoConfig` — wins over any `server.hostname` a user's own opencode config sets, so Overdeck's opencode server can never be made to listen on a non-loopback address by user config). This avoids brittle process/PID-based port scraping and gives the host and the watchdog a value they already know, at the cost of a narrow reserve-then-bind race (acceptable: single-tenant localhost agent processes, and an `opencode acp` bind failure surfaces through `AcpHost.start()`'s existing catch-and-report path — see Hazard H1).
- **D3 — Watchdog reply policy is "always", not `selectAutoPermissionOutcome`.** `selectAutoPermissionOutcome` (`src/lib/acp/permissions.ts`) operates on ACP's `RequestPermissionRequest.options` (a named list of allow/reject choices). The opencode HTTP `/permission` list returns bare `PermissionV1.Request` objects (`{id, sessionID, permission, patterns, metadata, always, tool}`) with no such option list — there is nothing to categorize. The watchdog therefore always replies `{"reply":"always"}`, matching Overdeck's existing stance (the ACP relay auto-approves every ask it receives) applied to the one reply shape this HTTP endpoint understands.
- **D4 — Stall-banner scope.** FR-5 renders the label only in `ConversationRow` (the conversation list). Surfacing the same label inside the full `ConversationPanel` header is explicitly deferred (see NonGoals) to keep this task a single reviewable vertical slice; the list is where an operator scanning many conversations needs the signal most.
- **D5 — Upstream filing left to the operator.** Per the issue text ("operator's call"), no xBRIEF item files the opencode bug report. The exact root-cause paragraph above (Problem, point 1) is written to be pasted directly into an upstream issue if the operator chooses to file it.

## Hazards

- **H1 — Port reservation race (D2).** The reserve-then-close-then-pass-to-child pattern has a narrow window where another process could bind the reserved port before `opencode acp` starts. `AcpHost.start()` already treats any runtime-start failure as a launch error (writes `acp-launch-error`, stops, rethrows — `src/lib/acp/host.ts:161-171`), and `runtimes/acp.ts spawnAgent` already tears down the tmux session on any spawn failure — so a bind conflict surfaces as an existing, already-tested failure path, not a new hang. No new retry logic is added; this is accepted as a residual risk given the low collision probability for ephemeral OS-assigned ports.
- **H2 — `OPENCODE_PERMISSION` overrides a user's own `opencode.jsonc` deny.** Documented in NFR-1/D1/FR-6; this is an intentional, narrowly-scoped posture change, not an oversight.
- **H3 — Watchdog racing the real ACP relay.** If the relay resolves an ask between the watchdog's `GET /permission` and its `POST .../reply`, the `POST` 404s; treated as benign (see item 3).
