# PAN-4589 — CI test gate: recognize commit-status CI (Dagger Cloud checks)

**Issue:** https://github.com/eltmon/overdeck/issues/4589
**Status:** planned (auto mode, 2026-10-24)

## Glossary

- **Check run** — a GitHub Checks API result (GitHub Actions jobs). In `gh pr view --json statusCheckRollup` it appears as `{"__typename":"CheckRun","name":"test","status":"COMPLETED","conclusion":"SUCCESS","detailsUrl":"…"}`.
- **Commit status / status context** — a GitHub Statuses API result. In the rollup it appears as `{"__typename":"StatusContext","context":"go-client/test","state":"FAILURE","targetUrl":"https://dagger.cloud/…"}`. It has **no `name`, `status` or `conclusion` field**. Its `state` is one of `EXPECTED`, `PENDING`, `SUCCESS`, `FAILURE`, `ERROR` (rollup, upper case) or `pending`, `success`, `failure`, `error` (REST/webhook, lower case).
- **Dagger Cloud check** — one commit status that Dagger Cloud posts per Dagger check. `context` is the check path (`golang/packages/tests/test`), `target_url` is `https://dagger.cloud/<org>/checks/github.com/<owner>/<repo>@<sha>?check=<context>`. Verified 2026-10-24 on `dagger/dagger@366d6dd0`: 90 statuses on one commit, all on `dagger.cloud`.
- **Test job / test check** — the CI check(s) the CI test gate (`verification.tests: ci`, PAN-3965) treats as the project's test run. Today only `isCiTestCheckName(name)` decides this.
- **CI test gate** — in `verification.tests: ci` mode the verification gate skips the local `test` gate; the PR head's CI test job is the test gate (merge readiness needs `testJobSucceeded`; a red test job is counted and fed back by `ci-failure-feedback.ts`).
- **Default-branch baseline** — `readDefaultBranchFailingTestChecks` in `ci-default-branch-tests.ts`: the failing test-check names on the newest default-branch commit whose test checks all finished. A PR failure whose failing test checks are all in this set is "inherited" and not counted.
- **Segment match** — split a context on `/` and test each segment with `isCiTestCheckName`.

## Problem

Every test-job classifier calls `isCiTestCheckName(check.name)`. A StatusContext has no `name`, so commit-status CI (Dagger Cloud; also Buildkite, Jenkins, CircleCI) is invisible: a Dagger-only project shows `testChecks: 'none'` and `testJobSucceeded: false` forever, the merge gate and auto-merge eligibility never see a passed test job, the default-branch baseline is `no-tests`, a green Dagger test status never resets the attempt streak or lifts the verification-stuck pause, and red-test feedback says "no failing workflow runs were found" with no link.

## Requirements

### Functional

- **FR-1** A new exported predicate `isDaggerCloudTestCheck(name, targetUrl)` returns true iff `targetUrl` parses as an `https:` URL whose hostname is `dagger.cloud` or ends with `.dagger.cloud`, AND at least one `/`-separated segment of `name` satisfies `isCiTestCheckName`. `isCiTestCheckName` is unchanged.
- **FR-2** A new exported predicate `isCiTestRollupCheck(check)` (rollup row with optional `name`, `context`, `targetUrl`) returns `isCiTestCheckName(check.name ?? check.context) || isDaggerCloudTestCheck(check.context, check.targetUrl)`. Every PR-rollup test classifier uses it.
- **FR-3** `pr-facts` produces correct `testChecks`, `testCheckFailures`, `testJobSucceeded` for rollups of Dagger StatusContext rows (green, red, pending). A failing StatusContext's `FailedCheck` has `name` = context and `targetUrl` = its targetUrl.
- **FR-4** The default-branch baseline reads each commit's combined status (paginated) in addition to check runs, and counts Dagger test statuses: `pending` → undecided, `failure`/`error` → failing, `success` → passing.
- **FR-5** Mode auto-detection stays workflow-only. When no qualifying workflow is found and `dagger.toml` exists at the project root or a polyrepo member root, the `local` decision's reason ends with `; dagger.toml present; set verification.tests: ci if Dagger Cloud checks are on`.
- **FR-6** A `status` webhook with `state: 'success'` whose `(context, target_url)` is a CI test check calls `recordCiTestGatePass` (resets the red-head streak, lifts the verification-stuck pause), exactly as a green test `check_run` does.
- **FR-7** CI test-gate feedback for a failing test check reported as a commit status lists each such check by name with its `targetUrl`; a Dagger Cloud one also carries the rerun command `` `dagger check dag://<context>` ``.
- **FR-8** `toChecksState` honors `state`: `FAILURE`/`ERROR` → `red`, `PENDING`/`EXPECTED` → `pending`.
- **FR-9** Docs describe what is recognized and the one config line a Dagger Cloud project adds.

- **NFR-1** Existing GitHub Actions projects classify exactly as before: all existing `isCiTestCheckName`, `pr-facts-test-checks`, `pr-facts-ci-test-job`, `ci-default-branch-tests`, `webhook-handlers`, `ci-failure-feedback`, merge-gate and auto-merge tests pass with no assertion edits (fixture *extensions* to answer the new `gh` call are allowed, see WI-3).
- **NFR-2** `src/lib/cloister/pr-facts.ts` stays ≤ 1000 lines (`wc -l`). No file-size allowlist edits.
- **NFR-3** No `execSync` (server-reachable code); `gh` calls stay async `execFile`.
- **NFR-4** No new HTTP route (would need a no-loss-matrix row).

## Decisions (made here; auto mode)

- **D1 Predicate home.** `isDaggerCloudTestCheck`, `isCiTestRollupCheck` and `isDaggerCloudUrl` live in `src/lib/cloister/verification-tests-mode.ts` beside `isCiTestCheckName`. One classifier module, already imported by every consumer.
- **D2 Host rule.** `https:` scheme and hostname `dagger.cloud` or `*.dagger.cloud`; a malformed URL is false. Subdomains are Dagger-controlled; anyone who can post a status to the repo can already post any URL, so the host check is classification, not a trust boundary.
- **D3 First arm uses `name ?? context`.** A non-Dagger status whose whole context matches the single-name pattern (`test`, `tests (22)`, `test-e2e`) is recognized through `isCiTestCheckName` — the intended path for Buildkite/Jenkins/CircleCI statuses named that way. A non-Dagger `go-client/test` stays unrecognized (whole-string match fails; segment match only runs for `dagger.cloud`).
- **D4 `error` is failing.** pr-facts already treats StatusContext `ERROR` as failed and `COUNTED_TEST_CONCLUSIONS` counts `ERROR`; the baseline maps status `error` → conclusion `failure` so names line up with the PR side.
- **D5 Pagination.** The combined-status call uses `gh api --paginate` because `dagger/dagger` already posts 90 statuses per commit; one page (100) would silently drop test statuses and mislabel inherited failures as this PR's.
- **D6 `targetUrl` only from StatusContext.** `FailedCheck.targetUrl` is set only from the rollup row's `targetUrl` (StatusContext). Check runs' `detailsUrl` is NOT copied, so existing `toEqual` expectations on `listFailedTestChecks` stay valid (NFR-1).
- **D7 pr-facts stays under the ceiling by call-site swaps.** No extraction refactor; the three classifiers swap to `isCiTestRollupCheck(check)` and `listFailedTestChecks` builds rows through one local closure. Net growth ≤ +5 lines.
- **D8 In scope beyond the issue list:** the status-webhook pass path (FR-6) and `toChecksState` (FR-8). Without FR-6 a Dagger project's stuck pause never lifts (PIPELINE-GATES.md promises it does); without FR-8 the board shows a Dagger-red PR green and the auto-merge scheduler enqueues it (the merge gate still refuses, via pr-facts).
- **D9 `dod-gate.ts` unchanged** (C13).
- **D10 Mode detection stays workflow-based** (issue scope 4, review of #3993: never drop the local test gate on a guess). `dagger.toml` changes only the reason text, never the mode.

```ts
/** True when a commit status's target URL is a Dagger Cloud page (https, `dagger.cloud` or a subdomain). */
export function isDaggerCloudUrl(targetUrl: string | null | undefined): boolean {
  if (!targetUrl) return false;
  try {
    const url = new URL(targetUrl);
    return url.protocol === 'https:' && (url.hostname === 'dagger.cloud' || url.hostname.endsWith('.dagger.cloud'));
  } catch {
    return false;
  }
}

/**
 * PAN-4589: true when a commit status is a Dagger Cloud test check. Dagger
 * Cloud posts one status per check, its context the check path
 * (`go-client/test`, `golang/packages/tests/test`); any path segment the
 * single-name matcher accepts makes it a test check.
 */
export function isDaggerCloudTestCheck(name: string | null | undefined, targetUrl: string | null | undefined): boolean {
  if (!name || !isDaggerCloudUrl(targetUrl)) return false;
  return name.split('/').some((segment) => isCiTestCheckName(segment));
}

/** A `statusCheckRollup` row: a check run (`name`) or a commit status (`context`, `targetUrl`). */
export interface CiRollupCheck {
  name?: string;
  context?: string;
  targetUrl?: string;
}

/** PAN-4589: true when a rollup row (check run or commit status) is the project's CI test job. */
export function isCiTestRollupCheck(check: CiRollupCheck): boolean {
  return isCiTestCheckName(check.name ?? check.context) || isDaggerCloudTestCheck(check.context, check.targetUrl);
}
```

```ts
export function toChecksState(
  rollup: ReadonlyArray<{ status?: string; conclusion?: string | null; state?: string }> | undefined,

  const rows = rollup ?? [];
  if (rows.length === 0) return 'pending';
  if (rows.some((row) => row.conclusion && !['SUCCESS', 'NEUTRAL', 'SKIPPED'].includes(row.conclusion.toUpperCase()))) {
```
