## Glossary

- **Needs-you item** — something blocked on the operator. This issue covers four kinds (FR-15): `question` (an AskUserQuestion or a `pan ask` decision), `approval` (a plan approval or a permission prompt), `finished` (a work agent signalled done, or an issue merged), `failed` (an agent died, a merge failed, a stalled review or a conflict repair escalated).
- **Web Push** — the W3C Push API. The phone's browser gives the dashboard a **subscription** `{ endpoint, keys: { p256dh, auth } }`. The `endpoint` is a URL at the browser vendor's **push service** (FCM for Chrome/Android, Apple for Safari/iOS, Mozilla autopush for Firefox). The machine POSTs a message to that URL and the push service wakes the phone.
- **VAPID** (RFC 8292) — the machine's own P-256 key pair. Each push request carries a JWT signed with it, so the push service knows which application server sent it. The public key is given to the browser at subscribe time.
- **RFC 8291 encryption** — the `aes128gcm` content encoding. The payload is encrypted with ECDH between a fresh sender key and the subscription's `p256dh` key, plus the 16-byte `auth` secret. Only the phone can decrypt it; the push service sees ciphertext.
- **`web-push`** — the npm package (`web-push@3.6.7`) that implements VAPID signing and RFC 8291 encryption. This plan uses its `generateRequestDetails()` and sends the request itself with `fetch`. No custom crypto (the PAN-2355 draft's D-5 already required this).
- **Service worker (`sw.js`)** — a script the browser keeps registered for the dashboard origin. Its `push` handler shows the notification even when no dashboard tab is open; its `notificationclick` handler opens the dashboard at the item's URL.
- **ntfy** — a self-hostable pub/sub notification server. Publishing is an HTTP POST to `<server>/<topic>` with `Title`, `Priority`, `Tags` and `Click` headers.
- **Provider** — one delivery channel behind the `PushProvider` interface (`webpush`, `ntfy`). PAN-2080 adds Slack, email and TTS behind the same interface.
- **Enrichment poller** — `src/dashboard/server/services/agent-enrichment-service.ts`. Every 10 s (`POLL_INTERVAL_MS = 10_000`, grep `const POLL_INTERVAL_MS`) it computes each running agent's pending input and emits `agent.enrichment_changed` with `pendingAskUserQuestion`, `pendingProposedPlan` and `pendingInputKinds`. It re-emits an unchanged pending state on purpose (`shouldForceReemitPendingInput`), so consumers must deduplicate.
- **Conversation pending-input feed** — `getConversationsPendingInputFeed()` in `src/lib/overdeck/conversation-reads.ts` (grep `export async function getConversationsPendingInputFeed`). It scans every live conversation's transcript tail and pane and returns rows `{ name, title, issueId, harness, pendingAskUserQuestion?, pendingProposedPlan?, pendingPaneChoice?, pendingPermission?, heldKickoff? }`. On success it returns `{ body: rows }` with `status` undefined. There is **no server event** when a conversation gets a pending AskUserQuestion; the browser polls `GET /api/conversations/pending-input` every 4 s.
- **AskUserQuestion hook** — `sync-sources/hooks/ask-user-question-hook`, registered as a `PreToolUse` hook with matcher `AskUserQuestion` (`src/lib/claude-hooks-registration.ts`, grep `ask-user-question-hook', matcher`). For every real decision question it POSTs `{ kind: "ask_user_question_blocked", timestamp, questions }` to `/api/agents/<id>/heartbeat` (via `pan_emit_event`). The server drops it today: `bodyToEvent` (`src/dashboard/server/services/agent-event-utils.ts`, grep `export const bodyToEvent`) returns `null` for unknown kinds. Conversations get `OVERDECK_AGENT_ID` on Herdr (`src/lib/overdeck/conversation-runtime.ts`, grep `Hooks attribute by OVERDECK_AGENT_ID`), and the hook falls back to the tmux session name on tmux.
- **Pipeline journal event** — `pipeline.journal` domain events. `appendPipelineEntry()` (`src/lib/cloister/pipeline-journal.ts`) calls `notifyPipeline()`, which reaches the server from any process (CLI processes POST `/api/internal/pipeline/notify`); `main.ts` turns it into `{ type: 'pipeline.journal', payload: { issueId, entry } }` (grep `type: 'pipeline.journal'`).
- **Primary vs peer dashboard** — `isPeerDashboardProcess()` (`src/lib/boot-gates.ts`). A peer dashboard must not send pushes, or the phone gets duplicates.
- **Secure context** — Web Push and service workers need HTTPS, or `http://localhost`. A phone reaches the machine over HTTPS through Tailscale Serve (PAN-1254 automates that setup; until it lands the operator runs `tailscale serve` by hand).

## Problem

When an agent or conversation asks a question, waits for approval, finishes or fails, nothing reaches the operator away from the screen. Desktop notifications (`src/dashboard/frontend/src/App/hooks/usePermissionNotifications.ts`, `useDesktopActivityNotifications.ts`) need an open dashboard tab. TTS needs the operator in the room. There is no push code at all: `grep -rniE "ntfy|web-push|webpush|vapid|PushSubscription|serviceWorker" src` finds nothing, and the frontend has no manifest and no service worker.

## Decisions

- **D-1 Web Push is the primary provider; ntfy is optional and carries titles only.** From epic D-16. The machine signs with its own VAPID key and sends directly to the browser's push service. No relay, no overdeck.ai involvement.
- **D-2 Use `web-push@3.6.7` for VAPID and RFC 8291; send with `fetch`.** Call `webpush.generateRequestDetails(subscription, payload, options)` to get `{ endpoint, method, headers, body }`, then send with the global `fetch` and an `AbortController` timeout of 5 s. This keeps the crypto in an audited library and keeps timeouts and tests in our hands. Add `@types/web-push@3.6.4` and `http_ece@1.2.0` (the version `web-push` itself uses, for decrypting in tests) as devDependencies.
- **D-3 Detection lives in one server service, `needs-you-push-service.ts`, fed by four sources.**
  1. `agent.enrichment_changed` events — agent questions (including `pan ask` decisions, whose `toolUseId` starts with `operator-decision:`), plan approvals and permission prompts.
  2. The conversation pending-input feed, scanned every **5 s**, but only while at least one push target exists (a Web Push subscription or a configured ntfy topic).
  3. **Instant wake:** the AskUserQuestion hook's `ask_user_question_blocked` heartbeat and the `conversation.permission_changed` event (with `waiting: true`) both call `wakeNeedsYouPush()`. A wake runs the conversation scan and an immediate enrichment poll (`pollEnrichmentNow()`, new export) after a 500 ms debounce. This is what keeps a Claude Code AskUserQuestion well under 10 s; the 5 s scan and 10 s poller are the fallback for other harnesses.
  4. Edge events for `finished` and `failed` (closed list in D-5).
- **D-4 Rising-edge model with per-subject pending sets.** Each subject (an agent id, or a conversation name) has a set of pending keys: `auq:<toolUseId>`, `plan:<toolUseId>`, `perm:<signature>` (conversations: `pendingPermission.signature ?? 'pending'`; agents: `perm:pending` while `pendingInputKinds` contains `permissionRequest`). A key notifies once, when it first appears. When a key disappears it is forgotten, so the next prompt notifies again. Keys are also deduplicated **across subjects**: a key that is currently active under any subject is not sent again. A conversation can appear both as an enrichment agent (`listRunningAgents` includes `conv-` state directories) and as a feed row, and `auq:`/`plan:` toolUseIds are globally unique, so this prevents a double push. On service start, items whose `askedAt`/`since` is more than 60 s before the service started are recorded silently (a restart never replays old questions). Items with no timestamp notify.
- **D-5 Closed trigger list.**

  | Kind | Source | Key |
  |---|---|---|
  | question | agent `pendingAskUserQuestion`; conversation row `pendingAskUserQuestion` | `auq:<toolUseId>` |
  | approval | agent `pendingProposedPlan` or `pendingInputKinds` ∋ `permissionRequest`; conversation row `pendingProposedPlan` or `pendingPermission` | `plan:<toolUseId>`, `perm:…` |
  | finished | `pipeline.journal` with `entry.type` `verification.started` (the work agent ran `pan done`) or `merge.completed` | `journal:<issueId>:<entry.type>:<entry.ts or data.head>` |
  | failed | `agent.heartbeat_dead`; `pipeline.journal` with `entry.type` `merge.failed`, `review.stall-escalated` or `conflict.repair-escalated` | `dead:<agentId>:<timestamp>`, `journal:…` |

  Everything else is out: `pendingPaneChoice`, `heldKickoff`, `rateLimit`, `sessionResume`, `agentTurnEnded`, `verification.failed` (that is routed back to the agent automatically), `agent.stopped`.
- **D-6 Payload is metadata-only by default.** The payload is encrypted end to end, but the phone's lock screen still shows it. The default body never contains question text. `push.includePreview: true` adds the first question text (or the plan's first line), truncated to 140 characters, to Web Push only. ntfy never gets a body or a preview.
- **D-7 Payload format (Web Push, JSON, encrypted) — the contract agreed with PAN-2355's `sw.js`:** exactly `{ "title": string, "body": string, "url": string, "tag": string }`, with no other keys. (`tag` is optional in the contract; this issue always sends it.) `url` is always a same-origin path:
  - question and approval items open that question: `/m?subject=<encodeURIComponent(subjectId)>`, where `subjectId` is the agent id (agent items) or the conversation name (conversation items). It is a query parameter, not a path segment, because the dashboard's static server returns 404 for any path whose last segment contains a dot, and ids can contain dots;
  - finished, failed, summary and test notifications open `/m`.

  `/m` is PAN-2355's phone shell (the Needs-you list). Until PAN-2355 lands, `/m` falls through to the SPA's `index.html`; the desktop app loads, and its answering dialogs still open by themselves because `AppLiveStoreHost` mounts them app-wide (hazard, not a blocker).
- **D-8 Titles.**
  - **Web Push** titles name the item: `Question · <label>`, `Approval needed · <label>`, `Finished · <issueId>`, `Failed · <label>`. `<label>` is the conversation title (cut to 60 characters, else its name), else `<issueId> <role>`, else the agent id.
  - **ntfy** titles carry only the kind and either `<issueId>` or the literal `a conversation`. Conversation titles are free text, so they never reach a third-party ntfy server.
  - Default bodies:
    - question: `Tap to answer.`
    - approval: `Tap to review.`
    - finished: `Work is done; verification started.` or `Merged.`
    - failed: `The agent stopped responding.`, `Merge failed.`, `A review stalled and needs you.` or `A conflict repair needs you.`
- **D-9 Rate limit.** At most 6 notifications per rolling 60 s across all subjects. Items over the limit are counted, not sent. When the window that dropped items closes, one `summary` notification goes out: `<N> more items need you` (url `/m`, tag `summary`).
- **D-10 Delivery rules (both providers).**
  - The request timeout is 5 s.
  - A network error, HTTP 429 or a 5xx gets exactly one retry after 5 s, then the item is dropped and counted.
  - Web Push 404 or 410 means the subscription is gone, so it is deleted.
  - Any other 4xx increments `failureCount` on the subscription and is logged.
  - Sending never blocks the event loop, never throws into the event-store subscriber, and never affects other services.
- **D-11 Web Push request options.**
  - `TTL: 3600`.
  - `urgency`: `'high'` for question, approval and failed; `'normal'` for finished, summary and test.
  - `topic`: the first 32 characters of base64url(sha256(tag)), so a newer push replaces an undelivered older one with the same tag.
  - `contentEncoding: 'aes128gcm'`.
  - `vapidDetails`: `{ subject, publicKey, privateKey }`.
- **D-12 VAPID key: created once, never overwritten.** It is stored at `<OVERDECK_HOME>/push/vapid.json` as `{ publicKey, privateKey, createdAt }`, file mode 0600, directory mode 0700. Creation follows `src/lib/environment-identity.ts` (grep `export async function ensureEnvironmentIdentity`): write a temp file, `link()` it into place, and treat `EEXIST` as "someone else won" and re-read. Regenerating the key would silently orphan every subscription, so nothing in this issue rotates it.
- **D-13 Subscription store.**
  - **File:** `<OVERDECK_HOME>/push/subscriptions.json`, mode 0600. A subscription endpoint plus its keys is a bearer push capability.
  - **Writes:** serialized through one in-process queue; each write goes to a temp file and is renamed into place. This is the `src/lib/access-tokens.ts` pattern.
  - **Record:** `{ id, endpoint, keys: { p256dh, auth }, label, credentialId: string | null, createdAt, lastSuccessAt: string | null, lastFailureAt: string | null, failureCount }`.
  - **`id`:** the first 16 hex characters of sha256(endpoint). Re-subscribing the same endpoint updates the existing record.
  - **Cap:** 20 records; a 21st distinct endpoint is rejected with `subscription-limit`.
- **D-14 Endpoint allowlist (SSRF guard).** An endpoint must be `https:`, have no credentials and no explicit port other than 443, and its hostname must be one of:
  - `fcm.googleapis.com`
  - `updates.push.services.mozilla.com`
  - `web.push.apple.com`, or any host ending in `.push.apple.com`
  - any host ending in `.notify.windows.com`

  Anything else is rejected with `endpoint-not-allowed`. The allowlist is a module constant; the dispatcher test injects a fake host through a constructor option that is not reachable from config or HTTP.
- **D-15 Revoked devices stop receiving push.** Each subscription records the subscribing credential: a device id for a paired device, `null` for the root session. Before each send, a subscription whose device record is missing or has `revokedAt` set is deleted and skipped. Device records come from `listAccessTokens()` (`src/lib/access-tokens.ts`). This keeps the epic's threat-model promise that revoking a device cuts it off.
- **D-16 Config block `push` in `config.yaml`, camelCase like `tts`.** All of it lives in a new file, `src/lib/config-yaml/push-config.ts`. `schema.ts` (1084 lines, cap 1114), `defaults.ts` and `merge.ts` each get 1–3 lines. `settings-api.ts` (1485 lines, cap 1508) is **not** touched: the Settings panel uses its own `/api/push/*` routes, and ntfy and event filters are edited in `config.yaml`.

  ```yaml
  push:
    enabled: true            # default true; subscribing a phone is the opt-in
    events: [question, approval, finished, failed]   # default: all four
    includePreview: false    # default false (D-6)
    webpush:
      subject: https://overdeck.ai   # default; Apple requires an https: or mailto: subject
    ntfy:                    # optional; provider is active only when url AND topic are set
      url: https://ntfy.example.net
      topic: deck-k3J9xQ2mV7pL4sTa
      token: tk_...          # optional bearer token for publishing
      clickBaseUrl: https://desk.tailnet.ts.net   # optional; Click header only when set
  ```
  Validation never throws at load time; the dashboard must boot with a bad block. An invalid `events` entry is ignored. A `url` that is not http(s), or a `topic` that fails `^[A-Za-z0-9_-]{1,64}$`, makes ntfy `misconfigured`, with the reason shown in `GET /api/push/status`. Config is read with `loadConfigSync()` at each dispatch, so edits take effect without a restart.
- **D-17 Seam with PAN-2355 (agreed with the PAN-2355 planner, 2026-11-01).** There is exactly one service worker.

  **PAN-2355 owns:**
  - `src/dashboard/frontend/public/manifest.webmanifest`;
  - `public/sw.js`, including its `push` and `notificationclick` handlers;
  - service-worker registration;
  - the phone shell at `/m` (`src/dashboard/frontend/src/components/mobile/MobileApp.tsx`).

  **PAN-2354 owns:**
  - the VAPID keys, the subscription store and routes, and the send path;
  - the **Turn on notifications** control, which goes in `MobileApp.tsx`'s header;
  - the desktop Settings → Anywhere **Phone notifications** panel.

  **Second-lander rule (both plans):**
  - Whichever issue lands second extends the existing `sw.js`; it never adds a second worker or a second script URL.
  - The same rule covers `manifest.webmanifest`, the `index.html` manifest link, and mounting the Turn on notifications control in `MobileApp.tsx`.
  - If this issue lands first, it creates `sw.js` and a minimal manifest that meet the contract, and PAN-2355 extends them.
  - If PAN-2355 lands first, this issue only checks its handlers against the contract and mounts the control.

  **Contract both sides honor:**
  - The payload is D-7.
  - `notificationclick` focuses an open same-origin client and navigates it to `data.url`; otherwise it opens a new window at `data.url`.
  - A non-same-origin `url` is replaced with `/m`.
  - `sw.js` registers no `fetch` handler unless PAN-2355 adds one for its precache.
  - Registration always uses `navigator.serviceWorker.register('/sw.js', { scope: '/' })`. Registering the same script URL and scope again returns the existing registration, so the control's call and PAN-2355's call never create two workers.
- **D-18 Routes are admin-scoped by default.** `/api/push/*` routes are not added to `ROUTE_SCOPES` (`src/dashboard/server/route-scopes.ts`), because an unlisted route needs `admin`, which is the intended scope. Paired phones hold `admin` (`src/dashboard/server/routes/pairing.ts`, grep `scopes: ['admin'], kind: 'device'`). Every new route gets a row in `tests/unit/lib/overdeck/no-loss-matrix.ts`, or `no-loss-matrix.test.ts` fails.

## Requirements

- **FR-1** A `push` config block (D-16) with defaults `enabled: true`, `events: ['question','approval','finished','failed']`, `includePreview: false`, `webpush.subject: 'https://overdeck.ai'`, and no ntfy. It is normalized into `NormalizedConfig.push` and never throws.
- **FR-2** A VAPID key pair is created once at `<OVERDECK_HOME>/push/vapid.json` (mode 0600) and is never overwritten (D-12).
- **FR-3** A subscription store with an endpoint allowlist, a cap of 20, credential binding and atomic 0600 writes (D-13, D-14, D-15).
- **FR-4** A `PushProvider` interface and a `NeedsYouNotification` type that PAN-2080 can implement against.
- **FR-5** A `webpush` provider that encrypts each payload with RFC 8291 `aes128gcm` to the subscription key, signs with VAPID, and follows D-10, D-11 and D-15.
- **FR-6** An `ntfy` provider that publishes a title-only message and follows D-8 and D-10.
- **FR-7** A pure classifier that turns enrichment payloads, conversation rows and edge events into needs-you items (D-4, D-5, D-7, D-8).
- **FR-8** A dispatcher that applies rising-edge dedup, the startup priming rule, the `events` filter, the rate limit with a summary (D-9), fan-out to providers, and counters.
- **FR-9** The server service `needs-you-push-service.ts`: event subscription, the conditional 5 s conversation scan, `wakeNeedsYouPush()` with a 500 ms debounce, primary-dashboard only.
- **FR-10** The AskUserQuestion hook's `ask_user_question_blocked` heartbeat wakes the service.
- **FR-11** Routes:
  - `GET /api/push/vapid-public-key`
  - `GET /api/push/status`
  - `POST /api/push/subscriptions`
  - `DELETE /api/push/subscriptions/:id`
  - `POST /api/push/test`
- **FR-12** Exactly one service worker at `/sw.js` whose `push` and `notificationclick` handlers meet the D-7/D-17 contract. It is created by this issue only if PAN-2355 has not landed it (second-lander rule); likewise the minimal manifest and `index.html` links.
- **FR-13** A shared **Turn on notifications** control that subscribes this device. It is mounted in `MobileApp.tsx`'s header (second-lander rule) and in a Settings → Anywhere **Phone notifications** panel that also lists subscribed devices, removes one, sends a test and shows ntfy status.
- **FR-14** Operator and developer documentation (W14).
- **NFR-1** A Claude Code AskUserQuestion in a conversation or agent produces a push request to the push service within 2 s of the hook firing (debounce 500 ms plus scan). Any other harness's question produces one within 10 s (5 s scan plus delivery). Agent questions without the hook produce one within 10 s plus the enrichment interval.
- **NFR-2** With no subscription and no ntfy topic, the service does no conversation scanning and sends nothing. Only the event subscriber is registered.
- **NFR-3** No `execSync` and no synchronous file I/O in server-reachable push code (use `node:fs/promises`). Every delay is a `setTimeout` that tests drive with fake timers.
- **NFR-4** No secret material appears in logs or in `GET /api/push/status`: no private VAPID key, no subscription keys, no full endpoint URL (only its host), no ntfy token, and the ntfy topic masked to its first 4 characters plus `…`.

### W6 Web Push provider (`webpush`)
- New `src/lib/push/webpush-provider.ts`: `createWebPushProvider(deps?: { fetchImpl?; now?; listCredentials?; readConfig?; extraHosts? }): PushProvider`.
- `hasTargets()` is true when at least one subscription exists.
- `send(n)` processes every subscription in parallel with `Promise.allSettled`:
  1. **Credential check (D-15).** If `credentialId !== null` and `listAccessTokens()` has no record with that id, or the record has `revokedAt`, remove the subscription and report `revoked`.
  2. **Build the request.** Call `webpush.generateRequestDetails({ endpoint, keys }, JSON.stringify(payload), { vapidDetails: { subject: cfg.webpush.subject, publicKey, privateKey }, TTL: 3600, urgency, topic, contentEncoding: 'aes128gcm' })`. Keys come from `ensureVapidKeys()`. The payload is exactly `{ title: n.title, body: n.body, url: n.url, tag: n.tag }` (D-7), with no other keys.
  3. **Send.** `fetchImpl(details.endpoint, { method: 'POST', headers: details.headers, body: details.body, signal })` with a 5 s timeout.
  4. **Outcome (D-10).**
     - 2xx: `recordPushDelivery(id,'success')`, report ok.
     - 404 or 410: remove the subscription, report `gone`.
     - 429, 5xx or a network error: wait 5 s (`setTimeout`) and retry once; on a second failure report `transient` and record a failure.
     - Any other status: record a failure and report `rejected`.
- Logs carry only the endpoint host and the subscription id.
- **Tests:** new `tests/unit/lib/push/webpush-provider.test.ts`, fake timers, with `fetchImpl` stubbed to capture requests:
  1. **Round trip.** Generate a subscriber key pair with `crypto.createECDH('prime256v1')` and 16 random auth bytes, and subscribe it with an allowed FCM endpoint. Send. Decrypt the captured body with `http_ece.decrypt(body, { version: 'aes128gcm', privateKey: ecdh, authSecret })`; the parsed result deep-equals `{ title, body, url, tag }` and has exactly those four keys.
  2. **Unreadable at the push service.** The captured body does not contain the payload's title bytes. Decrypting with a different ECDH key throws.
  3. **Headers.** `Content-Encoding: aes128gcm`, `TTL: 3600`, `Urgency: high` for a question, and an `Authorization` header that starts with `vapid t=`.
  4. A 410 removes the subscription.
  5. A 503 then 201: exactly two fetch calls, the second only after `advanceTimersByTimeAsync(5000)`.
  6. A revoked credential makes zero fetch calls and removes the record.

## Intersecting repo rules (restated)

- **Fake timers** for every retry, debounce, rate-limit and interval test: `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()`, never real 5 s waits, never `maxForks: 1`.
- **No `execSync`** and no blocking I/O in server-reachable code; use `node:fs/promises`.
- **Dashboard runs Node 22 from `dist/`.** Run `npm run build` before restarting it. `main.ts` is a boot-path change: run the build and check the server starts (`pan reload` is the operator's call, not the agent's).
- **New HTTP routes** need `no-loss-matrix.ts` rows; route scopes default to `admin` (D-18).
- **File-size guard:** `schema.ts` ≤ 1114, `merge.ts` ≤ 1045, `settings-api.ts` untouched, `main.ts` ≤ 1000, and every new file < 1000. Never raise an allowlist cap.
- **Frontend style** follows the `pan-style-guide` skill: no pill badges, `font-medium` at most, no decorative color.
- **Quality gates** before `pan done`: `npm run typecheck`, `npm run lint`, and `npx vitest run <touched test files>`. Never run the full `npm test` on the host.
- **Never send destructive requests speculatively.** Tests use stubbed `fetch`; nothing in the test suite hits a real push service or ntfy server.

## Non-goals

- Slack, email and TTS providers (PAN-2080, on the same `PushProvider` interface).

- Answering from the notification itself (notification actions or replies).
- Closing a notification on the phone after the item is answered elsewhere.
- Quiet hours, per-project routing, digests.
- Relay-delivered push or any overdeck.ai involvement (D-16 of the epic).
- VAPID key rotation.
- Pushes from peer dashboards or from other linked machines (fleet-wide needs-you is FR-13, owned by the conversations-across-machines issues).
- Setting up Tailscale Serve automatically (PAN-1254).
- Pricing copy in `anywhere.mdx` (the W-DOC owner applies OD-3).
