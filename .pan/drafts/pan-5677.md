# PAN-5677: Ctrl+K "Newest first" must pick the newest matching conversations on the server

**Issue:** [PAN-5677](https://github.com/eltmon/overdeck/issues/5677)

## Glossary

- **Palette search.** `GET /api/palette/search?q=&limit=` in `src/dashboard/server/routes/palette.ts`. The Ctrl+K command palette calls it with `limit=15`.
- **Chunk.** One indexed slice of a Claude Code transcript in `embeddings.db` (table `chunks`, columns include `session_id`, `parent_session_id`, `ts`, `text`). `ts` is an ISO-8601 UTC string (`2026-11-24T13:53:21.870Z`) or NULL.
- **BM25 leg / vector leg.** The two chunk scans the ranker runs: SQLite FTS5 keyword search (`searchBm25`) and sqlite-vec nearest-neighbour search (`searchVector`). Each returns at most 300 chunks for the palette (`CONVERSATION_CHUNK_POOL`).
- **RRF.** Reciprocal-rank fusion in `fuseRankedRows` (`src/lib/conversation-search/ranker.ts`). A chunk's `rrfScore` is the sum of `1/(60 + index + 1)` over the legs that returned it.
- **Candidate pool.** The fused, live-filtered chunk hits that `groupConversationHits` groups into one row per conversation.
- **Tier.** The ranking band of a grouped row: `title` (every query term prefixes a title word) < `text` (the query matched prose) < `path` (matched only inside code or a path).
- **Recency leg (new).** A second BM25 scan over the same FTS match, ordered by chunk `ts` newest first instead of by BM25 score. It runs only for a newest-first search.
- **Sort mode (new).** `relevance` (today's order, the default) or `recent` (newest first). Sent as the `sort` query parameter.
- **lastMatchAt (new).** For a grouped row: the newest `ts` among all of the row's chunk hits in the candidate pool and, for a title match, the conversation's last activity (`last_attached_at ?? created_at`). Null when none of these exist.

## Problem

Ctrl+K search for `restic` does not show conversation `20261124-2455` ("B2 backup recovery and storage optimization", active 2026-11-24), although its transcript mentions restic many times. The server ranks it 22nd and the palette asks for 15 rows.

Cause, verified in code:

1. `compareGroups` in `src/lib/conversation-search/group-hits.ts` (search `function compareGroups`) orders rows by tier, then best-chunk `score`, then `hitCount`. Recency is only the last tiebreaker, and that tiebreaker uses the best chunk's `ts`, not the conversation's newest match.
2. `groupConversationHits` truncates with `rows.slice(0, limit)` before the client sees anything.
3. The palette's **Newest first** toggle is on by default (`localStorage.getItem(PALETTE_CONVERSATIONS_NEWEST_FIRST_KEY) !== 'false'` in `src/dashboard/frontend/src/components/CommandPalette.tsx`). It only re-sorts the 15 rows the server already chose (`.sort(group === 'Conversations' && conversationsNewestFirst ? compareConversationActionsNewestFirst : …)`), so it can never surface a newer conversation the server ranked 16th or lower.
4. The BM25 leg keeps the 300 best-scoring chunks. For a common term (`backup` matches 15,837 chunks, `the` matches 509,299) a recent conversation's chunks can fall outside that pool entirely, so even a server-side sort over the pool would miss it.

## Decisions

- **D1. Fix newest-first on the server; leave relevance mode unchanged.** The issue offers (1) a recency decay in the score or (2) a server-side newest-first sort. Newest first is on by default, so (2) fixes the operator's case directly, and it changes no ranking for callers that never asked for it (the MCP `search_conversations` tool, fleet search). No recency decay is added to relevance mode.
- **D2. The `sort` query parameter.** `sort=recent` selects newest first. Any other value, or no value, means `relevance`. The default stays `relevance`, so `src/lib/mcp/tools-read.ts` and `src/dashboard/server/routes/fleet-awareness.ts` keep today's behaviour without changes.
- **D3. "Newest" means `lastMatchAt`**, the newest matching chunk (or title-match last activity) of the row, not the best chunk's `ts`. A long conversation whose best chunk is old but which mentioned the term yesterday must sort as yesterday.
- **D4. Recent-mode row order** is: tier (title < text < path), then `lastMatchAt` descending with null last, then the relevance comparator (score, hitCount, id) as tiebreak. Relevance-mode order is exactly today's `compareGroups`.
- **D5. Server and client sort on the same key.** The wire row gains `lastMatchAt`. The palette sets `sortTs` to `hit.lastMatchAt ?? hit.ts`, so `compareConversationActionsNewestFirst` (tier, then `sortTs` desc, then rank) reproduces the server order and never reshuffles it. The comparator itself does not change.
- **D6. The date chip shows `lastMatchAt ?? ts`** in both modes, so dates read in order under newest first.
- **D7. The recency leg is appended, not fused.** Its rows that are not already in the relevance hits are appended after them with `rrfScore: 0` and ranks continuing from the last relevance hit. RRF scores, the relevance hits' order, and each row's best hit (which prefers relevance hits because they come first) are unchanged. `hitCount` counts the union; the field already documents "chunk hits in the candidate pool".
- **D8. The recency leg runs only when `sort=recent`.** It reuses the existing `searchConversationBm25` DB-worker operation with a new payload field `order: 'recent'`, so it runs on the existing serial `conversation-text` lane under the existing `CHUNK_SCAN_DEADLINE_MS` (4 s, counted from submission). In relevance mode the BM25 payload is byte-for-byte today's payload (no `order` key).
- **D9. The recency leg is best effort.** A missed deadline or any error other than the request abort contributes no rows and logs one `console.warn`; the search returns the relevance pool. The leg's promise never rejects (abort is handled by the main path's `throwIfAborted`), so no unhandled rejection is possible.
- **D10. The toggle refetches.** `conversationsNewestFirst` joins the search effect's dependencies; toggling it sends a new request with the matching `sort` value.
- **D11. Scope boundary.** Fleet ("On &lt;machine&gt;") groups, the MCP tool and the CLI keep relevance order and do not forward `sort`.

## Requirements

- **FR-1.** `GET /api/palette/search?q=<q>&limit=<n>&sort=recent` returns conversation rows ordered by tier, then `lastMatchAt` descending (null last), then relevance, truncated to `limit`.
- **FR-2.** Without `sort`, or with any value other than `recent`, the endpoint returns exactly today's order and today's BM25 payload.
- **FR-3.** In recent mode the server adds up to 300 chunks from a recency-ordered BM25 scan to the candidate pool before grouping and truncation.
- **FR-4.** Every conversation row on the wire carries `lastMatchAt: string | null`.
- **FR-5.** The palette sends `sort=recent` while **Newest first** is on and `sort=relevance` while it is off, and refetches when the toggle changes.
- **FR-6.** The palette orders newest-first conversation rows and labels their date chip with `lastMatchAt ?? ts`.
- **FR-7.** The user docs describe newest first as a server-side choice of the newest matching conversations.
- **NFR-1.** A recency leg that misses its deadline or fails returns the relevance results; the request does not fail, and no conversation-search health failure is recorded for it.
- **NFR-2.** Relevance-mode latency is unchanged: no extra DB-worker job runs when `sort` is not `recent`.
- **NFR-3.** No file grows past its file-size guard limit (`scripts/lint-file-size.sh`; `CommandPalette.tsx` cap is 1124, today 1072 lines).

### W2. `appendRecentRows` merges recency rows after relevance hits (FR-3)

Files: `src/lib/conversation-search/ranker.ts`, test `src/lib/conversation-search/__tests__/ranker.test.ts`.

Add, below `fuseRankedRows`:
```ts
/**
 * Newest-first palette search (PAN-5677): append recency-leg rows that the
 * relevance hits do not already contain. Relevance hits keep their order,
 * ranks and RRF scores; appended rows score 0 and rank after them.
 */
export function appendRecentRows(input: {
  hits: ConversationSearchHit[];
  recentRows: RankedChunkRow[];
  query: string;
}): ConversationSearchHit[] {
  const seen = new Set(input.hits.map((hit) => hit.rowid));
  const out = [...input.hits];
  for (const row of input.recentRows) {
    if (seen.has(row.rowid)) continue;
    seen.add(row.rowid);
    const excerpt = buildMarkedExcerpt(row.text, input.query);
    out.push({ ...row, rank: out.length + 1, rrfScore: 0, excerpt, excerptSegments: parseMarkedExcerpt(excerpt) });
  }
  return out;
}
```
Tests (`describe('appendRecentRows (PAN-5677)')`): duplicates by `rowid` are dropped; relevance hits are returned unchanged and first; appended rows have `rrfScore` 0, consecutive ranks after the last relevance hit, and a marked excerpt (`⦇needle⦈`); a duplicate inside `recentRows` itself is appended once.

   function compareGroups(a, b) {            // relevance mode: identical to today

   function compareGroupsRecent(a, b) {
     const tierDiff = TIER_ORDER[a.tier] - TIER_ORDER[b.tier];

## Hazards

- **H1. Serial lane.** The recency leg queues behind the relevance BM25 scan on `conversation-text`. On a cold cache a very common term can miss the 4 s deadline; the result then degrades to the relevance pool (D9). Accepted.
- **H2. Unhandled rejection.** The recency-leg promise is created before `rankConversationSearch` is awaited. It must carry its own `.catch` at creation (W4 step 2) or a failure in the relevance path leaves it unobserved.
- **H3. Test fixtures without `lastMatchAt`.** Frontend fixtures in `CommandPalette.test.tsx` and fleet hits omit the field; the `?? hit.ts` fallback keeps them working. Do not make the frontend field required.
- **H4. `fleet-search.test.ts:22` pins `/api/palette/search?q=cache&limit=15`.** Fleet code is out of scope; do not change that URL.
- **H5. File-size guard.** `CommandPalette.tsx` is 1072 lines with a cap of 1124. W6 adds a handful of lines; never raise the cap.
