# PAN-5057 — Restart hold: the gate's claim step ignores a hold set after approval

**Issue:** [PAN-5057](https://github.com/eltmon/overdeck/issues/5057). Follow-up to PAN-5007 / PR #5056 (operator restart hold), raised in that PR's approving review ("advisory: claim route ignores a hold set in the ~5s after approval") and by the CodeRabbit inline comment on `src/dashboard/server/routes/restart-gate.ts`.

## Glossary

- **Restart gate** — the dashboard's in-memory approval queue for *voluntary* restarts (`pan reload`, bare `pan restart`, the post-merge deploy). One module owns it: `src/dashboard/server/services/restart-gate.ts`.
- **Requester** — a CLI process waiting at the gate. It runs `waitForRestartApproval()` in `src/lib/restart-gate-client.ts`, which polls `POST /api/restart-gate/requests` every 5 s (`RESTART_GATE_POLL_INTERVAL_MS`). Each poll refreshes the request's 20 s TTL (`REQUEST_TTL_MS`).
- **Epoch** — one approval. It snapshots the ids of every pending request (`RestartGateEpoch.requesterIds`). Status `approved` = epoch open, nobody claimed; `claimed` = one requester holds the claim.
- **Claim** — `POST /api/restart-gate/claim`. Exactly one epoch member is `granted: true` and performs the restart. Every other member is later marked *satisfied*.
- **Restart hold** — the PAN-5007 operator lock file `~/.overdeck/restart-hold.json`, written by `pan restart hold`, deleted by `pan restart release`, lapsing at its optional `--until`. Module: `src/lib/restart-hold.ts`. `readRestartHold()` returns the active hold or `null`; a file that exists but cannot be parsed reads as an active hold.
- **Cached hold** — the `hold` variable inside `createRestartGate()` (`let hold: RestartHold | null = null;`, line 417). It is refreshed only by `read()` and `sweep()` (every 5 s), and is used only to publish `restartHold` on the snapshot.
- **Fail closed** — when the hold cannot be read, behave as if a hold is active (refuse).

## Problem

PAN-5007 enforces the hold at `pan reload`, `pan restart`, `pan restart approve`, `POST /api/restart-gate/approve` (route, `const hold = yield* Effect.promise(() => readRestartHold());`) and `POST /api/system/restart-dashboard` (`src/dashboard/server/services/dashboard-restart.ts`, `hold = await readRestartHold();`). It is **not** checked at the claim step.

`src/dashboard/server/routes/restart-gate.ts` lines 77–91 (`postClaimRoute`) calls `getRestartGate().claim(requesterId)` directly, and the service's `claim` (`src/dashboard/server/services/restart-gate.ts` line 454, `claim: async (requesterId) => mutate((current, nowMs) => claimRestartGate(current, requesterId, nowMs)),`) never looks at the hold.

Sequence that leaks one restart:

1. `pan reload` is pending at the gate. The operator approves → epoch opens, status `approved`.
2. Within the next ≤5 s (before the requester's next poll), the operator runs `pan restart hold --reason "live check"`.
3. The requester polls, sees `status: 'approved', mayClaim: true`, posts the claim, gets `granted: true`, and restarts the dashboard — through the hold.

## Requirements

- **FR-1** While a restart hold is active, `claim` never grants: every call answers HTTP 200 `{ granted: false, status: <derived status>, restartHold: <the hold> }`, for every requester, including a live claimant re-claiming its own claim.
- **FR-2** A claim refused for a hold leaves gate state unchanged apart from the normal prune: the epoch stays open with the same `requesterIds`, an existing claim is neither added nor removed, so the requester keeps polling and its polls keep the epoch alive.
- **FR-3** The claim reads the hold file **fresh** on every call (not the cached hold). A hold written after the last sweep is seen by the very next claim.
- **FR-4** If reading the hold file throws, the claim is refused (`granted: false`, no `restartHold` field) and the error is logged with `console.error('[restart-gate] Reading the restart hold failed; refusing the claim:', error)`.
- **FR-5** An expired hold (its `until` is not in the future at claim time) does not block the claim.
- **FR-6** Once the hold is released (or expires), the next claim by an epoch member is granted with no second approval, provided the requester kept polling (its TTL never lapsed).
- **FR-7** A requester whose claim is refused for a hold logs one line saying the restart is approved but held, naming the hold, and that it will restart after `pan restart release` with no second approval. It logs it again only when the hold text changes. While held, its 60 s heartbeat says it is waiting for the hold to be released, not for operator approval.
- **FR-8** The docs say what FR-1–FR-7 mean for operators and agents (Work item 3).
- **NFR-1** Two concurrent claims still serialize: exactly one is granted when no hold is active (the existing `serializes concurrent claims so exactly one is granted` test stays green unchanged).
- **NFR-2** No change to the wire contract other than the additive optional `restartHold` field on the claim response. The claim route keeps answering 200, not 409: the client treats any non-OK claim as "unavailable", and the issue's fix direction specifies `granted: false`.
- **NFR-3** Every new delay-based client test uses fake timers (`vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync`), per the repo rule `fake-timers-for-retry-tests`. The client test file already does this in `beforeEach`.

## Decisions

- **D1 — check in the service, not the route.** The service already has an injectable `readHold` dep (`RestartGateDeps.readHold`), so the check is testable in `src/dashboard/server/services/__tests__/restart-gate.test.ts` next to the PAN-5007 cases, as the issue asks. The route file needs only its header comment updated.
- **D2 — the pure state machine decides.** `claimRestartGate(state, requesterId, nowMs, activeHold = null)` gains a 4th optional parameter. The service awaits the fresh read first, then calls `mutate(...)` synchronously, so the hold check and the state transition are one synchronous step (NFR-1).
- **D3 — fail closed on read error** (FR-4). Rationale: `restart-hold.ts` already treats an unreadable file as an active hold ("failing open would let a restart through that the operator asked to stop"), and the approve route fails with a 500 on the same error. The requester keeps polling and claims once the read succeeds. This deliberately differs from `refreshHold()` (keeps the last value), which only feeds the banner.
- **D4 — a successful claim-time read also updates the cached hold**, so the `publish()` inside `mutate` carries the new `restartHold` at once instead of up to 5 s later.
- **D5 — refuse a live claimant's re-claim too** (FR-1). One rule ("while held, claim never grants") is simpler than an exception. The existing claim is left as it is; it lapses after `CLAIM_LAPSE_MS` (5 min) like any claim. A live claim means a restart is already under way, which the banner already ranks above the hold (`if (hold && gate.status !== 'claimed')`).
- **D6 — the client change is in scope** (FR-7). Before this fix an approved requester waited at most ~5 s; now it can wait as long as the hold lasts, and without D6 it would print "Still waiting for operator approval", which is false. The change is a log line and a heartbeat text, nothing else in the loop changes.
- **D7 — no frontend change.** `RestartApprovalBanner.tsx` line 131–132 already shows "Restarts on hold" whenever a hold is set and status is not `claimed`, which covers `approved` + held.
- **D8 — no changelog edit.** `docs/RELEASING.md` "Update the public changelog" says `changelog.mdx` is written by hand on release day from `pan release notes`.
