# PAN-4340: Every mutating `pan spawn` worker gets its own item worktree; docs match the code

**Issue:** [PAN-4340](https://github.com/eltmon/overdeck/issues/4340)
**Parent PRD:** [.pan/drafts/deft-adoption.md](./deft-adoption.md), "Issue 6" (ready-to-file list, item 6 of 16; operator-approved 2026-09-28).
**Related:** PAN-4339 (claim refusal for live competing claims and overlapping scope, merged `9c31c3a9f8f`), PAN-4337 (git shim branch expectation for `.swarm/<item>` worktrees, merged `9d3d0258652`), PAN-4350 (re-dispatch budget reads the item branch).

## Glossary

- **Issue workspace** — the git worktree `<project>/workspaces/feature-<issue>/`, checked out on the **feature branch** `feature/<issue>` (lowercase issue id).
- **Item worktree** — a git worktree at `<workspace>/.swarm/<item-id>/`, checked out on the **item branch** `<feature-branch>-<item-id>` (a sibling of the feature branch, e.g. `feature/pan-7-item-a`). Created or reused by `createItemWorktree` in `src/lib/workspaces/item-worktree.ts`. `.swarm/` is gitignored. All worktrees of one repository share refs, so a commit on the item branch is visible from the issue workspace immediately, without any push.
- **Foreman** — the issue's `work` agent when the xBRIEF plan has parallel waves. Protocol lives in `sync-sources/skills/pan-foreman/SKILL.md` (operational) and `docs/FOREMAN.md` (reference).
- **Worker** — an agent the foreman dispatches onto one xBRIEF item. Two **dispatch kinds**:
  - **in-harness subagent** — the foreman's `Agent` tool, same harness family;
  - **`pan spawn` pane** — a terminal-backend pane created by `pan spawn --issue <id> --item <item> --model <m> [--harness <h>]`, used for cross-family workers or when the operator should see the worker as its own pane.
- **Hand-back** — the worker's last act: one commit with the `Item: <item-id>` trailer on its item branch, then a report of that commit to the foreman. The worker does not push and does not run `pan task done`.
- **Integrate** — the foreman's act of bringing the item commit onto the feature branch (cherry-pick or merge, keeping the `Item:` trailer), pushing the feature branch, and running `pan task done <issue> <item>`.
- **`--shared`** — the new `pan spawn` flag that keeps the old behavior: the worker pane runs in the issue workspace itself. For strictly serial use only.

## Problem

1. `pan spawn` gives a worker its own worktree only when the xBRIEF item declares a `files_scope`. `src/cli/commands/spawn.ts` lines 98-102 today:

   ```ts
   const filesScope = item.metadata?.files_scope;
   const cwd = filesScope?.length
     ? await (deps.createWorktree ?? createItemWorktree)(workspacePath, item.id)
     : workspacePath;
   ```

   An item without `files_scope` runs in the shared issue workspace, where the foreman skill itself warns that "concurrent workers in one worktree WILL clobber shared files" (`sync-sources/skills/pan-foreman/SKILL.md` line 47-48).

2. The docs contradict the code. `docs/FOREMAN.md` line 67 says "a `pan spawn` pane pushes the shared feature branch directly", and line 78-79 says "A `pan spawn` pane already pushed the shared branch itself — just confirm it landed." The skill says the same (`SKILL.md` lines 66-67, 68-70, 74-75, 84-85). But a scoped `pan spawn` worker commits on `<feature>-<item>` (`item-worktree.ts` line 30, `const itemBranch = \`${featureBranch}-${itemId}\`;`), which the foreman must integrate.

3. A worker in an item worktree cannot complete its own item. `pan task done` (`runTaskDone`, `src/cli/commands/task.ts` line 166) calls `markItemDone` (`src/lib/xbrief/continue-state.ts`, `export async function markItemDone`) with `repoRoots` derived from the **issue**, not the caller's cwd (`issueRepoRoots(issueId, workspacePath, planHome)`). `hasTrailerCommit` runs `git log -n 1 --grep=^Item: <id>` in each repo root, which walks the **issue workspace's HEAD** (the feature branch), and `unpushedCommitCount` checks that branch against its upstream. So a commit that exists only on the item branch is never found. This is why the protocol must be: the worker hands back, the foreman integrates and then runs `pan task done`. The code forces it; this plan just makes every dispatch kind follow it and makes the docs say so.

## Decisions (made here, not deferred)

- **D1. Item worktree is the default for every `pan spawn` worker.** `files_scope` no longer influences cwd. Without `--shared`, `pan spawn` always calls `createItemWorktree(workspacePath, item.id)`; with `--shared`, cwd is `workspacePath` — even when the item declares `files_scope`. (`files_scope` still drives claim-overlap refusal in `pan task claim`, PAN-4339; that code is untouched.)
- **D2. `--shared` is refused from a `pan spawn` worker pane.** "Foreman or operator only" is enforced by one closed-set check: when `process.env.OVERDECK_ITEM_ID` is set, `pan spawn --shared` prints an error and exits 1 before creating anything. `OVERDECK_ITEM_ID` is set only by `pan spawn` itself (`spawn.ts` line 130; `git grep OVERDECK_ITEM_ID -- src` finds no other writer), so its presence means the caller is a `pan spawn` worker. The foreman and operator shells do not carry it. This is a cooperative guard (a process can unset its env), matching the level of the other PATH/env guards; it is not a sandbox. `pan spawn` without `--shared` stays allowed from anywhere (no behavior change there).
- **D3. One hand-back protocol for both dispatch kinds.** Worker: `pan task claim` → implement → one commit with `Item: <item-id>` on its current branch (item branch; or the feature branch under `--shared`) → report the commit sha to the foreman → stop. Worker never pushes, never runs `pan task done`, never runs `pan done`. Foreman: integrate the commit onto the feature branch (cherry-pick or merge; re-add the trailer if squashing; nothing to integrate for a `--shared` worker whose commit is already on the feature branch) → `git push` the feature branch → `pan task done <issue> <item>`.
- **D4. How a pane worker reports.** The foreman writes a dispatch prompt (sent with `pan tell <worker-pane>` after `pan spawn` returns) that includes the foreman's own `$OVERDECK_AGENT_ID`. The worker's last step is `pan tell <that id> "<item-id> committed <sha> on <branch>"`. The prompt guard (`src/lib/terminal-backends/prompt-guard.ts`, rule 2) only gates prompts **to** `worker` panes, so a worker may message its foreman. The fact the foreman acts on is git, not the message: from the issue workspace, `git log --format=%H -E --grep='^Item: <item-id>[[:space:]]*$' <feature-branch>..<feature-branch>-<item-id>` shows the item commit. An in-harness subagent reports in its final Agent-tool result instead.
- **D5. No new state.** Worktree existence is the fact (it is read by `existsSync` in `createItemWorktree`). Nothing is stored, stamped, or journaled.
- **D6. Worker does not push its item branch.** The item branch has no upstream and nothing reads it remotely; the foreman sees it through shared refs.

## Requirements

- **FR-1.** Given an xBRIEF item with no `files_scope`, `pan spawn` (no `--shared`) calls `createItemWorktree(<workspace>, <item-id>)` and launches the pane with cwd `<workspace>/.swarm/<item-id>`.
- **FR-2.** Given an item with a `files_scope`, `pan spawn` (no `--shared`) behaves as FR-1 (unchanged from today).
- **FR-3.** Given `--shared`, `pan spawn` does not call `createItemWorktree` and launches the pane with cwd `<workspace>`, whether or not the item declares `files_scope`.
- **FR-4.** Given `--shared` and `OVERDECK_ITEM_ID` set in the caller's environment, `pan spawn` prints an error naming `--shared` as foreman/operator only, exits 1, creates no worktree, and starts no pane.
- **FR-5.** The item worktree is on branch `<feature-branch>-<item-id>` (existing `createItemWorktree` behavior, already pinned by `src/lib/workspaces/__tests__/item-worktree.test.ts`; not changed).
- **FR-6.** `sync-sources/skills/pan-foreman/SKILL.md` describes one hand-back protocol (D3, D4) for both dispatch kinds, includes a dispatch-prompt template for workers, names the foreman as the only caller of `pan task done`, and describes `--shared`.
- **FR-7.** `docs/FOREMAN.md` describes the same protocol and no longer says a `pan spawn` pane pushes the feature branch.
- **FR-8.** `sync-sources/agents/pan-work-agent.md` states the split correctly: workers claim and commit; the foreman integrates, pushes and runs `pan task done`.
- **NFR-1.** No new persisted state (D5).
- **NFR-2.** `npm run typecheck`, `npm run lint`, and `npx vitest run tests/unit/cli/commands/spawn.test.ts` pass. Do not run the full `npm test` on the host (CI runs it).
- **NFR-3.** No new file-size allowlist rows needed: `spawn.ts` (153 lines) and `spawn.test.ts` (210 lines) stay far under the 1000-line ceiling in `scripts/lint-file-size.sh`.

## Intersecting repo rules (restated)

- Async only in code reachable from the server; `createItemWorktree` already uses `execFile` promisified. Do not add `execSync`.
- Tests: no real git against `/tmp/proj` paths in `spawn.test.ts` — inject `createWorktree` via `SpawnDeps`. No new source-grep tests, no `skipIf`/`.only` (lint and the test-skip gate reject them).
- Commits: one commit per xBRIEF item with a body line `Item: <item-id>`; run only the touched test files.
- Worktree discipline: never `git checkout` another branch inside the workspace; never `git stash`.

## Non-goals

- No change to `createItemWorktree` or `worktreeBranch` (branch naming, reuse semantics).
- No refresh of a reused item worktree onto the latest feature branch (a stale base on re-dispatch is PAN-4350 territory).
- No change to `pan task claim` / `pan task done` code, the prompt guard, or the git shim (PAN-4337).
- No change to `pan worker run` (`src/lib/agents/worker/start.ts`) — it already uses item worktrees for non-read-only workers.
- No change to the dormant `pan swarm` machinery or `roles/work.md` swarm section.
- No new persisted state, lease, or journal event.
- No automatic cleanup of `.swarm/<item>` worktrees or item branches after integration.

## Hazards

- **H1.** Flipping the default breaks every existing `spawn.test.ts` case that does not inject `createWorktree` (real git against a fake path). W1 step 8 covers it.
- **H2.** `createItemWorktree` reuses an existing `.swarm/<item>` as is. A re-dispatch after the foreman integrated starts from the old item branch; the foreman's next cherry-pick may conflict. Not fixed here (non-goal).
- **H3.** `pan task done` run by a worker in `.swarm/<item>` fails with "no commit … carries the trailer" — expected; the docs must say the foreman runs it.
- **H4.** The `--shared` guard is env-based and cooperative (D2); do not describe it in docs as a security boundary.
