## Glossary

- **Agent token:** a `kind: 'token'` access-token record with `agentId`, `agentKind` (`'agent' | 'conversation'`) and `role` (W-TOK1). Its credential in the dashboard is `{ kind: 'token'; tokenId; scopes; agentId?; agentKind?; role? }` (`src/dashboard/server/routes/dashboard-auth.ts:158`).
- **Self route:** a route under `/api/self/` that acts for the agent whose token calls it. `selfCallerFromCredential` (`src/dashboard/server/self-caller.ts:52`) turns the credential into a `SelfCaller` (`agentId`, `agentKind`, `role`, `cwd`, `issueId`, `tmuxSession`) or a 403 `not-an-agent-token` / 404 `agent-gone` refusal.
- **Root credential:** `internal-token` or `root-session` (`dashboard-auth.ts:155-156`). Only a browser on this machine (root session) or the `pan` CLI (internal token) holds one.
- **Agent request:** a pending question from an agent to the operator that the operator answers in the dashboard. This item adds the store and the `secret` kind; W-LINK1 adds the `machine-link` kind.
- **Secret request:** an agent request of kind `secret`. It names an environment-variable-style `name` (for example `OPENAI_API_KEY`) and a short `prompt`.
- **Owner directory:** the agent's private directory under `~/.overdeck/`: `getAgentDir(agentId)` = `~/.overdeck/agents/<agentId>/` for an agent (`src/lib/agents/agent-state-read.ts:245`), `conversationStateDir(tmuxSession)` = `~/.overdeck/conversations/<tmuxSession>/` for a conversation (`src/lib/overdeck/conversation-pane-role.ts:7`). Both are outside every workspace, so no repository can commit a file in them.
- **Secrets directory:** `<owner directory>/secrets/`, mode 0700. A delivered secret is the file `<secrets directory>/<name>`, mode 0600.
- **Decisions panel:** the dashboard list of everything waiting on the operator, `src/dashboard/frontend/src/components/DecisionsPanel.tsx`, fed by `useDecisions()` (`src/dashboard/frontend/src/lib/useDecisions.ts:263`).
- **Wait chunk:** one blocking call of at most `WAIT_CHUNK_MS = 50_000` ms (`src/lib/mcp/tool.ts:31`). A wait answers `pending` with `next` (the call to make again) or a final status.
- **Canary:** in tests, a unique random secret value (for example `canary-<uuid>`) that the test searches for in every output to prove it never leaks.

## Requirements

### Functional

- **FR-1 Ask.** An agent token calls `POST /api/self/secret-requests` with `{ name, prompt, timeoutMs? }` and gets a pending request id plus the `secret_wait` call to make next.
- **FR-2 Wait.** `GET /api/self/secret-requests/:id/wait` blocks at most 50 s and answers the request's status; on `delivered` it answers the file path, never the value. Only the requesting agent can wait on its request.
- **FR-3 List.** `GET /api/agent-requests` (scope `read:conversations`) answers the pending requests for the Decisions panel, without any value or owner directory.
- **FR-4 Answer.** `POST /api/agent-requests/:id/secret` (root credential only) writes the value to `<owner directory>/secrets/<name>` (file 0600, directory 0700) and marks the request `delivered`. `POST /api/agent-requests/:id/decline` (root credential only) marks it `declined`.
- **FR-5 Expire.** A pending request becomes `expired` at its `expiresAt` (default 10 minutes after creation, 1 to 60 minutes allowed). A dashboard restart forgets every request.
- **FR-6 Tools.** `request_secret` and `secret_wait` are agent-only MCP tools over FR-1 and FR-2.
- **FR-7 Card.** The Decisions panel shows each pending secret request as a card with the agent, the prompt, the name, a masked input, Send and Decline. Only a root-session viewer gets the input and buttons; any other viewer reads "Answer this on <machine>'s own dashboard".
- **FR-8 Cleanup.** When an agent's tokens are revoked (stop, kill, exit, close-out, sweep), its secrets directory is deleted.

### Non-functional

- **NFR-1 The value stays out of every output** (epic NFR-2): never in a response body, a tool result, an activity entry, a `console.*` call, an error message, a URL, argv or env. It exists only in the answer request's body, in memory while the handler runs, and in the 0600 file.
- **NFR-2 One authority** (epic NFR-1): the tools call the routes; the gate plus the handler checks decide.
- **NFR-3 Async only** (repo rules `no-execsync-server`, `prefer-async`): `node:fs/promises` only; no `*Sync` call and no new `*Sync` function.
- **NFR-4 Fake timers** (repo rule `fake-timers-for-retry-tests`): expiry and wait tests use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`; never real sleeps.
- **NFR-5 Size** (epic NFR-5): every new module stays under 600 lines; `server.ts` grows by 4 lines at most.
- **NFR-6 Bounded waits** (epic NFR-8): no route or tool blocks longer than `WAIT_CHUNK_MS`.
- **NFR-7 Routes** (epic NFR-9): every new route lives in a top-level `routes/` file and has a no-loss row; the three agent-reachable routes have scope rows; the two answer routes have none on purpose (Decision D-4).

## Decisions

- **D-1 One store for every agent request kind.** `services/agent-requests.ts` holds `kind: 'secret' | 'machine-link'` and status `'pending' | 'delivered' | 'declined' | 'expired' | 'linked'` in its types, as the epic specifies, so W-LINK1 (PAN-4942) adds routes without reshaping the store. This item implements only the `secret` kind: no route creates a `machine-link` request, and the frontend adds only the `secretRequest` kind. *(Auto decision.)*
- **D-2 The owner directory is captured at creation.** The create route computes it from the `SelfCaller` (`getAgentDir(agentId)` for an agent, `conversationStateDir(tmuxSession)` for a conversation) and stores it on the held record. The answer handler never re-resolves it and no read route returns it.
- **D-3 Expiry is lazy; no background timer.** Every store method first marks overdue pending requests `expired`, and a wait's timer is `min(timeoutMs, expiresAt - now)`, so a waiter wakes at expiry. This is observably the same as the epic's 30 s sweep, starts no interval at boot, and tests deterministically with fake timers. *(Auto decision; deviates from the epic's wording, not its behaviour.)*
- **D-4 Answer routes are root-only and have no scope row.** The gate then refuses every registry credential (even one with `approve`) with 403 `insufficient_scope`, and the handler refuses anything but `internal-token` and `root-session` with 403 `{ code: 'root-only' }` as a second line. Why: a secret must come from the operator at this machine, never from a bot or another agent's token.
- **D-5 Self routes skip the CSRF helper.** The only credential that passes `selfCallerFromCredential` is a bearer token, and bearer tokens skip CSRF anyway (`dashboard-auth.ts:279-280`). The self POST route parses its body without `rejectUnsafeDashboardMutationRequest`; the answer routes call it, because a root session is a cookie.
- **D-6 A repeated ask returns the pending request.** When the same agent asks for the same `name` while a request for it is still pending, the create route answers that request (status 200, same `requestId`) instead of making a second one. Why: an agent that retries after a lost reply must not stack cards. *(Auto decision.)*
- **D-7 Delivery to a stopped agent is refused.** Before writing, the answer handler checks that the request's agent still holds an active (not revoked) agent token. If not, it marks the request `expired` and answers 409 `{ code: 'agent-stopped' }` without writing. Why: revocation already deleted the secrets directory, and a file written after it would never be cleaned up. *(Auto decision.)*
- **D-8 A restart forgets requests; the wait answers 404.** The store is in memory, so after a dashboard restart a wait on an old id gets 404 `{ code: 'unknown-request' }`, and the `secret_wait` description tells the agent to call `request_secret` again. *(Correction C-1.)*
- **D-9 A request decision is its own row.** A secret request becomes a `Decision` with `id` = the request id (32 hex), `source` = the requester's kind (`'agent'` or `'conversation'`), `kinds: ['secretRequest']`, `blocking: true`, and a new `agentRequest` field. `DecisionsPanel` renders `AgentRequestCard` for a decision with `agentRequest` and never shows the generic Open/Answer buttons for it. `MobileNeedsYou` shows "Answer on the desktop" for it. Why: the generic Answer button reopens the AskUserQuestion dialog, and an agent with both a question and a secret request would otherwise collide on the row key. `secretRequest` joins `BLOCKING_KINDS` because the agent is parked in `secret_wait`. *(Auto decision.)*
- **D-10 Labels.** A request's `label` is `"<agentId> · <ISSUE-ID>"` when the caller has an issue, else `"<agentId>"`. The activity entries read `Secret <name> delivered to <label>` and `Secret <name> declined for <label>`, never the value.
- **D-11 Limits.** `name` matches `^[A-Z][A-Z0-9_]{0,63}$` (safe as a file name: no `/`, no `.`). `prompt` is 1..300 characters after trimming. `timeoutMs` is an integer 60,000..3,600,000 (default 600,000). `value` is a non-empty string of at most 65,536 UTF-8 bytes. At most 20 pending requests per agent (`429 { code: 'too-many-requests' }`). A non-pending request is dropped 1 hour after it ends.
- **D-12 AC-12 evidence on this branch is an integration test.** Because no live agent holds an agent token until PAN-4932 merges (Fact 10), AC-12 is proven by an in-process test that mints a real agent token in a temporary `OVERDECK_HOME`, drives the routes through the real remote request gate, calls the MCP tools, and searches every response, tool result, activity entry and `console.*` call for the canary. The live transcript search is a post-PAN-4932 check recorded in `continue.json`. Browser UAT on this branch checks that the Decisions panel loads with `GET /api/agent-requests` returning an empty list. *(Auto decision.)*

## Corrections to the epic's W-SEC1 text

- **C-1** The epic says a restart makes the wait answer `expired`. The store is in memory, so the id is unknown after a restart: the wait answers 404 `unknown-request` (D-8).

     ```ts
     export interface AgentRequests {
       /** D-6: an existing pending request of the same agent and name is answered with created: false. */
       createSecret(caller: SelfCaller, input: { name: string; prompt: string; timeoutMs: number; label: string }):
     ```

## Acceptance criteria

- **AC-1 (WI-1)** `createAgentRequests` answers a repeated ask with the same id, refuses the 21st pending request of one agent, hides another agent's request from `getForCaller` and `wait`, and expires a request at `expiresAt` on fake timers.
- **AC-2 (WI-1)** `writeAgentSecretFile` produces a 0600 file in a 0700 `secrets` directory, tightens an existing 0755 directory, leaves no `.partial` file, and rejects a name with `/` or `.`.
- **AC-3 (WI-2)** `POST /api/self/secret-requests` answers 201 with `next.tool === 'secret_wait'` for an agent token, 403 `not-an-agent-token` for a root session, 400 with codes `bad-name`, `bad-prompt`, `bad-timeout`, `bad-body` for bad input, and 200 with the same `requestId` for a repeated ask.
- **AC-4 (WI-2)** The wait route answers `pending` with `next` after 50 s, `delivered` with `file` after delivery, and 404 `unknown-request` for another agent's request.
- **AC-5 (WI-3)** Through the real gate, a token with `approve` gets 403 on both answer routes; called directly, a non-root credential gets 403 `root-only`; `GET /api/agent-requests` answers rows without any `value`, `result` or owner-directory field.
- **AC-6 (WI-3)** Delivery writes the file and answers `delivered`; a second answer is 409 `not-pending`; delivery for a revoked agent is 409 `agent-stopped` and writes no file; decline makes the wait answer `declined`.
- **AC-7 (WI-4)** `revokeAgentMcpTokens` deletes `<dir>/secrets/` for an agent and for a conversation with `dir`, and does not fail when it is missing.
- **AC-8 (WI-5)** A non-agent token does not list `request_secret` or `secret_wait`; an agent token with `read:state` lists `secret_wait` but not `request_secret`; `request_secret` posts exactly `{ name, prompt }`; the four pinned tool tests pass with the new names.
- **AC-9 (WI-6, issue AC-12)** In the integration test a requested secret reaches the agent as a 0600 file, and the canary appears zero times in every route answer, MCP tool result, activity entry and `console.*` call.
- **AC-10 (WI-7)** A secret row from `GET /api/agent-requests` becomes a blocking decision labelled "Secret requested" with the `agentRequest` field; a phone shows "Answer on the desktop" for it.
- **AC-11 (WI-8)** A root-session viewer sends the value from a password input and the input is empty afterwards; a non-root viewer sees "Answer this on <machine>'s own dashboard" and no input; the Decisions panel shows the card instead of an Answer button.
- **AC-12 (WI-9)** `configuration/mcp.mdx` lists `request_secret` and `secret_wait` and has a Secrets subsection naming the file location, mode and cleanup; `docs/DASHBOARD-AUTH.md` documents both self routes and the root-only answer routes.

## Out of scope

- Answering a secret request from a phone, a linked machine's browser, a bot or any token (D-4).
- The `machine-link` request kind, its routes, its card and the `machineLink` frontend kind (W-LINK1, PAN-4942).
- Injecting the MCP server or the instructions block into agents (W-INJ1 PAN-4932, W-INJ4).
- Persisting requests across a dashboard restart.
- Isolation between agents that run as the same Unix user: mode 0600 protects against other users and against accidental exposure (transcripts, logs), not against another process of the same user.
- A `pan` CLI verb for requesting or answering secrets.
- Encrypting secret files at rest or rotating them.
