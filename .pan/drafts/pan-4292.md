# PAN-4292 — Steer running Claude Code turns from the dashboard composer (Ctrl+Enter) and `pan tell --steer`

**Issue:** [PAN-4292](https://github.com/eltmon/overdeck/issues/4292) · **Sibling (Codex):** [PAN-4303](https://github.com/eltmon/overdeck/issues/4303) · **Planned:** 2026-09-28 (auto mode)

## Summary

The dashboard composer can steer a running turn only for Pi conversations. This PRD adds a **Steer** delivery for **Claude Code** conversations and agents, a **Ctrl+Enter** (Cmd+Enter on macOS) composer shortcut, and a `pan tell --steer` flag. Steer for Claude Code types the message and then presses Claude Code's own *send-now* chord, **Ctrl+X Ctrl+S**, instead of Enter. That chord interrupts the running turn and sends the message at once. Enter keeps today's behavior. Codex moved to sibling issue [PAN-4303](https://github.com/eltmon/overdeck/issues/4303) (see Decision D2).

## Glossary

- **Turn** — one model run from a submitted user message until the harness is idle again.
- **Busy** — a turn is running. The composer receives this as the `agentBusy` prop of `ComposerFooter`.
- **Queue (Enter while busy)** — Claude Code's `chat:submit` action. While busy, Claude Code holds the message and feeds it to the model at the next tool boundary of the running turn, or after the turn. This is today's behavior for every dashboard and `pan tell` delivery.
- **Steer (Claude Code)** — Claude Code's `chat:sendNow` action. It **interrupts the running turn** and sends the typed message (and any queued messages) immediately. The pane then shows `Interrupted · What should Claude do instead?` above the new user message, and an in-flight Bash tool call continues as a background shell. When Claude Code is idle, `chat:sendNow` is a plain submit.
- **Steer (Pi)** — the existing Pi control-channel command `type: 'steer'` (`src/lib/overdeck/conversation-delivery.ts`). Unchanged by this issue.
- **Send-now chord** — the key sequence **Ctrl+X Ctrl+S**, bytes `0x18 0x13`. Claude Code 2.1.280 binds both `ctrl+enter` and `ctrl+x ctrl+s` to `chat:sendNow`. `0x13` is the XOFF byte, but Claude Code puts its tty in raw mode (IXON off), so the byte reaches the application.
- **Submit mode** — the new delivery parameter `submit: 'enter' | 'steer'` that this PRD threads through the delivery door. `'enter'` (the default) is today's behavior. `'steer'` replaces the final Enter keystroke with the send-now chord.
- **Steer kind** — the new `HarnessBehavior.steerKind` field in `packages/contracts/src/harness-behavior.ts`: `'send-now-keys'` (Claude Code), `'control-channel'` (Pi), or `null` (no steer support).
- **Delivery door** — `deliverAgentMessage()` in `src/lib/agents/delivery.ts`, the single primitive every dashboard and CLI message goes through. Its tiers, in order: Herdr `agent.prompt`, Codex app-server socket, ACP/Prime host socket, PTY supervisor socket, Channels bridge, tmux paste.
- **PTY supervisor** — `src/lib/channels/pty-supervisor.ts`, the process that owns a supervised agent's PTY and injects messages over a Unix socket.
- **Herdr** — the default terminal backend (`src/lib/terminal-backends/herdr.ts`), JSON API over a socket. **tmux** — the alternative backend (`src/lib/terminal-backends/tmux.ts`, `src/lib/tmux.ts`).

## Verified mechanics (implementation checkpoint from the issue — done during planning)

All facts below were checked on 2026-09-28 against the installed binaries. Re-check only if the versions changed.

1. **Claude Code 2.1.280 keybindings** (from the binary's default keybinding table, context `Chat`):
   `enter:"chat:submit"`, `"ctrl+x enter":"chat:queueSubmit"`, `"ctrl+x ctrl+s":"chat:sendNow"`, `"ctrl+enter":"chat:sendNow"`, `"ctrl+j":"chat:newline"`. The changelog line reads: *"Added a send-now key (ctrl+enter, or ctrl+x ctrl+s) that interrupts the current turn and sends all queued messages at once"*. Claude Code's own hint logic hides `ctrl+enter` when `TMUX` or `STY` is set, because a multiplexer cannot carry it.
2. **tmux 3.4 byte probe** (throwaway socket `-L pan4292probe`, raw-mode byte logger): `send-keys C-x C-s` → `18 13`; `send-keys C-x Enter` → `18 0d`; `send-keys C-Enter` → **no bytes at all**. So Ctrl+Enter cannot be sent through tmux.
3. **Herdr 0.9.1 byte probe** (isolated session `herdr --session pan4292probe`): `pane send-keys ctrl+x ctrl+s` → `18 13`; `pane send-keys ctrl+enter` → `0d` (indistinguishable from Enter, so it would **submit**, not steer). `pane send-text` writes raw bytes with **no bracketed-paste wrapping**, even when the application enabled mode 2004 (`a\nb` arrived as `61 0a 62`).
4. **Live Claude Code probe on tmux** (haiku, throwaway socket): while a turn ran `sleep 25`, pasting text then `send-keys C-x C-s` produced `Interrupted · What should Claude do instead?`, then the pasted message as a new user turn, and the model answered it (`BANANA`). While idle, text + `C-x C-s` submitted normally (`IDLE-OK`).
5. **Decision from 1–4:** the only chord that works on both backends is **Ctrl+X Ctrl+S**. Never send `ctrl+enter` / `C-Enter`.
6. **Codex (for the sibling):** `codex app-server` 0.158 exposes `turn/steer {threadId, input, expectedTurnId}`. Overdeck already uses it for sub-agents (`sendSubagentMessage`, `src/lib/codex/app-server-manager.ts` ~line 289). The owner message path (`handleMessageOp`, `src/lib/codex/app-server-host.ts` ~line 268) always sends `turn/start`, and the 0.158 schema says `turn/start` may itself steer an already-active turn. That needs its own verification → [PAN-4303](https://github.com/eltmon/overdeck/issues/4303).

## Decisions (made here; the executor does not re-decide)

- **D1 — Steer for Claude Code means interrupt-and-send-now.** The issue says steer "the same way the TUI's Ctrl+Enter does"; Ctrl+Enter is `chat:sendNow`, which interrupts. The selector label stays **Steer**; its tooltip says: *"Steer: interrupt the current turn and send now (Claude Code Ctrl+Enter). Auto queues the message for the running turn."*
- **D2 — Codex is a sibling issue ([PAN-4303](https://github.com/eltmon/overdeck/issues/4303)).** Codex uses a different transport and may already steer on `turn/start`. In this issue Codex has `steerKind: null`: no selector option, and `pan tell --steer` to a Codex target is refused.
- **D3 — The chord is Ctrl+X Ctrl+S on every backend**: tmux keys `C-x C-s`, Herdr keys `ctrl+x ctrl+s`, PTY bytes `\x18\x13`. One module holds the three spellings.
- **D4 — Capability lives in one place:** `HarnessBehavior.steerKind`. Claude Code = `'send-now-keys'`, `ohmypi` and `pi` = `'control-channel'`, every other harness = `null`. Frontend and server both read it through `getHarnessBehavior(harness).steerKind`.
- **D5 — Ctrl+Enter (or Cmd+Enter on macOS) always sends with `deliverAs: 'steer'` on a steer-capable harness**, busy or idle. Idle steer is a plain submit (verified), so this is safe and does not depend on a possibly-stale `agentBusy`. On a harness with `steerKind: null`, Ctrl+Enter behaves exactly like Enter.
- **D6 — Claude Code selector offers Auto and Steer only.** `ctrl+x enter` (`chat:queueSubmit`) was not verified, so no Follow-up option for Claude Code. Pi keeps Auto / Steer / Follow-up unchanged.
- **D7 — The selector choice persists per composer mount** (same `useState` as today). Choosing Steer makes Enter send as steer too. Ctrl+Enter always steers regardless of the selector.
- **D8 — Steer never degrades silently.** Tiers that cannot carry a steer (Codex app-server, ACP/Prime host, Channels bridge) return `{ ok: false, failure: 'steer-unsupported: <tier>' }` instead of delivering as a normal submit. A keyed delivery (`dedupKey`) with `submit: 'steer'` throws `MessageDeliveryFailed` (no caller combines them today).
- **D9 — An old PTY supervisor answers a steer honestly.** Supervisors launched before this change ignore `submit` and press Enter. The new supervisor answers a steer with JSON `{"ok":true,"submit":"steer"}`. When the client sent `submit: 'steer'` and the response body is not that JSON, `deliverAgentMessage` returns `{ ok: true, path: 'supervisor', steered: false, failure: 'supervisor predates steer; delivered as a normal submit' }`. The conversation route and `pan tell` show that text to the operator.
- **D10 — Herdr steer bypasses `agent.prompt`** (which always ends with Enter). It reads `agent.get`; refuses with `{ refused: true, reason: 'agent_blocked' }` when `agent_status === 'blocked'` (same rule as `agent.prompt`); otherwise it calls `pane.send_text` with the text wrapped in bracketed-paste markers `\x1b[200~…\x1b[201~`, waits `STEER_SETTLE_MS` (300 ms), then `pane.send_keys ['ctrl+x','ctrl+s']`. The prompt guard (`checkPrompt`) runs before either path, unchanged.
- **D11 — `pan tell --steer` scope:** supported for local targets whose harness has `steerKind === 'send-now-keys'`. Refused with exit 1 and nothing delivered or mailed for: remote (Fly) targets, any other harness (message names the harness and says steer is supported for Claude Code only), and paused/suspended/stopped agents (a steer to a non-running agent has nothing to interrupt; the refusal says to drop `--steer`).
- **D12 — `messageAgent` with `steer: true` skips `waitForAgentIdle(normalizedId, 5000)`**, still runs `ensureMainInputTarget` (PAN-4268), and passes `submit: 'steer'` to `deliverMessageWithTranscriptConfirmation`.
- **D13 — The conversation route accepts `deliverAs: 'steer'` for Claude Code only.** For a harness with `steerKind: null` it answers **422** `{ code: 'steer-unsupported', error: '<Harness> has no steer delivery' }` and delivers nothing. `deliverAs: 'follow_up'` on a Claude Code conversation is also 422 `steer-unsupported` (D6). Pi routing is unchanged.
- **D14 — The dashboard agent route** (`POST /api/agents/:id/message`) accepts `deliverAs: 'steer'` and calls `messageAgent(id, message, 'dashboard:user-message', { steer: true })`. `composerSend.ts` stops dropping `deliverAs` for agents.
