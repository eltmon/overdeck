# PAN-4660 — Duplicate-and-edit color theme editor in Settings > Appearance

**Issue:** https://github.com/eltmon/overdeck/issues/4660
**Split from:** #4644 (merged as `3a84c9758af`, PR #4689). PRD of the parent: `.pan/drafts/PAN-4644.md`.
**Status:** planning draft, 2026-11-02, auto mode (`pan plan --auto`, high effort)

## Glossary

- **Color theme** — a named set of colors with a `type` (`light` | `dark`) and three optional groups: `terminal`, `syntax`, `ui`. Defined in `packages/contracts/src/color-theme.ts` (`ColorThemeFile`, line 79; `ColorTheme`, line 89).
- **Built-in theme** — `overdeck-dark` or `overdeck-light` (`BUILTIN_COLOR_THEMES`, `packages/contracts/src/color-theme.ts:116`). It lives in code, carries a full 21-key `terminal` palette and no `ui` or `syntax` group. It is read-only.
- **User theme** — a theme stored as `~/.overdeck/themes/<id>.json`. The file name is the id; the id is not stored inside the file.
- **Reserved id** — an id in `RESERVED_COLOR_THEME_IDS` (`["overdeck-dark", "overdeck-light"]`, `color-theme.ts:107`). No user file may take a reserved id.
- **Selection / active theme** — the theme chosen for each mode (`ui.color_theme.light|dark` in `config.yaml`); the active theme is the selection for the current light/dark mode. Held in the `useColorTheme` zustand store (`src/dashboard/frontend/src/hooks/useColorTheme.ts`).
- **Effective terminal palette** — `effectiveTerminalPalette(theme)` (`color-theme.ts:195`): the built-in palette for the theme's type overlaid with the theme's own `terminal` colors.
- **Source theme** — the theme the operator clicked "Duplicate and edit" or "Edit" on.
- **Editor mode** — `duplicate` (save creates a new file through `POST /api/color-themes`) or `edit` (save overwrites the source user theme's file in place through the new `PUT /api/color-themes/:id`).
- **Draft** — the editor's in-memory state: the source theme, the name being typed, and the per-key **edits** the operator has made. Nothing in a draft reaches the server until Save.
- **Edit** (per key) — a color the operator picked for one key in this editor session. Removing an edit ("Revert") restores the source theme's value for that key (or "not set").
- **Set / not set** — a `ui` key or syntax scope is *set* when the saved theme will carry a value for it. A *not set* `ui` key inherits the design language's default token; a *not set* syntax scope keeps whatever the theme's other token rules (or the `github-light` fallback) give it.
- **Common syntax scopes** — the seven fixed scopes this editor edits: comment, string, keyword, function, variable, number, type. The exact TextMate scope string for each is fixed in the table under Decisions (D4).
- **Preview** — three samples inside the editor (terminal, UI card, highlighted code) rendered from the draft. The preview never touches `<html>`, `localStorage`, or the server.
- **`uiTokenStyles(theme)`** — new pure function: the CSS custom-property map that `applyUiTokens` writes for a theme. Extracted so the UI preview can apply the same map to a wrapper `<div>` instead of `<html>`.
- **Strict fetch mock** — `installStrictFetchMock` (`src/dashboard/frontend/src/test-utils/strictFetchMock.ts`): a test fetch mock that fails the test on any request its handler does not answer.

## Problem

PAN-4644 shipped the theme model, the `~/.overdeck/themes/` store, VS Code import, the light/dark pickers, and terminal, chat-syntax, and UI-token theming. The only way to change a theme's colors today is to hand-edit its JSON file. `configuration/appearance.mdx:97` says so explicitly: "a duplicate-and-edit color-picker editor … is tracked separately too (#4660) — until then, edit the JSON file by hand."

Two gaps block an in-dashboard editor:

1. **No in-place save.** `saveColorTheme` (`src/lib/color-themes/store.ts:127`) always goes through `claimThemeFile` (`store.ts:93`), which uses `link()` with create-only semantics and adds a `-2`, `-3`, … suffix when the id exists. Posting an edited `ayu-dark` today creates `ayu-dark-2.json`; there is no way to overwrite a user theme.
2. **No reusable token derivation.** `applyUiTokens` (`useColorTheme.ts:61`) computes the CSS custom properties and writes them straight onto `document.documentElement`. A live preview needs the same values on a sample element without repainting the whole dashboard.

## Scope

In scope:

- A store function and route that overwrite an existing user theme in place, refusing built-ins.
- A pure editor model (draft, duplicate naming, syntax scope editing, seeds).
- An inline editor panel in Settings > Appearance with color pickers for `terminal`, `ui`, and the seven common syntax scopes, plus a live preview.
- Entry points: a theme list under the pickers, with "Duplicate and edit" on every theme and "Edit" on user themes.
- Re-applying a selected theme after an in-place save, without a reload.
- Docs: `configuration/appearance.mdx`, `docs/DASHBOARD-ARCHITECTURE.md`.

## Non-goals

- Editing signal and state colors (`--state-*`, `--success*`, `--warning*`, `--destructive*`, `--info*`, `--signal-*`). The editor exposes only the seven `ui` keys in the contract.
- Editing arbitrary `tokenColors` rules, font styles, token backgrounds, or `syntax.colors` (`editor.background`/`editor.foreground`). Only the foreground of the seven common scopes is editable; every other rule carries over unchanged.
- Editing `terminal.cursorAccent` (it carries over unchanged).
- Editing alpha channels. The native color input is `#rrggbb` only.
- Changing a theme's `type` (light/dark). A copy keeps the source's type.
- Deleting or renaming theme files. (A name change in edit mode changes the display name only; the id/file name stays.)
- Auto-selecting a newly saved duplicate. It appears in the matching picker; the operator selects it.
- Restamping the tmux `window-style` background of existing sessions after an edit. Only new sessions read the background (`src/lib/color-themes/terminal-background.ts`), as today.
- Persisting an unsaved draft across a page reload.
- A routed editor page (see D2).
- `.vsix` import (#4659).
- Any change to `packages/contracts/src/color-theme.ts`.

## Planning Q&A (auto mode — defaults chosen, no operator questions)

1. **How does "Edit" on a user theme save in place, given `POST /api/color-themes` never overwrites?** Options: (a) add an optional `id` to the POST body that switches POST into overwrite mode; (b) a new `PUT /api/color-themes/:id` route backed by a new `updateColorTheme` store function. **Chose (b).** Create and overwrite are different operations with different failure modes (404, 403); mixing them in one route makes the POST contract conditional. The issue's "through `POST /api/color-themes`" sentence is about saving a *new* theme, which still uses POST.
2. **Editor surface: routed page, modal, or inline panel?** `configuration/appearance.mdx` ("Creation flows are pages, not modals") caps *modals* at four fields. **Chose an inline panel** inside the Appearance section, the same pattern as `ColorThemeImportPreview` (an inline panel below the pickers). It is not a modal, needs no change to the app's tab routing (`src/dashboard/frontend/src/App/routes.ts`, `Header.tsx` `Tab` union, `AppRoutes.tsx`), and the issue says the editor opens "in Settings > Appearance". Trade-off: an unsaved draft is lost on reload (listed as a non-goal).
3. **Which UI keys?** The issue lists six; the contract now has seven (`overlay` was added by PAN-4755, `color-theme.ts:43-44`). **Chose all seven** keys in `UI_KEYS`, because the editor must cover the contract, and `applyUiTokens` already honors `overlay`.
4. **Where is "Duplicate and edit"?** "On any theme" — the pickers show only the selected theme. **Chose a theme list** under the pickers listing every theme, each row with "Duplicate and edit"; user-theme rows also get "Edit". Duplicating a non-selected theme must not require selecting it first.
5. **How are not-set `ui` keys and syntax scopes shown?** Built-ins have no `ui`/`syntax` group. **Chose:** a not-set row shows a seed color in the picker and the label "Not set"; nothing is written for it unless the operator changes it. Seeds come from the effective terminal palette (table in D5) so they are deterministic and testable.
6. **What does Save do after a duplicate?** **Chose:** close the editor, toast success, refresh the theme list (`reconcileFromServer`). No auto-select.
7. **Duplicate name collisions?** **Chose:** `"<name> copy"`, then `"<name> copy 2"`, `"<name> copy 3"`, … — the first name not already used by any theme (case-insensitive, trimmed), capped at 80 characters by truncating the source name. The id is still assigned by the server (`slugifyThemeId` + the store's `-2` suffixing).
8. **`source` provenance on a copy?** **Chose:** a duplicate drops `source` (it is no longer the imported file); an in-place edit keeps the file's existing `source`.
9. **Terminal group on save?** **Chose:** `{ ...source.terminal, ...edits.terminal }`. Built-ins carry a full palette, so a copy of a built-in gets all 21 keys; a user theme keeps exactly the keys it had plus the edited ones.
10. **Can a user theme have the id `selection`?** `PUT /api/color-themes/selection` is the existing selection route; find-my-way (the router under Effect's `HttpRouter`, `node_modules/effect/dist/unstable/http/FindMyWay.js`) matches static segments before `:id`, so a theme with id `selection` could never be edited. **Chose:** `claimThemeFile` treats `selection` as taken (a theme named "Selection" saves as `selection-2`). A hand-written `selection.json` still lists and selects; only the editor's in-place save cannot reach it (hazard, not fixed).

## Requirements

- **FR-1** "Duplicate and edit" is available on every theme (built-in and user) in Settings > Appearance and opens the editor seeded with that theme's colors.
- **FR-2** "Edit" is available only on user themes. Built-in themes are read-only in the UI and on the server.
- **FR-3** The editor has color pickers for `terminal` (background, foreground, cursor, selectionBackground, and the 16 ANSI colors — 20 keys), `ui` (the seven contract keys), and `syntax` (foreground of the seven common scopes).
- **FR-4** Changing a color updates the editor's preview immediately (syntax sample within 150 ms) and sends no request to the server.
- **FR-5** A duplicate gets the name `"<name> copy"` (deduplicated per D7) and a new id; saving it writes a new file in `~/.overdeck/themes/` through `POST /api/color-themes`. The source theme is never modified.
- **FR-6** Saving an edited user theme overwrites `~/.overdeck/themes/<id>.json` in place through `PUT /api/color-themes/:id`; the id does not change.
- **FR-7** `PUT /api/color-themes/:id` returns 403 for a built-in/reserved id, 404 for an id with no file, 400 for an invalid id or an invalid theme body, and 200 `{ theme }` on success. It never creates a file.
- **FR-8** A saved theme appears in the picker matching its `type` without a reload, and survives a dashboard restart (it is read from disk on every `GET /api/color-themes`).
- **FR-9** Saving an edited user theme that is currently selected re-applies its terminal, syntax, and UI colors without a page reload.
- **FR-10** Syntax edits change only the foreground of the edited common scope; every other `tokenColors` rule carries over unchanged and in order. A theme with no `syntax` group and no syntax edits saves with no `syntax` group (keeping the `github-light` fallback).
- **NFR-1** `PUT /api/color-themes/:id` calls `rejectUnsafeDashboardMutationRequest` before reading the body, and validates the id against `COLOR_THEME_ID_RE` before touching the file system (no path traversal).
- **NFR-2** The in-place write is atomic: write a temp file in the themes directory, then `rename()` over the target. A reader never sees a half-written file.
- **NFR-3** The preview never writes to `document.documentElement`, `localStorage`, or the network.
- **NFR-4** No new synchronous file or process calls in server-reachable code (`no-execsync-server` rule). The store uses `fs/promises` only.
- **NFR-5** Every new frontend test file is listed in `scripts/frontend-test-subset.txt` (sorted position), or CI never runs it.
- **NFR-6** Tests that exercise the 150 ms syntax-preview debounce use `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()` (`fake-timers-for-retry-tests` rule); no real-time waits.

## Decisions

**D1 — Overwrite route.** `PUT /api/color-themes/:id`, body `{ theme }`. Status mapping is fixed: `builtin` → 403 `{ error: "built-in themes are read-only; duplicate it instead" }`; `not-found` → 404 `{ error: 'no user theme with id "<id>"' }`; `invalid-id` → 400 `{ error: "invalid theme id" }`; `invalid` → 400 `{ errors }`; `saved` → 200 `{ theme }`. Check order: auth, then id (built-in/reserved first, then regex), then body.

**D2 — Inline editor panel** (see Q&A 2). One editor open at a time; opening another replaces it after the current one closes (the list buttons are disabled while an editor is open).

**D3 — Draft model.** The draft never mutates the source theme. `draftToFile(draft)` is the only function that turns a draft into a saved shape:

```ts
{
  name: draft.name.trim(),
  type: source.type,
  terminal: { ...source.terminal, ...edits.terminal },          // omitted when empty
  ui: { ...source.ui, ...edits.ui },                            // omitted when empty
  syntax: applySyntaxEdits(source.syntax, edits.syntax),        // omitted when undefined
  source: mode === 'edit' ? source.source : undefined,          // omitted when undefined
}
```

**D4 — Common syntax scopes (fixed table).**

| key | Label | Scope string | Seed (effective terminal palette key) |
| --- | --- | --- | --- |
| `comment` | Comment | `comment` | `brightBlack` |
| `string` | String | `string` | `green` |
| `keyword` | Keyword | `keyword` | `magenta` |
| `function` | Function | `entity.name.function` | `blue` |
| `variable` | Variable | `variable` | `foreground` |
| `number` | Number | `constant.numeric` | `yellow` |
| `type` | Type | `entity.name.type` | `cyan` |

*Reading* a scope's current color (`syntaxForeground(syntax, scope)`): scan `tokenColors` from last to first; an entry matches when its scope list contains the scope string exactly (a string scope is split on `,` and trimmed; an array scope is used as is) and it has `settings.foreground`. The first match from the end wins. No match ⇒ not set.

*Writing* an edit (`applySyntaxEdits(syntax, edits)`): with no edits, return `syntax` unchanged (same reference, possibly `undefined`). Otherwise copy `tokenColors` (or `[]`), and for each edited key in table order: find the **last** entry whose `scope` is exactly the scope string, or an array of exactly one element equal to it. If found, replace it with `{ ...entry, settings: { ...entry.settings, foreground: color } }`; otherwise append `{ scope, settings: { foreground: color } }`. All other entries are kept by reference and in order. `syntax.colors` carries over unchanged.

Known limit (documented, not fixed): an appended `comment` rule does not override a more specific existing rule such as `comment.line`, because TextMate theme matching prefers the more specific scope. The preview shows exactly what Shiki renders, so the operator sees this.

**D5 — Seeds for not-set `ui` keys.** From the draft's effective terminal palette: `background`, `surface`, `overlay` ← `background`; `foreground` ← `foreground`; `border`, `muted` ← `brightBlack`; `accent` ← `blue`. A seed is only shown; it is never saved unless the operator changes the picker.

**D6 — Color input values.** `<input type="color">` accepts only `#rrggbb`. Every picker shows `toOpaqueHex(value)` (`color-theme.ts:152`); a change writes the input's 6-digit value as an edit. Untouched keys keep their original string (including 3/4/8-digit forms and alpha).

**D7 — Duplicate naming** (`duplicateThemeName(sourceName, existingNames)`): suffixes `" copy"`, `" copy 2"`, `" copy 3"`, …; return the first `<truncated name><suffix>` that does not equal any existing name (comparison: trimmed, lowercased). Truncate the source name so the result is at most 80 characters (the contract's name cap, `color-theme.ts:318`).

**D8 — Re-apply after in-place save.** `updateTheme` ends with `await get().reconcileFromServer()`. That refetch replaces the active theme objects, which (a) re-runs `applyUiTokens` for the current mode, (b) misses the `terminalPaletteCache` WeakMap so `XTerminal` gets a new palette and re-themes (`XTerminal.tsx:881-883`), and (c) changes `syntaxThemeName` (content-hashed, `syntaxTheme.ts:248-251`) so chat code blocks re-highlight. No new mechanism is needed; a test proves it.

**D9 — Syntax preview debounce.** Registering a Shiki theme per content hash on every picker drag is wasteful, so the code sample re-highlights 150 ms after the last change. Terminal and UI samples update synchronously.

**D10 — `selection` id.** `claimThemeFile` skips the candidate `selection` as if it were reserved (Q&A 10). This is a store-local constant (`ROUTE_SHADOWED_IDS = ['selection']`), not a contract change.

   ```ts
   export type UpdateColorThemeResult =
     | { kind: 'saved'; theme: ColorTheme; warnings: string[] }
     | { kind: 'builtin' }
     | { kind: 'invalid-id' }
     | { kind: 'not-found' }
     | { kind: 'invalid'; errors: string[] };

   /**
    * Overwrites an existing user theme file in place (PAN-4660). Never creates
    * a file and never touches a built-in/reserved id. Atomic: temp + rename.
    */
   export async function updateColorTheme(id: string, file: unknown): Promise<UpdateColorThemeResult> {
     if (Object.hasOwn(BUILTIN_COLOR_THEMES, id) || RESERVED_COLOR_THEME_IDS.includes(id)) return { kind: 'builtin' };
     if (!COLOR_THEME_ID_RE.test(id)) return { kind: 'invalid-id' };
     try {
       await access(themeFilePath(id));
     } catch (err) {
       if ((err as NodeJS.ErrnoException).code === 'ENOENT') return { kind: 'not-found' };
       throw err;
     }
     const result = normalizeColorTheme(file, id);
     if ('errors' in result) return { kind: 'invalid', errors: result.errors };
     const { id: _id, builtin: _builtin, ...fileContents } = result.theme;
     const tempPath = join(getColorThemesDir(), `.tmp-${process.pid}-${randomBytes(4).toString('hex')}`);
     await writeFile(tempPath, `${JSON.stringify(fileContents, null, 2)}\n`, { mode: 0o644 });
     try {
       await rename(tempPath, themeFilePath(id));
     } catch (err) {
       await rm(tempPath, { force: true });
       throw err;
     }
     return { kind: 'saved', theme: result.theme, warnings: result.warnings };
   }
   ```

```ts
  const data = await res.json().catch(() => null) as { error?: string; errors?: string[] } | null;
  if (!res.ok) throw new Error(data?.error ?? data?.errors?.join('; ') ?? `Failed to save theme (HTTP ${res.status})`);
  await get().reconcileFromServer();
},
```

## Risks and hazards

- **Shiki theme registrations grow per edit.** Each distinct syntax draft registers a new content-hashed theme in the shared highlighter (`registerCustomTheme`). The 150 ms debounce bounds this to one registration per pause. Accept; do not add an unregister path.
- **Not-set UI keys preview the current mode's defaults.** Editing a light theme while the dashboard is dark previews unset UI keys with dark defaults. The preview states this in one muted line.
- **`color-themes-routes.test.ts` fixes `OVERDECK_HOME` at import time.** New tests must use the existing file-level `home` and the `beforeEach` that clears it; do not set `OVERDECK_HOME` per test.
- **`scripts/frontend-test-subset.txt` is shared** by W3, W5, W6, W7. Each item adds its own line in sorted position; re-read the file before editing.
- **`selection.json` written by hand** cannot be edited in place (static route wins). Documented in D10; not fixed.
