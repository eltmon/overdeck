## Glossary

- **Home** — the operator's machine: the dashboard that holds the link to the VM.
- **Fly machine** — a Fly VM started by `addFlyMachine()` (`src/dashboard/server/services/fly-machine-service.ts`) that runs `pan serve` and is linked one way from home (PAN-4652). Its record lives in `${OVERDECK_HOME}/fly-machines.json` (`FlyMachineRecord`, `src/lib/anywhere/fly/machine-store.ts:32-50`).
- **Legacy remote work agent** — today's `pan start --remote` agent: a VM made by `createRemoteWorkspace()` (`src/lib/remote-workspace.ts:106`) that runs Claude Code in a raw tmux session named `agent-<issue>` (`spawnRemoteAgentWithoutConsentClaim`, `src/lib/remote/remote-agents.ts:578-704`) and no Overdeck server. Its transcript is invisible at home until the reap.
- **Linked work agent** (new) — what this issue builds: a work agent that runs as a **conversation** on a Fly machine's own server, started through the link (`POST /api/conversations`). Home sees it as a linked conversation (`/conv/@<environmentId>/<name>`).
- **remote-state** — `~/.overdeck/agents/agent-<issue>/remote-state.json` (`RemoteAgentState`, `remote-agents.ts:286-297`). The reap, `pan tell`, `pan kill`, output capture and the loops all read it.
- **Linked conversation cache** — home's `linked_conversations` table (`src/lib/overdeck/linked-conversations.ts`), filled from each linked machine's shared list (`GET /api/machines/conversations`). The shared list is built from `listConversations()` (`src/lib/overdeck/conversations.ts:553-571`), which drops names `LIKE 'agent-%'`.
- **The reap** — `reapCompletedRemoteAgents()` (`src/lib/remote/remote-completion.ts`), run every 60 s by the deacon child (`deacon-lite.ts:562`, behind the deacon freeze) and by `pan admin remote reap`. It hands a finished agent to review when `/workspace/.pan/REMOTE_DONE` exists and the branch is on origin.
- **The sweep** — `sweepFlyMachines()` (`src/lib/remote/fly-machine-loops.ts:157`), run every 60 s by the hygiene scheduler (not behind the freeze). It destroys a Fly machine that is gone, never linked, or has had no active linked conversation for `remote.fly.machine_idle_minutes` (default 30).
- **Work door route** (new) — `POST /api/remote/work-agents`, the dashboard route that starts a linked work agent.
- **VM worktree** — `/workspace/<projectKey>/workspaces/feature-<issue-lower>` on the Fly machine. `pan task` on the VM resolves the plan there (`resolveTaskContext`, `src/cli/commands/task.ts:59-67`: `join(resolved.projectPath, 'workspaces', \`feature-${issueId.toLowerCase()}\`)`).

## Problem

A `pan start <id> --remote` agent is invisible at home while it works. It runs in raw tmux over the Fly Machines exec API, so home has no transcript, no conversation row and no session row in the issue tree (only the `fly.io` chip from `resource-discovery.ts:575-589`). `collectSessionTreeNodes` (`src/dashboard/server/routes/projects.ts:239-242`) shows a row only when `state.json` exists, and the CLI path writes only `remote-state.json`. PAN-1775 asked for a session row; D-12 says the fix is to make the agent a linked conversation.

PAN-4652 made a Fly VM an ordinary linked machine. Its conversations stream live at home with a `fly-<id>` chip. But nothing starts a *work agent* there:

1. `pan start --remote` still calls `createRemoteWorkspace` and `spawnRemoteAgent` in the CLI process (`src/cli/commands/start.ts:316-517`, `handleRemoteWorkspace`).
2. `addFlyMachine` needs the link supervisor, which lives in the dashboard (`notifyLinksChanged` is a required argument, `fly-machine-service.ts:217-220`). So the CLI cannot do it in-process.
3. A work agent spawned by the owner's issue-start door would be named `agent-<issue>`. The shared list drops `agent-%`, so home's cache never has a row, and the sweep destroys the VM after 30 minutes under the running agent (planning comment on this issue, PAN-4743 D-4743-1).
4. Every remote helper addresses the tmux session by the agent id: `getRemoteAgentOutput` (`remote-agents.ts:709-723`, `capture-pane -t agentId`), `sendToRemoteAgent` (`:728-767`), `sendToRemoteAgentKeyed` (`remote-keyed-delivery.ts`), `killRemoteAgent` (`:784-802`), `remoteSessionExists` and the reap's `probeRemoteSession` (`remote-completion.ts:67-76`). A conversation's tmux session is `conv-<name>` (`conversation-runtime.ts`: `const tmuxSession = \`conv-${name}\`;`).
5. The loops would double-handle a VM that is both a remote agent and a Fly machine: `checkRemoteSpendCap` counts `listActiveRemoteAgentStates().length + countFlyMachines()` (`remote-agents.ts:414-441`), both heartbeats write it, and the credential refresh unions both name lists (`remote-credential-refresh.ts`, `const targets = [...activeStates.map(...), ...flyMachineNames.map(...)]`).

## Goals

- `pan start <id> --remote` (and `pan start <id> --machine fly`) starts the work agent as a conversation on a new Fly machine. Its transcript is live in the home dashboard while it works, with the `fly-<machineId>` chip.
- The issue tree shows the agent as a row under its issue that opens `/conv/@<environmentId>/<name>`.
- The automatic reap still hands the finished branch to review, and then destroys the Fly machine, its link and its record.
- `pan tell`, `pan kill`, the dashboard output view, `messageAgent` and the push daemon keep working against the new session.

## Non-goals

- Durable tier (`--tier durable`, `remote.resiliency_tier: durable`). Fly machines are ephemeral only (PAN-4652 non-goal). `pan start --remote` refuses the durable tier with a sentence; it never falls back to the legacy VM.
- Codex (or any harness other than Claude Code) as a Fly *work agent*. The REMOTE prompt contract is Claude Code's. Conversations keep their PAN-4296 Codex support.
- `pan start --machine auto` creating a Fly VM under `remote.auto_fly`. That setting does not exist on `main` (it is PAN-4743's, unmerged). Follow-up once PAN-4743 merges.
- `pan worker run --machine fly` and `pan lane start --machine fly` (PAN-4743 and PAN-4811 own them).
- Deleting the legacy raw-tmux spawn code (`createRemoteWorkspace`, `spawnRemoteAgent`, `handleRemoteAgentSpawn`, `/api/remote/workspaces/*`, `pan workspace create --remote`). They stay for legacy VMs that exist during rollout; the reap, tell and kill keep serving legacy remote-state files unchanged. Retiring them is a follow-up.
- **Pull here** for a linked work agent. Pulling it home releases it on the VM, and the reap will not hand it to review (see Hazards).
- The VM running its own review, test or merge. The VM only hosts the work conversation; review runs at home after the reap.
- A `SessionNode` contract change or opening a linked conversation in `SessionPanel`. The tree row is a conversation row (D-9).
- Docker Compose stacks on the VM for the agent (the legacy path's step 7 never ran: the old image had no Docker).
- Starting a linked work agent from the dashboard Start button with a Machine field. The dashboard's existing remote path (`spawn-issue.ts:818-829`) shells out to `pan start --remote`, which now uses the new path; no UI is added.

## Requirements

### Functional

- **FR-1** `pan start <id> --remote` never creates a VM in the CLI process. It POSTs `POST /api/remote/work-agents` to the running dashboard with no client timeout (`postWithoutTimeout`, `src/cli/commands/machines-fly.ts:45`) and prints the conversation URL. With no dashboard it exits 1 with the `NOT_RUNNING`/`NEEDS_PAN_UP` sentence from `machines-call.ts`.
- **FR-2** `pan start <id> --machine fly` (any case) behaves exactly as `pan start <id> --remote`.
- **FR-3** Before calling the dashboard, `pan start --remote` refuses, creating nothing:
  - a durable tier (`--tier durable`, or no `--tier` and `remote.resiliency_tier === 'durable'`) — `durable-unsupported`;
  - an issue with legacy remote workspace metadata (`findRemoteWorkspaceMetadata(id)` non-null) — `legacy-remote-workspace`, naming the VM;
  - a feature branch that is not on origin after the push step — `branch-not-pushed`.
- **FR-4** The work door route refuses, before any VM exists: a channel caller (403); `remote.enabled !== true` or no Fly token (the `addFlyMachine` early refusals); an unknown project for the issue prefix (404 `project-unknown`); a model whose provider is not `anthropic` (400 `harness-unsupported`); an agent whose remote-state status is `running`, or `starting` with `startedAt` less than 30 minutes ago (409 `already-running`). A `starting` state 30 minutes old or older is crashed provisioning and is overwritten.
- **FR-5** The work door provisions with `addFlyMachine({ projectKey, harness: 'claude-code' })`, creates the VM worktree with `git worktree add` in `/workspace/<projectKey>` on the VM (D-3), copies home's `<local workspace>/.overdeck/continue.json` to `<VM worktree>/.overdeck/continue.json` when it exists, copies skills (`FlyProvider.copySkillsToVm`), and starts the conversation through the link with `{ message, projectKey, cwd: <VM worktree>, issueId, harness: 'claude-code', model, effort }`.
- **FR-6** The conversation's first message is the rendered work prompt (`buildWorkAgentPrompt({ issueId, env: 'REMOTE', workspacePath: <VM worktree>, skipDynamicContext: true })`) when it is at most 50,000 characters. Otherwise the prompt is written to `/workspace/.pan/prompts/agent-<issue-lower>.md` and the message is `Read /workspace/.pan/prompts/agent-<issue-lower>.md and follow it exactly. It is your work-agent prompt for <ISSUE>.`
- **FR-7** remote-state for a linked work agent carries `linked: true`, `environmentId`, `linkId`, `flyMachineId`, `conversationName`, `tmuxSession: 'conv-<name>'`, `tmuxSocket: 'overdeck'`, `projectKey` and `workdir` (the VM worktree), with `vmName` equal to the Fly machine name (`overdeck-machine-<8 hex>`). It is written with `status: 'starting'` and `vmName: ''` before `addFlyMachine` runs, and reaches `running` only after the conversation and the push daemon started.
- **FR-8** `getRemoteAgentOutput`, `sendToRemoteAgent`, `sendToRemoteAgentKeyed`, `killRemoteAgent`, `remoteSessionExists`/`isRemoteAgentRunning` and the reap's probes address tmux session `state.tmuxSession ?? agentId` on socket `state.tmuxSocket ?? getManagedTmuxSocketName()`. For a legacy remote-state the commands are byte-for-byte unchanged.
- **FR-9** The push daemon of a linked work agent runs in its `workdir`; the legacy daemon still runs in `/workspace`.
- **FR-10** A linked remote-state is skipped by `checkRemoteSpendCap`'s agent count, by `refreshHostHeartbeatForEphemeralVms` and by `refreshClaudeCredentialsForActiveRemoteAgents`'s agent targets, because its Fly machine record already covers it. No second watchdog is installed (provisioning installed one).
- **FR-11** The sweep never idle-removes a Fly machine whose `environmentId` belongs to a linked remote-state with status `starting` or `running`. Removal of a gone machine (404, `stopped`, `destroyed`, `failed`) and of a never-linked record is unchanged.
- **FR-12** The reap hands a linked work agent to review exactly as today (sentinel present and branch on origin), copies `<workdir>/.overdeck/continue.json` back to `<local workspace>/.overdeck/continue.json`, kills its session, then destroys its Fly machine, removes its link and deletes its Fly record. It does not call `fly.deleteVm` or `deleteWorkspaceMetadata` for a linked agent.
- **FR-13** Any failure after the work door created the Fly machine destroys the machine, removes its link, deletes its record (through the PAN-4652 unlink hook) and saves remote-state with `status: 'error'`.
- **FR-14** Home's issue tree lists every cached linked conversation with an `issueId` and `releasedTo === null` as a conversation row under that issue, and the row's link is `/conv/@<environmentId>/<name>`.
- **FR-15** The REMOTE block of the work prompt names `{{WORKSPACE_PATH}}` for the workspace, continue file, spec and draft paths. The `REMOTE_DONE` sentinel stays `/workspace/.pan/REMOTE_DONE`.

## Decisions (made here)

- **D-1 The CLI calls the dashboard.** `addFlyMachine` needs `notifyLinksChanged` from `src/dashboard/server/routes/machines.ts`, and `linkFetch` uses the dashboard's link pool. So the whole start runs in one dashboard request, like `POST /api/machines/fly` (PAN-4652 D-13). It takes 5–15 minutes (provision, clone, worktree). The CLI waits with `postWithoutTimeout`. The dashboard's own remote path (`spawn-issue.ts:818-829`) already shells out to `pan start --remote`, so it follows automatically.
- **D-2 A conversation, not the owner's issue-start door.** The owner's door (`handleWorkIssueStart`, `routes/machines-work.ts:216-239`) spawns `agent-<issue>` and would run `pan done`, review and merge on the VM. The issue asks for `POST /api/conversations`; the server names it `YYYYMMDD-NNNN` (`generateConversationName`, `conversation-runtime.ts:281-284`). That name passes the shared list's `NOT LIKE 'agent-%'` filter, so no filter change is needed and the conversation is not an Overdeck work agent on the VM.
- **D-3 A git worktree on the VM, not `pan workspace create`.** `pan task` on the VM looks for `<project>/workspaces/feature-<issue>` and reads the spec from it (glossary; `readWorkspacePlanSync(workspacePath)`). `pan workspace create` cannot be used there: `createWorkspace` refuses below a 10 GiB free-disk floor with no bypass (`src/lib/workspace-manager/create.ts:202-207`, `DISK_SAFETY_FLOOR_BYTES = 10 * GIB` in `src/lib/disk-floor.ts:5`), a Fly machine's rootfs is not guaranteed to have 10 GiB free, and it would also install every dependency on a 2 GB VM. So the VM runs `git worktree add -b feature/<id> workspaces/feature-<id> origin/feature/<id>` in `/workspace/<projectKey>` after fetching the branch. The agent installs dependencies itself when it needs them. The conversation's `cwd` is that worktree; `resolveConversationCreateTarget` accepts a `cwd` inside the project (`conversation-create-input.ts:88-96`).
- **D-4 The feature branch is pushed by the CLI.** The CLI already holds the local worktree. It reuses the PAN-4683 push (`pushFeatureBranch`, `src/lib/overdeck/feature-branch-push.ts:26`, called the way `remote-workspace.ts:170-176` calls it), then confirms `git ls-remote --heads origin feature/<issue-lower>` is non-empty.
- **D-5 Session identity lives in remote-state; callers stay untouched.** Each remote tmux helper resolves its target from `loadRemoteAgentState(agentId)`. `tell.ts`, `kill.ts`, `messaging.ts`, `routes/agents/conversation.ts` and `services/agent-output-service.ts` need no edits. `pan tell agent-<issue>` keeps pasting into the agent's tmux pane over exec; the VM's conversation reads the transcript, so the message shows at home.
- **D-6 The VM's tmux socket is `overdeck`.** The VM server runs with the default `OVERDECK_HOME` under `/root`, so `managedInstanceName()` (`src/lib/instance-name.ts:26-31`) is `DEFAULT_INSTANCE_NAME`. Home may run a non-default instance (`overdeck-<hash>`), so remote-state records the VM socket instead of reusing home's `getManagedTmuxSocketName()`. The live checkpoint (WI-14) confirms it.
- **D-7 One watchdog, one heartbeat, one credential target, one cap slot.** The Fly machine record owns all four (FR-10). The push daemon stays (the rootfs resets on stop, `concerns.md`).
- **D-8 The reap owns teardown of a working agent's VM.** After `REMOTE_DONE` the conversation may end and the 30-minute idle clock would start; the reap is behind the deacon freeze but the sweep is not. Without FR-11 the sweep could destroy the VM before the hand-off, and review would never be requested. Once the reap hands off, saves `error`, or `pan kill` sets `stopped`, the state is no longer active and the sweep's idle rule applies again.
- **D-9 The tree row is a conversation row.** `resourceDetails.conversations` already renders as `<a href=…>` rows under each issue (`FeatureItem.tsx:890-903`), and `SharedConversationRow` carries `issueId` (`packages/contracts/src/linked-conversations.ts`). Resource discovery adds cached linked rows there, so any linked conversation with an issue shows under it, including the work agent. A `SessionNode` row would need a contracts change and a `SessionPanel` that can render a linked conversation; neither exists. The `fly.io` chip stays.
- **D-10 Anthropic models only.** The model comes from `determineModel({ model, role: 'work' })` and `resolveEffort({ …, harness: 'claude-code' })`, as `spawnRemoteAgentWithoutConsentClaim` does (`remote-agents.ts:585-592`). When `getProviderForModel(model).name !== 'anthropic'` the route refuses with `harness-unsupported` and names `--model`.
- **D-11 Consent.** The service wraps the start in `withAutoSpawnConsentClaim` under the same condition as `spawnRemoteAgent` (`remote-agents.ts:562-576`): skipped when `isOperatorStartedBy(startedBy)` or `autoSpawnConsentRequired !== true`; accepted after the conversation started; `isAccepted: (state) => state.status === 'running'`.
- **D-12 Tracker updates stay in the CLI.** The block at `start.ts:455-487` moves into `start-remote.ts` unchanged and runs after a 201.

## Hazards

- **Pull here on a working agent.** Pulling the conversation home sets `releasedTo`, the VM refuses new turns (409 `conversation-released`), and the sweep no longer sees an active row. FR-11 still protects the VM while remote-state is `running`, but the agent cannot continue. The docs say Pull here is not for work agents.
- **The VM's own server sees an issue worktree.** Its deacon may run hygiene over `/workspace/<key>/workspaces/feature-<id>` (for example close-out of a closed issue). The machine lives only for one run, so this is noted, not fixed.
- **Prompt delivered as a conversation message.** The VM's conversation runtime may title the conversation from the prompt's first line. That is cosmetic.
- **Merge order with PAN-4743.** PAN-4743 changes the CLI refusal sentence in `worker-remote.ts` and `cli/machines.mdx`. WI-9's interception in `start.ts` runs before `startOnMachine`, so `pan start --machine fly` reaches the new path whichever lands first. Rebase conflicts in `cli/machines.mdx` are textual only.
- **Long synchronous request.** Provisioning and the project clone take 5–15 minutes. The route holds the request; the CLI waits without a timeout; a dashboard restart mid-request leaves remote-state `starting` with a machine that the sweep removes after 30 minutes of no conversation. The next `pan start --remote` refuses `already-running` for 30 minutes after `startedAt`, then treats the `starting` state as crashed provisioning and overwrites it (FR-4). `pan kill` cannot clear it: with `vmName: ''` it never reaches `killRemoteAgent` (`kill.ts:126`).
- **Legacy states during rollout.** A legacy agent running when this ships keeps its raw `agent-<issue>` session; every path falls back to the agent id and home's socket (NFR-6).
