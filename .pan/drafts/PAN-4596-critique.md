## blocks-the-design: An ended hold briefly shows the false orphan state

The PRD's WI-3 initializes `useHeldKickoff` in `ConversationView` and selects the held view only when `heldKickoff.held` is true ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4596/.pan/drafts/PAN-4596.md), lines 155–169). The existing hook initializes `{ held: false }` and fills it only after an asynchronous GET ([heldKickoff.tsx](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4596/src/dashboard/frontend/src/components/chat/heldKickoff.tsx), lines 35–54). During that request, an ended empty conversation satisfies `isOrphaned`, so the panel displays “no saved history” and Resume ([ConversationPanel.tsx](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4596/src/dashboard/frontend/src/components/chat/ConversationPanel.tsx), lines 1282 and 1358–1388). A non-200 response or malformed JSON also becomes `{ held: false }` (hook lines 21–31), leaving that incorrect view in place. This directly breaks FR-2's “never” condition. Smallest fix: make kickoff lookup distinguish loading, verified not-held, and fetch failure; render the generic orphan state only after a successful `{ held: false }` response, and give a failed lookup a retry. Test the initial and failed-GET states, not only the final held response.

## blocks-the-design: A failed Start can permanently hide retry

The kickoff POST returns 200 after claiming and clearing `held_kickoff`, then runs delivery asynchronously ([conversation-kickoff.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4596/src/lib/overdeck/conversation-kickoff.ts), lines 35–55). On launch or delivery failure, that background task restores the hold and sets `forkStatus = 'failed'` (lines 18–32). WI-3 immediately calls `heldKickoff.refresh()` on the 200 response ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4596/.pan/drafts/PAN-4596.md), line 177). If the refresh lands before the background failure, GET returns `{ held: false }`; the hook then stops its interval because it polls only while `heldRef.current` is true ([heldKickoff.tsx](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4596/src/dashboard/frontend/src/components/chat/heldKickoff.tsx), lines 43–60). When the hold is restored, the panel still has `held: false` and routes the failed fork to `ForkProgressView`, which has no retry ([ConversationPanel.tsx](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4596/src/dashboard/frontend/src/components/chat/ConversationPanel.tsx), lines 1352–1357). That defeats FR-5. Smallest fix: keep rechecking the kickoff while a Start is pending and after a failed fork status, then show Start again when the hold is restored. Add a panel test where POST returns 200, GET first says false, the background delivery fails and restores the hold, and the retry button reappears.
