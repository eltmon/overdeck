## Glossary

- **The Cut (PAN-3917):** the removal of Overdeck's "state layer" (the `overdeck-state` branch, `.pan/records/`, the state doors). Planning artifacts now live under `.pan/` in the project repo and are committed on the feature branch by whoever writes them.
- **State plane:** the retired name for the `overdeck-state` branch checkout that pre-cut code committed and pushed planning artifacts to. Nothing pushes planning artifacts on an agent's behalf any more.
- **Plan home:** the repo root whose `.pan/` holds a project's drafts, specs, and continues (`getProjectPanPaths(projectRoot)` in `src/lib/pan-dir/specs.ts`). For overdeck it is the repo itself.
- **Primary checkout:** `/home/eltmon/Projects/overdeck`, the operator's `main` worktree. Agents never commit there.
- **Codebase map:** the four orientation files `architecture.md`, `conventions.md`, `concerns.md`, `stack.md`. Canonical, tracked location: `<projectRoot>/.overdeck/context/codebase/` (`roles/plan.md:48`). `.pan/context/` is the pre-PAN-1201 location, kept only as a read fallback (`src/lib/context-layers/layers.ts:69-73`, `docs/CONTEXT-LAYERS.md:236`).
- **Source run:** running the TypeScript sources directly (Vitest, `tsx`) so `import.meta.url` ends in `.ts`, as opposed to the built `dist/` bundles Node 22 serves in production.
- **Type stripping:** Node 22's built-in ability to load a `.ts` file by erasing type syntax. It does **not** rewrite the file's import specifiers, so `import './dashboard-cost-snapshot.js'` inside a `.ts` file still resolves to a `.js` file that does not exist in `src/`.
- **Dashboard database worker:** `src/dashboard/server/services/dashboard-db-worker.ts`, spawned as a `node:worker_threads` Worker by `src/dashboard/server/services/dashboard-db-task.ts` in four lanes (`read`, `long`, `semantic`, `parse`).
- **Polling snapshot:** the four operations `isPollingSnapshot` names at `dashboard-db-task.ts:359-362` (`getAgentCostStats`, `getCostsByIssueSnapshot`, `getConversationSearchStats`, `getConversationLedgerCosts`). Under Vitest every other operation runs in-process (`dashboard-db-task.ts:376`); these four always go to the real worker, and `src/dashboard/server/services/__tests__/dashboard-poll-worker.test.ts:15-16` pins that on purpose ("these expensive polls must never use the test-only synchronous inline resolver").
- **`makeWiredFakeDb`:** the in-memory Drizzle stand-in at `tests/unit/lib/overdeck/control-settings.test.ts:30-155`.

### F4 — the worker spawn dies under a source run

`src/dashboard/server/services/dashboard-db-task.ts:145-149`:

```ts
function workerScriptUrl(): URL {
  return import.meta.url.endsWith('.ts')
    ? new URL('./dashboard-db-worker.ts', import.meta.url)
    : new URL('./dashboard-db-worker.js', import.meta.url);
}
```

and `getWorker` at `:201-208` spawns `new Worker(workerScriptUrl(), { execArgv: process.execArgv.filter(arg => !arg.startsWith('--inspect')) })`.

Reproduced during planning (source run, `VITEST=1`, `OVERDECK_HOME` pointed at a scratch dir):

```
runDashboardDbJob('getAgentCostStats', { agentIds: ['agent-x'], nowMs: Date.now() })
→ rejects: Error: Cannot find module '/…/src/dashboard/server/services/dashboard-cost-snapshot.js'
           imported from /…/src/dashboard/server/services/dashboard-db-worker.ts
```

The worker's first import (`dashboard-db-worker.ts:1`, `./dashboard-cost-snapshot.js`) cannot resolve because type stripping leaves the `.js` specifier alone. Also verified: passing `--import tsx` / `--import tsx/esm` in the worker's `execArgv`, or running the parent under `node --import tsx` or the `tsx` CLI, does **not** fix it (same `ERR_MODULE_NOT_FOUND`) — tsx's loader hook does not attach to a worker whose entry is the raw `.ts` URL.

Why it was hidden: `getAgentCostStatsSnapshot` (`src/dashboard/server/services/dashboard-poll-snapshots.ts:25-40`) short-circuits to `[]` when the agent list is empty and only dispatches `getAgentCostStats` when it is not. Before fix10 (`2cd3bf4bc45`, "per-home Herdr session") test dashboards saw the operator's live agents, reached the polling snapshot, and the worker exploded; fix10 isolated the Herdr session per `OVERDECK_HOME`, so test agent lists are empty and the path is no longer reached. The defect is latent: any test that seeds agents and reaches a polling snapshot with `node:worker_threads` unmocked hits it again.

What **does** work (verified with a scratch script): an `eval: true` Worker whose code registers tsx's resolver in-thread and then dynamically imports the `.ts` entry:

```js
import('<tsx/esm/api>').then(({ register }) => { register(); return import('<file:///…/dashboard-db-worker.ts>'); });
```

With that bootstrap the worker came online, answered `{ id, operation: 'getAgentCostStats', payload: { agentIds: ['agent-x'], nowMs } }` with `{ ok: true, result: [] }`, and stayed alive. `createRequire(import.meta.url).resolve('tsx/esm/api')` from the `dashboard-db-task.ts` URL resolves to `node_modules/.bun/tsx@4.21.0/node_modules/tsx/dist/esm/api/index.cjs`, and `import()` of that path exposes `register` as a named export (verified). `tsx` is a devDependency (`package.json:205`, `^4.6.2`, installed 4.21.0), which is fine: the built `dist/` path never enters the `.ts` branch.

Two siblings carry the identical `.ts` branch and the identical latent defect: `src/lib/memory/checkpoint-client.ts:19-20` and `src/lib/memory/fts-db.ts:170`. The issue names only `dashboard-db-task.ts`; the siblings are a non-goal (see below).

## Decisions

- **D1 — `.pan/context/` is ignored, not tracked.** The canonical map is already tracked under `.overdeck/context/codebase/`; tracking the legacy copy would commit a stale duplicate. Ignoring it means `git add .pan/context/codebase/` would fail ("paths are ignored"), so the dead staging fallback in `completePlanningFilesToStage` is deleted in the same work item (it has no callers anyway), and the writer that produces the residue (`/pan-map` skill) is re-pointed at the canonical path.
- **D2 — The operator's untracked copy is not deleted by this change.** A diff cannot remove an untracked directory from the operator's primary checkout. After this lands, `git status` in the primary stops showing it; the operator may `rm -r /home/eltmon/Projects/overdeck/.pan/context` at leisure (the canonical copy is newer).
- **D3 — The worker fix is a tsx-registered eval bootstrap in the `.ts` branch, not an inline path.** Routing polling snapshots through `executeInline` under Vitest was rejected because `dashboard-poll-worker.test.ts:15-16` pins the opposite on purpose. The built branch (`./dashboard-db-worker.js`) is untouched.
- **D4 — tsx is resolved from the module's own location** via `createRequire(import.meta.url).resolve('tsx/esm/api')`, so the bootstrap does not depend on the process cwd. **Implementation checkpoint:** if the resolved `.cjs` path fails to `import()` inside the worker thread (it did not during planning), fall back to the bare specifier `'tsx/esm/api'` inside the eval string — that form was also verified, from the checkout root.
- **D5 — Test teardown is explicit.** `dashboard-db-task.ts` never `unref()`s its workers, so a real worker thread would keep a Vitest fork alive. The work item adds `__testInternals.terminateWorkers()` (same pattern as `src/lib/memory/fts-db.ts:184`, `export const __testInternals`), and the regression test calls it in `afterEach`.
- **D6 — Docstring wording is factual about today's behavior.** The rewritten docstring says the target is `.pan/drafts/` under `projectRoot`, that the copy is committed by the planning flow and never pushed from the function, and cites PAN-3935 for the open primary-checkout targeting bug. It must not claim the copy "lands on the feature branch" — today it does not (PAN-3935).
- **D7 — PRD filename is lowercase** (`.pan/drafts/pan-3930.md`), the canonical form `getIssueDraftPath` produces (`drafts.ts:28-38`).
