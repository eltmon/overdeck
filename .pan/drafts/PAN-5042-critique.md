## blocks-the-design: Reopened PR loses to a cached closed row

PRD D5 and WI-2 step 6 always drop the open row when the closed cache contains the same number. The closed cache lasts five minutes (PRD D3), while an active open listing refreshes after 30 seconds (`src/lib/overdeck/pr-cache-policy.ts:59-62`). If PR 7 is closed while another PR stays open, then PR 7 is reopened during that five-minute interval, the next open read contains PR 7 but the cached closed read still contains its old CLOSED row. The combined listing chooses CLOSED. `prFromGhRow` then discards it (`src/lib/overdeck/derived-issue-state.ts:427-432`), and PR sync may persist a false closed snapshot (`src/dashboard/server/services/pull-request-sync-service.ts:184-195,258-306`). The repository explicitly recognizes `reopened` PR events (`docs/PIPELINE-GATES.md:1804-1806`). Add a growth/reopen invalidation rule or otherwise resolve duplicate rows by freshness; test a reopen while another PR keeps the open cache on its 30-second TTL.

## blocks-the-design: Shrink invalidation misses an in-flight closed read

PRD D2 says a PR leaving the open listing is never missing from the combined listing. But `createSettledTtlPromiseCache.invalidate` leaves in-flight loads untouched (`src/lib/concurrency.ts:46-48,63-87`). A combined read can start a closed query, then another read can refresh the open listing and detect a shrink while that closed query is pending. The planned invalidation does not remove the pending closed read, so the second combined read can reuse a closed result fetched before the merge and omit the PR. Make the shrink path wait for and then supersede an in-flight closed read, or add a generation check that retries the closed read after shrink. Test this interleaving with deferred open and closed responses.

## blocks-the-design: PR watch can announce checks passed after a merge

PRD D8 says merged-row checks are display only, but the PR sync sweep feeds listing snapshots to the watch notifier. WI-7 changes `applySnapshot` to preserve a linked PR's prior checks, yet it explicitly leaves the unconditional `ctx.snapshots.set(... snapshotFromGhRow(row))` in `src/dashboard/server/services/pull-request-sync-service.ts:268-274`. A watched PR without a conversation link therefore gets fabricated `checks: 'green'` from a merged closed-listing row with no rollup. `runWatchPass` uses that snapshot (`src/dashboard/server/services/pull-request-sync-service.ts:392-413`), and `watchWake` emits `checks-passed` whenever green replaces red or pending (`src/dashboard/server/services/pull-request-watch-notifier.ts:62-84`). The existing watch test covers a listed PR without a matching link (`src/dashboard/server/services/__tests__/pull-request-sync-service.test.ts:747-763`). Keep unknown closed-row checks out of watch check transitions, or preserve the watch baseline when a rollup is absent; add a test asserting the merge notification has no false checks-passed event.
