# PAN-4724 — Incremental per-issue cost rollup for `getCostsByIssueSnapshot`

**Issue:** [PAN-4724](https://github.com/eltmon/overdeck/issues/4724)
**Status:** planned (auto mode, 2026-11-01)
**Base commit verified against:** `fc9e06d3e19` (feature/pan-4724)

## Glossary

- **`cost_events`** — the per-request cost ledger table in `~/.overdeck/overdeck.db`
  (the event-store database, not the legacy `panopticon.db` in `src/lib/database/schema.ts`).
  One row per model request. Columns used here: `id`, `ts` (epoch ms, NOT NULL),
  `issue_id`, `session_type` (the "stage"), `provider`, `model`, `input`, `output`,
  `cache_read`, `cache_write`, `cost`. Defined in
  `drizzle/overdeck/0000_overdeck_init.sql` (search `CREATE TABLE \`cost_events\``).
- **Snapshot / poll lane** — `getCostsByIssueSnapshot` is a shared server-wide value
  refreshed by `createRefreshingSnapshot` every 15 s (`ttlMs: 15_000`) on the `poll`
  lane of the dashboard database worker thread
  (`src/dashboard/server/services/dashboard-poll-snapshots.ts`).
- **Full scan aggregate** — today's `getCostsByIssue()` in
  `src/lib/overdeck/cost-sync.ts` (line ~243, search
  `export function getCostsByIssue(): Record<string, IssueAggregate>`): four
  `GROUP BY` queries over every row of `cost_events`.
- **Rollup** — the new table `cost_issue_rollup`, one row per **grain**.
- **Grain** — the tuple `(UPPER(issue_id), model, session_type, provider)`, with the
  raw (nullable) values. Live data: 3,006 grains for 771,393 rows.
- **Grain match** — `issue_key IS UPPER(x.issue_id) AND model IS x.model AND
  session_type IS x.session_type AND provider IS x.provider`. `IS` (not `=`) so NULL
  values match NULL values.
- **Install** — the one-time, atomic creation of the rollup table, its index, its
  triggers, and the backfill from existing `cost_events` rows.
- **Top-up** — an idempotent schema statement run on every writable open of
  `overdeck.db` from `ensureRuntimeIndexesSync` in `src/lib/overdeck/infra.ts`
  (line ~90). This is the overdeck.db migration path for existing databases.
- **Writer** — any code that inserts or updates `cost_events` rows (listed in
  Background).

## Problem

`dashboard.log` logs `[db-jobs] slow: op=getCostsByIssueSnapshot lane=poll ...
runMs=1300-1600` every 15-30 s around the clock (66,474 lines on 2026-11-01). Each
refresh reads all 771,393 `cost_events` rows four times. It holds the `poll` lane for
~1.5 s, delays every poll job queued behind it, uses a steady slice of a CPU core, and
grows with every agent turn. The `idx_cost_issue_upper` expression index does not
help: a whole-table `GROUP BY` still reads every row.

## Decisions

- **DEC-1: Trigger-maintained rollup table (the issue's preferred option 1).** SQLite
  `AFTER INSERT` and `AFTER UPDATE` triggers on `cost_events` maintain
  `cost_issue_rollup`. A trigger runs inside the statement that changed
  `cost_events`, so the rollup is updated in the same transaction as the insert. We
  use triggers, not JS code next to each insert, because there are four writers and
  one of them (the hook bundle `sync-sources/hooks/record-cost-event.js`) runs stale
  bundled code in another process. Only a database-level trigger sees its inserts.
  Reviewers must not "simplify" this into JS maintenance.
- **DEC-2: Option 2 (rowid watermark) is rejected.** `reclassifyUnknownCostEvents`
  rewrites `issue_id` on existing rows, which a rowid watermark cannot see.
- **DEC-3: One table at the finest grain.** The grain includes `provider`, so one table
  serves all four read queries (totals, models, stages, providers) with `GROUP BY` over
  ~3k rows. No separate per-dimension tables.
- **DEC-4: Grain keys are raw and nullable; matching uses `IS`.** No primary key and no
  `ON CONFLICT` upsert (SQLite unique indexes treat NULLs as distinct, so an upsert
  would duplicate NULL-key rows). The trigger runs `INSERT ... SELECT ... WHERE NOT
  EXISTS (grain match)` and then `UPDATE ... WHERE grain match`. SQLite has a single
  writer, so this pair cannot race.
- **DEC-5: Only the SQL sources change in `getCostsByIssue`.** The JS shaping
  (`?? 'unknown'`, `COALESCE(provider, 'unknown')` in SQL, `?? 0`, the `lastUpdated`
  conversion and fallback, `budgetWarning: false`, `ORDER BY total_cost DESC`) stays
  byte-for-byte the same. The NULL-issue bucket (JSON key `"null"`) is preserved
  because `GROUP BY issue_key` groups NULL keys together exactly as `GROUP BY
  UPPER(issue_id)` does.
- **DEC-6: Equality definition.** Integers (`calls`, the four token sums, `tokens`,
  `last_ts`) must match the full-scan aggregate exactly. `cost` (REAL) must match within
  an absolute tolerance of `1e-6` USD per value, because `cost = cost + NEW.cost`
  accumulates in a different order than `SUM(cost)` (SQLite's `SUM` uses compensated
  summation). Tests use `expect(a).toBeCloseTo(b, 6)` for cost fields.
- **DEC-7: Install lives in a new module and runs from the top-up.** New file
  `src/lib/overdeck/cost-issue-rollup.ts` exports `ensureCostIssueRollup(db)`. It takes
  the database handle as a parameter and imports nothing from `infra.ts` (infra imports
  it; an import back would fail `lint:circular`). `ensureRuntimeIndexesSync` in
  `infra.ts` gets one call line. `infra.ts` is at 941 lines (ceiling 1000), so the
  install code must not go there.
- **DEC-8: Not in `0000_overdeck_init.sql`.** The rollup is a derived table whose
  creation must be atomic with its backfill and triggers, so it has a single source:
  the module. Fresh databases get it from the same top-up call on their first open
  (backfill of an empty table is instant). This follows the precedent of
  `sessions_fts` in `src/lib/overdeck/discovered-sessions.ts` ("created inline here
  (not in the migration SQL) so it stays outside the OVERDECK_TABLE_COUNT check"), and
  it keeps `OVERDECK_TABLE_COUNT = 43` (`src/lib/overdeck/paths.ts`) and
  `scripts/gen-overdeck-erd.py` (which regex-parses only `CREATE TABLE`/`CREATE INDEX`)
  unchanged. The docs item records this exception in the "Schema changes" rule.
- **DEC-9: Additive install may run from any process.** Unlike
  `dropPipelineStateMirrorTables` (destructive, primary-only), the install only adds
  objects, so it runs on every writable open like the other top-ups. Read-only opens
  (`getOverdeckDatabase(path, { readOnly: true })`) never install.
- **DEC-10: Double-checked install guard.** Outside any transaction, one
  `sqlite_master` query checks whether all v1 objects exist. If yes, return. If no:
  `BEGIN IMMEDIATE`, check again inside the transaction (another process may have
  finished first), drop any partial v1 objects, create the table, the index, run the
  backfill, create the triggers, `COMMIT`. The write lock is never taken on an open
  where the rollup already exists. If `cost_events` does not exist (partially built
  test database), return `false` silently.
- **DEC-11: Versioned object names.** Every object carries the `_v1` suffix in its
  name. A future change to the grain or the aggregated columns ships `_v2` names; its
  install drops the `_v1` objects and rebuilds in the same transaction.
- **DEC-12: Exact `last_ts` when rows leave a grain.** The `AFTER UPDATE` trigger
  subtracts the OLD values from the OLD grain and adds the NEW values to the NEW grain.
  When the OLD grain's `calls` reaches 0, its row is deleted. When it still has rows and
  `OLD.ts` equalled its `last_ts`, `last_ts` is recomputed with `SELECT MAX(ts) FROM
  cost_events WHERE <grain match on OLD>`. This is rare (only `UNKNOWN` reclassification
  today) and keeps `lastUpdated` exact.
- **DEC-13: Reader falls back if the rollup is missing.** `getCostsByIssue()` calls
  `ensureCostIssueRollup(db)`; on `true` it reads the rollup; on `false` it returns the
  full-scan aggregate and logs one `console.warn` per process. The old query is kept,
  renamed `getCostsByIssueFullScan()` and exported, because (a) it is the fallback,
  (b) the equivalence test compares against it literally, as the issue AC requires.
- **DEC-14: The 15 s snapshot TTL stays.** A refresh now costs ~5 ms; no TTL change.
- **DEC-15: No DELETE trigger.** No code deletes `cost_events` rows. A future deleter
  (retention, manual cleanup) must either add a `_v2` DELETE trigger or rebuild the
  rollup; this is recorded in the codebase-map concerns.

## Requirements

### Functional

- **FR-1** A table `cost_issue_rollup` exists in every writable-opened `overdeck.db`,
  with columns `issue_key TEXT, model TEXT, session_type TEXT, provider TEXT, calls
  INTEGER NOT NULL DEFAULT 0, cost REAL NOT NULL DEFAULT 0, input INTEGER NOT NULL
  DEFAULT 0, output INTEGER NOT NULL DEFAULT 0, cache_read INTEGER NOT NULL DEFAULT 0,
  cache_write INTEGER NOT NULL DEFAULT 0, tokens INTEGER NOT NULL DEFAULT 0, last_ts
  INTEGER NOT NULL`, and index `cost_issue_rollup_key_idx_v1` on `(issue_key, model,
  session_type, provider)`.
- **FR-2** Install backfills the rollup from all existing `cost_events` rows in the same
  transaction that creates the triggers, so no insert is lost or double-counted.
- **FR-3** Every row inserted into `cost_events` by any writer (including raw SQL)
  updates its grain row: `calls + 1`, each sum `+ COALESCE(NEW.col, 0)`, `tokens +
  COALESCE(NEW.input + NEW.output + NEW.cache_read + NEW.cache_write, 0)`, `last_ts =
  MAX(last_ts, NEW.ts)`. `INSERT OR IGNORE` rows that are ignored change nothing.
- **FR-4** An `UPDATE` of any of `ts, issue_id, model, session_type, provider, cost,
  input, output, cache_read, cache_write` moves the row's contribution from the OLD
  grain to the NEW grain (DEC-12).
- **FR-5** `getCostsByIssue()` returns the same keys and values as
  `getCostsByIssueFullScan()` under DEC-6 equality, after install, after further
  inserts, and after `reclassifyUnknownCostEvents()`.
- **FR-6** When the rollup cannot be installed, `getCostsByIssue()` returns the
  full-scan result and logs one warning per process containing `[cost-issue-rollup]`.

### Non-functional

- **NFR-1** With ~750,000 `cost_events` rows, `getCostsByIssueSnapshot()` (from
  `dashboard-cost-snapshot.ts`) completes in under 50 ms (median of 5 runs after one
  warm-up), well below the 1,000 ms threshold of `formatSlowJobLine`
  (`src/dashboard/server/services/dashboard-db-task.ts` line ~143), so no `[db-jobs]
  slow: op=getCostsByIssueSnapshot` line is logged in steady state.
- **NFR-2** None of the four rollup read statements reads `cost_events`
  (`EXPLAIN QUERY PLAN` output contains no `cost_events`).
- **NFR-3** Install on an existing database whose rollup already exists does one
  `sqlite_master` read and takes no write lock.
- **NFR-4** No file grows past the file-size ratchet (`scripts/lint-file-size.sh`,
  ceiling 1000 lines). `infra.ts` grows by at most 3 lines.

4. Export `ensureCostIssueRollup(db: SqliteDatabase): boolean` (DEC-10):
   ```ts
   export function ensureCostIssueRollup(db: SqliteDatabase): boolean {
     if (!hasTable(db, 'cost_events')) return false;
     if (isInstalled(db)) return true;
     try {
       db.exec('BEGIN IMMEDIATE');
       try {
         if (!isInstalled(db)) installInTransaction(db);   // drop partial v1 objects, create, backfill, triggers
         db.exec('COMMIT');
       } catch (error) {
         db.exec('ROLLBACK');
         throw error;
       }
       return true;
     } catch (error) {
       console.error(`[cost-issue-rollup] install failed: ${error instanceof Error ? error.message : String(error)}`);
       return false;
     }
   }
   ```

### WI-2 — Update trigger for rows that change grain (FR-4)

   to `ROLLUP_TRIGGERS_SQL`:
   ```sql
   CREATE TRIGGER `cost_issue_rollup_au_v1`
   AFTER UPDATE OF ts, issue_id, model, session_type, provider, cost, input, output, cache_read, cache_write
   ON `cost_events` BEGIN
     -- remove OLD contribution
     UPDATE cost_issue_rollup SET
       calls = calls - 1,
       cost = cost - COALESCE(OLD.cost, 0),
       input = input - COALESCE(OLD.input, 0),
       output = output - COALESCE(OLD.output, 0),
       cache_read = cache_read - COALESCE(OLD.cache_read, 0),
       cache_write = cache_write - COALESCE(OLD.cache_write, 0),
       tokens = tokens - COALESCE(OLD.input + OLD.output + OLD.cache_read + OLD.cache_write, 0)
     WHERE issue_key IS UPPER(OLD.issue_id) AND model IS OLD.model
       AND session_type IS OLD.session_type AND provider IS OLD.provider;
     DELETE FROM cost_issue_rollup
     WHERE calls <= 0 AND issue_key IS UPPER(OLD.issue_id) AND model IS OLD.model
       AND session_type IS OLD.session_type AND provider IS OLD.provider;

         SELECT MAX(ts) FROM cost_events
         WHERE UPPER(issue_id) IS UPPER(OLD.issue_id) AND model IS OLD.model
           AND session_type IS OLD.session_type AND provider IS OLD.provider)
     WHERE last_ts = OLD.ts AND issue_key IS UPPER(OLD.issue_id) AND model IS OLD.model
       AND session_type IS OLD.session_type AND provider IS OLD.provider;

       WHERE NOT EXISTS (SELECT 1 FROM cost_issue_rollup
         WHERE issue_key IS UPPER(NEW.issue_id) AND model IS NEW.model
           AND session_type IS NEW.session_type AND provider IS NEW.provider);

       cache_write = cache_write + COALESCE(NEW.cache_write, 0),
       tokens = tokens + COALESCE(NEW.input + NEW.output + NEW.cache_read + NEW.cache_write, 0),
       last_ts = MAX(last_ts, NEW.ts)
     WHERE issue_key IS UPPER(NEW.issue_id) AND model IS NEW.model
       AND session_type IS NEW.session_type AND provider IS NEW.provider;
   END;
   ```
   Note the AFTER trigger sees the row already updated, so the `MAX(ts)` recompute
   reads the post-update table.

## Repo rules that intersect this change (restated)

- **No `execSync` in dashboard-reachable code.** Not needed here; all SQLite calls are
  in-process `node:sqlite`, which the poll lane already runs on the worker thread.
- **Fake timers for delay tests.** No test here waits on a timer; do not add real
  `setTimeout` waits.
- **Tests run in isolation:** run only the test files you touched
  (`npx vitest run <files>`); never the full `npm test` on the host.
- **File-size ratchet:** `infra.ts` is 941/1000 lines; add only the import and the call.
- **`lint:circular`:** `cost-issue-rollup.ts` must not import `infra.ts` or
  `cost-sync.ts`.
- **Overdeck.db schema path:** schema for existing databases lands as a top-up from
  `ensureRuntimeIndexesSync` (see DEC-8 for why not the init SQL).
- **Never destructive against the live DB in tests:** every test uses a temp
  `OVERDECK_HOME`; never open `~/.overdeck/overdeck.db` from a test.
