## Glossary

- **Grok Bot:** xAI's hosted assistant. It loads Cursor-format plugins: `.cursor-plugin/plugin.json` plus an `mcp.json` whose server has a remote `url`. It runs on xAI's servers, so it can only reach a public HTTPS URL.
- **xAI API / Responses API:** `POST https://api.x.ai/v1/responses`. A request may carry a **remote MCP tool**, `{ "type": "mcp", "server_url", "server_label", "allowed_tools", "authorization" }`; xAI's servers then call that MCP server during the response.
- **Public MCP:** Overdeck's opt-in public `/mcp` through Tailscale Funnel (PAN-4947, shipped). Switch `mcp.public.enabled`, off by default. Public URL shape: `https://<machine>.<tailnet>.ts.net:8443/mcp`. Over Funnel, `/mcp` accepts only OAuth-issued tokens (`src/dashboard/server/routes/mcp.ts:108-111`).
- **OAuth sign-in:** PAN-4945/PAN-4946 (shipped). A client registers, the operator approves the sign-in in the dashboard, and the client gets a 30-day access token (`odk_…`) and a 90-day rotating refresh token (`odr_…`). `pan mcp oauth issue --name <n> --level <read|message|operate|approve>` creates a sign-in at once for a client that cannot open a browser (`src/cli/commands/mcp-oauth.ts:58-70`).
- **Access level:** `read` = `read:state, read:conversations`; `message` adds `tell`; `operate` adds `operate`; `approve` adds `approve` (`configuration/mcp.mdx`, "Sign in with OAuth" table).
- **Bot snippets:** the pure functions in `src/dashboard/frontend/src/components/Settings/anywhere/botSnippets.ts` that the Connect a bot dialog (W-BOT1, PAN-4951, shipped) shows. Its header says: "The integration READMEs (W-INT1..4) must match these functions." Here: `grokBotMcpJson`, `xaiExample`, `oauthIssueCommand`, and the constants `PUBLIC_MCP_PLACEHOLDER_URL`, `XAI_ALLOWED_TOOLS`.
- **Shared skill:** `integrations/shared/SKILL.md`; `integrations/shared/sync-skill.mjs` already wrote its copy to `integrations/grok-bot/skills/overdeck/SKILL.md` (W-INT0, PAN-4952, shipped). `tests/unit/integrations/sync-skill.test.ts` checks the copy.
- **CP-8:** the epic's live checkpoint: install the plugin in Grok Bot, sign in with OAuth, call `list_conversations`; run the xAI example; confirm the xAI field names.
- **Source-introspection lint:** `scripts/lint-source-introspection.sh` (part of `npm run lint`). It flags a test file when a `readFile(` or `readFileSync(` call has, inside its parentheses, a quoted string ending in `.ts` or `.tsx`. A new flagged file fails lint.

## Decisions

- **D-1 The xAI item owns the snippet fix.** W-BOT1 is merged; the drift is in the xAI example; the W-INT4 README must match the snippet. So this issue fixes `xaiExample` in `botSnippets.ts` (WI-1) rather than copying a wrong snippet into the README.
- **D-2 Model `grok-4.7`.** It is xAI's documented flagship and the repo's own catalog entry (Fact 6, 7). Runnable examples accept `XAI_MODEL` to override it.
- **D-3 `authorization` carries the bare access token.** xAI documents the field as the token it sets in the Authorization header, matching OpenAI's Responses semantics, so the examples pass the bare `odk_…` value. Overdeck needs `Bearer <token>` (Fact 5). CP-8 sub-check (c) settles it live; the fallback is in "Implementation checkpoints". `bearerToken()` is not widened: that is an auth-boundary change outside this item.
- **D-4 Raw REST, no SDK.** Both examples POST JSON to `/v1/responses` with the field names in Fact 7. The xAI Python SDK spells two fields differently (`allowed_tool_names`, `extra_headers`); using the REST names in both languages keeps one shape to verify and needs no install.
- **D-5 Runnable and testable.** Each example takes `XAI_BASE_URL` (default `https://api.x.ai/v1`) so a test or a proxy can point it elsewhere. Each wraps its work in a `main` function (TypeScript: `async function main()`, no top-level `await`, no `import` statements) so it runs as ESM or CommonJS under Node's type stripping.
- **D-6 CP-8 is recorded, not run, by the work agent.** This host has no `tailscale` and no `XAI_API_KEY` (Fact 9), and turning Public MCP on publishes a sign-in page to the internet. The work agent never runs `tailscale funnel`, never sets `mcp.public.enabled`, and never calls the real xAI API. It records each live check as `Not run: <reason>` in `docs/verification.md` with the exact operator steps. AC-28 is satisfied by that record (its "or CP-8 records why" branch, read as "records why the check has not run"). If the operator later runs CP-8 and a client needs SSE responses to `POST`, that change to `routes/mcp.ts` is a follow-up issue.
- **D-7 No logo.** The repo has no PNG plugin logo; `plugin.json` omits `logo`, and `PUBLISHING.md` lists adding one as a pre-submission step.
- **D-8 Separate test files per example.** `tests/unit/integrations/grok-bot-example-ts.test.ts` and `grok-bot-example-py.test.ts` each carry their own small fake server, so the two example items share no file and can run in parallel. `tests/unit/integrations/grok-bot.test.ts` holds the manifest checks (WI-2) and the README and secret-scan checks (WI-5).
- **D-9 Secret scan by directory walk.** WI-5's scan lists `integrations/grok-bot/` recursively with `readdirSync` and reads each file by a joined path, so no `.ts` literal appears in a `readFile` call. It is a secret-hygiene scan over every file type in the package, not a wiring assertion.

## Hazards

- **H-1 Source-introspection lint.** A test that calls `readFileSync(new URL('…/xai-api.ts', …))` fails `npm run lint`. The example tests run the scripts; the secret scan reads by directory walk (D-9).
- **H-2 Blocking spawn deadlock.** `spawnSync`/`execFileSync` would block the event loop, so the in-process fake server could never answer. Use promisified `execFile`.
- **H-3 `__pycache__`.** Running the Python example or `py_compile` can write `examples/__pycache__/`. Set `PYTHONDONTWRITEBYTECODE=1`; never commit `__pycache__`.
