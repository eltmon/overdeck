# PAN-5019 — Phone app: pause notifications and choose which notification types to receive

**Issue:** [PAN-5019](https://github.com/eltmon/overdeck/issues/5019) · **Planned:** 2026-11-04 (auto mode) · **Base:** `main` @ `180d15a55fd`

## Summary

The Overdeck phone app gets every needs-you push that every paired machine sends. The only way
to stop them is the existing Notifications switch (which unregisters the phone at the directory)
or iOS Settings. This change adds, in the app's Settings:

1. **Pause** — a switch (pause until turned back on) plus "Pause for 1 hour" and "Pause until
   tomorrow 8:00". While paused, no machine sends this phone a needs-you push.
2. **Notification types** — six switches: agent questions, plan approvals, permission prompts,
   finished, failed, and agent stopped responding.

The phone owns the preferences. It sends them to each paired machine; the machine filters
**before it seals and sends**, so a muted or paused phone causes no `push` frame at the directory
and APNs is never woken.

## Glossary

- **Machine** — a computer running the Overdeck dashboard server, paired with the phone.
- **Phone record** — the machine's `kind: 'phone'` access-token record
  (`src/lib/access-token-records.ts`), minted by `POST /api/phones/exchange`. It carries the
  phone's `clientId` (UUID v4, stable per app install) and `pushKey`.
- **Native provider** — `createNativePushProvider` in `src/lib/push/native-provider.ts`: seals a
  needs-you notification to each phone's push key and sends a `push` frame to the overdeck.ai
  directory (`services/connect`).
- **Dispatcher** — `createNeedsYouDispatcher` in `src/lib/push/dispatcher.ts`: dedup, the global
  `push.events` config filter, the 6-per-minute rate limit, then fan-out to every provider (Web
  Push, ntfy, native).
- **NeedsYouKind** — the existing wire kind: `question | approval | finished | failed | summary | test`
  (`src/lib/push/types.ts` line 6). It is too coarse for the six switches: plan approvals and
  permission prompts are both `approval`, and "agent stopped responding" is `failed`.
- **Notification category** — NEW. The finer, user-facing classification a switch controls:
  `question | plan | permission | finished | failed | stopped`. `summary` and `test` are not
  categories a user can mute.
- **Notification preferences ("prefs")** — NEW. The JSON object the phone sends to each machine:
  `{ v: 1, pause: null | { until: string | null }, muted: PhoneNotificationCategory[] }`.
  `pause: null` = not paused; `pause.until: null` = paused until turned back on; `pause.until: ISO` =
  paused until that instant.
- **Link channel** — the end-to-end encrypted Noise channel the phone opens to a paired machine
  (`Connection.openLink` in `apps/mobile/src/shell/connection.ts`). `requestOnChannel` from
  `@overdeck/anywhere-channel/web` sends one HTTP request over it.
- **Sync** — sending the phone's current prefs to one machine and recording which prefs
  revision that machine has acknowledged.

## Decisions

- **D-1 Filter on the machine, in the native provider.** Each phone's prefs are checked inside
  `createNativePushProvider().send`, per phone, before sealing. The dispatcher, Web Push and ntfy
  are untouched (they serve browsers and topics, not the app). A filtered phone is **omitted** from
  the outcomes (no `skipped` outcome), so an all-paused fleet does not raise `stats.dropped` or
  `lastError`. `hasTargets()` is unchanged (it still counts phones).
- **D-2 Category is an explicit field.** `NeedsYouNotification` gains
  `category: NeedsYouCategory` where `NeedsYouCategory = PhoneNotificationCategory | 'summary' | 'test'`.
  `classify.ts` sets it where it already knows the source: `auq:` → `question`, `plan:` → `plan`,
  `perm:` → `permission`, `agent.heartbeat_dead` → `stopped`, journal finished → `finished`, journal
  failed → `failed`. The dispatcher summary sets `summary`; `sendTestPush` sets `test`. The
  provider never parses tag prefixes. `NeedsYouKind`, `PhonePushPayload` and the wire are unchanged.
- **D-3 What pause and mutes do to `summary` and `test`.** A paused phone receives nothing except
  `test`. Mutes never apply to `summary` or `test`. `test` always reaches every phone because it is
  the operator's explicit "Send test" check of the pipe. (Consequence: the device acceptance check
  must use a real needs-you event, not "Send test".)
- **D-4 Shared contract in `@overdeck/contracts`.** New `packages/contracts/src/phone-notifications.ts`
  holds `PhoneNotificationCategory`, `PHONE_NOTIFICATION_CATEGORIES`, `PhoneNotificationPreferences`,
  `DEFAULT_PHONE_NOTIFICATION_PREFERENCES`, `parsePhoneNotificationPreferences(value: unknown)` and
  `notificationAllowed(prefs, category, nowMs)`. Both the server and the phone import it.
- **D-5 `muted` is a list, not a map of booleans.** A category the phone does not list is on, so a
  category added later defaults on for older phones, and an older machine drops unknown strings when
  parsing (forward compatible).
- **D-6 Pause is an absolute instant.** The phone converts its choice to an ISO-8601 UTC instant
  before sending. "Pause for 1 hour" = now + 3,600,000 ms. "Pause until tomorrow 8:00" = the next
  08:00 in the phone's local time zone that is strictly after now (at 02:00 it is 08:00 the same
  day; at 09:00 it is 08:00 the next day). The Pause switch = `{ until: null }`. A past `until`
  means not paused; nothing on the machine runs a timer.
- **D-7 Machine store is a separate file keyed by `clientId`.** `<OVERDECK_HOME>/push/phone-preferences.json`
  (`{ v: 1, phones: { [clientId]: PhoneNotificationPreferences } }`), mode 0600, atomic write, one
  in-process queue, an in-memory cache loaded on first read. It is NOT stored on the access-token
  record (that file's `isRecord` validation is security-sensitive). Keying by `clientId` means a
  re-pair (new token record, same `clientId`) keeps the machine's copy. A corrupt or unreadable file
  reads as "no prefs" (fail open: notifications keep coming) with one `console.warn`, and the next
  write replaces it — the phone is the source of truth and resends. A write prunes entries whose
  `clientId` has no active phone record.
- **D-8 Two transports, both machine-side.**
  - The exchange: `POST /api/phones/exchange` accepts an optional `notificationPreferences` field.
    Valid prefs are stored and the answer adds `notificationPreferencesStored: true`. Invalid or
    absent prefs never fail the pairing; the answer then omits the flag. This makes a re-pair carry
    the settings without a second channel (which matters while PAN-5018 breaks link channels on a
    real iPhone).
  - `PUT /api/phones/self/notification-preferences` over a link channel for every later change.
    Scope `tell` in the scope table; the handler requires `credential.kind === 'phone'` (403
    otherwise), runs `rejectUnsafeDashboardMutationRequest`, answers 400 for an invalid body,
    stores by `credential.clientId`, and answers `{ ok: true }`.
- **D-9 Phone storage is `localStorage`.** Key `overdeck.notificationPrefs` holds
  `{ revision: number, prefs: PhoneNotificationPreferences }`; key `overdeck.notificationPrefsSynced`
  holds `{ [environmentId]: revision }`. Sign-out already calls `localStorage.clear()`, so sign-out
  resets them — correct. App restart and re-pair keep them.
- **D-10 Sync triggers and retry.** A sync pass sends the current prefs to every paired machine whose
  acknowledged revision is below the current revision and that the directory lists `online`. Passes
  run on: a prefs change, every directory `onStateChange` while `online` (this covers resume and a
  machine coming online), and right after a pairing whose answer lacked `notificationPreferencesStored`.
  One request per machine at a time, bounded to 10 s. After a failure the machine is not retried for
  60 s. A 404 or 405 answer marks the machine `outdated` (its Overdeck is too old) and it is not
  retried until the prefs change again or the app restarts.
- **D-11 Keep the existing Notifications switch.** It still controls the directory registration.
  Pause is separate and machine-side. The Settings text and the docs say what each does.
- **D-12 Android.** Push is iOS-only (`pushSupported()`), so the new controls render only inside the
  existing `notifications` section. No Android work.

## Requirements

- **FR-1** The phone app's Settings shows a Pause switch and two timed pause actions ("Pause for 1
  hour", "Pause until tomorrow 8:00"); while paused it shows when the pause ends (or "until you
  turn it back on") and a way to resume.
- **FR-2** While a phone is paused, no paired machine that has its prefs sends it a needs-you push
  (no `push` frame), except the operator's `test` push.
- **FR-3** The Settings shows one switch per category: agent questions, plan approvals, permission
  prompts, finished, failed, agent stopped responding.
- **FR-4** A muted category is not sent to that phone; every other category still is.
- **FR-5** The prefs survive an app restart and a re-pair with a machine.
- **FR-6** The phone sends its prefs to every paired machine (exchange at pairing, PUT afterwards)
  and the Settings shows which machines have not received them yet, or need an update.
- **FR-7** Every needs-you notification carries a category set by the classifier.
- **FR-8** Documentation describes pause, types, how they differ from the Notifications switch, the
  new route, and the device acceptance check.
- **NFR-1** Prefs parsing never throws; an invalid or missing prefs record means "deliver
  everything" (fail open).
- **NFR-2** Web Push, ntfy and the Live Activity are unaffected.
- **NFR-3** Tests involving delays (pause expiry, 60 s retry back-off, 10 s request bound) use
  `vi.useFakeTimers()`; never real `setTimeout` waits (repo rule `fake-timers-for-retry-tests`).
- **NFR-4** No new `execSync` or sync file I/O in server-reachable code (repo rule): the store uses
  `node:fs/promises`.

```ts
export type PhoneNotificationCategory = "question" | "plan" | "permission" | "finished" | "failed" | "stopped"
export const PHONE_NOTIFICATION_CATEGORIES: readonly PhoneNotificationCategory[] =
  ["question", "plan", "permission", "finished", "failed", "stopped"]
export interface PhoneNotificationPreferences {
  readonly v: 1
  /** null: not paused. `until: null`: paused until turned back on. `until`: ISO-8601 instant. */
  readonly pause: null | { readonly until: string | null }
  /** Categories this phone does not want. Unlisted categories are on. */
  readonly muted: readonly PhoneNotificationCategory[]
}
export const DEFAULT_PHONE_NOTIFICATION_PREFERENCES: PhoneNotificationPreferences = { v: 1, pause: null, muted: [] }
/** Null for anything that is not a v1 prefs object; drops unknown/duplicate `muted` entries; never throws. */
export function parsePhoneNotificationPreferences(value: unknown): PhoneNotificationPreferences | null
/** Whether a notification of `category` may go to a phone with `prefs` at `nowMs` (D-3). */
export function notificationAllowed(
  prefs: PhoneNotificationPreferences | null,
  category: PhoneNotificationCategory | "summary" | "test",
  nowMs: number,
): boolean
```

Rules for `parsePhoneNotificationPreferences`: `v` must be `1`; `pause` must be `null` or an object
whose `until` is `null` or a string `Date.parse` accepts (else return null); `muted` must be an array
(else null), keeping only known categories, deduplicated, in `PHONE_NOTIFICATION_CATEGORIES` order.

Rules for `notificationAllowed`: `prefs === null` → true. `category === 'test'` → true. Paused (pause
non-null and (`until === null` or `Date.parse(until) > nowMs`)) → false. `category === 'summary'` →
true. Otherwise → `!prefs.muted.includes(category)`.

Export from `index.ts` with `export * from "./phone-notifications"` next to `./phone-pairing`.

Tests: parse accepts a valid object; rejects `v: 2`, a non-array `muted`, an unparseable `until`;
drops `"bogus"` from `muted`; `notificationAllowed` table for null prefs, indefinite pause, future
`until`, past `until`, muted category, summary while muted, summary while paused, test while paused.

headers: { Authorization: \`Bearer ${machine.token}\`, 'Content-Type': 'application/json' }, body }, { signal })`,
`stream.destroy()` in `finally`.

`ShellApp.tsx`: create the sync in the services effect (iOS only — when `pushSupported()`), add it
to `Services`, `stop()` it in the cleanup, pass `notificationPreferences: readNotificationPrefs` and
`onPreferencesStored: markSynced` to `pairMachine` (WI-6).

Tests (fake timers): a stale online machine gets one PUT and becomes `synced`; an offline machine

second PUT follows another state change; a failure is not retried within 60 s but is after 60 s; a
machine already at the current revision gets no PUT.

## Repo rules that intersect this work

- **Fake timers** for every delay-based test (`vi.useFakeTimers()`, `vi.advanceTimersByTimeAsync`); never
  real waits; never lower `maxForks` to hide a leak.
- **No `execSync`** / sync child processes in server-reachable code; file I/O via `node:fs/promises`.
- **New HTTP route ⇒ a `tests/unit/lib/overdeck/no-loss-matrix.ts` row**, or CI fails.
- **New source-reading tests and added `skipIf`/`.only` fail the gates**; assert behaviour, not source text.
- **`apps/mobile` tests run with** `npm --prefix apps/mobile test` and typecheck with `npm run typecheck:mobile`;
  the root `npm test` does not run them. Contracts tests run with `npm --prefix packages/contracts test`
  and typecheck with `npm run typecheck:contracts`.
- **Quality gates before `pan done`:** `npm run typecheck`, `npm run lint`, `npm run typecheck:mobile`,
  and `npx vitest run <touched test files>` (plus `npm --prefix apps/mobile test` for the phone).
- **File size:** no `src/` file may grow past its `origin/main` line count if it is on the allowlist, and
  no new `src/` file may exceed 1,000 lines. None of the touched `src/` files is near that.

## Non-goals

- Relaying prefs through the overdeck.ai directory for machines the phone cannot reach (needs a
  `services/connect` change; follow-up [PAN-5022](https://github.com/eltmon/overdeck/issues/5022)).
- Dropping muted notifications on the phone in the Notification Service Extension (needs Apple's
  `com.apple.developer.usernotifications.filtering` entitlement; follow-up [PAN-5022](https://github.com/eltmon/overdeck/issues/5022)).
- Per-machine preferences (the issue marks them optional). The wire format already allows it later:
  the phone decides what to send each machine.
- Changing Web Push (browser `/m`) subscriptions, ntfy, the machine's `push.events` config, or the
  Live Activity.
- Android notification preferences (Android push is PAN-4840).
- Showing a phone's prefs in the machine's dashboard Settings → Anywhere.
- Excluding muted items from the dispatcher's rate-limit count (a burst of muted items can still
  produce a `summary` notification on an unpaused phone).
