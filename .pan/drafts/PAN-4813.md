# PAN-4813 — Support Kimi K3.1 Pro and K3.1 Pro Highspeed

**Issue:** https://github.com/eltmon/overdeck/issues/4813
**Status:** planned (auto mode, 2026-11-02)

Add Moonshot's Kimi K3.1 Pro and K3.1 Pro Highspeed (released about 2026-10-23) to Overdeck on all three
Kimi routes: Claude Code (Anthropic-compatible endpoint), the native `kimi` CLI harness (`kimi-code`), and
ACP. Follow the pattern Kimi K3 used (#2904 / PAN-2859). K3 stays as it is.

This PRD is lowered from the issue body. Where the issue text and the code disagree, the code wins and the
correction is stated in "Corrections to the issue text" below.

## Glossary

- **Claude Code route:** the `claude-code` harness pointed at Kimi's Anthropic-compatible endpoint. It uses
  the bare ids in `PROVIDERS.kimi.models` (for example `k3`, `k3[1m]`).
- **Coding endpoint:** the Kimi Code subscription endpoint, `KIMI_CODING_BASE_URL =
  'https://api.kimi.com/coding'` in `src/lib/providers.ts`. `getKimiAnthropicBaseUrl` selects it for keys
  that start with `sk-kimi-`. Model ids are short: `k3.1-pro`.
- **Platform endpoint:** the Moonshot pay-as-you-go endpoint, `KIMI_PLATFORM_BASE_URL =
  'https://api.moonshot.ai/anthropic'`. Selected for every other key. Model ids carry a `kimi-` prefix:
  `kimi-k3.1-pro`.
- **Native alias:** an id in the `kimi` CLI's own catalog (listed by `kimi provider list --json`),
  namespaced `kimi-code/<model>`. The `kimi-code` and `acp` harnesses both launch with it.
- **Canonical id:** the id Overdeck stores in config, pickers, and capability tables.
- **Launch model:** the string Overdeck passes as `claude --model '<id>'`. It is produced by
  `getClaudeCodeLaunchModel()` (`src/lib/kimi-claude-routing.ts`) and then `shellQuoteModelId()`
  (`src/lib/model-validation.ts`), which also applies `apiLaunchModelId()`.
- **Tier env vars:** `ANTHROPIC_DEFAULT_OPUS_MODEL` / `_SONNET_` / `_HAIKU_` / `ANTHROPIC_SMALL_FAST_MODEL` /
  `CLAUDE_CODE_SUBAGENT_MODEL`, built from `PROVIDERS.kimi.tierModels` in `getProviderEnv()`.
- **Lockstep test:** the test in `src/lib/acp/__tests__/kimi.test.ts` ("agrees with the kimi-code harness
  translation for every live Kimi model") that asserts, for every id in `PROVIDERS.kimi.models`,
  `translateKimiAcpModelId(id) === resolveKimiCodeModelAlias(id)`.

## Corrections to the issue text

1. **WI-1 target file.** The issue says to add capability rows to `model-capabilities.ts`. That file is at
   its file-size cap, so the rows go in `src/lib/model-capability-additions.ts`.
2. **FR-1 needs `getClaudeCodeLaunchModel` widened.** Changing `resolveKimiModelForEndpoint` alone only
   affects the tier env vars, which stay on K3. The `--model` argument would still send `k3.1-pro` to the
   platform endpoint. WI-4 below widens the guard in `getClaudeCodeLaunchModel`.
3. **Platform translation is gated on the platform URL exactly.** The issue's sketch translated K3.1 ids for
   every non-coding endpoint. The existing test "does not translate other model IDs or unrelated endpoints"
   expects unrelated endpoints to pass ids through. The translation therefore applies only when the base
   URL equals `KIMI_PLATFORM_BASE_URL`.
4. **WI-4 checkpoint resolved.** Aliases are live-verified (table above). No fallback wording.
5. **WI-5 "add the matching kimi-code/* rows" is a no-op in `modelCatalog.ts`.** Native picker rows come
   from `MODEL_CAPABILITIES` server-side. The Settings catalog gets only the two bare rows.
6. **Native alias and ACP maps land together with `PROVIDERS.kimi.models`.** The lockstep test forces it.
7. **Docs:** `configuration/model-presets.mdx` needs no change; `docs/MODEL-CONTEXT-AUDIT.md` does (the
   additions file names it as its source record).

## Decisions (made here, do not re-litigate)

1. **Canonical ids are `k3.1-pro` and `k3.1-pro-highspeed`.** No `[1m]` suffix variant, because there is no
   smaller tier. Claude Code gets its 1M window from `getClaudeCodeContextPolicyForModel`.
2. **Native aliases are `kimi-code/k3.1-pro` and `kimi-code/k3.1-pro-highspeed`** (live-verified).
3. **Capability class is `frontier`** for all four new ids.
4. **The fallback for both bare K3.1 ids is `claude-sonnet-5-5`**, the same as K3.
5. **K3 stays as it is.** Do not add K3 to `MODEL_DEPRECATIONS`. Do not change `PROVIDERS.kimi.tierModels`.
6. **`getClaudeCodeLaunchModel` gate is a narrow set**, `'kimi-k2.7-code'` plus the keys of the new
   exported `KIMI_PLATFORM_MODEL_IDS`. Do not widen it to every Kimi id: that would change the launch model
   of `k3`/`k3[1m]`, which is out of scope.
7. **Capability values.** `contextWindow: 1048576`; `effortLevels: ['low', 'medium', 'high', 'xhigh', 'max']`
   (canonical levels, the same as K3, translated natively by `kimi-effort.ts`); `costPer1MTokens: 6` for Pro
   and `12` for Highspeed (the average of input and output, the same formula as K3's 9); skills copied
   from the `'k3[1m]'` row (`'context-length': 100`), with Highspeed `speed: 88`. Display names:
   `Kimi K3.1 Pro (1M)` and `Kimi K3.1 Pro Highspeed (1M)` for all four rows.
8. **Cost rows** go immediately above the existing K3 rows in `DEFAULT_PRICING`, with the platform `kimi-`
   rows included because platform-endpoint transcripts record the platform id.

## Requirements

- **FR-1:** `k3.1-pro` and `k3.1-pro-highspeed` launch under the Claude Code route. On the coding endpoint

  `kimi-k3.1-pro-highspeed`.

- **NFR-1:** No new hardcoded model fallback (no-hardcoded-model-fallbacks rule). An unknown id still fails
