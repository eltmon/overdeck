## Glossary

- **Account service:** the Cloudflare Worker in `services/account/` at `https://account.overdeck.ai` (D1 database `overdeck-account`). See `docs/ACCOUNT-SERVICE.md`.
- **Connect service:** the Cloudflare Worker in `services/connect/` (the directory, relay credentials, webhook inbox), one `AccountDirectory` Durable Object (DO) per account. See `docs/CONNECT-SERVICE.md`.
- **Creem:** the payment provider and merchant of record (the legal seller; it collects and remits sales tax). REST API at `https://api.creem.io` (live) and `https://test-api.creem.io` (test mode), authenticated with the `x-api-key` header.
- **Product key:** this repo's name for one Creem product, for example `anywhere_annual_relay`. The catalog (WI-1) maps each key to a Creem product id from configuration.
- **Grant:** a row of the `grants` table, the invite-only allowlist. Its `entitlement` column is `free` or `tester`.
- **Entitlement:** the object `entitlementFor()` returns and `AccountRpc.verifyDevice` / `GET /v1/me` expose. It is the one entitlement API every hosted service asks.
- **Plan:** `Entitlement.plan`: `free`, `tester` (invited testers and the owner) or `anywhere` (a paying subscriber). New here: `anywhere`.
- **Relay add-on:** relay fallback with 50 GB of relay traffic a month, sold only on top of Anywhere, billed in the same charge (OD-3 in `.pan/drafts/pan-2350.md` lines 380–404).
- **Founding price:** $60/yr, annual only, locked while subscribed; ends at the first 500 founding subscribers or at a configured end date, whichever comes first.
- **Paid access:** the time during which a subscription row makes the plan `anywhere` (rule in D-6).
- **Lapse:** the account had a subscription and no row gives paid access any more. `lapsedAt` is when the last paid access ended.
- **Grace period / export window:** the two 30-day stages after `lapsedAt` (D-7). Deletion of hosted data above the free cap happens at the end of the export window.
- **Data holder:** a hosted service that must delete a user's data on account deletion (`AccountDataHolder` in `services/account/src/env.ts`). This PRD adds a `billing` holder.
- **Interstitial page:** a server-rendered page with one link to Creem, used instead of a 303 redirect (D-12).

## Problem

## Verified Creem facts (fetched 2026-11-16 from docs.creem.io)

- `POST /v1/checkouts` body `product_id` (required), `request_id`, `units`, `discount_code`, `customer {id|email}`, `success_url`, `metadata` (key-value); response has `id`, `status`, `checkout_url`.
- Webhooks: header `creem-signature` = lowercase hex HMAC-SHA256 of the **raw body** keyed by the webhook secret. Envelope `{ id: "evt_…", eventType, created_at (ms), object }`. Five attempts (30 s, 5 min, 30 min, 6 h), none after 24 h; automatic retries keep the same `id`. Creem waits 15 s.
- Event types used here: `checkout.completed`, `subscription.active`, `subscription.paid`, `subscription.canceled`, `subscription.scheduled_cancel`, `subscription.past_due`, `subscription.unpaid`, `subscription.expired`, `subscription.update`, `subscription.trialing`, `subscription.paused`. Others (`refund.created`, `dispute.created`, `credits.*`) are acknowledged and ignored.
- Subscription object: `id` (`sub_…`), `status`, `current_period_end_date` (ISO 8601), `product` (object or id), `customer` (object or id), `metadata`, `canceled_at`.
- `POST /v1/subscriptions/{id}/upgrade` body `product_id`, `update_behavior` (`proration-charge-immediately` | `proration-none`); supports single-item subscriptions only.
- `POST /v1/subscriptions/{id}/cancel` body `{ "mode": "immediate" | "scheduled" }` (OpenAPI `CancelSubscriptionRequestEntity`).
- Customer portal: `POST /v1/customers/billing` body `customer_id`, response `customer_portal_link` (feature page "Customer portal"). A second page names `/v1/customer-portal`; see implementation checkpoint IC-1. Cancelling in the portal is immediate.

## Requirements

### Functional

- **FR-1 Billing configuration.** Billing is enabled only when `CREEM_API_KEY`, `CREEM_WEBHOOK_SECRET`, `CREEM_API_BASE` and `CREEM_PRODUCTS` are all present and `CREEM_PRODUCTS` maps all six subscription product keys. Otherwise every billing route answers 503 `{"error":"billing_not_configured"}` (HTML routes: the account page with that notice) and the account page keeps today's Billing text. No value has a hardcoded default.
- **FR-2 Subscribe.** A signed-in account-page user without paid access posts a choice (monthly, annual or founding; relay yes/no) and gets a Creem checkout for exactly one product key, with `request_id` = our checkout id and `metadata` = `{ overdeck_user_id, overdeck_checkout_id }`, and `success_url` = `<PUBLIC_BASE_URL>/account?checkout=done`.
- **FR-3 Founding cap.** Founding checkouts are refused when (founding subscription rows) + (open founding reservations younger than 60 minutes) ≥ 500, or when `FOUNDING_ENDS_AT` is set and now ≥ it. The count check and the reservation insert are one SQL statement.
- **FR-4 Webhook.** `POST /webhooks/creem` verifies the signature over the raw body, deduplicates by event id, maps the event to a user, and upserts the subscription row; events older than the row's last applied event do not overwrite it.
- **FR-5 Paid access and lapse** follow D-6 and D-7, computed from stored timestamps and `deps.now()` at lookup time; no cron flips state.
- **FR-6 Entitlement** has the shape and values of D-5 for every combination of owner, grant and subscription.
- **FR-7 Allowlist.** An account with a non-revoked subscription row is allowed to sign in and its device tokens verify even when it has no unexpired grant (so a lapsed subscriber can always read and export).
- **FR-8 Relay add-on.** A paying user adds or removes the relay; the subscription moves to the paired product with `update_behavior: proration-charge-immediately`, and the row's product key updates from the API response.
- **FR-9 Manage billing.** A user with a subscription row gets a Creem portal link (payment method, invoices, cancel).
- **FR-10 Account page.** Plan and Billing sections render the exact strings of WI-6 for: billing off, never subscribed, checkout pending, paid (with or without relay, founding), past due, lapsed in grace, lapsed in export window, lapsed after deletion date.
- **FR-11 Cancel on deletion and revoke.** Account deletion cancels every live subscription (mode `immediate`) through a `billing` data holder before the rows are deleted; operator revoke marks the rows revoked and cancels them. Failed cancels retry hourly and show on the admin screen.
- **FR-12 Admin screen** shows each grant's billing state and "Founding places sold: N of 500".
- **FR-13 Connect plans.** Connect accepts `anywhere` (as directory plan `anywhere`, or `anywhere_relay` when `entitlement.relay` is true), allows the relay only for `tester` and `anywhere_relay`, and the inbox for every plan except `free`.
- **FR-14 Terms and docs** state prices, the founding rule, what happens at lapse, and the operator runbook (WI-10).

### Non-functional

- **NFR-1** The account service stores only Creem ids (customer, subscription, checkout), product keys, statuses, timestamps and event ids. Never card data, email, name or address.
- **NFR-2** Signature comparison is constant-time; the webhook route has no rate-limit bucket; its body limit is 64 KiB (65,536 bytes); every other route keeps 16 KiB.
- **NFR-3** Tests never hit the network or wait on real time: Creem calls go through the injected `deps.fetch`, time through `deps.now()`. Repo rule (restated): any delay/retry test uses `vi.useFakeTimers()`; none is expected here because retries are cron-driven.
- **NFR-4** Runtime code uses Web APIs only; `cloudflare:workers` stays imported only in `services/account/src/index.ts`; D1 calls use only `prepare/bind/first/all/run/batch` (the unit-test shim implements nothing else).
- **NFR-5** No file passes its `origin/main` line count plus the 1,000-line ceiling of `scripts/lint-file-size.sh`; new logic goes into new modules under `services/account/src/billing/`.
- **NFR-6** Self-hosting stays free: nothing outside `services/` and the docs changes; the git vault backend, federation and SSH hosts gain no gate. `pan vault migrate` is never gated (lapsed accounts keep read access, FR-7).
- **NFR-7** `verifyDevice` stays one D1 statement per call (subscription state joins in as a subquery).

## Decisions

- **D-1 Scope and split.** This issue ships the account-service billing core plus the minimum connect change that makes a paying account behave correctly. Everything separable is split (see header). Test applied: if this issue merges alone and the operator sets the Creem secrets, every account gets a correct entitlement.
- **D-2 One Creem product per combination.** Creem's upgrade endpoint supports single-item subscriptions only, so "billed in the same charge" means six subscription products: `anywhere_monthly`, `anywhere_monthly_relay`, `anywhere_annual`, `anywhere_annual_relay`, `founding_annual`, `founding_annual_relay`. Relay add/remove = upgrade to the paired key. Interval switching (monthly ↔ annual) is not offered in-app (non-goal); the user cancels in the portal and subscribes again.
- **D-3 Configuration.** Secrets: `CREEM_API_KEY`, `CREEM_WEBHOOK_SECRET`. Vars (`wrangler.jsonc`): `CREEM_API_BASE` (`https://api.creem.io`; test deployments use `https://test-api.creem.io`), `CREEM_PRODUCTS` (JSON object, key → `prod_…`), optional `FOUNDING_ENDS_AT` (ISO 8601 date-time; unset = no date limit yet). `FOUNDING_LIMIT = 500` is a code constant (a decided price term, not tuning).
- **D-4 Invite-only stays.** Billing does not open sign-up ([PAN-5455](https://github.com/eltmon/overdeck/issues/5455)). Any allowlisted account (free or tester grant) and the owner may subscribe. FR-7 adds subscribers to the allowed set so a subscriber is never locked out by grant expiry.
- **D-5 Entitlement shape (cross-service contract).** `entitlementFor(grant, billing?)` keeps its name and first parameter; the optional second parameter is the subscription state. Existing fields keep their meaning; new fields are additive:

  ```ts
  export interface Lapse { lapsedAt: number; graceEndsAt: number; deletesAt: number } // ms since epoch
  export interface Entitlement {
    plan: 'free' | 'tester' | 'anywhere';
    storageBytesCap: number;
    maxDevices: number | null;        // directory machines; null = unlimited
    relay: boolean;                   // relay fallback allowed
    inbox: boolean;                   // webhook inbox allowed
    vaultMaxMachines: number | null;  // machines syncing the hosted vault; null = unlimited
    lapse: Lapse | null;              // only when plan is 'free' and a lapsed subscription exists
  }
  ```

  Precedence, first match wins:

  | Case | plan | storageBytesCap | maxDevices | relay | inbox | vaultMaxMachines | lapse |
  | --- | --- | --- | --- | --- | --- | --- | --- |
  | paid access (D-6), any account incl. owner | `anywhere` | max(100 GiB, grant cap ?? 0) | null | product has relay | true | null | null |
  | owner | `tester` | 5 GiB | null | true | true | null | null |
  | active grant `free` | `free` | grant cap ?? 1 GiB | 3 | false | false | 2 | from billing |
  | active grant (any other value) | `tester` | grant cap ?? 5 GiB | null | true | true | null | null |
  | no active grant, non-revoked subscription row | `free` | 1 GiB | 3 | false | false | 2 | from billing |

  GiB = 1024³ bytes, matching `DEFAULT_STORAGE_CAP_BYTES = 5 * 1024 ** 3`. `FREE_STORAGE_CAP_BYTES = 1024 ** 3` and `ANYWHERE_STORAGE_CAP_BYTES = 100 * 1024 ** 3` are new exports.
- **D-6 Paid access rule.** A subscription row gives paid access at time `now` when `revoked_at IS NULL`, `paid_through IS NOT NULL`, and either status ∈ {`active`, `trialing`, `scheduled_cancel`, `canceled`} and `now < paid_through`, or status = `past_due` and `now < paid_through + 7 days` (Creem is retrying the card). `paused`, `unpaid`, `expired` and any unknown status give none. `canceled` keeps access until `paid_through` because the portal cancels immediately and the user has paid for the period. `paid_through` advances only from `subscription.paid` and `checkout.completed` events (whether Creem moves `current_period_end_date` on a failed renewal is unknown, and that must not grant free time), and only forward: `paid_through = max(paid_through, Date.parse(object.current_period_end_date))`. Refunds do not end access automatically (D-16).
- **D-7 Lapse timeline.** When no row gives paid access and at least one non-revoked row has `paid_through`, `lapsedAt` = the latest access end over those rows (`paid_through`, or `paid_through + 7 days` for `past_due`); `graceEndsAt = lapsedAt + 30 days`; `deletesAt = lapsedAt + 60 days`. At `lapsedAt` the plan becomes `free` at once: relay and inbox stop; directory machines already registered keep their rows (connect only refuses new machines past 3, `directory-state.ts` line 324). Hosted vault, enforced by PAN-4297: during grace (`lapsedAt`–`graceEndsAt`) all data stays readable and `pan vault migrate` works, writes follow the free cap (so a vault over 1 GiB is read-only); during the export window (`graceEndsAt`–`deletesAt`) the same access, and the account page warns of deletion; at `deletesAt`, a vault holding more than the free cap is deleted entirely and the account continues as Free; a vault within the cap is kept. Subscribing again at any time before `deletesAt` restores everything. Durations are a recorded auto-decision (the issue gives none).
- **D-8 Webhook mapping.** Creem's copying of checkout `metadata` onto subscription objects is unverified (IC-2), so mapping never depends on it.
  - `checkout.completed` (a checkout object): find our `checkouts` row by `object.request_id` (we send `request_id = checkout_id`; Creem echoes it), else by `object.metadata.overdeck_checkout_id`. Set `completed_at`, `creem_checkout_id`, `subscription_id = idOf(object.subscription)`. No row and no `metadata.overdeck_user_id` naming a user → 200, recorded, ignored (not ours). If `object.subscription` is a full object, also upsert its subscription row for the checkout's user.
  - `subscription.*`: user resolution order (1) `object.metadata.overdeck_user_id` naming a user; (2) the existing `subscriptions` row with id `object.id`; (3) the `checkouts` row with `subscription_id = object.id`; (4) the `checkouts` row named by `object.metadata.overdeck_checkout_id`. Unresolved → 503 `{"error":"unknown_subscription"}` (Creem retries; covers `subscription.paid` arriving before `checkout.completed`) and the event is upserted into `billing_unresolved` (event id, type, subscription id, first/last seen, attempts) so the admin screen shows it (WI-8); a later successful apply of that event id deletes its `billing_unresolved` row.
  - A resolved user that does not exist or has `deleted_at` set, or that is revoked (not the owner, no grant row, no non-revoked subscription row) → 200, recorded, and the subscription row is stored with `revoked_at` and `cancel_requested_at` set so `runPendingCancels` cancels it (in `waitUntil`, then hourly). Amended in review: a payment can land after the billing holder or the revoke ran, so ignoring it left a deleted account charged and re-admitted a revoked one.
  - A product id not in the catalog → 200, recorded, ignored (the Creem store may sell other things). Never map by email.
- **D-9 Idempotency and ordering.** Before applying, look up `billing_events.event_id`; if present → 200 `{"ok":true,"duplicate":true}`. The row upsert and the `billing_events` insert run in one `DB.batch`, so a failed apply is retried by Creem. A row is updated only when the envelope's `created_at` ≥ the row's `last_event_at`; older events are recorded and skipped.
- **D-10 Founding reservation.** Checkout for a founding key runs one batch: expire the user's own open (uncompleted) checkouts, then `INSERT … SELECT … WHERE <count> < 500` (exact SQL in WI-5). Zero rows inserted → the page says "The founding price is no longer available." Concurrent checkouts cannot both take the 500th place (one statement). The only overshoot left is a checkout paid after its 60-minute reservation expired while others took the freed places; that is accepted and visible on the admin screen's "Founding places sold" line. A replaced reservation is expired (`expires_at = now`), never deleted, so a late payment on its Creem URL still maps to the user (D-8).
- **D-11 Cancel paths.** Deletion: new holder `billing` (first in `HOLDER_NAMES`) cancels each of the user's rows whose status is not `canceled`/`expired` with `{ mode: 'immediate' }`; a 404 counts as cancelled; when all are cancelled it deletes the user's `subscriptions` and `checkouts` rows and acks. Operator revoke: `revokeGrant` sets `revoked_at` and `cancel_requested_at` on the user's rows in its existing batch; the admin handler runs `runPendingCancels` in `ctx.waitUntil`, and the hourly cron runs it too. Subscriptions that appear after a revoke or a deletion are cancelled too (D-8), and the cron purges rows of a user that no longer exists once their cancel is done. No refund is issued by code.
- **D-12 Interstitial instead of redirect.** The account page's CSP is `form-action 'self' https://github.com` (`services/account/src/http.ts` line 10). Browsers apply `form-action` to redirects after a form post, and the Creem checkout and portal hosts are not verified. So checkout, portal and relay actions answer 200 with a page holding one link ("Continue to secure checkout on Creem" / "Open billing on Creem"), and only for an `https:` URL. The CSP does not change.
- **D-13 Connect plan vocabulary.** Inside connect the directory plan becomes `ConnectPlan = 'free' | 'tester' | 'anywhere' | 'anywhere_relay'`. It is derived in `verifyIdentity` from the entitlement (`anywhere` + `relay: true` → `anywhere_relay`), stored in the DO meta row `plan` as today, and checked through two helpers in `packages/contracts/src/connect.ts`: `planAllowsRelay` (`tester`, `anywhere_relay`) and `planAllowsInbox` (all but `free`). Old `free`/`tester` behaviour is unchanged.
  **On the wire to machines and phones, `welcome.plan` and `welcome-client.plan` keep the released vocabulary `ConnectWirePlan = 'free' | 'tester'`**: every paid plan is sent as `tester` (`wirePlanOf`), and a new optional field `tier: ConnectPlan` carries the exact plan. Reason, verified in released code: the dashboard gates function on `plan === 'tester'` — inbox trigger creation (`src/dashboard/frontend/src/components/Settings/anywhere/directoryApi.ts` line 33, `inboxAvailable`, used by `AddTriggerDialog.tsx` line 97) and the relay status lines (`src/dashboard/server/services/anywhere-boot.ts` line 133) — and `packages/contracts/src/connect-view.ts` line 11 declares `DirectoryPlan = Schema.Literals(["free", "tester"])`. Sending `anywhere` would take the inbox away from paying users on every released client. Relay use already follows `welcome.relayAllowed` (`directory-client.ts` `relayEntitled`, the phone's `connection.ts` line 135), so a wire `tester` never grants the relay. The account service's `GET /v1/me` does send `plan: 'anywhere'`; released clients only display it (`account-view.ts`, `planLabel` falls back to a neutral text). [PAN-5454](https://github.com/eltmon/overdeck/issues/5454) moves the dashboard to `tier`, `relayAllowed` and `inboxAllowed`.
- **D-14 Deploy order.** Deploy `overdeck-connect` with WI-9 before setting the Creem secrets on `overdeck-account`; until then nobody can buy (FR-1), so the old connect never sees `anywhere`.
- **D-15 Prices on the page.** Display strings live in `services/account/src/billing/catalog.ts` and must match the Creem products; Creem's checkout shows the binding price. This lifts PAN-4959's "no `$` on the page" rule for the Billing section only.
- **D-16 Refunds.** `refund.created` and `dispute.created` are recorded and ignored; a refund does not end paid access by itself (its payload shape is unverified). An operator who refunds a subscription also revokes the account or cancels it in Creem; the docs runbook says so. Recorded as a hazard.

### WI-1 Billing schema, catalog and configuration (FR-1, D-2, D-3, NFR-1)

1. Migration `0004_billing.sql`:

   ```sql

   -- No semicolons inside comments: the Miniflare test splits statements on a semicolon at line end.
   CREATE TABLE subscriptions (
     subscription_id     TEXT PRIMARY KEY,
     user_id             TEXT NOT NULL,

     product_key         TEXT NOT NULL,

     paid_through        INTEGER,

   );
   CREATE INDEX subscriptions_user ON subscriptions (user_id);
   CREATE TABLE checkouts (
     checkout_id       TEXT PRIMARY KEY,
     user_id           TEXT NOT NULL,
     product_key       TEXT NOT NULL,
     founding          INTEGER NOT NULL DEFAULT 0,
     creem_checkout_id TEXT,
     subscription_id   TEXT,

   );

   CREATE TABLE billing_events (

     event_id        TEXT PRIMARY KEY,
   ```
