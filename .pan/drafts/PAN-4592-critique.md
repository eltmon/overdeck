## blocks-the-design: SARIF upload can turn advisory and base-branch runs red

The PRD promises that every advisory run is green and that push scans never fail (PRD lines 69–70 and 117–119). Yet WI-3 appends `github/codeql-action/upload-sarif@v3` with `if: always()` and no `continue-on-error` (PRD lines 383–389). A failed upload therefore fails the sole `semgrep` job even after a successful scan. This is a concrete case for private repositories without GitHub Code Security: [GitHub documents the unavailable-feature error](https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/integrate-with-existing-tools/upload-sarif-file). A red push check is exactly what D4 says must not happen. The smallest fix is to make the upload step non-fatal (`continue-on-error: true`), then add an acceptance case for an upload failure in advisory and push modes. [GitHub's workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) confirms step-level `continue-on-error` keeps the job passing.

## blocks-the-design: Dependabot pull requests are silently unscanned

FR-2 says the workflow scans pull requests, and FR-3 says a blocking PR with a new finding fails the `semgrep` job (PRD lines 65–70). The exact WI-3 YAML instead sets `jobs.semgrep.if: github.actor != 'dependabot[bot]'` (PRD line 344). For a Dependabot PR, GitHub skips the whole job, including the scan, so a new finding cannot fail it. There is no Dependabot exception in the stated requirements or decision record. Remove the job-level condition and cover a Dependabot PR in the workflow acceptance criteria. If SARIF permissions motivated the condition, handle upload eligibility at the upload step; [GitHub documents that Dependabot PRs have read-only tokens by default](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).

## sharpens-framing: CI blocking ignores the configured severity threshold

The existing local SAST gate filters parsed findings through `severityMeetsThreshold(f.severity, semgrep.severity)` before deciding whether blocking fails ([sast-run.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4592/src/lib/cloister/sast-run.ts), lines 277–290); `ERROR` is the default ([semgrep.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4592/src/lib/config-yaml/semgrep.ts), lines 42–50). WI-3 carries only the gate mode into the generated workflow and uses `semgrep scan --error` on every PR finding (PRD lines 335–367), so a WARNING or INFO finding can fail CI while the local `sast` gate passes. If this broader CI policy is intended, state it explicitly in D2 and the new CI documentation so operators know the same `gate: blocking` value has different thresholds. Otherwise, carry `security.semgrep.severity` into the workflow and test the filtering.
