# PAN-4740 — Linked machine over Fly proxy: first request after idle fails with "socket hang up"

**Issue:** [PAN-4740](https://github.com/eltmon/overdeck/issues/4740) (found in the
[PAN-4652](https://github.com/eltmon/overdeck/issues/4652) live check, 2026-11-01).

## Glossary

- **Linked machine** — another Overdeck dashboard this one reaches through a machine link
  (PAN-4645). Requests go over a **secure channel**.
- **Secure channel / `ChannelSocket`** — one Noise-encrypted connection to a linked machine,
  wrapped as a Node `stream.Duplex` that looks like a `net.Socket`
  (`src/lib/anywhere/channel/channel-socket.ts`). Over a Fly route the transport underneath is
  a WebSocket to `wss://<app>.fly.dev/ws/link`, passed through the **Fly proxy**.
- **`LinkAgent`** — the `http.Agent` subclass in `src/lib/anywhere/link-client.ts` whose
  connections are secure channels. One per linked machine (the `agents` map, `agentFor()`),
  `keepAlive: true`, `maxSockets: 4`.
- **Pool / free socket** — after a response completes, a keep-alive `http.Agent` parks the
  connection in `agent.freeSockets` and hands it to the next request (`req.reusedSocket` is
  then `true`).
- **Pool idle expiry** — the idle timeout a free socket carries; when it fires while the socket
  is free, Node's agent destroys the socket (`installListeners` → `onTimeout` in
  `node:_http_agent`).
- **Keep-alive hint** — the `Keep-Alive: timeout=N` response header. Node's HTTP server sends
  `timeout=5` because its default `keepAliveTimeout` is 5000 ms.
- **Stale channel** — a free socket whose far end is already gone, but home has not yet seen the
  close. Writing a request into it produces Node's `socket hang up` error
  (`ConnResetException`, `code: 'ECONNRESET'`) because the socket closes before any response
  byte arrives.
- **`linkFetch` / `linkForward`** — the two request helpers in `link-client.ts` that send
  through the pooled `LinkAgent`. `linkFetch` sends JSON (18 call sites, mostly `GET`, two
  `POST`, one `DELETE`); `linkForward` forwards any method and body
  (`linked-conversation-proxy.ts`, `fleet-add-project.ts`).
- **Safe method** — `GET`, `HEAD`, `OPTIONS`: methods that change nothing on the server
  (RFC 9110 §9.2.1), so resending one cannot cause a duplicate side effect.

## Problem

While the link supervisor reported a Fly-hosted machine `online`, the first `linkFetch` after an
idle spell failed with `socket hang up` (callers mapped it to `machine-unreachable`); an
immediate retry succeeded. Home's conversation-list sync logged
`could not fetch …'s conversations: socket hang up`. The request never reached the VM.

## Root cause (verified 2026-11-02 against Node v22.22.0 and the code at `ac62478a8e5`)

1. **The VM closes idle channels after 5 s.** The dashboard server is a stock
   `NodeHttp.createServer()` (`src/dashboard/server/server.ts`, search
   `const nodeServer = NodeHttp.createServer();`). Nothing sets `keepAliveTimeout`, so it is
   5000 ms (`node -e "console.log(require('http').createServer().keepAliveTimeout)"` prints
   `5000`) and every response carries `Keep-Alive: timeout=5`.
2. **`LinkAgent` never expires a pooled channel.** `LinkAgent` (`link-client.ts` lines 115–132)
   calls `super({ keepAlive: true, maxSockets: 4, ...options })` with no `timeout`. Node's
   `Agent.prototype.keepSocketAlive` computes `agentTimeout = this.options.timeout || 0` and
   applies the server hint only when `serverHintTimeout < agentTimeout`. With `agentTimeout = 0`
   that comparison is always false, so the free socket gets `setTimeout(0)`: no expiry, and the
   server's 5 s hint is ignored. Probe (scratch script, loopback TCP, stock server): after one
   response the free socket's `.timeout` is `0`; with `timeout: 4000` on the agent it is `4000`.
3. **Behind the Fly proxy the VM's close does not reach home before the next request.** Over a
   direct `tcp://` route the VM's close arrives as a FIN, the channel emits `close`, and the
   agent drops it. Over the Fly WebSocket proxy home kept the dead channel in the pool, reused
   it, and the write went nowhere. Node then raised `socket hang up` / `ECONNRESET` with
   `req.reusedSocket === true` (same probe: a server that destroys the socket on the second
   request yields exactly `{ err: 'socket hang up', code: 'ECONNRESET', reused: true }`).
   The Fly proxy's own idle behavior is unknown and does not matter: a client-side expiry
   below 5 s plus one retry on a stale reused channel covers any proxy behavior, and closes the
   same race on `tcp://` routes.
4. **`ChannelSocket`'s idle timer is one-shot.** `ChannelSocket.setTimeout` (channel-socket.ts
   lines 187–200) nulls `this.idleTimer` when it fires, and `touch()` only calls
   `this.idleTimer?.refresh()`, so after one `'timeout'` later traffic never re-arms it. A
   `net.Socket` re-arms on activity (probe: a `net.Socket` with `setTimeout(100)` fired twice
   when data was written after the first timeout; a `ChannelSocket` over `duplexPair()` with a
   dummy handshake fired once). This matters for the fix: a reused channel keeps the 4 s timer
   from the pool while it serves a request (`setRequestSocket` does not reset it when
   `req.timeout` is undefined). If that request is quiet for 4 s, the timer fires mid-request
   (harmless: the socket is not free), and then, back in the pool, `keepSocketAlive` sees
   `socket.timeout === 4000` and does not call `setTimeout` again, so that channel never
   expires. The header comment already promises "`net.Socket` semantics".

## Requirements

- **FR-1** A channel parked in a `LinkAgent` pool expires after at most `LINK_POOL_IDLE_MS`
  (4000 ms) of idleness, and after a shorter time when the peer's keep-alive hint asks for one.
- **FR-2** `ChannelSocket`'s idle timeout re-arms on traffic after it has fired once, matching
  `net.Socket`, until `setTimeout(0)` disables it or the socket is destroyed.
- **FR-3** When a safe-method request (`GET`, `HEAD`, `OPTIONS`) sent by `linkFetch` or
  `linkForward` fails on a reused pooled channel with `ECONNRESET` or `EPIPE` before any
  response arrived, the helper drops that agent's other free channels and resends the request
  exactly once on a fresh channel.
- **FR-4** A non-safe method (`POST`, `PUT`, `PATCH`, `DELETE`, …) is never resent. A failure on
  a freshly opened channel, a failure after a response began, an aborted request, a
  `linkForward` timeout, and a `LinkUnavailableError` are never retried; they reject exactly as
  today.
- **FR-5** `docs/ANYWHERE-ARCHITECTURE.md` describes the pool idle expiry and the one-retry
  rule, and the `link-client.ts` header comment states both.
- **NFR-1** No new dependency, no new config key, no change to the VM server's
  `keepAliveTimeout`, no change to the wire protocol.
- **NFR-2** Tests follow the repo's fake-timer rule: any test that waits on a delay uses
  `vi.useFakeTimers()` and advances it; no test sleeps on real time. Tests that use real
  loopback I/O must not gate that I/O on fake timers.

## Decisions

- **D1 — Fix both layers.** Pool idle expiry (FR-1) removes the common case; the retry (FR-3)
  covers a channel that dies inside the 4 s window (proxy restart, VM restart, network drop).
- **D2 — `LINK_POOL_IDLE_MS = 4_000`.** Below the VM's 5 s `keepAliveTimeout`, equal to what
  Node derives from the `timeout=5` hint (5000 − `agentKeepAliveTimeoutBuffer` 1000). Passed as
  the `http.Agent` `timeout` option, so Node's own `keepSocketAlive` applies it and lowers it
  further for a shorter hint. Not configurable.
- **D3 — Retry safe methods only.** A `POST` that hangs up on a reused channel was almost
  certainly never processed, but "almost" is not enough for `POST /api/fleet/issues/:id/start`
  or a forwarded conversation message: a duplicate starts a second agent or sends a prompt
  twice. After D2 a `POST` reaches a stale channel only inside the 4 s window, and it fails
  loudly as today; the caller decides. `PUT`/`DELETE` are excluded too: Overdeck routes do not
  promise RFC idempotency.
- **D4 — Exactly one retry, after dropping the agent's other free channels.** With
  `maxSockets: 4`, several channels idle together and die together; a bare retry could land on
  a sibling stale channel. `agent.freeSockets` is a documented public property; destroying its
  entries forces the retry onto a fresh channel (or onto a channel that just finished a request,
  which is live).
- **D5 — Retry codes are `ECONNRESET` and `EPIPE`.** `socket hang up` carries `ECONNRESET`;
  `EPIPE` is the write-side form of the same dead pipe. Nothing else is retried.
- **D6 — Fix `ChannelSocket` re-arm in `channel-socket.ts`, not by overriding
  `keepSocketAlive`.** The header already promises `net.Socket` semantics; the fix makes every
  consumer (the VM's HTTP server too) behave as Node expects. On the server side this only
  means a second `'timeout'` can now fire on a socket that survived the first, which is what a
  `net.Socket` already does there.
- **D7 — No live Fly reproduction is required.** The mechanism is reproduced in unit tests with
  loopback TCP and in-memory duplexes. A live check against a Fly machine is optional and not an
  acceptance criterion.

### WI-3 — Resend a safe request once after a stale pooled channel (FR-3, FR-4)

**File:** `src/lib/anywhere/link-client.ts`; test `src/lib/anywhere/__tests__/link-client.test.ts`.
Depends on WI-1 (same files).

Steps:

1. Add, near `agentFor`:

   ```ts
   /** Methods a stale pooled channel may resend: they change nothing on the other machine (PAN-4740 D3). */
   const RETRY_SAFE_METHODS = new Set(['GET', 'HEAD', 'OPTIONS']);
   const STALE_CHANNEL_CODES = new Set(['ECONNRESET', 'EPIPE']);

   /**
    * True when a request died on a reused pooled channel before any response byte: the far end
    * had already closed it. Pure.
    */
   export function isStaleChannelFailure(
     method: string, error: unknown, attempt: { reusedSocket: boolean; responded: boolean },
   ): boolean {
     if (!attempt.reusedSocket || attempt.responded) return false;
     if (!RETRY_SAFE_METHODS.has(method.toUpperCase())) return false;
     const code = (error as NodeJS.ErrnoException | null)?.code;
     return typeof code === 'string' && STALE_CHANNEL_CODES.has(code);
   }

   /** Close every idle channel in a pool; they idled and died together (PAN-4740 D4). */
   function dropIdleChannels(agent: Agent): void {
     for (const sockets of Object.values(agent.freeSockets)) {
       for (const socket of sockets ?? []) socket.destroy();
     }
   }
   ```

2. In `linkFetch`, move the `new Promise(...)` body into a local
   `const attempt = (): Promise<{ status: number; json: unknown }> => …`. Inside it, track
   `let responded = false;` set to `true` first thing in the response callback, and on
   `req.on('error', …)` reject with the error after attaching the facts:
   `reject(Object.assign(error, { [ATTEMPT]: { reusedSocket: req.reusedSocket === true, responded } }))`
   where `ATTEMPT` is a module-level `Symbol('linkAttempt')`; do the same in the `res.on('error')`

## Intersecting repo rules (restated)

- **Fake timers for delay tests** — any test that waits on a delay uses `vi.useFakeTimers()`
  and `vi.advanceTimersByTime()`; never real `setTimeout` waits. Do not gate real loopback I/O
  on fake timers (the WI-1/WI-3 loopback tests use no timers at all; they emit `'timeout'`
  directly).
- **Quality gates** — `npm run typecheck`, `npm run lint`, and `npx vitest run` on the touched
  test files only. Never run the full `npm test` on the host.
- **No `execSync`** in anything reachable from the dashboard server (not needed here).
- **File size** — `link-client.ts` is 324 lines and `channel-socket.ts` 239; both stay well
  under the 1000-line ceiling.
- **Surgical changes** — do not refactor `openLinkSocket`, `ws-linked.ts`, `port-forwards.ts`
  or `channel-agent.ts`; they open their own channels and are not pooled through `LinkAgent`.

## Non-goals

- Raising or changing the VM server's `keepAliveTimeout`.
- WebSocket-level pings on the `/ws/link` transport.
- Retrying non-safe methods, or retrying more than once.
- Making `LINK_POOL_IDLE_MS` configurable.
- Changing `channel-agent.ts` (per-channel agents used by the heartbeat and `channelRequest`).
- A live reproduction against a real Fly machine as an acceptance gate.

## Acceptance criteria

1. (WI-1) A `LinkAgent` free socket after a response from a server with a 60 s keep-alive has
   `.timeout === 4000`; with a 3 s keep-alive it has `.timeout === 2000`; emitting `'timeout'`
   on it destroys it and the next request opens a second connection.
2. (WI-2) A `ChannelSocket` with `setTimeout(1000)` emits `'timeout'` a second time when a write
   follows the first timeout and 1000 ms pass; after `setTimeout(0)` it emits no further
   `'timeout'`.
3. (WI-3) A `linkFetch` or `linkForward` `GET` whose reused channel hangs up resolves with the
   response from a second, fresh channel; a `POST` rejects with `ECONNRESET` and is not resent;
   a hang-up on a fresh channel rejects without a resend.
4. (WI-4) `docs/ANYWHERE-ARCHITECTURE.md` names `LINK_POOL_IDLE_MS`, the 4 s value, the safe
   methods, and states other methods are never resent.
