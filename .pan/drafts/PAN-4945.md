# PAN-4945 — OAuth 2.1 server for `/mcp` (PAN-4927 W-OAUTH1)

**Status:** planned · **Revision:** 1 (2026-11-04) · **Author:** Claude Opus 5.5 (planning agent, `pan plan --auto`)

**Depends on:** W-TOK1 ([PAN-4930](https://github.com/eltmon/overdeck/issues/4930), merged as #4968) and W-MCP1 ([PAN-4931](https://github.com/eltmon/overdeck/issues/4931), merged). Both are on `main` at `9d237e21afd`.
**Followed by:** W-OAUTH2 ([PAN-4946](https://github.com/eltmon/overdeck/issues/4946): approval card and sign-in list in the dashboard) and W-FUN1 ([PAN-4947](https://github.com/eltmon/overdeck/issues/4947): opt-in public `/mcp` through Tailscale Funnel, rate limits, audit).

This PRD lowers the epic's W-OAUTH1 text into executable work items, corrects the line numbers that drifted, and settles every gap the epic left open. Where this PRD and the epic disagree, this PRD wins for PAN-4945 (see "Corrections to the epic").

**Why.** A hosted MCP client (Claude Desktop connectors, Grok Bot, the xAI API) cannot be handed a token file. It expects the MCP authorization flow: discover the authorization server from `/mcp`, register itself, send the user's browser to an authorize page, and swap a code for tokens. Overdeck has no such server today. This item adds it, with one Overdeck twist: the operator approves each sign-in in their own dashboard, because the authorize page may be public and can never carry a dashboard session.

## Glossary

- **MCP (Model Context Protocol):** a JSON-RPC protocol an AI client uses to list and call tools. Overdeck serves it at `POST /mcp` (`src/dashboard/server/routes/mcp.ts`) and through `pan mcp serve` (`src/cli/commands/mcp.ts`).
- **Access token (`odk_`):** an `odk_<64 hex>` credential stored as a SHA-256 hash in `~/.overdeck/access-tokens.json` through `src/lib/access-tokens.ts`. The record shape and its validator live in the leaf module `src/lib/access-token-records.ts`. A `kind: 'token'` record authenticates from an `Authorization: Bearer` header.
- **Scope:** one of `read:events`, `read:state`, `read:conversations`, `read:costs`, `read:settings`, `tell`, `operate`, `approve`, `forward`, `admin` (`ACCESS_TOKEN_SCOPES`, `access-token-records.ts:6-17`). `scopeSatisfies` (`access-tokens.ts:157-160`): `admin` satisfies all, `operate` satisfies `tell`.
- **Root credential:** the internal token (`x-overdeck-internal-token`, which `pan` sends through `callDashboard`) or the root session cookie. `resolveDashboardCredential` returns `{ kind: 'internal-token' }` or `{ kind: 'root-session' }` for them (`dashboard-auth.ts:207-210`).
- **OAuth client:** an MCP client that registered itself through dynamic client registration. Its id is `odc_<32 hex>`. It is public: it has no secret (`token_endpoint_auth_method: "none"`).
- **Sign-in (family):** one approved authorization of one client. It owns exactly one live access token and one live refresh token at a time. Each refresh replaces both. Revoking the family ends the sign-in. "Family" is the OAuth term for the chain of refresh tokens that descend from one authorization.
- **Access level:** the operator-facing name of a scope set for an OAuth sign-in. Four levels, ids `read`, `message`, `operate`, `approve` (table in D-6).
- **Approval:** an in-memory record created when a browser opens the authorize page. It waits for the operator to approve or deny it from the dashboard (or the CLI). It shows an **approval code** such as `KQZT-MWRB`, which the operator compares with the code on the page.
- **Authorization code:** a single-use, 60-second value the authorize page hands to the client's redirect URI after approval. The client swaps it for tokens.
- **PKCE S256:** the client sends `code_challenge = base64url(SHA-256(code_verifier))` to the authorize endpoint, then proves it holds `code_verifier` at the token endpoint. This binds the code to the client that started the flow.
- **Refresh token (`odr_`):** an `odr_<64 hex>` value stored only as a SHA-256 hash in `~/.overdeck/mcp-oauth.json`. It is single use: each refresh returns a new one. A refresh token that was already used (a **retired** refresh token) shows theft, so presenting it revokes the whole family.
- **Issuer:** the base URL of this authorization server, such as `http://localhost:3011` or `https://desk.tailnet.ts.net`. Every metadata URL is built from it.
- **Protected-resource metadata (RFC 9728):** JSON at `/.well-known/oauth-protected-resource[/mcp]` that tells a client which authorization server guards `/mcp`.
- **Authorization-server metadata (RFC 8414):** JSON at `/.well-known/oauth-authorization-server` that lists the endpoints.
- **Dynamic client registration (DCR, RFC 7591):** `POST /oauth/mcp/register` with client metadata; the answer carries `client_id`.
- **Remote request gate:** the global middleware in `src/dashboard/server/remote-request-gate.ts`. It judges only `/api/*` and `/events/*`; `/mcp`, `/.well-known/*` and `/oauth/*` are outside it, so those handlers check their own input.
- **No-loss matrix:** `tests/unit/lib/overdeck/no-loss-matrix.ts`. Every `HttpRouter.add` route in a top-level file of `src/dashboard/server/routes/` needs one row or `tests/unit/lib/overdeck/no-loss-matrix.test.ts` fails.
- **Composer-command manifest:** `packages/contracts/src/composer-commands.generated.ts`, generated from the CLI registry. `npm run lint:slash-commands` fails when a new `pan` subcommand is missing from it.
- **MCP SDK:** `@modelcontextprotocol/sdk` 1.30.1 (`package.json`). Its client helpers in `node_modules/@modelcontextprotocol/sdk/dist/esm/client/auth.js` are the reference client for this PRD.

## Requirements

### Functional

- **FR-1 Record fields.** A `kind: 'token'` record may carry `oauthClientId` (`odc_<32 hex>`), `oauthFamilyId` (32 hex) and `expiresAt` (ISO 8601), all three together or none, never together with the agent fields. `verifyAccessToken` and `listActiveRecordsOfKind` treat a record whose `expiresAt` is at or before now as inactive. `pruneEndedAccessTokens` also removes an unrevoked OAuth record more than `olderThanMs` after its `expiresAt`, and a revoked one more than `olderThanMs` after `revokedAt` + 90 days (the refresh window), so a revocation outlives every refresh token that could see it (review correction, cycles 1-2). The resolved `token` credential carries `oauthClientId` when the record has one.
- **FR-2 Discovery.** `GET /.well-known/oauth-protected-resource`, `GET /.well-known/oauth-protected-resource/mcp` and `GET /.well-known/oauth-authorization-server` answer RFC 9728 / RFC 8414 JSON built from the issuer; an unknown host gets 400.
- **FR-3 Registration.** `POST /oauth/mcp/register` registers a public client (D-4) and answers 201 with RFC 7591 fields.
- **FR-4 Authorize and approval.** `GET /oauth/mcp/authorize` validates the request (D-5), creates a pending approval and answers an HTML page showing the client name, its redirect host and the approval code; the page polls `GET /oauth/mcp/authorize/status` every 2 s and follows the redirect once the operator decides.
- **FR-5 Token.** `POST /oauth/mcp/token` swaps a code for a 30-day access token and a 90-day refresh token (D-7), and rotates on `grant_type=refresh_token` (D-8).
- **FR-6 Revocation.** `POST /oauth/mcp/revoke` ends the family of the presented access or refresh token; `DELETE /api/mcp-oauth/sign-ins/:familyId` ends one family; revoking a family's current access token by any other path (Settings → Access Tokens, `pan token revoke`) ends the family at its next refresh (D-9).
- **FR-7 Operator endpoints.** `GET /api/mcp-oauth/approvals`, `POST /api/mcp-oauth/approvals/:id`, `GET /api/mcp-oauth/sign-ins`, `DELETE /api/mcp-oauth/sign-ins/:familyId`, `POST /api/mcp-oauth/issue` answer only root credentials.
- **FR-8 `/mcp` challenge.** The `/mcp` 401 carries `WWW-Authenticate: Bearer resource_metadata="<issuer>/.well-known/oauth-protected-resource/mcp"`.
- **FR-9 CLI.** `pan mcp oauth issue | list | revoke | pending | approve | deny` call the operator endpoints through `callDashboard`.
- **FR-10 Documentation.** `configuration/mcp.mdx` and `docs/DASHBOARD-AUTH.md` describe the flow, the levels, the endpoints and the CLI.

### Non-functional

- **NFR-1 Secrets.** Refresh tokens are stored only as SHA-256 hashes; access tokens only as the registry's hash. No token appears in a URL, a log line, an activity entry or an error body. Codes and approvals live only in memory. `~/.overdeck/mcp-oauth.json` is mode 0600, written by temp file plus rename.
- **NFR-2 Least privilege (epic NFR-11).** An OAuth record never carries `admin`, `forward`, `read:settings`, `read:costs` or `read:events`; `createAccessToken` refuses them when `oauthClientId` is set.
- **NFR-3 Hostile input.** `client_name`, `state` and every query or form field come from anyone who can reach the port. The authorize page HTML-escapes every value it shows and sends a nonce-based CSP. No endpoint redirects to a URI that was not registered for that client.
- **NFR-4 Async only.** No `execSync`, `spawnSync`, `execFileSync` or new `*Sync` function; file I/O through `node:fs/promises` (repo rules `no-execsync-server`, `prefer-async`).
- **NFR-5 Time in tests.** Expiry is tested through an injected `now()` on the service. Where `verifyAccessToken`'s `Date.now()` must move, tests call `vi.useFakeTimers({ toFake: ['Date'] })` and `vi.setSystemTime(...)`, faking `Date` only, so real file I/O keeps real timers (repo rule `fake-timers-for-retry-tests`; faking `setTimeout` around real I/O hangs on CI).
- **NFR-6 File size.** Every new module stays under 600 lines. `access-tokens.ts` grows by at most 35 lines (to ≤ 590); `dashboard-auth.ts` by at most 3; `server.ts` by at most 4; `routes/mcp.ts` by at most 12; `src/cli/commands/mcp.ts` by at most 8. No allowlist row is raised.
- **NFR-7 Routes.** Each of the 13 new routes is in a top-level file of `src/dashboard/server/routes/` and has a `no-loss-matrix.ts` row. None gets a `route-scopes.ts` row: the public ones are outside the gate (epic NFR-9 exception), and the `/api/mcp-oauth/*` ones stay `admin` by default and are further limited to root credentials in the handler.
- **NFR-8 Effect boundary.** The service and store are plain Promise modules; routes call them with `Effect.promise`. No new exported Effect wrapper; `npm run lint:effect-facades` does not rise.
- **NFR-9 Imports.** `src/lib/mcp/oauth-*.ts` import nothing from `src/dashboard/`. Server-only inputs (trusted origins, the Funnel base, request headers) are passed in by the route module.

## Decisions

- **D-1 Module layout.**
  - `src/lib/mcp/oauth-flow.ts` — pure: levels, validation, PKCE, issuer choice, metadata bodies, error bodies, the authorize page HTML. No I/O, no clock, no randomness (callers pass them in).
  - `src/lib/mcp/oauth-store.ts` — the only door for `~/.overdeck/mcp-oauth.json` (clients and families).
  - `src/lib/mcp/oauth-service.ts` — the in-memory approvals and codes, and every operation the routes call. `createMcpOAuthService(deps)` takes `now` and `randomBytes`; `mcpOAuthService` is the default instance.
  - `src/dashboard/server/routes/mcp-oauth.ts` — the 8 public routes and `issuerFor(request)`.
  - `src/dashboard/server/routes/mcp-oauth-admin.ts` — the 5 operator routes.
  - `src/cli/commands/mcp-oauth.ts` — the CLI verbs.
- **D-2 Issuer comes from an allowlist, never the raw `Host`.** `resolveIssuer({ funnel, hostHeaders, trustedOrigins, funnelBase })`:
  1. A Funnel request (`isTailscaleFunnelRequest`) → `funnelBase` (`triggerFunnelBaseUrl(getTrustedOrigins())`), or `null` when that is `null`.
  2. Otherwise, for each candidate host in order — the `Host` header, then the first comma-separated value of `X-Forwarded-Host` — lowercased: the first trusted origin whose `new URL(origin).host` equals it → that origin (without a trailing slash).
  3. Otherwise `null`. The caller answers 400 `{ "error": "unknown host" }` (metadata routes) or omits the `WWW-Authenticate` header (`/mcp`).
  Why: the SDK requires the advertised `resource` to have the origin the client used (Facts), and `getTrustedOrigins()` already contains `http://localhost:<port>` and `http://127.0.0.1:<port>`, so the epic's separate loopback branch is covered without trusting an arbitrary `Host`.
- **D-3 Levels** (in `oauth-flow.ts`):

  | id | Label | Scopes (`LEVEL_SCOPES`) |
  |---|---|---|
  | `read` | Read only | `read:state, read:conversations` |
  | `message` | Can message | `read:state, read:conversations, tell` |
  | `operate` | Can operate | `read:state, read:conversations, tell, operate` |
  | `approve` | Can approve | `read:state, read:conversations, tell, operate, approve` |

  `OAUTH_LEVELS = ['read', 'message', 'operate', 'approve'] as const` is the order from least to most privilege. `scopes_supported` in both metadata bodies is `["read", "message", "operate", "approve"]`. The token response's `scope` is the granted level id.
- **D-4 Registration rules.** Body is JSON (`Content-Type: application/json`, at most 16 KiB).
  - `redirect_uris`: required array of 1-5 strings, each at most 2,000 characters, parseable by `new URL`, with no fragment, and either `https:` (any host) or `http:` with hostname `127.0.0.1`, `[::1]` or `localhost`. Any other value → 400 `invalid_redirect_uri`.
  - `client_name`: optional string, trimmed, 1-100 characters; absent → `"Unnamed MCP client"`; present but empty or longer → 400 `invalid_client_metadata`.
  - `token_endpoint_auth_method`: absent or `"none"`; anything else → 400 `invalid_client_metadata`.
  - `grant_types`: absent or a subset of `authorization_code`, `refresh_token`; `response_types`: absent or a subset of `code`; else 400 `invalid_client_metadata`.
  - Every other field (`scope`, `logo_uri`, `client_uri`, `software_id`, …) is ignored.
  - Capacity: at most 50 clients. When full after pruning (D-10), the oldest client with no family (active or not) is evicted; when every client has a family, 400 `invalid_client_metadata` with description `"too many registered clients; revoke unused sign-ins"`.
  - 201 body: `{ client_id, client_id_issued_at, client_name, redirect_uris, token_endpoint_auth_method: "none", grant_types: ["authorization_code", "refresh_token"], response_types: ["code"] }`.
- **D-5 Authorize rules.**
  - Step 1, never redirect on failure: `client_id` must name a registered, non-headless client, and `redirect_uri` must match one of its URIs (D-5a). Else answer 400 with the HTML error page "This sign-in link is not valid. Start the sign-in again from your app." and no `Location`.
  - D-5a match: exact string equality; except that for a registered `http:` loopback URI the port may differ (RFC 8252 §7.3, OAuth 2.1 §8.4.2: native apps pick a free port per run). Scheme, host, path and query must still be equal.
  - Step 2, redirect on failure (302 to the requested `redirect_uri` with `error`, `error_description` and `state` when present, RFC 6749 §4.1.2.1): `response_type` must be `code` (else `unsupported_response_type`); `code_challenge` must match `^[A-Za-z0-9._~-]{43,128}$` and `code_challenge_method` must be `S256` (else `invalid_request`); `state`, when present, must be at most 500 characters (else `invalid_request`, without echoing it).
  - `state` is optional (the SDK may send none, Facts); PKCE carries the CSRF protection.
  - `scope` is optional: split on spaces, keep the known level ids, `requestedLevel` = the **lowest** level named; none named → `read`. Unknown names are ignored. Why lowest: a stock SDK client asks for every advertised scope (Facts), and the requested level becomes the default in the approval card (W-OAUTH2), so the safe default must be the least privilege. The operator picks the real level at approval.
  - `resource` and every other parameter are ignored.
  - Then create an approval and answer 200 with the page (D-11).
- **D-6 Approvals and codes (in memory, in the service).**
  - Approval: `{ id: <32 hex>, approvalCode, clientId, clientName, redirectUri, codeChallenge, state?, requestedLevel, createdAt, expiresAt: createdAt + 10 min, status: 'pending' | 'approved' | 'denied', code? }`.
  - `approvalCode`: 8 letters from `ABCDEFGHJKLMNPQRSTUVWXYZ` (no `I`, no `O`) shown as `XXXX-XXXX`.
  - At most 20 pending approvals; creating the 21st drops the oldest pending one.
  - Approve with a level → status `approved` and a code `{ value: base64url(32 random bytes), clientId, redirectUri, codeChallenge, level, expiresAt: now + 60 s, used: false, familyId?: string }`. Deny → status `denied`.
  - Status for the page: `pending` → `{ status: 'pending' }`; `approved` with an unused, unexpired code → `{ status: 'approved', redirect }` (the same redirect on every poll until the code is used or expires); `denied` → `{ status: 'denied', redirect }` with `error=access_denied`; anything else, including an unknown id → `{ status: 'expired' }`.
  - Lazy cleanup on every service call: drop approvals 60 s past `expiresAt`, and codes 10 minutes past `expiresAt` (kept that long only to detect reuse, D-7).
- **D-7 Code exchange (`grant_type=authorization_code`).** Form fields `code`, `client_id`, `redirect_uri`, `code_verifier` are all required (else `invalid_request`). Order:
  1. Unknown or expired code → 400 `invalid_grant`.
  2. A code already used → 400 `invalid_grant` and revoke the family it produced (RFC 6749 §4.1.2).
  3. Mark the code used **before** the remaining checks, so a failed attempt also consumes it.
  4. `client_id` must equal the code's client; `redirect_uri` must equal the code's `redirectUri` exactly (no port leniency here); `base64url(SHA-256(code_verifier))` must equal the challenge (constant-time). Any mismatch → 400 `invalid_grant`.
  5. Mint the access token (`createAccessToken` with `name: "<client name> (OAuth)"` truncated to 200 characters, `kind: 'token'`, `scopes: LEVEL_SCOPES[level]`, `oauthClientId`, `oauthFamilyId`, `expiresAt: now + 30 days`), then write the family `{ familyId, clientId, level, scopes, refreshHash, priorRefreshHashes: [], refreshExpiresAt: now + 90 days, accessTokenId, createdAt }` and set the client's `lastUsedAt`. If the family write fails, revoke the minted access token and answer 500 `server_error`.
  6. 200 `{ access_token, token_type: "Bearer", expires_in: 2592000, refresh_token, scope: <level id> }`.
- **D-8 Refresh (`grant_type=refresh_token`).** Fields `refresh_token` and `client_id` are required. All refresh work runs in one service-level serialized queue, so two refreshes never interleave. Order:
  1. Find the family whose `refreshHash` equals SHA-256 of the presented token (constant-time compare).
  2. Not found, but some family lists it in `priorRefreshHashes` → **reuse**: revoke that family (D-9) and answer 400 `invalid_grant`.
  3. Not found anywhere → 400 `invalid_grant`.
  4. Found, but `revokedAt` is set, or `refreshExpiresAt` is at or before now → 400 `invalid_grant`.
  5. Found, but `client_id` differs → 400 `invalid_grant` (no revocation: a wrong id is not proof of theft).
  6. Found, and the registry record `accessTokenId` exists with `revokedAt` set → the operator revoked it through another path: revoke the family and answer 400 `invalid_grant`. (Rotation never revokes the current `accessTokenId`, D-8.8, so a revoked current token always means an outside revocation. A record that no longer exists was pruned unrevoked after its expiry, so it is not a revocation: a revoked OAuth record is kept until `revokedAt` + 90 days + the prune margin, past the family's `refreshExpiresAt`, FR-1.)
  7. Mint a new access token as in D-7.5, then write the family: `refreshHash` = new hash, `priorRefreshHashes` = old hash prepended and cut to 20 entries, `accessTokenId` = new id; set the client's `lastUsedAt`.
  8. Revoke every other record of the family: `revokeAccessTokensMatching((r) => r.oauthFamilyId === familyId && r.id !== newId)`.
  9. 200 with the same body shape as D-7.6. The family's `refreshExpiresAt` does not move (90 days from the original approval); after that the client must sign in again.
- **D-9 Revoking a family.** Set the family's `revokedAt` and call `revokeAccessTokensMatching((r) => r.oauthFamilyId === familyId)`. Paths: the reuse rule, an outside revocation (D-8.6), a reused code (D-7.2), `POST /oauth/mcp/revoke`, `DELETE /api/mcp-oauth/sign-ins/:familyId`, `pan mcp oauth revoke`. `POST /oauth/mcp/revoke` (form field `token`; `token_type_hint` ignored) finds the family from an `odk_` token through `readActiveAccessTokenRecord` (which ignores `expiresAt`, so an expired access token can still end its sign-in) or from an `odr_` token by current or prior refresh hash, revokes it, and always answers 200 with an empty JSON object.
- **D-10 The store file.** `~/.overdeck/mcp-oauth.json`:

- **D-14 Expiry fires no revocation event.** `onAccessTokensRevoked` is not fired when an OAuth record expires. `/mcp` is stateless, so an expired token fails its next request; a long-lived `/ws/*` socket opened with an OAuth token is not closed at expiry. Accepted (H-4).

## Hazards

- **H-1 Open registration on the LAN.** The dashboard binds `0.0.0.0` and `/oauth/*` is outside the gate, so any LAN peer can register clients and open approvals. Each approval still needs the operator; capacity limits (50 clients, 20 pending approvals) bound the state. Rate limits arrive with W-FUN1 for Funnel only.
- **H-2 Consent phishing.** Anyone can start a sign-in that shows any client name. The page and the card show the approval code and the redirect host, and ask the operator to approve only a code they see on their own screen.
- **H-3 Two files, one sign-in.** A family lives in `mcp-oauth.json` and its access token in `access-tokens.json`. D-7.5 mints first and revokes the minted token if the family write fails; D-8 writes the family before revoking the old access token, so a crash between the two leaves an extra live access token that expires within 30 days and is ended by the next refresh (D-8.8).
- **H-4 Expiry is passive.** No event fires at expiry (D-14); an older Overdeck ignores `expiresAt` (documented).
- **H-5 The composer manifest.** Forgetting `npm run generate:slash-commands` after WI-12 turns `lint:slash-commands` red on CI.
- **H-6 Restart cancels sign-ins in progress.** Approvals and codes are in memory. The page then shows "expired" and the user starts again.
