# PAN-5219 — Phone: tapping an issue notification opens that issue's sheet

**Issue:** [PAN-5219](https://github.com/eltmon/overdeck/issues/5219)
**Planned:** 2026-11-14, `pan plan --auto` (no questions asked; every choice is recorded under Decisions and in the xBRIEF `autoDecisions`).
**Builds on:** PAN-4661 (the read-only phone issue sheet), PAN-5171 (`GET /api/issues/:id`), PAN-4838/PAN-4840 (native notification taps), PAN-2354 (needs-you push classifier).

## Glossary

- **Phone shell** — the React screens under `/m`, in `src/dashboard/frontend/src/components/mobile/`. The browser phone view (PWA) loads them from the machine. The installed phone app (`apps/mobile`, Capacitor) bundles its own copy, so it gets frontend changes only after an app update.
- **Issue sheet** — `MobileIssueSheet` (`src/dashboard/frontend/src/components/mobile/MobileIssueSheet.tsx`), the read-only full-screen issue view at `/m/pipeline?issue=<id>` (PAN-4661).
- **Edge notification** — a "finished", "failed" or "stopped" push built by `edgeNotificationFromEvent` in `src/lib/push/classify.ts`. Today two event types produce one: `agent.heartbeat_dead` (category `stopped`) and `pipeline.journal` entries listed in `JOURNAL_EDGES` (categories `finished`/`failed`).
- **Pending-item notification** — a question or approval push built by `toNotification` from a `PendingItem`. Its URL is `/m?subject=<id>`, which opens the answer card in Needs you.
- **Issue event** — the closed set of things an edge notification reports: `stopped` plus the five `JOURNAL_EDGES` keys. New contract type `PhoneIssueEvent`.
- **Route-scope table** — `ROUTE_SCOPES` in `src/dashboard/server/route-scopes.ts`. A phone credential reaches only the `METHOD path` rows listed there. Anything unlisted needs `admin`, which a phone never has. Phone scopes: `PHONE_TOKEN_SCOPES` in `src/lib/access-tokens.ts` line 112 (includes `read:state` and `read:costs`).
- **Telemetry client routes** — `TELEMETRY_CLIENT_ROUTES` in `packages/contracts/src/telemetry.ts` (from line 188). `route-scopes.test.ts` requires every `ROUTE_SCOPES` path to appear there. `tests/unit/telemetry-docs.test.ts` requires the list to match the `client_route` row of `docs/TELEMETRY.md` (line 190) exactly.
- **No-loss matrix** — `tests/unit/lib/overdeck/no-loss-matrix.ts`. `route-scopes.test.ts` requires every `ROUTE_SCOPES` row to name a surface listed there. `GET /api/issues/:id/check-runs` (line 410) and `GET /api/issues/:id/costs` (line 412) already are.
- **Agents Directory (live scope)** — `GET /api/agent-directory?scope=live` (contract `packages/contracts/src/agent-directory.ts`). It answers one `DirectoryEntry` per agent that is running or waiting now. Each entry has a server-derived `state` (`working | idle | blocked | done | stopped | unknown`), plus `role`, `harness`, `model` and `lastActivityAt`. It is already a `read:state` route and a telemetry client route.
- **Not available** — the sheet's wording for a value it could not read. It is never a blank screen and never a silent omission of a whole section.

## Problem

Tapping a phone notification about an issue ("Failed · MIN-1141", "Finished · PAN-5203") opens Needs you, which usually says "Nothing needs you." The operator wants the tap to show that issue: what it is, its description, and where it stands (phase, state, agent, cost, PR, checks).

Verified root cause:

- `src/lib/push/classify.ts` line 211 (`agent.heartbeat_dead`) and line 231 (`pipeline.journal`) both set `url: PHONE_SHELL_URL` (`'/m'`, line 62), although both know `issueId`.
- The sheet exists but shows only Phase, State, Needs you, Project, Pull request, Agent, Labels, Updated and a tracker link (`MobileIssueSheet.tsx` lines 61-106). It has no description, cost, checks counts or "what happened". When the issue record is missing, it returns early with only a header and title (lines 41-50).
- A phone cannot read `GET /api/issues/:id/costs` or `GET /api/issues/:id/check-runs`. Neither path is in `ROUTE_SCOPES`, and `/api/issues/:id` matches exactly one segment (`route-scopes.test.ts` line 25 asserts `/api/issues/PAN-1/tasks` is `admin`).
- **Android drops the new URL.** `apps/mobile/src/shell/notificationLink.ts` line 28 rejects every pathname except `/m`: `if (parsed.origin !== BASE || parsed.pathname !== '/m') return null;`. `ShellApp.tsx` (lines 127-129) then opens the machine list. The Java side (`PushNotice.java` line 55, `!url.startsWith("/m")`) and the iOS tap path (`notificationTap.ts` `safeMobilePath`, which allows `/m/…`) already accept `/m/pipeline`.

## Requirements

### Functional

- **FR-1** Every edge notification that has an `issueId` carries `url` = `/m/pipeline?issue=<id>&event=<kind>&at=<iso>`. An edge notification without an `issueId` (a dead agent with no issue) keeps `/m`.
- **FR-2** Pending-item notifications (questions and approvals) keep `/m?subject=<id>` (see D-2).
- **FR-3** The installed Android app opens a notification whose URL path is `/m/pipeline` at that path, not at the machine list.
- **FR-4** `readMobileRoute` reads `event` and `at` on `/m/pipeline?issue=…`. The sheet shows a **What happened** line for a known event kind, for example "Agent stopped responding at 19:43" or "Merged PR #5203 at 19:43".
- **FR-5** The sheet shows a **Status** group: phase, derived state, the current agent's role, model and harness, its live, idle or stopped status, and its last activity.
- **FR-6** The sheet shows **Cost**: the issue's total spend from `GET /api/issues/:id/costs` (`resolvedTotalCost ?? totalCost`) and the per-stage split from the response's `byStage`. The frontend only formats server numbers and never adds them up.
- **FR-7** The sheet shows **Pull request and checks**: the PR number (a link), PR state, review decision, and a checks summary (passed, failed, running) linking to the PR's checks page.
- **FR-8** The sheet shows the issue **Description** as Markdown. A long description starts collapsed with a **Show more** button.
- **FR-9** The sheet renders for any issue id: a pipeline issue, a planned or closed issue, another tracker's issue (Linear `MIN-1141`), or an id the tracker cannot answer. Each section shows what it has and "not available" for the rest.
- **FR-10** A phone credential can read `GET /api/issues/:id/costs` (`read:costs`) and `GET /api/issues/:id/check-runs` (`read:state`).
- **FR-11** The sheet stays read-only (D-4661-11): no request other than `GET`. Outside the rendered description, the only controls are Back, Show more/Show less, and outbound links. Inside the description subtree, whatever `ChatMarkdown` renders (inline links, code-block copy buttons) is allowed, and none of it changes server state.

### Non-functional

- **NFR-1** At 390×844, every button and link in the sheet is at least 44×44 CSS px. The page never scrolls horizontally. Everything inside `[data-testid="mobile-issue-description"]` (inline links, code-block copy buttons) is exempt (D-9).
- **NFR-2** A failed read (403 from an older machine, 500, malformed JSON) is not retried and stops polling. It shows its section's "not available" text.
- **NFR-3** The sheet adds at most three background reads per open sheet: costs (30 s), check-runs (60 s) and the live agents directory (15 s). Each stops after an error.

## Decisions

- **D-1 URL shape.** `phoneIssueSheetPath(issueId, event?)` in `packages/contracts/src/phone-notifications.ts` builds `/m/pipeline?` + `new URLSearchParams({ issue, event, at })`, omitting `event`/`at` when no event is given. The server classifier and the phone router both use it, so the two cannot drift. Example: `phoneIssueSheetPath('PAN-5', { kind: 'stopped', at: '2026-11-13T19:43:00.000Z' })` → `/m/pipeline?issue=PAN-5&event=stopped&at=2026-11-13T19%3A43%3A00.000Z`.
- **D-2 Questions and approvals keep `/m?subject=`.** The issue says "every notification that has an issueId", but its Problem and Tests sections name only the stopped and step notifications. A question needs the answer card, and the sheet is read-only, so sending a question to the sheet would remove the operator's way to answer it. This is a deliberate, recorded narrowing.
- **D-3 What happened comes from the URL, not a journal read.** No route exposes the pipeline journal, and the notification already knows the event. `event` is parsed against the closed `PhoneIssueEvent` list, and an unknown value is dropped, so URL text never reaches the screen. `at` comes from `entry.at ?? event.timestamp` for journal edges and `event.timestamp` for heartbeat edges. It never uses the `stamp` fallback at `classify.ts` line 223, which can be a commit SHA. An `at` that `Date.parse` rejects shows the label without a time.
- **D-4 Event labels** (in contracts, `PHONE_ISSUE_EVENT_LABELS`): `stopped` → "Agent stopped responding"; `verification.started` → "Work finished; verification started"; `merge.completed` → "Merged"; `merge.failed` → "Merge failed"; `review.stall-escalated` → "Review stalled and needs you"; `conflict.repair-escalated` → "Conflict repair needs you". When the kind is `merge.completed` and the sheet knows a PR number, the line reads "Merged PR #<n>".
- **D-5 Event time.** `formatEventTime(at, now)`: if `at` falls on the same local calendar day as `now`, `new Date(at).toLocaleTimeString(undefined, { hour: '2-digit', minute: '2-digit' })`; otherwise `new Date(at).toLocaleString(undefined, { month: 'short', day: 'numeric', hour: '2-digit', minute: '2-digit' })`. The line is `<label> at <time>`. Tests build the expected string with the same calls, so they do not depend on the time zone.
- **D-6 Agent and its live status.** The sheet reads `GET /api/agent-directory?scope=live`, whose `state` is server-derived. CLAUDE.md requires one module to answer liveness and idleness, so the frontend never infers idleness itself.
  - **Rule:** among entries with `kind === 'agent'` whose `issueId` matches case-insensitively, pick the one with the latest `lastActivityAt` (null sorts last; ties keep response order). Show `<role> · <model> · <harness>`, then `<status> · active <formatRelativeTime(lastActivityAt)>`. Status words: `working` → "Live", `idle` → "Idle", `blocked` → "Waiting for you", `done` → "Done", `stopped` → "Stopped", `unknown` → "Status not available". When more than one live agent matches, append " (+N more)".
  - **No live entry:** when the directory answered but has no entry for the issue, fall back to the store's agents (`selectAgents`) for that issue. Pick the latest `lastActivity ?? startedAt`, show `<role> · <model> · <harness ?? runtime>`, and status "Stopped".
  - **Directory failed or still loading:** use the same store fallback. Status comes from `classifyDashboardAgent(agent)` (`src/dashboard/frontend/src/lib/agent-classifier.ts`): `active` → "Live", otherwise "Stopped".
  - **No agent anywhere:** "No agent".
- **D-7 Cost.** The sheet calls its own `useQuery` (key `['mobile-issue-costs', ID]`, `retry: false`, `refetchInterval: (q) => q.state.status === 'error' ? false : 30_000`) on `/api/issues/<encodeURIComponent(id)>/costs`. It does not change the desktop `useIssueCostsQuery`. A response is valid only when `typeof totalCost === 'number'`; anything else counts as an error.
  - **Headline:** `resolvedTotalCost ?? totalCost`, formatted `$X.XX` (`toFixed(2)`).
  - **Zero:** a headline of 0 renders "No spend recorded".
  - **Error:** "Cost not available".
  - **Stage line:** `byStage` entries with `cost > 0`, sorted by cost descending. Show at most 4 as `<stage> $X.XX` joined with " · ", plus " · +N more" when there are more. Stage keys are the server's raw `session_type` values (`work`, `review.correctness`, `plan`, …), shown as-is.
- **D-8 PR and checks.**
  - **PR source:** `derived.pr` from the store first. When it is absent, use `checkRuns.pr` from `GET /api/issues/:id/check-runs` (key `['mobile-issue-check-runs', ID]`, `retry: false`, 60 s, stops on error).
  - **PR state:** `derived.pr.merged || derived.state === 'merged'` → "Merged"; `derived.state === 'closed'` → "Closed"; any other `derived.pr` → "Open". A PR known only from check-runs shows no state.
  - **Review:** from `derived.pr.reviewState`. `approved` → "Approved", `changes-requested` → "Changes requested", `review-requested` → "Review requested", `commented` → "Commented", `none` → "No review yet".
  - **Checks:** a valid check-runs response has numeric `summary.passed`, `summary.failed`, `summary.running` and `summary.pending`. With `summary.total > 0` it shows `<passed> passed · <failed> failed · <running + pending> running`, linking to `<prUrl>/checks`; `total === 0` shows "No checks reported". When check-runs failed or is invalid, fall back to `derived.pr.checks`: `green` → "Checks passed", `red` → "Checks failed", `pending` → "Checks running". With neither source, show "Checks not available".
  - **No PR:** no PR from either source renders "No pull request".
- **D-9 Description.** Rendered with `ChatMarkdown` (`src/dashboard/frontend/src/components/chat/ChatMarkdown.tsx`, `cwd={undefined}`), which the phone's conversation view already uses and which sanitizes HTML.
  - **Collapsing:** `shouldCollapseDescription(text)` is true when the text has more than 4 lines or more than 280 characters. When true, the body wrapper has `max-h-24 overflow-hidden` and `data-collapsed="true"`, and a `button` reads **Show more** or **Show less** (`min-h-11 min-w-11`). jsdom cannot measure overflow, so the rule is text-based.
  - **Empty states:** an empty or missing `description` renders "No description." A missing issue record renders "Description not available."
  - **Tap targets:** inline links and `ChatMarkdown`'s code-block copy buttons inside the description subtree are exempt from the 44 px rule and from the FR-11 control list. The Show more/Show less button sits outside that subtree.
  - **Headings:** the sheet's own section labels use `dt`/`p` elements, never `h2`, so the title stays the only sheet-level `h2`. Markdown headings inside the description subtree are fine.
- **D-10 No early return.** `MobileIssueSheet` renders every section whether or not `useIssueRecord` found the issue. With no record, the title is `IssueHeaderTitle` (existing). Derived state is `derivedByIssueId[issueId] ?? derivedByIssueId[issueId.toUpperCase()]`. The phase is `getPipelineIssuePhase(derived, null)`. The description is "Description not available." Project, Labels, Updated and the tracker link render only with a record.
- **D-11 Section order.** Header (Back + id); title; **What happened** (only with an event); a `dl` with Phase, State ("Not available" when no derived state), Needs you (unchanged rule), Agent; **Cost**; **Pull request** and **Checks**; **Description**; then Project, Labels, Updated; then **Open in tracker**.
- **D-12 Route scopes.** Add `{ method: 'GET', path: '/api/issues/:id/check-runs', scope: 'read:state' }` and `{ method: 'GET', path: '/api/issues/:id/costs', scope: 'read:costs' }` directly after the `/api/issues/:id` row. Add both paths to `TELEMETRY_CLIENT_ROUTES` in sorted position, after `"/api/issues/:id"` and before `"/api/issues/resource-allocated"`: first `"/api/issues/:id/check-runs"`, then `"/api/issues/:id/costs"`. Add them to the `docs/TELEMETRY.md` `client_route` row in the same order. `check-runs` at `read:state` lets any `read:state` credential, not only phones, trigger the route's live `gh api` call. It is a read with a 15 s timeout, so the risk is accepted, but the item is flagged for inspection.
- **D-13 Android link parser.** `parseNotificationLink` accepts pathname `/m` or any pathname starting with `/m/`, the same rule as iOS `safeMobilePath`. It returns `parsed.pathname + parsed.search`. `/mx` and `/m/../settings` (which resolves to `/settings`) stay rejected.
- **D-14 Older installed apps.** The server change takes effect on the next dashboard deploy, but the installed app's screens and link parser change only with an app update.
  - **iOS before the update:** `safeMobilePath` keeps `/m/pipeline`, so the tap should open the old PAN-4661 sheet. That holds if the Capacitor server serves `/m/pipeline` cold, as the WI-3 checkpoint verifies.
  - **Android before the update:** the tap opens the machine list (the old parser rejects `/m/pipeline`) until the app updates.
  - **Browser phone view:** gets everything at once.
  - The docs say this. A `/m?issue=` URL would avoid the Android gap, but the issue names `/m/pipeline?issue=<id>` in its required behavior and tests, so the plan follows the issue.
- **D-15 ntfy.** `ntfy-provider.ts` line 47 appends `n.url` to the optional `clickBaseUrl` Click header. The new path adds the issue id, which is already in the public title (D-8 of PAN-2354), plus the event kind and time. No conversation name or question text is added, so the PAN-2354 public-title rule still holds.
- **D-16 Playwright.**
  - **New spec:** `tests/pan-5219-mobile-issue-sheet.spec.ts` follows the PAN-4661 seeding pattern (snapshot cache plus closed `/ws/rpc`) and stubs the three reads with `page.route`.
  - **PAN-4661 spec:** it asserts that `/m/pipeline` makes no `/api/` request beyond `/m`'s baseline. Its sheet step now also reads `/api/issues/<id>/costs`, `/api/issues/<id>/check-runs` and `/api/agent-directory`.
```ts
/** What an issue notification reports (PAN-5219 D-3): `stopped` plus the notifying pipeline-journal entry types. */
export type PhoneIssueEvent =
  | "stopped"
  | "verification.started"
  | "merge.completed"
  | "merge.failed"
  | "review.stall-escalated"
  | "conflict.repair-escalated"

export const PHONE_ISSUE_EVENT_LABELS: Readonly<Record<PhoneIssueEvent, string>> = {
  stopped: "Agent stopped responding",
  "verification.started": "Work finished; verification started",
  "merge.completed": "Merged",
  "merge.failed": "Merge failed",
  "review.stall-escalated": "Review stalled and needs you",
  "conflict.repair-escalated": "Conflict repair needs you",
}

/** The kind when `value` is a known event, else null; never throws. */
export function parsePhoneIssueEvent(value: unknown): PhoneIssueEvent | null {
  // hasOwnProperty, not Object.hasOwn: the frontend compiles contracts with lib ES2020.
  return typeof value === "string" && Object.prototype.hasOwnProperty.call(PHONE_ISSUE_EVENT_LABELS, value)
    ? (value as PhoneIssueEvent)
    : null
}

/** `/m/pipeline?issue=<id>[&event=<kind>&at=<iso>]`: the phone issue sheet (PAN-5219 D-1). */
export function phoneIssueSheetPath(issueId: string, event?: { kind: PhoneIssueEvent; at: string } | null): string {
  const params = new URLSearchParams({ issue: issueId })
  if (event) {
    params.set("event", event.kind)
    params.set("at", event.at)
  }
  return `/m/pipeline?${params.toString()}`
}
```

Tests: the path with and without an event (exact strings from D-1), an id with a dot or space, encoded and round-tripping through `URLSearchParams`; `parsePhoneIssueEvent` returns every key, and returns null for `"toString"`, `"__proto__"`, `""`, `null` and `"merge"`.

## Planning Q&A

Auto mode: no questions were asked. The questions a normal session would have asked, and the defaults taken:

- **Should question/approval notifications with an issueId also open the sheet?** Options: all notifications, or edge notifications only. Chosen: edge notifications only (D-2). The sheet is read-only, and a question must stay answerable.
- **Where does "What happened" come from?** Options: URL parameters, or a new journal read route. Chosen: URL parameters (D-3). No route exists, and the notification knows the event.
- **URL `/m/pipeline?issue=` (breaks old Android builds until update) or `/m?issue=` (compatible)?** Chosen: `/m/pipeline?issue=`, as the issue specifies, plus the Android parser fix and a docs note (D-13, D-14).
- **How is live/idle decided?** Options: frontend inference from runtime activity, or the server's Agents Directory state. Chosen: the Agents Directory (D-6), per the one-liveness-module invariant.
