# PAN-4507 — Issue poller: back off when nothing changes

**Issue:** https://github.com/eltmon/overdeck/issues/4507
**Planned:** 2026-10-04 (auto mode, `pan plan --auto`) against `main` @ `b8853b45510`

## Glossary

- **Issue poller** — `IssueDataService` in `src/dashboard/server/services/issue-data-service.ts`. It polls each tracker (GitHub, Linear, Rally) on its own `setTimeout` chain and pushes changed issue lists to the read model.
- **Poll interval / cadence** — the delay `scheduleNext(tracker)` arms before the next poll. Stored as `TrackerState.currentInterval` and shown as `pollInterval` in `GET /api/cache-status`.
- **`POLL_INTERVALS`** — the per-tracker `{ default, min, max }` table. GitHub is `{ default: 30_000, min: 15_000, max: 300_000 }`.
- **Rate-limit backoff** — the existing extra delay from `CacheService.getBackoffMs(tracker, default)` (0, 1×, 4× or 9× the default, by quota remaining).
- **Suspension** — the existing `CacheService.getSuspensionMs(tracker)`: when quota is exhausted the poll waits until the reset time (capped at 1 h).
- **Quota pause** — the existing PAN-4264 PAT REST pause, `patRestPauseDelayMs()`. GitHub only.
- **Unchanged poll** — a scheduled GitHub poll where `issuesChanged(allIssues, oldData)` returns `false`. With ETags this is the case where every repo answered 304.
- **Unchanged streak** — the count of consecutive unchanged scheduled GitHub polls. New field `TrackerState.unchangedStreak`.
- **Unchanged backoff** — the new delay `min(default × 2^streak, max)`.
- **Cadence reset** — the new public method `IssueDataService.resetPollCadence(tracker)`: zero the streak and, when the armed timer fires later than `default` from now, re-arm it at `default`. It never polls and never touches the cache, so ETags survive.
- **Interval reason** — the new `TrackerState.intervalReason`, one of `default`, `unchanged-backoff`, `rate-limit-backoff`, `rate-limit-suspended`, `quota-pause`. It names the term that produced the armed delay.

## Problem

`IssueDataService` polls GitHub every 30 s. Each poll makes two sequential `octokit.paginate(octokit.issues.listForRepo, …)` calls per configured repo (open, then recently closed) in `pollGitHubRepos()`. With four repos that is 8 requests per 30 s, about 960 per hour. ETag 304s are free against the REST quota, but the requests still fill the quota ledger and logs. The interval only grows under rate-limit pressure (`getBackoffMs`), never when nothing changed.

## Requirements

- **FR-1** — When every scheduled GitHub poll is unchanged, the armed interval follows 30 s → 60 s → 120 s → 240 s → 300 s and stays at 300 s.
- **FR-2** — A scheduled GitHub poll that returns changed data resets the streak; the next interval is 30 s.
- **FR-3** — An operator refresh (`POST /api/trackers/refresh`, any `invalidateTracker` caller, `POST /api/cache/clear`) resets the streak; the next interval is 30 s.
- **FR-4** — A `GET /api/issues` request calls `resetPollCadence('github')`: the next GitHub poll fires no later than the rate-limit-adjusted interval at streak 0 (30 s when there is no rate-limit pressure).
- **FR-5** — A verified GitHub `issues` webhook for a tracked repo calls `resetPollCadence('github')`.
- **FR-6** — `GET /api/cache-status` reports per tracker `pollInterval` (existing), `pollIntervalReason`, `unchangedStreak`, and `nextPollAt` (ISO string or `null`).
- **FR-7** — Rate-limit backoff, suspension and quota pause keep their current effect. When both backoffs apply, the longer delay wins.

## Decisions

1. **GitHub only.** The streak advances only for GitHub. `unchangedStreak` exists on every `TrackerState` (default 0), so Linear and Rally always compute `unchanged-backoff` = default and behave exactly as today. Reason: the issue scopes GitHub; Linear has no webhook reset and a 5-minute full-refresh safety net, so backing it off is a separate decision.
2. **Formula.** `unchangedMs = min(default × 2^streak, max)`. `rateMs = min(max(default + rateBackoffMs, min), max)` (today's formula). `delay = max(unchangedMs, rateMs)`. Then the existing overrides in the same order: suspension (`min(suspendMs, 3_600_000)` replaces the delay), then quota pause (`max(delay, quotaPauseMs)`, GitHub only).

   | streak | unchangedMs |
   |---|---|
   | 0 | 30 000 |
   | 1 | 60 000 |
   | 2 | 120 000 |
   | 3 | 240 000 |
   | ≥4 | 300 000 |

3. **Reason precedence.** `quota-pause` if the quota pause set the final delay; else `rate-limit-suspended` if suspension applied; else `rate-limit-backoff` if `rateMs > default` and `rateMs >= unchangedMs`; else `unchanged-backoff` if `unchangedMs > default`; else `default`. Rate limit wins ties because quota pressure is the stronger signal. The cache-read `catch` path keeps `delay = default`, reason `default`. Five values, not three: suspension and quota pause exist, and reporting them as "default" would mislead.
4. **Where the streak moves.** Only in the `scheduleNext` timer callback for `github`, from the value `pollGitHub()` now returns: `true` (changed) → streak 0; `false` (unchanged) → streak + 1; `null` (skipped: PAT pause or no GitHub config) or a thrown error → streak unchanged. The startup poll in `start()` and the poll inside `invalidateTracker` do not advance it. So the first interval after start is always 30 s, even when the startup poll is all 304s. A per-repo error that shortens `allIssues` makes `changed` true and resets — accepted, it errs toward fresher data.
5. **Reset during an in-flight poll.** `TrackerState.cadenceGeneration` (number, starts 0) increments on every `resetPollCadence`. The timer callback captures it before polling; if it changed by the time the poll returns, the callback skips the streak increment. This covers a webhook that arrives while a poll is fetching pre-edit 304s.
6. **Reset semantics.** `resetPollCadence(tracker)`: streak = 0, `cadenceGeneration++`. If `started` and a timer is armed and `nextPollAt - Date.now() > POLL_INTERVALS[tracker].default`, clear it and call `scheduleNext(tracker)`. Otherwise leave the timer alone. Repeated resets therefore never postpone a poll that is already due within 30 s.
7. **Webhooks do not call `invalidateTracker`.** It deletes ETags; a webhook burst would turn every poll into full 200 fetches. Webhooks use `resetPollCadence`.
8. **Operator refresh keeps using `invalidateTracker`** (full re-fetch is what the operator asked for). It sets `unchangedStreak = 0` before its `scheduleNext`. `clearCacheAndRefresh()` gains a `resetPollCadence(tracker)` per tracker at its end, so its new data is followed by a 30 s cadence.
9. **"Opening the issue list" = `GET /api/issues`.** The Kanban board gets issues over the WS read-model snapshot, not HTTP. Hooking `ws-rpc.ts` `getSnapshot` is out: that file is at 1220 of a 1221-line cap. The operator's Refresh button already resets. Worst-case staleness for a board opened mid-backoff is 300 s, the same as the existing `max`.
10. **Webhook event set.** Only `issues` resets cadence. `check_run`, `status`, `pull_request*` fire constantly and would pin the cadence at 30 s. `issue_comment` does not change the issue-list fields shown on the board.
11. **`scheduleNext` clears any armed timer before arming** (`if (state.timer) clearTimeout(state.timer)`), and the timer callback sets `state.timer = null; state.nextPollAt = null` as its first statement. This enforces NFR-4 and fixes the pre-existing double-arm when `invalidateTracker` runs during an in-flight poll.
12. **Line budget.** The pure status-mapping helpers move to a new module first (WI-1), freeing ~70 lines. The delay math goes in a new pure module (WI-2), so the service gains only call sites.
