# PAN-4301 — Awareness feed: transitions instead of a live conversation index; one card per gauntlet run

**Issue:** [PAN-4301](https://github.com/eltmon/overdeck/issues/4301) · **Sibling (split out during planning):** [PAN-4306](https://github.com/eltmon/overdeck/issues/4306) — telemetry leaves `activity.entry` at the emit site, blocked by [PAN-4300](https://github.com/eltmon/overdeck/issues/4300).

References verified against `feature/pan-4301` at `b3b30e61bd5` (2026-09-28). Line numbers can drift; each reference also quotes a string to grep for.

Everything in this document is a selector over rows and events that already exist. It adds **no** table, column, stored status or server endpoint.

## Glossary

- **Awareness rail** — the right-hand column of the Command Deck, rendered by `SessionFeedSidebar` with `scopeSwitcher` (`src/dashboard/frontend/src/components/CommandDeck/index.tsx:1573`, grep `heading="Awareness"`). It has three **scopes** (Needs you / Project / Global) and, inside Project and Global, **tabs**.
- **Tab** — a filter over the merged feed: All, Chats, Activity (Git, Files and Comments are removed from the bar by this issue).
- **Feed entry** — one card in the rail. Types in `src/dashboard/frontend/src/components/sessionFeed/types.ts` (`SessionFeedEntry` union, grep `export type SessionFeedEntry =`). Every entry has one `timestamp`; the rail sorts and buckets by it (`mergeSessionFeedEntries`, `formatBucketLabel`).
- **Conversation row** — one element of `GET /api/conversations` (the enriched list from `getEnrichedConversationList`, `src/lib/overdeck/conversation-list.ts:264`, grep `...row,`). It spreads the stored `LegacyConversation` columns (`src/lib/overdeck/conversations.ts:236`) and adds `sessionAlive`, `isWorking`, `pendingInputCount`, `lastActivityAt` and the lane fields below.
- **Root conversation** — a conversation row that is not a lane.
- **Lane** — a conversation row with non-null `gauntletRun` **and** non-null `laneKey` (the same test `laneEnrichment` uses, `conversation-list.ts:88`). Lane rows also carry `laneRole` (`builder | critic | verifier | play | orchestrator`), `laneIteration`, `laneReport {seq, at, status, verdict}`, `laneVerdict` (critics/verifiers), `laneLatestVerdict` (builders), `criticOfConversationId`, `parentConversationId`, `parentConversationName`, and an explicit `projectKey` (lane launch refuses without a project, `src/lib/lanes/launch.ts:333-334`, and stores `projectKey: config.projectKey` at `:483`).
- **Gauntlet run** — the set of lanes that share `(projectKey, gauntletRun)`. Run keys repeat across projects, so the project is part of the key.
- **Run card** — the new feed entry kind `gauntlet_run`: one card per gauntlet run.
- **Lane activity (D10)** — the derived state `failed-to-start | needs-you | working | idle | starting | stopped`, first match wins, today computed by the private `activityOf` in `src/lib/lanes/views.ts:117` (grep `/** D10, first match wins. */`) with `STARTING_GRACE_MS = 3 * 60_000` at `:26`.
- **Singleton agent** — `flywheel-orchestrator` and `sequencer-runner`, today the module-private `SINGLETON_AGENT_IDS` in `src/lib/agents/identity.ts:49`. The `sequencer-runner` conversation row has a null title and renders as the "No messages yet" card.
- **Lifecycle timestamp** — the time of a recorded conversation fact: `endedAt` when `status === 'ended'` and `endedAt` is set, otherwise `createdAt`.
- **Recency timestamp** — `lastActivityAt ?? lastAttachedAt ?? createdAt` (today's `lastMessageDate`, `useConversationFeed.ts:42`). `lastActivityAt` is the transcript file mtime and moves on every write, so it is **not** a transition.
- **Window** — 24 hours before "now" (`FEED_WINDOW_MS = 24 * 60 * 60 * 1000`).
- **News / telemetry** — news answers "does the operator need to act, did something ship, fail or finish"; telemetry is progress detail. Telemetry belongs in `activity.detailed`; moving it there is PAN-4306, not this issue.

## Problem

See Appendix A for the full evidence. In short: the Chats source is a live index of every conversation dated by transcript mtime, so every working conversation — each gauntlet lane — jumps back to "Just Now" on each 30 s poll and nothing ages out; the `sequencer-runner` singleton shows as a blank "No messages yet" card; Project scope filters by issue id only, so issue-less lane conversations never show there; and the Git, Files and Comments tabs never show anything.

In scope: issue Wanted items 1, 2, 3, 5 and 6 — conversation entries dated by transitions, one card per gauntlet run, a windowed Chats index, singleton exclusion, a derived status dot, per-issue activity collapse in the view, project scope by conversation, hidden empty tabs, and the docs for all of it.

Out of scope (Non-goals):
- Moving telemetry out of `activity.entry` at emit sites, the prdGate "superseded failure" rule, and the "one merge card" rule — **PAN-4306** (blocked by PAN-4300).

## Requirements

### Functional

- **FR-1** In the All tab, a conversation entry's `timestamp` is its lifecycle timestamp, never `lastActivityAt`. The card labels the time `started` (from `createdAt`) or `ended` (from `endedAt`).
- **FR-2** The All tab includes a conversation entry only when its lifecycle timestamp is inside the window.
- **FR-3** The Chats tab is a windowed recency index: it includes a conversation entry when `sessionAlive` is true or its recency timestamp is inside the window, re-dates it to the recency timestamp (label `active`), and sorts newest first.
- **FR-4** No tab renders a conversation row whose `name` or `issueId` (lower-cased) is in `SINGLETON_AGENT_IDS`.
- **FR-5** The conversation card's status dot is derived from the row: `waiting` when `sessionAlive && pendingInputCount > 0`, else `active` when `sessionAlive && isWorking`, else `idle`.
- **FR-6** Lane rows never render as individual conversation cards. They are grouped into one `gauntlet_run` entry per `(projectKey, gauntletRun)`.
- **FR-7** A run card shows: title `<RUN KEY UPPER-CASED> · <projectKey>`; a counts line; a `latest:` line; a `launched from` line; a state dot. Its `timestamp` is the time of the latest notable event (FR-8), never a `lastActivityAt`.
- **FR-8** The latest notable event of a run is the newest of these per-lane facts: a report (`laneReport.at`), a failed start (`spawnError` set, dated `createdAt`), an end (`status === 'ended'` with `endedAt`), a launch (`createdAt`). Ties break in the order report > failed start > end > launch.
- **FR-9** The counts line lists, in this order and only when non-zero, role counts (`builder, critic, verifier, play, orchestrator`, pluralised with `s`) then activity counts (`needs you, failed to start, working, idle, starting, stopped`), joined with ` · `. Example: `6 builders · 6 working`; with one lane waiting: `6 builders · 1 needs you · 5 working`.
- **FR-10** A run card is included in All and Chats while at least one of its lanes has `sessionAlive` or its latest event is inside the window. It is dated by FR-8 in both tabs.
- **FR-11** Clicking a run card opens `/conv/<orchestratorName>` (the parent conversation, FR-7 rule in WI-6), or the first lane's conversation when no parent is known.
- **FR-12** A run card has an expand control. Expanded, it lists the run's lanes (builders by key, each followed by the critics/verifiers that judge it, then the rest by role order and key), each linking to `/conv/<name>`. The first expand fetches `GET /api/lanes?run=<run>` once (no polling), keeps only lanes whose `projectKey` equals the card's, and shows git facts beside matching lanes and archived lanes in a muted list. A fetch failure shows the lanes without git facts and the text `Lane details unavailable`.
- **FR-13** The lane activity rule (D10) exists once, as a pure function in `@overdeck/contracts`, used by both `src/lib/lanes/views.ts` and the run-card selector.
- **FR-14** In the All and Activity tabs, activity entries that name an issue collapse to one entry per issue (case-insensitive): the newest entry's headline, level, link and timestamp, plus `stepCount` = number of entries collapsed. The card shows `N steps` when `stepCount > 1`. This replaces the review-kickoff-only collapse (PAN-1556).
- **FR-15** In Project scope, an entry is kept when it is system-wide activity, or its issue is one of the project's issues, or it is a conversation whose id is in the project's conversation set, or it is a run card with at least one lane in that set. The project's conversation set is the one the Command Deck already computes with `resolveEffectiveProjectKey` (`projectConvIdSet`, `CommandDeck/index.tsx:1316`).
- **FR-16** The tab bar shows only All, Chats and Activity. A stored tab value of `git`, `files` or `comments` falls back to `all`. The merged feed no longer calls `useGitFeed`.

### Non-functional

- **NFR-1** No new stored state: no table, column, status field, or server endpoint. The only new fetch is the on-expand `GET /api/lanes?run=` (existing route).
- **NFR-2** The run-card selector, the tab filter, and the per-issue collapse are pure functions of their inputs plus an explicit `now`, unit-tested without React.
- **NFR-3** `src/lib/lanes/views.ts` output (`pan lane list`, `GET /api/lanes`) is unchanged: `src/lib/lanes/__tests__/views.test.ts` passes unmodified.
- **NFR-4** Frontend styling follows `pan-style-guide`: no pill badges, no decorative color, "running is not green" — reuse the `ConversationFeedCard` dot tokens (`bg-info` working, `bg-warning` waiting, `bg-muted-foreground/60` idle) and `bg-destructive` for failed.
- **NFR-5** Tests use an injected `now`; no real timers or waits (repo rule: fake timers for any delay-based test).
- **NFR-6** Quality gates: `npm run typecheck`, `npm run lint`, and `npx vitest run <touched test files>`; never the full `npm test` on the host.

## Decisions

- **D1 — Split.** Wanted item 4 (telemetry at emit sites) and its three ACs moved to PAN-4306. It touches six more subsystems and depends on PAN-4300; the feed work does not. Recorded as a comment on PAN-4301.
- **D2 — Two clocks on one entry.** A conversation entry carries `timestamp` (lifecycle) and `recencyAt` (recency). `filterSessionFeedEntriesForTab('chats', now)` re-dates to `recencyAt`. `ConversationFeedCard` renders `entry.timestamp` with `entry.timestampLabel`.
- **D3 — The All window applies to every conversation.** An alive conversation created three days ago has no transition in the window, so it is not in All; it is in Chats (alive) and the Command Deck list.
- **D4 — Pending-input `since` does not date entries.** The conversation row has `pendingInputCount` but no `since`. A waiting lane shows in the run card's counts and state dot and in its own Needs-you row (which has its own `since`); it does not move the run card's timestamp.
- **D5 — Group key uses the row's `projectKey`.** Lane launch always stores an explicit `projectKey` (glossary), so no cwd resolution is needed for grouping. Project scope still uses the Command Deck's one resolver (FR-15) — never a second "projectKey equals" check.
- **D6 — Aggregate counts line.** One line `roles · activities` (FR-9) instead of the appendix's per-role breakdown. It matches the issue AC text `6 builders · 6 working` and stays one line in a 320 px rail.
- **D7 — Per-issue collapse headline = newest entry.** The newest entry is the issue's current state. The merge-card rule needs emit-site `issueId`s and is PAN-4306.
- **D8 — Orchestrator.** The run's orchestrator is the `parentConversationId` shared by the most lanes whose parent is not itself a lane of the run; ties go to the smaller id. Its name is that lanes' `parentConversationName`; its title is the `title` of the root row with that id when present in the list.
- **D9 — Shared module location.** `packages/contracts/src/conversation-rows.ts` holds both `SINGLETON_AGENT_IDS` / `isSingletonConversation` and `LaneActivity` / `LANE_STARTING_GRACE_MS` / `laneActivityOf`: both classify conversation rows and both are needed by server and frontend.
- **D10 — Pure-function tests live in contracts.** `packages/contracts/src/__tests__/conversation-rows.test.ts` tests `laneActivityOf`; `src/lib/lanes/__tests__/views.test.ts` runs unchanged as the regression proof (NFR-3).
- **D11 — Git tab.** Hidden, and `useMergedFeed` stops merging `useGitFeed` (a 15 s poll of a table with 0 rows). Restoring it is a two-line change once a writer exists.
- **D12 — CI coverage.** The sessionFeed tests are not in root `package.json` `test:frontend-subset` today, so CI never runs them. WI-13 adds every sessionFeed test this issue touches or creates.
- **D13 — Size.** The plan exceeds the 25-file / 6-subsystem projection only through tests (11 files), three separate doc files, and `package.json`. All source changes sit in one directory (`components/sessionFeed/`) plus one contracts module; splitting further would create siblings that all edit `types.ts` and `useMergedFeed.ts` and serialize anyway.

```ts
// packages/contracts/src/conversation-rows.ts
/** Singleton runners spawn under their bare id (see src/lib/agents/identity.ts normalizeAgentId). */
export const SINGLETON_AGENT_IDS: ReadonlySet<string> = new Set(['flywheel-orchestrator', 'sequencer-runner']);

export function isSingletonConversation(row: { name: string; issueId?: string | null }): boolean {
  return SINGLETON_AGENT_IDS.has(row.name.toLowerCase())
    || (row.issueId != null && SINGLETON_AGENT_IDS.has(row.issueId.toLowerCase()));
}

export type LaneActivity = 'failed-to-start' | 'needs-you' | 'working' | 'idle' | 'starting' | 'stopped';
/** D10 `starting`: not alive, not ended, created less than this long ago. */
export const LANE_STARTING_GRACE_MS = 3 * 60_000;

export interface LaneActivityInput {
  archivedAt?: string | null;
  spawnError?: string | null;
  status?: 'active' | 'ended' | string | null;
  createdAt: string;
  sessionAlive?: boolean;
  isWorking?: boolean;
  pendingInputCount?: number;
}

/** D10, first match wins. */
export function laneActivityOf(row: LaneActivityInput, now: number): LaneActivity {
  if (row.archivedAt != null) return 'stopped';
  if (row.spawnError) return 'failed-to-start';
  if (row.sessionAlive) {
    if ((row.pendingInputCount ?? 0) > 0) return 'needs-you';
    if (row.isWorking) return 'working';
    return 'idle';
  }
  if (row.status === 'active' && now - Date.parse(row.createdAt) < LANE_STARTING_GRACE_MS) return 'starting';
  return 'stopped';
}
```

### WI-6 — Run-card selector `groupGauntletRuns` (FR-6 – FR-10, D4, D6, D8)

Files: new `src/dashboard/frontend/src/components/sessionFeed/gauntletRunEntries.ts`, new `__tests__/gauntletRunEntries.test.ts`.

`export function groupGauntletRuns(lanes: readonly ConversationFeedRow[], allRows: readonly ConversationFeedRow[], now: number): GauntletRunSessionFeedEntry[]`

Steps, per group `(projectKey ?? null, gauntletRun)`:
1. For each lane compute `activity = laneActivityOf(row, now)` (contracts).
2. **Counts line** per FR-9. Role order `builder, critic, verifier, play, orchestrator`; activity order and labels `needs-you → "needs you"`, `failed-to-start → "failed to start"`, `working`, `idle`, `starting`, `stopped`.
3. **State**: any `needs-you` → `needs-you`; else any `failed-to-start` or `laneReport.status` in `blocked | failed` → `failed`; else any `working` → `working`; else any `idle | starting` → `idle`; else `stopped`.
4. **Latest event** per FR-8 with text: report → `` `${key} ${role} i${iteration} reported ${status}` `` plus `` ` · verdict ${verdict}` `` when `laneReport.verdict` is set (omit ` i${iteration}` when `laneIteration` is null); failed start → `` `${key} ${role} failed to start` `` at `createdAt`; end → `` `${key} ${role} ended` `` at `endedAt`; launch → `` `${key} ${role} launched` `` at `createdAt`. Compare ISO strings with `Date.parse`.
5. **Orchestrator** per D8, title from `allRows`.
6. **Lane order** per FR-12: builders sorted by `laneKey`; after each builder, lanes whose `criticOfConversationId === builder.id` sorted by `createdAt`; then remaining lanes by role order, then `laneKey`.
7. `anyAlive` = any lane `sessionAlive`; `laneConversationIds` = lane ids.

Return runs sorted newest `latest.at` first.

Tests (inject `now`): six working builders in `india`/`lexerra` → one entry, `countsLine === '6 builders · 6 working'`, title parts `run === 'india'`, `projectKey === 'lexerra'`; the same six rows with `lastActivityAt` advanced by 5 minutes → identical `timestamp`; one lane with `laneReport {status:'done', at:T}` → `latest.text` contains that lane key and `reported done`, `timestamp === T`; one lane with `pendingInputCount: 1` → `countsLine` contains `1 needs you` and `state === 'needs-you'`; runs `india` in `lexerra` and `india` in `overdeck` → two entries with different ids; spawnError lane → `failed to start` count and `state === 'failed'`; critic with `criticOfConversationId` ordered right after its builder; orchestrator tie → smaller id.

### A.0 TL;DR

1. **The flood is not an event stream.** Chats is the whole `/api/conversations` list: one card per non-archived operator conversation, sorted by `lastActivityAt` (the transcript JSONL mtime). Every working conversation moves back to "Just Now" on each 30 s refetch. With 6 lexerra builder lanes working, 5 lane cards plus the orchestrator and one blank card filled the "Just Now" bucket.
2. **"No messages yet" is the `sequencer-runner` singleton.** Its row (id 46) has a null title and passes the list filter because its name has no `agent-` prefix. The card shows the title; when the title is null it falls back to the text "No messages yet".
3. **Activity (`activity.entry`) is about 70% telemetry.** Of 685 entries in 24h: phase progress 220 (32%), sequencer "role started" 155 (23%), ship cleanup 84 (12%), stack reaping 41 (6%), plan-skip echoes 17 (2%). Operator news is about 80 entries: 34 merges, 45 pipeline steps, plus memory-governor and restart lines.
4. **The two sources run on different clocks.** Activity is capped at 50 entries (`MAX_ACTIVITY_ENTRIES`), which is roughly the last hour. Chats never ages out: a conversation last active on 2026-08-20 is still listed.
5. **Two of the four sources are empty, and two tabs are stubs.** `git_operations` has 0 rows ever. `memory.observation_created` has 0 events in 7 days. Files and Comments are placeholders. In practice, Global/All is Chats plus at most 50 activity entries.
6. **Project scope filters by issue id, not by project.** Lane rows have `projectKey: 'lexerra'` and `issueId: null`, so Project scope hides them. The operator can only see them in Global, mixed with every other project.
7. **Gauntlet runs can be consolidated with no new stored state.** Lane rows carry `gauntletRun`, `laneKey`, `laneRole`, `parentConversationId`, `criticOfConversationId`, `laneIteration`, `laneReport` and `laneLatestVerdict`. The Command Deck already nests lanes (`conversation-tree.ts`), and `/api/lanes` already computes the lane activity state (`views.ts`). The feed just doesn't use either.

### A.3 How lanes are modeled (what's derivable)

`reference/lanes.mdx`: "A gauntlet run is the set of lanes that share a run key. There is no run table and no stored lane status: every state below is computed when you read it."

Per-row facts, written once at launch (`conversations` columns): `parent_conversation_id`, `gauntlet_run`, `lane_key`, `lane_role` (`builder|critic|verifier|play|orchestrator`), `critic_of_conversation_id`. The enriched list (`lib/overdeck/conversation-list.ts: laneEnrichment`) adds the derived fields `laneIteration`, `laneReport {seq, at, status, verdict}`, `laneLatestVerdict` (builders) and `laneVerdict` (critics/verifiers). Liveness comes from `sessionAlive`, `isWorking`, `pendingInputCount`, `spawnError`, `status`, `createdAt` and `endedAt`.

Existing derivations the feed can reuse:

- `src/lib/lanes/views.ts`: `activityOf` (D10: `failed-to-start | needs-you | working | idle | starting | stopped`), `LaneView`, behind `GET /api/lanes?run=&parent=&key=`. It includes archived lanes and runs git per lane (memoized for 3 s), so it suits an on-demand expand, not a 30 s poll.
- `src/lib/lanes/pairing.ts`: builder→critic pairing and latest verdict.
- `src/dashboard/frontend/src/components/CommandDeck/conversation-tree.ts`: `buildConversationTree` nests lanes under their launcher (critics under the builder they judge), and `groupSummary` counts `lanes / working / needsYou / reported`. The Command Deck list already consolidates lanes this way; the Awareness feed was never switched over to it.

The current sample is one run, `lexerra/india`: 6 builders, parent conversation 2884 ("Lexerra HOTEL gauntlet and 0.13.1 release"). The same orchestrator has run several passes (its title says HOTEL, the run key is `india`), so **the card must be named by the run key, not by the parent's title**.

Out of reach: the 32 "SB lane: …" conversations from 2026-09-25/26 predate `pan lane`. They have no `gauntlet_run` and no parent, so they cannot be grouped by these rules. All but one are already archived. The design covers tagged lanes only.

The `pan-gauntlet-loop` skill's "live progress page" (`gauntlet/status.json` + `assets/gauntlet-index.html`) is state the orchestrator writes inside the project. Overdeck cannot derive it, so the card should not depend on it.

### A.4 Principles: what deserves an entry

1. **The feed shows transitions, not a live index.** Each entry is stamped with the time of a recorded fact (created, ended, report filed, verdict, merge, failure, input requested). A transcript mtime is not such a fact, and it must never order the All view.
2. **One subject, one card.** Collapse by subject (issue, gauntlet run, conversation) and show the latest notable transition, with a count and an expand. This generalizes the existing review-kickoff collapse.
3. **The operator's four questions decide what shows.** (a) Is something waiting on me? That is Needs you, already correct. (b) Did something fail and stay failed? (c) Did something ship or merge? (d) Did a unit of work finish (planning complete, lane report, verdict, run finished)? Everything else is ambient and belongs in the raw Activity page log, not the rail.
4. **Levels mean something.** `error` means the operator may need to act. A gated retry that later succeeds is `info` (or not emitted) until it is final.
5. **Telemetry is removed where it's emitted, not in the view.** The 50-entry cap applies before any frontend filter, so telemetry left in `activity.entry` still evicts news. Fine-grained progress goes through `emitActivityDetailed`, the channel `activity-logger.ts` already documents for it.
6. **Scope by the subject's project.** A conversation or lane belongs to `projectKey`; an issue-less entry is not "unscoped" when its project is known.
7. **Hide tabs that have no data.** A tab whose source has no writer (Git, Files, Comments) is hidden until one exists.
8. **Derive, don't store.** Every rule below is a selector over rows and events that already exist. No new tables, columns or status fields.

### A.5 Proposed rules per tab and filter

#### A.5.1 Scopes

| Scope | Shows | Change |
|---|---|---|
| Needs you | `DecisionsPanel` | none. Consolidation never hides a pending-input subject: a lane waiting on input still gets its own Needs-you row |
| Project | entries whose `issueId ∈ project issues` **or** whose `projectKey === selected project` (conversations and run cards carry `projectKey`), plus `systemWide` | add `projectKey` to `ConversationSessionFeedEntry` and to run cards; change the `keep` predicate |
| Global | everything, same rules | no scope change; it just inherits the de-noised sources |

#### A.5.2 Filters

| Filter | Shows | Collapses | Drops |
|---|---|---|---|
| **All** | Operator news: activity entries in the "news" set (below); **gauntlet run cards**; conversation **lifecycle facts** for root conversations (created, ended, handed off), each dated by its own timestamp (`createdAt`, `endedAt`) | per-issue activity into one card (newest headline plus "N steps"); ship cleanup into its merge card; dashboard boot lines into one "Dashboard restarted" card | `lastActivityAt`-ordered conversation cards; singleton agents (`SINGLETON_AGENT_IDS` in `src/lib/agents/identity.ts`: `sequencer-runner`, `flywheel-orchestrator`; module-private today, so move it to `@overdeck/contracts` for the frontend to read); untitled conversations with no activity |
| **Chats** | A recency index of root conversations: sorted by `lastActivityAt`, windowed (active in the last 24h, or alive), status dot from `isWorking` / `pendingInputCount` / `sessionAlive` | each gauntlet run into one row (the run card), nested under nothing; lanes appear only when the row is expanded | singletons; ended conversations older than the window (they stay reachable from the Command Deck list and search); archived rows (already excluded) |
| **Activity** | `activity.entry` minus telemetry | per-issue, as in All | nothing extra in the view; telemetry is fixed at emit sites |
| **Git / Files / Comments** | hidden from the tab bar until a writer exists (`git_operations` has 0 rows; Files and Comments are stubs) | – | – |

**News set for `activity.entry`** (kept in the rail):
- merges and merge failures
- planning complete / work-agent started
- review and test verdicts
- phase entries with a *final* failure: the last entry for that (issue, phase) is a failure with nothing newer
- memory governor critical, holding and shedding lines
- one entry per dashboard restart
- anything with `desktop: true` or `level: 'error'` after the retry rule

**Moved to `activity.detailed`** (off the rail, still on the Activity page's Detailed stream):
- `start-agent.phase=*` and `complete-planning.phase=*` / `auto-promote.phase=*` at start, success or skipped
- `spawn.ts` "role started" for singleton roles (as review already is)
- "plan role already active; skipping lifecycle spawn"
- ship cleanup lines
- "reaped idle workspace UI stack"
- dashboard sub-boot lines

Expected effect on the 24h sample: about 685 → about 120 rail entries, and the 50-slot cache covers several hours instead of about one.

Caveat: today the Detailed stream is 99% the dead-agent loop (side finding S1), so "still visible in Detailed" is only true in practice once S1 is fixed. S1 is a prerequisite for Detailed to be a usable home for the moved telemetry.

### A.6 Gauntlet run consolidation design

**Group key:** `(projectKey, gauntletRun)`. Run keys are only unique per project in practice (the pattern `^[a-z0-9][a-z0-9-]{0,31}$` is reused across projects).

**Row source:** the `/api/conversations` rows the feed already polls. Each lane row carries `gauntletRun`, `laneKey`, `laneRole`, `laneIteration`, `laneReport`, `laneLatestVerdict` / `laneVerdict`, `sessionAlive`, `isWorking`, `pendingInputCount`, `spawnError`, `status`, `createdAt`, `endedAt` and `parentConversationId`/`Name`. There is no new fetch and no new stored field. To keep one D10 rule, move `activityOf` from `views.ts` into a pure shared function (for example `packages/contracts/src/lanes/activity.ts`) that both `views.ts` and the feed selector call.

**Card (collapsed):**
```
⛭ Gauntlet INDIA · lexerra                         3m
  6 builders: 6 working · 0 critics
  latest: 689 builder i1 reported done — or — 688 critic verdict WOWED (0 defects)
  launched from #2884 "Lexerra HOTEL gauntlet and 0.13.1 release"
```
- **Title:** the run key upper-cased, plus the project.
- **Counts:** by role × derived activity (`needs-you`, `failed-to-start`, `working`, `idle`, `starting`, `stopped`), with needs-you and failed-to-start shown first.
- **Latest notable event:** the newest of these facts across the run's lanes: `laneReport.at` (done / blocked / failed, with the critic verdict when present), a critic verdict, `pendingInputCount > 0` (lane needs you), `spawnError` (failed to start), a lane launch (`createdAt`), a lane end (`endedAt`).
- **Card timestamp:** that event's time, **not** max `lastActivityAt`. Otherwise the card would stay pinned to "Just Now" while builders work, which is the current bug.
- **Stripe / state:** the first match in the order needs-you > failed / blocked > working > idle > all stopped.
- **Click:** opens the orchestrator (`/conv/<parentConversationName>`), the conversation the operator talks to.

**Expanded:** one line per lane key in builder → critic → verifier order, using the same pairing as `pairing.ts` / `buildConversationTree` (critics under the builder they judge): `glyph key iN · activity · report/verdict · age`. Each line links to `/conv/<name>`. Opening the expand may call `GET /api/lanes?run=<run>` once for archived lanes and git facts (branch@sha, ahead, dirty). It is not polled.

**Lifetime:** the card exists while at least one lane row in the run is unarchived. Once every lane is reaped, the rows leave `/api/conversations` and the card disappears with them. Nothing is stored to keep it.

**Where:** a pure selector `groupGauntletRuns(entries)` in `components/sessionFeed/` (new `GauntletRunFeedCard.tsx` + `gauntletRunEntries.ts`), applied in `useMergedFeed` before the tab filter. It uses a new entry kind `gauntlet_run` in `types.ts`, rendered by `BucketSection`.
