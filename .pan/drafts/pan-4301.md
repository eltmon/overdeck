## TL;DR

1. **The flood is not an event stream.** Chats is the whole `/api/conversations` list: one card per non-archived operator conversation, sorted by `lastActivityAt` (the transcript JSONL mtime). Every working conversation moves back to "Just Now" on each 30 s refetch. With 6 lexerra builder lanes working, 5 lane cards plus the orchestrator and one blank card filled the "Just Now" bucket.
2. **"No messages yet" is the `sequencer-runner` singleton.** Its row (id 46) has a null title and passes the list filter because its name has no `agent-` prefix. The card shows the title; when the title is null it falls back to the text "No messages yet".
3. **Activity (`activity.entry`) is about 70% telemetry.** Of 685 entries in 24h: phase progress 220 (32%), sequencer "role started" 155 (23%), ship cleanup 84 (12%), stack reaping 41 (6%), plan-skip echoes 17 (2%). Operator news is about 80 entries: 34 merges, 45 pipeline steps, plus memory-governor and restart lines.
4. **The two sources run on different clocks.** Activity is capped at 50 entries (`MAX_ACTIVITY_ENTRIES`), which is roughly the last hour. Chats never ages out: a conversation last active on 2026-08-20 is still listed.
5. **Two of the four sources are empty, and two tabs are stubs.** `git_operations` has 0 rows ever. `memory.observation_created` has 0 events in 7 days. Files and Comments are placeholders. In practice, Global/All is Chats plus at most 50 activity entries.
6. **Project scope filters by issue id, not by project.** Lane rows have `projectKey: 'lexerra'` and `issueId: null`, so Project scope hides them. The operator can only see them in Global, mixed with every other project.
7. **Gauntlet runs can be consolidated with no new stored state.** Lane rows carry `gauntletRun`, `laneKey`, `laneRole`, `parentConversationId`, `criticOfConversationId`, `laneIteration`, `laneReport` and `laneLatestVerdict`. The Command Deck already nests lanes (`conversation-tree.ts`), and `/api/lanes` already computes the lane activity state (`views.ts`). The feed just doesn't use either.

## 3. How lanes are modeled (what's derivable)

`reference/lanes.mdx`: "A gauntlet run is the set of lanes that share a run key. There is no run table and no stored lane status: every state below is computed when you read it."

Per-row facts, written once at launch (`conversations` columns): `parent_conversation_id`, `gauntlet_run`, `lane_key`, `lane_role` (`builder|critic|verifier|play|orchestrator`), `critic_of_conversation_id`. The enriched list (`lib/overdeck/conversation-list.ts: laneEnrichment`) adds the derived fields `laneIteration`, `laneReport {seq, at, status, verdict}`, `laneLatestVerdict` (builders) and `laneVerdict` (critics/verifiers). Liveness comes from `sessionAlive`, `isWorking`, `pendingInputCount`, `spawnError`, `status`, `createdAt` and `endedAt`.

Existing derivations the feed can reuse:

- `src/lib/lanes/views.ts`: `activityOf` (D10: `failed-to-start | needs-you | working | idle | starting | stopped`), `LaneView`, behind `GET /api/lanes?run=&parent=&key=`. It includes archived lanes and runs git per lane (memoized for 3 s), so it suits an on-demand expand, not a 30 s poll.
- `src/lib/lanes/pairing.ts`: builder→critic pairing and latest verdict.
- `src/dashboard/frontend/src/components/CommandDeck/conversation-tree.ts`: `buildConversationTree` nests lanes under their launcher (critics under the builder they judge), and `groupSummary` counts `lanes / working / needsYou / reported`. The Command Deck list already consolidates lanes this way; the Awareness feed was never switched over to it.

The current sample is one run, `lexerra/india`: 6 builders, parent conversation 2884 ("Lexerra HOTEL gauntlet and 0.13.1 release"). The same orchestrator has run several passes (its title says HOTEL, the run key is `india`), so **the card must be named by the run key, not by the parent's title**.

Out of reach: the 32 "SB lane: …" conversations from 2026-09-25/26 predate `pan lane`. They have no `gauntlet_run` and no parent, so they cannot be grouped by these rules. All but one are already archived. The design covers tagged lanes only.

The `pan-gauntlet-loop` skill's "live progress page" (`gauntlet/status.json` + `assets/gauntlet-index.html`) is state the orchestrator writes inside the project. Overdeck cannot derive it, so the card should not depend on it.

## 4. Principles: what deserves an entry

1. **The feed shows transitions, not a live index.** Each entry is stamped with the time of a recorded fact (created, ended, report filed, verdict, merge, failure, input requested). A transcript mtime is not such a fact, and it must never order the All view.
2. **One subject, one card.** Collapse by subject (issue, gauntlet run, conversation) and show the latest notable transition, with a count and an expand. This generalizes the existing review-kickoff collapse.
3. **The operator's four questions decide what shows.** (a) Is something waiting on me? That is Needs you, already correct. (b) Did something fail and stay failed? (c) Did something ship or merge? (d) Did a unit of work finish (planning complete, lane report, verdict, run finished)? Everything else is ambient and belongs in the raw Activity page log, not the rail.
4. **Levels mean something.** `error` means the operator may need to act. A gated retry that later succeeds is `info` (or not emitted) until it is final.
5. **Telemetry is removed where it's emitted, not in the view.** The 50-entry cap applies before any frontend filter, so telemetry left in `activity.entry` still evicts news. Fine-grained progress goes through `emitActivityDetailed`, the channel `activity-logger.ts` already documents for it.
6. **Scope by the subject's project.** A conversation or lane belongs to `projectKey`; an issue-less entry is not "unscoped" when its project is known.
7. **Hide tabs that have no data.** A tab whose source has no writer (Git, Files, Comments) is hidden until one exists.
8. **Derive, don't store.** Every rule below is a selector over rows and events that already exist. No new tables, columns or status fields.

**News set for `activity.entry`** (kept in the rail):
- merges and merge failures
- planning complete / work-agent started
- review and test verdicts
- phase entries with a *final* failure: the last entry for that (issue, phase) is a failure with nothing newer
- memory governor critical, holding and shedding lines
- one entry per dashboard restart

## 6. Gauntlet run consolidation design

**Group key:** `(projectKey, gauntletRun)`. Run keys are only unique per project in practice (the pattern `^[a-z0-9][a-z0-9-]{0,31}$` is reused across projects).

**Row source:** the `/api/conversations` rows the feed already polls. Each lane row carries `gauntletRun`, `laneKey`, `laneRole`, `laneIteration`, `laneReport`, `laneLatestVerdict` / `laneVerdict`, `sessionAlive`, `isWorking`, `pendingInputCount`, `spawnError`, `status`, `createdAt`, `endedAt` and `parentConversationId`/`Name`. There is no new fetch and no new stored field. To keep one D10 rule, move `activityOf` from `views.ts` into a pure shared function (for example `packages/contracts/src/lanes/activity.ts`) that both `views.ts` and the feed selector call.

**Card (collapsed):**
```
⛭ Gauntlet INDIA · lexerra                         3m
  6 builders: 6 working · 0 critics
  latest: 689 builder i1 reported done — or — 688 critic verdict WOWED (0 defects)
  launched from #2884 "Lexerra HOTEL gauntlet and 0.13.1 release"
```
- **Title:** the run key upper-cased, plus the project.
- **Counts:** by role × derived activity (`needs-you`, `failed-to-start`, `working`, `idle`, `starting`, `stopped`), with needs-you and failed-to-start shown first.
- **Latest notable event:** the newest of these facts across the run's lanes: `laneReport.at` (done / blocked / failed, with the critic verdict when present), a critic verdict, `pendingInputCount > 0` (lane needs you), `spawnError` (failed to start), a lane launch (`createdAt`), a lane end (`endedAt`).
- **Card timestamp:** that event's time, **not** max `lastActivityAt`. Otherwise the card would stay pinned to "Just Now" while builders work, which is the current bug.
- **Stripe / state:** the first match in the order needs-you > failed / blocked > working > idle > all stopped.
- **Click:** opens the orchestrator (`/conv/<parentConversationName>`), the conversation the operator talks to.

**Expanded:** one line per lane key in builder → critic → verifier order, using the same pairing as `pairing.ts` / `buildConversationTree` (critics under the builder they judge): `glyph key iN · activity · report/verdict · age`. Each line links to `/conv/<name>`. Opening the expand may call `GET /api/lanes?run=<run>` once for archived lanes and git facts (branch@sha, ahead, dirty). It is not polled.

**Lifetime:** the card exists while at least one lane row in the run is unarchived. Once every lane is reaped, the rows leave `/api/conversations` and the card disappears with them. Nothing is stored to keep it.

**Where:** a pure selector `groupGauntletRuns(entries)` in `components/sessionFeed/` (new `GauntletRunFeedCard.tsx` + `gauntletRunEntries.ts`), applied in `useMergedFeed` before the tab filter. It uses a new entry kind `gauntlet_run` in `types.ts`, rendered by `BucketSection`.
