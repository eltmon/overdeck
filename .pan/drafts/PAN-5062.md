# PAN-5062 — dbt projects: placeholders in gate env, identifier-safe feature placeholder, per-workspace dev target

**Issue:** [PAN-5062](https://github.com/eltmon/overdeck/issues/5062)
**Planned against:** `feature/pan-5062` @ `df325e4cb3f` (2026-11-05)
**Planning mode:** `pan plan --auto` (decisions recorded below and in the xBRIEF `autoDecisions[]`)

## Goal

Make dbt projects (and similar data-build tools) work through the Overdeck
pipeline: `dbt parse` / `dbt build` run as verification gates, and every
workspace builds into its own dev schema, so parallel issues never collide.

## Glossary

- **Quality gate** — one entry of `projects.<key>.quality_gates` in
  `~/.overdeck/projects.yaml`. Type `QualityGateConfig`
  (`src/lib/workspace-config.ts`, `export interface QualityGateConfig`). The
  verification gate runs them through `runQualityGates()`
  (`src/lib/cloister/validation.ts`).
- **Host gate** — a command gate that runs on this machine as
  `nice -n 19 sh -c '<cmd>'` with the env from `buildQualityGateEnv()`.
- **Container gate** — a gate with `container: true` and `container_name`,
  run as `docker exec -e K="v" … <container> <cmd>`.
- **Remote gate** — a gate in a Fly workspace, run as `fly ssh console … -C "cd … && <cmd>"`.
- **Placeholder** — a `{{KEY}}` token replaced by `replacePlaceholders()`
  (`src/lib/workspace-config.ts`) from a `TemplatePlaceholders` object.
- **Placeholder construction site** — code that builds a `TemplatePlaceholders`
  (or the same shape) for one workspace. There are six (listed in WI-1).
- **`FEATURE_NAME`** — the lowercase issue id, e.g. `min-574`.
- **`FEATURE_IDENT`** (new) — `FEATURE_NAME` made safe as an unquoted SQL
  identifier: lowercase, every character outside `[a-z0-9_]` replaced by `_`.
  `min-574` → `min_574`.
- **Workspace `.env`** — `<workspace>/.env`, written once at workspace creation
  from `workspace.env.template` with placeholders rendered
  (`src/lib/workspace-manager/create.ts`, grep `Generate .env file`).
- **`workspace.env.load`** (new) — opt-in boolean. When `true`, the rendered
  workspace `.env` is exported into agent shells launched in the workspace and
  merged into host gate environments.
- **Launcher** — the bash script `generateLauncherScript()`
  (`src/lib/launcher-generator.ts`) writes for every agent, conversation,
  resume and recovery launch.
- **dbt `env_var()`** — dbt's Jinja function that reads the *process*
  environment. dbt never reads a `.env` file.

## Findings for issue item 3 (does the workspace `.env` reach agents and gates?)

Verified in code at `df325e4cb3f`:

1. **Agents: no.** `generateLauncherScript()` (`src/lib/launcher-generator.ts`)
   exports a fixed set of variables (`OVERDECK_HOME`, `SKIP_DOCS_INDEX`,
   terminal vars, `OVERDECK_AGENT_ID`/`ISSUE_ID`/`SESSION_TYPE`, provider
   exports, `extraEnvExports`). Nothing reads `<workspace>/.env`. A launched
   harness inherits the terminal-backend server environment (on tmux, the
   dashboard's env minus `PLANNING_TMUX_GLOBAL_ENV_TO_UNSET`, see
   `src/lib/terminal-backends/launch.ts` `prepareTmuxServer`) plus those exports.
2. **Gates: no.** `buildQualityGateEnv()` (`src/lib/cloister/validation.ts`)
   returns `{ SKIP_DOCS_INDEX: '1', ...process.env (filtered), ...gate.env }`.
   `process.env` is the dashboard's (which includes `~/.overdeck.env` via
   `src/lib/env-loader.ts`). `<workspace>/.env` is never read.
3. Tools that read `.env` themselves (docker compose) see it; dbt does not.
4. `workspace.env.secrets_file` (`EnvConfig` in `src/lib/workspace-config.ts`
   and the inline copy in `src/lib/projects.ts`, grep
   `env?: { template?: string; secrets_file?: string }`) is declared but has no
   reader anywhere in `src/`. It is dead config. This issue does not touch it.
5. On this machine no registered project sets `workspace.env.template`
   (checked `~/.overdeck/projects.yaml`), but other installs may, so a default
   change would be a silent behavior change for them.

**Decision (D-3):** load the workspace `.env` only when the project opts in with
`workspace.env.load: true`. Default off. When on:
- host gates get it merged with precedence
  `process.env (filtered) < workspace .env < rendered gate.env`;
- agent launchers export it right after `export SKIP_DOCS_INDEX=1`, so every
  Overdeck-managed export emitted later in the script (agent identity,
  provider env, PATH changes) still wins;
- the file is **parsed** (`KEY=value` lines) and each value is emitted through
  `shellQuote()`. It is never `source`d, because compose-style `.env` values
  (`URL=http://x?a=1&b=2`) are not valid shell and sourcing would execute them.
- reserved keys are dropped on load: any key starting with `OVERDECK_`, plus
  `PATH` and `HOME`.
- container gates and remote gates do not get it (NonGoal; the container has
  its own env from compose, and remote gates never received `gate.env` either).

For dbt specifically, the recommended recipe needs neither path: gates get
`DBT_SCHEMA` from `gate.env` with `{{FEATURE_IDENT}}` (WI-2), and agents get it
from the workspace `.env` with `env.load: true` (WI-4, WI-5).

## Decisions

- **D-1 `FEATURE_IDENT` is a required field** of `TemplatePlaceholders`. A
  required field makes `npm run typecheck` fail at any construction site that
  forgets it, which is how "available everywhere placeholders are" is enforced.
- **D-2 Normalization rule:** `toFeatureIdent(name) = name.toLowerCase().replace(/[^a-z0-9_]/g, '_')`.
  One character in, one character out. No collapsing of runs, no trimming, no
  leading-digit handling. Docs tell users to put it after a prefix
  (`dev_{{FEATURE_IDENT}}`), which also covers a name that starts with a digit.
- **D-3** Opt-in `workspace.env.load` (see Findings).
- **D-4 Render `gate.env` once per gate** and use the rendered object for both
  the host env and the container `-e` flags. When `opts.placeholders` is
  absent, values pass through unchanged (same rule as `gate.command` today).
- **D-5 Container `-e` quoting stays as is** (`-e K="v"`). Changing it to
  single quotes would stop host-side `$VAR` expansion that existing configs may
  rely on. `FEATURE_IDENT` values are `[a-z0-9_]`, so the recipe is safe.
- **D-6 Agent loading lives inside `generateLauncherScript()`**, not at spawn
  sites. There are 15 `generateLauncherScript(` call sites (spawn, resume,
  recovery ×5, messaging, conversations, planning …). One call inside the
  generator covers all of them. All logic lives in the new module
  `src/lib/workspace-env.ts`; the generator gains exactly one import and one
  call line (it is at 997 lines and the ceiling is 1000, see NFR-2).
- **D-7 Agent loading skips project roots and remote launches.** It applies only
  when `<workingDir>/.env` exists, a registered project contains `workingDir`
  (`findProjectByPath`, `src/lib/projects.ts`), that project has
  `workspace.env.load === true`, `resolve(workingDir) !== resolve(project.path)`,
  and `config.spawnMode !== 'remote'`.
- **D-8 Recipe gate names are `dbt-parse` and `dbt-build`.** A gate named
  exactly `test` is dropped from the local run when `verification.tests`
  resolves to `ci` (`selectLocalVerificationGates`,
  `src/lib/cloister/verification-tests-mode.ts`, `TEST_GATE_NAME = 'test'`).

## Requirements

- **FR-1** `gate.env` values are rendered with the same placeholders as
  `gate.command` before a host gate runs.
- **FR-2** `gate.env` values are rendered before they become `docker exec -e`
  flags for a container gate.
- **FR-3** `TemplatePlaceholders` has a required `FEATURE_IDENT`, produced by an
  exported `toFeatureIdent()`, and every placeholder construction site sets it.
- **FR-4** `workspace.env.load?: boolean` exists on both `EnvConfig`
  declarations; a new module parses and reads the workspace `.env`.
- **FR-5** Host gates merge the workspace `.env` when `env.load` is true, with
  precedence `process.env < workspace .env < gate.env`.
- **FR-6** Agent launchers in an opted-in workspace export the workspace `.env`
  values, quoted, before Overdeck's own exports.
- **FR-7** `configuration/projects.mdx` has a "dbt and data projects" recipe and
  lists every placeholder and the `env.load` switch.
- **FR-8** `configuration/polyrepo.mdx` and `docs/CONFIGURATION.md` list
  `FEATURE_IDENT` and `env.load`.
- **NFR-1** Tests use fake data only. No test requires dbt, DuckDB, Snowflake or
  Docker to be installed.
- **NFR-2** `src/lib/launcher-generator.ts` stays at or under 1000 lines
  (`scripts/lint-file-size.sh`, `CEILING=1000`). Never raise an allowlist cap.
- **NFR-3** No behavior change for projects that do not set `env.load` and do
  not use `{{…}}` in `gate.env`.
- **NFR-4** `npm run lint:circular` stays green (`workspace-env.ts` imports
  `projects.ts`; `launcher-generator.ts` imports `workspace-env.ts`).

## Intersecting repo rules (restated)

- Never `execSync` in server-reachable code. `validation.ts` and the launcher
  are server-reachable. Small sync `existsSync`/`readFileSync` of one `.env`
  file is acceptable (the generator already reads config sync); no child process.
- New tests must not read source files to grep them (`lint:source-introspection`)
  and must not add `skipIf`/`.only`.
- Quality gates before `pan done`: `npm run typecheck`, `npm run lint`, and
  `npx vitest run <touched test files>`. Never run the full `npm test`.
- File-size ratchet: a file over 1000 lines may not grow past its `origin/main`
  count or its allowlist cap; agents never raise caps. `merge-ops.ts` (1759
  lines, cap 1835) may grow by 1 line.
- `npm run typecheck` excludes `*.test.ts`; test fixtures that build a
  `TemplatePlaceholders` literal will not fail typecheck, so add
  `FEATURE_IDENT` to fixtures you touch on purpose.

### WI-3 — Workspace env module and `env.load` config field (FR-4)

New file `src/lib/workspace-env.ts`:
```ts
/** PAN-5062: the rendered workspace .env, exported only when the project sets workspace.env.load. */
export function parseWorkspaceEnv(content: string): Record<string, string>;
export function readWorkspaceEnv(workspacePath: string): Record<string, string>;
export function loadWorkspaceEnvForProject(project: ProjectConfig | null | undefined, workspacePath: string): Record<string, string>;
export function workspaceEnvLauncherLines(workingDir: string, findProject?: (p: string) => ProjectConfig | null): string[];
```
Rules:
- `parseWorkspaceEnv`: per line, trim; skip blank and `#` lines; strip an
  optional leading `export `; match `^([A-Za-z_][A-Za-z0-9_]*)=(.*)$`; strip one
  pair of matching surrounding `"` or `'`; drop reserved keys (`/^OVERDECK_/`,
  `PATH`, `HOME`). Lines that do not match are ignored.
- `readWorkspaceEnv`: `{}` when `<workspacePath>/.env` does not exist, else
  `parseWorkspaceEnv(readFileSync(...))`.
- `loadWorkspaceEnvForProject`: `{}` unless `project?.workspace?.env?.load === true`
  and `resolve(workspacePath) !== resolve(project.path)`; else `readWorkspaceEnv`.
- `workspaceEnvLauncherLines`: `[]` when `<workingDir>/.env` does not exist
  (checked first, so no project lookup happens for most launches); otherwise
  `findProject` (default `findProjectByPath`) → `loadWorkspaceEnvForProject` →
  `Object.entries(env).map(([k, v]) => \`export ${k}=${shellQuote(v)}\`)`.
  `shellQuote` is `src/lib/shell-quote.ts`.

Config type changes (same edit on both declarations):
- `src/lib/workspace-config.ts` `export interface EnvConfig` — add
  `/** PAN-5062: export the rendered .env into agent shells and host quality gates. */ load?: boolean;`
- `src/lib/projects.ts` — `env?: { template?: string; secrets_file?: string };`
  → `env?: { template?: string; secrets_file?: string; load?: boolean };`
  (same line; `projects.ts` is over 1000 lines and must not grow).

Tests: new `tests/unit/lib/workspace-env.test.ts` with temp dirs (real files,
fake values): parsing (comments, quotes, `export ` prefix, reserved keys
dropped, `a=1&b=2` kept literally); `loadWorkspaceEnvForProject` returns `{}`
when `load` is unset, when `workspacePath === project.path`, and the parsed map
when on; `workspaceEnvLauncherLines` with an injected `findProject` returns
`export DBT_SCHEMA='dev_min_574'` and quotes a value containing `'`/`&`/space.

## Non-goals

- Cloning or dropping a warehouse database per workspace (Hume create/teardown pattern).
- Per-project credentials and MCP servers (filed separately).
- Passing `gate.env` or the workspace `.env` to remote (Fly ssh) gates.
- Passing the workspace `.env` to container gates.
- Changing container `-e` quoting.
- Wiring or removing the dead `workspace.env.secrets_file` field.
- Re-rendering `<workspace>/.env` for workspaces created before `env.template` changed.
- Installing or invoking dbt, DuckDB or Snowflake in any test.
