# PAN-4265 — 'Setup changed' banner after most merges: auto-sync and explain what changed

**Issue:** [PAN-4265](https://github.com/eltmon/overdeck/issues/4265)
**Status:** planned (auto-planning, 2026-09-27)

## Glossary

- **Sync inputs** — every file or value that can change what `pan sync` writes: the
  `sync-sources/` tree, `~/.overdeck/context/global.md`, each registered project's
  context file and `.pan/skills/` tree, the dev-mode flag, and the cwd-scoped skills
  mirror source (the `skills/` tree above the process cwd).
- **Sync manifest** — `~/.overdeck/.sync-manifest.json`. `pan sync` writes it last
  (`src/cli/commands/sync.ts`, `time('write-sync-manifest', () => writeSyncManifest())`).
  Today it holds `{ hash, generatedAt }`.
- **Startup gate** — `isStartupSyncNeeded()` in `src/lib/sync-startup-gate.ts`, used by
  `pan sync --if-changed` (spawned detached by `pan up`, `src/cli/up-sidecars.ts`
  `spawnDeferredSync`) and by `GET /api/sync-status`.
- **Light sync** — `pan sync` with env `OVERDECK_HERDR_SYNC_LIGHT=1`: skips the Herdr
  binary update and integration installs (`src/lib/herdr-setup/ensure.ts`, `const light = mode === 'sync' && env.OVERDECK_HERDR_SYNC_LIGHT === '1'`).
- **Banner** — `SyncRequiredBanner` (`src/dashboard/frontend/src/components/SyncRequiredBanner.tsx`),
  which polls `GET /api/sync-status` every 60 s and shows "Setup changed — sync context,
  hooks, and skills" plus a **Sync now** button that calls `POST /api/system/sync`.
- **Input key** — a stable string naming one sync input in the v2 manifest's `inputs`
  map (see FR-1 for the key grammar).
- **Global comparison** — the comparison the dashboard uses: all input keys except the
  `cwd/` and `cwd-skills/` keys.
- **Auto-sync service** — the new dashboard-server service
  `src/dashboard/server/services/sync-auto-service.ts` that evaluates sync status on a
  timer, runs the light sync itself, and serves the cached status to the route.
- **Attempt key** — the value the service remembers per auto-sync attempt so it never
  retries the same input set twice: the current `globalHash`, or `error:<reason>` when
  the hash cannot be computed.

## Problem

The dashboard shows "Setup changed" after most merges. Three causes, verified in code:

1. `SYNC_SOURCES` (`src/lib/paths.ts`, `resolveSyncSourcesRoot`) resolves to the main
   checkout's `sync-sources/` for a `pan reload` generation, so every merge that touches
   a skill, rule, hook, or template moves the hash. Nothing re-syncs after a reload:
   `pan reload` (`src/cli/commands/reload.ts`) never runs `pan sync`; only `pan up` spawns
   the deferred `pan sync --if-changed`.
2. The hash includes `process.cwd()` and the cwd's top-level `skills/` tree
   (`computeSyncInputHash`, `hash.update(process.cwd())`). The live dashboard's cwd is
   the primary checkout (`/home/eltmon/Projects/overdeck`, verified via
   `/proc/<pid>/cwd`). Any `pan sync` run from a workspace or another project writes a
   manifest hash the dashboard can never match, so the banner stays up after a
   successful sync.
3. The banner only says *that* something changed. It cannot say *what*, because the
   manifest stores one opaque hash.

## Decisions (made here; the executor does not re-decide)

- **D1 — One server-side mechanism covers both triggers.** The auto-sync service runs
  in the dashboard server. A `pan reload` replaces the server, so the new server's boot
  evaluation runs the light sync ("after reload"). The 60 s evaluation interval catches
  the main checkout's `sync-sources/` moving between reloads. `pan reload` itself is not
  changed.
- **D2 — Attempt once per attempt key.** A failed or non-converging auto-sync is not
  retried until the inputs change again (new attempt key). The operator can always
  click **Sync now**.
- **D3 — Banner visibility.** The banner shows only in states `failed`, `unresolved`,
  and `disabled` (defined in FR-5). It is hidden in `idle`, `pending`, and `running`.
  `unresolved` is the concrete meaning of "a change a sync can't apply by itself": the
  sync succeeded but the recomputed status still says `needed`.
- **D4 — Dashboard compares globally, CLI compares everything.** The dashboard uses the
  global comparison (excludes `cwd/` and `cwd-skills/` keys). `pan sync --if-changed`
  keeps comparing all inputs, as today.
- **D5 — Auto runs use `pan sync --if-changed` with `OVERDECK_HERDR_SYNC_LIGHT=1`.**
  `--if-changed` makes an auto run exit early when another sync (for example `pan up`'s
  deferred sync) already wrote a current manifest. Manual **Sync now** keeps running
  plain `pan sync` with the light env, as today.
- **D6 — Boot delay 60 s.** The service evaluates immediately at boot (on
  `setImmediate`, not inline) but does not start an auto run until
  `AUTO_SYNC_BOOT_DELAY_MS = 60_000` has elapsed. This lowers overlap with `pan up`'s
  detached deferred sync. State stays `pending` (banner hidden) during the delay.
- **D7 — Setting.** `context.auto_sync` in `~/.overdeck/config.yaml` (normalized
  `config.context.autoSync`), default `true`. Read on every evaluation, so a change
  applies without a restart. No settings-UI toggle in this issue.
- **D8 — Peer dashboards never auto-run.** When `isPeerDashboardProcess()` is true the
  service starts with `autoRun: false`; a needed sync reports state `disabled`.
- **D9 — The route serves cached status.** `GET /api/sync-status` returns the service's
  last evaluation; it no longer hashes the input tree per request.
- **D10 — Manifest v1 compatibility.** A v1 manifest (no `inputs`) is read as "changed,
  no per-file record". The first sync after upgrade rewrites it as v2.

## Requirements

### Functional

- **FR-1 — Per-input digests.** The gate collects a `Map<inputKey, sha256hex>` with
  this key grammar (paths use `/`, relative to the named root):
  - `sync-sources/<relpath>` — every file under `SYNC_SOURCES.root` (walked once).
  - `global-context` — `~/.overdeck/context/global.md`.
  - `project-context/<projectKey>` — `resolveProjectContextFile(config.path)` when it exists.
  - `project-skills/<projectKey>/<relpath>` — every file under `<project>/.pan/skills`.
  - `cwd` — digest of the `process.cwd()` string.
  - `cwd-skills/<relpath>` — every file under the resolved top-level `skills/` tree.
  - `dev-mode` — digest of `String(isDevMode())`.
  The existence check stays: every `SYNC_SOURCES` entry must exist, else throw
  `missing sync input: <key> at <path>`; missing `global.md` throws
  `missing global context layer`.
- **FR-2 — Manifest v2.** `writeSyncManifest()` writes
  `{ version: 2, hash, globalHash, generatedAt, inputs }`. `hash` is the sha256 over all
  sorted `key\0digest\n` lines; `globalHash` is the same over keys that do not start
  with `cwd`. `isStartupSyncNeeded()` keeps its signature and compares `hash`.
- **FR-3 — Global status read.** New export `readSyncInputStatus()` in
  `src/lib/sync-startup-gate.ts` (re-exported from `src/lib/sync.ts`) returns
  `{ needed, reason, attemptKey, summary, changedKeys }` using the global comparison and
  the FR-4 summarizer. `needed` is false only when the manifest's `globalHash` equals the
  current one.
- **FR-4 — Change summary.** New pure module `src/lib/sync-change-summary.ts` exports
  `summarizeSyncInputChanges(previous, current)` returning `{ summary, changedKeys }`
  (rules in Work item 1).
- **FR-5 — Auto-sync service.** States: `idle` (not needed), `pending` (needed, enabled,
  not attempted for this attempt key), `running`, `failed` (last attempt for this key
  failed), `unresolved` (last attempt for this key succeeded, still needed), `disabled`
  (needed and auto-sync is off or `autoRun: false`). It auto-runs the light sync for a
  `pending` key once the boot delay has passed.
- **FR-6 — Shared single-flight runner.** `POST /api/system/sync` and auto runs go
  through one runner; a call while a run is in flight awaits that run.
- **FR-7 — Status payload.** `GET /api/sync-status` returns
  `{ needed, reason, banner, summary, details, autoSync: { enabled, state, lastError, lastRunAt } }`.
- **FR-8 — Banner reason text.** The banner renders only when `banner` is true and
  shows the summary sentence; in `failed` it also shows "Auto-sync failed" and the
  first line of `lastError`.
- **FR-9 — Setting.** `context.auto_sync: false` stops auto runs; the banner then shows
  for every needed sync, as it does today.

### Non-functional

- **NFR-1** — No `execSync`/`spawnSync` in server-reachable code; the runner uses
  `execFile` promisified (as `meta.ts` does today) with the 180 s timeout.
- **NFR-2** — Hashing runs at most once per 60 s interval plus once after each run,
  independent of how many browser tabs poll.
- **NFR-3** — Service tests use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync`;
  never real delays (repo rule: fake timers for retry/backoff/delay tests).
- **NFR-4** — The service imports `sync-startup-gate` lazily (dynamic `import()`), like
  `meta.ts` does with `require`, to avoid a new circular ESM edge in the server bundle.

## Work items

### 1. Change summarizer (pure) — FR-4

**Files:** new `src/lib/sync-change-summary.ts`, new `src/lib/__tests__/sync-change-summary.test.ts`.

```ts
export interface SyncChangeSummary { summary: string; changedKeys: string[] }
export function summarizeSyncInputChanges(
  previous: Record<string, string> | null | 'no-record',
  current: Record<string, string>,
  opts?: { excludeCwd?: boolean },   // default true
): SyncChangeSummary;
```

Rules:
1. `previous === null` → `summary: 'No sync has been recorded on this machine'`, `changedKeys: []`.
2. `previous === 'no-record'` (v1 manifest) → `summary: 'Setup inputs changed since the last sync (the previous sync kept no per-file record)'`, `changedKeys: []`.
3. Otherwise `changedKeys` = keys added, removed, or whose digest differs, minus keys
   starting with `cwd` when `excludeCwd`, sorted ascending.
4. Map each changed key to a unit `(noun, id)`:
   - `sync-sources/skills/<name>/…` and `sync-sources/dev-skills/<name>/…` → `skill`, id = first dir name (prefixed `dev:` for dev-skills). A file directly in `skills/` uses its file name as id.
   - `sync-sources/rules/<rest>` → `rule`; `sync-sources/hooks/<rest>` → `hook`; `sync-sources/agents/<rest>` → `agent definition`; `sync-sources/templates/<rest>` → `template`; id = `<rest>`.
   - `sync-sources/plugins.json` → singleton `the plugin list`.
   - any other `sync-sources/<rest>` → `other sync-sources file`, id = `<rest>`.
   - `global-context` → singleton `the global context`.
   - `project-context/<key>` → `project context`, id = key.
   - `project-skills/<key>/<name>/…` → `project skill`, id = `<key>/<name>`.
   - `dev-mode` → singleton `dev mode`.
   - `cwd`, `cwd-skills/…` (only when `excludeCwd` is false) → singleton `the working-directory skills`.
5. Count distinct ids per noun. Order: skill, rule, hook, agent definition, template,
   project skill, project context, other sync-sources file, then singletons in the
   order listed above. Phrase `1 <noun>` or `<n> <noun>s`.
6. Join: one part → `A`; two → `A and B`; three or more → `A, B, and C`. Append ` changed`.
   Example: 3 skill dirs + 1 rule → `3 skills and 1 rule changed`.
7. No changed keys → `summary: 'Setup inputs changed'`.

**Tests** (`src/lib/__tests__/sync-change-summary.test.ts`): three files in two skill
dirs + one rule → `2 skills and 1 rule changed`; global context + plugin list + one hook
→ `1 hook, the plugin list, and the global context changed`; a `cwd` key change alone
with default opts → `changedKeys` empty; `null` and `'no-record'` messages; a removed
key counts as changed.

### 4. Auto-sync service — FR-5, FR-6, NFR-1..4

**Files:** new `src/dashboard/server/services/sync-auto-service.ts`, new
`src/dashboard/server/services/__tests__/sync-auto-service.test.ts`.

API:

```ts
export type AutoSyncState = 'idle' | 'pending' | 'running' | 'failed' | 'unresolved' | 'disabled';
export interface SyncStatusPayload {
  needed: boolean;
  reason: string;
  banner: boolean;          // true only for failed | unresolved | disabled
  summary: string | null;
  details: string[];        // first 20 changedKeys
  autoSync: { enabled: boolean; state: AutoSyncState; lastError: string | null; lastRunAt: string | null };
}
export interface SyncRunResult { ok: boolean; output?: string; error?: string }
export interface SyncAutoDeps {
  readStatus: () => Promise<{ needed: boolean; reason: string; attemptKey: string; summary: string; changedKeys: string[] }>;
  runPanSync: (args: string[]) => Promise<SyncRunResult>;
  autoSyncEnabled: () => boolean;
  now?: () => Date;
}
export function startSyncAutoService(opts: { autoRun: boolean; deps?: Partial<SyncAutoDeps> }): void;
export function stopSyncAutoService(): void;
export function getSyncStatus(): SyncStatusPayload;
export function runSyncNow(trigger: 'manual' | 'auto'): Promise<SyncRunResult>;
export function evaluateSyncStatus(): Promise<SyncStatusPayload>;  // exported for tests
```

Behavior:
1. Default deps: `readStatus` = dynamic `import('../../../lib/sync-startup-gate.js')` then
   `readSyncInputStatus()`; `runPanSync(args)` = promisified `execFile` of
   `panCliInvocation(args)` with env `{ ...process.env, OVERDECK_HERDR_SYNC_LIGHT: '1' }`,
   `timeout: 180_000`, returning `{ ok: true, output }` or
   `{ ok: false, error: 'pan sync failed: <stderr || message>' }` (same text as today's
   route); `autoSyncEnabled` = `loadConfigSync().config.context.autoSync`.
2. `startSyncAutoService` records `bootAt`, schedules `evaluateSyncStatus()` on
   `setImmediate`, and a `setInterval(evaluate, 60_000)` with `unref()`. Idempotent.
3. `evaluateSyncStatus()`: read status; compute state per FR-5 using
   `lastAttempt = { key, ok } | null`. If state is `pending`, `autoRun` is true, and
   `now - bootAt >= 60_000`, call `runSyncNow('auto')` (do not await inside the interval
   tick beyond the single-flight promise). Cache and return the payload.
4. `runSyncNow(trigger)`: if a run is in flight, return that promise. Otherwise set
   state `running`; args are `['sync', '--if-changed']` for `auto` and `['sync']` for
   `manual`; for `auto`, record `lastAttempt = { key: <attemptKey at start>, ok }`; for
   `manual`, record `lastAttempt = { key: <attemptKey at start>, ok }` too (a manual
   failure shows `failed` the same way). Set `lastError` (null on success) and
   `lastRunAt`, then call `evaluateSyncStatus()` before resolving.
5. After a successful run whose re-evaluation still reports `needed` with the same
   attempt key, state is `unresolved`; with a different key, state is `pending` (inputs
   moved during the run) and the next tick runs again.
6. Before the first evaluation completes, `getSyncStatus()` returns
   `{ needed: false, reason: 'not evaluated yet', banner: false, summary: null, details: [], autoSync: { enabled: true, state: 'idle', lastError: null, lastRunAt: null } }`.
7. Log one line per run: `[sync-auto] <trigger> sync ok` or `[sync-auto] <trigger> sync failed: <error>`.

**Tests** (fake timers, stub deps; no real `pan`). `vi.useFakeTimers()` also fakes
`setImmediate`, so after `startSyncAutoService(...)` call `await vi.advanceTimersByTimeAsync(0)`
before asserting the boot state:
- boot: needed key K → state `pending`, `banner: false`; before 60 s no `runPanSync` call; after `advanceTimersByTimeAsync(60_000)` exactly one call with `['sync','--if-changed']`;
- success then status not needed → state `idle`, `banner: false`;
- failure → state `failed`, `banner: true`, `lastError` set; further ticks with key K make no new call; key K2 → one new call;
- success but still needed with key K → `unresolved`, `banner: true`, no further call;
- `autoSyncEnabled` false → state `disabled`, `banner: true`, zero calls; `autoRun: false` same;
- `runSyncNow('manual')` while an auto run is in flight → `runPanSync` called once, both resolve the same result.

## Acceptance criteria

1. (Item 1) `summarizeSyncInputChanges` returns `3 skills and 1 rule changed` for three skill dirs and one rule, and ignores `cwd` keys by default — proven by `src/lib/__tests__/sync-change-summary.test.ts`.
2. (Item 2) After `writeSyncManifest()`, the manifest has `version: 2` and `readSyncInputStatus().needed` is false; a manifest written from another cwd still reads as not needed.
3. (Item 3) `mergeConfigs()` defaults `context.autoSync` to true and honors `auto_sync: false` without dropping `rules`.
4. (Item 4) With stubbed deps and fake timers, a needed key triggers exactly one `pan sync --if-changed` after 60 s, a failure yields `banner: true` with `lastError`, and the same key never runs twice.
5. (Item 5) `GET /api/sync-status` returns the FR-7 payload from the service; `POST /api/system/sync` still returns `{ ok: true, output }` or a 500 with `error`.
6. (Item 6) The banner test renders "Auto-sync failed" and the summary for `state: 'failed'`, and no banner for `pending`.
7. (Item 7) `docs/CONTEXT-LAYERS.md` and `configuration/context-layers.mdx` describe auto-sync, the failure-only banner, and `context.auto_sync`.

## Non-goals

- A settings-UI toggle for `context.auto_sync` (config file only).
- Changing `pan reload` or `pan up`; `pan up`'s deferred full sync stays as is.
- Routing the post-approve `pan sync` in `src/dashboard/server/routes/workspaces/merge-ops.ts` (~line 1787) through the new runner.
- `fs.watch`/inotify-based change detection.
- A cross-process lock for concurrent `pan sync` runs.
- Making the input hashing asynchronous.

## Hazards

- `pan sync` has no lock. An auto run can overlap `pan up`'s detached deferred sync or an
  operator's CLI sync. Mitigations: 60 s boot delay and `--if-changed` on auto runs. The
  sync writes are idempotent copies; overlap was already possible via the button.
- The first evaluation after upgrade sees a v1 manifest and auto-syncs once. Expected.
- `meta.ts` uses `require` for the gate to avoid a circular import; the service must use
  a dynamic `import()` for the same reason.
- An auto sync runs `cleanupAgentDirectories` and the xBRIEF audit, same as the existing
  **Sync now** button and `pan up`'s deferred sync. This is not new exposure.
