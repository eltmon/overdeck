## Glossary

- **MCP (Model Context Protocol):** the JSON-RPC protocol an outside tool (another agent harness, a chat bot) uses to list and call *tools* on a server. The SDK is `@modelcontextprotocol/sdk`, already a direct dependency at `^1.30.1` (`package.json`, line 171).
- **Tool:** one named MCP operation with a JSON Schema for its input. A client calls `tools/list` to see them and `tools/call` to run one.
- **Tool module:** the new code under `src/lib/mcp/` that defines every Overdeck tool once. Both transports use it.
- **Transport:** how MCP messages travel. This issue ships two:
  - **stdio:** `pan mcp serve` reads JSON-RPC from stdin and writes it to stdout.
  - **streamable HTTP:** `POST /mcp` on the dashboard server.
- **Stateless JSON mode:** the streamable HTTP transport configured with `sessionIdGenerator: undefined` and `enableJsonResponse: true`. Every `POST /mcp` gets a fresh MCP server and transport, answers with one JSON body, and keeps no session. There is no SSE stream and no `Mcp-Session-Id`.
- **Dashboard API client:** the small fetch wrapper in the tool module that calls the dashboard's existing REST routes with `Authorization: Bearer <odk_ token>`.
- **`odk_` token / access token:** a scoped, revocable credential in `~/.overdeck/access-tokens.json`, read and written only by `src/lib/access-tokens.ts`. A `kind: 'token'` record authenticates only from the `Authorization: Bearer` header (`resolveDashboardCredential`, `src/dashboard/server/routes/dashboard-auth.ts`).
- **MCP token:** an access token minted for an MCP client. It is an ordinary `kind: 'token'` record. Its default scopes are `read:state`, `read:conversations`, `operate`; **Copy MCP URL** adds `approve` only when the operator ticks the box.
- **Scope:** a named grant on a token. `ACCESS_TOKEN_SCOPES` lives at `src/lib/access-tokens.ts` line 42. `admin` satisfies every scope; `operate` satisfies `tell` (`scopeSatisfies`, line 81).
- **`approve` scope (new):** the grant to answer a blocking prompt — a permission prompt, a pane-choice menu, a pi `ask` modal, a Codex approval, a plan approval, or an agent's question. Only `admin` implies it. It is off by default.
- **Route-scope table:** `ROUTE_SCOPES` in `src/dashboard/server/route-scopes.ts` (line 26). It is the one list of which scope each `METHOD path` needs. Anything unlisted needs `admin`. The remote request gate (`remote-request-gate.ts`) and `rejectUnauthorizedDashboardRequest` both read it.
- **Remote request gate:** global middleware in `src/dashboard/server/remote-request-gate.ts`. It gates only paths under `/api/` and `/events/`. **It does not see `/mcp`.**
- **Root credential:** the internal token or the root session cookie. Both count as `admin`. MCP never accepts them (D-21: always fenced).
- **Reachable address:** a trusted origin that is not loopback, listed by `GET /api/anywhere/status` as `addresses[]` with `loopback: false`. After [PAN-1254](https://github.com/eltmon/overdeck/issues/1254) sets up Tailscale Serve, the machine's Tailscale Serve URL is one of them.
- **Fleet reach:** one MCP URL reaching conversations on linked machines. **Out of scope here**; [PAN-4651](https://github.com/eltmon/overdeck/issues/4651) adds it.

## Problem

Outside tools cannot drive Overdeck today. The only MCP code in the repo is the Channels bridge (`src/lib/channels/overdeck-bridge.ts`), which is a per-agent message-delivery bridge, not a control surface (parent PRD D-21). An operator who wants Claude Desktop, another harness or a chat bot to list conversations, read one, send a message, or start a conversation or worker has no supported path.

## Proposal (the shape)

**Both transports are one tool module that proxies to the dashboard's existing HTTP routes with the caller's Bearer `odk_` token.**

- `/mcp` (inside the dashboard server) forwards the presented token to the dashboard's own loopback URL, `getDashboardLoopbackApiUrl()` (`src/lib/config.ts`, the function after `getDashboardApiUrl`). It must **not** use `getDashboardApiUrl()`: inside the server process `DASHBOARD_URL` holds the public URL (PAN-3331).
- `pan mcp serve` forwards its token to `getDashboardApiUrl()`, as every CLI → dashboard call does.
- So the route-scope table stays the **only** scope authority, the remote request gate judges every tool call by the token's scopes (PAN-2351 D-7: a registry credential is judged by its scopes, never by its peer), and D-21's "no second path to any operation" holds by construction. The tool module never calls `src/lib` operation functions directly.
- The one check the tool layer adds is `approve` on `answer_question` (see D-4649-5), because the dashboard answers a Claude Code AskUserQuestion through the ordinary message route.

Starting a worker has no HTTP route today (`pan worker run` calls `startWorker()` in-process). This issue adds `POST /api/workers`, which calls the same `startWorker()` core (`src/lib/agents/worker/start.ts`), so the operation still has one path.

## Requirements

### Functional

- **FR-1 `approve` scope.** `ACCESS_TOKEN_SCOPES` gains `approve`. Only `admin` implies it; `operate` does not. `pan token create --scopes` accepts it.
- **FR-2 Approval routes need `approve`.** The route-scope table maps these eight routes to `approve` (all are `admin` today because they are unlisted):
  - `POST /api/conversations/:id/permission`
  - `POST /api/conversations/:id/pane-choice`
  - `POST /api/conversations/:id/pi-ask-answer`
  - `POST /api/conversations/:id/codex-approval`
  - `POST /api/conversations/:name/plan-action`
  - `POST /api/agents/:id/answer-question`
  - `POST /api/agents/:id/plan-action`
  - `POST /api/agents/:id/permissions/:requestId/respond`
- **FR-3 Routes the MCP tools need.** The route-scope table maps:
  - `GET /api/palette/search` → `read:conversations` (search tool);
  - `POST /api/conversations` → `operate` (start a conversation);
  - `POST /api/workers` → `operate` (start a worker).
- **FR-4 Worker start route.** `POST /api/workers` starts a registered worker through `startWorker()` and returns `{ id, cwd, branch }`.
- **FR-5 Tools.** The tool module exposes exactly these ten tools (names are the public contract):

  | Tool | Input | Calls | Scope the route needs |
  |---|---|---|---|
  | `list_machines` | none | `GET /api/environment` | none (allowlisted) |
  | `list_conversations` | `limit?` (1–200, default 50) | `GET /api/conversations?limit=` | `read:conversations` |
  | `search_conversations` | `query`, `limit?` (1–50, default 20) | `GET /api/palette/search?q=&limit=` | `read:conversations` |
  | `read_conversation` | `conversation`, `before?`, `limit?` | `GET /api/conversations/:name/messages[?before=&limit=]` | `read:conversations` |
  | `send_message` | `conversation`, `message` | `POST /api/conversations/:name/message` | `tell` |
  | `start_conversation` | `message`, `projectKey?`, `model?`, `harness?`, `effort?`, `issueId?`, `machine?` | `POST /api/conversations` | `operate` |
  | `start_worker` | `issueId`, `prompt`, `model?`, `harness?`, `effort?`, `readOnly?`, `name?`, `machine?` | `POST /api/workers` | `operate` |
  | `list_pending_input` | none | `GET /api/conversations/pending-input` | `read:conversations` (already, via the `GET /api/conversations/:id` row) |
  | `answer_question` | `conversation`, `answers[]`, `questions?[]` | `GET /api/conversations/:id`, then `POST /api/conversations/:name/message` | `tell`, **plus `approve` checked by the tool** |
  | `answer_permission` | `conversation`, `signature`, `choice` (`allow-once` \| `allow-always` \| `deny`) | `POST /api/conversations/:id/permission` | `approve` |

  No tool pairs devices, mints or revokes tokens, reads or writes settings, or reaches vault setup.
- **FR-6 `machine` parameter (this machine only).** `list_machines` returns this machine only. `machine` on `start_conversation` and `start_worker` accepts: omitted, `auto`, this machine's `label`, or its `environmentId`. All four run here. Any other value returns a tool error that names the known machine.
- **FR-7 stdio transport.** `pan mcp serve` serves the tool module over stdio with the token from the `OVERDECK_MCP_TOKEN` environment variable.
- **FR-8 streamable HTTP transport.** `POST /mcp` on the dashboard serves the tool module in stateless JSON mode. `GET /mcp` and `DELETE /mcp` answer 405 with `Allow: POST`.
- **FR-9 Copy MCP URL.** Settings → Anywhere gains a **Copy MCP URL** button. It mints an MCP token through the existing `POST /api/access-tokens`, copies `<reachable address>/mcp` to the clipboard, and shows the URL, the `Authorization` header and a ready client config, each with its own Copy button.
- **FR-10 Revoke from Settings → Anywhere.** Settings → Anywhere gains an **Access tokens** panel that lists `kind: 'token'` records and revokes one through the existing `DELETE /api/access-tokens/:id`.

### Non-functional

- **NFR-1 Always fenced (D-21).** `/mcp` accepts only a `kind: 'token'` credential without `admin`. `pan mcp serve` refuses a token that is unknown, revoked, not `kind: 'token'`, or carries `admin`. Neither ever uses the internal token.
- **NFR-2 Revocation.** A revoked MCP token fails its next `/mcp` request at once when revoked through the dashboard, and within 5 s when revoked by another process (the registry snapshot refresh, `ACCESS_TOKEN_REFRESH_MS`). Stateless mode holds no session, so there is nothing else to close.
- **NFR-3 Async only.** Server-reachable code uses async I/O only: no `execSync`, no new `*Sync` tmux calls.
- **NFR-4 No token in a URL** (PAN-2351 D-10, `docs/DASHBOARD-AUTH.md` "Tokens never travel in a URL query parameter"). The token travels only in the `Authorization` header.
- **NFR-5 No feature gate (parent NFR-8).** Everything here works without an overdeck.ai account.
- **NFR-6 stdout is protocol-only.** `pan mcp serve` writes only JSON-RPC to stdout; every diagnostic goes to stderr.

## Decisions (made here; recorded in `plan.autoDecisions[]`)

- **D-4649-1 Token travels in a header, never the URL.** The parent PRD says Copy MCP URL "copies the machine's Tailscale Serve URL for `/mcp` with the token". `resolveDashboardCredential` reads tokens only from the Bearer header, and PAN-2351 D-10 forbids tokens in URLs because URLs land in proxy and access logs. So the copied URL is `<address>/mcp`, and the dialog also offers the `Authorization: Bearer odk_…` header and a client config that carries both. Every common MCP client accepts headers (`claude mcp add --transport http <name> <url> --header "Authorization: Bearer …"`, and `mcp.json`-style `"headers"`). This is not a contradiction with the parent: "with the token" is satisfied by the config block.
- **D-4649-2 Stateless JSON mode.** It removes session bookkeeping, keeps revocation to "the next request fails", and needs no `registerDeviceConnection` entry. The tools need no server-initiated notifications.
- **D-4649-3 Default MCP scopes are `read:state`, `read:conversations`, `operate`.** `operate` covers `tell` and the two spawn routes. The checkbox "Allow answering questions and approving permissions" adds `approve`; it is unchecked by default. `admin` is never offered.
- **D-4649-4 `/mcp` does its own credential check.** `/mcp` is outside `/api/` and `/events/`, so the remote request gate skips it, and `rejectUnauthorizedDashboardRequest` would demand `admin` for an unlisted path. The `/mcp` handler therefore runs, in order: `validateOriginHeaders` (403 on an untrusted present Origin), `getInternalToken()` configured (else 503), `resolveDashboardCredential` (null → 401), `kind !== 'token'` → 403, scopes include `admin` → 403. Each tool's own scope is then enforced by the route the tool proxies to.
- **D-4649-5 `answer_question` checks `approve` in the tool layer.** The dashboard answers a Claude Code AskUserQuestion by posting a composed message to `POST /api/conversations/:name/message` (`src/dashboard/frontend/src/App/hooks/usePendingInputDialogs.ts`, the block that builds `Operator answered the pending question`). That route needs only `tell`. `answer_question` therefore refuses unless the token's scopes satisfy `approve`. **Stated plainly in the docs:** a `tell` token can still send any text with `send_message`, so the `approve` scope does not stop text from reaching a conversation that is waiting on a question. It does stop keystroke-driven answers (FR-2) and the `answer_question` / `answer_permission` tools.
- **D-4649-6 `answer_question` serves Claude Code conversations only.** It reads `GET /api/conversations/:id` first. A `harness` other than `claude-code`, `null` or absent returns a tool error ("answer_question supports Claude Code conversations; answer this one from the dashboard"). pi and Codex prompts are answered by keystroke routes that have no MCP tool in this issue.
- **D-4649-7 `pan mcp serve` credential.** The token comes only from `OVERDECK_MCP_TOKEN` (an argv flag would show in `ps`). With no token, the command exits 1 and prints the exact command to create one: `pan token create mcp --scopes read:state,read:conversations,operate`. It verifies the token locally (`refreshAccessTokens()` then `verifyAccessToken()`) before serving, so a bad token fails at start, not on the first tool call.
- **D-4649-8 Search uses the palette route.** `search_conversations` calls `GET /api/palette/search` and returns only its `conversations` array. Granting `read:conversations` on that route also exposes its `memory`, `observations` and `summaries` arrays to `read:conversations` tokens; these are derived from conversations, so the grant is consistent.
- **D-4649-9 Copy MCP URL address choice.** The dialog lists reachable addresses from `GET /api/anywhere/status` (same filter as `PairDeviceDialog`: `loopback === false`) and preselects the first `https://` one, else the first one. With no reachable address it shows the existing `no-reachable-address` problem message and offers this browser's origin, labelled "Works only on this machine". This is the seam where [PAN-1254](https://github.com/eltmon/overdeck/issues/1254) adds the Tailscale Serve URL.
- **D-4649-10 Minting is root-only, unchanged.** Copy MCP URL calls `POST /api/access-tokens`, which only the internal token or the root session may call (PAN-2351 D-11). A paired device's browser gets 403, and the dialog shows "Only a browser on this machine can create MCP tokens."
- **D-4649-11 Worker route is in-process.** `POST /api/workers` calls `startWorker()` directly, as the review pipeline already calls `spawnRun` in-process (`routes/workspaces/review-pipeline.ts`). `parentId` is `null`; `startWorker` stamps `startedBy: 'pan-worker'` itself.
- **D-4649-12 Low-level SDK `Server`, no zod.** `zod` is not a direct dependency. The tool module uses `Server` from `@modelcontextprotocol/sdk/server/index.js` with `setRequestHandler(ListToolsRequestSchema, …)` and `setRequestHandler(CallToolRequestSchema, …)` and hand-written JSON Schemas, as `overdeck-bridge.ts` does.
- **D-4649-13 Build order is not a blocker.** The parent's build order says W-INT2 follows W-CONV3; the issue says it depends on nothing. With fleet reach carved out to PAN-4651, this machine's half needs no link or cache table, so it can start now.

## Non-goals

- Any change to the Channels bridge (`src/lib/channels/overdeck-bridge.ts`).

## Intersecting repo rules (restated)
