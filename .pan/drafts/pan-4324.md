# PAN-4324 — `pan close` DoD post-merge row trusts stored agent status

**Issue:** [PAN-4324](https://github.com/eltmon/overdeck/issues/4324)
**Planned against:** `feature/pan-4324` @ `8245832d81e` (2026-09-28)

## Summary

`pan close` refuses almost every merged issue on Definition-of-Done row 5 (`post-merge`) with
`running agents: agent-pan-<n>, planning-pan-<n>`, although those agents exited hours earlier
and have no pane. Row 5 filters agents by the **stored** `state.json` `status`, and that field
is a spawn-time snapshot: since PAN-3917 nothing writes `stopped` back when a work or planning
agent exits on its own. The fix makes row 5 confirm each claimed-live agent with the liveness
oracle (`src/lib/agents/liveness.ts`) and count it as running only when the oracle does not
confirm it dead. The gate stays read-only.

## Glossary

- **DoD gate** — `src/lib/lifecycle/dod-gate.ts`. It evaluates the Definition-of-Done rows
  that `pan close` / dashboard Close Out must pass. Row definitions (id, number, title,
  expected text) live in `src/lib/lifecycle/dod.ts`.
- **Row 5 / `post-merge`** — "Post-merge lifecycle ran". Checked by `checkPostMergeRow()`.
  It passes when the post-merge lifecycle is observed (canonical state `verifying_on_main`,
  a PR `mergedAt`, or a terminal state) AND no work/planning agent of the issue is running.
- **Stored status** — `AgentState.status` read from each agent's `state.json`
  (`listRunningAgents()` in `src/lib/agents/queries.ts`, which despite its name returns every
  state row). It is a spawn-time snapshot and goes stale when an agent exits by itself
  (see `.overdeck/context/codebase/concerns.md`, entry "`state.json` `status` is a spawn-time
  snapshot").
- **Claimed-live** — a stored status of `starting` or `running`.
- **Liveness oracle** — `src/lib/agents/liveness.ts`. `isAlive(agentId)` returns a
  `LivenessVerdict`: `{ alive: true, paneAlive: true, runtimePid?, backendState? }` or
  `{ alive: false, reason: 'no-session' | 'pane-dead' | 'runtime-missing' | 'runtime-indeterminate' }`.
  It is backend-aware (Herdr socket or tmux session + pane + harness process subtree).
- **`isConfirmedDead(verdict)`** — `liveness.ts` line ~101. True only when the verdict is not
  alive AND the reason is not `runtime-indeterminate`. A probe that could not answer is never
  treated as death.
- **`tmuxActive`** — a flag on `listRunningAgents()` rows. It reflects only the tmux census,
  so it reads every Herdr agent as gone. Row 5 must NOT use it.

## Requirements

- **FR-1** — Row 5 counts a work/planning agent of the issue as running only when its stored
  status is claimed-live AND `isAlive` does not confirm it dead (`!isConfirmedDead(verdict)`).
- **FR-2** — A claimed-live agent whose verdict is confirmed dead (`no-session`, `pane-dead`,
  `runtime-missing`) does not block row 5. The row's `observed` text still contains
  `no running work/planning agents` and names the dismissed ids as
  `(stored running, not live: <ids>)`.
- **FR-3** — A claimed-live agent whose verdict is `alive: true` (any `backendState`, including
  `idle`/`done`) blocks row 5 exactly as today: status `miss`, `observed` contains
  `running agents: <ids>`.
- **FR-4** — A claimed-live agent whose probe returns `runtime-indeterminate` or throws blocks
  row 5 (`miss`). The `observed` text reports it as `liveness indeterminate: <ids>`, separate
  from `running agents:`. One thrown probe never collapses the row into
  `post-merge evidence unavailable`.
- **FR-5** — `docs/MERGE-WORKFLOW.md` close-out section states the row 5 liveness rule.
- **NFR-1** — The gate writes nothing: no `state.json` status write, no event, no pane action.
- **NFR-2** — Liveness is injectable: `PostMergeRowDeps` gains a required `isAlive` seam so unit
  tests never touch Herdr or tmux.
- **NFR-3** — Probes for multiple agents run concurrently (`Promise.all`); there are at most a
  handful of agents per issue.

## Decisions

1. **Dep shape.** Add `isAlive: (agentId: string) => Promise<LivenessVerdict>` to
   `PostMergeRowDeps`. It returns the verdict, not a boolean, so the row can report
   `runtime-indeterminate` separately. It is **required**; the default object
   `defaultPostMergeRowDeps` sets it to `(agentId) => isAlive(agentId)` from
   `../agents/liveness.js`. An optional dep falling back to the real probe would make unit tests
   hit Herdr/tmux.
2. **Keep the stored-status prefilter.** Probe only claimed-live (`starting`/`running`) rows.
   This mirrors `deriveServedAgentStatuses` (claimed-live rows are confirmed; others pass
   through). Probing stored-`stopped` rows is out of scope: on Herdr a pane can outlive
   `pan kill`, and probing them would newly block issues the operator just stopped.
3. **Indeterminate counts as running.** Same rule every remediator uses via `isConfirmedDead`:
   a probe that cannot answer must never let close-out proceed.
4. **No special case for idle Herdr panes.** `alive: true` with `backendState: 'idle' | 'done'`
   still counts as running. The post-merge handoff is supposed to close those panes; a live pane
   after merge is a real miss (issue AC2).
5. **Never use `tmuxActive`** from the `listRunningAgents` rows (it reads every Herdr agent as
   gone).
6. **Row definition text in `dod.ts` is unchanged.** The expected text
   ("agents paused, workspace stack stopped, and verifying-on-main label applied") still holds.

## Non-goals

- Probing agents whose stored status is `stopped` (or any non-claimed-live status).
- Writing `stopped` back to `state.json` from the gate or anywhere else.
- Special-casing Herdr `backendState: 'idle' | 'done'` panes as not running.
- Changing any other DoD row, the row definition text in `src/lib/lifecycle/dod.ts`, or
  `pan close` control flow.
- Using `tmuxActive` or the census as the liveness source.
