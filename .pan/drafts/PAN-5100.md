# PAN-5100 — Capture phone and dashboard client errors in PostHog

**Issue:** [PAN-5100](https://github.com/eltmon/overdeck/issues/5100)
**Status:** planned (auto mode, 2026-11-06)
**Related:** [PAN-5021](https://github.com/eltmon/overdeck/issues/5021) (phone PostHog telemetry, open; this PRD supersedes its identity and opt-out decisions, see D-3), PAN-5016 (Anywhere events), PAN-5084 (CI/test exclusion), PAN-4835 H-4 (phone tokens cannot call admin routes).

## Glossary

- **Phone app / phone shell** — `apps/mobile`, the Capacitor app. It renders the frontend's `/m` screens (`MobileApp`) and sends every same-host `/api/` and `/ws/` request through the channel shims to the machine it is viewing.
- **Channel shims** — `installChannelShims` from `@overdeck/anywhere-channel/web`, installed in `apps/mobile/src/main.tsx` line 17. They replace `globalThis.fetch` and `WebSocket` for same-host `/api/` and `/ws/` requests only. Requests to `us.i.posthog.com` use the WebView's own network stack.
- **Machine** — the computer running the Overdeck dashboard server that the phone is paired with. It owns the telemetry setting (`resolveTelemetryState()` in `src/lib/telemetry/config.ts`).
- **Browser telemetry door** — `src/dashboard/frontend/src/lib/telemetry.ts`, the only browser module that imports `posthog-js` (`docs/TELEMETRY.md`, "Implementation boundaries").
- **Closed domain** — a property whose allowed values are a fixed list in `TELEMETRY_PROPERTY_DOMAINS` (`packages/contracts/src/telemetry.ts`). `tests/unit/contracts/telemetry-schema.test.ts` fails when any catalog property type widens to `string` or `number` (`PropertyValuesAreRestricted`). `tests/unit/telemetry-docs.test.ts` fails when `docs/TELEMETRY.md` and the contract disagree on any event, property or domain value.
- **Super property** — a property registered once with `posthog.register()` and sent on every later browser event, including `$exception`. Not part of the typed catalog. Precedent: `install_id`, `install_kind`, `operatorHash` in `initTelemetry()`.
- **Request failure** — a `fetch` to a same-origin `/api/` or `/events/` path that resolves with HTTP status ≥ 400, or that rejects (network error, timeout, abort).
- **Route template** — a path with id segments replaced by `:param` names, for example `/api/conversations/:id`. Only templates from a closed list are ever sent.
- **Route area** — the first path segment after `/api/` (for example `settings` for `/api/settings/models`), from a closed list.
- **Client config** — the JSON answer of the new `GET /api/telemetry/client-config` route.
- **Link** — the phone's secure channel to the machine (`apps/mobile/src/shell/connection.ts`).
- **Connection phase** — `deriveConnectionPhase()` in `src/dashboard/frontend/src/lib/connectionState.ts` line 68: `live | delayed | unreachable | restarting | unauthorized`.

## Problem

The operator saw "Couldn't load conversations" and other errors in the TestFlight phone app on 2026-11-06. None reached PostHog.

1. The phone app runs no telemetry. `apps/mobile/src/shell/MachineView.tsx` lines 1-6 say the frontend's telemetry is not run because it reads admin routes. `initTelemetry()` (`src/dashboard/frontend/src/lib/telemetry.ts` line 103) reads `GET /api/settings`, an admin route a phone token cannot call. Only `src/dashboard/frontend/src/main.tsx` line 21 calls it.
2. The desktop captures unhandled errors, root error-boundary crashes and three action failures. A failed read such as `fetchConversationList()` in `src/dashboard/frontend/src/components/mobile/MobileConversations.tsx` lines 30-35 throws `new Error('Failed to load conversations: <status>')`, and the component renders "Couldn't load conversations." at line 76. Nothing is captured.

## Goal

Every request failure, crash and link failure the operator can see, on the phone and on the desktop, reaches PostHog with enough detail to diagnose it, under the existing opt-out and privacy rules.

## Decisions

These are final. The work agent does not revisit them.

- **D-1 Capture at the fetch layer, not in the React Query caches.** Issue decision 3 asked for `QueryCache.onError` / `MutationCache.onError`. Those handlers receive only what the query function threw; every call site builds its own `Error` (for example the message string above), so route and status are not available there. 236 frontend files call `fetch` directly and only 50 use `fetchWithTimeout`. A single wrapper of `globalThis.fetch` sees every request with its URL, method and status. It is the same technique as `apps/mobile/src/shell/requestLog.ts` (lines 51-60). No `QueryCache`/`MutationCache` handlers are added.
- **D-2 `query_key_root` is dropped.** A fetch wrapper cannot know which query called it. The issue's other properties (route, method, status, client) are kept. `route` already names the endpoint.
- **D-3 PAN-5100 wins over PAN-5021.** The phone uses the machine's telemetry setting (no phone-side switch) and the machine's install id (no separate phone telemetry id). PAN-5021's `persistence: 'memory'` choice is kept: opening another machine reloads the page (C-7), so in-memory persistence stops machine A's id from reaching machine B's events.
- **D-4 Identity.** The phone calls `posthog.init` with `persistence: 'memory'` and `bootstrap: { distinctID: installId }`, so phone events share the `distinct_id` of the machine's Node events (`src/lib/telemetry/service.ts` line 79 uses `getOrCreateInstallId()` as `distinctId`). The desktop keeps its current anonymous browser `distinct_id`; changing it would break the continuity of existing charts. Both clients register `install_id`.
- **D-5 Common properties are super properties.** `client` (`phone` | `desktop`), `platform` (`ios` | `android` | `web`), `app_version` (phone only: `APP_VERSION` from `apps/mobile/src/shell/config.ts` line 10, which reads `apps/mobile/package.json`; the issue's reference to `version.ts` is wrong — that file only compares versions), `build_commit` (the machine's `getBuildInfo().buildCommit`; omitted when null), `install_kind`, `install_id`, and `operatorHash` when grouping is on. They are registered with `posthog.register()`, so `$exception` events carry `client=phone`. They are documented in prose, not in the catalog, because `app_version` and `build_commit` are free strings.
- **D-6 `route` is a closed domain.** Domain `client_route` = every distinct `path` in `ROUTE_SCOPES` (`src/dashboard/server/route-scopes.ts`), which is exactly the set of non-admin routes a phone token can call, plus `other`. A test asserts every `ROUTE_SCOPES` path is in the domain. Desktop admin routes therefore read `route=other`; the separate `route_area` property (D-7) still says which part of the API failed.
- **D-7 `route_area` is a closed domain.** Domain `client_route_area` = the distinct first segment after `/api/` of every `NO_LOSS_MATRIX` HTTP surface whose disposition is not `DELETE` (`tests/unit/lib/overdeck/no-loss-matrix.ts`), plus `telemetry` (the new route's area), plus `events` (for `/events/...` paths), plus `other`. A test asserts the matrix areas are a subset of the domain. A segment that is not in the list reads `other`, so an id can never be sent.
- **D-8 `status` is a closed domain.** `request_status`: `400`, `401`, `403`, `404`, `408`, `409`, `413`, `422`, `429`, `other_4xx`, `500`, `502`, `503`, `504`, `other_5xx`, `network`, `timeout`, `aborted`. A rejected fetch classifies as: `DOMException` named `TimeoutError` ⇒ `timeout`; `DOMException` named `AbortError` ⇒ `aborted`; anything else ⇒ `network`. `fetchWithTimeout` (`src/dashboard/frontend/src/lib/apiFetch.ts`) aborts with `AbortSignal.timeout`, whose reason is a `TimeoutError`.
- **D-9 Throttle.** At most one `client_request_failed` per (`route`, `route_area`, `status`) per 60 seconds per page load. The throttle map lives in module memory; a reload starts it again.
- **D-10 Consent on the phone.** The phone reads `GET /api/telemetry/client-config` (scope `read:state`) after the machine view mounts. It initializes PostHog only when `effectiveEnabled` is `true`. It caches the last answer per machine in `localStorage` under `overdeck.telemetry.<environmentId>` and initializes from a cached `true` immediately at mount, so a link that is down from the start is still reported. A fresh answer of `false` calls `disableTelemetry()` (opt out, stop capturing) and removes the cache entry. A later "on" answer re-enables capture with `opt_in_capturing` without a second `posthog.init` (WI-4b). Sign-out runs `localStorage.clear()` (`apps/mobile/src/shell/ShellApp.tsx` line 377), which removes every cached answer. Consequence, documented for the operator: turning telemetry off on a machine reaches the phone on its next successful connection to that machine.
- **D-11 The machine supplies the PostHog key and host to the phone.** The phone's Vite root is `apps/mobile` (`apps/mobile/vite.config.ts` `root: here`), so the frontend's `.env.production` key is not loaded. The client config returns `posthogKey` and `posthogHost` from the same values `AnalyticsService` uses (`process.env.POSTHOG_API_KEY ?? DEFAULT_POSTHOG_API_KEY`, `process.env.POSTHOG_HOST ?? DEFAULT_POSTHOG_HOST`, `src/lib/telemetry/service.ts` lines 12-13 and 232-234). The desktop keeps its build-time env values.
- **D-12 When telemetry is off, the client config returns only `{ "effectiveEnabled": false }`.** No install id, key or host leaves the machine.
- **D-13 The desktop keeps `/api/settings`.** Its telemetry block gains an optional `buildCommit`.
- **D-14 Link health uses a separate reason domain.** `linkFailureReason` (`src/lib/telemetry/anywhere.ts`) maps `MachineLinkError` codes that the phone never throws, and its domain `link_failure_reason` has no `none`, `removed` or drop values. New domain `link_reason` reuses its spellings where the meaning is the same (`offline`, `unreachable`, `pairing_refused`, `identity_mismatch`, `unsupported`, `other`) and adds the phone's own values. Mapping is in WI-9.
- **D-15 A link "drop" is the connection phase leaving `live`.** `MachineDialer` (`packages/anywhere-channel/src/dial-machine.ts` lines 37-59) exposes only `onRecovered`; the operator-visible symptom is the `/ws/rpc` stream going down, which the phase already models. A drop counts only after the phase has been `live` once in this page load (the first connect is not a drop). A drop that starts within 5 000 ms after a foreground resume (`markResumed`, `apps/mobile/src/shell/lifecycle.ts` line 25) has reason `resume`. `packages/anywhere-channel` is not changed.
- **D-16 The observer is installed once per page, outermost.** Desktop: in `main.tsx` before `void initTelemetry()`. Phone: in `main.tsx` after `installChannelShims` (and after `installRequestLog` when enabled), loaded by dynamic import before `ShellApp`, so it wraps the shimmed `fetch` and sees the app's requests. Requests to other hosts (PostHog itself) are ignored, so capture never recurses.
- **D-17 No new runtime dependency is planned for `apps/mobile`.** Vite resolves `posthog-js` from the importing file (`src/dashboard/frontend/src/lib/telemetry.ts`) up to `src/dashboard/frontend/node_modules`. **Implementation checkpoint:** run `npm --prefix apps/mobile run build`. If it fails to resolve `posthog-js`, add `"posthog-js"` to `apps/mobile/package.json` `dependencies` with the exact version from `src/dashboard/frontend/package.json` and run `bun install` (this also changes `bun.lock`). Do not add a Vite alias (`apps/mobile/src/__tests__/build-config.test.ts` asserts the alias list exactly).
- **D-18 Store privacy declarations change in this PR.** `apps/mobile/store/privacy-app.html` line 42, `apps/mobile/RELEASE.md` lines 153-156 and `apps/mobile/ios/App/App/PrivacyInfo.xcprivacy` say the app has no analytics or crash reporting. Shipping `posthog-js` with them unchanged is a false declaration.
- **D-20 Phone 403s are reported as-is.** Shared components inside `MobileApp` can still call an admin route a phone token cannot reach (PAN-4835 H-4); each becomes `client_request_failed` with `status=403`. That is the inventory of scope gaps the phone UI still has, which is diagnostic, not noise. The current scope inventory (`apps/mobile/request-log.json`) holds one such row (`GET /api/fleet/needs-you` → 403), and the 60 s throttle bounds repeats. `docs/TELEMETRY.md` states this (WI-11).
- **D-19 Out-of-repo and post-merge steps are operator steps.** The `overdeck.ai/privacy/app` copy (repo `eltmon/overdeck-landing`), the App Store Connect App Privacy answers, the Play Data safety form, and the TestFlight upload (`apps/mobile/RELEASE.md`) happen after merge. The work agent records them in `apps/mobile/acceptance/PAN-5100.md` as pending.

## Requirements

### Functional

- **FR-1** The contract defines events `client_request_failed` and `phone_link_state` with closed-domain properties (see "Contract shape").
- **FR-2** `GET /api/telemetry/client-config` answers a phone credential (`read:state`) with the client config (D-10, D-11, D-12).
- **FR-3** The desktop `/api/settings` telemetry block carries `buildCommit` when the build has one.
- **FR-4** The browser telemetry door initializes from a supplied config, registers the D-5 super properties, and can be disabled at runtime.
- **FR-5** Every request failure on a page with telemetry on produces at most one `client_request_failed` per D-9 key per 60 s, with `client`, `route`, `route_area`, `method`, `status`.
- **FR-6** The phone initializes PostHog only when the machine's effective setting is on (live or cached, D-10), and never when it is off.
- **FR-7** A render error inside `MobileApp` produces `$exception` with `client=phone` and shows a fallback with a Reload button.
- **FR-8** The phone sends `phone_link_state` on link failure, drop, recovery and route change, with a reason, the route and the time to recover.
- **FR-9** The phone's store privacy declarations describe the analytics and diagnostics the app now sends.
- **FR-10** `docs/TELEMETRY.md`, `configuration/telemetry.mdx` and `configuration/phone.mdx` describe what the phone and the desktop send.

### Non-functional

- **NFR-1** No event carries a response body, conversation name or id, message text, issue title, file path, machine label, environment id or full URL. Only closed-domain values and the D-5 super properties are sent. `sanitizePostHogEvent` stays in force.
- **NFR-2** Telemetry never changes app behavior: the fetch wrapper returns the inner `fetch` result or rethrows its error unchanged; every capture is wrapped so a throwing PostHog client is swallowed.
- **NFR-3** No events from Vitest or CI. `capture()` and `captureException()` keep their `import.meta.env.MODE === 'test'` guard. The machine's own CI/temporary-home exclusion (PAN-5084) makes the client config answer `effectiveEnabled: false` there.
- **NFR-4** Tests that exercise the 60-second throttle or any delay use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`. Tests that need a timeout error construct `new DOMException('…', 'TimeoutError')` directly; never rely on `AbortSignal.timeout` under fake timers (happy-dom ignores fake timers for it).

Add to `TELEMETRY_PROPERTY_DOMAINS` (alphabetical position, matching the existing order):

```ts
  client_route: TELEMETRY_CLIENT_ROUTES,          // every ROUTE_SCOPES path, sorted, then "other"
  client_route_area: TELEMETRY_CLIENT_ROUTE_AREAS, // sorted areas (D-7), then "other"

  link_reason: ["none", "offline", "no_path", "unreachable", "removed", "pairing_refused", "identity_mismatch", "unsupported", "channel_failed", "delayed", "restarting", "unauthorized", "resume", "other"],
  link_route: ["direct", "relay", "unknown"],
  link_state: ["failed", "dropped", "recovered", "route_changed"],
  recovery_bucket: ["none", "under_1s", "1s-4s", "5s-14s", "15s-59s", "60s+"],
  request_status: ["400", "401", "403", "404", "408", "409", "413", "422", "429", "other_4xx", "500", "502", "503", "504", "other_5xx", "network", "timeout", "aborted"],
  telemetry_client: ["phone", "desktop"],
```

Add to `TELEMETRY_EVENT_CATALOG`:

```ts
  client_request_failed: { client: "telemetry_client", route: "client_route", route_area: "client_route_area", method: "http_method", status: "request_status" },
  phone_link_state: { state: "link_state", reason: "link_reason", route: "link_route", recover_time: "recovery_bucket" },
```

`TELEMETRY_CLIENT_ROUTES` is a literal `as const` array written out in the source (no runtime derivation, so the type stays a closed union): the distinct `path` values of `ROUTE_SCOPES` after WI-3 adds `/api/telemetry/client-config`, sorted with `Array.prototype.sort()` (default UTF-16 order), then `"other"`. Generate the list once with:

```bash
grep -oE "path: '[^']*'" src/dashboard/server/route-scopes.ts | sed "s/path: '//; s/'//" | { cat; echo /api/telemetry/client-config; } | LC_ALL=C sort -u
```

`TELEMETRY_CLIENT_ROUTE_AREAS` is likewise literal: the distinct first segments after `/api/` of `NO_LOSS_MATRIX` HTTP surfaces whose disposition is not `DELETE`, plus `events` and `telemetry`, sorted with `LC_ALL=C sort -u`, then `"other"`.

Add types and two pure helpers next to `bucketRelayBytes`:

```ts
export type TelemetryClient = TelemetryPropertyValue<"telemetry_client">
export type TelemetryClientRoute = TelemetryPropertyValue<"client_route">
export type TelemetryClientRouteArea = TelemetryPropertyValue<"client_route_area">
export type TelemetryHttpMethod = TelemetryPropertyValue<"http_method">
export type TelemetryRequestStatus = TelemetryPropertyValue<"request_status">
export type TelemetryLinkState = TelemetryPropertyValue<"link_state">
export type TelemetryLinkReason = TelemetryPropertyValue<"link_reason">
export type TelemetryLinkRoute = TelemetryPropertyValue<"link_route">
export type TelemetryRecoveryBucket = TelemetryPropertyValue<"recovery_bucket">
export type ClientRequestFailedProperties = EventProperties<"client_request_failed">
export type PhoneLinkStateProperties = EventProperties<"phone_link_state">

/** PAN-5100: the closed route template and area for a same-origin path (query and hash ignored). */
export function clientRouteOf(pathname: string): { route: TelemetryClientRoute; route_area: TelemetryClientRouteArea }

/** PAN-5100: an HTTP status (≥ 400) as a closed bucket. */
export function bucketRequestStatus(status: number): TelemetryRequestStatus

/** PAN-5100: milliseconds to recover as a coarse bucket. */
export function bucketRecoveryMs(ms: number | null): TelemetryRecoveryBucket

/** PAN-5100: what `GET /api/telemetry/client-config` returns (D-10..D-12). */
export interface TelemetryClientConfig {
  readonly effectiveEnabled: boolean
  readonly installId?: string
  readonly installKind?: TelemetryInstallKind
  readonly buildCommit?: string
  readonly operatorHash?: string
  readonly posthogKey?: string
  readonly posthogHost?: string
}
```

`clientRouteOf` rules, in order:

1. Strip everything from the first `?` or `#`. Split on `/` and drop empty segments.
2. Among `TELEMETRY_CLIENT_ROUTES` (excluding `other`) with the same number of segments, a template matches when every literal segment is equal and every `:name` segment is a non-empty segment. Pick the match with the most literal segments; on a tie, the first in list order. No match ⇒ `route: "other"`.
3. `route_area`: when segment 0 is `events`, `events`. When segment 0 is `api` and segment 1 is in `TELEMETRY_CLIENT_ROUTE_AREAS`, that segment. Otherwise `other`.

`bucketRequestStatus`: an exact listed code returns itself as a string; other 400-499 ⇒ `other_4xx`; 500 and above ⇒ `other_5xx` unless listed. `bucketRecoveryMs`: `null` ⇒ `none`; < 1 000 ⇒ `under_1s`; < 5 000 ⇒ `1s-4s`; < 15 000 ⇒ `5s-14s`; < 60 000 ⇒ `15s-59s`; else `60s+`.

### WI-4b Browser door: consent lifecycle, pending exceptions, throw-safety

- **Files:** `src/dashboard/frontend/src/lib/telemetry.ts`, `src/dashboard/frontend/src/lib/__tests__/telemetry.test.ts` (same files as WI-4, so it runs after WI-4).
- **Module state:** `let loaded = false` (true once `posthog.init` has run in this page); `let consent: 'unknown' | 'on' | 'off' = 'unknown'` (capturing is allowed only when `on`; `initialized` from WI-4 becomes `consent === 'on'`); `let loadedIdentity: { installId?: string; key: string; host: string } | null = null`; `const pendingExceptions: Array<{ error: unknown; context: TelemetryExceptionContext }> = []`; `export const PENDING_EXCEPTION_LIMIT = 5`.
- **Steps:**
  1. **Re-enable without re-init.** posthog-js treats a second `init()` as a no-op, and `opt_out_capturing()` stores the denial in `localStorage` even when event persistence is `memory`. So, in `initTelemetryFromConfig` with an "on" config: when `loaded` is already true, do not call `posthog.init`; call `posthog.opt_in_capturing({ captureEventName: false })`, re-register the super properties and set `initialized = true`. When `loaded` is false, call `posthog.init(…)`, set `loaded = true`, then, if `posthog.has_opted_out_capturing()` returns true (a denial stored by an earlier page), call `posthog.opt_in_capturing({ captureEventName: false })`. The machine's current answer is the authority on every boot.
  2. **`disableTelemetry()`**: when `loaded`, call `posthog.opt_out_capturing()`; set `consent = 'off'`; clear `pendingExceptions`. Wrap in try/catch. An `initTelemetryFromConfig` call with an "off" config also sets `consent = 'off'`.
  3. **Pending exceptions.** `captureException(error, context)` while `consent === 'unknown'` (and outside test mode) pushes `{ error, context }` onto `pendingExceptions` while it holds fewer than `PENDING_EXCEPTION_LIMIT` entries; later ones are dropped. While `consent === 'off'` an exception is dropped, never queued, so a crash during a known-off period is never sent by a later "on". When `initTelemetryFromConfig` turns capturing on, it sends each pending entry once through the normal sanitized path and empties the list. When it returns false because the config is off, it empties the list without sending. This covers a `MobileApp` crash on its first render, which reaches `componentDidCatch` before `MachineView`'s boot effect runs.
  4. **Throw-safety.** `capture()` and `captureException()` wrap their `posthog.*` calls in try/catch and return normally when the SDK throws (NFR-2).
  5. **Reconcile on every "on" answer.** When `loaded` is true, an "on" config always re-registers the D-5 super properties and runs the existing operator-hash rule (register when present, `posthog.unregister('operatorHash')` when absent), so a machine that turned grouping off stops sending the hash. When the config's `installId`, key or host differs from `loadedIdentity`, the SDK cannot switch identity in place (the phone bootstraps `distinct_id` at `init`), so the door calls `posthog.opt_out_capturing()`, sets `consent = 'off'` for the rest of this page and returns false; the phone has already cached the fresh config (WI-6), and the next page load (opening a machine or restarting the app reloads the page) initializes with the new identity and opts back in through step 1.
- **Tests:** on → `disableTelemetry()` → on calls `opt_out_capturing` then `opt_in_capturing({ captureEventName: false })`, calls `posthog.init` once in total, and a later `capture()` reaches `posthog.capture`; with `has_opted_out_capturing` mocked to return true at first init and an "on" config, `opt_in_capturing({ captureEventName: false })` is called; a `captureException` before init followed by an "on" init sends exactly one `posthog.captureException`, and followed by an "off" init sends none; seven pre-init exceptions send at most five; off → `captureException` → on sends no `posthog.captureException` for the exception raised while off; a loaded door given an "on" config without `operatorHash` calls `posthog.unregister('operatorHash')`; a loaded door given an "on" config with a different `installId` calls `opt_out_capturing`, returns false, and a later `capture()` sends nothing; with `posthog.capture` and `posthog.captureException` mocked to throw, `capture()` and `captureException()` return without throwing.

## Critique response

### telemetry cannot resume after opt-out

Accepted. WI-4b adds the re-enable path: a door that has already run `posthog.init` in this page re-enables with `posthog.opt_in_capturing({ captureEventName: false })` instead of a second `init` (a no-op in posthog-js), and a first `init` with an "on" config calls the same opt-in when `has_opted_out_capturing()` reports a denial stored by an earlier page. Tests cover on → off → on and a stored denial at first init.

### initial phone render crashes are missed

Accepted. WI-4b adds a consent-gated pending-exception list in the browser door (at most 5 entries): `captureException` before init queues, an "on" init flushes once, an "off" init or `disableTelemetry()` discards. WI-7 notes that the boundary relies on it. Tests cover the flush with "on" and the discard with "off".

### background machine links are reported under the open machine

Accepted. WI-9b's reporter takes `currentEnvironmentId` and ignores `routeOpened` for any other machine before touching state, so notification-preference sync links to other paired machines never emit events or change the open machine's route. Test added.

### a throwing PostHog client can break the crash fallback

Accepted. WI-4b makes `capture()` and `captureException()` swallow SDK exceptions, and WI-7's `componentDidCatch` wraps its call too. WI-7 adds a test where `captureException` throws and the Reload fallback still renders.

### exceptions captured while telemetry is off

Accepted. WI-4b now tracks consent as `unknown | on | off`. Exceptions queue only while consent is `unknown`; while `off` they are dropped, so a later "on" never sends them. Test: off → crash → on sends nothing for that crash.

### reconnect does not refresh consent

Accepted. WI-6's `bootPhoneTelemetry` subscribes to the connection phase and re-reads the client config on every transition into `live`, applying a fresh "off" before further captures. Test: cached on → failed read → link recovers → fresh off ⇒ disabled.

### fresh config cannot replace cached properties

Accepted. WI-6 passes every fresh "on" answer to the door, and WI-4b step 5 reconciles it: super properties are re-registered and an absent `operatorHash` is unregistered. A changed install id, key or host stops capture for the rest of the page (posthog-js cannot change a bootstrapped identity in place); the fresh config is already cached, so the next page load initializes with it. Tests cover the hash removal and the identity change.
