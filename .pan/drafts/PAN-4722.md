# PAN-4722: Update all updates the `pan connect` runtime, not the global npm prefix

**Issue:** https://github.com/eltmon/overdeck/issues/4722
**Builds on:** PAN-4656 (`pan connect`, `.pan/drafts/PAN-4656.md`) and PAN-4654 (fleet versions and Update all, `.pan/drafts/PAN-4654.md`).

## Glossary

- **Connect runtime:** the per-home Overdeck install that `npx @overdeck/core connect` creates at `<OVERDECK_HOME>/runtime` with `npm install --prefix` (PAN-4656 D-4). The package lives at `<OVERDECK_HOME>/runtime/node_modules/@overdeck/core` (`runtimePackageRoot()`, `src/lib/anywhere/connect-runtime.ts:73`). The supervisor unit or launch agent and the dashboard run from it.
- **Package root:** the directory of the running `@overdeck/core` package. `packageRoot` in `src/lib/paths.ts:97` (`export const packageRoot = resolvePackageRootForDir(currentDir);`). Node resolves the main module through `realpath`, so this path has no symlinks.
- **OVERDECK_HOME:** `getOverdeckHome()` in `src/lib/paths.ts:9` — `process.env.OVERDECK_HOME` or `~/.overdeck`. The supervisor unit sets it (`src/lib/systemd.ts`, `OVERDECK_HOME=${overdeckHome}` in `renderSupervisorUnit`), so the dashboard a connect machine runs sees the same value `pan connect` used.
- **Install mode:** `FleetInstallMode` (`packages/contracts/src/fleet-versions.ts:13`) and `UpdateInstallMode` (`packages/contracts/src/update.ts:14`): `npm-global`, `development`, `desktop`. Reported in `GET /api/versions/self` and in the update snapshot.
- **UpdateManager:** `src/lib/update-manager.ts`. `check()` reads the npm dist-tags; `install()` runs the npm install and `pan sync` in the background and moves the snapshot `installing` → `ready` or `error`.
- **Update all / fleet update job:** `FleetUpdateService` (`src/dashboard/server/services/fleet-update-service.ts`). For the Overdeck component it calls `getUpdateManager()`, `check()`, `install()`, polls to `ready`, then restarts through `restartDashboardDetached()` (PAN-4654 D-8, D-9).
- **`ensureDurableRuntime(home, version)`:** `src/lib/anywhere/connect-runtime.ts:96`. No-op when the runtime already has `version`; else runs `npm install --prefix <home>/runtime --no-audit --no-fund --omit=dev @overdeck/core@<version>` (600 s timeout) and checks that `dist/cli/index.js` and `dist/supervisor/server.js` exist.
- **`panCliInvocation(args)`:** `src/lib/pan-cli-invocation.ts:17`. Returns `{ command: process.execPath, args: [<packageRoot>/dist/cli/index.js, ...args] }`, so a child CLI runs without `pan` on `PATH`.

## Problem

On a machine set up with `npx @overdeck/core connect`:

1. `currentInstallMode()` (`src/dashboard/server/routes/misc/updates.ts:10-13`) returns `npm-global` for anything that is not desktop or dev mode, and `getUpdateManager()` (`updates.ts:18-24`) builds the manager with `installMode: overdeckDevMode ? 'development' : 'npm-global'`.
2. `UpdateManager.install()` (`src/lib/update-manager.ts:143`) runs `npm install --global @overdeck/core@<v>`. On a system Node the global prefix is `/usr` and needs sudo, so it fails. Where it succeeds, it installs a global copy that nothing runs: the dashboard restarts from the runtime on the old version, and the fleet view keeps reporting the machine out of date.
3. Even when the npm step succeeds, `install()` then runs `execFileAsync('pan', ['sync'])` (`update-manager.ts:144`). A connect-only machine has no `pan` on `PATH` (the docs tell operators to use `~/.overdeck/runtime/node_modules/.bin/pan`), so this throws `ENOENT`, the snapshot goes to `error`, the fleet job marks Overdeck `failed`, and the dashboard is never restarted. The next Update all sees the old running version as `available` again and fails the same way.
4. `pan update` (`src/cli/commands/update.ts:74`) hardcodes the same `npm install --global`, so `~/.overdeck/runtime/node_modules/.bin/pan update` on a connect machine has the same bug.

Today's workaround is `npx @overdeck/core@latest connect` on the machine (`cli/machines.mdx`, "Updating and removing").

## Expected

When the running package root is `<OVERDECK_HOME>/runtime/node_modules/@overdeck/core`, Update all (and the in-app update dialog, and `pan update`) installs the target version into that runtime with the same command as `ensureDurableRuntime()`, then restarts the dashboard from it. Every other install keeps today's behavior.

## Decisions

- **D-1 No new install mode on the wire.** The issue offers two fixes: a fourth install mode (`npm-runtime`) or a prefix-aware `UpdateManager.install()`. This plan takes the prefix-aware install. `FleetInstallMode` and `UpdateInstallMode` stay unchanged and a connect machine keeps reporting `npm-global`, which here means "an npm-installed `@overdeck/core`, global or the connect runtime". *Why:* the peer decoder is a strict literal set, so a new literal breaks every viewer that predates it; nothing displays the value; and the only code that branches on it (`fleet-update-service.ts:226-228`) treats both installs the same. The smaller change satisfies the Expected section with no contract change.
- **D-2 Detection compares package roots.** `isRuntimePackageRoot(root, overdeckHome)` is true exactly when `root` and `runtimePackageRoot(overdeckHome)` name the same directory. Both sides are canonicalized with `realpathSync`, falling back to `path.resolve` when the path does not exist. *Why:* `packageRoot` is already symlink-free (Node realpaths the main module) but `OVERDECK_HOME` may contain a symlink; comparing raw strings would silently turn the fix off. `realpathSync` is a filesystem call, not a child process, and it runs once per process (the manager is cached), so the no-`execSync` rule is not affected.
- **D-3 Reuse `ensureDurableRuntime()` for the install.** The runtime install calls `ensureDurableRuntime(overdeckHome, version)` instead of building its own npm argv. *Why:* it is the exact command the issue asks for, it already has the 600 s timeout, `--omit=dev`, the npm stderr tail, and the check that `dist/cli/index.js` exists before anything restarts from it. Its failure text ends with "then run pan connect again", which is still a correct remedy on a connect machine; it is not changed.
- **D-4 `pan sync` runs through `panCliInvocation(['sync'])` in both install kinds.** *Why:* after the in-place install, `<packageRoot>/dist/cli/index.js` is the new CLI, and it needs no `pan` on `PATH`. For a global install `packageRoot` is the global package, so the same file runs as before.
- **D-5 A `pan sync` failure after a good install does not fail the install.** The snapshot moves to `ready` with `error: "Installed <v>, but pan sync failed: <message>. Run pan sync on this machine."`, and the failure is logged with `console.error`. *Why:* the files are already replaced. Failing would leave the old server running over new files and would repeat on every Update all. With `ready`, the fleet job restarts the dashboard as for any install.
- **D-6 `pan update` gets the same install target.** It calls the same exported install helper instead of its own `npm install --global`. When the CLI runs from the runtime, the failure hint names the runtime npm command instead of `sudo npm install -g`, and success prints the command that restarts the dashboard from the runtime. *Why:* the operator's documented way to run commands on a connect machine is `~/.overdeck/runtime/node_modules/.bin/pan`, so `pan update` there must not reach the global prefix.
- **D-7 Desktop mode is not touched.** `getUpdateManager()` keeps `installMode: overdeckDevMode ? 'development' : 'npm-global'`; only the new `runtimeHome` option is added. The desktop app updates through its bridge.
- **D-8 Release ordering is not a constraint.** Because D-1 adds no literal, this change can ship in any release after PAN-4654 without a compatibility note.

## Requirements

### Functional

- **FR-1** `isRuntimePackageRoot(root: string, overdeckHome: string): boolean` is exported from `src/lib/anywhere/connect-runtime.ts`. It returns true exactly when `root` and `runtimePackageRoot(overdeckHome)` are the same directory after canonicalization (D-2).
- **FR-2** When `UpdateManager` is constructed with `runtimeHome: <home>` (non-null), `install()` installs the target version by calling `ensureDurableRuntime(<home>, <version>)` and never runs `npm install --global`.
- **FR-3** When `runtimeHome` is null or omitted, `install()` runs `npm install --global @overdeck/core@<version>`, as today.
- **FR-4** After a successful npm step, `install()` runs `pan sync` as `process.execPath <packageRoot>/dist/cli/index.js sync` (`panCliInvocation(['sync'])`), never a bare `pan` resolved from `PATH` (D-4).
- **FR-5** When the `pan sync` step fails after a successful npm step, the snapshot moves to `ready` with `error` starting `Installed <version>, but pan sync failed:` (D-5). When the npm step fails, the snapshot moves to `error` with the npm failure message, as today.
- **FR-6** `getUpdateManager()` in `src/dashboard/server/routes/misc/updates.ts` passes `runtimeHome: getOverdeckHome()` when `isRuntimePackageRoot(packageRoot, getOverdeckHome())`, else `null`. Fleet Update all and `POST /api/update/install` on a connect machine therefore install into `<OVERDECK_HOME>/runtime` and then restart the dashboard through the unchanged `restartDashboardDetached()`.
- **FR-7** `pan update` (`src/cli/commands/update.ts`) installs through the same helper with the same detection. From the runtime, a failure prints the runtime npm command (not `sudo npm install -g`), and success prints `<OVERDECK_HOME>/runtime/node_modules/.bin/pan restart --dashboard --now` as the next step.
- **FR-8** The docs listed in WI-6 describe that Update all, the update dialog and `pan update` update a `pan connect` machine's `~/.overdeck/runtime`.

### Non-functional

- **NFR-1** No contract change: `FleetInstallMode`, `UpdateInstallMode`, `MachineVersionsReportSchema` and `GET /api/versions/self` stay byte-for-byte the same.
- **NFR-2** No `execSync` and no new `*Sync` child-process call on the dashboard path. The only sync call added is `realpathSync` inside `isRuntimePackageRoot` (D-2).
- **NFR-3** Unit tests run no real `npm`, `pan` or network: `UpdateManager` takes injectable install dependencies, and the existing `fetchImpl` stub supplies `check()`.

/** The side effects of an Overdeck install; injectable for tests (PAN-4722). */
export interface UpdateInstallDeps {
  /** Runs a command; rejects on a non-zero exit. */
  execFile: (file: string, args: readonly string[]) => Promise<void>;
  ensureDurableRuntime: (overdeckHome: string, version: string) => Promise<{ root: string; installed: boolean }>;

export async function installOverdeckPackage(

  deps: UpdateInstallDeps = defaultInstallDeps,

    return;

  await deps.execFile('npm', ['install', '--global', `@overdeck/core@${version}`]);
}

/** D-5: the files are already replaced, so a sync failure is reported, never fatal. Null on success. */
private async syncAfterInstall(version: string): Promise<string | null> {
  const sync = panCliInvocation(['sync']);
  try {
    await this.installDeps.execFile(sync.command, sync.args);
    return null;
  } catch (error) {
    const message = error instanceof Error ? error.message : String(error);

    return `Installed ${version}, but pan sync failed: ${message}. Run pan sync on this machine.`;

}

- No `execSync` in dashboard server code or anything it reaches; use `execFile` via `promisify` (already the pattern in `update-manager.ts`). `realpathSync` (filesystem, not a child process) is the one sync call added (D-2).
- Tests must not read source files (the lint rejects source-reading tests) and must not add `skipIf`/`.only`. Use injected dependencies, never real npm.
- No timers are added. `vi.waitFor` polls an in-memory snapshot; it does not wait on a retry delay, so the fake-timer rule does not apply.
- Run only the touched test files locally (`npx vitest run <file>`), never the full `npm test`.
- File-size ratchet: `update-manager.ts` is 155 lines and grows by about 40; no file nears a cap.
- Commits carry an `Item: <item-id>` trailer per xBRIEF item.

## Non-goals

- No new install mode (`npm-runtime`) in the contracts or the versions report (D-1).
- No change to the desktop app's update path or to how `getUpdateManager()` derives `installMode` (D-7).
- No restart of the supervisor service after an update. The supervisor keeps its old in-memory code until its next restart; its unit's `ExecStart` path does not change, so the next start runs the new version.
- No change to `ensureDurableRuntime()` itself, its error text, or its 600 s timeout.
- No change to how the fleet job polls, times out or restarts (`fleet-update-service.ts`).
- No detection of a runtime under an `OVERDECK_HOME` that differs from the process's own `OVERDECK_HOME`.
- The D-5 sync warning is not surfaced in the fleet row (`fleet-update-service.ts:319` sets the Overdeck detail to `installed <v>; restarting the dashboard`) or in `UpdateDialog.tsx`, which renders `error` only in the `error` phase. It is logged with `console.error` and carried in the pre-restart `GET /api/update/status` snapshot only.

## Hazards

- **H-1 Lazy imports between install and restart.** npm replaces the running server's files in place. A lazy `import()` between the install and the restart may fail. This is PAN-4654 H-3 and applies to global installs today; the restart follows at once.
- **H-2 Timeout parity.** `ensureDurableRuntime` times out at 600 s, the same as the fleet job's 10-minute poll cap. A slow npm can make the job report "did not finish within 10 minutes" just before the install itself fails. Accepted; both report a failure.
- **H-3 `pan update` from a shell without the service's `OVERDECK_HOME`.** If `pan connect` ran with a custom `OVERDECK_HOME` and the operator's shell does not set it, the CLI's detection is false and it falls back to the global install (today's behavior). The dashboard path is unaffected because the unit sets `OVERDECK_HOME`.
- **H-4 Dev workspaces.** In a repository checkout `packageRoot` is the checkout, so detection is false and `install()` is still refused for `development`.
