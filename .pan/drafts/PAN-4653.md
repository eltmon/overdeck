# PAN-4653: Auto-settle a conversation when its linked PR merges

**Issue:** [PAN-4653](https://github.com/eltmon/overdeck/issues/4653)
**Parent:** split from [PAN-4639](https://github.com/eltmon/overdeck/issues/4639) (merged in `8e7ead8a0aa`, PR #4709). PAN-4639 added the `settled_at` / `settle_reason` / `snoozed_until` columns, `src/lib/overdeck/conversation-triage-store.ts`, `POST /api/conversations/triage`, the Settled section and `TriageMenuItems`. This issue builds on all of them.
**Sibling:** auto-settle when idle is [PAN-4655](https://github.com/eltmon/overdeck/issues/4655) (not touched here).
**Status:** planned 2026-11-01 (`pan plan --auto`, high effort), verified against `01beb6b92f0`.

## Summary

Replace the PR-sync **auto-archive** with a non-destructive **auto-settle**. When the PR sync sweep sees a conversation's linked PR go from open to merged or closed, and every live link of that conversation is now merged or closed, it writes `settled_at = now`, `settle_reason = 'merge'` through the PAN-4639 triage store. It never archives, never stops anything, and no longer reads terminal liveness. A new global key `conversations.auto_settle_on_merge` (default **on**) controls it, a per-conversation override (`on` / `off` / `inherit`) beats the global key, and agent conversations are never auto-settled. The old key `conversations.auto_archive_on_merge` and the verb `pan conv auto-archive-on-merge` are removed.

## Glossary

- **PR sync sweep** — `runPullRequestSyncOnce` in `src/dashboard/server/services/pull-request-sync-service.ts`. Runs at boot +30 s, then every 60 s, on the primary dashboard only.
- **Transition** — within one sweep, a link whose stored snapshot was `open` when the sweep began (`ctx.openBefore`) gets a new snapshot whose state is `merged` or `closed` (`applySnapshot`, line 176). A first read of an already-merged PR is **not** a transition.
- **Finished-PR conversations** — the set of conversation names with a transition this sweep. Today it is `SweepContext.settled` (line 141); this issue renames it to `prFinished` because "settled" now means the operator-facing triage state.
- **Live link** — a row in `conversation_pull_requests` for the conversation with `dismissed_at IS NULL` (`link.dismissedAt === null`).
- **Settle** (PAN-4639) — set `conversations.settled_at` (epoch ms) and `settle_reason`. The conversation moves to the Settled section of the list. The session keeps running. Written by `settleConversation(name, reason, nowMs)` in `conversation-triage-store.ts`, which keeps an existing `settled_at` and reason and always clears `snoozed_until`.
- **Settle reason** — `manual` | `merge` | `idle`. This issue writes `merge`, also for a PR that was closed without merging.
- **Global setting** — `app_settings` row `conversations.auto_settle_on_merge`, value `'true'` or `'false'`. Unset reads as **on**.
- **Override** — new column `conversations.auto_settle_override` (text). Stored `'on'`, `'off'`, or NULL. NULL is exposed as `'inherit'` everywhere outside SQL.
- **Effective auto-settle** — `override === 'inherit' ? global : override === 'on'`.
- **Agent conversation** — a name for which `isAgentConversationName` (`src/lib/overdeck/conversations.ts:419`) is true: prefixes `agent-`, `planning-`, `specialist-`.
- **Triage write door** — `POST /api/conversations/triage` (`src/dashboard/server/routes/conversation-triage.ts`) and `applyTriageUpdate` in the store.
- **Enrichment** — `enrichConversationList` in `src/lib/overdeck/conversation-list.ts`; it already spreads `listConversationTriage(...)` into every row (line 205 and line 335), so any field added to `ConversationTriage` reaches `GET /api/conversations` with no change to `conversation-list.ts`.

## Decisions

- **D1 — Same trigger, same gate.** Keep today's trigger (the per-conversation open → merged/closed transition in `applySnapshot`) and today's gate (the conversation has at least one live link and every live link's snapshot state is `merged` or `closed`). A conversation with one merged PR and one open PR is not settled until the second one finishes.
- **D2 — Closed counts as merge.** A PR closed without merging settles the conversation too, with `settle_reason = 'merge'`. The reason enum stays `manual | merge | idle`.
- **D3 — No liveness check.** Settling touches no session, so the sweep no longer lists terminal sessions. `listLiveConversationSessions`, the `listLiveSessions` parameter and the `tmuxExecAsync` import are deleted. This removes the tmux-only liveness concern.
- **D4 — Effective setting.** `override === 'inherit' ? global : override === 'on'`. Global unset ⇒ on.
- **D5 — Agent conversations are never auto-settled**, whatever the override says.
- **D6 — Already settled ⇒ untouched.** A conversation that is already settled keeps its original `settled_at` and `settle_reason` (a manual settle stays `manual`). `settleConversation` already behaves this way; the sweep also skips it so it is not counted or logged.
- **D7 — A future snooze wins.** A conversation whose `snoozedUntil` is later than the sweep's `now` is **not** auto-settled and its snooze is kept. Rationale: the operator explicitly asked to see it again at that time; settling would clear `snoozed_until` (PAN-4639 D3) and silently drop the reminder. Because auto-settle fires only on the transition, such a conversation simply returns to Inbox at its wake time. A snooze whose time has passed does not block settling (settling clears it).
- **D8 — Fires once.** Only the transition fires, so a conversation the operator unsettles after an auto-settle stays unsettled on every later sweep. A PR that is reopened and then merged again is a new transition and settles again; that is accepted.
- **D9 — Override storage.** New nullable column `conversations.auto_settle_override text`. `'on'` / `'off'` stored as is; `'inherit'` stored as NULL; any other stored value reads as `'inherit'`. Read and written only through `conversation-triage-store.ts`, exposed on `ConversationTriage.autoSettleOverride` so the existing enrichment and route carry it.
- **D10 — Override writes go through the triage write door.** `TriageUpdate` gains `autoSettleOverride?: 'on' | 'off' | 'inherit'`; `POST /api/conversations/triage` accepts an update that sets only it. No new per-conversation route. The frontend uses a separate mutation that pushes **no** undo entry and shows **no** Undo toast (the override is a preference, not a triage move).
- **D11 — Global setting routes.** `GET /api/conversations/auto-settle-on-merge` → `{ enabled: boolean }`; `POST` with body `{ enabled: boolean }` → `{ enabled: boolean }`, 400 when `enabled` is not a boolean, 403 on a failed `validateOrigin`. Both live in `conversation-triage.ts`.
- **D12 — Old key and verb are removed, not aliased.** The behavior changed (archive → settle) and the default changed (off → on), so neither a fallback read of `conversations.auto_archive_on_merge` nor an `auto-archive-on-merge` alias would mean the same thing. The stale `app_settings` row is left in place and never read. Running `pan conv auto-archive-on-merge` after this change fails with Commander's unknown-command error.
- **D13 — CLI verbs.** `pan conv auto-settle-on-merge [on|off]` (global; prints `on` or `off` when the value is omitted). `pan conv auto-settle <query> [on|off|inherit]` (override; with the value omitted it prints `on`, `off`, or `inherit (global: on)` / `inherit (global: off)`). Two verbs because a single optional positional cannot tell a conversation query from `on`/`off`. The override verb goes through the dashboard route (so the enrichment cache is invalidated) and falls back to `applyTriageUpdate` when the dashboard is down, using `viaDashboard` in `pull-requests.ts`.
- **D14 — Settings toggle.** A self-contained component `AutoSettleOnMergeRow` with its own `useQuery` / `useMutation` against D11 (the `merge-train/config.ts` shape: optimistic update, restore on error), rendered in `SettingsPage.tsx` as a child of `ConversationSettingsSection`, before `ConversationSearchSection`. It never reads or writes `formData` or `settings-api.ts`.
- **D15 — Row and tab menu.** An "Auto-settle on merge" submenu in `TriageMenuItems` with three items: `Use global setting` (inherit), `Always` (on), `Never` (off). The current choice shows a lucide `Check` icon and `aria-current="true"`. It is shown wherever `TriageMenuItems` is shown today (top-level rows and the tab menu).
- **D16 — Refresh path.** The sweep calls `invalidateConversationListEnrichmentCache()` after it settles anything; the 10 s list poll picks it up. No new event type.
