# PAN-5237 — Composer: cancel a message while it shows "Sending…"

**Issue:** [PAN-5237](https://github.com/eltmon/overdeck/issues/5237)
**Builds on:** PAN-5184 (composer clears at once, per-conversation send queue), PAN-4278 (permission-pending holds, receipts), PAN-4279 (degraded-mode offline holds).

## Glossary

- **Bubble** — an optimistic user message in `useComposerStore().byConversation[name].optimistic` (type `ChatMessage`, `src/dashboard/frontend/src/components/chat/chat-types.ts`). It renders "Sending…" while `!acknowledged`.
- **Queued send** — a bubble whose POST has not started. It waits in the per-conversation chain `enqueueConversationSend` (`src/dashboard/frontend/src/lib/composerSendQueue.ts`).
- **In-flight send** — a bubble whose `POST /api/conversations/<name>/message` has started (`markSendStarted` was called) and has not answered.
- **Held bubble** — `deliveryState: 'held'`: the server answered 409 `permission-pending` (PAN-4278). It is resent by `releaseHeldMessages`.
- **Offline-held entry** — a `FailedMessage` with `heldOffline: true` in the outbox (`failed[]`), created by `holdSend` while the server is unreachable (PAN-4279). `flushHeldMessages` sends it on reconnect.
- **Outbox** — `failed[]` in the composer slice, rendered by `MessagesTimeline.tsx` with Retry/Copy/Discard.
- **Receipt** — the server's per-`(conversation name, clientMessageId)` record in `src/dashboard/server/services/conversation-message-receipts.ts`. It replays the first response for a repeated id for 24 h.
- **Commit point** — the single synchronous moment in `deliverConversationMessage` after which the message (or its side effect) can reach the agent: immediately before `deliver(...)` (pane paste), `deliverConversationViaControlChannel` (Pi), `compactConversationNative`, or `handleComposerCommandMessage` for a command message.
- **Delivery gate** — the object a receipt hands to the delivery handler: `isCancelled()` (read-only check) and `commit()` (atomic check-and-claim). After `commit()` returns `true` the send can no longer be cancelled.
- **Tombstone** — a receipt created by a cancel request for an id the server has not seen. It makes a late POST with that id answer 409 `cancelled` without delivering.
- **Restore target** — a registration the mounted composer makes so a cancelled message's text can be written back into its editor (`isEmpty()` / `setText()`).

## Problem

A bubble in the "Sending…" state cannot be cancelled. Since PAN-5184 a bubble is "Sending…" either because it waits in the client send queue or because its POST is in flight (up to 120 s, `composerSend.ts` line 135). The operator wants to abort such a message. Held messages already offer **Discard**, which drops the text; nothing else can be stopped.

## Decisions

- **D1 — One commit point per irreversible step.** The server can cancel only before the commit point. It never cancels between paste and Enter. A cancel that arrives after `commit()` answers `delivered`.
- **D2 — Three server outcomes.** `POST /api/conversations/:name/message/cancel` answers `{ outcome: 'cancelled' | 'delivered' | 'unknown' }`. Only `cancelled` lets the client say the message was cancelled.
  - receipt pending (not settled, not committed) → mark cancelled → `cancelled`;
  - receipt settled without a commit (the handler refused before delivering, e.g. 409 `permission-pending`, 400, 503 Kimi) → `cancelled` (nothing was delivered and the receipt replays that same refusal for this id);
  - receipt already cancelled → `cancelled`;
  - receipt committed (delivering or done, success or failure) → `delivered`;
  - no receipt → write a tombstone, answer `unknown` (the POST may not have arrived yet, or the receipt was lost to a restart or eviction — the server cannot tell, so it does not claim a cancel; the tombstone still refuses a late POST);
  - tombstone → `unknown` until a POST has hit it and been refused, then `cancelled` (a second Cancel click must not turn an unproven cancel into a claimed one).
- **D3 — The client never aborts the in-flight fetch.** This deviates from the issue's wording ("aborts the HTTP request"). After `cancelled`, the bubble leaves at once, but the POST stays open until the server's handler answers 409 `cancelled` at its next gate check. Reason: the server has no per-conversation serialization (verified 2026-11-13: no per-session lock, mutex or promise map in `src/lib/agents/`, `src/lib/terminal-backends/`, `conversation-message.ts` or `conversation-delivery.ts`, and the permission check and ensure-main run outside `deliverAgentMessage` anyway); aborting would let the next queued message start while the cancelled handler may still be sending ensure-main keys (`Down`/`Up`/`Enter`/`Escape`) to the same pane, which can submit a partial paste and breaks FR-5. The `AbortController` stays timeout-only.
- **D4 — Agent-endpoint sends are cancellable only while queued or held.** `/api/agents/:id/message` has no receipts, so an in-flight send to it cannot be confirmed cancelled. Its bubble shows no Cancel control while in flight.
- **D5 — Composer-empty rule.** "Empty" means the editor text is blank (trimmed), the conversation has no pending attachments, and no pending citations. Only a mounted composer can take the text back (restore target registered by `ComposerFooter`). If none is registered (switched away, `hideComposer`), the message goes to the outbox as **Cancelled**.
- **D6 — Held bubbles: Cancel replaces Discard.** Cancel keeps the text (composer or outbox); the outbox still offers Discard. `discardHeld` is removed.
- **D7 — Offline-held entries get a Cancel button.** Cancel stops the reconnect send: the text goes to the empty composer, or the entry becomes a Cancelled outbox entry (`heldOffline` cleared, so `flushHeldMessages` skips it).
- **D8 — A Cancelled outbox entry** is `{ kind: 'prompt', code: 'cancelled', retryable: true, deliveryUnknown: false, heldOffline: undefined, error: undefined }`. `deliveryUnknown: false` makes `retryFailed` mint a fresh `clientMessageId` (existing rule at `composerStore.ts` line 692). Its retry button reads **Resend**. It does not keep the steer/follow-up mode: the bubble never stored `deliverAs`, so Resend sends a normal message.
- **D9 — `/pan` commands and scheduled ("when limits reset") messages are not cancellable.** They do not produce Sending… bubbles.
- **D10 — Size.** The change spans server receipts, the delivery handler, one route, the client store, two timeline components and docs (≈26 files, more than 6 path prefixes). It is one contract: the client cancel cannot be verified without the server outcome, and the server endpoint has no user-visible effect alone. `plan.metadata.sizeJustification` records this.

## Requirements

- **FR-1** Every unacknowledged Sending… bubble with a `clientMessageId` shows a **Cancel** control, except an in-flight send to the agents endpoint (D4) and while a cancel is in progress or was refused.
- **FR-2** Cancelling a queued bubble removes it; it is never POSTed. Its text goes to the composer if empty (D5), else to the outbox as **Cancelled**.
- **FR-3** Cancelling an in-flight bubble calls the cancel route. On `cancelled` the bubble leaves (FR-2 disposition). On `delivered` the bubble stays and reads "Already delivered, can't cancel". On `unknown` or a failed cancel request the bubble stays and reads "Couldn't confirm the cancel", and Cancel is offered again.
- **FR-4** The server refuses delivery for a cancelled id: the message handler answers 409 `{ code: 'cancelled', deliveryUnknown: false, retryable: false }` at its next gate check and calls no delivery function.
- **FR-5** Cancelling one message never reorders, drops, or overlaps the others: later queued messages still go out in Send order, and the next POST starts only after the cancelled POST has answered.
- **FR-6** Held bubbles (permission-pending) cancel like queued ones (D6); offline-held entries cancel per D7.
- **FR-7** Never claim a cancel that did not happen: the bubble leaves as cancelled only on a client-side queued/held cancel, a server `cancelled` outcome, or a POST answer with `code: 'cancelled'`.
- **NFR-1** `src/dashboard/server/routes/conversations.ts` does not grow beyond 1034 lines.
- **NFR-2** Delay-based tests use `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()` (repo rule: fake timers for retry/backoff/delay tests).
- **NFR-3** No `execSync` or sync tmux calls in server code (repo rule); the gate is in-memory and synchronous by design (no I/O).
