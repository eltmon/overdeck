# PAN-4683 — `pan start --remote` re-plans an already-planned issue

**Issue:** [PAN-4683](https://github.com/eltmon/overdeck/issues/4683) — found during the PAN-4295 live smoke test.
**Status:** draft (auto-planned)

## Glossary

- **Primary checkout** — the project's main repo directory (`<projectRoot>`, on `main`). Planned specs do NOT land here until the feature merges.
- **Local workspace** — the git worktree at `<projectRoot>/workspaces/feature-<id-lower>/`, checked out on branch `feature/<id-lower>`. Planning runs here and commits the spec here.
- **Spec** — the canonical xBRIEF file `.pan/specs/<YYYY-MM-DD>-<ISSUE>-<slug>.xbrief.json` written by complete-planning. `parseXBriefFilename()` (`src/lib/xbrief/lifecycle.ts`) recognizes the name.
- **Feature branch ref** — `refs/heads/feature/<id-lower>` (local) or `refs/remotes/origin/feature/<id-lower>` (last-fetched origin copy).
- **Remote workspace** — a Fly Machine created by `createRemoteWorkspace()` (`src/lib/remote-workspace.ts`), recorded in `~/.overdeck/workspaces/<id>.yaml` (`loadWorkspaceMetadata`, `location: 'remote'`).
- **complete-planning** — `completePlanningForIssue()` in `src/lib/overdeck/planning-promotion.ts`, the server side of `pan plan finalize`.
- **Auto-start consent record** — `~/.overdeck/agents/planning-<id>/auto-spawn-on-finalize.json`, owned by `src/lib/planning/auto-spawn-consent.ts`. It already carries `workModel` (PAN-3022) from planning spawn to the post-planning work-agent spawn.
- **Consent-bearing spawn** — a `POST /api/agents` request with `autoSpawnConsentRequired: true`. Both the post-planning auto-start (`completePlanningAutoSpawn`) and the deferred hand-off retry (`deferred-handoff.ts` → `spawnWorkAgentThroughAgentsEndpoint(issueId, undefined, true, startedBy)`) send it.

## Problem

Three gaps on one path, all verified against the code at `fca895281a2`:

1. **Plan detection misses the feature branch.** `src/cli/commands/start.ts` (search `PAN-2407: route unplanned issues`, lines 870–875):

   ```ts
   const projectRoot = findProjectRoot(id);
   const existingPlan = workspacePath && !isRemote
     ? findPlanSync(workspacePath)
     : await Effect.runPromise(findSpecByIssue(projectRoot, id));
   ```

   With `--remote`, `findWorkspaceWithLocation(id, 'remote')` (start.ts ~line 191) never looks at the local workspace: it returns `{ workspacePath: null, isRemote: true }` (no VM yet) or `{ workspacePath: <metadata id>, isRemote: true }` (VM exists). Both take the `findSpecByIssue(projectRoot, id)` branch, which reads only `<projectRoot>/.pan/specs/`. The spec is on `feature/<id>`, so the lookup misses and `pan start` POSTs `/api/issues/<id>/start-planning` again. Seen live: PAN-4677 was planned, then `pan start PAN-4677 --remote` launched `planning-pan-4677` a second time.

2. **complete-planning never actually pushes the feature branch.** `commitCompletePlanningWorkspaceGit()` (planning-promotion.ts, search `const pushChild = spawn('git', ['push']`) runs a detached bare `git push` with `stdio: 'ignore'` and returns `pushed: true` unconditionally. A workspace branch tracks `origin/main` — verified in this workspace: `git config --get branch.feature/pan-4683.merge` prints `refs/heads/main` — and `push.default` is unset (`simple`), so the bare push fails with `fatal: The upstream branch of your current branch does not match the name of your current branch`. The failure is invisible. Meanwhile `createRemoteWorkspace()` runs `git fetch origin feature/<id> && git checkout feature/<id> || git checkout -b feature/<id>` on the VM (step 4), so a VM started after local planning silently gets a fresh branch off `main` with no spec.

3. **The post-planning auto-start ignores `--remote`.** `pan start <id> --remote` on an unplanned issue sends `workspaceLocation: 'remote'` to start-planning (start.ts `buildStartPlanningBody({ … workspaceLocation: effectiveRemote ? 'remote' : 'local' })`), but nothing persists it for the hand-off. `completePlanningAutoSpawn()` POSTs `/api/agents` with no location. The route (`src/dashboard/server/routes/agents/spawn-issue.ts`) goes remote only when remote workspace metadata already exists (`const isRemote = workspaceMetadata?.location === 'remote';`), otherwise it spawns `pan start <id> --local` through `buildPanStartArgs()` (`src/dashboard/server/routes/agents/shared.ts`, hard-coded `'--local'`). The deferred hand-off retry has the same gap because it goes through the same route.

Workaround used live: push `feature/<id>` by hand, then `pan start <id> --remote --plan skip`.

## Requirements

### Functional

- **FR-1** — `pan start <id>` decides "planned" by checking, in order: the local workspace (`findPlanSync`), the local feature branch ref, the origin feature branch ref, then the primary checkout. It checks the local workspace even when `--remote` is given or a remote workspace already exists.
- **FR-2** — `pan start <id> --remote` on a planned issue never POSTs `/api/issues/<id>/start-planning`; it proceeds to remote workspace creation and spawn.
- **FR-3** — complete-planning pushes the workspace's `feature/<id>` branch to `origin` with an explicit refspec, after the last planning commit and before the work-agent auto-start, and reports the real outcome in the `gitPushed` response field.
- **FR-4** — `createRemoteWorkspace()` pushes the local workspace's `feature/<id>` branch to `origin` before it creates the VM, and aborts (throws, no VM created) when that push fails.
- **FR-5** — The auto-start consent record carries the planning request's `workspaceLocation`; `writeAutoSpawnOnFinalizeFlag` persists it and a new reader returns it.
- **FR-6** — A consent-bearing `POST /api/agents` with no remote workspace metadata and a consent `workspaceLocation` of `'remote'` starts the work agent with `pan start <id> --remote` instead of `--local`, and skips the local-only steps (workspace creation, docker stack-health gate, container orchestration).
- **FR-7** — The docs describe the push-before-provision step and `pan start <id> --remote` on a planned issue, including the post-planning auto-start honoring `--remote`.

### Non-functional

- **NFR-1** — No push sets or changes the branch's upstream (`-u` is forbidden). `@{u}` readers (`src/lib/workspaces/git-state.ts`, `src/lib/xbrief/continue-state.ts`, `src/lib/lanes/*`) assume `origin/main`.
- **NFR-2** — No push bypasses git hooks (`--no-verify` is forbidden on pushes) and no push forces.
- **NFR-3** — `src/cli/commands/start.ts` must not grow: it is at its file-size cap (1283 lines, `scripts/file-size-allowlist.txt` row `PAN-4211`). `src/lib/overdeck/planning-promotion.ts` (995 lines) must not grow past 995. Raising an allowlist cap is forbidden for agents.
- **NFR-4** — No new synchronous child-process calls in code reachable from the dashboard server (`no-execsync-server` rule). Use `execFile` promisified.
- **NFR-5** — The plan lookup performs no network I/O (no `git fetch`). It reads only refs already present locally.

## Decisions (made in this doc)

- **D1 — Lookup order.** Local workspace → `refs/heads/feature/<id-lower>` → `refs/remotes/origin/feature/<id-lower>` → primary checkout. The first hit wins. A workspace draft found by `findPlanSync` counts, exactly as the existing local path already treats it.
- **D2 — No fetch in the lookup.** A stale origin view falls through to "not planned" (re-planning), which is today's behavior; adding network I/O to every `pan start` is not worth it. (autoDecision)
- **D3 — Push refspec.** `git push origin HEAD:refs/heads/feature/<id-lower>`. Before pushing, the helper refuses when HEAD is detached or on a branch other than `feature/<id-lower>`, and when no `origin` remote exists. No `-u`, no `--no-verify`, no `--force`. Timeout 120 000 ms.
- **D4 — Both push points.** Fix the complete-planning push (FR-3) AND push at remote-workspace creation (FR-4). FR-4 alone covers "planned days ago, `pan start --remote` today"; FR-3 makes the existing "pushed to git" response honest and makes the spec reach origin as the code always intended. (autoDecision)
- **D5 — Failure policy.** complete-planning push failure is non-fatal: log, emit a `branchPush` phase with status `failure`, return `gitPushed: false`. Remote-workspace push failure is fatal: throw before `fly.createVm` with a message naming the manual command, because a VM without the spec starts a work agent with no plan.
- **D6 — Location travels on the consent record**, mirroring `workModel` (PAN-3022). No new `POST /api/agents` body field. The deferred hand-off retry gets it for free. (autoDecision)
- **D7 — Remote spawn goes through `pan start --remote`.** The route reuses its existing detached `spawnPanCommand` path with `--remote`, so `handleRemoteWorkspace` in start.ts does VM creation, clone, checkout and spawn exactly as a manual `pan start --remote` does. The route does not create VMs itself (VM creation can take minutes; the HTTP request must not block on it).
- **D8 — Remote not enabled.** When the consent says remote but `loadConfigSync().remote?.enabled` is not true, the route returns HTTP 422 with `error: "Remote workspaces are not enabled for <ID>: run pan admin remote setup, or start it locally with pan start <ID> --local"`. complete-planning then records a normal hand-off failure (`spawn-failed`).
- **D9 — Dirty-tree check stays for remote** when the local workspace directory exists: uncommitted changes would not reach the VM, so refusing is correct. It is skipped only when the local workspace directory does not exist.
- **D10 — Polyrepo is out of scope.** The branch-ref lookup runs in `<projectRoot>` only; polyrepo projects are covered by the local-workspace step. Remote workspaces clone one repo today.

## Repo rules restated

- No `execSync` in dashboard-reachable code; use promisified `execFile`.
- Tests with delays use `vi.useFakeTimers()`; the push timeout is never awaited for real in tests (use execImpl spies).
- No new source-grep tests and no added `skipIf`/`.only` — the test-skip and lint gates reject them.
- File-size ratchet: start.ts ≤ 1283, planning-promotion.ts ≤ 995; never edit `scripts/file-size-allowlist.txt` upward.
- Never `git stash`; never `git checkout` another branch inside the workspace.

## Non-goals

- Fetching origin during plan lookup.
- Polyrepo plan homes on branch refs, and pushing a nested `pan_records.repo` spec repo.
- Running planning itself on Fly, or changing `pan plan --remote`.
- A new `workspaceLocation` field in the `POST /api/agents` body, or dashboard UI for choosing a location.
- Pushing uncommitted workspace changes to the VM.
- Changing the branch upstream (`-u`) or the worktree creation tracking setup.

## Hazards

- **H1** `pushPlanArtifacts` (`overdeck/plan-artifact-commit.ts`) resolves the target from `branch.<b>.merge`, which is `refs/heads/main` in a workspace. Never call it from a workspace; it would push planning commits to `main`.
- **H2** A real feature-branch push now happens on every finalize. Projects whose CI runs on branch pushes (for example GitLab branch pipelines) will see one pipeline per planned issue. This matches the code's original intent ("Planning complete and pushed to git").
- **H3** Pre-push hooks now run during complete-planning. A slow hook delays finalize by up to the 120 s timeout; a failing hook yields `gitPushed: false`, never a failed finalize.
- **H4** `findIssuePlan` returning a `<ref>:<path>` string is only ever truth-tested in start.ts; do not pass it to a file reader.
