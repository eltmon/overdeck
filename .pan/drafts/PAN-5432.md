# PAN-5432 — Fix the flaky rag-runs read in `injection.test.ts`

**Issue:** [PAN-5432](https://github.com/eltmon/overdeck/issues/5432)
**Kind:** test-only flake fix. No production code changes.

## Glossary

- **rag-runs log** — the per-workspace, per-day JSONL file at
  `<OVERDECK_HOME>/memory/<projectId>/<workspaceId>/rag-runs/<YYYY-MM-DD>.jsonl`,
  resolved by `resolveRagRunsFile()` in `src/lib/memory/paths.ts` (line 56).
  Prompt-time memory injection appends one `rag-decision` entry per prompt.
  Query expansion appends `query-expansion` entries to the same file.
- **Fire-and-forget append** — `void appendFile(...).catch(() => {})`: the
  write starts, but the caller does not wait for it to finish.
- **`writeDecision`** — the function in `src/lib/memory/injection.ts`
  (line 535) that records a `rag-decision` entry, either through an injected
  `logDecision` callback or by appending to the rag-runs log.
- **`injectWithLog`** — test helper in `tests/lib/memory/injection.test.ts`
  (line 166) that passes a `logDecision` callback, so the decision is captured
  in memory and nothing is appended to disk.
- **`readRagEntries`** — test helper (line 182) that reads the rag-runs log for
  date `2026-05-16` and parses each line as JSON.
- **`vi.waitFor`** — Vitest helper that retries a callback on an interval until
  it stops throwing or the timeout elapses. It uses Vitest's saved real timers.

## Problem

The v0.87.1 release workflow (run 43834978072) failed in its `pack` job. One
test failed on the first try and on its retry:

`tests/lib/memory/injection.test.ts` > "fact injection (PAN-5358)" >
"logs fact hit counts and allocations in rag-runs"

```
AssertionError: expected [] to have a length of 1 but got +0
```

Because `pack` failed, `npm` and `bare-host-macos` were skipped, and nothing
from v0.87.1 was published. The test passes locally (29/29) at the same commit.

## Root cause (verified)

`src/lib/memory/injection.ts`, `writeDecision`, lines 535–544 (search for
`void appendFile(filePath`):

```ts
async function writeDecision(input: PromptTimeMemoryInjectionInput, decision: PromptTimeRagDecisionLogEntry): Promise<void> {
  if (input.logDecision) {
    void input.logDecision(decision).catch(() => {});
    return;
  }

  const filePath = resolveRagRunsFile(input.identity.projectId, input.identity.workspaceId, decision.timestamp);
  await ensureParentDir(filePath);
  void appendFile(filePath, `${JSON.stringify(decision)}\n`, 'utf8').catch(() => {});
}
```

The append is deliberately fire-and-forget, so prompt-time injection never
waits on a log write. `injectPromptTimeMemory` awaits `writeDecision` (line 494),
but that only waits for `ensureParentDir`, not for the append.

The test (lines 936–960, search for `logs fact hit counts and allocations in rag-runs`)
reads the file once, right after `injectPromptTimeMemory` resolves:

```ts
      expect(result.status).toBe('injected');
      const entries = await readRagEntries();
      const decisionEntries = entries.filter((entry: { type: string }) => entry.type === 'rag-decision');
      expect(decisionEntries).toHaveLength(1);
```

On a loaded CI runner the append has not landed yet. The failure was
`expected []`, not ENOENT and not a JSON parse error. So the file existed and
held other entries (the awaited `query-expansion` entry), and only the
`rag-decision` append was late. This confirms the race.

### Why no other test needs the fix

- `readRagEntries` has exactly one caller: line 954. (`grep -n readRagEntries tests/lib/memory/injection.test.ts`
  shows the definition at line 182 and the call at line 954 only.)
- Tests that use `injectWithLog` pass `logDecision`. That callback assigns
  `decision` synchronously when `writeDecision` calls it, before the `void`ed
  promise matters, so those tests cannot race. This includes the sibling test
  "injects no facts from an empty or missing fact store" (line 962).
- `tests/lib/memory/query-expansion.test.ts` reads the rag-runs log at lines
  137, 194, 216 and 242, but those entries come from `logQueryExpansion`
  (`src/lib/memory/query-expansion.ts` line 232), which `await`s `appendJsonl`,
  and every caller awaits `logQueryExpansion` (lines 92, 131, 228). No race.

## Requirements

- **FR-1** — The test "logs fact hit counts and allocations in rag-runs" waits
  for the `rag-decision` entry to appear in the rag-runs log, polling with
  `vi.waitFor`, instead of reading the file once.
- **FR-2** — The test keeps its existing assertions on the entry:
  exactly one `rag-decision` entry, `hitCounts.facts >= 1`, `budgets.facts === 1500`,
  `allocationBytes.facts > 0`.
- **NFR-1** — No production code under `src/` changes. The rag-runs append in
  `writeDecision` stays fire-and-forget.
- **NFR-2** — No real sleeps (`setTimeout` delays, `sleep`) are added to the test.
- **NFR-3** — The poll tolerates a missing file and a partially written line by
  treating a read or parse error as "not yet" (`.catch(() => [])`), and gives up
  after 2000 ms.

## Decisions

- **D-1: Test-only fix.** The production write stays fire-and-forget. Waiting on
  a log write in the prompt-time path would add latency to every prompt, which
  is the thing the design avoids.
- **D-2: Inline `vi.waitFor` at the call site.** Do not change `readRagEntries`
  and do not add a new helper. There is one caller.
- **D-3: Real timers.** `vi.waitFor` polls real filesystem I/O. This test does
  not use fake timers and must not be wrapped in `vi.useFakeTimers()`. The
  repo's fake-timers rule ("Fake timers for retry / backoff / delay-based tests")
  targets code under test that sleeps; here the test polls for a real I/O
  completion with no fixed delay, so the rule does not apply. `vi.waitFor` uses
  Vitest's saved real timers, so it also works if a prior test leaked fake
  timers.
- **D-4: Timeout 2000 ms, interval 20 ms.** Large enough for a loaded runner,
  small enough to fail fast if the entry is truly never written.
- **D-5: No changelog entry.** The change is not user-facing, so
  `changelog.d/pan-5432.md` is not added.

## Work items

### WI-1 — Poll for the rag-decision entry in the flaky test

**File:** `tests/lib/memory/injection.test.ts`, test
`it('logs fact hit counts and allocations in rag-runs', …)` (lines 936–960).

**Steps:**

1. Replace the single read and the length assertion with a `vi.waitFor` poll
   that returns the matching entries.
2. Keep the three field assertions after the poll, unchanged.
3. Add a one-line comment above the poll that says why it polls: the rag-runs
   append in `writeDecision` is fire-and-forget.

**Before:**

```ts
      expect(result.status).toBe('injected');
      const entries = await readRagEntries();
      const decisionEntries = entries.filter((entry: { type: string }) => entry.type === 'rag-decision');
      expect(decisionEntries).toHaveLength(1);
      expect(decisionEntries[0].hitCounts.facts).toBeGreaterThanOrEqual(1);
```

**After:**

```ts
      expect(result.status).toBe('injected');
      // writeDecision appends to rag-runs fire-and-forget, so poll until the entry lands.
      const decisionEntries = await vi.waitFor(async () => {
        const found = (await readRagEntries().catch(() => []))
          .filter((entry: { type: string }) => entry.type === 'rag-decision');
        expect(found).toHaveLength(1);
        return found;
      }, { timeout: 2000, interval: 20 });
      expect(decisionEntries[0].hitCounts.facts).toBeGreaterThanOrEqual(1);
```

`vi` is already imported at line 4. No new imports are needed.

**Tests that prove it:** `npx vitest run tests/lib/memory/injection.test.ts`
exits 0. A local green run alone does not prove the race is gone (the test
already passed locally), so the review also checks the code shape: no bare
`await readRagEntries()` outside a `vi.waitFor` callback, and no change under
`src/`.

## Non-goals

- Making the production rag-runs append awaited.
- Re-running or re-cutting the v0.87.1 release. That is a release operation,
  not part of this change.
- Tests that call `injectPromptTimeMemory` without `logDecision` (for example
  line 513, "escapes retrieved memory text…") and leave an append in flight at
  teardown. They do not read the log, so they do not flake on this assertion.
