# PAN-4584 — Archiving a conversation shows pending, success, and failure feedback

**Issue:** [PAN-4584](https://github.com/eltmon/overdeck/issues/4584)
**Status:** draft (auto-planned 2026-10-24)

## Glossary

- **Archive request** — `POST /api/conversations/:name/archive`
  (`src/dashboard/server/routes/conversations.ts`, grep `'/api/conversations/:name/archive'`),
  which calls `archiveConversationByName` in `src/lib/overdeck/conversation-archive.ts`. It stops
  the live session before it returns, so it can take several seconds. Failure bodies are JSON
  `{ "error": "<message>" }` with status 400 (`Conversation is already archived`), 403 (origin
  check), 404 (`Conversation not found`) or 500 (`Internal server error`). Success is
  `{ "success": true }`.
- **Mutations hook** — `useConversationMutations(selected, onSelect)` in
  `src/dashboard/frontend/src/components/CommandDeck/useConversationMutations.ts`. It returns one
  memoized `ConversationMutations` object.
- **Hook instance** — each component that calls `useConversationMutations` gets its own
  `useMutation` observers. There are seven non-test instances: `Sidebar.tsx:248`,
  `UnscopedConversationChip.tsx:24`, `CommandDeck/index.tsx:1101`, `ConversationList.tsx:372`,
  `Stage/index.tsx:368`, `chat/HandoffNotice.tsx:15`, `chat/ConversationPanel.tsx:188`.
- **MutationCache** — TanStack Query v5 (`@tanstack/react-query` 5.103.2) keeps every running
  mutation in one cache on the shared `QueryClient`. All hook instances share it.
  `useMutationState` reads it reactively; `queryClient.isMutating(filters)` reads it at call
  time.
- **Archive-pending** — a conversation name for which an archive mutation with
  `mutationKey: ['conversation-archive']` is in `status: 'pending'` in the MutationCache.
- **Entry points** — the four UI controls that archive a conversation:
  1. **Row menu** — `ConversationRow.tsx`, the row's own ⋮ / right-click `MenuSurface`, item
     "Archive" (grep `void handleArchiveClick()`), confirm dialog in `handleArchiveClick`.
  2. **Action menu** — `ConversationActionMenu.tsx` (opened from a Stage tab, `Stage/index.tsx`
     grep `<ConversationActionMenu`), item "Archive", confirm dialog in `handleArchive`.
  3. **Panel header menu** — `chat/ConversationPanel.tsx` ⋮ menu item "Archive conversation"
     (grep `Archive conversation`). Rendered only when the `onArchived` prop is set, which in
     production is only `App/StandaloneRoutes.tsx:75` (`onArchived={() => window.close()}`).
  4. **Panel body buttons** — the "Archive" buttons in `ConversationView` empty states
     (spawn-failed and orphaned, grep `onClick={() => onArchive?.()}`), wired by
     `onArchive={!embedded ? handleArchive : undefined}` (grep `onArchive={!embedded`). These
     call `handleArchive` with no confirm dialog (unchanged).

## Problem

After the operator confirms an archive, nothing visible happens until the row disappears
seconds later. There is no spinner, no disabled state and no toast, so the operator cannot
tell whether the click registered. Failures are silent:

- `archiveMutation` (`useConversationMutations.ts`, grep `const archiveMutation = useMutation`)
  has only `onSuccess`. A failed request leaves the row with no message.
- `archiveConversation()` (same file, top) throws the fixed string `'Failed to archive
  conversation'` and discards the server's `error` field.
- `ConversationPanel.handleArchive` (grep `const handleArchive = useCallback(async () => {`)
  calls `fetch` directly, ignores `res.ok`, and logs errors only with `console.error`. A 4xx/5xx
  response is treated as success: it closes the deck tabs and calls `onArchived`.
- `ConversationActionMenu.handleArchive` calls `onCloseTab?.()` immediately after
  `mutations.archive(...)`, so the tab closes before the request resolves. On failure the tab is
  gone but the conversation is not archived.

## Decisions

- **D1 — Archive-pending lives in the MutationCache, not in a per-instance ref.** The
  retitle pattern (`pendingRetitleNamesRef`) is per hook instance, so the Stage tab menu and the
  panel (each with its own instance) could never show pending on the row rendered by
  `ConversationList`'s instance. `archiveMutation` gets `mutationKey: ['conversation-archive']`,
  and the hook derives the pending names with `useMutationState`. Every hook instance therefore
  sees every pending archive, whichever entry point started it.
- **D2 — The double-archive guard reads the MutationCache at call time.** `archive(name)`
  returns without calling `mutate` when `queryClient.isMutating({ mutationKey:
  ['conversation-archive'], predicate: (m) => m.state.variables === name }) > 0`. A synchronous
  read is correct because TanStack's `Mutation.execute` dispatches the `pending` action before
  its first `await` (query-core `mutation.ts`, `this.#dispatch({ type: 'pending', variables,
  isPaused })`), so a second click in the same tick already sees the first mutation.
- **D3 — Server message reaches the toast.** `archiveConversation()` parses the JSON body like
  `retitleConversation()` and throws `new Error(data?.error || 'Failed to archive conversation')`.
- **D4 — Toast copy.** Success: `toast.success(\`Archived "${title}"\`, { duration: 4000 })`.
  Failure: `toast.error(err.message, { duration: 6000 })`. These match the existing
  `retitleMutation` / `moveMutation` durations. The title comes from the `['conversations']`
  query cache in `onMutate` (same lookup as `moveMutation`, grep
  `previous?.find((c) => c.name === vars.name)?.title`), falling back to the name.
- **D5 — The action menu no longer closes the tab eagerly.** `archiveMutation.onSuccess` already
  calls `closeConversationPanes(name)`, which closes every `paneType: 'agent'` pane whose
  `conversationId === name` — the same pane `onCloseTab` closes (Stage conversation tabs are
  created with `conversationId: name`, `openConversationTab.ts:26`). The eager `onCloseTab?.()`
  call in the archive path is removed, so on failure the tab stays.
- **D6 — Panel archive goes through the shared hook.** `ConversationPanel.handleArchive`
  becomes `convMutations.archive(conversation.name, { onSuccess: onArchived })`. The hook's
  `archive` gains an optional second argument `{ onSuccess?: () => void }`, passed to
  `mutate(name, { onSuccess })` as a per-call callback. TanStack fires per-call callbacks only
  while the calling observer is mounted. That is correct here: `onArchived` is set only on the
  standalone route, where the panel is not inside a deck pane, so `closeConversationPanes` does
  not unmount it, and the hook's `onSelectConversation` for the panel instance is a no-op. If a
  future host unmounts the panel first, `onArchived` has nothing left to act on.
- **D7 — The panel shows archive-pending for its conversation from any entry point.** Because
  pending state is global (D1), the panel header shows the pending indicator whenever its
  conversation is archive-pending, not only when the header started it. This is a superset of
  the issue's "if archive was triggered from there" and keeps all entry points consistent.
- **D8 — Visuals reuse existing styles, no new CSS.** Row: a `Loader2` with
  `styles.conversationWorkingSpinner` replaces the status indicator, and the title gets
  `styles.titleRegenerating` (the muted shimmer pending retitle uses). Menus: the Archive item
  is `disabled`, its icon becomes `Loader2`, and its label becomes `Archiving…`. Panel header:
  an `Archiving…` chip using the same `conversationAboutToggle` + `Loader2` +
  `styles.spinnerIcon` markup as the existing "Stopping…" abort button.
- **D9 — No optimistic removal.** The row stays (in pending state) until the request succeeds
  and the `['conversations']` invalidation refetches. On failure it returns to normal.

## Requirements

- **FR-1** — After the operator confirms an archive from any entry point, the conversation's
  row renders a `Loader2` spinner in place of its status indicator and a muted title, in the
  first render after `mutate` is called, before the request resolves.
- **FR-2** — While a conversation is archive-pending, calling `mutations.archive(name)` from any
  hook instance does not send a second request, and every Archive menu item and panel archive
  button for that conversation renders `disabled`.
- **FR-3** — On a non-2xx archive response, the pending state clears, the row and deck tab stay,
  `onArchived` is not called, and `toast.error` shows the server's `error` string (or
  `Failed to archive conversation` when the body has none).
- **FR-4** — On a 2xx archive response, `toast.success` shows `Archived "<title>"`, the
  `['conversations']` query is invalidated, the conversation's deck panes close, the selection
  clears when it was selected, and the panel's `onArchived` (if given) is called.
- **FR-5** — The panel's archive (header menu and body buttons) uses the shared hook path; the
  raw `fetch` in `ConversationPanel.handleArchive` is removed.
- **FR-6** — The panel header renders an `Archiving…` indicator while its conversation is
  archive-pending.
- **NFR-1** — `useConversationMutations` still returns an identity-stable object when no archive
  pending state changed (PAN-4560 render-count tests keep passing).
- **NFR-2** — No file grows past its file-size limit: `ConversationRow.tsx` stays ≤ 1000 lines;
  `ConversationPanel.tsx` stays ≤ its `origin/main` line count (1480) — the change is net
  negative there.
- **NFR-3** — No new CSS classes; no server change.
