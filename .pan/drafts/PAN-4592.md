# PAN-4592: Opt-in Semgrep GitHub Actions workflow via `pan semgrep ci-setup`, with failure relay

**Issue:** [PAN-4592](https://github.com/eltmon/overdeck/issues/4592) — child of
[PAN-4585](https://github.com/eltmon/overdeck/issues/4585) (FR-7, issue work item 6).
**Status:** planned 2026-11-16 (auto mode, high effort), on `feature/pan-4592` at `61bf00321eb`.
**Depends on (both merged):** #4585 (`security.semgrep` config block, managed install),
#4590 (`sast` gate, `security.semgrep.gate`, `verification.sast`, `resolveSastGateMode`).

## Scope

1. `pan semgrep ci-setup <project>` (plus a `pan-semgrep` wrapper skill) opens a pull request
   that adds `.github/workflows/semgrep.yml` to the project's GitHub repository. It never
   pushes to the base branch.
2. A Semgrep check matcher used by the CI failure relay next to the test-job logic, so a red
   Semgrep job reaches the work agent with a findings excerpt and Semgrep-specific instructions.
3. Gate mode decides advisory vs required **in the generated workflow itself**: in `blocking`
   mode a pull request with a new finding fails the `semgrep` job (a normal required check); in
   `advisory` mode the job always concludes green and only warns. D1 explains why this replaces
   the issue's "add `semgrep` to `ADVISORY_CHECK_NAMES`" wording.
4. No HTTP route is added, so no no-loss matrix row is needed
   (`tests/unit/lib/overdeck/no-loss-matrix.test.ts` checks only `http` and `rpc` rows).

## Glossary

- **Semgrep CI workflow** — the file `.github/workflows/semgrep.yml` this command generates. One
  job, id and `name:` both `semgrep`, so GitHub names its check run `semgrep`.
- **Gate mode** — `resolveSastGateMode(security.semgrep, project.verification?.sast).mode` from
  `src/lib/cloister/sast-gate.ts` (lines 80-94): `off` when `security.semgrep.enabled` is
  false, else the project's valid `verification.sast`, else `security.semgrep.gate` (default
  `advisory`). `ci-setup` reads it once and writes `blocking` or `advisory` into the workflow
  (`off` is written as `advisory`).
- **`OVERDECK_SEMGREP_GATE`** — the job-level `env:` line in the workflow that holds the gate
  mode. The scan step fails the job only when it is `blocking` and the run is a pull request.
  An operator changes CI behaviour by editing this one line.
- **Diff-aware PR scan** — on `pull_request` the step passes
  `--baseline-commit <merge-base of origin/$BASE_REF and HEAD>`, so only findings the PR
  introduces are reported. Verified in the container (D5).
- **Push run** — a run on a push to the base branch. Only workflows generated with
  `--sarif-upload` have a push trigger (GitHub code scanning needs a base-branch analysis). A push
  run scans the whole tree and never fails the job.
- **Semgrep check** — a check whose name `isSemgrepCheckName` (WI-1) accepts: the trimmed name
  starts with `semgrep` (any case) followed by end-of-string or a non-alphanumeric character.
  Matches `semgrep`, `Semgrep OSS` (the code-scanning check name for Semgrep SARIF), `semgrep /
  scan`, `semgrep (pr)`. Rejects `semgrepx`, `run-semgrep`.
- **CI failure relay** — `relayCiFailureFeedback` in `src/lib/cloister/ci-failure-feedback.ts`:
  on a red PR check it writes a feedback file into the work agent's workspace and messages the
  agent. For each failing GitHub Actions job it includes a log excerpt chosen in
  `collectCheckRunFailures` (`src/lib/cloister/ci-check-run-failures.ts`).
- **Setup branch** — `overdeck/semgrep-ci`, the remote branch the PR comes from. It does not
  match `issueIdFromBranch` (`src/lib/webhook-handlers.ts` line 106,
  `/(?:feature|strike|bypass)\/([a-z]+-\d+)$/i`), so no webhook treats it as an issue branch.
- **Managed version** — `SEMGREP_VERSION = '1.180.0'` (`src/lib/semgrep/install.ts` line 9).
  The workflow pins `semgrep/semgrep:1.180.0` (the Docker Hub tag exists for amd64 and arm64,
  pushed 2026-10-07).
- **Git guard** — the per-agent `git` PATH shim (`src/lib/launcher-git-guard.ts`). `pan`'s own
  git operations set `OVERDECK_PAN_GIT_OP=1` to pass it (precedent:
  `src/lib/rebase-helper.ts` line 160).

## Requirements

- **FR-1** `pan semgrep ci-setup <project>` opens a GitHub PR from branch `overdeck/semgrep-ci`
  into the project's base branch that adds exactly one file, `.github/workflows/semgrep.yml`,
  and prints the PR URL. It never pushes to the base branch, never writes in the project's
  primary checkout's working tree, and never creates a local branch there.
- **FR-2** The workflow runs `semgrep scan` in `semgrep/semgrep:<SEMGREP_VERSION>` with one
  `--config <c>` per `security.semgrep.configs` entry, the `--severity` flags for
  `security.semgrep.severity` (D17), `--metrics off` and `--sarif-output=semgrep.sarif`; on `pull_request` it is diff-aware with `--error`; workflow
  `permissions` is `contents: read`. The job has no `if:` condition, so Dependabot pull
  requests are scanned too (D18).
- **FR-3** With gate mode `blocking`, a pull request whose changes add a finding fails the
  `semgrep` job. With any other gate mode, every run concludes green and prints a `::warning`
  annotation when Semgrep exits non-zero. A push run never fails the job.
- **FR-4** `--sarif-upload` adds a push trigger for the base branch, an `upload-sarif` step and
  the `security-events: write` and `actions: read` permissions. The upload step has
  `continue-on-error: true`, so a failed upload never fails the job (D19). Without the flag none
  of these appear. GitHub code scanning may then add its own check, governed by the repository's
  code-scanning settings, not by `OVERDECK_SEMGREP_GATE`.
- **FR-5** `ci-setup` refuses, with exit code 1 and a one-line reason, when: Semgrep is
  disabled; the project is unknown; the project has no `github_repo`; the project is polyrepo
  (`workspace.repos` non-empty); `origin`'s URL does not name `github_repo`; a `configs` entry
  is `auto`, absolute, contains a `..` segment, or has a character outside `[A-Za-z0-9._/@:+-]`;
  the base branch name has a character outside `[A-Za-z0-9._/-]`; the base branch already has
  `.github/workflows/semgrep.yml`; or `overdeck/semgrep-ci` exists on `origin` with no open PR.
  An open PR from `overdeck/semgrep-ci` is not a failure: `ci-setup` prints its URL and exits 0.
- **FR-6** `--dry-run` prints the target repository, base branch, setup branch, gate mode and
  the full workflow text, and runs no `git` or `gh` command.
- **FR-7** A red Semgrep check is relayed to the work agent like any other red check (the
  existing path), and its section of the feedback file carries a Semgrep excerpt (the findings
  block through the `Ran N rules on M files` line) and Semgrep-specific instructions (fix,
  rescan, the justified-`nosemgrep` rule).
- **NFR-1** No new HTTP route. `ci-setup` runs `git` and `gh` through promisified `execFile` with
  explicit timeouts (it is CLI-only, but no `execSync` is added anywhere).
- **NFR-2** Privacy (parent NFR-2): `--metrics off`, `SEMGREP_ENABLE_VERSION_CHECK: "0"`,
  `SEMGREP_SEND_METRICS: "off"`; never `--config auto`; no `SEMGREP_APP_TOKEN` (#4593).
- **NFR-3** Injection safety: every value interpolated into the workflow passes a strict charset
  (FR-5); `github.base_ref` reaches the shell only through `env:` (`BASE_REF`), never `${{ }}`
  inside `run:`.

## Decisions (made in this document)

- **D1 The workflow carries the gate mode; no read-side advisory list.** The issue asks for
  `gate: advisory` to add `semgrep` to `ADVISORY_CHECK_NAMES` for that project. That set is
  process-wide, and only `webhook-handlers.ts`, `github-app.ts` and `batch-auto-promote.ts`
  consult it. The verdicts merges actually wait on do not: `summarizeStatusCheckRollup` in
  `src/lib/cloister/pr-facts.ts` (line 245) counts every rollup row, and `toChecksState`
  (`src/lib/overdeck/derived-issue-state.ts` line 341) feeds `ready-set.ts` (lines 144, 207),
  `auto-merge-scheduler.ts` (line 195) and `strike-review.ts` (line 330). A per-project advisory
  list would have to reach every such reader, including ones not yet found, and
  `derived-issue-state.ts` (988 lines) and `pr-facts.ts` (991 lines) are at the 1000-line
  ceiling. A job that concludes green is advisory to every reader by construction.
  `src/lib/advisory-checks.ts` is not edited.
- **D2 Mode mapping, resolved once.** `ci-setup` writes `blocking` when the gate mode is
  `blocking`, else `advisory` (`advisory` and `off`). The workflow does not follow later config
  changes: the operator edits the `OVERDECK_SEMGREP_GATE` line, or deletes the file and runs
  `ci-setup` again. The local `sast` gate still follows the config live.
- **D3 Advisory runs are not relayed.** A green job fires no relay. This matches the local
  `sast` gate, where advisory findings are recorded but are not rework.
- **D4 Diff-aware PRs, no push trigger by default.** A whole-tree PR scan would fail every PR
  in `blocking` mode on a repo with any pre-existing finding. Pushes to the base branch are
  scanned only with `--sarif-upload` (code scanning needs a base analysis), and a push run never
  fails, so the workflow cannot turn the base branch red (a red main empties Overdeck's merge
  gate).
- **D5 Step script verified in the container (2026-11-16, `semgrep/semgrep:1.180.0`).** A
  scratch repo with one finding on `origin/main` and a branch adding a second gave: blocking PR
  with the added finding → exit 1, and the report shows only the added finding; blocking PR
  adding a clean file → exit 0; advisory PR with the finding → exit 0 plus the warning line;
  advisory with a missing rule file (Semgrep exit 7) → exit 0 plus the warning; push run (empty
  `BASE_REF`) → exit 0 with both findings reported; blocking with an unknown base ref → exit 128
  (`fatal: Not a valid object name origin/nosuchbranch`). The repo was owned by another uid, so
  the `safe.directory` line was exercised. `--sarif-output=semgrep.sarif` wrote the file in
  every case that scanned, and the text report stayed on stdout:

  ```
  ┌────────────────┐
  │ 1 Code Finding │
  └────────────────┘
      new.py
     ❯❯❱ no-eval
            ❰❰ Blocking ❱❱
            Do not use eval
              1┆ eval("2")
  ┌──────────────┐
  │ Scan Summary │
  └──────────────┘
  ✅ Scan completed successfully.
   • Findings: 1 (1 blocking)
  Ran 1 rule on 1 file: 1 finding.
  ```
  The plural header is `│ 2 Code Findings │`.

  **Local reproduction needs `GITHUB_WORKSPACE`.** Outside GitHub Actions the image refuses to
  scan unless code is mounted at `/src` (`adjust_for_docker` in
  `semgrep/config_resolver.py` raises "Detected Docker environment without a code volume").
  Semgrep skips that check when `GITHUB_WORKSPACE` is set (`env.py` `in_gh_action_default`),
  which GitHub Actions always sets. The D5 runs set `GITHUB_WORKSPACE=/w`, so they match CI.
- **D6 `--sarif-output`, not `--sarif` on stdout.** The relay excerpt needs the text report.
- **D7 Throwaway worktree, detached, push by refspec.** Like `pan strike`
  (`src/cli/commands/strike.ts` lines 181-224), `ci-setup` runs `git worktree add --detach`
  off `origin/<base>` into `<OVERDECK_HOME>/tmp/semgrep-ci-setup/<projectKey>-<epochMs>` (never
  `/tmp`), commits there, pushes with `git push origin HEAD:refs/heads/overdeck/semgrep-ci`
  (no local branch), and removes the worktree in `finally` with
  `git worktree remove --force <path>`. Every `git` call sets `OVERDECK_PAN_GIT_OP=1` so an agent
  running the command is not refused by its git guard (which refuses commits on a detached HEAD).
- **D8 The generated commit and push pass `--no-verify`.** The throwaway worktree has no
  installed dependencies, so repository hooks (Overdeck's own commitlint hook runs
  `npx --no -- commitlint`) cannot run there. The commit is one generated file, and the PR's CI
  and review gate it. Precedents for machine commits: `src/lib/cloister/uat-generation-deps.ts`
  line 250 and `src/lib/overdeck/planning-promotion.ts` lines 283, 289. Stated in the command
  help, the skill and the docs.
- **D9 Base branch.** `workspace.pr_target`, then `workspace.default_branch` (what
  `getRepoTargetBranch(undefined, config)` in `src/lib/project-repos.ts` line 56 returns when
  either is set), else `git symbolic-ref --short refs/remotes/origin/HEAD` with `origin/`
  stripped, else `main` — the `pan strike` resolution (`strike.ts` lines 126-166). The workflow
  must be on the branch PRs target.
- **D10 `workflow` scope failure is a named error.** Pushing `.github/workflows/` needs a
  credential with the `workflow` scope. When push stderr matches
  `/workflow.{0,40}scope|refusing to allow an OAuth App to create or update workflow/i`, print:
  `GitHub refused the push: the credential for origin lacks the "workflow" scope. Run "gh auth refresh -s workflow" (HTTPS remotes) or push over SSH, then run pan semgrep ci-setup <project> again.`
  Other git or gh failures print the first stderr line.
- **D11 Requires `security.semgrep.enabled: true`** (parent FR-1: one block turns the feature on).
- **D12 Never overwrite.** An existing workflow file on the base branch is a refusal; an open PR
  from the setup branch is success with its URL; a leftover remote branch with no open PR is a
  refusal.
- **D13 CLI-only.** The #4585 design also mentions a dashboard button; that is #4594.
- **D14 Origin must be `github_repo`.** If `origin` were a fork, the branch would go to the fork
  while `gh pr create --repo <github_repo>` looks for it upstream.
- **D15 Actions versions.** `actions/checkout@v4` (this repo's own workflows) and
  `github/codeql-action/upload-sarif@v3`.
- **D17 Severity threshold carried into CI.** Verified 2026-11-16 in `semgrep/semgrep:1.180.0`
  with one WARNING rule and one ERROR rule: `--severity ERROR` reports only the ERROR finding;
  `--severity WARNING --severity ERROR` and no flag report both. `--severity` accepts
  `INFO`, `WARNING`, `ERROR`. Mapping from `security.semgrep.severity`: `ERROR` (default) →
  `--severity ERROR`; `WARNING` → `--severity WARNING --severity ERROR`; `INFO` → no flag. So
  `gate: blocking` fails CI at the same threshold as the local `sast` gate. Both scan lines carry
  the flags.
- **D18 Dependabot pull requests are scanned.** No job-level `if:`. A Dependabot PR gets a
  read-only token, which is all the scan needs (`contents: read`); only the SARIF upload needs
  more, and D19 makes its failure non-fatal.
- **D19 SARIF upload never fails the job.** The upload step has `continue-on-error: true`
  (GitHub workflow syntax: a step with `continue-on-error` does not fail its job). An upload can
  fail on a private repository without GitHub code scanning, or on a Dependabot PR.
- **D16 Size.** About 20 files, but the finalize lint counts each top-level doc and manifest
  path as its own group (10 groups). The code is two areas (`src/lib/semgrep/`, the CI relay)
  plus CLI registration. `plan.metadata.sizeJustification` records this.

not `auto`, and has no `..` path segment. Reasons, for example
`security.semgrep.configs entry "auto" cannot be used in CI: --config auto needs metrics, which Overdeck turns off`

Exact text for `configs: ['p/default', '.semgrep/']`, base `main`, gate `advisory`, severity
`ERROR`, no upload, version `1.180.0`. Each `--config` value is written verbatim; nothing else is interpolated:

```yaml
# Generated by `pan semgrep ci-setup` (Overdeck). You may edit this file; Overdeck never rewrites it.
# Pull requests are scanned diff-aware: only findings on code the pull request adds are reported.
# OVERDECK_SEMGREP_GATE: blocking fails the job on a new finding; advisory only warns.
name: semgrep

on:
  pull_request: {}

permissions:
  contents: read

jobs:
  semgrep:
    name: semgrep
    runs-on: ubuntu-latest
    container:
      image: semgrep/semgrep:1.180.0
    env:
      OVERDECK_SEMGREP_GATE: advisory
      SEMGREP_ENABLE_VERSION_CHECK: "0"
      SEMGREP_SEND_METRICS: "off"
      BASE_REF: ${{ github.base_ref }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: semgrep scan
        run: |
          git config --global --add safe.directory "$GITHUB_WORKSPACE"
          scan() {
            if [ -n "$BASE_REF" ]; then
              base_sha=$(git merge-base "origin/$BASE_REF" HEAD) || return $?
              semgrep scan --config p/default --config .semgrep/ --severity ERROR --sarif-output=semgrep.sarif --metrics off --error --baseline-commit "$base_sha"
            else
              semgrep scan --config p/default --config .semgrep/ --severity ERROR --sarif-output=semgrep.sarif --metrics off
            fi
          }
          status=0
          scan || status=$?
          if [ "$status" -ne 0 ] && [ "$OVERDECK_SEMGREP_GATE" = "blocking" ] && [ -n "$BASE_REF" ]; then
            exit "$status"
          fi
          [ "$status" -eq 0 ] || echo "::warning title=semgrep::semgrep exited with status $status; this run does not fail (gate $OVERDECK_SEMGREP_GATE, or not a pull request)"
```

Default `run`: promisified `execFile(file, args, { cwd, timeout: timeoutMs, encoding: 'utf-8', env: { ...process.env, OVERDECK_PAN_GIT_OP: '1' } })`.
A rejected call carries `stderr`; the step that made it maps it to a refusal message.

Steps (each refusal returns `{ ok: false, message }` and runs nothing after it):
1. `cfg = await loadSemgrepConfig()` (default:
   `(await loadConfigNoMigration()).config.security.semgrep`). `cfg.enabled !== true` →
   `Semgrep support is off (security.semgrep.enabled: false in ~/.overdeck/config.yaml). Turn it on first.`
2. `project = getProject(key)` (default `getProjectSync`). Null →
   `Unknown project "<key>". Run: pan project list`. No `github_repo` →
   `Project <key> has no github_repo; pan semgrep ci-setup supports GitHub repositories only.`
   `workspace.repos` non-empty →
   `Project <key> is a polyrepo project; pan semgrep ci-setup supports single-repo projects only.`
3. `validateCiConfigs(cfg.configs)`.
4. `decision = resolveSastGateMode(cfg, project.verification?.sast, log)`;
   `gate = ciGateForMode(decision.mode)`.
5. Base branch per D9. Configured (`pr_target` or `default_branch`) → use it. Otherwise, on a
   real run, `git symbolic-ref --short refs/remotes/origin/HEAD` (cwd `project.path`, failure
   tolerated) with `origin/` stripped, else `main`. On a dry run no git command runs: use `main`
   and log `(no base branch configured; a real run reads origin/HEAD)`. Then `validateBaseBranch`.
6. `--dry-run`: log `Repository: <github_repo>`, `Base branch: <base>`,
   `Branch: overdeck/semgrep-ci`, `File: .github/workflows/semgrep.yml`,
   `Gate: <gate> (<decision.reason>)`, then the workflow text. Return
   `{ ok: true, prUrl: null, existing: false, dryRun: true }`.
7. `git remote get-url origin` (cwd `project.path`). Lower-case it and drop a trailing `.git`;
   unless it ends with `/<github_repo lower-cased>` or `:<github_repo lower-cased>`, refuse
   `origin of <path> is <url>, not <github_repo>; ci-setup pushes to origin and opens the pull request there.`
8. `git fetch origin <base>` (cwd `project.path`).
9. `git cat-file -e origin/<base>:.github/workflows/semgrep.yml` succeeds → refuse
   `<github_repo> already has .github/workflows/semgrep.yml on <base>; ci-setup never overwrites it.`
10. `gh pr list --repo <github_repo> --head overdeck/semgrep-ci --state open --json url --limit 1`;
    a URL → log `A pull request from overdeck/semgrep-ci is already open: <url>`, return
    `{ ok: true, prUrl: url, existing: true, dryRun: false }`.
11. `git ls-remote --heads origin overdeck/semgrep-ci` non-empty → refuse
    `Branch overdeck/semgrep-ci already exists on origin with no open pull request. Delete it or open a pull request from it.`
12. `mkdirp(tmpRoot())`; `path = join(tmpRoot(), `${key}-${now()}`)`;
    `git worktree add --detach <path> origin/<base>` (cwd `project.path`).
13. `try`:
    - `mkdirp(<path>/.github/workflows)`;
      `writeFile(<path>/.github/workflows/semgrep.yml, renderSemgrepWorkflow({ configs, baseBranch, gate, severity: cfg.severity, sarifUpload }))`.
    - `git add .github/workflows/semgrep.yml`; then
      `git commit --no-verify -m "ci: add semgrep workflow" -m "Generated by pan semgrep ci-setup."`
      (cwd `path`). A failure (for example no git identity) → refusal with git's first stderr line.
    - `git push --no-verify origin HEAD:refs/heads/overdeck/semgrep-ci` (cwd `path`). Failure →
      D10.
    - `gh pr create --repo <github_repo> --base <base> --head overdeck/semgrep-ci --title "ci: add Semgrep workflow" --body <body>`;
      the PR URL is the last non-empty stdout line. The body lists the configs, the gate
      (`blocking`: "a pull request that adds a Semgrep finding fails the semgrep check";
      `advisory`: "the semgrep check never fails; findings show as warnings"), how to change it
      (edit `OVERDECK_SEMGREP_GATE`), the diff-aware rule, whether SARIF upload is on, and that
      the commit skipped repository hooks (D8).

    `finally`: `git worktree remove --force <path>` (cwd `project.path`); a failure is logged as
    a warning naming the path, never thrown.
14. Return `{ ok: true, prUrl, existing: false, dryRun: false }`.

## Critique response

Answers to `.pan/drafts/PAN-4592-critique.md` (round 1).

### SARIF upload can turn advisory and base-branch runs red

Accepted. The upload step now has `continue-on-error: true` (D19, FR-4, WI-3 YAML), so a failed
upload (a private repository without code scanning, or a Dependabot PR's read-only token) never
fails the `semgrep` job. Advisory runs and push runs therefore stay green as FR-3 and D4 promise.
WI-3's test asserts the upload step carries `continue-on-error: true`.

### Dependabot pull requests are silently unscanned

Accepted. The job-level `if: github.actor != 'dependabot[bot]'` is removed (D18, FR-2), so a
Dependabot PR is scanned and, in blocking mode, a new finding fails it. The scan needs only
`contents: read`, which a Dependabot token has; the only step that needs more is the optional
upload, which D19 makes non-fatal. WI-3's test asserts `jobs.semgrep` has no `if` key.

### CI blocking ignores the configured severity threshold

Accepted (sharpens-framing). The workflow now carries `security.semgrep.severity` as `--severity`
flags (D17, verified in the container), so `gate: blocking` fails CI at the same threshold as the
local `sast` gate. WI-3 tests the three mappings.

### Unresolved after two critic rounds

- Origin check does not verify the push destination
- An unrelated open PR counts as setup success
