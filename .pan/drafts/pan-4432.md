# PAN-4432: CI test-failure relay never fires

**Issue:** [PAN-4432](https://github.com/eltmon/overdeck/issues/4432)
**Status:** planned (auto mode, 2026-09-30)

## Read this first: the issue's suspects are not the cause

The issue lists two suspects: an empty `pull_requests` array on `check_run`
payloads, or an exception swallowed inside the forked Effect fiber. Neither is
the primary cause. The verified root cause is this:

**The webhook route forks the handler dispatch with `Effect.forkChild` and then
returns the HTTP response. In Effect 4 (`4.0.0-beta.73`) a `forkChild` child is
scheduled, not started, and is interrupted when its parent fiber exits. So the
dispatch is interrupted before `dispatchWebhook` is ever called. No GitHub
webhook handler has run on this host since the Effect 4 upgrade.** The watcher
fiber that should log a failed dispatch is also a `forkChild`, so it dies the
same way and nothing is logged.

Evidence, gathered during planning:

1. **Scratch reproduction** against the repo's own `node_modules/effect`
   (4.0.0-beta.73). A handler that does `yield* Effect.forkChild(Effect.promise(() => dispatch()))`
   and returns, run inside a parent fiber that stays alive for 300 ms, prints
   `started false finished false`. The same script with
   `void dispatch().catch(...)` or `Effect.forkDetach(...)` prints
   `started true finished true`.
2. **Dashboard log** (`~/.overdeck/logs/dashboard.log`, read with `grep -a`):
   116,180 `[webhook] Received …` lines (85,428 `check_run`, 22,243
   `check_suite`, 1,463 `pull_request`, 2,023 `status`), and zero lines from
   any handler body: zero `[ci-failure-feedback]`, zero
   `[webhook] Review not started for`, zero `[webhook] Forked dispatch failed`.
   (The old `[webhook] Merge state reconciliation failed` lines came from the
   deleted periodic `reconcileStaleGitHubBlockers`, not from a webhook.)
3. **Event store** (`~/.overdeck/overdeck.db`, table `events`, 7-day
   retention): zero `project.ci_suite_observed` rows, although every push to
   `main` delivers a `check_suite` webhook that `handleCheckSuite` turns into
   that event.

The only other path that ever called the relay, `reconcileStaleGitHubBlockers`
(source `polling_reconciliation`), was deleted in `c3ec36c29a9` (PAN-3917, the
Cut). Since then nothing calls `relayCiFailureFeedback` at all.

The empty-`pull_requests` fallback is still in scope, because the issue's
acceptance criteria require it. It is a defensive fallback, not the fix.

## Glossary

- **Relay** — `relayCiFailureFeedback` in `src/lib/cloister/ci-failure-feedback.ts`.
  Writes a `ci-monitor` feedback file into the work agent's workspace and
  delivers a message to the agent.
- **Test gate (CI mode)** — for a project with `verification.tests: ci`
  (PAN-3965), the CI test job on the PR head *is* the verification gate's
  `test` check. A red test job on the head is recorded as a per-run
  verification artifact with `via: 'ci'`, journaled as
  `verification.failed { failedCheck: 'test', cycleCount, via: 'ci' }` in
  `<workspace>/.overdeck/pipeline.jsonl`, and delivered through the
  verification feedback door.
- **Verification feedback door** — `deliverVerificationFeedback` in
  `src/lib/cloister/verification-escalation.ts`. Resolves the work agent (or
  slot), resurrects it if needed, and surfaces a needs-you row when it cannot
  deliver.
- **Generic path** — the relay branch for a red check that is *not* a counted
  test-gate failure (lint, typecheck, a strike PR, an uncounted test failure).
  It messages the work agent with `SPECIALIST FEEDBACK: ci-monitor reported CI FAILED`.
- **Needs-you** — an operator-attention row. Raised through
  `surfaceIssueFeedbackNeedsYou` (`src/lib/cloister/feedback-target.ts`),
  wrapped in the relay by its local `surfaceNeedsYou` helper (injectable as
  `deps.surfaceNeedsYou`).
- **Dispatch** — `dispatchWebhook(eventType, payload)` in
  `src/dashboard/server/routes/webhooks.ts`: the switch that calls
  `handleCheckRun`, `handleCheckSuite`, `handlePullRequest`, and the rest.
- **Empty `pull_requests`** — GitHub leaves `check_run.pull_requests` and
  `check_suite.pull_requests` empty in some cases (fork PRs, a head branch
  that no longer matches, some re-runs). The handlers currently return early
  when the array is empty.
- **PrFacts** — `getPrFacts(issueId, deps?)` in `src/lib/cloister/pr-facts.ts`:
  a forge read of the issue's PR (`open`, `number`, `url`, `headSha`,
  `headBranch`, `testChecks`, …). Memoized 60 s unless `deps` are passed.

## Blast radius: fixing dispatch revives every webhook handler

The fix in WI-1 is small, but it turns on every handler in
`src/lib/webhook-handlers.ts` at once. All of these have been dead since the
Effect 4 upgrade and have not run live with the current code:

| Handler | Revived behavior | Guard that keeps it safe |
| --- | --- | --- |
| `handleCheckRun` | CI relay; `recordCiTestGatePass` (lifts a verification-stuck pause on a green test job) | per-issue relay queue; per-head record is the idempotency key |
| `handleCheckSuite` | `project.ci_suite_observed` events for the Command Deck CI chip; CI relay | observation only for the default-branch head |
| `handlePullRequest` (`opened`/`ready_for_review`) | starts the review pipeline for a PR opened outside `pan done` (`webhook-handlers.ts` lines 274-298) | `requestReviewPipeline.isInFlight` coalesces with `pan done` |
| `handlePullRequest` (`closed` + merged) | `postMergeLifecycle` and `finishStrike` (lines 306-329) | `in-flight-guard.ts` single flight + `_completedPostMerge` marker |
| `handlePullRequest` (`opened`/`closed`/`reopened`) | `enqueueProjectResourceRefresh` | queue coalescing |
| `handleStatus` | CI relay for commit statuses | same as the relay |
| `handleIssueComment` | one `gh pr view` per PR comment (cache bump only) | none; low volume |
| every handler | `bumpIssuePrTabCacheGeneration` | cheap, idempotent |

This plan does not disable any of them. They are documented behaviors, and
their guards exist. The review role must check that none of them misfires (see
WI-1 AC and the hazards in `continue.json`).

Two cost notes for reviewers. The relay's `listFailingRuns` and
`fetchRunFailedLogExcerpt` call `execFile('gh', …)` directly, not the metered
`runGh`, so they bypass the GitHub quota pause gate. A red matrix costs about
2 + N `gh` calls per head (N failing runs), once per head for the test gate and
once per head for the generic path. That is a known hazard, not in scope.

## Requirements

### Functional

- **FR-1** — A signed webhook accepted by `POST /api/webhooks/github` runs its
  handler (`dispatchWebhook`) after the 200 response is returned, every time.
- **FR-2** — A rejected or thrown dispatch is logged with
  `console.error('[webhook] Dispatch failed for <eventType>:', err)`. It is
  never swallowed.
- **FR-3** — A `check_run` payload with an empty `pull_requests` array, a
  conclusion that the handler acts on, a `check_suite.head_branch` naming an
  issue, and a `head_sha` equal to the open PR's head resolves to that PR and
  is handled exactly as if GitHub had listed it.
- **FR-4** — The same fallback applies to a `check_suite` payload with an empty
  `pull_requests` array and a failing conclusion.
- **FR-5** — Every relay decision not to deliver logs one
  `[ci-failure-feedback]` line that names the issue, the short head SHA, and
  the reason with the actual value.
- **FR-6** — When the relay's generic path cannot deliver its message to the
  work agent, it surfaces a needs-you row.

### Non-functional

- **NFR-1** — The fallback in FR-3/FR-4 makes a forge read only for an
  actionable event (a failing conclusion, or `SUCCESS` on a CI test check
  name). `in_progress`, `queued`, and non-test successes cost no API call.
- **NFR-2** — `tests/unit/lib/cloister/ci-failure-feedback.test.ts` stays at or
  under the 1000-line ceiling (`scripts/lint-file-size.sh`, `CEILING=1000`).
  It is 899 lines on `origin/main` today.
- **NFR-3** — No allowlist raise in `scripts/file-size-allowlist.txt`.

## Decisions

- **D1 — Fire-and-forget idiom.** Use a plain detached promise with a logging
  catch: `void dispatchWebhook(eventType, payload).catch(...)`. This is the
  idiom the dashboard routes already use (`routes/hooks.ts`, the
  `doGenerateAiTitle` call; `routes/resources/snapshot.ts`, the
  `refreshResourcesSnapshot` call). Do not use `Effect.forkDetach` here, and do
  not keep the watcher fiber: a half-fix that detaches only the dispatch keeps
  a dead watcher and loses the error log.
- **D2 — Fallback resolves by branch, confirmed by SHA.** The issue asks to
  "resolve the PR by head SHA". The handler resolves the issue from
  `check_run.check_suite.head_branch` (or `check_suite.head_branch`) with
  `issueIdFromBranch`, reads the PR fresh with `getPrFacts`, and accepts it only
  when `facts.open === true` and `facts.headSha === <payload head sha>`. The
  SHA equality is the resolution check. When `head_branch` is null or names no
  issue, the handler logs one line and skips. There is no
  `GET /repos/{repo}/commits/{sha}/pulls` call: Overdeck's PRs always come
  from `feature/`, `strike/` or `bypass/` branches in the same repo, where
  `head_branch` is set.
- **D3 — Fresh PR read in the fallback.** The fallback passes
  `{ fetchGitHubPr: fetchIssuePullRequest }` to `getPrFacts`, the same way
  `readFreshPrFacts` in `ci-failure-feedback.ts` does, so a stale 60 s memo
  from before a push cannot fail the SHA comparison.
- **D4 — Logs, not new state.** Observability is `console.log`/`console.warn`
  lines only. No new journal entry type, no new file.
- **D5 — Generic-path needs-you only when an agent exists.** A red check on a
  feature PR with no work-agent row (an operator's own branch) is not an
  operator alert. Needs-you is raised only when the relay tried to message a
  work agent and the message was not delivered (`delivered !== true`) or
  `messageAgent` threw.
- **D6 — No polling backstop in this issue.** A webhook missed while the
  dashboard is down (for example during `pan reload`) still stalls a PR. A
  backstop sweep has cross-process idempotency questions (the Deacon runs in a
  child process with its own relay memo). It is follow-up [PAN-4439](https://github.com/eltmon/overdeck/issues/4439).
- **D7 — The canary is a post-merge check, not an AC.** After the fix merges
  and `pan reload` ships it, the next push to `main` must produce a
  `project.ci_suite_observed` row in `~/.overdeck/overdeck.db` `events`. The
  work, review and test roles run before merge against the old dashboard, so
  they cannot observe it. The operator or Flywheel checks it after reload.

2. Add a module-private helper above `handleCheckRun`:

   ```ts
   type PayloadPr = { number: number; head: { ref: string; sha?: string } };

   /**
    * PAN-4432: GitHub leaves `pull_requests` empty for some check events. Find
    * the PR from the head branch and accept it only when the forge says it is
    * open at exactly this head SHA.
    */
   async function resolvePullRequestsForHead(
     listed: PayloadPr[] | undefined,
     headBranch: string | null | undefined,
     headSha: string | undefined,
     label: string,
   ): Promise<PayloadPr[]> {
     if (listed && listed.length > 0) return listed;
     const issueId = headBranch ? issueIdFromBranch(headBranch) : null;
     if (!issueId || !headSha) {
       console.log(`[webhook] ${label}: no pull_requests and no issue branch (head_branch=${headBranch ?? 'null'}); skipping`);
       return [];
     }
     try {
       const { fetchIssuePullRequest } = await import('./overdeck/pull-requests.js');
       const facts = await getPrFacts(issueId, { fetchGitHubPr: fetchIssuePullRequest });
       if (!facts.open || facts.number == null || facts.headSha !== headSha) {
         console.log(`[webhook] ${label}: no open PR for ${issueId} at ${headSha.slice(0, 8)} (open=${facts.open}, head=${facts.headSha?.slice(0, 8) ?? 'none'}); skipping`);
         return [];
       }
       return [{ number: facts.number, head: { ref: facts.headBranch ?? headBranch!, sha: headSha } }];
     } catch (err) {
       console.warn(`[webhook] ${label}: could not resolve the PR for ${issueId}: ${err instanceof Error ? err.message : String(err)}`);
       return [];
     }
   }
   ```

   Check `getPrFacts`'s deps parameter type (`PrFactsDeps` in

## Repo rules that apply here

- **No `execSync` in server-reachable code.** `webhook-handlers.ts` and
  `ci-failure-feedback.ts` run in the dashboard. Use async only.
- **Fake timers for delay tests.** None of the new tests wait on a timer; a
  `setImmediate` flush is enough. If a test ever needs a delay, use
  `vi.useFakeTimers()`.
- **File-size ratchet.** `scripts/lint-file-size.sh` compares against
  `origin/main`. Do not raise an allowlist row.
- **Quality gates** before `pan done`: `npm run typecheck`, `npm run lint`,
  `npx vitest run <touched test files>`. Never run the full `npm test`.
- **Source-reading tests fail lint.** Do not add a test that greps
  `webhooks.ts` for `forkChild`; the behavior tests in WI-1 are the guard.
  AC-1's grep is a reviewer check, not a test.

## Non-goals

- No polling or Deacon backstop for webhooks missed while the dashboard is
  down (follow-up [PAN-4439](https://github.com/eltmon/overdeck/issues/4439)).
- No change to the relay's attempt budget, escalation, or delivery door.
- No metering of the relay's raw `gh` calls through `runGh`.
- No disabling or gating of the revived webhook handlers (review start,
  post-merge, CI observation).
- No commit-to-PR lookup (`GET /repos/{repo}/commits/{sha}/pulls`); fork PRs
  are not supported by the fallback.
- No change to any other `Effect.forkChild` site (there is none under
  `src/dashboard/server/routes/` besides this one).
