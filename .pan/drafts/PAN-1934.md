# PAN-1934 — Verification gate: cap retries low and escalate to the operator instead of looping silently

**Issue:** [PAN-1934](https://github.com/eltmon/overdeck/issues/1934)
**Mode:** `pan plan --auto` (no interactive Q&A; inferred choices recorded in Auto-Decisions below and in `plan.autoDecisions[]`).

## Glossary

- **Verification gate** — Overdeck's server-side quality check that runs after a work agent signals "done" (`pan done`) and again on every `pan review request`, *before* the issue advances to the review role. Implemented in `src/lib/cloister/verification-runner.ts` (`runVerificationForIssue` / `runVerificationForIssuePromise`). Runs `quality_gates` from `projects.yaml` (typecheck → lint → test) plus a target-branch sync, a vBRIEF-conflict check, and an acceptance-criteria check. Distinct from GitHub CI.
- **Cycle** — one full pass of the gate. The agent triggers a new cycle each time it re-runs `pan review request` (via the `/rebase-and-submit` skill) after a failure. Each cycle = one full test-suite run = real token + wall-clock spend.
- **`verificationCycleCount` / `verificationMaxCycles`** — fields on the per-issue `ReviewStatus` record tracking how many cycles have run and the cap.
- **Circuit breaker** — the pre-run guard at the top of `runVerificationForIssuePromise` (today `verification-runner.ts:194`) that short-circuits when the cycle count is at/over the cap.
- **Escalation / needs-you** — pausing the work agent and flagging the issue for human attention. The existing primitive is `markWorkspaceStuck(issueId, reason, details)` in `src/lib/review-status.ts` (sets `stuck`/`stuckReason`/`stuckAt`/`stuckDetails`, emits a `status_changed` pipeline event, and the Deacon then skips the issue). Surfaced in the dashboard via the existing stuck UI (`CloisterStatusBar`, `BacklogDAG`, cockpit cards).
- **No-progress** — the same gate failing on consecutive cycles, i.e. the agent is not converging on green.

## Problem

(2026-06-16 live incident.) `agent-pan-1925` finished its beads, ran `pan done`, and the verification gate found one failing test that the agent's own change broke. The gate wrote a feedback file telling the agent *"fix the failing check … Do NOT stop … keep working until `pan review request` completes successfully,"* and the agent looped: read → edit → re-run the full suite (~28 s) → fail → new feedback file → retry. An operator caught it by eye and `pan pause`d it.

Two concrete defects:

1. **The cap is 10, not 3.** `VERIFICATION_MAX_CYCLES = 10` (`verification-runner.ts:29`). The feedback file literally reads "attempt 1/10". The documented PAN-174 safety valve in `CLAUDE.md:309` and `docs/SPECIALIST_WORKFLOW.md:560` says *"After 3 consecutive failures, verification is bypassed,"* which **disagrees with the code**.
2. **The cap silently bypasses; it never escalates.** When the cap is reached the circuit breaker sets `verificationStatus: 'skipped'` and returns `{ outcome: 'skipped' }`, which lets the work **advance to review/merge with a broken check** (because `verificationSatisfied()` only blocks on `'failed'`). There is no operator alert and **no no-progress detection** — an agent chasing an unwinnable target grinds through up to 10 full-suite runs, invisibly.

## Proposal

Replace silent bypass with **low cap + operator escalation**, and add **no-progress detection** so the common case (same check failing every cycle) escalates a cycle early.

1. **Cap = 3.** Lower `VERIFICATION_MAX_CYCLES` 10 → 3 so code matches the documented "3 consecutive failures". Add `NO_PROGRESS_REPEAT_THRESHOLD = 2`.
2. **Pure decision seam.** Add `decideVerificationDisposition({ newCycleCount, failedCheck, lastFailedCheck }) → { disposition: 'retry' | 'escalate'; reason }`. Escalate when `newCycleCount >= VERIFICATION_MAX_CYCLES`, **or** when `failedCheck === lastFailedCheck && newCycleCount >= NO_PROGRESS_REPEAT_THRESHOLD`. This pure function is the home of the regression test for "escalates after N consecutive identical failures."
3. **Escalate instead of looping.** Consolidate the four duplicated failure branches (sync-target, quality-gate, vbrief-conflicts, vbrief-ac) into one `handleVerificationFailure(...)` helper. On `escalate`, it: persists `verificationStatus: 'escalated'`; writes a feedback file whose body tells the agent to **STOP** (not "do NOT stop"); calls `markWorkspaceStuck(issueId, 'verification_unfixable', { failedCheck, cycleCount })`; pauses the agent with `setAgentPaused(agentId, …, true)` and stops it with `stopAgent(agentId)` (the async/Effect primitives — **never** the sync `stopAgentSync`); and returns `{ outcome: 'escalated', failedCheck, cycleCount, maxCycles }`. On `retry` it keeps today's behaviour (failed feedback + message + `{ outcome: 'failed' }`).
4. **Sticky, blocking escalation.** Repurpose the pre-run guard: if the issue is already `'escalated'` or at/over the cap, return `{ outcome: 'escalated' }` **without** running the expensive suite (replaces the old silent `'skipped'`). Make `verificationSatisfied()` (and therefore the merge gate) treat `'escalated'` as **not** satisfied, so escalated work cannot ride the merge gate.
5. **Callers don't advance on escalation.** The three call sites in `src/dashboard/server/routes/workspaces.ts` handle `outcome === 'escalated'`: the review-dispatch path does not spawn review; the `pan review request` path returns an escalation response; the post-rebase merge-verify path treats it as failure.
6. **Docs + dashboard agree.** Update `CLAUDE.md` and `docs/SPECIALIST_WORKFLOW.md` to state cap = 3 and escalation (not bypass), and fix the stale `verification-gate.ts` reference (the file is `verification-runner.ts`). Surface `'escalated'` in the cockpit and align the frontend default cap (10 → 3).

## Requirements

**Functional**
- **FR-1** — `VERIFICATION_MAX_CYCLES === 3`, matching the documented "after 3 consecutive failures" behaviour.
- **FR-2** — On reaching the escalation condition, the gate pauses+stops the work agent and marks the workspace stuck (operator-visible needs-you), instead of writing another "do NOT stop" feedback file.
- **FR-3** — No-progress detection: when the same check fails on `>= NO_PROGRESS_REPEAT_THRESHOLD (=2)` consecutive cycles, the gate escalates immediately, before the hard cap.
- **FR-4** — An escalated issue does not advance to review or merge; `verificationSatisfied()` returns `false` for `'escalated'`, blocking `readyForMerge`.
- **FR-5** — The pre-run guard returns `'escalated'` (never the old silent `'skipped'`) and does not run quality gates when the issue is already escalated or at/over the cap, so a broken check can never silently bypass the gate.
- **FR-6** — `CLAUDE.md` and `docs/SPECIALIST_WORKFLOW.md` state the cap (3) and the escalation behaviour, and reference `src/lib/cloister/verification-runner.ts` (the nonexistent `verification-gate.ts` reference is removed).
- **FR-7** — The escalated state is visible to the operator in the dashboard (verification status shows escalated + the stuck reason), and the frontend default cap matches the backend (3).

**Non-functional**
- **NFR-1** — Verification-runner code reachable from the dashboard server uses only the async/Effect agent primitives (`stopAgent`, `setAgentPaused`, `messageAgent`); never `stopAgentSync`, sync tmux, or `execSync` (server event-loop rule, PAN-70).
- **NFR-2** — Escalation is covered by a regression test asserting `outcome: 'escalated'` + pause + stuck after N consecutive identical failures, and that a single first-time failure still returns `'failed'` without pausing.

## Auto-Decisions (`--auto` mode)

- **AD1 — Cap = 3.** The issue allows "≤3"; 3 aligns the constant with the already-documented number (`CLAUDE.md:309`), the least-surprise choice.
- **AD2 — No-progress threshold = 2.** Same check failing on two consecutive cycles escalates at cycle 2 — one cycle before the hard cap — catching the incident (a repeatedly-failing test) sooner while staying conservative.
- **AD3 — No-progress granularity = gate name.** Track sameness at the gate level (`typecheck`/`lint`/`test`/`sync-target-branch`/`vbrief-conflicts`/`vbrief-ac`), not individual test names. Robust, matches the incident (the `test` gate kept failing), and avoids fragile vitest-output parsing. Per-test granularity is a NonGoal.
- **AD4 — Reuse existing escalation primitives.** `markWorkspaceStuck` (needs-you) + `setAgentPaused` + `stopAgent`, matching `pan pause` semantics and the existing operator surfaces. Use the async/Effect variants (server-safe).
- **AD5 — Escalate all four failure branches.** Sync-target, quality-gate, vbrief-conflicts, and vbrief-ac are the same hazard class; one shared helper applies escalation uniformly. No half-fix.
- **AD6 — `verificationLastFailedCheck` lives on the review-status record (DB cache).** It is a within-sequence hint; if lost on a cache rebuild the logic falls back to the hard cap. Avoids journaling churn.
- **AD7 — Escalated blocks merge.** `verificationSatisfied('escalated') === false`, replacing the old silent `'skipped'` bypass — the entire bug was broken work advancing silently.
- **AD8 — No new pipeline event type.** Visibility comes from `verificationStatus: 'escalated'` + the existing `stuck`/`status_changed` surface. Avoids contract churn.

## NonGoals

- Per-test-name no-progress tracking (gate-name granularity only).
- Changing the `quality_gates` command set or what counts as a failing check.
- The untracked pi/kimi cost-accounting sibling issue (explicitly out of scope here).
- A configurable per-project cap (hardcoded constant; configurability not requested).
- Auto-resuming an escalated agent (the operator intervenes via the existing unstick/unpause flow).
- A new needs-you UI surface beyond the existing stuck surface, or a new pipeline event type.

## Intersecting repo rules (restated for the executor)

- **Server async-only:** the verification runner is reached from the dashboard server — use `execAsync`/`spawn` and the Effect agent primitives; never `execSync` or sync tmux (PAN-70; `no-execsync-server`, `async-tmux` rules).
- **Single source of truth:** route the new `verificationLastFailedCheck` through `setReviewStatusSync`/`getReviewStatusSync` and the review-status DB mapper — do not touch the DB directly elsewhere.
- **Fake timers:** the runner has no internal backoff/delay, so its tests need no timers. If any new test introduces delay-based code, it MUST use `vi.useFakeTimers()` (repo rule) — but do not add real `setTimeout`-based waits.
- **No bandaids:** consolidate the four failure branches at the root rather than special-casing the test gate.
