# PAN-4697 — Move the CI frontend test list out of `package.json` into a union-merged list file

**Issue:** [PAN-4697](https://github.com/eltmon/overdeck/issues/4697)
**Long-term fix (out of scope here):** [PAN-3532](https://github.com/eltmon/overdeck/issues/3532) — run the whole frontend suite on CI, no allowlist.

## Glossary

- **Frontend subset** — the explicit list of frontend Vitest files CI runs. Today it is the
  value of the root `package.json` script `test:frontend-subset`. CI never runs the whole
  `src/dashboard/frontend` suite; a frontend test that is not in the subset never runs on CI.
- **List file** — the new file `scripts/frontend-test-subset.txt` that holds the subset, one
  path per line. Paths are relative to `src/dashboard/frontend/` (exactly the strings the
  `package.json` line passes today).
- **Runner** — the new script `scripts/run-frontend-test-subset.mjs`. It reads the list file
  and spawns the same `npm --prefix ./src/dashboard/frontend run test -- <paths>` command the
  `package.json` line runs today.
- **`merge=union`** — git's built-in union merge driver, set per path in `.gitattributes`.
  When both sides change the same hunk, git keeps both sides' lines (ours first, then theirs)
  instead of writing conflict markers. It needs no git config.
- **`git merge-tree --write-tree A B`** — computes the merge of A and B without touching the
  index or worktree. Exits 0 when clean, 1 on conflict. The pipeline's own conflict probe
  (`src/lib/cloister/conflict-gate.ts`, `probeBranchConflictPaths`) uses it.

## Problem

`package.json` line 141 holds `test:frontend-subset` as one 7,431-character line:

```json
"test:frontend-subset": "npm --prefix ./src/dashboard/frontend run test -- src/lib/__tests__/issueActions.test.ts src/lib/__tests__/issueActions.menu-by-state.test.ts …",
```

Every PR that adds a frontend test appends to that single line, so any two such PRs in flight
conflict. On 2026-11-01, after PAN-4643 and PAN-4626 merged, five open PRs (#4693, #4688,
#4686, #4692, #4689) went `CONFLICTING` at once on this line. Each conflict costs a work-agent
cycle and a re-review.

### Probe results (run during planning, git 2.43.0)

In a scratch repo with `list.txt merge=union` committed in `.gitattributes`:

1. Two branches that insert a different line at the **same** position: `git merge-tree
   --write-tree x z` exits 0 and the merged file holds both lines (`a b b2 c e`).
2. Negative control, same edits with no `.gitattributes`: `git merge-tree` exits 1 (conflict).
3. **`git merge-tree` reads `.gitattributes` from the checked-out worktree, not from the
   merged commits.** With the worktree on a branch that lacks the file, merging two branches
   that both carry the attribute conflicts (exit 1); with the worktree carrying the attribute,
   merging two branches that lack it is clean (exit 0).

Consequence of (3): the pipeline's conflict probe runs `git merge-tree` inside the workspace
worktree, so it honors the union rule once that workspace's checkout contains the new
`.gitattributes` line. A PR branch cut before this issue merges lacks the line in its worktree
and still sees one last conflict (on `package.json`) when it syncs main. The unit test in WI-4
must keep `.gitattributes` checked out in its temp repo's worktree.

GitHub's server-side `mergeable` flag (`src/lib/cloister/pr-facts.ts:464`) is computed by
GitHub, which likely ignores `merge=union` (`docs/MERGE-WORKFLOW.md:305-313` already records
this for the two existing union files; [PAN-4616](https://github.com/eltmon/overdeck/issues/4616),
open, owns verifying it and adding a fallback). The auto-merge scheduler skips PRs GitHub calls
`CONFLICTING` (`src/dashboard/server/services/auto-merge-scheduler.ts:111`) and the conflict
gate treats the forge result as a blocker (`src/lib/cloister/conflict-gate.ts`, `describeMergeBlock`).

4. Second probe, **plain 3-way merge with no union rule** (GitHub's worst case), base list
   `a c e g`: inserts into gaps a|c and e|g merge cleanly (exit 0); inserts into the
   **neighboring** gaps a|c and c|e merge cleanly (exit 0); only two inserts into the **same**
   gap a|c conflict (exit 1).

Consequence of (4): even if GitHub ignores the union rule, two PRs conflict at GitHub only when
both add a test that sorts into the same gap between two existing entries. Today every pair of
frontend-test PRs conflicts. `merge=union` then resolves that same-gap case for every local
merge path (the merge door's server rebase, `pan sync-main`, and the workspace conflict probe).
The residual GitHub-only same-gap conflict is a known limitation owned by PAN-4616.

## Decisions (made here; auto mode)

1. **Runner is a node script, not inline `$(grep …)` in `package.json`.** It matches the
   `scripts/*.mjs` convention, avoids `sh`-only command substitution, and gives the tests a
   behavior surface (`--dry-run`).
2. **List paths stay relative to `src/dashboard/frontend/`**, exactly as today, so the spawned
   command is byte-identical apart from path order.
3. **Sorted by convention, tolerant at runtime.** The list file is committed sorted (`LC_ALL=C
   sort` order). A union merge can leave lines out of order or duplicate a line both sides
   added. The runner therefore dedupes (first occurrence wins) and does not care about order.
   **The integrity test asserts only that every non-comment entry exists under
   `src/dashboard/frontend/`.** It asserts nothing about order or duplicates, because a clean
   union merge can produce either, and such an assertion would turn main red after a merge
   that git reported as clean.
4. **Existence is checked by the integrity test, not the runner.** Vitest silently ignores an
   explicit path that matches nothing as long as other paths match, so a deleted test left in
   the list is invisible today. The root Vitest suite (which CI runs) now catches it.
5. **Merge proof uses `git merge-tree --write-tree` in a temp repo** whose worktree carries the
   real `.gitattributes` rule line (copied from the repo's `.gitattributes` at test time), plus
   a negative control without the rule. Observed working in the probe above.
6. **Runner command-line contract** (the tests rely on it):
   - `node scripts/run-frontend-test-subset.mjs [--list <path>] [--dry-run] [extra args…]`
   - `--list <path>` — read this list file instead of `scripts/frontend-test-subset.txt`
     (path resolved against the current directory). Used by tests only.
   - `--dry-run` — print `JSON.stringify({ command: 'npm', args: [...] })` and one newline to
     stdout, exit 0, spawn nothing.
   - Every other argument is forwarded after the paths, preserving today's
     `npm run test:frontend-subset -- <extra>` behavior.
   - `args` is exactly `['--prefix', './src/dashboard/frontend', 'run', 'test', '--', ...paths, ...extra]`.
   - An empty resolved list (no non-comment lines) exits 1 with
     `run-frontend-test-subset: <list path> lists no test files` on stderr.
   - A missing list file exits 1 with a message naming the path.
7. **The operator's harness-native memory** (`~/.claude/projects/-home-eltmon-Projects-overdeck/memory/project_ci_runs_frontend_test_allowlist.md`)
   still says "append to `test:frontend-subset` in package.json". It is outside the repo and a
   managed session does not write harness-native memory. The PR body must call it out for the

### WI-1 — Runner script `scripts/run-frontend-test-subset.mjs` and its tests

**Why:** FR-2; the runner is what `package.json` will call.

**Files:** create `scripts/run-frontend-test-subset.mjs`; create
`tests/unit/scripts/run-frontend-test-subset.test.ts`.

**Steps:**

1. Write the runner (sketch, in the style of the other `scripts/*.mjs`):

   ```js
   #!/usr/bin/env node
   // Runs the CI frontend test subset listed in scripts/frontend-test-subset.txt (PAN-4697).
   // Paths are relative to src/dashboard/frontend. Long-term: PAN-3532 runs the whole suite.
   import { spawnSync } from 'node:child_process';
   import { existsSync, readFileSync } from 'node:fs';
   import { resolve } from 'node:path';
   import { fileURLToPath } from 'node:url';

   const repoRoot = fileURLToPath(new URL('..', import.meta.url));
   const argv = process.argv.slice(2);
   let listPath = resolve(repoRoot, 'scripts/frontend-test-subset.txt');
   let dryRun = false;
   const extra = [];
   for (let i = 0; i < argv.length; i++) {
     if (argv[i] === '--list') listPath = resolve(argv[++i]);
     else if (argv[i] === '--dry-run') dryRun = true;
     else extra.push(argv[i]);
   }
   if (!existsSync(listPath)) { console.error(`run-frontend-test-subset: ${listPath} not found`); process.exit(1); }
   const paths = [...new Set(readFileSync(listPath, 'utf8').split('\n')
     .map((line) => line.trim())
     .filter((line) => line !== '' && !line.startsWith('#')))];
   if (paths.length === 0) { console.error(`run-frontend-test-subset: ${listPath} lists no test files`); process.exit(1); }
   const args = ['--prefix', './src/dashboard/frontend', 'run', 'test', '--', ...paths, ...extra];
   if (dryRun) { process.stdout.write(`${JSON.stringify({ command: 'npm', args })}\n`); process.exit(0); }
   const result = spawnSync('npm', args, { cwd: repoRoot, stdio: 'inherit', shell: process.platform === 'win32' });
   process.exit(result.status ?? 1);
   ```

   Handle `\r\n` line endings (the `.trim()` covers it).
2. Write `tests/unit/scripts/run-frontend-test-subset.test.ts`. Execute the runner with
   `execFileSync('node', [RUNNER, '--list', fixture, '--dry-run', ...])` (pattern:

   `mkdtempSync(join(tmpdir(), 'frontend-subset-'))` dir. Named tests:

   - `dedupes a path listed twice (union-merge leftover)`
   - `forwards extra arguments after the paths`
   - `exits 1 when the list has no test files`

## Critique response

### Union merge does not clear GitHub's conflict gate

Accepted. Verified: `docs/MERGE-WORKFLOW.md:305-313` already records that GitHub's mergeable
check may ignore `merge=union`, and [PAN-4616](https://github.com/eltmon/overdeck/issues/4616)
(open) owns verifying it and adding a fallback for union-only conflicts. A planning probe (see
"Probe results" item 4) showed that plain 3-way merge (no union) conflicts only when two inserts
land in the same gap of the sorted list; inserts into different gaps, even neighboring ones,
merge cleanly. Changes made:

- FR-4 is narrowed to local git merges. New FR-7 states the GitHub-equivalent guarantee
  (different gaps merge cleanly without any driver), and WI-4 adds a test for it.
- The residual GitHub-only same-gap conflict is a stated known limitation (Hazards, Non-goals),
  delegated to PAN-4616 instead of duplicated here.
- No live GitHub checkpoint: it would mean pushing throwaway PRs to the real repo, and PAN-4616
  is the issue that owns that verification. The design stays: going from "every pair of
  frontend-test PRs conflicts" to "only same-gap pairs conflict at GitHub, none locally" is the
  outcome this issue claims.

### Update the union-merge workflow doc

Accepted. WI-5 and AC-5 now include `docs/MERGE-WORKFLOW.md:305-313`, which will list three
union-merged files and keep the GitHub caveat accurate for the new list.
