# PAN-2442 — ACP as Overdeck's structured agent control plane

**Issue:** https://github.com/eltmon/overdeck/issues/2442 · **Author:** oversight conversation, 2026-07-06, from commissioned deep research (verified July 2026).
**Verified-Against:** main @ 79daca1d8d.

## Glossary

- **ACP (Agent Client Protocol)**: JSON-RPC 2.0 over stdio between a *client* (normally an editor; here: Overdeck) and an *agent* (a coding CLI spawned as a subprocess). Spec: https://agentclientprotocol.com, Apache-2.0, protocol version 1 (stable), schema releases weekly-ish (v1.19.0 @ 2026-07-06). Governance: Zed + JetBrains, RFD process, foundation planned.
- **Session update stream**: `session/update` notifications — `agent_message_chunk`, `tool_call` / `tool_call_update` (with statuses + results), `plan` (structured task breakdown), `usage_update` (tokens, context size, optional cost incl. cache read/write). Turn ends with a typed StopReason.
- **Reversed services**: RPCs the CLIENT serves to the agent — `fs/read_text_file`, `fs/write_text_file`, `terminal/*` (client executes commands for the agent).
- **`session/load` vs `session/resume`**: load = agent replays full history as the update stream (client rebuilds transcript); resume = reconnect without replay. Both capability-gated.
- **acpx**: openclaw/acpx — MIT, alpha; a headless ACP client with persistent named sessions (`~/.acpx/sessions/`), prompt queueing, dead-process reconnect+resume, NDJSON event output. Prior art for our substrate layer.
- **Control plane vs display plane**: this PRD's central split — ACP carries structured control (prompts, updates, permissions); tmux/PTY remains the operator-attachable display.

## What ACP replaces in Overdeck (mapping table)

| Today (per-harness, fragile) | With ACP (typed, uniform) |
| --- | --- |
| `deliverAgentMessage`: PTY supervisor socket → channels MCP → tmux paste-buffer + Enter, echo-confirm heuristics (PAN-1769 triple-paste bug) | `session/prompt` request with acknowledged response; `session/cancel` for interrupts |
| Per-harness transcript resolvers (claude JSONL, pi triple-surface PAN-1908, codex rollout files; kimi would be a 4th) + tmux pane scraping | One `session/update` consumer; `session/load` replay on reattach |
| Permission/prompt detection from pane text (AUQ in-progress detection, codex consent screen PAN-2416, OAuth wedges) | `session/request_permission` RPC answered by the auto-approve policy engine |
| Liveness = tmux session exists + pane timestamp heuristics (auth-dead-but-alive gap, RUN-57) | Subprocess pipe EOF + typed StopReasons per turn (wedged-mid-turn still needs timeouts — keep the watchdog) |
| Per-harness cost parsers (PAN-2388's whole scope) | `usage_update` where implemented (Claude adapter yes; codex-acp gap #165; Goose discards #8132) — a *supplement* to PAN-2388, not a replacement |

## What ACP does NOT cover (explicitly retained Overdeck responsibilities)

Process spawn/supervision/restart (PTY supervisor stays), multi-machine transport (stdio only — remote/Fly work keeps its own channel), sandboxing + worktree management, scheduling/lanes/order book, and **the human-attachable terminal**: an ACP agent subprocess has no TUI. Decision D1 below.

## Decisions (made here, not left to the executor)

- **D1 — Hybrid planes.** ACP is the control plane; the agent process still runs under the PTY supervisor inside tmux so operators can attach and watch. For adapter-based agents whose ACP mode has no TUI output, the dashboard's session panel renders the `session/update` stream instead (richer than a pane). We do NOT remove tmux in this epic.
- **D2 — Build on the official TypeScript SDK** (`@agentclientprotocol/sdk`), not acpx. acpx is alpha and its persistence/queueing duplicates what Overdeck already owns (agents table, records). The Phase-0 spike reads acpx for design patterns (reconnect flow, NDJSON eventing) only.
- **D3 — First harness = Gemini CLI** (native `--acp`, reference implementation, zero adapter risk). Claude Code follows via `@zed-industries/claude-code-acp`; Kimi native lands as PAN-1837's implementation. Codex waits (adapter gaps: usage unpopulated).
- **D4 — Capability gates everywhere.** Feature use (loadSession, resume, usage) checks negotiated capabilities per session; absence degrades to current behavior, never errors.
- **D5 — Two-door compliance.** ACP updates flow INTO the existing doors: transcript events append through the same write door the JSONL tailers feed; costs from `usage_update` emit standard cost_events. No parallel state.

## Requirements

- FR-1: `AcpSessionClient` in `src/lib/acp/` wrapping the official SDK: spawn-under-PTY-supervisor, initialize/negotiate, session/new + load + resume, prompt, cancel, update-stream subscription, request_permission handler plumbed to the existing auto-approve policy.
- FR-2: `deliverAgentMessage` grows a top-priority ACP tier: if the agent's runtime record says `acp: true`, deliver via `session/prompt`; existing tiers remain as fallback.
- FR-3: Transcript: `session/update` events append to the agent's transcript store through the existing write door; the conversation panel renders them; `session/load` backfills on orchestrator restart.
- FR-4: Permissions: `session/request_permission` requests route through the auto-approve hook policy (same rules as today's PermissionRequest flow); unanswered → needs-you surface.
- FR-5: Harness flag `acp: true|false` per harness in config (default false); Gemini CLI ships with it available; enabling is per-project opt-in.
- FR-6: `usage_update` events (when capability present) emit cost_events rows tagged `source: acp` — reconciled against harness parsers by PAN-2388's machinery, never double-counted (dedupe key: session+turn).
- NFR-1: A wedged ACP agent (no update within the watchdog window mid-turn) surfaces through the existing stuck-detection; StopReasons feed the resolution states.
- NFR-2: Protocol version pinned; schema-release churn absorbed in `src/lib/acp/` only (no ACP types leak past the adapter boundary).
