# PAN-5402: Re-vendor the OKF skill at eltmon/okf v0.1.1 (adds `okf publish`)

**Issue:** https://github.com/eltmon/overdeck/issues/5402
**Upstream release:** https://github.com/eltmon/okf/releases/tag/v0.1.1 (annotated tag object `fca6633`, commit `d97b469`; adds `okf publish`, OKF-11, eltmon/okf PR #12)

## Glossary

- **OKF skill**: the `/okf` agent skill (`SKILL.md`, `README.md`, `docs/`, `references/`, `scripts/`, `templates/`). Its canonical repo is eltmon/okf.
- **Vendored tree**: the copy of one eltmon/okf release tag that Overdeck commits at `sync-sources/skills/okf/`. Only `scripts/vendor-okf-skill.sh` writes it. Nobody edits it by hand.
- **Pin file**: `sync-sources/skills/okf/.okf-skill-version`. One line holding the vendored tag plus a newline. Today it reads `v0.1.0`.
- **Vendor mode**: `bash scripts/vendor-okf-skill.sh <tag>`. It downloads `https://github.com/eltmon/okf/archive/refs/tags/<tag>.tar.gz`, `rsync -a --delete`s it into the vendored tree minus the root paths `.github .pan .overdeck tests CHANGELOG.md .gitignore .gitattributes`, and writes the pin file (`scripts/vendor-okf-skill.sh`, lines 109-125).
- **Pin check**: `bash scripts/vendor-okf-skill.sh --check`. It rebuilds the filtered tree of the tag named in the pin file and runs `diff -r -x __pycache__` against the vendored tree. It prints `okf skill matches eltmon/okf <tag>` and exits 0 on a match (lines 126-145).
- **`okf-vendor-pin`**: the CI workflow `.github/workflows/okf-vendor-pin.yml`. It runs the pin check on every PR that touches `sync-sources/skills/okf/**`.
- **changelog.d entry**: one file per PR at `changelog.d/<issue>.md`. `pan release stable` folds it into `changelog.mdx`. Format rules are in `changelog.d/README.md`, and `npm run lint:docs` (`scripts/lint-docs.js`, `checkChangelog`) enforces them.

## Background (verified 2026-11-15 against `a3a065e1bad`)

1. `sync-sources/skills/okf/.okf-skill-version` contains `v0.1.0`.
2. A dry run of vendor mode into a scratch copy of the vendored tree (`--dest <scratch>`) produced exactly this diff against the current tree. That is 5 modified paths and 10 added files:
   - Modified: `.okf-skill-version`, `README.md`, `SKILL.md`, `docs/USAGE.md`, `scripts/selftest.sh`
   - Added: `references/publish.md`, `scripts/publish.py`, `scripts/publish_markdown.py`, `scripts/publish_model.py`, `scripts/publish_redact.py`, `scripts/publish_render.py`, `scripts/publish_search.py`, `scripts/publish_assets/search.js`, `scripts/publish_assets/style.css`, `templates/okf-publish.yaml`
3. The `SKILL.md` change adds one command-table row (`| /okf publish --out <dir> [--check] | ... | references/publish.md |`) and a `## /okf publish --out <dir> [--check]` section. The frontmatter `description` is unchanged.
4. None of the 10 added paths is gitignored (`git check-ignore -v --no-index` printed nothing for each). The pin check therefore sees the same tree in CI as it does locally.
5. The only secret-shaped strings in the new tree are the redaction **regexes** in `scripts/publish_redact.py` lines 25-28 and `references/publish.md` lines 96-99 (for example `\bxox[abprs]-[A-Za-z0-9-]{10,}`). They are patterns, not literal tokens. No literal `xoxb-`, `ghp_`, `sk-…`, `AKIA…` or private-key block exists in any vendored file, so GitHub push protection has nothing to match.
6. No Overdeck lint reads the vendored files in a way the new content trips:
   - `eslint` scans `src/` only.
   - `lint:file-size` scans `src/**/*.ts(x)` only.
   - `lint:skills` validates `pan …` commands named in `SKILL.md`, and the new section names none.
   - `lint:slash-commands` compares the CLI registry, not skills.
   - `lint:prompt-trailer` covers `roles/*.md` and `pan-flywheel/SKILL.md` only.
   - `guard-no-state-layer` scans `sync-sources/**/*.md` for state-layer words, and a grep of the new tree's Markdown with its patterns found no hit.
7. `v0.1.0` appears as a literal in `src/cli/commands/__tests__/doctor-okf-skill.test.ts`, `src/lib/__tests__/vendored-skills.test.ts`, `tests/unit/lib/sync-okf-convergence.test.ts` and `tests/unit/scripts/vendor-okf-skill.test.ts`. Every occurrence is a fixture the test writes into a temp directory. None reads the real pin file, so none changes.
8. `configuration/knowledge.mdx` "## Where the skill lives" (lines 21-27) describes the vendoring process generically. It names no tag and no full command list, so the bump does not make it stale.

## Decisions

- **D1: The vendor script is the only writer of the vendored tree.** Do not hand-edit any file under `sync-sources/skills/okf/`. A hand edit fails `okf-vendor-pin` forever.
- **D2: The expected diff is fixed.** After vendor mode, `git status --short sync-sources/skills/okf` must list exactly the 15 paths in Background 2 (the 10 added files show as `??` before staging, or under the untracked `scripts/publish_assets/` directory). Any other path means the tag or the exclude list changed. In that case stop, do not commit, and report with `pan tell flywheel-orchestrator`.
- **D3: The changelog section is `#### New`.** `/okf publish` is a new capability that users can call.
- **D4: No change to `configuration/knowledge.mdx`.** The issue limits the change to the vendored tree plus the changelog entry, and Background 8 shows the page stays accurate. The changelog entry is the user-facing note.
- **D5: Test fixtures keep `v0.1.0`.** See Background 7.
- **D6: Do not run the skill's own scripts.** `scripts/selftest.sh` runs billed model calls, and `publish.py` is upstream-tested. Neither is part of this issue.
