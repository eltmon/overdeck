# PAN-5310 — Closed issues older than 14 days read as "writing code" / "No pull request yet"

**Issue:** https://github.com/eltmon/overdeck/issues/5310
**Status:** planned (auto mode, 2026-11-14)

## Glossary

- **Tracker poll window** — the dashboard keeps closed issues from the tracker poll only for `issues.closedWindowDays` days (default 14, `src/lib/config-yaml/defaults.ts`). Older closed issues are not in `lastFetchedIssues`.
- **Backfilled issue** — an issue older than the poll window that the server fetched on demand when someone opened it (`IssueDataService.backfillIssue()`, PAN-3659). It lives in the private map `backfilledIssues` in `src/dashboard/server/services/issue-data-service.ts` until a poll covers it again.
- **Derived state** — the per-issue pipeline answer (`DerivedIssueState`, `packages/contracts/src/derived-issue-state.ts`) computed from tracker + PR + git + panes by `deriveIssueState()` in `src/lib/overdeck/derived-issue-state.ts`. The server caches it in `derivedStatesCache` and ships it to the browser as `derivedIssueStateByIssueId`. The frontend reads it with `useDerivedIssueState(issueId)`.
- **Derived refresh** — `IssueDataService.scheduleDerivedStateRefreshForIssues()` → `refreshDerivedStates()` → `loadIssueStatesForProject()`. Only ids passed to the scheduler get a derived state.
- **Repo PR listing** — `listRepoPullRequests()` in `src/lib/overdeck/pr-listing.ts`: one `gh pr list --state open` plus one `gh pr list --state closed --limit 100`. Measured 2026-11-14: the oldest PR in eltmon/overdeck's closed listing was closed 2026-11-05, so the listing covers about 9 days.
- **Zombie PR** — a closed tracker issue whose PR is still open. `pipeline-membership.ts:139` names it bucket `zombie_pr` with the reason "issue is closed but a PR is still open — close/reconcile the PR".
- **Tracker closed** — the issue row's canonical state is `done` or `canceled`. The frontend predicate is `isClosedIssue(issue)` in `src/dashboard/frontend/src/lib/pipeline-state.ts` (line 124). The server predicate is `getTrackerIssue(id).open === false`.
- **Primary actions** — the buttons the issue header strip shows, from `getPhasePrimaryActions(state, phase)` in `src/dashboard/frontend/src/lib/issueActions.ts`. Today it ignores `enabledWhen`.

## Problem (verified against the code at `b41b8e75795`)

1. **Backfilled issues never get a derived state.** `pushUpdated()` (`issue-data-service.ts` line 790) schedules the derived refresh for `getCachedTrackerIssues()` (line 911), which returns only the four trackers' `lastFetchedIssues`. `backfillIssue()` (line 810) calls `pushUpdated()`, but the backfilled row is not in that list.    Every view that reads `useDerivedIssueState()` then renders its "nothing happened yet" default.
2. **Even with a derived state, an aged-out issue loses its merged PR.** `loadIssueStatesForProject()` (`derived-issue-state.ts` line 841) only knows PRs from the repo PR listing, which covers about 9 days of closed PRs. A backfilled issue (closed >14 days) therefore derives `closed` with no `pr`, so it can never read "Shipped". LEX-609's PR is open, so the open listing still finds it.
3. **The text is wrong when the state is present.**
   - `deriveNarrative` (`src/dashboard/frontend/src/components/Stage/cockpit/StatusNarrative.tsx` lines 24-67) has no `closed` branch. A closed issue falls through to "The crew is writing code", "Planning what to build" or "Waiting to start".

A closed issue with an open, unmerged PR would read "Merged to main" / "Merged and closed out". `derived.pr.merged` (contracts line 64, "survives state: closed (PAN-4290)") is the fact to read.
   - `derivePipelineState` (`src/dashboard/frontend/src/lib/issuePipelineState.ts` line 51) returns `generic` when `derived` is missing, even when the tracker says `done`. `generic` renders "Not started — No one has started this yet" with Start work (`lib/simple/userFacingState.ts` line 70) on the simple page and the peek popover.
4. **Header actions on a closed issue.** Traced:

   - The needs-you `pickup_gate` item (`issue-view/useIssueView.ts` line 446, `needsRelease`) has no closed check.
5. **The CLI cannot see a closed GitHub issue when `trackers.primary` is not `github`.** `readIssueFromTracker` (`derived-issue-state.ts` line 651) walks `[trackers.primary, trackers.secondary]` (line 680). ## Requirements

- **FR-1** — A backfilled issue is included in every derived refresh that `pushUpdated()` schedules, for as long as its row is in `backfilledIssues`. `getCachedTrackerIssues()` keeps returning raw tracker rows only (PAN-5261 FR-6: it feeds `seedTrackerIssues`/`noteTrackerIssues`).
- **FR-2** — For a backfilled GitHub issue whose PR is not in the repo PR listing, the derived refresh reads its merged PR for branch `feature/<id-lowercase>` once, through one metered `gh pr list --state merged --head <branch> --limit 1` call, and memoizes the settled answer (a row or `null`) for the process lifetime. A failed read is not memoized and reads as "no PR".
- **FR-3** — A closed issue's Status narrative (`deriveNarrative`) reads as closed, in three cases:
  - merged PR → headline `Shipped — this change is on main`, next `The issue is closed. Nothing needs you.`, `needsYou: false`;
  - open unmerged PR #N → headline `Closed, but pull request #N is still open — close or merge it`, next `The issue is closed but its pull request is still open. Close the pull request, or merge it if the change is still wanted.`, `needsYou: true`;
  - no PR → headline `Closed`, next `This issue is closed. Nothing needs you.`, `needsYou: false`.
  The closed branch runs first, before every other branch, and the ` Nothing needs you yet.` suffix is not appended to it. "Closed" means `derived.state === 'closed'` or the tracker row is closed.
- **FR-4** — `isShipped(derived)` is true only when `derived.state === 'merged'`, or `derived.state === 'closed'` and `derived.pr?.merged === true`. `deriveShip` gives a closed issue with an open PR status `pending`, its PR url/number, and `blockerReason` `The issue is closed, but this pull request is still open — close or merge it`. A closed issue with no PR gets ship status `closed`, and `ShipProgress` summarizes it as `Closed — no pull request is linked`. `deriveNowText` (useIssueView) for `closed` returns `Merged and closed out` (shipped), `Closed, but pull request #N is still open` (open PR), or `Closed` (no PR).
- **FR-5** — A closed issue offers no Plan…, Start work, Release, Close out or Create PR control in the issue view. Its only primary header action is Reopen. "Closed" here means the tracker row is `done`/`canceled` or `derived.state === 'closed'`.
- **FR-6** — `derivePipelineState` returns `done` when `derived` is missing and the tracker canonical state is `done`. The simple page and the peek popover then show "Done — This task is complete." and never "Not started".
- **FR-7** — The needs-you `pickup_gate` item is never raised for a closed issue.
- **FR-8** — `readIssueFromTracker` reads GitHub first for any id that `resolveGitHubIssue` resolves, whatever `trackers.primary`/`secondary` say, and then the configured trackers it has not tried. `pan show` then reports `closed` for a closed GitHub issue, with no `pr-outside-pipeline` attention.
- **NFR-1** — `src/dashboard/server/services/issue-data-service.ts` is exactly at its file-size cap (1754 lines, `scripts/file-size-allowlist.txt` line 141). Its change is net zero lines. Never raise the allowlist.
- **NFR-2** — No new `gh` call runs for an issue the repo listing already answers, or for any issue that is not backfilled. Every `gh` call goes through `runGh` with `caller: 'pr-cache'` (PAN-4264 quota metering).
- **NFR-3** — No new `execSync` or sync child-process call in server-reachable code. Tests that touch timers use `vi.useFakeTimers()`.

## Decisions (auto mode)

- **D1 — Schedule backfilled rows at the call site, not in `getCachedTrackerIssues()`.** That function feeds the tracker-change membership trigger (`read-model.ts` lines 679 and 690), which must see raw tracker rows only.
- **D2 — Per-issue merged-PR read is limited to backfilled ids.** Issues closed 9-14 days ago (in the poll window, beyond the closed listing) have the same gap, but widening the read to them costs a `gh` call per closed issue at boot. That is out of scope (see Non-goals). The backfilled set is small: it only holds issues someone opened.
- **D3 — Query `--state merged`, not `--state all`.** An open PR is already in the open listing. A closed-unmerged PR is dropped by `prFromGhRow` anyway. So only a merged row can change the answer.
- **D4 — Closed issues get Reopen as the only primary action.** Implemented in `getPhasePrimaryActions`: when the issue is closed, return `[reopen]` instead of the phase's keys. No new `PipelinePhase` member: `MERGED` stays the phase (`KanbanCards.tsx` line 516 and others key on phase names).
- **D5 — `isDoneOrCanceled` also counts `derived.state === 'closed'`.** The derived `closed` state is the tracker's closed state, so every gate that already excludes done/canceled issues (Plan, Start work, Cancel, Reset, Add to order book, Run on Deft) now excludes them in the window where the row's canonical state lags.
- **D6 — GitHub is tried first, not last, in `readIssueFromTracker`.** `resolveGitHubIssue` is an id-specific prefix mapping, so it is more specific than the global tracker order. The other configured trackers still run after it, deduplicated.
- **D7 — The Details tab hides the whole pickup section for a closed issue**, not just its Release button. Ready / Park / Blocks main have no meaning for a closed issue.
- **D9 — `StartAgentCta` and the action menu need no extra guard.** They read `startAgent.enabled`, and `canStartAgent` already excludes `isDoneOrCanceled`, which D5 widens.
- **D8 — The header pickup strip needs no code change.** With FR-1 the derived state is `closed`, `pickupStageFor('closed')` is `finished`, and the strip renders nothing (already covered by `PickupGateControls.test.tsx`).
