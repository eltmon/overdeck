## Glossary

- **Create core** — the one project-registration path. `resolveProjectCreateIntent` (`src/lib/projects/create.ts`) is read-only and safe per keystroke; `performProjectCreate` / `finishProjectSetup` (`src/lib/projects/create-perform.ts`) write. HTTP: `POST /api/projects/resolve` (`src/dashboard/server/routes/projects.ts:887`, `const postProjectsResolveRoute`) and `POST /api/projects` (`src/dashboard/server/routes/project-create-routes.ts:239`, `const postProjectsRoute`). There is never a second registration path (CLAUDE.md, "Project creation is one core, two halves").
- **Finding** — a blocking resolve result `{ field, code, message, detail? }` (`ProjectIntentFinding`, `create.ts:91`).
- **Notice** (new) — a non-blocking resolve result `{ code, message, detail? }`. A create with notices but no findings proceeds.
- **Repo-root snap** — when an `existing`-mode path is a subfolder of a git checkout, resolve replaces the path with the checkout root instead of refusing (Orca parity).
- **Nested repositories** — immediate child folders of a non-git folder that contain `.git` (directory *or* file — a linked worktree has a `.git` file).
- **Multi-repo project** — a project whose `projects.yaml` entry has `workspace.type: polyrepo` and a `workspace.repos[]` list, like `mind-your-now` and `auricle` on the operator's machine. Its root may be a git repo (MYN) or a plain folder (Auricle).
- **`pan_records.repo`** — the `workspace.repos[].name` whose checkout holds the project's `.pan/` planning records (`resolveInfraRepo`, `src/lib/projects.ts:882`). Missing means "the project root".
- **Suggestions** — the unregistered git repositories directly under `getDefaultCwd()` (`src/lib/default-cwd.ts`: `~/Projects` when it exists, else `~`).
- **AddProjectDialog** — the new modal (and, at `/projects/new`, page) that replaces the full-page chooser.
- **ProjectCreateForm** (new) — the chosen-mode form body of today's `NewProjectPage` (fields, Options disclosure, folder picker, progress, failure/repair UI), moved unchanged into its own component so the dialog's clone/create/folder steps and the page share it.
- **Launcher** — the type-to-start input in a Command Deck project's Home tab (`src/dashboard/frontend/src/components/Stage/HomePane/Launcher.tsx`), mounted by `ProjectHome` (`components/Stage/ProjectHome.tsx:114`).
- **Deck key** — the Stage's per-deck id (`api.deckKey` in `ProjectHome`), equal to the project key for a project deck.
- **Smart field** — the New Workspace name input, upgraded to classify what you type (issue ref, URL, branch, or plain name) and suggest actions.
- **Workspace resolve** — `resolveWorkspaceCreateIntent` (`src/lib/workspaces/create.ts:241`), served at `POST /api/workspace-registry/resolve` (`src/dashboard/server/routes/workspace-registry.ts:237`).

## Problem

1. **A subfolder inside a repo is refused.** `create.ts:670-682` pushes finding `repository-root-elsewhere` ("That folder is inside a Git repository rooted at X. Add that folder instead."). Orca silently uses the repo root. The already-registered checks (`create.ts:578-597`, `const registered = getProjectSync(key);`) also run *before* git-root detection, so they compare the subfolder, not the root.
2. **A folder of repos registers as one plain project.** Resolve sees a non-git folder (`create.ts:693-697`, `intent.isGitRepository = false;`) and offers nothing else. Operator decision 2026-09-27 (3): such a folder must be addable either as one project per repo, or as **one multi-repo (`workspace.type: polyrepo`) project**, and multi-repo projects stay first-class.
3. **No suggestions.** Nothing lists the repos already sitting in `~/Projects`.
4. **The Add-project surface is a full page with Ctrl-only submit.** `/projects/new` (`src/dashboard/frontend/src/pages/NewProjectPage.tsx`, 603 lines) navigates you away; clone submits only on Ctrl/Cmd+Enter (`NewProjectPage.tsx:173-182`, `if ((event.metaKey || event.ctrlKey) && event.key === 'Enter')`); a non-git folder is accepted with no explanation.
5. **After adding a project you land on its deck but the Launcher is not focused** (`App.tsx:232-246`, `handleProjectCreated`).
6. **New Workspace has a plain title input** (`NewWorkspacePage.tsx:253-265`, `data-testid="new-workspace-hero-title"`) and a free-text parent branch; with zero projects its resolve says "Multiple projects are registered — choose one." (`src/lib/workspaces/create.ts:171-176`).

## Decisions

Decisions D8–D12 come from the shared PRD; the rest are made here (auto mode).

- **D8 — Snap is a notice.** In `existing` mode, when `detectGitRoot(path)` returns a root ≠ `path`, resolve sets `intent.path` to the root, re-derives the auto name and key from the root's basename unless the caller supplied `name`, and adds notice `using-repository-root`. Git-root detection therefore moves ahead of the already-registered checks. **Home guard:** when the detected root equals the canonical home directory (a dotfiles-managed `~`), resolve does not snap and treats the folder as non-git (`gitRoot` stays set for information), so picking `~/Projects` still reaches the nested scan instead of offering to register `~`. Finding code `repository-root-elsewhere` is deleted from `ProjectIntentCode` (`create.ts:87`) and nothing emits it.
- **D9 — Nested scan is depth 1, capped at 50, sorted by name,** read with `readdir(withFileTypes)` + `stat(<child>/.git)`; dot-folders are skipped; no child processes.
- **D10 — Suggestions are read-only.** `GET /api/projects/suggestions` returns `{ root, repositories: [{ path, name }] }`, at most 20, unregistered by canonical path. `root` is `getDefaultCwd()`, which the dialog's folder step also uses as the picker's start folder. The route lives in `project-create-routes.ts` (371 lines), not `projects.ts` (955 lines, near the 1000 ceiling).
- **D11 — One dialog component.** `AddProjectDialog` renders as a modal (mounted once in `App/AppChrome.tsx`) or as a page (`variant="page"`, rendered by `NewProjectPage`). A zustand store opens the modal. `/projects/new?mode=…&returnTo=…` keeps working.
- **D12 — The Smart field classifies; it adds no spawn path.** First match wins: issue ref (`#12`, `<PREFIX>-12` for a registered prefix, case-insensitive, or a GitHub issue/PR URL) → "Open <ID> and start work" navigates to `/issues/<ID>`; branch match → sets `parentBranch`; else → workspace name.
- **D17 — Multi-repo create input.** `ProjectCreateInput.repos?: string[]` holds child folder *names* (single path segments) of `path`. It is honoured only in `existing` mode when `path` is not itself inside a git repository. Resolve validates every name and fills `intent.workspaceRepos`. Registration writes exactly the shape the live polyrepo projects use:
  ```yaml
  workspace:
    type: polyrepo
    workspaces_dir: workspaces
    repos:
      - { name: frontend, path: frontend, branch_prefix: feature/, default_branch: main, forge: github }
  pan_records: { repo: frontend }   # the first repo, so .pan/ lands inside a git checkout
  ```
  `default_branch` and `forge` are written per repo only when detected (the create core never guesses `main`, `create-perform.ts:80-82`). Workspace-level `default_branch` is omitted. No `tracker`/`github_repo` is written for a multi-repo project (one tracker cannot be inferred from N remotes). Why `pan_records`: `resolveInfraRepo` defaults to the root, and a plain-folder root (Auricle shape) would put `.pan/` outside any git repository.
- **D18 — "Add this folder as one project" means the multi-repo project.** W7's button label is kept; a sub-line reads "One multi-repo project spanning the checked repositories." This is the operator's decision (3), not a plain-folder registration. (A plain folder with *no* nested repos still gets "Add as folder".)
- **D19 — Batch and suggestion creates use a helper, not the stateful hook.** `useProjectCreateIntent` drives one debounced form and has no `repos` field. A new `resolveThenCreateProject(body)` in `components/project/new/resolveThenCreate.ts` POSTs `/api/projects/resolve`, returns the findings if any, else POSTs `/api/projects` (existing mode answers 200 synchronously, `project-create-routes.ts:338-363`). FR-17 and AC-7 are about routes, so this is still the one create core.
- **D20 — Nested batch reports once.** "Add N projects" creates sequentially; a failing row shows its message and the rest continue. When every row succeeds, the dialog calls `onCreated` once with the last project and closes. When any row fails, it stays open with per-row results and a **Done** button that calls `onCreated` with the last success (if any) and closes.
- **D21 — `returnTo` travels through the store.** `getProjectCreatedNavigation` (`App/routes.ts:143`) reads `window.location.search`, which in modal mode is `/workspaces/new`, not `/projects/new?returnTo=…`. It gains an optional `returnTo` parameter; `handleProjectCreated` passes `takeAddProjectReturnTo()` (store helper: returns and clears the store's `returnTo`, else `undefined`, and the function falls back to the URL).
- **D22 — The Smart field's "Use as the name" sets a slug.** `validateFeatureName` (`src/lib/workspace-manager/worktree-ops.ts:16`, `/^[a-zA-Z0-9-]+$/`) rejects spaces, so the suggestion reads `Use "fix-login-redirect-bug" as the name` and sets that slug. Implementation checkpoint resolved: the core already derives the branch (`intent.branchName = \`scratch/${name}\``, `workspaces/create.ts:339`), so the "Branch:" preview shows `intent.intent.branchName` and no second branch-slug function is added. The one slug function (`toWorkspaceSlug`) lives in `smartField.ts`.
- **D23 — The CLI prints notices.** `pan project add <subfolder>` now snaps; `src/cli/commands/project.ts` prints each notice as a dim line (`ℹ Using the repository root <root>.`) before creating. The `--dry-run` JSON gains `notices` (and `nestedRepositories`, `workspaceRepos`) automatically through `toPublicProjectIntent`.
- **D24 — Form body moves, it is not rewritten.** The chosen-mode view of `NewProjectPage` moves into `ProjectCreateForm.tsx` with identical labels, test ids, and aria wiring. The dialog's entry copy changes ("Open a folder", "Clone from URL"), so the two existing page tests update their entry-label regexes only; every row's interaction assertion stays.
- **D25 — New frontend tests join the CI subset.** Root `package.json` `test:frontend-subset` is the only frontend test list CI runs (codebase map, conventions.md). The new dialog, smart-field, and launcher-focus tests are appended to it.
- **D26 — Size.** This plan exceeds the 25-file / 6-subsystem projected-surface lint. The operator already split the program into three sibling issues (4280/4281/4282); W6–W8 share the create core, the dialog, and post-create navigation, and W9 was placed here by the PRD author. `plan.metadata.sizeJustification` records this.
