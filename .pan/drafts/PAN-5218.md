# PAN-5218: File a follow-up issue after merge for CodeRabbit findings nobody settled

**Issue:** https://github.com/eltmon/overdeck/issues/5218
**Status:** planned (auto mode, 2026-11-13; revised after plan critique round 1)

## Glossary

- **CodeRabbit relay.** `relayCodeRabbitReview` in `src/lib/cloister/coderabbit-feedback.ts`. It runs on the `pull_request_review` webhook for a review by `coderabbitai[bot]`, writes a feedback file listing each inline thread, and delivers a keyed message to the work agent (PAN-4773).
- **Delivery.** One relay of one CodeRabbit review, keyed by its `dedupKey` = `coderabbit-feedback:<issue-lower>:<reviewId>` (`codeRabbitDedupKey`, `coderabbit-feedback.ts` line 96).
- **Pipeline journal.** The append-only per-issue log at `<workspace>/.overdeck/pipeline.jsonl` (`src/lib/cloister/pipeline-journal.ts`). Entries are written at the moment of an action and never rewritten. It is never authority: where it disagrees with the PR, the PR wins.
- **Thread.** One top-level inline CodeRabbit comment (`CodeRabbitThread`, `src/lib/cloister/coderabbit-ingestion.ts` line 121): `id`, `path`, `line`, `severity`, `title`, `url`.
- **Settled thread.** A thread the work agent answered before the merge, as defined exactly in "Settlement truth table". Settlement is decided **per thread**, never for a whole delivery at once.
- **Follow-up issue.** A new GitHub issue created through the GitHub App, so authored by `overdeck-agent[bot]`. It quotes each unsettled thread of one delivery and links the PR and the review.
- **Needs-you.** The operator-attention signal raised by `surfaceIssueFeedbackNeedsYou` (`src/lib/cloister/feedback-target.ts` line 306): a warn-level activity entry `"<issue> needs you: <reason>"`.
- **Post-merge lifecycle.** `postMergeLifecycle` in `src/lib/cloister/merge-agent.ts` line 209. Every merge path reaches it, and it appends `merge.completed` once the forge answers "merged" (line 267).
- **Kick.** The immediate, non-awaited call to the filer from `postMergeLifecycle` right after `merge.completed`.
- **Patrol.** `recoverAdvisoryFollowups`, a deacon-lite routine (`src/lib/cloister/deacon-lite.ts` `runDeaconLite`, 60 s cadence) that finds merged issues whose journal still holds an unfiled, unfailed advisory delivery. It covers what the kick missed: a restart mid-filing, or a delivery journaled after `merge.completed`.
- **Advisory follow-up modules.** The new files `src/lib/cloister/advisory-followup-settlement.ts`, `advisory-followup.ts` and `advisory-followup-patrol.ts`. They are named "advisory" and not "coderabbit" because `merge-agent.ts` imports one of them and may not contain the string `coderabbit` (fact 5).

## Problem

A CodeRabbit finding relayed to a work agent is lost when the PR merges before the agent acts on it. Evidence from PAN-5198 / PR #5203: `review.verdict` at 21:00:02, `feedback.delivered` (kind `coderabbit`, dedupKey `coderabbit-feedback:pan-5198:5897989031`, one Major finding) at 21:00:37, `merge.attempted` at 21:10:38, `merge.completed` at 21:10:53, and no commit, re-review request or follow-up issue in between. The feedback body's step 5 (`coderabbit-feedback.ts` line 125) asks the agent to open a follow-up if the PR already merged, but nothing makes sure that happens:

```ts
    `5. If PR #${event.prNumber} has already merged when you read this, nothing more lands on it: open a follow-up issue`,
    '   for the findings you agree with instead of pushing.',
```

On the last 25 PRs CodeRabbit reviewed 14, posting 2 to 90 minutes before merge. The race is common.

## Verified facts the design rests on

1. **The journal entry is too thin today.** `recordFeedbackDelivered` (`src/lib/cloister/feedback-delivery-record.ts` line 66) writes only `{ kind, dedupKey, agentId }`. After the merge there is no repo, PR number, review id or thread list left to quote.
2. **The no-agent path journals nothing.** In `runRelay` (`coderabbit-feedback.ts` lines 169-208), every Needs-you branch returns without a journal entry.
3. **The GitHub App cannot create issues today.** A read of the live installation (`GET /app/installations/<id>` under the App JWT, 2026-11-13) returned `{"checks":"read","contents":"write","metadata":"read","statuses":"write","pull_requests":"write"}` for slug `overdeck-agent`. There is no `issues` permission, so `POST /repos/<owner>/<repo>/issues` returns 403 "Resource not accessible by integration" until the operator grants **Issues: Read and write**. Until then every follow-up takes the Needs-you path (FR-7), which the issue already names as the failure path.
4. **The Flywheel author gate names the old bot.** `roles/flywheel.md` line 100 and `sync-sources/skills/pan-flywheel/SKILL.md` line 98 allowlist `panopticon-agent[bot]`. The App slug is `overdeck-agent`, and `gh` prints the bot's login as `overdeck-agent`. That gate is a security rail pinned by `tests/unit/prompts/prompt-invariants.test.ts` line 35, and follow-up bodies quote third-party CodeRabbit text. This issue does not change it (NonGoal). The mismatch is reported on the issue (comment 6869213503).
5. **`merge-agent.ts` must never contain `coderabbit`.** `scripts/lint-no-coderabbit-merge-gate.sh` lists it in `GATE_FILES` and fails on a case-insensitive `grep -qi 'coderabbit'`. That includes import paths and comments.
6. **File-size headroom.** `merge-agent.ts` is 904 lines (cap 932, `scripts/file-size-allowlist.txt` line 105). `github-app.ts` is 921 (cap 1083, line 140). `deacon-lite.ts` is 702 (ceiling 1000). `src/dashboard/server/main.ts` is 981 with no allowlist row, so it must not be touched: no new dashboard service can be started there. No allowlist row may be raised.
7. **The relay is not awaited.** `webhook-handlers.ts` lines 430-432 start the relay with `void`. The relay then awaits a thread read (`coderabbit-feedback.ts` line 163) before it journals at line 209. So a `merge.completed` can land before the delivery entry. The kick alone would miss that delivery; the patrol catches it (D-2).
8. **Nothing re-runs a finished lifecycle.** `_completedPostMerge` is in memory. `pending-lifecycle.ts` re-runs a lifecycle only from a pending file that an older restart path writes, and it deletes the claim once `postMergeLifecycle` resolves. So the kick has no durable retry, and the patrol is the retry (D-2).
9. **`appendPipelineEntry` never reports a failed write.** It logs the failure and returns the stamped entry (`pipeline-journal.ts` lines 72-100). A journal marker alone cannot guarantee "filed once" (D-4).
10. **A re-review request carries only free text.** `requestReviewGuarded` builds `data.note` = `Agent re-review request (<n>/<max>): <message>` from `pan review request <id> -m <message>` (`review-pipeline.ts` line 707). It returns `already-passed` and journals nothing when an approval stands at the head (~line 690).
11. **Thread replies are the agent's existing explicit skip.** The feedback body (step 3, line 121) already tells the agent to reply on a thread with its reason when it rejects a finding. GitHub REST review comments carry `in_reply_to_id` pointing at the top-level comment.

## Decisions (made here; the executor does not re-decide)

- **D-1 Author.** Follow-ups are created only through the GitHub App (`POST /repos/{owner}/{repo}/issues`). There is no fallback to the `gh` user. Every failure, including the missing Issues permission, raises Needs-you and journals `feedback.followup_failed` (FR-7).
- **D-2 Two triggers, one filer.** The kick runs `fileAdvisoryFollowups` right after `merge.completed`, never awaited. The patrol re-runs it for any merged issue whose journal still holds a pending candidate: no `feedback.followup_filed` or `feedback.followup_failed` for its key. It waits until `merge.completed` is at least 10 minutes old and the candidate at least 2 minutes old, so it never races the kick's normal run. Neither trigger can delay or gate a merge: both run after the forge said "merged".
- **D-3 Settlement is per thread and tied to the thread.** A thread is settled by a reply on it, by a later commit that changed its file, or by a later re-review note naming its thread id. When a forge read fails, that evidence counts as absent and the thread is filed. A redundant follow-up costs one closed issue; a false "settled" loses the finding.
- **D-4 Dedup is the journal plus a forge lookup.** Before creating, the filer searches the tracker repo for an issue whose body contains the `dedupKey`. A hit journals `feedback.followup_filed` with `data.recovered: true` and creates nothing. A miss creates the issue, then journals the marker. The promise: one issue per key on every normal path. A duplicate needs a crash between POST and journal write **and** a search miss at least 10 minutes later. Strict exactly-once across processes is not promised.
- **D-5 Tracker repo.** The follow-up goes to the issue's GitHub tracker repo from `resolveGitHubIssue(issueId)` (`src/lib/tracker-utils.ts` line 94). For `{ isGitHub: false }`, raise Needs-you with the findings.
- **D-6 Older journal entries.** A `feedback.delivered` entry of kind `coderabbit` with no `data.threads` array (written before this change) is skipped with one log line.
- **D-7 Entry names.** `feedback.followup_filed` is spelled exactly as the issue spells it. The other new entries are `feedback.undelivered` and `feedback.followup_failed`.
- **D-8 Bounded reads.** Per PR: one paginated commit list, one paginated review-comment list, and one `commits/<sha>` read per non-merge commit later than the earliest candidate. The search lookup runs once per filing.
- **D-9 Every finding is listed.** The follow-up body lists every unsettled thread, with no cap. If GitHub rejects the body as too long (422), that is a filing failure: Needs-you carries the full finding list.

## Settlement truth table

The candidates are `feedback.delivered` and `feedback.undelivered` entries whose `data.kind` is in `ADVISORY_FOLLOWUP_KINDS = ['coderabbit']`. When one `dedupKey` has several entries, the latest is the candidate, and its `at` is the delivery time.

Delivery-level checks, in order:

| Check | Outcome |
| --- | --- |
| The journal holds `feedback.followup_filed` with this `dedupKey` | `already-filed`: nothing happens |
| The journal holds `feedback.followup_failed` with this `dedupKey` | `already-failed`: nothing happens (Needs-you was raised) |
| The entry has no `data.threads` array, `data.repo` or `data.prNumber` | `legacy`: one log line, nothing filed |

Then each thread is **settled** when any of these holds:

- **T (reply):** the PR has a review comment with `in_reply_to_id == thread.id` from a login other than `coderabbitai[bot]`.
- **P (commit on its file):** `thread.path` is set, and a single-parent PR commit with committer date strictly later than `at` lists `thread.path` among its changed files.
- **R (named in a re-review):** the journal holds a `review.requested` entry strictly later than `at` whose `data.note` contains `String(thread.id)`.

When no thread is unsettled, the outcome is `settled`. Otherwise it is `unsettled`, carrying only the unsettled threads in their original order. A failed commit-list read means no P for any thread, a failed per-commit file read means that commit settles nothing, and a failed comment read means no T.

Worked case (the critique's two-review example): review A has thread 11 on `src/a.ts`, and review B has thread 21 on `src/b.ts`. The agent commits a change to `src/b.ts` and runs `pan review request X -m "CodeRabbit 21: guarded b"`. Thread 21 is settled (P and R). Thread 11 stays unsettled, so A's follow-up is filed with thread 11.

## Requirements

### Functional

- **FR-1** The journal type union gains `feedback.undelivered`, `feedback.followup_filed` and `feedback.followup_failed`, and `pan show` prints a one-line summary for each.
- **FR-2** A delivered CodeRabbit relay journals `feedback.delivered` with `data` = `{ kind: 'coderabbit', dedupKey, agentId, repo, prNumber, reviewId, reviewUrl, threads }`, where `threads` holds every relayed thread as `{ id, path?, line?, severity?, title, url? }`.
- **FR-3** Each relay branch that raises Needs-you after the threads were fetched also journals `feedback.undelivered` with `data` = `{ kind: 'coderabbit', dedupKey, reason, repo, prNumber, reviewId, reviewUrl, threads }`. Needs-you is still raised.
- **FR-4** A pure function decides each candidate's outcome per the truth table.
- **FR-5** After `merge.completed`, the post-merge lifecycle kicks the filer, fire-and-forget. The deacon-lite patrol re-runs the filer for merged issues with pending candidates, per D-2.
- **FR-6** For each `unsettled` candidate the filer creates one GitHub issue through the App in the tracker repo (format below), unless the forge lookup finds one. Either way it journals `feedback.followup_filed` with `data` = `{ kind, dedupKey, issueNumber, issueUrl, repo, prNumber, threads: <count>, recovered?: true }`.
- **FR-7** When filing cannot happen (non-GitHub tracker, App not configured, forge error, missing Issues permission, body too long), the filer raises Needs-you naming the PR, the count, the cause and the fix, with `details.findings` listing every unsettled thread. It journals `feedback.followup_failed` with `{ kind, dedupKey, reason }`.
- **FR-8** A candidate with `feedback.followup_filed` or `feedback.followup_failed` for its key is never acted on again by either trigger.
- **FR-9** The feedback body's step 5 tells the agent that Overdeck files the follow-up after merge. Steps 3-4 and the delivery message tell it to name the thread ids it changed in `pan review request <id> -m "CodeRabbit <thread ids>: …"`.

### Non-functional

- **NFR-1** Nothing in this change delays, blocks or influences a merge. `merge-agent.ts` gains only a non-awaited call, and `npm run lint:no-coderabbit-merge-gate` stays green.
- **NFR-2** The filer and the patrol never throw into their callers. Every failure is logged or raised as Needs-you.
- **NFR-3** No `execSync` in server-reachable code. `gh` is called through `runGh` (`src/lib/github-quota/run-gh.ts`, async).
- **NFR-4** No file grows past its ceiling, and no allowlist row changes. `src/dashboard/server/main.ts` is not edited.

## Follow-up issue format

Title: `CodeRabbit follow-up for <ISSUE> (PR #<n>): <k> unsettled finding(s)`

Body (exact shape; `<…>` are substitutions):

```markdown
CodeRabbit posted these findings on PR #<n> (https://github.com/<prRepo>/pull/<n>), review <reviewUrl>.
They were relayed to <agentId, or "no work agent: <reason>"> at <at>, and the PR merged before they were settled:
no reply on the thread, no later commit to the file, and no re-review request naming the thread.

CodeRabbit is advisory. For each finding, fix it or close it with a reason.

- `<path>:<line>` [<severity>] <title> (<thread url>)
- …

Parent issue: <ISSUE>. Delivery key: `<dedupKey>`.
```

Location, line and severity follow `threadLine` in `coderabbit-feedback.ts` line 100: no `path` prints `general`, no `line` prints just the path, and no `severity` omits the brackets. Every unsettled thread is listed (D-9). The literal `Delivery key: \`<dedupKey>\`` line is what the D-4 search finds.

```ts
export async function fetchPullRequestSettlementFacts(
  repo: string,
  prNumber: number,
  since: string,
```

### W-6 The filer (FR-5 to FR-8, D-4, D-9)

New file `src/lib/cloister/advisory-followup.ts`, in the deps-injection style of `coderabbit-feedback.ts`:

```ts
export interface AdvisoryFollowupDeps {
  readJournal?: (workspacePath: string) => PipelineJournalEntry[];
  fetchFacts?: (repo: string, prNumber: number, since: string) => Promise<PullRequestSettlementFacts>;
  resolveTrackerRepo?: (issueId: string) => { owner: string; repo: string } | null;
  appConfigured?: () => boolean;
  findExisting?: (owner: string, repo: string, dedupKey: string) => Promise<{ number: number; url: string } | null>;
  createIssue?: (owner: string, repo: string, input: { title: string; body: string }) => Promise<{ number: number; url: string }>;
  appendEntry?: typeof appendPipelineEntry;
  surfaceNeedsYou?: (issueId: string, reason: string, details: Record<string, unknown>) => Promise<void>;
  log?: (line: string) => void;
}

export type AdvisoryFollowupOutcome =
  | { dedupKey: string; outcome: Exclude<AdvisorySettlement['outcome'], 'unsettled'> }
  | { dedupKey: string; outcome: 'filed'; issueNumber: number; issueUrl: string; recovered: boolean }
  | { dedupKey: string; outcome: 'needs-you'; reason: string };

/** Never throws. One in-flight run per issue in this process; a concurrent call joins it. */
export function fileAdvisoryFollowups(issueId: string, workspacePath: string, deps?: AdvisoryFollowupDeps): Promise<AdvisoryFollowupOutcome[]>;
```

Defaults:

- `readJournal`: `readPipelineJournal`.
- `fetchFacts`: `fetchPullRequestSettlementFacts` with a `runGh`-based runner, as in `coderabbit-feedback.ts` line 76.
- `resolveTrackerRepo`: `resolveGitHubIssue`, giving `{ owner, repo }`, or `null` when `isGitHub` is false.
- `appConfigured`: `isGitHubAppConfigured`.
- `findExisting`: through the same runner, `gh(['api', '-X', 'GET', 'search/issues', '-f', `q=repo:${owner}/${repo} is:issue in:body "${dedupKey}"`, '--jq', '.items[0] // empty | {number, url: .html_url}'])`. Empty stdout gives `null`, and a rejection propagates for the filer to log.
- `createIssue`: `createIssueWithApp`.
- `appendEntry`: `appendPipelineEntry`.
- `surfaceNeedsYou`: `surfaceIssueFeedbackNeedsYou`.
- `log`: `console.log`.

Steps:

1. Read the journal and take `advisoryCandidates`. Drop candidates for which `isAdvisoryCandidateClosed` is true, recording `already-filed` or `already-failed`. With none left, return without any forge read.
2. Group the remaining candidates by `repo#prNumber`. For each PR, call `fetchFacts` once, with `since` = the earliest candidate `at` for that PR.
3. Call `settleAdvisoryDelivery` on each candidate and log one line per outcome other than `unsettled`.
4. For each `unsettled` candidate:
   - **No tracker repo:** fail with "<ISSUE> is not tracked on GitHub, so …".
   - **App not configured:** fail with "no GitHub App is configured, so …".
   - **Otherwise:** call `findExisting`. A lookup error is logged and treated as a miss. A hit appends `feedback.followup_filed` with `recovered: true`. A miss calls `createIssue` with the PRD title and body, then appends `feedback.followup_filed` (source `advisory-followup`). An error from `createIssue` fails with its message. When `isIntegrationPermissionError(message)` holds, the reason is: `the GitHub App cannot create issues on <owner>/<repo>: grant it Issues: Read and write in its GitHub App settings and accept the new permission on the installation`.
5. "Fail" means two things:
   - raise Needs-you with `details` = `{ specialist: 'coderabbit', prNumber, dedupKey, findings: <every unsettled thread line> }`;
   - append `feedback.followup_failed` with `{ kind, dedupKey, reason }` (source `advisory-followup`).

### W-8 The deacon-lite patrol (FR-5, FR-8, D-2)

New file `src/lib/cloister/advisory-followup-patrol.ts`, and `src/lib/cloister/deacon-lite.ts`:

```ts
export const ADVISORY_PATROL_MERGE_AGE_MS = 10 * 60_000;
export const ADVISORY_PATROL_CANDIDATE_AGE_MS = 2 * 60_000;

export interface AdvisoryPatrolDeps {
  listWorkspaces?: () => Pick<WorkspaceRow, 'issueId' | 'path'>[];
  readJournal?: (workspacePath: string) => PipelineJournalEntry[];
  file?: (issueId: string, workspacePath: string) => Promise<AdvisoryFollowupOutcome[]>;
  log?: (line: string) => void;
}

/** One pass. Never throws. Returns one `<ISSUE>: <n> follow-up outcome(s)` line per issue it ran the filer for. */
export async function recoverAdvisoryFollowups(now = Date.now(), deps: AdvisoryPatrolDeps = {}): Promise<string[]>;
```

For each workspace with an `issueId` and an existing path, read the journal. Run the filer only when all three hold:

- the journal has a `merge.completed` entry at least `ADVISORY_PATROL_MERGE_AGE_MS` old;
- at least one `advisoryCandidates` entry has `isAdvisoryCandidateClosed` false;
- that entry is at least `ADVISORY_PATROL_CANDIDATE_AGE_MS` old.

One workspace's failure is logged, and the pass continues. The defaults are `listWorkspaces` from `../workspaces/resolver.js`, `readPipelineJournal`, `fileAdvisoryFollowups` and `console.log`.

```ts
  await recoverAdvisoryFollowups();
```

## Critique response

### merge can outrun the relay

Accepted. Fact 7 confirms it: the relay is not awaited, and it journals only after a thread read. The fix is the deacon-lite patrol (W-8, D-2). It runs the filer for any merged issue whose journal holds a pending candidate, whatever order `merge.completed` and the delivery entry landed in. The order `[merge.completed, feedback.delivered]` is a named W-8 test. I chose the patrol over a second trigger inside the relay because the patrol also answers the next finding, so one mechanism covers both. It also keeps the relay free of any merge awareness. This also covers a CodeRabbit review posted after the merge, which the first draft had listed as a NonGoal.

### detached filing has no durable retry

Accepted. Fact 8 confirms nothing re-runs a finished lifecycle. The patrol is the durable retry: the journal is the job record. An advisory candidate without `feedback.followup_filed` or `feedback.followup_failed` is a pending job, and the patrol reconciles it on every 60 s deacon-lite tick once the 10-minute and 2-minute ages pass. A restart at any point after `merge.completed` leaves the candidate pending, so the next patrol files it. The patrol runs after the merge, outside every merge path. It needs no new store and no `main.ts` change.

### unrelated work settles every finding

Accepted. Settlement is now per thread and tied to the thread (truth table, D-3). A commit settles a thread only when it changed that thread's file. A re-review note settles a thread only when it names that thread's id. A reply settles only the thread it answers. The critique's two-review example is the worked case, and it is a W-2 test. The relay now tells the agent to name thread ids in `pan review request -m` (W-3).

### journal-only dedup is not one issue ever

Accepted in part. Before creating, the filer searches the tracker repo for an issue whose body contains the delivery key (D-4, W-6). A hit repairs the journal marker instead of creating a second issue, and the W-6 "findExisting returns a hit" case tests it. That case is the successful-POST/failed-append scenario on the retry. Strict exactly-once across processes is narrowed explicitly, with no lock. A duplicate now needs a crash between POST and journal write and a search miss at least 10 minutes later, when the index has caught up. That costs one closed duplicate issue. A cross-process lock is out of proportion for an advisory, never-gating feature.

### the 100-thread cap drops findings

Accepted. The cap is gone (D-9). Every unsettled thread is listed, and a 120-thread case is a W-6 test. A body GitHub rejects as too long is a filing failure, so Needs-you carries the full finding list and nothing is dropped silently.
