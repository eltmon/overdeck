# PAN-4279 — One non-blocking degraded-mode banner for dashboard outages

**Issue:** [PAN-4279](https://github.com/eltmon/overdeck/issues/4279)
**Status:** planned (auto mode, 2026-09-27)
**Scope:** `src/dashboard/frontend/` only, plus `docs/DASHBOARD-ARCHITECTURE.md` and the root `package.json` frontend test subset. No server changes.

## Glossary

- **Connection store** — the new Zustand store `src/dashboard/frontend/src/lib/connectionState.ts` (WI-1). It is the single source of truth for "can this tab talk to the server right now, and how fresh is its data".
- **Connection phase** — the derived value the store exposes. Exactly one of:
  - `live` — the server answers and the `/ws/rpc` domain stream has bootstrapped.
  - `delayed` — the server answers HTTP, but the domain stream is reconnecting or the snapshot has not arrived yet.
  - `unreachable` — the server does not answer HTTP (network error, timeout, or a non-JSON proxy error page).
  - `restarting` — a planned restart is in progress (`dashboardLifecycle.active`, from `selectDashboardLifecycle` in the store).
- **Reachable** — a probe got a response whose body is JSON carrying a string `status` field, at any HTTP status. `/api/health` returns 503 with JSON in its "incoherent" states (`src/dashboard/server/health-response.ts`, `buildDashboardHealthResponse`) — that still means the server is up. A network error, a timeout (3 s), or a response whose body is not such JSON (Traefik 502/503/504 HTML) is **unreachable**.
- **Degraded mode** — any phase other than `live`. The last-known UI stays mounted, visible and navigable.
- **Degraded-mode banner** — the new `DegradedModeBanner` component (WI-3). The only outage indicator in the app shell.
- **First-load screen** — the only full-page outage state: shown when the tab has no snapshot at all (no localStorage cache, no successful bootstrap) and the phase is `unreachable` or `restarting`.
- **Held message** — a composer prompt submitted while the phase is `unreachable` or `restarting`. It is not POSTed; it waits in the composer outbox and is sent when the phase returns to `live` (WI-7).
- **Write action** — an issue action whose registry entry has `endpoint !== null` (`src/dashboard/frontend/src/lib/issueActions.ts`, `ISSUE_ACTION_DEFINITIONS`).
- **showOverlay** — the raw-DOM full-screen modal in `src/dashboard/frontend/src/recovery.tsx` (`export function showOverlay`, line 124). Framework-free so it works when React is dead.
- **Bootstrap** — `EventRouter`'s `getSnapshot` RPC plus replay (`src/dashboard/frontend/src/components/EventRouter.tsx`, `function bootstrap(): Promise<boolean>`, line 183).

## Problem

When the dashboard loses touch with its server — briefly or falsely — the UI blocks, and the app has several different outage screens. On 2026-09-27 ~23:30 UTC (build `b1d33b80407`) a modal "Server unreachable — Retry" overlay covered a conversation while the server was healthy: `/api/health` answered 200, `supervisor.log` shows no restart since 07:32 UTC, and `dashboard.log` shows `getSnapshot resolved in 4–6ms` for every call.

### Root cause of the 23:30 false alarm (what the code proves)

`EventRouter.bootstrap()` awaits `getTransport().request(... getSnapshot ...)` with **no timeout**, and `WsTransport.request` first awaits `clientPromise`, which awaits `ensureDashboardSession()` — a `fetch` with **no timeout** (`lib/wsTransport.ts:71-91`). If either never settles:

1. `bootstrapPromise` stays pinned and `bootstrapInFlight` stays `true` forever.
2. `reconnectDomainStream()` returns immediately (`if (bootstrapInFlight) return`, line 123), and so does `scheduleReconnectDomainStream()` (line 143). **The overlay's Retry button calls `reconnectDomainStream()`, so Retry is a no-op in exactly the state the overlay appears in.**
3. The fallback poller re-calls `bootstrap()`, which returns the same pinned promise, and after 3 minutes it stops permanently and shows the overlay (line 93-98).
4. Separately, `onRetry` shows the same overlay after 6 subscription retries (line 338) without checking whether HTTP answers.

Server logs rule out a slow snapshot server-side. **Implementation checkpoint (WI-2):** the work agent writes the fake-timer test "getSnapshot never resolves" first; it must reproduce (overlay after 3 min, Retry issues no new `getSnapshot`) on the unmodified code. If it does not reproduce, record that in the PR and still ship the fixes below — each closes a code-provable failure mode. Do not attempt to replay the live incident.

## Requirements

### Functional

- **FR-1** A connection store derives one phase (`live` / `delayed` / `unreachable` / `restarting`) from: the HTTP reachability poll, on-demand `/api/health` probes, the EventRouter stream state, and `dashboardLifecycle.active`.
- **FR-2** No code path hides mounted app content for an outage (`display: none`, unmount, or a modal overlay) while a snapshot exists.
- **FR-3** Exactly one banner component renders every outage state in the app shell, with copy per phase (see WI-3) and a "showing data from HH:MM" freshness stamp.
- **FR-4** A full-page screen renders only when the tab has no snapshot (no cache, no bootstrap) and the phase is `unreachable` or `restarting`.
- **FR-5** Before showing `unreachable`, the app probes `/api/health`; if the server is reachable the phase is `delayed` ("Live updates are delayed — reconnecting"), never `unreachable`.
- **FR-6** EventRouter bootstrap is bounded by a timeout, retries with backoff forever (no give-up window), and the banner's Retry always starts a fresh attempt, even while an older attempt is in flight.
- **FR-7** Both EventRouter `showOverlay` call sites are deleted; EventRouter no longer imports `showOverlay`/`hideOverlay`.
- **FR-8** Write actions in the issue-action surfaces are disabled while the phase is `unreachable` or `restarting`, stay visible, and carry the explanation "Can't reach the Overdeck server — available again when it reconnects."
- **FR-9** A composer prompt submitted while `unreachable` or `restarting` is held (not POSTed), shown in the outbox as "Waiting to send — will send when the server reconnects", and sent automatically once the phase returns to `live`.
- **FR-10** The asset-recovery overlay (`waitForServerThenReload`) shows its modal only for the `root_error_boundary` trigger.
- **FR-11** `docs/DASHBOARD-ARCHITECTURE.md` has a "Degraded mode" section describing the phases, the banner copy, the reachability rule, the first-load rule, held messages, and the audit dispositions.

## Decisions

- **D1 — Reachability sources.** The App's existing 5 s `/api/version` poll (`fetchBackendHealth`, `App/api.ts:40`, which also caches `supervisorUrl` for Force Restart) stays and feeds `serverReachable` into the connection store (2 consecutive failures ⇒ unreachable, one success ⇒ reachable — the existing threshold). EventRouter additionally calls `probeServerHealth()` (`GET /api/health`, 3 s timeout, reachability rule from the glossary) on every stream failure / staleness strike / bootstrap failure, and writes the result into the store immediately. Either source reporting reachable clears `unreachable`.
- **D2 — Phase precedence.** `restarting` > `unreachable` > `delayed` > `live`. `delayed` = reachable and `streamLive === false`. `streamLive` becomes `true` on a successful bootstrap and `false` when EventRouter marks reconnecting or a bootstrap fails/times out.
- **D3 — Freshness stamp.** `lastLiveAt` (epoch ms) = time of the last successful bootstrap or applied domain event batch; before any bootstrap it is the localStorage cache entry's `timestamp`. `snapshotCache.ts` gains `loadSnapshotCacheEntry(): { data, timestamp } | null`; `loadSnapshotFromCache` stays as a thin wrapper so the store's save path is untouched. Format: `HH:MM` via `toLocaleTimeString([], { hour: '2-digit', minute: '2-digit' })`.
- **D4 — Bootstrap timeout 20 s** (`BOOTSTRAP_TIMEOUT_MS = 20_000`). A timed-out attempt counts as a failure: clears `bootstrapPromise`/`bootstrapInFlight`, sets `streamLive=false`, probes health, and schedules a reconnect with the existing `eventRouterReconnectDelayMs` backoff (2 s doubling, cap 30 s, ±20 % jitter). A generation counter makes a late resolution of a superseded attempt a no-op (it must not call `syncSnapshot`).
- **D5 — No give-up window.** `SNAPSHOT_FALLBACK_WINDOW_MS` and `UNREACHABLE_OVERLAY_RETRY_ATTEMPTS` are deleted. The 2 s fallback poller keeps running until the first bootstrap succeeds, then stops (as today); after that, recovery is backoff-driven.
- **D6 — Retry.** The banner's Retry calls `requestReconnect()` on the connection store, which EventRouter registers on mount. It bumps the generation (abandoning any in-flight attempt), resets the backoff attempt counter, and runs a full-reset `reconnectDomainStream`, plus `queryClient.refetchQueries({ queryKey: ['backend-health'] })`.
- **D7 — Keep the refetch-on-recovery behavior.** `BackendConnectionBoundary`'s `invalidateQueries()` on the transition out of an outage (PAN-3867 comment, line 35-45) is kept, keyed on the phase leaving `unreachable`/`restarting`.
- **D8 — `backendOutageState.ts` is deleted.** Its seven `isBackendOutage()` guards exist only because the page was hidden (PAN-3867). Once nothing hides mounted pages they are permanently false; the `ComposerFooter` guard would also conflict with held messages and the `PipelineView`/`GodViewConfluence` guards would block navigation shortcuts on cached pages. Delete the module, every guard, and the reset in `test-setup.ts`. The menu-close-on-outage behavior (`useMenuOpen.getState().setOpenMenu(null)`) is also dropped: menus stay usable because the page stays visible.
- **D9 — Disabled-but-visible actions.** `IssueActionView` gains `blockedOffline: boolean` = `action.enabledWhen(state) && action.endpoint !== null && writeBlocked`. `enabled` = `enabledWhen && !blockedOffline`; `disabledReason` = the offline explanation when `blockedOffline`. `layout.rest` filters on `view.enabled || view.blockedOffline`, so offline-blocked actions stay in secondary/overflow, rendered disabled with the reason as tooltip. Only issue-action registry surfaces are gated; ad-hoc mutations elsewhere keep failing with their existing error toasts.
- **D10 — `writeBlocked`** = phase is `unreachable` or `restarting`. `delayed` does not block writes (HTTP works).
- **D11 — Held messages.** `ComposerFooter.handleSubmit` checks `isServerWriteBlocked()` before POSTing. Prompts are held via a new `holdSend(conversationName, text, { clientMessageId, deliverAs })` store action that appends a `FailedMessage` with `heldOffline: true`, `retryable: true`, no `error`; the editor is cleared and uploaded attachments consumed exactly as on a successful send. `/pan` portable commands are **not** held: they show the toast "Can't reach the Overdeck server — commands need a live connection" and keep the draft.
- **D12 — Flushing held messages.** `useComposerDeliveryState` gets an effect: when the phase is `live` and the conversation has held entries, send them one at a time in `createdAt` order via `retryFailed(...)`. `retryFailed` treats `heldOffline` like a never-sent message: it keeps the entry's `clientMessageId`, uses a fresh `createdAt`, and omits `retry: true`. Held messages for a conversation that is not mounted at reconnect are sent when its panel next mounts while `live`. Held messages live in the in-memory composer store like the existing failed outbox; a full page reload drops them (NonGoal). Drafts already persist in localStorage (`composerStore.ts` header comment), so "drafts are never lost" needs no new code.
- **D13 — Terminal.** No change to `XTerminal.tsx`; the plan only asserts its inline states still render (WI-8 browser test).
- **D14 — Asset recovery.** `waitForServerThenReload` shows the "Reconnecting to the dashboard…" modal only when `details.trigger === 'root_error_boundary'`. For `vite_preload_error`, `asset_load_error`, `window_module_error`, `unhandled_rejection` it polls `/` silently (the degraded banner already reflects server state via the health poll) and then reloads. The circuit-breaker overlay stays for all triggers.
- **D15 — Size.** One plan, not sibling issues: the issue's acceptance criteria bind the banner, offline send, disabled actions and the browser suite together, and splitting would ship a banner that promises behavior another issue delivers. Recorded as `plan.metadata.sizeJustification`.

## Repo rules restated

- Fake timers for every retry/backoff/timeout test (`vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()`); never real waits; never `maxForks: 1`.
- Quality gates: `npm run typecheck`, `npm run lint`, `npx vitest run <touched test files>`. Never run the full `npm test` on the host.
- Dashboard runs Node 22 from `dist/` only; `npm run build` before the Playwright suite.
- Frontend style: `pan-style-guide` (no pill badges, no decorative color; "running is not green").
- Never `git stash`; never `git checkout` inside the workspace.
- New frontend tests must be listed in `test:frontend-subset`.
- File-size ratchet is derived at lint time against `origin/main`; growth of an over-1000-line file needs an allowlist row with `# PAN-4279`.

## Non-goals

- No server-side changes (health route, RPC, snapshot).
- No persistence of held messages across a full page reload.
- No offline queueing of issue actions or any non-composer mutation — they are disabled, not queued.
- No change to `XTerminal.tsx`, `RootErrorBoundary`, or the reload circuit breaker.
- No change to region-level boundaries (`LoadingBoundary`, `ProjectMembershipBoundary`, Flywheel unreachable chip).
- No gating of non-registry mutations (settings saves, etc.); they keep failing with their existing toasts.
