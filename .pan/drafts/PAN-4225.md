# PAN-4225 — Per-issue continue/spec writers target the issue workspace, not the primary checkout

**Issue:** [PAN-4225](https://github.com/eltmon/overdeck/issues/4225) (split out of PAN-4224, closed).
**Status:** PRD for `pan plan --auto`. Verified against `feature/pan-4225` at `bea5bdbf1d2` on 2026-09-28.

## Glossary

- **Primary checkout** — the operator's clone of the project repo on `main` (for Overdeck: `/home/eltmon/Projects/overdeck`). Shared by every session. Anything written here and not committed blocks `git pull`/`reset --keep` when a merged PR adds the same path (PAN-4224).
- **Base workspace** — the issue's git worktree at `<project>/workspaces/feature-<issue-lowercase>/`, on branch `feature/<issue-lowercase>`. Swarm slot workspaces (`workspaces/feature-<issue>-slot-<n>`, see `src/lib/workspaces/shapes.ts` `resolveIssueWorkspaceDirs`) and strike workspaces are *separate* sibling checkouts, not the base workspace.
- **Plan home** — the checkout that holds `.pan/` for a path: `resolvePlanHome(p)` (`src/lib/pan-dir/paths.ts:46`). For a path inside `<project>/workspaces/<name>/` it is that workspace (or its `pan_records.repo` sub-repo for polyrepo projects); otherwise the primary checkout. It is idempotent: `resolvePlanHome(resolvePlanHome(p)) === resolvePlanHome(p)`.
- **Workspace plan home** — `resolvePlanHome(<base workspace>)`.
- **Continue file** — `<planHome>/.pan/continues/<ISSUE>.xbrief.json` (`continueStatePath`, `src/lib/xbrief/continue-state.ts:203`). Holds item statuses (which gate `pan done`), decisions, hazards, `sessionHistory[]`, `feedback[]`.
- **Spec** — `<planHome>/.pan/specs/<date>-<ISSUE>-<slug>.xbrief.json`. Its top-level `status` is the lifecycle (`proposed|active|completed|cancelled`); `plan.status` is the plan status.
- **Slot ledger** — `<planHome>/.pan/continues/<ISSUE>.slots.json` (`swarmSlotStatePath`, `src/lib/cloister/swarm-slot-store.ts:93`), the foreman/deacon swarm runtime ledger.
- **Server-dirtied file** — a tracked `.pan/` file the dashboard server (or a CLI verb other than the work agent) modified in the base workspace without committing.
- **Agent commit point** — a moment where the work agent's own process commits `.pan/` artifacts on its feature branch: `pan task claim|done` (`commitContinue`, `src/cli/commands/task.ts:78`) and, after this change, `pan done` before its rebase.

## Problem

`resolvePlanHome(p)` returns the workspace only when `p` is inside `<project>/workspaces/<name>/`. These writers pass the project root, so they write into the primary checkout and never commit:

| Writer | Location | Root passed |
|---|---|---|
| `clearFeedbackFiles` → `clearFeedbackForIssue` (every review dispatch, `review-agent.ts:459`) | `src/lib/cloister/feedback-writer.ts:67` (`const projectRoot = join(workspacePath, '..', '..');`) | project root |
| `writeFeedbackFile` → `appendFeedbackEntryForIssue` / `appendContinueSessionEntryForIssue` | `src/lib/cloister/feedback-writer.ts:103` (`const projectRoot = resolved?.projectPath ?? …`) | project root |
| `appendContinueSessionEntryForIssue` on plan restart / reopen / resume | `src/lib/overdeck/planning-sessions.ts:750`, `src/lib/reopen.ts:52`, `src/lib/agents/resume.ts:301` | project root |
| `transitionXBriefOnMain` | `src/lib/lifecycle/workflows.ts:576` (close-out), `src/dashboard/server/routes/agents/spawn.ts:614` (dashboard start), `src/cli/commands/start-status.ts:6` (CLI start), `src/lib/overdeck/issue-transitions.ts:202` (cancel), `src/cli/commands/scope.ts:392-449` (`pan scope`) | project root; never commits (`src/lib/xbrief/lifecycle-io.ts:275`: `// PAN-3917: the caller's agent commits the spec on its feature branch, so a`) |
| slot ledger | `src/lib/cloister/swarm-slot-store.ts:94` (`const planHome = resolvePlanHome(resolve(workspacePath, '..', '..'));`) | project root |

All four continue adapters in `lifecycle-io.ts` (`readContinueStateForIssue:303`, `appendContinueSessionEntryForIssue:310`, `appendFeedbackEntryForIssue:330`, `clearFeedbackForIssue:343`) call `resolvePlanHome(projectRoot)`, so every caller that hands them a project root lands in the primary checkout.

Readers are split the same way: `src/lib/cloister/handoff-context.ts:124` and `src/lib/cloister/test-skip-waiver.ts:47` and `src/dashboard/server/routes/workspaces.ts:185` read `resolvePlanHome(project.path)` (primary), while `pan task` (`src/cli/commands/task.ts:58`) and `pan done` (`src/cli/commands/done.ts:259`) write in the workspace.

Evidence (primary checkout, 2026-09-28 `git status --porcelain -- .pan`): eight tracked specs modified (`M .pan/specs/2026-09-28-PAN-4290-…` etc.) and untracked `?? .pan/continues/PAN-1166.xbrief.json`, `PAN-3684`, `PAN-3956`, `PAN-4311`. The issue also records a 247-byte `PAN-4198.xbrief.json` stub (`feedback: []`), which is what `clearFeedbackForIssue` creates through `updateContinueState`'s create-when-absent path.

A second, related defect: `updateContinueState` (`continue-state.ts:236`) treats an unparseable file as absent (`readContinueState` returns `null` on any parse error, `continue-state.ts:207-213`) and overwrites it with `emptyState`, wiping `items`. `writeContinueState` (`continue-state.ts:229`) is a bare `writeFileSync`, so a concurrent reader can see a half-written file. Today the server and `pan task` write different files; after this change they write the same workspace continue file, so this becomes a live data-loss path (a lost `items` map makes `pan done` refuse). The issue's unverified claim that tracked `PAN-4197.xbrief.json` lost its items fits this path.

## Decisions

- **D1 — One write location.** Per-issue continue and spec state is written to the **workspace plan home of the base workspace**: `resolvePlanHome(join(<projectRoot>, 'workspaces', 'feature-' + issue.toLowerCase()))`. Slot and strike workspaces never own it.
- **D2 — No workspace ⇒ no write.** When the base workspace directory does not exist, a writer skips and logs one line. It never falls back to the primary checkout. (Exception: the operator-invoked `pan scope` verbs, D6.)
- **D3 — The server never commits in a workspace.** Both start paths flip status *after* the agent is spawned (`start.ts:1203` spawns, `start.ts:1225` transitions; dashboard `markWorkStartAccepted` runs after acceptance) and every feedback write happens while the agent is live. A server `git commit` there races the agent's `index.lock` and moves HEAD under sha-pinned gates. Server writes stay uncommitted; the agent commit points commit them.
- **D4 — `pan done` commits pending per-issue artifacts before rebasing.** `rebaseAndPushRepos` (`src/lib/rebase-helper.ts:156`, `git rebase origin/${targetBranch}`) refuses when a tracked file is modified, so a server-dirtied continue file would break `pan done`. `pan done` commits `.pan/continues` and `.pan/specs` in the workspace plan home first (same shape as `recordTestWaiver`, `done.ts:256-271`). "nothing to commit" is success.
- **D5 — Close-out does not write the spec.** Completion is derivable from the merged PR and closed issue ("Overdeck stores no status it can derive"). Verified no reader gates on a spec's `completed` status: `grep -rn "'completed'" src/lib/pan-dir src/lib/backlog src/lib/pipeline-membership.ts src/lib/overdeck/derived-issue-state.ts` finds only the type union and a tracker-state mapper; `autonomous-work-dispatch.ts:90` (`isPlannedState`) is only asked about open, labelled tracker issues. Committing on main per close-out would add a main commit per issue and more primary-checkout churn — the thing this issue removes. `completeXBriefStep` returns `stepSkipped` with a stated reason. Operator-visible consequence: a merged issue's spec on main stays `active`, so `pan scope restore <merged-issue>` (`scope.ts:437-441`, guard "restore only works from completed/ or cancelled/") refuses it. That is correct — the spec already reads as active — and the docs say so; restore's guard is not changed.
- **D6 — `pan scope` verbs are explicit operator actions.** They write the workspace plan home when the base workspace exists (uncommitted, D3). Otherwise they write the primary plan home **and** commit (`commitPlanArtifacts`) **and** push (`pushPlanArtifacts`), exactly like the `pan orders` write verbs (`src/cli/commands/orders.ts:72-79`).
- **D7 — Cancel follows D1/D2.** `issue-transitions.ts` cancel writes the workspace spec when the base workspace still exists, else skips.
- **D8 — Readers read workspace first, then primary.** A merged or closed issue's continue file lives on main in the primary checkout, so readers fall back to it (the pattern already in `scope.ts:360-361`).
- **D9 — `transitionXBriefOnMain` is renamed `transitionIssueXBrief(planHome, issueId, targetDir, newStatus)`.** The old name and header claim it commits on main; it never has. The unused `commitMessage` parameter and the always-false `committed` result field are removed. Callers pass an already-resolved plan home, so routing is explicit at each call site.
- **D10 — Continue writes are atomic and never overwrite an unreadable file.** `writeContinueState` writes `<path>.tmp` then `renameSync`. `updateContinueState` throws `ContinueStateUnreadableError` when the file exists but does not parse; it creates a new file only when the file is absent. No cross-process lock (`src/lib/pan-dir/fs-lock.ts` is async-only and per-record; `updateContinueState` is sync). The residual lost-update window between two sync read-modify-writes is recorded as a hazard.
- **D11 — Slot ledger keeps its filename, moves to the base workspace plan home.** Computing it from the caller's path would split the ledger per slot workspace.
- **D12 — Clearing feedback never creates a file.** `clearFeedbackForIssue` is a no-op when the continue file is absent.

## Requirements

- **FR-1** The continue adapters (`appendContinueSessionEntryForIssue`, `appendFeedbackEntryForIssue`, `clearFeedbackForIssue`) write to the base workspace plan home and return `true`; with no base workspace they write nothing and return `false`.
- **FR-2** `readContinueStateForIssue` returns the workspace plan home's continue state when present, else the primary plan home's, else `null`.
- **FR-3** `clearFeedbackForIssue` never creates a continue file.
- **FR-4** `writeContinueState` is atomic (tmp + rename); `updateContinueState` refuses to overwrite an existing unparseable continue file.
- **FR-5** `writeFeedbackFile` and `clearFeedbackFiles` leave the primary checkout's `.pan/` untouched.
- **FR-6** `reopenWorkspaceState` reports `continueFileUpdated: false` when the base workspace is gone.
- **FR-7** `transitionIssueXBrief` writes only under the plan home it is given and performs no git operation.
- **FR-8** CLI and dashboard start transitions write the base workspace's spec, or skip when it is absent.
- **FR-9** Close-out writes no spec and reports the step as skipped with a reason.
- **FR-10** Cancel writes the base workspace's spec, or skips when it is absent.
- **FR-11** `pan scope propose|approve|complete|cancel|restore` write the workspace spec uncommitted when the base workspace exists; otherwise write, commit, and push on the primary plan home.
- **FR-12** `pan done` commits pending `.pan/continues` and `.pan/specs` changes in the workspace plan home before its rebase; other dirty paths are not staged.
- **FR-13** `handoff-context`, `test-skip-waiver`, and `GET /api/workspaces/:issueId/state-md` read continue state via FR-2.
- **FR-14** The slot ledger path resolves to the base workspace plan home for any caller path (base, slot, or nested).
- **FR-15** Docs state where per-issue continue/spec state is written and who commits it.
- **NFR-1** No `execSync`/sync child-process calls in server-reachable code (dashboard rule). All new git calls use `commitPlanArtifacts`/`pushPlanArtifacts` (async `execFile`).
- **NFR-2** Tests use temp directories (`mkdtempSync`) and temp git repos; no test reads source files (the lint gate rejects source-grep tests) and none adds `skipIf`/`.only`.
- **NFR-3** Files over 1000 lines (`src/dashboard/server/routes/workspaces.ts` 1358, `src/lib/lifecycle/workflows.ts` 1160) must not grow past their `origin/main` count; if unavoidable, add `<lines> <path> # PAN-4225` to `scripts/file-size-allowlist.txt` in the same commit.

```ts
export class ContinueStateUnreadableError extends Error {
  constructor(public readonly path: string, cause: unknown) {
    super(`The continue file ${path} exists but is not valid JSON (${cause instanceof Error ? cause.message : String(cause)}). Fix or restore it; Overdeck will not overwrite it.`);
    this.name = 'ContinueStateUnreadableError';
  }
}

export function writeContinueState(planHome: string, issueId: string, state: ContinueState): void {
  const path = continueStatePath(planHome, issueId);
  mkdirSync(dirname(path), { recursive: true });
  const tmp = `${path}.${process.pid}.tmp`;
  writeFileSync(tmp, `${JSON.stringify({ ...state, updated: new Date().toISOString() }, null, 2)}\n`, 'utf-8');
  renameSync(tmp, path);
}
```

```ts
/**
 * Server-side writers leave the issue's continue file and spec modified but
 * uncommitted in the workspace (PAN-4225 D3). Commit them on the feature
 * branch before the rebase, which refuses a dirty tracked file.
 */
export async function commitPendingIssueArtifacts(workspacePath: string, issueId: string): Promise<void> {
  const planHome = resolvePlanHome(workspacePath);
  // `git add` fails on a pathspec that matches nothing, so pass only paths that exist.
  const paths = [join('.pan', 'continues'), join('.pan', 'specs')].filter((p) => existsSync(join(planHome, p)));
  if (paths.length === 0) return;
  const result = await commitPlanArtifacts({ cwd: planHome, paths, message: planArtifactCommitMessage(issueId) });
  if (!result.committed && result.reason !== 'nothing to commit') {
    throw new Error(`Could not commit pending plan artifacts for ${issueId}: ${result.reason}`);
  }
}
```
