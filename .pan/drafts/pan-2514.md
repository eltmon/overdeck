# PAN-2514 — Claude Code Traffic Inspector

**Issue:** [PAN-2514](https://github.com/eltmon/overdeck/issues/2514)
**Mockup:** [`docs/design/mockups/pan-2514-traffic-inspector.html`](../../docs/design/mockups/pan-2514-traffic-inspector.html)
**Status:** draft
**Author model:** claude-opus-4-8

A new **Observability → Traffic** dashboard page that passively intercepts the
model API traffic our Claude Code agents send, and renders each request as
inspectable, collapsible blocks — system prompt, tool schemas ranked by byte
size, message history, response, and token usage. Inspired by Matt Pocock's
[`agent-proxy`](https://gist.github.com/mattpocock/5b3d76ea21f5f698aefded47a9cea3b1),
but built into the dashboard and driven by the per-model endpoint routing we
already have.

---

## Glossary

Define-before-use. Every term of art this document relies on:

- **Claude Code harness** — the `claude` CLI agent loop. Overdeck's default
  harness. This PRD's V1 scope is Claude Code only (not Pi/ohmypi, not Codex).
- **Anthropic protocol / `/v1/messages`** — the HTTP request shape Claude Code
  sends to a model endpoint: a JSON body with `system`, `tools`, `messages`,
  `model`, and a streamed Server-Sent-Events (SSE) response carrying content
  blocks and a final `usage` object.
- **`ANTHROPIC_BASE_URL`** — the env var Claude Code reads to decide *where* to
  send `/v1/messages`. Overdeck already rewrites this per model.
- **Upstream** — the real endpoint a request must ultimately reach:
  `api.anthropic.com` for native Claude, the CLIProxy sidecar
  (`http://127.0.0.1:8317`) for GPT/Gemini, or a provider's Anthropic-compatible
  URL (minimax/zai/mimo/kimi/openrouter/xai/nous/dashscope).
- **CLIProxy** — the existing Go sidecar on port 8317 that translates the
  Anthropic protocol to the OpenAI Responses transport for ChatGPT-subscription
  (Codex) auth. Managed by `src/lib/cliproxy.ts`.
- **Capture proxy** — the NEW sidecar this PRD adds: a small Node HTTP reverse
  proxy that logs `/v1/messages` traffic and forwards it untouched upstream.
- **Capture** — the master on/off feature. When ON, newly-spawned Claude Code
  agents route through the capture proxy.
- **Provider env chain** — the code that resolves a model to its endpoint env:
  `getProviderForModelSync` → `getProviderEnvSync` / `getCliproxyClientEnv` →
  `getProviderEnvForModel` → `getProviderExportsForModel` (launcher scripts) and
  `buildSpawnEnvForModel` (programmatic spawns).
- **Domain event / event bus** — the dashboard's server→frontend push channel
  (`subscribeDomainEvents` RPC over `/ws/rpc`, backed by `EventStore`).
- **`emitOnly`** — an `EventStore` method that fans an event to live subscribers
  **without** persisting it to SQLite; used for high-frequency/large events.
- **`app_settings`** — the key/value settings table in `overdeck.db`, read/written
  via `getSetting`/`setSetting`.
- **Tool byte ranking** — the gist's headline view: each tool schema in a
  request measured by serialized byte size and ranked largest-first, so you can
  see which tool definitions consume the context window.

## Motivation

`agent-proxy` answers a question we ask constantly: *what is actually in this
model call, and what's eating the context window?* — e.g. "69 tools · 154,946
tool bytes · 65,538 real input tokens", ranked by size. The gist requires
manually prefixing `ANTHROPIC_BASE_URL=… claude`. **We don't need to** — Overdeck
already sets that env var per model at launch, through a single code chain. We
can splice a logging proxy into that chain and render the traffic far better than
a terminal table: expand/collapse per section and per tool call, filter by agent
/ model / tool, live streaming.

---

## Goals

- Passive, transparent interception of Claude Code model traffic. Forwarding is
  byte-for-byte untouched; the proxy never alters requests or responses.
- A dashboard page that makes context spend legible: which tools are the hog,
  the full message history, real token usage.
- Reuse existing machinery (provider env chain, event bus, sidecar lifecycle
  pattern) — minimal new surface.

## Non-goals (V1)

- **Pi/ohmypi and Codex harnesses.** Pi uses an `rpc.in` FIFO transport; Codex
  uses the OpenAI Responses transport directly. Neither is an Anthropic
  `/v1/messages` proxy. Out of scope; the page states this.
- Editing/replaying/mutating requests. Read-only observation only.
- Cross-machine capture. Local only.
- Retroactive capture of already-running agents (env is fixed at launch).

## Requirements

### Functional

- **FR-1** A master **Capture** toggle persists across restarts and affects only
  **newly-spawned** Claude Code agents. Already-running agents keep their
  launch-time endpoint. The UI states this explicitly.
- **FR-2** When capture is ON, a logging reverse-proxy receives each Claude Code
  `/v1/messages` request, forwards it **untouched** to the correct upstream,
  streams the response back unmodified, and records a capture (request + response
  + usage) with **auth headers redacted**.
- **FR-3** Capture covers every Claude Code provider route that already sets an
  `ANTHROPIC_BASE_URL` (CLIProxy/GPT, Gemini, kimi, and static providers
  minimax/zai/mimo/openrouter/xai/nous/dashscope).
- **FR-4** Capture covers native Anthropic (Claude) models by injecting an
  `ANTHROPIC_BASE_URL` that today is absent for that branch. *(Carries a
  subscription-auth implementation checkpoint — see Work Item 4.)*
- **FR-5** A new **Observability → Traffic** page lists captured requests with
  filters: agent/session, model, tool type, direction (request/response), and
  free-text search.
- **FR-6** Each request renders as collapsible blocks: **System prompt**
  (byte/token count), **Tools** (every schema ranked by byte size with a size
  bar), **Messages** (history; `tool_use` and `tool_result` individually
  collapsible), **Response**, **Usage** (input/output/cache tokens).
- **FR-7** Capture summaries stream live to the page; the full request/response
  body is fetched on demand when a request is expanded.
- **FR-8** The capture proxy has a lifecycle mirroring CLIProxy: start/stop,
  status route, watchdog auto-restart, and a `pan restart` scope.

### Non-functional

- **NFR-1** Forwarding latency overhead is negligible; capture logging is
  fire-and-forget and never blocks the forward path or the dashboard event loop.
- **NFR-2** No `execSync` in server-reachable code. The sidecar is spawned with
  async `spawn` (detached, unref'd), mirroring `startCliproxyTask`.
- **NFR-3** Auth secrets (`Authorization`, `x-api-key`, `anthropic-*` tokens) are
  never persisted to disk or the event bus, and never displayed.
- **NFR-4** Bounded memory: the capture store is a bounded ring buffer (default
  200 requests); summary events use `emitOnly` (no SQLite persistence), matching
  the `issues.snapshot` precedent.
- **NFR-5** The capture proxy start is a boot-path change → runtime-boot-tested
  before it runs on the live server; restart uses `--health-timeout` ≥ 120s.

## Architecture

### Where the traffic is intercepted

Overdeck already funnels **every** Claude Code launch through the provider env
chain. Verified call graph (line numbers checked against the working tree):

```
getProviderForModelSync(model)              src/lib/providers.ts:309
  → getProviderEnvSync(provider, apiKey)    src/lib/providers.ts:391   (static providers, kimi)
  → getCliproxyClientEnv()                  src/lib/cliproxy.ts:666     (GPT/Gemini → CLIProxy)
getProviderEnvForModel(model)               src/lib/agents/provider-env.ts:26   ← the one dispatcher
  → getProviderExportsForModel(model)       src/lib/agents/provider-env.ts:120  → launcher scripts
  → buildSpawnEnvForModel(model, baseEnv)   src/lib/agents/provider-env.ts:144  → programmatic spawns
```

`getProviderEnvForModel` returns a `Record<string,string>` of env vars. For
native Anthropic it returns `{}` (line 28); for everything else it sets
`ANTHROPIC_BASE_URL` (+ auth). Both exit surfaces — `getProviderExportsForModel`
(bash `export` lines for launcher scripts) and `buildSpawnEnvForModel`
(programmatic env) — call `getProviderEnvForModel` first. **Wrapping the env at
those two points is the entire splice.** The `pty-supervisor` passes env through
untouched (`env: process.env`), so no launcher/supervisor changes are needed.

### The redirect (design decision)

When capture is ON, the wrap rewrites `ANTHROPIC_BASE_URL` to point at the
capture proxy, and encodes the **real upstream** and **agent id** so the proxy
knows where to forward and how to label the capture. The rule:

| Original env (capture OFF) | Rewritten `ANTHROPIC_BASE_URL` (capture ON) | Upstream the proxy forwards to |
|---|---|---|
| `ANTHROPIC_BASE_URL` set (CLIProxy/provider) | `http://127.0.0.1:8318/<agentId>/<b64url(upstream)>` | the original base URL |
| absent (native Claude, `{}`) | `http://127.0.0.1:8318/<agentId>/<b64url(https://api.anthropic.com)>` | `https://api.anthropic.com` |

`<b64url(...)>` is base64url of the original upstream base URL. Auth env
(`ANTHROPIC_AUTH_TOKEN`) is left exactly as the chain produced it (or absent for
native Claude — Claude Code supplies its own credentials, which the proxy relays
untouched).

**Why path-prefix routing:** Claude Code appends `/v1/messages` to
`ANTHROPIC_BASE_URL`, so a base of `…/<agentId>/<b64url>` yields a request path of
`/<agentId>/<b64url>/v1/messages`. The proxy parses the two leading segments to
get the agent id + upstream, strips them, and forwards `<upstream>/v1/messages`.
This gives per-agent attribution with no dependency on custom headers.

> **Implementation checkpoint (IC-1):** verify Claude Code honors an
> `ANTHROPIC_BASE_URL` that contains a **path** (not just origin). Test:
> `ANTHROPIC_BASE_URL=http://127.0.0.1:8318/probe/aHR0... claude -p "hi"` and
> confirm the proxy receives `/probe/aHR0.../v1/messages`.
> **Fallback if the client trims the path to origin:** set the agent id + upstream
> via `ANTHROPIC_CUSTOM_HEADERS="x-overdeck-agent: <id>\nx-overdeck-upstream: <b64>"`
> (Claude Code header-injection env) and read them in the proxy.
> **Final fallback:** one proxy port per upstream (group captures by upstream +
> launch timing; lose exact per-agent id). Pick the first that passes; record the
> choice in the module header.

### Native-Claude capture caveat

Native Claude with **subscription (claude.ai) OAuth** may refuse a custom base
URL or send tokens scoped to `api.anthropic.com`. See Work Item 4's checkpoint.
Capture for base-URL providers (FR-3) is unaffected and is the safe majority
path; native-Claude capture (FR-4) degrades gracefully if subscription auth
rejects the redirect (documented limitation, capture simply skips native Claude).

### Streaming to the UI (design decision)

Captured bodies are large (full system prompt + 60+ tool schemas + message
history). Following the `issues.snapshot` precedent
(`src/dashboard/server/event-store.ts:48-53,157-160`):

- The proxy async-POSTs each capture to a dashboard **ingest** route. The server
  stores the full body in a bounded in-memory ring buffer keyed by a capture id,
  computes the tool byte ranking, and `emitOnly`s a **lightweight summary** event
  (`traffic.captured`: id, agent, model, role, timestamp, token counts, top-N
  tool byte sizes, block counts) onto the bus.
- `EventRouter` receives the summary and updates the store; the page lists it.
- Expanding a request issues `GET /api/traffic/:id` to fetch the full stored
  body on demand.

This keeps the bus and SQLite log clean, decouples proxy throughput from the
dashboard event loop, and caps memory (NFR-4).

### Settings persistence (design decision)

The toggle is read on the launch hot path by `provider-env.ts` (lib-level, runs
in both CLI and server contexts), so it uses the `app_settings` KV store —
readable directly without the dashboard's Effect/DB-worker indirection:

- Key `traffic.capture_enabled` via `getSetting`/`setSetting`
  (`src/lib/overdeck/control-settings.ts:395,403`).
- `provider-env.ts` reads `getSetting('traffic.capture_enabled') === 'true'`.
- The page toggles it via `PUT /api/traffic/capture`.

### WI-2 — Capture proxy sidecar + lifecycle · traces FR-2, FR-8, NFR-1, NFR-2, NFR-5

**New file:** `src/lib/traffic-proxy.ts`, mirroring the CLIProxy triad
(`src/lib/cliproxy.ts`).

**Constants** (mirror cliproxy.ts:44-47):
```ts
export const TRAFFIC_PROXY_HOST = '127.0.0.1';
export const TRAFFIC_PROXY_PORT = 8318;
export const TRAFFIC_PROXY_BASE_URL = `http://${TRAFFIC_PROXY_HOST}:${TRAFFIC_PROXY_PORT}`;
```

**The proxy process** — a standalone Node script (built to
`dist/traffic-proxy.js`) that:
1. `http.createServer`, listens on 8318.
2. Parses the path `/<agentId>/<b64urlUpstream>/v1/messages`; base64url-decodes
   the upstream.
3. Streams the incoming request to `<upstream>/v1/messages` preserving method,
   body, and headers (including auth) — **untouched**.
4. Pipes the upstream response (SSE) straight back to the client — **untouched**.
5. In parallel, tees the request body and response stream into a capture buffer;
   on completion, **redacts** `authorization` / `x-api-key` / `anthropic-*` auth
   headers (NFR-3) and fire-and-forget POSTs the capture to the dashboard ingest
   route (WI-5). A logging failure never affects the forward (NFR-1).

**Lifecycle** (async, mirror `cliproxy.ts` names): `getTrafficProxyPidPath`,
`isTrafficProxyRunningTask`, `startTrafficProxyTask` (spawn detached + unref +
pidfile — mirror `startCliproxyTask` at cliproxy.ts:721, spawn at :740),
`stopTrafficProxyTask`, `restartTrafficProxyTask`. **No `execSync`** (NFR-2).

**Boot registration:** add to `startPostLaunchSidecars`
(`src/cli/up-sidecars.ts:11-45`, after the cliproxy block at :16-23) — start the
proxy only if `getSetting('traffic.capture_enabled') === 'true'`.

**Watchdog + status route:** mirror `startCliproxyWatchdog` /
`GET /api/cliproxy/status` (`src/dashboard/server/routes/cliproxy.ts:41,80`) with
`startTrafficProxyWatchdog` + `GET /api/traffic/status` in `routes/traffic.ts`.

**Restart scope:** add `'traffic-proxy'` to the scope enum
(`src/cli/commands/restart.ts:56`), a flag (`:46-48`), a case (`:242-248`), and
include it in `--full` (`:341-346`).

**Tests:** `tests/unit/lib/traffic-proxy.test.ts` — path parsing (agent id +
b64url upstream extraction), header redaction, that a logging-POST rejection does
not throw on the forward path. A `@slow` integration test forwards a request

### WI-3 — Splice the redirect into the provider env chain · traces FR-2, FR-3

**File:** `src/lib/agents/provider-env.ts`.

**New helper:**
```ts
import { getSetting } from '../overdeck/control-settings.js';
import { TRAFFIC_PROXY_BASE_URL } from '../traffic-proxy.js';

/** When capture is on, repoint ANTHROPIC_BASE_URL at the capture proxy,
 *  encoding the real upstream + agent id in the path. No-op otherwise. */
function applyTrafficCapture(model: string, env: Record<string, string>): Record<string, string> {
  if (getSetting('traffic.capture_enabled') !== 'true') return env;
  const agentId = process.env.OVERDECK_AGENT_ID ?? 'unknown';
  const upstream = env.ANTHROPIC_BASE_URL ?? 'https://api.anthropic.com';
  const b64 = Buffer.from(upstream).toString('base64url');
  return { ...env, ANTHROPIC_BASE_URL: `${TRAFFIC_PROXY_BASE_URL}/${agentId}/${b64}` };
}
```

**Before** (`getProviderExportsForModel`, provider-env.ts:120-131):
```ts

  const envVars = await getProviderEnvForModel(model);
  const unsetLines = PROVIDER_ENV_KEYS.map(key => `unset ${key}`);
  ...
```
**After:**
```ts
export async function getProviderExportsForModel(model: string): Promise<string> {
  const envVars = applyTrafficCapture(model, await getProviderEnvForModel(model));
  const unsetLines = PROVIDER_ENV_KEYS.map(key => `unset ${key}`);
  ...
```

**Before** (`buildSpawnEnvForModel`, provider-env.ts:154):
```ts
  const providerEnv = await getProviderEnvForModel(model);
```
**After:**

## Intersecting repo rules (restated for the executor)

- **No `execSync` in server-reachable code** — the sidecar spawns via async
  `spawn` (mirror `startCliproxyTask`); the watchdog uses `execAsync`. (NFR-2)
- **Dashboard server is Node 22 only** — the proxy is a separate Node process;
  build to `dist/` and run under Node 22, never Bun. Run `npm run build` before
  restarting after server changes.
- **Never hot-patch a boot-path change onto the live server** — the
  `startPostLaunchSidecars` addition is boot-path; runtime-boot-test on a
  throwaway instance; `pan restart --health-timeout` ≥ 120s. (NFR-5)
- **Fake timers for delay/watchdog tests** — the watchdog interval test uses
  `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync`, never real `setTimeout`.
- **Single source of truth / two doors** — read the toggle only via `getSetting`
  and captures only via the traffic-store service; no direct DB/filesystem reads
  for this state elsewhere.
- **No destructive/speculative HTTP** — ingest and status routes are GET/PUT of
  non-destructive state; no DELETE semantics introduced.
- **Style guide** — see WI-6 conformance bullet; reviewers grep the diff for
  `font-bold|font-semibold|Inter|rounded-full.*badge|slate-`.
