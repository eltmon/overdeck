# PAN-5394 — Admission tests assert after a fixed-count drive instead of waiting for the condition

**Issue:** [PAN-5394](https://github.com/eltmon/overdeck/issues/5394)
**Kind:** test-only flake fix. No production code changes.

## Glossary

- **Admission loop** — `acquireQualityGateAdmission` in `src/lib/cloister/quality-gate-admission.ts`. It writes a waiter ticket file, polls the queue, and admits a gate when a slot, CPU and memory allow it.
- **`onWaiting`** — the optional `QualityGateAdmissionDeps.onWaiting` callback. The loop calls it from `notifyWaiting` (source line 702, `deps.onWaiting?.(reason)`) only after `await persistTicket()`, a real filesystem write.
- **Report key / rate limit** — `notifyWaiting` reports the first reason, then a *changed* reason at most once per `QUALITY_GATE_WAIT_REPORT_MS`. The tests below inject a fixed clock, so after the first report no other reason is ever reported. The first call is therefore the only call that matters.
- **`drive(attempts, done?)`** — test helper at `tests/unit/lib/cloister/quality-gate-admission.test.ts` line 68. Each attempt yields 1 ms of real wall-clock time (`nativeSetTimeout(resolve, 1)`), one `realSetImmediate()`, then `vi.runOnlyPendingTimersAsync()`. It stops early when `done()` returns true. It never asserts.
- **`driveUntil(done)`** — line 80; `drive(100, done)` followed by `expect(done()).toBe(true)`.
- **Fixed-count drive** — `await drive(N)` with no `done` predicate. It allows roughly N ms of wall-clock time and then returns, whatever state the loop is in.
- **Positive assertion** — an assertion that something *has happened* (`toHaveBeenCalledWith`, `toHaveBeenCalledTimes(1)`, `mock.calls[0]![0]`, a file count that must reach a value). A **negative assertion** checks that something has *not* happened (`settled()` is false, no `owner.json`, `.not.toHaveBeenCalled()`).

## Problem

Main CI went red at `6a6e5f38220` (run 43753714635, job `test-shard (2/4)`). The test
`head-of-line fairness (PAN-5285) > re-reads the soft reserve every poll, so a lowered reserve unblocks a queued waiter`
failed on the first try and on its retry:

```
AssertionError: expected "vi.fn()" to be called with arguments: [ ObjectContaining{…} ]
Number of calls: 0
 ❯ tests/unit/lib/cloister/quality-gate-admission.test.ts:1053:25
```

The test runs `await drive(10)` (line 1050), then asserts that `onWaiting` was called (line 1053). Before the loop first calls `onWaiting`, it does real filesystem work on the libuv threadpool: it writes the waiter ticket, lists the queue directory, reads the footprint estimate, awaits the mocked config load, and writes the ticket again in `persistTicket()`. On a loaded CI runner that can take more than about 10 ms, so `onWaiting` has zero calls when the assertion runs. The negative `settled()` check at line 1052 passed, which fits: the waiter had not finished its first poll.

The planner ran the file pinned to one CPU core alongside three busy loops (`taskset -c 3`). It passed 48/48, so the flake depends on threadpool latency on CI rather than on CPU starvation alone. The CI evidence (zero calls, not settled) is enough to support the timing diagnosis.

The same fixed-count-then-positive-assertion shape appears at six other sites in the same file. They will flake the same way under the same load.

## Approach

At every site where a fixed-count drive is followed by a positive assertion, wait for the condition instead of a count:

```ts
await drive(200, () => onWaiting.mock.calls.length > 0)
```

`drive` already takes a `done` predicate. 200 attempts gives at least 200 ms of real time (twice the 100 attempts `driveUntil` uses), and the predicate returns on the first attempt where the condition holds, so fast hosts pay nothing extra. Fake timers stay on. No real delays are added.

`calls.length > 0` is the right predicate. A predicate that matched the exact asserted arguments would buy nothing: with a fixed clock the rate limit means the first reported reason is the only one, so if that reason is wrong the assertion fails either way. With `length > 0` it fails faster and with Vitest's full diff.

`drive(200, …)` is used rather than `driveUntil(…)` on purpose. `driveUntil` fails with `expected false to be true`. With `drive`, the `toHaveBeenCalledWith` that follows fails with the real diff of the arguments.

## Requirements

- **FR-1** — The soft-reserve test (`re-reads the soft reserve every poll, …`) waits for `onWaiting` to be called before it asserts on the call.
- **FR-2** — The two other fairness tests with a positive assertion after a fixed-count drive (`keeps FIFO when the waiter ahead would fit` and `admits an unfittable head alone once it is past the bound and the slots are empty`) wait for their callback before they assert.
- **FR-3** — The four memory-admission tests with a positive assertion after a fixed-count drive wait for their condition before they assert. The `toHaveBeenCalledTimes(1)` check in `waits on memory until MemAvailable recovers` runs only after the test has counted at least two more memory reads after the first report.
- **NFR-1** — Test-only change. No file under `src/` changes. The `drive`, `driveUntil` and `driveUntilResolved` helpers do not change.
- **NFR-2** — Fake timers stay on. No real `setTimeout` waits are added beyond what `drive` already does (repo rule *fake timers for retry/backoff/delay tests*: never add real delays, never mask with `maxForks: 1`).
- **NFR-3** — Every existing assertion stays. None is weakened, removed, or turned into `skipIf`/`.only` (the test-skip gate rejects added `skipIf`/`.only`).

### WI-3 — The four memory-admission tests wait for their condition (FR-3, NFR-1..3)

Same file, `describe('memory admission (PAN-5248)')`.

**Site C** — test `waits on memory until MemAvailable recovers` (line ~545). This test also asserts `toHaveBeenCalledTimes(1)`, which proves the loop does not report the same reason twice. That check only means something if more polls *completed* after the first report. A fixed `drive(10)` does not prove that: under the same threadpool latency, all ten attempts can pass while the next poll is still in flight. So the test counts memory reads. The `available` callback passed to `memDeps` runs once per poll (through `readPollMemory` → `readMemory(sampleMemory)`, source line ~709). After the first report, the test waits for two more reads: the second one starts only after the first later poll has finished its `notifyWaiting`. It asserts that count before it checks `onWaiting`.

Before:

```ts
    let available = 13 * GiB
    const onWaiting = vi.fn()
    const promise = acquireQualityGateAdmission(keyed, memDeps(rootDir, 1, () => available, { onWaiting }))
    const settled = settledFlag(promise)

    await drive(10)
    expect(settled()).toBe(false)
    expect(onWaiting).toHaveBeenCalledTimes(1)
```

After:

```ts
    let available = 13 * GiB
    let reads = 0
    const onWaiting = vi.fn()
    const promise = acquireQualityGateAdmission(keyed, memDeps(rootDir, 1, () => {
      reads++
      return available
    }, { onWaiting }))
    const settled = settledFlag(promise)

    await drive(200, () => onWaiting.mock.calls.length > 0)
    // Two more polls read memory after the first report, so toHaveBeenCalledTimes(1) proves no repeat report.
    const readsAtReport = reads
    await drive(200, () => reads >= readsAtReport + 2)
    expect(reads).toBeGreaterThanOrEqual(readsAtReport + 2)
    expect(settled()).toBe(false)
    expect(onWaiting).toHaveBeenCalledTimes(1)
```

The rest of the test (`toHaveBeenCalledWith({...})`, `available = 20 * GiB`, the resolve and release) does not change.

### WI-4 — Documentation

This change alters no documented surface. It edits one test file, and no doc, rule or user-facing page describes these tests or the `drive` helper. The repo rule this follows (fake timers, no real delays) is already documented in `sync-sources/rules/fake-timers-for-retry-tests.md` and `.overdeck/context/codebase/conventions.md`. ## Sites deliberately left unchanged

Each of these is a fixed-count drive followed only by negative assertions, or used only for ordering. A slow host makes them wait *less* far into the loop, so they cannot produce the zero-call failure this issue fixes. Do not change them.

One caveat: a slow host can make some of them *weaker*. For example, in `re-reads the estimate every poll, …` (line ~1025), `drive(10)` can finish before the first `readFootprintEstimate` call, and the test then passes without proving a re-read from 9 GiB. That is a coverage gap, not a flake, and it is out of scope here.

- **Negative-only:** line 246 (`N slots`, `secondResolved` false, no `slot-1.json`), 308, 393, 412 (includes `.not.toHaveBeenCalled()` at line 414), 954, 972, 996, 1025.
- **Ordering-only:** line 252 (`drive(5)` after `first.release()`), 908 (`never admits a head alone below the hard reserve…`), 926 (`counts the bound from the head's first memory block…`).
- **Already predicate-capped:** line 683 (`drive(40, () => reads > 2)`).

## Decisions

- **D1** — Use `drive(200, predicate)`, not `driveUntil`, so a failure shows the real argument diff from the assertion that follows.
- **D2** — The predicate is `calls.length > 0` (plus the waiter-file count at Site D), not an exact-argument match. With a fixed clock, only the first reason is ever reported.
- **D3** — Include the four memory-admission sites even though the issue names only the fairness block. They have the same cause and the same one-line fix, and leaving them would leave known flakes in the same file. They get their own item so review can tell them apart.
- **D4** — At Site C, replace the fixed `drive(10)` with a read-counting wait (two more `available` reads after the first report, asserted), so `toHaveBeenCalledTimes(1)` proves the no-repeat behavior even on a slow host. (Revised after plan critique round 1; see Critique response.)
- **D5** — The file-size ratchet does not apply: `scripts/lint-file-size.sh` excludes `*.test.ts` (line 145).

## Critique response

### Later polls are not established

Accepted. The critic is right that `drive(10)` waits a fixed amount of real time and does not prove another filesystem-backed poll completed, so `toHaveBeenCalledTimes(1)` could pass without testing repeat suppression. WI-3 Site C now counts calls to the `available` callback (one per poll, via `readMemory(sampleMemory)`), waits with `drive(200, () => reads >= readsAtReport + 2)` after the first report, and asserts `reads >= readsAtReport + 2` before it checks `toHaveBeenCalledTimes(1)`. Two reads are needed, not one: the first later read happens before that poll's `notifyWaiting`, and the second can start only after it finished. FR-3, D4 and AC-3 are updated to match.

### Unchanged drive can make re-read test vacuous

Accepted as framing. The "Sites deliberately left unchanged" section now says these drives cannot cause the zero-call failure, and it names the `re-reads the estimate every poll` test as one that a slow host can weaken. Fixing that coverage gap stays out of scope.
