# PAN-4757 — pan-2355-mobile e2e spec matches "yesterday" as a second "Yes" button

**Issue:** [PAN-4757](https://github.com/eltmon/overdeck/issues/4757)
**Introduced by:** PAN-2355 (#4693, `8e438c2660e`)
**Planned at:** `5f0dc01023e` on `feature/pan-4757`, 2026-11-02

## Glossary

- **Accessible name** — the text a screen reader announces for an element. For a `<button>` it is the concatenated text of everything inside it. The Needs-you row header button's accessible name includes the row label, the pending-input description and the relative time.
- **Strict mode (Playwright)** — every action (`tap`, `click`) and every `expect(locator)` assertion requires its locator to resolve to exactly one element. Two matches throw `strict mode violation … resolved to 2 elements`.
- **Substring name match** — Playwright's `getByRole(role, { name: 'Yes' })` is a **case-insensitive substring** match by default. `name: 'Yes'` matches any button whose accessible name contains `yes`, including `yesterday`. `{ exact: true }` switches it to a case-sensitive whole-string match (after whitespace trimming).
- **Testing-library name match** — `@testing-library`'s `getByRole(role, { name: 'Yes' })` is a whole-string match. This is why the Vitest test `MobileNeedsYou.test.tsx` cannot catch this bug; only the Playwright spec can.
- **Relative time** — `formatRelativeTime(date, now)` in `src/dashboard/frontend/src/lib/formatRelativeTime.ts`. It returns `just now`, `Ns ago`, `Nm ago`, `Nh ago`, `yesterday` (exactly 24–47 h), `Nd ago` (2–6 days) or a short date.
- **Fixture row** — an entry of the `PENDING` array in the spec, served by the mocked `GET /api/conversations/pending-input` route.

## Problem

`main` CI run #12496 (head `f0fbe1d4a8d`, docs-only, created `2026-11-02T00:37:29Z`) failed `test-e2e`:

```text
Error: locator.tap: Error: strict mode violation: locator('[data-subject-id="pan-2355-ship"]').getByRole('button', { name: 'Yes' }) resolved to 2 elements
  at src/dashboard/frontend/tests/pan-2355-mobile.spec.ts:133:54
```

Run #12495 (`3094afd254c`, created `2026-11-01T23:52:45Z`) was green.

## Root cause (verified)

The failure is a date bomb in the test, not a render bug and not a second question.

1. The fixture hard-codes the question time. `src/dashboard/frontend/tests/pan-2355-mobile.spec.ts`, lines 48–51:
   ```ts
   const PENDING = [
     auqRow('pan-2355-ship', 'Ship the phone shell', 'Ship it now?', '2026-11-01T00:00:00.000Z'),
     auqRow('pan-2355-docs', 'Write the phone docs', 'Publish the docs?', '2026-11-01T00:05:00.000Z'),
   ];
   ```
2. `useDecisions` copies `askedAt` into `since`: `src/dashboard/frontend/src/lib/useDecisions.ts`, line 79 (`return c.pendingPermission?.since ?? c.pendingAskUserQuestion?.askedAt ?? …`).
3. The row header `<button>` (`src/dashboard/frontend/src/components/mobile/MobileNeedsYou.tsx`, line 216) renders the relative time inside itself, at line 230:
   ```tsx
   <span className="shrink-0 text-xs text-muted-foreground">{formatRelativeTime(decision.since, now)}</span>
   ```
   That button sits inside the same `<li data-subject-id="pan-2355-ship">` (line 213) the spec scopes to.
4. `formatRelativeTime` returns `'yesterday'` when `diffDays === 1` (`formatRelativeTime.ts`, line 28).
5. Run #12495 ran 23 h 52 m after `askedAt` → header reads `23h ago`. Run #12496 ran 24 h 37 m after → header reads `yesterday`.
6. `first.getByRole('button', { name: 'Yes' })` (spec line 133) is a substring match, so it matched both the `Yes` option button and the row header button (`Ship the phone shell · Question waiting · yesterday`). Two elements → strict-mode violation.

Consequences: every `test-e2e` run between `2026-11-02T00:00Z` and `2026-11-03T00:00Z` fails deterministically. From `2026-11-03T00:00Z` the header reads `2d ago` and the spec passes again, so the bug hides until someone next changes the fixture dates. The two hypotheses in the issue body are ruled out: `QuestionCard` renders each option once (`MobileNeedsYou.tsx` lines 81–107, one `<button>` per option), and the fixture row has one question with options `Yes` and `No` (spec line 43).

## Requirements

- **FR-1** — The `Yes` option tap at spec line 133 resolves to exactly one element regardless of the row header's relative-time text. It uses `{ name: 'Yes', exact: true }`.
- **FR-2** — The `PENDING` fixture computes `askedAt` relative to the test's run time, and pins `pan-2355-ship` so its header always renders `yesterday`. This makes the former collision a permanent regression guard: without FR-1 the spec fails on every run; with FR-1 it passes on every run.
- **FR-3** — `docs/TESTING.md` states that Playwright `getByRole` name matching is a case-insensitive substring match and that short option names such as `Yes` need `exact: true`, and that e2e fixture timestamps are computed relative to `Date.now()`. `.overdeck/context/codebase/conventions.md` carries the same rule as one Testing bullet.
- **NFR-1** — No change to any component under `src/dashboard/frontend/src/`. The UI is correct; the test locator was wrong.
- **NFR-2** — No `.first()`, `.nth()`, retry, or `test.retry` added to the spec.
- **NFR-3** — The order of the Needs-you rows is unchanged: `pan-2355-ship` stays older than `pan-2355-docs`, so it remains the first answerable row and opens by default (`useDecisions.ts` lines 338–342 sort oldest first).

## Decisions (made here, not left to the executor)

- **D-1 Fix the locator, not the component.** The header's accessible name containing the relative time is correct accessibility behavior. The defect is the test's substring match.
- **D-2 `exact: true`, not `.first()`.** `.first()` would pick whichever matching button comes first in DOM order; that is the row header (line 216 precedes the card at line 232), so `.first()` would tap the wrong button. `exact: true` targets the option by its whole name.
- **D-3 Pin the ship row to 25 hours ago.** 25 h sits inside the `yesterday` band (24 h ≤ age < 48 h) with an hour of slack on each side of the spec's 3-minute timeout. The docs row is ship + 5 minutes (24 h 55 m ago), which also reads `yesterday` and keeps the original ordering (NFR-3).
- **D-4 Both spec edits land in one commit.** Pinning the fixture to `yesterday` without `exact: true` makes the spec fail on every run, so the two edits are not independently mergeable.
- **D-5 Leave the `Send` locator (line 134) as it is.** No other button in the ship card or its header contains `send` (header text is `Ship the phone shell`, `Question waiting`, `yesterday`). Changing it is not required by this bug. The docs rule (FR-3) covers future specs.
- **D-6 Leave `CONVERSATIONS` fixture dates alone.** Step 5 only asserts that the first list item contains `Ship the phone shell`; its ordering depends on the relative order of the two fixed timestamps, which does not drift.
- **D-7 No sweep of other specs.** Other specs under `src/dashboard/frontend/tests/` are out of scope. Eleven spec files already use `exact: true`.
