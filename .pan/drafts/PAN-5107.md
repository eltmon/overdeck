# PAN-5107: Phone app: delete your account from Settings

**Issue:** [PAN-5107](https://github.com/eltmon/overdeck/issues/5107)
**Status:** planned (auto planning, 2026-11-10)
**Base:** `feature/pan-5107` at `de06326928c`

## Why

Signing in to the phone app (`apps/mobile`) creates an overdeck.ai account. App Review Guideline
5.1.1(v) requires that an app which creates an account lets the user start deleting it from inside
the app. Google Play's account-deletion policy asks the same for the Play listing. The phone app has
no way to do this today, so the iPhone build cannot go to App Review. `apps/mobile/RELEASE.md`
("App Store review", lines 184-188) and `apps/mobile/README.md` (line 257) both say so.

The server side already exists. This change is phone-app code, its tests and its docs only.

## Glossary

- **Account service:** the overdeck.ai Cloudflare Worker in `services/account/`, served at
  `ACCOUNT_BASE_URL` (`apps/mobile/src/shell/config.ts`, line 7, default
  `https://account.overdeck.ai`). Deploying it is operator-only. This change does not touch it.
- **Device token:** the `odd_…` bearer token the phone got at sign-in, stored in the `account`
  secret as `AccountRecord.token` (`apps/mobile/src/shell/types.ts`, lines 4-8).
- **`DELETE /v1/account`:** the account-service route that starts deletion
  (`services/account/src/routes.ts`, line 53; handler `requestDeletionHandler` in
  `services/account/src/deletion.ts`, lines 114-121). It revokes every device of the account,
  opens a deletion job, and answers `202 {"deletionRequestedAt": <ms>}`.
- **Sign-out cleanup:** the ordered local cleanup in `signOut()` (`apps/mobile/src/shell/signOut.ts`,
  lines 52-81): remove the phone from each paired machine, delete the FCM token (Android), send
  `push-unregister` and `forget-client` to the directory, end the Live Activity (iOS), **revoke the
  device** (`DELETE /v1/devices/<id>`), delete keys and secrets, clear `localStorage`, reload.
- **Revoke step:** the one cleanup step that calls `DELETE /v1/devices/<id>`. `signOut()` runs it
  only when `deps.account` is non-null (`signOut.ts`, lines 74-77).
- **Signed-out notice:** a one-shot message shown on the sign-in screen after the reload that ends
  the cleanup. It is carried across the reload in `sessionStorage` (see D-3).
- **Token gone:** the account service refused the device token with 401 (`invalid_token`,
  `device_revoked`) or 403. The phone can no longer act on the account.
- **`DELETE_STATEMENT`:** the web page's sentence about what deletion removes
  (`services/account/src/account-page/page.ts`, lines 22-23).

## Verified facts (2026-11-10, `de06326928c`)

1. `requestDeletionHandler` calls `authenticateRequest(req, rc, { allowExpiredGrant: true })`
   (`deletion.ts`, line 116). So a lapsed grant never gets 403 on this route. `authenticateRequest`
   (`services/account/src/devices.ts`, lines 205-217) answers 401 with `{"error": <code>}` for
   `invalid_token`, `device_revoked` and `account_deleted`.
2. `lookupDevice` (`devices.ts`, line 151) checks `deleted_at` before `revoked_at`:
   `if (row.deleted_at !== null) return { ok: false, error: 'account_deleted' };`. So while a
   deletion job is open, every token of that account gets `401 {"error":"account_deleted"}`. Once
   the job completes and the rows are gone, it gets `invalid_token`.
3. The deletion job runs in `ctx.waitUntil` after the 202 (`deletion.ts`, line 119). The directory
   holder closes every machine and phone socket of the account (`docs/ACCOUNT-SERVICE.md`, line 141).
4. `DELETE_STATEMENT` is
   `'Deleting your account signs out every device, removes your machines from the directory and deletes all of your hosted data within 24 hours.'`
   and the web's success text is `DELETION_STARTED_MESSAGE = 'Your account is being deleted.'`
   (`services/account/src/account-page/actions.ts`, line 19).
5. `services/account/package.json` has no `@overdeck/contracts` dependency, and no file under
   `services/account/src` imports it. Sharing the text through contracts would change Worker source.
6. `signOut.ts` line 104-111 already calls the account service through `CapacitorHttp.request`
   with `Authorization: Bearer ${account.token}`. `CapacitorHttp.request` resolves for every HTTP
   status (including 5xx) and rejects on a network failure. Its `HttpOptions` has
   `connectTimeout?: number` and `readTimeout?: number` in milliseconds
   (`apps/mobile/node_modules/@capacitor/core/types/core-plugins.d.ts`, lines 134 and 138).
7. The cleanup's last steps are `clearStorage: () => localStorage.clear()` and
   `reload: () => navigate('/')` (`apps/mobile/src/shell/ShellApp.tsx`, lines 390-391), and
   `navigate` defaults to `location.assign`. Nothing in the cleanup clears `sessionStorage`.
   `ShellApp.tsx` (lines 52-62, `LAUNCH_URL_KEY`) already relies on `sessionStorage` surviving that
   reload.
8. `@capacitor/browser` is already a dependency and `signIn.ts` (line 58) opens pages with
   `Browser.open({ url })`.
9. Mobile tests run with `npm --prefix apps/mobile test` (CI job `mobile-android`,
   `.github/workflows/ci.yml`, line 315). The root `npm test` does not run them. Account-service
   tests live in the root suite under `tests/unit/services/account/`. `npm run typecheck:mobile`
   exists (`package.json`, line 115).
10. `apps/mobile/ACCEPTANCE.md` (lines 7-12) and `apps/mobile/README.md` (lines 244-246) say new
    evidence goes in `apps/mobile/acceptance/PAN-<n>.md` and nobody adds sections to
    `ACCEPTANCE.md`.
11. `changelog.mdx` has no `tags={["Upcoming"]}` block: its top block is
    `<Update label="v0.75.0" description="2026-11-10">` (line 13), already released.

## Decisions

- **D-1. No Worker change.** The phone calls the existing `DELETE /v1/account`. No file under
  `services/account/src/` changes, so no Worker deploy is needed.
- **D-2. The copy is duplicated, and a test pins it.** The phone gets its own copy of
  `DELETE_STATEMENT` and `DELETION_STARTED_MESSAGE` in a new module with no imports,
  `apps/mobile/src/shell/accountDeletionCopy.ts`. A root test imports both modules and asserts the
  strings are equal (an import test, not a source-grep test). Reason: fact 5; sharing through
  contracts would be a Worker source change.
- **D-3. The signed-out notice crosses the reload in `sessionStorage`.** Key
  `overdeck.signedOutNotice`, value `deletion-requested` or `finish-on-web`. The delete flow writes
  it before it runs the cleanup. `ShellApp` reads it in a `useState` initializer (no side effect)
  and removes the key in a mount effect, so the notice shows once. Reason: fact 7.
- **D-4. The revoke step is skipped by passing `account: null` to `signOut()`.** `signOut.ts` does
  not change. `deleteAccount()` calls `signOut({ ...cleanup, account: null })`, and a test that
  uses the real `signOut()` asserts that `DELETE /v1/devices/<id>` is never called. Reason: the
  server already revoked every device, and the `account` field is used only by the revoke step.
- **D-5. Status mapping.**

  | Account service answer | Outcome | Phone does |
  | --- | --- | --- |
  | `202` | `requested` | write notice `deletion-requested`, run cleanup without revoke |
  | `401` with body `error: "account_deleted"` | `requested` | same as 202 (a deletion is already open, for example a retry after a lost 202) |
  | any other `401`, or `403` | `token-gone` | write notice `finish-on-web`, run cleanup without revoke |
  | any other status (including 4xx and 5xx) | error `overdeck.ai answered HTTP <status>.` | stay signed in; show error and **Delete on the web** |
  | request rejects (network, timeout) | error with the rejection's message | stay signed in; show error and **Delete on the web** |

  The 403 branch stays even though fact 1 says this route cannot answer 403 today: the issue asks
  for it, and a future route change would otherwise strand the user in the error state.
- **D-6. The confirm word is exact.** The confirm button is enabled only when
  `input.trim() === 'DELETE'` (case-sensitive). The input sets `autoCapitalize="characters"`,
  `autoCorrect="off"`, `autoComplete="off"` and `spellCheck={false}` so phone keyboards produce
  capitals. The phone does not ask for the GitHub login.
- **D-7. Request timeouts.** The DELETE passes `connectTimeout: 15_000` and `readTimeout: 15_000`.
  A hung request becomes a rejection and lands in the error row of D-5. If the server finished but
  the answer was lost, a retry gets `401 account_deleted`, which D-5 maps to `requested`.
- **D-8. Acceptance evidence file.** The issue says "add a line to `apps/mobile/ACCEPTANCE.md`".
  That file's own header (fact 10) forbids adding to it. The evidence checklist goes in a new
  `apps/mobile/acceptance/PAN-5107.md` instead, and `ACCEPTANCE.md` does not change.
- **D-9. Changelog block.** Create the missing Upcoming block for the next release, `v0.76.0`, in
  the shape `docs/RELEASING.md` (line 123) expects.
- **D-10. Docs also fix two stale spots the issue did not name:** the RELEASE.md Store facts
  "Deletion:" bullet (line 165) and the README "What it cannot do yet" bullet (line 257).

## Requirements

- **FR-1.** Settings shows a **Delete account** button below **Sign out**, styled as destructive
  (`text-destructive`, same shape as Sign out).
- **FR-2.** Tapping **Delete account** opens a dialog (`role="dialog"`, `aria-modal="true"`) titled
  "Delete your account" that shows `DELETE_STATEMENT`, "This can't be undone.", a text field

  **Delete account**. Nothing is sent when the dialog opens.
- **FR-3.** The confirm button is disabled until the field holds exactly `DELETE` after trimming

- **FR-4.** Confirming sends `DELETE ${ACCOUNT_BASE_URL}/v1/account` through
  `CapacitorHttp.request` with `Authorization: Bearer <account.token>` and the D-7 timeouts.
- **FR-5.** The outcome follows the D-5 table.
- **FR-6.** On `requested`, the app runs the sign-out cleanup without the revoke step and, after

- **FR-7.** On `token-gone`, the app runs the same cleanup and, after the reload, the sign-in screen

  `Browser.open({ url })` from `@capacitor/browser`.

  disabled, and Cancel is disabled.
- **NFR-1.** No file under `services/account/src/` changes (D-1).
- **NFR-2.** The phone's copy of `DELETE_STATEMENT` and `DELETION_STARTED_MESSAGE` equals the

Module shape (follow `signOut.ts` style: injected deps, top-of-file doc comment):

```ts
/** Delete the overdeck.ai account from the phone (PAN-5107): DELETE /v1/account, then the sign-out cleanup without the revoke step. */
import { Browser } from '@capacitor/browser';
import { CapacitorHttp } from '@capacitor/core';

import { ACCOUNT_BASE_URL } from './config';
import { signOut, type SignOutDeps } from './signOut';
import type { AccountRecord } from './types';

export const DELETE_ACCOUNT_TIMEOUT_MS = 15_000;
export const SIGNED_OUT_NOTICE_KEY = 'overdeck.signedOutNotice';
export type SignedOutNotice = 'deletion-requested' | 'finish-on-web';
export type DeletionAnswer = 'requested' | 'token-gone';
export type DeleteAccountResult = { ok: true } | { ok: false; message: string };

/** D-5: 202, or 401 account_deleted → requested; other 401 or 403 → token-gone; any other status throws. */
export async function requestAccountDeletion(account: AccountRecord): Promise<DeletionAnswer> { … }

export interface DeleteAccountDeps {
  account: AccountRecord;
  /** The sign-out cleanup; deleteAccount runs it with `account: null`, which skips the revoke step. */
  cleanup: SignOutDeps;
  request?: (account: AccountRecord) => Promise<DeletionAnswer>; // default requestAccountDeletion
  setNotice?: (notice: SignedOutNotice) => void;                 // default writeSignedOutNotice
}

export async function deleteAccount(deps: DeleteAccountDeps): Promise<DeleteAccountResult> {
  let answer: DeletionAnswer;
  try {
    answer = await (deps.request ?? requestAccountDeletion)(deps.account);
  } catch (error) {
    return { ok: false, message: error instanceof Error ? error.message : String(error) };
  }
  (deps.setNotice ?? writeSignedOutNotice)(answer === 'requested' ? 'deletion-requested' : 'finish-on-web');
  await signOut({ ...deps.cleanup, account: null });
  return { ok: true };
}

export function writeSignedOutNotice(notice: SignedOutNotice): void { /* sessionStorage.setItem, try/catch */ }
export function readSignedOutNotice(): SignedOutNotice | null { /* only the two known values, else null; try/catch */ }
export function clearSignedOutNotice(): void { /* sessionStorage.removeItem, try/catch */ }
export const openAccountPage = (): Promise<void> => Browser.open({ url: `${ACCOUNT_BASE_URL}/account` });
```

`requestAccountDeletion` details:

1. `CapacitorHttp.request({ method: 'DELETE', url: \`${ACCOUNT_BASE_URL}/v1/account\`, headers: { Authorization: \`Bearer ${account.token}\` }, connectTimeout: DELETE_ACCOUNT_TIMEOUT_MS, readTimeout: DELETE_ACCOUNT_TIMEOUT_MS })`.
2. `202` → `'requested'`.
3. `401`: read the body's `error`. `response.data` may be a parsed object or a JSON string; read
   `error` from either, and treat anything unreadable as no code. `'account_deleted'` →
   `'requested'`; anything else → `'token-gone'`.
4. `403` → `'token-gone'`.
5. Any other status → `throw new Error(\`overdeck.ai answered HTTP ${status}.\`)`.
6. A rejection propagates unchanged.

`beforeEach` and `vi.useRealTimers()` in `afterEach` because the real `signOut()` has 5 s

## Hazards

- **H-1. Cleanup races the server's directory teardown.** After the 202 the account service closes
  every machine socket of the account in `ctx.waitUntil` (fact 3). The cleanup's
  `remove from <machine>` steps may then hit their 5 s timeout each, so "Deleting…" can last about
  5 s per paired machine. The machines may keep a stale phone record; deleting the account makes it
  useless. Keep the order (DELETE first), because a network failure must leave local state intact.
- **H-2. `CapacitorHttp` body shape.** `response.data` can be an object or a string depending on
  platform and content type. WI-2 step 3 reads both and must not throw on either.
- **H-3. `sessionStorage` unavailable.** Wrap every `sessionStorage` call in try/catch; a missing
  notice must never block sign-out or boot.
- **H-4. StrictMode or double render.** Read the notice in the `useState` initializer without side
  effects and clear it in an effect, never in the initializer.
