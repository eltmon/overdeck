# PAN-2383 — Editable per-issue Standing Crew (tiered-execution) toggle on the issue view

**Operator context:** RUN-56, FIRST Standing-Crew test-drive. This issue is BUILT BY the Standing Crew via its own per-issue override (`plan.metadata.tiered_execution: 'on'` in this vBRIEF). Bead difficulties are spread honestly so all three tiers + escalation are exercised on film.

## Glossary

- **Tiered execution / Standing Crew** — routing each vBRIEF bead to the cheapest warm agent tier that can do the work, with a durable supervisor. Off by default. Contract: `docs/TIERED-EXECUTION.md`.
- **Global flag** — `tiered_execution.enabled` in `~/.overdeck/config.yaml` (+ per-project `.pan.yaml` additive merge). The baseline on/off for a project.
- **Per-issue override** — a single issue's opt-in/opt-out of tiered execution, winning over the global flag for that one issue. Today it lives ONLY in `plan.metadata.tiered_execution` (`'on'|'off'`), set at planning time.
- **`resolveTieredExecutionEnabled(config, planMetadata)`** — `src/lib/agents/tier-table.ts:124`. The resolver: `plan.metadata.tiered_execution` (`'on'|'off'`) wins over `config.enabled`; unset inherits; any other value throws `TieredExecutionConfigError` (fail-loud). PAN-2383 extends this to also consult a new mutable record override.
- **The per-issue record** — `<workspace>/.pan/records/<issue-lowercase>.json`, `interface PanIssueRecord` in `src/lib/pan-dir/record.ts:127`. Durable, git-tracked, travels via `git push`. Already the home for per-issue overrides that beat project/global config (see `reviewMode`).
- **`reviewMode` precedent** — `PanIssueRecord.reviewMode` (`record.ts:139`, "Per-issue review mode override; beats project/global config"), resolved by `resolveReviewMode(issueId)` (`src/lib/cloister/review-agent.ts:890`) which reads `readIssueRecordSync(project, issueId)?.reviewMode` and falls back to global config. This is the exact schema+resolver pattern PAN-2383 mirrors.
- **`tierOverrides` (DO NOT CONFUSE)** — a *different* concept: the workspace `continue.json` `tierOverrides` map holds escalation's per-bead *effective-difficulty* promotions (`src/lib/agents/tier-replay.ts:60`). It is workspace-scoped and destroyed with the workspace. It is NOT the per-issue on/off override. PAN-2383 must use a distinctly-named field to avoid conflation.
- **PAN-1124 spec immutability** — the vBRIEF spec on main is immutable after planning; only `plan.status` may change (`updateSpecStatus`, `pan-dir/specs.ts`). Therefore `plan.metadata` cannot be the mutable home for a post-planning override.
- **The plan read door** — `GET /api/workspaces/:issueId/plan` (`src/dashboard/server/routes/workspaces/workspace-data.ts:763`) spreads the full vBRIEF doc (incl. `plan.metadata`). PAN-2383 extends its response with a computed `tieredExecution` block.
- **Write-door precedent (structure only, NOT the storage target)** — `PATCH /api/workspaces/:issueId/plan/inspection-policy` (`workspace-data.ts:822`) shows the route shape (origin check → `readJsonBody` → allow-list validation → mutate → register in `Layer.mergeAll`). NOTE: that precedent writes *directly to the vBRIEF spec file* via `writeFile(location.path, …)`, which is exactly what PAN-1124 forbids for `plan.metadata`. PAN-2383's write door instead persists to the RECORD via the `writeRecord*` family.

## Problem

The per-issue override *resolution* already exists (`resolveTieredExecutionEnabled`, `tier-table.ts:124`), and PAN-2378 shipped a **read-only** chip on the issue view (`PlanCard.tsx:66-75`, a static `<a>` link to docs). But:

1. There is **no way to flip the override from the UI** — the chip is a read-only link.
2. There is **no write door** for it. `plan.metadata` is immutable after planning (PAN-1124), so the override cannot be edited in place.
3. The only way to set the override today is at planning time.

Operators need to turn the Standing Crew on/off for a single issue **after planning** — "this is a good tiered candidate" / "take this one back to single-model" — without re-planning.

## Proposal

Give the per-issue override a **mutable home in the per-issue record** (`.pan/records/<issue>.json`), a new field `record.tieredExecutionOverride?: 'on' | 'off'` (unset = inherit). Persist edits through the `writeRecord*` write-door family (durable, git-committed). Extend the resolver so precedence is **record override > `plan.metadata.tiered_execution` > global flag**, fail-loud, no hardcoded fallback. Surface the resolved effective state + its source through the plan read door, and make the issue-view chip an **editable on / off / inherit** control that writes through a new PATCH endpoint.

**Why the record, not `continue.json` (candidate #2 from the issue):** `continue.json` is workspace-scoped and destroyed with the workspace; its `tierOverrides` map is already taken (escalation effective-difficulty). The record is durable, travels with git, and is already the canonical home for per-issue overrides that beat global config (`reviewMode`). Recorded as **AD1**.

**Mid-flight semantics:** dispatch reads the record fresh at each bead spawn (mirroring `resolveReviewMode`), so flipping the toggle affects **subsequent dispatches only** — it never kills or signals a running tier session mid-bead. The PATCH handler mutates the record and returns; it does not touch tmux/agents. Recorded as **H1**.

## Requirements

### Functional
- **FR-1** — A new mutable per-issue override field `tieredExecutionOverride?: 'on' | 'off'` on `PanIssueRecord` (`record.ts`), with `unset` meaning inherit. Persisted through a `writeRecord*`-family setter that queues the record's git auto-commit.
- **FR-2** — `resolveTieredExecutionEnabled` (or an issue-aware wrapper) resolves with precedence **record override > `plan.metadata.tiered_execution` > `config.enabled`**; unset record override preserves today's behavior exactly; invalid stored values throw `TieredExecutionConfigError` (fail-loud, no hardcoded fallback).
- **FR-3** — Live agent dispatch (`spawn-prep.ts` slot + single-work paths) honors the record override on the next dispatch after a flip.
- **FR-4** — The plan read door (`GET /api/workspaces/:issueId/plan`) returns a computed `tieredExecution: { effective: boolean, source: 'issue-override' | 'plan-metadata' | 'global', override: 'on' | 'off' | null }` block.
- **FR-5** — A write door `PATCH /api/workspaces/:issueId/tiered-execution` accepts `{ override: 'on' | 'off' | null }`, validates against that allow-list (400 otherwise), persists via the record setter, and returns the updated resolved `tieredExecution` block. It does NOT signal or kill running agents.
- **FR-6** — The issue-view chip (cockpit `PlanCard.tsx`) renders the resolved effective state + source sourced from the server (no client-side precedence compute).
- **FR-7** — The chip is an editable **on / off / inherit** control that PATCHes the write door with an optimistic cache update on `['workspace-plan', issueId]`.
- **FR-8** — `docs/TIERED-EXECUTION.md` documents the editable per-issue override, its record home, and the record > plan-metadata > global precedence; `CHANGELOG.md` notes the feature.

### Non-functional
- **NFR-1** — Single-source-of-truth: writes go through the record write door only; the resolver is the single read path for effective state. No direct store writes for the override outside the write door.
- **NFR-2** — Follow `pan-style-guide`: no decorative color; the control is muted; validation red only.
- **NFR-3** — Fail-loud: invalid override values are never silently inherited or persisted.
- **NFR-4** — The override field name must NOT reuse `tierOverrides` (escalation effective-difficulty map) to avoid conflation.

## NonGoals

- Editing the tier table / schema / dispatch behavior (PAN-1791 / PAN-2222 / PAN-2283 territory).
- Per-project tiered-execution editing (global Settings surface is PAN-2378's, unchanged).
- A second "issue inspector" surface for the control. `InspectorPanel` is a defunct era (`StatusHistoryTab.tsx:29` comment "in the InspectorPanel era, then lost"); no live inspector renders issue tiered state, so the canonical control lives in the cockpit `PlanCard.tsx` (the issue view, acceptance #1). Recorded as **AD2**.
- Mutating `plan.metadata` in place, or writing to the vBRIEF spec file (PAN-1124). The inspection-policy PATCH's direct-spec-write is a structural template only, not the storage target.
- Retroactively re-dispatching or killing in-flight tier sessions on a flip (mid-flight = subsequent dispatches only; H1).
- A `pan` CLI command for the override (the requirement is a UI toggle; a CLI can follow later, mirroring `pan review mode`).
