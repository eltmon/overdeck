## Glossary

- **Effort / canonical level** — one of `low`, `medium`, `high`, `xhigh`, `max` (`EFFORT_LEVELS`, `packages/contracts/src/effort.ts`). Default `high` (`DEFAULT_EFFORT`). Never default to `xhigh`/`max` (`sync-sources/rules/effort-high-default.md`).
- **Harness** — the agent CLI/runtime: `claude-code`, `codex`, `acp` (Kimi via ACP), `opencode` (OpenCode via ACP), `kimi-code` (native Kimi CLI), `ohmypi` (the "Pi" harness; launches the `omp` binary; legacy alias `pi`), `muse`, `prime-agent`.
- **Resolve** — `resolveEffort({ explicit, model, harness, role?, ... })` walks the precedence chain (explicit → item → plan → tier → sub-role → role → project → default `high`) and clamps the result. It is synchronous and has no child-process I/O.
- **Clamp** — canonical → canonical. If the model∩harness supported set lacks the requested level, use the highest supported level below it (rule D6 of PAN-4249). Implemented by `clampEffort` in `effort-support.ts`. `resolveEffort` always clamps.
- **Translate** — canonical → harness-native value inside an adapter. Only Kimi K3 translates (`src/lib/kimi-effort.ts`: `low→low`, `medium/high→high`, `xhigh/max→max`). Every other harness emits the canonical value unchanged.
- **Producer** — code that assembles a launcher config or host argv and therefore decides the effort value an adapter receives (for example `getCodexLauncherFields` in `src/lib/agents/runtime-command.ts`, or `CodexRuntime.spawnAgent` in `src/lib/runtimes/codex.ts`).
- **Adapter / emitter** — code that turns the received value into the harness's native input: a CLI flag (`--effort`, `--thinking`, `--reasoning-effort`), a `config.toml` key, an environment variable, or an ACP/app-server request. Files: `src/lib/launcher-generator.ts`, `src/lib/launcher-codex-command.ts`, `src/lib/runtimes/codex.ts` (`initCodexHome`), `src/lib/codex/app-server-host.ts`, `src/lib/acp/host.ts`, `src/lib/kimi-effort.ts`.
- **Fallback** — an adapter-local default such as `effort ?? 'high'`. `npm run lint:effort` ratchets these per file against a `BASELINE` table in `scripts/lint-effort.sh`.
- **Mapping test** — a table test that, for one harness, feeds each of the five canonical levels through the producer step (`resolveEffort({ explicit: level, model, harness })`) and then the adapter, and asserts the exact native value the harness receives.
- **CLIProxy** — the sidecar on port 8317 (`src/lib/cliproxy.ts`, pinned `CLIPROXY_RELEASE_VERSION = 'v7.3.16'` at line 61) that lets claude-code run GPT models by translating Anthropic `/v1/messages` requests into OpenAI/Codex requests.

### F7 — CLIProxy spike result: GPT via claude-code **does** honor `--effort`

1. **What Claude Code sends.** With a local capture listener as `ANTHROPIC_BASE_URL` and `claude -p --effort low|max --model gpt-5.6-luna`, every `/v1/messages` request carried `"thinking": {"type": "adaptive", "display": "omitted"}`, `"output_config": {"effort": "<level>"}`, and the `effort-2025-11-24` beta header. (Probe run 2026-10-04 during planning; the listener answered 400, so no model call was made.)
2. **What CLIProxy does with it.** The installed sidecar reports `CLIProxyAPI Version: 7.3.16, Commit: c404af96`. In `router-for-me/CLIProxyAPI` at tag `v7.3.16`, `internal/translator/codex/claude/codex_claude_request.go` (function `convertClaudeRequestToCodex`, block commented `// Convert thinking.budget_tokens to reasoning.effort.`) reads `output_config.effort` when `thinking.type` is `adaptive` or `auto` and writes it to the Codex request's `reasoning.effort`; the code comment says `ApplyThinking` clamps it to the target model's levels. With adaptive thinking and no `output_config.effort`, it sends `xhigh`; with no `thinking` block at all, it sends `medium`.
3. **Conclusion.** Claude-code-routed GPT sessions honor `--effort`. Overdeck always passes `--effort` to claude-code launches (PAN-4249 W5, PAN-3077), so they never fall into CLIProxy's `xhigh`/`medium` defaults. No follow-up issue is needed. W9 records this in the docs.

## Decisions

- **D1 — "Resolved upstream" means the producer resolves and the emitter never defaults.** Every producer calls `resolveEffort({ explicit: <value it was given>, model, harness[, role] }).effort` (idempotent for an already-resolved value; resolves `undefined` to the chain's default `high`; clamps). Emitters use the value they receive. No emitter contains `?? '<level>'`, a default parameter, `?? DEFAULT_EFFORT`, or a copy of the level list.
- **D2 — A missing value fails loudly where the harness always received one.** pi `--thinking`, muse `--reasoning-effort`, codex app-server `--effort`, codex `config.toml` `model_reasoning_effort`, OpenCode's `effort` config option (when the model exposes one), and Kimi K3 effort were always emitted before. If the resolved value is absent there, the emitter throws a named error (for example `ohmypi launcher requires piEffort`), matching the existing `... launcher requires <field>` errors in `launcher-generator.ts`. Paths that emitted conditionally before (OpenCode models without an `effort` option, Kimi K2.7, non-Kimi ACP providers) keep their condition. Rationale: `no-hardcoded-model-fallbacks` (fail loudly, never silently pick a literal) and PAN-4249 NFR-1 (an unconfigured launch still emits `high`, which is only provable if nothing can silently fall to a harness's own default).
- **D3 — Clamping lives in the producer's `resolveEffort` call, never in an emitter.** Emitters do not import `resolve-effort.ts` (it pulls `config-yaml` and `projects`). `launcher-generator.ts`, `launcher-codex-command.ts`, `acp/host.ts`, `codex/app-server-host.ts` and `kimi-effort.ts` import at most `isEffortLevel` from `@overdeck/contracts`.
- **D4 — OpenCode variants pass through.** OpenCode effort can be a free-form, model-advertised variant (`src/lib/overdeck/conversation-effort.ts` `OPENCODE_EFFORT_PATTERN`). A producer for the `opencode` harness passes a non-canonical variant through unchanged and resolves everything else, exactly like `resolveConversationEffort` does. `resolveEffort` would throw `InvalidEffortError` on a variant.
- **D5 — Kimi model rows list canonical levels; translation narrows.** `kimi-code/k3` and `kimi-code/k3-256k` get `effortLevels: ['low', 'medium', 'high', 'xhigh', 'max']`, matching `k3`/`k3[1m]`, with a comment that `src/lib/kimi-effort.ts` translates to the native `low/high/max`. This fixes F4 and follows PAN-4249 D6 ("clamp, don't translate"; translation stays in adapters). Side effect, intended: `roles.<role>.effort: medium` on `kimi-code/k3` now validates at config load (it means native `high`, as documented).
- **D6 — `gpt-5.5` gets `effortLevels: ['low', 'medium', 'high', 'xhigh']`** (F5), so `max` on gpt-5.5 clamps to `xhigh` before Codex sees it.
- **D7 — `ohmypi` and `muse` harness rows stay `["low","medium","high","xhigh"]`.** Both binaries now parse `max` (F6), but CLI parsing is not evidence the routed model honors it, PAN-4249 D8 set these rows, and the issue's acceptance criterion asks for "clamping for pi and muse `max`". The docs state that the CLIs parse `max` but Overdeck sends at most `xhigh`. Relaxing these rows is a separate operator decision (Non-goals).
- **D8 — The muse launcher's level guard is deleted, not replaced.** `if (!['low','medium','high','xhigh'].includes(effort)) throw ...` (`launcher-generator.ts` line 989) is unreachable once every muse producer clamps through `resolveEffort` (harness row lacks `max`), and it is an enum copy.
- **D9 — The two extension `ThinkingLevel` unions are not edited.** They model the Pi runtime's native API (`off`, `minimal`). `scripts/lint-effort.sh` keeps their counts (1 each) and re-labels both rows as native-vocabulary matches, like the existing `ContextWindowMeter.tsx` false-match row. The ohmypi extension is OMP-specific code slated for removal ([PAN-4003](https://github.com/eltmon/overdeck/issues/4003)).
- **D10 — Mapping tests extend existing test files** where a file already covers the adapter, to keep the surface small. Each harness's table runs every level in `EFFORT_LEVELS` (imported, not re-typed) through `resolveEffort({ explicit: level, model, harness })` then the adapter.
- **D11 — The CLIProxy spike is closed by F7.** No follow-up issue. **Implementation checkpoint (optional):** a work agent with a working CLIProxy may confirm end to end by adding `request-log: true` to the CLIProxy extra config (`getCliproxyConfigExtraPath()` in `src/lib/cliproxy.ts`) on a private test instance and checking one real turn's upstream `reasoning.effort`. Fallback if it cannot (no auth, shared sidecar busy): the docs cite F7's request capture and the v7.3.16 source location. Never enable request logging on the shared sidecar that live agents use.
