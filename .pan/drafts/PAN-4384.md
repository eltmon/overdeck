# PAN-4384 — Approved, green PRs that turn CONFLICTING sit forever: route them back for a sync-main repair

**Issue:** https://github.com/eltmon/overdeck/issues/4384
**Planned:** 2026-09-29 (auto planning, `pan plan --auto`)

## Glossary

- **Merge-ready** — the merge gate's answer for an issue: `evaluateIssueMergeGate` in
  `src/lib/cloister/merge-gate.ts` returns `ready: true`. The rule itself is
  `evaluateMergeReadiness` in `src/lib/cloister/pr-facts.ts`: open, not draft, no
  standing change request, approval proven at the PR head, checks green, the CI
  test job passed when the project runs `verification.tests: ci`, no failed
  required UAT at the head, and the forge says `mergeable`.
- **Merge-ready but conflicting** — every merge-ready condition holds except the
  last: the forge reports `mergeable: false` (`PrFacts.mergeable === false`,
  GitHub `mergeable: "CONFLICTING"`, `mergeStateStatus: "DIRTY"`). This is the
  state PR #4317 (PAN-1166) and PR #4322 (PAN-4311) sat in for about 13 hours on
  2026-09-28/29.
- **Approval at head** — an approval that names the PR's current head commit: a
  trusted verdict marker with `sha=<head>` (`PrFacts.approvedAtHead`) or a GitHub
  review whose `commit.oid` is the head (`forgeApprovalAtHead` in `pr-facts.ts`).
  GitHub's `reviewDecision: APPROVED` alone is NOT approval at head.
- **Repair episode** — one conflict on one approved head. Its key is the PR head
  sha at detection. A new head (for example after the repair pushes a merge of
  main) starts a new episode.
- **Repair** — delivering a sync-main instruction to the issue's work agent (live,
  resumed, or started) so it merges `origin/main` into the feature branch,
  resolves the conflicts, pushes, and re-requests review.
- **Conflict-repair patrol** — the new periodic routine this issue adds. It runs in
  the **dashboard process** (not the deacon child), on a 60 s tick.
- **Pipeline journal** — `<workspace>/.overdeck/pipeline.jsonl`, written through
  `appendPipelineEntry` in `src/lib/cloister/pipeline-journal.ts`. Append-only, never
  authority; the PR wins when they disagree.
- **Needs-you** — the operator-attention signal every feedback relay uses:
  `surfaceIssueFeedbackNeedsYou(issueId, reason, details)` in
  `src/lib/cloister/feedback-target.ts` (a `warn` activity entry "`<id> needs you: …`").
- **Guarded review request** — `requestReviewGuarded` in
  `src/dashboard/server/routes/workspaces/review-pipeline.ts`: the door behind
  `POST /api/review/:id/request`, `pan review request`, and `pan done`.

## Problem

An approved, green PR that becomes CONFLICTING with main is never routed back:

1. The merge gate refuses it (`evaluateMergeReadiness` returns
   `PR is not mergeable (state=conflicting)`), so no merge door ever reaches the
   merge executor's "agent conflict resolution" step (`docs/MERGE-WORKFLOW.md`
   "Merge-executor escalation", step 3). That step only sees PRs that already
   passed the gate.
2. The existing conflict gate (`src/lib/cloister/conflict-gate.ts`,
   `resolveConflictGate`) runs only before review dispatch (its one caller is
   `src/lib/cloister/review-agent.ts`, `resolveConflictGate(` near line 444). An
   approved PR never goes back through review dispatch.
3. The merge-train reconciler (`src/lib/cloister/merge-train-reconciler.ts`) runs
   only after a merge through the specialists route, only when `merge_train` is
   enabled for the project (overdeck does not enable it), and takes its siblings
   from `getMergeReadyIssues()`, which excludes a CONFLICTING PR by definition.
   A direct push to main (for example a `docs(workspace)` commit) triggers
   nothing.
4. Even after a repair, re-review does not start on this repo.
   `gh api repos/eltmon/overdeck/branches/main/protection` returns 404, so GitHub
   does not dismiss approvals on push. After the sync push, `reviewDecision` is
   still `APPROVED`, and `requestReviewGuarded` short-circuits:
   ```ts
   if (derived.pr?.reviewState === 'approved') {
     if (derived.pr?.checks !== 'green') { … return { kind: 'tests-requeued' }; }
     … return { kind: 'already-passed' };
   }
   ```
   The merge gate, however, needs approval at the NEW head. So `pan review request`
   and `pan done` are no-ops and the PR sits again, now non-conflicting but
   unapproved at head.

Evidence (2026-09-29): `gh pr view 4317 --json mergeable,mergeStateStatus,reviewDecision`
→ `CONFLICTING / DIRTY / APPROVED`; same for 4322. `git merge-tree` shows the
conflicting paths: PAN-1166 → `.overdeck/context/codebase/concerns.md`,
`scripts/file-size-allowlist.txt`; PAN-4311 → `scripts/file-size-allowlist.txt`.

## Requirements

- **FR-1** A PR that is merge-ready but conflicting is detected from the live forge
  facts (`getPrFacts`) by a predicate that reuses `evaluateMergeReadiness` with the
  same policy as `evaluateIssueMergeGate`. No status is stored.
- **FR-2** On the first patrol tick that sees a merge-ready-but-conflicting PR for
  a head with no prior repair, the patrol delivers one repair instruction to the
  issue's work agent (wake the live one, else resume or start one through
  `resolveIssueFeedbackTarget`) and appends `conflict.repair-requested` to the
  pipeline journal with `data.head`.
- **FR-3** At most one repair per episode (head). If the same head is still
  merge-ready but conflicting `CONFLICT_REPAIR_GRACE_MS` (45 min) after the repair
  entry, the patrol raises Needs-you once and appends `conflict.repair-escalated`
  (`data.head`, `data.reason`). It never sends a second repair for that head. An
  escalated head gets no further action.
- **FR-4** If the work agent cannot be reached (`resolveIssueFeedbackTarget` returns
  `needsYou`, or delivery fails), the patrol escalates immediately (FR-3's
  Needs-you + `conflict.repair-escalated` with `reason: 'unreachable'`), with no
  repair entry.
- **FR-5** The repair instruction names the exact steps: `pan sync-main <id>`,
  resolve both intents, regenerate generated files instead of hand-merging them
  (per-file rules in Work item 3), build, run gates, commit, **push**, then
  `pan review request <id>`.
- **FR-6** `requestReviewGuarded` short-circuits an approved PR only when the
  approval is not proven stale: when the forge proves the approval does NOT stand
  at the current head (`approvalStandsAtHead === false`), the request proceeds to
  start the review pipeline. `true` or unknown keeps today's behavior.
- **FR-7** Backstop: when a repair entry exists for head H1, the PR head is now a
  different sha, the forge says `mergeable: true`, and no `review.requested` entry
  was journaled after the repair entry and the repair entry is at least
  `CONFLICT_REPAIR_REVIEW_BACKSTOP_MS` (15 min) old, the patrol requests review once
  through `requestReviewGuarded` (source `conflict-repair`). The door journals
  `review.requested` itself, which ends the backstop for that repair.
- **FR-8** After a successful repair and re-approval at the new head, the PR is
  merge-ready again; the existing auto-merge scheduler
  (`src/dashboard/server/services/auto-merge-scheduler.ts`,
  `latestAutoMergeAllowsSchedule`, which re-arms a `blocked`/`failed` row for a new
  head) and executor merge it under the same auto-merge policy that applied
  before the conflict. No new merge door.
- **FR-9** The patrol skips an issue that is paused (`getIssuePause(issueId).status
  !== 'unpaused'`), and the whole patrol does nothing while the Deacon is frozen
  (`isDeaconGloballyPaused()`), on a peer dashboard (`isPeerDashboardProcess()`),
  or with `OVERDECK_DISABLE_CONFLICT_REPAIR=1`.
- **FR-10** `docs/PIPELINE-GATES.md` and `docs/MERGE-WORKFLOW.md` describe the
  conflict-repair step, its journal entries, the head-bound review request, and
  the escalation rule.
- **NFR-1** GitHub quota (PAN-4264): the patrol reads forge facts only for
  candidates whose journal says the last `review.verdict` is `APPROVED` with no
  later `merge.completed`; `getPrFacts` has a 60 s cache; the extra reviews read
  (`forgeApprovalAtHead`) happens only when `mergeable === false` and checks are
  green. Measured 2026-09-29: 2 workspaces match the journal pre-filter, so the
  patrol costs about 2 cached `gh` reads per minute.
- **NFR-2** Never throws out of a tick; one issue's failure does not stop the rest.
  An overlapping tick is skipped (in-flight guard, like `auto-merge-executor.ts`
  `runTick`).
- **NFR-3** Tests use `vi.useFakeTimers()` + `vi.setSystemTime()` and injected deps
  (repo rule: fake timers for delay-based code); no real waits, no source-grep
  tests, no `skipIf`.

## Decisions (made here; the executor does not re-decide)

1. **Host: dashboard process, not deacon-lite.** Deacon-lite runs in the deacon
   child. `grep -n "resumeAgent\|spawnRun\|messageAgent"` over `deacon-lite.ts`,
   `undispatched-review-recovery.ts`, `deferred-handoff.ts`,
   `deacon-api-recovery.ts` finds no resume-with-prompt precedent there, and
   `POST /api/agents` takes no prompt. Every prompt-carrying dispatch
   (`review-verdict-feedback.ts`, `conflict-gate.ts`) runs in the dashboard
   process. The patrol is a service beside `auto-merge-executor.ts`, started from
   `src/dashboard/server/main.ts`. It can call `requestReviewGuarded` in-process
   (no HTTP hop, no `AbortSignal.timeout`).
2. **Dispatch door:** `resolveIssueFeedbackTarget(issueId)` then
   `messageAgent(target.agentId, prompt, 'conflict-repair', { owesRework: true,
   feedbackRedelivery: true, dedupKey })` with
   `dedupKey = conflict-repair:<issue-lower>:<head8>`. On an error whose message
   contains `cannot enforce a dedup key`, retry once unkeyed (the
   `review-verdict-feedback.ts` precedent). This respects operator pauses and uses
   the resurrection ladder (live → resume → start).
3. **Episode key = PR head sha (8 chars) at detection**, stamped as `data.head`.
   Counting is journal-derived so a dashboard restart does not re-send a repair.
4. **Grace = 45 minutes.** A sync-main + conflict resolution + gates + push takes
   tens of minutes; the deacon-lite review recovery cooldown is 60 min. 45 min
   bounds how long a failed repair waits for a human, well under the 13 h seen.
5. **Escalation reading.** The issue's Wanted section ("escalate to Needs-you if
   the conflict survives one repair attempt") is authoritative. AC3's "a second
   failed repair" is read as "the second time the patrol would repair the same
   episode, it escalates instead".
6. **Needs-you door = `surfaceIssueFeedbackNeedsYou`**, not a `needs-you:` agent
   pause. `feedback-target.ts` treats a `needs-you:` pause as a pipeline pause the
   resurrection ladder lifts, and pausing would stop a work agent that may still
   be mid-repair. The board already shows a CONFLICTING PR as blocked
   (`CommandDeck/pipeline-helpers.ts`).
7. **Head-bound guard lives in `requestReviewGuarded` only.** The helper
   `readApprovalStandsAtHead` goes in `merge-gate.ts` (120 lines);
   `pr-facts.ts` is at 993 of the 1000-line ceiling and must not grow.
   `review-pipeline.ts` is at 960 lines; the guard change must add at most ~15
   lines.
8. **Auto-merge after repair uses the existing scheduler.** No change to
   `auto-merge-executor.ts`, `auto-merge-scheduler.ts`, or `merge-sync.ts`.

## Non-goals

- No server-side automatic rebase or merge of a conflicting branch, and no
  server-side conflict resolution.
- No change to `merge_train` flags or `merge-train-reconciler.ts` / `merge-train-deps.ts`.
- No change to the pre-review conflict gate (`conflict-gate.ts`) behavior or prompt.
- No stored status column, table, or flag; the journal entries are records of
  actions, not status.
- No new HTTP route (a new route needs a no-loss-matrix row).
- No agent pause and no `needs-you:` pause reason.
- No change to `reReviewGuardError` (the `/api/review/:id/trigger` path).
- No GitLab-specific conflict handling beyond what `evaluateMergeReadiness`
  already does (GitLab approval is `facts.approved`; the predicate inherits it).
- No change to branch protection on GitHub.

```ts
export interface ConflictRepairGateResult {
  /** True when the PR is merge-ready in every respect except `mergeable: false`. */
  conflicting: boolean;
  reason?: string;
  facts: PrFacts;
}

/**
 * PAN-4384: is this PR merge-ready except for a conflict with its base? The
 * same policy as evaluateIssueMergeGate, judged as if the forge said
 * `mergeable`. Approval must stand at the head: a marker, else a GitHub review
 * of the head read directly (withForgeApprovalAtHead skips unmergeable PRs).
 */
export async function evaluateConflictRepairGate(
  issueId: string,
  deps: MergeGateDeps = {},
): Promise<ConflictRepairGateResult> {
  const facts = deps.getFacts ? await deps.getFacts(issueId) : await getPrFacts(issueId);
  if (facts.error || !facts.open || facts.mergeable !== false) {
    return { conflicting: false, reason: facts.error ?? 'PR is not conflicting', facts };
  }
  if (facts.draft || facts.changesRequested || facts.checks !== 'green') {
    return { conflicting: false, reason: 'PR is not otherwise merge-ready', facts };
  }
  let approvedAtHead = facts.approvedAtHead === true;
  if (!approvedAtHead && facts.forge === 'github') {
    approvedAtHead = (await forgeApprovalAtHead(facts, deps.readReviews, deps.overdeckLogins)) === true;
  }
  const asMergeable: PrFacts = { ...facts, mergeable: true, ...(approvedAtHead ? { approvedAtHead: true } : {}) };
  const ciTestsRequired = facts.forge === 'github' && (deps.ciTestsRequired ?? issueRunsTestsOnCi)(issueId);
  let uatRequired = false;
  if (facts.uatVerdict?.status === 'failed') {
    try { uatRequired = await (deps.uatRequired ?? defaultUatRequired)(issueId); } catch { uatRequired = true; }
  }
  const readiness = evaluateMergeReadiness(asMergeable, { ciTestsRequired, uatRequired, requireApprovalAtHead: true });
  return readiness.ready ? { conflicting: true, facts } : { conflicting: false, reason: readiness.reason, facts };
}

/**
 * PAN-4384: does the PR's approval stand at its current head? `true` when a
 * marker or a GitHub review names the head, `false` when the forge proves it
 * does not (the head moved since the approving review), `undefined` when it
 * cannot tell (lookup failed, GitLab, no PR).
 */
export async function readApprovalStandsAtHead(
  issueId: string,
  deps: Pick<MergeGateDeps, 'getFacts' | 'readReviews' | 'overdeckLogins'> = {},
): Promise<boolean | undefined> {
  const facts = deps.getFacts ? await deps.getFacts(issueId) : await getPrFacts(issueId);
  if (facts.error || !facts.open) return undefined;
  if (facts.approvedAtHead === true) return true;
  if (facts.forge !== 'github') return undefined;
  return forgeApprovalAtHead(facts, deps.readReviews, deps.overdeckLogins);
}
```

Import `forgeApprovalAtHead` from `./pr-facts.js` (already exported at `pr-facts.ts`
`export async function forgeApprovalAtHead(`). Do not edit `pr-facts.ts`.

Tests (inject `getFacts`, `readReviews`, `overdeckLogins`, `ciTestsRequired`, `uatRequired`):

  if (process.env.OVERDECK_DISABLE_CONFLICT_REPAIR === '1') return false;
  if (isPeerDashboardProcess()) return false;
