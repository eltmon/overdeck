# PAN-4249 — Reasoning effort, end to end (program PRD + foundation slice)

**Issue:** [PAN-4249](https://github.com/eltmon/overdeck/issues/4249). The code audit with `file:line` citations is the first comment on the issue (HEAD `e9e8935b77a`, 2026-09-27). Every reference below was re-checked on this branch at `44f70f41000`.

**Consolidates:** #1142, #3919, #480 (partly obsolete: it proposes a `medium` default, which the `effort-high-default` rule forbids).

## How this issue is split

The whole program touches roughly 70 files across the CLI, library, dashboard server, dashboard frontend, contracts package, and docs. The plan-finalize surface lint caps one xBRIEF at 25 files. The work also splits cleanly by launch surface. So:

- **This issue (PAN-4249) ships the foundation**: one `EffortLevel` in `packages/contracts`, one `resolveEffort` module with the full precedence chain and clamping, effort config keys that are validated in one place, the `pan start` work path and definition-less role runs wired through the resolver, a lint ratchet against new fallbacks and enum copies, and the configuration docs page.
- **Eight sibling issues** each take one vertical slice. Every sibling is blocked by PAN-4249, because each one calls `resolveEffort` and imports the contracts enum. See [Sibling issues](#sibling-issues) for the map.

## Glossary

- **Effort** — the reasoning-effort level passed to a harness. The canonical levels, lowest to highest, are `low`, `medium`, `high`, `xhigh`, `max`.
- **Harness** — the coding-agent CLI or runtime that runs a model: `claude-code`, `codex`, `acp`, `opencode`, `kimi-code`, `ohmypi` (legacy alias `pi`), `muse`. Type `RuntimeName` in `src/lib/runtimes/types.ts`.
- **Launch surface** — any code path that starts or restarts an agent or conversation (for example `pan start`, a review convoy lane, a conversation resume).
- **Resolver** — the new `resolveEffort()` function in `src/lib/agents/resolve-effort.ts`. It is the only place that decides which effort a launch uses.
- **Source** — the precedence layer the resolved effort came from (`EffortSource`): `explicit`, `item`, `plan`, `tier`, `sub-role`, `role`, `project`, `default`.
- **Clamp** — replacing a requested canonical level with a supported canonical level when the model or the harness does not accept the requested one. Clamping never produces a non-canonical value.
- **Translate** — mapping a canonical level to a harness-native value (for example Kimi maps `medium`→`high`, `xhigh`/`max`→`max` in `src/lib/kimi-effort.ts`). Translation stays in harness adapters and is not the resolver's job.
- **Per-item override** — `metadata.effort` on one xBRIEF plan item (same home as the per-bead `metadata.model` override).
- **Per-issue override** — `plan.metadata.effort` in the issue's xBRIEF (same home as `plan.metadata.tiered_execution`).
- **Tier** — a named entry in `tiered_execution.tiers.<name>` (`src/lib/agents/tier-table-types.ts`). `resolveTier` maps an item's difficulty to a tier name.
- **Definition-less role run** — a role launch with no `roles/<role>.md` definition file, for example review convoy sub-roles and the tier supervisor. Built by `getRoleRuntimeBaseCommand` in `src/lib/agents/runtime-command.ts`.
- **Ratchet** — a lint that records today's count of a banned pattern per file and fails when any file's count goes up.

## Problem (foundation scope)

1. **No resolver.** Effort is resolved ad hoc. The three fallbacks in `src/lib/agents/runtime-command.ts` are:
   - line 111: `piEffort: effort ?? 'high',` (in `getOhmypiLauncherFields`)
   - line 201: `codexEffort: effort ?? 'high',` (in `getCodexLauncherFields`)
   - line 929: `` const effortFlag = !definitionPath ? ` --effort ${effort ?? 'high'}` : ''; `` (in `getRoleRuntimeBaseCommand`)
   Ten more `?? 'high'` sites live in conversation, launcher, codex, acp, kimi, and flywheel code (audit section 1). The siblings remove those.
2. **Enum copies.** `EffortLevel` is declared in `src/lib/model-capability-types.ts:26`. `ROLE_EFFORTS` is a separate array literal at `src/lib/config-yaml/schema.ts:380`. `FlywheelEffort` repeats the literal list at `packages/contracts/src/flywheel.ts:13` and `:17`. The dashboard frontend cannot import `src/lib`, so it has its own copies too.
3. **Config is mostly ignored.** `roles.<role>.effort` is validated for every role but read only by `pan start` for `work` (`src/cli/commands/start.ts:750`: `const resolvedEffort: RoleEffort | undefined = options.effort ?? yamlConfig.roles?.work?.effort;`). Sub-roles (`RoleSubConfig`, `schema.ts:375-377`), tiers (`TierDefinition`, `tier-table-types.ts:35-50`) and projects (`ProjectConfig`, `src/lib/projects.ts:360`) carry no effort.
4. **Validation is duplicated.** `validateRoleFields` in `src/lib/config-yaml/roles.ts:297-299` and `:344-350`, and `validateRoleFields` plus the model-aware block in `src/lib/settings-api.ts:512-515` and `:583-609` each re-implement the same checks.
5. **An explicit unsupported level is a hard error.** `pan start --effort max` on a model without `max` exits 1 (`start.ts:756-762`). The issue asks for clamping with a warning.

## Decisions

- **D1 — Decompose.** PAN-4249 ships the foundation. The eight siblings listed below ship the surfaces.
- **D2 — One enum.** `packages/contracts/src/effort.ts` owns `EFFORT_LEVELS`, `EffortLevel`, `DEFAULT_EFFORT`, `EffortSource`, `EffortLevelSchema`, `isEffortLevel`, and `compareEffort`. `src/lib/model-capability-types.ts` re-exports `EffortLevel` from `@overdeck/contracts`. `ROLE_EFFORTS` becomes `EFFORT_LEVELS`. `FlywheelEffort` becomes `EffortLevelSchema`. The frontend copies (`EffortPicker.tsx`, `ModelPicker.tsx`, `PlanDialog.tsx`) move in their owning siblings, because the frontend already imports `@overdeck/contracts`.
- **D3 — Precedence chain** (highest first): `explicit` (CLI flag or API body, and a conversation's stored effort when the caller passes it) → `item` (`item.metadata.effort`) → `plan` (`plan.metadata.effort`) → `tier` (`tiered_execution.tiers[tierName].effort`) → `sub-role` (`roles.<role>.sub.<subRole>.effort`) → `role` (`roles.<role>.effort`) → `project` (`projects.yaml` `<project>.effort`) → `default` (`high`).
- **D4 — Per-issue override home is the xBRIEF, not an issue record.** PAN-3917 deleted the per-issue record on purpose ("Overdeck stores no status it can derive"; see `resolveIssueWorkModel` in `src/lib/agents/staffing.ts:85`, which now always returns `undefined`). The derivable homes are `plan.metadata.effort` and per-item `metadata.effort`, both committed in git. This slice adds no issue-record field.
- **D5 — The resolver takes a tier name, not a difficulty.** `resolveTier` already maps difficulty to a tier. The resolver reads `tiers[tierName].effort` and never re-resolves a tier.
- **D6 — Clamp, don't translate.** The resolver clamps canonical→canonical only. The supported set is the intersection of the model's levels (`getModelEffortLevels(model)`, `src/lib/model-capabilities.ts:1391`) and the harness's levels (new `HarnessBehavior.effortLevels`). An `undefined` or empty list means "no restriction", which matches `roles.ts:346` (`supported.length > 0`). Rule: if the requested level is supported, use it. Otherwise use the highest supported level below the requested one. If no supported level is below it, use the lowest supported level. The result sets `clamped: true` and a `warning` string. If the intersection is empty, return the requested level unclamped with a warning.
- **D7 — Config stays strict; runtime input clamps.** A config value (`roles.*`, `sub.*`, `tiers.*`, project) that its statically resolved model cannot run is still rejected at config load, which is today's behavior and what `src/lib/__tests__/config-yaml-roles.test.ts` and `src/lib/__tests__/settings-api.test.ts` assert. An explicit runtime value (`pan start --effort`) that the launch model or harness cannot run is clamped with a warning printed to stderr. An explicit value outside the five canonical levels is still an error (exit 1).
- **D8 — Harness capability table.** Add `effortLevels?: readonly EffortLevel[]` to `HarnessBehavior` in `packages/contracts/src/harness-behavior.ts`. Set `ohmypi` and `muse` to `["low","medium","high","xhigh"]`. Leave every other harness `undefined` (all five). Kimi and opencode translation stays in their adapters (D6).
- **D9 — Role-file frontmatter stays as documentation.** `roles/*.md` `effort: high` frontmatter is still read by `roleSystemPromptInjection` when no effort is passed (`runtime-command.ts:842`). This slice always passes a resolved effort on the paths it touches, so frontmatter no longer decides those launches. Siblings do the same for theirs. No role file changes in this slice.
- **D10 — `effort-high-default` rule wording is unchanged.** The resolver's `default` layer is `high`. No default anywhere becomes `xhigh` or `max`.
- **D11 — Ratchet shape.** `scripts/lint-effort.sh` counts banned patterns per file and compares them to a baseline embedded in the script. A file whose count goes up fails. A file whose count goes down prints a note to lower the baseline. It does not fail, so parallel siblings don't conflict on baseline lines.
- **D13 — Leaf module for shared helpers.** `supportedEffortLevels`, `clampEffort` and `effortConfigErrors` live in `src/lib/agents/effort-support.ts`, which imports no config module, so the config validators can use them without an import cycle (see W2a).
- **D12 — Conversation effort is an `explicit` input.** Conversations have no role, tier, or plan. Conversation callers pass `conversations.effort` as `explicit`, or omit it to get `project`→`default`. The conversation sibling does this wiring.

## Requirements

- **FR-1** One canonical effort enum lives in `packages/contracts/src/effort.ts`. `src/lib/model-capability-types.ts`, `src/lib/config-yaml/schema.ts` and `packages/contracts/src/flywheel.ts` derive from it and declare no literal list of their own.
- **FR-2** `resolveEffort(input)` returns `{ effort, source, requested, clamped, warning? }` following the precedence chain in D3.
- **FR-3** `resolveEffort` clamps to the model∩harness supported set using the rule in D6.
- **FR-4** `effort` is accepted and validated on `roles.<role>.sub.<name>`, `tiered_execution.tiers.<name>`, and `projects.yaml` `<project>` entries. Validation uses one shared helper.
- **FR-5** `pan start` resolves work effort through `resolveEffort`. An explicit unsupported level is clamped with a stderr warning instead of exiting.
- **FR-6** `getRoleRuntimeBaseCommand`, `getCodexLauncherFields` and `getOhmypiLauncherFields` resolve their effort through `resolveEffort`. Definition-less role runs therefore honor `roles.<role>.sub.<subRole>.effort` and `roles.<role>.effort`.
- **FR-7** `npm run lint` includes `lint:effort`, which fails when any file gains an effort fallback or an effort enum copy beyond its baseline.
- **FR-8** A user-facing configuration page documents the effort levels, the precedence chain, every config key, clamping, and the high default.
- **NFR-1** No behavior change for a config with no effort keys: every touched launch still emits `high`.
- **NFR-2** The resolver is synchronous and does no child-process I/O, so server-reachable code may call it (no `execSync` rule). Project lookup reads `projects.yaml` through the existing sync reader.
- **NFR-3** `start.ts` and `runtime-command.ts` must not grow past their `scripts/file-size-allowlist.txt` ceilings (1283 and 961 lines). Any growth needs an audited allowlist row `<lines> <path> # PAN-4249` in the same commit.

   /** Canonical reasoning-effort levels, lowest to highest (PAN-4249). */

   export type EffortLevel = (typeof EFFORT_LEVELS)[number]
   /** The only default. Never xhigh or max (sync-sources/rules/effort-high-default.md). */

   export function compareEffort(a: EffortLevel, b: EffortLevel): number {

API:
```ts
import { DEFAULT_EFFORT, EFFORT_LEVELS, compareEffort, getHarnessBehavior, isEffortLevel,
  type EffortLevel, type EffortSource } from '@overdeck/contracts';
import type { NormalizedConfig, Role } from '../config-yaml/schema.js';
import type { RuntimeName } from '../runtimes/types.js';

export interface ResolveEffortInput {
  explicit?: string | null;          // CLI flag / API body / conversation's stored effort
  itemEffort?: unknown;              // xBRIEF item.metadata.effort
  planEffort?: unknown;              // xBRIEF plan.metadata.effort
  tierName?: string;                 // already-resolved tier (D5)
  role?: Role;
  subRole?: string;
  projectEffort?: EffortLevel;       // caller-supplied, OR looked up from issueId
  issueId?: string;                  // used only to look up the project when projectEffort is absent
  model?: string;
  harness?: RuntimeName | 'pi';
  config?: Pick<NormalizedConfig, 'roles' | 'tieredExecution'>;  // injectable; defaults to loadConfigSync().config
}

export interface ResolvedEffort {
  effort: EffortLevel;          // what to launch with (clamped)
  source: EffortSource;         // layer that supplied `requested`
  requested: EffortLevel;       // pre-clamp value
  clamped: boolean;
  warning?: string;             // set when clamped, or when the supported set is empty
}

export class InvalidEffortError extends Error {}  // explicit value that is not a canonical level

export function resolveEffort(input: ResolveEffortInput): ResolvedEffort;
```

1. `explicit`: `undefined`, `null` and `''` mean "not set". A non-canonical string throws `InvalidEffortError` with the message `Invalid effort '<v>'. Expected one of low, medium, high, xhigh, max.`

3. `tier`: `config.tieredExecution?.tiers?.[tierName]?.effort`.
4. `sub-role`: `config.roles?.[role]?.sub?.[subRole]?.effort`.
5. `role`: `config.roles?.[role]?.effort`.
6. `project`: `projectEffort`, else when `issueId` is set, look up `const resolved = resolveProjectFromIssueSync(issueId)` (`src/lib/projects.ts:857`; returns `ResolvedProject { projectKey, ... }` at `:476`, with no config field) and read `loadProjectsConfigSync().projects[resolved.projectKey]?.effort` (`:512`). Wrap the lookup in `try/catch` so that a failure falls through to `default`. A non-canonical project value is ignored (it falls through), and the result's `warning` says `projects.<key>.effort '<v>' is not a valid effort level; ignored.`
7. `default`: `DEFAULT_EFFORT`.
8. (Implemented in `effort-support.ts`, W2a.) Clamp with `supportedEffortLevels(model, harness)`. It intersects `getModelEffortLevels(model)` (treat `undefined` or `[]` as all five) with `getHarnessBehavior(harness).effortLevels` (treat `undefined` as all five). Then apply the D6 rule. Warning text: `Effort '<requested>' is not supported by <model>/<harness>; using '<effort>'.`
9. (Implemented in `effort-support.ts`, W2a.) `effortConfigErrors(fieldPath, effort, models)` returns `[]` when `effort` is `undefined`. It returns `["<fieldPath>.effort must be one of low, medium, high, xhigh, max"]` for a non-canonical value. For each model whose non-empty `getModelEffortLevels` list lacks the value, it returns `"<fieldPath>.effort '<v>' is not supported by <model> (supported: a, b)"`.
