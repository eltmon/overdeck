# PAN-4670 — Simple issue page: CSRF on every simple action, and no "Start work" while a work agent runs

**Issue:** [PAN-4670](https://github.com/eltmon/overdeck/issues/4670)
**Status:** planned (auto mode, 2026-11-01)

## Glossary

- **Simple mode** — the plain-English dashboard surface (`SimpleHomePage`, `SimpleIssuePage`, `NeedsYouStrip`). It projects the internal pipeline onto five user-facing states (`not-started`, `working`, `needs-you`, `ready`, `done`) in `src/dashboard/frontend/src/lib/simple/userFacingState.ts`.
- **`postJson`** — the private helper in `src/dashboard/frontend/src/lib/simple/useSimpleActions.ts` that every simple-mode mutation (`tell`, `answer`, `recover`, `unpause`, `merge`, `startWork`, `startPlanning`) uses to POST to the dashboard server.
- **CSRF header** — `x-overdeck-csrf-token` (`DASHBOARD_CSRF_HEADER`, `src/dashboard/server/routes/dashboard-auth.ts` line 18). A browser mutation carrying a session cookie but no matching header gets `403 { error: 'Invalid CSRF token' }` from `rejectUnsafeDashboardMutationRequest` (same file, line 207; the 403 is at line 227).
- **`dashboardMutationJsonHeaders()`** — `src/dashboard/frontend/src/lib/wsTransport.ts` lines 155-162. It awaits `ensureDashboardSession()`, then returns `{ 'Content-Type': 'application/json', 'x-overdeck-csrf-token': <token> }`, or throws `Dashboard CSRF token unavailable`. Call it with **no argument** (a relative REST path would throw inside `new URL(...)`).
- **Pipeline state** — `PipelineState` from `src/dashboard/frontend/src/lib/issuePipelineState.ts`, computed by `derivePipelineState({ derived, panes, issueCanonicalState })`.
- **Derived state** — `DerivedIssueState.state` from the server (`src/lib/overdeck/derived-issue-state.ts`, `deriveState`, lines 160-193).
- **Live pane** — a `BackendPane` whose `state` is `idle`, `working` or `blocked` (`isPaneLive`, `issuePipelineState.ts` line 40). `hasLivePane(panes, role)` is at line 44.
- **Bare turn end** — `isBareTurnEnd(agent)` in `derive.ts`: the agent's only pending signal is `agentTurnEnded`. It stopped talking; it asked nothing.
- **Plan-ready card** — the simple display `{ state: 'needs-you', title: 'The plan is ready', primaryAction: 'Start work', needsYouReason: 'start-work' }` (`BASE_BY_PIPELINE_STATE.planning_done_awaiting_work`).
- **Pre-work pipeline state** (new term) — `generic`, `planning_active` or `planning_done_awaiting_work`: the states `derivePipelineState` returns when the derived state is missing, `backlog`/`parked`, or `planned`. None of them consults a live work pane.
- **Work agent exists** (new term, defined by FR-3) — a live `work` pane for the issue, or a pipeline state only a work agent can produce (review, ready, merged, done, canceled).

## Problem

The operator opened PAN-4643 in simple mode on 2026-11-01. The page said **"The plan is ready. The plan is written and nothing is running. Nothing starts until you say go."** with a **Start work** button, while `agent-pan-4643` was working (its activity log on the same page showed tool calls two minutes old). Clicking **Start work** failed with an "Invalid CSRF token" dialog.

There are two independent defects.

### Defect 1: every simple-mode mutation fails the CSRF check

`src/dashboard/frontend/src/lib/simple/useSimpleActions.ts` lines 14-19:

```ts
async function postJson(url: string, body?: unknown): Promise<unknown> {
  const res = await fetch(url, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: body === undefined ? undefined : JSON.stringify(body),
  });
```

It sends no `x-overdeck-csrf-token` and no `credentials: 'include'`, so the server rejects every simple action with 403. The other surfaces already do it right, for example `src/dashboard/frontend/src/components/issue-view/StartAgentCta.tsx` line 35:

```ts
const response = await fetch(url, { method: 'POST', credentials: 'include', headers: await dashboardMutationJsonHeaders(), body: JSON.stringify(payload) });
```

### Defect 2: a finished-but-alive planner overrides a running work agent

`src/dashboard/frontend/src/lib/simple/derive.ts` lines 124-128:

```ts
export function isPlanReadyToStart(issue: Issue, pendingInputAgent: AgentSnapshot | undefined): boolean {
  if (issue.hasPlan !== true) return false;
  if (!pendingInputAgent || pendingInputAgent.role !== 'plan') return false;
  return isBareTurnEnd(pendingInputAgent);
}
```

`userFacingState.ts` `baseStateFor` returns `planning_done_awaiting_work` whenever `planReadyToStart` is true, ahead of the real `pipelineState`. PAN-4643's planner stayed alive at its prompt after finalize, so the card offered Start work while `pipelineState` was `in_progress_work_running`.

### A second trap the issue body does not mention

Making `isPlanReadyToStart` return false is **not enough**. In `deriveSimpleIssue` (`derive.ts` line 137) `pendingInputAgent = agents.find(hasPendingInput)` still picks the idle planner, so `pendingInput` stays true. In `userFacingState.ts`, `showsQuestion(input)` returns `pendingInput && planReadyToStart !== true`, which becomes **true**, and the page would render **"Question for you / Answer"** with an answer box aimed at the idle planner. The work-running card would still not appear. Once a work agent exists, a plan agent's bare turn end must not count as pending input at all.

### Why the issue's suggested rule ("any `in_progress_*` state means work exists") is wrong

`pan plan finalize` commits the PRD and spec to the feature branch. That makes the branch ahead of `origin/main` with no work agent ever started. The server's `deriveState` (`derived-issue-state.ts` lines 186-188) then returns `'working'`:

```ts
  if (livePanes.length > 0) return 'working';
  if (facts.branch && facts.branch.aheadOfMain > 0) return 'working';
```

Any live pane counts too, including an idle planner's. With no live work pane, `derivePipelineState` maps `'working'` to `in_progress_work_idle`. So the realistic shape of "plan finished, nothing started" is `in_progress_work_idle`, not `planning_done_awaiting_work`. Verified on 2026-11-01: `feature/pan-1224`, `feature/pan-1832`, `feature/pan-1894`, `feature/pan-1901`, `feature/pan-1934` and `feature/pan-2093` are ahead of `origin/main` with changes only under `.pan/`. Treating `in_progress_work_idle` as "work exists" would remove the plan-ready card in exactly the case it exists for. The existing plan-ready tests all use `derived('planned')`, which hides this.

## Requirements

- **FR-1** — Every simple-mode mutation sends `credentials: 'include'` and the headers returned by `await dashboardMutationJsonHeaders()` (which include `x-overdeck-csrf-token`).
- **FR-2** — A non-2xx response keeps its existing handling: a 409 with a resumable lifecycle opens the Resume / Start fresh dialog; any other failure throws an `Error` whose message is the server's `error` field. If `dashboardMutationJsonHeaders()` throws, the mutation fails with that error and the existing `onError` alert shows it.
- **FR-3** — A work agent exists for an issue when `hasLivePane(panes, 'work')` is true, or `pipelineState` is one of `in_review_reviewers_running`, `in_review_changes_requested`, `in_review_approved`, `ready_to_merge`, `merged`, `done`, `canceled`. `in_progress_work_idle` alone does not count.
- **FR-4** — `isPlanReadyToStart` returns false whenever a work agent exists (FR-3).
- **FR-5** — Once a work agent exists, a `role: 'plan'` agent at a bare turn end is not pending input: `deriveSimpleIssue` neither selects it as `pendingInputAgent` nor reports `pendingInput: true` because of it. A real question (AskUserQuestion, proposed plan, permission prompt, or a confident `asks_operator` turn-end assessment) still counts.
- **FR-6** — With no work agent, a written plan plus an idle plan agent at a bare turn end still yields the plan-ready card, in both the `derived('planned')` shape and the production `derived('working')` + no-work-pane shape.
- **FR-7** — The CI frontend subset runs the `useSimpleActions` tests.
- **FR-9** — When a live work pane exists and `derivePipelineState` returns a pre-work state (derived state missing, or still `planned` because the server read lags the pane inventory), simple mode uses `in_progress_work_running` instead, for the display, the rail and the returned `pipelineState`. A live work pane outranks a derived state that has not caught up.
- **FR-8** — Docs state the browser-mutation CSRF contract for simple mode and the plan-ready rule.
- **NFR-1** — No new server routes, no new store fields, no change to `SimpleIssuePage.tsx`, `SimpleHomePage.tsx` or `NeedsYouStrip.tsx` (they consume `deriveSimpleIssue` and `useSimpleActions` unchanged).
- **NFR-2** — No file grows past its `origin/main` line count plus the change itself; none of the touched files is near a file-size cap (largest is `derive.ts` at 230 lines).

## Decisions

1. **Rule for "work agent exists" (FR-3).** Live work pane, or a post-work pipeline state. Not `AgentSnapshot.status`: the terminal backend's pane inventory is the authority ("Overdeck stores no status it can derive"), and the issue body names the live work pane.
2. **`in_progress_work_idle` does not prove a work agent.** See "Why the issue's suggested rule is wrong" above. This deviates from the literal issue text on purpose; the issue's own third acceptance criterion ("with no work agent, the same idle-planner input still yields 'The plan is ready'") requires it.
3. **`generic` does not prove a work agent.** `generic` means the derived state has not loaded or is `backlog`/`parked`. Flipping the card off on missing data would be a guess.
4. **`isPlanReadyToStart` gets a third, required parameter** `workAgentExists: boolean`. A default would let a future call site silently reintroduce the bug. The one existing direct call (`simple-derive.test.ts` line 74) passes `false`.
5. **The pending-input fix lives in `deriveSimpleIssue`**, not in `userFacingState.ts`. `userFacingState.ts` stays a pure projection of its inputs; only its doc comment on `planReadyToStart` changes.
6. **`pendingInputAgent` skips the idle planner once work exists.** This changes the exported field only in that case. Its consumers (`SimpleHomePage.tsx` line 79, `NeedsYouStrip.tsx` lines 42 and 168, `SimpleIssuePage.tsx` line 73) read it only for needs-you items and question answering, so skipping a planner that asked nothing is correct for all of them, and it lets a real question from a later agent in the array be found.
7. **A dead work agent is out of scope.** If the work pane exited and the planner is still idle at a bare turn end, the card still says the plan is ready and offers Start work. `POST /api/agents` then answers 409 with a resumable lifecycle, and `postJson` already routes that into the Resume / Start fresh dialog, which is the right next step.
9. **The live-work-pane override (FR-9) lives in `derive.ts`, not in `derivePipelineState`.** `issuePipelineState.ts` is shared with Advanced mode and other surfaces; this issue changes only the simple-mode projection. The override applies only to pre-work states, so a review/ready/merged/done/canceled state is never rewritten.
8. **`useSimpleActions.test.tsx` mocks `../wsTransport`.** `wsTransport.ts` keeps `dashboardSessionPromise` and `dashboardCsrfToken` at module scope, so a test that runs the real module leaks state across cases. Mock it the way `src/dashboard/frontend/src/components/SyncRequiredBanner.test.tsx` line 5 does.
