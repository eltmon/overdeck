# PAN-4328: Session Vault passphrase unlock (keywrap/v1)

**Issue:** https://github.com/eltmon/overdeck/issues/4328
**Design:** `.pan/drafts/anywhere-accounts.md` §6.5 (lines 204-220) and N1 (lines 322-352)
**Parent:** PAN-2350. **Depends on:** PAN-2609 Phase A (merged as `7150767e255`).

## Glossary

| Term | Meaning |
| --- | --- |
| **Vault key `K`** | 32 random bytes at `${OVERDECK_HOME}/vault/key` (mode 0600). Created by `createVaultKey()` in `src/lib/vault/identity.ts`. Everything in the vault is encrypted with sub-keys derived from `K`. |
| **Recovery phrase** | The 24-word BIP-39 encoding of `K` (`keyToPhrase` / `phraseToKey` in `identity.ts`). Shown once at setup. It stays the root of recovery. |
| **Vault passphrase** | A human secret the user chooses (or accepts as generated). It never leaves the machine and is never stored. |
| **KEK** | Key-encryption key: `scrypt(passphrase, salt, 32, {N, r, p, maxmem: 256 MiB})`. |
| **Keywrap** | The object `keywrap/v1`: `K` encrypted with the KEK using AES-256-GCM. Stored on the backend, readable by nobody without the passphrase. |
| **Backend / `VaultStore`** | The interface in `src/lib/vault/store/types.ts`. Implementations: `DirVaultStore` (`store/dir.ts`, `dir:<path>` URLs) and `GitVaultStore` (`store/git.ts`, git remotes). The hosted `overdeck://` store (PAN-4297) does not exist yet. |
| **Reserved object name / slot** | An object name that is not a content id. `KEYWRAP_OBJECT_NAME = 'keywrap/v1'` is the only one (`types.ts`, search `export const KEYWRAP_OBJECT_NAME`). Stored at `objects/keywrap/v1`. |
| **`putSlot`** | New `VaultStore` operation added by this issue: overwrite or delete a reserved slot and publish the change immediately. |
| **EFF long wordlist** | The 7776-word diceware list from https://www.eff.org/files/2016/07/18/eff_large_wordlist.txt (sha256 `addd35536511597a02fa0a9ff1e5284677b8883b83e986e43f15a3db996b903e`, first word `abacus`, last `zoom`, all lowercase `[a-z-]`, 4 words contain `-`). Six words ≈ 77.5 bits. License CC BY 3.0 US. |
| **`CliIo`** | Injectable I/O used by every `pan vault` verb (`src/cli/commands/vault/shared.ts`). Tests use `captureIo()` from `tests/unit/cli/vault/helpers.ts`, whose `readLine` returns queued `answers` and ignores the prompt text. |

## Problem

A second machine joins a vault only by typing the 24-word recovery phrase (`pan vault join`, `src/cli/commands/vault/join.ts`). In the dual-boot case no other device is online to approve the new one, so the phrase is the only way in, and most people will not have it at hand. The flow fails at the step that matters most.

## Current state (verified 2026-09-29 against `7150767e255`)

- `src/lib/vault/store/types.ts`: `KEYWRAP_OBJECT_NAME = 'keywrap/v1'`, `RESERVED_OBJECT_NAMES`, and `objectRelativePath(id)` returns the name itself for reserved slots. Comment: "Phase A never writes it; reserving the name now means PAN-4328 lands without a format bump."
- `putObjects` on both backends **skips an id whose file already exists** (`dir.ts` and `git.ts`, search `if ((await readOrNull(path)) !== null) continue;`). So `putObjects` cannot overwrite a keywrap.
- `GitVaultStore.putObjects` writes files into the clone **without committing**. Only `casRefSerialized` commits and pushes, with `git add -A -- .` (search `'add', '-A', '--', '.'`). So a keywrap written through `putObjects` never reaches the remote until an unrelated settle happens, and it cannot be deleted at all.
- `VaultStore` has no delete operation.
- `tests/unit/lib/vault/store/contract.ts` has the case `'the reserved keywrap/v1 slot stores and reads like an object (PAN-4328 reservation)'`, which writes the slot through `putObjects`.
- `join.ts` reads the phrase **before** opening the store (`key = phraseToKey(await readPhrase(io, options.phraseFile))`), then opens or clones the store, then proves the key by decrypting the header ref (`readVaultHeader`). A wrong phrase prints `PHRASE_MISMATCH_MESSAGE` and removes a clone it created.
- `setup.ts` prints the phrase only when `!existingKey`, after `syncOnce`.
- There is **no dashboard vault UI** (`grep -rl vault src/dashboard` finds nothing) and `tests/unit/lib/vault/import-graph.test.ts` bans `src/dashboard/` imports from `src/lib/vault` and `src/cli/commands/vault`.
- Node 22 `crypto.scrypt` with `N=131072, r=8` **throws "memory limit exceeded" without `maxmem`** (default 32 MiB; the cost is 128·N·r = 128 MiB). With `maxmem: 256 * 1024 * 1024` one derivation took 280 ms on this host.
- `packages/contracts/src/composer-commands.generated.ts` lists every `pan vault` subcommand and option. It is generated by `scripts/generate-slash-commands.mjs` and checked by `scripts/lint-slash-commands.sh`.
- `scripts/lint-skills.sh` (in `npm run lint`) fails when `sync-sources/skills/pan-vault/SKILL.md` drifts from `--help`.

## Requirements

- **FR-1** A new `VaultStore.putSlot(name, bytes | null)` overwrites (bytes) or deletes (`null`) a reserved slot and publishes immediately on every backend. It rejects names outside `RESERVED_OBJECT_NAMES`.
- **FR-2** `putObjects` rejects reserved names, so nothing can write a slot through the immutable path.
- **FR-3** `src/lib/vault/keywrap.ts` wraps `K` under a passphrase into the exact `keywrap/v1` encoding below and unwraps it; a wrong passphrase returns `null` after a local GCM failure.
- **FR-4** A typed passphrase shorter than 16 characters (after normalization) is refused with `PASSPHRASE_LENGTH_MESSAGE`; one on the blocklist or with fewer than 6 distinct characters is refused with `PASSPHRASE_COMMON_MESSAGE`.
- **FR-5** `generatePassphrase()` returns 6 words drawn uniformly from the EFF long wordlist with `crypto.randomInt`, joined by single spaces.
- **FR-6** `pan vault passphrase set [--passphrase-file <path>] [--generate]` writes `keywrap/v1`; `pan vault passphrase remove` deletes it. `K` never changes.
- **FR-7** `pan vault setup` offers passphrase unlock after the recovery phrase is shown, with `--passphrase-file`, `--generate-passphrase` and `--no-passphrase` for non-interactive use.
- **FR-8** `pan vault join` reads `keywrap/v1` first and asks for the passphrase when it exists; an empty answer falls back to the recovery phrase. A wrong passphrase prints `PASSPHRASE_MISMATCH_MESSAGE`, writes nothing, and reads nothing else from the backend.
- **FR-9** Docs: a "Passphrase unlock" section in `docs/SESSION-VAULT.md` and `configuration/session-vault.mdx`, and the skill `sync-sources/skills/pan-vault/SKILL.md`.
- **NFR-1** `node:crypto` only (PAN-2609 NFR-9). Async `crypto.scrypt` (promisified), never `scryptSync`: the dashboard may call this later and must not block its event loop.
- **NFR-2** No `execSync` anywhere; git calls stay on the existing promisified `execFile` helper in `git.ts`.
- **NFR-3** The backend never holds `K`, the KEK or the passphrase in any form other than the GCM ciphertext.
- **NFR-4** The vault stays standalone: new modules import only Node built-ins and sibling vault modules (`import-graph.test.ts` must keep passing).
- **NFR-5** No new file under `src/` exceeds 1000 lines (`scripts/lint-file-size.sh`), and no existing file grows past its `origin/main` count or allowlist cap.

## The `keywrap/v1` encoding (decided)

UTF-8 JSON, exactly these eight keys, no others:

```json
{"v":1,"kdf":"scrypt","N":131072,"r":8,"p":1,"salt":"<base64 16 bytes>","nonce":"<base64 12 bytes>","ct":"<base64 48 bytes>"}
```

- `ct` = AES-256-GCM ciphertext of `K` (32 bytes) followed by the 16-byte auth tag (48 bytes total).
- GCM associated data = the UTF-8 bytes of `"overdeck-vault-keywrap-v1"`.
- `KEK = scrypt(normalize(passphrase), salt, 32, { N, r, p, maxmem: 256 * 1024 * 1024 })`. `maxmem` is mandatory (see Current state).
- `normalize(p)` = `p.normalize('NFKC').trim().replace(/\s+/g, ' ')`. Wrap, unwrap and the strength check all use the normalized form.
- **Parse validation before any scrypt call** (a malicious backend must not be able to make the client allocate unbounded memory): `v === 1`; `kdf === 'scrypt'`; `N`, `r`, `p` are integers; `N` is a power of two with `2**14 <= N <= 2**20`; `1 <= r <= 16`; `1 <= p <= 4`; `128 * N * r * p <= 256 * 1024 * 1024`; `salt` decodes to 16 bytes, `nonce` to 12, `ct` to 48; no extra keys. Any failure throws `KeywrapFormatError`.

## Decisions

- **D-1 Slot write is a new store operation.** `putSlot(name, bytes | null): Promise<void>` on `VaultStore`. Rationale: `putObjects` is immutable-by-id and the git backend publishes only inside `casRef`; neither can overwrite, delete or publish a slot. PAN-4297's HTTP store will implement the same method (a PUT/DELETE on the slot). Last write wins: no CAS on the slot, because two machines setting a passphrase at the same moment is not a real conflict (both wrap the same `K`).
- **D-2 `putObjects` rejects reserved names** with `Error('Reserved vault object ${name} must be written with putSlot')`. The existing contract case that wrote `keywrap/v1` through `putObjects` is rewritten to use `putSlot`.
- **D-3 Git `putSlot` algorithm** (inside the existing `locked()` clone lock, up to `CAS_ATTEMPTS` = 3):
  1. `refreshUnlocked()` (fetch + `reset --hard origin/main`).
  2. For `null`: if the slot file does not exist after the refresh, return immediately (delete-when-absent resolves; `git add` with a pathspec that matches nothing would exit non-zero and the `git()` helper would throw). Otherwise `rm(path, { force: true })`. For bytes: `writeAtomic(path, bytes)`.
  3. `git add -A -- objects/keywrap` (scoped: never `-- .`, so untracked settle objects do not ride along).
  4. `git diff --cached --name-only -- objects/keywrap`; empty stdout means nothing changed (same bytes re-set): return. Do not use `--quiet`: it exits 1 when there are changes and the `git()` helper throws on any non-zero exit.
  5. `git commit --quiet -m "vault: keywrap"` with `COMMIT_IDENTITY`; `git push --quiet origin HEAD:main`.
  6. On push failure: `undoLocalCommit()`, then `resetToRemote()`, then `git clean -fdq -- objects/keywrap` with `.catch(() => undefined)` as `casRefSerialized` does for its clean (a brand-new untracked slot file survives `reset --hard` and would otherwise be swept into the next settle's `add -A -- .`). `isNonFastForward` → next attempt; otherwise throw `VaultOfflineError`. After 3 non-fast-forward attempts throw `VaultOfflineError('Vault keywrap push kept conflicting')`.
  There is no delay between attempts, so no fake timers are needed (the fake-timers rule applies only to delay/backoff code).
- **D-4 Dir `putSlot`:** `writeAtomic(path, bytes)`, or `unlink` tolerating `ENOENT`.
- **D-5 Passphrase prompts echo**, exactly like the existing recovery-phrase prompt (`readPhrase` uses `io.readLine`). Masked input for both prompts is a separate change.
- **D-6 Setup validates `--passphrase-file` before creating anything.** A too-short passphrase exits 1 with `PASSPHRASE_LENGTH_MESSAGE` and no key, clone, config or remote write. This is how AC-3 is met without a half-set-up vault.
- **D-7 Setup offer logic** (runs only when a new key was created, i.e. the phrase was just printed):
  - `passphrase === false` (`--no-passphrase`): nothing.
  - `--passphrase-file`: use it (already validated).
  - `--generate-passphrase`: generate, print once.
  - otherwise, when `io.isTTY`: print `Also unlock with a passphrase on new machines. Suggested: <6 words>` then `io.readLine('Press Enter to use the suggested passphrase, type your own (16+ characters), or type "skip": ')`. Empty answer = the suggestion; `skip` = nothing; a typed passphrase that fails the strength check prints the reason and re-prompts, at most 3 attempts, then prints `PASSPHRASE_LATER_HINT` and skips.
  - otherwise (non-TTY, no flag): print `PASSPHRASE_LATER_HINT` only. This keeps every existing setup test (non-TTY, no answers) unchanged.
  - `--passphrase-file` together with `--generate-passphrase` exits 1 before anything is created: `Use either --passphrase-file or --generate-passphrase, not both.`
  - A `VaultOfflineError` from `putSlot` during setup prints `Could not store the passphrase: <message>. Run: pan vault passphrase set` and setup still exits 0 (the vault itself is set up).
- **D-8 Join order.** With `--phrase-file`: unchanged phrase-first flow (the file is parsed before any backend access). Otherwise: open/clone the store; when the clone already existed, `await store.refresh()` and ignore `VaultOfflineError` (use the local view); `getObject(KEYWRAP_OBJECT_NAME)`; then the passphrase or phrase path. On a wrong passphrase the header is **not** read. On a correct passphrase the header **is** still verified with `readVaultHeader` before `saveVaultKey`.
- **D-9 "No request other than the object read"** means: dir backend — only `getObject('keywrap/v1')` is called on the store (verified with `vi.spyOn(DirVaultStore.prototype, …)`); git backend — the clone/fetch is the read, and there is no commit and no push (the bare remote's `main` sha is unchanged), and a clone that join created is removed.
- **D-10 A malformed keywrap** (`KeywrapFormatError`) prints `KEYWRAP_UNREADABLE_MESSAGE` to stderr and join continues with the recovery phrase.
- **D-11 `--passphrase-file` on a vault with no keywrap** exits 1 with `This vault has no passphrase set. Use the recovery phrase: pan vault join <url> --phrase-file <path>` (and removes a created clone).
- **D-12 Blocklist** (compared after lowercasing and removing every character outside `[a-z0-9]`): `correcthorsebatterystaple`, `passwordpassword`, `password12345678`, `password123456789`, `1234567890123456`, `12345678901234567890`, `qwertyuiopasdfgh`, `qwertyuiopasdfghjkl`, `abcdefghijklmnop`, `abcdefghijklmnopqrstuvwxyz`, `iloveyouiloveyou`, `letmeinletmein`, `trustno1trustno1`, `thequickbrownfoxjumpsoverthelazydog`, `changemechangeme`, `overdeckoverdeck`, `overdecksessionvault`, `myvaultpassphrase`, `thisismypassphrase`, `sessionvaultpassphrase`. Plus: fewer than 6 distinct characters is refused.
- **D-13 Messages (exported constants in `keywrap.ts`):**
  - `PASSPHRASE_LENGTH_MESSAGE = 'A vault passphrase must be at least 16 characters.'`
  - `PASSPHRASE_COMMON_MESSAGE = 'That passphrase is too common or repetitive. Choose another, or use a generated one.'`
  - `PASSPHRASE_MISMATCH_MESSAGE = 'The passphrase did not unlock this vault.'`
  - `KEYWRAP_UNREADABLE_MESSAGE = 'The passphrase unlock object on this backend is unreadable; use the recovery phrase.'`
  - `PASSPHRASE_LATER_HINT = 'Tip: run pan vault passphrase set to unlock new machines with a passphrase instead of the 24 words.'`
- **D-14 Generated passphrases are printed once**, on their own line prefixed `Vault passphrase (shown only now): `.
- **D-15 Test cost.** `wrapVaultKey` takes an optional `params` argument so unit tests use `N = 2**14` (16 MiB, ~35 ms). The CLI always uses `DEFAULT_KEYWRAP_PARAMS = { N: 131072, r: 8, p: 1 }`, and the CLI tests (a handful of derivations at 128 MiB each) run at production params so the acceptance criteria are tested on the real format. The CLI test files add no parallelism of their own.

## Intersecting repo rules (restated)

- No `execSync`; git goes through the promisified `execFile` helper already in `git.ts`.
- Fake timers for retry/backoff/delay tests. The keywrap push retry has **no delay**, so none are needed; do not add a delay.
- `npm run typecheck` excludes test files; always run `npx vitest run <files>` for touched tests.
- Changing `pan vault` flags or help text requires updating `sync-sources/skills/pan-vault/SKILL.md` in the same commit; `scripts/lint-skills.sh` enforces it. New subcommands and options also change `packages/contracts/src/composer-commands.generated.ts`.
- No new `src/` file over 1000 lines; no existing file grows past its `origin/main` count or allowlist cap. Never raise an allowlist cap.
- Vault modules import only Node built-ins and sibling vault modules (`tests/unit/lib/vault/import-graph.test.ts`).
- Never run the full `npm test` on the host.

## Non-goals

- The dashboard unlock screen and the account first-run card: no dashboard vault UI exists and the vault may not import dashboard code. They belong to the account work (PAN-4293 family).
- The hosted `overdeck://` backend and its "serve keywrap only to authenticated devices" rule (PAN-4297). It must implement `putSlot`; nothing here builds it.
- Masked (no-echo) passphrase and recovery-phrase input.
- Showing passphrase state in `pan vault status`.
- OPAQUE/PAKE, a server-held wrapping key, tying unlock to a GitHub login (rejected by the design).
- Rotating `K` or re-encrypting any object.
- Argon2 or any non-`node:crypto` KDF.
