# PAN-4748: Fly API calls use flyctl's stored token, which goes stale until flyctl runs

**Issue:** [PAN-4748](https://github.com/eltmon/overdeck/issues/4748)
**Found in:** the PAN-4296 live check (2026-11-01, `docs/fly-provider.md` "Live verification (PAN-4296)"), and the PAN-4652 live check (its O4 destroy got 403).
**Planned against:** `feature/pan-4748` at `45524993754`. flyctl `v0.4.115` (Commit a1cf49a5, built 2026-10-08) on the planning host.

## Glossary

- **Machines API** — Fly's REST API at `https://api.machines.dev/v1`. Overdeck calls it through `FlyApiClient` in `src/lib/remote/fly-api.ts`.
- **flyctl** — Fly's CLI (`fly` / `flyctl`). Its login lives in `~/.fly/config.yml` under `access_token:`.
- **Stored token** — the `access_token` value in `~/.fly/config.yml`. On this host it is an `fm2_…` macaroon followed by comma-separated **discharge tokens** (3 comma-separated parts, 665 characters). Discharge tokens are short-lived; flyctl refreshes them and writes them back to the file **only when flyctl runs**.
- **Explicit token** — a token Overdeck gets from the environment: the variable `remote.fly.api_token_env` names, else `FLY_API_TOKEN`. Overdeck never refreshes an explicit token.
- **Token source** — new in this issue: the object a `FlyApiClient` asks for the token to send (`current()`) and asks again after an auth rejection (`refresh()`).
- **Auth rejection** — a Machines API answer with HTTP status 401 or 403. The stale stored token answers `403 {"error":"unauthorized"}`.
- **Refresh** — running `flyctl auth token --quiet --json`, which prints `{"token":"<token>"}` after flyctl has refreshed and persisted its tokens (see "Verified flyctl behaviour").
- **Deacon Fly loops** — `heartbeatFlyMachines`, `sweepFlyMachines`, `syncFlyCodexAuth` in `src/lib/remote/fly-machine-loops.ts`, run every 60 s by `src/lib/cloister/hygiene-scheduler.ts` (lines 99-104). Each returns string **loop lines** that `runAndLog` prints as `[hygiene-scheduler] <name>: <line>`.
- **`pollUntil`** — `src/lib/anywhere/fly/provision-shared.ts:55`, the probe loop used by the clone poll, both install polls, the dockerd poll and the health poll.
- **Rollback** — `rollback()` in `src/dashboard/server/services/fly-machine-service.ts:333`, which destroys the VM after a failed `add-fly`.

## Problem

`createFlyApiClient()` (`src/lib/remote/fly-api.ts:344`) takes an explicit token, else `FLY_API_TOKEN`, else the stored token read once by `readFlyctlConfigToken()` (`fly-api.ts:330`). The client keeps that one string for its whole life (`private readonly token: string`, `fly-api.ts:92`). When the stored token's discharge tokens expire and nobody has run flyctl since, every Machines API call answers 403. Nothing in Overdeck refreshes the stored token.

Observed (PAN-4296 run 1, machine `84eee59fe096e8`, app `pan-workspaces`): calls worked 22:32-22:36; from 22:37 every exec answered 403. Three failures followed:

1. **Clone poll hides the 403.** `pollUntil` swallows every probe error (`if (await probe().catch(() => false)) return true;`, `provision-shared.ts:61`), so `ensureFlyProject` (`src/lib/anywhere/fly/project.ts:74`) polled a 403 for the full 20 min and then failed with `project-failed` "did not finish within 20 min".
2. **Rollback destroy fails.** `rollback()` logged `Rollback could not destroy Fly machine …: Fly API error 403` and the VM kept running and billing until destroyed by hand.
3. **The deacon loops go dark.** `heartbeatFlyMachines` lines read `failed to refresh host heartbeat on <label>: Fly API error 403 for POST …` (no cause, no fix); `sweepFlyMachines` swallows the 403 in `reasonToRemove` (`fly-machine-loops.ts:128-131`) and prints nothing; `syncFlyCodexAuth` prints `the Fly machine did not answer` (`fly-machine-loops.ts:222`), which is wrong. With no heartbeat, a Fly machine's watchdog stops it after 300 s and its conversations are lost.

`fly machines list` at 22:55 rewrote `~/.fly/config.yml`, and the file's token answered 200 again.

## Verified flyctl behaviour (planning-time facts)

- `flyctl auth token` is defined in flyctl `internal/command/auth/token.go` (tag `v0.4.115`) with `command.RequireSession`. It is **deprecated and hidden** but present in v0.4.115.
- `RequireSession` (`internal/command/command.go:590-617`, v0.4.115) calls `config.MonitorTokens(ctx, config.Tokens(ctx), tryOpenUserURL)` before the command body runs, unless an env token (`FLY_ACCESS_TOKEN` / `FLY_API_TOKEN`) is set.
- `MonitorTokens` (`internal/config/tokens.go:37-55`) synchronously runs `fetchOrgTokens` and `refreshDischargeTokens(…, 30*time.Second)`, then `SetAccessToken(file, t.All())` when anything changed. So the command refreshes and persists before it prints.
- `RequireSession` refuses (non-interactive: exits non-zero) when the last login is older than `TokenTimeout = 30 * 24 * time.Hour`. Then only `fly auth login` helps.
- On the planning host, `fly auth token --quiet --json` printed exactly `{"token": <string of 665 chars>}` in 0.57 s, and its token's SHA-256 matched the file's `access_token` (both `89c86c6a9fa4…`).
- If `FLY_API_TOKEN` or `FLY_ACCESS_TOKEN` is set in flyctl's environment, flyctl prints that token instead. The refresh must strip both from the child environment.

## Decisions

- **D-1 Refresh on rejection, through flyctl.** When a Machines API call made with the **stored** token gets 401 or 403, the client runs `flyctl auth token --quiet --json`, takes the token from its JSON, and retries the same request once. No proactive refresh timer.
- **D-2 Explicit tokens are never refreshed.** A token from `remote.fly.api_token_env` / `FLY_API_TOKEN` / the `createFlyApiClient(token)` argument gets no retry: a 401/403 throws as today.
- **D-3 The token comes from flyctl's stdout, not a re-read of the file.** The JSON is what flyctl itself would send. Only when the flyctl run fails does the source re-read `~/.fly/config.yml` (another flyctl run may have refreshed it meanwhile).
- **D-4 One refresh at a time, process-wide.** Concurrent rejections share one in-flight refresh (module-level promise). A refresh whose rejected token already differs from the last refreshed token returns the newer token without spawning flyctl.
- **D-5 Failed-refresh cooldown: 60 s.** A refresh that fails (spawn error, non-zero exit, timeout, unparsable output, or the same token back) makes `refresh()` return `null` without spawning flyctl for the next 60 000 ms. Bounds flyctl spawns when the operator is logged out.
- **D-6 Retry once, immediately.** No backoff sleep. A 401/403 means the request was not executed, so retrying a POST (create, exec) is safe.
- **D-7 Binary resolution.** Run `flyctl` from `PATH`; if spawning it fails with `ENOENT`, run `join(homedir(), '.fly', 'bin', 'flyctl')`. Neither ⇒ the refresh fails (D-5).
- **D-8 Spawn async, bounded.** `execFile` (promisified) with `timeout: 30_000`, no stdin, env = `process.env` minus `FLY_API_TOKEN` and `FLY_ACCESS_TOKEN`. Never `execSync` (the client runs in the dashboard server and the deacon child).
- **D-9 A rejection that survives refresh is a hard failure.** `pollUntil` rethrows it as `FlyMachineError('fly-token-rejected', …)` (HTTP 424) instead of counting it as "not finished".
- **D-10 One wording for rejection.** Every operator-facing surface (loop lines, errors, `pan doctor`) uses `flyTokenRejectedMessage(error)`: `Fly token rejected (<status>): run \`fly auth login\`, or set FLY_API_TOKEN (or the variable remote.fly.api_token_env names) to a long-lived token from \`fly tokens create deploy -a <app>\``.
- **D-11 Overdeck does not mint or store a long-lived token.** Creating `fly tokens create deploy` and writing it to disk is the operator's call. Docs and `pan doctor` recommend it.
- **D-12 No token value ever reaches a log line, error message, activity entry or test snapshot.** Refresh failure messages name the command and exit code only, never stdout.
- **D-13 Keep the client's public shape.** `new FlyApiClient('<string>')` and `createFlyApiClient(token?: string)` keep working unchanged, so `fly-provider.ts:109`, `provision.ts:116` and `fly-machine-service.ts:134` need no edit. `createFlyApiClient()` still throws synchronously `Fly API token not found…` when no token exists anywhere (`hasFlyToken` in `fly-machine-service.ts:132-139` relies on it).
- **D-14 New module for the token source.** `src/lib/remote/fly-token.ts` holds the sources and the flyctl refresh. It must **not** import `fly-api.ts` (`fly-api.ts` imports it; a cycle fails `lint:circular`). `isFlyAuthError` and `flyTokenRejectedMessage` live in `fly-api.ts` next to `FlyApiError`.

## Requirements

- **FR-1** A Machines API call made with the stored token that gets 401 or 403 runs one flyctl refresh and retries the same request once with the refreshed token; a 200 on the retry is returned to the caller.
- **FR-2** A call made with an explicit token that gets 401/403 throws `FlyApiError` with that status, with no flyctl spawn and no retry.
- **FR-3** Concurrent rejections in one process spawn at most one flyctl refresh; a failed refresh suppresses further spawns for 60 s.
- **FR-4** The client re-reads the token for every request (refreshed token first, else the file), so a long-lived client (a 20-minute provision) picks up a token flyctl refreshed after the client was built.
- **FR-5** `pollUntil` rethrows a 401/403 `FlyApiError` from its probe as `FlyMachineError('fly-token-rejected')` with HTTP status 424; every other probe error still counts as "not finished".
- **FR-6** `heartbeatFlyMachines`, `sweepFlyMachines` and `syncFlyCodexAuth` each print a loop line containing `Fly token rejected (<status>)` for a machine whose call was rejected after refresh. The sweep keeps the record.
- **FR-7** `pan machines unlink` of a Fly machine whose destroy is rejected fails with code `fly-token-rejected` (424) and keeps the record; the rollback log line contains `Fly token rejected`.
- **FR-8** `pan doctor` shows a `Fly token` row when `remote.enabled` is true or `fly-machines.json` has a record: `ok` naming the token origin when a read-only Machines API call is accepted, `error` with the D-10 fix when it is rejected, nothing otherwise.
- **FR-9** `docs/fly-provider.md` and `configuration/linked-machines.mdx` explain the stored-token refresh, the long-lived-token recommendation, and the `Fly token` doctor row.
- **NFR-1** No token value appears in any log line, error message, activity entry or loop line (D-12).
- **NFR-2** No synchronous child process in any code path reachable from the dashboard server or deacon (D-8).
- **NFR-3** No new Effect wrapper around the new Promise functions (`lint:effect-facades`); no import cycle (`lint:circular`); `src/cli/commands/doctor.ts` stays at or under its file-size cap (966 lines on main, cap 1042).
- **NFR-4** Tests that exercise the cooldown inject `now`; no test waits on a real timer.

```ts
/** Where a FlyApiClient gets the token it sends (PAN-4748). */
export interface FlyTokenSource {
  /** Where the token came from: an explicit/env value, or flyctl's stored login. */
  readonly origin: 'explicit' | 'flyctl';
  /** The token to send now. */
  current(): Promise<string>;
  /**
   * Called after a 401/403 for `rejected`. Returns a different token to retry
   * once with, or null when there is none. Absent for explicit tokens (D-2).
   */
  refresh?(rejected: string): Promise<string | null>;
}

export function staticFlyTokenSource(token: string): FlyTokenSource;

export interface FlyctlTokenDeps {
  /** Async read of ~/.fly/config.yml's access_token, or undefined. */
  readStoredToken: () => Promise<string | undefined>;
  /** Run `flyctl auth token --quiet --json`; resolves stdout, rejects on spawn error / non-zero exit / timeout. */
  runFlyctl: () => Promise<string>;
  now: () => number;
}

export function flyctlTokenSource(initial: string, deps?: Partial<FlyctlTokenDeps>): FlyTokenSource;

/** Sync read used only by createFlyApiClient's "is there any token" check (existing behaviour). */
export function readStoredFlyTokenSync(): string | undefined;

/** Test seam: no production caller; resets the shared refresh state. */
export function _resetFlyTokenStateForTests(): void;
```

Module state (shared by every flyctl source in the process — D-4):

```ts
let refreshedToken: string | null = null;      // last token flyctl printed
let inflight: Promise<string | null> | null = null;
let failedAt: number | null = null;            // for the 60 s cooldown (D-5)
const REFRESH_COOLDOWN_MS = 60_000;
const FLYCTL_TIMEOUT_MS = 30_000;
```

Behaviour, step by step:

1. `current()` returns `refreshedToken` when set, else `await deps.readStoredToken()`, else `initial`.
2. `refresh(rejected)`:
   1. If `refreshedToken !== null && refreshedToken !== rejected`, return `refreshedToken` (someone already refreshed).
   2. If `failedAt !== null && deps.now() - failedAt < REFRESH_COOLDOWN_MS`, return `null`.
   3. If `inflight`, return `await inflight`.
   4. Otherwise set `inflight` to a promise that: runs `deps.runFlyctl()`; parses the **last** stdout line that starts with `{` as JSON; takes `token` when it is a non-empty string. If that throws or yields no token, it re-reads the stored token (D-3) and uses it only when it differs from `rejected`. If the result is a token different from `rejected`: set `refreshedToken`, clear `failedAt`, return it. Otherwise set `failedAt = deps.now()` and return `null`. Clear `inflight` in `finally`.
3. Default `runFlyctl` (D-7, D-8): `promisify(execFile)('flyctl', ['auth', 'token', '--quiet', '--json'], { timeout: FLYCTL_TIMEOUT_MS, env: <process.env without FLY_API_TOKEN and FLY_ACCESS_TOKEN>, windowsHide: true })`; on an error whose `code === 'ENOENT'`, run the same with `join(homedir(), '.fly', 'bin', 'flyctl')`. Errors it throws carry only `flyctl auth token exited <code>` / `flyctl not found` — never stdout (D-12).
4. Default `readStoredToken`: `readFile(join(homedir(), '.fly', 'config.yml'), 'utf8')` then the existing regex `/^access_token:\s*(\S+)/m`; `undefined` on any error.
5. `readStoredFlyTokenSync()` is the existing `readFlyctlConfigToken()` body moved here unchanged (existing sync read; it is a file read, not a child process, and only `createFlyApiClient` calls it).
