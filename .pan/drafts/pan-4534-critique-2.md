## blocks-the-design: First red check hides a later failed shard

Evidence: `src/lib/cloister/ci-failure-feedback.ts`, lines 682–688, skips a second relay on the same head unless it has newly counted a CI test-gate failure; lines 800–801 records that head after the first delivery. `src/lib/webhook-handlers.ts`, lines 275–292, sends each failed check run separately. The test setup at `tests/unit/lib/cloister/ci-failure-feedback.test.ts`, lines 105–107, uses the local test-gate path. If `lint` fails and is relayed before `test-shard (4/4)` concludes, the first feedback contains only lint. The later shard event is debounced before `collectFailures`, so the agent never receives the failing test named in FR-1. The CI test-gate exception does not cover projects with local verification. Smallest change: make the same-head debounce retain newly failed check identities and update or send feedback when a later failed check adds evidence; test lint-first, shard-second delivery without duplicate sends for repeated events.

## blocks-the-design: Inherited labels compare workflow names with job names

Evidence: `src/lib/cloister/ci-failure-feedback.ts`, lines 693–695, builds `mainFailingNames` from `gh run list` workflow-run names; lines 512–514 compares that set with check-run job names. This repository's workflow is named `CI` (`.github/workflows/ci.yml`, line 1), while its failed test checks are named `test-shard (N/4)` (lines 163–164). Thus a shard failing on both main and the PR is not marked `[INHERITED FROM MAIN]`, and the required-action text at `ci-failure-feedback.ts`, lines 589–591, tells the agent to fix it. The existing `readDefaultBranchFailingTestChecks` in `src/lib/cloister/ci-default-branch-tests.ts`, lines 124–153, already produces failing test **check names**. Smallest change: compare head test checks with that existing check-name set (and use check names for other jobs too); add a check-run-path test where the same shard fails on main and the PR.

## blocks-the-design: Full check-run objects can overflow the read buffer

Evidence: `src/lib/cloister/ci-check-run-failures.ts`, lines 39–45, gives `execFile` a 1 MiB default `maxBuffer`; line 108 emits entire check-run objects from every page, and lines 110–113 turn an overflow into a failed read. GitHub's [check-run API](https://docs.github.com/en/rest/checks/runs) includes `output.summary` and `output.text`, each allowed up to 65,535 characters. A small number of detailed checks can exceed 1 MiB before pagination matters. The second-page test at `tests/unit/lib/cloister/ci-failure-feedback.test.ts`, lines 1094–1102, mocks tiny objects, so it cannot catch this. While the workflow is in progress, the fallback can then find no failed run and lose the check-run failures. Smallest change: project only `id`, `name`, `conclusion`, URLs, and `app.slug` in the `gh api --jq` expression, and test a response with large check output.

## sharpens-framing: Retry bound applies to each failing job

Evidence: `src/lib/cloister/ci-check-run-failures.ts`, lines 87–97, can wait 120 seconds in backoff for one job, and lines 114–125 fetch jobs serially. Two unavailable logs cause 240 seconds of waiting, as the existing test advances `2 * 125_000` ms (`tests/unit/lib/cloister/ci-failure-feedback.test.ts`, lines 1118–1128). FR-4 and `docs/PIPELINE-GATES.md`, lines 241–242, say “two minutes in total” or “about two minutes” without the per-job qualification. Smallest change: either state the per-job bound and possible total delay explicitly, or fetch logs concurrently under one shared two-minute deadline if the feedback itself must arrive within that time.
