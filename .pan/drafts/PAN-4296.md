## Glossary

- **Home** — the operator's machine: the Overdeck dashboard that starts and links the Fly VM.
- **Fly machine** — a Fly VM that runs `pan serve` and is linked one way from home (PAN-4652 glossary). Started by `addFlyMachine()` (`src/dashboard/server/services/fly-machine-service.ts`), provisioned by `provisionFlyMachine()` (`src/lib/anywhere/fly/provision.ts`), recorded in `${OVERDECK_HOME}/fly-machines.json` (`src/lib/anywhere/fly/machine-store.ts`).
- **Machines exec API** — `FlyApiClient.execCommand(app, machineId, ['/bin/sh','-c',cmd], timeout)`: one command on the VM, 60 s deadline, returns `{ stdout, stderr, exit_code }`. Fly's exec shell runs with `HOME=/` (PAN-4652 live run), and `pan serve` started from it inherits `HOME=/`.
- **Codex conversation** — a conversation whose harness is `codex`. The server runs `codex app-server` through `dist/codex-app-server-host.js` (`src/lib/launcher-codex-command.ts:125-143`; transport default `'app-server'`, `src/lib/config-yaml/defaults.ts:285`). It talks to OpenAI **directly** with the Codex CLI's own sign-in. It does not use CLIProxy: no `model_provider`, `base_url` or `8317` appears in Codex launch code.
- **Native Codex sign-in** — `~/.codex/auth.json` (`getNativeCodexAuthPath()`, `src/lib/codex-auth.ts:82`). ChatGPT sign-in holds `tokens.{access_token,id_token,refresh_token,account_id}` and `last_refresh`; API-key mode holds `OPENAI_API_KEY` and no tokens. `classifyNativeCodexAuth(raw)` (`codex-auth.ts:111`) returns `valid | expired | missing | unknown`.
- **Managed CODEX_HOME** — each Codex conversation gets `${OVERDECK_HOME}/agents/<tmuxSession>/codex-home-v2` (`src/lib/overdeck/conversation-runtime.ts:670`). `initCodexHome()` (`src/lib/runtimes/codex.ts:266`) makes its `auth.json` a **symlink** to `codexDefaultHome()/auth.json`, and `codexDefaultHome()` is `join(homedir(), '.codex')` (`src/lib/runtimes/storage/codex.ts:17`; it ignores `$CODEX_HOME`). So on a Fly machine the file that matters is `$HOME/.codex/auth.json` = `/.codex/auth.json`.
- **Refresh-token family / burn** — OpenAI rotates the refresh token on every refresh. A *copy* of `auth.json` forks the family: when either copy refreshes, the other copy's refresh token is revoked, and that side wedges in a 401 `token_invalidated` loop. The codebase already treats this as a bug (PAN-2285/PAN-2639, comment at `runtimes/codex.ts:350-360`: "A copy forks the OAuth refresh-token family"). The access token lives about 10 days, and the Codex CLI refreshes proactively when `last_refresh` is about 8 days old, or on a 401. It rewrites `auth.json` in place with a new `last_refresh` (same comment: "FileAuthStorage::save … open+truncate+write").
- **Codex model floor** — the oldest Codex CLI OpenAI accepts for a model under ChatGPT sign-in (`CODEX_MODEL_MINIMUM_VERSIONS`, `src/lib/codex/model-floors.ts:22-27`). It is enforced by `canUseHarness()` (`src/lib/harness-policy.ts:156`) through `codexModelFloorDecision` (`:139`) with `context.codexCliVersion`.
- **Codex auth sync** (new) — the home↔VM copy of the native Codex sign-in for one Fly machine, decided by **newest refresh wins** (D-3).

## Problem

The parent PRD's FR-18 says Fly machines run "any supported harness: Claude Code at once, and Codex through PAN-4296". After PAN-4652, a Codex conversation cannot run on a Fly machine:

1. **Refused at the door.** `refuseEarly()` throws `harness-unsupported` unless `getHarnessBehavior(harness).capabilities.runsOnFlyMachine` (`fly-machine-service.ts:152-154`), and `CODEX_CAPABILITIES.runsOnFlyMachine` is `false` (`packages/contracts/src/harness-capabilities.ts:164`).
2. **Hard-coded harness.** `startFlyConversation()` always sends `harness: 'claude-code'` (`fly-machine-service.ts:253`, `const body = { message: input.message, projectKey: input.projectKey, harness: 'claude-code', model: input.model, effort: input.effort };`).
3. **No Codex CLI on the VM.** `docker/pan-workspace/Dockerfile` installs Claude Code (`RUN npm install -g @anthropic-ai/claude-code`) and no `@openai/codex`.
4. **No Codex sign-in on the VM.** `syncAllCredentials()` (`src/lib/remote/fly-provider.ts:559-565`) copies Claude and GitHub credentials only. A fresh Codex home without `auth.json` shows Codex's blocking sign-in screen (comment at `runtimes/codex.ts:241-245`). Also, `getProviderExportsForModel` throws "Codex/ChatGPT subscription login required" when there is no refresh token (`src/lib/agents/provider-env.ts:74-89`).
5. **Claude credentials are mandatory.** `prepareMachine()` fails with `credentials-failed` when `!synced.claude` (`provision.ts`, `if (!synced.claude) {`). An operator who only signs in to Codex cannot start a Fly machine for a Codex conversation.
6. **No refresh.** The 60 s credential refresh (`refreshClaudeCredentialsForActiveRemoteAgents`, `src/lib/remote/remote-credential-refresh.ts`) pushes Claude credentials only. It pushes home → VM, which for Codex would re-burn a VM whose Codex just refreshed (see Glossary).
7. **A missing model silently becomes Claude Code.** `resolveAllowedHarness` returns `'claude-code'` when there is no model (`conversation-runtime.ts:214-215`, `if (!model) return 'claude-code';`). The VM runs the same code, so `add-fly --harness codex` without `--model` would start a Claude Code conversation.
8. **The CLI has no `--harness`.** `pan machines add-fly` registers `--project/--message/--model/--effort/--region/--image/--json` only (`src/cli/commands/machines-fly.ts:115-121`); the route already accepts `harness` (`src/dashboard/server/routes/machines-fly.ts:29`, `STRING_FIELDS`).

## Goals

- `pan machines add-fly --project <key> --harness codex --model <openai id> --message "<text>"` starts a Fly machine, prepares Codex on it, and starts a Codex conversation there. The conversation streams in the home dashboard as a linked row with the `fly-<machineId>` chip.
- Every Fly machine is Codex-ready when home has the Codex CLI and a valid native sign-in, so a later Codex conversation on that machine (Pull here back, #4651's Machine field) needs no re-provisioning.
- Running Codex on a Fly machine never burns home's Codex sign-in, and home's sign-in never burns the VM's.
- Refusals happen at home before any Fly money is spent.

## Non-goals

- CLIProxy on the VM, or the VM reaching home's CLIProxy. Codex conversations do not use CLIProxy (Glossary), so the issue body's "how a remote agent reaches a GPT provider" question has no work in it.
- GPT models through the **claude-code** harness on Fly (that path needs CLIProxy, which the VM does not have). The claude-code model check is unchanged from PAN-4652: this issue adds no provider check for claude-code.
- Other non-Claude harnesses on Fly (ohmypi, acp, kimi-code, opencode, muse). Their `runsOnFlyMachine` stays `false`.
- Codex for `pan start --remote` work agents, and their forensics/salvage of Codex rollouts (`captureRemoteForensics`) — [PAN-4734](https://github.com/eltmon/overdeck/issues/4734) moves work agents onto Fly machines.
- The Machine field / `--machine fly` on `pan start`, `pan worker run`, `pan lane start` — #4651 and #4638.
- Codex `rules/` (execpolicy) and `~/.agents/skills` on the VM. The VM's Codex runs with an empty rules directory and no user skills.
- Fixing the open PAN-4652 follow-ups [#4738](https://github.com/eltmon/overdeck/issues/4738), [#4739](https://github.com/eltmon/overdeck/issues/4739), [#4740](https://github.com/eltmon/overdeck/issues/4740), [#4741](https://github.com/eltmon/overdeck/issues/4741) and the default-image bug [#4682](https://github.com/eltmon/overdeck/issues/4682).
- Changing the Claude credential refresh loop.
- A dashboard UI for adding Fly machines (#4651).

## Requirements

### Functional

- **FR-1** The `pan-workspace` image installs the Codex CLI (`npm install -g @openai/codex`), so `codex --version` runs on the VM.
- **FR-2** `CODEX_CAPABILITIES.runsOnFlyMachine` is `true`; every other non-Claude harness stays `false`.
- **FR-3** `addFlyMachine` with `harness: 'codex'` refuses before any VM is created when: no `model` is given (`bad-request`); the model's provider is not `openai` (`harness-unsupported`); home has no Codex CLI binary (`harness-unsupported`); home's native Codex sign-in is not `valid` (`credentials-failed`); or `canUseHarness('codex', model, authMode, <home Codex policy context>)` denies (`harness-unsupported`, with the policy reason).
- (FR-4 was retired in planning: a claude-code provider check would change PAN-4652 behavior; see Non-goals.)
- **FR-5** `provisionFlyMachine` takes `harness: 'claude-code' | 'codex'` (default `'claude-code'`). Claude credentials are required only when the harness is `claude-code`. For `codex`, a missing Claude credential is logged and provisioning continues.
- **FR-6** Provisioning prepares Codex when home has a Codex CLI and a `valid` native sign-in: it pins the VM's `codex --version` to home's (detached `npm install -g @openai/codex@<home version>`, polled up to 5 min), then pushes home's `auth.json` to `$HOME/.codex/auth.json` on the VM (mode 0600). The result carries `codexAuthPath` (the VM path) or `null` when Codex was not prepared. With `harness: 'codex'`, a failure to prepare Codex fails provisioning (`version-mismatch` or `credentials-failed`), and the VM is destroyed. With `claude-code` it is logged and `codexAuthPath` is `null`.
- **FR-7** `FlyMachineRecord` carries `codexAuthPath: string | null`. A record without the field (written by PAN-4652) reads as `null`; it does not make the store corrupt.
- **FR-8** `startFlyConversation` sends the requested harness (`input.harness ?? 'claude-code'`) in the `POST /api/conversations` body.
- **FR-9** `pan machines add-fly --harness <name>` sends `harness` to the route. The human output prints `codex: yes|no` from `record.codexAuthPath`.
- **FR-10** Every 60 s the deacon child runs `syncFlyCodexAuth()` over each record with a `linkId` and a `codexAuthPath`. For each, it reads the VM's `auth.json`, decides with D-3, and pushes, pulls, or does nothing. An exec failure is indeterminate and does nothing. With no such record it constructs no Fly client.
- **FR-11** A pull writes home's native Codex `auth.json` only when the VM copy is ChatGPT sign-in with all four tokens, has the same `account_id` as home, and has a strictly newer `last_refresh`. The write is atomic (temp file in the same directory, then rename) with mode 0600, and it goes to the real path when `~/.codex/auth.json` is itself a symlink.

- **NFR-1** With zero Fly machine records that have a `codexAuthPath`, `syncFlyCodexAuth` makes no Fly API call (same rule as PAN-4652 NFR-1).
- **NFR-2** No `auth.json` content, token, or base64 of either appears in a log line, an activity entry, an error message, or a thrown error's `detail`. Error messages name the path and the step only.
- **NFR-3** Poll, install-wait and loop tests use `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()`; no test waits on a real `setTimeout` (repo rule: fake timers for retry and delay tests).

- **NFR-5** No file passes the file-size guard (`scripts/lint-file-size.sh`, ceiling 1000, compared with `origin/main`). New logic goes in the new module `src/lib/anywhere/fly/codex-auth.ts`. `src/lib/remote/remote-agents.ts` is not touched.
- **NFR-6** Every new export has a production caller or carries the test-seam comment `/** Test seam: no production caller; … */`.

## Decisions (made here)

- **D-1 Provider routing: none needed.** Codex conversations use the Codex CLI's own sign-in and call OpenAI directly (Glossary). Nothing in this issue installs, starts or tunnels CLIProxy. This answers the issue body's open question.
- **D-2 Codex is prepared on every Fly machine when home can.** Home has Codex when `resolveHarnessBinary('codex')` (`src/lib/harness-binary.ts:260`) finds a binary, `readCodexCliVersion(binary)` returns a version, and `classifyNativeCodexAuth(await readFile(getNativeCodexAuthPath()))` is `valid`. Then provisioning pins the VM's Codex and pushes the sign-in, whatever the requested harness, so a Claude-first machine can take a Codex conversation later. It is fatal only for `harness: 'codex'`. When home lacks any of the three, provisioning logs one line and skips Codex.
- **D-3 Codex auth sync is "newest refresh wins", both ways.** A home → VM push alone would overwrite a VM that just refreshed with home's now-revoked token, and a VM refresh would silently burn home's Codex sign-in (Glossary). Decision function `decideCodexAuthSync(home, vm)` over parsed snapshots `{ raw, mode: 'chatgpt' | 'api-key' | 'unknown', accountId, lastRefreshMs, complete, key }`. `key` is the sign-in's content, not its bytes: for `chatgpt`, `JSON.stringify([access_token, id_token, refresh_token, account_id, last_refresh])`; for `api-key`, the `OPENAI_API_KEY` value. Comparing bytes would push every tick when Fly's exec output or Codex's rewrite changes whitespace, and a push (`mv -f`) that lands during a VM refresh loses the VM's new token.
  1. Home missing, or home mode `unknown` ⇒ `none` (nothing trustworthy to send).
  2. VM missing, or VM mode `unknown` ⇒ `push`.
  3. `home.key === vm.key` (same mode) ⇒ `none`.
  4. Both `chatgpt`, same non-empty `accountId`, `vm.complete`, and `vm.lastRefreshMs > home.lastRefreshMs` ⇒ `pull`.
  5. Otherwise ⇒ `push`. Home is the authority on which account is signed in, so a home re-login to another account is pushed.
  A concurrent refresh on both sides inside one 60 s window still burns one side. This is a residual risk, documented in the user docs with the fix (`codex login` at home; the next sync pushes it).
- **D-4 VM path from the exec shell.** The VM path is read with `printf %s "$HOME/.codex"` in the exec shell, and `//` is collapsed to `/`, the same way `OVERDECK_HOME_PROBE` is handled (`provision.ts`, `const OVERDECK_HOME_PROBE = 'printf %s "${OVERDECK_HOME:-$HOME/.overdeck}"';`). The result must start with `/`. It is never a literal `/root`. The path (`<dir>/auth.json`) is stored in the record as `codexAuthPath`.
- **D-5 Model and harness are checked at home, before any VM exists.** `harness: 'codex'` needs a `model` (no default model anywhere; repo rule "never hardcode a model fallback"). For codex, `getProviderForModel(model).name` (`src/lib/providers.ts:430`) must be `openai`. Claude Code requests are checked exactly as in PAN-4652. Then `canUseHarness('codex', model, await getProviderAuthMode(model), await resolveCodexPolicyContext('codex', model, authMode))` (`src/lib/agents/runtime-command.ts:656`, `src/lib/codex/policy-context.ts`) must allow it. Home's Codex version predicts the VM's, because D-2 pins the VM to it.
- **D-6 Version pin by install, like `pan` (PAN-4652 D-7).** When the VM's `codex --version` (parsed with `parseCodexCliVersion`, `app-server-manager.ts:673`) differs from home's, run `setsid nohup sh -c 'npm install -g @openai/codex@<v> > /tmp/codex-install.log 2>&1; echo $? > /tmp/codex-install.exit'` detached (reuse `detached()` from `provision.ts`), poll `cat /tmp/codex-install.exit` every 5 s for at most 5 min (`INSTALL_POLL`), then re-check. A mismatch after that is `version-mismatch` for `harness: 'codex'` and a logged skip otherwise.
- **D-7 Push format.** The push runs `mkdir -p <dir> && printf %s '<base64>' | base64 -d > <dir>/auth.json.tmp && chmod 600 <dir>/auth.json.tmp && mv -f <dir>/auth.json.tmp <dir>/auth.json` through `execCommand` (30 s timeout). A rename keeps the VM's per-conversation symlinks valid, because they resolve the global path by name. The `auth.json` is about 5 KB (about 7 KB base64), under the exec payload limit (~16 KB, PAN-4652 hazard), so no chunking is needed. If base64 of the file is over 12,000 characters, use `writeRemoteFile()` (`remote-agents.ts`, chunked) for the temp file instead.
- **D-8 Read format.** The VM read runs `if [ -f <path> ]; then cat <path>; else printf __MISSING__; fi`. Exit 0 with `__MISSING__` ⇒ VM missing. A non-zero exit or an API error ⇒ indeterminate: no push, no pull.
- **D-9 Where the code lives.** The new module `src/lib/anywhere/fly/codex-auth.ts` holds the snapshot parser, `decideCodexAuthSync`, the VM read and push helpers, the home write, `readHomeCodexState()` (D-2's three checks), and `prepareFlyCodex()` (D-6 + push). `provision.ts` calls `prepareFlyCodex`. `src/lib/remote/fly-machine-loops.ts` gains `syncFlyCodexAuth`, registered in `src/lib/cloister/hygiene-scheduler.ts` next to `heartbeatFlyMachines`. `fly-provider.ts` and `remote-credential-refresh.ts` are not changed.
- **D-10 Import hygiene.** `src/lib/codex/model-floors.ts` warns that `app-server-manager.ts` pulls in `ws`. `codex-auth.ts` loads `readCodexCliVersion` and `parseCodexCliVersion` with a dynamic `await import('../../codex/app-server-manager.js')` inside the function that needs them, never a static import. `fly-machine-service.ts` loads `resolveCodexPolicyContext` and `getProviderAuthMode` the same way.
- **D-11 Refusal text.** The `harness-unsupported` message for a harness whose `runsOnFlyMachine` is false becomes `Fly machines run Claude Code and Codex conversations; <harness> is not supported.` (no `#4296` reference).
- **D-12 Codex sandbox on the VM: live checkpoint with a fallback.** A fresh VM config gives `codex.permissionMode: 'auto-review'` (`defaults.ts:284`), hence `sandbox_mode = "workspace-write"` (`conversation-runtime.ts:674-678`), which on Linux uses Landlock/seccomp. It is unverified inside a Fly Firecracker VM as root. WI-9 checks it. **Fallback, if Codex cannot run a shell command on the VM:** provisioning writes `${overdeckHome}/config.yaml` on the VM with `codex:\n  permissionMode: full-access\n` before it starts `pan serve`. The VM is a disposable sandbox, like `IS_SANDBOX=1` for Claude (PAN-4652 D-4). Record the outcome in the docs either way.
- **D-13 The notify hook is optional.** `initCodexHome` adds `notify = [...]` only when `~/.overdeck/bin/codex-notify-hook` exists (`runtimes/codex.ts:304`, `if (existsSync(notifyHookPath)) {`). A VM that never ran `pan install` simply has no notify hook; nothing to do.

- Effort defaults stay `high`; nothing here sets `xhigh` or `max`.

- Never send destructive HTTP requests speculatively. Live Fly spend needs operator consent.
- Quality gates before `pan done`: `npm run typecheck`, `npm run lint`, and `npx vitest run <touched test files>`. Never the full `npm test` on the host. `npm run typecheck` excludes `*.test.ts`, so run the touched tests explicitly.
- Never `git stash`; never `git checkout` another branch in the workspace.

## Hazards

- **Secrets in logs.** `provision.ts`'s `run()` helper puts the step's stderr or stdout in its error. Do not use `run()` for the Codex read or push; use the WI-3 helpers, whose errors name no content (NFR-2).
- **Home process holding an old token.** After a pull, a running home Codex app-server may still hold the revoked refresh token in memory until it reloads `auth.json`. Codex reloads the file before refreshing on a 401; if a home conversation still wedges, resuming it re-reads the file. Documented, not fixed.
- **`~/.codex/auth.json` is a symlink at home on some machines.** `writeHomeCodexAuth` writes the symlink's target (WI-3 step 4); the test covers it.
- **Exec rate limit.** The sync adds one exec per Codex-ready machine per minute, next to the heartbeat. A 429 surfaces as an indeterminate read and is retried next tick.
- **Old `pan` on the VM.** The VM's `pan` is pinned to home's version (PAN-4652 D-7). Until a release contains this branch, only the live checkpoint's packed tarball has the Codex-capable server code. That matters only for the VM side, which this issue does not change.
- **Static import of `app-server-manager.js`.** It pulls `ws` into whatever imports it (D-10); keep the imports dynamic.
