# PAN-5348: Bare `/pan` in the composer lists the Overdeck commands

**Issue:** [PAN-5348](https://github.com/eltmon/overdeck/issues/5348)
**Planning mode:** `pan plan --auto` (no operator questions; defaults are recorded under "Decisions" and in `plan.autoDecisions[]`).

## Glossary

- **Composer:** the message box at the bottom of a dashboard conversation or agent pane. Its Send button and Enter key submit text.
- **Portable command:** composer text that starts with `/pan` followed by whitespace or end of text. The dashboard server intercepts it and never delivers it to the agent.
- **Manifest:** `COMPOSER_COMMAND_MANIFEST`, the generated list of every visible `pan` CLI command (440 entries, 92 of them top-level). File: `packages/contracts/src/composer-commands.generated.ts`. It is generated by `scripts/generate-slash-commands.mjs` and drift-gated by `scripts/lint-slash-commands.sh`. Never edit it by hand.
- **Manifest category:** the `category` field of a manifest entry (`Core`, `Lifecycle`, `Observation`, `Review`, `Flywheel`, `Conversation`, `Workspace`, `Data`, `Admin`, `Project`, `CLI`), assigned from `scripts/slash-commands-curation.json`.
- **Policy overlay:** `COMPOSER_COMMAND_POLICIES` in `src/lib/composer-commands/policy.ts`. It maps a command path to an execution mode. Only 8 paths have one (`start`, `plan`, `reload`, `show`, `status`, `tell`, `handoff`, `fork`); every other path falls back to `terminal-only`, which the server rejects with HTTP 422.
- **Composer-runnable command:** a manifest entry whose policy mode is not `terminal-only`.
- **Captured result:** a `ComposerCommandResult` with `kind: 'captured'`. The server answers it with HTTP 200 and the frontend renders it as a command result row with its `output` in a `<pre>` block (`CommandResultRow.tsx`).
- **Help entry:** a new dashboard-owned pseudo manifest entry, `COMPOSER_HELP_ENTRY`, that the parser returns for bare `/pan` and its help spellings. It is not part of the generated manifest.
- **Slash picker:** the autocomplete menu that opens when the operator types `/` in the composer (`SlashMenu` in `ComposerPromptEditor.tsx`).

## Problem

On 2026-11-15 the operator typed `/pan` alone and pressed Send. The send failed with HTTP 404, a toast ("Failed to send message (404): Missing an Overdeck command after /pan. Type /pan to list available commands."), and a failed bubble ("Command request failed …" with Discard). The error tells the operator to do what they just did.

### Cause (verified)

`src/lib/composer-commands/parser.ts`, `resolveEntry` (lines 110–127):

```ts
  const token = tokens[0] ?? '';
  throw new ComposerCommandParseError(
    'unknown-command',
    token
      ? `Unknown Overdeck command "${token}". Type /pan to list available commands.`
      : 'Missing an Overdeck command after /pan. Type /pan to list available commands.',
```

`parseOverdeckComposerCommand` (line 165) passes `tokenize(message.slice(4).trim())`, which is `[]` for bare `/pan`, so no manifest entry matches and the parser always throws. Commander's implicit `help` command is excluded from the manifest by `src/cli/command-introspection.ts` (see `docs/COMPOSER-SLASH-COMMANDS.md` line 18), so `/pan help` also throws (`Unknown Overdeck command "help"`).

There are exactly two production callers of `handleComposerCommandMessage` (verified by grep over `src/`, excluding tests):

- `src/lib/overdeck/conversation-message.ts` lines 487–517: conversation route. It maps `unknown-command` to 404 at line 511 (`const status = error.code === 'unknown-command' ? 404 : …`).
- `src/dashboard/server/routes/agents/messaging.ts` lines 72–121: agent route. Same mapping at line 117.

The frontend (`src/dashboard/frontend/src/components/chat/ComposerFooter.tsx` lines 603–647) shows a toast and a failed bubble for any non-2xx answer that is not a `ComposerCommandResult`.

### Related keyboard defect (verified)

With the slash picker open, Enter selects `filteredCommands[selectedIndex]` instead of sending (`ComposerPromptEditor.tsx`, the capture-phase `keydown` handler, `else if (e.key === 'Enter')`). For the filter `pan`, `filterCommands` (lines 194–207) matches label **or** description and keeps source order. In a Claude Code conversation the first match is the native `/context` entry, whose description "Inspect or expand the current context window" contains `pan` (`packages/contracts/src/harness-behavior.ts` line 95). So typing `/pan` and pressing Enter inserts `/context ` today. The filter `pan ` (with a space) already matches only Overdeck entries; the existing test "keeps menu open when typing spaces after /" covers `/pan work`.

## Requirements

### Functional

- **FR-1:** `parseOverdeckComposerCommand` returns `{ entry: COMPOSER_HELP_ENTRY, argv: ['help'] }` for `/pan`, `/pan help`, `/pan --help` and `/pan -h` (surrounding whitespace allowed, since the routes trim the message).
- **FR-2:** `/pan help <anything>` throws the existing generic positional error: code `unknown-command`, message `Unexpected token "<anything>" for /pan help. Expected syntax: /pan help.`
- **FR-3:** `handleComposerCommand` returns the help result for the help entry before it resolves a policy, issues a confirmation, or starts an executor. No child process is spawned.
- **FR-4:** The help result is a captured result: `{ kind: 'captured', status: 'completed', command: '/pan help', output: <list>, truncated: false }`. The list format is defined in Work Item 2.
- **FR-5:** The list has a "Run in this composer" section with every composer-runnable manifest entry, and then one section per manifest category, in the order each category first appears in the manifest, with every top-level manifest entry (`path.length === 1`) that is not composer-runnable. Terminal entries are written as `pan <syntax>`, composer entries as `/pan <syntax>`.
- **FR-6:** The unknown-command message stays `Unknown Overdeck command "<token>". Type /pan to list available commands.` The unreachable "Missing an Overdeck command after /pan" branch is deleted.
- **FR-7:** The conversation route and the agent route both answer bare `/pan` with HTTP 200 and the help result, and never call a delivery function.
- **FR-8:** The slash picker has a static `/pan` entry (description `List the available Overdeck commands`, insert `/pan`, category `Overdeck`), placed before the generated Overdeck entries.
- **FR-9:** For a non-empty filter, the slash picker ranks matches: rank 0 = exact label match (`label === '/' + filter`, case-insensitive), rank 1 = label-contains match, rank 2 = description-only match. The order stays category-contiguous: categories are ordered by their best-ranked member (ties by first appearance), and members inside a category by rank, then source index. An empty filter keeps source order. The flat order therefore always matches the grouped on-screen order, so ArrowUp/ArrowDown move row by row.
- **FR-10:** Typing `/pan ` (with a trailing space) in the picker shows only `/pan …` entries and no harness-native entries.

### Non-functional

- **NFR-1:** The help list is built in-process from the manifest and the policy overlay. It does not run `pan --help` or any child process.
- **NFR-2:** No edit to `composer-commands.generated.ts`, `scripts/slash-commands-curation.json`, or `COMPOSER_COMMAND_POLICIES`. `assertPolicyOverlayIntegrity()` throws at import time for a policy path without a manifest entry, so the help entry must never get a policy row.
- **NFR-3:** The help output is deterministic: two calls return identical strings.
- **NFR-4:** The frontend tests this change extends run in CI: `scripts/frontend-test-subset.txt` lists them.
- **NFR-5:** The `ComposerCommandResult` contract type and `isComposerCommandResult` stay unchanged.

## Decisions

1. **Server-side, not a frontend shortcut.** The server already intercepts `/pan` on both routes, and MCP `send_message` and `pan tell` reach the same routes. Answering there fixes every client at once. The issue's "local command result" means "not sent to the agent", which the server interception already guarantees.
2. **Reuse `kind: 'captured'`.** A new result kind would need the contracts type, `isComposerCommandResult` (a strict switch: an unknown 200 body returns `null`, and `ComposerFooter` then treats the send as an acknowledged prompt), `statusSentence`, and the row to change together. The captured row already renders multi-line output in a scrollable `<pre>` (max height 280 px). The row's status line reads `/pan help completed successfully.`
3. **Grouping source is the manifest category.** `pan --help` is a flat Commander list with no group headings (verified: all 219 lines), so "grouped like `pan --help`" is read as "grouped by the command categories the CLI registry assigns".
4. **Top-level commands only.** `pan --help` lists top-level commands. Listing all 440 entries would bury the useful ones. The footer line points to `pan <command> --help` for subcommands.
5. **Mark composer-runnable commands.** Only 8 of 92 top-level commands run in the composer; the rest answer 422 "must run in a terminal". The first section lists the runnable ones so the list does not advertise commands that fail when typed here.
6. **Help spellings:** `/pan`, `/pan help`, `/pan --help`, `/pan -h`. Commander accepts all three help forms, so operators type them by habit. `/pan help <verb>` is rejected (FR-2), not interpreted.
7. **The help entry is checked before the manifest.** A test asserts the manifest has no `help` path, so if the CLI ever registers a real `help` command the test fails and the owner decides which wins.
8. **Picker ranking fix is in scope.** Without it, `/pan` + Enter in a Claude Code conversation inserts `/context `, so the keyboard path to the same goal stays broken.

### Work Item 2 — Help list builder (FR-4, FR-5, NFR-1, NFR-3)

**New file:** `src/lib/composer-commands/help.ts`. **New test:** `src/lib/composer-commands/__tests__/help.test.ts`.

```ts
/**
 * Bare `/pan` help (PAN-5348): lists the Overdeck commands from the generated
 * manifest, composer-runnable ones first, the rest grouped by category.
 * Built in-process; never spawns `pan --help`.
 */
import { COMPOSER_COMMAND_MANIFEST, type ComposerCommandResult } from '@overdeck/contracts';
import { expectedSyntax } from './parser.js';
import { resolvePolicy } from './policy.js';

const SYNTAX_COLUMN_MAX = 36;

export function buildComposerHelpOutput(): string { /* see format below */ }

export function buildComposerHelpResult(): ComposerCommandResult {
  return { kind: 'captured', status: 'completed', command: '/pan help', output: buildComposerHelpOutput(), truncated: false };
}
```

Output format (exact; `<pad>` = syntax padded with spaces to the column width, then two spaces; column width = the longest syntax string over all listed lines, capped at `SYNTAX_COLUMN_MAX`; a longer syntax gets no padding, only the two spaces):

```
Overdeck commands

Run in this composer (type /pan <command>):
  /pan start <id> [options]<pad>Create workspace and spawn agent for an issue
  …one line per composer-runnable entry, in manifest order…

Run in a terminal (type pan <command> in a shell):

Core
  pan init<pad>Initialize Overdeck (~/.overdeck/)
  …

Lifecycle
  …

Run pan <command> --help in a terminal for subcommands and options.
```

Rules:

1. Composer-runnable entries = every manifest entry (any depth) with `resolvePolicy(entry.path).mode !== 'terminal-only'`, in manifest order. Syntax = `expectedSyntax(entry)` (starts with `/pan`).
2. Terminal entries = manifest entries with `path.length === 1` that are not composer-runnable. Group by `entry.category`; groups appear in the order their category first appears among these entries; entries keep manifest order inside a group. Syntax = `expectedSyntax(entry).replace(/^\/pan /, 'pan ')`.
3. Each group: a blank line, the category name on its own line, then its entry lines indented by two spaces.
4. Lines end without trailing spaces; the output ends with the footer line and no trailing newline.

Tests (`help.test.ts`):

- `lists composer-runnable commands first with /pan syntax`: output contains `/pan start <id>` and `/pan status`, and both appear before the line `Run in a terminal (type pan <command> in a shell):`.
- `groups terminal commands by manifest category`: output contains a line exactly `Lifecycle` and a line starting `  pan doctor`; no line starts with `  /pan doctor`. (Anchor every negative check to the start of a line, `^  `, so a description that names a command cannot fail the test.)
- `lists only top-level terminal commands`: no line starts with `  pan plan finalize` or `  pan review request`.
- `returns a deterministic captured result`: `buildComposerHelpResult()` deep-equals a second call and matches `{ kind: 'captured', status: 'completed', command: '/pan help', truncated: false }`; `output.length` is below 65,536.
- `counts every top-level command once`: the number of lines starting with two spaces then `pan ` or `/pan ` equals (top-level manifest entries that are terminal-only) + (composer-runnable entries).

### Work Item 5 — Picker ranks exact and label matches first (FR-9)

**File:** `src/dashboard/frontend/src/components/chat/ComposerPromptEditor.tsx`, `filterCommands` (lines 194–207).

After filtering, when `normalizedFilter` is non-empty, compute each match's rank: 0 when `cmd.label.toLowerCase() === '/' + normalizedFilter` (or `'/' + aliasFilter` when an alias applies), 1 when the label contains the filter (or the alias filter), 2 otherwise. Then order the matches so the result stays **category-contiguous** (`SlashMenu` renders rows grouped by `cmd.category || 'Commands'`, while `selectedIndex` walks the flat array, so a global rank sort would make ArrowDown jump between groups for mixed filters such as `co`):

1. Group the matches by `cmd.category || 'Commands'` (the same key `SlashMenu` uses).
2. Order the groups by their best (lowest) member rank; ties by the group's first appearance in source order.
3. Inside each group, order members by rank, then source index.
4. Concatenate the groups.

Implement with explicit `[rank, index]` comparisons so the result is stable on every engine. An empty filter returns the filtered list in source order, as today. `SlashMenu` and the keyboard handler both call `filterCommands`, so the highlighted row, the Enter selection and the group order stay consistent.

Before:
```ts
  return commands.filter((cmd) => {
    const haystack = `${cmd.label} ${cmd.description}`.toLowerCase();
    return (
      haystack.includes(normalizedFilter) ||
      (aliasFilter !== null && haystack.includes(aliasFilter))
    );
  });
```
After (shape):
```ts
  const matches = commands.filter((cmd) => { /* unchanged predicate */ });
  if (!normalizedFilter) return matches;
  return rankWithinCategories(matches, normalizedFilter, aliasFilter);
```
`rankWithinCategories` is a module-local function in the same file.

Tests (`ComposerPromptEditor.test.tsx`):

- `ranks the /pan entry first for the filter pan`: render `SlashMenu` with `getSlashCommands('claude-code')`, `filter="pan"`, `selectedIndex={0}`: the option with `aria-selected="true"` has label `/pan`; the first group heading rendered is `Overdeck`.
- `keeps description-only matches after label matches`: with `TEST_COMMANDS` plus `{ id: 'x', label: '/zzz', description: 'model helper', insert: '/zzz' }` and `filter="model"`, the first option is `/model`.
- `keeps the highlighted row in on-screen order for a mixed filter`: with `getSlashCommands('claude-code')` and `filter="co"`, render `SlashMenu` three times with `selectedIndex` 0, 1 and (option count − 1); each time `screen.getAllByRole('option')[i]` is the element with `aria-selected="true"`.
- Existing `SlashMenu filter` tests still pass unchanged.
