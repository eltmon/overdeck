# PAN-5610: CLI conversation writes fail with "Missing origin"

**Issue:** [PAN-5610](https://github.com/eltmon/overdeck/issues/5610)
**Overlaps:** [PAN-5523](https://github.com/eltmon/overdeck/issues/5523) (open, unplanned: same bug on `move` and `heal`, proposes a server-side fix)
**Precedent:** [PAN-5516](https://github.com/eltmon/overdeck/issues/5516) (same bug on `pan conversations resume`, fixed server-side with `crossSiteWriteRefusal`)

## Glossary

- **Origin check** — `validateOriginHeaders(headers, method)` in `src/dashboard/server/routes/origin-validation.ts` (line 127). For a non-GET/HEAD request with no `Origin` and no `Referer`, it returns `{ ok: false, error: 'Missing origin' }` unless the request carries `Authorization: Bearer odk_…`. `validateOrigin(request)` (line 166) is the wrapper that routes call.
- **Plain-guarded route** — a dashboard route whose handler calls `validateOrigin(request)` directly and returns 403 on failure. The internal token (`x-overdeck-internal-token`) does **not** exempt it.
- **Credential-exempt guard** — `rejectUnsafeDashboardMutationRequest` (`routes/dashboard-auth.ts:282`), `crossSiteWriteRefusal` (`linked-conversation-proxy.ts:119`), `requireTrustedOrigin` (`routes/merge-train.ts:524`) and `forbiddenOrigin` (`routes/shutdown.ts`). These skip the Origin check when the internal token (or another header-borne credential) is present.
- **`getDashboardApiUrl()`** — `src/lib/config.ts:442`. Returns `OVERDECK_DASHBOARD_URL`, else `DASHBOARD_URL`, else `http://localhost:<dashboard.api_port || 3011>`. The server's trusted set (`getTrustedOrigins()`, `origin-validation.ts:49`) always contains `http://localhost:<port>`.
- **Trusted Origin header** — `Origin: getDashboardApiUrl()`, the header sibling CLI verbs already send: `src/cli/commands/plan-finalize.ts:568` (`headers: { 'Content-Type': 'application/json', Origin: getDashboardApiUrl() }`), `src/cli/commands/lane.ts:134`, `src/cli/commands/fork-client.ts:163`.
- **`viaDashboard`** — a private helper duplicated in `pull-requests.ts` and `schedule.ts`: it tries the dashboard route first and falls back to an in-process write when the connection is refused. All its callers are writes.

## Problem

`pan conversations move <query> <projectKey>` always prints `Error: Missing origin`. The CLI sends `PATCH /api/conversations/<name>/move` with only `Content-Type`, and the route (`routes/conversations.ts:777`, `patchConversationMoveRoute`) is plain-guarded.

Reproduced during planning (2026-11-23) against the live dashboard, as a no-op move to the conversation's current project:

```
$ npx tsx src/cli/index.ts conversations move 20261123-4045 panopticon-cli
Error: Missing origin
```

### Audit of every non-GET dashboard call in `src/cli`

The issue asks to fix every other `src/cli` write that sends no Origin. Planning mapped each non-GET call site to its server route and that route's guard. Four files are broken. Each was confirmed live: a no-Origin POST with a bogus conversation name answered `403 {"error":"Missing origin"}` before any handler ran. With `Origin: http://localhost:3011` the same request reached the handler.

There is no global Origin middleware. Outside route handlers, `validateOriginHeaders` is called only by the WebSocket upgrade gate (`ws-auth.ts:50`), the linked-conversation proxy, `routes/mcp.ts:106` (only when an Origin is present) and `knowledge-viewer.ts`.

## Decisions

- **D-1: Fix the client, not the server.** Each broken call sends the trusted Origin header, as the issue body prescribes and as `plan-finalize.ts`, `lane.ts` and `fork-client.ts` already do. Server routes stay unchanged. PAN-5523 proposed the PAN-5516 server-side pattern instead (`callDashboard` plus `crossSiteWriteRefusal`). This plan follows the issue being planned. The client fix needs no change to a security boundary.
- **D-2: Inline the header; add no helper.** Four one-line edits. A shared helper for a single header would be an abstraction with no second use.
- **D-3: In `move.ts`, use the module constant.** `move.ts:17` already holds `const DASHBOARD_URL = getDashboardApiUrl();`, and the request URL uses it. The header uses the same constant: `Origin: DASHBOARD_URL`. The other three files call `getDashboardApiUrl()` inline, because they already call it to build the URL.
- **D-4: In `viaDashboard`, put `Origin` after the spread.** Write `headers: { 'Content-Type': 'application/json', ...(init.headers ?? {}), Origin: getDashboardApiUrl() }`, so no caller can drop it. Every `viaDashboard` caller is a write, so the header never reaches a GET.
- **D-5: PAN-5523.** The PR fixes both commands PAN-5523 names (`move`, `heal`), so the PR body says `Closes #5523` and explains that the client fix was chosen over the server fix that PAN-5523 proposed.
- **D-6: No source-scanning regression test.** A test that greps `src/cli` for raw `fetch` calls would be rejected by lint (new source-reading tests fail the gate). Each fixed file gets a behavior test that asserts the header.

## Requirements

- **FR-1:** `moveAction` sends `Origin: <getDashboardApiUrl()>` on its PATCH.
- **FR-2:** `healAction` sends `Origin: <getDashboardApiUrl()>` on its POST.
- **FR-3:** `linkPrAction`, `unlinkPrAction` and `autoSettleOverrideAction` send `Origin: <getDashboardApiUrl()>` on their dashboard request.
- **FR-4:** `scheduleAddAction`, `scheduleSetEnabledAction` and `scheduleRemoveAction` send `Origin: <getDashboardApiUrl()>` on their dashboard request.
- **FR-5:** Against a running dashboard, `pan conversations move <name> <projectKey>` prints `✓ Moved …` instead of `Error: Missing origin`.
- **FR-6:** `changelog.d/pan-5610.md` records the fix; `docs/DASHBOARD-AUTH.md` states the rule for CLI writes to plain-guarded routes.
- **NFR-1:** No dashboard server file changes.
- **NFR-2:** Each new test fails when its header line is removed and passes with it.

## Hazards

- **H-1: Untrusted dashboard URL.** If `OVERDECK_DASHBOARD_URL` names a host that is not in the server's trusted set, the error changes from `Missing origin` to `Invalid origin`. `plan-finalize` already behaves this way. Not solved here.
- **H-2: Stale installed CLI.** `pan` on PATH runs the deployed `dist` until `pan reload`. A test agent that runs `pan conversations move` before deploy sees the old failure. Verify with `npx tsx src/cli/index.ts`.
- **H-3: PAN-5523** is open and covers `move`/`heal` with a different fix. See D-5.

## Non-goals

- No change to any dashboard server route or to `validateOriginHeaders`.
- No change to `callDashboard` or to any verb that already works.
- No shared header helper.
- No source-scanning lint or test for raw `fetch` calls.
- No fix for H-1.
