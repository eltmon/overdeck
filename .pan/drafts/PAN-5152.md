# PAN-5152: Jira as a full issue tracker

**Issue:** https://github.com/eltmon/overdeck/issues/5152
**Verified against:** `main` at `3235e7fa459` (2026-11-11). Every file and line reference below was re-grepped at that commit. Line numbers can drift; each one carries a quoted grep anchor. Search for the anchor, not the number.

## 1. Glossary

- **Tracker adapter:** a class that implements `IssueTracker` (`src/lib/tracker/interface.ts`, anchor `export interface IssueTracker`). Its methods are `listIssues`, `getIssue`, `updateIssue`, `createIssue`, `getComments`, `addComment`, `transitionIssue`, `linkPR` and `getChildIssues`. Each returns an `Effect`.
- **Tracker `IssueState`:** the adapter-level state union, `'open' | 'in_progress' | 'in_review' | 'closed'` (`src/lib/tracker/interface.ts:28`, anchor `export type IssueState = 'open'`). It has four values.
- **Dashboard `IssueState`:** the lifecycle-service state union, `'open' | 'in_planning' | 'in_progress' | 'in_review' | 'verifying_on_main' | 'closed' | 'canceled'` (`src/dashboard/server/services/issue-lifecycle.ts:44`). It has seven values. It shares its name with the tracker union, so this PRD always says "tracker `IssueState`" or "dashboard `IssueState`".
- **Canonical state:** Overdeck's own state, `CanonicalState` in `src/core/state-mapping.ts:9`: `backlog`, `todo`, `in_progress`, `in_review`, `verifying_on_main`, `done`, `canceled`.
- **Jira Cloud:** Jira hosted by Atlassian at `https://<site>.atlassian.net`. It uses REST API v3. Authentication is HTTP Basic with `email:apiToken`, base64-encoded.
- **Jira Data Center (DC):** self-hosted Jira. It uses REST API v2. Authentication is a personal access token sent as `Authorization: Bearer <token>`.
- **Deployment type:** `cloud` or `datacenter`. Detected once per site from `GET /rest/api/2/serverInfo` (`deploymentType` is `"Cloud"` on Cloud, `"Server"` or `"DataCenter"` otherwise), unless the project config sets it.
- **Issue key:** a Jira issue id such as `PROJ-123`. It has the standard `PREFIX-NUMBER` shape that `parseIssueId` already accepts (`src/lib/issue-id.ts`, anchor `issueId.match(/^([A-Za-z]+)-(\d+)$/)`).
- **Jira project key:** the `PROJ` part of an issue key. In Overdeck it is the project's `issue_prefix`.
- **Workflow transition:** Jira does not let a client set a status directly. The client lists the transitions available from the current status (`GET /rest/api/{2|3}/issue/{key}/transitions`) and posts the id of one (`POST` the same path with `{"transition":{"id":"<id>"}}`).
- **Status category:** every Jira status belongs to one category, with key `new` (To Do), `indeterminate` (In Progress) or `done`. It arrives on `fields.status.statusCategory.key`.
- **ADF:** Atlassian Document Format, the JSON document tree Jira Cloud v3 uses for descriptions and comments.
- **Wiki markup:** the plain-text markup Jira DC v2 uses for descriptions and comments (`h1.`, `*bold*`, `{code}`, `[text|url]`).
- **JQL:** Jira Query Language, used to list and search issues.
- **Remote link:** a Jira issue link to an external URL (`POST /rest/api/{2|3}/issue/{key}/remotelink`). It is upserted by `globalId`.
- **Transition outcome:** the result type this PRD adds for a Jira status write: `transitioned`, `already`, `no-transition` or `error`. Only `transitioned` and `already` move or confirm the issue. None of them fails the calling pipeline step.
- **Issue-on-GitHub resolver:** `resolveGitHubIssue` (`src/lib/tracker-utils.ts:93`). Today it answers two different questions at once: "does this issue live on GitHub?" and "which GitHub repo holds this issue's pull requests?". See section 3.2.

## 2. Why

Teams that track work in Jira cannot use Overdeck today. Overdeck supports Linear, GitHub Issues, GitLab and Rally. Jira appears only as three leftovers, and no code reads a Jira issue. This issue adds Jira as a full tracker, so a project with `tracker: jira` works everywhere a Rally-tracked or Linear-tracked project works. That covers the kanban, the Command Deck tree, search, the issue view, planning and work prompts, lifecycle writes, the CLI, Settings and the docs.

## 4. Requirements

- **FR-1 (adapter):** `src/lib/tracker/jira.ts` implements every `IssueTracker` method against Jira Cloud (REST v3) and Jira DC (REST v2). `TrackerType` gains `'jira'`, and `createTracker` (`src/lib/tracker/factory.ts`) builds it.
- **FR-2 (configuration):** a project selects Jira with `tracker: jira` and `issue_prefix: <JIRA PROJECT KEY>` in `projects.yaml`, plus an optional `jira:` block (`site`, `deployment`, `status_map`). Credentials come from Settings (`tracker_keys.jira`, `tracker_keys.jira_email`, `tracker_keys.jira_base_url`) or from `JIRA_API_TOKEN`, `JIRA_EMAIL` and `JIRA_BASE_URL` in `~/.overdeck.env`. The deployment type is detected from the site, and `jira.deployment` overrides it.
- **FR-3 (ids):** a `PROJ-123` key resolves to its Jira-tracked project through `issue_prefix`, the same way a Linear id does. Registration refuses a second project with the same prefix, and the message names both projects.
- **FR-4 (dashboard issues):** Jira issues appear on the kanban board, in the Command Deck project tree, in search and in the issue view. Each shows title, description, status, labels, assignee, priority, parent and URL. The poller reads them on the Rally cycle.
- **FR-5 (state mapping):** a Jira status maps to a canonical state by status name first (per-project `jira.status_map` merged over the defaults in `state-mapping.ts`), then by status category (`new` to `todo`, `indeterminate` to `in_progress`, `done` to `done`). Overdeck writes no workflow labels to Jira.
- **FR-6 (lifecycle writes):** start work, request review, merge, close and reopen each move the Jira issue through its workflow by transition id. When no transition reaches the wanted status, the action logs the wanted status and the available transitions, and the pipeline continues. A Jira write never blocks a merge or a close-out.
- **FR-7 (text):** descriptions and comments convert from ADF (Cloud) or wiki markup (DC) to Markdown on read, and from Markdown to ADF or wiki markup on write. Planning and work agents see the Jira description and comments in Markdown.
- **FR-8 (pull request link):** the PR URL is attached to the Jira issue as a remote link by `pan done` and again at close-out. `pan done --comment` posts the same comment text it posts on Linear and GitHub. Close-out posts a close comment that contains the PR URL.
- **FR-9 (hierarchy):** `getChildIssues` returns the children of an epic and the subtasks of an issue.
- **FR-10 (CLI):** `pan issues`, `pan start`, `pan plan`, `pan show`, `pan done`, `pan close` and `pan reopen` work with a Jira key. `pan doctor` checks the Jira credentials with one authenticated call per site and names the fix when the check fails.
- **FR-11 (settings UI):** the Settings page has Jira rows for the token, the email and the site URL. The Add-project flow (CLI and dashboard dialog) accepts `jira` as a tracker.
- **FR-12 (docs):** `configuration/issue-trackers.mdx` gains a Jira section, and every doc that lists the supported trackers lists Jira.
- **FR-13 (routing):** a `tracker: jira` project with `github_repo` is never treated as a GitHub issue source, but its pull requests are still found in that GitHub repo. Projects with any other tracker value keep today's precedence exactly.
- **NFR-1:** no Jira call blocks the Node event loop. No `execSync` and no new `*Sync` function in server-reachable code. Every Jira call uses `fetch`.
- **NFR-2:** every Jira request has a 30 s timeout, built from an `AbortController` plus `setTimeout`, not `AbortSignal.timeout`, because happy-dom ignores fake timers there. HTTP 429 is retried after `Retry-After` seconds, at most 3 retries. Retry tests use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`.
- **NFR-3:** the Jira token, the email and the `Authorization` header value are never logged and never sent to telemetry. Error messages quote the URL path and HTTP status only. Test fixtures build fake tokens at runtime (for example `['fake', 'jira', 'token'].join('-')`) so GitHub push protection never sees a token-shaped literal.
- **NFR-4:** one variant per operation in `src/lib` (`npm run lint:effect-facades`). The adapter returns `Effect` values like the other adapters. The new modules add no exported Effect wrapper around in-repo Promise code and no sync/async twin.
- **NFR-5:** no file grows past its file-size cap (section 3.5), and no allowlist row is raised.

## 5. Decisions made here

1. **No Jira SDK and no new npm dependency.** Use `fetch` against the REST API, as `src/lib/tracker/rally-api.ts` does. The converters are hand-written.
2. **Polling, not webhooks.** Jira issues refresh on the Rally cycle (`poll-cadence.ts` `rally: { default: 120_000, min: 60_000, max: 600_000 }`). Jira webhooks are a follow-up.
3. **Listing uses JQL scoped to the project key:** `project = "<KEY>" AND statusCategory != Done ORDER BY updated DESC`. When `includeClosed` is true, drop the `statusCategory` clause. Cloud uses `GET /rest/api/3/search/jql` with `nextPageToken` paging. DC uses `GET /rest/api/2/search` with `startAt` paging. Cap the total at the `limit` filter (default 100), matching `pollRally`.
4. **Assignee and author are display names** (`fields.assignee.displayName`). Writing an assignee resolves the name to an `accountId` (Cloud: `GET /rest/api/3/user/search?query=<name>`) or a `name` (DC) only inside `updateIssue`/`createIssue`.
5. **Priority maps by name:** Highest to 1, High to 2, Medium to 3, Low and Lowest to 4. Unknown or missing maps to 3. Writes use the reverse map (1 to Highest, 2 to High, 3 to Medium, 4 to Low).
6. **The Jira project key is the project's `issue_prefix`.** There is no separate `jira.project_key`, so one value cannot drift from the other. Jira keys must be 1 to 10 letters. Keys containing digits or underscores (`AB2`, `MY_PROJ`) are out of scope, because `parseIssueId` and the existing `issue-prefix-invalid` check accept letters only (PAN-4860).
7. **Routing fix is narrow (FR-13).** `parseGitHubRepos` skips projects whose `tracker` is exactly `'jira'`, so `resolveGitHubIssue` answers "issue lives on GitHub" correctly for them. A new `resolveGitHubPullRequestRepo(issueId)` answers "which repo holds the PRs". It returns `resolveGitHubIssue`'s answer when `isGitHub` is true; otherwise, for a `tracker: jira` project with `github_repo`, it returns that repo. The four PR-semantic callers in 3.2 switch to it. Every other project resolves exactly as today, and a regression test pins the PAN-2449 shape.
8. **Jira writes go through one non-failing seam.** `src/lib/tracker/jira-lifecycle.ts` exports `transitionJiraIssue(issueId, target)`, `commentOnJiraIssue(issueId, markdown)` and `linkJiraPullRequest(issueId, prUrl)`. Each returns a `JiraWriteOutcome` and **never fails**: network, auth and "no transition" all come back as outcome values, and the seam logs them. Callers branch on `resolveTrackerType(issueId) === 'jira'` and call the seam. This puts the "never blocks a merge" rule (FR-6, AC3) in one place, so `merge-agent.ts`'s rethrow and close-out's 422 cannot fire for Jira. No fourth bespoke Effect client is added to `server.ts`.
9. **PR link and PR comment.** `pan done` calls `linkJiraPullRequest(issueId, prUrl)` for each PR that `openOrUpdatePullRequests` returns, and `transitionJiraIssue(issueId, 'in_review')`. With `--comment`, it also calls `commentOnJiraIssue` with the same `🤖 **Agent completed work:**` text Linear gets. Close-out (`closeViaDirect`) calls `linkJiraPullRequest` (idempotent by `globalId = prUrl`), `transitionJiraIssue(issueId, 'done')`, and `commentOnJiraIssue` with `Closed by Overdeck after merge of <prUrl>.` When the PR URL is unknown, the comment reads `Closed by Overdeck.`
10. **Canonical targets travel past the four-value tracker union.** `JiraTracker` adds a public method beyond the interface: `transitionToCanonical(key, target: JiraTransitionTarget): Effect<JiraTransitionOutcome, AnyTrackerError>`, where `JiraTransitionTarget = CanonicalState | 'in_planning'`. `transitionIssue(id, IssueState)` maps `open` to `todo`, `in_progress` to `in_progress`, `in_review` to `in_review` and `closed` to `done`, then delegates. The tracker `Issue` interface gains an optional `canonicalState?: CanonicalState` that the Jira adapter fills on every read. `rawState` carries the Jira status name.
11. **Dashboard `IssueState` to Jira target:** `open` to `todo`; `in_planning` to `in_planning`, which writes only when `jira.status_map.in_planning` is set and otherwise returns `already` with no request; `in_progress`; `in_review`; `verifying_on_main`; `closed` to `done`; `canceled`.
12. **Transition choice (`pickJiraTransition`):**
    1. Wanted status name = `status_map[target]`, else the `state-mapping.ts` jira default for that canonical state.
    2. If the current status name equals the wanted name (case-insensitive), return `already`.
    3. Otherwise pick the transition whose `to.name` equals the wanted name (case-insensitive).
    4. Otherwise, only for targets `todo`, `in_progress` and `done`, pick the single transition whose `to.statusCategory.key` is `new`, `indeterminate` or `done` respectively. This step applies only when exactly one such transition exists.
    5. Otherwise return `no-transition` with `wanted` and `available` (each `id`, `name`, `to.name`).
13. **Read mapping (`jiraStatusToCanonical`):**
    1. Case-insensitive reverse lookup of the merged status map. The first canonical key in `CANONICAL_STATES` order wins, so `In Review` maps to `in_review`, not `verifying_on_main`.
    2. Otherwise the status category: `new` to `todo`, `indeterminate` to `in_progress`, `done` to `done`.
    3. Otherwise `todo`.
14. **The `state-mapping.ts` jira entry becomes live.** It provides the default status names. Its `missingStateStrategy` stays unread.
15. **Credentials order:** `loadConfig().trackerKeys.jira` / `jiraEmail` / `jiraBaseUrl` (Settings). `load.ts` fills these from `JIRA_API_TOKEN` / `JIRA_EMAIL` / `JIRA_BASE_URL`, which `loadOverdeckEnv()` loads from `~/.overdeck.env` in both the CLI (`src/cli/index.ts:12`) and the dashboard (`src/dashboard/server/config.ts:69`). The site URL is the project's `jira.site` when set, else `trackerKeys.jiraBaseUrl`. Cloud requires the email. DC ignores it.
16. **Auth scheme by deployment.** Cloud uses `Basic base64(email:token)`. DC uses `Bearer token`. Deployment comes from `jira.deployment` when set. Otherwise a host ending in `.atlassian.net` is `cloud`, with no request. Otherwise one unauthenticated `GET /rest/api/2/serverInfo` is cached per site for the process lifetime: `deploymentType === 'Cloud'` gives `cloud`, anything else `datacenter`, and a failed probe falls back to `datacenter`.
17. **Settings has three flat keys,** `tracker_keys.jira`, `tracker_keys.jira_email` and `tracker_keys.jira_base_url`, rendered as three rows by the existing `TrackerKeysSection` loop. A nested object would break the one-string-per-row component.
18. **Add-project gains an optional tracker choice.** `ProjectCreateInput` gains `tracker?: 'jira'` and `jiraSite?: string`. The dialog shows an "Issue tracker" select (`Detect from remote` / `Jira`). Choosing Jira shows a "Jira site URL" field. `create-perform.ts` writes `tracker: 'jira'` and `jira: { site }`, after the GitHub/GitLab block, so the code repo is still written as `github_repo`/`gitlab_repo`. The CLI `pan project add` gains `--tracker jira` and `--jira-site <url>`.
19. **No shadow mode for Jira.** `shadow.trackers` gains no `jira` key. Shadow mode is a Rally/Linear feature and is out of scope.
20. **`command-deck.ts` sync-discussions stays as it is.** It has 2 spare lines. Jira comments reach planning through the planning prompt (WI-15), and the issue view through `fetchIssueDiscussions` (WI-17).
21. **Global `[trackers.jira]` is optional.** `TrackersConfig` (`src/lib/config.ts:51`) gains `jira?: JiraTrackersConfig` (`{ type: 'jira'; site?: string }`) only so that `trackersConfig[trackerType]` still type-checks. Jira is configured per project, and nothing requires the global entry.
22. **The factory's `jira` case works from a prefix alone.** Generic callers already pass the issue prefix as `team` (`pipeline-membership-gather.ts:197`, `team: issuePrefix`; `issue-closed.ts:69`, `team: resolvedProject.linearTeam`). So `createTracker({ type: 'jira' })` takes the Jira project key from `config.project ?? config.team`. It looks up the owning project with the existing `findProjectByTeam(key)` (`src/lib/projects.ts`, anchor `export function findProjectByTeam`) to read `jira.site`/`deployment`/`status_map`. The site comes from `config.site`, else the project `jira.site`, else `trackerKeys.jiraBaseUrl`. A new `createJiraTrackerForIssue(issueId)` derives the prefix with `extractPrefix` and calls it. With this, pipeline membership and `readLiveTrackerIssueState` work for Jira with no further edit.
23. **The destructive reaper never reads a Jira issue as closed in this issue.** `isTrackerIssueClosed` (`src/lib/cloister/issue-closed.ts:85`) returns false for every non-GitHub, non-Linear tracker (`isLinearIssueClosed` starts with `if (resolveTrackerType(issueId) !== 'linear') return false;`). That is the safe direction, because the reaper deletes workspaces. Jira workspaces are cleaned through the explicit close-out path (WI-13). Reaper support for Jira is a follow-up.
24. **GitHub-only surfaces stay GitHub-only.** `pan close --abandon` (`src/cli/commands/close.ts:288`, which refuses non-GitHub issues with an explicit message) and the `pan sync` drift checks (`src/cli/commands/sync.ts:807,870`, which skip non-GitHub ids) need no Jira branch. Both already skip or refuse cleanly.

## 8. Acceptance criteria

1. **AC-1 (WI-10).** Given a project with `tracker: jira` and valid credentials, when the dashboard polls, then its open Jira issues appear as rows with `source: 'jira'` and `canonicalStatus` equal to their mapped canonical state. The kanban places them in that column.
2. **AC-2 (WI-15, WI-16).** Given a Jira key, when planning or work starts, then the planning issue has the title and Markdown description, and the work-agent tracker context contains both. `pan start` moves the Jira issue to the status mapped to `in_progress` (WI-18).
3. **AC-3 (WI-7, WI-9, WI-12).** Given a Jira workflow with no transition to the wanted status, when a lifecycle action runs, then a `[jira]` warn line names the wanted status and the available transitions, and the step completes with success.
4. **AC-4 (WI-13).** Given a merged PR for a Jira issue, when close-out runs, then the seam was called to transition to `done`, a remote link with `globalId` equal to the PR URL was posted, and the close comment contains the PR URL.
5. **AC-5 (WI-5).** Given an HTTP 429 with `Retry-After: 2`, when the adapter calls Jira, then it retries after 2 s under fake timers and returns the second response.
6. **AC-6 (WI-21).** Given invalid credentials, when `pan doctor` runs, then it prints an error row for Jira whose fix names `JIRA_API_TOKEN` and Settings.
7. **AC-7 (WI-3, WI-6, WI-7, WI-8).** Unit tests cover the adapter for both deployment types, both converters, the state mapping, and id resolution with a Jira and a Linear project side by side, plus the PAN-2449-shape regression.
8. **AC-8 (WI-26, WI-27).** `configuration/issue-trackers.mdx` has a Jira section with Cloud and Data Center setup. Every tracker enumeration in `configuration/issue-trackers.mdx`, `concepts.mdx` and `cli/overview.mdx` lists Jira.
9. **AC-9 (WI-3).** A `tracker: jira` project with `github_repo` gives `resolveGitHubIssue(...).isGitHub === false` and a non-null `resolveGitHubPullRequestRepo(...)`. The PAN-2449 shape is unchanged.
10. **AC-10 (all).** `npm run typecheck`, `npm run lint` (which includes the file-size guard and `lint:effect-facades`) and the touched test files pass, and no allowlist row changed.

## 10. Repo rules that intersect this change (restated)

- **Fake timers** for every retry, backoff or delay test: `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()`. Never real `setTimeout` waits. Use `AbortController` plus `setTimeout` for timeouts, not `AbortSignal.timeout`, because happy-dom ignores fake timers there.
- **No `execSync`** in dashboard server code or anything reachable from it, and no new `*Sync` function. Server code uses async variants.
- **One variant per operation** in `src/lib` (`npm run lint:effect-facades`). No exported Effect wrapper around in-repo Promise code.
- **File-size guard:** never grow a file past its cap. Extract instead. Never raise an allowlist row.
- **Source-reading tests and new `skipIf`/`.only` fail lint.** Assert behaviour, never grep source in a test.
- **New lib modules import `getAgentState` from `agent-state-read.js`,** only if they need it, to avoid `lint:circular`.
- **Fake secrets** are built at runtime in fixtures, never as token-shaped literals (GitHub push protection GH013).
- **A new HTTP route needs a `no-loss-matrix.ts` row.** This plan adds no route; WI-11 changes only existing ones.
- **Quality gates before `pan done`:** `npm run typecheck`, `npm run lint`, and `npx vitest run <touched test files>`. Never the full `npm test` on the host.
