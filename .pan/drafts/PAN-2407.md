# PAN-2407 — One paved-road verb: `pan start` takes an issue from any state to running work

**Issue:** https://github.com/eltmon/overdeck/issues/2407
**Mode:** auto planning (non-interactive) — inferred choices recorded in `plan.autoDecisions[]`.

## Glossary

- **Paved road** — the single default command an operator types to "get this issue moving", regardless of what state the issue is in.
- **Planning mode** — how much planning happens before work starts: `interactive` (Q&A planning session), `auto` (non-interactive planning agent), `skip` (no planning agent; a minimal vBRIEF is synthesized from the issue title/body).
- **start-planning endpoint** — `POST /api/issues/:id/start-planning`, the dashboard route that creates the planning workspace and spawns the planning agent. Accepts `auto` and `autoStart` booleans (`src/lib/overdeck/planning-sessions.ts:142-143`).
- **auto-start stamp** — `autoSpawnOnFinalize: true` persisted in the planning agent state when planning is launched with `--auto-start`; `pan plan finalize` reads it (`src/cli/commands/plan-finalize.ts:131-132`, resolver `resolveAutoSpawnOnFinalize` at `src/lib/planning/spawn-planning-session.ts:82`) and auto-spawns the work agent after promotion.
- **Synthesized minimal vBRIEF** — the output of `writeAutoStartVBrief` + `createBeadsFromVBrief` (`src/cli/commands/start.ts:1215-1232`), today reached via `pan start --auto`.
- **Plan exists** — a spec resolvable for the issue: `findPlanSync(workspace)` when a workspace exists (`src/lib/vbrief/io.ts`), else `findSpecByIssue(projectRoot, issueId)` from `src/lib/pan-dir/specs.ts:216`.

## Problem

Getting an issue moving requires knowing a 2-verb × 3-flag matrix:

| You want | You must type today |
| --- | --- |
| Interactive planning only | `pan plan <id>` |
| Auto planning only | `pan plan <id> --auto` |
| Auto planning + start work | `pan plan <id> --auto --auto-start` |
| Skip planning, start work | `pan start <id> --auto` |
| Start work (plan exists) | `pan start <id>` |

Worse, `pan start <id>` on an **unplanned** issue today does not auto-plan — it silently creates one generic bead ("Implement issue", `src/cli/commands/start.ts:1239-1261`) and starts work with no real plan.

## Proposal

`pan start <id>` becomes the paved road: it takes the issue from whatever state it's in to running work.

- **No plan** → kick off planning at the configured depth, with the auto-start stamp set, so work begins automatically when planning finalizes.
- **Plan exists** → spawn work (current behavior, unchanged).
- **Work agent already running** → no-op with a clear message, exit 0.

Planning depth is one dial: `pan start <id> --plan interactive|auto|skip`, defaulting to new config key `planning.default_mode` (shipped default `auto`).

`pan plan <id>` remains the plan-ONLY verb. Its `--auto-start` flag is deprecated (warn + pointer to `pan start`); `pan start --auto` is deprecated as an alias of `--plan skip`. All old invocations keep working through the deprecation window.

## Requirements

- **FR-1** `pan start <id>` on an issue with no plan POSTs the start-planning endpoint with `auto: true, autoStart: true` (when effective mode is `auto`), streams SSE progress like `planCommand` (`src/cli/commands/plan.ts:53-84`), and exits reporting that the work agent will start automatically after planning finalizes.
- **FR-2** `pan start <id> --plan <mode>` accepts `interactive`, `auto`, `skip`; any other value exits 1 with an error listing the three valid modes.
- **FR-3** New config key `planning.default_mode` in `~/.overdeck/config.yaml` supplies the default mode. Unset → `auto`. An invalid config value makes `pan start` exit 1 naming the key and valid values (no silent fallback).
- **FR-4** `--plan skip` behaves exactly like today's `pan start --auto`: synthesized minimal vBRIEF + beads, then spawn work; works without the dashboard.
- **FR-5** `pan start --auto` keeps working as a deprecated alias of `--plan skip` and prints a deprecation warning naming `--plan skip`.
- **FR-6** `pan plan <id> --auto-start` keeps working (still stamps `autoSpawnOnFinalize`) and prints a deprecation pointer to `pan start <id>`.
- **FR-7** `pan start <id>` when the work agent's tmux session is live prints a no-op message (naming `pan tell <id>` and `tmux attach -t agent-<id>`) and exits 0. Paused and troubled gates keep their current exit-1 behavior.
- **FR-8** When a plan exists, `pan start <id>` runs the current work-spawn path unchanged.
- **FR-9** `pan start --dry-run` on an unplanned issue prints which planning mode it would use and exits without POSTing start-planning or creating anything.
- **FR-10** `sync-sources/skills/pan-start/SKILL.md` and `sync-sources/skills/pan-plan/SKILL.md` document the new surface; `scripts/lint-skills.sh` exits 0.
- **FR-11** The project `CLAUDE.md` "Planning Modes" section presents `pan start` as the paved road and marks the deprecated flags.
- **NFR-1** No dashboard API contract changes — the existing start-planning endpoint is reused as-is.
- **NFR-2** Backward compatibility: every currently-working invocation in the table above continues to work (with at most a deprecation warning).

## Design decisions (auto mode)

1. **Reuse the dashboard start-planning endpoint** rather than teaching the CLI to spawn planning sessions directly — identical to how `pan plan` works; keeps one spawn path (single-source-of-truth).
2. **Shipped default mode is `auto`** — per the issue's recommendation.
3. **Precedence:** `--plan` flag > legacy `--auto` (→ `skip`) > `planning.default_mode` > `auto`. If both `--plan` and `--auto` are passed, `--plan` wins and a warning is printed.
4. **`--plan interactive` also sets `autoStart: true`** — the issue specifies "Q&A session first, then continues to work on approval".
5. **Already-running → exit 0.** "No-op with a clear message" is a success for a command whose intent is "make it go" — it already is going. Paused/troubled remain exit 1 (those need operator action).
6. **Plan detection:** workspace exists → `findPlanSync(workspace)`; else `findSpecByIssue(projectRoot, issueId)` (Effect-based; a sync export mirroring `findSpecByIssueSync` in `src/lib/vbrief/io.ts:48` may be added). Any found spec counts as "plan exists" regardless of status; re-planning closed issues stays `pan reopen` territory.
7. **Mode validation happens at consumption** (in the resolver in `start.ts`), not at config load — config load stays resilient; the failure is loud where it matters.
8. **The single-generic-bead fallback (`start.ts:1239-1261`) is left in place.** It becomes unreachable on the paved road (unplanned issues route to planning first) but is retained as defense-in-depth for edge paths (additive-refactor/no-loss rule). Removing it is a NonGoal.
9. **Dashboard-down error:** when mode `auto`/`interactive` needs the endpoint and the dashboard is unreachable, fail with a message pointing at `pan up` (or `--plan skip` for offline).
10. **Deprecation is warn-only.** Flag removal is a future issue.

## Intersecting repo rules restated for the executor

- **Fake timers** for any retry/delay-based tests (`vi.useFakeTimers()`); SSE tests should mock `fetch`, never sleep.
- **Skills/CLI same-commit rule:** `scripts/lint-skills.sh` (in `npm run lint`) cross-checks SKILL.md flags against `pan <verb> --help`; the flag declaration and skill doc must land together.
- **No hardcoded model fallbacks** — untouched here; model/harness flags pass through as today.
- **No `execSync` in server-reachable code** — all changes are CLI-side; keep it that way.
- **Karpathy surgical-changes rule** — `start.ts` is 1,400+ lines; touch only the routing/entry sections named above.

- No changes to the start-planning or start-agent server route contracts.
- No removal of `pan plan`, `pan plan --auto`, `pan plan --auto-start`, or `pan start --auto` (deprecation warnings only).
- No removal of the single-generic-bead fallback in `start.ts`.
- No migration of flywheel/orchestrator call sites to the new surface (old flags keep working).
- No changes to remote (Fly.io) workspace spawn behavior beyond passing `workspaceLocation` through to start-planning.
