# PAN-4543 — `pan close` refuses landed, deployed issues

**Issue:** [PAN-4543](https://github.com/eltmon/overdeck/issues/4543)
**Base commit:** `cd27acfdc93` (main, 2026-10-04)
**Planning mode:** `pan plan --auto` (no operator questions; defaults recorded under "Decisions")

## Glossary

- **Close-out / `pan close`** — the ceremony in `src/lib/lifecycle/workflows.ts` `closeOut()` that evaluates the Definition-of-Done gate, archives planning, tears down the workspace, and closes the tracker issue. `pan close` runs it **in the CLI process**, not in the dashboard server (`src/cli/commands/close.ts`, `closeOutCommand` → `Effect.runPromise(closeOut(ctx, …))`).
- **DoD gate** — `evaluateDodGate()` in `src/lib/lifecycle/dod-gate.ts`. It computes nine rows (`DOD_ROWS` in `src/lib/lifecycle/dod.ts`). A row with status `miss` blocks close-out unless an operator passes `--accept-<row>`.
- **Row 3 (`verification`)** — `checkVerificationRow()`. Reads the workspace file `<workspace>/.overdeck/verification-latest.json` (the **latest artifact**).
- **Row 8 (`deploy`)** — `checkDeployRow()`. Fetches `GET <dashboard>/api/health` and checks that the live build commit contains the merge commit. Note: `dod.ts` numbers deploy as row 8; the `pan-close` skill text wrongly says row 7.
- **Settlement** — `TerminalVerdictSettlement { trackerClosed, landedWork, mainVerifyStatus }`, computed in `evaluateDodGate()` from rows 4 (merged) and 6 (main-verify). `landedWork` is `merged.status === 'pass'`; `mainVerifyStatus` is row 6's status.
- **Verification artifact** — `VerificationArtifact` in `src/lib/cloister/verification-artifact.ts`. Field `outcome` is today `'running' | 'passed' | 'failed'`. A **progress write** (options without `ranAt`) produces `outcome: 'running'`; a **terminal write** (options with `ranAt`) produces `passed`/`failed` and also writes an immutable **per-run file** under `.overdeck/verification/`.
- **Non-terminal artifact** — a latest artifact whose `outcome` is anything except `passed` or `failed` (today `running`; after this change also `skipped`).
- **Merged-skip** — `skipMergedVerification()` in `src/lib/cloister/verification-escalation.ts`. When the forge says the PR merged, it returns `{ outcome: 'skipped', reason: MERGED_VERIFICATION_REASON }` and the runner returns early. The runner (`runVerificationForIssueInProcess`, `src/lib/cloister/verification-runner.ts`) calls it at 8 points.
- **Event-loop stall** — a period where the dashboard server's Node event loop cannot service HTTP requests. `/api/health` normally answers in < 1 ms.
- **Implementation checkpoint** — a step whose answer needs live measurement. It states the fallback if measurement does not find an answer.

## Problem

Observed 2026-10-04 09:10–09:16 UTC while closing 18 merged and deployed issues (build `cd27acfd`):

1. **Row 8 times out.** 6 of 22 close-outs failed with `dod:deploy — dashboard not reachable at http://127.0.0.1:3011 … The operation was aborted due to timeout` (PAN-4509, PAN-4506, PAN-4383, PAN-4514, PAN-4541). Each passed on retry. A 0.5 s sampler saw `/api/health` take 4.66 s (09:15:17) and 4.05 s (09:15:51), each during a `pan close`. Each failure followed a **successful** close-out of the previous issue.
2. **Row 3 blocks on a stale `running` artifact.** PAN-4498 and PAN-4508 fail with `dod:verification — verification artifact: running at 2026-10-04T05:44:24Z` (and `05:45:37Z`). Both PRs passed verification (heads `3fe790ef`, `f91b6577`) and merged with green main CI.

Verified on disk during planning (`workspaces/feature-pan-4498/.overdeck/verification-latest.json`): `outcome: "running"`, `ranAt: 2026-10-04T05:44:24.683Z`, gates `install, typecheck, frontend-typecheck, lint, build, server-bundle` all `passed: true`, no `currentGate`. So a duplicate run (re-requested by deacon-lite at 05:06) finished every gate, then hit the **post-gate** merged-skip at `verification-runner.ts` line 592 (`const postGateMergedOutcome = await skipMergedVerification(issueId, logPrefix);`) and returned **before** the terminal write at line 637 (`const finalArtifact = writeVerificationArtifact(workspacePath, issueId, gateResults, {`). The last progress write (`outcome: 'running'`) stayed on disk forever.

## Root cause

1. `dod-gate.ts` line 278 (search: `signal: AbortSignal.timeout(3000)`) probes `/api/health` once with a 3 s budget; `checkDeployRow` (search: `health = await deps.readJson(\`${baseUrl}/api/health\`)`) has no retry. A 4–5 s server stall therefore produces a `miss`.
2. The stall itself is unexplained. Planning traced the most likely trigger (see WI-7): after a successful close-out the CLI calls `notifyCloseOutMembershipRefresh()` (`src/cli/commands/close.ts`, search `close-out-membership-refresh:`), which appends an `issue.statusChanged` event with `labels: ['closed-out']`. `src/dashboard/server/services/resource-refresh-triggers.ts` maps that to reason `issue.statusChanged:closed-out`, which is in `MEMBERSHIP_REFRESH_REASONS` (`project-resource-refresh-queue.ts`, search `'issue.statusChanged:closed-out'`), so the server runs `refreshResourceAllocatedProjects(…, { refreshMembership: true })` (`resource-discovery.ts` line ~845) for the whole project. That fits "failure follows a successful close-out". It is a suspect, not a proven cause.
3. `checkVerificationRow` (`dod-gate.ts` ~line 445–468) settles a **missing** artifact on landed work with green main CI (`if (!artifact && settlement?.landedWork && settlement.mainVerifyStatus === 'pass')`), but a `running` artifact falls through to `miss`.
4. The merged-skip path writes nothing, so the stale `running` file is never replaced.

## Decisions (auto mode)

- **D1 Retry on any error.** Connection refused during a deploy restart and a 5xx are as transient as a timeout. All three attempts failing is the real signal. Worst-case added latency: 3×5 s + 2×2 s = 19 s per close-out, acceptable for a human-gated ceremony.
- **D2 Retry lives in a new module** `src/lib/lifecycle/dod-deploy-probe.ts` (`readHealthWithRetry`), because `dod-gate.ts` has 12 lines of headroom. The pause uses `setTimeout` (fake-timer friendly), not an injected sleep. `forge-transient.ts` `retryTransientForgeOp` is not reused: it retries only forge-transient errors.
- **D3 Skipped writes are latest-only** (no per-run file). The run did not reach a verdict; `verification-cycles.ts` counts only `failed` per-run files and `readCiRuns` only `via: 'ci'` files, so neither changes behavior. Confirmed by reading `verification-cycles.ts` lines 60–150.
- **D4 Only the post-gate site finalizes, and only a `running` latest.** The early merged-skip sites (lines 304, 364, 420) run before this run writes anything, so the latest file belongs to a previous run (a real `passed`, or another run's `running`); a `running` artifact carries no run identifier, so the helper cannot tell whose it is. Those sites therefore pass no `workspacePath` (revised after plan critique round 1). The post-terminal sites (786, 837, 877) see this run's own terminal file, so finalizing there would be a no-op and they also pass none. The catch site (933) may fire before the first progress write, so it passes none either. Line 592 is the reported leak (all gates finished, no terminal write yet) and the one site where the `running` latest is certainly this run's own progress write.
- **D5 The finalize call lives in `skipMergedVerification`** (verification-escalation.ts, 200 lines) behind an optional `workspacePath` parameter, so the runner changes in place with zero net lines (NFR-1). The three callers inside `verification-escalation.ts` (`escalateVerificationStuck`, `deliverVerificationFeedback` ×2) pass no workspace and write nothing.
- **D6 Row 3 treats `skipped` like `running`.** Both are non-terminal for a verdict. A `failed` artifact keeps the existing path (`terminalVerdictSettlement`).
- **D7 Stall profiling never restarts the dashboard.** Primary method: `kill -USR1 <dashboard pid>` opens the inspector on `127.0.0.1:9229` in the running process; record a CPU profile over CDP while triggering the suspect. Fallback: a 100 ms `/api/health` latency sampler to discriminate suspects, then code reading. Reason: a restart with `--cpu-prof` is a deploy, which non-flywheel agents must not do.
- **D8 Trigger the suspect without appending events.** Re-sending the close-out event would append a new durable event row (its idempotency key includes a fresh timestamp) and fan it out to every subscriber, so it is ruled out (revised after plan critique round 1). Instead: (a) drive the membership half of suspect 1 with the existing operator "Retry membership" route `POST /api/pipeline/membership/refresh?project=overdeck` (`src/dashboard/server/routes/pipeline-membership.ts`, a re-gather with no durable write), and (b) observe the full close-out path passively by keeping the profiler and sampler attached while the operator or flywheel runs its own real `pan close`.
- **D9 The `pan close PAN-4498/PAN-4508` acceptance check is post-deploy.** The work agent cannot run it (it closes tracker issues and has no dry run). It stays in "Post-deploy verification" below and is not an item acceptance criterion.
- **D10 Fix the pan-close skill's row numbering** in the docs item (deploy is row 8; add `--accept-ship` row 7). It is the same doc surface the change touches.
- **D11 No change to the error path.** The runner's `catch` (line ~933) still returns `error` without finalizing a `running` artifact when the PR is not merged. Row 3's new rule already covers that file at close-out; changing the error path is out of scope.

```ts
/**
 * PAN-4543: a run that ends without a verdict (the PR merged mid-run) must not
 * leave its last progress write ('running') as the latest artifact. Rewrites
 * the latest file to 'skipped' only when it is still 'running', so a real
 * earlier verdict is never erased. Latest-only: no per-run file.
 */
export function markRunningVerificationArtifactSkipped(
  workspacePath: string,
  reason: string,
  now: Date = new Date(),
): VerificationArtifact | null {
  const current = readVerificationArtifact(workspacePath);
  if (!current || current.outcome !== 'running') return null;
  const { currentGate: _gate, currentGateOutput: _tail, ...rest } = current;
  const skipped: VerificationArtifact = { ...rest, outcome: 'skipped', skipReason: reason, ranAt: now.toISOString() };
  writeFileSync(verificationArtifactPath(workspacePath), JSON.stringify(skipped, null, 2));
  return skipped;
}
```

```ts
/** PAN-4543: DoD row 8's /api/health probe, retried across a short server stall. */
export const DEPLOY_PROBE_ATTEMPTS = 3;
export const DEPLOY_PROBE_TIMEOUT_MS = 5000;
export const DEPLOY_PROBE_PAUSE_MS = 2000;

export async function readHealthWithRetry(
  readJson: (url: string) => Promise<Record<string, unknown>>,
  url: string,
): Promise<Record<string, unknown>> {
  let lastError: unknown;
  for (let attempt = 1; attempt <= DEPLOY_PROBE_ATTEMPTS; attempt++) {
    try {
      return await readJson(url);
    } catch (error) {
      lastError = error;
      if (attempt < DEPLOY_PROBE_ATTEMPTS) await new Promise(resolve => setTimeout(resolve, DEPLOY_PROBE_PAUSE_MS));
    }
  }
  const message = lastError instanceof Error ? lastError.message : String(lastError);
  throw new Error(`after ${DEPLOY_PROBE_ATTEMPTS} attempts: ${message}`);
}
```

## Stall profile findings (PAN-4543 WI-7)

**Verdict: found and fixed.** The 4–5 s `/api/health` stall is `GET /api/costs/summary`. On `main` (`b01b6dd6c5b`) it ran three synchronous full scans of `~/.overdeck/costs/events.jsonl` per request (`src/dashboard/server/routes/costs.ts` lines 82–84, each `readEvents({ startDate })` → `src/lib/costs/events.ts:282` `readEvents` → `events.ts:96` `scanEventLinesSync`). God View polls this route every 30 s (`useConfluenceData.ts`, `refetchInterval: 30_000`), and the project overview polls it every 60 s. The stall was unrelated to close-out. A 3 s probe overlapping a ~4.8 s block every 30 s fails about (4.8 + 3) / 30 ≈ 26% of the time, which matches 6 of 22 observed failures. The 34 s gap between the two sampler spikes (09:15:17, 09:15:51) fits the 30 s poll plus jitter.

**Method.** No signal was sent to the live dashboard and nothing was restarted. D7's `kill -USR1` was not used, because it opens an inspector port that only a restart closes. The membership refresh route needs a CSRF or internal token, so it was not called either. Each suspect was imported and run out of process under `node --import tsx --cpu-prof`, with `perf_hooks.monitorEventLoopDelay` measuring the longest event-loop block:

| Suspect | Wall time | Max event-loop block |
| --- | --- | --- |
| 1a. `refreshMembershipSnapshotsForProjects([panopticon-cli])` ×3 | 4.6–5.1 s (awaiting the forge) | 15–18 ms |
| 1b. `refreshResourceAllocatedProjects(…, { refreshMembership: false })` ×3 | 0.8–12.2 s | 264–328 ms |
| 2. Closed-issue reaper (`closed-issue-reaper.ts` → `reap-issue-residue.ts` `rmSync` fallback) | — | runs in the Deacon child process, not the dashboard event loop |
| `readEvents({ startDate: monthAgo })` on the live 386 MB log (one scan) | 1.5–1.6 s | ≈ wall time (fully synchronous) |

The suspect-1 CPU profile is 92% idle. Its heaviest self-time frames are `lstat` (332 ms) and `spawn` (198 ms) over a 29 s run, so it is ruled out. The dashboard log (`~/.overdeck/logs/dashboard.log`) has no timestamps and cannot be aligned to 09:15. It does show 11,735 `Skipping malformed event line` warnings from the same cost-log scanners.

**Fix (this item's commit).** `src/lib/costs/events.ts` adds `readEventsSince(startDate)`, an async chunked reader. It uses the same bounded 64 KB chunks as `scanEventLinesSync`, but awaits each `FileHandle.read`, so the loop serves other requests between chunks. The summary route does one async scan of the month window and filters week and today from it in memory. Measured on the live 386 MB log: wall 1.0–1.1 s (was ~4.8 s), **max event-loop block 10 ms** (was ~4.8 s). `tests/unit/lib/costs/read-events-since.test.ts` proves windowing, malformed-line skipping, chunk-boundary correctness, and that the read yields the event loop (a `setImmediate` callback runs before it resolves). No `*Sync` call was added (NFR-3).

**Follow-up.** [PAN-4544](https://github.com/eltmon/overdeck/issues/4544): `GET /api/costs/stream`, polled by the Pipeline view, still blocks ~1.6 s per poll through sync `tailEvents` / `readEvents`. That is below the row 8 probe timeout (5 s, three attempts), so it no longer fails close-out. Fixing it needs async tail reads and an audit of other request-path cost readers, which is beyond this item.
