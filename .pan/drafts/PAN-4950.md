## Glossary

- **Connector:** the new Node process `pan mcp connector serve`. It runs next to a self-hosted bot (Hermes, OpenClaw, Grok Build on another computer), pairs once with one Overdeck machine, and serves the Overdeck MCP tools to the bot on `127.0.0.1:7466/mcp` (HTTP) or stdio. Every tool call travels to the machine over a Noise-encrypted secure channel inside a WebRTC data channel.
- **Machine:** the Overdeck dashboard (`pan up`) the connector pairs with. It holds the `connector` access-token record W-CONN1 mints.
- **Connector home:** the connector's own state directory, `$OVERDECK_CONNECTOR_HOME`, default `~/.overdeck-connector`, mode 0700. The connector never reads or writes `~/.overdeck/` (`OVERDECK_HOME`), so it can run on an Overdeck machine without touching that machine's sign-in, keys or config.
- **Account token:** the `odd_…` overdeck.ai device token from the RFC 8628 device flow (`requestDeviceCode` / `pollForToken`, `src/lib/account/client.ts:91`, `:131`). It authenticates the connector to the directory.
- **Directory:** `services/connect`, reached at `wss://connect.overdeck.ai/v1/directory`. The connector joins it as a **client** with `hello-client`, `platform: 'node'` (W-DIR1, D-18). It relays WebRTC signalling (`signal` frames) and hands out ICE servers (`ice-servers` frames). It routes signals only between sockets of the **same overdeck.ai account**.
- **`DirectoryWebClient`:** the client-role directory socket (`packages/anywhere-channel/src/directory-web.ts:95`). It takes an injectable `WebSocket` class (default `globalThis.WebSocket`) and sends the account token as the subprotocol `overdeck.bearer.<token>`.
- **`RtcTransport`:** the server's werift WebRTC transport (`src/lib/anywhere/channel/rtc-transport.ts:65`). `dial(peerEnvironmentId, { relay, purpose, signal })` resolves with a raw `Duplex` (`RtcDuplex`, which counts `bytesIn` / `bytesOut`, `rtc-duplex.ts:22-23`). One `RTCPeerConnection` per (peer, relay, purpose); each dial opens one more data channel on it.
- **Route:** how the connector reaches the machine. `rtc://<environmentId>` is a direct WebRTC path (STUN, no relay). `rtc+turn://<environmentId>` forces the TURN relay (relay plan only). Only ciphertext crosses either.
- **Secure channel / `ChannelSocket`:** the Noise handshake plus encrypted stream (`openChannel` / `openChannelOverTransport`, `src/lib/anywhere/channel/open.ts:47`, `:60`). **Pairing mode** (`{ mode: 'pairing', pairingCode }`, Noise XXpsk0) is keyed by the one-time `odp_` code. **Link mode** (`{ mode: 'link', remoteKeyHex }`, Noise IK) pins the machine's public key. `ChannelSocket.channel.remoteKeyHex` is the peer's proven static key.
- **Link key:** the connector's X25519 static key pair used in both pairing and link channels. The machine binds the `connector` record to its public key (`connectorKey`, W-CONN1). A fresh link key is generated on every `pair`.
- **Install key:** a second X25519 key pair, generated once per connector home. Its public half is sent as `hello-client.publicKeyHex` (the directory requires the field; for a `node` client it is not a push key, `packages/contracts/src/connect.ts:251-255`).
- **`clientId`:** a UUID v4 generated once per connector home. It is the directory client id, the device-flow `environment_id` (as the phone app does, `apps/mobile/src/shell/signIn.ts:51`), and the `clientId` sent to `POST /api/connectors/exchange`.
- **Pairing string:** `overdeck-connector:/pair#v=1&e=<environmentId>&k=<machineKeyHex>&c=<odp_code>`, shown by "Connect a bot" (W-BOT1). `parseConnectorPairLink(text)` (`packages/contracts/src/connector-pairing.ts:25`) parses it and returns `null` on any malformed part.
- **Connector token:** the `odk_…` token the exchange returns. It resolves on the machine only inside a link channel from the bound link key (`resolveDashboardCredential`, `src/dashboard/server/routes/dashboard-auth.ts:197-201`). Its scopes are a subset of `read:state, read:conversations, tell, operate, approve` (`read:state` always on).
- **Local token:** an `odl_<64 lowercase hex>` value in `<connectorHome>/local-token` (0600). A bot must send `Authorization: Bearer <local token>` to the loopback endpoint.
- **`LinkRouteSource` / `linkFetch`:** the dashboard's client for linked machines (`src/lib/anywhere/link-client.ts:62-69`, `:238`). `linkFetch(environmentId, path, { method, body, signal, routeSource })` sends one JSON request over a pool of secure channels (`LinkAgent`: `maxSockets: 4`, idle close `LINK_POOL_IDLE_MS = 4_000`), with `host: 'link.invalid'` and one resend of a `GET` that died on a stale pooled channel. The `routeSource` argument is a seam: any object with `routeFor`, `waitOnline` and `localKey` can drive it. The connector supplies its own.
- **Fleet spawn routes:** `POST /api/fleet/conversations`, `POST /api/fleet/workers`, `POST /api/fleet/issues/:id/start` (`src/dashboard/server/routes/fleet-work.ts:451-500`). The MCP tools `start_conversation`, `start_worker` and `start_issue` call **only** these routes, even for this machine (`src/lib/mcp/tools-write.ts:95`, `:135`, `:164`).
- **Relay metering:** the directory counts relay bytes only from the initiator's `relay-usage` frames (the responder never reports, `src/dashboard/server/services/relay-client.ts:5-7`). Over `rtc+turn://` the connector is the initiator, so it must report.

## Requirements

### Functional

- **FR-1 Connector home.** All connector state lives in the connector home (default `~/.overdeck-connector`, override `OVERDECK_CONNECTOR_HOME`): directory mode 0700, files `account.json`, `identity.json`, `pairing.json`, `local-token`, each mode 0600, each written atomically. Nothing under `~/.overdeck/` is read or written.
- **FR-2 Login.** `pan mcp connector login [--account-url <url>] [--directory-url <url>] [--label <name>]` runs the overdeck.ai device flow with `environment_id = clientId`, prints the URL and code, and stores the account token, device id and both service URLs in `account.json`.
- **FR-3 Pair.** `pan mcp connector pair '<pairing string>' [--label <name>]` needs a login; it dials the machine through the directory (direct, then relay when allowed), opens a pairing-mode channel with the code and a fresh link key, calls `POST /api/connectors/exchange`, refuses a machine whose proven key or descriptor key differs from the string's `k`, writes `pairing.json`, creates `local-token` if absent, and prints the next steps.
- **FR-4 Serve.** `pan mcp connector serve [--port <n>] [--stdio]` connects to the paired machine and serves the Overdeck MCP tools: HTTP on `127.0.0.1:<port>` (default 7466) `POST /mcp`, stateless JSON, local token required; `GET /healthz` answers `{ ok, machine, route }`; `--stdio` serves one stdio session instead. Each tool call is forwarded to the machine with the connector token over a link channel.
- **FR-5 Route and reconnect.** The connector tries `rtc://` first and falls back to `rtc+turn://` only when the directory's `welcome-client.relayAllowed` is true and the relay is not stopped; otherwise it reports "No direct path to <machine label>. Use the relay plan, or the Tailscale route in the README." After a lost connection it reconnects with back-off 1 s doubling to 60 s, reset on success.
- **FR-6 Relay metering.** Every relay data channel the connector opens is metered and reported to the directory as `relay-usage`, every 60 s and when the channel closes. A `relay-status` with `stopped: true` closes relay channels and refuses new relay dials with `RELAY_CAP_MESSAGE`.
- **FR-7 One machine.** A connector reaches only its paired machine. Its tool list omits `list_machines`, and the start tools omit the `machine` and `needs` arguments and refuse them when sent.
- **FR-8 Local work through a connector.** The fleet spawn routes admit a `connector` credential for a target that resolves to this machine and refuse any other target with 403 `{ code: 'connector-local-only' }`. So `start_conversation`, `start_worker` and `start_issue` work through a connector holding `operate`.
- **FR-9 Status and logout.** `pan mcp connector status` prints the signed-in account, the paired machine, the scopes and the live route (from the running `serve`'s `/healthz`, or "not serving"). `pan mcp connector logout` calls `DELETE /api/connectors/self` (best effort), sends `forget-client`, revokes the overdeck.ai device (best effort), and deletes the four home files.
- **FR-10 Documentation.** `configuration/mcp.mdx`, `docs/ANYWHERE-ARCHITECTURE.md` and `docs/DASHBOARD-AUTH.md` describe the shipped connector and the connector fleet rule (WI-11).

### Non-functional

- **NFR-1 Secrets stay in 0600 files and headers.** The account token, connector token, link and install secret keys and local token never appear in argv, environment exports the connector writes, logs, stdout or `/healthz`. stdout in `--stdio` mode carries only JSON-RPC; all diagnostics go to stderr.
- **NFR-2 Loopback only.** The HTTP endpoint binds `127.0.0.1` only and compares the local token in constant time.
- **NFR-3 Async only.** No `execSync`, `spawnSync`, `execFileSync`, `readFileSync`/`writeFileSync` or any new `*Sync` function in the new modules (repo rules `no-execsync-server`, `prefer-async`).
- **NFR-4 Fake timers.** Tests of back-off, probe timeouts, the relay meter interval and the device-flow wait use `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()`; never real sleeps (repo rule `fake-timers-for-retry-tests`). Timeouts in code use `AbortController` + `setTimeout`, never `AbortSignal.timeout`.
- **NFR-5 Lazy CLI load.** `src/cli/commands/mcp-connector.ts` imports only Commander types statically; werift, the directory client, the channel code and the MCP SDK load inside action handlers, so `pan` startup does not pay for them.
- **NFR-6 Module size.** Every new module stays under 600 lines; no edited file grows past its `origin/main` line count plus its stated budget.
- **NFR-7 Effect boundary.** No Effect wrappers in the new modules; `npm run lint:effect-facades` does not rise.
- **NFR-8 No new HTTP route.** This issue adds no dashboard route, so `route-scopes.ts` and `tests/unit/lib/overdeck/no-loss-matrix.ts` are unchanged. The connector's own loopback server is not a dashboard route.
- **NFR-9 No plaintext through overdeck.ai.** Pairing and link traffic always run inside the Noise channel; the directory and TURN relay carry only signalling and ciphertext.

## Decisions

- **D-1 Reuse `linkFetch` with a connector `LinkRouteSource`.** The connector implements `LinkRouteSource` (`routeFor`, `waitOnline`, `localKey`) and registers its RTC dialer with `setRtcDialer`; its `DashboardApi` calls `linkFetch(environmentId, path, { method, body, signal, routeSource })`. Why: `LinkAgent` already gives the pool the epic asks for (4 channels, 4 s idle), `channelAgent`-style keep-alive, `host: 'link.invalid'` and the stale-channel resend; a second copy would drift. The adapter maps a `json` of `{ error: 'invalid-json', … }` to `null` so tool projections behave as with `createFetchDashboardApi` (Fact 14).
- **D-2 Warm before online (CP-6).** Because `openLinkSocket` bounds a dial at 2.5 s (Fact 13), `routeFor` reports `state: 'online'` only after a **probe** — one link-mode `openChannel` on the chosen route with `timeoutMs: PROBE_TIMEOUT_MS = 15_000`, then the probe channel is closed — has established the `RTCPeerConnection`. Later pooled dials reuse that warm connection. Before every probe after the first, the connector calls `transport.close(environmentId)` so a dead peer connection is never reused.
- **D-3 Connection loss.** Any request failure whose error is a `ChannelOpenError` or a `LinkUnavailableError`, or a `directory` frame showing the machine offline, flips the route to `connecting` and starts the reconnect loop: probe direct, then relay when allowed; on failure wait `min(1_000 × 2^n, 60_000)` ms and try again; reset `n` on success. A directory frame showing the machine back online triggers an immediate probe. The tool call that saw the failure returns its error; the bot retries.
- **D-4 Route choice.** Direct first. Relay only when `directory.relayAllowed` and the last `relay-status` is not `stopped`. If both fail and relay is not allowed, the error text is exactly `No direct path to <label>. Use the relay plan, or the Tailscale route in the README.` (`<label>` = the paired machine label from `pairing.json`).
- **D-5 Connector-local fleet spawns (FR-8).** The epic said fleet `machine` arguments are "hidden or refused" through a connector, assuming local targets still worked; they do not (Fact 18). Chosen fix, smallest that keeps "no chained hops": a new `fleetSpawnGate` admits a channel request whose credential is `kind: 'connector'`; `fleetCaller` maps a connector to `{ actor: 'operator', ceiling: <its scopes>, viaToken: true, localOnly: true }`; each of the three spawn handlers answers 403 `{ code: 'connector-local-only', error: 'An Overdeck connector reaches only the machine it paired with; run a second connector for <label>.' }` when `caller.localOnly` and the resolved target is not `self`, **before** any side effect (worker id allocation, stand-in write, work-door post). `mayCreateFly` is `false` for a connector, so `machine: "fly"` never creates a VM. `POST /api/fleet/placement`, `POST /api/fleet/workers/:id/stop` and every fleet GET keep refusing channel callers. The alternative (hide the three start tools from connectors) was rejected because it makes `operate` inert while W-BOT1 offers it.
- **D-6 Connector tool list.** `serve` passes `connectorTools(ALL_TOOLS)` to `createOverdeckMcpServer`: it drops `list_machines`, and for `start_conversation`, `start_worker` and `start_issue` it returns a copy whose `inputSchema.properties` lacks `machine` and `needs` and whose `run` returns `errorResult('A connector reaches only the machine it paired with; omit machine and needs.')` when either argument is present, else calls the original `run`. `isAgent` is always `false`, so agent-only tools stay hidden by `visibleTools`. `list_pending_input` and `search_conversations` are left as they are: through a connector their fleet half fails, `search_conversations` drops it and `list_pending_input` shows `fleetError` (accepted; documented in WI-11).
- **D-7 Local HTTP transport.** One fresh `Server` plus SDK Node `StreamableHTTPServerTransport({ sessionIdGenerator: undefined, enableJsonResponse: true })` per `POST /mcp`, closed after the response, mirroring `routes/mcp.ts`. - **D-8 `/healthz` is unauthenticated** and answers exactly `{ "ok": <route !== 'down'>, "machine": "<label>", "route": "direct" | "relay" | "down" }` with `Cache-Control: no-store`. Why: `status` and container health checks need it without the token; it carries no secret and no scope list.

- **D-11 Labels.** The directory label and the exchange `label` are `--label`, else `os.hostname()`, cleaned by `clientLabel` (`directory-web.ts:84`) and cut to 64 characters. The device-flow label is chosen by the account service (it is never the hostname; Fact 16).
- **D-12 A fresh link key per `pair`.** Every `pair` generates a new link key pair with `generateStaticKeyPair()`, so the exchange never answers 409 `link-key-in-use`. The `clientId` stays, so the machine revokes the previous connector record for this home (Fact 6). `identity.json` keeps the new link key only after a successful exchange.
- **D-13 Local token survives re-pairing.** `pair` creates `local-token` only when it is absent or malformed, so bot configs keep working after a re-pair. `logout` deletes it.
- **D-14 Same account.** `pair` and `serve` require the target `environmentId` to appear in `directory.machines`. If it is absent: `This connector is signed in to an overdeck.ai account that does not include machine <environmentId>. Sign in with the account the machine uses: pan mcp connector logout, then login.` If it is present but not `online`: `<label> is offline in the overdeck.ai directory.`
- **D-15 Waiting for the directory.** `pair`, `serve` and `logout` wait at most `DIRECTORY_ONLINE_TIMEOUT_MS = 15_000` for `state === 'online'`; a `refused` state exits 1 with `directory.refusal`.

- **D-17 Status reads the running serve.** `status` fetches `http://127.0.0.1:<port>/healthz` (port from `--port`, default 7466) with a 2 s abort; no answer prints `route: not serving`.
- **D-18 Logout order and best effort.** In order: `DELETE /api/connectors/self` over a link channel (5 s), `forget-client` (when the directory is online), `revokeDevice` (5 s), then delete `pairing.json`, `local-token`, `identity.json`, `account.json`. A failed step prints one stderr line and never stops the next; the exit code is 0 once the files are gone.

## Hazards

- **H-1 Cold relay dials exceed 2.5 s.** Mitigated by D-2 (probe with 15 s before online; pooled dials reuse the warm peer connection).
- **H-2 A stale peer connection after the machine restarts.** Mitigated by D-3 (close the transport entry before each re-probe).
- **H-3 Two connector processes on one home** (for example `serve` running while `pair` re-pairs). `serve` reads `pairing.json` at start only; after a re-pair, restart `serve`. Documented in WI-12.
- **H-4 Token leakage through output.** Tests assert no `odk_`/`odd_`/`odl_` text in `pair`, `status` and `/healthz` output (WI-2, WI-6, WI-8).
- **H-5 Security change on the machine (WI-10).** The connector gate is narrowed to three spawn routes and to self targets, checked before any side effect; a test proves no remote call or allocation happens for a refused target.
- **H-6 The epic's directory deploy (CP-5)** is not done here; a release before it would ship a connector that the directory refuses with `bad_frame`.
