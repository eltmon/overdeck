# PAN-5137: per-PR `changelog.d/` entries, folded into `changelog.mdx` by `pan release stable`

Issue: [PAN-5137](https://github.com/eltmon/overdeck/issues/5137)

## Glossary

- **`changelog.mdx`**: the public, per-release changelog at the repo root. Mintlify serves it at `/changelog`. Each release is one `<Update label="vX.Y.Z" description="YYYY-MM-DD">` JSX block.
- **Upcoming block**: the `<Update label="v0.80.0" description="Unreleased" tags={["Upcoming"]}>` block at the top of `changelog.mdx` (line 13 today). Every PR adds a bullet to it, so any two PRs in flight conflict there.
- **Changelog entry file**: a new file `changelog.d/<name>.md` that one PR adds. It holds that PR's changelog bullets under `#### New`, `#### Improved` or `#### Fixed` headings. One file per PR means two PRs never touch the same lines.
- **Fold**: the step in `pan release stable` that reads every entry file, writes one dated `<Update>` block at the top of `changelog.mdx`, and deletes the entry files, all inside the release commit.
- **Release commit**: the `chore: release X.Y.Z` commit that `releaseCreateCommand` in `src/cli/commands/release.ts` makes before it tags.
- **Section**: one of the three headings `#### New`, `#### Improved`, `#### Fixed`. The fold writes them in that order.
- **`lint:docs`**: `node scripts/lint-docs.js`, part of `npm run lint` and CI. It already checks published pages for `$` and `<digit` (PAN-4509).

## Problem

Every PR appends a bullet to the same Upcoming block, so concurrent PRs conflict on `changelog.mdx` even when nothing else overlaps. Two recorded cases:

- 2026-11-10: PAN-5106 (#5110) conflicted after PAN-5107 (#5109) merged. Its agent had to merge main.
- 2026-11-11: PAN-5091 (#5134) was approved, then conflicted after PAN-5124 (#5135) merged. `git merge-tree` names only `changelog.mdx`. The PR came from a supervised handoff, so it had no work agent, and conflict repair journaled `conflict.repair-escalated` / `reason: unreachable`.

`merge=union` on `changelog.mdx` is rejected by the issue: the block's shared lines (`<Update>`, `#### New`, blank lines) would be emitted once and the bullets split around them, the same failure `.gitattributes` documents for `apps/mobile/ACCEPTANCE.md` (PAN-5054). The repo already solved that case with one file per issue (`apps/mobile/acceptance/PAN-<n>.md`). This PRD applies the same pattern to the changelog.

## Decisions

1. **Entry location and name.** `changelog.d/<name>.md`, where `<name>` is the lowercase issue ID (`pan-5137.md`). Work without an issue uses any unique lowercase kebab slug. Allowed file names match `^[a-z0-9][a-z0-9-]*\.md$`. Every other name in `changelog.d/` except `README.md` (for example `pan-123.mdx` or `Pan-1.md`) is an error, never silently skipped. `changelog.d/README.md` documents the format and is never folded or deleted.
2. **Entry format.** Markdown with section headings, copied verbatim into the block:
   ```markdown
   #### Fixed

   - **Short bold lead:** one or more plain sentences. ([#5137](https://github.com/eltmon/overdeck/issues/5137))
   ```
   Rules (the parser and the lint enforce the same rules):
   - Blank lines are ignored.
   - A heading line is exactly `#### New`, `#### Improved` or `#### Fixed`. Any other line starting with `#` is an error.
   - The first non-blank line must be a heading.
   - A line starting with `- ` starts a bullet. A line starting with two or more spaces continues the previous bullet. Any other line is an error.
   - Each heading has at least one bullet. A heading may appear only once per file.
   - The MDX safety rules apply: write `&#36;` for a dollar sign and `&lt;` before a digit.
3. **Fold order.** Sections in the order New, Improved, Fixed; a section with no bullets is omitted. Within a section, bullets come in entry-file order, sorted by file name with numeric collation (`a.localeCompare(b, 'en', { numeric: true })`), so `pan-999.md` precedes `pan-1000.md`. Lines inside a bullet keep their order.
4. **Block shape.** Exactly the shape of the v0.79.0 block:
   ```mdx
   <Update label="v0.80.0" description="2026-11-12">
     #### New

     - bullet from pan-5160.md

     #### Fixed

     - bullet from pan-5150.md

     [Compare v0.79.0...v0.80.0](https://github.com/eltmon/overdeck/compare/v0.79.0...v0.80.0)
   </Update>

   ```
   Every copied line gets a two-space indent. The block is inserted immediately before the first line that starts with `<Update `, followed by one blank line. The previous version in the compare link is the `label` of that first existing block (`v0.79.0`), never `getLatestTag`.
5. **Date.** `description` is the local date (`YYYY-MM-DD` from `getFullYear`, `getMonth() + 1`, `getDate()`, zero-padded) of the machine running the release. Not `toISOString()`, which gives the UTC date and is a day ahead on a US evening.
6. **Stable only.** `pan release canary` never reads or changes `changelog.d/` or `changelog.mdx`.
7. **Plan before mutating.** The fold is computed (all files read and validated, the new content built in memory) right after `ensureTagDoesNotExist`, before preflight and before any write. A malformed entry stops the release before the build starts, with the file name and line in the error. The write and the deletions happen inside the existing `try`, before `bun install`.
8. **Skips, never refusals, for the no-op cases.** No entry files: print `No changelog.d entries; changelog.mdx unchanged.` in dim text and continue. A block with `label="vX.Y.Z"` for the target version already exists (a retag after a failed release, possibly with new entries merged since): leave the entries in place for the next release and print, in yellow, `changelog.mdx already has a vX.Y.Z block (a retag?); left N changelog.d entries for the next release.` Both keep the idempotent retag path working.
9. **Refusals.** The fold throws, naming the reason, when: `changelog.mdx` still contains `tags={["Upcoming"]}` or `description="Unreleased"` (checked first, before either skip in Decision 8); an entry breaks an MDX safety rule; there is no `<Update ` line to insert before; or an entry file breaks a format rule or has a bad file name. (The pure `foldChangelogEntries` also throws on an existing target block, as a guard; `planChangelogFold` checks for that block first and skips per Decision 8.)
10. **Rollback.** If the release fails before the release commit, a second, separate best-effort `git restore --source=HEAD --staged --worktree -- changelog.mdx changelog.d` runs after the existing package restore, so a failing changelog restore can never strand the version bumps.
11. **Staging.** The release commit stages the fold with `git add -A -- changelog.mdx changelog.d`, which records the deletions. It runs only when the fold changed something.
12. **Lint guard.** `lint:docs` fails when `changelog.mdx` contains `tags={["Upcoming"]}` or `description="Unreleased"`, with a message that names `changelog.d/<issue>.md`. It also validates every `changelog.d/*.md` except `README.md` against Decision 1 and Decision 2, including `findMdxProblems`. This catches an agent that recreates the block from habit, and a bad entry at PR time instead of on release day.
13. **Duplicated parser.** `scripts/lint-docs.js` is plain Node JS and cannot import TypeScript from `src/`. It gets its own small validator, `findChangelogEntryProblems(fileName, content)`. The TypeScript parser in `src/lib/release/changelog-fold.ts` is the authority at release time. Each file carries a comment naming the other, and both test files cover the same rule cases.
14. **No new CLI flags, no help-text change.** A changed `pan release` help string would need the skill and `packages/contracts/src/composer-commands.generated.ts` regenerated in the same commit (`lint:skills`, `lint:slash-commands`). Nothing here needs a flag.
15. **No `roles/*.md` edit.** No role prompt mentions the Upcoming block, and `roles/*.md` ships to every project, while `changelog.d/` exists only in this repo. The repo-local pointers are: the RELEASE STEP comment, `changelog.d/README.md`, `CLAUDE.md`, `.overdeck/context/codebase/conventions.md` and the lint guard's message. No Prompt-Change trailer is needed.
16. **The public page loses its unreleased preview.** Upcoming changes are no longer visible on `/changelog` before the release. This is the cost of removing the conflict; GitHub shows merged PRs in the meantime.
17. **No changelog entry for PAN-5137 itself.** The change alters only this repo's release process; npm users see no change.

```ts
export type ChangelogSection = 'New' | 'Improved' | 'Fixed';
export const CHANGELOG_SECTIONS: readonly ChangelogSection[] = ['New', 'Improved', 'Fixed'];

export interface ChangelogEntryFile { fileName: string; content: string }
/** One parsed entry: section -> bullets, each bullet an array of raw lines. */
export type ParsedChangelogEntry = Map<ChangelogSection, string[][]>;

export class ChangelogEntryError extends Error {
  constructor(readonly fileName: string, readonly line: number | null, message: string) {
    super(line === null ? `changelog.d/${fileName}: ${message}` : `changelog.d/${fileName}:${line}: ${message}`);
  }
}

export const CHANGELOG_ENTRY_FILE_NAME = /^[a-z0-9][a-z0-9-]*\.md$/;
export function parseChangelogEntry(file: ChangelogEntryFile): ParsedChangelogEntry;
export function formatReleaseDate(now: Date): string; // local YYYY-MM-DD
export function stripInlineCode(line: string): string; // TS port of scripts/lint-docs.js stripInlineCode
export function hasUpcomingBlock(changelog: string): boolean; // tags={["Upcoming"]} or description="Unreleased"
export function foldChangelogEntries(params: {
  changelog: string;
  entries: ChangelogEntryFile[];
  version: string; // "0.80.0", no leading v
  date: string;    // "2026-11-12"
}): string;
```

`parseChangelogEntry` also applies the MDX safety rules from `findMdxProblems` in `scripts/lint-docs.js`: on each bullet or continuation line, after `stripInlineCode(line)`, a `$` throws `write &#36; instead of a dollar sign` and `/<\d/` throws `write &lt; instead of a bare < before a digit`, each with the file name and line. (Fenced code is impossible here: a line starting with three backticks is neither a bullet nor a continuation, so it already throws.) This is the release-time copy of the check, because release preflight runs `npm run build` and `npm test` but not `lint:docs`.

`foldChangelogEntries` steps:
1. Throw `Error('changelog.mdx still has an Upcoming block; move its bullets to changelog.d/ first')` if `hasUpcomingBlock(changelog)`.
2. Throw if `changelog` includes `<Update label="v${version}"`.
3. Find the index of the first line where `line.startsWith('<Update ')`; throw if none. Read the previous version from it with `/label="(v[^"]+)"/`.
4. Sort `entries` by `fileName` with numeric collation; parse each (throws `ChangelogEntryError`).
5. For each section in `CHANGELOG_SECTIONS`, collect all bullets from all entries in sorted order. Skip empty sections.
6. Build the block lines per Decision 4, then splice them plus one `''` line in before the found index. Return the joined string (keep the original trailing newline).

### WI-2 `release-wiring`: fold inside `pan release stable` (FR-2, FR-3, FR-4, FR-5, FR-6, NFR-1)

```ts
export interface ChangelogFoldPlan { changelogPath: string; content: string; entryPaths: string[] }
export type ChangelogFoldOutcome =
  | { kind: 'fold'; plan: ChangelogFoldPlan }
  | { kind: 'skip'; reason: 'canary' | 'no-entries' | 'block-exists'; message: string };

/** Reads and validates changelog.d/ and builds the new changelog.mdx text. Writes nothing. */
export function planChangelogFold(repoRoot: string, channel: ReleaseChannel, version: string, now: Date): ChangelogFoldOutcome {
  if (channel !== 'stable') return { kind: 'skip', reason: 'canary', message: '' };
  const changelogPath = join(repoRoot, 'changelog.mdx');
  const changelog = readFileSync(changelogPath, 'utf8');
  // Checked before every skip, so a leftover Upcoming block can never survive a stable release.
  if (hasUpcomingBlock(changelog)) {
    throw new Error('changelog.mdx still has an Upcoming/Unreleased block; move its bullets to changelog.d/<issue>.md first');
  }
  const dir = join(repoRoot, 'changelog.d');
  const names = existsSync(dir) ? readdirSync(dir).filter((name) => name !== 'README.md').sort() : [];
  for (const name of names) {
    if (!CHANGELOG_ENTRY_FILE_NAME.test(name)) {
      throw new ChangelogEntryError(name, null, 'file name must be lowercase kebab-case ending in .md, for example pan-5137.md');
    }
  }
  if (names.length === 0) return { kind: 'skip', reason: 'no-entries', message: 'No changelog.d entries; changelog.mdx unchanged.' };
  const entries = names.map((fileName) => ({ fileName, content: readFileSync(join(dir, fileName), 'utf8') }));
  entries.forEach((entry) => parseChangelogEntry(entry)); // validate even when skipping below
  if (changelog.includes(`<Update label="v${version}"`)) {
    const noun = names.length === 1 ? 'entry' : 'entries';
    return { kind: 'skip', reason: 'block-exists', message: `changelog.mdx already has a v${version} block (a retag?); left ${names.length} changelog.d ${noun} for the next release.` };
  }
  const content = foldChangelogEntries({ changelog, entries, version, date: formatReleaseDate(now) });
  return { kind: 'fold', plan: { changelogPath, content, entryPaths: names.map((name) => join(dir, name)) } };
}

export function applyChangelogFold(plan: ChangelogFoldPlan): void {
  writeFileSync(plan.changelogPath, plan.content);
  for (const path of plan.entryPaths) rmSync(path);
}
```

# changelog.d

`pan release stable` folds every file except this README into a dated `<Update>` block at the top of `changelog.mdx`, sections in the order New, Improved, Fixed, and deletes the files in the release commit.

    #### Fixed

- A bullet starts with `- `. Indent continuation lines by two spaces.
- Write `&#36;` for a dollar sign and `&lt;` before a digit. `npm run lint:docs` checks all of this.
