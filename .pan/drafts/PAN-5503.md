# PAN-5503: accuracy audit of the Configuration docs group

**Issue:** https://github.com/eltmon/overdeck/issues/5503 (part of epic #5467, docs overhaul)
**Priority:** P1. Docs-only change. No code changes, no `changelog.d` entry.
**Base:** `main` at `0558b4ab739` (v0.89.1 plus later merges), 2026-11-18. PAN-5471 (#5521) and PAN-5472 (#5535)
have both merged, so `model-presets.mdx` is audited on top of PAN-5471's result and `state-branch.mdx` is already
retired (see Decision D2).

## Summary

The issue asks for a line-by-line accuracy audit of every published page in the **Configuration** navigation group. The
planning session already did the audit: six research passes read all 23 pages (7,233 lines) against current code, and the
planner re-checked the headline findings by grep. This PRD lists every wrong, stale or removed claim per page, with the
exact current text, the replacement text and the code evidence. The implementation agent applies those changes, removes
the en and em dashes, fixes frontmatter, checks links, runs the Mintlify validators, and writes a PR body with one note per
page. It does not need to re-research; it only re-checks a claim when a listed grep anchor no longer matches.

## Glossary

- **Configuration group**: the `"group": "Configuration"` block in `docs.json` (around line 133). On the base it lists 23
  pages: `projects`, `telemetry`, `knowledge`, `harnesses`, `model-routing`, `model-presets`, `local-models`, `effort`,
  `terminal-backend`, `memory-governor`, `jev`, `semgrep`, `computer-use`, `context-layers`, `docs-rag`, `skills`,
  `memory`, `appearance`, `issue-trackers`, `polyrepo`, `progressive-polyrepo`, `auto-merge`, `order-books`. Each is
  `configuration/<name>.mdx`.
- **Claim**: any statement on a page a reader could act on: a command or flag, a config key or default, a UI label or
  location, a file path, a behavior, a limit, a list of supported harnesses, trackers or platforms, or a maturity label.
- **Primary source**: the code on the base (`git grep`), `pan <verb> --help`, `src/lib/config-yaml/defaults.ts`, the
  dashboard source under `src/dashboard/frontend/src/`, and `changelog.mdx`. Other `.mdx` pages, `docs/*.md` and
  `README.md` are never proof.
- **Grep anchor**: the quoted current text in each change table. Line numbers drift as earlier edits land, so find the
  text with `grep -n -F '<anchor>' configuration/<page>.mdx`, not by line number.
- **Dash rule**: no U+2013 (en dash) or U+2014 (em dash) anywhere in a touched page, frontmatter and body. Check:
  `grep -nP '[\x{2013}\x{2014}]' configuration/<page>.mdx` prints nothing. Replace a dash with a comma, colon, period,
  parentheses, or the word "to" for a range. Box-drawing characters such as `─` (U+2500) in diagrams are not dashes.
- **Frontmatter rule**: `title` is specific and searchable; `description` is 50 to 160 characters (count the text between
  the quotes); neither contains a dash. When this PRD retitles a page, also add `sidebarTitle: "<the old title>"` so the
  navigation label stays short (the pattern `configuration/docs-rag.mdx` already uses).
- **Experimental**: a dashboard view hidden unless Settings → Experimental → **Experimental features** is on. The gated
  views are listed in `EXPERIMENTAL_TAB_IDS` in `src/dashboard/frontend/src/lib/experimentalFeatures.ts` (agents,
  autopreso, resources, sessions, metrics, costs, health, god-view). None of the 23 pages describes a gated view, so no
  experimental labels are needed; the one "(experimental)" heading in `harnesses.mdx` describes a removed feature (WI-A3).
- **Follow-ups**: code bugs or out-of-scope doc problems found during the audit. They go in a `## Follow-ups` list in the
  PR body. This issue changes no code.
- **PR note**: a one-line summary of what changed on a page, or "verified, no change". Each page item puts its note in its
  commit message as a line `PR-note: configuration/<page>.mdx: <note>`; WI-Z1 collects them into the PR body.

## Common procedure for every page item

0. **Code wins.** If a primary source contradicts a row in this PRD (the research was wrong, or main moved), skip the row,
   record it in the PR note, and leave that row's acceptance criterion unticked with the evidence in the commit message
   (`pan task block` with the reason). Never write a claim the code contradicts to satisfy a row. Figures the code cannot
   confirm (install sizes, latencies measured elsewhere) stay as they are unless a row says to change them.
1. **Apply the change table.** For each row, find the grep anchor with `grep -n -F`, make the change, and keep the
   evidence in mind for the replacement wording. If an anchor no longer matches (another edit moved or reworded it), find
   the claim by meaning; if the claim is gone, skip the row and say so in the PR note.
2. **Spot-check before deleting.** Before deleting a whole section, re-run the row's evidence grep once. If the evidence no
   longer holds on the current branch (main moved), keep the section and note it as a Follow-up.
3. **Residual rule.** Read the whole page once. For a claim the table does not list that looks doubtful, verify it against a
   primary source; if the code disagrees, change the page to match the code. Do not chase claims that look right; the
   research passes already verified the listed "Verified, keep" claims.
4. **Dashes.** Remove every en and em dash in the page (dash rule). Do it in the same commit.
5. **Frontmatter.** Apply the work item's title change (with `sidebarTitle`) if any; confirm the description length is 50
   to 160 characters and dash-free. Quote a `description` that contains `: `.
6. **Links.** For each internal link, `ls <path>.mdx` (and `grep -n "^#.*<heading words>"` for an anchor), counting
   `docs.json` redirects. Fix any that fail.
7. **MDX safety.** Keep any new `<word>` placeholder inside backticks.
8. **Commit** with `Item: <id>`, its AC trailers and `PR-note: configuration/<page>.mdx: <one line>`; push; `pan task done`.
