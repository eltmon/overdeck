## Glossary

| Term | Meaning |
| --- | --- |
| **Event loop** | The single Node.js thread that services all HTTP requests, WebSocket frames, and timers in the dashboard server process. Synchronous work blocks everything. |
| **Deacon** | The 60-second patrol loop (`src/lib/cloister/deacon.ts`, `runPatrol` at :2592) that reconciles agent/pipeline state: orphan recovery, nudges, merge handoffs, reaping. Part of the Cloister. |
| **Cloister / CloisterService** | The lifecycle watchdog service (`src/lib/cloister/service.ts`) that owns the deacon patrol and a 60 s agent health-check loop (`performHealthCheck`, service.ts:1002-1064). Today it runs **in-process** with the dashboard server. |
| **Event store** | `src/dashboard/server/event-store.ts` — SQLite-backed append log **plus** an in-process Node `EventEmitter` (`emitter.emit('event', stored)` at event-store.ts:263). The SQLite rows travel across processes; the emitter notification does not. |
| **Read model** | In-memory state (`src/dashboard/server/read-model.ts`) bootstrapped once and maintained incrementally by domain events via `applyEvent`. Serves WS snapshots. |
| **IssueDataService** | The tracker poller + in-memory issue cache (`src/dashboard/server/services/issue-data-service.ts`). Its `getIssues()` is the hot path serving `GET /api/issues` and WS snapshots. |
| **resource-discovery** | `src/dashboard/server/services/resource-discovery.ts` — computes the Command Deck project tree (issues with live workspaces/agents/branches/PRs), 30 s stale-while-revalidate cache. |
| **Active/live predicate** | The existing filters at resource-discovery.ts:632-650 (`isActiveTrackerState`, `isTerminalTrackerState`, `isLiveResource`, `hasOpenPr`) that reduce ~1778 tracked issues to the ~13 with real in-flight work. |
| **readyForMerge** | Per-issue review-status flag (SQLite `review_status` + git journal record) meaning review+test passed and the merge gate may advance the issue. |
| **Internal token** | Shared-secret header (`INTERNAL_TOKEN_HEADER`, `ensureInternalTokenSync` — see `src/lib/agents/agent-runtime.ts:79-108`) that authenticates loopback HTTP calls from Overdeck-owned processes to the dashboard. |
| **Peer dashboard** | A dashboard instance running with `OVERDECK_DISABLE_DEACON=1` (workspace containers) — UI/read peer only, no deacon, cache-only polling (PAN-1817). |
| **Single-deacon invariant** | At most one deacon may run per `~/.overdeck` state directory (see `.claude/rules/single-deacon-invariant.md`). |
| **fork IPC** | The built-in message channel of `child_process.fork()` between parent and child Node processes. |

## Problem

Under current load (13 live work agents, 95 tracked agents, ~1778 tracked issues):

- `GET /api/issues` takes 1–7 s (should be <200 ms).
- The browser loops "Reconnecting…": the server heartbeats every 15 s (`Stream.tick('15 seconds')`, ws-rpc.ts:783-789); the client declares the stream dead after 35 s of silence (`STREAM_STALENESS_TIMEOUT_MS = 35_000`, EventRouter.tsx:25) and reconnects, triggering a fresh `getSnapshot` (~1.5 MB serialize + full `getIssues()` recompute) — which adds more main-thread CPU. A feedback loop.

`/api/issues` is served entirely from in-memory caches (verified: no DB/fs/network on the request path — issue-data-service.ts:396-490). The 1–7 s latency is **queueing delay** behind blocking work sharing the event loop. Three classes:

1. **The deacon runs in-process.** `getCloisterService().start()` is called directly at main.ts:613. The patrol runs ~40 reconcilers serially over sync SQLite (`node:sqlite` `DatabaseSync` via `listOverdeckAgentStatesSync`, src/lib/overdeck/agent-state-sync.ts:213-216), `execSync`-based tmux (`listSessionsSync`, src/lib/tmux.ts:525 — violating the PAN-70 no-execsync-server rule), and `readFileSync`+`JSON.parse` sweeps. The escape-hatch comment at main.ts:591-596 documents this exact starvation mode.
2. **Per-issue work scales with all ~1778 issues, not the ~13 active ones.** resource-discovery does ~1778 sync SQLite reads + ~1778 `readFileSync` calls every 30 s (`getReviewStatusSync(upper)` inside `ensureIssue`, resource-discovery.ts:457) *before* its active/live filter (652-666). GitHub polling fetches ALL closed issues with no date filter (issue-data-service.ts:867 — "so Done column is complete after restarts"). Every changed poll fans planning-refresh over every issue (`pushUpdated` → `schedulePlanningRefreshForIssues`, :714-737, no status filter). Patched incrementally 3× (d66e998b03: "600-900ms event loop stalls"; a0a8829eae: "870+ sync disk reads per call") without fixing the shape.
3. **Sync reads on the server main thread.** DB writes are worker-offloaded (`services/dashboard-db-task.ts:142-146`); reads are not.

## Requirements

### Functional

- **FR-1** The deacon/Cloister patrol and health-check loops run in a separate supervised Node 22 child process. The dashboard server process performs zero deacon work on its event loop.
- **FR-2** Domain/activity events emitted by the deacon child reach the dashboard's in-process subscribers (read model `applyEvent`, activity feed, TTS summarizer/playback, WebSocket clients) with the dashboard event store remaining the **single sequence-assigning writer**.
- **FR-3** Every existing cloister/deacon control affordance keeps working after extraction (no-loss audit table in WI-3; a table-driven test gates this).
- **FR-4** Child lifecycle: spawned at dashboard boot (same `OVERDECK_DISABLE_DEACON` + `shouldAutoStart()` gates as today), killed on dashboard shutdown, supervised restart on crash (bounded, with give-up + activity event), single-deacon invariant enforced via the existing `cloister.state` pid lock.
- **FR-5** resource-discovery reads review status only for issues surviving the cheap pre-filter (`!isTerminalTrackerState || hasOpenPr`), via one batched query per compute cycle — never one sync read per tracked issue.
- **FR-6** `schedulePlanningRefreshForIssues` skips issues whose canonical status is terminal (`done`/`canceled`).
- **FR-7** GitHub closed-issue fetching is bounded to a recency window (`issues.closed_window_days`, default 14), using the REST `since` parameter; open-issue fetching is unchanged.
- **FR-8** The `/api/issues` response is memoized per `(cycle, includeCompleted)` — including the serialized JSON string — and invalidated only when underlying data changes; the sort comparator does not allocate `Date` objects per comparison.
- **FR-9** `EventRouter` reconnects with exponential backoff + jitter; a staleness-triggered reconnect never runs concurrently with an in-flight bootstrap.
- **FR-10** An ESLint guard fails the build on `execSync` usage anywhere under `src/dashboard/server/`.
- **FR-11** The server exposes an event-loop delay gauge (via `perf_hooks.monitorEventLoopDelay`) in `GET /api/metrics/summary` and logs a warning when p99 over the last minute exceeds 100 ms.
- **FR-12** (RUN-56 B0, added 2026-07-05) The supervisor watchdog does not restart the dashboard on connection-refused / non-OK ("unreachable", `hardDown`) failures while a freshly-started dashboard is still warming up. A boot-grace window suppresses the hard-down restart decision until the dashboard has answered `GET /api/health` OK at least once since the watchdog started (or since the last watchdog-triggered restart), bounded by a configurable cap (`OVERDECK_SUPERVISOR_BOOT_GRACE_MS`, default 300 000 ms) after which a never-healthy boot is treated as genuinely dead and becomes restart-eligible. Each watchdog-triggered restart reseeds the window so the newly-spawned dashboard gets a fresh boot grace.

### Non-functional

- **NFR-1** `GET /api/issues` p95 < 200 ms with 1778 cached issues and 13 live agents.
- **NFR-2** Dashboard server event-loop delay p99 < 100 ms in steady state with the deacon child patrolling (measured by FR-11 gauge).
- **NFR-3** Zero client staleness reconnects (`[EventRouter] domain event stream stale`) during a 10-minute soak with live agents and the deacon patrolling.
- **NFR-4** A crashed deacon child is restarted within 60 s without any dashboard HTTP/WS impact.
- **NFR-5** (RUN-56 B0) After a dashboard deploy/restart, the supervisor watchdog performs zero false-positive "unreachable" restarts while the dashboard is warming up; the first restart it may issue can only occur after the dashboard has been healthy once or the boot-grace cap has elapsed.

## Design decisions (made here — do not re-litigate downstream)

- **D-1 — Event bridge = internal HTTP ingestion.** The deacon child delivers events via `POST /api/internal/events` (batch array), loopback URL + internal token (reuse the pattern of `emitAgentEvent`, agent-runtime.ts:79-108, default `http://127.0.0.1:3011`, agent-runtime.ts:27). The dashboard handler appends through its in-process event store — sequence assignment stays single-writer (two-door tenet). **Not** SQLite polling (two writers would race sequence assignment) and **not** fork IPC (the bridge must also serve a future manually-started deacon that isn't our child).
- **D-2 — Control state lives in durable planes, not process memory.** Aligns with `docs/FAILSAFE-CONTROL-ARCHITECTURE.md` Decision 4. `spawnsPaused` moves from an in-memory service field to SQLite `app_settings`. Deacon status/logs/last-patrol move to durable artifacts (D-4). The **only** fork-IPC command is "run patrol now" (POST `/api/deacon/patrol`). Config reload: the child re-checks `~/.overdeck/deacon/config.json` mtime at the start of each patrol (≤60 s latency; the PUT route just writes the file).
- **D-3 — Emergency paths execute in the dashboard process, child-independent.** `POST /api/cloister/emergency-stop` and `/brake` keep running in the dashboard (they act on tmux + SQLite flags, both cross-process safe; service.ts:966-967 already sets durable `deacon.globally_paused` + `flywheel.globally_paused`). An operator must be able to emergency-stop even when the child is wedged. The child observes the flags on its next cycle.
- **D-4 — Status/logs read from durable artifacts.** `lastPatrolResult` (today in-memory, deacon.ts:3198) is persisted into `~/.overdeck/deacon/health-state.json` (which already carries the `lastPatrol` heartbeat, deacon.ts:288). The in-memory log ring (`deaconLogs[]`, deacon.ts:3233) is mirrored to `~/.overdeck/logs/deacon.log` (file already exists as an ops convention); `GET /api/deacon/logs` returns the file tail. This also fixes the pre-existing bug where `pan admin cloister status` from the CLI shows empty logs/stopped deacon because it builds a fresh per-process service singleton (service.ts:1970).
- **D-5 — CLI `cloister start`/`stop` route through dashboard HTTP** (loopback + internal token), with a clear error when the dashboard is down. Today they start/stop an in-CLI-process service — meaningless post-extraction. Freeze (`freeze.ts`, direct SQLite) is already cross-process-correct and stays as-is.
- **D-6 — Flywheel glue reads issues via loopback.** `getSharedIssueService().getIssues()` at flywheel.ts:93-95 silently returns `[]` in a child process (the singleton is per-process, `try/catch` → empty). Replace with `GET /api/issues` over the internal loopback (precedent: orphan-proposed-reconciler.ts:264-280 using `OVERDECK_INTERNAL_DASHBOARD_URL`).
- **D-7 — Done-column completeness becomes a windowed guarantee.** Closed issues updated within `issues.closed_window_days` (default 14) appear; older closed issues live in GitHub only. This is a deliberate product trade: unbounded closed-issue polling is why 1778 issues are resident.
- **D-8 — Child supervision policy mirrors `src/supervisor/watchdog.ts`** (max 3 restarts in a sliding window — `OVERDECK_SUPERVISOR_MAX_RESTARTS` precedent at watchdog.ts:117 — then give up, emit an `activity` error event, and leave a clear status). Child gets its own SIGTERM handler calling `stopDeacon()` + `service.stop()` (closing the shutdown gap: main.ts:497-526 never stops the cloister today).
- **D-9 — What does NOT change:** patrol contents and cadence, `docs/DEACON-HEALTH-MONITORING.md` responsibilities, `OVERDECK_DISABLE_DEACON` semantics for peer containers (still: no deacon spawn), pause/freeze/troubled gates (already SQLite/fs), `deliverAgentMessage` (tmux/fs — travels), agent runtime adapters (stateless over tmux/fs, runtimes/index.ts:147 — travel).

### WI-2 — Event bridge: internal ingestion endpoint + deacon event client (FR-2)

**Files:** new route in `src/dashboard/server/routes/` (internal events); new `src/lib/cloister/deacon-event-client.ts`; `src/dashboard/server/main.ts:347-411` (notifier wiring); `src/lib/cloister/service.ts:890-892, 1406-1416`; `src/lib/activity-logger.ts` (provider indirection already exists via `setActivityEventStoreProvider`, wired in `initEventStore` at event-store.ts:381).

Why: the event store's emitter is in-process (event-store.ts:263). A child's direct SQLite appends would persist but never notify the dashboard's subscribers (domain-services.ts:171-178 read model; tts-summarizer.ts:222; tts-playback.ts:149; main.ts:457), and would race sequence assignment.

1. **Dashboard: `POST /api/internal/events`.** Auth: internal token header (same check as the heartbeat route — see `emitAgentEvent`'s counterpart handler); reject non-loopback origins. Body: `{ events: Array<Omit<StoredEvent,'sequence'>> }`. Handler appends each through the in-process event store (`getEventStore().append(...)`) so sequencing, persistence, emitter fan-out, and read-model `applyEvent` all happen exactly as if emitted locally. Return `{ appended: n }`.
2. **`deacon-event-client.ts`.** Implements the append/appendAsync surface the deacon side needs. Buffers events (FIFO, cap 1000; on overflow drop-oldest and `console.warn` a count — no silent truncation), flushes batches (≤50 events or 250 ms debounce) to the ingestion endpoint, retries with exponential backoff on failure. Losing events while the dashboard is down is acceptable: events are notifications; state-of-record is SQLite/fs/git (docs/AGENT-STATE-PLANES.md).
3. **Wire the child.** In `deacon-main.ts`: `setActivityEventStoreProvider(eventClient)` so every `emitActivityEntrySync`/`emitActivityTtsSync` call inside the deacon (e.g. deacon.ts:161, :175) routes to HTTP. Set the three notifiers (`setAgentStoppedNotifier` / `setAgentStatusChangedNotifier` / `setMergeReadyNotifier`, deacon.ts:1611-1693, fired at :3325) to closures that build the same events main.ts:347-411 builds today and hand them to the event client. `service.ts` direct appends (`this.eventStore.append({type:'agent.heartbeat_dead'})`, service.ts:1406-1416; `initEventStore` at :890-892) go through an injected store handle so the child injects the client — sever the static `dashboard/server` import (this also shrinks the deacon bundle; see coupling note: service.ts:5, flywheel.ts:21,93).
4. **Flywheel issue reads (D-6):** replace `getSharedIssueService().getIssues()` (flywheel.ts:93-95) with a loopback `GET /api/issues` fetch; on failure log loudly instead of the current silent `[]`.

**Tests:** `tests/unit/dashboard/internal-events-route.test.ts` — 401 without token; append assigns sequence; batch of N appends N; read-model applyEvent invoked. `tests/unit/lib/cloister/deacon-event-client.test.ts` — batching, retry backoff, drop-oldest warning. **Fake timers mandatory** for all debounce/backoff assertions.

```ts
private schedulePlanningRefreshForIssues(issues: any[]): void {
  for (const issue of issues) {
    const identifier = typeof issue?.identifier === 'string' ? issue.identifier : '';
    if (!identifier || this.planningRefreshQueued.has(identifier) || planningStateRefreshInFlight.has(identifier)) continue;
    const canonical = getCanonicalStatus(issue.status, issue.stateType);

    this.planningRefreshQueued.add(identifier);
    this.planningRefreshQueue.push(identifier);
  }
  this.drainPlanningRefreshQueue();
}
```

### New Work Item — WI-11: supervisor watchdog boot-grace window (FR-12, NFR-5)

**File:** `src/supervisor/watchdog.ts`; tests extend `src/supervisor/__tests__/watchdog.test.ts`.

Root cause of the 2026-07-05 false-positive: at watchdog start (or right after a deploy), the dashboard's HTTP listener may not be bound yet (Effect-layer bootstrap is slow and untested by CI). A refused connection is a **hard** failure (`isTimeoutError` → false), so `consecutiveHardFailures` climbs and `hardDown` (`>= failThreshold`, default 3 → ~30 s) triggers `dashboard unreachable`. The freshly-booting-but-alive server is killed, and each restart re-enters the same slow boot → churn (the PAN-1714 recurrence). The busy/timeout path already has a long leash (`busyFailThreshold` 12); the unshielded gap is the hard-down path during boot.

1. **Config.** Add `bootGraceMs: number` to `SupervisorWatchdogConfig` and parse it in `readWatchdogConfig` from `OVERDECK_SUPERVISOR_BOOT_GRACE_MS` via the existing `parsePositiveIntEnv` (default **300 000**). No hardcoded fallback elsewhere — the default lives in `readWatchdogConfig` alongside the other `OVERDECK_SUPERVISOR_*` defaults.
2. **State.** Add to `InternalState`: `hasBecomeHealthy: boolean` and `bootGraceStartedAt: number`. Initialize in the constructor: `hasBecomeHealthy: false`, `bootGraceStartedAt: this.now()` (uses the injected `now` so tests stay deterministic — the file already threads `this.now`).
3. **Mark healthy.** In the success branch of `runCheck` (the `if (!restartReason) { … }` block, ~line 242-255), set `this.state.hasBecomeHealthy = true` before returning.
4. **Suppress restart during boot grace.** Immediately before `this.pruneRestartAttempts(startedAt)` (~line 284) — the point reached only when a restart is imminent (`restartReason` is set) — insert:
   ```ts
   // PAN-2318 FR-12: boot grace. A dashboard that has not yet answered a health
   // check since this watchdog started (or since our last restart) may simply be
   // warming up — a refused connection during Effect-layer bootstrap is a HARD
   // failure and would otherwise trip `hardDown` in ~30s and kill a live boot
   // (PAN-1714 recurrence, 2026-07-05). Defer until the dashboard is healthy once,
   // capped at bootGraceMs so a genuinely-dead boot is still eventually restarted.
   if (restartReason && !this.state.hasBecomeHealthy
       && startedAt - this.state.bootGraceStartedAt < this.config.bootGraceMs) {
     await this.log(
       `watchdog: dashboard not yet healthy `
       + `${Math.round((startedAt - this.state.bootGraceStartedAt) / 1000)}s into boot grace `
       + `(${Math.round(this.config.bootGraceMs / 1000)}s cap) — deferring restart (${restartLogReason ?? restartReason})`,
     );
     await this.persistState();
     return;
   }
   ```
   Counters are intentionally NOT reset while deferring: if the cap elapses with the dashboard still never-healthy, the already-accumulated `hardDown`/`busyStarved` immediately qualifies and the restart proceeds — a genuinely-dead boot is not shielded forever.
5. **Reseed after restart.** Alongside the existing PAN-2219 `this.state.patrolUnhealthySince = null;` (~line 344, after `spawnRestart`), add `this.state.hasBecomeHealthy = false;` and `this.state.bootGraceStartedAt = this.now();` so the newly-spawned dashboard gets a fresh boot-grace window.

**Ordering note:** landing this reseed logic in the restart block means the grace also protects the server the watchdog itself spawns — closing the churn loop, not just the first boot.

**Decisions made here (do not re-litigate):**
- **D-10** Grace ends at FIRST successful `/api/health`, not at a fixed timer — a healthy server exits grace the instant it answers, so the cap only ever delays recovery of a *never-responding* boot. This is why a generous cap (300 s) is safe.
- **D-11** Grace suppresses the whole restart trigger (both `hardDown` and `busyStarved`) while `!hasBecomeHealthy`, because a warming-up server can present as either refused (hard) or slow-to-answer (timeout). Post-first-healthy, the existing thresholds are unchanged — this WI does not touch steady-state restart behavior.
- **D-12** Default `bootGraceMs = 300 000`. A dashboard that has never answered health for 5 minutes is treated as genuinely dead. Operators whose boots legitimately exceed this can raise `OVERDECK_SUPERVISOR_BOOT_GRACE_MS`.

**Tests (extend `watchdog.test.ts`, using the existing injected-`now` harness; fake timers for any delay assertions per repo rule):**
- Refused connections that reach `failThreshold` within the grace window and before any healthy check → `spawnRestart` NOT called; a "deferring restart" log present.
- Dashboard answers health OK once, then hard-fails to `failThreshold` → `spawnRestart` IS called (grace no longer applies).
- Never-healthy past `bootGraceMs` (advance injected `now`) → `spawnRestart` called.
- After a watchdog restart, a subsequent grace window applies to the new boot (`hasBecomeHealthy` reset; refused failures within the fresh window defer).
- `readWatchdogConfig` honors `OVERDECK_SUPERVISOR_BOOT_GRACE_MS`; default is 300 000 when unset.
