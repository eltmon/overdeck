# PAN-4659 — Import VS Code themes from a .vsix extension package

**Issue:** https://github.com/eltmon/overdeck/issues/4659
**Split from:** #4644 (merged as `3a84c9758af`, PR #4689) — the color theme model, the `~/.overdeck/themes/` store, single-file `.json` import, light/dark pickers.
**Status:** planning draft, 2026-11-02, auto mode (no operator questions; defaults recorded below).

## Glossary

- **Color theme** — a named set of colors with a `type` (`light` | `dark`) and optional `terminal`, `syntax`, `ui` groups. Type `ColorTheme` in `packages/contracts/src/color-theme.ts`. Stored as `~/.overdeck/themes/<id>.json` by `saveColorTheme()` (`src/lib/color-themes/store.ts`).
- **VS Code theme file** — a JSON-with-comments object with `name`, optional `type`, a `colors` map, `tokenColors` (an array of TextMate rules, or a string path to a `.tmTheme` file) and optional `include` (a relative path to another theme file whose values sit underneath this one).
- **`.vsix`** — a VS Code extension package. It is a plain ZIP archive. The extension lives under the `extension/` folder; its manifest is `extension/package.json`. Real packages also carry `[Content_Types].xml` and `extension.vsixmanifest` at the archive root.
- **`contributes.themes`** — the array in `extension/package.json` that lists color themes. Each entry has `label` (display name, may be an NLS placeholder like `%theme.label%`), `uiTheme` (`vs` | `vs-dark` | `hc-light` | `hc-black`) and `path` (relative to `extension/`, e.g. `./themes/dark.json`).
- **NLS placeholder** — a `label` of the form `%key%`, resolved from `extension/package.nls.json` (`{ "key": "Text" }` or `{ "key": { "message": "Text" } }`).
- **EOCD** — the ZIP End Of Central Directory record (signature `0x06054b50`, 22 fixed bytes + comment ≤ 65535 bytes) at the end of the archive. It gives the entry count, the central directory size and its offset.
- **Central directory (CD) entry** — signature `0x02014b50`, 46 fixed bytes + name + extra + comment. It carries flags, compression method, CRC-32, compressed and uncompressed sizes and the local header offset.
- **Local file header** — signature `0x04034b50`, 30 fixed bytes + name + extra, immediately followed by the entry data. Sizes in it may be zero (when general-purpose flag bit 3, "data descriptor", is set), so the reader always takes sizes from the CD entry.
- **ZIP64** — the 64-bit ZIP extension. Marked by EOCD fields set to `0xFFFF`/`0xFFFFFFFF`, a ZIP64 EOCD locator (signature `0x07064b50`) in the 20 bytes before the EOCD, CD size/offset fields of `0xFFFFFFFF`, or an extra field with header id `0x0001`. Not supported.
- **Stored / deflated** — compression method 0 (raw bytes) and 8 (raw DEFLATE, inflated with `zlib.inflateRaw`). No other method is supported.
- **Encrypted entry** — general-purpose flag bit 0 set, or compression method 99 (WinZip AES). Not supported.
- **Package-level error** — a failure that rejects the whole `.vsix` with HTTP 400 and writes nothing.
- **Theme-level error** — a failure in one `contributes.themes` entry. That theme is dropped with a warning naming it; the other themes still preview.
- **Include chain** — the list of theme files opened from a contributed theme down through its `include`s.

## Problem

Settings > Appearance > **Import VS Code theme** accepts only a single `.json` file. Most VS Code themes are distributed as `.vsix` packages that hold several themes (often a light and a dark variant) and use `include` to share a base file. Today the route refuses `.vsix` outright:

`src/dashboard/server/routes/color-themes.ts`, lines 81-86:

```ts
      if (typeof fileName !== 'string' || !/\.json$/i.test(fileName)) {
        return jsonResponse(
          { error: 'Only VS Code theme .json files are supported; .vsix import is tracked in #4659' },
          { status: 400 },
        );
      }
```

and the file input only offers `.json` (`src/dashboard/frontend/src/components/Settings/sections/ColorThemeSection.tsx`, line 79: `accept=".json"`).

## What already works (verified 2026-11-02, no change needed)

- `POST /api/color-themes/import/preview` already returns `{ themes: ColorTheme[], warnings: string[] }` — an **array** (`routes/color-themes.ts` line 97: `return jsonResponse({ themes: [{ ...theme, id: proposedId }], warnings });`).
- `ColorThemeImportPreview.tsx` already renders one card per theme (line 100: `themes.map((theme) => <ThemePreviewCard …/>)`) and its **Save** loops over every theme, POSTing each to `POST /api/color-themes` (lines 84-88).
- `saveColorTheme()` (`store.ts` lines 271-285) slugifies the name and `claimThemeFile()` appends `-2`, `-3`, … when an id is taken, so two themes with the same name in one package both save.
- The light picker lists only `type: 'light'` themes and the dark picker only `type: 'dark'` (`ColorThemeSection.tsx` lines 49 and 62).
- The dashboard server sets no request body cap (`grep -rn MaxBodySize src` finds nothing; Effect's `MaxBodySize` defaults to `undefined`), so a 10 MB archive (≈13.4 MB of base64 JSON) reaches the handler.
- No ZIP library is installed (`grep -i zip package.json src/dashboard/server/package.json` finds nothing). `zlib.crc32` exists on the required Node (`engines.node` is `>=22.16.0`; `@types/node` `zlib.d.ts` line 242 declares it).
- Verified on Node v22.22.0: `promisify(zlib.inflateRaw)(buf, { maxOutputLength: 2 * 1024 * 1024 })` rejects with `RangeError` code `ERR_BUFFER_TOO_LARGE` when the output would exceed the cap, without allocating the full output.

So this issue is the server-side archive reader and `.vsix` mapping, one route branch, a one-attribute UI change, a base64 speed fix, tests and docs.

## Requirements

- **FR-1** The preview route accepts a file name ending in `.vsix` (case-insensitive) and returns every importable theme from `contributes.themes` in one `{ themes, warnings }` response. It writes nothing.
- **FR-2** The ZIP reader supports stored (method 0) and deflated (method 8) entries, takes entry sizes from the central directory, and verifies each read entry's CRC-32 and uncompressed length.
- **FR-3** Package-level 400 (message names the reason; nothing written): archive larger than 10 MiB; not a ZIP (no EOCD); ZIP64; multi-disk archive; any encrypted entry; any entry name that is absolute (`/…`, `\…`, `C:…`), contains a backslash, contains a NUL, or has a `..` segment; duplicate entry names; missing `extension/package.json`; `extension/package.json` larger than 2 MiB or not a JSON object; `contributes.themes` missing, not an array, or empty; more than 20 entries in `contributes.themes`; zero themes left after theme-level errors.
- **FR-4** Theme-level errors drop only that theme, with a warning prefixed `"<label or path>": `. They are: `path` missing or not a string; `path` resolves outside `extension/`; `path` not ending in `.json`/`.jsonc` (a `.tmTheme` theme); theme or included file not in the archive; file larger than 2 MiB uncompressed; unsupported compression method; CRC/length mismatch or corrupt deflate data; invalid JSON or non-object JSON; `include` target outside `extension/` or not `.json`/`.jsonc`; include cycle; include depth over 5; mapping errors from `normalizeColorTheme`.
- **FR-5** `uiTheme` sets the type: `vs` and `hc-light` → `light`; `vs-dark` and `hc-black` → `dark`. A missing or other `uiTheme` keeps the existing resolution (the file's `type`, else `editor.background` luminance, else `dark`) and adds a warning.
- **FR-6** `include` is resolved: the included file's `colors` merge underneath the including file's (`{ ...base.colors, ...own.colors }`), and its `tokenColors` come first (`[...base.tokenColors, ...own.tokenColors]`, so the including file's rules win, as in VS Code). Include depth is at most 5; a cycle is refused.
- **FR-7** A string `tokenColors` (a `.tmTheme` path) in any file of the chain is skipped with a warning; the theme still imports, without those syntax rules.
- **FR-8** Theme name = resolved `label` (NLS placeholder resolved from `extension/package.nls.json`), else the theme file's `name`, else the theme file's base name without extension. `source.fileName` = `<vsix file name>:<path relative to extension/>`, e.g. `ayu-1.0.0.vsix:themes/ayu-dark.json`.
- **FR-9** The import file picker accepts `.json` and `.vsix`; the helper text says so.
- **NFR-1** No new dependency. No synchronous inflate or file I/O in server-reachable code (use `promisify(zlib.inflateRaw)`).
- **NFR-2** No entry is inflated beyond 2 MiB: the declared size is checked first, and `maxOutputLength` enforces it during inflate regardless of the declared size.
- **NFR-3** Only the entries the import needs are inflated (`extension/package.json`, `extension/package.nls.json`, contributed theme files and their includes). Nothing is written to disk during preview.
- **NFR-4** The single-file `.json` path keeps its current behavior, including the 413 for files over 2 MB and the existing warnings for `include` and string `tokenColors`. The one exception: a leading UTF-8 BOM is now stripped before parsing (W2), so a BOM-prefixed file imports instead of failing.
- **NFR-5** No file exceeds its `scripts/lint-file-size.sh` allowance (all touched files are far below the 1000-line ceiling today).

## Decisions (auto mode)

1. **Hand-rolled ZIP reader on `node:zlib`, not a dependency.** The issue lists it first, PAN-4644 kept dependencies minimal, and a new root dependency must also clear `lint:dist-externals`. The reader needs only the central directory, two compression methods and strict refusals, about 150 lines. Fallback if review objects: `fflate` (MIT, zero-dependency) with the same refusal checks done on its directory listing.
2. **Reader lives at `src/lib/color-themes/zip-reader.ts`**, generic over a `Buffer`, throwing `ZipFormatError`. `vsix-import.ts` converts `ZipFormatError` to `ColorThemeImportError` (package-level) or to a warning (theme-level).
3. **Refusals of FR-3 are checked over the whole central directory up front**, not only for entries the import reads. A `..` name anywhere rejects the package; this matches the issue ("Reject ZIP64, encrypted entries and absolute or `..` entry paths") and gives one mechanically testable rule.
4. **>10 MiB archive → 400** (issue AC), while the existing `.json` path keeps its 413 for >2 MB (NFR-4). The size check lives in `importVsixThemes()` so it is unit-testable; the route only maps `ColorThemeImportError` to 400.
5. **>20 themes → package-level 400**, not "import the first 20". Truncation would silently pick an arbitrary subset; a 400 naming the count is honest and matches how the other caps reject.
6. **A theme file over 2 MiB is a theme-level error** (that theme is dropped with a warning). `extension/package.json` over 2 MiB is package-level.
7. **Include paths**: resolve with `path.posix.normalize(path.posix.join(path.posix.dirname(<including entry>), <include>))`. Valid only when the result starts with `extension/`, has no `..` segment, and ends in `.json`/`.jsonc`. `../base.json` from `extension/themes/x.json` therefore resolves to `extension/base.json` and is allowed. Contributed `path` values resolve the same way against `extension/` (`path.posix.join('extension', path)`). A non-string `include` is ignored with a warning.
8. **Depth rule**: the contributed theme file is depth 0; each `include` adds 1. Depth 5 loads; depth 6 is a theme-level error `include depth exceeds 5`. Concretely, when about to load a file, refuse if the chain of files already open above it has more than 5 entries.
9. **Cycle rule**: refuse when the file about to load is already in the chain. The warning shows the chain, e.g. `include cycle: themes/a.json → themes/b.json → themes/a.json`.
10. **Missing `uiTheme`** → existing type resolution plus a warning (FR-5).
11. **Mapping reuse**: split `mapVsCodeTheme(text, fileName)` into `parseVsCodeThemeText(text)` and `mapVsCodeThemeObject(parsed, fileName)`; keep `mapVsCodeTheme` as their composition so the `.json` path and `vscode-import.test.ts` stay unchanged. The `.vsix` path hands `mapVsCodeThemeObject` an already-merged object: `include` deleted, `tokenColors` always an array, `name` set per FR-8, `type` set per FR-5. So the single-file warnings about `include` and string `tokenColors` never fire for `.vsix` themes.
12. **Theme-level warnings are prefixed** with `"<theme name or path>": ` so a multi-theme preview's warning list is unambiguous. Package-level warnings (none expected) and the `.json` path stay unprefixed.
13. **No per-theme selection in the preview.** The preview lists all themes and Save saves all, as the existing component does. Choosing a subset is out of scope.
14. **Fixtures are built at test time** by a small test-only ZIP writer (`src/lib/color-themes/__tests__/zip-fixture.ts`), not committed `.vsix` binaries. Only a writer can produce the ZIP64, encrypted and `..` cases. To guard against the reader and writer sharing a mistake, the writer produces deflated entries by default, supports a data-descriptor mode (local header sizes zero, flag bit 3), and puts a non-empty archive comment after the EOCD.
15. **`fileToBase64` is made chunked.** Its per-byte string concatenation (`useColorTheme.ts` lines 120-125) is acceptable at 2 MB but slow at 10 MB. Replace the loop with `String.fromCharCode(...bytes.subarray(i, i + 0x8000))` chunks (32 KiB keeps the spread below the engine's argument limit).

## Planning Q&A (auto mode — defaults chosen, no operator questions)

1. **Dependency or hand-rolled reader?** Options: hand-rolled on `node:zlib` / `fflate` / `yauzl`. Chose hand-rolled (Decision 1).
2. **Which failures reject the package and which drop one theme?** Chose the split in FR-3 / FR-4: the issue's explicit refusals and manifest problems are package-level; problems inside one theme's file chain are theme-level.
3. **More than 20 themes: reject or truncate?** Chose reject (Decision 5).
4. **Status code for a >10 MB archive?** Issue says 400; the `.json` path uses 413. Chose 400 for `.vsix` and left `.json` alone (Decision 4).
5. **Display name source?** Chose label → file `name` → base name (FR-8), because the label is what VS Code shows in its picker.
6. **Commit binary fixtures?** Chose a runtime writer (Decision 14).
7. **Fix the slow base64 encoder?** Chose yes, since this issue raises the upload size fivefold (Decision 15).

### W1 — ZIP reader (`zip-reader`)

**Files:** new `src/lib/color-themes/zip-reader.ts`; new test helper `src/lib/color-themes/__tests__/zip-fixture.ts`; new `src/lib/color-themes/__tests__/zip-reader.test.ts`.

**API (exact):**

```ts
/** Minimal read-only ZIP reader for .vsix import (PAN-4659): stored + deflated entries only. */
import { crc32, inflateRaw } from 'node:zlib';
import { promisify } from 'node:util';

export class ZipFormatError extends Error {
  constructor(message: string) { super(message); this.name = 'ZipFormatError'; }
}

export interface ZipEntry {
  name: string;
  method: number;
  compressedSize: number;
  uncompressedSize: number;
  crc32: number;
  localHeaderOffset: number;
}

/** Parses and validates the whole central directory. Throws ZipFormatError on any refusal in FR-3's ZIP list. Directory entries (names ending in '/') are validated but left out of the map. */
export function readZipDirectory(archive: Buffer): Map<string, ZipEntry>;

/** Reads one entry's bytes. Throws ZipFormatError when uncompressedSize > maxBytes, the method is not 0 or 8, the local header is bad, inflate fails or exceeds maxBytes, or the length/CRC-32 does not match. */
export async function readZipEntry(archive: Buffer, entry: ZipEntry, maxBytes: number): Promise<Buffer>;
```

**Steps:**

1. Find the EOCD: scan backwards from `archive.length - 22` down to `Math.max(0, archive.length - 22 - 0xffff)` for `readUInt32LE(i) === 0x06054b50`. None → `not a ZIP archive (end of central directory not found)`.
2. ZIP64 → `ZIP64 archives are not supported` when any of: EOCD disk-entry count or total count is `0xffff`; CD size or CD offset is `0xffffffff`; `eocd >= 20 && readUInt32LE(eocd - 20) === 0x07064b50`.
3. Disk number or CD-start disk number non-zero, or disk-entry count ≠ total count → `multi-disk archives are not supported`.
4. `cdOffset + cdSize > eocd` → `central directory is out of bounds`.
5. Walk `total` CD entries from `cdOffset`; each must start with `0x02014b50` and fit inside the CD, else `corrupt central directory`. Read flags (offset 8), method (10), crc (16), compressed (20), uncompressed (24), name length (28), extra length (30), comment length (32), local header offset (42). Name bytes decode as UTF-8 when flag bit 11 (`0x0800`) is set, else as `latin1`.
6. Per entry, in this order: compressed, uncompressed or local offset `=== 0xffffffff`, or an extra-field block with header id `0x0001` → ZIP64 error; `(flags & 0x0001) !== 0 || method === 99` → `encrypted entries are not supported ("<name>")`; unsafe name → `unsafe entry path "<name>" (absolute, backslash, NUL or ".." segment)`; name already seen → `duplicate entry "<name>"`.
7. Unsafe name test: `name.startsWith('/') || /^[A-Za-z]:/.test(name) || name.includes('\\') || name.includes('\0') || name.split('/').includes('..')`.
8. `readZipEntry`: check `entry.uncompressedSize > maxBytes` → `entry "<name>" is <n> bytes; the limit is <maxBytes>`. Method not 0/8 → `entry "<name>" uses unsupported compression method <m>`. Local header at `localHeaderOffset` must have signature `0x04034b50`; data starts at `offset + 30 + readUInt16LE(offset + 26) + readUInt16LE(offset + 28)` and must end within `archive.length`. Method 0: data is `subarray(start, start + compressedSize)` and `compressedSize` must equal `uncompressedSize`. Method 8: `await inflateRawAsync(slice, { maxOutputLength: maxBytes })`; map `ERR_BUFFER_TOO_LARGE` and any zlib error to `ZipFormatError`. Then `out.length !== uncompressedSize` or `(crc32(out) >>> 0) !== entry.crc32` → `entry "<name>" is corrupt (size or CRC mismatch)`.

### W3 — `.vsix` theme import (`vsix-import`)

**Files:** new `src/lib/color-themes/vsix-import.ts`; new `src/lib/color-themes/__tests__/vsix-import.test.ts`.

**API (exact):**

```ts
export const MAX_VSIX_BYTES = 10 * 1024 * 1024;
export const MAX_VSIX_FILE_BYTES = 2 * 1024 * 1024;
export const MAX_VSIX_THEMES = 20;
export const MAX_INCLUDE_DEPTH = 5;

/** Maps every theme in a .vsix's contributes.themes (PAN-4659). Throws ColorThemeImportError for package-level failures; theme-level failures become prefixed warnings. Writes nothing. */
export async function importVsixThemes(archive: Buffer, vsixFileName: string): Promise<{ themes: ColorTheme[]; warnings: string[] }>;
```

**Steps:**

1. `archive.byteLength > MAX_VSIX_BYTES` → throw `ColorThemeImportError(\`archive is ${(n / 1048576).toFixed(1)} MB; the .vsix import limit is 10 MB\`)`.
2. `readZipDirectory(archive)`; a `ZipFormatError` becomes `ColorThemeImportError(\`invalid .vsix: ${err.message}\`)`.
3. `extension/package.json` missing → `extension/package.json not found; is this a VS Code extension package?`. Read it with `readZipEntry(…, MAX_VSIX_FILE_BYTES)` (errors → package-level `invalid .vsix: …`), decode UTF-8, `parseVsCodeThemeText` (errors → `extension/package.json: <message>`).
4. `contributes.themes` not a non-empty array → `extension/package.json contributes no color themes (contributes.themes is missing or empty)`. Length > 20 → `package contributes <n> themes; at most 20 are supported`.
5. Read `extension/package.nls.json` only if present and only when some label matches `/^%(.+)%$/`; a read or parse failure there just leaves placeholders unresolved (warning `package.nls.json: <reason>; labels left unresolved`).
6. For each entry (in array order), inside a `try`: validate `path` (string; `.json`/`.jsonc`; resolves under `extension/` per Decision 7), map `uiTheme` (FR-5), call `loadMerged(entryPath, [])`, set `merged.name` (FR-8) and `merged.type` (when `uiTheme` mapped), call `mapVsCodeThemeObject(merged, \`${vsixFileName}:${entryPath.slice('extension/'.length)}\`)`, push the theme and its warnings (prefixed). On any `ColorThemeImportError` or `ZipFormatError`, push `"<label or path>": <message>; skipped` and continue.
7. `loadMerged(entryPath, chain)`: cycle check (Decision 9), depth check (Decision 8), entry exists (else `"<path>" not found in the package`), read with the 2 MiB cap, `parseVsCodeThemeText`. If `include` is a string, resolve (Decision 7) and recurse with `[...chain, entryPath]`; merge per FR-6. A string `tokenColors` adds the FR-7 warning and counts as `[]`. Return an object with `include` deleted and `tokenColors` an array.
8. After the loop, zero themes → throw `ColorThemeImportError(\`no importable themes in ${vsixFileName}: ${warnings.join('; ')}\`)`.

Use `import { posix } from 'node:path'` for all archive path math. Use a plain `for` loop with `await` (add `// eslint-disable-next-line no-await-in-loop` as `ColorThemeImportPreview.tsx` line 85 does if the rule fires).

## Non-goals

- Per-theme selection in the preview (import a subset of a package's themes).
- `.tmTheme` (XML plist) parsing, for either `tokenColors` or a contributed theme `path`.
- Icon themes (`contributes.iconThemes`) and product icon themes (`contributes.productIconThemes`).
- `semanticTokenColors` / `semanticHighlighting`.
- Downloading a `.vsix` from the VS Code Marketplace or Open VSX by name or URL.
- Changing the single-file `.json` import's limits, status codes or warnings (the BOM strip in W2 is the only `.json` change).
- A general request body cap for the dashboard server.
- ZIP64, multi-disk, encrypted, or non-deflate (bzip2, LZMA, zstd) archives.
- Writing any archive content to disk during preview.
