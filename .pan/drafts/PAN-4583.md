# PAN-4583 — Editor pane: read markdown anywhere under $HOME; keep writes limited to project roots

**Issue:** [PAN-4583](https://github.com/eltmon/overdeck/issues/4583) · **Related:** PAN-3260 (introduced the file-at-path door)

## Glossary

- **File-at-path door** — the two WebSocket RPC methods `pan.readFileAtPath` and `pan.writeFileAtPath`, implemented in `src/dashboard/server/services/file-at-path.ts` and wired in `src/dashboard/server/ws-rpc.ts` (lines 881-887, grep `door (PAN-3260), independent of issueId`). They read or write one markdown file by absolute path, with no `issueId`.
- **Editor pane** — the Stage tab with `paneType: 'editor'`, rendered by `src/dashboard/frontend/src/components/Stage/panes/EditorPane.tsx`. It loads a file through `readFileAtPath` and saves through `writeFileAtPath`.
- **Write roots** — the realpath of every registered project's `config.path` (from `listProjectsSync()`) plus the realpath of `OVERDECK_HOME`. Today this set is computed by `resolveAllowedRoots()` in `file-at-path.ts` (lines 45-65) and gates both reads and writes.
- **Home root** — `realpath(os.homedir())`: the operator's home directory with symlinks resolved.
- **Read roots** — write roots plus the home root. New in this issue.
- **`writable`** — a new boolean on `ReadFileAtPathResult`. It is `true` when the resolved file is inside a write root, `false` otherwise.
- **`isInsidePath(parent, child)`** — the helper in `file-at-path.ts` (lines 23-25) that returns true only when `child === parent` or `child` starts with `parent + sep`. The separator is what stops `/home/eltmon2/x.md` from passing a `/home/eltmon` root.

## Problem

Opening `~/Projects/OpenMontage/projects/myn-intro/artifacts/script.md` from a conversation chip shows "Couldn't open file — Path is outside the allowed project roots". `OpenMontage` is not a registered Overdeck project, so the read is rejected.

The root cause is that `readFileAtPath` and `writeFileAtPath` share one `validateAndResolve()` (file-at-path.ts lines 67-109). Its containment check (lines 98-101) rejects any realpath outside the write roots:

```ts
  const allowedRoots = await resolveAllowedRoots();
  if (!allowedRoots.some((root) => isInsidePath(root, realPath))) {
    throw new PanRpcError({ message: 'Path is outside the allowed project roots', code: 'PATH_NOT_ALLOWED' });
  }
```

The comment on `resolveAllowedRoots` (lines 45-49) says the allowlist is narrow "since this door also grants writes". Reads were narrowed only because they share the check.

## Proposal

Split containment by direction inside the same validation function:

- **Read:** accept a realpath inside the read roots (home root or any write root). Every other check stays as it is today.
- **Write:** unchanged. Accept a realpath inside the write roots only. No file creation.
- **Contract:** `ReadFileAtPathResult` gains `writable: boolean`.
- **Editor pane:** a `writable: false` file opens read-only with a note. The operator cannot type edits that can only fail on save.

## Requirements

### Functional

- **FR-1** `readFileAtPath` returns the file for an existing regular markdown file whose realpath is inside the home root or a write root, with `writable` set to whether the realpath is inside a write root.
- **FR-2** `readFileAtPath` rejects with `PATH_NOT_ALLOWED` a realpath outside every read root. This covers a symlink under the home root that resolves outside it and a sibling-prefix path such as `<home>2/x.md`.
- **FR-3** `writeFileAtPath` rejects with `PATH_NOT_ALLOWED` and the message `Path is outside the allowed project roots` any realpath outside the write roots, including a markdown file under the home root. Write behavior for paths inside write roots is unchanged.
- **FR-4** All pre-existing checks apply to both directions unchanged: max path length 4096, absolute path, markdown extension (`.md`, `.mdx`, `.markdown`) on the given path and on the realpath, existing regular file, and (read only) the 1 MiB size cap.
- **FR-5** `ReadFileAtPathResult` in `packages/contracts/src/rpc.ts` has a required `writable: Schema.Boolean` field, and the doc comment on `ReadFileAtPathRpc` describes the read roots and the meaning of `writable`.
- **FR-6** `EditorPane` renders a file loaded with `writable: false` read-only: the textarea has the `readonly` attribute and ignores change events, the Save button is disabled, Ctrl/Cmd+S sends no write, and a note with `data-testid="editor-pane-readonly-note"` reads `Read-only — this file is outside the registered project roots.`
- **FR-7** `docs/MARKDOWN-EDITOR-PANE.md` describes the split read/write containment, the `writable` field, the read-only pane state, and who can call `/ws/rpc`.

### Non-functional

- **NFR-1** Server tests never depend on the real home directory: the home root is injected by mocking `node:os` `homedir` in the test file.
- **NFR-2** No new npm dependency, no new RPC method, no new error code.
- **NFR-3** Containment is always evaluated on the realpath, never on the lexical path.

## Security analysis — who can call `/ws/rpc`

This section is the analysis the issue requires in the PR description. Work item 4 copies it into `docs/MARKDOWN-EDITOR-PANE.md`, and the work agent pastes it into the PR body.

1. **Every `/ws/rpc` caller holds the `admin` scope.** `rejectUnauthorizedRpcUpgrade` in `src/dashboard/server/ws-rpc.ts` (line 1120, grep `export function rejectUnauthorizedRpcUpgrade`) and the upgrade handler at line 1140 call `authorizeDashboardUpgrade(headers, method)` from `src/dashboard/server/ws-auth.ts` (lines 33-48). Its default `requiredScope` is `'admin'`. It checks the origin, then requires a credential (session cookie, internal token, or an `odk_` registry credential), then requires the scope. `docs/DASHBOARD-AUTH.md` (line 72) lists `/ws/rpc` under `admin`.
2. **`admin` already grants a shell as the dashboard user.** `scopeSatisfies` in `src/lib/access-tokens.ts` (lines 81-84) returns true for any required scope when `admin` is granted. `/ws/terminal` needs `operate` (`docs/DASHBOARD-AUTH.md` line 71). So every `/ws/rpc` caller can open a terminal pane and run `cat` on any file the dashboard user can read, which includes every file under `$HOME`. The read widening gives no caller access it does not already have.
3. **Callers by surface.** The local operator's browser (session cookie minted for loopback peers), the domain/Traefik-exposed dashboard (same credential requirement; `remote-request-gate.ts` and `ws-auth.ts` apply to remote peers too), paired devices (pairing always grants `['admin']`, `docs/DASHBOARD-AUTH.md` line 60), and the desktop app (it runs the same server and authenticates the same way) all reach `/ws/rpc` only with `admin`. A narrow `kind: 'token'` access token without `admin` gets 403 at the upgrade.
4. **Shared Sessions viewers cannot reach `/ws/rpc`.** The share service (`services/share`, `docs/SHARED-SESSIONS.md`) is a Cloudflare Worker that relays signaling only. A search of `src`, `apps`, and `packages` for `RTCDataChannel`, `DataChannel`, `webrtc`, and `odh_` finds no host-side transport in this repo, so no viewer message is routed to any RPC handler. If a later Shared Sessions phase proxies RPCs over the DataChannel, `readFileAtPath` and `writeFileAtPath` must be excluded from the proxied set. That is recorded as a hazard for future work, not a change in this issue.

Conclusion: every caller of this RPC is already an operator with shell-equivalent access, so the read widening is acceptable. The write door is not widened.

## Decisions

- **D-1 One validation function, a direction argument.** `validateAndResolve(path, door)` with `door: 'read' | 'write'` keeps the existing check order. The containment check sits exactly where it is today (after the realpath extension check, before the regular-file check), so write error precedence is unchanged.
- **D-2 Read-rejection message.** A read outside every read root throws `PATH_NOT_ALLOWED` with the message `Path is outside your home directory and the registered project roots`. A write outside the write roots keeps the existing message `Path is outside the allowed project roots`.
- **D-3 Home root injection.** `file-at-path.ts` imports `homedir` from `node:os`. Tests mock `node:os` with a spread of the real module so `tmpdir()` keeps working.
- **D-4 Frontend fails closed.** The pane treats only `writable === true` as editable. Every existing `readFileAtPath` mock in `EditorPane.test.tsx` gains `writable: true` so the existing save tests keep their meaning.
- **D-5 Home root equal to the filesystem root.** No special code. `isInsidePath('/', x)` only matches `x === '/'` because the prefix becomes `//`, so a home of `/` grants nothing extra. Do not change `isInsidePath`.
- **D-6 A missing home directory** (realpath of `homedir()` throws) contributes no read root, exactly like a missing project path today.
- **D-7 Contract and server ship as one work item.** Adding a required field to `ReadFileAtPathResult` breaks `npm run typecheck` until `readFileAtPath` returns it, so they cannot land separately.
