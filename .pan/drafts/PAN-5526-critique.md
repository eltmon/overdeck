## blocks-the-design: Explicit auto-start renews consent during promotion

The plan treats `autoSpawn: true` as a harmless explicit copy of the granted flag (PRD D5, FR-2, FR-5), but the server interprets it as a **new consent generation**. `src/lib/planning/spawn-planning-session.ts:77-84` calls `writeAutoSpawnOnFinalizeFlag` for any explicit boolean; `src/lib/planning/auto-spawn-consent.ts:139-147` creates a fresh UUID and sets status to `granted`. The complete-planning route does this before origin validation, its in-flight lease, and all promotion gates (`src/lib/overdeck/planning-promotion.ts:555-575`). If a work-start claim is made after the CLI's read but before the request reaches that resolver, the request replaces the claimed generation. Completing the old claim then cannot spend consent (`auto-spawn-consent.ts:190-205`); the existing test at `src/lib/planning/__tests__/resolve-auto-spawn-on-finalize.test.ts:78-86` demonstrates that old claims leave the new generation granted. A concurrent or repeated finalize can therefore leave usable auto-start consent after work has started. The existing omitted-body path already reads granted consent without rewriting it (`spawn-planning-session.ts:84`). Smallest fix: keep the shared CLI reader for reporting, but do not send an explicit `true` until the server has a path that verifies the current grant without creating a new generation. Update FR-2/FR-5 and the POST-body acceptance criteria accordingly, or include the server change and a claim-race test in this issue.

## blocks-the-design: Failure still announces implementation starting

`planFinalizeCommand` emits the activity entry and TTS line at `src/cli/commands/plan-finalize.ts:387-403`, before its POST at lines 417-420. After the planned reader change, a granted record makes both messages say implementation is starting even when the POST returns HTTP 500, times out, or fails and the command exits 1 at lines 439-457 and 519-520. The proposed console text repairs only the final human-readable branch; the activity feed and TTS still make a false promise on precisely the failure path this issue aims to correct. Smallest fix: emit a failure-specific activity/TTS message after promotion fails, and reserve “starting implementation” for a confirmed successful promotion. Add that failure case to the message test and adjust FR-2's activity criterion.

## sharpens-framing: A timeout does not establish that promotion failed

`promotePlanning` deliberately does not retry `AbortError` because the request may have partially executed (`src/cli/commands/plan-finalize.ts:604-618`). The proposed text says the dashboard “did not finish complete-planning” and tells the operator to run `pan plan done` in every failure case. For a timeout, the server may still be working or may have completed before the CLI prints. Smallest fix: describe the outcome as unconfirmed for timeouts and tell the operator to check whether promotion completed before retrying; keep the direct `pan plan done` instruction for confirmed failures. The docs paragraph should also qualify its claim that a marker is always written, since lines 454-455 explicitly handle a marker-write failure.
