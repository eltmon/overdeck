**Issue:** [PAN-4743](https://github.com/eltmon/overdeck/issues/4743) · **Parent PRD:** `.pan/drafts/pan-2350.md` (Overdeck Anywhere, revision 5): FR-10, FR-18, FR-22, D-12, D-19.
**Sibling PRDs:** `.pan/drafts/PAN-4651.md` (Machine field, Auto, fleet routes), `.pan/drafts/PAN-4652.md` (Fly machines, `addFlyMachine`), `.pan/drafts/PAN-4638.md` (lanes on linked machines).
**Planned:** 2026-11-02, `pan plan --auto`, against `main` at `367378705ca` (PAN-4651 #4744, PAN-4652 #4742 and PAN-4638 #4758 merged).

## Glossary

- **Home** — the operator's machine: the dashboard that starts the Fly VM and holds the link.
- **Fly machine** — a Fly.io VM that runs `pan serve` and is linked one way from home (PAN-4652). Its label is `fly-<machineId>`. `addFlyMachine()` in `src/dashboard/server/services/fly-machine-service.ts` is the one door that creates one.
- **Fly (new VM)** — the Machine-field choice and the `machine: "fly"` value of the fleet routes: "create a new Fly machine for this spawn, then start the work on it". It is different from naming an existing linked Fly machine by its label (`fly-<id>`), which already works.
- **Fleet route** — the `POST /api/fleet/*` spawn routes in `src/dashboard/server/routes/fleet-work.ts`. They resolve `machine` with `resolveTargetMachine` and post the owner's work door over the link.
- **Target** — `FleetTarget` (`src/dashboard/server/services/fleet-target.ts`): `{ ok: true, self: true, … }`, `{ ok: true, self: false, link, … }` or `{ ok: false, status, body }`.
- **Spawn context** (new) — `FlySpawn`: what a fleet route knows about the spawn that `addFlyMachine` needs (project key, harness, model, whether the caller may create a VM). Only a route that can run its work on a new Fly machine passes one.
- **Fly target door** (new) — `startFlyTarget()` in the new module `src/dashboard/server/services/fleet-fly-target.ts`: checks, `addFlyMachine`, and a `FleetTarget` for the new link with a `discard` hook.
- **Discard** — unlinking and destroying the Fly machine a spawn just created, when the spawn then fails. It calls `handleMachinesUnlink(link.id)` (`src/dashboard/server/routes/machines.ts`), which runs the PAN-4652 unlink hook (`removeFlyMachineForLink`, destroy, never stop).
- **Idle sweep** — `sweepFlyMachines` (`src/lib/remote/fly-machine-loops.ts`): every 60 s it destroys a Fly machine on which no *linked conversation* has been active for `remote.fly.machine_idle_minutes` (default 30).
- **`remote.auto_fly`** (new config key, `[remote]` in `~/.overdeck/config.toml`) — when `true`, **Auto** creates a Fly machine for a conversation when no machine fits (epic D-19). Default `false`.
- **Admin credential** — a dashboard credential whose `credentialScopes()` include `admin`: the internal token (every local `pan` CLI and agent), the root browser session, or an `odk_` token/device granted `admin`.

### What a new Fly machine can and cannot hold today (verified)

- **A conversation: yes.** A conversation on the VM is a linked conversation at home, so the idle sweep sees it (`fly-machine-loops.ts:144-147`: a machine is active while a linked row for its environment id is `active` or recently active). PAN-4652's live run streamed one home.
- **A work agent (`pan start --machine fly`): not safely.** The owner's issue-start door spawns `agent-<issue>` (`routes/machines-work.ts`, `handleWorkIssueStart`). The shared conversation list excludes `agent-%` rows (`src/lib/overdeck/conversations.ts:555`, `AND c.name NOT LIKE 'agent-%'`), so home's `linked_conversations` never has a row for it, and the idle sweep destroys the VM after 30 minutes under a running agent. [PAN-4734](https://github.com/eltmon/overdeck/issues/4734) makes Fly work agents linked conversations; that is the fix, and it is that issue's scope.
- **A worker (`pan worker run --machine fly`): never.** `startWorker` throws `"<issue> has no workspace at <path>. Run pan start <issue> first."` (`src/lib/agents/worker/start.ts:130-131`), and a new VM has no issue workspace.
- **A lane (`pan lane start --machine fly`): not through the resolver.** `launchLane` resolves the machine at step 3 (`src/lib/lanes/launch.ts:412-415`), before the harness is resolved (step 5, `:447-450`) and before the one-live-lane check (step 7). Provisioning there would create a VM for a launch that is then refused, and with the wrong harness. A new VM per lane needs provisioning moved inside the lane's project lock, plus the per-run cap `gauntlet.fly.max_vms` (epic FR-18). That is lane-core work, not resolver work.

So this issue delivers **Fly (new VM) for conversations** — the Machine field, `POST /api/fleet/conversations` `machine: "fly"`, and Auto's `remote.auto_fly` fallback for conversations — plus the **Add a Fly machine** dialog. Every other `--machine fly` refuses with a sentence that says why and what to use instead.

## Goals

- In the new-conversation dialog, **Fly (new VM)** is enabled when a project is chosen. Create starts a Fly machine, clones the project, starts the conversation there and opens it at `/conv/@<env>/<name>` with a `fly-<id>` chip.
- `POST /api/fleet/conversations { machine: "fly", projectKey, message, … }` does the same for any admin caller (the MCP `start_conversation` tool with an admin token included).
- With `remote.auto_fly = true`, **Auto** for a conversation creates a Fly machine when no machine fits, and says so in the reason line.
- Settings → Anywhere → Machines has **Add a Fly machine**, which calls `POST /api/machines/fly`.
- `pan start --machine fly`, `pan worker run --machine fly`, `pan lane start --machine fly` and the fleet worker and issue-start routes with `machine: "fly"` refuse with a sentence that names the reason and the alternative. No message names PAN-4652 any more.
- A spawn that created a Fly machine and then failed destroys that machine at once.

## Non-goals

- `pan start --machine fly` (a work agent on a new Fly machine) and Auto creating a VM for `pan start`. PAN-4734 owns Fly work agents; until their sessions are linked conversations, the idle sweep would destroy the VM under them (see Problem).
- `pan worker run --machine fly`: a worker needs its issue workspace, which a new VM never has.
- `pan lane start --machine fly` (a new VM per lane) and `gauntlet.fly.max_vms`. Lane-core work (see Problem); owned by the follow-up [PAN-4811](https://github.com/eltmon/overdeck/issues/4811), filed during planning.
- Auto creating a VM for workers, issue starts or lanes. `remote.auto_fly` covers conversations only.
- Changing the idle sweep, the spend cap, provisioning, `addFlyMachine` or `POST /api/machines/fly` behavior.
- Changing the MCP tool descriptions in `src/lib/mcp/tools-write.ts`.
- A Fly region picker with a list of regions, image selection, harness or first message in the Add-a-Fly-machine dialog (the CLI keeps those flags).
- Fixing [PAN-4740](https://github.com/eltmon/overdeck/issues/4740) (first request after idle hangs up) or [PAN-4741](https://github.com/eltmon/overdeck/issues/4741) (private Fly IPs ranked first).
- `POST /api/fleet/placement` and the CLI's Auto: they never answer Fly.

## Requirements

### Functional

- **FR-1** `resolveTargetMachine(machine, gitOrigin, needs, deps, spawn)` with `machine` equal to `fly` (any case) and a `spawn` context calls the Fly target door and returns its target. Without a `spawn` it refuses 400 `fly-unavailable` with the sentence in D-4743-6.
- **FR-2** The Fly target door refuses before creating anything, in this order: a caller without an admin credential (403 `fly-needs-admin`); no project (400 `fly-needs-project`); a project without a git origin (409 `project-has-no-origin`); a project whose origin is not on GitHub (409 `project-not-on-github`); `needs` with a tag other than `linux` or `docker` (409 `needs-unmet`, with `missing`).
- **FR-3** The Fly target door calls `addFlyMachine({ projectKey, harness?, model? }, { notifyLinksChanged })`. A `FlyMachineError` answers its `FLY_MACHINE_ERROR_STATUS` with `{ code, error: <message> }`; a `MachineLinkError` answers its `ERROR_STATUS` the same way; any other error answers 500 `{ code: 'fly-failed', error }`.
- **FR-4** On success the door returns `{ ok: true, self: false, link, environmentId, label: 'fly-<id>', reason: 'Fly (new VM) → fly-<id> (<region>)', discard }`, where `link` is the stored `MachineLink` and `discard()` unlinks and destroys that Fly machine. When `needs` includes `docker` and the record says `docker: false`, it discards the machine and answers 409 `needs-unmet` with `missing: ['docker']`.
- **FR-5** `remote.auto_fly` is an optional boolean in `[remote]`. A non-boolean value makes config loading throw `remote.auto_fly must be a boolean`.
- **FR-6** `resolveTargetMachine('auto', …)` with a `spawn` context, a non-null `gitOrigin`, `needs` within `linux`/`docker`, no fitting machine, and `remote.auto_fly === true` calls the Fly target door. Its reason is `Auto → fly-<id> (new Fly machine). No machine fits: <rejections>`. In every other no-fit case it answers 409 `no-machine-fits` exactly as today.
- **FR-7** `POST /api/fleet/conversations` passes a spawn context (`projectKey`, `harness`, `model`, `mayCreate`) to `resolveTarget`. `mayCreate` is true only for an admin credential. When the target has `discard` and the owner refuses (any answer other than 201, except 503 `machine-unreachable`), the route calls `discard()` before it answers the refusal. A 503 `machine-unreachable` (the 30 s `WORK_DOOR_TIMEOUT_MS`, or a hang-up, PAN-4740) does not discard, because the conversation may be starting on the VM; the route answers 503 with `<label> (new Fly machine) did not answer in time; it is still linked. Open it from the conversation list, or remove it with pan machines unlink <label>.` and leaves the VM to the idle sweep.
- **FR-8** `POST /api/fleet/workers`, `POST /api/fleet/issues/:id/start` and `POST /api/lanes` pass no spawn context, so `machine: "fly"` answers 400 `fly-unavailable` and creates nothing.
- **FR-9** `pan start --machine fly` and `pan worker run --machine fly` exit 1 with the CLI sentence in D-4743-6 and call no dashboard route.
- **FR-10** The Machine field's **Fly (new VM)** option is enabled when the dialog has a project and disabled, with the title `Fly (new VM) needs a project`, when it has none. Clearing the project while **Fly (new VM)** is chosen sets the Machine field back to this machine.
- **FR-11** While a conversation with **Fly (new VM)** is being created, the dialog shows `Starting a Fly machine. This takes a few minutes.` and the submit button reads `Starting…`.
- **FR-12** Settings → Anywhere → Machines shows **Add a Fly machine**. Its dialog has a Project select (optional) and a Region input under Advanced (optional), posts `POST /api/machines/fly`, shows the server's `message` on failure, and on success toasts `Linked <label> (Fly app <app>, region <region>)`, refreshes the machines list and closes.
- **FR-13** The documents in WI-11 describe the behavior above, and no document or code string says `needs PAN-4652` or `until PAN-4652` about Fly (new VM).

## Decisions (made here)

- **D-4743-1 Conversations only (auto mode).** The issue asks for `--machine fly` generally. Work agents on a new VM would be destroyed by the idle sweep (`conversations.ts:555` excludes `agent-%`, `fly-machine-loops.ts:144-147` counts only linked rows), workers cannot run without a workspace (`worker/start.ts:130-131`), and lanes resolve the machine before the harness and the one-live-lane check (`launch.ts:412-450`). Shipping `fly` there would create VMs that are destroyed under running work or leaked by refused launches. So Fly (new VM) ships for conversations, which is what the Machine field starts, and the rest refuse with an accurate sentence. PAN-4734 owns work agents on Fly (planning comment posted there); PAN-4811 owns lanes and `gauntlet.fly.max_vms`.
- **D-4743-2 The resolver takes a spawn context; the door lives in its own module.** `resolveTargetMachine` gains a fifth optional parameter `spawn?: FlySpawn`; its default `deps` stays the fourth. Every route already calls `deps.resolveTarget(machine, gitOrigin, needs)`, so the `fly` and auto-fly branches stay in one resolver and a route opts in by passing `spawn`. The provisioning logic (checks, `addFlyMachine`, error mapping, discard) goes in the new `services/fleet-fly-target.ts` so `fleet-target.ts` stays a pure resolver plus one call.
- **D-4743-3 The conversation still starts through the owner's work door.** The Fly target door calls `addFlyMachine` with `projectKey` and without `message`, then the conversation route posts `/api/machines/work/conversations` exactly as for any linked machine. One path for every machine keeps the caller's actor (an agent sender stays that agent, so the PAN-4651 agent fence applies), the git-origin project match and the `refreshLinked` listing. `startFlyConversation` (which always acts as `operator`) stays the `pan machines add-fly --message` path only. The clone step runs between linking and the work-door call, so the supervisor has the link open by then (the PAN-4652 header says the same).
- **D-4743-4 Who may create a VM: admin credentials only.** `POST /api/machines/fly` needs `admin` (PAN-4652 D-14) because a VM costs money. The fleet routes need only `operate`, so `fly` through them must not lower that bar. `FleetCaller` gains `mayCreateFly`, computed in `fleetCaller()` as `credentialScopes(credential).includes('admin')` before the ceiling drops `admin`. Local agents call through the internal token, which is admin, and could run `pan machines add-fly` anyway, so refusing agent senders would protect nothing; an `odk_` token or device without `admin` (an MCP client, a phone) is refused with 403 `fly-needs-admin`. Requests through a secure channel are already refused by `fleetWriteGate`.
- **D-4743-5 `needs` with Fly.** A Fly machine's tags are `linux` and, when its Docker started, `docker` (PAN-4652 live run: `dockerd --storage-driver=vfs`, `hello-world` exits 0). The door refuses any other tag before it creates anything. `docker` is checked again after provisioning against `record.docker`; a VM without it is discarded. The constant is `FLY_MACHINE_TAGS = ['linux', 'docker']` in `fleet-fly-target.ts`.
- **D-4743-6 The refusal sentences.**
  - Server, no spawn context (`fleet-target.ts`): `Fly (new VM) starts conversations only. To run this elsewhere, link a Fly machine with pan machines add-fly --project <key> and name it with --machine fly-<id>.`
  - CLI (`worker-remote.ts`, used by `pan start` and `pan worker run`): `--machine fly starts a new Fly machine for a conversation only: use Fly (new VM) in the new-conversation dialog, or pan machines add-fly --project <key> --message <text>. Work agents on a new Fly machine are PAN-4734.`
  - Server, no project: `Fly (new VM) needs a project: the new machine clones it.`
  - Server, not admin: `Starting a Fly machine needs an admin credential.`
  - Server, not GitHub: `Only GitHub projects can run on a Fly machine; <key> has no github_repo.` (the wording `ensureFlyProject` already uses, checked up front so no VM is created for nothing).
- **D-4743-7 Discard at once on a refusal, never on a timeout.** An owner refusal after provisioning leaves a VM with nothing on it. The idle sweep would destroy it after 30 minutes, but it would hold a `remote.max_concurrent_agents` slot meanwhile. `discard()` calls `handleMachinesUnlink(link.id)`, which notifies the peer, runs `removeFlyMachineForLink` (destroy), removes the link and calls `notifyLinksChanged`. A discard error is logged with `console.warn('[fleet-fly] …')` and never replaces the refusal the route answers; the sweep remains the backstop. A 503 `machine-unreachable` is not a refusal: `postWorkDoor` aborts after 30 s (`WORK_DOOR_TIMEOUT_MS`, `fleet-work.ts`) and PAN-4740 can hang up the first request, while the VM may already be starting the conversation. So a 503 keeps the VM and names it in the error; the idle sweep removes it if nothing runs there.
- **D-4743-8 `remote.auto_fly` lives in `config.toml`.** `[remote]` and `[remote.fly]` keys come from `config.toml` through `loadConfig()` (`src/lib/config.ts:368-400`); the `config.yaml` overlay replaces only `resiliency_tier` and `max_concurrent_agents` and spreads the rest, so `auto_fly` survives it. It is read per request (`(await loadConfig()).remote?.auto_fly === true`), like `machine_idle_minutes`. No Settings UI control is added.
- **D-4743-9 The fleet error shape.** Fleet refusals are `{ code, error }` (the dialog's `createFleetConversation` throws `answer.error`). `POST /api/machines/fly` keeps its own `{ error: <code>, message }` shape, which the Add-a-Fly-machine dialog reads as `body.message ?? body.error`.
- **D-4743-10 An activity entry for every VM the fleet creates.** The door emits the same entry `routes/machines-fly.ts` emits (`Added Fly machine "<label>" (<app>, <region>)`), with `source: 'dashboard'`, so a VM the dialog starts appears in the activity log like one `add-fly` starts.
- **D-4743-11 The dialog has two fields.** Project (optional) and Region (Advanced, optional): within the page-not-modal limit of four fields, like `AddSshMachineDialog`. A conversation on a new VM is started from the new-conversation dialog, so the Add dialog has no message, harness or model fields.
- **D-4743-12 Live check is consent-gated.** A real run costs Fly money. WI-12 asks the operator with `pan ask` before it spends; without consent it records the unit and browser evidence only and says so in the PR.

### WI-1 The Fly target door (FR-2, FR-3, FR-4, NFR-1, D-4743-2, -4, -5, -7, -9, -10)

- **Files:** `src/dashboard/server/services/fleet-fly-target.ts` (new), `src/dashboard/server/__tests__/fleet-fly-target.test.ts` (new).
- **Shape:**
  ```ts
  /** What a fleet route knows about a spawn that may run on a new Fly machine (PAN-4743). */
  export interface FlySpawn {
    projectKey: string | null;
    harness?: string;
    model?: string;
    /** The caller holds an admin credential (D-4743-4). */
    mayCreate: boolean;
  }

  export interface FlyTargetRequest extends FlySpawn {
    gitOrigin: string | null;
    needs: readonly string[];

  /** The tags a new Fly machine can have (D-4743-5). */
  export const FLY_MACHINE_TAGS: readonly string[] = ['linux', 'docker'];

  export interface FlyTargetDeps {
    addFly: (input: AddFlyMachineInput) => Promise<AddFlyMachineResult>;
    links: () => Promise<MachineLink[]>;
    unlink: (linkId: string) => Promise<void>;
    activity: (message: string, details: Record<string, unknown>) => void;
    warn: (message: string) => void;
  }

  export async function startFlyTarget(request: FlyTargetRequest, deps: FlyTargetDeps = defaultFlyTargetDeps()): Promise<FleetTarget>;
  ```
  `FleetTarget`'s remote variant gains `discard?: () => Promise<void>` (edit the type in `fleet-target.ts`; `fleet-fly-target.ts` imports the type only).
- **Defaults:** `addFly: (input) => addFlyMachine(input, { notifyLinksChanged })` (`notifyLinksChanged` from `../routes/machines.js`); `links: listLinks`; `unlink: async (id) => { await handleMachinesUnlink(id); }`; `activity` calls `emitActivityEntry({ source: 'dashboard', level: 'info', message, details: JSON.stringify(details) })`; `warn: (m) => console.warn(`[fleet-fly] ${m}`)`.
- **Steps:**
  1. Refuse in the FR-2 order, returning `{ ok: false, status, body: { code, error } }` (and `missing` for `needs-unmet`). The GitHub check is `!request.gitOrigin.startsWith('github.com/')`.
  2. `const result = await deps.addFly({ projectKey, ...(harness ? { harness } : {}), ...(model ? { model } : {}) })` inside `try`; map errors per FR-3 (`FLY_MACHINE_ERROR_STATUS` from `src/lib/anywhere/fly/provision.js`, which re-exports it; `ERROR_STATUS` and `MachineLinkError` as `routes/machines-fly.ts` imports them).

  4. Build `discard = async () => { try { await deps.unlink(link.id); } catch (error) { deps.warn(`could not discard ${result.record.label}: ${(error as Error).message}`); } }`.
  5. When `request.needs.includes('docker') && !result.record.docker`, `await discard()` and answer 409 `{ code: 'needs-unmet', error: '<label> has no docker', missing: ['docker'] }`.
  6. Emit the D-4743-10 activity entry, then return `{ ok: true, self: false, link, environmentId: link.environmentId, label: result.record.label, reason: `Fly (new VM) → ${result.record.label} (${result.record.region})`, discard }`.
