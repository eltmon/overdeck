# PAN-4935 — Agent MCP and bots (W-INJ4): Instructions blocks and the no-MCP fallback

**Status:** planned · **Revision:** 1 (2026-11-04) · **Author:** Claude Opus 5.5 (planning agent, `pan plan --auto`)
**Issue:** [PAN-4935](https://github.com/eltmon/overdeck/issues/4935) · **Epic:** [PAN-4927](https://github.com/eltmon/overdeck/issues/4927), work item **W-INJ4** in `.pan/drafts/pan-4927.md`
**Traces (epic):** FR-1, D-12, D-13, NFR-10, AC-6.
**Depends on (all merged on `main` at `7e4cfe981d2`):** W-INJ1 (PAN-4932), W-INJ2 (PAN-4933), W-INJ3 (PAN-4934), W-SELF2 (PAN-4937), W-DEL1 (PAN-4938), W-SCHED1 (PAN-4939), W-MEM1 (PAN-4940), W-SEC1 (PAN-4941), W-LINK1 (PAN-4942), W-PR1 (PAN-4943, merged as `7e4cfe981d2`), W-APPR1 (PAN-4944).

**Why this exists.** Since W-INJ1–3, every Claude Code, Codex, ACP (`acp`) and OpenCode (`opencode`) agent starts with an `overdeck` MCP server. Nothing tells the agent the server exists, which tools matter, or how the 50 s wait chunks work, so agents keep running `pan` in Bash and polling. Harnesses without the server (`kimi-code`, `ohmypi`, `muse`, `prime-agent`) are told nothing either. This item adds two short instruction blocks to the managed launch context: the **MCP block** for agents that get the server and the **CLI block** (the `pan` equivalents) for every other agent.

## Glossary

- **Managed launch context:** the Overdeck-owned Markdown every managed harness receives at launch: machine context, bundled rules, project layer, memory index and workspace layer. Built by `renderManagedLaunchContext(workspace, harness)` (`src/lib/context-layers/materialize.ts:30`). Claude Code gets it through `--append-system-prompt-file`, Codex as `developer_instructions`, ACP/OpenCode through the ACP host's `--context-file`, kimi-code in its first message, prime-agent through its own context file.
- **Shared launch file:** the file `materializeSharedManagedLaunchContext` writes at `~/.overdeck/context/launch/<harness>-<workspaceHash>.md` (`materialize.ts:70-80`) and that `claudeSystemPromptFiles` (`src/lib/context-layers/launch-sources.ts:10`) returns for claude-code, codex, kimi-code and ohmypi launches.
- **ACP context file:** `<agentDir>/acp-context.md`, written by `materializeAcpContextFile` (`src/lib/acp/context.ts:5`), called by `getAcpLauncherFields` (`src/lib/agents/runtime-command.ts:122`, call at line 147) and by `AcpRuntime.spawnAgent` (`src/lib/runtimes/acp.ts:181`).
- **Muse context file:** `~/.overdeck/agents/<id>/muse-context.md`, written by `materializeMuseContext` (`src/lib/runtimes/muse-context.ts:13`). It has its own composer and never calls `renderManagedLaunchContext`.
- **Overdeck MCP gate:** the existing rule for "this launch gets the `overdeck` MCP server": `overdeckMcpEnabledFor(harness, env)` (`src/lib/mcp/agent-injection.ts:36`) = the harness capability `overdeckMcp` (`harnessGetsOverdeckMcp`, line 31) **and** not a Docker workspace (`OVERDECK_DOCKER_WORKSPACE=1` or `PAN_DOCKER=1`) **and** config `mcp.agents` (default `true`).
- **MCP block:** `OVERDECK_MCP_INSTRUCTIONS`, the `## Overdeck tools` section (≤ 1,500 characters).
- **CLI block:** `OVERDECK_CLI_INSTRUCTIONS`, the `## Overdeck commands` section (≤ 1,500 characters).
- **Tools block:** whichever of the two a launch gets. Every managed launch context gets exactly one.
- **`ALL_TOOLS`:** the list of every Overdeck MCP tool (`src/lib/mcp/server.ts:44`).

## Requirements

### Functional

- **FR-1** Every managed launch context ends with exactly one tools block: the MCP block when the launch's Overdeck MCP gate is true, else the CLI block.
- **FR-2** The MCP block names only tools that exist in `ALL_TOOLS`, tells the agent to prefer them to `pan`, and states the wait-chunk rule (call `next` again on `running` or `pending`; never poll).
- **FR-3** The CLI block names the `pan` command for each topic the MCP block covers (delegation and waiting, checklist, done, handoff, memory, lanes, PR linking) and says secrets and machine links need the operator.
- **FR-4** The decision uses the same gate as injection (`overdeckMcpEnabledFor`), so a Docker workspace or `mcp.agents: false` gives a claude-code, codex, acp or opencode agent the CLI block.
- **FR-5** The two variants of the shared launch file never share a file.
- **FR-6** Muse launches get the tools block from the same gate.
- **FR-7** The docs say which agents get which block and what each block covers.

### Non-functional

- **NFR-1** Each block is at most 1,500 characters (epic NFR-10).
- **NFR-2** `src/lib/mcp/agent-instructions.ts` imports nothing (pure constants and one pure function). The gate moves to a leaf module `src/lib/mcp/overdeck-mcp-gate.ts` that imports only `../runtimes/behavior.js`, `../runtimes/types.js` (type) and `../config-yaml.js`. `npm run lint:circular` stays green.
- **NFR-3** No new `*Sync` function, no `execSync`, no sync/async twin (repo rules `no-execsync-server`, `prefer-async`; CLAUDE.md "One variant per operation"). Existing sync writes in `materialize.ts` stay as they are.
- **NFR-4** No god-file growth: `spawn.ts`, `spawn-prep.ts`, `spawn-planning-session.ts` and `conversation-runtime.ts` change in place only (zero added lines); `runtime-command.ts` grows by at most 3 lines and stays ≤ 1,000.
- **NFR-5** Fail safe: when the flag is absent or any check fails, the launch gets the CLI block, never a promise of tools it may not have.

## Decisions

- **D-1 The flag is computed from the gate, not threaded from injection results.** The epic says "callers that inject the server pass `true`". Threading the injection result would change every launch site in five god files (F-7, F-9) and reorder context rendering after the mint. The gate (`overdeckMcpEnabledFor`) is exactly the condition every `prepare*OverdeckMcp` checks before it injects, so computing the flag from it gives the same answer at three places: `claudeSystemPromptFiles`, `getAcpLauncherFields` and `materializeMuseContext`. The one difference (a failed mint, F-7) is accepted as H-1.
- **D-2 Absent flag ⇒ CLI block.** `renderManagedLaunchContext(workspace, harness, opts = {})` and its two materializers take `opts.overdeckMcp?: boolean`, default `false`. Every path that does not compute the flag (prime-agent, `AcpRuntime.spawnAgent`, tests) gets the CLI block. This matches F-6: none of those paths injects the server.
- **D-3 The gate moves to a leaf module.** `harnessGetsOverdeckMcp` and `overdeckMcpEnabledFor` move unchanged from `agent-injection.ts` to new `src/lib/mcp/overdeck-mcp-gate.ts`; `agent-injection.ts` imports them for its own use and re-exports them (`export { harnessGetsOverdeckMcp, overdeckMcpEnabledFor } from './overdeck-mcp-gate.js';`) so existing imports and tests keep working. Why: F-2 — `context-layers/` must not import the token/registry graph. This is a move, not a twin.
- **D-4 `getAcpLauncherFields` becomes async.** It computes `await overdeckMcpEnabledFor(harness)` itself and passes it to `materializeAcpContextFile`. Its four callers add `await` on the same line (zero added lines, NFR-4), and `conversation-runtime.ts:614` changes `ReturnType<…>` to `Awaited<ReturnType<…>>`. Why not an extra parameter: `spawn.ts` has one spare line (F-9) and the decision would live at four call sites instead of one.
- **D-5 Cache key.** `materializeSharedManagedLaunchContext` writes `<harness>-<workspaceHash>-mcp.md` or `<harness>-<workspaceHash>-cli.md`. F-8 shows no reader depends on the old name. Old `<harness>-<hash>.md` files are left on disk (each is overwritten on no launch any more; they are a few KB). No cleanup code.
- **D-6 One block for every role.** Review, test and ship tokens see fewer tools (F-5). The MCP block says "A tool missing from your list is outside your role's scope." instead of per-role variants, which would multiply cache variants and break NFR-10's single-block rule.
- **D-7 Block placement.** The tools block is the last section of `renderManagedLaunchContext` (after the workspace layer). In `materializeMuseContext` it goes after the workspace layer and before the role file, so the role prompt stays last as today.
- **D-8 Corrections to the epic's verbatim MCP block** (each traced to a fact): line 2 adds "A tool missing from your list is outside your role's scope." (F-5); the wait line says "when it answers `running` or `pending` with `next`, call `next` again" instead of "when it answers `status: "running"`, call its `next` again" (F-4). Everything else is verbatim.
- **D-9 Docker workspaces get the CLI block** (epic D-13), even though the epic notes the container has no `pan`. That is the epic's decision; this item does not change it (H-2).
- **D-10 Blocks are built with `[...].join('\n')`**, not template literals, so the backticks in the text need no escaping.
