**Issue:** [PAN-4434](https://github.com/eltmon/overdeck/issues/4434) · **Epic:** [PAN-2350](https://github.com/eltmon/overdeck/issues/2350) (Overdeck Anywhere, Phase 0) · **Split from:** [PAN-2351](https://github.com/eltmon/overdeck/issues/2351) (its retired FR-5 / W4 heartbeat half)

All file/line anchors were verified 2026-10-01 against `feature/pan-4434` at `8a82dad552b` (= `origin/main`; PAN-2351 #4441 has already landed, so `WS_TERMINAL_SCOPE` is on main). Line numbers drift; the quoted code is the search key.

## Glossary

- **Control frame** — a WebSocket text message on `/ws/terminal` that starts with the NUL character `\u0000` followed by a JSON object, for example `\u0000{"type":"snapshot",...}`. Server → client only. The server writes them with `sendControl` (`src/dashboard/server/ws-terminal.ts:92-96`, `ws.send(\`\u0000${JSON.stringify(payload)}\`)`). Anything without the prefix is raw terminal output.
- **Client control message** — a client → server text message that is a bare JSON object (no NUL prefix), for example `{"type":"attach","cols":80,"rows":24}`. The server classifies it with `parseControlMessage` (`ws-terminal.ts:78-90`). Anything it does not recognize is terminal **input** and is written to the PTY / Herdr bridge.
- **Ping frame** — the control frame `\u0000{"type":"ping"}` (server → client).
- **Pong message** — the client control message `{"type":"pong"}` (client → server).
- **Heartbeat** — the server-side timer added by this issue: every `TERMINAL_HEARTBEAT_INTERVAL_MS` (20 000 ms) it checks for inbound traffic and sends a ping frame.
- **Missed interval** — one heartbeat tick at which the server has received no inbound message of any kind since the previous tick.
- **Heartbeat opt-in** — the query parameter `heartbeat=1` on the `/ws/terminal` URL. Only a connection that carries it gets a heartbeat. Named by `TERMINAL_HEARTBEAT_QUERY_PARAM = 'heartbeat'`.
- **Stale bundle** — a browser tab still running the dashboard JavaScript from before a deploy. `pan reload` closes terminals with 4503 and the tab reconnects with its old bundle; `StaleBuildChip.tsx` only prompts for a reload, it does not force one.
- **PTY** — the `@lydell/node-pty` process running `tmux attach-session` that backs a tmux terminal (`ws-terminal.ts:572`). On a Herdr host the equivalent sink is `HerdrTerminalProcess` (`ws-terminal.ts:181`).

## Problem

Cloudflare and similar reverse proxies close a WebSocket after about 100 s with no traffic in either direction. `/ws/rpc` already emits `system.heartbeat` every 15 s (`src/dashboard/server/ws-rpc.ts`, `Stream.tick('15 seconds')`) and `/events/stream` already sends `: keepalive` every 15 s (`src/dashboard/server/routes/events.ts`, `KEEPALIVE_INTERVAL_MS = 15_000`). `/ws/terminal` sends nothing when the terminal is idle, so an idle terminal behind such a proxy drops every ~100 s. The server also has no way to notice a half-open terminal socket whose client vanished without a close.

Two facts in the current code shape the design:

1. **Every client handler writes unknown messages to the PTY.** There are four post-connection handlers — `handlePreAttachMessage` (`ws-terminal.ts:376`), Herdr `handleMessage` (`:198`), `handleJoinMessage` (`:460`) and `handleLocalMessage` (`:633`) — and each ends in a write (`bridge.write(message)`, `existingHub.pty.write(message)`, `ptyProcess.write(message)`, or `pendingInput.push`). A `{"type":"pong"}` that is not filtered out would be typed into the agent's terminal.
2. **The current client writes unknown control frames into xterm.** In `XTerminal.tsx:704-746` a `\u0000` frame whose `type` is not `snapshot` or `size` falls through to `queueLiveData(dataStr)`. A stale bundle receiving an unconditional ping would paint `{"type":"ping"}` into the terminal every 20 s, and because it never answers it would be terminated and reconnected every 40–60 s.

## Decisions

- **D-1 App-level data frame, not `ws.ping()`.** A text frame counts as traffic at every proxy; intermediaries handle protocol-level ping frames inconsistently. (From the issue.)
- **D-2 Opt-in by query parameter.** The server starts a heartbeat only when the upgrade URL carries `heartbeat=1`. A connection without it behaves exactly as today: no pings, never terminated by the heartbeat. Reason: stale bundles (Problem fact 2) would otherwise render ping text and reconnect in a loop until the operator reloads. A query parameter is used, not a field on the `attach` message, because the server reads `attach` only after `resolveTerminalAttachTarget`, which can wait up to `RESPAWN_WAIT_MS` (95 s, `ws-terminal.ts:36`) — longer than a proxy idle timeout. The heartbeat must run during that wait. Programmatic `operate`-token clients opt in the same way.
- **D-3 One filter at the single entry point.** Ping and pong client messages are dropped in the one `ws.on('message', …)` listener (`ws-terminal.ts:310-317`) before it dispatches to `messageHandler` or the pre-attach buffer. That covers all four handlers at once and keeps pongs out of the `PRE_ATTACH_MAX_MESSAGES` (32) / `PRE_ATTACH_MAX_BYTES` budget. `parseControlMessage` and the `ClientControlMessage` union are widened to recognize `ping` and `pong` so the types stay honest. A client `ping` is dropped, not answered.
- **D-4 The heartbeat module owns its activity listener and never imports `ws-terminal.ts`.** `ws-terminal-heartbeat.ts` registers its own `ws.on('message')` listener to record inbound traffic (any message, including pongs, counts) and receives the ping sender as a callback. `ws-terminal.ts` imports the heartbeat module, so the reverse import would be a cycle (`npm run lint:circular`).
- **D-5 Tick algorithm (normative).** Starting at connection, every 20 000 ms:
  1. If at least one inbound message arrived since the previous tick (or since start, for the first tick), set `missed = 0`; otherwise `missed += 1`.
  2. Clear the "arrived" flag.
  3. If `missed >= 2` (`TERMINAL_HEARTBEAT_MAX_MISSED`), clear the interval, log one `console.warn`, call `ws.terminate()`, and stop.
  4. Otherwise send the ping frame.
  The interval is cleared on `close` and on `error` (`ws.once`, the same pattern as `armReadyTimeout`, `ws-terminal.ts:106-107`). A responsive client therefore sees an outbound ping exactly every 20 000 ms; a dead client is terminated 40–60 s after its last message.
- **D-6 The heartbeat starts in `wss.on('connection')`, not in the upgrade block.** It is started right after the `[ws-terminal] WebSocket connected for session:` log line (`ws-terminal.ts:290`), after the session-name and `reauth-` checks, so a socket closed by those checks never gets a timer. The upgrade block (`ws-terminal.ts:244-253`) is untouched.
- **D-7 Client drops unrecognized-but-parsed control frames.** After the `snapshot`, `size` and new `ping` branches, a `\u0000` frame that parsed as JSON returns without being written to xterm. A `\u0000` message whose JSON is malformed still falls through to `queueLiveData` exactly as today, so a live PTY chunk that happens to begin with NUL is never lost.
- **D-8 Extract before adding.** `XTerminal.tsx` is 1075 lines; its `scripts/file-size-allowlist.txt` cap is 1075 (the last of four rows wins, `# PAN-1166`) and the god-file ceiling is 1000 (`scripts/lint-file-size.sh`, `CEILING=1000`), so it cannot grow. The control-frame types and the `JSON.parse` block move to `src/dashboard/frontend/src/components/terminal/terminalControlFrames.ts` first, in their own commit. The issue's rule applies to the end state: XTerminal.tsx's net line change across the whole PR is ≤ 0. `ws-terminal.ts` is 689 lines, under the ceiling and not allowlisted, so it may grow.
- **D-9 No shared contract package.** `packages/contracts` defines no `/ws/terminal` frame types today (only a session-name doc comment in `companion-terminal.ts:49`). The literals below are defined once in this PRD; the server and client items each define their own constants, so they need no dependency edge.

## Requirements

- **FR-1** A `/ws/terminal` connection whose URL carries `heartbeat=1` receives the ping frame every 20 000 ms from connection onward, including while the server waits for the attach handshake or a respawn.
- **FR-2** Any inbound message resets the missed-interval counter; after 2 consecutive missed intervals the server calls `ws.terminate()`. The heartbeat timer is cleared on `close` and `error`.
- **FR-3** A client message `{"type":"pong"}` or `{"type":"ping"}` never reaches the PTY, the Herdr bridge, `hub.pendingInput`, or the pre-attach buffer, on any of the four handler paths.
- **FR-4** A connection without `heartbeat=1` receives no ping frames and is never terminated by the heartbeat (no-loss for existing and stale clients).
- **FR-5** `XTerminal.tsx` connects with `heartbeat=1` and answers each ping frame with exactly one `{"type":"pong"}`; a ping frame is never written to xterm.
- **FR-6** `XTerminal.tsx` writes no parsed `\u0000` control frame of an unrecognized `type` into xterm; malformed `\u0000` messages keep today's pass-through behavior.
- **FR-7** The control-frame types and parse live in `components/terminal/terminalControlFrames.ts`; `XTerminal.tsx` has a net line change ≤ 0 across the PR.
- **FR-8** `docs/DASHBOARD-ARCHITECTURE.md`, `docs/DASHBOARD-AUTH.md` and `configuration/remote-access.mdx` describe the terminal heartbeat as shipped.
- **NFR-1** Every timer test uses `vi.useFakeTimers()` and `vi.advanceTimersByTime()`; no real waits (repo rule `fake-timers-for-retry-tests`).
- **NFR-2** `ws-terminal-heartbeat.ts` does not import `ws-terminal.ts`; `npm run lint:circular` stays green.
- **NFR-3** File-size ratchet: no allowlist cap is raised; `bash scripts/lint-file-size.sh` passes.
- **NFR-4** No `execSync` or other blocking call is added to server-reachable code (repo rule `no-execsync-server`); the dashboard still runs as the Node 22 dist.
- **NFR-5** The PR description records the manual check: a terminal left idle 10 minutes behind a proxy with a 100 s idle timeout stays connected. The tab stays **visible** for the whole check: browsers suspend hidden tabs, a suspended tab stops answering pings, and the server terminating it after 40–60 s is intended behavior, not a failure.

### W1 — Heartbeat module (`heartbeat-module`) — FR-1, FR-2, NFR-1, NFR-2

```ts
/**
 * App-level heartbeat for /ws/terminal (PAN-4434). Proxies such as Cloudflare
 * close a WebSocket after ~100 s without traffic, so an opted-in connection
 * (`?heartbeat=1`) gets a `\u0000{"type":"ping"}` control frame every 20 s,
 * and a client that sends nothing for two consecutive intervals is terminated.
 * A data frame is used instead of ws.ping() because every proxy counts it as
 * traffic. This module never imports ws-terminal.ts; the caller passes the
 * ping sender.
 */
import type { WebSocket } from 'ws';

export const TERMINAL_HEARTBEAT_INTERVAL_MS = 20_000;
export const TERMINAL_HEARTBEAT_MAX_MISSED = 2;
export const TERMINAL_HEARTBEAT_QUERY_PARAM = 'heartbeat';

/** True when the upgrade URL opted in with `heartbeat=1`. */
export function wantsTerminalHeartbeat(url: URL): boolean {
  return url.searchParams.get(TERMINAL_HEARTBEAT_QUERY_PARAM) === '1';
}

/** Start the heartbeat for one socket; returns a stop function. */
export function startTerminalHeartbeat(ws: WebSocket, sendPing: () => void): () => void {
  let receivedSinceTick = false;
  let missed = 0;
  ws.on('message', () => {
    receivedSinceTick = true;
  });
  const timer = setInterval(() => {
    missed = receivedSinceTick ? 0 : missed + 1;
    receivedSinceTick = false;
    if (missed >= TERMINAL_HEARTBEAT_MAX_MISSED) {
      clearInterval(timer);
      console.warn(`[ws-terminal] No client traffic for ${TERMINAL_HEARTBEAT_MAX_MISSED} heartbeat intervals; terminating`);
      ws.terminate();
      return;
    }
    sendPing();
  }, TERMINAL_HEARTBEAT_INTERVAL_MS);
  const stop = () => clearInterval(timer);
  ws.once('close', stop);
  ws.once('error', stop);
  return stop;
}
```
