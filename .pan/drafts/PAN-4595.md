# PAN-4595: `pan show --health` calls working Herdr agents stuck

**Issue:** [PAN-4595](https://github.com/eltmon/overdeck/issues/4595)
**Status:** planned (auto planning, 2026-10-24)

## Glossary

- **Herdr** — the default terminal backend. Agents run in Herdr panes, reached over an async socket. Herdr has no tmux `#{window_activity}` value.
- **Runtime mirror** — the in-process snapshot read by `getAgentRuntimeStateSync` (`src/lib/agents/runtime-state.ts`, line 99). It is populated only inside the dashboard server. In a fresh CLI process it is empty, so it returns `null` (see the comment at `runtime-state.ts` lines 100-102: "empty in fresh CLI processes").
- **Transcript heartbeat** — the newest activity time a harness runtime can see for an agent. For Claude Code it is `ClaudeCodeRuntimeSync.getHeartbeat` (`src/lib/runtimes/claude-code.ts`, `getHeartbeat(agentId: string): Heartbeat | null`, line 247): an active heartbeat file `~/.overdeck/heartbeats/<agentId>.json` younger than 5 minutes, else the mtime of the transcript JSONL whose absolute path the agent's `sessions.json` records (`getSessionPath`, line 133).
- **Heartbeat lookup** — the function `liveness.ts` calls to read the transcript heartbeat. `liveness.ts` cannot import the runtime registry (that closes an import cycle), so the registry registers the lookup with `registerLivenessHeartbeatLookup` when its module loads.
- **Runtime registry** — `src/lib/runtimes/index.ts`. Its last lines (157-166) register the heartbeat lookup and the runtime liveness probe as module-load side effects.
- **Effective last activity** — `getAgentEffectiveLastActivityMs` (`src/lib/agents/liveness.ts`, line 296): the max of the runtime mirror timestamp, tmux `window_activity`, and the transcript heartbeat.
- **CLI health path** — `pan show <id> --health` → `healthCommand('ping', …)` (`src/cli/commands/show.ts`, line 235) → `pingAgent` (`src/lib/health.ts`) → `pingAgentBody` (line ~110), which classifies `stuck` when the last activity is older than 30 minutes.

## Problem

`pan show <id> --health` reports actively working Herdr agents as `STUCK` ("No activity for 31 minutes"). On 2026-10-24 08:11Z it called `agent-pan-4582` and `agent-pan-4583` stuck while their Claude transcripts had been written within the last minute. The Flywheel uses this verdict to decide whether to `pan resume` or `pan tell` an agent, so a false `stuck` invites a recovery action on a healthy agent.

### Verified root cause

1. `pingAgentBody` (`src/lib/health.ts`, line 130) reads `getAgentEffectiveLastActivityMs(agentId)`.
2. In a CLI process all three sources of that resolver are empty for a Herdr agent:
   - the runtime mirror is empty (fresh CLI process);
   - tmux `window_activity` does not exist (Herdr pane);
   - `getTranscriptHeartbeatMs` (`liveness.ts`, line 72) returns `null` because `heartbeatLookup` is unset: `if (!heartbeatLookup) return null;`.
3. The only registrar is `src/lib/runtimes/index.ts` line 162:
   `registerLivenessHeartbeatLookup((agentId) => getRuntimeForAgent(agentId)?.getHeartbeat(agentId) ?? null);`
4. No module on the CLI health path imports `runtimes/index.ts`. Verified two ways during planning:
   - `madge` on `src/cli/commands/show.ts` and `src/cli/commands/worker.ts`: neither graph contains `src/lib/runtimes/index.ts`.
   - The deployed build (`~/.overdeck/deployments/dashboard/.pan-reload-generation-a/dist/`): a Node `indexOf` scan of every top-level CLI chunk finds no `registerRuntimeLivenessProbe(async` and no `getHeartbeat(` at all. The registration exists only in `dist/dashboard/runtimes-*.js` (the server bundle).
5. So `pingAgentBody` falls back to `state.json` `lastActivity`, which is the spawn time. Every Herdr agent older than 30 minutes reads `stuck`.

The default `pan show <id>` view on Herdr has the same blind spot: its health line calls `getAgentEffectiveLastActivityMs` directly (`show.ts`, line 342) and prints a stale "last activity".

Live data confirms the fix will find a signal: `~/.overdeck/agents/agent-pan-4582/sessions.json` ends with entries carrying `"path":"/home/eltmon/.claude/projects/-home-eltmon-Projects-overdeck-workspaces-feature-pan-4582/4c67f591-….jsonl"`, which `ClaudeCodeRuntimeSync.getSessionPath` reads first.

## Requirements

- **FR-1** — When `src/lib/health.ts` is loaded in any process, the liveness heartbeat lookup is registered, so `getAgentEffectiveLastActivityMs` includes the transcript heartbeat.
- **FR-2** — `pingAgent` classifies a live Herdr-hosted Claude Code agent as `healthy`, with `consecutiveFailures` reset to `0`, when its transcript was written within the last 15 minutes, even when the runtime mirror is empty and `state.json` `lastActivity` is hours old.
- **FR-3** — `pingAgent` still classifies a live agent `stuck` when every activity signal, including the transcript mtime, is older than 30 minutes.
- **FR-4** — The default `pan show <id>` view on a Herdr host prints a "last activity" derived from the transcript heartbeat (it imports `health.ts`, so FR-1 covers it).
- **FR-5** — The comments that name the heartbeat registrar (`liveness.ts` lines 52-63, `runtimes/index.ts` lines 157-159) and `docs/TERMINAL-BACKENDS.md` state that `src/lib/health.ts` loads the runtime registry so the CLI health path sees the transcript heartbeat.
- **NFR-1** — No new import cycle: `bash scripts/lint-circular-deps.sh` passes with no baseline change.
- **NFR-2** — The fix does not load the runtime registry for unrelated `pan` verbs. The import goes in `src/lib/health.ts`, not in `src/cli/index.ts`.
- **NFR-3** — The new test makes no real tmux or Herdr call and writes nothing under the real `~/.overdeck`.

## Decisions

- **D1: Import location is `src/lib/health.ts`.** `show.ts` (line 18) and `src/cli/commands/health.ts` (line 6) both import `pingAgent` from it, so one line fixes `pan show`, `pan show --health`, and `pan show --health ping|check`. The other importers of `lib/health.ts` (`src/lib/cloister/service.ts`, `service-crash.ts`, `service-health.ts`, `service-status.ts`) already import `runtimes/index.ts`, so nothing changes for them. Importing in `src/cli/index.ts` would load the registry for every `pan` invocation (NFR-2).
- **D2: Use a bare side-effect import** `import './runtimes/index.js';`. Precedent: `src/lib/terminal-backends/launch.ts` line 31, `import './tmux.js';` ("Importing it registers both adapters"). `package.json` has no `sideEffects` field, so the bundler keeps the import.
- **D3: No cycle.** A new edge `health.ts → runtimes/index.ts` closes a cycle only if `runtimes/index.ts` reaches `health.ts`. Planning ran `madge` from `src/lib/runtimes/index.ts`: 391 reachable modules, and `src/lib/health.ts` is not among them (only `provider-health.ts`, `workspace/stack-health.ts`, `memory/health.ts` match "health"). The show-command graph (398 modules) gains only 7: `src/lib/prime-agent/host-client.ts`, `src/lib/runtimes/{acp,claude-code,index,muse,pi,prime-agent}.ts`. A scan of those for top-level calls, timers, or `process.on` found only `const execAsync = promisify(exec)` in `acp.ts`.
- **D4: The proving test is a new file**, `tests/lib/health-herdr-heartbeat.test.ts`. It cannot extend `tests/lib/health-runtime-state.test.ts`: that file mocks `liveness.js` wholesale (so it cannot see registration) and mocks `agents.js` with only five exports and no `importOriginal`. The existing file stays unchanged unless the new import breaks it (see WI-1 checkpoint).
- **D5: Out of scope — other CLI idle consumers.** `pan worker wait` / `pan lane wait` (`src/lib/agents/worker/wait.ts`, via `idleAgeMs`) have the same unregistered lookup, but `worker.ts` does not import `health.ts`, and a missing signal there fails toward "no idle age", not a false recovery verdict. Recorded as a NonGoal and hazard; a follow-up issue may be filed.
- **D6: Only the Claude Code heartbeat is exercised by the new test.** The codex, acp, kimi-code, ohmypi, muse and prime-agent `getHeartbeat` implementations are unchanged.
