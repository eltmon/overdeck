# PAN-4940 — Agent MCP and bots (W-MEM1): memory add and search

**Status:** planned · **Revision:** 1 (2026-11-04) · **Author:** Claude Opus 5.5 (planning agent, `pan plan --auto`)
**Issue:** [PAN-4940](https://github.com/eltmon/overdeck/issues/4940) · **Epic:** [PAN-4927](https://github.com/eltmon/overdeck/issues/4927), PRD `.pan/drafts/pan-4927.md`, work item **W-MEM1** · **Requirement:** epic FR-6 · **Depends on:** W-SELF1 ([PAN-4936](https://github.com/eltmon/overdeck/issues/4936), merged on `main`)

**What this delivers.** Two agent-only MCP tools, `memory_add` and `memory_search`, over two new self routes. Each route runs the `pan memory` CLI as a self job for the calling agent, in that agent's checkout. The epic's W-MEM1 steps are followed, with six corrections (C-1 to C-6) that the current code forces. The largest one: `pan memory search --json` never returns curated facts, so this issue adds a `--facts` flag to the CLI, or AC-11 cannot pass.

---

## Glossary

- **Curated fact (fact):** one short markdown file with YAML frontmatter, `<store>/<id>.md`, written by `pan memory add` (`src/cli/commands/memory-facts.ts`). Types are `feedback`, `project`, `reference`, `user` (`MEMORY_FACT_TYPES`, `src/lib/memory/facts/store.ts:17`).
- **Fact store:** a directory of facts. Three exist: the **project store** `<checkout>/.overdeck/memory/` (`projectMemoryDir`, `store.ts:65`), the **operator store** `~/.overdeck/context/memory/` (`userMemoryDir`, `store.ts:69`, flag `--user`), and the **machine store** `~/.overdeck/context/machine-memory/` (`machineMemoryDir`, `store.ts:74`, flag `--machine`).
- **Cwd checkout / primary checkout:** a work agent runs in a git worktree, `<project>/workspaces/feature-<issue>/` (the cwd checkout). The project's main clone is the primary checkout (`ProjectConfig.path`).
- **Observation:** an automatically extracted memory record, searched through the FTS index by `searchMemory` (`src/lib/memory/cli.ts:146`). Observations are not facts.
- **Self route:** a route under `/api/self/` that acts for the calling agent. It accepts only an agent token and finds the agent from the token (`src/dashboard/server/self-caller.ts`, epic D-10).
- **Self job:** a `pan` CLI command a self route runs asynchronously with `execFile`, in the caller's cwd, with the caller's identity variables (`src/dashboard/server/services/self-jobs.ts`, epic D-11). Its stdout and stderr keep only the last 16 KiB (`SELF_JOB_OUTPUT_TAIL_BYTES`, `self-jobs.ts:28`).
- **Job answer:** `selfJobAnswer(state)` (`self-jobs.ts:98`): `{ status: 'done', exitCode, stdout, stderr, … }` or `{ status: 'running', jobId, verb, startedAt, next: { tool: 'wait_job', arguments: { jobId } } }`.
- **Argv piece (`SelfJobArg`):** the only way caller text reaches a job's argv (`src/dashboard/server/services/self-job-argv.ts`): `{ ref }` (an id matching `SELF_JOB_REF_PATTERN`), `{ flag, value }` (one `--flag=value` token), `{ switch }` (a bare `--switch`), `{ rest }` (positionals after `--`, last only).
- **Agent-only tool:** an `OverdeckTool` with `audience: 'agent'` (`src/lib/mcp/tool.ts`); `tools/list` shows it only to agent tokens (epic D-14).
- **Fact envelope:** the new JSON output of `pan memory search --facts --json`: one line, `{ "facts": FactMatch[], "observations": ObservationMatch[] }` (D-3).

## Corrections to the epic's W-MEM1 steps

- **C-1 Search must return facts.** The epic runs `memory search --limit=<n> --json -- <query>`, which returns observations only (Fact 5), so `memory_search` could never return a fact `memory_add` wrote (AC-11). Fix: a new `--facts` CLI flag (WI-1, D-2, D-3).
- **C-2 Search must read the store `add` wrote.** Even with facts, a read-mode search reads the primary checkout (Fact 6). Under `--facts`, project facts come from the cwd checkout unless `--project` is given (D-4). For the same reason, the issue's AC-11 phrase "`pan memory list` shows" it is satisfied as `pan memory list --here` run in the agent's cwd. Plain `pan memory list` shows the fact when the cwd is the primary checkout (a conversation started there) or after the agent's branch merges.
- **C-3 Observations must be scoped to the caller's project.** Without a scope flag, observations come from project `overdeck` (Fact 7). Under `--facts`, the cwd's project is the default (D-5).
- **C-4 `type: 'user'` needs a store.** The epic's body allows `type: 'user'` but passes no store flag, so the job always exits 1 (Fact 8). Fix: an optional `store` field (D-6).
- **C-5 The id pattern is the store's.** The epic restates `^[a-z0-9][a-z0-9-]{0,63}$`; the route imports `MEMORY_FACT_ID` (`{0,79}`, Fact 10) so there is one authority.
- **C-6 Files the epic omits.** The route layer must be registered in `src/dashboard/server/server.ts`; the tool tests in Fact 14 and the generated manifest and skill in Fact 13 change too.

## Requirements

### Functional

- **FR-1 Add.** `memory_add` writes one curated fact for the calling agent, through `pan memory add` run in the agent's cwd, to the project store (default), the operator store or the machine store.
- **FR-2 Search.** `memory_search` returns, for the calling agent, matching curated facts from the store `pan memory add` writes from its cwd, the operator store and the machine store, plus matching observations from the agent's project.
- **FR-3 Round trip (issue AC-11).** A fact `memory_add` wrote is listed by `pan memory list --here` run in the caller's cwd, and `memory_search` returns it.
- **FR-4 CLI envelope.** `pan memory search <query> --facts --json` prints one line of JSON `{ facts, observations }`. Plain `--json` output is unchanged.
- **FR-5 Agent identity only.** Both routes take the agent and its cwd from the agent token, never from the body, and refuse any other credential.
- **FR-6 Documentation.** The two tools, the two routes and the `--facts` flag are documented in the change.

### Non-functional

- **NFR-1 One door.** Both routes run the `pan` CLI as a self job (epic D-11); no route reads or writes fact files itself.
- **NFR-2 Argv safety.** Caller text reaches argv only through `SelfJobArg` pieces: the id as `{ ref }`, every other string as `{ flag, value }` or after `--` (`{ rest }`).
- **NFR-3 Bounded output.** The envelope is single-line JSON with no fact bodies and short observations, so a default search (limit 10) stays under the 16 KiB job tail.
- **NFR-4 Bounded waits.** Each route waits at most `WAIT_CHUNK_MS` (50 s) and otherwise answers `running` with `next: wait_job`.
- **NFR-5 Repo rules (restated).** No `execSync`/`spawnSync`/`execFileSync` in server-reachable code and no new `*Sync` function (rules `no-execsync-server`, `prefer-async`); tests of waits use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()` (rule `fake-timers-for-retry-tests`); new modules stay under 600 lines; `npm run lint:effect-facades` must not rise; every new HTTP route lives in a top-level `src/dashboard/server/routes/` file with a `route-scopes.ts` row and a `no-loss-matrix.ts` row; commit per item with an `Item: <item-id>` trailer; never run the full `npm test` on the host.

## Decisions

- **D-1 Start, then wait, then answer 200.** Each route starts its job, waits up to `WAIT_CHUNK_MS`, and answers **200** with `selfJobAnswer`: `done` with the result, or `running` with `next`. This matches W-SELF2 (`PAN-4937.md` D-3), so all job routes answer alike. A finished job with a non-zero `exitCode` is still `status: 'done'` and the tool passes it through as a normal result (W-SELF2 D-4); the tool descriptions say "a non-zero exitCode means pan refused; stderr says why".
- **D-2 One new CLI flag, `--facts`, on `pan memory search`.** It requires `--json` (`--facts` alone exits 1 with `--facts needs --json`) and switches the JSON output to the envelope. Why a flag and not a new default: the plain `--json` array has consumers (Fact 5). Why not read fact files in the route: the CLI stays the one door (NFR-1) and the server stays free of sync file reads.
- **D-3 Envelope shape.** One line (`JSON.stringify(value)`, no indentation):
  - `facts`: project-store matches, then operator, then machine; at most 5 per store (the existing `MATCHING_FACTS_LIMIT`, `memory-facts.ts:338`); active facts only; each `{ scope, type, id, title, description, tags, file }`. No `body`: the agent reads `file` when it needs the text. Why: bodies are unbounded and the job keeps only 16 KiB.
  - `observations`: each `{ score, id, timestamp, projectId, workspaceId, issueId, actionStatus, summary, files }`. No `narrative`, `tokens`, `sessionId`, `runId`, offsets or `model` (Fact 11).
- **D-4 Which project store `--facts` reads.** With `--project <key>`: that project's primary checkout (as text-mode search does). Without it: the cwd checkout (`resolveFactTarget({ here: true }, 'read')`), which is the store `pan memory add` writes from the same cwd. Outside a registered project: no project facts, operator and machine facts still returned.
- **D-5 Which observations `--facts` searches.** When none of `--project`, `--workspace`, `--issue`, `--global` or `--target` is given, `--facts` sets `project` to `await resolveProjectKeyForCwdAsync(process.cwd())`, or sets `global: true` when that is `null`. With any scope flag, the flags apply unchanged. Plain search (no `--facts`) keeps its `overdeck` default; fixing that default for humans is out of scope (Non-goals).
- **D-6 `store` field on `memory_add`.** Optional `store: 'project' | 'user' | 'machine'`. Default: `'user'` when `type` is `'user'`, else `'project'`. `type: 'user'` with `store: 'project'` is **400** `bad-request`. `'user'` adds the `--user` switch and `'machine'` adds `--machine`. Why: it is the same door the `project-memory` rule names (`pan memory add --user` / `--machine`), and it makes `type: 'user'` work (C-4).
- **D-7 Body limits on `POST /api/self/memory/facts`.** `id` matches `MEMORY_FACT_ID`; `type` is in `MEMORY_FACT_TYPES`; `description` is a string, trimmed to 1-200 characters (`MEMORY_FACT_DESCRIPTION_MAX`), with no `\n` or `\r`; `title` (optional) trimmed 1-200 characters, no line breaks; `body` (optional) at most 16,384 characters (`MEMORY_FACT_BODY_MAX`, keeps one argv element under Linux's 128 KiB per-argument limit); `tags` (optional) an array of at most 20 strings, each matching `^[A-Za-z0-9][A-Za-z0-9._-]{0,39}$` (no commas, because the CLI splits `--tags` on commas). The trimmed `description` and `title` are what the job receives.
- **D-8 Body limits on `POST /api/self/memory/search`.** `query` is a string trimmed to 1-500 characters; `limit` (optional) is an integer 1-20, default 10. Why 20, not the epic's 50: observations above about 20 can pass the 16 KiB tail (NFR-3). The trimmed query is passed after `--`.
- **D-9 Status codes and order.** Caller (403 `not-an-agent-token`, 404 `agent-gone`, from `selfCallerFromCredential`), body parse (400 `bad-body` for anything but a JSON object), field validation (400 `bad-request`, `error` names the field), job start (400 `bad-job-arg` from `SelfJobArgError`, 429 `too-many-jobs`), wait (200 job answer; a `null` from `wait` is 404 `unknown-job`). Error bodies are `{ error, code }`. Same order and codes as W-SELF2 D-2.
- **D-10 Scopes.** `POST /api/self/memory/facts` needs `tell`; `POST /api/self/memory/search` needs `read:state` (epic W-MEM1). Both tools are `audience: 'agent'` with the scope of their route.
- **D-11 No dependency on W-SELF2.** `routes/self-memory.ts` holds its own module-private start-and-wait helper (`startMemoryJob`), with the behavior of W-SELF2's `startSelfJobAnswer` (D-1, D-9). Whichever of PAN-4937 and PAN-4940 merges second may replace its copy with an import; neither issue waits for the other.
- **D-12 No CSRF check.** Only a header-borne agent token passes `selfCallerFromCredential`, so the routes skip the CSRF helper, as `self-requests.ts` does (its header, D-5).
- **D-13 Commit instruction lives in the tool description.** `add --json` drops the CLI's commit hint (Fact 9), so `memory_add`'s description tells the agent to commit `.overdeck/memory/<id>.md` with its work for a project fact.

## Architecture

```
agent ── memory_add {id,type,description,…} ──► POST /api/self/memory/facts   (scope tell)
                                                 │ selfCallerFromCredential → caller {agentId, cwd}
                                                 │ validate body → SelfJobArg[]
                                                 └ selfJobs.start('memory-add') → wait ≤ 50 s → 200 selfJobAnswer
                                                      job: pan memory add <id> --type=… --description=… [--user|--machine] --json
                                                           (cwd = caller checkout → writes <checkout>/.overdeck/memory/<id>.md)

agent ── memory_search {query,limit} ─────────► POST /api/self/memory/search  (scope read:state)
                                                 └ selfJobs.start('memory-search') → wait ≤ 50 s → 200 selfJobAnswer
                                                      job: pan memory search --limit=<n> --facts --json -- <query>
                                                           → {"facts":[…cwd checkout, operator, machine…],"observations":[…cwd project…]}
```
