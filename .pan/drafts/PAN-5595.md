# PAN-5595: Release workflow — handle npm staged versions in the publish steps

**Issue:** [PAN-5595](https://github.com/eltmon/overdeck/issues/5595)
**Status:** planned (auto planning, 2026-11-22)

## Glossary

- **Release workflow:** `.github/workflows/release.yml`. It runs on a pushed `vX.Y.Z` tag. Its `npm` job (line 309, `needs: [classify, pack, bare-host-macos]`) publishes three packages: `@overdeck/core`, `@overdeck/contracts` and `@overdeck/desktop`.
- **Publish step:** one of the three `run:` steps in the `npm` job: "Publish CLI to npm" (line 372), "Publish contracts to npm" (line 388) and "Publish desktop to npm" (line 403).
- **dist-tag:** the npm channel a publish goes to. The `classify` job outputs it as `needs.classify.outputs.npm_tag`. The value is `latest` for stable tags and `canary` for prerelease tags (lines 32 and 36).
- **Visible version:** `npm view <name>@<version> version` prints `<version>` on stdout. Only a visible version can be installed.
- **Staged version:** a version that npm accepted but holds back. A maintainer must approve it before it becomes public. While it is staged, `npm view` cannot see it and the tarball URL returns 404. A second publish of the same version fails with `E409 … Cannot publish over previously staged version "<version>"`. The npm CLI's `npm stage` commands manage staged versions. They first appear in **npm 11.15.0**. Tarballs checked during planning: 11.5.1, 11.10.0 to 11.14.1 have no `lib/commands/stage/`, and 11.15.0, 11.18.0, 11.20.0 and 11.21.3 have it.
- **Stage id:** the UUID that `npm stage list <name>` prints for each staged version. `npm stage approve <stage-id>` takes it.
- **Poll:** repeat `npm view <name>@<version> version` a fixed number of times, with a fixed pause between attempts, until it prints the version.
- **Trusted Publishing (OIDC):** CI authenticates to npm with the GitHub OIDC token, with no `NODE_AUTH_TOKEN`. The npm docs for `npm stage` (npm 11.21.3, `docs/content/commands/npm-stage.md`, "Trust Relationship Permissions") say that short-lived trust tokens "cannot run `npm stage` subcommands". So CI cannot list or approve staged versions. Only a maintainer can, on their own machine, with 2FA.

## Problem

npm accepted `@overdeck/core@0.90.0` in release run 44976899182 (2026-11-22 03:24 UTC) but did not make it visible. The job printed `+ @overdeck/core@0.90.0` and passed. `@overdeck/contracts` and `@overdeck/desktop` went live, but core stayed staged, so new users could not install the release. A rerun of the `npm` job failed with `E409 … Cannot publish over previously staged version "0.90.0"`.

Root cause: each publish step decides "already on npm" with `npm view "${PKG_NAME}@${PKG_VERSION}" version` (lines 378, 393, 408) and checks nothing after it publishes. That causes two failures:

1. After `npm publish` succeeds, the step exits 0 without checking visibility. The run goes green while core cannot be installed, and nothing tells the operator.
2. On a rerun, `npm view` still cannot see the staged version, so the step publishes again. npm answers E409, and the step fails with an error it does not explain.

Current code, the core step, lines 372-386 (contracts and desktop are the same except for the name/version lookup and `cd`):

```yaml
      - name: Publish CLI to npm
        run: |
          TGZ=$(ls "$RUNNER_TEMP"/release/*.tgz)
          read -r PKG_NAME PKG_VERSION <<EOF
          $(tar -xOzf "$TGZ" package/package.json | node -e 'const p=JSON.parse(require("fs").readFileSync(0));console.log(p.name+" "+p.version)')
          EOF
          if npm view "${PKG_NAME}@${PKG_VERSION}" version >/dev/null 2>&1; then
            echo "${PKG_NAME}@${PKG_VERSION} already on npm — skipping (retry-safe)."
            exit 0
          fi
          if [ "${{ needs.classify.outputs.npm_tag }}" = "latest" ]; then
            npm publish "$TGZ" --ignore-scripts --provenance --access public
          else
            npm publish "$TGZ" --ignore-scripts --provenance --access public --tag "${{ needs.classify.outputs.npm_tag }}"
          fi
```

## Requirements

### Functional

- **FR-1** One script, `scripts/npm-publish-retry-safe.sh`, does the whole publish for one package. All three publish steps call it, and no publish step contains inline `npm view` or `npm publish` logic.
- **FR-2** If the version is already visible before the publish, the script prints a skip message, does not call `npm publish`, and exits 0. This keeps the current retry-safe behavior and is the rerun path after a maintainer approves.
- **FR-3** After a successful `npm publish`, the script polls for visibility. It makes up to 40 checks, 30 s apart (20 minutes). It exits 0 as soon as the version is visible.
- **FR-4** If `npm publish` exits non-zero and its output contains `previously staged version` (case-insensitive), the script treats the version as staged. It prints that it is skipping the publish and goes straight to the FR-3 poll. It never publishes a second time.
- **FR-5** If the poll ends without the version becoming visible, the script exits 3. It prints a GitHub `::error::` annotation and the approval instructions in "Timeout message" below. The message never suggests publishing the same version again.
- **FR-6** Any other `npm publish` failure exits with npm's own non-zero exit status and prints npm's output. The script does not poll in this case.
- **FR-7** The script passes exactly `--ignore-scripts --provenance --access public --tag <dist-tag>` to `npm publish`. The `--ignore-scripts` guarantee from PAN-5176 stays, and the existing test now checks it through the stub's recorded argv.
- **FR-8** `docs/RELEASING.md` and `sync-sources/skills/pan-release/SKILL.md` describe the staged state, what the job does about it, the approval commands, and how to recover.

### Non-functional

- **NFR-1** The tests for the script spend no real wall-clock time waiting. The poll is a counted loop whose attempt count and interval come from environment variables, and the tests set the interval to `0`. The script never uses a `date`/`$SECONDS` deadline. (Repo rule: delay-based tests must not rely on real delays; tests with real waits go in `*.slow.test.ts`. This design needs neither.)
- **NFR-2** The script decides visibility by comparing `npm view` **stdout** with the version string, never by exit status. A missing version's exit status has varied across npm releases.
- **NFR-3** The `npm view` calls pass `--prefer-online`, so npm's local packument cache (registry `max-age=300`) cannot hide a version that has just become visible.
- **NFR-4** No GitHub expression (`${{ … }}`) is interpolated inside the script's shell text. The workflow passes the dist-tag through a step `env:` variable.

## Decisions

- **D-1 Script interface (fixed):**
  ```
  scripts/npm-publish-retry-safe.sh --tag <dist-tag> <package>
  ```
  `<package>` is either a `.tgz` file (tarball mode, used by core) or a directory that contains `package.json` (directory mode, used by contracts and desktop). Anything else, a missing `--tag`, or an unknown flag prints `usage:` to stderr and exits 2.
  - Tarball mode reads name and version with `tar -xOzf <tgz> package/package.json` piped to `node`, then runs `npm publish <tgz> <flags>` from the current directory. This is the same as today's core step.
  - Directory mode reads name and version from `<dir>/package.json` with `node`, passing the path as an argument rather than splicing it into JS source. It then runs `npm publish <flags>` inside `<dir>` with `cd`, as today's contracts and desktop steps do.
- **D-2 Always pass `--tag`.** Today's steps omit `--tag` when the dist-tag is `latest`. `npm publish --tag latest` does the same thing, so the script passes `--tag "$tag"` every time. One code path covers both channels.
- **D-3 Poll tuning env vars (names fixed):** `NPM_VISIBILITY_POLL_ATTEMPTS` (default `40`) and `NPM_VISIBILITY_POLL_INTERVAL_SECONDS` (default `30`). The loop runs `npm view` once per attempt and sleeps `interval` between attempts, not after the last one.
- **D-4 Exit codes (fixed):** `0` = visible (published now, published earlier, or staged and then approved during the poll). `2` = usage error. `3` = not visible after the poll. Any other non-zero value = npm's publish exit status (FR-6).
- **D-5 CI never runs `npm stage`.** OIDC trust tokens cannot run `npm stage` subcommands (see Glossary). So after a clean publish followed by a timeout, the message can only say the version is *most likely* staged. After an E409 it is certain. The two messages differ only in their first line.
- **D-6 No special case for E403 "cannot publish over the previously published versions".** The pre-publish visibility check already covers a version that is published and visible.
- **D-7 Packages stay sequential in one job.** core, contracts, then desktop. Each step's poll can take up to 20 minutes, so the worst case is 60 minutes, well inside the job's default 360-minute timeout. If core times out, the job stops before contracts and desktop. After the maintainer approves core, a rerun of the job skips core (FR-2) and publishes the other two.
- **D-8 No changelog entry.** This changes CI release behavior that only maintainers see. It is not a user-facing change, so `changelog.d/` gets no file.
- **D-9 npm version in messages:** the approval commands use `npx --yes npm@11 stage …`, because a maintainer's global npm may be older than 11.15. This machine has npm 10.9.4, for example. The issue text says "npm 11.5 or later"; the planning check of npm tarballs shows `npm stage` first ships in **11.15.0**, so docs and messages say 11.15.

### Timeout message (exact text; tests assert the bracketed parts)

On timeout after a clean publish:

```
::error::<name>@<version> is not visible on npm after <attempts> checks. npm most likely holds it as a staged version that a maintainer must approve.
```

On timeout after an E409 `previously staged version`:

```
::error::<name>@<version> is not visible on npm after <attempts> checks. npm holds it as a staged version that a maintainer must approve.
```

Both are followed by:

```
On a machine logged in to npm as an @overdeck maintainer (npm 11.15 or later), confirm the staged version and find its stage id:
  npx --yes npm@11 stage list <name>
  npx --yes npm@11 stage view <stage-id>
A package can have several staged versions. Approve only a stage id whose stage view output shows <name> and version <version>:
  npx --yes npm@11 stage approve <stage-id>    (prompts for 2FA)
Or approve it under Staged Packages in your npmjs.com account settings.
If stage list shows no staged <version>, it is not staged: check registry visibility with npm view <name>@<version> version and npm's status page instead of approving anything.
After the approval, re-run this failed job. The script finds the version and skips the publish.
Do not publish <name>@<version> again: npm refuses a second publish of a staged version (E409).
```

Script outline (bash, `#!/usr/bin/env bash`, `set -euo pipefail`, header comment that names PAN-5595 and the staged-version behavior; match the header style of `scripts/vendor-okf-skill.sh`):

```bash
usage() { echo "usage: scripts/npm-publish-retry-safe.sh --tag <dist-tag> <package.tgz|package-dir>" >&2; }
# parse --tag <v> and one positional; anything else -> usage; exit 2
# resolve mode: -f "$pkg" && "$pkg" == *.tgz -> tarball; -d "$pkg" && -f "$pkg/package.json" -> dir; else usage; exit 2
# read name/version (tarball: tar -xOzf "$pkg" package/package.json | node -e '…'; dir: node -e '…' "$pkg/package.json")

attempts="${NPM_VISIBILITY_POLL_ATTEMPTS:-40}"
interval="${NPM_VISIBILITY_POLL_INTERVAL_SECONDS:-30}"

is_visible() {
  local out
  out=$(npm view "${name}@${version}" version --prefer-online 2>/dev/null || true)
  [ "$(printf '%s' "$out" | tr -d '[:space:]')" = "$version" ]
}

if is_visible; then
  echo "${name}@${version} is already visible on npm. Skipping the publish (retry-safe)."
  exit 0
fi

staged=0
if [ "$mode" = tarball ]; then
  if output=$(npm publish "$pkg" --ignore-scripts --provenance --access public --tag "$tag" 2>&1); then status=0; else status=$?; fi
else
  if output=$(cd "$pkg" && npm publish --ignore-scripts --provenance --access public --tag "$tag" 2>&1); then status=0; else status=$?; fi
fi
printf '%s\n' "$output"
if [ "$status" -ne 0 ]; then
  if printf '%s' "$output" | grep -qi 'previously staged version'; then
    staged=1
    echo "${name}@${version} is already staged on npm. Skipping the publish and waiting for it to become visible."
  else
    exit "$status"
  fi
fi

for ((i = 1; i <= attempts; i++)); do
  if is_visible; then echo "${name}@${version} is visible on npm."; exit 0; fi
  [ "$i" -lt "$attempts" ] && sleep "$interval"
done
# print the Timeout message (see Decisions), first line chosen by $staged
exit 3
```

The executor may restructure this, but the behavior, exit codes, env var names and message text must match the Decisions section exactly. The `[ … ] && sleep` line must not trip `set -e` on the last attempt; use `if` instead.
