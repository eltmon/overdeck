# PAN-2093 — ohmypi/kimi work-agent spawn orphans on 30s ready.json readiness window

**Issue:** [PAN-2093](https://github.com/eltmon/overdeck/issues/2093) — bug(spawn): ohmypi/kimi work-agent spawn orphans on 30s ready.json readiness window (PAN-2009 ohmypi variant)
**Planned by:** agent:claude-opus-4-8 (auto mode)
**Date:** 2026-06-27

## Glossary

- **ohmypi / omp** — the `omp` coding-agent binary (oh-my-pi), run in `--mode rpc` reading commands from a per-agent FIFO. The `ohmypi` harness in Overdeck. Replaced the old `pi` harness in PAN-1989 (commit `7de7e5195`).
- **kimi-k2.7-code** — a model Cloister routes to the `ohmypi` harness via provider default. CLIProxy-routed; cold start (process launch + model/auth load) is slow.
- **ready.json** — a per-agent marker written by the ohmypi extension at `session_start` under `~/.overdeck/agents/<id>/ready.json`. Its presence is the readiness signal that the agent process is up and the FIFO has a reader.
- **readiness window** — the bounded poll loop that waits for `ready.json` before delivering the kickoff prompt. Today 30 seconds.
- **work startup grace** — `WORK_LAUNCHER_GRACE_MS = 120_000` (`src/lib/cloister/agent-grace.ts:1`). While an agent is in `starting` status, the Deacon will not declare it orphaned until this grace elapses.
- **orphan** — an agent whose `state.json` says running/starting but has no live tmux session. The Deacon resets it to `stopped` and records a failure.
- **Deacon** — the Cloister lifecycle watchdog that recovers orphaned agents and auto-resumes stopped work agents.

## Problem

A freshly spawned `ohmypi`/`kimi-k2.7-code` **work** agent silently orphans. `pan start <id> --auto` logs `ohmypi prompt delivery failed: ohmypi agent <id> did not become ready within 30s`, prints `✔ Agent spawned`, but no live work tmux session survives. The Deacon marks the agent `orphaned: tmux session missing (reconcile)` and re-attempts via its resume path — but every re-attempt hits the same 30s wall and re-orphans, so the issue is effectively stuck.

### Verified causal chain

1. **Work-agent spawn delivers the kickoff prompt through the ohmypi FIFO and waits for `ready.json` with a 30s window.**
   - `src/lib/agents.ts:428` `writeOhmypiAgentPrompt(agentId, prompt, timeoutSec = 30)` → `src/lib/agents.ts:292` `waitForOhmypiAgentReady(agentId, timeoutSec = 30)` polls `ready.json` every 500ms until the 30s deadline.
   - Called from the work spawn path `spawnAgent` at `src/lib/agents.ts:4085`, and also from `spawnRun` (3730), `resumeAgent` (5191), `restartAgent` (5398), `recoverAgent` (5582) — all inherit the 30s default.
   - The runtime adapter has its own copy: `src/lib/runtimes/ohmypi.ts:58` `SPAWN_READY_TIMEOUT_MS = 30_000`, used by `OhmypiRuntimeSync.spawnAgent` (`ohmypi.ts:351` `await waitForReady(agentId, SPAWN_READY_TIMEOUT_MS)`).

2. **kimi-k2.7-code cold start exceeds 30s.** The omp process launch plus CLIProxy model/auth load does not write `ready.json` within 30s, so the readiness poll times out, the prompt is never delivered, and on the spawn path the error is caught/logged and the function returns the agent state as "spawned" (`src/lib/agents.ts:4090-4098`).

3. **The session orphans.** With no kickoff and a slow/failed cold start the omp session does not survive as a healthy reader; the Deacon's `handleAgentHeartbeatDeadEvent` finds no tmux session and resets the agent to `stopped` with `lastFailureReason = "orphaned: tmux session missing (reconcile)"` (`src/lib/cloister/deacon.ts:5826-5842`).

4. **Re-spawn hits the same wall and never bounds.** The Deacon's auto-resume picks up stopped work agents (`autoResumeStoppedWorkAgents`, `deacon.ts:6916`) and `resumeAgent` already fresh-launches a dead ohmypi process instead of a doomed `omp --resume` (the PAN-2009 fix, `agents.ts:5015-5099`). But the fresh launch again waits only 30s for `ready.json` (`agents.ts:5191`), so it re-orphans. Worse, orphan recovery calls `resetAgentFailureCount(agentId)` before recording the failure (`deacon.ts:5837`), so `consecutiveFailures` resets to 1 every cycle and the agent never accrues to `troubled` (`maxConsecutiveFailures = 3` within a `10 min` window; backoff schedule `[5,30,120]s` — `src/lib/cloister/auto-resume-config.ts:9-13`). The result is an unbounded re-orphan loop, never a working agent and never a bounded stop.

### Notes on the issue's suspected causes

- The issue lists `supervisor:ineligible:harness-ohmypi` (`agents.ts:2119`) as suspected cause #1. **This is expected, not a bug.** The PTY supervisor delivers prompts only for `claude-code`/`codex`; ohmypi delivers through its FIFO, so it is correctly ineligible and falls back to FIFO delivery. It is a red herring for this issue.
- The genuine root cause is the 30s readiness window (issue suspected cause #2/#3), confirmed above.

## Proposal

Three-part fix, smallest-root-cause first.

1. **Raise the ohmypi readiness window from 30s to 90s** (root cause; satisfies AC-3 and AC-1). Raising the window has **no cost on the happy path** — the poll returns as soon as `ready.json` appears (every 500ms); it only extends how long we wait before giving up. 90s comfortably exceeds observed kimi cold starts and sits safely below the 120s work startup grace, so the Deacon will not orphan the agent mid-cold-start. Apply to both the live work path (`agents.ts`) and the runtime adapter (`ohmypi.ts`) for parity.

2. **Bound the Deacon's re-spawn of orphaned ohmypi work agents** (satisfies AC-2). Ensure a readiness-class orphan that recurs accrues toward `troubled` (bounded) instead of resetting its failure count every cycle, so a genuinely-unstartable agent stops after `maxConsecutiveFailures` rather than looping forever. With fix #1 a healthy kimi agent now succeeds before reaching that bound.

3. **Verify end-to-end** that `pan start <id> --auto` on a kimi-routed issue yields a live, progressing work session (AC-1).

### Decisions made in this document

- **Raise to a named constant `90_000`ms, not a config knob.** Simplicity first; matches the existing `SPAWN_READY_TIMEOUT_MS` constant style. (autoDecision)
- **Raise the ohmypi-specific window rather than introducing per-provider classification.** These functions are already ohmypi-specific, and raising the window is free on the happy path, so a single raised value covers kimi and any future CLIProxy-routed omp model without new plumbing. (autoDecision)
- **Invariant to preserve:** readiness window (90s) MUST stay strictly below `WORK_LAUNCHER_GRACE_MS` (120s). If a future change raises the readiness window past the grace, raise the grace in lockstep. Encode this as a comment at both constants and assert it in a test.

### Implementation checkpoint (Bead 2 only)

The Deacon's *observed* re-spawn behavior for an orphaned ohmypi work agent cannot be fully determined from static reading (the issue reporter observed "no re-spawn in 3 min"; static analysis says it should retry after the 5s backoff). **Before changing the Deacon, reproduce and capture `deacon.log` / agent `state.json` transitions** to determine which is true:
- **Branch A — retried but failing every cycle (failure count resets to 1):** bound the accrual so readiness-class orphans reach `troubled` after `maxConsecutiveFailures`.
- **Branch B — never retried (a gate drops it, e.g. the idle gate at `deacon.ts:6831-6836` or backoff):** fix the specific gate so orphaned ohmypi work agents are eligible for bounded re-spawn.
Either branch's fix MUST NOT change orphan recovery for `claude-code`/`codex` agents (regression-test this).

## Requirements

- **FR-1** — The ohmypi readiness wait tolerates a cold start longer than 30s (up to the new window) before giving up.
- **FR-2** — The raised readiness window is applied on every ohmypi readiness path: work spawn, role-run spawn, resume, restart, recover, and the runtime-adapter spawn.
- **FR-3** — The readiness window stays strictly below the work startup grace (`WORK_LAUNCHER_GRACE_MS`).
- **FR-4** — An ohmypi/kimi work agent spawned via `pan start <id> --auto` reaches a live tmux session and begins working its beads.
- **FR-5** — An ohmypi work agent that does orphan on readiness is re-spawned by the Deacon with **bounded** retries (reaches `troubled` after the configured max consecutive failures) rather than looping forever or being left permanently stopped.
- **NFR-1** — Deacon changes do not alter orphan recovery / auto-resume behavior for `claude-code` and `codex` agents.
- **NFR-2** — All new delay/backoff tests use fake timers (`vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()`), never real waits.
