# PAN-2093 — ohmypi/kimi work-agent spawn orphans on the 30s ready.json readiness window

**Issue:** [PAN-2093](https://github.com/eltmon/overdeck/issues/2093) — `bug(spawn): ohmypi/kimi work-agent spawn orphans on 30s ready.json readiness window (PAN-2009 ohmypi variant)`
**Planned by:** agent:claude-opus-4-8 (auto mode), 2026-06-27. All file:line references checked against `f2bbe0291` on `feature/pan-2093`.

> This revision merges the prior auto-planning pass (readiness window + bounded re-spawn) with a newly verified third root cause: the ohmypi **work** spawn never sets `remain-on-exit`, so when `omp` exits the tmux session is destroyed — which is the literal "tmux session missing" the issue reports.

## Glossary

- **ohmypi / omp** — the `omp` coding-agent binary (oh-my-pi), run in `--mode rpc` reading commands from a per-agent FIFO. The `ohmypi` harness in Overdeck. Separate runtime from the legacy `pi` harness (`src/lib/runtimes/ohmypi.ts` vs `pi.ts`).
- **kimi-k2.7-code** — a model Cloister routes to the `ohmypi` harness via provider default. CLIProxy-routed; cold start (process launch + model/auth load) is slow.
- **ready.json** — a per-agent marker written by the ohmypi extension at `session_start` under `~/.overdeck/agents/<id>/ready.json` (`ohmypiFifoPaths(agentId).readyPath`). Its presence is the readiness signal that omp is up and the FIFO has a reader.
- **readiness window** — the bounded poll loop that waits for `ready.json` before delivering the kickoff prompt. Today **30 seconds**.
- **work startup grace** — `WORK_LAUNCHER_GRACE_MS = 120_000` (`src/lib/cloister/agent-grace.ts:1`). While a work agent is in `starting` status, the Deacon will not declare it orphaned until this grace elapses.
- **remain-on-exit** — a tmux pane option; when `on`, the pane (and its single-pane session) survives after its process exits, leaving a *dead pane* instead of being destroyed. Planning/review sessions and `spawnRun` set it; the work-agent `spawnAgent` path does not.
- **`spawnRun` vs `spawnAgent`** — two spawn entry points in `src/lib/agents.ts`. `spawnRun` (`:~3500`) handles role-runs (review/test/etc.) and *does* set `remain-on-exit` after `createSession` (`:3724-3725`). `spawnAgent` (`:3778`) is the work/strike spawn used by `pan start`; it never sets `remain-on-exit`.
- **orphan** — an agent whose `state.json` says running/starting but has no live tmux session. The Deacon resets it to `stopped` and records a failure.
- **Deacon** — the Cloister lifecycle watchdog (`src/lib/cloister/deacon.ts`) that recovers orphaned agents and auto-resumes stopped work agents.

## Problem

A freshly spawned `ohmypi`/`kimi-k2.7-code` **work** agent silently orphans. `pan start <id> --auto` logs `ohmypi prompt delivery failed: ohmypi agent <id> did not become ready within 30s`, prints `✔ Agent spawned`, but **no live work tmux session exists** afterward. The Deacon marks the agent `orphaned: tmux session missing (reconcile)` (status `stopped`, `consecutiveFailures: 1`, `troubled: false`) and the issue is effectively stuck.

### Verified causal chain (three independent root causes)

**RC-1 — the readiness window is a hard-coded 30s, too short for kimi cold starts (→ AC-3).**
- `src/lib/agents.ts:428` `writeOhmypiAgentPrompt(agentId, prompt, timeoutSec = 30)` → `src/lib/agents.ts:292` `waitForOhmypiAgentReady(agentId, timeoutSec = 30)` polls `ready.json` every 500ms until the 30s deadline, then throws.
- Called from the work spawn `spawnAgent` at `src/lib/agents.ts:4085`, and from `spawnRun` (`:3730`), `resumeAgent` (`:5191`), `restartAgent` (`:5398`), `recoverAgent` (`:5582`) — all inherit the 30s default.
- The runtime adapter has its own copy: `src/lib/runtimes/ohmypi.ts:58` `SPAWN_READY_TIMEOUT_MS = 30_000`, used at `:351`.
- kimi-k2.7-code cold start (omp launch + CLIProxy model/auth) exceeds 30s, so the poll times out and the kickoff is never delivered. On the spawn path the error is caught/logged and the function returns "spawned" (`src/lib/agents.ts:4090-4098`).

**RC-2 — the ohmypi work session is destroyed when omp exits, because `remain-on-exit` is never set (→ AC-1; the literal "tmux session missing").**
- `spawnAgent` (`src/lib/agents.ts:3778`) creates the session at `:4056` and **never** sets `remain-on-exit`/`destroy-unattached` (zero `setOption` calls in the `spawnAgent` body, lines 3778–4130; `buildNewSessionArgs` doesn't set them either — `src/lib/tmux.ts:651-672`).
- The launcher runs `exec omp …` (`src/lib/launcher-generator.ts:638` returns `exec ${cmd}`), so when omp exits the pane has no process; with `remain-on-exit` unset (default `off`) the pane closes, the last window closes, and **the session is destroyed** → "tmux session missing".
- `claude-code` work agents are unaffected: Claude stays alive at its interactive prompt, keeping the pane alive. This is why only ohmypi exhibits the vanish.
- Contrast: `spawnRun` does set the options (`:3724-3725`), so its sessions survive a process exit. The work path simply omits this.

**RC-3 — once `remain-on-exit` is fixed, the Deacon's dead-pane orphan detector only covers planning sessions (→ AC-1 correctness; gates AC-2).**
- `handleAgentHeartbeatDeadEvent` checks `pane_dead` only when `agentId.startsWith('planning-')`; for any other *existing* session it returns `[] // truly still running` (`src/lib/cloister/deacon.ts:5800-5815`). So a *dead* omp work pane (after RC-2 is fixed) would be mistaken for "still running" forever. The dead-pane check must be extended to ohmypi work sessions.

**RC-4 — the re-spawn loop can fail to bound, because orphan recovery resets the failure count (→ AC-2).**
- The Deacon does auto-resume stopped work agents (`handleAgentStoppedEvent` → `resumeAgent`, `src/lib/cloister/deacon.ts:~6860, ~7012`), and `resumeAgent` already fresh-launches a dead omp instead of a doomed `omp --resume` (the PAN-2009 fix, `agents.ts:5015-5099`). But each fresh launch again waits only 30s (RC-1) and re-orphans.
- On each orphan, recovery calls `resetAgentFailureCount(agentId)` **unless** the death is a "rapid post-resume death" (`src/lib/cloister/deacon.ts:5834-5842`). `isRapidPostResumeDeath` keys off `RAPID_POST_RESUME_DEATH_MS = 120_000` (`deacon.ts:5742`). So a re-orphan *within 120s of resume* accrues toward `troubled` (bounded); one *after* 120s resets the count → unbounded loop, never reaching `troubled` (`maxConsecutiveFailures = 3`, window `10 min`, backoff `[5,30,120]s` — `src/lib/cloister/auto-resume-config.ts:9-13`). The field report ("failures stayed at 1, no re-spawn for 3+ minutes") is consistent with either the reset-loop or a run booted `OVERDECK_NO_RESUME=1` (the current throughput-unfreeze posture; an intentional global kill switch, out of scope).

### Notes on the issue's suspected causes

- `supervisor:ineligible:harness-ohmypi` (`agents.ts:2119`) is **expected, not a bug** — the PTY supervisor delivers prompts only for `claude-code`/`codex`; ohmypi correctly falls back to FIFO delivery. A red herring.
- The genuine root causes are RC-1 (window), RC-2/RC-3 (session vanish + dead-pane detection), and RC-4 (unbounded re-spawn).

## Proposal

Fix all four root causes, **scoping every behavioural change to the ohmypi harness** so claude-code/codex work-agent semantics are untouched (NFR-1).

1. **Raise the ohmypi readiness window 30s → 90s** (RC-1 → AC-3). Free on the happy path (the poll returns as soon as `ready.json` appears). 90s comfortably exceeds observed kimi cold starts and stays strictly below the 120s work startup grace, so the Deacon will not orphan the agent mid-cold-start. Applied to both `agents.ts` and the `ohmypi.ts` runtime constant for parity.
2. **Make the ohmypi work session survive a slow/dead omp** (RC-2 + RC-3 → AC-1). Set `remain-on-exit on` + `destroy-unattached off` on ohmypi work sessions at creation, and extend the Deacon's dead-pane orphan check from `planning-` sessions to ohmypi work sessions so a dead omp pane is recovered (reset to `stopped`) rather than treated as "still running".
3. **Bound the re-spawn of orphaned ohmypi work agents** (RC-4 → AC-2) so a genuinely-unstartable agent reaches `troubled` after `maxConsecutiveFailures` instead of looping forever. With fix #1 a healthy kimi agent succeeds before reaching that bound.

### Decisions made in this document

- **Raise to a named constant `OHMYPI_READY_TIMEOUT_SEC = 90` (90_000ms in the runtime), not an env knob.** Simplicity first; matches the existing `SPAWN_READY_TIMEOUT_MS` constant style. An env knob would also need clamping below the grace, adding complexity for little gain. (autoDecision)
- **Invariant to preserve:** readiness window (90s) MUST stay strictly below `WORK_LAUNCHER_GRACE_MS` (120s). Encode as a comment at both constants and assert in a test. (autoDecision)
- **Scope `remain-on-exit` + dead-pane detection to the ohmypi harness only.** claude-code/codex work sessions keep their current behaviour (their panes stay alive at the prompt, so they neither vanish nor need the dead-pane branch). Gating on `harness === 'ohmypi'` keeps the blast radius minimal. (autoDecision)
- **Do not make supervisor/PTY delivery eligible for ohmypi.** FIFO-RPC delivery works once readiness is honoured; broadening the supervisor is a separate, larger change. (NonGoal)

### Implementation checkpoints

- **Bead 2 (slow-vs-dead omp).** Reproduce on a kimi-routed issue with `remain-on-exit on` already applied; capture the pane. **If omp is alive but slow** (`ready.json` lands ~45–90s): the window raise (Bead 1) makes the kickoff succeed and the session stays live — done. **If omp exits early** with an auth/CLIProxy/model error: the now-preserved dead pane exposes it; file a *separate substrate issue* for that orthogonal omp-startup failure (PAN-2093's session-survival + recovery still apply). **Fallback if no live repro is available:** implement Beads 1–3 as specified — they are correct under both hypotheses — and note the deferred live confirmation in the PR.
- **Bead 3 (retry-vs-never).** Before changing the Deacon, reproduce and capture `deacon.log` / `state.json` transitions to determine: **Branch A** — it retries but `resetAgentFailureCount` (`deacon.ts:5837`) keeps the count at 1 outside the 120s rapid-death window → make readiness-class orphans accrue toward `troubled`; **Branch B** — a gate drops it entirely → fix that gate. Either branch's fix MUST NOT change orphan recovery for `claude-code`/`codex` (regression-test this).

## Requirements

- **FR-1** — The ohmypi readiness wait tolerates a cold start longer than 30s (up to the 90s window) before giving up, applied on every ohmypi readiness path: work spawn, role-run spawn, resume, restart, recover, and the runtime-adapter spawn.
- **FR-2** — The readiness window stays strictly below the work startup grace (`WORK_LAUNCHER_GRACE_MS`).
- **FR-3** — An ohmypi work-agent spawn whose omp process is slow **or** exits early does NOT result in a silently destroyed tmux session; the session persists (live pane if slow, dead pane if exited) and is visible via `tmux -L overdeck ls`.
- **FR-4** — A dead-pane ohmypi work session is detected by the Deacon as an orphan (status → `stopped`, failure recorded) rather than treated as still-running.
- **FR-5** — An ohmypi/kimi work agent spawned via `pan start <id> --auto` reaches a live tmux session and begins working its beads.
- **FR-6** — An ohmypi work agent that does orphan on readiness is re-spawned by the Deacon with **bounded** retries (reaches `troubled` after `maxConsecutiveFailures`) rather than looping forever or being left permanently stopped.
- **NFR-1** — The window, `remain-on-exit`, dead-pane-detection, and re-spawn-bounding changes do not alter behaviour for `claude-code` or `codex` agents.
- **NFR-2** — All new delay/backoff tests use fake timers (`vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()`), never real waits.

### Item 3 — Bound the Deacon's re-spawn of orphaned ohmypi work agents (`bound-ohmypi-orphan-respawn`) — FR-6, NFR-1
