## Glossary

- **Advancing ceiling** — `countRunningAgents()` in `src/lib/cloister/concurrency.ts` counts tmux-alive sessions whose name matches `agent-<id>-review`, `agent-<id>-review-*`, `agent-<id>-test`, `agent-<id>-ship`, or legacy `specialist-*` patterns. `canDispatchAdvancing()` (concurrency.ts:160) gates ALL review/test/ship spawns when this count meets or exceeds the `totalCeiling` (default 9 from PAN-1665).
- **Advancing zombie** — an advancing-role tmux session still alive after its verdict is recorded in `review_status`; it holds a ceiling slot for an issue that no longer needs it.
- **`KEEP_SPECIALIST_SESSIONS_ALIVE`** — a boolean flag in `src/lib/cloister/reap-terminal-sessions.ts:33`, currently `true` (PAN-2007 operator request); when true, `checkTerminalAdvancingSessions()` in deacon.ts returns early without reaping any sessions. This is the structural root of the zombie problem: the PAN-1716 reaper is disabled.
- **Test verdict journal** — `<workspace>/.pan/test/result.json`; written by the test agent BEFORE it POSTs the verdict (per test-agent-queue.ts:44). Read by `readTestVerdictArtifact()` in `src/lib/cloister/test-verdict.ts:54`.
- **Review verdict journal** — the per-issue record at `<workspace>/.pan/records/<issueId-lower>.json` (`PanIssuePipelineRecord` inside `PanIssueRecord`); written by `updateIssueRecordForReviewStatusSync(issueId, updated)` inside `setReviewStatusSync` at review-status.ts:408.
- **Journal reconcile** — `getReviewStatusSync(issueId)` in `src/lib/review-status.ts` reads from SQLite first; when the SQLite row is missing or stale, it falls back to the journal (per-issue record) and writes the verdict back to SQLite (`dbUpsert`). This is the "journal → DB" reconcile described in review-status.ts:775 and PAN-1988.
- **`loadReviewStatuses()`** — returns all rows from the SQLite `review_status` table (review-status.ts). Issues absent from SQLite are INVISIBLE to the patrol dispatchers even if their verdict lives in the journal.
- **Boot reconciliation (PAN-2076)** — `applyBootReconciliationDecision()` in `src/lib/cloister/deacon-auto-resume.ts`, called from `startDeacon()` (deacon.ts:3386). Handles work-agent resume decisions; does NOT call `getReviewStatusSync` for advancing agents, so journal verdicts for review/test agents are NOT reconciled on boot.
- **`checkTerminalAdvancingSessions()`** — deacon.ts:2477; uses `selectTerminalAdvancingSessions()` from `reap-terminal-sessions.ts:94` to find advancing sessions whose phase verdict is terminal, then kills them. Currently a no-op because `KEEP_SPECIALIST_SESSIONS_ALIVE = true`.
- **`selectTerminalAdvancingSessions()`** — pure function in reap-terminal-sessions.ts:94; given `statuses` (from DB) and `aliveSessions` (from tmux), returns sessions to reap. Consults `isRoleTerminal(role, status)` (reap-terminal-sessions.ts:77): review terminal when `reviewStatus ∈ {passed,failed,blocked}`; test terminal when `testStatus ∈ {passed,failed}`; ship terminal when `readyForMerge=true` or `mergeStatus ∈ {merged,failed}`.
- **`selectMergedWorkSessions()`** — reap-terminal-sessions.ts:130; reaps WORK sessions (agent-<id>) for merged issues. There is NO equivalent for ADVANCING sessions (agent-<id>-review, agent-<id>-test).

## Problem (verified 2026-07-04)

### 2026-07-03 incident

9 of 9 advancing slots (the entire PAN-1665 ceiling) were held by sessions for issues with recorded verdicts, two of which were already merged. `checkPendingTestDispatch` (deacon.ts:2881) deferred ALL further test dispatch as the ceiling was full. The pipeline was frozen for hours until a manual redeploy (`pan up`) rebuilt the DB cache and a manual `tmux kill-session` unblocked slots.

### Root causes (verified in source)

**Root cause 1 — `KEEP_SPECIALIST_SESSIONS_ALIVE = true` disables the only reaper:**

```ts
// src/lib/cloister/reap-terminal-sessions.ts:33
export const KEEP_SPECIALIST_SESSIONS_ALIVE = true;
```

And in `checkTerminalAdvancingSessions` (deacon.ts:2480–2483):
```ts
const { selectTerminalAdvancingSessions, KEEP_SPECIALIST_SESSIONS_ALIVE } = await import('./reap-terminal-sessions.js');
// PAN-2007: operator-requested temporary keep-alive — do not reap specialist sessions
if (KEEP_SPECIALIST_SESSIONS_ALIVE) return actions;
```

When the dashboard ran stale/broken code (throwing `Effect.catchAll is not a function` or `SQLITE_READONLY`), the HTTP POST from review/test agents failed. The agents wrote their verdicts to the workspace journal (`.pan/test/result.json` for test; per-issue record for review) and went idle — but their tmux sessions remained alive. With `KEEP_SPECIALIST_SESSIONS_ALIVE=true`, `checkTerminalAdvancingSessions` never reaps them.

**Root cause 2 — No advancing-session reaper for merged issues:**

`checkMergedWorkSessions()` (deacon.ts:2516) reaps WORK sessions (`agent-<id>`) for merged issues. It calls `selectMergedWorkSessions` (reap-terminal-sessions.ts:130). There is no equivalent function that reaps ADVANCING sessions (`agent-<id>-review`, `agent-<id>-test`) for merged issues. Both of the merged-issue sessions in the incident were advancing sessions, not work sessions.

**Root cause 3 — Journal verdicts not reconciled on boot:**

`startDeacon()` (deacon.ts:3373–3398) calls:
1. `reconcileAgentLiveness()` (deacon.ts:3386) — resumes agents per DB state; does NOT call `getReviewStatusSync`.
2. `runScheduledPatrol('startup')` (deacon.ts:3387) — runs all patrols; calls `checkCompletedButUnsignaledTests` (handles `.pan/test/result.json`) and `checkPostReviewCommits` (handles dispatching from existing review-status), but:
   - `loadReviewStatuses()` reads from SQLite. If the verdict POST failed and the SQLite row has no verdict (or is absent), the patrol dispatchers treat the issue as if no verdict was recorded.
   - `getReviewStatusSync(issueId)` would trigger journal→DB reconcile, but it is not called for every in-flight issue on boot.

**Combined effect:** a broken server write → verdict in journal only → sessions alive → DB shows no verdict → patrol sees ceiling full → ALL dispatch frozen.

## Requirements

- **FR-1** — On boot (inside `startDeacon()`), the system MUST call `getReviewStatusSync(issueId)` for every in-flight issue resolvable from the `review_status` SQLite table to trigger journal→DB reconcile. This ensures any verdict written to `.pan/test/result.json` or the per-issue record during a broken server period is applied to SQLite before the first patrol runs.
- **FR-2** — A new function `checkMergedAdvancingSessions()` MUST reap advancing sessions (`agent-<id>-review`, `agent-<id>-review-*`, `agent-<id>-test`, `agent-<id>-ship`) for issues whose `mergeStatus === 'merged'`, regardless of `KEEP_SPECIALIST_SESSIONS_ALIVE`. Merged issues have no further pipeline work — keeping their sessions alive serves no diagnostic value.
- **FR-3** — `checkMergedAdvancingSessions()` MUST be called both on boot (as part of `startDeacon()`) AND in the regular patrol cycle (`runScheduledPatrol`), so it self-heals without requiring a redeploy.
- **FR-4** — After journal reconcile (FR-1) applies new verdicts to SQLite, the patrol's `checkTerminalAdvancingSessions()` should also run to reap sessions whose verdicts became terminal during reconcile. Because `KEEP_SPECIALIST_SESSIONS_ALIVE` is still `true` for non-merged issues (the PAN-2007 keep-alive is deliberately preserved for debugging), the ONLY guaranteed reap path for non-merged terminal sessions remains `checkMergedAdvancingSessions()`. This PRD does NOT flip `KEEP_SPECIALIST_SESSIONS_ALIVE` to `false` — that is [PAN-2007](https://github.com/eltmon/overdeck/issues/2007)'s responsibility.
- **FR-5** — Regression test: with 9 advancing sessions held by merged issues and the ceiling at 9, after `checkMergedAdvancingSessions()` runs, all 9 sessions are reaped and `canDispatchAdvancing()` returns true.
- **FR-6** — Idempotency: calling journal reconcile or `checkMergedAdvancingSessions()` multiple times in succession produces the same result as calling once (no duplicate state writes, no double-kill of already-dead sessions).
- **NFR-1** — No new explicit `any`; async only (no `execSync`); no new files ≥1,000 lines.
- **NFR-2** — Boot reconcile (`getReviewStatusSync` fan-out) MUST be bounded: skip issues whose `mergeStatus === 'merged'` (their verdicts are irrelevant; reconciling them writes unnecessary work to SQLite). Call only for issues in `pending`, `reviewing`, `passed`, `failed`, `blocked`, `testing`, `dispatch_failed` states.

### W2 — `checkMergedAdvancingSessions()`: reap advancing zombies for merged issues (FR-2, FR-3, FR-5)

**File:** `src/lib/cloister/deacon.ts`

This is the advancing-session sibling of `checkMergedWorkSessions()` (deacon.ts:2516). Add the new function nearby (after `checkMergedWorkSessions`):

```ts
/**
 * PAN-2341: Reap advancing-role sessions (agent-<id>-review, agent-<id>-review-*,
 * agent-<id>-test, agent-<id>-ship) for issues whose mergeStatus is 'merged'.
 *
 * Advancing sessions for merged issues have no further pipeline work. This reaper
 * bypasses KEEP_SPECIALIST_SESSIONS_ALIVE (the PAN-2007 keep-alive flag) because
 * there is no diagnostic value in keeping sessions alive for already-merged issues.
 * The existing checkTerminalAdvancingSessions() handles non-merged terminal sessions,
 * but only when KEEP_SPECIALIST_SESSIONS_ALIVE=false (PAN-2007). This function
 * fills the gap for the merged-issue class regardless of that flag.
 */
export async function checkMergedAdvancingSessions(): Promise<string[]> {
  const actions: string[] = [];
  try {
    const { sessionsToReapForRole } = await import('./reap-terminal-sessions.js');
    const statuses = loadReviewStatuses();
    const aliveSessions = await Effect.runPromise(listSessionNames());
    const aliveSet = new Set([...aliveSessions]);
    for (const [issueId, status] of Object.entries(statuses)) {
      if (status.mergeStatus !== 'merged') continue;
      const toKill: string[] = [
        ...sessionsToReapForRole(issueId, 'review', [...aliveSet]),
        ...sessionsToReapForRole(issueId, 'test',   [...aliveSet]),
        ...sessionsToReapForRole(issueId, 'ship',   [...aliveSet]),
      ];
      for (const session of toKill) {
        try {
          await Effect.runPromise(killSession(session));
          aliveSet.delete(session);
          const msg = `checkMergedAdvancingSessions: reaped ${session} — issue ${issueId} is merged, advancing session is zombie (PAN-2341)`;
          actions.push(msg);
          logDeaconEventSync(msg);
          console.log(`[deacon] ${msg}`);
        } catch (err) {
          console.warn(`[deacon] Failed to reap merged advancing session ${session}: ${err instanceof Error ? err.message : String(err)}`);
        }
      }
    }
  } catch (err: any) {
    console.error('[deacon] Error in checkMergedAdvancingSessions:', err.message);
  }
  return actions;
}
```

Note: `loadReviewStatuses`, `listSessionNames`, `killSession`, `logDeaconEventSync`, and `Effect` are already imported in deacon.ts. `sessionsToReapForRole` is a new import from `'./reap-terminal-sessions.js'` (already imported as `selectTerminalAdvancingSessions` etc. — add `sessionsToReapForRole` to the same destructured import).
