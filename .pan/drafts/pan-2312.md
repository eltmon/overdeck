# PAN-2312 — Make the `better-sqlite3` rebuild non-fatal in workspace init

**Issue:** [PAN-2312](https://github.com/eltmon/overdeck/issues/2312) — bug(workspace-init):
transient better-sqlite3 prebuilt-binary fetch hard-fails fresh workspace init (no Python
for node-gyp fallback on Alpine)

## Glossary

- **init service** — the one-shot `init` service in the workspace devcontainer compose
  stack. It runs `bun install`, rebuilds native addons, builds contracts, and builds the
  dashboard server. `frontend` and `server` services `depends_on: init` with
  `condition: service_completed_successfully`, so if `init` exits non-zero the whole
  workspace stack is unhealthy and `pan start` aborts.
- **template** — `infra/.devcontainer-template/docker-compose.devcontainer.yml.template`.
  The committed source of truth. Rendered per workspace (placeholder substitution) into
  each workspace's `.devcontainer/docker-compose.devcontainer.yml`.
- **rendered compose** — `<workspace>/.devcontainer/docker-compose.devcontainer.yml`.
  **Gitignored** (`git check-ignore` confirms) — a derived artifact regenerated from the
  template at workspace create/rebuild. Not part of any PR diff.
- **prebuild-install** — the tool `better-sqlite3`'s install/rebuild uses to fetch a
  prebuilt native binary. On failure it falls back to a `node-gyp` source build.
- **node-gyp fallback** — compiling the native addon from source. Needs `python3` +
  `make` + `g++`, none of which exist on the Alpine init image → the fallback dies.

## Problem

`infra/.devcontainer-template/docker-compose.devcontainer.yml.template:42` runs:

```
npm rebuild better-sqlite3 2>&1 &&
```

The bare `&&` makes the rebuild **fatal**: any non-zero exit aborts the whole init
command chain. The Alpine init image has no `python3`/`make`/`g++`, so `better-sqlite3`
depends entirely on `prebuild-install` fetching a prebuilt binary. On a transient fetch
failure (or a missing prebuilt for the node version) it falls back to a node-gyp source
build, which fails for lack of Python, and **init hard-fails**. `pan start` then aborts
with "Workspace docker stack … is not healthy". Hit live on 2026-07-03 landing PAN-2310;
cleared only by a manual `pan workspace rebuild`.

This is disproportionate: `better-sqlite3` is a **dev-only transitive dependency** (pulled
by the `evalite` devDependency; verified absent from `src/` and from `package.json`
direct deps). The dashboard runtime uses bundled `node:sqlite`/`bun:sqlite` — it never
needs `better-sqlite3`. A flaky fetch of a dep the runtime doesn't use hard-fails *all*
fresh-workspace creation, directly threatening the stability-drain (every hand-pulled fix
needs a fresh workspace).

## Proposal

**Option 1 (issue-preferred, smallest): make the rebuild non-fatal.** Wrap the rebuild in
a subshell so a non-zero exit logs a warning and init continues. Reuse the exact idiom the
`bun install` line above it already uses (line 40: `{ cmd || { fallback; }; } &&`).

Before (template line 42):
```
        npm rebuild better-sqlite3 2>&1 &&
```

After:
```
        { npm rebuild better-sqlite3 2>&1 || echo 'WARN: better-sqlite3 rebuild failed (dev-only transitive dep via evalite; runtime uses bundled node:sqlite/bun:sqlite) — continuing init (PAN-2312).'; } &&
```

The command is a YAML folded block scalar (`>`), collapsed to one line, so `{ …; } &&`
and `||` behave as ordinary sh. All later steps (contracts build, dashboard server build,
the intentional `UNRESOLVED_IMPORT` guard at line 47) stay **fatal** — unchanged.

### Verification

`tests/unit/dashboard/config.test.ts:85` already reads the real template via
`readFileSync(resolve(process.cwd(), 'infra/.devcontainer-template/…'))`, renders
placeholders, and parses YAML. A new unit test uses the same approach to extract the
`init` service `command` string and assert the `better-sqlite3` rebuild is non-fatal.

## Decisions made in this doc (auto mode — no user Q&A)

- **D1 — Option 1 only, not 2/3/4.** Chose "make the rebuild non-fatal" over retrying the
  fetch (2), adding python3/make/g++ to the image (3), or excluding better-sqlite3 (4).
  Rationale: the issue names option 1 as preferred and smallest; the runtime never needs
  better-sqlite3, so once the failure is non-fatal a retry adds complexity for a dep whose
  failure is now harmless. Options 3/4 are larger surface changes (image bloat / install
  filtering) for no runtime benefit. Simplicity-first.
- **D2 — Fix the template, not the gitignored rendered compose, as the durable change.**
  The rendered `.devcontainer/docker-compose.devcontainer.yml` is gitignored and
  regenerated from the template, so it cannot carry the fix into main or into other
  workspaces. The committed fix is the template alone. The work agent mirrors the same
  edit into this workspace's local rendered copy so THIS workspace can rebuild cleanly,
  but that edit is expected to be absent from the PR diff (gitignored) — not a defect.
- **D3 — Warn, don't silently swallow.** On rebuild failure, emit a stdout warning naming
  better-sqlite3 as a dev-only dep, so init logs stay diagnosable rather than hiding the
  skipped step.

## NonGoals

- Do NOT add `python3`/`make`/`g++` to the init image (option 3).
- Do NOT exclude/filter `better-sqlite3` from `bun install` (option 4).
- Do NOT add a retry loop around the rebuild (option 2) — non-fatal makes it unnecessary.
- Do NOT weaken any other init step's fatality (contracts build, dashboard server build,
  the `UNRESOLVED_IMPORT` guard remain fatal).
- Do NOT commit the gitignored rendered `.devcontainer/docker-compose.devcontainer.yml`.

## Acceptance criteria

1. A transient `better-sqlite3` prebuild-fetch/rebuild failure no longer hard-fails init.
2. The init command still runs its later build steps and those remain fatal.
3. A unit test asserts init tolerates the better-sqlite3 rebuild step failing.
