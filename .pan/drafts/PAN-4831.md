## Glossary

- **Account service:** the overdeck.ai account Cloudflare Worker at `services/account/` (D1 database). It signs people in with GitHub and mints device tokens. Developer doc: `docs/ACCOUNT-SERVICE.md`.
- **PKCE flow:** the browser sign-in flow (RFC 7636 + RFC 8252). `GET /auth/start` → GitHub → a 302 back to the client's `redirect_uri` with `code=odc_…&state=…` → the client posts `POST /oauth/token` with `grant_type=authorization_code`, `code`, `code_verifier` and the identical `redirect_uri`. Code: `services/account/src/pkce.ts`.
- **Loopback redirect:** a `redirect_uri` of the form `http://127.0.0.1:<port>/…`, `http://localhost:<port>/…` or `http://[::1]:<port>/…` (RFC 8252 §7.3). The only redirect form the service accepts today. Used by the local dashboard.
- **Private-use URI scheme redirect:** a redirect whose scheme is a reverse-DNS name the native app owns (RFC 8252 §7.1). For the Overdeck phone app it is exactly `ai.overdeck.app:/oauth/callback` — note the single slash after the colon.
- **Native redirect / `NATIVE_APP_REDIRECT`:** the constant string `ai.overdeck.app:/oauth/callback` this issue adds.
- **Platform:** the `platform` request parameter and the `devices.platform` column, e.g. `linux-x64`. Validated by `PLATFORM_RE` in `services/account/src/devices.ts`.
- **Default label:** the device label the service picks at mint time (`defaultLabel()` in `devices.ts`), never the hostname (D-17 of PAN-4293).
- **Device flow:** the RFC 8628 headless sign-in (`POST /oauth/device/code`, `/activate`), code in `services/account/src/device-flow.ts`. It shares `isValidPlatform` and `defaultLabel` with the PKCE flow.
- **Phone app:** the Capacitor iOS/Android app the epic adds (`apps/mobile`, bundle id `ai.overdeck.app`). It is not part of this issue.

## Requirements

- **FR-1** `GET /auth/start` accepts `redirect_uri=ai.overdeck.app:/oauth/callback` (exact string) and redirects to GitHub (302), as it does for a loopback redirect.
- **FR-2** `GET /auth/start` refuses every other non-loopback `redirect_uri` with the existing 400 error page and no `Location` header. This includes `ai.overdeck.app:/other`, `ai.overdeck.app://oauth/callback`, `evil:/oauth/callback`, `AI.OVERDECK.APP:/oauth/callback` and `ai.overdeck.app:/oauth/callback?x=1`.
- **FR-3** After the GitHub leg, the browser is sent to `ai.overdeck.app:/oauth/callback?code=odc_…&state=…` (or `?error=access_denied&error_description=…&state=…`), and `POST /oauth/token` with that same `redirect_uri` and the matching verifier mints a device.
- **FR-4** `PLATFORM_RE` accepts `ios-arm64` and `android-arm64` in addition to the existing six desktop values, and nothing else new (`ios-x64`, `android-x64`, `ios-arm`, `iphone-arm64` stay invalid).
- **FR-5** `defaultLabel('ios-arm64')` is `"iPhone"`; `defaultLabel('android-arm64')` is `"Android phone"`. Existing labels are unchanged.
- **FR-6** `docs/ACCOUNT-SERVICE.md` describes the native redirect rule and the two phone platforms with their default labels.
- **NFR-1** Loopback behavior is unchanged: every existing test in `tests/unit/services/account/` still passes without edits to its expectations.
- **NFR-2** No new response header. In particular, no `Access-Control-*` header is added.
- **NFR-3** The native redirect is matched by exact string equality on the raw parameter (RFC 8252 §8.10 recommends exact matching for non-loopback redirects). No prefix, scheme-only or parsed-URL matching.

## Decisions

- **D-1 Exact match only.** `validateClientRedirect` returns the raw value only when `raw === NATIVE_APP_REDIRECT`; otherwise it returns `validateLoopbackRedirect(raw)`. Accepting any `ai.overdeck.app:` URL, or any path under it, is refused: it widens the redirect surface for no caller.
- **D-2 The device flow also accepts the phone platforms.** `device-flow.ts` uses the same `isValidPlatform` and `defaultLabel`. A device-flow request with `platform=ios-arm64` is now accepted and its `/activate` confirm page reads "Connect a **iPhone** to your Overdeck account?". The phone app never uses the device flow, and no caller sends those values there, so no extra gate and no wording change is added. (Recorded in `autoDecisions`.)
- **D-3 `src/lib/account/client.ts` stays unchanged.** Its `PLATFORM_ARCH_RE` validates the machine's own `process.platform`/`process.arch`. A machine is never a phone, and widening it would let a Node process on Android (Termux) register as "Android phone". Its comment ("matches the service's PLATFORM_RE") stays true as a subset; do not edit the file.
- **D-4 No CORS.** The phone app's WebView origin (`capacitor://localhost` on iOS, `https://localhost` on Android) is cross-origin to `account.overdeck.ai`, and the service sends no `Access-Control-*` headers. The phone app (epic item W-APP1) must call `POST /oauth/token` and `/v1/*` with native HTTP (Capacitor's `CapacitorHttp`), not WebView `fetch`. This issue adds no CORS headers. The planning agent posts this note on the epic so W-APP1 picks it up.
- **D-5 No schema change.** `platform` and `redirect_uri` columns are free `TEXT` (`0001_init.sql`), so no migration.

- **Should the device flow refuse phone platforms?** Options: (a) accept them via the shared validator (chosen), (b) add a separate desktop-only validator for the device flow. Chosen (a): the phone never uses the device flow, and a second validator adds code for no caller.

Chosen (a): AC-4 does not need it, it changes the auth surface, and `http.ts` documents "no Access-Control-* header" as an invariant.
