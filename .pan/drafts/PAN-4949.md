## Glossary

- **Access-token registry** — `~/.overdeck/access-tokens.json`, read and written only by `src/lib/access-tokens.ts`. Each record has an `id`, `name`, `scopes`, a SHA-256 `tokenHash` and an optional `kind`. The record shape and its validator `isRecord` live in the leaf module `src/lib/access-token-records.ts`.
- **Kind** — the record's `kind` field: `device` (default), `token`, `machine`, `phone`, and (new here) `connector`. An unknown kind makes the whole file corrupt, so every token is refused until it is repaired.
- **Scope** — one of `ACCESS_TOKEN_SCOPES` (`access-token-records.ts:6-17`). `admin` satisfies every scope; `operate` satisfies `tell` (`scopeSatisfies`, `access-tokens.ts:157-160`).
- **Overdeck connector** — the Node process a self-hosted bot runs (`pan mcp connector serve`, built by W-CONN2). It pairs once with one machine and then reaches it through a link-mode secure channel.
- **Connector credential** — a new `kind: 'connector'` access-token record bound to the connector's link public key (`connectorKey`, 64 lowercase hex) and its directory client id (`clientId`, a UUID v4). It authenticates only inside a link-mode channel whose proved remote key equals `connectorKey`.
- **Secure channel** — the Noise channel on the dashboard port (`src/dashboard/server/channel-listener.ts`). A request that arrived through one carries a `ChannelMarker` `{ mode, remoteKeyHex, pairingId }` (`packages/anywhere-channel/src/initiator.ts:72-82`), read with `channelOfRequest` (`src/dashboard/server/channel-peer.ts:25`).
- **Link mode / pairing mode** — a link-mode (Noise IK) channel proves a pinned key; a pairing-mode (Noise XXpsk0) channel proves knowledge of a one-time `odp_` code. The handshake of a pairing channel consumes the code (`takePairingById`, `pairing-credentials.ts:91`).
- **Pairing code** — an `odp_<64 hex>` value from `issuePairingCredential()` (`src/dashboard/server/pairing-credentials.ts:66`), in memory only, single use, 10-minute TTL. The same code can pair a browser (`POST /api/pairing/exchange`), a machine (`POST /api/machines/exchange`) or a phone (`POST /api/phones/exchange`).
- **pairingId** — 32 hex characters derived from a code with `pairingSecrets(nodeCrypto, code).pairingId` (`packages/anywhere-channel/src/noise.ts:150-154`). A pairing-mode channel's marker carries it.
- **Pairing intent** — new here: the in-memory note `{ name, scopes, expiresAt }` that says "this pairingId was issued for a connector, with these scopes". Stored by pairingId in `src/dashboard/server/connector-pairing.ts`.
- **Connector pairing string** — new here: `overdeck-connector:/pair#v=1&e=<environmentId>&k=<machineKeyHex>&c=<odp_code>`. The operator pastes it into the bot's shell for `pan mcp connector pair`.
- **Root credential** — the internal token or the root session cookie (`DashboardCredential` kinds `internal-token` and `root-session`). An `admin`-scoped `token` or `device` is not root.
- **Route-scope table** — `ROUTE_SCOPES` in `src/dashboard/server/route-scopes.ts`. An unlisted `METHOD path` needs `admin`.
- **No-loss matrix** — `tests/unit/lib/overdeck/no-loss-matrix.ts`; every HTTP route in a top-level `src/dashboard/server/routes/*.ts` file needs a row, and `src/dashboard/server/__tests__/route-scopes.test.ts` fails when a route-scope row has no matrix row.

## Requirements

### Functional

- **FR-1 Connector record.** The registry accepts `kind: 'connector'` records that carry exactly `connectorKey` (64 lowercase hex) and `clientId` (UUID v4), and no machine, phone, push or agent field. `createAccessToken` mints one only with scopes from `CONNECTOR_SCOPE_CHOICES = ['read:state', 'read:conversations', 'tell', 'operate', 'approve']`.
- **FR-2 Channel-only credential.** A connector record resolves to the credential `{ kind: 'connector', tokenId, clientId, connectorKey, scopes }` only from `Authorization: Bearer` inside a link-mode channel whose `remoteKeyHex` equals `connectorKey`. It resolves to `null` on a plain socket, in a pairing or approval channel, and in a link channel from another key.
- **FR-3 Chosen scopes only.** The credential's scopes are the record's scopes filtered to `CONNECTOR_SCOPE_CHOICES`, so it never carries `admin`, `forward`, `read:settings`, `read:costs` or `read:events`.
- **FR-4 Handshake pin.** A link-mode handshake from an active connector's key is admitted (`findActiveChannelTokenByKey` returns the connector record).
- **FR-5 Pairing intents.** `POST /api/connectors/pairing` (root only) issues a pairing code, stores the intent `{ name, scopes, expiresAt }` by its pairingId for 10 minutes, and returns `{ pairingString, expiresAt }`.
- **FR-6 Exchange.** `POST /api/connectors/exchange`, reachable only through a pairing-mode channel, takes the intent of `channel.pairingId`, refuses a channel without one (403 `not-a-connector-code`), refuses a key already bound (409 `link-key-in-use`), mints the connector record with the intent's name and scopes, revokes an older active connector with the same `clientId`, and returns `{ v: 1, token, tokenId, scopes, descriptor }` with `Cache-Control: no-store`.
- **FR-7 List and revoke.** `GET /api/connectors` (root only) lists active connectors without key material or hashes. `DELETE /api/connectors/:id` (root only) revokes one and closes its channels and connections at once. `DELETE /api/connectors/self` lets a connector revoke itself.
- **FR-8 Cross-refusal.** A code issued for a connector is refused by `POST /api/pairing/exchange`, `POST /api/machines/exchange` and `POST /api/phones/exchange` with 403 `{ code: 'connector-code' }`. The browser exchange refuses it before consuming it.
- **FR-9 Revocation reaches live sockets.** Revoking a connector record, by any process, closes its channels (through `registerRevocationClosers`) and its `/ws/rpc` and SSE connections (through `revocableCredentialId`).
- **FR-10 Capability.** `GET /api/environment` reports `capabilities.connector: true`; a descriptor without the field still decodes.
- **FR-11 Docs.** `docs/DASHBOARD-AUTH.md` and `docs/ANYWHERE-ARCHITECTURE.md` describe the connector kind, its routes, the cross-refusal and the downgrade cost.

### Non-functional

- **NFR-1 No secret in logs.** No activity entry, log line or error message contains a token, a pairing code or a pairing string. Entries name the connector, its `tokenId` and `clientId` only.
- **NFR-2 Async only.** No `execSync`, `spawnSync`, `execFileSync` or new `*Sync` function (repo rules `no-execsync-server`, `prefer-async`).
- **NFR-3 Fake timers.** The intent TTL test uses `vi.useFakeTimers()` and `vi.advanceTimersByTime()` (or `vi.setSystemTime`), never a real wait (repo rule `fake-timers-for-retry-tests`).
- **NFR-4 File size.** New modules stay under 600 lines (`connector-pairing.ts` under 120, `routes/connectors.ts` under 300). `src/lib/access-tokens.ts` grows by at most 45 lines. No file-size allowlist row is raised; agents cannot raise one.
- **NFR-5 Effect boundary.** No new exported Effect wrapper around Promise or sync code; `npm run lint:effect-facades` must not rise. Route handlers follow `phones.ts`: an exported async `handle…` function plus `HttpRouter.add` with `Effect.promise`.
- **NFR-6 Import graph.** `src/lib/access-token-records.ts` stays a leaf. `connector-pairing.ts` imports only `pairing-credentials.ts`, `@overdeck/anywhere-channel`, `@overdeck/contracts`, `environment-identity.ts`, `machine-key.ts` and the scope type; `npm run lint:circular` stays clean.
- **NFR-7 Every new HTTP route** lives in a top-level `src/dashboard/server/routes/` file, has a no-loss row, and has a route-scope row when a non-root credential may call it.

## Decisions

- **D-1 Record fields.** Add `connectorKey?: string` to `AccessTokenRecord` and `CreateAccessTokenInput`. Reuse the existing `clientId` field for the connector's client id (same format, same meaning as a phone's). Kind `connector` requires both; every other kind refuses `connectorKey`; `clientId` stays refused on `device`, `token` and `machine`.
- **D-2 Constants.** `CONNECTOR_SCOPE_CHOICES` and `BOT_DEFAULT_SCOPES = ['read:state', 'read:conversations', 'tell']` (epic D-4) are exported from `src/lib/access-tokens.ts` next to `PHONE_TOKEN_SCOPES`. `createAccessToken` refuses a connector input whose scopes leave that set with the message `'A connector token carries only read:state, read:conversations, tell, operate and approve (PAN-4927 D-4)'`.
- **D-3 Pairing string lives in contracts.** `packages/contracts/src/connector-pairing.ts` exports `CONNECTOR_PAIR_SCHEME = "overdeck-connector"`, `CONNECTOR_PAIR_LINK_VERSION = 1`, `CONNECTOR_PAIR_LINK_PREFIX = "overdeck-connector:/pair#"`, `buildConnectorPairLink(input)` and `parseConnectorPairLink(text)`, reusing the three regexes from `./phone-pairing`. Why: W-CONN2 (in `src/lib/mcp/connector/`) parses the string and cannot import from `src/dashboard/server/`; the phone link already sets this pattern.
- **D-4 The resolved credential carries `connectorKey`**, like the phone credential carries `phoneKey`. The self-revoke handler uses it to close the channel.
- **D-5 Defense in depth on scopes.** The resolver filters `record.scopes` to `CONNECTOR_SCOPE_CHOICES`, so a hand-edited record with `admin` still grants nothing outside the set (FR-3). `createAccessToken` is the first check; the resolver is the second.
- **D-6 Intent store.** A module-level `Map<pairingId, { name, scopes, expiresAt }>` in `src/dashboard/server/connector-pairing.ts`. Entries are pruned on every issue once they are older than `expiresAt + PAIRING_CREDENTIAL_TTL_MS` (the same rule as `pairing-credentials.ts:60-64`). A dashboard restart drops intents and pairing codes together, which is consistent: neither survives.
- **D-7 Intent lookup rules.** `takeConnectorIntent(pairingId)` removes the entry on every call and returns the intent only when it has not expired; otherwise `null`. `hasConnectorIntent(pairingId)` is read-only and returns `true` for any stored entry, expired or not, because a code issued for a connector must never pair anything else even after the intent lapses. `isConnectorCode(code)` derives the pairingId with `pairingSecrets(nodeCrypto, code).pairingId` and returns `hasConnectorIntent(pairingId)`.
- **D-8 Exchange order.** `handleConnectorsExchange(bodyText, channel)`: (1) 403 unless `channel?.mode === 'pairing'`; (2) `takeConnectorIntent(channel.pairingId ?? '')` — the intent is consumed before the body is read, so any outcome burns it (the handshake already burned the code); null → 403 `{ error: 'this pairing code was not issued for an Overdeck connector', code: 'not-a-connector-code' }`; (3) parse `{ v: 1, clientId, label }` → 400 on error; (4) 409 `link-key-in-use` when `findActiveChannelTokenByKey(channel.remoteKeyHex) !== null`; (5) mint; (6) revoke older active connectors with the same `clientId`; (7) activity entry; (8) respond.
- **D-9 Record name and label.** The record's `name` is the intent's `name` (what the operator typed). The connector's `label` (1-64 characters, normally its hostname) is validated and written only to the activity entry details.
- **D-10 Cross-refusal order and counting.** `POST /api/pairing/exchange` checks `isConnectorCode(credential)` after body validation and before `consumePairingCredential`, so a code pasted into a browser by mistake still pairs the connector. That refusal calls `recordPairingExchangeFailure()` (10 failures in 60 s already lock exchanges; one mistake costs nothing). `POST /api/machines/exchange` and `POST /api/phones/exchange` check `channel.pairingId !== null && hasConnectorIntent(channel.pairingId)` right after their pairing-mode check and before parsing the body; the handshake has already consumed the code there, so the operator issues a new one. All three answer 403 `{ error: 'this pairing code is for an Overdeck connector; run pan mcp connector pair with it', code: 'connector-code' }`.
- **D-11 Root-only routes.** `POST /api/connectors/pairing`, `GET /api/connectors` and `DELETE /api/connectors/:id` (non-`self`) accept only `internal-token` or `root-session`; any other credential gets 403 `{ error: 'only the internal token or the root session can manage connectors' }`. No route-scope row is added for them, so the gate already demands `admin`. POST and DELETE go through `rejectUnsafeDashboardMutationRequest` first (CSRF for the cookie); GET through `rejectUnauthorizedDashboardRequest`. Every response has `Cache-Control: no-store`.
- **D-12 Pairing route body.** `{ name: string (trimmed, 1-64 characters), scopes?: string[] }`. Missing `scopes` means `BOT_DEFAULT_SCOPES`. Present `scopes` must be a non-empty array of distinct values from `CONNECTOR_SCOPE_CHOICES`; anything else (including `admin` or `forward`) is 400 naming the first bad value.
- **D-13 Self revoke.** Route-scope row `{ method: 'DELETE', path: '/api/connectors/self', scope: 'read:state' }` (every connector holds `read:state`, see D-14). The handler requires `credential?.kind === 'connector'` (403 `{ error: 'only a paired connector may revoke itself' }`), revokes its `tokenId`, calls `closeDeviceConnections(tokenId)` and `closeChannelsForPeer(connectorKey)`.
- **D-14 Minimum scope.** Because `DELETE /api/connectors/self` needs `read:state`, a connector without `read:state` could not log out. The pairing route therefore always adds `read:state` to the chosen scopes (the W-BOT1 dialog shows it as always on). The stored intent carries the final set.
- **D-15 List shape.** `GET /api/connectors` → `{ connectors: [{ id, name, scopes, clientId, createdAt, lastUsedAt }] }`, active records only, read fresh with `listAccessTokens()`. No `connectorKey`, no hash (parity with `GET /api/devices`).
- **D-16 Revoke response.** `DELETE /api/connectors/:id` → 404 `{ error: 'no connector with id <id>' }` when no connector record has that id; else revoke, `closeDeviceConnections(id)`, `closeChannelsForPeer(connectorKey)`, activity entry, `{ ok: true }`.
- **D-17 Capability flag.** `EnvironmentCapabilities.connector: Schema.optional(Schema.Boolean)`; `buildEnvironmentDescriptor` sets `connector: true`. It is set in the same item that adds the exchange route, so a server never claims it without the route.
- **D-18 Link fence.** No change. `linkActorFence` fences only `machine` credentials (Fact 8), so a connector acts as the operator within its own scopes, and fleet routes refuse it as a channel caller (Fact 20).
- **D-19 Downgrade cost accepted.** A `connector` record makes an older Overdeck read the registry as corrupt and refuse every token until the record is removed, exactly as `machine` and `phone` records do (epic H-3). Documented in `docs/DASHBOARD-AUTH.md`.

## Acceptance criteria

- **AC-1 (W-1):** `createAccessToken` mints a `connector` record with chosen scopes and refuses `admin`, `forward`, `read:costs`, `read:settings` and `read:events`; a malformed connector record makes the registry corrupt; `findActiveChannelTokenByKey` returns an active connector by its key.
- **AC-2 (W-2):** a connector bearer resolves only inside a link channel from its `connectorKey`, with scopes filtered to `CONNECTOR_SCOPE_CHOICES`; it skips CSRF; revocation closes its channels and connections.
- **AC-3 (W-3):** `buildConnectorPairLink` and `parseConnectorPairLink` round-trip, and neither the phone parser nor the connector parser accepts the other's string.
- **AC-4 (W-4):** an issued intent is taken once, expires after 10 minutes, and `isConnectorCode` recognizes its code.
- **AC-5 (W-5):** the pairing, list and revoke routes accept only root credentials; revoke closes live channels at once; `DELETE /api/connectors/self` revokes only a connector's own record.
- **AC-6 (W-6):** the exchange mints a connector credential with the intent's scopes only through a pairing channel holding a connector intent; the descriptor reports `capabilities.connector: true`.
- **AC-7 (W-7):** a connector pairing code is refused as a browser, machine or phone pairing code with 403 `connector-code`.
- **AC-8 (W-8):** both docs describe the connector kind, routes, cross-refusal and downgrade cost.
- Epic **AC-20** is the union of AC-2, AC-6 and AC-7.
