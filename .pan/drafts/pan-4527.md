# PAN-4527 — Re-review joins a verification worker started on the previous head

**Issue:** [PAN-4527](https://github.com/eltmon/overdeck/issues/4527)
**PR:** [#4599](https://github.com/eltmon/overdeck/pull/4599)
**Status:** delivered. This PRD records the work in PR #4599.

## Glossary

- **Verification worker**: the detached process that runs the verification gate for one issue. The
  supervisor (`src/lib/cloister/verification-worker-supervisor.ts`) keeps its state in
  `~/.overdeck/verification-workers/<issue>/state.json`. That state includes `headAnchor`, the workspace head at
  launch.
- **Join**: a second verification request for the same issue waits for the live worker's result. It does
  not start a new worker.
- **Launch head**: the head anchor the worker started on.
- **Sync merge**: the merge of `origin/<target>` that review verification makes into the workspace before it
  runs the gates (`syncTargetBranch`). Its first parent is the launch head and its second parent is on
  `origin/<target>`. A fast-forward to a commit on `origin/<target>` also counts.
- **Same-head rule**: the result of comparing a later head with the launch head. It is `same` (unchanged),
  `synced` (only the worker's own sync merge), `moved` (any other commit), or `unknown` (git could not
  answer). `unknown` is treated as `moved`.
- **CI tests mode**: `verification.tests: ci`. In this mode the `test` gate reads the CI test job's verdict for
  a head (`readLatestCiTestResult(workspacePath, head8)`) and does not run tests locally.

## Root cause

1. `src/lib/cloister/verification-worker-supervisor.ts`, line 178 on main, in `runSupervisedVerificationInternal`:
   `const sameHead = options.syncTargetBranch !== false || existing.headAnchor === headAnchor;`
   Review verification never sets `syncTargetBranch: false`, so `sameHead` was always true. A request made
   after the agent pushed a fix therefore joined the worker that was still verifying the previous head.
2. `src/lib/cloister/verification-runner.ts`, ~lines 578-590 on main: `ciTestRed` read the CI verdict for the
   `headShort` captured at launch. A joined worker therefore failed the new head with the old head's red CI
   result. This was seen on PAN-4498 on 2026-10-04.

## Requirements

- **FR-1**: One shared function classifies a later head against a launch head as same, synced, moved or
  unknown. It works per repo for polyrepo composite anchors.
- **FR-2**: The supervisor joins a live review-verification worker only when the request's head is the
  worker's same or synced head. Otherwise it kills the worker and starts a fresh one.
- **FR-3**: A worker whose only HEAD change is its own sync merge is still joined.
- **FR-4**: In CI tests mode, the runner reads the CI verdict for the head it verifies now. That is the
  launch head when HEAD is same or synced; otherwise it is the current head.
- **FR-5**: `docs/PIPELINE-GATES.md` states when a re-review joins a live worker and when it restarts it.

## Acceptance criteria

1. Given a live review-verification worker launched on head A, when a request arrives with the branch tip at a
   new agent commit B, then the supervisor kills the A worker and starts a fresh one on B (supervisor join test).
2. Given a live review-verification worker whose only HEAD change is its own sync merge, when a duplicate
   request arrives, then it joins (supervisor join test).
3. Given CI recorded `failed` for head A and `passed` for head B, when verification of B reaches the ci-mode
   `test` gate, then `test` passes. A red head that only has a real sync merge on top still fails `test`
   (runner CI test).
4. Given the verification-head test repos, when the classifier runs, then an unchanged head is `same`, the sync
   merge and a fast-forward are `synced`, and agent commits are `moved`.
5. `docs/PIPELINE-GATES.md` contains the "Same head" subsection, which states both the join case and the restart
   case.

## Critique response

Round 1 critique: `.pan/drafts/pan-4527-critique.md`. The test for each finding is whether it is worse than before
PAN-4527, when every review request joined any live worker and used the launch head's CI verdict. PAN-4531
([#4608](https://github.com/eltmon/overdeck/pull/4608)) builds on this PR and merges next. Where it closes a
finding, the response says so.

### In-flight requests bypass the head check

Accepted, and closed by PAN-4531 rather than here. PAN-4527 fixes the cross-process join that the PAN-4498
incident showed ("Joining live verification worker"). A second in-process request that the
`requestReviewPipeline` guard answers `already-running` still rides the running request, as it did before.
PAN-4531 makes that safe. Its decided-stop check runs before each gate and after the last one. It finds an agent
commit, ends the run as `superseded`, and `runSupervisedVerificationInternal` restarts on the new head (bounded).
So the running request's push and review continuation carry the new head's verdict. One window remains: a commit
that lands after the final post-gate check and before the push. Merge verification re-verifies the exact head
before merge, so that window can delay a merge but cannot merge an unverified head.

### Commit topology cannot identify the worker's sync

Rejected, with reasons. An agent-made merge whose first parent is the launch head and whose second parent is on
`origin/<target>` is, for a clean merge, the same tree that the worker's own sync verifies. A different second
parent differs only by target-branch commits that main already verified. The one case the shape cannot catch is a
merge whose resolution adds new edits. Merge verification (`merge-verify`, exact anchor, never synced) re-verifies
that head before merge, so it cannot merge unverified. Recording the worker's own sync transition would need a
mid-run state write. Decision D1 rejected that, so the classifier needs no writer.

### A moved head inherits stale local gates

Accepted, and closed by PAN-4531. In PAN-4527 alone, a commit B during the gates gives a verdict from A's local
gates and B's CI verdict, labelled B. Before PAN-4527 it was A's gates and A's CI verdict, labelled B, which was
worse. PAN-4531 ends such a run as `superseded` before the next gate or after the last gate (failed or passed),
and the supervisor re-verifies B from the start. PAN-4531 also rewrites this PR's runner test, so that B is
committed before verification starts.

### Polyrepo CI lookup uses the wrapper head

Accepted as an existing bug, filed as [PAN-4624](https://github.com/eltmon/overdeck/issues/4624). On main, the
launch `headShort` already comes from `readWorkspaceHeadShort(workspacePath)` (`verification-runner.ts`, ~line 309),
which is the wrapper repo in a polyrepo. So polyrepo ci-mode CI lookups miss the member head with or without this
change. `resolveVerifiedHeadShort` keeps that lookup unchanged, and PAN-4624 fixes both call sites together.

### Partial snapshots can be classified as same

Fixed. `classifyVerificationHead` now returns `unknown` when either anchor lacks any of the expected repo roots,
before the equality shortcut. Two equal partial anchors are no longer `same`. New test: "a polyrepo anchor missing
a member repo is unknown, even when both sides match" (`verification-head.test.ts`). A monorepo anchor is a plain
sha mapped to its single root, so it is unaffected.

### Unresolved after two critic rounds

- Merge shape cannot prove sync ownership
