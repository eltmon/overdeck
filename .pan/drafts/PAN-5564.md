# PAN-5564: Make the changes-view DiffEditor mock mount synchronously

**Issue:** [PAN-5564](https://github.com/eltmon/overdeck/issues/5564)
**Type:** flaky-test fix. The only file this change touches is a test.

## Glossary

- **Changes view.** The `ChangesView` component in `src/dashboard/frontend/src/components/explorer/code/ChangesView.tsx`. It shows a Monaco diff of the file's committed (HEAD) text against the live draft. `CodePane` shows it when the operator picks the **Changes** tab.
- **DiffEditor mock.** The `vi.mock('@monaco-editor/react', …)` factory in `src/dashboard/frontend/src/components/explorer/code/__tests__/changes-view.test.tsx` at lines 50-96. It replaces Monaco's `DiffEditor` with a `<div data-testid="diff">` that contains a `<textarea data-testid="diff-modified">`.
- **onMount listener registration.** `ChangesView.handleMount` (lines 81-99) calls `editor.onDidChangeModelContent(...)` at line 84. In the mock, that call pushes a listener into `listeners.current`. The mock's `diff-modified` `onChange` calls every listener in that list. With an empty list, an edit in the diff never reaches the draft.
- **Passive effect.** A `useEffect` callback. React runs it after the commit and does not guarantee when. When an update happens outside `act` (here, after the HEAD read promise resolves), React schedules passive effects through its scheduler, so they can run after a `MutationObserver` microtask.
- **Layout effect.** A `useLayoutEffect` callback. React runs it synchronously during commit, before the browser (or happy-dom) can notify any `MutationObserver` of the DOM change.
- **findBy query.** Testing Library's `screen.findByTestId`. It wraps `waitFor` and resolves as soon as the element exists in the DOM. Its `MutationObserver` callback is one way it detects that the element exists.

## Problem

CI run 44414111727 (job `test-e2e`, main at `fd442d46e4`, a docs-only merge in PR #5559) failed with:

```
Changes view > goes back to the plain editor with the draft and the cursor preserved
AssertionError: expected 'my draft\n' to be 'edited in diff\n'   (changes-view.test.tsx:154)
```

The next main run (`0558b4ab73`, run 44417949004) passed the same code. The failure depends on timing.

### Root cause (verified against the code at 0558b4ab739)

1. `openChanges()` (test lines 120-128) clicks the **Changes** tab, then returns `screen.findByTestId('diff')`.
2. The click renders `ChangesView` in its `loading` state. `ChangesView` (lines 64-79) calls `readFile(rootId, path, 'HEAD')`. The mocked `readFile` resolves a promise, and `setFetched({status:'ready'})` runs **outside `act`**.
3. That update renders the DiffEditor mock. The `diff` element is now in the DOM. The mock's `props.onMount(...)` call sits in a passive effect, `React.useEffect(() => { … }, [])` at test line 63. Because the update is outside `act`, React may run that effect *after* the findBy query's `MutationObserver` microtask resolves the promise.
4. If it does, `openChanges()` returns before `handleMount` has run. `listeners.current` is still empty, `diffRef`/`onDiffMount` have not run, and `setPosition` has not been called.
5. Three assertions are exposed:
   - Test 1, line 140: `expect(mocks.diffSetPosition).toHaveBeenCalledWith(...)` runs right after `openChanges()`. It fails if the mount has not happened.
   - Test 2, line 146: `fireEvent.change(diff-modified)` iterates an empty listener list, so the draft keeps `'my draft\n'`.
   - Test 3, line 154: this is the CI failure. The same empty listener list leaves the draft as `'my draft\n'`. Line 156 can also fail, because `diffEditor.current` was never set, so `carriedPosition` is `null` and the plain editor's `setPosition` is not called.

### Why the plain-editor mock is not part of this race

The `MonacoCodeEditor` mock (test lines 28-48) also calls `onMount` from a passive effect, after the first async file read. But `openChanges()` next calls `fireEvent.change(monaco, 'my draft\n')` (line 123). Testing Library wraps that call in `act`. The resulting `useCodePaneSave.onChange` (`useCodePaneSave.ts`, line 153: `drafts.edited(key, text)`) updates the Zustand `useCodeDrafts` store. `CodePane` subscribes to that store at line 88 (`const text = useCodeDrafts((s) => s.drafts[key]?.text)`), so React re-renders inside `act`. Before React renders, it flushes pending passive effects, so the plain editor's `onMount` → `setEditor` runs before the **Changes** click.

Switching back to **File** (line 152) is also a `fireEvent` inside `act`. The plain editor renders and its effects flush synchronously. Only the DiffEditor mount happens after an un-`act`ed promise with no `act`-wrapped interaction before the assertions, so only the DiffEditor mock needs the fix.

## Decision

**Change the DiffEditor mock to call `props.onMount` from `React.useLayoutEffect` instead of `React.useEffect`.**

The issue offers two options. This one wins on these grounds:

- A layout effect runs synchronously in the same commit that inserts the `diff` element. By the time any `MutationObserver` or `waitFor` poll sees the element, `handleMount` has run. The race is gone; it is not just made less likely.
- It fixes every caller of `openChanges()` and the second `findByTestId('diff')` at line 164 without touching the tests' bodies.
- The other option, `await waitFor(() => expect(mocks.diffSetPosition).toHaveBeenCalled())` in `openChanges()`, depends on `handleMount`'s *conditional* `setPosition` (`ChangesView.tsx` lines 92-96, `if (position)`). If a future change makes `initialPosition` null, `openChanges()` would time out with an error that does not explain the cause. It also adds a polling wait.
- The real `@monaco-editor/react` calls `onMount` asynchronously after the editor loads. `ChangesView` must already handle a mount at any time, so a synchronous mount in the mock does not hide a product behavior that the tests rely on.

No product source changes. No changelog entry: this change is test-only and not user-facing (`changelog.d/README.md` covers user-facing changes only).
