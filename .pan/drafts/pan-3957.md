## 1. Glossary

| Term | Meaning |
| --- | --- |
| **Fact** (curated memory) | One durable, human-reviewable statement stored as one markdown file with YAML frontmatter. Examples: a working agreement ("make routine reversible calls yourself"), an operator correction, or a non-obvious project truth ("`schema.ts` is `panopticon.db`, not `overdeck.db`"). This issue adds facts. |
| **Observation memory** | The existing, automatically extracted session log substrate: `~/.overdeck/memory/{projectId}/{workspaceId}/{observations,pending,status.json,summaries,archive}` plus the FTS index (`docs/WORKSPACES-AND-PROJECTS.md:287-303`). The 12 existing `pan memory` verbs (`search`, `status`, `timeline`, `read`, `reset`, `summary`, `doctor`, `backfill`, `pin`, `unpin`, `pins`, `config`) operate on it. **Out of scope** here (issue: "Out of scope"). |
| **Project store** | The directory of project-scoped facts: `<planHome>/.overdeck/memory/`. It is flat, one file per fact, and the filename stem is the fact id. |
| **Operator store** | The directory of user-scoped facts: `~/.overdeck/context/memory/`. It is per machine and never committed. |
| **Plan home** | The checkout that holds a project's committed Overdeck artifacts: `resolvePlanHome(root)` in `src/lib/pan-dir/paths.ts:46`. For a single repository it is the checkout itself. For a polyrepo it is the `pan_records.repo` sub-repo. |
| **Primary checkout** | `ProjectConfig.path` from `~/.overdeck/projects.yaml`: the operator's main clone, not a `workspaces/feature-*` worktree. `findProjectByPath(workspace).path` resolves it (`src/lib/projects.ts:859`, synchronous). |
| **Memory index** | The rendered, budgeted list of active facts (one line per fact) that is injected at launch. It is **never stored**. It is derived from frontmatter every launch, and it takes over the job of Claude's `MEMORY.md`. |
| **Launch composition** | The Overdeck-owned context artifact built for one managed session. It comes from `renderManagedLaunchContext` (`src/lib/context-layers/materialize.ts:29`) or, for Muse, `materializeMuseContext` (`src/lib/runtimes/muse-context.ts:12`). |
| **Harness-native memory** | A memory store owned by the harness itself. Only Claude Code's auto-memory (`~/.claude/projects/<slug>/memory/`) is active on this host (see header facts). |
| **Claude project slug** | Claude Code's directory name for a cwd: every non-alphanumeric character becomes `-`. `/home/eltmon/Projects/overdeck` becomes `-home-eltmon-Projects-overdeck`, and `/home/eltmon/.paperclip/...` becomes `-home-eltmon--paperclip-...` (both verified in `~/.claude/projects/`). |
| **Machine-specific path** | An absolute path into one user's home directory: text matching `MACHINE_PATH_PATTERN` (D16). It cannot be true on another machine, so it never belongs in the project store. |
| **Pipeline runtime path** | A path the pipeline gates treat as Overdeck-owned scratch rather than work product: `isOverdeckWorkspaceRuntimePath` (`src/lib/state-plane.ts:77`) says yes for everything under `.pan/` and `.overdeck/`. D17 carves `.overdeck/memory/` out. |
| **Review marker** | The frontmatter key `review: [<flag>, …]`. A fact that carries a non-empty marker is listed by `pan memory list --review` but is excluded from the memory index. |
| **Active fact** | A parseable fact file with no review marker. |

## 2. Problem (current state, verified)

1. **Every harness keeps its own memory, and only Claude's is live.** Claude Code writes
   `~/.claude/projects/<slug>/memory/*.md` and preloads `MEMORY.md` (first ~200 lines / 25 KB) into every
   session (`docs/research/claude-code-memory-integration.md:8`). Codex managed sessions run with a
   per-agent `CODEX_HOME=~/.overdeck/agents/<id>/codex-home-v2` (`src/lib/runtimes/codex.ts:592`), so
   they never see any native store. Pi, OMP and Kimi have none. A Codex or Kimi agent on the same issue
   learns nothing from the 245 facts the operator's Claude sessions have built up.
2. **Overdeck already has a memory store that is fragmented even for Claude.** Claude's store follows the
   cwd, and the host has 51 stores, several for single workspaces (for example
   `-home-eltmon-Projects-myn-workspaces-feature-min-1039`). Facts do not travel to another machine or a
   teammate, and the project cannot review them.
3. **The context layers explicitly exclude it.** `docs/CONTEXT-LAYERS.md:361-362` says: "Claude auto
   memory is another input, normally under `~/.claude/projects/<project>/memory/`; it is not a
   context-layer source."
4. **The seams already exist.** Every managed launch composes one Overdeck-owned artifact:
   - `renderManagedLaunchContext` (`materialize.ts:29-47`, anchor `if (project) sections.push(renderProjectLayer(project.path, harness));`)
     is used by `claudeSystemPromptFiles` (`src/lib/context-layers/launch-sources.ts:10`, via
     `materializeSharedManagedLaunchContext` at line 31) for claude-code,
     codex, ohmypi and kimi-code, and by `materializeAcpContextFile` (`src/lib/acp/context.ts:11`) for acp
     and opencode.
   - `materializeMuseContext` (`src/lib/runtimes/muse-context.ts:14-16`, anchor `if (project) sections.push(renderProjectLayer(project.path, 'muse'));`) builds the same sections separately for muse.
   - The dashboard Context page preview composes its own copy in `previewForHarness`
     (`src/dashboard/server/routes/context.ts:398-405`). `docs/CONTEXT-LAYERS.md` promises that "the
     preview always matches what ships".
5. **The frontmatter shape is already indexed.** `parseConcept` (`src/lib/memory/injection.ts:610-623`)
   reads `id` / `type` / `description` (falling back to `title`) from OKF concept files for the prompt-time
   knowledge index. Facts that use the same keys are OKF-compatible.
6. **The workspace layer has a dead memory slot.** `assembleWorkspaceContext` accepts `memoryContext`
   (`src/lib/context-layers/assemble.ts:75`, `:95`), but no production caller passes it
   (`grep -rn "memoryContext:" src --include=*.ts` finds only tests). It is frozen at workspace
   creation, so it is the wrong carrier for facts that change. This PRD does not use it.
7. **The pipeline treats `.overdeck/` as disposable, so a fact could be lost silently.** Three
   predicates on `origin/main` decide that nothing under `.overdeck/` is work product:
   - `isOverdeckWorkspaceRuntimePath` (`src/lib/state-plane.ts:77-81`) feeds `isOverdeckOwnedOnlyStatus`
     (line 103), which `pan done`'s dirty preflight (`src/lib/work/done-preflight.ts:59`, run with
     `git status --porcelain -uall`) and the workspace merge-ops gate (`routes/workspaces/merge-ops.ts:74`)
     use. An uncommitted `.overdeck/memory/<id>.md` passes `pan done`, the PR opens without it, and the
     fact is gone when the workspace is closed out.
   - `AUTO_COMMIT_EXCLUDED_PATHS` (`src/lib/cloister/merge-agent.ts:42-55`, entry `'.overdeck/'`) drives
     the pre-sync auto-commit, which runs `git add -A` then `git reset HEAD -- <excluded paths>` (line 131),
     so sync-main never commits a fact. The entry exists for machine-local config copied into
     workspaces (PAN-1899), and myn and krux do not ignore `.overdeck/continue.json`, so the entry
     itself must stay.
   - `ARTIFACT_PATH_PREFIXES` (`src/lib/close-out.ts:32`) makes `isBranchMerged` read a branch whose only
     unmerged diff is a fact as merged (the code-diff checks at lines 147 and 195, and the post-merge
     commit check at line 106), so close-out can reap a fact-only branch. PAN-4577's import produces
     exactly such branches.

## 3. Decisions (made here; do not re-decide during implementation)

- **D1: Store paths.** Project store: `join(resolvePlanHome(root), '.overdeck', 'memory')`. Operator
  store: `join(getOverdeckHome(), 'context', 'memory')`. Both are flat. Facts use the plan home, not
  `projectContextDir` (`layers.ts:60`, which uses the bare `projectRoot`). The reason: a polyrepo
  wrapper ignores `.overdeck/` wholesale (`src/lib/workspace-manager/create.ts:89-92`, anchor
  `runtimeEntries.push('.overdeck/')`), and the plan home is the one tracked repository Overdeck already
  picks for polyrepos. For a single repository both resolve to the same directory.
- **D2: File format** (OKF-compatible, Claude-importable). Filename `<id>.md`, where
  `id` matches `/^[a-z0-9][a-z0-9-]{0,79}$/`. Frontmatter:

  ```yaml
  ---
  type: feedback            # required: feedback | project | reference | user
  title: Be decisive        # optional; defaults to the id with dashes as spaces, first letter upper-cased
  description: Make routine reversible calls yourself; ask only for irreversible or operator-owned ones.
                            # required, one line, <= 200 chars; this is the index line
  tags: [workflow]          # optional string array
  updated: 2026-09-23       # optional YYYY-MM-DD; add/edit set it; sort key
  source: claude:6c30e00a-54f1-4a0e-9d4b-1c2f3e4d5a6b   # optional provenance
  review: [unindexed]       # optional; non-empty means excluded from the index
  ---
  <body: the fact, then **Why:** and **How to apply:** lines, free markdown>
  ```

  The type `user` is valid only in the operator store. A `user` file in a project store is a problem
  (reported, skipped). A project-store fact containing a machine-specific path is also a problem (D16). Files named `README.md`, files starting with `.`, and non-`.md` files are ignored,
  so a human README may sit in the directory. Subdirectories are ignored.
- **D3: What launch reads.** The project section reads the **primary checkout's** project store
  (`findProjectByPath(workspace).path`), the same source the project layer already uses
  (`materialize.ts:31-32`). This includes uncommitted files in that working tree. A fact added in a
  workspace reaches other agents when its branch merges and the primary checkout pulls. The primary
  checkout can be on a non-main branch (it was on `feature/pan-3920` on 2026-09-23); that is accepted,
  matching the project layer. On another machine, a fact arrives with a normal `git pull` of that
  machine's primary checkout; nothing else syncs facts (operator comment 2026-10-20). A consequence, stated so nobody has to ask: a fact an agent adds **inside a
  workspace** is not in the index of that agent's own next session either. It appears in every session's
  index once the branch merges and the primary checkout pulls. The agent can still read it with
  `pan memory show --here <id>` (D4).
- **D4: Reads and writes resolve differently.**
  - **Reads** (`pan memory show`, `pan memory list`, and the W6 fact matcher) default to the **primary
    checkout's** project store: `projectMemoryDir(findProjectByPath(process.cwd()).path)`. That is the
    same store the index was rendered from (D3), so every `pan memory show <id>` hint an agent saw at
    launch resolves. `--here` reads the cwd checkout's store instead (a workspace's branch snapshot).
  - **Writes** (`pan memory add|edit|retire`) target the project store of the checkout that owns
    `process.cwd()` (`resolvePlanHome(process.cwd())` is depth-idempotent, `paths.ts:38-45`).
  - For both, `--project <key>` means that project's primary checkout and `--user` means the operator
    store. `--here` cannot be combined with `--project` or `--user`. If the cwd is outside a registered
    project and neither `--project` nor `--user` is given, the command refuses. Writes are **never
    committed** by Overdeck, and the command prints the path to commit.
  - `pan memory edit` reads the fact from the store it writes to (the cwd checkout). In a workspace whose
    branch predates the fact, edit fails with `no fact "<id>"`; the fix is to merge main into the branch
    or to edit from the primary checkout.
- **D5: No stored index.** Nothing writes a `MEMORY.md` or index file. The index is rendered at launch
  from frontmatter (CLAUDE.md: "Overdeck stores no status it can derive"). Claude's store shows why:
  160 of 223 files are indexed.
- **D6: The index format and budget.** One line per active fact: `- <type>/<id>: <description>`. Order by
  type (`feedback`, `project`, `reference`, `user`), then `updated` descending (missing sorts last), then
  id ascending. Budgets: project section 12,000 chars, operator section 4,000 chars, each counted on the
  rendered line list. When the next line would exceed the budget less 80 chars, stop and append
  `- … <n> more facts: run \`pan memory list\``. Bodies are never injected. An agent opens the file.
- **D7: Section text** (exact; W2 renders it):

  ```markdown
  ## Project memory

  Source: <absolute project store path> (<n> active facts, curated and committed with this repository)
  One line per fact. Open the fact (`pan memory show <id>`) before relying on its details.
  Record a new durable fact with `pan memory add`; never write harness-native memory.

  - feedback/be-decisive: Make routine reversible calls yourself; ask only for irreversible or operator-owned ones.
  ```

  The operator section is identical with the heading `## Operator memory`, the source path of the
  operator store, `(… active facts, this machine only)`, and `pan memory show --user <id>`. A store with
  zero active facts renders **no section** (not an empty heading).
- **D8: Placement in the composition.** Project memory goes after the project layer and before the
  workspace section. Operator memory goes right after project memory. Facts get no `{{#harness:X}}`
  rendering: they are harness-neutral text.
- **D9: Memory never breaks a launch.** `renderManagedMemorySections` catches every error, calls
  `console.warn('[memory] facts unavailable: <reason>')`, and returns `''`. A malformed fact file is
  skipped, never fatal.
- **D10: Secret guard.** `writeMemoryFact` refuses (`MemoryFactSensitiveError`) when
  `redactSensitiveText(serialized) !== serialized` (`src/lib/secret-redaction.ts:148`). That function
  redacts env assignments only for sensitive names (`SENSITIVE_ENV_NAME_PATTERN`, line 9), so
  `OVERDECK_RTK_ENABLED=0` passes. It also redacts labelled values (`LABELLED_SECRET_PATTERN`, line 8:
  `token: x`, `password=x`, case-insensitive), so a fact that writes `token: <value>` is refused. There
  is no override flag: rephrase the fact.
- **D11: Git ignore guard.** Before writing into a project store, `pan memory add` runs
  `git -C <planHome> check-ignore -q .overdeck/memory/<id>.md` through promisified `execFile`. Exit 0 (the
  path is ignored) means refuse, with the fix `add "!.overdeck/memory/" to <planHome>/.gitignore`. Exit 1
  means proceed. Any other exit (not a git repository) means print a yellow warning and proceed.
- **D12: `retire` deletes.** `pan memory retire <id>` unlinks the file. Git history is the archive, and
  the command prints `git -C <planHome> rm`-style guidance and the suggested commit subject
  `docs(memory): retire <id>`.
- **D13: Search.** `pan memory search <q>` (human output) prints matching facts **first** (the project
  store for the cwd or `--project`, then the operator store; at most 5 each). A fact matches when every
  whitespace-separated term of `<q>` appears case-insensitively in `id + title + description + tags +
  body`. `--json` output is **unchanged** (an array of observation hits), because
  `src/lib/compliance/status.ts` and scripts consume it. `pan memory list --query <q> --json` is the
  machine-readable fact search.
- **D14: Harness-native memory switch (phase 2).** Config `memory.harness_native_memory`, default
  `conversations`. The launcher emits `export CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` (a documented, stable
  knob: research doc line 19 and line 31) when the harness behavior's `contextLayerKind` is `claude` and
  either the mode is `off`, or the mode is `conversations` and `spawnMode !== 'conversation'`. Mode `on`
  emits nothing. The launcher never emits `unset`: a user who disabled auto-memory globally stays
  disabled. Operator conversations launch with `spawnMode: 'conversation'`
  (`src/lib/overdeck/conversation-runtime.ts:791`). Codex, Pi, OMP and Kimi need no switch (header
  facts).
- **D15: Import rules (phase 2).** These are in W9 and are listed there in full.
- **D16: Machine-specific facts stay out of the project store** (operator comment 2026-10-20). In
  `store.ts`:

  ```ts
  export const MACHINE_PATH_PATTERN = /\/home\/[^/\s]+\/|\/Users\/[^/\s]+\/|\b[A-Za-z]:\\Users\\/;
  ```

  `parseMemoryFact` with scope `project` returns the problem
  `machine-specific path "<first match>"; use ~ or a project-relative path, or keep the fact on this machine with --user`
  when `MACHINE_PATH_PATTERN` matches the title, description, any tag, or the body. Because
  `writeMemoryFact` validates by round-tripping through `parseMemoryFact` (W1 step 4), `pan memory add`
  and `edit` refuse such a fact, and a hand-written one is reported by `pan memory list` and left out of
  the index (problems are never injected). The operator store (scope `user`) accepts these paths: it is
  the per-machine home. The pattern is deliberately limited to home-directory paths. `/tmp/...`,
  `localhost:<port>` and `127.0.0.1` are often true project facts (a dev port, a scratch convention), so
  they are allowed. Local keys are already refused by D10.
- **D17: Facts survive the pipeline.** `.overdeck/memory/` is work product, not pipeline runtime. A new
  leaf helper in `src/lib/state-plane.ts`:

  ```ts
  /** PAN-3957: curated project facts are committed work product, unlike the rest of `.overdeck/`. */
  export const PROJECT_MEMORY_PATH = '.overdeck/memory';
  export function isProjectMemoryPath(relativePath: string): boolean {
    const normalized = relativePath.trim().replace(/\\/g, '/');
    return normalized === PROJECT_MEMORY_PATH || normalized.startsWith(`${PROJECT_MEMORY_PATH}/`);
  }
  ```

  It is used in three places: `isOverdeckWorkspaceRuntimePath` returns `false` for it, so `pan done`
  refuses an uncommitted fact (W12); the pre-sync auto-commit commits it (W13); `isBranchMerged` counts
  it as unmerged work (W14). The paths are relative to the repository being inspected, which for a
  polyrepo plan home is the `pan_records.repo` sub-repo (`done-preflight.ts` already checks each
  sub-repo separately).
- **D18: Scope of this issue.** PAN-3957 delivers phase 1 (W1–W8, W12–W14). Phase 2 (W9–W11: import and
  the native-memory switch) is PAN-4577, filed 2026-10-20 and blocked on this issue. Phase 1 is what
  makes the issue title true: every managed harness receives the same repo-owned index, and the bundled
  rule (W7) directs managed agents to `pan memory add` instead of harness-native memory. Phase 2 is the
  cutover (importing the old store and switching Claude's writer off). The split exists because
  the combined plan exceeds the finalize size lint (25 files) and the two phases are independently
  shippable. Phase 3 (§6) has no issue yet.

## 4. Requirements

### Functional

- **FR-1** `readMemoryFactsSync(dir, scope)` returns every valid fact in a flat directory and a `problems`
  list for every invalid `.md` file. It never throws for a missing directory (it returns empty).
- **FR-2** `writeMemoryFact` writes `<dir>/<id>.md` atomically (temp file + rename), refuses an existing
  id unless `overwrite`, refuses sensitive content (D10), and refuses `type: user` in a project store.
- **FR-3** Every managed launch composition (`renderManagedLaunchContext`, `materializeMuseContext`) contains
  `## Project memory` when the primary checkout's project store has ≥ 1 active fact, and
  `## Operator memory` when the operator store has ≥ 1 active fact. It follows D6, D7 and D8.
- **FR-4** Facts with a non-empty `review` marker never appear in a launch composition.
- **FR-5** The dashboard Context page preview shows the same memory sections as the launch composition
  for the selected project.

## 9. Non-goals

- Replacing or changing observation memory, its FTS index, prompt-time injection budgets
  (`PROMPT_TIME_MEMORY_BUDGETS`, `injection.ts:14-20`) or the SessionStart briefing.
- Injecting fact **bodies**, or retrieving facts per prompt (P3).
- A dashboard fact editor or a Settings toggle for `harness_native_memory` (P3).
- Committing, pushing or opening PRs on the author's behalf.
- Reaching sessions that are already running. Facts reach **new** sessions, the same as every context
  layer.
- Importing from Codex, Pi, OMP or Kimi (none has a native store with facts on this host).
- Changing `pan context diff`. It renders only the global layer today (`src/cli/commands/context-layers.ts:180-190`),
  shows no project layer either, and stays as is. The Context page preview is the full view (W4).
- Deleting, moving or editing any file under `~/.claude/`.
- Unmanaged Claude sessions (the operator running `claude` directly). They keep native auto-memory,
  untouched.
- Phase 2 in this issue: `pan memory import claude` and `memory.harness_native_memory` ship with PAN-4577.
- Syncing the operator store (`~/.overdeck/context/memory/`) between machines. It is per machine by
  design (Q6, D16); only the project store travels, through git.
- Auto-pulling the primary checkout. A fact reaches another machine when that machine's primary checkout
  is pulled by the operator or their tooling; Overdeck adds no fetch or pull.
- Changing how `.pan/` or the rest of `.overdeck/` is treated by the pipeline gates. Only
  `.overdeck/memory/` is carved out (D17).
