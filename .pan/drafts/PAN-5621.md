# PAN-5621: Detect and surface a starved gate admission queue

**Issue:** [PAN-5621](https://github.com/eltmon/overdeck/issues/5621)
**Split-off sibling:** [PAN-5623](https://github.com/eltmon/overdeck/issues/5623) (FR-2: reclaim parked workspace stacks while starved). Planning moved FR-2 there; see "Scope split" below.

## Glossary

- **Admission queue.** The machine-wide queue in `~/.overdeck/verification-workers/admission/` that every quality gate, local Vitest run and `tsc` lane joins before it runs (`src/lib/cloister/quality-gate-admission.ts`). A queued gate is a **waiter** (`waiter-<ticketId>.json`); a running gate is an **owner** that holds a **slot** (`owner.json`, `slot-<n>.json`).
- **Head.** The oldest live waiter, `snapshot.waiters[0]` in `readQualityGateQueue()`.
- **Footprint.** A gate's memory estimate: the largest of its last recorded peak RSS values, keyed by `footprintKey` (`readGateFootprintEstimate`, `src/lib/cloister/quality-gate-memory.ts`).
- **Soft reserve / hard reserve.** `resources.governor_soft_reserve_gb` and `resources.governor_hard_reserve_gb` in `~/.overdeck/config.yaml`, read with `resolveGateReserveBytes()`.
- **Memory-blocked.** The head failed the soft-reserve rule. It records the first such poll in its ticket as `memoryBlockedSince` (ms epoch). The value clears when the head fits.
- **Admitted alone (PAN-5285).** A head memory-blocked for more than 5 minutes runs alone once no slot is held, but only while `MemAvailable − footprint ≥ hard reserve`. Below that it is never admitted.
- **Starved.** No gate can ever start: no owner holds a slot, the head has been memory-blocked longer than `resources.quality_gate_starvation_minutes`, and `MemAvailable < hard reserve + clamped footprint`, so the PAN-5285 alone-admission cannot fire.
- **Starvation episode.** The span from the first poll that finds the queue starved until the queue shows progress or is confirmed empty. **Progress** means a live owner is seen, or the admission marker (below) names an admission at or after the episode opened. One episode produces one warning and one recovery message; a new head does not start a new episode.
- **Admission marker.** `~/.overdeck/verification-workers/admission/last-admitted.json` (`{"at": <ms>}`). Every successful admission writes it, best-effort, so a gate that starts and finishes between two 30 s polls still counts as progress. `readQualityGateQueue()` returns it as `lastAdmittedAt`.
- **Confirmed empty.** A snapshot with no waiters and no `readError`. A queue read that fails for any reason other than a missing admission root returns `readError`, and that result is "unknown", never "empty".
- **Starvation record.** `~/.overdeck/verification-workers/admission/starvation.json`: the durable state of one open episode. It records whether the opening alert has settled (`announced`) and whether the episode is closing with a recovery message still to settle (`closing`).
- **Settled emit.** `emitActivityEntryOnce({ id, … })` (`src/lib/activity-logger.ts:199-221`) with a stable id. It returns `appended`, `duplicate`, `unconfirmed` or `failed`. Every outcome except `failed` counts as settled; `failed` is retried on the next poll with the same id.
- **Top memory holders.** The 3 largest-RSS host processes from the runtime census (`topMemoryConsumers(getRuntimeCensus(), 3)`, `src/lib/cloister/memory-pressure-patrol.ts:498`).
- **Primary dashboard.** The dashboard process started without `OVERDECK_DISABLE_DEACON=1`. In `src/dashboard/server/main.ts` this is `!isPeerDashboard`.

## Problem

On 2026-11-23, from about 09:20Z, the admission queue ran no gate for at least 7 minutes while 7 waiters queued. The head (PAN-5489 typecheck) had waited 52 minutes. Two Flywheel substrate fixes (PAN-5601, PAN-5614) sat in verification behind it. Every waiter file showed `reason.kind: "memory"`. The typecheck footprint was 2,864,852,992 bytes, `governor_soft_reserve_gb: 10`, `governor_hard_reserve_gb: 8`, and MemAvailable stayed between 8.5 and 10.4 GB. The alone-admission needs `MemAvailable ≥ 8 GiB + 2.67 GiB ≈ 10.67 GiB`, so nothing could start. Nothing reported the stall. The Flywheel noticed only by reading waiter files, then stopped four MYN containers by hand.

The admission code already knows the head is blocked (`memoryBlockedSince`) and already knows the alone rule (`fitsAlone`, `quality-gate-admission.ts:704-707`). Nothing reads the two together, and nothing tells the operator.

## Scope split (decision)

The issue has three requirements. Planning keeps FR-1 and FR-3 here and moved FR-2 to [PAN-5623](https://github.com/eltmon/overdeck/issues/5623):

- FR-2 needs a restart path that does not exist. `rebuildWorkspaceStack` runs only at agent spawn (`src/lib/agents/workspace-stack-spawn-gate.ts`), on an `infraUnavailable` gate (`src/lib/cloister/verification-runner.ts` around line 558) and from the CLI. A parked agent woken by a message is not respawned, so it would resume against stopped containers.
- Stopped containers read as unhealthy (`evaluateWorkspaceStackHealth`, `src/lib/workspace/stack-health.ts`). `pan status` would print STACK BROKEN for every reclaimed issue.
- It overlaps [PAN-5250](https://github.com/eltmon/overdeck/issues/5250), which needs the same restart-on-demand path.
- The combined change exceeds the plan surface limit (25 files).

FR-1 alone is useful: the operator, or the Flywheel, learns of the stall within one poll of the threshold, with the facts needed to free memory by hand. PAN-5623 builds on this issue's starvation record.

The dashboard Needs-you **card** is out of scope. That needs a route, a contracts type and a frontend card, about 12 files. The episode reaches the operator through `pan status`, the activity feed and a phone push (`pushNeedsYouEdge`, the Needs-you push channel).

## Requirements

### Functional

- **FR-1** Starvation detection. While no owner holds a slot, and the head is memory-blocked for at least `resources.quality_gate_starvation_minutes` (default 15), and `MemAvailable < hard reserve + clamped footprint`, the primary dashboard opens a starvation episode. It writes the starvation record, then emits one `warn` activity entry as a settled emit, and sends one phone push. Each names the head, its wait time and the top memory holders. Until the activity entry settles, the record stays `announced: false` and every poll retries with the same id and push tag. That includes polls after a dashboard restart.
- **FR-2** One announcement per episode. Once the opening entry has settled, later polls in the same episode emit nothing. A new head or a change in MemAvailable does not count as a new episode, and neither does a dashboard restart. The episode closes on progress or on a confirmed empty queue. Closing first marks the record `closing`, then emits one `info` entry as a settled emit, and deletes the record only after that emit settles. A queue read that returns `readError` changes nothing.
- **FR-3** `pan status` prints one line while an episode is open. It shows the episode start, the current head gate and issue, how long the head has waited, the memory that head needs above the hard reserve, live MemAvailable, and the top memory holders captured at opening. The line prints even when no agent is running. Once the queue shows progress or is confirmed empty, a leftover record prints nothing.
- **FR-4** Configuration. `resources.quality_gate_starvation_minutes` is a number above 0 and under 30, default 15, read from the global config only. An out-of-range value is ignored and the default stays.
- **FR-5** Documentation and changelog. `docs/PIPELINE-GATES.md` (governor section), `configuration/memory-governor.mdx` (table row and paragraph), `changelog.d/pan-5621.md`.

(The issue's FR-1 maps to FR-1..FR-4 here. The issue's FR-3 maps to the tests in every work item and to FR-5. The issue's FR-2 is PAN-5623.)

### Non-functional

- **NFR-1** Detection never changes admission behavior. The queue's own decisions (FIFO, passing, alone-admission, CPU bypass) are unchanged. The edits in `quality-gate-admission.ts` are:
  - extra read-only snapshot fields (`ticketId`, `footprintKey`, `memoryBlockedSince` on entries; `readError` and `lastAdmittedAt` on the snapshot);
  - one `fitsAlone` helper moved into `quality-gate-memory.ts` with identical arithmetic;
  - one best-effort write of the admission marker after a successful admission. The write's error is swallowed, so it can never fail, delay past one file write, or change an admission.
- **NFR-2** Timers in tests are fake: `vi.useFakeTimers()` plus `vi.advanceTimersByTimeAsync()`. A test never waits on a real 30 s poll or a real 15-minute clock (repo rule `fake-timers-for-retry-tests`).
- **NFR-3** No synchronous child processes in dashboard-reachable code: no `execSync` and no `*Sync` tmux helpers (repo rules `no-execsync-server`, `prefer-async`). The census and file I/O are async.
- **NFR-4** The service never throws out of its timer. A failed or unknown read (a thrown error or a snapshot `readError`) skips that poll, and the episode state on disk stays as it was.
- **NFR-7** Phone delivery is best-effort. `pushNeedsYouEdge` returns nothing and confirms no delivery. The dispatcher drops a repeated tag for 24 h within one process (`EDGE_TAG_TTL_MS`, `src/lib/push/dispatcher.ts:44`). So a push repeats only when the dashboard restarts before the opening entry settles, and it can be lost if no push target is configured. The settled activity entry, the record and `pan status` are the guaranteed surfaces.
- **NFR-5** `src/lib/cloister/gate-starvation.ts` stays light, because `pan status` loads it. It must not directly import `memory-governor.ts`, `memory-pressure-patrol.ts`, `flywheel/board.ts` or any `src/dashboard/` module. The dynamic `proc-memory.js` import inside `readQualityGateMemory` already exists and is fine. Holders are collected in the dashboard service, which may import `memory-pressure-patrol.ts`.
- **NFR-6** File-size ratchet (`scripts/lint-file-size.sh`, ceiling 1000 lines, origin/main count or allowlist cap). `src/lib/config-yaml/merge.ts` is 1041 lines against cap 1045, so it gains exactly 1 line. `src/dashboard/server/main.ts` is 988 lines, so it gains at most 2 lines. `src/lib/cloister/quality-gate-admission.ts` is 947 lines; it must stay ≤ 1000. `src/lib/config-yaml/schema.ts` is not touched: new keys go in `schema-cpu.ts` / `merge-cpu.ts`. Never raise an allowlist cap.

## Design decisions

- **D1. Where detection runs.** It runs in a new primary-dashboard service, `src/dashboard/server/services/gate-starvation-service.ts`, started next to `startDiskAlertService()` in `main.ts`. It does not run inside each waiter: waiters are short-lived CLI wrappers and verification workers, and they would race to announce. It does not run in the deacon child's hygiene scheduler either. PAN-5623's reclaim needs the runtime mirror, which only the main process has (`concerns.md`, "Hygiene-scheduler module state lives in the deacon child"). It also needs `pushNeedsYouEdge`, which is a no-op outside the primary.
- **D2. Poll cadence.** 30 s (`GATE_STARVATION_POLL_MS = 30_000`), with an in-flight guard like the disk-alert service. Detection lags the threshold by at most one poll.
- **D3. Starvation predicate (pure).** It is `evaluateGateStarvation()` in `src/lib/cloister/gate-starvation.ts`. Starved iff **all** of these hold:
  1. `snapshot.owners.length === 0`. A running gate means the queue is moving.
  2. A head exists, and it has a `footprintKey`, a `ticketId` and a finite `memoryBlockedSince`. Tickets older than PAN-5285 have no `memoryBlockedSince`, so they are never starved (NonGoal).
  3. `now − head.memoryBlockedSince ≥ starvationMs`.
  4. MemAvailable is readable (non-null, > 0).
  5. `fitsAloneAboveHardReserve({ memAvailableBytes, memTotalBytes, hardReserveBytes, estimateBytes })` returns `ok: false`. The estimate is re-read from the footprint store (`readGateFootprintEstimate(head.footprintKey, root)`), not taken from the ticket. The waiter re-reads it each poll but persists it only on other writes.
- **D4. Episode lifecycle.**
  - **Opening.** An episode opens when the predicate is true and no record exists.
  - **Closing.** It closes when `starvationEpisodeCloseReason(snapshot, record.openedAtMs)` returns a reason:
    - `'admitted'`: `snapshot.owners.length > 0`, or `snapshot.lastAdmittedAt >= record.openedAtMs`;
    - `'emptied'`: otherwise, `snapshot.waiters.length === 0`.
  - **Unknown reads.** A snapshot with `readError` returns `null` and never closes or opens anything.
  - **Gaps between polls.** The admission marker covers a gate that starts and finishes between two polls. The predicate does not have to stay true while the episode is open, so a MemAvailable that flaps around the line cannot re-announce.
  - **Head rotation.** A wrapper waiter times out after 30 minutes, or its process exits, and the next waiter becomes head. The episode does not close: it hands over to the new head (D5). An owner on its own suppresses detection; NonGoal: a stuck owner is not starvation.
  - **Residual.** A gate admitted by a checkout older than this change writes no marker. If such a gate starts and finishes between two polls, the episode stays open and is handed over to the next head. Workspaces pick up the marker writer when they merge main, so this window closes on its own.
- **D5. Durable, settled announcements.** The record carries the delivery state, so no crash point can lose or repeat the activity entry.
  1. **Open.** Write the record with `announced: false`. Then announce: `push` the D8 notification (tag `gate-starvation:<since>`), then `emitOnce` the D8 warn entry with id `gate-starvation:<since>:opened`. When the emit settles, rewrite the record with `announced: true`.
  2. **Retry.** Any poll, including the first after a restart, that finds an open record with `announced: false` repeats step 1's announce with the same id and tag. A settled duplicate returns `duplicate`. A repeated push is dropped by the dispatcher within one process (NFR-7).
  3. **Close.** Rewrite the record with `closing: { at, reason }`, then `emitOnce` the D8 info entry with id `gate-starvation:<since>:recovered`, then delete the record only when that emit settles. A poll that finds a `closing` record retries only this step. A record still `announced: false` at close time skips the recovery emit and is deleted, because no warning ever reached the feed.
  4. **Handover.** In an open episode, when `snapshot.waiters[0].ticketId` differs from `record.head.ticketId`, the service rewrites `record.head` with the new head. It also re-reads that head's estimate (when it has a `footprintKey`), MemAvailable and the hard reserve, and recomputes `footprintBytes` with `fitsAloneAboveHardReserve` (`null` without a `footprintKey`). It keeps `since`, `openedAtMs`, `announced` and `holders`, and emits nothing.
- **D6. Record location and format.** The record lives at `<admissionRoot>/starvation.json`, written with `replaceFile` (temp + rename) from `quality-gate-admission-files.ts`. The marker `last-admitted.json` is written the same way. Admission's `listLiveTickets` only reads `waiter-*.json` and `.tmp-*`, and `listSlotOwnerFiles` only reads `owner.json` / `slot-<n>.json`. Both new files are therefore invisible to admission decisions (verified: `quality-gate-admission.ts:289-300`, `:371-401`). Schema:

  ```ts
  export interface GateStarvationRecord {
    version: 1
    /** ISO time the episode opened; also the stable id/tag stem. */
    since: string
    /** The same moment in ms, compared with the snapshot's lastAdmittedAt. */
    openedAtMs: number
    /** True once the opening warn entry settled (D5). */
    announced: boolean
    /** Set when the episode closed and its recovery entry has not settled yet (D5). */
    closing?: { at: string; reason: 'admitted' | 'emptied' }
    /** The current head; replaced on handover (D5). */
    head: { ticketId: string; issueId?: string; gateName: string; workspacePath: string; createdAt: number }
    memAvailableBytes: number
    hardReserveBytes: number
    /** The current head's footprint clamped to memTotal − hard reserve; null when it has no footprintKey. */
    footprintBytes: number | null
    /** Captured once, at opening. */
    holders: GateStarvationHolder[]
  }
  export interface GateStarvationHolder { pid: number; rssBytes: number; comm: string; sessionName: string | null }
  ```

  An unparseable record, or one with `version !== 1`, reads as `null`.
- **D7. Holders.** The service collects holders once, when the episode opens: `topMemoryConsumers(await getRuntimeCensus({ fresh: true }), 3)`. A failure records `[]`. It never blocks the announcement. The line labels them as captured at opening.
- **D8. Surfaces.**
  - Activity entry, opening: `{ source: 'cloister', level: 'warn', link: '/flywheel', message: formatGateStarvationLine(record, { now }), desktop: false }`. That is the D9 line, whose age reads `(<1 min)` at opening.
  - Activity entry, opening: sent with `emitOnce` and id `gate-starvation:<since>:opened`.
  - Activity entry, closing: `emitOnce({ id: 'gate-starvation:<since>:recovered', source: 'cloister', level: 'info', link: '/flywheel', message: 'Gate admission queue is moving again after <N> min: <a gate was admitted | the queue emptied>.' })`. `<N>` counts from `since` to `closing.at`.
  - Push, opening only: `{ kind: 'failed', category: 'failed', tag: 'gate-starvation:<since>', title: 'Gate queue stalled on memory', publicTitle: 'Gate queue stalled on memory', body: '<gate> for <issue> has waited <N> min; it needs <X> GiB above the <H> GiB hard reserve and <A> GiB is available.', url: '/m', issueId: head.issueId ?? null }`.
- **D9. Status line format** (one line; `formatGateStarvationLine`):

  `Gate queue starved since 09:27 (25 min): typecheck for PAN-5489 has waited 52 min and needs 2.7 GiB above the 8.0 GiB hard reserve; 9.4 GiB available. Top memory: java 3.1 GiB (pid 1234), node 2.2 GiB (pid 99, agent-pan-5611), qemu 1.9 GiB (pid 7). Free memory to let it start.`

  - Clock `HH:MM` and the minute ages use two private helpers in `gate-starvation.ts`, copied from `formatClock` and `formatWaitAge` in `src/lib/flywheel/board.ts:92-106`. Do not import `board.ts`: it has runtime imports (`../agents/provenance.js`), and NFR-5 keeps this module light.
  - `for <issue>` is omitted when the head has no `issueId`.
  - `Top memory at opening:` is the label, and it and its list are omitted when `holders` is empty. (The example line above reads `Top memory:` only for brevity; the implementation prints `Top memory at opening:`.)
  - ` and needs X GiB above the H GiB hard reserve` is omitted when `footprintBytes` is `null`.
  - The head named and the "has waited" age are always the record's current head (refreshed on handover, D5), so the gate named and its figures always belong together.
  - A holder shows `, <sessionName>` inside the parentheses only when `sessionName` is non-null.
  - GiB values have 1 decimal.
  - "available" is the live MemAvailable when the reader passes one, otherwise the record's value.
- **D10. `pan status` placement.** The line prints right after the restart-gate line and before the `No running agents.` early return, in yellow. `--json` output is unchanged; it stays an array of agents. `gateStarvationStatusLine()` lives in `gate-starvation.ts` and never throws. It returns `null` when there is no record, when the record is `closing`, when a fresh `readQualityGateQueue()` has a `readError`, when `starvationEpisodeCloseReason` returns a reason, or on any thrown error. It passes the live MemAvailable (`readQualityGateMemory()`) to the formatter. It shows the record's current head; between a handover and the next service poll (≤ 30 s), that head can be one ticket behind.
- **D11. Config key placement.** `quality_gate_starvation_minutes` goes in `schema-cpu.ts` (`CpuResourcesYamlConfig`, `CpuResourcesConfig`) beside the other `quality_gate_*` keys. Its validation goes in `merge-cpu.ts`: a finite number, `> 0 && < 30`, mirroring `quality_gate_cpu_bypass_minutes`. The upper bound keeps it under the 30-minute wrapper wait (`WRAPPER_MAX_WAIT_MS`, `src/lib/cloister/gate-admission-run.ts:23`), so a wrapper-run head can still be detected before it times out. The default of 15 goes in `defaults.ts`, with the 1-line copy in `merge.ts`. `resolveQualityGateStarvationMs()` in `gate-starvation.ts` reads `loadGlobalConfigNoMigration()` and never throws: on failure it returns `15 * 60_000`. It is read on every poll.

`settled(outcome) = outcome !== 'failed'`. An `emitOnce` that throws counts as `failed`. `push` is wrapped in try/catch.

`pollOnce` algorithm. It has an in-flight guard, and its whole body is in a try/catch that logs `[gate-starvation] poll failed: …` and returns (NFR-4).
1. `snapshot = await readQueue()`. **If `snapshot.readError` is set, return**, and leave the record untouched.
2. `record = await readRecord()`.
3. **Finish closing.** If `record?.closing`:
   - if `record.announced` is false, `clearRecord()` and return;
   - otherwise `outcome = await emitOnce(recovery entry, id 'gate-starvation:<since>:recovered')`, and `clearRecord()` only when settled.
   - Return.
4. **Open episode.** If `record` is set:
   - a. `reason = starvationEpisodeCloseReason(snapshot, record.openedAtMs)`. If `reason`, write `{ ...record, closing: { at: iso(now()), reason } }`, run step 3's settle on that record, and return.
   - b. If `!record.announced`, run `announce(record)`. It calls `push(opening notification)`, then `outcome = await emitOnce(opening entry, id 'gate-starvation:<since>:opened')`. When settled, set `record = { ...record, announced: true }` and write it.
   - c. **Handover.** If `snapshot.waiters[0]?.ticketId` is defined and differs from `record.head.ticketId`:
     - re-read memory, the hard reserve and (when the new head has a `footprintKey`) its estimate;
     - set `footprintBytes` from `fitsAloneAboveHardReserve(...).footprintBytes`, or `null` without a key;
     - write the record with the new head and figures, keeping `since`, `openedAtMs`, `announced` and `holders`;
     - emit nothing.

     If the memory read returns `null`, keep the old `memAvailableBytes`.
   - Return.
5. **Detect.** No record:
   - Read `starvationMs`, `memory`, `hardReserveBytes`, and the head estimate (only when the head has a `footprintKey`; otherwise `null`).
   - Call `evaluateGateStarvation`. If not starved, return.
   - If starved: `holders = await collectHolders().catch(() => [])`.
   - Build the record: `openedAtMs = now()`, `since = new Date(openedAtMs).toISOString()`, `announced: false`, no `closing`.
   - `await writeRecord(record)`, then run step 4b's announce.

Round 1 critique: `.pan/drafts/PAN-5621-critique.md` (codex/gpt-6-sol). All four `blocks-the-design` findings were correct, and the plan now changes each design.

### queue read failures close a live episode

Agreed. `readQualityGateQueue()` turned every error into `{ owners: [], waiters: [] }`, so a transient `readdir` failure looked like an empty queue. It would have deleted the record and announced a false recovery.

- **Snapshot.** WI-2 now separates the two cases. A missing admission root is a confirmed empty queue; any other error returns the snapshot with `readError` set.
- **Callers.** `starvationEpisodeCloseReason` returns `null` on `readError`. The service returns early without touching the record, and `gateStarvationStatusLine` returns `null` (D4, D10, NFR-4).
- **Tests.** The production read failure is tested in WI-2 (a regular file as the root gives ENOTDIR) and in WI-4 test 4, which runs the real `readQualityGateQueue` against that root with an open record and asserts no write, clear or emit.
- **Torn files.** A torn ticket file is not a concern: tickets and owner files are published with atomic link or rename (`publishExclusive`, `replaceFile`). A ticket that vanishes between `readdir` and `readJson` is a real departure.

### the record can suppress every alert

Agreed. "Write the record, then fire-and-forget the alert" made the record a lasting "announced" flag even when nothing was sent, and "clear, then emit" could lose the recovery.

- **Delivery state in the record.** The record now carries `announced` and `closing` (D5, D6).
- **Opening.** The opening entry goes through `emitActivityEntryOnce` with the stable id `gate-starvation:<since>:opened`. `announced` becomes true only after it settles, and every poll retries it, including the first poll after a restart.
- **Closing.** The record first gets `closing`, then the recovery entry is sent with id `gate-starvation:<since>:recovered`, and the record is deleted only after that settles.
- **Tests.** WI-4 tests 2, 3 and 6 cover a failed emit, a restart between the record write and the notification, and a failed recovery emit.
- **Phone push.** `pushNeedsYouEdge` has no outcome, so this plan weakens the phone guarantee explicitly (NFR-7) rather than adding a push outcome API. The push is resent on each retry with the stable tag `gate-starvation:<since>`. The dispatcher drops a repeated tag for 24 h within a process, so a duplicate phone push is possible only across a restart before the activity entry settles. The activity entry, the record and `pan status` remain the guaranteed surfaces.

### a short admitted gate never closes the episode

Agreed. An owner file exists only while a gate runs, so a 30 s poll can miss a whole admission. The plan adds a durable progress signal:

- **Marker.** Every successful admission writes `last-admitted.json` (`{ at: owner.acquiredAt }`), best-effort, with the error swallowed. This is one line after the ticket unlink in `acquireQualityGateAdmission` (WI-2 step 5); it changes no admission decision (NFR-1).
- **Snapshot and close rule.** `readQualityGateQueue()` returns the marker as `lastAdmittedAt`. The episode closes as `'admitted'` when `lastAdmittedAt >= openedAtMs`, even with no owner visible (D4).
- **Test.** WI-4 test 5 covers a gate completing between two polls with another waiter still queued.
- **Residual.** A gate admitted by a checkout older than this change writes no marker. This is recorded in D4 and the Non-goals; it disappears as workspaces merge main.

### head rotation keeps the previous gate's memory figures

Agreed. After a rotation, the record named the new head with the old head's footprint, so `pan status` gave a wrong instruction.

- **Handover.** The service now re-reads the new head's estimate, MemAvailable and the hard reserve, and recomputes the clamped footprint. It rewrites the record so the named gate and its figures always belong together (D5 step 4). `footprintBytes` is `null` when the new head has no `footprintKey`, and the line then omits "needs".
- **Labels.** The holders are labelled as captured at opening (D7, D9), and `pan status` uses live MemAvailable (D10).
- **Test.** WI-4 test 7 covers a rotation between gates with different estimates (2,864,852,992 vs 1,073,741,824 bytes) and asserts `needs 1.0 GiB`.

### Unresolved after two critic rounds

- Per-file read errors still look like an empty queue
- An admission during detection can be invisible
- A marker write failure hides a completed gate
- The phone push omits required memory holders

## Planning Q&A

`pan plan --auto`: no questions were asked. Defaults chosen:

2. **Needs-you surface?** Options: a new dashboard card, or the existing push channel plus the activity feed. **Chosen: push plus activity entry plus `pan status`.** A card needs a route, a contracts type and a frontend component, about 12 more files, for a rare event that the push already delivers.
3. **Where does detection run?** Options: inside waiters, the deacon child's hygiene scheduler, or a primary-dashboard service. **Chosen: primary-dashboard service.** It is the single writer, `pushNeedsYouEdge` works only there, and PAN-5623's reclaim needs the runtime mirror that only the main process has.
4. **Does a running owner suppress detection?** **Chosen: yes.** A running gate means the queue is moving, and an alone-admission needs empty slots anyway.
5. **Episode end?** **Chosen: when an owner appears or the queue empties.** Head rotation and flapping memory must not re-announce.
6. **Starvation minutes range?** **Chosen: above 0 and under 30, default 15.** This mirrors `quality_gate_cpu_bypass_minutes` and stays under the 30-minute wrapper wait.
