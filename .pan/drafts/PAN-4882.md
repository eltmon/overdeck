## Problem

v0.73.0 shipped Overdeck Anywhere. The PAN-4774 acceptance run on 2026-11-02 failed five criteria: AC-2 relay
half and AC-3 relay (#4862), AC-4 remote worker (fixed in #4864), AC-6 managed SSH host removal (#4861) and AC-15

behaviour on real machines. The PAN-4862 live check (its WI-4) never ran: its device code expired unapproved and
its VM was destroyed (`.pan/uat/pan-4862/live-relay.md`, `Status: pending operator approval`).
`docs/ANYWHERE-RELEASE-CHECKLIST.md` still lists these five as `failed`.

  `curl -s localhost:3011/api/health` and runs `git merge-base --is-ancestor <sha> <buildCommit>` for each fix
  SHA. All four ancestors ⇒ proceed and record whether the build also contains `v0.73.1`

  `pan tell flywheel-orchestrator "plan/work PAN-4882: deployed build <sha> lacks fix <sha>; needs pan reload"`,
  and wait for the deploy; never reload home yourself (NFR-1).
- **D-2 VM install path by version equality.** Home version = published version ⇒ every VM uses
  `registry.fly.io/pan-workspaces:latest` and `npm install -g @overdeck/core@<home version>` when its
  `pan --version` differs. Home version ≠ published version (for example home reloaded to 0.73.1 before npm got
  it) ⇒ first wait up to 30 min, re-checking `npm view @overdeck/core version` every 5 min; if still unequal,
  build a branch image from the deployed commit exactly as `docs/ANYWHERE-RELEASE-CHECKLIST.md` AC-5 describes
  (`git worktree add .tmp/pan-4882/src <buildCommit>` → `npm ci && npm run build && npm pack` there →
  `FROM registry.fly.io/pan-workspaces:latest` + `RUN npm install -g /tmp/overdeck-core-<v>.tgz` → `fly auth
  docker` right before `docker push registry.fly.io/pan-workspaces:pan-4882`, then verify the pushed digest),
  pass it with `--image` to `add-fly` and as the image of the hand-made VMs, and install the same tarball on
  the SSH VM with `scp`. Never set `[remote.fly] image`.
- **D-3 One device code, wait rule.** Only the relay VM runs `pan account login`. The agent sends
  `pan tell conv-flywheel "PAN-4882 device code <CODE> <URL> (signs in the relay VM pan4882-relay)"` and waits,
  polling the VM's login process. If the code expires, it runs `pan account login` again and sends the new code.
  The issue says to wait for the operator, so the agent keeps the relay VM and keeps waiting. At 30 min, and
  every 60 min after, it sends `pan tell flywheel-orchestrator "work PAN-4882: relay VM device code still
  unapproved (<n> min); AC-4/6/15 continue"` (fire-and-forget). The AC-4 and SSH chains run and finish in
  parallel meanwhile. Only when every other item before `cleanup-audit` is done and the code is still unapproved
  does the agent complete the four relay items (WI-2 to WI-5) by writing `not-run — device code not approved
  after <n> min` as each item's section in `ac-02-03-relay.md`, and WI-5 then tears the relay VM down (stop the
  login, `fly machine destroy`). That keeps the DAG moving: `cleanup-audit` and the closing items wait only on
  the relay chain being recorded, never on the approval itself. It never
  copies `account.json` and never proceeds past sign-in without approval.
- **D-4 Fix-or-file.** This issue fixes no code. Every `failed` check gets a new GitHub issue titled
  `Anywhere re-run (PAN-4882): <AC> <one-line symptom>` whose body has: the AC, the failing step, the exact
  command, its output trimmed to the relevant 40 lines, the deployed build, and a link to the evidence file
  path on the `feature/pan-4882` branch. The PAN-4862 PRD's pre-written follow-up applies: Outcome A passes and
  Outcome B fails ⇒ title "Relay data channel does not open over TLS TURN (PAN-4862 section 2)" with
  `DEBUG=werift*` logs from both ends. Outcome A fails ⇒ the PAN-4862 fix did not take effect on the VM; the
  issue says so and names the VM's `pan --version`.
- **D-5 Both relay directions.** Home's UDP is open, so only the VM exercises the fix. The VM is the responder when
  home posts the reconnect, and the initiator when the VM posts it to its own `localhost:3011`. Both are run.
- **D-6 Encryption evidence: decrypt the TURN TLS layer.** With TLS TURN, a raw capture shows only TLS to
  Cloudflare, which says nothing about what the relay sees. The relay VM's server runs with
  `NODE_OPTIONS=--tls-keylog=/root/tls-keys.log`, `tshark` decrypts the TLS layer with that key log, and the
  evidence shows the decrypted payload is TURN (`ChannelData` or `Send`/`Data` indications) carrying DTLS
  records, with the marker and `HTTP/1.1` absent. That is what Cloudflare's relay sees. **Implementation
  checkpoint:** if `tshark` cannot decode TURN-over-TLS with the key log after two attempts (different
  `-d tcp.port==443,tls` / `-o tls.keylog_file:` combinations), the AC-2 relay half is `approximated`, and the
  evidence states the marker and `HTTP/1.1` counts of the raw capture and that the TLS layer was not decrypted.
- **D-7 Capture filter: the TURN server only.** Resolve `turn.cloudflare.com` on the VM at capture time
  (`getent ahosts turn.cloudflare.com`; PAN-4774 saw `141.101.90.1` and `2a06:98c1:3200::1`) and capture
  `tcpdump -i any -w /root/relay.pcap 'host <v4> or host <v6>'`. An unfiltered capture picks up loopback health
  checks (PAN-4774 counted 10 `HTTP/1.1`), and decrypting it with the key log would also decrypt the VM's own
  directory websocket (its `HTTP/1.1 101` upgrade) and account calls, which say nothing about the relay.
- **D-8 Marker path.** The marker crosses the link in two places: the relay VM's machine tags
  (`anywhere: { machine: { tags: [pan4882relaymarker] } }` in the VM's `/root/.overdeck/config.yaml`, read by
  `src/lib/anywhere/machine-config.ts`, as PAN-4774 did; written before `pan serve` starts in WI-2) and a conversation on the relay VM created with
  message `pan4882relaymarker hello` under the fake harness. Home must show the marker (the conversation's
  messages through `GET /api/conversations/@<env>/<name>/messages` or the linked list) during the capture, so the
  capture provably covered marker traffic.
- **D-9 Self-reverting firewall.** Every relay item (WI-3, WI-4, WI-5) starts by killing any earlier timer
  (`pkill -f 'sleep 1800'`) and arming a new one,
  `nohup sh -c 'sleep 1800; iptables -F; ip6tables -F' >/dev/null 2>&1 &`, so a lost `fly ssh console` session
  does not force a VM restart (a restart resets the rootfs and loses the sign-in and install).
- **D-10 AC-15 runs between AC-6 add and AC-6 remove on the same SSH VM.** Remove stops the server, so Open in
  editor must run first. The conversation on the SSH VM uses the fake harness (no model credentials on the VM).
- **D-11 AC-15 evidence is the route's `commandLine`.** The agent clicks **Open in editor** → **VS Code** in the
  isolated browser and also reads the network response of `POST /api/linked-conversations/open-in-editor`.

- **D-12 AC-6 wait.** After **Remove**, the agent checks the SSH VM at 30 s, 90 s and 180 s. Pass needs, at all
  three: no process whose command line contains `supervisor/server.js` or `dashboard/server.js`, and
  `curl -s -o /dev/null -w '%{http_code}' 127.0.0.1:3011/api/health` printing `000`.
- **D-13 AC-6 case two (external server) is not re-run.** It passed on 2026-11-02 and the PAN-4861 fix changed only
  stop case 5 (its FR-4: cases 1–4 never call the supervisor stop).
- **D-14 The throwaway project.** Clone `https://github.com/eltmon/prepack-webpack-plugin` to
  `/home/eltmon/Projects/pan4882-anywhere-smoke`, then `pan project add /home/eltmon/Projects/pan4882-anywhere-smoke
  --name pan4882-anywhere-smoke`. The proposed `issue_prefix` must match `^[A-Z]+$` (PAN-4860). If it does not,
