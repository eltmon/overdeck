# PAN-5064: Skill packs and project skills — fix stale docs, add a pack authoring guide and a config reference

**Kind:** documentation, plus one CLI help string
**Verified against:** `feature/pan-5064` at `df325e4cb3f` (2026-11-05)

## Glossary

- **Skill** — a directory that holds a `SKILL.md` file. Claude Code, Codex and Pi load skills by name.
- **Bundled skill** — a skill Overdeck ships in `sync-sources/skills/` (or `sync-sources/dev-skills/`). `pan sync` copies it to `~/.overdeck/skills/`, then to `~/.claude/skills/` and `~/.agents/skills/`. "Bundled" is an adjective that means "shipped with Overdeck". This PRD does not change that word.
- **Project skill** — a skill in `<projectRoot>/.pan/skills/<name>/` in a project's own repo.
- **Skill pack** — a third-party git repository of skills. `pan skills pack add` registers it, pinned to one trusted commit. Overdeck mounts its enabled skills into managed Claude Code and Codex launches.
- **Skill bundle** — an operator synonym for **skill pack**. After this issue, the noun "skill bundle" has only that meaning in the docs and the skills.
- **Known pack** — a pack id with built-in defaults in `KNOWN_PACKS` (`src/lib/skill-packs/adapters.ts:80`): `mattpocock`, `deft`, `sageox`, `gstack`, `pstack`.
- **Custom pack** — any pack id that is not in `KNOWN_PACKS`.
- **Adapter** — the code that reads a pack's skills: `plain`, `claude-plugin`, `deft-readonly`, `gstack-runtime` (`PackAdapterId`, `adapters.ts:25`).
- **Opt-in skill** — a pack skill that the pack toggle never turns on. Only a value for that skill turns it on.
- **Extraction** — `~/.overdeck/packs/<id>/<commit>/`, the trusted commit's files (`packExtractDir`).
- **Render** — `~/.overdeck/packs/gstack/render/<commit>/`, the output of gstack's pack-mode setup (`packRenderDir`).
- **Mount** — the content-addressed plugin directory that a launch receives (`src/lib/skill-packs/mount.ts`).
- **Plan home** — the repo checkout that holds `.pan/` for a project: the project root, or the configured plan-home repo for a polyrepo project.
- **Level** — where an on/off value is stored: global, project, issue, or conversation.

Path abbreviations in this document: `sp/` = `src/lib/skill-packs/`, `so/` = `src/lib/skill-overrides/`.

**Correction to the issue text:** the issue cites `catalog.ts`, `store.ts`, `issue-file.ts`, `conversation-flags.ts` and `launcher-lines.ts` under `src/lib/skill-packs/`. These files live in `src/lib/skill-overrides/`. Their line numbers in the issue are otherwise accurate.

## Restated repo rules that apply to this change

1. **MDX safety (`scripts/lint-docs.js`, PAN-4509).** In prose (outside inline code and code fences), a `$` must be written `&#36;`, and a `<` before a digit must be written `&lt;`. `npm run lint:docs` enforces both rules on every page in `docs.json` nav.
2. **MDX placeholders.** Strict MDX parses a bare `<id>`, `<key>`, `<ISSUE>`, `<planHome>` or `<name>` in prose as a JSX tag, and the Mintlify build fails. The lint does not catch this. **Every angle-bracket placeholder in a `.mdx` file must sit inside backticks or a code fence.** Check each new or edited line.
3. **Every `docs/*.md` file must end with a newline** (`lint-docs.js` `checkDocsFiles`).
4. **Pages listed in `docs.json` must exist** as `<page>.mdx` or `<page>.md` (`lint-docs.js` `checkPublishedPages`).
5. **Skills and CLI move in lockstep** (`.overdeck/context/codebase/conventions.md`, `scripts/lint-skills.sh`). Any `pan <verb> …` command line written into `sync-sources/skills/<verb-named-skill>/SKILL.md` must use real subcommands and flags. The lint checks them against live `--help` output from `dist/cli/index.js`. `pan-sync` is verb-named, so it is checked. `pan-skill-creator` is not a top-level verb, so it is exempt. `sync-sources/dev-skills/` is never checked.
6. **Help text and the composer manifest move together.** `packages/contracts/src/composer-commands.generated.ts` is generated from the CLI registry. After a help-string change, run `npm run build:cli && npm run generate:slash-commands` and commit the regenerated file. Otherwise `npm run lint:slash-commands` fails with `composer-command manifest has drifted`.
7. **Quote the symbol, not the line number,** when a doc cites code. Line numbers drift; that is how mismatch 5 happened.
8. **Writing style (`sync-sources/rules/ste-writing.md`, `writing-style.md`).** Use active voice, short sentences, one term per concept, and contractions. Do not use dramatic labels.
9. **No full `npm test` on the host.** Run only `node scripts/lint-docs.js`, `npm run lint:skills`, `npm run lint:slash-commands`, `npm run typecheck`, and the greps named in each AC.

## Verified facts the new text must state

### Packs (authoring)

- **F-1 Adapter detection** (`sp/adapters.ts` `detectAdapter`, about line 193). A regular file at `.claude-plugin/plugin.json` gives `claude-plugin`. Anything else gives `plain`, including an empty repo. Detection never fails. `isFile` uses `lstat`, so a symlinked `plugin.json` gives `plain`. Order: `--adapter` flag or registry value, then `KNOWN_PACKS`, then detection (`sp/sources.ts`: `return explicit ?? KNOWN_PACKS[id]?.adapter ?? (await detectAdapter(dir));`).
- **F-2 Plain scan** (`PLAIN_MAX_DEPTH = 4`, `adapters.ts:136`). The scan starts at `skills/`, or at `skillsRoot` for a known pack. It goes four directory levels deep, so the deepest skill found is `skills/a/b/c/d/SKILL.md`. A skill is a directory with a regular-file `SKILL.md`. The walk does not go into a skill, so a skill nested inside another skill is not found. Symlinked directories are skipped. Directories are walked in sorted order.
- **F-3 `plugin.json` `skills` field** (claude-plugin). A **string** means: scan from that path, with the same four-level rule. An **array** means: each string is one skill directory, with no scan. Entries that are not strings, do not exist, or escape the plugin root are dropped silently. An entry with no `SKILL.md` is dropped. **Absent, or any other type**, means: scan `skills/`. Paths resolve against the plugin root. Absolute paths, `.`, `..` and paths that start `../` are rejected. An invalid `plugin.json` makes a `claude-plugin` pack fail to read (`invalid .claude-plugin/plugin.json: …`). The `plain` adapter ignores a bad `plugin.json`. The mounted plugin is named after the pack id, not after `plugin.json` `name` (`mount.ts`: `name: pack.id`).
- **F-4 Skill names** (`SKILL_NAME_PATTERN = /^[a-z0-9][a-z0-9-]*$/`, `adapters.ts:135`). The name is the frontmatter `name:`, or the leaf directory name when `name:` is absent. A name that fails the pattern is **dropped silently**. Overdeck does not fall back to the directory name: `name: My Skill` in `my-skill/SKILL.md` drops the skill. A duplicate name is dropped silently, and the first one in sorted order wins. Neither case appears in the add preview.
- **F-5 Frontmatter.** Overdeck reads only `name` and `description`, and keeps only the first line of `description`. Frontmatter must start on line 1 between `---` lines. Missing or unparseable frontmatter keeps the skill, under its directory name with an empty description.
- **F-6 License** (`adapters.ts`, `LICENSE_TOKENS = ['MIT', 'Apache', 'BSD', 'GPL']`). Overdeck first uses the `plugin.json` `license` string as written. Otherwise it reads `LICENSE`, then `LICENSE.md`, at the plugin root. Only the first non-blank line is checked, for one of the four case-sensitive tokens, and only that token is stored. With no match, the preview shows `unknown`. `LICENSE.txt` and `COPYING` are not read.
- **F-7 Not applied** (`notAppliedLabels`, `adapters.ts` about lines 413-430). `hooks` (`hooks/hooks.json`, or a `plugin.json` `hooks` key), `MCP servers` (`.mcp.json`, or a `plugin.json` `mcpServers` key), `commands` (a `commands/` directory), `agents` (an `agents/` directory), `context injection` and `git hooks` (Deft only), `executables (N)` (files in included skill directories that end `.sh` or have an exec bit), `project-mutating skills (N)` (included opt-in skills), `requires CLI (…)` (`directive` for Deft, `bun` for gstack). Only skill directories reach the agent. Scripts inside a skill directory are copied with it, so the agent can still run them. Overdeck never runs them itself.
- **F-8 Symlinks** (`mount.ts` copy filter: `filter: async (path) => !(await lstat(path)).isSymbolicLink()`). Every symlink at any depth is left out of the mount. Every other file is copied as is, hidden files included. There is no size limit.
- **F-9 Custom packs can set only their adapter.** The registry stores `url`, `ref`, `commit`, `adapter` and `browser` (`sp/sources.ts` `PackRegistryEntry`). `optIn`, `skillsRoot`, `pluginRoot` and `mountExtras` come only from `KNOWN_PACKS`, by id (`sources.ts`: `optIn: KNOWN_PACKS[id]?.optIn ?? []`; `so/catalog.ts` and `so/launch.ts` do the same). So in a custom pack, every skill turns on with the pack toggle, the plugin must sit at the repo root, and the plain scan root is always `skills/`. A custom url registered under a known id (for example `pstack`) inherits that id's options. Pack ids must match `/^[a-z0-9][a-z0-9-]*$/` and must not be a core skill name.
- **F-10 `--ref` rule** (`src/cli/commands/skills.ts` `skillsPackAddCommand`: `const ref = options.ref ?? known?.ref;`). A custom pack needs a url and `--ref`. A known pack defaults the url. Only `pstack` and `sageox` default the ref.

### Harness coverage

- **F-11 Claude Code** receives packs through `--plugin-dir "$PAN_SKILL_PLUGIN_DIR"` (`so/launcher-lines.ts`). This is a per-launch link at `~/.overdeck/launch/<key>/skill-packs` that points into the mount.
- **F-12 Codex** receives a block in `<CODEX_HOME>/config.toml`, between `# overdeck:skill-packs:begin` and `# overdeck:skill-packs:end`. The block has `[marketplaces.overdeck-packs]` (`source_type = "local"`) and `[plugins."<id>@overdeck-packs"] enabled = true` per pack. The plugins are copied to `<CODEX_HOME>/plugins/cache/overdeck-packs/<id>/<hash>` (`sp/mount.ts` `writeCodexPackBlock`).
- **F-13 Pi, other harnesses, and remote (Fly) launches receive no packs and no on/off overrides.** `pan skills launch-settings` exits 2 for any harness except `claude-code` and `codex` (`skillsLaunchSettingsCommand`: `if (options.harness !== 'claude-code' && options.harness !== 'codex')`). The launchers emit the step only for local launches of those two harnesses (`so/launcher-lines.ts` `appliesTo`: `return config.spawnMode !== 'remote' && (config.harness ?? 'claude-code') === harness;`).
- **F-14 Pi accepts `pan handoff --skill/--pack` and the New-conversation dialog's Skills choices without a warning.** The fork route validates and stores the values on the successor row with no harness check (`src/lib/overdeck/conversation-forks.ts`, `expandConversationSkillFlags` call), and a Pi launch never reads them.

### Conversation level

- **F-15** Only `pan handoff` has `--skill` and `--pack` (`src/cli/index.ts`, `.option('--pack <id>'`). The dashboard's **New conversation with options…** dialog has a **Skills** section. Its summary reads `{on} of {total} skills on`, it has a **Customize** button, and each skill row has **Inherit / On / Off**. Pack skills are grouped by pack, and there is no whole-pack toggle (`components/newConversation/ConversationSkillsField.tsx`, `NewConversationDialog.tsx`).
- **F-16 `--pack` is a snapshot.** `expandConversationSkillFlags` (`so/conversation-flags.ts`: `if (!skill.optIn) entries[`${packId}/${skill.name}`] = true;`) writes one explicit `true` per non-opt-in skill in the cached manifest at creation time. A skill that a later `pan skills pack update` adds is not in that map. It follows the normal chain (pack toggles, then off).

### Project skills

- **F-17** The catalog lists `<projectRoot>/.pan/skills` last (`so/catalog.ts:73`), and the first match by name wins. So a project skill with the same name as a skill in `~/.overdeck/skills`, `~/.claude/skills` or `~/.agents/skills` is listed as that other skill. Project skills appear only in project and issue context, never on the global Skills page.
- **F-18 Delivery** (`src/lib/skills-merge.ts` `mergePanSkillsIntoWorkspace`; only caller `src/lib/workspace-manager/create.ts`):
  - Overdeck copies `.pan/skills/<name>/` from the project's primary checkout into `<workspace>/.claude/skills/<name>/`. The copy happens **once, when the workspace manager creates an issue workspace** (planning, the dashboard, swarm, PR adoption).
  - Two cases copy nothing. The first is `pan workspace create` for a project with no `workspace:` block in `projects.yaml` (the CLI fallback calls only `mergeSkillsIntoWorkspace`, `src/cli/commands/workspace-create.ts`). The second is an existing workspace: `pan workspace update`, `pan sync-main` and `pan sync` never copy project skills.
  - A target directory that already exists is never overwritten. Bundled skills are copied first, so **a project skill with the same name as a bundled skill is skipped, and the bundled skill wins.**
- **F-19 Harness coverage for project skills.** Only Claude Code sessions whose working directory is the issue workspace see the copies: work agents, and a `pan handoff --issue` successor. Codex agents do not receive project skills. Their per-agent `CODEX_HOME/skills` is filled only from `~/.agents/skills` (`src/lib/runtimes/codex.ts` `syncCodexSkillsIntoHome`). Pi agents do not receive them either, because Pi reads `~/.agents/skills` and nothing copies `.pan/skills` there. Conversations started in any other directory do not see them.

### Config keys

- **F-20 `~/.overdeck/config.yaml`.** `skills.packs.<id>`: `{ url, ref, commit, adapter?, browser? }`.
  - `url`: a non-empty string.
  - `ref`: a non-empty string (tag, branch or SHA).
  - `commit`: 40 lowercase hex characters, the trusted commit.
  - `adapter`: optional, one of the four adapters. It is stored only when `--adapter` was passed. Otherwise Overdeck resolves it when it reads the pack.
  - `browser`: only `true` records consent (gstack).
  - Malformed entries are ignored. A config.yaml that does not parse yields no packs.
  - Writers: `pan skills pack add|update|browser|remove`. `pan skills pack sync` never moves the commit. The dashboard has no writer.
- **F-21** `skills.pack_overrides.<id>: true` means the pack is on globally. It is two-state: off is stored as no key. `skills.overrides.<skill>: false` means the skill is off globally. On is stored as no key. A `<pack>/<skill>` key stores only a difference from that skill's resting state. Core skills cannot be set. Writers: `pan skills set` and the dashboard (`PUT /api/skills/overrides`).
- **F-22 `~/.overdeck/projects.yaml`, under `projects.<key>`:**
  - `skill_overrides` (map of skill or `pack/skill` to boolean; three-state, where a missing key means inherit).
  - `skill_pack_overrides` (map of pack id to boolean; three-state).
  - `sageox_upload` (`enabled` | `disabled`; unset or any other value reads as disabled). Written by `pan skills pack sageox upload on|off --project <key>`.
  - `sageox_binding` (only the value `committed`). Written by `pan skills pack sageox commit --project <key>`.
  - `deft_integration` (`{ mode: managed, plan_digest, enabled_at }`; absent means off). Written by `pan skills deft enable|disable --project <key>`.
- **F-23 Issue file** `<planHome>/.pan/skill-overrides/<ISSUE>.yaml`: keys `issue:`, `skills:`, `packs:`, and `pipeline: deft`. It is written by `pan skills set … --issue`, the dashboard, and `pan skills deft use|back`. Every write is committed in the plan home on its checked-out branch (normally `main`) as `chore(workspace): skill overrides for <ISSUE>` (or `chore(workspace): pipeline for <ISSUE>`) and pushed to that branch's upstream. When the push fails, the commit stays and `pan skills set` prints `push pending: <reason>`. An issue file whose YAML does not parse **reads as empty** (`so/issue-file.ts` `parseYamlOrNull`).
- **F-24** There is no schema for any of these keys. Each reader validates by hand.
