# PAN-5111: Push history, withdrawn questions, and unreachable linked machines in Needs you

**Issue:** [PAN-5111](https://github.com/eltmon/overdeck/issues/5111)
**Planning mode:** `pan plan --auto` (no operator questions; defaults are recorded under "Decisions").

## Background

On 2026-11-10 the operator got two "needs you" pushes on the phone while Needs you on the
desktop was empty (`GET /api/needs-you` returned `{"conversations":[],"agents":[]}`). Nothing
on the machine recorded which pushes Overdeck sent, so the cause could not be proven. Two
causes were likely: a question that left Needs you without an answer (a hook-blocked
AskUserQuestion whose agent moved on), and a linked machine (`Edwards-MacBook-Air.local`)
whose Needs-You feed this dashboard could not fetch ("Secure channel ... did not open
within 10000 ms" in `dashboard.log`). This issue makes both causes visible.

The work has two independent slices that share no source files:

- **Slice A, push history:** record every push Overdeck sends, record when a pushed
  question or approval leaves the pending set, serve the last 50 entries, and show them in
  Settings.
- **Slice B, unreachable machines:** remember when a linked machine's Needs-You fetch fails
  and show a "Can't reach" row in Needs you on the desktop and the phone.

## Glossary

- **Push / notification:** one `NeedsYouNotification` (`src/lib/push/types.ts`) sent by the
  needs-you dispatcher to every provider (Web Push, ntfy, the Overdeck app `native`).
- **Dispatcher:** `createNeedsYouDispatcher` in `src/lib/push/dispatcher.ts`. It keeps, per
  subject, the set of pending keys and pushes a key once on its rising edge.
- **Subject:** the dispatcher's owner id for a set of pending items: `agent:<agentId>` (from
  `pendingItemsFromEnrichment`) or `conv:<conversationName>` (from
  `pendingItemsFromConversationRow`), both in `src/lib/push/classify.ts`.
- **Key:** a pending item's stable id: `auq:<toolUseId>` (AskUserQuestion, including Codex
  approvals whose toolUseId starts with `codex-approval:`), `plan:<toolUseId>` (plan
  approval), `perm:<signature>` or `perm:pending` (permission prompt). `auq:` and `plan:`
  keys are globally unique; `perm:` keys are unique only within one subject.
- **Owner:** a subject that currently lists a globally unique key (`keyOwners` map in the
  dispatcher). A key "leaves the pending set" when its last owner stops listing it.
- **Delivered push:** a notification that passed `dispatch()`'s config, event filter and rate
  limit, reached `deliver()`, and produced at least one provider outcome. Primed items, items
  active under another owner, filtered items, rate-limited items and pushes with no target are
  not delivered.
- **Answer window:** the time range in which an operator answer note credits a pushed entry:
  from its delivery to its departure plus 10 s, closed early by a re-push of the same key (D-7).
- **Warm:** the push service has run for 60 s and finished one conversation scan, so every
  still-pending item has been observed (D-8).
- **History entry:** one delivered push as recorded in `~/.overdeck/logs/push-sent.jsonl`.
- **Resolution:** the outcome recorded when a delivered `auq:`/`plan:`/`perm:` key leaves
  the pending set: `answered` or `resolved-without-answer`.
- **Operator answer note:** an in-memory record, made by an Overdeck answer door after it
  delivered an answer, that a given `auq:` key was answered by the operator.
- **Entry state:** what the API and UI show for a question or approval entry: `open`,
  `answered`, or `resolved-without-answer`. Derived at read time; never stored as `open`.
- **Linked machine / link:** a `MachineLink` (`src/lib/anywhere/link-store.ts`) this
  dashboard connects to. Its live state comes from the link supervisor (`status(link.id).state`,
  values include `online`, `offline`, `connecting`, `revoked`).
- **Fleet Needs-You:** `GET /api/fleet/needs-you` (`src/dashboard/server/routes/fleet-awareness.ts`),
  which serves the viewer-side cache built by `src/dashboard/server/services/linked-needs-you-sync.ts`.
- **Needs-You fetch failure:** the most recent `GET /api/machines/needs-you` call to a link
  threw, answered a status other than 200 or 404, or returned a malformed body, and no later
  call succeeded.
- **Channel caller:** a request that arrived through a secure channel (`channelOfRequest(request) !== null`,
  `src/dashboard/server/channel-peer.ts`). Linked machines and paired phones are channel callers.
- **Phone credential:** `resolveDashboardCredential(headers, channel)` returns `{ kind: 'phone', ... }`
  (`src/dashboard/server/routes/dashboard-auth.ts`, line 187). Phones carry `PHONE_TOKEN_SCOPES`
  (`src/lib/access-tokens.ts`, line 112), which include `read:conversations`.

## Decisions

- **D-1 (auto):** "Settings → Notifications" in the issue maps to Settings → Anywhere →
  **Phone notifications** (`PushPanel`). The list is a new `RecentNotifications` component
  rendered at the bottom of `PushPanel` under the heading "Recent notifications".
  Rationale: that panel is the only push settings surface; the desktop "Notifications"
  block in `DesktopSettingsSection` is about browser event toggles.
- **D-2 (auto):** History is append-only JSONL with two line types, `sent` and `resolved`.
  A `resolved` line references the `sent` line by a per-entry `id` (UUID v4), never by key,
  because `perm:pending` repeats across subjects and keys repeat after a re-push. Reads fold
  `resolved` lines onto `sent` lines by id, in any order.
- **D-3 (auto):** Every delivered push is recorded, including edge pushes (finished/failed),
  rate-limit summaries and the Settings **Send test**. Only delivered pushes are recorded;
  primed, filtered, rate-limited and active-elsewhere items are not (they were never sent).
- **D-4 (auto):** A history line stores `title`, never `body` or `publicTitle`, so the
  question text (the optional preview, D-8 of PAN-2354) never reaches disk. A delivery stores
  only `provider`, `target`, `ok`, the fixed `reason` code and the numeric `status`; provider
  `detail` text and rejection messages are never stored, because they can carry raw request
  errors, URLs or tokens. A push that reached no target (zero deliveries) is not a sent push
  and is not recorded.
- **D-5 (auto):** Rotation: before an append, if the file's byte size plus the line would
  exceed 5 MiB (5 × 1024 × 1024), rename `push-sent.jsonl` to `push-sent.jsonl.1`
  (replacing an older `.1`) and start a new file. Loading reads `.1` first, then the current
  file, so "last 50" spans a rotation.
- **D-6 (auto):** Answered versus withdrawn. A key resolves `answered` only when an Overdeck
  answer door recorded an operator answer note for that `auq:` key inside the push's answer
  window (D-7). Every other departure resolves `resolved-without-answer`, shown as "Answered
  or withdrawn", because a terminal answer and a withdrawn question look the same to the
  dashboard. A door notes the **pending question it verified and delivered to**, never a
  caller-supplied id it did not check, and only after delivery succeeded. Notes cover `auq:`
  keys only, through three doors: `POST /api/agents/:id/answer-question` (notes
  `questionSet.toolId` after `deliverAgentMessage` returned `ok`),
  `POST /api/conversations/:name/message` with a new `answersToolUseId` body field (noted only
  when that id is one of the conversation's pending questions before delivery, and delivery
  succeeded), and `POST /api/conversations/:id/codex-approval` (app-server path only, where the
  handler already checks the id against the live approval). Plan approvals and permission
  prompts always resolve `resolved-without-answer` (the plan-action routes carry no
  toolUseId). The pi `ask` door is skipped because ohmypi support is being removed.
- **D-7 (auto):** Answer windows. Notes are timestamps, not consumable flags
  (`operatorAnsweredBetween(key, fromMs, toMs)`). A pushed entry's window starts at its
  delivery time and ends at its departure plus 10 s (`RESOLVE_GRACE_MS = 10_000`), or earlier
  at the moment the same key is pushed again. The dispatcher waits the 10 s grace before it
  records the resolution, which removes the race where the transcript clears before the
  answer door wrote its note. On `dispose()` (shutdown), pending resolutions are recorded at
  once instead of dropped.
- **D-8 (auto):** Restart rule. The dispatcher's tracked set is memory only. On restart it
  re-adopts: when it sees a pending key that it does not push (a primed item), it asks the
  history for the newest unresolved entry with that key (and subject, for `perm:` keys) and
  tracks it under that id, so its departure is recorded. An entry state is derived at read
  time: a `resolved` line wins; else `open` when the dispatcher tracks the id or the key is
  pending now; else `resolved-without-answer` once the service is **warm** (at least 60 s
  since start and at least one completed conversation scan); before that the state is
  `null` (shown as nothing). Nothing writes an `open` line. Edge, summary and test entries
  have state `null`.
- **D-8a (auto):** Departures keep being observed without push targets. The conversation scan
  runs when a push target exists **or** the dispatcher tracks a conversation entry. Without a
  target it calls `observeSubject(subject, items, { notify: false })`, which records
  departures but neither pushes nor registers new keys (they push later, as today, once a
  target exists).
- **D-9 (auto):** History route: `GET /api/push/history`, scope `read:conversations`, answers
  `{ entries }` newest first, at most 50. Like PAN-5093's `/api/disk-alert`, the path is added
  to `ROUTE_SCOPES`, the no-loss matrix, `TELEMETRY_CLIENT_ROUTES` and the `client_route` row
  of `docs/TELEMETRY.md`.
- **D-10 (auto):** "Can't reach" rule. A link gets a row when all hold: the link record is not
  revoked (`revokedAt` null), not hidden, its supervisor state is not `revoked`, and it has a
  Needs-You fetch failure whose `lastAttemptAt` is at most 60 minutes old
  (`UNREACHABLE_FRESH_MS = 60 * 60 * 1000`). A 404 is not a failure (the peer predates the
  route) and clears one. A success clears it. `prune` drops it with the link.
  The supervisor state is deliberately **not** filtered on `offline`: a flapping link
  (`link-supervisor.ts` moves `online` → `connecting` → `offline` → retry → `online`, lines
  521-538, 646, 822) would make the row blink, and the logged incident repeats exactly that
  way. The fetch runs on every connect and on every heartbeat while no current feed is cached,
  so an online or flapping link keeps `lastAttemptAt` fresh, while a machine that is switched
  off stops producing attempts and its row expires within an hour. A machine that goes offline
  without a failed fetch never gets a row, so PAN-4651 NFR-2 ("an offline machine contributes
  no rows and no error") still holds for it.
- **D-11 (auto):** The row is not blocking, joins the desktop **System** group next to the
  disk alert, and counts in the Needs-you count. It disappears on its own when a fetch
  succeeds, the peer answers 404, the link is removed, or no fetch has failed for an hour.
- **D-12 (auto, auth surface):** The phone reads the unreachable list through
  `GET /api/fleet/needs-you`. The route keeps refusing every channel caller except one whose
  credential resolves to `kind: 'phone'`; that caller gets `{ machines: [], unreachable }`,
  never other machines' rows (the phone cannot open them: the linked-conversation proxy
  refuses channel callers). `refuseFleetRequest` itself is unchanged. The list holds only
  this machine's own link labels and failure reasons, which the phone already sees in the
  directory machine list.
- **D-13 (auto):** Row wording, identical on desktop and phone:
  `Can't reach <label>; it may have items waiting.` The decision label is
  `Can't reach <label>`; the kind label is `Can't reach machine`. UI strings and doc text added
  by this issue use no em dashes.
- **D-14 (auto, size):** The plan keeps both slices in one issue. The operator filed them as
  one incident fix with one acceptance list. The two slices share no files and no plan edges,
  so the work agent can run them in parallel. The file count is high because each slice
  carries its own tests and each doc page counts as its own subsystem.

## Requirements

- **FR-1:** Every delivered push that reached at least one target appends one `sent` line to
  `~/.overdeck/logs/push-sent.jsonl` with `id`, `ts`, `kind`, `category`, `key`, `subject`
  (or null), `title`, `issueId`, `url` and `deliveries[]` (`provider`, `target`, `ok`,
  optional `reason`, `status`).
- **FR-2:** The file rotates at 5 MiB to `push-sent.jsonl.1`.
- **FR-3:** When a delivered `auq:`/`plan:`/`perm:` key leaves the pending set, a `resolved`
  line records `answered` (an operator answer note exists) or `resolved-without-answer`.
- **FR-4:** The three answer doors in D-6 write an operator answer note after a successful
  delivery.
- **FR-5:** `GET /api/push/history` (scope `read:conversations`) returns the last 50 entries,
  newest first, each with `resolution` and derived `state`.
- **FR-6:** Settings → Anywhere → Phone notifications shows "Recent notifications": title,
  time, delivery outcome, state text, and an **Open** link to its conversation or issue.
- **FR-7:** The linked Needs-You sync remembers a per-link fetch failure until a success,
  a 404 or a prune.
- **FR-8:** `GET /api/fleet/needs-you` adds `unreachable: [{ environmentId, label, since, reason }]`
  per D-10, and serves a phone channel caller `{ machines: [], unreachable }` per D-12.
- **FR-9:** Needs you on the desktop shows a "Can't reach" card in the System group.
- **FR-10:** Needs you on the phone shows the same row with the D-13 text.
- **FR-11:** Docs describe the history, the states and the "Can't reach" row.
- **NFR-1:** Writing history never throws into the dispatcher and never blocks the event loop
  (async `fs/promises`, one serialized write queue, no `*Sync` calls).
- **NFR-2:** No question text, provider `detail` or rejection message reaches the history
  file (D-4). A test feeds a provider error containing a sentinel secret and checks the file.
- **NFR-3:** Delay-based tests use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`.
- **NFR-4:** No em dash in any line this issue adds to UI strings or docs.

**Steps:**

1. Add to `src/lib/push/types.ts` (types only):

   ```ts
   /** One provider target's result, as stored. Never carries provider detail text (D-4). */
   export interface PushDelivery {
     provider: string;

     ok: boolean;
     /** A ProviderSendOutcome reason code, or 'error' for a rejected provider. */
   ```

2. Create `src/lib/push/push-history.ts` with a module header naming PAN-5111. Export:

   ```ts
   export const PUSH_HISTORY_FILE = 'push-sent.jsonl';
   export const PUSH_HISTORY_MAX_BYTES = 5 * 1024 * 1024;
   export const PUSH_HISTORY_RECENT_LIMIT = 50;

   export type PushEntryState = 'open' | 'answered' | 'resolved-without-answer' | null;

   export interface PushHistoryEntry extends PushSentRecord {
     resolution: { outcome: PushResolutionOutcome; ts: string } | null;
   }

   export interface PushHistory extends PushHistorySink {
     /** Newest first, at most `limit` (default 50), resolutions folded in. */
     recent(limit?: number): Promise<PushHistoryEntry[]>;
     /** Resolves when the initial load finished (the service awaits it at start). */
     ready(): Promise<void>;
     /** Resolves when every queued write has landed (tests). */
     flush(): Promise<void>;
   }

   export function createPushHistory(opts?: { dir?: string; maxBytes?: number }): PushHistory;
   /** The process singleton under `join(getOverdeckHome(), 'logs')`. */
   export function getPushHistory(): PushHistory;

   export interface PushStateContext {
     trackedIds: ReadonlySet<string>;
     /** True when the running dispatcher has this key pending for this subject now. */
     isPending: (subject: string, key: string) => boolean;
     /** D-8: 60 s since service start and one completed conversation scan. */
     warm: boolean;
   }
   /** D-8: the derived state of one entry. */
   export function pushEntryState(entry: PushHistoryEntry, ctx: PushStateContext): PushEntryState;
   ```

3. Behavior:
   - Lines are JSON with `v: 1` and `type: 'sent' | 'resolved'`; a `sent` line spreads the
     `PushSentRecord`; a `resolved` line spreads the `PushResolutionRecord`.
   - All work runs on one promise chain. The first link loads: read `<dir>/push-sent.jsonl.1`
     then `<dir>/push-sent.jsonl` with `readFile` from `node:fs/promises` (a missing file is
     empty), parse each non-empty line, skip lines that fail `JSON.parse` or lack `type`/`id`,
     collect `sent` records in file order and `resolved` records in a `Map<id, …>` (last wins),
     keep the newest 200 `sent` records, and record the current file's byte size.
   - `recordSent` / `recordResolution` update memory synchronously (so `openEntryIdFor` sees a
     new entry at once) and enqueue the write: `mkdir(dir, { recursive: true, mode: 0o700 })`,
     rotate per D-5 with `rename`, then `appendFile(path, line + '\n', { mode: 0o600 })`.
     Catch every error and `console.warn('[push] history write failed:', message)`; never
     reject the chain. No `*Sync` calls.
   - `recordSent` writes only the `PushSentRecord` fields listed above; any extra property on
     the argument or on a delivery (for example a `detail`) is dropped (D-4).
   - `openEntryIdFor(subject, key)`: among in-memory `sent` records without a resolution and
     with `record.key === key` (and `record.subject === subject` unless the key starts with
     `auq:` or `plan:`), return the newest `{ id, ts }`, else `null`.
   - `recent(limit = 50)` awaits the chain, then returns the newest `limit` `sent` records,
     newest first, each with `resolution` from the map or `null`.
   - `pushEntryState(entry, ctx)`: `null` unless `entry.key` starts with `auq:`, `plan:` or
     `perm:`; `entry.resolution.outcome` when present; `'open'` when `ctx.trackedIds.has(entry.id)`
     or (`entry.subject !== null` and `ctx.isPending(entry.subject, entry.key)`);
     `'resolved-without-answer'` when `ctx.warm`; else `null`.

**Tests** (`tests/unit/lib/push/push-history.test.ts`, temp dir via `mkdtemp`):
- appends a `sent` line whose JSON has every FR-1 field and no `body` field;
- a delivery passed with `detail: 'token=SENTINEL-SECRET'` writes a line that does not
  contain `SENTINEL-SECRET`;
- folds a `resolved` line written before its `sent` line onto that entry;
- rotates to `.1` when the next line would cross a small `maxBytes`, and `recent()` still
  returns entries from both files; a fresh instance on the same dir returns the same entries;
- `openEntryIdFor` returns the newest unresolved entry for the key and `null` after it resolves;
- `pushEntryState` returns `null` (edge key; and unresolved, untracked, not pending, not warm),
  `'open'` (tracked; or pending), the stored outcome, and `'resolved-without-answer'` (warm).

## Critique response

Answers to `.pan/drafts/pan-5111-critique.md` (round 1). Each finding changed the design.

### Agent answer can be recorded after failed delivery

Accepted. The note no longer comes from a route-level wrapper keyed on the HTTP status. WI-3
step 1 keeps `deliverAgentMessage`'s result in the plain AskUserQuestion branch and calls
`noteOperatorAnswer` only when `delivery.ok`; the operator-decision branch notes only after its
existing `!result.ok` refusal. The HTTP response is unchanged (a NonGoal); a test mocks
`{ ok: false }` and checks that no note exists.

### Caller IDs are not checked against the answered question

Accepted. Every door now notes the question it verified (D-6, WI-3). The agent door notes
`questionSet.toolId`, the question the handler matched or fell back to and actually answered,
never the caller's id. The conversation `/message` door checks before delivery that
`answersToolUseId` is one of the conversation's pending questions (`getPendingQuestions`) and
notes it only then. The Codex door notes only in the app-server branch, after the existing
`requestedToolUseId !== expectedToolUseId` refusal, and notes `expectedToolUseId`. Each door has
a stale-id test.

### Repeated keys can consume the wrong answer note

Accepted. Notes are timestamps and are never consumed (WI-2 `operatorAnsweredBetween`). Each
pushed entry has an answer window from its delivery to its departure plus 10 s, and a re-push of
the same key closes the earlier window at the re-push time (D-7, WI-4 step 5). WI-4 tests leave
→ re-push → answer: only the second push resolves `answered`.

### A restart labels unresolved pushes withdrawn

Accepted. D-8 now keeps such entries indeterminate until the service is warm (60 s since start
and one completed conversation scan): before that an untracked, not-pending entry has state
`null`. An entry whose key is pending now shows `open`, and the new dispatcher re-adopts it from
the history (`openEntryIdFor`) when it sees the primed key, so its later departure is recorded
under the original id. `dispose()` records scheduled resolutions at once instead of dropping
them, so an answer noted during the grace still counts. WI-5 tests restart with a pending
question and the not-warm case; WI-4 tests dispose during the grace.

### Losing all targets stops withdrawal detection

Accepted. The conversation scan now runs when a push target exists or the dispatcher tracks a
conversation entry (D-8a, WI-5 step 2). Without a target it calls
`observeSubject(…, { notify: false })`, which records departures but neither pushes nor
registers new keys, so a new key is never treated as sent. Also, a push that reached no target
is no longer recorded at all (D-4). WI-5 tests removal of the last target followed by departure.

### Raw provider errors can reach the history file

Accepted. History stores only `provider`, `target`, `ok`, the fixed `reason` code and the numeric
`status` (D-4, NFR-2). Provider `detail` and rejection messages are never stored: the dispatcher
does not copy them into deliveries, and the history module drops any extra property it is
given. WI-1 and WI-4 each test a sentinel secret in a provider error and check the stored data.

### Unresolved after two critic rounds

- History loading races re-adoption
- A skipped target is counted as a sent push
- The stored title can contain question text
- Conversation warmth cannot prove an agent question left
