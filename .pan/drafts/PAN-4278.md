## Glossary

| Term | Definition |
| --- | --- |
| **Permission prompt** | Claude Code's blocking tool-permission menu drawn in the pane: a tool header (e.g. `Bash command`), the command/file detail, sometimes a reason line (e.g. `Dangerous rm operation on statically-unresolvable target: …`), the question `Do you want to proceed?`, and numbered options `1. Yes`, optionally `2. Yes, and don't ask again for …`, and a final `No, and tell Claude what to do differently (esc)`. It fires even with `--permission-mode bypassPermissions` for checks that "cannot be auto-allowed by permission rules". |
| **PermissionRequest hook** | Claude Code hook event fired when a permission prompt opens. Overdeck's script `sync-sources/hooks/permission-event-hook` pipes the full JSON payload to `POST /api/hooks/permission-event`. Payload (from the 2.1.280 bundle schema): `session_id`, `transcript_path`, `cwd`, `permission_mode?`, `agent_id?`, `agent_type?`, `hook_event_name`, `tool_name`, `tool_input`, `permission_suggestions?`, `mcp_server?`. **There is no reason field** — the reason text exists only on the pane. |
| **`agent_id`** | Hook field present **only** when the hook fires inside a subagent ("Absent for the main thread"). The subagent's human description lives in `<sessionDir>/<sessionId>/subagents/agent-<agent_id>.meta.json` → `.description` (e.g. `"Research Orca onboarding flow"`). `subagentsDirFor(sessionFile)` in `src/lib/transcript-landing.ts` returns that directory. |
| **Agent key** | `agent_id ?? 'main'` — identifies which thread of a conversation a hook event belongs to. |
| **Permission registry** | New in-memory, per-dashboard-process map: conversation name → agent key → hook facts (tool, input preview, agent label, requested-at). Enrichment only; the pane is authoritative. Lost on dashboard restart (acceptable: the pane still drives the dialog, just without the subagent label). |
| **Pending permission** | New field `pendingPermission` on a conversation row of `GET /api/conversations/pending-input` describing the prompt currently blocking the conversation. |
| **Answerable** | `pendingPermission.answerable === true` iff the pane read **right now** shows a parseable permission prompt. A registry entry without a prompt on the pane is `answerable: false` → the dialog shows only "Open terminal". |
| **Signature** | Stable identity of one on-screen prompt (header + detail + option labels). The answer route refuses when the signature on screen differs from the one the dialog rendered. |
| **Held message** | A composer message the server refused to paste because a permission prompt is up (409 `permission-pending`). The browser keeps it as a `held` bubble and resends it automatically once the prompt clears. |
| **Composer route** | `handleConversationMessage` in `src/lib/overdeck/conversation-message.ts` — the server side of `POST /api/conversations/:name/message`. |
| **Ensure-main** | `ensureMainInputTarget` (`src/lib/agents/input-target.ts`, PAN-4268): reads the pane and sends `Down`/`Up`/`Enter`/`Escape` to move Claude Code's agent selector back to `main` before a paste. |
| **Pane IO** | `resolveAgentPaneIo(agentId)` in `src/lib/terminal-backends/agent-pane-io.ts:116` → `{ backend, read(lines), sendKey('Up'|'Down'|'Enter'|'Escape') }`, bound to Herdr (`pane.read` visible + `pane.send_keys`) or tmux (`capturePane` + `sendKeysAsync`). The only backend-aware read+key door. |
| **DeliveryResult** | Return value of `deliverAgentMessage` (`src/lib/agents/delivery.ts:368`): `{ ok, path, failure?, deduplicated? }`. |

## Problem

Evidence (conversation 2942 = `20260927-3978`, session `96c91ded-4801-404a-9a21-1a5ce425bbf1`, 2026-09-27):

1. **15:32:21 UTC** a background subagent (`agent-a9ef2e8f37634bab2`, spawned by the main thread) ran `cd …/.tmp/orca-study && rm -f queue/* && …`, which triggered Claude Code's dangerous-rm prompt. It sat unanswered until **23:08:34** (answered "No"). The hook fired: `dashboard.log` line `[hooks] PermissionRequest session=96c91ded-… conv=20260927-3978 waiting=true tool=Bash`.
2. The dashboard showed nothing answerable. The hook route (`src/dashboard/server/routes/hooks.ts:517-560`, `postPermissionEventRoute`) reads only `session_id`, `hook_event_name`, `tool_name` and emits `conversation.permission_changed { conversationName, waiting, toolName }` via `emitOnly` (never persisted). The reducer (`packages/contracts/src/event-reducers.ts:1548-1558`) sets `conversationsAwaitingPermissionByName[name] = true`, whose **only** reader is a `TriangleAlert` icon in `src/dashboard/frontend/src/components/CommandDeck/ConversationRow.tsx:223,445-452`. It feeds no dialog, no Needs you row, no notification.
3. The conversation pending-input feed (`getConversationsPendingInputFeed`, `src/lib/overdeck/conversation-reads.ts:367-434`) reports only AskUserQuestion, plan approval and pane-choice menus. The pane-choice parser **deliberately excludes** the permission menu (`looksLikePermissionOptions`, `src/lib/pane-choice-menu.ts:105-112`, applied in card mode at `:214`). Worse, the conversation pane-choice path reads the pane through tmux `capturePane` only (`claudeConversationPaneChoice` → `captureSessionPaneChoice(conv.tmuxSession)` in `src/lib/overdeck/conversation-pane-choice.ts:37-43`), which answers `''` for a Herdr pane — so on the default backend it sees nothing at all.
4. For agents, the frontend toast in `src/dashboard/frontend/src/App/hooks/usePendingInputDialogs.ts:106-112` says the terminal dialog "cannot be answered from here yet". The only real permission dialog, `ChannelPermissionDialog` (`src/dashboard/frontend/src/components/ChannelPermissionDialog.tsx`, mounted at `App.tsx:949`), serves the Channels relay only.
5. **Lost messages.** Two composer sends at ≈15:24 UTC ("Look like a lot of stuff has been merged?", "BTW How can I launch Orca?") stayed on "Sent · waiting for transcript" forever. Transcript facts: a main-thread turn ran 15:23:34 → 15:24:59 (`turn_duration` 85537 ms, 4 background agents pending); the file holds **no** user record and **no** `queue-operation` for either text, in the main transcript or any `subagents/*.jsonl`. `dashboard.log` has **no** line for either send — the composer route logs nothing on success or on a returned failure. The dashboard process had rebooted shortly before (log line ~769961, between the 15:10:58 and 15:19:34 Stop hooks).

### Confirmed defects behind (5)

- **D1 — the composer route ignores the delivery result.** `src/lib/overdeck/conversation-message.ts:569-585`: `await deliverAgentMessage(conv.tmuxSession, deliveredMessage, 'conversation-message', method);` — the returned `DeliveryResult` is discarded; only a *thrown* `MessageDeliveryFailed` becomes a 503. The handler then returns `{ ok: true, inputTarget: 'main' }` (`:618-623`).
- **D2 — Herdr failures are returned, not thrown, and not logged.** `src/lib/agents/delivery.ts:423-431`: a Herdr throw becomes `return { ok: false, path: 'herdr', failure }`; a guard refusal becomes `{ ok: false, … failure: 'refused: …' }`. Herdr's `agent.prompt` refuses an agent it considers blocked (`agent_blocked`, `src/lib/terminal-backends/herdr.ts:827-828`). Together with D1 this is a silent-loss path: the bubble says "Sent", nothing was typed, nothing was logged.
- **D3 — the eaten-message watcher ignores the redelivery result.** `src/dashboard/server/services/conversation-eaten-message-watcher.ts:83-84` sets `redelivered = true` regardless of the returned `ok`.
- **Remaining silent path (kept on purpose):** `herdr.ts:824-838` reports `agent_prompt_stalled`/`timeout` as `delivered: true` because Herdr submits text + Enter before watching and its guide says never re-send. Its only cover is the frontend 4-minute "Not found in transcript" timer (`components/chat/useComposerEchoes.ts`), which runs only while the conversation panel is mounted and not streaming — the operator saw "indefinitely", so it did not fire for them. That is why D1's fix must return an immediate failure instead of relying on the timer.

Which of D2's branches (refusal, throw) or the stall path ate the 15:24 pair is **not yet proven**; W12 probes it.

## Requirements

### Functional

- **FR-1** A parser recognizes Claude Code 2.1.280's permission prompt on a plain-text pane screen and returns the tool header, detail lines, optional reason line, options (2 or 3) each classified `allow-once | allow-always | deny`, the cursor row, and a signature. It returns `null` for every non-permission screen, including PAN-3113 choice menus and the agent selector.
- **FR-2** The PermissionRequest hook records, per conversation and agent key, the tool name, a tool-input preview, the subagent id/type/description (subagent only) and the request time. Any CLEAR_ON event with the same agent key removes that entry. The emitted `conversation.permission_changed.waiting` is `true` while **any** entry remains for the conversation.
- **FR-3** `GET /api/conversations/pending-input` includes `pendingPermission` for a live Claude Code conversation when the pane shows a permission prompt or the registry holds an entry; `answerable` is true only when the pane shows a parseable prompt. `GET /api/conversations/:id` adds `'permissionRequest'` to `pendingInputKinds` in the same case.
- **FR-4** `POST /api/conversations/:id/permission` `{ signature, choice }` re-reads the pane, verifies the signature, sends arrow keys to the chosen option plus `Enter`, re-reads, and succeeds only when the prompt is gone. It sends **no** keys when the prompt is absent or changed.
- **FR-5** A `TerminalPermissionDialog` opens for each answerable `pendingPermission`, naming the conversation, the agent (`Main agent` or `Subagent: <description>`), the tool, the command/file, and the reason; it offers Allow once / Deny, and Allow always only when the prompt offers it. A non-answerable one shows "Open terminal" and no answer buttons. After a click it shows "Confirming…" until the feed no longer reports that signature.
- **FR-6** A pending permission puts the conversation in the Needs you section with the elapsed wait (`waiting <relative time>`), sorted oldest first.
- **FR-7** A pending permission raises a desktop notification once when first seen and again at 5 and 30 minutes while it is still pending.
- **FR-8** The composer route refuses to paste while the pane shows a permission prompt (`pendingPermission.answerable === true`) — **before** ensure-main runs — returning 409 `{ code: 'permission-pending', retryable: true, deliveryUnknown: false }`. A registry-only entry (`answerable: false`) never gates delivery.
- **FR-9** The composer keeps a refused message as a `held` bubble labelled `Waiting: the agent needs a permission answer first` and resends it (fresh `clientMessageId`) once the feed has no row for that conversation, or a row without `pendingPermission` (the feed omits conversations with nothing pending).
- **FR-10** When `deliverAgentMessage` returns `ok: false`, the composer route logs `[conversations] <name>: not delivered via <path>: <failure>` and returns 502 `{ code: 'not-delivered', error, retryable: true, deliveryUnknown: false }`; a successful delivery logs `[conversations] <name>: delivered via <path>`. The eaten-message watcher counts a redelivery only when it returned `ok: true`.
- **FR-11** A `not-delivered` failure renders in the outbox as `Not delivered — resend`; Resend uses a fresh `clientMessageId`.
- **FR-12** The PR body contains a `## Root cause` section naming the code path that lost the 15:24 messages (or, if no candidate reproduces, the candidates ruled out and why FR-10 closes each), and a regression test pins it.
- **FR-13** `docs/DASHBOARD-ARCHITECTURE.md` documents terminal permission prompts, the dialog, held messages and not-delivered failures.

### Non-functional

- **NFR-1** Every pane read and key in this feature goes through `resolveAgentPaneIo` (Herdr and tmux). No new tmux-only read.
- **NFR-2** No new `execSync`, no new `*Sync` tmux call, nothing blocking in server-reachable code (repo rules: no-execsync-server, prefer-async).
- **NFR-3** Tests with delays (5/30-minute re-notify, hold release polling, keystroke gaps) use `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()` or injected `sleep` — never real `setTimeout` waits (repo rule: fake-timers-for-retry-tests).
- **NFR-4** No persisted state: the registry is in memory, the held bubble lives in the in-memory composer store. A page reload drops a held bubble (documented limitation); a dashboard restart drops registry enrichment (dialog still works from the pane, subagent label becomes `Unknown agent`).
- **NFR-5** The pending-input feed stays within its existing budget: permission detection adds at most one pane read per live Claude Code conversation per poll, sharing the read with the pane-choice check where both run.

## Decisions (made here; do not re-litigate)

1. **One plan, not sibling issues.** AC 4 wants one PR write-up; the hold (FR-8) consumes the parser (FR-1); the docs item covers both. `plan.metadata.sizeJustification` records this.
2. **Scope is Claude Code conversations.** Work/review/test agents keep today's toast (`usePendingInputDialogs.ts:106-112`). A follow-up issue covers agents.
3. **The pane is authoritative; the hook registry only enriches.** No prompt on the pane ⇒ `answerable: false` ⇒ "Open terminal", never keys.
4. **Keys are arrows + Enter, never digits and never Escape.** Same reasoning as `buildChoiceKeystrokes` (`src/lib/pane-choice-menu.ts:278-296`): number keys are not guaranteed across versions. Deny = arrow to the `No…` row + `Enter` (Escape also dismisses other UI and would leave the menu ambiguous).
5. **Hold is client-side; refusal is server-side.** The server never pastes into a prompt and keeps no queue (NFR-4). The browser holds and resends.
6. **Receipts:** `withConversationMessageReceipt` (`src/dashboard/server/services/conversation-message-receipts.ts:22-74`) caches **every** response per `(name, clientMessageId)` for 24 h, including a 409. So a held release and a `not-delivered` Resend must mint a **fresh** `clientMessageId` with no `retry` flag — the same pattern `retryFailed` already uses for not-found entries (`src/dashboard/frontend/src/lib/composerStore.ts:536-543`). The receipts service is not changed.
7. **Permission check runs before ensure-main.** Ensure-main sends `Down`/`Up`/`Enter` (`input-target.ts` header). With a permission menu up, `Down` moves the menu cursor and `Enter` answers it. So FR-8's check goes **above** the `ensureMainInputTarget` call at `conversation-message.ts:532-545`.
8. **Subagent label on screen matching:** if the conversation has exactly one registry entry, use it. If it has several, pick the entry whose `toolInputPreview` (first 80 chars of the command / file path) appears in the parsed detail lines; if none or several match, label `Unknown agent`.
9. **Docs target** is `docs/DASHBOARD-ARCHITECTURE.md` (in this repo). The OKF `conversation-ui` concept lives in the separate `overdeck-knowledge` repo and is not edited by this PR.
10. **Two permission detectors will coexist** (agents keep `src/lib/agent-input-detection.ts:147-151`). Do not unify in this issue; record it in `.overdeck/context/codebase/concerns.md`.
11. **Hold only on a pane-confirmed prompt.** The registry is fed by a best-effort `curl -sf --max-time 1`; a lost CLEAR_ON post leaves a stale entry. Holding on it would block every send forever, so FR-8 requires `answerable === true`.

**API:**

```ts
export type PermissionChoice = 'allow-once' | 'allow-always' | 'deny';
export interface PermissionPromptOption { index: number; number: number; label: string; choice: PermissionChoice }
export interface PermissionPrompt {
  signature: string;          // `${header}::${detailLines.join('\n')}::${options.map(o => `${o.number}:${o.label}`).join('|')}`
  header: string;             // e.g. 'Bash command'
  detailLines: string[];      // command / file lines between header and question, trimmed
  reason: string | null;      // a detail line matching /^(Dangerous|Warning|This command|.*cannot be auto-allowed)/i, else null
  options: PermissionPromptOption[];
  selectedIndex: number;      // row with ❯
}
export function parsePermissionPrompt(paneText: string): PermissionPrompt | null;
export function permissionKeystrokes(prompt: PermissionPrompt, choice: PermissionChoice): Array<'Up'|'Down'|'Enter'> | null; // null when choice not offered
```

**Steps:** strip ANSI; call `parsePaneChoiceMenu(paneText, { mode: 'guard' })` (it keeps permission menus in guard mode and handles the `❯` row and the PAN-3068 footer case); accept only when (a) option 1 label matches `/^yes\b/i`, (b) the last option matches `/^no\b/i`, (c) 2 or 3 options, (d) a middle option (if any) matches `/^yes,?\s*(?:and\s*)?(?:allow|don't ask|always)/i`, (e) `Do you want to proceed?` or `looksLikePermissionText`'s pattern (`src/lib/agent-input-detection.ts:154`) appears above the options. Classify options: first → `allow-once`, middle → `allow-always`, last → `deny`. Header = the nearest non-empty line above the detail block that ends the rule `───`/is the prompt title (fixture decides; pin it in the test). `permissionKeystrokes` = arrows from `selectedIndex` to the option's index, then `Enter` (reuse the loop shape of `buildChoiceKeystrokes`).
