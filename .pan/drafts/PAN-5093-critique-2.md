## blocks-the-design: A config read error can clear an active disk alert

The PRD says a rejected threshold read keeps the last good values (`.pan/drafts/PAN-5093.md`, lines 124–130 and 431–432). But `loadGlobalConfigNoMigration()` uses `loadGlobalConfigFromDisk()` (`src/lib/config-yaml/load.ts`, lines 340–348), whose reader catches every non-ENOENT read or YAML parse error and returns `null` (`load.ts`, lines 122–132). The loader therefore resolves with defaults instead of rejecting. For example, with a configured 8 GiB warning threshold and 6 GiB free, a temporary read error changes the effective threshold to 5 GiB and clears the Needs-you item. Use an async config read path that distinguishes a genuinely missing file from an unreadable or malformed one, and retain the last good thresholds and index path on the latter. Test the real loader-to-service path, not only an injected `readThresholds` rejection.

## blocks-the-design: Sending a disk push still blocks the dashboard event loop

NFR-1 forbids blocking calls in the service or anything it calls (`.pan/drafts/PAN-5093.md`, lines 199–202), and WI-4 routes pushes through `pushNeedsYouEdge` (lines 414–420). The existing push service gives the dispatcher `readPushConfig = () => loadConfigSync().config.push` (`src/dashboard/server/services/needs-you-push-service.ts`, lines 76–78 and 140–148). Every `observeEdge` reaches `dispatch()`, which calls that reader (`src/lib/push/dispatcher.ts`, lines 197–210 and 136–139); `loadConfigSync()` performs synchronous filesystem checks and reads (`src/lib/config-yaml/load.ts`, lines 359–369 and 38–45). Thus a disk crossing performs blocking I/O while the disk is under pressure. Make the dispatcher's config available through an asynchronously refreshed snapshot, or specify another nonblocking dispatch path that preserves the existing push filters, and test that the production wiring avoids synchronous filesystem calls.
