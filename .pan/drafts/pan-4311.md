# PAN-4311 — CPU contention: weight the dashboard, nice batch agents, surface runaway processes, hold machine dispatch on CPU pressure

- **Issue:** https://github.com/eltmon/overdeck/issues/4311
- **Design research:** 2026-09-28, code read at `origin/main` 66712fd5f60, live probes of the 24-core host (Ubuntu, systemd 255, cgroup v2, herdr 0.9.1, tmux 3.4).
- **Planning pass:** 2026-09-28 (auto mode), every reference below re-verified against `feature/pan-4311` @ d10b6e7b338. Where the original design draft cited a line or seam that does not exist, the correction is stated in "Corrections to the design draft" and the work items use the corrected form.

## Glossary

- **PSI** — Linux Pressure Stall Information. `/proc/pressure/cpu` has a line `some avg10=X avg60=Y avg300=Z total=N`. `some avg60` is the percentage of the last 60 s during which at least one runnable task waited for a CPU. Unlike load average it does not count tasks blocked on IO (D-state).
- **load/core** — `os.loadavg()[0] / os.cpus().length`. The only CPU signal Overdeck reads today. IO wait inflates it.
- **cgroup / `app.slice`** — the systemd user manager puts every user service in `/sys/fs/cgroup/user.slice/user-<uid>.slice/user@<uid>.service/app.slice/<unit>`. On this host `app.slice/cgroup.subtree_control` is `memory pids`: the `cpu` controller is off, so CPU is shared per thread, not per unit.
- **`CPUWeight=`** — systemd unit property (1–10000, default 100). Setting it on any unit in a slice makes systemd enable the `cpu` controller there; CPU is then split between sibling cgroups by weight. Work-conserving: an idle machine still gives everyone all the CPU.
- **nice** — per-process scheduling priority (-20…19, default 0). Only orders threads *inside* one cgroup once the `cpu` controller is on. `nice -n N -- cmd` execs `cmd`, so the process identity (and Herdr foreground detection) is unchanged.
- **CPU class** — new concept in this issue. `interactive` (operator conversations, nice 0), `batch` (work/review/test/plan/worker/strike/uat agents, nice `resources.agent_nice`), `lane` (gauntlet lane conversations, nice `resources.lane_nice`).
- **Harness pid** — the pid of the agent's harness process (`claude`, `codex`, `kimi`, …) inside its pane. Distinct from the pane shell, which carries the same `OVERDECK_AGENT_ID` env.
- **Runaway** — a CPU-heavy process group descended from (or orphaned by) an Overdeck agent that matches one of the four legs in FR-9. Observe-only: never killed.
- **Governor** — the hysteresis state machine in `src/lib/cloister/memory-governor.ts` (`assessMemoryPressure`). Runs in the **deacon child process** (see below). Its verdict feeds only the memory-pressure patrol's activity-feed entries.
- **Stateless CPU check** — new: `assessCpuPressure()` in `src/lib/cloister/cpu-pressure.ts`. Reads PSI (load fallback) and compares against the hold threshold with no stored state, so it gives the same answer in any process (dashboard main, deacon child, `pan start` CLI).
- **Deacon child** — `src/dashboard/server/deacon-main.ts` runs `getCloisterService().start()` (l.143), which starts `startHygieneScheduler()` (`cloister/service.ts:348`). The deacon is a separate Node process spawned by `services/deacon-supervisor.ts`. Module-level caches there are invisible to the dashboard main process, which serves `/api/resources`.
- **Flywheel spawn** — an agent spawn whose `startedBy` starts with `flywheel:` (`isFlywheelStartedBy`, `src/lib/agents/provenance.ts:29`).
- **Transition-only feed entry** — an activity entry emitted once when a state is entered, keyed in memory so later ticks do not repeat it (the `lastLevel` pattern in `memory-pressure-patrol.ts:137`).

## Problem

On 2026-09-28 load reached ~79 on the 24-core host. A gauntlet lane ran 42 `yes` processes for 10 minutes. Conversation 2884 ran `git log --all --oneline -S "fly-hoff" | head` in Lexerra; the pickaxe printed nothing, `head` never closed the pipe, Claude Code's Bash tool timed out, and the `git` child survived under the harness at ~90% CPU for 95 minutes until killed by hand. The dashboard slowed down and conversations took a long time to load. On 2026-09-26 orphaned lane busy loops ran for over an hour unnoticed. Overdeck neither protected the dashboard, held new work, nor told the operator.

## Corrections to the design draft (applied in the work items)

1. **Process boundary.** The draft put the runaway patrol on the hygiene scheduler and expected its module cache to feed `/api/resources`. The hygiene scheduler runs in the deacon child; `/api/resources` is built in the main process. **Decision:** the runaway sampler lives in `src/lib/cloister/runaway-process-patrol.ts` but is started from `src/dashboard/server/main.ts` next to `startResourcesSnapshotService()`. One sampler, one process, async `/proc` reads only. This also puts it in the process where `isIdle` has data.
2. **Gates cannot read the governor's verdict.** No process except the deacon runs `assessMemoryPressure`, and the lane door (main), guardrail (main) and `spawnAgent` (`pan start` CLI) all live elsewhere. **Decision:** gates use the stateless `assessCpuPressure()` (hold if PSI `some avg60 >= governor_cpu_psi_hold_avg60`, else load/core `>= governor_cpu_soft_load_per_core` when PSI is unavailable). The governor's hysteresis stays in the deacon for the feed only.
3. **`coreServicePids` is not an existing function.** The patrol computes the exclusion set itself (FR-10).
4. **Gate exclusion by derivable facts.** The in-memory gate registry is unreadable cross-process. Gates run inside `overdeck-verification-*` scopes, which the patrol never enumerates, and every local gate is `nice -n 19`. **Decision:** exclude a process group whose leader has nice 19 while the group is younger than 20.5 min (the gate watchdog kills it after that).
5. **Harness pid from `/proc` data, not the `ps` probe.** The patrol already reads comm/ppid for every pid; it resolves the harness pid from those facts (FR-10).
6. **`nextGovernorModeWithRunway` is private** → export it for the table tests.
7. **`spawnAgent` is at l.612**, not l.108. Only `spawnAgent` is gated; `spawnRun` (non-work roles) is not — the Flywheel starts work agents.
8. **Lane door needs a 429 status and a `force` field** end to end (types, route, CLI).
9. **Herdr typed text** for a batch agent begins `nice -n 10 -- bash `, unquoted.
10. **History sampler has no caller** → wire it from `refreshResourcesSnapshot`. Its store is 24 h and in memory, so it cannot hold "a week" of samples. **Decision:** also append one durable calibration line to `~/.overdeck/logs/deacon.log` every 5 minutes from the memory-pressure patrol (FR-13).
11. **`docs/GOD-VIEW.md` does not mention `hostProcesses`**; the user-facing home of `resources.*` governor keys is `configuration/memory-governor.mdx`. Docs item retargeted.
12. **AC-0 (live cgroup check) cannot run in the work role** — it needs a deploy (`pan reload`), which only the Flywheel/operator performs. It becomes a post-merge verification checkpoint (see "Post-merge checkpoint"), not an xBRIEF acceptance criterion.

## Requirements

### Functional
- **FR-1** The dashboard transient unit is started with `--property=CPUWeight=<resources.dashboard_cpu_weight>` (default 1000).
- **FR-2** The supervisor unit file contains `CPUWeight=<resources.dashboard_cpu_weight>` under `[Service]`.
- **FR-3** Verification-worker scopes are started with `--property=CPUWeight=<resources.verification_cpu_weight>` (default 20).
- **FR-4** `launchAgentPane` prefixes argv with `nice -n <agent_nice> --` for the `batch` class and `nice -n <lane_nice> --` for the `lane` class; `interactive` and win32 are unchanged.
- **FR-5** CPU class defaults: `lane` when the conversation row has a non-null `laneRole`; `interactive` when `tokens.role === 'conversation'`; `batch` otherwise. Derived from the row, so a resumed lane stays `lane`.
- **FR-6** `/proc/pressure/cpu` is parsed (`src/lib/system-health/cpu-psi.ts`) (`some avg10`, `some avg60`); readers return `null` fields when the file is absent (darwin, old kernels).
- **FR-7** The governor's CPU rule uses PSI `some avg60` (hold `>= governor_cpu_psi_hold_avg60`, default 50, while admitting; stay held while `>= governor_cpu_psi_recovery_avg60`, default 25) and falls back to the load/core rule when PSI is null. A CPU-caused hold carries trigger kind `cpu`.
- **FR-8** The memory-pressure feed names CPU pressure for a `cpu` trigger and states the recovery condition in CPU terms.
- **FR-9** A process group is a runaway when its CPU sustained over the last 10 min is `>= 0.5` of one core **and** one leg holds: `orphaned` (age ≥ 10 min, no live harness ancestor, chain reaches pid 1 or the user manager); `detached-from-tool-shell` (non-shell direct child of the harness pid, age ≥ 10 min); `outlived-tool-call` (age > 15 min and the owning agent is idle or its harness is gone); `long-burn` (age ≥ 30 min).
- **FR-10** Runaway exclusions: harness pids and all their ancestors (pane shells); core services (comm `herdr`, comm starting `tmux`, the dashboard `process.pid`); Docker/containerd cgroups; gate-shaped groups (leader nice 19, age < 20.5 min); the quality-gate admission owner's pid and descendants (`~/.overdeck/verification-workers/admission/owner.json`).
- **FR-11** Runaway feed: one `warn` entry per `(owner, pgid, leader starttime)` at the crossing, one escalation at group age ≥ 60 min, one `info` resolve entry when the group exits. Never kills, pauses, or messages.
- **FR-12** `/api/resources` `hostProcesses` is built from the patrol's latest sample with agent attribution through `agentSessions[].rootPid = harnessPid`; the spike sampler is fed from the same tick.
- **FR-13** CPU PSI `some avg10/avg60` is recorded in the resource history sample (null on darwin) and the history response carries a `cpuPsi` series; the memory-pressure patrol logs one calibration line every 5 min.
- **FR-14** `launchLane` refuses with `LaneLaunchError(429, …cpu-saturated…)` when the stateless CPU check is saturated, unless `force: true`; `pan lane start --force` and `POST /api/lanes {force:true}` carry it.
- **FR-15** When `resources.governor_cpu_hold_dispatch` is true (default false), `spawnAgent` refuses a Flywheel spawn with a typed `CpuPressureHoldError` while the stateless CPU check is saturated. Operator spawns are never refused.
- **FR-16** `evaluateSpawnGuardrails` adds an acknowledgeable `cpu_saturated` warning (code `cpu_pressure`, severity `warning`) when the CPU check is saturated; it is not in `AUTOMATIC_SPAWN_GUARDRAIL_ACKNOWLEDGEMENT`.
- **FR-17** Quality-gate admission treats the host as pressured when PSI `some avg10 >= 25` (PSI present) instead of load/core `>= 1` (kept as the fallback); the utilization check is unchanged.
- **FR-18** Conversations are never gated by any CPU check.

### Non-functional
- **NFR-1** No stored status: every signal is read live from the kernel; the only in-memory state is the patrol's sample ring and transition-dedup keys, plus the governor's existing hysteresis.
- **NFR-2** No `execSync`/`execFileSync`/`*Sync` fs reads in the runaway patrol (it runs in the dashboard main process). `/proc` and cgroup reads use `fs/promises`.
- **NFR-3** Patrol cost is bounded: it reads only the enumerated Overdeck cgroups' `cgroup.procs`, one `stat` per pid per tick, and `environ`/`cmdline` once per `(pid, starttime)`.
- **NFR-4** Delay/interval tests use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync`; no test sleeps on real time.
- **NFR-5** Linux only. On darwin/win32 the patrol is a no-op, PSI readers return null, and `withCpuClass` on win32 returns argv unchanged (darwin gets `nice`, which exists there).
- **NFR-6** No hardcoded model/agent behavior changes beyond priority; Herdr detection keeps working because `nice` execs.

## Decisions

- **D1** Runaway sampler runs in the dashboard main process (Correction 1).
- **D2** Dispatch gates use the stateless `assessCpuPressure()`; the governor's hysteresis is feed-only (Correction 2).
- **D3** Flywheel spawn hold ships **default off** (`governor_cpu_hold_dispatch: false`) until calibration data exists. Reason: the 2026-08-02 swap-residency correction in `memory-governor.ts` records that a hold on a signal that stays elevated wedged the pipeline for weeks. The lane refusal (has `--force`) and the acknowledgeable guardrail warning ship on.
- **D4** Guardrail gets the CPU verdict as a second parameter `cpu: CpuPressureVerdict | null = null`, computed by the caller (`routes/agents/spawn.ts`) with `await assessCpuPressure()`. `spawn-gate.ts` passes `null` (no CPU warning on the resources page gate preview). Keeps `evaluateSpawnGuardrails` pure.
- **D5** A CPU trigger stores `readingBytes: 0, thresholdBytes: 0` and new optional fields `cpuSignal: 'psi-some-avg60' | 'load-per-core'`, `cpuReading: number`, `cpuThreshold: number`. When memory and CPU both hold, the memory trigger wins.
- **D6** Harness pid = the process closest to the pane root that carries `OVERDECK_AGENT_ID` or `OVERDECK_CONVERSATION` in its environ and whose comm is in the union of all harness `processNames`, or starts with `muse-bin-`, or is `node` with `codex-app-server-host` in its cmdline.
- **D7** A process group's runaway facts come from its representative member: the oldest member (ties → lowest pid). Group CPU is the sum of member CPU over the window. `count` = live member count.
- **D8** Conversations' idleness: `isIdle` returns false without runtime state. If a conversation has no runtime-mirror entry, the `outlived-tool-call` leg does not fire and the 30-min `long-burn` backstop catches the conv-2884 shape. Accepted.
- **D9** The lane CPU class is derived from `getConversationByName(name)?.laneRole` inside `spawnConversationSession`, not passed through `ConversationLaunchContext`, so resumes keep it.
- **D10** Quality-gate PSI threshold is a module constant `QUALITY_GATE_PSI_SOME_AVG10_START_THRESHOLD = 25` (same value as the governor recovery default: start heavy runs only when the machine is back to "recovered").
- **D11** One issue, one plan, with `plan.metadata.sizeJustification` (see below). Sibling issues were considered and rejected in auto mode: filing tracker issues is an operator action, and the three steps share the config keys, the PSI reader and the `cpu` trigger. The DAG has no edges between the three steps except through those shared foundations, so the work agent can fan out.
- **D12** `renderHerdrUnit` is unchanged (raising Herdr's weight now would lift every agent with it).
- **D13** The memory feed's dedup key becomes `level` + trigger kind while holding, so a CPU hold after a memory hold (or the reverse) emits a fresh entry.

## Background (design research, 2026-09-28)

Live facts that motivated the design, kept for the executor's context:
- `user@1000.service` delegates `cpu memory pids`; `user.slice`, `user-1000.slice`, `user@1000.service` have `cpu` in `subtree_control`; `app.slice` has `memory pids`. systemd turns controllers on lazily when a unit in the slice sets a CPU property.
- `overdeck-herdr.service` held 1,473 tasks (191 procs): the Herdr relay plus every agent, conversation and lane. Orphans re-parented to the user manager (pid 1917) stay in that cgroup (`flyctl` 62 h, `node` 56 h, `cliproxy` 29 h …), which is why attribution uses cgroup and environ, not only ppid.
- At load 21.8, `/proc/pressure/cpu` read `some avg60=10.66` and IO PSI `some avg60=18.25` — load average overstates CPU pressure.
- The dashboard main `node` averaged ~53% of a core over 77 min; event-loop p99 180-490 ms steady state. CPU weighting removes the contention part only.
- `systemd-oomd` (`ManagedOOMMemoryPressure=kill`, 50%) on `user@1000.service`: an oomd kill in `overdeck-herdr.service` takes out every agent at once — per-agent scopes (F3) would make it granular.
- Docker sits in `system.slice` (weight 100) beside `user.slice` (100): Docker saturation still leaves the user session ≥50%.

Options considered: O1 CPUWeight on dashboard/supervisor (chosen), O2 nice prefix (chosen), O3 per-agent scopes (follow-up), O4 PSI dispatch hold (chosen, Flywheel part opt-in), O5 runaway detector (chosen), O6 ionice (no effect), O7 IOWeight/CPUQuota (rejected: needs root / not work-conserving), O8 Docker cpu_shares (follow-up).
