# CPU contention: keeping the dashboard and the operator responsive

Date: 2026-09-28. Code read at `origin/main` 66712fd5f60. Live facts are read-only probes of this host (24 cores, Ubuntu, systemd 255, cgroup v2, herdr 0.9.1, tmux 3.4).

## Verdict

Overdeck has no working CPU protection today. The CLAUDE.md sentence "the resource governor holds dispatch during memory or CPU saturation" is false in effect:

1. The governor (`assessMemoryPressure`) does compute a CPU hold from `loadavg / cores >= 1.5`. But its only gating consumer, `preemption.ts:resumeYieldedAgents`, has **no production caller**, and `shed()` has none either. The one live consumer, `patrolMemoryPressure`, only writes activity-feed text. Nothing Overdeck launches waits on CPU: not `pan start`, the Flywheel, lanes, conversations, or resumes.
2. **The cause of the slowdown sits in the machine, not in Overdeck's code.** `app.slice/cgroup.subtree_control` is `memory pids`, with no `cpu`. Everything the operator cares about lives flat in `app.slice`: the dashboard, the supervisor, `overdeck-herdr.service` (the Herdr relay **plus every agent, conversation and lane**, 1,473 tasks), every legacy tmux pane scope, Chrome and ghostty. So the dashboard's single event-loop thread is scheduled as one thread among ~80 runnable threads at load 79. No unit sets a `CPUWeight`, and every process runs at nice 0.
3. **Runaway attribution already exists but has no input.** `buildHostProcesses` (per-agent CPU grouping with burst retention) is fed `[]` in production, and `createResourceSpikeSampler` (a transition-only "load spike, culprit X" feed entry) has no caller. The 95-minute `git log -S` and the 42 `yes` processes stayed invisible for that reason.

The smallest change that delivers most of the benefit takes two lines of launch configuration. (1) Give the dashboard and supervisor units a high `CPUWeight`. Setting it makes systemd enable the `cpu` controller in `app.slice`, which splits the CPU by cgroup instead of by thread. (2) Prefix non-conversation agent launches with `nice -n 10`, so that inside `overdeck-herdr.service` the Herdr relay and the operator's own conversations run ahead of batch agents. After that come three follow-ups: an observe-only runaway detector wired into the existing host-process and spike-sampler code, a CPU-pressure hold on machine-originated dispatch (lanes and Flywheel spawns), and per-agent systemd scopes in `overdeck-{conversations,agents,lanes}.slice`.

## Gaps, by goal

### (a) Keep the dashboard and the operator's interactive sessions responsive

- No cgroup CPU isolation inside `app.slice`, so the dashboard competes per thread with all agent threads.
- The Herdr relay, the process that streams pane output to the dashboard, shares its cgroup and nice level with every agent.
- Operator conversations and the batch agents in `overdeck-herdr.service` cannot be told apart.
- Nothing measures "the dashboard is being starved". The event-loop p99 mixes self-inflicted blocking with scheduler delay, while per-cgroup `cpu.pressure` separates them and nobody reads it.

### (b) Stop Overdeck from piling more work onto a saturated machine

- The governor's CPU hold gates nothing.
- The guardrail ignores CPU.
- `pan start` / Flywheel spawns skip the guardrail.
- Lanes have no gate at all.
- The signal is load average, which IO wait inflates, instead of CPU PSI.
- Other projects' test runs are unadmitted.

### (c) Notice and surface runaways without auto-killing

- There is no sampler of current per-process CPU, so no attribution to an agent, conversation or lane.
- Orphans (ppid → user manager) are not surfaced at all.
- There is no "descendant outlived its tool call" rule. The coordinator's 2026-09-28 case: conversation 2884 (Lexerra) ran `git log --all --oneline -S "fly-hoff" | head`. The pickaxe printed nothing, so `head` never closed the pipe. Claude Code's Bash tool timed out, but the `git` child survived under the harness at ~90% CPU for 95 minutes (11:03 to 12:39 UTC, when it was killed by hand).
- The 2026-09-26 orphaned lane busy loops ran for more than an hour. On 2026-09-28 a lane's 42 `yes` processes ran for 10 minutes. Neither produced a feed entry, because the spike sampler has no caller.

## Recommended design

Principle: every signal is read live from the kernel (cgroup membership, `/proc/<pid>/stat`, `/proc/<pid>/environ`, PSI). Nothing about processes is stored. The only in-memory state is transition-only dedup keys for feed emission, the same pattern as `memory-pressure-patrol.ts`'s `lastLevel`. Slice units and unit properties are configuration owned by `pan install`, like the Herdr unit today. Nothing kills anything.

### Step 1 (minimal, most of goal a): weights and nice

1. `src/cli/commands/restart.ts:spawnDashboardSystemdUnit()` (l.352): add `--property=CPUWeight=${resources.dashboardCpuWeight}` next to `ManagedOOMPreference=avoid` (l.373). Default **1000**.
2. `src/lib/systemd.ts:renderSupervisorUnit()` (l.69): add `CPUWeight=${dashboardCpuWeight}` under `[Service]`. `installSupervisorUnit` already rewrites the file and daemon-reloads when the text changes.
3. `src/lib/cloister/verification-worker-launcher.ts:buildVerificationWorkerLaunch()`: add `--property=CPUWeight=${resources.verificationCpuWeight}` (default **20**). Without it, once `app.slice` has the controller, each verification scope would get weight 100.
4. `src/lib/terminal-backends/launch.ts:launchAgentPane()` (l.141): wrap `request.argv` through a new pure function `withCpuClass(argv, cpuClass, platform)` in a new `src/lib/terminal-backends/cpu-class.ts`:
   - `cpuClass: 'interactive' | 'batch' | 'lane'` becomes a new field on `LaunchPaneRequest`.
   - Default: `interactive` when `tokens.role === 'conversation'` and the request carries no lane facts; `lane` when the conversation runtime is launching a lane (`conversation-runtime.ts` ~l.845 passes it from the lane door's input); `batch` otherwise.
   - `interactive` → argv unchanged. `batch` → `['nice', '-n', String(resources.agentNice), '--', ...argv]` (default 10). `lane` → `nice -n 15`.
   - On `win32`, return argv unchanged.
5. Config keys `resources.dashboard_cpu_weight`, `verification_cpu_weight`, `agent_nice` and `lane_nice` go in `src/lib/config-yaml/{schema,defaults,merge}.ts`, next to the governor keys.
6. `herdr-setup/service.ts:renderHerdrUnit()` stays **unchanged** in this step. Raising Herdr's weight now would lift every agent with it.

Expected effect at load 79: the dashboard cgroup gets up to 1000/(1000 + 100·k) of the machine, which on this host is several cores against the one it needs, so scheduler delay on its event loop largely disappears. Inside Herdr, the relay and operator conversations get about 10x the per-thread share of nice-10 agents (the nice step ratio is ~1.25x per level). The `yes` x42 lane at nice 15 would sit behind everything else.

### Step 2 (goal c): observe-only runaway detector

New `src/lib/cloister/runaway-process-patrol.ts`, registered in `hygiene-scheduler.ts` at `RUNAWAY_PATROL_INTERVAL_MS = 30_000`.

- Enumerate processes cheaply. Read `cgroup.procs` of `app.slice/overdeck-herdr.service`, `app.slice/overdeck-tmux-server.service`, `app.slice/tmux-spawn-*.scope`, and (after F3) `overdeck-*.slice/**`. The cgroup root comes from `/proc/self/cgroup` plus the user@ path. Fallback when that is unreadable: `/proc/[0-9]*` filtered to the same uid.
- CPU: `utime+stime` from `/proc/<pid>/stat` (fields 14/15, plus `starttime` field 22 for identity), as the delta between samples divided by `interval × CLK_TCK` (100 on Linux). Not `ps pcpu`. Keep a bounded ring of the last N samples per `(pid, starttime)` in memory, where N = window / interval.
- Attribution, in order:
  1. `OVERDECK_AGENT_ID` / `OVERDECK_CONVERSATION` / `OVERDECK_AGENT_STARTED_BY` from `/proc/<pid>/environ` (own uid, readable).
  2. The first ancestor carrying them (ppid walk).
  3. The cgroup name (F3 scope name, or `overdeck-herdr.service`).
  4. The cwd under `workspaces/feature-*` or the lanes root (`/proc/<pid>/cwd`).

  Lane vs conversation is resolved from the conversation row's lane facts, which are write-once facts and read as they are.
- Exclude:
  - the **harness pid** itself. Do not use "the first process carrying the id": `herdr.ts:startAgent` passes `spec.env` to `pane.split`, so the pane's `bash` is the first carrier and `claude` would stay a candidate. Resolve the harness pid with `agents/runtime-pid-probe.ts:findAgentRuntimePidInSubtree` (already used by `liveness.ts`) or Herdr `pane.process_info` foreground pids. A harness parsing a large transcript is not a runaway;
  - core-service pids (Herdr server, tmux server, dashboard, supervisor, deacon child) through the existing `coreServicePids` seam in `routes/resources/core-services.ts`. The Herdr server has no `OVERDECK_AGENT_ID`, sits in the agents' cgroup, and has averaged about 1.2 cores over its life;
  - pids in Docker/containerd cgroups;
  - the registered quality-gate process groups while younger than `GATE_TIMEOUT_MS` (export a reader from `validation.ts` for `registerGateProcessGroup`'s set);
  - the current admission owner's process tree (`owner.json` pid).
- Classify a process group as a runaway when **sustained CPU ≥ 50% of one core averaged over the last 10 min** and one of the following holds:
  - **orphaned**: no live Overdeck harness ancestor (ppid chain reaches the user manager / pid 1 / a subreaper without passing the harness), and age ≥ 10 min;
  - **detached from its tool shell**: a non-shell process whose **direct parent is the harness pid**, aged ≥ 10 min. Claude Code runs Bash tool commands through a `bash -c` shell, so a non-shell direct child of `claude` means its shell has already died, which happens when a timed-out tool shell is killed and the pipeline child is reparented to the harness. **Unverified:** whether conv-2884's `git` had ppid = the `claude` pid or was reparented to the user manager (pid 1917). In the second case the orphaned leg catches it at 10 min. Confirm with a live reproduction (`git log --all -S <absent> | head` under a 1-minute Bash timeout, then read `/proc/<git>/stat` field 4) before relying on this leg;
  - **outlived its tool call**: age > `runaway.max_tool_age_ms` (default 15 min, above Claude Code's 10-min Bash cap) **and** `liveness.isIdle(agentId)` is true **or** the harness pid is gone. This leg does **not** catch a conversation that kept working after the timeout, because `isIdle` is then false. The two legs above and the long-burn leg cover that case;
  - **long burn**: age ≥ 30 min regardless of agent state. This is the backstop that catches the conv-2884 shape even when neither of the earlier legs applies, and it also catches a still-attached busy loop.
- Group by `(owner, pgid)`, so that `yes` x42 is one row with `count: 42`.
- Emit transition-only:
  - One `warn` activity entry per group when it becomes a runaway. Key: `(owner, pgid, leader starttime)`. Message shape: "`git log --all -S …` (conv-2884, Lexerra) has burned 14 CPU-min over 16 min after its tool call returned. pgid 12345. Stop: `kill -TERM -12345`". `link: '/resources'`.
  - One escalation at 60 min.
  - A resolve entry when the group exits.
  - Truncate the command line to 120 characters. Command lines can carry secrets; the entry is local but the same text could end up in an issue.
- Wire the two existing unwired pieces instead of writing new UI:
  - Keep the latest sample in a module cache (`getRunawaySnapshot()`), so that `snapshot.ts:89` publishes `buildHostProcesses(realRecords, { agentSessions, coreServicePids })` instead of `buildHostProcesses([])`. Supply `agentSessions` as `{ agentId, rootPid: harnessPid, issueId }`, taken from the same harness-pid resolution. `buildHostProcesses` attributes by walking ppid to a `rootPid`, so without that array every Herdr-hosted process would land as `host`.
  - Feed `createResourceSpikeSampler().sample({ cpuPercent, load1, cores, processGroups })` from the same tick, so the machine-level "Load 79 spike: `yes` x42 (conv-lane-…)" line finally fires.
- It never kills, pauses or messages. Header comment: the stall-sweeper operator directive applies.

### Step 3 (goal b): hold machine-originated dispatch on CPU pressure

Calibration comes first, as Step 0 (ship it with Step 1). Record PSI cpu `some avg10/avg60` next to load/core in the resource history sampler (`routes/resources/history.ts:recordResourceHistorySample`), so a week of data sets the thresholds. There is one data point today: `some avg60 = 10.66` at load 21.8. A hold on a signal that stays elevated is exactly what wedged the pipeline for weeks in the swap-residency era (the operator-approved correction dated 2026-08-02 in `memory-governor.ts`). So the automatic hold on Flywheel spawns ships **default off**, behind `resources.governor_cpu_hold_dispatch: false`. The lane refusal (cheap fan-out, with a `force` escape) and the acknowledgeable guardrail warning ship on. The `cpu`-trigger feed entry fires regardless of the flag.

- Signal: add `readCpuPsi()` to `dashboard/server/services/proc-memory.ts`, parsing `/proc/pressure/cpu` `some avg10/avg60`. In `memory-governor.ts:nextGovernorModeWithRunway`, compute `cpuSaturated` from `psiCpuSomeAvg60 >= governor_cpu_psi_hold_avg60` (default 50) while admitting and `>= governor_cpu_psi_recovery_avg60` (default 25) while held. Fall back to the existing load/core rule when PSI is unavailable (darwin). Add a `'cpu'` `GovernorTriggerKind` so the feed says "CPU pressure …" instead of "before trigger details were available".
- Gates. All of them read `assessMemoryPressure()` or the cached verdict: no new stored state, and conversations are never gated.

## Ready-to-file GitHub issue

**Title:** CPU contention: weight the dashboard, nice batch agents, surface runaway processes, hold machine dispatch on CPU pressure

**Body:**

### Problem

On 2026-09-28 load reached ~79 on the 24-core host. A gauntlet lane ran 42 `yes` processes for 10 minutes. Separately, conversation 2884 ran `git log --all --oneline -S "fly-hoff" | head` in Lexerra: the pickaxe printed nothing, `head` never closed the pipe, and Claude Code's Bash tool timed out. The `git` child survived under the harness process after its tool call had returned, and burned ~90% CPU for 95 minutes until it was killed by hand. The detector must catch a long-running, CPU-heavy descendant that is still attached to a live harness, not only true orphans. The dashboard slowed down and conversations took a long time to load. On 2026-09-26, orphaned busy loops from a lane ran for more than an hour unnoticed. Overdeck neither protected the dashboard nor held new work nor told the operator.

### Current state

- The CPU hold in `cloister/memory-governor.ts:nextGovernorModeWithRunway` (load/core ≥ 1.5) gates nothing. Its only gating consumer, `preemption.ts:resumeYieldedAgents`, has no caller, and `shed()` has none. `patrolMemoryPressure` only writes feed text. A CPU-caused hold renders as "before trigger details were available" because no `cpu` trigger kind exists. CLAUDE.md's "holds dispatch during memory or CPU saturation" is wrong.
- `evaluateSpawnGuardrails` (`routes/agents/shared.ts`) ignores CPU. `pan start` spawns directly through `spawnAgent`, and `lanes/launch.ts:launchLane` has no resource check.
- Nothing reads `/proc/pressure/cpu`. Load average, which IO wait inflates, is the only CPU signal.
- `app.slice/cgroup.subtree_control` is `memory pids`, so the cpu controller is off. The dashboard, supervisor, `overdeck-herdr.service` (the Herdr relay plus every agent, conversation and lane, ~1,500 tasks), the tmux pane scopes, Chrome and ghostty all compete per thread. No unit sets `CPUWeight`. Every agent runs at nice 0. Only quality gates are niced (`validation.ts`, `nice -n 19`).
- `routes/resources/host-processes.ts:buildHostProcesses` is fed `[]` in production (`getHostProcessesSnapshot`), and `routes/resources/spike-sampler.ts:createResourceSpikeSampler` has no caller, so runaway attribution exists but never runs. `runtime-census.ts` uses `ps pcpu` (lifetime average) and sees only tmux panes.
- The Vitest CPU admission queue (`quality-gate-admission.ts`, `tests/vitest-cpu-admission.ts`) covers Overdeck's own runs only.
- Out of reach from user space: the NVMe schedulers are `none` (ionice has no effect) and `io` is not delegated (IOWeight has no effect).

### Design

Overdeck stores no status it can derive. Every signal is read live from the kernel (cgroup membership, `/proc/<pid>/stat`, `/proc/<pid>/environ`, PSI). The only in-memory state is the transition-only dedup keys for feed entries. Nothing is killed automatically.

1. **Weights and nice (goal: responsiveness)**
   - `restart.ts:spawnDashboardSystemdUnit` adds `--property=CPUWeight=<resources.dashboard_cpu_weight>` (default 1000).
   - `systemd.ts:renderSupervisorUnit` adds the same `CPUWeight=`.
   - `verification-worker-launcher.ts:buildVerificationWorkerLaunch` adds `--property=CPUWeight=<resources.verification_cpu_weight>` (default 20).
   - A new pure `terminal-backends/cpu-class.ts:withCpuClass(argv, cpuClass, platform)`, called from `launch.ts:launchAgentPane`, prefixes `nice -n <agent_nice>` (default 10) for batch roles and `nice -n <lane_nice>` (default 15) for lanes. Root operator conversations are unchanged. `LaunchPaneRequest` gains `cpuClass`, and the conversation runtime passes `lane` for lane launches.
   - `renderHerdrUnit` is unchanged in this issue.
   - Config keys go in `config-yaml/{schema,defaults,merge}.ts`.
2. **Runaway detector (goal: visibility, observe-only)**
   - New `cloister/runaway-process-patrol.ts` on a 30 s hygiene-scheduler interval.
   - It enumerates `cgroup.procs` of the Overdeck cgroups and computes per-process CPU from `utime+stime` deltas.
   - Attribution order: environ (`OVERDECK_AGENT_ID`/`OVERDECK_CONVERSATION`/`OVERDECK_AGENT_STARTED_BY`), then ppid walk, then cgroup, then cwd.
   - It excludes:
     - the harness pid, resolved through `runtime-pid-probe.ts:findAgentRuntimePidInSubtree` or Herdr `pane.process_info` (not "the first process carrying the id", which is the pane shell);
     - core-service pids (`coreServicePids` in `core-services.ts`);
     - Docker;
     - registered quality-gate process groups under the gate timeout;
     - the admission owner.
   - A process group is a runaway when it has sustained ≥ 50% of one core over the last 10 min **and** one of these holds:
     - it is orphaned and aged ≥ 10 min;
     - it is a non-shell direct child of the harness pid, aged ≥ 10 min (its tool shell has died). Confirm by reproduction that this is the conv-2884 shape;
     - it is aged > 15 min while its agent is idle or its harness is gone;
     - it is aged ≥ 30 min (the backstop).
   - It emits one `warn` activity entry per `(owner, pgid, starttime)`, naming owner, age, CPU-minutes, the truncated command and a `kill -TERM -<pgid>` hint. It escalates once at 60 min and adds a resolve entry on exit.
   - It feeds real records to `buildHostProcesses` (the `/resources` host-process panel) and to `createResourceSpikeSampler`.
   - It never kills, pauses or messages (the stall-sweeper directive applies).
3. **CPU-pressure dispatch hold (goal: don't pile on)**
   - `proc-memory.ts` parses `/proc/pressure/cpu`.
   - The governor's CPU rule uses PSI `some avg60` (hold ≥ 50, recover < 25; configurable), falls back to load/core when PSI is unavailable, and gets a `cpu` trigger kind.
   - `launchLane` refuses with `cpu-saturated` (429) unless `force` is set.
   - `spawnAgent` refuses `flywheel:`-provenanced spawns while held on CPU, but only when `resources.governor_cpu_hold_dispatch` is true (default **false** until a week of PSI samples, recorded in the resource history sampler as part of this issue, calibrates the threshold; see the 2026-08-02 swap-residency correction in `memory-governor.ts`).
   - `evaluateSpawnGuardrails` adds an acknowledgeable `cpu_saturated` warning, so deferred handoff retries wait for the pressure to clear.
   - Conversations and operator `pan start` are never blocked.
   - `quality-gate-admission.ts` samples PSI instead of load.

Out of scope, filed as follow-ups: per-agent `systemd-run --scope` placement in `overdeck-{conversations,agents,lanes}.slice` owned by `pan install` (and only then `CPUWeight=1000` on the Herdr unit), dashboard `cpu.pressure` in `/api/metrics`, and the IO delegation note.
