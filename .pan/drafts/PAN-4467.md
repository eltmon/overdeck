# PAN-4467 — Conflict repair skips an approved PR silently once its head moved past the approval

**Issue:** https://github.com/eltmon/overdeck/issues/4467
**Predecessors:** PAN-4384 (`.pan/drafts/PAN-4384.md`), PAN-4451 (`.pan/drafts/PAN-4451.md`)

## Glossary

- **Conflict-repair patrol** — the 60-second dashboard loop
  (`src/dashboard/server/services/conflict-repair-patrol.ts`) that runs
  `tickConflictRepair` in `src/lib/cloister/conflict-repair.ts`.
- **Conflict-repair gate** — `evaluateConflictRepairGate` in
  `src/lib/cloister/merge-gate.ts`. It answers `conflicting: true` when the PR is
  merge-ready except that the forge reports `mergeable: false`.
- **Candidate** — a workspace whose pipeline journal passes
  `isConflictRepairCandidate`: the last `review.verdict` entry is `APPROVED` and no
  `merge.completed` entry follows it.
- **Forge approval** — `PrFacts.approved === true`. On GitHub this is
  `reviewDecision: APPROVED`, or (when GitHub reached no decision) a trusted
  `overdeck-verdict: APPROVED` marker comment. It holds at **any** head: GitHub
  does not dismiss approvals on push in this repository.
- **Approval at head** — `PrFacts.approvedAtHead === true`, or
  `forgeApprovalAtHead(...) === true`: a trusted marker whose `sha=` is the head, or
  a trusted GitHub review whose `commit.oid` is the head.
- **Stale approval** — on GitHub only: a forge approval exists
  (`facts.approved === true`) but approval at head is not proven. This is the
  PR #4440 shape: approved at `13c97089`, head now `e05f77e6`.
- **Dismissed approval** — the forge no longer reports any approval
  (`facts.approved === false`, e.g. `reviewDecision: REVIEW_REQUIRED` in a repo that
  dismisses approvals on push) although the journal says `APPROVED`. The PR wins over
  the journal (CLAUDE.md: the pipeline journal is "never authority"), so this is
  **not** an approval for this issue. See Non-goals.
- **Head8** — the first 8 characters of the PR head sha; the episode key used by
  every `conflict.*` journal entry (`data.head`).
- **Declined conflicting head** — the gate answered `conflicting: false` for an open
  PR whose forge facts say `mergeable: false`.

## Problem

An approved PR whose head moved after approval (the agent merged main and pushed but
never re-requested review), and which then turns CONFLICTING again, has no route out:

1. The merge gate refuses it (conflicting, and not approved at head).
2. `evaluateConflictRepairGate` (`src/lib/cloister/merge-gate.ts`, search
   `const readiness = evaluateMergeReadiness(asMergeable, { ciTestsRequired: false, uatRequired, requireApprovalAtHead: true });`)
   only sets `approvedAtHead: true` on `asMergeable` when approval at head is proven
   (search `...(approvedAtHead ? { approvedAtHead: true } : {}),`). With a stale
   approval, `evaluateMergeReadiness` (`src/lib/cloister/pr-facts.ts`, search
   `reason: \`PR is not approved at PR HEAD ${head} (needs a review approving that commit)\``)
   returns not-ready, so the gate answers `conflicting: false`.
3. `tickIssue` (`src/lib/cloister/conflict-repair.ts`, search
   `if (!gate.conflicting) return reviewBackstop(d, issueId, entries, gate);`) then
   runs `reviewBackstop`, which returns `null` because `facts.mergeable !== true`
   (search `if (!facts.open || facts.mergeable !== true || !facts.headSha) return null;`).
4. `tickIssue` never logs `gate.reason`, so `dashboard.log` had zero
   `[conflict-repair] PAN-4433` lines in about 13 hours.

PAN-4451 explicitly left this case out ("a head that moved past its approval is out
of scope here — the agent's own `pan review request` covers it"); in PR #4440 the
agent never ran it.

## Requirements

### Functional

- **FR-1** For a GitHub PR that is open, not a draft, has no change request, has no
  red checks, has no failed required UAT at the head, reports `mergeable: false`,
  and has a **stale approval**, `evaluateConflictRepairGate` returns
  `{ conflicting: true, staleApproval: true, facts }`.
- **FR-2** When approval at head is proven, the gate returns `conflicting: true`
  with no `staleApproval` key (unchanged behavior). For a GitLab MR, `staleApproval`
  is never set. A GitHub PR with no forge approval at all (`approved: false`) still
  returns `conflicting: false` with the reason
  `PR is not approved at PR HEAD <sha> (needs a review approving that commit)`.
- **FR-3** The gate never calls `recordApprovalAtHead` (it does not today) — the
  stale case's synthetic `approvedAtHead: true` on `asMergeable` must never reach
  the board's per-head approval answers.
- **FR-4** When the gate answers `conflicting: true` with `staleApproval: true`, the
  patrol sends exactly one sync-main repair for that head through the existing
  `dispatchRepair` path. The repair prompt's first line says the PR
  `was approved at an older commit and now conflicts with origin/main`, and the
  journal entry `conflict.repair-requested` carries `data.staleApproval: true`.
  All other per-head rules (dedup by journal, 45-minute grace escalation,
  `unreachable` escalation, review backstop) apply unchanged.
- **FR-5** When the gate answers `conflicting: false` for a candidate whose facts
  are `open: true`, `mergeable: false`, and have a `headSha`, `tickIssue` logs
  `[conflict-repair] <ISSUE>: conflicting head <head8> not repaired: <reason>` once
  per `<ISSUE>:<head8>` per dashboard process. Declines for mergeable, closed, or
  unknown-mergeability PRs are not logged.
- **FR-6** Why the repair route is safe (decision D1): `evaluateIssueMergeGate` is
  unchanged, so nothing merges without approval at the new head; the repair prompt's
  step 5 demands `pan review request`; `requestReviewGuarded` proceeds for a stale
  approval (`readApprovalStandsAtHead` returns `false`); and `reviewBackstop`
  requests review once if the agent forgets.

### Non-functional

- **NFR-1** No new forge read: the gate keeps the single existing
  `forgeApprovalAtHead` call. The tick's per-candidate cost is unchanged.
- **NFR-2** Nothing is stored beyond what exists: the skip-log dedup is an
  in-memory `Set` like `refusalsSurfaced`, cleared by
  `__resetConflictRepairStateForTests`. A dashboard restart re-logs a declined head
  once; that is acceptable for a log line.
- **NFR-3** Tests that advance time use `vi.useFakeTimers()` /
  `vi.advanceTimersByTime()` (repo rule "fake timers for retry/backoff/delay tests").
  `conflict-repair.test.ts` already does this in `beforeEach`; new tests must not use
  real `setTimeout` waits.
- **NFR-4** No file crosses its file-size ratchet. `merge-gate.ts` is 200 lines and
  `conflict-repair.ts` 356; neither has an allowlist row and both stay far below the
  default cap.

## Decisions

- **D1 — Route a stale-approval conflict to a sync-main repair, not straight to
  Needs-you.** The issue offers both. The repair actually unblocks the PR, and the
  safety chain in FR-6 already guarantees re-review before merge. Needs-you is still
  reached through the existing escalation rules (grace expiry, unreachable agent).
- **D2 — This reverses PAN-4451's non-goal** "Conflicting PRs whose approval does not
  stand at the head are not repaired". PAN-4467 is the newer issue and supersedes it;
  this is not a contradiction between authoritative inputs for the same issue.
- **D3 — Stale = `facts.forge === 'github' && facts.approved === true && !approvedAtHead`**,
  where `approvedAtHead` is the gate's existing local (marker proof, else
  `forgeApprovalAtHead(...) === true`). `false` and `undefined` from
  `forgeApprovalAtHead` both count as "not proven". The forge check is required:
  GitLab never sets `approvedAtHead`, so without it every GitLab repair would be
  labeled stale.
- **D4 — Dismissed approvals are not repaired.** The forge is the authority; a PR
  the forge calls unapproved belongs to the review pipeline. FR-5 logs it instead.
- **D5 — Skip-log key is `<ISSUE>:<head8>`** (the AC says "once per issue and head"),
  not including the reason.
- **D6 — Prompt wording changes only in the first line.** Step 5 already says "The
  merged head needs a fresh approval before it can merge."

2. Add:

   ```ts
   /**
    * PAN-4467: a candidate whose open PR conflicts but that the gate declines
    * leaves one log line per head, so a skip is never silent.
    */
   function logDeclinedConflict(d: Resolved, issueId: string, gate: ConflictRepairGateResult): void {
     const { facts } = gate;
     if (!facts.open || facts.mergeable !== false || !facts.headSha) return;
     const head = facts.headSha.slice(0, 8);
     const key = `${issueId}:${head}`;
     if (declinesLogged.has(key)) return;
     declinesLogged.add(key);
     d.log(`[conflict-repair] ${issueId}: conflicting head ${head} not repaired: ${gate.reason ?? 'no reason given'}`);
   }
   ```

## Non-goals

- A dismissed approval (forge `approved: false`, journal `APPROVED`) is not repaired;
  it is only logged (FR-5).
- The sibling deadlock — approved at an older head, head moved, PR **mergeable**, no
  review request, no prior repair entry — is not routed here. The merge gate refuses
  it and `reviewBackstop` requires a prior `conflict.repair-requested`. File a
  follow-up issue rather than widening this change.
- No change to `evaluateIssueMergeGate`, `evaluateMergeReadiness`,
  `isConflictRepairCandidate`, the review backstop, the escalation timers, or the
  dashboard patrol host.
- No change to `changelog.mdx` (written at release time).
- No new journal entry type; no persistent store for skip logs.
