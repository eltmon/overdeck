# PAN-4358 — Ctrl+K conversation search: match titles, one row per conversation, down-rank path noise

**Issue:** [PAN-4358](https://github.com/eltmon/overdeck/issues/4358)
**Planned:** 2026-09-28 (auto planning, `--auto`)
**Base commit:** `7e9223421ad` (origin/main at planning time)

## Glossary

- **Palette** — the Ctrl+K / Cmd+K command palette, `src/dashboard/frontend/src/components/CommandPalette.tsx`. Ctrl+J opens it scoped to Conversations.
- **Conversations chip** — the palette scope chip that shows only conversation search results.
- **Chunk** — one row of the `chunks` table in the conversation-search sidecar DB (`src/lib/database/conversation-embeddings-db.ts`). It holds a ≤512-token window of one transcript message's text, with `session_id`, `parent_session_id`, `role` (`user` or `assistant` only — verified on the live DB: 187 129 user rows, 93 891 assistant rows), `ts`, `byte_offset`, `text`.
- **Chunk hit** — a `ConversationSearchHit` (`src/lib/conversation-search/ranker.ts`) returned by `rankConversationSearch()`: a chunk plus its RRF score, rank and marked excerpt.
- **RRF** — reciprocal rank fusion. `fuseRankedRows()` in `ranker.ts` merges the BM25 (FTS5) list and the vector (sqlite-vec) list by summing `1 / (k + position)`.
- **Candidate pool** — how many chunk hits the server asks the ranker for before grouping. Today it equals the palette limit (15), so one chatty conversation fills the list.
- **Conversation row** — a row in `conversations` in `~/.overdeck/overdeck.db`. It carries `name` (e.g. `20260919-9189`), `title`, `title_source` (`manual`, `auto`, `ai`, `ai-refined`, `ai-explicit`, `default`, `user`, or null), `project_key`, `cwd`, `archived_at`, `created_at`, `last_attached_at`. Its Claude session UUIDs live in `conversation_files.locator`.
- **Root session id** — `hit.parentSessionId ?? hit.sessionId`. A subagent chunk's root is its parent session.
- **Grouped row** — the new unit of the conversation result list: one per conversation, carrying its best chunk, a hit count and a match tier.
- **Match tier** — the ranking band of a grouped row. `title` (the conversation title matches the query) ranks above `text` (at least one chunk matches in prose, or matched only semantically) which ranks above `path` (every lexical match in every chunk sits inside a file path, a fenced code block or an inline code span).
- **Non-prose range** — a span of chunk text that is a fenced code block, an inline code span, or a path-like token (defined exactly in WI-1).
- **Title-only hit** — a grouped row whose conversation matched by title but has no chunk hit in the candidate pool. It has no byte offset.

## Problem (verified)

On 2026-09-29 the operator searched Ctrl+K for conversation 2832 (`name = 20260919-9189`, `title = "Personal portfolio deployment to GitHub"`, `title_source = ai-refined`, `project_key = papers-please`, not archived; Claude session `c66ac4d1-3f8f-4c81-b1a7-bc917fa527eb`). "eltmon", "eltmon.com", "personal site", "portfolio" and "Personal portfolio" never returned it. Planning verified three causes on the live data:

1. **Titles are never searched.** `searchConversations()` (`src/dashboard/server/routes/palette.ts`, line 302, `async function searchConversations(rawQuery: string, matchQuery: string, limit: number)`) returns `searchConversationChunks()` hits unchanged. Session `c66ac4d1…` has 39 chunks and **zero** BM25 matches for "portfolio" — the word appears only in the AI-refined title. Title search is the only route to this conversation for that query.
2. **Hits are chunks, not conversations.** The ranker slices fused chunks to `limit`. BM25 "portfolio" LIMIT 20 returned 20 chunks from 16 sessions; "eltmon" LIMIT 300 returned 300 chunks from 257 sessions.
3. **Common tokens in paths and tool output drown everything.** Every top "eltmon" BM25 hit was noise: `ls -l` owner columns inside a ``` fence (`drwx------ 4 eltmon eltmon 4096 …`), `/home/eltmon/.claude/skills/…` paths, and `<output-file>/tmp/claude-1000/-home-eltmon-Projects-lexerra/…` tokens. BM25 scored them ≈ -0.00 because the term is in nearly every document.

A fourth gap: archived conversations already appear (chunk hits are not filtered by archive state), but nothing marks them archived.

A fifth gap the issue implies: `docs/DESKTOP-APP.md` line 122 says conversation results **default to newest-first order**. `compareConversationActionsNewestFirst()` (`CommandPalette.tsx` line 215) sorts by timestamp only, so a correctly ranked title match would still land mid-list on first open unless the comparator sorts by tier first.

## Decisions (made here; executors do not re-decide)

- **D1 — Group on the resolved conversation name.** The group key is the `conversationId` the palette already computes (`routeableConversation(parentSessionId ?? sessionId).name`): the conversation row's `name` when one exists, else the root session id. Subagent chunks therefore fold into their parent conversation. The grouped row carries its best chunk's `sessionId`, `subagentId` and `byteOffset`, so opening still lands on the right message (and on the subagent, when the best chunk is one).
- **D2 — Tiers are strict bands, ordered `title` < `text` < `path`.** Within a band: best chunk RRF score descending, then hit count descending, then last-activity timestamp descending, then `conversationId` ascending (determinism). A title-only row's score is 0.
- **D3 — The best chunk of a group** is the highest-RRF chunk whose match kind is `text`; if the group has none, the highest-RRF chunk overall. Fused hits arrive in RRF-descending order, so "first seen" is "best".
- **D4 — Path/tool classification is lexical.** A chunk is `path` when it has ≥1 literal (case-insensitive) occurrence of a query term and **every** occurrence lies inside a non-prose range. A chunk with zero literal occurrences (vector-only hits, or BM25 porter-stem matches like "deploying" for "deployed") is `text`. Down-weighting is by tier, never by dropping: path-only conversations still appear, below every `title`/`text` conversation.
- **D5 — URLs count as paths.** `https://eltmon.com/…` is a slash-containing token, so a match inside it is non-prose. Accepted: the same term in prose ("I deployed eltmon.com") is `text`.
- **D6 — Candidate pool = 300 chunks** (`CONVERSATION_CHUNK_POOL = 300` in `palette.ts`) for both BM25 and vector candidate lists, and the fused list is not truncated below 300. Measured on the live 3.0 GB DB: BM25 "eltmon" LIMIT 300 took 336 ms warm, "portfolio" LIMIT 300 took 1 ms. The `limit` query parameter (palette sends 15, route default 20, max 50) applies to **grouped conversations**.
- **D7 — AC3 is a guarantee within the candidate pool.** A prose match ranked below the 300-chunk BM25/vector pools is not seen. Review and UAT must test AC3 against fixtures or queries where the prose chunk is in the pool, not against arbitrary live queries.
- **D8 — Title search runs independently of the embedding sidecar.** It reads `overdeck.db` only, so title matches are returned even when `conversationSearch.enabled` is false, when no embedding key is configured, or when the embed call throws (e.g. exhausted credits). `docs/DESKTOP-APP.md` line 124 changes accordingly.
- **D9 — Title match rule.** Query terms are `rawQuery.toLowerCase().match(/[\p{L}\p{N}_-]+/gu)` deduplicated (the same term regex `buildMarkedExcerpt()` uses). A title matches when every term is a prefix of at least one word of the lowercased title, words split by the same regex. So "portfolio", "Personal portfolio", "deploy" and "eltmon" (for a title word `eltmon-site`) match; "personal site" does not match "Personal portfolio deployment to GitHub". Title matching uses the raw query, never `buildMatchQuery()` output.
- **D10 — Title search scope.** All conversation rows with a non-empty `title`, archived or not, excluding names starting `agent-`, `planning-`, `specialist-` (the same exclusion `listConversations()` uses in `src/lib/overdeck/conversations.ts` line 606). SQL prefilter: `lower(c.title) LIKE ? ESCAPE '\'` per term (`%term%`, with `\`, `%`, `_` escaped), at most 8 terms, ordered by `COALESCE(c.last_attached_at, c.created_at) DESC`, `LIMIT 200`; then the D9 JS check; then slice to 50.
- **D11 — Archived rows are included and marked.** Every grouped row carries `archived: boolean` (`archivedAt !== null` on its conversation row; `false` when there is no row). The palette shows an `archived` chip. Opening an archived conversation uses the same pane path as any other.
- **D12 — New code goes in new modules.** `src/lib/overdeck/conversations.ts` (1222 lines) and `CommandPalette.tsx` (1124 lines) sit exactly at their `scripts/file-size-allowlist.txt` caps. No new allowlist rows: title search is a new module, and the palette's conversation-hit view-model moves out of `CommandPalette.tsx` into a new module, shrinking it.
- **D13 — Title-only hits open with no message target.** `byteOffset` is `null`; `handleOpenConversationHit()` skips `fetchConversationMessageLocator()` and the pending target, and opens the conversation pane at its default scroll position.
- **D14 — Newest-first keeps the tiers.** The palette's default newest-first order sorts by tier first, then timestamp, then rank. Relevance order sorts by `rank` (the server's grouped order, which already encodes tiers).

## Requirements

### Functional

- **FR-1** — A query whose terms all prefix-match words of a conversation's title (D9) returns that conversation in the `title` tier, ranked above every non-title conversation, including archived conversations and conversations with no transcript chunk hit.
- **FR-2** — `conversations` in `GET /api/palette/search` contains at most one row per `conversationId`; subagent chunks group into their parent conversation.
- **FR-3** — Each grouped row carries its best chunk's excerpt (D3), `hitCount` (number of chunk hits for that conversation in the candidate pool; 0 for title-only rows), `title`, `archived`, and `matchTier`.
- **FR-4** — The `limit` parameter caps grouped conversations, not chunks; the chunk candidate pool is 300 (D6).
- **FR-5** — A conversation whose only lexical matches sit inside non-prose ranges ranks in the `path` tier, below every `text`-tier conversation (D4, D7).
- **FR-6** — Title matches are returned when chunk search is disabled or fails (D8).
- **FR-7** — The palette labels a conversation row with its title when it has one, shows a hit-count chip when `hitCount > 1`, and shows an `archived` chip for archived rows.
- **FR-8** — In newest-first order the palette sorts conversation rows by tier, then timestamp (D14).
- **FR-9** — Selecting a title-only row opens the conversation pane without calling the message-locator route (D13).
- **FR-10** — Docs describe title matching, grouping, the tier order, archived marking and the disabled-search behavior.

### Non-functional

- **NFR-1** — Grouping and classification of a 300-chunk pool add no more than ~50 ms (pure string scans over ≤300 chunks of ≤~6 KB).
- **NFR-2** — Title search is one indexed-free SQL scan over `conversations` (~3 000 rows live) plus a JS filter; no child processes, no `execSync` (dashboard-server rule).
- **NFR-3** — `filterLiveHits()` stats each distinct transcript path once, not once per hit.
- **NFR-4** — No file in `scripts/file-size-allowlist.txt` grows past its cap (D12).
- **NFR-5** — No new circular import (`npm run lint:circular` uses madge): the new frontend module must not import from `CommandPalette.tsx`.

## Work items

### WI-1 — Chunk match classifier (`src/lib/conversation-search/match-context.ts`, new)

What/why: decide whether a chunk matched the query in prose or only inside paths/tool output (FR-5). Pure, DB-free.

Exports:

```ts
export type ChunkMatchKind = 'text' | 'path';

/** Lowercased, deduplicated query terms; same term regex as ranker.buildMarkedExcerpt. */
export function queryTerms(query: string): string[] {
  return [...new Set((query.toLowerCase().match(/[\p{L}\p{N}_-]+/gu) ?? []))];
}

export function classifyChunkMatch(text: string, query: string): ChunkMatchKind;
```

Algorithm for `classifyChunkMatch`:

1. `terms = queryTerms(query)`; if empty return `'text'`.
2. Build non-prose ranges `[start, end)` over `text`:
   - fenced blocks: `/```[\s\S]*?(?:```|$)/g` (an unterminated fence runs to the end of the chunk, because windows split long messages);
   - inline code: `/`[^`\n]+`/g`;
   - path-like tokens: `/[^\s<>"'`()[\]{},;]*\/[^\s<>"'`()[\]{},;]*/g` — any run of non-delimiter characters that contains `/`.
3. `lower = text.toLowerCase()`. For each term, walk every occurrence with `indexOf`. Count occurrences; if any occurrence's `[i, i + term.length)` is not fully inside one range, return `'text'`.
4. If the occurrence count is 0 return `'text'` (vector-only or stemmed match). Otherwise return `'path'`.

Tests — `src/lib/conversation-search/__tests__/match-context.test.ts`:
- prose occurrence (`"I deployed eltmon.com today"`, query `eltmon`) → `text`;
- only in `/home/eltmon/Projects/x` → `path`;
- only inside a ``` fence containing `drwx------ 4 eltmon eltmon 4096` → `path`;
- only inside an unterminated fence → `path`;
- only inside inline code `` `eltmon` `` → `path`;
- `<output-file>/tmp/claude-1000/-home-eltmon-Projects-lexerra/x</output-file>` → `path`;
- one path occurrence plus one prose occurrence → `text`;
- no literal occurrence → `text`;
- `queryTerms('Personal  portfolio portfolio')` → `['personal', 'portfolio']`.

### WI-2 — Conversation grouper (`src/lib/conversation-search/group-hits.ts`, new)

What/why: turn fused chunk hits plus title matches into one ranked row per conversation (FR-1..FR-5). Pure; the conversation lookup is injected so tests need no DB.

```ts
import type { ConversationSearchHit } from './ranker.js';
import { classifyChunkMatch, type ChunkMatchKind } from './match-context.js';

export type ConversationMatchTier = 'title' | 'text' | 'path';

export interface ConversationIdentity {
  conversationId: string;       // conversation row name, else the root session id
  projectKey: string | null;    // conversation row's project_key (yaml key) or null
  title: string | null;
  archived: boolean;
}

export interface TitleMatchedConversation extends ConversationIdentity {
  title: string;
  /** Claude session locator for opening; null when the row has no claude-code file. */
  sessionId: string | null;
  cwd: string;
  lastActivityAt: string | null;
}

export interface GroupedConversationHit {
  identity: ConversationIdentity;
  tier: ConversationMatchTier;
  hitCount: number;
  bestHit: ConversationSearchHit | null;   // null only for title-only rows
  titleMatch: TitleMatchedConversation | null;
  score: number;                            // bestHit?.rrfScore ?? 0
  lastActivityAt: string | null;            // bestHit?.ts ?? titleMatch?.lastActivityAt ?? null
}

export function groupConversationHits(input: {
  hits: ConversationSearchHit[];            // RRF-descending
  titleMatches: TitleMatchedConversation[];
  query: string;
  resolve: (rootSessionId: string) => ConversationIdentity;
  limit: number;
}): GroupedConversationHit[];
```

Steps:
1. For each hit in order: `root = hit.parentSessionId ?? hit.sessionId`; `identity = resolve(root)` (callers memoize); `key = identity.conversationId`; `kind = classifyChunkMatch(hit.text, query)`. Upsert the group: `hitCount += 1`; set `firstAny` if unset; if `kind === 'text'` set `firstText` if unset.
2. For each title match: upsert the group by `conversationId`, keep an existing chunk-derived identity but set `title`/`archived` from the title match, and record `titleMatch`.
3. `tier = titleMatch ? 'title' : firstText ? 'text' : 'path'`; `bestHit = firstText ?? firstAny ?? null`.
4. Sort by D2; slice to `limit`.

Tests — `src/lib/conversation-search/__tests__/group-hits.test.ts` (build hits with `fuseRankedRows()` or literal objects):
- three chunks from one session → one row, `hitCount: 3`, `bestHit` is the highest-RRF chunk;
- a subagent chunk (`parentSessionId: 'parent'`) and a parent chunk → one row keyed by the parent's conversation name, `bestHit.sessionId` is the subagent's when it has the higher score;
- two sessions resolving to the same conversation name → one row;
- a title-only match ranks first above a higher-scored `text` row; its `bestHit` is null and `hitCount` 0;
- a title match that also has chunk hits keeps `hitCount` and `bestHit`, tier `title`;
- a `path`-only conversation with the higher RRF score ranks below a `text` conversation (AC3);
- a group with one path chunk (higher RRF) and one prose chunk picks the prose chunk as `bestHit`;
- `limit: 2` over four conversations returns two rows (limit counts conversations);
- `archived: true` from `resolve` and from a title match is carried to the row.
