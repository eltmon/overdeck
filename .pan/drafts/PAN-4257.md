## Glossary

- **Effort** — the reasoning-effort level a harness launches with. Canonical levels, lowest to highest: `low`, `medium`, `high`, `xhigh`, `max` (`EFFORT_LEVELS` in `packages/contracts/src/effort.ts`). The default is `high`.
- **Effort source** — the precedence layer a resolved effort came from (`EffortSource`): `explicit`, `item`, `plan`, `tier`, `sub-role`, `role`, `project`, `default`.
- **Resolver** — `resolveEffort(input)` in `src/lib/agents/resolve-effort.ts`. It walks explicit → item → plan → tier → sub-role → role → project → default and clamps the result to the model and harness. It returns `{ effort, source, requested, clamped, warning? }`.
- **Tier** — a named entry in `tiered_execution.tiers.<name>`. Since PAN-4249 a tier may carry `effort` (`TierDefinition.effort` in `src/lib/agents/tier-table-types.ts`).
- **Staffing** — the result of `resolveStaffing(item, options)` in `src/lib/agents/staffing.ts`: which tier, model and harness run a plan item. It is the single staffing resolver (PAN-2397).
- **Implicit staffing** — staffing that comes from `roles.work` because tiered execution is off for the issue or the tier table cannot place the item. Its `tierName` is the literal `'default'` (`IMPLICIT_TIER_NAME`) and `implicit: true`. It is not a configured tier.
- **Slot** — a registered swarm worker for one plan item, spawned by `spawnRun(issueId, 'work', { slotIndex, slotItemId })` (dispatched by `src/lib/cloister/deacon-swarm.ts`).
- **Single-work agent** — the one foreground work agent for an issue (`spawnAgent` with no slot). `pan start`, the swarm foreman (`src/lib/cloister/swarm-foreman.ts`) and the merge-train conflict resolver all launch one. It is staffed for the plan's hardest remaining item (`resolveSingleWorkTierSpawnParams`).
- **Caller effort** — the `effort`/`effortSource` a caller passes in `SpawnOptions`/`SpawnRunOptions`. `pan start` always passes one (`src/cli/commands/start.ts:756`, grep `const resolved = resolveEffort({ explicit: options.effort, role: 'work'`), computed without a tier.
- **Explicit caller effort** — a caller effort whose `effortSource` is `'explicit'`, or that has no `effortSource` (the `spawnEffortFields` convention in `src/lib/agents/relaunch-effort.ts`).
- **Tier override** — an entry in the workspace continue file's `tierOverrides` map (`TierOverride` in `src/lib/xbrief/continue-state.ts:105`). `readTierOverrides` (`src/lib/xbrief/io.ts:338`) reads it; `applyEffectiveDifficulty` (`src/lib/agents/tier-escalation.ts`) overlays it onto an item before staffing.
- **Escalation** — moving a failing item up: retry at the same tier, then (new, optional) raise effort one level, then promote the item's effective difficulty one step (which re-staffs it on the next tier's model).
- **Effort-first** — the new opt-in `tiered_execution.escalation.effort_first: true`. Off by default.

## Problem

1. **Slots ignore tier effort.** `spawnRun`'s slot branch resolves the slot's tier model and harness, then forwards one caller effort to every slot: `src/lib/agents/spawn.ts:173-174` (`effort: options.effort,` / `effortSource: options.effortSource,`). The swarm dispatcher passes no effort at all (`deacon-swarm.ts:895`, grep `await deps.spawnRun(issueId, 'work', {`), so every slot launches at the role-file frontmatter `effort: high`, whatever `tiers.<t>.effort` says.
2. **Single-work agents ignore tier effort.** `spawnAgent` stages the caller effort into state and the launcher (`spawn.ts:705`, `spawnEffortFields(options.effort, options.effortSource)`, and `spawn.ts:810`, `effort: options.effort,`). `pan start` computes that value with no tier, and the foreman (`swarm-foreman.ts:44`) and the merge-train conflict resolver (`merge-train-deps.ts:66`) pass none.
3. **`Staffing` has no effort.** `Staffing` (`staffing.ts:35-41`) is `{ tierName, model, harness, implicit }`. `SlotTierSpawnParams` (`spawn-prep.ts:189-208`) has no effort either.
4. **Two review launches record no effort.** `spawnTierSupervisor` (`tier-supervisor.ts:132`) and the merge-train re-review (`merge-train-deps.ts:57`) pass no effort. The supervisor is a definition-less run, so its claude-code `--effort` flag already comes from the resolver inside `getRoleRuntimeBaseCommand`, but `AgentState.effort` stays empty and codex/omp/kimi launcher fields resolve without the sub-role. The re-review runs on `roles/review.md` frontmatter and ignores `roles.review.effort`.
5. **Escalation has no effort concept and no engine.** `TieredEscalationConfig` (`tier-table-types.ts:82-92`) has `enabled`, `retries_at_tier`, `max_promotions`. The decision engine `decideEscalation` was deleted as dead code by PAN-4014 (`100ead187f5`), after the Cut removed both triggers (`docs/THE-CUT.md:131-132`). Only `applyEffectiveDifficulty` and the action types survive in `tier-escalation.ts`.
6. **Settings drops tier effort.** The Tiered Execution crews editor dedupes tiers by model+harness (`staffingKey` in `src/dashboard/frontend/src/components/Settings/sections/tiered-crews.ts:95`) and `serializeCrews` writes only `model`, `harness`, `difficulties`, `distribution` (`tiered-crews.ts:177-182`). A Settings save today deletes a tier `effort` written in `config.yaml`. The Roles panel's sub-role card edits only `model` (`RolesPanel.tsx`, grep `model: patch.model as ModelRef,`).

## Decisions

- **D1 — Staffing resolves effort.** `resolveStaffing` returns `effort` and `effortSource` from `resolveEffort({ itemEffort, planEffort, tierName, role: 'work', issueId, model, harness, config })`. It is the one place a work launch's tier-aware effort is decided.
- **D2 — Implicit staffing passes no tier.** When `implicit: true`, staffing passes `tierName: undefined`. `'default'` is not a configured tier; a configured tier that happens to be named `default` must not leak into implicit staffing. Pseudo-tiers `override` and `role-default` from `resolveTier` are passed as-is; `tiers['override']` and `tiers['role-default']` are always undefined (`resolve-tier.ts` reserves both names), so the tier layer falls through to `roles.work`.
- **D3 — Distribution tiers clamp to the picked entry.** For a `distribution` tier, the resolver gets the picked entry's `model` and `harness`, not the representative's. The tier's single `effort` applies to every entry.
- **D4 — The caller-effort rule.** A launch uses the explicit caller effort when there is one. Otherwise it uses staffing's effort. Otherwise it uses the caller's value unchanged (which may be undefined, leaving today's role-file behavior). Staffing's chain is a superset of the chain `pan start` runs (it adds item, plan and tier), so replacing a non-explicit caller value with staffing's value never loses information. `pan start --effort max` still wins over a tier.
- **D5 — An explicit `--model` skips tier effort.** `resolveSlotTierSpawnParams` and `resolveSingleWorkTierSpawnParams` skip staffing when an explicit model is passed (PAN-3842). They also return no effort, so the caller's value is used. This matches the model rule: an explicit override bypasses tier routing.
- **D6 — The rule lives in one leaf module.** New `src/lib/agents/launch-effort.ts` exports `pickLaunchEffort(caller, staffed)`. It imports types only. `spawn.ts` calls it in two places. This keeps `spawn.ts` under its cap (NFR-2).
- **D7 — Review launches resolve at the callsite.** `spawnTierSupervisor` and the merge-train re-review call `resolveEffort` themselves and pass `effort` + `effortSource` to `spawnRun`. This slice does not add a general role-run default to `spawnRun`; that is [PAN-4256](https://github.com/eltmon/overdeck/issues/4256)'s scope (review parent, test, worker). The merge-train re-review does not know the model at the callsite, so it resolves without `model`; the default is `high`, which every current claude-code model accepts.
- **D8 — `effort_first` is optional in the validated shape.** `ValidatedEscalationConfig.effort_first?: boolean` is present only when the raw config sets it. A non-boolean value throws `TieredExecutionConfigError` with `tiered_execution.escalation.effort_first must be a boolean`. Omitting the key when unset keeps every existing `toEqual` on the escalation shape passing (`tests/lib/settings-api.test.ts:89`, `tier-table.test.ts:324`, `swarm-tiered-hooks.test.ts:27`).
- **D9 — Escalation order.** `decideEscalation` keeps the PAN-3858 order and inserts one step before promotion: (1) no effective difficulty → `block`; (2) `promotions >= max_promotions` → `block`; (3) difficulty `expert` → `block`; (4) `attemptsAtCurrentTier < retries_at_tier` → `retry`; (5) **new:** `effort_first === true`, the item has no `effectiveEffort` at its current difficulty, and a higher supported level exists → `raise-effort`; (6) `promote` to the next difficulty.
- **D10 — "One level" is relative to the resolved effort.** The caller passes the item's current resolved effort and, optionally, the supported levels (`supportedEffortLevels(model, harness)` from `src/lib/agents/effort-support.ts`). The next level is the first level in `EFFORT_LEVELS` above the current one that is in the supported list; an empty or missing list means no restriction. If there is no such level (already at the top, or the model supports nothing higher), step 5 is skipped and the item promotes.
- **D11 — One effort raise per difficulty; it does not count as a promotion.** An effort raise sets `TierOverride.effectiveEffort`. A promotion increments `promotions` and clears `effectiveEffort`, so the next tier starts at its own effort and may get one raise of its own. `max_promotions` counts model promotions only.
- **D12 — The raised effort reaches staffing at the `item` layer.** `applyEffectiveDifficulty` also sets `metadata.effort = override.effectiveEffort` when present. Staffing then resolves it as `source: 'item'`. This slice does not add an `escalation` value to `EffortSource` (it would change a contracts union that PAN-4253/4255 persist and display).
- **D13 — No live trigger in this slice.** The Cut removed escalation's triggers on purpose. This slice restores the pure engine `decideEscalation` and a pure applier `applyEscalationAction`, and proves the full path through `resolveStaffing` in tests. Wiring a trigger and a continue-file writer is [PAN-4512](https://github.com/eltmon/overdeck/issues/4512). The module header and the docs say plainly that no automatic trigger fires yet.
- **D14 — Escalation history is a union.** `TierOverride.history` becomes `Array<TierPromotionHistoryEntry | TierEffortRaiseHistoryEntry>`. The new entry is `{ at, kind: 'effort', from: EffortLevel, to: EffortLevel, reason }`. Existing entries (no `kind`) stay difficulty promotions. No code reads `history` today (`rg -n "\.history" src/lib/xbrief src/lib/agents` finds only the type).
- **D15 — Settings crews key on effort.** Two tiers with the same model and harness but different effort are two crews. `Crew` gains `effort?: EffortLevel`. The select offers "inherit" plus `EFFORT_LEVELS` from `@overdeck/contracts`.
- **D16 — Sub-role effort in the Roles panel.** Each sub-role card gets an effort select ("inherit" plus `EFFORT_LEVELS`). "inherit" removes the key. The server already merges `roles.<role>.sub.<name>` as whole objects (`src/lib/settings-api.ts:400-405`) and validates sub-role effort (`settings-api.ts:628`). The local `type Effort` in `RolesPanel.tsx` stays; its `lint:effort` baseline row belongs to PAN-4256.

## Repo rules that apply here (restated)

- **Effort defaults stay `high`.** Never default anything to `xhigh` or `max` (`sync-sources/rules/effort-high-default.md`). Effort-first escalation may raise to `xhigh`/`max` only because the operator opted in with `effort_first: true`.
- **No hardcoded fallbacks.** Do not add `?? 'high'` anywhere; `resolveEffort` owns the default (`npm run lint:effort`).
- **No `execSync` in server-reachable code.** `resolveEffort` is synchronous file reading only, which is allowed (PAN-4249 NFR-2). Do not add child processes.
- **File-size caps are never raised by agents.** If `spawn.ts` or `spawn-prep.ts` would exceed its cap, move code into `launch-effort.ts`.
- **Quality gates:** `npm run typecheck`, `npm run lint`, and `npx vitest run <touched test files>`. Never run the full `npm test` on the host. `npm run typecheck` excludes `*.test.ts`, so run each touched test file.
- **Tests read behavior, not source.** Do not add tests that grep source files, and do not add `skipIf`/`.only` (the test-skip gate fails them).
