# PAN-4242: Claude Code launches stall silently at the folder-trust dialog

**Issue:** [PAN-4242](https://github.com/eltmon/overdeck/issues/4242)
**Status:** planned (auto mode, 2026-11-23)
**Claude Code version probed:** 2.1.330

## Glossary

- **Folder-trust dialog** — Claude Code's startup screen titled `Accessing workspace:` with the text `Quick safety check: Is this a project you created or one you trust?`. It blocks the session until someone picks an option. Nothing reaches the transcript while it is on screen.
- **Plain trust dialog** — the variant shown for an untrusted folder. Options: `❯ No, exit` / `Yes, I trust this folder`. Choosing "No, exit" ends the session.
- **Backstop dialog** — the variant shown for a folder whose project settings carry *gated grants* (below) while the repository root is untrusted. It shows `⚠ This folder pre-approves N tool permission(s) in .claude/settings.json:` and the options `❯ No, continue without these permissions` / `Yes, I trust this folder`. It appears **even when the worktree itself is trusted**.
- **Gated grant** — a project-level setting Claude Code will not apply without repository trust. Probed: `permissions.allow` rules trigger the backstop; project `hooks` alone do not (and they still run).
- **Repository root** — the main checkout of a git repository: the parent directory of `git rev-parse --path-format=absolute --git-common-dir` when that path ends in `/.git`. For `workspaces/feature-x` of `/home/u/Projects/proj`, the repository root is `/home/u/Projects/proj`.
- **Pre-trust** — `preTrustDirectory(dir)` in `src/lib/workspace-manager/worktree-ops.ts`: sets `projects[dir].hasTrustDialogAccepted = true` and `bypassPermissionsModeAccepted = true` in `~/.claude.json` under Claude Code's own lock.
- **Launch chokepoint** — `launchAgentPane` in `src/lib/terminal-backends/launch.ts`. Every agent, planning, slot and conversation launch passes through it; it calls `preTrustClaudeCodeCwd(request)` first (PAN-3905).
- **Kickoff** — the first message a `pan handoff` successor conversation receives (the focus text for `--fresh`, the authored handoff summary otherwise), delivered by `deliverForkSeed` in `src/lib/overdeck/conversation-forks.ts`.
- **Held kickoff** — `conversations.held_kickoff` (PAN-4499): a kickoff stored instead of delivered. `claimHeldKickoff` reads and clears it in one transaction; `restoreHeldKickoff` writes it back only when the column is NULL.
- **Refused delivery** — a `DeliveryResult` with `ok: false` and `failure` starting with `refused:`. Both the Herdr path (`describeHerdrRefusal`, e.g. `refused: agent_blocked — …`) and the tmux guard (`refused: ${guard.reason}`) refuse **before any byte is typed**, so re-sending the text later cannot duplicate it.
- **Pane choice** — a blocking menu parsed from a pane screen by `parsePaneChoiceMenu` (`src/lib/pane-choice-menu.ts`) and answered with arrow keys + Enter by `answerSessionPaneChoice` (`src/lib/session-pane-choice.ts`).
- **Startup stall** — a Claude Code agent that, 180 s or more after its launch, has written no transcript since launch and whose pane shows a blocking menu.

## Background and verified evidence

### What the issue asked for

1. Pre-trust `--cwd` in the handoff spawn path.
2. Surface a blocked status for a session that has not produced its first transcript line within N seconds.
3. After a resume, re-deliver the original handoff prompt when the session never received it.

The 2026-11-23 comments add a second variant: `pan plan CLI-2` (project myn-cli) stalled 2 h 20 min at the **backstop dialog** although its worktree was trusted, and asked that `pan answer` / `answer_pane_choice` can see and answer the menu, and that a planning or work agent with no transcript a few minutes after launch is flagged.

### Fix 1 is already shipped, but un-normalized paths still miss

PR #4163 (PAN-3905, merged 2026-09-24T23:21Z) added `preTrustClaudeCodeCwd` to the launch chokepoint, and conversation launches go through it (`src/lib/overdeck/conversation-runtime.ts`, search `pane = await launchAgentPane({`). So handoff launches are pre-trusted today.

Two gaps remain:

- The handoff route only trims `--cwd` (`src/lib/overdeck/conversation-forks.ts`, search `const cwd = typeof body['cwd'] === 'string' && body['cwd'].trim()`). A trailing slash (shell completion adds one) or a symlinked path is written to `~/.claude.json` as given, but Claude Code looks up the physical cwd without a trailing slash, so the key never matches. The 2026-09-27 incident happened three days after #4163 merged; this is the most likely cause, but it is not proven.
- Trusting the worktree does not satisfy the backstop (next section).

### Probe results (Claude Code 2.1.330, isolated tmux socket, `--setting-sources project,local`, dirs under `/dev/shm` with no trusted ancestor)

| Setup | Result |
| --- | --- |
| Plain dir, untrusted | Plain trust dialog (`❯ No, exit` first) |
| Worktree pre-trusted, root untrusted, `.claude/settings.json` = `{"permissions":{"allow":["Bash(gh issue create:*)"]}}` | **Backstop dialog** |
| Same worktree, root **also** pre-trusted | No dialog; session starts |
| Worktree pre-trusted, root untrusted, settings with only `hooks` + `model` | No dialog; the SessionStart hook ran |

The `~/.claude.json` diff explains why overdeck worktrees do not stall but myn-cli ones do: `projects["/home/eltmon/Projects/overdeck"].hasTrustDialogAccepted` is `true`, `projects["/home/eltmon/Projects/myn-cli"].hasTrustDialogAccepted` is `false`. Both workspaces carry the same three `permissions.allow` rules in their synced settings.

The dialog component in the 2.1.330 bundle renders its options with `hideIndexes: true`, `cancelFirst: true`, `focus: "cancel"`, `confirmLabel: "Yes, I trust this folder"`, `cancelLabel: backstop ? "No, continue without these permissions" : "No, exit"`, and reports `{state: "blocked", kind: "permission", msg: "trust this folder"}` (which is what Herdr shows as `agent_status: blocked`).

### Why the grants are there

`copyOverdeckSettingsToWorkspace` (`src/lib/workspace-manager/migration.ts`, search `const merged = { ...globalSettings, ...workspaceSettings };`) copies the operator's whole `~/.claude/settings.json` into `<workspace>/.claude/settings.json`, `permissions.allow` included. It runs at workspace creation (`src/lib/workspace-manager/create.ts`, search `copyOverdeckSettingsToWorkspace(workspacePath)`), in `pan workspace` maintenance (`src/cli/commands/workspace-maintenance.ts`) and in hygiene (`src/lib/overdeck/workspace-hygiene.ts`). Agents run with the real `~/.claude` config (no `CLAUDE_CONFIG_DIR` anywhere in `src/lib`), so the operator's user-level allow rules already apply; the copy adds nothing but the gated grant.

### Why nothing could see or answer the menu

- `parsePaneChoiceMenu` requires options numbered from 1 (`OPTION_LINE = /^\s*(❯|›)?\s*(\d{1,2})[.)]\s+(\S.*)$/`). The trust dialog has no numbers, so it never parses.
- `pan answer` (`src/cli/commands/answer.ts`) captures with tmux `capturePane` (via `captureSessionPaneChoice`) and keys with tmux, so on a Herdr host (the default backend) it always prints `No pending choice menu`.
- Agent pane detection (`detectAwaitingInputForAgent`, `src/lib/agent-input-detection.ts`) also reads with tmux `capturePane`, which answers `''` for a Herdr pane, so `pendingInputKinds` stays empty. Herdr's `blocked` pane state does reach `derived-issue-state.ts` (`needs-you`) and the agents listing, which is why `pan show CLI-2` said `needs-you` while `list_pending_input` showed nothing.
- `resolveAgentPaneIo(agentId)` (`src/lib/terminal-backends/agent-pane-io.ts`) already reads (`pane.read`, source `visible`) and keys (`pane.send_keys`) any agent pane on Herdr, falling back to tmux. It is the door this plan uses.

### Why the kickoff is lost

`deliverForkSeed` → `injectForkSummary` → `deliverAgentMessage`. A refusal makes `assertForkDelivered` throw; the pipeline's `.catch` calls `handleForkPipelineFailure`, which sets `fork_status = 'failed'`, stores the error text and marks the conversation ended. The kickoff text is not kept anywhere a later step reads. `handleConversationResume` (`conversation-runtime.ts`, search `CONVERSATION RESUME:`) then sends only the generic resume notice built by `buildResumeContract(resumeCause)`.

## Requirements

- **FR-1** Every Claude Code launch pre-trusts the real path of its cwd (`realpath`, so no trailing slash and no symlink) in addition to the path as given.
- **FR-2** Every Claude Code launch whose cwd is inside a git working tree also pre-trusts that repository's root, unless the root is the home directory or `/`.
- **FR-3** Workspace settings sync stops copying the operator's user-level `permissions` block, and removes from an existing workspace settings file every `permissions.allow` and `permissions.additionalDirectories` entry that the user-level settings already grant.
- **FR-4** `parsePaneChoiceMenu` recognises both variants of Claude Code's folder-trust dialog as a two-option menu (in rendered order, numbered 1 and 2), in card mode and in guard mode.
- **FR-5** `pan answer <agent-or-conv>` lists and answers pane choices on Herdr and tmux hosts through `resolveAgentPaneIo`.
- **FR-6** A Claude Code agent that has written no transcript since launch 180 s or more after launch, and whose pane shows a blocking menu, reports `pendingInputKinds` containing `paneQuestion`, with a prompt that names the menu, its options and the `pan answer` command.
- **FR-7** When a fork kickoff delivery is refused, the kickoff text is stored as the conversation's held kickoff.
- **FR-8** When a conversation holding a kickoff that the operator did not ask to hold (its persisted fork request has no `hold: true`) is resumed by respawn, the held kickoff is delivered once in place of the generic resume notice; on failure it is restored.
- **FR-9** Docs describe the repository-root trust, the startup-stall signal, `pan answer` on Herdr and the undelivered-kickoff behaviour.
- **NFR-1** No `execSync` or other sync child process in any changed server-reachable code; git runs through promisified `execFile`.
- **NFR-2** `src/lib/overdeck/conversation-runtime.ts` must not grow (its `origin/main` count, 1224 lines, is also its allowlist cap). No other changed file may grow past 1000 lines.
- **NFR-3** Tests that exercise a delay use `vi.useFakeTimers()`; no real waits. Tests that touch `~/.claude.json` set `HOME` to a temp dir (the existing pattern in `tests/unit/lib/workspace-manager/pretrust-directory.test.ts`).
- **NFR-4** A kickoff is never delivered twice. A fork delivery stores the kickoff only on a refusal (nothing typed), never on a `stranded` outcome. The resume path claims the held text atomically and restores it when its own delivery throws, exactly as the existing kickoff door does; a resume delivery that throws after typing would be the same risk the door already accepts.

## Decisions

- **D1 — Trust the repository root at launch, not only at registration.** Project registration already pre-trusts the project root (`src/lib/project-registration.ts`, `src/lib/projects/create-perform.ts`), but older registrations (myn-cli) and `--cwd` handoffs into other repos are not covered. Claude Code itself says trusting a folder in a repository trusts the whole repository, so trusting the root grants nothing the worktree trust did not already imply.
- **D2 — Keep both prevention fixes.** FR-2 covers any repository, including ones whose tracked settings carry allow rules. FR-3 removes the redundant copy so a host whose root cannot be trusted (a repository rooted at `$HOME`) does not hit the backstop.
- **D3 — Recognise the trust dialog with a dedicated exact-shape detector**, anchored on the literal option `Yes, I trust this folder` plus a sibling option starting `No, ` and a harness footer hint. The numbered parser is not loosened (false positives park phantom cards in live conversations, per the module header).
- **D4 — Agents surface a startup stall as `paneQuestion`**, which the Decisions surface already renders and which needs no frontend change; the agent `paneChoice` card is not rendered by the frontend today (only conversations). The prompt tells the operator to run `pan answer <agent> <n>`.
- **D5 — Startup-stall gate:** Claude Code harness only (`getAgentState(agentId)?.harness` is `claude-code` or unset); `now - startedAt >= 180_000` ms; transcript mtime is `null` or earlier than `startedAt`; and the pane (read through `readAgentPaneText`) parses as a blocking menu in guard mode. No menu ⇒ no signal, so an idle resumed agent is never flagged.
- **D6 — Reuse `held_kickoff` for an undelivered kickoff.** A failed fork with a held kickoff renders as a held handoff (`HeldHandoffView`, `heldKickoff` needs-you kind) with a Start button; that is the intended recovery surface. Resume tells an undelivered kickoff from an operator hold by the persisted fork request: `buildForkRequest` writes `hold: true` only for `--hold` (`conversation-forks.ts`, search `...(hold ? { hold: true } : {})`). `fork_status` cannot be used: `markConversationRunning` (`conversations.ts`) resets `failed` to NULL whenever an ended row is resurrected, including the resume reattach branch. Consequence: an operator `--hold` whose Start delivery is later refused keeps `hold: true`, so a resume does not send it; the Start button still does.
- **D6a — How issue fix #2 is covered for conversations.** The handoff successor is a conversation, not an agent, so FR-6 does not apply to it. Its stall is already loud since PAN-3921: the kickoff delivery is refused (`agent_blocked`), the fork is marked failed with that error and the row ended. With WI-6 the kickoff is also held, so the conversation appears in Needs-you as a `heldKickoff` item with a Start button, and `pan answer conv-<name>` (WI-4) can answer the dialog.
- **D7 — Out of scope:** conversation pane-choice detection on Herdr for the dashboard feed and the MCP `answer_pane_choice` tool (PAN-5169 skipped it for polling cost; the refused kickoff already surfaces as a failed fork and a held handoff), and the agents `GET/POST /api/agents/:id/pane-choice` route.

```ts
/**
 * PAN-4242: the directories a Claude Code launch in `cwd` must have trusted.
 * The cwd as given and its real path (Claude Code keys trust by the physical
 * cwd, so a trailing slash or a symlink missed). Inside a git working tree,
 * also the repository root: Claude Code 2.1.x shows its trust dialog for a
 * worktree whose settings pre-approve tool permissions until the main
 * checkout is trusted, even when the worktree is. Home and `/` are never
 * added (Claude Code never saves home-directory trust).
 */
export async function claudeTrustTargets(cwd: string): Promise<string[]> {
  const targets = new Set<string>([cwd]);
  const real = await realpath(cwd).catch(() => null);
  if (real) targets.add(real);
  const root = await gitRepositoryRoot(real ?? cwd);
  if (root && root !== homedir() && root !== '/') targets.add(root);
  return [...targets];
}

/** Main checkout of the repository holding `dir`, or null outside a work tree. */
export async function gitRepositoryRoot(dir: string): Promise<string | null> {
  try {
    const { stdout } = await execFileAsync('git', ['-C', dir, 'rev-parse', '--path-format=absolute', '--git-common-dir'], { encoding: 'utf8', timeout: 5000 });
    const commonDir = stdout.trim();
    return commonDir.endsWith('/.git') ? dirname(commonDir) : null;
  } catch {
    return null;
  }
}
```

   `realpath` comes from `fs/promises`. A bare repository (common dir not ending in `/.git`) yields null.
