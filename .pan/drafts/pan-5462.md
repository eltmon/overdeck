# PAN-5462 — Computer use on Windows (WSL2) with Orca's PowerShell helper

**Issue:** [PAN-5462](https://github.com/eltmon/overdeck/issues/5462)
**Depends on:** PAN-5461 (Settings page + the platform provider seam in `src/lib/computer-use/platform.ts`). PAN-5452 shipped `pan computer` for Linux.
**Sibling:** PAN-5463 (macOS).

## Summary

Overdeck runs on Windows inside WSL2 (native Windows is unsupported; see `configuration/session-vault.mdx` and the changelog note on PAN-4421). This issue lets `pan computer` and Settings → Computer Use drive the **Windows desktop** from WSL2, by vendoring Orca's Windows helper `native/computer-use-windows/runtime.ps1` (MIT, 1821 lines, built-in .NET UI Automation, no installs) and running it through WSL interop with `powershell.exe`.

Nothing has to be installed on Windows: Windows PowerShell 5.1 and UI Automation ship with Windows 10/11. Setup is one click: copy the helper, test it, turn the flag on.

## Glossary

- **WSL interop**: WSL2's ability to run Windows `.exe` files from Linux. Enabled when `/proc/sys/fs/binfmt_misc/WSLInterop` (or `WSLInterop-late`) exists.
- **Windows side / Linux side**: Windows paths (`C:\…`) vs WSL paths (`/mnt/c/…`). Convert with `wslpath -w <linux>` and `wslpath -u <windows>`.
- **Helper dir**: `%LOCALAPPDATA%\Overdeck\computer-use\` on the Windows side. The helper script and operation files live here, never on `\\wsl.localhost\…` (PowerShell treats UNC paths as remote and execution policy may block them).
- **Provider**: `ComputerUseProvider` from PAN-5461's `platform.ts`. This issue adds the `wsl` provider.
- **One-shot call**: run `powershell.exe -File runtime.ps1 <opfile>` once per operation; the script prints one JSON object. Orca also has a persistent `-Serve` mode; we don't use it (D-3).
- **Seam**: everything PAN-5461 creates that this issue builds on: `platform.ts` (types, `detectPlatform`, `providerFor`), the `platform` parameter of `assertKeyComboAllowed`, the readiness refactor of `doctor-computer-use.ts`, and `ComputerUseSection.tsx`. This issue never creates or redefines any part of it.
- **Message prefix**: the Windows helper reports failures as `{ "ok": false, "error": "<code>: <text>" }` (for example `target_elevated: …`, `window_not_focused: …`). The prefix is part of the message, not a separate error code.

## Decisions

- **D-1 Platform:** `detectPlatform()` already returns `'wsl'` (PAN-5461 D-9). This issue registers `providerFor('wsl') → wslProvider`. The Linux/WSLg path is never used under WSL.
- **D-2 Executable:** resolve `powershell.exe` (Windows PowerShell 5.1) in this order: `which powershell.exe` (WSL appends the Windows PATH by default), then `/mnt/c/Windows/System32/WindowsPowerShell/v1.0/powershell.exe`. Never `pwsh` (Orca only tests 5.1; the script's `Add-Type -ReferencedAssemblies 'System.dll'` may not resolve on 7).
- **D-3 One-shot per call, not `-Serve`.** `pan computer` is one CLI process per command, and the desktop lock already serializes calls. Cost: `Add-Type` compiles the C# P/Invoke class on every call (~1–2 s). Accepted for v1; measure it in WI-7 and record the number.
- **D-4 Arguments:** `-NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -File <win helper path> <win op path>` (the same list as Orca's `windowsPowerShellRuntimeArgs` in `src/main/computer/desktop-script/runtime-host/windows-powershell-execution-policy.ts`). `Bypass` is process-scoped and needs no admin. Orca tries `RemoteSigned` first and retries with `Bypass`; we go straight to `Bypass` because the script is a file Overdeck itself wrote to a local path, and a retry would double the cost of a one-shot call. A Group Policy that enforces `AllSigned` overrides `-ExecutionPolicy`; then stderr matches `/\bUnauthorizedAccess\b|\bSecurityError\b|about_Execution_Policies/` and the bridge throws `helper_error` with the message `Windows execution policy blocked the computer-use helper (set by Group Policy). Ask the PC's administrator to allow local scripts.`
- **D-5 Files:** on every call, read the vendored `native/computer-use-windows/runtime.ps1` and the helper-dir copy; when the copy is missing or its sha256 differs, write the vendored bytes over it. Write each operation to `<helper dir>\ops\<uuid>.json`, delete it in `finally`. Resolve `%LOCALAPPDATA%` with `powershell.exe -NoLogo -NoProfile -NonInteractive -Command "[Environment]::GetFolderPath('LocalApplicationData')"`, convert with `wslpath -u`, append `Overdeck/computer-use`, and cache the resulting Linux path in `~/.overdeck/computer-use/windows-helper-dir.txt` so later CLI processes skip the extra PowerShell start. Re-resolve when the cached directory no longer exists. File modes on `/mnt/c` (drvfs) are not enforced without the `metadata` mount option; op files are short-lived and deleted in `finally`, so this is accepted and documented.
- **D-6 Output:** parse the last non-empty stdout line (trimmed, so a trailing `\r` is dropped) as JSON, exactly like the Linux helper. Extract that logic from `helper.ts` into an exported `parseHelperOutput(stdout, stderr)` so both bridges share one parser. Screenshots arrive inline as `screenshotPngBase64`, the same key the Linux helper uses, so `snapshot-store.ts` needs no change.
- **D-7 Timeouts:** 30 s per call (Orca's value and the Linux helper's `HELPER_TIMEOUT_MS`), `killSignal: 'SIGKILL'`, `maxBuffer` 64 MiB (the same as the Linux helper's `HELPER_MAX_BUFFER`; a full-screen PNG in base64 can exceed 20 MiB on a 4K display). On timeout, the interop stub is killed and the bridge throws `helper_timeout`. Killing the interop stub may leave the Windows `powershell.exe` running; one-shot mode gives no reliable Windows PID, so accept that risk and document it. The script's own operations are bounded (`SendMessageTimeout` 5 s, UIA calls), so orphans should be rare.
- **D-8 Blocked shortcuts:** port Orca's `WINDOWS_RULES` (Orca `src/main/computer/action-contracts/computer-blocked-key-combos.ts` lines 47–69 at `c6b9ac9549b`): Alt+F4 ("close the app"), Win+L ("lock Windows"), Ctrl+Shift+Escape ("open Task Manager"); aliases meta/super/win/cmd/command → `win`, cmdorctrl/commandorcontrol → `ctrl`, option → `alt`; key aliases `esc` → `escape`. The wsl provider sets `blockedKeyPlatform: 'windows'`.
- **D-9 Port record:** `runtime.ps1` gets the port header as `#` comment lines **before** the `param(` block (comments may precede `param` in PowerShell); add a record to `scripts/upstream-ports.json` and a `.ps1` case next to the `.py` case in `scripts/upstream-port-diff.sh` (line ~105, `if [[ "$local_path" == *.py ]]`). Upstream commit: **`c6b9ac9549b`**, the commit every other Orca record uses; verified at planning time that `runtime.ps1` at `c6b9ac9549b` is byte-identical to Orca's current HEAD. Copy the file with `git -C ~/Projects/orca show c6b9ac9549b:native/computer-use-windows/runtime.ps1`, never from the working tree.
- **D-10 File size:** `lint:file-size` only scans `src/**/*.ts(x)`, so the vendored script is exempt. TypeScript added here stays under 1000 lines per file.
- **D-11 Known limits, documented not fixed:** `list_windows` returns only the main window (always `index: 0`); DPI-aware only on the capture thread (mixed-DPI setups may misplace clicks); an elevated (admin) target app refuses input with a `target_elevated:` message; a WSL terminal started as admin runs an elevated helper; WSL1 is not supported (no `WSLInterop` binfmt entry); a Group Policy execution policy blocks the helper (D-4).
- **D-12 Element identity:** Windows matches elements by UIA `runtimeId` only (no signature check like Linux). Our snapshot cache stores the full element record exactly as on Linux; no change. The Windows snapshot carries `windowId` and no `windowIndex`; `snapshot-store.ts` already stores `windowIndex ?? null` and `format.ts` prints `[index -]`, so no change.
- **D-13 Packaging:** `package.json` `files` already lists the whole `native` dir (line ~75), so `native/computer-use-windows/` ships without an edit. WI-7's pack job proves it (`tar tzf` lists `package/native/computer-use-windows/runtime.ps1`).
- **D-14 Encoding:** `runtime.ps1` is pure ASCII with no BOM (checked at planning time). Windows PowerShell 5.1 reads a BOM-less script in the ANSI code page, so the two header lines must stay ASCII and the file must never gain a BOM or CRLF conversion. `native/computer-use-windows/.gitattributes` is not needed because the repo stores it with LF and PowerShell accepts LF.
- **D-15 Error mapping:** the bridge behaves exactly like `helper.ts`'s `runHelper`: a response with `ok: false` throws `ComputerUseError('helper_error', <error message>)`, so `run.ts` and every command keep assuming a returned response is a success. Message prefixes (`target_elevated:`, `window_not_focused:`, `stale element:`) stay inside the `helper_error` message; no new `ComputerUseErrorCode` values. The skill tells agents to read the prefix.
- **D-17 Interop env for services:** WSL runs a Windows `.exe` through the interop socket named by `WSL_INTEROP`. A shell started by WSL has it; the dashboard runs as a systemd user unit and may not. When the env passed to `execFile` lacks `WSL_INTEROP` and `/run/WSL/` contains `*_interop` sockets, the bridge sets `WSL_INTEROP` to `/run/WSL/1_interop` if it exists, else to the socket with the lowest numeric pid prefix. This is a cheap guard that can't be verified here (no Windows host); the WI-7 WSL job runs `pan computer` from a shell, so the service path stays unverified. If the operator's first Settings test fails with "Exec format error" or a vsock error while the CLI works, this guard is the place to look.
  **Implementation checkpoint (CI, WI-7 step 2):** the WSL job also runs `env -u WSL_INTEROP /mnt/c/Windows/System32/WindowsPowerShell/v1.0/powershell.exe -NoProfile -Command 1` and `env -u WSL_INTEROP pan computer list-apps --json`, and writes both exit codes to the job summary. **Fallback:** the guard only acts when the variable is missing, so it stays either way. If the second command fails, file a follow-up issue with the output and link it from the PR body.
- **D-18 Atomic copy:** `ensureHelperCopied` writes `runtime.ps1.tmp-<uuid>` in the helper dir and renames it over `runtime.ps1`, so a concurrent reader never sees a half-written script.
- **D-16 WSL1:** unsupported. The `interop` check reads only the `WSLInterop`/`WSLInterop-late` binfmt entries, which WSL1 doesn't have, so WSL1 reports interop `missing`.

## Requirements

### Functional
- **FR-1** Under WSL2 with interop, `pan computer capabilities --json` reports `desktopSession: { ok: true, label: 'windows · <build>' }`, where `<build>` is `[Environment]::OSVersion.Version` from `windowsVersion()` (WI-1; the handshake carries no OS build),, and the helper handshake with `platform: "win32"` and `provider: "orca-computer-use-windows"`. It never reports WSLg's `XDG_SESSION_TYPE`/`DISPLAY` as the session.
- **FR-2** Every `pan computer` subcommand works under WSL2 against Windows apps, using the same CLI flags and output as Linux. `list-windows` lists one window (index 0, the main window) per app (D-11).
- **FR-3** The wsl provider's `readiness()` reports: `interop` (WSL interop enabled), `powershell` (powershell.exe found and runs), `helper-dir` (helper dir writable from WSL), `helper` (handshake). `setupSteps` is empty when interop and PowerShell work — the helper copy happens automatically in `runHelper`, and the route adds `enable-flag` + `test-helper`.
- **FR-4** When interop is off, the `interop` check is `missing` with `fixCommand`: `Enable interop in /etc/wsl.conf ([interop] enabled=true), then run wsl --shutdown from Windows.` and Settings shows the off state with that command.
- **FR-5** Blocked Windows shortcuts are refused with `system_shortcut_blocked` unless `--allow-system-shortcut`.
- **FR-6** Settings → Computer Use on WSL shows the same card as Linux with Windows wording (WI-5).
- **FR-7** `pan doctor` (feature on) under WSL reports the four readiness checks.

### Non-functional
- **NFR-1** No sync child processes in server-reachable code (repo rule). Use promisified `execFile`.
- **NFR-2** Tests use fakes for `execFile`/fs; timeouts under `vi.useFakeTimers()` (repo rule `fake-timers-for-retry-tests`: never a real `setTimeout` delay in a test).
- **NFR-3** No new `route-scopes.ts` rows; reuse PAN-5461 routes.
- **NFR-4** The vendored script body is byte-identical to upstream at `c6b9ac9549b`; only the two header lines differ.

`runWindowsHelper` steps: resolve powershell (null → `ComputerUseError('no_desktop_session', 'powershell.exe was not found …')`) → resolve helper dir → `mkdir <linux>/ops` recursive → ensure copied → write `ops/<uuid>.json` → `wslpath -w` the helper path and the op path (two `execFile('wslpath', ['-w', p])` calls; trim output) → `execFile(powershell, D-4 args, { env, timeout: 30_000, killSignal: 'SIGKILL', maxBuffer: 64 MiB })` → `parseHelperOutput` → `ok:false` → `helper_error` with the helper's `error` string → `rm` op file in `finally`. Failure mapping: `killed === true` → `helper_timeout`; non-zero exit whose stderr matches the D-4 execution-policy regex → `helper_error` with the D-4 message; any other non-zero exit → `helper_error` with the last 500 chars of stderr; unparsable output → `helper_error` (from `parseHelperOutput`).

`readiness-wsl.ts` exports `wslReadiness(options: { probeHelper: 'wait' | 'if-free' }, deps?): Promise<ReadinessReport>` with four checks in order (labels in parentheses):
- `interop` (Windows interop): `ok`, detail "enabled", when `interopEnabled()`; else `missing`, detail "WSL can't run Windows programs", `fixCommand` = the FR-4 text. When missing, the next three checks are `unavailable` with detail "needs Windows interop".
- `powershell` (Windows PowerShell): call `windowsVersion()` (below); `ok` with detail `PowerShell <version>`; not found or failed → `missing`, detail "powershell.exe not found or failed to start".
- `helper-dir` (Helper folder): resolve the helper dir and write+remove a probe file there; `ok` with the Windows path as detail; failure → `missing` with the error message.
- `helper` (Helper test): handshake via `runWindowsHelper({ tool: 'handshake' })`, wrapped like the Linux provider does for `probeHelper` (`if-free` → `tryWithDesktopLock` with 2 s wait; skipped → `ok`, detail "skipped: an agent is using the desktop"). `ok` detail: `handshake ok`; failure → `missing` with the error message.
`setupSteps` is always `[]` (FR-3). `session` is `{ ok: true, label: 'windows · <build>' }` when interop and PowerShell are ok, else `{ ok: false, message: <first failing check's detail> }`.

`providers/wsl.ts`: `resolveSession()` checks `interopEnabled()` then `resolvePowershell()`; on failure returns `{ ok:false, code:'no_desktop_session', message }` — interop off → the FR-4 text; PowerShell missing → `powershell.exe was not found. WSL normally adds the Windows PATH; check appendWindowsPath in /etc/wsl.conf.` On success: `{ ok: true, session: { label: 'windows', env: process.env } }`. `readiness` → `wslReadiness`. `runHelper(op)` → `runWindowsHelper(op)`. `runSetupStep` → `{ status: 'skipped' }` for every id. `blockedKeyPlatform: 'windows'`.
