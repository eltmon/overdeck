# PAN-5462 — Computer use on Windows (WSL2) with Orca's PowerShell helper

**Issue:** [PAN-5462](https://github.com/eltmon/overdeck/issues/5462)
**Depends on:** PAN-5461 (Settings page + the platform provider seam in `src/lib/computer-use/platform.ts`). PAN-5452 shipped `pan computer` for Linux.
**Sibling:** PAN-5463 (macOS).

## Summary

Overdeck runs on Windows inside WSL2 (native Windows is unsupported; see `configuration/session-vault.mdx` and the changelog note on PAN-4421). This issue lets `pan computer` and Settings → Computer Use drive the **Windows desktop** from WSL2, by vendoring Orca's Windows helper `native/computer-use-windows/runtime.ps1` (MIT, 1821 lines, built-in .NET UI Automation, no installs) and running it through WSL interop with `powershell.exe`.

Nothing has to be installed on Windows: Windows PowerShell 5.1 and UI Automation ship with Windows 10/11. Setup is one click: copy the helper, test it, turn the flag on.

## Glossary

- **WSL interop**: WSL2's ability to run Windows `.exe` files from Linux. Enabled when `/proc/sys/fs/binfmt_misc/WSLInterop` (or `WSLInterop-late`) exists.
- **Windows side / Linux side**: Windows paths (`C:\…`) vs WSL paths (`/mnt/c/…`). Convert with `wslpath -w <linux>` and `wslpath -u <windows>`.
- **Helper dir**: `%LOCALAPPDATA%\Overdeck\computer-use\` on the Windows side. The helper script and operation files live here, never on `\\wsl.localhost\…` (PowerShell treats UNC paths as remote and execution policy may block them).
- **Provider**: `ComputerUseProvider` from PAN-5461's `platform.ts`. This issue adds the `wsl` provider.
- **One-shot call**: run `powershell.exe -File runtime.ps1 <opfile>` once per operation; the script prints one JSON object. Orca also has a persistent `-Serve` mode; we don't use it (D-3).

## Decisions

- **D-1 Platform:** `detectPlatform()` already returns `'wsl'` (PAN-5461 D-9). This issue registers `providerFor('wsl') → wslProvider`. The Linux/WSLg path is never used under WSL.
- **D-2 Executable:** resolve `powershell.exe` (Windows PowerShell 5.1) in this order: `which powershell.exe` (WSL appends the Windows PATH by default), then `/mnt/c/Windows/System32/WindowsPowerShell/v1.0/powershell.exe`. Never `pwsh` (Orca only tests 5.1; the script's `Add-Type -ReferencedAssemblies 'System.dll'` may not resolve on 7).
- **D-3 One-shot per call, not `-Serve`.** `pan computer` is one CLI process per command, and the desktop lock already serializes calls. Cost: `Add-Type` compiles the C# P/Invoke class on every call (~1–2 s). Accepted for v1; measure it in WI-7 and record the number.
- **D-4 Arguments:** `-NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -File <win helper path> <win op path>`. `Bypass` is process-scoped and needs no admin.
- **D-5 Files:** on first use (and whenever the vendored file's sha256 differs from the copy), copy `native/computer-use-windows/runtime.ps1` into the helper dir. Write each operation to `<helper dir>\ops\<uuid>.json`, delete it after the call. Resolve `%LOCALAPPDATA%` once per process with `powershell.exe -NoProfile -Command "[Environment]::GetFolderPath('LocalApplicationData')"` (or `cmd.exe /c echo %LOCALAPPDATA%`), then `wslpath -u` it.
- **D-6 Output:** read stdout, strip a trailing `\r`, `JSON.parse`. Screenshots arrive inline as `screenshotPngBase64`, the same key the Linux helper uses, so `snapshot-store.ts` needs no change.
- **D-7 Timeouts:** 30 s per call (Orca's value), `maxBuffer` 20 MiB. On timeout, kill the WSL-side interop process and return `helper_timeout`. Killing the interop stub may leave the Windows `powershell.exe` running; one-shot mode gives no reliable Windows PID, so accept that risk, log the timeout, and document it. The script's own operations are bounded (`SendMessageTimeout` 5 s, UIA calls), so orphans should be rare.
- **D-8 Blocked shortcuts:** port Orca's `WINDOWS_RULES` (Orca `src/main/computer/action-contracts/computer-blocked-key-combos.ts` lines 47–69): Alt+F4, Win+L, Ctrl+Shift+Escape; aliases cmd/command/meta/super/win → `win`, cmdorctrl → `ctrl`. The wsl provider sets `blockedKeyPlatform: 'windows'`.
- **D-9 Port record:** `runtime.ps1` gets the port header as `#` comment lines **before** the `param(` block (comments may precede `param` in PowerShell); add a record to `scripts/upstream-ports.json` and a `.ps1` branch next to the `.py` branch in `scripts/upstream-port-diff.sh` (the `.py` branch says "a .py port carries it as # ..."). Upstream commit: the Orca commit the file is copied from (`git -C ~/Projects/orca log -1 --format=%h -- native/computer-use-windows/runtime.ps1`; record the short hash).
- **D-10 File size:** `lint:file-size` only scans `src/**/*.ts(x)` (`scripts/lint-file-size.sh` line ~144), so the vendored script is exempt. TypeScript added here stays under 1000 lines per file.
- **D-11 Known limits, documented not fixed:** `list_windows` returns only the main window; DPI-aware only on the capture thread (mixed-DPI setups may misplace clicks); an elevated (admin) target app refuses input with `target_elevated`; a WSL terminal started as admin runs an elevated helper.
- **D-12 Element identity:** Windows matches elements by UIA `runtimeId` only (no signature check like Linux). Our snapshot cache passes the full element record exactly as on Linux; no change.
- **D-13 Packaging:** add `native/computer-use-windows/` under the existing `native` entry in `package.json` `files` (already covers the whole `native` dir — verify with `npm pack --dry-run | grep runtime.ps1`).

## Requirements

### Functional
- **FR-1** Under WSL2 with interop, `pan computer capabilities --json` reports `platform: 'wsl'`, a session label `windows · <Windows build>` (from the handshake), and the helper capabilities.
- **FR-2** Every `pan computer` subcommand works under WSL2 against Windows apps, using the same CLI flags and output as Linux.
- **FR-3** The wsl provider's `readiness()` reports: `interop` (WSL interop enabled), `powershell` (powershell.exe found and runs), `helper-dir` (helper dir writable from WSL), `helper` (handshake). `setupSteps` is empty when interop and PowerShell work — the helper copy happens automatically in `runHelper`, and the route adds `enable-flag` + `test-helper`.
- **FR-4** When interop is off, the `interop` check is `missing` with `fixCommand`: `Enable interop in /etc/wsl.conf ([interop] enabled=true), then run wsl --shutdown from Windows.` and Settings shows the off state with that command.
- **FR-5** Blocked Windows shortcuts are refused with `system_shortcut_blocked` unless `--allow-system-shortcut`.
- **FR-6** Settings → Computer Use on WSL shows the same card as Linux with Windows wording (WI-5).
- **FR-7** `pan doctor` (feature on) under WSL reports the four readiness checks.

### Non-functional
- **NFR-1** No sync child processes in server-reachable code (repo rule). Use promisified `execFile`.
- **NFR-2** Tests use fakes for `execFile`/fs; timeouts under `vi.useFakeTimers()`.
- **NFR-3** No new `route-scopes.ts` rows; reuse PAN-5461 routes.

### WI-1 The wsl provider
**Files:** new `src/lib/computer-use/providers/wsl.ts`, new `src/lib/computer-use/wsl-bridge.ts`; edit `src/lib/computer-use/platform.ts` (`providerFor` case `'wsl'`); tests `src/lib/computer-use/__tests__/wsl-bridge.test.ts`, `providers-wsl.test.ts`.

`wsl-bridge.ts` exports:
```ts
export interface WslBridgeDeps { execFile?: ExecFileFn; readFile?: …; writeFile?: …; mkdir?: …; rm?: …; which?: (cmd: string) => Promise<string | null>; }
export async function resolvePowershell(deps?): Promise<string | null>;               // D-2
export async function resolveHelperDir(deps?): Promise<{ win: string; linux: string }>; // D-5, cached per process
export async function ensureHelperCopied(dir, deps?): Promise<void>;                  // sha256 compare, copy
export async function runWindowsHelper(operation: Record<string, unknown>, deps?): Promise<HelperResponse>; // D-3..D-7
export async function interopEnabled(deps?): Promise<boolean>;                        // binfmt_misc check
```
`runWindowsHelper`: ensure copied → write `ops/<uuid>.json` (mode 0600 on the Linux side) → `wslpath -w` both paths → `execFile(powershell, args, { timeout: 30_000, maxBuffer: 20 MiB })` → parse → `rm` op file in `finally`. Map failures: non-zero exit with JSON on stdout → return it (the helper reports its own `{ok:false,error}`); unparsable output → `ComputerUseError('helper_error', <first 500 chars of stderr>)`; timeout → `helper_timeout`.

`providers/wsl.ts`: `resolveSession()` checks `interopEnabled()` and `resolvePowershell()`; on failure returns `{ ok:false, code:'no_desktop_session', message }` with the specific reason. Session label: `windows` (enriched with the handshake's OS version when `readiness` runs). `runHelper` → `runWindowsHelper`. `runSetupStep` → returns `{ status: 'skipped' }` for every id (nothing to install). `blockedKeyPlatform: 'windows'`.
