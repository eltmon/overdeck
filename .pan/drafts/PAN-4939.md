# PAN-4939 — MCP schedule tools: scheduled messages and recurring schedules (PAN-4927 W-SCHED1)

**Status:** planned · **Revision:** 1 (2026-11-03) · **Author:** Claude Opus 5.5 (planning agent, `pan plan --auto`)
**Issue:** [PAN-4939](https://github.com/eltmon/overdeck/issues/4939) · **Epic:** [PAN-4927](https://github.com/eltmon/overdeck/issues/4927), PRD `.pan/drafts/pan-4927.md`, section "W-SCHED1" (FR-5, AC-10) · **Depends on:** W-MCP1 ([PAN-4931](https://github.com/eltmon/overdeck/issues/4931), closed and merged: `scope`/`audience` on every tool, `visibleTools`, `PATCH`/`DELETE` in `dashboard-api.ts`).

**Why.** Overdeck already has two scheduling doors for a conversation: one-shot *scheduled messages* (PAN-4641) and recurring *schedules* (PAN-4640). Agents and bots can reach them only through `pan` over Bash (as `admin`) or not at all. This item gives the Overdeck MCP server five tools over the existing routes and moves the four recurring-schedule routes out of the implicit `admin` default into the route-scope table, so a scoped token can use them. No new HTTP route, no new library code.

---

## Glossary

- **MCP tool:** an `OverdeckTool` (`src/lib/mcp/tool.ts:21-31`): `name`, `description`, `inputSchema`, `scope`, `audience`, `run(args, ctx)`. Every tool proxies one or more dashboard routes through `ctx.api.request(method, path, body?)` with the caller's bearer token.
- **Route-scope table:** `ROUTE_SCOPES` in `src/dashboard/server/route-scopes.ts:28-…`. Each row is `{ method, path, scope }`. An unlisted `METHOD path` needs `admin` (`requiredScopeFor`, line 226).
- **Scheduled message (the "once" kind):** a row in `conversation_scheduled_messages`, managed only by `src/lib/overdeck/conversation-scheduled-messages.ts`. It is **not** a timer. The server computes `not_before` from the conversation's usage limit (`computeNotBefore`, line 58): if the conversation is not rate-limited it is due **now**; if it is limited it is held until the limit resets plus 60 s (or 15 min when the reset time is unknown). Claude Code conversations only. Statuses: `pending → sending → sent → delivered`, plus `failed`, `unknown`.
- **Schedule (the "recurring" kind):** a row in `conversation_schedules`, managed only by `src/lib/overdeck/conversation-schedules.ts`: one prompt, a 5-field cron, an IANA time zone, `enabled`. The dashboard sweep fires it.
- **`kind`:** the tool argument `'once' | 'recurring'` that picks between the two route families in `update_scheduled` and `delete_scheduled`.
- **Linked conversation name:** `@<machine label|environment id>/<name>`. `linked-conversation-proxy.ts` forwards `METHOD /api/conversations/%40<m>%2F<name>/<rest>` to the owner machine for every method (header comment, lines 1-25), and `requiredScopeFor` strips the `@<m>` segment (route-scopes.ts:226-232).
- **`scopeSatisfies(granted, required)`** (`src/lib/access-tokens.ts:172-175`): `admin` satisfies everything; `operate` satisfies `tell`; otherwise an exact match. **`tell` does not satisfy `read:conversations`.**

### Origin and CSRF

Every route above calls `validateOrigin(request)`. A request with no `Origin`/`Referer` passes for `GET`, and passes for `POST`/`PATCH`/`DELETE` when it carries `Authorization: Bearer odk_…` (`validateOriginHeaders`, `routes/origin-validation.ts:135-145`). The MCP client always sends that header, so the tools work without any route change. The schedule routes do not call the opt-in `rejectUnsafeDashboardMutationRequest` (`routes/dashboard-auth.ts:259`), and even that check lets a `kind: 'token'` credential skip Origin and CSRF (line 274). The only other layer is the global remote request gate, which judges the token's scopes against `route-scopes.ts` — the rows WI-1 adds.

## Requirements

### Functional

- **FR-1** `GET /api/conversations/:name/schedules` needs `read:conversations`; `POST /api/conversations/:name/schedules`, `PATCH /api/conversations/:name/schedules/:id` and `DELETE /api/conversations/:name/schedules/:id` need `tell`. The same holds for the linked form `/api/conversations/@<m>/<name>/schedules[/:id]`.
- **FR-2** Tool `schedule_message` queues a one-shot scheduled message on a conversation through `POST …/scheduled-messages`.
- **FR-3** Tool `schedule_recurring` creates a recurring schedule through `POST …/schedules`.
- **FR-4** Tool `list_scheduled` returns both kinds for one conversation as `{ once, recurring, onceSupported, usageLimit }`.
- **FR-5** Tool `update_scheduled` edits a pending one-shot message (`kind: 'once'`) or a schedule (`kind: 'recurring'`).
- **FR-6** Tool `delete_scheduled` cancels a one-shot message or deletes a schedule, chosen by `kind`.
- **FR-7** The five tools are in `ALL_TOOLS` with `audience: 'any'` and the scope of the route they call. A token with `read:conversations` and `tell` lists and uses all five; a `read:conversations`-only token lists `list_scheduled` and none of the other four (epic AC-10).
- **FR-8** Every conversation argument accepts a linked name `@<machine>/<name>`, sent percent-encoded as one path segment.
- **FR-9** The docs list the five tools, their scopes and their limits, and the scope table names schedules.

### Non-functional

- **NFR-1 One authority.** Each tool calls only the routes named here; no tool imports `src/lib/overdeck/*` or validates fields the route already validates, except the argument-shape checks listed per tool. `route-scopes.ts` stays the only scope authority (epic NFR-1).
- **NFR-2 Module boundary.** `src/lib/mcp/tools-schedule.ts` imports only `./tool.js` (and types). No `@overdeck/contracts`, no dashboard server code (server.ts:15-16).
- **NFR-3 No new route.** No change to `src/dashboard/server/routes/*` or `tests/unit/lib/overdeck/no-loss-matrix.ts`.
- **NFR-4 Size.** `tools-schedule.ts` stays under 600 lines; `tools-schedule.test.ts` under 600 lines.
- **NFR-5 Tests.** No real timers or sleeps; the tools have no timing logic, so no fake timers are needed. Run only touched test files (`npx vitest run <files>`), never the full `npm test`.
- **NFR-6 Effect boundary.** No Effect code is added; `npm run lint:effect-facades` must not rise.

## Decisions

- **D-1 Tool names and scopes** (copied from the epic): `schedule_message` `tell`, `schedule_recurring` `tell`, `list_scheduled` `read:conversations`, `update_scheduled` `tell`, `delete_scheduled` `tell`. All `audience: 'any'` (bots use them too).
- **D-2 The once kind has no time argument.** The route accepts only `message`; delivery time comes from the usage limit. `schedule_message`'s description must say so: "Queue a message to send to a Claude Code conversation after its usage limit resets. If the conversation is not rate-limited, Overdeck sends it within a minute." An agent that wants a message at a clock time uses `schedule_recurring`. Inventing a `sendAt` field is out of scope.
- **D-3 `conversation` is required on every tool.** The tool layer has no caller identity (`McpToolContext` has only `isAgent`), so there is no "self" default. Agents get their own conversation name from their launch context or `list_conversations`.
- **D-4 Cron only, no presets.** `schedule_recurring` takes a 5-field `cron`. `presetToCron` lives in `@overdeck/contracts`, which the MCP module must not import (NFR-2). The description gives examples: `0 9 * * 1-5` (weekdays 09:00), `0 21 * * *` (daily 21:00), `0 * * * *` (hourly).
- **D-5 Route validation is not duplicated.** Tools check only argument *shape*: required non-empty strings (`requiredString`), optional strings (`optionalString`), `kind` ∈ {`once`, `recurring`}, `id` a positive safe integer, `enabled` a boolean when present. Everything else (lengths, cron, zone, spacing, limits, harness support) comes back as the route's error through `routeErrorResult` (`HTTP <status>: <error>`).
- **D-6 `list_scheduled` shape.** It sends the two GETs in parallel (`Promise.all`). If the scheduled-messages GET is not 2xx, it returns that route error; else if the schedules GET is not 2xx, it returns that route error. On success it returns `{ once: <messages array>, recurring: <schedules array>, onceSupported: <supported>, usageLimit: <limit> }`. Why: the epic names `{ once, recurring }`; `onceSupported` and `usageLimit` tell the caller whether and when a once message will fire, at no cost. A partial result is not returned, so a caller never mistakes "the other half failed" for "empty".
- **D-7 `update_scheduled` and `delete_scheduled` refuse cross-kind fields.** With `kind: 'once'`, any of `prompt`, `cron`, `timeZone`, `enabled` is a tool error "prompt, cron, timeZone and enabled apply only to kind recurring"; `message` is required. With `kind: 'recurring'`, `message` is a tool error "message applies only to kind once"; the present fields among `prompt`, `cron`, `timeZone`, `enabled` are copied into the body; an empty patch is sent and the route answers 400 "Provide at least one of prompt, cron, timeZone, enabled". Why: a silently ignored field is worse than an error, and the empty-patch message already exists in the route.
- **D-8 `id` helper is local.** `tools-schedule.ts` defines a private `requiredId(args)` (positive safe integer, error "id must be a positive integer"). Why: `tool.ts` is shared with in-flight siblings (W-SELF1, W-DEL1, W-APPR1); not touching it avoids conflicts.
- **D-9 Tool order.** `ALL_TOOLS = [...READ_TOOLS, ...WRITE_TOOLS, ...SCHEDULE_TOOLS, ...APPROVE_TOOLS]`; `SCHEDULE_TOOLS = [schedule_message, schedule_recurring, list_scheduled, update_scheduled, delete_scheduled]`. The approval tools stay last, so `tools-approve.test.ts`'s "close the list" assertion still reads true.
- **D-10 Paths.** `const base = (conversation: string) => \`/api/conversations/${encodeURIComponent(conversation)}\`;` then `${base}/scheduled-messages`, `${base}/scheduled-messages/${id}`, `${base}/schedules`, `${base}/schedules/${id}`. This is the encoding `send_message` uses (`tools-write.ts:61`), so `@desk/conv-a` becomes `%40desk%2Fconv-a` and the linked proxy forwards it.
- **D-11 A linked owner must run this version.** On an older owner the `/schedules` routes still need `admin`, so a token gets 403 `insufficient_scope` there. Accept and document it in `configuration/mcp.mdx` "Fleet reach".
