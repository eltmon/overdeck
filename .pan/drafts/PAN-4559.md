# PAN-4559 — Cap domain-event gap replay and fall back to a snapshot

**Issue:** [PAN-4559](https://github.com/eltmon/overdeck/issues/4559)
**Follow-up filed during planning:** [PAN-4566](https://github.com/eltmon/overdeck/issues/4566) (a *failed* replay wedges the tab; out of scope here)

## Glossary

- **Domain event** — one row in the `events` table of `~/.overdeck/overdeck.db`, with a monotonic `sequence` (SQLite `INTEGER PRIMARY KEY AUTOINCREMENT`). The server streams them to the dashboard over `/ws/rpc` (`subscribeDomainEvents`).
- **Sequence gap** — the client received an event whose `sequence` is not `latestSequence + 1`. The recovery coordinator classifies it as `recover`.
- **Replay / catch-up** — the client asks the server for every event after `fromSequence` with the unary RPC `pan.replayEvents` (`WS_METHODS.replayEvents`), then applies them in order.
- **Bootstrap / snapshot recovery** — the client fetches the full current read model with `pan.getSnapshot` and replaces its store (`syncSnapshot`). Implemented by `bootstrap()` in `EventRouter.tsx`.
- **Replay cap** — the new upper bound on one replay: at most `REPLAY_MAX_EVENTS = 500` stored rows **and** at most `REPLAY_MAX_PAYLOAD_BYTES = 1 MiB` (1,048,576 bytes) of stored payload JSON text, measured with `Buffer.byteLength(row.payload, 'utf8')`.
- **Too far behind** — the gap after `fromSequence` exceeds the replay cap. The server answers with the signal `{ tooFarBehind: true }` instead of events.
- **Snapshot fallback** — the client's response to "too far behind": it runs its normal `bootstrap()` (a `getSnapshot`) on the existing transport, with no `resetTransport()`.
- **Full transport reset** — `resetTransport()` from `src/dashboard/frontend/src/lib/wsTransport.ts`; it kills every subscription on the shared socket. The snapshot fallback must not do this.
- **Recovery coordinator** — the state machine in `src/dashboard/frontend/src/lib/recoveryCoordinator.ts` (`latestSequence`, `bootstrapped`, `inFlight`, `pendingReplay`).

## Problem

Gap recovery replays every missed event in one unbounded read on the server's main thread.

- Client: `replay(fromSequence)` in `src/dashboard/frontend/src/components/EventRouter.tsx` (line 275, `async function replay(fromSequence: number) {`) calls `WS_METHODS.replayEvents({ fromSequence })` and loops while more events arrived meanwhile.
- Server: the handler in `src/dashboard/server/ws-rpc.ts` (lines 837–848, `[WS_METHODS.replayEvents]: (input) =>`) calls `eventStore.readFrom(input.fromSequence)`. In `src/dashboard/server/event-store.ts` (lines 230–235) `readFromStmt` is
  `SELECT sequence, type, timestamp, payload FROM events WHERE sequence > ? AND type != 'issues.snapshot' ORDER BY sequence ASC` — no `LIMIT`. It runs synchronously (`Effect.sync` in `src/dashboard/server/services/domain-services.ts` line 318) and `rowToStored` JSON-parses every row.

The live `events` table holds about 141,000 rows (about 19 MB of payload). A tab that returns after a laptop sleep can request a very large range. The server blocks its event loop while it reads, parses, encodes and sends that range; every other client and HTTP request waits. The client then applies each event one by one, when a fresh snapshot is cheaper.

## Requirements

- **FR-1** The event store exposes a bounded replay read whose SQL statement contains `LIMIT ?` and that never materializes more than `maxEvents + 1` rows.
- **FR-2** The bounded read reports `tooFarBehind: true` (and returns no events) when more than `REPLAY_MAX_EVENTS` rows follow `fromSequence`, or when the summed UTF-8 byte length of those rows' stored payload text exceeds `REPLAY_MAX_PAYLOAD_BYTES`.
- **FR-3** The bounded read keeps today's filter: it excludes `issues.snapshot` rows and returns events in ascending `sequence` order.
- **FR-4** The `pan.replayEvents` RPC success schema accepts either an array of `DomainEvent` (today's shape) or the struct `{ tooFarBehind: true }`.
- **FR-5** The `replayEvents` server handler answers `{ tooFarBehind: true }` for a too-far gap and the same event array as today for a gap within the cap.
- **FR-6** When a live sequence gap's replay answers `{ tooFarBehind: true }`, the client re-bootstraps through `getSnapshot` without calling `resetTransport()`, then catches up with a normal (small) replay and drains its deferred live events.
- **FR-7** When the replay inside `bootstrap()` (right after a fresh snapshot) answers `{ tooFarBehind: true }`, the client treats that bootstrap attempt as failed, so the existing failure backoff (2 s doubling, 30 s cap) schedules the next attempt. It never loops snapshot → replay → snapshot without a delay.
- **FR-8** A replay for a gap within the cap behaves exactly as today on the client: events apply, `markEventBatchApplied` advances, `completeReplayRecovery` decides whether to loop, deferred events drain.
- **FR-9** `docs/DASHBOARD-ARCHITECTURE.md` describes the replay cap, the `tooFarBehind` signal, and both client fallbacks.
- **NFR-1** `src/dashboard/server/ws-rpc.ts` does not grow: it stays at or below its `origin/main` line count (1220). Its allowlist row (`scripts/file-size-allowlist.txt`, last row 1221) must not be raised.
- **NFR-2** Client tests that involve backoff or the 16 ms flush use fake timers (`vi.useFakeTimers()` is already in the `beforeEach` of `EventRouter.test.tsx`). No real `setTimeout` waits.
- **NFR-3** Old dashboard tabs (JS loaded before the deploy) keep working for small gaps, because the array member of the union is unchanged.

## Decisions (made here, not left to the implementer)

1. **Signal shape: union success, not a typed error.** `ReplayEventsRpc.success` becomes `Schema.Union([Schema.Array(DomainEvent), ReplayTooFarBehind])` where `ReplayTooFarBehind = Schema.Struct({ tooFarBehind: Schema.Literal(true) })`. Reasons: (a) old open tabs decode an array exactly as today, so a deploy does not break small-gap replay on every open tab (NFR-3); (b) the three e2e transport mocks (`tests/e2e/issue-tree.spec.ts` line 250, `tests/e2e/merge-train.spec.ts` line 251, `tests/e2e/styleguide-conformance.spec.ts` line 355) return `Effect.succeed([])` and keep working unchanged; (c) it avoids depending on how Effect 4 beta's `runPromise` surfaces a typed RPC error to `wsTransport.request()`.
2. **Client discrimination uses `'tooFarBehind' in result`**, not `Array.isArray` (TypeScript's `Array.isArray` does not narrow a `ReadonlyArray` union cleanly).
3. **Both caps, count first.** SQL `LIMIT` fetches `maxEvents + 1` rows; one extra row tells "exactly at the cap" from "past it". If `rows.length > maxEvents` → too far behind. Otherwise sum `Buffer.byteLength(row.payload, 'utf8')` row by row and stop as soon as the sum exceeds `maxPayloadBytes` → too far behind. Only when both pass are rows JSON-parsed (`rowToStored`). The cap counts raw stored rows, before `passesDomainEventSchema` filtering in the handler.
4. **No span pre-check.** The `LIMIT` alone bounds the read; a `getLatestSequence()` span shortcut is not added.
5. **New method, `readFrom` untouched.** Add `readFromBounded(fromSequence, limits?)`. `readFrom` keeps its signature and SQL, because `src/dashboard/server/routes/events.ts` (line 206), `src/dashboard/server/routes/internal-events.ts` (line 228) and others already bound their own windows with a span cap of 1000.
6. **Constants live in `event-store.ts`**: `export const REPLAY_MAX_EVENTS = 500;` and `export const REPLAY_MAX_PAYLOAD_BYTES = 1024 * 1024;`. `limits` is an optional `{ maxEvents?: number; maxPayloadBytes?: number }` so tests can use small caps.
7. **Coordinator unchanged.** On `tooFarBehind`, `replay()` calls the existing `coordinator.failRecovery()`: it ends the replay phase (`inFlight = null`, so `beginSnapshotRecovery` can register), sets `bootstrapped = false` (live events defer during the snapshot), and sets `pendingReplay = true` (so `completeSnapshotRecovery` asks for the small follow-up replay that drains deferred events).
8. **`replay()` returns an outcome and never calls `bootstrap()` itself.** `replay()` is also awaited *inside* `bootstrap()`; calling `bootstrap()` from there would return the in-flight `bootstrapPromise` and await itself forever. So `replay()` returns `'caught-up' | 'too-far-behind' | 'failed'` and the caller acts:
   - live-gap callers (`handleEvent` and `drainDeferredEvents`) go through a new `recoverFromGap()` that calls `bootstrapWithReconnectRetry()` on `'too-far-behind'`;
   - `bootstrap()` throws on `'too-far-behind'` so its existing `catch` (failRecovery, `markStreamDown`, return `false`) runs, and `bootstrapWithReconnectRetry` schedules a backoff reconnect (FR-7). That backoff path performs its usual full reset; this happens only in the pathological case where a fresh snapshot is already more than the cap behind.
9. **`'failed'` keeps today's behavior** (log + `failRecovery()`, nothing else). Fixing the wedge it causes is [PAN-4566](https://github.com/eltmon/overdeck/issues/4566).
10. **The unwired remodel contract `src/lib/overdeck/observability.ts`** (its own `ReplayGap`/`SnapshotRequired` errors) is not touched.

```ts
    const maxEvents = limits.maxEvents ?? REPLAY_MAX_EVENTS;
    const maxPayloadBytes = limits.maxPayloadBytes ?? REPLAY_MAX_PAYLOAD_BYTES;
```

```ts
    // ── Replay: fetch missed events ──────────────────────────────────────────
    // Returns the outcome instead of acting on it: replay() also runs inside
    // bootstrap(), where calling bootstrap() again would await itself.
    async function replay(fromSequence: number): Promise<'caught-up' | 'too-far-behind' | 'failed'> {
      coordinator.beginReplayRecovery()
      try {
        const result = (await getTransport().request((client) =>
          (client as PanRpcProtocolClient)[WS_METHODS.replayEvents]({ fromSequence }),
        )) as ReplayEventsResult
        if ('tooFarBehind' in result) {
          // PAN-4559: the gap exceeds the server's replay cap. failRecovery()
          // ends the replay phase, defers live events and queues the small
          // replay that follows the snapshot; the caller re-bootstraps.
          console.warn(`[EventRouter] replay from ${fromSequence} is too far behind — falling back to a snapshot`)
          coordinator.failRecovery()
          return 'too-far-behind'
        }
        const typed = (result as DomainEvent[]).filter(isSequencedDomainEvent)
        if (typed.length > 0) {
          applyEvents(typed)
          coordinator.markEventBatchApplied(typed[typed.length - 1]!.sequence)
        }
        const needsAnotherReplay = coordinator.completeReplayRecovery()
        if (needsAnotherReplay) {
          return await replay(coordinator.getState().latestSequence)
        }
        drainDeferredEvents()
        return 'caught-up'
      } catch (err) {
        console.error('[EventRouter] replay failed:', err)
        coordinator.failRecovery()
        return 'failed'
      }
    }

    // A live sequence gap: replay, and re-bootstrap through getSnapshot on the
    // existing transport when the gap is past the replay cap (PAN-4559).
    function recoverFromGap() {
      void replay(coordinator.getState().latestSequence).then((outcome) => {
        if (outcome === 'too-far-behind') bootstrapWithReconnectRetry()
      })
    }
```

- **Quality gates** before `pan done`: `npm run typecheck`, `npm run lint`, and `npx vitest run` on the touched test files only. Never the full `npm test` on the host.
- **No `git stash`**; commit per item with an `Item: <id>` trailer.

## Non-goals

- Routing a *failed* (non-cap) replay to the snapshot fallback — PAN-4566.
- Changing `readFrom` or the SSE replay routes (`routes/events.ts`, `routes/internal-events.ts`), which already cap by span.
- Detecting events lost to 7-day compaction (a `fromSequence` older than the oldest retained row).
- Paginated replay (returning a partial page and continuing); past the cap the client always takes a snapshot.
- Touching `src/lib/overdeck/observability.ts` (unwired remodel contract) or the e2e transport mocks.
- Moving the replay read off the main thread (a worker or async driver).
- Updating the external OKF knowledge bundle (`../overdeck-knowledge`).
