# PAN-5465: Add skill packs to a running conversation (hot-load with /reload-plugins, resume fallback)

**Issue:** [PAN-5465](https://github.com/eltmon/overdeck/issues/5465)
**Companion:** [PAN-5464](https://github.com/eltmon/overdeck/issues/5464) (video skill set and pack groups). This issue works with plain packs on its own. `--group` / `groups` support in WI-3 and WI-5 is gated on PAN-5464's `resolvePackGroup` existing; if PAN-5464 has not merged when this is implemented, ship packs and pack skills only and leave `groups` out of the schema.

## Summary

Today a conversation's pack skills are fixed at launch: they come from the conversation row's skill map, set only when the conversation is created (`features/skill-packs.mdx`, "For one conversation"; PAN-4486). The operator wants to pull a pack (or a pack group, such as `video`) into a conversation that is already running, without losing its context.

A spike on 2026-11-17 proved Claude Code can do this in place. This issue adds the write path, the live apply, a resume fallback for harnesses that cannot hot-load, a CLI, an MCP tool (so the agent itself can say "load the video pack"), and a dashboard entry.

## Spike evidence (2026-11-17, Claude Code 2.1.326)

Two throwaway sessions on a private tmux socket, using Overdeck's exact layout: `--plugin-dir <launch>/skill-packs`, where `skill-packs` is a symlink to `<mount>/plugins/` and each pack is `plugins/<pack>/{.claude-plugin/plugin.json,skills/<skill>/SKILL.md}`.

| Session | Link at launch | After atomically re-pointing the link to a mount with a second pack, then `/reload-plugins` |
|---|---|---|
| A | mount with `packa` | `Reloaded: 3 plugins · 13 skills` (was 2 · 12). `/packb:beta-skill` ran and printed the skill's output. |
| B | **empty** `plugins/` dir | `Reloaded: 3 plugins · 13 skills` (was 1 · 11). "Use the beta-skill skill now." → `Skill(packb:beta-skill)` loaded and ran. |

So both the slash-command index and the model-facing skill list are rebuilt. The link must exist and be passed as `--plugin-dir` **at launch**; re-pointing works, adding a flag later does not.

## Glossary

- **Conversation skill map**: the row column `conversations.skill_overrides` (JSON `Record<string, boolean>`), decoded by `parseSkillOverridesColumn` in `src/lib/overdeck/conversations.ts` and read at launch by `loadConversationSkillLayer` in `src/lib/skill-overrides/launch.ts`. Keys are native skill names or `pack/skill` ids. It is the narrowest layer.
- **Plugin link**: `<OVERDECK_HOME>/launch/<launchKey>/skill-packs`, from `skillPackLinkPath` in `src/lib/skill-overrides/launcher-lines.ts`. For a conversation the launch key is its `managedStateKey` (the tmux/Herdr session name, `conv-…`).
- **Launch-settings step**: the launcher line `pan skills launch-settings … --conversation <session> --plugin-link <link>`, which calls `applyClaudePacks(ctx, link)` (`launch.ts`) → `buildMount` + `linkClaudeMount` (`src/lib/skill-packs/mount.ts`).
- **Hot apply**: rebuild the mount for the conversation's new skill map, re-point the plugin link, then deliver `/reload-plugins` to the session.
- **Resume apply**: stop the harness and resume the same conversation (`handleConversationStop`, then `handleConversationResume` in `src/lib/overdeck/conversation-runtime.ts`). Resume regenerates the launcher, so the new map applies; the transcript continues.
- **Pack group**: from PAN-5464 (`src/lib/skill-packs/groups.ts`, `resolvePackGroup`). Expands to pack ids.
- **Snapshot expansion**: a `--pack <id>` request becomes one `pack/skill: true` entry per non-opt-in skill the pack has now (existing logic in `src/lib/skill-overrides/conversation-flags.ts`, PAN-4499). There is no whole-pack toggle at conversation level.

## Requirements

- **FR-1**: Every local Claude Code launch passes `--plugin-dir <link>`, even with no packs selected; with no packs the link points at an empty plugins dir.
- **FR-2**: `POST /api/conversations/:name/skills` merges `skills` (`pack/skill` ids), `packs` (snapshot-expanded) and, after PAN-5464, `groups` into the row's skill map, then applies them.
- **FR-3**: For a running Claude Code conversation that was launched with `--plugin-dir` and adds no D-8 pack, apply is a hot apply. The response is `applied: "hot"` when the reload's skill count rose by exactly the number of newly mounted pack skills (D-5), else `applied: "sent"`.
- **FR-4**: For a running Codex conversation, or a Claude Code conversation launched before FR-1 (no `--plugin-dir` in its launcher), the route stores the map and returns `applied: "needs-restart"` unless the request has `restart: true`, in which case it does a resume apply and returns `applied: "restarted"`.
- **FR-5**: For a stopped conversation the route stores the map and returns `applied: "next-launch"`.
- **FR-6**: For Pi, ohmypi, opencode and other harnesses that never read pack values, the route returns 409 `Skill packs apply only to Claude Code and Codex conversations` and stores nothing.
- **FR-7**: `pan skills add <conversation> [--pack <id>]… [--skill <pack/skill>]… [--group <name>]… [--restart]` calls the route and prints the outcome in one plain sentence.
- **FR-8**: MCP tool `add_skills` (scope `operate`) calls the route. `conversation` defaults to the calling agent's own conversation.
- **FR-9**: The dashboard conversation action menu has **Add skills…**, which opens a modal with the same pack-skill list as the New conversation dialog's Skills section, plus one checkbox per pack group, and posts to the route.
- **NFR-1**: No `execSync`; pane capture and delivery use the async terminal-backend operations.
- **NFR-2**: Delivery of `/reload-plugins` goes through the conversation message path (`handleConversationMessage`), never raw `tmux send-keys`, so the busy-turn queueing and delivery receipts that path already has apply.
- **NFR-3**: Hot apply never kills or restarts the harness.

## Decisions

- **D-1. Add only, plus explicit off.** The route merges; it never clears unrelated entries. A request may carry `off: ["pack/skill"]` to set entries to `false`. Native (non-pack) skills are out of scope for hot apply: they are hidden through `--settings {"skillOverrides":…}`, fixed at launch, so a native-skill change returns `needs-restart` for every harness.
- **D-2. Empty mount.** A fixed dir `~/.overdeck/packs/mounts/empty/plugins/` (created on demand, never content-addressed). `linkClaudeMount(link, null)` points the link there instead of removing it. `gcMounts` skips the `empty` name.
- **D-3. Detecting "launched with `--plugin-dir`".** Read the live process, not the launcher script: the launcher emits the `PAN_SKILL_PLUGIN_DIR` line for every Claude launch that has a link, even when the link was absent at launch and `--plugin-dir` was never passed. Call `isAlive(<agentId>)` (`src/lib/agents/liveness.ts`); when it returns `{ alive: true, runtimePid }`, read `/proc/<runtimePid>/cmdline` with `fs/promises` `readFile`, split on `\0`, and require an exact `--plugin-dir` argument. No `runtimePid`, or an unreadable cmdline, means not hot-capable (`needs-restart`).
- **D-4. Busy conversations.** The `/reload-plugins` messages go through `handleConversationMessage`, which already queues behind an in-flight turn. Each wait starts when its delivery is confirmed.
- **D-5. Confirmation compares before and after.** A `Reloaded:` line prints whether or not the new pack loaded, so its presence proves nothing. Hot apply therefore runs two reloads:
  1. Deliver `/reload-plugins` with the link unchanged, and read the baseline skill count `S0` from the new `Reloaded: <p> plugins · <s> skills` line.
  2. Re-point the link (`applyClaudePacks`).
  3. Deliver `/reload-plugins` again and read `S1`.
  4. Outcome `hot` when `S1 − S0` equals the mounted pack-skill count after the change minus before (count `plugins/*/skills/*/SKILL.md` in the old and new mount). Otherwise `sent`, with a warning naming both numbers.
  Pane reads go through the terminal backend: capture every 1 s, for up to 15 s per reload, and take the newest line matching `/Reloaded: (\d+) plugins? · (\d+) skills?/`. `/reload-plugins` is a local command, so it costs no model tokens. Tests use fake timers.
- **D-6. Codex.** Codex has no reload command; the pack block lives in `$CODEX_HOME` config and plugin cache, written at launch. Resume apply is the only path.
- **D-7. Hot apply reuses the launch step's resolution.** It does not run a second, partial one. `skillsLaunchSettingsCommand` (`src/cli/commands/skills.ts`, from line 144) computes `exclude` from `resolveSageoxLaunch`, writes `deft.env` and the Deft deny, and merges the Semgrep hooks. Move the `exclude` computation into an exported `launchPackExclude(ctx, harness)` in `src/lib/skill-overrides/launch.ts`. The CLI step and hot apply both call it, so a hot rebuild keeps SageOx in or out exactly as the launch did.
- **D-8. Packs that need launch-time wiring are never hot-applied.** A request that would newly mount a skill from one of these packs returns `needs-restart`, or does a resume apply with `restart: true`:
  - `deft`: the env file and the CLI deny are launch-time settings.
  - `sageox`: its hooks are launch-time settings.
  - packs with adapter `gstack-runtime`: runtime env and browser.
  - any pack whose registry entry has `mcp: true` and whose manifest has `mcpServers`, such as `atlassian`: MCP config is fixed at launch.

  Decide this from the registry entry (`getPack`, `src/lib/skill-packs/sources.ts`) and the manifest, never from the pack id alone, except for `sageox`.

2. `conversation-skill-apply.ts` exports:

```ts
export type SkillApplyOutcome = 'hot' | 'sent' | 'needs-restart' | 'restarted' | 'next-launch';
export async function applyConversationSkills(
  name: string,
  request: { skills: string[]; packs: string[]; groups: string[]; off: string[]; restart: boolean },
  deps: ApplyDeps, // message delivery, pane capture, stop, resume, clock — injected for tests
): Promise<{ outcome: SkillApplyOutcome; added: string[]; warnings: string[] }>;
```

Steps:
   a. Load the row (`getConversationByName`); 404 if missing.
   b. Harness gate (FR-6).
   c. Expand groups → packs, then packs + skills → entries with the PAN-4499 helpers in `conversation-flags.ts` (same validation and `unknown skill:` errors). Apply `off`. Merge into the existing map; write with `setConversationSkillOverrides`.
   d. Not running (liveness from `src/lib/agents/liveness.ts`) → `next-launch`.
   e. Native skill in `skills`/`off`, or a newly mounted skill from a D-8 pack → `needs-restart`, or resume apply when `restart` is set.
   f. Codex, or Claude whose live process has no `--plugin-dir` (D-3) → `needs-restart`, or resume apply when `restart` is set.
   g. Claude hot apply, with `ctx = { cwd: row.cwd, issueId: row.issueId, conversation: row.tmuxSession }` and `link = skillPackLinkPath({ managedStateKey: row.tmuxSession, spawnMode: 'conversation', … })`:
      1. Run the baseline reload (D-5 step 1).
      2. Call `applyClaudePacks(ctx, link, await launchPackExclude(ctx, 'claude-code'))` (D-7).
      3. Run the second reload and compare (D-5 steps 3 and 4) → `hot` or `sent`.

      Deliver through `handleConversationMessage` (NFR-2, and the checkpoint above). Use the exact field names of the row type in `conversations.ts`. If the row has no `tmuxSession`, use `managedStateKey`, as the launcher does.

Tests (`src/lib/overdeck/__tests__/conversation-skill-apply.test.ts`, `vi.useFakeTimers()`):

## Repo rules that apply

- Quality gates: `npm run typecheck`, `npm run lint`, `npx vitest run <touched tests>`; never the full `npm test` on the host.
- No `execSync` in server-reachable code. Use async terminal-backend operations.
- Message delivery to agents goes through the backend `prompt()` / message path, never raw `tmux send-keys`.
- Delay-based tests use `vi.useFakeTimers()`.
- A new HTTP route needs a no-loss-matrix row and a `route-scopes.ts` row.
- After server changes, `npm run build` before restarting the dashboard; the dashboard runs only as Node 22 dist.
