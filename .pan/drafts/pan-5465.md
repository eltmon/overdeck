# PAN-5465: Add skill packs to a running conversation (hot-load with /reload-plugins, resume fallback)

**Issue:** [PAN-5465](https://github.com/eltmon/overdeck/issues/5465)
**Companion:** [PAN-5464](https://github.com/eltmon/overdeck/issues/5464) (video skill set and pack groups). This issue ships packs and pack skills only. Pack-group support (`--group`, `groups`) is deferred to [PAN-5497](https://github.com/eltmon/overdeck/issues/5497), which runs after both PAN-5464 and this issue merge (D-10).

## Summary

Today a conversation's pack skills are fixed at launch. They come from the conversation row's skill map, which is set only when the conversation is created (`features/skill-packs.mdx`, "For one conversation"; PAN-4486). The operator wants to pull a pack into a conversation that is already running, without losing its context.

Claude Code can do this in place (spikes below). This issue adds the write path, the live apply, a resume fallback for harnesses that cannot hot-load, a CLI (`pan skills add`), an MCP tool (`add_skills`, so the agent itself can say "load the mattpocock pack"), and an **Add skills…** dialog in the dashboard.

## Spike evidence (Claude Code 2.1.326)

**Spike 1 (2026-11-17, issue author).** Two throwaway sessions on a private tmux socket, using Overdeck's exact layout: `--plugin-dir <launch>/skill-packs`, where `skill-packs` is a symlink to `<mount>/plugins/` and each pack is `plugins/<pack>/{.claude-plugin/plugin.json,skills/<skill>/SKILL.md}`.

| Session | Link at launch | After atomically re-pointing the link to a mount with a second pack, then `/reload-plugins` |
|---|---|---|
| A | mount with `packa` | `Reloaded: 3 plugins · 13 skills` (was 2 · 12). `/packb:beta-skill` ran. |
| B | **empty** `plugins/` dir | `Reloaded: 3 plugins · 13 skills` (was 1 · 11). "Use the beta-skill skill now." → `Skill(packb:beta-skill)` ran. |

Both the slash-command index and the model-facing skill list are rebuilt. The link must exist and be passed as `--plugin-dir` **at launch**; re-pointing works, adding the flag later does not.

**Spike 2 (2026-11-17, planning session).** One session, `--plugin-dir` pointing at an empty `plugins/` dir, text delivered the way Overdeck delivers it (`tmux load-buffer` + `paste-buffer`, 300 ms, then `C-m`):

1. Idle, pasted `/reload-plugins` → it ran: `Reloaded: 1 plugin · 11 skills · 12 agents · 3 hooks · 0 plugin MCP servers · 0 plugin LSP servers`. A pasted slash command executes; no literal-key fallback is needed on tmux.
2. Started a turn (`sleep 25` in Bash). Mid-turn, re-pointed the link to a mount with one pack, then pasted `/reload-plugins` → the pane showed `❯ /reload-plugins ⎿ Queued · ctrl+x ctrl+s to send now`. When the turn ended, the queued command ran by itself: `Reloaded: 2 plugins · 12 skills …`.

So Claude Code itself queues a slash command sent mid-turn and runs it when the turn ends. Overdeck's message path does not queue. This matters for the MCP tool: an agent that calls `add_skills` on itself is mid-turn by definition.

## Glossary

- **Conversation skill map**: the row column `conversations.skill_overrides` (JSON `Record<string, boolean>`), decoded by `parseSkillOverridesColumn` (`src/lib/overdeck/conversation-launch-context.ts`) into `LegacyConversation.skillOverrides` (`src/lib/overdeck/conversations.ts`, field comment "PAN-4486: per-conversation skill on/off map"). Keys are native skill names or `pack/skill` ids. It is the narrowest layer.
- **Launch read of the map**: `loadConversationSkillLayer(tmuxSession)` in `src/lib/skill-overrides/launch.ts` (line ~64) calls `getSupervisedConversationByTmuxSession(tmuxSession)`, which picks the `/clear` chain head (the row with `cleared_to_conv_id IS NULL`), not the row a caller named.
- **Chain head**: after `/clear`, several rows share one terminal session; only the row with `clearedToConvId == null` owns it. Resolver: `resolveClearChainHead` and `isSupersededConversation` in `src/lib/overdeck/conversation-clear-chain.ts`.
- **Plugin link**: `<OVERDECK_HOME>/launch/<launchKey>/skill-packs`, from `skillPackLinkPath` in `src/lib/skill-overrides/launcher-lines.ts`. For a conversation the launch key is its `tmuxSession` (`conv-…`; `LegacyConversation.tmuxSession` is never null).
- **Mount**: a content-addressed dir under `~/.overdeck/packs/mounts/<hash>/` holding `plugins/<pack.id>/skills/<skill.name>/` (`buildMount`, `src/lib/skill-packs/mount.ts`). The link points at `<mount>/plugins`.
- **Launch-settings step**: the launcher line `pan skills launch-settings … --conversation <session> --plugin-link <link>` (`skillsLaunchSettingsCommand`, `src/cli/commands/skills.ts`, line 144). For Claude it calls `applyClaudePacks(ctx, link, exclude)` (`launch.ts`), which runs `resolveLaunchPackSelection` → `buildMount` → `linkClaudeMount`.
- **Pack selection**: the `{ selection, warnings, mcp }` that `resolveLaunchPackSelection(ctx, exclude)` (`launch.ts`, line ~104) returns. `selection.packs[]` has `id`, `skills[]`, and `transform` (`'gstack-runtime'` or `'deft-readonly'` when set); `mcp[]` lists `claude-plugin` packs whose manifest has `mcpServers`.
- **Hot apply**: rebuild the mount for the conversation's new map, re-point the plugin link, then deliver `/reload-plugins` to the running Claude Code session.
- **Resume apply**: stop the harness and resume the same conversation, as native compaction already does (`conversation-message.ts`: `stopConversationRuntime(conv, conv.name)` then `handleConversationResume(conv.name, { sendResumeContract: false }, { resolveSessionFile, resumeCause: 'system' })`). The resume regenerates the launcher, so the new map applies; the transcript continues.
- **Snapshot expansion**: a `--pack <id>` request becomes one `pack/skill: true` entry per non-opt-in skill the pack has now (`expandConversationSkillFlags`, `src/lib/skill-overrides/conversation-flags.ts`, PAN-4499). There is no whole-pack toggle at conversation level.
- **Launch-wired pack (D-8)**: a pack whose effect needs launch-time settings, so a hot apply cannot add or change it: `deft`, `sageox`, any pack with `transform: 'gstack-runtime'`, and any pack listed in the selection's `mcp[]`.
- **Self route**: an `/api/self/…` route. It takes the caller's identity from the agent token (`selfCallerFromCredential`, `src/dashboard/server/self-caller.ts`); a conversation token yields `caller.agentKind === 'conversation'` and `caller.agentId` = the conversation name.

## Requirements

- **FR-1**: Every local Claude Code launch that has a plugin link passes `--plugin-dir <link>`, even with no packs selected. With no packs, the link points at the fixed empty mount `~/.overdeck/packs/mounts/empty/plugins/`.
- **FR-2**: `POST /api/conversations/:name/skills` merges `skills` (`pack/skill` ids or native names) and `packs` (snapshot-expanded), and sets `off` ids to `false`, in the chain head's skill map, then applies the change. The response is `200 { outcome, added, warnings }`.
- **FR-3**: For a running Claude Code conversation that runs with `--plugin-dir <its link>` and whose change touches no launch-wired pack and no native skill, the apply is a hot apply. The outcome is `hot` when the second reload's skill count rose by exactly the mounted-skill delta, `sent` when the reloads ran but the count did not match, and `queued` when the conversation was mid-turn (D-4).
- **FR-4**: For a running Codex conversation, a Claude Code conversation without `--plugin-dir <its link>` in its live command line, or a change that touches a launch-wired pack or a native skill, the route stores the map and returns `needs-restart`. With `restart: true` it does a resume apply and returns `restarted`.
- **FR-5**: For a conversation whose runtime is confirmed stopped, the route stores the map and returns `next-launch`.
- **FR-6**: For Pi, ohmypi, opencode and every harness other than Claude Code and Codex, the route returns 409 `Skill packs apply only to Claude Code and Codex conversations` and stores nothing.
- **FR-7**: `GET /api/conversations/:name/skills` returns `{ conversation, harness, running, skillOverrides }` for the chain head, so the dashboard dialog can preselect current values.
- **FR-8**: `POST /api/self/skills` (agent token of kind `conversation` only) applies the same body to the caller's own conversation. It never waits for a reload line; a hot apply from here returns `queued`. `restart: true` is refused with 400 `A conversation cannot restart itself; ask the operator or call add_skills from another conversation`.
- **FR-9**: `pan skills add <conversation> [--pack <id>]… [--skill <id>]… [--off <id>]… [--restart]` calls FR-2 and prints the outcome in one plain sentence. `<conversation>` may be `self`, resolved with `resolveCurrentConversation()`. `self` with `--restart` exits 1 with `A conversation cannot restart itself; run this from another conversation or a terminal`, before any request (it would kill the caller's own turn).
- **FR-10**: MCP tool `add_skills` (scope `operate`). Without `conversation` it posts to FR-8; with `conversation` it posts to FR-2.
- **FR-11**: The conversation tab menu (`ConversationActionMenu`) and the conversation header menu (`ConversationHeaderMenu`) each have **Add skills…** for Claude Code and Codex conversations. It opens a dialog with the pack-skill list of the New conversation dialog, preselected from FR-7, and posts only the changed ids to FR-2.
- **NFR-1**: No `execSync` in server-reachable code. Process listing uses async `execFile('ps', …)`; pane reads use `readAgentPaneText`; delivery uses `deliverAgentMessage`.
- **NFR-2**: A hot apply never kills or restarts the harness.
- **NFR-3**: A hot apply never pastes into a permission prompt or a subagent view: it runs the same two pre-delivery checks as the message path and refuses with 409 when either fails, before anything is stored.
- **NFR-4**: Delay-based tests use `vi.useFakeTimers()`.
- **NFR-5**: One apply at a time per terminal session (keyed on the chain head's `tmuxSession`, so two names in one `/clear` chain share the lock); a second concurrent request gets 409 `apply-in-progress`.

## Decisions

- **D-1. Add only, plus explicit off.** The route merges; it never clears unrelated entries. `off: ["pack/skill"]` sets entries to `false`. Native (non-pack) skills are hidden through `--settings {"skillOverrides":…}`, which is fixed at launch, so any native name in `skills` or `off` makes the outcome `needs-restart` (or `restarted`) for every harness.
- **D-2. Empty mount.** A fixed dir `~/.overdeck/packs/mounts/empty/plugins/`, created on demand, never content-addressed. `linkClaudeMount(link, null)` points the link there instead of removing it. `gcMounts` skips the entry named `empty`.
- **D-3. "Runs with `--plugin-dir`" is read from the process table, not from liveness.** `isAlive` returns no `runtimePid` on Herdr (the default backend), so a pid-based check would always fail there. Instead, read `ps -eo pid=,ppid=,args=` (the existing `readProcessTable` in `src/lib/overdeck/conversation-runtime.ts`, line ~121; add `export` to it and to `type ProcessTableRow`) and require a row whose `args` contains `--plugin-dir <link>` followed by a space or the end of the string, where `<link>` is the conversation's exact plugin-link path. The link path embeds the conversation's session key, so the match is unique. `ps` works the same on Linux and macOS. A `ps` failure means not hot-capable (`needs-restart`).
- **D-4. Busy conversations get `queued`.** Spike 2 showed Claude Code queues a mid-turn slash command and runs it after the turn. So:
  - From the self route (FR-8) the caller is always mid-turn: re-point the link, deliver one `/reload-plugins`, return `queued` with no waits.
  - From FR-2, build the mount first (`buildMount(selection)`, no relink yet), then deliver the baseline reload (D-5 step 1). If no new `Reloaded:` line appears within 15 s, treat the conversation as busy: re-point the link, then read the pane once more. If a new `Reloaded:` line appeared after the timeout (the turn ended between the timeout and the re-point, so the queued reload ran against the old mount), send one more `/reload-plugins`; otherwise send nothing (the still-queued baseline reload runs after the re-point). Return `queued` in both cases.
  - The `queued` warning text: `The reload is queued and runs when the current turn ends. If the conversation is idle, send /reload-plugins.`
- **D-5. Confirmation compares before and after.** A `Reloaded:` line prints whether or not the new pack loaded, so its presence proves nothing. The idle hot apply runs two reloads:
  1. Deliver `/reload-plugins` with the link unchanged; read baseline skill count `S0` from the new `Reloaded:` line.
  2. Re-point the link to the mount built before step 1 (D-7).
  3. Deliver `/reload-plugins` again; read `S1`.
  4. Outcome `hot` when `S1 − S0` equals `newCount − oldCount`, where `newCount` = the sum of `skills.length` over the new `selection.packs`, and `oldCount` = the number of `plugins/*/skills/*` dirs under the link's target before step 2. Otherwise `sent`, with the warning `Reloaded, but the skill count changed by <S1−S0>, expected <delta>. Check the conversation.` When step 3's line never appears within 15 s, outcome `sent` with `The second reload was not confirmed.`
  - **Reading the pane:** `readAgentPaneText(conv.tmuxSession, 200, undefined, 'visible')` (as `conversation-runtime.ts`, line ~244, does). Regex `/Reloaded: (\d+) plugins? · (\d+) skills?/g`. Before each delivery, record the match count `N0` and the last match text `L0`. After delivery, poll every 1 s for up to 15 s; a new line exists when the match count is greater than `N0`, or the last match text differs from `L0`. Use the last match's skill number. A pane read that throws counts as "no new line yet".
  - `/reload-plugins` is a local command, so it costs no model tokens.
- **D-6. Codex.** Codex has no reload command; its pack block lives in `$CODEX_HOME` config and plugin cache, written at launch. Resume apply is the only path.
- **D-7. Hot apply reuses the launch step's resolution.** Move the `exclude` computation in `skillsLaunchSettingsCommand` (`resolveSageoxLaunch` → `new Set(sageox.active ? [] : [SAGEOX_PACK_ID])`) into an exported `launchPackExclude(ctx, harness)` in `src/lib/skill-overrides/launch.ts` that returns `{ exclude, sageox }` (the caller still prints `sageox.warnings` and uses `sageox.settings`). The CLI step and hot apply both call it. Hot apply calls `resolveLaunchPackSelection(ctx, exclude)` once, then `buildMount(selection)` and `linkClaudeMount(link, mount)` directly with that same selection, so the D-8 check and the mount see one resolution.
- **D-8. Launch-wired packs are never hot-applied.** Compare the new selection with what the link points at now: for each pack, the skill-name set in `selection.packs` versus the `plugins/<id>/skills/*` dir names under the current link target. If that set differs for any pack that is `deft`, `sageox`, has `transform === 'gstack-runtime'`, or appears in the selection's `mcp[]`, the outcome is `needs-restart` (or a resume apply with `restart: true`). Comparing against the live mount, not the old map, also catches a project-level toggle changed since launch.
- **D-9. Delivery path.** Deliver each `/reload-plugins` with `deliverAgentMessage(conv.tmuxSession, '/reload-plugins', 'skill-reload', 'tmux')` (`src/lib/agents/delivery.ts`, line 378). Verified facts about that function: (a) it deduplicates on `opts.messageId`, which defaults to a fresh `randomUUID()` per call, so two identical reloads in a row are both delivered (pass no `dedupKey`); (b) on a Herdr host the target is prompted through `herdrBackend.prompt`, which types the text into the pane, before the method is consulted; (c) on tmux, method `'tmux'` goes straight to `sendKeys(normalizedId, message)` (load-buffer, paste, Enter), the exact path spike 2 verified, and the text is pasted verbatim with no envelope. Force `'tmux'`; do not use `resolveConversationDeliveryMethod(conv)`, because a `channels` method hands the text to the model as a message, where a slash command does not run. Do not call `handleConversationMessage`: it would retitle a default-titled conversation as "/reload-plugins" and start the PAN-1635 eaten-message watcher, which can redeliver a local command that never becomes a transcript user record. Before storing anything on the hot path, run the message path's two guards:
  - `conversationPendingPermission(conv)` (`src/lib/overdeck/conversation-permission.ts`, line 199); when `answerable` → 409 `{ error: 'Waiting: the agent needs a permission answer first', code: 'permission-pending' }`.
  - `ensureMainInputTarget(conv.tmuxSession)` (`src/lib/agents/input-target.ts`, line 186); when not `ok` → 409 `{ error: target.reason, code: 'input-target-not-main' }`.
  A returned delivery with `ok: false` → outcome `sent` with the warning `The reload was not delivered: <failure>. Send /reload-plugins to the conversation.` (the map and link are already updated).
- **D-10. Pack groups are deferred.** `resolvePackGroup` (PAN-5464) does not exist on `main` today, and PAN-5464 is still in planning. A conditional item would let two different diffs both look done. So this issue has no `groups` field anywhere; PAN-5497 adds `groups` to FR-2/FR-8, `--group` to FR-9/FR-10 and group checkboxes to FR-11 after both issues merge.
- **D-11. Which row is written.** Resolve the named row; if `isSupersededConversation(row)`, use `resolveClearChainHead(row)` (null → 404 `Conversation not found`). Call `conversationWriteRefusal(head)` (`src/lib/overdeck/conversation-release.ts`, line 99) and `shutdownDrainingRefusal()` (`src/lib/shutdown/refusal.ts`) and return their response when non-null. Write the map with `setConversationSkillOverrides(head.name, merged)`.
- **D-12. Running.** Call `isAlive(head.tmuxSession)` (`src/lib/agents/liveness.ts`, line 201). `alive: true` → running. `isConfirmedDead(verdict)` → stopped (`next-launch`). `runtime-indeterminate` → write the map and return `needs-restart` with the warning `Could not tell whether the conversation is running.` This never restarts, even with `restart: true`: `liveness.ts` (`isConfirmedDead`) says a broken probe must never trigger a kill, relaunch or resume.
- **D-13. Validation happens before any write.** Unknown pack, uncached pack, unknown skill and malformed ids fail with 400 and the `ConversationSkillFlagError` message; nothing is stored. A request with all three lists empty is 400 `Nothing to add`.

`hotApplyPrecheck` order:
1. `hasPluginDirArg(await readProcessArgs(), link)` false (or `readProcessArgs` throws) → `{ kind: 'not-hot', reason: 'no-plugin-dir' }`.
2. Resolve the selection for `ctx = { cwd: conv.cwd, issueId: conv.issueId ?? undefined, conversation: conv.tmuxSession }` **using the new map**: pass `conversationLayer: merged` in the context (the field WI-2 adds to `LaunchSkillContext`), so the check sees the map before it is stored. `launchWiredChange(...)` non-empty → `{ kind: 'not-hot', reason: 'launch-wired' }`.
3. `pendingPermission(conv)?.answerable` → refused 409 `permission-pending`; `ensureMainInput(conv.tmuxSession)` not ok → refused 409 `input-target-not-main` (D-9).

4. All passed → `{ kind: 'ready', selection, mounted, warnings }`.

`hotApplyRun`:
- First `mount = await buildMount(ready.selection)` (no relink yet).
- `assumeBusy` → `relink(link, mount)`, deliver one reload, return `queued` (D-4). No pane reads.
- Otherwise D-5 steps 1–4 (step 2 is `relink(link, mount)`), with the D-4 busy fallback after step 1. Waits use `deps.sleep(1000)`, at most 15 iterations per reload. `oldCount` = total skill dirs in `ready.mounted`; `newCount` = sum of `skills.length` over `ready.selection.packs`.
- A delivery with `ok: false` → `sent` with the D-9 warning.

Tests (`vi.useFakeTimers()` for anything that waits; all I/O injected):
- `hasPluginDirArg`: matches `claude … --plugin-dir /x/launch/conv-a/skill-packs --model y` and an args string ending in the link; rejects `/x/launch/conv-ab/skill-packs` and a missing flag.
- `launchWiredChange`: adding a `deft` skill, a `gstack-runtime` pack, or a pack in `mcp[]` returns its id; adding a plain pack returns `[]`; an unchanged deft pack returns `[]`.
- `readReloadLines`: counts two lines and returns the last line's skill number.
- precheck: no `--plugin-dir` → `not-hot/no-plugin-dir`; launch-wired → `not-hot/launch-wired`; permission prompt → refused 409; subagent view → refused 409.
- run, idle: delivers `/reload-plugins`, then relinks, then delivers again (assert call order), returns `hot` when the skill delta matches, `sent` when it does not.
- run, busy (no baseline line within 15 s, and none after the relink) → relinks, delivers exactly one reload in total, returns `queued`.
- run, busy race (no line within 15 s, but a new line on the read after the relink) → delivers a second reload, returns `queued`.
- run, `assumeBusy` → relink then one delivery, no pane reads, `queued`.
