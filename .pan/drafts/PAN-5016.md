# PAN-5016 — Overdeck Anywhere telemetry: desktop events and hosted services

**Issue:** [PAN-5016](https://github.com/eltmon/overdeck/issues/5016) · **Sibling:** [PAN-5021](https://github.com/eltmon/overdeck/issues/5021) (phone app PostHog, blocked by PAN-4841) · **Planned:** 2026-11-04 (auto mode)

## Summary

Overdeck already sends anonymous PostHog telemetry from the CLI, the dashboard server and the dashboard frontend, through one typed event schema. Overdeck Anywhere sends no events at all. This issue adds seven Anywhere events to that schema and emits them from the dashboard server: machine-link started, approved and failed; phone paired and removed; secure-channel open result by route; and hourly relay usage as a byte bucket. The same opt-out and anonymity rules apply, with no new switch. The overdeck.ai Workers (`services/account`, `services/connect`, `services/share`) stay silent, and the docs say so.

The phone app's own PostHog moved to PAN-5021 (see "Part B").

## Glossary

- **Telemetry contract.** `packages/contracts/src/telemetry.ts`. It holds `TELEMETRY_EVENT_NAMES`, `TELEMETRY_PROPERTY_DOMAINS` (closed value lists) and `TELEMETRY_EVENT_CATALOG` (event → property → domain). TypeScript derives the allowed property values from it, so a property can never be a free string or number.
- **Schema drift tests.** `tests/unit/contracts/telemetry-schema.test.ts` pins the exact event list. `tests/unit/telemetry-docs.test.ts` parses the event and domain tables in `docs/TELEMETRY.md` and requires exact equality with the contract. A contract change without the matching docs rows fails CI.
- **AnalyticsService.** `src/lib/telemetry/service.ts`. The only Node module that imports `posthog-node`. `capture()` adds the install id, `$process_person_profile: false`, platform, arch, version, client type and the optional `operatorHash`. It never throws, and it does nothing when telemetry is off (`OVERDECK_TELEMETRY=0|false` or `telemetry.enabled: false`) or under Vitest (`telemetryBlockedForProcess`, `service.ts:51-53`).
- **Requester / approver.** In a machine link, the **requester** is the machine that starts the link. With a pairing code it runs `createMachineLink`; with two-screen approval it runs `join`. The **approver** is the machine that accepts it: it handles `POST /api/machines/exchange`, or it runs `runApprove`. Each machine sends events only about its own side.
- **Link method.** How a link started: `pairing_code` (a pasted `odp_` pairing URL), `ssh` (`pan machines add-ssh` with a prepared SSH forward), `fly` (Fly provisioning over a public route), `directory_approval` (two-screen approval through the overdeck.ai directory), or `other`.
- **Link supervisor.** `src/dashboard/server/services/link-supervisor.ts`. It keeps one secure channel open per linked machine. It probes routes in phases: the stored routes (`lan`, `tailnet`, `ssh`, `public`) together, then `direct` (WebRTC), then `relay` (WebRTC through TURN) (D-2356-8, `probePhased`).
- **Channel route.** The route kind of the channel that opened (`ROUTE_KINDS` in `packages/contracts/src/machines.ts:23`). When no channel opened, it is the last phase that was tried: `stored`, `direct` or `relay`.
- **Relay client.** `src/dashboard/server/services/relay-client.ts`. It meters the relay channels this machine dialed and reports the bytes to the directory as `relay-usage` frames. All bytes pass through `RelayClient.send(bytes)`.
- **Bucket.** A coarse range sent in place of a raw number, following the `count_bucket` and `quota_points_bucket` convention.

## Problem

`docs/TELEMETRY.md` "Event schema" has no event for machine linking, phone pairing, channel routes or relay use. So the maintainers cannot see whether Anywhere is used, which link method people choose, how often channels fall back to the relay, or which failures happen in practice. The operator asked for this coverage on 2026-11-04, during PAN-4841.

## Scope decisions (auto mode)

- **D-1. Split.** This issue covers the desktop events and the Workers decision. The phone app's PostHog and its store and privacy declarations are PAN-5021. There are three reasons. The phone's store and privacy files (`apps/mobile/RELEASE.md`, `apps/mobile/store/privacy-app.html`, `apps/mobile/ios/App/App/PrivacyInfo.xcprivacy`) exist only on the unmerged `feature/pan-4841` branch. The landing copy and the console answers are outside this repo. And the plan lint caps one plan at 6 two-segment path prefixes, which the desktop slice alone reaches: `packages/contracts`, `src/lib`, `src/dashboard`, `tests/unit`, `docs/TELEMETRY.md` and `configuration/telemetry.mdx`.
- **D-2. Workers stay silent.** `services/account`, `services/connect` and `services/share` send nothing to PostHog. The client-side events below already measure the link, pairing and relay funnel. Both Workers hold GitHub account ids and device ids by design, so any event they emit would sit next to an identity. `configuration/telemetry.mdx` also promises that account IDs and GitHub logins are never sent. And connect's `src/log.ts` already forbids labels, keys and payloads in its own logs (NFR-2356-1). The decision is recorded in `docs/TELEMETRY.md` (work item 9). Workers code is not touched.
- **D-3. No new switch.** The events go through `AnalyticsService`, so the existing opt-out (Settings switch, `telemetry.enabled`, `OVERDECK_TELEMETRY`) covers them.
- **D-4. Channel-event volume.** While a linked machine is offline, `connect()` retries with backoff indefinitely, so a raw per-probe event would flood PostHog. The supervisor therefore reports a channel outcome only when the `(route, ok, error_class)` tuple differs from the last tuple it reported for that link. Ten failed probes in a row with the same class produce one event. A route upgrade (`probeBetter` → `adopt` on a better route) is a new tuple and does report.
- **D-5. Relay usage is sampled hourly.** The relay client reports to the directory every 60 s, which is too often for telemetry. A sampler adds up the bytes and sends one `relay_usage_sampled` event when at least one hour has passed since its window started and the total is above zero. The event carries a bucket of the bytes since the previous sample. Bytes in a window that never sees another relay byte are not sent; that loss is accepted. This mirrors `GITHUB_QUOTA_TELEMETRY_INTERVAL_MS` (`src/lib/telemetry/github-quota-telemetry.ts:31`).
- **D-6. Approver-side method.** The approver of a pairing-channel exchange cannot tell whether the requester used a pasted pairing URL, SSH or Fly; all three present an `odp_` code. So `handleMachinesExchange` always reports `method=pairing_code`. The docs say this.
- **D-7. Relay refusals are not split.** `directory-rtc.ts` wraps the relay-plan and monthly-cap refusals as `ChannelOpenError('unreachable', message)`. Telling them apart would need a new code in `packages/anywhere-channel` (a seventh subsystem). The supervisor does distinguish "direct failed and the plan has no relay" by `NO_DIRECT_PATH_MESSAGE` (`link-supervisor.ts:382`) and reports it as `no_relay_plan`. Everything else stays `unreachable`.
- **D-8. Method from transport kind.** `createMachineLink` derives the method from its input. No `transport` gives `pairing_code`. `transport.kind === 'ssh'` gives `ssh` (`ssh-machine-service.ts:301-305`). `transport.kind === 'public'` gives `fly` (`fly-machine-service.ts:284-288`), because Fly is the only caller that passes `public`. Any other kind gives `other`.
- **D-9. Only success is reported for phones.** `phone_paired` fires on a successful `POST /api/phones/exchange`. Refusals (403, 400, 409) are not reported from the machine. PAN-5021 reports pairing failures from the phone, where the user sees them.
- **D-10. Out:** Session Vault and Shared Sessions events. `pan vault` deliberately sends no telemetry (PAN-2609 P-12; `src/cli/telemetry.ts` `isVaultInvocation`, `tests/unit/cli/telemetry-vault-bypass.test.ts`), and the issue's Scope does not list either.

## Requirements

- **FR-1.** The telemetry contract defines seven new events and seven new domains exactly as in work item 1. `docs/TELEMETRY.md` lists them, and both schema drift tests pass.
- **FR-2.** A requester's `createMachineLink` call sends `machine_link_started` once at entry. It then sends `machine_link_approved` (side `requester`) when it returns, or `machine_link_failed` (side `requester`, with a reason) when it throws. The method follows D-8.
- **FR-3.** The approver's `POST /api/machines/exchange` sends `machine_link_approved` (method `pairing_code`, side `approver`) after `grantMachineLink` succeeds. It sends `machine_link_failed` (reason `grant_refused`) when `grantMachineLink` throws `GrantMachineLinkError`.
- **FR-4.** Two-screen approval sends these events. On the requester: `machine_link_started` from `join`; `machine_link_failed` with reason `offline` when `join` cannot reach the directory; `machine_link_approved` (side `requester`) the first time `handleExchange` grants; and `machine_link_failed` with reason `approval_refused` from `rejectJoin`. On the approver: `machine_link_approved` (side `approver`) when `runApprove` succeeds, and `machine_link_failed` with reason `approval_failed` when it fails. The method is always `directory_approval`.
- **FR-5.** A successful phone exchange sends `phone_paired` with `replaced_previous` set to whether an older record for the same phone was revoked.
- **FR-6.** A phone revoking itself sends `phone_removed` with `by=phone`. An operator revoking a phone record through `DELETE /api/devices/:id` sends `phone_removed` with `by=operator`. Revoking a browser device sends nothing.
- **FR-7.** The link supervisor sends `anywhere_channel_opened` per D-4. Success carries `route` = the winning route kind and `error_class=none`. A failure carries the class from work item 7's mapping, with `route` = the adopted route's kind for adopt-time failures, or the last probed phase for probe failures.
- **FR-8.** The relay client feeds every reported byte count to the sampler, and the sampler sends `relay_usage_sampled` per D-5.
- **FR-9.** `docs/TELEMETRY.md` and `configuration/telemetry.mdx` describe the Anywhere events and state that the hosted services send no telemetry.
- **NFR-1.** No Anywhere event property carries a machine label, environment id, token id, URL, key, client id or byte count. Every value comes from a closed domain.
- **NFR-2.** Telemetry never changes a link, pairing or relay result. Every capture call is wrapped so that a throwing analytics client is swallowed.
- **NFR-3.** With telemetry off, no Anywhere event reaches PostHog. This is inherited from `AnalyticsService.getClient()`, and no new code path bypasses it.

export interface AnywhereAnalytics {

The relay sampler:

```ts
export const RELAY_USAGE_TELEMETRY_INTERVAL_MS = 60 * 60_000;

export class RelayUsageSampler {
  private total = 0;
  private windowStart: number | null = null;
  constructor(private readonly opts: { now?: () => number; analytics?: () => AnywhereAnalytics } = {}) {}
  record(bytes: number): void {
    if (!(bytes > 0)) return;
    const now = (this.opts.now ?? Date.now)();
    if (this.windowStart === null) this.windowStart = now;
    this.total += bytes;
    if (now - this.windowStart < RELAY_USAGE_TELEMETRY_INTERVAL_MS) return;
    safeCapture((this.opts.analytics ?? defaultAnywhereAnalytics)(), 'relay_usage_sampled', { bytes: bucketRelayBytes(this.total) });
    this.total = 0;
    this.windowStart = now;
  }
}

export const relayUsageSampler = new RelayUsageSampler();
```
