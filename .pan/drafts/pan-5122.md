# PAN-5122 — Companion terminal works on Herdr hosts

**Issue:** [PAN-5122](https://github.com/eltmon/overdeck/issues/5122) — Terminal tab says "conversation is not running" for Codex and OpenCode conversations on Herdr: the companion-terminal owner check is tmux-only.

**Base:** `main` at `de21d591ffd` (release 0.77.0). Every file/line reference below was verified against that commit. Line numbers can drift; each reference also quotes code to search for.

## Glossary

- **Owner** — the conversation's own terminal session or pane, named `conv-<name>` (`conv.tmuxSession`). On a Herdr host it is a Herdr pane whose `agentId` token is `conv-<name>`; Codex and OpenCode owners are *pane-bound* (no Herdr agent record, found by the token).
- **Companion** — a second terminal, named `companion-<ownerSession>`, that runs the harness's native client (`codex resume --remote …`, `opencode attach …`) against the owner's live runtime. The Terminal tab's "Native CLI" pane streams it.
- **Host port** — `CompanionTerminalHost` in `src/lib/overdeck/companion-terminal/host.ts`: four operations (`ownerStamp`, `readGeneration`, `create`, `kill`). The lifecycle uses only this port.
- **Owner stamp** — an identity for the owner's current incarnation. A respawned owner gets a new stamp. `null` means "the owner is not running".
- **Generation** — `companionGeneration(ownerSession, ownerStamp, fingerprint)`, 24 hex chars. Stamped on a companion at creation; a companion is reused only when its stamp equals the current generation.
- **Host backend** — the terminal backend the host is configured for: `hostTerminalBackendName()` in `src/lib/terminal-backends/select.ts` (env `OVERDECK_TERMINAL_BACKEND` → `terminal.backend` in config → default `herdr`). Memoized per process.
- **Herdr probe** — `probeHerdrAgentLiveness(name)` in `src/lib/terminal-backends/herdr.ts`. Answers `alive` (with `paneId`), `exited`, `absent` (Herdr answered: no such pane), or `indeterminate` (the socket did not answer).
- **Pane process liveness** — `paneProcessLiveness(paneId, api)` in `herdr.ts`: `running` when a foreground process whose pid differs from the pane's `shell_pid` exists, `exited` when only the shell is in the foreground, `indeterminate` on a transport failure.
- **Agent inventory** — `listHerdrAgents()` / `liveAgentInventory()` / Herdr `list()`: every pane with an `agentId` token (or a role/issue token plus a name) is an Overdeck agent there.

## Problem

On a Herdr host (the default), every Codex or OpenCode conversation's Terminal tab shows:

> The conversation is not running, so there is no session to attach to. Resume it, then open Terminal again.

The conversation is running. The owner check asks tmux, which holds nothing on a Herdr host:

- `src/lib/overdeck/companion-terminal/host.ts:60` `createTmuxCompanionHost` — `exists()` (line 61) runs `tmux has-session -t <name>`; `ownerStamp()` (line 70) returns `null` when it fails.
- `src/lib/overdeck/companion-terminal/index.ts:41` — `lifecycle ??= createCompanionTerminalLifecycle({ host: createTmuxCompanionHost(), adapters: defaultAdapters() });` wires tmux unconditionally.
- `src/lib/overdeck/companion-terminal/lifecycle.ts:119-120` — `const stamp = await host.ownerStamp(owner.ownerSession); if (!stamp) return { ok: false, reason: 'owner-not-running', message: OWNER_NOT_RUNNING_MESSAGE };`

Evidence (issue): conversation 3675 (`20261106-1898`, Codex) had `sessionAlive: true`, `herdr pane list` showed `conv-20261106-1898`, and `tmux -L overdeck has-session` returned 1.

Two more gaps sit behind the owner check and would break the fix if left alone:

1. **Browser attach.** The browser streams the companion through `/ws/terminal?session=companion-…`. On a Herdr host `resolveHerdrTerminalId` (`src/dashboard/server/services/terminal-service.ts:193`) finds a terminal only by Herdr agent name or `agentId` token (`findHerdrAgent`). A companion that carries neither resolves to `missing` and the socket closes.
2. **tmux is optional on Herdr hosts.** `src/lib/system-prerequisites.ts:361` — `if (definition.id === 'tmux') return backend === 'tmux';`. A companion kept on tmux would fail on a Herdr host with no tmux.

## Decisions

- **D1 — The companion is a Herdr pane on a Herdr host.** This is the issue's stated fix. The old doc line "on the managed tmux socket, on either host" (`docs/TERMINAL-BACKENDS.md` "Companion terminals" → **Session.**) is replaced. Rejected: Herdr owner check + tmux companion, because tmux is not a prerequisite under Herdr (above).
- **D2 — The companion is never an agent.** On tmux the `companion-` prefix is outside `OVERDECK_SESSION_NAME = /^(agent|planning|strike|conv)-/` (`src/lib/terminal-backends/tmux.ts:60`), so the inventory gives it no agent id. Herdr parity: the companion pane gets **no** `agentId`, `role`, `issue`, `harness`, or `model` token. It gets two dedicated tokens: `companion` = the companion session name and `companionGeneration` = the generation. Consequences: `listHerdrAgents`, Herdr `list()` `agentIdOf`, the agent directory's pane-only loop (`src/dashboard/server/services/agent-directory.ts:519`, `if (!pane.agentId && !pane.issue) continue;`), and the prompt guard never treat it as an agent. Therefore the Herdr host does **not** use `launchAgentPane` / `TerminalBackend.startAgent` (both stamp `agentId` and `role`); it uses `openAgentTab` plus its own `pane.report_metadata` call.
- **D3 — No `exec` on Herdr; run the client as a child and then `exit`.** The pane text is `<quoted argv> ; exit` (built by a new `herdrCompanionCommand(argv)`). Reason: with `exec`, the client takes the shell's pid, so `paneProcessLiveness` reads the live companion as `exited` (pid equals `shell_pid`, `herdr.ts:242` doc comment), and the residue reaper (`src/lib/cloister/herdr-residue-reaper.ts:64`, `!pane.hasAgentId && !pane.detected && pane.process === 'exited'`) would close it after two sweeps. With a child process, liveness reads `running`; when the client exits, `exit` ends the shell and the pane closes.
- **D4 — Owner stamp on a Herdr host.** From the Herdr probe of `ownerSession`:
  - `alive` → `herdr:<paneId>`. Herdr pane ids are never reused (`src/lib/terminal-backends/__fixtures__/herdr-v0.9.1/herdr-skill.md:69`, "Closed tab and pane IDs are not reused."), so a respawned owner (new tab) gets a new stamp.
  - `exited` → `null` (owner not running).
  - `absent` → fall back to the tmux host's `ownerStamp` (a conversation launched before the host moved to Herdr still runs in tmux; `conversation-liveness.ts` uses the same rule). If tmux has nothing or is not installed, the tmux stamp is `null`.
  - `indeterminate` → **throw** `Error('Herdr did not answer for <ownerSession>: <reason>')`. A `null` would make `open()` reap a live companion and say "not running" during a Herdr outage. The route turns the throw into a 500 `Could not open the terminal: …`, and the UI offers **Try again**.
- **D5 — Workspace.** Every companion opens in its own tab in the Herdr workspace `conversations` (the workspace operator conversations launch into: `const CONVERSATIONS_WORKSPACE = 'conversations';` at `src/lib/terminal-backends/launch.ts:48`). Change that line to `export const CONVERSATIONS_WORKSPACE = 'conversations';` (zero added lines) and resolve the workspace with `herdrBackend.workspaceFor(CONVERSATIONS_WORKSPACE, spec.cwd)`.
- **D6 — Host selection per call, tmux path unchanged.** A delegating host asks `hostTerminalBackendName()` on each operation and forwards to the Herdr host when the answer is `herdr`, otherwise to the unchanged `createTmuxCompanionHost()`. The Herdr host module is loaded with a lazy `import()` and memoized: `index.ts` is imported by `conversation-runtime.ts`, `conversation-lifecycle.ts`, `agent-projection.ts` and (lazily) `codex/app-server-host.ts`, and a static edge to `herdr.js` risks a `lint:circular` cycle. `getCompanionTerminalLifecycle()` stays synchronous.
- **D7 — Herdr lookups are bounded.** Every lookup the Herdr host makes (`session.snapshot`, `pane.process_info`) passes `{ timeoutMs: 2_000 }`, so owner teardown (`closeCompanionTerminalForOwner`) can never hold a stop up for 30 s.
- **D8 — `kill` closes every pane carrying the companion's name token** (residue included). It returns `true` when at least one `pane.close` resolved. When panes exist and every close rejected, it throws the first error (so `open()` fails instead of creating a duplicate). A snapshot transport failure throws.
- **D9 — `readGeneration` treats a dead or duplicated companion as stale.** No pane → `undefined`. More than one pane → `null`. One pane whose process liveness is not `running` → `null`. Otherwise the `companionGeneration` token, or `null` when it is missing or empty. `null` makes the lifecycle kill and recreate, which is always safe (the companion holds no state).
- **D10 — The generation env var is kept.** The Herdr tab env carries `OVERDECK_COMPANION_GENERATION=<generation>` and `TERM=xterm-256color`, both overriding adapter env, exactly as the tmux host does (`host.ts` `create`). The token, not the env, is what `readGeneration` reads.
- **D11 — Out of scope:** a tmux host whose owner runs on Herdr (rollback case) keeps today's tmux-only behavior; tmux companions left on a Herdr host are not reaped by the Herdr host; no change to contracts, routes, or the frontend.

## Requirements

- **FR-1** On a Herdr host, `open()` for a running Codex or OpenCode conversation whose owner is a live Herdr pane returns `status: 'attached'`, with no tmux call.
- **FR-2** On a Herdr host, the owner stamp follows D4 (alive → `herdr:<paneId>`, exited → null, absent → tmux fallback, indeterminate → throw).
- **FR-3** On a Herdr host, `create` opens a tab in the `conversations` workspace, stamps only the `companion` and `companionGeneration` tokens, and types `<quoted argv> ; exit` into the pane; a failure after the tab exists closes the pane and rethrows.
- **FR-4** On a Herdr host, `readGeneration` and `kill` follow D9 and D8.
- **FR-5** `/ws/terminal?session=companion-<owner>` on a Herdr host resolves to the companion pane's terminal id when that pane's process is running.
- **FR-6** The lifecycle uses the Herdr host when `hostTerminalBackendName()` answers `herdr`, and the unchanged tmux host otherwise.
- **FR-7** `docs/TERMINAL-BACKENDS.md` states that the companion terminal works on both backends and describes the Herdr implementation.
- **NFR-1** A companion pane never appears in `listHerdrAgents()` or as an `agentId` in Herdr `list()`.
- **NFR-2** On a tmux host, behavior is byte-for-byte unchanged; the existing tests in `src/lib/overdeck/companion-terminal/__tests__/` pass unmodified.
- **NFR-3** Every Herdr lookup in the companion host uses a 2 s timeout; all new code is async (no `*Sync`, no `execSync`).
- **NFR-4** No new import cycle: `npm run lint:circular` passes.

## Intersecting repo rules (restated)

- **Async only.** No `execSync`, no new `*Sync` tmux callers; the dashboard server must never block the event loop.
- **Fake timers for delay tests.** Any test that waits on a timeout or retry uses `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`; never real `setTimeout` delays. (The tests below inject fakes, so no real delay is needed.)
- **No source-reading tests, no `skipIf`/`.only`** — the lint and the test-skip gate reject them. Assert behavior through injected deps.
- **File-size ratchet.** `src/lib/terminal-backends/herdr.ts` is at 1006 lines against its 1008 cap (`scripts/file-size-allowlist.txt:152`). Put all new code in new files; do not add lines to `herdr.ts`. `launch.ts` gets a one-word change only.
- **Quality gates before `pan done`:** `npm run typecheck`, `npm run lint`, and `npx vitest run <touched test files>`. Never the full `npm test` on the host.
- **Herdr text must be well-formed UTF-16** (PAN-4506): argv comes from server-side records, so no new risk, but do not build the text with lone surrogates.

interface CompanionPane { readonly pane_id: string; readonly terminal_id: string; readonly tokens?: Record<string, string> }
async function companionPanes(api: HerdrApiClient, name: string): Promise<CompanionPane[]> {

export async function resolveHerdrTerminalId(

  deps: ResolveHerdrTerminalIdDeps = defaultResolveDeps,

## Hazards

- **H1** `codex/app-server-host.ts:906` lazily imports `closeCompanionTerminalForOwner` inside the Codex host process (which runs inside the owner pane). On a Herdr host that call now talks to the Herdr socket from that process; it is already wrapped to never throw, and D7 bounds it to 2 s per lookup.
- **H2** Herdr may detect `codex`/`opencode` in the companion pane and create an agent record for it. That record has no name and no `agentId` token, so `listHerdrAgents` skips it (`agent.tokens?.agentId ?? agent.name` is empty) and the residue reaper skips detected panes. Do not add `agent.rename` for the companion.
- **H3** Herdr restores drop pane tokens (#4096). A restored companion shell has no `companion` token, so the residue reaper closes it once it idles; the next open creates a fresh companion. No action needed.
- **H4** `openAgentTab` sizes the PTY through `sizeHerdrTerminal`, which spawns the `herdr` binary. Tests must inject `sizeTerminal`.
- **H5** `HerdrApiClient` is a class with private fields; test fakes are cast with `as unknown as HerdrApiClient`.
