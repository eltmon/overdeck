# PAN-5094 — Lane launches respect the disk floor; superseded lanes are flagged and reaped

**Issue:** [PAN-5094](https://github.com/eltmon/overdeck/issues/5094) ·
**Related:** PAN-4961 (disk floor, shipped), PAN-5093 (low-disk alert, open, the backstop), PAN-4223 (lanes), PAN-4638 (lanes on other machines)

## What happened

On 2026-11-06 a Lexerra gauntlet run ("juliet", conversation 3675) created 31 lane folders under
`~/Projects/lexerra-lanes` in three and a half hours, about 1.4 GiB each (~45 GiB), and reaped none.
Free space on `/` reached 17 MB once. Workspace starts were already held by the 10 GiB disk floor,
but lanes kept launching, because the lane door never asks the floor. The issue comment adds that only
5 of the 29 folders cleaned up later were `pan lane` lanes; the other 24 were worktrees the
orchestrator created itself with `git worktree add`. So a floor inside `pan lane start` alone would
not have stopped this run: the gauntlet-loop skill must also check the floor before any worktree the
orchestrator makes, and the PAN-5093 alert is the backstop.

## Glossary

| Term | Meaning |
|------|---------|
| Disk floor | `DISK_SAFETY_FLOOR_BYTES` = 10 GiB in `src/lib/disk-floor.ts`. Below it an ENOSPC write can zero-fill a file (PAN-1674), so disk-heavy phases are refused first. |
| Admission / reservation | `reserveDiskFloor({ path, bytes, label })` (`src/lib/disk-floor.ts`): under a cross-process lock, admits a phase when `available − in-flight reserved − own bytes ≥ 10 GiB` and writes a lease file to `~/.overdeck/disk-reservations/<uuid>.json`; the caller calls `reservation.release()` when the phase ends. Refusal text starts with `DISK_LOW_HELD_PREFIX` = `Disk low — new workspace starts are held`. |
| Preview | `previewDiskFloor({ path, bytes })`: the same arithmetic, writes nothing. |
| Lane | A conversation launched by `pan lane start` with four write-once facts: parent, run key, lane key, role (`builder`, `critic`, `verifier`, `play`, `orchestrator`). Its directory is under the project's **lanes root**. |
| Lanes root | `LaneConfig.lanesRoot` (`src/lib/lanes/config.ts`): `projects.<key>.gauntlet.lanes_root`, default `<parent of project>/<project basename>-lanes`. It can sit on a different filesystem than the project. |
| Home / owner | For a lane on another machine (`--machine`), home is the machine that ran `pan lane start`; the owner is the linked machine that creates the lane's directory (`src/lib/lanes/owner-launch.ts`). |
| Iteration | D7 of PAN-4223: the number of distinct working directories among lanes with the same (run, key, role), in launch order (`laneIterations`, `src/lib/lanes/iteration.ts`). A `--reuse` respawn shares its predecessor's directory and iteration. |
| Iteration group | All lane rows of one (run, key, role) with the same iteration (one directory; several rows only after `--reuse`). |
| Superseded | An iteration group of (run, key, role) whose iteration is lower than the highest iteration of that (run, key, role). |
| Reapable | A superseded lane that `pan lane reap` can remove now; exact rule in FR-6. |
| Activity | `LaneActivity` from `@overdeck/contracts` (`packages/contracts/src/conversation-rows.ts:15`): `failed-to-start`, `needs-you`, `working`, `idle`, `starting`, `stopped`. Archived lanes are `stopped`. |
| Unregistered directory | A directory directly under the lanes root that no lane row (archived included) has as its `cwd`. `pan lane reap` cannot remove it (it 404s on anything that is not a lane). |
| Composer manifest | `packages/contracts/src/composer-commands.generated.ts`, generated from the CLI by `npm run generate:slash-commands`, drift-gated by `npm run lint:slash-commands`. |

## Requirements

### Functional

- **FR-1** A lane launched on this machine is admitted against the disk floor at its **lanes root**
  before any directory, brief, worktree or conversation row is created. A refusal throws
  `LaneLaunchError(507, <reserveDiskFloor refusal text>, 'disk-low')`, so `POST /api/lanes` answers
  HTTP 507 `{ error, code: 'disk-low' }` and `pan lane start` prints the text and exits 1.
- **FR-2** A lane on another machine (`--machine`) is admitted by its **owner** against the owner's
  lanes root, with the same status, text and code; home runs no disk check for it. Home maps the
  owner's 507 to `LaneLaunchError(507, '<label>: <text>', 'disk-low')`.
- **FR-3** Bytes reserved: a launch that creates a new worktree (builder, critic, verifier,
  orchestrator without `--reuse`) reserves
  `max(estimateWorkspaceDiskCost(project).hostBytes, LANE_WORKTREE_MIN_BYTES)` with
  `LANE_WORKTREE_MIN_BYTES` = 2 GiB, so a project with no installed workspace to sample still reserves
  room for the lane's own install. A `--reuse` launch and a `play` launch reserve 0 bytes but are still
  refused below the floor.
- **FR-4** `--force` does not bypass the disk floor (it still bypasses only the CPU check).
- **FR-5** A refused or failed launch (git failure, any throw) releases its reservation before the
  error returns. A successful launch **holds** its reservation for `LANE_DISK_HOLD_MS` = 15 minutes
  after the door returns — the window in which the lane's agent checks out and installs its
  dependencies — then releases it; while held it counts against every later admission, so a burst of
  launches cannot each pass the floor before any of them has written. A failed release never fails a
  launch. A dashboard restart drops the timer; the lease's pid is then dead and the next admission
  prunes it.
- **FR-6** Every `LaneView` carries `reapable: boolean` and `supersededBy: string | null`.
  `reapable` means "superseded and inactive: a candidate for `pan lane reap`"; the reap can still
  refuse (a process in the directory, a dirty tree without `--park`), and the skill handles that. For each
  (run, key, role) with role ≠ `orchestrator`, every iteration group below the highest iteration is
  reapable when: it has at least one non-archived row; no non-archived row has activity `working`,
  `needs-you` or `starting`; and either some row of the group (archived included) filed a report or
  no non-archived row is `idle`. Every non-archived row of a reapable group is `reapable: true` with
  `supersededBy` = the name of the newest row (latest `createdAt`) of the highest iteration.
  Everything else is `reapable: false, supersededBy: null`.
- **FR-7** `pan lane list` prints a `REAPABLE` column (`yes` or `-`) after `ACTIVITY`, and
  `pan lane list --reapable` prints only reapable lanes, i.e. reap candidates (`No reapable lanes.` on stderr and exit 0 when
  none; `--json` prints the filtered array).
- **FR-8** After `pan lane wait` returns a report (any of its three forms), it reads
  `GET /api/lanes?run=<run>` (or `?parent=<conv>` for `--parent`) and, when any lane there is
  reapable, prints one stderr line **before** its existing status line:
  `reapable: <name>, <name> (superseded by a newer iteration); reap each with pan lane reap <name> before launching more lanes`.
  The read has its own 5-second timeout (`REAPABLE_HINT_TIMEOUT_MS`), so a slow dashboard delays a
  returned report by at most 5 s. A failed, timed-out or non-200 read prints nothing. Exit codes and
  the existing status line are unchanged.
- **FR-9** `pan lane disk-check [--project <key> | --path <dir>]` runs locally (no dashboard) and
  previews the floor at the **nearest existing ancestor** of the target directory (the target itself
  when it exists), so a lanes root on another filesystem that does not exist yet is checked on the
  filesystem it will be created on: with `--project`, the target is `config.lanesRoot` and the bytes
  are the FR-3 new-worktree bytes; with `--path`, the target is that directory with 0 bytes; with
  neither, the current directory with 0 bytes. Exit 0 with a `Disk ok: …` line on stdout when there
  is room, exit 4 with the refusal text on stderr when there is not, exit 1 on a usage error or unknown
  project. With `--project` it also lists unregistered directories under the lanes root.
- **FR-10** The `pan-gauntlet-loop` skill tells the orchestrator to run `pan lane disk-check` before
  every launch wave and before every worktree it creates itself (including `git worktree add` and
  Agent-tool worktree isolation), to stop launching on exit 4, to run
  `pan lane list --run <run> --reapable` and reap each listed lane before launching the next
  iteration, and to remove worktrees it created itself with `git worktree remove` once their area
  lands.
- **FR-11** The user docs (`reference/lanes.mdx`), the developer doc
  (`docs/WORKSPACES-AND-PROJECTS.md` disk floor section) and the `pan-lane` skill describe FR-1 to
  FR-9.

## Decisions

- **D1 Status 507 + code `disk-low`.** 507 Insufficient Storage is what `container-ops.ts` already
  answers for the same refusal; `code: 'disk-low'` is the machine-readable signal (never a prefix
  match). Adding 507 needs the `LaneLaunchError` status union (`types.ts:74`) and `OWNER_STATUSES`
  (`launch.ts:369`); nothing else.
- **D2 Same refusal text.** The lane door throws `reserveDiskFloor`'s own text unchanged (it starts
  with `Disk low — new workspace starts are held` and names free GiB, reserved GiB, own GiB and the
  floor). The issue asks for "the same 'Disk low' message and free GiB"; `disk-floor.ts` is not edited.
- **D3 Estimate = `max(estimateWorkspaceDiskCost(project).hostBytes, 2 GiB)`.** A builder lane
  installs its own dependencies in its worktree (the skill forbids installs in the primary checkout),
  so tracked bytes plus a sibling's unshared `node_modules` is the right order of magnitude (the
  incident lanes were ~1.4 GiB). `estimateWorkspaceDiskCost` finds `node_modules` only in a finished
  `feature-*` workspace or the primary checkout and counts a missing one as 0
  (`disk-cost.ts:148-172,201-223`), so a gauntlet project with neither would reserve only tracked
  bytes; the 2 GiB minimum (`LANE_WORKTREE_MIN_BYTES`, above the incident's measured 1.4 GiB per lane)
  is the conservative fallback. It overestimates a sparse-checkout lane; that is the safe direction.
  The estimate shares the workspace-start memo, so it is usually warm; a cold call can take ~10 s on a
  project with a compose template. No lane-only directory walk (lane worktrees are large and the
  minimum already covers the gap).
- **D4 Reserve 0 bytes for `--reuse` and `play`, but still check.** They create no worktree, but a
  launched agent writes to disk, and below the floor no new agent should start.
- **D5 `--force` never bypasses the floor.** CPU saturation is recoverable; ENOSPC zero-fills files.
  (`lane_start` over MCP strips `force` anyway.)
- **D6 Admission runs before the project lock; the lease is held through the install window.**
  Admission is already serialized by `reserveDiskFloor`'s cross-process file lock. The door starts
  the runtime without awaiting the lane's work, so releasing at return would free the lease after a
  small checkout and before the lane's install; the lease is therefore held for
  `LANE_DISK_HOLD_MS` (15 min) after a successful return by an unref'd timer
  (`holdLaneDisk`), and released at once on a throw. Holding it to the lane's first report or reap
  instead would need lease state that survives restarts and a release hook in report, stop and reap;
  a fixed window covers the install with no new state. While the lease is held, statfs also sees the
  lane's real bytes, so the window double-counts — the safe direction. Both doors attach this with
  `withProjectLock(...).then(onSuccess, onFailure)`, so the callback body is not re-indented, and a
  failed release never fails a launch.
- **D7 The reapable unit is the iteration group, not the row.** `--reuse` rows share one directory, so
  a group is reapable only when none of its rows is live. Every non-archived row is flagged; reaping
  the second row of a group hits `reapLane`'s "already gone" warning and still archives it.
- **D8 Orchestrator lanes are never reapable by this rule.** An archived orchestrator lane orphans the
  builders it launched (reference/lanes.mdx "Reap").
- **D9 Judges are reapable only after a newer judge iteration exists (same role rule).** A builder of
  iteration n+1 is told the path of the verdict file it answers (`contract.ts:46-47`), and the critic
  writes that file inside its own worktree (`gauntlet/notes/critique-<area>-iter<n>.json`). Reaping
  critic i(n) when builder i(n+1) launches would delete the file the builder is reading. By the time
  critic i(n+1) exists, builder i(n+1) has reported done.
- **D10 Builders are safe to reap once superseded.** Builder i(n+1)'s branch is cut from builder
  i(n)'s branch; `reapLane` keeps branches and refuses a dirty tree without `--park`.
- **D11 The wait hint goes on stderr before the status line.** Agents read the last stderr line for
  the `next:` command; the hint must not displace it.
- **D12 `pan lane disk-check` is a lane subcommand that runs locally.** The orchestrator already
  uses the `pan-lane` skill; a local core needs no route, scope or no-loss-matrix row (NFR-3) and works
  without the dashboard.
- **D13 Unregistered directories are listed, never removed.** Overdeck cannot know whether a directory
  it did not create holds unpushed work. The listing names them so the orchestrator removes them with
  `git worktree remove` (which refuses a dirty tree) after checking.
- **D14 No server-side auto-reap.** Reaping stays an explicit `pan lane reap`; Overdeck only flags.

   ```ts
    * Disk-floor admission for lane launches (PAN-5094). A lane's worktree is a
    * disk-heavy phase like a workspace start (PAN-4961): both lane doors admit it
    * with reserveDiskFloor at the lane's lanes root. A successful launch holds the
    * lease through the install window (the door does not await the lane's work); a
    * failed one releases it at once. All work is async (the doors run in the
    * dashboard server).
    */
   import { reserveDiskFloor, type DiskReservation } from '../disk-floor.js';
   import type { LaneRole } from '../overdeck/conversations.js';
   import { listProjectsAsync } from '../projects.js';
   import { estimateWorkspaceDiskCost } from '../workspace/disk-cost.js';
   import type { LaneConfig } from './config.js';
   import { LaneLaunchError } from './types.js';

   export const LANE_DISK_LOW_CODE = 'disk-low';
   const GIB = 1024 ** 3;
   /** D3: the least one new lane worktree reserves, for projects with no installed workspace to sample. */
   export const LANE_WORKTREE_MIN_BYTES = 2 * GIB;
   /** D6/FR-5: how long a launched lane's lease keeps counting (checkout plus dependency install). */
   export const LANE_DISK_HOLD_MS = 15 * 60_000;

   /** Test seams; production callers use the defaults. */
   export interface LaneDiskDeps {
     /** Free bytes on the filesystem holding `path`. Default readAvailableBytes. */
     read?: (path: string) => Promise<number>;
     /** The reservation ledger directory. Default ~/.overdeck/disk-reservations. */
     ledgerDir?: string;
     /** Bytes one new lane worktree adds. Default laneWorktreeBytes. */
     estimate?: (config: LaneConfig) => Promise<number>;
   }

   /**
    * D3: a new lane worktree costs what a workspace's host phase costs (tracked
    * files plus an install), and never less than LANE_WORKTREE_MIN_BYTES: the
    * workspace estimate counts a missing node_modules sample as 0.
    */
   export async function laneWorktreeBytes(
     config: LaneConfig,
     estimateWorkspace: typeof estimateWorkspaceDiskCost = estimateWorkspaceDiskCost,
   ): Promise<number> {
     const project = (await listProjectsAsync()).find((candidate) => candidate.key === config.projectKey)?.config
       ?? { path: config.projectPath };
     return Math.max((await estimateWorkspace(project)).hostBytes, LANE_WORKTREE_MIN_BYTES);
   }

   /** D4: --reuse and play create no worktree, so they reserve nothing but are still checked. */
   export async function laneLaunchBytes(
     input: { config: LaneConfig; role: LaneRole; reuse: boolean },
     deps: LaneDiskDeps = {},
   ): Promise<number> {
     if (input.reuse || input.role === 'play') return 0;
     return (deps.estimate ?? laneWorktreeBytes)(input.config);
   }

   /** FR-1/FR-2: admit a lane launch or throw LaneLaunchError(507, …, 'disk-low'). --force never reaches here (D5). */
   export async function admitLaneDisk(
     input: { config: LaneConfig; lanesRoot: string; role: LaneRole; reuse: boolean; label: string },
     deps: LaneDiskDeps = {},
   ): Promise<DiskReservation> {
     const bytes = await laneLaunchBytes(input, deps);
     const admission = await reserveDiskFloor(
       { path: input.lanesRoot, bytes, label: input.label },
       { ...(deps.read ? { read: deps.read } : {}), ...(deps.ledgerDir ? { ledgerDir: deps.ledgerDir } : {}) },
     );
     if (!admission.ok) throw new LaneLaunchError(507, admission.error, LANE_DISK_LOW_CODE);
     return admission.reservation;
   }

   /** FR-5: keep a launched lane's lease counting through its install window, then release it. */
   export function holdLaneDisk(reservation: DiskReservation, holdMs: number = LANE_DISK_HOLD_MS): void {
     const timer = setTimeout(() => {
       void reservation.release().catch(() => undefined);
     }, holdMs);
     timer.unref?.();
   }
   ```

### WI-4 — The reapable rule (`src/lib/lanes/reapable.ts`)

**What/why:** FR-6 as a pure function, so the rule is tested in isolation and views and the CLI share
one definition.

```ts
/**
 * PAN-5094: superseded lanes that `pan lane reap` can remove now. The unit is
 * the iteration group (one directory; several rows only after --reuse), so a
 * group is reapable only when none of its rows is live. Orchestrator lanes are
 * never reapable here: archiving one orphans the lanes it launched.
 */
import type { LaneActivity } from '@overdeck/contracts';

import type { LaneRole } from '../overdeck/conversations.js';

export interface ReapableRow {
  name: string;
  run: string;
  key: string;
  role: LaneRole;
  iteration: number;
  createdAt: string;
  archived: boolean;
  activity: LaneActivity;
  /** The lane filed at least one report. */
  reported: boolean;
}

const LIVE: ReadonlySet<LaneActivity> = new Set(['working', 'needs-you', 'starting']);

/** Lane name → name of the newest lane of the highest iteration, for every reapable lane. */
export function supersededLanes(rows: readonly ReapableRow[]): Map<string, string> {
  const groups = new Map<string, ReapableRow[]>();
  for (const row of rows) {
    if (row.role === 'orchestrator') continue;
    const id = `${row.run}\u0000${row.key}\u0000${row.role}`;
    groups.set(id, [...(groups.get(id) ?? []), row]);
  }
  const result = new Map<string, string>();
  for (const group of groups.values()) {
    const top = Math.max(...group.map((row) => row.iteration));
    const newest = group
      .filter((row) => row.iteration === top)
      .reduce((a, b) => (Date.parse(b.createdAt) >= Date.parse(a.createdAt) ? b : a));
    for (const iteration of new Set(group.map((row) => row.iteration))) {
      if (iteration >= top) continue;
      const members = group.filter((row) => row.iteration === iteration);
      const open = members.filter((row) => !row.archived);
      if (open.length === 0 || open.some((row) => LIVE.has(row.activity))) continue;
      if (!members.some((row) => row.reported) && open.some((row) => row.activity === 'idle')) continue;
      for (const row of open) result.set(row.name, newest.name);
    }
  }
  return result;
}
```

- builder i1 (idle, reported) + builder i2 (working) → i1 maps to i2's name; i2 absent.
- i1 `working` (reported) + i2 → nothing.
- i1 `idle`, not reported + i2 → nothing; i1 `stopped`, not reported + i2 → i1 reapable.
- i1 archived + i2 → nothing (archived rows never appear).
- two `--reuse` rows in i1 (one `stopped` reported, one `working`) + i2 → neither; both `stopped`

- orchestrator i1 (stopped, reported) + orchestrator i2 → nothing.

## Critique response

Answers to `.pan/drafts/PAN-5094-critique.md` (round 1, codex/gpt-6-sol).

### reservation ends before the lane writes

Accepted and changed. The doors start the runtime without awaiting it, so a lease released at return
would free the reservation after a small checkout and before the lane's install. FR-5 and D6 now hold
a successful launch's lease for `LANE_DISK_HOLD_MS` (15 minutes) after the door returns, through
`holdLaneDisk` (an unref'd timer that releases it); a throw still releases at once. While held, every
later admission counts it, so a burst of launches cannot each pass the floor. WI-1 adds a fake-timer
test where two held leases refuse a third admission until the window passes, and WI-2 adds a launch-
level overlap test (two launches held, the third refused). Holding until the lane's first report or
reap was rejected: it needs lease state that survives dashboard restarts and release hooks in report,
stop and reap, while a fixed window covers the install with no new state. A restart drops the timer
and the dead pid prunes the lease; that loses margin only, never correctness of the floor itself,
and the PAN-5093 alert stays the backstop.

### workspace estimate can omit lane dependencies

Accepted and changed. `laneWorktreeBytes` now returns
`max(estimateWorkspaceDiskCost(project).hostBytes, LANE_WORKTREE_MIN_BYTES)` with a 2 GiB minimum
(above the incident's measured 1.4 GiB per lane), so a project with no installed workspace or
primary-checkout `node_modules` still reserves room for the lane's own install (FR-3, D3). WI-1 tests
the minimum (0.3 GiB estimate → 2 GiB) and that a larger measurement wins (3 GiB → 3 GiB). A walk of
existing lane worktrees was not chosen: lane directories are large, the walk would add seconds to a
launch, and the minimum closes the gap the finding names.

### disk-check can inspect the wrong filesystem

Accepted and changed. FR-9 and WI-8 now preview at the nearest existing ancestor of the target
(`config.lanesRoot` with `--project`, the given or current directory otherwise), never at the project
path, so a lanes root on another mount that does not exist yet is checked on that mount. WI-8 tests it
with a path-dependent fake read (5 GiB on the lanes root's existing parent, 100 GiB elsewhere →
refusal at the parent). The launch doors were already correct: `prepareLanesRoot` creates the root
before admission.

### force test contradicts the CPU rule

Accepted. The WI-2 and WI-3 cases now assert that `force: true` still refuses with 507 and that
`cpuPressure` is not called.

### reapable does not guarantee a successful reap

Accepted. FR-6 defines `reapable` as "superseded and inactive: a candidate for `pan lane reap`", the
`--reapable` help text says "candidates for pan lane reap", the wait hint mentions `--park`, and WI-11
tells the orchestrator to rerun a dirty-tree refusal with `--park` and to leave a lane whose directory
still has processes, naming it in the run report.

### wait hint can delay a completed report

Accepted. `api` gains an optional timeout, and the hint's read uses `REAPABLE_HINT_TIMEOUT_MS` = 5 s,
so a slow dashboard delays a returned report by at most 5 seconds. WI-7 tests the timed-out path by
rejecting the fetch mock with a `TimeoutError`, never by waiting on a real timer.
