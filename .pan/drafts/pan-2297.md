# PAN-2297 — Auto-lower file-size baselines on the UAT batch merge path

**Issue:** [PAN-2297](https://github.com/eltmon/overdeck/issues/2297)
**Related:** [PAN-2296](https://github.com/eltmon/overdeck/issues/2296) (the incident), [PAN-2227](https://github.com/eltmon/overdeck/issues/2227) (added the ratchet guard)
**Mode:** `pan plan --auto` (no interactive Q&A; defaults recorded below and in `plan.autoDecisions`)

## Glossary

- **file-size baseline** — `scripts/file-size-baseline.txt`, one `"<lines> <path>"` entry per baselined "god file". A baselined file may **shrink** but never **grow**. Maintained by `scripts/lint-file-size.sh`.
- **`lint:file-size`** — `npm run lint:file-size` → `bash scripts/lint-file-size.sh` (check mode). Fails when a baselined file **grew** above its entry, **or** when it **shrank below** its entry (a *stale-high* baseline) — the latter is the PAN-2296 failure.
- **`--update` (auto-lower)** — `bash scripts/lint-file-size.sh --update`. Lowers stale entries to the current line count, drops entries for files now at/under the 1000-line ceiling or deleted. **Never raises or adds** entries. Lowering is always audit-exempt.
- **ratchet audit** — `scripts/lint-ratchet-audit.sh`. Only *raising/adding* a baseline entry needs an issue reference; *lowering* is free.
- **UAT batch promote** — `promoteUatGeneration()` merging a tested `uat/*` batch branch to `main` via one `--no-ff` merge and a direct `git push HEAD:main`. Real git wiring: `buildUatPromoteGitDeps().mergeIntoMain()` in `src/lib/cloister/uat-promote.ts`.
- **pre-push hook** — `.husky/pre-push`. Runs `lint-file-size.sh` (check) + `lint-ratchet-audit.sh` on pushes. A *check* — it can only block, and does not reliably fire on server-initiated automation pushes.

## Problem

[PAN-2296](https://github.com/eltmon/overdeck/issues/2296) exposed that when UAT batch `uat/pan-cobalt-0703` merged to `main`, a baselined source file shrank from 1925 → 1924 lines but `scripts/file-size-baseline.txt` stayed at 1925. `npm run lint:file-size` then failed on `main` with a stale-high baseline (it was fixed manually in commit `27a9a0f129`).

### Root cause (verified against the code at writing time)

`mergeIntoMain()` in `src/lib/cloister/uat-promote.ts` (real git deps, lines 211–229):

```ts
await runGit(['worktree', 'add', '--detach', worktreePath, 'origin/main'], projectRoot);
// ...
await runGit(['merge', '--no-ff', ref, '-m', message], worktreePath);   // line 222
await runGit(['push', 'origin', 'HEAD:main'], worktreePath);            // line 223
return (await runGit(['rev-parse', 'HEAD'], worktreePath)).stdout.trim();
```

There is **no baseline reconciliation** between the merge (222) and the push to `main` (223). The merged tree can shrink a baselined file below its recorded size, and that tree is pushed straight to `main`.

The only PAN-2227 guard is the `.husky/pre-push` hook (`.husky/pre-push:13` runs `bash scripts/lint-file-size.sh`). That guard is inadequate for this path because:

1. It is a **check**, not a fixer — even if it fired it would *block* the promote, wedging a fully review+test-passed batch on a one-line baseline drift.
2. It does not reliably fire on **server-initiated** pushes from the dashboard/cloister automation, so the stale baseline sailed through to `main`.

A grep of the whole tree confirms **no code path** invokes `lint-file-size.sh --update` (`--update` exists only as a manual CLI mode added by PAN-2227). So the "auto-lowering" the issue references was never wired into any merge path — the fix is to wire it into the final write point.

## Proposal

Enforce the invariant **at the final write point** (the promote's push to `main`), in code, independent of husky:

In `mergeIntoMain()`, after `git merge --no-ff` and **before** `git push origin HEAD:main`:

1. Run `bash scripts/lint-file-size.sh --update` in the merge worktree (cwd = the merged tree).
2. If it modified `scripts/file-size-baseline.txt`, `git add` it and `git commit --amend --no-edit` so the reconciled baseline is part of the single merge commit that lands on `main`.
3. Push.

Lowering a baseline is audit-exempt (`lint-ratchet-audit.sh` requires an issue reference only for *raises/adds*), so amending the merge commit with a lowered baseline does not trip the ratchet audit.

The reconcile logic is extracted into a small exported, independently unit-testable helper so its behavior is provable without standing up the full promote deps, and so a real-git integration test can reproduce PAN-2296 end-to-end.

### Why amend the merge commit (not a follow-up commit)

The promote's contract is "main receives EXACTLY the tree the operator exercised." Amending keeps `main` at a single `--no-ff` merge commit whose tree is the tested tree plus the baseline-metadata reconciliation (a documented, deliberate exception — baseline.txt is CI metadata, not tested behavior). A separate follow-up commit would add a second commit to `main` per promote for no benefit.

## Requirements

- **FR-1** — When a UAT batch merge shrinks a baselined file below its `scripts/file-size-baseline.txt` entry, the promote lowers the baseline entry to match before the merge commit is pushed to `main`.
- **FR-2** — The lowered baseline is part of the merge commit that lands on `main` (single merge commit; no second commit).
- **FR-3** — When the merged tree needs no baseline change, the promote pushes the merge commit unchanged (no empty amend, no spurious baseline churn).
- **FR-4** — After a promote, `npm run lint:file-size` passes against `main` for any baselined-file shrink introduced by the batch.
- **NFR-1** — The reconcile uses async child-process execution (no `execSync`; server-reachable code).
- **NFR-2** — The reconcile only ever lowers/drops baseline entries; it never raises or adds an entry (delegates to `lint-file-size.sh --update`, which enforces this).

## Non-Goals

- Changing the single-issue GitHub squash-merge path (feature-branch pre-push already forces a consistent tree before the PR is green; that path is out of scope).
- Modifying `.husky/pre-push` or husky behavior.
- Auto-**raising** baselines or auto-adding new entries (raises stay manual + audited).
- Reconciling the `eslint-any-allowlist.json` ratchet (this issue is file-size only).
- Changing UAT assembly (`uat-assemble`); the fix lives at the final write point (promote), not assembly.

## Work Items

1. **reconcile-helper** — new `src/lib/cloister/file-size-reconcile.ts`: exported `reconcileFileSizeBaseline(worktreePath, runGit)` that runs `bash scripts/lint-file-size.sh --update`, checks `git status --porcelain -- scripts/file-size-baseline.txt`, stages the baseline if changed, returns `{ changed: boolean }`. Unit test in `tests/unit/lib/cloister/file-size-reconcile.test.ts` (real temp git repo + installed script, mirroring `tests/unit/scripts/lint-file-size.test.ts`).
2. **wire-into-promote** — call the helper inside `mergeIntoMain()` between the `--no-ff` merge and the push; on `changed`, `git commit --amend --no-edit`; update the file's doc comment to record the baseline-reconcile exception to "exactly the tree tested."
3. **reproduce-integration-test** — real-git integration test that builds a bare origin + worktree, assembles a batch branch that shrinks a baselined file, drives `buildUatPromoteGitDeps().mergeIntoMain()`, and asserts the pushed `main` baseline is lowered so `lint-file-size.sh` (check) passes on `main`.
