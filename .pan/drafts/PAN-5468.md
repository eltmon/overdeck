## Glossary

- **Issue pipeline**: the fixed sequence an issue moves through: plan, work, verification, review,
  tests and UAT, merge, close-out. Each stage is run by an agent role or by the dashboard server.
- **Role**: a kind of agent Overdeck launches for one stage: `plan`, `work`, `review`, `test`,
  `strike`. Prompts live in `roles/<role>.md`.
- **xBRIEF plan**: the plan file with checklist items and acceptance criteria that planning writes to
  `.pan/specs/` and that `pan task` ticks off. Covered in depth by `features/planning.mdx`.
- **Verification gate**: the project's quality gates that the dashboard runs on the PR head after
  `pan done` and before review starts.
- **CI mode** (`verification.tests: ci`): the project's tests run once per push on CI. The CI test job
  on the PR head is the test gate; the host runs only the non-test gates.
- **Review modes**: `roles.review.mode` is `quick` (one reviewer, default), `full` (the review convoy:
  four parallel reviewers and a parent that writes one verdict) or `none` (no AI review).
- **UAT**: user acceptance testing in a real browser. Two different things share the word: a **UAT
  verdict** (a test role result posted as an `overdeck-uat` PR marker) and a **UAT hold** (a merge
  policy that keeps a ready PR waiting for a person).
- **The one merge gate**: `evaluateIssueMergeGate`, the single function every merge path asks.
- **Ready**: the derived issue state meaning approved at the PR head, no changes requested, checks
  green and mergeable. Awaiting Merge lists ready issues.
- **Needs you**: the one list of things a person must act on, shown as the top bar's `Needs you · N`
  button and in several panels.
- **Strike**: a short path for a small, already understood fix: one agent, a `strike/<id>` branch and a
  PR, with no plan and no review convoy.
- **Close-out**: the final ceremony that verifies a merged issue, cleans up and closes the tracker
  issue (`pan close` or the `Close Out` button).
- **Pipeline journal**: `<workspace>/.overdeck/pipeline.jsonl`, an append-only log of pipeline
  actions. Never authority: when it disagrees with the PR, the PR wins.
- **Mint check**: `npx -y mint@4.3.49 validate` and `npx -y mint@4.3.49 broken-links`, run from the
  workspace root. Always pin `mint@4.3.49` (the version the sibling docs issues standardized on).
  Never run `mint validate --fix`: it rewrites about 80 files that sibling issues edit in parallel.
- **Dash rule**: no em dash (U+2014) and no en dash (U+2013) anywhere this issue writes, including the
  frontmatter `title`, `sidebarTitle` and `description`, and every body line added or edited. Quoted
  code strings that contain an em dash (for example the Auto/Hold tooltips) must be paraphrased, not
  quoted.

`FE/` below means `src/dashboard/frontend/src/`.

## Background: verified facts

### Start an issue (`pan start`)

- `pan start --help`: `--plan <mode>` "Planning depth when no plan exists yet: interactive | auto |
  skip (default: config planning.default_mode, shipped default auto)". Other flags the page may
  mention: `--plan-model`, `--model`, `--harness`, `--effort`, `--force`, `--fresh`, `--remote`,
  `--machine`. `--auto` is deprecated (help: "[deprecated: use --plan skip]").
- Mode precedence, `src/cli/commands/planning-mode.ts:28-32` and line 77
  (`return { mode: 'auto', warnings };`): explicit `--plan`, then `--auto` (treated as `skip`, warns
  "--auto is deprecated; use --plan skip instead."), then `planning.default_mode`, then `auto`.
- Planning runs only when no plan exists: `src/cli/commands/start.ts` anchor
  `if (!existingPlan) {` (about line 674). With a plan already present, `--plan` is ignored and the
  work agent starts directly.
- `auto` and `interactive` start a planning session with `autoStart: true` (`start.ts` anchor
  `autoStart: true,` about line 700) and print "The work agent will start automatically after
  planning finalizes." (anchor at about line 732). So **`pan start` never stops at Planned**: the work
  agent starts when planning finalizes. `interactive` asks you questions; `auto` decides itself and
  records its choices in `plan.autoDecisions`.
- `skip` synthesizes a minimal xBRIEF from the issue title and body (`start.ts` anchor
  `Synthesizing minimal xBRIEF`) and starts work at once.
- `--plan-model` sets the planning model; `--model` stays the work model (`start.ts` anchor
  `workModel: options.model`).
- `--force` clears the paused and troubled gates (`start.ts` about lines 592-610). Do not claim it
  clears an operator-decision gate: that is only checked on the `--fresh` path
  (`src/cli/commands/start-fresh-session.ts` anchor `pass --force to discard it`). Code wins over the
  help text here.
- `--fresh` (help) "Drop the saved Claude session (non-destructive) and start a new one, replaces a
  live session too" (help uses an em dash; paraphrase).
- Planning started from the dashboard Plan dialog waits in **Planned** unless its checkbox
  `Start work as soon as the plan is ready` is ticked (`FE/components/PlanDialog.tsx` anchor
  `useState(false)` near the checkbox; label anchor `Start work as soon as the plan is ready`).
  `pan plan <id>` alone also leaves the issue in Planned.
- Dashboard issue actions (`FE/lib/issueActions.ts`): `Plan…`, `Accept plan`, `Start work`
  (`Start work` is enabled only when the plan has tasks and no agent is running, `canStartAgent`).
  There is no action named "Start Agent"; do not use that label.

### Plan (one paragraph only)

- `roles/plan.md`: the plan agent writes no code. It writes a PRD (`.pan/drafts/<issue>.md`), an xBRIEF
  plan, and `continue.json`, then runs `pan plan finalize`, which promotes the spec to `.pan/specs/`
  on the feature branch and moves the issue to Planned. The page links `/features/planning` for
  everything else (comment from #5469: "When you write the plan stage of the pipeline page, please
  link it to `/features/planning`").

### Work and `pan done`

- `roles/work.md` (anchor `pan task next`): the work agent claims one xBRIEF item at a time
  (`pan task claim`), commits each item with an `Item: <id>` trailer, pushes, and marks it done with
  `pan task done`. `pan task --help`: each id needs a pushed commit carrying `Item: <id>`.
- The work agent runs only the tests it touched, never the full suite (`roles/work.md` anchor
  `the verification gate runs it after`).
- `pan done --help`: "Mark work complete, move to review". Flags: `-c/--comment`, `--force` ("Skip
  pre-flight completion checks"), `--test-waived <reason>`, `--strike`.
- Preflight (`src/lib/work/done-preflight.ts`, anchor `Incomplete plan items`): it refuses when plan
  items or their acceptance criteria are open, when the workspace has uncommitted changes (ignoring
  `.pan/` and `.overdeck/`), or when the test-requirement gate finds code changes without tests.
  `--test-waived <reason>` skips only the test-requirement gate; `--force` skips all preflight.
- After preflight, `pan done` rebases onto the target branch and pushes (`src/cli/commands/done.ts`
  anchor `Rebasing onto target branch and pushing`), opens or updates the PR and marks it ready,
  moves the tracker issue to In Review, and asks the dashboard to start verification and review. If
  the dashboard is unreachable it still exits 0 and the GitHub webhook starts the same pipeline
  (`done.ts` header, about lines 10-11).

### Verification gate

- Gates come from the project's `quality_gates` in `projects.yaml`, or the defaults typecheck, lint
  and test (`src/lib/cloister/validation.ts` anchor `export const DEFAULT_GATES`). User docs for the
  key: `configuration/projects.mdx` section `### Quality gates`.
- Test mode (`src/lib/cloister/verification-tests-mode.ts` about lines 305-317): `verification.tests`
  is `ci` or `local`. When unset, it is `ci` if a GitHub Actions workflow runs a test job on pull
  requests, otherwise `local`. In CI mode the host skips the `test` gate and the CI test job on the PR
  head is the test gate (`docs/PIPELINE-GATES.md` heading `### One full-suite run per push, on CI`).
- On a failure the work agent gets a `VERIFICATION FAILED` message naming the failed check and is told
  to fix, push and run `pan review request` (`src/lib/cloister/verification-runner.ts` anchor
  `VERIFICATION FAILED for`). Review does not start until verification passes.
- Attempts: `VERIFICATION_MAX_CYCLES = 3` per PR head (`verification-cycles.ts`), and
  `NO_PROGRESS_REPEAT_THRESHOLD = 2` (same check failing twice in a row). On the final attempt, or on
  a repeated identical failure, Overdeck pauses and stops the work agent with the reason
  `needs-you: verification stuck ...` (`verification-escalation.ts` anchor
  `export const VERIFICATION_STUCK_PAUSE_PREFIX`). The pause is the operator signal.
- Test-skip gate (`docs/PIPELINE-GATES.md` about lines 780-824): an added `.skip`, `.only` or `xit`
  always fails; removing tests fails unless the whole diff balances or the subject under test was
  deleted. An operator can let one net removal through with
  `pan review waive-test-removal <id> --reason "<why>"` (`pan review --help`: "Operator-only"),
  pinned to the current head; then run `pan review request`.

### Review

- Default mode is quick: `src/lib/config-yaml/roles.ts` anchor `mode: 'quick',` (about line 45).
  `quick` = one reviewer covering correctness, security, performance and requirements; `full` = the
  review convoy (four parallel reviewers and a parent that writes `synthesis.md` and posts one
  verdict); `none` = no AI review, the verification gate still applies
  (`docs/REVIEW-AGENT-ARCHITECTURE.md` about lines 110-114). The convoy page is `/features/convoys`.
- The verdict is a PR review: approve, or request changes (`roles/review.md` anchor
  `pan admin specialists done review`). Approval counts only at the exact head commit (merge-gate
  docblock anchor `a marker naming another commit never approves a merge`).
- A request for changes goes back to the work agent as PR comments plus a direct message
  (`features/specialists.mdx` already says so; code: `deliverReviewVerdictFeedback`).
- `pan review --help` subcommands: `request [-m]`, `waive-test-removal`, `abort`, `restart
  [--model] [--role correctness|security|performance|requirements]`. There is no `pan review reset`;
  do not mention it.
  - `request`: re-request review after a fix. Automatic re-requests are capped at 25 per issue
    (`routes/workspaces/review-pipeline.ts` anchor `const MAX_AUTO_REQUEUE = 25;`), reset on dashboard
    restart.
  - `restart`: re-dispatches reviewer lanes missing a report and keeps completed reports
    (`review-restart.ts` header).
  - `abort`: kills running reviewers and leaves the worker idle.
- Convergence: there is no hard round limit. After at least 3 rounds
  (`review-convergence.ts` anchor `REVIEW_CONVERGENCE_MIN_CYCLES = 3`) where the blocker count rose or
  stalled, automatic re-review stops and Needs you shows `Review loop not converging`
  (`review-verdict-feedback.ts` anchor `Review loop not converging`). The count resets after an
  approved round.
- A push after approval needs a new review: approval is pinned to the head (changelog v0.73.0).

### Tests and UAT (implementation checkpoint, see D-3)

- The test role (`roles/test.md`; prompt in `src/lib/cloister/test-agent-queue.ts`
  `buildTestRolePrompt`) runs the project gates, decides whether browser UAT is needed from the
  acceptance criteria, drives the workspace-built dashboard with Playwright, and records two separate
  verdicts: tests and UAT. "There is no separate UAT role" (`roles/test.md:51`).
- A failed UAT verdict at the PR head blocks merge (`src/lib/cloister/pr-facts.ts` anchor
  `a failed UAT at this head is evidence the code does not work`). The gate never requires a passed
  UAT.
- **Today the test role does not start automatically after review approves.** The reactive dispatcher
  maps `review.approved` to the test role (`service-reactive.ts` anchor `case 'review.approved':`),
  but nothing emits that event (`git grep -n "review\.approved" -- src` shows only the type, the
  consumers, the forwarder and a comment). None of the last 12 merged PRs (#5513 to #5536) carries a
  `**test verdict:` comment or an `overdeck-uat` marker. Filed as **#5537**. The test role starts only
  when `pan review request` runs on a PR approved at head whose checks are not green
  (`review-pipeline.ts` anchor `dispatching test role`) or when an issue whose test agent was stopped
  is unpaused (`src/lib/agents/issue-pause.ts` anchor `dispatchTestAgentAndNotify`).
- For CI-mode projects the CI test job on the PR head is the test gate and the merge gate requires it
  (`pr-facts.ts` `evaluateMergeReadiness`), so untested code does not merge.

### Feedback that returns to the work agent

- **CI failures** (`src/lib/cloister/ci-failure-feedback.ts`, `relayCiFailureFeedback`): a failed PR
  check (from GitHub webhooks) writes a feedback file in the workspace and messages the work agent,
  with `gh run view --log-failed` excerpts. A failure that also fails on `main` is tagged
  `[INHERITED FROM MAIN` (anchor; the tag continues with an em dash, paraphrase it). In CI mode a red
  test job counts against the same 3-attempt verification budget. Only `feature/` heads count;
  cancelled or timed-out runs do not.
- **CodeRabbit** (`src/lib/advisory-checks.ts` anchor `new Set(['coderabbit'])`;
  `src/lib/cloister/coderabbit-feedback.ts`): advisory, never a merge gate, nothing waits for it. Its
  findings are relayed to the work agent, which fixes each one or replies on the thread. Findings
  still open after merge become a follow-up issue titled `CodeRabbit follow-up for ...`
  (`advisory-followup.ts` anchor `CodeRabbit follow-up for`). Reviewers also see the findings as
  context.
- **Merge conflicts**:
  1. Before review: a PR that conflicts with its target defers review and starts a conflict-resolver
     run, or messages the running agent, at most once per 30 minutes (`conflict-gate.ts` anchor
     `must be resolved before review dispatch`).
  2. After approval: the conflict-repair patrol asks the work agent once per PR head to run
     `pan sync-main` and push; if the head still conflicts after 45 minutes it raises Needs you
     (`conflict-repair.ts` anchor `CONFLICT_REPAIR_GRACE_MS = 45 * 60_000`).
  3. At merge: see the Merge button below.
  - `pan sync-main <id>` (help: "Merge latest main into workspace feature branch") merges, it does not
    rebase, and it does not push. Conflicts only in `.pan/` resolve to main; any other conflict aborts
    the merge for manual resolution (`merge-agent.ts` anchor `Resolve manually in the workspace`).

### Needs you and `pan ask`

- One selector feeds every Needs-you surface (`FE/lib/selectors/needsYou.ts` anchor
  `the one list of things a human must act on`): pending input (AskUserQuestion prompts, plans
  awaiting approval, permission prompts), issues whose derived attention is `needs-you`, Flywheel
  needs-you rows, and other decisions.
- Where it shows: the top bar button `Needs you · N` (`FE/components/flywheel/NeedsYouIndicator.tsx`
  anchor `Needs you · {count}`), the project Home `Needs you` panel, the Board strip and the Home page
  tile. The middle dot (U+00B7) is allowed; it is not a dash.
- `pan ask --help`: "Ask the operator a blocking decision; it appears in the dashboard Needs-you".
  Flags: `--option <label>` (2 to 4 times), `--context <text>`, `--withdraw`. Agents use it; the
  agent is told "Stop and wait: the answer arrives as a message in this session."
  (`src/cli/commands/ask.ts` anchor `Stop and wait`).
- The operator sees the question as a dialog headed `Decision` (`operator-decision.ts` anchor
  `header: 'Decision'`) and picks an option or types an answer; the answer arrives in the agent's
  session as a message. Any `pan tell` to the asking agent also closes the question.
- `pan answer <id> [option]` answers a numbered menu shown in an agent's terminal pane (not a
  `pan ask` decision). `pan parked` lists issues parked behind an operator gate, a zombie session or
  an idle running agent, with why and how to release each.

### Merge

- **The one merge gate**: `evaluateIssueMergeGate` (`src/lib/cloister/merge-gate.ts` anchor
  `Every merge door asks this one function`), using `evaluateMergeReadiness` (`pr-facts.ts`). Every
  merge path asks it: Awaiting Merge, the Merge button, auto-merge, the merge train and the per-project
  queue. A PR passes only when it is open and not a draft, approved at the head commit with no changes
  requested, all checks green (pending or no checks block), the CI test job passed on the head in CI
  mode, no failed UAT verdict at the head while the issue is held for UAT, and GitHub reports it
  mergeable. Nothing is stored: the
  answer is computed from the PR each time.
- **Merge button**: `POST /api/issues/:id/merge` runs `triggerMerge`
  (`src/dashboard/server/routes/workspaces/merge-ops.ts`), which asks the gate first. A clean PR is
  merged directly (anchor `PR is CLEAN`); otherwise the server rebases onto main, and if that rebase
  fails the work agent is asked to rebase (message starts `MERGE REQUESTED:`). Post-rebase
  verification is skipped when CI is already green on that commit. The merge is a squash merge
  (`method: 'squash'`).
- **Awaiting Merge** (`FE/components/AwaitingMergePage.tsx`): heading `Awaiting Merge`; lists ready
  issues; each row has `Merge` and an `Auto` / `Hold` toggle; sections `Blocked from Merge` and
  `Pipeline Override` (open PRs that are not ready, with `Force Approve` and `Force Merge`, both behind
  a confirmation; `Force Merge` skips the rebase, post-rebase verification and post-merge cleanup but
  still runs repository merge guards). `features/dashboard-views.mdx` section `## Awaiting Merge`
  already describes the page; link to it instead of repeating row details.
- **Merge policy and the default** (`src/lib/cloister/auto-merge-policy.ts` header;
  `src/lib/overdeck/control-settings.ts` anchor `defaults to true if unset`): per-issue label
  `auto-merge` or `hold-for-uat` (set with the `Auto` / `Hold` toggle), else the project's
  `auto_merge_default` (`auto` or `hold`), else the global `require_uat_before_merge`, which defaults
  to true. So **by default a ready PR waits for you to click Merge.** With the hold off, the
  auto-merge scheduler schedules every ready PR and merges it after a 5-minute cooldown
  (`auto-merge-config.ts` anchor `AUTO_MERGE_COOLDOWN_MS = 300_000`); `pan merge cancel <id>` cancels
  during the cooldown. Details: `/configuration/auto-merge`.
- **Merge train**: off by default (`control-settings.ts` anchor
  `getSetting(FLYWHEEL_MERGE_TRAIN_ENABLED_KEY) === 'true'`). One sentence and a link to
  `/features/merge-batches`.
- PRs use a non-closing issue reference; close-out owns closing the issue (`ensure-pr.ts` anchor
  `Overdeck's close-out owns issue closing`).

### Strikes

- `pan strike --help`: "Spawn strike agent(s), implement a fix on a strike branch and open a PR
  against main for the operator to merge. Bypasses plan/review/test/ship." (help uses an em dash;
  paraphrase.) Flags: `--model`, `--harness`, `--effort`, `--dry-run`. Takes several ids.
- Shape (`src/cli/commands/strike.ts`): branch `strike/<id>`, workspace `workspaces/feature-<id>-strike`.
  No xBRIEF, no review convoy, no test role (`roles/strike.md` anchor `There is no xBRIEF`). Meant for
  a clear, small, low-risk fix; the strike agent aborts if the fix turns out broader.
- **Code differs from the help text:** a green strike PR gets one automatic quick review per head; if
  it approves, the auto-merge scheduler merges it ahead of other PRs with the 5-minute cancel window.
  Only a UAT hold leaves it for your Merge click. A changes-requested verdict stops the strike and
  nothing reworks it (`src/dashboard/server/services/strike-review.ts` header;
  `auto-merge-scheduler.ts` anchor `A strike branch is high priority`; changelog v0.86.0 "Strike PRs
  merge on their own"). Code wins.
- After the PR merges, Overdeck stops the strike agent, removes its worktree and deletes the branch
  (`roles/strike.md`; journal entry `strike.landed`).
- `pan done --strike` only checks that the strike branch is contained in `origin/main`; it opens no PR.

### After merge: close-out

- Post-merge lifecycle (`postMergeLifecycle`, `src/lib/cloister/merge-agent.ts`): frees agents,
  tears down Docker, cleans labels, applies `verifying-on-main`, stops reviewers, and leaves the
  issue, workspace and branches for close-out (anchor `Awaiting close-out (verify on main)`).
- `pan close --help`: "Verify, clean up, and close issue on tracker". It checks the Definition of Done
  rows in `src/lib/lifecycle/dod.ts`: 1 Review passed, 2 Tests passed, 3 Verification green on the
  branch, 4 Merged to main, 5 Post-merge lifecycle ran, 6 Verified on main, 7 Version strings
  propagated, 8 Deployed, 9 Close-out teardown verified. Rows 1 to 8 each have an `--accept-*` flag,
  recorded as an explicit override; row 9 cannot be overridden. `--abandon <reason>` and
  `--residue <reason>` are operator-conversation only.
- Dashboard: the `Close Out` button (`FE/components/CloseOutIssueButton.tsx` anchor `'Close Out'`) asks
  for confirmation (`Close Out Issue`) and runs the same close-out.
- Automatic close-out was removed: `close_out.auto` is inert (`src/lib/config.ts` anchor
  `auto / auto_delay_minutes are inert`). Close-out settings are documented by #5479; link
  `/features/workspaces` only if that page has a close-out section when the work agent writes,
  otherwise mention no settings.
- After an issue is closed and its branch is merged, the closed-issue reaper removes the workspace
  and deletes the local and remote `feature/` branch (`closed-issue-reaper.ts`,
  `reap-issue-residue.ts` anchor `Destructive disk/branch cleanup stays gated on the merged check`).
  The page must warn: keep nothing you need inside `workspaces/feature-<id>/` once you close.

### Restart, rerun or reopen

| Situation | Command | Verified behavior |
| --- | --- | --- |
| Agent stopped or crashed | `pan recover [id]` | "Recover crashed or stopped agent"; `--all`, `--compact`, `--model` |
| Resume the saved session | `pan resume <id>` | "Resume from saved Claude session" |
| Start over with a new session | `pan start <id> --fresh` | drops the saved session (non-destructive), replaces a live one |
| Paused or troubled agent | `pan unpause <id>`, `pan untroubled <id>`, or `pan start <id> --force` | clears the gate |
| Re-run review after a fix | `pan review request <id> -m "..."` | re-requests review |
| Review stuck on missing reviewers | `pan review restart <id> [--role ...]` | re-dispatches lanes without a report, keeps finished ones |
| Stop reviewers | `pan review abort <id>` | kills reviewers, leaves worker idle |
| Issue already closed, completed or cancelled | `pan reopen <id> [--reason]` | reopens the tracker issue, adds `in-progress`, posts a comment (`src/lib/reopen.ts`); refuses an open issue unless `--force` |

`pan reopen --help` says it "resets specialist state"; the code (`src/lib/reopen.ts` header anchor
`Every one of those fields is now derived`) resets none, because that state is derived. Code wins: the
page says reopen reopens the issue and the pipeline picks it up from the PR and branch.

`pan kill <id>` stops agents and keeps the workspace. `pan wipe` is destructive; the page must not
recommend it for restarts.
