# PAN-4738: Fly machine first conversation message lost to Claude Code's "Make auto mode your default" startup dialog

**Issue:** [PAN-4738](https://github.com/eltmon/overdeck/issues/4738) · found in the PAN-4652 live check
(`docs/fly-provider.md`, "Live verification (PAN-4652)", Run 1, machine `862102ae249718`, 2026-11-01).
**Planned:** 2026-11-02, `pan plan --auto`, high effort.

## Glossary

- **Auto-default nudge** — Claude Code's one-shot startup dialog titled
  `Make auto mode your default permission mode?`, with the options
  `Yes, set auto mode as my default permission mode` and `No, keep <current mode>`.
  Internally its request kind is `auto_default_nudge`; showing it logs
  `tengu_auto_default_nudge_shown`.
- **Global config** — Claude Code's `~/.claude.json` (resolved from `$HOME`). It holds
  `hasCompletedOnboarding`, `bypassPermissionsModeAccepted`, per-project trust, and the
  nudge's dismissal flag `hasSeenAutoDefaultNudge`.
- **User settings** — Claude Code's `~/.claude/settings.json`. On a Fly VM Overdeck writes it
  from `buildClaudeUserSettings()` (`src/lib/claude-permissions.ts`).
- **`configureClaudeCode`** — `FlyProvider.configureClaudeCode(vmName)` in
  `src/lib/remote/fly-provider.ts`. It prepares Claude Code on a Fly VM. Both Fly paths call it:
  Fly machines (`src/lib/anywhere/fly/provision.ts`, line 265) and remote work agent VMs
  (`src/lib/remote-workspace.ts`, line 210; `src/cli/commands/start.ts`, line 418).
- **Readiness wait** — `waitForClaudeReady(tmuxSession)` in
  `src/lib/overdeck/claude-readiness.ts`. A new Claude Code conversation waits on it before the
  first message is delivered (`waitForConversationRuntimeReady`, case `claude-session-signal`,
  mode `spawn`, in `src/lib/overdeck/conversation-runtime.ts`).
- **Composer** — Claude Code's input box. Its prompt row starts with `❯`.
- **Spawn error** — the `spawn_error` column a failed conversation start writes through
  `updateSpawnError()` (`src/lib/overdeck/conversations.ts`). The conversation panel shows it.
- **Exec shell** — the shell the Fly Machines exec API runs. It has `HOME=/`, so on a Fly VM
  `~/.claude.json` is `/.claude.json`. `pan serve` on the VM runs with the same `HOME`, which is
  why the onboarding and trust keys `configureClaudeCode` writes do take effect.

## Problem

A conversation started on a Fly machine (`pan machines add-fly --message …`) lost its first
message. The VM's `fly-serve.log` shows `[conversations] Claude Code ready in conv-…`, then
`[tmux] Paste verification failed for conv-20261101-7678 after 2 attempts`, and the pane snapshot
shows the auto-default nudge. The paste went into the dialog; Claude sat at an empty prompt with
0% context. Every Fly VM starts with fresh Claude Code state, so this happens on every new Fly VM
whose account is eligible for the nudge.

## Root cause (verified 2026-11-02)

### 1. The dismissal key and the eligibility rule, from the Claude Code binary

The Fly image `pan-workspace:pan-4652` ships Claude Code **2.1.316**
(`docker run --rm --entrypoint sh pan-workspace:pan-4652 -c 'claude --version'` → `2.1.316 (Claude Code)`).
Its eligibility function, extracted with `grep -a -o` from
`/usr/lib/node_modules/@anthropic-ai/claude-code/bin/claude.exe`:

```js
function rgo(u,{requireOnboarding:n=!0}={}){let o=ue();if(n&&!o.hasCompletedOnboarding||o.hasSeenAutoDefaultNudge||!v("tengu_maple_pier",!0))return null;let e=be("userSettings")?.permissions?.defaultMode,t=["projectSettings","localSettings","flagSettings","policySettings"].some((r)=>be(r)?.permissions?.defaultMode);if(e&&e!=="auto"&&!t&&qV(u))return e;return null}
```

The host's Claude Code 2.1.293 has the same function (named `vAr`) and the same key. When the
dialog is answered, Claude Code saves the flag through its global-config writer:

```js
Ae((Q)=>Q.hasSeenAutoDefaultNudge?Q:{...Q,hasSeenAutoDefaultNudge:!0},L.storageV5)
```

`Ae` is the same writer that sets `hasCompletedOnboarding:!0` on login
(`Ae((g)=>{if(g.hasCompletedOnboarding)return g;return{...g,hasCompletedOnboarding:!0}},m)`), so
the key lives in `~/.claude.json`, beside the onboarding flag `configureClaudeCode` already writes.

So the dialog shows when **all** of these hold:

1. `hasCompletedOnboarding` is true (Overdeck sets it on the VM).
2. `hasSeenAutoDefaultNudge` is not true.
3. The server-side flag `tengu_maple_pier` is on (default `true`).
4. User settings set `permissions.defaultMode`, and it is not `auto`.
5. No project, local, flag or policy settings layer sets `defaultMode`.
6. `qV(u)` (2.1.316) / `c1(u)` (2.1.293): auto mode is available to this account and session.

On a Fly VM, condition 4 always holds: `buildClaudeUserSettings()` writes
`defaultMode: 'bypassPermissions'` or `'default'`, never `'auto'`
(`src/lib/claude-permissions.ts`, line 162:
`defaultMode: resolved === 'bypass' ? 'bypassPermissions' : 'default',`).
Conditions 3 and 6 depend on the account. That explains why the PAN-4652 agent's local docker
repro (no real Claude account) never showed the dialog: a negative local result proves nothing.

Do **not** confuse the key with the older keys present in an operator's `~/.claude.json`
(`hasSeenAutoDefaultNotice`, `hasResetAutoModeOptInForDefaultOffer`, `hasSeenAutoModeEntryWarning`,
`hasSeenAutoModeOutsideReadPrompt`). None of them gates this dialog; `hasSeenAutoDefaultNudge` does.

### 2. The readiness wait took the dialog for the composer

`waitForClaudeReady` returns as soon as the visible pane contains `❯`
(`src/lib/overdeck/claude-readiness.ts`, line 113: `if (capture.includes('❯')) {`). The nudge's
option list is a select whose focused row also starts with `❯`, so the wait reported ready while
the dialog had focus.

A bare-`❯` check cannot replace it: an idle 2.1.293 composer, captured in a throwaway tmux
session on 2026-11-02, renders its prompt row as `❯` + U+00A0 + placeholder text
(`❯ Try "edit index.ts to..."`), between two `─` rules. So the fix detects the dialog by its
title, which is a fixed string in the binary.

### 3. Why the paste guard did not stop the blind Enter (recorded, not fixed here)

The nudge renders its options with `hideIndexes:!0` (no `1.` / `2.` prefixes). The paste guard
`paneHasBlockingChoiceMenu()` (`src/lib/pane-choice-menu.ts`, line 270) only recognizes
**numbered** menus, so `sendKeys` in `src/lib/tmux.ts` (line 1125) logged
"Sending Enter anyway". The dialog's default focus is "Yes, set auto mode as my default", so that
Enter may have switched the VM's user settings to `defaultMode: "auto"`. The machine was destroyed
after the run, so nothing remains to repair. Extending the menu parser to unnumbered selects is a
separate change to a deliberately conservative module; it is a NonGoal here, filed as
[#4792](https://github.com/eltmon/overdeck/issues/4792).

## Requirements

- **FR-1** — `FlyProvider.configureClaudeCode` writes `hasSeenAutoDefaultNudge: true` into the
  VM's `~/.claude.json`, in the same Python patch that sets `hasCompletedOnboarding`. Existing keys
  in the file are kept.
- **FR-2** — `waitForClaudeReady` does not report ready while the visible pane contains the title
  `Make auto mode your default permission mode?`, even when a `❯` is also visible.
- **FR-3** — When the 30 s readiness deadline passes, the harness is still alive, and the last
  non-empty capture still shows that title, `waitForClaudeReady` throws an `Error` whose message
  names the dialog title and tells the operator to answer it in the conversation's terminal and
  send the message again. `startConversationRuntime` then records it as the spawn error and
  delivers nothing (its existing `catch`; Claude Code's `stopRuntimeOnStartFailure` is `false`, so
  the session stays open for the operator to answer).
- **FR-4** — When the dialog disappears before the deadline and the composer `❯` is visible,
  `waitForClaudeReady` resolves as it does today.
- **FR-5** — The docs describe the pre-answered dialog and the readiness behavior (WI-3).
- **NFR-1** — `src/lib/remote/fly-provider.ts` keeps no `bypassPermissions` string literal; the
  no-leak test `src/lib/__tests__/remote-settings-no-leak.test.ts` stays green.
- **NFR-2** — Readiness tests use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`, never
  real 30 s waits.
- **NFR-3** — No new test reads a `.ts` source file (`npm run lint:source-introspection`).
- **NFR-4** — Server-reachable code stays async: no `execSync`, no new `*Sync` tmux helper.

## Decisions

- **D-1: Fix both the cause and the guard.** The pre-answer (WI-1) removes the dialog on Fly VMs
  with a key verified in both shipped versions; it is the fix. The readiness guard (WI-2) covers
  the case where the dialog is on screen during the readiness window (a different host, a Claude
  Code that renames the key): that start becomes a visible spawn error instead of a silently lost
  message. It does **not** cover a dialog that mounts after the composer's `❯` first appears. Claude
  Code requests the nudge with `place:"under"` after waiting for the session to go idle
  (`await tGt(L.activity,L.signal)`), so it can appear a moment after readiness has already
  returned, and then the paste races it. That paste-time case belongs to the paste guard
  ([#4792](https://github.com/eltmon/overdeck/issues/4792)). The two items touch different files.
- **D-2: Fly VMs only; local `preTrustDirectory` is not changed.** Locally Overdeck never writes
  `defaultMode` into the operator's own user settings (the host has none), so condition 4 does not
  hold. Writing a "seen" flag into an operator's own config would suppress an offer they may want.
  The Fly VM's config is Overdeck-managed, like the bypass disclaimer it already pre-answers.
- **D-3: Detect the dialog by its exact title.** The title string is fixed in the binary
  (`ra` component `title:"Make auto mode your default permission mode?"`). Structural detection of
  the composer is unreliable (see Root cause 2). The title list holds one entry; adding other
  Claude Code nudges is a NonGoal.
- **D-4: Keep polling while the dialog shows; fail only at the deadline.** An operator watching
  the terminal can answer the dialog within the 30 s window, and then the first message still lands
  (FR-4). The harness-exit checks keep precedence: an exited harness is reported as today.
- **D-5: Test the VM payload, not the source.** The WI-1 test captures the command
  `configureClaudeCode` sends, base64-decodes the Python script, and asserts on it. It does not run
  Python (CI has Windows matrix jobs) and does not read `fly-provider.ts` (NFR-3).

### WI-2 — Readiness refuses the auto-default nudge (FR-2, FR-3, FR-4, NFR-2, NFR-4)

**File:** `src/lib/overdeck/claude-readiness.ts`.

Add, below `SESSION_ENDED_PREFIX`:

```ts
/**
 * Claude Code startup dialogs that take focus before the composer can (PAN-4738).
 * Their option rows start with the same ❯ the composer prompt does, so a ❯ alone
 * does not prove the composer is ready. Matched by exact title from the binary.

const BLOCKING_STARTUP_DIALOG_TITLES = ['Make auto mode your default permission mode?'] as const;

function blockingStartupDialogTitle(paneText: string): string | null {
  return BLOCKING_STARTUP_DIALOG_TITLES.find((title) => paneText.includes(title)) ?? null;
}
```
