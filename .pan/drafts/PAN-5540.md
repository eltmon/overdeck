# PAN-5540: Known skill packs (the video group) can't be discovered or added outside the CLI; agents don't know they exist

**Issue:** https://github.com/eltmon/overdeck/issues/5540
**Planned against:** `main` at `a1cfde59e98` (feature branch `feature/pan-5540`).
**Planning mode:** `pan plan --auto` (no operator questions; defaults recorded under "Decisions").

## Glossary

- **Pack** (skill pack): a third-party git repository of skills, registered under an id in `~/.overdeck/config.yaml` → `skills.packs.<id>` with `url`, `ref` and a trusted 40-hex `commit` (PAN-4334). Registering ("adding") a pack trusts that commit and turns nothing on.
- **Known pack**: an entry in `KNOWN_PACKS` (`src/lib/skill-packs/adapters.ts`, `export const KNOWN_PACKS` at line 115). It supplies a default `url`, and for some ids a default `ref`, adapter, disclosure, etc. Today's ids: `mattpocock`, `deft`, `sageox`, `gstack`, `pstack`, `atlassian`, `remotion`, `hyperframes`, `openmontage`, `video-use`.
- **Registered / added pack**: a known or custom pack that has a `skills.packs.<id>` entry (`listPacks()` in `src/lib/skill-packs/sources.ts`).
- **Not-added known pack**: a `KNOWN_PACKS` id with no registry entry.
- **Pack group**: a name for a list of pack ids (`src/lib/skill-packs/groups.ts`). Built-in: `video` = `remotion, hyperframes, openmontage, video-use` (`KNOWN_PACK_GROUPS`). `config.yaml` → `skills.pack_groups.<name>` adds groups or replaces a built-in by name (`listPackGroups()`). A group has no state of its own.
- **Missing member**: a pack id listed by a group that has no registry entry.
- **Preview**: the `PackPreview` that `addPack(input, confirm)` (`sources.ts`, `export async function addPack`) builds after fetching the repo and extracting the commit, before it writes anything. The CLI prints it and asks "Trust this commit?"; `--yes` trusts it.
- **Trust step**: calling `addPack`'s `confirm(preview)` callback. `true` writes the registry entry; `false` writes nothing (the clone and extraction stay on disk under `~/.overdeck/packs/<id>/`, exactly as a declined CLI add leaves them).
- **Dashboard-addable**: a known pack the dashboard may add with one click. Rule (decision D-1): it has a default `url` and a default `ref`, its adapter is not `gstack-runtime`, and adding it runs no build (`buildsOx(id)` is false, i.e. it is not `sageox`). Today that is `pstack`, `atlassian`, `remotion`, `hyperframes`, `openmontage`, `video-use`.
- **Cached**: `listPackCatalog()` (`src/lib/skill-overrides/catalog.ts`) reports `cached: true` when `~/.overdeck/packs/<id>/<commit>/` exists (and, for `gstack-runtime`, the render is ready). `addPack` creates that extraction, so a pack added through `addPack` is cached immediately.
- **Admin scope**: in `src/dashboard/server/route-scopes.ts`, the scope a remote credential needs per route. Unlisted routes need `admin`; root credentials (the local dashboard session) are `admin`.

## Problem

On a fresh machine the operator opened the Skills page and saw the video packs as absent, with no way to add them and no hint of the URLs. Verified on `a1cfde59e98`:

1. `SkillPacksSection.tsx` line 74: `const ADD_COMMAND = 'pan skills pack add mattpocock https://github.com/eltmon/skills --ref v1.2.3';`, shown at lines 158-159 when no pack is registered. No HTTP route registers a pack. Known packs and groups that are not added appear nowhere in the UI.
2. `ConversationSkillsField.tsx` (`fetchSkillGroups`) lists only registered packs (`body.packs` from `GET /api/skills/overrides`), so `video` is invisible until added.
3. `pan skills pack list` (`src/cli/commands/skills.ts`, `skillsPackListCommand`, lines 514-557) prints registered packs, then `Groups` with member ids (line 554-556), but never says which members are not added or how to add them. Its empty state (line 541) recommends only `mattpocock`.
4. No universal skill or rule tells an agent that known packs exist. The only installer guidance is the dev-scope `sync-sources/dev-skills/pan-skill-installer/SKILL.md`.
5. Docs: `docs/USAGE.md` line 426 and `configuration/skills.mdx` line 58 say only "pstack, sageox and atlassian" default the ref. `docs/SKILL-PACKS.md` line 162 says the git fetch is "CLI only" and lines 270-273 document `ADD_COMMAND`. `features/skill-packs.mdx` lines 165 and 183 say "only `pan skills pack add` can" register a pack.

PAN-4334 (`.pan/drafts/PAN-4334.md` line 229) deliberately left adding out of the dashboard ("Adding needs a consent flow that the CLI already provides"). This issue adds that consent flow to the dashboard, built on the same `addPack(input, confirm)` core.

## Requirements

### Functional

- **FR-1** A lib function lists every known pack with its default url, default ref, adapter, disclosure, whether it is added, whether it is dashboard-addable (and why not), its CLI add command, and the groups it belongs to; and lists every group (built-in and config) with its members, missing members, unknown members, dashboard-addability and CLI add command.
- **FR-2** `pan skills pack list` (text output) prints a "Known packs not added" section with each not-added known pack and the exact command that adds it, and for each group with missing members prints those members and `pan skills pack add --group <name>`. The empty-state line no longer recommends `mattpocock` alone. `--json` output is unchanged.
- **FR-3** `GET /api/skills/packs/available` returns the FR-1 listing.
- **FR-4** `POST /api/skills/packs/preview` with `{ id }` fetches and extracts a dashboard-addable known pack and returns its preview without registering it.
- **FR-5** `POST /api/skills/packs` with `{ id, commit }` registers a dashboard-addable known pack through `addPack`, only when the commit it resolves now equals the previewed `commit`.
- **FR-6** The request bodies of FR-4 and FR-5 accept only a known pack id (and the commit). They never accept a url, ref or adapter.
- **FR-7** The Skills page (global level) shows an "Available packs" list: each built-in or config group with missing members, and each not-added known pack, with its disclosure and either an **Add…** button (dashboard-addable) or the CLI command (not addable). The hard-coded `mattpocock` hint is removed.
- **FR-8** **Add…** opens one dialog that previews every pack being added (one preview request per pack, sequentially), shows each preview's source, commit, license, skills, opt-in skills, Not applied list, executables, MCP servers and disclosure, and adds them only after the operator presses **Trust and add**; one add request per pack, sequentially; a registered member is skipped and reported, a failed member is reported, the others continue.
- **FR-9** After an add, the Skills page shows the new packs as registered and cached (pack rows in Skill packs), and the Available list no longer shows them.
- **FR-10** The new-conversation skills field (also rendered by `AddSkillsModal`) shows each group with missing members as a row such as `video · 4 packs not added` with an **Add…** button that opens the same dialog in place; after an add the field's skill list refetches and shows the new pack groups.
- **FR-11** A shipped, universal bundled skill `sync-sources/skills/pan-skills/SKILL.md` tells agents which known packs and groups exist and how to add, enable and load them, so an agent asked for a missing video skill offers the install.
- **FR-12** Docs and changelog describe the video packs, groups, the new `pan skills pack list` output and the dashboard add flow.

### Non-functional

- **NFR-1** No `execSync` in code reachable from the dashboard server; git work stays in `sources.ts`'s async `execFile` helper (`git()`).
- **NFR-2** One registration path: the dashboard and the CLI both register through `addPack` in `sources.ts`. Url/ref defaulting for known packs lives in one lib function both call.
- **NFR-3** `src/lib/skill-packs/` never imports `src/lib/skill-overrides/` (existing convention, see the header comments of `adapters.ts`, `sources.ts`, `mount.ts`). Callers pass `CORE_SKILLS` (from `src/lib/skill-overrides/resolve.ts`) in as `reservedIds`.
- **NFR-4** The new routes require `admin` scope for remote credentials. They get it by **not** being listed in `ROUTE_SCOPES` (unlisted ⇒ `admin`, fail-closed); the route test asserts `requiredScopeFor(...) === 'admin'` for each.
- **NFR-5** In one server process, two git operations for the same pack id never run at the same time: a second preview while a preview runs shares that preview's result; any overlap that involves an add (add during preview, preview during add, add during add) answers HTTP 409 `busy`.
- **NFR-6** No file grows past 1000 lines (`scripts/lint-file-size.sh` ceiling). `src/cli/commands/skills.ts` is 791 lines today; keep it under 1000.
- **NFR-7** Frontend follows the dashboard style guide (`/pan-style-guide`): no pill badges, no decorative color, existing `Modal` (`components/shared/Modal.tsx`), `dashboardMutationJsonHeaders` for mutating requests.

## Decisions

- **D-1 Which packs the dashboard can add.** Only dashboard-addable packs (glossary). `mattpocock`, `deft` and `gstack` have no default ref (the operator must choose one); `gstack` runs `bash setup` and `sageox` runs `go build` when added, which can take minutes and download toolchains. Those rows show their CLI command instead of **Add…**. Reason codes: `needs-ref` (no default ref), `runs-build` (gstack-runtime adapter or `buildsOx(id)`). `needs-ref` wins when both apply. **This narrows the issue's acceptance sentence** "lists … each known pack with an Add action": all ten known packs are listed, six get **Add…**, four (`mattpocock`, `deft`, `gstack`, `sageox`) get their exact CLI command. The `video` group, which the acceptance sentence is about, is fully dashboard-addable.
- **D-2 Two-step trust over HTTP.** Preview and add are separate requests. Add re-runs `addPack` with `confirm = preview => preview.commit === body.commit`. If the ref now resolves to a different commit, nothing is written and the route answers 409 `commit-changed`; the dialog then shows "The pack changed since the preview. Preview again." and re-previews that pack. There is no server-side preview token or session.
- **D-3 Preview side effects.** A preview clones/fetches into `~/.overdeck/packs/<id>/repo` and extracts `~/.overdeck/packs/<id>/<commit>/`, then writes no registry entry. This matches a declined CLI add; a later add reuses the clone. No cleanup is added.
- **D-4 License.** `KnownPack` gets no license field. The listing shows no license; the preview shows `manifest.license` (or `unknown`).
- **D-5 Group add shape.** One dialog for the whole group: previews for every missing member first, one **Trust and add** button, then one add request per member. Already-registered members are skipped before preview (the listing knows them) and, if registered meanwhile, reported as "already added" on the 409 `exists` answer. A failed preview or add marks that member failed and the others continue (the CLI's `addGroupPacks` semantics).
- **D-6 Config groups.** Groups come from `listPackGroups()` so a config group that replaces `video` is what the UI and CLI show. A missing member that is not in `KNOWN_PACKS` is an **unknown member**: the group is not dashboard-addable and the UI shows `<id> is not a known pack; add it with pan skills pack add <id> <url> --ref <ref>`.
- **D-7 Where the Available list renders.** At the `global` level of the skill overrides panel only (the `/skills` page), because the registry is global. At `project` and `issue` levels, when no pack is registered, the empty state reads "No skill packs added. Add packs on the Skills page." with "Skills page" navigating to `/skills` via `window.history.pushState({}, '', '/skills'); window.dispatchEvent(new PopStateEvent('popstate'))` (the pattern in `src/dashboard/frontend/src/lib/navigateToDecision.ts`).
- **D-8 New-conversation field.** The **Add…** button opens `AddPacksDialog` nested over the new-conversation (or Add skills) dialog; `Modal` supports nesting (`modalLayerSeq` in `Modal.tsx`). Navigating to `/skills` would drop the open dialog's state. After an add, invalidate the query keys `['new-conversation-skills']` (prefix), `['skill-overrides']` and `['skill-packs-available']`. Only groups are shown in this field (the issue asks for groups); single not-added packs stay on the Skills page.
- **D-9 Agent guidance is a skill, not a rule.** A universal rule costs context in every session; a skill costs only its description line. The skill is the `pan skills` CLI-wrapper `sync-sources/skills/pan-skills/SKILL.md` (no wrapper exists today; `docs/SKILLS-CONVENTION.md` requires `pan-<verb>` naming and a description starting with the command, and `scripts/lint-skills.sh` validates every `pan skills …` command in it against `--help`). Its description carries the trigger words (missing skill, Remotion, HyperFrames, OpenMontage, video-use, video group).
- **D-10 `--json` unchanged.** `pan skills pack list --json` keeps its row shape (PAN-5464 D-2 kept groups text-only); the new known-pack section is text-only too.
- **D-11 Lock scope.** The per-id lock is in-process (module-level state in `known.ts`). A preview requested while a preview of the same id is running awaits and returns the same in-flight promise (so a dialog reopened mid-preview, or React StrictMode's double mount effect in dev — `main.tsx` renders `<React.StrictMode>` — never gets an error). An add while anything for that id is running, or a preview while an add is running, rejects with `busy`. A CLI add racing a dashboard add for the same id is not prevented (the CLI has the same race with itself today); this is a NonGoal.
- **D-14 Preview parity with the CLI.** The dialog shows the same rows `printPackPreview` (`src/cli/commands/skills.ts`, line ~292) prints for a non-runtime pack: Source (`url @ ref (short commit)`), Root (when `pluginRoot`), Adapter, License, Skills (count and opt-in names), Not mounted (`manifest.excluded`), Executables (first 3 then `…`), MCP servers (`name (url)`), Not applied (`notAppliedLabels(manifest.capabilities)`, exactly as the CLI computes it), plus the known pack's disclosure. `runtime`, `diff` and `oxBuild` rows never occur because such packs are not dashboard-addable.
- **D-12 Route file and scope.** New routes live in `src/dashboard/server/routes/misc/skill-packs.ts`, merged into `miscRouteLayer` in `src/dashboard/server/routes/misc.ts`. Each gets a `tests/unit/lib/overdeck/no-loss-matrix.ts` row (the inventory; the enumerator only scans top-level `routes/*.ts`, so add them by hand). They get **no** `ROUTE_SCOPES` row: unlisted routes need `admin`, which is the scope wanted, and `src/dashboard/server/__tests__/route-scopes.test.ts` ("lists every scoped path as a telemetry client route", PAN-5100) requires every listed path to also be in `TELEMETRY_CLIENT_ROUTES` (`packages/contracts/src/telemetry.ts`) and `docs/TELEMETRY.md`, which is for phone/remote routes. This narrows the issue's "needs a `route-scopes.ts` entry": the intent (correct scope) is met by the fail-closed default and pinned by the route test's `requiredScopeFor` assertions.
- **D-13 Request time.** A preview of a large repo can take tens of seconds; one request per pack keeps each well under Node's default 300 s `requestTimeout`. The dialog shows a per-pack "Fetching…" state; there is no client timeout.

  packs: string[];

  missing: string[];           // members with no registry entry, in group order

export function formatAvailablePackLines(listing: AvailablePackListing): string[];

export async function fetchAvailablePacks(): Promise<AvailablePackListing> {
  const res = await fetch('/api/skills/packs/available');

export type KnownPackErrorCode = 'bad-request' | 'unknown-pack' | 'not-addable' | 'busy' | 'commit-changed';
export class KnownPackError extends Error {
  constructor(readonly code: KnownPackErrorCode, message: string) { super(message); this.name = 'KnownPackError'; }
}

/** NFR-2: the url and ref a pack add uses; explicit values win over the known-pack defaults. Messages are the CLI's existing ones. */
export function knownPackSource(id: string, explicit: { url?: string; ref?: string } = {}): { url: string; ref: string } {
  const known = KNOWN_PACKS[id];
  const url = explicit.url ?? known?.url;
  const ref = explicit.ref ?? known?.ref;
  if (!url) throw new KnownPackError('bad-request', `pack ${id} has no default url; pass one: pan skills pack add ${id} <url> --ref <ref>`);
  if (!ref) throw new KnownPackError('bad-request', `pack ${id} has no default ref; pass --ref <tag-or-branch>`);
  return { url, ref };
}

// D-11: one operation per pack id in this process. A second preview shares the running preview.
const inFlight = new Map<string, { kind: 'preview' | 'add'; promise: Promise<PackPreview> }>();
function runExclusive(id: string, kind: 'preview' | 'add', run: () => Promise<PackPreview>): Promise<PackPreview> {
  const current = inFlight.get(id);
  if (current?.kind === 'preview' && kind === 'preview') return current.promise;
  if (current) throw new KnownPackError('busy', `pack ${id} is already being fetched or added; try again when it finishes`);
  const promise = run().finally(() => inFlight.delete(id));
  inFlight.set(id, { kind, promise });
  return promise;
}

function requireDashboardAddable(id: string): { url: string; ref: string } {
  if (!PACK_ID_PATTERN.test(id) || !KNOWN_PACKS[id]) throw new KnownPackError('unknown-pack', `unknown pack: ${id}`);
  const reason = notAddableReason(id);
  if (reason) throw new KnownPackError('not-addable', `pack ${id} cannot be added from the dashboard (${reason}); run ${packAddCommand(id)}`);
  return knownPackSource(id);
}

/** FR-4: fetch and extract; never writes the registry. Throws PackSourceError('exists') when registered. */
export async function previewKnownPack(id: string, reservedIds: readonly string[]): Promise<PackPreview> {
  const { url, ref } = requireDashboardAddable(id);
  return runExclusive(id, 'preview', async () => (await addPack({ id, url, ref, reservedIds }, async () => false)).preview);
}

/** FR-5 / D-2: registers only when the resolved commit equals the previewed one. */
export async function addKnownPack(id: string, expectedCommit: string, reservedIds: readonly string[]): Promise<PackPreview> {
  const { url, ref } = requireDashboardAddable(id);
  return runExclusive(id, 'add', async () => {
    const result = await addPack({ id, url, ref, reservedIds }, async preview => preview.commit === expectedCommit);
    if (!result.written) {
      throw new KnownPackError('commit-changed', `pack ${id} now resolves ${ref} to ${result.preview.commit.slice(0, 7)}, not the previewed ${expectedCommit.slice(0, 7)}; preview again`);
    }
    return result.preview;
  });
}

export interface PackPreviewDto {
  id: string; url: string; ref: string; commit: string; adapter: PackAdapterId; pluginRoot: string | null;
  license: string | null;
  skills: Array<{ name: string; description: string; optIn: boolean }>;
  excluded: Array<{ name: string; reason: string }>;
  notApplied: string[];
  executables: string[];
  mcpServers: Array<{ name: string; url: string }>;
  disclosure: string | null;
}
export function serializePackPreview(preview: PackPreview): PackPreviewDto; // fields from preview + preview.manifest; notApplied = notAppliedLabels(manifest.capabilities); disclosure = KNOWN_PACKS[id]?.disclosure ?? null
