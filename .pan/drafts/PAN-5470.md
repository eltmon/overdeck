## Glossary

- **Flywheel**: the `/pan-flywheel` loop skill running inside one operator conversation named
  `conv-flywheel`. It is not a daemon and keeps no run record.
- **Tick**: one turn of the loop: orient, drain in-flight work, pick, launch, watch, park. Each tick ends
  with one **tick marker** line that the page and `pan flywheel status` parse.
- **In flight**: issues the loop is moving now: the project's `workspaces/feature-*` directories plus the
  ids named in the newest tick marker, minus merged or closed issues.
- **Order book**: an operator-curated campaign of issues in Lane A (parallel) and Lane B (serial). Owned
  by `configuration/order-books.mdx`; this page only links it.
- **Backlog sequence**: the ranked list of open issues in `.pan/backlog/sequence.md`, written by the
  **sequencer** role (a `sequencer-runner` agent) and shown on the `/backlog` page (title
  `Backlog Sequencer`).
- **Pickup gate**: the per-issue operator override stored in the sequence: Auto, Promote or Vetoed.
- **Released**: the operator's "go" for a planned issue (`released` label), set with the **Release**
  button. Operator-only.
- **Parked (Flywheel sense)**: an issue held for a human decision, by the `parked` tracker label or a
  listing in `<planHome>/.pan/parked.md`. Its derived state in `pan show` is `parked`.
- **Parked orbit (`pan parked` sense)**: a stall the parked resolver finds: `operator-gate`,
  `zombie-session` or `idle-running`. A different thing from the Flywheel sense; the page must keep
  them apart.
- **Needs you**: the one list of things a person must act on. Flywheel items come from the tick marker's
  `needs-you=` field.
- **Plan home**: the repo that holds `.pan/` planning files; for a single-repo project, the project repo.
- **Mint check**: `npx -y mint@4.3.49 validate` and `npx -y mint@4.3.49 broken-links`, run from the
  workspace root. Always pin `mint@4.3.49`. Never run `mint validate --fix`: it rewrites about 80 files
  that sibling docs issues edit in parallel. Baseline on 2026-11-18: validate passes with 54 warnings
  (mostly `duplicate-h1`), broken-links reports none.
- **Dash rule**: no em dash (U+2014) and no en dash (U+2013) anywhere this issue writes, including the
  frontmatter `title`, `sidebarTitle` and `description`, and every body line added or edited. Code
  strings that contain an em dash (several UI tooltips do) must be paraphrased, not quoted.
- **MDX rule**: a bare `<word>` in prose is parsed as a JSX tag and breaks the build. Put every
  placeholder such as `<id>`, `<book-id>`, `<file>` and every `<https://...>` example inside backticks.

## Background: verified facts

### What the loop is and does

- `sync-sources/skills/pan-flywheel/SKILL.md` (the skill, synced to every harness) is the loop's whole
  prompt. Anchor `The Flywheel is a loop, not a daemon.` It runs in conversation `conv-flywheel`
  (`src/lib/flywheel/constants.ts` anchor `FLYWHEEL_CONVERSATION_SESSION = 'conv-flywheel'`).
- Phases, in order (skill headings): `## Phase 1 — Orient` (reads policies from
  `pan flywheel status --json` `.policies`, reads `.pan/flywheel/state.md`, reads
  `.pan/backlog/sequence.md`, reads the bound order book with `pan orders show`, lists in-flight work),
  `## Phase 1b — Drain what is already in flight` (walks every in-flight issue before picking anything
  new; table of stalls and first moves), `## Phase 2 — Pick the next item`, `## Phase 3 — Launch`
  (`pan start <issue-id>`), `## Phase 4 — Watch to landing`, `## Phase 5 — Park what you cannot decide`.
  (The headings contain em dashes; the page must not quote them.)
- Launch: the loop starts work only with `pan start` (skill anchor `pan start <issue-id>`), which plans
  the issue first if it has no plan. Link `/features/issue-pipeline` for the stages after that.
- Disk guard: if `pan start` fails with "Disk low", the loop launches nothing more that tick and raises
  a Needs-you item (skill anchor `Disk low`).
- Cadence (skill `## Cadence`): the loop schedules its own next tick with a background `sleep`: 450
  seconds while anything is in flight, 1000 seconds when idle, never longer than 1000 seconds. Nothing
  outside the conversation wakes it.
- Stop on its own: only when nothing is pickable and nothing is in flight; it then reports
  `phase=idle` with a Needs-you item saying the pipeline is idle (skill anchor
  `nothing pickable`).
- Rails the page should state (skill `## Doctrine and rails` and `## Guardrails`):
  - It orchestrates and never writes code, specs or plans; the only files it writes are
    `.pan/flywheel/state.md` and `.pan/flywheel/report.md`.
  - It never runs more work agents than `roles.flywheel.maxAgents` (default 30,
    `src/lib/config-yaml/roles.ts` anchor `maxAgents: 30,`). This cap is enforced by the loop's
    instructions, not by code; say "the loop keeps to", not "Overdeck enforces".
  - It never merges or deep-wipes from the loop (skill anchor `Do not auto-merge or deep-wipe`); merges
    follow the merge policy (link `/configuration/auto-merge`).
  - It never adds or removes the operator-only labels `released`, `vetoed`, `auto-merge`,
    `hold-for-uat`; its `gh` refuses those writes (skill anchor `grant-label writes`).
  - `vetoed` is absolute: never picked up, planned or struck.
  - It does not auto-start changes to pipeline machinery (TENET-10); it marks them `needs-handoff`.
  - Only one Flywheel per Overdeck install: every surface names the single conversation `conv-flywheel`
    (`constants.ts` comment `A second one would be a second orchestrator`), and `start` refuses while
    one runs. Write "one per install", not "per repo".
  - After a merge to Overdeck's own `main` with green CI it runs `pan reload`; it does not deploy other
    projects (skill anchor `Only for an Overdeck merge`). One sentence at most.
- **Author gate (early limitation, see D-3):** the skill's rail reads
  "`author.login ∈ {eltmon, panopticon-agent[bot]}` or `eltmon ∈ assignees`" (SKILL.md anchor
  `Author/assignee gate`). The login is the Overdeck maintainer's, hardcoded; nothing templates it at
  `pan sync`. The bot login is stale too: the GitHub App now posts as `<app-slug>[bot]`, for example
  `overdeck-agent[bot]` (`src/lib/github-app.ts` header), not `panopticon-agent[bot]`. Filed as
  **#5544** (with a comment on the bot login).
- Provenance: agents the loop starts carry `startedBy: flywheel:conv-flywheel` (`docs/FLYWHEEL.md`
  first paragraphs; code `resolveCliStartedBy`). Optional for the page; skip unless it fits naturally.
- Nothing is stored: the page and `pan flywheel status` derive everything on read from the
  conversation's transcript, the pipeline journals, the tracker and `.pan/flywheel/`
  (`src/lib/flywheel/derive-status.ts` `deriveFlywheelStatus`, `FE/pages/FlywheelPage.tsx` header
  comment anchor `Nothing on this page reads a stored run record`).
- Tick marker (skill `## Tick marker`; `src/lib/flywheel/tick-marker.ts`): one line ending every tick,
  for example `flywheel-tick: tick=3 pick=PAN-3964 phase=watch in-flight=PAN-3964,PAN-3920 needs-you=none`.
  Keys `tick`, `pick`, `phase` (`orient`, `pick`, `launch`, `watch`, `park`, `idle`, `stopping`),
  `in-flight`, `needs-you` (always last; items separated by `; `; an item may end with a URL in angle
  brackets). It is the loop's only status report.

### Start and control the loop

`pan flywheel --help` (verified 0.89.1): subcommands `start`, `stop`, `abort`, `pause`, `resume`,
`report`, `status`, `stats`.

| Command | Help text (verified) | Flags |
| --- | --- | --- |
| `pan flywheel start` | Launch a conversation running /pan-flywheel | `--model`, `--harness`, `--cwd <path>` (default cwd), `--orders <book-id>`, `--fresh` |
| `pan flywheel stop` | Ask the loop to write its report, wait for it, then pause | `--timeout <ms>` (default 120000) |
| `pan flywheel abort` | Stop the flywheel conversation without a report | none |
| `pan flywheel pause` | Stop the flywheel session, keeping its conversation and transcript | none |
| `pan flywheel resume` | Respawn a paused flywheel and re-send /pan-flywheel | none |
| `pan flywheel report` | Ask a running loop for its report, or print .pan/flywheel/report.md | none |
| `pan flywheel status` | Show the derived flywheel status: run, last tick, policies, in-flight issues, order book | `--json` |
| `pan flywheel stats` | Substrate-bug discovery rate and P0 count, computed from the tracker and forge | `--json`, `--window <days>` (default 30) |

Behavior (`src/lib/flywheel/actions.ts` `startFlywheel` and siblings; `docs/FLYWHEEL.md` "Verb → route →
view", verify against `actions.ts`):

- `start` creates `conv-flywheel` and sends `/pan-flywheel` (with the book id when `--orders` is given).
  It refuses when a flywheel is already running, and refuses a paused one unless `--fresh`. The CLI
  prints the reason and exits 1.
- `--fresh` replaces a paused flywheel conversation (or a leftover session with no conversation row);
  the old transcript stays on disk (FE `FlywheelConversationPane.tsx` anchor
  `The old transcript stays on disk`).
- `stop` sends a report request, waits until the loop prints a `phase=stopping` tick or the timeout
  passes, then pauses either way.
- `pause` stops the session and keeps the conversation and transcript; `resume` respawns it and sends
  `/pan-flywheel` again (safe: Orient re-reads everything); `abort` pauses without a report.
- `report` asks a running loop to write `.pan/flywheel/report.md`; when not running it prints the saved
  report, or "No report yet."
- `pan orders start <book-id>` opens the same `conv-flywheel` bound to a book. The difference between it
  and `pan flywheel start --orders` is already documented in `configuration/order-books.mdx` section
  `## Use the CLI`; link it, do not repeat it.
- Model and effort: `roles.flywheel.model` defaults to `claude-opus-5-5` and `roles.flywheel.effort` to
  `high` (`src/lib/config-yaml/roles.ts` anchor `flywheel: {`). Settings card fields, FE
  `components/Settings/RolesPanel.tsx`: `Flywheel effort`, `Flywheel max agents`, `Flywheel scope`.
  `roles.flywheel.scope` has no consumer outside config and Settings; **do not describe what scope
  does.** A resumed flywheel keeps the effort it started with (`configuration/effort.mdx` already says
  so; link `/configuration/effort`).
- Sample `pan flywheel status` text output (live, 2026-11-18): header line

### What the loop picks up

- Rule (`src/lib/backlog/pickup.ts` `isAutoPickable`, anchor
  `const released = s.released || autoPickupBacklog || activeBookMember;`): an issue is pickable when it
  is ready (`ready` label), planned (has an xBRIEF with tasks), released (`released` label, or
  Auto-pickup on, or a member of the active order book), and not parked, not vetoed, not under an
  `objection`, not already in the pipeline, and not an epic.
- Who checks the rule (verified):
  - The loop applies it before it runs `pan start` (skill `## Pickup gate`). `pan start` itself does not
    check it: `src/cli/commands/start.ts` has no `released`, `vetoed` or pickup check
    (`git grep -n -i "released\|vetoed\|pickup" -- src/cli/commands/start.ts` prints nothing).
  - Overdeck's automatic work dispatch, which starts work agents outside the loop (for example from the
    reactive lifecycle), checks the same ready, planned and release conditions in code
    (`src/lib/cloister/autonomous-work-dispatch.ts` `decideAutonomousWorkDispatch`, called from
    `service-reactive.ts`). One sentence at most; do not explain the dispatcher further.
  - The Forecast view on `/backlog` computes the same rule (`isAutoPickable`). Say "the Forecast shows
    the same rule".
- Order: a bound or running order book's items come first (skill Phase 1 step 3); otherwise the loop
  walks `.pan/backlog/sequence.md` in rank order. In the Forecast, a **Promote** gate jumps ahead of rank
  (`pickup.ts` `pickOrder`).
- Drain first: every tick walks in-flight issues before picking new ones (skill Phase 1b). Its stall
  table includes: planned but never started, agent dead or idle, PR conflicts with `main`, review never
  reports, checks red, merged but not closed out (it runs `pan close`, never on an `epic` issue), merged
  but not deployed (Overdeck only). Summarize in two or three sentences; do not reproduce the table.
- `objection`: the planning AI's written "held for review" in place of a plan (`pickup.ts` header
  anchor `objection  — AI raised`). The pickup controls offer **Override → Plan anyway** and
  **Accept & park** (`FE/components/backlog/PickupGateControls.tsx`).

| Switch | Default (code) | What it does (code wins) |
| --- | --- | --- |
| Auto-pickup | off (`=== 'true'; // defaults to false if unset`) | Off: the loop picks up only released issues and active order-book items. On: every ready, planned issue is pickable without a release (blanket release). |

### Parked issues (two meanings)

- **The loop parks** an issue it cannot decide (ambiguous scope, a design tradeoff, anything
  destructive or outside the issue's acceptance criteria) by writing it to `.pan/parked.md` with a
  one-line reason, then moves on (skill `## Phase 5`). It skips any issue with the `parked` label or a
  `.pan/parked.md` listing. You can park an issue yourself with the **Park** toggle in the pickup
  controls (sets the `parked` label; FE `PickupGateControls.tsx` anchor `label="Park"`). Such an issue
  derives state `parked` in `pan show` (`src/lib/overdeck/derived-issue-state.ts` anchor
  `` `<planHome>/.pan/parked.md` is the operator's parked list``). To unpark: remove the label, or
  delete the issue's line from `.pan/parked.md`.
- **`pan parked`** (`src/cli/commands/parked.ts`, `src/lib/parked/resolver.ts` `classifyParked`) lists
  a different set: issues stalled in one of three orbits, oldest first, each with why and the release
  condition:
  - `operator-gate`: an agent you paused (`pan unpause <id>`), one marked troubled after repeated crash
    or resume failures (`pan untroubled <id>`), one you stopped (`pan start <id>`), or an open `pan ask`
    decision (answer it in Needs you).
  - `zombie-session`: a live agent on an issue that is already closed.
  - `idle-running`: a live agent idle for 6 hours or more with no pipeline stage owning the next move
    (`IDLE_RUNNING_THRESHOLD_MS = 6 * 60 * 60_000`).
  - With nothing parked it prints `Nothing parked`, then explains that every in-flight issue has an
    autonomous next move (the text uses an em dash; paraphrase). `--json` prints the raw rows.
  - `pan parked` does not list `parked`-label or `.pan/parked.md` issues. Say so plainly.

  - **Re-rank all**: review pass; re-ranks the whole open backlog; slower and costlier.
  - **Clear**: deletes `sequence.md` and its cache; a creation pass then rebuilds it.
  - A banner `Sequencing pass running` shows `ranked N / M issues` while a pass runs. Only one pass runs
    at a time; a second request gets "A sequencer pass is still running..." (409,
    `routes/backlog.ts` anchor `sequencer_already_running`).
  - Automatic: when the backlog changes, the dashboard starts an incremental pass, at most once per 30
    minutes (`backlog-auto-trigger.ts` anchor `MIN_AUTO_PASS_INTERVAL_MS = 30 * 60_000`), and never on a
    `--no-resume` boot, during shutdown, or from a peer dashboard (`autonomousSpawnSuppressed`).
  - Each pass runs a `sequencer-runner` agent on `roles.sequencer.model` (default the expensive
    workhorse slot; `configuration/model-routing.mdx` already lists it; link `/configuration/model-routing`).
- Row actions: click a row to open the detail panel. Hover a row for **+ Order book**, which asks
  **Lane A** or **Lane B** and adds the issue to the running (else ready, else first) active book; a row
  already in a book shows **Open order book**.
- Pickup controls (FE `components/backlog/PickupGateControls.tsx`; the same controls appear in the
  Backlog detail panel, the issue cockpit and the issue drawer):
  - Planning stage: **Plan (Auto)** when unplanned; when planned, **Release ▶** (sets `released`) and
    **Re-plan**; when released, **Recall**. An objection shows **Override → Plan anyway** and
    **Accept & park**. (Labels contain arrows and symbols; render them as written in code or describe
    them; never write an em dash.)
  - Toggles: **Ready**, **Blocks main**, **Park**; `Planned` is shown as derived.
  - Planning select: **Skip**, **Auto**, **Interactive** (stored per issue in the sequence).
  - Gate select: **Auto**, **Promote** (jumps the queue ahead of rank), **Vetoed** (never auto-picked,
    planned or struck; also applies the `vetoed` label, `routes/backlog.ts` anchor
    `applyIssueVetoedLabel`).
- The file: `<planHome>/.pan/backlog/sequence.md` holds a human table, a rationale section for the top
  80 issues, and a machine-readable JSON block below the line
  `<!-- machine-readable; do not hand-edit below this line -->` (`sequence-io.ts` `MACHINE_MARKER`).
  It is committed on `main` of the plan home as `chore(workspace): backlog sequence` and pushed.
- `pan backlog write-sequence <file>` (help: "Validate a SequenceDoc JSON file, write it to
  .pan/backlog/sequence.md, and commit it"; `--project-root <path>`, default cwd): the sequencer agent
  writes its result through this command (`roles/sequencer.md` anchor
  `Do NOT write \`backlog/sequence.md\` directly`). It validates the JSON (`parseSequenceJson` in
  `src/lib/backlog/types.ts`; for example `why` is at most 140 characters, `score` 0 to 100), skips the
  rewrite when only the timestamp would change, commits `.pan/backlog`, and pushes. A validation error
  prints `Validation error: ...` and exits 1. Do not document the whole schema; name the fields
  (`issue`, `rank`, `size`, `importance`, `score`, `condition`, `dependsOn`, `why`, `gate`, `planning`)
  and link `/cli/pipeline-commands`.
- Order books: membership in the active book counts as a release; link `/configuration/order-books`.
