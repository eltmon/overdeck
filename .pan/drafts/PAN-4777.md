# PAN-4777 — Fly remote: `createRemoteWorkspace` leaks the VM when an exec throws; stale clone troubleshooting doc

**Issue:** [PAN-4777](https://github.com/eltmon/overdeck/issues/4777)
**Found while planning:** PAN-4685. The detached-clone fix (`cloneDetached`) shipped in #4713 (commit `74f4da1fb85`). The two leftovers below did not.

## Glossary

- **Fly machine / VM** — a Fly.io Machine created by `FlyProvider.createVm()` (`src/lib/remote/fly-provider.ts`). It bills while it runs. Overdeck calls it a "VM" and names it `<projectId>-<issue>-ws` (`vmName`).
- **`createRemoteWorkspace()`** — the shared creation routine in `src/lib/remote-workspace.ts`. Callers: `pan start --remote` (`src/cli/commands/start.ts`, two call sites), `pan workspace create --remote` (`src/cli/commands/workspace-create.ts`), `pan workspace migrate --to remote` (`src/cli/commands/workspace-migrate.ts`). None of the callers clean up the VM on failure; they only print the error.
- **Workspace metadata** — the YAML file `~/.overdeck/workspaces/<id>.yaml` written by `saveWorkspaceMetadata()` as the **last** creation step. It records `vmName`, `machineId`, `appName`. Until it exists, nothing in Overdeck points at the VM, so a VM left behind by a failed creation is invisible to Overdeck (a "leaked VM").
- **`resolveVm(vmName)`** — `FlyProvider.resolveVm` (`fly-provider.ts`, grep `async resolveVm(vmName: string)`). It looks for workspace metadata first. When none exists (always true during creation) it falls back to `this.getApi().listMachines(this.config.app)`. Any Fly API failure there (403 from an expired flyctl token as in #4748, a 5xx, a network error) rejects.
- **`sshImpl`** — `FlyProvider.sshImpl` (grep `private async sshImpl`). It converts only a `FlyApiError` thrown by `execCommand` into `{ exitCode: 1 }`. Its first line `await this.resolveVm(vm)` is outside that try, so a `resolveVm` failure rejects the `fly.ssh(...)` Effect, and `Effect.runPromise(fly.ssh(...))` throws.
- **Rollback** — deleting the VM with `fly.deleteVm(vmName)` after a creation step fails, then rethrowing.
- **Rollback failure** — `deleteVm` itself rejects. `deleteVm` also calls `resolveVm`, so under an expired token (#4748) it fails for the same reason the step failed. This is the realistic case, not an edge case.

## Problem

### 1. The VM leaks when a creation step throws

In `src/lib/remote-workspace.ts`, `createRemoteWorkspace()` creates the VM at step 1 (grep `const vmInfo = await Effect.runPromise(fly.createVm(vmName));`, line 139) and then runs these steps with no try/catch:

| Line(s) | Step | Can reject? |
|---|---|---|
| 146 | `await fly.syncAllCredentials(vmName)` | In practice no (both inner syncs catch and return `false`), but it is still after `createVm`. |
| 41–44 (in `cloneDetached`) | clone start exec: `fly.ssh(vmName, \`rm -f /tmp/pan-clone.exit && setsid nohup sh -c ...\`)` | Yes — not wrapped. |
| 60 (in `cloneDetached`) | failure-path `fly.ssh(vmName, 'tail -5 /tmp/pan-clone.log')` | Yes — not wrapped. |
| 161–163 | `git config user.email ... user.name ...` exec | Yes. |
| 170–175 | step 4, feature-branch checkout exec | Yes. |
| 182 | step 5, `fly.configureClaudeCode(vmName)` (calls `sshImpl` directly) | Yes. |
| 186–200 | step 6, `writeRemoteFile(...)` for `.pan/continue.json` | Yes (also throws on a non-zero exit). |
| 206 | step 6.5, `fly.copySkillsToVm(vmName)` | Yes. |
| 213, 223 | step 7, compose check and `docker compose up -d` execs | Yes. (The `exposePort` calls at 230–235 are already in a try.) |
| 256 | step 8, `saveWorkspaceMetadata(metadata)` | Yes (sync file write). |

Only two paths delete the VM today: the clone poll loop catches and retries (lines 51–57), and a non-zero clone exit code calls `fly.deleteVm(vmName)` at line 158 before throwing `Failed to clone: ...`. Any rejection from the table above escapes `createRemoteWorkspace()` with the VM still running and billing, and with no metadata pointing at it.

### 2. `docs/fly-provider.md` troubleshooting is stale

Under `### Exec / SSH commands fail` (line 440), the bullet at lines 450–453 reads:

```markdown
- **Fly API exec timeout** — individual exec calls default to 60 s. Long-running
  operations (e.g., `git clone` on a large repo) may time out. The clone step will
  delete the machine and surface the error; re-run after increasing `vm_memory` if the
  OOM killer is the cause.
```

Since #4713 the clone does not run inside one exec. It starts detached (`setsid nohup`), writes its log to `/tmp/pan-clone.log` and its exit code to `/tmp/pan-clone.exit`, and is polled every 5 s for up to 20 min (`CLONE_POLL_INTERVAL_MS`, `CLONE_DEADLINE_MS` in `remote-workspace.ts` lines 26–27). On a non-zero exit the VM is deleted and the error carries the last 5 log lines. On the deadline the error is `clone did not finish within 20 min`.

## Requirements

- **FR-1** — After `fly.createVm(vmName)` resolves, a rejection from any later step of `createRemoteWorkspace()` (every row of the table above, plus the clone-failure and clone-deadline throws) calls `fly.deleteVm(vmName)` exactly once and then rethrows the original error unchanged.
- **FR-2** — A non-zero clone exit still deletes the VM exactly once (no double delete from the old inline call plus the new rollback) and still throws `Failed to clone: <last 5 log lines>`.
- **FR-3** — When the rollback's `deleteVm` also rejects, `createRemoteWorkspace()` throws a new `Error` whose message contains: the original error message, `vmName`, `vmInfo.machineId`, `fly.getAppName()`, the delete error message, and the copy-pasteable command `fly machines destroy <machineId> -a <appName> --force`. The new error's `cause` is the original error.
- **FR-4** — A creation that fails never calls `saveWorkspaceMetadata` (unchanged from today, now asserted for the new failure paths).
- **FR-5** — `docs/fly-provider.md` describes the detached clone and the creation rollback accurately (see Work item 2 for the exact text).
- **NFR-1** — Tests use fake timers (`vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync`), never real 5 s waits. The existing test file already does this.
- **NFR-2** — No change to `FlyProvider` (`sshImpl`, `resolveVm`, `deleteVm` keep their signatures and behavior).

## Decisions

- **D-1 Rollback scope starts right after `createVm`.** The single try block begins on the line after `const vmInfo = ...createVm(...)` and ends after `saveWorkspaceMetadata(metadata)` / before `return metadata`. Everything in between is covered. This includes `syncAllCredentials` and the `git config` exec (lines 161–163), which the issue's step list does not name.
- **D-2 Use `fly.deleteVm(vmName)`, not a direct `destroyMachine(appName, machineId)`.** The issue names `deleteVm`; `deleteVm` also tears down the durable-tier volume (`<vmName>-workspace`), which a raw destroy would leave behind; and under an expired token a direct destroy would 403 just the same. FR-3's message gives the operator the manual fallback.
- **D-3 Remove the inline `deleteVm` at line 158.** The clone-failure branch now only throws; the shared catch deletes. This is how FR-2's "exactly once" holds.
- **D-4 Shape of the code.** Add a module-private helper in `remote-workspace.ts`:

  ```ts
  /**
   * Delete a VM whose creation failed, then return the error to throw
   * (PAN-4777). Before metadata is saved nothing points at the VM, so a VM
   * left running here bills with no record of it.
   */
  async function rollBackVm(
    fly: FlyProvider,
    vmName: string,
    machineId: string,
    error: unknown,
  ): Promise<unknown> {
    try {
      await Effect.runPromise(fly.deleteVm(vmName));
      return error;
    } catch (deleteError) {
      const reason = error instanceof Error ? error.message : String(error);
      const deleteReason = deleteError instanceof Error ? deleteError.message : String(deleteError);
      const appName = fly.getAppName();
      return new Error(
        `${reason}. The VM ${vmName} (machine ${machineId}, app ${appName}) could not be deleted: ${deleteReason}. ` +
          `Destroy it by hand: fly machines destroy ${machineId} -a ${appName} --force`,
        { cause: error },
      );
    }
  }
  ```

  and wrap the post-create steps:

  ```ts
  // before (line 139 onward)
  const vmInfo = await Effect.runPromise(fly.createVm(vmName));
  // Step 2 ...
  await fly.syncAllCredentials(vmName);
  ...
  const cloneResult = await cloneDetached(fly, vmName, httpsRepoUrl);
  if (cloneResult.exitCode !== 0) {
    await Effect.runPromise(fly.deleteVm(vmName));
    throw new Error(`Failed to clone: ${cloneResult.output}`);
  }
  ...
  saveWorkspaceMetadata(metadata);
  return metadata;

  // after
  const vmInfo = await Effect.runPromise(fly.createVm(vmName));
  try {
    // Step 2 ... (unchanged)
    await fly.syncAllCredentials(vmName);
    ...
    const cloneResult = await cloneDetached(fly, vmName, httpsRepoUrl);
    if (cloneResult.exitCode !== 0) {
      throw new Error(`Failed to clone: ${cloneResult.output}`);
    }
    ...
    saveWorkspaceMetadata(metadata);
    return metadata;
  } catch (error) {
    // Any failure once the VM exists deletes it (PAN-4777).
    throw await rollBackVm(fly, vmName, vmInfo.machineId, error);
  }
  ```

  Re-indent the wrapped block; do not otherwise edit the steps. Moving steps 2–8 into a separate `provisionRemoteWorkspace()` function is an acceptable equivalent if the executor prefers a smaller diff of indentation, but the try must cover exactly the same lines.
- **D-5 `cloneDetached` is unchanged.** Its start exec and log tail still throw on rejection; the outer catch handles them. Do not add local try/catch there.
- **D-6 `machineId` source.** Use `vmInfo.machineId` (from `createVm`), not a lookup. `vmInfo` is in scope in the catch because it is declared before the try.

## Non-goals

- No fix for expired flyctl tokens (#4748).
- No change to `FlyProvider.sshImpl` or `resolveVm` error handling. Swallowing `resolveVm` failures inside `sshImpl` would hide real errors from every other caller.
- No change to `FlyProvider.deleteVm`'s signature, and no machine-id-based delete path.
- No change to `FlyProvider.createVm`'s own failure paths (for example a machine that never reaches `started`). That failure happens before `createVm` resolves and is outside "once `createVm` succeeds".
- No change to `src/lib/anywhere/fly/provision.ts`. It already destroys its machine on a failed provision (`provisionFlyMachine`, grep `Could not destroy`) and is the precedent for this pattern.
- No change to the CLI callers in `start.ts`, `workspace-create.ts`, `workspace-migrate.ts`.
