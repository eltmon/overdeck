# PAN-3922 — Deacon-lite: relay run status from the deacon child to the dashboard; watchdog stale verdict

**Issue:** https://github.com/eltmon/overdeck/issues/3922
**Follow-up from:** PAN-3917 (The Overdeck Cut), integration notes + Codex review of the integrated diff.
**Planning mode:** `pan plan --auto` (no operator questions; defaults recorded in the xBRIEF `autoDecisions[]`).
**Verified against:** `feature/pan-3922` at `b7bedc3278a` (2026-09-19).

## Glossary

- **Deacon-lite** — the surviving patrol loop after the Cut: four observe-and-nudge routines in `src/lib/cloister/deacon-lite.ts`, run every 60 s by `tick()`.
- **Deacon child** — the separate Node process the dashboard forks to host Cloister and deacon-lite. Entry script `src/dashboard/server/deacon-main.ts`, built to `dist/dashboard/deacon.js`.
- **Deacon supervisor** — `src/dashboard/server/services/deacon-supervisor.ts`, the dashboard-process module that forks the child, restarts it, and talks to it over Node IPC (`child.send`).
- **IPC** — the Node `fork()` message channel between the dashboard process and the deacon child. Today it carries two parent→child messages, `{type:'patrol'}` and `{type:'reload-config'}`, and nothing child→parent.
- **Control surface** — `src/dashboard/server/services/cloister-control-surface.ts`, the dashboard-side composer behind `GET /api/deacon/status` and `GET /api/cloister/status`.
- **Deacon-lite status** — the `DeaconLiteStatus` shape `{ running, intervalMs, lastRunAt, lastRunError }` that the control surface, the dashboard widgets, the CLI, and the supervisor watchdog all read.
- **Supervisor watchdog** — `src/supervisor/watchdog.ts` (the `pan up` process supervisor's health loop, not the deacon supervisor). It polls `/api/health` and `/api/deacon/status` and restarts the dashboard on a stale patrol verdict.
- **Patrol report** — the new child→parent IPC message `{ type: 'patrol-done', at: string, error: string | null }` sent after every completed deacon-lite tick.
- **Stale verdict** — the watchdog's decision that the dashboard must restart because the last reported patrol is older than three patrol intervals.

## Problem

`GET /api/deacon/status` and `GET /api/cloister/status` call `getDeaconLiteStatus()` from the dashboard's own process memory (`cloister-control-surface.ts:35` and `:76`). But deacon-lite runs inside the deacon child: `service.ts:356` calls `startDeaconLite()` from `CloisterService.start()`, which `deacon-main.ts` runs in the forked process. The dashboard's copy of the module never starts a loop, so every consumer sees `running: false, lastRunAt: null, lastRunError: null`:

- `pan admin cloister status` prints `Status: Starting` forever (`src/cli/commands/cloister/status.ts:38` keys "Running" on `status.patrol.running`).
- The CommandDeck `DeaconStatus` widget shows no last-run age (`DeaconStatus.tsx:124`), and `DeaconActivityView` shows `Loop: Idle` (`DeaconActivityView.tsx:165`).
- The core-services row's `lastTickAgeSeconds` is always null (`routes/resources/core-services.ts:148`).
- The supervisor watchdog's stale verdict had to be neutralised in `c8a7c0f` because the timestamp was always missing; a genuinely wedged deacon is now invisible to it.

A second, smaller defect: the child's `patrol` IPC handler calls `runDeaconLite()` directly (`deacon-main.ts:95`), bypassing `tick()`, so a manual "Run patrol now" (`POST /api/deacon/patrol`) never updates `lastRunAt`/`lastRunError` even inside the child.

## Proposal

Keep deacon-lite's status in-memory and file-free, as the Cut decided (PAN-3917 W4). Add one child→parent IPC message: after every completed tick the child sends a **patrol report**; the deacon supervisor stores the latest report; the control surface composes `DeaconLiteStatus` from the supervisor (`running` = child process running, `intervalMs` = the exported constant, `lastRunAt`/`lastRunError` = the stored report). The watchdog's stale verdict reads only the relayed `deaconLite` fields. No new HTTP routes, no new files on disk, no frontend changes (the widgets already read the fields that will now be populated).

### Decision rules (made here, not by the executor)

- **D1 — Transport is the existing IPC channel**, not the deacon event client (`deacon-event-client.ts`). The event client is a batched, retried HTTP writer into the event store; a run-status ping needs neither durability nor sequence numbers, and IPC already carries `patrol`/`reload-config`.
- **D2 — The supervisor keeps the last report across child respawns.** It never resets the stored report when a child exits or a new one is forked. Reasoning: resetting would blind the watchdog to a child that respawns but never completes a patrol (the exact case the neutralised verdict cannot see). Keeping it means a respawned-but-wedged child produces a stale verdict after three intervals, which is the intended behaviour.
- **D3 — `running` in the dashboard's composed status means "the deacon child process is running"** (`isChildRunning()`), not "a report has arrived". A child that is up but has not yet completed its first tick shows `running: true, lastRunAt: null`, which the CLI already renders as `waiting for first run`.
- **D4 — The watchdog keeps the c8a7c0f "missing → no verdict" behaviour.** A null `lastRunAt` still yields no verdict; only a reported timestamp that is stale or unparsable restarts. The pre-cut "missing for N seconds" verdict is not restored.
- **D5 — The watchdog reads the relayed shape only.** `record.deaconLite.intervalMs` (fallback 60 000) and `record.deaconLite.lastRunAt`. The `record.config.patrolIntervalMs` and `record.state.lastPatrol` reads are fields of the deleted deacon; they are removed, and the test fixtures that still use them are migrated.
- **D6 — Manual patrols go through the tick.** `deacon-main.ts` calls the exported tick (`runDeaconLitePatrol`) for the `patrol` IPC message so a manual run stamps and relays status like an interval run.
- **D8 — `isRunning` and `deaconLite.running` may legitimately diverge.** `isRunning` (Cloister pid file) answers "is any Cloister alive"; `deaconLite.running` (`isChildRunning()`) answers "is this dashboard's deacon child alive and relaying". They differ when a foreign Cloister pid holds the single-deacon lock and the supervisor refuses to fork. Do not collapse them.
- **D7 — A tick stamps `lastRunAt` even while globally paused.** `runDeaconLite()` returns early when paused (`deacon-lite.ts:166`), but the tick still completes; a paused deacon is alive, and the watchdog must not restart it. This is the current behaviour, preserved.

## Requirements

### Functional

- **FR-1** After every completed deacon-lite tick in the child (interval or manual), the child sends the parent an IPC message `{ type: 'patrol-done', at: <ISO 8601>, error: <string | null> }`.
- **FR-2** The deacon supervisor stores the most recent valid patrol report and exposes it as `lastPatrolReport(): { at: string; error: string | null } | null`, on the `DeaconSupervisor` interface and as a default-singleton named export.
- **FR-3** `GET /api/deacon/status` returns `deaconLite.lastRunAt` and `deaconLite.lastRunError` equal to the stored report, `deaconLite.running` equal to `isChildRunning()`, and `deaconLite.intervalMs` equal to deacon-lite's interval constant.
- **FR-4** `GET /api/cloister/status` returns `patrol` composed the same way, and `lastCheck` derived from the relayed `lastRunAt`.
- **FR-5** `POST /api/deacon/patrol` (manual patrol) causes a new patrol report; the next `GET /api/deacon/status` shows an advanced `lastRunAt`.
- **FR-6** The supervisor watchdog's stale verdict reads `deaconLite.lastRunAt` and `deaconLite.intervalMs` from `/api/deacon/status`; a reported timestamp older than three intervals restarts the dashboard, a fresh one does not, and a null timestamp produces no verdict.

### Non-functional

- **NFR-1** No file on disk and no event-store row is written for run status (PAN-3917 W4 stays intact).
- **NFR-2** An unrecognised or malformed IPC message from the child is ignored; it never throws in the parent.
- **NFR-3** Existing injection seams keep their names (`CloisterControlDeps.readDeaconLiteStatus`, `DeaconSupervisorDeps`), so current tests keep compiling with only mock-list additions.
- **NFR-4** No frontend source changes; both widgets already read the populated fields.
