## Problem

After slice 4, a viewer can only watch. The parent PRD's *Input Model* promises two ways to take part: live **prompt suggestions** that every participant sees and the controller can pick, edit and send (FR-7), and a **direct-submit** grant that lets a contributor's prompts post straight to the conversation (FR-8). Several people submitting at once must not interleave mid-turn: the parent PRD decides a **strict FIFO queue on the host** that flushes at turn end, with an "agent is working / N queued" indicator (FR-14). Today:

- The `drafts` channel exists on every peer connection but carries nothing. `peer-hub.ts` line 281–282 subscribes to inbound messages on `control` only, and `webrtc-viewer.ts` line 230–231 attaches no listener to `drafts`.
- `onControlMessage` (`peer-hub.ts` lines 384–400) ignores every `control` payload except `hello`.
- The viewer's `readSharedMessage` (`webrtc-viewer.ts` lines 72–92) drops `author` on purpose, and `toChatMessage` (`SharedConversationView.tsx` lines 25–32) never copies it.
- Slice 2 already lets the controller grant and revoke the contributor flag, and the viewer server already tracks it (`share-join.ts` line 313 sets `join.contributor` from each `status admitted` frame, and `setState`, lines 445–454, emits a `state` event to the browser on every frame, so a contributor-only change reaches the page), but nothing uses it.

## Goal

A viewer types in a draft box under the shared conversation; every other participant sees the draft live in a suggestion list, and the host sees it in the share dialog, where they can pick it, edit it and send it. A contributor also gets a **Send** button that posts the prompt directly. Every send, from any source, goes through one host-side FIFO queue that delivers one prompt per agent turn. Viewers see "Agent is working · N queued". A prompt that came from a contributor or a picked suggestion shows its author on the viewers' timeline. Revoking the grant turns the contributor's composer back into a suggestion box at once.

## Requirements

Functional (FR-7, FR-8 and FR-14 here refine the parent PRD's requirements of the same number; the IDs below are this slice's own):

- **FR-1** The `drafts` channel carries draft snapshots both ways: viewer → host `DraftUpdate { text }`, host → viewer `DraftPayload { authorGithubId, authorLogin, text, updatedAt }`. The host sets the author fields from its own peer identity and snapshot, never from the inbound payload.
- **FR-2** The host keeps one draft per admitted viewer (LWW), relays each change to every **other** negotiated peer at most once per 200 ms per author (leading and trailing edge), and sends the full current draft set (minus the receiver's own) to a peer when its `drafts` channel and hello are both ready. An empty text deletes the draft. A viewer who leaves the snapshot's admitted set loses their draft, and the deletion is relayed.
- **FR-3** The host's share dialog lists the current drafts in `SuggestionList` (avatar, `@login`, text), oldest-started first. The controller can **Use** a draft (inline editor prefilled with its text), edit it, and **Send** it; a send of a draft clears that draft for everyone and tells its author "The host sent your suggestion."
- **FR-4** The viewer page shows a draft box under the timeline once admitted and connected. Typing sends a draft snapshot at most every 150 ms (trailing). The viewer also sees the other participants' drafts read-only in `SuggestionList`.
- **FR-5** A contributor's composer shows **Send** (and Ctrl/Cmd+Enter). Send posts `control` `{ kind: 'submit', clientId, text }` and clears the box and the draft. The host validates and answers `submit-ack` `queued` (with a 1-based position), then `sent`, or `rejected` with a reason.
- **FR-6** The host accepts a contributor submit only when the sender is a negotiated, eligible peer whose snapshot entry has `contributor: true`. Otherwise it answers `rejected not_contributor`.
- **FR-7** When a snapshot shows a contributor's grant gone (contributor false, or no longer admitted), the host drops that author's queued (not yet delivering) contributor submits and answers each with `rejected grant_revoked`. The viewer's composer loses **Send** as soon as its `JoinView.contributor` turns false.
- **FR-8** One `SubmitQueue` per share delivers in strict FIFO order across contributors and the controller. It never delivers while the agent is working, and after each delivery it waits for the turn to start (or for the transcript to change, or 30 s) and then to end before it delivers the next item.
- **FR-9** Delivery outcomes follow the scheduled-messages door rule: 2xx → `sent`; 409 → the item stays at the head and is retried on the next tick; any other 4xx → `rejected delivery_refused`; 5xx or a throw → `rejected delivery_unknown`, never re-delivered (at-most-once).
- **FR-10** Every stream in the presence payload carries `agentWorking` and `queued`. Viewers show "Agent is working · N queued", "N queued" or nothing; the share dialog shows the same line plus the queued items (author and text, read-only).
- **FR-11** A prompt is refused (`rejected invalid_prompt`, or HTTP 400 `invalid_prompt`) when its trimmed text is empty or its first non-whitespace character is `/`, `!` or `#`, and refused as `too_long` when it is longer than 8,000 characters. The same rule applies to contributor submits and controller sends.
- **FR-12** The host stamps `SharedMessage.author` (`{ login, avatarUrl }`) on the first user message appended after a delivery whose trimmed text equals the delivered text, and keeps the stamp in later `history` payloads. The viewer reads `author` and the timeline shows `@login` with the avatar on that user message.
- **FR-13** `POST /api/shares/:code/prompts` `{ text, draftGithubId? }` enqueues a controller send: 202 `{ ok: true, position }`; 400 `invalid_prompt` / `too_long` / `invalid_request`; 404 `share_not_found`; 409 `share_not_live`; 429 `queue_full`. `GET /api/shares` views carry `drafts` and `queue`.

Non-functional:

- **NFR-1** The wire stays scoped and versioned (parent NFR-2): every addition is an additive optional field or a new `kind` in an existing union. `v` stays 1. A slice-4 viewer ignores the new presence fields and `control` kinds; a slice-4 host ignores the new viewer messages.
- **NFR-2** `packages/contracts/src/sharing.ts` stays type-only and import-free (D-R3-8). Runtime helpers go in `sharing-wire.ts`.
- **NFR-3** Inbound viewer messages on `control` and `drafts` are reassembled with a 65,536-character cap (`SHARE_MAX_INBOUND_ENVELOPE_CHARS`), not the 32 Mi outbound cap, so one viewer cannot make the host buffer megabytes.
- **NFR-4** Queue and throttle tests use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`, never real delays (repo rule *Fake timers for retry / backoff / delay-based tests*).
- **NFR-5** Nothing in the hub, the board or the queue logs draft or prompt text (slice-3 rule: "Nothing here logs signaling data, ICE credentials or content").
- **NFR-6** No `execSync` and no sync tmux calls in any new server code (repo rules *No execSync in dashboard server code*, *Prefer async tmux primitives*). The queue reaches the terminal only through the delivery door.
- **NFR-7** No file grows past its file-size cap (`scripts/lint-file-size.sh`: 1,000-line ceiling for new files; existing files may not exceed their `origin/main` count or allowlist cap). `peer-hub.ts` is 502 lines today; drafts and queue logic live in the two new modules so the hub stays under 750.

## Decisions

- **D-1 Controller sends go through the same queue.** The host browser posts a picked or typed suggestion to `POST /api/shares/:code/prompts`, which enqueues it with `source: 'controller'`. *Why:* one ordering for every shared prompt, one "N queued" number, and attribution for picked drafts. The host's own normal composer is untouched and is not queued (NonGoal).
- **D-2 Suggestions live in the share dialog.** `SuggestionList` mounts in `ShareDialog` under the lobby panel, fed by the existing 1 s `GET /api/shares` poll (slice-2 D-6). *Why:* no new push channel to the host browser; drafts reach the host within about one second. A badge or composer-side list on the host's conversation page is a follow-up.
- **D-3 Queue status rides presence.** `SharedStream` gains optional `agentWorking?: boolean` and `queued?: number`. *Why:* status is per stream (a future task share has one agent and one queue per stream, parent NFR-3), and the hub already re-sends presence only when its JSON changes.
- **D-4 Viewer → host drafts use their own type.** `DraftUpdate { text }`. The viewer page does not reliably know its own GitHub id, and the host must not trust an inbound author anyway.
- **D-5 The author is not echoed its own draft.** Host → viewer relays skip the author. The only own-draft signal is `control` `{ kind: 'draft-sent' }` after the controller sent it. *Why:* echoing a snapshot back while the author types would overwrite their newer text.
- **D-6 Turn detection is polled, not pushed.** The queue ticks every 1,000 ms (`QUEUE_TICK_MS`) while it has items, is waiting on a turn, or has a watcher (at least one negotiated peer). Each tick reads `activity()` → `{ working, lastMessageId }`. Production: `resolveClaudeSessionFile(name)` (`conversation-bridge.ts` lines 185–195) then `summarizeConversationActivity(file, { harness: 'claude-code' })`; `lastMessageId` is the last summary message's id. A missing file or a thrown error reads `{ working: false, lastMessageId: null }`. *Why:* `summarizeConversationActivity` is mtime/size cached, so an unchanged transcript costs one `stat`; and its 180 s `WORKING_STALENESS_MS` (line 21) stops a dead agent from wedging the queue forever.
- **D-7 After a delivery, wait for the turn to start.** A freshly pasted prompt is not in the transcript yet, so `working` can still read false. State machine: `idle` → deliver head → `awaiting-start` (records `lastMessageId` at delivery time) → when a tick sees `working === true`, or a different `lastMessageId`, or 30,000 ms (`TURN_START_TIMEOUT_MS`) passed → `awaiting-end` → when a tick sees `working === false` → `idle`. *Why:* without the start wait, the next item would paste into the same turn. The `lastMessageId` check catches a turn that started and finished between two ticks. Non-Claude conversations have no activity source, so they fall back to one delivery per 30 s.
- **D-8 Door outcomes copy scheduled delivery.** See FR-9. 409 (`permission-pending`, `input-target-not-main`) is retried every tick without a cap: the operator answers the prompt and the queue resumes.
- **D-9 Command prefixes are refused.** `handleConversationMessage` runs `handleComposerCommandMessage` first (`conversation-message.ts` lines 427–446) and intercepts `/compact`; Claude Code's TUI also treats a leading `!` as a shell command and `#` as a memory note. A remote contributor must never reach any of them. The rule (FR-11) lives in one helper, `sharedPromptRefusal`, used by the viewer for early feedback and by the host for enforcement. It applies to controller sends too: the host can type any command into their own composer.
- **D-10 Attribution is correlation, not a prompt prefix.** The hub calls `bridge.expectAuthor(text, author)` right before each delivery and cancels it if the delivery is rejected. The bridge stamps the first appended `user` message whose `text.trim()` equals the expected text (oldest expectation first; at most 20 pending, oldest dropped). *Why:* prefixing `[@login]` would change what the agent reads. If the transcript text differs from the delivered text, the message simply has no author. The bridge only runs while a viewer is attached; a prompt delivered with no viewer attached stays unattributed.
- **D-11 Limits.** `SHARED_PROMPT_MAX_CHARS = 8_000` (drafts and prompts); `QUEUE_MAX_ITEMS = 20`; `QUEUE_MAX_PER_AUTHOR = 3` (queued contributor items per GitHub id; controller sends count only toward the total); `DRAFT_RELAY_MS = 200`; `DRAFT_SEND_MS = 150`; `SHARE_MAX_INBOUND_ENVELOPE_CHARS = 65_536`. A draft longer than the cap is ignored by the host, and the viewer's textarea has `maxLength={8000}`.
- **D-12 Client ids.** A contributor submit carries `clientId`: 1–64 characters of `[A-Za-z0-9_-]` (the viewer uses `crypto.randomUUID()`). A repeated `clientId` from the same author while that item is still queued is ignored. Acks echo it.
- **D-13 `ShareView` fields are optional.** `drafts?` and `queue?` are optional in the type so slice-2 fixtures and tests keep compiling; `viewOf` always sets both (empty when no hub).
- **D-14 A contributor's first prompt may retitle the conversation.** The door's `derivePromptTitle` runs for a default-titled conversation (`conversation-message.ts` lines 664–673), exactly as for the host's own first prompt. Accepted; not special-cased.
- **D-15 Drafts and queue are memory only.** Nothing is persisted. A host restart or a share end drops them. Items still queued when the hub closes are dropped; their peers are closing anyway.

## Host design

### Draft board (`src/dashboard/server/sharing/draft-board.ts`, new)

```ts
export const DRAFT_RELAY_MS = 200;
export interface DraftBoardDeps { now(): number; onRelay(payload: DraftPayload): void }
export class DraftBoard {
  update(author: ShareIdentity, text: string): void; // ignores text longer than SHARED_PROMPT_MAX_CHARS; '' deletes
  remove(githubId: number): void;                    // deletes and relays '' at once (no throttle)
  take(githubId: number): ShareDraftView | null;     // deletes, relays '' at once, returns what was there
  list(): ShareDraftView[];                          // oldest startedAt first
  payloads(): DraftPayload[];                        // current drafts as host → viewer payloads, oldest first
  close(): void;                                     // clears timers and drafts
}
```

Throttle per author: a change relays at once if the last relay for that author was at least `DRAFT_RELAY_MS` ago; otherwise one trailing relay is scheduled for `last + DRAFT_RELAY_MS` and sends the latest text then. `startedAt` is set when a draft goes from absent to non-empty and kept while it changes. `update(author, '')` for an author with no draft is a no-op (no relay), so a reconnecting viewer that re-sends an empty box costs nothing. `updatedAt` is the host clock (`now()`), never the viewer's.

### Submit queue (`src/dashboard/server/sharing/submit-queue.ts`, new)

```ts
export const QUEUE_TICK_MS = 1_000;
export const TURN_START_TIMEOUT_MS = 30_000;
export const QUEUE_MAX_ITEMS = 20;
export const QUEUE_MAX_PER_AUTHOR = 3;

export interface QueuedPrompt {
  readonly id: string;            // host id: `${source}-${counter}`
  readonly clientId: string | null;
  readonly source: 'contributor' | 'controller';
  readonly author: ShareIdentity | null;
  readonly text: string;
  readonly enqueuedAt: number;
}
export type DoorAnswer = { status: number; body: unknown };
export interface SubmitQueueDeps {
  deliver(text: string): Promise<DoorAnswer>;
  activity(): Promise<{ working: boolean; lastMessageId: string | null }>;
  now(): number;
}
export interface SubmitQueueEvents {
  onDelivering(item: QueuedPrompt): () => void;                 // returns an undo (D-10)
  onOutcome(item: QueuedPrompt, outcome: 'sent' | SharedSubmitReason): void;
  onStatus(status: { agentWorking: boolean; queued: number }): void; // only when it changed
}
export class SubmitQueue {
  constructor(deps: SubmitQueueDeps, events: SubmitQueueEvents);
  enqueue(item: Omit<QueuedPrompt, 'id' | 'enqueuedAt'>):
    | { ok: true; id: string; position: number }
    | { ok: false; reason: 'invalid_prompt' | 'too_long' | 'queue_full' };
  dropAuthor(githubId: number): QueuedPrompt[];  // queued contributor items only; never the delivering item
  setWatching(watching: boolean): void;          // the hub's "≥ 1 negotiated peer"
  view(): ShareQueueView;
  close(): void;
}
```

Rules:

1. `enqueue` checks `sharedPromptRefusal(text)` first, then `QUEUE_MAX_ITEMS` (all items, including the delivering one), then for `source: 'contributor'` `QUEUE_MAX_PER_AUTHOR`. `position` is the 1-based index in the waiting list, counting the delivering item as position 0. Each accepted enqueue starts the ticker.
2. The ticker is one `setTimeout(QUEUE_TICK_MS)` re-armed after each async tick finishes (never `setInterval`, never two ticks at once). It runs while the queue has items, the state is not `idle`, or `watching` is true; otherwise it stops.
3. A tick reads `activity()` (a throw reads `{ working: false, lastMessageId: null }`), emits `onStatus` when `agentWorking` or `queued` changed, then runs the D-7 state machine. In `idle` with a head and `working === false`, it calls `onDelivering(head)`, then `deliver(head.text)`, and applies FIFO rule FR-9: 2xx → remove head, `onOutcome(head, 'sent')`, state `awaiting-start`; 409 → call the undo, keep the head, stay `idle`; other 4xx → undo, remove, `onOutcome(head, 'delivery_refused')`; ≥ 500 or a throw → undo, remove, `onOutcome(head, 'delivery_unknown')`.
4. `close()` clears the timer and the items; no further callbacks fire.

export function productionSubmitQueueDeps(conversationName: string): SubmitQueueDeps {
  return {
    deliver: async (text) => decodeDoorResponse(await handleConversationMessage(conversationName, { message: text }, {
      resolveSessionFile, generateAiTitle: async () => {},
    })),
    activity: async () => {
      const file = await resolveClaudeSessionFile(conversationName);
      if (!file) return { working: false, lastMessageId: null };

        return { working: summary.isWorking, lastMessageId: summary.messages.at(-1)?.id ?? null };
      } catch { return { working: false, lastMessageId: null }; }
    },
    now: () => Date.now(),
  };
}

## Intersecting repo rules (restated)

- **Fake timers** for every delay-based test (`vi.useFakeTimers()`, `vi.advanceTimersByTimeAsync`); never real `setTimeout` waits; never lower `maxForks` to hide a leak.
- **No `execSync`** in dashboard server code; no new sync tmux calls. Delivery goes through the door, which uses the async terminal backend.
- **Quality gates:** `npm run typecheck`, `npm run lint`, and `npx vitest run <touched test files>`; never the full `npm test` on the host. `npm run typecheck` skips `*.test.ts`, so keep test fakes in sync with interfaces by running the tests.
- **File-size ratchet:** no file past its cap; plan an extraction, never an allowlist raise (WI-7 checkpoint).
- **New route ⇒ no-loss-matrix row** (WI-8), or CI fails.
- **Source-grep tests and `skipIf`/`.only` are rejected by lint** — assert behavior, not file text.
- **Style guide** for UI: no pill badges, no decorative color, neutral buttons, `font-mono` handles (*pan-style-guide*).
- **Playwright isolation:** isolated browser instance and profile per agent; never the operator's dashboard on 3011.
- **No logging of content** (NFR-5).

## Out of scope (NonGoals)

- Collaborative editing of one draft by many people (CRDT `collab` channel, parent *Forward compatibility*).
- Controller handoff and a viewer acting as controller (slice 7, [PAN-4478](https://github.com/eltmon/overdeck/issues/4478)); in this slice only the host picks and sends drafts.
- The read-only terminal channel (slice 6, [PAN-4477](https://github.com/eltmon/overdeck/issues/4477)).
- Persisting drafts or the queue across a host restart; host reconnect (slice 8, [PAN-4479](https://github.com/eltmon/overdeck/issues/4479)).
- Reordering, editing or cancelling queued prompts.
- Queuing the host's own normal composer sends.
- Showing contributor attribution in the host's own conversation timeline (the host's timeline comes from its local transcript, not `SharedMessage`).
- Attachments or images in shared prompts; slash commands, `!` shell commands and `#` memory notes from shared prompts.
- Resuming an ended conversation before delivering (the scheduled-messages tick does this; the share queue rejects instead).
- Auto-contributor designation by GitHub handle; the hosted web join (PAN-4481).
- Turn detection for non-Claude harnesses beyond the 30 s fallback.
- A suggestion list on the host's conversation page outside the share dialog.

## Hazards

- **Text correlation can miss.** If Claude Code stores the prompt with different whitespace or wrapping, the bridge leaves `author` unset. That is the designed fallback; never "fix" it by prefixing the prompt.
- **Fast turns between ticks.** A turn that starts and ends within one 1 s tick is caught by the `lastMessageId` change (D-7). A test must cover it (WI-4 c).
- **409 forever.** A permission prompt nobody answers holds the queue. That is intended; the status line keeps showing the queue.
- **Fakes drift.** `HostHub` gains methods; `share-host.test.ts`'s fake hub must implement them, and typecheck does not see test files.
- **Presence assertions change.** `presenceOf` now always adds `agentWorking` and `queued` to the stream, so the existing exact-match stream assertions in `peer-hub.test.ts` (around lines 597 and 633) must gain `agentWorking: false, queued: 0` in WI-7.
- **Seq on the viewer.** The hello is `control` seq 1; the first submit must be seq 2. A reset negotiation resets the counters.
- **ShareDialog is a modal.** The host must keep the share dialog open to see suggestions (D-2). Acceptable for v0.
