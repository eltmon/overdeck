# PAN-4258 — Planning effort: all five levels, PlanDialog defaults to `high`, fix "LOW effort planning"

**Issue:** [PAN-4258](https://github.com/eltmon/overdeck/issues/4258) — sibling S6 of [PAN-4249](https://github.com/eltmon/overdeck/issues/4249).
**Program PRD:** `.pan/drafts/PAN-4249.md` (section "Sibling issues"). **Audit:** first comment on #4249, section 6 bugs 2 and 3, section 1 "Non-`high` defaults".
**Foundation (landed, closed):** PAN-4249 shipped `EFFORT_LEVELS`/`EffortLevel`/`DEFAULT_EFFORT`/`isEffortLevel`/`compareEffort` in `packages/contracts/src/effort.ts` and `resolveEffort()` in `src/lib/agents/resolve-effort.ts`.

## Glossary

- **Effort / reasoning effort** — the `--effort` level a harness launches with. Canonical enum: `low`, `medium`, `high`, `xhigh`, `max` (`packages/contracts/src/effort.ts`, grep `export const EFFORT_LEVELS`).
- **`resolveEffort(input)`** — the single resolver (`src/lib/agents/resolve-effort.ts`). Precedence: `explicit` → item → plan → tier → sub-role (`roles.<role>.sub.<s>.effort`) → role (`roles.<role>.effort`) → project (`projects.<key>.effort`) → default `high`. Clamps the winner to the model + harness via `clampEffort` (`src/lib/agents/effort-support.ts`). An invalid `explicit` throws `InvalidEffortError`; invalid lower layers fall through. Returns `{ effort, source, requested, clamped, warning? }`.
- **Clamping** — if the model/harness pair does not support the requested level, use the highest supported level below it (e.g. `max` → `xhigh` on muse, whose `effortLevels` is `["low","medium","high","xhigh"]` in `packages/contracts/src/harness-behavior.ts`).
- **Planning prompt** — the markdown file `buildPlanningPrompt()` renders and `spawnPlanningSession()` writes to `~/.overdeck/agents/<session>/planning-prompt.md`. It contains an optional `EFFORT_SECTION` and `PROBE_SECTION`.
- **Probe pass** — the "Probe Pass (required before finalize)" prompt section; today rendered when `--probe` is set or `effort === 'high'`.
- **start-planning API** — `POST /api/issues/:id/start-planning`, implemented by `startPlanningForIssue()` in `src/lib/overdeck/planning-sessions.ts`. Called by `pan plan`, `pan start` (unplanned path), and the dashboard PlanDialog.
- **`lint:effort`** — `scripts/lint-effort.sh`, a shrink-only ratchet counting `effort ?? '<level>'` fallbacks and `'low' | 'medium'`-style enum copies per file against an embedded `BASELINE`. A file whose count drops prints `note: lower BASELINE[...]`; the slice that cleans a file deletes or lowers its row.

## Problem

1. `pan plan --effort` accepts only `low | medium | high` in its help (`src/cli/index.ts:322`) and type (`src/cli/commands/plan.ts:15`). `SpawnPlanningOptions.effort` and `buildPlanningPrompt`'s `effort` param are typed `'low' | 'medium' | 'high'` (`src/lib/planning/spawn-planning-session.ts:135` and `:199`).
2. **Bug ("LOW effort planning"):** `pan start --effort xhigh|max` on an unplanned issue forwards the raw value to start-planning (`src/cli/commands/start.ts:906`, `effort: options.effort,`). `buildPlanningPrompt` treats every non-`high`, non-`medium` value as low (`spawn-planning-session.ts:254-268`, grep `effort === 'high' ? 'High (Deep Analysis)' : 'Low (Quick Planning)'`), so the prompt tells the planner "The user has requested LOW effort planning".
3. For claude-code planning, the harness receives no effort: `getAgentRuntimeBaseCommand(planningModel, sessionName, roleAgentDefinitionPath('plan'), effectiveHarness)` at `spawn-planning-session.ts:551` omits the 5th `effort` parameter, so `roles/plan.md` frontmatter (`effort: high`) always decides. The other harness launcher fields receive the raw, unresolved, unclamped value (`:555-580`, `:621`). `roles.plan.effort` and `projects.<key>.effort` are never consulted for planning.
4. The start-planning API does not validate `body.effort` (`planning-sessions.ts:167`, destructured; `:428` `effort: effort || undefined,` forwarded as-is).
5. PlanDialog defaults to `medium` (`src/dashboard/frontend/src/components/PlanDialog.tsx:104`, `useState<'low' | 'medium' | 'high'>('medium')`) and labels medium "(default)" (`:886`), violating `sync-sources/rules/effort-high-default.md`. It offers only three levels (`:869`, `(['low', 'medium', 'high'] as const).map`).
6. `pan strike --dry-run` prints `Effort:     medium` when no `--effort` is given (`src/cli/commands/strike.ts:368`, `options.effort ?? 'medium'`), while help says "default high" (`src/cli/index.ts:493`). The real launch passes `options.effort` (undefined) to `spawnAgent` (`strike.ts:389`), so `roles/strike.md` frontmatter (`high`) decides and `roles.strike.effort` is ignored.

## Requirements

### Functional

- **FR-1** `pan plan --effort <level>` accepts `low`, `medium`, `high`, `xhigh`, `max`; its help text lists all five; the CLI forwards the value unchanged in the start-planning body.
- **FR-2** The start-planning API returns HTTP 400 with an error naming the valid levels when `body.effort` is present (not `undefined`, `null`, or `''`) and is not an `EffortLevel`. The rejection happens before any mutation (no issue fetch, lifecycle transition, event append, or agent-state write).
- **FR-3** `spawnPlanningSession` resolves effort once with `resolveEffort({ explicit: effort, role: 'plan', issueId, model: planningModel, harness: effectiveHarness })` and passes the resolved `.effort` to the claude-code base command (5th arg of `getAgentRuntimeBaseCommand`) and to every other harness's launcher fields (pi, codex, ACP, kimi-code, prime-agent, muse) and to `buildPlanningPrompt`.
- **FR-4** The planning prompt's effort section bands by rank: `low` → the existing LOW text; `medium` → no section; `high`, `xhigh`, `max` → the existing deep-analysis text with the heading naming the actual level (e.g. `## Planning Effort: Max (Deep Analysis)`) and the body sentence naming it (e.g. `**The user has requested MAX effort planning.**`). The text "LOW effort planning" appears only for `low`.
- **FR-5** The probe pass renders when `--probe` is set or the effort ranks at or above `high` (`compareEffort(effort, 'high') >= 0`).
- **FR-6** PlanDialog's initial effort is `high` (`DEFAULT_EFFORT`); it renders one button per `EFFORT_LEVELS` entry (five); the hint line marks `high` as the default.
- **FR-7** `pan strike` resolves effort once with `resolveEffort({ explicit: options.effort, role: 'strike', issueId, model: options.model, harness: options.harness })`; the dry-run prints the resolved level and its source; the real launch passes the same `effort` and `effortSource` to `spawnAgent`. An invalid `--effort` prints `Invalid --effort value: <v>. Expected one of low, medium, high, xhigh, max.` and the command fails without spawning.

### Non-functional

- **NFR-1** No new `?? '<level>'` fallback or effort-enum copy. `npm run lint:effort` passes, and the `BASELINE` rows for `src/lib/planning/spawn-planning-session.ts`, `src/cli/commands/plan.ts`, `src/dashboard/frontend/src/components/PlanDialog.tsx`, and `src/cli/commands/strike.ts` are deleted (their counts reach 0).
- **NFR-2** Defaults stay `high`; nothing defaults to `xhigh` or `max`.
- **NFR-3** File-size ratchet: `PlanDialog.tsx` (1093 lines on main) and `src/cli/index.ts` (1272) must not grow. `src/cli/commands/start.ts` is not edited.
- **NFR-4** Async-only: no `execSync` or new sync tmux calls in server-reachable code (`planning-sessions.ts`, `spawn-planning-session.ts`).

## Decisions

- **D1 — Prompt bands key off the resolved level, not the request source.** Because `resolveEffort` always returns a level (default `high`), every default planning run now carries the deep-analysis section and the probe pass. Rationale: one truth — the prompt describes the effort the harness actually runs at, and `high` is the declared default by rule. Recorded in `autoDecisions`.
- **D2 — `pan start` keeps forwarding its `--effort` to planning on the unplanned path** (`start.ts:906`). That is documented behavior (`sync-sources/skills/pan-start/SKILL.md:78`, PAN-3022 D4). The bug is fixed in the prompt banding (FR-4) and resolution (FR-3); `start.ts` is not edited (it is at 1281 lines against PAN-4249 NFR-3's ceiling).
- **D3 — `pan plan` does no client-side effort validation.** The API 400 (FR-2) is the single gate; `plan.ts` already surfaces `data.error` (`plan.ts:56-59`). `plan.ts` only retypes `effort` to `EffortLevel`.
- **D4 — PlanDialog always sends its selected effort** (now `high` by default) as `explicit`. Resolving the dialog default from `GET /api/effort/default` is out of scope.
- **D5 — The effort picker moves out of PlanDialog** into a new `src/dashboard/frontend/src/components/PlanEffortPicker.tsx`, so `PlanDialog.tsx` shrinks instead of growing past 1093 lines.
- **D6 — Strike clamps against `options.model` only** (undefined → harness-only clamp). `spawnAgent` resolves the strike model internally; re-resolving it in the CLI is out of scope.
- **D7 — The strike `BASELINE` row is labelled `# PAN-4259` but its only match is the dry-run `?? 'medium'` this issue removes;** delete the row here.
