## Revision 2 summary (2026-09-27)

Revision 1 designed a user-owned git "sync plane" that copied whole transcripts between one
user's machines. Revision 2 keeps that design's ownership model (single owner, explicit
adoption, compare-and-swap transfer) and changes four things:

1. **Storage format borrowed from agit** ([Einsia/agent-git](https://github.com/Einsia/agent-git),
   reviewed 2026-09-27). Transcripts are stored as immutable, content-addressed chunks plus an
   ordered index (`LOG`) and a resume selection (`VIEW`), not as a re-copied `transcript.jsonl`.
   Every save runs a continuity check, and every turn records a summary of the working tree's git state. Forks share storage with their parent.
2. **Standalone product surface.** `pan vault` works for a person who uses Overdeck *only* for
   this feature: no dashboard, no `pan install`, no registered projects. The engine lives in
   `src/lib/vault/`; the dashboard is one consumer of it.
3. **Always encrypted, backend-neutral.** Chunks and refs are encrypted on the client before any
   backend sees them. That makes a user's GitHub repo and a hosted overdeck.ai store equally
   unable to read content, so one format serves both.
4. **Phase B: a hosted vault on overdeck.ai** as a paid part of Overdeck Anywhere. It is an
   encrypted object store with a compare-and-swap ref service, **not a git server** (decision D-4).

Also: the original `pan devices` verb group is renamed `pan vault`; opt-in eviction of local
transcripts is added (FR-16), gated as an operator decision (D-7).

### Why not adopt agit itself

agit (Rust, MIT, created 2026-09-01) implements most of the local half well. It was not adopted
for these reasons, which is why this PRD copies its ideas instead:

- It requires a hub login even to record a local version, and its self-hosted backend
  (`AgentGit-backend`) is not publicly available (GitHub 404 on 2026-09-27).
- Its official hub stores plaintext transcripts and has telemetry that cannot be disabled
  (`DO_NOT_TRACK` and `AGIT_TELEMETRY_DISABLED` are ignored for `agent-git.com`, per its `docs/telemetry.md`).
- `agit setup` writes hooks, skills, MCP config and AGENTS.md blocks, which collides with
  Overdeck's managed context layers.
- Its protocol has already had one incompatible rewrite; its remote-control RFCs are not accepted.

Revisit if Einsia publishes the backend and drops the login requirement for local versions.

## Glossary

| Term | Definition |
| --- | --- |
| **Vault** | The user-scoped store of saved conversations. Local cache at `${OVERDECK_HOME}/vault/`; one configured **backend** holds the durable copy. Replaces revision 1's "sync plane". Never a project repo and never the archived `overdeck-state` branch. |
| **Backend** | Where the durable copy lives. v1: `git` (a private git remote the user owns). Phase B: `overdeck` (the hosted overdeck.ai vault). Tests: `dir` (a local directory). All implement one `VaultStore` interface (see Architecture). |
| **Native transcript** | The harness's own session file: Claude Code `~/.claude/projects/<cwd-slug>/<sid>.jsonl`; Codex `<CODEX_HOME>/sessions/YYYY/MM/DD/rollout-*.jsonl` (managed agents use `<agentDir>/codex-home`). |
| **Session record** | The vault's durable form of one conversation: a `meta` document plus `LOG`/`VIEW` indexes pointing at chunks. Identified by `vaultId` (UUID minted at first save, decoupled from machine-local ids). |
| **Chunk** | An immutable object holding the transcript lines appended during one settlement, zstd-compressed, then encrypted. Its id is a keyed hash of its plaintext (see D-3). |
| **LOG** | The ordered list of chunk ids that reproduces the full saved transcript. |
| **VIEW** | The ordered selection that a resume loads: from the last compaction boundary (inclusive) to the end. Claude Code boundary = a user line with `"isCompactSummary":true`; Codex boundary = a `{"type":"compacted"}` line. |
| **Settlement** | One save: read the native transcript, run the continuity check, write new chunks, update the record's refs. The vault's equivalent of a commit. |
| **Continuity check** | Compares the per-line hash sequence already saved with the live file's parseable lines. Result `noop` (nothing new), `append` (pure growth, save it), or `diverged` (a middle line changed: refuse and surface). Unparseable trailing lines are skipped and saved by a later settlement. |
| **cwd state** | A bounded summary of the conversation's working directory at settlement: git origin, HEAD, branch, dirty/clean, counts of staged/unstaged/untracked/conflicted files. No paths, diffs, or file contents. |
| **Owner machine** | The one machine allowed to settle a given session record. Only the owner writes it. |
| **Machine identity** | `machineId` (UUID) + label, created once at `${OVERDECK_HOME}/machine-id.json`. |
| **Browse copy** | A non-owner machine's read-only rendering of a record, badged with its owner. |
| **Adoption** | "Continue here": a non-owner rebuilds a native session from the record's `VIEW` and takes ownership through a compare-and-swap. The origin machine's native file is never modified. |
| **CAS** | Compare-and-swap on a ref: write succeeds only if the ref's version is unchanged since read. Git backend: push rejection. Hosted backend: a version precondition. |
| **Vault key** | The 256-bit symmetric key that encrypts all chunks and refs. It is generated at setup, stays on the user's devices, and can be recovered from a 24-word phrase. |
| **Standalone mode** | Running `pan vault` with no dashboard server, no `pan install`, and no registered projects. |
| **Eviction** | Opt-in deletion of a native transcript after the vault holds a verified copy (FR-16). |

## Problem

1. **Single machine.** Transcripts, conversation rows in `overdeck.db`, and live panes all live
   on the machine that created them. Work started on a desktop is invisible on a laptop.
   [PAN-3762](https://github.com/eltmon/overdeck/issues/3762) lets one client *operate* sessions on several machines, but it
   explicitly leaves moving a conversation to [PAN-2609](https://github.com/eltmon/overdeck/issues/2609) (`pan-3762.md` lines 67, 110, 377).
2. **Disk.** Measured on the operator's machine 2026-09-27: `~/.claude/projects` 20 GB (5,866
   JSONL files), `~/.codex/sessions` 9.7 GB, `~/.overdeck/agents` 13 GB, plus the local restic
   copy `~/.overdeck/transcript-preservation` 24 GB. Nothing can move transcripts off the
   machine. The restic service (`docs/TRANSCRIPT-PRESERVATION.md`) is local only, and
   [PAN-3012](https://github.com/eltmon/overdeck/issues/3012) OQ-2 puts off-machine durability out of scope.
3. **Only Claude Code can resume.** The only native-resume path is the plain fork, which is
   Claude Code only (`src/lib/overdeck/conversation-forks.ts` lines 453-457 and 813-817). Fly remote
   agents' transcripts are copied back to `~/.overdeck/agents/<id>/remote-sessions/` by
   `captureRemoteForensics` (`src/lib/remote/remote-completion.ts` lines 71-117), and nothing indexes or
   resumes them.
4. **A standalone audience exists.** agit reached ~370 stars in four weeks with only this
   feature. Some users want "version, back up, and resume my agent sessions anywhere" without
   adopting an orchestrator.

## Goal

**Phase A (this issue):**
1. A vault that saves Claude Code and Codex conversations as encrypted, content-addressed,
   versioned records on a backend the user chooses (v1: a private git remote).
2. Browse every saved conversation from any of the user's machines; adopt one to continue it
   natively.
3. Free local disk space by evicting native transcripts that the vault holds (opt-in).
4. A `pan vault` command group that works standalone, plus dashboard surfaces for Overdeck users.

**Phase B (split into its own issue at plan time; see "Phase B"):** a hosted overdeck.ai
backend, sold as part of an Overdeck Anywhere subscription.

Non-goals: concurrent multi-machine editing of one live session (CRDT); sharing with other
people ([PAN-658](https://github.com/eltmon/overdeck/issues/658)); live control of remote sessions ([PAN-3762](https://github.com/eltmon/overdeck/issues/3762)).

## Requirements

IDs FR-1..FR-9 and NFR-1..NFR-6 are from revision 1 and keep their numbers; changed text is
marked *(rev 2)*.

### Functional

- **FR-1** *(rev 2)* A user enables the vault with `pan vault setup <backend-url>` (or dashboard
  Settings). v1 accepts a git remote URL; Phase B adds `overdeck://`. Setup creates the vault key
  and shows the recovery phrase once. **Overdeck never provides or defaults a backend.** An
  unset backend means the vault is off, and every command says so plainly without erroring.
- **FR-2** Each machine has a stable identity (`machineId` + label), created on first vault use
  and recorded in the vault under `machines/<hmac(machineId)>`.
- **FR-3** *(rev 2)* Conversations are saved by settlement: (a) in Overdeck mode, automatically
  on transcript growth, debounced; (b) in standalone mode, by `pan vault save`, by the optional
  Claude Code Stop hook (FR-14), or by `pan vault sync`. Each settlement writes only new chunks.
  A sync cycle (push + pull) runs at dashboard boot, on a periodic timer, and on demand.
- **FR-4** Non-owned records appear in the dashboard conversation list as browse copies: full
  transcript rendering through the existing conversation UI, read-only composer, owner badge.
  They are excluded from cost totals and agent/runtime views. `pan vault list` and
  `pan vault show <id>` give the same information in the terminal.
- **FR-5** *(rev 2)* "Continue here" (dashboard action, `pan vault resume <id>`) on a browse
  copy performs the CAS ownership transfer, then materializes a native session from the record's
  `VIEW` and launches it. In Overdeck mode the new session is a managed conversation created
  through the fork pipeline. In standalone mode the harness is launched in the target cwd, or
  with `--no-launch` the launch command is printed. The origin machine shows "continued on
  <machine>" after its next pull, and its native file is never touched.
- **FR-6** *(rev 2)* Native adoption works for Claude Code in v1. Codex native adoption is an
  implementation checkpoint (WI-6). Records from other harnesses still save and browse; their
  adoption falls back to a summary-seeded fresh session, labeled as such.
- **FR-7** Exclusions: per-project and per-conversation opt-out (config list + a "never save"
  toggle). Excluded conversations never enter the vault; excluding a saved one tombstones it.
- **FR-8** *(rev 2)* Conflicts never lose data. Only the owner writes a record, and every
  settlement passes the continuity check (FR-11). A `diverged` result or an unexpected ref
  conflict is surfaced to the operator and never auto-resolved by discarding.
- **FR-9** After [PAN-2565](https://github.com/eltmon/overdeck/issues/2565) lands, task metadata syncs as an additional record type (schema
  reserved now, behavior gated on PAN-2565).
- **FR-10** Records use the chunk / `LOG` / `VIEW` format. A forked or adopted session's `LOG`
  starts with its parent's chunk ids up to the fork point, so shared history is stored once.
- **FR-11** Continuity check on every settlement with the three verdicts `noop` / `append` /
  `diverged` (glossary). Per-line hashes are stored with each chunk so the check never needs to
  download or decrypt earlier chunks.
- **FR-12** Each settlement records cwd state. On resume, if the target cwd's origin, HEAD,
  branch, or dirty state differs from the saved state, the user chooses: continue, continue and
  inject a short note describing the difference as the first message, or cancel. A cwd that is
  not a git repo skips the comparison and continues.
- **FR-13** Secret scan before a chunk is written: the same patterns Overdeck already uses for
  redaction (see WI-2 checkpoint). A hit blocks that record's settlement, names the line
  number and pattern (never the value), and offers `pan vault allow-secret` (per record, per
  line hash) or exclusion. Encryption does not replace this; a leaked vault key would expose
  every saved secret.
- **FR-14** Standalone mode: every `pan vault` verb works on a fresh `npm install -g
  @overdeck/core` with no `pan install`, no dashboard, no Herdr, and no registered projects.
  It discovers native transcripts in the default harness homes. It writes nothing into harness
  settings unless the user runs `pan vault setup --hooks`, which adds exactly one Claude Code
  Stop hook entry and prints what it added.
- **FR-15** Import any native session, not only Overdeck conversations: `pan vault save
  <session-id|path>` and `pan vault save --all [--since <date>] [--harness <h>]`.
- **FR-16** Eviction (opt-in, see D-7): `pan vault evict` and the retention policy may delete a
  native transcript only when (a) its record's last settlement covers every parseable line,
  (b) that settlement was read back from the backend and its hashes verified, and (c) the
  session is not live. `pan vault restore <id>` rebuilds the native file at its original
  path. Eviction goes through the one transcript-deletion door (`src/lib/cloister/transcript-retention.ts`).
- **FR-17** Resume from any saved version: `pan vault resume <id>@<version>` materializes the
  `LOG` prefix up to that version as a **new** record (a fork), never rewriting the original.
- **FR-18** Human-turn labeling: turn numbers count only prompts a person typed. Injected
  user-role lines (Claude Code `<task-notification>`, `<command-name>`,
  `<local-command-stdout>`, `<local-command-caveat>`, `[Request interrupted by user]`; Codex
  `<environment_context>`, `<codex_internal_context>`, `# Files mentioned by the user:`) are
  matched by known prefix, not by "starts with `<`".
- **FR-19** Fly remote agents: the reap step settles each copied remote transcript into the
  vault (when enabled) after `captureRemoteForensics` succeeds, so remote work becomes resumable.

### Non-functional

- **NFR-1** *(rev 2)* No plaintext conversation content, titles, cwd paths, or project names
  ever reach a backend. Backends see encrypted objects, opaque ids, sizes, and timestamps.
  The vault key never leaves the user's devices. Docs and setup output say plainly that losing
  every device and the recovery phrase means losing the vault.
- **NFR-2** `overdeck.db` stays a rebuildable cache: browse rows on any machine derive from the
  vault. Reads and writes go through the conversations domain doors.
- **NFR-3** All vault I/O is async (`execFile`/`spawn` with promises; no `execSync`), runs off
  the request path, and degrades to local-only when the backend is unreachable, with no
  error spam.
- **NFR-4** *(rev 2)* Vault operations never touch project repos, the `overdeck-state` branch,
  or other machines' native files. The only native writes are materialization of a new session
  file (FR-5, FR-17), restore (FR-16), and eviction through the retention door (FR-16).
- **NFR-5** Debounce, periodic sync, and backoff tests use `vi.useFakeTimers()`.
- **NFR-6** *(rev 2)* Large transcripts: chunks are append-only, so settlement cost scales with
  new lines, not file size. A per-settlement size guard (default 64 MB of new plaintext,
  configurable) splits oversized appends into several chunks rather than failing.
- **NFR-7** Standalone footprint: `pan vault` is lazy-loaded (`lazyAction` in
  `src/cli/index.ts`) and imports only `src/lib/vault/**`, transcript discovery, and config.
  It does not load the dashboard, Effect runtime layers, node-pty, or the terminal backend.
- **NFR-8** No telemetry. The vault sends nothing anywhere except to the configured backend.
- **NFR-9** Crypto uses `node:crypto` only (AES-256-GCM, HKDF-SHA256, HMAC-SHA256, scrypt for
  the recovery phrase). No new native dependency. Compression is zstd via `node:zlib`
  (`zstdCompressSync` exists on Node 22.15+; `package.json` requires `>=22.16.0`); the codec is
  recorded per chunk so it can change later.

## Architecture

### Module layout

```
src/lib/vault/
  identity.ts        machine id; vault key create/load/recover (FR-1, FR-2)
  format.ts          chunk encode/decode, LOG/VIEW, meta schema, versioning (FR-10)
  continuity.ts      line hashing + noop/append/diverged (FR-11)
  turns.ts           human-turn filter (FR-18)
  cwd-state.ts       bounded git summary + drift comparison (FR-12)
  secrets.ts         pre-settlement scan (FR-13)
  settle.ts          one settlement: read native, check, scan, chunk, write refs
  materialize.ts     VIEW -> native file per harness (FR-5, FR-6, FR-17)
  store/
    types.ts         VaultStore interface
    git.ts           git backend (v1)
    dir.ts           local-directory backend (tests, NAS)
  sync.ts            push/pull cycle, backoff, CAS adoption
src/cli/commands/vault/*.ts           pan vault verbs
src/dashboard/server/services/vault-service.ts   dashboard consumer (watch, import rows)
```

### Backend interface

```ts
// src/lib/vault/store/types.ts
export interface VaultStore {
  putObjects(objects: ReadonlyArray<{ id: string; bytes: Uint8Array }>): Promise<void>; // idempotent
  getObject(id: string): Promise<Uint8Array | null>;
  hasObjects(ids: readonly string[]): Promise<Set<string>>;
  readRef(name: string): Promise<{ value: Uint8Array; version: string } | null>;
  casRef(name: string, expectedVersion: string | null, value: Uint8Array): Promise<'ok' | 'conflict'>;
  listRefs(prefix: string): Promise<Array<{ name: string; version: string }>>;
}
```

All bytes passed in are already encrypted. Ref names are `hmac(key, 'ref:' + vaultId)` so the
backend cannot link records to conversations.

**Git backend:** local clone at `${OVERDECK_HOME}/vault/git/`. Objects at `objects/<id[0:2]>/<id>`;
refs at `refs/<name>` (file content = encrypted value). A pending batch is one git commit.
`casRef` = commit locally, then `git push`; a non-fast-forward rejection → `git pull --rebase`
of the vault's own commits → if the ref file changed upstream, return `conflict`, else retry.
Version = the blob SHA of the ref file. Never `git stash`.

### Record format

Per record, one encrypted ref value (JSON before encryption):

```jsonc
{
  "v": 1,
  "vaultId": "…",
  "owner": { "machineId": "…", "label": "desktop" },
  "harness": "claude-code",              // or "codex"
  "nativeSessionId": "…",                // owner-side; informational
  "title": "…", "model": "…", "project": "overdeck",
  "cwd": "/home/…", "gitOrigin": "git@github.com:eltmon/overdeck.git",
  "log":  ["<chunkId>", "…"],            // FR-10
  "view": { "fromChunk": 12, "fromLine": 40 },   // VIEW start; runs to the end
  "parent": { "vaultId": "…", "chunks": 9, "line": 17 },  // set on forks/adoptions
  "settlements": [ { "at": "…", "chunk": "<chunkId>", "turn": 7, "cwdState": { … } } ],
  "lineage": [ { "machineId": "…", "adoptedAt": "…" } ],
  "tombstone": false,
  "createdAt": "…", "updatedAt": "…", "endedAt": null
}
```

Chunk plaintext (before zstd and encryption):

```jsonc
{ "v": 1, "codec": "zstd", "lineHashes": ["<sha256[:16] per line>", "…"], "lines": ["<raw JSONL line>", "…"] }
```

`lines` are the native bytes, unchanged (no re-serialization), so restore reproduces the native
file byte-for-byte for the saved range. `settlements` is capped at the last 500 entries; older
entries are folded into a `settlementsArchive` chunk.

### Encryption (D-3)

- Vault key `K` (32 random bytes). Recovery phrase = 24 BIP-39 words encoding `K`; a new machine
  joins with `pan vault join <backend-url>` and enters the phrase. Stored at
  `${OVERDECK_HOME}/vault/key` (mode 0600).
- Sub-keys via HKDF: `K_enc`, `K_id`, `K_ref`.
- Chunk id = `hex(HMAC-SHA256(K_id, plaintext))[:40]`. It is keyed so the backend cannot confirm a
  guess of a chunk's content. Identical plaintext still dedupes within one vault.
- Encryption = AES-256-GCM with a random 96-bit nonce per object; stored as
  `nonce ‖ ciphertext ‖ tag`, with the id as associated data so objects cannot be swapped.

### Settlement (FR-3, FR-10, FR-11, FR-13)

1. Resolve the native file (Overdeck mode: `src/lib/agents/transcript-resolver.ts`; standalone:
   harness discovery roots in `src/lib/conversations/harness-discovery.ts`).
2. Read from the byte offset of the last settlement; split into lines; drop a trailing
   unparseable line.
3. Continuity: the saved line-hash sequence must be a prefix of the live one (verify the last
   saved chunk's final 16 hashes against the same positions in the live file; a mismatch
   triggers a full comparison). `noop` → stop. `diverged` → stop, record a `vault.diverged`
   state, surface it.
4. Secret scan the new lines (FR-13).
5. Split into chunks (NFR-6), encode, encrypt, `putObjects`.
6. Update `log`, recompute `view` if a compaction boundary appeared, append a settlement entry
   with turn number (FR-18) and cwd state (FR-12), then `casRef`.

Overdeck mode triggers settlement from the transcript watch the conversation service already
runs (`src/dashboard/server/services/conversation-service.ts`), debounced 30 s after the last
growth. Standalone triggers are listed in FR-3.

### Materialization (FR-5, FR-6, FR-17)

- **Claude Code:** fetch and decrypt the `VIEW` chunks, write them to
  `~/.claude/projects/<slug(targetCwd)>/<newSessionId>.jsonl`, rewriting only each line's
  `sessionId` field and, when the cwd changed, each line's `cwd` field. In Overdeck mode reuse
  the fork pipeline's plain-fork path (`runForkPipeline`, `src/lib/overdeck/conversation-forks.ts` line 434;
  `copySessionFromCompactBoundary`, `src/lib/conversations/summary-fork.ts` line 554), feeding it the
  materialized file as the parent.
- **Codex:** implementation checkpoint (WI-6).
- **Target cwd:** Overdeck mode maps `gitOrigin` to a registered project's checkout. Standalone
  uses `--cwd`, else the saved cwd if it exists, else an error naming both options.

### Decisions

- **D-1 Borrow agit's design, don't depend on agit.** Reasons are in "Why not adopt agit itself".
- **D-2 Chunks per settlement, not one file per line.** agit stores one object per event line,
  so a busy machine creates millions of files. A chunk per settlement keeps object count
  proportional to saves. Per-line hashes inside each chunk still support the continuity
  check and fork sharing.
- **D-3 Always encrypt, on every backend.** A single format serves both git and hosted. A
  private GitHub repo holding plaintext transcripts is one leaked token from exposing every
  secret an agent ever printed. The cost is key management (recovery phrase, join flow), which
  Phase B needs anyway.
- **D-4 The hosted vault is an object store with a ref service, not a git server.** The server
  holds only ciphertext, so git's server-side features (diffs, delta compression, web
  browsing) give no benefit. A git server (Gitea/Forgejo) adds repository operations, git-protocol
  scaling, and backups for nothing. The format needs only immutable objects plus
  compare-and-swap refs, which object storage plus a small consistent service provides directly.
- **D-5 Command name `pan vault`** (also `overdeck vault`, since both bins map to the same
  entry). Revision 1's `pan devices` described machines, not the thing users store. Do not
  overload `pan sync` (context/skills distribution) or `pan backup` (existing Overdeck
  config backups, `src/cli/index.ts` lines 208-220).
- **D-6 Single owner + CAS, no CRDT** (unchanged from revision 1).
- **D-7 Eviction is opt-in and ships dark.** The CLAUDE.md rule "JSONL session files are
  sacred" forbids deleting transcripts. FR-16 relaxes it only for files with a verified vault
  copy. **Operator decision required before merge:** confirm the relaxation. If declined, drop
  FR-16 and WI-8; the rest of the PRD is unaffected.

## Phase B — hosted vault on overdeck.ai (separate issue; do not build under PAN-2609)

**Product.** One Overdeck Anywhere subscription covers the hosted vault, the relay
([PAN-2356](https://github.com/eltmon/overdeck/issues/2356)), and push notifications ([PAN-2354](https://github.com/eltmon/overdeck/issues/2354)). Users who want only the vault pay
the same subscription. Self-hosting stays free: the git backend has no feature gate.

**Architecture.**
- Storage: Cloudflare R2 (the `overdeck.ai` zone already lives on Cloudflare; R2 has no egress
  fees, which matters because adoption and restore are download-heavy).
- Refs and CAS: one Cloudflare Durable Object per vault (strongly consistent, serializes CAS).
- API: a Worker at `vault.overdeck.ai` implementing `VaultStore` over HTTPS: `PUT/GET/HEAD
  /objects/:id`, `GET/PUT /refs/:name` with `If-Match: <version>`.
- Identity: GitHub OAuth, the same choice as PAN-2356 D-R2 and PAN-658. Each device gets a
  revocable device token. Accounts never gain decryption ability.
- Billing: Stripe subscription; quota enforced on stored bytes.
- The relay (Fly, PAN-2356 D-R1) and the vault (Cloudflare) are separate services that share the
  account system.

**Cost basis (for pricing).** From the operator's machine (an extreme user): about 30 GB of
native transcripts. A zstd level-3 sample (a 9.5 MB Claude JSONL → 2.16 MB) gives about 4.4×, so
about 7 GB stored before fork sharing. At R2's $0.015/GB-month that is about $0.10/month. Write
operations at a 5-minute sync cycle with 10 active agents for 8 h/day come to about 30k
writes/month, or about $0.14 at $4.50 per million. Raw cost for the heaviest realistic user is
under $0.50/month, so a $5/month tier with a generous cap (e.g. 50 GB stored) has a wide
margin. **Operator decision:** price, cap, and whether the vault is ever sold separately.

**Phase B requirements (to carry into the new issue):** HB-1 `overdeck://` backend passes the
same `VaultStore` contract tests as `git` and `dir`; HB-2 the server never receives plaintext
or the vault key (AC by traffic capture); HB-3 account deletion deletes all objects within 24 h;
HB-4 export: `pan vault migrate <new-backend>` copies every object and ref, so users are never
locked in; HB-5 web viewing, if ever built, decrypts in the browser with the key entered
locally and never uploads it.

## Out of Scope

- The hosted backend (Phase B, separate issue).
- Real-time co-presence, sharing with other people ([PAN-658](https://github.com/eltmon/overdeck/issues/658)), multi-user authorization ([PAN-2608](https://github.com/eltmon/overdeck/issues/2608)).
- Live control of sessions on other machines ([PAN-3762](https://github.com/eltmon/overdeck/issues/3762)).
- Saving agent runtime state, workspaces, Docker stacks, or terminal panes.
- Cost-history sync.
- Harnesses other than Claude Code and Codex for native adoption (they save and browse; adoption falls back to summary).
