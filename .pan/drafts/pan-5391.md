# PAN-5391: Editor bar offers a primary Merge while the PR's checks are still running (UNSTABLE treated as clean)

**Issue:** [PAN-5391](https://github.com/eltmon/overdeck/issues/5391) · Parent work: PAN-5191 (edit workspaces, D-F7 verdict table), PAN-5290 (editor bar, C-D6 polling) · Written against `a1e22e196f6`.

## 1. Glossary

- **Edit workspace** — a scratch git worktree on branch `scratch/edit-<stamp>` that the file explorer creates so the operator can edit files without touching the main checkout (PAN-5191).
- **Editor bar** — the one-line bar under a code pane header on a project or edit-workspace root. Component `WorkspaceBar` in `src/dashboard/frontend/src/components/explorer/edit/EditorBar.tsx`.
- **`mergeable`** — GitHub's `gh pr view --json mergeable` field: `MERGEABLE`, `CONFLICTING` or `UNKNOWN`.
- **`mergeStateStatus`** — GitHub's `gh pr view --json mergeStateStatus` field. Relevant values:
  - `CLEAN` — mergeable and every commit status / check passes.
  - `HAS_HOOKS` — mergeable with passing statuses; GitHub Enterprise pre-receive hooks exist.
  - `UNSTABLE` — mergeable, but at least one **non-required** check is pending or failing. On a repo with no required checks (such as `eltmon/overdeck`), a PR whose CI is still running reads `UNSTABLE`, not `BLOCKED`.
  - `BLOCKED` — required checks or reviews are not met.
  - `DIRTY`, `BEHIND`, `DRAFT`, `UNKNOWN` — see the D-F7 table.
- **Merge verdict** — `{ canMerge, reason }` computed by `mergeVerdict` (`src/dashboard/server/services/explorer/edit-workspace-gh.ts`). This issue adds a third field, `checksPassing`.
- **D-F7** — the merge verdict table decided in `.pan/drafts/pan-5191.md` §3.
- **C-D6** — the PAN-5290 decision that the status query refetches every 15 s only while GitHub is still deciding (`shouldPollPr`).
- **Amber state** (new) — the editor bar row for a PR that GitHub allows to merge but whose checks have not all passed (`canMerge && !checksPassing`).
- **`state-needs-you`** — the amber dashboard color token (`--state-needs-you`, `src/dashboard/frontend/src/index.css` line 207: `#d97706`). Tailwind class `bg-state-needs-you`.

## 2. Problem

`mergeVerdict` treats `UNSTABLE` like `CLEAN`:

```ts
// src/dashboard/server/services/explorer/edit-workspace-gh.ts, line 138
const MERGEABLE_STATUSES = new Set(['CLEAN', 'UNSTABLE', 'HAS_HOOKS']);
```

So seconds after a PR opens, while every CI job is pending, the editor bar shows the emerald "no conflicts" row with an enabled **primary** Merge:

> ● PR #5390 · no conflicts. Merging squashes it into `main`.  [View on GitHub] [Refresh] [Discard…] **[Merge]**

One click squash-merges an untested change into main, and nothing tells the operator the checks have not passed. The bar also stops polling once Merge is allowed, because `shouldPollPr` returns false whenever `pr.canMerge` is true:

```ts
// src/dashboard/frontend/src/components/explorer/edit/edit-workspace-http.ts, line 73
export function shouldPollPr(pr: EditWorkspacePr | null | undefined): boolean {
  if (!pr || pr.state !== 'OPEN' || pr.isDraft || pr.canMerge) return false
  return pr.mergeable === 'UNKNOWN' || pr.mergeStateStatus === 'UNKNOWN' || pr.mergeStateStatus === 'BLOCKED'
}
```

It never learns when the checks finish.

## 3. Decisions

The issue body decides the product behavior; this PRD keeps it and fills the gaps.

- **D-1 UNSTABLE stays mergeable.** GitHub allows the merge, so `canMerge` stays true and the server merge route (`src/dashboard/server/services/explorer/edit-workspace-pr.ts` line 145, `if (!pr.canMerge) throw new EditWorkspaceError('NOT_MERGEABLE', …)`) is unchanged. The client makes it a deliberate choice instead.
- **D-2 `checksPassing` truth table.** `checksPassing` is `true` only when `canMerge` is true **and** `mergeStateStatus` is `CLEAN` or `HAS_HOOKS`. It is `false` for `UNSTABLE` and for every `canMerge: false` verdict (merged, closed, draft, conflicting, blocked, behind, unknown, other). The issue defines only the three mergeable statuses; `false` elsewhere is the conservative default and the client never reads it when `canMerge` is false.
- **D-3 Contract field is required.** `EditWorkspacePr.checksPassing: boolean` is required, not optional. The dashboard server and frontend ship together, so there is no version skew to tolerate. Every typed fixture adds it.
- **D-4 Confirmation uses `shared/Modal`, not `useConfirm`.** `useConfirm` (`src/dashboard/frontend/src/components/DialogProvider.tsx`) throws outside `DialogProvider`, and `EditorBar.test.tsx` renders without one. The sibling dialogs (`DiscardDialog.tsx`, `CreatePrDialog.tsx`) build on `src/dashboard/frontend/src/components/shared/Modal.tsx` with `editDialog.module.css`. A new file `MergeAnywayDialog.tsx` follows that pattern.
- **D-5 Precedence: local blockers win.** The existing `blocked` chain in `WorkspaceBar` (`!pr.canMerge` reason → unsaved drafts → changes error → changes loading → uncommitted/unpushed) is evaluated first. The amber state applies only when `blocked === null`. A PR that is UNSTABLE **and** has unsaved or unpushed work shows today's disabled Merge with the local reason (live dot). Polling still runs in that case, because `shouldPollPr` looks only at the PR.
- **D-6 New dot key.** `BarDot` gains `'unchecked'`, mapped to `bg-state-needs-you`. The existing `'editing'` key uses the same class, but a separate key keeps `data-dot` meaningful in tests (`data-dot="unchecked"`).
- **D-7 The confirmation renders only while the amber state holds.** `WorkspaceBar` renders `MergeAnywayDialog` when `dialog === 'merge' && unchecked`. If a 15 s refetch turns the PR CLEAN (or non-mergeable) while the dialog is open, the dialog disappears and the bar shows the new state. No effect hook clears the `dialog` value; the next Create PR / Discard / Merge click overwrites it.
- **D-8 Merge anyway closes the dialog, then runs the existing `merge()`.** The bar's existing `merging` state shows "Merging…" on the Merge button. Errors toast through the existing `merge()` catch.
- **D-9 Polling for the amber state.** `shouldPollPr` returns true for an open, non-draft PR with `canMerge && !checksPassing`. A PR whose checks **fail** stays `UNSTABLE`, so the bar keeps polling `gh` every 15 s while it is mounted. That is the same cost `BLOCKED` already has; no backoff is added (NonGoal).
- **D-10 Exact strings.**
  - Amber sentence: `PR #N · no conflicts, but its checks have not all passed.` (rendered as `PR <Strong>#N</Strong> · no conflicts, but its checks have not all passed.`).
  - Dialog title: `Merge PR #N before its checks pass?`
  - Dialog body: `GitHub allows this merge, but the PR's checks have not all passed. Merging now squashes it into <defaultBranch> without waiting for them.` (`<defaultBranch>` in a `<code>` element).
  - Dialog buttons: **Cancel** (`styles.button`) and **Merge anyway** (`styles.primaryButton`).
  - Dialog test id: `merge-anyway-dialog`.

## 4. Requirements

### Functional

- **FR-1** `mergeVerdict` returns `{ canMerge: true, reason: null, checksPassing: true }` for an open, non-draft, `MERGEABLE` PR whose `mergeStateStatus` is `CLEAN` or `HAS_HOOKS`.
- **FR-2** `mergeVerdict` returns `{ canMerge: true, reason: null, checksPassing: false }` for the same PR with `mergeStateStatus` `UNSTABLE`.
- **FR-3** `mergeVerdict` returns `checksPassing: false` on every `canMerge: false` verdict, with `reason` unchanged.
- **FR-4** `EditWorkspacePr` (contract) carries `checksPassing: boolean`, and `GET /api/explorer/edit-workspaces/:workspaceId` returns it inside `pr`.
- **FR-5** `shouldPollPr` returns true for an open, non-draft PR with `canMerge: true, checksPassing: false`, and still returns false for a `CLEAN` PR (`checksPassing: true`), a draft, `DIRTY`, `BEHIND`, merged, or null.
- **FR-6** With `canMerge && !checksPassing` and no local blocker, the editor bar reads `PR #N · no conflicts, but its checks have not all passed.` with an amber (`data-dot="unchecked"`) dot.
- **FR-7** In that state **Merge** is enabled and rendered with `BUTTON` (outline), not `PRIMARY_BUTTON`.
- **FR-8** Clicking that Merge opens the confirmation dialog; only **Merge anyway** calls `mergeEditWorkspace`; **Cancel** closes it with no merge call.
- **FR-9** When a refetch reports `CLEAN` (`checksPassing: true`), the bar switches to today's emerald `PR #N · no conflicts. Merging squashes it into main.` row with a primary Merge that merges on one click (no dialog).
- **FR-10** `features/file-explorer.mdx` "Editing and PRs" describes the amber state, the confirmation and its **Merge anyway** button.

### Non-functional

- **NFR-1** No change to the server merge route, its error codes or the `gh` calls made per status read.
- **NFR-2** Delay-based tests use `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()`; never real 15 s waits (repo rule: fake timers for delay tests).
- **NFR-3** `EditorBar.tsx` stays under the 1,000-line file-size ceiling (`scripts/lint-file-size.sh`, `CEILING=1000`; the file is 487 lines today).
- **NFR-4** Frontend tests stay in `scripts/frontend-test-subset.txt` (CI runs only listed files). `EditorBar.test.tsx` is already listed (line 338). No new frontend test file is added.
