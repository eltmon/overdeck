## Goal

**Add an SSH machine** in Settings → Anywhere → Machines, or `pan machines add-ssh <host>`, makes this machine's dashboard server:

1. open an SSH session to the host (the server's own OpenSSH client, keys and `~/.ssh/config`);
2. check that the host has the same `pan` version as this machine;
3. adopt the Overdeck dashboard already running there, or start one with `pan up`;
4. forward a loopback port on this machine to the host's dashboard port;
5. pair over that forwarded port and save a machine link whose route has kind `ssh`.

Removing the machine stops the host's server only when this machine started it. Because the server runs SSH, an SSH machine can be added from any browser that can open this dashboard (epic D-13).

## Glossary

- **Linking machine:** the machine whose dashboard server runs `ssh` and holds the link. "Local" in this document.
- **SSH host:** the machine reached over SSH. "Remote" in this document. It runs its own Overdeck dashboard.
- **Destination:** what the operator typed: an `~/.ssh/config` alias (`desk`), `user@host`, a hostname, an IP, or `ssh://user@host:port`. It is passed to `ssh` unchanged, so every option in the linking machine's `~/.ssh/config` (User, Port, IdentityFile, IdentityAgent, ProxyJump, ProxyCommand, Include) applies.
- **SSH helper:** the hidden CLI verb `pan machines ssh-helper start|stop` that the linking server runs **on the SSH host** over SSH. It holds all remote-side logic in TypeScript, so the remote command line never contains operator input.
- **Helper result line:** the one stdout line the helper prints, starting with the sentinel `OVERDECK_SSH_HELPER ` followed by JSON. The local side ignores every other line (login-shell banners, profile output).
- **Launch marker:** the remote file `${OVERDECK_HOME}/ssh-launch/server.json` (0600) that the helper writes after it starts a server: `{ v: 1, pid, apiPort, version, startedAt, startedBy }`, where `startedBy` is the linking machine's environment id.
- **`managed` / `external`:** the launch kind of an SSH machine, from the linking machine's view. `managed` = this linking machine started the running server (marker `startedBy` equals our environment id **and** marker `pid` equals the pid `/api/health` reports). `external` = anything else (it was already running, another machine started it, or it was restarted since).
- **Remote lock:** the directory `${OVERDECK_HOME}/ssh-launch/lock` on the SSH host, created with `mkdir` (atomic). It serializes helpers from any number of linking machines. Stale after 180 s.
- **Local host lock:** an in-process lock in the linking server keyed by the normalized destination. Two add/remove/reconnect operations for the same destination never overlap.
- **Forward:** the long-running child `ssh -N -L 127.0.0.1:<localPort>:127.0.0.1:<remotePort> -- <destination>` owned by the linking server.
- **Forward supervisor:** the server service that keeps one forward per SSH machine running, restarts it with back-off, and reports its state.
- **SSH machine record:** one entry in the local file `${OVERDECK_HOME}/ssh-machines.json` (0600): destination, link id, environment id, local port, remote port, launch kind, optional pan path.
- **`ssh` route:** a link route `{ url: 'tcp://127.0.0.1:<localPort>', kind: 'ssh', source: 'pairing' }`. `ROUTE_KINDS` already contains `ssh` (`packages/contracts/src/machines.ts:18`).
- **Pinned version:** the SSH host's `pan --version` must equal this machine's version exactly. Anything else is the explicit `version-mismatch` error, which names both versions and the install command. Nothing is installed or upgraded automatically.
- **Secure channel, machine link, link supervisor, route ranking:** as defined in `.pan/drafts/PAN-4645.md` and `docs/ANYWHERE-ARCHITECTURE.md`.

## What exists today (verified at `1c20fe2c38b`)

- **Route model.** `src/lib/anywhere/routes.ts`: `routeFromPairingUrl()` (search `export function routeFromPairingUrl`) turns `http://h:p/#pair=odp_…` into `tcp://h:p` and refuses a loopback host unless `allowLoopback`, then classifies loopback as `lan`. There is no way to create a route with kind `ssh`. The module header says "`ssh`, `direct` and `relay` arrive in #4404 and #2356". `rankRoutes()` orders `lan < tailnet < ssh < public < direct < relay`.
- **Link creation.** `createMachineLink(input, overrides)` in `src/dashboard/server/services/machine-link-service.ts` (search `export async function createMachineLink`) takes only `{ pairingUrl, bothWays, access, allowLoopback }`. Step 1 is `routeFromPairingUrl`. Step 7 stores `[pairingRoute]` merged with the peer's advertised endpoints (`mergeAdvertised`).
- **Link store.** `src/lib/anywhere/link-store.ts` owns `${OVERDECK_HOME}/machine-links.json` (0600, temp file + rename, in-process write queue). `upsertLink` rebuilds each record from explicit fields, so it cannot carry SSH data. `setLinkRoutes(id, routes)` replaces a route list.
- **Machines routes.** `src/dashboard/server/routes/machines.ts`: `POST /api/machines/link`, `GET /api/machines` (`buildMachinesResponse`), `DELETE /api/machines/:id` (`handleMachinesUnlink`), `POST /api/machines/:id/reconnect`, `POST /api/machines/:id/routes`, `DELETE /api/machines/inbound/:tokenId`, `DELETE /api/machines/self`. Every operator route refuses requests that arrive through a secure channel (`refuseChannel`, search `function refuseChannel`). The layer is merged in `src/dashboard/server/server.ts` (search `machinesRouteLayer,`).
- **Boot.** `startAnywhere({ primary })` in `src/dashboard/server/services/anywhere-boot.ts` starts the link supervisor only on the primary dashboard (`hostsMachineLinks()`, `src/dashboard/server/main.ts:224`). `stopAnywhere()` tears it down.
- **Link supervisor.** `LinkSupervisor` (`src/dashboard/server/services/link-supervisor.ts`) probes every route of a link in parallel (2.5 s), keeps the best answering one, and re-checks better routes every 60 s. It has `updateRoutes(linkId, routes)` and `reconnect(linkId)`.
- **CLI.** `src/cli/commands/machines.ts` registers `pan machines link|list|unlink` (search `export function registerMachinesCommands`); `src/cli/commands/pair.ts` calls it. CLI verbs call the dashboard with the internal token through `callDashboard` (`src/cli/commands/dashboard-call.ts`).
- **`pan pair`.** `POST /api/pairing/credentials` with the internal token returns `{ credential, expiresAt }` (one use, 10 minutes, in memory).
- **`pan up`.** `defineUpCommand` (`src/cli/commands/dashboard-lifecycle-commands.ts:15`) has `--detach`, `--no-open` (honored at `src/cli/index.ts:814`, `if (options.open === false) return;`) and `--skip-traefik`. The detached branch (`src/cli/index.ts:908`) spawns `dist/dashboard/server.js`, waits for `/api/health`, and exits. `pan up` reads its ports from `${OVERDECK_HOME}/config.toml` (`readPlatformConfig()`, `src/lib/platform-lifecycle.ts:132`; `dashboard.api_port`, default 3011).

- **Frontend.** `src/dashboard/frontend/src/components/Settings/anywhere/MachinesPanel.tsx` (305 lines) lists links with a **Link a machine** button that opens `LinkMachineDialog.tsx`; `machinesApi.ts` holds the fetchers.
- **Plain-HTTP guard and trusted origins do not apply.** The forwarded port carries only the secure channel (first byte `0x00`), which the channel dispatcher accepts on the dashboard port. No browser ever talks to the forwarded port, so the old requirement to add `http://127.0.0.1:<localPort>` to `OVERDECK_TRUSTED_ORIGINS` (previous issue body) is retired (D-4404-12).
- **`pan pair` on npx machines** ([PAN-4628](https://github.com/eltmon/overdeck/issues/4628)) is fixed (issue closed).
- **No SSH code exists** for machines. `src/lib/remote/` is Fly-specific and is not touched.

## Requirements

### Functional

- **FR-1 Add an SSH machine.** `POST /api/machines/ssh { host, panPath?, bothWays?, access? }`, the **Add an SSH machine** dialog and `pan machines add-ssh <host>` run the add flow (D-4404-3) and return the new link view with an `ssh` block. The link's first route is the `ssh` route; the peer's advertised endpoints are merged as for any link.
- **FR-2 Pinned version.** Before running the helper, the add flow runs `pan --version` on the host. A different version fails with `version-mismatch`; a missing `pan` fails with `pan-missing`. Both messages name this machine's version and the command `npm install -g @overdeck/core@<local version>`. Nothing is installed.
- **FR-3 Start or adopt.** The helper adopts a dashboard that answers `/api/health` on the host's configured API port (`external`, or `managed` when the marker proves it). Otherwise it runs `pan up --detach --no-open --skip-traefik`, waits for health, writes the launch marker and reports `managed`.
- **FR-4 Pair over the forward.** The helper mints a pairing credential from the host's own dashboard and returns it inside the SSH session. The linking server opens the forward and links over `tcp://127.0.0.1:<localPort>` with that credential (Noise XXpsk0, unchanged from PAN-4645).
- **FR-5 Stop only what you started.** Removing an SSH machine (`DELETE /api/machines/:id`, `pan machines unlink`, **Remove**) runs `ssh-helper stop` only when the record's launch kind is `managed` and the operator did not ask to keep the server. The helper stops the server only when the marker still proves this machine started it, and only when no other machine holds an active link to it.
- **FR-6 Per-host lock.** At most one add/remove/reconnect runs per destination in the linking server (local host lock, `busy` error), and at most one helper runs per SSH host (remote lock).
- **FR-7 Forward supervision.** The primary dashboard keeps one forward per SSH machine record: started at boot, restarted with back-off after it exits, stopped at shutdown and on removal. Authentication and host-key failures stop retries and show `attention` until the operator reconnects.
- **FR-8 Reconnect.** `POST /api/machines/:id/reconnect` on an SSH-backed link restarts its forward and runs `ssh-helper start --no-pair`, which adopts or starts the server again without minting a credential, then asks the link supervisor to reconnect.
- **FR-9 Test.** `POST /api/machines/ssh/test { host, panPath? }`, the dialog's **Test** button and `pan machines test-ssh <host>` run only the version probe and report `{ reachable, panVersion, versionMatches }`. They never start, stop or pair anything.
- **FR-10 SSH config suggestions.** `GET /api/machines/ssh/config-hosts` lists the concrete `Host` aliases (no `*`, `?` or `!`) from the linking machine's `~/.ssh/config` and the files it `Include`s. The dialog offers them as suggestions. Nothing is imported or written.
- **FR-11 SSH state on the machine row.** `GET /api/machines` adds an optional `ssh` block to each SSH-backed link view: destination, launch kind, forward state and detail, local and remote port. The Machines panel and `pan machines list` show it.
- **FR-12 Typed errors.** Every failure returns `{ error: <SshMachineErrorCode | MachineLinkErrorCode>, message }` with a fixed HTTP status (D-4404-9). The dialog and CLI print the message.

### Non-functional

- **NFR-1 Async only.** All SSH, helper and forward process work in server-reachable code uses async `spawn`/`execFile` with timeouts. No `execSync`, no `*Sync` tmux calls, no new sync file reads in server code (epic NFR-7).
- **NFR-2 No shell injection.** `ssh` is spawned with an argv array, never a shell. The destination is validated and placed after `--`. The remote command string is built only from fixed tokens, a UUID and a validated absolute pan path (D-4404-4).
- **NFR-3 Host keys are the operator's.** Every `ssh` call uses `-o BatchMode=yes` and never `StrictHostKeyChecking=no` or `accept-new`. An unknown or changed host key fails with `host-key` and tells the operator to run `ssh <destination>` once in a terminal on this machine.
- **NFR-4 No plaintext.** The forward carries only the secure channel; the pairing credential travels only inside SSH and is never logged (epic NFR-1).
- **NFR-5 Bounded waits.** Version probe 20 s, helper `start` 150 s, helper `stop` 45 s, forward ready 15 s. The add request answers within 210 s in the worst case.
- **NFR-6 Fake timers.** Every test of back-off, lock waits, health polling or stop escalation uses `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`.
- **NFR-7 Credentials stay put.** The linking server's SSH keys never leave it. The helper result never carries a token other than the one-time pairing credential.

## Decisions (made here; the executor does not revisit them)

- **D-4404-1 The remote half is a hidden `pan` verb.** `pan machines ssh-helper start|stop` (registered with `{ hidden: true }`) runs on the SSH host. Shell templates sent over SSH are not used. This keeps lock, marker, adopt-or-start, pairing and stop logic in tested TypeScript, and makes the pinned-version check sufficient for protocol compatibility.
- **D-4404-2 Exact version pin.** The host's `pan --version` (the last stdout line matching `^\d+\.\d+\.\d+(?:-[0-9A-Za-z.-]+)?$`, so login-shell banners and update notices are ignored; no such line ⇒ `helper-failed`) must equal `getOverdeckVersion()` on the linking server (`src/dashboard/server/routes/misc/shared.ts:39`). The running server's version is reported but not pinned: link compatibility is already enforced by `createMachineLink` (`requireLinkCapable`). Upgrades are W-LINK7 ([PAN-4654](https://github.com/eltmon/overdeck/issues/4654)).
- **D-4404-3 The add flow, in order.**
  1. Validate the destination (`validateSshDestination`); take the local host lock.
  2. Version probe: `ssh … -- <dest> <remote "pan --version">`, timeout 20 s.
  3. Helper start: `ssh … -- <dest> <remote "pan machines ssh-helper start --linker <ourEnvId> --json">`, timeout 150 s. Parse the helper result line.
  4. If the helper's `environmentId` equals ours ⇒ `self-link` (stop the server again first if the helper reported `managed`).
  5. Pick a free loopback port (`listen(0)` on `127.0.0.1`, read the port, close) and write a **provisional** SSH machine record: `linkId: null`, that port, the helper's `apiPort` as `remotePort`, the helper's `launch`.
  6. `forwardSupervisor.ensure(record.id)`: start the forward and wait until the local port accepts a TCP connection (15 s). Then read the port back from the record (a port collision during this first start may have moved it, D-4404-10).
  7. `createMachineLink({ transport: { url: 'tcp://127.0.0.1:<localPort>', kind: 'ssh', pairingCode }, bothWays, access })`.
  8. `updateSshMachine(record.id, { linkId: link.id, environmentId })`; remove any older record with the same environment id (re-adding replaces, matching D-4645-18), stopping that record's forward but never its server.
  9. Release the lock and return the link view.

  **Rollback:** a failure after step 5 stops the forward and deletes the provisional record; if the helper reported `managed`, it also runs `ssh-helper stop --linker <ourEnvId>` (best effort, 45 s) so a failed add leaves no server it started. A record that still has `linkId: null` when the forward supervisor starts (the dashboard died mid-add) is deleted and gets no forward.
- **D-4404-4 The remote command string.** sshd hands the command to the user's login shell with `-c`. To get a login environment (nvm, `~/.local/bin`) in any shell, including fish, the string is always:

  ```
  sh -c 'exec "${SHELL:-/bin/sh}" -lc "<PAN> <ARGS>"'
  ```

  `<PAN>` is `pan` or the record's `panPath` (must match `^/[A-Za-z0-9._/-]{1,255}$`). `<ARGS>` is one of `--version`, `machines ssh-helper start --linker <uuid> --json`, `machines ssh-helper start --linker <uuid> --no-pair --json`, `machines ssh-helper stop --linker <uuid> --json`. `<uuid>` must match the environment-id UUID pattern. `remoteCommand()` throws on anything else, and a unit test asserts no other characters can reach the string.
- **D-4404-5 SSH options.** Base argv for every call: `['-T', '-o', 'BatchMode=yes', '-o', 'ConnectTimeout=10', '-o', 'ServerAliveInterval=15', '-o', 'ServerAliveCountMax=3']`. Commands append `['--', dest, remoteCommand]`. The forward uses the base without `-T`, plus `['-N', '-o', 'ExitOnForwardFailure=yes', '-L', '127.0.0.1:<lp>:127.0.0.1:<rp>', '--', dest]`. `ssh` is resolved from `PATH` (the smoke test relies on this).
- **D-4404-6 Destination grammar.** Accepted: `^(?:ssh://)?(?:[A-Za-z0-9._-]+@)?(?:[A-Za-z0-9._-]+|\[[0-9A-Fa-f:.]+\])(?::[0-9]{1,5})?$`, length ≤ 255, not starting with `-`, and a `:port` suffix only with the `ssh://` prefix. The lock key is the destination lowercased without `ssh://`.
- **D-4404-7 Launch marker and adopt rule.** The helper reads the API port with `readPlatformConfig().dashboardApiPort` (the same source as `pan up`) and polls `GET http://127.0.0.1:<apiPort>/api/health`. If it answers 200: launch is `managed` when the marker exists, `marker.startedBy === --linker` and `marker.pid === health.pid`; otherwise `external`. A marker whose pid differs from the health pid is stale and is deleted. If health does not answer, the helper spawns `process.execPath [process.argv[1], 'up', '--detach', '--no-open', '--skip-traefik']` with `stdio: ['ignore', 'pipe', 'pipe']` (never `inherit`: a sidecar that `pan up` leaves running would otherwise hold the SSH session's stdout open and hang the add until its timeout), waits for the child's `exit` event, not `close` (120 s), polls health every 500 ms for up to 30 s, writes the marker with the health pid and reports `managed`. No health ⇒ `start-failed` with the last 20 output lines.
- **D-4404-8 Stop rule.** `ssh-helper stop --linker <uuid>` under the remote lock:
  1. no health ⇒ `{ stopped: false, reason: 'not-running' }` (marker deleted);
  2. no marker, or `startedBy !== linker` ⇒ `reason: 'external'`;
  3. `marker.pid !== health.pid` ⇒ `reason: 'restarted'` (marker deleted);
  4. `GET /api/machines` on the host (internal token) lists an active inbound machine whose `environmentId !== linker` ⇒ `reason: 'in-use'`, so another machine's link is never broken;
  5. otherwise `SIGTERM` to the pid, poll every 250 ms for 10 s, then `SIGKILL` if it is still alive; delete the marker; `{ stopped: true, reason: 'stopped' }`.

  Only the dashboard process is signalled. Sidecars that `pan up` started (supervisor, CLIProxy) are left running and the docs say so. `pan down` is not used: it also stops Traefik and review sessions, which this machine did not start.
- **D-4404-9 Error codes and HTTP status.** `SshMachineErrorCode` = `bad-destination` 400, `busy` 409, `unresolvable` 502, `unreachable` 502, `host-key` 409, `auth-failed` 401, `pan-missing` 424, `version-mismatch` 409, `helper-failed` 502, `start-failed` 502, `forward-failed` 502, `self-link` 409, `not-found` 404. `MachineLinkError` codes keep their existing statuses. `classifySshFailure(exitCode, stderr)` maps: `Host key verification failed` or `REMOTE HOST IDENTIFICATION HAS CHANGED` ⇒ `host-key`; `Permission denied` ⇒ `auth-failed`; `Could not resolve hostname` ⇒ `unresolvable`; `Connection refused|Connection timed out|No route to host|Network is unreachable|Operation timed out` or a local timeout ⇒ `unreachable`; exit 127, `command not found` or `pan: not found` ⇒ `pan-missing`; anything else ⇒ `helper-failed` with the last 5 stderr lines.
- **D-4404-10 Forward supervisor states and back-off.** States `starting | up | down | attention`. On exit while not stopping: `auth-failed` or `host-key` ⇒ `attention` (no retry); stderr containing `Address already in use` or `cannot listen to port` ⇒ pick a new free port, replace the link's `ssh` route through `setLinkRoutes` and `LinkSupervisor.updateRoutes`, update the record, retry at once; anything else ⇒ `down`, retry after 1 s doubling to 60 s with ±20 % jitter. The attempt counter resets after a forward stays up 60 s. The forward pid is recorded in the SSH machine record; at boot, a recorded pid that is alive and whose command line (`ps -o args= -p <pid>`, async) contains `-L 127.0.0.1:<localPort>:` is sent `SIGTERM` before a new forward starts.
- **D-4404-11 Where it runs.** The forward supervisor starts in `startAnywhere` exactly where the link supervisor starts (primary only) and stops in `stopAnywhere`. The SSH routes refuse requests that arrive through a secure channel, like every other operator machines route, and need the operator credential (`rejectUnsafeDashboardMutationRequest` for POST, `rejectUnauthorizedDashboardRequest` for GET). They are not listed in `route-scopes.ts`, so a machine token (no `admin`) can never call them.
- **D-4404-12 No trusted-origin change.** The previous issue body's `OVERDECK_TRUSTED_ORIGINS` requirement is retired: no browser connects to the forwarded port.
- **D-4404-13 Link both ways by default.** As for `pan machines link`. The host's link back uses this machine's advertised endpoints; if the host cannot reach them (a VPS behind NAT reaching a laptop), that reverse link shows `offline` on the host. A reverse SSH forward (`-R`) is a non-goal.
- **D-4404-14 Better routes win.** The `ssh` route ranks after `lan` and `tailnet`. When the host advertises a LAN or Tailscale endpoint this machine can reach, the link supervisor moves to it within 60 s (epic D-10). The forward keeps running as the fallback.
- **D-4404-15 The add request is synchronous.** One `POST` that answers when the machine is linked or a step failed. The dialog shows a spinner with the text "Connecting to <host>. Starting Overdeck there can take a minute." Streaming per-step progress is a non-goal.
- **D-4404-16 #3863 scope.** This PR closes [PAN-3863](https://github.com/eltmon/overdeck/issues/3863) with its scope cut to what machine links make necessary: add, test, remove (with the keep-server choice), reconnect, state on the row, and SSH config aliases as suggestions. Its direct-SSH mode (SFTP, remote git, Herdr terminal inventory over raw SSH), config import with preview, terminal retention and reset, and the Share/Cloud surfaces are dropped: a linked machine runs its own full Overdeck, and remote control of its conversations and terminals arrives through the link ([PAN-4650](https://github.com/eltmon/overdeck/issues/4650), [PAN-4651](https://github.com/eltmon/overdeck/issues/4651)).

## Non-goals

- Installing or upgrading `pan` or Node on the SSH host, or using `npx` there.
- Accepting an unknown or changed host key from the browser, `StrictHostKeyChecking=no` or `accept-new`.
- Password, keyboard-interactive or MFA prompts (BatchMode only).
- A reverse SSH forward so the host can reach this machine.
- Restarting a dead remote server in the background; only an explicit Reconnect starts it again.
- Stopping sidecars (`pan down` effects) on the SSH host.
- Per-step progress streaming for the add request.
- #3863's direct-SSH mode (SFTP, remote git, Herdr terminal inventory over raw SSH), SSH config import with preview, terminal retention/reset, and the Share/Cloud surfaces.
- The desktop app running SSH (the previous body's desktop-managed launch).
- Windows SSH hosts or a Windows linking machine (untested; the docs say Linux and macOS).
- Real-OpenSSH or Docker end-to-end tests in CI.
