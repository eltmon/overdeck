# PAN-5224: Cut GitHub API polling — webhooks drive PR freshness, polling is the fallback

**Issue:** [PAN-5224](https://github.com/eltmon/overdeck/issues/5224)
**Planned:** 2026-11-14, auto mode, against `main` at `99517e495ab`.

## Glossary

- **Quota bucket** — GitHub's hourly allowance per credential *pool* and API *bucket*. Pools: `user` (the operator's `gh` token), `app` (the GitHub App installation token), `pat` (a tracker PAT). Buckets: `graphql` (points, 5,000/h) and `rest` (calls, 5,000/h). The ledger in `~/.overdeck/github-quota/ledger-<YYYYMMDDHH>.jsonl` records every metered call with `caller`, `pool`, `bucket`, `cost`, `ts`, `pid` (`src/lib/github-quota/ledger.ts`).
- **Caller** — the name a metered call is billed to (`runGh(..., { caller })` or `withGitHubCaller(name, fn)`, `src/lib/github-quota/run-gh.ts`, `caller-context.ts`). This issue targets `pr-cache` and `pipeline-membership`.
- **PR listing** — the per-repo `gh pr list` cache in `src/lib/overdeck/pr-listing.ts`: an *open read* (every field, estimated 3 points per call) and a *closed read* (no `statusCheckRollup`/`reviewRequests`/`mergeable`, estimated 1 point). Keyed by project path. Caller `pr-cache`.
- **Active tier / idle tier** — the open read's TTL depends on its content: a listing with at least one OPEN row uses the *active* TTL (today `PR_CACHE_TTL_MS` = 30 s); a listing with no OPEN row, and the closed read, use the *idle* TTL (today `PR_CACHE_IDLE_TTL_MS` = 5 min).
- **Membership PR snapshot** — a second, separate open-PR cache: `listOpenPullRequestsSnapshot(owner, repo)` in `src/lib/pipeline-membership-gather.ts` (REST `repos/<o>/<r>/pulls?state=open`, 30 s TTL, caller `pipeline-membership`). Read by every membership gather, by resource discovery (`src/dashboard/server/services/resource-discovery.ts` `loadOpenPullRequests`) and by agent GC (`src/lib/cloister/agent-gc.ts`).
- **Membership gather** — `gatherProjectLensSignals(project)` (`pipeline-membership-gather.ts`): one project's tracker issues, phase-labelled issues (5 REST listings), open PRs, branch refs, specs, issue states (GraphQL) and merged heads (GraphQL). Caller `pipeline-membership`.
- **Periodic convergence** — `startProjectResourceConvergence` (`src/dashboard/server/services/project-resource-refresh-queue.ts`): every 5 min, every project is enqueued with reason `periodic-convergence`, and that reason re-gathers membership.
- **Webhook relay** — the `smee-client` process that forwards GitHub App webhooks from smee.io to `POST /api/webhooks/github` (`src/lib/smee.ts`, `src/dashboard/server/routes/webhooks.ts`). Its health is the system-health service row `id: 'smee-relay'`, `label: 'Webhook relay'`, `status: 'running' | 'not_configured' | 'stopped' | 'unavailable'` (`src/dashboard/server/services/system-health-v2.ts` `serviceHealth`), sampled every 15 s (`src/lib/system-health/config.ts` `pollSeconds: 15`). **This is the existing webhook-health signal; this issue adds no new one.**
- **Webhooks healthy** — true only in the primary dashboard process, and only while the last accepted system-health sample has the `smee-relay` row with `status === 'running'`. Everything else (relay stopped, not configured, unavailable, no sample yet, peer dashboard, deacon, CLI) is **not healthy**, which keeps today's cadence.
- **Webhook-covered repo** — a repo whose GitHub App installation actually delivers webhooks to this machine. Verified on 2026-11-14: only `eltmon/overdeck` delivers (the dashboard log holds 191,485 `check_run`, 44,969 `check_suite`, 4,771 `status`, 3,368 `pull_request`, 1,351 `pull_request_review`, 238 `pull_request_review_thread` receipts, all from `eltmon/overdeck`, and zero `issues` receipts). The App is not installed on the other 8 tracked repos (`~/.overdeck/github-quota/repo-notes.json`).
- **Coalescer** — the new per-repo throttle (WI-6) that turns a burst of webhooks into a bounded number of listing invalidations plus derived-state refreshes.

### Root causes (verified)

1. **`pr-cache` is the 30 s active tier, not the idle tier.** Splitting the dashboard pid's `pr-cache` rows by cost: about 7 open reads (cost 3) per minute steadily, spiking to about 14 every 5 minutes, plus about 1 closed read (cost 1) per minute. Only three repos have open PRs (`gh api repos/<r>/pulls?state=open`): `stablyai/orca` (100), `eltmon/lexerra` (2), `eltmon/overdeck` (2). Three repos × 2 reads/min × 3 points = 1,080 points/h. That is the active tier. The idle tier (6 repos with no open PR, every 5 min, plus closed reads) adds roughly 300 points/h. The cache is lazy (`createSettledTtlPromiseCache`, `src/lib/concurrency.ts`), so the cadence is set by the TTL, because readers ask far more often than every 30 s: `IssueDataService.pushUpdated` → `scheduleDerivedStateRefreshForIssues(all cached issues)` on every tracker poll that changed, `pull-request-sync-service.ts` every 60 s, the auto-merge scheduler, and every dashboard route that calls `loadIssueStatesForProject`.
2. **`pipeline-membership` re-gathers every project every 5 minutes.** `MEMBERSHIP_REFRESH_REASONS` in `project-resource-refresh-queue.ts` contains `periodic-convergence`, so each 5-minute convergence tick (staggered over 4 minutes) runs a full gather per project. A gather on a repo without the App costs about 7 REST calls (`listOpenIssues` + 5 phase-label listings via `gh api`, `pipeline-membership-app-fallback.ts`, plus the membership PR snapshot) and about 2 GraphQL calls (issue states, merged heads). Nine GitHub projects × 12 gathers/h × 7 ≈ 756 REST/h, which matches the measured ~710/h across user and app pools. The steady per-minute REST trickle is the staggered convergence plus the membership PR snapshot's 30 s TTL being re-read by resource discovery on every `agent.*` resource refresh.
3. **Webhooks already arrive but only refresh a narrow set of things.** `src/lib/webhook-handlers.ts`: `handlePullRequest` invalidates the listing only for `opened|closed|reopened|ready_for_review` (line 318, `refreshIssuePullRequestStateNow(issueId)` at line 334); `handlePullRequestReview`, `handleCheckSuite`, `handleCheckRun` and `handleStatus` only call `bumpIssuePrTabCacheGeneration` and never invalidate the listing. The non-failing check handlers return early when `pull_requests` is empty (lines 220–223, 264–267).
4. **An invalidation that lands during an in-flight read is lost.** `createSettledTtlPromiseCache.invalidate(key)` (`src/lib/concurrency.ts` line 86) deletes only settled entries: `if (entries.get(key)?.settledAt !== null) entries.delete(key);`. A webhook that arrives while a read is in flight leaves the pre-event result cached for a full TTL. At 30 s this was tolerable; at 5 minutes it is a freshness bug.

## Requirements

### Functional

- **FR-1** — While webhooks are healthy, the PR listing's active-tier TTL is 5 minutes, and the idle-tier and closed-read TTL is 15 minutes. While webhooks are not healthy, the TTLs are today's: 30 s active, 5 min idle and closed. A listing that holds any OPEN row whose `mergeable` is `UNKNOWN` keeps the 30 s TTL in both states, because GitHub computes mergeability asynchronously and no webhook announces the settled value.
- **FR-2** — A `pull_request` (any action), `pull_request_review` (any action), `check_suite` (any action), `check_run` (`created`, or `completed` with a failing conclusion) or `status` webhook for a tracked repo invalidates that repo's PR listing (open and closed reads) and its membership PR snapshot, and schedules a derived-state refresh for the issue ids the payload names, through the coalescer (FR-6). An invalidation that lands during an in-flight read discards that read's result for later callers.
- **FR-3** — The membership PR snapshot uses the same health-dependent active TTL as FR-1 (5 min healthy, 30 s otherwise).
- **FR-4** — Periodic convergence re-gathers a project's membership only when its membership snapshot is older than the membership fallback interval: 30 minutes while webhooks are healthy and the project's tracker is GitHub, 5 minutes otherwise (today's behavior). Every other membership-refresh reason (boot-warm, closed-out, `pull_request:*`, the new tracker reason) still refreshes immediately.
- **FR-5** — A tracker poll that changes an issue's state or its labels, including an issue that drops out of the tracker rows, enqueues a membership-refreshing resource refresh for that issue's project, with reason `tracker:issues-changed`. Changes to any other field (title, body, updatedAt only) do not. The comparison baseline is the unfiltered issue set (`getIssues({ cycle: 'all' })`) taken before the first live update, so the first live change is caught.
- **FR-6** — The coalescer fires a repo's refresh at once when that repo has not fired in the last 6 seconds; otherwise it schedules exactly one trailing fire at `lastFire + 6 s`, carrying the union of issue ids seen meanwhile. Two fires of one repo are always at least 6 s apart, so any half-open 60-second window `[t, t + 60 s)` holds at most 10 fires.
- **FR-7** — Overdeck's own actions invalidate the listing regardless of webhook coverage: the review door (already, `review-pipeline.ts` line 266), a journaled `review.verdict` APPROVED (already, `issue-pr-refresh.ts` line 27), and a journaled `merge.completed` (new). The review door and `merge.completed` also invalidate the repo's membership PR snapshot and then enqueue a membership-refreshing resource refresh. The `pull_request` webhook's existing membership refresh (`opened|closed|reopened|ready_for_review`) also invalidates the membership PR snapshot first.
- **FR-8** — Merge-time decisions keep reading the PR per issue through `getPrFacts` (`src/lib/cloister/pr-facts.ts`), never the listing; this issue changes neither `getPrFacts`, its 60 s cache, nor the merge gate.
- **FR-9** — Webhook health is read from the existing system-health `smee-relay` row in the primary dashboard only, and only from a sample whose freshness is `fresh` and whose `observedAt` is at most 60 s old; a `measuring` or `stale` sample reads as not healthy. The library default (deacon, CLI, peer dashboard) is "not healthy".

### Non-functional

- **NFR-1** — Idle-dashboard GitHub use is under 15% of the **user** pool's GraphQL bucket and under 15% of the **user** pool's REST bucket, measured over a clean 30-minute window (no dashboard reload inside it) with the usual open PRs, per the recipe in WI-12. The App-pool REST figure is recorded beside it.
- **NFR-2** — While webhooks are healthy, a PR, review or check change on a webhook-covered repo reaches the dashboard's derived issue state within 10 seconds of the webhook's arrival (coalescer ≤ 6 s + one open read). On repos without webhook coverage, the bound is the fallback TTL (5 minutes).
- **NFR-3** — No new GitHub caller, no new health signal, no new config key, no new persisted state. All new state is process memory.
- **NFR-4** — Every TTL, poll-interval and coalescer test uses `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()` (repo rule `fake-timers-for-retry-tests`). No real `setTimeout` waits in tests.
- **NFR-5** — No sync exec in server code (repo rule `no-execsync-server`); the health check reads the in-memory sampler snapshot only.
- **NFR-6** — No file grows past the 1,000-line ceiling or its `scripts/file-size-allowlist.txt` cap. `src/dashboard/server/main.ts` is at 981 lines, so it gains at most 3 lines. `src/dashboard/server/services/issue-data-service.ts` is at 1,748 lines against its 1,754 cap (the last allowlist row wins), so it gains at most 6 lines, all in WI-13.
- **NFR-7** — A derived-state refresh that started before a webhook invalidation never overwrites the result of a refresh that started after it (WI-13).

## Decisions (made here; do not re-decide)

- **D-1 — The poll tier is chosen by the global relay signal, not per repo.** Only `eltmon/overdeck` delivers webhooks, but `stablyai/orca` and `eltmon/lexerra` produce two-thirds of the 30 s tier's spend. Keeping uncovered repos at 30 s spends ~14% of user GraphQL on those two alone, so NFR-1 cannot be met that way. FR-1's instruction is to reuse the existing signal, and that signal is the relay. `isAppMarkedNotInstalled` (`src/lib/github-quota/repo-notes.ts`) is not used for the tier: its marks expire after 6 hours and were observed unrenewed past expiry, so it cannot stand in for coverage. Consequence: on uncovered repos PR state lags up to 5 minutes (was 30 s); the PR body says so and recommends installing the App on repos the operator owns.
- **D-2 — Membership fallback depends on the tracker.** GitHub-tracker projects (`tryResolveProjectTrackerType(project) === 'github'`) use 30 minutes while healthy. Other trackers (Linear, Jira, GitLab-backed) keep the 5-minute convergence, because their tracker has no webhook into Overdeck; their GitHub cost is small (lexerra only).
- **D-3 — NFR-1 is scoped to the user pool.** The issue reports "user-pool pace". The App pool's dominant spender is `close-out`, a separate subsystem (closed-issue reaper). Follow-up [PAN-5227](https://github.com/eltmon/overdeck/issues/5227) covers it; this PR reports the App figure but does not change it.
- **D-4 — Tracker trigger comes from the issue poller, not an `issues` webhook.** Zero `issues` webhooks have ever been received (the App does not subscribe to Issues). The trigger diffs the unfiltered issue set (`getIssues({ cycle: 'all' })`) per identifier (state + labels, plus disappearance), never by array index, because `createIssueDelta` (`packages/contracts/src/issue-delta.ts`) is index-based and an insertion would mark every row changed. It is seeded from the pre-subscription snapshot.
- **D-5 — Webhook health is injected, the library default is "not healthy".** Only the process that receives `POST /api/webhooks/github` can invalidate, so only the primary dashboard (not a peer, not the deacon, not a CLI) registers the healthy provider. Peer dashboards read the same smee pidfile, so registration is gated on `!isPeerDashboard`.
- **D-6 — In-flight invalidation is opt-in on the cache primitive.** `invalidate(key, { includeInFlight: true })` deletes the entry even while its load runs; existing callers keep today's semantics. Callers awaiting the in-flight promise still receive its value; the next `get` starts a fresh load.
- **D-7 — Coalescer spacing is 6 s.** Leading edge immediate, one trailing fire. Worst case 10 fires/min/repo; freshness worst case ≈ 6 s + one open read (~1 s on `eltmon/overdeck`), inside NFR-2.
- **D-8 — `check_run` filtering.** `check_run` makes up ~80% of receipts. Only `created` (checks start, aggregate → pending) and `completed` with a conclusion in `FAILING_CHECK_CONCLUSIONS` (red early) trigger. A successful `check_run` does not; the aggregate turns green when its `check_suite` completes, which triggers.
- **D-9 — Conversation PR chips stay on the 60 s sweep.** `pull-request-sync-service.ts` keeps `PR_SYNC_INTERVAL_MS = 60_000`; after a webhook invalidation its next sweep reads fresh. NFR-2's 10 s bound applies to derived issue state, not to conversation PR chips.
- **D-10 — Before/after measurement.** The before numbers are the table above. The work agent cannot deploy (deploys are the Flywheel's `pan reload`), so the PR body carries the before table, the budget model, and an unchecked "after" checkbox with the WI-12 recipe; the after numbers are posted as a PR comment after the Flywheel reloads the dashboard with this change.

## Work items

### WI-1 — In-flight invalidation on the settled TTL cache

**Why:** root cause 4; FR-2, D-6.
**Files:** `src/lib/concurrency.ts`, `tests/unit/lib/concurrency.test.ts`.

Change `SettledTtlPromiseCache.invalidate` to accept an optional options object.

Before (`src/lib/concurrency.ts`, grep `get.invalidate = (key?: K): void`):

```ts
  get.invalidate = (key?: K): void => {
    if (key === undefined) {
      for (const [k, entry] of entries) {
        if (entry.settledAt !== null) entries.delete(k);
      }
      return;
    }
    if (entries.get(key)?.settledAt !== null) entries.delete(key);
  };
```

After:

```ts
  get.invalidate = (key?: K, options: { includeInFlight?: boolean } = {}): void => {
    if (key === undefined) {
      for (const [k, entry] of entries) {
        if (options.includeInFlight || entry.settledAt !== null) entries.delete(k);
      }
      return;
    }
    if (options.includeInFlight || entries.get(key)?.settledAt !== null) entries.delete(key);
  };
```

Update the `SettledTtlPromiseCache` interface's `invalidate` signature to match. The existing settle handler (`entry.settledAt = now()`) writes to the orphaned entry object, which is harmless; the rejection handler already checks `entries.get(key) === entry`.

**Tests** (add to `tests/unit/lib/concurrency.test.ts`, describe `createSettledTtlPromiseCache`):
- `invalidate(key, { includeInFlight: true }) during a load makes the next get start a new load` — first `get` returns a pending promise; invalidate; second `get` calls `load` a second time; the first promise still resolves to its own value.
- `invalidate(key) without the option keeps the in-flight load single-flight` (today's behavior pinned).

### Own actions reuse a stale membership PR snapshot

Accepted. `refreshMembershipSnapshotsForProjects` invalidates only the membership-result cache, and the gather reads the separately cached `listOpenPullRequestsSnapshot`. ### Tracker trigger misses issues leaving the current view

Accepted. The callback's `issues` argument is `getIssues()` with the default `cycle: 'current'` filter. WI-10 now reads `issueService.getIssues({ cycle: 'all' })` and also treats an identifier that disappears from the baseline as changed. A transition-out test is added. FR-5 and D-4 state the rule.

### The first live tracker change only seeds the trigger

Accepted. WI-10 now exports `seedTrackerIssues`, called in `read-model.ts` immediately before `issueService.onIssuesChanged(...)` is installed with the pre-subscription `getIssues({ cycle: 'all' })` snapshot; every callback then diffs. A first-live-update change test is added.

### A pre-webhook read can overwrite fresh derived state

Accepted. New WI-13 adds a run counter to `IssueDataService.refreshDerivedStates`: a run never writes an issue's derived state when a later-started run already wrote it. Later-started runs begin after the coalescer's invalidation (deferred by `setImmediate`), so their listing read is post-event. The change is 5 lines in `issue-data-service.ts` (1,748 → 1,753 against its 1,754 cap), and NFR-6 and NFR-7 state the limit and the guarantee. The test resolves the old run last.

### Relay health can stay true on a stale sample

Accepted. `isWebhookRelayRunningInLastSample` (WI-5) now requires `assessment.freshness.status === 'fresh'` and an `observedAt` no older than 60 s (4 × the 15 s poll) before it reads the `smee-relay` row, so a `measuring` boot snapshot, a `stale` failed collection, or a hung collector all read as not healthy (the 30 s cadence). Tests cover measuring, stale, 30-s-old, 61-s-old and stopped-relay samples. FR-9 states the rule.

### Six-second spacing can fire eleven times in sixty seconds

Accepted (framing). FR-6 now states the invariant as "consecutive fires at least 6 s apart", which bounds any half-open 60-second window at 10 fires. The WI-6 test advances to t = 59 999 ms, expects exactly 10 fires, and checks the 6 000 ms spacing.
