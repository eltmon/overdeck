# PAN-4497 — Conversation timeline rows overlap when scrolling back through a long conversation

**Issue:** https://github.com/eltmon/overdeck/issues/4497
**Status:** planned (auto mode, 2026-10-03)

## Glossary

- **Timeline** — the conversation message list rendered by `MessagesTimeline`
  (`src/dashboard/frontend/src/components/chat/messagesTimeline/MessagesTimeline.tsx`).
- **Virtual row** — any row before the last 8 rows. It is rendered only while it is
  near the viewport, through `@tanstack/react-virtual` (`useVirtualizer`, line 199).
  Today each virtual row is `position: absolute` at `translateY(virtualItem.start)`.
- **Tail row** — one of the last `ALWAYS_UNVIRTUALIZED_TAIL_ROWS = 8` rows
  (`messagesTimeline/helpers.ts`, line 4). Tail rows always render in normal flow
  after the virtual block.
- **Virtualizer key** — the string `getItemKey(index)` returns. TanStack stores
  measured heights in `itemSizeCache` (a `Map<key, number>`) and mounted DOM nodes in
  `elementsCache` (a `Map<key, element>`), both keyed by this string.
- **Estimate** — the height `estimateMessagesTimelineRowHeight()`
  (`chat/MessagesTimeline.logic.ts`, line 252) guesses before a row is measured. It is
  often hundreds of pixels wrong for long assistant messages, wide tables and tool
  groups.
- **Measured size** — the height TanStack read from the DOM, stored in `itemSizeCache`.
- **Row width** — the width of the rows themselves. `.messagesTimelineInner`
  (`CommandDeck/styles/command-deck.module.css`, line 3600) caps it at
  `max-width: 760px`.
- **Container width** — `clientWidth` of the scroll container
  (`.messagesTimeline`, line 3591). It is wider than the row width whenever the
  conversation panel is wider than 792px (760px + 2 × 16px padding).
- **Settled** — no scroll input for at least two animation frames plus 200 ms, so
  every ResizeObserver callback has run.

## Problem and verified root cause

The operator saw rows draw on top of each other in conversation
`20260928-7563-post-clear-1415587e` (`/conv/3183`). I reproduced it against the live
dashboard on 2026-10-03 with a Playwright probe that compares each virtual row's
measured height with the distance to the next row's `translateY`. There are two
separate mechanisms.

### Mechanism A — lasting overlap after a width change (primary)

`MessagesTimeline.tsx` lines 197-208:

```tsx
const widthKey = `width:${Math.round(width)}`;

const rowVirtualizer = useVirtualizer({
  count: virtualRows.length,
  getScrollElement: () => scrollContainerRef.current,
  getItemKey: (index) => `${widthKey}:${virtualRows[index]!.id}`,
  estimateSize: (index) =>
    estimateMessagesTimelineRowHeight(virtualRows[index]!, { timelineWidth: width, hideToolCalls }),
  measureElement: (el) => el.getBoundingClientRect().height,
  useAnimationFrameWithResizeObserver: true,
  overscan: 8,
});
```

`width` is the **container** width (ResizeObserver on `scrollContainerRef`,
lines 216-223). Any container-width change renames every virtualizer key, so every
measured size in `itemSizeCache` is orphaned and every row falls back to its
estimate. A mounted row is measured again only if (a) its own ResizeObserver fires,
which needs its border box to change, or (b) React calls its `ref` again, which needs a
remount. React keys the row by `row.id` (line 463), so it never remounts. When the
panel is wider than 792px, a width change does not change the row width (capped at
760px), so no row's ResizeObserver fires. The mounted rows stay at their estimates
and overlap each other until they scroll out and back in.

Evidence (probe at viewport 2600 → container 1720px, then narrowed):

```
resize 2480 cw 1600 overlaps [{"i":156,"measured":68,"slot":64,"over":4},{"i":158,...}]
resize 2340 cw 1460 overlaps [..., {"i":160,"measured":520,"slot":223,"over":297}]
resize 2600 cw 1720 overlaps []        <- original keys' cache entries were never deleted
```

Control: at viewport 1600 (container 720px < 792px) the same resizes reflow every
row, every ResizeObserver fires, and no overlap remains.

The same defect affects the "Hide tool calls" toggle. Lines 210-214 call
`rowVirtualizer.measure()` when `hideToolCalls` changes. In
`@tanstack/virtual-core@3.17.11` (`src/index.ts`, line 2111) `measure()` only clears
`itemSizeCache` and notifies; it does not re-read any element. Rows whose height
did not change (every plain message row) fall back to their estimates and overlap.
This follows from the code; the spec in WI-3 checks it.

### Mechanism B — transient overlap while scrolling up fast (secondary)

During user scrolling, `Virtualizer.measureElement` (the `ref` callback,
`index.ts` lines 1648-1682) skips the synchronous read
(`(!this.isScrolling || this.scrollState)` is false) and waits for the ResizeObserver,
which `useAnimationFrameWithResizeObserver: true` defers by one more frame. A row that
mounts during a fast upward wheel is positioned for about two frames at the estimate
of the row above it. A per-frame probe (wheel −300px every 25 ms) recorded 29 rows
overlapping by up to 614px, each for 2 frames. On a loaded dashboard with heavy
markdown rendering this can last longer and is visible as flicker.

## Approach (decisions made)

1. **Stable keys + explicit re-measure, no `measure()` (fixes A).** `getItemKey`
   returns the row id alone, so measured sizes survive a width change. The
   `hideToolCalls` `measure()` call is removed: it drops every cached size, and
   `resizeItem` cannot restore an unchanged row (see the next paragraph). A layout
   effect instead re-reads every mounted row with `resizeItem` whenever the **row**
   width or `hideToolCalls` changes, so a row that did change is corrected in the same
   layout pass instead of one ResizeObserver frame later. Estimates use the row width.
   Unmounted rows keep their last measured size and are corrected when they mount;
   TanStack compensates the scroll offset for rows above the viewport.

   Why not `measure()` followed by `resizeItem`: `resizeItem`
   (`virtual-core/src/index.ts` lines 1684-1757) computes
   `delta = size - (itemSizeCache.get(key) ?? cachedSize)` and writes
   `itemSizeCache.set(key, size)` only inside `if (delta !== 0)`. After `measure()`,
   `itemSizeCache` is empty, but `cachedSize` comes from the flat measurement array,
   which is rebuilt lazily on the next render and still holds the old measured
   height. For an unchanged row `delta` is 0, nothing is written, and the rebuild uses
   the estimate — the bug again.
2. **Flow layout for virtual rows (fixes B and makes overlap impossible).** Render the
   visible virtual rows in normal block flow inside one wrapper translated to the
   first visible item's `start`. This is the TanStack "dynamic" example pattern. Rows
   then stack by their real heights in the same frame the browser lays them out, so
   two virtual rows cannot overlap regardless of measurement timing. A wrong
   measurement can now cause only a small scroll-offset error, never overlap.
3. Keep `useAnimationFrameWithResizeObserver: true`. After decision 2 it no longer
   causes overlap, and removing it risks "ResizeObserver loop" warnings.
4. Do not upgrade `@tanstack/react-virtual` (`^3.14.13`, core `3.17.11`).
5. The Playwright check runs against the **isolated dashboard fixture**
   (`tests/fixtures/isolated-dashboard.ts`): its own temp `OVERDECK_HOME`, its own
   port and the workspace's built frontend, in a fresh browser context. It never
   touches the operator's live dashboard on 3011. Conversation data is route-mocked.

## Requirements

- **FR-1** — `getItemKey` returns `virtualRows[index]!.id` with no width component, so
  the virtualizer key and the React key are the same string.
- **FR-2** — When the row width or `hideToolCalls` changes, every mounted virtual row's
  height is re-read from the DOM in the same layout pass (`resizeItem`), with the size
  cache left intact. Nothing in `MessagesTimeline.tsx` calls `rowVirtualizer.measure()`.
- **FR-3** — `estimateSize` receives the row width (the `clientWidth` of
  `innerRef`, initial value 760), not the container width.
- **FR-4** — Visible virtual rows render in normal block flow inside a single
  absolutely positioned wrapper with `transform: translateY(<first visible item start>px)`;
  each row wrapper has `display: flow-root` so child margins stay inside the measured
  box.
- **FR-5** — A Playwright spec on the isolated dashboard asserts that no two timeline
  rows' bounding boxes intersect, per frame during wheel scrolling and when settled
  after a width change, a tool-group expansion, a late image load and a
  "Hide tool calls" toggle.
- **FR-6** — `docs/DASHBOARD-ARCHITECTURE.md` and the `MessagesTimeline.tsx` module
  header describe the flow layout, the stable keys and the re-measure rule.
- **NFR-1** — No new dependency and no version change of `@tanstack/react-virtual`.
- **NFR-2** — Existing behavior stays: pinned-to-bottom auto-scroll (commit
  `80b33db80`, `userScrollIntentRef`), Ctrl+F search `scrollToRow`, target-message
  outline, round markers, tail rows and the scroll-to-bottom button.
- **NFR-3** — `MessagesTimeline.tsx` (720 lines today) stays under the 1000-line
  ceiling of `scripts/lint-file-size.sh`. Net growth is expected to be under 30 lines.

3. Replace the `hideToolCalls` effect (lines 210-214) and the container-width

```tsx
  // Re-read mounted rows in this layout pass when the row width or the tool-call
  // toggle changes. Do not call measure() here: it drops every cached size, and
  // resizeItem() writes only a changed size, so unchanged rows would fall back to
  // their estimates and overlap (PAN-4497).
  useLayoutEffect(() => {
    rowVirtualizer.elementsCache.forEach((el) => {
      if (!el.isConnected) return;
      rowVirtualizer.resizeItem(rowVirtualizer.indexFromElement(el), el.getBoundingClientRect().height);
    });

  // Track the row width for estimates and for the re-measure above.
  useLayoutEffect(() => {
    const el = innerRef.current;
    if (!el) return;
    const ro = new ResizeObserver(() => setRowWidth(Math.round(el.clientWidth)));
    ro.observe(el);
    return () => ro.disconnect();
  }, []);
```

   `Virtualizer` in `@tanstack/virtual-core@3.17.11` (`src/index.ts` lines 503, 1602,
   1684). `resizeItem` already ignores an out-of-range index.

After:

```tsx
{virtualRows.length > 0 && (
  <div style={{ height: rowVirtualizer.getTotalSize(), position: 'relative' }}>
    {/* Rows stack in normal flow under one translated wrapper, so two rows can
        never overlap while a measurement is pending (PAN-4497). */}
    <div
      style={{
        position: 'absolute',
        top: 0,
        left: 0,
        width: '100%',
        transform: `translateY(${dedupedVirtualItems[0]?.start ?? 0}px)`,
      }}
    >
      {dedupedVirtualItems.map((virtualItem) => {
        const row = virtualRows[virtualItem.index]!;
        ...
        return (
          <div
            key={row.id}
            data-index={virtualItem.index}
            data-search-row-id={row.id}
            ref={rowVirtualizer.measureElement}
            style={{
              display: 'flow-root',
              background: 'var(--background)',
              outline: ...,
              outlineOffset: '-2px',
              borderRadius: 8,
            }}
          >
```

Rules:

- `dedupedVirtualItems` must stay in ascending index order and contiguous. The
  default range extractor guarantees this; do not add a custom `rangeExtractor`.
- `display: flow-root` is required. Without it a child's vertical margin can collapse
  through the row wrapper: `getBoundingClientRect().height` would then exclude it while
  the layout still includes it, so the total size drifts and the spacing between rows
  changes from today's.
- Keep `background`, `outline`, `outlineOffset` and `borderRadius` exactly as they are.
- Update the module header comment (lines 1-12) to say that virtual rows render in
  flow inside one translated wrapper and that keys are the row id.
