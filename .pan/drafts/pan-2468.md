## 1. Glossary

Define-before-use. Every term of art in this document:

- **OKF (Open Knowledge Format)** — Google Cloud's vendor-neutral spec (v0.1 Draft, announced 2026-06-12) for representing knowledge as a directory of Markdown files with YAML frontmatter. Spec: https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md (Apache-2.0).
- **Bundle** — an OKF directory tree, distributable as a git repo or subdirectory. The unit of knowledge.
- **Concept** — one non-reserved `.md` file in a bundle; exactly one idea per file. Its **concept ID** is the file path minus `.md` (e.g. `tables/orders`).
- **Frontmatter** — the YAML block at the top of a concept. OKF requires exactly one field (`type`); recommends `title`, `description`, `resource`, `tags`, `timestamp`. **Extensions clause (§4.1):** "Producers MAY include any additional keys. Consumers SHOULD preserve unknown keys when round-tripping and SHOULD NOT reject documents with unrecognized fields."
- **`tags`** — recommended OKF frontmatter field: a flat YAML list of short strings for cross-cutting categorization. No controlled vocabulary, no hierarchy; tag-browsing views are synthesized by consumers.
- **Reserved files** — `index.md` (directory listing for progressive disclosure; no frontmatter except bundle-root `okf_version`) and `log.md` (per-directory change history, `## YYYY-MM-DD` headings, newest first). Never concept documents.
- **Karpathy llm-wiki** — Andrej Karpathy's "LLM Knowledge Bases" pattern (X post 2026-04-03, gist 2026-04-04: https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f). Three layers: immutable `raw/` sources, an LLM-owned `wiki/` of interlinked Markdown, and a prose **schema file** that "makes the LLM a disciplined wiki maintainer." Three operations: **ingest** (new source → update pages), **query** (answers filed back as pages), **lint** (patrol for contradictions, staleness, orphans). Deliberately anti-RAG: synthesis compounds at write time.
- **Knowledge repo** — this skill's default bundle host: a companion git repo named `<project>-knowledge`, PR-gated, carrying its own CI conformance gate.
- **Pointer file (`.okf.yml`)** — a tiny file in the *code* repo recording where the project's bundle lives (companion repo URL or in-repo path). All skill commands resolve the bundle through it.
- **Conformance gate** — deterministic Python validation (`validate.py --strict` + `diff_lint.py`) run locally and as a required CI check on knowledge-repo PRs. Never an LLM.
- **Diff-lint** — the "was-clean-now-broken" check: compares validation results between a PR's base and head so pre-existing warnings don't block, but new breakage does.
- **`okf-embeddings`** — the extension standard this PRD defines (v0.1, ours): a committed `okf-embeddings.yaml` manifest + committed per-profile vector shards + a gitignored derived SQLite index. See §5.3.
- **Profile** — one named embedding configuration in the manifest (provider + model + dimensions + endpoint).
- **Vector shard** — a committed JSONL file (`embeddings/<profile>.okfe.jsonl`), one line per chunk: concept ID, content hash, vector. Shareable so consumers don't recompute.
- **Content hash** — SHA-256 of a concept's normalized content; stored beside each vector so staleness is detected per-concept and re-embedding is incremental.
- **BM25** — classic keyword relevance ranking (SQLite FTS5 built-in). The zero-dependency search floor.
- **RRF (Reciprocal Rank Fusion)** — rank-fusion formula `score = Σ 1/(K + rank)`, K=60, used to merge BM25 and vector result lists. Already used in three Overdeck subsystems.
- **Observations** — Overdeck's LLM-extracted, append-only JSONL memory records captured from agent transcripts (`~/.overdeck/memory/<project>/<issue>/observations/`), FTS-indexed, injected at prompt time with token budgets. Implementation: `src/lib/memory/` (extract.ts, observations.ts, injection.ts, search.ts).
- **Ollama** — local model server (localhost:11434) that serves embedding models such as `nomic-embed-text` (768-dim). This is the "Llama-based / local scoring" path — free, no API key.
- **mnemos** — arhuman/mnemos: a cgo-free Go MCP memory server that indexes Markdown/OKF bundles into SQLite FTS5 and serves cited search to Claude Code. Relevant as a compatible *read layer*, not a dependency.
- **claude-mega-brain** — guhcostan/claude-mega-brain: a Claude Code plugin that scans a project for OKF-frontmattered files at SessionStart and injects a compact concept index. Prior art for prompt-time injection.
- **kcmd** — Google's "Metadata as Code" CLI/library/MCP server (knowledge-catalog `toolbox/mdcode`): git-style `init/pull/status/push` sync between local YAML/Markdown and the cloud Knowledge Catalog service. Out of scope for v1; noted for future interop.

## 2. Vision & motivation

Every project accumulates knowledge that lives only in heads and transcripts: why an architecture was rejected, how overtime calculations actually work, which invariant a subsystem protects. Agents re-derive this context every session — slowly, expensively, and sometimes wrongly.

The skill maintains a **wiki-style OKF bundle per project** — interlinked Markdown concepts, one idea per file — kept current by the same agents that do the development work:

- **Before a feature**: a topic-focused *study* pass documents what exists today (e.g. "overtime calculations") so planning starts from written truth.
- **After a feature**: a *retro* pass asks "what did this session have to rediscover that the wiki should have known?" and files it.
- **At any time**: an *extract* pass pulls the few relevant concepts into a prompt — hybrid semantic + keyword search when embeddings exist, keyword-only otherwise, plain index-reading at the floor.

Correctness is enforced by the bundle itself (CI conformance gate), not by any agent's discipline. The skill is **fully portable** — plain git + GitHub + Python for anyone — and **lights up extra leverage when Overdeck is present** (Observations mining, post-merge automation, embedding-provider reuse, prompt-time injection).

The strategy in one line: **OKF on disk, Karpathy in behavior, embeddings as a conformant extension.**

## 3. Research grounding (verified 2026-07-07)

- OKF spec v0.1 Draft; `type` is the only required frontmatter field; `tags` is a recommended flat list; arbitrary extension keys are explicitly conformant (§4.1, §9). Consumers MUST tolerate unknown keys, unknown types, broken links.
- Ecosystem (~3.5 weeks post-launch): 25+ community skills/tools; largest is claude-mega-brain (111★, SessionStart injection); mnemos, okf-mcp MCP servers; Google's Knowledge Catalog + kcmd; W3C Holon CG forming.
- **Vector-search convention already emerging, and it is NOT frontmatter.** Every implementation (hdean-ssp/okf-tools, travisjakel/okf-ingest, OKFgraph, mnemos) treats Markdown as source of truth and the vector index as a derived, rebuildable sidecar DB; hybrid BM25+vector; local models favored. Nobody has standardized embedding *metadata* (model, dims, hashes) — that gap is what `okf-embeddings` fills. Zero upstream spec issues propose vector fields.
- Karpathy llm-wiki (Apr 2026): three layers, ingest/query/lint, schema-as-prose. LangChain **OpenWiki** (Jul 2026) productized the codebase variant with scheduled agent runs opening doc-update PRs — field validation of our retro/sync loop.
- Overdeck verified capabilities: embedding providers `openai`/`voyage`/`ollama` (`src/lib/conversations/embeddings/providers.ts`); sqlite-vec 0.1.9 ANN + Float32-BLOB in-memory cosine fallback; RRF hybrid ranking (`src/lib/conversations/search.ts`, `src/lib/conversation-search/ranker.ts`, `src/lib/docs/query.ts`); Observations pipeline (`src/lib/memory/`); `pan memory search` CLI.

## 4. Requirements

### Functional

- **FR-1** `/okf init` scaffolds a knowledge bundle (companion repo by default, in-repo directory optional), writes the pointer file, seeds `index.md`/`log.md` + starter concepts, installs the CI conformance gate, and adds one discovery line to the code repo's `CLAUDE.md`/`AGENTS.md`.
- **FR-2** `/okf author "<topic>"` writes/updates a single concept: infer-and-confirm `type`, frontmatter handled by the skill, relative cross-links, index/log regeneration, local validation.
- **FR-3** `/okf convert <path>` onboards existing docs non-destructively: dry-run plan first, frontmatter-first edits, confirmed renames, never deletes a README.
- **FR-4** `/okf sync [--topic "<focus>"]` maps code changes since the last log entry (or PR base) to concepts, updates them, appends `log.md`, regenerates `index.md`, validates, and opens a PR. `--topic` restricts the pass to concepts matching the focus (tag match + search).
- **FR-5** `/okf study "<focus>"` (pre-feature pass) researches the **current codebase** for a topic (e.g. "overtime calculations"), then creates/refreshes the concepts describing today's behavior, opening a PR. Output is written knowledge, not chat.
- **FR-6** `/okf retro` (post-implementation pass) reviews the change (diff + available session context) and answers: *what would have made this work easier if it had been documented?* Files the answers as concepts via PR. With Overdeck: mines the issue's Observations; without: uses `git diff` + the current transcript.
- **FR-7** `/okf extract "<query>" [--budget <tokens>]` returns the ranked, token-budgeted set of relevant concepts formatted for prompt inclusion. Ranking: hybrid RRF (BM25 + vectors) when an index exists; BM25-only when no embedding backend; index.md-guided reading as the floor. Cites concept IDs.
- **FR-8** `/okf validate [--strict]` runs the deterministic conformance gate locally — identical code to CI. Exit 0/1/2 (clean / lint findings / errors).
- **FR-9** `/okf lint` runs the semantic patrol (LLM): contradictions, stale claims vs. `timestamp`, orphaned concepts, missing cross-links. Advisory only — never the merge gate.
- **FR-10** `/okf embed [--profile <name>]` reads `okf-embeddings.yaml`, embeds only concepts whose content hash changed, updates the profile's vector shard, and rebuilds the local index.
- **FR-11** The `okf-embeddings` v0.1 format (§5.3) is implemented exactly as specified: committed manifest, committed shareable shards, gitignored derived index, per-concept content hashes, pluggable providers (`openai`, `voyage`, `ollama`, `custom` OpenAI-compatible endpoint).
- **FR-12** All bundle writes are PR-gated by default; the CI gate (validate --strict + diff-lint) is installed by init as a required check.
- **FR-13** Every command works with zero Overdeck present (deps: git, gh, Python 3 + PyYAML; embeddings additionally need an API key or Ollama).
- **FR-14** When Overdeck is detected, the skill uses: `projects.yaml`/pointer discovery, Overdeck's configured embedding provider, Observations for retro, and exposes a hook point for `postMergeLifecycle` auto-retro. Core never *imports* Overdeck — it detects and lights up.
- **FR-15** Reading behavior (taught in SKILL.md): read `index.md` first, load only relevant concepts, answer only from loaded concepts, cite concept IDs, never invent.

### Non-functional

- **NFR-1** Conformance verdicts are deterministic — same input, same verdict, no LLM in the gate.
- **NFR-2** Graceful degradation at every tier: no embeddings → BM25; no index → guided reading. No command hard-fails for a missing optional backend.
- **NFR-3** Bundles remain conformant OKF v0.1 — a vanilla OKF consumer that has never heard of this skill reads them fine (extension keys tolerated per spec §4.1/§9).
- **NFR-4** Vector shards are incremental: an unchanged concept is never re-embedded; a changed one is re-embedded alone.
- **NFR-5** Local index rebuild is always possible from Markdown + shards alone (`--rebuild`), and from Markdown alone (re-embed).
- **NFR-6** The embed/search scripts run under plain CPython (stdlib + PyYAML; `sqlite-vec` optional with BLOB-cosine fallback).

## 5. Design

### 5.1 Bundle location & discovery

Default: companion repo `<project>-knowledge` (PR gating, CODEOWNERS, independent history). Optional: in-repo directory (e.g. `knowledge/`) for solo projects via `/okf init --local knowledge/`.

Either way, init writes **`.okf.yml`** at the code-repo root:

```yaml
# .okf.yml — where this project's knowledge bundle lives
bundle: git@github.com:acme/acme-pay-knowledge.git   # or: ./knowledge
```

Every other command resolves the bundle through this pointer (Overdeck's `projects.yaml` `knowledge_repo:` field, when present, wins). Commands are location-agnostic beyond resolution.

### 5.3 The `okf-embeddings` extension standard, v0.1

**Design stance:** Markdown is the source of truth; vectors are derived data. But derived data that costs money/time to compute is worth *sharing* — so the standard splits three ways:

| Artifact | Location | Committed? | Why |
| --- | --- | --- | --- |
| **Manifest** | `okf-embeddings.yaml` (bundle root) | yes | Human-readable contract: which profiles exist, how content is chunked and hashed. Reviewable in PRs. |
| **Vector shards** | `embeddings/<profile>.okfe.jsonl` | yes, per-profile `share: true` (default for the default profile) | So teammates/CI/consumers reuse embeddings instead of recomputing. One JSON line per chunk → line-level diffs, no binary churn; content hashes make stale entries safe (they're just re-embedded). |
| **Local index** | `.okf-index/` (SQLite: FTS5 + sqlite-vec or BLOB) | no (gitignored by init) | Machine-local cache; binary; trivially rebuilt from Markdown + shards. This is the only gitignored piece. |

**Manifest schema:**

```yaml
# okf-embeddings.yaml — okf-embeddings extension, v0.1
okf_embeddings_version: "0.1"
default_profile: local

profiles:
  local:
    provider: ollama                 # openai | voyage | ollama | custom
    model: nomic-embed-text
    dim: 768
    endpoint: http://localhost:11434 # optional; custom REQUIRES an OpenAI-compatible endpoint
    share: true                      # commit this profile's shard
  cloud:
    provider: openai
    model: text-embedding-3-small
    dim: 1536
    share: false                     # local-only shard (still written, gitignored via pattern)

chunking:
  strategy: concept                  # v0.1: whole-concept only ("section" reserved for v0.2)
  max_tokens: 512                    # concepts longer than this are truncated for embedding,
                                     # flagged by lint as split candidates

hash: sha256                         # over normalized content: frontmatter minus timestamp,
                                     # plus body, LF-normalized, trailing whitespace stripped
vectors_dir: embeddings
```

**Shard format** — `embeddings/<profile>.okfe.jsonl`, one line per chunk:

```json
{"id":"tables/orders#0","concept":"tables/orders","hash":"sha256:9f2c…","dim":768,"v":[0.0123,-0.0456,…]}
```

Rules: lines sorted by `id` (stable diffs); one line per (concept, chunk); vectors L2-normalized floats, 6-decimal precision (cosine = dot product); a reader MUST ignore lines whose `hash` mismatches the concept's current content and SHOULD re-embed them; a writer replaces lines in place. Size envelope: ~6–19 KB/concept/profile → a 500-concept bundle ≈ 3–10 MB per shared profile. Committed by default for ONE profile; additional profiles default local-only.

**Frontmatter footprint:** exactly one optional key, `x_embed: exclude`, to opt a concept out of embedding (secrets, boilerplate). **No vectors in frontmatter, ever.** Conformant under OKF §4.1; the `x_` prefix avoids collision with future blessed field names (upstream is actively adding fields — e.g. `reliability`, PR #159).

**Provider contract:** `embed(texts: list[str]) -> list[list[float]]`, batched, L2-normalized output. Built-ins: `openai` (api.openai.com/v1/embeddings), `voyage`, `ollama` (localhost-only), `custom` (any OpenAI-compatible `/v1/embeddings` endpoint + env-var key). Adding a provider = one small adapter in `embed.py`.

**Interop & succession:** different consumers of the same bundle MAY use different profiles — hashes keep every shard independently verifiable. If the upstream spec or the ecosystem later standardizes embedding metadata, this extension is migrated to it and `okf_embeddings_version` marks the boundary (explicit adopt-the-standard clause; Decision D-4).

### 5.4 Search stack (used by `extract`, `sync --topic`, `study`)

```
query ──► BM25 (FTS5 over concepts)  ──┐
      └─► vector (query embed → ANN)  ─┴─► RRF (K=60) ─► token-budgeted selection ─► cited output
```

Tiered degradation (NFR-2): no vector backend → BM25-only; no index at all → the skill reads `index.md` and follows links (OKF progressive disclosure). `search.py --format prompt` emits a paste-ready block: concept ID + title + body excerpt per hit, within budget.

### 5.6 Decisions (made here, not re-litigated later)

- **D-1 Name:** `/okf` (ecosystem-aligned).
- **D-2 Home:** standalone repo `~/Projects/okf-skill` — a shippable product installable by non-Overdeck users (`~/.claude/skills/okf/`); Overdeck distribution via `pan sync` comes after. *(Operator may override to `sync-sources/`.)*
- **D-3 Vector sharing:** shards committed by default for the default profile (recompute-avoidance beats repo size at this scale); only the binary SQLite index is gitignored.
- **D-4 Standards posture:** ship `okf-embeddings` as our extension; after v1 works on ≥2 real bundles, file an upstream discussion issue on GoogleCloudPlatform/knowledge-catalog proposing it; if the ecosystem standardizes something else, adopt it and migrate.
- **D-5 Gate is deterministic:** the merge gate is Python; `lint` (LLM) is advisory forever.
- **D-6 Chunking v0.1 = whole concept.** OKF concepts are already atomic; section-chunking is deferred to okf-embeddings v0.2 (lint flags oversized concepts instead).
- **D-7 kcmd/MCP interop deferred:** kcmd targets Google Cloud Knowledge Catalog sync; mnemos already serves OKF bundles over MCP. v1 neither depends on nor conflicts with either (PAN-2066 keeps the MCP item).

## 7. Acceptance criteria (mechanical, 1:1 with work items)

1. `selftest.sh` passes end-to-end on a machine with only git+gh+python3+PyYAML (WI-1..9, 12..15 standalone paths).
2. A fixture bundle missing `type` fails validate with exit 2 (WI-3 negative test).
3. `init` output passes `validate.py --strict` and its CI workflow is syntactically valid (WI-4).
4. `sync` on a fixture change yields a PR branch: bundle validates, log.md +1 dated entry, index regenerated inside markers (WI-6/7).
5. `study "overtime calculations"` against the fixture codebase produces ≥1 validating concept tagged `overtime-calculations` (WI-8).
6. `retro` from fixture observations produces ≥1 concept citing a recorded decision (WI-9).
7. Editing one concept and running `embed` rewrites exactly one shard line; all other lines byte-identical (WI-10).
8. `extract` returns ranked cited concepts with no embedding backend configured (BM25 floor), and different ranking with vectors present (WI-11/12).
9. Deleting `.okf-index/` and re-running any search command transparently rebuilds it (NFR-5).
10. A stock OKF validator (no skill knowledge) accepts a bundle containing `okf-embeddings.yaml`, shards, and `x_embed` keys (NFR-3).

## 9. Intersecting repo rules, restated for the executor
