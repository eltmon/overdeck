# PAN-5209 — `pan close`: compare against `origin/<target>`, and accept merged forge artifacts on the review and tests rows

**Issue:** [PAN-5209](https://github.com/eltmon/overdeck/issues/5209)
**Related:** [PAN-5097](https://github.com/eltmon/overdeck/issues/5097) (recording review verdicts in polyrepo GitLab workspaces — a different problem: it writes verdicts, this issue reads landing evidence), [PAN-3215](https://github.com/eltmon/overdeck/issues/3215) (added the GitLab merged-MR path to close-out), [PAN-4821](https://github.com/eltmon/overdeck/issues/4821) (a failed forge read is never "no PR").

## Glossary

- **Close-out** — `pan close <id>` and `POST /api/issues/:id/close-out`. Both call `closeOut()` in `src/lib/lifecycle/workflows.ts`, which evaluates the Definition-of-Done gate before it archives, tears down, and closes the tracker issue.
- **DoD gate / rows** — `evaluateDodGate()` in `src/lib/lifecycle/dod-gate.ts`. Eight rows: 1 review, 2 tests, 3 verification, 4 merged, 5 post-merge, 6 main-verify, 7 ship, 8 deploy. A row is `pass`, `skip`, or `miss`; an unaccepted `miss` blocks close-out.
- **Merged check** — row 4. Its evidence comes from `verifyBranchMergedImpl()` (step id `close-out:verify-merged`), which runs `verifyConventionBranchMerged()` for every required repo.
- **Root** — one `MergeVerificationRoot` `{ repoKey, dir, sourceBranch, targetBranch, forge }`. `dir` is the project's primary checkout of that repo (for MYN: `/home/eltmon/Projects/myn/<path>`), not the workspace worktree. Nobody pulls `main` in those checkouts, so their local `main` goes stale.
- **Target branch** — the bare branch name from config (`root.targetBranch`, usually `main`).
- **Comparison ref** — the ref every ancestry, diff and log comparison uses. After this change it is `origin/<targetBranch>` after a successful fetch, or the bare local `<targetBranch>` when the fetch fails.
- **Polyrepo** — a project with more than one entry under `workspace.repos` in `projects.yaml` (MYN: `fe`, `api`, `infra`, `docs`, `myn-skills`, `openclaw-plugin`, `hermes-plugin`, `splash`). Members may sit on different forges (`myn-skills`, `openclaw-plugin` and `hermes-plugin` have `remote: github`; the others are GitLab).
- **Repo landing evidence** — new in this issue (WI-5): for each required repo, whether a merged PR/MR exists for its source branch (`merged`), the branch has no work of its own (`no-branch-work`), its work is not landed or landed without a merged artifact (`unlanded`), or a git/forge read failed (`unverifiable`). Complete = no `unlanded`/`unverifiable` repo and at least one `merged` repo.
- **Why not `assessMergeCompleteness`** — the existing "Single Merge Oracle" in `src/lib/cloister/merge-completeness.ts` returns `no-changes` as soon as `origin/<target>..origin/<source>` counts 0, **before** it asks the forge. MYN MRs merge with merge commits, so on 2026-11-13 every MIN-1139/MIN-1140 repo (`frontend`, `api`, `infra`, `docs`, `splash`, `hermes-mind-your-now`) counted 0 ahead: the oracle would find no positive merged evidence and rows 1/2 would still miss. It also upserts a merge-set row (`ensureMergeSetForIssue`), and the DoD gate only reads. So rows 1/2 get their own read-only evidence module that asks the forge first.
- **First-parent line** — `git rev-list --first-parent <ref>`: main's own commit line. A branch tip **on** it is a pointer to main history (no work of its own, e.g. `myn-skills` `feature/min-1140` == `origin/main`); a tip that is an ancestor of `<ref>` but **off** that line arrived through a merge (work that landed). Pipeline membership uses the same test (`snapshotBranchRefs`, PAN-2887).
- **Post-merge delta tolerance** — the logic in `verifySquashMergedPrByBranch()` that still accepts a squash-merged GitHub PR when the branch tip moved past the merged head, as long as every later non-merge commit is on the comparison ref, or the branch-unique delta touches only `.pan/` paths.

## Requirements

### Functional

- **FR-1** — Every ancestry, three-dot diff and `git log` comparison in the merged check (the eight sites above) uses the comparison ref. The ref is resolved once per root by `git fetch origin +refs/heads/<target>:refs/remotes/origin/<target>` in `root.dir`. A successful fetch gives `origin/<target>`. A non-zero exit or a timeout (30 s) gives the bare local `<target>` **only when** `git rev-parse --verify --quiet refs/heads/<target>^{commit}` resolves; when it does not, there is no comparison ref and the merged step for that root fails with `Cannot verify merge: git fetch origin <target> failed (<reason>) and no local <target> branch exists` (no git comparison runs, because the existing diff commands swallow errors with `2>/dev/null || true` and an empty diff would read as "squash-merged").
- **FR-2** — When the fetch fails, the step says so. On a passing or skipped step the note is appended to `details`; on a failing step it is appended to `error` in parentheses (row 4's `observed` text is `details || error`, and the multi-root aggregator keeps only `error` for failures). Note text: `Checked against local <target> because git fetch origin <target> failed: <reason>`, where `<reason>` is the first non-empty line of the error's stderr, else its message, cut to 200 characters.
- **FR-3** — The fetch only updates `refs/remotes/origin/<target>`. It never checks out, resets, or moves the local `<target>` branch, and it never fetches the feature branch (that fetch already exists in `verifyRemoteBranchIfPresent`).
- **FR-4** — A branch with commits that are not on `origin/<target>` (and no merged PR/MR that accepts them) still fails with the existing message `<n> unmerged commit(s) on <source>. Merge before closing out.`, where `<n>` now counts `origin/<target>..<source>`.
- **FR-5** — For a GitLab root, a merged MR for the source branch counts as merged the same way a squash-merged GitHub PR does in `verifySquashMergedPrByBranch`: an MR whose head equals the branch tip passes (existing behavior); an MR whose head differs passes when every non-merge commit in `<mrHead>..<tip>` is an ancestor of the comparison ref, or when the branch-unique delta touches only `.pan/` paths; otherwise it fails with `<branchRef> has <n> commit(s) after merged MR !<iid> that are not on <comparisonRef>: <shas>`. In the shared state-plane check (both forges) the three-dot fallback requires at least one changed file: `statePlaneOnly = deltaFiles.length > 0 && deltaFiles.every(f => f.startsWith('.pan/'))`. An empty delta therefore falls to the strict failure instead of reading as "state-plane commits (0 file(s))". This is the one behavior change on the GitHub path; its strings stay identical.
- **FR-6** — Rows 1 (review) and 2 (tests) of a non-GitHub-tracked issue (`ctx.github` undefined) whose GitHub PR read answers "no PR" (null, not an error) read repo landing evidence. Per required repo (`resolveProjectReposForIssue(issueId)` filtered by `required`), in this order:
  1. `getForgeAdapter(repo.forge).findMergedArtifact({ sourceBranch, targetBranch, cwd: repoPath })` — bare `targetBranch`, no `headSha`. A thrown error → `unverifiable`, reason `<repoKey>: merged-artifact lookup failed: <message>`. An artifact → `merged` (keep `url`).
  2. Otherwise `resolveTargetComparison(repoPath, targetBranch)` (from WI-2). A result with a `note` (fetch failed, local fallback) or with no ref → `unverifiable`, reason `<repoKey>: git read failed: <note or error>` — rows 1/2 never judge landing against an unrefreshed target. Then `git ls-remote --heads origin <source>` (cwd `repoPath`, 30 s timeout): a non-zero exit → `unverifiable` (`<repoKey>: git read failed: <reason>`). Non-empty output → `git fetch origin +refs/heads/<source>:refs/remotes/origin/<source>`; a fetch failure → `unverifiable`; on success the tip is `origin/<source>`. Empty output (the forge says the branch is absent) → the tip is `refs/heads/<source>` when `git rev-parse --verify --quiet refs/heads/<source>^{commit}` resolves (an unpushed local branch), else `no-branch-work`, reason `<repoKey>: no <source> branch`. A cached `refs/remotes/origin/<source>` is never used without a successful refresh.
  3. `git merge-base --is-ancestor <tip> <ref>` fails → `unlanded`, reason `<repoKey>: <source> is not on <ref> and has no merged review artifact`.
  4. The tip is on the first-parent line of `<ref>` (`git rev-list --first-parent <ref>` contains it) → `no-branch-work`, reason `<repoKey>: <source> points at <ref> history`. Off that line → `unlanded`, reason `<repoKey>: <source> work reached <ref> without a merged review artifact`.
  5. Any git command in steps 2–4 throwing (other than the expected non-zero exit of `--is-ancestor` and `rev-parse --verify --quiet`) → `unverifiable`, reason `<repoKey>: git read failed: <message>`.
- **FR-7** — When the evidence is complete (no `unlanded`, no `unverifiable`, at least one `merged`), rows 1 and 2 are both `skip` (not `pass`: no review decision or check result was observed). Observed for row 1: `no pull request found on the forge for this issue; forge merge complete: <list>; skipped — merged forge artifacts are landing evidence; the forge review decision is not read`. Row 2 ends `…; skipped — merged forge artifacts are landing evidence; forge check results are not read`. `<list>` joins the repos in resolved order with `, `: `<repoKey> merged (<url>)` (or `<repoKey> merged` without a URL) and `<repoKey> no branch work`. A `skip` does not block close-out (`evaluateDodGate` blocks only on `miss`).
- **FR-8** — When the evidence is incomplete, rows 1 and 2 keep today's behavior (strike skip, tracker-closed settlement, else `miss`) and observed gains a suffix: `; forge merge incomplete: <unlanded reasons joined by '; '>` when a repo is `unlanded`; `; forge merge incomplete: no repository has a merged review artifact` when none is `merged`; `; forge merge incomplete: no repositories resolved` when no required repo resolves.
- **FR-9** — When any repo is `unverifiable`, or the evidence read itself throws, rows 1 and 2 are `miss` with no strike or settlement waiver (PAN-4821: a failed read is not absence). Observed: `no pull request found on the forge for this issue; forge merge evidence unavailable: <unverifiable reasons joined by '; '>`, or `…; forge merge state read failed: <message>` for a throw.
- **FR-10** — The evidence is read at most once per `evaluateDodGate()` call, only when a row needs it (rows 1 and 2 share one memoized promise). The read writes nothing (no merge-set row, no file).

## Decisions (made here, not left to the executor)

- **D-1 Extraction first, verbatim.** Lines 595–991 of `workflows.ts` (from `export interface MergeVerificationRoot` through the end of `verifySquashMergedPrByBranch`) move unchanged to a new `src/lib/lifecycle/verify-merged.ts`. The unexported Effect wrapper `verifyBranchMerged` (line 584) and `__testInternals` stay in `workflows.ts` and import `verifyBranchMergedImpl` from the new module. `workflows.ts` does **not** re-export the moved names; tests import them from `verify-merged.js`.
- **D-2 Fetch-failure fallback is the local ref** (as the issue says), even when a cached `origin/<target>` exists.
- **D-3 Explicit refspec.** `git fetch origin +refs/heads/<t>:refs/remotes/origin/<t>` updates the remote-tracking ref even in a clone with a narrowed `remote.origin.fetch`. The `+` matches git's default refspec (remote-tracking refs may be force-updated).
- **D-4 One fetch per root.** `verifyRootConventionBranches` resolves the comparison once and passes it to both the `feature/` and `strike/` calls. Direct callers of `verifyConventionBranchMerged` without a resolved comparison get one fetch.
- **D-5 Rows 1/2 get a read-only, forge-first evidence module (`dod-forge-merge.ts`).** `assessMergeCompleteness` is not reused: it skips the forge for zero-ahead repos (every MIN-1139/1140 repo) and writes a merge-set row. `gatherIssueBranchContainment` is not used either: it resolves local `main` before `origin/main` and would class `myn-skills` as unmerged. The new module asks the forge first for every repo, then classifies the rest with the comparison ref from WI-2 and the first-parent test pipeline membership already uses.
- **D-6 Merged = landing evidence; approvals and pipelines are not read.** The issue (requirement 3) asks for merged MRs to be accepted as landing evidence on these rows. A probe of MR !121 showed GitLab approvals carry no signal (`approved: true`, zero approvers, zero required), and `glab mr list` returns no pipeline field.
- **D-7 `skip`, not `pass`.** The rows never observed a review decision or a check result, so they must not record `pass`. `skip` is the existing outcome for "landed, verdict not produced": `terminalVerdictSettlement` returns `skip` for an unknown verdict once the tracker is closed and work landed. This fallback applies the same outcome before close-out closes the tracker, and the observed text says what was not read.
- **D-8 Unknown `origin`.** A repo with no `origin` remote fails the fetch and falls back to the local ref with the FR-2 note.

```ts
/** The ref the merged check compares against, and why when it is not origin/<target>. */
export type TargetComparison =
  | { ref: string; note?: string }
  | { ref: null; error: string };

export async function resolveTargetComparison(dir: string, targetBranch: string): Promise<TargetComparison> {
  try {
    await execAsync(
      `git fetch origin +refs/heads/${targetBranch}:refs/remotes/origin/${targetBranch}`,
      { cwd: dir, encoding: 'utf-8', timeout: 30000 },
    );
    return { ref: `origin/${targetBranch}` };
  } catch (err) {
    const reason = fetchFailureReason(err);
    try {
      await execAsync(`git rev-parse --verify --quiet refs/heads/${targetBranch}^{commit}`, { cwd: dir, encoding: 'utf-8' });
    } catch {
      return { ref: null, error: `Cannot verify merge: git fetch origin ${targetBranch} failed (${reason}) and no local ${targetBranch} branch exists` };
    }
    return { ref: targetBranch, note: `Checked against local ${targetBranch} because git fetch origin ${targetBranch} failed: ${reason}` };
  }
}
```
