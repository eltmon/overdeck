# PAN-4400: One-click provider presets ("Apply Anthropic defaults" / "Apply OpenAI defaults")

**Issue:** [PAN-4400](https://github.com/eltmon/overdeck/issues/4400)
**Date:** 2026-09-29. Repo facts read at `bbadb008e7b` (branch `feature/pan-4400`).
**Planning mode:** `pan plan --auto`. Every choice the issue left open is recorded under "Decisions" and in the xBRIEF `plan.autoDecisions[]`.

## Glossary

- **Preset:** a versioned, named bundle of values for Overdeck's model settings, all from one provider. Presets are data in `src/lib/model-presets/presets.ts`. Applying a preset writes explicit values into `~/.overdeck/config.yaml` once. A preset is never a live config key: the retired `models.preset` key (`docs/CONFIGURATION.md` line 248, "Removed: Presets, Work-Type Overrides, Thinking Levels") stays retired.
- **Preset id:** `anthropic`, `anthropic-cost-saver` (pilot variant), `openai`.
- **Preset setting registry:** the list of every model-valued or effort-valued config path Overdeck has (`PRESET_SETTINGS` in `src/lib/model-presets/presets.ts`). Each preset gives every registry entry either a value or an explicit `keep` with a reason.
- **Keep entry:** a registry entry the preset deliberately does not write, plus the reason. Keep entries appear in the diff as "not set" rows.
- **Plan (preset plan):** the computed per-setting diff for one preset against the current global config (`PresetPlan`, from `planPresetApply()`). The CLI, the HTTP route and the UI all render this one object. A plan never writes.
- **Row:** one entry in a plan: `{ path, label, group, before, after, status, reason? }`. `status` is `change` (value differs and will be written), `same` (already equal), or `skipped` (not written; `reason` says why).
- **Plan digest:** a SHA-256 hex string over the plan's rows (canonical JSON). Apply takes the digest the operator saw and refuses if the recomputed plan's digest differs.
- **Path-scoped write:** a YAML edit that parses `config.yaml` with `yaml`'s `parseDocument`, changes only the named paths with `setIn`/`deleteIn`, and writes the document back. Every other node, including comments, keeps its exact text.
- **Undo record:** the pre-apply raw value of every path the last apply changed, stored in `~/.overdeck/model-presets-state.json`. Undo is single-level.
- **Workhorse ref:** a model reference of the form `workhorse:expensive|mid|cheap` (`src/lib/config-yaml/schema.ts`, `WorkhorseSlot` near line 358), dereferenced by `derefWorkhorse` (`src/lib/config-yaml/roles.ts`).
- **Band (tier band):** the preset's model for a tiered-execution tier, chosen by the hardest difficulty the tier owns: `trivial` → cheap band; `simple`/`medium` → mid band; `complex`/`expert` → expensive band.
- **Settings door:** the dashboard's config write path in `src/lib/settings-api.ts`: `runSettingsWriteSerialized` (line 889) plus `saveSettingsApi` (line 901).

## Problem

Operators must set about 40 model and effort settings by hand to get a coherent lineup (workhorse slots, 10 roles, 4 review lanes, tiers, the conversation default, background AI models). There is no one-click way to adopt an eval-backed lineup from one provider. The operator asked (2026-09-29) for "Apply Anthropic defaults" and "Apply OpenAI defaults" buttons.

Evidence for the values exists:

- `docs/model-evals/2026-09-29-opus-5-5-vs-sonnet-5-5.md` (committed on main). Verdict: keep `workhorses.mid` on Opus 5.5 and review on Opus. Sonnet 5.5 found the known review blocker 10 of 60 times vs Opus's 30 of 60. It matched Opus on delegated execution at about 45% of the cost.
- `.pan/drafts/model-routing-2026-09.md` (GPT-6 Astra/Sol/Luna placement research, Codex harness, the Codex ≥ 0.156.1 floor from [PAN-4363](https://github.com/eltmon/overdeck/issues/4363)). No GPT model has been run through Overdeck's evals yet. The E2 report's route was Claude-only.
- Issue comment by the operator (2026-09-29): Anthropic preset keeps `mid` = Opus 5.5 and review on Opus. It may offer a pilot "cost-saver" variant with `roles.review.model: workhorse:expensive` and `roles.work.model` split 70% `workhorse:mid` / 30% `claude-sonnet-5-5`.

## Verified facts the design depends on

1. **The whole-document settings save is unsafe for this feature.** `saveSettingsApi` → `writeYamlConfigPreservingComments` (`src/lib/settings-api.ts` line 763) does these things:
   - It replaces `workhorses` and `roles` wholesale (line 785-786: `doc.setIn(['workhorses'], config.workhorses ?? {});` / `doc.setIn(['roles'], config.roles ?? {});`), so comments are lost and all seeded role defaults are written out.
   - It writes `api_keys` back in plaintext (lines 946-958). `config.apiKeys` already holds environment-variable keys and resolved `$VAR` references (`applyEnvironmentFallbacks`, `src/lib/config-yaml/load.ts` lines 188-234), so a round trip writes environment secrets into `config.yaml`.
   - It drops `tts.summarizer.batch_window_seconds` and `memory.features.knowledge_index`.
   - Its input comes from `loadConfigSync`, which merges the project `.pan.yaml`, so project values get copied into the global file.

   The issue's AC1 ("leaves every other config key untouched") cannot hold through that path. There is **no API-key masking** anywhere on the server. The issue's "masked keys" premise is false; the test fixture uses `$VAR` env references and literal keys instead.
2. **The write queue is per-process.** `runSettingsWriteSerialized` (`src/lib/settings-api.ts` line 889) is an in-process promise chain. A CLI process and the dashboard do not serialize against each other.
3. **`models.providers.<p>` is `boolean | ProviderConfig`** (`src/lib/config-yaml/schema.ts` line 507; `ProviderConfig` at line 18: `enabled`, `api_key?`, `harness?`, `auth?`). `setIn(['models','providers','openai','harness'])` fails on a boolean scalar.
4. **Model catalog check:** `hasModelCapability(resolveModelId(id))` (`src/lib/model-capabilities.ts` line 1388 and line 46). All preset ids exist: `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-4-5`, `gpt-6-astra`, `gpt-6-sol`, `gpt-6-luna`.
5. **Effort:** `EffortLevel` / `DEFAULT_EFFORT = "high"` in `packages/contracts/src/effort.ts`. `effortConfigErrors(fieldPath, effort, models)` in `src/lib/agents/effort-support.ts` line 73. Haiku 4.5 has no effort control, so a preset never sets effort where the model is the Anthropic cheap slot.
6. **Credentials:** `getProviderAuthMode(model)` (`src/lib/agents/runtime-command.ts` line 653) returns `'api-key' | 'subscription' | undefined`; `undefined` means no credentials. Harness legality: `canUseHarness(harness, model, authMode, context)` (`src/lib/harness-policy.ts` line 156). The Codex version context comes from `resolveCodexPolicyContext(harness, model, authMode)` (`src/lib/codex/policy-context.ts` line 24).
7. **Background AI runs through `claude -p`.** `invokeClaudeStructured` (`src/lib/conversations/transcript-summary.ts` line 344) spawns `claude` with `getProviderEnvForModel(model)`. An OpenAI model there needs the CLIProxy route. The routing research says GPT-6 Luna (77% hallucination rate) is "not yet" fit for titles, compaction, summaries or memory.
8. **Role distributions validate:** `validateModelRef(..., allowDistribution=true)` for `roles.<role>.model` (`src/lib/settings-api.ts` ~line 576); sub-roles reject distributions.
9. **No undo exists** for settings writes today. The only backup is the one-time `settings.json.backup` migration (`src/lib/config-migration.ts` line 23).
10. **Old dead routes:** `GET /api/settings/optimal-defaults` and `/minimax-defaults` (`src/dashboard/server/routes/settings.ts` lines 185-203) have no frontend caller. They stay; deleting them needs no-loss-matrix work that is out of scope.
11. **File-size headroom:** `src/dashboard/server/routes/settings.ts` has 0 lines free (cap 1104, current 1104). `src/lib/settings-api.ts` has 42 free. `src/cli/index.ts` has 96 free. New code goes in new files.
12. **Settings UI:** the Models area is the `#model-routing` section of `SettingsPage.tsx` (lines 484-492: `<WorkhorsePanel />` then `<RolesPanel />`). `components/Settings/__tests__/SettingsPage.test.ts` lines 90-98 pin that tag order. Lines 131-143 forbid the source text `onSave={`, `onReset={` and `hasChanges`. `SettingsPage` keeps a `formData` copy taken once (lines 370-374). Its autosave `saveSettings()` (lines 78-173) refreshes only `workhorses`, `roles`, `ui` and part of `conversations` before each whole-document PUT. Any other preset-written path (for example `models.providers`, `models.default_conversation_model`, `tiered_execution`, `tts_summarizer`) would be reverted by the next autosave from a stale `formData`.

## Decisions

- **D1: Path-scoped write door, not `saveSettingsApi`.** A new module `src/lib/model-presets/apply.ts` edits only the preset's paths. The sequence is: read the file text, `parseDocument`, apply `setIn`/`deleteIn`, validate the candidate, compare-and-swap on the file text, write atomically (temp file + `rename`), then `clearConfigCache()` (`src/lib/config-yaml/load.ts` line 184). It runs inside `runSettingsWriteSerialized` so it serializes with dashboard saves in the same process. Reason: fact 1.
- **D2: Cross-process safety by compare-and-swap.** The CLI calls the lib directly, the same way `pan skills` does. Immediately before writing, apply re-reads `config.yaml` and aborts with `ConfigChangedError` ("config.yaml changed while applying; run the command again") if the text differs from what it planned against. No HTTP round trip from the CLI.
- **D3: Validation before write.** The candidate document is converted with `doc.toJS()` and passed to `mergeConfigs(candidate)` (`src/lib/config-yaml/merge.ts` line 157), which must not throw. The result's `config.tieredExecutionInvalid` must be `undefined` whenever it was `undefined` for the current file. For every effort path the preset writes, `effortConfigErrors(path, effort, [resolvedModel])` must return `[]`. Any failure aborts the apply and writes nothing.
- **D4: Presets cover every model setting through a registry.** Each preset maps every `PRESET_SETTINGS` entry to a value or `keep` + reason. A unit test enumerates the registry. Unknown model ids fail the test (issue AC4).
- **D5: Presets ship three ids.** `anthropic` (v1), `anthropic-cost-saver` (v1, `pilot: true`, labelled "Pilot" in the UI and CLI), and `openai` (v1, evidence status `research`). The operator comment explicitly allows the cost-saver variant. It is two data rows on top of `anthropic`, so it is cheap to include.
- **D6: The OpenAI preset ships now, marked research-backed.** Its `evidence.status` is `'research'`, citing `.pan/drafts/model-routing-2026-09.md` and naming the pending gates (E2 review recall and E6 pipeline head-to-head for GPT). The docs page says this plainly on every OpenAI row. The operator asked for the OpenAI button, and issue AC3 exercises it.
- **D7: The OpenAI preset keeps background AI on its current values.** This covers titles, compaction, fork summary, handoff author, status review, the TTS summarizer, memory extraction and the provider fallback. Both presets keep `tts.summarizer.model`, because that service calls the OpenAI chat API directly with an OpenAI API key (`src/dashboard/server/services/tts-summarizer.ts` line 114). Reasons: fact 7, and the 272K GPT context pin excludes GPT from the 1M fork-summary slot. These appear as "not set" rows with the reason.
- **D8: Credentials gate the whole preset.** If `getProviderAuthMode(<preset mid model>)` returns `undefined`, the plan is `blocked` with a reason naming the sign-in or API-key step, every `change` row becomes `skipped`, and apply refuses. Per-row harness legality uses `canUseHarness`. A disallowed role, lane or tier row is `skipped` with the policy reason. A disallowed **workhorse** row blocks the whole plan, because roles reference the slots.
- **D9: Tiers are user-named, so tier rows are computed from the current config.** For each existing `tiered_execution.tiers.<name>`, the preset sets `model` to the band ref for its hardest difficulty, sets `harness` to the preset provider's harness, and sets `effort` to the band's effort when the band defines one. If the tier has a `distribution`, the preset deletes it: the row shows the old distribution with after = "(removed)", and undo restores it. If `tiered_execution.supervisor` exists, the preset sets its `model` to `workhorse:expensive` and its `harness`. The preset never touches `tiered_execution.enabled` and never creates tiers or a supervisor. With no tiers, the plan carries the note "tiered execution has no tiers; nothing to set".
- **D10: Provider nodes are written as whole raw nodes.** The row for `models.providers.<p>` holds the raw node before and after. If the node is boolean or absent, the OpenAI preset writes an object `{ enabled: true, harness: codex }`. The Anthropic preset writes boolean `true` only when the node is `false`. An absent Anthropic node is already enabled (`enabledProviders: new Set(['anthropic'])` in `src/lib/config-yaml/defaults.ts`), so it is `same`, and fresh installs get no spurious row. If it is an object, only `enabled`/`harness` change and every other key (`api_key`, `auth`) is kept. Undo restores the raw node exactly (a boolean stays a boolean). The Anthropic preset does not change `models.providers.openai`, and the OpenAI preset does not change `models.providers.anthropic`.
- **D11: Undo rule.** The undo record stores `{ presetId, version, appliedAt, changes: [{ path, before, after }] }`, where `before` is the raw JSON value or `{ absent: true }`. Undo restores a path only if its current value deep-equals `after`. Otherwise it leaves the path alone and reports "changed since apply; left as is". `absent` restores by `deleteIn`. Undo runs through the same door as apply (D1-D3), clears the undo record and clears `lastApplied`. Only one level exists: a new apply replaces the record.
- **D12: "Preset updated" state.** `~/.overdeck/model-presets-state.json` (`join(getOverdeckHome(), 'model-presets-state.json')`, `src/lib/paths.ts` line 9) holds `{ lastApplied?: { presetId, version, appliedAt }, undo?: UndoRecord }`. `listPresetStatus()` reports `updateAvailable: true` when `lastApplied.presetId === preset.id && lastApplied.version < preset.version`. Nothing auto-applies. This file stores facts that cannot be derived (what was applied, and prior values), so it is consistent with "store no status you can derive".
- **D13: New code lives in new files.** Lib: `src/lib/model-presets/`. HTTP: `src/dashboard/server/routes/model-presets.ts`, mounted in `src/dashboard/server/server.ts` beside `settingsRouteLayer` (line 365). CLI: `src/cli/commands/models.ts` as a lazy group. UI: `components/Settings/ModelPresetsBar.tsx` and `PresetDiffDialog.tsx`.
- **D14: The Settings page refreshes `formData` after an apply or undo.** `SettingsPage` passes `onPresetChanged` to `ModelPresetsBar` (never `onSave`/`onReset`). After an apply or undo, it refetches `['settings']` and replaces `formData` with the fresh document. That stops the next autosave from reverting preset-written paths (fact 12).
- **D15: One diff for CLI and UI.** The CLI `--dry-run` / `show` and the route `GET /api/model-presets/:id/plan` both return `planPresetApply()` output. `pan models preset apply <id> --dry-run --json` prints exactly the route's JSON body. The text renderer `formatPresetPlanText(plan)` lives in `src/lib/model-presets/format.ts`. The UI renders the same rows. The CLI adds `pan models preset undo`, so undo is reachable without the dashboard.
- **D16: Anthropic tier bands use the expensive slot for `expert` too.** No eval covers Fable 5.1, and it costs 2.5× Opus 5.5. A later preset version may add it.
- **D17: Size.** The plan exceeds the finalize surface lint (25 files / 6 two-segment subsystems) because every Mintlify page, fixture and generated manifest counts as its own subsystem. A sibling split does not avoid this: any slice that carries docs trips the rule. AC3 also requires the CLI and the UI to consume one diff engine. `plan.metadata.sizeJustification` records this.

## Requirements

- **FR-1** The preset data module defines `anthropic`, `anthropic-cost-saver` and `openai`, each with `id`, `label`, `provider`, `version`, `date`, `pilot`, `evidence { status: 'eval' | 'research', reportPath, summary }`, and an entry (value or keep + reason) for every `PRESET_SETTINGS` path.
- **FR-2** Every model id any preset writes passes `hasModelCapability(resolveModelId(id))`, and no id is in `MODEL_DEPRECATIONS`. Every effort value is `high` and passes `effortConfigErrors`. No preset uses `xhigh` or `max`.
- **FR-3** `planPresetApply(presetId, deps)` returns a `PresetPlan { presetId, version, provider, blocked?: { reason }, rows: Row[], notes: string[], digest }` computed against the global `config.yaml` text. It never writes.
- **FR-4** `applyPreset(presetId, { expectedDigest })` writes only the plan's `change` rows through the path-scoped door (D1-D3), records the undo record and `lastApplied`, and returns `{ applied: Row[], skipped: Row[] }`. It refuses when the plan is `blocked`, when the digest differs (`PresetPlanStaleError`), or when the file changed mid-apply (`ConfigChangedError`).
- **FR-5** `undoLastPresetApply()` restores the prior values under the D11 rule and returns `{ restored: string[], leftAsIs: { path, reason }[] }`. With no undo record it throws `NoPresetUndoError`.
- **FR-6** `listPresetStatus()` returns each preset's metadata plus `lastApplied` and `updateAvailable` (D12), and `undoAvailable: boolean`.
- **FR-7** HTTP: `GET /api/model-presets` (list + status), `GET /api/model-presets/:id/plan`, `POST /api/model-presets/:id/apply` (body `{ expectedDigest }`), `POST /api/model-presets/undo`. The two POST routes are guarded by `rejectUnsafeDashboardMutationRequest`. Errors map to 404 (unknown id), 409 (blocked, stale digest, config changed, no undo) and 400 (validation).
- **FR-8** CLI: `pan models preset list`, `pan models preset show <id>`, `pan models preset apply <id> [--dry-run] [--yes] [--json]`, `pan models preset undo [--json]`. `apply` without `--dry-run` prints the diff and asks for confirmation unless `--yes` is given. It exits 1 on a blocked plan, printing the reason.
- **FR-9** Settings → Model Routing shows one button per preset ("Apply Anthropic defaults", "Apply Anthropic cost-saver (pilot)", "Apply OpenAI defaults"). A click opens a diff dialog listing `change` rows (before → after), `skipped` rows with reasons, and notes. Confirming calls the apply route with the plan's digest. After success, a toast says "Applied <label>" with an "Undo" action. A blocked plan shows its reason, and the confirm button is disabled.
- **FR-10** When `updateAvailable` is true for a preset, Settings shows "<label> updated (v<N>): review changes". Clicking it opens that preset's diff dialog. Nothing auto-applies.
- **FR-11** After an apply or undo in the UI, `SettingsPage` refetches settings and replaces its `formData` (D14).
- **FR-12** Docs: a user page `configuration/model-presets.mdx` (listed in `docs.json` after `configuration/harnesses`) documents each preset, which model does which job and why, the eval evidence (scores, cost, delegation finding, date, link to the eval report), and the research-only status of the OpenAI preset. `configuration/harnesses.mdx`, `docs/MODEL_ROUTING.md`, `docs/CONFIGURATION.md`, `docs/MODEL-CALLS.md` and `docs/model-evals/README.md` link to it.
- **NFR-1** Applying a preset leaves every config node outside the plan's `change` paths byte-identical, including comments, `$VAR` api-key references, unknown top-level keys, and values that exist only in a project `.pan.yaml` (which never enter the global file).
- **NFR-2** An apply followed by an undo restores `config.yaml` to text that parses to a document deep-equal to the original. Every node the apply did not touch keeps its exact original text.
- **NFR-3** No hardcoded model fallback: presets only fill explicit settings. Nothing in the preset code path picks a model when a value is missing.
- **NFR-4** New lib code keeps the dashboard event loop free: no `execSync`, and only async `fs/promises` in route-reachable code.
- **NFR-5** No file grows past its `scripts/lint-file-size.sh` cap. No allowlist raise.

### WI-1 Preset data and setting registry (FR-1, FR-2, NFR-3)

Files: `src/lib/model-presets/presets.ts` (new), `tests/unit/lib/model-presets/presets.test.ts` (new).

## Hazards

- **H1: Stale Settings page tabs.** A Settings tab left open while the CLI applies a preset keeps a stale `formData`. Its next autosave reverts preset paths that `saveSettings()` does not refresh. This is pre-existing behavior for any out-of-band config edit, so it is out of scope; the docs page tells users to reload Settings after a CLI apply.
- **H2: The `models.preset` key is retired** and may be ignored or stripped by config migration. Never persist preset state in `config.yaml`.
- **H3: `routes/settings.ts` has zero line headroom.** Do not add routes there.
- **H4: `SettingsPage.test.ts` pins source text** (tag order, forbidden prop names).
- **H5: `memory.extraction.provider` and `registry.classification.provider` are coupled to their models.** The Anthropic preset writes both memory keys together. Registry stays `keep`.
