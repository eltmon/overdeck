# PAN-4929 — Skip the root dependency install when a workspace root has no package.json

**Issue:** [PAN-4929](https://github.com/eltmon/overdeck/issues/4929)
**Duplicates closed by this work:** [PAN-4553](https://github.com/eltmon/overdeck/issues/4553), [PAN-4390](https://github.com/eltmon/overdeck/issues/4390)
**Status:** planned (auto mode, 2026-11-03)

## Glossary

- **Workspace root** — the directory `createWorkspace` builds at `<project>/workspaces/feature-<issue>/`. For a monorepo it is a git worktree of the project. For a polyrepo it is a plain container directory holding one sub-directory per configured repo.
- **Polyrepo** — a project whose `projects.yaml` entry has `workspace.type: polyrepo` and a `workspace.repos[]` list. Mind Your Now (`mind-your-now`, prefix `MIN`) and botland (prefix `BOT`) are polyrepo projects.
- **Root install** — the `<package manager> install` that `createWorkspace` runs with `cwd: workspacePath`.
- **Per-repo install** — a `<package manager> install` run with `cwd: <workspacePath>/<repo.name>` for one polyrepo repo.
- **npm prefix walk** — when the current directory has no `package.json`, npm walks up the parent directories to the first one that holds `package.json` or `node_modules` and treats that as the project. If none exists it still fails with `ENOENT`.
- **Setup-incomplete marker** — the PAN-4171 marker (`src/lib/workspace-manager/setup-marker.ts`). A retry of `createWorkspace` on a workspace that carries it resumes the setup steps instead of failing with "Workspace already exists".
- **Stub package.json** — `{"name":"myn-workspace-root","private":true}`, the hand-written workaround agents put at MYN workspace roots on 2026-10-10.

## Problem

`pan start MIN-1135 --plan auto --host --yes` (2026-11-03) created every MYN sub-repo worktree and then failed:

```
✖ Workspace creation failed: Dependency install failed (npm): Command failed: npm install
npm error path /home/eltmon/Projects/package.json
```

`src/lib/workspace-manager/create.ts` runs the root install unconditionally. A polyrepo workspace root has no `package.json`, so npm walks up from `~/Projects/myn/workspaces/feature-min-1135` to `~/Projects` (which has a `node_modules/` directory since 2026-08-05), fails there, and **also writes a stray `~/Projects/package-lock.json`** (timestamp 2026-11-03 16:21, the same minute as the failure). The failure is fatal, so every MYN and botland `pan start` / `pan workspace create` aborts.

## Root cause and history (answer to the issue's question)

The issue asks why earlier MYN workspaces (MIN-1071..1076) did not hit this. **They did hit it.** The transcript `~/.claude/projects/-home-eltmon-Projects-myn/4659504b-fb56-4e58-9180-a4708993b53c.jsonl` shows an agent on 2026-10-10 writing the stub package.json into `feature-min-1046`, `1071`, `1072`, `1073`, `1074`, then `1075` and `1076`, and re-running `pan start`. The surviving roots confirm it: `~/Projects/myn/workspaces/feature-min-1072/package.json` and `feature-min-1078/package.json` both contain the stub. It was not a config change (the `hermes-plugin` repo has no root impact) and not PAN-4429 / #4431.

Timeline from `git log -S`:

1. `ada4f64db4d` / `736d0ddb03b` (2026-04-14, "make bun install failure fatal") turned an install failure into an early `return result`, but left `result.success = true`. Polyrepo creates silently skipped every setup step after the install and still reported success.
2. `0b46ac71117` (PAN-2154, 2026-07-02) moved the block into `src/lib/workspace-manager/create.ts` unchanged.
3. `ddbff6616db` ([#4163](https://github.com/eltmon/overdeck/pull/4163), PAN-3905, 2026-09-24) set `result.success = false` on that early return. From then on every polyrepo create fails. [PAN-4390](https://github.com/eltmon/overdeck/issues/4390) (MIN-1045, 2026-09-29) was the first report, [PAN-4553](https://github.com/eltmon/overdeck/issues/4553) (MIN-1046, 2026-10-10; botland BOT-1, 2026-11-02) the second.

Empirical probe (npm 10.9.4, Node 22.22.0, run in the planning scratchpad): `npm install` in an empty directory fails with `npm error enoent` both with and without an ancestor `node_modules`; with an ancestor `node_modules` it also writes `package-lock.json` into that ancestor. So the only correct root behavior is "do not run the package manager when there is no `package.json`".

## Why per-repo installs are opt-in (decision)

The issue proposes installing inside every polyrepo repo that has a `package.json`, respecting a per-repo package manager (for example pnpm for `fe`). Three verified facts make an automatic per-repo host install harmful for MYN today:

1. **Host pnpm is broken on this machine.** `pnpm --version` exits 1 with `Cannot find module '/home/eltmon/.cache/node/corepack/v1/pnpm/12.4.2/bin/pnpm.cjs'`. A fatal per-repo `pnpm install` in `fe` would keep every MYN create failing.
2. **The MYN container owns `fe/node_modules`.** `infra/.devcontainer-template/docker-compose.devcontainer.yml.template` runs `CI=true pnpm install` in the `init-fe` service against the bind-mounted `../fe`. The existing `feature-min-1078/fe/node_modules/.modules.yaml` records `storeDir: /workspaces/feature/fe/.pnpm-store/v10` (a container path). A host install would lay down `node_modules` against a different store, which pnpm refuses to reuse without an interactive purge, and `CI=true` gives it no TTY.
3. **The repo already decided this for gates.** `src/lib/cloister/verification-runner.ts` (search `Polyrepo workspace — per-repo dependencies managed by quality gates`) skips installs for polyrepo workspaces with the comment "Polyrepo workspaces manage deps per-repo via quality gate commands or containers."

Also, `myn-skills/` has a `package.json` with no lockfile: an automatic `npm install` there would create an untracked `package-lock.json` in that repo, which dirties its git status.

**Decision:** add an optional `package_manager?: 'bun' | 'npm' | 'pnpm'` field to each polyrepo repo entry (`RepoConfig`). `createWorkspace` runs a per-repo install only when that field is set **and** `<workspacePath>/<repo.name>/package.json` exists. No field ⇒ no per-repo install. The MYN config does not set the field, so MYN creates no per-repo installs and the container keeps owning `fe`. The predicate is `package.json`, never a lockfile: `api/` has `package-lock.json` but no `package.json`.

## Requirements

- **FR-1** — When `<workspacePath>/package.json` does not exist, `createWorkspace` runs no root install, removes no root `node_modules`, pushes the exact step `No root package.json; skipped root install`, emits `progress('Installing dependencies', 'No root package.json — skipped', 'complete')`, and continues setup.
- **FR-2** — When `<workspacePath>/package.json` exists, the root install behaves exactly as today: same package-manager resolution (`projectConfig.package_manager`, else `bun` if `bun.lock` exists, else `npm`), same stale `node_modules` cleanup, same command, same fatal failure.
- **FR-3** — `RepoConfig` gains `package_manager?: 'bun' | 'npm' | 'pnpm'`. For each polyrepo repo with `link_type !== 'symlink'`, the field set, and `<workspacePath>/<repo.name>/package.json` present, `createWorkspace` runs the install command for that package manager with `cwd` set to the repo directory and pushes the step `Installed dependencies in <repo.name> (<pm>)`.
- **FR-4** — A per-repo install failure is fatal: `result.success = false`, the error `Dependency install failed in <repo.name> (<pm>): <message, first 200 chars>`, progress status `error`, and an early return (the setup-incomplete marker stays, so a retry resumes).
- **FR-5** — A repo with `package_manager` set but no `package.json` in its directory pushes the step `<repo.name>: no package.json; skipped install` and runs nothing. A repo whose directory does not exist (progressive mode, not yet added) is skipped silently.
- **FR-6** — The legacy CLI path in `src/cli/commands/workspace-create.ts` (projects without `workspace` config) runs its install only when `<workspacePath>/package.json` exists.
- **FR-7** — The docs state the root-skip rule and the opt-in `repos[].package_manager` field, and stop claiming lockfile auto-detection that the code does not do.
- **NFR-1** — No new `execSync` reachable from the dashboard server. `create.ts` keeps using `execAsync`; the CLI file keeps its existing `execSync` (CLI-only).
- **NFR-2** — `src/lib/workspace-manager/create.ts` stays under the 1000-line file-size ceiling (it is 768 lines on `origin/main`).
- **NFR-3** — Tests use the existing mocked `util.promisify` / `disk-floor` scaffolding in `tests/lib/workspace-manager.test.ts`; no real package manager runs in tests.

```ts
import { existsSync } from 'fs';
import { join } from 'path';

export type WorkspacePackageManager = 'bun' | 'npm' | 'pnpm';

/** True when `dir` holds a package.json. A package manager must never run without one:
 * npm walks up to the nearest ancestor with node_modules and writes a lockfile there (PAN-4929). */
export function hasPackageJson(dir: string): boolean {
  return existsSync(join(dir, 'package.json'));
}

export function installCommandFor(pkgManager: WorkspacePackageManager): string {
  return pkgManager === 'bun' ? 'bun install' : `${pkgManager} install`;
}
```

```ts
  if (workspaceConfig.type === 'polyrepo' && workspaceConfig.repos) {
    for (const repo of workspaceConfig.repos) {
      if (repo.link_type === 'symlink' || !repo.package_manager) continue;
      const repoDir = join(workspacePath, repo.name);
      if (!existsSync(repoDir)) continue; // progressive mode: repo not added yet
      if (!hasPackageJson(repoDir)) {
        result.steps.push(`${repo.name}: no package.json; skipped install`);
        continue;
      }
      progress('Installing dependencies', `${repo.name} (${repo.package_manager})`);
      try {
        await execAsync(installCommandFor(repo.package_manager), { cwd: repoDir, encoding: 'utf-8' });
        result.steps.push(`Installed dependencies in ${repo.name} (${repo.package_manager})`);
      } catch (installErr: any) {
        result.errors.push(`Dependency install failed in ${repo.name} (${repo.package_manager}): ${installErr.message?.slice(0, 200)}`);
        result.success = false;
        progress('Installing dependencies', `Failed in ${repo.name} — workspace creation aborted`, 'error');
        return result;
      }
    }
  }
```
