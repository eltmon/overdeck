## Summary

The issue asks for a line-by-line accuracy audit of every published page in the **Features** navigation group. The
planning session already did the audit. Ten research passes read all 20 pages (5,679 lines) against the code on the
base. The planner then checked every change-table row mechanically: each grep anchor matches its page exactly once,
and each evidence quote cited with a full repo path greps in its file. Quotes cited by a bare file name, or with
escaped quotes, were not machine-checked; the planner spot-checked them for the rows below and for every section
deletion. Absence claims ("no match") were re-run for the deleted skills and the mission-control sections. The planner
also re-checked these high-stakes claims by hand:

- the model lock in conversations (`ComposerToolbar.tsx:20`, `ComposerFooter.tsx:186`, `conversation-runtime.ts:435-445`);
- every `pan handoff` option (`src/cli/index.ts:378-397`);
- the test-role dispatch gap (#5537 open; `review-pipeline.ts:644` is the only request-time dispatch; nothing emits `review.approved`);
- the server merge path (`merge-ops.ts:878`, `merge-strike.ts:630-636`);
- the `pan workspace destroy --force` no-op (`workspace-list.ts:505-523`);
- the mission-control section deletions (BadgeBar, the `ActivityView` hosts and `TranscriptUpload` have no mounted importer);
- the stale handoff-dialog screenshot (it shows a **Harness** dropdown that `ModelPicker.tsx:446-449` no longer renders).

This PRD lists every wrong, stale or removed claim per page, each with the exact current text, the replacement text and
the code evidence. The implementation agent does seven things. It applies those changes. It removes the en and em dashes.
It fixes frontmatter. It deletes the screenshots that show removed UI. It checks links. It runs the Mintlify validators.
It writes a PR body with one note per page. It does not need to re-research. It re-checks a claim only when a grep anchor
no longer matches.

## Glossary

- **Features group**: the `"group": "Features"` block in `docs.json` (line 104). On the base it lists 20 pages, each
  `features/<name>.mdx`: `issue-pipeline`, `planning`, `flywheel`, `conversations`, `file-explorer`, `mission-control`,
  `dashboard-views`, `costs`, `convoys`, `specialists`, `merge-batches`, `swarm`, `skills`, `skill-packs`, `workspaces`,
  `cloister`, `safe-shutdown`, `open-in-overdeck`, `desktop-app`, `keyboard-shortcuts`.
- **Listed pages**: the 14 pages named in the issue body. **Added pages**: the six pages the epic's child issues added to
  the group after the issue was filed (`issue-pipeline` by PAN-5468, `planning` by PAN-5469, `flywheel` by PAN-5470,
  `dashboard-views` by PAN-5474, `costs` by PAN-5475, `desktop-app` by PAN-5473).
- **Claim**: any statement on a page a reader could act on. That includes a command or flag, a config key or default, a
  UI label or location, a file path, a behavior, a limit, a keyboard binding, and a list of supported harnesses or
  platforms.
- **Primary source**: the code on the base (`git grep`), the commander definitions under `src/cli/`,
  `src/lib/config-yaml/defaults.ts`, the dashboard source under `src/dashboard/frontend/src/` and
  `src/dashboard/server/`, and `changelog.mdx`. Other `.mdx` pages, `docs/*.md`, `README.md` and skills are never proof.
  One exception: for the Flywheel loop's own behavior, `sync-sources/skills/pan-flywheel/SKILL.md` is the program
  `pan flywheel start` runs, so it counts. Where it disagrees with code, code wins.
- **Grep anchor**: the quoted current text in each change table. Line numbers drift as earlier edits land, so find the
  text with `grep -n -F '<anchor>' features/<page>.mdx`, not by line number. In the appendices an anchor is the text
  inside the outer backticks of the "Grep anchor" cell. Where a cell holds `\|`, the page has a plain `|`. Where a
  replacement holds `` \` ``, type a plain backtick; the backslash only escapes it inside the table cell. Line numbers
  in an appendix are base line numbers; each section item states its range by heading.
- **Dash rule**: no U+2013 (en dash) or U+2014 (em dash) anywhere in a touched page, frontmatter and body. Check:
  `grep -nP '[\x{2013}\x{2014}]' features/<page>.mdx` prints nothing. Replace a dash with a comma, colon, period,
  parentheses, or the word "to" for a range. Arrows (`→`) and box-drawing characters (`─`, `│`, `├`) are not dashes.
- **Frontmatter rule**: `title` is specific and searchable. `description` is 50 to 160 characters, counting the text
  between the quotes. Neither contains a dash. When this PRD retitles a page, also add `sidebarTitle: "<the old title>"`,
  unless the page already has a `sidebarTitle`, so the navigation label stays short. `configuration/docs-rag.mdx` uses
  this pattern already.
- **Experimental**: a dashboard view hidden unless Settings → Experimental → **Experimental features** is on. The gated
  tab ids are in `EXPERIMENTAL_TAB_IDS` (`src/dashboard/frontend/src/lib/experimentalFeatures.ts:4`): `agents`,
  `autopreso`, `resources`, `sessions`, `metrics`, `costs`, `health`, `god-view`. Navigating to one with the switch off
  lands on Home (`src/dashboard/frontend/src/App.tsx:410` "const nextTab = denyExperimental && isExperimentalTab(tab) ?
  'home' : tab;").
- **Stale screenshot**: a page image that shows UI the code no longer renders. This issue does not recapture images.
  Where only the alt text is wrong, the alt text is rewritten. Where the image shows removed UI, the `<ThemedImage>`
  block is deleted and a recapture goes to Follow-ups (Decision D5).
- **Follow-ups**: code bugs or out-of-scope doc problems found during the audit. They go in a `## Follow-ups` list in the
  PR body. This issue changes no code.
- **PR note**: a one-line summary of what changed on a page, or "verified, no change". Each page item puts its note in its
  commit message as a line `PR-note: features/<page>.mdx: <note>`. WI-Z1 collects them into the PR body.

## Common procedure for every page item

0. **Code wins.** If a primary source contradicts a row in this PRD (the research was wrong, or main moved), skip the
   row and record it in the PR note. Leave that row's acceptance criterion unticked and put the evidence in the commit
   message (`pan task block` with the reason). Never write a claim the code contradicts to satisfy a row.
1. **Apply the change table.** For each row, find the grep anchor with `grep -n -F`, make the change, and keep the
   evidence in mind for the replacement wording. If an anchor no longer matches because another edit moved or reworded
   it, find the claim by meaning. If the claim is gone, skip the row and say so in the PR note. "Replacement blocks"
   in an appendix hold the exact text for rows that say "see block".
2. **Spot-check before deleting.** Before deleting a whole section, re-run the row's evidence grep once. If the evidence
   no longer holds on the current branch (main moved), keep the section and note it as a Follow-up.
3. **Residual rule.** Read the whole page (or the item's line range) once. For a claim the table does not list that
   looks doubtful, verify it against a primary source. If the code disagrees, change the page to match the code. Do not
   chase claims that look right; the research passes verified the claims in each appendix's "Verified, keep" list.
4. **Dashes.** Remove every en and em dash in the item's range (dash rule). Do it in the same commit.
5. **Frontmatter.** Apply the item's title and description changes, if any. Confirm the description is 50 to 160
   characters and dash-free. Quote a `description` that contains `: ` (every new value below is already quoted).
6. **Links.** For each internal link, `ls <path>.mdx`, and for an anchor `grep -n "^#.*<heading words>"`, counting
   `docs.json` redirects. Fix any that fail.
7. **MDX safety.** Keep any new `<word>` placeholder inside backticks. Run `npm run lint:docs`.
8. **Commit** with `Item: <id>`, its AC trailers and `PR-note: features/<page>.mdx: <one line>`. Push. Run `pan task done`.
