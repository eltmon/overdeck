## Glossary

- **Sign-in (family):** one approved OAuth grant for one client, stored in `~/.overdeck/mcp-oauth.json` as a family record (`oauthFamilyId`, 32 hex). It holds the current access token (`odk_`, 30 days) and a rotating refresh token (`odr_`, 90 days). Ending the family ends both.
- **Pending approval:** an in-memory record the server creates when a client opens `GET /oauth/mcp/authorize`. It has an id (32 hex), an **approval code** (`ABCD-EFGH`, 8 letters from A-Z without I and O), the client name, the redirect host, a requested level and a 10-minute expiry. A dashboard restart loses it.
- **Level:** one of four access levels; the frontend shows the label. `read` = Read only (`read:state, read:conversations`), `message` = Can message (+ `tell`), `operate` = Can operate (+ `operate`), `approve` = Can approve (+ `approve`). Defined in `LEVEL_LABELS` / `LEVEL_SCOPES`, `src/lib/mcp/oauth-flow.ts:19-34`.
- **Root viewer:** a browser whose credential is the root session cookie, or a caller with the internal token. `AnywhereStatus.viewer.kind` (`GET /api/anywhere/status`) reports it as `'root-session'` or `'internal-token'`. Every `/api/mcp-oauth/*` route answers 403 to anyone else (`mcp-oauth-admin.ts:39-44`, `rejectRequest`).
- **Decision:** one row of "everything waiting on the operator", the `Decision` interface in `src/dashboard/frontend/src/lib/useDecisions.ts:84-127`. `useDecisions()` (line 305) builds the list; `DecisionsPanel`, `DecisionsCount`, `DecisionsIndicator` and `MobileNeedsYou` read it.
- **Pending-input kind:** a string in `Decision.kinds`, labelled through `PENDING_INPUT_KIND_LABEL` (`src/dashboard/frontend/src/lib/pendingInput.ts:28-41`).
- **Agent token:** a `kind: 'token'` access-token record with `agentId` set (PAN-4930). One exists per running managed agent, so it floods the token lists.
- **Frontend test subset:** `scripts/frontend-test-subset.txt`. CI runs only the frontend Vitest files listed there (one path per line, relative to `src/dashboard/frontend`, `merge=union`). A new frontend test file that is not listed never runs in CI.

All frontend paths below are relative to `src/dashboard/frontend/src/` unless they start with `src/`, `scripts/`, `docs/`, `configuration/` or `.overdeck/`.

## Facts this plan is built on (verified 2026-11-04 at `648b7574c1f`)

**The operator routes (W-OAUTH1, `src/dashboard/server/routes/mcp-oauth-admin.ts`).** All answer `Cache-Control: no-store` and 403 `{ error }` to a non-root credential.

| Route | Request | Answer |
|---|---|---|
| `GET /api/mcp-oauth/approvals` | — | `{ approvals: PendingApprovalView[] }`, pending and unexpired only, oldest first |
| `POST /api/mcp-oauth/approvals/:id` | `{ decision: 'approve', level }` or `{ decision: 'deny' }` | 200 `{ status: 'approved' \| 'denied' }`; 400 bad body or level; 404 `unknown or expired sign-in request`; 409 `this sign-in request was already <status>` |
| `GET /api/mcp-oauth/sign-ins` | — | `{ signIns: SignInView[] }`, active families only |
| `DELETE /api/mcp-oauth/sign-ins/:familyId` | — | 200 `{ revoked: true }`; 404 `no active sign-in <id>` |

Mutations go through `rejectUnsafeDashboardMutationRequest`, so the browser must send the CSRF headers from `dashboardMutationJsonHeaders()` (`lib/wsTransport`), as `revokeAccessToken` does (`components/Settings/anywhere/anywhereApi.ts:216-221`).

The view shapes (`src/lib/mcp/oauth-service.ts:68-89`):

```ts
export interface PendingApprovalView {
  id: string; clientId: string; clientName: string; redirectHost: string;
  requestedLevel: OAuthLevel; approvalCode: string; createdAt: string; expiresAt: string;
}
export interface SignInView {
  familyId: string; clientId: string; clientName: string; level: OAuthLevel; scopes: string[];
  createdAt: string; lastUsedAt: string | null; accessExpiresAt: string | null;
  refreshExpiresAt: string; headless: boolean;
}
```

## Requirements

### Functional

- **FR-1 Approval card.** For each pending approval, a root viewer's Needs-you panel shows a card: "<client name> wants access to Overdeck", the redirect host, the approval code in large monospace type, and the sentence "Approve only if the page you opened shows this code." It has a level select (Read only, Can message, Can operate, Can approve) that defaults to the approval's requested level, an Approve button and a Deny button.
- **FR-2 Decide.** Approve posts `{ decision: 'approve', level }` with the selected level; Deny posts `{ decision: 'deny' }`. A failure shows the server's error text on the card. The card leaves the list on the next poll after the server stops listing it.
- **FR-3 Feed.** `useDecisions()` adds one blocking decision of kind `mcpSignIn` per pending approval, polled every 5 s, only while the viewer is a root viewer. The count badge and the indicator include it.
- **FR-4 Sign-in list.** Settings → Access Tokens and Settings → Anywhere → Access tokens each show a "Sign-ins" list of active sign-ins: client name, level label, created, last used, expires, a "headless" chip for `pan mcp oauth issue` sign-ins, and Revoke. Revoke asks for confirmation, then ends the sign-in.
- **FR-5 Agent tokens folded.** Both token lists hide records with `agentId` behind a "Show agent tokens (N)" toggle, collapsed by default.
- **FR-6 Mobile.** The phone Needs-you screen shows an MCP sign-in row with "Approve on the desktop" and no answer controls.

### Non-functional

- **NFR-1 No new server surface.** No new route, route-scope row, no-loss row, CLI verb, config key or `src/lib` change. The diff is confined to `src/dashboard/frontend/src/`, `scripts/frontend-test-subset.txt` and documentation.
- **NFR-2 No secret in the browser.** No token, refresh token or code verifier ever reaches the frontend; the approval code is not a secret (the authorize page shows it publicly). Nothing logs.
- **NFR-3 Fake timers.** Any test that waits on a poll or a timeout uses `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`, never real sleeps (repo rule `fake-timers-for-retry-tests`). Tests that touch happy-dom never use `AbortSignal.timeout`, which ignores fake timers; use an `AbortController` plus `setTimeout`.
- **NFR-4 File size.** New modules stay under 600 lines. No file grows past its `origin/main` line count plus the budget in its work item; no file here is near the 1,000-line guard.
- **NFR-5 Style.** Follow the dashboard style guide (skill `pan-style-guide`): no Inter, no pill badges, no decorative color, weights within their tier. The card reuses the `decisions.module.css` row, badge and button classes; new classes are limited to the code display and the level select.
- **NFR-6 Tests run in CI.** Every new frontend test file is added to `scripts/frontend-test-subset.txt` in sorted position.
- **NFR-7 Gate is not the boundary.** The root-viewer gate on the approvals query only avoids a 403 poll from phones and paired devices. The server's root check (`mcp-oauth-admin.ts:39-44`) is the security boundary.

## Decisions

- **D-1 Surfaces.** The Sign-ins list is one component, `components/Settings/anywhere/McpSignInsList.tsx`, mounted in both `AccessTokensSection` (Settings → Access Tokens, the surface AC-17 names) and `AccessTokensPanel` (the epic's file list). Why: the token list already appears in both places on one shared query key, and both are where an operator looks for MCP access.
- **D-2 Decision shape.** `Decision` gains `mcpSignIn?: McpSignInApproval` (the whole `PendingApprovalView` row). The row uses `id = approval.id`, `source: 'agent'`, `label = clientName`, `kinds: ['mcpSignIn']`, `since = createdAt`, `blocking: true`. Every consumer checks `decision.mcpSignIn` before `decision.source`.
- **D-3 Blocking.** `mcpSignIn` joins `BLOCKING_KINDS`. Why: a person is parked on the authorize page, and the request dies in 10 minutes.
- **D-4 Label.** `PENDING_INPUT_KIND_LABEL.mcpSignIn = 'MCP sign-in waiting'`.
- **D-5 Root gate.** `useDecisions` reads `ANYWHERE_STATUS_QUERY_KEY` with `loadAnywhereStatus`, `staleTime: 60_000`, `retry: false`. The approvals query (`queryKey: ['mcp-oauth-approvals']`, `refetchInterval: 5000`) is `enabled` only when `status.viewer.kind` is `'root-session'` or `'internal-token'`. A non-root viewer therefore never sees the card (NFR-7).
- **D-6 Fetch errors.** `fetchMcpSignInApprovals` resolves `[]` on any non-2xx or network error, like `fetchAgentRequests`, so a 403 or 404 never throws inside `useDecisions`.
- **D-7 No optimistic hide.** After a decision, the card invalidates `['mcp-oauth-approvals']`. On 404 or 409 it shows the error (for example, `pan mcp oauth approve` raced the card) and still invalidates, so the next fetch drops the row.
- **D-8 Level default.** The select starts at `approval.requestedLevel` when it is one of the four levels, else `read`.
- **D-9 Client API home.** All frontend OAuth types, the level mirror, query keys and fetchers live in `components/Settings/anywhere/anywhereApi.ts` (276 lines, budget +70), beside `MCP_DEFAULT_SCOPES`. The level mirror carries the comment "mirrors LEVEL_LABELS in src/lib/mcp/oauth-flow.ts".
- **D-10 Revoke refresh.** After revoking a sign-in, invalidate `MCP_SIGN_INS_QUERY_KEY` and `ANYWHERE_ACCESS_TOKENS_QUERY_KEY`, because the family's access token is revoked too.
- **D-11 Sign-ins 403.** `loadMcpSignIns` throws `AccessTokensForbiddenError` on 403, and the list shows "Only a browser on this machine can list sign-ins." (the token panel's wording, `AccessTokensPanel.tsx:52`). Any other failure shows "Could not load sign-ins: <message>".
- **D-12 "Expires".** The list's expires column shows `refreshExpiresAt`, when the sign-in ends unless the client refreshes. `accessExpiresAt` is not shown.
- **D-13 OAuth access tokens stay in the token lists.** The lists keep showing `oauthClientId` records as today; `mcp.mdx:323-325` already documents revoking one there. Only agent tokens fold.
- **D-14 Agent-token count.** N in "Show agent tokens (N)" counts every listed record with `agentId`, revoked ones included, because both lists show revoked rows. With N = 0 the toggle is not rendered.
- **D-15 Polling.** The sign-ins query polls every 5 s (`refetchInterval: 5000`, `retry: false`), matching `AccessTokensPanel`, so a newly swapped code shows without a reload.

## Hazards

- **H-1 The status query is new in `useDecisions`.** Every consumer now triggers `GET /api/anywhere/status` once per minute at most. A test that renders the real `useDecisions` without seeding it falls through to the test's fetch stub; the approvals query then stays disabled. That is the intended failure mode; do not add a retry.
- **H-2 Restart loses approvals.** Pending approvals are in memory; after a dashboard restart the card disappears and the client's page shows `expired`. Expected; documented in `mcp.mdx:216-218`.
- **H-3 Race with the CLI.** `pan mcp oauth approve` can decide a request while the card is open; the card's click then gets 409 and shows it (D-7).
- **H-4 Settings page shows the list twice.** Both token surfaces are on the one Settings page, so the Sign-ins list appears twice, as the token list already does. Accepted (D-1).
- **H-5 Approve does not mint immediately.** A sign-in appears in the list only after the client swaps its code (within 60 s). UAT must let the client finish the exchange before checking the list.

## Out of scope

- Any server, route, CLI, config or `src/lib` change (NFR-1).
- Approving from a phone or a paired device, or from a linked machine's dashboard.
- Notifications (desktop, push, TTS) for a new sign-in.
- Editing a sign-in's level after approval.
- Hiding OAuth access tokens from the token lists (D-13).
- Widening `PendingInputSource`.
