# PAN-4628: npx launch — panes get a stale internal token, so `pan pair` and other CLI calls are rejected

**Issue:** [PAN-4628](https://github.com/eltmon/overdeck/issues/4628) · **Parent PRD:** `.pan/drafts/pan-2350.md` (Overdeck Anywhere, rev. 5), work item **W-SEC2**, parent requirement FR-1 (pairing is how machines link). **Follow-up that builds on this:** [PAN-4656](https://github.com/eltmon/overdeck/issues/4656) (W-LINK9, `pan connect`).

**Done when (W-SEC2):** `pan pair` on a fresh `npx @overdeck/core` machine prints a link another machine can use, and CLI calls from panes that inherited an old token keep working after the dashboard is restarted with npx.

## Glossary

- **Internal token** — the machine's root secret for the dashboard. The server compares it against the `x-overdeck-internal-token` header (or `Authorization: Bearer`). Resolved by `src/lib/internal-token.ts`.
- **Token file** — `<OVERDECK_HOME>/internal-token` (default `~/.overdeck/internal-token`), mode `0600`, one line of 64 hex characters.
- **Env token** — the `OVERDECK_INTERNAL_TOKEN` environment variable.
- **`pan serve`** — the npx launcher command. `npx @overdeck/core` with no arguments runs `pan serve` (`src/cli/index.ts` line 86: `process.argv.push('serve')`). It spawns `dist/dashboard/server.js` and opens the browser.
- **`pan up`** — the normal launcher. Its server calls `ensureInternalToken()` at boot (`src/dashboard/server/main.ts` line 139) and never sees an env token.
- **Herdr server** — the long-lived `herdr --session <session> server` process. It is started detached or as a systemd user unit and is never restarted by Overdeck (`src/lib/herdr-setup/service.ts` header). Every pane it opens inherits the environment the Herdr server had when it started.
- **Stale pane** — a pane whose environment carries an env token from an earlier `pan serve` run, which the running dashboard no longer holds.
- **Reader** — any code that resolves the internal token to send or check it. There are seven (listed in "Cause").

## Problem and verified cause

On a machine started with `npx @overdeck/core`, `pan pair` and `pan devices list` fail with: *"The dashboard rejected this machine's internal token. `pan pair` needs a dashboard started by `pan up` (a `pan serve` server does not share it)."* Any CLI → dashboard call from a pane fails the same way, and hook heartbeats from those panes get 403.

Verified in code on `feature/pan-4628` at `7dcd0bebe41` (== `origin/main`):

1. **`pan serve` mints a throwaway token.** `src/cli/index.ts` lines 1215–1272 (anchor: `const internalToken = process.env.OVERDECK_INTERNAL_TOKEN || randomBytes(32).toString('hex');`, line 1235). It passes the token to the server only through env (line 1249: `env: { ...process.env, PORT: String(port), OVERDECK_INTERNAL_TOKEN: internalToken }`) and never writes the token file. So on a fresh npx machine the file does not exist, and the token changes on every launch.
2. **Every reader prefers env over the file.** So an env token, once present, always wins, even when it is stale:
   - `src/lib/internal-token.ts` lines 41–64, `getInternalToken()` (anchor: `const fromEnv = process.env.OVERDECK_INTERNAL_TOKEN;`, line 44). `ensureInternalToken()` (lines 74–95) calls it first.
   - `src/dashboard/server/routes/agents/shared.ts` lines 221–230, `readInternalTokenForRequest()` (server side, used by `validateAgentRuntimeEventAuth`).
   - `src/lib/caveman/workspace.ts` lines 219–224, the generated hook script's `function internalToken()`.
   - `sync-sources/hooks/pan-hook-lib.sh` lines 264–275 (`PAN_INTERNAL_TOKEN="${OVERDECK_INTERNAL_TOKEN:-}"`).
   - `sync-sources/hooks/session-start-hook` lines 80–86, `sync-sources/hooks/user-prompt-submit-hook` lines 33–39, `sync-sources/hooks/stop-hook` lines 75–81 (each `INTERNAL_TOKEN="${OVERDECK_INTERNAL_TOKEN:-}"` then a file fallback).
3. **The Herdr server keeps the first token it saw.** When the dashboard spawns the Herdr server detached, the server inherits the dashboard's env, including the env token of that `pan serve` run. Panes inherit it from Herdr. After a later npx launch the dashboard holds a new token; panes still send the old one; the server answers 401.
4. **On a fresh npx machine it fails even without a stale Herdr server.** With no token file, a CLI process with no env token calls `ensureInternalToken()`, which generates a *new* file token that the env-token server has never seen. On systemd hosts the Herdr unit carries no env token, so every pane is in this state.

The issue reporter verified (3) on a live machine: conversation token == Herdr server token != dashboard token, and the token file was absent.

## Decisions

- **D-1 The token file is the single source of truth; readers check it first.** Every reader resolves: token file (non-empty) → env token → none. *Rejected alternative:* inject the current token into each pane's env in `launchAgentPane`. Reasons: (a) it reaches only panes launched after the fix, while existing panes of an old Herdr server stay broken until Herdr restarts, which Overdeck never does; (b) `launchAgentPane` also runs in CLI processes (`src/lib/agents/spawn.ts`, `resume.ts`, `recovery.ts`), which would copy their own stale value; (c) it puts the root secret into every agent's environment, where `env`/`printenv` output lands in transcripts that sync to other machines, against "The machine's root internal token never leaves the machine" (`configuration/remote-access.mdx` line 12). File-first fixes existing stale panes on the next `pan` call and the next hook run, because each call re-resolves.
- **D-2 `ensureInternalToken()` seeds the file from env when no file exists.** Order: token file → (no file) write `env token ?? random 32-byte hex` to the file with mode `0600` and return it. After the first `ensureInternalToken()` on a home, the file always exists, so all readers agree. An env token is therefore only a seed: once the file exists, `OVERDECK_INTERNAL_TOKEN` is ignored. `getInternalToken()` never writes.
- **D-3 Cache by source.** `getInternalToken()` keeps its process-wide cache, but `ensureInternalToken()` returns the cached value without file I/O only when it came from the file. A value cached from env still goes through the file check and the seed write. This keeps per-request server paths (`deacon-event-client.ts` calls `ensureInternalToken()` per request) free of repeated sync reads after boot (NFR-2).
- **D-4 `pan serve` resolves its token with `ensureInternalToken()` and stops adding it to the server's env.** The child still inherits an operator-set `OVERDECK_INTERNAL_TOKEN` through `...process.env`; the child's own `ensureInternalToken()` then reads the file the parent just wrote. The browser fragment `#overdeck_token=` uses the same value. With no explicit env token, the dashboard's environment no longer carries the secret, so a Herdr server spawned from it never captures one.
- **D-5 Extract the `serve` action to `src/cli/commands/serve.ts`.** Registered with the existing `lazyAction(() => import('./commands/serve.js'), 'serveCommand')` pattern, with injectable `spawn` and browser opener so a unit test can check the token and the child env. Paths are resolved from `packageRoot` (`src/lib/paths.ts` line 97), not `import.meta.url`: the CLI loads command modules lazily as `dist/` chunks (PAN-4195; see the comment at `src/cli/commands/dev.ts` lines 13–15). `src/cli/index.ts` shrinks by about 55 lines; no allowlist change.
- **D-6 New `pan pair` / `pan devices` 401 text.** After D-1–D-4 a 401 means the token file does not match the running dashboard: a different `OVERDECK_HOME`, or a dashboard started before this fix (it still holds a throwaway npx token). The message says so and tells the operator to restart the dashboard. It no longer claims `pan serve` is unsupported.
- **D-7 Docs: the issue's "Docs: None" is overridden.** `configuration/remote-access.mdx` lines 85–87 state the behavior this issue removes, and `docs/DASHBOARD-AUTH.md` lines 10–13 describe the token without its resolution order. Both change (work item 7).

## Requirements

- **FR-1** `pan serve` resolves the internal token with `ensureInternalToken()`, so `<OVERDECK_HOME>/internal-token` exists after the first npx launch and holds the same value on every later launch.
- **FR-2** `pan serve` does not add `OVERDECK_INTERNAL_TOKEN` to the dashboard child's env; the child sees the variable only when the operator set it.
- **FR-3** `getInternalToken()` returns the token file's value when the file exists and is non-empty, else the env token, else `null`.
- **FR-4** `ensureInternalToken()` returns the token file's value when present; otherwise it writes `env token ?? random` to the file (mode `0600`) and returns it.
- **FR-5** The server-side reader `readInternalTokenForRequest()` uses the order of FR-3.
- **FR-6** The caveman hook script's `internalToken()` uses the order of FR-3.
- **FR-7** The four shell readers (`pan-hook-lib.sh`, `session-start-hook`, `user-prompt-submit-hook`, `stop-hook`) use the order of FR-3.
- **FR-8** On a 401, `pan pair`, `pan devices list` and `pan devices revoke` print the D-6 message.
- **FR-9** `docs/DASHBOARD-AUTH.md` and `configuration/remote-access.mdx` state the file-first resolution order and that `pan pair` works with dashboards started by `pan up` or `npx @overdeck/core`.
- **NFR-1** No change puts the internal token into a pane's environment. `launchAgentPane` and the Herdr spawn are not changed.
- **NFR-2** After the server boots, resolving the token in a request path does no file I/O (`getInternalToken()` and `ensureInternalToken()` hit the cache).
- **NFR-3** `src/cli/index.ts` does not grow; no `scripts/file-size-allowlist.txt` row is added or raised.

function readTokenFile(): string | null {
  const path = tokenFilePath();
  if (!existsSync(path)) return null;
  try {
    const value = readFileSync(path, 'utf8').trim();
    return value.length > 0 ? value : null;
  } catch {
    return null;
  }
}

function envToken(): string | null {
  const value = process.env.OVERDECK_INTERNAL_TOKEN;
  return value && value.length > 0 ? value : null;
}

export function getInternalToken(): string | null {
  if (cached !== undefined) return cached?.token ?? null;
  const fromFile = readTokenFile();
  if (fromFile) cached = { token: fromFile, source: 'file' };
  else {
    const fromEnv = envToken();
    cached = fromEnv ? { token: fromEnv, source: 'env' } : null;
  }
  return cached?.token ?? null;
}

export function ensureInternalToken(): string {
  if (cached?.source === 'file') return cached.token;

  const token = envToken() ?? randomBytes(32).toString('hex');

## Hazards

- **H-1 An operator-set env token no longer overrides an existing file.** `scripts/windows-smoke/probe.ps1` lines 249–251 set `OVERDECK_INTERNAL_TOKEN` for `pan serve` on a fresh home: the seed rule (D-2) writes it to the file, so the probe still matches. Any setup that relied on env overriding an existing file must write the file instead (documented in item 7).
- **H-2 Test pollution through the seed write.** `ensureInternalToken()` now writes the file when env is set. A test file that calls a CLI sender (pair, devices, merge, plan, start) with one env token and later expects a different env token in the same temp home would read the first one. Mitigation: the regression sweep; fix any such test by deleting the token file in `beforeEach`, not by changing the resolver.
- **H-3 Hooks reach running panes only after `pan sync`.** The synced copies under the operator's home are not updated by the merge itself.
- **H-4 A dashboard started before this fix still holds its old env-only token.** CLIs will read the (new or absent) file and get 401 with the D-6 message until the operator restarts the dashboard once.
- **H-6 Already-generated caveman scripts keep the old order.** Workspaces set up before the merge keep their generated script until the caveman setup runs again; the fix reaches new or re-set-up workspaces.
- **H-5 Lazy chunk paths.** `serve.ts` must resolve the bundle from `packageRoot`, not `import.meta.url` (D-5).
