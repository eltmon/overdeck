# PAN-5282: Upgrade CLIProxy to v8.0.71 with a v8-layout generated config

Issue: [PAN-5282](https://github.com/eltmon/overdeck/issues/5282). It blocks [PAN-5278](https://github.com/eltmon/overdeck/issues/5278), which is paused until this merges. This issue takes over PAN-5278's work item 1.

Revised 2026-11-14 by the planning session. The first draft's FR-1 upgrade path was wrong against the code (a running proxy never upgraded, and a running v7 would hot-reload a v8 config it cannot read). This revision fixes that, settles the open questions with a live v8.0.71 probe, and splits the work into small items.

## Glossary

- **CLIProxy**: the CLIProxyAPI sidecar Overdeck installs and supervises (`src/lib/cliproxy.ts`). It listens on `127.0.0.1:8317`. Claude Code agents that run GPT (or Gemini) models point `ANTHROPIC_BASE_URL` at it.
- **Pin**: `CLIPROXY_RELEASE_VERSION` in `src/lib/cliproxy.ts` (line 69, grep `const CLIPROXY_RELEASE_VERSION = 'v7.3.16';`). `installCliproxy` downloads that release. `isCliproxyUpToDateTask` (line 461) runs the installed binary with `--version` and compares the banner to the pin.
- **Stale binary**: the installed binary's version is not the pin. Overdeck installs a new binary either while no proxy runs or (new in this issue) immediately before it stops the old proxy, so "installed binary is current" stands in for "the running proxy is current". One window breaks that: if the process dies between the download and the stop, an old proxy keeps running beside a current binary. `pan restart --cliproxy` recovers it (it stops first).
- **Hot reload**: CLIProxy watches `config.yaml` and reloads it in place. Verified on the live machine: the proxy (pid started 2026-11-03 08:30) logged `config successfully reloaded` at 2026-11-14 12:53:02, when `config.yaml` changed. v8.0.71 does the same: in a throwaway probe, an in-place overwrite of `config.yaml` that added a second `access.api-keys` entry made that key return 200 on `/v1/models` within about a second, and the log said `api-keys count: 1 -> 2` and `config successfully reloaded`. An earlier `sed -i` edit (which replaces the file by rename) was **not** picked up, so Overdeck must keep writing `config.yaml` in place with `writeFile`, never by temp file plus rename.
- **Legacy layout**: the v7 flat config keys (`host`, `port`, `auth-dir`, `api-keys` as a list, `gemini-api-key`, `debug`, `remote-management`, `oauth-model-alias`, `oauth-excluded-models`, `request-retry`, `max-retry-interval`, `proxy-url`).
- **v8 layout**: the nested config that starts with `config-version: 8` and has `server:`, `access:`, `management:`, `routing:`, `observability:` and `oauth:` sections (upstream `config.example.yaml` at tag `v8.0.71`). In v8 the root `api-keys:` is a **mapping** of upstream provider groups (`api-keys.gemini`, …), while client keys live in `access.api-keys`. "These cannot share one YAML key" (example, legacy-compatibility block at the end).
- **`config.extra.yaml`**: the operator-owned file `~/.overdeck/cliproxy/config.extra.yaml`. Today `buildCliproxyConfig` appends it to the generated config as text (`readConfigExtra`, line 329). On the operator's machine it holds legacy-layout `oauth-model-alias.codex` (9 aliases), a `remote-management` block with a plaintext `secret-key`, and a v8-compatible `routing` block.
- **Codex alias**: an entry under `oauth-model-alias.codex` (legacy) or `oauth.model-alias.codex` (v8): `{ name: <upstream Codex model>, alias: <client-visible name> }`, for example `{ name: gpt-6-sol, alias: claude-opus-5 }`.
- **Model pool collision**: v8 builds one merged `/v1` model list and routes a client model name to any upstream that offers it. The `oauth:` section of the example says: "Because aliases affect the merged /v1 model list and merged request routing, overlapping client-visible names can become ambiguous across providers." A real Claude account natively offers names such as `claude-fable-5`, `claude-opus-4-6` and `claude-sonnet-4-6`, which the operator's Codex aliases also claim.
- **Management API**: CLIProxy's admin API under `/v0/management/*` (unchanged paths and payloads in v8, upstream `docs/management-api-v8.md` "v0 compatibility") and `/v8/management/*`. The key is `management.secret-key`. An empty key turns the API off (404).
- **Bcrypt-shaped key**: a string matching `/^\$2[aby]\$\d{2}\$/`. CLIProxy replaces a plaintext `secret-key` in `config.yaml` with its bcrypt hash on startup.

## Requirements

- **FR-1** The pin is `v8.0.71`.
- **FR-2** Overdeck writes `config.yaml` in the v8 layout, starting with `config-version: 8`, built as an object and serialized with the `yaml` package.
- **FR-3** `config.extra.yaml` is parsed as YAML, its legacy keys are converted to v8 keys (Decision 3), and the result is deep-merged over the generated config. Extra wins on conflicts. An unparseable extra file is logged and ignored, so the proxy still starts.
- **FR-4** The generated config sets `routing.session-affinity: true` and `routing.session-affinity-ttl: "1h"`. Extra may override both.
- **FR-5** The generated config enables the management API on localhost only: `management.allow-remote: false`, `management.secret-key` = the plaintext key in `~/.overdeck/cliproxy/management-key`. Overdeck creates that file (mode 0600, random key) when it is missing or empty. A plaintext `secret-key` from extra (v8 `management.secret-key` or legacy `remote-management.secret-key`) wins and Overdeck writes it into the key file, so the key file always holds the active plaintext key. A bcrypt-shaped extra key is ignored with a log line, and the key file's key is used.
- **FR-6** After the merge, `oauth.excluded-models.claude` contains every `alias` string under `oauth.model-alias.codex`, unioned with any entries already there, de-duplicated and sorted. The key is written only when that list is non-empty.
- **FR-7** `export async function readManagementKey(): Promise<string | null>` exists in `src/lib/cliproxy.ts` for PAN-5278.
- **FR-8** Overdeck never writes the v8 layout while a stale binary may be running. `startCliproxy` with a running stale proxy downloads the pinned binary first, then stops the old proxy, writes the config and starts the new one. If the download fails, the old proxy keeps running and `config.yaml` is untouched. `bridgeGeminiAuthToCliproxy` writes the config directly only when the binary is current; otherwise it calls `startCliproxy()`, which upgrades and then writes.
- **FR-9** `config.yaml` is rewritten only when its parsed content differs from the generated object, ignoring a bcrypt-shaped `management.secret-key` on disk unless the active key changed in this build. A missing or unparseable `config.yaml` is always written.
- **FR-10** After every config ensure, `config.yaml` has mode 0600.
- **NFR-1** All new code is async. The sync `ensureConfigFile`, the text `readConfigExtra`, `buildCliproxyConfig`, `serializeYamlString` and the sync `readBridgedGeminiApiKey` are deleted (one variant per operation, `docs/EFFECT-BRIDGING.md`). `startCliproxy` uses `ensureDirsAsync`.
- **NFR-2** No test talks to port 8317, the live `~/.overdeck/cliproxy/` directory, any upstream provider, or spawns a real CLIProxy. The decision logic in FR-8 and FR-9 lives in pure functions with direct unit tests.

## Decisions

1. **Pin `v8.0.71`.** Do not chase a later patch in this issue.
2. **Module split.**
   - `src/lib/cliproxy-config.ts` (new, pure, no I/O): `convertLegacyKeys`, `deepMerge`, `isBcryptHash`, `buildCliproxyConfigV8`, `configNeedsWrite`, `planCliproxyStart`. It imports only from `yaml` and `node:util`. Host, port and the client token come in as arguments, so it never imports `cliproxy.ts` (`npm run lint:circular`).
   - `src/lib/cliproxy-config-files.ts` (new, async file I/O, every function takes paths as arguments): `readManagementKeyFile`, `writeManagementKeyFile`, `generateManagementKey`, `readConfigExtraFile`, `writeCliproxyConfig`. It imports from `cliproxy-config.ts`, never from `cliproxy.ts`.
   - `src/lib/cliproxy.ts` keeps the lifecycle and owns the default paths. It wires the helpers into `ensureConfigFileAsync`, `startCliproxy` and the Gemini bridge, and exports `readManagementKey()`.
3. **Legacy-to-v8 conversion of extra** covers exactly these top-level keys. Every other key is merged as-is (v8 still reads legacy keys):

   | Legacy key in extra | v8 key |
   | --- | --- |
   | `host` | `server.host` |
   | `port` | `server.port` |
   | `remote-management` | `management` |
   | `api-keys` **when it is a list** | `access.api-keys` |
   | `request-retry` | `routing.retry.request-retry` |
   | `max-retry-interval` | `routing.retry.max-retry-interval` |
   | `debug` | `observability.logs.debug` |
   | `proxy-url` | `requests.proxy-url` |
   | `auth-dir` | `oauth.auth-dir` |
   | `oauth-model-alias` | `oauth.model-alias` |
   | `oauth-excluded-models` | `oauth.excluded-models` |

   A root `api-keys` that is a mapping is already the v8 provider-group shape and stays where it is. Conversion order: build the converted legacy object first, then deep-merge extra's v8-spelled keys over it, so a v8 key in extra beats its legacy twin in extra (same rule as upstream). `gemini-api-key` and `codex:` are not converted (NonGoals).
4. **Deep merge rule.** Plain objects merge key by key. Arrays and scalars from the overlay replace the base value. `null` in the overlay replaces too. The FR-6 exclusion list and the client-token rule (Decision 5) run after the merge.
5. **Overdeck's client token stays.** After the merge, if `access.api-keys` is not a list, set it to `[clientToken]`; if it is a list without `clientToken`, append it. Overdeck's own clients use that token (`getCliproxyClientEnv`, line 536).
6. **Do not edit the operator's `config.extra.yaml`.** Conversion happens in memory on every build.
7. **Gemini key** goes to `api-keys.gemini: [{ name: 'overdeck-gemini', keys: [{ 'api-key': <key> }] }]`. Leave out `quota-exceeded`.
8. **Upgrade trigger: explicit start paths only.** `startCliproxy` upgrades a running stale proxy (FR-8). That covers `pan up`, `pan dev`, `pan restart --cliproxy`, the dashboard Restart CLIProxy button, the watchdog, and the first Gemini spawn through the claude-code harness (the bridge calls `startCliproxy()` when the binary is stale). A dashboard reload does not restart the proxy. Docs and the changelog tell the operator to run `pan restart --cliproxy` once after updating. Rationale: an automatic restart on every dashboard boot would interrupt in-flight GPT requests on routine reloads; the upgrade is a one-time event the operator triggers right before signing Claude in.
9. **Operator alias targets are not rewritten.** If v8 hides an alias because its upstream model is not in the account's catalog (Verified fact 11), the operator edits `config.extra.yaml`. The docs say how to check (`GET /v1/models`).
10. **Churn rule (FR-9) by semantic compare**, not a sidecar file: parse the on-disk YAML; if its `management.secret-key` is bcrypt-shaped and the active key did not change, compare as if it held the generated plaintext; rewrite only on a difference. This works across the CLI and dashboard processes and still restores a hand-edited `config.yaml`.
11. **Global exclusion, no per-account fallback.** Verified fact 10 shows `oauth.excluded-models.claude` works on v8.0.71. If the work agent's own probe (work item 9) contradicts it, stop and report through `pan tell flywheel-orchestrator`; do not improvise a per-account rewrite.
12. **Management key generation:** `randomBytes(24).toString('base64url')` (32 characters).
13. **Write `config.yaml` in place.** Use `writeFile` (truncate and write), never a temp file plus rename: v8's watcher missed a rename in the probe (Glossary, Hot reload).
14. **Leave the management control panel at its default (enabled).** Turning the management API on for everyone also lets CLIProxy download its web panel from GitHub. The operator uses that panel today (`~/.overdeck/cliproxy/static/` exists), and the base config stays minimal. An operator who wants it off sets `management.disable-control-panel: true` in extra.
15. **Key rotation.** The active key comes from extra when extra sets a plaintext one, else from the key file. Editing the key file by hand does not reach a running proxy whose `config.yaml` holds a hash, because the compare (Decision 10) treats the hash as unchanged. To rotate, set `management.secret-key` in extra, or delete `management-key` and run `pan restart --cliproxy` so Overdeck generates a new key.
