# PAN-4896: pan connect on macOS prints a Linux-only systemd-run warning

**Issue:** [PAN-4896](https://github.com/eltmon/overdeck/issues/4896)
**Planned:** 2026-11-04 (auto mode, base `22769ffffe8`)

## Glossary

- **PAN-2804 warning** — the `console.warn` in `spawnDashboardDetached` that reads
  `[dashboard] WARNING (PAN-2804): could not start the dashboard via systemd-run. It shares the invoking process tree's cgroup; restarting that unit/scope will kill it.`
  It exists so a Linux operator learns that the dashboard fell back to a plain detached
  child, which dies when the invoking cgroup (a systemd unit or tmux scope) is restarted.
- **`spawnDashboardDetached`** — `src/cli/commands/restart.ts`, the one function that starts
  the dashboard server process for `pan up`, `pan restart`, `pan reload` and `pan connect`.
- **`spawnDashboardSystemdUnit`** — private helper in the same file that runs
  `systemd-run --user --unit overdeck-dashboard-<ms> …` and returns a handle, or `null` when
  the platform is not Linux or `systemd-run` fails.
- **Plain detached spawn** — the fallback: `spawn(process.execPath, [serverPath], { detached: true })`
  followed by `child.unref()`.
- **darwin** — the value of `process.platform` on macOS. macOS has no systemd and no cgroups;
  its supervisor is the launchd agent `ai.overdeck.supervisor` (`src/lib/launchd.ts`).

## Problem

On macOS 26.6, `npx @overdeck/core@0.73.1 connect --label mac-rig --json` printed the PAN-2804
warning even though the launch agent installed and the dashboard started correctly.

The issue body says "the systemd-run attempt and its warning should run only on Linux". The
attempt **already** runs only on Linux. The defect is narrower: the warning is printed
unconditionally after the helper returns `null`, and on darwin the helper returns `null`
without trying anything.

Verified references (base `22769ffffe8`):

- `src/cli/commands/restart.ts`, line 305 — `const systemdHandle = spawnDashboardSystemdUnit(serverPath, fullEnv, identity.repoRoot, cpuWeight, opts?.runSystemctl);`
- `src/cli/commands/restart.ts`, line 306 — `if (systemdHandle) return systemdHandle;`
- `src/cli/commands/restart.ts`, lines 308–318 — the plain detached spawn, then the unconditional
  `console.warn('[dashboard] WARNING (PAN-2804): could not start the dashboard via systemd-run. ' + …)`.
- `src/cli/commands/restart.ts`, line 363 — inside `spawnDashboardSystemdUnit`:
  `if (process.platform !== 'linux') return null;` (the existing Linux-only guard on the attempt).
- `src/cli/commands/connect.ts`, line 329 — the darwin call site:
  `await lifecycle.restartDashboard(config, () => restart.spawnDashboardDetached(config, { resume: true }), {`
- `tests/unit/cli/restart-spawn-pid.test.ts` — existing unit tests for `spawnDashboardDetached`.
  `beforeEach` pins `vi.spyOn(process, 'platform', 'get').mockReturnValue('linux')`; `afterEach`
  calls `vi.restoreAllMocks()`. The test `returns the detached child pid when systemd-run is unavailable`
  silences `console.warn` but never asserts it, so no test proves the warning fires on Linux.
- `docs/ANYWHERE-ARCHITECTURE.md`, the **D-10 macOS** bullet under `## pan connect (W-LINK9, FR-25)`
  (search: `- **D-10 macOS.**`) — describes the launchd agent; says nothing about how the dashboard
  process itself is spawned on darwin.

## Decisions

- **D1 — gate only the warning.** Wrap the existing `console.warn` in
  `if (process.platform === 'linux') { … }`. Do not add a second guard around the `systemd-run`
  call; `spawnDashboardSystemdUnit` already returns `null` on non-Linux (line 363). Do not change the
  helper's return type to distinguish "skipped" from "failed": that is a larger diff for the same result.
- **D2 — predicate is `=== 'linux'`, not "has systemd".** A Linux host without systemd (or where
  `systemd-run --user` fails) is exactly the case PAN-2804 warns about, so it must keep warning.
- **D3 — darwin (and every other non-Linux platform) spawns silently.** The plain detached spawn is
  the normal path there, not a degraded one. win32 is already refused earlier by `pan connect`
  (`connect.ts`, `if (deps.platform === 'win32') return fail(WINDOWS_MESSAGE);`) and gets the same
  silent behavior from `pan up` — acceptable, since cgroups do not exist there either.
- **D4 — tmux PAN-1798 sibling is out of scope.** `src/lib/tmux.ts` (`ensureOverdeckTmuxServerSync`)
  has the same shape: on darwin it tries `systemd-run`, fails with ENOENT, and prints
  `[tmux] WARNING (PAN-1798): …`. It is excluded because (a) it fires only under
  `terminal.backend: tmux`, not on `pan connect`'s default Herdr path, and (b) `src/lib/tmux.ts` is at
  1167 lines with an allowlist cap of 1167 (`scripts/file-size-allowlist.txt`, last row, PAN-4292), so
  any net-positive edit fails `scripts/lint-file-size.sh` and would need an extraction item.
  A follow-up issue is appropriate.

## Requirements

- **FR-1** — On `process.platform === 'darwin'`, `spawnDashboardDetached` emits no `console.warn`
  call containing `PAN-2804` and makes no `execFileSync('systemd-run', …)` call.
- **FR-2** — On `process.platform === 'linux'`, when `systemd-run` fails, `spawnDashboardDetached`
  still emits the PAN-2804 warning exactly once, with unchanged text.
- **FR-3** — On every platform the fallback still spawns the server detached and returns a handle
  whose `pid()` resolves to the child pid.
- **FR-4** — `docs/ANYWHERE-ARCHITECTURE.md` D-10 states that on macOS the dashboard runs as a plain
  detached child (no systemd transient unit) and that no systemd warning is printed.
- **NFR-1** — No change to the PAN-2804 warning text, the systemd-run arguments, or the spawn options.
- **NFR-2** — Tests use the existing `vi.spyOn(process, 'platform', 'get')` pattern and fake timers
  already set in `beforeEach`; no real waits (fake-timers rule).

## Work items

### WI-1 — Gate the PAN-2804 warning on Linux (FR-1, FR-2, FR-3, NFR-1)

File: `src/cli/commands/restart.ts`, function `spawnDashboardDetached`.

Before (lines 314–318):

```ts
  child.unref();
  console.warn(
    '[dashboard] WARNING (PAN-2804): could not start the dashboard via systemd-run. ' +
      'It shares the invoking process tree\'s cgroup; restarting that unit/scope will kill it.',
  );
```

After:

```ts
  child.unref();
  // PAN-4896: only Linux tries systemd-run; elsewhere (macOS launchd) the
  // detached child is the normal path, so there is nothing to warn about.
  if (process.platform === 'linux') {
    console.warn(
      '[dashboard] WARNING (PAN-2804): could not start the dashboard via systemd-run. ' +
        'It shares the invoking process tree\'s cgroup; restarting that unit/scope will kill it.',
    );
  }
```

Nothing else in the function changes. `restart.ts` is 781 lines and not allowlisted, so the growth
is within the 1000-line ceiling.

### WI-2 — Unit tests for the platform gate (FR-1, FR-2, FR-3, NFR-2)

Add two tests:

1. `does not attempt systemd-run or warn on darwin (PAN-4896)` — override the platform with
   `vi.spyOn(process, 'platform', 'get').mockReturnValue('darwin')`, mock
   `processMocks.spawn.mockReturnValue({ pid: 4321, unref: vi.fn() })`, spy

   - no `warn` call has a first argument containing `'PAN-2804'`;
   - `await handle.pid!()` resolves to `4321`.
2. `warns once on linux when systemd-run fails (PAN-2804)` — keep the `beforeEach` linux pin,
   make `processMocks.execFileSync` throw, mock `spawn`, spy `console.warn`, call
   `spawnDashboardDetached(config, bundle)`, assert exactly one `warn` call whose first argument
   contains `'could not start the dashboard via systemd-run'`.

Implementation checkpoint: the darwin path calls `loadConfigSync()`, `openDashboardLogStdio()` and
`resolveNode22()` (returns `process.execPath`). The existing linux "systemd-run is unavailable" test
already runs all three under the vitest temp `OVERDECK_HOME`, and none branches on platform, so they
are expected to work unchanged. Fallback if one does throw under the mocked platform: mock that
module with `vi.mock` at the top of the test file in the same style as the existing
`child_process` mock.

Assert on `warn.mock.calls` filtered by substring, not on `toHaveBeenCalledTimes(0)`, because other
modules may legitimately warn about unrelated things (for example a missing config file).
