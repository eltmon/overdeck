# PAN-4596: An ended held handoff shows 'no saved history' and hides its unsent kickoff

**Issue:** [PAN-4596](https://github.com/eltmon/overdeck/issues/4596)
**Builds on:** PAN-4499 (held kickoff, `pan handoff --hold`, the kickoff door), merged as `ded4b988a55` (#4502).

## Glossary

- **Held handoff / held conversation** — a conversation created by `pan handoff --hold` (or the fork modal's "Hold — start it myself" checkbox). Its session is launched but its first message (the *kickoff*) is not sent.
- **Held kickoff** — the stored kickoff text, column `conversations.held_kickoff` in `~/.overdeck/overdeck.db`. **Non-null means held and not yet sent.** It is cleared atomically when the kickoff is claimed and restored if delivery fails. This column, not `forkRequest.hold`, is the "kickoff not sent" signal: `forkRequest.hold` stays `true` forever, even after the kickoff is sent.
- **Kickoff door** — `GET`/`POST /api/conversations/:name/kickoff` (`src/dashboard/server/routes/conversation-kickoff.ts`, logic in `src/lib/overdeck/conversation-kickoff.ts`). `GET` answers `{ held: true, text }` or `{ held: false }`. `POST` claims the held kickoff exactly once and delivers it. `pan handoff start <conv>` (`src/cli/commands/handoff-start.ts`) is a thin client of this `POST`.
- **Ended conversation** — a conversation row with `status: 'ended'`; the frontend sees `conversation.sessionAlive === false`.
- **Orphaned empty state** — the `isOrphaned` branch of `ConversationView` in `src/dashboard/frontend/src/components/chat/ConversationPanel.tsx`, which renders "This conversation has no saved history…" with **Resume Session** and **Archive**.
- **Focus** — the steering text passed to `pan handoff` (`ForkRequest.handoffFocus`, stored inside the JSON column `conversations.fork_request`).
- **Handoff doc** — the authored handoff document; its path is `conversations.handoff_doc_path`, exposed to the frontend as `conversation.handoffDocPath` and served by `GET /api/conversations/:name/handoff-doc`.
- **Pending-input feed** — `GET /api/conversations/pending-input`, built by `getConversationsPendingInputFeed` in `src/lib/overdeck/conversation-reads.ts`. It feeds the Awareness rail's **Needs you** tab (the `DecisionsPanel`) through `src/dashboard/frontend/src/lib/useDecisions.ts`.
- **Kind** — a string in a pending-input subject's `kinds` array (`askUserQuestion`, `paneChoice`, …). Labels live in `PENDING_INPUT_KIND_LABEL` in `src/dashboard/frontend/src/lib/pendingInput.ts`.

## Problem

Conversation 3230 (`20261004-43a2`) was created by `pan handoff --hold` on 2026-10-04. Its kickoff was never sent. Its session ended on 2026-10-15. Verified read-only against `~/.overdeck/overdeck.db`: the row has `status = 'ended'`, `held_kickoff` is 7319 characters (the authored handoff), `fork_request.hold = true`, `fork_request.handoffFocus = "Read .pan/handoff-brief.md FIRST …"`, and `handoff_doc_path` is set. No transcript exists because Claude Code writes the JSONL only on the first message. (The row has since been archived, so it cannot serve as the live test subject.)

The conversation page shows the generic orphaned text and offers **Resume Session** and **Archive**. It never says the conversation is a held handoff and never shows the focus or the handoff doc. The operator cannot tell what it was waiting for. The Awareness rail's Needs you tab does not list it either, so nothing in the dashboard surfaced it for 20 days.

### Root cause (verified)

1. `ConversationView` computes `isOrphaned` at `ConversationPanel.tsx` line 1282:
   ```ts
   const isOrphaned = !isLoading && !isDiscovering && !awaitingFirstPayload && data != null && !hasTimelineActivity && !conversation.sessionAlive && !isSpawnFailed && !isSpawning;
   ```
   It never consults the held kickoff. The held-kickoff UI from PAN-4499 lives only in `ComposerFooter` (`useHeldKickoff`, `HeldKickoffNotice`, `ComposerFooter.tsx` lines 157 and 703), and the panel tail (`{isOrphaned ? null : … onResume ? <ConversationResumeControls/> : … <ComposerFooter/>}`, around line 1441) never mounts the composer for an ended row. So an ended held conversation has no held UI at all.
2. `getConversationsPendingInputFeed` (`conversation-reads.ts` line 376) scans only conversations whose terminal session is alive (`liveSessionNames.has(conv.tmuxSession)`, line 383) and reports only JSONL/pane prompts. A held kickoff is neither, so Needs you never shows it — alive or ended.

### What already works (verified, no change needed)

`POST /api/conversations/:name/kickoff` → `startHeldKickoff` → `deliverClaimedKickoff` (`conversation-kickoff.ts`) calls `ensureForkSessionReady(conv, conv.claudeSessionId, false)` (`conversation-forks.ts` line 221). When the terminal session is gone, that function calls `forkSpawnConversationSession(…, resume=false, …)` and waits for the session, then `deliverForkSeed` delivers the kickoff and calls `markConversationActive`. So **the door already relaunches an ended session and sends the kickoff.** The **Start** button only needs to call this door. `pan handoff start <conv>` already does exactly that.

`ForkProgressView` (`src/dashboard/frontend/src/components/chat/ForkProgressView.tsx`) renders a failed delivery with no retry button, so a failed Start must not hand the operator to that view (see D4).

## Proposal

1. The kickoff door's `GET` also returns the handoff focus, parsed server-side from `fork_request`.
2. `ConversationView` reads the held kickoff for ended conversations. When it is held, the panel shows a new **held handoff** view instead of the orphaned text: title "Held handoff — kickoff not sent", the focus, the working directory, the handoff doc path with an **Open handoff doc** button, a collapsible copy of the full kickoff text, a **Start** button that POSTs the kickoff door, and **Archive**. **Resume Session** is not offered.
3. The pending-input feed adds every unarchived held conversation (alive or ended) as a row carrying `heldKickoff: { since, focus? }`. The frontend maps it to a new `heldKickoff` kind labeled "Held handoff — kickoff not sent", listed in the Needs you **Waiting** group, with an **Open** button that navigates to the conversation.
4. Docs describe the ended-held view and the Needs you entry.

## Decisions

- **D1 — "kickoff not sent" = `held_kickoff IS NOT NULL`.** Not `forkRequest.hold`, which stays true after the kickoff is sent. Every new check reads the held-kickoff store (`readHeldKickoff`, the new `listHeldKickoffNames`).
- **D2 — Start reuses the kickoff door unchanged.** `startHeldKickoff(name)` from `src/dashboard/frontend/src/components/chat/heldKickoff.tsx` with no `text` (sends the stored kickoff verbatim). No new server endpoint, no new spawn path. The only server change on this path is the extra `focus` field on `GET`.
- **D3 — Hide Resume Session for a held conversation.** Resume (`handleConversationResume`, `src/lib/overdeck/conversation-runtime.ts` line 1074) finds no transcript, spawns a fresh session and sends a `CONVERSATION RESUME` contract as the first message. That writes a transcript, leaves the kickoff still held, and starts the agent without its brief. The held view offers Start and Archive only.
- **D4 — The held view takes precedence over a *failed* fork status, not over an in-flight one.** When a Start fails, the door restores `held_kickoff` and sets `forkStatus = 'failed'`. `ForkProgressView` has no retry, so the held view renders instead, with the `forkError` shown as a warning line ("The last start failed: <error>") and Start available to retry. While `forkStatus` is `'spawning'`/`'injecting'` (Start in flight), `ForkProgressView` keeps rendering as today.
- **D5 — Only ended conversations get the new panel view.** A live held conversation already shows `HeldKickoffNotice` in its composer (PAN-4499); leave it unchanged. To avoid a second 5 s poll on live conversations, `useHeldKickoff` gains an optional `enabled` flag (default `true`); the panel passes `enabled: !conversation.sessionAlive`. When disabled the hook makes no request and reports `{ held: false }`. For ended conversations the panel also passes `pollAlways: true` (critique response) so a hold restored after a failed Start is seen.
- **D6 — "Brief path" = the working directory plus the handoff doc path.** The focus usually names a brief relative to the conversation's cwd (`.pan/handoff-brief.md`), and the authored handoff doc is `handoffDocPath`. The view shows both: `Working directory: <cwd>` and `Handoff doc: <handoffDocPath>` with an **Open handoff doc** button that opens `/api/conversations/<name>/handoff-doc` in a new tab (the same URL `ConversationActionMenu.tsx` line 290 uses).
- **D7 — Needs you lists held conversations whether alive or ended**, so a held kickoff is visible for as long as it waits. Archived rows are excluded (`listConversations` already filters `archived_at IS NULL`; the new store query filters it too). Superseded `/clear` rows are excluded (`isSupersededConversation`).
- **D8 — `heldKickoff` is a non-blocking kind** (Needs you "Waiting" group). Nothing is stalled mid-turn; the operator deliberately held it. Do not add it to `BLOCKING_KINDS` in `useDecisions.ts`.
- **D9 — The Needs you row for a held-only decision has one "Open" button that navigates to `/conv/<name>`.** The generic "Answer" button calls `requestReopen`, which opens no dialog for a held kickoff (the same dead-button problem PAN-3276 fixed in the sidebar). A held-only decision means: `kinds` is exactly `['heldKickoff']`. A row that also carries another kind (for example `permissionRequest`) keeps its normal Answer path.
- **D10 — The feed row's `since` is the conversation's `createdAt`** (ISO string). The hold begins when the conversation is created.
- **D11 — Wire shapes are fixed here** so frontend and backend items can be built in parallel:
  - `GET /api/conversations/:name/kickoff` → `{ held: false }` or `{ held: true, text: string, focus?: string }` (`focus` omitted when `fork_request` has no non-empty `handoffFocus`).
  - Pending-input feed row (additive optional field): `heldKickoff?: { since: string; focus?: string }`. A held row that has no other pending surface is `{ name, title, issueId, harness, heldKickoff }`. A row that also has an AUQ/plan/pane choice/permission keeps those fields and gains `heldKickoff`. The server does **not** set `pendingInputKinds` on these rows (the frontend's `conversationKinds` uses an explicit `pendingInputKinds` verbatim and would drop the other kinds).

## Requirements

- **FR-1** — `GET /api/conversations/:name/kickoff` returns `focus` (the trimmed `handoffFocus` from `fork_request`) when the conversation is held and the focus is non-empty.
- **FR-2** — An ended conversation whose kickoff is held renders the held handoff view, never the "no saved history" text.
- **FR-3** — The held handoff view shows the title "Held handoff — kickoff not sent", the focus (when present), the working directory, the handoff doc path (when present), and the full kickoff text behind a disclosure.
- **FR-4** — The held handoff view offers **Start** (POST the kickoff door with an empty body) and **Archive**, and does not offer Resume Session.
- **FR-5** — After a failed Start, the held handoff view renders with the failure message and Start enabled, even when a kickoff lookup ran between the Start and the background failure.
- **FR-9** — An ended empty conversation never shows "no saved history" before a kickoff lookup has succeeded with `{ held: false }`: it shows the loading skeleton while the lookup is pending and a retryable warning when the lookup fails.
- **FR-6** — The pending-input feed includes a row with `heldKickoff` for every unarchived, non-superseded conversation with a held kickoff, whether or not its session is alive.
- **FR-7** — Needs you lists a held conversation under "Waiting" with the label "Held handoff — kickoff not sent", the focus as its prompt, and an Open button that navigates to the conversation.
- **FR-8** — The docs describe the ended-held view and the Needs you entry.
- **NFR-1** — No extra kickoff polling for live conversations (D5). Ended conversations open in the panel poll the kickoff door every 5 s (`pollAlways`), one small GET each.
- **NFR-2** — `ConversationPanel.tsx` stays at or under its allowlist cap (1531, last row in `scripts/file-size-allowlist.txt`); the new view lives in its own file. `conversation-reads.ts` (964 lines, no allowlist row) stays at or under 1000 lines.
- **NFR-3** — Existing consumers of the pending-input feed (`usePendingInputDialogs`, `useHeldMessageRelease`, `useTerminalPermissionDialog`, `usePermissionNotifications`, `useConversationPaneChoice`) tolerate a row with no AUQ/plan/permission/pane-choice payload without opening a dialog or firing a notification.

## Critique response

Plan critic round 1 (`.pan/drafts/PAN-4596-critique.md`) raised two blocks-the-design findings. Both are correct and the work items above now fix them.

### An ended hold briefly shows the false orphan state

Accepted. `useHeldKickoff` started as `{ held: false }` and turned fetch failures into `{ held: false }`, so an ended empty conversation satisfied `isOrphaned` while the lookup was in flight or after it failed. WI-2 now gives the hook a `status: 'loading' | 'ready' | 'error'` that distinguishes a pending lookup, a verified `{ held: false }`, and a failed lookup. WI-3 shows the loading skeleton while pending, a retryable "Couldn't check whether this conversation is waiting to start" warning on failure, and adds `!heldLookupPending && !heldLookupFailed` to `isOrphaned`, so the generic text renders only after a successful `{ held: false }` (FR-9). The panel tests cover the pending and failed-GET states.

### A failed Start can permanently hide retry

Accepted. `POST …/kickoff` answers 200 after claiming the hold and delivers in the background; a failure restores the hold later, but the hook stopped polling once it saw `held: false`. WI-2 adds `pollAlways`, which the panel passes for ended conversations, so the panel re-reads the door every 5 s and sees a restored hold. WI-3 adds `kickoffStartPending`, which shows the existing "Starting…" placeholder between Start's 200 and the refetched `forkStatus`, and clears when `forkStatus` is set, the session is alive, or the hold returns. A panel test (fake timers) walks POST 200 → GET `held: false` → background failure → GET `held: true` and asserts the held view and Start return with the failure message (FR-5).

### Unresolved after two critic rounds

- A failed lookup removes Resume from saved conversations
- A conversation switch can show the previous kickoff
