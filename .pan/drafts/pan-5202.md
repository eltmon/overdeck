# PAN-5202 — Flux: live meeting sessions that capture open items, propose ticket changes and draw diagrams

## 1. Summary

Flux is a new dashboard page where an operator starts a **Flux session** linked to one registered project, then runs a meeting. Overdeck listens to the meeting audio, transcribes it with speaker labels, and a project-scoped agent conversation turns what it hears into three live outputs:

1. **Open items** — action items, open questions, decisions and risks, each attributed to the speaker who raised it.
2. **Ticket proposals** — create, update, comment on, transition or close an issue in the project's tracker. Every proposal waits in an approval queue; nothing reaches the tracker until a person clicks Approve.
3. **Diagrams** — architecture, sequence and flow diagrams as Mermaid source, rendered live, revised as the discussion changes them, and openable on the existing Excalidraw whiteboard.

When the meeting ends, the operator exports a Markdown summary (transcript, items, applied tracker changes, diagrams).

## 2. Glossary

- **Flux session** — one meeting. It has an id (`flux-<YYYYMMDD>-<4 hex>`), a project key, an STT provider, a backbone conversation, and a state directory. A session is `live` (audio may flow) or `ended` (read-only).
- **Backbone conversation** — the Overdeck-managed conversation that does the reasoning for one Flux session. It is an ordinary persistent conversation created through `handleConversationCreate` (`src/lib/overdeck/conversation-runtime.ts`, search `export async function handleConversationCreate`), with `projectKey` set and its cwd at the project's primary checkout. It reads code but never edits it (FR-9).
- **Transcript turn** — one committed utterance from the STT engine, with speaker label, audio channel and timing. The type is `TranscriptTurn`, defined by PAN-5201 FR-1 in `src/voice/transcript-turn.ts`.
- **Audio channel** — `local` (the operator's microphone) or `remote` (a captured browser tab or system audio, so remote call participants are heard). Each channel runs its own STT stream.
- **Speaker label** — the provider's speaker id within a channel, for example `remote:S2`. A **speaker name** is the display name an operator assigns to a label ("Dana"). Names live in the session, not in the provider.
- **Transcript batch** — the turns that arrived since the last delivery to the backbone conversation, sent as one message (FR-6).
- **Open item** — an `item` record with `kind` `action | question | decision | risk`, `text`, `speaker`, optional `owner` and `issueRef`, and `status` `open | done | dropped`.
- **Ticket proposal** — a `proposal` record describing one tracker write: `create`, `update`, `comment`, `transition` or `close`. Status `pending | approved | rejected | applied | failed`.
- **"Delete a ticket"** — Flux maps the operator's "delete" to `close`: a comment that records the reason and the meeting, then `transitionIssue(id, 'closed')`. `IssueTracker` (`src/lib/tracker/interface.ts`, search `export interface IssueTracker`) has no delete method, `IssueState` is only `'open' | 'in_progress' | 'in_review' | 'closed'` (search `export type IssueState`), and deleting tracker history is irreversible, so Flux never deletes.
- **Diagram** — a named Mermaid document (`slug`, `title`, `source`, `revision`) owned by a session.
- **Flux tools** — MCP tools on the `overdeck` MCP server that only a backbone conversation may call: `flux_add_item`, `flux_update_item`, `flux_propose_ticket`, `flux_upsert_diagram`, `flux_search_issues`, `flux_get_issue`.
- **State directory** — `~/.overdeck/flux/<projectKey>/<sessionId>/` (path built from `getOverdeckHome()` in `src/lib/paths.ts`).

## 3. Decisions

- **D-1 The backbone is a persistent managed conversation, not a direct API call.** AutoPreso calls OpenAI directly with `OPENAI_API_KEY` (`src/autopreso/agent.ts`, search `createOpenAI({ apiKey: process.env.OPENAI_API_KEY })`). A Flux session needs the project's code, the tracker and a long memory of the meeting, which an Overdeck conversation already has: harness choice, subscription auth, cost attribution, transcript persistence, resume. The no-one-shot-agents rule forbids `claude -p` style execution. So each session creates one conversation and feeds it transcript batches through `handleConversationMessage` (`src/lib/overdeck/conversation-message.ts`, search `export async function handleConversationMessage`; it is the handler behind `POST /api/conversations/:name/message`). Flux imports both handlers from `src/lib/overdeck/`, never from a routes file. A conversation created this way gets the `overdeck` MCP server with a token minted at launch, scoped by `AGENT_TOKEN_SCOPES.conversation` (`src/lib/mcp/agent-token.ts`): `read:events`, `read:state`, `read:conversations`, `tell`, `operate`, `approve`, never `admin`.
- **D-2 The model comes from the conversation default.** The start form offers the same model picker as a new conversation, preselected to the configured conversation default. If no default is configured, session start fails with the existing "no default configured" error. No model id is hardcoded (no-hardcoded-model-fallbacks rule).
- **D-3 Every tracker write needs approval.** The agent only creates proposals. The Flux page shows each one with a diff-style preview and Approve, Edit and Reject buttons. Approve applies it through the project's `IssueTracker`. There is no auto-apply mode in this issue (§10).
- **D-4 Audio comes from the browser, on two channels.** The microphone alone does not hear remote participants. The page captures the mic with `getUserMedia` and, when the operator clicks "Add call audio", a tab or screen with audio via `getDisplayMedia({ audio: true, video: true })` (the video track is stopped immediately). Each channel is a separate STT stream, which gives a free "operator vs. the call" split and lets diarization focus on the remote channel. Meeting bots (Recall.ai and similar) are out of scope (§10). Browser limits to state in the docs: Chrome and Edge capture tab audio on every OS and system audio on Windows and ChromeOS; Firefox and Safari do not capture tab audio, so they get mic-only sessions.
- **D-5 Diagrams are Mermaid source.** Models write and revise Mermaid text reliably, revisions are plain-text diffs, and the export can embed them in Markdown. The page renders them with the `mermaid` package (new frontend dependency, lazy-loaded). "Open on whiteboard" converts a diagram into Excalidraw elements with `@excalidraw/mermaid-to-excalidraw` (new frontend dependency) and opens it in the existing `@excalidraw/excalidraw` canvas. AutoPreso stays as it is.
- **D-6 State lives in the state directory, not in git and not in SQLite.** Meeting content is sensitive and not derivable from git or the tracker, so it is stored outside the repo. Files are append-only JSONL plus one small JSON metadata file (§6). Audio is never written to disk. The export (FR-12) is the only path into a repository, and it is an explicit operator action.
- **D-7 Flux has its own WebSocket path and does not use `/ws/voice`.** `/ws/voice` allows one active socket for the whole server and forwards every committed turn into the AutoPreso singleton (`src/dashboard/server/ws-voice.ts`, search `autoPresoSession.processTranscript`). Flux adds `/ws/flux?session=<id>`, which accepts audio for one live session and pushes session events. One live session per project at a time; sessions for different projects may run at once (NFR-3).
- **D-8 Flux tools are scoped to backbone conversations.** The tools post to new `/api/flux/...` routes. Their `ROUTE_SCOPES` rows use scope `operate`, because a conversation token never carries `admin`. Each route resolves the caller with `selfCallerFromCredential` (`src/dashboard/server/self-caller.ts`, the same resolver `routes/self-requests.ts` uses) and refuses (403, code `NOT_FLUX_BACKBONE`) unless `caller.agentKind === 'conversation'` and `caller.agentId` equals the `conversationName` of a live session. Operator routes (WI-7) stay `admin`. The tools carry `audience: 'agent'` like the self tools (`src/lib/mcp/tools-self.ts`).
- **D-9 The page is experimental at first.** Its tab id `flux` joins `EXPERIMENTAL_TAB_IDS` (`src/dashboard/frontend/src/lib/experimentalFeatures.ts`), so it shows only when `experimental.experimentalFeatures` is on, like AutoPreso.
- **D-10 Naming.** The page and feature are "Flux". Deepgram also sells an STT model named Flux; where PAN-5201 exposes that model, its label is always "Deepgram Flux" so the two never share a bare name in the UI.

## 4. Requirements

### Functional

- **FR-1 Start a session.** From the Flux page the operator picks a registered project (default: the project in `?project=<key>` or the last one used), an STT provider (default: the configured provider from Voice settings, filtered to providers that report `capabilities.diarization !== 'none'`; others are shown disabled with the reason), a model, and an optional meeting title and agenda text. Start creates the state directory, the backbone conversation (D-1) and the session metadata, and returns the session id.
- **FR-2 Capture audio on two channels.** Mic is on by default; "Add call audio" adds the remote channel (D-4). Each channel shows a level meter and a mute toggle. Muting stops sending frames for that channel.
- **FR-3 Live transcript with speakers.** Partial text shows per channel. Committed turns show with timestamp, channel and speaker name (or label), color-coded per speaker. Clicking a speaker label opens a rename field; the name applies to all past and future turns with that label in the session and is sent to the backbone in the next batch. When an engine emits a `SpeakerRevision` (PAN-5201 FR-2), the session appends a `turn.relabeled` event, updates the turn on the page, and lists the relabel in the next batch so the backbone can correct attributions.
- **FR-4 Open items panel.** Items group by kind, show speaker and owner, and can be edited, marked done, or dropped by the operator. Operator edits are recorded as events and sent to the backbone in the next batch so the agent does not re-add them.
- **FR-5 Ticket proposals panel.** Pending proposals show the target issue (or "new issue"), the change as a before/after preview, the agent's one-line reason, and the transcript turns it cites. Buttons: Approve, Edit (opens the fields in place, then Approve), Reject. Approve calls the tracker; the result becomes `applied` with the issue URL, or `failed` with the tracker error and a Retry button.
- **FR-6 Transcript batching to the backbone.** The server delivers a batch when the conversation is idle (one delivery in flight at a time) and at least one of: 3 or more turns are pending, or 20 seconds have passed since the oldest pending turn, or the operator clicks "Analyze now". A batch carries turns as `[mm:ss] <speaker name or label> (<channel>): <text>` lines plus any speaker renames and operator edits since the last batch. Turns that arrive while a delivery is in flight wait for the next batch; none are dropped.
- **FR-7 Diagrams panel.** Tabs per diagram. Each shows the rendered Mermaid, a "Source" toggle, the revision number, and "Open on whiteboard". A render error shows the Mermaid parse error and the last good render.
- **FR-8 Flux tools.** The backbone conversation calls:
  - `flux_add_item({ kind, text, speaker?, owner?, issueRef?, turnRefs[] })` → item id.
  - `flux_update_item({ itemId, text?, status?, owner?, issueRef? })`.
  - `flux_propose_ticket({ op, issueRef?, title?, body?, labels?, state?, comment?, reason, turnRefs[] })` → proposal id. `op` is `create | update | comment | transition | close`. `issueRef` is required for every op except `create`.
  - `flux_upsert_diagram({ slug, title, source, reason })` → revision number. The server validates that `source` is non-empty and under 64 KB; the frontend validates Mermaid syntax.
  - `flux_search_issues({ query, state? })` and `flux_get_issue({ issueRef })` → read-only tracker access through the project's tracker (`listIssues`, `getIssue`).
- **FR-9 The backbone never edits code or the tracker directly.** Its kickoff message (template `roles/flux.md`) tells it: read code to understand architecture, use only Flux tools for outputs, never write files, never run tracker CLIs or tracker MCP write tools, never call `pan` verbs that change state. The conversation runs in the project's primary checkout; this is safe only because it does not write, so the template states the rule twice and the session-start code may pass the harness's plan permission mode, but only if the WI-4 checkpoint proves that `flux_*` MCP tool calls still succeed in that mode.
- **FR-10 End a session.** "End meeting" stops audio, flushes the last batch, sends a final message asking the backbone for a closing summary via `flux_add_item({ kind: 'decision', ... })` items and a final diagram pass, waits up to 120 seconds for the conversation to go idle, then marks the session `ended`. The conversation is stopped (not archived) and can be resumed from the conversation list.
- **FR-11 Session list and reopen.** The Flux page lists sessions for the selected project (newest first) with title, date, duration, item and proposal counts. Opening an ended session shows everything read-only, and pending proposals can still be approved or rejected.
- **FR-12 Export.** "Export" produces Markdown: header, attendees (speaker names), open items by kind, applied tracker changes with links, rejected proposals, diagrams as fenced `mermaid` blocks, and the full transcript. Two targets: download the file, or write it to `<planHome>/.pan/notes/flux-<YYYY-MM-DD>-<slug>.md` in the project's plan home without committing.
- **FR-13 Provider failure is visible.** If a channel's STT stream errors or stops, the channel shows the error and a Reconnect button; the other channel keeps running. If the backbone conversation stops, the page shows it with a Resume button; pending turns stay queued.

### Non-functional

- **NFR-1 Latency.** A committed turn appears on the page within 1 second of the provider committing it. A batch is delivered within 1 second of its trigger when the conversation is idle.
- **NFR-2 No event-loop blocking.** No `execSync` or other sync child-process call in any new server code. File writes use `fs/promises` appends.
- **NFR-3 Concurrency.** At most one live session per project. Starting a second live session for the same project returns 409 with the existing session id. Different projects may run at once; each session owns its own STT streams and conversation. Session objects live in a `Map<sessionId, FluxSession>` in one module; there is no module-level singleton session (contrast `export const autoPresoSession` in `src/autopreso/session.ts`).
- **NFR-4 Bounded memory.** The server keeps at most the last 500 turns per session in memory; the rest are read from `transcript.jsonl` on demand. Audio frames are capped at 64,000 bytes, matching `MAX_AUDIO_FRAME_BYTES` in `ws-voice.ts`.
- **NFR-5 Crash safety.** A dashboard restart loses only in-flight audio. On boot, sessions whose metadata says `live` are marked `interrupted`; the page offers Resume, which reconnects audio and reuses the same backbone conversation.
- **NFR-6 Privacy.** Audio is never persisted. State files are created with mode `0600`, directories `0700`. Provider API keys never reach the browser (the redaction pattern in `src/dashboard/server/routes/voice.ts`, search `function redactVoiceSettings`).

## 5. Repo rules that apply (restated)

- No `execSync` or blocking child-process calls in dashboard server code or anything it imports.
- Tests that involve the 20-second batch timer, the 120-second end-of-meeting wait, or any retry use `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()`. Never wait on real timers.
- Every new HTTP route needs a row in `tests/unit/lib/overdeck/no-loss-matrix.ts` and a scope row in `ROUTE_SCOPES` (`src/dashboard/server/route-scopes.ts`), or CI fails.
- The new WebSocket path `/ws/flux` must be added to `UPGRADE_PATHS` in `src/dashboard/frontend/tests/pan-1166-ws-auth.spec.ts`, and its upgrade handler uses `authorizeDashboardUpgrade(..., 'admin', ...)` like `ws-voice.ts`.
- `roles/flux.md` is a kickoff template; any commit that adds or changes it needs a `Prompt-Change:` trailer (`lint:prompt-trailer`).
- New lib modules that need agent state import `getAgentState` from `agent-state-read.js`, never `agent-state.js` (avoids `lint:circular`).
- One variant per operation in `src/lib`: no exported Effect wrapper around a Promise function and no sync/async twins.
- A user-facing change adds `changelog.d/PAN-5202.md` (format in `changelog.d/README.md`).
- Before writing UI, load the `pan-style-guide` skill. No Inter, no pill badges, no decorative color; speaker colors come from the existing categorical tokens.
- Quality gates before `pan done`: `npm run typecheck`, `npm run lint`, and `npx vitest run <touched test files>`. Never run the full `npm test` locally.

## 6. Architecture

```
Browser (Flux page)                         Dashboard server (Node 22)
 mic  ─getUserMedia──┐                      /ws/flux?session=<id>
 tab  ─getDisplayMedia┤ PCM16 16 kHz frames  ├─ channel 'local'  → STT stream (PAN-5201 provider)
                      └─ tagged by channel ──►├─ channel 'remote' → STT stream
                                              │        │ TranscriptTurn
 transcript / items / proposals / diagrams ◄──┤   FluxSession (src/flux/session.ts)
        (session events over the same WS)     │     ├─ appends transcript.jsonl, events.jsonl
                                              │     ├─ batcher (FR-6) ──► backbone conversation
                                              │     │                     (handleConversationMessage)
 Approve proposal ── POST /api/flux/... ──────┤     │                            │ MCP flux_* tools
                                              │     └─ applies approved proposal ◄┘ POST /api/flux/<id>/tools/...
                                              │          via project IssueTracker (createIssue, updateIssue,
                                              │          addComment, transitionIssue)
```

**Wire format on `/ws/flux`.** Binary frames: byte 0 is the channel (`0` = local, `1` = remote), the rest is PCM16LE mono at 16 kHz. Text frames from the client: `{ type: 'stop' }`, `{ type: 'channel', channel, muted }`. Text frames from the server: `flux:snapshot` (full session view on connect), `flux:partial` `{ channel, text }`, `flux:turn` `{ turn }`, `flux:item`, `flux:proposal`, `flux:diagram`, `flux:speaker`, `flux:status`, `flux:error` `{ channel?, error }`.

**State directory** `~/.overdeck/flux/<projectKey>/<sessionId>/`:
- `session.json` — `{ id, projectKey, title, agenda, provider, model, conversationName, status: 'live'|'interrupted'|'ended', startedAt, endedAt?, speakers: { [label]: name } }`. Rewritten atomically (write temp file, rename).
- `transcript.jsonl` — one `TranscriptTurn` per line plus `turnId` (`t-<n>`).
- `events.jsonl` — append-only event log: `item.added`, `item.updated`, `proposal.created`, `proposal.edited`, `proposal.approved`, `proposal.rejected`, `proposal.applied`, `proposal.failed`, `diagram.revised`, `speaker.renamed`, `turn.relabeled`, `batch.delivered`. Current items, proposals and diagrams are a fold over this file; nothing else stores them.
