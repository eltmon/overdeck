# PAN-3420 — Durable issue history: closed-out issues must not render as never-started

**Issue:** https://github.com/eltmon/overdeck/issues/3420
**Mode:** `--auto` planning (decisions recorded in `autoDecisions`, no operator Q&A)

## Glossary

- **Permanent plane** — the git `overdeck-state` branch (on disk `${OVERDECK_HOME}/state/<project>/`). Holds `records/<issue>.json` (per-issue durable record), `specs/*.xbrief.json` (immutable plans), `drafts/`, `continues/`.
- **Runtime plane** — local SQLite `~/.overdeck/overdeck.db` (`review_status` verdict cache, `agents` table, event store). Rebuildable; treated as a cache.
- **Record / durable record** — `records/<issue>.json`, schema `PanIssueRecord` (`src/lib/pan-dir/record.ts:219-255`). Read door: `readIssueRecordSync` (`src/lib/pan-dir/record.ts:481`). Write doors: `writeIssueRecordSync` (`record.ts:408`), `updateIssueRecord` (`src/lib/pan-dir/record-update.ts:471`).
- **Pipeline journal** — the `pipeline` block of the record (`PanIssuePipelineRecord`, `record.ts:162-207`). Read through `readJournalStatusSync` and reconciled into the runtime cache by `resolveJournalReconciledReviewStatusSync` (`src/lib/review-status-read.ts:13-54`).
- **Close-out** — `pan close <id>` / dashboard Close Out (`src/lib/lifecycle/workflows.ts` `closeOut`, lines 168-331). Tears down tmux sessions, Docker stack, workspace worktree, feature branches, agent state dirs (via `removeAgentStateDir`, `src/lib/agents/state-dir-removal.ts:118`, which preserves only `**/*.jsonl`), clears the `review_status` row (`clearReviewStatusStep`, `workflows.ts:1017-1051`), marks the journal `closedOut` (`markPipelineClosedOutStep`, `workflows.ts:333-347`).
- **ReviewStatus** — the live verdict shape (`src/lib/review-status-reconcile.ts:32-85`): review/test/merge/uat/verification statuses + notes, `history: StatusHistoryEntry[]` (`reconcile.ts:16-21`), `reviewerVerdicts` per-sub-role map.
- **Issue view kit** — `src/dashboard/frontend/src/components/issue-view/`; `useIssueView.ts` builds the `IssueViewModel` every density (rail/cockpit/console) consumes.
- **Retained transcripts** — after close-out, agent dirs under `~/.overdeck/agents/` keep only `.jsonl` files (e.g. `agent-min-929/activity.jsonl`); the directory name carries the agent-to-issue link.
- **PAN-2401 overlay** — `readWorkspacePlanSync` (`src/lib/xbrief/io.ts:358-369`) overlays the record's `statusOverrides` onto the spec, so `/api/issues/:id/tasks` already returns completed task statuses post-close-out.

## Problem

A completed, merged, closed-out issue renders as **never-started** on both the dashboard issue-detail page and `pan show`. Observed on MYN `MIN-929` (closed out 2026-08-01): pipeline strip shows dates only for PLAN and DONE; WORK/REVIEW/TEST/SHIP show "—"; all four review specialists show "QUEUED — starts when the convoy slot frees"; tasks badge shows 0/0; conversations tab says "Nothing here yet — no agent has started on this issue"; verification gates show pending TYPECHECK/LINT/TEST and unavailable UAT; activity rail is empty; `pan show MIN-929` prints `cv (no work history)`.

The durable history exists: the record (`records/min-929.json`) carries `pipeline.reviewStatus: "passed"`, `testStatus: "passed"`, `verificationStatus: "passed"`, `mergeStatus: "merged"`, `closedOut/closedOutAt`, `prUrl`, `reviewRequestedAt/reviewSpawnedAt`, `closeOut.usage.byStage` (per-specialist costs), `closeOut.merges`, `closeOut.dodGate.rows`, `sessionHistory` (23 entries), `tasks.claimHistory` (17 completed claims), and 79 `statusOverrides` (all completed). The spec on `overdeck-state` has all 17 items. Retained agent dirs hold `activity.jsonl` for `planning-min-929`, `agent-min-929`, and the five review agents.

### Root cause — six live-only read paths (verified against the tree)

1. **Journal nulling (by design, do not revert).** `resolveJournalReconciledReviewStatusSync` (`src/lib/review-status-read.ts:21-28`) returns `null` and deletes the SQLite row when the journal is `closedOut`. `getReviewStatusSync` (`src/lib/review-status.ts:727-740`) therefore yields `null`. Every surface keying off the review-status payload collapses to its pending default.
2. **Status route synthesizes an all-pending default.** `GET /api/review/:issueId/status` (`src/dashboard/server/routes/workspaces.ts:1363-1428`) — `getReviewStatusSync` returns `null` at line 1375, so lines 1376-1383 build `{reviewStatus:'pending', testStatus:'pending', mergeStatus:'pending'}` and `enrichReviewStatusFromSessions` (`src/lib/review-status-enrichment.ts:74-162`) finds no tmux sessions. This one payload feeds the pipeline strip dates (`useDrawerData.ts:307-333` `phaseTimeline`), verification gates (`useIssueView.ts:387-409` `deriveVerification` via `useReviewStatusQuery`, `queries.ts:298-304`), the narrative recent-events (`useIssueView.ts:296`), and the specialist strip's sub-statuses.
3. **Specialist strip defaults to queued.** `deriveSpecialistChips` (`src/dashboard/frontend/src/components/issue-detail/deriveSpecialists.ts:78-127`) builds chips from store agents + `reviewSubStatuses`; with neither present, lines 70/119 emit `{status:'queued', lastLine:'starts when the convoy slot frees'}` — for reviewers that finished hours ago.
4. **Drawer tasks badge reads the wrong source.** `IssueDrawer.tsx:11-15` `taskBadge` consumes `useDrawerData.ts:235-251,422`, which reads `issue.tasks` — a field the `Issue` type never sets — so 0/0 forever. The API `GET /api/issues/:id/tasks` (`src/dashboard/server/routes/issues.ts:677-689` → `src/lib/overdeck/issue-reads.ts:179-241`) correctly returns 17 tasks with completed statuses (PAN-2401 overlay) for the same issue.
5. **Conversations tab + activity rail read pruned live state.** The tab (`DrawerAgentSession.tsx`, mounted via `IssueDetail.tsx:304-316`) synthesizes conversations from store `agentsById`, which `pruneAgentsForReadSource` (`src/dashboard/server/read-model.ts:164-187`) empties for closed issues; the rail (`IssueDetail.tsx:389-398` → `useDrawerData.ts:397-416`) reads transient event-store arrays (`read-model.ts:524-545`). Meanwhile `GET /api/command-deck/activity/:issueId` (`src/dashboard/server/routes/command-deck.ts:187-208`) still resolves retained plan/work sessions from agent dirs.
6. **`pan show` reads `cv.json`, which close-out deletes.** `show.ts:82` `readAgentCVSync` reads `~/.overdeck/agents/agent-<id>/cv.json` (`src/lib/cv.ts:44,50`); `removeAgentStateDir` deletes everything non-`.jsonl`, so `show.ts:163` prints `(no work history)`. `show.ts:83` `getReviewStatusSync` likewise returns `null`.

### Durable-snapshot gap

Two history fields are **not** journaled today, so even a record-reading resolver cannot fully reconstruct post-hoc state for future close-outs:

- `ReviewStatus.history` (the verdict timeline: review/test/merge/inspect/uat/release entries with timestamps) is written raw to the SQLite `status_history` table (`src/lib/review-status.ts:302-324`) but `PanIssuePipelineRecord` has **no `history` field** (`record.ts:162-207`), and `clearReviewStatusStep` wipes the runtime copy.
- `reviewerVerdicts` is schema'd on the record (`record.ts:204`) and written by `buildIssueRecord` (`src/lib/pan-dir/records.ts:144`), yet MIN-929's record has it `undefined` — the convoy-completion write path does not reliably journal it.

## Proposal

Endorsed fix shape from the strike analysis (issue comment, 2026-08-01): a **unified durable issue-history resolver** — one read door that sources terminal-issue history from the permanent plane — plus a **close-out snapshot** that journals the verdict timeline before runtime state is cleared, plus rewiring the six surfaces to the door, plus a no-loss regression test.

1. **Snapshot at close-out (write side).** Extend `PanIssuePipelineRecord` with `history?: StatusHistoryEntry[]`. During `closeOut`, before `clearReviewStatusStep`, copy the final live `ReviewStatus` fields (`history`, `reviewerVerdicts`, `reviewCycleHistory`, `uatStatus/uatNotes`, `verificationStatus/verificationNotes`, `testStatus/testNotes`, `reviewStatus/reviewNotes`, `reviewSpawnedAt`) into the record pipeline block via the record write door. Also add a unit-tested guarantee that convoy completion journals `reviewerVerdicts` (close the gap that left MIN-929's record without them). Additive only: nothing is cleared earlier or additionally.
2. **One read door: `src/lib/issue-history/resolver.ts`.** New module exporting `resolveIssueHistorySync(issueId): IssueHistory | null` (plus types in `src/lib/issue-history/types.ts`). It reads only the permanent plane (record door + `findSpecByIssue` at `src/lib/pan-dir/specs.ts:213` + retained agent dirs) and derives a normalized DTO: verdicts, verdict timeline, phase timestamps, specialist verdicts, task summary (spec items + `statusOverrides` overlay), retained session list, activity entries (from `sessionHistory`), merges, usage. Derivation rules are specified below so no judgment is needed downstream.
3. **Rewire server routes to the door (fallback only).** When the live read yields nothing AND the record says `closedOut`, the route synthesizes its response from `IssueHistory`:
   - `GET /api/review/:issueId/status` returns the journaled verdicts + `history` + `reviewerVerdicts` + derived `phases` + `closedOut: true` instead of the all-pending default.
   - `GET /api/command-deck/activity/:issueId` merges durable sessions (with transcript paths) and activity entries into its response for terminal issues.
   In-flight issues are byte-for-byte unaffected (fallback engages only when the live read is empty and the record is terminal).
4. **Rewire `pan show`.** When `cv.json` and the live review status are absent, derive the CV line (totals, success rate, avg duration, recent entries) from `tasks.claimHistory` + `sessionHistory`, and print the durable verdict line from the resolver.
5. **Frontend consumes the enriched payloads.** Drawer tasks badge reads the existing tasks query instead of `issue.tasks`; `phaseTimeline` prefers the payload's `phases`; specialist chips render journaled verdicts (`done`/passed/blocked, never "queued" when `closedOut`); conversations tab lists retained sessions from the activity API with transcript links; activity rail falls back to durable activity entries. No visual redesign — data-source fixes only.
6. **No-loss regression test.** A fixture closed-out record + spec drives the resolver and each read door; asserts phases/specialists/tasks/history/sessions are non-empty and correct, and asserts an in-flight fixture is untouched by the fallback.

### IssueHistory DTO (contract for items 2-5)

```ts
// src/lib/issue-history/types.ts
import type { StatusHistoryEntry } from '../../lib/review-status-reconcile.js';

export interface IssueHistoryPhase {
  id: 'plan' | 'work' | 'review' | 'test' | 'ship' | 'done';
  at: string | null; // ISO 8601
}

export interface IssueHistorySpecialist {
  role: string;                        // e.g. 'review.security'
  verdict: 'passed' | 'blocked' | 'unknown';
  atCommit?: string;
  findingsPath?: string;
}

export interface IssueHistorySession {
  agentId: string;                     // e.g. 'agent-min-929-review-security'
  role: 'plan' | 'work' | 'review' | 'test' | 'strike' | 'other';
  transcriptPath: string | null;       // absolute path to retained .jsonl, or null
}

export interface IssueHistoryActivityEntry {
  timestamp: string;
  kind: string;                        // sessionHistory reason: planning|start|resume|end|...
  summary: string;                     // note, may be ''
}

export interface IssueHistory {
  issueId: string;
  closedOut: boolean;
  closedOutAt: string | null;
  verdicts: {
    review: string | null; test: string | null; uat: string | null;
    verification: string | null; inspect: string | null;
    merge: string | null; release: string | null;
    reviewNotes?: string; testNotes?: string; uatNotes?: string; verificationNotes?: string;
    prUrl?: string; prNumber?: number;
    reviewedAtCommit?: string; lastVerifiedCommit?: string;
    reviewRequestedAt?: string; reviewSpawnedAt?: string;
  };
  history: StatusHistoryEntry[];       // journaled timeline; [] for pre-PAN-3420 close-outs
  phases: IssueHistoryPhase[];
  specialists: IssueHistorySpecialist[];
  tasks: { total: number; completed: number } | null; // null when no spec
  sessions: IssueHistorySession[];
  activity: IssueHistoryActivityEntry[];
  merges: string[];
}
```

### Derivation rules (decided here, not downstream)

- `closedOut` = `record.pipeline.closedOut === true`; `closedOutAt` = `record.pipeline.closedOutAt ?? null`.
- `verdicts` = straight copies from `record.pipeline` (`reviewStatus/testStatus/uatStatus/verificationStatus/inspectStatus/mergeStatus/releaseStatus` + notes + PR fields + `reviewRequestedAt/reviewSpawnedAt`).
- `history` = `record.pipeline.history ?? []`.
- `phases`:
  - `plan` = timestamp of the first `sessionHistory` entry with `reason === 'planning'`, else `record.created`.
  - `work` = timestamp of the first `sessionHistory` entry with `reason === 'start'`, else null.
  - `review` = `pipeline.reviewSpawnedAt ?? pipeline.reviewRequestedAt ?? null`.
  - `test` = timestamp of the last `history` entry with `type === 'test'`, else null.
  - `ship` = timestamp of the last `history` entry with `type === 'merge'`, else (`mergeStatus === 'merged'` ? `closedOutAt` : null).
  - `done` = `closedOutAt`.
- `specialists`: from `pipeline.reviewerVerdicts` map → `{role: 'review.'+subRole, verdict, atCommit, findingsPath}`. Fallback when absent (pre-fix records): for each `review.<sub>` key in `closeOut.usage.byStage`, emit `{role, verdict: pipeline.reviewStatus === 'passed' ? 'passed' : 'unknown'}` — a passed convoy means every specialist that ran completed; usage proves it ran.
- `tasks`: resolve the spec via `findSpecByIssue`, apply `record.statusOverrides` with the existing `applyStatusOverrides` (`src/lib/xbrief/io.ts`), count items with status `completed`. `null` when no spec exists.
- `sessions`: scan `~/.overdeck/agents/` for directories named `{agent,planning,strike,knowledge}-<issue-lowercase>*`; `role` from the prefix (`planning-` → plan, `agent-<issue>-review*` → review, `agent-` → work, `strike-` → strike, else other); `transcriptPath` = first `*.jsonl` inside the dir (e.g. `activity.jsonl`), else null. Sort: plan, work, review, test, strike, other.
- `activity` = `record.sessionHistory` mapped to `{timestamp, kind: reason, summary: note ?? ''}`, order preserved.
- `merges` = `record.closeOut.merges ?? []`.
- For an **in-flight** issue the resolver still returns the durable base (callers decide to use it as fallback only); it must never read SQLite, tmux, or the tracker.

Skip the merge-queue and tmux enrichment in the closed-out branch (nothing is live). `computeQueuePositionFromStatusSync(null)` behavior is unchanged on the live path.

**`GET /api/command-deck/activity/:issueId`** (`command-deck.ts:187-208`, `fetchActivityDataWithContext`). After the existing live assembly, when `resolveIssueHistorySync(issueId)?.closedOut`: append `h.sessions` (as the response's session entries, including `transcriptPath`) for any agent ids not already present, and append `h.activity` entries to the activity list. Additive merge — live entries win on id conflict.

**`pan show`** (`show.ts`). After line 82:

```ts
const cvData = readAgentCVSync(agentId)
  ?? deriveCvFromHistory(resolveIssueHistorySync(issueId)); // null when not closed-out / no record
```

`deriveCvFromHistory` (exported from the resolver module): `totalIssues` = claimHistory length; success = claims with `outcome === 'completed'`; failure = `outcome === 'failed'`; `successRate` = success/(success+failure), 0 when denominator 0; `avgDuration` = mean of `(releasedAt - claimedAt)` minutes over completed claims (rounded); `recentWork` = last 3 claims mapped to `{issueId, startedAt: claimedAt, completedAt: releasedAt, outcome}`. Also in `show.ts`, when `pipelineStatus` is null but the resolver returns `closedOut`, print one durable verdict line: `pipeline review passed · test passed · merged · closed out <relative date>` (verdicts joined with ` · `, skipping nulls).

### Frontend wiring details

- **Tasks badge** (`useDrawerData.ts:235-251,422`, `IssueDrawer.tsx:11-15`): add a tasks query hook (alongside `useReviewStatusQuery` in `src/dashboard/frontend/src/components/CommandDeck/ZoneCOverviewTabs/queries.ts`) fetching `GET /api/issues/:id/tasks`; the badge computes `closed = tasks.filter(t => t.status === 'completed').length`, `total = tasks.length`, falling back to the current `0/0` derivation only while the query loads. (The TasksPanel already consumes this endpoint — reuse its hook if one exists; add one if not.)
- **Phase rail dates** (`useDrawerData.ts:307-333`): when the review-status payload carries `phases` (the additive field above), map `plan→planned`, `work→implemented`, `review→reviewed`, `ship→shipping`, `done→merged` and format with the existing `formatWhen`; live fields keep priority when the payload is not closed-out.
- **Specialist chips** (`deriveSpecialists.ts:78-127`): new input `closedOut` + `reviewerVerdicts` from the status payload. When no live session/sub-status exists for a role AND `closedOut`, emit `{status:'done', verdict, lastLine: verdict === 'blocked' ? 'blocked at close-out' : 'passed', hasConversation: <transcript retained>}`. Never emit the "starts when the convoy slot frees" copy when `closedOut`.
- **Conversations tab** (`DrawerAgentSession.tsx` / `IssueDetail.tsx:304-316`): when the store has no live agent for the issue, fetch the activity API (already queried elsewhere) and render the retained-session list — each row: role + agent id + a link/button opening the retained transcript via the existing conversation/JSONL viewer path. Replace the "Nothing here yet — no agent has started on this issue" copy only when the retained list is empty too.
- **Activity rail** (`useDrawerData.ts:397-416`): when the store's `recentActivity`/`detailedActivity` are empty for a closed-out issue, fall back to the activity API's durable entries (kind + summary + timestamp).

## Requirements

- **FR-1** — A closed-out issue's pipeline strip shows true per-phase dates (WORK/REVIEW/TEST/SHIP), resolved from the durable record after workspace archive.
- **FR-2** — Specialist chips for a closed-out issue show completed verdicts; the "QUEUED — starts when the convoy slot frees" copy never appears for a closed-out issue.
- **FR-3** — The drawer tasks badge shows real counts (e.g. `tasks 17/17`) sourced from `/api/issues/:id/tasks`.
- **FR-4** — The conversations tab lists the retained plan/work/review sessions (with transcript access) for a closed-out issue.
- **FR-5** — The activity rail shows durable history entries for a closed-out issue.
- **FR-6** — Verification gates and UAT show the journaled outcomes for a closed-out issue.
- **FR-7** — `pan show <id>` on a closed-out issue reports real work history (totals, success rate, recent entries) and the durable verdict line; never "(no work history)" for an issue with claim history.
- **FR-8** — Close-out journals the full verdict timeline (`history`, `reviewerVerdicts`, cycle history, UAT/verification verdicts) into the record before clearing runtime state.
- **NFR-1** — All history surfaces resolve through `src/lib/issue-history/resolver.ts`; no surface adds its own direct record/spec/agent-dir reads (single read door; the resolver itself uses the record door and `findSpecByIssue`).
- **NFR-2** — In-flight issues are unaffected: every fallback engages only when the live read is empty AND `record.pipeline.closedOut === true`. Existing route/CLI behavior for live issues is byte-identical.
- **NFR-3** — Regression: a fixture closed-out record + spec asserts the resolver and each read door return non-empty, correct history; an in-flight fixture asserts the fallback stays inert.
- **NFR-4** — Close-out changes are additive: nothing is cleared earlier, and no existing record field is rewritten after `closedOutAt`.

## NonGoals

- Not reverting or weakening the closed-out journal nulling in `review-status-read.ts` — runtime-cache hygiene stays; history surfaces get a durable read instead.
- Not promoting the event store or `status_history` SQLite tables to durable planes.
- Not changing what close-out tears down (workspace, Docker, branches, agent dirs, tmux sessions all still cleaned; only a record snapshot is added before clearing).
- Not backfilling pre-PAN-3420 records with a synthetic `history` array — the resolver degrades gracefully (`history: []`, specialists from `usage.byStage`).
- No visual/UX redesign of the issue detail page — data-source fixes only.
- Not changing the live read paths' behavior for in-flight issues in any way.
