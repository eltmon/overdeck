## Glossary

- **Directory:** the connect service, `services/connect`, a Cloudflare Worker with one `AccountDirectory` Durable Object (DO) per account. Public socket: `GET /v1/directory` (WebSocket upgrade).
- **Machine:** a dashboard server. It opens a directory socket with an `Authorization: Bearer odd_…` header and registers with a `hello` frame. Rows live in the DO's `machines` table.
- **Client / phone:** the phone app (PAN-4823). It opens a directory socket from a browser WebView, so it cannot send an `Authorization` header. It registers with a `hello-client` frame. This issue adds the `clients` table for it.
- **Role:** whether a socket is a machine socket or a client socket. A socket has no role until its first valid hello.
- **Bearer subprotocol:** the WebSocket subprotocol string `overdeck.bearer.<odd_token>` in the `Sec-WebSocket-Protocol` request header. The server must echo the same string in the 101 response, or the browser closes the socket.
- **Reducer:** the pure function `reduce(state, event, ctx) → { state, effects }` in `services/connect/src/directory-state.ts`. It makes every decision. The DO glue (`directory.ts`) runs the effects.
- **Effect:** a data instruction the reducer returns (`put-machine`, `send`, `close`, `log`, …). The glue runs them in order: persist → register → send → close → log.
- **Target:** where a `send` or `close` effect goes (`'self'`, `'others'`, `'all'`, `{ environmentId }`).
- **Attachment:** per-socket JSON that survives DO hibernation (`ws.serializeAttachment`).
- **Hibernation:** the DO may be evicted from memory while sockets stay open; the runtime restores attachments and tags, never in-memory fields.
- **Socket tag:** a string given to `ctx.acceptWebSocket(ws, tags)`. Tags are fixed at accept time and cannot change later.

## Requirements

### Functional

- **FR-1 Subprotocol auth.** `GET /v1/directory` accepts the account token as the subprotocol `overdeck.bearer.<odd_token>` in `Sec-WebSocket-Protocol` when no `Authorization` header is present, and the 101 response carries `Sec-WebSocket-Protocol: overdeck.bearer.<odd_token>` (the same string). The `Authorization` header form keeps working unchanged for machines.
- **FR-2 Client registration.** A socket whose first frame is a valid `hello-client` registers as a client: its row is upserted in a new `clients` table and it receives `welcome-client { protocol: 1, plan, relayAllowed, machines }`, where `machines` is the account's machine list with online state.
- **FR-3 Client cap.** At most `CLIENT_LIMIT` (5) client rows per account, on every plan. A `hello-client` for a new `clientId` when 5 rows exist gets `error { code: 'client_limit', message: CLIENT_LIMIT_MESSAGE }` and close `4013`. A known `clientId` re-registers on a full account.
- **FR-4 Clients are not machines.** A client never counts against `maxDevices`, never appears in any `welcome` or `directory` frame's `machines`, and never receives `approval-request`, `approval-cancel` or inbox frames.
- **FR-5 Clients see machine changes.** Every `directory` broadcast that machines receive is also sent to every registered client socket.
- **FR-6 Replacement.** A second socket for the same `clientId` closes the older one with `4011` (`replaced`).
- **FR-7 Signal routing.**
  - client → machine: forwarded when `to` is an online machine, with `from` stamped as the sender's `clientId`; `purpose` must be `'link'` (anything else is `bad_frame` at decode).
  - machine → client: forwarded when `to` is an online client and `purpose` is `'link'`, with `from` stamped as the machine's environment id.
  - client → client: refused with `error { code: 'bad_frame' }`.
  - target offline or unknown: `error { code: 'peer_offline' }` (with `session`), as for machines.
- **FR-8 ICE servers and relay metering for clients.** `ice-servers` and `relay-usage` from a client follow the machine rules unchanged: STUN for `relay: false`; for `relay: true` the order plan (`tester`) → monthly cap → TURN configured; usage is metered against the account and the resulting `relay-status` reaches every machine and every client.
- **FR-9 Forget.** `forget-client` from a client deletes its row and closes its socket with `4012` (`forgotten`). The freed slot is usable at once.
- **FR-10 Offline.** When a client's last socket closes, its row's `last_seen_at` is set to now; no frame is broadcast.

### Non-functional

- **NFR-1 No contract or machine change.** `packages/contracts/`, `src/`, and `packages/anywhere-channel/` are not modified. `CONNECT_PROTOCOL_VERSION` stays `1`.
- **NFR-2 Hibernation compatibility.** Sockets accepted before this deploy (tag `'machine'`, attachment `{ identity, environmentId }` with no `clientId`) keep working as machine sockets. The tag string `'machine'` is not renamed.
- **NFR-3 Logs.** Log lines for client events name the frame type, the `clientId` and the outcome, never a label, key, token, app version or payload.
- **NFR-4 Token stays in the Worker.** The bearer token (from the header or the subprotocol) never reaches the Durable Object; only the verified identity does (`X-Connect-Identity`), as today.
- **NFR-5 Module size.** No source file passes 600 lines; client-role reducer logic lives in a new module.
- **NFR-6 Tests.** Reducer tests are pure (no timers). The Miniflare test waits on events only, never sleeps (repo rule: fake timers for delays; real-socket tests have no sleeps).
- **NFR-7 Storage forward-compatibility.** The `clients` table is created with the three push columns PAN-4830 needs (`push_platform`, `push_token`, `aps_environment`, all nullable), because `CREATE TABLE IF NOT EXISTS` cannot add columns to a table that already exists in production.

## Decisions

- **D-1 Role lives in the attachment, not in a socket tag** (amends epic W-CON2 step 2, "Tag client sockets `client`"). Tags are fixed at `acceptWebSocket` (fact 5), but the role is known only at the first hello. Every socket keeps the tag `'machine'` (renaming it would orphan hibernated production sockets, NFR-2). The attachment gains `clientId: string | null`. Role rule: `clientId !== null` ⇒ client; else `environmentId !== null` ⇒ machine; else unregistered. An attachment without the `clientId` key reads as `null`. With at most 3+5 sockets per free account (tester accounts have more machines but still a handful), filtering by attachment costs nothing.
- **D-2 Token precedence.** If `Authorization` is present, it is the only token source (machines; behavior unchanged, no echo). Otherwise the token comes from the bearer subprotocol: split `Sec-WebSocket-Protocol` on `,`, trim each entry, take the first entry that starts with `overdeck.bearer.`; the rest of that entry must match `odd_[0-9a-f]{64}`, else 401 `invalid_token`. Neither present ⇒ 401 `invalid_token` (as today).
- **D-3 The Worker echoes the subprotocol** by re-wrapping the DO's 101 (fact 8), so the token never enters the DO (NFR-4). Only a response with `status === 101` and a non-null `webSocket` is re-wrapped; any other DO response passes through as today.
- **D-4 Decoding by role.** `protocol.ts` exports `decodeFrame(raw, role)` where `role` is `'machine' | 'client' | null`:
  - `null` (no hello yet): a frame whose `type` is `'hello-client'` is decoded with the client rules; every other frame with the machine rules (so `hello` registers a machine and any other first frame keeps today's close `4010 'hello required'`).
  - `'machine'`: machine rules only (`hello-client` ⇒ `bad_frame`).
  - `'client'`: client rules only: `hello-client`, `signal` (`purpose` must be `'link'`, `to` a UUID), `ice-servers`, `relay-usage`, `forget-client`. `push-register` and `push-unregister` stay `bad_frame` until PAN-4830 (W-CON3). Any machine-only type ⇒ `bad_frame`.
  - `hello-client` with `protocol !== 1` ⇒ `unsupported` (close 4010), exactly as `hello`.
  - `decodeMachineFrame(raw)` stays exported as `decodeFrame(raw, 'machine')` narrowed to machine frames, so existing callers and tests keep working.
- **D-5 Two reducers, one direction of import.** Client events go to a new `services/connect/src/client-state.ts` (`reduceClient`). It imports values and types from `directory-state.ts`; `directory-state.ts` never imports `client-state.ts`. The DO glue picks the reducer by event kind. Machine-side client awareness (state field, targets, machine→client signal, client broadcasts) stays in `directory-state.ts` as data and targets only. This keeps the graph acyclic (fact 16) and both files under 600 lines (NFR-5).
- **D-6 Targets.** `'others'` keeps its meaning — every other registered **machine** socket — so approvals (fact 11, lines 445, 465) stay machine-only with no edit. `'all'` stays self + other machines. Two new targets: `'clients'` (every registered client socket except the event's own) and `{ clientId }` (that client's sockets except the event's own). Every `directory` broadcast and the `relay-status` send gain a sibling `{ to: 'clients' }` effect with the same frame.
- **D-7 `signal.to` lookup order.** Both roles' `to` is a UUID. For a machine sender: `to === self` ⇒ `bad_frame`; approval purpose check (unchanged) ⇒ `approval_unknown`; `to` is an online machine ⇒ forward to it; `to` is an online client and `purpose === 'link'` ⇒ forward to `{ clientId: to }`; else `peer_offline`. An `approval` signal to a client therefore always fails the approval check first. For a client sender: `to` is any known client row (including itself) ⇒ `bad_frame` "a phone cannot signal a phone"; `to` is an online machine ⇒ forward; else `peer_offline`.
- **D-8 The cap counts rows, not online sockets,** and applies on every plan (it is the constant `CLIENT_LIMIT`, not `maxDevices`). This matches AC-2 and the contracts.
- **D-9 `ice-servers` and `relay-usage` share one implementation.** The two `case` bodies at `directory-state.ts:352-382` and `406-419` move into exported helpers (`iceServersAnswer`, `relayUsageAnswer`) taking a log subject, used by both reducers. No behavior change for machines except the extra `{ to: 'clients' }` relay-status send.
- **D-10 Plan is refreshed by `hello-client` too.** As `hello` does (`directory-state.ts:210-211`), a `hello-client` whose identity plan differs from `state.plan` emits `put-plan`. A client's relay check then sees the current plan even if no machine is online.
- **D-11 Log subject.** The `log` effect gains an optional `clientId`; `logFrame(type, environmentId, outcome, clientId?)` adds `"client": <clientId>` to the JSON line only when given. Client events log `environmentId: null`.
- **D-12 `onlineClients` is optional in `ReduceContext`** (default empty set). The glue always passes it; existing reducer tests that build `ctx` literals keep running without edits.
- **D-13 Client rows carry push columns but `ClientRow` does not.** The SQL table has `push_platform`, `push_token`, `aps_environment` (NFR-7). The `put-client` upsert never writes them (its `ON CONFLICT … DO UPDATE SET` lists only the identity columns and `last_seen_at`), so a re-registering phone keeps a registration PAN-4830 stored. `ClientRow` gains push fields in PAN-4830, not here.
- **D-14 Machines cannot forget clients.** A machine `forget` naming a clientId finds no machine and logs `unknown_machine`, as today. Machine-side removal of a directory client is out of scope (see Hazards H-3).

     export function directoryToken(headers: Headers): { authorization: string | null; protocol: string | null } {

## Hazards

- **H-1 Hibernated attachments.** Production sockets accepted before the deploy have no `clientId` key. `roleOf` must treat a missing key as `null` (machine if `environmentId` is set). Renaming the tag would make `getWebSockets('machine')` miss them.
- **H-2 Overloading `'others'`.** If client sockets were added to `registered()`, approvals (`directory-state.ts:445`, `465`) and inbox delivery would reach phones. Keep `registered()` machine-only and give clients their own targets.
- **H-3 Stale client rows hold slots.** The cap counts rows (D-8). A phone that is lost or uninstalled without `forget-client` keeps its row; after five such phones the account cannot add a phone. The epic's `CLIENT_LIMIT_MESSAGE` says "Remove one in the app or on a machine", but no machine path removes a directory client yet. Recommended follow-up (to be filed against the epic): a machine frame that forgets a client, wired to the device list's Remove (W-MAC1 step 6). Not built here.
- **H-4 Undici and 101.** `routes.test.ts` cannot construct a 101 (fact 15); the echo is asserted only in the Miniflare test. Keep the re-wrap behind `res.status === 101 && res.webSocket` so the 204 fake stub path still returns the stub response.
- **H-5 Miniflare test ordering.** All tests in `miniflare.test.ts` share one Miniflare instance and its Durable Object state. After the existing 4009 test the `u-free` account holds envs 1, 2 and 4. The phone tests therefore use their own free account (`u-phones`, WI-7) and machines `envId(41..43)`, so they pass regardless of test order.
