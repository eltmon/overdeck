# PAN-5447: Command palette conversation search stalls 15 s+

**Issue:** [PAN-5447](https://github.com/eltmon/overdeck/issues/5447)
**Status:** Planned (auto mode, 2026-11-17)
**Base commit:** `0917c8358a7`

## Summary

Ctrl+J conversation search runs a 1.1–1.2 s brute-force sqlite-vec KNN scan on
the dashboard's main thread for every keystroke-level request, and searches the
browser has already abandoned keep running to completion. Overlapping searches
stack, freeze the event loop (`/api/version` stalled 4.8 s), and the final query
waits behind them; under memory pressure the operator saw a 16.5 s request end
in a 499.

This change moves the BM25 and vector scans into the existing dashboard DB
worker thread on two new serial lanes, threads the HTTP request's abort signal
through the whole search so a superseded request stops before its scan, runs
BM25 concurrently with the query embedding, bounds every slow leg with a
deadline that degrades to keyword + title results, and gives the palette client
a 10 s timeout with its own message.

## Glossary

- **Palette search route** — `GET /api/palette/search?q=&limit=` in
  `src/dashboard/server/routes/palette.ts`. Serves the Ctrl+K / Ctrl+J palette,
  the MCP `search_conversations` tool (`src/lib/mcp/tools-read.ts:98`) and
  fleet peers (`src/dashboard/server/routes/fleet-awareness.ts:118`, 2.5 s
  budget per peer).
- **Chunk search** — the conversation transcript search over the
  `embeddings.db` sidecar: BM25 over `chunks_fts` plus KNN over the sqlite-vec
  `chunks_vec` virtual table, fused with reciprocal rank fusion (RRF) in
  `src/lib/conversation-search/ranker.ts`.
- **BM25 leg** — `EmbeddingsDbHandle.searchBm25` (`src/lib/database/conversation-embeddings-db.ts:424`).
  Synchronous SQLite FTS5 query; up to ~0.5 s on a cold page cache.
- **Vector leg** — `EmbeddingsDbHandle.searchVector`
  (`conversation-embeddings-db.ts:437`). Synchronous brute-force KNN over
  515,905 × 1536-float vectors; 1.1–1.2 s warm, much slower cold.
- **Query embedding** — one OpenAI `embedMany` call for the query text
  (`src/lib/conversation-search/embedding-provider.ts`, `embed`), 220–420 ms
  measured. Async network I/O; it stays on the main thread.
- **Live filter** — `filterLiveHits` in
  `src/dashboard/server/services/conversation-search-service.ts:108`. Drops
  hits whose transcript file no longer exists (lists `file_cursors`, then
  `stat`s each path).
- **Dashboard DB worker** — the `node:worker_threads` pool driven by
  `runDashboardDbJob` in `src/dashboard/server/services/dashboard-db-task.ts`,
  executing ops in `src/dashboard/server/services/dashboard-db-worker.ts`. One
  worker thread per **lane**; each worker runs one job at a time
  (`MAX_CONCURRENT_JOBS_PER_LANE = 1`, `dashboard-db-worker.ts:186`).
- **Lane** — `WorkerLane` (`dashboard-db-task.ts:64`), today
  `'read' | 'long' | 'semantic' | 'parse' | 'poll'`. This change adds
  `'conversation-text'` and `'conversation-vector'`.
- **Serial lane** — a lane whose waiting jobs are queued on the **main thread**
  and posted to the worker one at a time, so an aborted waiter is removed
  before the worker ever sees it. New concept in this change.
- **Superseded search** — a palette request the browser aborted because the
  user typed more (the palette aborts the previous fetch on every debounced
  keystroke, `CommandPalette.tsx:418`).
- **Request signal** — the `AbortSignal` that `Effect.promise((signal) => …)`
  hands its callback. It aborts when the request fiber is interrupted.
  `@effect/platform-node`'s `NodeHttpServer` interrupts the request fiber with
  `ClientAbort` when the client socket or response closes
  (`node_modules/@effect/platform-node/dist/NodeHttpServer.js:154-156` and
  `:192-194`, grep `fiber.interruptUnsafe(parent.id, ClientAbort.annotation)`).
  The dashboard serves through that path: `src/dashboard/server/server.ts:203`
  (`NodeHttpServer.make(() => {`) installs `makeHandler` as the `request`
  listener, and `server.ts:613` (`HttpRouter.serve(makeRoutesLayer, { disableLogger: true })`)
  mounts the routes. `holdRequestsUntilServed` (`server-bind.ts:44`) only holds
  requests during startup and then hands each one to that same handler.
- **Deadline** — a per-leg time budget measured from the moment the leg is
  submitted. A leg that misses its deadline contributes no rows; the search
  still returns the other legs' rows.
- **Degraded result** — a palette response built without one or more legs
  (vector, BM25, live filter) because of a deadline or an embedding failure.

## Root cause (verified against code at `0917c8358a7`)

1. **Synchronous scans on the event loop.**
   `searchConversationChunks` (`conversation-search-service.ts:60-100`) opens
   the embeddings DB on the main thread (`getHandle`, line 41) and calls
   `handle.db.searchBm25` / `handle.db.searchVector` synchronously (lines
   78-79). The `setImmediate` wrapper (line 72) only defers the work by one
   tick; it does not move it off the thread. node:sqlite `DatabaseSync` has no
   interrupt API (prototype is `open, close, prepare, exec, function, location,
   aggregate, createSession, applyChangeset, enableLoadExtension,
   loadExtension`, checked on Node v22.22.0), so a started scan cannot be
   stopped.
2. **Superseded searches run to completion.** The route
   (`palette.ts:498`) uses `Effect.promise(async () => …)` without taking the
   signal, so `runPaletteSearch` never learns the client left.
3. **Cheap legs wait for the expensive one.** `rankConversationSearch`
   (`ranker.ts:48`) awaits the embedding (`ranker.ts:56`,
   `await options.provider.embed([query])`) before it starts BM25, and the
   route returns nothing until the vector scan finishes. `embed` has no timeout.
   `runPaletteSearch` (`palette.ts:445-481`) also awaits the memory FTS fan-out
   before it starts conversation search (line 474).
4. **The client never times out.** `fetchPaletteSearch`
   (`CommandPalette.tsx:253-270`) waits for the request to settle.

## Decisions (made here; auto mode)

- **D1 — Scans move to the existing dashboard DB worker, on two new lanes.**
  BM25 and the live filter run on lane `conversation-text`; the vector scan runs
  on lane `conversation-vector`. No new worker entry, so no change to
  `src/dashboard/server/tsdown.config.ts` or
  `apps/desktop/scripts/prepare-server-resources.mjs` (`ENTRY_POINTS`). The
  worker already loads sqlite-vec (`getConversationSearchStats` runs on the
  `poll` lane).
- **D2 — Two lanes, not one.** A vector scan that cannot be stopped must not
  delay the next query's BM25 leg. Each lane has its own worker thread and its
  own read connection; the OS page cache is shared, so memory cost is two small
  SQLite page caches.
- **D3 — Waiters queue on the main thread (serial lanes).** The worker starts a
  synchronous job inside its `message` handler, so a cancel message posted
  after job B cannot overtake B. For `conversation-text` and
  `conversation-vector`, `runDashboardDbJob` posts one job at a time per lane
  and keeps the rest in a main-thread FIFO. Abort removes a waiter from the
  FIFO. The in-flight job always runs to completion; its result is discarded
  if its caller aborted.
- **D4 — Never terminate the worker to cancel.** Terminating does not stop a
  native SQLite call already running (V8 termination only lands when control
  returns to JS), so a replacement worker would scan concurrently with the
  dying one, and every keystroke burst would reopen the 5.1 GB DB.
- **D5 — Cancellation is per request signal, never global latest-wins.** The
  palette route also serves MCP `search_conversations`, fleet peers and other
  browser tabs. The `semantic` lane's `cancelOlderSemanticSearches`
  (`dashboard-db-task.ts:210-215`) would let one client cancel another's
  search, so it is not reused.
- **D6 — Query embedding stays on the main thread**, runs concurrently with the
  BM25 leg, and gets a 2,500 ms timeout (`QUERY_EMBED_TIMEOUT_MS`). Measured
  latency is 220–420 ms, so 2.5 s is ~6× headroom.
- **D7 — Deadlines.** BM25 leg and vector leg: 4,000 ms each
  (`CHUNK_SCAN_DEADLINE_MS`), measured from submission, so queue wait counts.
  Live filter: 2,000 ms (`LIVE_FILTER_DEADLINE_MS`). A missed deadline aborts
  the leg's job (removing it from the waiter FIFO if it has not started) and
  the leg contributes `[]`; the live filter on deadline returns the hits
  unfiltered. Server worst case is about max(4, 2.5 + 4) + 2 = 8.5 s, under
  the client's 10 s timeout.
- **D8 — Health recording.** An abort records nothing. An embedding failure or
  embedding timeout calls `recordConversationSearchFailure(error)` (PAN-3771
  banner) and the search still returns BM25 + title rows. A successful
  embedding calls `recordConversationSearchSuccess()`. A leg deadline logs one
  `console.warn` line and records nothing. Any other store error keeps today's
  behavior: record failure, return `[]`.
- **D9 — Client timeout is 10,000 ms** (`PALETTE_SEARCH_TIMEOUT_MS`), with its
  own controller and its own message, distinct from a supersede abort.
- **D10 — Memory FTS and conversation search run in parallel** inside
  `runPaletteSearch` (memory FTS is already a worker; awaiting it first only
  adds latency).
- **D12 — Known residual.** A superseded request whose embedding finished
  before its abort has already posted its vector job; that scan runs to
  completion (D4) and the next query's vector job waits for it. Because the
  4 s deadline counts queue wait (D7), on a cold page cache the final query can
  return keyword + title rows only, with no indication (D11). This is intended:
  a fast degraded answer beats a 16 s spinner.
- **D11 — No new response fields.** The palette response shape
  (`{ memory, observations, summaries, conversations }`) is unchanged; degraded
  results are not flagged to the client in this issue.

## Requirements

### Functional

- **FR-1** — A search whose HTTP client disconnects stops before the vector
  scan: when the request signal aborts during the query embedding or while the
  vector job waits in the main-thread FIFO, no vector job reaches the worker
  for that request.
- **FR-2** — The BM25 leg starts without waiting for the query embedding.
- **FR-3** — A query-embedding failure or a query-embedding timeout
  (2,500 ms) still returns BM25 hits and title matches.
- **FR-4** — A BM25 or vector leg that exceeds 4,000 ms from submission
  contributes no rows, and the route returns the remaining rows.
- **FR-5** — The palette client stops waiting after 10,000 ms, aborts the
  request, and shows "Search timed out after 10 s. Try again." instead of the
  spinner.
- **FR-6** — An aborted search records neither a failure nor a success in
  conversation-search health and logs no `[palette] search failed` line.
- **FR-7** — Memory FTS search and conversation search start concurrently.

### Non-functional

- **NFR-1** — The dashboard main thread runs no `embeddings.db` SQLite query
  for palette search: `conversation-search-service.ts` no longer imports
  `openEmbeddingsDb`.
- **NFR-2** — At most one BM25/live-filter job and one vector job run at any
  time across all palette searches (one per serial lane).
- **NFR-3** — No worker thread is terminated to cancel a search.
- **NFR-4** — Every delay-based test uses `vi.useFakeTimers()` and
  `vi.advanceTimersByTimeAsync()`; none waits on real time.

### WI-4 — Ranker: concurrent BM25, abortable embedding with timeout

**Files:** `src/lib/conversation-search/ranker.ts`,
`src/lib/conversation-search/__tests__/ranker.test.ts`.

**Before (`ranker.ts:48-66`):**

```ts
export async function rankConversationSearch(options) {
  const query = options.query.trim();
  if (!query) return [];
  const limit = options.limit ?? DEFAULT_LIMIT;
  const candidateLimit = options.candidateLimit ?? Math.max(DEFAULT_CANDIDATE_LIMIT, limit);
  const embeddedQuery = await options.provider.embed([query]);
  const queryEmbedding = embeddedQuery.embeddings[0];
  if (!queryEmbedding) return [];

    Promise.resolve(options.store.searchBm25(query, candidateLimit)),
    Promise.resolve(options.store.searchVector(queryEmbedding, candidateLimit)),
  ]);
  return fuseRankedRows({ bm25Rows, vectorRows, query, limit, rrfK: options.rrfK ?? DEFAULT_RRF_K });
}
```

**After:**

```ts
export const DEFAULT_EMBED_TIMEOUT_MS = 2_500;

export class ConversationQueryEmbedTimeoutError extends Error {
  constructor(readonly timeoutMs: number) {
    super(`Query embedding timed out after ${timeoutMs} ms`);
    this.name = 'ConversationQueryEmbedTimeoutError';
  }
}

export interface RankConversationSearchOptions {
  query: string;
  store: ConversationRankerStore;
  provider: ConversationEmbeddingProvider;
  limit?: number;
  candidateLimit?: number;
  rrfK?: number;
  /** Request signal; abort rejects with signal.reason and skips the vector leg. */
  signal?: AbortSignal;
  /** Query-embedding budget; default DEFAULT_EMBED_TIMEOUT_MS. */
  embedTimeoutMs?: number;
  /** Called once when the embedding fails or times out (not on abort). */
  onEmbedFailure?: (error: unknown) => void;
  /** Called once when the embedding succeeds. */
  onEmbedSuccess?: () => void;
}

export async function rankConversationSearch(options: RankConversationSearchOptions): Promise<ConversationSearchHit[]> {
  const query = options.query.trim();
  if (!query) return [];
  options.signal?.throwIfAborted();
  const limit = options.limit ?? DEFAULT_LIMIT;
  const candidateLimit = options.candidateLimit ?? Math.max(DEFAULT_CANDIDATE_LIMIT, limit);

  const bm25 = Promise.resolve().then(() => options.store.searchBm25(query, candidateLimit));
  const vector = embedQuery(options, query).then(
    (embedding) => {
      options.signal?.throwIfAborted();
      return embedding ? options.store.searchVector(embedding, candidateLimit) : [];
    },
    (error: unknown) => {
      options.signal?.throwIfAborted();
      options.onEmbedFailure?.(error);
      return [];
    },
  );
  const [bm25Rows, vectorRows] = await Promise.all([bm25, vector]);
  options.signal?.throwIfAborted();
  return fuseRankedRows({ bm25Rows, vectorRows, query, limit, rrfK: options.rrfK ?? DEFAULT_RRF_K });
}
```

`embedQuery(options, query)` (private): creates an `AbortController`, links
`options.signal` to it (abort → `controller.abort(options.signal.reason)`),
starts `setTimeout(() => { timedOut = true; controller.abort(); }, options.embedTimeoutMs ?? DEFAULT_EMBED_TIMEOUT_MS)`,
calls `options.provider.embed([query], { signal: controller.signal })`, and in
`finally` clears the timer and removes the listener. If `timedOut` and the call
rejected, throw `new ConversationQueryEmbedTimeoutError(ms)`. On success call
`options.onEmbedSuccess?.()` and return `result.embeddings[0] ?? null`.

The vector leg runs only after the embedding resolves, so an abort during the
embedding means `searchVector` is never called (FR-1). `ConversationRankerStore`
is unchanged.

test `src/dashboard/server/services/__tests__/conversation-search-service.test.ts`.

**Steps:**

1. Remove the main-thread DB handle: drop `openEmbeddingsDb` /
   `dimensionsForModel` / `EmbeddingsDbHandle` imports, the `db` field of
   `ConversationSearchServiceHandle`, `filterLiveHits`, and the `setImmediate`
   wrapper. `getHandle` caches only the provider, keyed by the same
   `signatureForConfig`.
2. Export constants `CHUNK_SCAN_DEADLINE_MS = 4_000`,
   `LIVE_FILTER_DEADLINE_MS = 2_000`.
3. New signature:

   ```ts
   export async function searchConversationChunks(input: {
     rawQuery: string;
     matchQuery: string;
     limit: number;
     candidateLimit?: number;
     config?: NormalizedConversationSearchConfig;
     signal?: AbortSignal;
   }): Promise<ConversationSearchHit[]>
   ```

4. Private `runLeg<T>(operation, payload, deadlineMs, signal)`: creates a
   deadline `AbortController`, `setTimeout(() => deadline.abort(new ChunkLegDeadlineError(operation, deadlineMs)), deadlineMs)`,
   combines with `const combined = signal ? AbortSignal.any([signal, deadline.signal]) : deadline.signal`,
   calls `runDashboardDbJob<ChunkSearchJobResult<T>>(operation, payload, undefined, { signal: combined })`,
   clears the timer in `finally`. Returns the job result; rethrows everything
   except `ChunkLegDeadlineError`, which it maps to `{ deadline: true }` after a
   single `console.warn('[conversation-search] <operation> exceeded <ms> ms; continuing without it')`.
5. Store adapter passed to `rankConversationSearch`:
   - `searchBm25` → `runLeg('searchConversationBm25', { dbPath, model, matchQuery: input.matchQuery, limit }, CHUNK_SCAN_DEADLINE_MS, signal)`;
     deadline ⇒ `[]`; `available:false` ⇒ throw an internal
     `EmbeddingsDbUnavailable` marker.
   - `searchVector` → same with `'searchConversationVector'` and `{ embedding, limit }`.
6. Call `rankConversationSearch({ …, signal: input.signal, onEmbedFailure: recordConversationSearchFailure, onEmbedSuccess: recordConversationSearchSuccess })`.
7. Live filter: unique session ids of the hits →
   `runLeg('filterLiveConversationSessions', { dbPath, model, sessionIds }, LIVE_FILTER_DEADLINE_MS, signal)`;
   keep hits whose `sessionId` is in the returned list; deadline ⇒ keep all hits.
8. Error handling: if `input.signal?.aborted`, rethrow `input.signal.reason`
   and record nothing. `EmbeddingsDbUnavailable` ⇒ return `[]`, record nothing
   (today's behavior when `db.available` is false). Any other error ⇒
   `recordConversationSearchFailure(error)`, `console.error` as today, return `[]`.
9. `closeConversationSearchService()` also calls `closeChunkSearchHandles()`
   (closes the Vitest inline cache; production worker handles die with the
   process).

### WI-7 — Palette client timeout

**Files:** `src/dashboard/frontend/src/components/CommandPalette.tsx`,
`src/dashboard/frontend/src/components/CommandPalette.test.tsx`.

**Before (`CommandPalette.tsx:253-270`):** `fetchPaletteSearch(query, signal)`
passes the effect's `signal` straight to `fetch` and returns `EMPTY_SEARCH` on
any `AbortError`.

**After:**

```ts
const PALETTE_SEARCH_TIMEOUT_MS = 10_000;
const SEARCH_TIMED_OUT = 'timed out';

async function fetchPaletteSearch(query: string, signal: AbortSignal): Promise<PaletteSearchResponse> {
  // Own controller: a supersede abort (signal) and our timeout must stay distinguishable (PAN-5447).
  const request = new AbortController();
  const onSupersede = () => request.abort();
  signal.addEventListener('abort', onSupersede, { once: true });
  let timedOut = false;
  const timer = setTimeout(() => { timedOut = true; request.abort(); }, PALETTE_SEARCH_TIMEOUT_MS);
  try {
    const res = await fetch(`/api/palette/search?q=${encodeURIComponent(query)}&limit=15`, { signal: request.signal });
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    const data = await res.json() as PaletteSearchResponse;
    return { /* unchanged mapping */ };
  } catch (err) {
    if (signal.aborted) return EMPTY_SEARCH;
    if (timedOut) throw new Error(SEARCH_TIMED_OUT);
    throw err;
  } finally {
    clearTimeout(timer);
    signal.removeEventListener('abort', onSupersede);
  }
}
```

The effect (lines 388-419) is unchanged: a timeout rejects, the `.catch` sets
`searchError` to `'timed out'` (the effect's own controller is not aborted),
and `.finally` clears the spinner.

inside `Command.Empty` (lines 936-945), which renders only when
`visibleGroups.length === 0`. In the All scope, or with fleet/file hits, other
matching rows would hide it and the user would see neither spinner nor message.
So:

1. Define `const searchTimedOut = searchError === SEARCH_TIMED_OUT && query.trim().length >= 2;`.
2. Directly after the spinner row (the `isSearchLoading && …` block at lines
   930-935), render a notice row in the same slot and style, without the
   spinner icon, when `!isSearchLoading && searchTimedOut`:
   `Search timed out after 10 s. Try again.`
3. In the empty-state branch, render `null` instead of `Command.Empty` when
   `searchTimedOut` (the notice row already says it). All other empty-state
   text is unchanged, including
   `` `Search unavailable (${searchError}): sign in again / try again` ``.

## Planning Q&A

Auto mode: no operator questions were asked. Defaults chosen and why:

- **Q: One worker lane or two for the scans?** Options: one lane (simpler),
  two lanes (BM25 never waits behind an unstoppable vector scan). **Chosen:**
  two lanes (D2).
- **Q: Cancel by terminating the worker or by a main-thread waiter queue?**
  **Chosen:** main-thread queue; terminate cannot stop native SQLite and would
  reopen a 5.1 GB DB per burst (D3, D4).
- **Q: Server-side deadline for the vector leg?** Options: none (rely on the
  client timeout), or a deadline that degrades to keyword + title. **Chosen:**
  4 s deadline per leg (D7), so a cold-cache scan yields keyword results
  instead of a spinner.
- **Q: Timeout values?** Embedding 2.5 s (measured ≤ 420 ms), scan legs 4 s,
  live filter 2 s, client 10 s (above the ~8.5 s server bound).
- **Q: Record embed timeouts in the health banner?** **Chosen:** yes for
  embedding failure and timeout, never for abort or scan deadline (D8).
