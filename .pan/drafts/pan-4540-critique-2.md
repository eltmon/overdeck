## blocks-the-design: Fresh mergeability read can return the same cached answer

`src/lib/cloister/merge-gate.ts:117-120` retries after 3 seconds with `fresh: true`. That flag skips only `prFactsCache` (`src/lib/cloister/pr-facts.ts:588-594`): `readPrFacts` passes no freshness flag to `fetchIssuePullRequest` (`src/lib/cloister/pr-facts.ts:654-657`). The default fetch still returns the PR tab's cached response (`src/lib/overdeck/pull-requests.ts:275-289`), whose TTL is 60 seconds (`src/dashboard/server/services/pr-tab-cache.ts:9-15,37-45`). Thus an initial `mergeable: null` can be read again from the same cached response, violating FR-3 and the re-read acceptance criterion even if GitHub computed mergeability during the 3-second wait. The proposed test injects `getFacts` (`src/lib/cloister/__tests__/merge-gate.test.ts:143-155`), so it cannot detect this cache path. Pass `fresh` through to `fetchIssuePullRequest` and bypass its PR tab cache for the retry; add a test using the real cache path with an initial cached UNKNOWN response.

## blocks-the-design: Concurrent merge still strands an auto-merge row

`triggerMerge` checks `normalMergeEligibility` before its forge gate (`src/dashboard/server/routes/workspaces/merge-ops.ts:275-281`). An already running merge of the same issue returns `{ success: false, outcome: 'merging' }` (`src/dashboard/server/routes/workspaces/merge-strike.ts:416-427`). The executor handles a failed result without `refused`, `deferred`, or `retryable` by calling `markFailed` (`src/dashboard/server/services/auto-merge-executor.ts:264-305`), and the scheduler will not re-arm a failed row at the same head (`src/dashboard/server/services/auto-merge-scheduler.ts:146-156`). No merge command ran for this auto-merge attempt, so a manual merge that later fails or stops can strand its approved head. Return this active-merge refusal as `deferred` from `triggerMerge`; the executor already requeues deferred results at lines 275-281. Add an executor test for that result path.

## sharpens-framing: Failed-row definition contradicts retained refusals

The PRD defines a failed row as one whose merge command ran (`.pan/drafts/pan-4540.md:11`), and the xBRIEF's docs acceptance criterion repeats that definition. Yet FR-1 deliberately leaves closed-PR, wrong-target, polyrepo, and `.planning/` refusals as failed before a merge command (`.pan/drafts/pan-4540.md:36-41,102-108`); the current docs acknowledge that exception (`docs/MERGE-WORKFLOW.md:178-182`). Revise the glossary and xBRIEF docs criterion to say that `failed` also includes refusals requiring operator action, so implementation and documentation do not imply that every failed row attempted a merge.
