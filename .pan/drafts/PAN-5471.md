## Summary

Overdeck has no user page that explains how it chooses the model and harness for each agent. The published pages that try are wrong: `features/cloister.mdx` describes a keyword "complexity detection" router with a Haiku/Kimi/Opus table and a `~/.overdeck/cloister/config.json` `model_selection` block, and `concepts.mdx` says Overdeck routes "automatically based on task type, capability, and budget". That router was deleted in PAN-1048 (`docs/MODEL_ROUTING.md` banner). `configuration/harnesses.mdx` also says a role `harness` setting wins and that Settings has a harness selector per role; neither is true.

This issue adds one page, `configuration/model-routing.mdx`, puts it in `docs.json` navigation, replaces the two stale sections with short pointers, corrects the two harness claims, and links the new page from the presets, effort and developer routing docs.

Every fact the page needs is in the **Fact sheet** below, each with its source. The writer uses the fact sheet and must not copy old docs or `blog/standing-crew.mdx` (the blog draft describes standing tier sessions and promotion that do not run today). If code moved since this PRD was written, the code wins: re-check the cited source and say so in the commit body.

## Glossary

- **Role**: one kind of agent run in Overdeck. The role literals are `plan`, `work`, `review`, `test`, `ship`, `strike`, `sequencer`, `knowledge`, `worker` and `flywheel` (`DEFAULT_ROLES` in `src/lib/config-yaml/roles.ts`). Each has a role file in `roles/<role>.md`, except `ship`, which runs server-side.
- **Sub-role**: a configuration slot under a role, with its own model and effort. Review has four: `security`, `correctness`, `performance`, `requirements`. Plan has one: `critic`.
- **Workhorse slot**: one of three named model slots, `expensive`, `mid` and `cheap` (`workhorses:` in `~/.overdeck/config.yaml`). Roles and tiers point at a slot with the reference `workhorse:<slot>`.
- **Model reference (ref)**: the value of a `model` setting. It is a model id (`claude-opus-5-5`), a workhorse ref (`workhorse:mid`), a weighted list (a distribution), or, for a sub-role only, `parent`.
- **Harness**: the coding-agent CLI that runs a model (`claude-code`, `codex`, `pi`, `kimi-code`, `opencode`, `acp`, `muse`, `prime-agent`, `grok`, `ohmypi`).
- **Provider default harness**: the harness a provider's models run on unless something picks one explicitly. Set it in Settings → Providers ("Default harness"), stored as `models.providers.<provider>.harness`. In code the normalized map is `providerHarnesses`.
- **Tiered execution**: optional staffing that picks the work agent's model, harness and effort from the plan items' `difficulty` (and optionally `kind`), instead of `roles.work`. Configured in `tiered_execution:`. The blog name is **Standing Crew**; the Settings UI calls a tier a **crew** and the supervisor the **Standing reviewer**.
- **Tier / crew**: one row of the tier table: a model (or distribution), a harness, optional effort, and the difficulties it owns.
- **Swarm**: the mode where an issue's plan items run in parallel slot agents (`pan swarm`, `features/swarm.mdx`).
- **Preset**: a one-time write of a coherent model lineup into `config.yaml` (`configuration/model-presets.mdx`).
- **Mintlify**: the docs generator. Pages are `.mdx` files at the repo root; navigation is `docs.json`.

## Fact sheet (verified 2026-11-18 against v0.89.0, commit 76237b3febb)

### Model resolution for a role

- F-1. A role's model resolves through `resolveModel(role, subRole, config, spawnKey)` (`src/lib/config-yaml/roles.ts`, search `export function resolveModel`). Order: the sub-role's model if set and not `parent`; else the role's model (a distribution picks one entry, see F-9); else the built-in default (`DEFAULT_MODEL_REFS`). A workhorse ref is then replaced with the slot's model (`derefWorkhorse`).
- F-2. Built-in role defaults (`DEFAULT_ROLES` and `DEFAULT_MODEL_REFS`, `src/lib/config-yaml/roles.ts`):
  | Role | Default model | What it does (source) |
  |---|---|---|
  | `plan` | `workhorse:expensive` | Researches the issue, writes the PRD and xBRIEF plan (`roles/plan.md`) |
  | `work` | `workhorse:mid` | Implements the plan's items in the issue workspace (`roles/work.md`) |
  | `review` | `workhorse:expensive`, `mode: quick` | Reviews the PR; in `full` mode writes the synthesis of the four lanes (`roles/review.md`) |
  | `review.security` | `workhorse:expensive` | Security lane (`full` mode only) |
  | `review.correctness`, `review.performance`, `review.requirements` | `workhorse:mid` | The other three lanes (`full` mode only) |
  | `test` | `workhorse:mid` | Runs verification suites and browser UAT (`roles/test.md`) |
  | `ship` | `workhorse:mid` | Shipping is server-side; no ship agent is spawned in the normal pipeline. The setting remains for the merge specialist identity (`docs/ROLES.md`, "There is no spawned `ship` role file") |
  | `strike` | `workhorse:expensive` | Precision fix opened as a PR against `main`, skipping plan, review and test (`roles/strike.md`) |
  | `sequencer` | `workhorse:expensive` | Ranks the open backlog into `.pan/backlog/sequence.md` (`roles/sequencer.md`) |
  | `knowledge` | `workhorse:expensive` | Maintains the project's OKF knowledge bundle, started by `pan knowledge` (`roles/knowledge.md`, `src/cli/commands/knowledge.ts`) |
  | `worker` | `workhorse:mid` | A delegated worker from `pan worker run` (`roles/worker.md`) |
  | `flywheel` | `claude-opus-5-5`, `effort: high` | The Flywheel orchestrator (`roles/flywheel.md`) |
- F-3. Built-in workhorse defaults (`DEFAULT_WORKHORSES`): `expensive: claude-opus-5-5`, `mid: claude-opus-5-5`, `cheap: claude-haiku-5-5`. Only these three slot names are allowed; another key fails config load ("unknown workhorse slot", `mergeRoleConfig`). A slot cannot point at another slot or at `parent` (`validateRoleModelRefs`).
- F-4. A ref to a slot that is not defined fails with `config.yaml: <field> references workhorse:<slot> but workhorses.<slot> is not defined` (`derefWorkhorse`).
- F-5. Review mode `roles.review.mode`: `quick` (default, one reviewer), `full` (four lanes plus the review parent's synthesis), `none` (no AI review; the verification gate still runs). Setting `roles.review.model` alone does not move the lanes, because each lane has its own default; set a lane to `parent` to inherit `roles.review.model` (`docs/CONFIGURATION.md`, "Review Mode and Reviewer Models"; `RolesPanel.tsx` review mode options). `roles.review.sub.synthesis` is retired (`RETIRED_SUB_ROLES`).
- F-6. The plan critic model is `roles.plan.sub.critic.model`. It has no default and must be from a different model family than the planner (`docs/CONFIGURATION.md`, "Plan critic model"). Link to `/features/planning` for details; do not repeat them.
- F-7. A role's `effort` (`roles.<role>.effort`) and a sub-role's (`roles.<role>.sub.<name>.effort`) feed the effort precedence chain (F-24).
- F-8. Per-call overrides: `pan start <id> --model <model>` sets the work model for that session and skips tier selection (`resolveSingleWorkTierSpawnParams` in `src/lib/agents/spawn-prep.ts`, comment "an override skips tier selection entirely"). `pan start --plan-model <model>` overrides the planning model when that start auto-plans. `pan plan <id> --model <model>` sets the planning model. Note: `pan start --tier` is unrelated; it is the remote workspace resiliency tier `ephemeral | durable` (`pan start --help`).
- F-9. Distribution: a role's `model` can be a list of `{ model, weight }` entries (positive integer weights). The pick is a hash of the spawn key `<role>:<issueId>`, so one issue always gets the same entry across respawns (`pickPercentModelRef` via `resolveModel`; spawn key built in `src/lib/agents/spawn.ts`, search `const modelSpawnKey`). A sub-role never samples the parent's distribution. In Settings the role card's button reads `Use distribution` (and `Use single model` to go back) (`RolesPanel.tsx`).
- F-10. `GET /api/models/resolve` returns the model each role and review lane resolves to under the current config (`src/dashboard/server/routes/specialists/project-routes.ts`).

### Settings → Model Routing (dashboard)

All UI labels below are quoted from `src/dashboard/frontend/src/components/Settings/`.

- F-11. Settings is the first sidebar entry `Model Routing`, then `Providers`, ..., `Coding Agents`, `Tiered Execution` (`settingsPageConstants.ts`, `SETTINGS_NAV_ITEMS`). The Model Routing section shows, top to bottom: the presets bar (`ModelPresetsBar.tsx`), `Workhorse Models` ("Set the three model slots that roles reference with workhorse:<slot>."; slots `Expensive`, `Mid`, `Cheap`), and `Role Models` ("Route plan, work, review, test, ship, and Flywheel runs through workhorse slots or explicit models.") (`SettingsPage.tsx`, search `id="model-routing"`).
- F-12. `Role Models` shows eight role cards: Plan, Work, Strike, Review, Test, Ship, Flywheel, Sequencer (`RolesPanel.tsx`, `const ROLES`). `knowledge`, `worker` and the plan `critic` sub-role have no card; set them in `config.yaml`. Review's card has `Show sub-roles` with the four lanes, each with a model and an `Effort` select (`Inherit`, or a level), and the `Review mode` select. The Flywheel card adds `Flywheel effort`, `Flywheel max agents` and `Flywheel scope`. There is no per-role harness control and no role-level effort control except Flywheel's.
- F-13. The model select groups options as `Inheritance` (sub-roles only: Parent), `Workhorse`, and specific models by provider (`RolesPanel.tsx`, search `optgroup label`).
- F-14. Settings saves automatically (autosave pipeline, `useAutosavePipeline` in `SettingsPage.tsx`). Saving writes the ref back to `config.yaml`, never the model a slot currently holds (`docs/MODEL_ROUTING.md`, "Tiered execution and roles.work").

### Which harness runs a model

- F-15. Harness resolution (`resolveHarness` in `src/lib/harness-resolve.ts`): an explicit pick wins (`pan start --harness`, `pan plan --harness`, a launch panel or model picker row that names a harness); else the provider default harness from Settings → Providers (`models.providers.<provider>.harness`); else the provider's built-in default. The `role` input is "INTENTIONALLY IGNORED" (comment in `resolveHarness`).
- F-16. `roles.<role>.harness` is validated on load but no pipeline spawn reads it (PAN-5518). Its only effect: the dashboard Plan dialog preselects `roles.plan.harness` (`PlanDialog.tsx`, search `defaultPlanningHarness`). The page must not tell users to set a per-role harness to route pipeline agents.
- F-17. Built-in provider defaults (`defaultHarness` in `src/lib/providers.ts`): Anthropic → `claude-code`; OpenAI → `codex`; Kimi → `kimi-code`; Google, MiniMax, Z.AI, MiMo, OpenRouter, Nous, DashScope, xAI, Groq, Cerebras, Mistral → `pi`; Ollama → `claude-code`. Link to `/configuration/harnesses` for the full list rather than copying every provider.
- F-18. Settings → Providers shows, per provider, `Default harness` with `Default (<built-in>)` plus the allowed harnesses (`ProviderManagementSection.tsx`). The toggle `Show all harness/model permutations` (off by default) makes model pickers show explicit harness and model combinations instead of only each provider's default harness.
- F-19. The YAML shape written by Settings is:
  ```yaml
  models:
    providers:
      openai:
        enabled: true
        harness: codex
  ```
  (`providerConfigForSave` in `src/lib/settings-api.ts`; read by `applyProviderHarness` in `src/lib/config-yaml/merge.ts`). A disabled provider does not reroute a role: the agent still launches on the configured model, and `pan doctor` flags a crew model or `roles.work.model` whose provider is not enabled (`docs/CONFIGURATION.md`, "When Providers are Disabled").
- F-20. If the chosen harness is denied by policy for the model, an explicit pick fails loudly; a provider-default pick falls back to `claude-code` only for models native to it, and otherwise fails (`resolveHarness`, comments "PAN-1871").

### Tiered execution

- F-21. Off by default (`DEFAULT_TIERED_EXECUTION_CONFIG.enabled: false`, `src/lib/agents/tier-table.ts`). Turn it on with `tiered_execution.enabled: true` or the Settings switch `Route work by difficulty`. Per issue, a plan can set `plan.metadata.tiered_execution: on | off`, which wins over the global switch; any other value is an error (`resolveTieredExecutionEnabled`). There is no CLI flag; the dashboard per-issue toggle in the plan card is broken (PAN-5517) and must not be documented.
- F-22. Example block (adapted from `docs/MODEL_ROUTING.md`; tier names are free text):
  ```yaml
  workhorses: { expensive: claude-opus-5-5, mid: claude-opus-5-5, cheap: claude-haiku-5-5 }
  tiered_execution:
    enabled: true
    tiers:
      trivial:       { model: workhorse:cheap,     harness: claude-code, difficulties: [trivial] }
      simple-medium: { model: workhorse:mid,       harness: claude-code, difficulties: [simple, medium], effort: high }
      complex:       { model: workhorse:expensive, harness: claude-code, difficulties: [complex, expert], effort: high }
    supervisor: { model: workhorse:expensive, harness: claude-code, subscribe: flagged }
  ```
- F-23. Validation (`validateTieredExecutionConfig`, `tier-table.ts`): each of the five difficulties `trivial`, `simple`, `medium`, `complex`, `expert` maps to exactly one tier; a `supervisor` is required once tiers exist; `by_kind` keys must be item kinds (`docs`, `api`, `backend`, `frontend`, `infra`, `test`, `refactor`, `design`, `spike`) and values existing tier names; a `distribution` replaces `model`/`harness` and its integer weights must total exactly 100. A Settings save refuses an invalid block. At config load an invalid block does not stop Overdeck: tiered staffing is turned off, a warning is logged ("tiered_execution is INVALID — tiered staffing disabled until fixed", `merge.ts`), and `pan doctor` shows "tiered_execution is invalid and has been disabled" (`src/cli/commands/doctor-tier-fitness.ts`). Workhorse refs to undefined slots are invalid the same way.
- F-24. Tier resolution for one item (`resolveTier` in `src/lib/agents/resolve-tier.ts`): a `by_kind` match for the item's `kind` first, then the item's `difficulty`. An item that matches neither falls through to `roles.work` (`resolveStaffing` in `src/lib/agents/staffing.ts`, the `catch` that calls `resolveImplicitStaffing`). The harness comes from the tier (or the distribution entry), not from the provider default.
- F-25. Who runs: in the normal pipeline one work agent runs the whole plan, staffed at the tier of the hardest item still open (`selectStaffingItem` / `selectHardestItem` in `src/lib/agents/spawn-prep.ts`). In swarm mode each item runs in its own slot agent staffed at that item's tier (`resolveSlotTierSpawnParams`, `src/lib/agents/spawn.ts`). `pan start --model` skips tier selection (F-8).
- F-26. Effort: a tier's `effort` sits in the precedence chain below item and plan effort and above sub-role and role effort (`resolveEffort` in `src/lib/agents/resolve-effort.ts`; table in `configuration/effort.mdx`, "Where effort comes from"). Link, do not copy the table.
- F-27. Supervisor (`Standing reviewer` in Settings): a review-only agent, configured with `model`, `harness` and `subscribe`. It runs only in swarm mode, after a slot's work merges (`fireTieredCommitHooks` in `src/lib/cloister/swarm-tiered-hooks.ts`, called from `src/lib/cloister/deacon-swarm.ts`). `subscribe`: `all` reviews every item; `flagged` reviews items with `metadata.requiresInspection: true`; `sampled` reviews a fixed 25% of items chosen by a hash of the item id (`DEFAULT_SUPERVISOR_SAMPLE_RATE` in `src/lib/agents/tier-supervisor.ts`). Its block verdict has no effect today (PAN-5517), so the page says the supervisor reviews and reports, and must not say it halts or blocks work.
- F-28. Commit feed (swarm mode only): after a slot merges, every live slot agent gets a read-only message with the item title and the diff (`src/lib/agents/tier-feed.ts`). `feed.exclude` drops matching paths from the diff; `feed.max_diff_bytes` (default none) swaps an oversized diff for a `--stat` summary.
- F-29. Fitness warnings (`src/lib/agents/tier-fitness.ts`): `underpowered` (the model's capability class is below what the tier's hardest difficulty needs: `expert` needs a frontier-class model, `medium` and `complex` a workhorse-class one), `overpowered` (a frontier model on a tier that only owns easy difficulties), `unknown-model`, `provider-not-enabled`, `supervisor-underpowered`. They show in `pan doctor`, as badges in Settings → Tiered Execution, and as a spawn log line. They warn; they do not block.
- F-30. `pan admin config tiers` prints `roles.work → <model>`, whether tiering is enabled (or invalid with the reason), one line per tier with its resolved model, harness and difficulties, `[overrides roles.work]` where the tier launches a different model than `roles.work`, and the note "Planned issues take their tier's model, not roles.work." (`src/cli/commands/config-tiers.ts`; live output verified 2026-11-18).
- F-31. Settings → Tiered Execution, in order (`TieredExecutionSection.tsx`): `Route work by difficulty` switch; an invalid-config banner when the block is invalid; `Who handles each difficulty?` (one crew per difficulty); `The crews` with `+ Add crew`; `Standing reviewer` (Model, Harness, Reviews: all, flagged, sampled); `Kind overrides`; `Advanced` with `Commit feed`, `Escalation` and `Session replay`; `What this writes to config.yaml`. A crew is labelled with its model name, `<slot> → <model>` for a workhorse ref, or `N-model mix` for a distribution. On save each crew becomes one tier named after its difficulties joined by hyphens, for example `simple-medium` (`tiered-crews.ts`, `deriveTierName`).
- F-32. Saved but not acted on today (verified in code during planning; tracked in PAN-5517 and PAN-4512). The page lists these once, in one short subsection, and links the two issues:
  - `escalation.*` (`enabled`, `retries_at_tier`, `max_promotions`, `effort_first`): `decideEscalation` has no caller (PAN-4512).
  - `replay_threshold` and `compaction_reroute` (Session replay): the replay code was deleted in PAN-3917.
  - `feed.callouts` `notify` and `corroborate`: the call-out endpoint has no server handler.
  - The supervisor's block verdict (F-27).

### Presets and effort

- F-33. A preset writes explicit values into `config.yaml` once (workhorse slots, roles, review lanes, effort, existing tiers' model/harness/effort, conversation and background models); it never turns tiered execution on or off and never creates tiers. Apply it from Settings → Model Routing or `pan models preset list | show | apply | undo` (`configuration/model-presets.mdx`, `pan models preset --help`). Every effort a preset sets is `high`. Link `/configuration/model-presets`; do not copy its tables.
- F-34. Effort levels are `low`, `medium`, `high`, `xhigh`, `max`; the default is `high` (`packages/contracts/src/effort.ts`). Link `/configuration/effort` for the precedence chain.

### Removed routing (for the replacement sections)

- F-35. There is no complexity or keyword routing, no automatic model selection by task type or budget, and no `model_selection` / `complexity_routing` block. The work-type router and `models.overrides` were removed in PAN-1048 (`docs/MODEL_ROUTING.md` banner; `docs/CONFIGURATION.md`, "Removed: Presets, Work-Type Overrides, Thinking Levels"). A config that still has `models.overrides` loads, logs one warning, and ignores it.
- F-36. Conversations are not pipeline roles: a new conversation uses `models.default_conversation_model` unless you pick a model when you start it; background AI calls (titles, compaction, memory extraction) have their own settings in Settings → Background AI (`docs/MODEL-CALLS.md`, part B). The page mentions this in one or two sentences and does not document those settings.
