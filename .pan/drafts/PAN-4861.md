# PAN-4861: Removing a managed SSH machine stops its dashboard, but the `pan up` supervisor restarts it

**Issue:** https://github.com/eltmon/overdeck/issues/4861
**Found by:** the Overdeck Anywhere release acceptance run (#4774, AC-6), on a Fly VM reached as `ssh://root@127.0.0.1:10022`.
**Supersedes:** the "only the dashboard process is signalled" sentence of D-4404-8 (`.pan/drafts/PAN-4404.md`, which stays as history).

## Glossary

- **SSH helper:** `pan machines ssh-helper start|stop --linker <uuid> --json`. It runs on the SSH host, started over SSH by the linking dashboard. Code: `src/lib/anywhere/ssh/helper.ts`. CLI wiring: `src/cli/commands/machines-ssh.ts` (`runHelper`, which calls `defaultHelperDeps(cliVersion(command))`).
- **Linker:** the environment id (lowercase UUID) of the linking dashboard. It is passed as `--linker`.
- **Launch marker:** `${OVERDECK_HOME}/ssh-launch/server.json` (mode 0600) on the host: `{ v: 1, pid, apiPort, version, startedAt, startedBy }`. The helper writes it only after it ran `pan up` itself. `startedBy` is the linker.
- **`managed` / `external`:** a start result. `managed` means the marker names this linker and the pid that `/api/health` reports. Anything else is `external`.
- **Stop case 5:** the last branch of `stopLocked` in `helper.ts`. The marker names this linker and the live health pid, and no other machine holds an active inbound link. Today it sends `SIGTERM` (then `SIGKILL` after 10 s) to the dashboard pid only. Cases 1–4 return `not-running`, `external`, `restarted` and `in-use` without signalling anything.
- **Supervisor:** the small watchdog process `dist/supervisor/server.js` (`src/supervisor/server.ts`). It listens on `127.0.0.1:<dashboardApiPort + 1>` (`getSupervisorPort()` in `src/lib/supervisor.ts`, default 3012). It polls `/api/health` every 10 s and runs `pan restart --dashboard` after 3 consecutive failures (`src/supervisor/watchdog.ts`). It has no "stopped on purpose" state.
- **Supervisor run modes** (`startSupervisorSidecar` in `src/cli/up-sidecars.ts`):
  1. the systemd user unit `overdeck-supervisor.service` (`startSupervisorUnitIfAvailable`, `src/lib/systemd.ts`), only for the canonical home (`supervisorUnitAllowed()`);
  2. on macOS, the launchd agent `ai.overdeck.supervisor`, which only `pan connect` loads (`src/lib/launchd.ts`). `pan up` never loads it;
  3. otherwise a plain detached process whose pid is in `${OVERDECK_HOME}/supervisor.pid` (`startSupervisorProcess`, `src/lib/supervisor.ts`).
- **`pan down` supervisor stop:** `src/cli/index.ts`, the `down` action: `if (await stopSupervisorUnitIfActive()) … else if (isSupervisorRunning()) stopSupervisorProcess();`.

## Problem

Removing an SSH machine whose server Overdeck started (`launch: managed`, "Leave the server running" unchecked) does not leave the server stopped. The remove dialog says "Removing this machine stops that server." The helper sends `SIGTERM` to the dashboard pid. But `pan up` also started the supervisor, and the supervisor restarts the dashboard within about 30 s (3 failed polls × 10 s). The helper has already deleted the launch marker, so the restarted server is `external` from then on, and no later remove stops it.

Evidence (2026-11-02, Fly VM): link `811d32dbd41258` was added `online` with `ssh.launch: managed`. The VM ran `dashboard/server.js` (pid 1856) and `supervisor/server.js` (1984). After Remove, pid 1856 exited. About 30 s later, `supervisor/server.js` (1984) still ran, a new `dashboard/server.js` (pid 2639) answered `/api/health`, and `/root/.overdeck/ssh-launch/` was empty.

### Root cause (verified)

`src/lib/anywhere/ssh/helper.ts`, module header lines 18–20:

```ts
 * - **Stop** (D-4404-8): signal the dashboard only when the marker still proves
 *   this linker started it and no other machine holds an active link to it.
 *   Sidecars that `pan up` started are left running; `pan down` is not used.
```

`stopLocked` (search for `deps.kill(healthPid, 'SIGTERM');`) signals only `healthPid`. The supervisor is not a passive sidecar. It owns the dashboard's lifecycle and restarts it.

## Decisions

- **D-4861-1 Stop the supervisor before the dashboard, in stop case 5 only.** Case 5 is reachable only when this linker's helper ran `pan up` itself: the marker is written only on that path, and `in-use` already protects other machines' links. So any supervisor alive at case 5 has one job left, which is to restart the dashboard we are about to stop. The helper stops it the way `pan down` does (the systemd user unit when it is active, else the `supervisor.pid` process), then signals the dashboard. Cases 1–4 never touch the supervisor.
- **D-4861-2 No provenance field in the marker.** The helper does not record which supervisor it started. Reason: a provenance rule leaves the dashboard restarting whenever the supervisor was already running at start (for example a `pan connect` host whose unit was active while its dashboard had crashed), and it cannot help markers written before this fix. The marker schema stays `{ v: 1, pid, apiPort, version, startedAt, startedBy }`. Counter-case, accepted and documented: on a host where `pan connect` enabled `overdeck-supervisor.service`, a managed remove stops that unit. The unit stays enabled, so it starts again at the next boot.
- **D-4861-3 Verify that the supervisor is gone before signalling the dashboard.** After the stop, the helper polls `GET http://127.0.0.1:<supervisorPort>/health` every 250 ms for up to 3 s. If a supervisor still answers (`200` with JSON `ok: true`), the helper does not signal the dashboard and answers `stop-failed`. Its message names the port and the launchd agent. The marker is kept, so the server stays `managed`. This one mechanism-agnostic check covers the launchd agent (KeepAlive respawns it, and the helper never boots it out) and any stop that failed. A port answer that is not `ok: true` (some other program on that port) does not count as a supervisor.
- **D-4861-4 No supervisor HTTP stop route, no `pan down`.** A new stop route on the supervisor would add an unauthenticated loopback surface for no gain. `pan down` also stops smee, Traefik and the dashboard by port, which this linker did not start; the D-4404-8 objection to it stands.
- **D-4861-5 No helper protocol change.** `SSH_HELPER_PROTOCOL` stays `1`. `HelperStopReason` (`'stopped' | 'not-running' | 'external' | 'restarted' | 'in-use'`, mirrored by `STOP_REASONS` in `src/lib/anywhere/ssh/target.ts`) does not grow. A supervisor that cannot be stopped is reported through the existing `stop-failed` error code, which the linking side already maps to removal reason `stop-failed` (`stopRemoteServer` in `src/dashboard/server/services/ssh-machine-service.ts`).
- **D-4861-6 The stop timeout grows from 45 s to 60 s.** The worst-case stop path becomes: lock wait 30 s + health 2 s + machines list + supervisor stop (≤ 3 s systemctl, or ≤ 2 s for the process) + supervisor probe ≤ 3 s + dashboard grace 10 s ≈ 50 s. `HELPER_STOP_TIMEOUT_MS` in `ssh-machine-service.ts` changes from `45_000` to `60_000`.
- **D-4861-7 The sync stop is allowed here.** `stopSupervisorProcess()` is synchronous (`Atomics.wait`, up to 2 s). The helper runs only from the `pan machines ssh-helper` CLI process (`src/cli/commands/machines-ssh.ts`), never from the dashboard server, so the "no sync calls in server-reachable code" rule does not apply. Do not create an async twin of `stopSupervisorProcess` (the façade ratchet, `npm run lint:effect-facades`, forbids twins without a documented reason).

## Requirements

- **FR-1** In stop case 5, the helper stops the host's supervisor before it sends any signal to the dashboard pid.
- **FR-2** The supervisor stop mirrors `pan down`: `stopSupervisorUnitIfActive()` first; when that returns `false`, `stopSupervisorProcess()`.
- **FR-3** After the supervisor stop, the helper confirms that nothing answers `GET /health` with `ok: true` on the supervisor port within 3 s. If something still answers, the helper answers `{ ok: false, error: 'stop-failed' }`, never signals the dashboard, and keeps the launch marker.
- **FR-4** Stop cases 1–4 (`not-running`, `external`, `restarted`, `in-use`) and machines-list failures never call the supervisor stop.
- **FR-5** With no supervisor running, case 5 behaves exactly as before: `SIGTERM`, `SIGKILL` after 10 s when still alive, marker deleted, `{ stopped: true, reason: 'stopped' }`.
- **FR-6** The linking side waits up to 60 s for `ssh-helper stop` (`HELPER_STOP_TIMEOUT_MS = 60_000`).
- **FR-7** The docs describe the new stop rule: removal stops the dashboard and the supervisor that would restart it; other sidecars (CLIProxy, Traefik, smee) keep running; a supervisor that cannot be stopped leaves the server running.
- **NFR-1** Helper tests use fake timers and in-memory dependencies only. No real process, port or file is touched. (Repo rule: retry, back-off and delay tests use `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()`, never real `setTimeout` waits.)
- **NFR-2** `helper.ts` stays under the file-size ceiling. It is 436 lines today; the ceiling is 1000 (`scripts/lint-file-size.sh`). No allowlist change.
- **NFR-3** No new import cycle. `npm run lint:circular` stays green after `helper.ts` imports `../../supervisor.js` and `../../systemd.js`.

### WI-1 Supervisor stop in the SSH helper (FR-1, FR-2, FR-3, FR-4, FR-5, NFR-2, NFR-3)

**Files:** `src/lib/anywhere/ssh/helper.ts`.

1. Add two fields to `HelperDeps`:

   ```ts
   /** The host's supervisor port (dashboard API port + 1). */
   supervisorPort: number;
   /**
    * Stop the host's supervisor the way `pan down` does: the systemd user unit
    * when it is active, else the process in `${OVERDECK_HOME}/supervisor.pid`.
    */
   stopSupervisor(): Promise<void>;
   ```

2. Add the default and wire it in `defaultHelperDeps`:

   ```ts
   import { getSupervisorPort, stopSupervisorProcess } from '../../supervisor.js';
   import { stopSupervisorUnitIfActive } from '../../systemd.js';

   /** D-4861-1: the same supervisor stop as `pan down`. The helper runs only in the CLI, so the sync process stop is allowed (D-4861-7). */
   async function stopSupervisorDefault(): Promise<void> {
     if (await stopSupervisorUnitIfActive()) return;
     stopSupervisorProcess();
   }
   ```

   In `defaultHelperDeps`, add `supervisorPort: getSupervisorPort(),` and `stopSupervisor: stopSupervisorDefault,`. `stopSupervisorProcess()` is already a no-op (it only clears a stale pidfile) when no supervisor process runs.

3. Add the constant and probe next to the other stop constants (search for `export const STOP_POLL_MS = 250;`):

   ```ts
   export const SUPERVISOR_STOP_WAIT_MS = 3_000;
   ```

   ```ts
   /** True when a supervisor answers `GET /health` with `ok: true` on the supervisor port. */
   async function supervisorAnswers(deps: HelperDeps): Promise<boolean> {
     try {
       const response = await deps.fetch(`http://127.0.0.1:${deps.supervisorPort}/health`, {
         signal: AbortSignal.timeout(HEALTH_REQUEST_TIMEOUT_MS),
       });
       const body = (await response.json().catch(() => null)) as { ok?: unknown } | null;
       return response.ok && body?.ok === true;
     } catch {
       return false;
     }
   }
   ```

4. In `stopLocked`, insert the supervisor stop between the `in-use` check and the dashboard `SIGTERM`.

   Before:

   ```ts
     if (others) return stopped(false, 'in-use');

     try {
       deps.kill(healthPid, 'SIGTERM');
   ```

   After:

   ```ts
     if (others) return stopped(false, 'in-use');

     // D-4861-1: the supervisor restarts a dashboard it watches, so it goes first.
     try {
       await deps.stopSupervisor();
     } catch (error) {
       return failure('stop-failed', `Could not stop the supervisor on this host: ${(error as Error).message}`);
     }
     const supervisorDeadline = deps.now() + SUPERVISOR_STOP_WAIT_MS;
     while ((await supervisorAnswers(deps)) && deps.now() < supervisorDeadline) await sleep(STOP_POLL_MS);
     if (await supervisorAnswers(deps)) {
       return failure(
         'stop-failed',
         `A supervisor still answers on port ${deps.supervisorPort} (on a Mac, the launchd agent ai.overdeck.supervisor that pan connect loads). It would restart the dashboard, so the server was left running.`,
       );
     }

     try {
       deps.kill(healthPid, 'SIGTERM');
   ```

   The rest of case 5 is unchanged.

5. Update the module header bullet (lines 18–20) to:

   ```ts
    * - **Stop** (D-4404-8, D-4861-1): when the marker still proves this linker
    *   started the dashboard and no other machine holds an active link to it,
    *   stop the supervisor first (the systemd unit or the supervisor.pid
    *   process, as `pan down` does), confirm nothing answers on its port, then
    *   signal the dashboard. Other sidecars that `pan up` started are left

   ```

## Acceptance criteria

- **AC-1 (WI-1, WI-2)** Given a managed marker for this linker and a running, stoppable supervisor that restarts the dashboard 30 s after it dies, when `runHelperStop` runs, then it returns `{ stopped: true, reason: 'stopped' }`, `stopSupervisor` is invoked before `kill`, and after advancing fake time by 60 s `/api/health` still answers nothing.
- **AC-2 (WI-1, WI-2)** Given a supervisor that still answers `ok: true` after the stop, when `runHelperStop` runs, then it returns `{ ok: false, error: 'stop-failed' }` with a message naming the supervisor port, never calls `kill`, and the marker file still exists.
- **AC-3 (WI-1, WI-2)** Given stop cases 1–4 or a failed machines list, when `runHelperStop` runs, then `stopSupervisor` is never called.
- **AC-4 (WI-1, WI-2)** Given no supervisor, when case 5 runs, then the kill calls are exactly `[[4242, 'SIGTERM']]` when the dashboard exits, and `[[4242, 'SIGTERM'], [4242, 'SIGKILL']]` when it is still alive after 10 s.
- **AC-5 (WI-1)** `defaultHelperDeps` returns `supervisorPort` equal to `getSupervisorPort()` and a `stopSupervisor` that calls `stopSupervisorUnitIfActive()` and, only when that returns `false`, `stopSupervisorProcess()`; `npm run typecheck` and `npm run lint:circular` pass.
- **AC-6 (WI-3)** `HELPER_STOP_TIMEOUT_MS` is `60_000` and the service test asserts the stop SSH call's `timeoutMs` is `60_000`.
- **AC-7 (WI-4)** `docs/ANYWHERE-ARCHITECTURE.md` names D-4861-1 and says the supervisor is stopped before the dashboard and that an unstoppable supervisor leaves the server running with `stop-failed`; `configuration/linked-machines.mdx` no longer contains "Removal stops only the dashboard process" and says the supervisor is stopped with the dashboard; `npm run lint:docs` passes.

## Non-goals

- No change to the supervisor (`src/supervisor/*`) beyond the header comment: no stop route, no "stopped on purpose" state in the watchdog.
- No change to the start path, the launch marker schema, or `SSH_HELPER_PROTOCOL`.
- No new `HelperStopReason` and no frontend change. The remove dialog and the linking side keep their current texts; surfacing `stop-failed` to the operator in the UI is not part of this issue.
- The helper never boots out the launchd agent and never disables (`systemctl disable`) the systemd unit.
- No change to `pan down`, and no stop of CLIProxy, Traefik, smee or review sessions.
- No handling of a detached `pan restart --dashboard` that a supervisor spawned before it was stopped (the supervisor only spawns one after ≥ 3 failed polls, and case 5 runs against a healthy dashboard).
- No live end-to-end SSH smoke of the managed path; `scripts/anywhere/ssh-machine-smoke.mjs` stays as is (its docs say the managed path is covered by helper unit tests).

## Notes for review

- A `stop-failed` remove still deletes the linking-side record and stops the forward, so the host stays `managed` with a marker for this linker. Re-adding the machine finds that marker and reports `managed` again, so the next remove retries the stop. This is a consistent recovery path, not an orphaned marker.
- Nothing in the dashboard restarts the supervisor between its stop and the dashboard kill: `startSupervisorProcess` is called only from CLI paths (`src/cli/up-sidecars.ts`, `src/cli/commands/connect.ts`, `src/cli/commands/dev.ts`).
