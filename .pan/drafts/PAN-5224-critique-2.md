## blocks-the-design: Webhook refresh reads the stale listing

WI-3 and WI-6 invalidate the open/closed promise caches and then schedule a derived-state refresh (`.pan/drafts/PAN-5224.md:194-197,292-295`). But `IssueDataService.refreshDerivedStates` calls the dashboard adapter (`src/dashboard/server/services/issue-data-service.ts:984-989`), whose default is `listRepoPullRequestsStaleOk` (`src/dashboard/server/services/derived-issue-state.ts:103-116`). That function starts a fresh read but immediately returns `lastRepoPullRequests` while its `settledAt` is under two minutes old (`src/lib/overdeck/pr-listing.ts:25,282-289`). `invalidateRepoPullRequests` does not clear that map (`src/lib/overdeck/pr-listing.ts:241-245`). A webhook arriving just after a successful read therefore causes the new derived refresh to write the old PR state. WI-13's run counter cannot help because the later run itself receives the stale rows. Make event invalidation also invalidate the stale-while-revalidate answer, guard against an old in-flight read repopulating it, and test the derived-state path with a prepopulated last listing.

## blocks-the-design: Uncovered repos exceed the stated fallback

NFR-2 and D-1 promise a five-minute bound for repos without webhook coverage (`.pan/drafts/PAN-5224.md:78,87`), and WI-11 would publish that bound (`:445`). Yet FR-1 and WI-3 cache an empty open listing for 15 minutes while the global relay is healthy (`:65,194-204`); a newly opened PR in an uncovered repo sends no invalidation. FR-4 separately makes GitHub-tracked membership wait for a 30-minute age threshold (`:68,351-366`), with the five-minute convergence tick adding possible delay. The plan's own mechanisms allow a new PR to remain absent from derived state for 15 minutes and from membership longer. Either provide a per-repo refresh path that meets the five-minute requirement and rework the quota model, or change NFR-2, D-1, the PR-body language and docs to state the actual bounds.

## blocks-the-design: Tracker diff reads projected state

WI-10 seeds and diffs `issueService.getIssues({ cycle: 'all' })` as if it were raw tracker data (`.pan/drafts/PAN-5224.md:375-396`). `computeIssues` applies derived state even for `cycle: 'all'` and replaces `state` with `verifying_on_main` when a PR is merged and the tracker issue is neither done nor canceled (`src/dashboard/server/services/issue-data-service.ts:491-515`). Thus a later tracker poll changing that issue from `in_progress` to `in_review` yields the same fingerprint, so FR-5's required membership refresh is missed. The same projection can also create a false tracker change after a derived refresh. Seed and diff the raw tracker rows already collected by `getCachedTrackerIssues` (`src/dashboard/server/services/issue-data-service.ts:908-915`), through a read-only accessor or equivalent, while observing that file's size cap.

## sharpens-framing: Ten seconds is not a proven delivery bound

NFR-2 promises that a covered repo's PR, review or check change reaches derived state within ten seconds (`.pan/drafts/PAN-5224.md:78`), but D-7 budgets about one second for the read (`:93`). The open PR read itself allows 20 seconds (`src/lib/overdeck/pr-listing.ts:167-169`), before the derived loader and any queued work finish. WI-6 tests only coalescer spacing (`.pan/drafts/PAN-5224.md:300-304`), not end-to-end delivery. Narrow NFR-2 to a measurable scheduling or normal-case objective, or specify the timeout and end-to-end test that enforce a ten-second deadline.
