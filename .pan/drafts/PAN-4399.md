# PAN-4399 — Post-planning auto-spawn must never fail silently

**Issue:** [PAN-4399](https://github.com/eltmon/overdeck/issues/4399)
**Planning mode:** `pan plan --auto` (decisions below are recorded as autoDecisions, no operator Q&A)

## Glossary

- **Auto-start / auto-handoff** — planning launched with `--auto-start` finalizes and immediately asks the dashboard to start the work agent. Code: `completePlanningAutoSpawn` in `src/lib/overdeck/planning-promotion.ts`.
- **Deferred hand-off (PAN-4155)** — when the auto-start is refused, complete-planning journals `handoff.deferred` in the workspace pipeline journal and deacon-lite's `retryDeferredHandoffs` (`src/lib/cloister/deferred-handoff.ts`) retries the spawn on a backoff (2, 4, 8, 16, then every 20 min) for up to 2 hours (`DEFERRED_HANDOFF_WINDOW_MS`). Today only guardrail refusals are deferred.
- **Pipeline journal** — `<workspace>/.overdeck/pipeline.jsonl`, append-only, written at the moment of an action (`src/lib/cloister/pipeline-journal.ts`). Handoff entry types already exist: `handoff.deferred | handoff.retried | handoff.started | handoff.abandoned`. `data` is `Record<string, unknown>`, so new reasons need no type change.
- **Stack gate** — the workspace docker-stack health check in `POST /api/agents` (`src/dashboard/server/routes/agents/spawn.ts`, "stackHealthGate"). When unhealthy it runs one in-process rebuild via `assertWorkspaceStackHealthyForSpawn` (`src/lib/agents/spawn-prep.ts`), bounded by `SPAWN_STACK_REBUILD_MAX_ATTEMPTS = 3` and `SPAWN_STACK_REBUILD_COOLDOWN_MS = 15 min`, then answers **422** with `stackHealth` in the body.
- **Rebuild-and-start** — `POST /api/workspaces/:issueId/rebuild-and-start` (`src/dashboard/server/routes/workspaces.ts`, search `postWorkspaceRebuildAndStartRoute`). It spawns a detached `pan workspace rebuild <id> && pan start <id>` and returns `{ success: true, activityId }` **before either command has run**.
- **Derived issue state** — `deriveIssueState(facts)` in `src/lib/overdeck/derived-issue-state.ts`, vocabulary in `packages/contracts/src/derived-issue-state.ts`. `state` is one of nine states; `attention` is an orthogonal operator signal (`needs-you | stuck | api-error`).
- **Work agent started** — the agent state row `agent-<issue-lower>` exists with a `startedAt`. Per CLAUDE.md, agent state is written only after the terminal-backend session exists, so absence means the agent never came up.
- **Grace window** — `WORK_START_GRACE_MS = 10 * 60_000`. Time after a journaled `handoff.started` within which a missing work agent is still considered "starting" (the container wait alone can take 3 min, `maxWaitMs` in `spawn-helpers.ts`).

## Problem (verified)

On 2026-09-29, [PAN-4370](https://github.com/eltmon/overdeck/issues/4370) and [PAN-4384](https://github.com/eltmon/overdeck/issues/4384) sat 7–9 hours shown as "working" with no work agent. The evidence from `~/.overdeck/logs/dashboard.log` for PAN-4384:

```
[complete-planning] CALLED for PAN-4384 (skipKill=false, autoSpawn=true)
[agents] Workspace stack for PAN-4384 unhealthy (No Docker containers found for workspace stack pan-4384) — rebuilding before spawn (attempt 1/3)
[agents] Workspace stack rebuild failed for PAN-4384: Command failed: docker compose ... up -d --build
 Network overdeck-feature-pan-4384_default Error Error response from daemon: all predefined address pools have been fully subnetted
[complete-planning] Marked planning-pan-4384 as stopped (hasLiveTmuxSession=false)
```

There is **no** `[complete-planning] ... auto-handoff failed` line, and the activity store holds exactly `Rebuild & start for PAN-4384 started` then `Rebuild & start for PAN-4384 failed`. Three defects combine:

1. **D1 — fire-and-forget recovery reported as success.** `completePlanningAutoSpawn` (planning-promotion.ts, search `if (skipReason === 'stack-unhealthy')`, ~line 524) posts rebuild-and-start and, on its immediate 200, returns `{ workAgentSpawned: true }`. The detached rebuild then fails; `spawnPanCommand`'s `finalize` emits one activity error and nothing journals or retries.
2. **D2 — stack-unhealthy never reaches the PAN-4155 retry.** `workAgentDeferred: true` is set only for `skipReason === 'guardrails' && body['guardrails']` (planning-promotion.ts ~line 555).
3. **D3 — the plan commit reads as work.** `deriveState` returns `'working'` when `facts.branch.aheadOfMain > 0` (derived-issue-state.ts ~line 177, `if (facts.branch && facts.branch.aheadOfMain > 0) return 'working';`). Finalize commits `chore(plan): complete planning for <ID>` on the feature branch, so an issue with no agent and no PR shows "Working" in Command Deck (`featureStateBadge.ts` `working: { label: 'Working', ... }`) and "Paused mid-work" in simple mode.

The docker network exhaustion itself is environmental and out of scope; this issue makes any such failure visible and retried.

## Decisions (made here, auto mode)

- **AD-1: Reuse PAN-4155, no second retry loop.** A stack-unhealthy auto-start refusal is journaled as `handoff.deferred` with `data.reason: 'stack-unhealthy'` and retried by the existing `retryDeferredHandoffs`. Each retry POSTs `/api/agents`, whose stack gate already runs the bounded in-process rebuild (`pan workspace rebuild` calls the same `rebuildWorkspaceStack`, verified: `src/cli/commands/workspace-rebuild.ts:19`).
- **AD-2: Drop the rebuild-and-start hop from the auto-start path.** Keeping it would race a detached `docker compose up --build` against deacon-lite's first retry at +2 min on the same compose project. The route itself stays (the dashboard's "Rebuild & start" button uses it).
- **AD-3: Consent survives the stack refusal.** Verified: the auto-start consent is claimed only by `pan start` (`src/cli/commands/start.ts:448`/`:1214` read `OVERDECK_AUTO_SPAWN_CONSENT_REQUIRED`); the 422 at the stack gate returns before `pan start` runs, so `readAutoSpawnOnFinalizeFlagAsync` still answers `granted` and the retry does not stand down.
- **AD-4: Journal `handoff.started` on every accepted auto-start.** complete-planning appends `handoff.started` (source `complete-planning`, `data.queued: true` when the response had `startingContainers`) so an acceptance that later dies in the background (container-wait timeout in `spawn-helpers.ts`, or anything else) is detectable. Such late failures are **surfaced, not retried** (see NonGoals).
- **AD-5: Additive attention, not a state-table reorder.** Add `IssueAttention` literal `"work-not-started"` and an optional `workStart` detail on `DerivedIssueState`. `state` precedence is unchanged; consumers override the "working" presentation from these fields. Changing the nine-state precedence would ripple into every consumer (lanes, action phases, simple mode).
- **AD-6: Journal-triggered only.** The derivation fires only when the workspace journal holds a `handoff.*` entry. Issues planned without auto-start (human-initiated planning) never journal a hand-off and keep today's behavior; that is the pickup gate's "planned ≠ startable" state.
- **AD-7: Surfaces.** Command Deck (row badge, Needs-you grouping, subline) and the Kanban/simple-mode Needs-you strip (which already has a "Start work" button posting `/api/agents`). God View is agent-scoped (`useConfluenceData.ts` iterates `agentsByIssue`), so it never showed these issues as working; it is unchanged.
- **AD-8: Keep the 2-hour window for stack failures.** With 3 bounded rebuilds landing at roughly 0 / ~18 / ~38 minutes, later retries only detect an operator fix. The "retrying" label keeps the issue visible meanwhile, and give-up raises Needs-you on the next derivation.

## Requirements

- **FR-1** — When the auto-start POST `/api/agents` answers stack-unhealthy (422 with `stackHealth`, or an error matching `/workspace docker stack/i`), complete-planning journals `handoff.deferred` with `data.reason: 'stack-unhealthy'` and returns `workAgentDeferred: true`; it never posts rebuild-and-start and never reports `workAgentSpawned: true` for that refusal.
- **FR-2** — Every deferral, retry-give-up entry, activity line and `planning.failed` payload carries the real reason (`guardrails` or `stack-unhealthy`); no stack failure is described as "spawn guardrails".
- **FR-3** — deacon-lite retries a `stack-unhealthy` deferral on the existing backoff; a successful retry appends `handoff.started` and the work agent starts without operator action.
- **FR-4** — On give-up (2 h window) a `stack-unhealthy` deferral writes `handoff.abandoned` (`outcome: 'gave-up'`, `skipReason: 'stack-unhealthy'`, `error`), `planning.failed` (`stage: 'auto-handoff'`), and a warn activity line naming `pan start <ID>`.
- **FR-5** — complete-planning and deacon-lite's `retryDeferredHandoffs` append `handoff.started` when the auto-start was accepted, stamping `data.requestedAt` with the time captured immediately before the spawn call (not the entry's own `at`, which is written only after `pan start` has already run to completion and recorded its own, earlier `startedAt`).
- **FR-6** — `deriveIssueState` reports `attention: 'work-not-started'` and `workStart: { status: 'not-started', error?, at }` when the issue is open, there is no PR, no live pane, no work agent started at/after the hand-off request (`data.requestedAt` on a `handoff.started` entry; the entry's own `at` for every other type), and the last `handoff.*` entry is `handoff.abandoned` with `outcome: 'gave-up'`, or `handoff.started` older than `WORK_START_GRACE_MS`.
- **FR-7** — `deriveIssueState` reports `workStart: { status: 'retrying', error?, nextRetryAt?, at, held? }` (no attention) when the last `handoff.*` entry is `handoff.deferred` or `handoff.retried` under the same no-PR / no-pane / no-started-agent conditions; `held: true` is set when that entry's `data.deaconPaused` is true (PAN-4210: the retry is journaled but not actually running while the Deacon is frozen).
- **FR-8** — Command Deck shows the badge "Work agent not started" (tone `human`) for FR-6, "Work start retrying" (tone `machine`) for an unheld FR-7, or "Work start held" (tone `machine`) for a `held` FR-7, instead of "Working"; FR-6 issues count as Needs-you and their subline names the error.
- **FR-9** — The Kanban/simple Needs-you strip lists FR-6 issues with the label "Work agent not started", the journaled error as the sentence, and a working "Start work" button.
- **FR-10** — `pan plan finalize` output and the complete-planning response message name the deferral reason (no "spawn guardrails" text for a stack deferral).
- **NFR-1** — Deferral/retry tests inject `now` (as the existing PAN-4155 tests do); any test that exercises a real `setTimeout`/`setInterval` uses `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()` (repo rule: fake timers for delay tests).
- **NFR-2** — The batch derivation adds at most one journal tail read and one agent-state file read per branch-only (no-PR) issue; no new git or forge calls (preserves PAN-3969's batched `for-each-ref`).
- **NFR-3** — `src/lib/overdeck/planning-promotion.ts` stays ≤ 1000 lines (`scripts/lint-file-size.sh` CEILING; its allowlist cap is 997 so any growth past 1000 fails). `derived-issue-state.ts` stays ≤ 1000. New derivation logic lives in a new module.
- **NFR-4** — New lib modules import `getAgentState` from `src/lib/agents/agent-state-read.js` (the leaf), never from `agents.js`, or `lint:circular` fails.

## NonGoals

- Spawning the work agent without the docker stack when plan items do not need it (the issue's "consider" bullet). `work` keeps its deliberate hard stack gate (PAN-1645 comment in `spawn-prep.ts`); deciding per-plan stack need is a separate design.
- Fixing docker address-pool exhaustion ("all predefined address pools have been fully subnetted").
- Retrying failures that happen after an accepted spawn (container-wait timeout, background `pan start` failure); they are surfaced by FR-6, not retried.
- Changing the nine-state precedence or `deriveState`.
- God View changes; the cockpit `NeedsYouSlot` kinds.
- Changing `DEFERRED_HANDOFF_WINDOW_MS`, the backoff, or `SPAWN_STACK_REBUILD_*` constants.
- Removing the `/api/workspaces/:id/rebuild-and-start` route or the dashboard "Rebuild & start" action.
- Showing Needs-you for planned issues that never had an auto-start (no journal entry).

## Hazards

- `lint:circular`: `work-start-state.ts` must import from `agent-state-read.js`, `workspaces/resolver.js` and `cloister/pipeline-journal.js` only; run `npm run lint` early.
- `getWorkspaceForIssue` opens the overdeck DB; in the batch loader call it only for no-PR issues and catch errors.
- Every stack-unhealthy retry makes the spawn route emit an `agent-spawn-blocked-stack-unhealthy` error activity; about 8 in 2 hours. Accepted noise; do not add suppression.
- `complete-planning.test.ts` asserts on the old rebuild-and-start request list; that test must be replaced, not kept green by re-adding the hop.

## Acceptance criteria

1. (WI-1) Given a `handoff.deferred` entry with `reason: 'stack-unhealthy'` and `now` past `nextRetryAt`, `retryDeferredHandoffs` POSTs through the spawn stub and appends `handoff.started` on success or `handoff.retried` carrying `reason: 'stack-unhealthy'` on refusal.
2. (WI-1) Past the 2-hour window the same deferral appends `handoff.abandoned` with `skipReason: 'stack-unhealthy'` and emits a warn activity containing `pan start`.
