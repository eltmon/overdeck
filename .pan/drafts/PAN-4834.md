# PAN-4834 — HTTP/1.1 and WebSocket clients over the secure channel, and the page shims

**Status:** draft · **Revision:** 1 (2026-11-03) · **Author:** Claude Opus 5.5 (planning agent, `pan plan --auto`)
**Issue:** [PAN-4834](https://github.com/eltmon/overdeck/issues/4834) · **Epic:** [PAN-4823](https://github.com/eltmon/overdeck/issues/4823), work item **W-WEB2** of `.pan/drafts/pan-4823.md` (acceptance **AC-6**, checkpoint **CP-2**)

**Downstream:** [PAN-4837](https://github.com/eltmon/overdeck/issues/4837) (W-APP1, the Capacitor app) calls `installChannelShims` from its `main.tsx`.
**Sequencing gate:** the epic says "do not start before the Anywhere acceptance run [PAN-4774](https://github.com/eltmon/overdeck/issues/4774) passes". PAN-4774 is CLOSED (verified 2026-11-03 with `gh issue view 4774`).

**Why this exists.** Inside a secure channel the machine speaks plain HTTP/1.1: `installChannelListener` hands every accepted channel to the dashboard's Node HTTP server as if it were a TCP socket. Machines reach each other with a Node `http.Agent` whose `createConnection` returns the channel. A browser WebView has no such hook: `fetch` and `WebSocket` cannot be pointed at a custom byte stream. The phone app therefore needs its own HTTP/1.1 client, its own RFC 6455 WebSocket client, and two page shims that send the existing frontend's `/api/*` and `/ws/*` traffic through the channel without changing that frontend.

## Glossary

- **Machine:** a computer running the Overdeck dashboard server (`pan up`).
- **Secure channel:** the Noise-authenticated, `@hyperswarm/secret-stream`-encrypted byte stream between the phone and a machine. On the phone it is `SecureChannel.stream` (a `streamx` `Duplex`) returned by `openSecureChannel` (`packages/anywhere-channel/src/secure-channel-web.ts`).
- **Channel stream:** the plaintext side of one secure channel. One channel carries one HTTP/1.1 connection (no multiplexer, `docs/ANYWHERE-ARCHITECTURE.md` "One session per connection").
- **Dial:** a function `() => Promise<ChannelStream>` that opens one fresh secure channel to one machine. In the app (PAN-4837) it is `createMachineDialer(...).dialMachine(env, { relay })` → `openSecureChannel(rtcDuplex, { mode: 'link', ... })` → `.stream`. In tests it is a `duplexPair()` plus `acceptRawChannel`.
- **Channel listener:** `src/dashboard/server/channel-listener.ts`, the machine side that runs the responder handshake and hands the channel to Node's HTTP server.
- **Pool:** the phone-side keep-alive pool of open channels to one machine (this issue).
- **Shims:** replacements for `globalThis.fetch` and `globalThis.WebSocket` that route machine URLs through the pool or a dedicated channel (this issue).
- **Phone token:** the `phone` access token a machine mints at `POST /api/phones/exchange` (PAN-4835, merged). The shims send it as `Authorization: Bearer <token>`.
- **Native shell:** the Capacitor app, recognised by `globalThis.__OVERDECK_NATIVE__ === true` (pan-4823 W-APP1 step 5).
- **CP-2:** pan-4823 implementation checkpoint "direct URL loads": elements whose URL the WebView loads itself (`<img src>`, `<a href>`, `EventSource`) bypass `fetch` and so bypass the channel.
- **Stale channel:** a pooled channel the machine already closed (its HTTP server closes an idle keep-alive connection after 5 s) but the pool has not noticed yet.

## Requirements

### Functional

- **FR-1 HTTP/1.1 over a channel.** The package serialises an HTTP/1.1 request onto a channel stream and parses the response: status line, headers, `Content-Length` bodies, `chunked` bodies, read-to-close bodies, and no body for `HEAD`, 204 and 304.
- **FR-2 Keep-alive pool.** Requests to one machine share a pool of at most 4 open channels, one request in flight per channel. A channel that idles for 4 s (or `N*1000-1000` ms for a smaller `Keep-Alive: timeout=N` hint) is closed. Requests beyond 4 in flight wait in FIFO order.
- **FR-3 Stale resend.** A `GET`, `HEAD` or `OPTIONS` that fails on a reused channel before any response byte arrives is resent once on a fresh channel, after the pool drops its idle channels. Other methods and responded requests are never resent.
- **FR-4 WebSocket over a channel.** A class with the browser `WebSocket` interface opens a dedicated channel, performs the RFC 6455 opening handshake (random key, checked `Sec-WebSocket-Accept`, optional subprotocol), then frames: masked client frames, text, binary, continuation, ping/pong, close. The server's close code and reason reach the `close` event.
- **FR-5 fetch shim.** `installChannelShims` replaces `fetch`. A URL that is relative, or has the page's protocol and host, and whose path starts with `/api/` or `/ws/`, goes to the current machine's pool with `Authorization: Bearer <phone token>`; the result is a real `Response`. Every other URL uses the original `fetch`.
- **FR-6 WebSocket shim.** `installChannelShims` replaces `WebSocket`. A URL that is relative, or has the page's host with scheme `ws:`, `wss:` or the page's own protocol, and whose path starts with `/api/` or `/ws/`, opens a channel WebSocket to the current machine; every other URL (for example the directory at `wss://connect.overdeck.ai`) uses the original constructor.
- **FR-7 Machine switching.** The shims read the current machine on every call (FR-10 of the epic), never once at install.
- **FR-8 CP-2.** In the native shell, chat attachment thumbnails and the image lightbox load their `/api/…` images through `fetch` into object URLs.

### Non-functional

- **NFR-1 Same runtime rules as the package.** No `node:*` import, no `require(`, no global `Buffer` in package source outside the existing exceptions; `Uint8Array` signatures; `b4a`, `TextEncoder`/`TextDecoder` at runtime.
- **NFR-2 Bounded parsing.** Response heads are capped at 64 KiB, response bodies and WebSocket messages at 32 MiB (the same as `LINK_FORWARD_MAX_BYTES`); exceeding a cap fails the request or the socket and destroys the channel.
- **NFR-3 Fake timers.** Tests of the idle timer, the close-handshake timeout and any delay use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()` (repo rule `fake-timers-for-retry-tests`). The integration test drives real streams and has no sleeps (pan-4823 NFR-8 exception).
- **NFR-4 Header hygiene.** Channel requests carry `Host: link.invalid` and never `Origin`, `Cookie`, or a caller-supplied `Host`, `Connection`, `Content-Length`, `Transfer-Encoding`, `Keep-Alive`, `Upgrade` or `Accept-Encoding`; the client sends `Accept-Encoding: identity` so the response is never compressed.
- **NFR-5 No token leaks.** The phone token is attached only to requests the routing rule sends to the channel; it is never sent to the original `fetch`/`WebSocket`.
- **NFR-6 Small modules.** Every new package file stays under 600 lines.

## Decisions

- **D-1 Five modules in the package, all exported from `./web`.** `http1.ts` (pure wire), `http-client.ts` (one request on a channel, and the pool), `ws-frames.ts` (pure RFC 6455 framing), `ws-client.ts` (`ChannelWebSocket`), `shims.ts` (`installChannelShims`). They are runtime-neutral, but the phone is their only consumer, so they live behind `./web` like the rest of the phone pieces. Only the shims item edits `web.ts` (one owner, no merge race).
- **D-2 The machine is a getter, and the token belongs to the machine.** The epic sketched `installChannelShims({ currentMachine, bearerToken })`. Each paired machine issues its own phone token, so the token is a field of the current machine: `installChannelShims({ currentMachine: () => ShimMachine | null })` with `ShimMachine = { environmentId, bearerToken, dial }`. The package stays transport-agnostic; PAN-4837 composes `dial` from `createMachineDialer` and `openSecureChannel`.
- **D-3 One pool per machine, kept by the shims.** The shims keep `Map<environmentId, ChannelPool>`. Switching machines leaves the old pool to idle out on its own timer. `uninstall()` closes every pool.
- **D-4 A WebSocket gets its own channel.** The upgrade consumes the HTTP connection, so `ChannelWebSocket` calls `dial()` itself and never borrows from the pool, and it does not count toward the pool's 4.
- **D-5 Normalise fetch input through `Request`.** For a string or `URL` input the shim builds `new Request('http://link.invalid' + pathAndQuery, init)`. For a `Request` input it uses `init ? new Request(input, init) : input` as is, and never passes a `Request` as the init dictionary of another `Request` (its stream body would need `duplex: 'half'`, which WebKit rejects). The normalised request's URL is never used; the path comes from `channelPathFor`. The shim then reads `method`, `headers` and `await request.arrayBuffer()`. This handles strings, `URL`, `Request`, `Headers`/array/record headers, `FormData` (multipart boundary in `content-type`), `Blob`, `URLSearchParams` and streams with the platform's own rules, and throws the same `TypeError` a native `fetch` would (for example a `GET` with a body). The fixed `http://link.invalid` base avoids custom-scheme `Request` quirks.
- **D-6 Bodies are buffered.** `request()` resolves with the whole body. No phone screen streams a response (Fact 13), and buffering keeps channel reuse simple. The shim wraps the body in `new Response(...)`, whose `.body.getReader()` still works.
- **D-7 SHA-1 from `@noble/hashes/legacy.js`, not the port.** `CryptoPort` stays as PAN-4833 defined it (three functions, golden-vectored). `ws-frames.ts` imports `sha1` from `@noble/hashes/legacy.js` directly; randomness (the key and masks) comes from a `CryptoPort` argument defaulting to `webCrypto`.
- **D-8 Browser semantics where the frontend can tell.** `binaryType` defaults to `'blob'` (the spec default; Effect reads a `Blob` with `.arrayBuffer()`), `'arraybuffer'` is supported. `send()` in `CONNECTING` throws `DOMException` `InvalidStateError`; after `CLOSING` it drops data silently. `close(code, reason)` accepts only 1000 or 3000–4999 (else `DOMException` `InvalidAccessError`) and a reason of at most 123 UTF-8 bytes (else `DOMException` `SyntaxError`). An abnormal end fires `error` and then `close` with code 1006 and `wasClean: false`. Constants `CONNECTING=0, OPEN=1, CLOSING=2, CLOSED=3` exist on the class and on instances.
- **D-9 Not supported (documented, not silent):** sending a `Blob` over a channel WebSocket throws `TypeError('Blob payloads are not supported over the channel')` (no caller sends one); `bufferedAmount` is always 0; `extensions` is always `''` and the client offers none; redirects are returned as-is (3xx `Response`), never followed; no request timeout beyond the caller's `AbortSignal`.
- **D-10 Abort destroys the channel.** An aborted in-flight request destroys its channel (its state is unknown) and rejects with `signal.reason` when it is an `Error`/`DOMException`, else `new DOMException('The operation was aborted.', 'AbortError')`. A queued request that is aborted leaves the queue.
- **D-11 Network failures look like browser network failures.** A channel failure seen through the fetch shim rejects with `new TypeError('Failed to fetch', { cause })`. With no current machine it rejects with `new TypeError('Failed to fetch', { cause: new Error('No machine is selected') })`, and a WebSocket fires `error` then `close` 1006.
- **D-12 CP-2 takes the primary path, gated on `isNativeShell()`.** A hook `useChannelMediaSrc(url)` fetches `/api/…` media into an object URL in the native shell and returns the URL unchanged elsewhere. When the fetch fails it returns the original URL, so the `<img>` fails to load and the existing `onError` path hides the thumbnail. This issue creates `src/dashboard/frontend/src/lib/nativeShell.ts` with the exact one-liner from pan-4823 W-APP1 step 5; PAN-4837 reuses it and must not redefine it.
- **D-13 Status text and null bodies.** The shim passes `statusText` from the status line, drops `transfer-encoding`, `connection` and `keep-alive` from the response headers (the body is already de-chunked), and uses a `null` body for 101, 103, 204, 205 and 304. Statuses outside 200–599 other than those reject with `TypeError('Failed to fetch')` because `Response` cannot represent them.

### WI-1 `http-wire` — HTTP/1.1 serialiser and response parser (pure)

- **What and why:** FR-1. The byte-level half of the HTTP client, testable without streams.
- **Files:** new `packages/anywhere-channel/src/http1.ts`; new `packages/anywhere-channel/src/__tests__/http1.test.ts`.
- **Steps:**
  1. Types:
     ```ts
     export type HeaderPairs = Array<[name: string, value: string]>;
     export interface HttpRequest { method: string; path: string; headers?: HeaderPairs | Record<string, string>; body?: Uint8Array }
     export interface HttpResponseHead { status: number; statusText: string; httpVersion: '1.0' | '1.1'; headers: HeaderPairs /* names lowercased, order kept */ }
     export interface HttpResponse extends HttpResponseHead { body: Uint8Array }
     export type HttpParseErrorCode = 'bad-status-line' | 'bad-header' | 'headers-too-large' | 'body-too-large' | 'bad-chunk' | 'truncated';
     export class HttpParseError extends Error { constructor(readonly code: HttpParseErrorCode, message: string) }
     export const CHANNEL_HOST = 'link.invalid';
     export const MAX_RESPONSE_HEAD_BYTES = 64 * 1024;
     export const MAX_RESPONSE_BODY_BYTES = 32 * 1024 * 1024;
     ```
  2. `serializeHead(method, path, headers: HeaderPairs): Uint8Array` — validates and writes `METHOD SP path SP HTTP/1.1 CRLF`, each `name: value CRLF`, then `CRLF`, UTF-8 via `TextEncoder`. Throws `TypeError` when `method` is not `/^[A-Z]+$/`, `path` does not start with `/` or contains a space, CR or LF, a header name is not an RFC 7230 token (`/^[!#$%&'*+.^_`|~0-9A-Za-z-]+$/`), or a value contains CR, LF or NUL.
  3. `serializeRequest(req: HttpRequest): Uint8Array` — header list = `Host: link.invalid`, `Connection: keep-alive`, `Accept-Encoding: identity`, then the caller's headers minus (case-insensitive) `host`, `connection`, `content-length`, `transfer-encoding`, `keep-alive`, `upgrade`, `accept-encoding`, `origin`, `cookie`, then `Content-Length: <n>` when `body` is present, or `Content-Length: 0` when the method is `POST`, `PUT`, `PATCH` or `DELETE` without a body. Returns head and body concatenated (`b4a.concat`).
  4. `class ResponseParser`, constructed with `{ method: string; maxHeadBytes?: number; maxBodyBytes?: number }`:
     - `push(chunk: Uint8Array): ParseStep` where `ParseStep = { state: 'more' } | { state: 'done'; response: HttpResponse; keepAlive: boolean; keepAliveTimeoutMs: number | null; leftover: Uint8Array }`. Bytes after a completed response are returned in `leftover`, never dropped.
     - `end(): ParseStep` — the stream ended: completes a read-to-close body (`keepAlive: false`), otherwise throws `HttpParseError('truncated')`.
     - `readonly responded: boolean` — true once any response byte was pushed.
     - Status line `HTTP/1.x SP 3DIGIT [SP reason]`; otherwise `bad-status-line`. Header lines `name: value` with optional whitespace trimmed; obs-fold or a missing colon is `bad-header`. More than `maxHeadBytes` before the blank line is `headers-too-large`.
     - Interim `1xx` responses other than 101 are discarded and parsing continues with the next head.
     - 101: `done` at the end of the head, empty body, `keepAlive: false`, the rest in `leftover`.
     - No body for method `HEAD` and for 204 and 304.
     - `transfer-encoding` whose last coding is `chunked`: hex size (extensions after `;` ignored), data, CRLF, repeat until size 0, then trailer lines until a blank line (trailers discarded). Malformed sizes or missing CRLF are `bad-chunk`.
     - Else `content-length`: one non-negative integer; repeated values must be identical (else `bad-header`).
     - Else read until `end()`.
     - Total body over `maxBodyBytes` is `body-too-large`.
     - `keepAlive`: HTTP/1.1 unless `connection` contains `close`; HTTP/1.0 only when `connection` contains `keep-alive`; always false for read-to-close bodies and 101.
     - `keepAliveTimeoutMs`: `N * 1000` from `keep-alive: timeout=N`, else `null`.
- **Tests (`http1.test.ts`):** request bytes for a GET (exact string including `Host: link.invalid`, `Connection: keep-alive`, `Accept-Encoding: identity`, no `Content-Length`); a POST with a 5-byte body has `Content-Length: 5`; a bodiless POST has `Content-Length: 0`; caller `Origin`, `Cookie`, `Host` and `Content-Length` are dropped; `serializeHead` throws on `get`, a path with a space and a value with CRLF; parser cases fed in 1-byte slices and in one chunk: content-length body, chunked body with an extension and a trailer, read-to-close body completed by `end()`, `HEAD` with `content-length: 10` and no body, 204, a `100 Continue` before a 200, a 101 with 3 bytes of leftover, two pipelined responses where the second appears in `leftover`, `connection: close` gives `keepAlive: false`, `keep-alive: timeout=5` gives 5000, each error code (including `truncated` from `end()` mid content-length body and `body-too-large` with `maxBodyBytes: 4`).
- **Verify:** `npx vitest run packages/anywhere-channel/src/__tests__/http1.test.ts`; `npm run typecheck:anywhere-channel`.

     ```ts
     export type ChannelHttpErrorCode = 'channel-closed' | 'parse' | 'dial-failed' | 'pool-closed';
     export class ChannelHttpError extends Error {
       constructor(readonly code: ChannelHttpErrorCode, message: string, readonly responded: boolean, options?: { cause?: unknown })
     }
     export const CHANNEL_POOL_MAX = 4;
     export const CHANNEL_POOL_IDLE_MS = 4_000;
     ```
  2. `requestOnChannel(stream, req, opts?: { signal?: AbortSignal }): Promise<{ response: HttpResponse; reusable: boolean; keepAliveTimeoutMs: number | null }>`: writes `serializeRequest(req)`, feeds every `data` chunk to a `ResponseParser({ method: req.method })`, and on `done` removes its listeners and resolves. `reusable` is `keepAlive && leftover.length === 0 && !stream.destroyed`. On `end`/`close` before `done`, calls `parser.end()` (a read-to-close body resolves with `reusable: false`); otherwise rejects `ChannelHttpError('channel-closed', …, parser.responded)`. A parse error or an `error` event destroys the stream and rejects (`'parse'` with the `HttpParseError` as `cause`, or `'channel-closed'`). Abort per D-10. Listeners are always removed on settle.
  3. `createChannelPool({ dial, max = CHANNEL_POOL_MAX, idleMs = CHANNEL_POOL_IDLE_MS }): ChannelPool` with `request(req, opts?: { signal?: AbortSignal }): Promise<HttpResponse>`, `close(): void`, and read-only `size` (open channels, busy + idle) and `idleCount`.
     - Acquire: take the most recently idled channel (stop its timer); else if `size < max`, call `dial()` (a rejection becomes `ChannelHttpError('dial-failed', …, false, { cause })` for that request only); else enqueue (FIFO).
     - Release: when `reusable`, park the channel as idle with a timer of `idleMs`, or `hint - 1000` when `keepAliveTimeoutMs` gives `hint` and `0 < hint - 1000 < idleMs`; on expiry `end()` then `destroy()` it. When not reusable, destroy it. Either way hand the freed capacity to the next queued request.
     - An idle channel that emits `close` or `end` leaves the pool at once.
     - Stale resend (FR-3): when the request ran on a channel that had served a previous request, failed with `code === 'channel-closed'` and `responded === false`, and the method is `GET`, `HEAD` or `OPTIONS`, destroy every idle channel and run the request once more on a freshly dialled channel. Never resend otherwise, and never more than once.
     - `close()`: destroys every channel, clears timers, rejects queued requests and every later `request()` with `ChannelHttpError('pool-closed', …, false)`.

## Hazards

- **H-1 Bytes behind a response.** A response can be followed by bytes on the same channel (a misbehaving server, or a 101 with the first frame). `ResponseParser` returns them as `leftover`; the pool treats a non-empty leftover as not reusable, and `ChannelWebSocket` feeds it to the frame decoder. Dropping it loses the first WebSocket frame.
- **H-2 Listener leaks across pooled requests.** `requestOnChannel` must remove its `data`/`end`/`close`/`error` listeners on every settle path; otherwise a later request on the same channel sees two parsers.
- **H-3 `capacitor:` origin is `"null"`.** Fact 8. Comparing `origin` silently routes nothing on iOS.
- **H-4 Server keep-alive is 5 s.** The pool's 4 s idle and the stale resend exist because the machine closes idle connections at 5 s (Fact 3, PAN-4740).
- **H-5 Abort and pool capacity.** An aborted in-flight request must destroy its channel and free the slot, or the pool shrinks permanently.
- **H-6 Fake timers and real streams.** Do not combine `vi.useFakeTimers()` with the real `http.createServer` cases; Node's HTTP server keeps internal timers. Use scripted fake channels for timer tests (WI-2 test plan).
- **H-7 `tests/` imports.** Tests under `tests/` must not import `streamx` or `b4a` (not hoisted). Use `node:stream` and the package's exports.
- **H-8 `nativeShell.ts` ownership.** This issue creates it; PAN-4837's planner must reuse it, not redefine it.
