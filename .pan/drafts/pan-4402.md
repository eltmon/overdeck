# PAN-4402 — Desktop app: open a chosen machine's dashboard with no local server

**Status:** planned (auto) · **Date:** 2026-11-01 · **Author:** Claude Opus 5.5 (planning agent)
**Issue:** [PAN-4402](https://github.com/eltmon/overdeck/issues/4402) · **Epic PRD:** [`.pan/drafts/pan-2350.md`](./pan-2350.md) revision 5, work item **W-PHONE3**, decision **D-14** · **Epic:** [PAN-2350](https://github.com/eltmon/overdeck/issues/2350)

**Done when (from the epic):** the desktop app, with its local server off, opens the desktop's dashboard over Tailscale.

---

## Glossary

- **Desktop app:** the Electron app in `apps/desktop/`. Its main process (`src/main.ts`) today always spawns an **embedded server** (`src/server.ts`, the dashboard `server.js` run with `ELECTRON_RUN_AS_NODE=1`) and loads its `http://127.0.0.1:<port>` origin in a `BrowserWindow`.
- **Local mode:** today's behavior. The embedded server runs and the window shows this computer's dashboard.
- **Machine:** one running Overdeck server with its own `OVERDECK_HOME`. Its identity is its **environment id** (`environmentId`, a UUID), served without a credential by `GET /api/environment` together with a `label`, `protocolVersion` and `capabilities` (the **descriptor**, `src/dashboard/server/routes/environment.ts:26-37`).
- **Remote mode:** new. The desktop app does **not** start the embedded server. Its windows show one chosen other machine's dashboard, loaded from that machine's own origin.
- **Chosen machine / machine record:** the one machine the desktop app opens in remote mode. Its record (base URL, environment id, label, device id, encrypted device token, active flag) is stored in `<userData>/remote-machine.json`. There is at most one record (D-14: "the desktop app connects to one machine").
- **Base URL:** the origin of the chosen machine as given in its pairing link, for example `http://100.101.102.103:3011` or `https://desk.tail1234.ts.net`. Always reduced to `URL.origin` (scheme, host, port; no path).
- **Pairing link:** the link `pan pair` or Settings → Anywhere → **Pair a device** prints: `<base>/#pair=<credential>` (`src/cli/commands/pair.ts:38-40`). The **pairing credential** is a one-time `odp_…` string, valid 10 minutes.
- **Device token:** the revocable `odk_…` credential `POST /api/pairing/exchange` returns when called with `delivery: 'bearer'` (`src/dashboard/server/routes/pairing.ts:133`). It has `scopes: ['admin']` and is listed under the machine's paired devices.
- **`safeStorage`:** Electron's OS-keystore string encryption (`safeStorage.encryptString` / `decryptString`; Keychain on macOS, DPAPI on Windows, libsecret or KWallet on Linux). On Linux, the `basic_text` backend uses a hard-coded key and is plaintext-equivalent.
- **Remote partition:** an Electron session created with `session.fromPartition('remote-<environmentId>')`. The name has **no** `persist:` prefix, so the session's cookies, cache and storage live only in memory and nothing in it reaches disk.
- **Device cookie:** `overdeck_device`, the cookie a paired browser presents (`src/dashboard/server/routes/dashboard-auth.ts:17`). Its value is the device token. The server accepts it on HTTP routes, the session mint and every `/ws/*` upgrade.
- **Preflight:** the check the main process runs before it opens the chosen machine: descriptor answers, environment id matches the record, protocol version is supported, and the device token still mints a session.
- **Connect window:** a new small local window (`apps/desktop/resources/connect.html`) with its own preload. It takes a pairing link and shows the chosen machine's state and errors. It works with no server running anywhere.
- **Transport policy:** the rule that decides which base URLs may carry the device token (FR-3).

## Problem

The desktop app can only show this computer's dashboard, and it always runs a server to do so. The epic's laptop story needs the opposite as well: on a laptop that should not run Overdeck itself, open the desktop's dashboard over Tailscale, with the laptop's credential stored safely. A browser can already pair with a machine (`/#pair=` handling in `src/dashboard/frontend/src/lib/wsTransport.ts:79-157`), but a browser keeps the device token in its cookie jar, and the desktop app has no way to open another machine at all.

D-14 narrows this issue: no machine catalog and no environment switcher (those become server-side machine links in [PAN-4645](https://github.com/eltmon/overdeck/issues/4645), W-LINK1). The desktop app opens **one** chosen machine and stores that machine's device credential with `safeStorage`.

**Server contracts this issue consumes (no server change is needed):**
- `GET /api/environment` and `POST /api/pairing/exchange` need no credential (`src/dashboard/server/remote-request-gate.ts:45-53`).
- Exchange body: `{ credential, label, delivery: 'bearer' }`, label 1–200 chars (`pairing.ts:107-113`). Bearer response: `{ deviceId, environmentId, csrfToken, token }`. Failures: 400 bad body, 401 unknown or used credential, 410 expired, 429 rate limited, 403 `Invalid origin`.
- **Origin rule** (`src/dashboard/server/routes/origin-validation.ts:127-164`): a POST with neither `Origin` nor `Referer` is refused with `Missing origin` unless it carries an `odk_` bearer. The exchange has no bearer yet, so the main process **must** send `Origin: <base origin>`, and that origin must be in the machine's trusted origins. It is, when the link came from Settings → Anywhere (the dialog adds the chosen address) or from `pan pair` with its default or loopback base.
- **Session mint** (`src/dashboard/server/routes/dashboard-session.ts:96-107`): `POST /api/dashboard/session` with a device credential (cookie or `Authorization: Bearer odk_…`) answers 200 `{ ok, csrfToken }` and a refreshed `overdeck_device` cookie (`Max-Age` 30 days). An unknown or revoked token falls through to the root mint check and answers 401 to a non-loopback caller.
- **CSRF:** a device credential is **not** exempt from CSRF on mutations guarded by `rejectUnsafeDashboardMutationRequest` (`dashboard-auth.ts:219-220` exempts only `internal-token` and `token`). `DELETE /api/devices/:id` uses that guard, so a self-revoke needs `Content-Type: application/json` and `x-overdeck-csrf-token` from a session mint. A paired device may revoke itself (`pairing.ts:183-185`).
- The cloister routes (`src/dashboard/server/routes/cloister.ts:81-120`) have no route-level CSRF check; the remote request gate admits a device bearer with the `admin` scope.
- The frontend is same-origin: `resolveRpcUrl` builds `/ws/rpc` from `window.location` (`wsTransport.ts:27-38`), and `ensureDashboardSession` (`wsTransport.ts:128-157`) mints with `credentials: 'include'`. A page loaded from the machine's own origin with the device cookie already set therefore works with **no frontend change**.

**Pre-existing defect (not fixed here):** the menu and tray **Emergency Stop** call `/api/agents/emergency-stop`, which no route serves (the route is `/api/cloister/emergency-stop`). This issue keeps the path unchanged; see NonGoals.

## Decisions

- **D-1 One chosen machine, no catalog.** The desktop app stores at most one machine record. Pairing with a new machine replaces the record (after a best-effort self-revoke of the old device, FR-9). The catalog and switcher belong to PAN-4645.
- **D-2 Load the machine's own origin; the frontend is unchanged.** Remote mode loads the base URL in a `BrowserWindow`. Every relative `fetch('/api/…')` and `/ws/*` URL then resolves to the chosen machine, exactly like a paired browser. No change to `src/dashboard/frontend/`.
- **D-3 Authenticate the page with the device cookie in an in-memory partition.** Before loading, the main process sets `overdeck_device=<token>` in the remote partition with `ses.cookies.set({ url: baseUrl, name: 'overdeck_device', value: token, httpOnly: true, sameSite: 'strict', secure: baseUrl.startsWith('https:') })`. The partition name `remote-<environmentId>` has no `persist:` prefix, so the cookie and the server's 30-day refresh of it stay in memory. The only copy on disk is the `safeStorage` ciphertext.
  - *Why not header injection:* `webRequest.onBeforeSendHeaders` could add `Authorization: Bearer`, but whether Electron 40 applies it to WebSocket upgrades is unverified, and cookies are what the frontend and `/ws/*` already use.
  - *Cost:* the remote window's `localStorage` (UI preferences, drafts) resets on every launch. Accepted; a persistent partition with Set-Cookie stripping is a possible follow-up.
- **D-4 `safeStorage` is mandatory.** The record is saved only when `safeStorage.isEncryptionAvailable()` is true **and**, on Linux, `safeStorage.getSelectedStorageBackend()` is not `basic_text` (a hard-coded key) or `unknown`. Otherwise pairing is refused **before** the pairing credential is spent, with the message in FR-5.
- **D-5 Transport policy.** The device token travels only over an encrypted route or the loopback interface (epic revision 3: no unencrypted traffic between machines). Allowed base URLs:
  1. any `https:` URL;
  2. `http:` when the host is loopback (`localhost`, `127.0.0.0/8`, `::1`), an SSH forward or a local test server;
  3. `http:` when the host is a Tailscale address — an IPv4 address in `100.64.0.0/10`, an IPv6 address in `fd7a:115c:a1e0::/48`, a name ending in `.ts.net`, or a name whose DNS lookup returns only such addresses (MagicDNS short names like `desk`). WireGuard encrypts the tailnet.
  
  Every other `http:` URL is refused with the FR-3 message. The policy is checked at pairing **and** at every launch preflight (a name can re-resolve).
- **D-6 Preflight before the token leaves the main process.** At launch and on **Open** the main process (1) checks the transport policy, (2) fetches the descriptor and requires `environmentId` to equal the record's and `protocolVersion === 1`, (3) mints a session with `Authorization: Bearer <token>` and `Origin: <base origin>`. Only a 200 opens the window. A 401 means the device was revoked. Nothing falls back to local mode silently: a failure opens the connect window with the reason, and the operator chooses **Retry** or **Use this computer**.
- **D-7 Remote mode never starts the embedded server.** `startServer` is not called while the record is active. Switching to remote mode stops a running embedded server; **Use this computer** starts it again.
- **D-8 The remote page keeps `overdeckBridge`.** The chosen machine is the operator's own paired machine, and the frontend needs the bridge for notifications, terminal pop-outs and desktop settings. The connect window's IPC handlers accept calls only from the connect window's `webContents`, so the remote page cannot pair, switch or forget. `RESTART_DASHBOARD` rejects in remote mode.
- **D-9 Navigation stays on the machine.** In a remote window, `will-navigate` to another origin is prevented and opened with `shell.openExternal` (http/https only); `setWindowOpenHandler` denies new windows to other origins the same way.
- **D-10 Main-process calls carry the token.** A new `dashboardFetch(path, init)` prefixes the active base URL and, in remote mode, adds `Authorization: Bearer <token>`. Menu workspaces, tray health polling and `callServerApi` use it, so the tray and menu reflect the chosen machine.
- **D-11 Device label.** The exchange label is `Overdeck desktop on <os.hostname()>`, cut to 200 characters, so the machine's Devices list names this computer.
- **D-12 Docs ship despite the issue's "Docs: None".** The issue says the epic's W-DOC section assigns no page. The repo's PRD rule requires a docs work item for new behavior, and `configuration/remote-access.mdx:308-315` describes this issue as a "connection list, environment switcher", which D-14 made wrong. W-9 updates both pages.

## Requirements

- **FR-1 Pair from a link.** The connect window accepts a pairing link (`<base>/#pair=odp_…`). The main process parses it, applies FR-3 and D-4, fetches the descriptor, exchanges the credential with `delivery: 'bearer'` and `Origin: <base origin>`, checks that the response's `environmentId` equals the descriptor's, and saves the record (FR-2). A bare `odp_…` string without a base URL is refused with "Paste the whole pairing link, including the address."
- **FR-2 Encrypted record.** `<userData>/remote-machine.json` holds `{ version: 1, active, baseUrl, environmentId, label, deviceId, pairedAt, tokenCiphertext }`, where `tokenCiphertext` is the base64 of `safeStorage.encryptString(token)`. The plaintext token is never written to disk, never placed in `desktop-settings.json`, never sent to any renderer, and never logged. The file is written atomically (temp file + rename) with mode `0o600`.
- **FR-3 Transport policy (D-5).** A disallowed base URL is refused with: "Overdeck sends this computer's credential only over HTTPS, Tailscale or this computer's loopback. Use the machine's Tailscale address or an HTTPS address."
- **FR-4 Boot in remote mode.** When the record is active, the app does not start the embedded server, runs preflight (D-6), and on success opens the main window on the base URL in the remote partition with the device cookie set (D-3).
- **FR-5 Clear failures.** Every failure opens or updates the connect window with one plain sentence:
  - unreachable: "Can't reach <label> at <origin>. Check that its Overdeck is running and that this computer is on the same tailnet.";
  - wrong machine: "<origin> is now a different Overdeck machine (<new label>). Pair again.";
  - revoked: "<label> no longer accepts this computer's credential. Pair again with a new link.";
  - protocol: "<label> speaks Overdeck protocol <n>; this app supports 1. Update the older side.";
  - no secret store (D-4): "This computer has no secure credential store (GNOME Keyring, KWallet, Keychain or Windows credential protection), so Overdeck will not save a machine credential.";
  - exchange errors: the server's own `error` text, prefixed "Pairing failed: ". When that text is `Invalid origin`, append " Add <origin> under Settings → Anywhere → trusted addresses on that machine.";
  - store decrypt failure (H-5): "This computer's credential store could not decrypt the saved credential. Pair again."
- **FR-6 Switching.** **Connect to a Machine…** (menu and tray) opens the connect window. A successful pairing stops the embedded server, closes the local windows and opens the remote main window. **Use This Computer** clears `active`, closes remote windows and starts the embedded server, which opens the local window as today.
- **FR-7 Windows follow the mode.** Terminal pop-out windows use the same base URL and partition as the main window. `RESTART_DASHBOARD` rejects in remote mode with "This window shows <label>. Restart its dashboard on that machine."
- **FR-8 Main-process calls follow the mode (D-10).** Tray health polling, the menu's workspace list and `callServerApi` reach the chosen machine with the bearer token in remote mode, and the embedded server in local mode.
- **FR-9 Forget.** **Forget <label>** in the connect window mints a session with the bearer to get a CSRF token, sends `DELETE /api/devices/<deviceId>` (self-revoke), then deletes the record regardless of the result. When the revoke fails, the window says: "Removed from this computer. <label> could not be reached; revoke "<device label>" in its Settings → Anywhere → Devices."
- **FR-10 Navigation guard (D-9).**
- **NFR-1 No disk plaintext.** After pairing and a full session in remote mode, no file under `<userData>` contains the `odk_` token in plain text.
- **NFR-2 No server change.** No file under `src/dashboard/` or `src/lib/` changes.
- **NFR-3 Tests are unit tests with Electron mocked**, in `apps/desktop/tests/`. Timers in reconnect or polling tests use `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()`. `fetch` is injected or stubbed, never real network.
- **NFR-4 Local mode unchanged.** With no record, or an inactive one, boot, windows, tray and menu behave exactly as before.

### W-1 `machine-url.ts` — pairing link parser and transport policy (FR-1, FR-3, D-5)

New file `apps/desktop/src/machine-url.ts`, pure, no Electron import.

```ts
export interface PairingLink { baseUrl: string; credential: string }
export type ParseResult = { ok: true; link: PairingLink } | { ok: false; error: string };
export function parsePairingLink(input: string): ParseResult;
// trims; requires http:/https: URL; credential = URLSearchParams(hash).get('pair') and must start with 'odp_';
// baseUrl = new URL(input).origin. Bare 'odp_…' → FR-1 message. Other junk → "That is not an Overdeck pairing link."

export type LookupAll = (host: string) => Promise<string[]>; // injected; production uses dns.promises.lookup(host, { all: true })
export type TransportVerdict = { ok: true; kind: 'https' | 'loopback' | 'tailnet' } | { ok: false; error: string };
export function assessMachineTransport(baseUrl: string, lookupAll: LookupAll): Promise<TransportVerdict>;
export function isTailnetAddress(ip: string): boolean;   // 100.64.0.0/10 or fd7a:115c:a1e0::/48
export function isLoopbackAddress(ip: string): boolean;  // 127.0.0.0/8, ::1
```

Rules, in order: `https:` → ok `https`; host `localhost` or loopback literal → ok `loopback`; tailnet literal or `*.ts.net` → ok `tailnet`; other name → `lookupAll`; every address tailnet → `tailnet`, every address loopback → `loopback`; lookup error or any other address → the FR-3 message. IPv6 literals arrive bracketed in `URL.hostname` (`[::1]`); strip the brackets.

**Tests** `apps/desktop/tests/machine-url.test.ts`: a Settings → Anywhere link parses to its origin and credential; a link with a path (`https://desk.ts.net/foo/#pair=odp_x`) yields origin only; bare `odp_x` and a link without `#pair=` are refused; `http://192.168.1.5:3011` is refused with the FR-3 text; `http://100.64.0.1`, `http://100.127.255.254` pass as tailnet and `http://100.128.0.1` is refused; `http://[fd7a:115c:a1e0::1]:3011` passes; `http://desk:3011` with a lookup returning `['100.90.1.2']` passes, and with `['100.90.1.2', '192.168.1.5']` is refused; `http://127.0.0.1:3011` passes as loopback; `https://anything.example` passes.

### W-3 `machine-client.ts` — pairing, preflight and self-revoke over HTTP (FR-1, FR-5, FR-9, D-6, D-11)

New file `apps/desktop/src/machine-client.ts`. Every function takes a `fetchImpl: typeof fetch` and a `lookupAll` so tests inject them; production passes `globalThis.fetch` and the DNS lookup. All requests use `AbortSignal.timeout(5_000)`.

```ts
export const SUPPORTED_ENVIRONMENT_PROTOCOL_VERSION = 1; // mirrors ENVIRONMENT_PROTOCOL_VERSION, packages/contracts/src/environment.ts:12
export interface MachineDescriptor { environmentId: string; label: string; protocolVersion: number }
export function fetchMachineDescriptor(baseUrl: string, deps): Promise<{ ok: true; descriptor: MachineDescriptor } | { ok: false; error: string }>;
export function pairWithMachine(linkText: string, deps): Promise<{ ok: true; record: MachineRecord } | { ok: false; error: string }>;
export type PreflightResult = { ok: true; token: string } | { ok: false; reason: 'transport' | 'unreachable' | 'wrong-machine' | 'protocol' | 'revoked' | 'store'; error: string };
export function preflightMachine(record: MachineRecord, deps): Promise<PreflightResult>;
export function revokeOwnDevice(record: MachineRecord, token: string, deps): Promise<boolean>;
```

`pairWithMachine` order (credential is spent only at step 5):
1. `parsePairingLink` (W-1).
2. `credentialStoreStatus()` (W-2) — refuse before any network call.
3. `assessMachineTransport` (W-1).
4. `fetchMachineDescriptor`; require `descriptorVersion === 1`, string `environmentId`, `protocolVersion === SUPPORTED_ENVIRONMENT_PROTOCOL_VERSION`, `capabilities.pairing === true`.
5. Exchange:

```ts
const response = await fetchImpl(`${baseUrl}/api/pairing/exchange`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', Origin: baseUrl },
  body: JSON.stringify({ credential, label: deviceLabel(), delivery: 'bearer' }),
  signal: AbortSignal.timeout(5_000),
});
// non-2xx → { ok: false, error: `Pairing failed: ${body.error ?? `HTTP ${status}`}` }
// 2xx → require typeof token === 'string' && token.startsWith('odk_') and environmentId === descriptor.environmentId
```

6. If an older record exists, call `revokeOwnDevice` on it (result ignored), then `saveMachineRecord({ active: true, baseUrl, environmentId, label: descriptor.label, deviceId, pairedAt: new Date().toISOString() }, token)`.

`preflightMachine`: transport → descriptor (network error ⇒ `unreachable`; id mismatch ⇒ `wrong-machine`; version ⇒ `protocol`) → `readMachineToken` (throw ⇒ `store`) → `POST ${baseUrl}/api/dashboard/session` with `Authorization: Bearer <token>`, `Origin: baseUrl`; 200 ⇒ ok; 401 or 403 ⇒ `revoked`; other ⇒ `unreachable`. Messages are the FR-5 texts.

`revokeOwnDevice`: session mint as above, read `csrfToken`, then `DELETE ${baseUrl}/api/devices/${encodeURIComponent(deviceId)}` with `Authorization`, `Content-Type: application/json`, `x-overdeck-csrf-token`, body `{}`; returns `response.ok`, `false` on any throw.

`deviceLabel()` = `` `Overdeck desktop on ${OS.hostname()}`.slice(0, 200) ``.

**Tests** `apps/desktop/tests/machine-client.test.ts` (`fetchImpl` is a `vi.fn` router; store module mocked): the exchange request carries `Origin` equal to the base origin, `delivery: 'bearer'` and the hostname label; a 401 exchange returns `Pairing failed: unknown or already used pairing credential` and saves nothing; a response `environmentId` different from the descriptor's is refused; an unavailable store refuses with no fetch call; preflight maps descriptor id mismatch to `wrong-machine`, session 401 to `revoked`, a rejected fetch to `unreachable`, and 200 to `ok` with the token; `revokeOwnDevice` sends the CSRF header from the mint response and returns `false` when the mint rejects.

## Hazards

- **H-1 A different server at the same address.** Preflight compares the environment id before the cookie is set, but a host that changes between preflight and page load would receive the cookie. Accepted until W-SEC1 pins machine keys.
- **H-2 Untrusted origin.** If the base origin is not in the machine's trusted origins, the exchange returns 403 `Invalid origin` before the credential is spent. The FR-5 "Pairing failed: Invalid origin" message should say what to do; append: " Add <origin> under Settings → Anywhere → trusted addresses on that machine."
- **H-3 `export let serverUrl` live bindings.** `menu.ts` and `tray.ts` read `serverUrl` from `main.ts`; W-7 removes those imports. Keep `serverUrl` in `main.ts` for the local server only.
- **H-4 Window recreation.** A `BrowserWindow`'s partition cannot change after creation; switching modes must close and recreate the main window and every terminal window.
- **H-5 Linux keyring locked.** `isEncryptionAvailable()` can be true while `decryptString` throws (keyring locked or reset). Preflight maps that throw to `store` with: "This computer's credential store could not decrypt the saved credential. Pair again."
