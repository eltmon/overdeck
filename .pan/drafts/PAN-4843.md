This PRD adds a third needs-you push provider next to Web Push and ntfy. For each paired phone it seals the notification with `crypto_box_seal` to the phone's push key and sends it to the overdeck.ai directory in a `push` frame. Settings shows how many phones receive these notifications.

## Glossary

- **Needs-you push:** the PAN-2354 feature that notifies the operator's phone when an agent or conversation asks a question, waits for approval, finishes or fails. Code: `src/lib/push/` and `src/dashboard/server/services/needs-you-push-service.ts`.
- **Provider:** an object that implements `PushProvider` (`src/lib/push/types.ts:33-38`): `name`, `hasTargets()`, `send(notification)`. Today there are two: `webpush` and `ntfy`. This issue adds `native`.
- **Dispatcher:** `src/lib/push/dispatcher.ts`. It decides *when* to notify (rising edges, dedup, 6 per minute) and fans each notification out to every provider. It does not change in this issue.
- **`NeedsYouNotification`:** the provider input (`types.ts:8-21`): `kind`, `tag`, `title`, `publicTitle`, `body`, `url`, `issueId`, `ts`.
- **`ProviderSendOutcome`:** the provider output per target (`types.ts:23-31`): `{ target, ok: true }` or `{ target, ok: false, reason: 'gone' | 'rejected' | 'transient' | 'revoked' | 'skipped', status?, detail? }`.
- **Phone record:** an access-token record with `kind: 'phone'` (`src/lib/access-tokens.ts:83-105`). It carries `clientId` (the phone's directory client id, UUID v4) and `pushKey` (the phone's X25519 push public key, 64 lowercase hex). Minted by `POST /api/phones/exchange` (PAN-4835).
- **Push key:** the phone's X25519 key pair for notifications. The machine holds only the public half (`pushKey`).
- **Sealed box:** libsodium `crypto_box_seal(message, recipientPublicKey)`. Output = 32-byte ephemeral public key + ciphertext + 16-byte MAC, so it is exactly 48 bytes longer than the message (`crypto_box_SEALBYTES`). Only the holder of the recipient secret key can open it (`crypto_box_seal_open`).
- **Directory:** the overdeck.ai connect service (`services/connect`). The machine keeps one WebSocket to it through `DirectoryClient` (`src/dashboard/server/services/directory-client.ts`).
- **`push` frame:** machine → directory, `{ type: 'push', requestId, to, sealed, urgency, collapseId }` (`packages/contracts/src/connect.ts:140-152`).
- **`push-result` frame:** directory → machine, `{ type: 'push-result', requestId, ok: true }` or `{ …, ok: false, error: 'no_registration' | 'rate_limited' | 'delivery_failed' | 'unknown_client' }` (`connect.ts:200-202`).
- **Phone push payload:** the JSON plaintext the machine seals. Defined in this PRD (D-3) and exported as `PhonePushPayload` from `packages/contracts/src/connect.ts`.
- **`PUSH_PLAINTEXT_MAX_BYTES`:** `2_256` (`connect.ts:39`). The largest plaintext one push may seal. 2,256 + 48 = 2,304 bytes, and base64 of 2,304 bytes is exactly 3,072 characters = `PUSH_SEALED_MAX_CHARS` (`connect.ts:34`).
- **Primary dashboard:** the dashboard process that owns side effects. A peer dashboard (`isPeerDashboard` in `main.ts`) starts neither the push service nor the directory client.

## Requirements

### Functional

- **FR-1** A provider named `native` exists in `src/lib/push/native-provider.ts` and is the third entry of `defaultProviders()`.
- **FR-2** For each active phone record that has a `pushKey`, `send(notification)` sends exactly one `push` frame whose `to` is that record's `clientId`.
- **FR-3** The `sealed` field is `crypto_box_seal` of the UTF-8 JSON phone push payload (D-3) to that phone's `pushKey`, base64 (standard alphabet). It opens with the phone's secret key.
- **FR-4** The JSON plaintext is at most `PUSH_PLAINTEXT_MAX_BYTES` (2,256) bytes. Longer payloads are trimmed by the rule in D-4. A payload that cannot fit is not sent.
- **FR-5** `urgency` follows `webPushUrgency(kind)`. `collapseId` is the first 32 lowercase hex characters of `sha256(tag)`. `requestId` is 16 random bytes as 32 lowercase hex.
- **FR-6** The provider waits up to 10 s for the `push-result` with the same `requestId` and maps it to a `ProviderSendOutcome` by the table in D-5.
- **FR-7** `hasTargets()` is `true` only when at least one active phone record has a `pushKey` **and** the directory client exists and is online.
- **FR-8** `GET /api/push/status` gains `native: { phones: number; directoryOnline: boolean }`.
- **FR-9** Settings → Anywhere → Phone notifications shows one "Overdeck app" status line (exact strings in D-7).
- **FR-10** The Send test toast does not report `skipped` outcomes as a failure (D-6).
- **FR-11** (AC-9 of the epic) A needs-you event produces one `push` frame per phone, and each frame's sealed payload opens with that phone's push secret key.

### Non-functional

- **NFR-1** No log line, outcome `detail`, or status field contains the sealed body, a push key, or notification text. Logs may carry the first 8 characters of a `clientId` and the outcome.
- **NFR-2** `src/lib/push/` imports nothing from `src/dashboard/server/`. The provider reaches the directory only through the port type in D-2.
- **NFR-3** Nothing in the provider throws into the dispatcher: every phone's send settles to an outcome (`Promise.allSettled`, as `webpush-provider.ts` does).
- **NFR-4** Tests that exercise the 10 s wait use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()` (repo rule "fake timers for retry / backoff / delay-based tests"). No test sleeps on real time.
- **NFR-5** No file exceeds its file-size ratchet (its line count on `origin/main`, or its `scripts/file-size-allowlist.txt` cap). `needs-you-push-service.ts` (215 lines) and `PushPanel.tsx` (121 lines) grow by under 30 lines each.

## Decisions

- **D-1 Plaintext cap is `PUSH_PLAINTEXT_MAX_BYTES` (2,256), not 2,900.** The epic (NFR-5, W-MAC3 step 2) says 2,900 bytes, but 2,900 bytes seal to 3,932 base64 characters, which the contract cap `PUSH_SEALED_MAX_CHARS = 3_072` refuses. PAN-4828 D-3 exported the correct cap and the issue comment of 2026-11-03 directs this issue to use it. The provider imports the constant; it never hard-codes 2,256 or 2,900.

- **D-2 The provider takes a lazy directory port; `anywhere-boot.ts` does not change.** The epic names `anywhere-boot.ts` "(inject the directory port)". Fact 2 shows the push service is built before `setDirectoryClient` runs, so a captured value would be `null` forever. The provider therefore takes a getter and resolves it on every `hasTargets()` and `send()`. `needs-you-push-service.ts` passes `currentDirectoryClient`. The port type lives in `native-provider.ts` so `src/lib` does not import the server (NFR-2):
  ```ts
  import type { DirectoryToMachineFrame, MachineToDirectoryFrame } from '@overdeck/contracts';

  type PushResultFrame = Extract<DirectoryToMachineFrame, { type: 'push-result' }>;

  /** The part of the directory client the native provider uses (structurally `DirectoryClient`). */
  export interface PushDirectoryPort {
    isOnline(): boolean;
    send(frame: MachineToDirectoryFrame): boolean;
    on(type: 'push-result', handler: (frame: PushResultFrame) => void): () => void;
  }
  ```
  `DirectoryClient` satisfies this structurally; no `implements` clause is added to it.

- **D-3 The phone push payload.** Field order as listed; `v` is always `1`:
  ```ts
  /** The plaintext a machine seals into a `push` frame (PAN-4843). UTF-8 JSON, at most PUSH_PLAINTEXT_MAX_BYTES. */
  export interface PhonePushPayload {
    readonly v: 1
    /** The sending machine's environment id; the phone opens this machine when the notification is tapped. */
    readonly machine: string
    readonly kind: "question" | "approval" | "finished" | "failed" | "summary" | "test"
    /** The full title (the Web Push `title`), never `publicTitle`: the payload is end-to-end encrypted. */
    readonly title: string
    readonly body: string
    /** Same-origin dashboard path, e.g. `/m?subject=my-conv`. */
    readonly url: string
    /** Dedup and replace key; the phone uses it as the notification thread / tag. */
    readonly tag: string
    readonly issueId: string | null
    /** ISO 8601. */
    readonly ts: string
  }
  ```
  It is exported from `packages/contracts/src/connect.ts`, next to the `push` frame, because it is the wire format that W-APP1, W-IOS1 and W-AND1 decode. `connect.ts` is runtime-import-free; this adds only a type. The directory never parses it. `title` is `notification.title`, because only the phone can read the payload; `body` is `notification.body`, which already honours `includePreview` (`classify.ts:162-173`).

- **D-4 Trim rule (mechanical).** `size(p) = Buffer.byteLength(JSON.stringify(p), 'utf8')`. Code points are counted with `Array.from(s)` (never `s.length` or `s.slice`, which split surrogate pairs). The ellipsis is `'…'` (U+2026).
  1. If `size(p) <= PUSH_PLAINTEXT_MAX_BYTES`, send `p` unchanged.
  2. Otherwise trim `body`: binary-search the largest `k` in `[0, Array.from(body).length - 1]` such that `size({ ...p, body: cp(body, k) + '…' }) <= MAX`, where `cp(s, k) = Array.from(s).slice(0, k).join('')`. If a `k` exists, use it.
  3. If no `k` fits (even `body: '…'` is too large), set `body: ''` and trim `title` the same way (largest `k` with `title = cp(title, k) + '…'`).
  4. If no `k` fits for `title` either (even with `body: ''` and `title: '…'`), the payload cannot be sent: return `null`. The provider then answers every phone with `{ ok: false, reason: 'rejected', detail: 'payload-too-large' }` and sends no frame.
  `url`, `tag`, `machine`, `kind`, `issueId` and `ts` are never altered. Because the trim is the same for every phone (the plaintext does not depend on the phone), it runs once per `send()` call, before sealing.

- **D-5 Outcome mapping.** `target` is `native:<clientId>` for every outcome.

  | Situation | Outcome |
  | --- | --- |
  | `push-result` `ok: true` | `{ ok: true }` |
  | `error: 'no_registration'` | `{ ok: false, reason: 'skipped', detail: 'no_registration' }` |
  | `error: 'unknown_client'` | `{ ok: false, reason: 'skipped', detail: 'unknown_client' }` |
  | `error: 'rate_limited'` | `{ ok: false, reason: 'transient', detail: 'rate_limited' }` |
  | `error: 'delivery_failed'` | `{ ok: false, reason: 'transient', detail: 'delivery_failed' }` |
  | no `push-result` within 10 s (`NATIVE_PUSH_RESULT_TIMEOUT_MS = 10_000`) | `{ ok: false, reason: 'transient', detail: 'timeout' }` |
  | directory getter returns `null`, `isOnline()` is false, or `send()` returns `false` | `{ ok: false, reason: 'transient', detail: 'directory-offline' }`, no wait |
  | payload cannot fit (D-4 step 4) | `{ ok: false, reason: 'rejected', detail: 'payload-too-large' }`, no frame |
  | sealing throws (malformed `pushKey`) | `{ ok: false, reason: 'rejected', detail: 'seal-failed' }`, no frame |
  | no active phone record has a `pushKey` | `send()` returns `[]` and sends nothing |

  Only `push-result` frames are correlated (by `requestId`). An `error` frame is ignored, so until PAN-4830 is deployed every send waits the full 10 s and ends as `timeout` (H-1). The handler is subscribed **before** `send()` and unsubscribed when the wait settles, so a fast answer is never missed and no handler leaks.

- **D-6 `skipped` is not an operator error in the Send test toast; the dispatcher stays as it is.** `no_registration` and `unknown_client` mean the phone turned notifications off or signed out (epic W-MAC3 step 2: "not errors to the operator"). They map to the existing `skipped` reason. `PushPanel.tsx` `handleTest` changes its failure pick to `outcomes.find((outcome) => !outcome.ok && outcome.reason !== 'skipped')`. The success toast counts only `ok` outcomes, as today. This also stops Web Push's existing `skipped` (`endpoint-not-allowed`) from showing as "Test failed", which is correct: that subscription was not attempted. The dispatcher (`dispatcher.ts`) is **not** changed: `skipped` outcomes still count under `byProvider.native.failed` and may set `lastError`. That distortion is accepted because `PushPanel` does not display `stats`, and changing the dispatcher would alter Web Push accounting outside this issue.

- **D-7 Settings status line.** `PushStatus.native = { phones, directoryOnline }`, where `phones` = number of active phone records with a `pushKey` (the same list the provider sends to) and `directoryOnline` = `currentDirectoryClient()?.isOnline() ?? false`. `PushPanel` renders one `<p>` directly under the ntfy line, with `data-testid="push-native-line"`, text from `nativeLine(native)`:
  - `phones === 0` → `Overdeck app: no phones paired.`
  - `phones === 1` and online → `Overdeck app: 1 phone`
  - `phones >= 2` and online → `Overdeck app: <N> phones`
  - `phones >= 1` and offline → the above plus ` · not connected to overdeck.ai, so no notifications reach them`
  The field is **required** in both `PushStatus` types; both frontend test literals gain `native: { phones: 0, directoryOnline: false }`.

- **D-8 One shared phone list.** `native-provider.ts` exports `nativePushPhones(): Array<{ clientId: string; pushKey: string }>` (default source `listActiveRecordsOfKind('phone')`, filtered to records with both fields). The provider uses it through an injectable `listPhones` dep (default `nativePushPhones`); `getNeedsYouPushStatus` calls `nativePushPhones().length`. This keeps the Settings count and the send list identical.

- **D-9 Seal helper lives with the open helper.** `src/lib/anywhere/sealed-box.ts` gains `sealTo(recipientPublicKey: Uint8Array, message: Uint8Array): Buffer`, using the module's existing `sodium-native` handle. It throws when the key is not 32 bytes (`sodium.crypto_box_PUBLICKEYBYTES`). The name matches `services/connect/src/seal.ts` `sealTo(publicKey, message)`.

- **D-10 Docs: additive sentences only.** W-DOC ([PAN-4842](https://github.com/eltmon/overdeck/issues/4842)) owns the full phone-app documentation (`configuration/phone-app.mdx`, the CONNECT-SERVICE and ANYWHERE-ARCHITECTURE rewrites). This issue, like PAN-4828 D-8, changes only the sentences that would become false and adds one provider paragraph. See W-7.

     /** `crypto_box_seal` of `message` to an X25519 public key: 48 bytes longer than the message (PAN-4843). */
     export function sealTo(recipientPublicKey: Uint8Array, message: Uint8Array): Buffer {
       if (recipientPublicKey.byteLength !== sodium.crypto_box_PUBLICKEYBYTES) throw new Error('sealTo needs a 32-byte public key');

     4. For each phone, in parallel with `Promise.allSettled`, run `sendOne(phone)`:
        - `port = deps.directory()`; if `null` or `!port.isOnline()` → `directory-offline`.
        - `sealed = sealTo(Buffer.from(phone.pushKey, 'hex'), plaintext).toString('base64')` in a `try`; on throw → `seal-failed`.
        - `requestId = randomRequestId()`; subscribe `port.on('push-result', …)` filtered by `requestId`, start a `setTimeout(NATIVE_PUSH_RESULT_TIMEOUT_MS)`, then `port.send({ type: 'push', requestId, to: phone.clientId, sealed, urgency, collapseId })`. If `send` returns `false`: clear the timer, unsubscribe, → `directory-offline`.
        - On the matching frame or the timeout: clear the timer, unsubscribe, map per D-5.
        - A rejected `allSettled` entry becomes `{ target: 'native:<clientId>', ok: false, reason: 'transient', detail: <error message> }` (same shape as `webpush-provider.ts`).
     5. Log one `console.warn` per non-ok outcome except `skipped`: `[push] native (<clientId first 8>…) <detail>`. Never the sealed text, key or titles (NFR-1).

## Acceptance criteria

- **AC-1 (W-1):** `sealTo(pk, m)` returns `m.byteLength + 48` bytes that `openSealed` opens with the matching key pair and refuses (null) with another pair; a 31-byte key throws.
- **AC-2 (W-2):** `packages/contracts/src/connect.ts` exports `PhonePushPayload` with the D-3 fields; `npm run typecheck` and `npm run typecheck:connect` exit 0.
- **AC-3 (W-3):** a 5,000-byte body, a 3,000-emoji body and a 2,000-quote body each produce a plaintext of at most 2,256 bytes with unchanged `url`/`tag`/`machine`; an oversize `url` returns null.
- **AC-4 (W-4):** each phone receives one `push` frame whose `sealed` opens only with its own push key to the built payload; `push-result` errors and the 10 s timeout map per D-5 under fake timers.
- **AC-5 (W-5, epic AC-9):** an `agent.enrichment_changed` question produces one `push` frame per phone (two phones → two frames), and each `sealed` opens with that phone's push key; `GET /api/push/status` carries `native: { phones, directoryOnline }`.
- **AC-6 (W-6):** Settings → Anywhere → Phone notifications renders the D-7 line for 0, 1 and 3 phones, and a Send test whose only non-ok outcome is `skipped` shows the success toast.
- **AC-7 (W-7):** `configuration/push-notifications.mdx` states that Overdeck app notifications pass through connect.overdeck.ai as ciphertext and has a `## The Overdeck app` section; `docs/DASHBOARD-ARCHITECTURE.md` names `native-provider.ts` and the lazy directory port.

## Hazards

- **H-1 The live directory cannot answer `push` until PAN-4830 is deployed.** Fact 10: it replies `error bad_frame` without a `requestId`, so every send waits 10 s and ends as `timeout`. Harmless in practice: no phone with a `pushKey` can exist before W-APP1 ships, and normal dispatch is fire-and-forget. While phones exist and PAN-4830 is not deployed, **Send test** waits up to 10 s. Accepted; do not add `error`-frame correlation.
- **H-2 Sequencing.** The issue says not to start before PAN-4774's acceptance run passes. Planning does not start work; the handoff gate is outside this session.
- **H-3 Module mocks in the service test.** `needs-you-push-service.test.ts` imports the service once at top level with `await import`. Adding `vi.mock` for `directory-client.js` or `native-provider.js` in that file affects every case in it. Prefer injecting `providers` (AC-9 case) and put the status case in the separate `needs-you-push-status.test.ts`.
- **H-4 Snapshot freshness.** `listActiveRecordsOfKind` reads a snapshot refreshed every 5 s. A phone paired a moment ago may miss one notification. Accepted (FR-9 of the epic allows 5 s).
- **H-5 Each machine pushes on its own.** A phone paired with two machines gets one notification from each machine for their own items. There is no cross-machine dedup, by design (each machine is paired separately, epic D-3).

## Non-goals

- The directory side: decoding `push`, APNs/FCM delivery, rate limiting at the directory (PAN-4830, W-CON3).
- The phone side: decrypting in the iOS Notification Service Extension or Android `FirebaseMessagingService`, the sealed-fixture generator in `tests/fixtures/phone-push/` (W-IOS1, W-AND1), Live Activity `push-activity` frames (W-IOS2).
- Changing dispatcher stats, the 6-per-minute limit, dedup, or how Web Push and ntfy send.
- Correlating directory `error` frames to push requests.
- Any change to `anywhere-boot.ts` or `directory-client.ts`.
- New HTTP routes, new config keys, or a per-phone notification list in Settings (the count only).
- The full phone-app documentation (`configuration/phone-app.mdx`, CONNECT-SERVICE and ANYWHERE-ARCHITECTURE sections) — PAN-4842 (W-DOC).
