# PAN-5604 — Stale "waiting on you" toast on page load, and toasts that never close with their question

**Issue:** [PAN-5604](https://github.com/eltmon/overdeck/issues/5604)
**Status:** draft (planned in `pan plan --auto`, 2026-11-23)
**Area:** dashboard frontend — pending-input dialogs and notifications

## Glossary

- **Pending input** — anything that blocks an agent or conversation on the operator: an
  AskUserQuestion (AUQ), a `pan ask` operator decision (delivered to the client as an AUQ whose
  `toolUseId` starts with `operator-decision:`, see `src/lib/cloister/operator-decision.ts` line 30
  `OPERATOR_DECISION_TOOL_ID_PREFIX` and `operatorDecisionAsPendingQuestion` around line 167), a
  proposed plan (ExitPlanMode), or a terminal permission prompt.
- **Agent pending input** — pending input that lives on `agentsById[<id>].pendingAskUserQuestion` /
  `.pendingProposedPlan` in the dashboard Zustand store (`src/dashboard/frontend/src/lib/store.ts`),
  read through `selectAgentsWithPendingAskUserQuestion` (line 427) and
  `selectAgentsWithPendingProposedPlan` (line 448). It arrives through the `/ws/rpc` snapshot and
  `agent.enrichment_changed` events (`packages/contracts/src/event-reducers.ts` line 396).
- **Conversation pending input** — rows from `GET /api/conversations/pending-input`, polled every 4 s
  by React Query in `usePendingInputDialogs.ts` (lines 170-179, query key
  `['conv-ask-user-question']`). This feed is always fetched live over HTTP; there is no React Query
  persister in the frontend (`grep -rn persistQueryClient src/dashboard/frontend/src` is empty).
- **Snapshot cache** — the localStorage copy of the last full `DashboardSnapshot`
  (`src/dashboard/frontend/src/lib/snapshotCache.ts`, PAN-437, key `pan-snapshot-cache-v1`).
  `saveSnapshotToCache` runs only inside the store's `syncSnapshot` action (`lib/store.ts` lines
  192-195), so events applied after a snapshot never refresh it. It can therefore hold a question that
  was answered long ago.
- **Cached phase** — the window between page load and the first successful live bootstrap. During it
  the store holds the snapshot cache (`EventRouter.tsx` lines 194-199:
  `const cached = loadSnapshotCacheEntry()` → `syncSnapshot(cached.data)` →
  `connection.markSnapshotCached(...)`).
- **Live bootstrap** — `bootstrap()` in `src/dashboard/frontend/src/components/EventRouter.tsx`
  (around lines 211-260): it awaits `getSnapshot`, then calls `syncSnapshot(snapshot)` (line 238) and
  then `connection.setStreamLive(true)` (line 245). Every live full snapshot goes through it; the
  only other `syncSnapshot(` call in EventRouter is the cache load at line 197.
- **Connection store** — `src/dashboard/frontend/src/lib/connectionState.ts` (PAN-4279), Zustand.
  `streamLive` is true after a live bootstrap and goes false again on every stream outage
  (`markStreamDown`, EventRouter line 123).
- **Agent pending-input gate** — the new tiny Zustand store `useAgentPendingInputGate` in
  `src/dashboard/frontend/src/lib/agentPendingInputGate.ts` this PRD adds. Its one field `held` is
  either a frozen copy of the agent pending-input lists (the gate is **held**) or `null` (the gate is
  **settled**). At page load it is held with empty lists. `bootstrap()` holds it immediately before
  `syncSnapshot(snapshot)` and settles it only after that bootstrap's replay has applied. Holding an
  already-held gate keeps the earlier copy.
- **Post-snapshot replay** — in `bootstrap()`, `coordinator.completeSnapshotRecovery(snapshot.sequence)`
  (`EventRouter.tsx` line 246) returns `needsReplay = true` when live events arrived while the
  snapshot was in flight (`lib/recoveryCoordinator.ts` lines 110-121); `replay(snapshot.sequence)`
  then applies the missed events and drains the deferred ones. Until it finishes, the store holds the
  snapshot without those events.
- **Notification key / tag** — the string that identifies one pending-input announcement, e.g.
  `agent::<agentId>::<toolUseId>`, `agent-plan::…`, `conv::<name>::<toolUseId>`, `conv-plan::…`,
  `conv-perm::<name>::<signature>` and the permission reminder tags `conv-perm::…::300000` /
  `::1800000`. It is used as the sonner toast id and the desktop `Notification` tag.

## Problem

Observed 2026-11-23 on [PAN-5058](https://github.com/eltmon/overdeck/issues/5058): the operator
answered `pan ask` decision `od-82901a56` from the dashboard; the server cleared it 9 s later
(`agent.enrichment_changed`, `hasPendingQuestion: 0`). Three minutes later a fresh load of
`/issues/PAN-5058` showed the toast "PAN-5058 is waiting on you — Should CP-1 …" with an **Answer**
button for about 12 s.

Two defects:

1. **Announcements (and the modal) fire on the cached snapshot.** The announce effect in
   `src/dashboard/frontend/src/App/hooks/usePendingInputDialogs.ts` (lines 311-371) treats every
   agent pending input in the store as new, and during the cached phase the store holds the stale
   snapshot cache. The same arrays (lines 62-63) feed `askUserQuestionSubjects` (line 230) and
   `planApprovalSubjects` (line 191), which open `AskUserQuestionDialog` / `PlanApprovalDialog` in
   `App/AppLiveStoreHost.tsx` (lines 93-110). `useAskUserQuestionUiStore` is not persisted, so on a
   fresh load nothing filters the stale subject out: the modal can open for an answered question too.
2. **Toasts never close when their question closes.** `showPendingInputNotification`
   (`App/hooks/usePermissionNotifications.ts` lines 13-25) shows `toast.info` with a fixed 12 s
   duration and no id, and creates a desktop `Notification` that nothing keeps. When a key leaves
   `liveKeys`, the announce effect only forgets it (`usePendingInputDialogs.ts` lines 368-370), and
   `usePermissionNotifications` only clears its reminder timers (lines 66-70). The toast and desktop
   notification stay up.

## Decisions (made in this doc)

- **D-1 Gate on recovery, not on `streamLive`.** `streamLive` flips false on every staleness
  strike and reconnect. A gate that follows it would empty the agent lists on each blip; with fix 2
  that would dismiss live toasts, close an open modal mid-answer, forget the keys and re-announce on
  reconnect. During an outage the store does not change (live events are deferred, and only
  `bootstrap()` writes a new snapshot), so the gate only needs to bracket the moment a snapshot is
  written: hold before `syncSnapshot(snapshot)`, settle after the post-snapshot replay. A stream outage
  with no bootstrap never touches the gate.
- **D-2 Held means "the last settled copy", not "empty".** While held, `useLivePendingAgentInputs`
  returns the lists captured when the gate was first held: empty lists at page load (so the snapshot
  cache never shows), and the pre-reconnect live lists during a reconnect (so already-announced keys
  are neither dismissed nor re-announced, and an open modal stays open). When the gate settles, the
  lists switch to the store and the announce effect sees one clean diff: questions answered during the
  outage close, new ones are announced, unchanged ones are untouched. The frozen copy is taken from the
  same memoized selectors the hook uses, so array identity is stable. The gate lives in its own store,
  read by a selector, so there is no `useRef` read or `setState` call during render (the React
  compiler lint stays clean) and no render loop when a test mocks the selectors with non-memoized
  functions (`App.test.tsx` lines 164-167 do exactly that).
- **D-9 Settle rules in `bootstrap()`.** Settle only when (a) no replay was needed or `replay()`
  returned `'caught-up'`, and (b) `gen === generation` (a newer bootstrap owns the gate otherwise). A
  `'too-far-behind'` replay already throws into the `catch` and retries; the gate stays held. A
  `'failed'` replay leaves the gate held too: `replay()` has called `coordinator.failRecovery()`, which
  sets `bootstrapped = false`, so every later live event is deferred and the store is frozen anyway;
  showing its pending input would only expose questions the missed events may have cleared. The next
  successful bootstrap (transport `onReconnect`, the staleness watchdog, or the Retry button through
  `requestReconnect`) settles it. That frozen-store state is pre-existing and is a non-goal here.
- **D-3 Gate the source arrays, so the modal is gated too (auto decision).** The issue asks to gate
  the announce loop. The modal reads the same arrays and has the same bug, so the gate sits on the
  two agent arrays (`agentsWithAskUserQuestion`, `agentsWithProposedPlan`): they read as one stable
  empty array at page load and as the last settled copy while the gate is held (D-2). One gate covers
  toast, desktop notification, modal and the reconcile effect (lines 535-570; reconciling against
  empty lists at page load is a no-op because the UI store starts empty).
- **D-4 Never gate conversation pending input.** Those rows come from a live HTTP poll and are never
  cached, so a conversation question may toast before the `/ws/rpc` bootstrap finishes.
- **D-5 Handles live in a module-level map.** `usePermissionNotifications.ts` keeps
  `const openDesktopNotifications = new Map<string, Notification>()`. `showPendingInputNotification`
  passes `id: tag` to `toast.info` and stores the `Notification` under `tag`. A new export
  `dismissPendingInputNotification(tag)` calls `toast.dismiss(tag)`, closes the stored notification and
  deletes the entry. Entries are also deleted on notification click and on its `onclose`. Callers
  need no per-key state of their own.
- **D-6 Permission prompts are covered.** They share `showPendingInputNotification`, so when a
  permission prompt clears, `usePermissionNotifications` dismisses its key **and** both reminder tags
  (`${key}::${after}` for each `PERMISSION_RENOTIFY_AFTER_MS` value).
- **D-7 Extract the announce effect.** Lines 311-371 move into a new hook
  `App/hooks/usePendingInputAnnouncements.ts` so it can be tested with `renderHook` and the real
  stores, without mounting `usePendingInputDialogs` (React Query, mutations, three stores).
- **D-8 A toast closes when the server clears the question**, not on the optimistic answer. In the
  incident that is 9 s after the answer. Clicking a sonner action button already closes that toast.

## Requirements

- **FR-1** Before the first live bootstrap of a page load settles, no agent pending input (AUQ, operator
  decision, proposed plan) from the snapshot cache produces a toast, a desktop notification, an
  `AskUserQuestionDialog` or a `PlanApprovalDialog`.
- **FR-2** After a live bootstrap settles, an agent pending input present in the live store is
  announced exactly once per key, whether or not it was also in the cache.
- **FR-3** *Retired in the critique revision* (it required a one-way latch, which opened before the
  post-snapshot replay). Replaced by FR-8 and FR-9.
- **FR-4** Every pending-input toast uses its notification key as the sonner toast id, and every
  desktop notification it creates is kept by key until dismissed, clicked or closed.
- **FR-5** When an agent or conversation pending-input key leaves the live set, the dashboard calls
  `toast.dismiss(key)` and closes that key's desktop notification.
- **FR-6** When a conversation permission prompt clears, the dashboard dismisses the first-sight key
  and both reminder keys (toast and desktop notification), and cancels the reminder timers (existing
  behavior kept).
- **FR-7** Conversation pending input (AUQ, plan, permission) is never gated on the agent
  pending-input gate.
- **FR-8** The gate is held from immediately before `bootstrap()` calls `syncSnapshot(snapshot)` until
  that same bootstrap's post-snapshot replay has applied (no replay needed, or `'caught-up'`) and its
  generation is still current. While held, agent pending input reads as the copy taken when the gate
  was first held (empty lists at page load).
- **FR-9** A stream outage without a bootstrap never changes the gate. A reconnect bootstrap neither
  dismisses nor re-announces a key that is pending both before and after it, and never shows a
  question that its new snapshot carries but its post-snapshot replay clears.
- **NFR-1** Tests that involve timing use `vi.useFakeTimers()` (repo rule
  `fake-timers-for-retry-tests`): with sonner mocked there is no 12 s timer to advance, so tests assert
  on `toast.dismiss(key)` and `Notification#close`, never on real time.
- **NFR-2** Every new or changed frontend test file is listed in `scripts/frontend-test-subset.txt`
  (sorted position; the file is `merge=union`), or CI never runs it.
- **NFR-3** No new `*Sync` primitives, no server changes, no change to the `/ws/rpc` contract.
- **NFR-4** `usePendingInputDialogs.ts` must not grow (file-size ratchet compares against
  `origin/main`); extraction (D-7) shrinks it.

## Critique response

### Latch opens before replay clears questions

The finding is right, and the plan now fixes it. `bootstrap()` calls `syncSnapshot(snapshot)` and
`setStreamLive(true)` (lines 238 and 245) before `completeSnapshotRecovery` decides on a replay
(line 246) and before `replay()` applies the missed events. A latch set inside `setStreamLive(true)`
therefore opened on a snapshot that could still carry a question a deferred `agent.enrichment_changed`
was about to clear. The one-way latch also left the same window open on every reconnect.

Changes made:

- The one-way `liveSnapshotLoaded` latch in `lib/connectionState.ts` is gone; FR-3 is retired. A new
  store, `lib/agentPendingInputGate.ts` (item 1, glossary, D-1, D-2, D-9, FR-8), is held immediately
  before `syncSnapshot(snapshot)` and settled only after the post-snapshot replay returns
  `'caught-up'` (or no replay was needed) and the bootstrap generation is still current. This happens
  on the first bootstrap and on every reconnect, because both go through `bootstrap()`.
- While held, `useLivePendingAgentInputs` returns the copy taken when the gate was first held: empty
  lists at page load, the pre-reconnect live lists during a reconnect (item 4, D-2, FR-9). Already
  announced keys are neither dismissed nor re-announced during recovery, and an open modal stays open.
- The tests the critique asked for are in item 5 step 5: a snapshot with a question plus a replayed
  clearing event shows no toast and an always-empty AUQ list (so no dialog subject), and a reconnect
  keeps the announced question without a dismiss or a second toast while ignoring a question its
  replay clears. Item 1 adds `EventRouter.test.tsx` cases that pin the hold and settle points,
  including the failed and too-far-behind replay outcomes.
- `lib/refresh-dashboard-state.ts` writes a live snapshot outside `bootstrap()` and is deliberately not
  gated; the reason is under Non-goals.

### Unresolved after two critic rounds

- Failed replay can hold the gate indefinitely
- A router remount replays stale cache through a settled gate
