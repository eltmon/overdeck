# PAN-2294 — Notify the flywheel orchestrator when the operator promotes/merges a UAT train

**Issue:** [PAN-2294](https://github.com/eltmon/overdeck/issues/2294)
**Mode:** `pan plan --auto` (no interactive Q&A).

## Glossary

- **UAT generation / batch** — a `uat/<codename>` git branch bundling several review+test-passed
  issues for one-click operator merge. Assembled by the reconciler (`runUatTrainReconcile`, 60s).
- **Promote** — the operator clicking **Merge** on a UAT batch. HTTP `POST
  /api/flywheel/uat-generations/:name/promote` → `postUatGenerationPromotePayload` →
  `promoteUatGeneration` (no-ff merge of the batch branch onto `main`, then per-member
  `firePostMergeLifecycle`).
- **flywheel-orchestrator** — the singleton autonomous agent (`FLYWHEEL_ORCHESTRATOR_AGENT_ID =
  'flywheel-orchestrator'`) running an Observe→Act loop, arming its next tick with
  `ScheduleWakeup(~1000s)`. It sits idle at its prompt between ticks.
- **Ready set** — the merge-ordered list of issues the flywheel has cleared to merge, emitted in
  its `activePipeline` snapshot; the UAT reconciler rebuilds batches from it.
- **messageAgent(agentId, message, caller?)** — the high-level delivery primitive
  (`src/lib/agents/messaging.ts`, re-exported from `src/lib/agents.ts`). Guards session liveness,
  waits for idle, then delivers via `deliverAgentMessage`. This is the proven mechanism
  stuck-remediation uses to poke the orchestrator (`stuck-remediation.ts:344-345`). It injects
  input into the orchestrator's tmux session, waking it immediately from its idle wait.

## Problem

On a successful promote, `postUatGenerationPromotePayload` runs `firePostMergeLifecycle` per member
but **never signals the running `flywheel-orchestrator`**. The flywheel only learns of the merge on
its next tick (~1000s later). In that window the 60s UAT reconciler rebuilds a batch from the stale
last-emitted ready set: the just-merged member may still show `shipping`, and the promote moved
`main`, re-triggering review/test on the remaining ready PRs (flipping them to `pending`). A
not-ready train pops up merge-clickable; clicking it is rejected by the PAN-1759 member-state gate
with a `member-not-ready` error. The gate is correct — the defect is that the flywheel isn't told to
immediately re-derive a clean ready set and rebuild a batch that excludes the merged + regressed
members.

## Desired behavior

On a **successful** UAT generation promote, immediately notify the running `flywheel-orchestrator`
so it re-runs its Observe→Act loop within seconds instead of after a full tick:

- Re-emit a fresh `activePipeline` ready set that drops the merged member(s).
- Re-assemble a clean batch (`assemble-uat`) containing only members currently review+test passed.
- Close out the promoted issue(s).

## Design (additive notification hook — NOT a refactor)

Reuse the existing transport; do **not** build a new one.

### New module: `src/lib/cloister/uat-promote-notify.ts`

Export `notifyFlywheelOfUatPromote(result: PromoteResult, deps?)`. All branching lives here so the
call site is one unconditional best-effort line, and every branch is unit-testable via injected deps.

Behavior (best-effort — every path swallows its own errors; a notification failure must never affect
the promote HTTP response):

1. `result.success !== true` → return (no-op). Failed promotes notify nothing.
2. `getFlywheelActiveRunId()` falsy → return. No active flywheel run means nothing consumes the
   notification.
3. `isFlywheelGloballyPaused()` truthy → return. A paused flywheel must not be poked.
4. Always `recordDeaconNudge({...})` a durable JSONL breadcrumb (machine-readable "for the
   flywheel", via existing `deacon-nudge-log.ts`) so even a promote that lands while the orchestrator
   session is momentarily dead is recorded for its next boot.
5. If `sessionExistsSync(FLYWHEEL_ORCHESTRATOR_AGENT_ID)` → `await messageAgent(FLYWHEEL_ORCHESTRATOR_AGENT_ID, <promote-nudge message>, 'uat-promote-notify')`.
   If no live session → skip delivery (breadcrumb already recorded). This satisfies "no-op safely
   when there is no live orchestrator session."

Injected deps (default to the real implementations) for testability:
`getActiveRunId`, `isPaused`, `sessionExists`, `message` (messageAgent), `recordNudge`.

**Nudge message** (promote-specific, modeled on the stuck-remediation stage-1 poke):

> `UAT batch <generation> just merged to main (members: <ids>; sha <shortSha>). Re-run your
> Observe→Act loop NOW — do NOT wait for your next scheduled tick. Re-derive and re-emit the ready
> set EXCLUDING the merged member(s), re-assemble a clean UAT batch (assemble-uat) that contains only
> members currently passing review AND test (main just moved, so some ready PRs may have regressed to
> pending), close out the merged issue(s), then re-arm your next tick with ScheduleWakeup. Do NOT ask
> the operator a question and do NOT pause.`

**recordDeaconNudge fields:** `patrol: 'uat-promote-notify'`, `issueId: <first merged member>`,
`action: 'notified flywheel-orchestrator to re-derive ready set after UAT promote'`,
`reason: 'operator promoted a UAT batch; flywheel must immediately rebuild to drop merged + regressed members before its next tick'`,
`state: { generation, members, mergeSha, delivered: <bool> }`.

### Wiring: `src/dashboard/server/services/uat-train.ts` → `postUatGenerationPromotePayload`

After `promoteUatGeneration(...)` resolves, before returning `result`:

```ts
const result = await promoteUatGeneration(name, root, { ...deps });
await notifyFlywheelOfUatPromote(result).catch(() => {}); // best-effort; never blocks the response contract
return result;
```

Awaited (not fire-and-forget) for deterministic ordering and testability; the internal idle-wait is
bounded (~5s worst case) and acceptable for a manual Merge click. The `.catch` is belt-and-suspenders
on top of the helper's own internal error swallowing.

## Decisions

- **D1 — Branching lives in the helper.** `notifyFlywheelOfUatPromote` internally no-ops on
  `!result.success` / no active run / paused, so the call site is one unconditional line and each
  branch is covered by the helper's unit test.
- **D2 — Reuse `messageAgent` + `recordDeaconNudge`, no new transport.** Directly satisfies the
  issue's "do not build a new transport" constraint and matches the proven stuck-remediation poke.
- **D3 — Always record the JSONL breadcrumb when a flywheel run is active, even if the session is
  momentarily dead.** Guarantees the merge is recoverable on the orchestrator's next boot.
- **D4 — Await the notification with a `.catch`.** Deterministic + testable; bounded latency for a
  manual click.

## Requirements

- **FR-1** On a successful promote with a live, un-paused, active-run orchestrator, deliver a nudge
  message to the `flywheel-orchestrator` tmux session via `messageAgent`.
- **FR-2** The nudge instructs the orchestrator to re-derive the ready set excluding merged members,
  re-assemble a clean UAT batch (review+test passed only), and close out the merged issue(s).
- **FR-3** No-op safely (no throw, no message) when: the promote failed, no flywheel run is active,
  the flywheel is globally paused, or no live orchestrator session exists.
- **FR-4** Record a durable JSONL breadcrumb (`recordDeaconNudge`) whenever a flywheel run is active
  on a successful promote, including when the session is dead (delivered=false).
- **FR-5** The notification is wired into `postUatGenerationPromotePayload` and never alters the
  promote HTTP response contract, whether it succeeds or throws internally.
- **NFR-1** Additive only — no change to promote/merge semantics, `PromoteResult` shape, or the
  member-state gate.

## Acceptance criteria

Map 1:1 to the beads below; all mechanically checkable via the named unit tests + typecheck.

## Out of scope (NonGoals)

- Changing the PAN-1759 promote member-state gate or the promote/merge git logic.
- Changing the 60s reconciler cadence or its batch-assembly algorithm.
- Building a new message transport, socket, or event bus.
- Notifying on any event other than a successful UAT generation promote (e.g. individual PR merges).
- Guaranteeing the orchestrator's subsequent actions succeed — this issue only guarantees the
  notification is delivered/recorded; the orchestrator's Observe→Act loop is its own responsibility.
