# PAN-4363: Refuse GPT-6 Sol and Luna launches on Codex CLIs below 0.156.1

**Issue:** [PAN-4363](https://github.com/eltmon/overdeck/issues/4363) (issue D2 of `.pan/drafts/model-routing-2026-09.md`).
**Prerequisite for:** PAN-4364 (GPT-6 `tierModels` remap). **Related:** PAN-4359, PAN-3313.
**Planned:** 2026-09-29, auto mode, against `feature/pan-4363` at `f2898591ccc`.

## Glossary

- **Codex CLI** — OpenAI's `codex` binary. Overdeck's `codex` harness runs it as a persistent `codex app-server` child.
- **ChatGPT sign-in (subscription auth)** — Codex authenticated with a ChatGPT account (`codex login`). `getProviderAuthMode(model)` (`src/lib/agents/runtime-command.ts:653`) returns `'subscription'` for OpenAI models in this case, else the configured `providerAuth.openai` or `'api-key'`. It never returns `undefined` for OpenAI.
- **Client-version floor** — the oldest Codex CLI version OpenAI's backend accepts for a model under ChatGPT sign-in. Below it, the backend answers HTTP 400 "The 'gpt-6-luna' model is not supported when using Codex with a ChatGPT account".
- **Harness policy** — `canUseHarness(harness, model, authMode)` in `src/lib/harness-policy.ts`. A sync, pure function that answers "may this combination launch?". Every spawn path ends in it.
- **Harness resolver** — `resolveHarness(input)` in `src/lib/harness-resolve.ts`. The async chokepoint every work, role, planning, resume, specialist, flywheel and conversation spawn calls before it writes agent state.
- **Policy context** — a new optional fourth argument to `canUseHarness` that carries host facts the pure policy cannot read itself. This change adds one field: `codexCliVersion`.
- **CLIProxy** — the local sidecar on port 8317 (`src/lib/cliproxy.ts`) that bridges the ChatGPT OAuth token to an Anthropic-compatible endpoint for the claude-code harness. Pinned to `CLIPROXY_RELEASE_VERSION = 'v7.3.16'` (`src/lib/cliproxy.ts:57`).

## Problem

- OpenAI's backend refuses `gpt-6-sol` and `gpt-6-luna` for ChatGPT-sign-in clients whose Codex version is below 0.155.x. `gpt-6-astra` still works on the same account. Sources: openai/codex#47784, clodex#267, pi-openai-toolkit#8/#9, litellm-mysubs#2.
- The first Codex release whose model catalog lists both ids is 0.156.1 (see `configuration/harnesses.mdx`, the "OpenAI Codex CLI" section: "The Codex CLI lists them in its model catalog from `0.156.1`").
- Overdeck's only Codex version gates are `MINIMUM_CODEX_VERSION = '0.144.0'` (app-server transport) and `MINIMUM_NATIVE_ENDPOINT_CODEX_VERSION = '0.153.4'` (native terminal attach), both in `src/lib/codex/app-server-manager.ts` (search `const MINIMUM_CODEX_VERSION`, line 16, and `export const MINIMUM_NATIVE_ENDPOINT_CODEX_VERSION`, line 22).
- So a host on Codex 0.153.4–0.156.0 passes every Overdeck check, launches a Sol or Luna agent, and the agent dies on its first turn with the 400.
- `pan doctor` shows `Codex CLI v0.153.4` as OK (`checkCodex`, `src/cli/commands/doctor.ts:95`) and says nothing about GPT-6.

## Verified facts (planning session, 2026-09-29)

1. **The backend gates on the Codex binary's version, not Overdeck's `clientInfo`.** Overdeck sends `clientInfo: { name: 'overdeck', version: this.options.clientVersion ?? '0.0.0' }` in `initialize` (`app-server-manager.ts:186-193`), and no caller sets `clientVersion`. A probe on this host (Codex CLI 0.158.0) ran `codex app-server` over stdio with exactly that `clientInfo` (overdeck/0.0.0), then `thread/start` with `gpt-6-luna` and one `turn/start`. The turn completed with the answer "ok". So `0.0.0` in `clientInfo` does not trigger the 400, and a floor on the binary version is the correct fix.
2. **CLIProxy 7.3.16 serves both models on ChatGPT sign-in.** `GET /v1/models` lists `gpt-6-luna` and `gpt-6-astra`. `POST /v1/messages` with `model: "gpt-6-luna"` returned `"text":"ok"`. `POST /v1/messages` with `model: "claude-opus-5"` (the reference install's `oauth-model-alias` for `gpt-6-sol`) returned `"model":"gpt-6-sol"`, `"text":"ok"`. So the CLIProxy route needs no pin bump; issue work item 4 reduces to recording the verified version.
3. **`POST /v1/messages` with `model: "gpt-6-sol"` returned "unknown provider for model gpt-6-sol"** on the reference install. The cause is operator config, not a version gate: `~/.overdeck/cliproxy/config.extra.yaml` aliases `gpt-6-sol` (and `gpt-5.6-luna`, `gpt-5.6-terra`) to Claude ids, and CLIProxy then hides the upstream id (none of those three appear in `/v1/models`). This matters to PAN-4364, not here. See hazard H3.
4. **`pan install` does not install or upgrade the Codex CLI.** The only Codex install instruction in the code is the copyable hint `npm install -g @openai/codex` in `src/lib/system-prerequisites.ts:183-192`, whose module header says "Install hints are copyable commands, not actions — installing system packages needs sudo/user consent, so Overdeck never runs them itself." See decision D2.
5. `resolveHarness` runs before the first agent-state write in `spawnAgentWithoutConsentClaim` (`src/lib/agents/spawn.ts:680` `resolveHarness(`, then `saveAgentStateSync(state)` at `:715`). The OpenAI provider's built-in harness is `codex` (`src/lib/providers.ts:134` `defaultHarness: 'codex'`), so a policy denial in `resolveHarness` throws `HarnessResolutionError` instead of falling back to claude-code (`harness-resolve.ts:104-121`).
6. `pan start --harness codex --model <m>` checks the policy in `resolveExplicitHarnessFlag` (`src/cli/commands/start.ts:152-176`) and calls `exitCli(1)` on a denial. It runs at `start.ts:736`, before any workspace or agent work.

## Decisions

- **D1 — Where the rule lives.** The rule lives in `canUseHarness` (harness policy), which stays sync and pure. It gains an optional fourth argument `context?: HarnessPolicyContext` (`{ codexCliVersion?: string }`). Async callers that are about to launch (`resolveHarness`, `resolveExplicitHarnessFlag`) read the version and pass it. Sync callers (pickers, tier validation, the settings harness-policy route) pass nothing, and the rule does not fire for them. They all reach `resolveHarness` before a launch, so the gate still holds.
- **D2 — The error names the real upgrade command, not `pan install`.** The issue text says the error "includes the upgrade command (`pan install`)". `pan install` does not touch the Codex CLI (verified fact 4), and extending it would break the rule stated in `system-prerequisites.ts` that Overdeck never runs system package installs. So the refusal names the required version and `npm install -g @openai/codex`, the command the prerequisites checklist already shows. The string becomes one exported constant, `CODEX_CLI_INSTALL_COMMAND`, which the prerequisites entry also uses. This adds an import edge from `system-prerequisites.ts` into `app-server-manager.ts`; there is no cycle and both are Node-only. If review objects to that coupling, the fallback is to leave `system-prerequisites.ts` untouched and accept the constant as one more copy of the literal.
- **D2a — The flagless path.** `pan start <id> --model gpt-6-luna` without `--harness` skips `resolveExplicitHarnessFlag` (it returns early when `harness` is undefined). That launch is refused later, inside `spawnAgent`'s `resolveHarness`, through the existing `HarnessResolutionError` path. The refusal still comes before any agent row (`spawn.ts:680` before `:715`), but after workspace creation. The issue's acceptance criterion uses the explicit `--harness codex` flag, which WI-4 refuses before any workspace work.
- **D3 — The rule applies only under ChatGPT sign-in.** It fires only when `authMode === 'subscription'`. API-key users are never refused, because the 400 is specific to ChatGPT accounts.
- **D4 — An unreadable version fails open.** When `codex --version` cannot be run or parsed, the resolver passes no version, the policy allows the launch, and the app-server's own `assertSupportedVersion` (`app-server-manager.ts:454`) keeps failing loudly as it does today. `pan doctor` reports a WARN "version unknown" row. Failing closed on a flaky probe would block every GPT-6 launch.
- **D5 — The version is read fresh on every launch.** The dashboard is long-lived. An operator who upgrades Codex must not stay refused until a restart. `codex --version` takes milliseconds. The reader does not cache, unlike `hasHarnessBinary`.
- **D6 — Exact model ids.** The table has exactly `gpt-6-sol` and `gpt-6-luna`, each mapped to `0.156.1`. No bracketed context-window variants of these ids exist in `PROVIDERS.openai.models` (`providers.ts:135`). `gpt-6-astra` is not in the table.
- **D7 — Doctor severity is WARN.** No "enabled model" setting exists in Overdeck, and Sol and Luna are documented as opt-in. `pan doctor` exits 1 on any error row (`doctor.ts:1014`, `hasErrors`). So doctor emits one row per table entry: OK when the floor is met or auth is API-key, WARN when Codex is below the floor under ChatGPT sign-in, WARN when the version is unknown. It emits no rows when Codex is not installed, because `checkCodex` already warns about that. The launch-time refusal is the hard stop.
- **D8 — The version probe uses the resolver's binary.** `resolveCodexPolicyContext` resolves the binary with `resolveHarnessBinary('codex', configuredHarnessBinaryPath('codex') ? { executablePath } : undefined)`, the same call `hasHarnessBinary` makes (`harness-resolve.ts:45-61`). So the version it reads is the binary the availability check approved.
- **D9 — CLIProxy.** No pin change. A comment beside `CLIPROXY_RELEASE_VERSION` records that 7.3.16 was verified to serve `gpt-6-sol` and `gpt-6-luna` on ChatGPT sign-in on 2026-09-29. The docs record the same fact.

## Requirements

- **FR-1** — `src/lib/codex/app-server-manager.ts` exports a per-model floor table `CODEX_MODEL_MINIMUM_VERSIONS` with `gpt-6-sol` and `gpt-6-luna` mapped to `'0.156.1'`, and a lookup `codexModelMinimumVersion(model)` that returns `undefined` for every other id.
- **FR-2** — `canUseHarness('codex', model, 'subscription', { codexCliVersion })` returns `{ allowed: false, reason }` when the model has a floor and `compareVersions(codexCliVersion, floor) < 0`. The reason names the model, the installed version, the required version, and `npm install -g @openai/codex`.
- **FR-3** — `canUseHarness` returns the pre-change decision when `context` is absent, when `codexCliVersion` is absent, when `authMode` is not `'subscription'`, when the harness is not `codex`, or when the model has no floor.
- **FR-4** — `resolveHarness` passes the policy context to `canUseHarness`, so every spawn path that calls it (work, role runs, planning, resume, specialists, flywheel, conversations) refuses a below-floor Sol or Luna launch with a `HarnessResolutionError` before any agent state is written.
- **FR-5** — `pan start <id> --model gpt-6-luna --harness codex` on a host whose Codex CLI is 0.153.4 under ChatGPT sign-in exits 1, prints the FR-2 reason to stderr, and calls neither workspace creation nor `spawnAgent`.
- **FR-6** — `pan doctor` prints one `Codex model floor` row per table entry, with the severities in D7.
- **FR-7** — `configuration/harnesses.mdx` states the floor, the refusal behavior, the upgrade command, and the verified CLIProxy version.
- **NFR-1** — `canUseHarness` stays synchronous and performs no I/O.
- **NFR-2** — No server-reachable code gains `execSync`. The new version reader uses `execFile` promisified, with a timeout.
- **NFR-3** — The refusal never substitutes another model or another harness.

/** PAN-4363: ChatGPT sign-in refuses some models below a Codex CLI version. */
function codexModelFloorDecision(
  model: string,
  authMode: AuthMode | undefined,
  context: HarnessPolicyContext | undefined,
): HarnessPolicyDecision {
  const installed = context?.codexCliVersion
  const floor = codexModelMinimumVersion(model)
  if (authMode !== 'subscription' || !installed || !floor || compareVersions(installed, floor) >= 0) {
    return ALLOWED
  }
  return {
    allowed: false,
    reason:
      `${model} needs Codex CLI ${floor} or newer under ChatGPT sign-in; this host has ${installed}, and OpenAI rejects the model with HTTP 400 below that version. ` +
      `Upgrade with \`${CODEX_CLI_INSTALL_COMMAND}\`, then check \`codex --version\`, or pick a different model.`,
  }
}
