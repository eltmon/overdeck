## Glossary

| Term | Definition |
| --- | --- |
| **Share** | One act of sharing: a host exposes a **share scope** to invited viewers via a link. Identified by a room. |
| **Share scope** | What is being shared. v0 supports exactly one kind: a single conversation (`{ kind: 'conversation', id }`). The type is a discriminated union so a future `{ kind: 'task', id }` (a PAN-2565 multi-agent task) is additive. |
| **Stream** | One agent session's event sequence inside a share. A v0 conversation share has exactly **one** stream. Every content envelope carries a `streamId` from day one so multi-stream shares are a data change, not a format change. |
| **Room** | The share-service record for one share (one `ShareRoom` Durable Object): membership, lobby, block list, controller. Holds no content. |
| **Data owner** | The machine that owns the shared conversation (JSONL, tmux session) and acts as the WebRTC hub. Fixed for the life of the share. |
| **Controller** | The participant currently driving: admits/kicks/revokes, picks and sends prompt drafts, grants contributor. Exactly one at a time; transferable; the data owner can always reclaim it. |
| **Viewer** | An admitted participant. Renders the share in their own local Overdeck dashboard. View-only unless granted contributor. |
| **Contributor** | A viewer holding the **direct-submit** grant: their prompts post straight to the conversation without controller approval. Not the controller. |
| **Lobby** | The waiting room between GitHub authentication and host admission. A lobby occupant receives zero content. |
| **Share service** (rev 2: "share service") | New Cloudflare Worker at `https://share.overdeck.ai`, source `services/share/`. It holds the room registry, the lobby and admission state, the SDP/ICE relay and TURN credential issuance. It never sees content. Slice 1 (this issue). |
| **Room Durable Object** | The `ShareRoom` Durable Object class. Each room is one instance, addressed by `idFromName(shortCode)`. It holds the room record in its storage and every room WebSocket (hibernation API). |
| **Room record** | The persisted state of one room: scope, data owner, controller, participants (lobby/admitted, contributor, connected), block list, host token hash, host-connected flag, and status (`active` or `ended`). |
| **Room snapshot** | The room record minus secrets (`RoomSnapshot` in `@overdeck/contracts`). The share service sends it to the host after every change. Viewers never receive it. |
| **Short code** | The 8-character `/s/<code>` segment, drawn from `BCDFGHJKLMNPQRSTVWXZ23456789`. It routes a joiner to a room's lobby and grants nothing. |
| **Host token** | `odh_` + 64 lowercase hex characters, minted at room creation and returned once to the host. The room stores only its SHA-256 hash. It authenticates the host WebSocket and `DELETE`. |
| **Device token** | A PAN-4293 account-service token (`odd_…`), held server-side by a local Overdeck (PAN-4330). The share Worker verifies it with `env.ACCOUNT.verifyDevice(token)`. It replaces the rev-2 identity JWT. |
| **Account service** | PAN-4293's Cloudflare Worker at `https://account.overdeck.ai` (`services/account/`). The share Worker reaches it only through the `ACCOUNT` service binding (entrypoint `AccountRpc`). |
| **Reducer** | `services/share/src/room-state.ts`: a pure function `(room, event, now) → { room, effects }`. All room rules live here, so tests inject the clock and never sleep. |
| **Wire format** | The scoped, versioned schema (in `@overdeck/contracts`) for everything crossing host→viewer data channels. Deliberately NOT the internal `PanRpcGroup`/`ChatMessage` types. |

## Problem

Overdeck is a bundled local client/server app — every user runs the dashboard on their own
localhost, and the conversation data, the Claude Code JSONL session, and the tmux session all
live on that one machine behind that user's NAT. There is no way for two people on a refinement
call to look at the same conversation, watch the same investigation unfold, or collaboratively
shape a prompt. The natural model — "give somebody a link" — does not work: the link would point
at a machine the recipient cannot route to.

The killer use case: a refinement call where one person drives a codebase investigation in
Overdeck and the rest of the team watches live, suggests prompts, and collaboratively converges
on the right next step.

## Goal

Let an Overdeck host share **one conversation** with other Overdeck users via an
`overdeck.ai/s/<id>` link. Viewers render that conversation live in their own local
Overdeck dashboard. Delivered as:

1. A new **share service** on Cloudflare at `share.overdeck.ai` (rooms, lobby, WebRTC handshake relay, TURN credentials), using PAN-4293 for identity.
2. A **host-side WebRTC transport** in the dashboard server, hub for N viewers.
3. A **viewer-side** shared-conversation surface in the dashboard frontend (browser-native WebRTC).
4. **Invite-only access control**: host-approval lobby, admit / kick / revoke, per-session block list.
5. **Host role & handoff**, **link lifecycle**, **disconnect/reconnect resilience**.
6. **Input model**: live prompt-suggestion drafts + an opt-in direct-submit (contributor) permission.
7. **Two first-class clients**: dashboard and CLI (`pan share`, `pan join`).

This PRD describes all of **Shared Sessions v0**. Rev 3 delivers it as eleven vertical slices
(see *Slice map*). PAN-658 is slice 1. Each slice is complete and reviewable on its own, and the
feature is complete when all eleven have merged.

## Operator decisions

Auto planning cannot ask the operator. These three choices conflict with the operator's stated goal or with
earlier comments, so each has a recorded default that the operator can overturn. No slice-1 code
depends on OD-1 or OD-2, so overturning them later costs no rework here.

**OD-1 — install-required vs hosted web join.** Operator goal (2026-10-02, verbatim): "the operator
can give someone a link to a conversation and that person can join it and talk with the AI
directly." Rev 2 requires the joiner to have Overdeck installed, and excludes a hosted web view
because "it would put conversation content on overdeck.ai". That reason holds only for a
server-rendered view. A static page on `share.overdeck.ai` that runs the same browser
`RTCPeerConnection` viewer keeps content peer-to-peer: the Worker serves only the page and the
signaling relay. The real gap is sign-in. The account service supports PKCE with a loopback
redirect (which needs a local dashboard) and device flow. It has no browser web-session flow, so a
hosted join needs a new PAN-4293 flow plus a browser-authenticated viewer WebSocket.
**Default: install-required for v0**, with the hosted join filed as
[PAN-4481](https://github.com/eltmon/overdeck/issues/4481) for the operator to approve or reject.
"Talk with the AI directly" maps to the contributor grant (FR-8). Slice 2 makes **Admit as
contributor** a one-click lobby action, and slice 1 supports it with `admit` + `contributor: true`
in a single frame.

**OD-2 — allowlist collision.** The PAN-4293 account service is invite-only until billing exists.
A GitHub account that is not allowlisted cannot sign in, so it can never get a device token. In
practice, "give someone a link" works only after the operator adds that person on
`account.overdeck.ai/admin`. **Default: viewers must be allowlisted accounts**, which is consistent
with the invite-only phase. The share Worker requires `verifyDevice` → `ok: true`. The alternative
is an identity-only `participant` grant class in PAN-4293 (sign-in allowed, no paid entitlement);
that is a PAN-4293 change and needs the operator's call. This default most directly contradicts the
operator's verbatim goal. Raised on PAN-4293.

**OD-3 — transport.** The PAN-2350 comment (2026-07-04) recommended plain WSS rooms over the
PAN-2356 relay as v0. The operator comment of 2026-10-02 specifies a Durable Object doing "SDP/ICE
relay over WebSocket hibernation" plus "Cloudflare's managed TURN service". **The newer comment
wins: the transport is WebRTC DataChannels.** PAN-2356 is not built, and the share Worker does not
depend on it.

## Rev-3 design decisions

- **D-R3-1 — no identity JWT.** In rev 2, the signaling service minted the JWT, and the same
  service relayed the SDP that carries the DTLS fingerprints. So the JWT never protected against a
  malicious signaling service; it only added a key pair and a JWKS endpoint. In rev 3, the Worker
  verifies the device token and sends the verified identity to the host over the host's
  authenticated WebSocket. The trust root is the same, and there is one fewer secret.
- **D-R3-2 — only local Overdeck servers hold credentials.** Both the host WebSocket (host token)
  and the viewer WebSocket (device token) are opened by a local Overdeck **server** with an
  `Authorization` header, never by a browser. PAN-4330 keeps device tokens out of browsers. The
  viewer's browser gets SDP and ICE from its own local server (slice 4).
- **D-R3-3 — the share service is the room authority; the data owner is the control authority.**
  Admission-changing frames (admit, kick, revoke, un-revoke, contributor, controller, end) are
  accepted **only on the host WebSocket**. The data owner's server relays a viewer-controller's
  commands after checking `controllerGithubId` (slice 7). This matches the issue: "the data-owner
  machine stays the hub and the authority".
- **D-R3-4 — join URL host `share.overdeck.ai`.** The `overdeck.ai` apex is served by Vercel (see
  `docs/ACCOUNT-SERVICE.md` on the PAN-4293 branch: "the apex stays on Vercel"), so a Worker cannot
  own `overdeck.ai/s/*`. `joinUrl` is built from the `PUBLIC_BASE_URL` var, so moving it later is
  a config change. A Vercel redirect `overdeck.ai/s/:code → share.overdeck.ai/s/:code` is an
  optional ops step for the operator.
- **D-R3-5 — `githubLogin` required.** The lobby must show a handle so the controller knows whom
  they are admitting. PAN-4293's `VerifyResult` currently lacks `githubLogin`, and the request is
  posted on PAN-4293. Until the field exists, the Worker answers 503 `account_service_outdated`; it
  never shows an unnamed joiner. The avatar URL is derived:
  `https://avatars.githubusercontent.com/u/<githubId>`.
- **D-R3-6 — TURN credential TTL 3600 s, requested over the WebSocket.** The host can request ICE
  servers at any time; a viewer only once admitted, so lobby occupants cannot consume TURN.
  Clients ask again on renegotiation. This replaces rev 2's `POST /api/turn-credentials`.
- **D-R3-7 — slice 1 uses string error codes, like PAN-4293.** The Worker is its own deployable
  with no `src/lib` imports. New `src/lib/errors.ts` tags (rev 2 *New Error Types*) belong to the
  host slices (2–3) that throw them.
- **D-R3-8 — protocol types are type-only and import-free.** `packages/contracts/src/sharing.ts`
  contains only `type`/`interface` declarations and no `import`. The Worker imports it with a
  relative `import type` (`../../../packages/contracts/src/sharing.ts`), so `typecheck:share` does
  not depend on `build:contracts` and the Worker bundle gains no runtime code. Runtime validation
  of untrusted frames lives in `services/share/src/protocol.ts`.

## Requirements

Functional requirements. Work items reference these via their **Traces** line.

- **FR-1** A host can create a share for one conversation and receive a `https://share.overdeck.ai/s/<shortCode>` link (rev 3, D-R3-4; dashboard action and `pan share <conversationId>`).
- **FR-2** A link recipient authenticates with GitHub through the PAN-4293 account service (PKCE loopback from the dashboard, or device flow for the CLI, both via PAN-4330) before reaching the lobby. The share service accepts only a device token that `verifyDevice` reports `ok: true`.
- **FR-3** No participant receives any conversation/draft/terminal/presence content before the controller admits them from the lobby. Link possession alone grants nothing.
- **FR-4** The controller can admit, kick (soft — re-lobby-able), revoke (hard — per-room block list), and un-revoke participants, and can revoke the entire link.
- **FR-5** An admitted viewer's local dashboard renders the shared conversation live, including full-history backfill on join.
- **FR-6** Presence shows GitHub avatar + handle of every participant, marking the controller and the host.
- **FR-7** Viewers compose prompt drafts that sync live (keystroke-level snapshots) to all participants; the controller sees a stacked list and can pick, optionally edit, and send one.
- **FR-8** The controller can grant/revoke **direct-submit** per viewer; a contributor's prompts post directly to the conversation.
- **FR-9** A viewer can toggle to a **read-only** terminal view of the host's tmux session; viewer keystrokes structurally cannot reach the host shell.
- **FR-10** The controller role is transferable to any admitted viewer; the data owner can reclaim it unilaterally; exactly one controller at a time.
- **FR-11** Link lifetime = conversation lifetime (no fixed-duration expiry); the link dies when the host ends the share; manual whole-link revoke is always available.
- **FR-12** After a host network drop or `pan` restart, admitted viewers auto-restore without re-admission if the host returns within 5 minutes; past the window the room tears down and re-joining goes through the lobby.
- **FR-13** `pan join <link-or-code>` authenticates via device flow, auto-starts the local dashboard if needed, and lands the user in the lobby.
- **FR-14** Concurrent contributor submissions are strict-FIFO queued; submissions arriving while the agent is mid-turn are queued and flushed at turn end; a "composing / agent is working" indicator is shown. (Resolves the issue's open question with its stated lean.)

Non-functional requirements:

- **NFR-1** Content (conversation, drafts, terminal bytes) never transits the share service — peer-to-peer DataChannels only, TURN relay at most. Verified by an e2e test instrumenting the signaling WS.
- **NFR-2** Everything crossing a data channel uses the scoped, versioned wire format from `@overdeck/contracts` — never internal RPC types. Version skew between host and viewer degrades gracefully (notice, not breakage).
- **NFR-3** Every content envelope carries a `streamId`; the share scope is a discriminated union — extending to multi-stream task shares (PAN-2565) must require **no breaking wire change and no schema migration rewrite** (see *Forward compatibility*).
- **NFR-4** The host's WebRTC hub gates content on its **own** admitted set — the share service is never the sole authority for content access.
- **NFR-5** Viewers require no native dependency (browser-native `RTCPeerConnection`); the host-side WebRTC dependency must not break `bun run` dev mode unless a native addon is unavoidable (prefer pure-TS `werift`).
- **NFR-6** The host dashboard itself remains localhost-only; sharing exposes only the shared scope's channels, only to admitted peers.
- **NFR-7** Works through symmetric NATs via Cloudflare Realtime TURN, with short-lived credentials (TTL 3600 s) issued by the share service only to the host and admitted viewers (rev 3; was `coturn`).
- **NFR-8** The share service is a Cloudflare Worker that uses Web APIs only; `cloudflare:workers` is imported only in `services/share/src/index.ts`. Agents may run `wrangler dev --local` and `wrangler deploy --dry-run` and nothing else. Deploying is operator-only.
- **NFR-9** Room rules are a pure reducer with an injected clock. The 5-minute reconnect window is tested by passing `now`, never by sleeping (repo fake-timers rule).

## Design Goals

- **Invite-only is non-negotiable.** Possession of a link never, by itself, grants access.
- **Content stays peer-to-peer.** The share service relays handshake + membership only.
- **The viewer needs no native dependency.** The host's Node server is the WebRTC hub; viewers connect with browser-native WebRTC.
- **Survive a host blip.** A wifi drop or a `pan` restart inside a 5-minute window does not end the session or force re-admission.
- **Two clients, one access model.** Dashboard and CLI both share and join; both funnel through the same lobby. The CLI is not a back door.
- **Defense in depth.** The host's WebRTC peer independently gates content on its own admitted set.
- **Don't box in the roadmap.** The share model must extend to multi-agent tasks (PAN-2565) and inform the collaborative-editing followup without a rewrite (see *Forward compatibility*).

## Forward compatibility — multi-agent tasks and the parity roadmap

[PAN-2565](https://github.com/eltmon/overdeck/issues/2565) introduces task surfaces containing
**N agent sessions**. Sharing such a task is a followup to both issues — but v0 decisions here
must not force a rewrite there. Four commitments, all cheap now and expensive later:

1. **Share scope is a discriminated union.** Everywhere the design says "what is shared", the
   type is `ShareScope = { kind: 'conversation'; conversationId: string }` — v0's only variant.
   A future `{ kind: 'task'; taskId: string }` is an additive variant. The share service
   treats the scope as opaque (it already never inspects content); only host and viewer interpret it.
2. **Every content envelope carries `streamId` from day one.** A v0 conversation share has
   exactly one stream (`streamId` = the conversation id). Multi-stream shares later reuse the
   same five channel labels — the envelope, not the channel, identifies the member session.
   Late-added streams announce themselves via the `presence` channel (`streams` array), so a
   viewer can render per-stream tabs without new channels.
3. **Host persistence is keyed by room, not by conversation.** (Rev 3: a 0600 JSON file, `${OVERDECK_HOME}/shared-sessions.json`, replaces the rev-2 `shared_sessions` table; see *Data Model*. The keying rule is unchanged.) Primary key `room_id`, with
   `scope_kind` + `scope_id` columns and a uniqueness constraint on `(scope_kind, scope_id, status='active')`
   semantics (enforced in code: one active share per scope). Adding task shares is a new
   `scope_kind` value, not a table rewrite.
4. **Version negotiation advertises supported scope kinds.** The connect handshake exchanges
   `{ v, scopeKinds: ['conversation'] }`. A future host offering a task share to an old viewer
   detects the gap and shows "viewer's Overdeck is too old for task shares" instead of breaking.

Also anticipated (no code impact in v0, recorded so the design stays honest):

- **Collaborative editing (PAN-659 lineage / PAN-2566 §3–4):** the `drafts` channel's
  last-write-wins snapshots are explicitly a v0 simplification. If CRDT co-editing lands later,
  it rides a **new channel** (`collab`) rather than mutating `drafts` semantics.
- **Persistent roles (PAN-2566 §4):** the lobby/admit model is deliberately session-scoped. If
  durable multi-user projects arrive, they are a different authorization layer on top; nothing in
  the room model assumes membership outlives the room.

### WebRTC dependency (decided at the start of slice 3, PAN-4474)

| Option | Type | Trade-off |
|---|---|---|
| `werift` | **Pure TypeScript** WebRTC | No native addon — eliminates build/runtime risk. Preferred if data-channel support is adequate (it is data-channel-first). |
| `@roamhq/wrtc` | Native Node addon | Battle-tested, but native-addon finickiness (same class as `node-pty`). Node 22 only; breaks under Bun. |

**Decision rule:** evaluate `werift` first with a two-peer data-channel spike (loopback + forced-TURN);
adopt it if the spike passes throughput ≥ 5 MB/s and 1k-message ordering. Fall back to `@roamhq/wrtc`
only on spike failure. If the native addon is chosen: externalize it in the server `tsdown.config.ts`
bundle, add it to `sync-sources/rules/dashboard-node22-only.md`, and document that sharing requires the
built `dist/dashboard/server.js` under Node 22. The viewer side uses browser-native
`RTCPeerConnection` either way.

## Architecture

### Components

```
   HOST machine            share.overdeck.ai (Cloudflare)          VIEWER machine
 ┌─────────────────┐     ┌──────────────────────────────┐     ┌─────────────────────┐
 │ dashboard server │ WSS │ Worker overdeck-share        │ WSS │ dashboard server    │
 │  (Node 22)       │◄───►│  ShareRoom Durable Object    │◄───►│  (holds device token│
 │  - conversation  │host │   (lobby, admission, SDP/ICE │join │   relays SDP to its │
 │  - tmux session  │token│    relay, 5-min alarm)       │token│   browser)          │
 │  - WebRTC hub    │     │  ──ACCOUNT binding──► account│     │ dashboard frontend  │
 │                  │     │  ──fetch──► Realtime TURN API│     │  - RTCPeerConnection│
 │                  │     └──────────────────────────────┘     └──────────┬──────────┘
 │       └──────────┼──── WebRTC DataChannels (DTLS) ─────────────────────┘
 └─────────────────┘   STUN-direct, or relayed by Cloudflare Realtime TURN
```

- **Host** — the machine that owns the conversation + tmux session. Its dashboard **server** is
  the WebRTC hub: one `RTCPeerConnection` per viewer. Source of truth.
- **Viewer** — runs their own Overdeck. The **browser** frontend holds one `RTCPeerConnection`
  to the host server and renders the share. The viewer's local **server** holds the viewer's
  device token, opens the `/join` WebSocket to the share service, and relays SDP/ICE to its own
  browser (D-R3-2). It also receives the join intent and opens the frontend route.
- **Share service** (`share.overdeck.ai`, slice 1) — Cloudflare Worker + `ShareRoom` Durable
  Object: rooms, lobby, admission, SDP/ICE relay, TURN credential issuance. Identity comes from the
  PAN-4293 account service through a service binding. **Never sees content.**
- **TURN** — Cloudflare Realtime TURN (managed) for peer pairs that cannot NAT-traverse directly.

### Two-role decomposition of "host"

| Role | What it is | Mobility |
|---|---|---|
| **Data owner** | The machine with the conversation + tmux session; the WebRTC hub. | Fixed for the share. The conversation does not migrate machines in v0. |
| **Controller** | The participant who *drives*: admit/kick/revoke, pick/send prompts, grant contributor, hand off. | Transferable to any admitted viewer; the data owner can always reclaim it. Exactly one at a time. |

"Host" is modeled as a **role on the room**, not a property of a connection.

### Why the hub is the host's server, not the host's browser

- The conversation source of truth, the JSONL session, and the tmux session all live in the
  host's Node server. Terminal sharing (`node-pty tmux attach-session`) originates there.
- The host's browser tab is ephemeral; the server is always-on under `pan up`. A host closing or
  refreshing a tab must not drop every viewer.
- Disconnect/reconnect resilience (5-minute window, survives `pan` restart) only makes sense with
  a long-lived server peer.

### Reuse: the terminal-sharing primitive

`src/dashboard/server/pty-hub.ts` already implements a multi-client hub — `activePtyHubs`,
`addClientToHub`, `broadcastToHub`, and a single designated `inputClient` — consumed by
`src/dashboard/server/ws-terminal.ts` (one `node-pty tmux attach-session` per session, N clients).
v0 adds a **WebRTC DataChannel consumer** of that same hub's byte stream — the PTY plumbing is
unchanged; the terminal data channel is just another subscriber alongside the raw-WebSocket clients.

### Identity (`src/account.ts`)

```ts
export type AccountVerifyResult =
  | { ok: true; userId: string; githubId: number; githubLogin?: string; deviceId: string }
  | { ok: false; error: 'invalid_token' | 'device_revoked' | 'grant_expired' | 'account_deleted' };
export interface AccountBinding { verifyDevice(token: string): Promise<AccountVerifyResult> }

  Promise<{ ok: true; identity: ShareIdentity } | { ok: false; status: 401 | 403 | 503; error: string }>;
```

Rules, in this order:
1. The header is not `Bearer odd_<64 hex>` → 401 `invalid_token`. Do not call the binding.
2. `verifyDevice` throws → 503 `account_unavailable`.
3. `ok: false` with `grant_expired` → 403. Any other error → 401 with that error code.
4. `ok: true` without a non-empty `githubLogin` → 503 `account_service_outdated` (D-R3-5).
5. Otherwise return `{ githubId, login: githubLogin, avatarUrl: 'https://avatars.githubusercontent.com/u/' + githubId }`.

### HTTP API (`src/routes.ts`)

Every response carries `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. JSON
request bodies over 16 KiB → 413. An unknown path → 404 `{"error":"not_found"}`. A wrong method →
405 with an `Allow` header.

| Method & path | Auth | Behavior |
| --- | --- | --- |
| `GET /healthz` | — | 200 `{"ok":true,"configured":<bool>,"turn":<bool>}` |
| `POST /v1/rooms` | `Bearer odd_…` | Body `CreateRoomRequest`. Verify the identity. Apply rate limit `ROOM_CREATE_LIMIT.limit({ key: String(githubId) })`; failure → 429 `{"error":"rate_limited"}` with `Retry-After: 60`. Validate the scope (`kind === 'conversation'`; `conversationId` is 1–200 characters with no control characters) → else 400 `invalid_request`. Generate a short code and a host token. Call DO `init` with `{ shortCode, scope, dataOwner: identity, hostTokenHash, createdAt }`. On DO 409 (the code exists), retry with a fresh code up to 3 times, then 503 `code_space_exhausted`. Return 201 `CreateRoomResponse`. |
| `DELETE /v1/rooms/:code` | `Bearer odh_…` | Normalize the code (uppercase; strip spaces and dashes). Forward to DO `delete` with the host-token hash. 204 on success; 404 `not_found` for an unknown code, an ended room **or** a wrong token (no oracle). |
| `GET /v1/rooms/:code/host` | `Bearer odh_…`, `Upgrade: websocket`, `?v=1` | A missing upgrade header → 426. `v` ≠ `1` → 400 `unsupported_protocol`. Forward to DO `host` with the token hash. The DO answers 404 for an unknown or ended room or a wrong token, else 101. |
| `GET /v1/rooms/:code/join` | `Bearer odd_…`, `Upgrade: websocket`, `?v=1` | Same upgrade and version checks. Verify the identity, then forward to DO `join` with `X-Share-Identity`. The DO answers 404 for an unknown or ended room, else 101. Blocked and other refusals are delivered **after** the upgrade, as a close code, so the local server shows a reason. |
| `GET /s/:code` | — | Landing HTML (`pages.ts`). Active room → 200 page: "You were invited to a shared Overdeck conversation", the command `pan join <CODE>`, and a link to install docs. No host name, scope, participant count or any room data. Unknown or ended → 404 page "This share link has ended or does not exist." The CSP header is the PAN-4293 HTML header (`default-src 'none'; style-src 'unsafe-inline'; frame-ancestors 'none'; base-uri 'none'`). Slice 4 later adds the localhost-detect script. |

`CreateRoomResponse = { shortCode, hostToken, joinUrl: PUBLIC_BASE_URL + '/s/' + shortCode, snapshot: RoomSnapshot }`.

### Codes (`src/codes.ts`)

- `SHORT_CODE_ALPHABET = 'BCDFGHJKLMNPQRSTVWXZ23456789'` (28 symbols; no vowels, so no words; no
  0/O/1/I). `newShortCode(deps)` draws 8 symbols by rejection sampling over random bytes:
  discard bytes ≥ 252 (= 28 × 9), so the distribution is uniform. `normalizeShortCode(input)`
  uppercases, strips spaces and dashes, and returns `null` unless the result is exactly 8
  alphabet symbols.
- `newHostToken(deps)` returns `'odh_' + hex(randomBytes(32))`.
- `sha256Hex(s)` uses `crypto.subtle.digest('SHA-256', …)`. `timingSafeEqualHex(a, b)` compares
  equal-length strings in constant time.

### Frame decoding (`src/protocol.ts`)

`decodeHostFrame(raw: string | ArrayBuffer)` and `decodeViewerFrame(raw)` return
`{ ok: true, frame } | { ok: false, code: 'invalid_frame' | 'frame_too_large' }`.
- Binary frames → `invalid_frame`. A string over **64 KiB** (65,536 UTF-16 code units) →
  `frame_too_large`. JSON parse failure, or a non-object → `invalid_frame`.
- `type` must be one of the frame's union members. Every listed field must have its exact
  primitive type; `githubId` must be a positive safe integer. **Unknown extra fields are
  dropped**: the decoder builds a new object from known keys only, so nothing unlisted is ever
  forwarded.
- `SignalData` must contain `sdp` or `candidate` or both; `sdp.sdp` ≤ 32 KiB;
  `candidate.candidate` ≤ 2 KiB.

### Room rules (`src/room-state.ts`, the reducer)

```ts
export const HOST_RECONNECT_WINDOW_MS = 300_000;
export const MAX_PARTICIPANTS = 50;   // lobby + admitted
export const MAX_LOBBY = 20;
export interface ParticipantRecord { identity: ShareIdentity; state: 'lobby' | 'admitted'; contributor: boolean; connected: boolean; joinedAt: number }
export interface RoomRecord {
  v: 1; shortCode: string; scope: ShareScope; hostTokenHash: string;
  dataOwner: ShareIdentity; controllerGithubId: number;
  status: 'active' | 'ended';
  hostConnected: boolean; hostDisconnectedAt: number | null;
  participants: Record<string, ParticipantRecord>;   // key = String(githubId)
  blocked: Record<string, ShareIdentity>;
  createdAt: number;
}
export type RoomEvent =
  | { kind: 'host-connected' } | { kind: 'host-disconnected' }
  | { kind: 'viewer-connected'; identity: ShareIdentity }
  | { kind: 'viewer-disconnected'; githubId: number }
  | { kind: 'viewer-frame'; githubId: number; frame: ViewerFrame }
  | { kind: 'host-frame'; frame: HostFrame }
  | { kind: 'alarm' } | { kind: 'delete' };
export type RoomEffect =
  | { kind: 'send-host'; frame: ServiceToHostFrame }
  | { kind: 'send-viewer'; githubId: number; frame: ServiceToViewerFrame }
  | { kind: 'close-viewer'; githubId: number; code: ShareCloseCode; reason: string }
  | { kind: 'close-all'; code: ShareCloseCode; reason: string }
  | { kind: 'set-alarm'; at: number } | { kind: 'cancel-alarm' }
  | { kind: 'fetch-ice-servers'; target: 'host' | { githubId: number } }
  | { kind: 'delete-storage' };
export function createRoom(input: { shortCode; scope; dataOwner; hostTokenHash }, now: number): RoomRecord;  // controller = dataOwner, host not yet connected, hostDisconnectedAt = now
export function reduce(room: RoomRecord, event: RoomEvent, now: number): { room: RoomRecord; effects: RoomEffect[] };
export function toSnapshot(room: RoomRecord): RoomSnapshot;   // strips hostTokenHash, joinedAt
```

`reduce` never mutates its input. "Snapshot to host" below means
`send-host { type: 'room', snapshot: toSnapshot(next) }`; it is emitted after every state change,
and only when the host is connected. A newly created room arms the reconnect alarm
(`set-alarm now + HOST_RECONNECT_WINDOW_MS`), because a host that creates a room and never parks
must not leave a room alive forever.

| Event | Precondition | Result |
| --- | --- | --- |
| any event | `status === 'ended'` | No state change. `viewer-connected` → `close-viewer 4004`. Everything else → no effects. |
| `host-connected` | — | `hostConnected = true`, `hostDisconnectedAt = null`, `cancel-alarm`. Snapshot to host. Every connected **admitted** viewer gets `status host-reconnected` if the host was previously parked. Lobby viewers get nothing. |
| `host-disconnected` | — | `hostConnected = false`, `hostDisconnectedAt = now`, `set-alarm now + HOST_RECONNECT_WINDOW_MS`. Every connected admitted viewer gets `status host-disconnected`. |
| `alarm` | `!hostConnected && now - hostDisconnectedAt >= HOST_RECONNECT_WINDOW_MS` | End the room (see `end`). Otherwise no effects (a stale alarm). |
| `viewer-connected` | githubId ∈ `blocked` | `close-viewer 4003 'blocked'`. No state change, and the host is **not** told. |
| ″ | githubId = `dataOwner.githubId` | `close-viewer 4009 'is-host'`. |
| ″ | an existing participant (any state) | Mark `connected = true`. (The DO glue has already closed any older socket for this githubId with 4008 `replaced`; the reducer emits no close.) If admitted, send `status admitted` (+ `contributor`), plus `status host-disconnected` when the host is away; if lobby, send `status lobby`. Snapshot to host. **This is the auto-restore path:** an admitted viewer who drops and reconnects is never re-lobbied. |
| ″ | new; participants = `MAX_PARTICIPANTS` or lobby count = `MAX_LOBBY` | `close-viewer 4013`. |
| ″ | new | Add `{ state: 'lobby', contributor: false, connected: true }`. Send **exactly one** frame to the viewer, `status lobby`. Snapshot to host. |
| `viewer-disconnected` | lobby participant | Remove it. Snapshot to host. |
| ″ | admitted | `connected = false`, stays admitted. Snapshot to host. |
| `viewer-frame leave` | — | Remove the participant from any state. `close-viewer 1000 'left'`. Snapshot to host. |
| `viewer-frame signal` | admitted **and** host connected | `send-host { type: 'signal', githubId, data }`. |
| ″ | lobby | `send-viewer error not_admitted`. **Nothing reaches the host.** |
| ″ | admitted, host away | Dropped silently (the viewer already has `host-disconnected`). |
| `viewer-frame ice-servers` | admitted | `fetch-ice-servers { githubId }`. |
| ″ | lobby | `send-viewer error not_admitted`. |
| `host-frame admit` | githubId is a lobby participant | `state = 'admitted'`, `contributor = frame.contributor === true`. Send `status admitted` (+ `contributor`) to the viewer. Snapshot. Not a lobby participant → `send-host error unknown_participant`. |
| `host-frame kick` | githubId is a participant | Remove it. `close-viewer 4010 'kicked'`. Snapshot. A kicked viewer who reconnects is **new**, so lands in the lobby. Otherwise `unknown_participant`. |
| `host-frame revoke` | githubId is a participant | Remove it, add its identity to `blocked`, `close-viewer 4011 'revoked'`, snapshot. Unknown githubId → `unknown_participant` (the host revokes only identities it has seen). If the revoked id was the controller, the controller returns to `dataOwner`. |
| `host-frame unrevoke` | githubId ∈ `blocked` | Remove it from `blocked`. Snapshot. Otherwise `unknown_participant`. |
| `host-frame set-contributor` | admitted | Set `contributor`. Send `status admitted` with the new `contributor` to that viewer. Snapshot. Otherwise `unknown_participant`. |
| `host-frame set-controller` | githubId = `dataOwner.githubId`, or an admitted participant | `controllerGithubId = githubId`. Snapshot. Otherwise `unknown_participant`. Reclaim is `set-controller` with the data owner's id, and it is always accepted. |
| `host-frame signal` | target admitted and connected | `send-viewer { type: 'signal', data }`. A lobby target → `send-host error not_admitted` and **nothing to the viewer**. Unknown → `unknown_participant`. |
| `host-frame ice-servers` | — | `fetch-ice-servers 'host'`. |
| `host-frame end`, `delete` | — | `status = 'ended'`. Send `close-all 4004 'room-ended'`, `cancel-alarm`, `delete-storage`. |

Controller bookkeeping: when the controller is kicked or leaves, `controllerGithubId` returns to
`dataOwner.githubId`.

**Invite-only, stated as the reducer guarantees it (FR-3):** until a `host-frame admit` names a
viewer, every effect addressed to that viewer is one of these: `status lobby`,
`error not_admitted`, or a close. It never receives a snapshot, another participant's identity,
`signal` or ICE servers. The unit tests assert this as an exhaustive check over every frame type.

### Durable Object glue (`src/room.ts` + `ShareRoom` in `src/index.ts`)

- **Load.** The constructor runs `ctx.blockConcurrencyWhile` to load `ctx.storage.get('room')`
  into memory (or `null`). Every handler works on that cached record.
- **Persist.** After each `reduce`, if the record changed, `await ctx.storage.put('room', next)`
  **before** executing effects, so a crash never sends a status the storage does not hold.
  `delete-storage` → `ctx.storage.deleteAll()` plus `deleteAlarm()`.
- **Internal requests** (from `routes.ts` only):
  - `POST /init` → 409 if a record exists, else `createRoom` + persist + `set-alarm` → 201 with the snapshot.
  - `POST /delete` → compare `HDR_HOST_TOKEN_HASH` in constant time; mismatch or no room → 404; else reduce `delete` → 204.
  - `GET /status` → 200 `{ status }`, or 404 when there is no record.
  - `GET /host` (upgrade) → token check as for delete → `new WebSocketPair()`, `ctx.acceptWebSocket(server, ['host'])`, `server.serializeAttachment({ role: 'host' })`, close any older host socket with 4008, reduce `host-connected`, return 101.
  - `GET /join` (upgrade) → parse `HDR_IDENTITY` → close every existing socket tagged `'v:' + githubId` with 4008 `replaced` → accept with tags `['viewer', 'v:' + githubId]` and attachment `{ role: 'viewer', identity }` → reduce `viewer-connected`.
- **Hibernation handlers.**
  - `webSocketMessage(ws, msg)`: read the attachment role, decode with `protocol.ts`. A decode failure → send `error <code>` on that socket only. Otherwise reduce `host-frame` or `viewer-frame`.
  - `webSocketClose` / `webSocketError`: reduce `host-disconnected` or `viewer-disconnected`, but **only if `ws` is still the current socket for that role and id**. A socket already replaced by a 4008 must not mark the newer connection offline.
- **Effects.**
  - `send-*` → `ws.send(JSON.stringify(frame))` on `ctx.getWebSockets('host')` or `ctx.getWebSockets('v:' + id)`. Skip when no socket exists.
  - `close-viewer` / `close-all` → `ws.close(code, reason)`. Send any pending `status` frames first.
  - `set-alarm` → `ctx.storage.setAlarm(at)`; `cancel-alarm` → `ctx.storage.deleteAlarm()`.
  - `fetch-ice-servers` → `turn.fetchIceServers` (WI-1.6), then send `ice-servers`, or `error turn_unavailable` on failure.
- **`alarm()`** → reduce `{ kind: 'alarm' }` with `Date.now()`.
- The DO is the only place that calls `Date.now()`. Everything below it receives `now`.

## Identity & GitHub OAuth

Rev 3: **the share service performs no OAuth.** The PAN-4293 account service handles all GitHub

PAN-4330 local client handles all token storage.

- **Viewer:** the same. A viewer must be a signed-in, **allowlisted** account (OD-2).
- The share Worker verifies every device token with `env.ACCOUNT.verifyDevice` on every
  `POST /v1/rooms` and every `/join` upgrade. Verification is one D1 lookup with no cache, so a

- Rev 2's `~/.overdeck/github-identity.json`, identity JWT and JWKS are retired (D-R3-1).

GitHub sign-in supplies *identity and accountability*. The lobby and the block list supply
*authorization*. Both are required; neither alone is sufficient.

## Access Control — Invite-Only

Invite-only is a **hard requirement** (FR-3, FR-4). The `/s/<shortCode>` link is a routing token,
not a capability — every participant is in the room only because the controller let them in.

### The lobby

1. A joiner's local Overdeck server, holding the joiner's device token, opens `GET /v1/rooms/:code/join`.
2. They land in the room's **lobby** (`state: 'lobby'`). The share service sends the joiner
   exactly one frame, `status lobby`, and sends the host a room snapshot that lists the joiner's
   GitHub avatar and handle.
3. **No WebRTC offer is created and no DataChannel is opened** until the controller admits them.
   A lobby viewer receives zero conversation/terminal/draft/presence content.
4. The controller **admits** → the host creates an `RTCPeerConnection`, exchanges SDP/ICE via the
   share-service relay, opens the data channels, and backfills history.

### Controller actions

| Action | Effect |
|---|---|
| **admit** | Move a lobby joiner into the room; host opens their peer connection + channels. |
| **kick** *(soft)* | Tear down that viewer's `RTCPeerConnection` immediately; their UI shows "removed by host". A kicked user who re-clicks the link **re-enters the lobby** and can be re-admitted. For "not right now". |
| **revoke** *(hard)* | Tear down channels **and** add the GitHub id to the room's `blockList`. Works on a connected viewer *or* a lobby joiner. A revoked user re-clicking the link cannot re-enter the lobby and cannot be re-admitted unless the controller un-revokes. For "not at all". The block list is what makes invite-only enforceable against a leaked link. |
| **un-revoke** | Remove a GitHub id from the `blockList`. |
| **revoke link** | `DELETE /v1/rooms/:code` (or host frame `end`) — kills the whole room; drops every participant (lobby + admitted) with close 4004. |

### Defense in depth — the host gates content itself (NFR-4)

The host's WebRTC hub keeps its **own** in-memory admitted set and **only opens content data
channels to viewers it has itself admitted** — it never treats the share service's room state
as the sole authority. A compromised or buggy share service could mis-report membership, but
it cannot make the host stream content to an un-admitted peer.

On a host **process restart** within the reconnect window, the host's in-memory set is gone; it
re-reads the admitted + block lists from the share service room state to resume. That is a
narrow, documented trust window on an Overdeck-operated service, and only membership metadata
(never content) is involved.

Rev 3 adds a second layer at the share service itself: the reducer relays SDP/ICE and TURN
credentials only to and from **admitted** viewers (see *Room rules*), so even a buggy host cannot
start a peer connection with a lobby occupant.

## Host Role & Handoff

- The **controller** role is transferable to any admitted viewer mid-session ("you drive for a
  while"). The data-owner machine stays the hub and the authority — it accepts control commands
  (admit/kick/revoke, contributor grants, send-prompt) only from the participant who currently
  holds the controller role (FR-10).
- **Handoff:** the current controller assigns the role to a chosen viewer (a `handoff` control
  message). The **data owner can always reclaim** the controller role unilaterally — it is their
  machine and their conversation.
- Exactly one controller exists at any time. `controllerGithubId` in the room state is the single
  source of truth; the host enforces it on every inbound control command.

## Link Lifecycle & Disconnect/Reconnect

### Link lifecycle (FR-11)

- **Link lifetime = conversation lifetime.** The `/s/<shortCode>` link is valid as long as the
  host keeps the conversation shared. It expires automatically when the host ends/closes the
  shared conversation (the room is torn down).
- **No fixed-duration expiry** — no 24-hour timer.
- **Manual link revoke** stays available at any time (`DELETE /api/sessions/:roomId`), dropping
  every participant including those in the lobby.

### Host disconnect & reconnect (FR-12)

- If the host's network blips or its dashboard process restarts, viewers show a
  "host disconnected — reconnecting…" state and always have a manual **Leave** action.
- **Reconnect window: 5 minutes.** The share service holds the room (id, host token hash,
  admitted list, block list, contributor grants, controller) in Durable Object storage. A Durable
  Object alarm fires 5 minutes after `hostConnected` goes false and ends the room if the host has
  not returned. Because the record is in storage, a share-service redeploy or a Durable Object
  hibernation does not end a room.
- **Within the window:** the host re-parks on `GET /v1/rooms/:code/host` with the same host token, re-reads
  room state, and **admitted viewers auto-restore** — their peer connections are re-negotiated
  with no re-admission. This holds even across a full host *process* restart, because membership
  lives in the share service's room record, not only in host memory.
- **Past the window:** the room is destroyed, the link dies; a fresh share creates a fresh room
  and everyone re-joins through the lobby.

To survive a process restart, the host persists a minimal record locally (see *Data Model*) so it
knows which room to re-park on after `pan up` comes back.

## Transport & Wire Format

### Peer connections and data channels

One `RTCPeerConnection` per viewer (host hub ⇄ viewer browser). Each carries five labeled,
**reliable, ordered** WebRTC DataChannels:

| Channel | Direction | Payload |
|---|---|---|
| `control` | bidirectional | admit / kick / revoke / contributor-grant / handoff / send-prompt + acks |
| `conversation` | host → viewer | per-stream history backfill + live message append/update |
| `drafts` | bidirectional | per-viewer prompt-draft snapshots, broadcast to all participants |
| `terminal` | host → viewer | raw tmux bytes — only while the viewer has terminal view toggled |
| `presence` | host → viewer | lobby + admitted roster, join/leave, contributor flags, stream roster |

ICE: STUN-direct preferred; Cloudflare Realtime TURN relay fallback (ICE servers from the share service, D-R3-6). DataChannels are DTLS-encrypted by
default — content is encrypted in transit end to end.

**Multi-stream note (NFR-3):** channels are *not* duplicated per stream. The envelope's `streamId`
multiplexes member sessions over the same five channels; the `presence` channel announces the
stream roster. v0 has exactly one stream.

### Scoped, versioned wire format (NFR-2, NFR-3)

Conversation events cross the channel in a wire format defined **specifically for sharing** — not
the internal `PanRpcGroup` / `ChatMessage` types (`packages/contracts/src/rpc.ts:145`). Host and
viewer run independently-updated Overdeck versions; coupling the wire format to an internal type
would break rendering on version skew. The wire format is an explicit allow-list of fields
permitted to cross the host→viewer boundary. It lives in `packages/contracts/src/sharing.ts` and
is exported from `@overdeck/contracts`.

```ts
type ShareScope =
  | { kind: 'conversation'; conversationId: string };
  // future (PAN-2565 followup): | { kind: 'task'; taskId: string }

interface SharedEnvelope {
  v: 1;                                   // wire format version — bump on breaking change
  ch: 'control'|'conversation'|'drafts'|'terminal'|'presence';
  streamId: string;                       // member session id; v0: always the shared conversation's id
  seq: number;                            // per-channel, per-stream monotonic, for gap detection
  t: number;                              // host epoch ms
  payload: unknown;                       // channel-specific, schemas below
}

// connect handshake (first message on `control`, both directions)
interface SharedHello {
  v: 1;
  scopeKinds: Array<'conversation'>;      // additive: ['conversation','task'] later
  scope: ShareScope;
}

// conversation channel
type ConversationPayload =
  | { kind: 'history'; messages: SharedMessage[] }      // full backfill on join (per stream)
  | { kind: 'append';  message: SharedMessage }
  | { kind: 'update';  message: SharedMessage };        // streaming token updates

interface SharedMessage {                 // explicit subset mapped from internal ChatMessage
  id: string;
  role: 'user' | 'assistant' | 'system';
  text: string;
  turnId?: string;
  author?: { login: string; avatarUrl: string };        // which human sent a user message
  createdAt: string;
  completedAt?: string;
  streaming?: boolean;
  sequence?: number;
}

// presence channel
interface PresencePayload {
  controllerGithubId: string;
  participants: Array<{
    githubId: string; login: string; avatarUrl: string;
    state: 'lobby' | 'admitted';
    contributor: boolean;
    isHost: boolean;
  }>;
  streams: Array<{                        // stream roster; v0: exactly one entry
    streamId: string;
    label: string;                        // e.g. conversation title
    kind: 'conversation';                 // additive union later (e.g. 'terminal-agent')
  }>;
}

// drafts channel
interface DraftPayload {
  authorGithubId: string;
  authorLogin: string;
  text: string;                           // full snapshot, last-write-wins per author
  updatedAt: number;
}
```

The host maps its internal `ChatMessage` to `SharedMessage` at the transport boundary; the viewer
renders `SharedMessage` directly. Version negotiation: `SharedHello` exchanges `v` and
`scopeKinds`; a viewer on an older wire version renders best-effort and shows a "host is on a
newer Overdeck" notice rather than breaking; a viewer missing the share's scope kind gets an
explicit "your Overdeck is too old for this share type" state.

## Conversation Sharing

### Host side

- A new host module subscribes to the host's local conversation event source (the same source
  feeding the conversation read model — `watchConversation` in
  `src/dashboard/server/services/conversation/watch.ts`, re-exported by the 13-line barrel
  `src/dashboard/server/services/conversation-service.ts`; message parsing reuses
  `src/dashboard/server/services/shared-transcript-parser.ts`).
- On viewer admit: send a `conversation` `history` backfill (the **full** conversation, read from
  the host's local store / JSONL), then stream live `append` / `update` events.
- **Full history on join** is locked (FR-5) — the data lives in the host's local store and the
  DataChannel can carry it. A progressive lazy-load is a future optimization, not v0.

### Viewer side

- The viewer's dashboard frontend opens a route, e.g. `/#/shared/<roomId>`, mounted when the join
  intent arrives.
- It establishes the browser `RTCPeerConnection`, renders the `conversation` channel through the
  existing conversation UI components (`ConversationPanel` / `MessagesTimeline` in
  `src/dashboard/frontend/src/components/chat/`), reusing message rendering as-is.
- The viewer's surface is **read of conversation + compose of drafts** — see *Input Model*.

### Default surface & terminal toggle (FR-9)

The **conversation panel** is the default shared surface. A **terminal view toggle** lets a viewer
flip to the host's live tmux pane.

- The `terminal` channel carries raw bytes from the existing PTY hub (`pty-hub.ts`) — the WebRTC
  transport subscribes to `broadcastToHub()` output as an additional consumer.
- **Strictly one-directional, host → viewer.** Viewer keystrokes never reach the host's shell.
  Read-only is locked, not optional — terminal sharing is "watch me work", not "drive my shell".
  The terminal data channel has no inbound handler on the host.

## Input Model

- **View-only by default.** A newly-admitted viewer cannot drive the conversation; they compose
  **prompt suggestions** in their own local draft box (FR-7).
- **Suggestion UI — stacked list.** The controller sees every viewer's pending draft as a stacked
  list with author avatars (queue-of-questions feel) and picks one to send, optionally editing it
  first.
- **Drafts sync live as people type** — plain-text full-snapshot updates over the `drafts` channel.
  No CRDT, no rich editor in v0 (a CRDT `collab` channel is the followup's job — see *Forward
  compatibility*). Last-write-wins per draft, scoped to the author.
- **Direct-submit (contributor) permission (FR-8).** The controller can grant any admitted viewer
  **direct-submit**: that viewer's prompts post straight into the conversation without the
  controller picking each one. Per-viewer, controller-granted, revocable.
  - Direct-submit is **not** host handoff — a contributor sends prompts but cannot
    admit/kick/revoke or hand off. Many contributors may exist; there is still exactly one
    controller.
  - Direct-submit does **not** bypass the lobby. Everyone is host-admitted first; contributor is a
    second, separate grant applied after admission.

### Concurrent submission ordering — decided (FR-14)

The issue's one open question is resolved with its stated lean: **strict FIFO queue** on the host;
submissions arriving while the agent is mid-turn are queued and flushed in order when the turn
ends; the presence-driven composer shows "agent is working" and "N queued" so contributors see why
their prompt hasn't landed. Auto-contributor pre-designation (grant on admit by GitHub handle) is
a nice-to-have and **out of v0**.

## Clients & Join Paths

Two first-class clients in v0: the **dashboard** and the **CLI**. Both can host-share and join.
All join paths funnel through the same host-approval lobby.

### Dashboard

- **Host (FR-1):** a "Share this conversation" action in the conversation panel calls
  `POST /api/sessions` (via the host's dashboard server) and surfaces the `/s/<shortCode>` link +
  a participant/lobby management panel.
- **Viewer (FR-2):** open the link in a browser → GitHub OAuth on `overdeck.ai` →
  **localhost-detect**: the share page probes for a running local Overdeck at `localhost:<port>`
  and POSTs the join intent there → the local dashboard opens `/#/shared/<roomId>` → lobby.
  A `pan://` protocol handler was considered and rejected (OS-level registration is finicky
  cross-platform; note the desktop app (`apps/desktop/src/protocol.ts`) may later register one as
  an *additional* path — not required for v0).

### CLI (FR-13)

- `pan share <conversationId>` — host side. Prints the `/s/<shortCode>` link and a short join code.
- `pan join <link-or-code>` — viewer side. Authenticates via GitHub **device flow**, posts the
  join intent straight to its own local dashboard (it already knows the local port — no
  localhost-detect needed), lands in the lobby; on admit, the shared conversation opens in that
  user's local dashboard.

### Cold start

A viewer who clicks the **browser** link with no local Overdeck running cannot be auto-helped by
the share page — a web page cannot spawn a local process. The page detects "no localhost" and
instructs the user to run `pan join <link-or-code>`. **`pan join` auto-starts the local dashboard
if it is not already running**, then proceeds to the lobby — so the CLI is the cold-start recovery
path for an installed-but-not-running viewer. A viewer with **no Overdeck installed at all** must
install it first. A hosted web join for the truly-uninstalled case is filed as
[PAN-4481](https://github.com/eltmon/overdeck/issues/4481) and awaits operator decision OD-1. Rev 3
corrects rev 2's reasoning: a static page running the browser WebRTC viewer would **not** put
content on `overdeck.ai`; the blocker is the missing web sign-in flow.

## Data Model

### Host-side persistence (slice 2, PAN-4473; slice 8, PAN-4479)

The host persists a minimal record so it can re-park on its room after a `pan` restart. Rev 3
replaces the rev-2 `shared_sessions` SQLite table: post-Cut there is no
`src/lib/database/schema.ts`, the database has a single drizzle init migration, and the repo rule
is "Overdeck stores no status it can derive". The host token is a secret that cannot be derived, so
it lives in a file, using the same pattern as `~/.overdeck/access-tokens.json` and
`~/.overdeck/trusted-origins.json`:

`${OVERDECK_HOME}/shared-sessions.json`, mode 0600:

```json
{ "version": 1,
  "rooms": {
    "<shortCode>": { "scopeKind": "conversation", "scopeId": "<conversation name>",
                     "hostToken": "odh_…", "createdAt": "<ISO>" } } }
```

- Keyed by room (forward-compat commitment 3). At most one entry per `(scopeKind, scopeId)`,
  enforced by the accessor.
- An entry is removed when the share ends (host `end`, `DELETE`, a 404 on re-park, or close 4004).
- Participants, contributor grants, the controller and the block list are **not** stored on the
  host. They live in the share service's room record, and the host reads them from the `room`
  snapshot on every park. That is what makes auto-restore after a restart correct.

### Share service

One `ShareRoom` Durable Object per room. Its storage holds a single key, `room` (the `RoomRecord`
in *Room rules*), plus at most one alarm. Storage is durable, so a redeploy or a hibernation does
not end rooms. `end`, `DELETE` and the expired alarm call `deleteAll()`, so an ended room leaves
nothing behind. There is no D1 database and no cross-room registry: a short code addresses its
room directly through `idFromName`.

## Security Considerations

- **Invite-only is enforced in three places.** (1) The share-service reducer: a lobby occupant
  receives only `status lobby`, `error not_admitted` or a close, and never gets SDP, ICE servers,
  snapshots or other identities. (2) The host hub's own admitted set (NFR-4, slice 3). (3) The
  block list, which refuses a revoked githubId with close 4003 before it reaches the lobby.
- **The link is not a capability.** The short code only routes a joiner to the lobby. The landing
  page reveals nothing about the room except whether it is active.
- **Identity is server-verified.** Every `POST /v1/rooms` and `/join` calls
  `env.ACCOUNT.verifyDevice` over a service binding. There is no self-asserted handle, and no
  public-internet hop between the Workers.
- **Credentials live only in local servers** (D-R3-2). The host token is returned once; the Durable
  Object stores only its SHA-256 hash and compares in constant time. Neither the Worker nor the
  host logs it. A wrong token, an unknown code and an ended room all answer the same 404.
- **Content is end-to-end encrypted** over DTLS DataChannels and never transits the share service
  (NFR-1; e2e-verified in slice 11).
- **TURN credentials are short-lived** (3600 s), issued only to the host and admitted viewers, and
  never logged. The TURN API token is a Worker secret.
- **Untrusted input is bounded.** Frames are at most 64 KiB, decoded to known keys only, and
  binary frames are rejected. Request bodies are at most 16 KiB. Rooms hold at most 50
  participants with a lobby of at most 20. Room creation is limited to 10 per GitHub account per
  60 s (Workers Rate Limiting binding).
- **Terminal sharing is read-only** (slice 6): the host exposes no inbound terminal path.
- **The host dashboard stays local and unauthenticated** for its own UI. Sharing exposes only the
  shared scope's channels, only to admitted peers (NFR-6).
- **Deploy is operator-only.** No agent runs `wrangler deploy`, `wrangler secret put`,
  `wrangler login` or any remote Cloudflare command.
