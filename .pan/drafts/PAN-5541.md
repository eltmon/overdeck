# PAN-5541 — Secret requests: the Needs-you item opens a place to type the secret

**Issue:** [PAN-5541](https://github.com/eltmon/overdeck/issues/5541)
**Base commit:** `a1cfde59e98` (main, 2026-11-18)
**Planning mode:** `pan plan --auto` (no operator questions; defaults recorded under "Decisions")

## Glossary

- **Agent request** — a question an agent asks the operator through the dashboard instead of the chat. Two kinds exist: a **secret request** (MCP tool `request_secret`, agent then parks in `secret_wait`) and a **machine-link request** (MCP tool `link_machine`, agent then parks in `link_machine_wait`). Held in memory by `src/dashboard/server/services/agent-requests.ts`.
- **Request id** — the 32-hex id of one agent request (`AgentRequestView.id`). Not the agent's id.
- **Owner** — the agent or conversation that made the request: `agentKind: 'agent'` with a normalized agent id such as `agent-pan-1`, or `agentKind: 'conversation'` with the conversation name.
- **Decision** — one row of `useDecisions()` (`src/dashboard/frontend/src/lib/useDecisions.ts`). An agent request becomes a Decision through `agentRequestDecisions()`, with `Decision.id` = the **request id** and `Decision.agentRequest` set.
- **Needs-you item** — one `NeedsYouItem` from `useNeedsYouItems()` (`src/dashboard/frontend/src/lib/selectors/needsYou.ts`). Every Needs-you surface opens an item with `item.open()`.
- **Needs-you surfaces** — project Home (`components/Stage/HomePane/HomeNeedsYou.tsx`), the top bar's "Needs you · N" menu (`components/flywheel/NeedsYouIndicator.tsx`), the kanban strip (`components/KanbanBoard/NeedsYouStrip.tsx`), Simple Home (`components/simple/SimpleHomePage.tsx`), the conversation list's Needs you section (`components/CommandDeck/ConversationList.tsx`), the Live dock (`components/dock/ConversationDock.tsx`), and the phone list (`components/mobile/MobileNeedsYou.tsx`).
- **Root session** — a browser on the dashboard's own machine (`viewer.kind === 'root-session'` from `loadAnywhereStatus`). Only a root session (or the internal token) may answer an agent request (server rule D-4, `routes/agent-requests.ts`).
- **Answer body** — the part of `AgentRequestCard` that a viewer acts on: the prompt and masked input with Send/Decline (secret), or the hint with Link a machine…/Dismiss (machine link), or the "answer elsewhere" line for a non-root viewer.
- **Pinned request card** — the new card this issue adds at the top of a conversation panel while that conversation (or agent) has a pending agent request.
- **Agent-request dialog** — the new modal this issue adds; it shows the answer body for one request id.

## Problem and verified cause

The operator clicked a Needs-you item for an agent that had called `request_secret` and landed on a page with no secret input.

1. **The only answer UI is `AgentRequestCard`**, mounted only by `DecisionsPanel` (`src/dashboard/frontend/src/components/DecisionsPanel.tsx`, grep anchor `: d.agentRequest`), which mounts only in the session-feed sidebar's Needs you tab.
2. **Opening the item goes nowhere useful.** `buildNeedsYouItems` section (d) (`lib/selectors/needsYou.ts`, grep anchor `open: () => navigateToDecisionSubject(decision)`) passes the Decision to `navigateToDecisionSubject` (`lib/navigateToDecision.ts`). For an agent request, `decision.id` is the **request id** (`agentRequestDecisions` in `lib/useDecisions.ts`, grep anchor `id: row.id,`), so:
   - a conversation owner navigates to `/conv/<request id>` — a conversation that does not exist;
   - an agent owner has no `issueId` on the Decision, so `decisionSubjectPath` returns `null` and nothing happens.
3. **Project Home never lists the item.** Section (d) items carry no `projectKey`, and `components/Stage/ProjectHome.tsx` calls `useNeedsYouItems({ projectKey })`, which drops items without one (`const kept = opts?.projectKey ? all.filter(...)`). The existing test "keeps only the matching project when filtering, dropping decision items" (`lib/selectors/__tests__/needsYou.test.ts`) pins that behavior for decisions in general.
4. **The conversation itself shows nothing.** `components/chat/ConversationPanel.tsx` has no reference to agent requests, and the server's conversation rows (`src/lib/overdeck/conversation-list.ts`) never report a secret request as pending input, so the conversation list's Needs you section and the Live dock never flag the owner either.
5. **The row carries no issue id.** `GET /api/agent-requests` (`handleAgentRequestList` in `src/dashboard/server/routes/agent-requests.ts`) answers `id, kind, agentId, agentKind, label, name, prompt, hint, createdAt, expiresAt`. The caller's issue id (`SelfCaller.issueId`, `src/dashboard/server/self-caller.ts`) is known when the request is created but is only folded into the free-text `label` (`requestLabel` in `routes/self-requests.ts`: `` `${caller.agentId} · ${caller.issueId}` ``).
6. **The phone line is vague.** `MobileNeedsYou.tsx` `ReadOnlyAction` renders `Answer on the desktop` (grep anchor `if (decision.agentRequest) return`), and the card's non-root text is `Answer this on {label ?? 'this machine'}'s own dashboard`, which names no reason and reads wrong ("this machine") for a remote viewer when the label is unknown.

## Decisions (made here; `--auto` mode)

- **D1 — Needs-you open path is a dialog, not a navigation.** `item.open()` for an agent-request decision opens a global **agent-request dialog** that renders the answer body for that request id, over whatever page the operator is on. Rationale: the issue's acceptance says "shows the masked input without any other navigation"; a dialog works for owners that have no route (an agent with no issue) and for every surface that calls `item.open()` (Home, top bar, kanban strip, Simple Home). The dialog follows the existing global-dialog-host pattern (`components/Settings/anywhere/anywhereDialogStore.ts` + `AnywhereDialogHost.tsx`, mounted in `src/dashboard/frontend/src/main.tsx`).
- **D2 — `Decision.id` stays the request id.** React keys (`request:${d.id}` in DecisionsPanel) and the section (d) dedupe key `decision:<id>` depend on it. Owner data lives in `Decision.agentRequest`, which gains `agentKind` and `issueId`.
- **D3 — The server adds `issueId` to each agent request.** `AgentRequestView` gains `issueId: string | null`, set from `caller.issueId` in `insert()`; the list route adds `issueId` to each row. This is additive: older frontends ignore it, and the new frontend treats a missing field as `null`. The self (agent-side) routes pick explicit fields and are unchanged.
- **D4 — Needs-you items for agent requests get a `projectKey`.** Rule: a conversation owner → `projectOf.conversation(agentId)`, falling back to `projectOf.issue(issueId)` when the request has an issue id; an agent owner → `projectOf.issue(issueId)` when it has one; otherwise no `projectKey` (the item still shows in the top bar under "Other"). Only agent-request decisions change; every other decision keeps no `projectKey`.
- **D5 — One answer body, three frames.** Extract the answer body from `AgentRequestCard` into an exported `AgentRequestAnswer` component in the same file. `AgentRequestCard` (Decisions panel row frame) = frame + `AgentRequestAnswer`; the dialog = `Modal` + `AgentRequestAnswer`; the pinned request card reuses `AgentRequestCard` unchanged; the phone list renders `AgentRequestAnswer` in place of `Answer on the desktop`. The root-session rule stays in one place.
- **D6 — The pinned request card mounts in three places, one per owner chrome, so each request renders once per surface and in every view mode.**
  - **Conversation owners:** `ConversationPanel` (`components/chat/ConversationPanel.tsx`) renders it for `{ kind: 'conversation', name: conversation.name }` immediately after the `ConversationMachineBanner` line and outside its `!embedded` guard. `ConversationPanel` hosts both its conversation view and its terminal view (`ConversationTerminalView`, grep anchor `showTerminal && viewMode === 'terminal'`), so both modes show it.
  - **Agent owners in the issue drawer:** `components/drawer/DrawerAgentSession.tsx` renders it for `{ kind: 'agent', id: agent.id }` directly above each of the two containers that hold `{sessionBody}` (the compact layout's `data-section="SessionPanel"` div and the full layout's bordered div). Its terminal view renders `XTerminal` directly, not `ConversationPanel`, so the mount must sit outside `sessionBody`.
  - **Agent owners in the Stage session pane:** `components/CommandDeck/SessionView/SessionPanel.tsx` renders it for `{ kind: 'agent', id: session.sessionId }` directly above `<div className={styles.sessionPanelContent}>`, which covers its conversation, findings and terminal (`XTerminal`) views.
  - `ConversationPanel` never matches agent owners, so an agent session whose conversation view embeds `ConversationPanel` with `agentId` shows the card once (from the drawer or pane chrome), not twice.
- **D7 — Owner match for the pinned card.** `{ kind: 'conversation', name }` matches `agentKind === 'conversation' && agentId === name`; `{ kind: 'agent', id }` matches `agentKind === 'agent'` with agent ids compared case-insensitively (the server normalizes agent owners to `agent-<issue lowercase>`; the frontend `agent.id` and `session.sessionId` use the same form).
- **D8 — The dialog closes itself when its request leaves the pending list** (answered here, answered elsewhere, declined, expired, dashboard restarted). On a successful Send it shows a `sonner` toast `Sent <NAME> to <label>`; on Decline/Dismiss it shows `Declined <label>'s request`. Clicking **Link a machine…** in the dialog closes the agent-request dialog before opening Link a machine, so two modals never stack (the Link a machine dialog already resolves the request by id, PAN-4942 D-11).
- **D9 — Conversation list and Live dock flag the owner locally.** `ConversationList` overlays its own copy of each conversation row: a conversation that owns a pending agent request gets `pendingInputCount ≥ 1` and the kind (`secretRequest` / `machineLink`) appended to `pendingInputKinds`, so it lands in the list's **Needs you** section with the "Secret requested" indicator; clicking the row opens the conversation, where the pinned request card shows (D6). The Live dock adds the request's `issueId` (lowercased) to `needsYouIds`. The overlay is local to these two components: the server's pending-input kinds, `usePendingInputSubjects`, push notifications and the Needs-you selector's section (a) are untouched, so no item is counted twice.
- **D10 — Non-root text names the machine and the reason.** The machine named is the one running this dashboard (`status.machine.label`), not the agent's host: a remote (Fly) agent's request is still answered on the dashboard machine. Exact strings (exported from `AgentRequestCard.tsx` as `agentRequestElsewhereText(kind, machineLabel)`):
  - secret, label known: `Answer this on <label>'s own dashboard. A secret can be typed only in a browser on <label> itself, so it never crosses the network.`
  - machine link, label known: `Answer this on <label>'s own dashboard. Machines can be linked only from a browser on <label> itself.`
  - secret, label unknown (`status.machine` is null): `Answer this in a browser on the machine that runs this dashboard. A secret can be typed only there, so it never crosses the network.`
  - machine link, label unknown: `Answer this in a browser on the machine that runs this dashboard. Machines can be linked only from there.`
- **D12 — A failed or malformed poll never closes the dialog.** `fetchAgentRequests` today answers `[]` on a timeout, a non-OK status, a network error or a 200 body without a `requests` array, which would look like "request gone" and drop a half-typed secret. It now throws in all four cases (like `fetchDiskAlert`, PAN-5093), and every `['agent-requests']` query sets `retry: false`, so react-query keeps the last successful rows.
- **D13 — The conversation row's pulsing indicator opens the conversation for an agent request.** `AwaitingInputIndicator` stops click propagation (`components/AwaitingInputIndicator.tsx`, `e.stopPropagation()`), and `ConversationRow` wires it to `requestReopen(conv.name)`, which does nothing without a dialog payload. When the row's kinds contain `secretRequest` or `machineLink` and no `askUserQuestion`, `exitPlanMode` or `enterPlanMode`, the indicator calls `onSelect(conv.name)` instead, which opens the conversation and its pinned card.
- **D11 — Live verification recipe** (implementation checkpoint, below) uses the work agent's own `request_secret` MCP tool and the branch frontend served by Vite on port 3010 (the only dev port the server trusts, `getTrustedOrigins` in `src/dashboard/server/routes/origin-validation.ts`), proxied to the live dashboard on `127.0.0.1:3011`.

## Requirements

- **FR-1** — Activating a Needs-you item whose decision has `agentRequest` opens the agent-request dialog for that request id on every surface that calls `item.open()` (project Home, top bar menu, kanban strip, Simple Home). It never navigates.
- **FR-2** — The dialog shows the same answer body as the Decisions panel card: for a root session, the prompt, the secret's `name`, a `type="password"` input labelled `Value for <NAME>`, **Send** and **Decline** (secret), or the hint, **Link a machine…** and **Dismiss** (machine link).
- **FR-3** — The dialog closes when its request id is no longer in `GET /api/agent-requests`, with the toasts in D8.
- **FR-4** — `GET /api/agent-requests` rows carry `issueId` (string or `null`), taken from the requesting caller.
- **FR-5** — An agent-request Needs-you item carries a `projectKey` per D4, so project Home lists it under its project.
- **FR-6** — The owner's surfaces (D6: `ConversationPanel` for a conversation owner; `DrawerAgentSession` and `SessionPanel` for an agent owner) render `AgentRequestCard` for each pending request at the top, embedded or not, in every view mode including terminal.
- **FR-7** — A conversation that owns a pending agent request appears in the conversation list's Needs you section; an issue whose agent or conversation owns one shows the Live dock needs-you dot (D9).
- **FR-8** — A non-root viewer sees the D10 text in the card, the dialog, the pinned card and the phone list; the phone list no longer says `Answer on the desktop` for an agent request.
- **NFR-1** — The secret value lives only in component state until Send; the input clears on every answer; the value never enters a URL, a log, a toast or a store. The dialog store holds only the request id.
- **NFR-2** — No new polling: the dialog, the pinned card, the conversation list overlay and the dock read the existing `['agent-requests']` react-query key (`refetchInterval: 5000`), so react-query dedupes them with `useDecisions`.
- **NFR-3** — No file exceeds 1000 lines (`scripts/lint-file-size.sh`); `ConversationPanel.tsx` (912 lines at base) and `ConversationList.tsx` (916) grow by at most a handful of lines each.
- **NFR-4** — Every new frontend test file is listed in `scripts/frontend-test-subset.txt` (CI runs only that list).
