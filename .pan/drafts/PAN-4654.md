# PAN-4654 — Fleet versions and Update all, including harness CLIs

**Issue:** [PAN-4654](https://github.com/eltmon/overdeck/issues/4654) · **Epic:** [PAN-2350](https://github.com/eltmon/overdeck/issues/2350) · **Parent PRD:** `.pan/drafts/pan-2350.md` (revision 5)
**Status:** planned (auto mode, 2026-11-01) · **Author:** planning agent (Claude Opus 5.5)
**Owns:** W-LINK7 (FR-29, NFR-6 of the parent PRD) · **Depends on:** [PAN-4645](https://github.com/eltmon/overdeck/issues/4645) (merged as `1c20fe2c38b`: links, the link supervisor, `linkFetch`, machine tokens, the `unsupported` state)
**Verified against:** `feature/pan-4654` at `1c20fe2c38b` (same tree as `origin/main`). Every file and line cited below was read at that commit.

W-LINK7 has three parts. One: every machine reports its Overdeck version and the version of each installed harness CLI, and the operator sees one table with one row per machine. Two: a machine whose link protocol differs shows `unsupported` with the exact Overdeck version and install command, and is never retried in a loop. Three: **Update all** updates Overdeck and the installed harness CLIs on every online machine, waits for running turns to end unless the operator chooses **Update now**, and shows each version before and after.

## Glossary

- **Machine:** one running Overdeck server with its own `OVERDECK_HOME`, identified by its environment id (`src/lib/environment-identity.ts`). "This machine" is the one whose dashboard the operator has open.
- **Link, linked machine, link supervisor, `linkFetch`:** as defined in PAN-4645. A link is a record that lets this machine's server reach another machine over a secure channel. The link supervisor (`src/dashboard/server/services/link-supervisor.ts`) owns each link's state (`online`, `connecting`, `offline`, `unsupported`, `revoked`). `linkFetch(environmentId, path, init)` (`src/lib/anywhere/link-client.ts:181`) sends one JSON request to a linked machine and fails within 2.5 s when the machine cannot be reached.
- **Link protocol:** `LINK_PROTOCOL_VERSION = 1` (`packages/contracts/src/machines.ts:15`). This is the version that gates links (D-4645-11). It is **not** `ENVIRONMENT_PROTOCOL_VERSION` (`packages/contracts/src/environment.ts:14`), which stays `1` because the desktop app clients check it. This issue never bumps either constant.
- **Harness CLI:** the command-line program a harness runs: `claude` (Claude Code), `codex` (Codex CLI), `kimi` (Kimi Code CLI, used by both the `kimi-code` and `acp` harnesses), `opencode`, `muse`, `omp` (OhMyPi), `prime-agent`. The map from harness to binary name is `HARNESS_BINARY_BY_RUNTIME` (`src/lib/harness-binary.ts:65-74`).
- **Version report:** what one machine says about itself: Overdeck version, install mode, link protocol, one entry per installed harness CLI (binary, version, update command), and the current update job. Served by `GET /api/versions/self`.
- **Fleet table:** one row per machine (this machine first, then every outbound link), built by `GET /api/machines/versions` on this machine from its own report plus each online linked machine's report.
- **Update job:** the work one machine does after an update request: wait for turns, update each harness CLI, update Overdeck, restart the dashboard when Overdeck changed. Each machine runs its own job. The job is persisted in `${OVERDECK_HOME}/fleet-update.json` so it survives the dashboard restart.
- **Component:** one thing an update job updates: `overdeck` or one harness CLI binary. Each component carries `before`, `after`, `status` and `detail`.
- **Turn in progress (working turn):** an entry of the live agent directory (`getLiveAgentDirectory()`, `src/dashboard/server/services/agent-directory.ts:704`) whose `state` is `'working'`. Agent rows get it from the pane state, conversation rows from `conversationState` (`agent-directory.ts:291-296`). There is no other machine-wide "busy" signal in the code.
- **When-idle mode / now mode:** the two update modes. When-idle waits until the machine has no working turn. Now (**Update now**) starts at once.
- **Install mode:** how Overdeck is installed on a machine: `npm-global` (installed with `npm install -g @overdeck/core`), `development` (running from a repository checkout or a `pan reload` deployment generation; `overdeckDevMode`, `src/dashboard/server/routes/misc/shared.ts:47`), or `desktop` (the Electron app's embedded server; `OVERDECK_MODE=desktop`, set at `apps/desktop/src/server.ts:90`).
- **Update plan:** for one harness CLI, the argv Overdeck may run to update it, or `null` with a copyable command and a reason when Overdeck must not run it.
- **npm prefix:** the directory that holds a global npm install: a binary whose real path matches `<prefix>/lib/node_modules/<package>/…` was installed by npm into `<prefix>`.

## Requirements

### Functional

- **FR-1 Exact install version for an unsupported machine.** A link the supervisor marks `unsupported` names the exact Overdeck version to install and where: the peer's version on this machine when the peer speaks a newer link protocol, this machine's version on the peer otherwise. This holds for both detection paths (descriptor mismatch and handshake refusal `02`). The detail ends with the exact command, `npm install -g @overdeck/core@<version>`.
- **FR-2 Unsupported is never retried in a loop.** An `unsupported` link is not probed again until **Reconnect** or a restart (already true; kept and tested for the refusal path too).
- **FR-3 Version report.** Every machine answers `GET /api/versions/self` with its Overdeck version, install mode, link protocol, one entry per installed harness CLI (deduplicated by binary) with its version and update plan, and its current update job.
- **FR-4 Fleet table.** `GET /api/machines/versions` on this machine returns one row per machine: this machine first, then every outbound link in link-store order. Online links that answer carry their report; online links that predate this feature (`404`) carry `updateSupported: false`; `unsupported` links carry the install version, place and command from FR-1; `offline`, `connecting` and `revoked` links carry their state, state detail and last known Overdeck version.
- **FR-5 Update all.** `POST /api/machines/update` starts an update job on this machine and on every online linked machine that supports it (or on the listed machines only). It never touches an offline, connecting, unsupported or revoked machine; the response lists each skipped machine with the reason.
- **FR-6 Each harness CLI is updated with its own command.** Order of preference: npm-installed CLIs are updated with `npm install -g --prefix <prefix> <package>@latest` using `<prefix>/bin/npm`; other installs run the harness's own update argv (`claude update`, `codex update`, `kimi upgrade --yes`, `opencode upgrade`). Homebrew installs, Windows, missing update commands, a pinned harness and an unwritable npm prefix are never run; they report `skipped` with a copyable command.
- **FR-7 Overdeck is updated last.** On an `npm-global` machine the job runs the existing `UpdateManager` (`check()` then `install()`), and, when the installed version changed, restarts the dashboard through the same internal path as `POST /api/system/restart-dashboard`. On `development` and `desktop` machines the Overdeck component is `skipped` with the reason, and the harness CLIs still update.
- **FR-8 Running turns.** In when-idle mode a job waits until the machine has no working turn, re-checking every 5 s, and reports how many turns it is waiting for. It never starts on its own while a turn is working, however long it waits; after 30 minutes the row says it is still waiting and points at **Update now**. **Update now** on a waiting job starts it at once. **Cancel** stops a waiting job.
- **FR-9 Before and after versions.** Each component records the version before the job and after it. The Overdeck `after` value is read by the restarted dashboard on boot, from the job file.
- **FR-10 Fenced.** A linked machine may read the version report with a `read:state` machine token. It may start, escalate or cancel an update only with an operator-level link and an `operator` actor stamp. An agent-stamped request, an agent-fenced link and any other non-admin credential get `403`. The fleet routes (`/api/machines/versions`, `/api/machines/update`) refuse any request that arrives through a channel.
- **FR-11 CLI.** `pan machines versions [--json]` prints the fleet table. `pan machines update [--now] [--machine <label>]… [--json]` starts Update all (or the listed machines) and prints what started and what was skipped. `pan machines update --cancel [--machine <label>]…` cancels waiting jobs.
- **FR-12 UI.** Settings → Anywhere gains a **Fleet versions** panel under Machines: one row per machine, one column per harness CLI found anywhere in the fleet, **Update all**, and per-row **Update now** and **Cancel** while that row waits.

### Non-functional

- **NFR-1 Async only.** Every exec in this feature is `execFile` (promisified) or `spawn`, never `execSync`, never a shell string. No new `*Sync` tmux calls. (Repo rule: no `execSync` in dashboard-server-reachable code, PAN-70.)
- **NFR-2 Bounded reads.** `GET /api/machines/versions` waits at most 2.5 s per linked machine (the `linkFetch` bound) and asks all of them in parallel. Harness `--version` results are cached 60 s per binary real path and modification time; a job always re-reads with the cache bypassed.
- **NFR-3 No caller-chosen commands.** Every command an update job runs comes from the machine's own update plan. The request body carries only `mode`. A caller can never choose a version, a package or an argv.
- **NFR-4 Bounded exec.** Each update command runs with stdin closed (`stdio: ['ignore', 'pipe', 'pipe']`), a 10-minute timeout, and keeps the last 2,000 characters of output in the component's `detail` on failure.
- **NFR-5 No protocol bump.** `ENVIRONMENT_PROTOCOL_VERSION` and `LINK_PROTOCOL_VERSION` stay `1`. A machine without this feature is detected by a `404` from `GET /api/versions/self`, not by a protocol change.
- **NFR-6 Tests use fake timers.** The turn wait and the job's install poll are delay logic; their tests use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`, never real waits (repo rule).

## Decisions

- **D-1 Gate on the link protocol, not the environment protocol.** "Protocol gating" in W-LINK7 is the PAN-4645 gate (`linkProtocol` + `capabilities.machineLinks`). Bumping `ENVIRONMENT_PROTOCOL_VERSION` would break desktop clients (D-4645-11). The only gating change here is FR-1's message fix and the structured install hint.
- **D-2 One install command.** The exact command shown for an unsupported machine is `npm install -g @overdeck/core@<version>` (`overdeckInstallCommand(version)` in `packages/contracts/src/machines.ts`). `npm-global` is the default distribution. A desktop or development machine still gets the version, which is the part that matters.
- **D-3 Each machine runs its own job; the viewing machine keeps no fleet state.** **Update all** sends one start request per machine and returns. The fleet table reads each machine's job from that machine's report. Nothing on the viewing machine tracks other machines' jobs, so a restart of any machine, including the viewing one, loses nothing. (Repo principle: store no status you can derive.)
- **D-4 The job file is the one stored piece.** `${OVERDECK_HOME}/fleet-update.json` holds the current or last job. It is written atomically (temp file + rename) at every phase change. It is needed because the Overdeck step restarts the dashboard and the before/after values must survive that. On boot, a job left in `restarting` is finished: Overdeck `after` = the running version; `updated` when it differs from `before`, else `failed` with "the restarted dashboard still runs <v>". A job left in `waiting` or `updating` by a crash is marked `failed` with "interrupted by a dashboard restart".
- **D-5 Machine-wide turn wait.** When-idle waits for zero working entries in the live agent directory, all harnesses together. The Overdeck install replaces files that running agents' `pan` calls read, so a per-harness wait would not protect Overdeck. On a machine that is always busy the operator uses **Update now**; the job never proceeds on its own (FR-8). The 30-minute mark only changes the message.
- **D-6 Harness update data lives in `HarnessCapabilities`.** Two new fields: `updateArgs: readonly string[] | null` (argv after the binary) and `npmPackage: string | null`. The update-plan code reads them and never compares harness names, so `lint:harness-branches` does not grow. Values:

  | Harness | `updateArgs` | `npmPackage` | Why |
  | --- | --- | --- | --- |
  | `claude-code` | `["update"]` | `"@anthropic-ai/claude-code"` | Same commands as `claudeCodeUpgradePlan` |
  | `codex` | `["update"]` | `"@openai/codex"` | Probed `codex update` |
  | `kimi-code`, `acp` | `["upgrade", "--yes"]` | `null` | Probed; `--yes` skips the prompt |
  | `opencode` | `["upgrade"]` | `"opencode-ai"` | Probed; npm package from `system-prerequisites.ts` |
  | `muse` | `null` | `null` | No update command |
  | `prime-agent` | `null` | `null` | Pinned to `0.8` (`compat.ts:19`); `@latest` would break it |
  | `ohmypi` | `null` | `null` | OhMyPi support is being removed; Overdeck does not update it |

  A harness with both `null` is still listed with its version, as `skipped` with `installHint` (or "Overdeck does not update <label>") as the command.
- **D-7 npm first.** When the binary's real path is under `<prefix>/lib/node_modules/<npmPackage>/`, the plan is npm, even when `updateArgs` exists, because npm is the one updater known to work for npm installs (it is what `claudeCodeUpgradePlan` does). `<prefix>/bin/npm` is used when it is executable, else `npm`. An unwritable `<prefix>/lib/node_modules` gives `skipped` with `sudo npm install -g --prefix <prefix> <package>@latest`.
- **D-8 Overdeck reuses `UpdateManager`.** `misc/updates.ts` exports its manager getter (`getUpdateManager()`). The job calls `check()`; when the phase is `available` it calls `install()` and polls `getSnapshot()` every 1 s until `ready` or `error` (10-minute cap). `current` ⇒ component `current`, no restart. There is one npm path for Overdeck, not two.
- **D-9 Restart through one function.** The body of `POST /api/system/restart-dashboard` (`meta.ts:412-452`) moves into `restartDashboardDetached(requester)` in `src/dashboard/server/services/dashboard-restart.ts`. The route and the job both call it, so the job's restart claims the restart gate and never waits on the PAN-3729 banner.
- **D-10 Fencing.** `POST`/`DELETE /api/versions/self/update` carry the `operate` scope row. Through a channel, the handler also requires `credential.kind === 'machine'`, `credential.actor === 'operator'` and `credential.access === 'operator'`; anything else is `403 { error: 'fleet-update-forbidden' }`. Outside a channel it uses `rejectUnsafeDashboardMutationRequest` (the local mutation guard that `POST /api/machines/link` uses) and then requires `scopeSatisfies(credentialScopes(credential), 'admin')` for `device` and `token` credentials. `GET /api/versions/self` carries `read:state`.
- **D-11 404 means "predates fleet updates".** No new capability flag (NFR-5). The fleet table treats a `404` from `GET /api/versions/self` as `updateSupported: false` with "Overdeck <peerVersion> on <label> predates fleet updates. Install <this version>: `npm install -g @overdeck/core@<this version>`".
- **D-12 This machine is updated last in the fan-out.** `POST /api/machines/update` sends the peer requests first (in parallel, each bounded by `linkFetch`), then starts this machine's job, then answers. This machine's restart (if any) happens minutes later, after the response.
- **D-13 One job at a time.** A start request while a job is `waiting` with `mode: 'now'` escalates it (`200`); any other start while a job is active is `409 { error: 'update-in-progress', job }`. `DELETE` on a non-waiting job is `409 { error: 'not-waiting' }`.
- **D-14 Job only on the primary dashboard.** The update routes answer `409 { error: 'not-primary' }` on a peer dashboard, decided by `hostsMachineLinks()` imported from `src/lib/boot-gates.ts` — the same gate `startAnywhere` gets at `main.ts:224`. Never import from `main.ts`.
- **D-15 Version parsing.** The first `\d+\.\d+\.\d+(?:-[0-9A-Za-z.-]+)?` in the combined stdout and stderr of `<binary> --version` (8 s timeout). That matches every probed banner. No match ⇒ version `null`.
- **D-16 Fleet table columns.** The UI shows one column per harness binary found on at least one machine, ordered `claude, codex, kimi, opencode, muse, prime-agent, omp`, then any other binary alphabetically.

### Planning decisions (auto mode)

Planning ran with `pan plan --auto`, so no question was put to the operator. Each default below is also recorded in `plan.autoDecisions[]`.

1. **Unsupported fix scope:** fix the refusal-path version bug and add the install command (FR-1), keep `ENVIRONMENT_PROTOCOL_VERSION` (D-1). *Rationale:* the issue's done-when is "shows `unsupported` with the exact `pan` version to install"; the refusal path currently names the wrong one.
2. **Turn wait granularity:** machine-wide (D-5). *Rationale:* matches FR-29's text ("a machine with a turn in progress") and protects the Overdeck install.
3. **Which harnesses update:** claude, codex, kimi, opencode; muse, prime-agent and omp are listed but not updated (D-6). *Rationale:* those three have no update command, a pinned version, or support being removed.
4. **Update target:** latest published version (npm `latest`/`canary` per the machine's channel; each harness's own "latest"). The caller cannot choose (NFR-3). *Rationale:* "Update all" means update; letting a remote caller pick versions would allow downgrades.
5. **Development and desktop installs:** Overdeck component skipped with a reason; harness CLIs still update (FR-7). *Rationale:* `UpdateManager` already refuses development builds, and the desktop app has its own updater.
6. **Cancel:** included for waiting jobs only (FR-8). *Rationale:* an operator who starts Update all on a busy machine needs a way out other than Update now.
7. **Sibling split:** none; one issue with `sizeJustification`. *Rationale:* the epic already scoped W-LINK7 to this one issue, and its done-when needs the report, the job and the table together.

## Wire shapes

New file `packages/contracts/src/fleet-versions.ts` (exported from `packages/contracts/src/index.ts`). Plain TypeScript interfaces plus `Schema` structs, in the style of `machines.ts`.

```ts
export type FleetInstallMode = "npm-global" | "development" | "desktop"
export type FleetComponentStatus = "pending" | "running" | "updated" | "current" | "skipped" | "failed"
export type FleetJobPhase = "waiting" | "updating" | "restarting" | "done" | "failed" | "cancelled"
export type FleetUpdateMode = "when-idle" | "now"

export interface HarnessVersionView {
  binary: string            // "claude", "codex", "kimi", …
  label: string             // HarnessCapabilities.binaryLabel of the first harness using it
  harnesses: string[]       // runtime names that use this binary, e.g. ["acp", "kimi-code"]
  version: string | null
  updatable: boolean        // true when the plan has an argv
  command: string           // copyable command (the plan's display)
  reason: string | null     // why not updatable
}

export interface FleetComponent {
  name: string              // "overdeck" or a binary name
  label: string             // "Overdeck", "Claude Code", …
  before: string | null
  after: string | null
  status: FleetComponentStatus
  detail: string | null     // reason, or the output tail on failure
}

export interface FleetUpdateJob {
  id: string                // random UUID
  mode: FleetUpdateMode
  phase: FleetJobPhase
  requestedBy: string       // "operator" or "machine:<label>"
  startedAt: string         // ISO
  waitingTurns: number      // working turns at the last check (0 once updating)
  waitingSince: string | null
  finishedAt: string | null
  components: FleetComponent[]
}

export interface MachineVersionsReport {
  environmentId: string
  label: string
  overdeck: { version: string; installMode: FleetInstallMode; linkProtocol: number }
  harnesses: HarnessVersionView[]
  job: FleetUpdateJob | null
}

export interface FleetVersionRow {
  environmentId: string
  label: string
  self: boolean
  state: LinkState | "self"
  stateDetail: string | null
  peerVersion: string | null
  report: MachineVersionsReport | null
  updateSupported: boolean
  install: { version: string; on: "this-machine" | "peer"; command: string } | null
  error: string | null
}

export interface FleetVersionsResponse { rows: FleetVersionRow[] }

export interface FleetUpdateResponse {
  started: { environmentId: string; label: string; job: FleetUpdateJob }[]
  skipped: { environmentId: string; label: string; reason: string }[]
}

export const FLEET_UPDATE_STILL_WAITING_MS = 30 * 60_000
```

## Hazards

- **H-1 Busy machines never go idle.** The operator's own machine usually has working agents, so when-idle can wait indefinitely. This is by design (D-5); the 30-minute message and **Update now** are the exits.
- **H-2 Development machines do not update Overdeck.** `pan reload` deployments and repository checkouts report `development`; the Overdeck component is `skipped`. Do not try to make the job run `pan reload` — the Flywheel is the deployer on such machines.
- **H-3 npm replaces the running server's files.** `npm install -g @overdeck/core` overwrites the dist the dashboard runs from, which is why the restart follows at once (D-8, D-9). Lazy imports between install and restart may fail; the existing `UpdateManager` path has the same property.
- **H-4 `codex update` and `opencode upgrade` might prompt.** Implementation checkpoint for WI-3/WI-5: on a scratch machine or with `--help` only, confirm neither waits for input when stdin is closed. Fallback: stdin is `ignore`, so a prompt reads EOF and the command exits or times out at 10 min; the component becomes `failed` with the output tail and the copyable command, and the other components still run. Never run a real update while implementing on the operator's machine.
- **H-5 Version caches.** `readClaudeCodeVersion` keeps its own 60 s cache for the Claude Code banner; the job reads with the fleet module's `readCliVersion(refresh: true)`, never through `readClaudeCodeVersion`, so a stale "after" cannot appear.
- **H-6 Peer dashboards.** A second dashboard on the same home must not run a second job (D-14).
- **H-7 New routes and the no-loss matrix.** All five routes need rows or CI fails (WI-3, WI-6, WI-7).
- **H-8 File sizes.** `link-supervisor.ts` (658 lines) and `meta.ts` (472) are under the 1,000-line ceiling; WI-4 shrinks `meta.ts`. No allowlist changes.
- **H-10 Real CLIs are reachable from any server that shares the operator's `HOME`.** Binary resolution searches home directories and a login shell (WI-10 "Safety first"). Unit tests inject every exec and resolver; the smoke isolates `HOME`, `PATH` and `SHELL` and guards before updating. Never run `POST /api/machines/update` or `pan machines update` against the operator's live dashboard while implementing.
- **H-11 `typecheck` skips test files.** `npm run typecheck` excludes `*.test.ts`, so test helpers that build `HarnessCapabilities` literals will not fail typecheck after WI-2 adds two required fields. Grep tests for `CAPABILITIES` literals and partial capability objects and add the fields there too.
- **H-9 Gate tests.** Do not add source-grep tests or `skipIf`/`.only` (`lint:source-introspection`, test-skip gate). Assert behavior through injected deps.

## Non-goals

- Updating a machine that is offline, connecting, unsupported or revoked; such machines are listed and skipped.
- Choosing a target version for Overdeck or a harness (always latest on the machine's channel).
- Updating OhMyPi (`omp`), Muse or Prime Agent; installing a harness CLI that is missing.
- Updating Overdeck on development or desktop installs, or running `pan reload` from the job.
- Restarting or resuming running agents or conversations after a harness update (running sessions keep their binary; new launches use the new one).
- Any change to `ENVIRONMENT_PROTOCOL_VERSION`, `LINK_PROTOCOL_VERSION`, the descriptor, the heartbeat or `MachineLinkView`.
- Per-harness turn waiting, scheduled or automatic fleet updates.
- Fleet usage (FR-31), settings comparison (FR-32) and every other PAN-2350 work item (sibling issues).
