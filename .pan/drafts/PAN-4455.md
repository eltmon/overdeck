# PAN-4455: Overdeck Anywhere — "Continue on another device" from the conversation itself

**Issue:** [PAN-4455](https://github.com/eltmon/overdeck/issues/4455) · **Epic:** [PAN-2350](https://github.com/eltmon/overdeck/issues/2350) · **Depends on:** PAN-4446 (merged as `1ccfed74215`, #4461: `POST /api/vault/sync`, `syncVaultNow()`), PAN-4447 (merged as `073615936f0`, #4462: `conversation.vaultContinuity`, `VaultContinuityNotice`) · **Planned:** 2026-10-01 (auto mode) against `900462b4444`

## Summary

The conversation header menu and the conversation row menu get one new entry, **Continue on another device**. It opens a dialog with two tabs:

- **Open on another screen** (this machine stays in charge): a QR code and a Copy button for `<trusted address>/conv/<id>`, optionally with a one-time pairing credential in the URL fragment so an unpaired phone pairs and lands on the conversation in one step. No new server route.
- **Hand off to another machine** (Session Vault): **Hand off now** settles this conversation into the vault immediately through the vault-service queue (one new route), reports the version, and leaves a notice above the composer saying new messages here will be saved as a separate copy.

On the receiving machine, vault browse rows get **Check for new conversations**, which runs PAN-4446's queued Sync now.

## Glossary

- **Managed conversation** — a row in the `conversations` table of `overdeck.db`, read with `getConversationByName(name)` (`src/lib/overdeck/conversations.ts`, line 613). The frontend type is `Conversation` in `src/dashboard/frontend/src/components/CommandDeck/ConversationList.tsx` (fields used here: `id: number`, `name`, `title?`, `harness?`, `sessionAlive`, `origin?`, `vaultContinuity?`).
- **Vault browse row** — a read-only conversation row (`origin === 'vault'`, name `vault-<vaultId>`) for a vault record another machine owns (PAN-4436). It is not in `overdeck.db`.
- **Session Vault / settle / version** — the encrypted cross-machine transcript store (`src/lib/vault/`, `docs/SESSION-VAULT.md`). `settle()` (`src/lib/vault/settle.ts`, line 205) appends new transcript lines as a `Settlement` to a record and writes it with `store.casRef`. On the git backend `casRef` fetches, commits and **pushes** in one step (`src/lib/vault/store/git.ts`, lines 286–323), so a settle that returns `append` is already on the remote. A record's version is `(record.settlementsArchive?.length ?? 0) + record.settlements.length` (settle.ts, line 417).
- **Settle verdicts** — `SettleResult` (settle.ts, lines 71–86): `noop`, `append` (with `version`, `lines`, optional `forkedFrom`, optional `wip`), `diverged`, `blocked` (secret-scan `hits: { line, pattern }[]`), `excluded`, `offline`.
- **WIP snapshot** — the uncommitted-code bundle a settlement can carry (`src/lib/vault/wip-capture.ts`). `WipCaptureResult` (lines 39–42): `{ status: 'off' | 'throttled' | 'unchanged' | 'no-git' }`, `{ status: 'captured' }`, or `{ status: 'skipped'; wip: { skipped: 'clean' | 'too-large' | 'secret' | 'no-git' | 'error'; bytes?; reason? }; hits?: { file, pattern }[] }`. `WipMode` is `'auto' | 'force' | 'off'`.
- **P-6 fork** — when this machine settles new lines into a record another machine now owns, `settle()` writes a new record titled `<title> (continued on <this machine>)` and returns `forkedFrom` (settle.ts, lines 238–262).
- **Vault service queue** — `enqueueVaultOperation(label, run)` in `src/dashboard/server/services/vault-service.ts` (line 133): every dashboard vault operation runs one at a time through it.
- **Credential kind** — what `resolveDashboardCredential(headers)?.kind` returns (`src/dashboard/server/routes/dashboard-auth.ts`): `internal-token` (CLI, agents), `root-session` (a browser on this machine), `device` (a paired device), `token` (a scoped API token).
- **Trusted address / reachable address** — an origin in `getTrustedOrigins()`; `GET /api/anywhere/status` returns them as `addresses: { origin, loopback }[]`. A reachable address is one with `loopback: false`.
- **Pairing credential** — a one-use, 10-minute `odp_…` value from `POST /api/pairing/credentials` (`src/dashboard/server/routes/pairing.ts`, line 64; root session or internal token only). It is only ever put in a URL fragment `#pair=<credential>`. `consumePairingCredential()` (`src/dashboard/frontend/src/lib/wsTransport.ts`, lines 83–94) strips `pair` from the fragment, keeps `pathname` and `search`, and exchanges it for a device cookie.
- **Dialog host** — a component mounted once at the app root that renders a dialog from a zustand store, so the dialog outlives the menu that opened it. Precedent: `LinkPullRequestDialogHost` (`src/dashboard/frontend/src/components/chat/LinkPullRequestDialog.tsx`, lines 17–55; mounted in `src/dashboard/frontend/src/main.tsx`, line 63).
- **No-loss matrix** — `tests/unit/lib/overdeck/no-loss-matrix.ts`; every HTTP route needs a row or CI fails.
- **File-size guard** — `scripts/lint-file-size.sh`: a `src` file over 1000 lines may not grow past its `origin/main` count or its `scripts/file-size-allowlist.txt` cap (last row wins). Agents may not raise a cap.

## Decisions (made in this document)

- **D-1 One dialog, two tabs, one global host.** A zustand store `useContinueOnDeviceStore` holds the target conversation; `ContinueOnDeviceDialogHost` is mounted in `main.tsx` next to `LinkPullRequestDialogHost`. Both menus call `openContinueOnDevice(target)`. The dialog therefore outlives the menu.
- **D-2 Default tab.** `'handoff'` when the status has no reachable address **and** `vault.state === 'ready'` **and** the harness is `claude-code` or `codex`; otherwise `'screen'`.
- **D-3 Credential kind reaches the browser through the status route.** `GET /api/anywhere/status` gains `viewer: { kind: 'root-session' | 'device' | 'token' | 'internal-token' | null }`, computed in the route from `resolveDashboardCredential(request.headers)`. No new route (the issue forbids one for this tab).
- **D-4 "Also pair the device"** is rendered only when `viewer.kind === 'root-session'`, checked by default. The plain link `<address>/conv/<id>`, its Copy button and its QR code render as soon as an address is selected, whatever the checkbox says (issue AC 2). When the box is checked, a **Create pairing link** button renders below them; clicking it calls `issuePairingLink()` once and **replaces** the link, Copy value and QR code with `<address>/conv/<id>#pair=<credential>` (the `credential` field, never `pairingPath`) plus the expiry text. Unchecking, changing the address, or expiry followed by unchecking reverts to the plain link. Opening the dialog never mints a credential.
- **D-5 Link shape.** `${origin}/conv/${target.id}` plus `?view=terminal` when the panel's view mode was `terminal` at open time (the row menu always passes `conversation`). The origin is always a reachable (non-loopback) trusted address; the tab never offers a loopback or "this machine only" choice.
- **D-6 Hand-off goes through the same queued settle as the poller.** `queuedSettle` is split: a new exported `settleOnQueue(path, harness, wip, { readBack })` returns the outcome; the poller keeps a thin wrapper that awaits it and logs failures (unchanged behavior). The hand-off calls `settleOnQueue(…, 'force', { readBack: true })`. The record is read back **inside the same queue slot**, so a sync cycle cannot reset the git clone between the settle and the read.
- **D-7 WIP mode `force`.** `pan vault save` and the poller's "conversation left the active list" path both use `force`; a hand-off is exactly when uncommitted code should travel.
- **D-8 A `noop` settle is still a successful hand-off.** The poller usually settled the conversation already. The response reports the latest version and its settlement time with `alreadySaved: true`; the dialog shows the same "Saved as version …" sentence (it is true). A `noop` with no readable record means the transcript has nothing to save yet → `not-saved` / `empty`.
- **D-9 Response contract.** `handOffConversation(name)` in a new `services/vault-handoff.ts` returns `{ status: number; body: HandOffBody }` (the `vault-continue.ts` precedent), with `body.result` as the discriminator (see WI-2). 200 only for `saved`.
- **D-10 A code-snapshot problem is not a success.** When the transcript saved but the WIP snapshot was skipped for `secret`, `too-large` or `error`, the response is still 200 `saved` with `wipProblem: { message, fix }`; the dialog shows "The conversation was saved (version N), but its code snapshot was not." plus the message and fix, never the "Saved as version" sentence, and records no composer notice.
- **D-11 Fork after adoption.** When `forkedFrom` is set, the success sentence says the turns were saved as a separate copy (WI-6 text).
- **D-12 Messages are built in the hand-off service**, not imported from `src/cli/commands/vault/save.ts` (the server never imports `src/cli/`). Blocked-line fix: `pan vault allow-secret <nativePath> <line>`. Blocked-snapshot fix: `pan vault allow-secret <vaultId-8> --file <file>`.
- **D-13 Who may hand off.** Root session and paired device only (the existing `operatorVaultMutation` shell); internal token and scoped tokens get 403 and the service is never called. A device also needs the `admin` scope, which `route-scopes.ts` already requires for unlisted routes; no row is added there.
- **D-14 Hand-off works on any dashboard.** Like setup/join (PAN-4446 D-7), it does not require the sync loop to be running; only Sync now does.
- **D-15 Composer notice state is per browser.** A hand-off is an operator act, not derivable state, so `useHandoffNoticeStore` (zustand `persist`, localStorage key `overdeck:handoff-notices`) records `{ [conversationName]: { at: string } }`. It is recorded only after a `saved` response with `wipProblem === null` and only when `target.sessionAlive` was true. It renders only while `conversation.sessionAlive` is true; an effect clears the entry when the conversation is seen with `sessionAlive === false`. **Keep working here** clears it; **Stop this session** calls the existing `useConversationMutations(...).stop(name)` and clears it.
- **D-16 PAN-4447's notice supersedes.** When `conversation.vaultContinuity` is set, `ComposerFooter` shows `VaultContinuityNotice` only, never both.
- **D-17 "Check for new conversations"** is a menu item on vault browse rows only, in its own component `VaultRowSyncMenuItem`, which queries `['vault-status']` only while the menu is open, renders only when `running === true`, posts `POST /api/vault/sync`, invalidates `['conversations']` and `['vault-status']` on 200, and toasts the server `error` otherwise.
- **D-18 The menu entry is hidden for vault browse rows** (`origin === 'vault'`): there is nothing local to hand off.
- **D-19 No line-count field is added to the vault list cache.** The integration test proves the line count on machine B by reading the synced record's last `Settlement.lines`. Changing the list cache is out of scope.
- **D-20 ConversationPanel stays within its cap** by extracting the About drawer into `ConversationAboutDrawer.tsx` in the same item that adds the menu entry. Never raise the allowlist cap.
- **D-21 The QR image is duplicated** (about 10 lines) in the new tab instead of exporting it from `PairDeviceDialog.tsx`, so the pair dialog and its tests stay untouched.

## Requirements

### Functional

- **FR-1** The conversation header ⋮ menu shows **Continue on another device** for every non-vault conversation; it opens the dialog for that conversation.
- **FR-2** The conversation row ⋮ menu shows the same entry for non-vault rows.
- **FR-3** The dialog has the tabs **Open on another screen** and **Hand off to another machine**, opened on the tab D-2 selects.
- **FR-4** The screen tab offers only reachable trusted addresses; the QR code and the Copy button encode `<address>/conv/<id>` (D-5). With no reachable address it shows no QR code and offers adding one.
- **FR-5** For a root session, **Also pair the device** (default on) produces `<address>/conv/<id>#pair=odp_…`; opening that link in a fresh browser pairs it and shows the conversation with the fragment removed.
- **FR-6** For any other credential kind, **Also pair the device** is not rendered and no pairing credential is requested.
- **FR-7** `GET /api/anywhere/status` includes `viewer.kind`.
- **FR-8** `POST /api/vault/sessions/by-conversation/:name/settle` settles that conversation through the vault-service queue with WIP mode `force` and returns the D-9 contract.
- **FR-9** The route returns 403 for the internal token and for scoped tokens, without calling the service.
- **FR-10** The hand-off tab, when the vault is `ready` and the harness is supported, shows **Hand off now**; on success it shows `Saved as version <n> at <time>. On your other machine, open "<title>" from <machine> and click Continue here.`
- **FR-11** A blocked save shows each blocked line number and pattern and the `pan vault allow-secret` command, and no "Saved as version" text.
- **FR-12** When the vault is off, locked or rotation-pending, or the harness is unsupported, the hand-off tab shows the reason and its fix action and never calls the route.
- **FR-13** After a successful hand-off of a live conversation, the composer shows `Handed off at <time>. New messages here will be saved as a separate copy.` with **Keep working here** and **Stop this session**, until dismissed or the session stops.
- **FR-14** Vault browse rows' menu shows **Check for new conversations** when the vault service runs; it runs one queued sync.
- **FR-15** A hand-off settles the transcript so that a second machine running `pan vault sync` lists the record and reads the new line count.

### Non-functional

- **NFR-1** No new server route other than FR-8; no change to settle, adoption or fork semantics.
- **NFR-2** No blocking calls in server-reachable code (no `execSync`); the hand-off runs on the existing promise queue.
- **NFR-3** A pairing credential appears only in a URL fragment and in React component state, never in a toast, log, query cache or `localStorage`.
- **NFR-4** `npm run lint` passes, including the file-size guard: `ConversationPanel.tsx` ends at 1531 lines or fewer.
- **NFR-5** Browser verification uses an isolated dashboard and fresh Playwright browser contexts; it never touches the operator's live dashboard or another agent's browser.

```ts
// After
export type QueuedSettleOutcome =
  | { status: 'unavailable'; opened: Exclude<VaultOpenResult, { status: 'open' }> }
  | { status: 'settled'; result: SettleResult; record: SessionRecord | null };

/**
 * The one dashboard settle path (PAN-4455 D-6): the poller and the hand-off route
 * both call it. `readBack` reads the settled record inside the same queue slot.
 * Throws whatever `settle()` throws; callers decide whether to log or report.
 */
export function settleOnQueue(path: string, harness: string, wip: WipMode, options: { readBack?: boolean } = {}): Promise<QueuedSettleOutcome> {
  return enqueueVaultOperation('settle', async () => {
    const opened = await deps.openVaultContext();
    if (opened.status !== 'open') return { status: 'unavailable' as const, opened };
    const config = await deps.readVaultConfig();
    const { store, keys } = opened.vault;
    const result = await deps.settle({ nativePath: path, harness, store, keys, config, wip });
    const record = options.readBack && result.vaultId ? await readRecordOrNull(store, keys, result.vaultId) : null;
    return { status: 'settled' as const, result, record };
  });
}

/** A failing settle logs once per distinct message and never throws out of the poller's timers (NFR-6). */
async function queuedSettle(path: string, harness: string, wip: WipMode): Promise<void> {
  try {
    await settleOnQueue(path, harness, wip);
  } catch (error) {
    console.warn(`[vault] settle failed for ${path}:`, error);
  }
}
```

Keep the existing doc comment that sits above `queuedSettle` and the stray `/** Idempotent … */` comment untouched except to move the NFR-6 sentence onto the wrapper as shown.

### WI-2 `handoff-service` — `handOffConversation(name)` (backend)

**Files:** new `src/dashboard/server/services/vault-handoff.ts`, new `tests/unit/dashboard/server/services/vault-handoff.test.ts`.

```ts
export interface VaultHandoffDeps {
  getConversation?: (name: string) => LegacyConversation | null;   // default getConversationByName
  resolvePath?: (conv: LegacyConversation) => Promise<string | null>; // default resolveSessionFile
  settle?: typeof settleOnQueue;                                      // default settleOnQueue
  machineLabel?: () => Promise<string>;                               // default (await ensureEnvironmentIdentity()).label
}

export type HandOffBody =
  | { result: 'saved'; vaultId: string; version: number; savedAt: string; title: string; machineLabel: string;
      logLines: number; alreadySaved: boolean; forkedFrom: { vaultId: string; version: number } | null;
      wipProblem: { message: string; fix: string | null } | null }
  | { result: 'blocked'; error: string; hits: Array<{ line: number; pattern: string }>; fixes: string[] }
  | { result: 'offline'; error: string; fix: string }
  | { result: 'not-saved'; reason: 'diverged' | 'excluded' | 'empty'; error: string }
  | { result: 'unsupported-harness'; error: string }
  | { result: 'vault-unavailable'; state: 'off' | 'rotation-pending' | 'key-missing' | 'key-mismatch'; error: string }
  | { result: 'not-found'; error: string };

export async function handOffConversation(name: string, deps: VaultHandoffDeps = {}): Promise<{ status: number; body: HandOffBody }>;
```

Steps, in order:
1. `conv = getConversation(name)`; `null` → 404 `{ result: 'not-found', error: 'No conversation named <name>.' }`.
2. `harness = conv.harness ?? 'claude-code'`; not `claude-code`/`codex` → 422 `{ result: 'unsupported-harness', error: 'Hand-off works for Claude Code and Codex conversations. This conversation runs on <harness>.' }`.
3. `nativePath = await resolvePath(conv)`; `null` → 404 `{ result: 'not-found', error: 'This conversation has no transcript file yet.' }`.
4. `outcome = await settle(nativePath, harness, 'force', { readBack: true })`.
5. `outcome.status === 'unavailable'` → 409 `{ result: 'vault-unavailable', state: outcome.opened.status, error: vaultUnavailableMessage(outcome.opened) }` (import from `vault-service.ts`).
6. Map `outcome.result.verdict`:

## Repo rules restated

- Quality gates before `pan done`: `npm run typecheck`, `npm run lint`, and `npx vitest run <the test files you touched>`. Never run the full `npm test` on the host.
- Frontend tests run with `npm --prefix ./src/dashboard/frontend run test -- <files>`.
