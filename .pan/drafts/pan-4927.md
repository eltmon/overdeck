# PAN-4927 — Overdeck MCP for agents and bots

**Status:** draft for operator review · **Revision:** 1 (2026-11-03) · **Author:** Claude Opus 5.5 (PRD writer for the orchestrator conversation bc25680b)
**Issue:** [PAN-4927](https://github.com/eltmon/overdeck/issues/4927) · **Builds on:** [PAN-4649](https://github.com/eltmon/overdeck/issues/4649) (`.pan/drafts/pan-4649.md`, the MCP server), PAN-4651 (fleet reach), and the phone-app building blocks [PAN-4829](https://github.com/eltmon/overdeck/issues/4829), [PAN-4833](https://github.com/eltmon/overdeck/issues/4833), [PAN-4834](https://github.com/eltmon/overdeck/issues/4834), [PAN-4835](https://github.com/eltmon/overdeck/issues/4835) (all closed)
**Ships:** one epic, no phases. Each work item becomes a child issue that runs through the normal pipeline; the Flywheel orchestrates them. "Build order" orders the items by dependency only.

**Why this exists.** Overdeck already serves an MCP server with 10 tools (`src/lib/mcp/`), but only outside tools use it, through Copy MCP URL or `pan mcp serve`. Overdeck's own agents never get it: they run `pan` over Bash with this machine's internal token, which is `admin`. So an agent's actions carry no identity and no scope, and everything an agent does needs a CLI verb and a Bash call. t3code (nightly v0.1.7-nightly.20261103.4119) gives every agent one MCP endpoint, a per-thread token and short instructions, and lets outside clients sign in with OAuth. This epic does the same for Overdeck: every managed agent gets the Overdeck tools with its own scoped token; agent workflow becomes tools; and outside bots (Hermes, OpenClaw, Grok Build, Grok Bot, the xAI API) get secure, revocable access through real, open-source plugins.

**Two reach paths for bots, both with TLS or Noise ending on hardware the operator controls.** A self-hosted bot runs the **Overdeck connector** next to it: a small Node process that pairs with one machine and reaches it over the existing end-to-end encrypted channel (direct WebRTC, or the TURN relay on the relay plan). A hosted bot that cannot run a process (Grok Bot, the xAI API) uses an opt-in public `/mcp` through Tailscale Funnel with OAuth. Nothing on overdeck.ai ever sees plaintext MCP traffic.

## Glossary

- **MCP (Model Context Protocol):** a JSON-RPC protocol an AI client uses to list and call tools on a server.
- **Overdeck MCP server:** the tool module in `src/lib/mcp/` (`createOverdeckMcpServer`, `src/lib/mcp/server.ts:37`). Two transports serve it today: `POST /mcp` on the dashboard (`src/dashboard/server/routes/mcp.ts`) and `pan mcp serve` over stdio (`src/cli/commands/mcp.ts`). Every tool calls an ordinary dashboard HTTP route with the caller's token.
- **Tool:** one MCP operation, an `OverdeckTool` (`src/lib/mcp/tool.ts:16-21`): `name`, `description`, `inputSchema`, `run`.
- **Access token:** an `odk_<64 hex>` credential in `~/.overdeck/access-tokens.json`, managed by `src/lib/access-tokens.ts`. Only its SHA-256 is stored. Each record has `scopes` and a `kind`: `device`, `token`, `machine` or `phone` (`access-tokens.ts:75`).
- **Scope:** one of `read:events`, `read:state`, `read:conversations`, `read:costs`, `read:settings`, `tell`, `operate`, `approve`, `forward`, `admin` (`access-tokens.ts:62-73`). `admin` satisfies every scope and `operate` satisfies `tell` (`scopeSatisfies`, line 172).
- **Route-scope table:** `ROUTE_SCOPES` in `src/dashboard/server/route-scopes.ts:28-153`, the one list of which scope each `METHOD path` needs. An unlisted route needs `admin`.
- **No-loss matrix:** `tests/unit/lib/overdeck/no-loss-matrix.ts`. Every HTTP route in a top-level file of `src/dashboard/server/routes/` must have a row, or `tests/unit/lib/overdeck/no-loss-matrix.test.ts` fails. `src/dashboard/server/__tests__/route-scopes.test.ts:12` also fails when a route-scope row has no matrix row.
- **Managed agent:** any harness session Overdeck launches: a work agent, a role run (plan, review, test, ship, flywheel, strike, sequencer, knowledge, worker; `src/lib/agents/role.ts:6`), or a **conversation** (a chat session started from the dashboard, `handleConversationCreate`, `src/lib/overdeck/conversation-runtime.ts:994`).
- **Harness:** the agent program: `claude-code`, `codex`, `acp`, `opencode`, `kimi-code`, `ohmypi`, `muse`, `prime-agent` (`RuntimeName`, `src/lib/runtimes/types.ts:46`).
- **Agent token:** a new kind of `kind: 'token'` record this PRD adds (W-TOK1). It carries `agentId` and `agentKind`, is minted when its agent launches and is revoked when it stops.
- **Self route:** a new route under `/api/self/` that acts for the calling agent. It accepts only an agent token and finds the agent from the token, never from the request body.
- **Job:** a `pan` CLI command a self route runs as an asynchronous child process for the calling agent (D-11).
- **Wait chunk:** one blocking call of at most 50 s (`WAIT_CHUNK_MS = 50_000`) that returns early when the awaited state changes (D-12).
- **Outside client / bot:** an MCP client Overdeck did not launch: Claude Desktop, Hermes, OpenClaw, Grok Build, Grok Bot, the xAI API.
- **Hermes:** Hermes Agent, a self-hosted chat agent (`~/Projects/hermes-agent`, checkout 2026-11-03, HEAD `9aa8a3e00c`).
- **OpenClaw:** a self-hosted agent gateway (`~/Projects/OpenClaw`, checkout 2026-05-07, HEAD `6110e47be0`; older than the current release, see CP-7).
- **Grok Build:** xAI's local coding agent. It loads plugins from `.grok-plugin/plugin.json` and stdio MCP servers from `.mcp.json`.
- **Grok Bot:** xAI's hosted assistant. It loads Cursor-format plugins (`.cursor-plugin/plugin.json`, `mcp.json` with a remote `url`). It runs on xAI's servers and cannot reach a laptop.
- **Directory:** the overdeck.ai connection service `services/connect` (`wss://connect.overdeck.ai/v1/directory`). Machines register with `hello`; directory **clients** register with `hello-client` and never count as machines (PAN-4829, `services/connect/src/client-state.ts`).
- **Secure channel:** the Noise handshake plus `@hyperswarm/secret-stream` between two Overdeck endpoints (`packages/anywhere-channel`, PAN-4833). **Pairing mode** uses a one-time `odp_` code; **link mode** pins the responder's public key.
- **Routes `rtc://` and `rtc+turn://`:** a WebRTC data channel to a machine, direct or through the TURN relay (relay plan only). Only ciphertext crosses either.
- **Overdeck connector:** a new Node process (W-CONN2), started with `pan mcp connector serve`. It runs next to a bot, joins the directory as a client, pairs with one machine, and serves the Overdeck MCP tools to the bot on loopback HTTP and stdio, forwarding every tool call over the secure channel.
- **Connector credential:** a new access-token kind `connector` (W-CONN1), bound to the connector's link public key. It authenticates only inside a link-mode channel from that key, like `phone` (PAN-4835).
- **Tailscale Serve / Funnel:** Serve publishes a local port to the tailnet only. Funnel publishes it to the public internet on port 443, 8443 or 10000.
- **OAuth 2.1 terms:** *protected-resource metadata* (RFC 9728) tells a client which authorization server guards a resource; *authorization-server metadata* (RFC 8414) lists its endpoints; *dynamic client registration* (DCR, RFC 7591) lets a client register itself; *PKCE S256* binds the authorization code to a secret the client holds.

## Requirements

### Functional

- **FR-1 Every managed agent gets the Overdeck tools.** Every work agent, role run and conversation on `claude-code`, `codex`, `acp` or `opencode` that runs on this host starts with an MCP server named `overdeck` and a short instructions block. Other harnesses get the instructions with `pan` equivalents (D-13).
- **FR-2 Per-agent token.** Each such agent has its own agent token, minted at launch, scoped by role (D-8), never `admin` or `forward`, and revoked when the agent stops, is killed, or its issue is closed out. A crash leaves no live token for more than one boot sweep.
- **FR-3 Agent workflow tools.** An agent can claim and complete checklist items, signal done, hand off, and write a worker report through tools, acting only for itself.
- **FR-4 Delegation and waiting.** An agent can delegate a task to a worker, wait for it, read its status, and cancel it; start, wait for and stop lanes; start an issue; stop or interrupt a conversation. Every wait returns within 50 s and returns early on a state change.
- **FR-5 Scheduling.** An agent can create, list, change and delete one-shot scheduled messages and recurring schedules for a conversation.
- **FR-6 Memory.** An agent can add a curated memory fact and search memory.
- **FR-7 Secrets.** An agent can ask the operator for a secret. The operator answers in a masked input in the dashboard. The value reaches only that agent, as a 0600 file, and never enters a transcript, tool argument or log.
- **FR-8 Link a machine.** An agent can ask the operator to link another machine. The dashboard shows a card that opens the existing Link a machine flow; the pairing code never passes through the agent.
- **FR-9 Pull requests.** An agent can link a PR to its conversation and watch it. A watched PR's check, review, mergeability or state change is delivered to the agent as a message.
- **FR-10 Approvals everywhere.** Tools answer every pending-input kind Overdeck already routes (permission, AskUserQuestion on every harness that supports it, pane choice, Pi ask, Codex approval, plan approval), and `list_pending_input` covers this machine and every online linked machine.
- **FR-11 OAuth on `/mcp`.** An outside client can register itself, sign in with PKCE S256, and get a 30-day access token plus a rotating refresh token. The operator approves each sign-in in the dashboard and picks its access level. Each sign-in is listed and revocable in Settings → Access Tokens.
- **FR-12 Public `/mcp` (opt in).** With a Settings switch on, `/mcp` and the OAuth endpoints answer through Tailscale Funnel, only with OAuth-issued tokens, rate limited and audited. Off by default.
- **FR-13 Overdeck connector.** A self-hosted bot reaches one machine through `pan mcp connector serve`, which signs in to overdeck.ai, joins the directory as a client, pairs once by code, dials `rtc://` or `rtc+turn://`, and serves the Overdeck tools on loopback HTTP and stdio.
- **FR-14 Connect a bot.** Settings → Anywhere has a "Connect a bot" dialog: pick Hermes, OpenClaw, Grok Build, Grok Bot or the xAI API; choose scopes (defaults `read:state, read:conversations, tell`; `operate`, `approve` opt in); get a pairing code or a token and the exact config for that platform.
- **FR-15 Integration packages.** `integrations/hermes/`, `integrations/openclaw/`, `integrations/grok-build/`, `integrations/grok-bot/` are real, installable, MIT plugins with their own README, version and tests, sharing one Overdeck skill text. CI builds and tests each one. Publishing to outside registries is a separate operator-approved step (D-5).
- **FR-16 Documentation.** Every changed surface is documented in the same change set (W-DOC).

### Non-functional

- **NFR-1 One authority.** Every tool calls a dashboard route, and `route-scopes.ts` judges it. No tool reaches a library function directly. Agent-only tools also require an agent token in the route handler.
- **NFR-2 Secrets stay out of argv, env exports, launchers and transcripts.** Agent tokens, connector tokens, refresh tokens and requested secrets live only in 0600 files under `~/.overdeck/` (or the connector's home) and in `Authorization` headers. No token in a URL.
- **NFR-3 Async only.** No `execSync`, `spawnSync` or `execFileSync` in server-reachable code; no new `*Sync` function anywhere; async tmux only (repo rules `no-execsync-server`, `async-tmux`, `prefer-async`). Existing sync callers stay as they are.
- **NFR-4 Fake timers.** Tests of TTLs, waits, retries, rate limits and sweeps use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`, never real sleeps (repo rule `fake-timers-for-retry-tests`). Tests that touch happy-dom use an `AbortController` plus `setTimeout`, not `AbortSignal.timeout`, which ignores fake timers.
- **NFR-5 File size.** Every new module stays under 600 lines. Files already near or above the 1,000-line guard (listed in Facts) grow by at most the stated budget in each work item; put logic in new modules and call it with one line.
- **NFR-6 Effect boundary.** No new exported Effect wrapper around in-repo Promise or sync code and no sync/async twins; `npm run lint:effect-facades` must not rise (`scripts/effect-facades-baseline.txt`).
- **NFR-7 No plaintext through overdeck.ai.** Connector traffic is Noise-encrypted end to end; the directory and the TURN relay see only ciphertext. Public `/mcp` ends TLS on the operator's machine (Funnel). There is no MCP relay on overdeck.ai.
- **NFR-8 Bounded waits.** No tool call blocks longer than 50 s. Instructions tell agents never to poll in a loop.
- **NFR-9 Every new HTTP route** is in a top-level file of `src/dashboard/server/routes/` (the no-loss test reads only that directory, `no-loss-matrix.test.ts:34`), has a row in `tests/unit/lib/overdeck/no-loss-matrix.ts`, and has a row in `route-scopes.ts` unless this PRD names it as an exception with its own check (`/mcp`, `/.well-known/*`, `/oauth/mcp/*`).
- **NFR-10 Small tool lists.** `tools/list` returns only the tools the caller can use: agent-only tools only to agent tokens, and only tools whose route scope the token holds. The instructions block is at most 1,500 characters.
- **NFR-11 Least privilege for bots.** Bot tokens and connector credentials never carry `admin`, `forward`, `read:settings` or `read:costs`.

## Decisions

- **D-1 Pipeline.** Every work item becomes a child issue of PAN-4927 and runs through `pan start` and the review pipeline. The Flywheel orchestrates them. (Operator, 2026-11-03.)
- **D-2 Every managed agent gets the Overdeck MCP server**, with a per-agent scoped token minted at launch and revoked when the agent stops. (Operator, 2026-11-03.)
- **D-3 Reach for outside bots.** (Operator, 2026-11-03; connector added by the orchestrator the same day.)
  1. **Self-hosted bots (Hermes, OpenClaw, Grok Build on another computer) use the Overdeck connector** by default (W-CONN*). Encryption ends inside the bot's own container, the relay and overdeck.ai see only ciphertext, no Tailscale is needed, and the relay plan has a concrete use.
  2. **Tailscale is the alternative** for self-hosted bots: Tailscale inside the bot's container with an ephemeral, tagged auth key whose ACL reaches only the dashboard host on 443, and the bot calls `https://<machine>.<tailnet>.ts.net/mcp` with a bearer token. Each integration README documents it as a second section.
  3. **Hosted bots (Grok Bot, the xAI API) use the opt-in public `/mcp`** through Tailscale Funnel with OAuth, because nobody can run a process on xAI's servers. TLS ends on the operator's machine.
  4. **No MCP relay on overdeck.ai.** A relay would have to decrypt traffic, which breaks the rule against unencrypted traffic through Overdeck's servers.
- **D-4 Bot scopes.** Default `read:state, read:conversations, tell`. `operate` and `approve` are opt-in per bot. A bot never gets `admin`, `forward`, `read:settings` or `read:costs` (NFR-11). `read:events` is not offered: no tool needs it.
- **D-5 Integration packages** live in this repo under `integrations/<platform>/`, MIT. The work items build and test them and write publish instructions in each `PUBLISHING.md`. Publishing to npm, PyPI or any plugin catalog is a separate step the operator approves at the end; no work item publishes.
- **D-6 An agent token is a `kind: 'token'` record with three new optional fields:** `agentId` (the agent id, or the conversation name), `agentKind: 'agent' | 'conversation'`, and `role` (the `Role`, or `'conversation'`).
  - **Why not a new kind:** the three `kind === 'token'` checks (Facts) keep working unchanged, and an older Overdeck reads the file without calling it corrupt (unknown fields are ignored; an unknown kind refuses every token). An older version would treat an agent token as a plain token, which grants nothing the agent does not already hold through `pan`.
  - The resolved credential gains the fields: `{ kind: 'token'; tokenId; scopes; agentId?; agentKind?; role? }`.
- **D-7 Token delivery.** The plaintext token goes to `<agentDir>/mcp-token` with mode 0600, where `<agentDir>` is `~/.overdeck/agents/<agentId>/` for agents and `~/.overdeck/conversations/<name>/` for conversations (both outside every workspace, so no repo can commit them). The MCP config passes only the file path, in `OVERDECK_MCP_TOKEN_FILE`. `pan mcp serve` reads `OVERDECK_MCP_TOKEN` first, else the file. The token never appears in a launcher script (work launchers are 0755).
- **D-8 Scopes by role.** Rule: an agent gets what its job needs and never `approve` unless it acts for the operator.

  | Who | Scopes |
  |---|---|
  | work, worker, plan, strike, sequencer, knowledge, flywheel | `read:events, read:state, read:conversations, tell, operate` |
  | review, test, ship (specialists) | `read:events, read:state, read:conversations, tell` |
  | conversation (operator's chat) | `read:events, read:state, read:conversations, tell, operate, approve` |

  Never `admin`, `forward`, `read:settings`, `read:costs`. The table lives in one constant, `AGENT_TOKEN_SCOPES`, in `src/lib/mcp/agent-token.ts`.
- **D-9 An agent token on a linked machine acts as that agent.** `linked-conversation-proxy.ts` and `fleetCaller` (`fleet-work.ts:102`) forward an agent token with actor `{ agentId }` and the token's scopes as ceiling, not as `operator`. This keeps the PAN-4650 fence (an agent reads linked conversations but never changes them), exactly what `pan` with a sender header gets today.
- **D-10 Self routes.** Caller-identity routes live under `/api/self/` in new top-level route files. The scope table admits them with the scope named per route; the handler then requires `credential.kind === 'token' && credential.agentId`, else 403 `{ error: 'self routes need an agent token', code: 'not-an-agent-token' }`. The agent is found from the token only.
- **D-11 CLI-backed self routes run the `pan` CLI as an async job.** For operations whose only door is a CLI verb (task, done, handoff, worker report, lane wait and report, memory add, memory search), the route runs `process.execPath <packageRoot>/dist/cli/index.js <verb> …` with `execFile` from `node:child_process` (promisified, never the sync form), with `cwd` = the agent's workspace (`AgentState.workspace`, `agent-state-read.ts:51`) or the conversation's `cwd`, and env `OVERDECK_AGENT_ID=<agentId>` for an agent or `OVERDECK_CONVERSATION=<name>` for a conversation (the variables a managed session already carries, `conversation-runtime.ts:802`, and the ones `pan` reads, for example `pan worker run --parent`'s default, `src/cli/commands/worker.ts:525`). Why: the CLI stays the single door, no second implementation can drift, and the server stays async. Each job has a 15-minute hard timeout, keeps the last 16 KiB of stdout and stderr, and is held in memory for 1 hour after it ends.
- **D-12 Waits are chunks.** Every wait route blocks at most `WAIT_CHUNK_MS = 50_000` and returns `{ status: 'done', … }` or `{ status: 'running', next: { tool, arguments } }`. The instructions tell the agent to call `next` again and never to sleep or poll. 50 s stays under the roughly 100 s idle cut-off t3code measured at its edge.
- **D-13 Harness coverage.**
  - `claude-code`, `codex`, `acp`, `opencode`: the `overdeck` MCP server plus the MCP instructions block.
  - `ohmypi`, `kimi-code`, `muse`, `prime-agent`: no MCP server. They get the CLI instructions block, which names the `pan` command for each tool. (ohmypi support is being removed; do not add Pi MCP plumbing here.)
  - Injection is skipped (and the CLI block used) when the harness runs in a Docker workspace (`OVERDECK_DOCKER_WORKSPACE=1` or `PAN_DOCKER=1`, the same test as `decideChannelsForWorkAgent`, `supervisor-channels.ts:324-330`), because the container has no `pan` and no path to the token file.
  - Config `mcp.agents: false` turns injection off for all agents (default `true`), as a kill switch.
- **D-14 Tool visibility.** Each `OverdeckTool` gains `scope: AccessTokenScope` (the scope its route needs) and `audience: 'any' | 'agent'`. `tools/list` shows a tool when `scopeSatisfies(ctx.scopes, tool.scope)` and (`audience === 'any'` or the caller is an agent token). `tools/call` of a hidden tool returns the same error as an unknown tool.
- **D-15 OAuth design.**
  - Endpoints: `GET /.well-known/oauth-protected-resource`, `GET /.well-known/oauth-protected-resource/mcp`, `GET /.well-known/oauth-authorization-server`, `POST /oauth/mcp/register`, `GET /oauth/mcp/authorize`, `GET /oauth/mcp/authorize/status`, `POST /oauth/mcp/token`, `POST /oauth/mcp/revoke`.
  - Registration is stored (not stateless): client id `odc_<32 hex>`, name ≤ 100 characters, 1-5 redirect URIs that are `https:` or loopback `http:`; public clients only (`token_endpoint_auth_method: "none"`). Unused registrations expire after 24 h.
  - Authorize validates `client_id`, exact `redirect_uri`, `response_type=code`, `code_challenge_method=S256`, `state`, and an optional `scope`. It then shows a page with an 8-character approval code (`ABCD-EFGH`) and creates a pending approval. The operator approves or denies it in the dashboard (a needs-you card on this machine, reachable only by a root credential), choosing an access level. The page checks `authorize/status` every 2 s and redirects with `code` and `state` once approved. Why: over Funnel the page is public and no dashboard session can exist there (`dashboard-auth.ts:453-456`), so approval must happen on the operator's own dashboard. A pending approval expires after 10 minutes. MYN's callback design (a raw `customerId` parameter, `McpOAuthController.java:556-563`) is not copied.
  - Access levels map to scopes: **Read only** (default) = `read:state, read:conversations`; **Can message** = + `tell`; **Can operate** = + `operate`; **Can approve** = + `operate, approve`.
  - Codes are single use and live 60 s. The token endpoint requires `code_verifier` and the exact `redirect_uri`, always.
  - The access token is an `odk_` record of kind `token` with `oauthClientId` and `expiresAt` (30 days). The refresh token is `odr_<64 hex>`, stored as SHA-256 in `~/.overdeck/mcp-oauth.json` (0600), valid 90 days, single use and rotating: a refresh mints a new access token and a new refresh token and revokes the old access token. A reused refresh token revokes the whole sign-in (the "family"). t3code has no refresh tokens; Overdeck adds them so a hosted bot does not need a new approval every 30 days.
  - `verifyAccessToken` refuses a record whose `expiresAt` is in the past. Expired and revoked OAuth and agent records are pruned 7 days after they end.
- **D-16 Public `/mcp`.** Off by default (`mcp.public.enabled: false`). Overdeck prints the Funnel commands and never runs `tailscale` (same rule as triggers). Port 8443, which triggers already use for `/hooks`, with three more `--set-path` mounts: `/mcp`, `/.well-known`, `/oauth`. Only with the switch on, the gate admits Funnel requests to exactly the D-15 endpoints and `POST /mcp`; `/mcp` then accepts only tokens with `oauthClientId` from a Funnel request. Rate limits: 60 requests per minute per access token on `/mcp`, 20 per minute per source IP (`x-forwarded-for` from tailscaled) on `/oauth/mcp/*` and `/.well-known/*`; over the limit answers 429 with `Retry-After`. Each Funnel request writes one activity entry (method, path, status, client id; never a token).
- **D-17 Connector credential.** A new kind `connector`, bound to `connectorKey` (the connector's link public key, 64 hex) and `clientId` (UUID v4). It resolves only inside a link-mode channel whose `remoteKeyHex` equals `connectorKey`, carries the scopes chosen at pairing (subset of `read:state, read:conversations, tell, operate, approve`), skips CSRF like `phone` (bearer inside a Noise-authenticated channel), and counts as an `operator` actor for the link fence only within its own scopes. Why a new kind rather than reusing `phone`: a phone record "always carries `PHONE_TOKEN_SCOPES`" (`access-tokens.ts:24-30`) and is a phone in the device list; a connector has chosen scopes and is a bot. Why not `kind: 'token'`: a token authenticates on plain sockets, so a stolen connector token would work without the key. Cost: an older Overdeck sees the file as corrupt, the same accepted cost as `machine` and `phone` (H-3).
- **D-18 Connector in the directory.** `ClientPlatform` gains `'node'`. Phones (`ios`, `android`) keep `CLIENT_LIMIT = 5`. Connectors get their own `CONNECTOR_LIMIT = 10` per account, counted separately. Why separate: phones and bots are different populations, so an operator with two phones and four bots is not locked out, and the relay's per-account metering already bounds abuse. `push-register` from a `node` client is `bad_frame`. `CONNECT_PROTOCOL_VERSION` stays `1`. The directory deploys before any connector release, because an old directory refuses `platform: 'node'`.
- **D-19 Connector CLI.** `pan connect` already exists (makes this machine a linked machine, `src/cli/commands/connect.ts`), so the connector lives under the existing `mcp` group: `pan mcp connector login | pair <code> | serve | status | logout`. It ships in `@overdeck/core` (`npx -y @overdeck/core@<version> mcp connector serve`), because it reuses `src/lib/mcp/`, `src/lib/anywhere/channel/` and werift. A slim package is a possible follow-up, not part of this epic. It needs Node 22.16 or later (`package.json` `engines`).
- **D-20 Connector local endpoint.** `serve` listens on `127.0.0.1:<port>` only (default `7466`, `--port` to change), path `/mcp`, stateless JSON like the dashboard's `/mcp`. It requires `Authorization: Bearer <local token>`, an `odl_<64 hex>` value written to `<connectorHome>/local-token` (0600) at pairing, so another process in the same container cannot use it without the file. `--stdio` serves one stdio session instead.
- **D-21 Hermes plugin shape.** Tools come from Hermes's own MCP client: the operator adds `mcp_servers.overdeck` (connector loopback URL plus `Authorization: "Bearer ${OVERDECK_CONNECTOR_LOCAL_TOKEN}"`). The Python plugin adds what MCP cannot: the `pre_llm_call` needs-you summary, the `/overdeck` command (status, pending list, answering), the bundled skill, and a `hermes overdeck` CLI command that prints setup. The plugin reaches the tools with `ctx.call_mcp("overdeck", …)` (granted through `mcp_allowlist`). Why: one MCP client, one tool list that always matches the server, and no 30 duplicated schemas in Python. The plugin does not use `register_approval_transport`, which routes Hermes's own approvals, not Overdeck's; answering Overdeck prompts from chat goes through `/overdeck answer`.
- **D-22 OpenClaw plugin shape.** Tools come from OpenClaw's `mcp.servers.overdeck` with `transport: "streamable-http"` pointing at the connector. The plugin (`definePluginEntry`) adds the `before_prompt_build` summary hook, the skill, and two small native tools for chat approvals (`overdeck_pending`, `overdeck_answer`) declared in `contracts.tools`. If CP-7 shows the current OpenClaw does not load `mcp.servers` for the main runtime, the plugin registers native proxies for every tool instead (fallback in W-INT2).

## Hazards

- **H-1 Agents still hold `admin` through `pan`.** The internal token stays reachable to agents that run `pan` in a shell. Agent tokens give the tool path identity and least privilege; they are not a sandbox. Accept for this epic; taking `admin` away from agents' shells is out of scope.
- **H-2 Registry growth.** Every launch adds a record. Pruning 7 days after revocation bounds the file (about 1,400 records at 200 launches a day). `verifyAccessToken` stays linear and constant-time per record; accept.
- **H-3 Downgrades.** A `connector` record makes an older Overdeck refuse every token until it is removed, as `machine` and `phone` records already do. Agent and OAuth fields are ignored by older versions, so an older version would accept an expired OAuth token until it is revoked. Document both in `docs/DASHBOARD-AUTH.md`.
- **H-4 Pairing code reuse.** Handled by W-CONN1 step 7 for connector codes. Browser, machine and phone codes keep the PAN-4823 H-1 acceptance.
- **H-5 Prompt injection through tool results.** Conversation text reaches bots and agents as tool output. The shared skill and the instructions say it is data. `approve` is off by default for every bot and absent for every agent except conversations.
- **H-6 Consent phishing on the public sign-in page.** Anyone can start a sign-in. The operator must approve it in their own dashboard, and the card asks them to compare the code with the page they opened. Unused clients expire after 24 h; rate limits cap attempts.
- **H-7 Jobs run with the dashboard's rights.** A self route runs `pan` as the dashboard user. The verb list is closed, argv is built from validated fields only (W-SELF1 step 2), and the agent is taken from the token.
