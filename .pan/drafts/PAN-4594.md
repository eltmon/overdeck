## Scope of this PRD

The issue asked for four things. A plan that carried all four touched about 29 files and 8
"subsystems", and `pan plan finalize` refuses plans over 25 files or 6 subsystems. The four
things split cleanly into **controls** (write configuration) and **visibility** (read the gate's
result); the two halves share no source file. This PRD plans the controls:

1. Settings → **Security** section: enable, gate mode, severity, configs, timeout, MCP server,
   edit hook, and an install button that calls `POST /api/prereqs/install` with `tool: semgrep`.
2. A **path-scoped write door** for `security.semgrep` in `~/.overdeck/config.yaml`.
3. **Per-project override** (`verification.sast` in `~/.overdeck/projects.yaml`) in Project settings.

The visibility half is filed as [PAN-5449](https://github.com/eltmon/overdeck/issues/5449). The
research for it is kept in the fenced section "Sibling design notes: sast visibility" at the end
of this file. That section is **not** a work item of this plan.

## Glossary

- **`security.semgrep`** — the config block in `~/.overdeck/config.yaml` (global layer) that turns
  Semgrep on and configures it. Keys: `enabled`, `mcp`, `edit_hook` (booleans), `gate`
  (`off|advisory|blocking`), `severity` (`INFO|WARNING|ERROR`), `configs` (non-empty list of
  registry ids or repo-relative paths, none starting with `-`), `timeout_seconds` (positive
  integer). Defaults: `false, false, false, advisory, ERROR, [p/default], 300`
  (`DEFAULT_NORMALIZED_SECURITY`, `src/lib/config-yaml/semgrep.ts` line 42).
- **`normalizeSecurityConfig`** — `src/lib/config-yaml/semgrep.ts` line 68. Folds a raw
  `security:` block onto defaults and **throws** an `Error` with a readable message on any bad
  value. It is the one validator for this block; this PRD reuses it and never re-implements its
  rules.
- **Path-scoped write door** — a writer that parses `config.yaml` with `yaml`'s `parseDocument`,
  changes only named paths with `doc.setIn`, and writes the document back, so comments and every
  other key keep their text. Precedent: `src/lib/jev/settings.ts` (`saveJevSettings`, line 83).
  The opposite is the whole-document `saveSettingsApi` (`src/lib/settings-api.ts`), which is lossy
  (see `.overdeck/context/codebase/concerns.md` "The whole-document settings save is lossy").
- **`runSettingsWriteSerialized`** — `src/lib/settings-api.ts` line 908; serializes every
  config.yaml writer in the dashboard process so two saves cannot interleave.
- **Config cache** — `loadConfigSync()` (`src/lib/config-yaml/load.ts` line 364) caches by file
  mtime; `clearConfigCache()` (line 200) drops it. Another process (the verification runner) sees
  a change on its next `loadConfig*` call because the mtime changed.
- **`verification.sast`** — per-project key in `~/.overdeck/projects.yaml`
  (`ProjectVerificationConfig`, `src/lib/workspace-config.ts`), `off|advisory|blocking`. It
  overrides `security.semgrep.gate` for one project. It cannot turn Semgrep on.
- **`resolveSastGateMode(semgrep, override, warn)`** — `src/lib/cloister/sast-gate.ts` line 82.
  Returns `{ mode, reason }`: `off` with reason `security.semgrep.enabled is false` when disabled;
  otherwise the override when valid; otherwise `security.semgrep.gate`.
- **Prereq install** — `POST /api/prereqs/install` (`src/dashboard/server/routes/prereqs.ts`,
  `installToolRoute`) → `installTool('semgrep')` → `installSemgrep()`
  (`src/lib/prereqs/registry.ts` line 356). It **refuses** with `success: false` and the message
  `Semgrep support is off (security.semgrep.enabled: false in ~/.overdeck/config.yaml)` unless
  `enabled: true` is already saved. It can run up to 600 s (`uv tool install`, ~350 MB).
  `GET /api/prereqs/useSemgrep` answers `{ tools: [{ tool: 'semgrep', installed, installable }], ready, missing }`;
  `installed` is `false` while disabled and otherwise runs `~/.overdeck/bin/semgrep --version`
  (a child process) and compares it with `SEMGREP_VERSION` (`'1.180.0'`, `src/lib/semgrep/install.ts` line 9).
- **No-loss matrix** — `tests/unit/lib/overdeck/no-loss-matrix.ts`; every HTTP route must have a
  row or CI fails.
- **Strict fetch mock** — `src/dashboard/frontend/src/test-utils/strictFetchMock.ts`; frontend
  tests that install it fail on any request they did not handle.
- **Frontend test subset** — `scripts/frontend-test-subset.txt`: the only frontend test files CI
  runs. A new frontend test file must be added there (sorted position) or CI never runs it.

## Requirements

IDs are local to this PRD. This PRD implements the controls half of PAN-4585 FR-8.

- **FR-1** Settings has a **Security** section (nav id `security`) that shows the current value of
  every `security.semgrep` key and edits each one: `enabled`, `gate`, `severity`, `configs`,
  `timeout_seconds`, `mcp`, `edit_hook`.
- **FR-2** Every Security-section save goes through a path-scoped write door. It changes only
  `security.semgrep.<key>` nodes named in the request. Comments and every other key in
  `config.yaml` survive the save (a `doc.toString()` round trip may re-indent, but the comment
  text, the other top-level blocks and their values are kept; WI-1's preservation test checks this). A request with an invalid value or an unknown key is
  rejected with HTTP 400 and the file is not written.
- **FR-3** The section shows the managed install's state and an **Install Semgrep 1.180.0** button
  that calls `POST /api/prereqs/install` with `{ "tool": "semgrep" }`. The button is disabled while
  `enabled` is `false`. After the request ends, the section shows the returned `message` and
  re-reads the install state once.
- **FR-4** Project settings (`ProjectSettingsSection`) has a **Semgrep gate** control with four
  choices: Off, Advisory, Blocking, Global default. A choice writes
  `projects.<key>.verification.sast` in `~/.overdeck/projects.yaml`; Global default deletes only
  `verification.sast` and keeps any `verification.tests`. The control shows the effective mode and
  its reason, and says so when Semgrep is off for every project.
- **FR-5** Four new routes back these controls, and `POST /api/prereqs/install` gains
  `rejectUnsafeDashboardMutationRequest` (D13, WI-8). The new routes are: `GET`/`PUT /api/semgrep/settings` and
  `GET`/`POST /api/projects/:projectKey/sast`. The two mutations call
  `rejectUnsafeDashboardMutationRequest`. All four have no-loss-matrix rows.
- **FR-6** `configuration/semgrep.mdx` documents the Security section, the install button and the
  per-project control, and `changelog.d/pan-4594.md` announces them.
- **Moved to [PAN-5449](https://github.com/eltmon/overdeck/issues/5449)** (no FR id here): the sast
  skipped state in `VerificationGatesPanel.tsx` and the findings list in the issue view.
- **NFR-1** No `execSync` and no synchronous child process in any new server-reachable code. File
  reads and writes in the new lib modules are async (`readFile`, `writeFileAtomic`).
- **NFR-2** Nothing polls `GET /api/prereqs/useSemgrep`, because every call with Semgrep enabled
  spawns `semgrep --version`. The UI reads it on mount (only while enabled), after a save that
  changes `enabled`, and after an install request.
- **NFR-3** No test runs the real Semgrep binary, the network, the real `~/.overdeck/config.yaml`,
  or the real `~/.overdeck/projects.yaml`.
- **NFR-4** Dashboard style follows the `pan-style-guide` skill: no Inter, no bold outside the

## Decisions (made in this document)

- **D1 Split at controls vs visibility.** Controls = this issue; visibility = PAN-5449 (filed
  2026-11-16, comment on #4594 records the split). The halves share no source file, so a
  `sizeJustification` would not be honest.
- **D2 The Security section edits every key of `security.semgrep`**, including `mcp`,
  `edit_hook` and `timeout_seconds`, which shipped (#4590, #4591) after this issue was written.
  Leaving them out would force a hand edit of the same block.
- **D3 API keys are the YAML keys** (`edit_hook`, `timeout_seconds`, snake_case), so the door maps
  request keys to YAML paths 1:1 with no translation table.
- **D4 PUT takes a partial patch.** `PUT /api/semgrep/settings` accepts an object holding any
  subset of the seven keys. Only keys present are written. This lets each control save on its own
  without overwriting a key another control changed.
- **D5 Validation = `normalizeSecurityConfig` on the candidate block.** The candidate is the
  current raw `security.semgrep` mapping from the document merged with the patch. If
  `normalizeSecurityConfig({ semgrep: candidate }, DEFAULT_NORMALIZED_SECURITY)` throws, the door
  throws `SemgrepSettingsValidationError` with that message and writes nothing. Reason: a bad
  value in this block makes every `loadConfigSync()` caller throw, so the door must never write one.
- **D6 After a write the door calls `clearConfigCache()`**, so the very next
  `installSemgrep()` in this process sees `enabled: true` even if the mtime did not tick.
- **D7 A `security:` or `security.semgrep:` node that exists but is not a map** (for example
  `security:` with no value, which parses as null) is replaced with an empty map before `setIn`.
  `normalizeSecurityConfig` already treats null as "absent", so this loses no data.
- **D8 GET returns the normalized view plus `pinnedVersion`.** If the existing block is invalid,
  `GET /api/semgrep/settings` answers 422 `{ error }` and the section shows that error instead
  of the controls.
- **D9 Text fields commit on blur or Enter**, like `MergeTrainBatchingSection`'s `NumberField`.
  Switches and selects save on change. No debounce timer, so no fake-timer tests are needed.
- **D10 The per-project setter lives in a new module `src/lib/semgrep/project-override.ts`**,
  built on the exported `updateProjectsConfigAsync` (`src/lib/projects.ts` line 659).
  `src/lib/projects.ts` is 1212 lines against its allowlist cap of 1217 (last row,
  `scripts/file-size-allowlist.txt`, `1217 src/lib/projects.ts # PAN-4223`), so a setter does not
  fit there, and agents may not raise the cap.
- **D11 All four routes live in one new route file `src/dashboard/server/routes/semgrep.ts`**
  exporting one `semgrepRouteLayer`, registered once in `server.ts`.
- **D12 The install button shows a long-running state.** The text reads
  `Installing… this can take several minutes`. If the `fetch` rejects (network error or the
  browser gave up), the section shows `The install request ended without an answer; checking the install state…`
  and re-reads `GET /api/prereqs/useSemgrep` once.
  **Implementation checkpoint:** before marking the install item done, confirm in the code that the
  dashboard server sets no request timeout shorter than 600 s on `POST /api/prereqs/install`
  (search `src/dashboard/server/` for `timeout`/`requestTimeout`). Fallback if one exists: keep the
  UI exactly as specified (the re-read covers it) and record the finding in the PR description;
  do not change server timeouts in this issue.
- **D13 `POST /api/prereqs/install` gains the mutation guard (WI-8).** It had no
  `rejectUnsafeDashboardMutationRequest`, and its body parser accepts JSON under any content type,
  so a cross-origin request reaching loopback could start an install. `rg '/api/prereqs/install'`
  finds no caller besides the route itself, so adding the guard breaks nothing. The Security
  section sends `dashboardMutationJsonHeaders()`.
- **D14 Per-project control placement:** a new row in `ProjectSettingsSection`
  (`src/dashboard/frontend/src/components/CommandDeck/ProjectSettingsDisclosure.tsx`, line 314),
  directly after the Merge train row and before `<VersionShipSettings projectKey={projectKey} />`
  (line 451). It uses the same four-button segmented style as the Merge train row. The collapsed
  summary line is unchanged.
- **D15 Section placement:** nav item `{ id: 'security', label: 'Security', icon: ShieldAlert }`
  directly after `permissions` in `SETTINGS_NAV_ITEMS`
  (`src/dashboard/frontend/src/components/Settings/settingsPageConstants.ts` line 64), and
  `<SecuritySection />` rendered in `SettingsPage.tsx` directly after the `<PermissionsSection … />`
  element (line ~536). The section is self-contained (own hook), like `MergeTrainBatchingSection`.
- **D17 Who can call the new routes.** None of the four routes gets a `ROUTE_SCOPES` row in
  `src/dashboard/server/route-scopes.ts`, so `rejectUnauthorizedDashboardRequest`
  (`routes/dashboard-auth.ts` line 525) requires `admin` from any scoped credential (access token,
  per-agent MCP token, phone, connector). Only an admin credential (the internal token, the root
  dashboard session, or an admin-scoped token) can read or write them. That is the same posture as
  `/api/jev/settings` and `/api/projects/:projectKey/merge-train`. A gated work agent therefore
  cannot switch its own `sast` gate off through these routes with its MCP token. A process running
  as the operator's OS user can already edit `~/.overdeck/config.yaml` and `projects.yaml`
  directly, so the routes add no capability beyond that; PAN-4585 FR-11 (a repo `.pan.yaml` cannot
  set `security`) is unchanged.
- **D18 Server-reachable reads use async variants.** `src/lib/projects.ts`'s header (lines 7-58)
  says "Do not add new synchronous callers; server-reachable code uses the async variants." The
  project route reads the project with the Effect variant `getProject(key)` (`src/lib/projects.ts`
  line 1211) and the Semgrep config with `loadConfigNoMigration()` (`src/lib/config-yaml/load.ts`
  line 318). It never calls `getProjectSync` or `loadConfigSync`.
- **D16 Effect timing is documented, not engineered.** A gate-mode, severity, configs or timeout
  change applies to the next verification run (the runner reloads config each run). `mcp` and
  `edit_hook` apply to agent sessions started after the change. The Security section states both
  in its description text.

```ts
// src/lib/semgrep/settings.ts (new)
export const SEMGREP_SETTINGS_KEYS = ['enabled', 'mcp', 'edit_hook', 'gate', 'severity', 'configs', 'timeout_seconds'] as const;
export type SemgrepSettingsKey = (typeof SEMGREP_SETTINGS_KEYS)[number];
export type SemgrepSettingsPatch = Partial<Pick<NormalizedSemgrepConfig, SemgrepSettingsKey>>;

export interface SemgrepSettingsView extends NormalizedSemgrepConfig {
  /** SEMGREP_VERSION from src/lib/semgrep/install.ts. */
  pinnedVersion: string;
}

export interface SemgrepSettingsDeps { configPath?: string }

export class SemgrepSettingsValidationError extends Error { /* name = 'SemgrepSettingsValidationError' */ }

export async function readSemgrepSettings(deps?: SemgrepSettingsDeps): Promise<SemgrepSettingsView>;
export function saveSemgrepSettings(input: unknown, deps?: SemgrepSettingsDeps): Promise<SemgrepSettingsView>;
```

Steps:

1. `readConfigDocument(path)`: copy the jev helper (ENOENT → `parseDocument('')`).
2. `viewFromDocument(doc)`: `const raw = (doc.toJS() as { security?: unknown } | null)?.security;`
   then `normalizeSecurityConfig(raw as YamlSecurityConfig, DEFAULT_NORMALIZED_SECURITY).semgrep`;
   a thrown `Error` becomes `SemgrepSettingsValidationError(err.message)`. Return
   `{ ...semgrep, configs: [...semgrep.configs], pinnedVersion: SEMGREP_VERSION }`.
3. `readSemgrepSettings`: path = `deps?.configPath ?? getGlobalConfigPath()`; return
   `viewFromDocument(await readConfigDocument(path))`.
4. `saveSemgrepSettings(input)`:
   - If `input` is not a plain object (null, array, primitive) → throw
     `SemgrepSettingsValidationError('body must be an object of security.semgrep keys')`.
   - If any own key is not in `SEMGREP_SETTINGS_KEYS` → throw
     `SemgrepSettingsValidationError('unknown key security.semgrep.<key>')`.
   - If no keys → throw `SemgrepSettingsValidationError('nothing to save')`.
   - Inside `runSettingsWriteSerialized(async () => { … })`: re-read the document. If
     `doc.errors.length > 0` (YAML syntax error), throw
     `SemgrepSettingsValidationError('~/.overdeck/config.yaml has a YAML syntax error: <first error message>')`
     and write nothing; `readSemgrepSettings` throws the same error. Then take
     `current = doc.toJS()?.security?.semgrep` when it is a plain object, else `{}`; build
     `candidate = { ...current, ...patch }`; run
     `normalizeSecurityConfig({ semgrep: candidate }, DEFAULT_NORMALIZED_SECURITY)` and convert a
     throw into `SemgrepSettingsValidationError` (no write).
   - D7: if `doc.getIn(['security'])` is not a map (`isMap` from `yaml`), `doc.setIn(['security'], doc.createNode({}))`;
     same for `['security','semgrep']`.
   - For each key in the patch: `doc.setIn(['security','semgrep', key], key === 'configs' ? doc.createNode(trimmedConfigs) : value)`,
     where `trimmedConfigs` is the normalized `configs` array (trimmed strings).
   - `await writeFileAtomic(path, doc.toString({ lineWidth: 120 }), 0o600)`; `clearConfigCache()`;
     return `viewFromDocument(doc)`.

Before (no door exists) → after (sketch of the write body):

```ts
return runSettingsWriteSerialized(async () => {
  const doc = await readConfigDocument(path);
  const current = currentSemgrepMapping(doc);
  try {
    normalizeSecurityConfig({ semgrep: { ...current, ...patch } }, DEFAULT_NORMALIZED_SECURITY);
  } catch (err) {
    throw new SemgrepSettingsValidationError(err instanceof Error ? err.message : String(err));
  }
  ensureMap(doc, ['security']);
  ensureMap(doc, ['security', 'semgrep']);
  for (const [key, value] of Object.entries(patch)) {
    doc.setIn(['security', 'semgrep', key], key === 'configs' ? doc.createNode((value as string[]).map((c) => c.trim())) : value);
  }
  await writeFileAtomic(path, doc.toString({ lineWidth: 120 }), 0o600);
  clearConfigCache();
  return viewFromDocument(doc);
});
```

```ts
export interface SemgrepSettingsView {
  enabled: boolean; mcp: boolean; edit_hook: boolean;
  gate: 'off' | 'advisory' | 'blocking'; severity: 'INFO' | 'WARNING' | 'ERROR';
  configs: string[]; timeout_seconds: number; pinnedVersion: string;
}
export type SemgrepSettingsPatch = Partial<Omit<SemgrepSettingsView, 'pinnedVersion'>>;

export function useSemgrepSettings(): {
  settings: SemgrepSettingsView | undefined;
  loadError: string | null;          // GET error text (422 body.error, or HTTP status)
  save: (patch: SemgrepSettingsPatch) => void;
  saving: boolean;
  serverError: string | null;        // last PUT 400 body.error or failure text; cleared on success
  installed: boolean | undefined;    // undefined while unknown or while disabled
  install: () => void;
  installing: boolean;

};
```

- Settings query key `['semgrep-settings']`, `GET /api/semgrep/settings` after
  `ensureDashboardSession()` (as `useJevSettings` does).
- Install-state query key `['semgrep-install-status']`, `GET /api/prereqs/useSemgrep`,
  `enabled: settings?.enabled === true`, `refetchOnWindowFocus: false`, no `refetchInterval`
  (NFR-2). `installed = data.tools.find(t => t.tool === 'semgrep')?.installed`.
- `save(patch)` is **serialized** (critique response "Concurrent saves can show stale settings"):
  the hook keeps `pendingRef` (the merged patch not yet sent: `{ ...pendingRef.current, ...patch }`)
  and `inFlightRef` (the running drain promise), exactly like `useJevSettings`'s `drain`
  (`Settings/hooks/useJevSettings.ts` lines 36-71). Only one PUT is in flight at a time; a save made
  during a PUT is merged into `pendingRef` and sent after the PUT ends. Each PUT is
  `PUT /api/semgrep/settings` with `await dashboardMutationJsonHeaders()` and
  `credentials: 'include'`. 200 → `queryClient.setQueryData(['semgrep-settings'], body)` (responses
  arrive in send order, so the last one written is the latest view), clear `serverError`, and if the
  sent patch contained `enabled`, `invalidateQueries(['semgrep-install-status'])`. 400 →
  `serverError = body.error`. Other → `serverError = 'Failed to save Semgrep settings (HTTP <status>)'`.
  `saving` is true while a PUT is in flight or a patch is pending. No timer is used.
- `install()`: `POST /api/prereqs/install`, body `{ "tool": "semgrep" }`, mutation headers.
  While pending `installing = true`. Response JSON `{ success, message }` → `installMessage = message`.
  A rejected fetch → `installMessage = 'The install request ended without an answer; checking the install state…'` (D12).
  Either way, then `invalidateQueries(['semgrep-install-status'])` once.
