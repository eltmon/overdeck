# PAN-5165: Atlassian Rovo MCP v2 as an Overdeck skill pack

**Issue:** [PAN-5165](https://github.com/eltmon/overdeck/issues/5165). Builds on PAN-5152 (Jira tracker, v0.79.0), PAN-4334 (skill packs) and PAN-5061 (project MCP servers).

## Glossary

- **Skill pack.** A third-party skill repository registered with `pan skills pack add <id>`, pinned to a trusted commit, cached under `~/.overdeck/packs/<id>/<commit>/`, and mounted into agents per launch (`src/lib/skill-packs/`, `src/lib/skill-overrides/`).
- **Registry entry.** `skills.packs.<id>` in `~/.overdeck/config.yaml`: `url`, `ref`, `commit`, optional `adapter`, optional `browser: true` (`PackRegistryEntry`, `src/lib/skill-packs/sources.ts` line 46).
- **Known pack.** An entry in `KNOWN_PACKS` (`src/lib/skill-packs/adapters.ts` line 80) that supplies defaults (url, adapter, ref, opt-ins, disclosure) for `pan skills pack add <id>`.
- **Manifest.** What an adapter reads from a pack checkout: skills plus capabilities (`PackManifest`, `adapters.ts` line 54). `readPackManifest` is at `adapters.ts` line 339.
- **Not applied.** A capability a pack carries that Overdeck never passes to agents; listed by `notAppliedLabels` (`adapters.ts` line 413) in the add/update preview, `pan skills pack list` and the dashboard pack row.
- **Launch pack selection.** The packs whose skills a launch mounts: `resolveLaunchPackSelection` (`src/lib/skill-overrides/launch.ts` line 96). A pack is in the selection when at least one of its skills resolves on for that launch.
- **Launch MCP file.** `<agent dir>/overdeck-mcp.json`, written by `prepareClaudeOverdeckMcp` (`src/lib/mcp/agent-injection.ts` line 125) and passed to Claude Code as `--mcp-config=` (the ACP host reads the same file). Codex gets the same servers through `prepareCodexOverdeckMcp` (line 190) into `codex-home-v2/config.toml`.
- **Project MCP servers.** `projects.<key>.mcp_servers` (PAN-5061), resolved by `resolveProjectMcpServers` (`src/lib/projects/project-mcp.ts` line 109).
- **Pack MCP server.** NEW in this issue: an MCP server a pack declares in its plugin `.mcp.json` that Overdeck now passes to agents.
- **MCP consent.** NEW: `mcp: true` on a registry entry, recorded only when the operator confirmed an add/update preview that listed the pack's MCP servers.
- **Rovo MCP Server.** Atlassian's hosted MCP server, v2 endpoint `https://mcp.atlassian.com/v2/mcp` (early access per Atlassian).
- **Tracker keys.** `config.trackerKeys` from `loadConfigNoMigration()`; PAN-5152 added `jira` (API token), `jiraEmail`, `jiraBaseUrl`, filled from Settings → Tracker Keys or `JIRA_API_TOKEN` / `JIRA_EMAIL` / `JIRA_BASE_URL` (`src/lib/config-yaml/load.ts` lines 256-258).

### Atlassian API-token auth (implementation checkpoint, resolved in planning)

Atlassian's page "Configuring authentication via API token" (support.atlassian.com/atlassian-rovo-mcp-server/docs/configuring-authentication-via-api-token/) and the upstream README at the pinned commit both state:

| Mechanism | Header |
| --- | --- |
| Personal API token (Basic auth) | `Authorization: Basic <base64(email:api_token)>` |
| Service account API key | `Authorization: Bearer <api_key>` |

The page's example client config is `{ "mcpServers": { "atlassian-mcp": { "url": "https://mcp.atlassian.com/v2/mcp", "headers": { "Authorization": "Basic BASE64_ENCODED_EMAIL_AND_TOKEN" } } } }`. API-token auth works only when an org admin enabled it (Atlassian Administration → Rovo → Rovo MCP server → Authentication), and the token needs the right scopes. The page does not say whether a classic unscoped token works. **Decision: take the header path (Work item 3 decision), not the fallback.** The doctor check reports a rejected token so the scope/admin caveat surfaces.

Unauthenticated probe (planning, `curl`): both `GET` and an MCP `initialize` `POST` to `https://mcp.atlassian.com/v2/mcp` return `HTTP 401` with `www-authenticate: Bearer resource_metadata="https://mcp.atlassian.com/.well-known/oauth-protected-resource/v2/mcp"`.

## Decisions

- **D-1 Seam.** Pack servers merge in `agent-injection.ts`, next to project servers, for both Claude-format launches and Codex. `runtime-command.ts` is not edited.
- **D-2 Which entries apply.** Only `type: "http"` entries with an `https://` url, a name matching `^[A-Za-z0-9_-]+$` other than `overdeck`, and string header values. Any entry whose url or a header value contains `${` is not applied (packs get no variable expansion, so a pack can never pull an operator secret). `stdio`, `sse` and anything else stay **Not applied**: a stdio entry would run pack code at every launch.
- **D-3 Where servers are read.** Only for the `claude-plugin` adapter, at manifest-read time, from the cached extract at the trusted commit: `plugin.json` `mcpServers` as a string path (resolved through `toRepoRelative` against the plugin root), else as an inline object (the servers map, or `{mcpServers:{…}}`), else `<plugin root>/.mcp.json` when it is a file. A missing or unparseable file applies nothing. Launches read the manifest from the catalog, never the network and never git.
- **D-4 Consent.** A pack's MCP servers reach agents only when its registry entry has `mcp: true`. `addPack` and `updatePack` record it exactly when the confirmed preview listed applied MCP servers. Packs trusted before this change keep their old promise ("MCP servers: Not applied") until the operator runs `pan skills pack update <id>`; a launch that skips a pack's servers for missing consent logs one warning.
- **D-5 Enabled.** A pack contributes MCP servers to a launch exactly when it is in that launch's pack selection (at least one of its skills resolves on, including the conversation layer). A disabled pack contributes nothing.
- **D-6 Precedence.** `overdeck`, then the launching role's servers, then project `mcp_servers`, then pack servers, then (between packs) the pack with the lower id. A pack server whose name is taken by any earlier source is skipped with `[pack-mcp] <pack>: server <name> skipped: <reason>`. A project server named `atlassian` therefore overrides the pack's, which is the escape for Bearer keys or OAuth-only setups.
- **D-7 Auth header.** For pack id `atlassian` only, for a server whose url is `https:` with hostname exactly `mcp.atlassian.com` and that has no `Authorization` header (any case): add `Authorization: Basic base64(<jiraEmail>:<jira token>)` when both tracker keys are non-empty and `jiraBaseUrl` is unset or a Cloud site (`isCloudJiraSite`, `src/lib/tracker/jira-config.ts` line 36). Otherwise no header; Claude Code agents rely on the operator's OAuth login under the same name and URL.
- **D-7b Codex without a header.** Codex agents use a per-agent `codex-home-v2`, so the operator's OAuth sign-in is not available to them. `prepareCodexOverdeckMcp` skips a pack server for which `atlassianNeedsInteractiveAuth(server)` is true (https `mcp.atlassian.com` URL, no Authorization header) and warns once: `[pack-mcp] atlassian: server atlassian skipped for codex: set the Jira email and API token (Codex agents cannot reuse an /mcp sign-in)`. Claude-format launches keep the header-less server.
- **D-7c Credential scope.** The header uses the global Jira tracker keys for any project where the pack is on. PAN-5152 stores them globally; a project `mcp_servers` entry named `atlassian` covers a per-project account or a Bearer service-account key. The header value is written only into the 0600 launch file / per-agent Codex config, like PAN-5061 header values, and never logged.
- **D-8 Allowed tools.** Pack server names join `overdeckMcpServerNames`, so Claude Code launches get `--allowedTools=mcp__overdeck,…,mcp__atlassian` as project servers do.
- **D-9 Known pack.** `atlassian`: url `https://github.com/atlassian/atlassian-mcp-server` (upstream; the fork-first policy gets a documented exception because the pack carries no Overdeck changes and the 40-hex pin already controls updates), adapter `claude-plugin`, ref `3be55622453304b905f0c0fd5ef96fa4d638627c`, `skillsExclude: ['skills/v1']`, opt-in the four write skills, and a disclosure. No `skillsRoot` (the claude-plugin adapter ignores it; `plugin.json` already says `skills`).
- **D-10 Doctor.** New `src/cli/commands/doctor-atlassian.ts`. Silent unless the `atlassian` pack is registered. One row named `Atlassian MCP`.
- **D-11 Not in scope.** No npm release is run by this issue (the changelog entry is folded by the next `pan release stable`). No dashboard UI change beyond what existing fields carry.

```ts
export interface AtlassianTrackerKeys { jira?: string; jiraEmail?: string; jiraBaseUrl?: string }

/** `Basic base64(email:token)` from the Jira tracker keys, or null when either is missing or the site is Data Center. */
export function atlassianBasicAuth(keys: AtlassianTrackerKeys | undefined): string | null {
  const token = keys?.jira?.trim();
  const email = keys?.jiraEmail?.trim();
  if (!token || !email) return null;
  if (keys?.jiraBaseUrl && !isCloudJiraSite(keys.jiraBaseUrl)) return null;
  return `Basic ${Buffer.from(`${email}:${token}`).toString('base64')}`;
}

/** Add the Authorization header to every https mcp.atlassian.com server that has none (any case). */
export function withAtlassianAuth<T extends { url: string; headers: Record<string, string> }>(
  servers: Record<string, T>, keys: AtlassianTrackerKeys | undefined,
): Record<string, T>
```
