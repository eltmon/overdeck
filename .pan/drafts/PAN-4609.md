# PAN-4609 — Docs: what verification runs, why it is slow, and how to choose a project's local gates

**Issue:** [PAN-4609](https://github.com/eltmon/overdeck/issues/4609)
**Kind:** docs-only. No source, test, config or prompt file changes.
**Planned against:** `main` at `68641f097c3` (2026-10-24).

## Glossary

- **Verification run** — one call of `runVerificationForIssueInProcess`
  (`src/lib/cloister/verification-runner.ts`). It is the code between "an agent
  asked for review" and "the review convoy starts". It runs in a detached
  *verification worker* process.
- **Verification worker** — the child process that runs a verification run.
  `runSupervisedVerification` (`src/lib/cloister/verification-worker-supervisor.ts`)
  launches it in a systemd user scope (`buildVerificationWorkerLaunch`,
  `src/lib/cloister/verification-worker-launcher.ts`) and writes its state and
  log under `~/.overdeck/verification-workers/<issue>/`.
- **Quality gate** — one entry of a project's `quality_gates:` map in
  `~/.overdeck/projects.yaml`, typed as `QualityGateConfig`
  (`src/lib/workspace-config.ts`). `runQualityGates`
  (`src/lib/cloister/validation.ts`) runs the entries.
- **`DEFAULT_GATES`** — the `typecheck`, `lint`, `test` gates in
  `src/lib/cloister/validation.ts` that run when a project declares no
  `quality_gates`.
- **CPU admission** — the machine-wide queue in
  `src/lib/cloister/quality-gate-admission.ts`
  (`acquireQualityGateAdmission`). One holder at a time across every issue and
  every agent shell; a holder is recorded in
  `~/.overdeck/verification-workers/admission/owner.json`.
- **PSI** — Linux CPU Pressure Stall Information. `some avg10` is the share of
  the last 10 seconds in which at least one runnable task waited for a CPU.
  Read by `readCpuPsi` (`src/lib/system-health/cpu-psi.ts`).
- **Tests mode** — `verification.tests: ci | local`
  (`resolveVerificationTestsModeDecision`,
  `src/lib/cloister/verification-tests-mode.ts`). In `ci` mode the gate named
  `test` is not run on the host (`selectLocalVerificationGates`).
- **`overdeck/test`** — the commit status context posted on a pass
  (`postOverdeckTestsStatus`, `src/lib/github-app.ts`; the context string is
  singular, see the comment above the `reportCommitStatus` call).

## Facts the new text must state (verified)

### F1. The order of a verification run

`runVerificationForIssueInProcess` (`src/lib/cloister/verification-runner.ts`)
does these steps in this order. Each step that fails returns early with the
named `failedCheck`; later steps do not run.

| # | Step | Code (grep anchor) | `failedCheck` on failure |
|---|------|--------------------|--------------------------|
| 0 | Skip if the PR already merged (`skipMergedVerification`, repeated after most later steps); skip if this head already used `VERIFICATION_MAX_CYCLES` (3) attempts | `if (currentCycles >= VERIFICATION_MAX_CYCLES)` | none (outcome `skipped`) |
| 1 | Snapshot the head for the test-skip waiver | `const testSkipHead = await snapshotWorkspaceHeads` | — |
| 2 | Merge `origin/<target>` into each repo root (skipped when `syncTargetBranch: false`, the merge-time path) | `syncSingleRepo(root.dir, root.targetBranch)` | `sync-target-branch` |
| 3 | Pick gates: `quality_gates`, else `DEFAULT_GATES`; drop `test` in `ci` tests mode | `const configuredGates =`, `selectLocalVerificationGates(configuredGates, testsMode)` | — |
| 4 | Non-polyrepo only: `<package_manager> install` (60 s timeout) and each `workspace_packages[].build_command` (30 s timeout). Warn-only, not admission-gated, not niced | `Installing dependencies:`, `Building workspace package:` | none (a failure is a log warning) |
| 5 | Test-skip diff check | `evaluateTestSkipGate(workspacePath, repoRoots, testSkipHead)` | `test-skip` |
| 6 | Plan-integrity check (only if 5 passed) | `evaluatePlanIntegrityGate(issueId, workspacePath, repoRoots)` | `plan-integrity` |

| 11 | Acceptance-criteria check on the xBRIEF | `acStatus = getXBriefACStatus(workspacePath)` | `vbrief-conflicts` or `vbrief-ac` |

After a pass, `createRequestReviewPipeline`
(`src/lib/cloister/request-review-pipeline.ts`) runs `pushBranch` and then
`dispatchReview` (the review convoy).

**Doors.** Verification starts from `startRequestReviewPipeline`
(`src/dashboard/server/routes/workspaces/review-pipeline.ts`; reached by
`pan done`, `pan review request`, the PR webhook, deacon-lite) and again at
merge time from `triggerMerge` (`src/dashboard/server/routes/workspaces/merge-ops.ts`,
log prefix `merge-verify`, no target sync). The merge-time run is skipped when
CI is already green on the exact tip commit (`skipLocalVerification = true`,
PAN-2487). So one issue can run the gates twice.

### F2. How one quality gate runs (`runQualityGates`, `src/lib/cloister/validation.ts`)

- Only gates whose `phase` (default `pre_push`) matches run. `required`
  defaults to true; the first failed required gate ends the loop (`break`).
- `{{…}}` placeholders (`CHANGED_BASE`, `FEATURE_FOLDER`, `WORKSPACE_PATH`, …)
  are substituted into `command` and `container_name` (`replacePlaceholders`).
- `type: http_health` gates wait `wait` seconds (default 120), curl `url`, and
  compare with `expect_status` (default 200). They take no CPU admission.
- Container gates (`container: true` + `container_name`) run
  `docker exec -w /workspaces/feature/<path>`; a missing container is
  `infraUnavailable`, not a code failure (PAN-2461).
- Local host gates run as `nice -n 19 sh -c '<command>'`
  (`resolvedCommand = \`nice -n 19 sh -c`).
- Every local or container gate attempt queues for CPU admission first
  (`Queued for CPU admission:` → `acquireQualityGateAdmission` → `Admitted:`),
  and releases it when the attempt ends. Remote (Fly) gates skip admission.
  N gates means N separate waits; `retry: N` means up to N+1 waits for one gate.
- Each attempt has a 20-minute timeout (`GATE_TIMEOUT_MS`), with a process-group
  watchdog at timeout + 30 s.
- `const startTime = Date.now();` (validation.ts line 289) is taken *before*
  admission (`admission = await acquireQualityGateAdmission`, line 414), so the
  `✓ "<name>" passed (<N>ms)` log line and the artifact's `durationMs` include
  the queue wait and every retry.
- Gate env (`buildQualityGateEnv`): drops every `OVERDECK_*` key except
  `OVERDECK_HOME`, drops `API_PORT`, `PORT`, `DASHBOARD_URL` unless the gate
  sets them, sets `SKIP_DOCS_INDEX=1`, then applies the gate's `env`. Admitted
  gates also get `OVERDECK_GATE_ADMITTED=1`.

### F3. The admission rules (`src/lib/cloister/quality-gate-admission.ts`)

- One holder machine-wide (`owner.json` written with `wx`). Waiters are tickets
  `waiter-<id>.json` served oldest-first (FIFO by `createdAt`).
- The head waiter samples pressure (`sampleQualityGatePressure`, 250 ms CPU
  sample). The host is *pressured* when CPU utilization ≥ 0.75
  (`QUALITY_GATE_CPU_START_THRESHOLD`) **or** contended: PSI `some avg10` ≥ 25
  (`QUALITY_GATE_PSI_SOME_AVG10_START_THRESHOLD`), or, only when PSI is
  unavailable, 1-minute load per core ≥ 1
  (`QUALITY_GATE_LOAD_PER_CORE_START_THRESHOLD`).
- Not pressured → write `owner.json`, wait 1.5 s
  (`QUALITY_GATE_ADMISSION_SETTLE_MS`), sample again; if pressured now, give the
  slot back and keep waiting. Poll interval 1 s.
- A holder older than 25 minutes (`QUALITY_GATE_ADMISSION_STALE_MS`) or with a
  dead pid is cleared.
- Direct Vitest runs join the same queue: both `vitest.config.ts` and
  `src/dashboard/frontend/vitest.config.ts` list `tests/vitest-cpu-admission.ts`
  as `globalSetup`, which calls `acquireQualityGateAdmission` (gate name
  `vitest`, 30-minute max wait) unless `OVERDECK_GATE_ADMITTED=1`,
  `OVERDECK_GATE_ADMISSION=0`, or `CI` is set. So an agent's own
  `npx vitest run <files>` competes with every verification run for the slot.

### F4. Worker process limits

- `buildVerificationWorkerLaunch` runs the worker under
  `systemd-run --user --scope --property=CPUWeight=<resources.verification_cpu_weight>`
  (default 20, `src/lib/config-yaml/defaults.ts`) on Linux.
- `MAX_RUN_MS` = 65 minutes, counted from `admittedAt` (the first admission),
  not from launch (`verificationWorkerDeadline`). Queue time before the first
  admission does not use the budget.
- Files under `~/.overdeck/verification-workers/<issue>/` (issue id lowercased):
  `state.json` (`phase: queued | running`, `admittedAt`, `currentGate`,
  `currentAttempt`), `worker-<runId>.log`, `result-<runId>.json`.

### F5. Facts behind the gate-selection advice

- `npm run typecheck` (`package.json`) includes `typecheck:frontend`, which is
  `scripts/lint-frontend-types.sh`: a **baseline ratchet** (error count may not
  grow), not a strict zero-error check.
- `npm run build` runs `scripts/build-post-cli.mjs`, which runs
  `build:dashboard:frontend` (`tsc && vite build` in
  `src/dashboard/frontend/package.json` — strict `tsc`) and
  `build:dashboard:server:bundle` (the server bundle).
- Overdeck's CI (`.github/workflows/ci.yml`) runs `npm run build` and
  `npm run typecheck` in the `build` job, lint in `lint-group` / `lint`, and
  tests in `test-shard` / `test`.
- The runner's own install (F1 step 4) is warn-only. An `install` gate such as
  `bun install --frozen-lockfile` therefore adds a *failing* lockfile check, not
  a second install.
- A red **non-test** CI check (lint, build) reaches a live work agent as a
  plain "CI FAILED" message from `relayCiFailureFeedbackInQueue`
  (`src/lib/cloister/ci-failure-feedback.ts`): it is written as `ci-monitor`
  feedback, sent only when a `work`-role agent exists, debounced per head, not
  counted against `VERIFICATION_MAX_CYCLES`, and filtered against checks
  already failing on `main`. Only the CI **test** job goes through the
  verification feedback door with attempt counting.
- Overdeck's own gates (per-machine `~/.overdeck/projects.yaml`, entry
  `panopticon-cli`, not tracked in the repo) since 2026-10-24: `install`
  (`bun install --frozen-lockfile`), `typecheck` (`npm run typecheck`), `test`
  (changed-file Vitest for root and frontend, `retry: 1`, deferred to CI in
  `ci` mode).

## Rules that intersect this work

- **lint:docs (`scripts/lint-docs.js`).** For published pages (in `docs.json`,
  which includes `configuration/projects`): a `$` in prose outside inline code
  or fences fails (write `&#36;`), and `<` directly before a digit fails (write
  `&lt;` or put a space). Commands with `$HOME`/`$PATH` go in fenced blocks or
  inline code. For `docs/*.md`: file must be non-empty and end with a newline.
- **Writing style.** Plain prose, active voice, full sentences, no hype words.
- **No destructive "tests" in docs.** Do not tell the reader to delete
  `owner.json` or `~/.overdeck/verification-workers/` to "fix" the queue. A stale
  owner clears itself (25 min or dead pid); say that.
- **Docs-only.** Do not touch `src/`, `tests/`, `roles/`, `projects.yaml`, or
  any config. `npm run typecheck` is not needed.
