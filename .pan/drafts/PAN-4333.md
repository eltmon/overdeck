# PAN-4333: Session Vault key rotation after device loss (key ring, re-encrypt refs under a new key)

**Issue:** [PAN-4333](https://github.com/eltmon/overdeck/issues/4333) · **Epic:** PAN-2350 · **Design:** `.pan/drafts/anywhere-accounts.md` §6.5 ("Revocation limit, stated plainly") · **Builds on:** PAN-2609 (Session Vault Phase A), PAN-4328 (passphrase keywrap, merged), PAN-4329 (WIP snapshots, merged)

## 1. Summary

Revoking a device (or, on the git backend, removing its machine record and rotating git credentials) stops it syncing, but the device still holds the vault key `K` in `${OVERDECK_HOME}/vault/key`. Anyone holding that device can decrypt any vault ciphertext they obtain. This issue adds `pan vault rotate-key`: it generates a new vault key `K'`, re-encrypts every record and machine ref under `K'` in **one atomic backend commit**, keeps every older chunk readable through a **key ring** stored inside the (encrypted) vault header, re-wraps or removes the passphrase keywrap, and prints a new 24-word recovery phrase. Machines that still hold the retired key are refused every further write and told to re-join.

Rotation protects **everything written after the rotation**. Ciphertext written before it stays readable by whoever holds the retired key: that is the accepted trade-off of the key ring (the issue's "history does not need to be re-encrypted in one pass").

## 2. Glossary

| Term | Meaning |
| --- | --- |
| **Vault key `K`** | 32 random bytes, `${OVERDECK_HOME}/vault/key` (0600). Sub-keys `K_enc`, `K_id`, `K_ref` derive from it by HKDF (`src/lib/vault/identity.ts` `deriveSubkeys`, line 147). |
| **Current key** | The key that opens the header ref `h/header` right now. Every new write is sealed under it. |
| **Retired key** | A key that was current before a rotation. It still decrypts chunks and WIP parts written while it was current. |
| **Key ring** | The ordered list of retired keys (newest first), stored as base64 inside the header value, which is sealed under the current key. Only holders of the current key can read it. |
| **Header** | The ref `h/header` (`HEADER_REF_NAME`, `src/lib/vault/format.ts` line 49): `VaultHeader` sealed under `K_enc`. Joining proves a key by decrypting it. After this issue it also carries `keyRing` and `rotatedAt`. |
| **Header version** | The backend's opaque version token of the `h/header` ref (`VaultRef.version`). It changes only when the header is rewritten, which after setup happens only at rotation. |
| **Ref rename** | Record refs are named `r/<hmac(K_ref, 'rec:'+vaultId)>` and machine refs `m/<hmac(K_ref, 'env:'+environmentId)>` (`refName`, format.ts line 208). A new `K` means a new `K_ref`, so every ref gets a new name at rotation. `vaultId` and `environmentId` do not change. |
| **Retired-ref marker** | The value rotation writes at each old ref name: `{ v: 1, type: 'retired', at }` sealed under the retired key. Stale readers decode it as "not a session" (P-19), so a stale settle returns `excluded` instead of creating a truncated record. |
| **Batch CAS (`casRefs`)** | New `VaultStore` operation: an all-or-nothing compare-and-swap over several refs. Git: one commit and one push. Dir: all ref locks taken in sorted order, all versions checked, then all written. |
| **Assert-only op** | A `casRefs` op with no `value`: it only requires the ref to be at `expectedVersion` and writes nothing. |
| **Key-guarded store** | A `VaultStore` decorator (`KeyGuardedStore`) that adds an assert-only op on `h/header` at the verified header version to every ref write, and re-verifies the header after every `refresh`. Every CLI verb gets it through `openVault`. |
| **Stale machine** | A legitimate machine that still holds the retired key after another machine rotated. It must not write anything new under the retired key; it re-joins with the new phrase or passphrase. |
| **Pending rotation** | `${OVERDECK_HOME}/vault/key.next` (0600) exists: a rotation started on this machine and has not finished. It holds `K'`. |
| **Unpublished objects** | Objects written by `putObjects` that no successful ref write has published yet (git: untracked files in the vault clone). |

## 4. Decisions

- **D-1 Ring lives in the header.** The retired keys are stored as `keyRing: string[]` (base64 of each raw 32-byte key, newest first) inside the header value, sealed under the current key. No local ring file. A device that obtains the current key (phrase or passphrase) gets the whole ring on its next header read. A device with only a retired key cannot read the ring.
- **D-2 Refs are all re-encrypted; chunks are not.** Record refs, machine refs and the header are re-sealed under `K'` at rotation. Chunks, settlement-archive chunks and WIP parts keep their ids and their original key. Therefore `decryptRef` stays current-key-only, and only `decodeChunk` / `decodeWipParts` fall back through the ring.
- **D-3 Ring fallback via `VaultSubkeys.previous`.** `VaultSubkeys` gains an optional `previous?: VaultSubkeys[]` (newest first). `decodeChunk` and `decodeWipParts` try the current keys, then each `previous` entry, and throw the current key's `VaultAuthenticationError` when none authenticates. The content-id check uses the `K_id` of the key that decrypted. Encoding functions ignore `previous`.
- **D-4 Old ref names get a retired-ref marker, not a delete.** Rotation overwrites each old `r/` and `m/` name with `{ v: 1, type: 'retired', at }` sealed under the retired key. Rationale: a delete would make a stale machine's owned-record settle mint a truncated record (settle.ts, absent-ref branch); the marker makes it return `excluded`. No ref-delete operation is added.
- **D-5 One atomic commit via `casRefs`.** `VaultStore.casRefs(ops)` is added to the contract. Rotation writes every new-name ref, every marker and the new header in one `casRefs` call. On git that is one commit and one push, so no reader ever sees a half-rotated vault. On dir it is lock-all-then-write; a crash mid-write can leave a mix, which re-running `pan vault rotate-key` repairs (it resumes from `key.next`). `casRef` delegates to `casRefs` in both backends so there is one write path per backend.
- **D-6 Readers skip refs they cannot open.** `syncOnce` and `pan vault status` classify every listed ref as *current* (opens with the current key), *retired* (opens with a ring key: the markers) or *unreadable* (no key opens it), skip the latter two, and report counts. A junk ref written by a revoked device with write access can no longer break sync.
- **D-7 Writes are guarded by the header version (`KeyGuardedStore`).** `openKeyring(store, key)` reads `h/header`, verifies it opens with `key`, loads the ring into `keys.previous`, and returns a `KeyGuardedStore` bound to the header version it verified. The decorator:
  - `casRef(name, expected, value)` → `inner.casRefs([{ name, expectedVersion: expected, value }, { name: 'h/header', expectedVersion: headerVersion }])`; on `conflict` it re-reads the header and throws `VaultKeyRetiredError` if the header version changed and the header no longer opens with this key.
  - `casRefs(ops)` → the same, with the header assert appended.
  - `refresh()` → `inner.refresh()`, then re-reads the header: same version → return; different version that still opens with this key → adopt the new version and reload the ring; otherwise throw `VaultKeyRetiredError`.
  - `putSlot(name, bytes)` → `this.refresh()` first, then `inner.putSlot` (so a stale machine cannot re-wrap a retired key under a passphrase).
  - every other method passes through.
  `openVault` (shared.ts) is the one CLI entry point that builds it, so every verb that writes (`save`, `sync`, `resume`, `exclude`, `allow-secret`, `evict`, `restore`, `passphrase set|remove`) is guarded without editing those verbs.
- **D-8 Residual window, stated.** On the **dir** backend `putObjects` writes immediately, so a stale machine that passes its header check in the milliseconds before a rotation commits can leave an unreferenced object sealed under the retired key. On **git**, such objects stay untracked in the stale machine's clone and are removed by `discardUnpublished` when it re-joins (D-10), so they are never pushed. The docs state this.
- **D-9 `discardUnpublished()` joins the contract.** `VaultStore.discardUnpublished(): Promise<void>` drops unpublished objects. Git: under the clone lock, `git reset --hard origin/main` when `origin/main` exists, then `git clean -fdq -- objects refs`. Dir: resolves without doing anything (objects are published on write). Rotation calls it before its batch (so the rotation commit publishes no stale objects); join calls it after it has verified a replacement key.
- **D-10 Re-join replaces the key in place.** `pan vault join <backend>` on a machine already configured for the same backend: refresh the existing clone first on **every** path (offline → keep the local view), verify the new key opens the header, `discardUnpublished()`, then save the key. The local index and list cache are kept: `vaultId`s survive rotation, so the next settle continues each owned record under its new ref name.
- **D-11 Crash safety order.** `K'` is written to `key.next` (0600, atomic) **before** any backend write. The rotation commit (the batch that swaps the header) is the point of no return. The binding sequence is: save `key.next` → commit → put or remove the keywrap → `saveVaultKey(K')` (atomic write of `key`) → print the new phrase → `unlink(key.next)`. Resume rule: if `key.next` exists, `rotate-key` uses it as `K'`; if the header already opens with `K'` the commit happened and only the finishing steps run; otherwise the commit is retried with the same `K'`. A crash between printing and unlinking only re-prints the same phrase on the next run. The phrase is printed on every run that finishes, because no verb shows a phrase later.
- **D-12 Keywrap handling mirrors setup.** Flags: `--passphrase-file <path>`, `--generate-passphrase`, `--no-passphrase`. If the backend has `keywrap/v1`: a flag decides; with no flag on a TTY, prompt with `choosePassphrase` (Enter generates one); with no flag off a TTY, exit 1 **before any write** with `This vault has a passphrase. Pass --passphrase-file <path>, --generate-passphrase or --no-passphrase.` If the backend has no keywrap: only `--passphrase-file` / `--generate-passphrase` create one; otherwise print `PASSPHRASE_LATER_HINT`. The wrap is computed before the commit (a strength failure changes nothing) and stored with `putSlot` after it. `--no-passphrase` deletes an existing keywrap. The keywrap never keeps pointing at a retired key after a finished rotation.
- **D-13 Confirmation.** On a TTY, rotation asks `Rotate the vault key? Every other machine must re-join with the new recovery phrase or passphrase. [y/N]` and stops on anything but `y`/`yes`. Off a TTY it requires `--yes`, else exit 1 with `Pass --yes to rotate the vault key without a prompt.` A resumed rotation (`key.next` present) skips the prompt.
- **D-14 Retries.** Rotation retries the batch up to 5 times on `conflict` (another machine settled in between; each retry re-reads all refs). After 5 it exits 1 with `Another machine kept writing to the vault. Stop pan vault on your other machines and run pan vault rotate-key again.` and keeps `key.next`.
- **D-15 Verb name** `pan vault rotate-key`. Module `src/cli/commands/vault/rotate-key.ts`, export `rotateKeyCommand`. Library core `src/lib/vault/rotate.ts`. Guard and ring loading `src/lib/vault/keyring.ts`. All three import only Node built-ins and sibling vault modules (NFR-1).
- **D-16 Hosted backend.** No `overdeck://` store exists. Rotation uses only `VaultStore` methods, so a hosted store that passes the shared contract suite (which now covers `casRefs` and `discardUnpublished`) supports rotation unchanged. PAN-4297 must implement both; the docs say so.
- **D-17 PAN-4330 docs.** `configuration/anywhere-sign-in.mdx` does not exist yet, so this issue does not edit it. The session-vault docs gain a "Lost a device? Rotate the key" section that PAN-4330's revocation note can link to.
- **D-18 Status shows the rotation.** `pan vault status` prints `Key rotated:   <rotatedAt | never>` and JSON field `keyRotatedAt`; `openVault` returns `rotatedAt` from the header.

## 5. Requirements

- **FR-1** `pan vault rotate-key` replaces the vault key: afterwards `h/header` opens only with `K'`, `${OVERDECK_HOME}/vault/key` holds `K'`, and the printed 24 words decode to `K'`.
- **FR-2** Every record ref and machine ref that opened with the retired key is readable under `K'` at its new name with identical decrypted content (tombstones stay tombstones).
- **FR-3** Every chunk and WIP part written before rotation stays readable: `show`, `resume`, `restore`, eviction verification and WIP apply work on pre-rotation records, through the key ring.
- **FR-4** The rotation lands in one `casRefs` call; on git it is exactly one new commit on `main`.
- **FR-5** Each old ref name holds a retired-ref marker sealed under the retired key.
- **FR-6** After rotation, a machine holding the retired key writes no new ref value and no new published object: its `save`/`sync` fail with `VaultKeyRetiredError`'s message `This machine's vault key was retired by a key rotation. Run: pan vault join <backend> with the new recovery phrase or passphrase.`
- **FR-7** `keywrap/v1` is re-wrapped under `K'` or removed, per D-12; it never wraps a retired key after a finished rotation.
- **FR-8** A stale machine re-joins with `pan vault join <backend>` and the new phrase or passphrase; its owned records keep settling under their new names with no gap.
- **FR-9** A rotation interrupted at any point resumes with the same `K'` when `pan vault rotate-key` runs again, and never leaves the vault without a locally stored key that opens it.
- **FR-10** `syncOnce` and `pan vault status` skip refs sealed under a ring key or under no known key, and report `retired` and `unreadable` counts, instead of throwing.
- **FR-11** `VaultStore` gains `casRefs` and `discardUnpublished`, implemented by dir and git and covered by the shared contract suite.
- **FR-12** A join whose key does not open the header prints: `The recovery phrase does not match this vault. If the vault key was rotated, use the new recovery phrase or passphrase.` (passphrase path: `The passphrase unlocked a key this vault no longer uses. The vault key was rotated; use the new recovery phrase, or finish the rotation with pan vault rotate-key on the machine that started it.`).
- **FR-13** `openVault` refuses with `A vault key rotation started on this machine has not finished. Run: pan vault rotate-key` while `key.next` exists; with `quiet` (the `save --hook` Stop-hook path) it returns null silently instead, so a hook never fails the harness.
- **NFR-1** `keyring.ts`, `rotate.ts` and `rotate-key.ts` import only Node built-ins and sibling vault modules (`tests/unit/lib/vault/import-graph.test.ts` stays green; `rotate.ts` does not import `store/dir.js` or `store/git.js`).
- **NFR-2** `node:crypto` only; no new dependency. The new key comes from `createVaultKey()`.
- **NFR-3** No plaintext reaches the backend: the two-machine e2e plaintext scan passes after a rotation.
- **NFR-4** Async only: no `execSync`, no `scryptSync`, no `git stash`.
- **NFR-5** Tests use temp `OVERDECK_HOME`s and temp remotes; any retry/backoff test uses `vi.useFakeTimers()` (repo rule: fake timers for delay tests).

export async function decodeChunk(bytes: Uint8Array, id: string, keys: VaultSubkeys): Promise<DecodedChunk> {
  let first: unknown;
  for (const candidate of [keys, ...(keys.previous ?? [])]) {
    try {
      return await decodeChunkWith(bytes, id, candidate);
    } catch (error) {
      if (!(error instanceof VaultAuthenticationError)) throw error;
      first ??= error;
    }

}

## 7. Store contract changes

`src/lib/vault/store/types.ts`:

```ts
export interface RefOp {
  name: string;
  expectedVersion: string | null;
  /** Omitted = assert-only: the ref must be at expectedVersion; nothing is written. */
  value?: Uint8Array;
}

export interface VaultStore {
  // ...existing methods...
  /**
   * All-or-nothing CAS over several distinct refs: when every op's ref is at its
   * expectedVersion, write every op that carries a value and publish them together;
   * otherwise write nothing and return 'conflict'. Throws for duplicate names.
   */
  casRefs(ops: ReadonlyArray<RefOp>): Promise<CasResult>;
  /** Drop objects no ref write has published yet. A backend that publishes on write resolves at once. */
  discardUnpublished(): Promise<void>;
}
```

Git `casRefs`: same cycle as today's `casRefSerialized` (refresh, compare each op's `remoteBlobSha`, write each valued op, `add -A -- .`, commit, push, non-fast-forward retry ×3, offline reset) with message `vault: settle` for one valued op and `vault: batch` otherwise. `casRef(name, v, value)` becomes `casRefs([{ name, expectedVersion: v, value }])`. Dir `casRefs`: inside `casQueue`, nest `withFileLock` for each op's `<ref>.lock` in ascending name order, compare every version, then `writeAtomic` every valued op. `casRef` delegates the same way.

## 8. Rotation algorithm (`src/lib/vault/rotate.ts`)

```ts
export interface RotateOptions {
  store: VaultStore;            // the raw store, not the guarded one
  currentKey: Buffer;           // from loadVaultKey()
  /** keywrap/v1 bytes to publish under K' (already wrapped), null = delete, undefined = leave absent. */
  keywrap?: Uint8Array | null;
  now?: () => Date;
  maxAttempts?: number;         // default 5
}
export interface RotateResult { newKey: Buffer; records: number; machines: number; resumed: boolean; committed: 'now' | 'earlier' }
export async function rotateVaultKey(options: RotateOptions): Promise<RotateResult>;
```

Key-file helpers live in `rotate.ts`: `nextKeyPath()` = `join(vaultDir(), 'key.next')`, `loadNextKey()`, `saveNextKey(key)` (0600, temp + rename, same as `saveVaultKey`), `clearNextKey()`.

Steps:

1. `K'` = `loadNextKey()` ?? (`createVaultKey()` then `saveNextKey`). `resumed` = a `key.next` already existed.
2. `store.refresh()`; read `h/header`. If it opens with `K'` → the commit happened earlier: skip to step 6 with `committed: 'earlier'`. If it opens with `currentKey` → continue. Otherwise throw `Error('The vault key on this machine does not open the vault; nothing was rotated.')`.
3. `store.discardUnpublished()`.
4. Build ops: for every `listRefs('r/')` and `listRefs('m/')` entry, `readRef`; decrypt with the current keys; skip refs that fail authentication (older markers, junk); skip values that are neither `session` nor `machine`. For each kept value: the new name = `refName(kind, value.vaultId | value.environmentId, K'_ref)`; op `{ name: newName, expectedVersion: <existing version or null>, value: encryptRef(newName, value, K') }` and op `{ name: oldName, expectedVersion: ref.version, value: encryptRef(oldName, { v:1, type:'retired', at }, K) }`. Header op: `{ name: 'h/header', expectedVersion: header.version, value: encryptRef('h/header', { ...oldHeader, rotatedAt: at, keyRing: [b64(currentKey), ...(oldHeader.keyRing ?? [])] }, K') }`.
5. `casRefs(ops)`: `ok` → `committed: 'now'`; `conflict` → back to step 2 (attempt counter, D-14); `VaultOfflineError` propagates (nothing committed, `key.next` kept).
6. Keywrap: `undefined` → nothing; bytes → `putSlot(KEYWRAP_OBJECT_NAME, bytes)`; `null` → `putSlot(KEYWRAP_OBJECT_NAME, null)`.
7. `saveVaultKey(K')`. Return; the CLI prints the phrase and then calls `clearNextKey()` (D-11).

## 12. Non-goals

- Re-encrypting existing chunks, settlement-archive chunks or WIP parts under `K'` (the ring keeps them readable).
- Deleting refs or objects from the backend, or garbage-collecting markers and orphan objects.
- Implementing the hosted `overdeck://` store, device revocation, `pan account`, or editing `configuration/anywhere-sign-in.mdx` (PAN-4297, PAN-4330).
- Automatic rotation (on revoke, on a schedule) or rotation from the dashboard UI.
- Rotating git credentials for the user; the docs tell them to.
- Removing a key from the ring.
- "Approve from another device" key transfer.
