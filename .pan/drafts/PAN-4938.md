## Glossary

- **Agent token:** an `odk_` access-token record of `kind: 'token'` with `agentId`, `agentKind: 'agent' | 'conversation'` and `role` (W-TOK1). The resolved dashboard credential is `{ kind: 'token'; tokenId; scopes; agentId?; agentKind?; role? }` (`src/dashboard/server/routes/dashboard-auth.ts:158`).
- **Self route:** a route under `/api/self/` that acts for the calling agent. `selfCallerFromCredential` (`src/dashboard/server/self-caller.ts:52`) turns the credential into a `SelfCaller` `{ agentId, agentKind, role, cwd, issueId, tmuxSession }` or a 403 `not-an-agent-token` / 404 `agent-gone` refusal. The agent always comes from the token, never the body.
- **Self job:** a `pan` CLI command a self route runs asynchronously (`src/dashboard/server/services/self-jobs.ts`). Verbs are a closed set (`services/self-job-argv.ts:14-24`); `lane-report` is already in it (line 21).
- **Wait chunk:** one blocking call of at most `WAIT_CHUNK_MS = 50_000` (`src/lib/mcp/tool.ts:31`). A wait route answers `done` or `running` with `next`, the call to make again.
- **Worker:** an agent started by `pan worker run` / `startWorker` (`src/lib/agents/worker/start.ts`). Its id is `agent-<issue>-worker-<n>` (`isWorkerId`, `src/lib/agents/worker/ids.ts:39`). A local worker has a write-once `worker.json` (`facts.ts`, `WorkerFacts.parentId`, `startedAt`).
- **Stand-in:** the local directory of a worker that runs on a linked machine. It has `remote.json` (`RemoteStandIn`, `src/lib/agents/worker/remote-standin.ts:18-34`, with `parentId`, `createdAt`, `state`) and mirrored reports, and **no `worker.json`**.
- **Worker parent id:** the `parentId` a worker records. For an agent it is the agent id (`agent-pan-1`); for a conversation it is the conversation's **tmux session** `conv-<name>`, because `pan worker run` defaults `--parent` to `OVERDECK_CONVERSATION` (`src/cli/commands/worker.ts`, `resolveWorkerParent`) and the remote follower keys on the `conv-` prefix (`src/dashboard/server/services/remote-worker-follower.ts:209-212`).
- **Lane:** a conversation launched by `pan lane start` / `POST /api/lanes` with write-once run, key and role facts (`src/lib/lanes/launch.ts`). Its `parent` must be a conversation (`launch.ts:397-398`). Lane reports live in the worker report store keyed `conv-<name>`.
- **Lane set wait:** `waitForLaneSet(filter, options, deps)` (`src/lib/lanes/wait.ts:181`) returns the next report of any lane in a run or of a parent after a cursor `<atMs>.<name>.<seq>`.
- **Fleet caller:** `FleetCaller { actor, ceiling?, mayCreateFly? }` (`src/dashboard/server/routes/fleet-work.ts:95-100`), the identity a forwarded call carries to a linked machine. `actor` is `'operator'` or `{ agentId }` (`LinkActorInit`, `src/lib/anywhere/link-client.ts:144`).
- **Agent fence:** on the owner machine, an agent actor may read a linked conversation but not change it (`src/dashboard/server/link-fence.ts:82`); work doors stamp `startedBy` so the starting machine's agent may later stop what it started.
- **Audience:** `OverdeckTool.audience` — `'agent'` tools are listed only to agent tokens (`src/lib/mcp/server.ts:43-45`).

## Facts this plan is built on (verified 2026-11-03 on `origin/main` f683d45e7f6)

1. **The tool layer has no caller identity.** `McpToolContext` is `{ api; scopes; isAgent }` (`src/lib/mcp/tool.ts:13-19`). A tool cannot fill `parentId` or `issueId` itself; only a self route can.
2. **`POST /api/fleet/workers` takes `parentId` from the body** (`handleFleetWorker`, `fleet-work.ts:262-299`; `PARENT_ID_RE = /^[A-Za-z0-9_:.-]+$/`, `start.ts:86`). A local worker starts through `startWorker`; a remote one gets a stand-in and the owner's worker work door.
3. **`fleetCaller` treats every token as the operator** (`fleet-work.ts:102-109`):
   ```ts
   if (credential?.kind === 'token') {
     return { actor: 'operator', ceiling: credentialScopes(credential).filter(...), mayCreateFly };
   }
   ```
   and so does the linked-conversation proxy (`src/dashboard/server/linked-conversation-proxy.ts:129-132`):
   ```ts
   const tokenCeiling = input.credential?.kind === 'token' ? credentialScopes(input.credential).filter(...) : null;
   const actor = tokenCeiling ? 'operator' : actorForSender(input.sender);
   ```
4. **What `pan` gets today on a linked machine.** `senderFromEnv` (`src/lib/terminal-backends/prompt-guard.ts:216-224`) returns the agent id when `OVERDECK_AGENT_ID` is set, else `conv-operator-<pid>`; `actorForSender` (`linked-conversation-proxy.ts:95-98`) maps `conv-operator-*` and any issue-less `conv-*` sender to `'operator'` and any other sender to `{ agentId }`. So an agent's `pan` acts as that agent, and a conversation's `pan` acts as the operator.
5. **Work doors accept agent actors.** `handleWorkWorker` / `handleWorkIssueStart` (`src/dashboard/server/routes/machines-work.ts`) require a `machine` credential and stamp `startedBy`; only the project door checks the actor. `POST /api/workers/:id/stop` fences an agent actor to workers its machine started (`routes/workers.ts:168-180`).
6. **The worker wait already exists but lives partly in the CLI.** `waitForWorkerReport(id, { afterSeq, timeoutMs, idleGraceMs, startupGraceMs, pollMs, signal }, deps)` (`src/lib/agents/worker/wait.ts:107`) returns `report | exited-without-report | idle-without-report | timeout`. The stand-in variant `standInWaitDeps` and the dispatcher `waitForAnyWorker` are in `src/cli/commands/worker-remote.ts:101-126`. No dashboard server module imports from `src/cli/commands/` (checked with grep).
7. **Chunked waits defeat the startup grace.** `waitForWorkerReport` sets `startedAt = now()` per call (`wait.ts:118`) and counts a death only `seenAlive || current - startedAt >= startupGraceMs` (default 60 s), and idleness only after `current - startedAt >= startupGraceMs`. With 50 s chunks and the 60 s default, a worker that died before the chunk began is never confirmed dead and is never idle: every chunk answers `timeout`, forever.
8. **`readWorkerFacts` is the ownership source for local workers only.** `readWorkerFacts(id)` (`facts.ts:27`) reads `worker.json`; a stand-in has none, so it returns `null`. `listWorkers({ parentId })` (`list.ts:18`) therefore never lists stand-ins. `listRemoteStandIns()` (`remote-standin.ts:63`) lists them.
9. **`GET /api/workers/:id/status` answers 404 `unknown-worker` for a stand-in** (it calls `readFacts`, `routes/workers.ts:152-153`). `POST /api/workers/:id/stop` does the same; a stand-in is stopped with `POST /api/fleet/workers/:id/stop` (`fleet-work.ts:338-349`).
10. **The issue-start door is an Effect with services.** `spawnIssueAgentForRoute` (`src/dashboard/server/routes/agents/spawn-issue.ts:209`) yields `EventStoreService`, `IssueLifecycle` and `ReadModelService`. `handleWorkIssueStart` (`machines-work.ts:218-243`) is therefore generic over `R` and `yield*`s `deps.spawn`; its route does `return yield* handleWorkIssueStart(...)` (`machines-work.ts:320-329`). `handleFleetIssueStart` (`fleet-work.ts:315`) is a Promise, called inside `Effect.promise` (`fleet-work.ts:475`), and refuses a local target with 400 `use-local-start` (`fleet-work.ts:326`).
11. **Lanes.** `POST /api/lanes` requires `parent`, `role`, `brief` (`routes/lanes.ts`, `parseLaneLaunchBody`) and calls the exported `handleLaneLaunch(request, { viaChannel, caller })` (`lanes.ts:201`). `GET /api/lanes` and `GET /api/lanes/:name` have no-loss rows (`tests/unit/lib/overdeck/no-loss-matrix.ts:75-76`) but **no route-scope rows**, so a token needs `admin` for them. `POST /api/lanes` and `POST /api/lanes/:name/stop` are `operate` (`route-scopes.ts:74, 76`).
12. **`waitForLaneSet` is CLI-shaped.** Its default `listLanes` fetches `/api/lanes` over HTTP and its default `warn` writes to `process.stderr` (`wait.ts:63-75, 185-188`). It has no `signal`. In-process, `listLaneViews(filter: { run?, parentName?, key?, role? })` (`src/lib/lanes/views.ts:77-82`) is the source.
13. **`reportLane` finds its lane from `OVERDECK_CONVERSATION`** (`src/lib/lanes/report.ts:109-115`). `selfJobEnv` sets it only for conversation callers (`self-jobs.ts:84-91`). CLI flags: `--status <s>`, `--stdin`, `--verdict <v>`, `--defects <n>` (`src/cli/commands/lane.ts:665-673`).
14. **Conversation stop and abort routes exist and are `operate`** (`route-scopes.ts:72-73`; handlers `routes/conversations.ts:331`, `:445`). Abort supports Pi conversations only and answers 400 "Abort control endpoint is only supported for Pi conversations" for every other harness (`src/lib/overdeck/conversation-delivery.ts:471-485`). No interrupt route exists for Claude Code or Codex.
15. **Tests that pin tool lists.** `tests/unit/lib/mcp/visibility.test.ts` asserts `toHaveLength(13)` for `read:state, read:conversations, operate` and exactly `['list_machines', 'wait_job']` for a `read:state` agent token. `tests/unit/lib/mcp/tool-annotations.test.ts:31-36` asserts every tool outside `SELF_TOOLS` has `audience: 'any'`. `tests/unit/lib/mcp/tools-approve.test.ts:28-35` pins the whole `ALL_TOOLS` name list. All three break as soon as this issue adds a tool. `src/dashboard/server/__tests__/mcp-route.test.ts:128` computes its list from `ALL_TOOLS` and does not break.
16. **File sizes.** `fleet-work.ts` 490 lines, `linked-conversation-proxy.ts` 196, `routes/lanes.ts` 382, `src/lib/mcp/tools-write.ts` 137, `src/lib/mcp/server.ts` 67, `src/dashboard/server/server.ts` 578, `src/cli/commands/worker-remote.ts` 180. All under the 600-line design rule and the 1,000-line guard.

## Requirements

### Functional

- **FR-1 Delegate.** An agent with an issue calls `delegate_task` and a worker starts on that issue with the caller as its parent, on this machine or the `machine` it names. A caller without an issue gets the error text `delegate_task needs an issue; use start_conversation`.
- **FR-2 Wait for a worker.** `task_wait` returns the worker's report (`done`), a reportless end (`ended`, with the last assistant message), or `running` with `next` after at most 50 s. It works for local workers and for stand-ins, and only for the caller's own workers.
- **FR-3 Worker status and list.** `list_workers` lists the caller's workers (local and stand-ins) with state and latest report; `task_status` returns one of them.
- **FR-4 Cancel a worker.** `task_cancel` stops one of the caller's workers, local or remote.
- **FR-5 Lanes.** A conversation starts a lane under itself with `lane_start`, reads one with `lane_status`, stops one with `lane_stop`, waits for its lanes' next report with `lane_wait` (at most 50 s per call), and, inside a lane, files its report with `lane_report`.
- **FR-6 Start an issue.** `start_issue` starts a planned issue's work agent on this machine through the same gates as the dashboard's Start button, or on a linked machine through its work door.
- **FR-7 Stop and interrupt a conversation.** `stop_conversation` stops a conversation; `interrupt_conversation` interrupts a Pi conversation's turn and returns the route's error text unchanged for other harnesses.
- **FR-8 An agent token acts as that agent on a linked machine** (epic D-9). A conversation's token keeps acting as the operator, limited by its scopes.
- **FR-9 Documentation.** `configuration/mcp.mdx` and `docs/DASHBOARD-AUTH.md` describe every new tool and route in the same change set.

### Non-functional

- **NFR-1 One authority.** Every tool calls a dashboard route; `route-scopes.ts` judges it. Every new route is in a top-level file of `src/dashboard/server/routes/`, has a `no-loss-matrix.ts` row and a `route-scopes.ts` row.
- **NFR-2 Bounded waits.** No new route or tool blocks longer than 50 s.
- **NFR-3 Async only.** No `execSync`, `spawnSync`, `execFileSync`, and no new `*Sync` function (repo rules `no-execsync-server`, `prefer-async`).
- **NFR-4 Fake timers.** Tests of waits and timeouts use `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()`, never real sleeps (repo rule `fake-timers-for-retry-tests`).
- **NFR-5 Size.** Every new module stays under 600 lines.
- **NFR-6 Effect boundary.** No new exported Effect wrapper around in-repo Promise or sync code and no sync/async twin; `npm run lint:effect-facades` must not rise. `lint:circular` stays clean.
- **NFR-7 Identity from the token only.** No self route reads an agent id, issue id or parent id from the body, query or headers.
- **NFR-8 AC-2 of the epic stays true:** `tools/list` for a `read:state`-only non-agent token still returns only `list_machines` (so no new `audience: 'any'` tool may have scope `read:state`).

## Decisions

- **D-1 `delegate_task` posts a self route, not the fleet route.** Facts 1-2: the tool cannot know the caller. New `POST /api/self/workers` (scope `operate`) resolves the caller, builds the fleet body itself (`issueId` = caller's issue, `parentId` = worker parent id, D-2), and calls `handleFleetWorker`. Body fields `issueId` and `parentId` are never read from the request.
- **D-2 Worker parent id.** One helper `workerParentOf(caller)`: `caller.agentKind === 'agent' ? caller.agentId : caller.tmuxSession ?? \`conv-${caller.agentId}\``. Every ownership comparison uses it, case-insensitively, so `pan worker list --parent conv-<name>` and the remote follower see these workers exactly as they see `pan worker run` workers.
- **D-3 Ownership reads both sources.** A worker id is the caller's when `readWorkerFacts(id)?.parentId` or `readRemoteStandIn(id)?.parentId` equals `workerParentOf(caller)` (case-insensitive). Otherwise every worker route answers 404 `{ code: 'unknown-worker', error: 'no such worker' }`, the same for a missing worker and another agent's worker.
- **D-4 Move the stand-in wait to `src/lib`.** `standInWaitDeps` and `waitForAnyWorker` move verbatim to new `src/lib/agents/worker/wait-any.ts`; `worker-remote.ts` re-exports both names (one implementation, so `worker.ts` and `tests/unit/cli/worker-remote.test.ts` change nothing).
- **D-5 Chunked waits carry the worker's age.** The worker wait route passes `startupGraceMs = Math.max(0, WAIT_STARTUP_GRACE_MS - (Date.now() - launchedAtMs))`, where `launchedAtMs` is `Date.parse(facts.startedAt)` or `Date.parse(standIn.createdAt)`; an unparsable time keeps `WAIT_STARTUP_GRACE_MS`. A worker older than 60 s is then judged dead or idle in the first poll of any chunk (Fact 7).
- **D-6 Worker status is a self route.** `task_status` → new `GET /api/self/workers/:id`, `list_workers` → new `GET /api/self/workers`; both owner-only and both include stand-ins. The epic's mapping to `GET /api/workers/:id/status` is not used because that route answers 404 for every stand-in (Fact 9) and checks no ownership.
- **D-7 `task_cancel` is two calls over existing doors.** It calls `GET /api/self/workers/:id` (owner check and local/remote), then `POST /api/workers/:id/stop` for a local worker or `POST /api/fleet/workers/:id/stop` for a stand-in. No new write route.
- **D-8 `start_issue` local branch: `handleFleetIssueStart` becomes an Effect.** It mirrors `handleWorkIssueStart`: `handleFleetIssueStart<R>(issueId, raw, caller, deps: FleetIssueStartDeps<R>): Effect.Effect<HttpServerResponse, unknown, R>` with `deps.spawn` = `spawnIssueAgentForRoute`. When the target is this machine and `caller.viaToken` is true, it `yield*`s `deps.spawn({ body: { issueId, ...options }, internalRequest: false })`; every other caller keeps 400 `use-local-start`. The route does `return yield* handleFleetIssueStart(...)`. Why not a sentinel return: the Effect shape is the one `machines-work.ts` already uses for the same door, so the executor copies a working pattern. `lint:effect-facades` does not apply: `scripts/audit-effect-boundary.mjs` audits only `src/lib` modules (line 286), and `fleet-work.ts` is in `src/dashboard`.
- **D-9 Link actor for tokens.** New `tokenLinkActor(credential)` in `linked-conversation-proxy.ts`: an agent token with `agentKind === 'agent'` → `{ agentId: credential.agentId }`; every other token (plain token, conversation token) → `'operator'`. The ceiling (the token's scopes minus `admin`) applies to all tokens unchanged. `forwardLinkedConversationRequest` and `fleetCaller` both use it. Why a conversation token stays `'operator'`: Fact 4 — a conversation's own `pan` acts as the operator today, and the epic's D-9 rule is parity with `pan`; fencing the operator's chat would also break answering a linked machine's prompts (W-APPR1) from it.
- **D-10 `FleetCaller.viaToken`.** `fleetCaller` sets `viaToken: true` for every `token` credential. Only `handleFleetIssueStart` reads it (D-8).
- **D-11 Lanes are agent-only tools, and `lane_start` is a self route.** A lane's `parent` must be a conversation (Fact 11) and the tool cannot know the caller (Fact 1). New `POST /api/self/lanes` (scope `operate`) sets `parent` to the caller's conversation name and drops any `parent` and `force` in the body, then calls `handleLaneLaunch`. An agent-kind caller gets 409 `{ code: 'not-a-conversation', error: 'lane_start needs a launching conversation; an agent delegates with delegate_task' }`. `lane_status` (→ `GET /api/lanes/:name`) and `lane_stop` (→ `POST /api/lanes/:name/stop`) are `audience: 'agent'` too, so NFR-8 holds and all lane tools live together. `GET /api/lanes` and `GET /api/lanes/:name` get `read:state` rows.
- **D-12 `lane_wait` and `lane_report` run in process.** `POST /api/self/lanes/wait` (scope `read:state`) calls `waitForLaneSet` with `listLanes` mapped onto `listLaneViews` and `warn` collecting lines into the answer; the set is `{ run }` when given, else `{ parent: <caller's conversation name> }`; an agent-kind caller without `run` gets 409 `not-a-conversation`. `POST /api/self/lanes/report` (scope `tell`) requires the caller to be a lane conversation (409 `{ code: 'not-a-lane' }` otherwise), validates `verdict` with `isLaneVerdict` and `defects` as a non-negative integer, starts the existing `lane-report` job verb with the report on stdin, waits up to 50 s, and answers `selfJobAnswer`.
- **D-13 Tool files.** Worker tools go in new `src/lib/mcp/tools-delegate.ts` (`DELEGATE_TOOLS`, all `audience: 'agent'`), lane tools in new `src/lib/mcp/tools-lanes.ts` (`LANE_TOOLS`, all `audience: 'agent'`), and the three `audience: 'any'` tools (`start_issue`, `stop_conversation`, `interrupt_conversation`) in `src/lib/mcp/tools-write.ts` (`WRITE_TOOLS`). `ALL_TOOLS` becomes `[...READ_TOOLS, ...WRITE_TOOLS, ...SCHEDULE_TOOLS, ...APPROVE_TOOLS, ...SELF_TOOLS, ...DELEGATE_TOOLS, ...LANE_TOOLS]`. `tools-self.ts` and `self-job-argv.ts` are not edited (W-SELF2 owns them).
- **D-14 Worker routes in one file, lane routes in another.** New `src/dashboard/server/routes/self-workers.ts` (four routes) and `src/dashboard/server/routes/self-lanes.ts` (three routes), each exporting a route layer registered in `src/dashboard/server/server.ts` next to `selfJobsRouteLayer` (line 376).
- **D-15 Tool-list tests stop pinning counts.** Before any tool is added, `visibility.test.ts`, `tool-annotations.test.ts` and `tools-approve.test.ts` are rewritten to compute from `ALL_TOOLS` and the per-file arrays, keeping the AC-2 invariant exact. Each new tool's own test file asserts its scope equals `requiredScopeFor(method, path)` of its route and its audience.
