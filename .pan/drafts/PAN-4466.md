# PAN-4466 — Needs-you shows permission prompts with no way to answer them

**Issue:** [PAN-4466](https://github.com/eltmon/overdeck/issues/4466)
**Builds on:** PAN-4278 (terminal permission prompts in Claude Code conversations, PR #4284)
**Planned:** 2026-10-02, `pan plan --auto` (no operator questions; defaults recorded in "Decisions")

## Glossary

- **Permission prompt** — the block Claude Code draws in place of its input box while a tool call waits for permission: a `───` rule, a title line (`Bash command`, or `Bash command · from the <type> agent` for a subagent), the command, an optional reason (`│ Dangerous rm operation …`), `Do you want to proceed?`, then `❯ 1. Yes`, optionally `2. Yes, and always allow …`, and `No`, then the footer `Esc to cancel · Tab to amend`.
- **Clipped prompt** — a permission prompt taller than the pane's visible screen, so its `───` rule and title line have scrolled off the top. Only the tail of the command, the reason, the question, the options and the footer are visible.
- **Pane read** — the dashboard's read of a conversation's terminal screen through `resolveAgentPaneIo` (`src/lib/terminal-backends/agent-pane-io.ts`). On Herdr this is `pane.read` with source `visible`: only the rows currently on screen. A full-screen TUI has no scrollback, so `recent` returns the same rows.
- **Registry** — the in-memory record of `PermissionRequest` hook posts per conversation and per agent key (`agent_id ?? 'main'`), in `src/lib/overdeck/conversation-permission-registry.ts`. It names the asking agent, the tool, a 200-character input preview and the request time. It is empty after a dashboard restart.
- **`pendingPermission`** — the feed field (`PendingPermission` in `src/lib/overdeck/conversation-permission.ts`) that the pending-input feed (`GET /api/conversations/pending-input`) and `GET /api/conversations/:id` carry.
- **Answerable** — `pendingPermission.answerable === true`: the pane parser found the prompt on screen, so the dashboard can answer it with arrow keys + Enter. `false` means only the registry knows about a request.
- **Needs-you row** — one row in the Awareness rail's Needs-you scope (`NeedsYouSection` in `src/dashboard/frontend/src/components/sessionFeed/SessionFeedSidebar.tsx`).
- **Decisions panel** — the popover list from `DecisionsIndicator` (`src/dashboard/frontend/src/components/DecisionsPanel.tsx`), fed by `useDecisions`.
- **Permission dialog** — `TerminalPermissionDialog` (`src/dashboard/frontend/src/components/TerminalPermissionDialog.tsx`), state in `useTerminalPermissionDialog`.
- **Terminal view** — a conversation pane in the Command Deck showing the live xterm terminal instead of the chat transcript. Selected per pane by `pane.viewMode === 'terminal'` (`src/dashboard/frontend/src/components/Stage/panes/AgentPane.tsx`, line 28).

## Problem

On 2026-10-02 the operator saw a Needs-you row "20260929-6671 · Subagent: Find better Overdeck screenshots · waiting" with no way to act on it. The conversation's read model held:

```
pendingPermission: { answerable: false, options: [], agentLabel: "Subagent: Find better Overdeck screenshots",
                     agentKey: "a022774fdd0117553", toolName: "Bash", detailLines: ["S=/tmp/…; node shoot2.cjs …"], since: "2026-10-02T02:31:52Z" }
```

### Root cause (verified during planning)

The prompt **was** on screen. The conversation runs in Herdr pane `w21:p29`, whose viewport is 20 rows (`herdr pane list` → `"viewport_rows":20`). The subagent's Bash command is about 40 lines long, so the prompt is taller than the screen and its `───` rule and `Bash command · from the general-purpose agent` title scrolled off the top. This is the whole visible screen (Claude Code 2.1.284, `herdr pane read w21:p29 --source visible`):

   │ Your Now\"].includes(t)) b.style.display=\"none\";})"},{"wait":500}]}'

`parsePermissionPrompt` (`src/lib/agents/permission-prompt.ts`, lines 149–154) requires a `───` rule within `MAX_BLOCK_LINES` (40) above the question and returns `null` without one:

```ts
  // The prompt block starts under the nearest ─── rule above the question.
  let rule = -1;
  for (let j = q - 1; j >= 0 && q - j <= MAX_BLOCK_LINES; j -= 1) {
    if (SEPARATOR_LINE.test(lines[j]!)) { rule = j; break; }
  }
  if (rule < 0) return null;
```

A planning probe (`tsx` script, read-only) confirmed: the live capture above parses to `null`; the existing fixture `src/lib/agents/__fixtures__/claude-code-2.1.280/permission-subagent.txt` parses (header `Bash command`), and the same fixture with its rule and title lines removed parses to `null`.

`pendingPermissionFromPane` (`src/lib/overdeck/conversation-permission.ts`, lines 140–153) then falls back to the registry entry and emits `answerable: false` with `options: []`.

**This is not subagent-specific.** A main-agent prompt with a long command fails the same way. The subagent case is simply where long commands show up most.

### Consequences today

1. The dialog offers only **Dismiss** and **Open terminal**; the Needs-you row shows `<agent> · <tool>` and `waiting <time>` with no next step.
2. **Open terminal does not open the terminal.** `useTerminalPermissionDialog.onOpenTerminal` (line 91) calls `navigateToDecisionSubject({ id, source: 'conversation' })`, which pushes `/conv/<name>` with no `?view=terminal`. `CommandDeck` declares a `conversationViewMode` prop (`src/dashboard/frontend/src/components/CommandDeck/index.tsx`, line 153) but never reads it, and its deep-link effect (around line 596, `openConversationTabIn(projectName, conv.name, …, target)`) passes no view mode. Its `appliedConvId` guard also skips a second navigation to the same conversation. So the operator lands on the chat transcript.
3. **The composer can answer the prompt by accident.** The composer route (`src/lib/overdeck/conversation-message.ts`, line 560) holds a send only when `pendingPermission?.answerable`. A clipped prompt is not answerable, so a send proceeds to `ensureMainInputTarget`, whose `Down`/`Enter` keys move the menu cursor and answer the prompt.
4. The Needs-you row label is the raw conversation name (`20260929-6671`), because `NeedsYouSection` labels a subject `formatIssueRef(issueId) ?? agentId` and conversation subjects carry no title.

## Requirements

### Functional

- **FR-1** `parsePermissionPrompt` returns a prompt for a clipped permission prompt that meets the clipped acceptance rules (Decision D2), with `clipped: true`, `header: null` and `fromAgent: null`.
- **FR-2** For a clipped prompt the parser never infers the asking thread: callers treat the thread as unknown, never as "main".
- **FR-3** A wrapped reason (`│ Dangerous …` followed by `│ or use a literal path)`) is joined into one `reason` string and its continuation line does not appear in `detailLines`.
- **FR-4** `pendingPermission` for a clipped prompt is `answerable: true`, carries the parsed options, `clipped: true`, and `inputPreview` (the matched registry entry's 200-character input preview, else `null`).
- **FR-5** `POST /api/conversations/:id/permission` answers a clipped prompt exactly like an unclipped one (signature check, arrow keys + Enter, confirm it left the screen) and clears the matched registry entry.
- **FR-6** The composer route holds a message (409 `permission-pending`) while a clipped prompt is on screen.
- **FR-7** The permission dialog shows, for a clipped prompt, the start of the command from `inputPreview` and the visible part from `detailLines`, and says the top of the prompt is off-screen.
- **FR-8** The permission dialog, for a non-answerable prompt, states the next step in words and makes **Open terminal** the primary button.
- **FR-9** **Open terminal** (dialog) navigates to `/conv/<name>?view=terminal`, and the Command Deck shows that conversation's pane in terminal view, including when the conversation pane was already open in chat view.
- **FR-10** A Needs-you row and a Decisions-panel row for a pending permission show the asking agent, the tool, the next step (`click to answer` or `answer in the terminal`), and the first line of the command; a Needs-you row is labeled with the conversation's title.
- **FR-11** Clicking a Needs-you row for a non-answerable permission navigates straight to the conversation's terminal view (one click), without opening the dialog.

### Non-functional

- **NFR-1** No false-positive answer path: the answer endpoint still re-parses the pane and refuses (409) when the prompt is gone or its signature changed. Clipped detection never relaxes the bottom-of-screen, single-cursor and option-shape rules.
- **NFR-2** `src/dashboard/frontend/src/components/CommandDeck/index.tsx` does not grow past its allowlist cap (1612 lines; 1608 on `origin/main` at planning time). Work item 6 extracts code so the file shrinks.
- **NFR-3** No new `*Sync` tmux or Herdr calls; all pane I/O stays on the existing async `resolveAgentPaneIo` path.
- **NFR-4** Every existing test in `permission-prompt.test.ts`, `conversation-permission-feed.test.ts` and `conversation-permission-answer.test.ts` keeps passing unchanged, except assertions on `permissionSummary` text that FR-10 deliberately changes.

## Decisions

- **D1 — Fix the parser, not the pane height.** The prompt is on screen; the parser is too strict. Launching conversation panes taller would only move the threshold (a 60-line command clips any pane), so it is a NonGoal here.
- **D2 — Clipped acceptance rules.** A clipped prompt is accepted only when ALL hold:
  1. Every existing rule up to and including the question check passes: option 1 starts with `Yes`, options run 2–3 rows, the last is `No`, a 3-option middle row matches `ALLOW_ALWAYS_LABEL`, exactly one `❯` cursor row, and nothing but blanks, rules and footer hints sit below the options.
  2. The question line matches `QUESTION_LINE` (`/^do you want to\b/i`). The looser `PERMISSION_TEXT` fallback is not enough for a clipped prompt.
  3. No `SEPARATOR_LINE` exists between line `max(0, q - MAX_BLOCK_LINES)` and the question line `q`.
  4. At least one trailing line below the options matches `/\besc to cancel\b/i`.
  5. At least one non-blank line exists above the question in that window.
- **D3 — Detection is not gated on the registry.** A clipped prompt is answerable whether or not a registry entry exists. Reasons: the registry is empty after every dashboard restart, and the composer hold (FR-6) needs detection to be on — missing a prompt is the dangerous direction, because the composer then sends keys into it. A detection false positive costs only an Allow/Deny button that the answer endpoint refuses with 409.
- **D4 — Thread is unknown, expressed by `clipped`.** `PermissionPrompt` gains `clipped: boolean`. When `clipped` is true, `header` and `fromAgent` are `null` and every caller checks `clipped` before reading `fromAgent` as "main thread". `header` becomes `string | null`.
- **D5 — Clipped signature.** `signature = (clipped ? '(clipped)' : title) + '::' + detail + '::' + options`. The visible lines of a blocked TUI do not change between reads, so the signature is stable for one prompt.
- **D6 — "Expandable" command means click-opens-dialog.** The Needs-you row shows the first line of the command, truncated by CSS, with the full text in the row's `title` attribute. Clicking an answerable row opens the dialog, which shows the full command. No inline expander.
- **D7 — One-click terminal for non-answerable rows.** A Needs-you row whose permission is non-answerable navigates to `/conv/<name>?view=terminal` on click and does not reopen the dialog (FR-11). Answerable rows keep today's behavior (navigate + `requestReopen`, which focuses the dialog).
- **D8 — Next-step text lives in `permissionSummary`.** Both the Needs-you row and the Decisions panel render `permissionSummary`, so the next step goes there once: `"<agent> · <tool> · click to answer"` when answerable, `"<agent> · <tool> · answer in the terminal"` when not. With no tool: `"<agent> · click to answer"` / `"<agent> · answer in the terminal"`.
- **D9 — Command line source.** `permissionCommand` = first non-empty line of `inputPreview` when present, else first entry of `detailLines`, else absent. `inputPreview` is preferred because it is the start of the command, which a clipped screen cannot show.
- **D10 — Changelog.** Add one line under a `#### Fixed` heading in the `<Update label="v0.65.0" … tags={["Upcoming"]}>` block of `changelog.mdx` (create the heading after `#### Changed` if absent). If that block no longer exists at implementation time, add it to whichever `Upcoming` block is at the top.

```ts
  // The prompt block starts under the nearest ─── rule above the question. A
  // prompt taller than the screen has lost its rule and title off the top: it
  // is accepted as clipped only under the stricter rules below.
  const windowStart = Math.max(0, q - MAX_BLOCK_LINES);
  let rule = -1;
  for (let j = q - 1; j >= windowStart; j -= 1) {
    if (SEPARATOR_LINE.test(lines[j]!)) { rule = j; break; }
  }
  const clipped = rule < 0;
  if (clipped) {
    if (!QUESTION_LINE.test(question)) return null;
    if (!trailing.some((line) => CANCEL_HINT.test(line))) return null;
  }

  const blockStart = clipped ? windowStart : rule + 1;
  const rawBlock = lines.slice(blockStart, q).filter((line) => line.trim() !== '');
  if (rawBlock.length === 0) return null;
  const title = clipped ? null : rawBlock[0]!.trim();
  const fromMatch = title ? FROM_AGENT_SUFFIX.exec(title) : null;
  const header = title === null ? null : fromMatch ? fromMatch[1]!.trim() : title;
  const fromAgent = fromMatch ? fromMatch[2]!.trim() : null;
```

```ts
  const detailLines: string[] = [];
  let reason: string | null = null;
  let inReason = false;
  for (const raw of clipped ? rawBlock : rawBlock.slice(1)) {
    const hadBar = REASON_BAR.test(raw.trim());
    const text = raw.trim().replace(REASON_BAR, '');
    if (reason === null && REASON_TEXT.test(text)) { reason = text; inReason = true; continue; }
    // A long reason wraps onto further │ rows; they continue it, not the command.
    if (inReason && hadBar) { reason = `${reason} ${text}`; continue; }
    inReason = false;
    detailLines.push(text);
  }
```
