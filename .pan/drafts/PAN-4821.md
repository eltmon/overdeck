# PAN-4821: Close-out reports "no pull request found" when the forge PR read fails

**Issue:** [PAN-4821](https://github.com/eltmon/overdeck/issues/4821)
**Status:** planned (auto mode, 2026-11-02)

## Glossary

- **Close-out** — the `pan close <id>` ceremony (`src/cli/commands/close.ts`). It runs `closeOut()`
  (`src/lib/lifecycle/workflows.ts`) in the CLI's own process, which first evaluates the DoD gate.
- **DoD gate** — the Definition-of-Done gate, `evaluateDodGate()` in `src/lib/lifecycle/dod-gate.ts`.
  It returns nine rows. Each row has a status `pass | miss | skip` (`DodRowStatus` in
  `src/lib/lifecycle/dod.ts`). An unaccepted `miss` blocks close-out. `close.ts` prints the first failed
  step's text as `Close-out failed: <text>`.
- **Verdict rows** — rows 1 (`review`) and 2 (`tests`). Both are computed by `checkVerdict()` in
  `dod-gate.ts` from the PR that `DodStatusRowDeps.readPullRequest` returns.
- **Row 4 (`merged`)** — `checkMergedRow()`. It reads the PR through `MergedRowDeps.readPullRequest` to get
  `mergedAt` and `mergeCommit`. Row 6 (`main-verify`) and row 8 (`deploy`) use that `mergeCommit`.
- **Row 5 (`post-merge`)** — `checkPostMergeRow()`. It reads the PR's `mergedAt` through
  `PostMergeRowDeps.readMergedAt`, as a secondary signal beside the canonical state.
- **PR read** — `fetchIssuePullRequest(issueId)` in `src/lib/overdeck/pull-requests.ts`. It returns
  `IssuePrEndpointResponse = { issueId, pr: IssuePullRequestData | null, error?: string }`.
  - **Absent:** `{ pr: null }` with no `error` — the forge answered and no PR exists for
    `feature/<id>` or `strike/<id>`, or the issue is not a GitHub issue.
  - **Read failed:** `{ pr: null, error }` — the forge lookup threw. Two sources produce it:
    `resolveIssuePullRequestRef()` (the GitHub App REST lookup, or `gh pr list` when no App is configured,
    through `lookupPullRequestForBranch()` in `src/lib/github-pr-lookup.ts`) and
    `fetchIssuePullRequestFromRef()` (`gh pr view`, 15 s timeout).
- **PR-tab cache** — the in-process map in `src/dashboard/server/services/pr-tab-cache.ts`
  (`getCachedIssuePrTabResponse` / `setCachedIssuePrTabResponse`). An entry lives until the issue's
  generation is bumped by a PR webhook, or for `PR_TAB_CACHE_TTL_MS` (60 s).
- **Retry pause** — the wait between the first and second PR read attempt in the new helper.

## Problem

`pan close <id> --force` failed three times on 2026-11-02 with
`Close-out failed: no pull request found on the forge for this issue` for issues whose PRs were merged
([PAN-4748](https://github.com/eltmon/overdeck/issues/4748) PR #4796,
[PAN-4810](https://github.com/eltmon/overdeck/issues/4810) PR #4814,
[PAN-4813](https://github.com/eltmon/overdeck/issues/4813) PR #4816). Each passed on an immediate retry.
Both failure bursts were the first close-outs after a `pan reload`.

The certain defect: the gate maps every PR read failure to "no PR".

`src/lib/lifecycle/dod-gate.ts` lines 302-306 (grep anchor `return response.error ? null : response.pr;`):

```ts
const defaultDeps: DodStatusRowDeps = {
  readPullRequest: async issueId => {
    const response = await fetchIssuePullRequest(issueId);
    return response.error ? null : response.pr;
  },
```

`checkVerdict()` lines 393-398 (grep anchor `deps.readPullRequest(issueId))().catch(() => null)`) then
also maps a thrown read to `null`, and reports the absence text:

```ts
  const pr = await (async () => deps.readPullRequest(issueId))().catch(() => null);

  if (!pr) {
    const observed = 'no pull request found on the forge for this issue';
```

So the real error text is thrown away. Worse, a read failure can be settled into a `skip` by the strike
path or by `terminalVerdictSettlement()`, even though a failed read cannot rule out
`CHANGES_REQUESTED` or red checks.

`fetchIssuePullRequest()` (`src/lib/overdeck/pull-requests.ts` lines 275-291, grep anchor
`setCachedIssuePrTabResponse('pr', issueId, generation, result);`) also caches the error response, so
inside one process every later read in the next 60 s returns the same failure without asking the forge.

## Root-cause notes (not fixed here)

The trigger is unknown. These facts were verified while planning and go to the work agent as hazards:

- `pan close` runs `closeOut` in the CLI process (`close.ts` line 402, `Effect.runPromise(closeOut(ctx, …))`),
  so every CLI close-out starts with an empty PR-tab cache and an empty installation-token memo
  (`installationTokenMemo` in `src/lib/github-app.ts`). The in-process cache alone cannot explain the
  "first close-out after reload" pattern.
- Every GitHub App REST call goes through `finishAppRestCall()` (`src/lib/github-quota/rest-meter.ts`
  line 119), which throws `GitHubRateLimitedError` on a recorded rate-limit refusal. The pause file read by
  `assertGitHubCallAllowed()` is shared on disk across processes. A dashboard boot burst after
  `pan reload` that draws a secondary rate limit is one candidate trigger. The new warn line (FR-4) records
  the real error so the next occurrence names it. This plan does not encode a conclusion.

## Decisions

1. **A read failure keeps status `miss`.** No fourth `DodRowStatus`. A new status would ripple into
   `workflows.ts` (row→step mapping), `close.ts` `renderDodGate`, the pan-close skill's
   PASS/MISS/SKIP/MISS-ACCEPTED table and the `--accept-*` semantics. An unreadable PR must block exactly
   like a miss and stay overridable with `--accept-review` / `--accept-tests`. The issue's "typed
   unknown/error row" is met by a typed error (`PullRequestReadError`) and a distinct observed text.
2. **A read failure fails closed in the verdict rows.** No strike skip, no terminal-settlement skip.
   Both of those reason from "no PR exists, so no verdict to check". A failed read cannot show that.
   This matches `readCompletedCloseOut()`'s rule ("Fail closed: a read error means we cannot confirm
   close-out").
3. **Two attempts, a 1000 ms pause.** One retry, as the issue asks. The pause is short so a persistent
   outage adds at most about one second plus the read timeouts per reader.
4. **The retry lives in a new lifecycle module, not in `fetchIssuePullRequest`.** A retry inside
   `fetchIssuePullRequest` would add latency to the dashboard PR tab and double up with the merge gate's
   own reread (`MERGEABILITY_REREAD_MS` in `cloister/merge-gate.ts`). `dod-gate.ts` is 933 lines against
   the 1000-line ceiling of `scripts/lint-file-size.sh`, so the helper goes in a sibling file, mirroring
   `src/lib/lifecycle/dod-deploy-probe.ts`.
5. **Row 4 uses the same retrying read.** Row 4 reads first (serially, before rows 1/2/5). When its retry
   succeeds, the success is cached and rows 1, 2 and 5 are served from the cache. Its existing failure text
   `forge metadata unavailable: <message>` stays; the message now carries the attempt count.
6. **Row 5 stays tolerant of a read failure.** `readMergedAt` catches `PullRequestReadError` and returns
   `undefined`, which is today's behavior. Row 5's primary evidence is the canonical state; a missing
   `mergedAt` can only turn a pass into a miss, never the reverse, so tolerance cannot wrongly pass the
   row. Making it throw would turn a `canonical state: done` pass into a miss during an outage.
7. **Only error responses are excluded from the cache.** An absent answer (`pr: null`, no `error`) and a
   found PR are still cached.
8. **Log with `console.warn`**, prefix `[dod-gate]`, on every failed attempt — including a first attempt
   whose retry succeeds. A successful retry leaves no trace in the row text, so the warn line is the only
   record of the trigger. `console.warn` is the lifecycle convention (`close-issue.ts` line 361) and goes
   to stderr in the CLI, where the operator sees it.

## Requirements

- **FR-1** — `fetchIssuePullRequest()` never stores a response that carries `error` in the PR-tab cache.
  A second call after a failed read asks the forge again. Absent and found responses are still cached.
- **FR-2** — A new helper `readPullRequestWithRetry()` reads the PR at most `PR_READ_ATTEMPTS` (2) times,
  pausing `PR_READ_PAUSE_MS` (1000 ms) between attempts. It returns the PR or `null` (absent). After the
  last failed attempt it throws `PullRequestReadError`, whose message is
  `pull request read failed on the forge after 2 attempts: <last underlying error>`.
- **FR-3** — Rows 1 and 2 report a read failure as `miss`. The observed text is the
  `PullRequestReadError` message verbatim (`pull request read failed on the forge after 2 attempts:
  <underlying error>`, what the default deps always produce), or
  `pull request read failed on the forge: <message>` for any other thrown door. It is never the absence
  text, and a read failure is never a strike or terminal-settlement `skip`.
- **FR-4** — Every failed attempt writes one `console.warn` line:
  `[dod-gate] <ISSUE-ID> pull request read failed (attempt <n> of 2): <underlying error>`.
- **FR-5** — Row 4 reads the PR through the retrying helper. On a final failure its observed text
  contains `forge metadata unavailable: pull request read failed on the forge after 2 attempts:`.
- **FR-6** — Row 5's `mergedAt` read goes through the helper and returns `undefined` on
  `PullRequestReadError` instead of throwing.
- **FR-7** — `docs/MERGE-WORKFLOW.md` and `sync-sources/skills/pan-close/SKILL.md` describe the read-failure
  text and the single retry for rows 1 and 2.
- **NFR-1** — Tests that exercise the retry pause use `vi.useFakeTimers()` and
  `vi.advanceTimersByTimeAsync()`; no test waits on a real `setTimeout` (repo rule: fake timers for
  retry/backoff tests).
- **NFR-2** — `src/lib/lifecycle/dod-gate.ts` stays at or below 1000 lines (file-size ceiling). No
  allowlist change.

### WI-2 — Retrying PR read helper with a typed error and warn lines (FR-2, FR-4, NFR-1)

**New file:** `src/lib/lifecycle/dod-pr-read.ts`, modeled on `src/lib/lifecycle/dod-deploy-probe.ts`.

```ts
/**
 * PAN-4821: DoD rows 1, 2, 4 and 5 read the issue's PR from the forge. A failed
 * read is a different fact from "no PR exists": the old reader mapped both to
 * null, so a transient forge error closed out as "no pull request found". This
 * reader retries once, logs every failed attempt (the only trace when the retry
 * succeeds), and throws a typed error so callers report the real cause.
 */
import type { IssuePrEndpointResponse, IssuePullRequestData } from '../overdeck/pull-requests.js';

export const PR_READ_ATTEMPTS = 2;
export const PR_READ_PAUSE_MS = 1000;

export class PullRequestReadError extends Error {
  readonly issueId: string;
  readonly underlying: string;

  constructor(issueId: string, underlying: string) {
    super(`pull request read failed on the forge after ${PR_READ_ATTEMPTS} attempts: ${underlying}`);
    this.name = 'PullRequestReadError';
    this.issueId = issueId;
    this.underlying = underlying;
  }
}

/** The PR, or null when the forge answered that none exists. Throws `PullRequestReadError` when every attempt fails. */
export async function readPullRequestWithRetry(
  fetchPr: (issueId: string) => Promise<IssuePrEndpointResponse>,
  issueId: string,
): Promise<IssuePullRequestData | null> {
  let lastError = 'unknown error';
  for (let attempt = 1; attempt <= PR_READ_ATTEMPTS; attempt++) {
    try {
      const response = await fetchPr(issueId);
      if (!response.error) return response.pr;
      lastError = response.error;
    } catch (error) {
      lastError = error instanceof Error ? error.message : String(error);
    }
    console.warn(
      `[dod-gate] ${issueId.toUpperCase()} pull request read failed (attempt ${attempt} of ${PR_READ_ATTEMPTS}): ${lastError}`,
    );
    if (attempt < PR_READ_ATTEMPTS) await new Promise(resolve => setTimeout(resolve, PR_READ_PAUSE_MS));
  }
  throw new PullRequestReadError(issueId, lastError);
}
```

## Repo rules that apply

- **Fake timers for retry/delay tests** — never wait on a real `setTimeout` in a test; use
  `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()`. Attach `.rejects` expectations before advancing.
- **No `execSync`** in code reachable from the dashboard server (`pull-requests.ts` is). This change adds none.
- **File-size ceiling** — `scripts/lint-file-size.sh` fails a non-test src file over 1000 lines or grown past
