# PAN-4508 — Jev settings in the dashboard: route, model and timeout, plus a per-feature usage readout

**Issue:** [PAN-4508](https://github.com/eltmon/overdeck/issues/4508) · **Builds on:** PAN-4369 (Jev client), PAN-4371 (turn-end), PAN-4372 (AC review), PAN-4400 (path-scoped config writes)

## Glossary

- **Jev** — TypeSafe AI's judgment model, called through `@typesafe-ai/sdk`. Overdeck wraps it in `src/lib/jev/`. `assess()` in `src/lib/jev/client.ts` is the only entry point that sends a request.
- **Jev feature / Jev toggle** — one of the three background-AI feature keys `jevTurnEndAssessment`, `jevAcceptanceCriteriaReview`, `jevMemoryRelevance` (`src/lib/background-ai/registry.ts`, lines 19–21). Each has an on/off switch in Settings → Background AI, stored at `background_ai.features.<key>` in `~/.overdeck/config.yaml`. All three default off.
- **Toggle on** — in this document, `background_ai.features.<key> === true` in the raw config, regardless of low-cost mode (`background_ai.cheap_mode`). Low-cost mode can be switched off at any time, so a toggle that is on must already have a model.
- **`jev:` block** — the YAML mapping in `~/.overdeck/config.yaml` with keys `base_url`, `model`, `api_key_ref`, `timeout_ms` (`YamlJevConfig`, `src/lib/config-yaml/jev.ts`, lines 1–7). Any mapping, even `{}`, marks Jev as configured (`normalizeJevConfig`).
- **Route** — which endpoint Jev requests go to. **Zen** = `base_url: https://opencode.ai/zen` (OpenCode Zen). **Direct** = no `base_url` key (the SDK uses `https://api.typesafe.ai`). **Custom** = any other `base_url` value; the UI shows it read-only and preserves it.
- **Path-scoped write door** — a config.yaml writer that parses the file with `yaml`'s `parseDocument`, edits only named paths with `setIn`/`deleteIn`, and writes the document back inside `runSettingsWriteSerialized` (`src/lib/settings-api.ts`, line ~899). Model presets use it (PAN-4400, `src/lib/model-presets/apply.ts`).
- **Whole-document settings save** — `PUT /api/settings` → `validateSettingsApi` → `saveSettingsApi` → `writeYamlConfigPreservingComments` (`src/lib/settings-api.ts`). It writes only the blocks it lists in `topLevelSections` and never touches `jev:` (verified: `grep -n jev src/lib/settings-api.ts` returns nothing).
- **Real call** — one request that `assess()` actually sent to TypeSafe: an `answered` or a `failed` result produced inside `withJevSlot`. Memo hits and `unavailable` results sent nothing and are **not** calls.
- **Usage log** — the new append-only JSONL files `~/.overdeck/jev/usage/<UTC YYYY-MM-DD>.jsonl`, one line per real call.
- **Usage readout** — the per-feature text shown under each Jev toggle: calls in the last 24 hours, last call time, last error.

## Problem

Settings → Background AI has the three Jev toggles and the TypeSafe API key, but `jev.base_url`, `jev.model` (required, no default) and `jev.timeout_ms` live only in `~/.overdeck/config.yaml`. The free `jev-1.13-free` model is limited-time, so switching to `jev-1.13` or to the direct TypeSafe route means hand-editing YAML. There is also no view of what Jev is doing: acceptance-criteria judgments go to eval-log files, turn-end labels live only in memory, and failed requests are recorded nowhere.

## Decisions

- **D1 — Dedicated path-scoped door, not the whole-document save.** Jev route/model/timeout are written by a new `src/lib/jev/settings.ts` through `PUT /api/jev/settings`, following the PAN-4400 model-presets pattern. Reasons: `routes/settings.ts` has zero headroom; the whole-document save is lossy (codebase map `concerns.md`: it copies project-layer values into the global file); and since `writeYamlConfigPreservingComments` never touches `jev:`, the two writers coexist without reverting each other. Both run inside `runSettingsWriteSerialized`, and each re-reads the file inside its turn, so concurrent saves do not lose writes.
- **D2 — Route rule.** `zen` writes `base_url: https://opencode.ai/zen`. `direct` deletes the `base_url` key. `custom` leaves `base_url` unchanged and is accepted only when the current `base_url` is already a non-Zen value. Reading: no `base_url` → `direct`; `base_url` equal to `https://opencode.ai/zen` after trimming one trailing `/` → `zen`; anything else → `custom`.
- **D3 — Model rule.** The model is free text (trimmed). A blank model deletes the `jev.model` key. A blank model is rejected (HTTP 400) while any Jev toggle is on in the current on-disk config. The UI offers suggestions through a `<datalist>`: `jev-1.13-free`, `jev-1.13` (Zen), `jev-1.13.0` (direct). Suggestions are hints only; any non-blank string is accepted.
- **D4 — Timeout rule.** `timeoutMs` must be an integer from 1 to 30000 inclusive, the same bounds `normalizeJevConfig` enforces. Validation runs **before** the write: an out-of-range `timeout_ms` on disk makes every `loadConfigSync()` caller throw, not just Jev.
- **D5 — `api_key_ref` stays YAML-only.** The issue's Proposal lists route, model and timeout. The door never writes or deletes `api_key_ref`; GET returns it read-only for display.
- **D6 — The door creates the `jev:` block on first save.** Saving from the panel when no block exists creates `jev:` with the submitted keys. The panel never saves unless the operator edits one of its fields, so an untouched Settings page never creates the block.
- **D7 — After a successful write**, the door calls `clearConfigCache()` and `resetJevMemo()`. Clearing the memo ensures that after a route or timeout change the next call goes to the network with the new values rather than answering from a result obtained on the old route (the memo key ignores `base_url`).
- **D8 — Toggle-on validation in the whole-document save, with grandfathering.** `validateSettingsApi` rejects a save that turns a Jev toggle from off to on while the current `jev.model` is blank. A toggle that is already on with a blank model on disk produces a **warning**, not an error, so an operator already in that state can still save unrelated settings (theme, keys). Client-side, the toggle click is blocked before any save, because the autosave pipeline calls `setFormData(next)` before the PUT and a server-only 400 would leave the switch visually on.
- **D9 — Validation logic lives in a pure leaf module** `src/lib/jev/settings-validation.ts` (type-only imports). `settings-api.ts` imports it, and `src/lib/jev/settings.ts` imports both it and `runSettingsWriteSerialized` from `settings-api.ts`. A leaf avoids an import cycle (`npm run lint` runs `lint:circular`).
- **D10 — Usage log stores no message text.** Each line stores `ts`, `feature`, `outcome` (`answered` | `failed`), `reason` (the closed `JevFailureReason`, failures only), `status` (HTTP status when the error is an `APIError`, else omitted), `model`, `durationMs`. It never stores the key, the state, the questions, the answers, or `err.message`. SDK error messages can echo response bodies, and the client header promises never to log the error object.
- **D11 — Usage aggregation window.** `calls24h` counts lines with `ts` within the last 24 hours. `lastCallAt` and `lastError` scan the day files for the last 7 UTC days (today plus 6 earlier). `lastError` is the most recent `failed` line in that window, even if a later call succeeded; the UI shows its time so the operator can judge how old it is. Missing files are skipped. Reads use `fs/promises` (no sync I/O in server-reachable code).
- **D12 — Writes never fail the call.** `appendJevUsage` swallows every error, like `appendAcceptanceCriteriaEvalLog` in `src/lib/jev/eval-log.ts`. `assess()` calls it fire-and-forget (`void`).
- **D13 — One route file** `src/dashboard/server/routes/jev.ts` holds `GET /api/jev/settings`, `PUT /api/jev/settings` and `GET /api/jev/usage`. PUT calls `rejectUnsafeDashboardMutationRequest(request)` first, as the model-presets routes do.
- **D14 — Frontend state.** `SettingsPage.tsx` owns two queries (`['jev-settings']`, `['jev-usage']`) through a new hook file `hooks/useJevSettings.ts` and passes plain props down, so `BackgroundAiSection` and `JevSettingsPanel` stay presentational and testable without a `QueryClientProvider`. The `jev` prop on `BackgroundAiSection` is optional; when it is absent the panel and readouts do not render, which keeps the existing `BackgroundAiSection.test.tsx` cases valid.

## Requirements

- **FR-1** `GET /api/jev/settings` returns `{ configured, route, baseUrl, model, timeoutMs, apiKeyRef }` read from the raw global `jev:` block. Defaults when unset: `route: 'direct'`, `baseUrl: null`, `model: null`, `timeoutMs: 2000`, `apiKeyRef: 'TYPESAFE_API_KEY'`.
- **FR-2** `PUT /api/jev/settings` with `{ route, model, timeoutMs }` validates per D2–D4, writes only `jev.base_url`, `jev.model`, `jev.timeout_ms` per D1/D2/D6, preserves every other key and comment in config.yaml, and returns the FR-1 shape. Invalid input returns HTTP 400 `{ error, errors }` and leaves the file byte-identical.
- **FR-3** After a successful PUT, the next `assess()` call in the dashboard process uses the new model, base URL and timeout without a restart (D7).
- **FR-4** Turning a Jev toggle on while the model is blank shows a validation message in Settings and does not save; the server rejects the same transition with HTTP 400 (D8).
- **FR-5** Every real call appends one usage line (D10, D12); memo hits and `unavailable` results append nothing.
- **FR-6** `GET /api/jev/usage` returns `{ hours: 24, features: { <each of the 3 Jev keys>: { calls24h, lastCallAt, lastError } } }` with all three keys always present (D11).
- **FR-7** Settings → Background AI shows, under each Jev toggle, the calls in the last 24 hours, the last call time and the last error.
- **FR-8** The Settings panel offers a route select, a model field and a timeout field, autosaved (route immediately, text and number fields debounced by `AUTOSAVE_DEBOUNCE_MS` = 600 ms), with inline validation errors.
- **FR-9** `configuration/jev.mdx` describes the Settings controls and the usage readout.
- **NFR-1** No growth of `src/dashboard/server/routes/settings.ts`; at most 10 added lines in `src/lib/settings-api.ts`.
- **NFR-2** No synchronous filesystem or child-process calls in any new server-reachable code.
- **NFR-3** The usage log and the API responses never contain the API key, request state, answers, or SDK error message text.

## API contract (shared by backend and frontend items)

```ts
// GET /api/jev/settings  and the 200 body of PUT /api/jev/settings
type JevRoute = 'zen' | 'direct' | 'custom';
interface JevSettingsView {
  configured: boolean;      // a jev: block exists in the global config.yaml
  route: JevRoute;
  baseUrl: string | null;   // raw jev.base_url, null when absent
  model: string | null;     // raw jev.model trimmed, null when absent or blank
  timeoutMs: number;        // raw jev.timeout_ms, 2000 when absent
  apiKeyRef: string;        // raw jev.api_key_ref, 'TYPESAFE_API_KEY' when absent (read-only)
}
// PUT /api/jev/settings body
interface JevSettingsInput { route: JevRoute; model: string; timeoutMs: number }
// PUT 400 body
interface JevSettingsError { error: string; errors: string[] }   // error = errors.join('; ')

// GET /api/jev/usage
interface JevUsageView {
  hours: 24;
  features: Record<'jevTurnEndAssessment' | 'jevAcceptanceCriteriaReview' | 'jevMemoryRelevance', {
    calls24h: number;
    lastCallAt: string | null;                                     // ISO timestamp
    lastError: { at: string; reason: string; status?: number } | null;
  }>;
}
```

Exact validation error strings (tests assert these):

- `jev.model is required while a Jev feature is on`
- `jev.timeout_ms must be an integer between 1 and 30000`
- `route must be zen, direct, or custom`
- `route custom keeps an existing custom base_url; none is set`
- Toggle error (whole-document save): `Set a Jev model in Settings → Background AI before turning on <feature key>`
- Toggle warning (grandfathered): `<feature key> is on but jev.model is not set; Jev makes no requests until a model is set`

## Intersecting repo rules (restated)

- Fake timers for any debounce/delay test: `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()`; never real `setTimeout` waits.
- No `execSync` or other blocking calls in dashboard-server-reachable code; use `fs/promises`.
- File-size guard: never grow `routes/settings.ts`; never raise an allowlist cap. Extract a module instead.
- New HTTP routes need a no-loss matrix row, or CI goes red.
- Import `loadConfigSync`/`clearConfigCache`/`getGlobalConfigPath` from `../config-yaml/load.js` in new lib modules, not from `../config-yaml.js`, to avoid tripping module mocks and `lint:circular`.
- Never run the full `npm test` locally; run only the touched test files.
- Dashboard UI follows the pan-style-guide skill: no pill badges, muted text for metadata, no decorative color; errors use the existing `text-destructive` token.
- Commit per item with an `Item: <item-id>` trailer.
