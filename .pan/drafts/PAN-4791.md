# PAN-4791 — CodeRabbit follow-ups on #4789: bound the Fly cleanup promise, add volume cleanup to the recovery text

**Issue:** [PAN-4791](https://github.com/eltmon/overdeck/issues/4791) · **Parent:** PAN-4777, PR [#4789](https://github.com/eltmon/overdeck/pull/4789) (merged 2026-11-02 04:52 UTC)

## Glossary

- **`createVm`** — `FlyProvider.createVm(name)` in `src/lib/remote/fly-provider.ts` (line 181). It ensures the app, adopts or creates the machine, on the durable tier creates or reuses the `<name>-workspace` volume *before* the machine, and waits up to 300 s for the machine to reach `started`. A failed wait rethrows with the text `Check: fly machines list -a ${this.config.app}`.
- **Rollback** — the PAN-4777 `try { … } catch (error) { throw await rollBackVm(…) }` block in `createRemoteWorkspace` (`src/lib/remote-workspace.ts`). It starts *after* `const vmInfo = await Effect.runPromise(fly.createVm(vmName));` (line 165), so it covers only failures after `createVm` resolves.
- **`rollBackVm`** — `src/lib/remote-workspace.ts` line 71. Calls `fly.deleteVm(vmName)`; if that rejects, returns an error that names the machine and the hand-destroy command.
- **`deleteVm`** — `FlyProvider.deleteVm(name)` (`fly-provider.ts` line 291). Destroys the machine first, then best-effort deletes the `<name>-workspace` volume, swallowing any volume error.
- **Resiliency tier** — `'ephemeral' | 'durable'`, read with `FlyProvider.getResiliencyTier()` (`fly-provider.ts` line 115). Only the durable tier attaches a `<vmName>-workspace` volume at `/workspace`.
- **Recovery text** — the error message `rollBackVm` returns when the delete fails.

## Problem

CodeRabbit left two Minor findings on #4789 that the merge train landed without answering. Both are verified against `main` at `5b9726f07a8`.

**Finding 1 — comment `4438995645` on `docs/fly-provider.md` line 67.** The doc promises that any failure after the machine is created deletes the machine. That is false for one window: `createVm` calls `api.createMachine(...)` and then `api.waitForState(..., 'started', 300)`. If the wait fails, `createVm` rejects, so `createRemoteWorkspace` never reaches the rollback `try`. The machine stays. On the durable tier, the `<vmName>-workspace` volume (created before `createMachine`) also stays, and it stays even if `createMachine` itself fails. The doc repeats the over-broad promise at lines 458–460 ("any failure after the machine is created … deletes the machine").

Grep anchors in `docs/fly-provider.md`:

- line 67: `   - If any step after the machine is created fails, delete the machine before reporting the error`
- lines 458–460: `- **Creation fails after the machine exists** — any failure after the machine is` / `created (credential sync, clone, branch checkout, Claude Code setup, skills copy,` / `compose) deletes the machine before the error is shown.`

The same doc also states the startup wait as 120 s in three places (line 62 `Wait up to 120 s for it to reach \`started\``, line 257 `up to 120 seconds.`, line 447 `the 120 s wait timed out`). The code waits 300 s for both a fresh and an adopted machine (`fly-provider.ts` `waitForState(this.config.app, machine.id, 'started', 300)` and `waitForState(this.config.app, existing.id, 'started', 300)`). New text that describes the startup-wait failure next to a wrong figure would be a fresh defect, so this PRD corrects the figure in those three lines.

**Finding 2 — comment `4438995647` on `src/lib/remote-workspace.ts` line 86.** When `rollBackVm`'s delete fails, `deleteVm` rejected at `resolveVm` or `destroyMachine`, which both run before the volume step. So on the durable tier the volume still exists, attached to the machine. The recovery text tells the operator only to destroy the machine:

```ts
// src/lib/remote-workspace.ts lines 84–88 (current)
    return new Error(
      `${reason}. The VM ${vmName} (machine ${machineId}, app ${appName}) could not be deleted: ${deleteReason}. ` +
        `Destroy it by hand: fly machines destroy ${machineId} -a ${appName} --force`,
      { cause: error },
    );
```

A volume left behind keeps billing with nothing in Overdeck pointing at it.

## Requirements

The boundary is `createVm` resolving, not the machine reaching `started`: `createVm` still calls `api.getMachine` after a successful wait, and a failure there also skips rollback.

It names `fly machines list -a <app>` to find it, and gives two recovery paths: re-run `pan workspace create --remote <issue>` (which adopts and starts the leftover machine) or destroy it by hand. It never suggests `pan workspace start`, which refuses an issue that has no saved metadata.

## Decisions (made here, not deferred)

1. **Narrow the doc; do not add cleanup inside `createVm`.** The issue asks to "limit the cleanup promise". Making `createVm` delete a machine that failed its startup wait is a behavior change with its own risks (the machine may still be pulling the image and start seconds later). Out of scope; see Non-goals.
2. **Recovery text is tier-conditional.** `rollBackVm` already holds `fly`; it calls `fly.getResiliencyTier()` and appends the volume step only when the result is `'durable'`. Ephemeral machines have no volume, so telling those operators to hunt one is noise.
3. **Order in the recovery text: machine first, then volume.** An attached volume cannot be destroyed while its machine exists.
4. **Use `--yes` on `fly volumes destroy`.** Verified with `fly volumes destroy --help`: `-y, --yes  Accept all confirmations`. `fly volumes list -a <app>` is verified with `fly volumes list --help`.
5. **Thread replies cite the fix commit and PAN-4791, not the PR URL.** `pan task done` needs every item complete before `pan done` opens the PR, so the PR URL does not exist while items run. GitHub cross-links the issue to the PR once `pan done` opens it. Each thread maps to exactly one work item, so each item ends with its own reply.
6. **Fix the 120 s figure only in `docs/fly-provider.md`.** No other doc states the Fly startup wait (grep for `120 s` / `120 seconds` across `docs/`, `configuration/`, `reference/`).

## Non-goals

- Changing `createVm` to delete a machine (or a durable volume) when its startup wait or `createMachine` fails.
- Changing `deleteVm`'s silent swallow of a volume-delete error (machine destroyed, volume delete fails, operator never told).
- Writing a user-facing page for the durable resiliency tier (none exists today).
- Any change to `src/lib/remote/fly-provider.ts`, `src/lib/remote/fly-api.ts`, or the Fly machine provisioning path in `src/lib/anywhere/fly/`.

## Critique response

Round 1 critique (`.pan/drafts/PAN-4791-critique.md`). All three blocking findings were verified against the code and accepted; the draft changed for each.

### Started is not the rollback boundary

Accepted. `createVm` calls `api.getMachine` after a successful `waitForState` (adopted path), so reaching `started` is not where rollback begins; `createVm` resolving is. FR-1 now names that boundary, and WI-1 steps 2 and 5 phrase it for operators as "a setup step after the create step" (credential sync onward), never "after `started`".

### Startup recovery command requires missing metadata

Accepted. `startCommand` in `src/cli/commands/workspace-remote.ts` loads workspace metadata and fails with `No remote workspace found` when it is absent, and `createRemoteWorkspace` saves metadata only after setup succeeds. WI-1 step 4 now recommends re-running `pan workspace create --remote <issue>`, which adopts and starts a leftover machine by name (`createVm`'s get-or-create path), or `fly machines destroy` by hand. FR-2 and AC-2a forbid the `pan workspace start` instruction there.

### Durable volume deletion is not guaranteed

Accepted. `deleteVm` swallows `listVolumes` and `deleteVolume` errors, and `rollBackVm` then reports only the original error. Changing that stays a non-goal, so the doc no longer promises the volume is deleted: WI-1 steps 2 and 5 say rollback *tries* to delete it, and the troubleshooting bullet tells durable operators to check `fly volumes list -a <app>` after any failed creation (FR-2a, AC-3).

### Zero-match grep has a failing status

Accepted (sharpens-framing). AC-1 and the WI-1 verification now use `! grep -Eq '120 s|120 seconds' docs/fly-provider.md`, which exits 0 on the correct document.
