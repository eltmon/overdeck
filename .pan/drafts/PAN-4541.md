# PAN-4541 — Boot preflight reads `from "custom"` inside a comment and blocks every `pan reload`

**Issue:** [PAN-4541](https://github.com/eltmon/overdeck/issues/4541)
**Status:** planned (auto mode)

## Glossary

- **Boot preflight** — the check `pan reload` runs on a freshly built dashboard
  generation before it moves traffic onto it. It calls
  `dashboardServerBootFailure(serverPath)` in
  `src/lib/deploy/dashboard-bundle-integrity.ts`, which calls
  `unresolvedBundleImports(serverPath)` in `src/lib/bundle-imports.ts`. A
  non-null result aborts the reload with "… — old dashboard left running".
- **Generation** — a deployment root under
  `~/.overdeck/deployments/dashboard/.pan-reload-generation-{a,b}`. `pan reload`
  builds `origin/main` into the idle generation, preflights it, then switches.
- **Bare specifier** — an import source that is a package name (`effect`,
  `@lydell/node-pty`), not a relative path, absolute path, or `node:` builtin.
  Only bare specifiers are resolved by the preflight; the filter is
  `PACKAGE_SPECIFIER_PATTERN` in `src/lib/bundle-imports.ts`.
- **es-module-lexer** — Guy Bedford's ES module import/export lexer (the one
  Vite uses). It tokenizes JavaScript, so it never reports text inside
  comments, string literals, template literals, or regex literals. Version
  2.3.2 is already in `bun.lock` (a transitive dependency of `vitest`) but is
  **not** declared in any `package.json`, so `src/` cannot import it today.
- **Inlined (bundled) dependency** — a package tsdown copies into the output
  chunk, so the emitted `dist/*.js` has no `import … from "<package>"` for it
  and needs nothing in `node_modules` at runtime.
- **Old CLI / new CLI** — the `pan` binary that runs `pan reload` is the build
  that is *already installed*, not the build being deployed. The fix in this
  issue protects deploys only once the CLI running `pan reload` contains it.

## Problem

Every `pan reload` of `main` since `66777e339e4` (PAN-4508) fails:

> Deployment cannot resolve custom from …/.pan-reload-generation-a/dist/dashboard/server.js — the dashboard server would die on ERR_MODULE_NOT_FOUND at boot. Run `bun install` in the deployment root, then reload again — old dashboard left running

No module named `custom` exists. The preflight scans the bundle with a regex
that also matches text inside comments.

### Verified root cause

1. `src/lib/bundle-imports.ts` lines 15–16:
   ```ts
   /** `from "x"`, `import "x"`, and `import("x")` in bundled ESM output. */
   const IMPORT_SOURCE_PATTERN = /\b(?:from|import)\s*\(?\s*(["'])([^"'\n]+)\1/g;
   ```
   The loop at lines 33–42 (`for (const match of source.matchAll(IMPORT_SOURCE_PATTERN))`)
   treats every match as an import.
2. `src/lib/jev/settings-validation.ts` line 9 (added by PAN-4508):
   ```ts
   /** The canonical OpenCode Zen gateway base_url; distinguishes the "zen" route from "custom". */
   ```
   Rolldown keeps JSDoc comments. Verified on the live generation-b bundle
   (`906978556d7`): `dist/dashboard/server.js` contains 1014 lines starting
   with `/**`. So this comment lands in `server.js`, the regex reads
   `from "custom"`, and `custom` is reported as an unresolvable bare import.
3. The same hazard is latent in the scanner's own header: the JSDoc on line 15
   (`` `from "x"` ``) survives into the `agents-*.js` chunk of the live build
   (verified: `grep -c 'from "x"'` on that chunk returns 1). It does not trip
   today only because the preflight scans the entry file `server.js` and not
   chunks. Any chunking change that moves `bundle-imports.ts` into `server.js`
   would make the old scanner report `x`.

### Probe evidence for the chosen lexer

Run in planning against the live generation-b build with
es-module-lexer 2.3.2 (`initSync()` then `parse()`):

- `dist/dashboard/server.js` (3.1 MB): lexed in 14 ms, 314 import records.
  The set of specifiers is **identical** to the regex's set on that
  (pre-PAN-4508) bundle — no regex-only and no lexer-only entries.
- `dist/pty-supervisor.js`: identical sets (`@lydell/node-pty`).
- Synthetic source
  ``/* x from "custom" */ const s = "import(\"y\")"; const t = `from "z"`; const r = /from "w"/; import a from "real"; export * from "re-exp"; const d = import("dyn"); import.meta.url; import(variable);``
  returns exactly `real`, `re-exp`, `dyn`, plus two records with `n === undefined`
  (`import.meta` and `import(variable)`).
- `initSync()` is synchronous and idempotent (`if (E) return;`), so the
  function stays synchronous.

## Requirements

- **FR-1** — `src/lib/jev/settings-validation.ts` contains no `from "…"`,
  `import "…"`, or `import("…")` text in comments. Behavior is unchanged.
- **FR-2** — `unresolvedBundleImports(scriptPath)` reports only specifiers of
  real ESM syntax: static `import … from`, side-effect `import "…"`,
  `export … from`, and dynamic `import("literal")`. Text inside comments,
  string literals, template literals, and regex literals is never reported.
- **FR-3** — A real `import x from "really-missing-pkg"` that does not resolve
  from the bundle's location is still reported (PAN-3264 / PAN-3172
  protection preserved).
- **FR-4** — The exported signature `unresolvedBundleImports(scriptPath: string): string[]`
  and every caller (`dashboard-bundle-integrity.ts`, `pty-supervisor-locate.ts`,
  `reload.ts`, `restart.ts`) are unchanged.
- **FR-5** — Docs state that the boot preflight resolves real import
  specifiers only.
- **NFR-1** — The lexer is inlined into every `dist/` bundle that contains
  `bundle-imports.ts`. No `dist/**/*.js` file has a bare `es-module-lexer`
  import. The check whose job is to detect an incomplete `node_modules` must
  not itself need a `node_modules` entry.
- **NFR-2** — No new runtime (`dependencies`) entry in any `package.json`.
- **NFR-3** — No comment or string added by this change contains
  `from "…"`, `import "…"`, or `import("…")` with a quoted package-shaped
  word. The *old* CLI still scans the *new* `server.js` with the regex on the
  first reload after merge (see Decision D3).

## Decisions

- **D1 — Library: es-module-lexer, declared as a root devDependency and
  inlined.** None of `es-module-lexer`, `acorn`, or `oxc` is declared in any
  `package.json`. `typescript` is a devDependency and ~9 MB, too large to
  inline into the CLI; `scripts/lint-dist-externals.mjs` uses
  `ts.preProcessFile` only because it is a build-time script. The issue's rule
  ("do not add a new runtime dependency if an existing parser covers it")
  therefore permits adding one; we go further and add **no runtime
  dependency**: declare `es-module-lexer` in the root `devDependencies` at
  `^2.3.2` (the version already in `bun.lock`) and list it in `deps.alwaysBundle`
  in both tsdown configs. Why inlined and not a `dependencies` entry: the
  dashboard bundle decides externals from `src/dashboard/server/package.json`
  while the CLI bundle uses the root `package.json`; an external lexer would
  make the preflight (and `resolvePtySupervisorScriptPath()` in the running
  server) fail to load in exactly the incomplete-`node_modules` state it
  exists to detect. `npm run lint:dist-externals` is the guard: a devDependency
  left external fails it.
- **D2 — Specifier filter.** Keep each import record whose `n` is a string
  (drops `import.meta` and non-literal `import(expr)`), then apply the existing
  `PACKAGE_SPECIFIER_PATTERN` unchanged. Keep the existing
  `MODULE_NOT_FOUND` / `ERR_MODULE_NOT_FOUND` handling unchanged.
- **D3 — Bootstrap order.** The `pan reload` that deploys this merge runs the
  currently installed CLI with the old regex. Only WI-1 (the comment reword)
  unblocks that reload; WI-2 protects reloads only after the CLI running
  `pan reload` is rebuilt with it. Therefore the post-merge deploy
  verification belongs to WI-1's outcome, and WI-2 must not add text that the
  old regex would misread (NFR-3).
- **D4 — Lexer failure.** `parse()` throws a `ParseError` on input it cannot
  tokenize. Do not catch it. A rolldown-emitted bundle that fails to lex is a
  packaging defect that Node would also fail to load. In `reload.ts` the throw
  lands in the existing try/catch and becomes "… — old dashboard left
  running" (fail closed). This matches today's contract, where `readFileSync`
  can already throw.
- **D5 — Post-merge deploy verification is not a work-agent item.** The work
  agent cannot run `pan reload` of `origin/main` before its own PR merges.
  The flywheel runs `pan reload` after an overdeck merge lands with green CI
  (docs/THE-CUT.md D1). The work agent proves the equivalent pre-merge: the
  branch's own `npm run build` output passes both the old regex and the new
  lexer with an empty result.
- **D6 — No source-reading test for FR-1.** The test lint rejects new tests
  that read repository source files. FR-1 is checked by a grep verify command
  and by review of the diff.
