# PAN-4591: Semgrep in-session for agents — `semgrep` MCP server, post-edit scan hook, `semgrep` skill

**Issue:** [PAN-4591](https://github.com/eltmon/overdeck/issues/4591) (child of #4585, phase 1 shipped)
**Status:** planned 2026-11-16 (auto mode, high effort)
**Sibling filed during planning:** [#5434](https://github.com/eltmon/overdeck/issues/5434) — the Codex
`apply_patch` edit hook (see "Deferred: Codex edit hook").

## Scope of this PRD

Phase 1 (#4585) shipped the `security.semgrep.enabled` key, the managed Semgrep CLI at
`~/.overdeck/bin/semgrep` (pinned `1.180.0`) and the `pan doctor` rows. This PRD adds what the
agent sees while it works:

1. A stdio `semgrep` MCP server for **work** agents and the **review `security`** convoy lane, on
   every harness that already receives launch MCP servers (Claude Code, Codex, the ACP host).
2. A post-edit scan hook for **Claude Code work agents** that scans only the edited file and returns
   findings to the model.
3. A `semgrep` skill that teaches triage, justified `nosemgrep`, custom rules with `semgrep --test`,
   and the MCP tools.
4. Two config keys, `security.semgrep.mcp` and `security.semgrep.edit_hook`, and the harness matrix
   in the docs.

The Codex edit hook is **not** in this plan. It is #5434 (reasons below).

## Glossary

- **Managed launcher** — `~/.overdeck/bin/semgrep`, a symlink to
  `~/.overdeck/tools/semgrep/bin/semgrep` created by phase 1 (`src/lib/semgrep/install.ts`,
  `managedSemgrepPath()`, `semgrepToolsDir()`). "Managed" means `lstat` says symlink **and**
  `readlink` equals that exact target. Anything else at that path is **foreign**.
- **Launch MCP file** — `<agent dir>/overdeck-mcp.json`, written by `prepareClaudeOverdeckMcp`
  (`src/lib/mcp/agent-injection.ts`). Claude Code loads it with `--mcp-config=`; the ACP host reads
  the same file and passes its stdio servers to `session/new` (PAN-4934).
- **Codex server map** — the `[mcp_servers.<name>]` tables `initCodexHome()`
  (`src/lib/runtimes/codex.ts`) writes from the map `prepareCodexOverdeckMcp` returns.
- **Launch settings step** — `pan skills launch-settings` (`skillsLaunchSettingsCommand`,
  `src/cli/commands/skills.ts`), which every local Claude Code and Codex launcher runs before the
  harness starts. For Claude it prints one JSON object that the launcher passes as
  `claude --settings "$PAN_SKILL_SETTINGS"`; that JSON can carry `skillOverrides`, `env`, `hooks`
  and `permissions`. SageOx already injects per-launch hooks this way (PAN-4852).
- **Convoy lane** — one of the four review sub-roles (`security`, `correctness`, `performance`,
  `requirements`). A lane is a separate agent spawned by `spawnRun` (`src/lib/agents/spawn.ts`)
  with `role: 'review'` and `options.subRole`; its state file stores `reviewSubRole`
  (`src/lib/agents/agent-state-read.ts`, line 203). The convoy dispatcher
  (`src/lib/cloister/review-convoy.ts`, near line 193: `const reviewerAgent =
  reviewerAgentId(opts.issueId, opts.subRole)`) first tries `resumeAgent(reviewerAgent, prompt)`
  (state already holds `reviewSubRole`), and otherwise calls `spawnRun` with
  `spawnOptions = { workspace, subRole: opts.subRole, … }`. Lanes have **no** role definition file
  (`roleAgentDefinitionPath('review', subRole)` returns `null`), so role frontmatter cannot give
  them an MCP server.
- **Eligible MCP launch** — an agent launch (not a conversation) whose role is `work`, or whose
  role is `review` with sub-role `security`.
- **Eligible hook session** — a Claude Code agent session with `OVERDECK_AGENT_ID` set whose
  `state.json` `role` is `work`.
- **Quiet env** — the env every in-session Semgrep process gets (NFR-2 below).

## Probes run while planning (Semgrep 1.180.0, Claude Code 2.1.325, 2026-11-16)

All probes used a throwaway install (`uv tool install semgrep==1.180.0` into the planning
scratchpad) and a throwaway git repo with a file containing `subprocess.call(cmd, shell=True)` and
`eval(x)`.

1. **`semgrep mcp -k post-tool-cli-scan -a claude` is unusable.** Fed a Claude `PostToolUse`
   payload for that file, it printed `No SEMGREP_APP_TOKEN found, please login to Semgrep to use this
   hook.` and exited `2` after 3 s. It also printed `Tracing initialized with trace ID: …
   (https://app.datadoghq.com/apm/trace/…)` — it starts OpenTelemetry tracing to Semgrep unless
   `SEMGREP_MCP_DISABLE_TRACING=true` (source: `semgrep/mcp/utilities/tracing.py`,
   `is_tracing_disabled`). `-a` accepts only `claude|cursor|windsurf` (no Codex). Every `-k` mode
   except `inject-secure-defaults*` needs a token. So the hook is Overdeck's own script (D2).
2. **`semgrep mcp` (stdio) starts without a token.** `initialize` answers in 1.7 s (`serverInfo`
   `Semgrep 1.29.0`). The server sends `roots/list` requests to the client; a client that does not
   answer them hangs every tool call (Claude Code answers them). Default tools:
   `semgrep_rule_schema`, `get_supported_languages`, `semgrep_findings`,
   `semgrep_scan_with_custom_rule`, `semgrep_scan`, `get_abstract_syntax_tree`,
   `semgrep_scan_supply_chain`.
3. **With `SEMGREP_SEND_METRICS=off`, `semgrep_scan` always fails:** `Cannot run scan with auto
   config when metrics are off. Please allow metrics or run with a specific config.` Its input schema
   takes only `code_files`, so no config can be passed (`server.py`, `get_semgrep_scan_args`).
   `semgrep_scan_with_custom_rule` works (0.4 s, found the `eval` with a one-line rule),
   `get_abstract_syntax_tree` works (0.3 s), `semgrep_rule_schema` works (0.5 s; it fetches the schema
   from `semgrep.dev` and sends no code). `semgrep_findings` and `semgrep_scan_supply_chain` call the
   Semgrep AppSec Platform and need a token (#4593 territory).
4. **Tool-disable env vars work.** With `SEMGREP_SCAN_DISABLED=true`,
   `SEMGREP_FINDINGS_DISABLED=true`, `SEMGREP_SCAN_SUPPLY_CHAIN_DISABLED=true` the server lists
   exactly `semgrep_rule_schema`, `get_supported_languages`, `semgrep_scan_with_custom_rule`,
   `get_abstract_syntax_tree`; calling `semgrep_scan` answers `Unknown tool: semgrep_scan`.
5. **A one-file CLI scan takes about 2 s.** `semgrep scan --config p/default --json --quiet
   --metrics=off bad.py` took 2.13 s and 1.78 s (registry fetch included) and reported
   `python.lang.security.audit.subprocess-shell-true.subprocess-shell-true` (line 3) and
   `python.lang.security.audit.eval-detected.eval-detected` (line 5); a clean file took 1.81 s.
6. **Semgrep writes `~/.semgrep/` unless told otherwise.** The scan updated
   `~/.semgrep/settings.yml` and `~/.semgrep/semgrep.log`. With
   `SEMGREP_SETTINGS_FILE=<dir>/settings.yml` and `SEMGREP_LOG_FILE=<dir>/semgrep.log` the same scan
   wrote only those two files and left `~/.semgrep/*` mtimes unchanged. The API token lookup order is
   `SEMGREP_APP_TOKEN` env, then `api_token` in the settings file (`semgrep/app/auth.py`, `get_token`),
   so an Overdeck-owned settings file plus removing `SEMGREP_APP_TOKEN` keeps a logged-in user's token
   out of agent sessions.
7. **A per-launch Claude hook reaches the model.** `claude -p --settings <file>` with
   `{"hooks":{"PostToolUse":[{"matcher":"Edit|Write|MultiEdit","hooks":[{"type":"command","command":"<script>","timeout":30}]}]}}`
   where the script prints
   `{"hookSpecificOutput":{"hookEventName":"PostToolUse","additionalContext":"SEMGREP-MARKER-7731: …"}}`:
   after one `Write`, the model quoted `SEMGREP-MARKER-7731: …` verbatim as hook context.
8. **One idle `semgrep mcp` process uses about 100 MB RSS** (`ps` RSS 102960 KiB, Python).
9. **The exact WI-2 server definition works through Claude Code.** `claude -p --strict-mcp-config
   --mcp-config=<file> --allowedTools=mcp__semgrep` with
   `{"command":"/usr/bin/env","args":["-u","SEMGREP_APP_TOKEN","-u","SEMGREP_RULES","<semgrep>","mcp"],"env":{…quiet env, settings/log paths, tracing off, three tools disabled…}}`
   and `SEMGREP_APP_TOKEN=fake` in the parent env: the model saw exactly the four tools,
   `get_supported_languages` returned 65 entries, and `semgrep_scan_with_custom_rule` with an
   `eval(...)` rule reported line 5 with no tool errors. Claude Code answers `roots/list`.
10. **`roots/list` needs an answer, not support.** The server sends `roots/list` even to a client that
    declares no `roots` capability. A client that replies with a JSON-RPC error (`-32601 Method not
    found`) gets normal tool results; only a client that never replies hangs (probe 2).
11. **Codex 0.169.0 runs the server.** A scratch `CODEX_HOME` whose `config.toml` has
    `[mcp_servers.semgrep]` with the same command, args and env plus
    `default_tools_approval_mode = "approve"`; `codex exec` logged
    `mcp: semgrep/get_supported_languages (completed)` and
    `mcp: semgrep/semgrep_scan_with_custom_rule (completed)` and answered `LANGS=65 LINES=5`.
12. **OpenCode 1.18.31's MCP client runs the server.** `opencode mcp list` showed `semgrep connected`
    and `opencode run --model opencode/beam-free` called `semgrep_get_supported_languages` and
    answered `LANGS=65`.
13. **A second `--allowedTools=` flag adds to the first.** With user settings excluded
    (`--setting-sources project`) and `--permission-mode default`: `--allowedTools=Read,Grep,mcp__overdeck`
    alone → the model reported "Claude requested permissions to use
    mcp__semgrep__get_supported_languages, but you haven't granted it yet"; the same plus
    `--allowedTools=mcp__semgrep` → the call ran (`OK:65`).

## Requirements

IDs FR-5 and FR-9 come from #4585 (retired there, owned here). New IDs continue from FR-11.

- **FR-5** When `security.semgrep.enabled` and `security.semgrep.mcp` are both `true`, every
  eligible MCP launch on Claude Code, Codex, or the ACP host gets a stdio MCP server named
  `semgrep` that runs the managed launcher with `mcp`. No other launch gets it: not plan, test,
  ship, flywheel, worker or conversation launches, not the `correctness`, `performance` or
  `requirements` lanes, and not the review synthesis parent.
- **FR-9** `sync-sources/skills/semgrep/SKILL.md` ships. While `security.semgrep.enabled` is
  `false`, every Claude Code and Codex launch hides it (`skillOverrides: { semgrep: 'off' }`,
  Codex `[[skills.config]] enabled=false`).
- **FR-12** When `security.semgrep.enabled` and `security.semgrep.edit_hook` are both `true`, every
  local Claude Code **agent** launch (not a conversation launch) gets a per-launch `PostToolUse`
  hook on `Edit|Write|MultiEdit` through the launch settings JSON. In an eligible hook session the
  hook scans only the edited file and, when Semgrep reports findings, returns them to the model as
  `additionalContext`. It prints nothing when the file is clean, when the session is not eligible,
  and on any error.
- **FR-13** `security.semgrep.mcp` and `security.semgrep.edit_hook` are booleans, default `false`,
  validated like `enabled` (a non-boolean throws at config load). The project layer still cannot
  set them (FR-11, unchanged).
- **FR-14** A launch on a harness that receives no launch MCP servers (pi, ohmypi, kimi-code native,
  muse, prime-agent) logs the existing "does not provision MCP" warning with `semgrep` in its server
  list when the launch would otherwise get the server. The docs carry a harness matrix.
- **FR-15** The MCP server is injected only when the managed launcher is managed (Glossary). A
  missing or foreign launcher skips the server with one warning that names the fix (`pan sync`).
  The edit hook applies the same ownership rule before it runs Semgrep and stays silent otherwise.
- **NFR-2 (extended from #4585)** Every Semgrep process this PRD starts runs with
  `SEMGREP_ENABLE_VERSION_CHECK=0`, `SEMGREP_SEND_METRICS=off`,
  `SEMGREP_SETTINGS_FILE=<OVERDECK_HOME>/tools/semgrep/settings.yml`,
  `SEMGREP_LOG_FILE=<OVERDECK_HOME>/tools/semgrep/semgrep.log`, and without `SEMGREP_APP_TOKEN` or
  `SEMGREP_RULES` in its environment. The MCP server also gets `SEMGREP_MCP_DISABLE_TRACING=true`.
- **NFR-3** Async only in server-reachable code: the MCP resolver uses `fs/promises`; the hook uses
  promisified `execFile` with a timeout. No `execSync`.
- **NFR-8 Fail open.** Injection never throws (a resolver error logs one warning and the launch
  proceeds without `semgrep`). The launch settings step never fails because of Semgrep. The hook
  always exits `0`.
- **NFR-9 Hook budget.** Scan timeout 30 s (`execFile` `timeout`), Claude hook `timeout: 40`. Skip
  files over 1 MiB, files under `node_modules/`, `.git/` or `dist/`, and files whose extension is in
  the skip list (WI-4). List at most 10 findings.
- **NFR-10** No test runs the real Semgrep binary, the network, or a real Claude session. Inject
  `execFile`, file reads, config and platform through deps objects. No `skipIf`/`.only`.
- **NFR-11** The MCP server exposes only tools that work without a Semgrep login and with metrics
  off: `semgrep_scan`, `semgrep_findings` and `semgrep_scan_supply_chain` are disabled (probes 3–4).
- **NFR-12** Resource cost is documented: about 100 MB per eligible agent with `mcp` on, about 2 s
  per edit with `edit_hook` on.

## Decisions (made in this document)

- **D1 The Claude edit hook is injected per launch, not added to `OVERDECK_HOOK_REGISTRATIONS`.**
  The issue text names `OVERDECK_HOOK_REGISTRATIONS`. That list writes a permanent entry into
  `~/.claude/settings.json`, which fires for every Claude session on the machine (the operator's own
  sessions too) and would "register into a harness" while Semgrep is off, against #4585 FR-1. The
  launch settings step already injects per-launch hooks for SageOx, so the hook exists only in
  sessions launched while the feature is on. The issue's intent (toggle-gated, managed sessions
  only, scan only the edited file) is kept. Recorded in `plan.autoDecisions`.
- **D2 Overdeck's own hook script, not `semgrep mcp -k post-tool-cli-scan`.** Probe 1: it needs a
  Semgrep login and starts Datadog tracing.
- **D3 Disable `semgrep_scan`, `semgrep_findings`, `semgrep_scan_supply_chain`** (NFR-11). Registry
  scans go through the CLI by absolute path; the skill teaches that.
- **D4 `mcp` and `edit_hook` default to `false`.** Each costs memory or edit latency (NFR-12), and
  phase-1 adopters who only turned on the install must not see new behavior on upgrade.
- **D5 Roles.** MCP: `work` and the review `security` lane (issue text). Edit hook: `work` only,
  checked inside the script from `state.json`, because only work agents edit source. Conversation
  launches get neither (the launch settings step sees `--conversation`; the injection owner has
  `agentKind: 'conversation'` and `role: 'conversation'`).
- **D6 The Codex edit hook moves to #5434.** `src/lib/sageox/codex-hooks.ts` writes and deletes
  `<CODEX_HOME>/hooks.json` as a whole with index-keyed trust hashes, so a second hook source needs a
  composer; and nobody has verified that Codex 0.169.0 fires `PostToolUse` for `apply_patch` or which
  output reaches the model. Codex agents still get the MCP server here.
- **D7 ACP gets the MCP server for free.** The issue says ACP gets no MCP; that is stale since
  PAN-4934: `src/lib/acp/host.ts` (`readAcpMcpServers(args.mcpConfig)`, near line 877) passes the
  launch MCP file's stdio servers to `session/new`. Adding `semgrep` to that file reaches opencode,
  grok and kimi-over-ACP. ACP agents do not run Claude hooks, so they get no edit hook (documented).
  ohmypi stays out of scope (issue).
- **D8 Hook rules:** `--config p/default`, plus `--config <cwd>/.semgrep.yml` when that file exists
  and `--config <cwd>/.semgrep/` when that directory exists, where `<cwd>` is the hook payload's
  `cwd`. When #4590 adds a `configs` key, it should switch the hook to read it (hazard H3).
- **D9 The skill is static text; managed launches hide it while off.** Unmanaged sessions (the
  operator's own `claude`) see every synced skill; the skill's first step tells the agent to check
  that the managed launcher exists and to stop if it does not. `pan sync` also copies skills to
  `~/.agents/skills`, which harnesses without a launch settings step (pi, kimi-code, muse, …) read
  with no per-launch hiding; those sessions see the skill too and the same first step applies.
  Carve-out from #4585 FR-1: a skill file runs nothing and registers no tool.
- **D10 The hook script is copied by `pan sync` but never registered globally.** It joins
  `HOOK_SCRIPT_NAMES` (copied to `~/.overdeck/bin/`) so its path is stable across deployments; it is
  **not** added to `OVERDECK_HOOK_REGISTRATIONS`. Carve-out from FR-1: a copied file runs nothing.
- **D11 Sub-role plumbing.** `OverdeckMcpLaunchOwner` gains `subRole?: string`. `spawnRun` passes
  `options.subRole` on fresh spawns. Resume and recovery paths (`resume.ts` via
  `buildAgentLaunchConfig`, `recovery.ts`, `messaging.ts`) do not pass it; for a `review` agent
  owner without `subRole`, injection reads `getAgentState(agentId)?.reviewSubRole` from
  `agent-state-read.js` (state exists on resume; on a fresh spawn it may not, which is why
  `spawnRun` passes it explicitly).
- **D12 Scrub through `/usr/bin/env -u`.** Claude's MCP `env` block can add variables but cannot
  remove inherited ones, so the server command is
  `/usr/bin/env -u SEMGREP_APP_TOKEN -u SEMGREP_RULES <managed launcher> mcp`. `/usr/bin/env` with
  `-u` exists on Linux and macOS; Windows is unsupported (#4585 NFR-6).
- **D13 Overdeck-owned Semgrep state.** `SEMGREP_SETTINGS_FILE` and `SEMGREP_LOG_FILE` point under
  `~/.overdeck/tools/semgrep/` (probe 6), so agent scans never read the user's login token and never
  write `~/.semgrep/`.
- **D14 Docker workspaces and remote launches get nothing.** The resolver returns `null` when
  `OVERDECK_DOCKER_WORKSPACE=1` or `PAN_DOCKER=1` (the same rule as `overdeckMcpEnabledFor` in
  `src/lib/mcp/overdeck-mcp-gate.ts`). Remote (Fly) launches (`src/lib/remote/remote-agents.ts`)
  never call `prepareClaudeOverdeckMcp` and the launch settings step skips `spawnMode: 'remote'`
  (`appliesTo` in `src/lib/skill-overrides/launcher-lines.ts`), so no change is needed there.
- **D15 Hook feedback uses `additionalContext`, not `decision: "block"`.** Findings are advice; the
  #4590 `sast` gate is the enforcement point. Probe 7 shows `additionalContext` reaches the model.

## Repo rules that apply (restated)

- **No `execSync`** in anything reachable from the dashboard server. `agent-injection.ts` and the
  new `src/lib/semgrep/in-session.ts` are reachable from spawn routes. Use `fs/promises` and
  promisified `execFile`.
- **No test runs real Semgrep, the network, or Claude.** CI has no Semgrep. Inject deps. Do not add
  `skipIf`/`.only` (the test-skip gate fails them). Do not write tests that read source files and
  grep them (the lint gate rejects source-reading tests).
- **File-size ratchet** (`scripts/lint-file-size.sh` compares files above 1000 lines with their
  `origin/main` count): `src/lib/agents/spawn.ts` is 1088 lines (cap 1089) — edit the two existing
  call lines in place, add no lines. `src/cli/commands/__tests__/skills.test.ts` is 988 lines — add
  at most 6 lines there and put new launch-settings tests in a new file. Never raise an allowlist row.
- **Import cycles:** import `getAgentState` from `../agents/agent-state-read.js`, never
  `agent-state.js` (lint:circular).
- **Hook bundles are committed.** After editing `sync-sources/hooks/semgrep-edit-hook.ts`, run
  `npm run build:scripts` and commit `sync-sources/hooks/semgrep-edit-hook.js` (and the `.d.ts` if
  tsdown emits one). The pre-push guard requires the rebuilt `.js`. If the build also rewrites
  `record-cost-event.js` or `gh-issue-trailer-hook.js`, restore those two with
  `git restore sync-sources/hooks/record-cost-event.js sync-sources/hooks/gh-issue-trailer-hook.js`.
- **`npm run build:scripts` is not part of `npm run build`** (`scripts/build-post-cli.mjs`, PAN-2699).
- **Changelog:** one file `changelog.d/pan-4591.md` (lowercase), never `changelog.mdx`.
- **Conventional commits**, lower-case subject ≤100 chars, `Item: <item-id>` trailer per item.
  Gates before `pan done`: `npm run typecheck`, `npm run lint`, `npx vitest run <touched tests>`.

2. **Running the CLI.** `~/.overdeck/bin` is not on `PATH`. Define and use:
   ```bash
   SG="${OVERDECK_HOME:-$HOME/.overdeck}/bin/semgrep"
   sg() { env -u SEMGREP_APP_TOKEN -u SEMGREP_RULES SEMGREP_ENABLE_VERSION_CHECK=0 SEMGREP_SEND_METRICS=off \
     SEMGREP_SETTINGS_FILE="${OVERDECK_HOME:-$HOME/.overdeck}/tools/semgrep/settings.yml" \
     SEMGREP_LOG_FILE="${OVERDECK_HOME:-$HOME/.overdeck}/tools/semgrep/semgrep.log" "$SG" "$@"; }
   sg scan --config p/default --json --quiet --metrics=off <files>
   ```
   Never `--config auto` (it needs metrics). Scan files you changed, not the whole repo.
3. **Triage a finding.** Read the rule id, the line and the message; decide true or false positive
   by reading the data flow, not the rule name. A true positive: fix the code, then rescan the file.
4. **Suppressing a false positive.** Only on the exact line, only naming the rule:
   `# nosemgrep: <rule-id> -- <one-line reason>` (use the file's comment syntax). Never a bare
   `nosemgrep`, never a file-level or `.semgrepignore` exclusion to make a finding go away; reviewers
   and the `sast` gate treat unjustified suppressions as defects.
5. **Custom rules.** Put project rules in `.semgrep.yml` or `.semgrep/` at the repo root (the hook
   loads both). Write a test file next to the rule with `# ruleid: <id>` above lines that must match
   and `# ok: <id>` above lines that must not, then run `sg --test <rules dir>`; it must pass before
   you commit the rule.
6. **MCP tools** (work agents and the review security lane, when the operator enabled
   `security.semgrep.mcp`): `semgrep_scan_with_custom_rule` (try a rule against code before writing
   it to disk), `semgrep_rule_schema`, `get_abstract_syntax_tree` (see how Semgrep parses a snippet),
   `get_supported_languages`. `semgrep_scan` is intentionally absent; use the CLI.
7. **Hook findings.** A message starting `Semgrep found` after an edit comes from the post-edit hook;
   handle it with sections 3–4 before moving on.
