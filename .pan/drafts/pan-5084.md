# PAN-5084 — Telemetry: CI runs, test homes and throwaway VMs report as new installs

**Issue:** [PAN-5084](https://github.com/eltmon/overdeck/issues/5084)
**Status:** planned (auto mode, 2026-11-05)

## Glossary

- **Install id** — the random UUIDv4 in `${OVERDECK_HOME}/telemetry-id` (file name `telemetry-id`, constant `INSTALL_ID_FILE` in `src/lib/telemetry/install-id.ts`). It is the PostHog `distinct_id` of every Node event and the `install_id` super property of browser events. A fresh `OVERDECK_HOME` mints a fresh id. (The issue body calls the file `install-id`; the real name is `telemetry-id`.)
- **Ghost install** — an install id that appears on exactly one day. 5,818 of 5,824 ids in the last 30 days are ghosts: CI jobs, agent test stacks and throwaway VMs.
- **Configured state** — `telemetry.enabled` in `~/.overdeck/config.yaml` (default `true`), read with `loadConfigSync()`.
- **Effective state** — whether telemetry actually sends. Today it is `resolveTelemetryEnabled()` in `src/lib/telemetry/config.ts`: the env var `OVERDECK_TELEMETRY=0|false` forces off, else the configured state.
- **Process block** — `telemetryBlockedForProcess()` in `src/lib/telemetry/service.ts` line 51: off under Vitest (`VITEST`) or `NODE_ENV=test`. This PRD does not change it.
- **Automatic exclusion** — new: an environment where Overdeck turns telemetry off without the user asking, because the run is almost certainly not a real install. Two kinds: `ci` (the `CI` env var is set) and `temporary_home` (the Overdeck home lies under a temp directory).
- **Forced on** — new: `OVERDECK_TELEMETRY=1` or `OVERDECK_TELEMETRY=true`. It cancels automatic exclusions only. It never overrides `telemetry.enabled: false` and never overrides `OVERDECK_TELEMETRY=0`.
- **Install kind** — new closed-enum property `install_kind` stamped on every Node and browser event: `user`, `remote_vm`, `dev_checkout`, `container`.
- **Install-kind marker** — new file `${OVERDECK_HOME}/install-kind` whose trimmed content is one install-kind value. Fly provisioning writes `remote_vm` into it.
- **Dev checkout** — Overdeck running from a source tree, detected by the existing `isDevMode()` (`src/lib/paths.ts` line 301: `existsSync(join(packageRoot, 'src'))`). The operator's own `pan reload` dashboard runs from `~/.overdeck/deployments/dashboard/.pan-reload-generation-{a,b}`, a git worktree with `src/`, so it reports `dev_checkout`. That is the intended result: the operator's own machines are filtered out of adoption dashboards.
- **Drift test** — `tests/unit/telemetry-docs.test.ts`: it parses the event table and the domain table in `docs/TELEMETRY.md` and requires exact equality with `TELEMETRY_EVENT_CATALOG` and `TELEMETRY_PROPERTY_DOMAINS` in `packages/contracts/src/telemetry.ts`.

## Problem

PostHog project 514675 (last 30 days, queried 2026-11-05): 5,824 distinct ids on `server_boot` / `instance_heartbeat` / `cli_command_run`, only 6 active on two or more days. Every CI job that boots `dist/dashboard/server.js` or runs the CLI (`.github/workflows/ci.yml` jobs `test-e2e` line 268 and the clean-install smoke line 476, `windows-smoke.yml`), every agent test stack with an isolated home, and every throwaway Fly VM reports as a new install. Only `release.yml` line 130 sets `OVERDECK_TELEMETRY: '0'`, and only for one step. So the dashboards cannot show real adoption.

## Proposal (summary)

1. Add two automatic exclusions to the one effective-state door, `resolveTelemetryEnabled()`: `CI` set, and an Overdeck home under a temp directory. `OVERDECK_TELEMETRY=1` cancels them. Because the Settings API and the browser read the same door, the browser SDK and the Settings page follow automatically.
2. Set `OVERDECK_TELEMETRY: '0'` at workflow level in `ci.yml` and `windows-smoke.yml`, inside the WSL probe script, and in every test harness that spawns a server or CLI.
3. Stamp `install_kind` on every Node event and every browser event so the remaining traffic can be filtered in PostHog.
4. Show the real reason in Settings when telemetry is forced off.
5. Document all of it.

## Requirements

### Functional

- **FR-1** — When `OVERDECK_TELEMETRY` is unset and `CI` is set to a value other than empty, `0` or `false` (case-insensitive), `resolveTelemetryEnabled()` returns `false` and no Node or browser telemetry is sent.
- **FR-2** — When the Overdeck home (`getOverdeckHome()`) is inside `os.tmpdir()`, inside `/tmp` (POSIX only), or inside `~/.overdeck/tmp` (`join(getCanonicalOverdeckHome(), 'tmp')`), and `OVERDECK_TELEMETRY` is not forced on, `resolveTelemetryEnabled()` returns `false`. "Inside" includes equal, uses `path.relative` containment (never `startsWith`), and checks both the resolved and the `realpathSync` form of each path when the path exists.
- **FR-3** — `OVERDECK_TELEMETRY=1` or `true` (case-insensitive, trimmed) cancels FR-1 and FR-2. It does not override `telemetry.enabled: false`.
- **FR-4** — Precedence is fixed (see "Decision: precedence"). `resolveTelemetryState()` returns the effective state and, when off, the reason: `environment`, `config`, `ci` or `temporary_home`.
- **FR-5** — `GET /api/settings` returns `telemetry.disabledBy` (one of the four reasons, omitted when enabled) and `telemetry.installKind`. The save response computes `effectiveEnabled` and `disabledBy` through the same door as the load response.
- **FR-6** — Every Node event (`AnalyticsService.capture`) and every Node exception (`AnalyticsService.captureException`) carries `install_kind` with one of `user`, `remote_vm`, `dev_checkout`, `container`.
- **FR-7** — The browser registers `install_kind` as a PostHog super property from `telemetry.installKind`, so every browser event carries it.
- **FR-8** — Install kind resolves in this order: marker file value (when it is one of the four values) → `dev_checkout` when `isDevMode()` → `container` when `/.dockerenv` or `/run/.containerenv` exists → `user`.
- **FR-9** — `provisionFlyMachine()` writes `remote_vm\n` to `${overdeckHome}/install-kind` on the VM, before `pan serve` starts.
- **FR-10** — `ci.yml` and `windows-smoke.yml` set `OVERDECK_TELEMETRY: '0'` in the top-level `env:`; `scripts/windows-smoke/probe-wsl.sh` exports `OVERDECK_TELEMETRY=0`.
- **FR-11** — The Playwright isolated-dashboard fixture, the two Playwright specs that start their own throwaway dashboard (`system-health-pill.spec.ts`, `health-page.spec.ts`), the two-dashboard test helper and the three `scripts/anywhere/*-smoke.mjs` scripts set `OVERDECK_TELEMETRY: '0'` in the env of every server and CLI they spawn.
- **FR-12** — `install_kind` is a domain in `TELEMETRY_PROPERTY_DOMAINS` and a row in the `docs/TELEMETRY.md` domain table; the drift test passes.
- **FR-13** — The Settings → Telemetry status line names the actual reason when telemetry is configured on but forced off.
- **FR-14** — `docs/TELEMETRY.md` and `configuration/telemetry.mdx` describe the automatic exclusions, the `OVERDECK_TELEMETRY=1` override, the precedence, and `install_kind`.

### Non-functional

- **NFR-1** — The new filesystem probes never throw to a caller. Every new fs probe is wrapped; a failure falls back (exclusion check: not excluded; install kind: next rule). NFR-1 does not change config-read failure behavior: `loadConfigSync()` may still throw out of `resolveTelemetryState()` exactly as it throws out of `resolveTelemetryEnabled()` today. `AnalyticsService.getClient()` and `synchronizeAnalyticsServices()` already catch it and fail closed; the Settings API path keeps today's behavior.
- **NFR-2** — `install_kind` is resolved once per process and cached (like `cachedOverdeckVersion` in `service.ts`); captures do no repeated fs probes.
- **NFR-3** — No new value in any event is free-form: `install_kind` comes only from the closed domain.
- **NFR-4** — `src/lib/settings-api.ts` (1503 lines, cap 1508 in `scripts/file-size-allowlist.txt`, last row wins) must not grow. The plan shrinks it.
- **NFR-5** — `service.ts` keeps importing only `resolveTelemetryEnabled` from `./config.js`. Three suites (`service.test.ts`, `flag-door.test.ts`, `github-telemetry-privacy.test.ts`) mock `config.js` with a factory that exports only that function; any other import from it would be `undefined` there.

## Decisions (made in this doc)

### Decision: precedence

Evaluate top to bottom; the first matching row wins.

| # | Condition | Result | `disabledBy` |
|---|---|---|---|
| 1 | `OVERDECK_TELEMETRY` is `0` or `false` | off | `environment` |
| 2 | `telemetry.enabled: false` in config | off | `config` |
| 3 | `OVERDECK_TELEMETRY` is `1` or `true` | on | — |
| 4 | `CI` set (non-empty, not `0`/`false`) | off | `ci` |
| 5 | Overdeck home inside a temp dir (FR-2) | off | `temporary_home` |
| 6 | otherwise | on | — |

Why: an explicit user opt-out (rows 1-2) is never overridden by a flag that exists for test fixtures. Row 3 must beat both rows 4 and 5, because `tests/unit/lib/telemetry/fatal-process.test.ts` lines 46-61 spawn a child with a `tmpdir()` home, `OVERDECK_TELEMETRY: '1'`, and (on GitHub) an inherited `CI=true`, and expect capture.

### Decision: where the gate lives

The new exclusions go in `resolveTelemetryEnabled()` (via a new `resolveTelemetryState()` in the same file), not in `telemetryBlockedForProcess()`. `telemetryBlockedForProcess` is private to `service.ts`; the Settings API (`src/lib/settings-api-telemetry.ts` `telemetrySettingsFromConfig`) and the browser (`initTelemetry` reads `effectiveEnabled`) only see `resolveTelemetryEnabled`. A gate in `service.ts` would leave the browser SDK sending from a CI dashboard.

### Decision: detection is a separate pure module

The CI/temp-home check lives in a new `src/lib/telemetry/environment.ts` with injectable inputs. Reasons: (a) it gets direct unit tests without touching real env; (b) `config.test.ts` and `settings-telemetry.test.ts` run the real `resolveTelemetryEnabled()` under the Vitest setup, which sets `OVERDECK_HOME` to a temp dir for every test (`tests/setup/overdeck-home.ts` line 12) and, on GitHub, `CI=true`. Those suites mock `environment.js` to return "no exclusion" by default so their existing assertions still hold, and add cases for the new reasons.

### Decision: install kind sources

- `remote_vm` comes only from the marker file, which Overdeck's Anywhere Fly provisioning writes. No `FLY_*` env sniffing: a user who self-hosts Overdeck on their own Fly app is a real user.
- The marker accepts any of the four values (one domain check). This also lets an operator tag a lab machine by hand; it costs no extra code.
- `dev_checkout` reuses `isDevMode()`; no second "is this a checkout" test.
- `container` checks `/.dockerenv` (Docker) and `/run/.containerenv` (Podman) only.
- Remote work agents under `src/lib/remote/` (fly-provider) run harnesses, not `pan`, on the VM, so they send no Overdeck telemetry and need no tag.

### Decision: `/tmp` is included on POSIX

Agent shells set `TMPDIR` to `~/.overdeck/tmp/...`, so `os.tmpdir()` is not `/tmp` there, but agents have created test stacks with literal `/tmp/...` homes. On non-Windows platforms `/tmp` is checked in addition to `os.tmpdir()`.

### Decision: WSL needs its own export

GitHub step env does not cross into the `wsl-bash` shell of `Vampire/setup-wsl` (no `WSLENV` is set in `windows-smoke.yml`), so neither the workflow `env:` nor `CI` reaches `probe-wsl.sh`. The script exports `OVERDECK_TELEMETRY=0` itself, next to `export NO_COLOR=1` (line 46).

### Decision: one issue with a size justification

The projected surface is about 30 files across 10 path prefixes, mostly one-line env additions plus their tests. Splitting the env wiring from the gate ships a half-fix (CI keeps minting ids from paths the gate does not see, or tagged traffic keeps arriving untagged), and the post-deploy PostHog filter needs both halves. `plan.metadata.sizeJustification` records this.

### WI-2 — install-kind resolver (FR-8, NFR-1, NFR-2)

New file `src/lib/telemetry/install-kind.ts`; new test `tests/unit/lib/telemetry/install-kind.test.ts`.

```ts
import { existsSync, readFileSync } from 'node:fs';
import { join } from 'node:path';
import { TELEMETRY_INSTALL_KINDS, type TelemetryInstallKind } from '@overdeck/contracts';
import { getOverdeckHome, isDevMode } from '../paths.js';

/** PAN-5084: `${OVERDECK_HOME}/install-kind`; Anywhere Fly provisioning writes `remote_vm`. */
export const INSTALL_KIND_FILENAME = 'install-kind';

export interface InstallKindProbe {
  overdeckHome: string;
  exists: (path: string) => boolean;
  readFile: (path: string) => string;
  isDevCheckout: () => boolean;
}

function isInstallKind(value: string): value is TelemetryInstallKind {
  return (TELEMETRY_INSTALL_KINDS as readonly string[]).includes(value);
}

export function resolveInstallKind(probe: InstallKindProbe = defaultProbe()): TelemetryInstallKind {
  try {
    const marker = probe.readFile(join(probe.overdeckHome, INSTALL_KIND_FILENAME)).trim();
    if (isInstallKind(marker)) return marker;
  } catch { /* no marker */ }
  try { if (probe.isDevCheckout()) return 'dev_checkout'; } catch { /* fall through */ }
  try {
    if (probe.exists('/.dockerenv') || probe.exists('/run/.containerenv')) return 'container';
  } catch { /* fall through */ }
  return 'user';
}

let cachedInstallKind: TelemetryInstallKind | undefined;
/** The process's install kind, resolved once (NFR-2). */
export function getInstallKind(): TelemetryInstallKind {
  return cachedInstallKind ??= resolveInstallKind();
}
```

`defaultProbe()` returns `{ overdeckHome: getOverdeckHome(), exists: existsSync, readFile: (p) => readFileSync(p, 'utf8'), isDevCheckout: isDevMode }`. Match the codebase's style; the snippet is the contract, not a mandate on formatting.

Tests (injected probe, no real fs): marker `remote_vm\n` → `remote_vm` even when `isDevCheckout` is true; marker `bogus` → ignored, falls to next rule; no marker + dev checkout → `dev_checkout`; no marker, not dev, `/.dockerenv` exists → `container`; `/run/.containerenv` → `container`; nothing → `user`; `readFile` and `exists` throwing non-ENOENT errors → still returns a value (no throw).

### WI-6 — `resolveTelemetryState()` with the precedence table (FR-3, FR-4)

After (whole file):

```ts
import { loadConfigSync } from '../config-yaml.js';
import { detectTelemetryAutoExclusion, telemetryEnvironmentForcesOn } from './environment.js';

export type TelemetryDisabledReason = 'environment' | 'config' | 'ci' | 'temporary_home';

export interface TelemetryState {
  enabled: boolean;
  disabledBy?: TelemetryDisabledReason;
}

export function telemetryEnvironmentForcesOff(): boolean {
  const envValue = process.env.OVERDECK_TELEMETRY?.trim().toLowerCase();
  return envValue === '0' || envValue === 'false';
}

/** PAN-5084 precedence: env off > config off > env on > CI > temporary home > on. */
export function resolveTelemetryState(configuredEnabled?: boolean): TelemetryState {
  if (telemetryEnvironmentForcesOff()) return { enabled: false, disabledBy: 'environment' };
  // Read YAML only after the env check, so a broken config under OVERDECK_TELEMETRY=0 still resolves off.
  const enabledInConfig = configuredEnabled ?? loadConfigSync().config.telemetry?.enabled !== false;
  if (!enabledInConfig) return { enabled: false, disabledBy: 'config' };
  if (telemetryEnvironmentForcesOn()) return { enabled: true };
  const excluded = detectTelemetryAutoExclusion();
  return excluded ? { enabled: false, disabledBy: excluded } : { enabled: true };
}

export function resolveTelemetryEnabled(): boolean {
  return resolveTelemetryState().enabled;
}
```
