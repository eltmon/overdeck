# PAN-5423: Make the "Answer delivered to …" toast clickable

**Issue:** [PAN-5423](https://github.com/eltmon/overdeck/issues/5423)

## Glossary

- **Toast** — a transient notification drawn by the `sonner` library (v1.7.4). `toast.success(message, options)` accepts `options.action = { label, onClick }`, which renders a button inside the toast.
- **Answer dialog** — the dashboard modals that answer a pending input: the AskUserQuestion dialog (`AskUserQuestionDialog`) and the plan approval dialog (`PlanApprovalDialog`). Both are driven by the hook `usePendingInputDialogs`.
- **Subject** — what a dialog answers. Either an **agent** (`kind: 'agent'`, `id` = agent id, usually with an `issueId`) or a **conversation** (`kind: 'conv'`, `id` = conversation name, possibly `@<env>/<name>` for a linked machine).
- **Success toast** — the toast a mutation shows after the server accepted an answer: "Answer delivered to X", "Approval sent to X", "Plan approved for X", "Plan feedback sent to X".
- **Decision door** — `navigateToDecisionSubject()` in `src/dashboard/frontend/src/lib/navigateToDecision.ts`: the one function that sends the operator to a subject. It resolves the path with `decisionSubjectPath()` (conversation → `/conv/<name>` or `/conv/@<env>/<name>`; agent → `/issues/<issueId>`, or `null` when the agent has no issue), then does `history.pushState` plus a synthetic `popstate` that `App` already listens to.

## Problem

After the operator answers a pending question from the dashboard dialog, a toast says "Answer delivered to <title>". The toast has no click target, so clicking it does nothing. The operator expects it to open the conversation or issue that received the answer. The sibling success toasts (Codex approval, plan approve / request changes) have the same gap.

## Decisions

1. **Click target = an "Open" action button.** `toast.success(message, { action: { label: 'Open', onClick } })`. This matches the existing toasts in this code (`'Answer'` in `usePermissionNotifications.ts:17`, `'Open terminal'` at line 147 of the hook) and the issue's first suggested fix. Sonner 1.7.4 has no whole-toast `onClick` option; a custom `toast.custom` JSX toast would break the success styling and is not worth it.
2. **One helper owns the toast call.** A new module `src/dashboard/frontend/src/lib/deliveredToast.ts` exports `showDeliveredToast(message, target)`, which calls `toast.success` with the action. The hook calls it at all four success sites. This makes the wiring testable by mocking `sonner` without rendering the 664-line hook, and keeps `navigateToDecision.ts` free of a `sonner` import.
3. **Navigation goes through the decision door.** The helper maps `kind: 'conv'` → `{ source: 'conversation', id }` and `kind: 'agent'` → `{ source: 'agent', id, issueId }`, checks `decisionSubjectPath(...)`, and its `onClick` calls `navigateToDecisionSubject(...)`. No hand-built paths, no `window.location` assignment. Linked-machine ids (`@env/name`) work because the door already handles them.
4. **Agent with no `issueId` ⇒ plain toast, no action.** `decisionSubjectPath` returns `null`; the helper calls `toast.success(message)` with no options object, exactly as today.
5. **Conversation with an `issueId` ⇒ open the conversation**, not the issue: the conversation is what received the answer.
6. **`issueId` is a local optional field on the mutation variables**, next to `label`. `PendingAnswerTarget` stays unchanged (it describes the HTTP request; `buildPendingAnswerRequest` destructures only its own fields, so an extra field is ignored).
7. **Scope = four success toasts:** "Answer delivered to", "Approval sent to" (Codex), "Plan approved for", "Plan feedback sent to". The channel-permission toasts ("Allowed <agentId> to continue" / "Denied permission request for …", around line 582) are out of scope: the issue names only the Codex approval and plan toasts as siblings.
8. **Error toasts stay unchanged.** A failed delivery has nothing to open.
9. **Message text stays unchanged.** Only an options argument is added.

## Requirements

- **FR-2** — After an AskUserQuestion answer is accepted for an **agent** subject that has an `issueId`, the toast has an `Open` action that navigates to `/issues/<issueId>`.
- **FR-3** — An agent subject without an `issueId` produces the same toast with no action (no broken button).

- **FR-5** — Both plan-action success toasts ("Plan approved for …", "Plan feedback sent to …") have an `Open` action: conversation → `/conv/<name>`, agent → `/issues/<issueId>`.
- **FR-6** — A changelog entry tells users the notification now opens the subject.

### WI-1 — `showDeliveredToast` helper and its test (FR-1..FR-5 foundation, NFR-1, NFR-2)

Files: new `src/dashboard/frontend/src/lib/deliveredToast.ts`; new `src/dashboard/frontend/src/lib/__tests__/deliveredToast.test.ts`; `scripts/frontend-test-subset.txt`.

1. Create `deliveredToast.ts`:
   ```ts
   /**
    * showDeliveredToast — the success toast after the dashboard delivered an
    * answer, approval or plan action (PAN-5423). It carries an "Open" action
    * that sends the operator to the subject that received it, through the
    * decision door: a conversation opens /conv/<name>, an agent opens its
    * issue. An agent with no issue gets the plain toast.
    */
   import { toast } from 'sonner';
   import { decisionSubjectPath, navigateToDecisionSubject, type DecisionSubjectTarget } from './navigateToDecision';

   export interface DeliveredSubject {
     kind: 'agent' | 'conv';
     id: string;
     issueId?: string | null;
   }

   export function showDeliveredToast(message: string, subject: DeliveredSubject): void {
     const target: DecisionSubjectTarget = subject.kind === 'conv'
       ? { id: subject.id, source: 'conversation' }
       : { id: subject.id, source: 'agent', issueId: subject.issueId ?? undefined };
     if (decisionSubjectPath(target) === null) {
       toast.success(message);
       return;
     }
     toast.success(message, { action: { label: 'Open', onClick: () => navigateToDecisionSubject(target) } });
   }
   ```
