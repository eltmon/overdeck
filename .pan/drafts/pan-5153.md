# PAN-5153: GitHub organizations: per-repository identity and visible owners

**Issue:** https://github.com/eltmon/overdeck/issues/5153
**Status:** draft written 2026-11-11 by the operator's conversation, verified against main at `3235e7fa459`. The planner verifies the references again, then lowers this document into the xBRIEF without re-deciding anything.

Overdeck holds one GitHub App installation and treats it as valid for every repository. This change makes Overdeck pick the acting identity per repository: the App's bot where the App is installed, the signed-in `gh` user everywhere else. It also shows the operator which GitHub owner (user or organization) each project belongs to and which identity acts there.

This document is the implementation brief. Every decision is made here. Where a step needs a live check, it is marked **Implementation checkpoint** and has a fallback.

## Glossary

- **Owner:** the first segment of a project's `github_repo: owner/repo` in `~/.overdeck/projects.yaml`. An owner is a GitHub user account or a GitHub organization.
- **GitHub App (the App):** the App whose credentials are in `~/.overdeck/github-app/` (`app-id`, `private-key.pem`, `installation-id`, `app-slug`). `scripts/create-github-app.mjs` creates it.
- **Installation:** one account (user or organization) on which the App is installed. An installation covers all of that account's repositories or a selected list of them. Each installation has a numeric id.
- **Home installation:** the installation whose id is in `~/.overdeck/github-app/installation-id`. It is the only installation Overdeck knows today.
- **Installation token:** a token that lasts about one hour, minted for one installation with the App's JWT. It works only on repositories that installation covers.
- **App JWT:** a short-lived token signed with the App's private key. It authenticates as the App itself, not as an installation.
- **Covered repository:** a repository on which the App is installed, through any installation.
- **Bot:** the App's GitHub login, `<app-slug>[bot]` (for example `overdeck-agent[bot]`).
- **gh user:** the account the `gh` CLI is signed in as (`gh api user --jq .login`).
- **Identity:** who acts on a repository. `app` means the bot through an installation token. `user` means the gh user. `none` means neither is available.
- **App branch / gh branch:** many functions have two code paths: one that calls the GitHub REST API with an installation token, and one that runs the `gh` CLI as the gh user.
- **Repo notes:** `~/.overdeck/github-quota/repo-notes.json`, written by `src/lib/github-quota/repo-notes.ts`. It records repositories where an App call returned 404, for 6 hours.
- **PAT:** the personal access token in `tracker_keys.github` or `GITHUB_TOKEN`. The issue poller and `GitHubClient` use it. This change does not touch it.

## Why

The operator started a job that uses a GitHub organization and asked whether Overdeck knows which organization to post to.

Overdeck does know the target: every project carries `github_repo: owner/repo`. What is wrong is the identity. Verified on the operator's machine:

- The App is owned by `eltmon` and has one installation: the `eltmon` user account, with selected repositories.
- `GET /repos/mindyournow/myn-cli/installation` with the App JWT returns 404. `mindyournow/myn-cli` is a registered project.
- `~/.overdeck/github-quota/repo-notes.json` already lists `eltmon/krux` as not covered. So coverage differs between repositories of the same owner.

## Requirements

- **FR-1 (installation per repository):** for a repository `owner/repo`, Overdeck finds the App installation that covers it by asking GitHub (`GET /repos/{owner}/{repo}/installation` with the App JWT). It does not store an installation id per repository on disk.
- **FR-2 (token per repository):** every App REST call for a path under `/repos/{owner}/{repo}/` uses a token minted for the installation that covers that repository. Tokens are memoized per installation until 5 minutes before they expire.
- **FR-3 (identity per repository):** `resolveRepoIdentity(owner, repo)` returns `app` when the repository is covered, `user` when it is not covered and `gh` is signed in, and `none` otherwise.
- **FR-4 (branch per repository):** every branch point that chooses between the App branch and the gh branch chooses per repository. A machine with the App configured takes the gh branch for an uncovered repository.
- **FR-5 (spawn writes no dead credentials):** agent spawn sets the HTTPS remote, the bot git identity and the credential file only for a covered repository. For any other repository it leaves the remote, the git user and the credentials unchanged and logs the identity it resolved. Spawn never refuses because of the identity.
- **FR-6 (verdicts and checks):** the review verdict uses an installation token only for a covered repository and otherwise posts as the gh user. The verification check run and the commit statuses are skipped (as they are today without the App) for an uncovered repository.
- **FR-7 (explicit repository):** the two `gh` call sites in F6 and F7 pass the issue's own repository with `--repo`.
- **FR-8 (identities endpoint):** `GET /api/github/identities` returns, for every registered project with a `github_repo`, its owner, its repository, the identity mode, the acting login and a one-sentence reason, grouped by owner, plus the gh user's login and the App's slug.
- **FR-9 (doctor):** `pan doctor` prints one row per owner. The row is `ok` when every project of that owner has a working identity. It is `warn`, with the fix, when the gh user cannot push to a repository, when the organization requires SAML authorization for the token, when `gh` is not signed in, or when a repository's `credential.helper` still points at Overdeck's bot credential file although the App does not cover it. Running `pan doctor` re-checks coverage immediately instead of waiting for the 6-hour repo note to expire.
- **FR-10 (sidebar owners):** when the registered projects belong to two or more owners, the sidebar project list is grouped under one header per owner. Each group can be collapsed, and the collapsed groups are remembered in the browser. With fewer than two owners the list renders as it does today.
- **FR-11 (identity chip):** the Command Deck project header shows `owner · acting login` for the selected project, with the reason as its tooltip.
- **FR-12 (settings):** the Settings page has a read-only "GitHub identities" section: the gh user, the App slug, and a table with one row per project (owner, project, repository, acts as, why).
- **FR-13 (docs):** the docs named in W12 describe per-repository identity, how to cover an organization, and where to see the identity.
- **NFR-1 (no behavior change on failure):** when the installation lookup fails for a reason other than 404 (network, 5xx, timeout), the code behaves as it does today: it takes the App branch with the home installation's token.
- **NFR-2 (machine-wide checks unchanged):** `isGitHubAppConfigured()`, `getMergeBackendStatus()`, `verifyAppCanMerge()`, `getAppStatus()` and the quota sampler keep their meaning and keep using the home installation. `installation-id` stays required.
- **NFR-3 (cost):** one installation lookup per repository per process per 6 hours. The lookup uses the App JWT and is not written to the quota ledger.
- **NFR-4 (file sizes):** no row in `scripts/file-size-allowlist.txt` is raised. See "Repo rules".
- **NFR-5 (tests):** no test reads a source file as text, no added `skipIf`, `.skip` or `.only`, fake timers for anything that waits, and token-shaped fixtures are built at runtime.

## Repo rules that apply (restated)

1. **File-size ratchet.** Agents may not raise a row in `scripts/file-size-allowlist.txt`; the last row for a file is its cap. Current counts and caps: `src/lib/github-app.ts` 1083 of 1083, `src/lib/agents/spawn.ts` 1088 of 1089, `src/dashboard/server/routes/command-deck.ts` 1329 of 1331, `src/dashboard/frontend/src/components/Sidebar.tsx` 1000 of 1019, `src/dashboard/server/routes/workspaces/merge-ops.ts` 1763 of 1835, `src/cli/commands/doctor.ts` 973 of 1042. 2. **One variant per operation in `src/lib`.** `npm run lint:effect-facades` fails on an exported Effect wrapper around in-repo Promise code and on a sync/async twin. Every new function in this change is a plain `async` function. Do not add Effect wrappers.
3. **No import cycles.** `npm run lint` includes `lint:circular`. The new modules import in one direction only: `github-app-auth.ts` imports nothing from the other three; `github-app-installations.ts` imports `github-app-auth.ts` and `github-quota/repo-notes.ts`; `github-app.ts` imports both; `github-repo-identity.ts` imports `github-app.ts`, `github-app-installations.ts` and `github-quota/identity.ts`.
4. **No `execSync` in server-reachable code.** Use `execFile` through `promisify`, or `runGh` from `src/lib/github-quota/run-gh.ts`.
5. **Fake timers.** A test that depends on time (the 6-hour cache, token expiry) uses `vi.useFakeTimers()` with `vi.setSystemTime()` and `vi.advanceTimersByTimeAsync()`. Never a real `setTimeout` wait.
6. **No source-reading tests.** `lint:source-introspection` fails a new test that reads a source file as text. Assert on return values and rendered output.
7. **Token fixtures.** GitHub push protection blocks a branch that contains a string shaped like a real token (`ghs_…`, `ghp_…`). Build fake tokens at runtime, for example `['gh', 's_', 'test'].join('')`.
8. **New HTTP route.** A new route needs a row in `tests/unit/lib/overdeck/no-loss-matrix.ts` and a row in `src/dashboard/server/route-scopes.ts`, or CI fails. A route with no scope row requires `admin`.
9. **Frontend tests.** CI runs only the files listed in `scripts/frontend-test-subset.txt` (one path per line, relative to `src/dashboard/frontend`, sorted). Add every new frontend test there. Run one with `npm --prefix src/dashboard/frontend run test -- <path relative to src/dashboard/frontend>`. The frontend typecheck excludes test files, so grep test fixtures by hand after changing a type.
10. **Never run the full `npm test` on the host.** Run `npm run typecheck`, `npm run lint` and `npx vitest run <the test files you touched>`.
11. **Dashboard UI.** Load the `pan-style-guide` skill before writing JSX. No pill badges, no decorative color, no new font weights.

## Decisions made during planning

1. **Coverage is per repository, the display is per owner.** One owner can have covered and uncovered repositories (`eltmon/overdeck` and `eltmon/krux`). The resolver takes `owner` and `repo`. The sidebar, the settings table and the doctor rows group by owner.
2. **One App, many installations.** There is no second App and no per-owner credential directory. To cover an organization, the operator makes the App public in its GitHub settings and installs it on the organization. Overdeck then finds that installation by itself (FR-1). W12 documents this.
3. **The gh branch is the fallback, and it already exists.** Most Overdeck installations have no App and run every operation through `gh`. This change routes an uncovered repository to that same path. It adds no new way to act on GitHub.
4. **The home installation stays.** Keeping `installation-id` required means the machine-wide checks need no change (NFR-2).
5. **Lookup failure means "assume covered".** This keeps today's behavior under a network failure (NFR-1) and makes `appCoversRepo` safe to call anywhere without a try block.
6. **Negative results reuse repo notes; positive results stay in memory.** Repo notes already persist "not installed" for 6 hours across processes. A positive result costs one request per process, so it needs no file.
7. **Spawn warns and never refuses.** The gh login is read with a call that returns null during a GitHub rate-limit pause. Refusing on `none` would block every spawn during such a pause.
8. **Collapse instead of a filter.** The sidebar gets collapsible owner groups, stored in `localStorage` like the existing `MORE_COLLAPSED_KEY`. A separate owner filter would be a second control for the same need.
9. **No owner picker in the Add-project dialog.** No mode creates a repository on GitHub: clone takes a URL or `owner/repo`, existing takes a folder, and new runs `git init` only (`src/lib/projects/create-perform.ts` line 440). There is nothing for a picker to choose.
10. **No contracts change.** The response type of the new endpoint is declared in the server service and again in the frontend hook, as `MergeBackendStatus` is today (`src/dashboard/frontend/src/components/merge-train/MergeTrainView.tsx` line 117).
11. **`githubPrLookupSource()` is unchanged.** It is a log label with no repository in scope (`src/lib/github-pr-lookup.ts` line 8).

   1. `appCoversRepo(owner, repo)` is true: `{ mode: 'app', actor: botName(), detail: 'GitHub App is installed on this repository' }`.

   1. Take every project from `listProjects()` whose config has `github_repo` in the form `owner/repo`. Skip the others.
   2. When `opts.fresh` is true, call `clearAppNotInstalled(owner, repo)` for each and `resetRepoInstallationCache()` once, so coverage is looked up again.

   4. Group by owner. Compare owners case-insensitively and display the first spelling seen. Sort owners and, inside an owner, projects by name with `localeCompare`.

## Out of scope

- **A separate GitHub account per owner** (a work account next to a personal one, or an Enterprise Managed User), and a separate PAT per owner. `gh` holds several accounts but uses one at a time, and about 60 call sites run `gh`. Tracked in PAN-5154 (https://github.com/eltmon/overdeck/issues/5154).
- **GitHub Enterprise Server and `ghe.com` hosts.** `api.github.com` is hardcoded in six files and nothing reads `GH_HOST`. Also tracked in PAN-5154.
- **A second GitHub App** or per-owner App credentials.
- **Repairing a repository whose `origin` an earlier spawn already rewrote.** `pan doctor` reports it with the fix (W8); Overdeck does not rewrite the remote back.
- **The PAT paths** (`GitHubClient`, the issue poller, the webhook allowlist in `src/lib/webhook-handlers.ts` line 122).
- **Per-installation quota pools.** Calls through any installation are still recorded in the single `app` pool.
