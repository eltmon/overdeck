# PAN-5069 — Connect a bot in one paste and one approval

**Issue:** https://github.com/eltmon/overdeck/issues/5069
**Related:** PAN-4927 (connector), PAN-4950 (connector CLI), PAN-5058 (hosted-bot relay, parked), PAN-5068 (login retry, open)
**Planned:** 2026-11-05, auto mode, high effort.

This PRD holds the whole design. The work is split into four issues (see "Decomposition"):
this issue (PAN-5069) builds **Part A, the bot side**. Parts B, C and D are sibling issues that
cite the sections of this document named for them.

## Glossary

- **Connector** — the process a self-hosted bot runs to reach one Overdeck machine's MCP tools
  (`pan mcp connector …`, code in `src/lib/mcp/connector/`). It joins the overdeck.ai directory
  as a `platform: 'node'` client and dials the machine over a secure channel.
- **Connector home** — the connector's state directory: `$OVERDECK_CONNECTOR_HOME`, default
  `~/.overdeck-connector`, mode 0700, files mode 0600 (`src/lib/mcp/connector/home.ts`).
- **Pairing code** — a one-time `odp_<64 hex>` credential minted by the machine
  (`src/dashboard/server/pairing-credentials.ts`, `issuePairingCredential`). Single use, kept
  only in dashboard memory as a hash plus its Noise PSK.
- **Pairing string** — the text that carries a pairing code to a connector:
  `overdeck-connector:/pair#v=1&e=<environmentId>&k=<machineKeyHex>&c=<code>`
  (`packages/contracts/src/connector-pairing.ts`, `buildConnectorPairLink`).
- **Connector intent** — the dashboard's in-memory note, by pairingId, that a pairing code was
  issued for a connector with a name and scopes (`src/dashboard/server/connector-pairing.ts`).
  Part B turns it into a **connector request** (adds id, platform, status).
- **Device flow** — the overdeck.ai RFC 8628 sign-in (`services/account/src/device-flow.ts`).
  The connector requests a device code; a human opens the **activate link**
  (`verification_uri_complete`, `https://account.overdeck.ai/activate?user_code=XXXXXXXX`) and
  approves through GitHub; the connector polls and gets an account device token.
- **Root consent** — an action only the machine's root viewer (the root browser session or the
  internal token) can take. `POST /api/connectors/pairing` is root only (`rejectNonRoot`).
- **Copy message** — the one message the dashboard copies to the clipboard for the operator to
  paste into the bot (Part B). It embeds the pairing string and the `connect` command.
- **Status line** — the last line `pan mcp connector connect` prints on stdout:
  `OVERDECK_CONNECT <one-line JSON>`. It is the machine-readable contract the bot acts on.
- **Registration** — what the bot adds to its own MCP client config so it can call the tools: a
  stdio server whose command is `npx -y @overdeck/core@<version> mcp connector serve --stdio`.
- **Needs-you** — the dashboard's Decisions panel (`components/DecisionsPanel.tsx`, fed by
  `lib/useDecisions.ts`).

## Problem

Observed live on 2026-11-05 with Grok Bot. Connecting a bot today takes: pick a platform (Grok
Bot offers only Public MCP), copy a pairing string out of a dialog that mixes four `npx`
commands, an `export` and a YAML block, put the string in the bot's secret store (unreliable
across Grok's turns), have the bot run `login`, open the activate page and type an 8-letter
code within 15 minutes, then run `pair`, `serve`, and register a stdio server by hand. Closing
the dialog loses the pairing string: the Bots list shows "No bots connected" and no pending
request. The operator's verdict: "confusing, tedious … I would not want [users] to have to go
through all this."

The bot is an AI agent with a shell. It can do every step itself; the human should only consent.

## Operator decisions (issue comment, 2026-11-05) — authoritative

1. Flow: Settings → Anywhere → Bots → **Connect a bot** → pick the bot → pick access (default
   Read + Tell) → click **Copy for <bot>**. The operator pastes the message into the bot. The bot
   runs the one command, then shows the operator **one link**. The operator clicks the link and
   clicks **Authorize**. The bot finishes alone (pairs, verifies the route, registers the MCP
   server, makes a test call) and reports done.
2. **Approval stays on the machine.** The Copy click is the machine's root consent: it mints the
   one-time, short-lived pairing code with the chosen scopes, embedded in the copied message. Only
   a code minted by the machine can pair. overdeck.ai alone must never be able to attach a bot to
   a machine.
3. The link the bot shows is the device-flow `verification_uri_complete` with the code prefilled;
   the page names the bot and the machine; the operator signs in and clicks Authorize once.
4. After pairing, the machine shows the bot under Bots and a Needs-you notice
   "grok-bot connected with Read + Tell", with Revoke.
5. Nothing is lost when a dialog closes: a pending (copied, not yet paired) request is listed
   under Bots with Copy again / Cancel and its expiry.
6. A machine-side confirm card may be added only with a stated reason; no second required
   operator step without one.
7. Test bot: Grok Bot (cloud VM, Node 24, UDP blocked, TCP to TURN open, secret store unreliable
   across turns — do not depend on it).

These override the issue body's "Design notes" where they differ (the body proposed a
machine-side Approve/Deny card and "no pairing string"; the comment replaces the card with the
Copy click and embeds the code in the message).

### Security model (NFR-6)

Two independent things must both hold before a bot reaches a machine:

1. **A machine-minted pairing code.** Only the root viewer can mint one
   (`handleConnectorPairing` → `rejectNonRoot`). The code never leaves the clipboard and the bot's
   shell; overdeck.ai never sees it. The Noise XXpsk0 handshake proves the bot holds it; the
   machine burns it on first use (`takePairingById`, "any outcome removes it") and binds the new
   `connector` token to the bot's proved link key (`handleConnectorsExchange`).
2. **An overdeck.ai sign-in to the same account as the machine.** The directory only lets a
   client signal machines of its own account (`machineInDirectory`).

A compromised overdeck.ai can forge (2) but not (1), so it cannot attach a bot. The names on the
Authorize page (Part C) are **claims sent by whoever requested the device code** and are shown as
such; they are not an authority. **No machine-side confirm card is added (decision 6):** the code
is minted only by an explicit root click, is single use, expires (Part B: 30 minutes), and is
bound at exchange to the link key the bot proved, so a second confirm click would protect nothing
the code does not already protect, while adding the operator step the operator asked to avoid.

## Requirements

Part A (this issue):

- **FR-1** `pan mcp connector connect <pairingString> [--name <bot>] [--platform <id>] [--wait <seconds>] [--account-url <url>] [--directory-url <url>]` exists and is idempotent: running it again after any outcome continues from the stage it reached.
- **FR-2** Every run of `connect` prints exactly one status line, as the last line of stdout: `OVERDECK_CONNECT ` followed by one-line JSON with `v: 1` and `status` in `ready | authorize | retry | error`. Exit code: `ready` 0, `error` 1, `authorize` 3, `retry` 4.
- **FR-3** Sign-in is resumable. With no `account.json` and no live pending sign-in, `connect` requests a device code, saves it to `pending-signin.json`, prints the activate link, and exits 3 at once. A later run with a live pending sign-in polls that same device code for up to `--wait` seconds (default 120): approved → continues; still pending → exits 3 with the same link; expired → requests a new code and exits 3 with the new link; denied → removes the file, exits 1 `signin-denied`.
- **FR-4** Pairing is idempotent. When `pairing.json` names the same `environmentId` and `machineKeyHex` as the pairing string and the verify call succeeds, `connect` does not use the code. When verify answers 401 or 403, or there is no matching pairing, `connect` pairs with the code.
- **FR-5** Verify: `connect` opens a `ConnectorLink` to the paired machine and calls `GET /api/connectors/self` within 30 s; `ready` carries the machine label, the route (`direct` or `relay`) and the scopes.
- **FR-6** `ready` carries the registration for the bot: a stdio server named `overdeck`, command `npx`, args `["-y", "@overdeck/core@<running version>", "mcp", "connector", "serve", "--stdio"]`, plus `env.OVERDECK_CONNECTOR_HOME` only when that variable is set. Human-readable lines before the status line show the same registration in the platform's own config shape for `grok-bot` and `grok-build`, and as generic stdio JSON for every other platform.
- **FR-7** Every failure prints a stable `code` and a `next` sentence written for the bot (table in A-6). A pairing code the machine refuses (`ChannelOpenError` code `pairing-refused`) is reported as `pairing-code-refused` without a relay retry.
- **FR-8** The pairing string may carry the machine's name as `n=<percent-encoded label>` (at most 64 characters after decoding). `parseConnectorPairLink` returns it as optional `machineLabel`; a string without `n`, or with a bad `n`, still parses (with no `machineLabel`). `issueConnectorPairing` emits `n` from `ensureEnvironmentIdentity().label`.
- **FR-9** `requestDeviceCode` sends `client_name` (the bot name) and `target_name` (the machine name) when given, each trimmed and cut to 64 characters. The current account service ignores unknown form fields, so `connect` works before Part C deploys.
- **FR-10** `GET /api/connectors/self` answers a `connector` credential with `{ id, name, scopes, clientId, machine: { environmentId, label } }`; any other credential gets 403 `{ code: 'not-a-connector' }`. The scope table admits it with `read:state`.
- **FR-11** `login`, `pair`, `serve`, `status` and `logout` keep their behavior and messages. `logout` also deletes `pending-signin.json`.

Part B (sibling): **FR-12** Copy for <bot> copies one message built by `connectMessage(...)`. **FR-13** Connector pairing codes live 30 minutes; browser, machine and phone codes keep 10. **FR-14** Pending connector requests are listed under Bots with expiry, Copy again and Cancel; they live in dashboard memory and a restart drops them. **FR-15** A paired request shows a non-blocking Needs-you notice "<name> connected with <scopes>" with Revoke and Dismiss for 24 h. **FR-16** Grok Bot offers the connector reach first. **FR-17** `configuration/bots.mdx` and `configuration/mcp.mdx` describe the one-paste flow.

Part C (sibling): **FR-18** `GET /activate?user_code=<valid code>` renders the confirm step directly, naming the bot and machine as claims, with one Authorize button that starts the GitHub leg. **FR-19** `POST /oauth/device/code` stores optional `client_name`/`target_name` (≤64 chars, HTML-escaped on render) in new `device_grants` columns (migration `0003`). **FR-20** A GET with an invalid code renders the plain form and counts against `activate-fail`.

Part D (sibling): **FR-21** `integrations/shared/SKILL.md` gains a "Connect to Overdeck" section on the status-line contract; safety rule 1 allows the one-time Copy message. **FR-22** Each platform README contains its `connectMessage` output verbatim. **FR-23** Grok Bot's `mcp.json` uses the connector stdio command. **FR-24** Hermes and OpenClaw stdio registration formats are verified against their docs and printed by `connect` for those platforms.

Non-functional:

- **NFR-1** `connect` never prints a token: not the connector token, the local token, the account device token, or the device code. The only secret-like text it prints is the activate link's user code, which is the point of the link.
- **NFR-2** Async fs only; every new connector-home file is written with `writeSecretFile` (0600, atomic) and read with the existing strict readers.
- **NFR-3** Tests of polling and waits use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`; no real waits.
- **NFR-4** `connect` never reads or writes `~/.overdeck` (OVERDECK_HOME).
- **NFR-5** `src/cli/commands/mcp-connector.ts` keeps importing only Commander types statically; `connect` loads its module inside the action.
- **NFR-6** Only a machine-minted code can pair (security model above). Part A does not change that.

```ts
/** FR-10: the calling connector's own record. Exactly a connector credential may call this. */
export async function handleConnectorSelf(credential: DashboardCredential | null): Promise<HttpServerResponse.HttpServerResponse> {
  if (credential?.kind !== 'connector') {
    return noStore(jsonResponse({ error: 'only a paired connector may read itself', code: 'not-a-connector' }, { status: 403 }));
  }
  const record = (await listAccessTokens()).find((entry) => entry.id === credential.tokenId && !entry.revokedAt);
  if (!record) return noStore(jsonResponse({ error: 'this connector was removed', code: 'connector-removed' }, { status: 403 }));
  const descriptor = await buildEnvironmentDescriptor();
  return noStore(jsonResponse({
    id: record.id,
    name: record.name,
    scopes: record.scopes,
    clientId: record.clientId ?? null,
    machine: { environmentId: descriptor.environmentId, label: descriptor.label },
  }));
}
```

### A-7. Resumable sign-in (FR-3, FR-9)

Files: `src/lib/mcp/connector/connect-signin.ts` (new), `tests/unit/lib/mcp/connector/connect-signin.test.ts` (new).

```ts
export type SignInResult =
  | { ok: true; account: ConnectorAccount }
  | { ok: false; status: ConnectStatus };   // authorize | retry | error

export async function ensureSignedIn(
  opts: { home: string; env: NodeJS.ProcessEnv; accountUrl?: string; directoryUrl?: string;
          clientName?: string; targetName?: string; waitSeconds: number },
  io: ConnectorIo,
  deps: { fetch?: typeof fetch; now?: () => number } = {},
): Promise<SignInResult>;
```

Steps, in order:

1. `readAccount(home)` → present: return `{ ok: true, account }`. (A stale device token shows
   up later as `directory-refused`; the `next` text covers it.)
2. Resolve `baseUrl` (`resolveBaseUrl`) and `directoryUrl` (`parseDirectoryUrl`) as
   `runConnectorLogin` does; `platformString()` null → `error unsupported-platform`;
   `ensureIdentity(home)` for the `clientId`.
3. `readPendingSignIn(home)`. If present, `baseUrl` matches and `Date.parse(expiresAt) > now`:
   **poll** — call `pollForToken(baseUrl, { deviceCode, userCode, verificationUri,
   verificationUriComplete, interval, expiresIn: budget }, …)` with
   `budget = min(waitSeconds, secondsUntilExpiry)`. (Passing the budget as `expiresIn` makes
   `pollForToken` stop at the budget without changing `client.ts`.) Outcomes:
   - `ok` → `getMe`, `writeAccount` (same record `runConnectorLogin` writes),
     `removePendingSignIn`, return ok.
   - `expired_token` with `detail === 'expired_token'` (the **server** said the grant expired,
     `client.ts` line 207) → remove the file and go to step 4, whatever the local clock says.
   - `expired_token` with any other `detail` (the local budget ran out, line 159) and now < real
     expiry → return `authorize` with the **same** url.
   - `expired_token` with any other `detail` and real expiry passed → remove the file and go to step 4.
   - `access_denied` → remove the file, return `error signin-denied`.
   - `unreachable` or `failed` → re-read `account.json`; present (a concurrent run finished
     the grant) → return ok; else `retry network`.
   With `waitSeconds === 0` skip polling and return `authorize` with the same url.
4. Otherwise (no live pending sign-in): `requestDeviceCode(baseUrl, { platform, environmentId:
   clientId, clientName, targetName })`; on `AccountClientError` or a thrown fetch → `retry
   network`. Write `pending-signin.json` with `expiresAt = now + expiresIn * 1000`. Print
   `Open this link and click Authorize: <verificationUriComplete>` and return `authorize` at
   once (no polling: most bot shells show output only after the command exits).

Tests (fake timers, injected `fetch`): fresh run writes the pending file and returns authorize
without a token poll; rerun with an approved grant writes `account.json` and removes the
pending file; rerun with a pending grant and `waitSeconds: 10` returns authorize with the same
url after advancing 10 s; an expired pending file triggers a new device-code request; denied →
`signin-denied` and the file is gone; the device-code form carries `client_name`/`target_name`.

Stages:

1. `parseConnectorPairLink` → null: status `error bad-pairing-string`.
2. `ensureSignedIn({ clientName: opts.name, targetName: link.machineLabel, … })`; not ok →
   print its status, return its exit code. Home read errors → `error home-unreadable`.
3. `readPairing(home)`: when it names `link.environmentId` and `link.machineKeyHex`, run

   Noise handshake and no HTTP status ever comes back. Only transport failures and the 30 s
   timeout are `retry verify-failed`.
4. `pairWithMachine({ pairingString, label: opts.name, home, appVersion }, deps)`; failure →
   map its `code` through the A-6 table (`network`, `machine-offline`, `machine-unreachable` are
   `retry`; the rest `error`), with `detail: outcome.message`. Success → stage 5.
5. **Verify:** create the directory client and RTC as `runConnectorServe` does, construct
   `ConnectorLink`, `await within(link.connect(), 30_000)` (`within` is private in `pair.ts`:

6. Print `Connected to <machine> over <route> with <scopes>.`, the `registrationLines(platform, …)`,
   then the `ready` status line; return 0.

to stdout. Nothing prints a token (NFR-1). `--name` is the label the directory and the machine's

## Risks

- **A code can burn on a dropped handshake.** `takePairingById` consumes on any outcome, so a
  transport drop after the machine took the PSK leaves a used code; the next run reports
  `pairing-code-refused` and the operator clicks Copy again (Part B makes that one click).
- **Grok Bot's VM blocks UDP.** Without the relay plan `connect` ends in `relay-plan-needed`;
  that is the honest outcome until PAN-5058.
- **PAN-5068 edits `requestDeviceCode`.** A-3 touches only the form building to keep the merge clean.
- **Two concurrent runs** share `pending-signin.json`; the account service consumes a grant
  atomically, so the loser re-reads `account.json` (A-7 step 3).
