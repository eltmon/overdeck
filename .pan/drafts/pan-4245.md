# PAN-4245 — Conversation titles and About summaries cover everything still in context

**Issue:** [PAN-4245](https://github.com/eltmon/overdeck/issues/4245)
**Status:** planned (auto mode, 2026-09-27)
**Base commit:** `93468d610c1`

## Glossary

- **Compaction** — when a Claude Code session nears its context limit, the harness replaces the older turns with a model-written summary. Overdeck's own "native compaction" does the same thing.
- **compact_boundary record** — a JSONL line `{"type":"system","subtype":"compact_boundary",...}` that marks where a compaction happened.
- **Compaction summary record** — the JSONL line written right after a boundary: `{"type":"user","isCompactSummary":true,"isVisibleInTranscriptOnly":true,"message":{"role":"user","content":"This session is being continued from a previous conversation that ran out of context. The summary below covers the earlier portion of the conversation.\n\nSummary:\n1. Primary Request and Intent:\n   - …"}}`. `message.content` is one plain string in every observed record (Claude Code and Overdeck native). The summary is the model's own account of what is still in context.
- **Continuation preamble** — the fixed first paragraph of every summary: `This session is being continued from a previous conversation that ran out of context. The summary below covers the earlier portion of the conversation.` It ends at the first blank line (`\n\n`).
- **Primary Request and Intent section** — section 1 of a Claude Code summary: a line `1. Primary Request and Intent:` followed by bullet lines (`   - …`) until the line that starts section 2 (`2. …`).
- **Latest compaction summary** (`latestCompactSummary`) — the new parse-result field this PRD adds: the text and position of the last summary record in a transcript.
- **sequence** — the monotonic per-JSONL-line counter the Claude parser assigns (`parser.ts`, `const lineSequence = sequence++;`). It continues across incremental parses because `ParseState.lastSequence` is threaded. Every `ChatMessage` the Claude parser emits carries it.
- **Title transcript / About transcript** — the plain-text transcript strings built by `serializeConversationTranscript` and sent to Haiku to produce a conversation title or the About-drawer summary.
- **Purpose** — the new `serializeConversationTranscript` option `'about' | 'title'` that selects which budget applies when a summary exists.

## Problem

In a long conversation the AI title and the About summary describe only the most recent request. Conversation 2878 (`~/.claude/projects/-home-eltmon-Projects-overdeck/0974944a-eba1-43b8-9888-a2a123b5047f.jsonl`, 83 MB, four compactions) was renamed "Overdeck intro video revisions and deployment", which was only its last topic. Verified on 2026-09-27: the summary record at line 25044 is a string of 14,506 chars and opens with `Summary:\n1. Primary Request and Intent:\n   - I orchestrate Overdeck development …`.

## Root cause (verified against `93468d610c1`)

1. **The parser drops the summary text.** `src/dashboard/server/services/conversation/parser.ts` line 204 (`const text = renderableUserText(rawContent);`, string content) and line 264 (`const text = renderableUserText(block.text);`, array content) call `renderableUserText`, which calls `isSystemInjection` in `src/dashboard/server/services/conversation/message-filters.ts`. Line 11 (`if (text.startsWith('This session is being continued from a previous conversation')) return true;`) makes the parser skip it. Hiding it from the chat view is correct; the side effect is that no model prompt ever sees it.
2. **The parser keeps no summary text.** The `compact_boundary` branch (`parser.ts` lines 474-486, `} else if (entry.type === 'system' && (entry as Record<string, unknown>).subtype === 'compact_boundary') {`) stores only `{id, timestamp, trigger, preTokens, model}`.
3. **The serializer keeps only the two ends.** `serializeConversationTranscript` (`src/lib/conversations/transcript-summary.ts` lines 72-93) caps each message at `PER_MESSAGE_LIMIT` (1,800) and, over `TRANSCRIPT_BUDGET` (24,000), keeps `HEAD_BUDGET` (8,000) + `TAIL_BUDGET` (15,000) chars (lines 36-43). `titleTranscriptWindow` (lines 171-179) narrows titles to 2,500 head + 5,000 tail (lines 44-47).
4. **The title prompt favors the tail.** `summarizeTranscriptTitle` (lines 353-370) says: `'what it is *currently* about. If the topic shifted, favor the most recent direction.'` (line 362).
5. **The fallback title uses the latest request.** `fallbackTranscriptTitle` (lines 114-130) takes `userLines.at(-1)` (line 125).
6. **The About summary sees the same head+tail.** `summarizeTranscriptAbout` (lines 372-386).
7. **Large transcripts go through a chunk loop the issue did not name.** A cold `getCachedMessages` call on a file over `MAX_READ_BYTES` (10 MB, `conversation/types.ts` line 89) reaches `parseConversationMessages(file, 0)`, which delegates to `parseEntireConversation` (`parser.ts` line 85: `if (fromByteOffset === 0 && !priorState && fileSize > MAX_READ_BYTES) {`). That function loops 10 MB chunks, threads an explicit `priorState = { … }` literal (lines 706-719), and returns `{ ...last, messages, workLog, compactBoundaries, totalCost, totalTokens }` (line 734). A field that each chunk reports only for itself is lost when the summary is not in the last chunk. Conversation 2878 is exactly this case.

Callers that build the transcripts:

- Periodic auto refine — `src/lib/overdeck/title-refinement.ts` lines 88-98 (`handleTurnComplete`, writes `title_source 'ai-refined'`).
- Explicit retitle — `src/lib/overdeck/conversation-reads.ts` lines 787-802 (`retitleConversation`, uses `fallbackTranscriptTitle` on timeout).
- About drawer — `src/lib/overdeck/conversation-reads.ts` lines 839-850 (`getConversationAbout`).

## Requirements

### Functional

- **FR-1** The Claude Code parser records the latest compaction summary on its parse result as `latestCompactSummary: { text, sequence, uuid?, timestamp? }`, detected by `entry.isCompactSummary === true` (never by the text prefix). String content and text-block-array content are both supported.
- **FR-2** `messages` is unchanged: the summary still does not appear in the chat view.
- **FR-3** The summary survives every multi-read path: incremental `parseConversationMessages` calls with `priorState`, the `parseEntireConversation` chunk loop, and the `getCachedMessages` incremental merge. A newer summary replaces an older one; a read with no new summary keeps the older one.
- **FR-4** `serializeConversationTranscript(messages, { compactSummary, purpose })` puts the summary first under a fixed label and then only the turns whose `sequence` is after the summary's. Turns before the summary are dropped.
- **FR-5** With a summary, the About transcript keeps up to 14,000 summary chars and fills the rest of the 24,000 budget with the most recent post-summary turns. The title transcript keeps up to 4,000 summary chars plus up to 3,500 chars of the most recent post-summary turns.
- **FR-6** The title prompt asks for the overall scope of the work still in context and no longer says "favor the most recent direction". The About prompt treats a leading summary as the earlier part of the conversation.
- **FR-7** When the transcript carries a summary, `fallbackTranscriptTitle` derives the title from the first item of the summary's Primary Request and Intent section; otherwise it keeps today's latest-`User:` rule.
- **FR-8** Auto refine, explicit retitle, and the About drawer pass `latestCompactSummary` and the matching purpose to the serializer.

### Non-functional

- **NFR-1** With no summary, `serializeConversationTranscript` output is byte-identical to today's for every input, regardless of `purpose`.
- **NFR-2** No second read of the transcript file: the summary is captured during the existing parse.
- **NFR-3** The summary is part of the transcript string, so it stays inside `fenceUntrustedTranscript` (PAN-2657). The Overdeck-native trailer ("Continue from this summary without redoing already-completed work.") is an instruction and must never be placed outside the fence.
- **NFR-4** `latestCompactSummary` is not added to any RPC/wire schema (`@overdeck/contracts`). It lives on the server-side `ParseResult` only.
- **NFR-5** `npm run typecheck` and `npm run lint` pass; every touched test file passes under `npx vitest run <file>`.

## Decisions (auto mode)

1. **The summary field is part of `ParseState`, not only `ParseResult`.** Each parse returns `foundInThisRead ?? priorState?.latestCompactSummary`. This makes the chunk loop and the incremental path correct by construction. The explicit field lists that must also carry it are named in WI-1 and WI-2.
2. **Purpose flag, not string-marker parsing.** `serializeConversationTranscript` takes `purpose: 'about' | 'title'` (default `'about'`). With a summary and `purpose: 'title'` the output is at most ~7,700 chars, so `titleTranscriptWindow` (budget 8,000) passes it through unchanged. `titleTranscriptWindow` itself is not modified. This avoids parsing a marker back out of a string, which would break on summaries that quote the marker (a summary of this very work would).
3. **Strip the continuation preamble.** When the summary text starts with `This session is being continued from a previous conversation`, drop everything up to and including the first `\n\n`. For Claude Code summaries the kept text starts with `Summary:\n1. Primary Request and Intent:`. If no `\n\n` exists, keep the text unchanged.
4. **Messages without `sequence` are kept** after the summary (they cannot be placed). The Claude parser always sets `sequence`, so this only matters for synthetic input.
5. **Type location.** `src/lib/conversations/transcript-summary.ts` exports a structural `TranscriptCompactSummary { text: string; sequence: number }` so the module stays a leaf. `src/dashboard/server/services/conversation/types.ts` exports the richer `CompactSummaryRecord { text; sequence; uuid?; timestamp? }`, which is structurally assignable. Nothing goes into `@overdeck/contracts` (an RPC schema).
6. **Truncation marker.** An over-cap summary is cut with `text.slice(0, cap) + '…'`, matching the per-message truncation style.
7. **Prompt builders are exported** (`buildTranscriptTitlePrompt`, `buildTranscriptAboutPrompt`) so the prompt wording is unit-testable without spawning `claude`.
8. **Other harnesses fall back to today's behavior by construction.** Codex, OpenCode (ACP), Pi, ohmypi, Kimi, and Muse parsers never set `latestCompactSummary`, so their output stays byte-identical (NFR-1).
9. **Manual check without mutating the operator's conversation.** The 2878 check runs a gitignored scratch script against the workspace source that prints the title and About; it does not call `retitleConversation` (which would overwrite 2878's title with `title_source 'ai-explicit'`).
10. **New test files instead of growing `conversation-service.test.ts`.** That file is 1,398 lines, over the 1,000-line ceiling in `scripts/lint-file-size.sh`; a new file avoids an allowlist row.

     options: SerializeTranscriptOptions = {},

     if (!options.compactSummary || !summaryText) {
       // unchanged head+tail path (byte-identical, NFR-1)

     const purpose = options.purpose ?? 'about';
     const cap = purpose === 'title' ? TITLE_SUMMARY_BUDGET : ABOUT_SUMMARY_BUDGET;

     const summarySection = `${COMPACT_SUMMARY_LABEL}\n${summaryPart}`;

     const joined = renderTurns(after).join('\n\n');
