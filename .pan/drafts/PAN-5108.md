# PAN-5108: Auto-update harness CLIs (Claude Code first) by default, with a Settings switch to turn it off

**Issue:** https://github.com/eltmon/overdeck/issues/5108
**Status:** planned (auto mode, 2026-11-10)

## Problem

On 2026-11-10 the operator picked Claude Fable 5.2 and Overdeck refused the launch: "Claude Fable 5.2 (claude-fable-5-2) needs Claude Code 2.1.321 or newer, but Overdeck would launch Claude Code 2.1.293 … Upgrade it with `npm install -g … @anthropic-ai/claude-code@latest` …". Every user hits this after each new model launch. Overdeck must keep harness CLIs current by default, and the operator must be able to turn that off in Settings.

## Glossary

- **Harness CLI**: the coding-agent binary a harness launches (`claude`, `codex`, `kimi`, `opencode`, …). One binary can serve several harnesses (`kimi` serves `acp` and `kimi-code`).
- **Update plan (fleet)**: `HarnessUpdatePlan` in `src/lib/fleet/harness-versions.ts` (PAN-4654). `argv` is the command Overdeck may run, or `null` when it must not run anything. Built by `harnessUpdatePlan()`.
- **Upgrade plan (Claude Code)**: `ClaudeUpgradePlan` in `src/lib/claude-code/version.ts` (PAN-4359). `runnable` + `argv`. Built by `claudeCodeUpgradePlan()`. Native installs get `[realPath, 'update']`; user-writable npm installs get `[npmBin, 'install', '-g', '--prefix', prefix, '@anthropic-ai/claude-code@latest']`.
- **npm-based plan**: a fleet update plan built by the npm branch of `harnessUpdatePlan()` (the binary's real path contains `/lib/node_modules/<npmPackage>/`). After this issue the plan carries `npmPackage: string` for these and `npmPackage: null` for every other plan.
- **Refusal**: the `ClaudeCodeTooOldError` that `assertClaudeCodeSupportsModel()` throws when the launch binary is older than the model's `minClaudeCodeVersion`. `prepareHarnessLaunch()` (`src/lib/harness-binary.ts`, line 318) calls it for every `claude-code` launch.
- **Update on refusal**: the new step that runs the Claude Code upgrade plan once when the refusal would fire and auto-update is on, then re-checks.
- **Background updater**: the new primary-dashboard service that checks and updates npm-based harness CLIs 2 minutes after boot and every 24 hours.
- **Update queue**: the new process-wide serial queue in `src/lib/fleet/harness-update-runner.ts`. One update command runs at a time in a process. A request whose key equals a queued or running request's key joins that request instead of running again.
- **Cooldown**: after an update on refusal fails for a command, further launches do not retry it for 15 minutes. They raise the refusal at once with the remembered error.
- **Needs you**: the dashboard's decisions panel (`src/dashboard/frontend/src/components/DecisionsPanel.tsx`) fed by `useDecisions()`. The "System" group holds machine items such as the PAN-5093 disk alert.
- **Primary dashboard**: the dashboard process where `isPeerDashboard` is false in `src/dashboard/server/main.ts`.
- **God-file budget**: `scripts/lint-file-size.sh` fails when a file over 1000 lines grows past its `origin/main` count or its last `scripts/file-size-allowlist.txt` row. Agents cannot raise a cap.

## Decisions

Issue decisions D1-D5 are the operator's. D6-D17 are planning decisions made in auto mode.

- **D1 (issue)** Setting `harnesses.auto_update` (boolean, default `true`) in the global config. Settings switch: "Keep coding-agent CLIs up to date automatically". Off = today's behavior exactly (refusal + banner).
- **D2 (issue)** Background updater: dashboard-server service, boot + 2 minutes, then every 24 hours; async only; one update at a time; one log line per outcome; a failure goes to Needs you as a warning (never an error toast loop) and retries at the next run; the log line says running sessions keep their binary.
- **D3 (issue)** Update on refusal: when the refusal would fire and auto-update is on, run the Claude Code update plan once, re-check, continue the launch if it passes, otherwise raise today's refusal with the update's error appended. An in-process lock makes concurrent launches share one update.
- **D4 (issue)** Scope: harness CLIs whose update plan is npm-based. A harness with no update plan is skipped and logged. The Overdeck package is out of scope.
- **D5 (issue)** TENET-10: keep the launch hook small, put the updater logic in its own module, test the refusal path with auto-update on and off.
- **D6** The background updater runs only npm-based plans (`plan.npmPackage !== null && plan.argv !== null`). A runnable non-npm plan (native `claude update`, `kimi upgrade --yes`, `opencode upgrade`, a non-npm `codex update`) is skipped and logged with its command. Native Claude Code already updates itself.
- **D7** Update on refusal runs the Claude Code upgrade plan from `claudeCodeUpgradePlan()` whenever `plan.runnable && plan.argv` (npm or native). That is the same command the existing Upgrade Claude Code button runs. A non-runnable plan (root-owned npm prefix, Homebrew, unknown install, Windows) raises today's refusal unchanged and runs nothing.
- **D8** Every update command runs through one process-wide update queue in `src/lib`, keyed by `argv.join(' ')`. The background updater, update on refusal and the existing fleet "Update all" job all use it. So two npm global installs never run at once in one process. Every job yields the same type, a command result or `null` (the job ran no command because its own pre-check found nothing to do), so a request that joins a run another path started receives that plain result, never the other path's own outcome. A joiner that receives `null` and still needs the update queues its own run once, and update on refusal always re-checks its own model minimum before the launch continues (review cycle 1).
- **D9** The queued job re-checks before it runs. Update on refusal re-reads the version with `refresh: true` and skips the command when the binary already satisfies the minimum. The background updater asks npm for the latest version and skips when current. This covers an update another process finished first.
- **D10** Update commands run with `execFile` (argv, never a shell string), `PATH` = `<dirname(launch binary path)>:${process.env.PATH}` (same rule as `POST /api/claude-code/upgrade`, so nvm's `npm` finds `node`), `maxBuffer` 16 MiB, and a timeout. The output kept is the last 2000 characters.
- **D11** Update on refusal times out after 3 minutes (`LAUNCH_UPDATE_TIMEOUT_MS = 180_000`). After a failure, the cooldown (`LAUNCH_UPDATE_RETRY_MS = 900_000`, 15 minutes) stops further launches from rerunning the same command. They raise the refusal at once with the remembered error. A success clears the cooldown entry.
- **D12** The background updater's command timeout is 10 minutes (the existing `UPDATE_TIMEOUT_MS`). `npm view` gets 60 seconds.
- **D13** `harnesses.auto_update` is machine-wide. `stripProjectSecurity()` also drops `harnesses` from a project `.pan.yaml`, so a project file never sets it. The launch hook and the service read it through `loadGlobalConfigNoMigration()`. A config read error means "off" for that check (Overdeck cannot confirm the operator did not turn it off). A config.yaml that fails to parse is not a read error: the loader returns the defaults, so auto-update is on, the same fallback every other setting has with a broken config. A value other than a literal boolean is ignored and the default `true` applies.
- **D14** Test safety. The default enablement reader `isHarnessAutoUpdateEnabled()` returns `false` when `process.env.VITEST` is set. Tests that need auto-update on inject the reader. So no test that reaches the real launch hook or service can start a real `npm install -g`.
- **D15** Needs you is state-based. Each completed background pass replaces the failure list with exactly that pass's failures. A failure item disappears when the next pass ends that binary as updated, current or skipped, or when auto-update is off (an off pass empties the list). Items are non-blocking, in the "System" group, one per failing binary. Update-on-refusal failures do not create Needs-you items, because the launch error already reports them.
- **D16** The phone shows a failure as a read-only line: `Update failed. Overdeck retries at the next daily check.` (no Open or Answer button).
- **D17** The Settings switch lives in a new "Coding Agents" section (`id: 'coding-agents'`) placed directly after the Permissions section and nav entry. The YAML write never deletes the `harnesses` block when a PUT omits it, so a stale browser tab cannot silently turn auto-update back on.

## Requirements

### Functional

- **FR-1** `DEFAULT_CONFIG.harnesses.autoUpdate` is `true`. `mergeConfigs()` sets `harnesses.autoUpdate` from a YAML `harnesses.auto_update` boolean and ignores non-booleans. A project `.pan.yaml` cannot set it.
- **FR-2** `GET /api/settings` returns `harnesses.auto_update` (the effective value). `PUT /api/settings` with `harnesses.auto_update: false` writes `harnesses:\n  auto_update: false` to `~/.overdeck/config.yaml`. A PUT that omits `harnesses` leaves the block on disk unchanged. A non-boolean `auto_update` fails validation with `harnesses.auto_update must be a boolean`.
- **FR-3** Settings shows a "Coding Agents" section with the switch "Keep coding-agent CLIs up to date automatically". Toggling it saves through the normal settings autosave.
- **FR-4** With auto-update on, a `claude-code` launch whose binary is below the model minimum and whose upgrade plan is runnable runs the plan once through the update queue, re-reads the version, and proceeds when it now satisfies the minimum.
- **FR-5** With auto-update on, when the update fails or the version is still too old, the launch raises `ClaudeCodeTooOldError` whose message is today's message plus one appended sentence naming the failure.
- **FR-6** With auto-update off, or with a non-runnable plan, the launch raises today's `ClaudeCodeTooOldError` with a byte-identical message and runs no command.
- **FR-7** Concurrent launches that hit the refusal for the same command share one update run. Within 15 minutes of a failed update on refusal, a launch does not rerun the command.
- **FR-8** The background updater starts in the primary dashboard only, runs its first pass 2 minutes after start and then every 24 hours after each pass ends, and processes one CLI at a time.
- **FR-9** In a pass, an npm-based CLI below npm's latest version is updated. A current one is skipped. A CLI with no update plan, or a non-npm plan, is skipped and logged. A failure is recorded without throwing.
- **FR-10** Each outcome produces exactly one log line. The `updated` line says running sessions keep their current binary and new launches use the new one.
- **FR-11** `GET /api/harness-auto-update` returns the updater snapshot (`HarnessAutoUpdateSnapshot`) with scope `read:state`.
- **FR-12** Needs you shows one non-blocking "System" item per failing binary, with the error tail, the manual command, and the retry note. The phone shows the D16 line.
- **FR-13** The existing fleet "Update all" job runs its harness commands through the same update queue.

### Non-functional

- **NFR-1** No `execSync`, no `spawnSync`, no blocking call in server-reachable code. Every exec is `execFile` with an argv.
- **NFR-2** God-file budgets in the table above hold. `bash scripts/lint-file-size.sh` passes.
- **NFR-3** Timer-driven tests use `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()`. Every I/O dependency (config reader, CLI detection, `npm view`, command runner, version reader, log, emit) is injected, so fake timers never gate real I/O.
- **NFR-4** No test runs a real `npm install` (D14).
- **NFR-5** Docs use no em dashes in new text.

## Non-goals

- Updating the Overdeck package itself (`pan` updates stay explicit).
- Background updates for non-npm installs (native Claude Code, Kimi, Homebrew, a root-owned npm prefix, Windows).
- Running `sudo` or any root-owned install.
- Restarting or touching running agent or conversation sessions after an update.
- A cross-process lock between a CLI process and the dashboard (the lock is in-process, per D3).
- An immediate pass when the Settings switch is turned back on (the next scheduled pass applies it).
- Needs-you items for update-on-refusal failures (the launch error reports them).
- Changes to the Upgrade Claude Code banner or `POST /api/claude-code/upgrade`.
- A per-harness on/off setting.

## Hazards

- **Callers may time out while the launch updates.** The dashboard's `fetchWithTimeout` defaults to 20 seconds. A launch that runs the update on refusal can take longer, so the browser may show a timeout while the server finishes the launch. The background updater (boot + 2 minutes) makes this path rare. Do not add new client timeouts in this issue.
- **Existing tests reach the refusal path.** `claude-code.test.ts` "throws ClaudeCodeTooOldError…" passes a runnable plan. It must inject `autoUpdateEnabled: async () => false` (D14 also guards it).
- **Peer dashboards** do not start the service. They can still run update on refusal for their own launches; this is intended.
- **npm view and nvm.** `npm view` and the install must run with `PATH` starting with the launch binary's directory (D10), or nvm's `npm` shebang can fail to find `node`.
