# PAN-5347: Composer `/` menu lists skills under a labeled Skills group

**Issue:** [PAN-5347](https://github.com/eltmon/overdeck/issues/5347)
**Status:** planned (auto mode, 2026-11-15)
**Base commit:** `eaaeeb3ec58` on `feature/pan-5347`

## Glossary

- **Composer** — the message box at the bottom of a dashboard conversation. React component `ComposerFooter` (`src/dashboard/frontend/src/components/chat/ComposerFooter.tsx`) wraps the Lexical editor `ComposerPromptEditor` (`.../chat/ComposerPromptEditor.tsx`).
- **Slash menu** — the popup `SlashMenu` (in `ComposerPromptEditor.tsx`) that opens when the operator types `/`. It filters `SlashCommand[]` by the text after the last `/` and groups rows under a header per `SlashCommand.category`.
- **Source** — one list that `getSlashCommands(harness)` (`.../chat/slashCommands.ts`) concatenates into the menu. Today there are four: harness native commands, the static `/handoff` entry, the generated `pan` CLI manifest (`COMPOSER_COMMAND_MANIFEST`), and curated variants (`COMPOSER_COMMAND_VARIANTS`). This issue adds a fifth: skills.
- **Skill** — a directory holding a `SKILL.md`. Claude Code runs an installed skill when the operator types `/<skill-name>`.
- **Skill catalog** — `listSkillCatalog()` in `src/lib/skill-overrides/catalog.ts`: every skill under `~/.overdeck/skills`, `~/.claude/skills`, `~/.agents/skills` and `<projectRoot>/.pan/skills`, one entry per name, with `description` (first line of the frontmatter `description`) and `origin`.
- **Skill override layers** — per-skill on/off values at four levels, narrowest wins: conversation (`conversations.skill_overrides`, PAN-4486) > issue (`<planHome>/.pan/skill-overrides/<ISSUE>.yaml`) > project (`projects.yaml` `skill_overrides`) > global (`config.yaml` `skills.overrides`). Resolved by `resolveOne()` in `src/lib/skill-overrides/resolve.ts`.
- **Core skill** — a skill in `CORE_SKILLS` (`src/lib/skill-overrides/resolve.ts`, around line 13: `'pan', 'pan-done', 'pan-flywheel', 'pan-foreman', 'pan-plan', 'pan-start', 'pan-task', 'pan-tell', 'pan-worker', 'work-complete', 'write-xbrief'`). It is always enabled and reported with `core: true`.
- **Pack skill** — a skill from a third-party skill pack (PAN-4334). The API reports it as `packs[].skills[]` with id `pack/skill`; Claude Code sees it as `/<pack>:<skill>` through a generated plugin. Out of scope here.
- **Launch scope** — what `resolveLaunchScope({ cwd, issueId })` in `src/lib/skill-overrides/launch.ts` (line ~51) returns: project derived from the cwd with `resolveProjectKeyForCwdAsync`, issue from the context or the workspace path. The launcher uses this scope, plus the conversation row's skill map, to decide which skills Claude Code hides (`--settings '{"skillOverrides":{…:"off"}}'`).
- **Harness capability** — a field on `HarnessCapabilities` (`packages/contracts/src/harness-capabilities.ts`). Code that decides something per harness reads a capability. It never compares harness names (`lint:harness-branches` ratchet, PAN-4562).
- **Synthetic conversation** — a `Conversation` object the frontend builds for an agent session that has no `conversations` row (`SessionPanel.tsx` `synthesizedConversation`, id `-1`, name = session id, cwd = workspace; `AgentOutputPanel.tsx` `specialistConversation`, id `0`, cwd `''`). Real rows have id ≥ 1.
- **D8 fallback** — the existing pattern in `ConversationSkillsField.tsx`: when the skills request fails for an issue no registered project owns, retry without the issue.

## Problem

The `/` menu lists no skills. Typing `/pan-cons` finds nothing, although `pan-consolidate-conversations` is installed, enabled, and runs when Claude Code gets `/pan-consolidate-conversations`. `getSlashCommands` (`src/dashboard/frontend/src/components/chat/slashCommands.ts:41`) has no skill source:

```ts
export function getSlashCommands(harness: HarnessName): SlashCommand[] {
  const behavior = getHarnessBehavior(harness);
  const nativeCommands = (behavior.nativeCommands ?? []).map(command => ({ … category: `${behavior.displayName} native` }));
  return [
    ...nativeCommands,
    ...STATIC_SLASH_COMMANDS,
    ...OVERDECK_SLASH_COMMANDS,
    ...CURATED_OVERDECK_VARIANTS,
  ];
}
```

So `pan-flywheel`, `pan-recap` and every other skill-only workflow is invisible from the composer. An operator must already know a skill's exact name.

## Proposal (summary)

1. Declare a new harness capability, `skillSlashCommands: boolean`. Claude Code is `true`; every other harness is `false`.
2. Extend `GET /api/skills/overrides` with optional `conversation=<name>`, `cwd=<path>` and (already existing) `issue=<id>` parameters for a launch-scope lookup. With a known conversation row, the server resolves skill states the way a launch of that conversation does: launch scope from the row's cwd and issue, plus the row's own skill map as the conversation layer. Without a row (agent sessions), it resolves launch scope from the given `cwd` and `issue`, which is what a work-agent launch uses.
3. Add a frontend module `skillSlashCommands.ts` that fetches that list when the slash menu opens and maps every enabled native skill to a `SlashCommand` in category **Skills**.
4. `getSlashCommands(harness, skillCommands)` appends the skill entries as one block after the existing four sources, only when the harness declares `skillSlashCommands`.
5. `ComposerPromptEditor` takes a `skillContext` prop, calls the hook, and passes its result to `getSlashCommands`. `ComposerFooter` passes `skillContextForConversation(conversation)`.
6. Document the new group, the capability and the new parameters.

## Requirements

### Functional

- **FR-1** In a Claude Code conversation, typing `/pan-cons` in the composer shows `/pan-consolidate-conversations` under a header reading **Skills**, with the skill's catalog description.
- **FR-2** Choosing a skill entry replaces the trigger `/` and filter text with `/<skill-name> ` (trailing space).
- **FR-3** A skill whose resolved state is off for the conversation does not appear. "Resolved" means the same precedence a launch uses: conversation row map > issue > project (derived from the conversation's cwd) > global.
- **FR-4** Core skills appear (they are always enabled), except the names the composer intercepts before they reach the harness (FR-8).
- **FR-5** CLI verbs keep their **Overdeck** header; native commands keep their `<Harness> native` header; `/handoff` keeps **Conversation**.
- **FR-6** A harness whose capabilities declare `skillSlashCommands: false` shows no **Skills** group and makes no skills request.
- **FR-7** `GET /api/skills/overrides?conversation=<name>[&cwd=<path>][&issue=<id>]` returns `{ project, issue, skills, packs }` resolved for that launch scope, without the `overriddenBelow` / `packOverriddenBelow` aggregates. A known row wins over `cwd`/`issue`. An unknown name with no `cwd` answers 404 with `code: "unknown-conversation"`; an unknown name with a `cwd` resolves from the `cwd` and `issue`. A request with `cwd` and no `conversation` also takes this path.
- **FR-10** A work-agent or planning-agent session view (synthetic conversation with a workspace cwd) shows the Skills group resolved from that workspace's project and issue.
- **FR-8** The Skills group never lists `pan` (the composer treats `/pan …` as a portable Overdeck command) or `pan-handoff` / `handoff` (the composer opens the handoff dialog for those).
- **FR-9** When the skills request fails or is still in flight, the menu still shows the other four sources unchanged.

### Non-functional

- **NFR-1** No skills request fires on composer mount. The request fires only when the slash menu opens, so the `ComposerFooter*.test.tsx` fetch assertions (for example `ComposerFooter.test.tsx` line ~254) stay valid.
- **NFR-2** No `useQuery` in the `ComposerFooter` subtree. `heldKickoff.tsx` and `scheduledMessages.ts` document why: many test files mount `ComposerFooter` without a `QueryClientProvider`. Use plain `fetch` in a hook, like those modules.
- **NFR-3** Skill entries form one contiguous block at the end of the list, so keyboard order (index in the filtered array) matches the visual order of the grouped menu. Existing selections do not move: typing `/pan sync` still highlights the CLI entry first.
- **NFR-4** `ComposerFooter.tsx` stays at or under 1000 lines (`scripts/lint-file-size.sh` `CEILING=1000`; it is 975 at base). Its change is one prop.
- **NFR-5** The new GET parameter adds no new route, so no no-loss-matrix row and no `route-scopes.ts` change.
- **NFR-6** Server code stays async apart from the existing synchronous SQLite row read `getConversationByName` (already used by `routes/admin.ts` and `routes/conversation-message-cancel.ts`). No `execSync`.

## Decisions

- **D1 — Capability, not a name check.** Add `skillSlashCommands` to `HarnessCapabilities`. Claude Code runs a skill from `/<skill>`. For Codex, Pi and the other harnesses, `/<skill>` as a skill invocation is not verified, so they declare `false`. A later harness flips its own field once verified.
- **D2 — Server resolves the launch scope.** The frontend `Conversation` type has no skill map, and `projectKey` is null for most conversations (the project comes from the cwd). The launcher already resolves this (`pan skills launch-settings --cwd … [--issue …] [--conversation …]`, `launcher-lines.ts`), so the server reuses `resolveLaunchScope` and, for a real row, the row's `skillOverrides`. This is what makes FR-3 match what Claude Code actually hides. Agent sessions have no row, so the frontend also sends `cwd` and `issue` and the server falls back to them (FR-10).
- **D3 — Native skills only.** Pack skills (`packs[].skills[]`) are excluded: the API id is `pack/skill`, the harness name is `pack:skill`, and the Deft adapter renames skills. A follow-up can add them.
- **D4 — Skills go last.** Placing them before **Overdeck** would let a skill whose description contains `pan sync` take the first row and steal Enter from `/pan sync`. Last keeps every existing selection.
- **D5 — Fetch on open, refetch on every open.** The hook fetches each time the menu goes from closed to open, and keeps the previous list visible until the new one lands. No module cache, so a skill toggled in Settings shows up on the next `/`.
- **D6 — Context rules.** `skillContextForConversation(conv)` returns `undefined` when `conv.origin` is `'linked'` or `'vault'` (their skills live on another machine). Otherwise it returns `{ conversationName: conv.id > 0 ? conv.name : undefined, cwd: conv.cwd || undefined, issueId: conv.issueId ?? undefined }`, and `undefined` when both `conversationName` and `cwd` are absent (for example the specialist synthetic with `cwd: ''`). No context means no Skills group and no request.
- **D7 — Intercepted names are excluded by a constant.** `COMPOSER_INTERCEPTED_SKILL_NAMES = new Set(['pan', 'pan-handoff', 'handoff'])` in the new module, with a comment pointing at the two regexes in `ComposerFooter.tsx` (`/^\/(?:pan[\s-])?handoff(?:\s+(.+))?$/i` and `/^\/pan(?:\s|$)/i`).
- **D8 — Unknown issue falls back server-side.** If the row's issue is owned by no registered project and the cwd gives no project, `listSkillStates` throws `unknown-issue`. The conversation path catches that one code and retries with `{ projectKey }` only (D8 pattern moved server-side).
- **D9 — Description fallback.** A skill with no description shows an empty description. No invented text.
- **D10 — Stable empty array.** The hook returns one module-level frozen constant `EMPTY_SKILL_COMMANDS` when disabled and as its initial state, so the `slashCommands` memo and the editor's keydown effect do not re-run every render.
- **D11 — No UAT xBRIEF item.** Live browser verification is an acceptance criterion for the review/test roles (AC-8), not a work item, because `pan task done` requires an `Item:` commit and verification produces none.

   export async function listConversationSkillStates(query: LaunchScopeQuery): Promise<SkillStateList> {
     let row: { cwd: string; issueId: string | null; skillOverrides: Record<string, boolean> | null } | null = null;
     if (query.conversationName) {

     const conversationOverrides = row?.skillOverrides ?? undefined;
     try {

     } catch (error) {
       if (error instanceof SkillOverrideError && error.code === 'unknown-issue') {
         return listSkillStates({ projectKey: scope.projectKey, conversationOverrides });
       }
       throw error;
     }
   }
