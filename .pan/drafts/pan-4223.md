## Summary

Today a gauntlet orchestrator fans work out in two ways. A Claude orchestrator uses the Agent tool, whose sub-agents can only be Anthropic models. For any other model it abuses `pan handoff`: it creates a git worktree by hand, writes a brief file, and hands off from a throwaway conversation that already runs the wanted model, because `pan handoff` ignores `--harness`. The result is a flat list of conversations titled "SB lane: …". They are parented (inside a JSON blob) to the throwaway conversation, not to the orchestrator. Nothing in Overdeck knows they are lanes. The orchestrator watches a hand-rolled `sentinel.log` to learn when a lane finishes, and cleans up worktrees by hand. A GPT, Codex or Kimi orchestrator cannot fan out at all, so the skill tells the operator to run the gauntlet from a Claude session.

This PRD adds one thin concept and one door:

- A **lane** is an ordinary Overdeck conversation that carries four launch-time facts on its row: its parent conversation, its run key, its lane key and its role. A **gauntlet run** is the set of lanes that share a run key. There is no run table and no stored lane status.
- **`pan lane start`** (CLI) and **`POST /api/lanes`** (API) share one core. The core creates the lane's isolated working directory under a configurable lanes root, stamps the brief, creates the conversation with any harness, model and effort, and records the parent link. Any conversation can call it, whatever its harness, because it is a shell command that reads `$OVERDECK_CONVERSATION`.
- **`pan lane report | wait | list | stop | reap`** give the orchestrator a lifecycle. The report and wait machinery is the `pan worker` machinery, reused. `pan tell` delivers messages (with one bug fixed). `pan lane reap` removes the lane's directory and archives its conversation (`--keep` leaves it listed).
- **`pan handoff` and `pan fork`** (CLI and dashboard) record the same parent link on the successor conversation, so a handoff chain is a tree too.
- The **Command Deck** conversation list nests every conversation with a parent under that parent in collapsible groups: lanes under their orchestrator, successors under their predecessor, at most two levels deep. The **Agents page** nests them too.
- The **`pan-gauntlet-loop` skill** replaces "run the gauntlet from a Claude session" with the lane door, and absorbs the rules that GAUNTLET-LOOP-V3 learned the hard way.

## Glossary

- **Orchestrator**: the conversation that runs a gauntlet loop. It launches lanes, reads their reports, merges, and keeps the run's board. V3 calls the top orchestrator the *supervisor*.
- **Gauntlet run**: one pass of the loop, named by a **run key** (for example `hotel`). It is not a stored object. It is the set of lane rows whose `gauntlet_run` column equals the key. The run's contract, board and notes stay in the project repo (`gauntlet/RUN-<CODENAME>.md`, `gauntlet/status.json`), as the skill already says.
- **Lane**: a conversation launched by the lane door. Its row carries `parent_conversation_id`, `gauntlet_run`, `lane_key` and `lane_role`.
- **Lane key**: the lane's short name inside its run, usually the issue number (`663`) or an area key (`terrain-look`).
- **Lane role**: one of `builder`, `critic`, `verifier`, `play`, `orchestrator`.
  - `builder` implements, commits and pushes its own branch.
  - `critic` judges a candidate blind and never edits.
  - `verifier` is an adversarial engineering critic (V3 "Verifiers"). The door treats it like `critic` except for the parent rule in D8.
  - `play` is a cold play-agent (V3 "Play-agents") with no repo and no project context.
  - `orchestrator` is a cluster orchestrator under the root orchestrator (V3 §7 "Orchestrator tiers").
- **Iteration**: the n-th lane with the same (run, key, role). It is derived by counting rows; it is never stored. Shown as `i2`.
- **Lanes root**: the directory under which the door creates lane working directories. Per project, configurable, default `<parent of project path>/<project dir name>-lanes` (Lexerra: `/home/eltmon/Projects/lexerra-lanes`).
- **Lane working directory**: a git worktree (builder: on a branch; critic, verifier, orchestrator: detached at a commit) or, for `play`, a plain empty directory outside the repo.
- **Brief**: the lane's work order. The door copies it, write-once, to `~/.overdeck/agents/conv-<name>/lane-brief.md`.
- **Lane contract**: the initial message the door delivers. It points at the brief and states the role rules and how to report (text in WI-3).
- **Report**: a Markdown result the lane writes with `pan lane report`. It is stored as `~/.overdeck/agents/conv-<name>/reports/<seq>.json` by the existing worker report store. A report is an artifact written at the moment of the action, never status.
- **Derived lane state**: what the UI and `pan lane list` show. It is computed on every read from the terminal backend (liveness), the report files and git. It is never stored.
- **Reap**: stop a lane if it runs, check that nothing still runs in its directory, optionally park uncommitted work as a patch, remove the worktree, then archive the lane's conversation unless `--keep` is given (D14).
- **Launch-time fact**: a value that is true because of how something was started (like a pane token or a conversation's `cwd`). It never changes and is not status. The four lane columns are launch-time facts.
- **Parent link**: a row's `parent_conversation_id`. Two writers set it, both at creation: the lane door and the fork door (`handleConversationSummaryFork`, WI-14). Nothing updates it.
- **Successor**: a conversation created by `pan handoff`, `pan fork`, the dashboard fork modal or the `/handoff` composer command, in any fork mode (`plain`, `summary`, `handoff`). Its parent link names the source conversation; its three lane columns are null. A successor is not a lane, even when its source is one.
- **Effective launcher**: for lane-door rules (D4, D8), the row reached by starting at the launching conversation and following parent links while the current row is a successor. It is either a lane or a conversation with no parent (D21).
- **Root conversation**: a conversation whose effective launcher is not a lane. A successor of a root is a root; a successor of a lane is not.
- **Natural depth / display depth**: a row whose parent link is null, or names a row absent from the list being rendered, has natural depth 0. Any other row has its parent's natural depth plus 1. Its display depth is `min(natural depth, 2)` (D22).
- **Space-bunny (SB) lanes**: the lanes the HOTEL orchestrator launched on 2026-09-25 with the free model `stealth/space-bunny-alpha`.

### `pan handoff` is the wrong launcher

- `--harness` is ignored (above); the harness follows the model's provider. A lane needs an explicit harness.
- Handoff authors a handoff document from the source transcript. A lane needs a brief, not a summary of the orchestrator's history. The authoring phase takes minutes and can hang (V3 §5: "NEVER wrap `pan handoff` in a shell `timeout` … killing it forces the degraded summary fork").
- Handoff has no `--effort` (`src/cli/index.ts:378-390`); the child inherits the source's effort (`src/lib/overdeck/conversation-forks.ts:890`).
- The only parent record is inside `conversations.fork_request` JSON on the child (`conversation-forks.ts:896-913`, `ForkRequest.parentConversationName` at `src/lib/overdeck/conversations.ts:213-230`). The forward pointer `handoff_target_conv_id` is written on the source only when a handoff document was produced (`recordConversationHandoff`, `conversations.ts:1032-1040`, called at `conversation-forks.ts:573`).

### `pan worker run` cannot carry lanes

`pan worker` (PAN-3920) already has the lifecycle a lane needs (parent, report, wait, `pan tell`), but:

- `--issue` is required: `'--issue is required: a worker belongs to an issue.'` (`src/cli/commands/worker.ts:181`). Gauntlet lanes are not Overdeck pipeline issues.
- The issue workspace must exist and `--cwd` must resolve inside it (`src/lib/agents/worker/start.ts:114-127`). The default worktree is `<workspace>/.swarm/worker-<n>/` (`start.ts:147`). Lanes live under a lanes root, off the project's base ref.
- A worker is a native agent, not a conversation: `registerConversation: false` (`start.ts:151-162`). The Command Deck conversation list renders only conversation rows, so workers can never nest there.

## Requirements

### Functional

- **FR-1** A conversation row can carry four launch-time lane facts: `parent_conversation_id` (UUID of the launching conversation), `gauntlet_run`, `lane_key`, `lane_role`. They are written once at creation and never updated.
- **FR-2** `pan lane start` and `POST /api/lanes` create a lane through one core function. The CLI calls the API; no second creation path exists.
- **FR-3** The lane's working directory is created under the project's lanes root. The lanes root must resolve under `$HOME`, must not resolve under `/tmp`, and must not equal or contain the project's primary checkout path.
- **FR-4** For `builder`: a git worktree on a new branch (default `<run>/<key>`) cut from the base ref (default `origin/<default_branch>`, fetched first), with the project's sparse-checkout patterns applied when configured. For `critic`, `verifier` and `orchestrator`: a detached worktree at `--at <ref>` (critic, verifier: required; orchestrator: default the base ref).
- **FR-5** For `play`: an empty plain directory under the lanes root, and the conversation is created with `bareContext: true` and `skipClaudeMd: true` (PAN-4185 flags).
- **FR-6** The door refuses (HTTP 409, CLI exit 1) when another lane with the same (run, key, role) has a live harness, or when any live lane already uses the target directory. `--replace` stops the live lane of the same (run, key, role) through the conversation stop door first.
- **FR-7** Iterations and continuation. Without `--reuse`, every launch is a new iteration with a new directory (paths in D8); a builder iteration n ≥ 2 gets a new branch `<run>/<key>-i<n>` cut from the previous builder iteration's branch, because a branch that reported `done` is frozen (V5). `--reuse` launches a new conversation in the directory of the latest earlier lane with the same (run, key, role), which must not be live (respawn with continuation after a crash or a stop); it keeps that iteration number. An existing target directory without `--reuse` is refused.
- **FR-8** The door accepts `--harness`, `--model`, `--effort`. When a flag is absent it uses `projects.<key>.gauntlet.roles.<role>` from config. When no model results, the door refuses; there is no hardcoded model fallback.
- **FR-9** The door copies the brief (`--brief <file>` or `--prompt <text>`, exactly one) to `~/.overdeck/agents/conv-<name>/lane-brief.md` write-once, and delivers the lane contract (WI-3) as the initial message.
- **FR-10** The lane's title is `--title`, else `<run> <key> · <role>`, stored with `titleSource: 'manual'`. The door never calls AI title generation.
- **FR-11** `pan lane report` (run inside a lane) writes a report through the worker report store keyed `conv-<name>`, with status `done | blocked | failed` and, for git-backed lanes, the `head` SHA and branch at report time.
- **FR-12** A `builder` lane's `done` report is refused while `git status --porcelain` is non-empty or the branch has commits not on its upstream (or has no upstream). `--allow-unpushed` overrides.
- **FR-13** `pan lane wait <lane>` has `pan worker wait` semantics and exit codes (0 done, 4 blocked/failed, 2 exited or idle 10 min without a report, 3 timeout, 1 error).
- **FR-14** `pan lane wait --run <key>` (or `--parent <conv>`) returns the next report of any lane in the set after a cursor, and prints the next command with the new cursor.
- **FR-15** `pan lane list [--run] [--parent] [--json]` and `GET /api/lanes` show every lane with its derived state (table in D10), newest report, git facts and cost.
- **FR-16** `pan tell` refuses to message a `critic` or `verifier` lane that has a `done` report, and says "launch a fresh critic". `--force` overrides.
- **FR-17** `pan tell conv-<name>` resolves the conversation's real harness (fixes the `messaging.ts:242-247` lookup).
- **FR-18** The Command Deck conversation list renders each lane under its parent conversation, in a collapsible group, with role, lane key, iteration, activity and newest report status. Orchestrator lanes nest their own lanes (depth 2).
- **FR-19** The Agents page shows lanes under their parent: the History view through `parentId`, the Live view as child lines of the parent row. A lane that needs the operator also appears as its own row in "Needs you".
- **FR-20** `pan lane reap` stops a live lane through the conversation stop door, then refuses while `pidsWithCwdUnder(dir)` is non-empty and prints those PIDs. It never kills a process.
- **FR-21** `pan lane reap` refuses a dirty worktree unless `--park`, which writes the uncommitted work to `~/.overdeck/agents/conv-<name>/parked-<timestamp>.patch` first. It removes only directories under the lanes root that belong to that lane, runs `git worktree remove` (never `--force`) and `git worktree prune`, and keeps the branch.
- **FR-22** The skill documents the lane door as the fan-out path for any harness, deletes the "run the gauntlet from a Claude session" rule, and folds in the V3 rules in the table above.
- **FR-23** (operator Q2) After the directory is removed, `pan lane reap` and `POST /api/lanes/:name/reap` archive the lane's conversation through `archiveConversationByName`. `--keep` (`keep: true`) skips the archive and leaves an ended, unarchived row. An "already archived" answer counts as archived. A failed archive leaves the removal in place and returns `archived: false` with a warning. A refused reap (FR-20, FR-21, the lanes-root check) archives nothing.
- **FR-24** Archived lanes stay in `GET /api/lanes`, `GET /api/lanes/:name` and `pan lane list`, with `archived: true` and `activity: 'stopped'`. Iteration counting (D7) counts them.
- **FR-25** (operator Q3) Every conversation created by `handleConversationSummaryFork` (`pan handoff`, `pan fork`, the dashboard fork modal and the `/handoff` composer command; fork modes `plain`, `summary` and `handoff`) carries `parent_conversation_id` = the source conversation's UUID, written in the creating `INSERT`. Its `gauntlet_run`, `lane_key` and `lane_role` stay null.
- **FR-26** The Command Deck list and the Agents History view nest every conversation whose parent link is set and whose parent is in the rendered list: lanes under their launcher, successors under their predecessor. Rows render in pre-order of the parent-link tree at display depth `min(natural depth, 2)`. A row with natural depth 3 or more carries a marker: `↳ continued from #<parent id>` for a successor, `lane of #<parent id> · <run>` for a lane.
- **FR-27** A successor row shows `continues ← #<parent id>`, a link to `/conv/<parent id>`, wherever it renders (nested, flattened or top level).
- **FR-28** A top-level Command Deck group sits where its highest-ranked member would sit in the flat order of today (`ConversationList.tsx:266-276`). It is expanded by default while any descendant is active by that list's `isActive` predicate (`:266`), and collapsed otherwise.
- **FR-29** The Agents Live view nests lanes, not successors: a lane with its parent present is a child line of the parent row, and a successor keeps its own row with `continues ← #<parent id>` in its label. The live scope's ancestor walk does not climb from a successor to its predecessor.
- **FR-30** The lane door applies D4 and D8 to the effective launcher (D21), not to the launching row. The new lane's parent link still names the launching row.

### Non-functional

- **NFR-1** No stored lane status. Every state the UI or CLI shows is derived on read from backend liveness, report files and git. The four columns are launch-time facts.
- **NFR-2** Server-side git and filesystem work uses async `execFile` with timeouts (never `execSync` in the server; rule `no-execsync-server.md`).
- **NFR-3** `GET /api/lanes` bounds its git work: git facts run with a concurrency limit of 8 (`withConcurrencyLimit`, `src/lib/concurrency.ts`), each git call has a 10 s timeout, and the whole answer is memoized per filter for 3 s (same as `DIRECTORY_MEMO_MS`). The conversation list enrichment does no git work for lanes.
- **NFR-4** Lane launches for one project are serialized in-process, so the FR-6 check and the row insert cannot race.
- **NFR-5** Existing `POST /api/conversations` behavior is unchanged (same body, same response, same title generation).
- **NFR-6** The UI follows the `pan-style-guide` skill (load it before UI work): no pill badges, no decorative color, no green for "running", existing weight tiers.
- **NFR-7** Apart from the parent link on the new row, fork and handoff behavior is unchanged: the same request body, response shape, validation, `fork_request` JSON, `handoff_target_conv_id` write, title and pipeline.

## Decisions

- **D1 A lane is a conversation, not a worker.** FR-18 forces it: the Command Deck list renders only conversation rows, and workers have `registerConversation: false`. Conversations already support every harness, model and effort, have a transcript view and a composer, and carry `totalCost`. Workers stay the tool for issue-linked delegation inside the pipeline; lanes are the tool for fan-out outside it.
- **D2 Four columns, no run table.** `parent_conversation_id TEXT REFERENCES conversations(id)`, `gauntlet_run TEXT`, `lane_key TEXT`, `lane_role TEXT`, plus two indexes. A run is `WHERE gauntlet_run = ?`. The run's contract and board stay in the project repo.
- **D3 Handoff and fork successors nest (reversed 2026-09-26 by operator decision Q3).** Two writers set `parent_conversation_id`, both at creation: the lane door, with the three lane columns, and the fork door `handleConversationSummaryFork`, with the parent link only (FR-25, WI-14). Nesting keys on `parent_conversation_id IS NOT NULL` with the parent present in the rendered list, not on `lane_key`, so a handoff chain renders as a tree (FR-26). `fork_request` and `handoff_target_conv_id` keep their meaning (NFR-7). Rows created elsewhere get no parent link: post-`/clear` siblings (they keep `cleared_to_conv_id`), backfilled agent rows, retrospective conversations and `POST /api/conversations`. Existing rows are not backfilled from `fork_request`: the link is a launch-time fact, and the HOTEL space-bunny lanes' `fork_request` names the throwaway conversation 2898, not the orchestrator, so a backfill would nest them under the wrong row.
- **D4 The run key.** `--run` is required when the effective launcher (D21) is not a lane; a lane whose effective launcher is an `orchestrator` lane inherits that lane's run and `--run` must match if given. Pattern `^[a-z0-9][a-z0-9-]{0,31}$`. Lane key pattern `^[a-z0-9][a-z0-9._-]{0,39}$`.
- **D5 Parent resolution.** `--parent <ref>` (numeric conversation id, conversation name, or `conv-<name>`), else `$OVERDECK_CONVERSATION` with the `conv-` prefix stripped. The parent must be an existing conversation row. With neither, the CLI exits 1: "pan lane start must run inside a conversation or name --parent". Native agents (`$OVERDECK_AGENT_ID`) are not lane parents.
- **D6 Succession.** When an orchestrator hands itself off, the successor nests under it (D3), and the lanes the predecessor already launched stay nested under the predecessor. They stay because the parent link is a write-once launch-time fact (FR-1); moving them to the successor would turn it into stored status. The predecessor's group therefore reads: its own lanes, then the successor, which nests the lanes it launches later. The successor row shows `continues ← #<predecessor id>` (FR-27), the backward counterpart of the existing "Open handoff target" menu item (`ConversationRow.tsx:625-632`). A root successor passes the same `--run` for new lanes and sees every lane of the run, both generations, with `pan lane list --run <key>`. When a row's parent is not in the Command Deck list (archived, or filtered out by project or tab), the row renders at top level with the caption `lane of #<parent id> · <run>` (a lane) or its `continues ← #<parent id>` link (a successor). Reaping an orchestrator lane archives it (D14), so builders it launched that are not yet reaped render as orphans; reap builders before their orchestrator lane.
- **D7 Iteration is derived.** Iteration = the number of distinct `cwd` values among lane rows with the same (run, key, role), counting rows in `created_at` order up to and including this one. A `--reuse` respawn shares its predecessor's directory, so it keeps the iteration; every other launch (including a `--replace`, and including a duplicate that was later stopped) has a new directory and so counts as a new iteration. The builder recipe for "NOT_YET, build again" is simply a new `pan lane start --role builder --key <key>`: the door cuts `<run>/<key>-i<n>` from the previous iteration's branch (the previous lane's newest report `git.branch`, else the naming convention `<run>/<key>` for i1 and `<run>/<key>-i<n-1>` after that). `--from <ref>` overrides the base.
- **D20 Effort values.** The door accepts what the conversation door accepts: `low | medium | high` (`SAFE_EFFORT_PATTERN`, `conversation-runtime.ts:191`), free-form for `opencode`. `xhigh` is refused with the message "effort must be low, medium or high"; V3 reserves `xhigh` for the operator's explicit choice, and extending the pattern is a separate change to both doors.
- **D8 Role rules the door enforces.**

  | Role | Parent may be | Working directory | Extra |
  |---|---|---|---|
  | `orchestrator` | a root conversation only | detached worktree at `--at` (default base ref) `<root>/<run>-<key>-orch` | may launch `builder`, `verifier`, `play` |
  | `builder` | root or `orchestrator` lane | worktree on branch `--branch` (default `<run>/<key>` for i1, `<run>/<key>-i<n>` after) at `<root>/<run>-<key>` (i1) or `<root>/<run>-<key>-i<n>` (n ≥ 2) | may launch nothing |
  | `critic` | a root conversation only | detached worktree at required `--at` `<root>/<run>-<key>-critic-i<n>` | may launch nothing; never re-tasked (FR-16) |
  | `verifier` | root or `orchestrator` lane | detached worktree at required `--at` `<root>/<run>-<key>-verify-i<n>` | may launch nothing; never re-tasked (FR-16) |
  | `play` | root or `orchestrator` lane | empty directory `<root>/<run>-<key>-play-i<n>` | `bareContext` + `skipClaudeMd` forced |

  "Parent may be" is checked against the effective launcher (D21): "a root conversation" means one whose effective launcher is not a lane (glossary), and "`orchestrator` lane" means one whose effective launcher is an `orchestrator` lane.
- **D9 The brief lives in the conversation's state directory,** not in the worktree, so it never dirties the tree and survives reaping. `conv-*` directories are never cleaned (`agent-directory-cleanup.ts:95-106`).
- **D10 Derived lane state.** Computed per read:

  | `activity` | Rule (first match wins) | Source |
  |---|---|---|
  | `failed-to-start` | `spawnError` is set | conversation row |
  | `needs-you` | harness alive and `pendingInputCount > 0` | list enrichment |
  | `working` | harness alive and `isWorking` | list enrichment |
  | `idle` | harness alive | list enrichment |
  | `starting` | not alive, not ended, created less than 3 min ago | row |
  | `stopped` | otherwise | row |

  Report: newest `{ seq, at, status, head, branch }` from `listWorkerReports('conv-<name>')`. Git (git-backed roles, `GET /api/lanes` only): `branch`, `head`, `ahead` (`git rev-list --count @{u}..HEAD`, null without upstream), `dirty` (`git status --porcelain` non-empty). Board vocabulary (AWAITING CRITIQUE, WOWED, ACCEPTED, SHIPPED) stays in the project's `gauntlet/status.json`; Overdeck does not model verdicts.
- **D11 Reports reuse the worker store keyed `conv-<name>`.** `report.ts` gains an optional `git` field on `WorkerReport`. The lane report guard keys on `$OVERDECK_CONVERSATION` (exported for every harness), not on `$OVERDECK_AGENT_ID`.
- **D12 Messaging reuses `pan tell`.** Orchestrators message lanes with `pan tell conv-<name> "<text>"`. No `pan lane tell` verb.
- **D13 Stop reuses the conversation stop door** (`POST /api/conversations/:name/stop` → `handleConversationStop`, `conversation-runtime.ts:1018`). `pan lane stop` is a thin CLI over it.
- **D14 Reap archives the conversation by default (operator decision Q2, 2026-09-26).** After the directory is removed, reap calls `archiveConversationByName(name, deps)` (`conversation-archive.ts:144`), the path the archive route uses, with the same three dependencies (`routes/conversations.ts:792-796`), so a finished run leaves the Command Deck. `--keep` skips the archive; the ended lane then stays nested and collapsed. The archive deletes only `~/.overdeck/conversation-attachments/<name>`; the brief, the reports and any parked patch in `~/.overdeck/agents/conv-<name>/` survive, and the transcript stays reachable from the archived list. Archived lanes stay in the lane views (FR-24), so a run's ledger stays complete. The archive runs last, only after the removal succeeded: a 400 "already archived" counts as archived; any other failure returns `{ removed: true, archived: false }` with the warning `reaped, but archiving failed: <error>; archive conv <id> from the Command Deck`, and the CLI prints it and exits 0, because the directory work is done and the archive can be repeated.
- **D15 Herdr is unchanged.** Lane panes live in the existing `conversations` Herdr workspace (`src/lib/terminal-backends/launch.ts:44`). No `parent` pane token is stamped; the DB column is the single record of the link.
- **D16 One launch path.** The runtime-start block of `handleConversationCreate` is extracted into `startConversationRuntime(…)`; `POST /api/conversations` and the lane core both call it.
- **D17 CLI verb name `pan lane`** with six subcommands: `start`, `list`, `wait`, `report`, `stop`, `reap` (operator decision Q1, 2026-09-26; `pan gauntlet lane …` was rejected as longer to type in every brief).
- **D18 Command Deck groups are per-viewer collapsible, and a group ranks by its best member** (changed 2026-09-26 for D3). A group is a top-level row and every row nested under it, lanes and successors alike. Collapsed state lives in `localStorage` key `commandDeck.groups.collapsed` (a JSON array of top-level conversation names), wrapped in try/catch. Default: expanded while any descendant is active by the list's existing `isActive` predicate (`ConversationList.tsx:266`: `sessionAlive`, or a fork in progress); collapsed otherwise. A handoff source is usually ended while its successor runs, so ranking a group by its top row alone would bury the live successor in the inactive half behind a closed toggle; instead the group takes the position its highest-ranked member would have in today's flat order (FR-28).
- **D19 The Agent tool stays valid.** The skill keeps Agent-tool fan-out for Claude orchestrators whose lanes are short, Anthropic-model and single-turn. It requires the lane door when (a) the orchestrator's harness has no Agent tool, (b) the lane's model is not available to the Agent tool, (c) the lane must survive the orchestrator's context loss or run longer than one turn, or (d) the lane needs its own branch. Critics may use either path; the board's `critic` field names the Agent id or the lane conversation id.
- **D21 A successor inherits its source's standing at the lane door, not its lane facts** (added 2026-09-26 for D3). The effective launcher (glossary) is found by following parent links from the launching row while the current row is a successor (`lane_key` null and parent link set); the walk stops at a lane or at a row with no parent. Parent links always point at an older row, so the walk ends; the implementation still stops at a repeated id. So an orchestrator lane that hands itself off keeps its standing: the successor may launch builders, verifiers and play lanes in the same run, and still may not launch critics (V8). A handed-off root orchestrator is a root and may launch critics. A successor is never a lane itself: `pan lane report` from it fails "not inside a lane", `pan lane list` does not show it, and continuing a lane's own work in a fresh conversation is `pan lane start --reuse` (FR-7), not `pan handoff`.
- **D22 Nesting depth is capped at two; deeper rows flatten** (added 2026-09-26 for D3). Handoff chains make deep trees likely (orchestrator → successor → its successor → its lanes). Both the Command Deck and the Agents History view render rows in pre-order of the parent-link tree (siblings: live first, then `createdAt` ascending) at display depth `min(natural depth, 2)`. A row with natural depth 3 or more keeps its pre-order position (right below its natural parent's row and that parent's earlier children) but renders at depth 2 inside the same depth-1 group, with the marker `↳ continued from #<parent id>` (a successor) or `lane of #<parent id> · <run>` (a lane) so the real parent stays named. Example (every row ended, created in the order named): O launches lanes L1, L2 and hands off to O2; O2 launches M1 and hands off to O3; O3 launches N1. Rendered: O (0); L1, L2, O2 (1); M1, O3 (2); N1 (2, `lane of #<O3 id> · <run>`). Only a top-level row carries a collapse toggle (D18), so every lane of an expanded group is visible; none is hidden behind a deeper toggle.
- **D23 The Agents Live view nests lanes only** (added 2026-09-26 for D3). The Live view shows what runs now, and a stopped entry falls into its collapsed Idle footer. A live successor nested as a child line under its ended predecessor would disappear there, so a successor keeps its own Live row with `continues ← #<parent id>` in its label, and `keepWithAncestors` (`agent-directory.ts:398-410`) does not climb a succession edge (a conversation entry without `lane` whose `parentId` is set). Lanes nest as before (FR-19), and a lane's walk to its launcher still runs. The History view nests successors (FR-26), because it is the record of what happened.

## Intersecting repo rules (restated)

- Async only in the server: `execFile` from `node:child_process` promisified, with `timeout`; never `execSync` (`sync-sources/rules/no-execsync-server.md`).
- One variant per operation in `src/lib`; no Effect wrapper around in-repo Promise code (CLAUDE.md "Key Invariants"; `npm run lint:effect-facades`).
- Fake timers or injected `now`/`sleep` for every wait or retry test (`fake-timers-for-retry-tests.md`); `waitForWorkerReport` already takes `now` and `sleep`.
- No hardcoded model fallbacks (`no-hardcoded-model-fallbacks.md`): a missing model is an error.
- Spawned agents run in an isolated cwd, never the primary checkout (`handoff-isolate-cwd.md`); FR-3 enforces it for lanes.
- Agents are persistent sessions, never one-shot execs (`no-oneshot-agents.md`): lanes are conversations.
- Never run destructive HTTP requests speculatively (CLAUDE.md): tests use injected deps, never the live dashboard.
- Quality gates: `npm run typecheck`, `npm run lint`, and `npx vitest run <touched test files>`. `npm run typecheck` excludes `*.test.ts`, so run the touched tests.
- UI: load the `pan-style-guide` skill before WI-10 and WI-11.

2. New pure module `conversation-tree.ts`:

   ```ts
   export interface ConversationTreeNode {
     conv: Conversation;
     /** Display depth, min(naturalDepth, 2) (D22). */
     depth: 0 | 1 | 2;
     naturalDepth: number;
     /** Top-level nodes only: every descendant in pre-order, each at its display depth. Empty below the top level. */
     descendants: ConversationTreeNode[];
     /** Parent id when the row has a parent link but the parent is not in `rows` (rendered top level, D6). */
     orphanOf: number | null;
     /** Parent id when naturalDepth > 2 (rendered at depth 2 with a marker, D22). */
     flattenedFrom: number | null;
   }
   /** Nest every row whose parent link names a row in `rows` (lanes and successors alike); cap display depth at 2. */
   export function buildConversationTree(rows: readonly Conversation[]): ConversationTreeNode[]
   export function groupSummary(node: ConversationTreeNode): { lanes: number; successors: number; working: number; needsYou: number; reported: number }
   ```

   Rules:
   - A row nests when `parentConversationId` is non-null and that id is in `rows`; the lane columns play no part in nesting. A row whose parent id is absent is top level with `orphanOf` set.
   - Top-level order (FR-28, D18): `rows` arrives in today's flat order (active then inactive, each sorted). Each top-level node takes the index of its earliest member (itself or any descendant) in `rows`, and top-level nodes sort by that index. An ended predecessor with a live successor therefore sits where the successor would sit.
   - Descendants: pre-order walk of the parent-link tree; siblings live first (the list's `isActive`), then `createdAt` ascending; `depth = min(naturalDepth, 2)`; `flattenedFrom = parentConversationId` when `naturalDepth > 2`.
   - The walk keeps a visited set and never visits a row twice. Parent links always point at older rows, so a cycle cannot occur; the set is a guard.
   - `groupSummary` counts over every descendant: `lanes` (rows with `laneKey`), `successors` (rows without), `working`, `needsYou` (`pendingInputCount > 0`) and `reported` (lanes with `laneReport`).
3. `ConversationList.tsx`:

   ```tsx

   // after
   return buildConversationTree([...active, ...inactive]);
   ```

   The render loop maps top-level nodes. A node with descendants renders its `ConversationRow`, then a toggle line (collapsed `▸`, expanded `▾`) that lists only the non-zero counts from `groupSummary`, in the order `1 successor · 7 lanes · 3 working · 1 needs you · 2 reported` (for example `▸ 1 successor · 1 working` for a plain handoff), then, when expanded, each descendant as `ConversationRow variant="nested"` indented one step per display depth. ## Decisions from the operator (2026-09-26)

1. **Q1, verb name: `pan lane`.** Kept as drafted: `pan lane start|list|wait|report|stop|reap` (D17). `pan gauntlet lane …` is rejected.
2. **Q2, reap archives by default.** `pan lane reap` archives the lane's conversation through the existing archive path (`archiveConversationByName`) after the directory is removed; `--keep` leaves it as an ended row. Recorded in D14, FR-23 and FR-24; `--archive` is gone. Consequences: `GET /api/lanes` and `pan lane list` read archived lanes too (WI-5), and the reap result gains `archived` (WI-7, WI-8).
3. **Q3, handoff and fork nest successors.** D3 is reversed. `pan handoff` and `pan fork`, CLI and dashboard, stamp `parent_conversation_id` on the successor (FR-25, WI-14). Nesting in the Command Deck and the Agents page keys on `parent_conversation_id IS NOT NULL` (FR-26): successors nest under their predecessor, lanes under their orchestrator. Decided in this PRD to make that work:
   - An orchestrator that hands itself off keeps its lanes where they were launched, under the predecessor; the successor nests beside them and shows `continues ← #<id>` (D6, FR-27).
   - Nesting shows at most two levels; deeper rows keep their pre-order place at depth 2 with `↳ continued from #<id>` or `lane of #<id> · <run>` (D22).
   - A group ranks by its best member and opens while any member is active, so a live successor is never buried under its ended predecessor (D18, FR-28).
   - The Agents Live view nests lanes only; a successor keeps its own row there (D23, FR-29). History nests both.
   - A successor of a lane is not a lane, but it keeps its source's standing at the lane door, so a handed-off orchestrator lane still may not launch critics (D21, FR-30).
