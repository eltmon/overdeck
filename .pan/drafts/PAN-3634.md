# PAN-3634 — Flywheel provenance comes from `startedBy`, not the dead `flywheel.active_run_id` setting

**Issue:** [PAN-3634](https://github.com/eltmon/overdeck/issues/3634)
**Planning mode:** `pan plan --auto` (no operator Q&A; decisions recorded below and in `plan.autoDecisions[]`).
**Base commit:** `b6941f3bc98` (main, 2026-09-26).

## Glossary

- **`startedBy`** — the provenance token written into every agent's `~/.overdeck/agents/<id>/state.json` at spawn time. It names the path that launched the agent: `operator:cli:pan-start`, `operator:dashboard`, `planning-auto-handoff`, `resume-agent`, `orphan-proposed-reconciler`, and so on. Launchers also export it into the agent's pane as `OVERDECK_AGENT_STARTED_BY`, so any `pan` command the agent runs inherits it.
- **`flywheelRunId`** — a legacy `AgentState` field (`RUN-<n>`). Spawn code fills it from `getFlywheelActiveRunId()`, which reads the `flywheel.active_run_id` row in `app_settings`. Since the PAN-3917 Cut nothing writes that row, so on the operator's host every spawn inherits a stale value (`RUN-92`).
- **The Flywheel** — the `/pan-flywheel` loop skill running in the single conversation `conv-flywheel` (`FLYWHEEL_CONVERSATION_SESSION` in `src/lib/flywheel/constants.ts`). It launches work by running `pan start <id>` in its own shell. There is no run record and no run id (`docs/FLYWHEEL.md`, line 3).
- **`OVERDECK_CONVERSATION`** — env var exported into every conversation's shell by `spawnConversationSession` (`src/lib/overdeck/conversation-runtime.ts`, search `export OVERDECK_CONVERSATION=`). Inside the Flywheel's shell its value is `conv-flywheel`.
- **Flywheel token** — the new provenance value `flywheel:conv-flywheel` (constant `FLYWHEEL_STARTED_BY`). Any `startedBy` beginning with `flywheel:` is Flywheel provenance; this includes legacy `flywheel:RUN-<n>` values already on disk.
- **Operator-started exemption** — `cloister.concurrency.exempt_operator_started` (default `true`, PAN-1812). When on, the emergency brake (`emergencyBrake()`) and the memory governor's hard-band shed (`selectAgentToPause()`) only stop work agents the Flywheel dispatched. Everything else is exempt.
- **Planning auto-handoff** — when a planning session started with auto-start finalizes, the server posts to `/api/agents` (and on an unhealthy stack, `/api/workspaces/:id/rebuild-and-start`) with `startedBy: 'planning-auto-handoff'` to start the work agent. A guardrail refusal is retried later by the deferred hand-off retry (`src/lib/cloister/deferred-handoff.ts`, PAN-4155).
- **Chain** — one planning session plus the work agent its auto-handoff starts. The **chain originator** is the planning session's `startedBy`.
- **Consent claim** — `spawnRun` (`src/lib/agents/spawn.ts`) and `remote-agents.ts` skip the auto-spawn consent claim when `isOperatorStartedBy(startedBy)` is true. `planning-auto-handoff` is deliberately *not* operator provenance, so the auto-handoff goes through the consent claim.

## Problem

1. `resolveFlywheelSpawnEnv()` (`src/lib/agents/spawn-prep.ts:56-61`) falls back to `getFlywheelActiveRunId()` whenever no run id is passed — and no caller passes one. So every spawn (operator, auto-handoff, recovery) stamps whatever run id the dead `flywheel.active_run_id` setting holds.
2. Both reaping filters treat "has a `flywheelRunId`" as "Flywheel-dispatched":
   - `src/lib/cloister/concurrency.ts:281-285` (`emergencyBrake`)
   - `src/lib/cloister/memory-governor.ts:370-380` (`selectAgentToPause`)
   With the stale `RUN-92` on every agent, the exemption exempts nobody.
3. The Flywheel itself never marks its own launches: `conv-flywheel` does not export `OVERDECK_AGENT_STARTED_BY`, so `pan start` run by the Flywheel resolves `startedBy: operator:cli:pan-start` (`resolveCliStartedBy` in `src/lib/agents/provenance.ts`). Only the ambient run id distinguished them.
4. The auto-handoff always posts `startedBy: 'planning-auto-handoff'`, so even with a correct predicate the work half of a Flywheel chain would lose its Flywheel provenance.

The issue author's 2026-09-26 comment restates the goal: stop reading the dead setting and derive Flywheel provenance from `startedBy` or the `conv-flywheel` spawner.

## Decisions (made here, not deferred)

- **D1 — One provenance signal.** Flywheel provenance is `startedBy` starting with `flywheel:`. `flywheelRunId` is no longer written by any spawn path and no longer read by any reaping filter.
- **D2 — Token.** The Flywheel's shell mints `flywheel:conv-flywheel`. `resolveCliStartedBy` returns it when `OVERDECK_AGENT_STARTED_BY` is unset/blank **and** `OVERDECK_CONVERSATION` (trimmed) equals `conv-flywheel`. Inherited `OVERDECK_AGENT_STARTED_BY` always wins (precedence: inherited → conversation → default).
- **D3 — Predicate.** `isFlywheelStartedBy(startedBy)` is `true` iff `startedBy` (trimmed) starts with `flywheel:`. The exemption rule: with `exempt_operator_started` on, an agent is reapable **iff** `isFlywheelStartedBy(agent.startedBy)`. This preserves today's intent ("everything the Flywheel did not dispatch is exempt"), including `planning-auto-handoff`, `resume-agent`, `orphan-proposed-reconciler` and `dashboard:*`. Do **not** use `isOperatorStartedBy` for the exemption — that would leave `planning-auto-handoff` children reapable, which is the bug.
- **D4 — Handoff inherits only Flywheel provenance.** The auto-handoff (both POSTs in `completePlanningAutoSpawn`) and the deferred retry send `planningHandoffStartedBy(planningState?.startedBy)`: `flywheel:conv-flywheel` when the `planning-<issue>` state's `startedBy` is Flywheel provenance, otherwise the unchanged `planning-auto-handoff`. The handoff never sends the operator token itself, because `isOperatorStartedBy('operator:…')` would skip the consent claim and change auto-handoff behavior (violates the issue's AC3). The Flywheel token is not operator provenance, so the consent claim still runs for Flywheel chains exactly as it does today.
- **D5 — Validator.** `resolveRequestedStartedBy` (`src/dashboard/server/routes/agents/shared.ts:85-100`) accepts `flywheel:conv-flywheel` as an internal token. It keeps accepting legacy `flywheel:RUN-<n>` (panes launched before this change still carry that env).
- **D6 — Keep the persisted field.** `flywheelRunId` stays in `packages/contracts/src/events.ts:253`, `packages/contracts/src/event-reducers.ts:525`, `src/lib/agents/agent-state-read.ts:186,277`, and the agents table. It is inert legacy data: historical events carry it, and `tests/unit/lib/pan-1908-no-loss-audit.test.ts` and `tests/unit/helpers/overdeck-test-db.test.ts` enumerate it. The `activeRunId` member of the `FlywheelRuntime` resolver interface in `control-settings.ts` also stays (interface only, no implementation; `no-loss-matrix.ts` names `getFlywheelRuntime`).
- **D7 — AC2 restated.** The issue body's AC2 says a Flywheel chain "keeps its `flywheelRunId` on both halves". The author's later comment retires run ids, so AC2 becomes: a Flywheel-dispatched chain carries `flywheel:` provenance in both `planning-<issue>` and `agent-<issue>` state, and the work half is selectable by the emergency brake and the governor shed.

## Requirements

- **FR-1** — No spawn path reads `flywheel.active_run_id`; `getFlywheelActiveRunId` is deleted, and no spawn writes `flywheelRunId` into agent state or exports `OVERDECK_FLYWHEEL_RUN_ID` / `OVERDECK_FLYWHEEL_AGENT_ROLE` into a launcher or session env.
- **FR-2** — `pan start` / `pan plan` run from the `conv-flywheel` shell (no inherited `OVERDECK_AGENT_STARTED_BY`) resolve `startedBy: flywheel:conv-flywheel`; run anywhere else they resolve their operator default.
- **FR-3** — The dashboard accepts `flywheel:conv-flywheel` as an internal `startedBy` on `/api/agents`, `/api/workspaces/:id/rebuild-and-start` and `/api/issues/:id/start-planning`, and still accepts legacy `flywheel:RUN-<n>`.
- **FR-4** — With `exempt_operator_started` on, `emergencyBrake()` and `selectAgentToPause()` consider only agents whose `startedBy` starts with `flywheel:`; a stale `flywheelRunId` on an agent has no effect.
- **FR-5** — The planning auto-handoff (both POSTs) sends `flywheel:conv-flywheel` when the planning session's `startedBy` is Flywheel provenance, and `planning-auto-handoff` otherwise.
- **FR-6** — The deferred hand-off retry sends the same `startedBy` the original hand-off would have sent (FR-5 rule).
- **FR-7** — Docs state the provenance rule and the exemption predicate.
- **NFR-1** — Operator-chain auto-handoff behavior is otherwise unchanged: same `startedBy` (`planning-auto-handoff`), same consent claim, same guardrail acknowledgement, same rebuild-and-start fallback.
- **NFR-2** — Tests that touch timers use fake timers (`vi.useFakeTimers()`); the deferred-handoff test already does — keep it that way.

## Hazards

- **H1 — Transient permissiveness.** Agents the Flywheel dispatched before this lands carry `startedBy: operator:cli:pan-start` (nothing ever exported a Flywheel token into `conv-flywheel`), so after deploy they are exempt until they roll over. Correct going forward; no migration.
- **H2 — Env precedence.** Inherited `OVERDECK_AGENT_STARTED_BY` must be checked before `OVERDECK_CONVERSATION`. Every server-side detached `pan start` sets `OVERDECK_AGENT_STARTED_BY` (`routes/agents/spawn.ts` ~785, `routes/workspaces.ts` ~962), so a dashboard process that happens to inherit `OVERDECK_CONVERSATION=conv-flywheel` cannot mislabel its spawns. Flipping the order would.
- **H3 — Typecheck blind spot.** `npm run typecheck` excludes `*.test.ts`. A test still mocking `getFlywheelActiveRunId` or passing `flywheelRunId` only fails under vitest — run every named test file.
- **H4 — Stale in-pane env.** Live panes launched before this change may still export `OVERDECK_FLYWHEEL_RUN_ID`; after WI-1 nothing reads it, so it is harmless.
