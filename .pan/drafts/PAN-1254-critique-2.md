## blocks-the-design: Token protection can be silently removed

The PRD's W-18 guard returns unchanged whenever the incoming `dashboard.require_token_mint` is absent ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-1254/.pan/drafts/PAN-1254.md), lines 332–345). That field is optional in the API type and validation ([settings-api.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-1254/src/lib/settings-api.ts), lines 273–274 and 1334–1343), while the save path writes `dashboard: settings.dashboard` verbatim (line 1050). An older or partial settings payload can therefore remove `require_token_mint: true`; the remote-access reader treats the missing value as false ([config.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-1254/src/lib/remote-access/config.ts), lines 30–42), reopening root-session minting through Serve ([dashboard-auth.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-1254/src/dashboard/server/routes/dashboard-auth.ts), lines 359–372). Even explicit `false` can pass when W-18 consults the three-second cached Tailscale state (PRD line 189) before the new Serve configuration is visible. Smallest change: inside the serialized save, preserve the current persisted `true` value unless a fresh, successful Serve-status read proves this dashboard is no longer forwarded; treat omission like a stale value. Add a save-path test with an omitted `dashboard` field and one with a cached pre-Serve result.

## blocks-the-design: Cached state stops setup after successful steps

W-1 memoizes `readTailscaleState()` for three seconds ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-1254/.pan/drafts/PAN-1254.md), line 189). W-11 immediately rereads `nextStep` after each action and exits 1 if it is unchanged (lines 273–282). A fast successful `serve`/`protect` request, daemon restart, or operator command can leave the cached pre-action step in place, making `pan tailscale setup` report failure even though the action succeeded. The draft's injected state-sequence tests do not exercise the real cache. Smallest change: invalidate the state cache after every local mutation and after the dashboard Serve response, or provide a forced fresh read for post-action checks; test a successful action completed within the cache TTL.

## blocks-the-design: Existing Funnel is mistaken for private Serve

D-8 and W-1 decide Serve is ready solely from the `TCP["443"]` and `Web["<name>:443"].Handlers["/"]` proxy target ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-1254/.pan/drafts/PAN-1254.md), lines 101–103 and 189). Tailscale's [ServeConfig](https://github.com/tailscale/tailscale/blob/main/ipn/serve.go) also has `AllowFunnel` for the same host:port. [Tailscale's Serve documentation](https://tailscale.com/docs/features/tailscale-serve) says Funnel on that port makes it publicly reachable. If Funnel already proxies this dashboard, the proposed parser returns `proxiesDashboard: true`, and W-5 skips the `serve` command as `changed: false` (PRD lines 227–234); setup can claim ready while the URL remains public. Smallest change: parse `AllowFunnel["<name>:443"]`, report a distinct public-Funnel conflict, and refuse to claim `ready` or alter that handler. Add that JSON shape to W-1 and W-5 tests.

## blocks-the-design: Userspace fallback leaves the failed mode active

C-1 says to install and sign in with userspace Tailscale, then stop offering it if the inbound check fails ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-1254/.pan/drafts/PAN-1254.md), line 145). But D-7 always prefers any installed `${OVERDECK_HOME}/tailscale/bin/tailscale` over the system binary (line 91), and W-3's fallback only changes `installPlan()` (lines 202–204). After a failed live check, the trial binaries remain selected, so status, setup, and the userspace route can still use the mode the fallback supposedly disabled. The draft's `ts-install-plan.ac2`, `route-tailscale-status.ac3`, and `pan-tailscale-setup.ac5` also require userspace behavior unconditionally, so a correctly applied C-1 fallback contradicts those acceptance checks. Smallest change: make the fallback govern binary resolution and the userspace action route as well as install plans, and make the affected acceptance checks conditional on C-1 passing; state how a trial installation is handled after failure.
