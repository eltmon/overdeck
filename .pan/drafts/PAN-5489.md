# PAN-5489: Workspace creation fails when the creating process lacks HUME_API_KEY, the error hides the cause, and a retry skips the Hume step

**Issue:** https://github.com/eltmon/overdeck/issues/5489
**Planned:** 2026-11-23 (auto mode, high effort)

## Glossary

- **Hume step**: the part of `createWorkspace` that runs when a project's `workspace.hume` block is set. It clones a Hume EVI config through the Hume API and writes `<workspace>/.hume-config` (`HUME_CONFIG_ID=…`). Code: `src/lib/hume.ts` (`createHumeConfig`) called from `src/lib/workspace-manager/create.ts` line 618.
- **Step lines**: the `steps: string[]` array a setup helper (`createHumeConfig`, `addTunnelIngress`) returns. Each line starts with `[hume]` or `[tunnel]`. `createWorkspace` copies them into `result.steps`.
- **Setup marker** (PAN-4171): the file `<workspace>/.overdeck/setup-incomplete`. `createWorkspace` writes it when the worktree exists and removes it when setup ends. While it exists, every caller re-runs `createWorkspace`, which resumes setup. Code: `src/lib/workspace-manager/setup-marker.ts`.
- **secrets_file**: a project's `workspace.env.secrets_file` in `~/.overdeck/projects.yaml` (an absolute or `~/` dotenv path outside the repo). PAN-5061 reads it with `readProjectSecrets` in `src/lib/projects/launch-env.ts` and gives its keys to that project's agent panes only.
- **`~/.overdeck.env`**: Overdeck's global dotenv file. The CLI loads it at start (`src/cli/index.ts` lines 12-36). The dashboard loads it once at boot (`src/dashboard/server/config.ts` line 69, `loadOverdeckEnv()`).
- **Issue-start routes**: `POST /api/fleet/issues/:id/start` (`src/dashboard/server/routes/fleet-work.ts`, handler `handleFleetIssueStart`, used by the MCP `start_issue` tool) and `POST /api/machines/work/issues/:id/start` (`src/dashboard/server/routes/machines-work.ts`, handler `handleWorkIssueStart`, the linked-machine work door). Both call `spawnIssueAgentForRoute` (`src/dashboard/server/routes/agents/spawn-issue.ts`).
- **`httpHandler`**: the route wrapper in `src/dashboard/server/routes/http-handler.ts` that maps typed errors to HTTP statuses and turns any other failure into a logged `500 {"error": <message>}`.

## Problem — what the evidence shows (corrects the issue's diagnosis)

The issue says the CLI path loads neither `~/.overdeck.env` nor the project's secrets_file. Investigation on 2026-11-23 shows the failure happens elsewhere:

1. **`pan plan` does not create the workspace in the CLI process.** `src/cli/commands/plan.ts` line 39 only POSTs to `/api/issues/:id/start-planning`. The dashboard runs `spawnPlanningSession` (`src/lib/overdeck/planning-sessions.ts` line 480), which calls `createWorkspace` in the dashboard process (`src/lib/planning/spawn-planning-session.ts` line 435). `~/.overdeck/logs/dashboard.log` lines 2547584-2547587 (MIN-1142) and 2613728-2613731 (MIN-1144, 2026-11-23T02:42Z) show the Hume failure inside the dashboard: `[start-planning] Workspace errors: [ 'Hume EVI config setup had failures (see steps for details)' ]`.
2. **The CLI already loads `~/.overdeck.env`** (`src/cli/index.ts` line 14). A "load the env in the CLI" fix would change nothing.
3. **Why the dashboard lacked the key is not determined.** The dashboard reads `~/.overdeck.env` once at boot. `/proc/<pid>/environ` shows only exec-time env, so it cannot show keys `loadOverdeckEnv()` set later. `~/.overdeck.env` was last modified 2026-11-23 00:29, so the key may have been added after an older dashboard booted. The design below makes the outcome independent of the answer.
4. **The step text never reaches anyone.** `create.ts` line 628 pushes `'Hume EVI config setup had failures (see steps for details)'`. The steps are in `result.steps`, which the planning path never prints or logs (`spawn-planning-session.ts` lines 445-450 log only `errors`). The tunnel step has the same message at line 612.
5. **A retry skips the Hume step (issue defect 3, confirmed in code and log).** `create.ts` lines 737-739 always call `clearWorkspaceSetupIncomplete` before returning, even when the Hume step failed. `spawn-planning-session.ts` line 426 then treats the directory as a finished workspace and never calls `createWorkspace` again. `dashboard.log` confirms it: the second `START for MIN-1142` (line 2547630) reaches `SSE complete` (line 2547650) with no `Creating workspace via library` line between them. So the "successful re-run" for MIN-1142 skipped the Hume step, and `.hume-config` stayed absent. Exporting `~/.overdeck.env` in the caller's shell was not what made the re-run succeed.
6. **The MCP `start_issue` 500 (issue comment, 2026-11-22).** `handleFleetIssueStart` (`fleet-work.ts` line 350) returns `Effect<…, unknown, R>` and its route (`fleet-work.ts` lines 524-536) is not wrapped in `httpHandler`. Any failure from `spawnIssueAgentForRoute` therefore reaches the platform's default handler: no log line and a 500 body without an `error` field, which the MCP tool renders as `HTTP 500: request failed` (`src/lib/mcp/tool.ts` line 62). One concrete failure source: `spawn-issue.ts` lines 353-365 wrap `yield* Effect.promise(() => execAsync('pan workspace create …'))` in a JS `try/catch`. A rejected `Effect.promise` is a defect, which a `try/catch` around `yield*` never sees (the file itself explains this at line 861), so a failed `pan workspace create` escapes as an unlogged defect instead of the intended `500 {"error": "Failed to create workspace …"}`. Whether this was the cause of the two MIN-1142 500s is not confirmed; the fix makes the next one log and explain itself.

## Requirements

### Functional

- **FR-1** The Hume step resolves its API key at the moment of use, in this order: (a) `process.env[<api_key_env>]` when non-empty; (b) the project's secrets_file; (c) a fresh read of `~/.overdeck.env`. `<api_key_env>` is `config.api_key_env`, default `HUME_API_KEY`. An empty string counts as absent.
- **FR-2** When no source has the key, the step line names the env var and every source checked, for example `[hume] API key not found: HUME_API_KEY is not set in the process environment, /home/u/.myn/.env or /home/u/.overdeck.env`. It never prints a key value.
- **FR-3** `deleteHumeConfig` uses the same resolver, so workspace removal finds the key the same way.
- **FR-4** When the Hume step fails, the `createWorkspace` error text contains the failing step line(s): `Hume EVI config setup failed: <line>`. The tunnel step's error uses the same format: `Tunnel setup failed: <line(s)>`. The phrase `see steps for details` no longer appears anywhere in `src/`.
- **FR-5** When the Hume step fails, `createWorkspace` keeps the setup marker, so the next `createWorkspace` for that issue resumes setup and runs the Hume step again. Other soft failures (ports, devcontainer render, tunnel, Docker) keep today's behavior and clear the marker.
- **FR-6** `spawnIssueAgentForRoute` returns `500 {"error": "Failed to create workspace for <ID>: <message>", "hint": …}` and logs one `console.error` line when `pan workspace create` fails, instead of escaping as a defect.
- **FR-7** Both issue-start handlers (`handleFleetIssueStart`, `handleWorkIssueStart`) never fail their Effect. Any failure becomes a `500 {"error": <message>}` response and a server-side `console.error` line.
- **FR-8** `httpHandler` logs a `console.error` line for the two typed errors it maps to 500 (`WorkspaceCreateError`, `AgentStartError`), in addition to returning their message.

### Non-functional

- **NFR-1** The resolver never writes to `process.env`. The dashboard process launches every project's agents, so writing one project's secrets into it would leak them to other projects (PAN-5061 D-7). The key is passed as a value.
- **NFR-2** No synchronous filesystem or child-process calls in the new code; `hume.ts` and `create.ts` are reachable from the dashboard server (repo rule: no `execSync`/blocking calls in server-reachable code). Use `node:fs/promises`.
- **NFR-3** No log line, error, or step line contains a secret value. Name keys and file paths only.
- **NFR-4** No touched file grows past its file-size ceiling (1000 lines, `scripts/lint-file-size.sh` line 39). `spawn-issue.ts` is at 955 lines, so the FR-6 logic goes in a new module.

## Decisions (made here; the executor does not revisit them)

- **D1 — Point-of-use resolution, not a CLI env load.** The failing process is the dashboard. Resolving at use time also covers a dashboard that booted before the key was added to `~/.overdeck.env`.
- **D2 — Order is process env → secrets_file → `~/.overdeck.env`.** An explicit value in the running process (operator export, or what the dashboard loaded at boot) wins; the project's own file comes before the global file because it is project-specific.
- **D3 — Only a Hume failure keeps the setup marker.** The Hume step is idempotent (it reuses a config with the same name, `hume.ts` lines 84-95), and its output (`.hume-config`) is what a retry must produce. Keeping the marker for every soft failure would make a persistently broken port range or devcontainer warning fail every later start. This revises the PAN-4171 rule in `docs/WORKSPACES-AND-PROJECTS.md` lines 586-589 for Hume only.
- **D4 — Failing step lines** are the step lines that contain `failed` or `not found` (case-insensitive); if none match, the last step line. Joined with `; `.
- **D5 — Tunnel error text is fixed too** (same message, same file, same helper). The tunnel marker behavior does not change.
- **D6 — The issue-start handlers wrap themselves in `httpHandler`** inside the exported function, so the existing direct-call tests (`fleet-workers.test.ts`, `fleet-connector.test.ts`) can assert the 500 mapping without building a router.
- **D7 — Existing workspaces already left without `.hume-config` and without a marker are not repaired** by this change (NonGoal). The operator re-creates such a workspace.

   ```ts
   /** PAN-5489: the step lines that explain a failed setup step (D4). */
   export function failingStepLines(steps: readonly string[]): string {
     const failed = steps.filter((line) => /\b(failed|not found)\b/i.test(line));
     const lines = failed.length > 0 ? failed : steps.slice(-1);
     return lines.join('; ');
   ```
