# PAN-4881 — Make `projects-rename.test.ts` hermetic against leaked internal-token state

**Issue:** [PAN-4881](https://github.com/eltmon/overdeck/issues/4881)
**Planned:** 2026-11-03 (auto mode, high effort)
**Base commit:** `ddb75ed0651`

## Glossary

- **Internal token** — the shared secret that authorizes server-internal and CLI calls to the dashboard. Sent in the `x-overdeck-internal-token` header (`INTERNAL_TOKEN_HEADER`). Resolved by `getInternalToken()` in `src/lib/internal-token.ts`.
- **Token file** — `<OVERDECK_HOME>/internal-token`. Since PAN-4628 the token file **wins over** the `OVERDECK_INTERNAL_TOKEN` env var: env is read only when no file exists.
- **Token cache** — the module-level `cached` variable in `src/lib/internal-token.ts`. `_resetInternalTokenCacheForTests()` clears it. Resetting the cache does **not** delete the token file.
- **Worker home** — the per-pool-slot Overdeck home that `tests/setup/overdeck-home.ts` assigns: `<OVERDECK_TEST_HOME_ROOT>/worker-<VITEST_POOL_ID>`. `tests/global-setup.ts` creates one `OVERDECK_TEST_HOME_ROOT` per vitest run, so **every test file that runs in the same pool slot shares the same worker home directory**. Files persist there between test files.
- **Leaker** — any test file that, directly or through production code (`ensureInternalToken()` in CLI commands, `agent-runtime.ts`, `deacon-event-client.ts`, …), writes `<worker home>/internal-token` and does not delete it.
- **Setup file** — a file in `vitest.config.ts` `test.setupFiles`. Vitest runs each setup file once **before each test file**, before the test file's imports.
- **Repro config** — a throwaway vitest config (recipe in "Verification recipe") that drops `globalSetup` so the caller can pre-seed a worker home.

## Problem

The v0.73.1 Release workflow (run 41582696575, job `npm`, step "Test (full suite — gate the release)") failed: 8 tests in `src/dashboard/server/routes/__tests__/projects-rename.test.ts` got `401 {"error":"unauthorized"}`. The same commit passed sharded main CI. Nothing was published; re-running the release job is the instance recovery.

### Root cause (verified)

1. The test mocks only the `paths.js` **constants** `OVERDECK_HOME` and `CONFIG_DIR` (lines 14–21, `OVERDECK_HOME: TEST_HOME,`). It spreads `...real`, so `getOverdeckHome()` stays real.
2. `src/lib/internal-token.ts` resolves the token file with `join(getOverdeckHome(), TOKEN_FILE_NAME)` (`function tokenFilePath()`). `getOverdeckHome()` (`src/lib/paths.ts` line 9, `return process.env.OVERDECK_HOME || getCanonicalOverdeckHome();`) reads the env var at call time. That env var is the **worker home**, not `TEST_HOME`.
3. The test's `beforeEach` (line 69) sets `process.env['OVERDECK_INTERNAL_TOKEN'] = INTERNAL_TOKEN` and resets the cache, but never deletes `<worker home>/internal-token`. Its `afterEach` (line 78) deletes `TEST_HOME`, which never held the token file.
4. When a leaker ran earlier in the same pool slot, `<worker home>/internal-token` holds a different token. `getInternalToken()` reads the file first, so the env token is ignored.
5. The route `POST /api/projects/:projectKey/rename` (`src/dashboard/server/routes/project-rename.ts` line 22, `const authError = rejectUnsafeDashboardMutationRequest(request);`) authenticates through `rejectUnsafeDashboardMutationRequest` (`src/dashboard/server/routes/dashboard-auth.ts` line 247) → `rejectUnauthorizedDashboardRequest` (line 452) → `getInternalToken()`. The header `projects-rename-test-token` does not match the file token, so the route returns 401.
6. Sharded CI and the single-job release run assign files to pool slots differently, so the failure appears only when a leaker happens to precede this file in the same slot. CI's `retry: 1` does not help: the stale file survives the retry.

### Empirical reproduction (done during planning)

Seeding `stale-token` into `<root>/worker-0/internal-token` and `<root>/worker-1/internal-token`, then running only `projects-rename.test.ts` with the repro config and `--maxWorkers=1`, produced exactly the release failure: **8 failed, 1 passed**, every failure `expected { status: 401, … } to deeply equal { status: 200 | 400 | 404 | 409, … }`. The one passing test is the unauthorized-request test.

### The established local fix pattern

34 sibling test files already guard against this. Example, `src/dashboard/server/routes/__tests__/issues-reopen.test.ts` lines 164–168:

```ts
    process.env.OVERDECK_INTERNAL_TOKEN = 'test-token';
    delete process.env.OVERDECK_TRUSTED_ORIGINS;
    // The token file wins over env (PAN-4628); delete any file a sibling
    // test in this worker's shared OVERDECK_HOME left behind.
    rmSync(join(getOverdeckHome(), 'internal-token'), { force: true });
    _resetInternalTokenCacheForTests();
```

`projects-rename.test.ts` is missing this line. The class of bug stays open for every future route test that forgets it, because nothing clears the worker home between test files.

## Requirements

- **FR-1** — `projects-rename.test.ts` deletes `join(getOverdeckHome(), 'internal-token')` before each test, before it resets the token cache, so its env token is the one the route sees.
- **FR-2** — `projects-rename.test.ts` deletes `join(getOverdeckHome(), 'internal-token')` after each test, so this file never leaks a token file to the next file in its pool slot.
- **FR-3** — `projects-rename.test.ts` contains a regression test that writes a stale token file into the worker home, re-applies the per-test token setup, and asserts the rename route returns 200 with the test token.
- **FR-4** — `tests/setup/overdeck-home.ts` deletes `<worker home>/internal-token` every time it runs (once per test file), so no test file can inherit a token file from an earlier file in the same pool slot.
- **FR-5** — `docs/TESTING.md` documents the shared worker home, the token-file-wins rule, the setup-file guard, and the per-test cleanup idiom for route tests that authenticate with an env token.
- **FR-6** — `tests/unit/cli/serve.test.ts` and `tests/lib/work-agent-lifecycle.test.ts`, the two leakers the planning hunt found, delete the worker-home token file (`tokenFilePath()` in serve, `join(getOverdeckHome(), 'internal-token')` in lifecycle) in their `afterEach`, so each leaves no token file in its worker home.
- **NFR-1** — No production code under `src/` (outside `__tests__/`) changes. `src/lib/internal-token.ts` resolution order (file first, then env) is unchanged.
- **NFR-2** — The fix follows the existing sibling idiom (`rmSync(join(getOverdeckHome(), 'internal-token'), { force: true })`); no new shared test helper module is introduced.
- **NFR-3** — No new `skipIf`, `.only`, or source-grepping test is added (the test-skip and lint gates reject them).

## Decisions (made here, auto mode)

1. **Delete the token file in the worker home; do not repoint `OVERDECK_HOME` at `TEST_HOME`.** The issue suggests "point any home or token-file directory at a per-test temporary directory." Setting `process.env.OVERDECK_HOME = TEST_HOME` per test would work, but it differs from all 34 sibling files and widens the env surface: modules that captured the `OVERDECK_HOME` constant at import would disagree with `getOverdeckHome()`. The sibling idiom is proven and minimal.
2. **Close the leak class in the setup file, and also fix the two leakers the hunt found.** The issue says "If another file is leaking token state, fix that file too." Leakers are hard to enumerate completely: production paths that call `ensureInternalToken()` (CLI `plan`, `merge`, `start`, `dashboard-call`, `machines-fly`, `admin/conversations-handler`, `agent-runtime.ts`, `deacon-event-client.ts`) run in many tests, and tests that spawn `dist/cli/index.js` inherit the worker `OVERDECK_HOME` and are invisible to source grep. Clearing `<worker home>/internal-token` at the start of every test file (WI-2) closes the whole class. The two leakers the planning hunt proved (see "Leaker hunt") also get a one-line `afterEach` cleanup (WI-4, WI-5), so they clean up after themselves as the issue asks. The hunt is not exhaustive; WI-2 is what covers the rest.
3. **Keep the 34 hand-rolled per-file guards.** They become partly redundant after FR-4 but still protect against same-file leaks. Removing them is out of scope (surgical-changes rule).
4. **The setup guard runs at setup-file top level, not in a `beforeAll`/`beforeEach` hook.** Top level runs before the test file's imports, so a test file that seeds a token file at import time or in its own hooks keeps it. A global `beforeEach` would delete files that test files seed in `beforeAll`.
5. **"Full single-job run" verification.** The repo rule forbids running the full `npm test` on the host. The host-side proof is the seeded repro (deterministic, same failure shape). The full single-job confirmation is the next Release workflow run on CI, which is outside this issue's diff.
