## blocks-the-design: A lost first poll can discard an approval

WI-3 says `registered` becomes true only after an `ok` poll and yields without withdrawing while it is false ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4888/.pan/drafts/PAN-4888.md), lines 295–308). The server registers the request synchronously in `upsertRestartRequest` ([restart-gate.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4888/src/dashboard/server/services/restart-gate.ts), lines 192–239), while `gatePost` can report `unavailable` if the response is lost or cannot be parsed ([restart-gate-client.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4888/src/lib/restart-gate-client.ts), lines 121–142). Sequence: the first poll registers, its response is lost, the operator approves, then a marker arrives. `registered` is still false, so the holder discards that approval and exits. Track whether any registration *attempt* was sent; allow a direct yield only before the first attempt. Add a lost-response-then-approval test.

## blocks-the-design: Failed withdraw is treated as permission to yield

WI-3 maps a 404 or unavailable withdraw response to `superseded` ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4888/.pan/drafts/PAN-4888.md), lines 264–277 and 299–309, 325). `gatePost` returns `unavailable` after a timeout or response failure even if the server handled the request ([restart-gate-client.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4888/src/lib/restart-gate-client.ts), lines 127–142). The current server has the gate routes but no withdraw route ([routes/restart-gate.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4888/src/dashboard/server/routes/restart-gate.ts), lines 40–117), so 404 also does not prove that no approval exists. An approval can be accepted, withdraw can fail or answer 404, and the holder then exits without claiming it. After a registration attempt, step aside only on an explicit `{ withdrawn: true }` response. Keep polling or fail closed on 404/unavailable, and replace the test that expects a 404 to supersede.

## blocks-the-design: Unreadable health can delete a live generation

WI-6 returns `null` on a health timeout or exception, then rolls back `dist/` and removes the generation whenever the result differs from `builtSha` ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4888/.pan/drafts/PAN-4888.md), lines 472–483 and 488–516). A dashboard starting from that generation may not answer `/api/health` during the 3-second read. The existing `liveDashboardDeploymentRoots` already detects processes running from each generation ([build-from-origin.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4888/src/lib/deploy/build-from-origin.ts), lines 198–270), while `removeDashboardDeployment` removes the directory even when `git worktree remove` fails (lines 306–316). Treat an indeterminate health read as indeterminate: check live occupants or wait for a definite result, and never remove a generation that may be running. Add a test where health times out while the generation has a live dashboard process.

## blocks-the-design: A PID-only marker can address a different process

WI-2 keys marker ownership to `byPid`, targets only `targetPid`, and accepts a marker when `process.kill(byPid, 0)` says some process with that PID exists ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4888/.pan/drafts/PAN-4888.md), lines 173–190 and 211–222). The 30-second freshness window does not distinguish a dead process from a new process that reused its PID. The holder may therefore withdraw its request and discard its build although no newcomer is waiting. A reused holder PID can also receive a marker intended for the previous holder. Include a stable per-invocation identity in the marker and lock record, and validate both process identities before yielding; test PID reuse within the freshness window.
