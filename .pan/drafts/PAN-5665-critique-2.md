## blocks-the-design: Queued prompts can enter the replacement run

The proposed `resetForNewRun` only removes `optimistic` bubbles and changes held-offline outbox entries (`.pan/drafts/PAN-5665.md`, lines 90-103). A prompt already queued by `ComposerFooter.tsx`, lines 578-597, remains in the name-keyed queue in `src/dashboard/frontend/src/lib/composerSendQueue.ts`, lines 14-24. Once an earlier send settles, `deliverQueuedPrompt` checks only `consumeCancelledSend(clientMessageId)` and then POSTs to the reused conversation name (`src/dashboard/frontend/src/components/chat/queuedPromptSend.ts`, lines 26-39). Clearing its bubble does not put its ID in `cancelledSendIds`. Thus a prompt submitted to old run A can be sent to new run B after the cache claim. Smallest change: when replacing a known run, cancel every queued old-run prompt before dropping its bubble, and add a test with a blocked first send, a queued second send, a run switch, then release of the first send; the second prompt must never POST to B.

## blocks-the-design: Late command results repopulate the new timeline

The reset clears `commandResults` only at claim time (`.pan/drafts/PAN-5665.md`, lines 93-100). An in-flight `/pan` command retains its async continuation across panel unmount: `ComposerFooter.tsx`, lines 600-624, awaits `sendConversationMessage` and then calls `addCommandResult(submitConversationName, ...)` without checking the run. The new panel reads that same name-keyed array and appends it to visible messages (`ConversationPanel.tsx`, lines 610-628). A response arriving after the claim therefore puts old-run content in B's timeline, contrary to FR-1. Smallest change: bind pending command results to the originating run and discard their result when that run is replaced; test a deferred `/pan` response resolved after the run switch.

## blocks-the-design: First claim can preserve an old held prompt

D5 expressly keeps composer state when the per-QueryClient owner is unknown (`.pan/drafts/PAN-5665.md`, lines 50-56; WI-1, lines 132-149). The composer store is a process singleton keyed by conversation name (`src/dashboard/frontend/src/lib/composerStore.ts`, lines 299-300, 463), and `holdSend` stores a prompt with `heldOffline: true` (lines 798-811). The delivery hook automatically flushes held prompts by name when the connection is live, including prompts held while its panel was unmounted (`src/dashboard/frontend/src/components/chat/useComposerDeliveryState.ts`, lines 121-135). Reproduction path: hold a prompt in the Command Deck on run A, leave that view, start B through the CLI while the browser is disconnected, then open the Flywheel pane for the first time and reconnect. Its first claim preserves A's held prompt; the new panel sends it to B. Smallest change: on an unknown first owner, cancel held prompts unless their run can be proved to match the fetched row; add a first-claim test with preexisting held state and a new row.
