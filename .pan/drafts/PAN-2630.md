# PAN-2630: Put `pan` on PATH for spawned agents and source-checkout operators

**Issue:** https://github.com/eltmon/overdeck/issues/2630
**Status:** planned (auto mode, 2026-11-05)
**Verified against:** `feature/pan-2630` at `df325e4cb3f` (v0.74.0)

## Glossary

- **`pan` shim** — a two-line `/bin/sh` script named `pan` (and an identical one named `overdeck`)
  that runs `exec '<node>' '<packageRoot>/dist/cli/index.js' "$@"`. The node path and package root
  are absolute paths baked in when the shim is rendered. It is not a symlink.
- **Shim directory** — `<OVERDECK_HOME>/cli-bin/` (default `~/.overdeck/cli-bin/`). It holds only
  the `pan` and `overdeck` shims. The path is resolved with `getOverdeckHome()` at render time and
  baked into launchers as a literal.
- **Launcher** — the `launcher.sh` bash script that `generateLauncherScript()`
  (`src/lib/launcher-generator.ts`) produces for every agent, conversation, planner, recovery and
  runtime launch. It sets env, then runs the harness (Claude Code, Codex, Pi, Kimi, ACP, Muse).
- **Harness PATH line** — the `export PATH='<dir of harness binary>':"$PATH"` line built by
  `harnessPathExport()` (`src/lib/harness-binary.ts`, line 309) and passed to the generator in
  `extraEnvExports`.
- **Generating process** — the Node process that calls `generateLauncherScript()`. Usually the
  dashboard server, which runs from the live `pan reload` deployment generation
  (`~/.overdeck/deployments/dashboard/.pan-reload-generation-{a,b}`). `pan start` run from a shell is
  also a generating process.
- **Source checkout** — a `git clone` of `eltmon/overdeck` built with `bun install && npm run build`,
  as opposed to `npm install -g @overdeck/core` or the curl installer (`scripts/install.sh`).
- **Remote launcher** — a launcher with `spawnMode: 'remote'` that runs on a Fly VM.

## Problem

On a source-checkout machine nothing puts `pan` on PATH:

1. **Operators.** `package.json` declares `"bin": { "overdeck": "./dist/cli/index.js", "pan": "./dist/cli/index.js" }`,
   but only `npm install -g` / `npm link` create the global link. `scripts/postinstall.mjs` copies
   hooks into `~/.overdeck/bin` and nothing else. `pan install` (`src/cli/commands/install.ts`)
   never links `pan`. `src/lib/deploy/global-cli-link.ts` (PAN-3538) only repoints a link that
   already exists; with none it returns `{ status: 'absent' }`.
2. **Agents.** `src/lib/agents/spawn.ts` lines 405–409 add only the harness PATH line, plus
   `$HOME/.overdeck/bin` for the knowledge role, and that directory holds no `pan`:
   ```ts
   const extraEnvExports = [harnessLaunch.pathExport, ...(options.extraEnvExports ?? [])];
   if (role === 'knowledge' && !extraEnvExports.includes('export PATH="$HOME/.overdeck/bin:$PATH"')) {
   ```
   The conversation launcher (`src/lib/overdeck/conversation-runtime.ts`, around line 807) adds only
   the gh shim. Agents whose PATH lacks `pan` cannot run `pan done`, `pan task done` or `pan doctor`
   from their shell. The `overdeck` MCP server (PAN-4927) covers some verbs, but not every one.
3. **Doctor.** `pan doctor` has no "is `pan` on PATH" check. `describeCliGenerationDrift()`
   (`global-cli-link.ts`, line 133: `return { ok: true, message: 'no global CLI link on this machine' };`)
   reports OK in exactly this case. And the operator cannot run `pan doctor` anyway, since `pan` is
   the missing command.

The dashboard server itself no longer needs `pan` on PATH: `src/lib/pan-cli-invocation.ts`
(`panCliInvocation()`, lines 17–26) runs `process.execPath` with `<packageRoot>/dist/cli/index.js`.
This plan reuses that function to render the shim.

## Decisions

- **D-1. Exec shim, not a symlink.** A symlink to `dist/cli/index.js` runs through its
  `#!/usr/bin/env node` shebang, so it picks whatever `node` is first on PATH, which can be missing
  or older than Node 22. The shim calls the generating process's own node by absolute path.
- **D-2. One shared shim directory, `<OVERDECK_HOME>/cli-bin`.** This is the operator's proposed
  fix (issue comment, 2026-11-05). It also gives operators a stable directory to add to their own
  PATH. Per-agent directories were rejected: they need an id that some launchers lack, and they
  give operators nothing.
- **D-3. Every launcher re-writes the shim at launch time.** The launcher writes it with bash, from
  content rendered by the generating process. Normally that is the dashboard server, so the shim
  follows the live reload generation. Resume and recovery launchers re-assert it. No launch
  depends on `pan install` or `pan sync` having run first.
- **D-4. The shim directory goes first on PATH.** The launcher prepends it after all
  `extraEnvExports` lines (which include the harness PATH line), so it ends up in front of the
  harness binary's directory. On nvm machines that directory also holds the global `pan` link. Agents
  therefore run the same CLI build as the process that launched them, which also removes
  PAN-3538-style drift for agents. The shim directory holds only `pan` and `overdeck`, so it shadows
  nothing else.
- **D-5. Atomic, best-effort writes.** Bash writes `pan.tmp.$$`, runs `chmod 0755`, then `mv -f`
  into place, so a parallel launch never runs a half-written file. The block runs only when
  `<packageRoot>/dist/cli/index.js` exists, and the PATH export runs only when the writes succeed.
  The block never aborts the launcher.
- **D-6. Electron.** In the desktop app the server's `process.execPath` is the Electron binary
  (`apps/desktop/src/server.ts`, lines 96–99, PAN-2559). A shim that execs Electron without
  `ELECTRON_RUN_AS_NODE=1` relaunches the desktop app. When `process.versions.electron` is set at
  render time, or when the generating process has `ELECTRON_RUN_AS_NODE=1` in its env (the desktop
  server is started with it), the shim adds `export ELECTRON_RUN_AS_NODE=1` before `exec`.
- **D-7. Remote launchers are unchanged.** Fly VMs have their own install, and the host's paths are
  invalid there. The generator skips the shim when `spawnMode === 'remote'`.
- **D-8. Doctor warns; it does not fix.** The new check has status `warn` (agents no longer depend
  on it) and lists three remedies. There is no `pan doctor --fix`, and nothing edits shell rc files.
- **D-9. `pan install` and `pan sync` also write the shim**, through the same TypeScript writer, so
  an operator who adds `~/.overdeck/cli-bin` to PATH has a working `pan` before any agent launches.
  `pan install` also prints the PATH line when `pan` is not on PATH.
- **D-10. Last writer wins.** If `pan sync` runs from an `npm link`ed dev checkout, the shim points
  at that checkout until the next launch from the dashboard rewrites it. This is accepted: the
  launch-time rewrite (D-3) is the authority.
- **D-11. The postinstall hint applies only to source checkouts.** `scripts/postinstall.mjs` prints
  one hint line when `<PACKAGE_ROOT>/src` exists (the same dev-mode signal as `isDevMode()` in
  `src/lib/paths.ts`, line 301) and no `pan` is on PATH. Published installs do not ship `src/`, so
  `npm install -g` never prints it.

## Requirements

- **FR-1** Every non-remote launcher writes `<OVERDECK_HOME>/cli-bin/pan` and `.../overdeck`. Each
  is a shim that execs the generating process's `process.execPath` with
  `<packageRoot>/dist/cli/index.js` and forwards `"$@"`. The launcher then prepends the shim
  directory to PATH after every `extraEnvExports` line.
- **FR-2** Shim writes are atomic (temp file plus `mv -f`) and best-effort. If the CLI bundle is
  missing or a write fails, the launcher skips the PATH export and does not exit.
- **FR-3** When `process.versions.electron` is set at render time, the shim exports
  `ELECTRON_RUN_AS_NODE=1` before `exec`.
- **FR-4** `pan install` writes the shims and prints the shim directory. When no `pan` is on PATH it
  prints `export PATH="<shim dir>:$PATH"` as the line to add to the shell profile.
- **FR-5** `pan sync` writes the shims (but not with `--dry-run`) and reports the result in one line.
- **FR-6** `pan doctor` shows a `pan on PATH` row. It is `ok` with the resolved path when `pan` is
  found, and `warn` with the three remedies when it is not.
- **FR-7** `scripts/postinstall.mjs` prints a one-line hint in a source checkout when `pan` is not on
  PATH.
- **FR-8** The docs cover source-checkout install steps, the `pan: command not found` bootstrap, and
  the launcher PATH line.
- **NFR-1** `src/lib/launcher-generator.ts` stays at or under 1000 lines (it is 997 now, and its
  file-size cap is the 1000-line ceiling). `src/lib/agents/spawn.ts` (1088 lines, cap 1089) is not
  touched.
- **NFR-2** The doctor check and the shim module spawn no child processes and call no `execSync`.
  PATH lookup is a pure scan of `PATH` segments with injectable fs deps.
- **NFR-3** Shim content and the shim directory are baked as absolute literals at render time. The
  shim never reads `$HOME` or `$OVERDECK_HOME` when it runs.
- **NFR-4** Remote launchers (`spawnMode: 'remote'`) produce the same script as before.

Exports:

```ts
export interface PanCliShimRuntime {
  nodePath?: string;            // default process.execPath (via panCliInvocation)
  root?: string;                // default packageRoot (via panCliInvocation)
  electron?: boolean;           // default Boolean(process.versions.electron) || process.env.ELECTRON_RUN_AS_NODE === '1'
  dir?: string;                 // default panCliShimDir()
}

/** `<OVERDECK_HOME>/cli-bin`, read at call time so OVERDECK_HOME overrides apply. */
export function panCliShimDir(): string;

/** Absolute path of the CLI bundle the shim execs: panCliInvocation([]).args[0]. */
export function panCliBundlePath(runtime?: PanCliShimRuntime): string;

/** Shim file content. Exactly:
 *  #!/bin/sh
 *  [export ELECTRON_RUN_AS_NODE=1]        ← only when electron
 *  exec '<node>' '<bundle>' "$@"
 *  (paths quoted with shellQuote) */
export function renderPanCliShim(runtime?: PanCliShimRuntime): string;

/** Bash lines for the launcher (see snippet below). */
export function panCliShimLauncherLines(runtime?: PanCliShimRuntime): string[];

/** Async atomic write of `pan` and `overdeck` (writeFile tmp with mode 0o755, then rename).
 *  Returns { status: 'written', dir } | { status: 'missing-bundle', bundle } | { status: 'error', message }.
 *  Never throws. */
export async function writePanCliShims(runtime?: PanCliShimRuntime): Promise<PanCliShimWriteResult>;

/** First executable `name` on `pathEnv` (pure scan; deps injectable). Returns absolute path or null. */
export function findExecutableOnPath(
  name: string,
  pathEnv: string | undefined,
  deps?: { isExecutableFile?: (path: string) => boolean },
): string | null;
```

`findExecutableOnPath` splits `pathEnv` on `:`, skips empty segments, and returns the first
`join(segment, name)` for which `isExecutableFile` is true. The default implementation is
`statSync(p).isFile()` plus `accessSync(p, constants.X_OK)` inside a try/catch. This is CLI-only
synchronous fs (no child process), which NFR-2 allows.

Launcher lines (`panCliShimLauncherLines`). Paths are `shellQuote`d literals. The heredoc delimiter
is quoted, so the shim body is not expanded. This exact shape (a quoted heredoc inside the `if`
condition list, `then` after the delimiter) was verified in bash on 2026-11-05: it resolves `pan` to
the shim, forwards `"b c"` as one argument, leaves no `*.tmp.*` file, and with a missing bundle exits
0 without touching PATH. Keep this shape; do not restructure it:

```bash
if [ -f '<bundle>' ] && mkdir -p '<dir>' 2>/dev/null \
  && cat > '<dir>'/pan.tmp.$$ <<'OVERDECK_PAN_SHIM'
#!/bin/sh
exec '<node>' '<bundle>' "$@"
OVERDECK_PAN_SHIM
then
  if chmod 0755 '<dir>'/pan.tmp.$$ && cp -p '<dir>'/pan.tmp.$$ '<dir>'/overdeck.tmp.$$ \
    && mv -f '<dir>'/overdeck.tmp.$$ '<dir>'/overdeck && mv -f '<dir>'/pan.tmp.$$ '<dir>'/pan; then
    export PATH='<dir>':"$PATH"
  fi
  rm -f '<dir>'/pan.tmp.$$ '<dir>'/overdeck.tmp.$$ 2>/dev/null
fi
```

The exact formatting is the implementer's choice, but it must keep these properties: (a) the shim
body comes from `renderPanCliShim()` and is not hand-written a second time; (b) temp files use
`$$` and are removed on every path; (c) a failure anywhere skips the PATH export and leaves the
launcher's exit status untouched (no `set -e` interaction: the block is a compound `if`).

## Repo rules that apply

- **No `execSync` in dashboard-reachable code.** `pan-cli-shim.ts` is reachable from the server
  (through the launcher generator). Its launcher-line builder is pure string work, and
  `writePanCliShims()` is async `fs/promises`. Only `findExecutableOnPath` uses sync `statSync`/`accessSync`,
  and it has CLI-only callers.
- **File-size ratchet** (`scripts/lint-file-size.sh`): `launcher-generator.ts` may grow by at most 3
  lines. Never raise an allowlist cap.
- **New tests must not read source files** and must not add `skipIf`/`.only` (lint and the test-skip
  gate).
- **Quality gates:** `npm run typecheck`, `npm run lint`, and `npx vitest run <touched test files>`.
  Never run the full `npm test`.
- **Commits** carry an `Item: <item-id>` trailer, one per xBRIEF item.

## Non-goals

- No `pan doctor --fix` and no automatic `npm link` or `npm install -g`.
- No edits to operator shell rc or profile files (the curl installer `scripts/install.sh` already
  does that for npm installs).
- No change to `global-cli-link.ts` repoint semantics (PAN-3538).
- Remote (Fly) launchers are unchanged.
- The knowledge-role `$HOME/.overdeck/bin` PATH line in `spawn.ts` is unchanged.
- The packaged desktop layout, where `<packageRoot>/dist/cli/index.js` may not exist, gets no shim
  (the `[ -f ]` guard covers it). Making `pan` work for packaged desktop users is out of scope.
