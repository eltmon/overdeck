# PAN-4464 — One-click Linear MCP auth banner

**Issue:** [PAN-4464](https://github.com/eltmon/overdeck/issues/4464)
**Planned at:** `900462b4444` (main), 2026-10-01. Auto-planned (`pan plan --auto`).

## Problem

Operator report (2026-10-01): "This should not be so complicated. I should be able to simply click on
something to fix the issue." / "It won't even let me click the conversation."

The Linear MCP auth banner, for an expired link, shows:

1. The blocked agent as `conv-20261001-eba1`, plain text, with no title. The conversation is
   "Fernkite: hosted Emma assessment" at `/conv/3172`.
2. "This authorization link expired — it refreshes automatically when a blocked agent generates a
   fresh one", with no way to make that happen. The operator's orchestrator had to `pan tell` the
   blocked conversation to retry its Linear call.
3. A "Paste the localhost callback URL here" field as the primary action. That step is only needed
   when the browser runs on a different machine from the agent.

## Glossary

- **Intervention / lifecycle** — the folded state of `linear_mcp_auth.*` domain events in
  `src/lib/linear-mcp-auth.ts`. One lifecycle is open from the first `linear_mcp_auth.required` event
  until a `linear_mcp_auth.healthy` event closes it. `GET /api/linear-mcp-auth` serves its projection:
  `{ status: 'none'|'active'|'expired', authUrl, authUrlAgentId, authUrlExpiresAt, declaredAt, blockedAgents[] }`.
- **Owner** — `authUrlAgentId`: the blocked agent whose `mcp__linear__authenticate` call produced the
  current `authUrl`. Claude Code starts a localhost OAuth callback listener *inside that agent's
  process*, so only the owner can finish a same-machine OAuth flow.
- **Same-machine flow** — the browser runs on the agent's host. Linear redirects to
  `http://localhost:<port>/callback`, the owner's listener receives it, and Claude Code stores the token
  with no paste.
- **Remote flow** — the browser runs elsewhere. The redirect to `localhost` fails in that browser; the
  operator pastes the callback URL into the banner, which relays it to the owner
  (`POST /api/linear-mcp-auth/callback`, existing).
- **Marker** — `${OVERDECK_HOME}/agents/<agentId>/linear-mcp-auth-pending`, touched by the hook
  `sync-sources/hooks/linear-mcp-auth-hook` whenever it emits `required`. The hook emits `healthy` only
  when a `mcp__linear__*` call returns cleanly **and** the marker exists.
- **Wake pass** — `processLinearMcpAuthWake()` in `src/lib/linear-mcp-auth.ts`. When a lifecycle
  closes it messages **every** blocked agent in it (`LINEAR_MCP_AUTH_WAKE_COPY`).
- **Refresh request** — new: the server messages one blocked agent to call `mcp__linear__authenticate`
  once, which makes the hook emit a `required` event with a fresh `authUrl`.
- **Verify request** — new: the server messages the owner to make one lightweight Linear read, so the
  hook emits `healthy` and the lifecycle closes.
- **Loopback host** — a dashboard hostname that resolves to this machine: `localhost`, any
  `*.localhost` (the Traefik dashboard is `overdeck.localhost`), `127.0.0.0/8`, `::1` / `[::1]`.
- **Delivery door** — `messageAgent()` in `src/lib/agents/messaging.ts`; returns
  `MessageDeliveryOutcome { delivered, queuedToMail, reason?, ... }`. Never raw tmux keystrokes.

## Findings (verified against the code at `900462b4444`)

### F1 — Why the conversation is not clickable

`src/dashboard/server/routes/linear-mcp-auth.ts`, `withConversationUrls` (line 85), resolves:

```ts
const conversation = getConversationByName(agent.agentId);   // line 94
```

The blocked agent id is the conversation's **tmux session** name. The live row for `/conv/3172` is
`{ rowid: 3172, name: '20261001-eba1', tmux_session: 'conv-20261001-eba1', title: 'Fernkite: hosted Emma assessment' }`.
`getConversationByName('conv-20261001-eba1')` matches `c.name = 'conv-20261001-eba1'`, which never
exists, so `conversationUrl` is always `null` and the banner renders plain text
(`LinearMcpAuthBanner.tsx` lines 107–113). The right lookup already exists:
`getConversationByTmuxSession(tmuxSession)` in `src/lib/overdeck/conversations.ts` (line 638) strips the
`conv-` prefix and filters `archived_at IS NULL`. `LegacyConversation` (line 236) carries
`id: number` (the rowid) and `title: string | null`.

### F2 — Nothing closes the lifecycle after a same-machine OAuth

`healthy` is emitted only (a) by the hook on a clean `mcp__linear__*` call when the marker exists, or
(b) by the operator via `POST /api/linear-mcp-auth/complete`. The browser reaching
`localhost:<port>/callback` fires no hook. The owner sits idle at its prompt (the plan role prompt and
`LINEAR_MCP_AUTH_WAKE_COPY` both tell it to "call mcp__linear__authenticate once and wait"). So today,
after a same-machine approval, the banner stays up until someone pokes the owner. This PRD adds the
**verify request** to close that gap.

### F3 — Expired links have no regeneration path

`projectLifecycle` (line 223 of `src/lib/linear-mcp-auth.ts`) reports `status: 'expired'` once
`authUrlExpiresAt < now` (TTL `LINEAR_MCP_AUTH_URL_TTL_MS` = 30 min). A fresh URL appears only when some
blocked agent emits a new `required` event with an `authUrl`, which requires the agent to call
`mcp__linear__authenticate` again. Nothing asks it to.

### F4 — "Resume all blocked agents" already works

Scope item 4 of the issue ("resume all agents blocked on Linear, not just the one that generated the
link") is already implemented: `processLinearMcpAuthWake()` wakes every agent of the completed lifecycle,
and `src/lib/__tests__/linear-mcp-auth-wake.test.ts` → "wakes every agent in the completed lifecycle
exactly once" proves it. Cloister triggers it on every `linear_mcp_auth.healthy`
(`src/lib/cloister/service-reactive.ts` line 387). No new wake code is needed; WI-9 adds a regression
test for the new flow's shape (a healthy emitted by a refreshed owner wakes a non-owner conversation).

### F5 — Popup blockers

A `window.open` called after an `await` is not tied to the user gesture, and browsers block it. The
banner must open the tab synchronously in the click handler and navigate it later.

## Decisions

- **D1 — One "Connect Linear" button.** It replaces the "Open Linear authorization" anchor and the
  expired/waiting copy as the primary action. It is shown for `status: 'active'` and `'expired'`.
- **D2 — Server decides open vs refresh** in one route, `POST /api/linear-mcp-auth/connect`. The link is
  *usable* iff `status === 'active'` **and** `authUrl !== null` **and** the owner is not confirmed dead
  (`isConfirmedDead(await isAlive(owner))` from `src/lib/agents/liveness.ts` is `false`; a thrown probe
  or `runtime-indeterminate` counts as alive). Usable → `200 { action: 'open', authUrl, authUrlAgentId }`.
  Otherwise the server sends a refresh request and returns `202 { action: 'refreshing', requestedFrom, previousAuthUrl }`.
- **D3 — Refresh candidate order:** `authUrlAgentId` first (if non-null), then the remaining
  `blockedAgents` sorted by `declaredAt` descending, de-duplicated. For each candidate call
  `messageAgent(candidate, LINEAR_MCP_AUTH_REFRESH_COPY, 'linear-mcp-auth-refresh')`; accept the first
  outcome with `delivered === true`. A thrown error or `delivered === false` moves to the next candidate.
  No candidate delivered → `409 { success: false, error: 'Could not reach any blocked agent to generate a fresh Linear link. Open one of the blocked conversations and ask it to call mcp__linear__authenticate.' }`.
- **D4 — Refresh throttle.** A module-level record `{ declaredAt, agentId, at }` in the connect module.
  If a refresh for the same lifecycle (`intervention.declaredAt`) was delivered less than
  `LINEAR_MCP_AUTH_REFRESH_THROTTLE_MS = 60_000` ago, return the same `202` with the recorded
  `requestedFrom` and send nothing. Reason: a second `authenticate` call in the same process can replace
  the callback listener and break the tab the operator is already in. In-memory is enough: it is a
  rate limit, not state (CLAUDE.md "stores no status it can derive").
- **D5 — Verify request** via `POST /api/linear-mcp-auth/verify`. `status === 'none'` →
  `200 { alreadyConnected: true }`. `authUrlAgentId === null` → `409`. Otherwise message the owner with
  `LINEAR_MCP_AUTH_VERIFY_COPY` (caller `'linear-mcp-auth-verify'`) and return
  `202 { requestedFrom }`; `delivered === false` or a throw → `409` with the reason. Throttle: same
  lifecycle within `LINEAR_MCP_AUTH_VERIFY_THROTTLE_MS = 15_000` → `202` without sending.
- **D6 — Message copy (exact strings).** Neither reuses `LINEAR_MCP_AUTH_WAKE_COPY`, because that copy
  tells the agent to call `authenticate` again on failure, which would mint a new URL mid-flow.

  ```ts
  export const LINEAR_MCP_AUTH_REFRESH_COPY = 'The Linear authorization link you generated has expired and the operator wants to connect now. Call mcp__linear__authenticate exactly once to generate a fresh authorization URL, state the URL in one sentence, then stop and wait — Overdeck shows the link to the operator and wakes you when authentication is restored. Do not do anything else.';
  export const LINEAR_MCP_AUTH_VERIFY_COPY = 'The operator approved Linear access in their browser. Re-check Linear access now with exactly one lightweight read (e.g. mcp__linear__list_issues with a limit of 1). If it succeeds, resume your canonical task. If it fails or the Linear tools are unavailable, do NOT call mcp__linear__authenticate — stop and wait; the operator will retry from the dashboard.';
  ```
- **D7 — Logic lives in `src/lib`, routes stay thin.** New modules `src/lib/linear-mcp-auth-connect.ts`
  and `src/lib/linear-mcp-auth-verify.ts`. The `messageAgent(` calls therefore sit outside the
  scan roots of `tests/unit/lib/agents/delivery-no-loss-audit.test.ts` (`lib/cloister`, `cli`,
  `dashboard/server`), exactly like the existing wake pass in `src/lib/linear-mcp-auth.ts`. The route
  file gains **no** new `messageAgent(` line, so `KNOWN_CALL_SITES` needs no change.
- **D8 — Client waits, server returns immediately.** The connect route never holds the request open.
  The banner polls `GET /api/linear-mcp-auth` every 1 s while a connect flow is in progress and treats
  `status === 'active' && authUrl !== null && authUrl !== previousAuthUrl` as "fresh link arrived".
  Timeout: 90 s → error toast "No fresh Linear link yet — open a blocked conversation to check on it."
- **D9 — Auto-verify on return, loopback only.** After the tab is navigated to the authorization URL,
  and only when `isLoopbackHost(window.location.hostname)`, the first `window` `focus` event or
  `document` `visibilitychange` to `visible` that happens ≥ 2 s after navigation POSTs `/verify`. A
  "Check now" button is always shown while waiting for approval. On a non-loopback origin the paste
  relay is the completion path, so no auto-verify fires.
- **D10 — Success.** While a connect flow is in progress, the banner remembers the last non-`none`
  `blockedAgents.length` (N). When the polled status turns `'none'`, it shows
  `toast.success('Linear connected — N agent(s) resumed')` and the banner unmounts. A `'none'` that
  arrives while no flow is in progress shows no toast.
- **D11 — Verify timeout.** 60 s after a verify request without `'none'`, the flow returns to
  "awaiting approval" with the copy "Linear still isn't connected. Finish approving in the Linear tab,
  then click Check now."
- **D12 — Agent row label and link.** Label: `conversationTitle ?? issueId ?? agentId`. Link:
  `conversationUrl` when set; else `/issues/<issueId>` (the dashboard issue view route, see
  `App.test.tsx` `'/issues/PAN-1234'`) when `issueId` is set; else plain text. The raw `agentId` goes in
  the link's `title` attribute. When `issueId` is set and a tracker URL resolves
  (`agent.issueUrl ?? trackerIssueUrl(agent.issueId)`), a trailing external-link icon anchor with
  `aria-label="Open <issueId> in tracker"` opens it in a new tab.
- **D13 — Fallback disclosure.** The paste field, its submit button, the explanatory paragraph, and the
  "Mark completed" button move into one `<details>` element whose `<summary>` reads
  "Signed in from a different device? Paste the callback URL". `open` is set initially when
  `!isLoopbackHost(window.location.hostname)`. "Mark completed" stays inside the disclosure, relabeled
  "Already authorized another way? Mark completed".
- **D14 — Opener hygiene.** The click handler calls `window.open('about:blank', '_blank')` (no
  `noopener`, so the handle is kept). Before navigating it sets `tab.opener = null`, then
  `tab.location.href = authUrl`. If `window.open` returns `null`, the flow stores the URL and renders an
  "Open Linear authorization" anchor (`target="_blank" rel="noreferrer"`) instead. On a connect error
  or refresh timeout the blank tab is closed (`tab.close()`).
- **D15 — Conversation lookup.** `withConversationUrls` uses `getConversationByTmuxSession(agentId)`,
  falling back to `getConversationByName(agentId.slice('conv-'.length))` so an archived conversation
  still resolves.

## Requirements

- **FR-1** — A blocked `conv-*` agent whose conversation row exists is projected with
  `conversationUrl: '/conv/<rowid>'` and `conversationTitle: <title|null>`.
- **FR-2** — Each banner row shows the label and link from D12.
- **FR-3** — `POST /api/linear-mcp-auth/connect` implements D2–D4 and rejects requests without a
  trusted origin with 403.
- **FR-4** — `POST /api/linear-mcp-auth/verify` implements D5 and rejects requests without a trusted
  origin with 403.
- **FR-5** — The banner's primary action is "Connect Linear", which runs the flow in D8–D11 and D14
  with progress copy: "Opening Linear…", "Getting a fresh link…", "Approve access in the Linear tab,
  then come back here.", "Checking Linear access…".
- **FR-6** — The paste field and "Mark completed" live in the D13 disclosure; it is expanded initially
  only on a non-loopback host.
- **FR-7** — A healthy event from the (refreshed) owner wakes every blocked agent of the lifecycle,
  including conversations that never produced an `authUrl` (regression lock for F4).
- **FR-8** — `docs/LINEAR-MCP-AUTH.md` describes the connect, refresh, verify flows, the new routes, and
  the new projection fields.
- **NFR-1** — No `execSync` and no synchronous child-process calls in any new server-reachable code;
  all I/O is async.
- **NFR-2** — Every poll, timeout, and throttle test uses `vi.useFakeTimers()` with
  `vi.advanceTimersByTimeAsync()`; no real `setTimeout` waits in tests (repo rule
  `fake-timers-for-retry-tests`). Note: happy-dom's `AbortSignal.timeout` ignores fake timers — use
  `AbortController` + `setTimeout` if an abort is needed.
- **NFR-3** — Every new HTTP route has a row in `tests/unit/lib/overdeck/no-loss-matrix.ts` (CI fails
  otherwise).
- **NFR-4** — Messages to agents go only through `messageAgent()` (delivery door), never tmux.

```ts
export const LINEAR_MCP_AUTH_REFRESH_COPY = '…D6 text…';
export const LINEAR_MCP_AUTH_REFRESH_THROTTLE_MS = 60_000;
export type LinearMcpAuthConnectResult =
  | { kind: 'open'; authUrl: string; authUrlAgentId: string | null }
  | { kind: 'refreshing'; requestedFrom: string; previousAuthUrl: string | null }
  | { kind: 'nothing-pending' }
  | { kind: 'unreachable'; error: string };
export async function connectLinearMcpAuth(deps?: ConnectDeps): Promise<LinearMcpAuthConnectResult>;
export function _resetLinearMcpAuthConnectForTests(): void;
```

`ConnectDeps` (test seam, production passes nothing): `resolve` (default
`resolveLinearMcpAuthIntervention`), `isAlive` (default from `./agents/liveness.js`), `messageAgent`
(default from `./agents/messaging.js`), `now` (default `Date.now`). Steps:

1. `intervention = await resolve()`. `status === 'none'` → `{ kind: 'nothing-pending' }`.
2. If `status === 'active' && authUrl !== null`: owner = `authUrlAgentId`. If owner is null, or
   `isAlive(owner)` throws, or `!isConfirmedDead(verdict)` → return `open`.
3. Throttle check (D4) keyed by `intervention.declaredAt`.
4. Iterate candidates (D3); on first `delivered === true` record the throttle entry and return
   `refreshing` with `previousAuthUrl: intervention.authUrl`.
5. None delivered → `unreachable` with the D3 error string.

active+alive owner → open with no `messageAgent` call; expired → refresh to owner first;
active but owner confirmed dead (`{ alive: false, reason: 'no-session' }`) → refresh;
`runtime-indeterminate` → open; owner delivery `{ delivered: false }` → next newest-declared
candidate; all fail → unreachable; second call within 60 s → same `requestedFrom`, `messageAgent`
called once; call after 60 s → sends again; `none` → nothing-pending.

/** True when the dashboard hostname resolves to this machine (PAN-4464). */
export function isLoopbackHost(hostname: string): boolean {
  const host = hostname.toLowerCase();
  return host === 'localhost'
    || host.endsWith('.localhost')
    || host === '::1' || host === '[::1]'
    || /^127(\.\d{1,3}){3}$/.test(host);
}

### WI-8 — Connect flow hook and fast polling (FR-5, D8–D11, D14)

Files: new `src/dashboard/frontend/src/hooks/useLinearConnectFlow.ts`, its test
`src/dashboard/frontend/src/hooks/__tests__/useLinearConnectFlow.test.tsx`, and
`src/dashboard/frontend/src/hooks/useLinearMcpAuthStatus.ts`.

`useLinearMcpAuthStatus(options?: { fast?: boolean })`: `refetchInterval` returns `1_000` when
`options.fast`, else the existing `none ? 30_000 : 5_000` rule.

`useLinearConnectFlow()` **owns the status query**: it holds `phase` in state and calls
`useLinearMcpAuthStatus({ fast: phase !== 'idle' })` itself, so there is no circular dependency between
the poll rate and the flow. It returns `{ intervention, phase, fallbackUrl, notice, connect(), checkNow() }`
with `phase: 'idle' | 'opening' | 'refreshing' | 'awaiting-approval' | 'checking'`. The banner calls only
`useLinearConnectFlow()` and reads `intervention` from it; it no longer calls `useLinearMcpAuthStatus`
directly. Transitions:

- `connect()`: `tab = window.open('about:blank', '_blank')`; phase `opening`; POST `/connect`.
  `200 open` → navigate (D14), phase `awaiting-approval`. `202 refreshing` → store
  `previousAuthUrl`, phase `refreshing`. Non-2xx → `tab?.close()`, `toast.error(body.error)`, phase
  `idle`.
- In `refreshing`, an `intervention` with a fresh link (D8) → navigate, phase `awaiting-approval`;
  90 s without one → `tab?.close()`, error toast (D8 text), phase `idle`.
- In `awaiting-approval` on a loopback host: focus / visibility handler (D9) → `checkNow()`.
- `checkNow()`: POST `/verify`; phase `checking`; `200 alreadyConnected` leaves the success path to the
  poll; non-2xx → error toast, phase `awaiting-approval`. 60 s in `checking` without `none` → phase
  `awaiting-approval` with the D11 message exposed as `notice`.
- Any phase ≠ `idle` and `intervention.status === 'none'` → success toast (D10), phase `idle`.

Tests mock `../useLinearMcpAuthStatus` to return a controllable `data` and assert the `fast` option
passed to it (`false` while idle, `true` during a flow). Tests use
`vi.useFakeTimers()`, mock `fetch`, `window.open` (returning a fake `{ location: { href: '' }, opener: {}, close: vi.fn() }`
and `null`), and `sonner`'s `toast`. Cases: valid-link path navigates the tab and nulls `opener`;
refresh path waits for a new `authUrl` then navigates; refresh timeout closes the tab and toasts;
`window.open` returning `null` exposes `fallbackUrl`; focus on loopback POSTs `/verify` once;
focus on non-loopback posts nothing; `none` during a flow toasts "Linear connected — 2 agents resumed".

## Intersecting repo rules (restated)

- Fake timers for every delay/poll/throttle test (`vi.useFakeTimers()`, `vi.advanceTimersByTimeAsync`).
- No `execSync` or blocking child-process calls in server-reachable code.
- New HTTP route ⇒ `no-loss-matrix.ts` row, or CI fails.
- Messages go through `messageAgent()` only; never raw tmux.
- New lib modules that need agent state import from leaf modules to avoid `lint:circular` (connect
  and verify import only `./linear-mcp-auth.js`, `./agents/messaging.js`, `./agents/liveness.js`).
- New tests must not read source files or use `skipIf`/`.only` (test-skip gate).
- Quality gates before `pan done`: `npm run typecheck`, `npm run lint`, and
  `npx vitest run <touched test files>`; never the full `npm test` on the host.

## Non-goals

- No new domain event type and no contract (`packages/contracts`) change.
- No change to the hook script `sync-sources/hooks/linear-mcp-auth-hook` or its emitted kinds.
- No reading of Claude Code credential stores (`~/.claude/.credentials.json`) to detect OAuth.
- No change to the wake pass (`processLinearMcpAuthWake`) or `LINEAR_MCP_AUTH_WAKE_COPY`.
- No removal of the callback-relay or mark-completed routes.
- No support for non-Claude-Code harnesses (the detection hook is Claude-Code-only).
- No server-side long-poll for the fresh link.

## Hazards

- **H1 — No live OAuth in tests.** Real Linear consent cannot run in CI. All tests mock the API; the
  same-machine flow is proven by the mocked Playwright run plus the unit tests of each step.
- **H2 — Premature verify.** If the operator returns before approving, the owner's read fails. The
  verify copy forbids calling `authenticate`, so the open tab stays valid; the banner returns to
  awaiting approval after 60 s.
- **H3 — Headless focus.** `page.bringToFront()` may not emit `focus` in headless Chromium; WI-12 falls
  back to clicking "Check now".
- **H4 — Liveness for conversations.** `isAlive('conv-…')` must work on Herdr and tmux; a thrown probe
  counts as alive (D2), so a broken probe never forces a needless refresh.
