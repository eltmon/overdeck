## 1. Glossary

| Term | Meaning |
|---|---|
| **Agents Directory** | The new three-pane view at `/agents` (tree, list, detail). It becomes the default view mode of the existing `FleetAgentsView` route component. |
| **Directory entry** | One row the directory shows: an agent, a conversation, a subagent, a worker, or an external agent. Contract `DirectoryEntry` (W1). |
| **Native agent** | An agent Overdeck launched and recorded in `~/.overdeck/agents/<id>/state.json`: work, plan, strike, review, test, ship, flywheel, and (after W10) worker. |
| **Pane** | A live terminal-backend pane (Herdr or tmux) as `BackendPane` (`packages/contracts/src/backend-pane.ts:11`). |
| **Pane-only agent** | A pane with Overdeck tokens but no `state.json`. Today these are `pan spawn` foreman workers (`src/cli/commands/spawn.ts`). |
| **Conversation** | An operator conversation row in `overdeck.db` (`conversations` table), listed by `getEnrichedConversationList` (`src/lib/overdeck/conversation-list.ts:73`). |
| **Subagent** | An in-harness child session: a Claude Code `Agent`/`Task` subagent (`<session>/subagents/agent-<id>.jsonl`) or a Codex child thread (`rollout-*.jsonl` with `thread_spawn.parent_thread_id`). See `docs/CONVERSATION-SUBAGENTS.md`. |
| **Worker** | A native agent with role `worker` started by `pan worker run` (Phase B). It has a parent, an issue, a pane, a transcript, and a report. Not a conversation: it has no `conversations` row and no composer by default. |
| **Foreman worker** | A `pan spawn` pane (role token `worker`, no `state.json`). Unchanged by this issue; shown as a pane-only entry. |
| **External agent** | An agent that another tool launched (for example the Codex plugin's detached `codex` process). Overdeck did not launch it and cannot stop it. Recorded by a **registration** (Phase C). |
| **Registration** | A write-once `registration.json` in `~/.overdeck/agents/ext-<source>-<slug>/`, plus append-only `sessions.json` lines that point at the transcript. It holds facts only (who, what, where, parent), never status. |
| **Parent** | The conversation or agent that spawned an entry. Stored as an id: an agent id (`agent-pan-3920`), a conversation tmux session (`conv-…`), or `claude-session:<uuid>` when only a Claude session id is known. |
| **Report** | The worker's result: `~/.overdeck/agents/<id>/reports/<seq>.json`, written atomically by `pan worker report`. |
| **Location** | `local` or `remote`. Remote means the agent's `remote-state.json` says `location: 'remote'` (a Fly VM). |
| **Container node** | A left-tree node: a location, a project, an issue, or a project's "Conversations" group. Agents are never tree nodes; they are list rows. |
| **Directory window** | How far back stopped entries are kept: 24 hours by default, 7 days with the "7d" toggle. Live entries are always shown. |
| **Transcript ref** | Which existing route renders an entry's transcript: the agent route `/api/agents/:id/conversation` (PAN-3950), the conversation route `/api/conversations/:name/messages`, or a subagent query on either. |
| **Operator conversation** | A prompt sender whose id starts `conv-` and has no issue token (`isOperatorConversation`, `prompt-guard.ts:124`). |

## 2. Problem

1. **The Agents page is a card grid, not a directory.** `FleetAgentsView`
   (`src/dashboard/frontend/src/components/Agents/FleetAgentsView.tsx`, 591 lines) renders cards
   from the store's `agentsById`. Its `table` and `timeline` modes are "Coming soon" placeholders
   (`FleetAgentsView.test.tsx:433-450`). It shows no conversations and no subagents. It does not
   show where an agent lives, who spawned it, or its transcript and PR side by side.
2. **Panes cannot be joined to agents on Herdr.** `BackendPane` has no agent id
   (`packages/contracts/src/backend-pane.ts:11-26`). `paneFromBackendSnapshot` drops the `agentId`
   token (`src/lib/overdeck/derived-issue-state.ts:524-544`, anchor `id: snapshot.paneId,`). On Herdr
   `pane.id` is `w1:p1`, so `/api/agents` keys panes by `pane.terminalId ?? pane.id`
   (`src/dashboard/server/routes/agents/listing.ts:69`, anchor `const paneById = new Map`), which is
   not the agent name. The directory must not depend on that key.
3. **Work-agent subagents are invisible.** Subagent discovery exists only for conversations
   (`src/dashboard/server/services/conversation/subagents.ts`, `codex-subagents.ts`). A work agent's
   in-harness subagents (the foreman's same-family workers, `docs/FOREMAN.md`) have no route.
4. **Externally spawned agents are invisible** (operator comment 1). On 2026-09-20, GPT-5.6 Sol
   workers launched through the Codex plugin did real work but left no `~/.overdeck/agents/<id>/`,
   no pane, no conversation row and no cost attribution. Their only traces are the plugin's job
   records and the Codex rollouts. The plugin also **deletes** its job records when the parent
   Claude session ends: `cleanupSessionJobs` in
   `~/.claude/plugins/cache/openai-codex/codex/1.0.6/scripts/session-lifecycle-hook.mjs:42-75`
   (anchor `jobs: state.jobs.filter((job) => job.sessionId !== sessionId)`). A read-on-demand view
   of those files therefore loses the worker as soon as the parent ends. The link has to be recorded
   when Overdeck first sees it.
5. **An Overdeck spawn returns nothing to its parent** (operator comment 2). The plugin wins because
   the calling conversation gets the worker's report back as a tool result. `pan spawn` prints a
   pane id and exits (`src/cli/commands/spawn.ts:156`, anchor `console.log((pane as AgentPaneRef).paneId);`).
   An orchestrating conversation has to poll files or CI to learn that a worker finished.

## 4. Decisions (made here; do not re-decide during implementation)

- **D1 — The directory is derived on read. It stores nothing.** `GET /api/agent-directory`
  recomputes entries from `state.json` files, the pane inventory, the conversation list, transcript
  files, `remote-state.json`, and (Phase C) registrations. Nothing it computes is written anywhere.
  No `agent_directory.*` event is added. The frontend refetches (D7).
- **D2 — Entry ids** (stable, unique across kinds):
  - native agent: its agent id (`agent-pan-3920`, `planning-pan-3920`, `agent-pan-3920-worker-1`);
  - pane-only agent: `pane.agentId` when the pane carries one, else `pane:<pane.id>`;
  - conversation: `conv:<conversation.name>`;
  - subagent: `sub:<parentEntryId>:<subagentId>`;
  - external agent: its registration id (`ext-codex-plugin-task-mu9b1x4e-bqx80g`).
- **D3 — State vocabulary.** `DirectoryEntryState = 'working' | 'idle' | 'blocked' | 'done' | 'stopped' | 'unknown'`.
  Mapping rules:
  - native or pane-only agent with a pane: `working`/`idle`/`blocked`/`done`/`unknown` pass through
    from `BackendPane.state`; `exited` becomes `stopped`. No pane: `stopped`. A remote agent
    (`remote-state.json` `location === 'remote'`) is `unknown` (the Fly VM runs its own tmux,
    `docs/TERMINAL-BACKENDS.md` "Not yet routed").
  - worker (Phase B): as a native agent, except a pane in `idle` whose latest report is newer than
    the pane's `stateSince` becomes `done`.
  - conversation: `sessionAlive` false → `stopped`; else `pendingInputCount > 0` → `blocked`; else
    `isWorking` → `working`; else `idle`.
  - subagent: the subagent transcript's mtime is within 120 s **and** the parent entry is not
    `stopped` → `working`; otherwise `done`. (One rule for Claude and Codex; no parent parse.)
  - external agent (Phase C): recorded pid alive with matching start time → `working`; else the
    transcript's last turn is complete → `done`; else `stopped`.
- **D4 — Membership in the window.** Live entries (state not `stopped`/`done`) are always included.
  Other entries are included when their last activity is within the window (24 h default, 7 d via
  `?windowHours=168`). Last activity: native agent `state.lastActivity ?? state.stoppedAt ?? state.startedAt`;
  conversation `lastActivityAt ?? endedAt ?? createdAt`; subagent transcript mtime; external agent
  transcript mtime or `registeredAt`. A parent is always included when any of its children is.
- **D5 — Tree shape.** Location → project → { issue nodes (sorted by issue number descending),
  one "Conversations" node for the project's issue-less conversations and their descendants }.
  Project key: `resolveProjectFromIssueSync(issueId)?.projectKey` for entries with an issue; for
  issue-less entries the conversation's `projectKey`, else `findProjectKeyByPathSync(cwd)` (new
  helper, W3), else the literal `unassigned` (label "No project"). The locations appear in the
  order `local`, `remote`; `remote` is omitted when it has no entries.
- **D6 — Where a row appears.** An entry belongs to (a) its issue node when it has an issue, and
  (b) the container of its **root ancestor** (follow `parentId` until an entry has none or the
  parent is not in the result). In the middle list, a child renders indented under its parent when
  both are in the selected container. A child whose parent is outside the container renders at top
  level with a "spawned by <parent label>" line.
- **D7 — Refresh.** The frontend uses React Query key `['agent-directory', windowHours]` with
  `refetchInterval: 5_000` and `refetchIntervalInBackground: false`, and invalidates the key
  (throttled to once per 2 s) whenever the store's `backendPanesById` object changes. The server
  memoizes the computed response for 3 s per `windowHours`.
- **D8 — Transcripts reuse existing routes.** Agents, workers, pane-only agents with an agent id,
  and external agents use `GET /api/agents/:id/conversation` (`buildAgentConversationResult`,
  `src/dashboard/server/routes/agents/conversation.ts:121`). Conversations use the conversation
  route. Conversation subagents use the existing `?agentId=` query. Agent subagents use a new
  `?subagentId=` query on the agent route (W2). No new transcript parser.
- **D9 — Composer policy in the detail pane.** Conversations and native non-worker agents keep
  `ConversationPanel`'s own composer. Workers get no composer; a "Message worker" button reveals
  the shared `TellComposer` (`src/dashboard/frontend/src/components/issue-view/TellComposer.tsx:13`).
  External agents and subagents are read-only (Overdeck has no delivery channel to them).
- **D10 — PR context.** For an entry with an issue, the detail pane reads
  `useDerivedIssueState(issueId)` (`src/dashboard/frontend/src/lib/store.ts`, anchor
  `export function useDerivedIssueState`): `state`, `pr.number`, `pr.url`, `pr.reviewState`,
  `pr.checks`, `pr.mergeable`, `branch.name`, `branch.aheadOfMain`, `branch.pushed`. PAN-3822 only
  blocks PR context for **issue-less** conversations; those show no PR block in this issue.
- **D11 — No-loss for the Fleet page.** `FleetAgentsView` keeps `grid`, `table` and `timeline`
  exactly as they are. `directory` is added and becomes the default when `?view=` is absent.
  `MetricStrip`, the phase/project/model filters, inline `StartAgentCta` and `IssueActionMenu`
  stay on the grid view. Nothing is removed.
- **D12 — Worker ids.** `agent-<issue-lowercase>-worker-<n>`, `n` = 1 + the highest existing
  `n` among `~/.overdeck/agents/agent-<issue>-worker-*` directories. This name passes
  `isValidAgentDirectoryName` (`src/lib/agent-directory-cleanup.ts:63`: remainder `worker-<n>`
  matches `^[a-z0-9-]+$`), so `pan sync`'s cleanup (`src/cli/commands/sync.ts:647`) keeps it. It is
  also exactly `runAgentId(issueId, 'worker', String(n))` (`src/lib/agents/spawn-prep.ts:941`).
- **D13 — Worker model and harness routing.** `determineModel({ role: 'worker' })` resolves
  `roles.worker.model` from `config.yaml`, else `DEFAULT_MODEL_REFS.worker = 'workhorse:mid'` (same
  as `work`). Harness: `resolveHarness({ explicit, role: 'worker', model })`, the same call every
  role run makes. `--model` and `--harness` override both.
- **D14 — Worker working directory.** Without `--read-only`: a git worktree at
  `<workspace>/.swarm/worker-<n>/` on branch `<feature-branch>/worker-<n>`, created with the same
  algorithm as `pan spawn`'s `defaultCreateWorktree` (`src/cli/commands/spawn.ts:69-90`). That
  function is moved to `src/lib/workspaces/item-worktree.ts` and both callers import it. With
  `--read-only`: the issue workspace itself. `--cwd <path>` overrides both and must resolve inside
  the issue workspace (refuse otherwise).
- **D15 — Report contract.** The worker ends its turn by running
  `pan worker report <id> --file <path> [--status done|blocked|failed]` (or `--stdin`). The command
  writes `reports/<seq>.json` (`seq` zero-padded to 4 digits, 1-based) as
  `{ "seq": 1, "at": "<ISO>", "status": "done", "body": "<markdown>" }` with the temp-file-plus-
  rename pattern of `writeResult` (`src/lib/cloister/verification-worker.ts:20-24`, anchor
  `const temp = \`${path}.${process.pid}.tmp\`;`). Reports are never rewritten or deleted by
  Overdeck. It does **not** POST `/api/agents/:id/work-complete`
  (`src/dashboard/server/routes/agents/runtime-events.ts:124`): that emits the work agent's
  `resolution_set: done` runtime event, and the directory already derives a worker's `done` from
  its newest report (D3), so the extra signal would only widen the blast radius.
- **D16 — Wait algorithm.** `waitForWorkerReport` polls every 2 s. It returns the first report
  whose `seq` is greater than the baseline (`--after <seq>`, default: the highest `seq` present when
  the wait started; `pan worker run` uses 0). On each poll it also reads liveness (`isAlive`,
  `src/lib/agents/liveness.ts:149`): a confirmed death (`isConfirmedDead`) with no report returns
  `exited-without-report`. A pane that has been idle (`idleAgeMs`, `liveness.ts:307`) for more than
  `idleGraceMs` (default 10 minutes) with no report returns `idle-without-report` and leaves the
  worker running. A deadline (`--timeout <seconds>`, default none for `wait`, none for `run`) returns
  `timeout`. No nudging: the wait never messages the worker.
- **D17 — Exit codes** for `pan worker run` and `pan worker wait`: `0` report with status `done`;
  `4` report with status `blocked` or `failed` (body still printed); `2` `exited-without-report` or
  `idle-without-report` (the worker's last assistant message is printed, prefixed
  `[no report — last assistant message]`); `3` timeout (prints `worker <id> is still running; run: pan worker wait <id>`);
  `1` usage or spawn error. The report body goes to **stdout**; every status line goes to **stderr**.
- **D18 — Last-assistant-message fallback.** The CLI fetches
  `GET <getDashboardApiUrlSync()>/api/agents/<id>/conversation` (`src/lib/config.ts:411`) and takes
  the last message with `role === 'assistant'`. When the dashboard is unreachable it prints the
  transcript path from `resolveJsonlPath` (`src/lib/agents/transcript-resolver.ts:323`) instead.
  The CLI never imports dashboard-server parser modules.
- **D19 — Read-only mode** blocks git writes only. File-system and network sandboxing are out of
  scope (operator comment 2). The guard change is W12.
- **D20 — Registration storage (Phase C).** `~/.overdeck/agents/ext-<source>-<slug>/registration.json`
  is written once with the `wx` flag and never rewritten. Later facts (thread id, transcript path)
  are appended to that directory's `sessions.json` through `appendSessionIdToHistory`
  (`src/lib/session-history.ts:202`). That makes the PAN-3950 agent transcript route work for
  external agents with no route change, because `listAgentTranscriptCandidates` reads indexed
  `path` entries first (`src/lib/agents/transcript-resolver.ts:251-255`, anchor
  `if (entry.path) {`). `isExternalAgentDirectory(name)` (`name.startsWith('ext-')`) is added to
  the cleanup preserve list next to `isConversationDirectory` (`agent-directory-cleanup.ts:164`).
- **D21 — External liveness (Phase C).** A registration may record `pid` and `pidStartTime`
  (field 22 of `/proc/<pid>/stat`). Alive = `/proc/<pid>/stat` exists and its field 22 equals the
  recorded value. On a platform without `/proc`, alive = `process.kill(pid, 0)` succeeds. No
  subprocess is spawned.
- **D22 — Codex-plugin adapter (Phase C)** reads only. It never writes into
  `~/.claude/plugins/**`. It scans every 15 s (`setInterval`, `unref()`), and registers each job id
  once (existence of the registration directory is the "seen" check).
- **D23 — `pan spawn` is not changed.** Foreman workers stay pane-only. Routing `pan spawn`
  through the worker core is a possible follow-up, not part of this issue.
- **D24 — The directory stays behind the experimental gate.** `/agents` is in `EXPERIMENTAL_TAB_IDS`
  (`src/dashboard/frontend/src/lib/experimentalFeatures.ts:4-15`). This issue does not change that.
  After the operator has used the directory for a week, a one-line follow-up removes `'agents'` from
  the set.
- **D25 — A worker stays warm after it reports** (PAN-2579 policy, `docs/ROLES.md` "Session
  lifecycle: warm by default"). Follow-ups use `pan tell <id>` and then `pan worker wait <id>`.
  `pan worker run --stop-after-report` stops it after the first report.
- **D26 — Phase order.** Phase A (this issue) and Phase B run in parallel; Phase C starts after
  Phase A merges. A and B touch different files except `packages/contracts/src/index.ts` and docs;
  C needs A's directory service.

## 5. Requirements

### Functional

- **FR-1** The directory lists: native agents (all roles) in the window; pane-only agents; conversations
  in the window; Claude and Codex subagents of every listed conversation and native agent that is
  not `stopped`; workers (Phase B); external agents (Phase C). Conversation agent dirs (`conv-*`)
  are never listed as native agents.
- **FR-2** Every entry carries `id`, `kind`, `label`, `location`, `projectKey`, `issueId`,
  `parentId`, `role`, `harness`, `model`, `state`, `startedAt`, `lastActivityAt`, `costUsd`,
  `source`, `transcript` (W1 schema).
- **FR-3** The left tree follows D5 and shows, per node, the number of live entries and total entries.
- **FR-4** The middle list follows D6: columns label/id, role, harness · model, state, age
  (since `startedAt`), last activity, spawned by. Sorted live first, then last activity descending.
- **FR-5** The detail pane shows the header (label, id, harness, model, state, parent link, started,
  last activity, cost), the transcript per D8, the issue context per D10 with `IssueActionMenu`
  in `primary-strip` mode, and the composer policy of D9.
- **FR-6** Keyboard: `↑`/`↓` move the selection inside the focused pane; `←`/`→` and `Tab`/`Shift+Tab`
  move focus between panes; `Enter` on a tree node focuses the list, on a list row focuses the
  detail; `/` focuses the list filter. Selection is mirrored in the URL:
  `/agents?node=<nodeId>&entry=<entryId>&window=24|168` via `history.replaceState`.
- **FR-7** `?view=grid|table|timeline` keep today's behavior; no `?view=` means `directory` (D11).
- **FR-8** `BackendPane.agentId` is present for every pane whose launcher stamped `agentId`
  (Herdr) and for every tmux agent session.
- **FR-9** `GET /api/agents/:id/conversation?subagentId=<sid>` returns the named subagent transcript
  of an agent; `GET /api/agents/:id/subagents` lists them.
- **FR-10** `pan worker run --issue <id> (--prompt <text> | --brief <file>)` starts a worker per D12–D14
  and blocks until D16 resolves, then prints per D17.
- **FR-11** `pan worker run --detach` prints only the worker id and exits 0 after the pane exists.
  `pan worker wait <id>`, `pan worker report <id>`, `pan worker list` behave as in W14.
- **FR-12** The worker is a native agent: `state.json` with `role: 'worker'`, `parentId`, `startedBy: 'pan-worker'`;
  pane tokens `{ issue, role: 'worker', harness, model, agentId, parent }`; a transcript on the agent
  route; no `conversations` row.
- **FR-13** `--read-only` installs a git guard that refuses write subcommands inside the worker's cwd (W12).
- **FR-14** The prompt guard accepts a prompt to a `worker` pane from the sender whose id equals the
  pane's `parent` token (Q5). Conversation launchers export `OVERDECK_CONVERSATION` (Q3).
- **FR-15** A `/pan-worker` skill and a one-rule launch-context pointer tell agents to use workers

```
pan worker run --issue <id> (--prompt <text> | --brief <file>) [--model <m>] [--harness <h>]
               [--read-only] [--cwd <path>] [--parent <id>] [--name <label>]
               [--detach] [--timeout <seconds>] [--stop-after-report]
pan worker wait <worker-id> [--after <seq>] [--timeout <seconds>]
pan worker report <worker-id> (--file <path> | --stdin) [--status done|blocked|failed]
pan worker list [--issue <id>] [--parent <id>] [--json]
```

- **Parent resolution** (`run`): `--parent` → `OVERDECK_AGENT_ID` → `OVERDECK_CONVERSATION` → none.
  When none and stdin is not a TTY (called by an agent), fail with exit 1:
  "Cannot tell which conversation or agent is spawning this worker. Pass --parent <conversation-or-agent-id>."
  An interactive operator shell may run without a parent.
- `run` without `--detach`: `startWorker`, print `worker <id> started (cwd <cwd>)` to stderr, then
  `waitForWorkerReport(id, { afterSeq: 0, timeoutMs })` and print per D17. With `--stop-after-report`,
  after a `report` outcome call the existing stop path: `Effect.runPromise(stopAgent(id, 'operator'))`
  (`src/lib/agents/termination.ts:205`, anchor `export const stopAgent = (`).
- `run --detach`: print only the id to stdout; exit 0.
- `wait`: validate `WORKER_ID_RE`; exit 1 when the worker dir does not exist.
- `report`: validate the id; read the body; `writeWorkerReport`; print `report <seq> recorded` to stderr.
- `list`: read `worker.json` of every `agent-*-worker-*` dir, filter, and print a table
  (id, issue, parent, state from `isAlive`, latest report seq/status) or JSON.

**Tests** (`tests/unit/cli/worker-command.test.ts`, new; worker core mocked): exit code per
outcome (0, 4, 2, 3, 1); report body on stdout and status on stderr; parent resolution order; the
non-TTY missing-parent error text; `--detach` prints only the id.
