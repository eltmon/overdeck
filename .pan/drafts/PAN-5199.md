# PAN-5199: Polyrepo workspaces: work agent start refused as dirty because the wrapper repo doesn't ignore Overdeck's own sync files

**Issue:** [PAN-5199](https://github.com/eltmon/overdeck/issues/5199)
**Planned at:** `e27dba4604f` (branch `feature/pan-5199`), 2026-11-13

## Glossary

- **Polyrepo project** — a project whose `projects.yaml` entry sets `workspace.type: polyrepo` and lists `workspace.repos[]` (MYN is the live example: `fe/`, `api/`, `infra/`, `docs/`, …).
- **Wrapper repo** (also "scaffold repo") — the workspace *root* of a polyrepo workspace, `<project>/workspaces/feature-<issue>/`. `createWorkspace` creates it as a plain directory (`mkdirSync`); planning completion runs `git init` in it (`src/lib/overdeck/planning-promotion.ts`, `commitCompletePlanningWorkspaceGit`, grep `execImpl('git', ['init']`). It has no remote. It tracks `.gitignore` and any planning artifacts the planning commit stages (`git add .pan/`); all code lives in the sub-repo worktrees under it.
- **Sync paths** — files and directories that Overdeck itself writes into a workspace root while it creates or syncs the workspace. They are never work product.
- **Start gate** (the "dirty-workspace gate") — the check in `spawnIssueAgentForRoute` that runs `git status --porcelain --untracked-files=all` in the workspace root and returns HTTP 409 `WORKSPACE_DIRTY` unless every listed path is Overdeck-owned. It logs `agent.start_refused_dirty_workspace`.
- **Porcelain entry** — one line of `git status --porcelain` output: a two-character status (`??` = untracked, ` M` = modified tracked file, and so on), a space, and a path.
- **Heal** — rewriting an existing wrapper `.gitignore` so it carries every required entry, then committing it in the wrapper repo.

## Decisions (made here; auto-planning mode)

- **D1. One shared list, in a leaf module.** A new module `src/lib/workspace-sync-paths.ts` (no imports) holds two constants and one predicate:
  - `OVERDECK_PROJECT_GITIGNORE_ENTRIES` — the existing `ensurePanGitignore` list, moved here verbatim. `ensurePanGitignore` imports it. The project `.gitignore` behaviour does not change.
  - `OVERDECK_WORKSPACE_ROOT_SYNC_ENTRIES = ['.claude/', '.mcp.json', '.hume-config', '.env']` — every sync path in the writer table that the project list does not already cover.
  - `isOverdeckWorkspaceSyncPath(path)` — true when the path matches an entry in either constant. An entry that ends in `/` matches the bare directory name or any path under it. Any other entry matches the exact path only.
  The wrapper `.gitignore`, and the start gate, both read these constants. No second copy exists. It is a leaf so that `state-plane.ts`, `migration.ts` and the dashboard route can all import it without a `lint:circular` failure.
- **D2. The wrapper ignores `.claude/` as a whole.** The wrapper is Overdeck's scaffold. Overdeck creates it, it has no remote, it holds no code, and every file under its `.claude/` is written by Overdeck. A project repo can track parts of `.claude/`, so the *project* `.gitignore` list stays narrow (`.claude/skills/` only). See NonGoals.
- **D3. The start gate accepts sync paths only as untracked (`??`) entries, and only in a polyrepo wrapper.** `isOnlyOverdeckRuntimeWorkspaceChanges` gains an options argument `{ polyrepoWrapper?: boolean }` (default `false`). The sync-path tolerance applies only when `polyrepoWrapper` is true, which the route passes when `projectConfig.workspace.type === 'polyrepo'`. In a monorepo, `?? .claude/agents/my-agent.md` or a hand-made `?? .mcp.json` can be team-owned work (`configuration/meta-repos.mdx` lines 33–42), so a monorepo start gate behaves exactly as today. Inside a wrapper, a *tracked, modified* or staged sync path (` M .claude/settings.json`, `A  .mcp.json`) stays refused too.
- **D4. `isOverdeckWorkspaceRuntimePath` is not widened.** It also feeds `isOverdeckOwnedOnlyStatus`, which the `pan done` preflight (`src/lib/work/done-preflight.ts`) and merge-ops (`src/dashboard/server/routes/workspaces/merge-ops.ts`) use for every project. The new tolerance lives only in `isOnlyOverdeckRuntimeWorkspaceChanges` (the start gate).
- **D5. Heal runs in the start route, before the dirty check, on local polyrepo workspaces only.** Every start (`pan start`, dashboard Start Agent, MCP `start_issue`, the planning auto-handoff, machine work) goes through `spawnIssueAgentForRoute`, so one call site covers the "next `pan start`" requirement. `createWorkspace` already runs the ensure on its resume path. The heal is skipped when the wrapper has no `.git` (planning has not run `git init` yet) or when the workspace directory does not exist (remote start).
- **D6. The heal commits only `.gitignore`, and a failed heal commit leaves the tree exactly as it was.** `commitPolyrepoWorkspaceGitignoreAsync` changes to check and commit the `.gitignore` path only (`git diff --cached --quiet -- .gitignore`, `git commit … -- .gitignore`), so any other staged entry stays staged and uncommitted, and the gate still sees it. The heal runs only on a tracked, clean `.gitignore`. If the commit does not land, it restores `.gitignore` from HEAD in both the index and the working tree (`git restore --source=HEAD --staged --worktree`). It never leaves ` M .gitignore` behind, which would make the gate refuse for a new reason. With D3 the gate still accepts the untracked sync paths, so the start succeeds anyway.
- **D7. The heal module is extracted.** `ensurePolyrepoWorkspaceGitignore` and `commitPolyrepoWorkspaceGitignoreAsync` move unchanged from `create.ts` into a new module `src/lib/workspace-manager/polyrepo-gitignore.ts`. `create.ts` re-exports both, so the existing imports and tests keep working. Reason: `spawn-issue.ts` must import the heal helper, and `create.ts` pulls in DNS, tunnel, Hume, Docker and workspace-row modules that the route must not depend on. `spawn-issue.ts` is at 918 of the 1000-line ceiling, so the route change is one guarded call plus its lifecycle log.
- **D8. Static list, no per-project template discovery.** `.mcp.json` is a per-project `*.template` target. The start gate is a pure function over porcelain text, so it needs a static list, and the issue requires one shared list for both uses. `.mcp.json` is the only root template target in the only live polyrepo project. Other per-project template targets are a NonGoal.
- **D9. The heal commit moves the wrapper HEAD, and that is safe.** The plan-integrity gate finds the `Plan-Finalized` trailer by a `git log` search over `mergeBase..HEAD` (`src/lib/cloister/plan-integrity-run.ts` line 114), so a commit on top does not hide it. For polyrepo projects the spec usually lives in the nested plan-home repo anyway. The wrapper HEAD is still never a review anchor (`docs/WORKSPACES-AND-PROJECTS.md`, "Wrapper-repo git posture"). The doc sentence that says the wrapper HEAD "never moves" is corrected in WI-8.

## Requirements

- **FR-1** — `ensurePolyrepoWorkspaceGitignore` writes every entry of `OVERDECK_PROJECT_GITIGNORE_ENTRIES` and `OVERDECK_WORKSPACE_ROOT_SYNC_ENTRIES` into the wrapper `.gitignore`, after the existing sub-repo and runtime entries. It writes each entry once and is idempotent.
- **FR-2** — `ensurePanGitignore` reads `OVERDECK_PROJECT_GITIGNORE_ENTRIES` from the shared module. Its output for a project `.gitignore` does not change.
- **FR-3** — `healPolyrepoWorkspaceGitignoreAsync(workspacePath, repos)` runs only when the wrapper `.gitignore` is tracked and clean, and commits nothing but `.gitignore`. It runs the ensure and, when entries were added, commits `.gitignore` in the wrapper repo. When the commit does not land, it restores `.gitignore` from HEAD and reports a warning.
- **FR-4** — `spawnIssueAgentForRoute` calls the heal before the dirty-workspace check for a local polyrepo workspace whose wrapper has a `.git`, and records the outcome in the agent lifecycle log.
- **FR-5** — `isOnlyOverdeckRuntimeWorkspaceChanges(porcelain, { polyrepoWrapper: true })` returns true when every porcelain entry is Overdeck runtime (`.pan/`, `.overdeck/`), generated hook output (`.husky/_/`), or an *untracked* (`??`) sync path. The route passes `polyrepoWrapper: true` only for polyrepo projects.
- **FR-6** — Real uncommitted changes are still refused: any path outside those sets, any tracked or staged (non-`??`) change to a sync path, and, without `polyrepoWrapper: true` (every monorepo), every sync path.
- **FR-7** — `parsePorcelainStatusEntries(porcelain)` returns `{ status, path }` per path. `parsePorcelainStatusPaths` returns the same paths it returns today.
- **NFR-1** — The heal never throws into the route. Every failure is caught, logged, and the start continues to the gate.
- **NFR-2** — No synchronous child-process call in dashboard-reachable code (repo rule: no `execSync` in server code). The heal uses the async `exec`/`execFile` helpers only.
- **NFR-3** — No file passes its file-size ceiling: `spawn-issue.ts` stays under 1000 lines, and `create.ts` gets shorter.
- **NFR-4** — `npm run lint:circular` stays green: `src/lib/workspace-sync-paths.ts` imports nothing.

Steps:
1. If `!existsSync(join(workspacePath, '.git'))`, return `{ added: [], committed: false, warning: null }`.
2. Precondition: `.gitignore` is tracked and clean. Run `git ls-files --error-unmatch -- .gitignore` and `git status --porcelain -- .gitignore` (async `execAsync`, `cwd: workspacePath`). 3. Call `ensurePolyrepoWorkspaceGitignore(workspacePath, repos)`. If `added` is empty, return `{ added: [], committed: false, warning: null }`.
4. Call `commitPolyrepoWorkspaceGitignoreAsync(workspacePath)`.
5. Check: run `git status --porcelain -- .gitignore`. An empty result means the commit landed: return `{ added, committed: true, warning: null }`.
6. Otherwise restore from HEAD: `await execAsync('git restore --source=HEAD --staged --worktree -- .gitignore', { cwd: workspacePath })`. Return `{ added, committed: false, warning: <commit message or 'wrapper .gitignore commit did not land'> }`.
7. Wrap steps 2–6 in `try/catch`. On any throw after step 3 wrote the file, run the step-6 restore (best effort, in its own `try`). Return `{ added: [], committed: false, warning: err.message }`.

### WI-5 — Porcelain entries parser (`porcelain-status-entries`) — FR-7

```ts
export interface PorcelainStatusEntry {
  /** The two-character porcelain status, e.g. `??`, ` M`, `R `. */
  status: string;
  path: string;
}

export function parsePorcelainStatusEntries(porcelain: string): PorcelainStatusEntry[] {
  return porcelain
    .split('\n')
    .map((line) => line.trimEnd())
    .filter(Boolean)
    .flatMap((line) => {
      const status = line.slice(0, 2);
      const pathPart = line.length > 3 ? line.slice(3).trim() : '';
      const paths = status.includes('R') || status.includes('C')
        ? pathPart.split(' -> ')
        : [pathPart];
      return paths.map((path) => ({ status, path: unquoteGitPath(path) }));
    })
    .filter((entry) => Boolean(entry.path));
}

export function parsePorcelainStatusPaths(porcelain: string): string[] {
  return parsePorcelainStatusEntries(porcelain).map((entry) => entry.path);
}
```
