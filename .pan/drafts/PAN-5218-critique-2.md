## blocks-the-design: close-out can erase the retry job

The PRD makes the workspace journal the patrol's only pending-job record and waits 10 minutes after `merge.completed` ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5218/.pan/drafts/PAN-5218.md), lines 47-48 and 410-416). A closed issue is reaped before the new patrol would run in `runDeaconLite` ([deacon-lite.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5218/src/lib/cloister/deacon-lite.ts), lines 595-611); the reactive close handler also reaps it immediately ([closed-issue-reaper.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5218/src/lib/cloister/closed-issue-reaper.ts), lines 129-169). Reaping removes the workspace that contains `.overdeck/pipeline.jsonl` ([reap-issue-residue.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5218/src/lib/cloister/reap-issue-residue.ts), lines 73-101; [pipeline-journal.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5218/src/lib/cloister/pipeline-journal.ts), lines 78-82). If the kick is interrupted and close-out happens inside ten minutes, no candidate survives for the patrol. Resolve this by flushing pending candidates before workspace reaping or by keeping the retry record outside the disposable workspace; test close-out before the patrol threshold.

## blocks-the-design: a commit to one file settles unrelated threads in it

The PRD defines a thread as settled whenever a later single-parent commit lists its path ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5218/.pan/drafts/PAN-5218.md), lines 69-73). Two CodeRabbit threads on different lines of `src/a.ts` therefore both disappear when an agent fixes only one and commits `src/a.ts`. The existing relay has a per-thread reply command ([coderabbit-feedback.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5218/src/lib/cloister/coderabbit-feedback.ts), lines 119-123), and `pan review request -m` reaches a journaled note ([review-pipeline.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5218/src/dashboard/server/routes/workspaces/review-pipeline.ts), lines 706-712). Require evidence tied to each thread ID for a commit to settle it, or treat a path-only commit as insufficient; add a two-threads-in-one-file test.

## blocks-the-design: substring matching settles the wrong thread

The R rule says `data.note` need only contain `String(thread.id)` ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5218/.pan/drafts/PAN-5218.md), line 73). A note naming thread `111` therefore settles thread `11`; free-text prose or another number can do the same. `requestReviewGuarded` prefixes the message with a counter and stores it as the note ([review-pipeline.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5218/src/dashboard/server/routes/workspaces/review-pipeline.ts), lines 706-712), so a raw substring check also scans text outside the agent's thread list. Parse exact IDs from the prescribed `CodeRabbit <thread ids>:` segment, with numeric token boundaries, and test `11` against `111`.

## blocks-the-design: settled candidates trigger forge reads forever

The PRD closes a candidate only for `feedback.followup_filed` or `feedback.followup_failed` ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5218/.pan/drafts/PAN-5218.md), lines 63-67 and 410-416). W-6 logs `settled` without appending a terminal entry (lines 321-332). Thus every 60-second deacon patrol ([deacon-lite.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5218/src/lib/cloister/deacon-lite.ts), line 620) fetches commits, changed files, and replies again for every fully settled delivery until its workspace disappears. Record a terminal settled outcome and exclude it from later patrols; test that the second pass performs no forge reads.

## blocks-the-design: a failed dedup lookup becomes permission to create

W-6 treats a `findExisting` error as a miss and proceeds to `createIssue` ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5218/.pan/drafts/PAN-5218.md), lines 315 and 326-329). A successful prior POST can lack a marker because `appendPipelineEntry` swallows write failures and still returns success ([pipeline-journal.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5218/src/lib/cloister/pipeline-journal.ts), lines 65-100). On retry, a transient search failure creates a second issue even without a crash. Treat lookup failure as a filing failure that raises Needs-you and makes no POST; test that path.
