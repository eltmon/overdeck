## 0. The three decisions the issue asked for (adopted in `--auto` mode)

The issue lists three things "to decide when this is picked up". Each is decided here and recorded in
the xBRIEF `plan.autoDecisions[]`.

| # | Question | Decision | Alternatives rejected |
| --- | --- | --- | --- |
| **Q1** | Where does a synced operator store live? | **The existing operator store directory becomes a plain git clone of a private repository the operator owns.** `pan memory sync --setup <git-url>` runs `git init` in `~/.overdeck/context/memory/` and adds `origin`. There is no config key: "sync is on" means "the directory has a `.git` with an `origin`". `pan memory sync` commits, fetches, merges and pushes; `pan sync`, the dashboard, and `pan memory add/edit/retire --user` call it. This is the issue's own example ("a private git repository that `pan sync` pulls and pushes"). | (a) **Ride the Session Vault.** It is encrypted, but its records are opaque HMAC-named refs, so facts could no longer be read, grepped or edited with normal tools. Facts are plain, OKF-compatible markdown by design (PAN-3957 Q3), and D10 already refuses secret-like text. The vault encrypts because transcripts contain everything an agent printed; facts do not. (b) **A config key `memory.operator_sync.remote`.** It would duplicate what `git remote get-url origin` already says (CLAUDE.md: "Overdeck stores no status it can derive"). (c) **A hosted Overdeck service.** Out of scope; no account service API for this exists. |
| **Q2** | How do machine-specific facts stay local? | **A third store, the machine store, at `~/.overdeck/context/machine-memory/` (scope `machine`, flag `--machine`). It is never synced.** It renders as `## Machine memory`. Because the operator store now travels, the PAN-3957 D16 home-directory-path guard (`MACHINE_PATH_PATTERN`) now applies to the operator store too, and its refusal message points at `--machine` instead of `--user`. `pan memory sync --setup` moves any existing home-path operator fact into the machine store before the first commit. The sync also holds back (never commits) a file that fails that guard or trips secret redaction. | (a) A frontmatter flag (`local: true`) inside the synced directory: git cannot ignore a file by its content, so every sync would need a hand-maintained exclude list. (b) A `local/` subdirectory inside the clone plus a `.gitignore`: it puts one store inside another's git tree, and the reader already ignores subdirectories, so it would need a second read path anyway. |
| **Q3** | How is a conflict resolved when two machines edit the same fact? | **The remote version keeps the fact id; the local version is kept as a new, review-marked fact `<id>-conflict-<machine>` that is committed and pushed.** Nothing is lost and no merge ever blocks: a review-marked fact is never injected (PAN-3957 FR-4), `pan memory list --user --review` lists it, and the operator resolves it with `pan memory edit --user <id>` and `pan memory retire --user <id>-conflict-<machine>`. An edit beats a deletion (modify/delete keeps the edited file). | (a) Leave git conflict markers for the operator: a merge in progress blocks every later sync on that machine, and nobody watches it. (b) Last-writer-wins by the `updated` date: the date has day granularity, so two edits on one day tie, and the loser is silently lost. |

## 1. Glossary

| Term | Meaning |
| --- | --- |
| **Fact** | One curated memory statement: one markdown file `<id>.md` with YAML frontmatter (PAN-3957 D2, `configuration/memory.mdx`). |
| **Project store** | `<planHome>/.overdeck/memory/`. Committed in the project repository. Unchanged by this issue. |
| **Operator store** | `~/.overdeck/context/memory/` (scope `user`, flag `--user`). Before this issue it was per machine. After it, it is the store that **travels with the operator**: it syncs when it is a clone (below), and it refuses home-directory paths whether or not it syncs. |
| **Machine store** | **New.** `~/.overdeck/context/machine-memory/` (scope `machine`, flag `--machine`). Per machine, never synced, the only store that accepts home-directory paths. |
| **Synced operator store** | An operator store directory that contains `.git` (a git repository with an `origin` remote). `isOperatorMemorySynced(dir)` is `existsSync(join(dir, '.git'))`. |
| **Sync remote** | The operator-owned private git repository at `origin`. Branch `main` only. |
| **Sync** | One run of `syncOperatorMemory`: lock, commit local changes (minus held-back files), fetch, merge `origin/main`, resolve conflicts, push. Never throws. |
| **Held-back file** | A changed `.md` file in the synced operator store that the sync refuses to commit: its text trips `redactSensitiveText` (`src/lib/secret-redaction.ts:148`) or matches `MACHINE_PATH_PATTERN` (`src/lib/memory/facts/store.ts:22`). It stays on disk, uncommitted, and is reported on every sync. |
| **Conflict copy** | The fact file `<id>-conflict-<label-slug>.md` the sync writes when both machines changed `<id>.md`. It holds this machine's version, carries `review: [sync-conflict]`, and is committed and pushed. |
| **Machine label** | `label` from `~/.overdeck/environment-id.json` (`readEnvironmentIdentity()`, `src/lib/environment-identity.ts:55`), falling back to `os.hostname()`. Used in the commit identity and the conflict copy name. |
| **Label slug** | The machine label lower-cased, every run of `[^a-z0-9]` replaced by `-`, leading/trailing `-` trimmed, cut to 24 characters, and `machine` when that leaves an empty string. `eltmon-z790` → `eltmon-z790`. |
| **Sync outcome** | The value `syncOperatorMemory` returns (§3 D7). |

## 3. Decisions (made here; do not re-decide during implementation)

- **D1: Store paths.** Operator store unchanged: `userMemoryDir()`. New machine store:
  `machineMemoryDir()` = `join(getOverdeckHome(), 'context', 'machine-memory')`. Both flat. The sync lock
  file is `${userMemoryDir()}.lock` (beside the store, never inside it).
- **D2: Scope `machine`.** `MemoryFactScope = 'project' | 'user' | 'machine'`. `type: user` is valid in
  scopes `user` and `machine` (still a problem in `project`). `MACHINE_PATH_PATTERN` is checked for scopes
  `project` **and** `user`; scope `machine` accepts everything else the parser accepts.
- **D3: One refusal message for both guarded stores.** The D16 problem reason becomes, for both `project`
  and `user`:
  `machine-specific path "<m>"; use ~ or a relative path, or keep the fact on this machine with --machine`.
  This changes PAN-3957's message text (its tests are updated in W1). A home-path operator fact written
  before this issue becomes a parse problem: `pan memory list --user` reports it and the index skips it.
  `pan memory sync --setup` migrates such files (D9); without sync, the operator moves them by hand
  (documented in W12).
- **D4: Rendering.** Section order: Project memory, Operator memory, Machine memory, joined by the existing
  `\n\n---\n\n`. New budget `MACHINE_MEMORY_CHAR_BUDGET = 2_000`. Section text per scope:

  | Scope | Heading | `sourceSuffix` | show hint | list hint |
  | --- | --- | --- | --- | --- |
  | `project` | `## Project memory` | `curated and committed with this repository` (unchanged) | `pan memory show <id>` | `pan memory list` |
  | `user`, synced | `## Operator memory` | `synced across your machines by pan memory sync` | `pan memory show --user <id>` | `pan memory list --user` |
  | `user`, not synced | `## Operator memory` | `not synced; pan memory sync --setup <git-url> shares it across machines` | same | same |
  | `machine` | `## Machine memory` | `this machine only, never synced` | `pan memory show --machine <id>` | `pan memory list --machine` |

  "Synced" is `isOperatorMemorySynced(input.dir)`, a sync `existsSync` (the launch path is synchronous,
  `materialize.ts`). **The launch path never touches the network**: no fetch, pull or git process is ever
  added to `render.ts`, `materialize.ts` or `muse-context.ts`. Freshness comes from the sync triggers (D11).
  `renderManagedMemorySections` gains `opts.machineDir?: string` (default `machineMemoryDir()`).
- **D5: The sync remote is the operator's.** Overdeck never creates the repository, never checks that it is
  private, and never stores the URL anywhere but `.git/config`. Docs tell the operator to use a private
  repository. Credentials come from the operator's git setup (SSH key or credential helper), the same as
  the vault (`git.ts:4-5`). Every printed or JSON-rendered remote URL goes through `redactRemoteUrl`
  (strips `userinfo@` from `scheme://userinfo@host/…`), so a token embedded in an HTTPS URL never reaches
  the terminal or the dashboard log.
- **D6: Git invocation.** Every git call is `promisify(execFile)('git', args, { cwd: dir, env: {
  ...process.env, GIT_TERMINAL_PROMPT: '0', OVERDECK_PAN_GIT_OP: '1' }, encoding: 'utf8', timeout })`.
  Network commands (`ls-remote`, `fetch`, `push`) use `timeout: SYNC_NETWORK_TIMEOUT_MS = 30_000`; local
  commands have no timeout. Commits pass `-c user.name=pan memory sync (<label>) -c
  user.email=memory-sync@overdeck.local`, so a machine with no global git identity still commits and
  every commit names its machine. Never `execSync`, never `git stash`, never `reset --hard` (the operator
  may have uncommitted facts in the store; contrast the vault's own clone, `git.ts:12-16`).
- **D7: Sync outcome type** (exported from `src/lib/memory/facts/operator-sync.ts`):

  ```ts
  export type OperatorMemorySyncOutcome =
    | { status: 'not-configured'; dir: string }
    | {
        status: 'synced';
        dir: string;
        committed: boolean;      // a local commit was made this run
        pulled: string[];        // fact files the merge changed, relative to dir
        pushed: boolean;         // a push succeeded this run
        conflicts: string[];     // ids of conflict copies written this run
        heldBack: HeldBackFile[];
      }
    | { status: 'offline'; dir: string; error: string; committed: boolean; heldBack: HeldBackFile[] }
    | { status: 'failed'; dir: string; error: string };

  export interface HeldBackFile { path: string; reason: 'secret-like content' | 'machine-specific path' }
  ```

  `syncOperatorMemory` **never throws**: every error becomes `offline` (any network command failed or
  timed out) or `failed` (anything else). A local commit made before an offline fetch stays and is pushed
  by the next sync; that is safe here because the sync merges instead of compare-and-swapping.
- **D8: The sync algorithm.** `syncOperatorMemory(opts?: { dir?: string; label?: string })` runs, under
  `withFileLock(`${dir}.lock`, …, { staleMs: 300_000 })` (a run can spend up to 3 × (fetch + push) × 30 s = 180 s on the network, so the stale window must exceed it; the lock file's parent `~/.overdeck/context/` is created first with `mkdir -p`):
  1. If `!existsSync(join(dir, '.git'))` return `not-configured`.
  2. If `join(dir, '.git', 'MERGE_HEAD')` exists (a crashed earlier run), run `git merge --abort`.
  3. `git add -A`. Then for every path in `git diff --cached --name-only --diff-filter=AMR -z` (R so a rename cannot bypass the check) that ends in
     `.md`, is not `README.md`, and has no `/`: read the file; if `redactSensitiveText(text) !== text`
     hold it back with reason `secret-like content`, else if `MACHINE_PATH_PATTERN.test(text)` hold it
     back with reason `machine-specific path`. Holding back is `git reset -q -- <path>`.
  4. If `git diff --cached --quiet` exits 1, commit with `-m "memory: sync from <label>"` (`committed: true`).
  5. `git fetch origin` (network). On failure return `offline`.
  6. If `git rev-parse --verify -q refs/remotes/origin/main` fails (the remote is empty): if `git rev-parse
     --verify -q HEAD` succeeds, `git push -u origin HEAD:main`; return `synced`.
  7. If `HEAD` does not exist (nothing local was committed): `git checkout -q -B main --track origin/main`;
     on failure return `failed` with git's stderr (an untracked held-back file that collides with a remote
     file is the only known cause); else `pulled` = `git ls-files` (every fact now present); go to 10.
  8. Record `pre = git rev-parse HEAD`, then `git merge --no-edit --allow-unrelated-histories origin/main`
     (with the D6 identity flags). On exit 0 go to 9. If it exits non-zero and `git diff --name-only
     --diff-filter=U` is non-empty, call `resolveSyncConflicts` (W6, D10) and commit the merge with
     `git commit --no-edit` (identity flags). Any other merge failure: `git merge --abort` if `MERGE_HEAD`
     exists, return `failed`.
     **Until W6 lands**, the conflict branch runs `git merge --abort` and returns `failed` with
     `merge conflict in <paths>; nothing was changed`. W6 replaces exactly that branch.
  9. `pulled` = `git diff --name-only <pre> HEAD` filtered to top-level `.md` files.
  10. If `git rev-list --count origin/main..HEAD` is greater than 0, `git push origin HEAD:main`. If the push
      fails and `isNonFastForward(stderr)` (copy the vault's regex, `git.ts:87-92`), go back to step 5; at
      most 3 attempts in total, then return `offline` with `push rejected 3 times`. Any other push failure
      returns `offline`. Success sets `pushed: true`.
  11. Return `synced`.
- **D9: Setup.** `setupOperatorMemorySync(remoteUrl, opts?: { dir?: string; machineDir?: string; label?: string })`
  returns `{ migrated: Array<{ id: string; to: string }>; kept: string[]; outcome: OperatorMemorySyncOutcome }`
  or throws `OperatorMemorySetupError` with a printable message. In order:
  1. If `.git` exists: read `git remote get-url origin`. Same URL ⇒ skip to step 5 (idempotent). Different
     URL ⇒ throw `already synced with <redacted url>; to switch, run git -C <dir> remote set-url origin <url>`.
     `.git` exists but `git remote get-url origin` fails (no origin: a hand-run `git init`, or a setup that died
     between `init` and `remote add`) ⇒ run `git ls-remote <url>` as in step 2, then only `git remote add origin
     <url>`, then go to step 5.
  2. `git ls-remote <url>` (network, from `os.tmpdir()` as cwd). Failure ⇒ throw
     `cannot reach <redacted url>: <stderr>`; **nothing on disk has changed yet**.
  3. Migrate: for every top-level `<id>.md` in the operator store whose text matches
     `MACHINE_PATH_PATTERN`, `rename` it to `<machineDir>/<id>.md` (`mkdir -p` first). If the destination
     exists, leave the file where it is and add the id to `kept` (it will be held back by every sync).
  4. `mkdir -p <dir>`, `git init -q`, `git symbolic-ref HEAD refs/heads/main` (works on every git version,
     unlike `git init -b`, which needs git 2.28+), then `git remote add origin <url>`.
  5. Run the D8 sync inside the same lock (factor D8 into an unexported `syncLocked(dir, label)` so setup
     does not re-take the lock). Return its outcome.
- **D10: Conflict resolution** (`resolveSyncConflicts`, W6). For each path in `git diff --name-only
  --diff-filter=U -z`, read its stages from `git ls-files -u -z -- <path>` (stage 2 = ours, 3 = theirs):
  - **Both stages present** (modify/modify or add/add): `git checkout --theirs -- <path>`. If the path is a
    top-level `<id>.md` that is not `README.md`, also write the conflict copy from `git show :2:<path>`.
  - **Only ours** (they deleted, we edited): `git checkout --ours -- <path>`.
  - **Only theirs** (we deleted, they edited): `git checkout --theirs -- <path>`.
  - Then `git add -- <path>`.

  Conflict copy id: `${id.slice(0, 80 - suffix.length)}${suffix}` with `suffix = '-conflict-' + labelSlug`,
  so it always matches `MEMORY_FACT_ID` (≤ 80 characters). Content: parse ours with
  `parseMemoryFact(file, text, 'user')`. If it parses, serialize with `serializeMemoryFact` after setting
  `review` to the de-duplicated `[...review, 'sync-conflict']` and `source` to `sync-conflict:<id>`; if it
  does not parse, write ours byte for byte (it then shows as a `Problems:` entry). The copy overwrites an
  existing copy with the same name (the newest local version wins the copy slot). `git add` the copy.
  Return the list of copy ids. The copy is committed by the merge commit (D8 step 8) and pushed, so the
  other machine sees both versions too.
- **D11: Sync triggers.** Exactly four, none at launch:
  1. `pan memory sync` (explicit verb, W7).
  2. `pan sync`: a step that runs **before** the `--if-changed` early return (`sync.ts:120`), skipped under
     `--dry-run` and `--backup-only`, silent when not configured (W9).
  3. The dashboard: a new service runs `syncOperatorMemory()` in-process 60 s after boot and every 15 min,
     single-flight, only when the store is synced, and not on a peer dashboard (W10). In-process is safe:
     every git call is async `execFile` (no `execSync`, rule `no-execsync-server`).
  4. `pan memory add|edit|retire --user`: after a successful write, when the store is synced, run one sync
     and print a one-line outcome (W8). `--project` and `--machine` writes never sync.
- **D12: CLI surface.**
  - `pan memory show|list|add|edit|retire` gain `--machine`. `--project`, `--user`, `--machine` and `--here`
    are mutually exclusive (error text `--project, --user, --machine and --here are mutually exclusive`).
    `add --type user` is allowed with `--user` or `--machine`; otherwise the refusal text becomes
    `user facts go in the operator store: add --user (or --machine for this machine only)`.
  - The `--user` option descriptions change from "(per-machine)" to "(travels with you; synced when set up)";
    for example `Write to the operator store (travels with you; synced when set up)`. `--machine`
    descriptions: `Read from the machine store (this machine only)` (show), `List the machine store (this
    machine only)` (list), `Write to the machine store (this machine only)` (add), `Edit the machine store
    (this machine only)` (edit), `Retire from the machine store (this machine only)` (retire).
  - `pan memory search` prints a third block `Machine memory:` (at most 5) after `Operator memory:`.
    `--json` stays the observation array only (PAN-3957 D13).
  - New verb `pan memory sync [--setup <git-url>] [--status] [--json]`. `--setup` and `--status` are mutually
    exclusive. Exit codes: plain sync exits 0 on `synced` (conflicts and held-back files print as yellow
    warnings), 1 on `not-configured`, `offline` or `failed`. `--setup` exits 1 when setup throws or its
    outcome is not `synced`. `--status` always exits 0.
  - Every new or changed flag lands in `sync-sources/skills/pan-memory/SKILL.md` and the regenerated
    composer manifest in the same commit (PAN-3957 NFR-4, NFR-6).
- **D13: Status** (`readOperatorMemorySyncStatus(opts?)`, no network): `{ configured: boolean; dir: string;
  remote: string | null /* redacted */; lastCommit: { sha: string; date: string; subject: string } | null;
  ahead: number; behind: number /* against the last fetched origin/main */; uncommitted: number /* git
  status --porcelain lines */; conflicts: string[] /* ids of facts whose review includes 'sync-conflict' */ }`.
- **D14: The universal rule stays terse.** `sync-sources/rules/project-memory.md` gains one clause, not a
  paragraph (operator feedback "rules must be terse").

## 4. Requirements

### Functional

- **FR-1** `machineMemoryDir()` returns `join(getOverdeckHome(), 'context', 'machine-memory')`, and
  `readMemoryFactsSync(dir, 'machine')` / `writeMemoryFact(dir, 'machine', …)` accept `type: user` and
  home-directory paths.
- **FR-2** `parseMemoryFact` with scope `user` or `project` returns the D3 problem for a home-directory path;
  `writeMemoryFact` therefore refuses it in both stores.
- **FR-3** Every launch composition renders `## Machine memory` (D4) when the machine store has ≥ 1 active
  fact, after `## Operator memory`; the operator section's source line says whether it is synced (D4).
- **FR-4** The dashboard Context preview renders the machine section from `<overdeckHome>/context/machine-memory`.
- **FR-5** `pan memory show|list|add|edit|retire --machine` read and write the machine store; `search`
  prints `Machine memory:` matches.
- **FR-6** `syncOperatorMemory` implements D8 and returns a D7 outcome without throwing; it never commits a
  held-back file.

## Planning Q&A

`pan plan --auto` (2026-10-21): no AskUserQuestion. The issue named its own example for Q1 (a private git
repository that `pan sync` pulls and pushes), and the planner adopted it. Q2 and Q3 had no stated default;
the planner chose the options in §0 and recorded all three in `plan.autoDecisions[]`, with these reasons:

- **Q1 → plain git clone of the operator store.** It follows the issue's example, keeps facts readable
  markdown (PAN-3957 Q3), and copies the vault's proven git mechanics without its encryption, which exists
  for transcripts, not for secret-guarded one-line facts.
- **Q2 → a separate machine store.** Git cannot ignore by content, and the existing reader already skips
  subdirectories, so a sibling directory is the one design that needs no exclude list and no second
  reader. Applying D16's guard to the operator store follows from the store now travelling.
- **Q3 → remote keeps the id, local becomes a review-marked conflict copy.** It loses nothing, never
  blocks an unattended sync, and reuses PAN-3957's review marker, so no new state is invented.

Additional choices made while planning: the dashboard runs the sync on a 15-minute timer (W10), because
`pan sync --if-changed` never runs when only a remote changed (§2 item 7), and without the timer a
long-running machine would pull only when the operator runs `pan sync`; and `--user` writes sync at once
(W8), so a fact an agent records reaches the other machines without waiting for the next timer.
