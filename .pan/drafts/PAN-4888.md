# PAN-4888 — A newer `pan reload` replaces a held one, so one approval ships the newest build

**Issue:** [PAN-4888](https://github.com/eltmon/overdeck/issues/4888)
**Planning mode:** `pan plan --auto` (no operator questions; every default is recorded under "Decisions").

## Glossary

- **Restart lock** — the file `~/.overdeck/restart.lock` (`src/lib/restart-lock.ts`). It holds one JSON record `{ pid, ts, caller }`. Only one process may hold it. `pan reload` takes it with `caller: 'pan reload'` and keeps it through build, approval wait, and restart.
- **Restart gate** — the operator approval step for voluntary restarts (PAN-3729). Client: `src/lib/restart-gate-client.ts` (`waitForRestartApproval`). Server: `src/dashboard/server/services/restart-gate.ts`, an in-memory request map. Banner: `src/dashboard/frontend/src/components/RestartApprovalBanner.tsx`.
- **Holder** — the `pan reload` process that currently holds the restart lock.
- **Newcomer** — a later `pan reload` that finds the lock held.
- **Target SHA** — the `origin/main` commit a reload resolves (after `git fetch origin main`) and builds. Today it is `DashboardDeployment.builtSha`.
- **Supersede** — the holder steps aside so the newcomer can build the newer target SHA and take the gate.
- **Supersede marker** — a new per-newcomer file `~/.overdeck/reload-supersede/<byPid>.json` that a newcomer writes, and rewrites on every poll, to ask one specific holder (by pid) to step aside.
- **Withdraw** — a new gate call, `POST /api/restart-gate/withdraw`, that removes a request from the gate only while it is outside an epoch. It is the atomic step that makes stepping aside safe.
- **Covered** — the newcomer's target is equal to, or an ancestor of, the holder's target, so the holder already ships everything the newcomer would.
- **Supersedable holder** — a lock record written by new code with `caller: 'pan reload'` and `supersedable: true`. Records from older CLIs lack the field.
- **Generation** — one of the two fixed build worktrees `~/.overdeck/deployments/dashboard/.pan-reload-generation-{a,b}` (`dashboardDeploymentRoots()` in `src/lib/deploy/build-from-origin.ts`).
- **Activation** — `activateDashboardDeployment()` swaps the primary checkout's `dist/` to the new build and returns `commit()`/`rollback()`.
- **Epoch** — one operator approval over the requests pending at that moment (server gate). A request that is part of an epoch reads `approved`/`claimed`, not `pending`.

## Problem

On 2026-11-03 the operator approved two dashboard restarts twice, and the first approval shipped a stale build.

- 00:03Z: a reload held the lock and waited about 2 hours for approval while five PRs merged. The Flywheel's `pan reload` exited with `restart in progress (held by PID 1195603 (pan reload))`. Approving the held reload deployed the pre-merge build `8a70af99fc6`; a second reload and a second approval were needed for `530ee175e8c`.
- 06:50Z: the same shape with PID 151912.

Root cause, verified in `src/cli/commands/reload.ts` at `a3e375f6819`:

1. Lines 182-191 — the newcomer is dropped:

   ```ts
   const lock = await acquireRestartLock('pan reload');
   if (!lock) {
     const holder = await readRestartLockHolder();
     const heldBy = holder ? `held by PID ${holder.pid} (${holder.caller})` : 'held by another process';
     const error = `restart in progress (${heldBy})`;
     ...
     process.exitCode = 2;
     return;
   }
   ```

2. Lines 232-298 build from the `origin/main` fetched at start (`buildDashboardFromOriginMain` fetches inside, `build-from-origin.ts` line 346). Lines 308-315 then call `waitForRestartApproval(...)` with no time limit while still holding the lock. So a held reload can only ever ship what `main` was when it started.

3. The banner (`RestartApprovalBanner.tsx` line 119, `const reasons = gate.pending.map((request) => request.reason || request.kind).join('; ');`) never shows `builtSha`, although the wire contract already carries it (`packages/contracts/src/types.ts` line 540, `builtSha: Schema.optional(Schema.String)`). The operator approves blind.

Facts verified during planning that shape the fix:

- `pan restart` waits on the gate **before** it takes the lock (`src/cli/commands/restart.ts` lines 619-634, `awaitRestartGate(scope)` then `acquireRestartLock('pan restart')`). So `pan reload` is the only caller that holds the lock while waiting for approval.
- Before the gate wait, the holder has already written `active-dashboard-bundle.json` for its new generation (`reload.ts` line 274, `await writeActiveDashboardBundle({`) and swapped primary `dist/` (`reload.ts` line 280, `activation = await activateDashboardDeployment(repoRoot, deployment);`). A holder that steps aside must undo both, the same way the restart-failure branch does (`reload.ts` lines 395-397).
- `deploy-progress.ts` line 73 (`if (last && last.trigger === RELOAD_CALLER && !last.success && last.phase !== 'stopping')`) turns any failed `pan reload` restart-status entry into a `Deploy ✗` chip for 15 minutes. A holder that steps aside must therefore write **no** restart-status entry.
- The server gate expires a request that is not refreshed for 20 s (`REQUEST_TTL_MS`) and lapses a claim after 5 minutes (`CLAIM_LAPSE_MS`). That rules out "rebuild after approval": a holder rebuilding for minutes after its claim stops polling, so its request expires and the epoch is pruned as `pruned-unclaimed` mid-build.

## Decisions

These were made in `--auto` mode. Each is final for the work agent.

- **D1 — Supersede, not refresh-at-approval.** The issue offered both. Supersede fixes both symptoms (the newer reload is no longer dropped, and the one waiting request is the newest build). Refresh-at-approval leaves the newer reload refused with exit 2 and a failed restart-status entry, and it delays the restart after the click by a full build, during which the gate request and claim expire (see Problem).
- **D2 — The supersede request is a per-newcomer file, not a gate field.** The holder may still be building and not yet polling the gate, so the request must exist outside the gate. Each newcomer owns `~/.overdeck/reload-supersede/<byPid>.json`, rewrites it on every 2 s poll, and deletes only its own file. Two newcomers can never overwrite or delete each other's request (critique finding 3).
- **D3 — Only supersedable `pan reload` holders step aside.** Holders with caller `pan restart`, `supervisor restart`, `supervisor watchdog`, or `pan connect`, and `pan reload` holders written by an older CLI (no `supersedable: true`), are refused exactly as today. This also makes the first deploy of this change safe: the installed (old) CLI is the holder, and the newcomer refuses at once instead of hanging.
- **D4 — Targets are compared by git ancestry, never by inequality alone.** The holder records its target SHA in the lock record. With `git merge-base --is-ancestor`: equal, or the newcomer's target is an ancestor of the holder's ⇒ **covered**, the newcomer exits 0 without building; the holder's target is a strict ancestor of the newcomer's ⇒ supersede; neither (diverged history) or a git error ⇒ refuse with exit 2. So an older, paused invocation can never replace a newer build (critique finding 2), and the Flywheel never rebuilds the same commit on every tick.
- **D5 — The target SHA is resolved before the lock and the build is pinned to it.** `pan reload` fetches and resolves `origin/main` first, records it in the lock, and builds exactly that commit. Without pinning, the build's own fetch could pick a later commit than the one recorded, and D4 would compare against the wrong SHA.
- **D6 — An approval already given is never thrown away; stepping aside goes through an atomic withdraw.** When the holder is asked to step aside and has already registered its gate request, it calls `POST /api/restart-gate/withdraw`. The server removes the request only when it is not part of an epoch, in the same synchronous transition that `approve` uses, so approve and withdraw are serialized. `withdrawn` ⇒ step aside. `kept` (an approval landed) ⇒ claim and restart as approved; the newcomer waits for the lock. A holder that has not registered yet (still before its first poll) has nothing to lose and steps aside directly. If the route answers 404 (a server older than this change) or does not answer, the holder steps aside as well; the residual race then is one poll interval on a server that cannot be approved through anyway when it does not answer (critique finding 1).
- **D7 — The newcomer waits at most 20 minutes for the holder to step aside** (`RELOAD_SUPERSEDE_WAIT_MS = 20 * 60_000`, poll every `RELOAD_SUPERSEDE_POLL_MS = 2_000`). The bound covers a holder that is still building (it checks the marker when it reaches the gate). On timeout the newcomer deletes its marker and refuses with exit 2.
- **D8 — A superseded holder exits 0, writes no restart-status entry, and reports a new composer phase `superseded`.** It is not a failure: a newer reload replaced it. A failed entry would light `Deploy ✗` (see Problem).
- **D9 — A marker is honored only by its target pid, only while its writer is alive, and only while it is fresh.** Fresh means rewritten within `RELOAD_SUPERSEDE_FRESH_MS = 30_000`. A newcomer killed mid-wait stops refreshing, so within 30 s its file is ignored even if its pid is later reused.
- **D11 — A holder asked to step aside keeps its build when the dashboard already runs it.** It compares `/api/health` `buildCommit` (the full `git rev-parse HEAD` of the build worktree, set in `src/dashboard/server/tsdown.config.ts` line 89) with its `builtSha`. Equal ⇒ commit like the `satisfied` branch; otherwise undo. This closes the window where `pan restart --now` or the dashboard's own restart button booted the holder's build during the wait.
- **D12 — The `pan dev` path runs before any target resolution.** When a `pan dev` supervisor marker exists, `pan reload` keeps today's path exactly: take the plain restart lock, signal SIGUSR2, return. It fetches nothing, so an unreachable origin never blocks a dev hot-restart (critique finding 4).
- **D10 — The banner and the CLI wait lines show the 12-character build SHA.** The `pan status` gate line stays as it is, to keep the plan within the 25-file surface limit; the issue only requires the banner. 12 characters match the existing `✓ Built dashboard from origin/main <12>` line (`build-from-origin.ts` line 373). A "main has moved past this build" indicator is out of scope (it needs a server-side comparison and a snapshot contract change); supersede already keeps the waiting build current whenever the Flywheel runs `pan reload`.

## Requirements

### Functional

- **FR-1** A `pan reload` without `--skip-build` that finds the lock held by a supersedable `pan reload` whose recorded `targetSha` is a strict ancestor of its own target SHA (or that recorded none) writes a supersede marker naming the holder's pid, waits for the lock, then builds its own target SHA and requests approval.
- **FR-2** A `pan reload` whose target SHA equals, or is an ancestor of, the holder's recorded `targetSha` exits 0 without building, prints the holder's pid and the holder's 12-character SHA, and writes no restart-status entry. A target whose history diverged from the holder's is refused with exit 2.
- **FR-3** A holder whose pid is named by a fresh marker whose writer is alive, and whose gate request the server agrees to withdraw (or that has not registered yet), steps aside. When the running dashboard's `/api/health` `buildCommit` equals the holder's `builtSha` (another restart already put this build live), it keeps the build exactly as the `satisfied` branch does. Otherwise it restores the previous active-bundle record, rolls back the primary `dist/` activation, and removes its generation worktree. Either way it writes no restart-status entry, prints that it was superseded, reports composer phase `superseded`, releases the lock, and exits 0.
- **FR-4** A holder whose gate request is part of an epoch (`approved` or `claimed`, including an approval that lands between two polls) keeps it: the withdraw answers `kept`, and the holder performs its approved restart.
- **FR-5** A newcomer that finds the lock held by a non-supersedable holder, or that runs with `--skip-build`, is refused exactly as today: exit code 2, the message `restart in progress (held by PID <pid> (<caller>))`, and a failed restart-status entry.
- **FR-6** A newcomer whose holder has not stepped aside within 20 minutes clears its own marker, prints that the holder did not step aside, records a failed restart-status entry, and exits 2.
- **FR-7** The reload builds exactly the target SHA it recorded in the lock.
- **FR-8** The restart banner shows `build <sha12>` for each waiting request that carries `builtSha`.
- **FR-9** The CLI wait lines name the build SHA of the request when it carries one.
- **FR-11** `POST /api/restart-gate/withdraw` with `{ requesterId }` removes that request from the pending list and answers `{ withdrawn: true }` when the request is not part of the open epoch and not satisfied; otherwise it changes nothing and answers `{ withdrawn: false, status }`. A missing `requesterId` answers 400.
- **FR-12** When a `pan dev` supervisor owns the dashboard, `pan reload` signals it without fetching `origin/main`.
- **FR-10** The reload skill, the merge-workflow doc and the Flywheel skill describe the supersede behavior and the exit codes.

### Non-functional

- **NFR-1** Every test of a poll or wait loop uses `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()`; no test waits on a real 2 s or 5 s delay.
- **NFR-2** Exactly one new HTTP route, `POST /api/restart-gate/withdraw`, with a row in `tests/unit/lib/overdeck/no-loss-matrix.ts`. The existing gate routes, their JSON shapes and `RestartGateSnapshot` do not change.
- **NFR-3** No approval timeout is added. The gate wait stays unbounded (PAN-3729 property).
- **NFR-4** A marker never makes any process other than its `targetPid` step aside, and a newcomer never deletes a marker file other than its own.
- **NFR-5** No `execSync` and no `*Sync` child-process call in any touched file (CLI code shares lib modules with the server).

### WI-2 `supersede-protocol` — new module with per-newcomer markers and the newcomer's lock loop

**Why:** one place owns the supersede protocol (FR-1, FR-2, FR-5, FR-6, D2, D3, D4, D7, D9, NFR-4).

**New file:** `src/lib/deploy/reload-supersede.ts`. **New test:** `tests/unit/lib/deploy/reload-supersede.test.ts` (`@vitest-environment node`, temp `OVERDECK_HOME` like `src/lib/__tests__/restart-lock.test.ts`, fake timers for the loop, every git and lock call injected).

Module header comment: a newer `pan reload` replaces a waiting one (PAN-4888); name the marker directory; state the D3, D4, D6 and D9 rules in one sentence each.

Exports (exact names):

```ts
export const RELOAD_CALLER = 'pan reload';
export const RELOAD_SUPERSEDE_POLL_MS = 2_000;
export const RELOAD_SUPERSEDE_WAIT_MS = 20 * 60_000;
export const RELOAD_SUPERSEDE_FRESH_MS = 30_000;

export interface ReloadSupersedeRequest {
  readonly targetPid: number;   // the holder asked to step aside
  readonly byPid: number;       // the newcomer that asked (also the file name)
  readonly targetSha: string;   // the newcomer's target SHA
  readonly refreshedAt: string; // ISO time of the last rewrite
}

export function reloadSupersedeDir(): string;                         // join(getOverdeckHome(), 'reload-supersede')
export function reloadSupersedeFile(byPid: number): string;           // join(reloadSupersedeDir(), `${byPid}.json`)
export async function writeReloadSupersedeRequest(request: ReloadSupersedeRequest): Promise<void>; // mkdir -p, tmp file + rename into reloadSupersedeFile(request.byPid), mode 0o600
export async function deleteOwnReloadSupersedeRequest(byPid: number): Promise<void>;               // unlink reloadSupersedeFile(byPid); ENOENT is fine; never touches another pid's file
export async function listReloadSupersedeRequests(): Promise<ReloadSupersedeRequest[]>;            // readdir + parse; skip unreadable or bad-shape files; [] when the dir is missing

/** Holder side: the detail line when a live, fresh newcomer asked this pid to step aside, else null. */
export async function reloadSupersedeDetail(
  pid: number = process.pid,
  deps?: { readonly isAlive?: (pid: number) => boolean; readonly now?: () => number },
): Promise<string | null>;

export type ReloadLockOutcome =
  | { readonly kind: 'acquired'; readonly lock: RestartLockHandle }
  | { readonly kind: 'covered'; readonly holder: RestartLockHolder }
  | { readonly kind: 'refused'; readonly message: string };

export interface AcquireReloadLockDeps {
  /** `git merge-base --is-ancestor ancestor descendant`: true, false, or throws on a git error. */
  readonly isAncestor: (ancestor: string, descendant: string) => Promise<boolean>;
  readonly acquire?: typeof acquireRestartLock;
  readonly readHolder?: typeof readRestartLockHolder;
  readonly now?: () => number;
  readonly sleep?: (ms: number) => Promise<void>;
  readonly pid?: number;
  readonly log?: (message: string) => void;
}

export async function acquireReloadLock(
  targetSha: string | undefined,
  deps: AcquireReloadLockDeps,
): Promise<ReloadLockOutcome>;
```

`defaultIsAlive(pid)` is `process.kill(pid, 0)` returning true, or true on `EPERM`, false otherwise (same as `isProcessAlive` in `restart-lock.ts`; copy it, do not export the private one).

`reloadSupersedeDetail(pid)` lists the requests and keeps those with `targetPid === pid`, `isAlive(byPid)`, and `now() - Date.parse(refreshedAt) < RELOAD_SUPERSEDE_FRESH_MS`. With none it returns null. Otherwise it takes the most recently refreshed one and returns: `superseded by a newer pan reload (PID <byPid>) that builds origin/main <targetSha.slice(0, 12)>`. It never deletes files.

**Target comparison** (private helper `compareTargets(holderSha, ownSha, isAncestor)` returning `'covered' | 'supersede' | 'diverged'`):

1. `holderSha === ownSha` ⇒ `covered`.
2. `await isAncestor(ownSha, holderSha)` ⇒ `covered` (the holder's build is newer and contains ours).
3. `await isAncestor(holderSha, ownSha)` ⇒ `supersede`.
4. Otherwise, or when `isAncestor` throws ⇒ `diverged`.

Cache the result per `holder.pid` + `holder.targetSha` so git runs once per holder, not once per poll.

`acquireReloadLock` algorithm (decision rules, in order, inside a loop; `deadline = now() + RELOAD_SUPERSEDE_WAIT_MS`). **Every return path first calls `deleteOwnReloadSupersedeRequest(pid)`.**

1. `lock = await acquire(RELOAD_CALLER, { targetSha, supersedable: true })` (omit `targetSha` when undefined). A lock ⇒ return `{ kind: 'acquired', lock }`.
2. `holder = await readHolder()`. Null (freed between the two calls) ⇒ go to step 7.
3. `heldBy = \`held by PID ${holder.pid} (${holder.caller})\``. If `targetSha` is undefined (a `--skip-build` newcomer), or `holder.caller !== RELOAD_CALLER`, or `holder.supersedable !== true` ⇒ return `{ kind: 'refused', message: \`restart in progress (${heldBy})\` }`. This message is byte-identical to today's.
4. If `holder.targetSha` is set: `compareTargets(holder.targetSha, targetSha)`. `covered` ⇒ return `{ kind: 'covered', holder }`. `diverged` ⇒ return `{ kind: 'refused', message: \`restart in progress (${heldBy}); its build ${holder.targetSha.slice(0, 12)} and origin/main ${targetSha.slice(0, 12)} have diverged, so it was not replaced\` }`. `supersede` ⇒ continue. A holder without `targetSha` (a `--skip-build` reload) ⇒ continue.
5. Write (or rewrite) the own marker `{ targetPid: holder.pid, byPid: pid, targetSha, refreshedAt: new Date(now()).toISOString() }` on **every** iteration that reaches this step, so it stays fresh and follows a new holder pid.
6. The first time a given `holder.pid` reaches step 5, log: `A reload of origin/main ${holderSha} holds the restart lock (PID ${holder.pid}); asked it to step aside for origin/main ${targetSha.slice(0, 12)}.` where `holderSha` is `holder.targetSha?.slice(0, 12) ?? 'an unbuilt reload'`.
7. If `now() >= deadline` ⇒ return `{ kind: 'refused', message: \`restart in progress (${heldBy}); it did not step aside for a newer reload within 20 minutes\` }` (use `held by another process` when the last holder read was null).
8. `await sleep(RELOAD_SUPERSEDE_POLL_MS)` and loop.

Tests (fake timers; injected `acquire`, `readHolder`, `isAncestor`; marker files in a temp `OVERDECK_HOME`):

- `refuses a non-reload holder with today's message` — holder `{ caller: 'pan restart', pid: 77 }` ⇒ message exactly `restart in progress (held by PID 77 (pan restart))`; no marker file.
- `refuses an old-CLI reload holder that is not supersedable`.
- `refuses a skip-build newcomer`.

### WI-3 `gate-yield-hook` — `waitForRestartApproval` steps aside only through a withdraw

**Why:** the holder needs a safe point to step aside that never discards an approval, even one that lands between two polls (FR-3, FR-4, D6).

**File:** `src/lib/restart-gate-client.ts`. **Test:** `tests/unit/lib/restart-gate-client.test.ts`.

Steps:

1. Add a client call (same style as `claimRestartGate`):

   ```ts
   export type RestartGateWithdrawResult = 'withdrawn' | 'kept' | 'absent' | 'unavailable';

   /**
    * PAN-4888: remove this request from the gate only while it is outside an
    * epoch. `kept` means an approval already covers it and it must restart.
    */
   export async function withdrawRestartGateRequest(
     requesterId: string,
     options: RestartGateHttpOptions = {},
   ): Promise<RestartGateWithdrawResult> {
     const result = await gatePost<{ withdrawn?: boolean }>(
       '/api/restart-gate/withdraw', { requesterId }, options, GATE_CALL_TIMEOUT_MS,
     );
     if (result.kind === 'absent') return 'absent';
     if (result.kind === 'unavailable') return 'unavailable';
     return result.payload.withdrawn === true ? 'withdrawn' : 'kept';
   }
   ```

2. Add to `RestartGateWaitOptions`:

   ```ts
   /**
    * PAN-4888: asked at the top of every loop iteration while this request is
    * outside an epoch. A non-null string asks this requester to step aside; it
    * does so only after the gate agrees to withdraw the request.
    */
   readonly shouldYield?: () => Promise<string | null>;
   ```

3. Extend the outcome union: `| { readonly proceed: false; readonly reason: 'superseded'; readonly detail: string }`.

4. In the loop keep `let registered = false;` (set true after any poll with `kind === 'ok'`) and `let inEpoch = false;` (after an ok poll: `poll.payload.status === 'approved' || poll.payload.status === 'claimed'`; unchanged on `unavailable`). At the **top** of each iteration, when `options.shouldYield && !inEpoch`:

   ```ts
   const detail = await options.shouldYield();
   if (detail) {
     const withdrawal = registered
       ? await withdrawRestartGateRequest(request.requesterId, options)
   ```

## Edge cases and how the plan handles them

- **Holder is still building** when the newcomer arrives: the newcomer writes the marker and waits (D7); the holder checks the marker before its first gate poll and steps aside.
- **Approval lands at the same moment:** the holder steps aside only after the server withdraws its request, and the server refuses once an epoch covers it (D6, WI-10). Then the holder claims and restarts with its build; the newcomer takes the lock, builds the newer commit, and asks once more. That second approval is real: the newer commit was never approved.
- **Two newcomers race:** each writes its own marker file; one acquires the lock; the other then sees that one as the holder and, with the same or an older commit, exits 0 as `covered`. If one waiter dies, the other's marker is untouched and still fresh.
- **An older invocation resumes late:** it resolved commit A, then paused while a newer reload took the lock for B. A is an ancestor of B, so it exits 0 as `covered` and never writes a marker (D4).
- **Diverged history (force-push to main):** neither target contains the other ⇒ refused with exit 2 and a `have diverged` message; nothing is replaced.
- **Newcomer is killed mid-wait:** its marker stops refreshing and its `byPid` is dead, so the holder ignores it (D9) and keeps waiting.
- **Old CLI holder during the first deploy of this change:** not supersedable ⇒ immediate refusal as today (D3).
- **Operator clicks approve after the holder stepped aside:** the withdraw removed the request at once, so the banner already cleared; an approve now finds nothing pending and says so. The newcomer's request appears when its build finishes.
- **`--skip-build` newcomer:** never supersedes (it carries no build) ⇒ refused as today.
- **`pan dev` session owns the dashboard:** the dev branch runs first and fetches nothing (D12).

## Critique response

Round 1 critic (`.pan/drafts/PAN-4888-critique.md`) raised four design findings. All four were valid and the design changed for each.

### Approval can be discarded between polls

Accepted. Checking the marker before each poll left a window: an approval during the 5 s sleep put the request in an epoch the holder had not seen yet. The holder now steps aside only through a new atomic `POST /api/restart-gate/withdraw` (WI-10). The server's transition is synchronous like `approve`, so the two are serialized: a request already in the epoch answers `withdrawn: false`, and the holder claims and restarts instead (WI-3, D6). NFR-2 now allows exactly this one route, with its no-loss matrix row. A test drives the exact interleaving (approval during the sleep, then a marker). The only residual case is a gate that answers 404 for the route (a server older than this change) or does not answer; there the holder steps aside as before, which D6 records.

### An older target can replace a newer build

Accepted. Inequality is not an ordering. Targets are now compared with `git merge-base --is-ancestor` (new `isAncestorCommit`, WI-4; `compareTargets`, WI-2): equal or older ⇒ `covered` (exit 0, no marker), strictly newer ⇒ supersede, diverged or git error ⇒ refused with exit 2. Tests cover the paused older invocation and diverged history. No re-resolve on contention is needed: the ancestry check alone guarantees a replacement only ever moves forward, and a newcomer whose fetch was stale simply exits as covered.

### One marker loses concurrent waiters

Accepted. Markers are now per newcomer (`~/.overdeck/reload-supersede/<byPid>.json`), rewritten on every 2 s poll, and each newcomer deletes only its own file by path (no read-then-unlink). The holder lists the directory and honors any fresh marker from a live writer that names it (D2, D9). Tests cover two waiters where one dies, and stale or dead markers being ignored.

### Target fetch breaks the pan dev shortcut

Accepted. The `pan dev` branch now runs first, before any target resolution, with today's plain lock, SIGUSR2, messages and exit codes (D12, WI-5 step 1). A new test proves a dev-mode reload signals while `git fetch` would fail and never calls `acquireReloadLock`.

### Unresolved after two critic rounds

- A lost first poll can discard an approval
- Failed withdraw is treated as permission to yield
- Unreadable health can delete a live generation
- A PID-only marker can address a different process
