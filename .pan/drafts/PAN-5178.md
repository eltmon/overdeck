# PAN-5178: A deep-linked drawer waits 1 to 2 s because its request is issued last in the tab-open burst

**Issue:** [PAN-5178](https://github.com/eltmon/overdeck/issues/5178)
**Status:** draft (planning, `pan plan --auto`)

## Glossary

- **Boot burst**: the about 45 REST requests a dashboard tab sends in the first 100 ms after `domcontentloaded` (settings, status chips, banners, the drawer's reads). Measured list: see "Evidence".
- **HTTP/1.1 connection pool**: Chromium sends at most 6 requests at a time to one HTTP/1.1 origin. Requests beyond 6 wait in the browser. `http://localhost:3011` and the desktop shell are HTTP/1.1. `https://overdeck.localhost` (Traefik) is HTTP/2, which has no such limit.
- **Queued time**: the time between a request's Playwright `request` event and `request.timing().requestStart`. It is time spent in the browser, before the server sees the request.
- **TTFB**: time to first byte, `timing().responseStart - timing().requestStart`. It is the server's share.
- **Session mint**: `POST /api/dashboard/session`, sent by `ensureDashboardSession()` in `src/dashboard/frontend/src/lib/wsTransport.ts` (line 133, `export function ensureDashboardSession(url?: string): Promise<void> {`). It returns the CSRF token and refreshes the session cookie. It is memoized in the module variable `dashboardSessionPromise`.
- **RPC client gate**: the `WsTransport` constructor (`wsTransport.ts`, line 237) builds its RPC client only after the session mint resolves: `this.clientPromise = ensureDashboardSession(url).then(() => ...)`. So `/ws/rpc` sends no RPC (no `getSnapshot`, no subscriptions) until the mint returns.
- **Issue record read**: `GET /api/issues/:id`, added by PAN-5171. The frontend reads it through `fetchIssueRecord(issueId)` under the React Query key `issueRecordQueryKey(issueId)` = `['issue', issueId.toUpperCase()]`, both exported from `src/dashboard/frontend/src/components/issue-view/useIssueRecord.ts` (lines 9 and 24).
- **Deep link**: a page load whose URL names an issue: `?issue=<ID>` on any route (read by `readDrawerFromUrl` in `src/dashboard/frontend/src/lib/store.ts`, line 168), or the path `/issues/<ID>` (parsed by `getIssueIdFromPath` in `src/dashboard/frontend/src/App/routes.ts`, line 68).
- **Shared-conversation route**: a page whose hash matches `#/shared/<code>`, detected by `sharedRouteCode(hash)` in `src/dashboard/frontend/src/components/chat/sharing/joinApi.ts` (line 14). It renders a guest view with no dashboard session.
- **Snapshot path**: the server work for one `pan.getSnapshot` RPC: `ReadModelService.getSnapshot` (`src/dashboard/server/read-model.ts`, line 407), then the Effect RPC server's schema encode of the `Exit` and `JSON.stringify` (`RpcSerialization.layerJson`), then the WebSocket send.
- **Event-loop delay**: what `perf_hooks.monitorEventLoopDelay()` records; its `max` is the longest time the loop could not run a timer.

## Problem

Opening `/?issue=PAN-5170` in a fresh tab shows the drawer's loading state for about 2.2 s. The issue's hypothesis was that the first `/ws/rpc` snapshot blocks the event loop. Planning measured it. The hypothesis is wrong, and the real cause is request ordering.

### Evidence (measured 2026-11-13 on build 6ce53e6402d, 1,450 issues, 1,662 agents)

Scripts are in the planning session scratchpad. Their logic is restated in WI-5, which makes them a committed check.

1. **The issue read is fast on the server and slow in the browser.** On `http://localhost:3011`, signed in, the drawer's `GET /api/issues/PAN-5170` took 1,085 to 2,394 ms in total. It was queued for 1,094 to 2,348 ms and had a TTFB of 3 to 72 ms. Standalone it answers in 1 ms.
2. **The session mint is also issued last.** `POST /api/dashboard/session` was the last of about 45 requests, queued 1,440 to 1,984 ms. All three RPC sends (`subscribeDomainEvents`, `getSnapshot`, `subscribeIssueEvents`) left the socket within 10 ms of the mint returning. The socket itself had opened about 2 s earlier.
3. **Slow status reads hold the 6 slots.** `/api/prerequisites` (0.8 to 2.1 s, no cache), `/api/claude-code/status` (0.5 to 1.4 s), `/api/flywheel/status` (0.2 to 1.7 s), `/api/workspace-registry` (333 KB, 1.2 s and more). These are all in-burst numbers. `/api/settings/codex-auth` answers in 11 ms standalone, so its 1.2 s in-burst TTFB came from server load, not from the endpoint.
3a. **Top-level `main.tsx` requests already go first.** The two requests `main.tsx` sends at module top level (`reconcileFromServer`: `/api/settings`, `/api/color-themes`) left at `domcontentloaded` with `queued=0` and finished in 97 to 191 ms, about 90 ms before the component burst. This is direct evidence that a request started from `main.tsx` before render beats the burst.
4. **On HTTP/2 the server is the queue.** On `https://overdeck.localhost`, signed in, nothing queues in the browser. But the issue read's TTFB was 1,008 ms and the session mint's TTFB was 1,431 ms. The server was busy with the burst, and these two requests arrived behind it.
5. **Requests issued first are fast on both origins.** An init script that fired the mint and the issue read at `domcontentloaded` got the mint back in 41 to 52 ms and the issue (with its title) in 108 to 121 ms. That held on both origins and in three runs. The app's own later copies of the same requests still took 1.0 to 1.8 s.
6. **The snapshot path is not the stall.** Server log: `getSnapshot resolved in 3ms` to `11ms`. Offline, on the real 5.5 MB payload, the first encode in a fresh process (cold JIT) took 91 to 96 ms (schema encode of the `Exit` 64 to 65 ms, `JSON.stringify` 23 to 26 ms, `TextEncoder` 4 to 5 ms). Warm encodes took 43 to 65 ms. On the WI-4 fixture shape (1,500 issues with 2,400-character descriptions, 100 agents), cold took 52 to 63 ms and warm 28 to 35 ms. Issue `description` is 3.5 MB of the payload (61%). So the first connect after a server start, at production volume, is about 100 to 110 ms. Every later connect is about 55 to 75 ms. That is far below the 1.5 s stall.
7. **The dashboard is busy in the background.** `[event-loop-monitor] Dashboard event loop p99 delay ... exceeded 100ms` appears 24,013 times in `~/.overdeck/logs/dashboard.log`. With no tab opening, the server process averaged 73% CPU, and single pings stalled up to 1.5 s. During the burst, pings from another client stalled 280 to 433 ms.

**What this issue does not fix.** The issue also says other clients (CLI calls, agents' MCP tools, webhooks) stall when a tab opens. That is true, but the cause is the whole burst landing on a busy server, not the snapshot. This plan fixes the deep-linked drawer and the session mint only. The server-side burst congestion and the slow status endpoints are filed as [PAN-5180](https://github.com/eltmon/overdeck/issues/5180), with the numbers above.

### Why the mint is last

`ensureDashboardSession()` runs its `fetch` inside a `.then()` callback, which is a microtask. `getTransport()` is first called from a React effect in `EventRouter.tsx` (line 227 or 394). By then the same React commit has already queued about 40 component `fetch` calls in the same task. The mint therefore joins the queue at the end. The drawer's issue read comes from `useIssueRecord`'s `useQuery`, which is also near the end of that commit.

## Proposal

1. Start the session mint and the deep-linked issue read from `main.tsx`, before `ReactDOM.createRoot(...).render(...)`. Both requests then leave the browser first, before any component mounts. This puts them first in the HTTP/1.1 pool and first at the server on HTTP/2. React Query dedupes the drawer's later read onto the prefetched result, and `dashboardSessionPromise` dedupes the transport's mint.
2. Remove a per-connect deep copy from the snapshot path. `cleanIssues` (read-model.ts, line 169) deep-walks every issue (`toJsonish`) on every `getSnapshot`. That also happens every 500 ms while any issue stream is open, through `getCachedAgentIssueLookup` in `ws-rpc.ts` (line 314). Memoize the result by source-array identity, which is stable because `IssueDataService.getIssues()` returns a cached array (`issue-data-service.ts`, lines 393 to 417).
3. Add the two tests the issue asks for: an event-loop delay test for a `/ws/rpc` `getSnapshot` with 1,500 issues, and a Playwright latency check of the deep link (a committed script with `--assert`).
4. Document the boot order and the snapshot cost.

## Decisions

- **D-1 Fix ordering, not the snapshot.** Measurement refuted the hypothesis (Evidence 1 to 6). The issue marks the hypothesis "unconfirmed" and makes "Confirm" step 1, and its two acceptance criteria are outcomes, not mechanisms. So this plan keeps both acceptance criteria and changes the fix. The issue's three snapshot options (chunked build, pre-serialized snapshot, small first frame) are not built. A warm connect's snapshot path is about 55 to 75 ms (handler plus encode plus stringify), which is under the 100 ms criterion. Only the first connect after a server start, at production agent volume, reaches about 100 to 110 ms, from JIT warm-up.
- **D-2 One boot module.** A new module `src/dashboard/frontend/src/lib/bootRequests.ts` owns everything that must leave the browser before React mounts. `main.tsx` calls `startBootRequests(queryClient)` once. The module exports `startBootRequests` and `deepLinkedIssueId`, so tests cover it without importing `main.tsx`.
- **D-3 Do not demote other fetches.** Planning tested `fetch(..., { priority: 'low' })`: it works in Chromium only if every other boot fetch is marked low (30+ call sites). Raising the critical fetch to `priority: 'high'` did nothing. With 6 slow requests in flight, a prioritized request still waited 1,010 ms. Issuing first is one file and needs no call-site discipline.
- **D-4 Fire both requests in parallel, not chained.** The issue read does not wait for the mint. If it waited, it would land behind the React commit's burst again. A browser with no cookie yet (first visit from a remote device) gets 401 on the prefetch. React Query then keeps an error with no data, and `useIssueRecord`'s `useQuery` refetches on mount, so the result matches today.
- **D-5 Scope of the deep link.** `?issue=<ID>` (any route) and `/issues/<ID>` only. The cockpit route `/command-deck/<project>/<issue>` is a NonGoal.
- **D-6 The shared-conversation route sends nothing.** On `#/shared/<code>`, `startBootRequests` returns without sending either request. That route is a guest view, and a root mint there could set `sessionAuthFailed` for a guest. The native shell needs no check, because `ensureDashboardSession` already returns early there (`isNativeShell()`, `wsTransport.ts` line 135).
- **D-7 Errors are swallowed at the boot call site.** `startBootRequests` calls `void ensureDashboardSession().catch(() => {})`. `ensureDashboardSession` already resets `dashboardSessionPromise` to `null` on failure and sets `sessionAuthFailed` on 401, so the transport's own later call retries. The prefetch uses `queryClient.prefetchQuery`, which never rejects.
- **D-8 Memoize `cleanIssues` by input identity.** A module-level `WeakMap<readonly unknown[], unknown[]>` inside `cleanIssues`. All three call sites (read-model.ts lines 425, 639 and 663) pass `IssueDataService.getIssues()` output or the `onIssuesChanged` argument, which is the same cached array. A new poll result is a new array, so it misses the cache and is cleaned. Reducers never mutate `issuesRaw` entries in place: every `issuesRaw` write in `packages/contracts/src/event-reducers.ts` (lines 795 to 910) replaces or maps. `applyIssueDelta` (`packages/contracts/src/issue-delta.ts`, line 17) writes only into `previous.slice(0, delta.length)`, a copy. So sharing cleaned rows across snapshots is safe.
- **D-9 The event-loop test uses a test RPC group.** The test serves `RpcGroup.make(GetSnapshotRpc)`, with `GetSnapshotRpc` from `@overdeck/contracts`. It runs over the real `RpcServer.toHttpEffectWebsocket` and `RpcSerialization.layerJson`, against a real `ReadModelServiceLive`. It does not mount `websocketRpcRouteLayer`, which needs `EventStoreService`, `TerminalService` and `PanOpen` stubs. The production handler (`ws-rpc.ts`, lines 751 to 769) only adds a log line and `mapError` around the same call. The handler layer mirrors `PanRpcGroup.toLayer(Effect.gen(...))` (`ws-rpc.ts`, line 696), and the handler key is the RPC tag `'pan.getSnapshot'` (`WS_METHODS.getSnapshot`, `packages/contracts/src/rpc.ts` line 46):

```ts
const group = RpcGroup.make(GetSnapshotRpc);
const handlers = group.toLayer(Effect.gen(function* () {
  const readModel = yield* ReadModelService;
  return group.of({ [WS_METHODS.getSnapshot]: () => readModel.getSnapshot });
}));
// Layer.mergeAll(handlers, RpcSerialization.layerJson), provided with
// ReadModelServiceLive.pipe(Layer.provide(mockAgentsResolverLayer))
```
- **D-9a Two limits: warm connects and the first connect.** Cold JIT makes the first encode about 1.6 times slower (Evidence 6). So NFR-1 is split.
  - **Warm (NFR-1):** 1,500 issues and 100 agents. One unmeasured warm-up connect, then three measured connects, each with its own histogram. The smallest of the three `max` values must be under 100 ms. A single sample also absorbs GC and runner preemption. A real synchronous span longer than 100 ms shows in every run, so the smallest still catches a regression.
  - **First connect (NFR-1b):** 1,500 issues and 1,700 agents (production volume), measured on the first connect in a fresh test-file process, so the encode code is cold. Its `max` must be under 300 ms. Locally the full production payload's cold encode plus stringify measured 91 to 96 ms, and the handler adds 3 to 11 ms. This one-time JIT warm-up per server process is accepted, and the limit guards against the 1 s class of stall.
  - The test prints every value.
- **D-9c The histogram stays on through one timer turn.** `monitorEventLoopDelay` records a delay only when its own timer fires. A synchronous span can end, and the reply can be read, before that timer runs. So after the reply arrives, the test waits one 20 ms `setTimeout` turn before `h.disable()`. A self-check test proves the harness works: it injects `setImmediate(() => busyWait(120))` inside an enabled window, then asserts `max >= 100`. `busyWait(ms)` spins on `performance.now()`. The 20 ms turn is the only timer wait the test may use.
- **D-9b `_queryClient` in WI-1.** The frontend tsconfig sets `noUnusedParameters: true` (`src/dashboard/frontend/tsconfig.json`, line 20). TypeScript exempts parameters whose names start with `_`, so WI-1 declares `_queryClient`, and WI-2 renames it to `queryClient` when it starts using it.
- **D-10 Fixture size.** 1,500 issues, each with a 2,400-character `description` (the measured average is 3,477 KB over 1,450 issues). The warm test uses 100 stored agents. The first-connect test uses 1,700, which matches production's 1,662. The acceptance criterion names 1,500 issues. Pruning agents is a separate concern (NonGoals).
- **D-4a The issue read recovers once the session is up.** The early issue read can answer 401 when this browser has no credential yet. That happens on a first visit with `#pair=<credential>` (the exchange runs before the mint, `wsTransport.ts` lines 117 to 145) or with `#overdeck_token=`, because `remote-request-gate.ts` (lines 150 to 166) gates the read until a credential exists. TanStack Query calls the query function synchronously, so the issue read leaves even before the mint. `useIssueRecord` uses `retry: false`. So `startBootRequests` waits for both the prefetch and the session. If the session succeeded and the issue query is in `error`, it calls `queryClient.invalidateQueries({ queryKey, exact: true })`. A mounted hook then refetches, and an unmounted one fetches on mount, because the query is stale. An authenticated tab keeps the parallel fast path.
- **D-11 The Playwright check is a committed script, not a CI spec.** `scripts/verify-deep-link-latency.mjs` follows `scripts/verify-dashboard-performance.mjs` (a `--base-url` flag and an `--assert` flag). A CI spec cannot show the queue: `tests/e2e/styleguide-conformance.spec.ts` replaces `window.fetch` (line 219), so no request reaches a socket.
- **D-11a The branch frontend is verified through Vite against the running API.** WI-1 and WI-2 change only the frontend. The Vite dev server proxies `/api` and `/ws` to `VITE_PROXY_TARGET`, default `http://127.0.0.1:3011` (`src/dashboard/frontend/vite.config.ts`, lines 16 to 30 and 84 to 90). It serves the page over HTTP/1.1, so the browser's 6-request limit applies. WI-7 runs the script against `http://127.0.0.1:3019`, where `cd src/dashboard/frontend && npx vite --port 3019 --strictPort` serves the branch frontend in front of the running dashboard. No branch-built dashboard server is needed. The test role repeats the same run in its own isolated browser (AC-7).
- **D-12 Thresholds.** The issue read completes within 300 ms of its `request` event, and the drawer shows the real title within 1,000 ms of `domcontentloaded`. Both come from the issue. Event-loop `max` during the test connect is under 100 ms. Never raise a threshold to make a test pass.

## Requirements

- **FR-1** On a normal dashboard load, the frontend sends `POST /api/dashboard/session` before any React component's request. It is sent from `startBootRequests`, called in `main.tsx` before `ReactDOM.createRoot`.
- **FR-2** On a deep link (`?issue=<ID>` or `/issues/<ID>`), the frontend sends `GET /api/issues/<ID>` from `startBootRequests` before React renders, and stores the result under `issueRecordQueryKey(<ID>)`.
- **FR-3** A `useIssueRecord(<ID>)` that mounts after the prefetch adds no second `GET /api/issues/<ID>`.
- **FR-4** On the shared-conversation route, `startBootRequests` sends no request.
- **FR-5** `cleanIssues` returns the same output array for the same input array, and cleans a new input array as before (Dates to ISO strings, non-finite numbers to `null`, cycles to `null`).
- **FR-6** A committed script measures the deep-link issue read and the drawer title against a live dashboard, and exits non-zero under `--assert` when a threshold is exceeded.
- **FR-7** When the early issue read fails because the session was not ready (for example a pairing first visit), the issue query refetches after the session succeeds, and the drawer shows the title.
- **NFR-1** Warm connects: event-loop delay `max` stays under 100 ms while a WebSocket client connects to the RPC server and completes `pan.getSnapshot` with a 1,500-issue read model (smallest of three measured connects after one warm-up).
- **NFR-1b** First connect in a fresh process at production volume (1,500 issues, 1,700 agents): event-loop delay `max` stays under 300 ms.
- **NFR-2** The snapshot wire format is unchanged: same RPC, same schema, same fields. The client needs no change.
- **NFR-3** No new synchronous child-process or filesystem call in server code. The change adds none.

   Rewrite the body of `startBootRequests` as below. The parameter is renamed `queryClient`, and the WI-1 mint line becomes the `session` constant:

```ts
export function startBootRequests(queryClient: QueryClient, location: BootLocation = window.location): void {
  if (sharedRouteCode(location.hash)) return
  const session = ensureDashboardSession()
  void session.catch(() => {})
  const issueId = deepLinkedIssueId(location)
  if (!issueId) return
  const queryKey = issueRecordQueryKey(issueId)
  const prefetch = queryClient.prefetchQuery({
    queryKey,
    queryFn: () => fetchIssueRecord(issueId),
    staleTime: 30_000,
  })
  // D-4a: a first visit (#pair=, #overdeck_token=) has no credential until the
  // session settles, so the early read may answer 401. Refetch it then.
  void Promise.allSettled([prefetch, session]).then(([, sessionResult]) => {
    if (sessionResult.status !== 'fulfilled') return
    if (queryClient.getQueryState(queryKey)?.status !== 'error') return
    void queryClient.invalidateQueries({ queryKey, exact: true })
  })
}
```

   `staleTime: 30_000` matches `useIssueRecord`'s own `staleTime`. The prefetch is not chained on the mint (D-4). The recovery runs only after both have settled (D-4a).

## Critique response

### Shared-route fixture is invalid

Accepted. `sharedRouteCode` needs an 8-character code from its alphabet, so `#/shared/abc` returns `null`. Every test and criterion now uses `#/shared/bcdf-ghjk`, the value the existing test uses (`SharedConversationView.test.tsx`, line 297).

### Issue prefetch outruns authentication

Accepted. On a first visit with `#pair=` or `#overdeck_token=`, the early issue read can answer 401 before the session exists, and `useIssueRecord` does not retry. The draft now adds D-4a and FR-7:

- `startBootRequests` waits for both the prefetch and the session.
- When the session succeeded and the issue query is in `error`, it invalidates that query, so a mounted hook refetches.

WI-2 adds the test the critique asked for: a pending pairing exchange, a hook mounted while the exchange is pending, a 401 first read, and the title after the exchange resolves. An authenticated tab keeps the parallel fast path and makes one read, which a separate test checks.

### Delay monitor can miss the blocking span

Accepted. The `measured` helper in WI-4 now keeps the histogram on through one 20 ms timer turn after the reply (D-9c). A third test injects a 120 ms synchronous block and asserts that the harness reports `max >= 100`. The timer rule is amended: that single measurement turn is the only timer wait allowed.

### Warm fixture omits the first production connect

Accepted, by splitting the requirement. NFR-1 now covers warm connects (under 100 ms, 1,500 issues, 100 agents). NFR-1b covers the first connect in a fresh process at production volume (1,500 issues, 1,700 agents), with an explicit 300 ms limit. WI-4's first test measures that cold connect. The 300 ms figure accepts a one-time JIT warm-up per server process: locally the cold encode plus stringify of the full production payload is 91 to 96 ms. The limit still guards against the 1 s class of stall. D-9a states both limits.
