## Glossary

- **PWA (progressive web app):** a web page the phone installs to its home screen. It needs a web app manifest, a service worker and an HTTPS origin. It then opens full screen, with its own icon.
- **Web app manifest:** `FE/public/manifest.webmanifest`, a JSON file that names the app, its icons, its start URL and its display mode. The static server already serves `.webmanifest` as `application/manifest+json` (mime 4.1.0, used by `NodeHttpPlatform`).
- **Service worker (SW):** `FE/public/sw.js`, a script the browser runs in the background for the origin. In this plan it handles only push notifications and notification taps. It never intercepts network requests.
- **Tailscale Serve:** a Tailscale feature that publishes a local port as `https://<machine>.<tailnet>.ts.net`. It ends TLS and proxies to `http://127.0.0.1:<dashboard port>`. Because the proxy connects from `127.0.0.1`, the dashboard sees every visitor as a loopback peer (`isLoopbackPeer`, `src/dashboard/server/routes/dashboard-auth.ts:335-348`).
- **`require_token_mint`:** the `dashboard.require_token_mint` key in `~/.overdeck/config.yaml` (read by `src/lib/remote-access/config.ts:156-170`, default `false`). When it is `false`, a loopback peer with no credential gets the **root** session cookie from `POST /api/dashboard/session` (`dashboard-session.ts:76-129`, `dashboard-auth.ts:368`). When it is `true`, a request that carries `X-Forwarded-For`, `X-Forwarded-Host` or `Forwarded` counts as remote and needs a credential (`remote-request-gate.ts:70-73`).
- **Pairing credential:** a one-time `odp_` + 64 hex characters code (10-minute life, in memory only, `pairing-credentials.ts:15-16`). The browser consumes it from a `#pair=<credential>` URL fragment (`FE/src/lib/wsTransport.ts:83-123`) and exchanges it at `POST /api/pairing/exchange` for a device session.
- **Device session:** an `odk_` device token held in the HttpOnly `overdeck_device` cookie (`dashboard-auth.ts:15-18`, `Max-Age=2592000`, 30 days). Paired devices get `scopes: ['admin']` (`src/dashboard/server/routes/pairing.ts:123`), so every route-scope check passes for them. They still cannot create pairing credentials, add trusted origins or revoke devices.
- **Trusted origin:** an origin listed in `~/.overdeck/trusted-origins.json` or `OVERDECK_TRUSTED_ORIGINS` (`origin-validation.ts:49-97`). The pairing exchange, every WebSocket upgrade and every mutation check `Origin` against it.
- **Phone shell:** the new full-screen React surface at the path `/m`, rendered by `FE/src/components/mobile/MobileApp.tsx` without the desktop chrome (no Sidebar, Stage, terminals or dialog host).
- **Needs-you subject:** one item blocked on the operator. Agents come from the Zustand store (`selectPendingInputSubjects`, `FE/src/lib/store.ts:556`). Conversations come from `GET /api/conversations/pending-input`. `useDecisions()` (`FE/src/lib/useDecisions.ts:200`) joins both into sorted `Decision` rows whose `id` is an agent id or a conversation name.
- **AUQ (AskUserQuestion):** a question an agent asks with options. Payload: `pendingAskUserQuestion: { toolUseId, askedAt, questions: [{ question, header?, multiSelect?, options: [{ label, description? }] }] }` (`packages/contracts/src/types.ts:366-378`).
- **Answer transports:** the four ways the desktop delivers an AUQ answer, all in `FE/src/App/hooks/usePendingInputDialogs.ts`:
  1. agent → `POST /api/agents/:id/answer-question` with `{ answers, toolUseId }` (lines 371-386);
  2. pi or ohmypi conversation → `POST /api/conversations/:id/pi-ask-answer` with `{ toolUseId, answers }` (lines 389-401);
  3. any other conversation → `POST /api/conversations/:id/message` with `{ message }`, where `message` is the "Operator answered the pending question…" text (lines 402-420);
  4. Codex approval (a `toolUseId` starting with `codex-approval:`) → `POST /api/conversations/:id/codex-approval` with `{ optionNumber, toolUseId }`, where `optionNumber` is parsed from the chosen label with `/^\s*(\d+)/` (lines 438-470 and 476-489).
- **Tap count:** taps the operator makes, counting the tap that opens the app or the notification. "Three taps or fewer" means: open (1), choose an option (2), Send (3).

## Problem

The epic's FR-16 says the phone installs one machine's dashboard as a PWA over Tailscale Serve HTTPS, sees the fleet through that machine's links, and never holds machine keys. Its done check for W-PHONE2 is: "The installed PWA answers an AskUserQuestion in three taps or fewer."

None of that exists today (verified):

- `FE/index.html` has only a charset, a viewport and the favicon. There is no manifest, no `theme-color`, no `apple-touch-icon`, no service worker and no PWA library in any `package.json`.
- The desktop layout is the only layout. Its one phone affordance is the Sidebar hamburger (`FE/src/components/Sidebar.tsx:513-537`). Answering an AUQ needs the desktop modal `AskUserQuestionDialog`, which only `AppLiveStoreHost` mounts.
- No URL opens a specific question. `requestReopen` (`FE/src/lib/askUserQuestionUiStore.ts:91-94`) lives in memory only.
- An iPhone home-screen app has its own storage, separate from Safari. A device cookie set while pairing in Safari does not reach the installed app, and the 64-character pairing code cannot be typed. Today the installed app would stop at "Dashboard session could not be established" (`FE/src/App/BackendConnectionBoundary.tsx`).
- With `require_token_mint` off, any phone that opens the Tailscale Serve address without a device cookie gets the root session. Because `resolveDashboardCredential` checks the root cookie before the device cookie (`dashboard-auth.ts:162-178`), that phone stays root.

## Decisions

- **D-1 Ownership boundary with PAN-2354 (Web Push).** This issue owns the manifest, the icons, `FE/public/sw.js` **including its `push` and `notificationclick` handlers**, the service-worker registration and the phone shell. PAN-2354 owns the VAPID keys, the subscription store and routes, the sending path and the "Turn on notifications" control, which it adds to the header of `MobileApp.tsx`. The PAN-2354 planner was told this on 2026-11-01 through `pan tell planning-pan-2354`. **Rule for both issues:** whichever lands second extends the existing `sw.js` and never registers a second worker. The PAN-2354 planner adopted this split, the D-2 payload and the D-3 deep link, and added three more second-lander rules, which this plan mirrors (their PRD `workspaces/feature-pan-2354/.pan/drafts/pan-2354.md`, D-7 and D-17):
  1. **Manifest:** if PAN-2354 lands first, it creates a minimal `manifest.webmanifest` (`start_url` `/m`, `display` `standalone`, the `favicon.svg` icon) plus the `index.html` manifest link. W-2 then extends that manifest to the D-7 values and never adds a second link.
  2. **Notifications control:** `FE/src/components/push/TurnOnNotificationsButton.tsx`, export `TurnOnNotificationsButton` with a `compact` prop. If it exists on main when W-4 lands, `MobileApp.tsx` mounts `<TurnOnNotificationsButton compact />` at the end of its header. Otherwise PAN-2354 mounts it when it lands.
  3. **Registration:** the control also calls `navigator.serviceWorker.register('/sw.js', { scope: '/' })`. That is the same script and scope as D-6, so the two registrations are idempotent and must never diverge.
- **D-2 Push payload contract.** `sw.js` reads each push message as JSON `{ title: string, body: string, url: string, tag?: string }`. `url` is a same-origin path: `/m?subject=<encodeURIComponent(subjectId)>` opens that question, and `/m` opens the Needs-you list. A missing or cross-origin `url` falls back to `/m`. A payload that is not valid JSON shows the title "Overdeck" with the body "Something needs you" and opens `/m`.
- **D-3 Deep links are query parameters on `/m`, never path segments.** The static server returns 404 for a missing path that has a file extension (`src/dashboard/server/server.ts:239-241`), so an id with a dot in a path segment would break. The shell reads:
  - `/m` → Needs-you list;
  - `/m?subject=<id>` → the Needs-you list with that subject's card open and scrolled into view;
  - `/m?tab=conversations` → the conversation list;
  - `/m?conversation=<numeric id>` → that conversation, full screen.
- **D-4 The phone shell is a standalone branch, lazy-loaded.** `FE/src/App.tsx` matches `pathname === '/m' || pathname === '/m/'` next to the existing popout branches (lines 121-133) and renders `<MobileApp />` through `React.lazy`, inside `<Suspense>`. The desktop bundle gains only the lazy import. No automatic redirect from `/` to `/m` and no "switch to mobile" banner.
- **D-5 A hand-written service worker with no fetch handler.** `index.html` is served `no-cache, no-store` on purpose (`server.ts:255`, `:271-272`), and its boot watchdog polls `fetch('/', { cache: 'no-store' })` (`FE/index.html:70-164`). A caching worker would break both and could show stale dashboard state. So `sw.js` is a plain file in `FE/public/` (Vite copies `public/` to `dist/dashboard/public/` unchanged), with `install` (`skipWaiting`), `activate` (`clients.claim`), `push` and `notificationclick` listeners only. No `vite-plugin-pwa`, no Workbox, no precache, no offline page. **Implementation checkpoint:** if Chrome's installability check refuses the app without a fetch handler, add `self.addEventListener('fetch', () => {})` (a listener that never calls `respondWith`, so every request still goes to the network) and record it in the commit message.
- **D-6 The worker is registered only from the phone shell.** `MobileApp.tsx` calls `navigator.serviceWorker.register('/sw.js', { scope: '/' })` once on mount when `window.isSecureContext && 'serviceWorker' in navigator && !import.meta.env.DEV`. Registration failure logs one `console.warn` and never blocks the shell. The desktop pages never register it.
- **D-7 Manifest values.** `id: "/m"`, `name: "Overdeck"`, `short_name: "Overdeck"`, `start_url: "/m"`, `scope: "/"` (so `/conv/…` links stay inside the app), `display: "standalone"`, `background_color` and `theme_color` `"#202020"` (the default Broadsheet dark background, `hsl(0 0% 12.5%)`, `FE/src/index.css:481-483`). Icons: `/icons/icon-192.png` (192×192), `/icons/icon-512.png` (512×512), `/icons/icon-maskable-512.png` (512×512, `"purpose": "maskable"`, mark inside the central 80%), and `/icons/apple-touch-icon.png` (180×180, no transparency). One manifest serves every machine; per-machine app names are out of scope.
- **D-8 Pairing inside the installed app.** When the session mint fails (`useConnectionState().sessionAuthFailed === true`, `FE/src/lib/connectionState.ts:27`), the shell renders `MobilePairScreen` instead of the "session could not be established" screen. It offers **Scan pairing code** (camera plus the `jsqr` decoder, loaded with a dynamic `import()` only on this screen) and a paste field. A valid code is handed to the existing bootstrap: `history.replaceState(null, '', '/m#pair=' + credential)` then `window.location.reload()`. `ensureDashboardSession` then consumes and exchanges it exactly as it does today. No change to `wsTransport.ts`.
  - **Dependency:** `jsqr@1.4.0` in `FE/package.json` `dependencies`. iOS Safari has no `BarcodeDetector`, so a JavaScript decoder is required.
  - **Implementation checkpoint:** `getUserMedia({ video: { facingMode: 'environment' } })` inside an installed iOS app. *Fallback:* if the camera is unavailable or denied, the screen says "Camera is not available. Paste the pairing link instead." and the paste field still works.
- **D-9 Phone setup is a new dialog in Settings → Anywhere, reusing pairing.** A **Set up a phone** button opens `SetUpPhoneDialog`. It has four steps:
  1. install Tailscale on the phone;
  2. choose this machine's HTTPS address;
  3. confirm `require_token_mint` is on;
  4. scan the pairing code.

  It calls the existing `fetchAnywhereStatus`, `addTrustedAddress` and `issuePairingLink` (`FE/src/components/Settings/anywhere/anywhereApi.ts:84-103`). The phone link is `${origin}/m#pair=${credential}`. It is **not** `pairingPath`, which is `/#pair=…`.
- **D-10 The `require_token_mint` gate.** [PAN-4645](https://github.com/eltmon/overdeck/issues/4645) W-SEC4 turns the key on automatically; this issue does not duplicate that. The dialog reads `dashboard.require_token_mint` from `GET /api/settings`. While it is `false`, step 4 stays hidden and the dialog shows the warning and an **Open the setting** button that calls `requestSettingsSection('access-tokens')` (the section id rendered by `AccessTokensSection.tsx:83`), plus **Check again**. The dialog never writes settings itself.
- **D-11 The Tailscale app step reuses PAN-1254 when it exists.** **Implementation checkpoint:** run `git grep -n -i "tailscale" -- src/dashboard/frontend/src`. If [PAN-1254](https://github.com/eltmon/overdeck/issues/1254) has landed a phone-app QR component, import and render it in step 1. Otherwise render a QR code of `https://tailscale.com/download` with `qrcode-generator` (already a dependency, used the same way in `PairDeviceDialog.tsx:10`) and the text "Install Tailscale on your phone and sign in with the same account as this machine."
- **D-12 One answer module shared by desktop and phone.** The transport choice in `usePendingInputDialogs.ts:359-470` moves into a new pure module, `FE/src/lib/pendingInputAnswer.ts`. Both the desktop hook and the phone card call it. Behavior, endpoints, bodies and headers stay byte-identical, including the plain `{ 'Content-Type': 'application/json' }` headers. CSRF unification for these routes stays out of scope, as in revision 1's D-3. `Decision` and `ConversationPendingInputRow` gain `harness?: string | null`, copied from the REST row, so the phone can route pi conversations.
- **D-13 What the phone can answer.** It answers single-question and multi-question AUQs through all four transports, one label per question, which is the same as the desktop dialog. Every other subject kind is a read-only row:
  - a conversation subject has an **Open** button that goes to `/m?conversation=<id>`;
  - an agent subject shows "Answer on the desktop".

  The kinds covered by this are permission prompts, plan approvals, pane choices, rate limits, session resume, held kickoffs and turn-ended.
- **D-14 Conversations reuse `ConversationPanel` unchanged.** The conversation view mounts `ConversationPanel` exactly as `StandaloneConversationPopoutRoute` does (`FE/src/App/StandaloneRoutes.tsx:38-80`): fetch `/api/conversations/<numericId>` with a 5 s `refetchInterval`, and render inside a full-height wrapper with a back header. `ConversationPanel.tsx` is **never edited**: it has 11 lines of headroom under its file-size cap (1520 lines today, cap 1531 in `scripts/file-size-allowlist.txt`). Phone layout fixes go in the wrapper's classes only.
- **D-15 The fleet comes through the same APIs.** The phone reads `GET /api/conversations` and `GET /api/conversations/pending-input`. [PAN-4650](https://github.com/eltmon/overdeck/issues/4650) and [PAN-4651](https://github.com/eltmon/overdeck/issues/4651) merge linked machines' rows into those same responses at read time (epic D-5). So the phone sees the fleet when they land, with no aggregation code here.
- **D-16 No mockup gate.** The operator's mockup rule covers redesigns of established surfaces. `/m` is a new surface built from existing components, and the epic assigned an interactive mockup issue ([PAN-4646](https://github.com/eltmon/overdeck/issues/4646)) only to W-CONV5. Instead, the PR carries Playwright screenshots of every phone screen at 390×844 (the self-verify rule).
- **D-17 Styling.** Tailwind utility classes, with no new CSS module. Follow `/pan-style-guide` (`design/style-guide/STYLE-GUIDE.md`): `font-medium` at most, `rounded-sm` badges and no pills, one signal color per row, and a running state is never green. Every tappable control is at least 44×44 CSS px (`min-h-11 min-w-11`). The bottom tab bar pads by `env(safe-area-inset-bottom)`. `index.html` adds `viewport-fit=cover`.

## Requirements

### Functional

- **FR-1** `GET /manifest.webmanifest` returns the D-7 manifest with `content-type: application/manifest+json`. `index.html` links it and adds `theme-color`, `apple-touch-icon`, `apple-mobile-web-app-capable`, `mobile-web-app-capable` and `apple-mobile-web-app-title` tags.
- **FR-2** `GET /sw.js` returns a JavaScript file with `push` and `notificationclick` listeners that follow D-2, and no caching. `notificationclick` closes the notification, focuses an open same-origin window and navigates it to the URL, or opens a new window at the URL.
- **FR-3** `/m` renders the phone shell with no desktop chrome. It has a bottom tab bar with **Needs you** (default) and **Conversations**, honors the D-3 query parameters, mounts `EventRouter`, registers the worker (D-6), and offers installation:
  - an **Install app** button when `beforeinstallprompt` fires;
  - on iOS Safari, when not installed, the hint "To install, tap Share, then Add to Home Screen";
  - nothing when `matchMedia('(display-mode: standalone)').matches`.
- **FR-4** The Needs-you tab lists `useDecisions()` rows, blocking rows first. The first AUQ row, or the `?subject=` row, is expanded with its options as full-width buttons. Choosing an option and tapping **Send** delivers the answer through `pendingInputAnswer.ts`. It marks the `toolUseId` answered (`useAskUserQuestionUiStore.markAnswered`) and removes the card. On failure it un-marks and shows the error under the card.
- **FR-5** The Conversations tab lists `GET /api/conversations` (title, issue id, time since last activity), newest first. Tapping a row opens `/m?conversation=<id>`, which renders `ConversationPanel` per D-14 with a **Back** control.
- **FR-6** Without a session (D-8), the shell shows **Pair this phone**: **Scan pairing code**, a paste field and **Pair**. `parsePairingInput(input, origin)` accepts a full pairing link or a bare `odp_` + 64 hex code. It rejects anything else with "That is not an Overdeck pairing code." It rejects a link for another origin with "This code is for <origin>. Open Overdeck at that address instead."
- **FR-7** Settings → Anywhere shows **Set up a phone** next to **Pair a device**. The dialog implements D-9 to D-11. Its address list offers only trusted, non-loopback `https://` origins, plus an input that adds an `https://` origin through `addTrustedAddress`; an `http://` entry is refused with "A phone app needs an https:// address." Step 4 has an **Android / iPhone** switch:
  - **Android:** one QR code of `${origin}/m#pair=${credential}`.
  - **iPhone:** two QR codes. "1. Open in Safari, then Share → Add to Home Screen" encodes `${origin}/m`. "2. In the installed app, tap Scan pairing code" encodes `${origin}/m#pair=${credential}`.

  Both show the expiry time and **Create another code**. A 403 from `issuePairingLink` shows "Pairing links can be created only from a browser on this machine."
- **FR-8** `pendingInputAnswer.ts` exports:
  - `parseCodexOptionNumber(label: string): number | null`;
  - `buildPendingAnswerRequest(target: PendingAnswerTarget): { url: string; body: Record<string, unknown> } | { error: string }`;
  - `postPendingAnswer(request: { url: string; body: Record<string, unknown> }, failureLabel: string): Promise<unknown>`, which uses `fetchWithTimeout`, the plain JSON header and the existing error-body parsing.

  `PendingAnswerTarget = { kind: 'agent' | 'conv'; id: string; answers: string[]; questions?: ReadonlyArray<{ question: string }>; harness?: string | null; toolUseId?: string }`. A `codex-approval:` `toolUseId` with no parsable number returns `{ error: 'Could not determine which option was selected' }`.

### Non-functional

- **NFR-1** The desktop bundle does not grow by the phone code. `MobileApp` and everything under `FE/src/components/mobile/` load only through `React.lazy`. `npm run build` emits a separate chunk for them.
- **NFR-2** The worker never caches and never intercepts requests: `sw.js` contains no `caches.` call and no `respondWith`.
- **NFR-3** The answer from a single-question, single-select AUQ takes at most three taps from the home-screen icon or from the notification. The Playwright spec proves the in-app part (two taps after `/m` loads).
- **NFR-4** Every tappable control in the phone shell measures at least 44×44 CSS px at a 390×844 viewport.
- **NFR-5** The phone never holds a machine key or the internal token. It holds only the device cookie from pairing.
- **NFR-6** Timers in new code (scan loop, install prompt) are tested with `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`, never real waits.
