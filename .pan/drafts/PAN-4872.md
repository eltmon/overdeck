# PAN-4872: New conversation on another machine shows this machine's working directory

**Issue:** [PAN-4872](https://github.com/eltmon/overdeck/issues/4872)
**Status:** planned (auto mode, 2026-11-03)
**Verified against:** `feature/pan-4872` at `725de1a3f3d`

## Summary

In the new-conversation dialog, choosing a linked machine (for example "laptop") in the
**Machine** field leaves the **Working directory** field showing this machine's project
path, such as `/home/me/Projects/overdeck`. The field is disabled, but it still displays a
path that does not exist on the chosen machine and is never sent.

The start itself is already correct. The dialog never sends a `cwd` to another machine, and
the other machine decides the directory from the project's git origin. So this is a display
bug in one React component. The fix replaces the stale path with a plain sentence that says
which machine sets the directory and what it will be.

## Glossary

- **This machine:** the machine whose dashboard the operator is using. In the Machine field
  it is the option with value `''`.
- **Linked machine:** another Overdeck machine joined through Overdeck Anywhere. In the
  Machine field its option value is the link's `environmentId` and its text is the link's
  `label`.
- **Auto:** the Machine option `'auto'`. The server picks a machine by load and capability
  tags at create time, so the dialog does not know the machine in advance.
- **Fly (new VM):** the Machine option `'fly'`. The server starts a new Fly machine, clones
  the project there and runs the conversation on it. The option is enabled only with a
  project.
- **Fleet route:** `POST /api/fleet/conversations` in
  `src/dashboard/server/routes/fleet-work.ts`. The dialog uses it for every Machine choice
  except this machine.
- **Work door:** `POST /api/machines/work/conversations` in
  `src/dashboard/server/routes/machines-work.ts`. The fleet route calls it on the linked
  machine. It takes a `gitOrigin` slug, never a path.
- **gitOrigin:** a repository slug such as `github.com/eltmon/overdeck`, from the project's
  `github_repo` or `gitlab_repo`.
- **Default working directory:** `getDefaultCwd()` in `src/lib/default-cwd.ts`:
  `~/Projects` when it exists, else the home directory, evaluated on the machine that runs
  the conversation.
- **cwd hint:** the new sentence the Working directory field shows (as its placeholder)
  when the Machine field is not this machine.

## Current behavior (verified)

### The dialog shows the local path for every machine

`src/dashboard/frontend/src/components/newConversation/NewConversationDialog.tsx`, lines
221-233 (search for `htmlFor={cwdId}`):

```tsx
<label htmlFor={cwdId} className={styles.label}>Working directory</label>
<div className={styles.field}>
  <span className={styles.lead} aria-hidden="true"><Folder size={14} /></span>
  <input
    id={cwdId}
    className={cn(styles.input, styles.mono)}
    spellCheck={false}
    value={cwd}
    disabled={!projectKey || machine.machine !== ''}
    placeholder={projectKey ? '' : 'Default working directory'}
    onChange={(e) => setCwd(e.target.value)}
  />
</div>
```

`cwd` is set to the project's local path by the preset effect (line 101, `setCwd(preset.path)`)
and by `chooseProject` (line 132, `setCwd(next?.path ?? '')`). Changing the Machine field
(`setMachine`, line 219) never touches it. So with a linked machine chosen, the disabled
input still renders this machine's path.

### The remote start sends no cwd

`src/dashboard/frontend/src/components/newConversation/newConversationApi.ts`, line 77
(search for `const FLEET_FIELDS`):

```ts
const FLEET_FIELDS = ['projectKey', 'model', 'harness', 'effort', 'issueId'] as const;
```

`createFleetConversation` copies only these keys from the dialog payload, so `cwd` never
reaches `/api/fleet/conversations`. The fleet route also reads only
`['machine', 'projectKey', 'model', 'harness', 'effort', 'issueId']` (`fleet-work.ts`
line 202, search for `optionalStrings(body, ['machine'`). For a linked machine it posts
`{ ...options, message, gitOrigin }` to the work door (line 224). For Auto or Fly it does
the same once a target is chosen; when Auto picks this machine, it calls
`createLocal({ ...options, message, projectKey })` (line 216), again without `cwd`.

### The other machine decides the directory

`src/dashboard/server/routes/machines-work.ts`, header lines 10-12:

> A caller never chooses a path on this machine: it names a repository, and this machine
> decides where that repository lives.

`handleWorkConversation` (line 137) matches `gitOrigin` to a local project and calls
`handleConversationCreate` with that `projectKey`, so the conversation starts in that
machine's checkout. With `gitOrigin: null` it creates with no project, and
`handleConversationCreate` uses `getDefaultCwd()` (`src/lib/overdeck/conversation-runtime.ts`
line 1010). The header's phrase "the home directory when `gitOrigin` is null" is slightly
wrong: it is the default working directory (`~/Projects`, else home).

The contracts also forbid sharing paths across machines:
`packages/contracts/src/machines.ts`, `MachineProject` (search for
`as linked machines see it (never a path)`).

Server coverage already exists: `src/dashboard/server/__tests__/fleet-conversations.test.ts`
test `ac10: a remote target posts the work door with the slug…` asserts the work-door body
is `{ effort: 'high', message: 'hi', gitOrigin: 'github.com/eltmon/overdeck' }`, with no path.

**Conclusion:** the half of the issue's "Expected" that says "the conversation starts in a
directory that exists on that machine" is already true. Only the display is wrong. No
server change is needed.

## Decisions

- **D1 — Show a hint, not the other machine's paths.** The issue offers two readings:
  offer the chosen machine's paths, or clear the field and explain. The first is ruled out
  by design: the work door takes a repository, never a path, and `MachineProject` is
  documented "never a path". So the field clears and explains.
- **D2 — Keep the `cwd` state.** The fix is render-only. `cwd` is not cleared when a
  remote machine is chosen, so switching back to this machine restores the path, including
  a subdirectory the operator typed.
- **D3 — The hint is the input's placeholder.** The input stays in place (so the label still
  points at a control), stays disabled, renders `value=""`, and shows the hint as its
  `placeholder`. The same text goes in its `title` so a long project name is readable on
  hover. The existing `.input::placeholder` style
  (`NewConversationDialog.module.css` line 161) applies.
- **D4 — Label plumbing lives in `MachineField.tsx`.** `MachineField.tsx` exports a pure
  function `machineCwdHint` and a hook `useMachineCwdHint` that reads the same
  `useQuery({ queryKey: MACHINES_QUERY_KEY, queryFn: loadMachines, staleTime: 15_000 })`
  as `MachineField`. React Query dedupes the request, so no new fetch appears. The dialog
  calls only the hook.
- **D5 — The hint text, exactly.** `machineCwdHint(machine, label, projectName)`:

  | `machine` | Who (`<who>`) |
  | --- | --- |
  | `''` (this machine) | none: return `null` |
  | `'auto'` | `the machine Auto picks` |
  | `'fly'` | `the new Fly machine` |
  | a link id whose link is in the machines list | that link's `label` |
  | a link id not in the list (went offline or hidden between refetches) | `the chosen machine` |

  Where (`<where>`): `its copy of <projectName>` when a project is chosen, else
  `its default working directory`. `<projectName>` is the project's `name`, falling back to
  its `key`. Result: `Set by <who>: <where>`.

  Examples: `Set by desk: its copy of Overdeck`;
  `Set by the machine Auto picks: its default working directory`;
  `Set by the new Fly machine: its copy of Overdeck`.
- **D6 — The label lookup uses every link, not only online ones.** `useMachineCwdHint`
  finds the link by `environmentId` in `data.links` without the online/hidden filter, so a
  link that drops offline after being chosen still shows its label. Only an id missing from
  the list falls back to `the chosen machine`.
- **D7 — Scope is the dialog.** The CLI (`--machine`) and the MCP `start_conversation` tool
  take no cwd, so they have no equivalent bug.

## Requirements

- **FR-1:** With the Machine field set to anything but this machine, the Working directory
  field shows no path from this machine: its value is empty.
- **FR-2:** In that state the field shows the cwd hint from D5 as its placeholder and title.
- **FR-3:** Switching the Machine field back to this machine restores the previous `cwd`
  value, including an operator-edited subdirectory.
- **FR-4:** A conversation created for another machine sends no `cwd` key to
  `/api/fleet/conversations`, even when the operator edited the working directory first.
- **FR-5:** The linked-machines user doc and the Anywhere architecture doc state that the
  other machine sets the working directory and what the field shows.
- **NFR-1:** No new network request: the hook reuses `MACHINES_QUERY_KEY`.
- **NFR-2:** No server code changes. The only server file touched is a comment fix in
  `machines-work.ts`.

1. In `MachineField.tsx`, after `parseNeedsInput`, add:

   ```tsx
   /**
    * PAN-4872: what the Working directory field says when another machine runs the
    * conversation. That machine picks the directory from the project's repository
    * (the work door never takes a path), so this machine's path is never shown.
    * Null for this machine.
    */
   export function machineCwdHint(machine: string, label: string | null, projectName: string | null): string | null {
     if (machine === '') return null;
     const who = machine === 'auto' ? 'the machine Auto picks' : machine === 'fly' ? 'the new Fly machine' : (label ?? 'the chosen machine');
     return `Set by ${who}: ${projectName ? `its copy of ${projectName}` : 'its default working directory'}`;
   }

   /** `machineCwdHint` with the chosen link's label from the shared machines query. */
   export function useMachineCwdHint(choice: MachineChoice, projectName: string | null): string | null {
     const { data } = useQuery({ queryKey: MACHINES_QUERY_KEY, queryFn: loadMachines, staleTime: 15_000 });
     const label = (data?.links ?? []).find((link) => link.environmentId === choice.machine)?.label ?? null;
     return machineCwdHint(choice.machine, label, projectName);
   }
   ```

## Non-goals

- Listing, browsing or validating directories on another machine. The work door never takes
  a path, and the contracts never expose one.
- Sending a subdirectory (relative path inside the project) to another machine.
- Warning in the dialog when the chosen machine lacks the project. The server already
  answers 404 `project-missing` with the `pan machines add-project` command.
- Any change to the fleet route, the work door, the CLI `--machine` flags, or the MCP
  `start_conversation` tool.
