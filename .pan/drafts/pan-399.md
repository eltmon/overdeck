# PAN-399 — Release specialist: coordinated post-merge rollout and release safety

> **Source of truth for implementation.** This PRD carries the chosen approach,
> exact file paths, and decisions so a work agent can execute without re-deriving
> context. The vBRIEF (`.pan/spec.vbrief.json`) lowers this into beads.

## Glossary

- **Merge set / change-set manifest** — the `MergeSet` object built by PAN-632,
  defined in `src/lib/merge-set.ts` and persisted in the `merge_sets` /
  `merge_set_repos` SQLite tables. It records, per issue, every repo/component
  that landed, its `mergeOrder`, whether it is `required`, and reaches
  `status: 'merged'` when the coordinated merge completes. **This is PAN-399's
  input.**
- **Release set** — PAN-399's own per-issue, per-component rollout state,
  mirroring the merge-set pattern. New: `ReleaseSet` /
  `ReleaseComponentState` (`src/lib/release-set.ts`) + `release_sets` /
  `release_set_components` tables.
- **Release specialist** — the post-merge flow that consumes the merge set,
  resolves the ordered component release plan, drives/awaits rollout, verifies
  health, and halts/rolls back on failure. Not an agent — a deterministic
  server-side step inside `postMergeLifecycle`.
- **Component** — a named deployable unit in a project's `release:` config
  (e.g. `api`, `frontend`, `docs`). Distinct from a repo.
- **Trigger mode** — per-component `trigger: auto | manual | skip`:
  - `auto` — an external CI/CD (Vercel, K8s) deploys automatically; the
    specialist *waits for and verifies* it (polls `health_url`), it does NOT
    itself invoke the deploy.
  - `manual` — the specialist does not deploy; it records the component as
    awaiting a human deploy and does not block the rest as failed.
  - `skip` — excluded from the release plan entirely.
- **releaseStatus** — new issue-level pipeline status:
  `pending → releasing → passed | failed | partial | rolled_back | skipped`.
- **postMergeLifecycle** — `src/lib/cloister/merge-agent.ts:319`, the existing
  non-destructive post-merge handoff that sets `mergeStatus:'merged'` and
  transitions the issue to `verifying_on_main`. The release step hooks in here.

## Problem

A cross-repo / multi-service change can merge cleanly and still leave production
unusable if components roll out in the wrong order, or a later deploy fails
after an earlier one succeeded. PAN-632 owns coordinated *merge*; nothing today
owns coordinated *release*. There is no `releaseStatus`, no `release:` config,
and no rollout ordering / health / rollback machinery.

## Proposal

Add a deterministic **release specialist** that runs inside `postMergeLifecycle`
after the issue reaches `verifying_on_main`:

1. Read the merged `MergeSet` (`getMergeSetSync(issueId)`).
2. Load the project's `release:` config from `projects.yaml`.
3. Resolve an ordered component plan (topological sort on `depends_on`,
   excluding `trigger:skip`; cycle ⇒ fail).
4. For each component in order: honor trigger mode; for `auto`, poll `health_url`
   until healthy or timeout; run `version_check` then `smoke_test`; on failure,
   halt remaining components and run `rollback` if configured.
5. Persist per-component state to the release set; set issue `releaseStatus`.
6. Projects with no `release:` config are skipped cleanly (no releaseStatus set
   beyond `skipped`; nothing fails).

State is written only through the existing write door (`setReviewStatusSync`)
and the release-set DB module (mirroring merge-set), preserving the
single-source-of-truth tenet.

## Requirements

### Functional

- **FR-1** Parse a `release:` section per project in `projects.yaml` into a typed
  `ReleaseConfig` (`components: Record<string, ReleaseComponentConfig>`).
- **FR-2** Consume the merged `MergeSet` for the issue as the release trigger
  input.
- **FR-3** Resolve an ordered release plan by topological sort over
  `depends_on`, excluding `trigger:skip`; a dependency cycle fails resolution
  with a clear error.
- **FR-4** For `trigger:auto` components, poll `health_url` until healthy or a
  bounded timeout; run `version_check` and `smoke_test` when configured.
- **FR-5** On any component stage failure, halt all remaining components in the
  plan (stop-on-failure).
- **FR-6** Run the `rollback` hook where configured on failure; set the
  component `rolled_back`; where no rollback is configured, mark the release
  `partial`/`failed` (never pretend success).
- **FR-7** Expose issue-level `releaseStatus`
  (`pending|releasing|passed|failed|partial|rolled_back|skipped`) and
  component-level state on the dashboard.
- **FR-8** Trigger the release specialist from `postMergeLifecycle` after
  `verifying_on_main`.
- **FR-9** Projects without a `release:` section are skipped cleanly.
- **FR-10** Provide a `pan rollout status <id>` / `pan rollout retry <id>` CLI
  to inspect and re-run a release (named `rollout` to avoid colliding with the
  existing npm-publish verb `pan release`).

### Non-functional

- **NFR-1** All shell execution (health/version/smoke/rollback) uses async
  `exec`/`spawn` with timeouts — never `execSync` (server-reachable; PAN-70).
- **NFR-2** Any test exercising poll/backoff/timeout uses `vi.useFakeTimers()` +
  `advanceTimersByTimeAsync` — never real waits.
- **NFR-3** New CLI verb ⇒ matching `skills/pan-rollout/SKILL.md` in the same
  commit (skills↔CLI lockstep, `scripts/lint-skills.sh`).
- **NFR-4** Status writes go only through `setReviewStatusSync`; release-set
  reads/writes go only through the release-set DB module (single source of
  truth).

## Key decisions (auto-mode — see autoDecisions in vBRIEF)

- **D1 — `auto` = wait-and-verify, not deploy.** For MVP the specialist does not
  itself shell out to `kubectl`/`vercel` to deploy `auto` components. It waits
  for the external auto-deploy and verifies via `health_url`/`version_check`/
  `smoke_test`. `provider` is informational metadata for future provider-plugin
  routing. Rationale: the issue lists Kubernetes/Vercel as `trigger: auto`
  (their CI already deploys); actively triggering deploys per provider is a
  larger, provider-specific effort out of scope for the first cut.
- **D2 — Release set mirrors merge set.** Reuse the established per-issue /
  per-component table + model shape (`merge_sets`→`release_sets`) rather than
  inventing a new persistence pattern. Convention-aligned, dashboard-ready.
- **D3 — CLI verb is `pan rollout`, not `pan release`.** `pan release` is the
  npm stable/canary publish flow (`src/cli/commands/release.ts`). Overloading it
  would be confusing and lint-fragile.
- **D4 — MYN AC verified by fixture + docs, not by editing live config.**
  `projects.yaml` is machine config at `~/.overdeck/` (outside the repo). AC2 is
  proven by a resolver test over a MYN-shaped fixture (`frontend depends_on
  api`, `docs: skip`) plus the documented example; the operator adds the block
  to their live config.
- **D5 — Close-out is not gated on releaseStatus (MVP).** Surfacing
  `partial`/`failed`/`rolled_back` is sufficient for this issue; auto-blocking
  `pan close` on release state is a follow-up (see NonGoals).

## Non-goals

- Actively invoking provider deploy commands for `auto` components (kubectl
  apply, vercel deploy) — MVP waits and verifies (D1).
- Filtering the release plan to only the *affected* components of the change-set
  (needs a repo→component mapping that does not exist yet); MVP releases the full
  ordered project component graph.
- Gating `pan close` / issue completion on `releaseStatus` (D5).
- Pre-merge review/test coordination, PR/MR creation, rebasing, conflict
  resolution — owned by PAN-632 and the merge pipeline.
- A generic provider-plugin abstraction; `provider` is informational for now.
