# PAN-5609 — Show active conversation-search indexing in the dashboard top bar

**Issue:** https://github.com/eltmon/overdeck/issues/5609
**Status:** planned (auto mode, 2026-11-23)

## Glossary

- **Conversation search** — the dashboard feature that embeds Claude Code JSONL transcripts into
  a vector index so the command palette (`Ctrl+K`) finds past conversations by content.
- **Indexing activity** — any of the four ways the dashboard writes to that index (see *kind*).
- **Kind** — which path is indexing:
  - `startup`: the watcher's full sweep when it starts (`runFullIndex('startup')`).
  - `catch-up`: the watcher's sweep after a watcher restart (`runFullIndex('catch-up')`).
  - `incremental`: the watcher's per-file queue (`drainQueue()`), fed by file events.
  - `full-reindex`: the Settings "Estimate & reindex" job (`POST /api/settings/conversation-search/reindex`).
- **Batch** — a sweep with a known file list: `startup`, `catch-up` or `full-reindex`. It reports
  progress through the indexer's `onProgress` callback.
- **Burst** — one stretch of incremental work: it starts whenever no batch runs, `queued + inFlight`
  is above 0 and no burst is active (including the moment a sweep ends with files queued), and ends
  when `queued + inFlight` returns to 0.
- **Activity tracker** — the new server module `src/dashboard/server/services/conversation-search-activity.ts`.
  It is the one source of indexing activity (FR-1).
- **Activity snapshot** — `ConversationSearchActivitySnapshot`, the complete activity state the
  tracker publishes (shape in WI-1).
- **`emitOnly`** — `EventStore.emitOnly()` (`src/dashboard/server/event-store.ts`, line 429): fans an
  event out to live `/ws/rpc` subscribers and the server read model with sequence `-1`; it is never
  persisted or replayed. `github_quota.changed` and `system.shutdown_changed` use it.
- **Read model** — `ReadModelState` in `packages/contracts/src/event-reducers.ts`. The server
  (`src/dashboard/server/read-model.ts`) and the frontend Zustand store
  (`src/dashboard/frontend/src/lib/store.ts`, `DashboardState extends ReadModelState`) run the same
  reducers.
- **Exception chips** — the top bar's `data-testid="topbar-exception-chips"` group in
  `src/dashboard/frontend/src/App/AppChrome.tsx` (line 213). Each chip renders only while its
  condition is true.
- **Indicator** — the new top-bar chip `ConversationSearchIndexingIndicator`.
- **Visible / linger** — the indicator is *visible* when its chip renders. *Linger* is the 2 s it
  stays visible after activity ends.

## Problem

The dashboard indexes transcripts in the background, but the top chrome says nothing about it.
The only top-of-page signal is `ConversationSearchBanner`
(`src/dashboard/frontend/src/components/ConversationSearchBanner.tsx`, line 34:
`if (status.available && !recentlyFailing && !watcherDown) return null;`), which appears only on
failure. The operator cannot tell when indexing runs, how far along it is, or why the machine is busy.

Operator request (2026-11-23): "when we are actively indexing we should show that on dashboard top,
and hovering or clicking it should even show details about its indexing".

## Requirements

- **FR-1** One server-side source of indexing activity covers all three paths. Its snapshot carries:
  kind (`startup`, `catch-up`, `incremental`, `full-reindex`), active flag, files scanned, files
  indexed, chunks indexed, current file, queue length and in-flight count for incremental work,
  started-at, ended-at, and the last error of the current run. The watcher sweep passes `onProgress`
  so it reports live counts. The manual reindex route writes to the same source instead of its
  private module variable. `GET /api/settings/conversation-search/reindex-progress` keeps working,
  with its old response shape, reading from the new source.
- **FR-2** The activity reaches the frontend through the existing `/ws/rpc` read-model event stream
  (snapshot field on connect, then `conversation_search.activity_changed` events). No new frontend
  polling loop.
- **FR-3** A compact indicator in the top bar's exception chips (not a full-width banner) is visible
  while indexing is active and hidden when idle. `startup` and `full-reindex` show at once.
  `incremental` and `catch-up` show only once the run has stayed active for 3 s. The indicator stays
  visible at least 2 s after work ends.
- **FR-4** Hovering (or keyboard-focusing) the indicator shows a tooltip: what kind of indexing runs,
  files done / total, chunks indexed, elapsed time.
- **FR-5** Clicking the indicator opens a popover with: kind, files done / total, chunks indexed,
  current file, queued and in-flight counts, started-at, elapsed, last error (when there is one), and
  an "Open conversation search settings" action that opens Settings scrolled to the Conversation
  Search card (`requestSettingsSection('conversation-search')` + `onOpenSettings()`, the pattern
  `ConversationSearchBanner` uses).
- **FR-6** Follow the `pan-style-guide` skill (Broadsheet default theme): no pill badges, no
  decorative color, a quiet activity glyph in `text-muted-foreground` rather than a green "running"
  signal.
- **NFR-1** The server emits at most one `conversation_search.activity_changed` event per 500 ms, and
  the final state of a run always arrives (leading emit plus a guaranteed trailing emit).
- **NFR-2** Tests for the throttle and the frontend show/hide timing use fake timers
  (`vi.useFakeTimers()` + `vi.advanceTimersByTime()`), never real delays.
- **NFR-3** No file-size ratchet growth: `src/dashboard/server/routes/settings.ts` is 1102 lines with
  a cap of 1104 (`scripts/file-size-allowlist.txt`, last row wins). WI-4 must leave it at 1104 lines
  or fewer.
- **NFR-4** The frontend indicator is a leaf: `AppChrome` calls no store selector (docs/DASHBOARD-ARCHITECTURE.md
  "Top bar (PAN-5292)" and "Render discipline (PAN-4560)").

## Decisions (made here; the work agent does not re-decide them)

- **D-1 Event shape.** New in-memory event `conversation_search.activity_changed` with payload
  `{ activity: ConversationSearchActivitySnapshot }` (complete snapshot, reducer is a plain replace),
  emitted only through `emitOnly`, like `system.shutdown_changed`. Snapshot field name in
  `DashboardSnapshot` and `ReadModelState`: `conversationSearchActivity`. `syncSnapshot` uses
  `snapshot.conversationSearchActivity ?? null` (never falls back to old state), so a server restart
  mid-index never leaves a stuck indicator.
- **D-2 One run at a time in the snapshot.** The tracker holds at most one batch. A batch hides
  incremental counts: while a batch is active the snapshot's kind and counts are the batch's;
  `queued` / `inFlight` always come from the watcher queue. A new `beginBatch` replaces any current
  batch. Every batch method goes through a handle; a handle that is no longer current is a no-op, so
  a late `end()` from an aborted sweep never clears the reindex that replaced it.
- **D-3 Idle snapshot keeps the last run.** When a run ends, the snapshot keeps `kind`, the counts,
  `startedAt`, sets `endedAt`, `active: false`, `currentFile: null`. Before any run, `kind` is `null`
  and counts are 0. The frontend renders the last-run values during linger.
- **D-4 Errors belong to the current run.** `lastError` / `lastErrorAt` reset when a batch or burst
  starts. The banner (`ConversationSearchBanner`) stays the persistent failure surface.
- **D-5 Throttle.** `NFR-1` via leading + trailing throttle in the tracker, 500 ms, timers
  `unref()`-ed. An emit whose snapshot equals the last emitted one (compare `JSON.stringify` of the
  snapshot) is skipped. `emitOnly` is wrapped in try/catch exactly as `github-quota.ts` line 39–46
  does ("Event store not ready yet").
- **D-6 Legacy reindex-progress route.** `GET /api/settings/conversation-search/reindex-progress`
  returns `toLegacyReindexProgress(tracker.getSnapshot())`: when `kind === 'full-reindex'`,
  `{ active, filesScanned, filesIndexed, chunksIndexed, currentFile?, startedAt? }` with `startedAt`
  as epoch milliseconds (`Date.parse`) and `currentFile` omitted when null; otherwise
  `{ active: false, filesScanned: 0, filesIndexed: 0, chunksIndexed: 0 }`. The mapper lives in the
  tracker module (NFR-3).
- **D-7 Visibility rules** (pure state machine, WI-6):

  | Latest snapshot | Indicator now | Result |
  | --- | --- | --- |
  | active, kind `startup` or `full-reindex` | any | visible now; cancel linger and pending show |
  | active, kind `incremental` or `catch-up` | visible | stays visible; cancel linger |
  | active, kind `incremental` or `catch-up` | hidden, no pending show | start a 3 s show timer |
  | active, kind `incremental` or `catch-up` | hidden, show timer pending | keep the timer |
  | null or not active | visible, no linger timer | start a 2 s linger timer; stay visible |
  | null or not active | hidden | cancel the show timer |
  | show timer fires | — | visible only if the latest snapshot is active |
  | linger timer fires | — | hidden only if the latest snapshot is not active |

  A kind change while visible never hides the indicator. The 3 s gate applies only hidden → visible.
- **D-8 No setState in effects.** The visibility state machine is a plain-TS external store
  subscribed to `useDashboardStore` outside React; the component reads it with
  `useSyncExternalStore`. This keeps the component clean for the React Compiler lint
  (`react-hooks/set-state-in-effect`) and puts all timers in testable plain code.
- **D-9 UI primitives.** No Radix popover exists and no app-level `TooltipProvider` is mounted, so the
  indicator uses plain React state: a hover/focus tooltip (`role="tooltip"`, `onMouseEnter` /
  `onMouseLeave` / `onFocus` / `onBlur`) and a click popover (`role="dialog"`) with the
  outside-mousedown and Escape close effect `NeedsYouIndicator.tsx` uses (lines 76–90). The tooltip
  is hidden while the popover is open. While the popover is open the indicator stays mounted even
  if the state machine says hidden.
- **D-10 Labels.**
  - Kind labels: `startup` → "Startup sweep", `catch-up` → "Catch-up after watcher restart",
    `incremental` → "New transcript changes", `full-reindex` → "Full reindex".
  - Chip text: `Indexing <filesIndexed>/<filesScanned>` with `toLocaleString()` numbers when
    `filesScanned > 0`, else `Indexing`.
  - Elapsed: `formatIndexingElapsed(ms)` → `"42s"` under 60 s, `"3m 05s"` under 60 min,
    `"1h 02m"` above. Elapsed = `(endedAt ?? now) - startedAt`.
  - Current file: the snapshot already holds a basename (`<session-uuid>.jsonl`); the popover renders
    it with `truncate` and the full value in `title`.
- **D-11 Settings anchor.** `ConversationSearchSection.tsx` gets `id="conversation-search"` and
  `scroll-mt-4` on its card div (the `div` with `px-4 py-3 rounded-lg bg-muted/15`, line 77). The
  link calls `requestSettingsSection('conversation-search')` then `onOpenSettings()`.
- **D-12 Docs scope.** `docs/EXTERNAL-EVENT-STREAM.md` is not changed: it lists only public-catalog
  events plus two in-memory examples, and the other in-memory events (`github_quota.changed`,
  `system.shutdown_changed`) are not listed there either.

```ts

import type { ConversationIndexProgress } from '../../../lib/conversation-search/indexer.js';
import { getEventStore } from '../event-store.js';

export const ACTIVITY_EMIT_THROTTLE_MS = 500;
export type ConversationSearchBatchKind = Exclude<ConversationSearchActivityKind, 'incremental'>;

export interface ConversationSearchBatchHandle {
  progress(progress: ConversationIndexProgress): void;
  recordError(reason: unknown): void;
  end(): void;
}

export interface ConversationSearchActivityTracker {
  beginBatch(kind: ConversationSearchBatchKind): ConversationSearchBatchHandle;
  /** The watcher queue changed. `startedFile` names a file that just went in flight. */
  setQueue(queued: number, inFlight: number, startedFile?: string): void;
  /** One incremental file finished. */
  recordIncrementalFile(chunksIndexed: number): void;
  recordIncrementalError(reason: unknown): void;
  /** Watcher stopped: queue counts go to 0 and any burst ends. Batches end through their handle. */
  resetQueue(): void;
  getSnapshot(): ConversationSearchActivitySnapshot;
}

export function createConversationSearchActivityTracker(deps?: {
  emit?: (snapshot: ConversationSearchActivitySnapshot) => void;
  now?: () => number;
  throttleMs?: number;
}): ConversationSearchActivityTracker;

/** The dashboard's tracker; emits `conversation_search.activity_changed` via emitOnly. */
export const conversationSearchActivity: ConversationSearchActivityTracker;

/** D-6 legacy shape for GET /api/settings/conversation-search/reindex-progress. */
export function toLegacyReindexProgress(snapshot: ConversationSearchActivitySnapshot): {
  active: boolean; filesScanned: number; filesIndexed: number; chunksIndexed: number;
  currentFile?: string; startedAt?: number;
};
```

Behavior:
- Internal state: `batch: { token, kind, filesScanned, filesIndexed, chunksIndexed, currentFile, startedAt, lastError, lastErrorAt } | null`,
  `burst: { filesIndexed, chunksIndexed, currentFile, startedAt, lastError, lastErrorAt, endedAt, active }`,
  `queued`, `inFlight`, and `last: ConversationSearchActivitySnapshot` (last finished run, for D-3).
- `beginBatch(kind)`: new token; batch starts with counts 0, `startedAt = iso(now())`, no error.
  Schedules an emit.
- `handle.progress(p)`: only when the handle's token is current. Copies `filesScanned`,
  `filesIndexed`, `chunksIndexed`, `currentFile ?? null`. Schedules an emit.
- `handle.recordError(reason)`: only when current. `lastError = reason instanceof Error ? reason.message : String(reason)`,
  `lastErrorAt = iso(now())`.
- `handle.end()`: only when current. Stores the batch as the last run (`active: false`,
  `endedAt = iso(now())`, `currentFile: null`), sets `batch = null`, then runs the burst-start rule
  below (files queued during a sweep start a burst the moment the sweep ends). Schedules an emit.
- **Burst-start rule** (evaluated in `setQueue` and in `handle.end()`): a burst starts whenever no
  batch is current, `queued + inFlight > 0`, and no burst is active. It starts with counts 0,
  `startedAt = iso(now())`, error cleared. `beginBatch` ends an active burst (it becomes the last
  run, as below) before the batch starts.
- `setQueue(queued, inFlight, startedFile?)`: stores counts, then runs the burst-start rule. A
  `startedFile` sets the burst's `currentFile` to its basename. When the total returns to 0 during a
  burst, the burst ends: it becomes the last run (`kind: 'incremental'`, `active: false`, `endedAt`,
  `currentFile: null`). Schedules an emit.
- `recordIncrementalFile(chunks)`: burst `filesIndexed += 1`, `chunksIndexed += chunks`.
- `getSnapshot()` derivation:
  - batch current → `{ active: true, kind: batch.kind, counts and currentFile from the batch, queued, inFlight, startedAt, endedAt: null, lastError... }`
  - else burst active → `{ active: true, kind: 'incremental', filesIndexed, chunksIndexed, filesScanned: filesIndexed + queued + inFlight, currentFile, queued, inFlight, startedAt, endedAt: null, ... }`
  - else the last run with current `queued` / `inFlight`, or the empty snapshot
    (`active: false, kind: null`, zeros, nulls) before any run.
- Throttle (D-5): `scheduleEmit()` emits at once when the last emit is `throttleMs` or more ago;
  otherwise it sets one trailing timer for the remainder, and the trailing timer emits the snapshot
  current at fire time. Skip an emit equal to the last one.
- Default `emit`: `getEventStore().emitOnly({ type: 'conversation_search.activity_changed', timestamp: new Date().toISOString(), payload: { activity } })`
  inside try/catch.

   resolve, and `recordIncrementalFile` receives each result's `chunksIndexed`.

6. A file event during the startup sweep (hold `indexAll` on a deferred promise) is queued; when
   `indexAll` resolves, the snapshot reports `active: true`, `kind: 'incremental'` until that file's
   index call resolves, then `active: false`.
