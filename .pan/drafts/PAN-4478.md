## Glossary

| Term | Meaning in this document |
| --- | --- |
| **Data owner** | The machine (and GitHub identity, `RoomSnapshot.dataOwner`) that owns the shared conversation. Its dashboard **server** runs the `ShareManager` and the `PeerHub`; its **browser** shows the share dialog. Fixed for the life of the share. |
| **Viewer** | An admitted participant. Its browser holds one `RTCPeerConnection` to the data owner's hub (slice 4). |
| **Controller** | The one participant whose share commands (admit, kick, revoke, un-revoke, contributor grants, handoff) and prompt sends the host accepts. Initially the data owner. |
| **Handoff** | The controller gives control to an admitted viewer, or a viewer-controller gives it back to the data owner. On the wire it is the existing host frame `set-controller { githubId }`. |
| **Reclaim** | The data owner takes control back unilaterally: `set-controller` with the data owner's own id. Always accepted, whoever is controller. |
| **Appointment** | The host's own record of the viewer it last made controller (`ControllerState.appointed`, new). `null` means the data owner. Only a `set-controller` that this host process sent changes it. |
| **Effective controller** | What the host enforces: the appointed viewer **if** the latest room snapshot's `controllerGithubId` equals that appointment, otherwise the data owner. See D-2. |
| **Share command** | `ShareCommand` in `packages/contracts/src/sharing.ts` line 99: the host frames the data owner's browser may request through `POST /api/shares/:code/commands`. This slice adds `set-controller`. |
| **Controller command** | `SharedControllerCommand` (new): a share command a viewer-controller sends over the `control` data channel. Every share command except `unrevoke`. |
| **Controller send** | A prompt that the controller puts in the share's `SubmitQueue` (slice 5). The data owner's comes through `POST /api/shares/:code/prompts`; a viewer-controller's comes through the new `control` payload `controller-send`. |
| **Ack** | The new host → viewer `control` payload `command-ack`, answering one `command` or `controller-send` by its `clientId`. |
| **Eligible viewer** | Slice-3 term (`peer-hub.ts` lines 305–311, `reconcile`): in the hub's host-admitted set **and** listed in the latest snapshot as `admitted` and `connected`. |
| **Negotiated peer** | A `PeerEntry` whose `helloState === 'negotiated'` (`peer-hub.ts` line 172). |
| **Host-admitted set** | `PeerHub.hostAdmitted` (`peer-hub.ts` line 187): ids this host process admitted itself. The NFR-4 content gate. |

## Problem

The share service already tracks a controller (slice 1): `RoomSnapshot.controllerGithubId`, the host frame `set-controller`, and the reducer rule that a kicked, revoked or departed controller hands control back to the data owner (`services/share/src/room-state.ts` lines 156–160 and 318–323). Nothing on the host or viewer uses it:

- `ShareCommand` (`packages/contracts/src/sharing.ts` line 99) does not include `set-controller`, so `parseShareCommand` (`src/dashboard/server/routes/shares.ts` lines 61–79, `COMMAND_TYPES` at line 29) refuses it and `frameOf` (`src/dashboard/server/services/share-host.ts` lines 132–147) cannot build it.
- `ShareManager.command` (`share-host.ts` lines 188–201) and `ShareManager.sendPrompt` (lines 204–215) accept every request from the data owner's browser, whoever the room says the controller is.
- `PeerHub.onControlMessage` (`src/dashboard/server/sharing/peer-hub.ts` lines 476–498) reads only `hello` and `submit`. A viewer cannot send any share command.
- `presenceOf` (`peer-hub.ts` lines 641–672) copies `snapshot.controllerGithubId` straight from the share service, so a buggy or compromised share service decides who the viewers see as controller.
- A viewer browser does not know its own GitHub id (`JoinView` carries `login` only, and presence has no "you" marker), so it cannot tell whether it is the controller.
- The user docs say so: `configuration/shared-sessions.mdx` lines 71–77, "Controller: … In this release this is always the host" and "Handing control to another person comes in a later release."

## Goal

The data owner clicks **Hand control** next to an admitted viewer in the share dialog. That viewer's page shows a **You have control** panel with the lobby (admit, admit as contributor, revoke, grant or remove contributor, kick, hand control on), a controller-mode suggestion list and a **Send prompt** button. Every command the viewer-controller sends reaches the share service through the data owner's server, which checks it first. While a viewer controls, the data owner's lobby actions are replaced by "@login has control" and **Reclaim control**, which always works. A command from anyone who is not the effective controller is rejected with `not_controller`.

## Requirements

Functional (this slice's own IDs; FR-10 of the parent PRD is the requirement they refine):

- **FR-1** `ShareCommand` includes `set-controller { githubId }`. `POST /api/shares/:code/commands` accepts it and the host relays it as the existing host frame.
- **FR-2** The host keeps its own appointment. The effective controller is the appointed viewer when the latest snapshot's `controllerGithubId` equals it, and the data owner otherwise. A snapshot that no longer lists the appointed viewer as `admitted` clears the appointment.
- **FR-3** The host accepts a share command or a controller send only from the effective controller. The single exception is reclaim: the data owner's `set-controller` with its own id is always accepted.
- **FR-4** A `set-controller` target must be the data owner, or a participant listed as `admitted` in the latest snapshot **and** in the host-admitted set. Anything else is refused `unknown_participant`. A viewer-controller naming itself is refused `invalid_target`.
- **FR-5** When the data owner is not the effective controller, `POST /api/shares/:code/commands` (except reclaim) and `POST /api/shares/:code/prompts` answer 409 `not_controller`. `DELETE /api/shares/:code` (End share) is never gated.
- **FR-6** A negotiated, eligible viewer that is the effective controller can send `control` `{ kind: 'command', clientId, command }` with one of `admit`, `kick`, `revoke`, `set-contributor`, `set-controller`. The host validates the target against the latest snapshot (FR-8), relays the frame through the host socket, updates its host-admitted set and appointment exactly as for the data owner's own commands, and answers `command-ack`.
- **FR-7** The same viewer can send `control` `{ kind: 'controller-send', clientId, text, draftGithubId? }`. The host queues it through the slice-5 `sendFromController` door, credited to the viewer-controller (or to the picked draft's author), and answers `command-ack accepted` with the 1-based queue position, or `rejected` with the queue's reason.
- **FR-8** Viewer command targets: `admit` needs a `lobby` participant; `kick` and `revoke` need any listed participant; `set-contributor` needs an `admitted` participant; `set-controller` follows FR-4. A target that fails is refused `unknown_participant`; the viewer's own id is refused `invalid_target`; a malformed command or `unrevoke` is refused `invalid_command`; a host socket that cannot send is refused `not_connected`.
- **FR-9** After a peer's hello negotiates, the host sends it `control` `{ kind: 'identity', githubId }` with that peer's own id, before any presence.
- **FR-10** Presence `controllerGithubId` is the host's effective controller, never the raw snapshot value. A reclaim (or a hand-back to the data owner) refreshes presence on every negotiated peer at once; a handoff to a viewer shows once the snapshot confirms it.
- **FR-11** `ShareView` carries `controllerGithubId` (the effective controller). The share dialog's lobby panel shows **Hand control** on each admitted participant while the data owner controls; while a viewer controls it shows "@login has control.", one **Reclaim control** button, no other lobby actions, and the suggestion list in read-only `view` mode.
- **FR-12** The viewer page shows the **You have control** panel only while presence `controllerGithubId` equals the viewer's identity id. The panel has **Hand control back to @owner**, the lobby roster with the controller actions of FR-8 (no Blocked section, no un-revoke), and errors from rejected acks. The composer shows **Send prompt** (controller send) and the suggestion list in `controller` mode (**Use**, edit, **Send**). Every viewer's header shows "@login has control" while a viewer controls.
- **FR-13** A viewer's command or controller send that gets no ack within 10 s (`COMMAND_ACK_TIMEOUT_MS`) fails with "The host did not answer." Pending commands fail with "Connection to the host was lost." when the peer is reset.

Non-functional:

- **NFR-1 (security, NFR-4 of the parent PRD)** A share service that reports a controller the host never appointed cannot give that participant any power. The host's appointment is the authority (D-R3-3: "the data owner is the control authority"); the room's `controllerGithubId` only confirms it.
- **NFR-2 (version skew)** Every new `control` payload is additive. An older viewer ignores `identity` and `command-ack` (its `onControl`, `webrtc-viewer.ts` lines 317–371, returns on unknown kinds) and never shows controller UI. An older host ignores `command` and `controller-send` (its `onControlMessage` returns), so the viewer's pending call times out under FR-13.
- **NFR-3** Inbound `command` and `controller-send` envelopes are read with the existing 64 Ki inbound reader (`entry.reader`, `peer-hub.ts` line 163). The host rebuilds a command from its known keys only, so no unlisted field reaches the share service.
- **NFR-4** No new HTTP route, so no `tests/unit/lib/overdeck/no-loss-matrix.ts` row. No change under `services/share/`.
- **NFR-5** `peer-hub.ts` (682 lines on `main`), `share-host.ts` (474) and `SharedConversationView.tsx` (312) stay under the 1,000-line ceiling of `scripts/lint-file-size.sh`.

## Decisions

- **D-1 — The data owner obeys the controller rule too.** Parent PRD *Host Role & Handoff*: the host "accepts control commands … only from the participant who currently holds the controller role" and "exactly one controller exists at any time". So while a viewer controls, the data owner's browser commands and prompt sends answer 409 `not_controller`. The data owner is never locked out, because reclaim is one click and always accepted, and **End share** is never gated. (Normal typing in the data owner's own conversation composer is not a share action and is untouched.)
- **D-2 — The host trusts only a controller it appointed (NFR-1).** Effective controller = `appointed` when `snapshot.controllerGithubId === appointed`, else the data owner. Consequences: a handoff takes effect when the next snapshot confirms it (milliseconds); a reclaim takes effect at once on the host, before the share service confirms it; a share service that names an unappointed controller only produces "the data owner controls". This mirrors slice 3's host-admitted set, which "a room snapshot can remove … but never add".
- **D-3 — The appointment lives in the hub.** `PeerHub` already owns the host-admitted set and presence, so it owns a `ControllerState`. `ShareManager` reads it through three new `HostHub` methods (`controllerGithubId`, `isHostAdmitted`, `appoint`). `PeerHubContext` does not change, so no other `PeerHub` constructor breaks.
- **D-4 — One gate function.** `controlRefusal` in the new pure module `src/dashboard/server/sharing/controller.ts` decides every command for both actors. `ShareManager.command` calls it with the owner actor; `PeerHub` calls it with the viewer actor.
- **D-5 — The data owner's path keeps slice-2 target semantics.** For the owner actor, only `set-controller` targets are checked on the host (FR-4); admit, kick, revoke, un-revoke and set-contributor still go to the share service, which answers `unknown_participant` into `lastError` as today. This keeps the slice-2 tests at `share-host.test.ts` line 261 (admit id 5 against an empty snapshot → 202) valid. A viewer-controller's commands arrive from a remote peer, so the host validates their targets itself and answers each with an ack.
- **D-6 — The viewer learns its own id from the host.** The host sends `control` `identity { githubId }` after the hello. This needs no viewer-server change (`JoinView` stays as it is, and `account.json`'s `githubId` may be `null`), and it is host-authoritative. Rejected alternative: add `githubId` to `JoinView` from `account.json` in `share-join.ts`.
- **D-7 — A viewer-controller cannot un-revoke or end the share.** Presence never carries the block list (slice 3 D-17/D-18, `peer-hub.ts` line 37), and widening it is out of scope. Un-revoke and End share stay with the data owner, who reclaims first. `readControllerCommand` therefore refuses `unrevoke`.
- **D-8 — A handoff target does not have to be connected.** The share service accepts any admitted participant (`room-state.ts` line 320) and viewer presence has no `connected` field, so the host requires `admitted` (snapshot) and host-admitted, nothing more.
- **D-9 — Presence refresh.** `appoint(id)` refreshes presence on every peer only when the new appointment is the data owner. A handoff to a viewer waits for the confirming snapshot, so presence goes straight from the old controller to the new one with no flash of the data owner in between. (Another presence trigger in that millisecond window, such as a queue status change, can still show the data owner briefly; that is accepted.)
- **D-10 — A disconnected controller keeps control.** The share service resets the controller only on kick, revoke or leave. The host does the same: an admitted but offline controller stays controller, and the data owner can reclaim.
- **D-11 — Controller sends are queue items.** A viewer-controller's prompt goes through `sendFromController` (`peer-hub.ts` lines 280–292) with the viewer's identity as author, so it joins the same FIFO queue with `source: 'controller'` and the viewers' timelines credit the right person. The ack is `accepted` once queued; no later `sent` ack (same as the data owner's controller sends).
- **D-12 — Refusal status codes on the host API.** Every gate refusal on `POST /api/shares/:code/commands` and `/prompts` is HTTP 409 with `{ error, message }`: `not_controller` ("Another participant has control. Reclaim control first."), `unknown_participant` ("That person is not in the room.").
- **D-13 — Ack timeout.** `COMMAND_ACK_TIMEOUT_MS = 10_000` in `useSharedJoin.ts`. Tests use fake timers.
- **D-14 — End-to-end proof uses three dashboards.** The handoff chain needs three identities: owner (id 1), alice (id 100, B) and bob (id 200, C).

## Host design

### Controller module (`src/dashboard/server/sharing/controller.ts`, new)

A pure module, no I/O, no timers. Header comment states D-2, D-4 and D-5.

```ts
import type { RoomSnapshot, ShareCommand, SharedCommandRefusal, SharedControllerCommand } from '@overdeck/contracts';

export type ControlActor = { readonly kind: 'owner' } | { readonly kind: 'viewer'; readonly githubId: number };
export type ControlRefusal = Extract<SharedCommandRefusal, 'not_controller' | 'unknown_participant' | 'invalid_target' | 'invalid_command'>;

/** The host's own appointment (D-2). `null` = the data owner. */
export class ControllerState {
  private appointed: number | null = null;

  /** The effective controller, or null before the first snapshot. */
  current(snapshot: RoomSnapshot | null): number | null {
    if (!snapshot) return null;
    const appointed = this.appointed;
    return appointed !== null && snapshot.controllerGithubId === appointed ? appointed : snapshot.dataOwner.githubId;
  }

  appoint(githubId: number, ownerGithubId: number): void {
    this.appointed = githubId === ownerGithubId ? null : githubId;
  }

  /** A viewer the snapshot no longer lists as admitted loses the appointment (FR-2). */
  onSnapshot(snapshot: RoomSnapshot): void {
    const appointed = this.appointed;
    if (appointed === null) return;
    if (!snapshot.participants.some((p) => p.githubId === appointed && p.state === 'admitted')) this.appointed = null;
  }
}

export function controlRefusal(input: {
  readonly snapshot: RoomSnapshot;
  readonly controllerGithubId: number;
  readonly actor: ControlActor;
  readonly command: ShareCommand;
  isHostAdmitted(githubId: number): boolean;
}): ControlRefusal | null;

/** A viewer's command rebuilt from its known keys, or null (FR-8, NFR-3). `unrevoke` is null (D-7). */
export function readControllerCommand(value: unknown): SharedControllerCommand | null;
```

`controlRefusal` rules, in this order:

1. `owner = snapshot.dataOwner.githubId`; `actorId = actor.kind === 'owner' ? owner : actor.githubId`; `target = command.githubId`.
2. Reclaim: `actor.kind === 'owner' && command.type === 'set-controller' && target === owner` → `null`.
3. `actorId !== controllerGithubId` → `'not_controller'`.
4. `actor.kind === 'viewer' && command.type === 'unrevoke'` → `'invalid_command'`.
5. `actor.kind === 'viewer' && target === actorId` → `'invalid_target'`.
6. `set-controller`: `target === owner` → `null`; a participant `p` with `p.githubId === target && p.state === 'admitted' && isHostAdmitted(target)` → `null`; else `'unknown_participant'`.
7. `actor.kind === 'owner'` → `null` (D-5).
8. Viewer targets, `p = snapshot.participants.find((x) => x.githubId === target)`: `admit` needs `p?.state === 'lobby'`; `kick`/`revoke` need `p`; `set-contributor` needs `p?.state === 'admitted'`. Otherwise `'unknown_participant'`; when satisfied → `null`.

`readControllerCommand`: `value` must be a non-array object; `type` one of `admit`, `kick`, `revoke`, `set-contributor`, `set-controller`; `githubId` a positive safe integer; `admit` keeps `contributor` only when it is a boolean (a non-boolean `contributor` → `null`); `set-contributor` requires a boolean `contributor`. Build a new object from those keys only (same style as `frameOf`).

Tests: `src/dashboard/server/sharing/__tests__/controller.test.ts` (new) — `describe('ControllerState')` and `describe('controlRefusal')` and `describe('readControllerCommand')`, covering every numbered rule above, including: an unappointed snapshot controller yields the data owner; reclaim while a viewer controls returns `null`; a lobby target for `set-controller` is `unknown_participant`; `unrevoke` from a viewer is `invalid_command`; unknown keys never survive `readControllerCommand`.
