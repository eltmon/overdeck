# PAN-3974 — Native OpenCode CLI in the conversation TERMINAL

**Issue:** [eltmon/overdeck#3974](https://github.com/eltmon/overdeck/issues/3974) (the issue body is the spec; this is the implementation brief).
**Depends on:** PAN-3937 (#3970) — `opencode-port` + `acp-session-id` recorded per conversation.
**Reused by:** PAN-3835 (Codex `codex resume --remote`).

## Glossary

- **Owner** — the conversation's own tmux session (`conv.tmuxSession`, e.g. `conv-20260919-8174`) running the ACP host (`acp-host` → `opencode acp --hostname 127.0.0.1 --port <port>`). Dashboard delivery goes to it over the ACP socket. Never touched by this work except teardown hooks.
- **Companion** — a second tmux session on the same managed socket, named `companion-<ownerTmux>`, running a native client (`opencode attach …`) against the owner's server and exact session. Holds no state of its own; the OpenCode session does.
- **Target** — what an adapter resolves from recorded files: absolute binary, argv, cwd, and a **fingerprint** (`<port>:<sessionId>`).
- **Generation** — `sha256(ownerTmux | owner #{session_created} | fingerprint)` truncated to 24 hex. Changes on every owner respawn (new tmux session, new port). Stamped on the companion at creation as the tmux session env var `OVERDECK_COMPANION_GENERATION` (`new-session -e`, atomic) and read back with `show-environment`. The tmux session is the authority — nothing is stored in a DB or in memory beyond a per-owner promise lock.
- **Runtime log** — the owner pane (ACP host log), i.e. what TERMINAL shows today.

## Requirements

- **FR-1** TERMINAL on a live OpenCode conversation with both recorded values opens or reuses exactly one companion running `opencode attach http://127.0.0.1:<port> --session <id> --dir <cwd>`.
- **FR-2** Dashboard delivery stays on the ACP socket; the companion never receives dashboard prompts; no second server/session starts (attach only; no `--fork`, no `--continue`).
- **FR-3** Server resolves port, session id, cwd, binary, and companion session name. Mutation bodies accept only whitelisted keys (`{}` for open, `{ generation }` for close); any other key (url, command, sessionId, cwd, target, port, …) → 400.
- **FR-4** Returning to Conversation or browser disconnect leaves companion + owner running; explicit Close kills only the companion; owner stop/archive/delete/restart/resume kills the companion.
- **FR-5** Pre-PAN-3937 conversations (`acp-session-id` present, `opencode-port` absent, owner alive) get `restart-required` with an actionable message and a Runtime log view; no automatic restart.
- **FR-6** Codex app-server and every other harness keep today's TERMINAL (owner pane) unchanged.
- **FR-7** Concurrency: per-owner serialized open/close; concurrent opens create one companion; a companion stamped with an old generation is replaced, never reused; an open whose owner changed while it was creating kills what it created; a close carrying a stale generation is refused (409) and kills nothing.
- **NFR-1** Async only (no `execSync`/`*Sync` tmux), no raw tmux text delivery, no DB access, no model fallback.
- **NFR-2** Both routes are mutations and use `rejectUnsafeDashboardMutationRequest` (auth + JSON + trusted origin + CSRF). There is no read route: open is idempotent and returns the state.
- **NFR-3** No new file over 1000 lines; no existing file grows past its cap.

## Decisions

1. Companion session name = `companion-<ownerTmux>`; validated with `validateSessionName`.
2. State table (OpenCode adapter), evaluated server-side on every open:
   | owner tmux alive | `opencode-port` | `acp-session-id` | HTTP `GET /session/<id>` | result |
   | --- | --- | --- | --- | --- |
   | no | – | – | – | `owner-not-running` ("Resume the conversation first") |
   | yes | missing | present | – | `restart-required` |
   | yes | missing/present | missing | – | `owner-starting` |
   | yes | present | present | network error / non-200 | `owner-starting` (non-404) or `session-missing` (404) |
   | yes | present | present | 200 | target ok |
   Malformed port (not an integer 1–65535) or session id (not `^ses_[A-Za-z0-9]{1,120}$`) ⇒ `restart-required` with the malformed-file message.
3. Command is argv, shell-quoted per element and prefixed with `exec`, so the pane process is `opencode attach`; when it exits the session ends and the next open recreates it.
4. When unsure (generation missing/mismatched), kill and recreate — the companion is stateless.
5. Owner teardown hook `closeCompanionTerminalForOwner(ownerTmux)` is called from `stopConversationRuntime` (stop, delete, archive, resume/restart failure, flywheel archive) **after** the shared-session early return (a runtime another conversation still owns keeps its companion), from `spawnConversationSession` right before it kills the owner session (every resume/restart/restart-all), and, for owners that exited on their own, from the conversation lifecycle poll and the PTY supervisor's `exited` event, each before the row is marked ended. Harness-agnostic: it only kills `companion-<ownerTmux>` if present.
6. Frontend keeps the global `ViewMode` (`conversation | terminal`). For companion-capable harnesses the terminal view renders `ConversationTerminalView`, which has a local `Native CLI | Runtime log` switch and a Close button; other harnesses render the existing `<XTerminal sessionName={conversation.tmuxSession} />` unchanged.
7. The shared seam lives in `packages/contracts/src/companion-terminal.ts`: `CompanionTerminalKind`, `companionTerminalKindFor(conversation)`, and the wire types. PAN-3835 adds `'codex-resume-remote'` there, a server adapter, and nothing in the lifecycle, routes, or UI.
