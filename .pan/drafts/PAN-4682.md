# PAN-4682: Fly remote default image follows the Fly app

**Issue:** [PAN-4682](https://github.com/eltmon/overdeck/issues/4682)
**Sibling:** [PAN-4778](https://github.com/eltmon/overdeck/issues/4778) (CI image-build workflow, out of scope here)
**Planned:** 2026-11-01 (auto mode), at `45524993754`

## Glossary

- **Fly app** — a Fly.io application that owns Fly Machines. Overdeck reads its name from
  `[remote.fly] app` in `~/.overdeck/config.toml`; the default is `pan-workspaces`.
- **Fly registry** — `registry.fly.io`, Fly's private Docker registry. It is app-scoped: an
  image can only be pushed to, and pulled from, `registry.fly.io/<app-name>`. A repository
  with no matching app does not exist.
- **Workspace image** — the Docker image every Overdeck Fly Machine runs, built from
  `docker/pan-workspace/Dockerfile`. "pan-workspace" is the name of the Dockerfile folder,
  not of a Fly app.
- **Derived default image** — `registry.fly.io/<resolved app>:latest`, the value this issue
  makes the default when no image is configured.
- **Resolved app** — the app name after defaults apply: `[remote.fly] app` when set, else
  `pan-workspaces`.
- **`FlyProvider`** — `src/lib/remote/fly-provider.ts`, the provider remote work agents
  (`pan start --remote`) use to create Fly Machines.
- **Fly machine provisioning** — `src/lib/anywhere/fly/provision.ts`
  `provisionFlyMachine()`, used by `pan machines add-fly` (PAN-4652). It does not use
  `FlyProvider` to create the machine; it calls the Fly API directly with its own defaults.

## Problem

Both code paths that create Fly Machines default the image to
`registry.fly.io/pan-workspace:latest`. That repository does not exist:
`GET https://registry.fly.io/v2/pan-workspace/tags/list` answers `NAME_UNKNOWN`. The only
pushed image is `registry.fly.io/pan-workspaces:latest` (the app name, built 2026-06-09).
So with no `[remote.fly] image` set, every machine create points at a missing image.

The wrong literal appears in five places:

| Site | Line (at `45524993754`) | Grep anchor |
| --- | --- | --- |
| `src/lib/remote/fly-provider.ts` | 97 | `image: config.image ?? 'registry.fly.io/pan-workspace:latest',` |
| `src/lib/anywhere/fly/provision.ts` | 70 | `const DEFAULT_IMAGE = 'registry.fly.io/pan-workspace:latest';` |
| `src/cli/commands/remote/setup.ts` | 101 | `image: 'registry.fly.io/pan-workspace:latest',` |
| `src/cli/commands/machines-fly.ts` | 123 | `'Image (default: remote.fly.image, else registry.fly.io/pan-workspace:latest)'` |
| `packages/contracts/src/composer-commands.generated.ts` | 60 | generated from the line above |

and in the docs: `docs/fly-provider.md` (lines 32, 117-118, 144, 184-188, 428, 488-490) and
`cli/machines.mdx` line 126.

`pan remote setup` is the worst site: it writes the dead literal into the operator's
`config.toml`, so an operator who ran it stays broken after the code default changes.

The CI workflow `.github/workflows/build-workspace-image.yml` has the same naming mistake
(`APP_NAME: pan-workspace`), but it is also broken for two unrelated reasons and has never
published an image. That is [PAN-4778](https://github.com/eltmon/overdeck/issues/4778), not
this issue (see Decisions D-3).

## Requirements

### Functional

- **FR-1** — When `[remote.fly] image` is unset, `FlyProvider` creates machines with image
  `registry.fly.io/<resolved app>:latest`. With no `app` set that is
  `registry.fly.io/pan-workspaces:latest`; with `app = "my-app"` it is
  `registry.fly.io/my-app:latest`.
- **FR-2** — When `[remote.fly] image` and `--image` are both unset, `provisionFlyMachine()`
  creates the machine with image `registry.fly.io/<resolved app>:latest`, where the resolved
  app is the same `appName` value it passes to `ensureApp` and `createMachine`.
- **FR-3** — An explicit image always wins over the derived default: `--image` (provisioning
  only), then `[remote.fly] image`, then the derived default. The order is unchanged from
  today; only the last fallback changes.
- **FR-4** — Both code paths compute the derived default through one exported function in
  `src/lib/remote/fly-provider.ts`, so the two defaults cannot drift apart again.
- **FR-5** — `pan remote setup` no longer writes an `image` key into the `[remote.fly]`
  block it seeds, so the derived default applies and follows a later edit of `app`.
- **FR-6** — `pan machines add-fly --help` describes the `--image` default as
  `registry.fly.io/<app>:latest`, and the committed composer-command manifest matches.
- **FR-7** — `docs/fly-provider.md` and `cli/machines.mdx` name the derived default, and
  the build-and-push commands push to `registry.fly.io/pan-workspaces:latest`.

### Non-functional

- **NFR-1** — No new runtime I/O: the default is a pure string function.
- **NFR-2** — No config migration. Overdeck does not rewrite an operator's `config.toml`;
  operators who already have the dead literal follow the troubleshooting note (FR-7).
- **NFR-3** — No change to `tests/lib/remote/fly-api.test.ts`. Its
  `registry.fly.io/pan-workspace:latest` strings are opaque fixtures passed straight through
  the API client, not defaults.

## Decisions

- **D-1 Shared helper, not two literals.** Add to `src/lib/remote/fly-provider.ts`:
  `export const DEFAULT_FLY_APP = 'pan-workspaces';` and
  `export function defaultFlyImage(app: string): string`. `provision.ts` already has the
  comment "The same defaults as FlyProvider's constructor." above duplicated constants;
  that duplication is how one copy can drift. `provision.ts` already imports
  `type FlyProvider` from that module and imports `remote/index.js`, which imports
  `fly-provider.js` at runtime, so a value import adds no new module edge and no cycle.
- **D-2 `pan remote setup` omits `image`.** Writing the derived value
  (`registry.fly.io/pan-workspaces:latest`) would pin it, and an operator who later edits
  `app` (the setup output tells them to) would be broken again. Omitting the key lets FR-1
  follow the app. `RemoteConfig['fly'].image` is already optional (`src/lib/config.ts`
  line 72, `image?: string;`).
- **D-3 The CI workflow is a sibling issue.** Fixing `APP_NAME` alone would not make the
  workflow pass: every run dies on `fly: command not found` (the setup action puts only
  `flyctl` on `PATH`), and the repository has no Actions secrets, so `FLY_API_TOKEN` needs
  an operator. Also, edits under `.github/workflows/` cannot be pushed with the agent's
  GitHub OAuth credential (no `workflow` scope), so including one would put this whole
  branch's push at risk. Filed as [PAN-4778](https://github.com/eltmon/overdeck/issues/4778).
- **D-4 No silent migration of the old literal.** Treating
  `registry.fly.io/pan-workspace:latest` as "unset" in code would hide config from the
  operator. The troubleshooting section names the literal and tells them to delete the
  line instead.
- **D-5 Leave historical text alone.** `docs/prds/active/PAN-340-plan.md` and the PAN-4652 /
  PAN-4296 live-verification sections record what happened; they are not instructions.
  The one sentence in `docs/fly-provider.md` that tells operators to set the workaround
  (lines 488-490) is updated to say this issue fixed the default.
