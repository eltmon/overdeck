# PAN-4663 — One Docker bridge network per Overdeck workspace stack

**Issue:** [PAN-4663](https://github.com/eltmon/overdeck/issues/4663)
**Status:** planned (auto mode, 2026-11-01)

## Glossary

- **Workspace stack** — the Docker Compose project that runs one Overdeck feature
  workspace (`overdeck-feature-pan-<n>`). It is rendered from the template at
  `infra/.devcontainer-template/docker-compose.devcontainer.yml.template` into
  `<workspace>/.devcontainer/docker-compose.devcontainer.yml`.
- **Bridge pool** — Docker's set of predefined address pools for user-defined
  bridge networks. On this host it fits about 31 networks
  (`DEFAULT_DOCKER_BRIDGE_POOL_LIMIT = 31`, `src/lib/docker-bridge-pool.ts` line 24).
  When it is exhausted, every `docker network create` fails with
  `all predefined address pools have been fully subnetted`.
- **`_default` network** — the network Compose creates implicitly, named
  `<project>_default`, for any service that declares neither `networks:` nor
  `network_mode:`. If no service needs it, Compose does not create it.
- **`devnet`** — the stack's own declared network (`<project>_devnet`). The only
  non-external network an Overdeck workspace stack should create.
- **`overdeck`** — the shared Traefik network, declared `external: true` in the
  template. Compose attaches to it but never creates it.
- **`network_mode: none`** — a Compose service key that gives the container a
  loopback-only network namespace and attaches it to no network.
- **`init-perms`** — the one-shot template service added by PAN-2777 (commit
  `0c818f484ef`). It runs `chown node:node /workspaces/overdeck/node_modules` as
  root on the `container-node-modules` named volume and exits.
- **Rendered template** — the template after placeholder substitution
  (`{{FEATURE_FOLDER}}`, `{{PROJECT_PATH}}`, `{{PROJECTS_DIR}}`).

## Problem

Every Overdeck workspace stack creates two bridge networks: `<project>_devnet`
and an empty `<project>_default`. On 2026-11-01 eleven live stacks each held a
`_default` network with zero running containers, which pushed the host to the
bridge-pool limit. Four planned issues (PAN-4645, PAN-4648, PAN-4649, PAN-4295)
could not start: the spawn-time stack self-heal (`rebuildWorkspaceStack`, called
from `src/lib/agents/spawn-prep.ts`) failed with
`failed to create network overdeck-feature-pan-4645_devnet: ... all predefined address pools have been fully subnetted`.

## Root cause (verified)

The `init-perms` service in
`infra/.devcontainer-template/docker-compose.devcontainer.yml.template` has no
`networks:` key and no `network_mode:` key. Grep anchor:

```yaml
  init-perms:
    build:
      context: .
      dockerfile: Dockerfile
    user: root
    command: chown node:node /workspaces/overdeck/node_modules
    volumes:
      - container-node-modules:/workspaces/overdeck/node_modules
```

Every other service (`dev`, `init`, `frontend`, `server`) lists `networks:`
(`devnet`, and `overdeck` for the routed ones). So Compose puts `init-perms` on an
implicit `default` network and creates `<project>_default` just for it.

Verified during planning with `docker compose config` (Docker Compose v5.1.0) on
the template rendered with `FEATURE_FOLDER=feature-pan-probe`:

- Current template: top-level `networks` = `default, devnet, overdeck`;
  `init-perms.networks` = `{default}`.
- With `network_mode: none` added to `init-perms`: top-level `networks` =
  `devnet, overdeck`; `init-perms.network_mode` = `none`, no `networks` key.

`docker compose config` prints two warnings on stderr ("The \"LINEAR_API_KEY\"
variable is not set", same for `GITHUB_TOKEN`). They are harmless; send stderr to
`/dev/null` when you parse the JSON.

## Decisions

- **D1 — Fix the template with `network_mode: none` on `init-perms`.** The service
  only runs `chown` on a named volume and needs no network. Attaching it to
  `devnet` instead would also stop the extra network, but it would give a root
  container network access it does not need. `network_mode: none` is the smaller
  privilege. `build:` still works: image builds use the build network, not the
  service's runtime `network_mode`.
- **D2 — Guard with a structural test, not a name list.** The test asserts that
  every service in the rendered template either sets a non-empty
  `network_mode` string or declares at least one network (list entries or map
  keys) none of which is `default`. A future one-shot service without either,
  or with an empty `networks:`, fails the test.
- **D3 — No migration sweep for existing `_default` networks.** Live stacks keep
  their old `_default` network until their next rebuild or teardown. A rebuild
  heals it: `rebuildWorkspaceStack` (`src/lib/workspace/rebuild-stack.ts`, grep
  `'down', '-v', '--remove-orphans'`) runs `down` against the *old* rendered
  compose file, which still declares `default`, so Compose removes the
  `_default` network before re-rendering. Teardown paths also call
  `removeComposeProjectNetworks` (`src/lib/workspace-manager/docker.ts` line 60),
  which removes every network labeled with the compose project. `pan workspace
  reap` does not touch them, because it requires the workspace directory to be
  gone. The wasted subnets therefore free up as stacks rebuild or tear down, not
  at merge time. The docs say so.
- **D4 — Leave generic `_default` handling unchanged.** `WORKSPACE_NETWORK_RE` in
  `src/lib/workspace/traefik-connect.ts`, the orphan-network identity in
  `src/lib/workspace/orphan-networks.ts`, `src/lib/docker-bridge-pool.ts`, and
  `isOneShotService` in `src/lib/cloister/uat-stack.ts` all handle `_default` and
  `init-perms` generically. Other projects' templates can still produce a
  `_default` network, so these stay as they are.
- **D5 — Bundled project templates need no change.** Every service in
  `sync-sources/templates/docker/{dotnet,monorepo,nextjs,python-fastapi,react-vite,spring-boot}/docker-compose.yml`
  already lists `networks:` (checked during planning). `docker/pan-workspace/docker-compose.yml`
  has one service and no top-level networks; its `_default` network is its only
  network, which is normal Compose behavior.
- **D6 — The live check uses a scratch compose project.** The renderer reads the
  template from the project's primary checkout: `renderDevcontainer` in
  `src/lib/workspace/devcontainer-renderer.ts` line 213 does
  `join(opts.projectConfig.path, composeTemplate)`. So this workspace's own
  `.devcontainer/`, a `pan workspace rebuild`, and the spawn-time self-heal all
  render from `main`'s template and still show the bug until this change merges.
  Live verification must render the branch template into a scratch directory
  (see "Implementation checkpoint" in WI-1).

## Requirements

- **FR-1** — The rendered workspace compose file's `init-perms` service sets
  `network_mode: none` and declares no `networks` key.
- **FR-2** — A rendered Overdeck workspace stack creates exactly one
  non-external network, `<project>_devnet`, and no `<project>_default` network.
- **FR-3** — A unit test fails if any service in the rendered template has
  neither a non-empty `network_mode` string nor a non-empty `networks`
  declaration (list or map) that does not name `default`. An empty
  `networks: []` or `networks: {}` counts as undeclared, because Compose still
  attaches such a service to `default` (verified by the plan critic with
  `docker compose config`).
- **FR-4** — The docs state the authoring rule (every compose service lists
  `networks:` or sets `network_mode:`) and explain that existing `_default`
  networks free up on rebuild or teardown.
- **NFR-1** — `init-perms` keeps its current behavior: same `user: root`, same
  `command`, same volume, and `init` still waits on it with
  `condition: service_completed_successfully`.
- **NFR-2** — No change to network-cleanup, Traefik-reconcile, bridge-pool, or
  UAT-stack code (D4).

### WI-2 — Guard test: every service declares a network (FR-1, FR-3)

**File:** `tests/unit/lib/workspace/devcontainer-init-command.test.ts`. It already
renders the template with `readDevcontainerTemplate()`.

1. Widen the `DevcontainerCompose` interface so `services` is typed as
   `Record<string, DevcontainerService | undefined>` where
   `DevcontainerService` has optional `user`, `command`, `volumes`,
   `depends_on`, `networks?: unknown`, and `network_mode?: string`. Keep the
   existing tests compiling against it.
2. In the existing test `repairs the node_modules volume ownership before
   installing dependencies`, add `network_mode: 'none'` to the
   `toMatchObject` for `init-perms`, and add
   `expect(perms).not.toHaveProperty('networks')`.
3. Add a module-level helper next to `readDevcontainerTemplate()` and a new
   test. Compose accepts `networks:` as a list (`- devnet`) or a map
   (`devnet: {}`), so the helper reads both shapes:

```ts
function declaredNetworkNames(networks: unknown): string[] {
  if (Array.isArray(networks)) return networks.map(String);
  if (networks && typeof networks === 'object') return Object.keys(networks);
  return [];
}
```

```ts
  it('attaches every service to a declared network so Compose creates no _default network', () => {
    const services = readDevcontainerTemplate().services ?? {};

    expect(Object.keys(services).length).toBeGreaterThan(0);
    // An empty networks: [] / {} still lands the service on `default`, so it
    // counts as undeclared (PAN-4663).
    const undeclared = Object.entries(services)
      .filter(([, service]) => {
        if (typeof service?.network_mode === 'string' && service.network_mode.length > 0) return false;
        const names = declaredNetworkNames(service?.networks);
        return names.length === 0 || names.includes('default');
      })
      .map(([name]) => name);
    expect(undeclared).toEqual([]);
  });
```

- The test-skip gate fails on any added `it.skip`, `it.skipIf`, or `.only`. Add

- Run only the touched test file, never the full `npm test`.

Verify: `npx vitest run tests/unit/lib/workspace/devcontainer-init-command.test.ts`

## Critique response

### Guard accepts empty networks

Accepted. The plan critic showed that `networks: []` and `networks: {}` both
still attach the service to `default`. FR-3, D2, and the WI-2 test now treat a
service as declared only when it sets a non-empty `network_mode` string or
lists at least one network (list entry or map key) and none of them is
`default`. The new `declaredNetworkNames()` helper reads both the list and map
shapes. AC-3 names the empty-declaration case.

### Network rule needs a scope

Accepted. The pan-docker skill sentence (WI-3 item 3) now applies the rule only
to stacks that declare named networks, and says a stack with no declared
networks that relies only on `_default` is fine, since that is its only
network. The template README keeps the unscoped rule, because the Overdeck
template already declares `devnet`.

### Scratch create has other failure modes

Accepted. The WI-1 fallback now treats a build failure (the Dockerfile curls
`bun.sh/install`), a registry pull failure, a missing external `overdeck`
network, and pool exhaustion as inconclusive. In each case the work agent runs
`down -v`, records the error and the normalized `docker compose config` output
in the commit message, and defers live confirmation to the first post-merge
rebuild. Only a successful `create` that shows a `_default` network or any
network other than `pan4663-netprobe_devnet` counts as a failed fix.
