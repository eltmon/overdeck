# PAN-4799 — Merge train "What to UAT" reads member plans from where they live

**Issue:** https://github.com/eltmon/overdeck/issues/4799
**Status:** draft (auto-planned 2026-11-02)

## Glossary

- **Merge train / UAT batch / generation** — a `uat/<label>-<codename>-<MMDD>` branch that merges every ready feature branch onto `main` so the operator can test them together. One row in the merge-sync store, typed `UatGeneration` (`src/lib/overdeck/merge-types.ts`, `export interface UatGeneration`).
- **Member** — one feature (`UatGenerationMember`: `issueId`, `branch`, …) bundled into a generation.
- **Chain** — the list of generations for one project, newest first, from `listUatGenerations({ projectRoot, limit: CHAIN_PAYLOAD_LIMIT })` (limit 10). A member can appear in several generations of the chain (a superseded batch and its replacement).
- **Batch worktree** — `UatGeneration.worktreePath`, the git worktree the generation was assembled in: `<projectRoot>/workspaces/<generationFolderName(name)>` (`src/lib/cloister/uat-generation-engine.ts`, `const worktreePath = \`${input.projectRoot}/workspaces/${generationFolderName(name)}\``). It has every member branch merged in. For a polyrepo project it is a wrapper folder holding one `<repoKey>/` worktree per contributing repo. Cleanup removes it and sets `cleanedAt`.
- **Feature workspace** — `<projectRoot>/workspaces/feature-<issue>/`, the member's own worktree on `feature/<issue>`.
- **xBRIEF spec** — the plan file `.pan/specs/<date>-<ISSUE>-<slug>.xbrief.json`. It is committed on the feature branch and reaches `main` only when the PR merges.
- **Plan home** — the checkout holding `.pan/`. `getProjectPanPaths(root)` (`src/lib/pan-dir/paths.ts`) resolves it through `resolvePlanHome`, which (a) maps any path inside `<project>/workspaces/<name>/` to that workspace checkout, and (b) for a polyrepo project appends the `pan_records.repo` sub-repo. So passing a workspace or batch-worktree path to `findXBriefByIssue` already lands in the right `.pan/specs`.
- **"What to UAT"** — the per-member acceptance-criteria checklist the Merge train card renders (`src/dashboard/frontend/src/components/merge-train/MergeTrainView.tsx`, `What to UAT —`). When `planResolved` is false it renders `Plan not found for {member.issueId} — its UAT checklist could not be read; …`.
- **`planResolved`** — PAN-3165 flag on each member payload. `false` means the spec could not be found, which is different from a spec with zero criteria.

## Problem

The "What to UAT" section shows "Plan not found for PAN-xxxx" for every batch member (operator screenshot, batch `pan-wren-1102-14`: PAN-4658, PAN-4683, PAN-4748).

Root cause, verified against the code at `2f515908a4a`:

- `src/dashboard/server/services/uat-train.ts` line 675: `const acCache = await loadAcceptanceCriteriaCache(memberIssueIds, root);` passes the project root (the primary checkout, on `main`).
- line 640: `const found = await Effect.runPromise(findXBriefByIssue(root, upperIssueId));` searches only that root.

Every batch member is unmerged by definition, so its spec is not on `main` and the lookup can never succeed. The dashboard log shows `[uat-train] no xBRIEF spec resolved for <id> under <root>` for PAN and MIN issues alike. This is the third lookup-root bug in this function: PAN-1696 (dashboard root instead of the project root), PAN-3165 (plan-home ignored), and now PAN-4799 (main instead of the branch).

## Decisions (made here, binding on the work agent)

- **D1 — Lookup order.** For each member, the candidate roots are, in order:
  1. The batch worktree of the **newest** generation in the chain that contains the member, has no `cleanedAt`, and whose `worktreePath` exists on disk.
  2. The member's feature workspace: `getWorkspaceInfoForIssue(issueId).localPath` from `src/dashboard/server/routes/workspaces.ts` (the resolver `POST /api/review/:issueId/request` uses), only when `exists && !isRemote && localPath` and the path exists on disk.
  3. The project root, **always** (not existence-gated; `findXBriefByIssue` already returns null for a root with no `.pan/specs`).
  Duplicates are removed, keeping the first occurrence. The first root whose `findXBriefByIssue` returns a spec wins.
- **D2 — Polyrepo.** Pass the batch wrapper folder / feature workspace path straight to `findXBriefByIssue`. `getProjectPanPaths` → `resolvePlanHome` maps it to `<checkout>/<pan_records.repo path>`. Verified: MYN, Auricle and Botland all have plan-home repos whose config `name` equals `path` (`infra`/`infra`, `bot-land`/`bot-land`), and `/home/eltmon/Projects/myn/workspaces/feature-min-1072/infra/.pan/specs` exists. No new plan-home seam is added.
- **D3 — Resolver placement.** The ordering logic lives in a new pure module `src/dashboard/server/services/uat-member-spec-roots.ts` with injected `exists(path)` and `featureWorkspacePath(issueId)` functions, so it is unit-tested without mocks. `uat-train.ts` wires the real `existsSync` and `getWorkspaceInfoForIssue`. Importing `routes/workspaces.ts` from a service is allowed: services already import route modules (`services/anywhere-boot.ts`, `services/fleet-update-service.ts`), and a madge run on `routes/workspaces.ts` (851 modules) shows it does not reach `services/uat-train.ts`, so no import cycle forms. `routes/workspaces.ts` itself is **not edited** (it is at 1355 lines against a 1358 allowlist cap).
- **D4 — Cache key (revised after critique).** `acceptanceCriteriaByIssue` stays keyed by upper-case issue id, and each entry records the `path` actually read plus a `rootsKey` (the member's candidate roots joined with `\0`). **Only a hit from the first candidate root (`roots[0]`) is stored.** A hit from a later root is returned for this poll but not cached (any existing entry is deleted), so the next poll searches the higher-priority roots again and a spec that appears there wins. An entry is reused only when its `rootsKey` equals the member's current candidate list **and** `stat(path).mtimeMs` is unchanged. A changed candidate list (a new batch worktree, a workspace appearing or being reaped) forces re-resolution. A failed `stat` deletes the entry and falls through to resolution **in the same call**. Re-searching fallback roots every poll is bounded by `xbrief-index.ts`'s 5 s per-root index TTL.
- **D7 — Stale index recovery (added after critique).** `findXBriefByIssue` serves a per-root index cached for 5 s, so it can return a path whose file was just deleted. In the per-root loop, when `stat(found.path)` fails with `ENOENT`, call `invalidateXBriefIndex(root)` (exported from `src/lib/xbrief/xbrief-index.ts`), retry `findXBriefByIssue(root, id)` once, and if that returns null or another missing path, continue to the next root. Any other failure (a `readXBriefDocument` parse or merge-conflict error, a non-ENOENT stat error) keeps today's behaviour: warn and report `planResolved: false` for that member without trying later roots, because a broken spec is a real plan that needs fixing, not a missing one.
- **D5 — No frontend change.** `planResolved` already drives the "Plan not found" note in `MergeTrainView.tsx`.
- **D6 — Warning text.** On a miss, the warning lists every root tried: `[uat-train] no xBRIEF spec resolved for ${id} under ${roots.join(', ')} — UAT checklist unavailable`.

## Requirements

- **FR-1** A batch member whose spec exists only on its feature branch renders its acceptance criteria (`planResolved: true`) when the batch worktree exists.
- **FR-2** When no live batch worktree exists, the member's spec is read from its local feature workspace.
- **FR-3** When neither the batch worktree nor the feature workspace yields a spec, the project root is searched (already-merged members).
- **FR-4** A member with no spec in any root still reports `planResolved: false`, so the "Plan not found" note still renders.
- **FR-5** The newest live generation containing the member supplies the batch worktree; cleaned generations (`cleanedAt` set) and worktrees missing on disk are skipped.
- **FR-6** Remote (fly) workspaces and missing feature workspaces are skipped without error.
- **FR-7** The mtime cache stores only first-root hits and reuses an entry only for the same candidate list and unchanged mtime of the path actually read; a reaped source falls through to the next root on the same poll; a spec that appears in a higher-priority root replaces a fallback result on the next poll.
- **FR-9** A stale index entry pointing at a deleted spec file does not end the lookup: that root's index is invalidated, retried once, and the remaining roots are tried in the same poll.
- **FR-8** `docs/MERGE-WORKFLOW.md` states where the "What to UAT" checklist is read from.
- **NFR-1** For a member whose spec is in its first candidate root (the normal case), steady state does no xBRIEF index scan: per poll it costs one `getWorkspaceInfoForIssue` call, at most two `existsSync` checks (to rebuild the candidate list for `rootsKey`) and one `stat` of the cached spec. A member resolved from a fallback root re-queries the index each poll, bounded by the index's 5 s TTL.
- **NFR-2** No new import cycle: `npm run lint:circular` passes.
- **NFR-3** `uat-train.ts` stays under the 1000-line file-size ceiling; `routes/workspaces.ts` is not modified.

```ts
/**
 * Where a merge-train member's xBRIEF spec can live, in lookup order (PAN-4799).
 *
 * A spec is committed on the feature branch and reaches main only when the PR
 * merges, so every batch member's spec is missing from the project root. Look
 * in the batch worktree (every member merged in), then the member's own
 * feature workspace, then the project root (already-merged members).
 */
import type { UatGeneration } from '../../../lib/overdeck/merge-types.js';

export interface MemberSpecRootDeps {
  exists: (path: string) => boolean;
  /** Local feature-workspace path for the issue, or null (none, or remote). */
  featureWorkspacePath: (issueId: string) => string | null;
}

export function memberSpecRoots(
  issueId: string,
  chain: ReadonlyArray<Pick<UatGeneration, 'worktreePath' | 'cleanedAt' | 'members'>>,
  projectRoot: string,
  deps: MemberSpecRootDeps,
): string[] {
  const upper = issueId.toUpperCase();
  const roots: string[] = [];
  const batch = chain.find((gen) =>
    !gen.cleanedAt
    && gen.members.some((m) => m.issueId.toUpperCase() === upper)
    && deps.exists(gen.worktreePath));
  if (batch) roots.push(batch.worktreePath);
  const workspace = deps.featureWorkspacePath(upper);
  if (workspace && deps.exists(workspace)) roots.push(workspace);
  roots.push(projectRoot);
  return [...new Set(roots)];
}
```

## Critique response

### Cached fallback masks a newly available batch spec

Accepted. D4 now caches only hits from the first candidate root. A hit from a later root is served for that poll but not stored, so every later poll searches the higher-priority roots again, and a spec that appears in the batch worktree wins on the next poll. The re-search cost is bounded by the per-root 5 s index TTL in `xbrief-index.ts`. New work item W2b step 1 and its test `prefers a spec that appears in the batch worktree over a cached fallback` cover it (FR-7).

### Deleted indexed spec prevents same-poll fallback

Accepted. New decision D7: when `stat(found.path)` fails with `ENOENT`, the loop calls `invalidateXBriefIndex(root)`, retries that root once, and then continues to the remaining roots in the same poll. Other errors keep the existing warn-and-`planResolved: false` path. W2b step 2 and the test `recovers from a stale index entry for a deleted spec` cover it (FR-9).

### UAT criterion excludes valid empty plans

Accepted. AC-UAT now requires `planResolved: true` with `acceptanceCriteria` equal to the spec's extracted criteria, including an empty list.

### Unresolved after two critic rounds

- Negative index delays priority change
- Malformed specs bypass the broken-spec rule
