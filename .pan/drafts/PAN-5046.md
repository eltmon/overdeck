# PAN-5046: Phone link keeps dropping on 5G — re-offer storm, held messages, boot-time link errors

**Issue:** [PAN-5046](https://github.com/eltmon/overdeck/issues/5046)
**Related:** PAN-5018 (phone link diagnostics and suspect-connection eviction, merged as #5034, commit `06aca3e599d`).
**Planning mode:** `pan plan --auto` (no operator questions; defaults recorded under "Decisions").

## Glossary

- **Phone dialer** — `createMachineDialer` in `packages/anywhere-channel/src/dial-machine.ts`. Keeps one browser
  `RTCPeerConnection` ("pc") per `(environmentId, relay)` key and opens one `ovdl` data channel per dial on it.
- **Entry** — the dialer's `PeerEntry` record for one pc: its signalling `session` id, pending candidates, waiters.
- **Session id** — the 16-byte hex id the initiator stamps on every `signal` frame for one pc. The server indexes its
  pcs by session (`RtcTransport.bySession`) and by `peer|route|purpose` key (`RtcTransport.byKey`).
- **Re-offer / replacement** — the phone sends an `offer` with a *new* session id. The server's `RtcTransport.accept`
  closes the previous pc for the same key and logs `rtc closing session <old> for <peer>: a new offer replaced it`.
- **ICE restart** — renegotiating the *same* pc with fresh ICE credentials (`createOffer({ iceRestart: true })`)
  so a network change (Wi-Fi ↔ 5G, cell handover) finds a new path while the DTLS/SCTP association and every open
  data channel survive. It reuses the existing session id.
- **Raw channel** — an `RtcDuplexWeb` (`packages/anywhere-channel/src/rtc-duplex-web.ts`): a streamx `Duplex` over
  one data channel. The Noise "secure channel" runs on top of it (`openSecureChannel`).
- **Eviction (PAN-5018 D-5)** — `apps/mobile/src/shell/connection.ts` `secure()` closes the phone's pcs to a machine
  when a secure open fails with `ChannelOpenError` code `timeout` or `protocol`.
- **Connection phase** — the dashboard frontend's derived link state (`deriveConnectionPhase`,
  `src/dashboard/frontend/src/lib/connectionState.ts`). Held composer messages flush only in phase `live`.
- **Link route source** — the module-level `source` in `src/lib/anywhere/link-client.ts` that `linkFetch` /
  `openLinkSocket` read; `null` makes them throw `Machine links are not running on this dashboard`.

## Problem

On 2026-11-04 around 17:45Z the operator typed in a conversation in the iPhone app on 5G. The screen blanked with a
"couldn't connect" message; a message sat at "Waiting to send — will send when the server reconnects" for a long
time. The home dashboard did not restart. `~/.overdeck/logs/dashboard.log` shows three separate things.

### Finding 1 — the re-offer storm (the real bug)

Log lines 2174958–2178541: 27 `rtc closing session <s> for 933e853d: a new offer replaced it`, three
`rtc session <s> 933e853d failed`. Every offer is `(link, direct)`; no relay offer appears. Every replaced session had
just logged `connected`; in two cases the next offer arrived before the previous session even connected
(`b9dd8bc4` → `e025aedf`, lines 2177836–2177838).

The phone sends a new session id only when `dial()` finds no live entry:

1. `packages/anywhere-channel/src/dial-machine.ts` line 236 — a pc whose `connectionState` is `disconnected` is
   treated as dead and closed:
   ```ts
   if (entry && (entry.closed || ['failed', 'closed', 'disconnected'].includes(entry.pc.connectionState))) {
     closeEntry(entry, new Error(`direct connection ${entry.pc.connectionState}`));
   ```
   `disconnected` is the transient state a network change produces; ICE often recovers from it. Closing the pc on the
   next dial forces a new offer instead of an ICE restart.
2. `apps/mobile/src/shell/connection.ts` lines 213–216 — PAN-5018 eviction closes **every** pc to the machine:
   ```ts
   if (suspectsPeerConnection(error)) {
     routes.delete(environmentId);
     directory.dialer.close(environmentId);
   }
   ```
3. `forgetRoutes()` on app resume (`apps/mobile/src/shell/lifecycle.ts` `resume`) — one re-offer per resume; 27
   resumes in a few minutes is implausible, so this is not the storm.

**Why one eviction becomes a loop.** Per the WebRTC spec, `RTCPeerConnection.close()` closes its data channels
abruptly and fires **no** `close` event on them. The dialer's `closeEntry` (line 82) calls `entry.pc.close()` and
rejects pending dial waiters, but every raw channel it already handed out (`RtcDuplexWeb`, which ends only on the
channel's `close` event, rtc-duplex-web.ts line 45) stays silently open. So:

1. A 5G change stalls pc N. A handshake on it times out (10 s, `DEFAULT_OPEN_TIMEOUT_MS`), code `timeout`.
2. Eviction closes pc N and every other pc to the machine; the next dial creates pc N+1 → new offer.
3. Raw channels that were mid-handshake on pc N (or N+1 when the next eviction lands) never see `close`. Their
   handshakes hang until they too time out with `timeout` → eviction again → closes the **healthy** current pc →
   new offer → the server replaces the session it just connected.
4. The `/ws/rpc` `ChannelWebSocket` on a locally closed pc also never closes, so the frontend does not learn the
   link died until its own watchdog fires; when it does, every reconnect dials into the churn. Composer messages
   stay held ("Waiting to send") the whole time.

The server log alone cannot distinguish cause 1 from cause 2 because the phone's `[overdeck] link …` lines exist
only on the device. The plan fixes both and the reproduction work item captures both sides' lines.

**The server cannot accept an ICE restart today.** `src/lib/anywhere/channel/rtc-transport.ts` line 277 drops an
offer on a known session:
```ts
if (data.sdp?.type === 'offer') this.log(`rtc offer dropped: session ${shortId(session)} from ${shortId(from)} is already open`);
```
werift 0.25.1 (`node_modules/werift/lib/webrtc/src/transport/ice.js` lines 253–264) restarts its ICE transport when
`setRemoteDescription` brings a changed `ice-ufrag`/`ice-pwd`, so routing that offer through the existing pc's
`setRemoteDescription` + `createAnswer` is enough on the server side.

### Finding 2 — "Machine links are not running on this dashboard" is a boot-ordering race, not per-pass

The issue counted 96 such lines "every pass". The log shows exactly five of them right after each
`[overdeck] Dashboard listening` line (for example lines 2174355 → 2174406–2174410), never between boots. The
dashboard restarted many times, which made it look periodic. The Fly VM `fly-8d4101ae001028` lines (around line
2143683) are the same boot burst from when that VM still had a live link; nothing logs for it afterwards.

Cause — `src/dashboard/server/services/anywhere-boot.ts`:
```ts
  supervisor.start();                       // line ~169: links start connecting
  ...
  await workerFollower.start()...           // awaits
  ...
  await laneFollower.start()...             // awaits
  setLinkStatusSource(supervisor);
  setLinkPresenceSource(supervisor);
  setLinkRouteSource(supervisor);           // line ~180: too late
```
A fast link (the MacBook on the LAN) delivers its descriptor during those awaits. `onDescriptor` runs the three
linked syncs (`linked-conversations-sync.ts`, `linked-projects-sync.ts`, `linked-needs-you-sync.ts`), whose
`linkFetch` sees `source === null` and throws. The caches stay empty until the next heartbeat with a changed hash.
Fix: wire the three sources before `supervisor.start()`. No "skip destroyed machines" logic is needed: a link whose
machine is gone never comes online, so it never triggers `onDescriptor`.

### Finding 3 — the unknown-peer refusals are the MacBook re-linking, not the phone

`Initiator key 4a70be6a806b0ee8…` (log lines 2079661–2079797) is the `machineKey` of `Edwards-MacBook-Air.local` in
`~/.overdeck/machine-links.json` and in four `machine:Edwards-MacBook-Air.local` access tokens, three revoked on
2026-11-03 (17:54:58Z, 17:58:51Z, 19:43:23Z) with replacements minutes later. Neighbouring GitHub sync lines use
`since=2026-10-20T17:54…` (a 14-day window), which dates the refusals to about 2026-11-03T17:54Z — inside the first
re-link window. Four refusals = the MacBook dialing home during two re-link gaps. No code change; the docs gain a
line explaining what `unknown-peer` looks like during a re-link.

## Requirements

### Functional

- **FR-1** — When the phone dialer closes a pc (any reason), every raw channel it handed out on that pc ends at once
  with an error (`destroy(new Error('direct connection closed: <reason>'))`), so open streams close and in-flight
  handshakes fail immediately instead of hanging until the 10 s timeout.
- **FR-2** — A handshake failure on a raw channel whose pc was closed by the dialer maps to `ChannelOpenError` code
  `unreachable` (not `identity-refused`, not `timeout`), so it never triggers eviction and never shows "Pair again".
- **FR-3** — PAN-5018 eviction closes only the pc that carried the failed raw channel, and only while that pc is still
  the dialer's current entry for its key. A late timeout from an older pc never closes a newer one.
- **FR-4** — A pc in `disconnected` is reused by new dials (no new offer). If it is still `disconnected` after
  `DISCONNECT_GRACE_MS` (2 000 ms), the dialer performs one ICE restart on the same session. If it is not `connected`
  within `ICE_RESTART_TIMEOUT_MS` (10 000 ms) of sending the restart offer, the dialer closes the entry (FR-1 applies)
  and the next dial sends a fresh offer. `failed` and `closed` still close the entry at once.
- **FR-5** — The phone dialer applies an `answer` whenever its pc's `signalingState` is `have-local-offer` (the initial
  answer and each ICE-restart answer); it ignores an answer in any other state.
- **FR-6** — The server's `RtcTransport` answers an `offer` on a known, open session from the same peer by
  renegotiating the existing pc (`setRemoteDescription(offer)`, `createAnswer`, `setLocalDescription`, send `answer`)
  and logs `rtc session <s> ice restart from <from>` followed by `rtc session <s> answered`. Offers for a session of
  another peer or a closed session keep today's drop lines.
- **FR-7** — The phone dialer logs (through an injected `log`, default `console.warn` with `[overdeck] `):
  `rtc <env8> disconnected; ice restart in 2000 ms`, `rtc <env8> ice restart sent`,
  `rtc <env8> ice restart recovered`, `rtc <env8> ice restart timed out; closing`, and
  `rtc <env8> closing session <s8>: <reason>` for every entry close. Ids are cut to 8 characters; no SDP, candidate,
  key or token text.
- **FR-8** — When the phone's link to the current machine recovers after a failure (an ICE restart reaches
  `connected`, or a new pc connects after the previous one for the same machine closed), and the frontend connection
  phase is not `live`, the shell calls `useConnectionState.getState().requestReconnect()` so the `/ws/rpc` stream
  reconnects now instead of waiting out its backoff (up to `RECONNECT_MAX_DELAY_MS` = 10 s). Held composer messages
  then flush through the existing `flushHeldMessages` path.
- **FR-9** — `startAnywhere` wires `setLinkStatusSource`, `setLinkPresenceSource` and `setLinkRouteSource` to the
  supervisor before `supervisor.start()`, so a boot never logs `could not fetch <machine>'s …: Machine links are not
  running on this dashboard` for a link that comes online during boot.

### Non-functional

- **NFR-1** — A new phone against an old server (which still drops a known-session offer) recovers through FR-4's
  restart timeout and a fresh offer; an old phone against a new server behaves exactly as today.
- **NFR-2** — No log line on either side carries SDP, ICE candidate text, keys, tokens or pairing codes (PAN-5018
  NFR-1 stays in force).
- **NFR-3** — Tests that exercise the grace and restart timers use `vi.useFakeTimers()` with
  `vi.advanceTimersByTimeAsync` (repo rule "Fake timers for retry / backoff / delay-based tests"). Tests over real UDP
  (werift ↔ werift) keep real timers, as `rtc-transport.test.ts` already does, and must finish in under 15 s each.
- **NFR-4** — No `execSync` and no new sync helpers in server-reachable code (repo rule).

## Decisions

- **D-1 (FR-1, FR-2)** — The dialer tracks the raw channels it hands out per entry (`entry.duplexes: Set<RtcDuplexWeb>`)
  and `closeEntry` destroys each with an `Error`. A destroyed-with-error duplex makes `FrameReader` fail with that error
  (wire.ts `onError`), which `toOpenError` maps to `unreachable`. The fix does not depend on whether a browser fires
  `close` on data channels after `pc.close()`.
- **D-2 (FR-3)** — The dialer gains `evict(raw: RtcDuplexWeb, reason: string): void`. It finds the entry that owns `raw`
  (a `WeakMap<RtcDuplexWeb, PeerEntry>`) and closes it only if `byKey.get(entry.key) === entry`. `connection.ts`
  `secure()` calls `directory.dialer.evict(raw, …)` instead of `directory.dialer.close(environmentId)`; it still
  deletes the remembered route. The eviction codes stay `timeout` and `protocol`.
- **D-3 (FR-4)** — ICE restart uses `pc.createOffer({ iceRestart: true })` + `setLocalDescription` + send on the same
  session, not `pc.restartIce()` + `negotiationneeded`, so the flow does not depend on event timing. One restart is
  in flight per entry; a later `disconnected` after recovery may start another.
- **D-4 (FR-6)** — The server keeps today's immediate replacement for a **new** session id from the same key. A phone
  sends a new session only after it closed its old pc, so a graceful two-pc handover would only hold dead pcs longer.
- **D-5 (FR-8)** — Recovery triggers `requestReconnect()` (EventRouter's `forceReconnect`), not `resetTransport()`,
  and only when the phase is not `live`, so a healthy stream is never torn down and the initial bootstrap is not
  disturbed (the first pc for a machine is never a "recovery").
- **D-6 (FR-9)** — Extract the wiring into an exported helper in `anywhere-boot.ts` so its call order is unit-testable
  without booting the dashboard. No source-text test (repo lint rejects source-grep tests).
- **D-7** — No skip logic for destroyed or unlinked machines (Finding 2). No code change for Finding 3.
- **D-9 (FR-4, FR-6)** — During a restart, both sides hold new-generation candidates until the new description pair is
  in place: the phone sets `remoteSet = false` before sending the restart offer; the server sets `localSent = false`
  before applying it. Both flags already exist and the existing drain paths restore them.
- **D-8** — Server-initiated ICE restart for machine↔machine links (`RtcTransport.dial` as initiator also treats
  `disconnected` as dead) is out of scope; this issue fixes the phone path the operator hit.
