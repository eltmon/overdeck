# PAN-5361: make the bare-host-linux idle verdict robust to host PID bursts

**Issue:** https://github.com/eltmon/overdeck/issues/5361
**Status:** planned (auto mode, 2026-11-15)

## Summary

The `bare-host-linux` CI job fails its idle check on about 3% of runs with no Overdeck change. The Linux rule `pid-net` subtracts one 30 s baseline sample of machine-wide PID consumption from one 30 s idle sample. The hosted runner produces bursts of about +20 and +60 PIDs per window at random, in both windows. A burst in the idle window fails the check; a burst in the baseline window hides real idle work. The fix takes three windows per side on Linux and decides on `min(idle windows) − min(baseline windows)`, so one burst in any one window cannot move the verdict. It also adds a `/proc` attribution of the dashboard's own process tree, a controlled steady-spawner canary, and a calibration run. macOS keeps its exact current behaviour.

## Glossary

- **PID counter**: the kernel's last-allocated PID. Every new process **and every new thread** takes the next number, machine-wide. `new_pids()` reads it by running `sh -c 'echo $$'` before and after a `sleep`.
- **Window**: one `new_pids "$WINDOW_SECS"` call (30 s). Its count is "new PIDs in the window". Between the two counter reads only `sleep` runs.
- **Baseline window**: a window with no Overdeck process alive (after `stop_all`, before the idle dashboard starts).
- **Idle window**: a window taken while the directly started dashboard (`dist/dashboard/server.js`) is idle, after `SETTLE_SECS`.
- **Burst**: a window whose count exceeds its side's typical level by roughly +15 or more, caused by the runner host, not Overdeck. Observed sizes about +20 and about +60 at 5–7% per window (issue evidence, 211 runs).
- **pid-net**: the Linux deciding rule. Today `idleNew − baselineNew` over one window each. After this change: `min(idle windows) − min(baseline windows)`.
- **traced-cost**: the macOS deciding rule (unchanged): traced `child_process` calls in the idle window plus `(BARE_PATH_ENTRIES − 1)` per call that failed to spawn.
- **Spawn tracer**: the Node preload `spawn-trace.cjs` written by `write_spawn_tracer()`; it logs one JSON line per `child_process` call into `spawn-trace.log`.
- **Dashboard tree**: the idle server process, its descendants (by `ppid` chain), and any process whose `/proc/<pid>/cmdline` contains `"$WORK_DIR/home/"` or `"$WORK_DIR/tools/"` (the two strings `kill_work_processes` matches at `:468-471`, which also catches a daemonized child reparented away from the server).
- **Tasks**: the sum of `num_threads` (field 20 of `/proc/<pid>/stat`) over the dashboard tree, so it counts processes and threads.
- **Deciding window**: the idle window with the smallest count (first one on ties). Its index is reported.
- **Attribution**: per idle window, the PIDs the dashboard tree accounts for: the larger of weighted traced calls and tree task growth. Defined numerically in FR-6.
- **D14 rule**: the PAN-5176 calibration rule `budget = max(10, min(30, 3 × highest sample))`, never above 30 (`scripts/bare-host-smoke.sh:34`).
- **Spawner canary**: a run of the smoke with `--idle-spawner-ms <n>`, which loads a preload into the idle dashboard that spawns `true` every `n` ms. It must fail `pid-net`.

## Requirements

### Functional

- **FR-1**: On Linux the smoke takes `WINDOWS_PER_SIDE_LINUX=3` back-to-back baseline windows and 3 back-to-back idle windows; `pid-net` = `min(idle) − min(baseline)`. A single burst of up to +65 in any one window can move `pid-net` only by the normal spread between that side's windows (the minimum falls through to the next-smallest window), never by the burst's size. A run already within that spread of the budget can still flip; the test `a burst on the unique minimum window moves the net by at most the window spread` pins this.
- **FR-2**: On macOS the smoke takes exactly 1 baseline and 1 idle window with today's timing and today's second-resolution inclusive trace stamps. The `traced-cost` rule, value and budget are unchanged.
- **FR-3**: `result.json` keeps `idle.rule`, `idle.value`, `idle.budget`, `idle.net`, `idle.netPerSec`, `idle.baselineNew`, `idle.idleNew`, `idle.spawns`, and adds `idle.windowsPerSide`, `idle.baselineWindows` (array of counts), `idle.idleWindows` (array of objects), `idle.decidingWindow`, `idle.attribution`, `idle.injectedSpawnerMs`. `baselineNew`/`idleNew` become the minima (on macOS: the single values, as today).
- **FR-4**: The printed summary and `GITHUB_STEP_SUMMARY` show every window's raw count on both sides, and the minima.
- **FR-5**: On Linux, at every window boundary of the idle side, the smoke records the dashboard tree's process count and task count from `/proc`, using only bash builtins, outside the two counter reads.
- **FR-6**: Attribution of the deciding idle window `d`: `tracedPids_d` = traced call records in `[from_d, to_d)` with `event !== "exit"`, each weighted 2 when the call went through a shell (`exec`/`execSync` or `options.shell`) and 1 otherwise; `growth_d = max(0, tasksEnd_d − tasksStart_d)`; `attributed_d = max(tracedPids_d, growth_d)` (not the sum: a traced child still alive at the end snapshot appears in both signals, so summing would count it twice); `excess_d = idleWindows[d].new − baselineMin`. `source = "dashboard-tree"` when `2 × attributed_d ≥ excess_d`, else `"unattributed"`. On a Linux idle failure the job prints `excess source: the dashboard process tree (...)` or `excess source: not accounted for by the dashboard probes (traced calls, live tree tasks); the source is likely elsewhere on the host, but short-lived threads and non-Node grandchildren are invisible to the probes (...)`.
- **FR-7**: `--idle-spawner-ms <n>` (whole number ≥ 50) loads a preload into the idle dashboard server only, which spawns `true` every `n` ms. `idle.injectedSpawnerMs` records `n` (null otherwise).
- **FR-8**: A new CI job `bare-host-linux-spawner-canary` runs the smoke with `--idle-spawner-ms 500` when the smoke changes and passes only when the smoke fails on `pid-net` with `attribution.source === "dashboard-tree"`.
- **FR-9**: `IDLE_BUDGET_LINUX` is set by the D14 rule from ≥ 20 calibration runs of the new measure; the calibration values are recorded.

### Non-functional

- **NFR-1**: Between the two counter reads of every window only `sleep` runs. Snapshots, `date` stamps and file writes happen outside them. Baseline and idle windows use the same function.
- **NFR-2**: The whole script still parses and runs under macOS `/bin/bash` 3.2 (no `declare -A`, `mapfile`, `${x,,}`, `;&`, `|&`, `[[ -v ]]`), including Linux-only functions.
- **NFR-3**: The Linux job grows by at most about 3 minutes (2 extra windows per side = +120 s, plus snapshots).
- **NFR-4**: The final diff contains no temporary calibration workflow and no matrix on `bare-host-linux`.

## Decisions (made here)

1. **Estimator: min of 3 per side.** A real steady regression shows up in every idle window, so the minimum keeps it; one runner burst moves only one window. Median-of-3 survives only one burst per side; min-of-3 survives two. Attributing the whole verdict to the dashboard tree via a PID namespace (`unshare --pid`) was rejected: Ubuntu 24.04 runners restrict unprivileged user namespaces, and it changes the process model under test.
2. **macOS frozen at N=1.** The macOS rule is `traced-cost` over one window and the known-bad job depends on it. Extra macOS windows would add minutes on a 5-concurrent-job queue for a number that does not decide.
3. **Fallback N.** If any calibration run shows a burst (count > that side's median across all calibration runs + 15) in **every** window of one side, set `WINDOWS_PER_SIDE_LINUX=5` and redo calibration. This is implementation checkpoint CP-1.
4. **Budget.** Apply D14 to the calibration nets. It will be 30 unless 3 × the highest net is below 30. Never above 30.
5. **Spawner canary rate 500 ms**, not the issue's 2 s example: 2 s adds about +15 per window, which on a normal net of about 6 gives about 21, under the budget of 30 on both old and new measures. 500 ms adds about +60 (net about 66), well over any D14 budget.
6. **Verdict code moves to `scripts/bare-host-smoke/result.mjs`** with pure exports, as the issue invites, so the estimator gets a unit test. `write_result` keeps exporting env vars and runs `node "$SCRIPT_DIR/bare-host-smoke/result.mjs"`.
7. **`SCRIPT_DIR` is resolved at the top of the script**, before any function runs, because `main` does `cd "$WORK_DIR/home"` and `die_setup` can call `write_result` early.
8. **Linux trace stamps use milliseconds** (`date +%s%3N`, GNU) with half-open bounds `[from, to)`, so back-to-back windows never share a record. macOS keeps `$(date +%s)000` / `$(date +%s)999` inclusive.
9. **Attribution is a heuristic diagnostic, never the verdict.** `/proc` has no per-process fork counter, boundary snapshots see only live tasks, and the tracer sees only Node `child_process` calls. Shell calls weigh 2 as an upper bound (`sh` + program), which biases toward blaming the dashboard, the safer side.
10. **Calibration runs on a temporary push-triggered workflow** (`.github/workflows/bare-host-calibration.yml`, `on: push: branches: [feature/pan-5361]`), because `ci.yml` runs only on PRs and on main, its `concurrency` cancels superseded runs, and `workflow_dispatch` needs the file on the default branch. It smokes the published `@overdeck/core@0.86.0` (`--version`), so it needs no build job. It is deleted before `pan done`.
11. **No changelog entry.** The change is CI-only and users do not notice it (`changelog.d/README.md`).

  # fixed point: add any pid whose ppid is a member, until no change

  # sum procs and threads over members

## Critique response

### Empty idle windows crash result reporting

Accepted, and the PRD is changed. WI-1 now says `decideIdle` computes `spawns` only when there is at least one idle window and otherwise returns `spawns: null` with `idleNew`, `decidingWindow`, `net`, `value` and `attribution` null and `pass: false`. `result.json` is still written and rendered with `n/a`, matching today's behaviour for empty trace bounds, so a boot failure or a `die_setup` call keeps its structured result and CI artifact. WI-1 adds the test `no idle windows (boot failure or setup error) returns spawns null and pass false, and renderLines prints n/a` for both OSes, and `result-module.ac6` checks it.

### Retaken windows use the wrong tree boundary

Accepted, and the PRD is changed. Boundary snapshots are no longer shared between windows. WI-3 now takes a start snapshot immediately before each window's `from` stamp, retakes and **replaces** that start snapshot when a negative count forces a retake, and takes the end snapshot after `to`. `R_IDLE_TREE` carries one `startProcs:startTasks:endProcs:endTasks` entry per window, so a window's tree delta always covers the same 30 s as its count and trace bounds. `tree-snapshot.ac4` checks that the retake path calls `tree_snapshot` before the retake's `from` stamp.

### A single burst can flip the verdict (round 2)

Accepted, and the PRD is changed. Min-of-3 does not give exact one-burst immunity: a burst on the unique minimum window moves the minimum to the next-smallest window. FR-1 now states the real property: one burst moves the net by at most the normal spread between that side's windows, never by the burst's size. The issue's AC1 targets the observed failure mode, a burst adding +20 to +65 to one sample; under min-of-3 that excess cannot reach the verdict, and the residual change is the few-PID window spread, which the D14 budget (3 × the highest calibration net) already absorbs. A new named test pins the near-budget case. Exact immunity would need an estimator that ignores the window counts' own spread, which also ignores real changes of that size, so it is not adopted.

### Attribution double counts live children (round 2)

Accepted, and the PRD is changed. `attributed_d` is now `max(tracedPids_d, growth_d)`, a conservative bound: a traced child still alive at the end snapshot counts once, not twice. A named test covers a traced child that stays alive across the end snapshot. The steady-spawner canary is unaffected: its 60 short-lived `true` calls give `tracedPids` 60 and growth near 0.

### Aggregate traces include unmeasured gaps (round 2)

Accepted. The top-level `spawns` summary is now the sum of the per-window summaries, so calls made in the gaps between windows (during the snapshots and `date` stamps) are excluded from it.

### Unattributed does not establish another host source

Accepted in part. The JSON value stays `unattributed`. The printed line no longer claims the source is the host as a fact: it says the excess is not accounted for by the dashboard probes, that the source is likely elsewhere on the host, and that short-lived threads and non-Node grandchildren are invisible to the probes. The issue's AC4 asks the output to say whether the excess came from the dashboard tree or elsewhere, so the line keeps naming the likely side while stating the probes' blind spots.

### Unresolved after two critic rounds

- A single burst can flip the verdict
- Attribution double counts live children
