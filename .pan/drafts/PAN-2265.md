# PAN-2265 — Fix GitHub GraphQL quota exhaustion: route remaining pollers off `gh` GraphQL

**Issue:** [PAN-2265](https://github.com/eltmon/overdeck/issues/2265)
**Planning model:** claude-opus-4-8 (`--auto`)

## Glossary

- **`gh` GraphQL calls** — the `gh` CLI's high-level subcommands (`gh pr view/list`,
  `gh issue view/list`) execute against GitHub's **GraphQL** API, which has its own
  5000/hr primary budget *separate* from REST. This budget is what exhausted.
- **App REST path** — reads via the provisioned GitHub App's **installation token**
  hitting GitHub's **REST** endpoints (`GET /repos/{o}/{r}/pulls/{n}`, `/issues/{n}`,
  `/pulls?head=…`). Separate quota, no GraphQL. Gated by `isGitHubAppConfigured()`.
- **`review_status`** — the per-issue store (SQLite, mirrored to git) that webhooks
  write merge/CI/blocker/review state into. Read door `getReviewStatusSync`
  (`src/lib/review-status.ts:714`), write door `setReviewStatusSync` (:221).
- **Canonical template** — `refreshMergeStateFromGitHub`
  (`src/lib/webhook-handlers.ts:206-257`): already branches on
  `isGitHubAppConfigured()` → App REST, else `gh` GraphQL fallback. Every bead below
  replicates this exact shape. **Landed in this branch as commit `a5d4148d28`.**

## Problem

GraphQL quota on the personal `eltmon/overdeck` token (user 678719) is exhausted:
hundreds of `GraphQL: API rate limit already exceeded` entries in `dashboard.log`.
The GitHub App + smee webhook backend has now been **provisioned** (App id `4205044`,
webhooks verified flowing), so `isGitHubAppConfigured()` returns **true** and the App
REST path is available. But several automated pollers still call `gh` GraphQL
**unconditionally** — they do not branch on App config — so they keep burning the
GraphQL budget every tick. This issue routes those remaining pollers off GraphQL.

## App REST helpers (Bead F — the foundation)

Add to `src/lib/github-app.ts`, mirroring the existing `getPullRequestStatePromise`
(:398) / `getPullRequestState` Effect wrapper (:691) using the internal `githubApi<T>()`
helper (:257). Export both a `…Promise` and an Effect-wrapped form:

- `listPullRequestsForHeadPromise(owner, repo, branch, state: 'open'|'closed'|'all')`
  → `Array<{ number, state, merged, mergedAt }>` via `GET /repos/{o}/{r}/pulls?head={owner}:{branch}&state={state}` (REST).
- `getIssueStatePromise(owner, repo, number)` → `{ state: 'open'|'closed' }` via
  `GET /repos/{o}/{r}/issues/{number}` (REST).
- `listOpenIssuesWithLabelsPromise(owner, repo)` → `Array<{ number, labels: string[] }>`
  via paginated `GET /repos/{o}/{r}/issues?state=open&per_page=100` (REST; filter out PRs).

Unit tests cover the returned shape for each helper (mock `githubApi`).

## Consumer pattern (Beads 1, 4b, 4c, 5a, 5b, 6a)

Each replicates the canonical template exactly:

```ts
import { isGitHubAppConfigured, listPullRequestsForHead } from '…/github-app.js';
// …
if (isGitHubAppConfigured()) {
  const prs = await Effect.runPromise(listPullRequestsForHead(owner, repo, branch, 'open'));
  return prs.length > 0;                 // App REST — installation token, no GraphQL
}
// existing gh fallback UNCHANGED (only runs when the App is not configured)
```

Bead 1 (flywheel) is the exception: its fallback is `gh api` REST pagination, **not**
`gh issue list` GraphQL — the GraphQL path is removed entirely so it never burns the
GraphQL budget regardless of App state. Preserve its degrade-to-empty `try/catch`
(never throws in a sandbox without creds).

## Display tabs (Bead 6b — webhook-aware cache, not a blind timer)

`/api/issues/:id/pr` and `/api/issues/:id/discussions` currently refetch heavy
`gh pr view --json files,statusCheckRollup,body,…` every 30 s per open tab. Make the
endpoints serve a per-issue cache and refetch from GitHub **only** when a relevant
webhook (`pull_request`, `pull_request_review`, `issue_comment`) has bumped that
issue's cache generation. The webhook handlers (`handlePullRequest` etc.) bump the
generation; the endpoint compares and serves the cache otherwise. Server-side only —
the frontend and its `refetchInterval` are untouched (the cache collapses the actual
GitHub fetch frequency from every-30s to only-on-change).

## GraphQL cool-down gate (Bead 7 — defense-in-depth)

New `src/lib/github-graphql-cooldown.ts`: `noteGraphQLRateLimit(err)` records a
timestamp when a `gh` error message matches `rate limit already exceeded` /
`API rate limit`; `isInGraphQLCooldown()` returns true for ~60 s after. Wire it into
`refreshMergeStateFromGitHub`'s `gh` fallback (`webhook-handlers.ts:239`) — the path
the operator observed failing repeatedly during exhaustion — so a depleted budget
isn't hammered with doomed retries. **Timing test MUST use `vi.useFakeTimers()` +
`vi.advanceTimersByTimeAsync()`** (repo rule — never real `setTimeout` waits).

## `--auto` decisions

1. **App-REST helpers live in one foundation bead (F).** `listPullRequestsForHead`,
   `getIssueState`, `listOpenIssuesWithLabels` are shared by 6 consumers; centralizing
   them mirrors the existing `getPullRequestStatePromise` and keeps consumer beads to a
   one-branch diff. F is `requiresInspection: true` — a wrong return shape would infect
   all consumers.
2. **Flywheel fallback is `gh api` REST, not `gh issue list` GraphQL.** The list op has
   a trivial REST equivalent; removing the GraphQL path entirely guarantees FR-1 even
   when the App is absent (the sandbox constraint that originally justified `gh`).
3. **Full App-REST reconstruction of the heavy PR display field set is a NonGoal
   (follow-up).** It only burns quota while a human has a Command Deck tab open
   (bounded), the webhook-aware cache (FR-7) already collapses its frequency, and
   reconstructing `files`/`statusCheckRollup`/`body`/`reviewDecision` across multiple
   REST endpoints is expert-risk UI work that deserves a dedicated issue with UAT.
4. **Cool-down wired into the one observed-failing fallback**, not every call site —
   the module is exported so remaining fallbacks can adopt it later; over-wiring it now
   would bloat the bead past independent reviewability.
