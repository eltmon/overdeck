# PAN-2672 — Post-`/clear` sibling conversations render the wrong transcript

**Issue:** https://github.com/eltmon/overdeck/issues/2672
**Type:** bug
**Author model:** claude-opus-4-8
**Status:** draft PRD

---

## Glossary

- **`/clear`** — a Claude Code (terminal harness) built-in command. It stops writing the
  current session JSONL and starts a **new** JSONL with a fresh session-id under the same
  `~/.claude/projects/<encoded-cwd>/` directory. The tmux pane keeps running the same process.
  It is **not** a compaction and **not** an Overdeck command.
- **Conversation row** — a row in the `conversations` table (`src/lib/database/schema.ts:466`).
  Identified by `name`; carries `tmux_session`, `cwd`, `claude_session_id`, `status`,
  `cleared_to_conv_id`.
- **`claude_session_id`** — the Claude Code session UUID recorded on the conversation row
  (`schema.ts:477`). Set at spawn (`src/lib/agents/spawn.ts:286`), updated on compaction
  (`src/lib/overdeck/conversation-message.ts:412` via `setConversationClaudeSessionId`), and
  set on a post-`/clear` sibling by the orphan detector
  (`src/dashboard/server/services/conversation-lifecycle.ts:403`).
- **Launcher pin** — the `--session-id '<uuid>'` written into
  `~/.overdeck/conversations/<tmux>/launcher.sh` at spawn. Read by
  `readLauncherPinnedSessionId(tmuxSession)`
  (`src/dashboard/server/routes/jsonl-resolver.ts`). It is **keyed by tmux session, written
  once at spawn, and never rewritten by `/clear`.**
- **Post-`/clear` sibling** — a new conversation row the orphan detector creates after a
  `/clear`, sharing the parent's `tmux_session` and pointing at the new JSONL. The parent is
  linked via `parent.cleared_to_conv_id = sibling.id` (PAN-1458).
- **Transcript resolver** — `resolveSessionFile(conv)` in
  `src/lib/overdeck/conversation-reads.ts:140`, which decides **which JSONL** a conversation
  row renders in the conversation/chat panel.

---

## Problem

After a `/clear` in a terminal-mode conversation, the parent conversation and its
post-`/clear` sibling **both render the same original (pre-clear) transcript** in the
conversation view. The sibling never shows its own post-clear history.

Reproduced live on conversation `20260714-4351` (parent) / `20260714-4351-post-clear-b20e39ae`
(sibling), cwd `/home/eltmon/Projects/myn`, tmux `conv-20260714-4351`:

- `~/.overdeck/conversations/conv-20260714-4351/launcher.sh` pins
  `--session-id '1086ec05-e7aa-45bd-bfc7-67135a6906b9'` (pre-clear session, JSONL mtime 16:55).
- The live session is `b20e39ae-…` (JSONL mtime 17:05) — the sibling's own session.
- The pin is frozen at `1086ec05`; `/clear` never rewrote it.

### Root cause (build-independent, present at current HEAD)

`resolveSessionFile` resolves the JSONL from the **per-tmux launcher pin first**, and only
falls back to the row's own recorded id (`src/lib/overdeck/conversation-reads.ts:157-158`):

```ts
const pinned = await readLauncherPinnedSessionId(conv.tmuxSession);
const sessionId = pinned ?? conv.claudeSessionId;
```

Because the parent and the sibling **share one `tmux_session`**, they read the **same**
launcher and get the **same** `pinned` id. And because `/clear` never rewrites the launcher,
that pinned id is frozen at the parent's original session. So every conversation row on that
tmux resolves to the same pre-clear JSONL, regardless of its own correct `claude_session_id`.

Pin-first was chosen (see the comment at `conversation-reads.ts:154-156`) to handle
**compaction lag**: Claude Code compacts in place to a new session id, and the launcher pin
reflects that live id before Overdeck's watcher updates `claude_session_id`. `/clear` is the
**inverse** case — the pin is stale and the recorded id is fresh — so pin-first is exactly
wrong there.

### Not the bug (documented so it isn't chased)

- **Terminal view showing the same pane.** Both rows share one tmux pane by design; there is
  exactly one live terminal, so both rows' terminal view can only show that single pane. Not
  fixable at the pane level and not this bug.
- **The `overdeck.db` vs `panopticon.db` / null `claude_session_id` divergence** observed live
  was a **stale-build artifact**: the running dashboard (pid at investigation time, built
  16:39) predates the `claude_session_id` migration (PAN-451, `schema.ts:1204`) and still
  opened the legacy `overdeck.db`. On a current build the id persists. It is **not** a root
  cause and is out of scope here — do not entangle this fix with the PAN-1979 DB migration.

---

## Requirements

- **FR-1** — When rendering a conversation whose launcher pin points at a session that belongs
  to a *different* conversation row, the transcript resolver MUST use the row's own recorded
  `claude_session_id`, not the shared pin.
- **FR-2** — A post-`/clear` parent conversation MUST render its pre-clear transcript, and its
  sibling MUST render its post-clear transcript (distinct content), on a current build.
- **FR-3** — The fix MUST NOT change transcript resolution for the normal single-conversation
  case, including compaction (where the pin is legitimately fresher than the recorded id).
- **NFR-1** — No new database query per transcript render beyond a single indexed lookup by
  `claude_session_id` (`getConversationByClaudeSessionId`, already used elsewhere), and only
  when the pin and recorded id differ.

## Work Items

### WI-1 — Prefer the row's own `claude_session_id` when the launcher pin belongs to another conversation
*(FR-1, FR-2, FR-3, NFR-1)*

**Files:** `src/lib/overdeck/conversation-reads.ts` (the claude-code branch of
`resolveSessionFile`, lines 154-158). `getConversationByClaudeSessionId` is **already imported**
at `conversation-reads.ts:26` — no new import needed.

**Why:** the pin is per-tmux and shared across post-`/clear` siblings, and frozen at spawn. If
the pinned session id is owned by a *different* conversation row, the pin does not describe
*this* row, so the row's own recorded id is authoritative. In the compaction case the pinned
id is *this* row's new (not-yet-recorded) session and is owned by no other row, so pin-first is
preserved.

**Before** (`conversation-reads.ts:154-158`):

```ts
// claude-code: prefer the launcher's pinned live session id, then the recorded
// canonical id. Do not guess from JSONL mtime; compaction can make old files
// newer than the terminal's current transcript.
const pinned = await readLauncherPinnedSessionId(conv.tmuxSession);
const sessionId = pinned ?? conv.claudeSessionId;
```

**After:**

```ts
// claude-code: prefer the launcher's pinned live session id, then the recorded
// canonical id. Do not guess from JSONL mtime; compaction can make old files
// newer than the terminal's current transcript.
const pinned = await readLauncherPinnedSessionId(conv.tmuxSession);
let sessionId = pinned ?? conv.claudeSessionId;
// PAN-2672: the launcher pin is keyed by tmux session and is written once at
// spawn — `/clear` starts a new Claude Code session but never rewrites it, and
// post-`/clear` siblings share the parent's tmux session. So a shared/stale pin
// can point at a session that belongs to a *different* conversation row. When it
// does, it does not describe THIS row; fall back to this row's own recorded id.
// (The compaction case is preserved: there the pinned id is this row's own new
// session and is owned by no other row, so pin-first still wins.)
if (pinned && conv.claudeSessionId && pinned !== conv.claudeSessionId) {
  const pinnedOwner = getConversationByClaudeSessionId(pinned);
  if (pinnedOwner && pinnedOwner.name !== conv.name) {
    sessionId = conv.claudeSessionId;
  }
}
```

**Decision rules (made in this doc):**
- Diverge from the pin **only** when all of: a pin exists, this row has a recorded
  `claude_session_id`, the two differ, and `getConversationByClaudeSessionId(pinned)` returns a
  row whose `name !== conv.name`. Any other combination keeps the existing `pinned ??
  conv.claudeSessionId` behavior.
- If `getConversationByClaudeSessionId(pinned)` returns `null` (pin points at a session with no
  row yet — a live session before its row is written), keep pin-first. This is deliberate and
  preserves the live-session banner path already relied on downstream
  (`conversation-reads.ts:166-170`).

**Steps:**
1. Change `const sessionId` → `let sessionId` at line 158.
2. Insert the PAN-2672 divergence block immediately after line 158, before the existing
   `if (sessionId) {` block.
3. No import changes.

**Proves it:** WI-4 unit tests.

## Acceptance Criteria

- **AC-1 (WI-1, FR-1/FR-3)** — `resolveSessionFile` returns the row's own `claude_session_id`
  JSONL when the pin differs and is owned by another conversation row; returns the pinned JSONL
  in every other case (equal pin, unowned pin, no recorded id). Proven by WI-4 cases 1-5.
- **AC-2 (WI-2)** — Forking from a post-`/clear` sibling uses the sibling's transcript, not the
  parent's (shared resolver confirmed, or duplicate patched). Proven by a fork-path test.
- **AC-3 (WI-3, FR-2)** — On a current build, after a `/clear` and one lifecycle tick, the
  parent row is `ended` and the sibling is the sole active row on the tmux session (verified;
  guarded + regression-tested only if reproduced active).
- **AC-4 (end-to-end, FR-2)** — Manual: in a terminal conversation, run `/clear`, then open both
  the parent and the sibling in the dashboard. The parent shows the pre-clear transcript; the
  sibling shows the post-clear transcript. They differ.
- **AC-5** — `npm run typecheck`, lint, and the conversation-reads test file pass with no new
  failures.

## Notes for the implementer

- The entire correctness of WI-1 rests on `claude_session_id` being populated on both rows. It
  is: spawn sets it (`spawn.ts:286`), the migration backfills legacy rows (`schema.ts:1204-1218`),
  and the orphan detector sets it on the sibling (`conversation-lifecycle.ts:403`). If you are
  testing against a dashboard started before the PAN-451 migration, restart onto a current build
  first (`npm run build` then restart) or you will see the stale-build null-id artifact and
  misread the fix as ineffective.
- Do **not** widen this into the PAN-1979 `overdeck.db` → `panopticon.db` migration. That
  divergence was a stale-build observation, not a cause of this bug.
