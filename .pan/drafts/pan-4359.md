# PAN-4359 — Detect Claude Code versions too old for a model, and help users upgrade

**Issue:** [PAN-4359](https://github.com/eltmon/overdeck/issues/4359)
**Sibling (split out):** [PAN-4360](https://github.com/eltmon/overdeck/issues/4360) — `pan claude upgrade` and the upgrade offer in `pan install` / `pan sync`.
**Status:** planned (auto mode, 2026-09-28)

## Glossary

- **Claude Code** — Anthropic's `claude` CLI. It is the default Overdeck harness (`claude-code`).
- **Launch binary** — the absolute `claude` path that `resolveHarnessBinary('claude-code')` returns (`src/lib/harness-binary.ts`). Every launcher prepends its directory to `PATH` (`harnessPathExport`), so this is the binary new agents and conversations run.
- **Shadow binary** — any other executable named `claude` on the server `PATH` that is not the launch binary. An operator who types `claude` in a shell may get the shadow, not the launch binary.
- **Minimum version** — `minClaudeCodeVersion` on a model's capability row: the oldest Claude Code that knows the model. Example: `claude-sonnet-5-5` needs `2.1.284`.
- **Install method** — how the launch binary was installed, derived from its real path: `npm` (npm global prefix), `native` (Anthropic's native installer, `claude update`), `homebrew` (Homebrew cask), or `unknown`.
- **Upgrade plan** — the command that upgrades Claude Code for one install method, plus whether Overdeck may run it itself (`runnable`).
- **Configured models** — every model id the operator's `~/.overdeck/config.yaml` (with defaults applied) can launch: role models (including percentage distributions and sub-roles), workhorse slots, tiered-execution tier models, and the default conversation model.
- **Launch gate** — the check inside `prepareHarnessLaunch` that refuses a `claude-code` launch whose model needs a newer Claude Code than the launch binary.
- **System notices row** — the banner stack in `src/dashboard/frontend/src/App/AppChrome.tsx` (`data-component="system-notices-row"`).

## Problem

New models can need a newer Claude Code than the user has. Claude Sonnet 5.5 needs Claude Code 2.1.284, and v0.63.0 made it the Sonnet-tier default. Claude Fable 5.1 needs 2.1.255. Today the requirement lives only in free-text `notes` (`src/lib/model-capability-additions.ts`, lines 32 and 58) and the changelog. An operator on an older Claude Code upgrades Overdeck and Sonnet-tier agents fail at launch with no reason and no fix. Nothing in `src/` compares Claude Code versions.

This machine shows the shadow case too: `which -a claude` lists `~/.config/nvm/versions/node/v22.22.0/bin/claude` (2.1.284) and `/usr/local/bin/claude` → `/usr/local/lib/node_modules/@anthropic-ai/claude-code/cli.js` (2.0.19, root-owned).

## Decisions

- **D1 — Minimum lives on the capability row.** Add `minClaudeCodeVersion?: string` to `ModelCapability`. Set it for `claude-fable-5-1` (`2.1.255`) and `claude-sonnet-5-5` (`2.1.284`), the two models with a documented requirement. Leave it unset elsewhere; unset means "no known minimum".
- **D2 — One gate, inside `prepareHarnessLaunch`.** `prepareHarnessLaunch(harness, options)` gains `options.model`. When `harness === 'claude-code'` and the model (after `resolveModelId`) has a minimum, it reads the launch binary's version and throws `ClaudeCodeTooOldError` if it is older. No fallback to another model or harness.
- **D3 — Unreadable version allows the launch.** If `claude --version` fails, times out, or prints no `X.Y.Z`, the gate logs one `console.warn` per binary (`[claude-code] could not read the version of <path>; skipping the minimum-version check for <model>`) and lets the launch proceed. Blocking on a parse failure would brick every launch on an unexpected banner. `pan doctor` reports the unknown version as `warn`.
- **D4 — No model, no gate.** When a launch has no model (API conversation create without `model`), Claude Code picks its own default and Overdeck cannot know it, so the gate is skipped.
- **D5 — Overdeck runs the upgrade only when the target is user-writable.** Runnable: `native` (`claude update`), `npm` whose `<prefix>/lib/node_modules` is writable by the server user, `homebrew` when `brew` resolves. Not runnable: root-owned npm prefix (show `sudo npm install -g --prefix <prefix> @anthropic-ai/claude-code@latest`), `unknown` (show `claude update`), and any `win32` host. Not-runnable plans render a copyable command, never a button.
- **D6 — npm upgrades target the detected prefix.** Command: `<npm> install -g --prefix <prefix> @anthropic-ai/claude-code@latest`, where `<npm>` is `<prefix>/bin/npm` when that file is executable, else `npm`. This upgrades the launch binary even when the server's own `npm` belongs to another Node version.
- **D7 — Version reads are cached by real path and mtime.** Cache key `${realpath}:${mtimeMs}`, value `Promise<string | null>`, TTL 60 s, `{ refresh: true }` bypasses. An upgrade changes the mtime (npm) or the real path (native `versions/<v>` symlink), so the next read misses the cache without waiting for the TTL.
- **D8 — The banner is derived from configured models.** `GET /api/claude-code/status` evaluates every configured model that has a minimum against the launch binary. The banner shows while any is unmet. It does not consult harness routing: an Anthropic model routed to another harness still counts (rare, and a false banner is cheaper than a failed launch).
- **D9 — Upgrade runs in a terminal session and keeps its output.** `POST /api/claude-code/upgrade` opens session `claude-code-upgrade` running the plan's command, then prints the re-read version, a note that running sessions keep their old binary, and waits for Enter so the output stays visible. The request body is ignored; the command comes only from the server-side plan (no client-supplied command text).
- **D10 — Homebrew cask name is an implementation checkpoint.** Expected command `brew upgrade --cask claude-code`. Before coding, confirm the cask name from Claude Code's setup docs (`https://code.claude.com/docs/en/setup`) or `brew info --cask claude-code` if `brew` exists. **Fallback:** if it cannot be confirmed, classify Homebrew paths as `homebrew` but with `runnable: false` and display `brew upgrade claude-code`.
- **D11 — CLI upgrade command is split out.** `pan claude upgrade` and the `pan install`/`pan sync` offer move to [PAN-4360](https://github.com/eltmon/overdeck/issues/4360). No PAN-4359 acceptance criterion names them; `pan doctor` and the launch refusal give terminal users the exact command.
- **D12 — Reuse `compareSemver`/`extractSemver`** from `src/lib/herdr-setup/binary.ts`.
- **D13 — Overdeck-upgrade-time warning is the dashboard banner.** The issue asks that the first `pan up` / dashboard load after upgrading Overdeck raise the warning. The banner queries `/api/claude-code/status` on first dashboard load, which covers it; `pan doctor` covers terminal users. `pan up` prints no extra line.

## Requirements

### Functional

- **FR-1** `ModelCapability` has optional `minClaudeCodeVersion`; Fable 5.1 = `2.1.255`, Sonnet 5.5 = `2.1.284`.
- **FR-2** A module reads the launch binary's Claude Code version asynchronously, cached per D7.
- **FR-3** A module derives the install method and upgrade plan from the binary's real path per D5, D6, D10.
- **FR-4** A module lists every `claude` executable on the server `PATH` (deduplicated by real path) so shadows can be reported.
- **FR-5** A module lists configured models with their config sources and evaluates each model's minimum against an installed version.
- **FR-6** `prepareHarnessLaunch` refuses a `claude-code` launch whose model minimum exceeds the launch binary's version, with a message naming the model, both versions, the binary path, the upgrade command, and "No terminal session was created."
- **FR-7** All nine Claude-Code-capable `prepareHarnessLaunch` call sites pass their model.
- **FR-8** `GET /api/claude-code/status` returns version, binary path, install method, upgrade plan, per-model requirements and shadows; `?refresh=1` bypasses the cache.
- **FR-9** `POST /api/claude-code/upgrade` opens the upgrade terminal session for runnable plans; 409 when one is already running; 400 with the copyable command when not runnable.
- **FR-10** The dashboard shows a banner while any configured model's minimum is unmet, with an **Upgrade Claude Code** button (runnable) or a copyable command (not runnable), re-checks after the upgrade, and clears when satisfied.
- **FR-11** `pan doctor` reports the installed version, install method, launch binary path, each configured model's minimum, and every shadow binary with its version.
- **FR-12** Docs describe version requirements, the upgrade paths, the release-time rule to set `minClaudeCodeVersion`, and the changelog note.

### Non-functional

- **NFR-1** No `execSync`/`spawnSync` in any new or touched server-reachable code; process calls use `execFile` promisified with a 10 s timeout.
- **NFR-2** A launch pays at most one `claude --version` per binary per 60 s.
- **NFR-3** The upgrade route never executes client-supplied text.
- **NFR-4** No new import cycle (`npm run lint:circular` passes).

  options?: HarnessLaunchOptions,

## Repo rules that apply

- No `execSync` in dashboard-server-reachable code; use promisified `execFile`/`spawn` (rule: no-execsync-server).
- Tests that exercise the 60 s cache TTL or the banner's 5 s poll use `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()`, never real waits (rule: fake-timers-for-retry-tests).
- Never hardcode a model fallback; the gate refuses, it never substitutes (rule: no-hardcoded-model-fallbacks).
- New HTTP routes need no-loss-matrix rows or CI fails.
- A file grown past its `origin/main` line count needs a `scripts/file-size-allowlist.txt` row `<lines> <path> # PAN-4359` in the same commit.
- Quality gates before `pan done`: `npm run typecheck`, `npm run lint`, `npx vitest run <touched test files>`; never the full `npm test` on the host.
- Dashboard UI follows `/pan-style-guide` (warning tokens, no pills, no decorative color).
- `lint:file-size` compares against `origin/main`: keep each launch-site edit on the existing single line (`prepareHarnessLaunch(x, { model: y })`) so `spawn.ts`, `messaging.ts`, `conversation-runtime.ts` and the others do not grow.

## Non-goals

- `pan claude upgrade` and the upgrade offer in `pan install` / `pan sync` (→ [PAN-4360](https://github.com/eltmon/overdeck/issues/4360)).
- Upgrading shadow binaries; doctor only reports them.
- Running `sudo` or any root-owned install from Overdeck.
- Windows-host upgrade execution (copyable command only).
- A `pan doctor --fix` flag.
- Checking launches that have no model (D4).
- Restarting running agents or conversations after an upgrade.
- Auto-upgrading Claude Code without an operator click.
- Maximum-version checks or pinning Claude Code.
