# PAN-5398: `pan open` opens a phantom deck when a project's key differs from its name

**Issue:** [PAN-5398](https://github.com/eltmon/overdeck/issues/5398) · **Parent work:** PAN-5349 (`pan open` / Open in Overdeck) · **Planning mode:** `--auto`

## Glossary

- **Registered key** — the key of a project in `~/.overdeck/projects.yaml` (`projects.<key>`), e.g. `panopticon-cli`. Explorer root ids use it: `project:panopticon-cli`.
- **Display name** — `projects.<key>.name` in `projects.yaml`, e.g. `overdeck`. May be absent; then the key is shown.
- **Deck** — the per-project tabbed pane set on the Command Deck. The dashboard keys every deck by the project's **display name** (`name ?? key`): the project switcher calls `pick(project.name)`, `selectedProjectKey` holds that name, `localStorage['pan-panes:<name>']` holds the panes, and the URL is `/command-deck/<name>`.
- **Deck key** — the string a deck is keyed by: `name ?? key`. New field `deckKey` on `UiOpenResolution` carries it.
- **Phantom deck** — a deck created under a string that no project switcher row selects (here, the registered key `panopticon-cli`). It shows "No issues for this project", a `–` mark, and none of the real deck's tabs.
- **`UiOpenResolution`** — the server's answer for a path (`packages/contracts/src/ui-commands.ts`): which project, explorer root, relative path and kind to show. Carried by the `open-path` UI command and returned by `POST /api/ui/open`.
- **Explorer root id** — `project:<registeredKey>`, `issue:<ID>` or `workspace:<scratchId>`. Always keyed by the registered key; this does not change.

## Problem

`pan open features/mission-control.mdx --line 84`, run in `~/Projects/overdeck`, opened the file in a deck labelled `panopticon-cli` instead of the `overdeck` deck the operator had open. The CLI printed `Opened features/mission-control.mdx in panopticon-cli`. 5 of 21 registered projects have a key that differs from their name: `panopticon-cli`/overdeck, `primalroll`/PrimalRoll, `orbacade`/Orbacade, `dfai`/DFAI, `t2o-osdp`/T2O-OSDP.

### Cause (verified)

- Decks are keyed by display name. `src/dashboard/frontend/src/components/frame/ProjectSwitcher.tsx` line 101: `onClick={() => pick(project.name)}`. `src/dashboard/frontend/src/components/CommandDeck/projectsData.ts` lines 258–264 build each project's `name` as `proj.name ?? proj.key`. `src/dashboard/frontend/src/App.tsx` line 588 (`handleSelectProject`) writes `/command-deck/${encodeURIComponent(projectName)}`.
- The resolution carries only the registered key. `src/dashboard/server/routes/ui-open.ts` lines 112–119 set `projectKey: root.projectKey`, and every `ExplorerRoot.projectKey` from `src/dashboard/server/services/explorer/roots.ts` (`resolveProjectRoot`, `resolveIssueRoot`, `resolveWorkspaceRoot`) is the registered key.
- `src/dashboard/frontend/src/lib/uiCommands/openPathInDeck.ts` line 14 destructures `const { projectKey: deckKey, … } = resolution` and passes that key to `ensureHome`, `openInDeck`, `openCodePane`, `openDock`, `setRootOverride` and `selectActivePaneId`.
- `src/dashboard/frontend/src/components/open/OpenPathHost.tsx` line 72 replaces the URL with `/command-deck/${encodeURIComponent(resolution.projectKey)}`. So the `/open` link (and `pan open --new-tab`, and `pan open` with no listening tab) also lands on the phantom deck.
- `src/cli/commands/open.ts` line 193 prints `Opened ${relPath} in ${String(body['projectKey'])}`, which names the registered key.

## Decisions (made here)

1. **D-1: Server computes `deckKey`.** `UiOpenResolution` gains a required `deckKey: Schema.String`. The server sets it to `projectDeckKey(registeredProject)` = `name ?? key` for the registered project whose key equals `root.projectKey`. If no registered project has that key, `deckKey = root.projectKey`. `projectKey` and `rootId` keep the registered key.
2. **D-2: One rule, one function.** A pure `projectDeckKey(project: { key: string; name?: string | null }): string` (returns `project.name ?? project.key`) lives in `packages/contracts/src/ui-commands.ts`. The server uses it, and `fetchProjects` in `projectsData.ts` uses it instead of its inline `proj.name ?? proj.key`, so the switcher and the resolver can never disagree. The rule stays `??` (not `||`), exactly matching today's switcher behaviour.
3. **D-3: Look up by `root.projectKey`, not `hit.projectKey`.** `resolvePathRoot` can return `projectKey: ''` for a scratch workspace outside every project; `root.projectKey` (from `resolveExplorerRoot`) is always the real registered key.
4. **D-4: Name lookup uses the unfiltered project list.** `realCandidates` drops projects whose path does not resolve; the name lookup reads the raw `deps.listProjects()` rows so a project with a broken path still gets its display name.
5. **D-5: One success sentence, shared.** A pure `uiOpenSummary(r: Pick<UiOpenResolution, 'deckKey' | 'rootId' | 'relPath'>): string` in `packages/contracts/src/ui-commands.ts` builds the sentence. The CLI success line and the dashboard toast both use it, so they print identical text:
   - `relPath` non-empty → `Opened <relPath> in <deckKey>` (e.g. `Opened features/mission-control.mdx in overdeck`);
   - `relPath === ''` and `rootId` starts with `issue:` → `Opened the <ID> workspace in <deckKey>` (e.g. `Opened the PAN-5295 workspace in overdeck`), where `<ID>` is `rootId` after `issue:`;
   - otherwise → `Opened root folder in <deckKey>`.
   The issue case is derived from the resolution, not from the CLI's parsed target, so `pan open PAN-5295` and `pan open ~/Projects/overdeck/workspaces/feature-pan-5295` print the same thing, and the toast (which never sees the CLI target) agrees.
6. **D-6: The toast drops "from pan open".** The toast text becomes exactly `uiOpenSummary(resolution)`. The `/open` link uses the same toast, so "from pan open" was already wrong there.
7. **D-7: CLI tolerates an older server.** The CLI reads `deckKey` and falls back to `projectKey` when the response has no string `deckKey` (a newer CLI talking to an older dashboard). The frontend needs no fallback: the server serves its own bundle.
8. **D-8: CLI imports the helper lazily.** `src/cli/commands/open.ts` already loads `@overdeck/contracts` with `await import('@overdeck/contracts')` (`loadEditors`, line 24) to keep the CLI's module graph light. `openInDashboard` does the same for `uiOpenSummary`: `const { uiOpenSummary } = await import('@overdeck/contracts');`. Do not add a static value import from `@overdeck/contracts` to `open.ts`.

## Requirements

- **FR-1** `POST /api/ui/open` returns, and the published `open-path` command carries, `deckKey` = the registered project's `name`, or its `key` when it has no name. `projectKey` and `rootId` are unchanged (registered key).
- **FR-2** `openPathInDeck` passes `resolution.deckKey` as the deck argument to every deck call: `ensureHome`, `openInDeck({ projectKey })`, `openCodePane`, `openDock`, `setRootOverride`, `selectActivePaneId`, and the `useActiveDock` deck comparison. `rootId` stays as resolved.
- **FR-3** The `/open` link host replaces the URL with `/command-deck/<encodeURIComponent(deckKey)>`.
- **FR-4** The CLI success line is `uiOpenSummary(...)`: it names the project by display name and an issue workspace by its issue id.
- **FR-5** The dashboard toast after an open is the same sentence as the CLI line.
- **FR-6** The project switcher's deck key and the resolver's `deckKey` come from the same `projectDeckKey` function.
- **FR-7** Docs describe `deckKey`, the `/command-deck/<deckKey>` link redirect, and the success sentence; a changelog entry records the fix.
- **NFR-1** No new HTTP route, RPC method or stored state. The change is additive to the `UiOpenResolution` schema.
- **NFR-2** No server-reachable sync I/O is added (`listProjectsAsync` stays the source).
- **NFR-3** No file grows past its `origin/main` line count plus this change's own lines in a way that trips `scripts/lint-file-size.sh`; none of the touched files is near a cap.
