# PAN-4860: `pan project add` proposes an issue prefix with digits, which `parseIssueId` rejects

**Issue:** https://github.com/eltmon/overdeck/issues/4860
**Found by:** Overdeck Anywhere release acceptance run (#4774, AC-4).
**Planned at:** `feature/pan-4860` @ `743046794be` (same code as `main`).

## Glossary

- **Issue prefix** — the letters before the dash in a standard issue ID (`PAN` in `PAN-4860`). Stored as `issue_prefix` in `~/.overdeck/projects.yaml`; issue→project resolution matches on it.
- **Create resolver** — `resolveProjectCreateIntent()` in `src/lib/projects/create.ts`. The read-only half of project creation; it computes a `ProjectCreateIntent` with `proposedIssuePrefix` and blocking `findings`. Both the CLI (`pan project add|clone|new`) and the dashboard Add-project dialog call it.
- **Finding** — a blocking `{ field, code, message, detail }` record on the intent. Code `issue-prefix-invalid` blocks creation; the dashboard renders `message` under the Issue prefix field.
- **`parseIssueId`** — `src/lib/issue-id.ts`. Standard format regex `^([A-Za-z]+)-(\d+)$` (letters-only prefix), then Rally (`F|US|DE|TA|TC` + digits), then an optional per-project `issue_pattern` regex.
- **`issue_pattern`** — per-project custom regex in `projects.yaml`, already supported by `parseIssueId`'s `custom` branch. This is the existing escape hatch for any project whose tracker IDs do not fit `LETTERS-NUMBER`.
- **Round-trip** — a proposed prefix `P` round-trips when `parseIssueId(`${P}-1`)` returns `{ prefix: P, format: 'standard' }`.

## Problem

`pan project add /home/eltmon/Projects/pan4774-anywhere-smoke --name pan4774-anywhere-smoke` saved `issue_prefix: PAN4774ANY`. No issue ID with that prefix parses, because `parseIssueId` accepts letters only. `resolveProjectFromIssue` returns null, and `pan worker run --issue PAN4774ANY-1 --machine <fly>` reported "PAN4774ANY-1's project has no github_repo or gitlab_repo here" although the project has a `github_repo`.

Cause, verified at `src/lib/projects/create.ts` lines 810–838 (grep anchor: `// 5. Issue prefix.`):

```ts
const proposed = (input.issuePrefix ?? key.toUpperCase().replace(/-/g, '').slice(0, 10)).trim();
if (!/^[A-Z][A-Z0-9]{0,9}$/.test(proposed)) {
  findings.push({
    field: 'issuePrefix',
    code: 'issue-prefix-invalid',
    message:
      'Issue prefix must start with a letter and contain only uppercase letters and digits (max 10 chars).',
    detail: proposed,
  });
}
```

The proposal keeps digits from the key, and the validation allows digits. `parseIssueId` (`src/lib/issue-id.ts` line 42, anchor: `issueId.match(/^([A-Za-z]+)-(\d+)$/)`) rejects them. Reproduction: a directory named `abc123-x` dry-runs to `"proposedIssuePrefix": "ABC123X"`, and `parseIssueId('ABC123X-1')` returns null.

## Decision: make creation letters-only; do not widen the parser

The issue offers two fixes. This plan takes the first: the create resolver proposes and accepts letters only.

Reasons, all verified:

1. **The letters-only shape is load-bearing far beyond `parseIssueId`.** `grep -rnE "\[A-Za-z\]\+-|\[A-Z\]\+-|\[a-z\]\+-" src` finds 67 non-test sites hard-coding it: `src/lib/workspace/orphan-networks.ts:55` (compose project names), `src/lib/cloister/service-reactive.ts:24` (specialist session names), `src/lib/workspaces/rebuild.ts:37` (`feature-<id>` dirs), `src/lib/cloister/closed-issue-reaper.ts:25`, `src/lib/webhook-handlers.ts:106` (branch refs), `src/lib/resource-utils.ts:4` (`parseIssueIdFromText`), and more. Widening only the parser would leave a digit-prefixed project silently missed by every one of them (unreaped workspaces, orphaned docker networks, unrouted webhooks). Widening all 67 is a separate, much larger change.
2. **Projects that truly need digits already have a path:** `issue_pattern` (the `custom` branch of `parseIssueId`).
3. **No frontend change is needed.** The dashboard has no client-side copy of the rule: `grep -rn "A-Z0-9\]{0,9}" src` matches only `create.ts`. `ProjectCreateForm.tsx` renders the server's finding message via `<Findings findings={findingsFor('issuePrefix')} … />`.

## Requirements

- **FR-1** The proposed issue prefix contains only the uppercase letters of the project key, in order, truncated to 10 characters. Digits, dashes, and every other non-letter character are dropped.
- **FR-2** The resolver rejects any issue prefix (proposed or explicit via `--issue-prefix`, the dashboard Options field, or a `.pan/project.toml` Linear team) that does not match `^[A-Z]{1,10}$`, with finding code `issue-prefix-invalid`.
- **FR-3** The `issue-prefix-invalid` message states the letters-only rule and does not mention digits.
- **FR-4** Every prefix the resolver accepts round-trips through `parseIssueId` as a standard-format ID.
- **FR-5** When the key contains no letters (for example `2048`), the resolver emits `issue-prefix-invalid` with `detail: ''` and leaves `proposedIssuePrefix` null; the operator must supply a prefix.
- **FR-6** User docs and the `pan-new-project` skill state that issue prefixes are 1–10 uppercase letters, digits not allowed.
- **NFR-1** `parseIssueId`, `parseIssueIdFromText`, and the 67 shape regexes are unchanged.
- **NFR-2** `src/lib/projects/create.ts` does not grow in line count beyond `origin/main` (file-size ratchet; the change is a net ±1 line). `create.ts` is not in `scripts/file-size-allowlist.txt`.

## Non-goals

- Widening `parseIssueId`, `parseIssueIdFromText`, or any of the 67 `LETTERS-NUMBER` regexes to accept digits.
- Migrating or repairing existing `projects.yaml` entries with digit prefixes. One is live on the operator machine (`t2o-osdp` → `T2OOSDP`); it stays as is. The operator can rename it or add `issue_pattern`.
- A `pan doctor` check for existing invalid prefixes.
- Any frontend change in the Add-project dialog.
- Auto-uppercasing an explicit lowercase `--issue-prefix`.
