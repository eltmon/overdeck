## Glossary

- **Machine, environment id, label:** one Overdeck server and its UUID identity (`src/lib/environment-identity.ts`). The UI says "machine"; the code says "environment".
- **Link, linking machine, linked machine:** from PAN-4645. Links live in `${OVERDECK_HOME}/machine-links.json` (`src/lib/anywhere/link-store.ts`). The machine you sit at is the **viewer**; the machine that runs a piece of work is its **owner** (PAN-4650 vocabulary).
- **Machine credential:** a `kind: 'machine'` access token (`src/lib/access-tokens.ts`, `MACHINE_TOKEN_SCOPES`), valid only inside a secure channel whose proved key matches the record. Its record carries the peer's `environmentId` and `access` (`operator` | `agent-fenced`).
- **Actor stamp:** headers `x-overdeck-link-actor: operator | agent:<id>` and `x-overdeck-link-ceiling: <scopes>` added by the viewer to every forwarded request (`src/lib/anywhere/link-actor.ts`). The owner trusts them only inside a channel; a ceiling only narrows scopes.
- **Agent fence:** `linkActorFence` in `src/dashboard/server/link-fence.ts`, which today refuses every non-GET `/api/conversations*` write, `/ws/terminal` and `/ws/forward` from a machine credential whose actor is an agent.
- **Link-started:** a conversation or worker that an owner created because a linked machine asked through a work door. Its row records the asking machine's environment id (`started_by_environment_id`, new here).
- **Work door:** an owner-side route under `/api/machines/work/*` (new here) through which a linked machine starts a conversation, a worker, an issue agent or a project on this machine. Machine credential only.
- **Fleet route:** a viewer-side route under `/api/fleet/*` (new here) that serves this machine's browser, CLI and MCP by combining this machine with its linked machines. Fleet routes refuse any request that arrives through a channel (no chained hops), exactly like `refuseFleetRequest` in `src/dashboard/server/routes/machines-fleet.ts`.
- **Stand-in worker:** a local agent directory `~/.overdeck/agents/<localId>/` created on the viewer for a worker that runs on another machine. It holds `remote.json` and mirrored `reports/<seq>.json`, so `pan worker wait` and the parent read it like a local worker.
- **Follower:** the viewer service that keeps each stand-in in step with its remote worker (reports, liveness, stop).
- **Load sample:** `{ cpuPsiSomeAvg10, cpuSaturated, memAvailableBytes, workingAgents }` measured on a machine every 15 s.
- **Capability tags:** short strings a machine reports (`linux`, `macos`, `windows`, `docker`, `gpu`, `ios-sim`, plus operator tags). `--needs` requires every listed tag.
- **Placement:** the D-19 choice of a machine for **Auto**; it returns the chosen machine, a one-line reason and a per-machine rejection list.
- **Git origin slug:** `github.com/<owner>/<repo>` or `gitlab.com/<path>` built from a project's `github_repo` / `gitlab_repo` (the existing `gitOriginOf` in `src/lib/anywhere/shared-conversations.ts`, ~line 76). Projects on two machines are "the same repository" when their slugs are equal (case-insensitive).
- **Hash-driven sync:** the PAN-4650 pattern: the owner puts a short hash of a list in the 15 s heartbeat; the viewer fetches the list on connect and whenever the hash changes; nothing polls.

## Requirements

### Functional (from pan-2350, scoped to this issue)

- **FR-1 (epic FR-10) Start on any machine.** The new-conversation dialog has a **Machine** field: this machine (default), **Auto**, each online linked machine by label, and **Fly (new VM)** shown disabled. `pan start <issue> --machine <label|auto>`, `pan worker run --machine <label|auto>` and `pan lane start --machine <label|auto>` exist. A conversation started on another machine runs there and is listed on both.
- **FR-2 (epic FR-11, D-11) Delegation with a report back.** A worker started on another machine is followed until it ends; its reports reach the parent the way a local worker's do. Project match by git origin; a missing project names **Add this project to <machine>**. An offline target delays the follower (back-off up to 5 minutes) without failing it, and the follower resumes after a dashboard restart. Stopping the parent stops the remote worker. Work starts from the target's view of `origin`; unpushed local commits make the CLI refuse unless `--push-first` or `--ignore-unpushed`.
- **FR-3 (epic FR-4) Fencing of delegated work.** On the owner, an agent actor may create work through the work doors and may change only conversations and workers its own linked machine started. Operator actors keep today's rights. No link can pair, mint tokens, change settings or hop to a third machine.
- **FR-4 (epic FR-12) Projects across machines.** With **Combine matching repositories across machines** on (default), the sidebar shows one project per git origin slug with "· N machines", attaches linked conversations to the local project with the same slug, and lists projects that exist only on another machine. **Add this project to <machine>** clones the repository on that machine through the project-creation core and copies selected git-ignored files (`.env`, `.envrc`, `.dev.vars` preselected, at most 1 MiB each) through the secure channel.
- **FR-5 (epic FR-13) Fleet awareness.** Needs-You lists pending input from every online linked machine, labelled by machine. Palette search shows hits from every online linked machine, grouped by machine. `pan machines who <issue>` lists which machines run agents or conversations for an issue.
- **FR-6 (epic FR-22, D-19) Auto placement.** Each machine adds its load sample to the heartbeat; the Machines list (CLI and Settings) shows it. **Auto** picks by the D-19 rule and the dialog and the CLI print `Auto → <label> (CPU pressure N%, X GB free, K agents)`.
- **FR-7 (epic FR-23) Capabilities and reserved machines.** Each machine reports detected tags (`linux`/`macos`/`windows`, `docker`, `gpu`, `ios-sim`) plus `anywhere.machine.tags`; `--needs <tag,…>` and the dialog's **Needs** field restrict candidates; `anywhere.machine.placement: on-request` reserves a machine.
- **FR-8 (epic FR-31) Fleet usage.** The Costs page gains a **Machines** tab: one row per machine (today, week, month), an **All machines** total, cached numbers with their time for offline machines, and duplicate provider requests counted once.
- **FR-9 (epic FR-32) Compare settings.** Settings → Anywhere → Machines → **Compare settings** lists `config.yaml` keys whose values differ between this machine and the chosen machine, secrets only as "set"/"not set", each with a copyable `pan admin config set <key> <value>` line, plus **Open <label>'s dashboard** when a Tailscale Serve route exists.
- **FR-10 (epic FR-27) MCP fleet reach.** One MCP URL lists both machines, lists and searches both machines' conversations, reads and messages a conversation on a linked machine, and starts conversations and workers on any machine (`machine` = label or `auto`). Calls are limited to the `odk_` token's scopes on every machine; a settings change answers 403.

### Non-functional

- **NFR-1 No new polling.** Projects, Needs-You and load reach the viewer through the heartbeat (hash-driven sync or the payload itself). Search, placement, usage, compare and "who" fan out once per user action, 2.5 s per link.
- **NFR-2 Offline is never a global failure.** An offline or unsupported machine is skipped (or served from cache) with its label and state; it never turns a fleet answer into an error.
- **NFR-3 Owner is authority.** The viewer never writes state for another machine's work; stand-ins hold only mirrored reports and the follower's last observation.
- **NFR-4 Async only.** No `execSync`, no new `*Sync` tmux calls in server-reachable code (capability probes use `execFile` with a timeout).
- **NFR-5 Compatibility.** A peer that predates a route answers 404 or `403 insufficient_scope missingScope admin`; fleet routes show that machine as "needs Overdeck <version>" (the `predatesFleetUpdates` rule, `machines-fleet.ts:83`) and never retry in a loop.
- **NFR-6 Secrets stay home.** No fleet route returns a secret value. Project files cross only an operator-level link with the operator actor.

## Decisions (made here; the executor does not revisit them)

- **D-4651-1 Provenance column.** `conversations` gains `started_by_environment_id TEXT` (nullable; null = started locally). Top-up in `src/lib/overdeck/infra.ts` right after the PAN-4639 lines (`settled_at` / `snoozed_until`), mirrored in `drizzle/overdeck/0000_overdeck_init.sql`. `WorkerFacts` gains optional `startedBy: { environmentId: string; parentId: string | null } | null` (absent on old files ⇒ local). Doors: `markConversationStartedBy(name, environmentId)` and `conversationStartedBy(name)` in a new leaf `src/lib/overdeck/conversation-provenance.ts`; nothing else writes the column.
- **D-4651-2 Fence widening (epic FR-4).** `linkActorFence(credential, method, pathname, deps?)` gains an optional `deps: { conversationStartedBy(name: string): string | null }`. For a machine credential with an agent actor:
  - `POST /api/machines/work/conversations`, `/workers`, `/issues/:id/start` are **allowed** (delegation).
  - `POST /api/machines/work/projects` is **refused** (operator only, D-4651-14).
  - A non-GET `/api/conversations/<name>/…` write is allowed only when `conversationStartedBy(name) === credential.environmentId`; otherwise `agent-fenced`.
  - `POST /api/workers/:id/stop` passes the fence; the stop route itself refuses an agent actor with 403 `agent-fenced` unless the worker's `worker.json` `startedBy.environmentId` equals the credential's environment id (reading `worker.json` is async, and the gate is synchronous).
  - `POST /api/conversations` (bare create), `POST /api/workers`, `POST /api/lanes` stay **refused** to agent actors over a link: link-started work goes through the work doors so it is stamped.
  - `/ws/terminal` and `/ws/forward` stay refused.
  The fence stays synchronous (the remote request gate at `remote-request-gate.ts:130` is synchronous); `deps.conversationStartedBy` defaults to the provenance door, a synchronous SQLite read like every other `overdeck.db` door.
- **D-4651-3 Work doors are owner routes, machine credential only.** `src/dashboard/server/routes/machines-work.ts` (new) holds every work door. Each one: refuses a non-machine credential with 403 `machine-only`; resolves the project on this machine; compares the caller's `gitOrigin` slug (case-insensitive) with the resolved project's slug; answers 404 `{ code: 'project-missing', gitOrigin, machine: <this label> }` when there is no project or the slugs differ; then calls the existing local path and stamps provenance with `credential.environmentId`. Scope rows: each door `operate`. One shared guard `workDoorPreflight(request, body)` lives in the same file.
  - `POST /api/machines/work/conversations { gitOrigin, message, model?, harness?, effort?, issueId? }` → `handleConversationCreate({ …, projectKey: <resolved> }, deps)` → `markConversationStartedBy`. `gitOrigin: null` means "no project" (conversation in the home directory, no origin check). Answers `{ name }`.
  - `POST /api/machines/work/workers { gitOrigin, issueId, prompt, model?, harness?, effort?, readOnly?, name?, parentId? }` → project from `resolveProjectFromIssueSync(issueId)` (`src/lib/projects.ts:942`) then the origin check → `startWorker({ …, parentId: null, startedBy: { environmentId, parentId } })`. Answers `{ id, cwd, branch }`.
  - `POST /api/machines/work/issues/:id/start { gitOrigin, model?, harness?, effort? }` → the same project + origin check → runs the same spawn the `POST /api/agents` handler runs (extract the body of that handler's spawn call into `spawnIssueAgentForRoute(...)` in `routes/agents/spawn.ts` without changing its behavior, so both routes call it; net growth of `spawn.ts` ≤ 0 by moving the extracted helper to `routes/agents/spawn-issue.ts`). Answers `{ issueId, agentId }`.
- **D-4651-4 Worker status for followers.** Owner routes in `routes/workers.ts`: `GET /api/workers/:id/status?after=<seq>` (`read:state`) answers `{ id, liveness: { alive, confirmedDead }, idleAgeMs, reports: WorkerReport[] /* seq > after, at most 20 */, lastAssistantMessage: string | null /* only when confirmedDead */ }`; `POST /api/workers/:id/stop` (`operate`) calls `stopAgent(id, 'operator')` and answers `{ stopped: true }`. Both 404 `{ code: 'unknown-worker' }` for an id that is not a worker. Liveness uses `isAlive` / `isConfirmedDead` / `idleAgeMs` from `src/lib/agents/liveness.ts`.
- **D-4651-5 Stand-in and follower (viewer).** `POST /api/fleet/workers` with a remote target: allocate a local id with `allocateWorkerId(issueId)`, create `~/.overdeck/agents/<localId>/`, call the work door, then write `remote.json` (0600, temp file + rename): `{ v: 1, environmentId, label, remoteId, parentId, issueId, createdAt, state: 'running' | 'exited' | 'stopped', lastSeq, lastSeenAt, lastAssistantMessage: string | null, idleAgeMs: number | null, unreachableSince: string | null }`. The follower (`src/dashboard/server/services/remote-worker-follower.ts`, started in `startAnywhere` on the primary dashboard):
  - Loads every `remote.json` whose `state` is `running` at boot (resume after restart).
  - Polls each running stand-in every 5 s while its link is online: `GET /api/workers/<remoteId>/status?after=<lastSeq>` → writes each new report into the stand-in's `reports/<seq>.json` with the existing `writeWorkerReport`-compatible format, keeping the owner's `seq`; updates `lastSeq`, `idleAgeMs`, `lastSeenAt`; on `confirmedDead` sets `state: 'exited'` and `lastAssistantMessage`.
  - When the link is not online or a call fails with `LinkUnavailableError`, it backs off 1 s doubling to 300 s with ±20 % jitter and sets `unreachableSince`; it never gives up on its own.
  - Parent stop cascade: on every poll it checks the parent. An agent `parentId` is checked with `isAlive(parentId)`; a conversation `parentId` (`conv-…`) is checked by its row (archived, or status `ended`). Two consecutive dead (or ended) observations post `POST /api/workers/<remoteId>/stop` (actor `operator` — the parent's own machine is cleaning up its delegation) and set `state: 'stopped'`. Any other `parentId` never cascades. `allocateWorkerId` already creates the stand-in directory. A local worker gets the same cascade only for stand-ins; local workers keep today's behavior (NonGoal).
- **D-4651-6 `pan worker wait` on a stand-in.** `worker.ts` passes `WaitDeps` built from `remote.json` when the directory has one: `isAlive` ⇒ `running` → alive, `exited`/`stopped` → confirmed dead; `unreachableSince` set ⇒ alive (a sleeping desktop delays, never fails); `idleAgeMs` from the file; `fetchLastAssistantMessage` from the file. `listReports` is unchanged (mirrored files). `pan worker run --machine … ` without `--detach` waits exactly like a local run.
- **D-4651-7 Unpushed commits (epic D-11).** Before a remote `pan start` or `pan worker run`, the CLI counts `git rev-list --count @{u}..HEAD` in the parent's cwd (the issue workspace for `pan start`). Count > 0 ⇒ exit 1 with `N commits on <branch> are not pushed; <label> starts from origin. Re-run with --push-first to push them, or --ignore-unpushed.` `--push-first` runs `git push` (async `execFile`) and proceeds only on exit 0. No upstream ⇒ treated as count 0 with a one-line note. One helper: `src/cli/commands/delegation-push-check.ts`.
- **D-4651-8 Load in the heartbeat; tags too (deviates from epic FR-23 wording).** `HeartbeatPayload` gains optional `load?: LoadSample`, `tags?: string[]`, `placement?: 'auto' | 'on-request'`, `projectsHash?: string`, `needsYouHash?: string`. Tags ride in the heartbeat, not in the public descriptor, because `GET /api/environment` needs no credential and operator tags may name a purpose ("payments", "client-x"). The descriptor is unchanged.
  - **Load sample** (`src/dashboard/server/services/machine-load.ts`): every 15 s, `readCpuPsi().someAvg10`, `assessCpuPressure().saturated`, `readProcMemory().memAvailable` (bytes), and `workingAgents` = number of `getLiveAgentDirectory()` entries with `state === 'working'` (the fleet-update definition; `countWorkingTurns` moves into this module and `fleet-update-service.ts` imports it). The heartbeat reads the last sample (never waits).
  - **Tags** (`src/lib/anywhere/machine-capabilities.ts`): detected once at server start and every 10 minutes: OS from `process.platform` (`linux`→`linux`, `darwin`→`macos`, `win32`→`windows`); `docker` when `execFile('docker', ['info'], { timeout: 10_000 })` exits 0; `gpu` when `execFile('nvidia-smi', ['-L'], { timeout: 5_000 })` exits 0; `ios-sim` when on macOS and `execFile('xcrun', ['simctl', 'list', 'devices'], { timeout: 10_000 })` exits 0. ## Intersecting repo rules (restated)

- Dashboard runs Node 22 from `dist/` only; run `npm run build` before restarting it. Never Bun or tsx.
- No `execSync` in server-reachable code; capability probes and `git` calls use async `execFile` with a timeout.
- Every retry, back-off, poll, heartbeat or wait test uses `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`; never real waits.
- A new HTTP route needs a row in `tests/unit/lib/overdeck/no-loss-matrix.ts` and, unless it is admin-only, a row in `src/dashboard/server/route-scopes.ts`.
- Changing a `pan` verb's flags or help needs the matching `sync-sources/skills/pan-<verb>/SKILL.md` edit in the same commit (`scripts/lint-skills.sh`): `pan-worker`, `pan-start`, `pan-lane`, `pan-admin-config`.
- God files must not grow past their `origin/main` count or allowlist cap (`scripts/lint-file-size.sh`): `start.ts` (cap 1283), `cli/index.ts`, `CommandPalette.tsx` (1124), `Sidebar.tsx` (1019), `settings-api.ts` (1508), `routes/settings.ts` (1104), `routes/conversations.ts`, `conversation-runtime.ts`, `config-yaml/schema.ts`. - New must-run frontend tests go into `scripts/frontend-test-subset.txt` in sorted position.
- New lib modules import `getAgentState` from `agent-state-read.js` (the leaf) to avoid `lint:circular`.
- Agent state rows only after the terminal-backend session exists; a stand-in is a directory with `remote.json`, never a fake agent state row.
- JSONL transcripts are never deleted or truncated. Never send a destructive HTTP request speculatively.
- Frontend follows `pan-style-guide`: no pill badges, no decorative colour, "running" is never green; machine labels are muted text.
- Quality gates before `pan done`: `npm run typecheck`, `npm run lint`, `npx vitest run <touched tests>`; never the full `npm test` on the host.
- Browser verification uses an isolated Playwright context and profile; never another agent's session.
