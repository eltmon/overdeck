## Problem

A browse copy (PAN-4436) is read-only and tells the operator to run `pan vault resume <id8>` in a terminal. The
dashboard cannot continue the conversation. Four facts verified during planning shape the design:

1. **The CLI already has the whole sequence.** `resumeCommand` (`resume.ts` lines 156-259) resolves the target
   cwd, applies the WIP snapshot (`applyCode`, lines 110-154), checks drift, adopts, and launches
   `claude --resume <id>` / `codex resume <id>`. It prompts on a TTY and prints; none of it is callable from a
   route. The dashboard needs a write-free preview half and a non-interactive continue half.
2. **No route creates a managed conversation that resumes an outside session.** `runForkPipeline`
   (`src/lib/overdeck/conversation-forks.ts` line 418) needs a parent row. Its plain-fork branch (lines 437-452)
   is the pattern to reuse: create the row with `claudeSessionId`, set `forkStatus: 'spawning'`, call
   `ensureForkSessionReady(conv, sessionId, true, true)` (line 306), `markConversationActive`, clear the fork
   status.
3. **Codex managed conversations do not read `~/.codex`.** They run with a private home
   `${OVERDECK_HOME}/agents/<tmuxSession>/codex-home-v2` (`conversation-runtime.ts` line 659), whose
   `sessions/` is a symlink to `codexAgentSessionsDir(agentDir)` (`src/lib/runtimes/codex.ts` lines 265-275),
   and resume finds the rollout through `resolveCodexRolloutPath(tmuxSession)`
   (`src/lib/agents/transcript-resolver.ts` line 155), which reads `<agentDir>/codex-thread-id` and scans every
   `codex-home*` directory. `adoptRecord` must therefore write the rollout into that agent directory, not into
   `~/.codex`.
4. **`isWipPresent` writes git objects.** It calls `buildWipCommit` (`src/lib/vault/wip-capture.ts`), which
   runs `git add -A` into a temporary index, `write-tree` and `commit-tree` in the repository. A preview must
   write nothing, so it never calls `isWipPresent`; only the continue step does.

## Goal

- A browse copy shows a "Continue here" button. Clicking it opens a dialog that shows where the conversation
  will run, what happens to the code snapshot, and any drift, then continues it in one click.
- Continuing applies the WIP snapshot (in place on a clean checkout, in a new workspace on a dirty one), adopts
  the record, opens a managed conversation resuming the saved VIEW, and removes the browse row.
- On a machine with no matching project, the dialog offers to clone and register it through the existing
  Add-project dialog, then continues in the new checkout.
- Two machines racing: exactly one adopts; the other shows "Already continued on <label>" and writes no native
  file.

## Requirements

### Functional

- **FR-1** `GET /api/vault/sessions/:vaultId/continue-preview` returns the `ContinuePreview` of the wire contract
  and writes nothing (no git object, no file, no row).
- **FR-2** The preview names the target checkout by the D-2 rule, or explains why there is none.
- **FR-3** The preview reports the WIP snapshot (`captured` with `at`, `bytes`, `branch`, `base`; `skipped`
  with the reason; or `none`) and the code placement (`in-place`, `new-workspace`, `none`).
- **FR-4** The preview reports the drift fields. When the code placement is `in-place` or `new-workspace`, the
  drift fields are empty (an applied snapshot reproduces the saved state, as in `resume.ts` line 193).
- **FR-5** With no target checkout and a record `gitOrigin` that `parseRepoUrl` can parse, the preview returns
  `clone: { url, slug }`. The dialog offers "Clone and register <slug>", which opens the Add-project dialog in
  clone mode with the URL filled in. On success the dialog re-reads the preview.
- **FR-6** Project match: `parseRepoUrl(gitOrigin).slug`, compared case-insensitively to `github_repo` when the
  provider is `github` and to `gitlab_repo` when it is `gitlab`, over `listProjectsAsync()`. The first match in
  `listProjectsAsync()` order wins.
- **FR-7** `POST /api/vault/sessions/:vaultId/continue` `{ expectedOwnerToken: string; onDrift?: 'continue' | 'note' }`
  runs, inside one `enqueueVaultOperation('continue', …)` call: re-read the record (refuse if owned here or owned
  by someone other than the preview showed, D-6), resolve the target (D-2), apply the WIP snapshot (D-4), re-check drift (D-5), `adoptRecord`
  (D-6), then create and launch the managed conversation (FR-8, FR-9), then `removeVaultBrowseRow(vaultId)`.
- **FR-8** The managed conversation row: `claudeSessionId = newSessionId`, `cwd = targetCwd`,
  `harness = record.harness`, `title = record.title`, `titleSource: 'manual'`, `model = record.model` when it
  matches `MODEL_ID_PATTERN` (else omitted), no `effort` (inherits `high`), `projectKey` = the matched project
  key or `null`, `forkStatus: 'spawning'`.
- **FR-9** The launch runs outside the vault queue, registered with `registerInFlightForkPipeline`
  (`conversation-forks.ts` line 590): `ensureForkSessionReady(conv, newSessionId, true, true)`; for `note`,
  `injectForkSummary(conv, driftNote(fields), 'vault-continue')` (line 351); then `markConversationActive` and
  `updateForkStatus(name, null)`. A failure calls `handleForkPipelineFailure(name, err)` (line 411).
- **FR-10** A lost adoption race returns 409 `{ code: 'already-continued', label }`; the dialog shows
  `Already continued on <label>.` No native file and no conversation row are written. A code snapshot already
  applied is reported in the same response (`codeAppliedAt`).
- **FR-11** A browse copy's read-only notice (PAN-4436) gains a "Continue here" button that opens the dialog.
  The dialog's drift step offers "Continue", "Continue with a note" and "Cancel". On success the dashboard
  selects the new conversation.
- **FR-12** Codex records adopt into `codexAgentHome(${OVERDECK_HOME}/agents/<tmuxSession>)` and record the
  thread id with `recordCodexRolloutSession(tmuxSession, newSessionId, path)`
  (`src/lib/runtimes/codex.ts` line 213), so `spawnConversationSession(…, resume = true, 'codex', …)` launches
  `codex resume <newSessionId>`.
- **FR-13** Records whose harness is not `claude-code` or `codex` return 400 with
  `<harness> has no native resume. Run: pan vault resume <id8>` (the CLI writes a seed digest).

### Non-functional

- **NFR-1** All I/O is async; no `execSync` in any dashboard-reachable file.
- **NFR-2** Routes: GET calls `rejectUnauthorizedDashboardRequest`, POST calls
  `rejectUnsafeDashboardMutationRequest` (`src/dashboard/server/routes/dashboard-auth.ts` lines 353, 187).
- **NFR-3** The vault engine stays standalone: the new engine module imports only Node built-ins and sibling
  vault modules; the import-graph test passes unchanged.
- **NFR-4** Nothing in this plan writes to the operator's real `~/.claude` or `~/.codex` during tests: unit

  directory.
- **NFR-5** Files stay under their size caps (see "Intersecting repo rules").

## Decisions (made in this document)

- **D-1 Split.** Round-trip states → PAN-4447 (see "Scope split").
- **D-2 Target checkout.** In order: (a) `record.cwd` is an existing directory here → it; (b) else a project
  matches (FR-6) → that project's `config.path`; (c) else `gitOrigin` parses → no target, `clone` offer; (d) else
  no target, reason `no-checkout`, message
  `The saved working directory <cwd> does not exist here and the record has no git origin. Run: pan vault resume <id8> --cwd <dir>`.
  The route takes no `cwd` from the browser: a browser-chosen directory is a path-injection surface and the
  CLI already covers it.
- **D-3 Project match lives in the projects domain.** New `src/lib/projects/origin-match.ts`
  `findProjectForGitOrigin(gitOrigin, projects)`, pure over the `listProjectsAsync()` result, so it is testable
  without a registry.
- **D-4 WIP apply.** Owner-here records never reach this path (D-6). For a captured snapshot:
  - Target not a git checkout (`readCwdState` null) → placement `none`, continue without code (same as the CLI).
  - Clean target → `applyWipSnapshot({ cwd, … })` in place. On a primary checkout this can move its branch or
    detach HEAD (wip-apply D-12: fast-forward only, never backward). The issue asks for in-place on clean, and
    a fresh clone depends on it, so this is kept; the preview shows `wip.branch` and `wip.base` so the operator
    sees the resulting state.
  - Dirty target → if `isWipPresent(cwd, wip)` → no apply, continue in `cwd`. Otherwise create a scratch
    workspace through the normal path: `resolveWorkspaceCreateIntent({ kind: 'scratch', isolated: true,
    projectKey, name })` then `performWorkspaceCreate(intent)` (`src/lib/workspaces/create.ts` lines 286, 417),
    then `applyWipSnapshot({ cwd: intent.path, … })` in that clean worktree; the target becomes `intent.path`.
    `name` is `vault-<id8>`; on a `path-exists` finding try `vault-<id8>-2` … `vault-<id8>-9`, then fail with
    the finding's message. The workspace's `scratch/vault-<id8>` branch is left behind when `checkoutBase`
    switches to `wip.branch`; that is harmless and is not cleaned up.
  - Dirty target and no project key (no match by D-3 and no registered project containing the target by
    `isPathUnder`) → 409 `{ code: 'dirty-unregistered', error: '<cwd> has uncommitted changes and is not a registered project, so no workspace can be created for the code snapshot. Commit or move the changes, or run: pan vault resume <id8> --worktree <dir>' }`. Nothing is written.
  - `applyWipSnapshot` returns `failed` → 409 `{ code: 'wip-failed', error: 'Cannot apply the code snapshot: <reason>' }`, nothing adopted.
- **D-5 Drift at continue time.** Recompute the drift fields after the WIP step, exactly as FR-4. Non-empty and no
  `onDrift` in the body → 409 `{ code: 'drift', fields }` (the checkout changed since the preview); the dialog
  shows the drift step again. `cancel` is client-side only and never POSTs.
- **D-6 Ownership checks.** The preview returns `ownerToken`, the first 16 hex characters of
  `sha256(record.owner.environmentId)` (opaque: the browser never sees an environment id). The POST body must
  carry it as `expectedOwnerToken` (400 when absent). Before any write, `continueHere` re-reads the record:
  owned by this machine → 409 `{ code: 'owned-here', error: 'This conversation is already owned by this machine.' }`;
  owner token differs from `expectedOwnerToken` → 409 `already-continued` with the current owner's label (another
  machine continued it after the dialog opened; taking it over silently would steal a live conversation).
  The check is anchored to the CAS: `continueHere` passes the owner it verified as
  `expectedOwnerEnvironmentId`, and `adoptRecord` compares it with the same read its `casRef` starts from. An
  adoption by another machine during the WIP step (D-4) is therefore refused with `already-continued`, never taken
  over, and the truly concurrent case (both read the same version) is decided by `casRef`: the loser gets
  `conflict` → FR-10. (Review cycle 1: the first version re-read inside `adoptRecord` and could steal a
  conversation adopted during the WIP step.)
- **D-7 Materialized path check.** Claude records adopt with `projectsRoot: claudeProjectsRoot()`
  (`src/lib/runtimes/storage/claude-code.ts` line 19). Before creating the row, assert
  `outcome.path === sessionFilePath(targetCwd, outcome.newSessionId)` (line 55); a mismatch throws
  `Materialized transcript <path> is not where Claude Code resumes <expected>` and the route returns 500. The
  record is already adopted then; the operator can still run `claude --resume` by hand, and the error says so.
- **D-8 The conversation door.** New `src/lib/overdeck/conversation-vault-continue.ts` exports
  `createVaultContinuedConversation(input)` (row) and `launchVaultContinuedConversation(conv, note)` (spawn).
  The dashboard service calls them; no route touches `createConversation` directly. Names: `name =
  <yyyymmdd>-<4 hex>`, `tmuxSession = conv-<name>`, the plain-fork rule at `conversation-forks.ts` lines 846-849.
- **D-9 Codex home.** For codex records the service computes `tmuxSession` first, then adopts with
  `codexHome: codexAgentHome(join(getOverdeckHome(), 'agents', tmuxSession))`
  (`src/lib/runtimes/storage/codex.ts`), which is the directory `initCodexHome` later symlinks
  `codex-home-v2/sessions` to. **Implementation checkpoint:** after adoption, assert
  `resolveCodexRolloutPath(tmuxSession)` returns `outcome.path`. Fallback when it does not: return 500 with
  `Codex continue could not place the rollout where the managed conversation reads it. Run: pan vault resume <id8>`
  and file a follow-up issue; do not add a second codex path.
- **D-10 Drift note delivery.** `injectForkSummary(conv, driftNote(fields), 'vault-continue')` after the session
  is ready. It already waits for the ready signal, delivers through the conversation's delivery method and
  confirms acceptance, for both Claude Code and Codex. The dashboard never imports a CLI module, so `driftNote`
  (`src/cli/commands/vault/resume.ts` line 64) is **moved** to the new engine module `continue-inspect.ts` and re-exported from `resume.ts` (`export { driftNote } from
  '../../../lib/vault/continue-inspect.js';`), so the CLI text and tests stay identical.
- **D-11 Restart during spawn.** The row has `forkStatus: 'spawning'` and no `forkRequest`, so
  `recoverStuckForks` (`conversation-forks.ts` line 620) marks it `failed` and ended after a dashboard restart.
  The native file exists and the row is resumable from the normal Resume control. This is accepted; no
  `forkRequest` shape is added.
- **D-12 Browse row removal is last and best-effort.** After the row is created, `removeVaultBrowseRow(vaultId)`;
  a throw is logged `[vault] continue: browse row removal failed …` and not returned (PAN-4436's sync removes a
  row whose record is owned here at the next cycle).
- **D-13 Clone reuses the Add-project dialog.** `useAddProjectDialog.show(mode, returnTo, options?)` gains
  `options: { initialUrl?: string; onCreated?: (project) => void }`, threaded to
  `useProjectCreateIntent({ initialUrl })`. No new route, no second registration path.
- **D-14 No CLI refactor.** `resumeCommand` keeps its own flow; only `driftNote` moves (D-10). Sharing more is a
  separate change.
- **D-15 Title.** The row title is `record.title` unchanged; the browse row it replaces showed the same title.

### Wire contract

```ts
// GET /api/vault/sessions/:vaultId/continue-preview → 200 ContinuePreview
//   404 { error: 'No saved conversation matches <id8>.' }  (no record, or tombstone)
//   409 { error: <vault off / key message>, code: 'vault-unavailable' }
interface ContinuePreview {
  vaultId: string;
  title: string;
  harness: string;                 // 'claude-code' | 'codex' | other (other → resumable: false)
  resumable: boolean;
  ownerLabel: string;              // current owner
  ownerToken: string;              // D-6: sha256(owner.environmentId).slice(0, 16)
  ownedHere: boolean;
  target: null | { cwd: string; source: 'saved-cwd' | 'project'; projectKey: string | null; dirty: boolean; isGit: boolean };
  noTargetReason: null | 'clone-offered' | 'no-checkout';
  clone: null | { url: string; slug: string | null };
  wip: { kind: 'none' } | { kind: 'skipped'; reason: string }
     | { kind: 'captured'; at: string; bytes: number; branch: string | null; base: string };
  codePlacement: 'in-place' | 'new-workspace' | 'none';
  drift: string[];                 // CwdStateField names; [] when codePlacement !== 'none'
  savedCwd: string;
}

// POST /api/vault/sessions/:vaultId/continue { expectedOwnerToken: string; onDrift?: 'continue' | 'note' } →
//   200 { conversation: { name: string; title: string; cwd: string }; codeApplied: boolean; workspacePath: string | null; note?: string }
//   400 { error } (missing expectedOwnerToken; bad onDrift; non-resumable harness FR-13)
//   404 { error }
//   409 { code: 'already-continued', label: string, error: 'Already continued on <label>.', codeAppliedAt: string | null }
//   409 { code: 'drift', fields: string[], error }
//   409 { code: 'owned-here' | 'dirty-unregistered' | 'wip-failed' | 'no-target' | 'vault-unavailable', error }
```

`note` in the 200 response echoes a WIP-apply note (for example "HEAD is detached …").
