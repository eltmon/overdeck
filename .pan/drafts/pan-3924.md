# PAN-3924 — pipeline-membership: capture gh GraphQL stderr, retry once, and make the tracker-issue lens prefix-correct for GitHub

**Issue:** https://github.com/eltmon/overdeck/issues/3924
**Follow-up from:** PAN-3917 (The Overdeck Cut) integration notes and the Codex review of the integrated diff.
**Planned:** 2026-09-19 (auto mode, `pan plan --auto`)

## Glossary

- **Pipeline membership** — the per-project verdict of which issues are "in the pipeline". Computed by `gatherProjectLensSignals` (`src/lib/pipeline-membership-gather.ts`) and classified by `resolvePipelineMembership` (`src/lib/pipeline-membership.ts`).
- **Gather** — one full collection of lens signals for one project: tracker issues, open PRs, branch refs, spec ids, then two batched GitHub GraphQL calls (merged-PR heads and issue states).
- **Membership snapshot** — the server-side cache of the last successful gather per project, held in `membershipSnapshots` (`src/dashboard/server/services/pipeline-membership.ts:78`). A **last-good snapshot** is a snapshot whose `refreshedAt` is non-zero.
- **Cold snapshot** — a project entry whose `refreshedAt` is `0` (no gather has ever succeeded since the server started).
- **Refresh** — `refreshMembershipSnapshot` (`services/pipeline-membership.ts:81-111`). On failure it keeps `value`/`refreshedAt`, records `lastError`, and logs `[pipeline-membership] refresh failed for <project>; keeping last-good snapshot: <message>`.
- **The banner** — the `role="alert"` box rendered by `ProjectMembershipBoundary` (`src/dashboard/frontend/src/components/CommandDeck/ProjectMembershipBoundary.tsx:60-85`). The issue calls it a toast. It renders when `GET /api/pipeline/membership` returns a body with `status: 'unavailable'` or a non-2xx status, which the route does only for a cold snapshot (`routes/pipeline-membership.ts:39-50`).
- **`forge_unavailable`** — one of the `MembershipUnavailableReason` values (`packages/contracts/src/types.ts:25`). `withUnavailableReason` (`gather.ts:259-274`) wraps any forge/tracker call failure in `PipelineMembershipUnavailableError` with this reason and the original error's `message`.
- **`runGitHubGraphql`** — the private helper at `gather.ts:89-114` that shells out to `gh api graphql -f query=<query>` and returns stdout. Both batched GraphQL functions take it as a default parameter.
- **GraphQL envelope** — the JSON object gh prints on stdout: `{ data?, errors? }`. gh exits non-zero when `errors` is present even if `data` is usable.
- **Tracker `ref`** — the human-readable identifier on the normalized `Issue` (`src/lib/tracker/interface.ts:35-36`). Linear/GitLab/Rally return a prefixed id like `MIN-902`; the GitHub tracker returns a bare `#<number>` (`src/lib/tracker/github.ts:384`).
- **Issue prefix** — the project's `issue_prefix` (e.g. `PAN`); Overdeck's `PAN-<n>` is layered on top of GitHub's `#<n>`.
- **File-size ratchet** — `scripts/lint-file-size.sh` (run by `npm run lint`) fails if an existing non-test source file has more lines than on `origin/main` unless `scripts/file-size-allowlist.txt` carries a row. `pipeline-membership-gather.ts` is 765 lines on `origin/main`; it must not end above 765 lines.

## Problem

1. **Diagnostic blindness.** `runGitHubGraphql` catches the execFile rejection, inspects only `stdout`, and rethrows the original error. The rejection's `message` is `Command failed: gh api graphql -f query=<50-alias query>` — the query is huge, and `stderr` (which carries gh's real reason, e.g. `error connecting to api.github.com` or `HTTP 502`) is dropped. The operator sees `[pipeline-membership] refresh failed for overdeck ... Command failed: gh api graphql ... (forge_unavailable)` and cannot tell why. This fired intermittently, including 4x on the 0.51.0 build, while the same 50-issue batch succeeds by hand.
2. **No tolerance for a single transient failure.** One failed `gh` subprocess fails the whole gather. There is no retry.
3. **Banner on a single failure.** The issue asks that a single failed refresh must not surface the banner when a last-good snapshot exists. Verified state of the code (see "Decisions" D5): the service and route already preserve and serve the last-good snapshot; the observed boot-time banner is the cold case. This PRD pins the last-good behavior with regression tests rather than changing it.
4. **`listProjectTrackerIssues` is blind to GitHub-tracked projects.** `gather.ts:238-246` maps `issue.ref.toUpperCase()` and drops anything not starting with `${issuePrefix}-`. GitHub refs are `#N`, so every GitHub issue is dropped. The correct mapping already exists as `issueIdFromTrackerIssue` (`src/cli/commands/admin/migrate-plan-home.ts:51-56`). Note: the gather calls `deps.listTrackerIssues` only for non-GitHub trackers (`gather.ts:547-550`), so this bug changes no live membership output today; it is a latent correctness bug in a function that any future GitHub caller would hit.

## Requirements

### Functional

- **FR-1** A failed `gh api graphql` subprocess produces an error whose message contains the exit code (or `timeout` when `killed` is true), the attempt count, and up to 500 characters of trimmed stderr (or `no stderr` when empty), and does NOT contain the GraphQL query text.
- **FR-2** When gh exits non-zero but stdout is a JSON envelope whose `data` is a non-null object, the runner returns stdout (existing behavior, unchanged).
- **FR-3** When stdout is a JSON envelope without usable `data` (errors-only, e.g. a query error or a rate-limit envelope), the runner throws immediately without retrying.
- **FR-4** When stdout is empty or not JSON (network failure, gh crash, timeout), the runner waits 1 000 ms and runs the same query exactly once more; a second failure throws the FR-1 error with attempt count 2.
- **FR-5** The FR-1 message propagates unchanged through `withUnavailableReason` into `PipelineMembershipUnavailableError.message` (reason `forge_unavailable`), and therefore into `snapshot.lastError`, the `[pipeline-membership] refresh failed` log line, and the `PipelineMembershipUnavailableBody.message`.
- **FR-6** When a project has a last-good snapshot and a subsequent refresh fails, `readPipelineMembershipSnapshotsForProjects` returns `{ project, memberships }` with no `error` and no `unavailableReason`, and both `GET /api/pipeline/membership` and `POST /api/pipeline/membership/refresh` return HTTP 200 with the bare membership array (pinned by tests; no behavior change).
- **FR-7** `issueIdFromTrackerIssue` lives in `src/lib/tracker/issue-id.ts` and is re-exported from `src/cli/commands/admin/migrate-plan-home.ts` so existing imports keep working.
- **FR-8** `listProjectTrackerIssues` maps rows through a pure exported function `projectTrackerIssueRows(issues, trackerType, issuePrefix)` that uses `issueIdFromTrackerIssue`; for `trackerType === 'github'` an issue with `ref: '#12'` and prefix `PAN` yields `issueId: 'PAN-12'`; for other trackers `ref` is upper-cased and rows whose id does not start with `${PREFIX}-` are dropped.
- **FR-9** `configuration/issue-trackers.mdx` states, next to the existing pipeline-membership paragraph, that a transient GitHub GraphQL failure is retried once, that the last successful membership snapshot keeps serving while a refresh fails, and that the server log line `[pipeline-membership] refresh failed` carries gh's stderr.

### Non-functional

- **NFR-1** Retry tests use `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()`; the default delay is implemented as `new Promise((resolve) => setTimeout(resolve, ms))` on the global `setTimeout` (never `node:timers/promises`, which fake timers do not intercept).
- **NFR-2** No `execSync`/`spawnSync` anywhere in the touched modules; the import-graph guard at R15 stays green (no `/database/`, `review-status`, `agent-state`, or `tmux` module may enter the gatherer's import graph — in particular `src/lib/` must not import `src/cli/commands/admin/migrate-plan-home.ts`).
- **NFR-3** `src/lib/pipeline-membership-gather.ts` ends at or below 765 lines (its `origin/main` count); no `scripts/file-size-allowlist.txt` row is added. New modules stay far below the 1 000-line ceiling.
- **NFR-4** `gh` per-attempt timeout stays 30 000 ms and `maxBuffer` stays 4 MiB.
- **NFR-5** Quality gates pass: `npm run typecheck`, `npm run lint`, `npm test`.

## Decisions

- **D1 — Retry discriminator is "does stdout parse as a JSON envelope".** Three-way rule in the catch block: (a) JSON with non-null `data` object → return stdout; (b) JSON without usable data → throw, no retry (deterministic query/rate-limit errors; retrying burns quota); (c) empty or non-JSON stdout → retry once after 1 000 ms. The unused cooldown module is not wired in.
- **D2 — One retry, fixed 1 000 ms delay, no backoff.** The issue asks for "retry once". Worst case per chunk is 30 s + 1 s + 30 s ≈ 61 s (see hazard H1).
- **D3 — Extract the runner into a new module `src/lib/github-graphql-run.ts`.** Reason: (i) the ratchet forbids growing gather.ts; (ii) a module with injectable `exec` and `delay` is unit-testable without `vi.mock('node:child_process')` in the 1 361-line gather test, where such a mock would also swallow `defaultDeps.run` and `listOpenPullRequestsSnapshot`.
- **D4 — Error is a plain `Error` with `cause` set to the original rejection.** `new Error(message, { cause })` is valid here: the root tsconfig targets `ES2022` with `lib: ["ES2022", …]`, and `src/lib/tmux-dedup.ts:217` already uses the options bag. No new error class; the message is the contract (FR-1). Callers already only read `message`.
- **D5 — The "banner on a single failure" ask is already satisfied server-side; pin it, do not change it.** R10 keeps `value`/`refreshedAt` on failure; R11 returns memberships whenever `refreshedAt` is truthy; R12/R13 return the bare array in that case. The boot-time banner is the cold case (first gather after restart fails); `periodic-convergence` (R19) re-gathers within 5 minutes and the retry-once change reduces the chance it fails at all. Auto-rescheduling a failed cold refresh is a NonGoal.
- **D6 — Relocate `issueIdFromTrackerIssue` to `src/lib/tracker/issue-id.ts`.** The issue names the CLI file, but `src/lib` importing `src/cli/commands/…` is the wrong layering direction and risks the R15 import-graph guard. The CLI file re-exports it so R16 keeps compiling without edits.
- **D7 — `listProjectTrackerIssues` stays private; its mapping becomes a pure exported function.** `projectTrackerIssueRows` is the unit-test target; the tracker/network wiring is unchanged and untested (as today).
- **D8 — The REST `gh api --paginate` path (`listOpenPullRequestsSnapshot`, gather.ts:62-78) is out of scope.** Same class of bug, but not named by the issue; file a follow-up if it recurs.

/**
 * gh GraphQL runner for the pipeline-membership gatherer (PAN-3924).
 *
 * Shells out to `gh api graphql`. A failed subprocess used to surface as
 * `Command failed: gh api graphql -f query=<huge query>` with stderr dropped,
 * so intermittent forge failures were undiagnosable. The error now carries
 * gh's stderr, the exit code / timeout, and the attempt count, and a failure
 * with no JSON envelope on stdout is retried once.
 */
import { execFile } from 'node:child_process';
import { promisify } from 'node:util';

const execFileAsync = promisify(execFile);

export const GH_GRAPHQL_RETRY_DELAY_MS = 1_000;
export const GH_GRAPHQL_STDERR_LIMIT = 500;

export type GhExec = (args: string[]) => Promise<{ stdout: string }>;
export type Delay = (ms: number) => Promise<void>;

interface ExecFailure { code?: number | string | null; killed?: boolean; signal?: string | null; stdout?: string; stderr?: string }

const defaultExec: GhExec = (args) => execFileAsync('gh', args, {
  encoding: 'utf-8',
  timeout: 30_000,
  maxBuffer: 4 * 1024 * 1024,
});

// Global setTimeout on purpose: vitest fake timers intercept it; node:timers/promises they do not.
const defaultDelay: Delay = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

function parseEnvelope(stdout: string | undefined): { parsed: true; hasData: boolean } | { parsed: false } {
  if (typeof stdout !== 'string' || stdout.length === 0) return { parsed: false };
  try {
    const envelope = JSON.parse(stdout) as { data?: unknown };
    return { parsed: true, hasData: envelope.data !== undefined && envelope.data !== null };
  } catch {
    return { parsed: false };
  }
}

export function describeGhGraphqlFailure(error: unknown, attempt: number): string {
  const failure = (error ?? {}) as ExecFailure;
  const status = failure.killed ? 'timeout' : `exit ${failure.code ?? 'unknown'}`;
  const stderr = (failure.stderr ?? '').trim();
  const detail = stderr.length > 0 ? stderr.slice(0, GH_GRAPHQL_STDERR_LIMIT) : 'no stderr';
  return `gh api graphql failed (${status}, attempt ${attempt}): ${detail}`;
}

export async function runGitHubGraphql(
  query: string,
  exec: GhExec = defaultExec,
  delay: Delay = defaultDelay,
): Promise<string> {
  for (let attempt = 1; ; attempt++) {
    try {
      const { stdout } = await exec(['api', 'graphql', '-f', `query=${query}`]);
      return stdout;
    } catch (error) {
      const stdout = (error as ExecFailure).stdout;
      const envelope = parseEnvelope(stdout);
      // gh exits non-zero when the envelope carries per-field errors but still
      // prints partial data; callers use the resolvable fields.
      if (envelope.parsed && envelope.hasData) return stdout as string;
      const wrapped = new Error(describeGhGraphqlFailure(error, attempt), { cause: error });
      // An envelope without data is a deterministic GraphQL error — never retry it.
      if (envelope.parsed || attempt > 1) throw wrapped;
      await delay(GH_GRAPHQL_RETRY_DELAY_MS);
    }
  }
}
