# PAN-4372: Jev advisory semantic review of xBRIEF acceptance criteria at `pan plan finalize` (warnings only)

Date: 2026-09-29. Status: PRD (auto-planned). Parent research: [`.pan/drafts/jev-integration.md`](jev-integration.md) item 2 / "Issue 2". Depends on PAN-4369 (the optional Jev client), merged in PR #4380 (commit `ced6c89b4a0`).

This PRD is the implementation brief. It names every file, function, decision and test. An executor must not need to re-research anything below.

---

## Glossary

- **Jev**: TypeSafe AI's "System One" judgment model. It takes a `state` (text or JSON) plus named questions and returns a typed answer per question. It never generates text.
- **Noul**: a Jev yes/no question. The answer is `{ type: 'noul', noul: <probability 0..1 that the statement is true> }` (SDK type `NoulResponse`, `node_modules/@typesafe-ai/sdk/dist/index.d.mts` lines 87–90).
- **`assess()`**: the single Jev entry point in `src/lib/jev/client.ts` (line 84). It never throws. It returns `{ status: 'answered', answers, model, usage }`, `{ status: 'unavailable', reason }` (a gate said no; no request was sent) or `{ status: 'failed', reason, message }` (a request went out and did not succeed). It applies the feature gate, the memo, the concurrency cap and cost recording.
- **Feature toggle `jevAcceptanceCriteriaReview`**: a background-AI feature key in `src/lib/background-ai/registry.ts` (line 102), `defaultEnabled: false`. `background_ai.cheap_mode: true` also disables it.
- **AC**: an acceptance criterion: a sub-item of a plan item with `metadata.kind === 'acceptance_criterion'`. AC ids follow `<item-id>.acN` (dotted).
- **Keyword rule**: the existing `ac-not-observable` check in `lintItem` (`src/lib/xbrief/quality-lint.ts` lines 172–174): an AC title fails when its lowercased text contains none of `OBSERVABLE_TERMS` (line 36).
- **Quality gate**: `evaluatePlanFinalizeQualityGate` in `src/cli/commands/plan-finalize.ts` (lines 44–56). It calls the synchronous `lintPlanQuality`; any `error` issue makes finalize exit 3.
- **Semantic review**: the new advisory Jev check this issue adds. It produces only `warn` issues and never changes the exit code.
- **Shadow eval log**: an append-only local JSONL file that records, per AC, the keyword rule's verdict next to Jev's Nouls, for threshold tuning. Nothing reads it back as authority.
- **Question-set version**: `QUESTION_SET_VERSION` in `src/lib/jev/questions.ts` (line 8). It is part of the memo key, and every change to question text or thresholds bumps it.

## Problem

`lintItem` flags `ac-not-observable` when an AC title contains none of the 49 substrings in `OBSERVABLE_TERMS`. The list includes `'when '`, `'then '`, `'passes'` and `'contains'`. So "Given the page loads then it works" passes, and "The CLI exit code is 2 on a missing file" fails. Planners learn to add magic words instead of writing testable criteria. Nothing today detects an AC that packs several independent behaviors into one line.

## Proposal (summary)

Add `reviewAcceptanceCriteria(doc)` in a new `src/lib/jev/acceptance-criteria.ts`. It sends **one** Jev request per plan with two Nouls per AC (observable? compound?) and turns low/high answers into `warn`-severity `QualityIssue`s. `pan plan finalize` calls it after the keyword quality gate passes and prints its warnings in the existing warnings block. The keyword rule stays the gate. `lintPlanQuality`, `assertPlanQuality` and `src/lib/overdeck/planning-promotion.ts` are untouched. When the feature is on and Jev answers, one line per AC goes to a local shadow eval log. An evalite eval with 60+ labeled ACs from `.pan/specs/*.xbrief.json` measures agreement.

## Integration constraints (restated from the issue; non-negotiable)

1. **Optional, off by default.** With no `jev:` block, the toggle off (default), or `background_ai.cheap_mode: true`, nothing calls Jev, and finalize output and exit code are exactly today's. No startup check, no error, no extra line.
2. **Model from config only.** `assess()` already enforces this: `jev.model` or `unavailable: model-not-configured`. The new code must call `assess('jevAcceptanceCriteriaReview', …)` and **never** `createJevClient` directly (that would bypass the gate, memo and cost recording). The eval is the one exception, following `evals/jev-smoke.eval.ts`.
3. **Disclosure.** The Settings toggle description and `configuration/jev.mdx` state exactly what leaves the host: the id and title text of each AC of the plan's non-cancelled items.
4. **Advisory only.** Plans can quote text the public wrote into `eltmon/overdeck` issues, and Jev is weak against adversarial state. So Jev output never blocks and never becomes an `error`.

## Decisions (made here; auto-planning mode)

- **D1 State shape.** `state = { criteria: { "<acId>": "<ac title>", … } }`: a JSON object keyed by AC id, in plan order. The issue text calls the state "the list of `{ id, title }`" but also writes the question as `criteria[<id>]`. An object keyed by id carries the same id and title data and makes the question text literally resolve. Duplicate AC ids across items: first occurrence wins, later duplicates are dropped from the request and produce no issue.
- **D2 Question texts** (exact, built per AC with `noul()` from `@typesafe-ai/sdk`):
  - `observable_<acId>`: `Does criteria["<acId>"] describe a behavior a test or a person can observe, such as an output, stored state, UI change, exit code or emitted event?`
  - `compound_<acId>`: `Does criteria["<acId>"] describe more than one independent behavior?`
- **D3 Question keys use the raw AC id** (`observable_ac1` for id `ac1`; `observable_foo.ac2` for id `foo.ac2`). The SDK types allow any string key (`interface Questions { [name: string]: Question }`). The server's rule is unverified. If it rejects dotted keys, `assess` returns `failed/bad-request` and finalize prints the FR-8 line, so the failure is visible and harmless. The eval exercises real dotted ids (FR-10); if the live eval gets `bad-request`, the follow-up is to switch keys to positional (`observable_<n>`). That is out of scope here.
- **D4 Thresholds.** `JEV_AC_OBSERVABLE_MIN_NOUL = 0.5` (warn when `noul < 0.5`), `JEV_AC_COMPOUND_MAX_NOUL = 0.5` (warn when `noul > 0.5`). Both live in `src/lib/jev/questions.ts`. They are neutral starting points, to be tuned from the eval and the shadow log.
- **D5 Version bump.** Set `QUESTION_SET_VERSION` to origin/main's value + 1 at rebase time (it is 1 on main today, so 2). PAN-4371 will bump it too; whichever lands second re-bumps.
- **D6 Warnings merge into the existing block.** No separate "Jev" section, so the output shape does not fork: `formatQualityIssues` renders `  [warn] ac-semantic-not-observable: <message>`.
- **D7 `--no-quality-lint` skips Jev.** No gate ran, so there is nothing to advise on.
- **D8 `failed` is reported in one dim line; `unavailable`/`skipped` are silent** (FR-8). An operator who turned the toggle on should learn when it breaks; an operator who did not must see no change.
- **D9 Shadow log home.** `join(getOverdeckHome(), 'jev', 'eval-log', 'acceptance-criteria', `${YYYY-MM-DD}.jsonl`)`, UTC date of the write. `getOverdeckHome()` is in `src/lib/paths.ts` (line 9). Pattern follows the rag-runs log (`src/lib/memory/query-expansion.ts`, `appendJsonl`, lines ~233–258). `keywordVerdict` is `'observable'` when `OBSERVABLE_TERMS.some(t => title.toLowerCase().includes(t))`, else `'not-observable'`; `OBSERVABLE_TERMS` is imported (already exported); `quality-lint.ts` is not edited.
- **D10 Module split.** The log writer is its own file, `src/lib/jev/eval-log.ts`, so its tests stay separate. `acceptance-criteria.ts` calls it.
- **D11 Size justification.** The plan touches 14 files. The projected-surface lint counts 9 "subsystems" only because single files at a repo root each count as one (`evals/jev-acceptance-criteria.eval.ts`, `evals/README.md`, `docs/XBRIEF.md`, `configuration/jev.mdx`). The real areas are four: `src/lib/jev`, `src/cli`, `evals`, docs. The disclosure text must ship with the feature it discloses, so a sibling split would be wrong. `plan.metadata.sizeJustification` records this.
