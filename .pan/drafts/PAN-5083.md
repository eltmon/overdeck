# PAN-5083: Telemetry — record which MCP protocol revisions, clients and surfaces are used

**Issue:** [PAN-5083](https://github.com/eltmon/overdeck/issues/5083)
**Related:** [PAN-5082](https://github.com/eltmon/overdeck/issues/5082) (move every MCP surface to SDK v2 and the 2026-07-28 spec). This issue supplies the data to time that move.

## Glossary

- **MCP surface** — one of the transports that serves Overdeck's MCP tool module (`src/lib/mcp/server.ts` `createOverdeckMcpServer`). There are five, named by the `mcp_surface` telemetry domain:
  - `dashboard_http` — `POST /mcp` on the dashboard (`src/dashboard/server/routes/mcp.ts`), reached on loopback, LAN or tailnet. Managed agents, Copy MCP URL tokens and OAuth sign-ins all land here.
  - `public_http` — the same `POST /mcp` route reached through Tailscale Funnel (Public MCP, PAN-4947). Identified by the `Tailscale-Funnel-Request` header (`isTailscaleFunnelRequest` in `src/dashboard/server/routes/dashboard-auth.ts`, line 458).
  - `stdio` — `pan mcp serve` (`src/cli/commands/mcp.ts` `runMcpServe`, line 78).
  - `connector_http` — `pan mcp connector serve` in HTTP mode (`src/lib/mcp/connector/serve.ts` `startConnectorHttp`, line 101).
  - `connector_stdio` — `pan mcp connector serve --stdio` (`serveConnectorStdio`, line 176).
- **Protocol revision** — the MCP spec version a client speaks, a date string such as `2025-11-25`. Before 2026-07-28 a client names it in the `initialize` request's `params.protocolVersion` and then in the `MCP-Protocol-Version` HTTP header. In the 2026-07-28 spec there is no `initialize`; every request carries `params._meta["io.modelcontextprotocol/protocolVersion"]` (required) and `params._meta["io.modelcontextprotocol/clientInfo"]` (optional).
- **Requested protocol** — the revision the client asked for. SDK 1.30.1 silently answers an unsupported request with its latest (`2025-11-25`), so the requested value, not the answered one, is the migration signal.
- **clientInfo** — `{ name, version, title?, ... }` the client sends. Verified names on this machine (planning probe, 2026-11-06): Claude Code 2.1.293 sends `name: "claude-code"`, `protocolVersion: "2025-11-25"`; Codex CLI 0.159.0 sends `name: "codex-mcp-client"`, `protocolVersion: "2025-06-18"`. Every other client name in this document is a substring rule, not a verified value.
- **Session-identifying message** — a JSON-RPC message from which this issue derives an `mcp_session_seen` event: an `initialize` request, or any request whose `params._meta` carries the 2026-07-28 protocol or clientInfo key.
- **Caller key** — an opaque, process-local string that ties a later `tools/call` to the client seen earlier from the same caller (dashboard: `oauthClientId ?? tokenId`; stdio and connector surfaces: a fixed per-surface string). It is never sent.
- **Usage ledger** — the file `~/.overdeck/telemetry-mcp-seen.json` (under `getOverdeckHome()`), holding the UTC day and the dedupe keys already sent that day.
- **Install** — one `~/.overdeck` with its `telemetry-id` (`src/lib/telemetry/install-id.ts`). PostHog `distinct_id` is the install id.

## Background (verified 2026-11-06)

- `packages/contracts/src/telemetry.ts` defines every event (`TELEMETRY_EVENT_NAMES`, line 4), property domains (`TELEMETRY_PROPERTY_DOMAINS`, line 120) and the catalog (`TELEMETRY_EVENT_CATALOG`, line 181). It has no MCP event.
- `docs/TELEMETRY.md` holds the event table and domain table; `tests/unit/telemetry-docs.test.ts` fails unless both tables equal the contract exactly (regexes ``^\| `([a-z_]+)` \| `([^`]*=[^`]*)` \|`` for events and ``^\| `([a-z_]+)` \| ((?:`[^`]+`(?:, )?)+) \|$`` for domains; date values such as `2026-07-28` match).
- `src/lib/telemetry/service.ts` `AnalyticsService.capture` is the only Node send door; it applies the opt-out (`resolveTelemetryEnabled`, `src/lib/telemetry/config.ts`) and blocks capture under Vitest (`telemetryBlockedForProcess`, line 51, not exported today).
- `src/lib/telemetry/instance-heartbeat.ts` is the precedent for a once-per-day event with a file under `getOverdeckHome()` written tmp + rename.
- `src/lib/telemetry/anywhere.ts` is the precedent for a capture module with injectable analytics and a `safeCapture` that swallows throws.
- SDK 1.30.1 (`node_modules/@modelcontextprotocol/sdk/dist/esm/server/webStandardStreamableHttp.js`, lines 550–561 and 774–781): for every non-`initialize` request the HTTP transport calls `validateProtocolVersion`, which answers **400** for an `MCP-Protocol-Version` header outside `SUPPORTED_PROTOCOL_VERSIONS` (`2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`, `2024-10-07`) **before** `onmessage` runs. A 2026-07-28 client never sends `initialize`, so on HTTP it is refused before any SDK hook sees it. HTTP observation must read the raw body and header before `transport.handleRequest`.
- In stateless HTTP mode (`sessionIdGenerator: undefined`, `routes/mcp.ts` line 62) every POST gets a fresh `Server`; only the `initialize` POST carries `clientInfo`, and later `tools/call` POSTs carry only the header.
- Transport interface (`dist/esm/shared/transport.d.ts`, line 79): `onmessage?: (message, extra?) => void`, assigned by `Protocol.connect`. In `tests/unit/cli/mcp.test.ts` (lines 46–53) the test writes stdin before the transport attaches, so buffered input can flow on the first tick after `connect`; a wrap installed after `connect` could miss `initialize`. The stdio hook must be installed before `connect`.
- `src/lib/mcp/connector/home.ts` never touches `~/.overdeck`, but `pan mcp connector serve` already runs inside the CLI telemetry lifecycle (`src/cli/telemetry.ts`), which reads `~/.overdeck/config.yaml`, creates `~/.overdeck/telemetry-id` and sends `cli_command_run` (verb `other`). Connector processes therefore already obey the same opt-out.
- `ALL_TOOLS` (`src/lib/mcp/server.ts`, line 43) lists every tool; the connector's `connectorTools()` is a subset with the same names.

## Repository rules that apply (restated)

- Closed enums only: no raw client name, client version, `title`, `websiteUrl`, token value, token id, OAuth client id, IP, host, path, prompt or tool argument reaches PostHog (`docs/TELEMETRY.md` "Event schema").

- No `execSync` and no blocking child-process calls in server-reachable code; the ledger uses `node:fs/promises` only.
- Telemetry must never fail or slow the caller: every capture and ledger write is wrapped, and MCP request handling never awaits telemetry.
- Delay or date tests inject a `now` function; no real waits. (Fake-timer rule: if a test needs time to pass, inject `now` or use `vi.useFakeTimers()`.)
- Quality gates per item: `npm run typecheck`, `npm run lint`, and `npx vitest run <touched test files>`; never the full `npm test` on the host.
- New lib modules must not create import cycles (`lint:circular`). `src/lib/telemetry/mcp-classify.ts` imports only `@overdeck/contracts` types.
- File-size ratchet: no touched file may grow past its `origin/main` line count cap; all touched files are well under the 1000-line ceiling.

## Decisions

- **D-1 One shared observer, two hook points.** The single code path is a new module `src/lib/telemetry/mcp.ts` (`McpUsageTelemetry`). `createOverdeckMcpServer` cannot see headers or raw messages, so: HTTP surfaces call `usage.noteRequest(label, parsedBody, protocolHeader)` before `transport.handleRequest`; stdio surfaces call `observeMcpTransport(transport, label, usage)` before `server.connect`; tool calls are recorded inside `server.ts`'s `CallToolRequestSchema` handler. This deviates from the issue's "in `server.ts`" wording because SDK 1.30.1 refuses 2026-07-28 HTTP requests before any server-level hook.
- **D-2 Emit rule.** `mcp_session_seen` comes only from a session-identifying message. A plain v1 `tools/call` (header only, no `_meta` keys) never emits a session event.
- **D-3 Protocol value.** On `initialize`: `params.protocolVersion` (requested). Otherwise: `_meta["io.modelcontextprotocol/protocolVersion"]`, else the `MCP-Protocol-Version` header, else `other`. Bucketing is exact string match against the domain; anything else is `other`.
- **D-4 Client value.** From `initialize` `params.clientInfo.name`, or `_meta["io.modelcontextprotocol/clientInfo"].name`. When a session-identifying message has no name, the tracker uses the client last remembered for the caller key, else `other`. Bucketing rules, first match wins, on `name.toLowerCase()`:

  | Order | Substring | Bucket |
  | --- | --- | --- |
  | 1 | `cursor` | `cursor` |
  | 2 | `codex` | `codex` |
  | 3 | `claude-code` or `claude code` | `claude_code` |
  | 4 | `visual studio code`, `vscode` or `vs code` | `vscode` |
  | 5 | `chatgpt` or `openai` | `chatgpt` |
  | 6 | `grok` | `grok` |
  | 7 | `hermes` | `hermes` |
  | 8 | `openclaw` | `openclaw` |
  | 9 | `gemini` | `gemini` |
  | 10 | `opencode` | `opencode` |
  | 11 | `kimi` | `kimi` |
  | 12 | `overdeck` | `overdeck_connector` |
  | — | anything else, a non-string, or a name over 200 characters | `other` |

  `opencode` and `kimi` are added to the issue's list because they are Overdeck-managed ACP harnesses that spawn `pan mcp serve` (codebase map `concerns.md`, PAN-4934 probe) and would otherwise all read `other`.
- **D-5 Auth value.** `mcp_auth` domain is `agent_token`, `oauth`, `access_token`, `connector`. Mapping: a token record or credential with a non-empty `oauthClientId` → `oauth`; else with a non-empty `agentId` → `agent_token`; else → `access_token` (Copy MCP URL / `pan token create`). Both connector surfaces → `connector`. The issue's `device` and `none` are dropped: `/mcp` answers 403 to every non-`kind: 'token'` credential (`routes/mcp.ts` lines 104–106), `pan mcp serve` refuses non-token records (`src/cli/commands/mcp.ts` lines 91–94), unauthenticated requests are refused before observation, so neither value could ever be sent. `access_token` is added because plain tokens are the common case and fit no listed value.
- **D-6 Dedupe key and scope.** At most one `mcp_session_seen` per (UTC day, surface, client, protocol, auth) per install. Auth is part of the key (the issue names surface, client, protocol) so `mcp_auth` stays accurate: one operator's Copy-MCP-URL Claude Code would otherwise hide behind managed agents' `agent_token`. Volume stays bounded: at most 4 auth values per triple per day.
- **D-7 Persistence.** Process memory is the fast path. For `dashboard_http`, `public_http` and `stdio` the tracker also reads and writes the usage ledger, because `pan mcp serve` runs one process per agent session and memory alone would send one event per session. Writes are tmp + rename; a cross-process write race may lose a key and send one duplicate, which is accepted. The connector surfaces dedupe in memory only and never write the ledger, so the connector adds no new file under `~/.overdeck` beyond what its CLI lifecycle already writes.
- **D-8 Connector surfaces do emit.** They run inside the CLI telemetry lifecycle, which already applies the `~/.overdeck` opt-out and install id; bots behind connectors are the "which bots matter" signal the issue asks for.
- **D-9 `mcp_tool_called` is presence-per-day.** At most one event per (UTC day, surface, client, tool) per install, properties `mcp_surface`, `mcp_client`, `mcp_tool`, no count. A daily count would need cross-process merging (stdio servers are separate processes), restarts would send partial counts, and `count_bucket` tops out at `11+`, which most tool-days would hit. Install-days per tool and client is the coarse signal. Unknown or hidden tool names are not recorded (the client controls that string).
- **D-10 Tool-call client.** `_meta["io.modelcontextprotocol/clientInfo"].name` on the call when present, else the caller key's remembered client, else `other`.
- **D-11 Caller keys.** Dashboard: `credential.oauthClientId ?? credential.tokenId`. `pan mcp serve`: `stdio`. Connector HTTP: `connector_http` (one shared local token). Connector stdio: `connector_stdio`. The remembered-client map holds at most 256 keys and evicts the oldest insertion.
- **D-12 Opt-out.** The tracker's `enabled()` defaults to `!telemetryBlockedForProcess() && resolveTelemetryEnabled()` and is checked after the in-memory fast path. When it returns false the tracker sends nothing and reads or writes no ledger. `telemetryBlockedForProcess` becomes an export of `service.ts`.
- **D-13 PostHog dashboard.** The PR delivers the three insight definitions in `docs/TELEMETRY.md`. Creating the "MCP usage" dashboard in PostHog project 514675 is a post-merge operator step (or an agent with the PostHog MCP server, `reference/posthog-agents.mdx`), done once events arrive.
- **D-14 Channels bridge excluded.** `src/lib/channels/overdeck-bridge.ts` is a separate MCP server for message delivery, not one of the five surfaces; it records nothing.

## Requirements

### Functional

- **FR-1** The contract defines event `mcp_session_seen` with properties `mcp_surface=mcp_surface; mcp_protocol=mcp_protocol; mcp_client=mcp_client; mcp_auth=mcp_auth`, and the domains: `mcp_surface` = `dashboard_http`, `public_http`, `stdio`, `connector_http`, `connector_stdio`; `mcp_protocol` = `2026-07-28`, `2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`, `2024-10-07`, `other`; `mcp_client` = `claude_code`, `codex`, `cursor`, `vscode`, `chatgpt`, `grok`, `hermes`, `openclaw`, `gemini`, `opencode`, `kimi`, `overdeck_connector`, `other`; `mcp_auth` = `agent_token`, `oauth`, `access_token`, `connector`.
- **FR-2** The contract defines event `mcp_tool_called` with properties `mcp_surface=mcp_surface; mcp_client=mcp_client; mcp_tool=mcp_tool`, where `mcp_tool` lists exactly the names in `ALL_TOOLS`, alphabetically, kept in step by a test.
- **FR-3** A pure classifier turns a JSON-RPC message (object or batch array) plus an optional protocol header into zero or more session facts per D-2, D-3 and D-4.
- **FR-4** The tracker sends `mcp_session_seen` at most once per D-6 key per process, and per install for persisted surfaces (D-7).
- **FR-5** Each of the five surfaces labels its traffic with the right `mcp_surface`, `mcp_auth` (D-5) and caller key (D-11).
- **FR-6** HTTP surfaces observe the parsed body and `mcp-protocol-version` header before the SDK transport, so a 2026-07-28 request that the transport refuses with 400 is still recorded.
- **FR-7** Stdio surfaces observe every inbound message, including one buffered before `connect` returns.
- **FR-8** A successful lookup in the `tools/call` handler records `mcp_tool_called` once per D-9 key.
- **FR-9** `docs/TELEMETRY.md`, `configuration/telemetry.mdx` and `configuration/mcp.mdx` describe both events, what is and is not sent, and the dedupe rules.
- **FR-10** `docs/TELEMETRY.md` defines the three PostHog insights for the "MCP usage" dashboard.

### Non-functional

- **NFR-1 Privacy.** Captured payloads contain only closed-domain values plus the standard stamped properties. A raw client name, version, `title`, `websiteUrl`, token value, token id, OAuth client id, caller key, tool argument, host name, user name or home path never appears.
- **NFR-2 Opt-out.** With `OVERDECK_TELEMETRY=0` or `telemetry.enabled: false`, no MCP event is captured and the usage ledger is neither read nor written.
- **NFR-3 No effect on MCP.** Observation adds no awaited work to request handling; a throwing analytics client or a failed ledger write never changes an MCP response.
- **NFR-4 SDK v2 durability.** The classifier reads only raw JSON-RPC fields and the header; it imports nothing from the SDK. The only SDK-bound code is the stdio `onmessage` hook and the `tools/call` handler hook, which PAN-5082 may move.
- **NFR-5 Bounded memory.** The in-memory dedupe set is cleared on UTC day change; the caller-key map holds at most 256 entries.

```ts
export interface McpUsageLabel { surface: TelemetryMcpSurface; auth: TelemetryMcpAuth; callerKey: string }
export interface McpUsageTelemetryOptions {
  analytics?: () => Pick<AnalyticsService, 'capture'>;  // default getAnalyticsService(getAnalyticsClientTypeForProcess())
  now?: () => number;                                    // default Date.now
  enabled?: () => boolean;                               // default mcpTelemetryEnabled (D-12)
  ledgerFile?: () => string;                             // default join(getOverdeckHome(), 'telemetry-mcp-seen.json')
}
export class McpUsageTelemetry {
  noteRequest(label: McpUsageLabel, message: unknown, protocolHeader?: string): void;
  noteToolCall(label: McpUsageLabel, toolName: string, params: unknown): void;
  settled(): Promise<void>; // resolves when queued ledger writes finish (tests)
}
export const mcpUsageTelemetry: McpUsageTelemetry;
/** D-12: !telemetryBlockedForProcess() && resolveTelemetryEnabled(); false on any throw. */
export function mcpTelemetryEnabled(): boolean;
export function observeMcpTransport(transport: Transport, label: McpUsageLabel, usage?: McpUsageTelemetry): void;
```

Behaviour:
1. Both note methods are synchronous, wrapped in `try/catch`, and return `void`; nothing awaits them.
2. Day = `new Date(now()).toISOString().slice(0, 10)`. When the day differs from the stored day, clear the in-memory key set and the loaded-ledger promise.
3. `noteRequest`: for each fact from `mcpSessionFacts`, if `fact.client` is defined remember it for `label.callerKey` (map capped at 256, delete the oldest key on overflow); resolve client = `fact.client ?? remembered ?? 'other'`; key = `session|${surface}|${client}|${protocol}|${auth}`; then `emitOnce(key, 'mcp_session_seen', { mcp_surface, mcp_protocol, mcp_client, mcp_auth })`.
4. `noteToolCall`: return when `toolName` is not in `TELEMETRY_PROPERTY_DOMAINS.mcp_tool`; client = `mcpRequestClient(params) ?? remembered ?? 'other'`; key = `tool|${surface}|${client}|${tool}`; `emitOnce(...)` with `mcp_tool_called`.
5. `emitOnce`: return if the key is in memory; return if `!enabled()`; add the key to memory synchronously; for connector surfaces capture now (inside try/catch) and stop. For persisted surfaces queue (via `trackAnalyticsTask`) an async step: load the ledger once per day (`readFile` + JSON parse; a missing, unparsable or other-day file reads as empty); if the key is already in the ledger, stop; else capture, then write `{ day, keys }` (re-read, union same-day keys, write `<file>.<pid>.tmp`, `rename`). Writes are serialized through one promise chain per tracker. Every failure is swallowed.
6. `observeMcpTransport` installs an accessor property `onmessage` on the transport instance **before** `connect`: when the assigned value is a function, the setter stores `(message, extra) => { usage.noteRequest(label, message); handler(message, extra); }`; when it is not a function (for example `undefined` on close), the setter stores it unwrapped. The getter returns whatever was stored.

Test `tests/unit/lib/telemetry/mcp-telemetry.test.ts` with injected `analytics`, `now`, `enabled` and a temp `ledgerFile`: one capture for two identical initializes; a second capture after `now` crosses UTC midnight; a new tracker on the same ledger file sends nothing for a key already written that day (`await settled()` first); connector surfaces never create the ledger file; `enabled: () => false` → no capture and no file; a throwing analytics client → no throw from `noteRequest`; tool call with a remembered client; unknown tool name → no capture; `observeMcpTransport` sees a message the transport delivers right after the handler is set; with `VITEST` and `NODE_ENV` cleared (restored in `afterEach`) and `OVERDECK_TELEMETRY=0`, `mcpTelemetryEnabled()` returns false and a tracker using the default `enabled` captures nothing and creates no ledger file (NFR-2).
