# PAN-2168 — Global navigation affordance to Flywheel openQuestions from anywhere

**Issue:** [PAN-2168](https://github.com/eltmon/overdeck/issues/2168) ·
feat(dashboard): global navigation affordance to Flywheel openQuestions from anywhere

## Glossary

- **openQuestions** — `FlywheelStatus.openQuestions: ReadonlyArray<string>`
  (`packages/contracts/src/flywheel.ts:224`, schema `:243`). Non-blocking
  decisions the orchestrator wants the operator to weigh in on. Emitted every
  tick by `pan flywheel emit-status`.
- **App bar** — the global top strip rendered on every route by
  `App/AppChrome.tsx` (the `<div … h-12 …>` at `AppChrome.tsx:164`). Its
  right-side group (`AppChrome.tsx:190-226`) holds existing system indicators
  (`DeaconPauseToggle`, running-agent pill, `StoppedAgentsBanner`,
  `LowCostModePill`, `SystemHealthPill`, `SystemMenu`).
- **Flywheel status tab** — the default left-rail tab of `pages/FlywheelPage.tsx`
  (`FlywheelLeftTab` defaults to `'status'`, `FlywheelPage.tsx:294`) that renders
  `FlywheelStatusDetails`, which contains the "Open Questions for the Next Tick"
  section (`FlywheelStatusDetails.tsx:271-279`).
- **`subscribeFlywheelStatus`** — RPC subscription helper
  (`lib/wsTransport.ts:283`) that streams `FlywheelStatus | null` over `/ws/rpc`.
- **`/api/flywheel/current`** — REST endpoint returning the latest
  `FlywheelStatus | null` (used to seed `FlywheelPage`, `FlywheelPage.tsx:59-63`).

## Problem

`FlywheelStatus.openQuestions[]` is only visible on the Flywheel status surface.
The operator has no way to jump to openQuestions from anywhere in the dashboard,
so time-sensitive decisions (e.g. releasing MIN merges blocked on the per-project
UAT gate) sit unseen until they happen to open the Flywheel page.

## Proposal

Add a persistent, global indicator to the app bar's right-side status group
(`AppChrome.tsx:190-226`) that:

1. Shows a count badge of currently-open questions from the latest
   `FlywheelStatus` snapshot. Hidden when 0; visible when >0 (AC1).
2. On click, navigates to the Flywheel tab and reveals the openQuestions list
   with each question's full text (AC2).
3. Updates live as new snapshots arrive over `/ws/rpc` (AC3).
4. Conforms to `pan-style-guide`: no pill (`rounded-full`) status badge, no
   `font-bold`/`font-semibold`, color-signal = operator-attention =
   `--warning` (amber; "a human must act") with the 8% bg / 32% border tint
   formula (AC4).

### Data path (presentation only — no new data path)

The indicator subscribes to live flywheel status the same way `FlywheelPage`
does (`FlywheelPage.tsx:373-395`): seed once from `/api/flywheel/current`, then
apply pushes from `subscribeFlywheelStatus`, with a periodic refetch of
`/api/flywheel/current` so a restart/replay can't strand a stale value. Count =
`status?.openQuestions.length ?? 0`. When the endpoint returns `null` (no
current run), count is 0 → indicator hidden.

### Reveal mechanism

A small shared signal module decouples the indicator from the Flywheel page so
neither imports the other:

- `lib/flywheelReveal.ts` — exports `requestRevealOpenQuestions()`,
  `consumePendingReveal(): boolean`, and `subscribeRevealOpenQuestions(cb): () => void`.
  Implemented as a sticky-pending boolean plus a listener set (no `window`
  magic-string duplication).
- Indicator `onClick` → `requestRevealOpenQuestions()` then the `onActivate`
  callback (navigate to the Flywheel tab via `setActiveTab('flywheel')`).
- `FlywheelPage` consumes the signal: on mount, if `consumePendingReveal()` is
  true, reveal; while mounted, `subscribeRevealOpenQuestions` handles the
  already-on-page case. "Reveal" = force the left tab to `'status'` and
  `scrollIntoView` the openQuestions section (anchored by a new
  `id="flywheel-open-questions"` on its `Section`).

Because `AppRoutes` remounts `FlywheelPage` on each navigation and its left tab
defaults to `'status'` (`FlywheelPage.tsx:294`), a cold navigation already
renders the openQuestions list; the reveal signal additionally forces the status
tab + scroll for the warm (already-on-Flywheel) case.

## Requirements

- **FR-1:** A global indicator in the app bar shows the open-question count when
  >0 and is hidden when 0, on every dashboard route.
- **FR-2:** Activating the indicator navigates to the Flywheel tab and reveals
  the openQuestions list (status tab active, section scrolled into view), showing
  each question's full text.
- **FR-3:** The indicator reflects the latest `FlywheelStatus` snapshot live —
  a new `subscribeFlywheelStatus` push updates the count with no reload.
- **NFR-1:** Styling passes `pan-style-guide`: no `rounded-full` status badge,
  no `font-bold`/`font-semibold`, color-signal = `--warning` (operator
  attention), badge tint = 8% bg / 32% border.
- **NFR-2:** No new server data path — reuse `subscribeFlywheelStatus` and
  `/api/flywheel/current`.

## Planning Q&A

This issue was planned in `--auto` mode; no interactive questions were asked.
Defaults chosen (also recorded in `plan.autoDecisions[]`):

- **Placement** → app bar right-side status group (`AppChrome.tsx:190-226`),
  matching the issue's suggested placement and where every other global system
  indicator already lives.
- **Color signal** → `--warning` (amber). The style-guide table maps "a human
  must act / awaiting approval" to amber; an open question is exactly that. The
  issue's "needs-you / attention" maps here.
- **Reveal target** → existing "Open Questions for the Next Tick" section in the
  Flywheel status tab, not a new drawer. Reuses the surface that already renders
  full question text; smallest change that satisfies AC2.
- **Paused-run handling** → count derives from the latest snapshot;
  `/api/flywheel/current` returns `null` when paused, zeroing the indicator on
  the next refetch. The indicator does not add a separate run-lifecycle query
  (kept minimal). See hazard H1.
- **Decouple via signal module** → a tiny `flywheelReveal.ts` rather than a
  `window` CustomEvent inline, to avoid duplicating an event-name string across
  two components and to make the reveal contract unit-testable.

## Non-goals

- No change to how openQuestions are produced or emitted (server/orchestrator
  untouched).
- No new dedicated openQuestions drawer/route — reuse the Flywheel status tab.
- No badge in the left `Sidebar` (the issue asks for the top app bar).
- No mark-as-read / dismissal / persistence of individual questions.
- No change to the existing `flywheel-live` sidebar nav badge.
