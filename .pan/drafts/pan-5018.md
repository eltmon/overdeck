# PAN-5018: Phone app link to a paired machine fails with "Could not open a secure channel"

**Issue:** https://github.com/eltmon/overdeck/issues/5018
**Found during:** PAN-4841 (store builds). Code from PAN-4837, PAN-4927, PAN-2356.
**Planning mode:** `pan plan --auto` (no operator questions; defaults are recorded under "Decisions").

## Glossary

- **Machine:** a computer that runs Overdeck. Here it is `eltmon-z790`, environment id `e91ffda1…`.
- **Phone:** the Capacitor app `apps/mobile` ("Overdeck Anywhere"). It is a directory *client*, with a client id (here `98bd79fd…`).
- **Directory:** the overdeck.ai Worker `services/connect`. One Durable Object per account. It forwards `signal` frames between phone and machine and answers `ice-servers` requests.
- **Directory client (machine):** `DirectoryClient` in `src/dashboard/server/services/directory-client.ts`. One WebSocket from the dashboard to the directory.
- **Signal frame:** a directory frame that carries a WebRTC offer, answer or ICE candidate for one *session* (a random 32-hex id the initiator picks per peer connection).
- **RtcTransport:** `src/lib/anywhere/channel/rtc-transport.ts`. The machine's WebRTC layer (werift 0.25.1). As responder it creates a peer connection when an offer arrives (`accept`). Its first step is `requestIceServers`, which sends an `ice-servers` frame to the directory.
- **Machine dialer (phone):** `createMachineDialer` in `packages/anywhere-channel/src/dial-machine.ts`. Keeps one `RTCPeerConnection` per (machine, relay) and opens one more `ovdl` data channel on it per dial. A dial on an existing connection sends no offer.
- **Raw channel:** an open `ovdl` data channel, before the secure handshake.
- **Secure channel / handshake:** the Noise handshake that runs on a raw channel. Phone side: `openSecureChannel` → `packages/anywhere-channel/src/initiator.ts`. Machine side: `acceptChannel` in `src/lib/anywhere/channel/accept.ts`, called by the channel listener `src/dashboard/server/channel-listener.ts`.
- **Mode:** the handshake mode in the preamble: `link` (Noise IK, pinned keys), `pairing` (XXpsk0 with an `odp_` code) or `approval`.
- **`ChannelOpenError` code (phone):** `unreachable | timeout | aborted | unknown-peer | pairing-refused | identity-refused | unsupported | busy | protocol` (`packages/anywhere-channel/src/initiator.ts`, line 43).
- **`ChannelAcceptError` code (machine):** `timeout | bad-preamble | unsupported | unknown-peer | pairing-refused | approval-refused | handshake-failed | closed` (`accept.ts`, line 42).
- **Zombie peer connection:** a phone peer connection whose state still reads `connected` but whose machine side is gone (closed, replaced or restarted). A new data channel on it opens locally, but nothing answers the handshake.
- **Simulator scenario:** the reproduction run defined in WI-8, on the Mac rig iOS Simulator (`apps/mobile/README.md`, "Run in the iOS Simulator").

## Problem

On a real iPhone (TestFlight 1.0 (1)), pairing with `eltmon-z790` works, but every later link fails with "Could not open a secure channel to eltmon-z790." The operator has uninstalled the TestFlight app until the problem is fixed and proven on the iOS Simulator on the Mac rig.

### Evidence (from the issue and its comment)

1. Directory tail, 12:13:14 and 12:14:29 UTC: the phone sent an offer plus candidates (5 `signal` frames each). The directory logged `forwarded` to `e91ffda1…` for each one.
2. The machine sent nothing back: no `ice-servers` request (the responder's first step) and no `signal` frame. In the same minutes it sent `push` frames that the directory `delivered`, so its socket and `DirectoryClient.send` worked.
3. 12:15:16 a `pan reload` restarted the dashboard. 12:15:25 the phone offered again, and 12:15:26 the machine requested `ice-servers` and answered. The old process (up since about 11:27 UTC) silently did not answer.
4. The machine's `dashboard.log` has no `[anywhere] channel refused` line.

### What the code shows (verified 2026-11-04 against `180d15a55fd`)

- `apps/mobile/src/shell/connection.ts`, `dialRaw` (line 101): a failed direct dial becomes `no-path` ("No direct path …") or, after a failed relay dial, `unreachable` ("Could not reach … directly or through the relay"). The text "Could not open a secure channel" comes **only** from `channelError` (line 69, default branch at line 85), which `secure()` (line 132) calls when `openSecureChannel` fails **after the raw channel opened**. So at least some of the failures the operator saw had an open raw channel and a failed handshake. With no new offer answered, the only way to get an open raw channel is a dial that reused an existing peer connection (`dial-machine.ts` line 257: `entry.pc.createDataChannel(...)` on a reused entry). That fits the zombie peer connection picture.
- `dial-machine.ts` `awaitOpen` (line 195) closes the peer connection on failure only when the dial created it (`ownsEntry && !entry.everOpen`, line 211). A reused connection is never evicted on a failed dial, and a handshake failure is not seen by the dialer at all. So a zombie connection is reused by every dial until its state changes or `forgetRoutes()` runs. This makes the failure sticky ("every later link fails").
- `channelError` maps `timeout`, `busy`, `protocol`, `aborted` and `unreachable` to the same text, so the phone cannot say which happened.
- `rtc-transport.ts` `onSignal` (line 235) swallows every exception (`catch { … }` at line 247) and returns silently on three branches: a known session whose `peer` differs or which is `closed` (line 240), and a first frame that is not an offer (line 245). Nothing is logged on any branch.
- `channel-listener.ts` `accept` (line 136, catch at line 157): `if (code !== 'closed' && code !== 'timeout') log(...)`. A `closed` or `timeout` refusal leaves no trace. Worse, `accept.ts` `toAcceptError` (line 236) maps **every unexpected exception** (anything that is neither a `ChannelAcceptError` nor a `WireError`) to code `closed`, so a real bug inside the handshake is also silent.
- `directory-client.ts` logs nothing: not reconnects, not refusals (including close 4011 `replaced`, "Another Overdeck process registered this machine with the directory"), not frames that arrive on a socket that is no longer current (`socket.on('message', …)` at line 267 drops them).

The cause of evidence 2 (a long-running machine process that does not answer offers) cannot be proven by reading the code. The operator's instruction is: fix the problems first, prove them on the iOS Simulator, then ask for phone tests. So this plan (a) makes every layer say what happened, (b) removes the sticky zombie-connection failure on the phone, (c) reproduces the failure on the Simulator against a machine running this branch with the new logs, and (d) fixes the cause the logs show, with a regression test.

## Requirements

### Functional

- **FR-1** The phone logs every failed dial and every failed secure-channel open with the `ChannelOpenError` code (or `ConnectionError` kind), the message, the machine label, the route (`direct` or `relay`) and whether the dial reused an existing peer connection.
- **FR-2** When the phone web bundle is built with `VITE_OVERDECK_DEBUG_ERRORS=1`, the on-screen text of a failed link ends with ` (<code>)`, for example "Could not open a secure channel to desk. (timeout)". Without that flag the text is unchanged.
- **FR-3** When a link-mode or pairing-mode secure open fails with `timeout` or `protocol` on the phone, the phone closes its peer connections to that machine and forgets the remembered route, so the next dial sends a fresh offer.
- **FR-4** `acceptChannel` errors carry the handshake mode once the preamble is parsed (`null` before), and an unexpected exception inside the handshake gets the new code `internal` instead of `closed`.
- **FR-5** The channel listener logs every refusal with its code, mode and message. `closed` and `timeout` refusals are logged only when `OVERDECK_ANYWHERE_DEBUG=1`; every other code, including `internal`, is always logged.
- **FR-6** `RtcTransport` logs, always, one line per offer it receives (peer, session, purpose, route) and one line for its outcome: `answered`, `dropped: <reason>` or `failed at <step>: <message>`. It logs, always, each peer connection state change to `connected`, `failed` or `closed`. It logs dropped candidates and answers only when `OVERDECK_ANYWHERE_DEBUG=1`.
- **FR-7** `DirectoryClient` logs, always, each transition: `online` (welcome), socket closed with code, refusal with message, pong-timeout drop, account change. With `OVERDECK_ANYWHERE_DEBUG=1` it also logs each `signal` frame it receives (from, session, sdp type or candidate) and each message that arrives on a socket that is no longer current.
- **FR-8** On the iOS Simulator on the Mac rig, a phone paired with a machine that runs this branch links successfully after the Simulator scenario (WI-8). The run is recorded in `apps/mobile/ACCEPTANCE.md`.
- **FR-9** The cause that WI-8 identifies is fixed, and a regression test reproduces the faulty state, fails on the pre-fix code and passes after the fix.
- **FR-10** The docs describe the new log lines, `OVERDECK_ANYWHERE_DEBUG` and `VITE_OVERDECK_DEBUG_ERRORS`.

### Non-functional

- **NFR-1** No log line contains SDP text, ICE candidate strings, keys, tokens, pairing codes or plaintext. Ids are cut to their first 8 characters. (The directory smoke already asserts "no Worker log line carries the marker or SDP text"; the machine logs follow the same rule.)
- **NFR-2** Always-on lines are bounded by real events: one per offer, one per outcome, one per connection state change, one per directory transition. No always-on line per candidate or per data-channel message.
- **NFR-3** No `execSync` in server-reachable code; no new sync tmux calls (repo rules). All new logging is synchronous `console.warn` only.
- **NFR-4** Tests that wait on time use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()` (repo rule "fake timers for retry/backoff/delay tests"). Exception: `rtc-transport.test.ts` runs real UDP I/O on loopback and keeps real timers, as its header says.
- **NFR-5** No file grows past the file-size ratchet (`scripts/lint-file-size.sh`, ceiling 1000 lines; every touched file is under 450 lines today).

## Decisions

- **D-1 (auto)** Diagnose first, then fix. The issue and the operator comment both say this. The root-cause item (WI-9) runs only after the logs exist and the Simulator scenario has run.
- **D-2 (auto)** "Debug build" for the on-screen code means the web bundle flag `VITE_OVERDECK_DEBUG_ERRORS=1`, read in `apps/mobile/src/shell/config.ts` like `VITE_OVERDECK_REQUEST_LOG`. Reason: the Xcode Debug/Release configuration does not reach the Vite bundle, and the only native signal (`OverdeckKeys.pushEnvironment()`) is async and iOS-only. A build-time flag is deterministic and testable.
- **D-3 (auto)** Machine debug lines are gated by the environment variable `OVERDECK_ANYWHERE_DEBUG=1`, read through one helper `src/lib/anywhere/debug-log.ts`. Overdeck has no log-level system today (`grep -rn OVERDECK_DEBUG src` finds nothing in these modules). Reason for a gate: the link supervisor's phased probing aborts losing channels, so `closed` refusals happen in normal operation and would flood the log.
- **D-4 (auto)** Per-offer, per-outcome and per-state-change RTC lines and directory transitions are always on (FR-6, FR-7). Reason: the failure appears only in a process that has run for a long time, so a debug flag set after the fact would miss it. These events are rare (NFR-2).
- **D-5 (auto)** The phone evicts the peer connection on a handshake `timeout` or `protocol` failure (FR-3), not on a definitive refusal (`unknown-peer`, `pairing-refused`, `identity-refused`, `unsupported`) and not on `busy`. Reason: a raw channel that opened but got no handshake reply means the connection under it is suspect; a refusal proves the machine is alive and answering. Cost: other channels to that machine on the same connection close and the shims reconnect, which is the right result for a zombie connection.
- **D-6 (auto)** The new accept code is `internal` (FR-4). It is a new member of `ChannelAcceptErrorCode`. Only `accept.ts` and `channel-listener.ts` read the code (`grep -rn ChannelAcceptError src`), and the listener logs every code except `closed` and `timeout`, so `internal` is logged without more changes.
- **D-7 (auto)** The Simulator scenario runs against a peer test dashboard built from this branch, with its own `OVERDECK_HOME`, not against the operator's live `eltmon-z790` dashboard. Reason: the operator's dashboard runs `main`; this branch's logs and fixes must be on the machine side of the test. Setup facts (from project memory `live-fly-check-test-home`): separate HOME with symlinks to the real `~/.claude`, `~/.config` and `~/.gitconfig`; start the server through a symlink whose path does not contain `dist/dashboard/server.js` (the host orphan reaper kills such processes after 120 s); set `OVERDECK_ANYWHERE_SUPERVISOR=1` so the peer dashboard hosts machine links (`src/lib/boot-gates.ts` line 47).
- **D-8 (auto)** If the overdeck.ai sign-in on the test dashboard or in the Simulator app needs credentials, the work agent asks the operator once (the operator types credentials only; the agent does every other step). This is the only operator step.
- **D-9 (auto)** The Worker (`services/connect`) is not changed. If the machine logs prove that forwarded offers never reach the machine's `RtcTransport`, the work agent files a follow-up issue for a Worker-side delivery count instead of deploying the Worker from this issue.
- **D-10 (auto)** If the Simulator scenario does not reproduce the failure, WI-9 records the evidence and ships WI-1 to WI-7 without a speculative fix (see WI-9 fallback). The PR then says `Refs PAN-5018`, not `Fixes`, so the issue stays open for the next phone test.
