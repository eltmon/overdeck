# PAN-4221 — Recover a review that was never dispatched after a verification pass

**Issue:** [PAN-4221](https://github.com/eltmon/overdeck/issues/4221)
**Status:** planned (auto mode, 2026-09-26)

## Problem

On 2026-09-25, PAN-4198, PAN-4199, PAN-4200 and PAN-4201 all ended with
`verification.passed` as the last entry of their pipeline journal. Each
verification worker (a detached child process) finished and logged
`Verification passed … proceeding to review-agent`, but no review was ever
dispatched. The PRs sat green for about 15 hours and the merge train had
nothing to carry.

The dashboard restarted (deploys) while the workers ran. The "push the branch,
then dispatch the review" continuation lives in the dashboard process
(`requestReviewPipeline` in `src/lib/cloister/request-review-pipeline.ts`,
awaiting `runSupervisedVerification`). It died with the old process. Nothing
picks up a finished worker's result after a restart, and deacon-lite skips any
issue whose last journal entry is `verification.*` on purpose
(`src/lib/cloister/deacon-lite.ts`, the "ACCEPTED v1 GAPS" block). That skip is
right for `verification.failed` (the agent owes rework) and wrong for
`verification.passed` (Overdeck owes a review).

## Glossary

- **Pipeline journal** — `<workspace>/.overdeck/pipeline.jsonl`, the append-only
  per-issue log of what Overdeck did (`src/lib/cloister/pipeline-journal.ts`).
  It is never authority: where it disagrees with the PR, the PR wins.
- **Tail** — the last entry of the journal (`lastPipelineEntry(workspacePath)`).
- **Verification worker** — the detached `dist/verification-worker.js` child
  that runs the quality gates. Its state and result files live under
  `~/.overdeck/verification-workers/<issue-lowercase>/` (`state.json`,
  `result-<runId>.json`). The worker itself writes the `verification.*`
  journal entries (it runs `runVerificationForIssueInProcess`).
- **Supervisor** — `runSupervisedVerification` in
  `src/lib/cloister/verification-worker-supervisor.ts`: the dashboard-process
  code that launches the worker and polls for its result file.
- **Guarded review route** — `POST /api/review/:issueId/request` without
  `force`/`nudge` (`requestReviewGuarded` in
  `src/dashboard/server/routes/workspaces/review-pipeline.ts`). It refuses a
  merged issue, never re-reviews an approved head, counts requests against the
  per-issue breaker (`MAX_AUTO_REQUEUE` = 25), refuses a dirty tree, coalesces
  with an in-flight pipeline, journals `review.requested`, re-runs
  verification, pushes, and dispatches the review.
- **`requestReviewThroughRoute`** — `src/lib/cloister/review-request-route.ts`:
  the HTTP client for the guarded review route, carrying the internal token.
  It is the only review door that works from the deacon child.
- **Deacon child** — `dist/dashboard/deacon.js` (`src/dashboard/server/deacon-main.ts`).
  Cloister and deacon-lite run only there, never in the dashboard process
  (`docs/DASHBOARD-ARCHITECTURE.md` line 19). The in-process review starter
  registry (`getRequestReviewStarter()`) is always `null` in this child.
- **Primary head8** — the first 8 chars of the verified sha of the workspace's
  primary repo. For a monorepo that is the workspace HEAD. For a polyrepo it
  is the sha of `resolveWorkspaceRepoRoots(...)[0].repoKey` inside the
  composite anchor from `snapshotWorkspaceHeads`. `verification.passed` stores
  it as `data.head`.
- **Quick review** — review mode `quick` (the default from `resolveReviewMode`).
  It spawns only the parent `agent-<issue>-review` and writes NO
  `review.dispatched` entry. So while a healthy quick review runs, the tail
  stays `verification.passed`.
- **Recovery source allowlist** — the `verification.passed` entry's `source` is
  the runner's `logPrefix`: `request-review` (the `startRequestReviewPipeline`
  door: `pan done`, `pan review request`, webhook, deacon-lite), `review` (the
  dashboard `/trigger` button route), or `merge-verify` (the post-rebase merge
  gate in `routes/workspaces/merge-ops.ts`).

## Requirements

### Functional

- **FR-1** — When an issue's journal tail is `verification.passed`, the
  recovery routine re-requests the review through the guarded review route
  (`requestReviewThroughRoute`, `source: 'deacon-lite'`) only when ALL hold:
  1. the tail `source` is exactly `request-review` (allowlist, see D3);
  2. the tail is at least `UNDISPATCHED_REVIEW_MIN_AGE_MS` = 5 minutes old;
  3. the tail's `data.head` is a non-empty string equal to the workspace's
     current primary head8 (a missing or unreadable head skips);
  4. `isVerificationWorkerActive(issueId)` is false;
  5. the live inventory is readable and has no pane whose agent id is exactly
     `agent-<issue-lowercase>-review` or starts with `agent-<issue-lowercase>-review-`;
  6. `getIssuePause(issueId).status === 'unpaused'`;
  7. the configured review mode is not `none`;
  8. the per-issue in-memory cooldown (1 hour) has passed;
  9. fewer than `UNDISPATCHED_REVIEW_ATTEMPT_CAP` = 3 `review.requested`
     entries with `source: 'deacon-lite'` exist after the last
     `review.requested` entry with any other source.
- **FR-2** — A `verification.failed` or `verification.started` tail, and a
  `verification.passed` tail whose source is `review` or `merge-verify`, are
  never acted on.
- **FR-3** — Across repeated patrol ticks for one stalled issue, the review is
  requested exactly once per cooldown window. A request the route refuses is
  not retried before the cooldown ends.
- **FR-4** — When the attempt cap (FR-1.9) is reached, the routine logs one
  `[deacon-lite]` warning and one warn-level activity entry for that issue per
  process, and takes no further action.
- **FR-5** — The routine runs in `runDeaconLite()`, so the first patrol at
  deacon start (dashboard boot) already covers issues stalled before the
  restart.
- **FR-6** — `readVerificationWorkerState` matches the `issueId` in
  `state.json` case-insensitively, so `isVerificationWorkerActive('PAN-1')`
  sees a worker whose state file says `pan-1`.
- **FR-7** — One exported helper computes the primary head8 from a head
  anchor. The verification runner and the recovery routine both use it.

### Non-functional

- **NFR-1** — No new stored state. The routine reads the journal, the worker
  state/result files, the inventory and the pause gate. The only thing it
  causes to be written is the route's own `review.requested` entry.
- **NFR-2** — No GitHub or tracker call from the routine itself. The guarded
  route owns every forge check.
- **NFR-3** — Tests use `vi.useFakeTimers()` and `vi.setSystemTime()`, never
  real delays (repo rule: fake timers for delay-based tests).
- **NFR-4** — No `execSync`. Head reads use the existing async
  `snapshotWorkspaceHeads`.
- **NFR-5** — No file crosses the 1000-line ceiling of
  `scripts/lint-file-size.sh`. The routine lives in its own module, like
  `deferred-handoff.ts`.

## Decisions

- **D1 — Dispatch door: the guarded review route, which re-verifies.**
  The deacon child cannot reach the in-process pipeline, and
  `requestReviewThroughRoute` is the established child-safe door
  (`rerequestHaltedReview` uses it). Re-running verification is correct, not
  waste: after hours of stall, `main` has moved, and verification syncs the
  target branch first. The route journals `review.requested` on acceptance,
  which moves the tail and makes the next tick skip the issue. Verification
  workers already queue through CPU admission, so recovering several issues
  at boot does not start a CPU storm. A skip-verification door would be a new
  mutation surface in a 960-line route file; it is a non-goal.
- **D2 — One mechanism covers both fix bullets of the issue.** Deacon-lite's
  first patrol runs when the deacon child starts, so boot is covered. The
  worker writes `verification.passed` in the same run, just before it writes
  `result-<runId>.json`, so the journal entry is the worker's finished-result
  record. The live-worker check (`isVerificationWorkerActive`) reads the
  supervisor's `state.json` and tests for the result file, which is the
  "re-read `result-*.json`" evidence. A worker that outlives the restart and
  then FAILS delivers its own feedback (`deliverVerificationFeedback` runs
  inside the worker), so there is no gap on the failure side. No second
  dispatch path is built, because exactly-once is much simpler with one door.
- **D3 — Source allowlist is `request-review` only.** `merge-verify` passes
  belong to the merge door. A `review` (dashboard `/trigger`) pass may have
  been launched with a per-run review mode (`none`/`quick`/`full`) that the
  guarded route cannot reproduce, so recovering it could override the
  operator's choice. The `/trigger` path is operator-driven and visible as a
  pending operation, so the operator can click again.
- **D4 — A live review parent blocks recovery.** Quick mode writes no
  `review.dispatched`, so the tail stays `verification.passed` during a
  healthy quick review. The existing lane-only rule
  (`agent-<issue>-review-` prefix) from `recoverStalledReviews` is wrong here;
  the parent `agent-<issue>-review` must count as live.
- **D5 — Min age 5 minutes, cooldown 1 hour, cap 3.** Five minutes is "older
  than a few minutes" and well past a normal push-and-dispatch. A slower
  in-progress dispatch is still covered: the route answers `already-running`
  while the dashboard's in-flight guard holds. One hour matches the existing
  `STALLED_REVIEW_COOLDOWN_MS`. The cap of 3 matches
  `SYNTHESIS_REDISPATCH_CAP` and stops an hourly re-verify loop when every
  dispatch comes back gated (for example a conflict-gated branch whose
  verification keeps passing). A request from any other source resets the
  count.
- **D6 — Review mode `none` skips.** With mode `none`,
  `spawnReviewRoleForIssue` returns success without spawning anything and
  nothing is journaled, so the tail stays `verification.passed` forever.
  Without this rule, recovery would re-verify every hour until the cap.
  The routine reads the mode through `resolveReviewMode()`, loaded by dynamic
  import (review-agent.ts is heavy).
- **D7 — Head check uses the primary head8.** Comparing the wrapper repo HEAD
  never matches on a polyrepo. The runner's derivation moves into
  `src/lib/cloister/verified-head.ts` so the two sides cannot drift.

   ```ts
   /**
    * The primary repo's verified sha (PAN-4221). A polyrepo anchor is a
    * composite `repo@sha …` snapshot, so slicing it yields garbage: resolve the
    * primary repo's sha out of it. The verification runner stamps
    * `verification.passed.data.head` with this; deacon-lite compares against it.
    */
   import { parseCompositeSnapshot, snapshotWorkspaceHeads } from '../git-utils.js';

   export function primaryShaFromAnchor(anchor: string | undefined, primaryRepoKey: string | undefined): string | undefined {
     if (!anchor) return undefined;
     const composite = parseCompositeSnapshot(anchor);
     if (composite.size === 0) return anchor;
     return (primaryRepoKey && composite.get(primaryRepoKey)) ?? [...composite.values()][0];
   }

   /** The workspace's current primary head8, or undefined when git cannot say. */
   export async function readPrimaryHead8(issueId: string, workspacePath: string): Promise<string | undefined> {
     const anchor = await snapshotWorkspaceHeads(issueId, workspacePath);
     const { resolveWorkspaceRepoRoots } = await import('../project-repos.js');
     const primary = resolveWorkspaceRepoRoots(issueId, workspacePath)[0]?.repoKey;
     return primaryShaFromAnchor(anchor, primary)?.slice(0, 8);
   }
   ```

## Non-goals

- A skip-verification dispatch door (re-verification is intended, D1).
- Re-attaching the dashboard supervisor to a still-running worker after boot
  (D2: the journal path covers it after the worker finishes).
- Recovering a `review` (dashboard `/trigger`) or `merge-verify` pass (D3).
- Fixing the dead `getRequestReviewStarter()` fallback in
  `recoverStalledReviews` (always `null` in the deacon child). Recorded as a
  hazard; a follow-up issue should switch it to `requestReviewThroughRoute`.
- Recovering a dead quick-mode reviewer, or a partly-verdicted convoy (the
  existing accepted gaps).
- Any new journal entry type.
