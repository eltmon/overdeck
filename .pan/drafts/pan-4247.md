# PAN-4247 — Messages routed into a running subagent, joined messages, and "Sent · waiting for transcript" forever

**Issue:** [PAN-4247](https://github.com/eltmon/overdeck/issues/4247)
**Planning mode:** `pan plan --auto` (no operator Q&A; defaults recorded under "Decisions").

## Glossary

- **Main transcript** — the Claude Code session JSONL at `~/.claude/projects/<encoded-cwd>/<sessionId>.jsonl`, resolved by `sessionFilePath(workspace, sessionId)` in `src/lib/runtimes/storage/claude-code.ts`.
- **Sidechain / subagent transcript** — `<sessionFile minus .jsonl>/subagents/agent-<agentId>.jsonl`, with metadata in `agent-<agentId>.meta.json` (`description`, `agentType`, `toolUseId`, `requestShape: "background"`). Directory helper: `subagentsDirFor()` in `src/dashboard/server/services/conversation/subagents.ts:35`. Every record carries `isSidechain: true`.
- **Human sidechain input** — a sidechain record with `type: "user"`, `isSidechain: true`, `origin: { kind: "human" }`. Claude Code writes one when it routes operator-typed input into a subagent. Its `message.content` is a string wrapped like this (verified in conv 2942's `agent-a87bd589c7d68d29a.jsonl`, line 167):
  ```
  The user sent a new message while you were working:
  <operator text>

  This is how Claude Code surfaces messages the user sends mid-turn — …
  ```
  Other `origin.kind` values seen in real subagent files — `coordinator`, `peer`, `task-notification`, and records with no `origin` — are NOT operator input and must never match.
- **Mid-turn main delivery** — when the main agent is busy, Claude Code writes a `{"type":"queue-operation","operation":"enqueue","content":"<text>"}` record immediately, and later an `{"type":"attachment","attachment":{"type":"queued_command","prompt":"<text>","commandMode":"prompt",…}}` record when the queued input is consumed. Neither is a `type: "user"` record.
- **Task-notification wake** — a main-transcript user record whose text starts with `<task-notification>`. Claude Code writes it when a background subagent reports; the main agent then produces assistant records that have nothing to do with a just-delivered message.
- **Optimistic bubble** — a composer-store `ChatMessage` with id `optimistic-<clientMessageId>`, created by `addOptimistic` in `src/dashboard/frontend/src/lib/composerStore.ts:379`. `deliveryState` is `'pending' | 'accepted' | 'unknown'` (`chat-types.ts:21`). `acknowledged: true` + `deliveryState: 'accepted'` renders "Sent · waiting for transcript" (`messageRows.tsx:59`).
- **Echo reconciliation** — `reconcileComposerEchoes()` in `src/dashboard/frontend/src/lib/composerEchoes.ts:18`, driven by `useComposerEchoes()` in `src/dashboard/frontend/src/components/chat/useComposerEchoes.ts`. It removes an optimistic or failed-prompt entry when a main-transcript `role: 'user'` message matches its `clientMessageId`, or its normalized text with `createdAt >= local.createdAt`.
- **Failed outbox** — `failed: FailedMessage[]` in the composer store, rendered with Retry/Discard at `MessagesTimeline.tsx:633-667`.
- **Landing** — the outcome of transcript confirmation after a `pan tell` delivery: `main`, `subagent`, or `none`.

## Problem (verified evidence)

Conversation 2942 (`20260927-3978`), main transcript `~/.claude/projects/-home-eltmon-Projects-overdeck/96c91ded-4801-404a-9a21-1a5ce425bbf1.jsonl`:

1. **Input routed into a subagent.** Four inputs sent while background agent `a87bd589c7d68d29a` ("Draft and file title/summary issue") was alive exist ONLY in `subagents/agent-a87bd589c7d68d29a.jsonl` lines 167, 185, 197, 201 as human sidechain inputs. The main transcript has no records at all between 09:20 and 09:22:51. One input was a `pan tell` from conv 20260923-7019, and `pan tell` printed "turn confirmed".
2. **Why `pan tell` said "turn confirmed".** `waitForTranscriptMessageLanding()` (`src/lib/agents/delivery.ts:785`) returns true on `result.matchedUserRecord || (result.realAssistantTurnCount ?? 0) > 0` (line 797). The subagent's task-notification landed in main at 09:22:51 (line 1639) and the main agent answered at 09:22:58 (line 1641), inside the 30 s window, so an unrelated assistant turn counted as confirmation.
3. **Joined messages.** Two dashboard sends ("Ah ok that was it", "I was sending to a subagent wasnt I?") appear in main as ONE `queue-operation` enqueue (line 1702) and one `queued_command` attachment (line 1711) with text `Ah ok that was itI was sending to a subagent wasnt I?` — no separator. The parser renders the attachment as a user message (`parser.ts:545-572`), which matches neither bubble.
4. **Waiting forever.** `useComposerEchoes` only times out bubbles that are NOT acknowledged (`markDeliveryUnknown`). An acknowledged bubble that never matches shows "Sent · waiting for transcript" with no end.

## Requirements

- **FR-1** Transcript confirmation treats a `queue-operation` enqueue `content` or a `queued_command` attachment `prompt` that contains the message as a main landing.
- **FR-2** Transcript confirmation does not count assistant records whose nearest preceding user record after the probe offset is a task-notification wake.
- **FR-3** Transcript confirmation detects a human sidechain input containing the message in any `subagents/agent-*.jsonl` written after the pre-delivery snapshot, and reports landing `subagent` with the subagent's `agentId` and `description`.
- **FR-4** When the landing is `subagent`, delivery does not attempt a second delivery.
- **FR-5** `pan tell` whose message landed in a subagent exits 1 and prints that the message went to the named subagent, never "turn confirmed".
- **FR-6** The conversation subagent list (`SubagentSummary`) carries `background` and the subagent's recent human sidechain inputs (`humanInputs`), derived from the transcripts on each poll.
- **FR-7** A pending or accepted optimistic bubble whose text matches a human sidechain input created at or after it renders "Delivered to subagent · <description>" and never "Sent · waiting for transcript".
- **FR-8** One main-transcript user message whose normalized text equals the concatenation of two or more consecutive pending bubbles (joined by `''`, `'\n'`, or `' '`) clears all of them.
- **FR-9** An accepted bubble with no match after `TURN_STALL_MS` (4 min), while the conversation is not streaming, moves to the failed outbox labeled "Not found in transcript", with Resend and Copy actions. A late echo still clears it.
- **FR-10** Resend from a not-found entry sends with a fresh `clientMessageId` and without `retry: true`.
- **FR-11** The composer shows a notice when the latest human sidechain input is newer than the latest main-transcript user message ("routed" notice, requires Send anyway / Wait confirmation), or, failing that, when a background subagent is running ("running" notice, informational).
- **NFR-1** The sidechain human-input scanner reads each subagent file incrementally from a cached byte offset; it never re-reads a whole file on every 2 s poll.
- **NFR-2** Every timer-driven test uses `vi.useFakeTimers()` with `vi.advanceTimersByTime*` (repo rule `fake-timers-for-retry-tests`). No real `setTimeout` waits in tests.
- **NFR-3** No `execSync` or other sync child-process calls in server-reachable code (repo rule `no-execsync-server`). File reads use `node:fs/promises` or streams, matching `transcript-landing.ts`.
- **NFR-4** Overdeck stores no delivery status. Every new state is derived from transcripts on read (subagent human inputs) or held in the existing ephemeral composer store.

## Decisions (auto mode)

- **D1 — Join fix is reconciliation-only.** The composer already serializes sends per conversation (`ComposerFooter.tsx:177` disables while `sending`, which spans the POST). The join happened inside Claude Code's input queue: one enqueue record with the combined text. The transcript does not show the mechanism, so this PR matches joined text in the reconciler and does not change injection. Source-side separation is a non-goal.
- **D2 — `pan tell` sidechain landing is a failure.** It returns `{ delivered: false, confirmed: false, queuedToMail: true, reason }` and the CLI exits 1. The caller's intent (reach the main agent) failed, and a retry would land in the subagent again. The mail file records it with kind `'queued'` (not `'delivered'`) so the text is kept for manual delivery.
- **D3 — Transport is `SubagentSummary`.** Add optional `background` and `humanInputs` to the existing summary, so the 2 s subagent poll and its change-only emission carry them. No new `ConversationEvent` kind. Both the live stream (`startSubagentListPolling`) and the one-shot `GET /api/conversations/:name/messages` include them, because both call `listSubagentSummaries`.
- **D4 — Routing notice wording is hedged for the "running" case.** This transcript proves routing only after the fact. The "running background subagent" notice says Claude Code *may* route typed input to it and never blocks sending. Only the evidence-based "routed" notice asks for confirmation.
- **D5 — The not-found timeout is gated on `streaming === false`.** A message queued during a long tool call is legitimately unrendered until consumed (the parser renders only the `queued_command` attachment, written at consume time). The bubble moves to the outbox only when it is ≥ `TURN_STALL_MS` old AND the conversation is not streaming.
- **D6 — The sidechain match uses `includes`, not equality, on whitespace-normalized text.** The delivered text can carry an `@<attachment path>` prefix or a context envelope. Rule: `normalizeWs(input.text).includes(normalizeWs(local.text))`, where `normalizeWs = s => s.replace(/\s+/g, ' ').trim()`.
- **D7 — Human-input retention.** Keep at most the 20 most recent human inputs per subagent, and each input's text truncated to 2,000 characters. That bounds payload size while covering every realistic send.
