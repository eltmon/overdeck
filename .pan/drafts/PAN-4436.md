## Problem

PAN-2609 stores every saved conversation in the vault, and PAN-4307 makes the primary dashboard pull all
records into the list cache every sync cycle. A conversation saved on another machine is still invisible in
the dashboard: the only way to read it is `pan vault show <id>` in a terminal. PAN-2609 FR-4 asks for these
records to appear in the conversation list as **browse copies**: the full transcript rendered through the
existing conversation UI, an owner badge, a read-only composer, and no presence in cost totals or
agent/runtime views.

## Goal

- After a sync cycle, each non-owned Claude Code or Codex record appears in the Command Deck conversation
  list with `from <machine>`, opens to its full transcript, and shows a read-only notice with the exact
  `pan vault resume <vaultId>` command instead of a composer. No Resume control appears, and the server
  refuses resume.
- Browse rows never reach cost totals, the conversation ledger costs, the Agents Directory, lanes, the
  lifecycle poller, restart-all, or the pull-request sync sweep.
- When a record is tombstoned, becomes owned by this machine, or disappears from the vault, the next sync
  removes its row and its cache file.

## Requirements

### Functional

- **FR-1** (PAN-2609 FR-4) After each successful sync cycle, the dashboard writes one browse cache file per
  non-owned record whose harness is `claude-code` or `codex`. The file holds the record's decrypted LOG
  lines, one per line, newline-terminated (`nativeFileContent` format). It is written before the row exists.
- **FR-2** A refresh appends only LOG chunks past the manifest's chunk count when the cache file's size equals
  the manifest's byte count and the harness is unchanged. Otherwise it rewrites the whole file. When the
  list-cache `updatedAt` equals the manifest's `updatedAt` and the file size matches, it reads no record.
- **FR-3** For each cache file it wrote or kept, the dashboard upserts row `vault-<vaultId>` with
  `origin = 'vault'`, `status = 'ended'`, `ended_at` = record `updatedAt` (never null), `created_at` = record
  `createdAt`, `title`, `cwd`, `harness`, `model`, `vault_owner_label` = record `owner.label`,
  `tmux_session = 'conv-vault-<vaultId>'`, `title_source = 'manual'`.
- **FR-4** On conflict, the upsert updates only `title`, `cwd`, `harness`, `model`, `ended_at`,
  `vault_owner_label`, and only when the existing row has `origin = 'vault'`. It never changes `archived_at`,
  `project_key`, favorites, or a local row that happens to hold the name.
- **FR-5** A record that is tombstoned, owned here, absent from the list cache, or of another harness has its
  cache file, manifest entry and row removed in the same refresh. Removal first sets to NULL every
  `parent_conversation_id`, `critic_of_conversation_id`, `handoff_target_conv_id` and `cleared_to_conv_id`
  that points at the browse row, so a fork of a browse row never blocks removal.
- **FR-6** `listConversations()` excludes browse rows. So do the raw readers
  `listConversationsForPullRequestSync()` and the `managed-archived` branch of the sessions feed.
- **FR-7** `GET /api/conversations` returns local rows (unchanged enrichment) followed, on `offset === 0`
  only, by browse rows with `origin: 'vault'`, `vaultOwnerLabel`, `sessionAlive: false`, `isWorking: false`,
  `totalCost: 0`, `totalTokens: 0`, `lastActivityAt` = `endedAt`, `isFavorited`, `pendingInputCount: 0`,
  `pendingInputKinds: []`, `transcriptMissing: false`, `needsTerminal: false`, `pullRequest: null`,
  `pullRequestCount: 0`. The Agents Directory and lanes keep calling `getEnrichedConversationList`.
- **FR-8** `GET /api/conversations/:id` and `GET /api/conversations/:name/messages` work for a browse row:
  `resolveSessionFile` returns its browse cache file before any other harness branch.
- **FR-9** Reading a browse row's messages never calls `updateConversationCost`, and the response carries
  `totalCost: 0` and `totalTokens: 0`.
- **FR-10** `POST /api/conversations/:name/resume` on a browse row returns 409 with
  `{ error: 'Read-only copy from <label>. To continue it here, run: pan vault resume <vaultId>', code: 'vault-browse-copy' }`
  and starts nothing. (`POST …/message` already returns 422 for every ended row.)
- **FR-11** The conversation row shows `from <label>` for a browse row, in both the flat and the nested
  project-tree variants.
- **FR-12** The conversation panel of a browse row shows a read-only notice in place of the composer:
  `Read-only copy from <label>.` and `To continue it here, run: pan vault resume <vaultId>`. No Resume control
  renders.
- **FR-13** When a refresh inserted, updated or removed at least one row, the dashboard emits one
  `conversation.created` event, so open lists refetch at once.
- **FR-14** `OVERDECK_VAULT_IN_PEER=1` starts the vault service and the browse service in a peer dashboard.
  It exists for isolated UAT fixtures that own a throwaway `OVERDECK_HOME`.

### Non-functional

- **NFR-1** (PAN-2609 NFR-2) `overdeck.db` stays a rebuildable cache: every browse row derives from the vault
  and the browse cache, and a refresh reconciles rows to exactly the set of cache entries it kept.
- **NFR-2** `src/lib/vault/browse.ts` stays inside the vault import graph: Node built-ins and sibling vault
  modules only.
- **NFR-3** Browse cache files, the manifest and the browse directory are owner-only (files 0600, directory
  0700). Nothing writes a browse file outside `${vaultDir()}/browse/`: every `vaultId` is checked against
  `/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/` before it becomes part of a path, and
  every removal checks that the target is inside the browse directory.
- **NFR-4** No browse code calls the deletion door. A test spies on `transcript-deletion-door.js` and asserts
  zero calls across refreshes that remove files.
- **NFR-5** All I/O is async (`node:fs/promises`); no `execSync` anywhere reachable from the dashboard. A
  refresh runs only inside the sync cycle, never on an HTTP request.
- **NFR-6** One bad record never stops a refresh: its error is collected, its existing row and file stay, and
  the service logs one `console.warn('[vault] browse …')` line per distinct message.
- **NFR-7** No capped file exceeds its cap (`bash scripts/lint-file-size.sh` passes).

## Decisions (made in this document)

- **D-1 Browse only `claude-code` and `codex`.** The dashboard has parsers for both, and the vault discovers
  and settles only these two (`src/lib/vault/discover.ts` `harness: 'claude-code' | 'codex'`). A record with
  any other harness gets no cache file and no row (FR-5).
- **D-2 LOG, not VIEW.** Browsing shows the full saved transcript, so the cache holds the LOG. The VIEW is
  what a resume loads (PAN-2609 glossary) and stays PAN-4437's concern.
- **D-3 The engine owns the cache; a dashboard service owns the rows.** `src/lib/vault/browse.ts` cannot
  import the conversations door (NFR-2), and the door must not know the vault format. A new dashboard module
  `src/dashboard/server/services/vault-browse-service.ts` joins them: it runs the cache refresh, then the
  door's upserts and removals, then emits the event.
- **D-4 The refresh hooks `onVaultSyncReport`.** PAN-4307 FR-13 exports it for this purpose. The listener runs
  inside the vault queue, after the pull, so the list cache is fresh and nothing races a settle.
- **D-5 `origin` lives on `LegacyConversation`.** `LegacyConversation` gains `origin: 'local' | 'vault'` and
  `vaultOwnerLabel: string | null`, read by `LEGACY_CONVERSATION_SELECT`. Every reader that spreads the row
  (list, single read) then carries both fields to the frontend with no per-route code. Both
  `conversation-reads.ts` and `conversation-runtime.ts` import `type LegacyConversation as Conversation`, so
  no second type changes.
- **D-6 The name prefix is reserved.** `origin = 'vault'` ⇔ `name` starts with `vault-`. The door writes only
  such names, and `createConversation` throws `conversation names starting with "vault-" are reserved for
  Session Vault browse copies` for any other writer. (Generated names are `YYYYMMDD-NNNN`,
  `generateConversationName` in `conversation-runtime.ts`, so nothing hits this today.)
- **D-7 Full `vaultId` in the notice.** The notice and the resume refusal print the full `vaultId`, not an
  8-character prefix. `resolveVaultId` (`src/cli/commands/vault/show.ts`) resolves an exact id without
  ambiguity, so the copied command always works.
- **D-8 Forks are allowed; removal detaches them.** A fork or summary-fork of a browse row creates a new local
  conversation and leaves the copy untouched, so it does not break "read-only". The only risk is the
  `ON DELETE no action` foreign keys on `conversations`, which would make removal throw forever. FR-5's
  detach step handles every referencing column instead of a guard per entry point.
- **D-9 Composer wrapper, not an early return.** `ComposerFooter` calls hooks from its first line, so an early
  return would break the rules of hooks. The existing function is renamed `ComposerFooterInput` (not
  exported) and a new exported `ComposerFooter` returns the notice for a browse row or
  `<ComposerFooterInput {...props} />` otherwise. `ConversationPanel.tsx` (at its cap) changes only its
  `onResume` line.
- **D-10 Badge and notice reuse existing classes.** The badge reuses `styles.conversationBranchChip` /
  `styles.conversationBranchChipText` with a lucide `MonitorSmartphone` icon at size 10, like the branch chip
  next to it. The notice reuses `styles.composerFooter` / `styles.composerBox`. No CSS module change, no pill,
  no color (style guide: restrained color).
- **D-11 Grouping follows the existing rule.** A browse row carries `project_key = NULL`, so it groups by
  `cwd` like any row (`resolveEffectiveProjectKey`, `CommandDeck/projectsData.ts`). A foreign `cwd` lands in
  the "No project" bucket. Matching a record to a local project by git origin is PAN-4437's project-match
  work.
- **D-12 Peer override env var.** The isolated Playwright fixture is a peer, so PAN-4307 never starts the
  sync loop there and no browse row could ever appear. `OVERDECK_VAULT_IN_PEER=1` (FR-14) starts the vault
  and browse services in a peer. The fixture spreads `process.env` into the child, so the spec sets the
  variable in its own process and the fixture file does not change. It is documented as UAT-only; a peer
  that shares the primary's home must never set it.
- **D-13 One event per refresh.** A first sync can create hundreds of rows. One `conversation.created`
  (payload `conversationName` = the first changed row's name) bumps `conversationsListRevision` once
  (`packages/contracts/src/event-reducers.ts`, anchor `case 'conversation.created': {`).
- **D-14 Stale rows persist while the vault is off.** PAN-4307's cycle calls listeners only when the vault
  opens. With the vault off or its key missing, browse rows and files stay as the last successful sync left
  them. Cleanup on vault shutdown is a non-goal.
- **D-15 Extract before growing.** `conversations.ts` is at its cap (1222/1222). WI-1 moves
  `getConversationLedgerCosts` (33 lines) to `conversation-ledger-costs.ts` with a one-line re-export, which
  leaves room for WI-3's ~21 added lines (target ≤ 1215).

## Intersecting repo rules (restated)

- No `execSync` in dashboard-reachable code; use `node:fs/promises` (`sync-sources/rules/no-execsync-server.md`).
- Tests that wait on time use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync` (`fake-timers-for-retry-tests.md`). This plan adds no timers; the browse service test drives the listener directly.
- JSONL session files are sacred. Only the deletion door removes a **native** transcript. Browse cache files are derived decrypted copies inside `${vaultDir()}/browse/` and are removed with `rm` under a containment check, never through the door (NFR-4).
- The vault import graph (NFR-2): `src/lib/vault/browse.ts` imports only Node built-ins and `./config.js`, `./format.js`, `./local-index.js`, `./identity.js` (types), `./store/types.js` (types). - File-size ratchet: `conversations.ts` 1222/1222, `src/dashboard/server/routes/conversations.ts` 1072/1072, `chat/ConversationPanel.tsx` 1531/1531, `conversation-runtime.ts` 1240/1252. Files under 1000 lines may grow up to 1000. Never edit `scripts/file-size-allowlist.txt`.
- New lib modules that need agent state import from `agent-state-read.js`, not `agents.js` (lint:circular). This plan's new modules need none.
- Tests that read source text or add `skipIf`/`.only` fail lint and the test-skip gate; assert behavior.
- Quality gates before `pan done`: `npm run typecheck`, `npm run lint`, `npx vitest run <touched tests>`. Never run the full `npm test` on the host. `npm run typecheck` skips `*.test.ts`, so run the touched tests.

Data flow of one refresh:

```
cycle() ─ syncOnce ─ replaceListCache ─ afterSettle ─▶ listener(report, vault)          (4307)
  vault-browse-service.refreshVaultBrowseCopies(vault)
    1. refreshBrowseCache({ store, keys })        → { copies, removed, failed }         (browse.ts)
    2. upsertVaultBrowseRow(copy) for each copy   → 'inserted' | 'updated' | 'unchanged' | 'conflict'
    3. removeVaultBrowseRow(id) for every browse row whose id ∉ copies ∪ failed
    4. any change → emit one conversation.created
```

### WI-2 `vault-browse-cache` — `src/lib/vault/browse.ts` (FR-1, FR-2, FR-5 cache half, NFR-2..NFR-4, D-1, D-2)

Files: `src/lib/vault/browse.ts` (new), `tests/unit/lib/vault/browse.test.ts` (new).

1. Exports:

```ts
export const BROWSE_DIRNAME = 'browse';
export const BROWSE_HARNESSES = ['claude-code', 'codex'] as const;
export function vaultBrowseDir(): string;                               // join(vaultDir(), BROWSE_DIRNAME)
export function isBrowsableVaultId(vaultId: string): boolean;           // NFR-3 UUID regex
/** Throws on an id that fails isBrowsableVaultId. */
export function vaultBrowseFilePath(vaultId: string, harness: string): string; // codex → rollout-<id>.jsonl, else <id>.jsonl
export interface BrowseCopy {
  vaultId: string; harness: 'claude-code' | 'codex'; title: string; ownerLabel: string;
  cwd: string; model: string | null; createdAt: string; updatedAt: string; path: string;
}
export interface BrowseRefreshResult {
  copies: BrowseCopy[];                                  // every cache entry kept or written this refresh
  removed: string[];                                     // vaultIds whose file + manifest entry were removed
  failed: Array<{ vaultId: string; message: string }>;   // wanted but not refreshed; file + manifest kept
}
export async function refreshBrowseCache(options: {
  store: VaultStore; keys: VaultSubkeys; rows?: readonly ListCacheRow[];   // rows default: readListCache()
}): Promise<BrowseRefreshResult>;
```

2. Manifest `browse/manifest.json`, shape
   `{ v: 1, entries: Record<vaultId, { harness, chunks, bytes, updatedAt, title, ownerLabel, cwd, model, createdAt }> }`.
   A missing or unparseable manifest reads as `{ v: 1, entries: {} }` (every file then rewrites). Write it
   through a temp file + `rename`, mode 0600. Create the directory with `mkdir(…, { recursive: true, mode: 0o700 })`.
3. Wanted set: rows with `!ownerIsHere && !tombstone && BROWSE_HARNESSES.includes(harness) && isBrowsableVaultId(vaultId)`.
4. For each wanted row, inside its own `try` (NFR-6; errors go to `failed`, the old file and entry stay):
   - `entry = manifest.entries[vaultId]`, `path = vaultBrowseFilePath(vaultId, row.harness)`,
     `size = (await stat(path)).size` or `null` when missing.
   - **Skip:** `entry && entry.updatedAt === row.updatedAt && entry.harness === row.harness && size === entry.bytes`
     → push the `BrowseCopy` built from `entry`; read no record (FR-2).
   - Otherwise load the record: `name = refName('record', vaultId, keys.K_ref)`, `ref = await store.readRef(name)`,
     `value = ref ? await readSessionRecord(name, ref.value, keys) : null`. `null` or a tombstone → treat as
     not wanted (step 5 removes it).
   - **Append:** `entry && entry.harness === record.harness && size === entry.bytes && entry.chunks <= record.log.length`
     → decode `record.log.slice(entry.chunks)` in order (`store.getObject(id)` then `decodeChunk(bytes, id, keys)`;
     a missing object throws `Vault chunk <id> of record <vaultId> is missing from the backend`) and
     `appendFile(path, browseFileContent(lines), { mode: 0o600 })` when there are new lines. `browseFileContent` is a
     private one-liner in `browse.ts` identical to `materialize.ts` `nativeFileContent`; do not import `materialize.js`.
   - **Rewrite:** otherwise decode every chunk of `record.log` and write `browseFileContent(allLines)` to a
     temp file in the browse dir, then `rename` it onto `path` (mode 0600). If the harness changed, remove the
     other-harness file for the same id.
   - Set `manifest.entries[vaultId]` from the record (`bytes` = new file size, `chunks = record.log.length`)
     and push the `BrowseCopy`.
5. Removal: every manifest entry whose `vaultId` is neither a kept copy nor in `failed`: remove both possible
   files (`<id>.jsonl`, `rollout-<id>.jsonl`) with `rm(path, { force: true })` after asserting
   `relative(vaultBrowseDir(), path)` does not start with `..` and is not absolute, delete the entry, push
   the id to `removed`. Never import `transcript-deletion-door`.
6. Save the manifest once at the end.
7. Tests (`tests/unit/lib/vault/browse.test.ts`; temp `OVERDECK_HOME`, a `dir:` store fixture built the way
   `tests/unit/lib/vault/sync.test.ts` builds one, records written with the real `settle()`):
   - a non-owned Claude record produces `browse/<id>.jsonl` whose bytes equal `nativeFileContent` of its LOG

## Non-goals

- "Continue here" in the dashboard, the drift dialog, WIP apply, clone-and-register, project matching by git
  origin, and "continued on <machine>" states (PAN-4437).
- Browse copies for harnesses other than Claude Code and Codex (D-1).
- Rendering the VIEW instead of the LOG (D-2).
- Refusing fork or summary-fork of a browse row (D-8); the fork is a new local conversation.
- Removing browse rows when the vault is turned off or its key is missing (D-14).
- A "Sync now" button or route; the refresh runs only inside the sync cycle.
- Excluding browse rows from conversation title search (`conversation-title-search.ts`); opening one from
  search is a valid read.
- Any change to cost ingestion: `src/lib/costs/reconciler.ts` scans `~/.claude/projects` and
  `~/.overdeck/agents/*`, and the Codex collector scans Codex homes, none of which contain `vault/browse/`.
- Any change to the PAN-4307 sync loop, settle poller, eviction, or routes, other than the `main.ts` start block.
- CSS module changes, new design tokens, or per-row actions menus for browse rows.
- Changing Delete or Archive for browse rows. `handleConversationDelete` archives the row (it never deletes it),
  and the upsert never touches `archived_at`, so a deleted or archived browse copy stays hidden across syncs until
  its record goes away, when the next refresh removes it.

## Hazards

- **H-1 Capped files.** `conversations.ts`, `routes/conversations.ts`, `ConversationPanel.tsx` are at their caps
  and `conversation-runtime.ts` has 12 lines of headroom. WI-1 must land before WI-3 edits `conversations.ts`.
  Run `bash scripts/lint-file-size.sh` after each of those items.
- **H-2 Foreign keys.** `foreign_keys = ON` and four `ON DELETE no action` self-references on `conversations`.
  `removeVaultBrowseRow` must null them in the same transaction or a forked browse row blocks removal forever.
- **H-3 Deletion door.** Calling `removeTranscriptFile` from browse code would break PAN-4307 AC-4 (no sync cycle
  reaches the door). Use `rm` under the containment check.
- **H-4 Path safety.** `vaultId` comes from decrypted, authenticated records, but it still becomes a file name.
  Validate it with the UUID regex before any `join`.
- **H-5 Cost ingestion.** Never place browse files under `~/.claude/projects`, `~/.codex`, or
  `~/.overdeck/agents`; the cost reconciler would bill them as new sessions.
- **H-6 Two-second polling.** `ConversationList` polls every 2 s while any row has
  `!sessionAlive && !endedAt && !spawnError`. `ended_at` must never be null on a browse row (FR-3).
- **H-7 Peer override.** `OVERDECK_VAULT_IN_PEER=1` on a peer that shares the primary's home would run two sync
  loops on one vault. The docs say so; the variable is only for fixtures with a throwaway home.
- **H-8 PAN-4307 references.** `vault-service.ts`, `open.ts` and the `main.ts` vault block exist only on
  `origin/feature/pan-4307` at planning time. If PAN-4307 merged with a different shape, follow its anchors
  (`onVaultSyncReport(listener`, `startVaultService();`) and keep this plan's behavior.
- **H-9 Name collision.** A local conversation named `vault-<uuid>` from before this change would block its
  browse row (`'conflict'`, warned once). No generated name has that shape, so this is unlikely.
