# PAN-5042: PR listing read flaps between ok and failed

**Issue:** https://github.com/eltmon/overdeck/issues/5042
**Status:** planned (auto mode, 2026-11-04)

## Summary

The repo PR listing that feeds the board, the auto-merge scheduler, the UAT
train, the PR sync sweep and the Flywheel runs one
`gh pr list --state all --limit 100` with `statusCheckRollup` and
`reviewRequests` on every row. On 2026-11-04 that query failed with
**`HTTP 504: 504 Gateway Timeout (https://api.github.com/graphql)`** after
about 11 s: GitHub's own GraphQL gateway gives up before our 20 s exec timeout
does. The `catch {}` in `readRepoPullRequests` returns `null` and logs
nothing, so the scheduler reports "PR listing unavailable" for minutes at a
time and nobody can see why.

This change splits the listing into two reads (open PRs with every field,
closed PRs with cheap fields), logs every listing failure with its reason
once per change, and lets the auto-merge scheduler depend on the open read
only.

## Measured evidence (planning session, 2026-11-04 ~17:30Z, overdeck repo)

| Query | Result | Time |
| --- | --- | --- |
| `--state all --limit 100`, full field set (today's query) | `HTTP 504` from GitHub GraphQL, twice | 11.2 s each |
| `--state open --limit 100`, full field set | ok, 2 rows | 0.75 s |
| `--state closed --limit 100`, full set minus `statusCheckRollup`, `reviewRequests`, `mergeable` | ok, 100 rows (all `MERGED`) | 2.1 s |
| `--state closed --limit 100`, cheap set plus `statusCheckRollup` | ok, 100 rows | 10.3 s |

Conclusions the plan relies on:

- `statusCheckRollup` on 100 closed rows alone costs ~10 s, which is GitHub's
  GraphQL budget. Keeping the rollup on closed rows, even at a smaller limit,
  is the wrong lever.
- Raising our 20 s timeout changes nothing: GitHub answers 504 first.
- `gh pr list --state closed` returns `MERGED` rows as well as `CLOSED` rows
  (all 100 rows above were `MERGED`).

## Glossary

- **PR listing** — the per-repo array of `GhPrRow` objects read from
  `gh pr list --json …`, cached in process memory. Today one cache,
  `cachedRepoPullRequests` in `src/lib/overdeck/derived-issue-state.ts`.
- **Open listing** — the new read `gh pr list --state open --limit 100 --json <GH_PR_FIELDS>` (every field, unchanged field set).
- **Closed listing** — the new read `gh pr list --state closed --limit 100 --json <GH_CLOSED_PR_FIELDS>`; returns merged and closed-unmerged PRs without `statusCheckRollup`, `reviewRequests` or `mergeable`.
- **Combined listing** — open rows plus closed rows, deduplicated by PR number (the closed row wins), sorted by PR number descending. This is what `readRepoPullRequests` returns after the change.
- **Failed read** — a listing read that answers `null`. Callers that back off (scheduler, PR sync) must tell `null` ("failed") from `[]` ("no PRs"). Unchanged contract.
- **Stale-OK read** — `listRepoPullRequestsStaleOk` (PAN-3925): serves the last good combined listing while a refresh runs, up to `PR_LISTING_MAX_STALE_MS` (2 min).
- **Shrink** — an open-listing refresh in which a PR number that was in the previous successful open listing for that repo is missing. The PR closed or merged, so the closed listing must be re-read.
- **Metered call** — a `gh` exec through `runGh` (`src/lib/github-quota/run-gh.ts`, PAN-4264), which can throw `GitHubQuotaPausedError` (pause gate) or `GitHubRateLimitedError` (GitHub refused).
- **Failure reason** — the one-line text the new logging prints for a failed read (see FR-3).

## Decisions

- **D1 — Split into two reads; no combined cache.** The open listing and the
  closed listing each get their own `createSettledTtlPromiseCache`.
  `readRepoPullRequests` composes them; it does not add a third cache (a
  nested cache would let open data age to 2× the TTL).
- **D2 — Read open first, then closed, sequentially** inside
  `readRepoPullRequests` (never `Promise.all`). The open loader runs the
  shrink check before it resolves (WI-9). Because
  `createSettledTtlPromiseCache.invalidate` leaves an in-flight load alone
  (`src/lib/concurrency.ts`, "In-flight loads are untouched"), a shrink also
  bumps a per-repo **closed generation** (D14), and a combined read re-reads
  the closed listing once when the closed value it got was loaded under an
  older generation than the one it saw after its open read. This is the
  consistency rule: a PR that leaves the open listing used by a combined read
  is never missing from that combined read.
- **D3 — Closed-listing TTL.** A successful closed listing is cached for
  `PR_CACHE_IDLE_TTL_MS` (5 min, `src/lib/overdeck/pr-cache-policy.ts`); a
  failed one (`null`) for `PR_CACHE_TTL_MS` (30 s), so a failure is retried
  as fast as today. The open loader invalidates the closed cache on a shrink;
  `invalidateRepoPullRequests` invalidates both caches.
- **D4 — Open-listing TTL unchanged:** `prListingTtlMs(rows, PR_CACHE_TTL_MS)`
  — 30 s, or 5 min when the repo has no open PR.
- **D5 — Combined order and duplicates:** concatenate open and closed rows;
  when both listings hold the same number, keep the row from the listing that
  settled later (open wins when `open.settledAt > closed.settledAt`, else
  closed wins). A merge inside one combined read lets the closed row win (the
  closed read ran after the open read); a PR reopened while a 5-minute closed
  listing is still cached lets the fresh open row win. Then sort by `number`
  descending. This matches `gh`'s newest-first order
  today, so `loadIssueStatesForProject`'s last-wins `prByIssue.set` keeps
  choosing the same row.
- **D6 — A combined read fails if either read fails** (`null`).
  `lastRepoPullRequests` is updated only when both succeed, with `settledAt` =
  the open listing's settle time (not `Date.now()` at composition), so the
  stale-OK age bound still measures the open data.
- **D7 — Open-only consumers read the open listing.** New export
  `readOpenRepoPullRequests(projectPath): Promise<readonly GhPrRow[] | null>`.
  The scheduler, merge-path-owner's `defaultPrOf`, `listReadyIssuesForProject`
  and `listOpenPullRequestsForProject` default to it, so a closed-listing
  failure never stops scheduling. The scheduler still treats `null` as
  "PR listing unavailable", never as "no PRs".
- **D8 — Merged rows without a rollup report `checks: 'green'`.** New helper
  `checksFromGhRow(row)`: `row.statusCheckRollup !== undefined` →
  `toChecksState(row.statusCheckRollup)`; else merged (`row.mergedAt` set or
  `state === 'MERGED'`) → `'green'`; else `'pending'` (today's value).
  Rationale: the value is display only (see above), and every Overdeck merge
  path requires green checks. An admin merge over red checks shows green after
  this change; accepted.
- **D9 — PR sync keeps the last observed checks.** When a listing row has no
  `statusCheckRollup` and the link already has a snapshot, the new snapshot
  keeps `link.snapshot.checks`. The merged snapshot is final, so this keeps a
  PR that merged red recorded as red. With no previous snapshot,
  `checksFromGhRow` decides.
- **D10 — Log every failure reason once per change** per
  `(projectPath, listing)` where listing is `open` or `closed`, and log the
  recovery. Format in FR-3.
- **D11 — Extract the GitHub listing into `src/lib/overdeck/pr-listing.ts`.**
  `derived-issue-state.ts` is at 988 of 1000 allowed lines; the new code does
  not fit. `derived-issue-state.ts` re-exports every moved name so no importer
  changes. `pr-listing.ts` must not import `derived-issue-state.ts`
  (`npm run lint:circular`).
- **D12 — Quota.** Today: one call per 30 s priced 3 points
  (`priceGhListCall`: one 100-row page, weight 3). After: the open call is
  priced the same (3 points per 30 s); the closed call is priced 1 point
  (weight 0) and runs once per 5 min or per shrink. Net spend rises by about
  0.1-0.3 points per 30 s per repo, and the call stops failing with 504.
- **D13 — Timeouts stay at 20 s** for both reads (the 504 comes from GitHub first).
- **D14 — Closed generation.** `closedGeneration: Map<string, number>` per repo,
  starting at 0. A shrink increments it and invalidates the settled closed
  entry. The closed loader records the generation current when it *starts*
  in its value. `readRepoPullRequests` captures the generation right after its
  open await; if the closed value's generation is lower, it invalidates the
  closed cache (the awaited load has settled by then, so `invalidate` removes
  it) and reads the closed listing once more. One retry is enough: the retry
  starts after the shrink that the open rows in hand reflect; a later shrink
  belongs to a later open listing, whose PR is still in the open rows this
  read uses.
- **D15 — Rows without a rollup are unobserved for PR watches.** A listing row
  with `statusCheckRollup === undefined` carries no observation of checks,
  review requests or mergeability. The PR sync sweep records such keys in a
  per-sweep `unobserved` set; `runWatchPass` treats a watched key in that set
  as not covered by the listing, so it takes the existing one-`gh pr view`
  path (`GH_PR_VIEW_FIELDS` includes `statusCheckRollup`), and when that read
  is skipped (backoff) or fails, the key is deleted from `ctx.snapshots`
  before `notify`, so `watchWake` never sees a guessed `checks` value. A
  watched PR ends its watch on merge or close, so this costs at most one
  `gh pr view` per watch.

  2. `GitHubRateLimitedError` → `rate limited: <error.message>`
  3. exec error with `code === 'ERR_CHILD_PROCESS_STDIO_MAXBUFFER'` → `output exceeded maxBuffer` (Node also sets `killed` here, so this check comes first)

  The reason is cut to 200 characters.
