# PAN-4293 — overdeck.ai account service (identity for hosted features)

**Issue:** [PAN-4293](https://github.com/eltmon/overdeck/issues/4293) · **Epic:** PAN-2350 (Overdeck Anywhere) · **Design:** `.pan/drafts/anywhere-accounts.md` §6.3, §6.4, §6.9 · **Planned:** 2026-10-01 → 2026-10-02

**Operator decisions that shape this PRD:**

- **2026-10-01, issue comment:** until billing (PAN-4294, Creem) exists, the operator grants access manually **through a UI, not a CLI or config file**: an admin screen that lists, adds (by GitHub username, optional note and expiry), revokes (including the account's device tokens) and approves pending sign-ins. Deploying is an explicit operator checkpoint.
- **2026-10-01, in session:** move to the operator's Kubernetes with Postgres. **Superseded on 2026-10-02.** The cluster survey from that round is kept as Appendix A.
- **2026-10-02, in session (current):** use **Cloudflare**, back to `anywhere-accounts.md` §6.9: Workers + D1 for accounts, devices and the allowlist; R2 + Durable Objects for the hosted vault contract. Keep: (1) invite-only allowlist enforced server-side before any token is minted; (2) the operator-only admin screen with optional note and expiry; (3) a per-tester storage cap enforced server-side, default 5 GB; (4) rate limiting on the public sign-in endpoints; (5) the `tester` entitlement stub so Creem can replace grants later without a migration. `overdeck.ai` DNS is already on Cloudflare. Build and test locally with wrangler/Miniflare; never deploy.

This PRD is the implementation brief. An executor that cannot re-research the design should be able to build each work item from this text alone. Every decision is made here. Steps that need live verification are marked **Implementation checkpoint** with a fallback.

## 1. Glossary

| Term | Meaning in this document |
| --- | --- |
| **Account service** | The Cloudflare Worker built by this issue, at `https://account.overdeck.ai`. Source in `services/account/`. |
| **Worker** | A Cloudflare Workers script. Runs on `workerd`, which exposes Web APIs (`fetch`, `Request`, `Response`, `URL`, `crypto.subtle`, `crypto.getRandomValues`, `crypto.randomUUID`), not Node APIs. |
| **D1** | Cloudflare's SQLite database for Workers. Binding `DB`. API: `db.prepare(sql).bind(...).first()/all()/run()`, `db.batch([...])`. |
| **wrangler** | Cloudflare's CLI. Here it is used only for local work: `wrangler dev --local`, `wrangler d1 migrations apply --local`, and `wrangler deploy --dry-run` (bundle without uploading). |
| **Miniflare** | The local simulator of the Workers runtime (it runs the real `workerd` binary). The integration test loads the bundled Worker into Miniflare with a local D1. |
| **D1 shim** | A small test helper that implements the D1 API subset on Node's `node:sqlite` `DatabaseSync`, so unit tests run in the root Vitest suite without `workerd`. |
| **Service binding / RPC entrypoint** | A Worker-to-Worker call that never crosses the public internet. The account service exports a `WorkerEntrypoint` class `AccountRpc`; the hosted vault (PAN-4297) binds to it and calls `verifyDevice(token)`. |
| **GitHub leg** | The round trip to GitHub's OAuth App authorize page and back to `/auth/github/callback`. Every sign-in (dashboard, CLI, admin) uses it. The GitHub access token it yields is used once to read the user's id and login, then discarded. |
| **PKCE flow** | OAuth 2.0 authorization-code flow with PKCE (RFC 7636), `S256` only, redirecting to a loopback URL on the user's machine (RFC 8252 §7.3). Used by the local dashboard; the client is PAN-4330. |
| **Device flow** | OAuth 2.0 Device Authorization Grant (RFC 8628), served by the account service itself. Used by the CLI, SSH and headless machines. The user types an 8-character code at `/activate`. |
| **Device token** | The long-lived bearer credential a client holds after sign-in: `odd_` + 64 lowercase hex chars (256 random bits). Stored server-side only as its SHA-256 hex hash. Revocable instantly. |
| **Device record** | A row in `devices`: server-minted `deviceId` (UUID v4), token hash, `platform`, user-visible `label`, opaque `environmentId`, created/last-used/revoked timestamps. |
| **environmentId** | The client install's machine identity, a lowercase UUID v4 from `${OVERDECK_HOME}/environment-id.json` (`src/lib/environment-identity.ts`, `UUID_V4_LOWERCASE`). Sent once at sign-in; stored opaque. |
| **Grant** | An allowlist entry: GitHub numeric id → entitlement, note, granted date, optional expiry, optional storage cap. Only the operator creates grants, through the admin screen. |
| **Owner** | The operator, identified by the secret `OWNER_GITHUB_ID`. Always allowed to sign in; the only identity that can open the admin screen. |
| **Pending attempt** | A record that a non-allowlisted GitHub account completed the GitHub leg. Shown on the admin screen with a one-click **Allow**. |
| **Entitlement** | `{ plan: 'tester', storageBytesCap, maxDevices }`, produced by one function, `entitlementFor()`, which PAN-4294 (billing) later reimplements without changing its signature. |
| **Storage cap** | The maximum stored bytes a user's hosted vault may hold. Default 5 GB (5 × 1024³ = 5,368,709,120 bytes); the operator may set a different cap per grant. The account service publishes it in the entitlement; the vault Worker enforces it on every write (section 7.13). |
| **Rate limit** | A fixed-window counter per (bucket, client IP) in D1. Exceeding it returns HTTP 429 with `Retry-After`. |
| **Data holder** | A hosted Worker that stores a user's data and must delete it on account deletion. Today none is deployed; the hosted vault (PAN-4297) becomes the first through the optional `VAULT` service binding. |
| **Deletion job** | A row in `deletion_jobs` tracking an account deletion until every data holder has acknowledged it. Retried by the hourly cron trigger. |
| **Admin screen** | Server-rendered HTML at `https://account.overdeck.ai/admin`, reachable only by the owner. No JavaScript. |
| **Implementation checkpoint** | A step that needs a human or a live system. The executor stops at it, notifies the operator, and follows the stated fallback. |

## 2. Problem

Three planned hosted features assume an overdeck.ai identity service exists, and none of them builds it: the PAN-2356 relay (GitHub OAuth at the relay, D-R2), PAN-658 Shared Sessions (GitHub identity for participants), and PAN-4297 hosted Session Vault (device authorization). The client side is PAN-4330, which depends on this service. Nothing in the code touches accounts today: the only overdeck.ai references are the install URL, the docs site and a git author email. `overdeck.ai` itself is a Vercel landing site (`docs/REBRAND-DEPLOYMENT-RUNBOOK.md` line 9), and the zone's nameservers are Cloudflare (`dig NS overdeck.ai` → `lucy.ns.cloudflare.com`, `rick.ns.cloudflare.com`, checked 2026-10-01), so a Worker can own a subdomain.

## 3. Scope

**In scope:** the account service Worker in `services/account/`: GitHub sign-in; the loopback PKCE flow; the RFC 8628 device flow; device tokens and records; the device API (`/v1/*`); the `AccountRpc.verifyDevice` contract; account deletion with fan-out; an hourly maintenance cron; the invite-only allowlist with per-grant storage cap and the `tester` entitlement stub; rate limiting on public sign-in endpoints; the owner-only admin screen; the hosted vault contract (types, the quota decision function, the R2 + Durable Object CAS shape) that PAN-4297 implements. Plus repo wiring (Bun workspace, typecheck lane), unit tests, a Miniflare integration test, docs, and a deploy runbook that ends at an operator checkpoint.

**Out of scope (NonGoals; review enforces these as must-not constraints):**

- Any client code: `pan account` verbs, `src/lib/account/`, dashboard `/api/account/*` routes, Settings → Anywhere, the first-run card, wrapper skills, no-loss-matrix rows. All PAN-4330.
- The hosted vault Worker itself: R2 bucket, the per-vault Durable Object, object/ref endpoints, keywrap serving, `GET /v1/vault` discovery, and the byte accounting that enforces the cap. All PAN-4297. This issue only fixes the contract in 7.13.
- Billing, Creem, paid plans. PAN-4294.
- Relay, push notifications, shared sessions. PAN-2356, PAN-2354, PAN-658.
- Kubernetes, Postgres or any non-Cloudflare hosting (withdrawn 2026-10-02; Appendix A is reference only).
- Email/password sign-in, email storage, any identity provider other than GitHub.
- Any GitHub OAuth scope beyond `read:user`; any repository access.
- Key rotation, "approve from another device", a web transcript viewer.
- Any route on the apex `overdeck.ai` (Vercel owns it).
- CORS: no `Access-Control-*` header on any response. `/v1/*` is called server-to-server by the local Overdeck server or CLI, never from a browser.
- Persisting the GitHub access token anywhere.
- Receiving, storing or logging the vault key, a vault passphrase or any plaintext user content.
- Any agent running a command that touches the operator's Cloudflare account or GitHub settings: `wrangler deploy` (without `--dry-run`), `wrangler login`, `wrangler d1 create`, `wrangler d1 migrations apply --remote`, `wrangler secret put`, `wrangler rollback`, DNS edits, OAuth App creation.
- Changes to anything under `src/` (the local Overdeck product).

## 4. Decisions (made here; numbered for review)

1. **D-1 Allowlist lives in D1, managed by the admin screen.** The 2026-09-29 comment said "allowlist in a Worker secret"; the 2026-10-01 comment replaced it with grants through a UI. The `grants` table is the allowlist. Only `OWNER_GITHUB_ID` is configuration.
2. **D-2 Placement: `services/account/` as a Bun workspace** in this monorepo, with its own `package.json`, `tsconfig.json`, `wrangler.jsonc` and `migrations/`. Follows PAN-658's `services/signaling-service/` convention and PAN-2356 D-R4. The root `typecheck` chain gains a `typecheck:account` lane, because the root `tsconfig.json` includes only `src/**/*`.
3. **D-3 Host: `https://account.overdeck.ai`**, a Workers custom domain (the apex is Vercel). All public paths live on this host. The device flow returns `verification_uri`, so clients never hardcode it. **Hazard for PAN-4330:** its body says `overdeck.ai/activate`; it must read `verification_uri` from the response and the base URL from config.
4. **D-4 Storage: one D1 database** `overdeck-account`. The admin screen is list-and-filter queries; nothing in the account service needs per-object serialization beyond D1's single writer.
5. **D-5 Every secret is hash-at-rest with SHA-256 hex:** device tokens, authorization codes, device codes, user codes, OAuth state values, admin session ids. All carry fresh randomness from `crypto.getRandomValues`, so a fast hash is correct. Lookup is by hash equality in SQL.
6. **D-6 Device token entropy is 256 bits** (`odd_` + 64 hex), matching epic decision D-6 and PAN-2356 FR-R1 rather than the 128 bits in §6.9.
7. **D-7 Loopback redirect policy (RFC 8252 §7.3).** `/auth/start` accepts `redirect_uri` only if `new URL(redirect_uri)` has protocol `http:`, hostname exactly `127.0.0.1`, `localhost` or `[::1]`, any port or none, no username, no password, no hash. Anything else → 400 HTML error page and **no redirect**. The client picks the port (PAN-4330). `code_challenge_method` must be `S256`. Authorization codes are single-use, expire after 5 minutes, and the exchange requires the identical `redirect_uri` string.
8. **D-8 GitHub token is single-use and never stored.** Identity key = numeric GitHub `id`; `login` is display-only, refreshed on every sign-in. OAuth scope `read:user`.
9. **D-9 Admin "add by username" resolves the id at grant time** with `GET https://api.github.com/users/<username>` (unauthenticated, `User-Agent: overdeck-account`) and stores the numeric id. 404 → "GitHub user not found"; 403/429 → "GitHub rate limit reached; try again in a few minutes".
10. **D-10 Pending attempts are bounded:** one row per GitHub id (first seen, last seen, attempt count, last flow), purged 30 days after `last_seen_at`. Only completed GitHub sign-ins create rows; the admin sign-in never does.
11. **D-11 The allowlist gate runs before any token or code is minted.** `resolveSignIn` (7.5) is the only path to `mintDevice` and to authorization-code creation, and it calls `isAllowed` first. The token endpoint mints only from an authorization code or an approved device grant, both of which exist only after that check passed. A grant removed or expired between approval and exchange is caught: `exchangeAuthorizationCode` and `exchangeDeviceCode` call `isAllowed` again before minting and return `access_denied` if it fails.
12. **D-12 Rate limiting on public sign-in endpoints** (operator requirement 4). Fixed windows per (bucket, client IP) in the D1 `rate_limits` table, client IP from `CF-Connecting-IP` (hashed before storage). Exceeding a limit returns 429 with `Retry-After: <seconds to window end>`: JSON `{"error":"rate_limited"}` on `/oauth/*`, an HTML page elsewhere. Buckets:

    | Bucket | Applies to | Limit |
    | --- | --- | --- |
    | `auth-start` | `GET /auth/start` | 20 per 10 min |
    | `github-callback` | `GET /auth/github/callback` | 30 per 10 min |
    | `device-code` | `POST /oauth/device/code` | 10 per 10 min |
    | `token` | `POST /oauth/token` | 120 per 10 min (a CLI polling every 5 s for 15 min makes 180 over the full grant, spread over windows) |
    | `activate` | `POST /activate`, `POST /activate/confirm` | 30 per 15 min |
    | `activate-fail` | wrong user codes on `POST /activate` | 10 per 15 min (the 11th wrong code → 429) |
    | `admin-login` | `POST /admin/login` | 10 per 10 min |

    The limits are a single constant table in `src/rate-limit.ts`. `routes.ts` applies the per-route buckets before dispatch; `device-flow.ts` counts `activate-fail` itself. `/v1/*` and `/admin` reads are not rate limited (they need a valid token or session).
13. **D-13 Non-allowlisted outcome per flow.** PKCE: 302 to the validated `redirect_uri` with `error=access_denied&error_description=invite_only&state=<client state>`. Device flow: the browser shows the invite-only page and the CLI's next poll returns `access_denied`. Both record a pending attempt. Invite-only text: "Overdeck accounts are invite-only right now. Everything local keeps working, and you can use your own git remote for Session Vault." with a link to `https://docs.overdeck.ai/configuration/session-vault`.
14. **D-14 "Allow" creates a grant; it does not mint a token.** The person signs in again. The admin screen says: "Allowing an account lets it sign in. Ask the person to sign in again."
15. **D-15 Grant expiry, operator revoke and account deletion are distinct.**
    - *Grant expired:* devices stay; `verifyDevice` returns `grant_expired`; `/v1/*` returns 403 `grant_expired` except `GET /v1/me`, `DELETE /v1/devices/:id`, `DELETE /v1/account`. Re-allowing restores access without re-sign-in.
    - *Operator revoke:* deletes the grant and revokes every device of that user (`revoked_by = 'operator'`). The `users` row stays.
    - *Account deletion:* revokes every device (`revoked_by = 'account-deletion'`), deletes the grant and pending row, starts a deletion job, and finally deletes the user and device rows.
16. **D-16 Deletion fan-out contract.** Each data holder's RPC entrypoint implements `deleteAccountData(userId: string): Promise<{ deleted: true }>` (type `AccountDataHolder` in `src/contract.ts`), idempotently. The account service calls every holder bound in its env (today only the optional `VAULT` binding, absent until PAN-4297 adds it), first via `ctx.waitUntil`, then hourly until each acks; then it deletes the user's device and user rows and sets `completed_at`. With no holders bound the job completes in the same request. The 24-hour SLA (PAN-2609 HB-3) belongs to the holder; the admin screen flags jobs older than 24 hours.
17. **D-17 Device record rules.** `deviceId` = `crypto.randomUUID()`. `platform` must match `^(linux|darwin|win32)-(x64|arm64)$`. Default label: `linux` → "Linux device", `darwin` → "macOS device", `win32` → "Windows device" (never the hostname). `environmentId` must match `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`. Signing in again from the same `(userId, environmentId)` rotates that active row's token hash in place. Labels are 1–64 characters after trimming, no control characters.
18. **D-18 `last_used_at` is throttled** to one write per device per 5 minutes, so the vault's hot path does not write D1 on every request.
19. **D-19 Admin screen is Worker-served HTML** at `/admin`, with its own GitHub sign-in (purpose `admin`) and a session row; authorized iff the GitHub id equals `OWNER_GITHUB_ID`. No dependency on PAN-4330.
20. **D-20 Admin session and CSRF.** Cookie `__Host-od_admin=<64 hex>`; `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=43200`. `Lax` because the session is set on the redirect back from github.com, where a `Strict` cookie would not be sent. Every admin `POST` must carry a `csrf` form field equal to the session's `csrf_token` and an `Origin` header equal to the origin of `PUBLIC_BASE_URL`; otherwise 403.
21. **D-21 OAuth state is browser-bound.** Starting a GitHub leg writes an `auth_requests` row keyed by `sha256(state)` (10-minute expiry) and sets `__Host-od_state=<state>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=600`. The callback requires cookie = `state`, deletes the row (single use) and clears the cookie.
22. **D-22 Owner is implicitly allowed:** `isAllowed(githubId)` = owner or an unexpired grant. The owner has no `grants` row; the admin screen shows a fixed "owner (always allowed)" line. The owner's entitlement is `entitlementFor(null)` (the default cap).
23. **D-23 Configuration.** Committed in `wrangler.jsonc` `vars`: `PUBLIC_BASE_URL = "https://account.overdeck.ai"`. Set by the operator with `wrangler secret put`, never committed: `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `OWNER_GITHUB_ID`. Missing `PUBLIC_BASE_URL`, `GITHUB_CLIENT_ID` or `GITHUB_CLIENT_SECRET` → every route except `/healthz` returns 503 `{"error":"not_configured","missing":[...names]}`. Missing or non-numeric `OWNER_GITHUB_ID` → `/admin*` returns 503 and the owner bypass is off. No value has a hardcoded default. Local development reads the same names from `services/account/.dev.vars` (gitignored; `.dev.vars.example` is committed with placeholders).
24. **D-24 Testing has two layers.** (a) **Unit tests** in the root Vitest suite (`tests/unit/services/account/*.test.ts`) run on Node 22 against a D1 shim over `node:sqlite`. Logic uses Web APIs only, so no `nodejs_compat` flag. `src/index.ts` is the only file that imports `cloudflare:workers`; it delegates to `handle()` in `src/routes.ts`, `runMaintenance()` in `src/maintenance.ts` and `verifyDeviceToken()` in `src/devices.ts`. Time and outbound HTTP come from `Deps { now(): number; fetch: typeof fetch }`, so tests control both without waiting. Unit tests never import `src/index.ts`. (b) **One integration test** (`tests/integration/services/account/miniflare.test.ts`) bundles the real Worker with `wrangler deploy --dry-run`, loads it into Miniflare with a local D1 and the migrations applied, intercepts outbound GitHub calls with Miniflare's `outboundService`, and drives the full flows through real `workerd`. This is the operator's "test locally with wrangler/Miniflare".
25. **D-25 No agent deploys.** Allowed wrangler commands for agents: `wrangler dev --local`, `wrangler d1 migrations apply overdeck-account --local`, `wrangler deploy --dry-run --outdir <dir>`. Everything else in section 3's last NonGoal bullet is operator-only. The deploy runbook ends at an operator checkpoint.
26. **D-26 Storage cap** (operator requirement 3). `grants.storage_cap_bytes` is nullable; `entitlementFor(grant)` returns `grant?.storage_cap_bytes ?? DEFAULT_STORAGE_CAP_BYTES` where `DEFAULT_STORAGE_CAP_BYTES = 5 * 1024 ** 3`. The admin add form takes an optional cap in whole GB (1–1000, default 5); the grants table shows it. Enforcement is server-side in the vault Worker (PAN-4297) on every write, using `quotaDecision()` from `src/entitlement.ts` (7.13). The account service holds no user data, so it has nothing of its own to enforce.
27. **D-27 Entitlement stub stays migration-free for billing** (operator requirement 5). `grants.entitlement` is a TEXT column defaulting to `'tester'`; `entitlementFor` is the only reader. PAN-4294 later adds plan rows or columns alongside and changes the body of `entitlementFor`; no existing column changes meaning, so no data migration is needed.
28. **D-28 Security headers.** HTML responses: `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; form-action 'self' https://github.com; frame-ancestors 'none'; base-uri 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`. JSON: `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`. All HTML interpolation goes through `escapeHtml()`. Request bodies over 16 KiB → 413.
29. **D-29 Dependencies are dev-only and pinned exactly.** `services/account/package.json` devDependencies: `@cloudflare/workers-types`, `wrangler`, and `miniflare` at the exact version that `wrangler` itself depends on (on 2026-10-01: `wrangler@4.146.0` depends on `miniflare@5.20261001.0-alpha`; re-check with `npm view wrangler@<version> dependencies` at implementation time and pin both). The Worker has no runtime dependencies. `wrangler` brings the `workerd` binary into `bun install`; that is accepted as the cost of local testing.

## 5. Requirements

### Functional

- **FR-1** Completing the PKCE flow with an allowlisted GitHub account yields a device token from `POST /oauth/token` (`grant_type=authorization_code`), and a `devices` row holds its SHA-256 hash.
- **FR-2** The device flow (`POST /oauth/device/code`, approval at `/activate`, polls with `grant_type=urn:ietf:params:oauth:grant-type:device_code`) yields a device token with no browser on the CLI's machine. Polls return `authorization_pending`, `slow_down`, `access_denied` and `expired_token` per RFC 8628 §3.5.
- **FR-3** A GitHub account that is neither the owner nor holds an unexpired grant never obtains an authorization code, an approved device grant or a device token; its sign-in creates or updates one `pending_attempts` row.
- **FR-4** `GET /v1/me`, `GET /v1/devices`, `PATCH /v1/devices/:id`, `DELETE /v1/devices/:id` authenticate with `Authorization: Bearer odd_…` and act only on the caller's own user.
- **FR-5** A revoked device token is refused on the next request: 401 `device_revoked` from `/v1/*` and `{ ok: false, error: 'device_revoked' }` from `verifyDevice`. No cache sits in front of the D1 lookup.
- **FR-6** `AccountRpc.verifyDevice(token)` returns `{ ok: true, userId, githubId, deviceId, entitlement }` for a live token, or `{ ok: false, error }` with `error` ∈ `invalid_token | device_revoked | grant_expired | account_deleted`.
- **FR-7** `DELETE /v1/account` revokes all of the user's devices at once, removes the grant and pending row, and runs the deletion job until every bound data holder acknowledges, then deletes the user's rows.
- **FR-8** The owner signs in at `/admin` with GitHub; any other account gets 403; with `OWNER_GITHUB_ID` unset `/admin` returns 503.
- **FR-9** The admin screen lists grants (login, GitHub id, granted date, entitlement, storage cap, note, expiry, active device count, last seen), adds a grant by GitHub username with optional note, expiry date and storage cap, and revokes a grant together with all of that account's device tokens.
- **FR-10** The admin screen lists pending attempts with an **Allow** button that creates a `tester` grant with the default cap, and lists incomplete deletion jobs with their age, flagging any older than 24 hours.
- **FR-11** `entitlementFor(grant)` returns `{ plan: 'tester', storageBytesCap: grant?.storage_cap_bytes ?? 5368709120, maxDevices: null }`, and `quotaDecision(entitlement, usedBytes, incomingBytes)` returns `{ allowed: false, reason: 'quota_exceeded' }` exactly when `usedBytes + incomingBytes > storageBytesCap`.
- **FR-12** Each public sign-in endpoint returns 429 with `Retry-After` once its D-12 limit is exceeded for a client IP, and accepts requests again after the window ends.
- **FR-13** The hourly cron retries incomplete deletion jobs and purges expired short-lived rows (7.10).
- **FR-14** `GET /healthz` returns 200 `{"ok":true,"configured":<bool>}` without revealing any configuration value.

### Non-functional

- **NFR-1** The account service never receives, stores or logs the vault key, a vault passphrase or plaintext user content; no endpoint accepts such data.
- **NFR-2** No GitHub access token is persisted: after any flow, a dump of every D1 table contains no `gho_`/`ghu_` prefix and no token value returned by the GitHub mock.
- **NFR-3** No plaintext device token, authorization code, device code, user code, OAuth state, admin session id or client IP is persisted; only SHA-256 hashes.
- **NFR-4** No response carries `Access-Control-Allow-Origin`; `OPTIONS` on any path returns 405.
- **NFR-5** Local Overdeck never requires an account: this issue adds no code under `src/`.
- **NFR-6** Runtime code uses Web APIs only (no `node:` imports under `services/account/src/`) and imports `cloudflare:workers` only in `src/index.ts`.
- **NFR-7** Every new source file stays under the 1000-line ceiling of `scripts/lint-file-size.sh` (`CEILING=1000`, line 39).
- **NFR-8** Unit tests use injected `deps.now()` for expiry, throttle, retention and rate-limit windows; any test that would wait uses `vi.useFakeTimers()`. No real sleeps.
- **NFR-9** The Worker bundle builds with `wrangler deploy --dry-run` without Cloudflare credentials.

### 7.5 GitHub leg (`src/github.ts`, `src/github-callback.ts`)

1. `startGitHubLeg(rc, purpose, payload)`: `state = randomHex(32)`; insert `auth_requests(sha256(state), purpose, JSON payload, now, now + 600_000)`; 302 to `https://github.com/login/oauth/authorize?client_id=…&redirect_uri=<base>/auth/github/callback&scope=read:user&state=<state>&allow_signup=true` with the D-21 cookie.
2. `GET /auth/github/callback?code&state` (or `?error=access_denied&state`):
   - Missing `state`, missing or mismatched cookie, or no unexpired row → 400 page "This sign-in link expired or was already used. Start again." The row is deleted with `DELETE … RETURNING *` (single use); the cookie is cleared with `Max-Age=0`.
   - `error` present → `onGitHubDenied(purpose, payload)`: PKCE redirects with `error=access_denied&error_description=github_denied`; device marks the grant `denied`; admin shows the sign-in page with "Sign-in was cancelled".
   - Else `exchangeCode(code)`: `POST https://github.com/login/oauth/access_token`, `Accept: application/json`, body `client_id, client_secret, code, redirect_uri`; non-200 or no `access_token` → 502 page "GitHub sign-in failed; try again". Then `fetchUser(token)`: `GET https://api.github.com/user`, `Authorization: Bearer <token>`, `Accept: application/vnd.github+json`, `User-Agent: overdeck-account`. Take numeric `id` and `login`. The token is never written anywhere.
   - Dispatch `onGitHubIdentity(purpose, payload, { githubId, login })` in `pkce.ts`, `device-flow.ts` or `admin/session.ts`.
3. `resolveSignIn(rc, identity, flow)` (the D-11 gate): `isAllowed` false → `recordPendingAttempt(githubId, login, flow)` → `{ allowed: false }`. True → upsert `users` (insert with `crypto.randomUUID()` if new, else update `github_login`); `deleted_at` set → `{ allowed: false, reason: 'account_deleting' }` (page: "This account is being deleted. Try again after deletion finishes."); else `{ allowed: true, userId }`.
4. `lookupUserByLogin(login)` for the admin screen (D-9).

### 7.6 PKCE flow (`src/pkce.ts`)

1. `GET /auth/start?redirect_uri&state&code_challenge&code_challenge_method&platform&environment_id`: validate per D-7 (`code_challenge` `^[A-Za-z0-9_-]{43}$`, `state` 1–256 chars) and D-17; failure → 400 HTML naming the bad parameter, no redirect. Then `startGitHubLeg(rc, 'pkce', { redirectUri, clientState, codeChallenge, platform, environmentId })`.
2. `onGitHubIdentity('pkce')`: `resolveSignIn(…, 'pkce')`. Not allowed → 302 `<redirectUri>?error=access_denied&error_description=invite_only&state=…` (or `account_deleting`). Allowed → `code = 'odc_' + randomHex(32)`; insert `auth_codes(…, expires_at now + 300_000)`; 302 `<redirectUri>?code=…&state=…` via `URL.searchParams.set`.
3. `exchangeAuthorizationCode(rc, form)`: `code_verifier` must match `^[A-Za-z0-9._~-]{43,128}$` else 400 `invalid_request`. `DELETE FROM auth_codes WHERE code_hash = ? RETURNING *` (single use even on failure). No row, expired, `redirect_uri` not identical, or `s256Challenge(verifier) !== code_challenge` → 400 `{"error":"invalid_grant"}`. Re-check `isAllowed` for the user's `github_id` (D-11) → 400 `access_denied` if it fails. Success → `mintDevice` → 200 `{"access_token":"odd_…","token_type":"Bearer","device_id":"…","label":"Linux device"}`.

`s256Challenge(verifier)` = base64url without padding of SHA-256 of the ASCII verifier.

### 7.7 Device flow (`src/device-flow.ts`)

1. `POST /oauth/device/code` (form `platform`, `environment_id`): validate (400 `invalid_request`); `deviceCode = 'oddc_' + randomHex(32)`; `userCode()` (8 chars from `BCDFGHJKLMNPQRSTVWXZ`, retry up to 3 times on a unique-hash collision); insert `device_grants(status 'pending', interval_s 5, created_at now, expires_at now + 900_000)`; 200 `{device_code, user_code:"BCDF-GHJK", verification_uri:"<base>/activate", verification_uri_complete:"<base>/activate?user_code=BCDFGHJK", expires_in:900, interval:5}`.
2. `GET /activate[?user_code=…]`: HTML form (prefilled) posting to `/activate`.
3. `POST /activate`: normalize (uppercase; drop `-` and spaces). Look up a `pending`, unexpired grant by `sha256(normalized)`. None → `hit(rc, 'activate-fail')`; if that returns not-ok → 429 page "Too many wrong codes. Wait 15 minutes and try again."; else re-render with "That code is not valid or has expired." Found → confirm page "Connect a **Windows device** to your Overdeck account?" (label from the grant's platform) with a form POSTing to `/activate/confirm`.
4. `POST /activate/confirm`: re-validate the grant; `startGitHubLeg(rc, 'device', { deviceCodeHash })`.
5. `onGitHubIdentity('device')`: grant missing or expired → page "This code expired. Run the sign-in command again." `resolveSignIn(…, 'device')`: not allowed → `status='denied'` + invite-only page. Allowed → `status='approved', user_id=…` + "Device connected. You can close this tab and return to your terminal."
6. `exchangeDeviceCode(rc, form)` (field `device_code`): no row → 400 `invalid_grant`. Expired → delete, 400 `expired_token`. `last_polled_at` set and `now - last_polled_at < interval_s * 1000` → `interval_s += 5`, `last_polled_at = now`, 400 `{"error":"slow_down","interval":<new>}`. Else `last_polled_at = now`, then `pending` → 400 `authorization_pending`; `denied` → delete, 400 `access_denied`; `approved` → re-check `isAllowed` (D-11; fail → delete, `access_denied`), delete row, `mintDevice`, 200 token response as in 7.6.

### 7.8 Device credentials and `verifyDevice` (`src/crypto.ts`, `src/devices.ts`, `src/contract.ts`, `src/index.ts`)

```ts
// contract.ts — consumed by PAN-4297 (hosted vault) and later services.
export type { Entitlement } from './entitlement.ts';
export { quotaDecision, DEFAULT_STORAGE_CAP_BYTES } from './entitlement.ts';
export type VerifyResult =
  | { ok: true; userId: string; githubId: number; deviceId: string; entitlement: Entitlement }
  | { ok: false; error: 'invalid_token' | 'device_revoked' | 'grant_expired' | 'account_deleted' };
export interface AccountDataHolder { deleteAccountData(userId: string): Promise<{ deleted: true }> }
```

- `mintDevice(rc, userId, platform, environmentId)`: `token = 'odd_' + randomHex(32)`. Active row for `(userId, environmentId)` → `UPDATE devices SET token_hash=?, platform=?, last_used_at=NULL WHERE device_id=?` (label kept). Else insert with `crypto.randomUUID()` and the default label. Returns `{ token, deviceId, label }`; the plaintext token exists only in this return value.
- `verifyDeviceToken(rc, token)`: shape `^odd_[0-9a-f]{64}$` else `invalid_token`. One query joining `devices` → `users` → `grants` (LEFT JOIN) by `sha256(token)`. No row → `invalid_token`; `deleted_at` → `account_deleted`; `revoked_at` → `device_revoked`; not owner and no unexpired grant → `grant_expired`; else D-18 throttle (`UPDATE devices SET last_used_at=? WHERE device_id=? AND (last_used_at IS NULL OR last_used_at < ?)`) and `ok: true` with `entitlementFor(grant)`.
- `authenticateRequest(req, rc, { allowExpiredGrant })`: `invalid_token`/`device_revoked`/`account_deleted` → 401 `{"error":<code>}` with `WWW-Authenticate: Bearer error="invalid_token"`; `grant_expired` → 403 unless `allowExpiredGrant`.
- `index.ts`: `export class AccountRpc extends WorkerEntrypoint<Env> { async verifyDevice(token: string): Promise<VerifyResult> { return verifyDeviceToken(makeRc(this.env, this.ctx), token); } }`. The scaffold version returns `{ ok: false, error: 'invalid_token' }`.

### 7.9 Device API (`src/api.ts`)

- `GET /v1/me` (expired grants allowed) → `{ userId, githubId, githubLogin, deviceId, entitlement, access: { status: 'active' | 'grant_expired', expiresAt: number | null } }`.

### 7.10 Deletion and maintenance (`src/deletion.ts`, `src/maintenance.ts`)

`requestDeletion(rc, userId)` runs one `DB.batch`: `UPDATE users SET deleted_at = ?`; `UPDATE devices SET revoked_at = ?, revoked_by = 'account-deletion' WHERE user_id = ? AND revoked_at IS NULL`; `DELETE FROM grants WHERE github_id = ?`; `DELETE FROM pending_attempts WHERE github_id = ?`; `INSERT OR IGNORE INTO deletion_jobs (user_id, requested_at, holders_pending) VALUES (?, ?, ?)` with `holders_pending = JSON.stringify(boundHolders(env))` (`['vault']` when `env.VAULT` is set, else `[]`). Then `rc.ctx.waitUntil(runDeletionJob(rc, userId))`. Response 202 `{"deletionRequestedAt":<requested_at>}`; a repeat returns the original timestamp.

`runDeletionJob(rc, userId)`: for each pending name, call the bound holder's `deleteAccountData(userId)`; success removes the name; a throw increments `attempts` and stores `last_error` (message, ≤ 200 chars); a name with no binding stays pending with `last_error = 'holder <name> not bound'`. When none remain: `DELETE FROM devices WHERE user_id = ?`, `DELETE FROM users WHERE user_id = ?`, `UPDATE deletion_jobs SET completed_at = ?, holders_pending = '[]'`.

`runMaintenance(env, deps)` (cron `0 * * * *`): `runDeletionJob` for every job with `completed_at IS NULL`; then purge `auth_requests`, `auth_codes`, `admin_sessions` with `expires_at < now`; `device_grants` with `expires_at < now - 3_600_000`; `pending_attempts` with `last_seen_at < now - 30 days`; `devices` with `revoked_at < now - 90 days`; `rate_limits` with `window_start < now - 3_600_000`; `deletion_jobs` with `completed_at < now - 30 days`.

### 7.11 Rate limiting (`src/rate-limit.ts`)

```ts
export const LIMITS = {
  'auth-start':      { limit: 20,  windowMs: 600_000 },
  'github-callback': { limit: 30,  windowMs: 600_000 },
  'device-code':     { limit: 10,  windowMs: 600_000 },
  'token':           { limit: 120, windowMs: 600_000 },
  'activate':        { limit: 30,  windowMs: 900_000 },
  'activate-fail':   { limit: 10,  windowMs: 900_000 },
  'admin-login':     { limit: 10,  windowMs: 600_000 },
} as const;
export type Bucket = keyof typeof LIMITS;
export async function hit(rc: RequestContext, bucket: Bucket): Promise<{ ok: true } | { ok: false; retryAfterS: number }>;
```

`hit` uses one upsert so concurrent requests cannot both reset a window:

```sql
INSERT INTO rate_limits (bucket, client_hash, window_start, count) VALUES (?1, ?2, ?3, 1)
ON CONFLICT (bucket, client_hash) DO UPDATE SET
  count        = CASE WHEN rate_limits.window_start <= ?3 - ?4 THEN 1 ELSE rate_limits.count + 1 END,
  window_start = CASE WHEN rate_limits.window_start <= ?3 - ?4 THEN ?3 ELSE rate_limits.window_start END
RETURNING window_start, count;
```

(`?3` = now, `?4` = `windowMs`.) `count > limit` → `{ ok: false, retryAfterS: ceil((window_start + windowMs - now) / 1000) }`. `client_hash = sha256Hex(req.headers.get('CF-Connecting-IP') ?? 'unknown')`.

### 7.12 Admin screen (`src/admin/session.ts`, `src/admin/screen.ts`, `src/admin/pending.ts`)

- `GET /admin` without a valid session → sign-in page with a `POST /admin/login` button "Sign in with GitHub". `POST /admin/login` → `startGitHubLeg(rc, 'admin', {})`.
- `onGitHubIdentity('admin')`: `githubId === config.ownerGithubId` → session (`randomHex(32)`, `csrf = randomHex(16)`, `expires_at = now + 43_200_000`), D-20 cookie, 302 `/admin`. Otherwise 403 page "This page is for the Overdeck operator." No pending row.
- `requireOwnerSession(req, rc)`: cookie → `sha256` → unexpired session whose `github_id` still equals `ownerGithubId`; else the sign-in page. POSTs also pass the D-20 `csrf` and `Origin` checks (403 page "Request rejected").
- `POST /admin/logout` → delete the session row, clear the cookie, 302 `/admin`.
- **Page**, top to bottom: (1) header "Overdeck accounts (invite-only)", owner login, logout form; (2) "Owner (always allowed): GitHub id …"; (3) **Allowlisted accounts** table — login (link `https://github.com/<login>`), GitHub id, granted date (UTC `YYYY-MM-DD`), entitlement, storage cap ("5 GB" or the set value), note, expires (date / "never" / "expired" in the warning color), active devices, last seen (max `last_used_at` of active devices or "—"), **Revoke** — sorted by `granted_at` descending; (4) **Add an account** form — GitHub username (`^[A-Za-z0-9](?:[A-Za-z0-9-]{0,38})$`), note (≤ 200 chars), expiry date (end of that UTC day), storage cap in GB (integer 1–1000, empty = default 5); errors re-render with the message above the form; (5) **Pending sign-in attempts** — login, GitHub id, first seen, last seen, attempts, flow, **Allow**, with the D-14 sentence; (6) **Account deletions in progress** — user id, requested at, age in hours, holders pending, attempts, last error; rows older than 24 hours show "overdue" in the warning color.
- `POST /admin/grants` (form `username`, `note`, `expires`, `cap_gb`, `csrf`) → `lookupUserByLogin` → `addGrant(githubId, login, { note, expiresAt, storageCapBytes }, 'admin-add')` as an upsert (re-adding updates note, expiry and cap) and delete any pending row for that id → 303 `/admin`.
- `POST /admin/grants/:githubId/revoke` → `revokeGrant`: one batch that deletes the grant and sets `revoked_at = now, revoked_by = 'operator'` on every active device of that user → 303 `/admin`.
- `POST /admin/pending/:githubId/allow` → read the pending row (404 page if gone) → `addGrant(githubId, login, {}, 'admin-allow-pending')` and delete the pending row → 303 `/admin`.

### 7.13 Entitlement, storage cap and the hosted vault contract

```ts
// entitlement.ts — the only entitlement source until PAN-4294 replaces the body of entitlementFor.
export const DEFAULT_STORAGE_CAP_BYTES = 5 * 1024 ** 3; // 5 GB
export interface Entitlement { plan: 'tester'; storageBytesCap: number; maxDevices: number | null }
export function entitlementFor(grant: GrantRow | null): Entitlement {
  return { plan: 'tester', storageBytesCap: grant?.storage_cap_bytes ?? DEFAULT_STORAGE_CAP_BYTES, maxDevices: null };
}
export function quotaDecision(e: Entitlement, usedBytes: number, incomingBytes: number):
  { allowed: true } | { allowed: false; reason: 'quota_exceeded'; capBytes: number; usedBytes: number } {
  return usedBytes + incomingBytes > e.storageBytesCap
    ? { allowed: false, reason: 'quota_exceeded', capBytes: e.storageBytesCap, usedBytes }
    : { allowed: true };
}
```

**Contract the hosted vault (PAN-4297) must implement** (recorded in `docs/ACCOUNT-SERVICE.md` "Hosted vault contract"; not built here):

1. **Auth:** every request carries `Authorization: Bearer odd_…`; the vault calls `env.ACCOUNT.verifyDevice(token)` through a service binding to `AccountRpc` and refuses anything but `ok: true`.
2. **Storage cap:** one Durable Object per vault holds `usedBytes`. Before accepting an object `PUT`, the vault calls `quotaDecision(entitlement, usedBytes, body.length)`; `allowed: false` → 507 `{"error":"quota_exceeded","capBytes":…,"usedBytes":…}` and nothing is written. Re-putting an existing id is free (content-addressed, no size change).
3. **CAS:** refs live in the per-vault Durable Object's storage. Create-if-absent (`If-None-Match: *`) and swap (`If-Match: <version>`) run inside the object's single-threaded `fetch`, so the read-compare-write needs no lock; a mismatch → 412.
4. **Chunks** live in R2 under content-derived keys; immutable.
5. **Deletion:** the vault's RPC entrypoint implements `AccountDataHolder.deleteAccountData(userId)` idempotently, deleting every R2 object and the Durable Object's storage for that user's vault within 24 hours; the account service's `VAULT` binding points at it.
