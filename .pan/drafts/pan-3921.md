# PAN-3921 — Route conversations and `pan handoff` through the terminal backend (Herdr) with role tokens; PTY supervisor off on Herdr

- Issue: https://github.com/eltmon/overdeck/issues/3921
- Parent: PAN-3917 (The Overdeck Cut), FR-5 and W8 step 4; follow-up named in `docs/THE-CUT.md` line 214.
- Sibling: PAN-3936 (https://github.com/eltmon/overdeck/issues/3936) — the `muse.ts` / `kimi-code.ts` runtime adapters, split out at planning time (see Decisions D9).
- Branch: `feature/pan-3921`, planned against `b7bedc3278a` (2026-09-19).

## Glossary

- **Terminal backend** — the adapter that owns agent terminals: creates workspaces, starts panes, delivers prompts, reports liveness. Two adapters: **Herdr** (default) and **tmux**. Contract: `src/lib/terminal-backends/types.ts`. Selection: `hostTerminalBackendName()` in `src/lib/terminal-backends/select.ts` (env `OVERDECK_TERMINAL_BACKEND`, then `terminal.backend` in config, then Herdr when its socket exists).
- **Launch door** — `launchAgentPane(request, backend?)` in `src/lib/terminal-backends/launch.ts` (line 69). Resolves the backend, finds or creates the issue workspace (`workspaceFor`), starts the pane (`startAgent`) and stamps the pane tokens. Work agents, specialists, `pan spawn` and `pan strike` already use it; conversations do not.
- **Pane tokens** — `PaneTokens { issue?, role, harness, model }` (`packages/contracts/src/terminal-backend.ts` line 25). Stamped with `pane.report_metadata` on Herdr; derived from agent state on tmux (`tokensFromLaunchMetadata`, `src/lib/terminal-backends/prompt-guard.ts` line 51). The dashboard read model turns tokens into a `BackendPane` (`packages/contracts/src/backend-pane.ts`) and the issue view renders rows by `role` (`useDrawerData.ts` line 172 filters `pane.role === 'review'`).
- **Agent role** — `AgentRole = "work" | "worker" | "review" | "test" | "uat" | "strike" | "plan"` (`terminal-backend.ts` line 18). There is no value for a conversation today.
- **Conversation** — an operator-driven harness session registered in the `conversations` table (`src/lib/overdeck/conversations.ts`). Its identity on the backend is `tmuxSession` (`conv-<name>`), which on tmux is the session name and on Herdr becomes the live agent name (`agent.rename`). The dashboard terminal, `pan tell`, and `deliverAgentMessage` all address it by that name.
- **Conversation state dir** — `~/.overdeck/conversations/<tmuxSession>/` (`stateDir` in `spawnConversationSession`, `conversation-runtime.ts` line 557). Holds `launcher.sh`; this PRD adds `pane-role`.
- **PTY supervisor** — `node dist/pty-supervisor.js <harness …>` wrapper that gives tmux launches a delivery socket. It allocates a second pseudo-terminal, so the pane's foreground process stays `node` and Herdr's detector (which keys on the foreground process) never sees the harness. Proved live in PAN-3917 fix11 (`docs/TERMINAL-BACKENDS.md` lines 166–195). `decideSupervisorForWorkAgent` (`src/lib/agents/supervisor-channels.ts` line 138) already refuses it when `options.backend === 'herdr'`.
- **Herdr detection** — after `pane.split` + `pane.send_input`, the adapter polls until Herdr reports an agent in the pane, up to `AGENT_DETECT_TIMEOUT_MS = 60_000` (`herdr.ts` line 64); a timeout is a launch failure and the pane is closed. Herdr 0.9.1 detects these kinds: pi, claude, codex, gemini, cursor, devin, agy, cline, omp, mastracode, opencode, copilot, kimi, kiro, droid, amp, grok, hermes, kilo, qodercli, qwen, letta, maki, muse (from `herdr agent start --help`). `acp` (Overdeck's ACP host process) is not a detectable kind.
- **Liveness door** — one function that answers "is this conversation's terminal alive?" for whichever backend the host runs. Work agents have it in `isAlive` (`src/lib/agents/liveness.ts` line 149). Conversations do not: every conversation liveness read is a tmux call today.
- **Runtime census** — `getRuntimeCensus()` (`src/lib/runtime-census.ts` line 173): one `tmux list-panes` + one `ps` snapshot. tmux-only by construction.
- **Fork pipeline** — `runForkPipeline` in `src/lib/overdeck/conversation-forks.ts` (line 412); `pan fork`, `pan handoff`, and the dashboard fork modal all enter through `handleConversationSummaryFork` (line 706), which creates the conversation row and then spawns it via `ensureForkSessionReady` (line 315) → `spawnConversationSession`.
- **FR-17 prompt guard** — `checkPrompt` in `prompt-guard.ts`: a prompt to a `worker` pane of issue X is accepted only from X's `work` pane or from an operator conversation (a sender with no `issue` token).

## Problem

`spawnConversationSession` (`src/lib/overdeck/conversation-runtime.ts` line 545) creates its pane with tmux `createSession` (line 808) and wraps the harness in the PTY supervisor whenever `shouldUseSupervisorForConversation` says so (line 705). On a Herdr host that has three consequences:

1. The pane never reaches Herdr. Conversations, `pan handoff`, and `pan flywheel start` land in tmux while every work agent lands in Herdr; the issue tree cannot show a handoff as a Review row (PAN-3917 FR-5), and an operator conversation is invisible to the backend inventory.
2. If the pane were simply redirected to Herdr today, the supervisor wrapper would make detection fail and `startAgent` would close the pane after 60 s — the exact `pan start PAN-3705` failure.
3. Every conversation liveness read is tmux-only: `conversationSessionAlive` does not exist; `conversation-reads.ts` line 436, `conversation-list.ts` line 101, `conversation-delivery.ts` line 188, the fork seams (`conversation-forks.ts` lines 268–293), `pending-respawn.ts` line 70, `pollConversations` (`conversation-lifecycle.ts` line 128, via the tmux census), and `pan flywheel start` (`flywheel.ts` lines 85–93) all ask tmux. A Herdr-hosted conversation would read as dead everywhere, and the lifecycle poller would mark it ended 30 s after creation.

Delivery and the terminal are already backend-aware by agent name: `deliverAgentMessage` routes to `herdrBackend.prompt` when `findHerdrAgent(id)` answers (`src/lib/agents/delivery.ts` lines 380–399), and the terminal WebSocket resolves `resolveHerdrTerminalId(sessionName)` first (`src/dashboard/server/services/terminal-service.ts` line 192). Naming the Herdr agent `conv-<name>` (the `tmuxSession`) makes both work unchanged.

## Requirements

- **FR-1** `AgentRole`, `AGENT_ROLES`, and the `BackendPane.role` literal gain the value `conversation`. `toPaneRole('conversation')` returns `'conversation'`. Nothing that renders panes by role treats `conversation` as a review, test, uat, work, or worker pane.
- **FR-2** `spawnConversationSession` launches through `launchAgentPane` with `agentId = tmuxSession`, `argv = ['bash', <launcherScript>]`, `env = { ...BLANKED_PROVIDER_ENV, TERM: 'xterm-256color' }`, and tokens `{ issue: issueId (omitted when absent), role, harness, model: model ?? 'default' }`. On tmux the observable behavior is unchanged (same session name, cwd, env, launcher command, `destroy-unattached off`, `remain-on-exit on`).
- **FR-3** The PTY supervisor is used for a conversation only when the resolved backend is `tmux` and `shouldUseSupervisorForConversation` is true. On Herdr no `pty-token` is written, no `node … pty-supervisor.js` appears in the launcher, and `waitForPtySupervisorOrFallback` is not called.
- **FR-4** A conversation's pane role is persisted in `<stateDir>/pane-role` and read on every respawn, resume, restart-all, and fork-pipeline spawn. A conversation with no persisted role and no explicit role launches with role `conversation`.
- **FR-5** `pan handoff` accepts `--role <role>` (`conversation | work | review | test | plan`). The fork endpoint accepts `role` (validated with `isAgentRole`, `400 Invalid role` otherwise) and persists it as the new conversation's pane role before the fork pipeline starts. Without `--role` the role is `conversation`. A handoff launched with `--issue PAN-1 --role review` renders as the Review row of PAN-1 (`pane.role === 'review'`, `pane.issue === 'PAN-1'`).
- **FR-6** `pan handoff --issue <id>` with no `--cwd` uses `getIssueWorkspacePath(id)` as the successor's cwd when that directory exists; otherwise today's fallback (parent cwd, then `process.cwd()`). An explicit `--cwd` always wins. The `--issue` value is also the pane's `issue` token, so on Herdr the pane is placed in that issue's Herdr workspace (`workspaceFor(issueId, cwd)`).
- **FR-7** One conversation liveness door, `src/lib/overdeck/conversation-liveness.ts`, exports `conversationSessionAlive(tmuxSession)`, `listLiveConversationSessions()`, `conversationHarnessAlive(tmuxSession)`, and `waitForConversationSession(tmuxSession, timeoutMs)`. On tmux they call `sessionExists`, `listSessionNames`, `isHarnessProcessAlive`, and the existing poll loop. On Herdr they call `probeHerdrAgentLiveness` / `listHerdrAgents` by agent name; `indeterminate` (socket did not answer) reads as **alive**, `absent` and `exited` read as dead. Every tmux liveness call in the conversation code paths listed in W5 goes through this door.
- **FR-8** `pollConversations` on a Herdr host derives "session gone" and "harness gone" from the Herdr inventory (`listHerdrAgents`), not from the tmux census, and never marks a conversation ended while the census/inventory is unavailable. A Herdr conversation younger than `AGENT_DETECT_TIMEOUT_MS + SPAWN_GRACE_PERIOD_MS` (90 s) is never marked ended.
- **FR-9** `stopConversationRuntime` closes the Herdr pane by agent name (`findHerdrAgent` → `herdrBackend.close({ paneId })`) in addition to the process-tree kill; `spawnConversationSession` closes an existing pane of the same name on either backend before launching (tmux `killSession`, Herdr `pane.close`).
- **FR-10** `waitForConversationRuntimeReady` on a Herdr host waits with `herdrBackend.wait({ agentName: tmuxSession }, ['idle', 'blocked'], timeoutMs)` for every harness whose tmux readiness is a pane scrape (ohmypi, codex-tui, muse, kimi-code). The claude-code ready-signal file and the ACP/codex-app-server socket waits stay as they are.
- **FR-11** `pan flywheel start` waits for the conversation through the liveness door and delivers the kickoff command through `deliverAgentMessage` instead of `waitForTmuxSession` + `sendKeysAsync`.
- **FR-12** Documentation: `docs/TERMINAL-BACKENDS.md` states that conversations, `pan handoff`, and `pan flywheel start` launch through the launch door and lists the conversation liveness door; the "Known gap" paragraph names only `isAliveSync` and PAN-3936. `docs/THE-CUT.md` line 214 is rewritten to say the placement landed in PAN-3921 and how `--role` selects the row. `sync-sources/skills/pan-handoff/SKILL.md` documents `--role` and the `--issue` cwd default. The `launch.ts` module header no longer says handoff does not route through it.
- **NFR-1** `npm run typecheck`, `npm run lint`, and `npm test` pass. `scripts/lint-skills.sh` passes (the `--role` flag and its skill text land in one commit).
- **NFR-2** No test touches the live Herdr socket or the live tmux server: backends are injected (`launchAgentPane(request, backend)`, `LivenessDeps`), and every poll or timeout uses Vitest fake timers.
- **NFR-3** Server-reachable code stays async (`execFile`/`spawn`, `sendKeysAsync`); no `execSync`.
- **NFR-4** No per-harness fallback to tmux on a Herdr host. A harness Herdr cannot detect fails the launch with the adapter's diagnosis, exactly as work agents do today.

## Decisions

- **D1 — New role value `conversation`.** `PaneTokens.role` is required and closed. Reusing `work` for conversations would make every `--issue` conversation a second Work row and, under FR-17, let it prompt that issue's workers. `conversation` with an `issue` token is an issue-scoped conversation that the guard does **not** treat as the work pane; `conversation` with no `issue` is an operator conversation, exactly as FR-5 of PAN-3917 defines it. Rule: a token `role` other than `conversation` is stamped only when the operator asked for it with `--role`.
- **D2 — Role lives in a state-dir file, not a DB column.** The `conversations` table has two migration systems behind it (`overdeck.db`); a column would need both. `<stateDir>/pane-role` is created by the same code that creates `launcher.sh`, survives respawn/resume/restart-all/fork recovery, and disappears with the state dir.
- **D3 — Handoff cwd defaults to the issue workspace only when `--issue` is given and `--cwd` is not.** That is what FR-5 of PAN-3917 asks for ("places its pane in the issue workspace") and it removes the case where a successor inherits the primary checkout as cwd. The workspace is a git worktree, so the existing `isInsideGitWorkTree` check passes.
- **D4 — Herdr `indeterminate` is alive.** A Herdr outage must not end every conversation. Same rule `isAliveOnHerdr` already applies to agents.
- **D5 — `stopConversationRuntime` keeps the process-tree kill.** `conversationRuntimeRootPids` matches the launcher script path in `ps` output, which is backend-neutral; the Herdr `pane.close` is added, not substituted.
- **D6 — Readiness on Herdr is `agent.wait`.** Herdr's `idle|blocked` states are the oracle for any detected kind; pane scrapes (`waitForPiTuiReady`, `waitForCodexTuiReady`, `waitForMuseTuiReady`) are tmux-only by construction.
- **D7 — Conversation launcher shape is unchanged (no `exec`, keep-alive loop).** Implementation checkpoint C1 below verifies Herdr detects the non-exec'd child; fallback is documented there.
- **D8 — The `conversations` Herdr workspace keeps its `issue: 'conversations'` workspace token.** `paneFromBackendSnapshot` (`derived-issue-state.ts` line 471) and the backend inventory read **pane** tokens only (`backend-inventory.ts` line 262); no reader consumes workspace tokens (verified by grep 2026-09-19). Operator conversation panes carry no `issue` token.
- **D9 — `muse.ts` / `kimi-code.ts` adapters are PAN-3936.** Their only live callers are specialist rotation and crash respawn; the change is independent of everything here (it needs only `launchAgentPane` and `prepareSupervisorForFreshLaunch`, both on main), and keeping it here pushes the plan over the finalize surface gate (25 files / 6 subsystems).
- **D10 — No tmux fallback per harness (NFR-4).** Parity with work agents; a fallback would put one conversation in tmux and its siblings in Herdr, and the inventory would read the tmux one as dead.
