# PAN-5498: auto-start after planning honors --host and survives an interrupted start

**Issue:** https://github.com/eltmon/overdeck/issues/5498
**PR:** https://github.com/eltmon/overdeck/pull/5524
**Status:** implemented on `feature/pan-5498` (commits 27f9e61e3af, c6558597e85). This PRD records the design so the xBRIEF checklist can be verified.

## Glossary

- **Auto-spawn consent record:** the v2 JSON file `~/.overdeck/agents/planning-<id>/auto-spawn-on-finalize.json` (`src/lib/planning/auto-spawn-consent.ts`). Status is `granted`, `claimed` or `spent`; it also carries `workModel` and `workspaceLocation`.
- **Consent-bearing spawn request:** a `POST /api/agents` body with `autoSpawnConsentRequired: true`. complete-planning and deacon-lite retries send it.
- **Stack-health gate:** the check in `src/dashboard/server/routes/agents/spawn-issue.ts` that rebuilds an unhealthy workspace Docker stack and refuses with 422 `start_blocked_stack_unhealthy` unless the host override is set (`allowHost`).
- **Host override:** the operator's `--host` choice, confirmed by the phrase `I understand this bypasses workspace isolation for <ID>` (`buildHostOverrideConfirmation`).
- **Pipeline journal:** append-only `<workspace>/.overdeck/pipeline.jsonl` (`src/lib/cloister/pipeline-journal.ts`). The last `handoff.*` entry drives deacon-lite.
- **Deacon-lite retry:** `retryDeferredHandoffs` in `src/lib/cloister/deferred-handoff.ts`; backoff 2, 4, 8, 16, then every 20 minutes inside a 2 hour window.

## Problem

`pan start <id> --plan auto --host --yes` sometimes never starts the work agent after planning finalizes.

1. `--host` reaches the planning start but not the finalize-time spawn request or the deacon-lite retries. With no healthy Docker stack the spawn route refuses with 422 (PAN-5484 at 12:29:43Z on 2026-11-17). PAN-5483 lost `--host` too and started only because its rebuild produced containers.
2. When the spawn request is in flight during a slow stack rebuild and the dashboard restarts, nothing is journaled, so deacon-lite has nothing to resume (PAN-5469).

## Requirements

- **FR-1:** When planning starts with a confirmed `--host`, the auto-spawn consent record stores `hostOverride: true`. A new planning cycle without `--host` clears it, and a spent record grants nothing.
- **FR-2:** The start-planning route accepts `host: true` only with the matching confirmation phrase, and refuses a mismatch with 409 `host_override_confirmation_required`.
- **FR-3:** A consent-bearing spawn request uses the consent record's host override as `allowHost`. A request without consent never does.
- **FR-4:** complete-planning appends `handoff.requested` to the pipeline journal before the spawn POST, and `handoff.abandoned` (`outcome: failed`) when the POST fails outright.
- **FR-5:** deacon-lite resumes a trailing `handoff.requested` 10 minutes after the request, on the existing backoff, and stands down when the work agent was started after the request.
- **FR-6:** `pan show` and the flywheel board render `handoff.requested`.
- **NFR-1:** `planning-promotion.ts` stays under its file-size allowance (997 lines).
- **NFR-2:** Delay tests use `vi.useFakeTimers()`.

## Critique response

### Finalize timeout can leave no recoverable handoff

Scope decision: this issue covers a dashboard death after promotion finishes, which is the PAN-5469 evidence. PAN-5469's server-side promotion completed (commit `418ad11f928` carries the `Plan-Finalized` trailer and the issue got `planned`), and no handoff was attempted, so the loss happened at or after the spawn. `handoff.requested` is now journaled before the spawn POST, so deacon-lite resumes that case (FR-4, FR-5).

A death during promotion itself (before the journal entry) leaves an unpromoted plan. Recovering it needs a consumer for the pending-promotion marker, which does not exist today, and the v2 consent fix in `readAutoSpawnOnFinalize`. That is a separate recovery mechanism, tracked in PAN-5527 (https://github.com/eltmon/overdeck/issues/5527). Journaling the request earlier would let deacon-lite start a work agent on a plan that was never promoted, which is worse than the gap.

### A failed journal write is reported as durable

Fixed. `journalHandoffRequest` now reads the journal back and returns `true` only when the `handoff.requested` entry is on disk. When it is not, it warns that a restart before the start answers will not be resumed. Precondition: recovery needs a writable `<workspace>/.overdeck/pipeline.jsonl`. Test: `src/lib/overdeck/__tests__/planning-handoff-journal.test.ts`.

### Route acceptance criteria have no route verification

FR-2 now has a route test: `src/lib/overdeck/__tests__/start-planning-host-override.test.ts` checks the 409 `host_override_confirmation_required` refusal with no mutation, and that the exact phrase passes. FR-3 lives in `spawn-issue.ts`, which has no route test harness today. Its data side is covered by `auto-spawn-consent.test.ts` (`readAutoSpawnConsentHostOverride`). The route side is one guarded expression: `consentHostOverride` is read only when `autoSpawnConsentRequired` is set, and that flag is only honored for internal requests. Building a harness for that route is out of scope for this fix.

### Unresolved after two critic rounds

- Planned state precedes recoverable handoff
- A stranded consent claim stops recovery
