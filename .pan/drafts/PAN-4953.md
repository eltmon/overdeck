## Glossary

- **Hermes:** Hermes Agent, a self-hosted Python chat agent. Source: `~/Projects/hermes-agent`.
- **Hermes plugin:** a Python package Hermes loads through the `hermes_agent.plugins` entry-point group (a pip install) or from a directory `~/.hermes/plugins/<name>/` that holds `plugin.yaml` and `__init__.py` (a "directory drop"). The package exposes `register(ctx)`.
- **`ctx` (PluginContext):** the object Hermes passes to `register`. Methods this plugin uses, all in `~/Projects/hermes-agent/hermes_cli/plugins.py` unless noted:
  - `ctx.get_config(key, default)` (line 266): reads `plugins.entries.<plugin_id>.settings.<key>` from `config.yaml`, falling back to the legacy `plugins.entries.<plugin_id>.config.<key>`. It does **not** read keys placed directly under `plugins.entries.<plugin_id>`.
  - `ctx.call_mcp(server, tool, arguments, timeout=30)` (line 502): calls one tool on a Hermes-configured MCP server through Hermes's own MCP client. It raises `PermissionError` when `server` is not in `plugins.entries.<plugin_id>.mcp_allowlist` (read from the entry root, line 558-566). It returns an **envelope** (see below).
  - `ctx.register_hook(name, callback)` (line 935).
  - `ctx.register_command(name, handler, description, args_hint)` (line 649): an in-chat slash command. The handler is `fn(raw_args: str, **context) -> str | None`; Hermes passes `source`, `session_id`, `session_key`, `platform` only to keyword parameters the handler declares (`hermes_cli/plugin_command_dispatch.py:11-31`).
  - `ctx.register_skill(name, path, description)` (`hermes_cli/plugins_content.py:32`): raises `FileNotFoundError` when `path` does not exist.
  - `ctx.register_cli_command(name, help, setup_fn, handler_fn, description)` (line 635): a `hermes <name> …` subcommand; `setup_fn` receives the argparse subparser, `handler_fn` becomes `set_defaults(func=…)`.
- **Envelope:** what `ctx.call_mcp` returns, built by `_mcp_envelope` (`plugins.py:534-552`) from the JSON string `_render_call_tool_result` makes (`tools/mcp_tool_handlers.py:651-689`):
  - success: `{"ok": True, "result": "<the tool's text block>"}`. Overdeck's tools put `JSON.stringify(data, null, 2)` in that text block (`jsonResult`, `src/lib/mcp/tool.ts:45-47`), so `result` is a **JSON string that must be decoded a second time**.
  - tool error (`isError: true`, for example the missing-`approve` refusal): `{"ok": False, "error": "<text>"}`.
  - over 64 KB: `result` is cut and the envelope carries `"truncated": True`; the cut string is not valid JSON.
- **Plugin id:** the key Hermes files a plugin under. An entry-point plugin's id is the entry-point **name** (`hermes_cli/plugins_discovery.py:91-95`); a directory plugin's id is the **directory name** (`plugins_discovery.py:144`). This plugin's id is `overdeck` in both cases.
- **`pre_llm_call` hook:** Hermes calls it before each model request with keyword arguments (`session_id`, `user_message`, `conversation_history`, `is_first_turn`, `model`, `platform`, …; `hermes_cli/hooks.py:112-115`). Returning `{"context": "<text>"}` injects that text into the turn (`hermes_cli/plugins_dispatch.py:282-283`). It runs under `plugins.hook_callback_timeout`, default 30 s (`config_defaults.py:1704`).
- **Overdeck MCP server:** the tools in `src/lib/mcp/`. A bot reaches them through the **Overdeck connector** (`pan mcp connector serve`, loopback `http://127.0.0.1:7466/mcp`, bearer = the connector's `odl_` local token) or directly at a dashboard's `/mcp` over Tailscale with an `odk_` access token.
- **`list_pending_input`:** the read tool (`src/lib/mcp/tools-approve.ts:97-140`, scope `read:conversations`). It returns `{"machines": [{"environmentId", "label", "conversations": [...], "agents": [...]}], "fleetError"?}`. The first machine is `{"environmentId": null, "label": "this machine"}`. A linked machine's conversation names are already prefixed `@<environmentId>/<name>`; its agents carry `"remote": true`.
- **Conversation row** (from `getConversationsPendingInputFeed`, `src/lib/overdeck/conversation-reads.ts:431-460`): `name`, `title`, `issueId`, `harness` (default `claude-code`), and any of `pendingAskUserQuestion` (`{toolUseId, askedAt, questions: [{question, header?, multiSelect?, options: [{label, description?}]}]}`, `src/lib/agent-enrichment.ts:75-85`), `pendingProposedPlan` (`{toolUseId, askedAt, plan}`), `pendingPaneChoice` (`{signature, title, contextLines, options: [{…label…}], selectedIndex, …}`, `src/lib/session-pane-choice.ts:21-30`), `pendingPermission` (`{signature: string|null, answerable, agentLabel, toolName, header, …, options: [{choice, label}], since}`, `src/lib/overdeck/conversation-permission.ts:42-59`), `heldKickoff` (`{since, focus?}`).
- **Agent row** (from `localNeedsYou`, `src/dashboard/server/routes/needs-you.ts:30-41`): `id`, `issueId`, `pendingInputKinds` (strings such as `askUserQuestion`, `permissionRequest`, `exitPlanMode`, `paneQuestion`, `agentTurnEnded`; `src/lib/agent-enrichment.ts:55-73`), optional `pendingAskUserQuestion`, optional `permissionRequests: [{requestId, toolName, description, inputPreview, createdAt}]`, and `remote: true` on a linked machine's agent.
- **Answer tools** (all scope `approve`, `src/lib/mcp/tools-approve.ts`): `answer_question` (line 143), `answer_permission` (194), `answer_pane_choice` (222), `answer_codex_approval` (247), `answer_pi_ask` (274), `answer_plan` (299), `answer_agent_plan` (328), `answer_agent_permission` (357). A token without `approve` does not see them in `tools/list` and is refused if it calls one.
- **Pending item:** one answerable (or listed-only) thing the plugin derives from the `list_pending_input` result. One row can produce several items (for example one per agent permission request).
- **Item key:** a tuple that identifies a pending item across two reads: `(target, kind, identity)`, where `identity` is the prompt's own signature, `toolUseId` or `requestId`.
- **Snapshot:** the numbered list `/overdeck pending` last showed in one chat session, kept in memory for 10 minutes so `/overdeck answer <n>` can refer to it by number.
- **CP-9:** the epic's implementation checkpoint for this item: a live run of the plugin in the target Hermes.

## Corrections to the epic's W-INT1

- **C-1 Settings live under `settings:`.** The epic's YAML puts `summary` and `allow_answers` under `plugins.entries.overdeck`. The plugin reads them with `ctx.get_config`, so they move to `plugins.entries.overdeck.settings`. `mcp_allowlist` stays at the entry root, where Hermes reads it. `hermesConfig`, `configuration/mcp.mdx` and the package README change to match (WI-6).
- **C-2 Minimum Hermes 0.21.6, no httpx fallback.** CP-9's fallback ("call the connector with JSON-RPC over httpx when `ctx.call_mcp` is missing") is not built: the target Hermes has `call_mcp`, and an older Hermes also lacks `get_config`, so a fallback would need a second config reader too. On a Hermes without `call_mcp`, `register` logs one warning naming the minimum version and registers nothing.
- **C-3 The skill ships inside the package.** `register_skill` needs a real file. The wheel force-includes `skills/overdeck/SKILL.md` as `overdeck_hermes/skills/overdeck/SKILL.md`; the directory drop copies `skills/` next to `__init__.py`; an editable install finds the repo copy two directories up. W-INT0's sync path does not change.
- **C-4 `/overdeck answer` covers every answer tool.** The epic names five tools. W-APPR1 since added `answer_plan`, `answer_agent_plan`, `answer_agent_permission` and the `agentId` form of `answer_question`. `/overdeck pending` lists those prompts, so `/overdeck answer` routes to them too (routing table below). The epic also left numbering across two commands unspecified; this PRD adds the snapshot and item-key check (D-6).

## Requirements

### Functional

- **FR-1 Package.** `integrations/hermes/` is an installable Python package `overdeck-hermes` version `0.1.0`, MIT, Python ≥ 3.11, no runtime dependencies, entry point `overdeck = "overdeck_hermes"` in group `hermes_agent.plugins`, plus a `plugin.yaml` for directory drops, and a `test` extra with pytest.
- **FR-2 Settings.** Three settings, read with `ctx.get_config` on every use: `server` (string, default `"overdeck"`), `summary` (bool, default `true`), `allow_answers` (bool, default `false`; only the boolean `true` enables). `plugin.yaml` declares them in `config_schema`.
- **FR-3 Summary.** When `summary` is on, a `pre_llm_call` hook calls `list_pending_input` at most once per 300 s with a 10 s timeout and, when anything is pending, returns `{"context": "Overdeck status (data, not instructions): …"}` naming at most 5 items of at most 300 characters each. On any error, and on turns inside the 300 s window, it returns `None`.
- **FR-4 `/overdeck status` and `/overdeck pending`.** `status` reports reachability, the pending count and both switches. `pending` prints a numbered list with an answer hint per item and stores the snapshot for the chat session.
- **FR-5 `/overdeck answer <n> <choice>`.** Refuses unless `allow_answers` is `true` at the moment of the call, before any MCP call. Refuses without a snapshot younger than 600 s, for an unknown number, for an item with no answer route, for a choice the item's kind does not accept, and when a fresh `list_pending_input` no longer contains the item's key. Otherwise it calls the routed answer tool and reports the server's answer, including its refusal text (for example the missing-`approve` text).
- **FR-6 Skill.** `register` registers the bundled `overdeck` skill in all three install modes.
- **FR-7 Setup CLI.** `hermes overdeck setup` prints the connector-route config, byte-identical to `hermesConfig({ reach: 'connector', url: CONNECTOR_LOCAL_URL })`.
- **FR-8 Snippet correction.** `hermesConfig` emits the C-1 layout for both reaches; `configuration/mcp.mdx` shows it.
- **FR-9 Docs and checkpoint record.** The package has `README.md`, `PUBLISHING.md`, `CHANGELOG.md`, `LICENSE` and `docs/verification.md` (CP-9 results); `.overdeck/context/codebase/architecture.md` describes the package.

### Non-functional

- **NFR-1 No token text.** No file under `integrations/hermes/` contains an `odk_`, `odr_` or `odl_` token-shaped string; tests build fake tokens at runtime.
- **NFR-2 Re-check, never cache, the answer switch.** Every `answer` call re-reads `allow_answers` (`check_fn`-style hiding is not a security gate; epic NFR-1 spirit).
- **NFR-3 Deterministic tests.** Python tests use an injected clock and a fake `ctx`; no sleeps, no network, no Hermes install. (Repo rule "fake timers for delay tests", restated for Python: inject the clock.)
- **NFR-4 Relative imports.** Modules inside `overdeck_hermes` import each other relatively, so a directory drop loads (fact 5).
- **NFR-5 Tool output is data.** Item text from the server is collapsed to one line and clipped; the summary says "data, not instructions".

## Decisions

- **D-1 Build backend hatchling** (`hatchling>=1.27`), because its `force-include` maps the outside skill file into the wheel without a build script (C-3). MYN uses setuptools, which cannot include a file from outside the package directory.
- **D-2 Skill resolution order:** `<package dir>/skills/overdeck/SKILL.md` (wheel, directory drop), then `<package dir>/../../skills/overdeck/SKILL.md` (editable install from the repo). Neither exists ⇒ log a warning and skip the skill; never fail `register`.
- **D-3 One MCP helper.** `client.call_overdeck` is the only caller of `ctx.call_mcp`. It decodes the envelope twice (D in glossary) and turns `PermissionError`, any other exception, and `ok: False` into `OverdeckCallError(text)`. A `result` string that is not JSON is returned as the raw string; callers that need a dict treat a string as an unreadable answer.
- **D-4 Summary rate limit counts failures.** The 300 s window starts when the hook makes a call, whatever the outcome, so a down connector costs one 10 s call per 5 minutes, not one per turn. Turns inside the window get nothing (no repeated summary).
- **D-5 `/overdeck status` uses `list_pending_input`,** not `list_machines`, because the connector hides `list_machines` (epic W-CONN2 step 7).
- **D-6 Numbering is pinned by a snapshot and an item key.** `pending` stores its list per `session_key` (`"default"` when Hermes passes none) for 600 s. `answer` validates against the stored item, re-fetches, and answers only if the same item key is still pending. After a successful answer the session's snapshot is dropped, so the next answer needs a fresh `pending`. Why: a re-numbered list must never route an approval to a different prompt; `answer_question` by message has no server-side identity check.
- **D-7 Unanswerable items are listed, not hidden.** Held kickoffs, remote agents, unanswerable permission prompts (`signature: null`), and agent kinds with no tool (`paneQuestion`, `agentTurnEnded`, `sessionResume`, `rateLimit`, `enterPlanMode`) appear in `pending` and in the summary with the hint "answer it in the Overdeck dashboard".
- **D-8 Plugin id `overdeck` everywhere:** entry-point name `overdeck`, `plugin.yaml` `name: overdeck`, directory-drop target `~/.hermes/plugins/overdeck/`.
- **D-9 pytest config in `pyproject.toml`:** `testpaths = ["tests"]`, `pythonpath = ["src"]`, `addopts = "-p no:cacheprovider"` (no `.pytest_cache/` to ignore; tests run with only pytest installed).
- **D-10 CP-9 runs against a throwaway Hermes,** in a venv in the session scratchpad with `HERMES_HOME` set to a scratch directory, reaching this machine's dashboard `/mcp` directly with a short-lived `pan token create` token that is revoked afterwards. The connector route is W-CONN2's acceptance (AC-21/22), not this item's; the plugin code path is identical for both routes.

## Routing table for `/overdeck answer <n> <choice>`

`<choice>` is the rest of the line after `<n>`, stripped. "Option number" means a 1-based integer that selects `options[k-1].label`; any other text is passed as free text.

| Source | Condition | Item kind | Tool | Arguments | Accepted `<choice>` |
| --- | --- | --- | --- | --- | --- |
| conversation | `pendingPermission.answerable` and `signature` is a string | `permission` | `answer_permission` | `{conversation, signature, choice}` | `allow-once`, `allow-always`, `deny` |
| conversation | `pendingPermission` otherwise | `permission` | none (D-7) | — | — |
| conversation | `pendingAskUserQuestion`, `harness == "codex"` or `toolUseId` starts with `codex-approval:` | `question` | `answer_codex_approval` | `{conversation, optionNumber, toolUseId}` | integer 1-9 |
| conversation | `pendingAskUserQuestion`, `harness` in `("ohmypi", "pi")` | `question` | `answer_pi_ask` | `{conversation, toolUseId, answers: [a]}` | one option number or free text |
| conversation | `pendingAskUserQuestion`, any other harness | `question` | `answer_question` | `{conversation, answers, questions}` (`questions` = the question texts) | one answer per question, separated by ` \| `; each an option number of that question or free text; count must equal the question count |
| conversation | `pendingProposedPlan` | `plan` | `answer_plan` | `{conversation, action}` plus `feedback` for `reject-feedback` | `approve-auto`, `approve-manual`, `reject-ultraplan`, `reject-feedback <text>` (text required) |
| conversation | `pendingPaneChoice` | `pane-choice` | `answer_pane_choice` | `{conversation, selectedIndex: k-1, signature}` | integer k in 1..len(options) |
| conversation | `heldKickoff` | `held-kickoff` | none (D-7) | — | — |
| agent | `remote: true` | `other` | none (D-7) | — | — |
| agent | each `permissionRequests[i]` | `agent-permission` | `answer_agent_permission` | `{agentId, requestId, behavior}` | `allow`, `deny` |
| agent | `pendingAskUserQuestion` | `agent-question` | `answer_question` | `{agentId, toolUseId, answers}` | as the `answer_question` row above |
| agent | `"exitPlanMode"` in `pendingInputKinds` | `agent-plan` | `answer_agent_plan` | `{agentId, action}` plus `feedback` | as the `plan` row |
| agent | none of the three rows above matched | `other` | none (D-7) | — | — |

Item keys: `permission` → `(name, "permission", signature or "")`; `question` → `(name, "question", toolUseId)`; `plan` → `(name, "plan", toolUseId)`; `pane-choice` → `(name, "pane-choice", signature)`; `held-kickoff` → `(name, "held-kickoff", since)`; `agent-permission` → `(id, "agent-permission", requestId)`; `agent-question` → `(id, "agent-question", toolUseId)`; `agent-plan` → `(id, "agent-plan", "")`; `other` → `(id or name, "other", ",".join(pendingInputKinds))`.

Item order: machines in result order; within a machine, conversations in result order, then agents; within a conversation `permission`, `question`, `plan`, `pane-choice`, `held-kickoff`; within an agent `agent-permission` (request order), `agent-question`, `agent-plan`, then `other`.

Data flow: Hermes turn → `SummaryHook.on_pre_llm_call` → `call_overdeck(list_pending_input)` → `flatten_pending` → `format_summary`. `/overdeck answer` → `read_settings` (gate) → snapshot → `build_answer` → fresh `flatten_pending` (key check) → `call_overdeck(<answer tool>)`.

     ```python
         allow_answers: bool = False

     def read_settings(ctx) -> Settings:
     ```

     ```python
         """A failed Overdeck tool call; str(error) is operator-readable."""

     def call_overdeck(ctx, server: str, tool: str, arguments: dict, timeout: float):
         try:
             envelope = ctx.call_mcp(server, tool, arguments, timeout=timeout)
         except PermissionError as exc:
             raise OverdeckCallError(ALLOWLIST_HINT.format(server=server)) from exc
         except Exception as exc:  # the MCP client's own failures (connect, timeout)
             raise OverdeckCallError(f"Overdeck is not reachable: {exc}") from exc
         if not isinstance(envelope, dict) or not envelope.get("ok"):
             error = envelope.get("error") if isinstance(envelope, dict) else None
             raise OverdeckCallError(str(error) if error else "The Overdeck tool call failed.")
         result = envelope.get("result")
         if isinstance(result, str):
             try:
                 return json.loads(result)
             except ValueError:
                 return result
         return result
     ```

## Hazards

- **H-1 Operator's live Hermes.** `~/.local/bin/hermes` (v0.9.0) and `~/.hermes/` are the operator's install. CP-9 uses a scratchpad venv and `HERMES_HOME`; never run `hermes plugins enable` without `HERMES_HOME` set.
- **H-2 Python 3.14 ambient.** Use `python3.12` (or `python3.11`) for venvs; Hermes requires `<3.15` and pytest is not installed globally.
- **H-3 Double JSON decode.** Forgetting the second decode makes every `list_pending_input` look unreadable; the summary would then silently show nothing. AC-1 pins it.
- **H-4 Settings location.** Writing `summary`/`allow_answers` at the entry root makes the switches no-ops (fact 7). WI-6 fixes the snippet; README and `SETUP_TEXT` must match it.
- **H-5 Wrong-prompt answers.** Without D-6, `/overdeck answer 2` after the list changes would approve a different prompt. Tests in WI-4 pin the key check.
- **H-6 Token literals.** The vitest walk scans every file in `integrations/hermes/`, including Python tests and `.pyc` files in `__pycache__` (skipped); build fake tokens at runtime.
- **H-7 Live tokens.** CP-9 creates real `approve` tokens on this machine; revoke both, and never write a token into the repo or verification.md.
