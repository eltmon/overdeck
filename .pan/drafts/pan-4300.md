# PAN-4300 — Dead agents re-emit `heartbeat_dead` + `status_changed → running` every minute

**Issue:** [PAN-4300](https://github.com/eltmon/overdeck/issues/4300)
**Status:** planned (auto mode, 2026-09-28)
**Prerequisite for:** the Awareness feed redesign (PRD `pan-4301.md`), which moves telemetry into the Activity page's Detailed stream.

## Glossary

- **Deacon child** — the forked process `dist/dashboard/deacon.js`, built from `src/dashboard/server/deacon-main.ts`. Cloister and deacon-lite run only in this child, never in the dashboard process (`docs/DASHBOARD-ARCHITECTURE.md`, "Deacon child process", line 18-19).
- **Deacon-lite patrol tick** — one run of `runDeaconLite()` in `src/lib/cloister/deacon-lite.ts`. `startDeaconLite()` runs one immediately, then one every `DEACON_LITE_INTERVAL_MS` (60,000 ms).
- **`reconcileAgentLiveness`** — the deacon-lite routine that finds agents whose `state.json` says `running` but that the terminal backend no longer hosts, and reports each one through the notifier seam.
- **Notifier seam** — `setAgentStoppedNotifier(fn)` in deacon-lite. The process that runs deacon-lite registers a function; deacon-lite calls `fn(agentId)` for each confirmed-dead agent. Two registrations exist: `src/dashboard/server/deacon-main.ts` (the live one) and `src/dashboard/server/main.ts` (wired, but unreachable today because the dashboard process never runs deacon-lite).
- **Confirmed dead** — the agent is absent from the backend inventory (`liveAgentInventory()`) AND the liveness oracle `isAlive()` in `src/lib/agents/liveness.ts` returns a verdict for which `isConfirmedDead(verdict)` is true. An indeterminate probe (`runtime-indeterminate`) is never death.
- **Launch generation** — which launch of an agent id a `state.json` describes. `spawn.ts` writes `startedAt` on spawn; `resume.ts` (line ~670, `agentState.lastResumeAt = resumeStartedAt`) writes `lastResumeAt` on resume. The generation key is `` `${startedAt}|${lastResumeAt ?? ''}` ``.
- **Reported-dead guard** — the new module-level `Map<agentId, generationKey>` in deacon-lite that remembers which agents it already reported dead, so it reports each death once.
- **Read model** — the dashboard's in-memory state (`src/dashboard/server/read-model.ts`), fed by the event store. Its reducers live in `packages/contracts/src/event-reducers.ts`.
- **Served status** — the agent status the read model serves to clients. Since #4098, `deriveServedAgentStatuses` (read-model.ts ~line 258-300) downgrades a stored `running`/`starting` to `stopped` when the backend has no live pane. So the display does not depend on the deacon event.

## Problem

Every dead agent whose `state.json` status stays `running` re-emits two events about once a minute, forever: `agent.heartbeat_dead` and `agent.status_changed` with `status: 'running'` and no `previousStatus`. In the 24 hours to 2026-09-28 that was about 50,000 events (24,919 `heartbeat_dead` + 24,918 `status_changed`), 99% of the Activity page's Detailed stream. Worst offenders: `agent-min-889-review` and four convoy reviewers (1,442 each), `planning-pan-1641` (1,344), `agent-pan-1641-test` (1,225), `planning-pan-4278` (663).

### Root cause (verified 2026-09-28 at `b3b30e61bd5`)

1. **Nothing moves a dead supervisor-launched agent's `state.json` off `running`.** The supervisor's `exited` lifecycle event (`applyAgentLifecycleEventWithDeps`, `src/dashboard/server/services/agent-projection.ts` ~line 266, `case 'exited':`) appends `agent.stopped` and writes no status. That is deliberate (PAN-3917 FR-12, PAN-3962: "Agents append an event and write no status anywhere").
2. **`reconcileAgentLiveness` reports every such agent on every tick.** `src/lib/cloister/deacon-lite.ts` line 129-160:

   ```ts
   export async function reconcileAgentLiveness(): Promise<string[]> {
     const actions: string[] = [];
     const runningAgents = listAgentStates({ status: 'running' });
     ...
     for (const agent of runningAgents) {
       if (liveIds.has(agent.id)) continue;
       const verdict = await isAlive(agent.id);
       if (verdict.alive || !isConfirmedDead(verdict)) continue;
       ...
       if (agentStoppedNotifier) {
         try {
           agentStoppedNotifier(agent.id);
   ```

   It keeps no memory between ticks and writes nothing, so the next tick sees the same agent and reports it again.
3. **The notifier emits the wrong status.** `src/dashboard/server/deacon-main.ts` line 71-86 (and the copy in `src/dashboard/server/main.ts` line 459-490) does:

   ```ts
   append(domainEvent('agent.heartbeat_dead', { agentId, issueId: state.issueId, sessionId: state.sessionId }));
   append(domainEvent('agent.status_changed', buildAgentStatusChangedPayload(state, undefined, false)));
   ```

   `state.status` is still `running`, so the event says `status: 'running'` and `previousStatus: undefined`. In the read model, `agent.stopped` already set the agent to `stopped`; this event flips it back to `running` (with `hasLivePane: false`) every minute. The Activity page renders it as "Agent X status → running".

Side effect worth noting: `main.ts` (~line 651-665) subscribes to `agent.heartbeat_dead` and runs `reconcileAgentMemory` and `syncTranscriptPollerRegistry` for each one, so the repeat also drives about 25,000 needless memory sweeps and poller syncs a day. The fix removes that churn too.

## Decisions

- **D1 — Emit on the transition; do not write `stopped` to `state.json`.** The issue allows either "reconcile the saved status once" or "emit only on a real transition". This plan picks the second, for three reasons found in the code:
  1. deacon-lite's own header and the `reconcileAgentLiveness` comment say it never writes a record or a state file and only corrects the cache side.
  2. The read model already derives served status from the backend inventory (#4098), so the deacon event is a one-time signal, not the display source.
  3. `detectCrashedAgents` (`src/lib/agents/recovery.ts` ~line 464) and `pan recover` list crashed agents precisely as "`state.json` says running, oracle says dead". Writing `stopped` from the patrol would silently empty that list. The `pan admin agents exited` precedent (`src/cli/commands/admin/agents-exited.ts`) writes `stopped` from a launcher's direct report, not from a patrol's inference; this patrol is inference.
- **D2 — The guard is in-memory in deacon-lite, keyed by agent id + launch generation.** Keying on id alone would never report a resumed agent that dies again. The entry is removed when the agent is observed alive (in the inventory, or `isAlive` says alive) or when it leaves the `running` list, so the map cannot grow without bound. An indeterminate verdict leaves the entry as it is.
- **D3 — Accepted cost: one re-emission per still-dead agent per deacon child restart.** The guard lives in process memory, so each deacon child start (every `pan reload` / dashboard restart) reports each still-dead `running` agent once. That is bounded by the number of such `state.json` rows (tens), not 1,440 × N per day. Persisting the guard is out of scope.
- **D4 — The dead-agent `status_changed` payload says `stopped`.** `status: 'stopped'`, `previousStatus: <recorded status>` (normally `'running'`), `hasLivePane: false`, `hasLiveTmuxSession: false`. `previousStatus` is never omitted when a `state.json` exists.
- **D5 — One shared builder in `src/lib`.** `toAgentStatusPayload`, `buildAgentStatusChangedPayload`, and the new `buildConfirmedDeadAgentEvents` move to `src/lib/cloister/agent-status-events.ts`. `deacon-main.ts` and `main.ts` import them and delete their local copies. Two hand-synced copies is how the two sites could drift.
- **D6 — The notifier signature stays `(agentId: string) => void`.** Each registration still reads `getAgentState(agentId)` itself. This keeps deacon-lite free of any state read beyond `listAgentStates`.
- **D7 — Docs placement.** `docs/DASHBOARD-ARCHITECTURE.md` has no "events" section (its headings are at lines 1, 387, 449, 530, 647). The emission rule goes in the "Deacon child process" bullet list (line 18-23), which is where deacon-lite's behaviour is already documented.

## Requirements

### Functional

- **FR-1** — Within one process, `reconcileAgentLiveness` calls the stopped notifier at most once for a given agent id and launch generation while that agent stays confirmed dead across any number of ticks.
- **FR-2** — When an agent with a guard entry is observed alive (present in the inventory, or `isAlive` returns `alive: true`) or is no longer in `listAgentStates({ status: 'running' })`, its guard entry is removed, so a later confirmed death is reported again.
- **FR-3** — When a confirmed-dead agent's launch generation (`startedAt` + `lastResumeAt`) differs from its guard entry, the notifier is called again and the entry is updated.
- **FR-4** — The `agent.status_changed` event emitted for a confirmed-dead agent that has a `state.json` carries `status: 'stopped'`, `previousStatus` equal to `toAgentStatusPayload(state.status)`, `hasLivePane: false`, and `hasLiveTmuxSession: false`.
- **FR-5** — The `agent.heartbeat_dead` event keeps its payload: `{ agentId, issueId, sessionId }` when a `state.json` exists, `{ agentId }` when it does not. With no `state.json`, no `status_changed` event is emitted (unchanged).
- **FR-6** — `deacon-main.ts` and `main.ts` build both events through `buildConfirmedDeadAgentEvents` and build status payloads through the shared `buildAgentStatusChangedPayload`; neither file defines its own copy.

### Non-functional

- **NFR-1** — deacon-lite writes no `state.json` and no record. `reconcileAgentLiveness` keeps its "correct the cache side only" contract.
- **NFR-2** — Tests that exercise ticks use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`, never real delays (repo rule: fake timers for retry/backoff/delay-based tests).
- **NFR-3** — After a deacon child restart, at most one `heartbeat_dead` / `status_changed` pair per still-dead agent is emitted (D3).
- **NFR-4** — No new `execSync` or sync tmux call in server-reachable code (repo rules: no `execSync` in dashboard server, prefer async tmux). The change adds none.
- **NFR-5** — `src/dashboard/server/main.ts` (897 lines at planning time; ceiling 1000 in `scripts/lint-file-size.sh`) shrinks; no `scripts/file-size-allowlist.txt` row is needed. If any touched file grows past its `origin/main` line count and past the ceiling, add an audited `<lines> <path> # PAN-4300` row in the same commit.

```ts
export function toAgentStatusPayload(status: AgentState['status'] | undefined): AgentStatusPayload { ...same body as today... }

  state: AgentState,
  previousStatus?: AgentState['status'],
  hasLiveTmuxSession?: boolean,

/**
 * The events for an agent deacon-lite confirmed dead. With a state.json:
 * `agent.heartbeat_dead` then `agent.status_changed` recording the transition
 * from the recorded status to `stopped` with no live pane. Without one: only
 * `agent.heartbeat_dead`. The state.json itself is not changed.
 */
export function buildConfirmedDeadAgentEvents(
  agentId: string,
  state: AgentState | null,
  now: () => string = () => new Date().toISOString(),
): Array<Omit<DomainEvent, 'sequence'>> {
  if (!state) {
    return [{ type: 'agent.heartbeat_dead', timestamp: now(), payload: { agentId } } as Omit<DomainEvent, 'sequence'>];
  }
  return [
    { type: 'agent.heartbeat_dead', timestamp: now(), payload: { agentId, issueId: state.issueId, sessionId: state.sessionId } } as Omit<DomainEvent, 'sequence'>,
    {
      type: 'agent.status_changed',
      timestamp: now(),
      payload: buildAgentStatusChangedPayload({ ...state, status: 'stopped' }, state.status, false),
    } as Omit<DomainEvent, 'sequence'>,
  ];
}
```

## Non-goals

- Writing `stopped` (or any field) to `state.json` from deacon-lite or from the notifiers.
- Making the supervisor's `exited` lifecycle handler write `stopped` to `state.json`.
- Persisting the reported-dead guard across deacon child restarts.
- Deleting the unreachable `setAgentStoppedNotifier` registration in `main.ts`, or the unused `agentStatusChangedNotifier` call path in deacon-lite.
- Changing the read model reducers, `deriveServedAgentStatuses`, the Activity page rendering, or the Awareness feed (PAN-4301).
- Changing `detectCrashedAgents` / `pan recover`.
- Cleaning up historical `heartbeat_dead` / `status_changed` rows already in the event store.
