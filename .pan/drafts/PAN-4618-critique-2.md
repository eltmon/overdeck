## blocks-the-design: Cancelled runs still exhaust DoD's probe budget

The PRD identifies cancelled runs filling the five-candidate budget as a cause of false DoD misses ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4618/.pan/drafts/PAN-4618.md), line 98), yet D5 explicitly counts candidates with cancelled required checks (lines 180–187). Work item 4 increments `probed` whenever all required check names exist, even if every CI job was cancelled (lines 384–393). The existing reader treats a cancelled job as unsuccessful because only `status === 'completed' && conclusion === 'success'` enters `successful` ([pull-requests.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4618/src/lib/overdeck/pull-requests.ts), lines 128–142). Five cancelled, fully instantiated runs above a green run still produce a DoD miss. Skip fully cancelled/indecisive candidates without spending the five-run budget, and add that exact test; keep genuinely failed runs counted.

## blocks-the-design: The CI chip treats cancellation as a failed verdict

FR-7 and the deploy rule call a cancelled CI run indecisive ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4618/.pan/drafts/PAN-4618.md), lines 134–141 and 561–568). FR-6 instead projects suites from the newest CI run, including a cancelled newest run (lines 130–133 and 188–197). `deriveProjectCi` explicitly classifies `cancelled` as `failure` ([project-ci.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4618/packages/contracts/src/project-ci.ts), lines 13–26), and the chip renders that as red `CI ✗` ([ProjectCiChip.tsx](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4618/src/dashboard/frontend/src/components/CommandDeck/ProjectCiChip.tsx), lines 13–32). After an operator cancels the newest run, the chip reports a code failure that did not occur. Specify and test an indecisive chip state for cancellation (or project the newest decisive run with an explicit pending/unknown indicator); update the reducer or projection as needed.

## blocks-the-design: A guard-only webhook can still show green CI

The plan says the chip must not show success from the guard workflow alone ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4618/.pan/drafts/PAN-4618.md), line 99). Its webhook change only switches the SHA resolver. `observationFromCheckSuite` accepts every `github-actions` suite on that SHA, without checking its workflow ([project-ci-observation.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4618/src/lib/ci/project-ci-observation.ts), lines 71–88). The event reducer creates a record from that single authoritative suite ([event-reducers.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4618/packages/contracts/src/event-reducers.ts), lines 687–695), and `deriveProjectCi` calls a completed successful singleton `success` ([project-ci.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4618/packages/contracts/src/project-ci.ts), lines 17–26). On a mixed/code push, the guard suite can complete before the queued CI suite arrives, so the chip still shows false green. Require evidence of the CI workflow's own run before the chip can be green; test a successful guard webhook arriving while that CI run is queued.

## blocks-the-design: Timed-out main CI is omitted from the Flywheel verdict

The glossary calls `timed_out` decisive ([PRD](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4618/.pan/drafts/PAN-4618.md), lines 34–38), and the chip classifies it as failure ([project-ci.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4618/packages/contracts/src/project-ci.ts), lines 13–25). The verbatim red-main rule and recap command select only `success` or `failure` (PRD lines 552–559 and 579–581). A timed-out newest run is therefore skipped, so Flywheel can report an older green run while main's current decisive run failed. Include `timed_out` as a red conclusion in both commands and spell out its treatment in FR-7.
