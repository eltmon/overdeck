# PAN-3942 — Per-skill on/off at global, project, and issue level

**Issue:** https://github.com/eltmon/overdeck/issues/3942
**Status:** PLANNED (rescoped by the operator on 2026-09-28; see Planning Q&A)

## Summary

Operators choose which skills Overdeck-managed agents get. Every skill has an
on/off state that can be set at three levels: a **global default**, a
**project override**, and an **issue override**. The narrowest level that has a
value wins: issue beats project, project beats global, and a skill with no
value anywhere is on. A small set of **core workflow skills** that the pipeline
depends on is always on and cannot be switched off.

The state is visible and editable in three dashboard places (Skills page,
project settings, issue view) and from the CLI (`pan skills`). At launch,
Overdeck hides every skill that resolves to off from Claude Code and Codex
sessions, using each harness's own per-session mechanism. No skill files are
copied, moved, or deleted.

## Glossary

- **Skill** — a directory with a `SKILL.md` whose YAML frontmatter has `name` and `description`. Harnesses list each skill's name and description in the model context.
- **Skill name** — the directory name of the skill (for example `grilling`). Overrides and harness hide lists are keyed by skill name.
- **Skill catalog** — the set of skill names Overdeck can see: directories with a `SKILL.md` under `~/.overdeck/skills/`, `~/.claude/skills/`, `~/.agents/skills/`, and, when a project is in scope, `<projectRoot>/.pan/skills/`. Built by `listSkillCatalog()` (work item 1).
- **Override** — an explicit boolean for one skill at one level: `true` = on, `false` = off. Absent = inherit from the next broader level.
- **Level** — one of `global`, `project`, `issue`. Precedence, narrowest first: `issue` > `project` > `global` > built-in default (on).
- **Source** — the level that produced a skill's effective state: `core`, `issue`, `project`, `global`, or `default`.
- **Core skill** — a skill in `CORE_SKILLS` (work item 1). Always effective-on with source `core`. Overrides for core skills are rejected on write and ignored on read.
- **Effective state** — the resolved on/off state of one skill for one (project, issue) context, with its source.
- **Disabled list** — the sorted list of skill names whose effective state is off for a launch. This is what the harness hides.
- **Managed launch** — a harness session Overdeck starts through a generated launcher script (`generateLauncherScript`, `src/lib/launcher-generator.ts:282`): work, review, test, ship, plan, and conversation sessions.
- **planHome** — the repo that holds a project's `.pan/` planning artifacts; `resolvePlanHome(projectRoot)` in `src/lib/pan-dir/paths.ts:46`.
- **Plan-artifact commit door** — `commitPlanArtifacts()` and `pushPlanArtifacts()` in `src/lib/overdeck/plan-artifact-commit.ts:48` and `:234`. They commit and push `.pan/` files on the plan home's current branch (main), pathspec-scoped.

### Harness hiding mechanisms (probed live on 2026-09-28)

- **Claude Code 2.1.280:** `claude --settings '<json>'` accepts `{"skillOverrides":{"<name>":"off"}}`. Probe: `claude -p --settings '{"skillOverrides":{"grilling":"off","domain-modeling":"off"}}' …` reported `grilling: no`, `domain-modeling: no`, `codebase-design: yes`. The same prompt without `--settings` reported all three `yes`. Re-run from inside `workspaces/feature-pan-3942`, where `grilling` exists in both `~/.claude/skills` and the workspace `.claude/skills`: `--settings '{"skillOverrides":{"grilling":"off"}}'` still reported `grilling: no`, `codebase-design: yes` — the override hides every copy by name. Values allowed by the binary's schema: `on`, `name-only`, `user-invocable-only`, `off`. We use `off` only.
- **Codex 0.157.1:** `skills.config` array entries with `name` (or `path`) and `enabled`. Probe: `codex exec -c 'skills.config=[{name="grilling",enabled=false}]' …` reported `grilling: no`, `codebase-design: yes`. The per-agent `config.toml` is read in every Codex mode (exec, tui, work-tui, app-server), so we write the entries there as TOML array-of-tables:
  ```toml
  [[skills.config]]
  name = "grilling"
  enabled = false
  ```
- Other harnesses (ohmypi, acp/opencode, kimi-code, muse) are out of scope. Pi has no Overdeck runtime yet (`'pi'` normalizes to `'ohmypi'`, `packages/contracts/src/types.ts:87-101`; OMP removal parked in #4003).

## Decisions

- **D1 — Scope (operator, Q1).** Per-skill on/off at global, project, issue levels only. No bundles, includes, digests, provenance reports, conversation scope, role/audience filtering, Git/registry sources, or context-cost estimates.
- **D2 — Storage (operator, Q2 + planner).**
  - Global: `~/.overdeck/config.yaml`, key `skills.overrides: { <name>: true|false }`. Read and written by the new store module with the `yaml` Document API (comment-preserving), inside the exported settings write queue. `schema.ts`/`merge.ts`/`defaults.ts` are not changed (ratchet), so `NormalizedConfig` does not carry this key; the store module is the only reader.
  - Project: `~/.overdeck/projects.yaml`, key `projects.<key>.skill_overrides: { <name>: true|false }`, written through `updateProjectsConfigAsync` (exported; the `async function` line becomes `export async function`, no other change to `projects.ts`). The store module reads it with a local type `ProjectConfig & { skill_overrides?: Record<string, boolean> }`.
  - Issue (operator Q2, option 1): `<planHome>/.pan/skill-overrides/<ISSUE>.yaml`, committed and pushed on main in the plan home through the plan-artifact commit door. Readable before the issue is planned or has a workspace.
- **D3 — Precedence.** For a non-core skill: issue value if defined, else project value, else global value, else `true` (source `default`). Core skills are always `true` with source `core`.
- **D4 — Core skills.** `CORE_SKILLS = ['pan', 'pan-done', 'pan-flywheel', 'pan-foreman', 'pan-plan', 'pan-start', 'pan-task', 'pan-tell', 'pan-worker', 'work-complete', 'write-xbrief']`. Rationale: these drive the lifecycle verbs (`pan start/plan/task/done/tell`), delegation (`pan-worker`, `pan-foreman`), the flywheel loop (`roles/flywheel.md:38-40` names `pan-flywheel` as its operating prompt), and self-planning (`write-xbrief`, `work-complete`). All 11 exist in `sync-sources/skills/`. The list is a constant in `src/lib/skill-overrides/resolve.ts`; changing it is a code change.
- **D5 — Mechanism.** Name-keyed per-launch hiding, no file filtering. Claude Code: `--settings '{"skillOverrides":{…:"off"}}'`. Codex: `[[skills.config]] name=… enabled=false` blocks appended to the per-agent `$CODEX_HOME/config.toml` between marker comments. Workspace `.claude/skills` seeding is unchanged.
- **D6 — Single seam: launch-time CLI step.** `generateLauncherScript` emits one bash step that runs a hidden CLI subcommand, `pan skills launch-settings`, before the harness starts. The subcommand resolves overrides asynchronously in its own process. This covers all managed launch paths (work, review/test/ship, plan, conversation, resume, recovery) without touching the spawn files that are over the file-size ratchet (`spawn-prep.ts` 1088, `spawn.ts` 1069, `conversation-runtime.ts` 1222 lines), and keeps sync config reads out of server code.
- **D7 — Fail-open.** If the step fails (non-zero exit, `pan` missing), the launcher prints `[launcher] WARNING: skill overrides not applied: …` to stderr and starts the harness with no hidden skills. A broken override file must not block agent launches; core skills are unaffected either way.
- **D8 — Timing.** Overrides are read at launch. A running session keeps the skill set it launched with; changes apply at the next launch (fresh or resume, both re-run the launcher). The UI says so.
- **D9 — Issue for a launch.** Explicit `--issue` (the generator passes `config.overdeckEnv.issueId` when set), else `issueIdFromWorkspacePath(workingDir)`, else no issue level. Project from `findProjectByPath(workingDir)`; no project → global only.
- **D10 — Writes validate.** A write rejects: a core skill name (`core skill cannot be overridden`), a name not in the catalog for that context (`unknown skill`), a missing/unknown project or issue. Reads tolerate stale names (unknown names are ignored in the effective list but still honored in the disabled list, so a skill that exists only in the workspace copy still hides).
- **D11 — Clearing.** Setting a level to `inherit` (`enabled: null`) deletes that key. When an issue file has no keys left, the file is deleted and the deletion is committed.
- **D12 — Remote launches.** `spawnMode === 'remote'` (Fly) launchers do not emit the step (the remote image may not have `pan` on PATH). Documented as a limit.

## Requirements

- **FR-1** — A skill's effective state resolves as issue > project > global > default(on); core skills are always on.
- **FR-2** — Global overrides persist in `~/.overdeck/config.yaml` under `skills.overrides`, preserving comments and other keys.
- **FR-3** — Project overrides persist in `projects.yaml` under `projects.<key>.skill_overrides`.
- **FR-4** — Issue overrides persist in `<planHome>/.pan/skill-overrides/<ISSUE>.yaml`, committed and pushed on main through the plan-artifact commit door.
- **FR-5** — Writes reject core skills, unknown skills, and unknown projects/issues with a clear message; clearing a level removes the key (and an empty issue file).
- **FR-6** — Claude Code managed launches receive `--settings` with `skillOverrides` set to `off` for every disabled skill.
- **FR-7** — Codex managed launches get `[[skills.config]] … enabled = false` entries for every disabled skill in the per-agent `config.toml`.
- **FR-8** — `pan skills` lists every catalog skill with effective state and source for an optional `--project`/`--issue` context; `pan skills set <skill> on|off|inherit [--project <key> | --issue <id>]` writes an override.
- **FR-9** — The Skills page shows every skill with a global toggle, core skills locked and labeled, effective state and source.
- **FR-10** — Project settings and the issue view show per-level overrides (inherit/on/off) with the effective state and its source.
- **FR-11** — User-facing docs describe the three levels, precedence, core skills, storage locations, CLI, the Claude Code/Codex-only scope, and next-launch timing.
- **NFR-1** — No change to `pan sync`, `~/.claude/skills`, `~/.agents/skills`, workspace skill seeding, or user-owned harness settings files.
- **NFR-2** — Override failure never blocks a launch (fail-open with a warning).
- **NFR-3** — No new synchronous config/projects reads in dashboard-server-reachable code; server routes use the async store functions.
- **NFR-4** — No file over the 1000-line ratchet grows (`launcher-generator.ts` stays ≤ 1000 lines; `projects.ts` and `settings-api.ts` change by one keyword each).
- **NFR-5** — Stay within finalize limits: ≤ 25 files, ≤ 6 subsystems.
