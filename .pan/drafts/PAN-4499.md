# PAN-4499 — `pan handoff --skill/--pack` for the new conversation, and `--hold` to create it without sending the kickoff

**Issue:** [PAN-4499](https://github.com/eltmon/overdeck/issues/4499)
**Builds on:** PAN-4486 (per-conversation skill layer), PAN-4334 (skill packs), PAN-1568 (server-owned fork pipeline), PAN-3921 (fork delivery failures surface).

## Glossary

- **Handoff** — `pan handoff [conv] [focus...]`. The CLI posts to the dashboard route `POST /api/conversations/:name/summary-fork` with `forkMode: 'handoff'`. The server authors a handoff document, creates the new conversation row, spawns its session, and sends the document as the first message.
- **Source conversation** — the conversation being handed off (`conv` in `handleConversationSummaryFork`).
- **Successor** — the new conversation the handoff creates.
- **Kickoff** — the first message the fork pipeline sends to the successor. For a handoff it is the handoff document text; when authoring falls back it is the fallback summary (`prependFallbackFocus(...)`). In code it is the `summary` variable in `runForkPipeline` and the second argument of `injectForkSummary`.
- **Conversation skill layer** — `conversations.skill_overrides` (PAN-4486): a JSON map `{ "<skill>": true|false, "<pack>/<skill>": true|false }` on the conversation row. `pan skills launch-settings --conversation <tmux>` rereads it at every launch and applies it as the narrowest layer (`src/lib/skill-overrides/launch.ts`, `loadConversationSkillLayer`).
- **Pack skill id** — `<pack>/<skill>`, e.g. `mattpocock/grilling`. A pack skill is mounted at launch only when it resolves on (`resolvePackSkill` in `src/lib/skill-overrides/resolve.ts`). Packs are off by default.
- **Opt-in pack skill** — a manifest skill with `optIn: true`. Pack toggles never turn it on; only a per-skill value does.
- **Held conversation** — a successor created with `--hold`: its session is launched, the kickoff is stored, and nothing has been sent to the harness yet.
- **Kickoff door** — the new route `POST /api/conversations/:name/kickoff`. It is the only path that sends a held kickoff, and it sends it at most once.
- **Claim** — the atomic compare-and-set that takes the held kickoff off the row. Only the caller whose claim succeeds may send it.

## Problem

1. `pan handoff` cannot give the successor its own skills. PAN-4486 added the conversation skill layer, but only the new-conversation dialog writes it. The workaround (an issue-level override plus `--issue`) turns the skill on for every agent on that issue.
2. `pan handoff` always sends the kickoff as soon as the session is up, so the successor starts working at once. The operator wants to open it, inspect it, and start it themselves (for example on a recorded stream).

## Requirements

### Functional

- **FR-1** `pan handoff --skill <name>` (repeatable) turns that skill on in the successor's conversation skill layer only. `<name>` is a native skill name or a pack skill id `<pack>/<skill>`.
- **FR-2** `pan handoff --pack <id>` (repeatable) turns on, in the successor's conversation skill layer only, every non-opt-in skill of that pack's cached manifest, as `<pack>/<skill>: true` entries.
- **FR-3** The successor's skill map is the source's map with the requested entries applied on top (requested entries win). No global, project, or issue store is written.
- **FR-4** An unknown skill, an unknown pack, a pack skill id whose skill is not in the manifest, or an uncached pack fails with HTTP 400 before any conversation row is created. The error names the bad value and lists the known skills (for skills) or known pack ids (for packs). An uncached pack uses the existing wording `pack <id> is not cached; run pan skills pack sync <id>`.
- **FR-5** `pan handoff --hold` authors the kickoff, creates the row, and launches the session, but sends nothing to the harness. The kickoff is stored on the row as held.
- **FR-6** `GET /api/conversations/:name/kickoff` answers `{ held: true, text }` for a held conversation and `{ held: false }` otherwise (200 both), and 404 for an unknown conversation.
- **FR-7** `POST /api/conversations/:name/kickoff` (body `{ text?: string }`) claims the held kickoff and sends it (or the operator's edited `text`) once. A second call, or a call on a conversation that was never held, answers 409 and sends nothing.
- **FR-8** `pan handoff start <conv>` (id or name) calls the kickoff door, waits for delivery like `pan handoff` waits for a fork, and prints the result. It exits 1 on 404/409 or a failed delivery.
- **FR-9** In the dashboard, a held conversation's composer shows a notice that it is waiting to be started, and the composer is seeded with the kickoff text. Pressing Send calls the kickoff door (never the normal message route).
- **FR-10** The composer `/handoff` (and `/pan handoff`) pass `--skill`, `--pack`, and `--hold` through: the fork modal parses them out of the trailing text, shows them, and sends them in the fork request body. The rest of the text stays the focus.
- **FR-11** `--model` and `--effort` keep working together with `--skill`, `--pack`, and `--hold`.
- **FR-12** A dashboard restart while a held handoff is still authoring or spawning resumes it as held (the persisted `ForkRequest` carries `hold: true`), and never sends the kickoff.

### Non-functional

- **NFR-1** Without the new flags, `pan handoff` sends exactly the same request body and the server behaves exactly as today.
- **NFR-2** No file grows past its file-size cap: `conversation-forks.ts` stays ≤ 1000 lines, `conversations.ts` ≤ 1222, `ComposerFooter.tsx` ≤ 1000, `routes/conversations.ts` is not touched.
- **NFR-3** Exactly-once is enforced by a single synchronous SQLite transaction in the dashboard process (better-sqlite3 runs it atomically), not by the client.
- **NFR-4** Tests that wait use fake timers (`vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync`), never real delays (repo rule `fake-timers-for-retry-tests`).
- **NFR-5** Server-reachable code uses no `execSync` and no `*Sync` tmux calls (repo rules `no-execsync-server`, `prefer-async`).

## Decisions

- **D1 — Server validates skills and packs.** `fork-client.ts` documents the route as the single owner of the fork pipeline, so validation lives in the route, not the CLI. The CLI forwards `skills: string[]` and `packs: string[]` and relays the server's error text.
- **D2 — `--pack` expands to per-skill entries.** The conversation layer stores per-skill values only and `resolvePackSkill` already honors them, so `--pack mattpocock` writes `mattpocock/<skill>: true` for every manifest skill with `optIn: false`. Opt-in skills are skipped, matching what a pack toggle does at any other level. No change to `resolve.ts` or `launch.ts`. A pack updated later does not add new skills to an existing conversation; that is acceptable because the map is a launch-time fact.
- **D3 — Core skills named by `--skill` are accepted and store nothing.** Core skills are always on, so the request is already satisfied.
- **D4 — Merged map cap.** The successor's merged map must hold ≤ 200 entries (`MAX_SKILL_OVERRIDES`); otherwise 400 `too many skill overrides`.
- **D5 — The held kickoff lives in a new column `conversations.held_kickoff` (text).** Non-null means held. It stores the exact kickoff text, which covers the fallback-summary case where there is no handoff document file. It is not added to `LEGACY_CONVERSATION_SELECT` or `LegacyConversation` (that file has 3 lines of headroom); a new leaf module reads and writes it.
- **D6 — No new `forkStatus` value.** `getStuckForks`, `recoverStuckForks`, the lifecycle sweeper, and the CLI's `isForkResultInProgress` all treat any non-null, non-`'failed'` forkStatus as in flight. A held pipeline therefore finishes with `forkStatus = null`, and the hold is recorded only in `held_kickoff`.
- **D7 — One delivery tail.** The tail of `runForkPipeline` (inject → mark active → stranded/clear status) becomes the exported `deliverForkSeed(conv, seed, caller)`. Both `runForkPipeline` and the kickoff door call it.
- **D8 — Kickoff door delivers in the background.** The route claims synchronously, starts delivery with `registerInFlightForkPipeline(...)`, and answers 200 with the conversation at once. Delivery progress and failure show through `forkStatus`/`forkError` exactly like a fork. The CLI polls the same way `forkConversationViaServer` does.
- **D9 — Failed delivery restores the hold only when nothing was sent.** If `ensureForkSessionReady` throws, or `injectForkSummary` throws (delivery reported not-ok), the door writes the claimed text back with `restoreHeldKickoff` and sets `forkStatus='failed'` with the error. A `'stranded'` result (text is in the pane but not submitted) does not restore, because the text already reached the terminal. The door never calls `markConversationEnded` (unlike `handleForkPipelineFailure`), because the session is a live conversation.
- **D10 — `hold` is valid for `handoff` and `summary` fork modes; `plain` + `hold` is a 400.** A plain fork has no kickoff. Only `pan handoff` exposes `--hold` on the CLI.
- **D11 — `pan handoff start` is a Commander subcommand**, registered like `planCmd.command('finalize')`. **Implementation checkpoint:** after adding it, run `node dist/cli/index.js handoff self --help` and a unit parse test that `pan handoff self some focus` still reaches `handoffCommand`. Fallback if Commander routes `self`/focus wrongly: drop the subcommand and intercept `convRef === 'start'` at the top of `handoffCommand`, delegating to `handoffStartCommand(focusArgs[0])`.
- **D12 — Dashboard Send on a held conversation goes to the kickoff door.** If the composer text, with all whitespace runs collapsed to one space and trimmed, equals the stored kickoff normalized the same way, the composer POSTs no `text` (the server sends the stored kickoff verbatim). Otherwise it POSTs the edited `text`. A 409 shows a toast `This conversation was already started` and refreshes the held state.
- **D13 — Composer flag parsing lives in the fork modal.** `ForkModal` parses `--skill <v>`, `--pack <v>`, and `--hold` tokens out of `initialFocus`, so both `/handoff` (frontend regex) and `/pan handoff` (server control plane) get it with no change to `ComposerFooter`'s regex, the control plane, or the `overdeck:open-fork-modal` event. Verified path for `/pan handoff`: `src/lib/composer-commands/parser.ts` builds `argv: [...entry.path, ...positionals, ...flags]` (line 254), keeping each flag in canonical form but moving all flags after the positionals, and `uiCommandResult` joins `argv.slice(path.length)` into `focus`. So `/pan handoff --skill grilling --hold do X` arrives as `do X --skill grilling --hold`, and the parser must remove flag tokens wherever they appear. That path rejects `--skill`/`--pack`/`--hold` as unknown flags until WI-6 and WI-7 regenerate `composer-commands.generated.ts`; the `/handoff` regex path needs no regeneration. The modal shows the parsed skills and packs as removable chips and `--hold` as a "Hold — start it myself" checkbox (also usable without the flag). It does not add a full skill picker.
- **D14 — Other delivery paths do not clear the hold.** `pan tell` or another agent message to a held conversation leaves `held_kickoff` in place; the kickoff can still be sent once through the door.

```ts
import type { PackCatalogEntry, SkillCatalogEntry } from './catalog.js';
import { isCoreSkill, isPackSkillId } from './resolve.js';

export class ConversationSkillFlagError extends Error {}

const SKILL_ID_PATTERN = /^[A-Za-z0-9][A-Za-z0-9._-]*(\/[A-Za-z0-9][A-Za-z0-9._-]*)?$/;

/** A request-body list: absent → []; otherwise an array of id-shaped strings, else throws `Invalid <field>`. */
export function parseSkillFlagList(raw: unknown, field: 'skills' | 'packs'): string[];

/** Pure: the entries the flags add. Throws ConversationSkillFlagError naming the bad value and the known list. */
export function expandConversationSkillFlags(
  flags: { skills: readonly string[]; packs: readonly string[] },
  catalog: { skills: readonly SkillCatalogEntry[]; packs: readonly PackCatalogEntry[] },
): Record<string, boolean>;

/** Loads listSkillCatalog({ projectRoot }) and listPackCatalog(), then expands. */
export async function resolveConversationSkillFlags(
  flags: { skills: readonly string[]; packs: readonly string[] },
  projectRoot?: string,
): Promise<Record<string, boolean>>;
```

Rules for `expandConversationSkillFlags`, in this order:
1. For each pack id in `flags.packs`: not in `catalog.packs` → throw `` `unknown pack: ${id}. Known packs: ${ids.join(', ') || '(none registered)'}` ``. `manifest === null` → throw `` `pack ${id} is not cached; run pan skills pack sync ${id}` ``. Otherwise add `${id}/${skill.name}: true` for every `manifest.skills` entry with `optIn === false`.
2. For each name in `flags.skills`: if `isPackSkillId(name)`, split at the first `/`; unknown pack or skill not in its manifest → throw the unknown-skill error; uncached pack → the not-cached error; else add `name: true`. Otherwise: `isCoreSkill(name)` → add nothing; not in `catalog.skills` → throw the unknown-skill error; else add `name: true`.
3. Unknown-skill error text: `` `unknown skill: ${name}. Known skills: ${known.join(', ')}` `` where `known` is every `catalog.skills` name followed by every `<pack>/<skill>` id from cached manifests, sorted.

`parseSkillFlagList` throws `ConversationSkillFlagError('Invalid skills')` / `('Invalid packs')` when `raw` is not an array, has a non-string, or a string that fails `SKILL_ID_PATTERN` (packs: the part without `/` only, i.e. `/^[A-Za-z0-9][A-Za-z0-9._-]*$/`).
