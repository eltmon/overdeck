# PAN-4931 — MCP tool module: visibility, methods, token file (PAN-4927 W-MCP1)

**Status:** planned · **Revision:** 1 (2026-11-03) · **Author:** Claude Opus 5.5 (planning agent, `pan plan --auto`)
**Issue:** [PAN-4931](https://github.com/eltmon/overdeck/issues/4931) · **Epic:** [PAN-4927](https://github.com/eltmon/overdeck/issues/4927), PRD `.pan/drafts/pan-4927.md`, work item **W-MCP1** (D-14, NFR-10, D-7)
**Depends on:** nothing. Sibling [PAN-4930](https://github.com/eltmon/overdeck/issues/4930) (W-TOK1) adds `agentId` to token records and credentials; this issue must compile and pass whether PAN-4930 lands before or after it (D-1 below).

**Why.** The Overdeck MCP server lists all ten tools to every caller, even tools whose route the token cannot use. Later epic items add agent-only tools that must not appear for outside clients. Later tools also need `PUT`, `PATCH` and `DELETE` and abortable requests. Managed agents (W-INJ*) will get their token through a 0600 file, so `pan mcp serve` must read it from `OVERDECK_MCP_TOKEN_FILE`.

## Glossary

- **MCP tool module:** `src/lib/mcp/`. `createOverdeckMcpServer(ctx)` (`src/lib/mcp/server.ts:37`) builds one SDK `Server` with every tool in `ALL_TOOLS` (`server.ts:35`).
- **Tool:** an `OverdeckTool` (`src/lib/mcp/tool.ts:16-21`): `name`, `description`, `inputSchema`, `run(args, ctx)`.
- **Tool context:** `McpToolContext` (`tool.ts:10-14`): `api` (a `DashboardApi`) and `scopes` (the caller token's scopes).
- **Scope:** an `AccessTokenScope` (`src/lib/access-tokens.ts:62-73`). `scopeSatisfies(granted, required)` (`access-tokens.ts:172-175`): `admin` satisfies all; `operate` satisfies `tell`; otherwise exact match.
- **Route-scope table:** `ROUTE_SCOPES` in `src/dashboard/server/route-scopes.ts`; `requiredScopeFor(method, pathname)` (`route-scopes.ts:226`) returns the scope a `METHOD path` needs (unlisted = `admin`).
- **Tool scope (new):** `OverdeckTool.scope`, the scope of the route the tool calls. It decides visibility only; the route still enforces its own scope.
- **Audience (new):** `OverdeckTool.audience: 'any' | 'agent'`. `'agent'` tools are shown only to an agent token.
- **Agent token:** a `kind: 'token'` access-token record that carries an `agentId` string (W-TOK1, PAN-4930). Before PAN-4930 lands, no record carries it.
- **Visible tools (new):** `visibleTools(ctx, tools)`, the tools a caller may list and call.
- **Hidden tool:** a tool not in `visibleTools` for the caller. Calling it answers exactly like an unknown tool: `Unknown tool <name>`.
- **Transports:** `POST /mcp` (`src/dashboard/server/routes/mcp.ts`) and `pan mcp serve` over stdio (`src/cli/commands/mcp.ts`).
- **Composer-command manifest:** `packages/contracts/src/composer-commands.generated.ts`, generated from every Commander `.description(...)`. `npm run lint:slash-commands` (`scripts/lint-slash-commands.sh`) fails when it drifts from `dist/cli/index.js`.

## Requirements

### Functional

- **FR-1 Scope visibility.** `tools/list` returns only tools where `scopeSatisfies(ctx.scopes, tool.scope)` holds, in `ALL_TOOLS` order.
- **FR-2 Audience visibility.** A tool with `audience: 'agent'` is listed only when `ctx.isAgent` is `true`.
- **FR-3 Hidden equals unknown.** `tools/call` of a hidden tool returns `isError: true` with text exactly `Unknown tool <name>` and makes no dashboard request.
- **FR-4 Tool annotations.** Each of the ten tools declares `audience: 'any'` and the scope in Facts table 3.
- **FR-5 More HTTP methods.** `DashboardApi.request` accepts `GET`, `POST`, `PUT`, `PATCH`, `DELETE`. `POST`, `PUT`, `PATCH` send a JSON body (`body ?? {}`) with `Content-Type: application/json`. `GET` and `DELETE` send no body and no `Content-Type`.
- **FR-6 Abortable requests.** `request` takes an optional fourth argument `{ signal?: AbortSignal }`, passes the signal to `fetch`, and rethrows the original error unchanged when the signal is aborted.
- **FR-7 Token file.** `pan mcp serve` uses `OVERDECK_MCP_TOKEN` when it is non-empty after trim; otherwise it reads the file named by `OVERDECK_MCP_TOKEN_FILE` and trims it.
- **FR-8 File mode.** `pan mcp serve` refuses (exit 1) a token file whose mode has any group or other bit (`(mode & 0o077) !== 0`), with stderr containing `OVERDECK_MCP_TOKEN_FILE must be mode 0600`.
- **FR-9 Agent identity.** Both transports set `isAgent` from the presented token's `agentId` (a non-empty string) through one helper, `hasAgentId`.

### Non-functional

- **NFR-1 Async only.** Token-file reading uses `node:fs/promises` (`open`, `FileHandle.stat`, `FileHandle.readFile`). No `*Sync` call is added (repo rules `no-execsync-server`, `prefer-async`).
- **NFR-2 No shared mutation with PAN-4930.** This issue does not edit `src/lib/access-tokens.ts` or `src/dashboard/server/routes/dashboard-auth.ts`, and does not widen `AccessTokenRecord` or `DashboardCredential`.
- **NFR-3 Route authority unchanged.** Visibility is a filter on top of the routes; no route scope, route handler or `route-scopes.ts` row changes. `answer_question` keeps its in-tool `approve` check.
- **NFR-4 Docs ship with the change.** `configuration/mcp.mdx` and `docs/DASHBOARD-AUTH.md` describe the new behavior in the same PR.
- **NFR-5 Sizes.** Every touched file stays under 600 lines.

## Decisions

- **D-1 Read `agentId` structurally, not by type.** PAN-4930 adds `agentId` to `AccessTokenRecord` and the `token` credential, but it may land after this issue. So `tool.ts` exports:
  ```ts
  /**
   * True when a token record or credential names a managed agent (PAN-4927 D-6,
   * D-14): `agentId` is a non-empty string. Reads the field structurally, so it
   * compiles before and after W-TOK1 adds `agentId` to the record and credential types.
   */
  export function hasAgentId(value: object): boolean {
    return 'agentId' in value && typeof value.agentId === 'string' && value.agentId.length > 0;
  }
  ```
  The CLI passes `isAgent: hasAgentId(record)`; the route passes `isAgent: hasAgentId(credential)`. Consequence: the CLI path detects agent tokens as soon as PAN-4930 writes the field (Fact 5); the HTTP path detects them once PAN-4930 step 4 fills the credential (Fact 6). Both converge with no further change here. Rejected: widening the types here (shared mutation with PAN-4930, NFR-2); adding a dependency edge (the issue says it depends on nothing).
- **D-2 `isAgent` is required on `McpToolContext`.** Every caller must decide. The harness `connectClient(api, scopes, isAgent = false)` keeps existing test call sites unchanged.
- **D-3 Keep the in-tool `approve` check in `answer_question`.** With `scope: 'approve'` the server already hides it, so the check is reachable only by calling `run` directly. It stays as defense in depth (NFR-3); `MISSING_APPROVE_TEXT` stays exported and is tested through a direct `run` call.
- **D-4 Tool lists are injectable for tests.** `visibleTools(ctx, tools = ALL_TOOLS)` and `createOverdeckMcpServer(ctx, tools = ALL_TOOLS)`. No real `audience: 'agent'` tool exists in this issue, so tests pass a synthetic one. Production callers never pass the second argument.
- **D-5 The file is read through one handle.** `open(path, 'r')`, then `handle.stat()` for the mode, then `handle.readFile('utf8')`, then `handle.close()` in `finally`. The mode checked is the mode of the bytes read (no gap between a path `stat` and a path read).
- **D-6 Exact `pan mcp serve` messages** (all to stderr, exit 1):
  - neither set: `OVERDECK_MCP_TOKEN or OVERDECK_MCP_TOKEN_FILE is not set. Create a token with: ${CREATE_HINT}`
  - open/stat/read fails: `OVERDECK_MCP_TOKEN_FILE could not be read: ${error.message}`
  - mode has group/other bits: `OVERDECK_MCP_TOKEN_FILE must be mode 0600 (it is 0${(mode & 0o777).toString(8)}). Fix it with: chmod 600 ${path}`
  - empty after trim: `OVERDECK_MCP_TOKEN_FILE is empty: ${path}`
  - the existing three refusal messages are unchanged (they still say `OVERDECK_MCP_TOKEN is refused: …` for a token from either source).
- **D-7 Aborts are not "unreachable".** In `dashboard-api.ts`, the `catch` around `fetchImpl` rethrows the original error when `init?.signal?.aborted` is true; every other error keeps the `Overdeck dashboard unreachable at …` wrapping.
- **D-8 Update the `pan mcp serve` description and regenerate the manifest.** New description: `Serve Overdeck as an MCP server over stdio (token from OVERDECK_MCP_TOKEN or OVERDECK_MCP_TOKEN_FILE; see configuration/mcp.mdx)`. Then `npm run build:cli && npm run generate:slash-commands` and commit `packages/contracts/src/composer-commands.generated.ts`.
- **D-9 No Windows ACL check.** The mode check uses POSIX bits. `pan` agents run on Linux and macOS; a Windows user keeps `OVERDECK_MCP_TOKEN`. Recorded as a non-goal.
