## The goal in one scenario

You are mid-conversation at your desktop when you have to take the dog to the vet. You grab the laptop. In the waiting room you open Overdeck on the laptop.

The desktop's conversations are in your sidebar next to the laptop's own. Each one carries a "desk" machine chip, and its title bar is a lighter shade than a local conversation's. You open the conversation you left. It is still running on the desktop, and you read it live and reply: you are **remote-controlling** it.

Later the desktop needs to go offline, so you click **Pull here**. The desktop finishes or stops the current turn and hands the conversation over, including its uncommitted code changes. From then on the laptop runs it, and the desktop shows it as "Continued on laptop", read-only. At home you push it back the same way. A conversation runs on exactly one machine at a time.

The laptop reaches the desktop over Tailscale. Overdeck installed and signed in Tailscale on both machines when you first linked them. If a machine has no Tailscale, the overdeck.ai directory introduces the two machines so they connect directly. Only when no direct path exists, and only on the relay plan, do bytes pass through a relay.

All traffic between the two machines is end-to-end encrypted on every route, and a relay forwards bytes it cannot read.

The same fleet includes Fly.io VMs. You can start a conversation "on Fly" or let a gauntlet loop place its heavy critic lanes there, and they appear as one more machine with live conversations.

## Glossary

- **Machine:** one running Overdeck server (`pan up`, `pan serve` or the desktop app) with its own `OVERDECK_HOME`. A machine's identity is its **environment id**, a UUID created once in `${OVERDECK_HOME}/environment-id.json` by `ensureEnvironmentIdentity()` (`src/lib/environment-identity.ts`), with a label that defaults to the hostname. "Environment" (the code's word) and "machine" (the UI's word) are the same thing.
- **Machine key:** a long-term X25519 key pair created with the environment id and stored in `${OVERDECK_HOME}/machine-key` (0600). Its public half is published in the descriptor and pinned by every linked machine at pairing.
- **Descriptor:** the public answer of `GET /api/environment` (`buildEnvironmentDescriptor()`, `src/dashboard/server/routes/environment.ts`): environment id, label, OS, server version, `protocolVersion` (`ENVIRONMENT_PROTOCOL_VERSION = 1`, `packages/contracts/src/environment.ts:12`), capability flags and, new here, the machine key's public half. It needs no credential.
- **Machine link:** what lets one machine's server act on another's. A link holds a scoped credential, the other machine's pinned public key and a list of routes. This plan calls the machine that holds the link the **linking machine** and the other the **linked machine**. A link is one-directional; **Link both ways** creates two links in one action.
- **Secure channel:** the end-to-end encrypted byte stream between two linked machines. It is a Noise protocol session keyed by the two machine keys, carried over any route. Ordinary HTTP and WebSocket requests run inside it, so nothing between the two machines (a LAN, Tailscale, an SSH hop, the relay, Cloudflare) sees plaintext.
- **Route:** one way to reach a linked machine. A link uses the first route that answers. The kinds are:
  - `lan`;
  - `tailnet` (Tailscale);
  - `ssh` (a forwarded loopback port);
  - `public` (a public address such as a Fly VM's);
  - `direct` (a peer-to-peer path the directory helped open through NAT);
  - `relay` (bytes forwarded by a TURN server).
- **Directory:** the overdeck.ai service that knows an account's machines. For each machine it stores the environment id, label, machine-key fingerprint, presence and current candidate addresses. It introduces two machines so they can connect directly. It never carries their traffic, and it never vouches for a machine's key.
- **Owner machine:** the one machine whose harness runs a conversation and whose disk holds its live transcript. Ownership changes only through a pull or a vault Continue here.
- **Remote control:** using a conversation on its owner machine from another machine through a link. Everything still runs on the owner.
- **Pull:** making this machine the owner of a conversation. The old owner stops its harness session and becomes read-only for that conversation.
- **Saved copy:** the Session Vault record of a conversation (`SessionRecord`, `src/lib/vault/format.ts:149`). It is encrypted and versioned, and readable when the owner is off. Today it appears as a `vault-<vaultId>` row with `origin = 'vault'`.
- **Relay:** the last-resort fallback when no direct path exists between two machines. It forwards secure-channel bytes, which it cannot read, through a TURN server. It is metered and is available only on the relay plan.
- **Operator-level** vs **agent-fenced:** the two access levels a link can carry (FR-4).

## What t3code does, and what this plan takes from it

t3code runs a full server on every machine. Each client (desktop, web, mobile) holds a catalog of machines, each with ordered routes, and connects to each machine directly from the client. The sidebar merges all machines, grouped by git repository, with a machine icon on rows from other machines. Offline machines' threads stay listed from a client cache, with an "<machine> is offline" banner. Threads never move between machines. Machines link to each other's MCP endpoint to delegate tasks. The relay is a broker on Cloudflare that provisions one Cloudflare Tunnel per machine. Cloudflare's edge terminates TLS on those tunnels, so app traffic is readable inside Cloudflare's network.

**Taken:** the descriptor check before any credential; ordered routes with direct routes first and the relay last; learned LAN and Tailscale routes; the 60 s better-route check; the merged sidebar grouped by repository; machine chips; offline rows kept from cache; delegation matched by git repository with back-off while the target sleeps; SSH launch that stops only servers it started; protocol and capability gating; "add this project to another machine" with `.env` copy; freeze-vs-network diagnosis.

**Done differently:**
1. **Federation runs server to server**, through each machine's own Overdeck server, not from the client (D-1).
2. **Every byte between machines is end-to-end encrypted** by the machines themselves, so no route, including the relay, is trusted (D-2). t3code relies on TLS that Cloudflare terminates.
3. **Conversations move** (Pull here), and t3code's cannot.
4. **Agent-originated calls are always fenced**, even on an operator-level link.
5. **The relay URL is a runtime setting.**

  - Routing a new thread to the machine with the most free CPU and memory [12:04] (FR-22).
  - Reserving machines for a purpose, such as Macs for iOS work [12:04] (FR-23).
  - `npx t3 connect` on a fresh server: run one command, open the link, log out of SSH and manage the machine from then on [13:04] (FR-25).

  - Thread-to-thread messages by id [08:03] (FR-28).
  - **Update all**, which updates the app and the Claude and Codex CLIs on every machine [31:21] (FR-29).
  - Opening a remote machine's checkout in VS Code over SSH [32:22] (FR-30).
  - Usage from every connected environment [22:11] (FR-31).
  - Settings that apply to one machine or all, with a view of which machine has what [29:18] (FR-32).
  - Small reads on poor mobile connections [23:12] (NFR-9).

  - t3code streams a remote iOS simulator and a remote browser [25:14], [26:16]. This plan forwards a dev-server port through the secure channel instead (FR-24), which covers web apps. Streaming a simulator or browser view is out of scope for this release.
  - T3 Connect is free for three devices because all traffic goes through t3code's tunnel [36:23]. Here the directory moves no conversation bytes, so a free directory for three machines costs overdeck.ai almost nothing (OD-3).

## Requirements

### Functional

- **FR-1 Link machines.** `pan machines link <pairing-url>` and Settings → Anywhere → Machines → **Link a machine** take a pairing link from the other machine.
  - The pairing handshake runs inside a secure channel whose Noise handshake mixes in the one-time pairing code as a pre-shared key. An attacker on the route who lacks the code cannot pair in the middle.
  - Each side then pins the other's machine key and stores a `machine`-kind token for the other.
  - **Link both ways** creates both directions in one action.
  - Either side can revoke a link, and a revoke closes live channels within 5 s.
- **FR-2 Routes.** Each link keeps an ordered route list.
  - **Sources:** the pairing URL, **Add route**, addresses the linked machine advertises in its descriptor (`lan`, `tailnet`, Tailscale Serve HTTPS), and, when signed in, the directory.
  - **Ranking:** `lan < tailnet < ssh < public < direct < relay`. The relay is used only when every other route has failed and the account's plan includes relay service.
  - **Identity check:** a channel is opened only to a route whose handshake proves the pinned machine key. No credential is ever sent before that proof.
- **FR-3 Link supervisor.** For each link, the server keeps a secure channel open on the best answering route.
  - **Probing:** routes are probed in parallel with a 2.5 s timeout.
  - **Reconnect:** back-off starts at 1 s and doubles to 300 s, with jitter.
  - **Better routes:** earlier routes are re-checked every 60 s.
  - **States:** `online`, `connecting`, `offline`, `unsupported` (protocol mismatch) or `revoked`.
  - **Bound:** no user-facing request waits more than 2.5 s on an unreachable machine.
- **FR-4 Access levels.** A link is **operator-level** (the default between your own machines; the pairing screen says so) or **agent-fenced**.
  - **Stamping:** the linking server stamps every forwarded request with its actor (`operator` or `agent:<id>`) and the agent's permission ceiling. The linked server trusts the stamp because the link is the trust boundary, but a stamp can only narrow what the link allows, never widen it. A request with no stamp counts as `agent`.
  - **Fencing:** agent requests may change only conversations that link started. On an agent-fenced link, operator requests are fenced the same way.
  - **Limits on every link:** no link can pair devices, mint tokens, change settings or use the linked machine's own links (no chained hops).
- **FR-5 Shared conversation list.** Once linked, the linking machine lists every conversation of the linked machine: native session id, title, project, git origin, harness, model, status, last activity, issue link and owner machine. This is on by default (D-4). The linked machine can stop sharing (Settings → Anywhere → Machines → **Share my conversations**), and its rows disappear on the next sync. Content is fetched only when a conversation is opened.
- **FR-6 One row per conversation.** A conversation appears once on a machine, keyed by (owner environment id, native session id). The row reads live from the owner when it is online, and from the saved copy when it is offline and a saved copy exists. A local conversation, a linked conversation and a vault copy of the same session never show as two rows.
- **FR-7 Remote control.** Opening a linked conversation streams its transcript live. You can send messages, answer AskUserQuestion prompts, approve permission requests, stop, abort, switch model and open its terminal. Images and file attachments in the transcript load from the owner through the secure channel. Every action runs on the owner. The URL names the owner: `/conv/@<environmentId>/<name>`. Local `/conv/<rowid>` URLs keep working.
- **FR-8 Pull here.** **Pull here** on a linked conversation (and `pan conv pull <conv>`) makes this machine the owner. The steps run in this order:
  1. **Ask to release.** This machine asks the owner to release the conversation. If a turn is running, the dialog offers **Wait for this turn** or **Stop it now**.
  2. **Release.** The owner settles the conversation, including a WIP snapshot of uncommitted and unpushed code. It stops its harness session and marks the conversation **released to <this machine>**. From then on it refuses new turns for that conversation.
  3. **Transfer.** The settled record and WIP snapshot travel through the secure channel. No vault backend is needed when both machines are online.
  4. **Adopt.** This machine adopts the record through the existing Continue here path (`services/vault-continue.ts`). It resolves the project checkout by git origin, offers a clone when the project is missing, applies the WIP snapshot and resumes the harness session.
  5. **Finish.** The old owner shows the conversation as "Continued on <this machine>", read-only.

  If adoption fails, the release is undone and the old owner resumes. A conversation is never run by two machines at once (D-8). When the old owner is offline, Pull here falls back to the vault: it adopts the latest saved copy, through a compare-and-swap so only one machine wins.
- **FR-9 Machine-aware UI.** Rows from another machine carry a machine chip. The title bar has four states (D-6). An offline owner shows a banner, "<label> is offline (last seen <time>)", with **Reconnect**, **Read saved copy** and **Continue here**, each shown only when it applies. **Hide this machine** removes its rows without unlinking.
- **FR-10 Start anything on any machine.** The new-conversation dialog (`components/newConversation/NewConversationDialog.tsx`) gains a **Machine** field, which defaults to this machine and includes **Auto** (FR-22) and **Fly (new VM)**. The CLI gains:
  - `pan start <issue> --machine <label|auto|fly>`;
  - `pan worker run --machine <label|auto|fly>`;
  - `pan lane start --machine <label|auto|fly>` ([PAN-4638](https://github.com/eltmon/overdeck/issues/4638)).

  Conversations, work agents, workers and lanes can all run on any machine, including Fly.
- **FR-11 Delegation with a report back.** Work an agent starts on another machine is followed until it ends, and its report or last reply returns to the parent the way a local worker's report does.
  - **Project match:** by git origin. If nothing matches, the error names **Add this project to <machine>**.
  - **Offline target:** if the target goes offline, the follower retries with back-off up to 5 minutes and resumes after a restart.
  - **Stop:** stopping the parent stops the remote task.
- **FR-12 Projects across machines.** The sidebar groups the same repository across machines by git origin; the setting **Combine matching repositories across machines** is on by default. **Add this project to <machine>** clones the repository there through the project-creation core (`src/lib/projects/create.ts`, `create-perform.ts`). It also copies the git-ignored files you select (`.env`, `.envrc` and `.dev.vars` preselected, at most 1 MiB each) through the secure channels.
- **FR-13 Fleet awareness.** Needs-You, search and "which machine is working on PAN-<n>" cover all online linked machines, with each result labelled by machine.
- **FR-14 (retired in revision 4).** "Reach without Tailscale" through a relay WebSocket is replaced by FR-19 to FR-21.
- **FR-15 Push to a phone.** Needs-you events (approval, question, agent finished or failed) reach a phone as Web Push. The machine sends them directly to the browser's push service with its own VAPID keys. Each payload is encrypted to the phone's subscription key (RFC 8291), so neither the push service nor overdeck.ai can read it. A self-hosted ntfy topic is an optional second provider, carrying titles only when configured.
- **FR-16 Phone.** The phone installs the dashboard of one machine as a PWA over Tailscale Serve HTTPS, and sees the fleet through that machine's links. Overdeck walks the operator through installing the Tailscale app on the phone (FR-19). The phone never holds machine keys.
- **FR-17 SSH machines.** **Add an SSH machine** (and `pan machines add-ssh <host>`) has this machine's server open an SSH session to the host. It starts or adopts `pan up` there, forwards a loopback port, pairs over it, and adds an `ssh` route. It stops only a server it started itself.
- **FR-18 Fly VMs are machines.** A Fly VM runs an Overdeck server (`pan serve`) and is linked at spawn. Conversations, work agents, workers and gauntlet lanes run there with any supported harness: Claude Code at once, and Codex through [PAN-4296](https://github.com/eltmon/overdeck/issues/4296). They are ordinary linked conversations with live transcripts, terminals, remote control and Pull here. Home reaches the VM over its `public` address through Fly's proxy, inside the secure channel. When the operator has given Overdeck a Tailscale OAuth client, the VM also joins the tailnet with an ephemeral key, which removes the VM from the tailnet when it stops. A run-level cap (`remote.max_concurrent_agents`, plus a per-gauntlet-run `gauntlet.fly.max_vms`) bounds spend.
- **FR-19 Tailscale set up by Overdeck.** **Set up Tailscale** in Settings → Anywhere and in the link flow (also `pan tailscale setup`) does the following:
  1. **Detect** the `tailscale` CLI and its state (`tailscale status --json`).
  2. **Install** it with the platform's standard installer. Steps that need an administrator password run in a visible terminal pane where the operator types it (D-17).
  3. **Sign in:** start the login and open the sign-in URL Tailscale prints.
  4. **Serve:** set this user as the Tailscale operator so Overdeck can run `tailscale serve`, and turn on Tailscale Serve HTTPS for the dashboard. Overdeck checks whether MagicDNS and HTTPS certificates are on for the tailnet, and links the admin page when they are not.
  5. **Discover:** offer **Link** for every tailnet peer whose descriptor answers on the Overdeck port. Linking still needs a pairing code or an approval (FR-20).

  For a phone, it shows a QR code for the Tailscale app and the account to sign in with. The Anywhere status card shows Tailscale's state on every machine.
- **FR-20 Directory (account service).** A machine signed in to an overdeck.ai account registers in the account's directory: environment id, label, machine-key fingerprint, presence, and candidate addresses (LAN, tailnet, public, and the addresses STUN reports). Using the directory, it can:
  - see all of the account's machines, online or not, without being on the same network;
  - **approve a new machine** from any machine already linked. Both screens show the new machine's key fingerprint, and approving it creates the links with no pairing code;
  - open a `direct` route to a machine with no Tailscale, by exchanging connection candidates through the directory and opening a peer-to-peer path through NAT (D-3).

  The directory moves only addresses, presence, fingerprints and connection setup messages. It never moves conversation bytes.
- **FR-21 Relay fallback (relay plan only).** When every other route to a linked machine fails, and the account's plan includes relay service, the two machines connect through a TURN server. The connection carries the same secure channel. Usage is counted per account. At the monthly allowance (50 GB, OD-3) the relay stops until the next month, and the status card says "Relay allowance used; install Tailscale or add 50 GB" with an **Add 50 GB** button. The Anywhere status card shows **Using relay** and the bytes used this month, so the operator can see when installing Tailscale would remove the cost.
- **FR-22 Automatic machine choice.** **Auto** in the Machine field, and `--machine auto` on `pan start`, `pan worker run` and `pan lane start`, picks the machine by the rule in D-19.
  - **Load reporting:** each machine adds its CPU pressure (`readCpuPsi()` in `src/lib/system-health/cpu-psi.ts`, the `some avg10` value), available memory and running-agent count to the 15 s link heartbeat (FR-3).
  - **Machines list:** it shows those three numbers for every online machine.
  - **Feedback:** the dialog and the CLI name the chosen machine and the reason, for example `Auto → desk (CPU pressure 3%, 41 GB free, 2 agents)`.
- **FR-23 Machine capabilities and reserved machines.**
  - **Detected tags:** each machine's descriptor advertises capability tags that it detects at server start: its OS (`linux`, `macos`, `windows`), `docker` (`docker info` succeeds), `gpu` (`nvidia-smi` succeeds) and `ios-sim` (on macOS, `xcrun simctl list` succeeds).
  - **Operator tags:** the operator adds tags of their own in `anywhere.machine.tags`.
  - **Requirements:** `--needs <tag,…>` on the three commands in FR-22, and a **Needs** field in the new-conversation dialog, limit the choice to machines that have every tag. A gauntlet critic that runs a Docker Compose stack declares `--needs docker`.
  - **Reserved machines:** `anywhere.machine.placement: on-request` reserves a machine. **Auto** never picks it unless it is the only online machine with a required tag. Naming it with `--machine <label>` always works.
- **FR-24 Preview another machine's dev server.** **Open preview** on a linked conversation (and `pan machines forward <label> <port>`) forwards a TCP port from the owner to this machine through the secure channel.
  - **Ports:** the owner's dev-server ports for that workspace are offered, and the operator can type any other port.
  - **Local end:** this machine listens on `127.0.0.1` on a free port and opens it in the browser. The forward closes when the operator stops it, or after 30 minutes with no connection.
  - **Limits:** the rules are in D-22.
- **FR-25 One command for a fresh server.** `pan connect` (and `npx @overdeck/core connect` on a machine with no install) turns a machine reached over SSH into a lasting linked machine:
  1. It installs the server as a user service, so it survives logout and reboot. On Linux it uses the supervisor unit (`installSupervisorUnit()` in `src/lib/systemd.ts`) and turns on lingering for the user. When `loginctl enable-linger` needs elevation, it prints the exact `sudo loginctl enable-linger <user>` line and waits for the operator to run it. On macOS it installs a launchd agent.
  2. It starts the server and prints one link. Opening the link on a linked machine pairs it (FR-1). When the machine is signed in to an account, it also shows as waiting for approval in the directory (FR-20).
  3. When lingering cannot be turned on, it says plainly that the server stops at logout.

  After this the operator can log out of SSH and manage the machine from any linked machine.
- **FR-26 Webhook triggers.** A conversation or a project can have triggers. A trigger is a secret URL; each event sent to it either sends a message to the conversation or starts a new conversation from a prompt template. Manage triggers with `pan triggers add|list|remove` and Settings → Anywhere → Triggers.
  - **Delivery routes** (D-20):
    - **Tailscale Funnel** on the machine: free, and only works while the machine is online.
    - **Directory inbox** at `https://connect.overdeck.ai/h/<id>`: holds events for up to 24 hours while the machine is offline, then delivers them in order.
  - **Signatures:** the machine checks GitHub's `X-Hub-Signature-256` and Stripe's `Stripe-Signature` when the trigger has a signing secret.
  - **Untrusted input:** the event body (at most 64 KiB, truncated beyond that) reaches the agent marked as external data. A trigger can only send a message or start a conversation. It can never answer a question or approve a permission.
  - **Not the CI webhook:** this is separate from the existing GitHub webhook that feeds CI state (`/api/webhooks/github`, `src/dashboard/server/routes/webhooks.ts`).
- **FR-27 Overdeck MCP server.** Outside tools (another agent harness, a chat bot) can drive Overdeck through MCP (D-21).
  - **Tools:** list machines, list and search conversations, read a conversation, send a message, start a conversation (with `machine`, including `auto`), and start a worker.
  - **Transports:** stdio with `pan mcp serve`, and streamable HTTP at `/mcp` on the dashboard.
  - **Copy MCP URL:** in Settings → Anywhere, it mints a scoped `odk_` token and copies the machine's Tailscale Serve URL for `/mcp` with the token.
  - **Fleet reach:** one URL reaches the whole fleet through this machine's links.
- **FR-28 Message another machine's conversation.** `pan tell @<label>/<conv> "<message>"` delivers to a conversation on a linked machine through the link. The owner applies the same role and id checks it applies to a local `pan tell` (`src/cli/commands/tell.ts`). A call from an agent is fenced (FR-4).
- **FR-29 Fleet updates include the harnesses.** **Update all** (W-LINK7) updates Overdeck and the harness CLIs (Claude Code, Codex and the other installed harnesses, each with its own update command) on every online machine.
  - **Versions:** a per-machine table shows each version before and after.
  - **Running turns:** a machine with a turn in progress is updated after the turn ends, unless the operator chooses **Update now**.
- **FR-30 Open another machine's checkout in a local editor.** Today **Open in editor** (`src/dashboard/server/services/open.ts`; editor list in `packages/contracts/src/editor.ts`) launches the editor on the machine that runs the server.
  - **Linked conversations:** on a linked conversation, the action runs on the viewing machine instead. It launches the editor in remote-SSH mode at the owner's checkout (`code --remote ssh-remote+<host> <path>`). This needs an `ssh` route or a tailnet hostname that accepts SSH (Tailscale SSH or OpenSSH).
  - **Editors:** VS Code, VS Code Insiders and VSCodium are supported. *Implementation checkpoint:* check whether Cursor's and Windsurf's CLIs accept the same `--remote` flag, and enable them only if they do. *Fallback:* hide the action for those editors, with a tooltip that names the supported editors.
- **FR-31 Fleet usage.** The cost and usage view gains a **Machine** column and an **All machines** total. It reads each linked machine's cost summary over the link (`read:costs` scope on machine tokens, D-9). An offline machine shows its last cached numbers with their time. Usage per provider account is counted once even when several machines use the same account.
- **FR-32 Compare settings across machines.** **Compare settings** in Settings → Anywhere → Machines shows the settings whose resolved values differ between this machine and a chosen linked machine. Secrets are shown only as "set" or "not set".
  - **Read-only:** links never change settings (FR-4), so the comparison is read-only.
  - **Copying:** for each difference it offers a copyable `pan config set <key> <value>` line to run on the target machine, or opens that machine's dashboard when it is reachable over Tailscale Serve.
  - **Token scope:** machine tokens gain `read:settings`, which returns redacted resolved values.

### Non-functional

- **NFR-1 No plaintext between machines.** Every byte between two machines travels inside a secure channel, whatever the route. A route that cannot carry a secure channel is not offered.
- **NFR-2 No root credential leaves a machine.** Links, devices and the relay never hold the internal token or a root session.
- **NFR-3 Owner is authority.** A linked conversation's state is whatever the owner says. The linking machine keeps only a read cache (D-5) and never writes status for another machine's conversation.
- **NFR-4 One runner per conversation.** At most one machine runs a conversation's harness at any time, enforced by release-before-adopt (FR-8) and by the vault compare-and-swap.
- **NFR-5 Bounded idle traffic.** An idle link costs at most one heartbeat every 15 s plus deltas, with no full-list polling.
- **NFR-6 Compatibility.** Every link checks `protocolVersion` and capability flags. A mismatched machine shows as `unsupported` with the exact `pan` version to install, and is never retried in a loop.
- **NFR-7 Async only.** Link, channel, route, SSH and proxy code reachable from the dashboard server uses async I/O. No `execSync`, and no new `*Sync` tmux calls.
- **NFR-8 Self-hosting has no feature gate.** Everything except the hosted directory, the relay, the directory webhook inbox and the hosted vault works without an overdeck.ai account.
- **NFR-9 Small reads on slow links.**
  - **Opening:** opening a linked conversation transfers no more than the bounded open window (75 rows or 1 MiB, PAN-4558) plus 64 KiB.
  - **Returning:** going back to a conversation opened in the last 10 minutes transfers only the rows newer than the cached sequence.
  - **Why it matters:** this is what makes a phone on a poor connection usable, and the relay costs money per gigabyte.

## Decisions

- **D-1 Federation runs server to server.**
  - **What "client to server" would have meant** (t3code's way): the laptop's browser page connects directly to the desktop's Overdeck server and to every other machine. The page keeps the list of machines and their credentials, and it decrypts and caches everything itself.
  - **What this plan does instead:** the laptop's browser talks only to the laptop's own Overdeck server, as today. That server holds the links and talks to the desktop's server over the secure channel.
  - **Why:**
    1. To **pull** a conversation, the laptop must run its own Overdeck server anyway, because that is what runs the harness. So the laptop always has a server to hold the links.
    2. End-to-end encryption needs long-term keys on both ends. A server can hold a machine key in a 0600 file. A browser page would have to keep keys in browser storage and load its code from whichever machine it is talking to.
    3. The frontend is same-origin by construction (`resolveRpcUrl` builds from `window.location`; about 400 `fetch('/api/…')` calls are relative; CORS exists only on the session mint; cookies are `SameSite=Strict`). Client-side federation would mean rewriting that transport.
    4. Delegation and gauntlet lanes are server-to-server calls in any design.
  - **Cost:** a phone opens one machine's dashboard and sees the fleet through that machine (FR-16).
- **D-2 Secure channel.**
  - **Protocol:** a Noise protocol handshake (`Noise_IK` once keys are pinned; `Noise_XXpsk` with the pairing code during pairing) over X25519, ChaCha20-Poly1305 and BLAKE2/SHA-256. All three primitives are in Node's built-in `crypto`. The implementation uses a vetted Noise library chosen in W-SEC1, never hand-rolled framing on top of raw primitives.
  - **Transport:** the channel is a byte stream. The receiving end hands each decrypted stream to its existing HTTP server as a connection (`server.emit('connection', stream)`), so every existing route, the `/ws/rpc` event stream and the `/ws/terminal` PTY stream work across a link unchanged. The linking end gives its HTTP and WebSocket clients a `createConnection` that returns a channel stream.
  - **Routes:** each route carries the channel the same way: raw TCP on `lan`/`tailnet`, the forwarded port on `ssh`, and binary WebSocket frames through the relay.
- **D-3 Directory first, relay last.** The overdeck.ai connection service introduces machines and steps aside. It forwards bytes only when nothing else works.
  - **Where:** a new `services/connect` Cloudflare Worker (FSL-1.1-MIT like `services/account` and `services/share`) at `connect.overdeck.ai`, with one Durable Object per account. This follows the 2026-10-02 decision to run all overdeck.ai services on Cloudflare.
  - **Directory and presence:** each signed-in machine keeps one hibernating WebSocket to its account's Durable Object. Through it the machine publishes its environment id, label, key fingerprint and candidate addresses, and receives approval requests and connection offers.
  - **Direct connections:** two machines that cannot reach each other directly exchange connection candidates through the Durable Object. They then open a WebRTC data channel using STUN for NAT traversal, and the secure channel runs inside it.
    - The data channel uses `werift` (pure TypeScript), the library PAN-658 already chose for Shared Sessions.
    - The candidate-exchange code follows `services/share`'s room protocol.
    - This is the `direct` route. No conversation bytes touch overdeck.ai.
  - **Relay fallback:** when STUN cannot open a path (symmetric NAT, UDP blocked), a relay-plan account receives short-lived Cloudflare Realtime TURN credentials. The same WebRTC connection then runs through TURN, still carrying the secure channel, so TURN forwards only ciphertext. Cloudflare charges $0.05 per GB after the first 1,000 GB a month, shared across the whole Cloudflare account (`docs/SHARED-SESSIONS.md:106`).
  - **No tunnels:** there is no Cloudflare Tunnel and no `cloudflared`.
  - **Self-hosting:** `anywhere.directory_url` is a runtime setting, defaulting to `https://connect.overdeck.ai`. A self-hoster can run their own `services/connect` and point their TURN credentials at their own server.
  - **Replaces:** the July design (Fly host, its own OAuth, traffic readable in the relay) and revisions 2 and 3 (Cloudflare Tunnel, then a Durable Object byte pipe).
- **D-4 Sharing is on by default.** Linking your machines shares the conversation list both ways, and content is fetched live on open. Each machine has one switch to stop sharing. There is no per-conversation privacy flag in this release (OD-1).
- **D-5 Linked conversations live in a cache table, not in `conversations`.**
  - **Table:** `linked_conversations` in `overdeck.db`, keyed by (environment id, conversation name). It holds the FR-5 metadata, including the native session id that FR-6 deduplicates on, plus `cached_at` and the owner's `sequence`.
  - **Lifecycle:** it is rebuilt from the owner on every connect, pruned when the owner stops reporting a row, and written only from the owner's own answer.
  - **Why:** CLAUDE.md says "Overdeck stores no status it can derive" and "there are no placeholder rows". Rows in `conversations` drive liveness, costs, lanes and the PR sweep. A separate cache that the list API merges at read time keeps the owner authoritative and still lists offline machines.
- **D-6 Title bar states.** These are surface tones per the dashboard style guide (load `pan-style-guide` when implementing), never status colors. An interactive mockup is approved before implementation.

  | State | Title bar | Extra |
  |---|---|---|
  | Local | `var(--card)` (unchanged) | none |
  | Remote control, owner online | new token `--surface-remote`: `--card` mixed about 6% toward `--background`, in both themes | chip "on <label>" |
  | Owner offline, saved copy exists | `--surface-remote` plus muted foreground | offline banner with **Read saved copy** and **Continue here** |
  | Owner offline, no saved copy | `--surface-remote` plus muted foreground | offline banner with **Reconnect** |
  | Released to another machine (on the old owner) | `--surface-remote` plus muted foreground | "Continued on <label>" with **Open there** |
- **D-7 Owner machine is a column.** `conversations` gains `environment_id TEXT`, backfilled with this machine's id for local rows and with the record owner's id for vault rows, plus `released_to TEXT` (the environment id it was pulled to, or null).
- **D-8 Single runner through release-before-adopt.**
  - A pull is a two-step handoff: the owner releases first, then the target adopts.
  - While `released_to` is set, the old owner's conversation routes refuse new turns (409 `conversation-released`). `/resume` refuses too, unless the pull failed and was undone.
  - The vault compare-and-swap still guards the offline path.
  - There is no shared or simultaneous running, by the operator's decision of 2026-10-29.
- **D-9 Machine-link tokens are a new token kind.**
  - `AccessTokenKind` gains `'machine'`. A machine token carries `read:events`, `read:state`, `read:conversations`, `read:costs`, `read:settings` (redacted values, FR-32), `tell` and `operate`, plus `forward` on operator-level links only (D-22). It never carries `admin`, and it is accepted only inside a secure channel.
  - `route-scopes.ts` gains rows for:
    - the `/ws/rpc` conversation-message and domain-event subscriptions;
    - send, stop, abort and permission answers;
    - conversation, worker and lane spawn;
    - the release, transfer and settle routes for Pull here.
  - Pairing, token minting, settings and vault setup stay `admin`.
- **D-10 Routes are ranked direct first, the relay last.** The ranking is `lan < tailnet < ssh < public < direct < relay`, which extends t3code's. A route learned from a descriptor borrows its link and is dropped when no longer advertised.
- **D-11 Delegated work starts from the remote's checkout.** Work on another machine gets its own workspace branched from that machine's view of `origin`. Unpushed local commits are not visible there. If the parent has unpushed commits, the CLI says so and offers `--push-first`.
- **D-12 Fly VMs are machines.** The Fly image ships `pan` and runs `pan serve`. At spawn, the home machine creates a pairing code and passes it to the VM through the Fly Machines exec API, and the VM's server links back over a secure channel. Remote agents and conversations are then linked conversations, which dissolves [PAN-1775](https://github.com/eltmon/overdeck/issues/1775) and the invisible-transcript gap. Before that, restore the three loops the Cut deleted and stop copying the operator's private SSH key to VMs (W-FLY1).
- **D-13 SSH is run by the server.** The server that holds the link opens the SSH session, so SSH machines work from any browser. PAN-4404's design is kept: pinned version, `managed` vs `external` markers, stop only what you started, per-host lock, explicit version-mismatch error.
- **D-14 The desktop app connects to one machine.** [PAN-4402](https://github.com/eltmon/overdeck/issues/4402) is narrowed to letting the desktop app open a chosen machine's dashboard with no local server, storing that machine's device credential with Electron `safeStorage`.
- **D-15 Carried forward from revision 1 (D-7 as amended 2026-09-28).** Cloud components carry transport only. An overdeck.ai service may store encrypted, user-keyed data it cannot read, with the key held only on the user's devices. No pipeline, agent or issue state moves to the cloud. The relay (D-3) and the hosted vault depend on this.
- **D-16 Push needs no relay.** Web Push from the machine itself with RFC 8291 payload encryption (FR-15) replaces both the ntfy-only design ([PAN-2354](https://github.com/eltmon/overdeck/issues/2354)) and relay-delivered push. This is free for self-hosters. It changes the pricing page, which sells "relay and hosted push" (OD-3).
- **D-17 Tailscale is the encouraged route, and Overdeck sets it up.** Tailscale is end-to-end encrypted, handles NAT traversal itself, and costs overdeck.ai no bandwidth. So the link flow offers **Set up Tailscale** first, and offers the directory only when the operator declines or a machine cannot run Tailscale. Overdeck never asks for, stores or passes an administrator password.
  - **Installers:** a step that needs elevation runs the platform's official installer in a visible terminal pane, where the operator types the password:
    - Linux: `curl -fsSL https://tailscale.com/install.sh | sh`;
    - macOS: the standalone package, or `brew install --cask tailscale` when Homebrew is present;
    - Windows: `winget install tailscale.tailscale`;
    - WSL2: use the Windows client.
  - **Implementation checkpoint (W-TS1):** on Linux without sudo, run `tailscaled` in userspace-networking mode as the user. The live test must show that it accepts inbound connections to the Overdeck port. *Fallback:* show the installer command and stop there.
- **D-18 The directory never vouches for a key.** The machine keys the secure channel trusts come only from a pairing code (FR-1) or from an approval on an already-linked machine that shows the same fingerprint on both screens (FR-20). A compromised directory can at worst hide a machine or offer wrong addresses. It can never make a machine trust an impostor.
- **D-19 The Auto placement rule.** It is deterministic, so the same inputs always pick the same machine.
  1. **Candidates:** this machine plus every online, compatible linked machine that has the project (matched by git origin) and every tag in `--needs`.
  2. **Exclusions:**
     - Reserved machines (`on-request`), unless one is the only candidate with a required tag.
     - Machines that `assessCpuPressure()` (`src/lib/cloister/cpu-pressure.ts`, the check lane launches already use in `src/lib/lanes/launch.ts`) calls CPU-saturated.
     - Fly, unless `remote.auto_fly: true` and every other candidate is excluded.
  3. **Score:** lowest CPU pressure (`some avg10`) wins. Ties go to the most available memory, then the fewest running agents, then this machine.
  4. **No candidate:** the command fails and names the reason for each machine, for example `laptop: no docker; desk: offline`.
  5. **No project:** a machine without the project is never a candidate. The error offers **Add this project to <machine>** (FR-12).
- **D-20 The webhook inbox stores only sealed events.**
  - **Funnel:** with Tailscale Funnel, events go straight to the machine and overdeck.ai never sees them.
  - **Inbox:** the directory inbox must terminate TLS for the sender (GitHub, Stripe), so it sees each event in memory once. It immediately seals the event to the target machine's public key (an X25519 sealed box) and stores only that sealed copy. It deletes the copy when the machine acknowledges delivery, or after 24 hours.
  - **Disclosure:** this is the one place overdeck.ai sees content, and only content that a third party sends to a URL the operator published. It is consistent with D-15, which allows storing only data the service cannot read. The trigger settings page states it plainly.
  - **Signatures:** signature checks run on the machine, so the directory needs no signing secret.
- **D-21 One MCP server, always fenced.**
  - **Shape:** the MCP server is a thin layer over the existing routes, so it adds no second path to any operation. Its calls carry the `odk_` token's scopes and are treated like agent calls (FR-4): no pairing, token minting or settings.
  - **Approvals:** answering questions and approving permissions need an `approve` scope, which is off by default.
  - **Not Channels:** this server is separate from the Channels bridge (`src/lib/channels/overdeck-bridge.ts`), which is a per-agent message-delivery bridge, not a control surface.
- **D-22 Port forwards cannot bypass token scopes.**
  - **Who:** only operator-level links carry `forward`. Agent-fenced links and MCP tokens never do.
  - **Owner end:** the owner forwards only to its own loopback addresses. It refuses its dashboard, supervisor and Traefik ports, so a forward can never reach an Overdeck API without a scoped token.
  - **Viewing end:** the viewing machine listens on `127.0.0.1` only.

## Settled by the operator (2026-10-29 and 2026-11-01)

- **Encryption:** no unencrypted traffic between machines, on any route. This is D-2 and D-3, and it replaces revision 2's OD-1.
- **Access:** remote control is the everyday mode. Operator-level links between your own machines are the default, which replaces revision 2's OD-3.
- **Pulling:** pulling makes the laptop the only runner, and simultaneous running is not supported (FR-8, D-8).
- **One release:** everything ships together in one release, with no phases.
- **Fly:** Fly VMs are machines that run conversations, not only work agents (D-12, FR-18). Gauntlet lanes spread across machines, including Fly ([PAN-4638](https://github.com/eltmon/overdeck/issues/4638)). This replaces revision 2's OD-5.
- **Tailscale first:** encourage Tailscale so overdeck.ai pays no bandwidth, and have Overdeck install and set it up (D-17, FR-19).
- **Directory first:** overdeck.ai is a directory first and a relay only when nothing else works (D-3, FR-20, FR-21).
- **Two prices:** pricing distinguishes directory service from relay service (OD-3).
- **Phone:** the phone uses the Tailscale app, so no browser holds machine keys in this release. This follows from Tailscale-first and replaces revision 3's OD-2; the operator can reverse it.
- **Free directory (2026-11-01):** a free overdeck.ai account includes the directory and direct connections for up to 3 machines. Anywhere, at today's price, adds unlimited machines, the webhook inbox and the 100 GB hosted vault. The relay is a +$30/yr add-on with 50 GB a month. The founding price ($60/yr) applies to Anywhere and ends at 500 subscribers or 90 days after release (OD-3).
- **t3code parity (2026-11-01):** the multi-machine features from the 2026-10-29 t3code video ship in this release (FR-22 to FR-32, NFR-9). Its other features (inbox sidebar, scheduled conversations, send when limits reset, quoting a reply, self-triage, VS Code theme import) are tracked as separate issues outside this epic.

## Open decisions

- **OD-1 Per-conversation privacy.** *Recommendation:* none in this release. Linked machines see every conversation's metadata.
- **OD-2 (retired in revision 4; settled as "Phone" above).**
- **OD-3 Prices for directory service and relay service (settled 2026-11-01).** The cost basis:
  - **Directory, presence and direct connections** cost overdeck.ai almost nothing per user: Worker requests and hibernating Durable Object time, a few cents a month.
  - **The relay** costs about $0.05 per GB once all users together pass 1,000 GB a month.
  - **The hosted vault's** costs are already modeled in `pan-2609.md`.

  *Structure and prices (approved by the operator on 2026-11-01):*

  | Tier | Includes | Price |
  |---|---|---|
  | Free, no account | Everything over Tailscale, LAN, SSH and Fly; Tailscale Funnel triggers; Web Push; the MCP server; Session Vault on your own git or directory | $0 |
  | Free account | Free, plus the directory and direct connections for up to 3 machines | $0 |
  | Anywhere | Unlimited machines in the directory, the webhook inbox with 24-hour hold, and the 100 GB hosted vault | today's Anywhere price ($96/yr or $10/mo) is the starting point |
  | Relay add-on | Anywhere, plus relay fallback with 50 GB of relay traffic a month. At the cap the relay stops until next month; an extra 50 GB is a one-time $3 purchase. No per-gigabyte billing | +$3/mo or +$30/yr on the Anywhere subscription ($13/mo or $126/yr in all), billed in the same charge |

  *Why a free directory:* T3 Connect is free for three devices, and t3code says a larger plan is coming [36:23]. A paid directory would lose people who compare the two directly. Our directory costs a few cents per user per month because it moves no conversation bytes, so the free account can match t3code's three devices. The paid tiers then sell what costs money or does real work: more machines, the webhook inbox, the hosted vault and the relay.

  *Relay add-on reasoning:*
  - **Cost:** a user who uses all 50 GB every month costs about $2.50 a month at Cloudflare's $0.05 per GB (after the first 1,000 GB a month, shared by all users), so the add-on roughly breaks even in the worst case. Most relay users will use far less, because the relay carries traffic only when no direct path works.
  - **Fees:** the add-on is part of the Anywhere charge, never a separate one. Creem's $0.40 fixed fee would take about 17% of a separate $3 charge.
  - **Hard cap:** the cap bounds what one user can cost and avoids building usage billing on Creem. The message at the cap is "Relay allowance used; install Tailscale or add 50 GB".
  - **Revisit:** check the allowance against real monthly use of the first relay users. If dev-server previews (FR-24) push typical use near the cap, lower the allowance or keep previews off the relay.

  *Founding price:* $60 a year, annual only, locked while subscribed. It applies to the Anywhere tier, and founders add the relay at the normal $30 a year. It ends at the first 500 subscribers or 90 days after the Anywhere release ships, whichever comes first. This replaces "until the relay ships", which would have ended it on launch day because the relay ships in the same release.

  Until billing ([PAN-4294](https://github.com/eltmon/overdeck/issues/4294)) ships, the paid tiers are available only to invite-allowlisted accounts, with the 50 GB relay cap enforced by `services/connect` (W-LINK8). The free account's 3-machine limit is enforced by `services/connect` from day one. Billing needs the relay add-on and the one-time 50 GB purchase as Creem products.

- **OD-4 Docker on Fly.** Gauntlet critics often run a full stack with Docker Compose. Whether the `pan-workspace` Fly image can run Docker needs a live check (implementation checkpoint in W-FLY2). *Fallback:* machines advertise a `docker` capability in the descriptor, and `pan lane start --machine auto` places Docker-needing critics only on machines that have it.

## Threat model changes

- **A stolen laptop holds machine links.** It gets operator-level access to the desktop's conversations, but no admin: it cannot pair, mint tokens or change settings. Revoke it from the desktop's Machines list, and its channels close within 5 s.
- **A compromised linked machine** can drive conversations on the machines it links to, but cannot hop further, and its agents are fenced (FR-4).
- **An attacker on any route** (LAN, a hostile Wi-Fi, the relay, Cloudflare) sees only Noise ciphertext. They cannot pair in the middle without the one-time code, and cannot impersonate a machine without its key (D-2).
- **The directory operator** (overdeck.ai) sees account and machine ids, labels, key fingerprints, presence and the machines' IP addresses. It cannot impersonate a machine (D-18). **TURN** sees only ciphertext and byte counts. Push payloads are encrypted to the phone, and the hosted vault stays ciphertext (D-15).

- **A webhook trigger URL** is a bearer secret. Anyone holding it can send a message to the conversation, but only as marked external data: never an approval or an answer (FR-26). With the inbox, overdeck.ai sees each event once in memory and stores only a sealed copy (D-20).
- **An MCP token** can drive conversations within its scopes, and never pair, mint tokens or change settings (D-21). Revoking it from Settings → Anywhere closes its sessions within 5 s, like any `odk_` token.
- **A port forward** reaches only the owner's loopback services that are not Overdeck's own APIs, and only over operator-level links (D-22).

## Intersecting repo rules (restated for executors)

- The dashboard server runs Node 22 dist only, never Bun or tsx. Run `npm run build` before a restart.
- No `execSync` in server-reachable code. Use async tmux primitives only.
- Tests of retry, back-off, heartbeat, reconnect or follow use `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()`.
- Agent state is written only after the terminal-backend session exists. There are no placeholder rows, so remote spawns write rows only after the owner confirms the session.
- A new HTTP route needs a row in `tests/unit/lib/overdeck/no-loss-matrix.ts` and in `src/dashboard/server/route-scopes.ts`.
- JSONL transcripts are never deleted or truncated. A pull copies the transcript and never removes the old owner's file. Never send a destructive HTTP request speculatively.
- New issue work goes through `pan start`. Planning artifacts live under `.pan/` in this repo.
