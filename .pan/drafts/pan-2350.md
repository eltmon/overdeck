## Glossary

- **Home machine** — the developer workstation running the Overdeck dashboard server (`dist/dashboard/server.js`, Node 22, port 3011) and all agents. Behind NAT; no inbound ports.
- **Internal token** — the 32-byte hex root secret at `~/.overdeck/internal-token` (`src/lib/internal-token.ts`), auto-generated at first server start, sent as `x-overdeck-internal-token` or `Authorization: Bearer`. Today it is the *only* credential; every caller that isn't a loopback browser holds root.
- **Session cookie** — `overdeck_session`, an HMAC-SHA256 derivative of the internal token minted by `POST /api/dashboard/session` (`src/dashboard/server/server.ts`, handlers in `src/dashboard/server/routes/dashboard-auth.ts`). Minting requires loopback/Docker-bridge peer or the internal token (`rejectUnauthorizedDashboardSessionMintRequest`, `dashboard-auth.ts:290`; `isLoopbackPeer`, `dashboard-auth.ts:275`).
- **Bootstrap token flow** — the frontend reads `#overdeck_token=<token>` from the URL hash, strips it from history, and exchanges it for the session cookie (`consumeDashboardBootstrapToken`, `src/dashboard/frontend/src/lib/wsTransport.ts:50-62`; exchange at `:64-81`). This is the existing mechanism for authorizing a browser that is not loopback.
- **Trusted origins** — the allowlist in `src/dashboard/server/routes/origin-validation.ts` built from the port, `DASHBOARD_URL`, `OVERDECK_TRUSTED_ORIGINS` (CSV, `:26`), and `OVERDECK_TRAEFIK_DOMAIN` (`:31`).
- **Scoped access token** — NEW (this epic): a per-device/per-service credential with an explicit scope set, issued and revocable from the dashboard, stored server-side. Replaces handing the root internal token to remote devices/services.
- **Hermes** — the operator's OpenClaw-gateway fork on Fly.io (app `hermes-eltmon`, region iad), a Slack-connected chat agent. No Overdeck integration exists today (repo-wide grep: zero hits).
- **Fly 6PN** — Fly.io private IPv6 WireGuard mesh. `flyctl` can mint a WireGuard peer config for an external machine, putting the home machine on the same private network as Hermes with outbound-only connectivity.
- **Relay** — NEW (Phase 3): a small always-on cloud service the home machine dials *out* to over a persistent connection; phones/browsers/collaborators reach the relay's public endpoint and traffic is forwarded down the established connection. The pattern used by Nabu Casa, Happy, VS Code tunnels, Omnara.
- **Needs-you event** — any event requiring operator attention: AskUserQuestion prompts, blocked agents, merge gates. Sourced from the SSE stream (`GET /events/stream`, `src/dashboard/server/routes/events.ts:120`) with resumable delivery via `Last-Event-ID`.
- **PWA** — Progressive Web App; the mobile-first web surface with home-screen install + Web Push (iOS 16.4+ home-screen PWAs, native on Android).

## Problem

Overdeck is single-machine and single-credential by construction:

1. **No remote reachability.** The dashboard binds localhost; the machine is behind NAT. There is no path for a phone, a second laptop, or a cloud service to reach it.
2. **No identity granularity.** All auth collapses to one root internal token. `isLoopbackPeer` means a LAN phone can't even mint a session without being handed root.
3. **A live gap in the one WS surface that matters most.** `/ws/terminal` upgrades are authorized by origin check *only* — the PAN-457 token/session gate was removed as a hotfix (`authorizeTerminalUpgrade`, `src/dashboard/server/ws-terminal.ts:88-101`, comment references #1166). Acceptable for localhost; disqualifying for any remote exposure. [PAN-1166](https://github.com/eltmon/overdeck/issues/1166) tracks the proper fix and is a hard prerequisite of this epic.
4. **No cloud→desk inbound path.** The existing Fly remote-workspace subsystem (`src/lib/remote/`: `fly-provider.ts`, `remote-agents.ts`, `remote-completion.ts`) is host-pull over SSH. Nothing lets Hermes (or a phone) initiate contact.
5. **No user/participant model.** `conversations` has no owner column (`src/lib/overdeck/conversations.ts:33-91`); nothing anywhere models a second human. [PAN-658](https://github.com/eltmon/overdeck/issues/658) requires one.

## Threat model

This epic turns a localhost-only server into a remotely reachable one, so the security bar is "assume the edge is hostile." Assets at risk, in order: (1) **agent control** — `tell`/`operate` reach `deliverAgentMessage` and terminals, i.e. arbitrary instruction of processes running with the operator's local trust; (2) **conversation and pipeline content** — agent transcripts can contain code and secrets; (3) **the root internal token** — its compromise collapses every boundary below.

Adversaries considered: internet scanners at the public edge (Cloudflare/relay), the holder of a leaked device or service token, a compromised relay (Phase 3), a rogue Slack member speaking through Hermes, and a subscriber to a push channel.

Standing mitigations, enforced per phase: scope floor with per-purpose revocable credentials (NFR-3); peer-address trust disabled whenever any proxy fronts the server (PAN-2351 D-4, PAN-2352 D-2); the root internal token never leaves the home machine (AC-1); push payloads minimized so notification infrastructure learns metadata, not content (NFR-7); every external write action attributable to a named credential in the activity feed (NFR-8); the relay authenticates identity but holds no instance scopes (PAN-2356 FR-R4), with an honest documented privacy tier and an E2E upgrade path (PAN-2356 D-R3).

Out of model: physical access to the home machine; compromise of the operator's Cloudflare/GitHub accounts (root-equivalent by delegation — protect them with hardware-key 2FA); malicious code already running locally.

## Requirements

### Functional

- **FR-1** A scoped access-token system: tokens carry a scope set from {`read:events`, `read:state`, `read:conversations`, `tell`, `operate`, `admin`}, are individually revocable, never equal the root internal token, and are issued from an authenticated dashboard surface (UI + CLI).
- **FR-2** The bootstrap flow (`#overdeck_token=`) must accept and prefer scoped device tokens; handing the root token to a browser becomes a deprecated path.
- **FR-3** `/ws/terminal` upgrades require session-cookie or token auth in addition to origin validation, with a bootstrap path that works via Traefik and via Cloudflare (supersedes the #1166 hotfix; implement per [PAN-1166](https://github.com/eltmon/overdeck/issues/1166)'s acceptance criteria).
- **FR-4** All long-lived WS and SSE connections send an application-level heartbeat every ≤25s (Cloudflare idle cutoff is ~100s of silence).
- **FR-5** Remote browser access: the operator can open the dashboard from any network via a Cloudflare Tunnel hostname gated by Cloudflare Access (SSO), with terminals, conversations, and the flywheel view fully functional.
- **FR-6** Hermes bridge: an external service holding a scoped token can (a) subscribe to the event stream, (b) read pipeline/agent/conversation state, (c) send a message to a named agent or conversation (routed through `deliverAgentMessage` — no new write door), and (d) create a conversation. Reachability via Fly 6PN WireGuard (no public API exposure required for this leg).
- **FR-7** Push bridge: needs-you events produce push notifications to the operator's phone (ntfy first; Web Push when the PWA lands). Notify on needs-you, not on all activity.
- **FR-8** Mobile PWA: a mobile-first surface with (a) Needs-You feed as home screen with answer/approve actions, (b) conversation read+compose, (c) pipeline board, (d) terminal as read-mostly escape hatch, (e) installable manifest + Web Push.
- **FR-9** Relay service (Phase 3): home machine connects outbound-only; relay authenticates humans via GitHub OAuth; per-instance isolation; relay cannot read conversation content (TLS passthrough or client-side crypto); relay is the APNs/FCM/Web Push origin.
- **FR-10** [PAN-658](https://github.com/eltmon/overdeck/issues/658) Shared Sessions v0 rides the Phase 3 relay (plain WSS rooms) for transport, keeping its locked lobby/admit/kick/revoke/controller design unchanged; WebRTC DataChannels become a later optimization, not the v0 transport.

### Non-functional

- **NFR-1** No inbound firewall ports on the home machine, ever. All reachability is outbound-initiated (cloudflared, WireGuard, relay dial-out).
- **NFR-2** Visitors (phone browsers, collaborators) install nothing — no Tailscale, no VPN, no client daemon. WireGuard appears only machine-to-machine (home ↔ Fly 6PN).
- **NFR-3** Scope floor: a leaked `read:events` token must not permit `tell`/`operate`/PTY access. Every new route declares its required scope explicitly.
- **NFR-4** Cost ceiling: Phases 0–2 ≈ $0/mo (+domain); Phase 3 ≤ $5/mo until multi-tenant demand justifies more.
- **NFR-5** Dashboard server remains Node 22 dist-only (node-pty, circular-ESM constraints); no `execSync` anywhere server-reachable; retry/delay tests use fake timers.
- **NFR-6** Recoverability: relay and tunnel layers are stateless or rebuildable; no canonical state lives in the cloud (two-doors tenet — cloud components are transport, not a third state plane). *(Amended 2026-09-28 with D-7.)* Encrypted, user-keyed data that an overdeck.ai service stores but cannot read (the hosted Session Vault) is not a state plane: it is the user's own backup, readable only on the user's devices, and Overdeck's state still derives from git, the tracker, the PR and the terminal backend.
- **NFR-7** Notification payload minimization: push/notification bodies carry metadata only (role, issue, "needs an answer") by default on every transport (ntfy, Web Push, relay). Agent-prompt content may appear only behind an explicit opt-in config flag. Notification infrastructure (ntfy.sh upstream, APNs/FCM, the relay, the phone's lock screen) is treated as a third party that reads everything sent.
- **NFR-8** Attributable external actions: every mutating call on an external surface (`/api/external/*`, relay-proxied requests, pairing approvals) emits an auditable `activity.entry` event naming the credential (token name / paired identity), the action, and the outcome. "Who told the agent to do that" is answerable from the dashboard activity feed, not from guesswork.

## Phases / work items

Each phase below becomes (or references) its own issue and gets a full implementation-grade spec at `pan plan` time. This PRD fixes scope, decisions, and interfaces.

### Phase 0 — security prerequisites (issue: PAN-2351; depends on [PAN-1166](https://github.com/eltmon/overdeck/issues/1166))

**W0.1 Scoped access tokens (FR-1, FR-2, NFR-3).** New table (SQLite, runtime plane) `access_tokens(id, name, token_hash, scopes, created_at, last_used_at, revoked_at)`. Verification joins the existing auth helpers in `dashboard-auth.ts` — `rejectUnauthorizedDashboardRequest` gains an optional `requiredScope` parameter; internal token ⇒ implicit `admin`. Issue/revoke via new authenticated routes + dashboard Settings panel + `pan token create|list|revoke`. Token format `odk_<32hex>`; store SHA-256 hash only.
**W0.2 ws-terminal gate (FR-3).** Land [PAN-1166](https://github.com/eltmon/overdeck/issues/1166) with the scope model available: terminal upgrade requires session cookie (browser) or token with `operate` (programmatic). Origin validation stays.
**W0.3 Heartbeats (FR-4).** App-level ping/pong on `/ws/rpc`, `/ws/terminal` (control-message `{type:'ping'}`) and SSE keepalive comments every 20s in `routes/events.ts`.
**Acceptance:** a `read:events` token can stream SSE but gets 403 on tell/terminal; revocation takes effect ≤5s; terminals survive 10 minutes idle behind a 100s-idle proxy.

### Phase 1a — remote dashboard access, operator-only (issue: PAN-2352)

Ops + config + docs, minimal code. `cloudflared` on the home machine → `deck.<domain>` → `http://localhost:3011`; Cloudflare Access policy = operator email(s); add `https://deck.<domain>` to `OVERDECK_TRUSTED_ORIGINS`; first-visit device authorization via the bootstrap flow carrying a **device-scoped** token (FR-2). Deliverables: setup runbook in `docs/REMOTE-ACCESS.md`, a `pan remote-access doctor` check (tunnel up, origin trusted, heartbeat active), and the coffee-shop walkthrough (second laptop = same URL + device token; optional `cloudflared` SSH for code editing).
**Acceptance:** phone on cellular loads dashboard, streams a live terminal ≥10 min, answers an AUQ; second laptop picks up the flywheel conversation with zero home-machine changes.

### Phase 1b — Hermes external-agent bridge (issue: PAN-2353)

**W1b.1 Fly 6PN peering.** WireGuard-peer the home machine into the Fly org (`flyctl wireguard create`); systemd unit; Hermes reaches `http://<6pn-addr>:3011` privately. Implementation checkpoint: verify dashboard binding/reachability over the WG interface; fallback = cloudflared service-token path (same API, public edge).
**W1b.2 External-agent API surface.** No new write doors — thin authenticated routes over existing primitives: `GET /events/stream` (exists; scope `read:events`), `GET /api/external/state` (pipeline/agents/conversations summary; scope `read:state`), `POST /api/external/tell {target, message}` → `deliverAgentMessage` (scope `tell`), `POST /api/external/conversations` (scope `operate`). Route module `src/dashboard/server/routes/external.ts`, following the `merge-ops.ts:1766` internal-notify pattern for shape.
**W1b.3 Hermes side.** A small Overdeck skill/plugin for Hermes (its repo, not this one): token + base URL config, event subscription → Slack notifications, `tell`/status commands.
**Acceptance:** from Slack, "what's the flywheel doing?" returns live state; "tell agent <id> X" lands in the agent's pane via the supervisor path; Hermes pings Slack when a needs-you event fires; the scoped token cannot open a terminal.

### Phase 1c — needs-you push bridge (issue: PAN-2354)

A small subscriber (inside the dashboard server, reusing the event store subscription — not a separate daemon) filters needs-you event types → POSTs to configured ntfy topic(s). Config block `push: { provider: 'ntfy', url, topic, events: [...] }`. Web Push provider slot reserved for Phase 2. Omnara rule: needs-you only, batched, with deep links to `deck.<domain>` routes.
**Acceptance:** AUQ fired while operator is out → phone notification ≤10s with a link that opens the answering surface.

### Phase 2 — mobile PWA (issue: PAN-2355)

Same React codebase; mobile-first routes (`/m/…` or responsive redesign of existing routes — decide at plan time with an interactive mockup per operator preference): Needs-You feed (home), conversation view (JSONL message stream + composer → `deliverAgentMessage`), pipeline board, read-mostly terminal. PWA manifest + service worker + Web Push subscription (server keeps VAPID keys; iOS requires home-screen install). Expo/native wrapper explicitly deferred until PWA push reliability proves insufficient.
**Acceptance:** installable on iOS/Android; Web Push arrives with app closed (Android) / installed-PWA (iOS); AUQ answerable in ≤3 taps from notification.

### Phase 3 — relay service (issue: PAN-2356; product phase, build when multi-machine/multi-user demand is real)

Outbound-only daemon connection from each Overdeck instance to a small relay (Fly shared-cpu-1x ~$2/mo, or Cloudflare Durable Objects + WebSocket hibernation ~$5/mo — decide at plan time); GitHub OAuth at the relay; one logical room per home instance; content privacy via Nabu-Casa-style TLS passthrough (browser-first) with Happy-style QR-paired E2E as the native-app upgrade; relay hosts push origin (Web Push/APNs/FCM) and becomes the multi-tenant front door. Cloudflare Tunnel remains the operator's personal path; the relay is the *product's* path.

### Phase 4 — Shared Sessions v0 (existing issue [PAN-658](https://github.com/eltmon/overdeck/issues/658))

Keep the locked design (GitHub identity, lobby/admit/kick/revoke/block, controller handoff, draft-suggestion flow, versioned wire format). Transport change per FR-10: v0 rooms over the Phase 3 relay (plain WSS), taking the issue's own "dumb WS relay as phase 0" suggestion; WebRTC + TURN deferred to a bandwidth/latency optimization issue. Identity and rendezvous come from Phase 3 instead of being built bespoke.

## Intersecting repo rules (restated for executors)

- Dashboard server runs Node 22 dist only; never Bun; `npm run build` before restart; never hot-patch a boot-path change onto the live server (throwaway boot-test + `pan restart --health-timeout 120`).
- No `execSync` in server-reachable code; async tmux primitives only (`sendKeysAsync`, load-buffer/paste-buffer pattern).
- Retry/backoff/delay tests use `vi.useFakeTimers()` — heartbeat/reconnect tests included.
- Two-doors tenet: new reads extend resolvers, new writes extend the record writer; external routes must not touch stores directly.
- Never hardcode a model fallback; never speculatively send destructive HTTP requests; JSONL session files are sacred.
- Work agents run through `pan` (`pan start`/`pan swarm`/`pan plan`); specs land in `.pan/specs/` on main via the pipeline, drafts in `.pan/drafts/` (the `overdeck-state` branch is archived since the Cut).

## 2026-09-28 pricing decision

Operator-approved. Not yet available.

- **Self-hosted (open source):** $0 forever, unlimited on your own backend, all of Session Vault
  Phase A ([PAN-2609](https://github.com/eltmon/overdeck/issues/2609)). Self-hosting, federation
  (PAN-3762) and SSH hosts (PAN-3863) have no feature gate.
- **Vault Free (hosted):** $0, 1 GB stored, 2 machines, end-to-end encrypted.
- **Anywhere:** $96/yr (shown as $8/mo) or $10 month-to-month: 100 GB hosted vault, unlimited
  machines, relay (PAN-2356) and push (PAN-2354) as they ship. Hosted compute
  ([PAN-4298](https://github.com/eltmon/overdeck/issues/4298)) is billed separately by usage.
- **Founding price:** $60/yr, annual only, locked while subscribed; first 500 subscribers or
  until the relay ships, whichever comes first.
- **Storage add-on:** +$3/mo or +$30/yr per +100 GB. **Team:** not at launch.
- **Payment provider:** Creem as merchant of record (3.9% + $0.40 per charge; payouts at the
  higher of $7 or 1%). This replaces the Stripe assumption in PAN-4294.

The cost basis, fees and margins are in [PAN-2609](https://github.com/eltmon/overdeck/blob/main/.pan/drafts/pan-2609.md)
"Phase B pricing (decided 2026-09-28)". The Phase 3 relay cost envelope (NFR-4) is unchanged;
it is the operator's infrastructure cost, not a price. Public write-up for review:
[PR #4309](https://github.com/eltmon/overdeck/pull/4309).
