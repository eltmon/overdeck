## The goal in one scenario

You are mid-conversation at your desktop when you have to take the dog to the vet. You grab the laptop. In the waiting room you open Overdeck on the laptop.

The desktop's conversations are in your sidebar next to the laptop's own. Each one carries a "desk" machine chip, and its title bar is a lighter shade than a local conversation's. You open the conversation you left. It is still running on the desktop, and you read it live and reply: you are **remote-controlling** it.

Later the desktop needs to go offline, so you click **Pull here**. The desktop finishes or stops the current turn and hands the conversation over, including its uncommitted code changes. From then on the laptop runs it, and the desktop shows it as "Continued on laptop", read-only. At home you push it back the same way. A conversation runs on exactly one machine at a time.

All traffic between the two machines is end-to-end encrypted on every route: LAN, Tailscale, SSH and the overdeck.ai relay. The relay passes bytes it cannot read.

The same fleet includes Fly.io VMs. You can start a conversation "on Fly" or let a gauntlet loop place its heavy critic lanes there, and they appear as one more machine with live conversations.

## Glossary

- **Machine:** one running Overdeck server (`pan up`, `pan serve` or the desktop app) with its own `OVERDECK_HOME`. A machine's identity is its **environment id**, a UUID created once in `${OVERDECK_HOME}/environment-id.json` by `ensureEnvironmentIdentity()` (`src/lib/environment-identity.ts`), with a label that defaults to the hostname. "Environment" (the code's word) and "machine" (the UI's word) are the same thing.
- **Machine key:** a long-term X25519 key pair created with the environment id and stored in `${OVERDECK_HOME}/machine-key` (0600). Its public half is published in the descriptor and pinned by every linked machine at pairing.
- **Descriptor:** the public answer of `GET /api/environment` (`buildEnvironmentDescriptor()`, `src/dashboard/server/routes/environment.ts`): environment id, label, OS, server version, `protocolVersion` (`ENVIRONMENT_PROTOCOL_VERSION = 1`, `packages/contracts/src/environment.ts:12`), capability flags and, new here, the machine key's public half. It needs no credential.
- **Machine link:** what lets one machine's server act on another's. A link holds a scoped credential, the other machine's pinned public key and a list of routes. This plan calls the machine that holds the link the **linking machine** and the other the **linked machine**. A link is one-directional; **Link both ways** creates two links in one action.
- **Secure channel:** the end-to-end encrypted byte stream between two linked machines. It is a Noise protocol session keyed by the two machine keys, carried over any route. Ordinary HTTP and WebSocket requests run inside it, so nothing between the two machines (a LAN, Tailscale, an SSH hop, the relay, Cloudflare) sees plaintext.
- **Route:** one way to reach a linked machine: `lan`, `tailnet`, `ssh` (a forwarded loopback port) or `relay`. A link uses the first route that answers.
- **Owner machine:** the one machine whose harness runs a conversation and whose disk holds its live transcript. Ownership changes only through a pull or a vault Continue here.
- **Remote control:** using a conversation on its owner machine from another machine through a link. Everything still runs on the owner.
- **Pull:** making this machine the owner of a conversation. The old owner stops its harness session and becomes read-only for that conversation.
- **Saved copy:** the Session Vault record of a conversation (`SessionRecord`, `src/lib/vault/format.ts:149`). It is encrypted and versioned, and readable when the owner is off. Today it appears as a `vault-<vaultId>` row with `origin = 'vault'`.
- **Relay:** an overdeck.ai service that connects two machines when neither can reach the other directly. In this plan it is a **blind pipe**. Both machines dial out to it, and it forwards secure-channel bytes between them without being able to read them.
- **Operator-level** vs **agent-fenced:** the two access levels a link can carry (FR-4).

## What exists today (verified 2026-10-29 on `origin/main` `990c96ddeac`)

**Shipped and reused by this plan:**

- **Pairing:** `pan pair` (`src/cli/commands/pair.ts`) issues a one-time `odp_` credential (10 minutes, single use, in memory). `POST /api/pairing/exchange` (`src/dashboard/server/routes/pairing.ts`) trades it for a revocable `odk_` device token. With `delivery: 'bearer'` the token returns in the response body (line 110). Every device gets `scopes: ['admin']` today.

Every `/ws/*` except `/ws/terminal` (`operate`) needs `admin`.
- **Security plumbing:** the remote request gate (`remote-request-gate.ts`), WebSocket auth (`ws-auth.ts`), revoke closing live sockets (`device-connections.ts`), and Settings → Anywhere (pair dialog, Devices panel, trusted addresses).
- **Session Vault Phase A** (`src/lib/vault/`):

  - It shows other machines' conversations as read-only `vault-<id>` rows (`upsertVaultBrowseRow`, `src/lib/overdeck/conversation-vault-rows.ts`).
  - It has **Continue here** (`services/vault-continue.ts`; the project is matched by git origin through `findProjectForGitOrigin`, `src/lib/projects/origin-match.ts:13`; adoption is a compare-and-swap on the record ref, so only one machine can win) and **Hand off now** (`vault-handoff.ts`).
- **Conversations table:** `conversations` in `overdeck.db` has `origin TEXT DEFAULT 'local'` and `vault_owner_label` (`src/lib/overdeck/infra.ts:140-141`). It has no owner-machine column.
- **Conversation title bar:** `ConversationPanel.tsx:694` renders `styles.conversationHeaderShell`, styled at `command-deck.module.css:3218` with `background: var(--card)`.
- **Fly.io remote agents** (`src/lib/remote/`): **work agents only, Claude Code only**. `spawnRemoteAgentWithoutConsentClaim` hard-codes `harness: 'claude-code'` and the work role. Results return as a pushed branch through a manual `pan admin remote reap`. They have not been verified live since the Cut, which deleted auto-reap, the ephemeral-VM heartbeat and the credential refresh.
- **Gauntlet lanes** (`src/lib/lanes/`, `pan lane`):
  - Lanes are conversations in their own worktrees.
  - A builder reports `done` only after its branch is pushed.
  - A critic checks out the builder's reported head.
  - Launches are refused under CPU pressure (`assessCpuPressure`, `src/lib/lanes/launch.ts:327`).
- **Hosted services, code only:** `services/account` (GitHub sign-in, device flow, invite allowlist) and `services/share` (Shared Sessions rendezvous over WebRTC). Neither is deployed.

**Known blockers:**
- [PAN-4628](https://github.com/eltmon/overdeck/issues/4628): `pan pair` fails on every `npx @overdeck/core` machine.
- [PAN-4299](https://github.com/eltmon/overdeck/issues/4299): Traefik publishes 80/443/8080 on all interfaces, so a LAN client can forge `Host` and mint a root session.
- `dashboard.require_token_mint` defaults to `false`. Behind Tailscale Serve, that lets every remote visitor auto-mint the root session.

## What t3code does, and what this plan takes from it

t3code runs a full server on every machine. Each client (desktop, web, mobile) holds a catalog of machines, each with ordered routes, and connects to each machine directly from the client. The sidebar merges all machines, grouped by git repository, with a machine icon on rows from other machines. Offline machines' threads stay listed from a client cache, with an "<machine> is offline" banner. Threads never move between machines. Machines link to each other's MCP endpoint to delegate tasks. The relay is a broker on Cloudflare that provisions one Cloudflare Tunnel per machine. Cloudflare's edge terminates TLS on those tunnels, so app traffic is readable inside Cloudflare's network.

**Taken:** the descriptor check before any credential; ordered routes with direct routes first and the relay last; learned LAN and Tailscale routes; the 60 s better-route check; the merged sidebar grouped by repository; machine chips; offline rows kept from cache; delegation matched by git repository with back-off while the target sleeps; SSH launch that stops only servers it started; protocol and capability gating; "add this project to another machine" with `.env` copy; freeze-vs-network diagnosis.

**Done differently:**
1. **Federation runs server to server**, through each machine's own Overdeck server, not from the client (D-1).
2. **Every byte between machines is end-to-end encrypted** by the machines themselves, so no route, including the relay, is trusted (D-2). t3code relies on TLS that Cloudflare terminates.
3. **Conversations move** (Pull here), and t3code's cannot.
4. **Agent-originated calls are always fenced**, even on an operator-level link.
5. **The relay URL is a runtime setting.**

## Requirements

### Functional

- **FR-1 Link machines.** `pan machines link <pairing-url>` and Settings → Anywhere → Machines → **Link a machine** take a pairing link from the other machine.
  - The pairing handshake runs inside a secure channel whose Noise handshake mixes in the one-time pairing code as a pre-shared key. An attacker on the route who lacks the code cannot pair in the middle.
  - Each side then pins the other's machine key and stores a `machine`-kind token for the other.
  - **Link both ways** creates both directions in one action.
  - Either side can revoke a link, and a revoke closes live channels within 5 s.
- **FR-2 Routes.** Each link keeps an ordered route list.
  - **Sources:** the pairing URL, **Add route**, and addresses the linked machine advertises in its descriptor (`lan`, `tailnet`, Tailscale Serve HTTPS).
  - **Ranking:** `lan < tailnet < ssh < relay`.
  - **Identity check:** a channel is opened only to a route whose handshake proves the pinned machine key. No credential is ever sent before that proof.
- **FR-3 Link supervisor.** For each link, the server keeps a secure channel open on the best answering route.
  - **Probing:** routes are probed in parallel with a 2.5 s timeout.
  - **Reconnect:** back-off starts at 1 s and doubles to 300 s, with jitter.
  - **Better routes:** earlier routes are re-checked every 60 s.
  - **States:** `online`, `connecting`, `offline`, `unsupported` (protocol mismatch) or `revoked`.
  - **Bound:** no user-facing request waits more than 2.5 s on an unreachable machine.
- **FR-4 Access levels.** A link is **operator-level** (the default between your own machines; the pairing screen says so) or **agent-fenced**.
  - **Stamping:** the linking server stamps every forwarded request with its actor (`operator` or `agent:<id>`) and the agent's permission ceiling. The linked server trusts the stamp because the link is the trust boundary, but a stamp can only narrow what the link allows, never widen it. A request with no stamp counts as `agent`.
  - **Fencing:** agent requests may change only conversations that link started. On an agent-fenced link, operator requests are fenced the same way.
  - **Limits on every link:** no link can pair devices, mint tokens, change settings or use the linked machine's own links (no chained hops).
- **FR-5 Shared conversation list.** Once linked, the linking machine lists every conversation of the linked machine: native session id, title, project, git origin, harness, model, status, last activity, issue link and owner machine. This is on by default (D-4). The linked machine can stop sharing (Settings → Anywhere → Machines → **Share my conversations**), and its rows disappear on the next sync. Content is fetched only when a conversation is opened.
- **FR-6 One row per conversation.** A conversation appears once on a machine, keyed by (owner environment id, native session id). The row reads live from the owner when it is online, and from the saved copy when it is offline and a saved copy exists. A local conversation, a linked conversation and a vault copy of the same session never show as two rows.
- **FR-7 Remote control.** Opening a linked conversation streams its transcript live. You can send messages, answer AskUserQuestion prompts, approve permission requests, stop, abort, switch model and open its terminal. Every action runs on the owner. The URL names the owner: `/conv/@<environmentId>/<name>`. Local `/conv/<rowid>` URLs keep working.
- **FR-8 Pull here.** **Pull here** on a linked conversation (and `pan conv pull <conv>`) makes this machine the owner. The steps run in this order:
  1. **Ask to release.** This machine asks the owner to release the conversation. If a turn is running, the dialog offers **Wait for this turn** or **Stop it now**.
  2. **Release.** The owner settles the conversation, including a WIP snapshot of uncommitted and unpushed code. It stops its harness session and marks the conversation **released to <this machine>**. From then on it refuses new turns for that conversation.
  3. **Transfer.** The settled record and WIP snapshot travel through the secure channel. No vault backend is needed when both machines are online.
  4. **Adopt.** This machine adopts the record through the existing Continue here path (`services/vault-continue.ts`). It resolves the project checkout by git origin, offers a clone when the project is missing, applies the WIP snapshot and resumes the harness session.
  5. **Finish.** The old owner shows the conversation as "Continued on <this machine>", read-only.

  If adoption fails, the release is undone and the old owner resumes. A conversation is never run by two machines at once (D-8). When the old owner is offline, Pull here falls back to the vault: it adopts the latest saved copy, through a compare-and-swap so only one machine wins.
- **FR-9 Machine-aware UI.** Rows from another machine carry a machine chip. The title bar has four states (D-6). An offline owner shows a banner, "<label> is offline (last seen <time>)", with **Reconnect**, **Read saved copy** and **Continue here**, each shown only when it applies. **Hide this machine** removes its rows without unlinking.
- **FR-10 Start anything on any machine.** The new-conversation dialog (`components/newConversation/NewConversationDialog.tsx`) gains a **Machine** field, which defaults to this machine and includes **Fly (new VM)**. The CLI gains:
  - `pan start <issue> --machine <label|fly>`;
  - `pan worker run --machine <label|fly>`;
  - `pan lane start --machine <label|auto|fly>` ([PAN-4638](https://github.com/eltmon/overdeck/issues/4638)).

  Conversations, work agents, workers and lanes can all run on any machine, including Fly.
- **FR-11 Delegation with a report back.** Work an agent starts on another machine is followed until it ends, and its report or last reply returns to the parent the way a local worker's report does.
  - **Project match:** by git origin. If nothing matches, the error names **Add this project to <machine>**.
  - **Offline target:** if the target goes offline, the follower retries with back-off up to 5 minutes and resumes after a restart.
  - **Stop:** stopping the parent stops the remote task.
- **FR-12 Projects across machines.** The sidebar groups the same repository across machines by git origin; the setting **Combine matching repositories across machines** is on by default. **Add this project to <machine>** clones the repository there through the project-creation core (`src/lib/projects/create.ts`, `create-perform.ts`). It also copies the git-ignored files you select (`.env`, `.envrc` and `.dev.vars` preselected, at most 1 MiB each) through the secure channels.
- **FR-13 Fleet awareness.** Needs-You, search and "which machine is working on PAN-<n>" cover all online linked machines, with each result labelled by machine.
- **FR-14 Reach without Tailscale.** A machine signed in to an overdeck.ai account can turn on **Reach from anywhere**. It keeps one outbound WebSocket to the relay, and every linked machine of the same account gains a `relay` route to it. Secure-channel bytes pass through the relay unchanged (D-3).
- **FR-15 Push to a phone.** Needs-you events (approval, question, agent finished or failed) reach a phone as Web Push. The machine sends them directly to the browser's push service with its own VAPID keys. Each payload is encrypted to the phone's subscription key (RFC 8291), so neither the push service nor overdeck.ai can read it. A self-hosted ntfy topic is an optional second provider, carrying titles only when configured.
- **FR-16 Phone.** The phone installs the dashboard of one machine as a PWA over an HTTPS route (Tailscale Serve), and sees the fleet through that machine's links.
- **FR-17 SSH machines.** **Add an SSH machine** (and `pan machines add-ssh <host>`) has this machine's server open an SSH session to the host. It starts or adopts `pan up` there, forwards a loopback port, pairs over it, and adds an `ssh` route. It stops only a server it started itself.
- **FR-18 Fly VMs are machines.** A Fly VM runs an Overdeck server (`pan serve`) and is linked at spawn. Conversations, work agents, workers and gauntlet lanes run there with any supported harness: Claude Code at once, and Codex through [PAN-4296](https://github.com/eltmon/overdeck/issues/4296). They are ordinary linked conversations with live transcripts, terminals, remote control and Pull here. A run-level cap (`remote.max_concurrent_agents`, plus a per-gauntlet-run `gauntlet.fly.max_vms`) bounds spend.

### Non-functional

- **NFR-1 No plaintext between machines.** Every byte between two machines travels inside a secure channel, whatever the route. A route that cannot carry a secure channel is not offered.
- **NFR-2 No root credential leaves a machine.** Links, devices and the relay never hold the internal token or a root session.
- **NFR-3 Owner is authority.** A linked conversation's state is whatever the owner says. The linking machine keeps only a read cache (D-5) and never writes status for another machine's conversation.
- **NFR-4 One runner per conversation.** At most one machine runs a conversation's harness at any time, enforced by release-before-adopt (FR-8) and by the vault compare-and-swap.
- **NFR-5 Bounded idle traffic.** An idle link costs at most one heartbeat every 15 s plus deltas, with no full-list polling.
- **NFR-6 Compatibility.** Every link checks `protocolVersion` and capability flags. A mismatched machine shows as `unsupported` with the exact `pan` version to install, and is never retried in a loop.
- **NFR-7 Async only.** Link, channel, route, SSH and proxy code reachable from the dashboard server uses async I/O. No `execSync`, and no new `*Sync` tmux calls.
- **NFR-8 Self-hosting has no feature gate.** Everything except the hosted relay and the hosted vault works without an overdeck.ai account.

## Decisions

- **D-1 Federation runs server to server.**
  - **What "client to server" would have meant** (t3code's way): the laptop's browser page connects directly to the desktop's Overdeck server and to every other machine. The page keeps the list of machines and their credentials, and it decrypts and caches everything itself.
  - **What this plan does instead:** the laptop's browser talks only to the laptop's own Overdeck server, as today. That server holds the links and talks to the desktop's server over the secure channel.
  - **Why:**
    1. To **pull** a conversation, the laptop must run its own Overdeck server anyway, because that is what runs the harness. So the laptop always has a server to hold the links.
    2. End-to-end encryption needs long-term keys on both ends. A server can hold a machine key in a 0600 file. A browser page would have to keep keys in browser storage and load its code from whichever machine it is talking to.
    3. The frontend is same-origin by construction (`resolveRpcUrl` builds from `window.location`; about 400 `fetch('/api/…')` calls are relative; CORS exists only on the session mint; cookies are `SameSite=Strict`). Client-side federation would mean rewriting that transport.
    4. Delegation and gauntlet lanes are server-to-server calls in any design.
  - **Cost:** a phone opens one machine's dashboard and sees the fleet through that machine (FR-16).
- **D-2 Secure channel.**
  - **Protocol:** a Noise protocol handshake (`Noise_IK` once keys are pinned; `Noise_XXpsk` with the pairing code during pairing) over X25519, ChaCha20-Poly1305 and BLAKE2/SHA-256. All three primitives are in Node's built-in `crypto`. The implementation uses a vetted Noise library chosen in W-SEC1, never hand-rolled framing on top of raw primitives.
  - **Transport:** the channel is a byte stream. The receiving end hands each decrypted stream to its existing HTTP server as a connection (`server.emit('connection', stream)`), so every existing route, the `/ws/rpc` event stream and the `/ws/terminal` PTY stream work across a link unchanged. The linking end gives its HTTP and WebSocket clients a `createConnection` that returns a channel stream.
  - **Routes:** each route carries the channel the same way: raw TCP on `lan`/`tailnet`, the forwarded port on `ssh`, and binary WebSocket frames through the relay.
- **D-3 The relay is a blind pipe.**
  - **Where:** a Cloudflare Worker at `relay.overdeck.ai`, with one Durable Object per machine, following the 2026-10-02 decision to run all overdeck.ai services on Cloudflare.
  - **How:** a machine with **Reach from anywhere** keeps one outbound WebSocket to its Durable Object, authenticated with its `services/account` device token. A linking machine of the same account opens a connection request. The Durable Object asks the listening machine to open a matching WebSocket and then forwards binary frames between the two.
  - **What it sees:** account and machine ids, connection times and byte counts. It never sees content, because the frames are secure-channel ciphertext.
  - **No tunnels:** there is no Cloudflare Tunnel and no `cloudflared` binary, so the tunnel reaper, recovery and per-machine tunnel caps that t3code needs do not exist here.
  - **Configuration:** the relay URL is the runtime setting `anywhere.relay_url`, defaulting to `https://relay.overdeck.ai`.
  - **Replaces:** both the July design (Fly host, its own OAuth, traffic readable in the relay) and revision 2's Cloudflare Tunnel design.
- **D-4 Sharing is on by default.** Linking your machines shares the conversation list both ways, and content is fetched live on open. Each machine has one switch to stop sharing. There is no per-conversation privacy flag in this release (OD-1).
- **D-5 Linked conversations live in a cache table, not in `conversations`.**
  - **Table:** `linked_conversations` in `overdeck.db`, keyed by (environment id, conversation name). It holds the FR-5 metadata, including the native session id that FR-6 deduplicates on, plus `cached_at` and the owner's `sequence`.
  - **Lifecycle:** it is rebuilt from the owner on every connect, pruned when the owner stops reporting a row, and written only from the owner's own answer.
  - **Why:** CLAUDE.md says "Overdeck stores no status it can derive" and "there are no placeholder rows". Rows in `conversations` drive liveness, costs, lanes and the PR sweep. A separate cache that the list API merges at read time keeps the owner authoritative and still lists offline machines.
- **D-6 Title bar states.** These are surface tones per the dashboard style guide (load `pan-style-guide` when implementing), never status colors. An interactive mockup is approved before implementation.

  | State | Title bar | Extra |
  |---|---|---|
  | Local | `var(--card)` (unchanged) | none |
  | Remote control, owner online | new token `--surface-remote`: `--card` mixed about 6% toward `--background`, in both themes | chip "on <label>" |
  | Owner offline, saved copy exists | `--surface-remote` plus muted foreground | offline banner with **Read saved copy** and **Continue here** |
  | Owner offline, no saved copy | `--surface-remote` plus muted foreground | offline banner with **Reconnect** |
  | Released to another machine (on the old owner) | `--surface-remote` plus muted foreground | "Continued on <label>" with **Open there** |
- **D-7 Owner machine is a column.** `conversations` gains `environment_id TEXT`, backfilled with this machine's id for local rows and with the record owner's id for vault rows, plus `released_to TEXT` (the environment id it was pulled to, or null).
- **D-8 Single runner through release-before-adopt.**
  - A pull is a two-step handoff: the owner releases first, then the target adopts.
  - While `released_to` is set, the old owner's conversation routes refuse new turns (409 `conversation-released`). `/resume` refuses too, unless the pull failed and was undone.
  - The vault compare-and-swap still guards the offline path.
  - There is no shared or simultaneous running, by the operator's decision of 2026-10-29.
- **D-9 Machine-link tokens are a new token kind.**
  - `AccessTokenKind` gains `'machine'`. A machine token carries `read:events`, `read:state`, `read:conversations`, `tell` and `operate`, never `admin`, and is accepted only inside a secure channel.
  - `route-scopes.ts` gains rows for:
    - the `/ws/rpc` conversation-message and domain-event subscriptions;
    - send, stop, abort and permission answers;
    - conversation, worker and lane spawn;
    - the release, transfer and settle routes for Pull here.
  - Pairing, token minting, settings and vault setup stay `admin`.
- **D-10 Routes are ranked direct first, the relay last.** This is t3code's ranking: `lan < tailnet < ssh < relay`. A route learned from a descriptor borrows its link and is dropped when no longer advertised.
- **D-11 Delegated work starts from the remote's checkout.** Work on another machine gets its own workspace branched from that machine's view of `origin`. Unpushed local commits are not visible there. If the parent has unpushed commits, the CLI says so and offers `--push-first`.
- **D-12 Fly VMs are machines.** The Fly image ships `pan` and runs `pan serve`. At spawn, the home machine creates a pairing code and passes it to the VM through the Fly Machines exec API, and the VM's server links back over a secure channel. Remote agents and conversations are then linked conversations, which dissolves [PAN-1775](https://github.com/eltmon/overdeck/issues/1775) and the invisible-transcript gap. Before that, restore the three loops the Cut deleted and stop copying the operator's private SSH key to VMs (W-FLY1).
- **D-13 SSH is run by the server.** The server that holds the link opens the SSH session, so SSH machines work from any browser. PAN-4404's design is kept: pinned version, `managed` vs `external` markers, stop only what you started, per-host lock, explicit version-mismatch error.
- **D-14 The desktop app connects to one machine.** [PAN-4402](https://github.com/eltmon/overdeck/issues/4402) is narrowed to letting the desktop app open a chosen machine's dashboard with no local server, storing that machine's device credential with Electron `safeStorage`.
- **D-15 Carried forward from revision 1 (D-7 as amended 2026-09-28).** Cloud components carry transport only. An overdeck.ai service may store encrypted, user-keyed data it cannot read, with the key held only on the user's devices. No pipeline, agent or issue state moves to the cloud. The relay (D-3) and the hosted vault depend on this.
- **D-16 Push needs no relay.** Web Push from the machine itself with RFC 8291 payload encryption (FR-15) replaces both the ntfy-only design ([PAN-2354](https://github.com/eltmon/overdeck/issues/2354)) and relay-delivered push. This is free for self-hosters. It changes the pricing page, which sells "relay and hosted push" (OD-3).

## Settled by the operator on 2026-10-29

- **Encryption:** no unencrypted traffic between machines, on any route. This is D-2 and D-3, and it replaces revision 2's OD-1.
- **Access:** remote control is the everyday mode. Operator-level links between your own machines are the default, which replaces revision 2's OD-3.
- **Pulling:** pulling makes the laptop the only runner, and simultaneous running is not supported (FR-8, D-8).
- **One release:** everything ships together in one release, with no phases.
- **Fly:** Fly VMs are machines that run conversations, not only work agents (D-12, FR-18). Gauntlet lanes spread across machines, including Fly ([PAN-4638](https://github.com/eltmon/overdeck/issues/4638)). This replaces revision 2's OD-5.

## Open decisions

- **OD-1 Per-conversation privacy.** *Recommendation:* none in this release. Linked machines see every conversation's metadata.
- **OD-2 Phone away from home without Tailscale.** In this plan the phone reaches a machine over Tailscale (FR-16). Reaching it through the relay with end-to-end encryption would need the phone's browser to run the secure channel itself: the PWA, installed at home from your own machine, would hold a key and speak Noise through the relay. *Recommendation:* include it only if the operator wants phone access without Tailscale in this release. It is the one piece where a browser holds keys.
- **OD-3 Pricing page.** With push free (D-16), the paid Anywhere plan is the relay plus the hosted vault. The founding price ends "when the relay ships", which now means this release. *Recommendation:* update `anywhere.mdx` in W-DOC to drop "hosted push", and decide whether to keep the founding offer open past this release.
- **OD-4 Docker on Fly.** Gauntlet critics often run a full stack with Docker Compose. Whether the `pan-workspace` Fly image can run Docker needs a live check (implementation checkpoint in W-FLY2). *Fallback:* machines advertise a `docker` capability in the descriptor, and `pan lane start --machine auto` places Docker-needing critics only on machines that have it.

## Threat model changes

- **A stolen laptop holds machine links.** It gets operator-level access to the desktop's conversations, but no admin: it cannot pair, mint tokens or change settings. Revoke it from the desktop's Machines list, and its channels close within 5 s.
- **A compromised linked machine** can drive conversations on the machines it links to, but cannot hop further, and its agents are fenced (FR-4).
- **An attacker on any route** (LAN, a hostile Wi-Fi, the relay, Cloudflare) sees only Noise ciphertext. They cannot pair in the middle without the one-time code, and cannot impersonate a machine without its key (D-2).
- **The relay operator** sees account and machine ids, connection times and byte counts. Push payloads are encrypted to the phone, and the hosted vault stays ciphertext (D-15).

## Intersecting repo rules (restated for executors)

- The dashboard server runs Node 22 dist only, never Bun or tsx. Run `npm run build` before a restart.
- No `execSync` in server-reachable code. Use async tmux primitives only.
- Tests of retry, back-off, heartbeat, reconnect or follow use `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()`.
- Agent state is written only after the terminal-backend session exists. There are no placeholder rows, so remote spawns write rows only after the owner confirms the session.
- A new HTTP route needs a row in `tests/unit/lib/overdeck/no-loss-matrix.ts` and in `src/dashboard/server/route-scopes.ts`.
- JSONL transcripts are never deleted or truncated. A pull copies the transcript and never removes the old owner's file. Never send a destructive HTTP request speculatively.
- New issue work goes through `pan start`. Planning artifacts live under `.pan/` in this repo.

## 2026-09-28 pricing decision (carried over unchanged; see OD-3)

Operator-approved. Not yet available.

- **Self-hosted (open source):** $0 forever, unlimited on your own backend, all of Session Vault
  Phase A ([PAN-2609](https://github.com/eltmon/overdeck/issues/2609)). Self-hosting, federation
  (PAN-3762) and SSH hosts (PAN-3863) have no feature gate.
- **Vault Free (hosted):** $0, 1 GB stored, 2 machines, end-to-end encrypted.
- **Anywhere:** $96/yr (shown as $8/mo) or $10 month-to-month: 100 GB hosted vault, unlimited
  machines, relay (PAN-2356) and push (PAN-2354) as they ship. Hosted compute
  ([PAN-4298](https://github.com/eltmon/overdeck/issues/4298)) is billed separately by usage.
- **Founding price:** $60/yr, annual only, locked while subscribed; first 500 subscribers or
  until the relay ships, whichever comes first.
- **Storage add-on:** +$3/mo or +$30/yr per +100 GB. **Team:** not at launch.
- **Payment provider:** Creem as merchant of record (3.9% + $0.40 per charge; payouts at the
  higher of $7 or 1%). This replaces the Stripe assumption in PAN-4294.
