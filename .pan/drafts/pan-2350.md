## The goal in one scenario

You are away from home with your laptop. Your desktop at home is on and has three projects open, with conversations and agents running. You open Overdeck on the laptop. The desktop's conversations are in your sidebar next to the laptop's own. Each one carries a small "desk" machine chip, and its title bar is a lighter shade than a local conversation's. You open one, read it live and reply, and the agent on the desktop gets your message. You start a new conversation and pick "on desk", because that is where the project and its Docker services live. You ask a laptop agent to hand a long test run to the desktop and report back. When you get home, you click **Move here** on a laptop conversation and continue it on the desktop at once.

If the desktop goes offline, its conversations stay listed and marked offline. If Session Vault is set up, you can still read the saved copy and **Continue here**. A Fly.io machine you started for an agent shows up the same way: as one more machine, with live conversations.

Everything in this scenario works over your LAN or Tailscale for free. The paid Anywhere plan adds reaching the desktop with no Tailscale (the relay), push notifications to your phone, and the hosted vault.

## Glossary

- **Machine:** one running Overdeck server (`pan up`, `pan serve` or the desktop app) with its own `OVERDECK_HOME`. A machine's identity is its **environment id**: a UUID created once in `${OVERDECK_HOME}/environment-id.json` by `ensureEnvironmentIdentity()` (`src/lib/environment-identity.ts`), with a label that defaults to the hostname. "Environment" (t3code's word, used in the code) and "machine" (used in the UI) mean the same thing.
- **Descriptor:** the public answer of `GET /api/environment` (`buildEnvironmentDescriptor()`, `src/dashboard/server/routes/environment.ts`): environment id, label, OS, server version, `protocolVersion` (`ENVIRONMENT_PROTOCOL_VERSION = 1`, `packages/contracts/src/environment.ts:12`) and capability flags. It needs no credential.
- **Machine link:** a credential that lets one machine's server act on another machine's server, with a list of routes to reach it. This plan calls the machine holding the credential the **linking machine** and the other one the **linked machine**. A link is one-directional. Linking both ways is one user action that creates two links.
- **Route:** one way to reach a linked machine: `lan`, `tailnet`, `ssh` (a forwarded loopback port) or `relay`. A link has an ordered list of routes and uses the first one that answers.
- **Owner machine:** the machine whose disk holds a conversation's transcript and whose harness runs it. Every conversation has exactly one owner at a time.
- **Linked conversation:** a conversation owned by a linked machine, as seen on the linking machine. The linking machine lists it from a cache and reads or sends to it live through the link.
- **Saved copy:** the Session Vault record of a conversation (`SessionRecord`, `src/lib/vault/format.ts:149`). It is encrypted, versioned, and readable when the owner machine is off. Today a saved copy appears as a `vault-<vaultId>` row with `origin = 'vault'`.
- **Reach, move, delegate:** the three ways to work across machines. *Reach* means using a conversation where it lives, which needs the owner online. *Move* means changing a conversation's owner through the vault (Continue here, Move here), which works with the old owner offline. *Delegate* means asking another machine to run a task and report back.
- **Relay:** an overdeck.ai service that lets a machine with no public address be reached without Tailscale. In this plan it is a **broker**. It sets up the connection and mints a one-time credential. Conversation traffic does not pass through the relay Worker.
- **Operator-level link** vs **agent-fenced:** the two access levels a machine link can carry (FR-4).

## What exists today (verified 2026-10-29 on `origin/main` `990c96ddeac`)

**Shipped and reused by this plan:**
- **Machine identity and descriptor:** `environment-id.json` and `GET /api/environment` (PAN-3762 server slice, PR #4417).
- **Pairing:** `pan pair` (`src/cli/commands/pair.ts`) issues a one-time `odp_` credential (10 minutes, single use, held in memory). `POST /api/pairing/exchange` (`src/dashboard/server/routes/pairing.ts`) trades it for a revocable `odk_` device token. With `delivery: 'bearer'` the token comes back in the response body (line 110). That is the hook a server-to-server link uses. Today every device gets `scopes: ['admin']`.
- **Tokens and scopes:** `src/lib/access-tokens.ts` has `ACCESS_TOKEN_SCOPES = ['read:events','read:state','read:conversations','tell','operate','admin']` (line 42) and `AccessTokenKind = 'device' | 'token'` (line 44). `src/dashboard/server/route-scopes.ts` maps routes to scopes, and any route not listed needs `admin`. **Every `/ws/*` except `/ws/terminal` (`operate`) needs `admin`**, so a scoped token cannot subscribe to live conversation events.
- **The remote request gate** (`remote-request-gate.ts`), WebSocket auth (`ws-auth.ts`), revoke closing live sockets (`device-connections.ts`), and Settings → Anywhere (pair dialog, Devices panel, trusted addresses in `~/.overdeck/trusted-origins.json`).
- **Session Vault Phase A** (`src/lib/vault/`, PAN-2609 and follow-ups). It settles a conversation 30 s after it goes quiet and syncs every 300 s through a git or directory backend. It shows other machines' conversations as read-only `vault-<id>` rows (`upsertVaultBrowseRow`, `src/lib/overdeck/conversation-vault-rows.ts`). It has **Continue here** (`services/vault-continue.ts`; the project is matched by git origin with `findProjectForGitOrigin`, `src/lib/projects/origin-match.ts:13`), **Hand off now** (`vault-handoff.ts`), and **Continue on another device** (PAN-4455).
- **Conversations:** the `conversations` table in `overdeck.db` has `origin TEXT DEFAULT 'local'` and `vault_owner_label` (`src/lib/overdeck/infra.ts:140-141`). It has **no owner-machine column**. `/conv/<id>` URLs use a per-machine SQLite rowid.
- **The conversation title bar:** `ConversationPanel.tsx:694` renders `styles.conversationHeaderShell`, styled at `command-deck.module.css:3218` with `background: var(--card)`. It does not look at `origin` today.
- **Fly.io remote work agents** (`src/lib/remote/`): Claude Code work agents only. They return results as a pushed branch through a manual `pan admin remote reap`. They have not been verified live since the Cut, which removed auto-reap, the ephemeral-VM heartbeat and the credential refresh.
- **Hosted services, code only:** `services/account` (GitHub sign-in, device flow, invite allowlist) and `services/share` (Shared Sessions rendezvous over WebRTC). Neither is deployed (no DNS), and nothing in `src/` calls them.

**Not built:** any way for one dashboard to show another machine's conversations; the frontend is same-origin only (`resolveRpcUrl`, `src/dashboard/frontend/src/lib/wsTransport.ts:27`). Also not built: advertised endpoints, SSH hosts, the relay, push off the LAN, the mobile PWA, cross-machine delegation, and the sign-in client.

**Known blockers in the reach path:**
- [PAN-4628](https://github.com/eltmon/overdeck/issues/4628): `pan pair` fails on every machine started with `npx @overdeck/core`.
- [PAN-4299](https://github.com/eltmon/overdeck/issues/4299): Traefik publishes 80/443/8080 on all interfaces, so a LAN client can forge `Host` and mint a root session.
- `dashboard.require_token_mint` defaults to `false`. Behind a local proxy such as Tailscale Serve, that lets every remote visitor auto-mint the root session.

## What t3code does, and what this plan takes from it

t3code runs a full server on every machine. Its clients (desktop, web, mobile) keep a catalog of machines, each with ordered routes, and connect to each machine directly. The sidebar merges all machines, grouped by git repository, and marks rows from other machines with a machine icon. An offline machine's threads stay listed from a client cache, with a composer banner "<machine> is offline" offering **Reconnect** and **Disconnect server**. Threads never move between machines. Instead, a machine can link to another machine's MCP endpoint (a "peer link") and delegate tasks there. Its relay is a broker on Cloudflare (Worker, Clerk, PlanetScale, one Cloudflare Tunnel per machine). It mints a one-time credential bound to the client's key, and app traffic then goes through the tunnel, not the relay Worker. Push notifications come from signed activity summaries sent through the relay.

**Taken:** the descriptor check before sending any credential; ordered routes with direct routes ranked first and the relay last; learned LAN and Tailscale routes; a 60 s check for a better route; the merged sidebar grouped by repository; machine chips; offline rows kept from cache; the relay as a broker; push from signed summaries; the webhook inbox; delegation matched by git repository with back-off while the target sleeps; SSH launch that stops only servers it started; protocol and capability gating; "add this project to another machine" with `.env` file copy; and the server reporting event-loop freezes so clients can say "froze", not "network".

**Done differently:**
1. **Federation runs server to server, not in the client** (D-1).
2. **Conversations can move** through Session Vault, which t3code cannot do.
3. **Agent-originated calls are always fenced**, even on a full-access link (FR-4). t3code leaves full-access links unfenced.
4. **The relay URL is a runtime setting**, so self-hosting the relay needs no rebuild.
5. **Self-hosters get push through ntfy**, so no feature needs the paid relay except reach without Tailscale.

## Requirements

### Functional

- **FR-1 Link machines.** `pan machines link <pairing-url>` and Settings → Anywhere → Machines → **Link a machine** take a pairing link from the other machine. They check its descriptor, exchange the code with `delivery: 'bearer'` for a `machine`-kind token, and store the link. **Link both ways** also issues a pairing code on this machine and sends it through the new link, so the other machine links back. The link is revocable from either side, and a revoke closes live sockets within 5 s.
- **FR-2 Routes.** Each link keeps an ordered route list. Routes come from the pairing URL, from **Add route**, and from addresses the linked machine advertises in its descriptor (`lan`, `tailnet`, and Tailscale Serve HTTPS when it answers the descriptor). Direct routes rank `lan < tailnet < ssh < relay`. A token is sent only to a route whose descriptor returns the link's environment id, and an HTTPS-paired token is never sent over plain HTTP outside the tailnet.
- **FR-3 Link supervisor.** For each link, the server keeps one connection on the best answering route. It probes routes in parallel (2.5 s timeout), reconnects with back-off (1 s, doubling to 300 s, with jitter), checks earlier routes every 60 s, and reports the state as `online`, `connecting`, `offline`, `unsupported` (protocol mismatch) or `revoked`. No user-facing request waits longer than 2.5 s on an unreachable machine.
- **FR-4 Access levels.** A link is **operator-level** (the default when you link two of your own machines; the pairing screen says so) or **agent-fenced**. On any link, a request that originates from an agent (delegation, `pan worker run --machine`) carries the agent's permission ceiling and may change only conversations that link started. The linking server stamps every forwarded request with its actor (`operator` or `agent:<id>`) and the agent's permission ceiling. The linked server trusts the stamp because the link credential is the trust boundary, but a stamp can only narrow what the link allows, never widen it. A request with no stamp is treated as `agent`. On an agent-fenced link, operator requests are fenced the same way. No link can pair devices, mint tokens, change settings or use the linked machine's own links (no chained hops).
- **FR-5 Shared conversation list.** Once linked, the linking machine lists every conversation of the linked machine: native session id, title, project, git origin, harness, model, status, last activity, and the issue link. This is on by default (D-3). The linked machine can switch sharing off for all linking machines (Settings → Anywhere → Machines → **Share my conversations**), and its rows then disappear on the next sync. Content is fetched only when a conversation is opened.
- **FR-6 One row per conversation.** A conversation appears once on a machine, keyed by (owner environment id, native session id). The row reads live from the owner when it is online, and from the saved copy when the owner is offline and a saved copy exists. A local conversation, a linked conversation and a vault browse copy of the same session never show as two rows.
- **FR-7 Open and use a linked conversation.** Opening one streams its transcript live, and you can send messages, answer AskUserQuestion prompts, stop, abort, switch model and open its terminal. Every action runs on the owner machine. The URL names the owner machine: `/conv/@<environmentId>/<name>`. Local `/conv/<rowid>` URLs keep working.
- **FR-8 Machine-aware UI.** Rows from another machine carry a machine chip with its label. The title bar has four states (D-6). An offline owner shows a banner, "<label> is offline (last seen <time>)", with **Reconnect**, **Read saved copy** (when one exists) and **Continue here** (when one exists). **Hide this machine** removes its rows without unlinking.
- **FR-9 Start work on another machine.** The new-conversation dialog (`components/newConversation/NewConversationDialog.tsx`) gains a **Machine** field, which defaults to this machine. `pan start <issue> --machine <label>` starts the issue's work agent on that machine, and `pan worker run --machine <label>` starts a worker there.
- **FR-10 Delegation with a report back.** A worker or conversation started on another machine by an agent is followed until it ends, and its report or last reply returns to the parent like a local worker's report. The target project is matched by git origin (`findProjectForGitOrigin`). With no match, the call fails and names the "Add this project to <machine>" action. If the target goes offline, the follower retries with back-off up to 5 minutes and resumes after a restart. Stopping the parent stops the remote task.
- **FR-11 Move here.** On a linked conversation whose owner is online, **Move here** asks the owner to settle now (the existing Hand off now path) and then syncs this machine at once. The conversation continues here, normally in under 30 s, through the existing Continue here flow, with no wait for the 300 s sync.
- **FR-12 Projects across machines.** The sidebar groups the same repository across machines by git origin. The setting **Combine matching repositories across machines** is on by default. **Add this project to <machine>** clones the repository there through the project-creation core (`src/lib/projects/create.ts` + `create-perform.ts`). It also copies the git-ignored files you select (`.env`, `.envrc`, `.dev.vars` preselected, at most 1 MiB each), relayed through this machine.
- **FR-13 Fleet awareness.** Needs-You, search and "which machine is working on PAN-<n>" cover all online linked machines, with each result labelled by machine.
- **FR-14 Reach without Tailscale (paid).** A machine signed in to an overdeck.ai account can turn on **Reach from anywhere**. The relay then adds a `relay` route that every linked machine and paired device of the same account can use.
- **FR-15 Push.** Needs-you events (approval, question, agent finished or failed) reach a phone through either of two providers: the relay (hosted, paid) or a self-hosted ntfy topic (free). Payloads carry the project title, conversation title and phase by default, and never prompt content unless configured.
- **FR-16 SSH machines.** **Add an SSH machine** (and `pan machines add-ssh <host>`) has this machine's server open an SSH session to the host. It starts or adopts `pan up` there, forwards a loopback port, pairs over it, and adds an `ssh` route. It stops only a server it started itself.
- **FR-17 Fly machines are machines.** A Fly.io VM started for an agent runs an Overdeck server and is linked automatically at spawn. Its agents are linked conversations with live transcripts and terminals.

### Non-functional

- **NFR-1 No root credential leaves a machine.** Links, devices and the relay never hold the internal token or a root session.
- **NFR-2 Owner is authority.** A linked conversation's state is whatever the owner machine says. The linking machine keeps only a read cache (D-2) and never writes status for another machine's conversation.
- **NFR-3 Bounded idle traffic.** An idle link costs at most one heartbeat every 15 s plus deltas. There is no full-list polling across a link.
- **NFR-4 Compatibility.** Every request across a link checks `protocolVersion` and capability flags. A mismatched machine shows as `unsupported` with the exact `pan` version to run, and is never retried in a loop.
- **NFR-5 Async only.** Link, route, SSH and proxy code reachable from the dashboard server uses async I/O. No `execSync`, and no new `*Sync` tmux calls.
- **NFR-6 Relay sees no conversation content.** The relay Worker handles identity, link records, connection handshakes, push summaries and held webhooks. No transcript, terminal or RPC traffic passes through the Worker. OD-1 covers the Cloudflare tunnel edge.
- **NFR-7 Self-hosting has no feature gate.** Everything except the hosted relay, hosted push and the hosted vault works without an overdeck.ai account (decided 2026-09-28; restated here).

## Decisions (made here, not left to executors)

- **D-1 Federation is server to server.** The browser talks only to the server it was loaded from, as today. That server holds the machine links, keeps the cache of linked conversations, and proxies reads, sends and terminals to the owner.
  - *Why:* the frontend is same-origin by construction: `resolveRpcUrl` builds from `window.location`, about 400 `fetch('/api/…')` calls are relative, CORS exists only on the session mint, and cookies are `SameSite=Strict`. Client-side federation would mean rewriting the transport, which PAN-4402 itself flagged as "verify first". The server already has the receiving pattern (vault browse rows) and the credential hook (`delivery: 'bearer'`). Delegation needs server-to-server calls anyway, and offline listing needs a cache that outlives a browser tab.
  - *Cost:* a device with no Overdeck server of its own (a phone, a borrowed browser) opens one machine's dashboard directly and sees whatever that machine can reach through its links. This is a deliberate limit. The phone work in Phase 3 does not reintroduce client federation.
- **D-2 Linked conversations live in a cache table, not in `conversations`.** A new `linked_conversations` table in `overdeck.db` is keyed by (environment id, conversation name). It holds the FR-5 metadata, including the native session id that FR-6 deduplicates on, plus `cached_at` and the owner's `sequence`. It is rebuilt from the owner on every connect and pruned when the owner stops reporting a row. It is never written from anything except the owner's own answer.
  - *Why:* CLAUDE.md says "Overdeck stores no status it can derive" and "there are no placeholder rows". Rows in `conversations` drive liveness, costs, lanes and the PR sweep, and a remote row there would invite local code to act on it. A separate cache that the list API merges at read time keeps the owner as the authority (NFR-2) and still lists offline machines. The vault's existing `vault-<id>` rows stay as they are: they represent a local copy that exists on this disk.
- **D-3 Sharing is on by default.** Linking your machines shares the conversation list both ways, and content is fetched live on open. Each machine has one switch to stop sharing. There is no per-conversation privacy flag in this epic (OD-2). The operator can reverse this default.
- **D-4 Owner machine is a column.** `conversations` gains `environment_id TEXT`, backfilled with this machine's id for local rows and with the record owner's id for vault browse rows. FR-6 deduplication keys on (`environment_id`, native session id).
- **D-5 Machine-link tokens are a new token kind.** `AccessTokenKind` gains `'machine'`. A machine token carries `read:events`, `read:state`, `read:conversations`, `tell` and `operate`, and never `admin`. `route-scopes.ts` gains rows for:
  - `/ws/rpc` conversation-message and domain-event subscriptions (`read:conversations`, `read:events`);
  - conversation send, stop and abort (`tell` / `operate`);
  - conversation and worker spawn (`operate`);
  - the vault settle and sync triggers (`operate`).

  Pairing, token minting, settings and vault setup stay `admin`.
- **D-6 Title bar states.** These are surface tones from the dashboard style guide (load the `pan-style-guide` skill when implementing), never status colors:

  | State | Title bar | Extra |
  |---|---|---|
  | Local | `var(--card)` (unchanged) | none |
  | Linked, owner online | new token `--surface-remote`: `--card` mixed about 6% toward `--background`, in both themes | machine chip "on <label>" |
  | Linked, owner offline, saved copy exists | `--surface-remote` plus the muted foreground | offline banner with **Read saved copy** and **Continue here** |
  | Linked, owner offline, no saved copy | `--surface-remote` plus the muted foreground | offline banner with **Reconnect**; the transcript area says it is unavailable until <label> is back |

  The machine-aware sidebar and title bar go through an interactive mockup before implementation (W1.7), per the operator's rule for UX redesigns.
- **D-7 Routes are ranked direct first, the relay last.** This copies t3code's ranking: `lan < tailnet < ssh < relay`. A route learned from a descriptor borrows the credential of the route it was learned over and is dropped when the machine stops advertising it.
- **D-8 The relay is a broker on Cloudflare.**
  - **Pieces:** a Worker plus D1 (or Durable Objects) at `relay.overdeck.ai`, using `services/account` for identity (no separate OAuth), and one Cloudflare Tunnel per machine for the data path. This follows the 2026-10-02 decision to run all overdeck.ai services on Cloudflare, and t3code's working design.
  - **Connecting:** the relay mints a one-time credential bound to the connecting client's key. The client redeems it directly with the machine for an ordinary machine-link or device token.
  - **Configuration:** the relay URL is a runtime setting (`anywhere.relay_url`), defaulting to `https://relay.overdeck.ai`.
  - **What this replaces:** the July design (Fly host, its own GitHub OAuth, the relay carrying traffic over WSS; `pan-2356.md` D-R1..D-R4).
- **D-9 Push has two providers.** One interface, `src/lib/push/`, with `relay` (hosted) and `ntfy` (self-hosted topic URL). It sends the same signed, minimized summaries. This replaces the ntfy-only design of PAN-2354 and gives PAN-2080 its push transport.
- **D-10 The phone is a client of one machine.** The phone opens one machine's dashboard over Tailscale Serve HTTPS or the relay, and installs it as a PWA. PAN-2355's `/m` surface and mockup gate stay. Its dependency on the Cloudflare Tunnel runbook (PAN-2352) is dropped: any HTTPS route works.
- **D-11 Delegated work starts from the remote.** A task delegated to another machine runs in that machine's checkout of the project. A work agent there gets its own workspace branched from the remote's view of `origin`. Unpushed local commits are not visible there. If the parent's branch has unpushed commits, the CLI says so and offers `--push-first`. It never copies a working tree silently.
- **D-12 Fly VMs become machines (resolves inventory gap G-F13).** The Fly image ships `pan` and runs `pan serve` headless. At spawn, the home machine mints a pairing credential for the VM and links to it. Remote agents are then linked conversations, which dissolves PAN-1775 ("Fly agents as session rows") and the invisible-transcript gap. Code still returns as a pushed branch. First, restore the three loops the Cut deleted and stop copying the operator's private SSH key to VMs (W5.0).
- **D-13 SSH is run by the server, not the desktop app.** Under D-1, the server that holds the link opens the SSH session. So SSH machines work from any browser, not only from Electron. PAN-4404's design (pinned version, `managed` vs `external` markers, stop only what you started, per-host lock, an explicit version-mismatch error) is kept and moved server-side.
- **D-15 Carried forward from revision 1 (D-7 as amended 2026-09-28).** Cloud components carry transport only. An overdeck.ai service may store encrypted, user-keyed data that it cannot read, with the key held only on the user's devices. No pipeline, agent or issue state moves to the cloud. The relay (D-8), push (D-9) and the hosted vault all depend on this.
- **D-14 The desktop app connects to one machine.** PAN-4402 is narrowed to letting the desktop app open a chosen machine's dashboard with no local server, and storing that machine's device credential with Electron `safeStorage`. Fleet behaviour comes from that machine's links.

## Open decisions for the operator

Each one has a recommendation, and the plan proceeds on the recommendation unless the operator changes it.

- **OD-1 Relay privacy.** With Cloudflare Tunnels, Cloudflare's edge terminates TLS for the tunnel hostname, so conversation traffic is in cleartext inside Cloudflare's network. t3code accepts this and does not discuss it. Revision 1's acceptance criterion "relay provably cannot read conversation plaintext" is **not** met by this design.
  - *Recommendation:* accept it for v1, and state it plainly on the Anywhere page ("traffic through the relay passes through Cloudflare; use Tailscale for end-to-end encryption").
  - *Later:* add end-to-end encryption between client and machine as a follow-up. A Durable Object WebSocket relay with a Noise handshake is the known shape.
- **OD-2 Per-conversation privacy.**
  - *Recommendation:* none in this epic. Revisit if the operator wants some conversations kept off other machines.
- **OD-3 Operator-level links by default between your own machines.**
  - *Recommendation:* yes, because without it the laptop cannot reply in a desktop conversation. Agent-originated calls stay fenced on every link (FR-4).
- **OD-4 Founding price.** The founding price ends "when the relay ships" (`anywhere.mdx`), and in this plan the relay is Phase 3.
  - *Recommendation:* keep that wording, and decide whether the relay's beta counts as "ships".
- **OD-5 Fly as machines (D-12).**
  - *Recommendation:* yes. The alternative keeps a second remote-agent model with its own rows, terminal path and reaping.

## Threat model changes

- **A stolen laptop holds a machine link.** It gets operator-level access to the desktop's conversations, but no admin: it cannot pair, mint tokens or change settings. Revoke it from the desktop's Machines list, and live sockets close within 5 s. The same is true of a paired browser today, so links add no new class of risk.
- **A compromised linked machine** can drive conversations on the machines it links to, but cannot hop further (FR-4). Its agents are fenced to the conversations they started.
- **A recycled LAN address** answering a saved route gets no credential, because of the descriptor check (FR-2).
- **The relay operator** (overdeck.ai) sees identity, link records, handshakes, push summaries and held webhooks. Cloudflare's edge sees tunnel traffic (OD-1). The hosted vault stays ciphertext only (D-15).

## Intersecting repo rules (restated for executors)

- The dashboard server runs Node 22 dist only, never Bun or tsx. Run `npm run build` before a restart.
- No `execSync` in server-reachable code. Use async tmux primitives only.
- Tests of retry, back-off, heartbeat or reconnect use `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()`. The link supervisor and delegation follower tests must follow this.
- Agent state is written only after the terminal-backend session exists. There are no placeholder rows, so remote spawns (W2.1, W5.1) write rows only after the owner confirms the session.
- A new HTTP route needs a row in `tests/unit/lib/overdeck/no-loss-matrix.ts` and in `src/dashboard/server/route-scopes.ts`.
- JSONL transcripts are never deleted or truncated. Never send a destructive HTTP request speculatively.
- New issue work goes through `pan start`. Planning artifacts live under `.pan/` in this repo.
