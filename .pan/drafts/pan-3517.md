## Glossary

- **Review convoy** — the four parallel sub-reviewers (`correctness`, `security`, `performance`, `requirements`) plus the **synthesis parent** (`agent-<issue>-review`) that runs a shared discovery pass, then synthesizes their reports.
- **Fork / forked session** — a copy of the parent's Claude Code session JSONL under a fresh session UUID, launched with `claude --resume <new-id>`, so the parent's discovery history replays as the reviewer's opening prefix. Machinery: `forkParentSessionForReviewer`, `src/lib/cloister/review-convoy.ts:400`.
- **Cache scope / `prompt_cache_key`** — OpenAI's prompt-cache routing hint. CLIProxy v7.2.113 derives it deterministically (uuid5) from `claude:<sessionID>:agent:<agentID>`, honoring the `X-Claude-Code-Session-Id` request header over payload `metadata.user_id` — **in its codex/OpenAI executor only** (identity prefix `cli-proxy-api:codex:claude-code`). Anthropic's cache is content-addressed and ignores keys entirely.
- **Cache cohort** — the set of sessions sharing one cache scope (parent + 4 forks + their resumes) so a prefix cached by one is readable by all.
- **SessionStart briefing** — the `<overdeck-memory-context>` standing memory briefing the dashboard composes per session id and the SessionStart hook emits as `additionalContext` (PAN-3286 FR-10). Server path: `handleMemorySessionStartBody`, `src/dashboard/server/routes/hooks.ts:180`.
- **Static preamble** — the Claude Code system prompt + tool definitions, ~20–23k tokens, byte-identical across same-toolset sessions; always the first cache-matching region.
- **Hit ratio** — for a fork's first own API request: `cache_read_input_tokens / (cache_read_input_tokens + input_tokens)`. The acceptance metric of this PRD.
- **Warm window** — the provider-side lifetime of a cached prefix (OpenAI ~5–10 min, Anthropic 5 min default). Forks fire seconds after discovery-ready, so fork first-requests are always inside it; resumes usually are not (out of scope here — see PAN-3518).

## Background and verified evidence

### The mechanism as built

1. `handleReviewDiscoveryReady` (`src/lib/cloister/review-convoy.ts:577`) launches the convoy with `forkFromParent: true`.
2. Per reviewer, fork gates (`review-convoy.ts:482-496`): fork mode on AND parent harness `=== 'claude-code'` AND reviewer model `===` parent model AND reviewer has no prior own session.
3. `forkParentSessionForReviewer` (`review-convoy.ts:400-416`) copies the parent JSONL via `reserveForkSession` + `copySessionForFork(..., { fullHistory: true })`.
4. The fork spawn exports the cache-scope header for non-Anthropic models (`review-convoy.ts:267-275`):
   ```ts
   forkScopeHeaderExport = `export ANTHROPIC_CUSTOM_HEADERS="X-Claude-Code-Session-Id: ${opts.forkParentSessionId}"`;
   ```
   passed as `extraEnvExports` in the spawn options (`review-convoy.ts:284`), and `reviewForkedFromParent: true` is persisted (`review-convoy.ts:292`).
5. **The resume path never re-exports the header.** `resumeAgent` rebuilds the launcher with `extraEnvExports: [harnessLaunch.pathExport]` only (`src/lib/agents/resume.ts:435`). A resumed fork silently switches back to its own session scope, leaving the cohort.

### What production shows (2026-08-02, all claude-code + GPT-via-cliproxy)

- 12 fork families (~46 forked first requests) since the header-fix commit `0da888cbcc`: dominant signature is `cache_read` ≈ 20–23k or 0 against inputs of 100–190k. Only the static preamble matches.
- **Decisive family (PAN-3427, parent session `6f7108cc`)**, run on a dashboard build verifiably containing the fix: fork launchers export `ANTHROPIC_CUSTOM_HEADERS="X-Claude-Code-Session-Id: 6f7108cc-…"` (matches `session.id` of the parent), parent reading 206k+ cached 50 s before forks fired, copied history byte-identical through 183 lines — forks still read only 19,968–22,016 of ~167k. Same key + warm scope + identical stored history ⟹ **byte drift inside the request, before the end of the replayed prefix**.
- **Drift suspect confirmed:** the fork's SessionStart hook composes a *fresh* briefing. The server claims briefings per session id (`claimSessionBriefing`, called from `composeBriefingForSessionStart`, `hooks.ts:264-288`); a fork's new UUID always wins the claim, and the fresh briefing differs from the parent's already-copied one (measured 18,972 vs 20,802 bytes). Claude Code places SessionStart `additionalContext` at the head of the message stream — the transcript shows the parent's briefing as its first user message — so a fresh head message breaks the exact-prefix match immediately after the static preamble. Secondary suspect: per-launch dynamic system-prompt sections (git-status snapshot). WI-5's capture distinguishes them if WI-2 doesn't fully close the gap.
- Within-session caching is healthy (requests 2+ of every session read 68k–224k cached). The loss is concentrated at session boundaries: ~4M uncached input tokens/day in fork first-requests fleet-wide, plus a similar amount in resume re-bills (PAN-3518).

### Root causes this PRD fixes

- **RC-1 (content drift):** SessionStart briefing is re-composed and re-injected for sessions whose history already contains a briefing — every fork copy, and every ordinary `--resume`. Per session id claim-keying (`hooks.ts:271`) makes forks always lose.
- **RC-2 (scope loss on resume):** the cache-scope header exists only on the fork's first spawn; resumes regenerate the launcher without it (`resume.ts:435`), so even a within-TTL resume leaves the cohort.

## Requirements

- **FR-1** — A session whose history already carries a SessionStart briefing MUST NOT receive a fresh one injected at launch. The rule is keyed on the Claude Code SessionStart `source` field: `source === 'resume'` suppresses briefing composition by default; `startup`/`clear`/`compact` are unaffected. Fork launches (which are `--resume` launches) are covered by the same rule — no fork-specific marker is needed.
- **FR-2** — The suppression MUST NOT skip transcript registration for memory observation polling — only briefing composition. The observations pipeline (`registerTranscriptForPolling`, `hooks.ts:245-253`) runs exactly as today for resumed sessions.
- **FR-3** — A forked reviewer's resumes MUST re-export `ANTHROPIC_CUSTOM_HEADERS="X-Claude-Code-Session-Id: <parent session id>"` whenever the resolved model's provider is not `anthropic` (same provider check as the fork spawn, `review-convoy.ts:270-274`), keeping the whole fork family in one cache cohort for its members' entire lifetime.
- **FR-4** — The suppression in FR-1 MUST be reversible via a single config knob, defaulting to the new behavior (suppress).
- **FR-5** — A mechanical measurement MUST exist that reports per-fork hit ratio for any convoy from local JSONL files alone, so this PRD's effect is verifiable without provider access.
- **FR-6** — A documented wire-capture runbook MUST exist for the case where FR-1+FR-3 land and FR-5 still shows < 80% hit ratio, so the residual drift source (e.g. dynamic system-prompt sections) is identifiable from actual request bytes.
- **NFR-1** — No change to the SessionStart hook script (`sync-sources/hooks/session-start-hook`) — suppression is server-side, so no `pan sync` redistribution is required and non-synced installs behave no worse than today.
- **NFR-2** — No DB schema migration. Runtime fork-scope state uses the existing agent-dir marker-file pattern (`reviewer-signaled`, `reviewer-launcher.pid` at `review-convoy.ts:179-180`).
- **NFR-3** — Anthropic-routed convoys are unaffected (they never receive the header — content-addressed cache needs no scope), and FR-1 improves their fork hit rate the same way (identical head bytes).
- **NFR-4** — Codex/pi/kimi harnesses are untouched; convoy cache-sharing remains claude-code-only by design (documented in WI-6).

## Decisions (made in this document — no judgment calls left to the executor)

- **D-1 — Suppression is server-side, keyed on `source === 'resume'`.** The hook already POSTs Claude Code's full SessionStart payload (which contains `source`) to `/api/memory/session/start`; the payload schema at `hooks.ts:69-73` simply doesn't retain `source` today. We add it and gate briefing composition on it. Rationale: one TS change with unit tests beats shell logic in a distributed hook; hook redistribution (NFR-1) is avoided. An ordinary resume's history always contains its launch briefing, so the freshness delta lost is small; the win is prefix stability for every resume fleet-wide, not just forks.
- **D-2 — Knob: `memory.sessionStartBriefingOnResume`, default `false`** (suppress). Parsed in `src/lib/memory/settings.ts` alongside `promptTimeInjectionEnabled` (accessor pattern at `isMemoryPromptTimeInjectionEnabled`, settings.ts:80), defaulted in `defaultMemorySettings()` (settings.ts:~94-105). Setting `true` restores today's behavior exactly.
- **D-3 — Fork scope persists as an agent-dir marker file, not a state field.** `~/.overdeck/agents/<reviewer-id>/fork-cache-scope` contains the parent session id, written at fork spawn, removed at any fresh non-fork spawn of that reviewer, read at resume-launcher build. Rejected alternative: a new `agents` table column (pattern: `runSchemaTopUp` at `src/lib/overdeck/infra.ts:199`) — heavier, and the value is only ever needed on the same machine at launcher-build time. Marker files under the agent dir are already the established runtime-artifact pattern and are cleaned by the agent-dir deletion door for free.
- **D-4 — Header value stays the parent's session id**, not a synthetic convoy id. CLIProxy treats the header as an opaque scope string either way; using the parent's id keeps the parent (synthesis follow-ups included) inside the cohort with zero extra bookkeeping.
- **D-5 — Acceptance gate is the FR-5 script, not the wire capture.** ≥ 80% hit ratio on the first own request of each fork in a fresh convoy family is success. The capture (FR-6) runs only if the gate fails, and its outcome decides whether a CLIProxy canonicalization follow-up issue is filed (decision point, with the fallback being "ship FR-1+FR-3, file the follow-up with capture evidence attached").
- **D-6 — Provider check duplicated at resume, not persisted.** `getProviderForModelSync(model).name !== 'anthropic'` is re-evaluated at resume-launcher build with the resume's resolved model (same call as `review-convoy.ts:270-271`). Persisting the boolean would go stale on a model routing change; re-evaluating is one sync call.

### WI-3 (FR-5, D-5) — `scripts/measure-convoy-cache.ts`: mechanical fork hit-ratio report

**Files:**
- `scripts/measure-convoy-cache.ts` (new)
- `tests/scripts/measure-convoy-cache.test.ts` (new; `tests/scripts/` already exists — see `tests/scripts/session-start-hook.test.ts`)

**Behavior:** run with `bun scripts/measure-convoy-cache.ts [--since <ISO date>] [--projects-dir <glob override>]`. Default scan: `~/.claude/projects/-*workspaces-*/*.jsonl` modified since `--since` (default 48 h ago).

Algorithm (this is exactly the procedure used in the 2026-08-02 investigation; implement it as written):
1. Group session files by the `timestamp` of their first parseable entry. Groups of ≥ 2 are **fork families**.
2. In each family, the largest file is the **parent**. For each other member (**fork**): find the last index `k` where `forkLines[k] === parentLines[k]` (byte comparison of raw lines). Lines `k+1..` are the fork's **own entries**.
3. In the fork's own entries, find the first entry whose `message.usage` has nonzero `input_tokens` or `cache_read_input_tokens` — the fork's **first own request**. Hit ratio = `cache_read / (cache_read + input)`.
4. Print per family: parent session prefix, copied-line count, per-fork session prefix + first-own `input`/`cache_read`/hit-ratio. Then an aggregate line: families found, forks measured, mean hit ratio, count below 80%.

Export the pure helpers (`findDivergencePoint(parentLines, forkLines)`, `firstOwnUsage(lines)`) for tests. Tests use small fixture JSONL strings (no real `~/.claude` access): divergence on identical prefix + appended entries; first-usage skipping metadata entries; hit-ratio arithmetic.

### WI-4 (D-5) — Controlled verification convoy and acceptance gate

**Procedure (run by the implementing agent after WI-1..WI-3 land and the dashboard is rebuilt + restarted):**
1. Pick an issue with an open PR and a completed prior review (any recent convoy issue works; PAN-3410 or PAN-3427 are suitable).
2. Trigger a fresh convoy cycle: `pan admin specialists discovery-ready review <ISSUE>` after clearing the reviewers' saved sessions (`pan review reset <ISSUE> --reviewers` — verify exact subcommand with `pan review --help`; the goal is fork-eligible reviewers with no own sessions).
3. Wait for all four reviewer reports (`.pan/review/<runId>/*.md` in the workspace).
4. Run `bun scripts/measure-convoy-cache.ts --since <fork time>` and record the hit ratios.
5. **Gate:** all four forks ≥ 80% on first own request ⇒ success, proceed to WI-6. Any fork < 80% ⇒ run WI-5's capture, attach findings to the issue, and file the CLIProxy canonicalization follow-up with the captured byte diff (this is the D-5 decision point — shipping WI-1..WI-3 is still correct; the follow-up is additive).

### WI-5 (FR-6) — Wire-capture runbook

**File:** `docs/REVIEW-CACHE-VERIFICATION.md` (new).

Contents: how to interpret `measure-convoy-cache.ts` output; the capture procedure when the gate fails —
1. CLIProxy serves plain HTTP on `127.0.0.1:8317` (launchers set `ANTHROPIC_BASE_URL="http://127.0.0.1:8317"`), so no TLS interception is needed between Claude Code and the proxy.
2. Run the real CLIProxy on port 8318 (edit the port in `~/.overdeck/cliproxy/config.yaml`; note `src/lib/cliproxy.ts` regenerates this config — re-apply after any `pan restart --cliproxy`).
3. Run a logging shim on 8317 that forwards to 8318 and dumps request bodies to disk (a ~40-line `node`/`bun` HTTP proxy; include a ready-to-paste implementation in the runbook).
4. Diff a fork's first request body against the parent's last pre-fork request body; the first differing byte region is the residual drift source (expected candidates: the system prompt's dynamic git-status block, or a head-placed SessionStart message that escaped WI-1).
5. Restore port 8317 and restart cliproxy when done.
