# PAN-4933 — Codex agents get the `overdeck` MCP server (epic PAN-4927, item W-INJ2)

**Status:** planned · **Revision:** 1 (2026-11-04) · **Author:** Claude Opus 5.5 (planning agent, `pan plan --auto`)
**Issue:** [PAN-4933](https://github.com/eltmon/overdeck/issues/4933) · **Epic:** [PAN-4927](https://github.com/eltmon/overdeck/issues/4927), PRD `.pan/drafts/pan-4927.md`, section "W-INJ2 — Codex: `[mcp_servers.overdeck]`"
**Depends on:** W-INJ1 = [PAN-4932](https://github.com/eltmon/overdeck/issues/4932), merged to `main` as `b4b96c624b0` (PRD `.pan/drafts/PAN-4932.md`).
**Unblocks:** W-INJ4 (instructions blocks read the `overdeckMcp` capability this item flips for Codex).

**What this does.** Every Codex launch Overdeck makes on this host (work agents, role runs, planning sessions, recovery and message-fallback relaunches, and conversations) gets an `[mcp_servers.overdeck]` table in its per-agent `config.toml`. The table runs `pan mcp serve` with only the token-file path in its env, the same entry Claude Code agents already get from W-INJ1. It also sets `default_tools_approval_mode = "approve"`, because Codex otherwise blocks every call to an Overdeck tool (Fact 4).

---

## Glossary

- **Overdeck MCP server:** the tool module in `src/lib/mcp/`, served over stdio by `pan mcp serve`. Every tool calls a dashboard HTTP route with the caller's bearer token.
- **Agent token:** a `kind: 'token'` access-token record with `agentId`, `agentKind` and `role` (W-TOK1). Its plaintext lives only in `<dir>/mcp-token`, mode 0600.
- **Owner:** the agent or conversation a token belongs to. `<dir>` is `~/.overdeck/agents/<agentId>/` for an agent and `~/.overdeck/conversations/conv-<name>/` (the conversation state dir) for a conversation.
- **`CODEX_HOME`:** the per-agent Codex config root, `~/.overdeck/agents/<id>/codex-home-v2/`. `initCodexHome` (`src/lib/runtimes/codex.ts:266`) rewrites its `config.toml` on every launch, mode 0600.
- **`[mcp_servers.<name>]`:** a Codex `config.toml` table that declares one MCP server: `command`, `args`, an `env` inline table, and options.
- **`default_tools_approval_mode`:** a key inside `[mcp_servers.<name>]`. Codex 0.159.0 accepts `"auto"`, `"prompt"`, `"writes"` or `"approve"` (Fact 3). `"approve"` approves every tool of that server without asking.
- **Approval policy:** Codex's `approval_policy` (`never`, `on-request`, …). Overdeck writes `never` for the `full-access` permission mode and `on-request` for the others (`getCodexLauncherFields`, `src/lib/agents/runtime-command.ts:186`).
- **Codex modes Overdeck uses:** `work-tui` (the interactive `codex` TUI, `launcher-codex-command.ts:97`) and `app-server` (the Overdeck host `dist/codex-app-server-host.js` runs `codex app-server`, `launcher-codex-command.ts:122`). The default transport is `app-server` (`runtime-command.ts:205`, `conversation-runtime.ts:684`).
- **`overdeckMcp` capability:** `HarnessCapabilities.overdeckMcp` (`packages/contracts/src/harness-capabilities.ts:70`). `harnessGetsOverdeckMcp` reads it. Only Claude Code declares `true` today; PAN-4932 D-1 says W-INJ2 flips Codex.
- **CP-2:** the epic's implementation checkpoint "Codex modes load `[mcp_servers.overdeck]`".

## Requirements

### Functional

- **FR-1 Codex agent launches get the server.** C1-C5 write `[mcp_servers.overdeck]` into the agent's `config.toml` when `overdeckMcpEnabledFor('codex')` is true, with the agent's own token file (`~/.overdeck/agents/<agentId>/mcp-token`) and the token role the Claude Code path already uses at that site.
- **FR-2 Codex conversations get the server.** C6 writes the table for a conversation that has a row and is not bare, owned by the conversation (`agentKind: 'conversation'`, `agentId = row.name`, `role = conversationTokenRole(row, role, tmuxSession)`, `dir = stateDir`). A bare conversation and a session without a row get no table and no token (W-INJ1 rule).
- **FR-3 No approval prompt.** The `overdeck` table carries `default_tools_approval_mode = "approve"`, so a model-initiated Overdeck tool call needs no approval under any `approval_policy`.
- **FR-4 Role servers stay.** A role's frontmatter `mcpServers` (for example `playwright` on the test role) are still written next to `overdeck`. If a role declares a server named `overdeck`, Overdeck's entry wins.
- **FR-5 Same switches as Claude Code.** No table when `mcp.agents: false`, when `OVERDECK_DOCKER_WORKSPACE=1` or `PAN_DOCKER=1`, or when the mint fails. A failed mint starts the agent without the server and logs one `[agent-injection] overdeck MCP skipped for <id>: <reason>` warning.
- **FR-6 Capability.** `CODEX_CAPABILITIES.overdeckMcp` is `true`. Claude Code and Codex are the only harnesses that declare it.
- **FR-7 Documentation** states that Codex launches get the server, the approval key, and the CP-2 result (W-6).

### Non-functional

- **NFR-1 No token in config.** `config.toml` holds only the token-file path; the text `odk_` never appears in it or in a launcher script.
- **NFR-2 Valid config only.** `initCodexHome` never writes a `default_tools_approval_mode` value outside `auto | prompt | writes | approve`, because a bad value makes Codex refuse the whole config and the agent never starts (Fact 3).
- **NFR-3 Async only.** No `execSync`, `spawnSync`, `execFileSync` or new `*Sync` function. The mint stays in the async helpers; `initCodexHome` and `getCodexLauncherFields` stay as they are (synchronous, existing callers).
- **NFR-4 File budgets** as in Fact 7. No allowlist row changes.
- **NFR-5 No harness-name branches.** New code gates on `getHarnessBehavior(h).usesCodexHome` or the capability, never on a `'codex'` string literal, so `npm run lint:harness-branches` stays at its baseline.
- **NFR-6 No new import edges into `runtime-command.ts` or `runtimes/codex.ts`.** `agent-injection.ts` must not import `runtimes/codex.ts`; it declares its own structural type, so `npm run lint:circular` stays clean.

## Decisions

- **D-1 Mint at the call site, pass the server map in.** A new `prepareCodexOverdeckMcp(owner)` in `agent-injection.ts` returns `{ overdeck: <entry> }` or `{}`. `getCodexLauncherFields` gains an optional sixth parameter `overdeckMcpServers: Record<string, CodexMcpServerDef> = {}` and stays synchronous. Each of C1-C5 passes `await prepareCodexOverdeckMcp({ … })` as that argument; C6 passes it as `mcpServers` to `initCodexHome`. **Why:** the mint must run before `initCodexHome` writes `config.toml`, and at four of five sites the Claude spread runs after the Codex fields are built. Keeping `getCodexLauncherFields` synchronous keeps the two tests in Fact 8 green, adds no import edge to `runtime-command.ts`, and keeps the `work` role test ("no `[mcp_servers` section") true because the server appears only when a caller passes it. Rejected: making `getCodexLauncherFields` async and minting inside it (breaks two tests, adds `runtime-command.ts → agent-injection.ts`, and every caller still changes).
- **D-2 `default_tools_approval_mode = "approve"` on the `overdeck` table only.** It is the Codex counterpart of W-INJ1's `--allowedTools=mcp__overdeck`. The token's scopes bound what the tools can do, and `route-scopes.ts` judges every call, so approving the server's tools does not widen anything. Role servers (for example `playwright`) keep their current behaviour; changing them is out of scope.
- **D-3 The field lives on `CodexMcpServerDef`.** Add `defaultToolsApprovalMode?: 'auto' | 'prompt' | 'writes' | 'approve'`. `initCodexHome` emits `default_tools_approval_mode = "<v>"` after the `env` line only when the value is one of the four; any other value is dropped with one `console.warn` naming the server (NFR-2). `overdeckStdioServer` stays unchanged, because the Claude Code JSON must not carry this key.
- **D-4 Gate on `usesCodexHome`.** `prepareCodexOverdeckMcp` returns `{}` unless `getHarnessBehavior(owner.harness).usesCodexHome`, then applies `overdeckMcpEnabledFor`. The shared mint (enabled check, owner dir, `ensureAgentMcpToken`) moves into one private helper both `prepare*` functions call, so the two paths cannot drift.
- **D-5 Conversation row lookup moves up.** In `spawnConversationSession`, `const tokenRow = bareContext ? null : getConversationByTmuxSession(tmuxSession);` moves from line 772 to right after `const role = …` (line 587), so the Codex branch and the Claude spread at line 773 both use it. No behaviour change for Claude Code.
- **D-6 CP-2 is recorded from the planning probes** (Facts 3-5): config parse, app-server load and direct call, and a model-initiated call through `codex exec` with and without the approval key. The CLI fallback flags are not built. The unit tests pin the exact TOML the probes used. A live check with a real Codex conversation after deploy is the closing evidence for epic AC-4 (implementation checkpoint below).
- **D-7 Flip the capability in the helper item.** `CODEX_CAPABILITIES.overdeckMcp: true` lands with `prepareCodexOverdeckMcp`, whose tests need it. Flipping it before the call sites are wired changes nothing at runtime: `prepareClaudeOverdeckMcp` still returns `{}` for Codex, and nothing else reads the capability yet (W-INJ4 is not merged).

## Hazards

- **H-1 A bad approval value kills the launch.** Codex refuses the whole config for an unknown `default_tools_approval_mode` value (Fact 3). W-1 validates the value; never write a value from user input without the check.
- **H-2 An older Codex.** An older Codex that predates `default_tools_approval_mode` ignores it as an unknown key (0.159.0 ignores unknown keys in the table, Fact 3); the server then loads but its calls need approval as in Fact 4. Overdeck already requires Codex 0.156.1+ for current models (`src/lib/codex/model-floors.ts:16`). Accept; no version floor is added here.
- **H-3 Tests writing into the real home.** Any test that reaches a real `getCodexLauncherFields` or `prepareCodexOverdeckMcp` must set `HOME` and `OVERDECK_HOME` to a temp dir (Fact 9), or it mints a token into the real `~/.overdeck/access-tokens.json` and writes `~/.overdeck/agents/<id>/`.
- **H-4 Tool timeouts for future wait tools.** Codex's default MCP tool timeout is about 60 s; the epic's wait tools block up to 50 s (D-12). That fits, but W-SELF1 must keep chunks at or under 50 s or set `tool_timeout_sec` on this table. Not changed here.
- **H-5 Startup timeout.** Codex waits a default startup time for `pan mcp serve` to answer `initialize`. The probe started well within it. Under heavy CPU pressure a slow start makes Codex run without the server for that session; the agent can still use `pan`. Not changed here.
- **H-6 Capability readers.** Flipping `CODEX_CAPABILITIES.overdeckMcp` makes W-INJ4 give Codex the MCP instructions block when it lands. That is intended; nothing else reads the capability today.
