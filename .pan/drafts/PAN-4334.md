# External skill packs on top of PAN-3942 — research and design

**Date:** 2026-09-28 · **Scope:** research and design only (no repo edits, no agents, no PRs)
**Base:** `origin/main` @ `b769558ef76` — PAN-3942 merged today as #4326. Issue #3942 is still OPEN, but this follow-up builds on landed code, not an in-flight branch.

## 0. Glossary

- **Pack.** A third-party git repository of Agent Skills that the operator registered with `pan skills pack add`. Identified by a **pack id** matching `^[a-z0-9][a-z0-9-]*$` (e.g. `mattpocock`).
- **Registry entry.** The stored decision for one pack: `~/.overdeck/config.yaml` → `skills.packs.<id>: { url, ref, commit, adapter? }`.
- **Ref.** What the operator asked to track (a tag such as `v1.2.3`, or a branch).
- **Trusted commit.** The 40-hex SHA the operator approved at add/update time (`commit` in the registry). Every launch mounts exactly this commit, never the moving ref.
- **Pack cache.** Disposable, derived files under `~/.overdeck/packs/<id>/`: `repo.git` (blobless bare clone) and `<commit>/` (read-only `git archive` extraction).
- **Adapter.** Code that reads a pack checkout and returns a **pack manifest** (`PackManifest`: skills, capabilities, license, upstream plugin name). v1 adapters: `plain`, `claude-plugin`.
- **Known pack.** An entry in the `KNOWN_PACKS` table (`src/lib/skill-packs/adapters.ts`) carrying defaults for a well-known source: `mattpocock` (adapter `claude-plugin`, opt-in `setup-matt-pocock-skills`), `sageox` (`kind: 'integration'`, not addable).
- **Pack skill id.** `pack/skill` (e.g. `mattpocock/grilling`). Used in the UI, the CLI, and override keys. `/` is illegal in Agent Skills names, so it never collides with a native skill.
- **Harness-visible name.** `pack:skill` (e.g. `mattpocock:grilling`), produced by the Claude Code and Codex plugin systems from the generated wrapper plugin named after the pack id.
- **Native skill.** Any skill found by the existing PAN-3942 `listSkillCatalog()` roots. Default on.
- **Opt-in skill.** A pack skill the adapter marks `optIn: true`. The pack toggle never turns it on; only a per-skill `on` does.
- **Pack toggle.** The per-level on/off for a whole pack: global `skills.pack_overrides.<id>`, project `skill_pack_overrides.<id>`, issue file `packs.<id>`.
- **Capability.** Anything a pack contains besides skills (hooks, MCP servers, commands, agents, context injection, git hooks, executables, project-mutating skills, required CLIs). v1 reports every capability as **"Not applied"** and mounts none.
- **Selection.** The sorted set of `pack@commit:skill` triples enabled for one launch context.
- **Mount.** The content-addressed wrapper directory `~/.overdeck/packs/mounts/<sha256-of-selection>/` holding generated plugin manifests and verbatim skill copies for both harnesses.
- **Plugin link.** A per-launch symlink `<OVERDECK_HOME>/launch/<launchKey>/skill-packs` → `<mount>/plugins`, passed to Claude Code as `--plugin-dir`. **Launch key** = `managedStateKey ?? overdeckEnv.agentId ?? sessionId` (the same chain as `launcher-generator.ts:400`).
- **Launch step.** The existing PAN-3942 bash step `pan skills launch-settings …` that every local Claude Code / Codex launcher runs before the harness starts.

## 1. Verdict

1. **Build one generic "external pack" mechanism, not three integrations.** A pack is a git repo pinned to a commit the user approved. Overdeck caches that commit and **mounts the enabled pack skills per launch through each harness's own plugin system.** Claude Code 2.1.280 has `--plugin-dir <folder-of-plugins>` for a single session. Codex 0.158 loads local-marketplace plugins from the per-agent `CODEX_HOME`. Both show plugin skills as `plugin:skill`, so `mattpocock:grilling` cannot collide with Overdeck's bundled `grilling`. Overdeck generates the plugin wrapper itself and puts only `skills/` in it. Upstream hooks, MCP servers and commands are therefore left out by construction, not just by policy.
2. **Pack toggles use PAN-3942's three levels and its stores.** A pack gets on/off at global, project and issue. Each pack skill gets a per-skill override keyed `pack/skill`. Pack skills are **off unless turned on**, which is the explicit opt-in. Core skills are unaffected.
3. **The three sources are very different:**
   - **Matt Pocock (`mattpocock/skills`)** is a plain drop-in pack: MIT, skills only, and `.claude-plugin/plugin.json` lists the 25 published skills. **It should go first.** Four Overdeck bundled skills (`grilling`, `codebase-design`, `domain-modeling`, `improve-codebase-architecture`) are unattributed June-2026 copies of it and are now stale.
   - **Deft (`deftai/directive`)** is not a skill pack. It is a practice layer that installs by writing tracked repo files: an `AGENTS.md` managed section, hooks in four host config files, `.githooks` + `core.hooksPath`, a guard workflow, a `package.json` pin and an `xbrief/` tree. Only a 7-skill engine-free subset can be a pack today. Clean per-launch toggling needs upstream changes, listed in §6.
   - **SageOx (`sageox/ox`)** is **not a pack** either. It is a CLI, hooks and a cloud service. Its skills are thin wrappers around the `ox` binary and are useless without `ox login` + `ox init`, and `ox` overwrites them on its own. Overdeck has removed it twice, citing a trust boundary. **Decline it as a pack.** It stays an integration under #2444, and the Skills page lists it as such.
4. **Sequencing:** first the pack mechanism plus the `mattpocock` pack (one issue, body in §10). Next, the `deft` read-only pack plus Directive-project detection, under #3943, with upstream PRs 1–3 filed in parallel. Full Deft mode only after upstream PRs 5–6. SageOx: no pack work.

### Existing patterns this design rejects

- `sync-sources/plugins.json` + `src/lib/claude-plugins-provision.ts` install Claude plugins **at user scope for every Overdeck user**. They would leak project- and issue-scoped packs into every session, including sessions the user runs outside Overdeck.
- The `pan-skill-installer` dev skill (`sync-sources/dev-skills/pan-skill-installer/SKILL.md`) vendors a skill into `sync-sources/`. That is the bundled tier, and it is how the four Matt copies arrived without attribution.
- The #3942 research comment proposed named presets (`matt-pocock-core`, `deft-readonly`, `sageox-read`). The rescoped PAN-3942 cut bundles. Here a "pack" is a **source** with on/off, not a named selection.

## 4. The pack model

### 4.1 Source, pin, cache

- **Source types (v1): git only.** Config holds `url` + `ref` + `commit`. All three targets are git repos. Deft's npm tarball carries the engine, not extra skills, and its git tags match the npm versions. An npm source type is not needed and is out of scope.
- **Pin.** `ref` is what the user asked for: a tag, or a branch to track for updates. `commit` is the **trusted SHA**, and every launch mounts exactly that commit. A tag or branch can move, so the SHA the user approved is a decision, not derivable status.
- **Cache (derived, deletable at any time).**
  - `~/.overdeck/packs/<id>/repo.git`: blobless bare clone.
  - `~/.overdeck/packs/<id>/<commit>/`: `git archive` extraction, read-only.
  - `~/.overdeck/packs/mounts/<sha256>/`: the generated wrapper, content-addressed by the sorted `[pack@commit:skill…]` selection plus the adapter version. Built in a temp dir and then renamed, immutable after that.
  - All git work uses async `execFile` (the server rule forbids `execSync`).
- **Launches never touch the network.** If a pinned commit is not cached, the launch step rebuilds it from `repo.git` when that is present. Otherwise it skips the pack with the PAN-3942 fail-open warning. `pan skills pack sync` re-fetches.
- **Updates.**
  - `pan skills pack update <id>` fetches, resolves `ref`, and prints a diff against the trusted commit: skills added, removed or changed, and new capabilities (§4.4). After explicit confirmation it rewrites `commit`.
  - "Update available" is computed on demand with `git ls-remote` and is never stored.

### 4.2 Identity and namespacing

- **Overdeck id: `pack/skill`** (e.g. `mattpocock/grilling`). It is used in the UI, the CLI and override keys. `/` is not allowed in Agent Skills names, so it can never collide with a bundled or project skill name.
- **Harness-visible name: `pack:skill`**, produced by the plugin systems on both harnesses. The wrapper plugin is named after the pack id.
- **Adapters may map names.** The Deft adapter strips `deft-directive-`, so `deft/glossary` shows as `deft:glossary`.
- **Pack id rules:** `[a-z0-9][a-z0-9-]*`, unique in the registry, and never equal to a core skill name.

### 4.3 Resolution: pack toggle and per-skill override

For a pack skill `p/s` (never core), walk the levels narrowest first. At each level, **a per-skill override beats that level's pack toggle**. The first level with any value wins. If no level has a value, the skill is **off** (source `default`). Skills an adapter marks **opt-in** ignore pack toggles and only turn on through a per-skill `on`.

```
for level in [issue, project, global]:
  if overrides[level]["p/s"] defined → return (value, level)
  if packToggles[level]["p"] defined and !optIn(s) → return (value, `${level}-pack`)
return (false, 'default')
```

| Global | Project | Issue | Result | Why |
|---|---|---|---|---|
| pack on | skill `mattpocock/tdd` off | — | tdd **off** (project) | narrower per-skill value |
| pack on | — | pack off | all **off** (issue-pack) | narrowest level with a value |
| — | skill `mattpocock/grilling` on | pack off | grilling **off** (issue-pack) | issue level decides before project is consulted |
| skill `mattpocock/grilling` on | — | — | grilling **on**, rest off | single-skill opt-in without the pack |
| pack on | — | — | `setup-matt-pocock-skills` **off** | opt-in skill ignores pack toggles |

**Global write rule for pack skills (a deliberate departure from #3942 UI decision #1).** At global, a pack skill stores only its deviation from the global pack toggle:
- If the chosen value equals the pack's global state, the key is cleared.
- If it differs, `true` or `false` is stored.

So `true` can be stored at global for a pack skill, even though native skills have no "force on" at global. The reason is the different default: pack skills are off unless turned on, so "on" at global is the deviation.

`disabledSkillNames()` must **exclude ids containing `/`**. Pack skills are filtered when the mount is built; they are never hidden by name. Sending `mattpocock/grilling` to Claude `skillOverrides` would be a stray key.

### 4.4 Non-skill parts: declared, never applied (v1)

An adapter returns `{ skills[], capabilities }`, where `capabilities` lists what the pack has **besides** skills:
- `hooks`
- `mcpServers`
- `commands`
- `agents`
- `contextInjection` (AGENTS.md/CLAUDE.md edits)
- `gitHooks`
- `executables`: bundled scripts inside skill dirs
- `projectMutatingSkills`
- `requiresCli`, e.g. `ox` or `directive`

The add, update and preview output lists each one as **"Not applied."** v1 mounts `skills/` only.

A later issue can add **capability grants**: a second, explicit, per-pack consent stored as `grants: [hooks]` in the registry entry. Both harness plugin formats can carry hooks and MCP, so a granted capability would travel through the same wrapper. None of the three targets needs that in v1.

### 4.5 Trust

- **Adding a pack is the trust grant.** `pan skills pack add <id> <url> --ref <ref>` fetches, resolves, runs the adapter, prints the preview (license, skills, opt-in skills, executables, "Not applied" capabilities, commit), and writes the registry entry only after interactive confirmation or `--yes`.
- **Adding enables nothing.** Every pack skill stays off at every level until the user toggles it.
- **Updates re-confirm** against the diff.
- **Repos cannot declare packs.** A project cannot auto-trust a pack through a committed file (for example `.pan/skill-packs.yaml`); this is a non-goal.
- **The dashboard in v1 can toggle and view packs but not add them.** It shows the CLI command. Adding needs a consent flow that the CLI already provides.
- Remote (Fly) launches get no packs, as in PAN-3942 D12.

### 4.6 Stored vs derived ("Overdeck stores no status it can derive")

| Stored (decisions) | Where |
|---|---|
| Pack registry: `id`, `url`, `ref`, trusted `commit`, `adapter` (only when not the known-pack default) | `~/.overdeck/config.yaml` `skills.packs.<id>` |
| Global pack toggle | `config.yaml` `skills.pack_overrides.<id>: true` (two-state: on = stored `true`, off = key cleared) |
| Project pack toggle | `projects.yaml` `projects.<key>.skill_pack_overrides.<id>: true\|false` |
| Issue pack toggle | `<planHome>/.pan/skill-overrides/<ISSUE>.yaml` new top-level `packs:` map (same file, same commit door) |
| Per-skill pack overrides | the existing PAN-3942 maps, keys `pack/skill` |

| Derived (never stored) | From |
|---|---|
| Skill list, descriptions, opt-in flags, capabilities, license | adapter over `~/.overdeck/packs/<id>/<commit>/` |
| Cached / missing | `fs.stat` |
| Update available | `git ls-remote` on demand |
| Mount path | hash of the launch's resolved selection |
| Which pack skills a running agent got | recomputed; changes apply at next launch (PAN-3942 D8) |
| Name overlap with bundled skills (e.g. `mattpocock/grilling` vs `grilling`) | catalog comparison |
| Duplicate user-installed plugin | `~/.claude/plugins/installed_plugins.json` read on demand |
| Directive / SageOx project detection | `.deft/core/VERSION`, `deft:managed-section`, `.sageox/` |

### 4.7 Launch mount (both harnesses, one artifact)

The mount directory serves both harnesses at once:

```
~/.overdeck/packs/mounts/<sha256>/
  .agents/plugins/marketplace.json          # Codex local marketplace "overdeck-packs"
  plugins/<pack>/.claude-plugin/plugin.json # {"name":"<pack>","skills":["./skills/<s>",…]}
  plugins/<pack>/.codex-plugin/plugin.json
  plugins/<pack>/skills/<s>/…               # verbatim copies (no symlinks: Codex drops them)
```

- **Claude Code.**
  - The existing `pan skills launch-settings` step (one process, about 0.4 s) gains `--plugin-link <path>`. The launcher passes `~/.overdeck/launch/<managedStateKey>/skill-packs` (`managedStateKey` is at `launcher-generator.ts:400`).
  - The step points that symlink at `<mount>/plugins`, or removes it when no pack skill is on.
  - `launcher-lines.ts` adds `[ -d <link> ] && PAN_SKILL_PLUGIN_DIR=<link>` and the command suffix `${PAN_SKILL_PLUGIN_DIR:+--plugin-dir "$PAN_SKILL_PLUGIN_DIR"}`.
  - Stdout stays the single `--settings` JSON, so the existing `''|'{'*'}'` guard is unchanged.
- **Codex.**
  - The same step, which already runs after `export CODEX_HOME=` and after `initCodexHome` rewrites `config.toml`, writes a second marked block, `# overdeck:skill-packs:begin/end`, containing `[marketplaces.overdeck-packs] source_type="local" source="<mount>"` and one `[plugins."<pack>@overdeck-packs"] enabled = true` per pack.
  - It copies each pack into `$CODEX_HOME/plugins/cache/overdeck-packs/<pack>/<mount-hash>/`.
  - It prunes any other `overdeck-packs/*` entries.
- **The generated `.codex-plugin/plugin.json` `version` must equal `<mount-hash>`.** The cache directory is keyed by version, and a mismatch would stop the loader from matching them.
- **Interactive consent is unverified.** `--settings` has no prompt, but `--plugin-dir` might show a consent dialog in an interactive (pane) launch, and that would hang a managed agent. The checkpoint must include one interactive launch.
- **Required implementation checkpoint.** Use the repo's precedent, `codex debug prompt-input` with an isolated `CODEX_HOME` (`runtimes/codex.ts:15-18`). Confirmed present in 0.158.0: `codex debug --help` lists `prompt-input  Render the model-visible prompt input list as JSON`. It must list `mattpocock:grilling`. For Claude: `claude -p --plugin-dir <link> …` must report `mattpocock:grilling` present, and `grilling` must still resolve to the bundled copy.
- **Codex fallback**, only if the checkpoint fails because Codex will not load a hand-populated cache: copy to `$CODEX_HOME/skills/<pack>-<skill>/` with frontmatter `name:` rewritten, and prune everything carrying that prefix. The Overdeck id is unchanged.

**Title:** External skill packs: pinned git sources mounted per launch, with pack on/off at global, project, and issue level

**PRD:** [.pan/drafts/PAN-<n>.md](.pan/drafts/PAN-<n>.md)

**Labels:** enhancement · **Depends on:** #3942 (merged in #4326) · **Related:** #3943 (Deft), #2444 (SageOx), #791

### Problem

PAN-3942 lets operators turn skills on and off at three levels, but only for skills already on disk. Operators want third-party skill collections — first Matt Pocock's `mattpocock/skills` — available to Overdeck agents as explicit, pinned, per-level opt-ins.

Today the only paths are:
- vendoring into `sync-sources/`. That is how four Matt skills (`grilling`, `codebase-design`, `domain-modeling`, `improve-codebase-architecture`) arrived in `fc915e7fbc9`, unattributed and now stale.
- user-scope plugin installs (`sync-sources/plugins.json`), which leak into every session, including ones started outside Overdeck.

Copying pack skills into `~/.claude/skills` or `~/.agents/skills` is not an option: `listSkillCatalog` dedupes by directory name (first root wins), and unmanaged sessions would see project-scoped packs.

### Design

- **Pack = git source pinned to a trusted commit.**
  - Registry in `~/.overdeck/config.yaml` `skills.packs.<id>: { url, ref, commit, adapter? }`.
  - `pan skills pack add <id> <url> --ref <ref>` fetches, resolves the ref to a commit, runs the adapter, prints a preview (license, skills, opt-in skills, executables, and non-skill capabilities marked "Not applied") and writes the entry only after confirmation or `--yes`.
  - `pan skills pack update <id>` shows the diff against the trusted commit and re-confirms. `remove`, `list` and `sync` complete the set.
  - Cache: `~/.overdeck/packs/<id>/repo.git` + `<commit>/`. It is disposable, and all git calls are async `execFile`.
- **Adapters (v1):**
  - `plain` (`skills/**/SKILL.md`)
  - `claude-plugin` (`.claude-plugin/plugin.json` `skills[]`)
  - a known-pack table: `mattpocock` = `claude-plugin`, opt-in `setup-matt-pocock-skills`; `sageox` = integration, not addable, points at #2444
- **Ids.**
  - Overdeck id `pack/skill` for the UI, CLI and override keys.
  - Harness name `pack:skill` via the plugin systems.
- **Toggles.**
  - Global `config.yaml` `skills.pack_overrides.<id>: true` (two-state).
  - Project `projects.yaml` `skill_pack_overrides`.
  - Issue: a `packs:` map in the existing `<planHome>/.pan/skill-overrides/<ISSUE>.yaml`.
  - Per-skill overrides reuse the PAN-3942 maps with `pack/skill` keys.
- **Resolution.** For each level, narrowest first, a per-skill value beats that level's pack toggle, and the first level with any value wins. Default is off. Opt-in skills ignore pack toggles. Pack skills are never core. `disabledSkillNames()` excludes ids containing `/`.

  | Global | Project | Issue | Result |
  |---|---|---|---|
  | pack on | skill `mattpocock/tdd` off | — | tdd off (source `project`) |
  | pack on | — | pack off | all off (source `issue-pack`) |
  | — | skill `mattpocock/grilling` on | pack off | grilling off (source `issue-pack`) |
  | skill `mattpocock/grilling` on | — | — | grilling on (source `global`), rest off (`default`) |
  | pack on | — | — | `setup-matt-pocock-skills` off (opt-in, source `default`) |

- **Global write rule for pack skills.** This is a deliberate departure from #3942 UI decision #1. At global, a pack skill stores only its deviation from the global pack toggle: a value equal to the pack's state clears the key; a different value stores `true` or `false`. So `true` can be stored at global, because pack skills default to off.
- **Launch.** The existing `pan skills launch-settings` step builds (or reuses) a content-addressed mount `~/.overdeck/packs/mounts/<sha256>/`. It holds `plugins/<pack>/{.claude-plugin,.codex-plugin}/plugin.json` + verbatim `skills/` copies, plus `.agents/plugins/marketplace.json`.
  - **Claude:** the step points `~/.overdeck/launch/<managedStateKey>/skill-packs` at `<mount>/plugins`, and the command gains `${PAN_SKILL_PLUGIN_DIR:+--plugin-dir "$PAN_SKILL_PLUGIN_DIR"}`. Stdout stays the `--settings` JSON.
  - **Codex:** a `# overdeck:skill-packs:begin/end` block in the per-agent `config.toml` (local marketplace `overdeck-packs` + `[plugins."<pack>@overdeck-packs"] enabled = true`), a copy into `$CODEX_HOME/plugins/cache/overdeck-packs/<pack>/<hash>/`, and pruning of stale entries.
  - **Codex fallback**, only if Codex will not load the hand-populated plugin cache: copy each enabled skill to `$CODEX_HOME/skills/<pack>-<skill>/` with frontmatter `name:` rewritten to `<pack>-<skill>`, and prune every `<pack>-*` directory not in the current selection on each launch. `syncCodexSkillsIntoHome` preserves destination-only skills, so this pruning is required.
  - The launch step does no network and fails open, as in PAN-3942 D7. Remote launches are excluded (D12). Changes apply at next launch (D8).
- **Stored vs derived.** Only the registry entry (including the trusted commit) and the toggles are stored. Skill lists, capabilities, cache presence, update availability, mount paths and bundled-name overlaps are derived on demand.
- **UI.**
  - A "Skill packs" block in `SkillOverridesPanel` at all three levels. Each pack row carries a pack control (global switch; project and issue `Inherit | On | Off` with the effective value in the Inherit label), the source `@ ref (short sha)`, the license, the skill count and "Not applied: …".
  - Rows expand to per-skill controls, with opt-in and "Overdeck also bundles `<name>`" notes and derived notices (not cached, update available, duplicate Claude plugin install).
  - Adding a pack is CLI-only in v1; the empty state shows the command.

## 12. Planning decisions (auto mode)

- **PD-1 Pack skills are not merged into `listSkillCatalog()`.** `SkillOverridesPanel.tsx` `inherited()` returns `on: skill.global !== false`, so a pack skill rendered as a native row would show "on" by default, the opposite of the pack default. `catalog.ts` gains a separate `listPackCatalog()`; `resolve.ts` gains `resolvePackStates()`; `listSkillStates()` returns `skills` (native, unchanged) plus `packs: PackState[]`.
- **PD-2 Launch key without touching `launcher-generator.ts`.** `prepareClaudeContext(config)` (`launcher-context.ts:18`) receives the whole `LauncherConfig`, and `SkillOverrideLaunchConfig` is structural. Add optional `managedStateKey?`, `sessionId?`, `overdeckEnv.agentId?` to it and compute the key in `launcher-lines.ts`. **No key (or a key not matching `^[A-Za-z0-9._-]+$`) ⇒ no `--plugin-link`, no `PAN_SKILL_PLUGIN_DIR` line, no `--plugin-dir` suffix** (packs skipped for that launch; settings step unchanged).
- **PD-3 No network in the default GET.** `GET /api/skills/overrides` is also the PUT response body. `updateAvailable` is computed only when the GET carries `checkUpdates=1` (no new route). `SkillPacksSection` issues that request separately, at global level only. The PUT response never runs `git ls-remote`.
- **PD-4 Launch path runs no git.** If the trusted commit's extraction `~/.overdeck/packs/<id>/<commit>/` is missing, the launch step skips that pack and prints `[launcher] WARNING: skill pack <id> not cached; run pan skills pack sync <id>` to stderr. It never rebuilds from `repo.git` (a blobless repo can lazy-fetch blobs = network).
- **PD-5 Issue file shape** becomes `{ issue, skills, packs }`. The file is deleted only when both maps are empty. `listLowerLevelOverrides()` keeps its per-skill map (pack-skill keys `p/s` appear naturally) and a new `listLowerLevelPackOverrides()` reports pack toggles; the global GET returns it as `packOverriddenBelow`.
- **PD-6 Global write rule for `/` ids.** Resting value = `optIn ? false : (globalPackToggle === true)`. Chosen value equal to resting ⇒ delete the key (prune empty maps); different ⇒ store `true`/`false`. `inherit` at global ⇒ delete the key.
- **PD-7 Errors.** New `SkillOverrideErrorCode` `'unknown-pack'` → HTTP 404. A `pack/skill` whose pack is unregistered, or whose skill is not in the manifest ⇒ `unknown-skill` (`unknown skill: <id>`). A registered but uncached pack ⇒ `bad-request` (`pack <id> is not cached; run pan skills pack sync <id>`).
- **PD-8 Symlinks are never copied.** Mount copies skip every symlink (`lstat`), so a pack symlink pointing outside the repo cannot pull host files into the mount.
- **PD-9 CLI shape.** `pan skills set <args...>`: with `--pack <id>` exactly one positional (the state); without it exactly two (skill, state). `pan skills list --json` keeps printing the native `skills` array (unchanged); pack JSON comes from `pan skills pack list --json`.
