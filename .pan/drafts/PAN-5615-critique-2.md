## blocks-the-design: Delivery still misses the Flywheel harness

The proposed W10 fixes only `messageAgent`'s liveness lookup (`src/lib/agents/messaging.ts:271-276`). The later delivery call (`src/lib/agents/messaging.ts:797-805`) enters `deliverAgentMessage`, whose `targetHarness` calls `getConversationByTmuxSession(agentId)` (`src/lib/agents/delivery.ts:55-68`). That lookup strips `conv-` and queries `c.name = 'flywheel'` (`src/lib/overdeck/conversations.ts:628-636`), while Flywheel creation stores both name and session as `conv-flywheel` (`src/lib/flywheel/actions.ts:218-227`). Its harness is therefore still unknown at the delivery door. On Herdr, `isHostBackedTarget(undefined)` permits a host-backed Flywheel to enter `agent.prompt` (`src/lib/agents/delivery.ts:432-459`), the path the existing `tests/unit/lib/agents/delivery-conversation-herdr.test.ts:10-12,131-145` explicitly guards against because it types into host stdin. W10's new test stops at `no-session`, so it cannot catch this. Smallest fix: make `targetHarness` use the existing exact-session resolver `getSupervisedConversationByTmuxSession` (`src/lib/overdeck/conversations.ts:639-646`), and add a delivery test with a row named and sessioned `conv-flywheel` on a host-backed harness that proves Herdr `agent.prompt` is never called.

## blocks-the-design: Strike still promises a comment read on the next tick

W5 explicitly edits only the two `pan tell` targets in `roles/strike.md:99,108`, leaving line 98: the issue comment is what "the orchestrator's next tick" reads. The PRD's FR-5 and W8 state the `/pan-flywheel` loop has no issue-comment read step; its tick orientation and drain steps (`sync-sources/skills/pan-flywheel/SKILL.md:105-138`) read status, PRs, panes and transcripts, without directing the agent to read issue comments. The unchanged sentence tells strike agents their mandatory comment reaches the Flywheel automatically when an optional tell fails, recreating the false delivery assurance this plan corrects for the other roles. Smallest fix: include the sentence at `roles/strike.md:97-98` in W5 and change it to say the comment stays on record for the operator and Flywheel to read, without promising a next-tick read.

## footnote: Zero-match grep exits unsuccessfully

The W1-W5 `verify_commands` use `grep -c flywheel-orchestrator roles/<file>` and expect `0`. A zero-match `grep -c` prints `0` but exits 1; I rechecked with `grep -c 'no-ops gracefully' roles/strike.md`, which printed `0` and returned status 1. If the executor treats a nonzero verification exit as failure, these items fail despite correct edits. Smallest fix: use `! grep -q flywheel-orchestrator roles/<file>` for the absence check.
