# PAN-3022 — Carry the operator's `pan start --model` through the planning → work auto-handoff

**Issue:** [PAN-3022](https://github.com/eltmon/overdeck/issues/3022)
**Status:** planned (auto mode, 2026-09-26)

## Summary

`pan start <id> --model X` on an unplanned issue starts planning with auto-start. When
planning finalizes, the work agent the handoff spawns must run on `X`. Today it runs on
the `roles.work` default: the CLI sends `workModel: X` to `start-planning`, the server
validates it and then drops it, and every handoff spawner posts no model. This PRD stores
`X` in the auto-start consent record (the handoff's own durable record) and makes every
consent-bearing spawn honor it.

## Glossary

- **Auto-start consent record** — the JSON file
  `~/.overdeck/agents/planning-<issue>/auto-spawn-on-finalize.json`
  (`autoSpawnOnFinalizeFlagPath`, `src/lib/planning/auto-spawn-consent.ts`). Version 2
  shape: `{ version: 2, generation, status: 'granted'|'claimed'|'spent', claimId?, updatedAt }`.
  Written when planning starts; claimed and spent by the work spawn that the planning
  handoff triggers.
- **Generation** — a random UUID per consent write. A new planning cycle writes a new
  generation.
- **Consent-bearing spawn** — any work spawn called with `autoSpawnConsentRequired: true`
  by a non-operator `startedBy`. These spawns go through `withAutoSpawnConsentClaim`.
  Operator starts (`isOperatorStartedBy`) never claim consent.
- **Planning handoff** — the work spawn after `pan plan finalize` when auto-start was
  requested. It has five entry paths (see "Handoff paths").
- **Work model** — the model the operator named with `pan start --model` when that start
  also kicked off planning. Sent to `POST /api/issues/:id/start-planning` as `workModel`.
- **`resolveIssueWorkModel`** — `src/lib/agents/staffing.ts:85`. After the Cut (PAN-3917)
  it always returns `undefined`. It is dead code.
- **Explicit model** — a model that `POST /api/agents` forwards to `pan start` as
  `--model`. An explicit model skips tier resolution (PAN-3857, PAN-3842).

## Requirements

- **FR-1** When `POST /api/issues/:id/start-planning` receives a valid `workModel`, the new
  consent generation it writes stores that model as `workModel`.
- **FR-2** A new planning cycle without `workModel` writes a consent generation with no
  `workModel` (a stale model from an earlier cycle never survives a re-plan).
- **FR-3** The complete-planning consent rewrite (`resolveAutoSpawnOnFinalize` with an
  explicit boolean) preserves the current record's `workModel`.
- **FR-4** Every consent-bearing work spawn (paths A–E) runs on the consent `workModel`
  when one is stored. It wins over `options.model` on that spawn.
- **FR-5** `POST /api/agents` with `autoSpawnConsentRequired: true` and no `body.model`
  uses the consent `workModel` for its pre-flight checks (provider auth, provider health)
  and forwards it to `pan start` as `--model`.
- **FR-6** An operator start (`isOperatorStartedBy`) or any spawn without
  `autoSpawnConsentRequired` never reads the consent `workModel`. A later bare
  `pan start <id>` falls back to config routing as before.
- **FR-7** The consent `workModel` is readable only while the record status is `granted`
  or `claimed`. A `spent` record yields no model.
- **FR-8** `resolveIssueWorkModel` is deleted.
- **NFR-1** No new file, no new store, no `.pan/` write. The consent record stays the only
  home.
- **NFR-2** The consent record stays backward compatible: records without `workModel` and
  legacy `{ autoSpawnOnFinalize: boolean }` records parse as before.
- **NFR-3** No sync I/O added to dashboard-server-reachable code. All consent reads use the
  existing async `readFile` helpers.

## Decisions

- **D1 — Home is the consent record.** The issue comment names two acceptable homes: "the
  handoff itself or a durable per-issue home such as `.pan/continues/<issue>.xbrief.json`".
  The consent record *is* the handoff's durable record: it is generation-scoped (one per
  planning cycle), every handoff path already claims it, and it exists before planning
  starts. `.pan/continues/<issue>.xbrief.json` does not exist at start-planning time and
  would need a write-door commit before any spec exists. Chosen: consent record.
- **D2 — Precedence on a consent-bearing spawn is `claim.workModel ?? options.model`.**
  Operator starts never take the claim path, so on this path `options.model` is either the
  route's forwarded copy of the same consent model, or `pan start`'s prior-agent resume
  continuity (`resolvePanStartSpawnModel`, `src/cli/commands/start-spawn-model.ts`). A stale
  prior-agent model must not beat the operator's fresh `--model` on a re-plan.
- **D3 — Write rule for `workModel`.** `writeAutoSpawnOnFinalizeFlag(issueId, enabled, options?)`:
  - `options.workModel` is a string → store it.
  - `options.workModel === null` → store nothing (clear).
  - `options` or `options.workModel` is `undefined` → keep the current record's `workModel`
    (read under the same lock).
  `spawnPlanningSession` (new cycle) always passes `workModel: opts.workModel ?? null`.
  `resolveAutoSpawnOnFinalize` passes nothing, so it preserves.
- **D4 — Model only.** `--harness` and `--effort` on the unplanned `pan start` path go to the
  planning agent today. Carrying them to the work agent is out of scope.
- **D5 — The route gets a tiny pure helper for testability.** The route is a large Effect
  generator. Put the choice in `resolveWorkSpawnRequestedModel(bodyModel, consentWorkModel)`
  in `src/dashboard/server/routes/agents/shared.ts` and unit-test the helper.

## Non-goals

- Carrying `--harness` or `--effort` to the handoff work agent.
- Any new per-issue store, `.pan/` write, or revival of the deleted pipeline record.
- A dashboard UI for choosing the work model at planning start.
- Fixing `readAutoSpawnOnFinalize` in `src/cli/commands/plan-finalize.ts:140-146`, which
  reads only the legacy `autoSpawnOnFinalize` field and so reports `false` for v2 records.

## Repo rules that intersect this change

- No `execSync` or new sync I/O in dashboard-server-reachable code. The consent reads use
  `fs/promises`.
- Fake timers for any delay-based test (none expected here).
- Skills ↔ CLI lockstep: `scripts/lint-skills.sh` runs in `npm run lint`.
- Quality gates: `npm run typecheck`, `npm run lint`, `npx vitest run <touched test files>`.
  Never run the full `npm test` on the host.
- Never hardcode a model fallback: an absent consent model falls through to
  `determineModel`'s configured role resolution, never a literal.
