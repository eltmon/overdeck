**Sibling (dashboard slice, split out by this plan):** https://github.com/eltmon/overdeck/issues/4657
**Depends on (sibling only):** #4639 (snooze and settle)
**Planned:** 2026-11-01, auto mode, against `main` at `56d9b528230`.

## Glossary

- **Conversation** — a row in the `conversations` table of `overdeck.db` (`drizzle/overdeck/0000_overdeck_init.sql`, `CREATE TABLE \`conversations\``). It has two different identifiers that must not be confused: `id` is the text primary key that child tables reference (`conversation_id` foreign keys join `c.id`), and the `/conv/<n>` number is the SQLite `rowid`, which `getConversationById(n)` resolves (`WHERE c.rowid = ?`). It also has a unique `name` (for example `conv-20261101-1234`). `status` is `active` or `ended`; `archived_at` is set when archived.
- **Schedule** — a new row in the new `conversation_schedules` table. It holds one prompt, one recurrence, one IANA time zone, an `enabled` flag, `next_run_at` and the last run's outcome. A conversation has zero or more schedules.
- **Recurrence** — a standard 5-field cron expression (`minute hour day-of-month month day-of-week`) evaluated in the schedule's time zone. Presets (`--hourly`, `--daily HH:MM`, `--weekdays HH:MM`, `--weekly "<day> HH:MM"`) are CLI sugar that compile to a 5-field cron before storage. Only the cron string is stored.
- **Occurrence** — one instant at which a recurrence fires.
- **Due** — a schedule is due when `enabled = 1` and `next_run_at <= now`.
- **Sweep** — the new dashboard-resident service `conversation-schedule-service.ts`. It runs 30 s after boot, then every 60 s, and fires due schedules.
- **Fire** — deliver one schedule's prompt to its conversation: resume the session first if it is not running, then deliver the prompt like an operator message.
- **Claim** — the compare-and-set `UPDATE` that advances a due schedule's `next_run_at` to the next future occurrence *before* the fire. It makes a fire at-most-once.
- **Missed-run collapse** — when the dashboard was down across several occurrences, the schedule fires once on the next sweep, because the claim computes the next occurrence from the current wall clock, not from the stale `next_run_at`.
- **Door** — the only module allowed to read or write a table (repo convention, for example `src/lib/overdeck/conversation-bookmarks.ts`).
- **Primary dashboard** — the dashboard process that owns `~/.overdeck`. A **peer dashboard** (`isPeerDashboard` in `src/dashboard/server/main.ts`, from `isPeerDashboardProcess` in `src/lib/boot-gates.ts`) never runs write services.
- **croner** — the MIT-licensed, zero-dependency npm package `croner` (pinned `10.0.1`, released 2026-02-01) used only to parse cron patterns and compute the next occurrence in a time zone. It is always constructed with `paused: true`, so it never arms a timer.
- **Pi harness** — `pi` or `ohmypi`; `isPiControlChannelHarness` in `src/lib/overdeck/conversation-delivery.ts` line 276.

## Problem

Overdeck has no time-based trigger for a conversation. A conversation can use its own harness's wakeup or cron tools, but those die with the process, and `src/lib/resume-contract.ts` tells a resumed session to re-arm them itself. The t3code demo the issue cites shows the feature Overdeck lacks: a thread that runs a stored prompt daily at 21:00, survives restarts, and resurfaces when it runs.

## What the code does today (verified 2026-11-01)

1. **Message delivery refuses ended sessions.** `handleConversationMessage` in `src/lib/overdeck/conversation-message.ts` (line 407) returns `422 'Session has ended — start a new run to interact'` when `conv.status === 'ended'` (grep anchor: `Session has ended — start a new run to interact`). The issue's claim that the message route resumes an ended session is not true for this route; the dashboard composer calls `POST /api/conversations/:name/resume` first (`src/dashboard/frontend/src/components/chat/conversationResumeApi.ts`). The sweep must therefore resume first, then deliver.
2. **Resume hardcodes its cause.** `handleConversationResume` in `src/lib/overdeck/conversation-runtime.ts` (line 1074) computes `resumeCause = conv.status === 'ended' ? 'operator' : 'system'` (grep anchor: `resumeCause = conv.status === 'ended' ? 'operator' : 'system'`). A scheduled resume would tell the agent "The operator resumed this session". `ResumeCause` in `src/lib/resume-contract.ts` already has `'message'`, whose text is "This session was resumed because a new message arrived while it was stopped."

## Decisions (auto mode)

- **D1 — Host process: the dashboard, not the deacon child.** The sweep is a dashboard service started only on a primary dashboard, like the PR sync sweep. Resume and delivery are in-process calls; the deacon child would need two internal HTTP hops and could not pass a resume cause. The issue's "within one deacon tick" acceptance criterion is satisfied by the same 60 s cadence. The sweep ignores the deacon pause toggle, because a scheduled prompt follows the operator-message rule (conversations are never gated).
- **D2 — Fire semantics: claim, then fire, at most once.** For each due schedule the sweep first claims it with `UPDATE ... SET next_run_at = <next>, last_run_at = <now> WHERE id = ? AND next_run_at = <expected> AND enabled = 1`. Only when that changed one row does it fire. A crash mid-fire loses that run rather than duplicating it.
- **D3 — No retries.** A failed fire (conversation missing, resume error, any non-2xx from delivery, including `409 permission-pending`) records `last_run_status = 'failed'` and `last_run_error = <message>` and waits for the next occurrence. A daily schedule blocked by a permission prompt must not retry 1,440 times.
- **D4 — Missed-run collapse falls out of D2.** The next occurrence is `nextRunAfter(cron, tz, now)`, strictly after the current wall clock, so a backlog of missed occurrences fires once.
- **D5 — Resume, then deliver.** If the harness is not alive (`conversationHarnessAlive(tmuxSession)` is false), the sweep calls `handleConversationResume(name, {}, { resolveSessionFile, resumeCause: 'message' })`, then `handleConversationMessage`. A live session is not resumed (resume would also bump `last_attached_at`).
- **D6 — Resume cause.** `handleConversationResume` gains an optional `resumeCause` on its `deps` argument. The sweep passes `'message'`. Existing callers are unchanged.
- **D7 — Follow-up, never steer.** The sweep passes `deliverAs: 'follow_up'` only for Pi harnesses and omits `deliverAs` for every other harness.
- **D8 — Prompt header.** The delivered text is `[Scheduled run · schedule <id> · <cron> · <timeZone>]\n\n<prompt>`. The header tells the agent why the message arrived, and because the text no longer starts with `/`, the composer-command router (`handleComposerCommandMessage`) never treats a stored prompt as a `/pan` command.
- **D9 — Storage format.** Store the 5-field cron and the IANA time zone. Reject anything that is not exactly 5 whitespace-separated fields (croner also accepts 6- and 7-field patterns and `@daily` nicknames; reject them). Reject a pattern with no future occurrence (croner returns `null`, for example `0 9 30 2 *`).
- **D10 — Default time zone.** The CLI and the API default to `Intl.DateTimeFormat().resolvedOptions().timeZone` of the process that creates the schedule (CLI and dashboard run on the same machine). The zone is stored on the row at creation. No new config key.
- **D11 — Minimum spacing 15 minutes.** Reject a recurrence whose next 24 occurrences (from now) include two less than 15 minutes apart. Message: `Schedules must be at least 15 minutes apart`. This is the cost guard: `* * * * *` on a frontier-model conversation would send 1,440 turns a day.
- **D12 — Model and effort.** A scheduled run uses the conversation's current model and effort (resume reads the stored ones). No per-schedule model or effort.
- **D13 — Reuse the conversation.** Each run goes to the same conversation, as in t3code. "A new conversation each run" is out of scope.
- **D14 — Eligibility.** Refuse to create a schedule on an agent conversation (`isAgentConversationName` in `src/lib/overdeck/conversations.ts` line 462: prefixes `agent-`, `planning-`, `specialist-`) with `409 code: 'agent-conversation'`, and on a Session Vault browse copy (`origin === 'vault'`) with `409 code: 'vault-browse-copy'`.
- **D15 — Archived conversations skip and advance.** A due schedule whose conversation is archived is claimed (advanced) and recorded as `last_run_status = 'skipped'`, `last_run_error = 'conversation archived'`. It never fires, and unarchiving does not trigger a catch-up run.
- **D16 — Paused schedules.** Pausing sets `enabled = 0`. Resuming sets `enabled = 1` and recomputes `next_run_at` from now, so pausing across a fire time never causes a catch-up run.
- **D17 — Superseded `/clear` rows.** At fire time, if the conversation is superseded (`isSupersededConversation`, `src/lib/overdeck/conversation-clear-chain.ts`), the sweep targets `resolveClearChainHead(conv)`. A broken chain (`null`) records `failed` with `conversation was cleared and its continuation is unavailable`.
- **D18 — Limits.** At most 20 schedules per conversation (`409 code: 'limit'`); prompt length 1–40,000 characters after trim (the header plus the prompt stays under the 50,000-character message cap).
- **D19 — Schedule ids are integers.** `id INTEGER PRIMARY KEY AUTOINCREMENT`, so the CLI can say `pan conv schedule rm 3`.
- **D20 — Dependency.** Add `"croner": "10.0.1"` (exact) to `dependencies` in `package.json` (not devDependencies: tsdown leaves `dependencies` external, so `dist/` needs it installed). Install with `bun add croner@10.0.1 --exact`. Version 11.0.0 was released 2026-10-26 and is too new.
- **D21 — CLI writes go through the dashboard when it is up.** `add`, `pause`, `resume`, `rm` call the routes (so later dashboard events fire), with the in-process door as the offline fallback, exactly like `link-pr`. `list` reads the door in-process.
- **D22 — `conversations.ts` must not grow.** `src/lib/overdeck/conversations.ts` is 1,222 lines, and its last allowlist row in `scripts/file-size-allowlist.txt` is exactly 1,222. All schedule queries live in the new door and join `conversations` by name, as the bookmarks door does.

## Requirements

### Functional

- **FR-1** — `overdeck.db` has a `conversation_schedules` table (schema in WI-2) on fresh and existing databases, deleted with its conversation (`ON DELETE cascade`).
- **FR-2** — A recurrence is a 5-field cron plus an IANA zone; invalid fields, invalid zones, patterns with no future occurrence and patterns with occurrences less than 15 minutes apart are rejected with a specific message.
- **FR-3** — Presets compile to cron: hourly → `0 * * * *`; daily `HH:MM` → `M H * * *`; weekdays `HH:MM` → `M H * * 1-5`; weekly `<day> HH:MM` → `M H * * <0-6>` (sun=0 … sat=6).
- **FR-4** — Next-occurrence computation is DST-correct in the schedule's zone and strictly after the reference instant.
- **FR-5** — The door creates, lists, updates (prompt, cron, zone, enabled), and removes schedules, and refuses agent conversations, vault copies, unknown conversations, and a 21st schedule.
- **FR-6** — `GET/POST /api/conversations/:name/schedules` and `PATCH/DELETE /api/conversations/:name/schedules/:id` expose the door with origin validation.
- **FR-7** — The sweep fires each due schedule at most once per occurrence, within 60 s of `next_run_at` while the dashboard runs, and advances `next_run_at` and `last_run_at`.
- **FR-8** — A fire on a conversation whose harness is not alive resumes it (cause `message`) and then delivers the prompt.
- **FR-9** — After downtime spanning several occurrences, the schedule fires once, not once per missed occurrence.
- **FR-10** — Paused schedules never fire; schedules on archived conversations are advanced and recorded `skipped`, never fired.
- **FR-11** — A failed fire records `last_run_status = 'failed'` and the error, and does not retry before the next occurrence.
- **FR-12** — `pan conv schedule add <conv> (--cron <expr> | --hourly | --daily <HH:MM> | --weekdays <HH:MM> | --weekly "<day> <HH:MM>") (--prompt <text> | --prompt-file <path>) [--tz <zone>] [--paused] [--json]` creates a schedule; `<conv>` accepts `self`/`.`/`current`/`me`, a conversation number, a name, or a unique title match.
- **FR-13** — `pan conv schedule list [conv] [--json]` prints every schedule (or one conversation's) with the next run formatted in the schedule's zone; `pause <id>`, `resume <id>`, `rm <id>` change one schedule.
- **FR-14** — Pi conversations receive scheduled prompts as `follow_up`; other harnesses receive a plain submit.
- **FR-15** — The user docs, the `pan-conversations` skill and the dashboard architecture doc describe schedules, the CLI verbs and the firing rules.

```ts
/**
 * PAN-4640: recurrence rules for conversation schedules. A schedule stores a
 * 5-field cron and an IANA time zone; presets are sugar compiled here. croner
 * is used only to parse and compute the next occurrence — always paused, so it
 * never arms a timer.
 */
import { Cron } from 'croner';

export const MIN_SCHEDULE_SPACING_MS = 15 * 60_000;
const SPACING_SAMPLE = 24;

export type SchedulePreset =
  | { kind: 'hourly' }
  | { kind: 'daily'; time: string }      // 'HH:MM', 24-hour
  | { kind: 'weekdays'; time: string }
  | { kind: 'weekly'; day: string; time: string }; // day: sun|mon|tue|wed|thu|fri|sat

export type RecurrenceCheck = { ok: true } | { ok: false; error: string };

export function defaultScheduleTimeZone(): string;
export function isValidTimeZone(zone: string): boolean;          // try new Intl.DateTimeFormat('en-US', { timeZone: zone }); RangeError ⇒ false
export function presetToCron(preset: SchedulePreset): string;    // throws Error on bad HH:MM or day
export function validateRecurrence(cron: string, timeZone: string, now: Date): RecurrenceCheck;
export function nextRunAfter(cron: string, timeZone: string, after: Date): Date | null;
```

3. `validateRecurrence` order: (a) `cron.trim().split(/\s+/).length !== 5` ⇒ `Cron expression must have exactly 5 fields (minute hour day-of-month month day-of-week)`; (b) `!isValidTimeZone` ⇒ `Unknown time zone: <zone>`; (c) `new Cron(cron, { timezone, paused: true })` throws ⇒ `Invalid cron expression: <croner message>`; (d) `nextRuns(SPACING_SAMPLE, now)` is empty ⇒ `Cron expression never fires`; (e) any consecutive gap in those runs `< MIN_SCHEDULE_SPACING_MS` ⇒ `Schedules must be at least 15 minutes apart`.
4. `nextRunAfter` returns `new Cron(cron, { timezone: timeZone, paused: true }).nextRun(after)` (croner returns the first occurrence strictly after `after`, or `null`).
5. `presetToCron`: parse `HH:MM` with `/^([01]\d|2[0-3]):([0-5]\d)$/`; drop leading zeros in the cron (`09:05` ⇒ minute `5`, hour `9`); days map `sun=0 … sat=6`, case-insensitive, three-letter only.

3. Rules:
   - `validateScheduleInput`: `prompt` must be a string, trimmed length 1–40,000; `cron` a string; `timeZone` defaults to `defaultScheduleTimeZone()` when absent; `enabled` defaults to `true`, else must be boolean; then `validateRecurrence(cron, timeZone, new Date(now))`.

   - `listDueSchedules` returns `archived = c.archived_at IS NOT NULL`.
   - `claimScheduleRun`: `UPDATE conversation_schedules SET next_run_at = ?, last_run_at = ?, enabled = CASE WHEN ? IS NULL THEN 0 ELSE enabled END, updated_at = ? WHERE id = ? AND next_run_at = ? AND enabled = 1`; return `changes === 1`.
