# PAN-5184: Composer keeps sent text and blocks a second send until the server acknowledges

**Issue:** https://github.com/eltmon/overdeck/issues/5184
**Status:** planned (auto mode, 2026-11-13)
**Base:** `main` @ `5d4bacc78e9`

## Glossary

- **Composer** — `ComposerFooter` (`src/dashboard/frontend/src/components/chat/ComposerFooter.tsx`), the message box under a conversation. Its editor is Lexical (`ComposerPromptEditor.tsx`).
- **Prompt send** — a Send whose text does not start with `/pan` (`isPortableCommand` is false). It renders an optimistic bubble through `onSend` and POSTs to `/api/conversations/:name/message` (or `/api/agents/:id/message` when `agentId` is set).
- **`/pan` command** — a Send whose text matches `/^\/pan(?:\s|$)/i`. The dashboard control plane answers it with a structured `ComposerCommandResult`. It never renders an optimistic bubble. **Unchanged by this issue.**
- **Optimistic bubble** — a `ChatMessage` in `composerStore` slice `optimistic[]`, added by `addOptimistic` (via `useStableComposerProps.onSend`). Its `deliveryState` shows "Sending…" (`pending`), "Delivery not confirmed" (`unknown`), "Sent · waiting for transcript" (`accepted`), `held`, and so on.
- **Outbox** — slice `failed[]` in `composerStore`, rendered by `MessagesTimeline.tsx` (search `Failed message outbox`) with Retry/Resend (when `retryable !== false`), Copy (prompts) and Discard.
- **Held bubble** — a bubble with `deliveryState: 'held'`: the server answered 409 `permission-pending`, so nothing was pasted. `useHeldMessageRelease` (`App/hooks/useHeldMessageRelease.ts`) calls `releaseHeld` once the permission prompt is gone; `releaseHeldMessages` resends held bubbles in array order.
- **Send queue** — NEW. A per-conversation promise chain (`lib/composerSendQueue.ts`). A task added for conversation X starts only after every earlier task for X has settled (resolved or rejected).
- **`sending` flag** — `ComposerSlice.sending` in `composerStore`, read by `useConversationSending`. It drives `isDisabled` in `ComposerFooter` (editor read-only, attach/voice/model picker disabled, paste and drop ignored).
- **Draft** — `localStorage['conv-draft:<name>']`, written by `ComposerPlugin` in `ComposerPromptEditor.tsx` with a 300 ms debounce, plus flushes on unmount and `pagehide`.
- **`TURN_STALL_MS`** — 4 minutes (`lib/workingPhase.ts`). `useComposerEchoes.ts` marks a pending bubble `unknown` and moves an `accepted` bubble to the outbox ("Not found in transcript") once it is older than this, counted from the bubble's `createdAt`.

## Problem

After Send, the sent text stays in the composer until the server acknowledges the POST, and the composer refuses a second Send until then. A busy agent can take seconds, up to the client's 120 s request bound, to acknowledge. The operator cannot quickly send a follow-up, and the text appears twice: once in the "Sending…" bubble and once in the box.

Operator report (2026-11-13, conv-flywheel): "when I send something, it stays in composer so I cant quickly add another message to the chat".

## Root cause (verified against `5d4bacc78e9`)

1. `ComposerFooter.tsx` line 182: `const isDisabled = !conversation.sessionAlive || sending;`. `handleSubmit` (line 400) returns early when `isDisabled`. The editor gets `disabled={isDisabled}` (search `<ComposerPromptEditor`), so it is read-only during a send.
2. `ComposerFooter.tsx` line 492: `setSendingFor(submitConversationName, true);` runs for every send, and the `finally` at the end of `handleSubmit` resets it only after `await sendConversationMessage(...)` settles.
3. `ComposerFooter.tsx` lines 603–608: the editor is cleared only after the POST resolves:
   ```ts
   if (submitConversationName === currentConversationNameRef.current) {
     editor.update(() => {
       $getRoot().clear();
     });
     setText('');
   }
   ```
4. `lib/composerSend.ts` (search `setTimeout(() => controller.abort(), 120_000)`): one POST may take up to 120 s.

## Requirements

### Functional

- **FR-1** On a prompt send, the composer editor is empty and the `conv-draft:<name>` key is gone from `localStorage` synchronously inside `handleSubmit`, after `onSend` added the optimistic bubble and before the POST settles.
- **FR-2** A prompt send never sets the `sending` flag. While earlier prompt sends are in flight, the editor stays editable and Send accepts a new prompt.
- **FR-3** Composer prompt POSTs for one conversation run one at a time, in Send order: POST N+1 starts only after POST N has settled (success or failure). A failed or timed-out POST never stops later POSTs.
- **FR-4** A failed prompt send moves to the outbox (`onSendFailed` → `failSend`) and is not put back in the composer. Text typed after Send is never cleared by an earlier send settling.
- **FR-5** Uploaded attachments and citations are consumed at Send time (attachments: `consumeAttachments` right after `onSend`; citations: unchanged, `consumeCitations` already runs before the POST).
- **FR-6** `/pan` commands, the held-kickoff Send (PAN-4499) and the "when limits reset" schedule Send (PAN-4641) keep today's behavior: they set `sending`, keep the text until their round trip succeeds, and do not use the send queue.
- **FR-7** A queued prompt is held, without a POST, when an earlier bubble of the same conversation is `held`, so a permission-prompt hold never lets a later message overtake an earlier one. `releaseHeldMessages` sends each held bubble through the send queue.
- **FR-8** `retryFailed` sends its POST through the send queue, so a retry waits for in-flight composer sends of the same conversation.
- **FR-9** When a queued prompt's POST starts, its bubble's `createdAt` resets to now (and `unknown` returns to `pending`), so time spent waiting in the queue never counts toward `TURN_STALL_MS`.
- **FR-10** An outbox Retry of a failure whose response said `deliveryUnknown: false` (the server proved nothing was delivered) sends a fresh `clientMessageId` with no `retry` flag, so the server's receipts cache cannot replay the old rejection.

### Non-functional

- **NFR-1** `ComposerFooter.tsx` stays at or under 1000 lines (`scripts/lint-file-size.sh` fails any file above 1000 lines that has no allowlist row; it has none, and agents must not add one).
- **NFR-2** When a conversation's queue is empty, a new task starts synchronously (the POST's `fetch` is called inside the same `handleSubmit` call), so single-send timing and existing tests that assert `fetch` right after Send keep working.
- **NFR-3** Any delay-based test uses `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()` (repo rule `fake-timers-for-retry-tests`). No real waits.
- **NFR-4** Every new frontend test file is added to `scripts/frontend-test-subset.txt` in sorted position (CI runs only listed frontend files; the file is `merge=union`).

## Decisions

- **D1 — Queue lives in a new module, `lib/composerSendQueue.ts`.** It holds no React or Zustand state, only a `Map<string, Promise<void>>` of tails. `resetComposerStore()` calls its test reset. Reason: unit-testable alone, and it keeps `ComposerFooter.tsx` under NFR-1.
- **D2 — Queue key is the conversation name** (`conversation.name`), the same key drafts and `composerStore` slices use. Agent-backed panels use the same key.
- **D3 — The queue entry is a fully composed payload.** Upload checks, the offline hold (`isServerWriteBlocked`), citation and attachment consumption, `clientMessageId` and `deliverAs` are all resolved before enqueue. Only the hold-behind check (FR-7), the clock reset (FR-9), and the POST and its outcome run inside the task.
- **D4 — `/pan` commands bypass the queue** (FR-6). They are answered by the dashboard control plane and never reach the harness transcript, so ordering against prompts does not matter, and queuing them would make a command wait up to 120 s per earlier prompt.
- **D5 — Steer sends (`deliverAs: 'steer'`, Ctrl/Cmd+Enter) are queued like any prompt.** Delivering a steer before an earlier in-flight prompt would reorder the operator's messages.
- **D6 — Focus moves to the synchronous clear.** `editor.focus()` runs once, at Send. Nothing focuses the editor when a queued POST settles, because the operator may be typing or working elsewhere by then.
- **D7 — The prompt POST and its outcome move into `components/chat/queuedPromptSend.ts`** (`deliverQueuedPrompt`). `ComposerFooter` passes it the captured props (callbacks, `agentId`, `deliverAs`, an `openUi` callback). The captured callbacks are store or query-client calls, so they stay valid after the composer unmounts.
- **D8 — An explicit `clearDraft(name)` runs at Send** in addition to the editor clear. The editor clear already schedules `saveDraft('')` through the debounce, but a crash or kill inside that 300 ms window fires no `pagehide`. Draft helpers move to `lib/composerDraft.ts` so `ComposerFooter` imports `clearDraft` from a module the `ComposerFooter` tests do not mock (every test file mocks `../ComposerPromptEditor` with only `loadDraft` and the component).
- **D9 — Doc consequence of FR-4.** Today a rejected send (for example 409 `input-target-not-main`) leaves the text in the editor, and `docs/DASHBOARD-ARCHITECTURE.md` says "the draft stays in the editor". After this change the text is only in the outbox. `input-target-not-main` is `retryable: true, deliveryUnknown: false` (`src/lib/overdeck/conversation-message.ts`, search `code: 'input-target-not-main'`), so the outbox offers Retry; a non-retryable rejection such as 422 `steer-unsupported` offers Copy and Discard. The doc sentence is corrected in WI-8.
- **D10 — Retry after a proven non-delivery uses a fresh identity (FR-10).** `withConversationMessageReceipt` (`src/dashboard/server/services/conversation-message-receipts.ts`) caches every response, including a 409, under `(name, clientMessageId)` for 24 h, and `retryFailed` reuses the old id with `retry: true` for every code except `not-delivered` and not-found-in-transcript. So today a Retry of `input-target-not-main` replays the same 409. This mattered little while the text stayed in the editor (a fresh Send minted a new id); after FR-4 the outbox is the only recovery path. A response with `deliveryUnknown: false` proves nothing was pasted, so a fresh send cannot duplicate it. Fixed in WI-9.

### WI-1 — Per-conversation send queue (`lib/composerSendQueue.ts`) — FR-3, NFR-2

New file `src/dashboard/frontend/src/lib/composerSendQueue.ts`:

```ts
/**
 * Per-conversation send queue (PAN-5184).
 *
 * The composer clears on Send and lets the operator send again at once, so
 * several POSTs for one conversation can be pending together. This chain runs
 * them one at a time, in the order they were enqueued: a task starts only after
 * every earlier task for the same conversation has settled. A rejected task
 * never blocks the ones behind it. With an empty queue a task starts
 * synchronously, so a single send keeps its old timing.
 *
 * Never enqueue from inside a running task for the same conversation: the inner
 * task waits for the outer one, which waits for the inner one.
 */
const tails = new Map<string, Promise<void>>();

export function enqueueConversationSend<T>(conversationName: string, task: () => Promise<T>): Promise<T> {
  const previous = tails.get(conversationName);
  const run = previous ? previous.then(() => task()) : (async () => task())();
  const tail = run.then(() => undefined, () => undefined);
  tails.set(conversationName, tail);
  void tail.then(() => {
    if (tails.get(conversationName) === tail) tails.delete(conversationName);
  });
  return run;
}

/** Test-only: drop every pending tail. */
export function resetConversationSendQueues(): void {
  tails.clear();
}
```

```ts
import { toast } from 'sonner';
import type { ComposerCommandResult } from '@overdeck/contracts';
import { MessageSendError, sendConversationMessage, sendFailureDetails, useComposerStore, type SendFailureDetails } from '../../lib/composerStore';

export interface QueuedPrompt {
  conversationName: string;
  message: string;
  clientMessageId: string;
  agentId?: string;
  deliverAs?: 'steer' | 'follow_up';
  onAcknowledged?: (text: string, clientMessageId?: string) => void;
  onFailed?: (text: string, kind: 'command' | 'prompt', details?: SendFailureDetails) => void;
  /** The server asked the dashboard to open a dialog (handoff/fork) instead. */
  onOpenUi: (action: Extract<ComposerCommandResult, { kind: 'ui' }>['action'], focus?: string) => void;
}

/** Runs inside the conversation's send queue (PAN-5184). Never touches the editor. */
export async function deliverQueuedPrompt(prompt: QueuedPrompt): Promise<void> {
  const { conversationName: name, message, clientMessageId } = prompt;
  // FR-7: never overtake an earlier message held behind a permission prompt.
  if (useComposerStore.getState().holdBehindHeld(name, clientMessageId)) return;
  // FR-9: time spent waiting in the queue does not count toward TURN_STALL_MS.
  useComposerStore.getState().markSendStarted(name, clientMessageId);
  try {
    const result = await sendConversationMessage(name, message, prompt.agentId, prompt.deliverAs, undefined, {
      clientMessageId,
      // PAN-4292 NFR-4: never let a steer degrade to a queued message silently.
      onSteerDegraded: (reason) => toast.warning(`Sent without interrupting: ${reason}`),
    });
    if (result?.kind === 'ui') prompt.onOpenUi(result.action, result.args.focus || undefined);
    else if (result) useComposerStore.getState().addCommandResult(name, message, result);
    else prompt.onAcknowledged?.(message, clientMessageId);
  } catch (err) {
    // PAN-4278: a permission prompt is up, so the server pasted nothing.
    if (err instanceof MessageSendError && err.code === 'permission-pending') {
      useComposerStore.getState().hold(name, clientMessageId);
      return;
    }
    console.error('[ComposerFooter] Failed to send:', err);
    toast.error(err instanceof Error ? err.message : 'Failed to send message');
    prompt.onFailed?.(message, 'prompt', { ...sendFailureDetails(err), clientMessageId, deliverAs: prompt.deliverAs });
  }
}
```

(The exact `onOpenUi` action type follows `ComposerCommandResult`'s `ui` variant in `@overdeck/contracts`; if `Extract<…>` does not type-check, use `'handoff' | 'fork'`, the values `isComposerCommandResult` accepts.)
