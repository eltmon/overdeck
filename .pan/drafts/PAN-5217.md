# PAN-5217 — Flywheel page: Needs-you rows nest buttons inside a button role

**Issue:** [PAN-5217](https://github.com/eltmon/overdeck/issues/5217)
**Origin:** CodeRabbit Major finding on PR [#5203](https://github.com/eltmon/overdeck/pull/5203) (PAN-5198), merged without the fix.
**Rule:** W3C ACT rule 307n5z, "Element with presentational children has no focusable content" — https://www.w3.org/WAI/standards-guidelines/act/rules/307n5z/

## Glossary

- **Needs-you block** — the warning-bordered `<div role="group" aria-label="Needs you" data-testid="flywheel-needs-you">` on the Flywheel page's Status tab. It lists the items from the loop's last tick `needs-you=` line, one `<li>` per item.
- **Needs-you row** — one `<li data-testid="flywheel-needs-you-item">` inside that block. Its text is split into segments by `needsYouSegments()` (`src/dashboard/frontend/src/lib/flywheelNeedsYouLinks.ts`): plain text, issue IDs (rendered as `<button data-testid="flywheel-needs-you-issue">`) and known PRs (rendered as `<a data-testid="flywheel-needs-you-pr">`).
- **Jump** — the row action "show the message that raised this". `FlywheelStatusPane` calls the `onNeedsYouClick(messageId)` prop. `FlywheelPage.handleNeedsYouClick` then calls `resolveNeedsYouAction()`. It reopens the flywheel conversation's pending AskUserQuestion when one is open; otherwise it scrolls the conversation pane to `messageId`, or to the newest tick message when `messageId` is undefined.
- **Jump button** — the new native `<button type="button">` this issue adds to each row to carry the jump action.
- **Presentational children** — ARIA's `button` role (implicit on `<button>`, explicit through `role="button"`) has children-presentational semantics. Assistive technology may flatten its descendants, so a focusable descendant (a nested button or link) loses its own name and role.

## Problem

Each needs-you row is an `<li role="button" tabIndex={0}>` with row-level `onClick` and `onKeyDown`, and it wraps the issue `<button>`s and PR `<a>`s. That is a button containing buttons and links: invalid nesting under ACT 307n5z. The `stopPropagation` calls on the inner controls stop the row from firing a jump on a click, but they do not fix focus or naming in browser and screen-reader combinations that flatten button descendants.

Current code, `src/dashboard/frontend/src/components/flywheel/FlywheelStatusPane.tsx` lines 146–196 (grep anchor: `role="button"`):

```tsx
{needsYouRows(tick).map((row) => (
  <li
    key={row.key}
    role="button"
    tabIndex={0}
    data-testid="flywheel-needs-you-item"
    title="Show the message that first raised this, or the question the flywheel is waiting on"
    className="cursor-pointer rounded-sm hover:bg-warning/[0.14]"
    onClick={() => onNeedsYouClick?.(row.messageId)}
    onKeyDown={(e) => {
      if (e.key === 'Enter' || e.key === ' ') {
        e.preventDefault();
        onNeedsYouClick?.(row.messageId);
      }
    }}
  >
    {needsYouSegments(row.text, status.inFlight).map((segment, i) => {
      if (segment.kind === 'issue') {
        return (
          <button
            key={i}
            type="button"
            className="font-mono text-foreground hover:underline"
            data-testid="flywheel-needs-you-issue"
            onClick={(e) => { e.stopPropagation(); onNavigateIssue?.(segment.issueId); }}
            onKeyDown={(e) => { if (e.key === 'Enter' || e.key === ' ') e.stopPropagation(); }}
          >
            {segment.text}
          </button>
        );
      }
      if (segment.kind === 'pr') {
        return (
          <a
            key={i}
            href={segment.url}
            target="_blank"
            rel="noreferrer"
            className="font-mono hover:underline"
            data-testid="flywheel-needs-you-pr"
            onClick={(e) => e.stopPropagation()}
            onKeyDown={(e) => { if (e.key === 'Enter' || e.key === ' ') e.stopPropagation(); }}
          >
            {segment.text}
          </a>
        );
      }
      return <span key={i}>{segment.text}</span>;
    })}
  </li>
))}
```

## Requirements

- **FR-1** — The needs-you `<li>` is non-interactive. It has no `role` attribute, no `tabIndex`, no `onClick`, no `onKeyDown`, no `title`, and no `cursor-pointer` or hover-background classes. It keeps `key={row.key}` and `data-testid="flywheel-needs-you-item"`.
- **FR-2** — Each row renders exactly one jump button: a native `<button type="button">` with `aria-label="Show where this was raised"`, `data-testid="flywheel-needs-you-jump"`, and `title="Show the message that first raised this, or the question the flywheel is waiting on"`. It is the first child of the `<li>`, beside the text and never around it. Its only content is a lucide-react `MessageSquare` icon with `aria-hidden="true"`. Activating it calls `onNeedsYouClick?.(row.messageId)`.
- **FR-3** — The jump button renders on every row, including rows where `row.messageId` is undefined and panes rendered without an `onNeedsYouClick` prop.
- **FR-4** — The issue buttons and PR links keep their own focus and activation and carry no `stopPropagation` and no `onKeyDown` handler. An issue button calls `onNavigateIssue?.(segment.issueId)` directly; a PR link has no `onClick`.
- **FR-5** — Pending-question priority does not change. `resolveNeedsYouAction()` (`src/dashboard/frontend/src/lib/flywheelNeedsYou.ts`) and `FlywheelPage.handleNeedsYouClick` (`src/dashboard/frontend/src/pages/FlywheelPage.tsx` lines 74–83) are not edited, and the FlywheelPage tests still prove reopen-before-jump through the jump button.
- **FR-6** — In the rendered Status pane, no element with the button role (native `<button>` or `[role="button"]`) contains a `button`, `a`, `[role="button"]` or `[role="link"]` descendant.
- **FR-7** — `docs/FLYWHEEL.md` and `changelog.d/pan-5217.md` describe the jump button instead of a clickable row.
- **NFR-1** — No visual change to the row text. Segments still render inline in the same order with the same classes. The block container (`data-testid="flywheel-needs-you"`) is untouched, because `FlywheelPage.tsx` line 102 queries it for the reveal scroll.
- **NFR-2** — Follow the dashboard style guide (`pan-style-guide`): the icon button is muted (`text-muted-foreground`, `hover:text-foreground`), no decorative color, no pill shape.

## Decisions

- **D-1: Leading icon button.** The jump button is the `<li>`'s first child, so the buttons line up in one column and the tab order in a row is jump, then issue buttons and PR links in text order. Placing it after the text was rejected because the buttons would move with each row's text length.
- **D-2: Icon `MessageSquare` from `lucide-react`.** It is installed (`node_modules/lucide-react/dist/esm/icons/message-square.js`) and already used in the dashboard (`components/CommandDeck/ActivityView/AgentSection.tsx`). `lucide-react` is already imported in this directory (`FlywheelConversationPane.tsx` line 10). Size: `className="h-3 w-3"`.
- **D-3: Always render the jump button (FR-3).** The page handler's reopen-question path needs no message id, and the handler falls back to the newest tick's id when `messageId` is undefined. A conditional button would remove the only way to reopen the question from a row.
- **D-4: Keep `data-testid="flywheel-needs-you-item"` on the `<li>`.** Tests use it to count rows and read row text. The jump action gets its own testid, `flywheel-needs-you-jump`.
- **D-5: Retarget the existing tests, do not delete them.** Every test that clicks the `<li>` today clicks the jump button instead. The `keyDown(row, { key: 'Enter' })` assertion is dropped, because a native button activates on Enter and Space without a handler and jsdom's `fireEvent.keyDown` does not synthesize a click.
- **D-6: The no-nesting test is render-based.** It walks `screen.getAllByRole('button')` in a rendered pane whose needs-you item contains an issue ID and a known PR. Against current `main` it fails, because the `<li role="button">` contains the issue button and the PR link. It never reads source text: the lint gate rejects new source-reading tests.
- **D-7: Two plan items with no edge.** The component change and both test files are one item, because changing the component without retargeting `FlywheelPage.test.tsx` leaves CI red (both files are in `scripts/frontend-test-subset.txt`, lines 267 and 366). The docs item touches different files and can run in parallel.
