# PAN-5461 — Computer use: Settings page with one-click setup, and the platform provider seam

**Issue:** [PAN-5461](https://github.com/eltmon/overdeck/issues/5461)
**Follows:** PAN-5452 (the `pan computer` CLI, merged in #5457)
**Siblings that build on this:** PAN-5462 (Windows via WSL2), PAN-5463 (macOS)
**Mockup (operator-approved 2026-11-17):** `.tmp/computer-use-settings/index.html` in the primary checkout (gitignored). Screens are described in WI-6 so the executor does not need the file.

## Summary

PAN-5452 shipped `pan computer` (Linux only), the global `computer_use.enabled` flag, a `pan doctor` check and the `pan-computer-use` skill. Turning it on still means hand-editing `~/.overdeck/config.yaml`, and the readiness checks only exist inside `pan doctor`, which reports nothing while the feature is off.

This issue adds **Settings → Computer Use**: one button installs any missing system packages, turns on GNOME accessibility, sets `computer_use.enabled: true`, and tests the helper. It also introduces the **platform provider seam** (`src/lib/computer-use/platform.ts`) so PAN-5462 and PAN-5463 add Windows and macOS as providers instead of editing `if (platform !== 'linux')` branches.

## Glossary

- **Host**: the machine running the Overdeck dashboard server. Every status on the page describes the host's desktop, never the device the browser runs on (the dashboard can be opened from a phone).
- **Provider**: an object implementing `ComputerUseProvider` (WI-1) for one platform: it detects the desktop session, reports readiness, runs setup steps, and runs the helper. This issue ships one provider, `linux`.
- **Platform id**: `'linux' | 'wsl' | 'darwin'`, from `detectPlatform()` (WI-1). `'wsl'` is Linux running under WSL2 (`WSL_DISTRO_NAME` set, or `/proc/sys/kernel/osrelease` contains `microsoft`, case-insensitive).
- **Readiness check**: one row of the "What Overdeck checked" list: `{ id, label, status, detail, fixCommand? }`, `status` ∈ `ok | action | missing | unavailable`.
- **Setup step**: one action the Setup button runs: `install-packages`, `enable-accessibility`, `enable-flag`, `test-helper`. Steps already satisfied are skipped.
- **Desktop lease**: PAN-5452's single-holder lock on input (`~/.overdeck/computer-use/lease.json`, 120 s TTL), read with the new `readLease()` export (WI-2).
- **Settings door**: a path-scoped writer that edits only named YAML paths in `~/.overdeck/config.yaml` with `doc.setIn`, preserving comments. Pattern: `src/lib/semgrep/settings.ts`.
- **Mutation guard**: `rejectUnsafeDashboardMutationRequest(request)` from `src/dashboard/server/routes/dashboard-auth.ts`, used by every mutating route.
- **Admin-only route**: a route with no row in `src/dashboard/server/route-scopes.ts`; unlisted routes need `admin` (comment at the top of that file).

## Decisions

- **D-1 One button, not a checklist of fixes.** The page has a single primary action ("Set up and turn on", or "Turn on Computer Use" when nothing is missing). The readiness checks sit in a collapsed "What Overdeck checked" list. Individual fix buttons are not shipped (operator feedback 2026-11-17: "it should just be one click").
- **D-2 Package installs use the OS's own password prompt.** On Linux the server runs `pkexec <pkgmgr> install -y <fixed list>` so the desktop's polkit dialog asks for the password once. Overdeck never sees the password. See the WI-4 implementation checkpoint for the fallback.
- **D-3 The package list is fixed server-side.** The setup route never takes package names, commands or paths from the request body. The body is empty.
- **D-4 Supported package managers for one-click install:** `apt-get` (python3-gi gir1.2-atspi-2.0 xdotool xclip; plus grim on Wayland), `dnf` (python3-gobject at-spi2-core xdotool xclip; plus grim), `pacman` (python-gobject at-spi2-core xdotool xclip; plus grim). Any other manager (zypper, apk, none) gets no install step; setup stops at that step and shows the per-manager command from `getLinuxManualInstallHint`-style text in the failure message.
- **D-5 GNOME accessibility is turned on without a password:** `gsettings set org.gnome.desktop.interface toolkit-accessibility true`, run with the session env from `resolveDesktopEnv()` (it needs `DBUS_SESSION_BUS_ADDRESS`). Skipped when `gsettings` is not on PATH (non-GNOME desktops), and the check row reads `ok` with detail "not GNOME".
- **D-6 Readiness runs whether or not the feature is on.** The logic moves out of `src/cli/commands/doctor-computer-use.ts` into `src/lib/computer-use/readiness.ts` (provider method). `pan doctor` keeps its current behavior (no rows while off) by wrapping it.
- **D-7 Status refresh never waits behind an agent.** The page's readiness call runs the helper handshake only if the desktop lock is free within 2 s; otherwise the `test-helper` check reports `ok` with detail "skipped: an agent is using the desktop". Implement with a new `tryWithDesktopLock(fn, { waitMs: 2000 })` in `lease.ts` that returns `{ acquired: false }` instead of waiting. The Setup button's `test-helper` step waits normally (up to 30 s) because the operator asked for it.
- **D-8 Routes are admin-only.** No `route-scopes.ts` rows. Mutations call the mutation guard. An agent's scoped token can't turn computer use on.
- **D-9 WSL is detected and refused until PAN-5462.** `detectPlatform()` returns `'wsl'` under WSL2 and `providerFor('wsl')` returns `null` in this issue, so the page shows "Not available on this machine" and `pan computer` refuses with `unsupported_platform`. Reason: WSLg gives Linux GUI apps a display, so without this the Linux provider would drive WSLg windows instead of the Windows desktop.
- **D-10 The seam is owned here.** `platform.ts`'s types are specified verbatim in WI-1. PAN-5462 and PAN-5463 add providers by registering them in `providerFor`; they must not change the interface without updating this PRD's text in their own PR.
- **D-11 "Turn off" is a plain switch** once the feature is on. Turning off does not uninstall packages or turn GNOME accessibility back off.
- **D-12 The `disabled` error names the page.** New text: `Computer use is off. Turn it on in the dashboard under Settings → Computer Use, or set computer_use: { enabled: true } in ~/.overdeck/config.yaml.`

## Requirements

### Functional
- **FR-1** `detectPlatform()` returns `'linux'`, `'wsl'`, `'darwin'` or `'unsupported'` as defined in the Glossary; `providerFor(id)` returns the registered provider or `null`.
- **FR-2** Every `pan computer` command resolves its provider through `providerFor(detectPlatform())`; a `null` provider throws `unsupported_platform` with the existing message shape (`Computer use isn't supported on this host (<platform>) yet.`).
- **FR-3** The Linux provider's `readiness()` returns these checks in order: `session` (Desktop session), `atspi` (Accessibility bindings), `gnome-a11y` (GNOME accessibility), `input` (Mouse and keyboard input, xdotool, X11 only; `ok` with detail "Wayland: not used" on Wayland), `screenshots` (built in on X11; grim on Wayland), `clipboard` (xclip, xsel or wl-copy), `helper` (handshake). Same probes as today's doctor check.
- **FR-4** `GET /api/computer-use/status` returns `{ platform, supported, enabled, hostname, session, checks[], setupSteps[], lease, skill }` (shape in WI-3). Readiness follows D-7.
- **FR-5** `POST /api/computer-use/setup` runs the needed setup steps in order and returns `{ ok, steps: [{ id, label, status: 'done'|'skipped'|'failed'|'waiting', message?, command? }], status }`. It stops at the first `failed` or `waiting` step. It only turns the flag on if every earlier step succeeded.
- **FR-6** `PUT /api/computer-use/settings` with `{ enabled: boolean }` writes `computer_use.enabled` through a settings door and returns the new status.
- **FR-7** `POST /api/computer-use/release` force-releases the desktop lease and returns the new status.
- **FR-8** Settings shows a "Computer Use" nav item directly after "Security", rendering the section described in WI-6.
- **FR-9** The command palette offers "Open Computer Use settings" (keywords: computer, desktop, automation, screen).
- **FR-10** `pan computer` commands that fail with `disabled` print the D-12 message.
- **FR-11** `pan doctor` output is unchanged in content (still no rows while off) after the refactor.

### Non-functional
- **NFR-1** No `execSync`/`spawnSync` in any code reachable from the dashboard server (repo rule `no-execsync-server`). Use `execFile` promisified, as `doctor-computer-use.ts` does today.
- **NFR-2** The status route answers in under 3 s when the lock is held (D-7) and probes run in parallel where independent.
- **NFR-3** Tests that exercise timeouts or polling use `vi.useFakeTimers()` (repo rule `fake-timers-for-retry-tests`).
- **NFR-4** UI follows `pan-style-guide`: Broadsheet vocabulary, badge tint 8%/32%, `rounded-md` badges (no pills), amber = operator must act, emerald = outcome, blue = machine working, no `font-bold`/`font-semibold`, switch tracks use `.switch-track-on`, no new `useMemo`/`useCallback`/`memo` (React Compiler).
- **NFR-5** No file in `src/` passes 1000 lines (`lint:file-size`). `doctor.ts`, `schema.ts` and `index.ts` are already near their allowlist rows; this issue adds no lines to them beyond imports.

Create `platform.ts` with exactly these exported types (D-10):

```ts
export type ComputerUsePlatformId = 'linux' | 'wsl' | 'darwin';

export type ReadinessStatus = 'ok' | 'action' | 'missing' | 'unavailable';

export interface ReadinessCheck {
  id: string;
  label: string;
  status: ReadinessStatus;
  /** One short sentence, e.g. "x11 · display :1" or "Not importable". */
  detail: string;
  /** Shown only when setup can't do it for the operator. */
  fixCommand?: string;
}

/** A session the provider resolved; opaque to callers except `label`. */
export interface ProviderSession {
  label: string;               // e.g. "x11 · display :1"
  env: NodeJS.ProcessEnv;      // env the helper runs with
}

export type SetupStepId = 'install-packages' | 'enable-accessibility' | 'grant-permissions' | 'enable-flag' | 'test-helper';

export interface SetupStep {
  id: SetupStepId;
  label: string;               // e.g. "Install xdotool, xclip"
  needsPassword?: boolean;     // shows "your system will ask for your password once"
}

export interface SetupStepResult {
  /** 'waiting' = the operator must act outside Overdeck (e.g. macOS permission toggles); setup stops and the button becomes "Continue". */
  status: 'done' | 'skipped' | 'failed' | 'waiting';
  message?: string;            // failed/waiting: what happened + what to do
  command?: string;            // a shell command the operator can copy (shown with a Copy button)
}

export interface ReadinessReport {
  session: { ok: true; label: string } | { ok: false; message: string };
  checks: ReadinessCheck[];
  /** Steps the Setup button would run now, in order. Empty when ready. Never includes enable-flag (the route adds it). */
  setupSteps: SetupStep[];
}

export interface ComputerUseProvider {
  id: ComputerUsePlatformId;
  resolveSession(): Promise<{ ok: true; session: ProviderSession } | { ok: false; code: 'no_desktop_session'; message: string }>;
  readiness(options: { probeHelper: 'wait' | 'if-free' }): Promise<ReadinessReport>;
  runSetupStep(id: Exclude<SetupStepId, 'enable-flag' | 'test-helper'>): Promise<SetupStepResult>;
  runHelper(operation: Record<string, unknown>, session: ProviderSession): Promise<HelperResponse>;
  /** Blocked shortcut rules for this platform (see blocked-key-combos.ts). */
  blockedKeyPlatform: 'linux' | 'windows' | 'mac';
}

export function detectPlatform(deps?: { platform?: NodeJS.Platform; env?: NodeJS.ProcessEnv; readOsRelease?: () => string | null }): ComputerUsePlatformId | 'unsupported';
export function providerFor(id: ComputerUsePlatformId | 'unsupported'): ComputerUseProvider | null;
```

### WI-4 One-click setup
**Files:** new `src/lib/computer-use/setup.ts`; `providers/linux.ts` (`runSetupStep`); tests `src/lib/computer-use/__tests__/setup.test.ts`, `providers-linux-setup.test.ts`.

`runSetup(deps)`:
1. Build status with `probeHelper: 'if-free'`. If `!supported` or no session → return `{ ok: false, steps: [] , status }` with message "Computer use isn't available on this host."
2. For each provider step in order: call `provider.runSetupStep(id)`. Stop on `failed`.
3. If all earlier steps passed and `enabled` is false → `saveComputerUseSettings({ enabled: true })` as the `enable-flag` step.
4. `test-helper` step: `withDesktopLock(() => provider.runHelper({ tool: 'handshake' }, session))` with a 30 s cap. A failure here leaves the flag on (the operator can turn it off) and reports the helper error message.
5. Return the step list and the fresh status.

Only one setup may run at a time: guard with a module-level in-flight promise; a second POST while one runs gets 409 `{ error: 'Setup is already running' }`.

Linux `runSetupStep`:
- `install-packages`: `execFile('pkexec', [pmPath, ...installArgs, ...packages], { env: session.env, timeout: 10 * 60_000 })` where `pmPath` is the absolute path of the detected manager (`/usr/bin/apt-get` etc., resolved with `which`), `installArgs` is `['install','-y']` for apt-get/dnf and `['-S','--noconfirm','--needed']` for pacman. For apt-get, the D-4 packages only; never `apt-get update` (keeps it one prompt; if install fails with "Unable to locate package", the failure message tells the operator to run `sudo apt-get update` first). pkexec exit 126 = the operator cancelled or auth failed → `failed`, message "The password prompt was cancelled. Try again, or run: sudo <cmd>". Exit 127 = no authentication agent → apply the checkpoint fallback.
- `enable-accessibility`: `execFile('gsettings', ['set','org.gnome.desktop.interface','toolkit-accessibility','true'], { env: session.env })`. Note: newly started apps pick this up; already-running apps may need a restart — say so in the step's done message ("Done. Apps opened before this need a restart to show their contents.").

**Implementation checkpoint (pkexec from a systemd user service).** The dashboard runs as a systemd user unit (`overdeck-dashboard-*.service`), not inside the graphical login session, and polkit may find no authentication agent for it (pkexec exits 127 with "No authentication agent found"). Verify on the operator's desktop by running the real setup route with a harmless package that is already installed (WI-8) and observing whether a polkit dialog appears. **Fallback if it doesn't:** launch a terminal window in the desktop session that runs the install with sudo and keeps the window open: try in order `gnome-terminal -- bash -c '<cmd>; echo; read -p "Press Enter to close"'`, `x-terminal-emulator -e bash -c '…'`, `konsole -e …`, `xterm -e …`, all with `session.env`. The step then returns `failed` with message "A terminal window opened to install the packages. Enter your password there, then press Set up again." If no terminal can be launched, return `failed` with the `sudo …` command. Record which path shipped in the PR description.
