# PAN-2426 — Adapt to upstream xBRIEF v0.8 (vBRIEF renamed to xBRIEF)

**Issue:** https://github.com/eltmon/overdeck/issues/2426
**Status:** draft
**Author:** Claude (Fable 5), 2026-07-06
**Upstream:** https://github.com/deftai/xBRIEF — spec v0.8.0, `docs/xbrief-spec-0.8.md`

---

## Glossary

- **vBRIEF / xBRIEF** — the open plan-document spec Overdeck uses for machine-readable
  work plans. Upstream (deftai) renamed the project vBRIEF → xBRIEF on 2026-06-26
  (v0.7.0, pure rename) and shipped spec v0.8.0 on 2026-06-30. One spec, two names.
- **Envelope** — the top-level info object in a spec document. v0.5/v0.6 documents use
  the key `vBRIEFInfo`; v0.7/v0.8 documents use the key `xBRIEFInfo`. Same shape
  (`version`, `created`, `author`, `description`, …), different key.
- **Internal canonical field** — the TypeScript field name `vBRIEFInfo` on
  `VBriefDocument` (`src/lib/vbrief/types.ts:155`). ~15 non-test call sites (including
  frontend components) access `doc.vBRIEFInfo`. This PRD keeps that field name
  unchanged; only the *on-disk JSON key* varies by version.
- **Read door / write door** — per the single-source-of-truth tenet, spec reads go
  through `readPlanSync()` (`src/lib/vbrief/io.ts:186`) and
  `parsePanSpecDocumentFromString()` (`src/lib/pan-dir/specs.ts`); this PRD adds a
  single serialization function as the write door for spec JSON.
- **Fork** — `eltmon/vBRIEF`, our GitHub fork of the upstream spec repo. Currently
  0 commits ahead / 9 behind `deftai/xBRIEF` master (verified 2026-07-06).

## Problem

Upstream renamed the spec repo and envelope key, and bumped the spec to v0.8. Overdeck:

1. Writes documents with `version: '0.6'` and the `vBRIEFInfo` envelope.
2. **Rejects** any document using the `xBRIEFInfo` envelope — `readPlanSync()`
   (`src/lib/vbrief/io.ts:194`) and `parsePanSpecDocumentFromString()`
   (`src/lib/pan-dir/specs.ts:103`) require the literal key `vBRIEFInfo`.
3. Has a fork (`eltmon/vBRIEF`) frozen at the pre-rename state.

Nothing is broken today (upstream v0.8 tooling still reads v0.5–0.7 documents), but
deft's own backlog contains a "remove vbrief readpath" item
(`deftai/directive` repo, `xbrief/proposed/2026-06-30-2112-remove-vbrief-readpath.xbrief.json`),
so the legacy read path will eventually disappear upstream. We should be able to read
AND emit v0.8 before that becomes a compatibility cliff.

## What v0.8 adds (relative to the v0.6 we write)

Verified against `deftai/xBRIEF` `CHANGELOG.md` (0.7.0 + 0.8.0 sections) and PR #29:

| Change | Overdeck impact |
| --- | --- |
| Envelope `vBRIEFInfo` → `xBRIEFInfo` | **The core of this PRD** — read both, emit by version |
| `PlanItem.items` preferred over `subItems` | **Already done** — `subItemsOf()` (`src/lib/vbrief/types.ts:171-173`) reads `items ?? subItems`; builder emits `items` (`src/lib/vbrief/builder.ts:121`) |
| `failed` status normative | **Already in our enum** — `VBriefItemStatus` (`src/lib/vbrief/types.ts:26`) includes `'failed'`. No type change needed; pipeline call-site adoption is OUT OF SCOPE (follow-up) |
| `PlanItem.type` (task/group/milestone/epic), `PlanItem.summary`, `planRefs`, `status: "auto"` rollups, `Source`/`Confidence` narrative keys, `x-<consumer>/` extension namespace | OUT OF SCOPE — additive optional features, file follow-up issues if wanted |
| Versioned schema `schemas/xbrief-core-0.8.schema.json` | Used only as a validation checkpoint (see WI-5) |

## Scope decisions (made here, not by the executor)

- **D-1: Keep the internal TypeScript field named `vBRIEFInfo`.** Renaming it would
  touch ~15 files including frontend components and `src/dashboard/frontend/src/components/vbrief/types.ts:70`
  for zero behavior gain. The envelope key is translated at the read/write doors only.
- **D-2: Envelope key on disk is derived from `version`.** Version `>= 0.7` ⇒ write
  `xBRIEFInfo`; version `< 0.7` ⇒ write `vBRIEFInfo`. This preserves round-trip
  fidelity: a v0.6 spec read and re-written stays `vBRIEFInfo`; a v0.8 spec stays
  `xBRIEFInfo`. No document is silently up-converted.
- **D-3: Writers bump to `'0.8'`.** Our emitted documents already satisfy v0.8 rules
  (they use `items`, never `auto`, never `type`), so bumping the version + envelope key
  is sufficient for spec-valid v0.8 output.
- **D-4: All changes land in one PR.** Read-compat and writer-bump ship together; the
  same release that starts writing v0.8 can read it. Older Overdeck releases cannot
  read v0.8 specs — acceptable because specs are read by the same installation that
  writes them.
- **D-5: NOT renaming `.vbrief.json` files, `docs/VBRIEF.md`, skills, or viewer
  components.** Internal naming has no interop cost. Deferred indefinitely (issue
  work item 5 stays open as a possible follow-up with a no-loss audit gate).
- **D-6: Deep-clone and byte-size uses of `JSON.stringify(doc)` are NOT write sites.**
  `src/lib/vbrief/dag.ts:581` (clone), `src/lib/vbrief/io.ts:212` (clone),
  `src/lib/vbrief/dag.ts:1088` (byte count) stay as plain `JSON.stringify` — they never
  touch disk. Do not route them through the serializer.

## Requirements

### Functional

- **FR-1** Readers accept documents whose envelope key is `xBRIEFInfo`, normalizing to
  the internal `vBRIEFInfo` field so all downstream code is unaffected.
- **FR-2** Readers continue to accept `vBRIEFInfo` documents (v0.5/v0.6) unchanged.
  Error messages that enumerate accepted shapes mention both keys.
- **FR-3** A single serializer function is the only path from a `VBriefDocument` (or
  `PanSpecDocument`) to spec-file JSON; it emits `xBRIEFInfo` when
  `parseFloat(version) >= 0.7`, else `vBRIEFInfo`.
- **FR-4** All seven disk-write sites (listed in WI-3) route through the serializer.
- **FR-5** `PlanBuilder.build()` and `autoSynthesizeVBrief` emit `version: '0.8'`.
- **FR-6** Round-trip fidelity per D-2: version determines the on-disk key, both
  directions, verified by tests.
- **FR-7** Fork `eltmon/vBRIEF` fast-forwarded to `deftai/xBRIEF` master and renamed
  `eltmon/xBRIEF`; the fork link in `CLAUDE.md` updated.

### Non-functional

- **NFR-1** No frontend component changes. The plan API returns the in-memory
  (normalized) shape, so `VBriefHeader.tsx` etc. keep reading `doc.vBRIEFInfo`.
- **NFR-2** Every existing spec under `.pan/specs/` on main (all `vBRIEFInfo` v0.5/v0.6)
  still loads via `findPlan()` / `readSpec()` with zero behavior change.
- **NFR-3** A freshly emitted document validates against upstream
  `schemas/xbrief-core-0.8.schema.json` (implementation checkpoint in WI-5).

### WI-2 — Read door: accept the `xBRIEFInfo` envelope (traces: FR-1, FR-2)

**Files:** `src/lib/vbrief/io.ts`, `src/lib/vbrief/vbrief-index.ts`, `src/lib/pan-dir/specs.ts`

1. Add to `src/lib/vbrief/io.ts` (near the top, after imports):

```ts
/**
 * Normalize the on-disk envelope key to the internal canonical field.
 * v0.7+ documents use `xBRIEFInfo`; v0.5/v0.6 use `vBRIEFInfo`. Internally
 * everything is `vBRIEFInfo` (see PAN-2426 D-1); serializeVBriefDocument
 * restores the version-appropriate key on write.
 */
export function normalizeVBriefEnvelope<T extends Record<string, unknown>>(parsed: T): T {
  if (parsed && typeof parsed === 'object' && !('vBRIEFInfo' in parsed) && 'xBRIEFInfo' in parsed) {
    const { xBRIEFInfo, ...rest } = parsed as Record<string, unknown>;
    return { vBRIEFInfo: xBRIEFInfo, ...rest } as unknown as T;
  }
  return parsed;
}
```

### WI-3 — Write door: version-keyed serializer, applied at all write sites (traces: FR-3, FR-4, FR-6)

1. Add to `src/lib/vbrief/io.ts`:

```ts
/**
 * Single write door for spec JSON (PAN-2426 D-2). The on-disk envelope key is
 * derived from the document version: ≥0.7 emits `xBRIEFInfo`, <0.7 emits
 * `vBRIEFInfo`. Preserves round-trip fidelity — never silently up-converts.
 */
export function serializeVBriefDocument(doc: { vBRIEFInfo: { version: string } }): string {
  const version = parseFloat(doc.vBRIEFInfo.version);
  if (Number.isFinite(version) && version >= 0.7) {
    const { vBRIEFInfo, ...rest } = doc as Record<string, unknown> & { vBRIEFInfo: unknown };
    return JSON.stringify({ xBRIEFInfo: vBRIEFInfo, ...rest }, null, 2);
  }
  return JSON.stringify(doc, null, 2);
}
```

   (Loose parameter type is deliberate: `PanSpecDocument` carries an extra top-level
   `status` key that must pass through untouched.)

2. Replace `JSON.stringify(doc-or-equivalent, null, 2)` with
   `serializeVBriefDocument(...)` at exactly these seven disk-write sites:

   - `src/lib/vbrief/dag.ts:859` (`doc`)
   - `src/lib/vbrief/lifecycle-io.ts:76` (`nextDocument`)
   - `src/lib/vbrief/lifecycle-io.ts:96` (`specDocument`)
   - `src/lib/vbrief/lifecycle-io.ts:238` (`doc`)
   - `src/lib/pan-dir/specs.ts:143` (`doc`, inside the Effect `fs.writeFileString`)
