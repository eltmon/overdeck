## blocks-the-design: A merged feature PR hides an active strike

The PRD's D6 and W3 call `readStrikePr` only when `!derived?.pr` and prefer `derived.pr` unconditionally. Yet `prFromGhRow` retains merged PRs (`src/lib/overdeck/derived-issue-state.ts:422-438`), the batch loader stores them under the base issue (`:918-924`), and `deriveState` returns `merged` before considering any live pane (`:160-165`). The Flywheel deriver then removes every `merged` row (`src/lib/flywheel/derive-status.ts:321-322`). Thus a strike workspace on an open issue whose earlier `feature/<id>` PR merged is absent, even with a new open `strike/<id>` PR. The GitLab conversion and loader have the same shape (`derived-issue-state.ts:475-494, 946-949`). Change D6/W3 so only an **open** feature PR takes precedence over an open strike PR; preserve tracker-closed precedence. Add a test with an open tracker issue, merged feature PR in `loadStates`, and open strike PR, asserting that the strike row remains in review with the strike PR.

## blocks-the-design: Cached listings can omit an open strike PR

W3 claims the cached forge listing supplies the open strike PR, but the GitHub listing reads only `gh pr list --state all --limit 100` (`src/lib/overdeck/derived-issue-state.ts:380-393`) and the GitLab listing requests one `per_page=100` page (`:496-503`). An open strike PR outside those 100 all-state results is invisible, so FR-4's open-PR requirement fails even though the PR exists. Ensure the shared cached source covers all open PRs on both forges, or explicitly narrow FR-4 to the listing window and explain the resulting missing PRs. Test a strike PR older than 100 newer merged or closed requests.

## blocks-the-design: Strike lookup defeats the dashboard's stale read

The dashboard adapter intentionally gives `loadStates` `listRepoPullRequestsStaleOk` (`src/dashboard/server/services/derived-issue-state.ts:17-20, 101-115`), which returns a recent settled listing while refreshing it (`src/lib/overdeck/derived-issue-state.ts:402-419`). W3 then calls the strict `listRepoPullRequests` from `defaultReadStrikePr` on each strike row. Once the 30-second cache expires, that call waits for the refresh, so `/api/flywheel/status` can wait on the forge for up to its 20-second timeout (`derived-issue-state.ts:390-392`) even when the dashboard has a valid listing younger than two minutes. It can also pair feature state from the stale listing with a strike PR from the fresh one. Feed the strike selector the same listing snapshot used by `loadStates` on the dashboard, while keeping the CLI's chosen freshness policy. Add a test where a refresh is pending and a recent settled listing already contains the strike PR; the dashboard status must resolve without waiting for the refresh.
