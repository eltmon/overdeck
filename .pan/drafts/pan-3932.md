# PAN-3932: AutoMergeToggle per-issue label is silently ignored, and its tooltip doesn't explain the mechanism

**Issue:** [PAN-3932](https://github.com/eltmon/overdeck/issues/3932)

## Glossary

- **AutoMergeToggle** — `src/dashboard/frontend/src/components/AutoMergeToggle.tsx`. A read-only indicator (four render sites) showing whether the merge train will auto-merge an issue's PR (`⚡ Auto`) or hold it for a human UAT batch (`🔒 Hold`).
- **Auto-merge policy tiers** — the three-level precedence that decides the effective auto-merge value for an issue, highest first: (1) the issue's own tracker label, (2) the project's `auto_merge_default`, (3) the global `require_uat_before_merge` setting. Implemented by `shouldHoldForUat()` in `src/lib/cloister/auto-merge-policy.ts`.
- **Per-issue tracker label** — `auto-merge` (forces tier 1 = auto) or `hold-for-uat` (forces tier 1 = hold), applied directly to the GitHub/GitLab issue. Read by `autoMergeFromLabels()` in `src/lib/cloister/auto-merge-eligibility.ts:39-43`. This is what PAN-3917 (The Overdeck Cut) replaced the old per-issue database record with — "which is where an operator toggle can live without Overdeck storing a copy of it" (`auto-merge-eligibility.ts:10-12`).
- **The Cut / PAN-3917** — the September 2026 remodel (`.pan/drafts/pan-3917.md`) that deleted Overdeck's derivable status storage. Decision D3 made `AutoMergeToggle` read-only because the per-issue routing key it used to write is gone as a record; it is now this label.
- **Merge train** — the per-project auto-merge/UAT-batch orchestration under `src/dashboard/server/routes/merge-train.ts`, exposed at `/api/merge-train/*`.

## Problem

`AutoMergeToggle`'s tooltip (`AutoMergeToggle.tsx:56-60`) says the value is "Set by the project default" and never mentions the per-issue tracker label — even though the label is the mechanism PAN-3917 introduced specifically so operators would have a per-issue override that doesn't require a toggle write path (see Glossary). That is the literal issue as filed.

Investigating the toggle's actual data source turned up a second, more consequential problem: **the code the tooltip would need to describe doesn't exist yet.** Both server functions that feed the toggle hardcode the per-issue tier to `undefined` instead of reading the label, so the label has **zero effect** on what the toggle shows or on whether an auto-merge can be scheduled:

- `getAutoMergePolicyPayload()` (`merge-train.ts:632`, backs `GET /api/merge-train/auto-merge`, which is what `AutoMergeToggle` renders):
  ```ts
  const held = shouldHoldForUat(undefined, getProjectAutoMergeDefault(issueId), globalRequireUat);
  ```
- `postAutoMergeSchedulePayload()` (`merge-train.ts:519`, the early gate before an auto-merge is scheduled):
  ```ts
  if (shouldHoldForUat(undefined, projectDefault, globalRequireUat)) {
    return { status: 412, body: { error: 'UAT is still required before merge' } };
  }
  ```

Compare `isAutoMergeEligible()` (`auto-merge-eligibility.ts:69-98`, used only when the merge-train executor actually fires on an already-scheduled entry), which does it correctly:
```ts
const hold = shouldHoldForUat(
  autoMergeFromLabels(labels),
  (deps.getProjectDefault ?? getProjectAutoMergeDefault)(issueId),
  globalRequireUat,
);
```

`shouldHoldForUat()` itself is correct and fully tested (`tests/unit/lib/cloister/auto-merge-policy.test.ts`) — tier 1 (`true`/`false`) always wins over tiers 2/3. The bug is that two of its three call sites never pass tier 1.

**Consequence today:** an operator who adds the `auto-merge` label to an issue to override a project default of `hold` (or the global UAT-required setting) gets no effect — the toggle keeps showing `Hold`, and `POST /api/merge-train/auto-merge/schedule` keeps returning `412 UAT is still required before merge`, even though `isAutoMergeEligible()` (reached only for an entry that already got past that 412) would have honored the label. The label is decorative.

**Why the tooltip fix can't ship alone:** writing a tooltip that says "reflects your issue's `auto-merge`/`hold-for-uat` label" while the display code ignores that label would document a lie. Fixing the tooltip requires fixing the read path first (Item 1), which also requires fixing the scheduling gate in the same pass — shipping the display fix without the scheduling fix would make the toggle show `Auto` for a labeled issue that the scheduler would still refuse to auto-merge, a *new*, user-visible inconsistency the tooltip fix would introduce.

**Two adjacent bugs found during this investigation are explicitly out of scope** (filed as separate issues so this fix stays reviewable as one vertical slice):
- [#3954](https://github.com/eltmon/overdeck/issues/3954) — `pan merge cancel` still calls the pre-cut `/api/flywheel/auto-merge/:id` (now `/api/merge-train/auto-merge/:id`); a CLI bug in a different file, unrelated to the toggle's label precedence.
- [#3955](https://github.com/eltmon/overdeck/issues/3955) — `configuration/auto-merge.mdx` documents a `pan flywheel config` CLI subcommand that no longer exists (PAN-3917 D12 left `flywheel` with only `start|stop|status`) and several other stale `/api/flywheel/*` references throughout the doc, beyond the one section this PRD's docs item touches.

## Proposal

1. Fix the two `merge-train.ts` call sites to read the issue's cached tracker labels and pass `autoMergeFromLabels(labels)` as the tier-1 argument to `shouldHoldForUat()`, matching the already-correct, already-tested pattern in `auto-merge-eligibility.ts`. Use the **cached** label source (`getSharedIssueService().getTrackerIssue(issueId)?.labels`), not a live `gh issue view` call, because `getAutoMergePolicyPayload` runs in a polled dashboard read path across every in-flight issue in every project — a live forge call per issue there would be a real latency/rate-limit regression.
2. Rewrite `AutoMergeToggle`'s tooltip to state plainly that the control is read-only and to name the three-tier precedence and where to change each tier.
3. Add a new "Auto-merge policy tiers" section to `configuration/auto-merge.mdx` documenting the per-issue label as tier 1, so the user-facing doc and the in-app tooltip agree.
4. Leave the toggle read-only. Building a write path (the issue's other named option) would reverse PAN-3917 decision D3, which deliberately removed the per-issue write surface so Overdeck stores no copy of operator-settable state — see `docs/THE-CUT.md:213` ("Change the policy through the tracker label ... not the toggle"). Re-opening that door is a larger, separate design decision than this issue asks for.

## Decisions (recorded here per plan authoring rules)

- **D1 — Scope includes the label-precedence bug, not just the tooltip.** The tooltip cannot be written truthfully without the display code actually consulting the label first (see Problem). Both fixes ship together as one item since they are the same one-line pattern change in the same file (`merge-train.ts`), introduced by the same missing import.
- **D2 — Keep the toggle read-only.** Per PAN-3917 D3 and `docs/THE-CUT.md:213`, this is the deliberate, already-shipped design; PAN-3932 does not reopen it. (This satisfies the auto-mode requirement to pick the smallest defensible option when an issue names two: "make it write" vs "explain it" — the doc trail already picked "explain it" for this repo.)
- **D3 — Cached labels, not a live forge call, for the display path.** `getAutoMergePolicyPayload` iterates every in-flight issue across every project on a poll; adding a `gh issue view` per issue there is a latency and rate-limit risk `isAutoMergeEligible`'s default deps don't have to worry about (it's called once, on-demand, for one issue). The schedule path (`postAutoMergeSchedulePayload`) is low-frequency, but for consistency and to avoid two different label-fetch strategies in the same file, it also uses the cached source.
- **D4 — File, don't fix, the two adjacent bugs.** `pan merge cancel`'s dead endpoint (#3954) and the doc's broader staleness (#3955) are different files/subsystems with their own test surfaces; bundling them here would turn a small, reviewable fix into a multi-subsystem change. Recorded as hazards in `continue.json`.

## Requirements

- **FR-1.** `GET /api/merge-train/auto-merge` (`getAutoMergePolicyPayload`) MUST resolve an in-flight issue's `autoMerge` value using the issue's own `auto-merge`/`hold-for-uat` tracker label when present, falling back to the project's `auto_merge_default`, falling back to the global `require_uat_before_merge` setting — the same precedence `shouldHoldForUat()` already implements and `auto-merge-eligibility.ts` already tests.
- **FR-2.** `POST /api/merge-train/auto-merge/schedule` (`postAutoMergeSchedulePayload`)'s early UAT-hold check MUST use the same per-issue label precedence as FR-1, so an issue labeled `auto-merge` is never rejected with `412 UAT is still required before merge` when the label alone would make it eligible.
- **FR-3.** Both FR-1 and FR-2 MUST read labels from the dashboard's cached tracker-issue store (`getSharedIssueService().getTrackerIssue(issueId)`), not a live forge call.
- **FR-4.** `AutoMergeToggle`'s tooltip MUST state that the control is read-only and MUST name all three precedence tiers (issue label, project default, global setting) in the order they apply.
- **FR-5.** `configuration/auto-merge.mdx` MUST document the per-issue label as the top-precedence tier, consistent with FR-1/FR-2's corrected behavior.
- **NFR-1.** No change to `isAutoMergeEligible()`, `isMergeEligible()`/`gatherMergeEligibility()`, the merge executor, UAT batch trains, or any write path for the per-issue label (the toggle stays read-only; labels are still applied only via the tracker's own UI/CLI, e.g. `gh issue edit --add-label auto-merge`).
- **NFR-2.** No regression to the existing, passing tests in `src/dashboard/server/routes/__tests__/merge-train-config-auto-merge.test.ts` — in particular the "refuses while UAT is still required" case (no label present) must still return 412.

```markdown
## Per-issue override

Any issue can carry one of two labels that beat both the project default and
the global setting:

- `auto-merge` — this issue always auto-merges when eligible, regardless of
  the project or global setting.
- `hold-for-uat` — this issue always waits for a human batch review,
  regardless of the project or global setting.

Apply or remove the label through the tracker (for GitHub, `gh issue edit
<n> --add-label auto-merge` or `--remove-label auto-merge`). The dashboard's
`AutoMergeToggle` (the ⚡/🔒 control next to an in-flight issue) shows the
*result* of this three-tier resolution — issue label, then project default,
then global setting — and is read-only: change the policy at whichever tier
you mean, not by clicking the indicator.
```
