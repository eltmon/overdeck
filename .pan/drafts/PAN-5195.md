# PAN-5195 — File explorer: discard untracked and newly added files to the Overdeck trash

**Status:** planned, 2026-11-13 (auto planning). **Issue:** [PAN-5195](https://github.com/eltmon/overdeck/issues/5195) · **Parent:** [PAN-5183](https://github.com/eltmon/overdeck/issues/5183)
**Parent PRD:** `.pan/drafts/pan-5183.md` (WI-3: "For untracked files, discard moves them to the Overdeck trash through WI-11's `trashPaths`"). **Trash PRD:** `.pan/drafts/pan-5187.md` (D-C6 layout, D-C8 delete rules). **Later consumer:** PAN-5190 (child E, undo) reads the trash ids this issue returns.

## 1. Glossary

- **Explorer root** — a directory the explorer serves, typed `ExplorerRoot` (`src/dashboard/server/services/explorer/roots.ts`). `kind: 'project'` roots are read-only; every write refuses them with `EDIT_WORKSPACE_REQUIRED`.
- **Requested path** — one root-relative path from `ExplorerGitStageInput.paths`. The context menu sends every selected target, changed or not.
- **HEAD content** — a requested path *has HEAD content* when `git ls-tree -r HEAD` lists the path itself or any file under it.
- **Index-new entry** — an index entry (`git ls-files`) that is not in HEAD: a file added with `git add` and never committed, including the new path of a staged rename.
- **Untracked entry** — what `git ls-files --others --exclude-standard --directory --no-empty-directory` prints. It never prints ignored files. A directory with no tracked content prints once, collapsed, with a trailing `/` (`newdir/`), exactly as `git status --untracked-files=normal` reports it.
- **Overdeck trash** — `<getOverdeckHome()>/trash/<root-slug>/<stamp>-<n>/`, written only by `trashPaths` in `src/dashboard/server/services/explorer/trash.ts` (PAN-5187). Each moved path gets one **trash id** `<root-slug>/<stamp>-<n>`. `pan.explorerRestore` moves an id back.
- **No-overlay restore** — `git restore --source=HEAD --staged --worktree -- <paths>`. In its default no-overlay mode it *deletes* index entries under `<paths>` that are absent from HEAD, from both index and worktree, unrecoverably. It never touches untracked files.

## 2. Problem

`gitStage(root, paths, 'discard')` in `src/dashboard/server/services/explorer/git.ts` (search `Discarding files that are not in HEAD needs the Overdeck trash`) refuses the whole request with `NOT_IMPLEMENTED` when any requested path, or any index entry under a requested directory, is absent from HEAD. The guard exists because a no-overlay restore would delete such files outright. So the operator cannot discard an untracked or newly added file from the explorer. PAN-5187 shipped `trashPaths`; nothing wires discard to it.

## 4. Git behavior this plan relies on (probed 2026-11-13, git in this workspace)

| Probe | Result |
| --- | --- |

| `git restore --staged -- u` on a purely untracked path | **fails**: "pathspec 'u' did not match any file(s) known to git" |
| `git restore --staged -- dir` on a directory with HEAD content and no index changes | exit 0, no-op |
| `ls-files --others --exclude-standard --directory --no-empty-directory -- dir/ignonly` (only `*.log` files, ignored) | prints nothing |

## 5. Decisions

- **D-1 Mixed folder: trash only the new entries inside it, restore the rest.** A requested folder holding committed files and new files is not refused. Its untracked entries go to the trash; its committed files are restored from HEAD. This is the issue's own "What is needed" and matches what git status shows inside the folder.
- **D-2 The trash set is git's view, never "not in HEAD".** Only untracked entries (after unstaging) are trashed. Ignored files, unknown paths and unchanged committed files are no-ops. Reason: the menu sends every selected target; a multi-select holding `.env` (ignored) next to a modified file must not trash `.env`.
- **D-3 Order: unstage, list, trash, restore.**
  1. Resolve every requested path with `resolveInsideRoot(root, p, { forWrite: true })` (unchanged loop).
  2. Read: `git ls-tree -r -z --name-only HEAD -- …paths` and `git ls-files -z -- …paths`. A non-zero exit, a timeout or `truncated` on either throws `EXPLORER_FAILED` (`failed('git ls-tree', run)` / `failed('git ls-files', run)`). Nothing has changed yet.
  3. **Unstage** the requested paths that have at least one index-new entry at or under them: `git restore --staged -- …unstagePaths`. Pathspecs, not a per-file list, so a folder of 10,000 new files is one argument. This moves no file; content stays in the worktree. Skip when `unstagePaths` is empty.
  4. **List** untracked entries: `git ls-files -z --others --exclude-standard --directory --no-empty-directory -- …paths`. Strip one trailing `/` from each record. Because step 3 ran first, a new folder whose files were partly staged lists once, collapsed, and becomes one trash entry.
  5. **Trash** them: `trashIds = await trashPaths(root, untracked)` when `untracked` is non-empty, else `[]`. `trashPaths` validates every target before moving any (D-C8).
  6. **Restore** the requested paths that have HEAD content: `git restore --source=HEAD --staged --worktree -- …headPaths`. Skip when `headPaths` is empty. After step 3 no index-new entry remains under them, so the no-overlay restore deletes nothing.
  7. Return `{ trashIds }`.
- **D-4 What "validate before changing anything" means here.** Steps 1-2 and `trashPaths`'s own pre-move checks run before any file moves. The only change that can precede a failure is step 3's unstage, which loses no content (the files stay in the worktree as untracked). If step 4 or 5 fails, the error propagates and nothing was trashed or restored. If step 6 fails after step 5 trashed entries, throw `EXPLORER_FAILED` whose message is `git restore failed: <why>; moved to the Overdeck trash: <comma-separated trash ids>` so the operator can restore them.
- **D-5 Return the trash ids.** `ExplorerGitStageResult` becomes `Schema.Struct({ trashIds: Schema.Array(Schema.String) })`, **required**. `stage` and `unstage` return `{ trashIds: [] }`; discard returns what step 5 returned (in `trashPaths` order). The field is required because the explorer is unreleased (its entries sit in `changelog.d/`, not `changelog.mdx`), so no older server answers `{}` to a newer client. PAN-5190's undo consumes it; this issue adds no undo UI.
- **D-6 A staged-new file that is missing on disk** (`AD`) is unstaged by step 3 and then simply absent; it is not trashed and no `NOT_FOUND` is thrown.
- **D-7 A new folder that holds ignored files is trashed whole**, ignored contents included, because git lists it collapsed as one untracked entry. The trash is recoverable, and leaving a folder of only ignored files behind would not discard the new folder.
- **D-8 Empty HEAD (no commits).** `git ls-tree HEAD` fails, so discard throws `EXPLORER_FAILED` before changing anything. Not worth a special path.
- **D-9 Header comment.** The `git.ts` header's last paragraph is rewritten to describe D-3 and D-4.

## 7. Requirements

- **FR-1** Discarding an untracked file, or an untracked folder, moves it to the Overdeck trash and removes it from the worktree.
- **FR-2** Discarding a staged-new file unstages it and moves it to the Overdeck trash, including when it was edited after staging.
- **FR-3** Discarding a folder that holds committed and new files restores the committed files from HEAD and trashes only the new entries; a new subfolder becomes one trash entry.
- **FR-4** Discard never trashes an ignored file on its own, and never trashes an unchanged committed file. An ignored file inside a wholly new untracked folder goes to the trash with that folder (D-7).
- **FR-5** `pan.explorerGitStage` returns `{ trashIds: string[] }`: the trash ids of the discard, and `[]` for stage and unstage.
- **FR-6** Every requested path is resolved, and the HEAD and index reads succeed, before any git command or file move changes anything; a failed HEAD restore after a trash reports the trash ids in its error message.
- **FR-7** The frontend `gitStage` wrapper returns the RPC result so PAN-5190 can read `trashIds`.
- **NFR-1** Tests that reach `trashPaths` run with `OVERDECK_HOME` pointing at a temp directory.
- **NFR-2** `docs/DASHBOARD-ARCHITECTURE.md` and `changelog.d/pan-5195.md` describe the new discard behavior.

## 10. Non-goals

- No undo or redo UI for discard; PAN-5190 owns undo and reads `trashIds`.
- No change to the confirm dialog or the context menu's enablement rules.
- Discarding the new path of a staged rename (`git mv a.txt d/b.txt`, discard `d/b.txt`) trashes `d/b.txt` and leaves `a.txt` staged as deleted; restoring the rename's origin is not done here.

- Discard in a repository with no commits fails with `EXPLORER_FAILED`.
- No change to `trashPaths`, `restore` or `pruneTrash`.
- Never trash an ignored file on its own or an unchanged committed file (an ignored file inside a wholly new untracked folder goes with that folder, D-7).
