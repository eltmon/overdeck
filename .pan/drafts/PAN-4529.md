## Glossary

- **Mod:** a Claude Code plugin whose `hooks/hooks.json` names a hooks module under `modules`. The module exports `register(on, options)` and registers function hooks `($, e, next)` that observe, rewrite or answer engine events and can draw UI. Added in Claude Code 2.1.287 (2026-10-01); the local build is 2.1.288.
- **Function hook / hook:** one `on(event, matcher?, hook)` registration in a mod. `$` is the engine API (`$.ui`, `$.prompt`, `$.session`, `$.http`, …), `e` the frozen event input, `next(e)` the rest of the chain.
- **Settings hook:** the older shell-command hook configured in `settings.json` (`PreToolUse`, `Stop`, …). Overdeck installs these today. Mods can observe them as `classic.<Event>`.
- **Band:** a mod's drawing in the `AbovePrompt` render site, the row above the prompt box.
- **Pane:** a mod-opened panel (`$.ui.open` plus a `ui.render` hook on `Pane`). It docks beside the transcript only in the fullscreen layout; otherwise it sits inline above the prompt.
- **Status entry:** `$.ui.status(text)`, one pinned line per plugin. Distinct from the `statusLine` settings command Overdeck already ships.
- **Managed session:** a Claude Code process Overdeck launches for a role (work, review, plan, test, flywheel, conversation) in a Herdr or tmux pane.
- **Harness parity:** Overdeck also runs Codex, Pi, Kimi and other harnesses. A Claude-Code-only capability must not become the only path to a pipeline behavior.
- **Report:** the two deliverable files, `.pan/drafts/claude-code-mods-evaluation.md` (source of truth) and `.pan/drafts/claude-code-mods-evaluation.html` (the same content, self-contained).
- **Research brief:** `.pan/drafts/claude-code-mods-research.md`, the pre-gathered mods research. It is an input; it is committed unmodified.
- **Scratch dir:** `/tmp/pan-4529-mods-scratch/`, the only place a throwaway prototype may be written. It is outside the repo and outside `~/.claude`.
- **Evidence ref:** a `path:line` reference into the Overdeck repo plus a quoted grep anchor, the literal code text at that line.

## Background and problem

Claude Code mods run inside the Claude Code process and can draw UI, rewrite or answer tool calls and prompts, start turns, append rows, and talk to Unix sockets. Overdeck today reaches into Claude Code from the outside: shell settings hooks that POST to the dashboard, keystroke and paste delivery through Herdr or tmux, pane scraping for permission prompts, transcript parsing for questions and the Flywheel tick marker, and a bash status line. The operator wants an in-depth, review-ready evaluation of where mods could replace or improve these paths, what they cannot do, and what to adopt first. No adoption happens in this issue.

**Scope correction on #92533.** The bug title is "Any function-hook tool.call on Bash breaks Agent isolation: "worktree" — every Bash call refused". It concerns Claude Code's own `Agent` subagents spawned with `isolation: "worktree"` (Claude Code creates `<repo>/.claude/worktrees/agent-*`). A grep of `roles/`, `sync-sources/` and `docs/` finds no Overdeck prompt that requests `isolation: "worktree"`, but any agent may choose it ad hoc through the Agent tool. So the report must state: any Overdeck mod that registers a `tool.call` hook on `Bash` (for example a git-guard replacement) breaks every Bash call in worktree-isolated subagents of that session until #92533 is fixed. That makes it a blocker for candidate 7's git-guard idea and a constraint on every other candidate, not a blocker for mods in general.

## Candidate leads (decisions made here; the work agent evaluates these, it does not invent others)

**Candidate 1 — Operator state in the agent's own pane (band or status entry).** Capability: `ui.render` on `AbovePrompt`, `$.ui.status`, `$.clock.every`, and `$.http.fetch` against the dashboard or `$.fs.read` of a state file. State to show: issue, pipeline phase, verification and review state, Needs-you. Facts to carry: Overdeck sets no fullscreen flag, so under tmux the session is main-screen (`isFullscreen: false`) and a pane opens inline, not docked; Herdr's fullscreen behavior is **UNVERIFIED** and must be an explicit open question. Whatever a mod draws reaches the dashboard's terminal panel through the raw PTY stream, so the operator sees it with no dashboard change, but non-Claude harnesses get nothing, so the dashboard stays the source of truth. Compare against the shipped bash status line (`src/lib/sync.ts:614`). Note #99354 (docked pane ignores light theme).

**Candidate 2 — Reliable in-session message delivery.** There is no listening API in `$`, so the report evaluates exactly these three shapes:
- (a) **Pull:** `$.clock.every` plus `$.http.fetch` to the dashboard (or `$.fs.read` of a spool file), then `$.prompt.submit({ text, asUser })`. `submit` resolves as the turn starts, which is a positive delivery acknowledgment the keystroke path lacks (`herdr.ts:807`, PAN-4492 "cannot verify its own Enter"). It never folds into a running turn. The steer equivalent is `$.session.append` of a user-role `isMeta` row, which reaches "a running turn's requests from the loop's next top". It removes the PAN-4506 failure class (text never crosses Herdr's JSON API) but adds a poll interval and a dependency on the mod being loaded.
- (b) **Peer socket:** `session.receive`, with `SendMessage` accepting `uds:<socket>` addresses (types `SendFile`/`SendMessage` `to`; `SessionSendResult` says "another session's socket"). The wire protocol is undocumented. Mark it **UNVERIFIED** and an implementation checkpoint for a follow-up, with (a) as the fallback.
- (c) **Existing Channels MCP bridge** (`supervisor-channels.ts:290`, `overdeck-bridge.ts:275`): opt-in, work role only. The report compares (a) and (b) against it.
Note #96336 is Desktop-only and does not block terminal sessions.

**Candidate 3 — Liveness and activity signals.** Capability: `turn.start`, `turn.step`, `turn.complete`, `session.end`, `classic.Stop`, `$.http.fetch` to the dashboard heartbeat route. Compare with the settings-hook heartbeat (`pan-hook-lib.sh:343`) and `liveness.ts:173`/`:363`. Key point to evaluate: hooks already give event-driven turn boundaries; a mod adds `turn.step` (per-model-request, "thinking" vs tool time) and `$.session.usage()`, but a mod that is unloaded (3 worker crashes, remote kill switch #99130, `disableAllHooks`) goes silent, so it cannot be the only liveness source. Relate to PAN-4522 (runtime map reset on restart) only as context.

**Candidate 4 — AskUserQuestion and permission prompts.** Capability: `tool.call` on `AskUserQuestion` (hold the call, answer with `{ result }`), the `AskUserQuestion` render site, `tool.check` returning `{ decision }`. Facts to carry: the 10 s budget excludes time inside `$` calls except `$.clock.sleep`, so holding a question requires one long-poll `$.http.fetch` the dashboard keeps open, never sleep-and-retry. `tool.check` could answer permission decisions in-process, replacing pane parsing (`permission-prompt.ts:105`) and keystrokes (`:219`), but the permission prompt itself cannot be redrawn (docs overview). Approving tool calls from a mod bypasses `ask` rules and, without the sec-default guard, non-managed `PreToolUse` blocks — a security finding. Compare with the PAN-1520 deny hook (`ask-user-question-hook:4`).

**Candidate 5 — Flywheel and gauntlet loops.** Capability: a Pane drawn from `$.state`, fed by `$.clock.every` + `$.http.fetch`, plus `$.command.register` for a `/flywheel` view. Compare with the tick marker (`tick-marker.ts:19`, `derive-status.ts:257`), which the header comment calls "the only channel from the loop to the page". A mod could emit structured tick events instead of transcript text, but the marker is harness-neutral; evaluate whether a mod replaces or only mirrors it.

**Candidate 6 — Reviewer and worker progress bands.** Capability: band or `$.ui.status` in reviewer/worker panes, fed by the dashboard. Overdeck code: `review-convoy.ts:315`, `verification-runner.ts:297`. Evaluate value given these panes are rarely watched directly (the dashboard reviewer tree is the operator surface).

**Candidate 7 — Other uses.** Evaluate exactly these, each as a sub-row or short subsection with its Overdeck file:

2. `prompt.compose` / `prompt.context` as a delivery path for context layers instead of file injection (context: `docs/CONTEXT-LAYERS.md`).

## Cross-cutting sections (decisions)

**Hard limits** — list from docs reference "Limits" and the brief §10: no listening sockets; cannot redraw the permission prompt; drawing only in terminal and Desktop (none under `claude -p`, VS Code #99045); hooks fail open; one shared worker; remote kill switch (#99130); `disableAllHooks` stops mods and the custom status line together; `$.store` 4 MiB and not atomic across sessions; tmux main-screen layout; `$.audio` silent on Linux; early-access API that "may change between releases without notice".

**Security and supply chain** — mods are not sandboxed and run with user permissions; no per-mod consent at install; review is `claude plugin validate`. Overdeck facts: `claude-plugins-provision.ts:83` already installs plugins at user scope, so shipping a mod through `pan sync` reaches every Claude Code session on the machine, not only managed ones; `claude-settings-overlay.ts:109` deny rules do not bind a mod's own `$.fs`/`$.process`. Mitigation lead to propose: a CI ratchet that runs `claude plugin validate --json` on any shipped mod and fails when its `calls:` set grows beyond an allowlist.

**Managed Claude home and sync targets** — Overdeck writes into `~/.claude` (skills, agents, settings hooks, status line) via `pan sync`; there is no separate managed Claude home (`CLAUDE_CONFIG_DIR` is not used in `src/`). Delivery routes for a mod: user-scope plugin install (existing marketplace path), `--plugin-dir` per launch (existing skill-pack line, but that reverses the hooks-excluded-by-construction decision at `mount.ts:13`), or `CLAUDE_CODE_PLUGIN_DIRS` in user settings `env` (affects every session). Scoping a mod to managed sessions only requires a runtime check (for example `$.env.get('OVERDECK_AGENT_ID')`) or per-launch `--plugin-dir`; the report weighs these.

# usage: pan-4529-check-refs.sh <markdown file>; prints BAD lines; prints checked=<n> to stderr
f="$1"; n=0
