## Glossary

| Term | Meaning |
| --- | --- |
| **Environment** | One independently running Overdeck server and the machine-local projects, agents, conversations, terminals, credentials, and runtime state it owns. |
| **Environment ID** | A stable opaque ID generated by an Overdeck server. Every client-visible project, issue, agent, conversation, and terminal reference is paired with it. |
| **Connection catalog** | Client-owned persisted records for known environments: label, endpoint/transport, environment ID, protected session credential, last connection result, and optional SSH launch metadata. |
| **Environment descriptor** | Server-reported identity, platform, Overdeck version, and capability flags returned during connection bootstrap. |
| **Endpoint provider** | A way to reach an environment: same-origin local, direct HTTPS, Tailscale HTTPS, SSH-forwarded loopback, or a future Anywhere relay. Providers converge on the same HTTP/WebSocket client contract. |
| **Pairing credential** | A short-lived, single-use secret printed or displayed by the server. A client exchanges it for a revocable device session. It is not the root internal token. |
| **Device session** | A revocable credential stored by one client for one environment after pairing. |
| **Scoped reference** | `{ environmentId, localId }`, where `localId` is an existing project, issue, agent, conversation, or terminal ID meaningful only to its environment. |
| **Federated client** | The dashboard shell that holds several environment connections and routes every read, mutation, stream, and terminal to the environment named in the scoped reference. |
| **Origin machine** | The environment that owns an entity and executes every operation on it. This issue does not migrate live ownership between machines. |
| **Credential registry** | The one file-backed store of revocable bearer credentials, `${OVERDECK_HOME}/access-tokens.json`, owned by `src/lib/access-tokens.ts`. Its contract is PAN-2351 W1 (D-1, D-2). Device sessions are records in it. |
| **Device token** | An `odk_<64 hex>` secret created by a pairing exchange. Only its SHA-256 hash is stored. A browser holds it in the `overdeck_device` cookie; a desktop client (PAN-4402) holds it as a bearer token. |
| **Root session** | The existing `overdeck_session` cookie. Its value is an HMAC of the internal token, so it is the same for every browser and cannot be revoked per device. Pairing never issues it. |
| **Dashboard credential** | What `resolveDashboardCredential(headers)` returns: `internal-token`, `root-session`, or `device` (with its record id). `null` means no credential. |
| **Trusted local caller** | A request whose real TCP peer passes `isLoopbackPeer` (loopback, host-local Docker bridge, or own container network) and, when `require_token_mint` is on, carries no proxy forwarding header. |
| **Remote request gate** | A global `HttpRouter` middleware that returns 401 for any `/api/*` or `/events/*` request that has no dashboard credential, is not a trusted local caller, and is not on the unauthenticated allowlist. |
| **`require_token_mint`** | `dashboard.require_token_mint` in `~/.overdeck/config.yaml` (PAN-2351 D-4). When `true`, loopback peer trust no longer mints a root session and proxied loopback requests are treated as remote. |

## Problem

Overdeck Anywhere currently treats remote use as access to one home orchestrator. [PAN-2350](https://github.com/eltmon/overdeck/issues/2350) adds tunnels, a relay, mobile access, and distributed agent metadata around that central instance. This works for reaching one machine from a phone and for shared sessions, but it makes the common desktop-plus-laptop case depend on a shared control/data plane.

t3code ships a simpler model. Every machine runs a complete server. Clients save several environments and connect directly to each one. The machine remains authoritative for its files, git state, terminals, and provider sessions. The client scopes identities by environment, handles connection/version state separately, and routes operations to the selected server. Direct HTTPS, Tailscale, SSH forwarding, and relay connections are transport choices under one connection catalog.

Overdeck should adopt that architecture for single-operator multi-machine use. Existing relay work remains useful as an optional endpoint provider and shared-session substrate, but it is no longer the prerequisite for using several operator-owned machines from one dashboard.

## Architecture comparison and decision

| Concern | Existing Anywhere direction | Adopted direction |
| --- | --- | --- |
| Authority | One home orchestrator is the primary instance. | Every machine is an independent authority for its local entities. |
| Multi-machine UI | Relay/remote state planes make another machine visible. | The client opens one connection per saved environment and composes the UI. |
| Runtime state | Agent metadata is distributed so one server can locate remote runtime. | Runtime stays local. The scoped reference routes the request to its owner. |
| Reachability | Cloudflare/relay is central. | Direct HTTPS, Tailscale, and SSH work first; relay is another endpoint provider. |
| Identity | Scoped tokens on the home server plus relay identity. | Pairing and revocable device sessions are per environment; relay identity can wrap the same contract. |
| Failure mode | Relay or home instance failure can hide the whole system. | One failed environment is isolated; other connections remain live. |
| Version skew | Planned around relay/client compatibility. | Every descriptor advertises server version and capability flags; clients gate actions per environment. |
| Cross-machine continuation | Requires transcript/state distribution. | Browse and control stay on the origin first. Ownership transfer remains separate in [PAN-2609](https://github.com/eltmon/overdeck/issues/2609) / [PAN-3513](https://github.com/eltmon/overdeck/issues/3513). |

**Decision:** Implement client-side environment federation as the default Overdeck Anywhere architecture for one operator using several machines. Keep [PAN-2356](https://github.com/eltmon/overdeck/issues/2356) as an optional relay endpoint and shared-session service. Do not require relay deployment, global agent state, or transcript replication for v1 federation.

## Requirements

### Functional requirements

- **FR-1 — Stable environment identity.** Each server owns a stable opaque `environmentId` under `OVERDECK_HOME`. It returns that ID, a user-facing machine label, OS/architecture, exact Overdeck version, and capabilities from a versioned descriptor endpoint/RPC. *(2026-09-28)* The ID is the one per-machine identity for all of Overdeck: its file, shape and module are fixed by the "Shared machine identity contract" below, and [PAN-2609](https://github.com/eltmon/overdeck/issues/2609) (Session Vault) reuses it instead of minting a `machineId`. If PAN-2609 Phase A lands first, it creates the identity in exactly that form and this issue adopts it without a migration.
- **FR-2 — Scoped references.** All federated client state and navigation use `{ environmentId, localId }`. The environment ID must participate in query/cache keys, selection state, URLs, event routing, terminal attachment, mutation dispatch, and persisted recent-history entries.
- **FR-3 — Connection catalog.** Desktop stores several environment profiles. Each profile carries label, endpoint-provider configuration, expected environment ID, protected device credential, last connected descriptor, and connection status. Secrets use the Electron secret-storage boundary and never localStorage/plain JSON.
- **FR-4 — Local compatibility.** With no catalog configured, the current same-origin server is materialized as the implicit local environment. Existing URLs and single-machine behavior continue to work.
- **FR-5 — Independent connections.** The client maintains one RPC/SSE/terminal transport context per connected environment. A failure, reconnect, auth expiry, or version mismatch in one context does not reset another.
- **FR-6 — Environment UI.** Settings → Connections lists local and remote environments with label, machine, endpoint type, status, version, and actions to add, reconnect, rename, forget, or revoke. The app shell shows the active environment and supports switching. Aggregated lists label every row by environment and never merge colliding local IDs.
- **FR-7 — One-time pairing.** `pan pair` and the dashboard issue a short-lived single-use credential and pairing URL. The target server exchanges it for a revocable device session. The root internal token never crosses the machine boundary or appears in the pairing URL.
- **FR-8 — Revocation.** Server and UI/CLI list paired devices/sessions and revoke them immediately. Revocation closes or rejects HTTP, SSE, RPC, and terminal access for that session without changing other devices.
- **FR-9 — Direct endpoints.** A headless server can advertise configured HTTPS/Tailscale endpoints. Pairing output distinguishes unreachable loopback endpoints from reachable ones and never claims network reachability it has not verified.
- **FR-10 — Desktop-managed SSH.** The desktop accepts an SSH target, probes non-interactive Node/Overdeck availability, starts or reuses `pan serve` on remote loopback, creates a local port forward, pairs, saves the environment, monitors the child processes, and reconnects after desktop restart. Generated remote launcher state is namespaced under `~/.overdeck/ssh-launch/<host-key>/` on the remote machine.
- **FR-11 — Version and capabilities.** The client compares its contract version with each descriptor. It shows actionable version mismatch state and gates unsupported actions from advertised capabilities before dispatch.
- **FR-12 — Transport-neutral routing.** Direct, Tailscale, SSH, and future relay profiles all produce the same resolved HTTP/WS base URL and device-session provider. Feature code does not branch on transport type.
- **FR-13 — Ownership clarity.** Every project, agent, conversation, terminal, issue action, AskUserQuestion prompt, and flywheel surface shows or inherits its environment. Mutations always execute on the owning environment.
- **FR-14 — Existing Anywhere integration.** [PAN-2350](https://github.com/eltmon/overdeck/issues/2350), [PAN-2351](https://github.com/eltmon/overdeck/issues/2351), [PAN-2352](https://github.com/eltmon/overdeck/issues/2352), [PAN-2356](https://github.com/eltmon/overdeck/issues/2356), [PAN-2609](https://github.com/eltmon/overdeck/issues/2609), and [PAN-3513](https://github.com/eltmon/overdeck/issues/3513) receive an explicit disposition: prerequisite, absorbed, relay-only, continuation-only, or superseded.
- **FR-15 — Remote request gate.** *(2026-09-29)* Every `/api/*` and `/events/*` request that is not a trusted local caller must carry a dashboard credential, except the unauthenticated allowlist: `GET /api/health`, `GET /api/environment`, `OPTIONS` and `POST /api/dashboard/session`, `POST /api/pairing/exchange`, and `POST /api/webhooks/github` (HMAC-verified by its route). Static SPA files stay public. This closes the existing LAN hole and is required before any network endpoint is advertised.
- **FR-16 — Devices never get a root session.** *(2026-09-29)* A request authenticated only by a device credential never receives the `overdeck_session` cookie from any route. The session mint returns `csrfToken` and refreshes `overdeck_device` instead.
- **FR-17 — One credential registry.** *(2026-09-29)* Device sessions are records in the PAN-2351 credential registry (`src/lib/access-tokens.ts`, `${OVERDECK_HOME}/access-tokens.json`). Whichever of PAN-2351 and PAN-3762 lands first creates the module in exactly PAN-2351 W1's form, plus the optional `kind` field defined here. No second token store is created.

### Non-functional requirements

- **NFR-1 — Isolation.** One environment cannot read or mutate another environment's server state. The client is a router, not a new canonical store.
- **NFR-2 — Secret safety.** Pairing and device secrets never appear in query strings, logs, activity payloads, analytics, or unencrypted catalog files. Pairing URLs put the credential in the fragment when browser delivery is required.
- **NFR-3 — No new state door.** Servers continue to use each domain's canonical read resolver and write surface. Federation adds routing before those doors; it does not add direct DB, state-branch, `state.json`, or tracker access.
- **NFR-4 — Server runtime.** Dashboard production remains Node 22 and built `dist/dashboard/server.js`. No `execSync` is introduced in server-reachable code.
- **NFR-5 — Test timing.** SSH reconnect, pairing expiry, retry, backoff, heartbeat, and revocation timing tests use Vitest fake timers. Real-time network checks live in a separate `@slow` integration suite.
- **NFR-6 — Compatibility.** Local-only startup, routes, command palette actions, issue lifecycle, conversations, terminals, flywheel, Machine Room, and settings remain available. A no-loss audit test accounts for each pre-federation route/action/status/view.
- **NFR-7 — Failure reporting.** Connection errors name the affected environment, failed stage, and next action. An offline laptop must not produce a global dashboard failure banner for a healthy desktop environment.
- **NFR-8 — Performance.** Two idle connected environments add no more than two persistent control connections each. Aggregation must not multiply server polling when an event subscription already exists.
- **NFR-9 — Platform scope.** Linux/macOS desktop and headless Linux are v1. Windows direct connections are supported if the server already runs; desktop-managed SSH launch on Windows is deferred unless the existing desktop SSH process layer proves portable without extra work. PAN-4331 verified on 2026-09-29 (run https://github.com/eltmon/overdeck/actions/runs/36615182191, GitHub `windows-2022` runners) that a Linux Session Vault conversation continues in WSL2 but not on native Windows, where `pan vault join` fails under the Git for Windows default `core.autocrlf=true` (#4418), `pan vault resume` cannot launch Claude Code (#4419), and the dashboard started by `npx @overdeck/core` serves 404 for every page (#4420).

## Decisions

1. **The environment is the routing boundary.** Do not create a global ID migration. Existing local IDs stay unchanged and become unique when paired with `environmentId`.
2. **The catalog is client state.** It stores connection metadata and protected credentials only. It is not canonical issue, agent, conversation, or pipeline state.
3. **One active environment first, aggregation second.** The first usable increment switches the whole shell between environments. Aggregated overview/Needs-You/search follows once scoped query keys and navigation are mechanically safe.
4. **SSH forwards loopback.** The remote server remains bound to loopback for SSH profiles; the desktop owns the forward. Direct profiles require explicit network binding and trusted HTTPS/Tailscale configuration.
5. **Pairing creates server-side sessions.** Do not extend the root `internal-token` bootstrap to remote clients. [PAN-2351](https://github.com/eltmon/overdeck/issues/2351)'s scoped-token work may supply storage/verification primitives, but the user contract is paired devices and revocable sessions.
6. **The relay implements an endpoint provider.** [PAN-2356](https://github.com/eltmon/overdeck/issues/2356) may provide reachability, identity assertion, and push. It must not replace the environment descriptor, scoped refs, or per-environment authorization checks.
7. **No live ownership transfer in v1.** A laptop can operate a desktop-owned agent through the desktop environment. Moving the conversation or agent to the laptop is separate continuation/migration work.
8. **Server update is explicit.** The descriptor advertises update capability. The client may guide or invoke a supported update, but never silently restarts a machine with active work.

### Shared machine identity contract (rev 3, decided 2026-09-28)

This block is identical in `pan-3762.md` and `pan-2609.md`. Change both or neither.

- **Owner.** One stable identifier per machine: `environmentId`, owned by
  [PAN-3762](https://github.com/eltmon/overdeck/issues/3762) FR-1. PAN-2609 reuses it and never
  creates its own machine identifier.
- **File.** `${OVERDECK_HOME}/environment-id.json`, mode `0600`, written atomically (temp file in
  the same directory, then rename), created only when absent.
- **Shape.** `{ "v": 1, "environmentId": "<UUID v4, lowercase>", "label": "<os.hostname() at creation>", "createdAt": "<ISO-8601 UTC>" }`.
  `label` is user-facing and may be renamed; `environmentId` never changes.
- **Module.** `src/lib/environment-identity.ts` exports
  `readEnvironmentIdentity(): Promise<EnvironmentIdentity | null>` and
  `ensureEnvironmentIdentity(): Promise<EnvironmentIdentity>` (read, or create if absent). It
  imports only Node built-ins and `src/lib/paths.ts`, so the standalone `pan vault` CLI can load
  it without the dashboard, Effect runtime layers, node-pty, or the terminal backend
  (PAN-2609 NFR-7). PAN-3762 W1 wraps the value in its branded `EnvironmentId` contract type and
  serves it from the environment descriptor.
- **Corrupt file.** Never silently replaced: a new id would orphan every vault record the machine
  owns and every client catalog entry that expects the old id. The read fails with an error
  naming the file; recovery is an explicit operator action defined by PAN-3762 W1.
- **Interim.** Whichever issue lands first creates the module and the file in exactly this form.
  If PAN-2609 Phase A lands first, WI-1 creates them and PAN-3762 W1 adopts them unchanged, with
  no migration. No `machine-id.json` is ever written.

## This issue's implementation (2026-09-29)

### Scope in one sentence

Every Overdeck server gets a public environment descriptor, refuses uncredentialed requests from anything that is not a trusted local caller, and lets an operator pair another device with `pan pair`. Pairing gives that device its own revocable `odk_` session, and revoking it cuts HTTP, SSE and WebSocket access within five seconds, without the root internal token ever leaving the machine.

### Decisions for this issue

- **D-3762-1 Descriptor route.** `GET /api/environment` is a new unauthenticated route. `/api/health` stays unchanged because it exposes `serverPath`. The descriptor contains no paths, usernames, tokens or secrets.
- **D-3762-2 Registry.** Adopt PAN-2351 W1 exactly: `src/lib/access-tokens.ts`, file `${OVERDECK_HOME}/access-tokens.json`, mode `0600`, atomic write (temp file in the same directory, then rename), record `{ id, name, scopes, tokenHash, createdAt, lastUsedAt, revokedAt? }`, token `odk_${randomBytes(32).toString('hex')}`, SHA-256 hex at rest, `timingSafeEqual` compare. Add one optional field, `kind?: 'device' | 'token'`; pairing writes `kind: 'device'`. Scopes are always `['admin']` here; scope enforcement, `pan token` and the Settings token UI stay in PAN-2351. A corrupt or unreadable registry means zero valid tokens plus a loud error (PAN-2351 NFR-4), never a permissive parse.
- **D-3762-3 Verification is synchronous against a cache.** `hasDashboardAuthHeaders` is synchronous and called everywhere. `verifyAccessToken(presented)` checks an in-memory snapshot. The server loads it at boot (`await refreshAccessTokens()`) and refreshes it with an async `stat` every 5 s (an unref'd `setInterval`). Server-side create/revoke update the snapshot immediately. A CLI write while the server runs is picked up within 5 s. `lastUsedAt` updates are async and throttled to one write per record per minute.
- **D-3762-4 Device cookie.** A browser device session is the cookie `overdeck_device=<odk token>; Path=/; HttpOnly; SameSite=Strict; Max-Age=2592000` plus `; Secure` on HTTPS (same attributes as `dashboardSessionCookieHeader`). `Authorization: Bearer odk_...` is also accepted, for PAN-4402's desktop client. The CSRF token stays the existing global `dashboardCsrfToken()`; CSRF defends cookies, and a revoked device's cookie no longer authenticates.
- **D-3762-5 Pairing credential.** `odp_${randomBytes(32).toString('hex')}`, held only in the dashboard server's memory as a SHA-256 hash, single use, expires 10 minutes after issue. A server restart invalidates outstanding credentials, and the docs say so. The pairing URL is `<base>/#pair=<credential>`; the credential is always in the fragment, never in a query string (NFR-2).
- **D-3762-6 Exchange rate limit.** After 10 failed exchanges within 60 s, the exchange route returns 429 for the next 60 s. The window is process-wide.
- **D-3762-7 Who may issue pairing credentials.** `POST /api/pairing/credentials` requires the internal token or the root session (plus CSRF for the cookie). A device credential gets 403, so a paired device cannot mint more devices.
- **D-3762-8 Remote request gate.** Implemented as one global `HttpRouter.middleware(..., { global: true })` layer (Effect `4.0.0-beta.73`, `node_modules/effect/dist/unstable/http/HttpRouter.d.ts:495-553`), not per-route edits. Rule, in order:
  1. The path does not start with `/api/` or `/events/`: pass (static SPA).
  2. `method + path` is on the allowlist (FR-15): pass.
  3. `resolveDashboardCredential(headers)` is not `null`: pass.
  4. The request is a trusted local caller: pass.
  5. Otherwise: 401 `{ "error": "unauthorized" }`.
  Proxy forwarding headers are `x-forwarded-for`, `x-forwarded-host` and `forwarded`.
- **D-3762-9 `require_token_mint`.** Read `dashboard.require_token_mint` (boolean, default `false`) from raw `${OVERDECK_HOME}/config.yaml` in `src/lib/remote-access/config.ts`, the same way `readTraefikConfigFromYaml()` does. Do not touch `schema.ts`, which is at its size cap. Cache it for the process lifetime; changing it needs a dashboard restart, and the docs say so. When `true`: (a) `rejectUnauthorizedDashboardSessionMintRequest` ignores `isLoopbackPeer`; (b) the gate treats a loopback peer that carries a proxy forwarding header as remote. PAN-2351 later adds the schema entry and Settings toggle.
- **D-3762-10 Revocation reaches live connections.** A new server module, `src/dashboard/server/device-connections.ts`, keeps `Map<deviceId, Set<() => void>>`. `authorizeDashboardUpgrade` returns the credential. Each of the four WebSocket handlers and `/events/stream` registers a close callback for device credentials and unregisters it on close. `DELETE /api/devices/:id` revokes in the registry, then calls every callback for that id (WebSocket close code `4401`, reason `device revoked`; SSE stream interrupted).
- **D-3762-11 CLI.** `pan pair` and `pan devices` call the running dashboard with the internal token (the `plan.ts:37-40` pattern). `pan devices revoke` falls back to writing the registry directly only when the dashboard is unreachable; in that case no live connections exist to close. Both verbs are excluded from wrapper skills in `docs/SKILLS-CONVENTION.md` (their `--help` plus `configuration/remote-access.mdx` suffice).
- **D-3762-12 Browser landing.** `wsTransport.ts` consumes `#pair=` before the session mint, posts it to `/api/pairing/exchange` with `delivery: 'cookie'`, then mints as usual. A failed exchange throws a `DashboardSessionError`-style error with the server's message; it never falls back to the root bootstrap.
- **D-3762-13 Origins stay manual here.** Until PAN-4403 ships advertised endpoints, an operator who opens the dashboard at a non-default origin (for example `https://desk.tailnet.ts.net`) adds it to `OVERDECK_TRUSTED_ORIGINS`. The docs show exactly this.

```ts
// before
export function hasDashboardAuthHeaders(headers: HeaderMap): boolean {
  return hasDashboardInternalTokenHeaders(headers) || constantTimeTokenEqual(cookieValue(getHeaderFromMap(headers, 'cookie'), DASHBOARD_SESSION_COOKIE), getDashboardSessionToken());
}

// after
export type DashboardCredential =
  | { kind: 'internal-token' }
  | { kind: 'root-session' }
  | { kind: 'device'; deviceId: string }

export function resolveDashboardCredential(headers: HeaderMap): DashboardCredential | null {
  if (hasDashboardInternalTokenHeaders(headers)) return { kind: 'internal-token' }
  const cookie = getHeaderFromMap(headers, 'cookie')
  if (constantTimeTokenEqual(cookieValue(cookie, DASHBOARD_SESSION_COOKIE), getDashboardSessionToken())) return { kind: 'root-session' }
  const device = verifyAccessToken(cookieValue(cookie, DASHBOARD_DEVICE_COOKIE) ?? bearerToken(headers))
  return device.ok ? { kind: 'device', deviceId: device.record.id } : null
}

export function hasDashboardAuthHeaders(headers: HeaderMap): boolean {
  return resolveDashboardCredential(headers) !== null
}
```
