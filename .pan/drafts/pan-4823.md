# PAN-4823 — The Overdeck phone app (iOS and Android)

**Status:** draft for operator review · **Revision:** 1 (2026-11-02) · **Author:** Claude Opus 5.5, conversation bc25680b
**Issue:** [PAN-4823](https://github.com/eltmon/overdeck/issues/4823) · **Parent plan:** [PAN-2350](https://github.com/eltmon/overdeck/issues/2350) (`.pan/drafts/pan-2350.md`, revision 5)
**Ships:** after the Overdeck Anywhere release ([PAN-4774](https://github.com/eltmon/overdeck/issues/4774) acceptance run). One release, no phases. "Build order" orders the work by dependency only.

**Why this exists.** PAN-2350 serves the phone as a PWA over Tailscale Serve HTTPS ("Phone" decision, `pan-2350.md` line 372). A relay-plan customer without Tailscale therefore gets push notifications but cannot open the app away from home. The operator decided on 2026-11-02 to ship a native app that reaches machines through the overdeck.ai directory and relay, end-to-end encrypted, with no Tailscale. The PWA stays as the free option that works over Tailscale and needs no account.

**One PRD for both platforms.** iOS and Android share one codebase (Capacitor, D-1). The parts that differ are separate work items (W-IOS*, W-AND*), so the pipeline runs them in parallel.

## Glossary

- **Machine:** a computer running the Overdeck dashboard server (`pan up`). It has a machine key and an environment id.
- **Phone app:** the native iOS and Android app this PRD adds, at `apps/mobile`. Bundle id `ai.overdeck.app`, display name "Overdeck".
- **PWA:** the existing installable web app at `/m` (`src/dashboard/frontend/src/components/mobile/`).
- **Capacitor:** a framework that packages a web app as a native iOS and Android app. The web code runs in the platform WebView (WKWebView on iOS, Android System WebView). Native code is added as plugins. Mind Your Now ships its app with Capacitor 8 from this host today (`~/Projects/myn-rel-574/capacitor.config.ts`).
- **Directory:** the overdeck.ai connection service, `services/connect`, at `wss://connect.overdeck.ai/v1/directory`. One Durable Object per account lists the account's machines and passes WebRTC setup messages between them. It moves no conversation bytes.
- **Client:** a new directory role this PRD adds. A phone app connected to the directory. It is not a machine and does not count against the free account's three-machine limit.
- **Account token:** an `odd_…` device token from `account.overdeck.ai` (`services/account/src/devices.ts`). It authorizes the directory socket.
- **Secure channel:** the encrypted byte stream between two Overdeck endpoints. A Noise handshake (`noise-handshake` 4.2.0), then `@hyperswarm/secret-stream` 6.9.2 (libsodium `crypto_secretstream_xchacha20poly1305`). Code: `src/lib/anywhere/channel/`.
- **Pairing mode / link mode:** two channel handshake modes (`src/lib/anywhere/channel/noise.ts`). Pairing is `Noise_XXpsk0` keyed by a one-time pairing code (`odp_<64 hex>`). Link is `Noise_IK`, where the dialer pins the responder's public key.
- **Route:** one way to reach a machine. The phone app uses `rtc://<environmentId>` (direct WebRTC through NAT) and `rtc+turn://<environmentId>` (WebRTC through the TURN relay, relay plan only).
- **Phone credential:** a new access-token record kind, `phone`, on the machine (W-MAC1). It is bound to the phone's channel public key and resolves only inside a link-mode channel from that key.
- **Link key / push key:** two X25519 key pairs the phone app generates. The link key authenticates the phone in the secure channel. The push key decrypts notification payloads. The push secret key never enters JavaScript.
- **Sealed payload:** a notification payload encrypted with libsodium `crypto_box_seal` to the phone's push public key. Only the phone can open it.
- **APNs / FCM:** Apple Push Notification service and Firebase Cloud Messaging, the only ways to wake a closed iOS or Android app.
- **NSE:** iOS Notification Service Extension. A small native extension iOS runs when an alert arrives with `mutable-content: 1`. It can rewrite the title and body before display. It is how iOS shows a decrypted notification.
- **Live Activity:** an iOS lock-screen and Dynamic Island card. Its content updates by APNs push and is rendered by iOS directly, with no app code in between.

## Facts this plan is built on (verified 2026-11-02)

**The PWA reuses most of the desktop frontend.** The phone screens are about 990 lines (`MobileApp.tsx` 233, `MobileNeedsYou.tsx` 243, `MobilePairScreen.tsx` 192, `MobileIssueSheet.tsx` 128, `MobileConversations.tsx` 109, `MobilePipeline.tsx` 87). The conversation view mounts the desktop `components/chat/ConversationPanel.tsx` (1520 lines) unchanged (`MobileConversations.tsx:95`). Live data flows through `components/EventRouter.tsx` over `/ws/rpc` with the Effect `RpcClient` (`lib/wsTransport.ts:171-181`). A React Native app would have to rewrite all of this. Capacitor runs it as is.

**The RPC socket uses the page's global `WebSocket`.** `lib/wsTransport.ts:174-175`:
```ts
const socketLayer = Socket.layerWebSocket(resolvedUrl).pipe(
  Layer.provide(Socket.layerWebSocketConstructorGlobal),
```
So a `WebSocket` replacement installed on `globalThis` before the app loads carries `/ws/rpc` with no change to the RPC code.

**Inside a secure channel the wire format is HTTP/1.1.** The machine hands each decrypted channel to its Node HTTP server (`src/dashboard/server/channel-listener.ts:129-133`; WebRTC data channels enter at `acceptRawChannel`, line 99). Machines talk to each other with a Node `http.Agent` whose `createConnection` returns the channel (`src/lib/anywhere/channel/channel-agent.ts:19`). A browser has no such agent, so the phone app needs its own HTTP/1.1 and WebSocket client over the channel (W-WEB2).

**The channel libraries have browser builds, untested here.** `sodium-universal` 5.0.1 maps `sodium-native` to `sodium-javascript` (pure JS) in its `browser` field. `b4a` 1.9.0 has `browser.js`. `streamx` is browser-safe. `sodium-javascript` is not installed in this repo today. Whether Vite honours the mapping and whether pure-JS XChaCha20 is fast enough is checkpoint CP-1.

**`noise.ts` and `wire.ts` use Node APIs.** They import `node:crypto` (`createHash('sha256')`, `randomBytes`, `timingSafeEqual`) and `Buffer`. W-WEB1 moves them behind a small crypto port so the server and the phone run the same protocol code.

**A machine answers any incoming WebRTC offer.** `RtcTransport.onSignal` accepts an offer from any `from` id (`src/lib/anywhere/channel/rtc-transport.ts:231-259`). The Noise handshake decides who gets in. The machine's directory client ignores frame types it does not know (`src/dashboard/server/services/directory-client.ts:341-342`, `default: break`). So the directory can route phone↔machine signals with no change to existing machines, and `CONNECT_PROTOCOL_VERSION` stays `1`.

**The directory has no role but "machine".** A socket must send `hello` with a machine key, server version and endpoints, and each `hello` row counts against `maxDevices` (`services/connect/src/directory-state.ts:212-222`):
```ts
const existing = state.machines.find((m) => m.environmentId === env);
if (!existing && identity.maxDevices !== null && state.machines.length >= identity.maxDevices) {
```
A phone sending `hello` would use one of the free account's three machine slots. W-CON2 adds a client role.

**Account sign-in accepts loopback redirects only.** `services/account/src/pkce.ts:20-36` (`validateLoopbackRedirect`) requires `http:` and a loopback host. `PLATFORM_RE` is `/^(linux|darwin|win32)-(x64|arm64)$/` (`devices.ts:18`). `defaultLabel` falls back to "Linux device" (`devices.ts:58-62`).

**Over a channel, only `machine` credentials resolve.** `src/dashboard/server/routes/dashboard-auth.ts:176-196`:
```ts
if (channel !== null) {
  if (channel.mode !== 'link') return null;
  const verified = verifyAccessToken(bearerToken(headers));
  if (!verified.ok) return null;
  const { record } = verified;
  if (record.kind !== 'machine' || record.machineKey !== channel.remoteKeyHex || !record.environmentId || !record.access) return null;
```
Paired browser devices (`kind: 'device'`, scope `admin`) do not resolve over a channel, and session mint is refused there.

**Machine-link scopes already cover everything the phone does.** `MACHINE_TOKEN_SCOPES('operator')` (`src/lib/access-tokens.ts:93-97`) is `read:events, read:state, read:conversations, read:costs, read:settings, tell, operate, approve, forward`. The phone's actions map to those scopes (`src/dashboard/server/route-scopes.ts`):
- reading conversations, `GET /api/fleet/needs-you` and `pan.subscribeConversationMessages`: `read:conversations` (lines 36, 104, 155);
- sending a message and uploading an image: `tell` (lines 42, 133);
- answering a question (`answer-question`, `codex-approval`, `pi-ask-answer`): `approve` (lines 53-56);
- starting or stopping a turn: `operate` (lines 61, 66).

**The pairing channel has a fixed allowlist.** `src/dashboard/server/remote-request-gate.ts:113-114`:
```ts
export const PAIRING_CHANNEL_ALLOWLIST: ReadonlySet<string> = new Set(['GET /api/environment', 'POST /api/machines/exchange']);
```

**Push has a provider interface.** `src/lib/push/types.ts` defines `PushProvider { name; hasTargets(); send(notification) }`. `needs-you-push-service.ts:72-74` lists the providers:
```ts
function defaultProviders(): PushProvider[] {
  return [createWebPushProvider(), createNtfyProvider()];
}
```
The dispatcher (`src/lib/push/dispatcher.ts`) already notifies on rising edges, deduplicates, and limits to 6 pushes per 60 s for every provider.

**Release tooling exists on this host and the Mac rig.**
- Android: the Android SDK is at `~/Android/Sdk`, and MYN's signed `.aab` bundles are built here (`~/Projects/myn/release-artifacts/android-57.*`). MYN's Android app uses Firebase messaging (`android/app/build.gradle:101-105`).
- iOS: the Mac rig archives and uploads MYN with Xcode under the operator's Apple ID (skill `myn-rig-release`; machine memory `mac-rig-ios-upload`: the App Store Connect API keys cannot cloud-sign, so uploads need the Xcode Apple ID session).
- MYN's platform minimums are iOS 15.0 and Android `minSdkVersion 24`, `targetSdkVersion 36`.

**What t3code ships, for comparison** (`~/Projects/t3code`, checkout 2026-10-19). Expo SDK 58 and React Native 0.88 in `apps/mobile`, with eight custom native modules. Push goes through its relay to APNs and FCM in plaintext: the relay sees project title, thread title, phase, headline and model (`packages/contracts/src/relay.ts:120-131`). It has iOS Live Activities via `expo-widgets`. It has no end-to-end encryption between phone and machine.

## Requirements

### Functional

- **FR-1 Install from the stores.** The app is listed on the Apple App Store and Google Play as "Overdeck", bundle id `ai.overdeck.app`.
- **FR-2 Sign in.** The app signs in to overdeck.ai with GitHub through the account service's PKCE flow in the system browser, and stores the account token on the device.
- **FR-3 See your machines.** After sign-in the app lists the account's machines from the directory, with online state, label and fingerprint.
- **FR-4 Pair with a machine.** The operator pairs the app with a machine by scanning a QR code shown in that machine's Settings → Anywhere. Pairing needs no Tailscale and works across networks.
- **FR-5 Use the phone screens.** For a paired, online machine the app shows the same screens as the PWA: Needs you (with answering questions and approvals), Conversations (read and send), Pipeline. Data comes from that machine; other machines appear through its links, as in the PWA.
- **FR-6 End-to-end encryption.** Every byte between the app and a machine travels inside the secure channel. The directory, the TURN relay, Apple and Google never see plaintext conversation data.
- **FR-7 Routes.** The app reaches a machine over `rtc://` (direct). When no direct path exists and the account's plan allows relay, it uses `rtc+turn://`. Otherwise it shows "No direct path to <machine>. Install Tailscale on it or use the relay plan."
- **FR-8 Notifications.** Needs-you events (question, approval, finished, failed, summary, test) reach the phone as system notifications, even when the app is closed. The notification text is encrypted to the phone; the directory and Apple/Google see only ciphertext. Tapping one opens the matching screen.
- **FR-9 Revocation.** The machine lists paired phones next to paired browsers. Removing one ends its live connections within 5 s and stops its notifications. Signing out on the phone removes its directory registration and push token.
- **FR-10 Several machines.** The app keeps a list of paired machines and switches between them.
- **FR-11 Live Activity (iOS).** A lock-screen and Dynamic Island card shows how many items need you and how many agents are running, and nothing else (OD-1).

### Non-functional

- **NFR-1 Same protocol code.** The phone and the server run the same Noise and wire-framing source files, so the two cannot drift.
- **NFR-2 Keys stay on the device.** The link secret key is stored in the iOS Keychain (`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`) or Android Keystore-encrypted storage, and is never backed up or synced. The push secret key stays in native code. Note: the Secure Enclave supports only P-256 keys, so these X25519 keys are Keychain-protected, not Secure Enclave keys.
- **NFR-3 Not a machine.** A phone never counts against the account's machine limit. A cap of 5 clients per account bounds abuse.
- **NFR-4 Least privilege.** A phone credential carries `read:events, read:state, read:conversations, read:costs, read:settings, tell, operate, approve`. Never `admin` and never `forward`. Screens that need other scopes are hidden in the app.
- **NFR-5 Payload size.** A sealed notification fits APNs and FCM limits (4 KB): the plaintext is trimmed to 2,900 bytes before sealing.
- **NFR-6 Compatibility.** The app checks the machine descriptor's `linkProtocol` and `capabilities.phoneApp`. A machine without `phoneApp` shows "Update Overdeck on <machine> to use the app" with the minimum `pan` version.
- **NFR-7 Async only.** New server code uses async I/O. No `execSync`, no new `*Sync` tmux calls (repo rule).
- **NFR-8 Fake timers.** Tests of retries, backoff, TTLs and reconnects use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`, never real waits (repo rule). Exception: the Node integration test in W-WEB2 drives real sockets, but it has no sleeps.
- **NFR-9 Bounded reads.** The app relies on the bounded conversation open (75 rows or 1 MiB, PAN-4558); no new unbounded endpoint.

## Decisions

- **D-1 Capacitor, not React Native.**
  - **What:** `apps/mobile` is a Capacitor 8 project whose web layer is a mobile build of the existing React frontend.
  - **Why:**
    1. The phone screens, the conversation panel, the event router and the RPC client run unchanged in the WebView. React Native would rewrite about 4,000 lines and keep a second UI in sync forever.
    2. WKWebView and Android WebView both support `RTCPeerConnection` with TURN, which the directory routes need.
    3. The operator already builds and ships a Capacitor 8 app (MYN) from this host and the Mac rig, with the same signing and upload steps.
  - **Cost:** native features (push decryption, Live Activity, key storage) are written as small Swift and Kotlin pieces in the Capacitor project.
- **D-2 The phone is a directory client, not a machine.** A new `hello-client` frame registers the socket in a separate `clients` table. Clients receive the machine list, may signal machines, and may request ICE servers. Machines may signal clients. Clients may not signal clients. Clients do not count against `maxDevices`; at most 5 clients per account.
- **D-3 Pairing reuses the pairing-mode channel.** The machine shows a QR code carrying its environment id, machine public key and a one-time `odp_` pairing code. The phone dials `rtc://<environmentId>` through the directory, opens a pairing-mode channel with the code, and calls a new `POST /api/phones/exchange`. That route mints the phone credential. Each machine is paired separately; the fleet is seen through the paired machine's links, as in the PWA (PAN-2350 D-1).
- **D-4 Phone credential.** A new access-token kind `phone`, bound to the phone's link public key (`phoneKey`). It resolves only inside a link-mode channel whose `remoteKeyHex` equals `phoneKey`. Scopes per NFR-4.
  - **CSRF is not required for `phone` credentials.** CSRF protects ambient cookie authentication from cross-site requests. A phone request carries an explicit bearer token inside a channel the Noise handshake authenticated, so there is no ambient credential to abuse.
- **D-5 Push goes through the directory, sealed.** The machine seals each notification to the phone's push key and sends it in a `push` frame to the directory, addressed to the phone's client id. The directory looks up the phone's APNs or FCM registration and delivers the ciphertext.
  - **This reverses PAN-2350 D-16 for the phone app only.** D-16 said push needs no relay. That stays true for Web Push and the PWA. Native push cannot avoid Apple and Google, and the machine should not hold APNs or FCM credentials, so the directory forwards it. The content stays end to end encrypted.
  - **iOS:** an alert push with placeholder text ("Overdeck", "Something needs you"), `mutable-content: 1` and the sealed payload in a custom key. The NSE decrypts it and replaces the title and body. If decryption fails, the placeholder shows.
  - **Android:** a data-only FCM message carrying the sealed payload. A native `FirebaseMessagingService` decrypts it and posts the notification, also when the app is closed.
  - Push tokens are registered with the directory by the phone, so the machine never sees an APNs or FCM token.
- **D-6 Sign-in redirect.** The app uses the private-use URI scheme `ai.overdeck.app:/oauth/callback` (RFC 8252 §7.1) with PKCE. The account service allows exactly this redirect. It needs no website changes, unlike universal links.
- **D-7 One protocol implementation.** `noise.ts` and `wire.ts` move into a new workspace package `packages/anywhere-channel` (MIT) with a crypto port (`sha256`, `randomBytes`, `timingSafeEqual`). The server's `src/lib/anywhere/channel/` imports them from the package with a Node port; the phone imports them with a WebCrypto/`@noble/hashes` port.
- **D-8 Licence.** `apps/mobile` and `packages/anywhere-channel` are MIT like the rest of the repo. The directory's push forwarding lives in `services/connect`, which stays FSL-1.1-MIT (`services/LICENSE.md`).
- **D-9 Plans.** The app is free to download. It works on the free account (directory and direct connections for up to 3 machines; phones are not counted). Relay needs the relay add-on, as for machines. Push forwarding is available on every plan; the directory limits it to 30 pushes per minute per account.
- **D-10 No over-the-air updates.** Releases go through the stores. Capacitor has no first-party OTA, and a third-party update channel would let a server change the code that holds the keys.
- **D-11 Correction to PAN-2350.** `pan-2350.md` D-2 says the channel uses "ChaCha20-Poly1305" and that "all three primitives are in Node's built-in `crypto`". The handshake uses `crypto_aead_chacha20poly1305_ietf`, the bulk stream uses libsodium `crypto_secretstream_xchacha20poly1305`, and the crypto comes from libsodium (`sodium-native`), not Node's `crypto`. W-DOC fixes the epic text.

## Open decisions

None open.

- **OD-1 Live Activity content (settled by the operator, 2026-11-02): counts only.** An APNs `liveactivity` push carries the card's content, and iOS renders it with no app code in between, so it cannot be decrypted on the phone the way an alert can. The card therefore shows only "N need you · M running": no titles, names or text. The directory and Apple see those two numbers per update and nothing else. Full content like t3code's was rejected because it breaks FR-6. The Live Activity is on by default, with a switch in the app's Settings to turn it off.

## Architecture

```
 Phone app (Capacitor WebView)                       overdeck.ai                         Machine (pan up)
 ─────────────────────────────                       ───────────                         ────────────────
 sign-in ── system browser ──────────────► account.overdeck.ai  (PKCE, ai.overdeck.app:/oauth/callback)
 directory socket  ── hello-client ──────► connect.overdeck.ai ◄── hello ──────────────── directory client
 RTCPeerConnection ◄──── offer/answer/ICE via `signal` frames ────►                       werift RtcTransport
        │  data channel "ovdl" (direct, or TURN on relay plan)                                     │
        └──────────── Noise (pairing XXpsk0 once, then link IK) + secret-stream ──────────────────►│ acceptRawChannel
            HTTP/1.1 + WebSocket over the channel: /api/*, /ws/rpc                                 │ Node HTTP server
 notifications ◄── APNs / FCM ◄── connect (ciphertext only) ◄── `push` frame (sealed) ─────────────┘ native push provider
```

     - `push-unregister {}`, `forget-client {}`
  2. Add directory → client frames: `welcome-client { protocol, plan, relayAllowed, machines: DirectoryMachine[] }`; reuse `directory`, `signal`, `ice-servers`, `relay-status`, `error`.
  3. Add machine → directory `push { requestId: <32 hex>, to: <clientId>, sealed: <base64, ≤ 3,072 chars>, urgency: 'high' | 'normal', collapseId: <32 hex> }` and directory → machine `push-result { requestId, ok: boolean, error?: 'no_registration' | 'rate_limited' | 'delivery_failed' | 'unknown_client' }`.
  4. Add `CLIENT_LIMIT = 5`, `CLIENT_LIMIT_MESSAGE = 'This account already has 5 phones. Remove one in the app or on a machine.'`, `PUSH_RATE_PER_MINUTE = 30`.
  5. Keep `CONNECT_PROTOCOL_VERSION = 1`.

### W-CON2 — Directory: the client role

- **What and why:** D-2. Phones join the directory without using a machine slot.
- **Files:** `services/connect/src/protocol.ts` (decoder), `services/connect/src/directory-state.ts`, `services/connect/src/directory.ts` (storage and socket tags), new `services/connect/src/clients.ts` if `directory-state.ts` would pass 600 lines; tests under `tests/unit/services/connect/`.
- **Steps:**
  1. Storage: new table `clients(client_id TEXT PRIMARY KEY, label TEXT, public_key_hex TEXT, platform TEXT, app_version TEXT, device_id TEXT, registered_at INTEGER, last_seen_at INTEGER, push_platform TEXT, push_token TEXT, aps_environment TEXT)`. Add it in the existing schema bootstrap in `directory.ts` (the DO uses `CREATE TABLE IF NOT EXISTS`; no wrangler migration is needed for new tables in an existing SQLite class).
  2. Socket attachment gains `role: 'machine' | 'client'` and `clientId`. Tag client sockets `client`.
  3. `hello-client`: if `clients` already has 5 rows and `clientId` is new, send `error{code:'client_limit', message: CLIENT_LIMIT_MESSAGE}` and close with a new close code `4013 clientLimit` (add to `CONNECT_CLOSE_CODES`). Otherwise upsert the row, send `welcome-client`, and send `directory` frames to the client on every machine change. A second socket with the same `clientId` closes the older one with 4011.
  4. `signal` routing:
     - client → machine: allowed when `to` is an online machine; `from` is stamped with the clientId; `purpose` must be `'link'` (else `bad_frame`).
     - machine → client: allowed when `to` is an online client.
     - client → client: `bad_frame`.
  5. `ice-servers` and `relay-usage` from clients follow the machine rules unchanged (plan check, cap, metering by account).
  6. Clients are not counted in `maxDevices`, never appear in machines' `directory` frames, and are not sent `approval-request`.
  7. `forget-client` deletes the row and closes with 4012.
  8. Browser WebSockets cannot send an `Authorization` header, so `GET /v1/directory` (`services/connect/src/routes.ts:88-102`, auth in `account.ts:27`) also accepts the account token as the subprotocol `overdeck.bearer.<odd_token>` in `Sec-WebSocket-Protocol`, and echoes that subprotocol in the 101 response (browsers drop a connection whose chosen subprotocol is missing). The header form stays for machines.
- **Tests:** the subprotocol form authenticates and is echoed; a phone's `hello-client` on a free account that already has 3 machines succeeds; a 6th client gets 4013; client→machine signal is delivered with `from` = clientId; client→client is refused; machine→client is delivered; a client never appears in a machine's `directory` frame.
- **Verify:** `npm run typecheck:connect` (or the service's typecheck script); `npx vitest run tests/unit/services/connect/`.

### W-CON3 — Directory: push registration and delivery

- **What and why:** D-5. Deliver sealed notifications to APNs and FCM.
- **Files:** new `services/connect/src/push/apns.ts`, `services/connect/src/push/fcm.ts`, `services/connect/src/push/deliver.ts`; `directory-state.ts` (frame handling); `services/connect/src/env.ts` (new secrets); `services/connect/wrangler.jsonc` (new vars); tests under `tests/unit/services/connect/push/`.
- **Steps:**
  1. `push-register` from a client stores `push_platform`, `push_token`, `aps_environment` on its row. `push-unregister` clears them.
  2. `push` from a machine: check that `to` is a client of the account with a registration (else `push-result{ok:false,error:'no_registration'}` or `'unknown_client'`). Enforce 30 per minute per account (else `'rate_limited'`). Deliver, then answer `push-result`.
  3. APNs (`apns.ts`): token auth with an ES256 JWT from the `.p8` key (`APNS_KEY_P8`, `APNS_KEY_ID`, `APNS_TEAM_ID`). Cache the JWT for 45 minutes; APNs answers `429 TooManyProviderTokenUpdates` when it is refreshed more often than about every 20 minutes (t3code `infra/relay/src/agentActivity/ApnsProviderTokens.ts:12-17`). Host `api.push.apple.com`, or `api.sandbox.push.apple.com` when `aps_environment` is `sandbox`. Headers: `apns-push-type: alert`, `apns-topic: ai.overdeck.app`, `apns-priority: 10` for `high` else `5`, `apns-collapse-id: <collapseId>`. Body:
     ```json
     { "aps": { "alert": { "title": "Overdeck", "body": "Something needs you" }, "mutable-content": 1, "sound": "default", "thread-id": "<collapseId>" }, "s": "<sealed>" }
     ```
  4. ## Implementation checkpoints

- **CP-1 Sodium in the WebView** (W-WEB1). Fallback: `libsodium-wrappers` adapter.
- **CP-2 Direct URL loads** (W-WEB2). Fallback: hide those elements in the native build.
- **CP-3 Background connection.** iOS suspends the WebView in the background, which drops the WebRTC connection. The app reconnects on foreground; notifications cover the background. Pass: after 5 minutes in the background, reopening shows fresh Needs-you data within 5 s on the same network. If reconnect takes longer, show cached data with an "Updating…" banner; no background keep-alive.

- **CP-4 Camera in the WebView** (W-APP1). The PWA's scanner uses `getUserMedia` and `jsqr` (`MobilePairScreen.tsx`). Confirm that it opens the rear camera inside WKWebView on the `capacitor://localhost` origin and inside Android WebView (with `NSCameraUsageDescription` and the Android `CAMERA` permission). **Fallback:** `@capacitor/camera` takes a photo and `jsqr` decodes it (MYN uses `@capacitor/camera` 8.2 on this toolchain); the `ai.overdeck.app:/pair#…` link path needs no camera at all.

## Hazards

- **H-1 Pairing code reuse.** The code pool is shared with browser and machine pairing (`pairing-credentials.ts`). A code shown for the app could be used by a browser. Accept: the code is single use, expires in 10 minutes, and the exchange route decides what the code mints.
- **H-2 Relay metering by the phone.** The phone reports its own relay bytes, as machines do. A modified app could under-report. Accept for now (same trust model as machines); the TURN credential TTL is 600 s.
- **H-3 Store review.** Apple may ask how sign-in works for reviewers. Provide a reviewer account on the allowlist and a test machine that stays online during review.
- **H-4 Push permission denied.** The app works without notifications; Settings shows how to turn them on.

## Acceptance criteria
