## 0. Glossary

- **Pack.** A third-party git repo of Agent Skills registered with `pan skills pack add` (PAN-4334). Registry: `~/.overdeck/config.yaml` → `skills.packs.<id>: { url, ref, commit, adapter? }`.
- **Trusted commit.** The 40-hex commit the operator approved at add time. Every launch mounts exactly this commit.
- **`KNOWN_PACKS`.** The per-pack-id defaults table in `src/lib/skill-packs/adapters.ts` (search `export const KNOWN_PACKS`). Keyed by **pack id**, not URL. Read by `sources.ts` (`packAdapter`, `manifestAt`), `catalog.ts` (`listPackCatalog`), `store.ts` (`disclosure`) and the CLI.
- **Adapter.** How a pack checkout is read: `plain` (scan a dir for `*/SKILL.md`), `claude-plugin` (read `.claude-plugin/plugin.json`, else scan `skills/`), `deft-readonly`.
- **Plugin root (new).** A repo-relative directory that holds the pack's plugin: `.claude-plugin/plugin.json`, `skills/`, `agents/`, `hooks/`, `.mcp.json`, `commands/`, `LICENSE`. Default: the repo root (`''`). For pstack: `harness/pstack/claude-code`. New field `KnownPack.pluginRoot`.
- **`skillsRoot` (existing).** The directory the `plain` adapter scans instead of `skills/` (only `sageox` uses it: `extensions/skills`). It stays; it is resolved relative to the plugin root, which is the repo root for every pack except pstack.
- **Mount.** The content-addressed wrapper `~/.overdeck/packs/mounts/<sha256>/plugins/<pack>/…` built per launch selection (`src/lib/skill-packs/mount.ts`). Today it holds only `skills/<name>/` copies plus generated `.claude-plugin/plugin.json` and `.codex-plugin/plugin.json`.
- **Mount extras (new).** Plugin-root-relative paths of read-only reference files a known pack's skills link to by relative path, copied into `plugins/<pack>/<path>` next to `skills/`. New field `KnownPack.mountExtras`. For pstack: `['docs', 'README.md']`.
- **Opt-in skill.** A pack skill that the pack toggle never turns on; only a per-skill `on` does (`resolvePackSkill` in `src/lib/skill-overrides/resolve.ts`).
- **Harness-visible name.** Claude Code and Codex namespace plugin skills as `<plugin>:<skill>`, so pstack's `tdd` is `/pstack:tdd`. Overdeck's own id is `pstack/tdd`.
- **pstack.** Lauren Tan's (poteto's) skill set in Cursor's plugin repo. The fork `https://github.com/eltmon/plugins` (MIT) was forked 2026-11-01 from `cursor/plugins` main at `ae5650febf4320793844c12c4adaa937f417f8da`; fork `main` still equals that commit (verified with `git ls-remote`).
- **Claude Code adapter doc.** `harness/pstack/claude-code/docs/harness/claude-code.md` (67 lines). It maps Cursor tool, subagent, model and path names to Claude Code. 23 of the 58 `SKILL.md` files open with "read [the Claude Code adapter](../../docs/harness/claude-code.md) once per session".
- **Workspace CLI.** The CLI built from this workspace: `node /home/eltmon/Projects/overdeck/workspaces/feature-pan-4728/dist/cli/index.js`. The deployed `pan` (0.72.0) does not have this issue's code until the PR merges and `pan reload` runs.

## 1. Verdict

pstack fits the existing pack machinery with three small extensions and one CLI convenience:

1. **Plugin root.** `readPackManifest` reads everything under `join(root, pluginRoot)` and returns skill dirs **repo-relative** (prefixed with the plugin root). Because `PackSkill.dir` stays repo-relative, `treeHash` (git `commit:path`), `listExecutables`, and the mount's `join(pack.root, skill.dir)` keep working unchanged.
2. **Subfolder extraction.** `extractCommit` archives only the plugin root (`git archive <commit> -- <pluginRoot>`), so the blobless clone never downloads the dozen unrelated Cursor plugins.
3. **Mount extras.** The mount also copies `docs/` and `README.md` from the plugin root into `plugins/pstack/`. Without it, the `../../docs/harness/claude-code.md` link in 23 skills dangles, and the adapter doc's own "read the local copy and never fetch it" rule pushes the agent toward fetching upstream `cursor/plugins` URLs, which the operator forbids.
4. **CLI defaults.** `pan skills pack add <id> [url]`: the url defaults to `KNOWN_PACKS[id].url` and `--ref` defaults to the new `KNOWN_PACKS[id].ref`. Only `pstack` gets a default ref (the fork commit), so `pan skills pack add pstack` works with no other argument.

No fork changes are needed: the fork's `harness/pstack/claude-code/` build is mounted as-is.

## 3. Decisions (auto mode)

- **D1 — Add `KnownPack.pluginRoot`; keep `skillsRoot`.** They mean different things: `pluginRoot` relocates the whole plugin (manifest, skills, capability probes, license); `skillsRoot` changes only the `plain` scan dir. Folding sageox into `pluginRoot: 'extensions'` would move its capability probes from the repo root to `extensions/` and could change its "Not applied" output, which the acceptance forbids. `skillsRoot` is resolved under the plugin root; with no `pluginRoot` that is the repo root, so sageox is unchanged.
- **D2 — `pluginRoot` comes from `KNOWN_PACKS` only.** No registry field, no `--plugin-root` CLI flag. Any `pack add pstack <other-url>` still gets the pstack root, the same way `mattpocock` defaults apply by id.
- **D3 — `PackSkill.dir` stays repo-relative.** `readPackManifest` computes `base = join(root, pluginRoot)`, runs the existing logic against `base`, and prefixes every returned skill dir and executable with `pluginRoot`. `treeHash`, `updatePack`'s `changed` diff, `listExecutables`, and `populateMount` need no change for skills.
- **D4 — Extract only the plugin root.** `extractCommit(id, commit, pluginRoot?)` adds `-- <pluginRoot>` to `git archive`. The extraction dir stays `packs/<id>/<commit>/` and keeps repo-relative paths inside it (`<dir>/harness/pstack/claude-code/…`). An existing extraction is reused only when `join(dir, pluginRoot)` is a directory; otherwise the stale dir is removed and re-extracted.
- **D5 — Mount extras.** `KnownPack.mountExtras` (plugin-root-relative). `launch.ts` passes `pluginRoot` and `mountExtras` from `KNOWN_PACKS[pack.id]` into `MountPack`. `populateMount` copies each extra that exists with the same symlink-skipping copy and skips a missing extra silently (a later commit may drop it). Each extra enters `mountHash` as an entry, so packs without extras keep their current hash and `MOUNT_FORMAT_VERSION` stays `2`. An extra may not be `skills`, `.claude-plugin`, `.codex-plugin`, or start with one of them followed by `/`, and may not escape the plugin root.
- **D6 — pstack extras are `['docs', 'README.md']`.** The adapter doc says the plugin ships `docs/guide/` and `README.md` and tells the agent to read the local copy. 2.4 MB per content-addressed mount is acceptable.
- **D7 — Default ref is the fork commit SHA.** `KNOWN_PACKS.pstack.ref = 'ae5650febf4320793844c12c4adaa937f417f8da'` (the commit the issue names as the fork point; fork `main` equals it today). With a SHA ref, `packUpdateAvailable` reports nothing; the operator moves the pin with `pan skills pack update pstack --ref <sha-or-branch>`. No other known pack gets a default ref, so `mattpocock`, `deft` and `sageox` still require `--ref`.
- **D8 — Opt-in list (7 skills).** Rule: a pstack skill is opt-in when its own procedure writes outside the task's diff — user-global config, new or edited skill files, PRs, or a network-exposed service. Opt-in: `setup-pstack` (writes `~/.claude/rules/pstack-models.md`, which every Claude Code session on the host loads), `automate-me` (writes a personal mode skill, then commits and opens a PR), `reflect` (copies a skill folder into a skills dir and edits it), `create-verification-skill` and `create-formal-verification-skill` (write a project-local skill under `.cursor/skills/` → `.claude/skills/`, an Overdeck sync target in workspaces), `maintain-verification-skill` ("at most one PR of proven corrections"), `make-bot-ui` (builds a webhook UI for a Grok bot and exposes it on Tailscale). Not opt-in: `poteto-mode` — the operator named it as wanted, it is user-invoked only (`disable-model-invocation: true`), and its PR/shipping playbooks run only when the operator drives it; the docs warn about them. `maintain-formal-verification-skill` edits verification files in the repo like any coding skill and opens no PR, so it stays default.
- **D9 — Agents stay "Not applied".** The mount carries skills (plus extras), never `agents/`. `poteto-mode` asks for `pstack:poteto-agent`/`pstack:comment-sicko` subagents; under the mount those types do not exist and the agent falls back to `general-purpose`. Documented, not fixed.
- **D10 — Codex gets the Claude Code build.** The fork has no Codex build of pstack. The mount already writes a `.codex-plugin/plugin.json`; skills that name Claude Code tools still load. Documented.
- **D11 — Preview shows the root.** `PackPreview` gains `pluginRoot?: string` (set only when the known pack has one); the CLI preview prints a `Root` row after `Source`. Executables are already printed repo-relative, so they show the root too.
- **D12 — Live verification uses the workspace CLI against the real host.** Same shape as PAN-4424 WI-4/WI-5: register pstack on the host (registration enables nothing), turn it on for project `panopticon-cli` for the length of the check, verify the mount and a Claude Code slash invocation, then set it back to `inherit`. End state: pstack registered at `ae5650f`, every toggle off/inherit.
