# PAN-5093 — Disk alert: Needs-you item and phone push when free disk drops below 5 GiB / 2 GiB

**Issue:** https://github.com/eltmon/overdeck/issues/5093
**Planned:** 2026-11-06 (auto mode, high effort)

## Why

On 2026-11-06 free space on `/` fell 7.5 GiB → 4.1 GiB → 17 MB within about an
hour. Nothing told the operator; the Flywheel found it on a tick. At that level
SQLite (`~/.overdeck/overdeck.db`, `opencode.db`) and transcript JSONL writes can
fail mid-write and zero-fill files (the 2026-08 crash-reboot truncation and
PAN-1674 incidents). The second drop came from the dashboard's own conversation
search index (`embeddings.db`, 3.8 → 4.08 GB in about a minute).

Today's code has two disk guards and neither tells anyone:

- `src/lib/disk-floor.ts` refuses **new** workspace setups below 10 GiB (PAN-4961).
- `src/lib/cloister/disk-pressure-patrol.ts` (PAN-3809) prunes Docker BuildKit
  cache below 10 GiB and writes an activity entry.

This issue adds an operator alert: a Needs-you item on the dashboard and the
phone, and a phone push, once per threshold crossing, with a read-only list of
the biggest space holders so the operator can decide what to delete.

## Glossary

- **Overdeck home** — the directory `getOverdeckHome()` returns
  (`src/lib/paths.ts`), normally `~/.overdeck`. The alert watches the filesystem
  that holds it.
- **Free bytes** — `statfs(path).bavail * statfs(path).bsize`, exactly what
  `readAvailableBytes` in `src/lib/disk-floor.ts` (line 18) returns: space an
  unprivileged process can still write.
- **Level** — the alert state: `ok`, `warning` (free below the warning
  threshold) or `critical` (free below the critical threshold).
- **Crossing** — a level change upward in severity: `ok → warning`,
  `ok → critical` or `warning → critical`. Only crossings push.
- **Recovery margin** — 0.5 GiB of hysteresis. A level lowers only when free
  bytes reach that level's threshold **plus** the margin, so free space that
  hovers at 5.0 GiB does not push on every poll.
- **Holders** — the read-only hint list: the sizes of the biggest directories
  and files on the same filesystem, plus Docker's reclaimable bytes.
- **Needs-you** — the dashboard's list of everything waiting on the operator.
  One hook (`useDecisions`, `src/dashboard/frontend/src/lib/useDecisions.ts`)
  builds it; `DecisionsPanel` (desktop) and `MobileNeedsYou` (the `/m` phone
  screen) render it.
- **Push dispatcher** — `createNeedsYouDispatcher` in
  `src/lib/push/dispatcher.ts`, owned by the needs-you push service
  (`src/dashboard/server/services/needs-you-push-service.ts`). It fans one
  notification out to Web Push, ntfy and the Overdeck app (`native`).
- **Edge notification** — a one-shot push sent through
  `dispatcher.observeEdge(notification)`. It dedups by `tag` for 24 h
  (`EDGE_TAG_TTL_MS`, dispatcher.ts line 26), so every crossing needs a tag that
  includes a timestamp.
- **Primary dashboard** — the dashboard process that is not a peer
  (`isPeerDashboardProcess()` false, `src/dashboard/server/main.ts` line 247). Only
  the primary runs the push service; a peer would send every push twice.

## Decisions (made in this doc)

- **D-1 Placement: the primary dashboard, not the Deacon.** The push dispatcher
  lives in the primary dashboard process, and the deacon child is a separate
  Node process. A dashboard service reaches the dispatcher with a function call;
  a deacon patrol would need a new cross-process event. The alert also must not
  sit behind the Deacon freeze (`deacon.globally_paused` silences every
  deacon-lite routine): a frozen Deacon is exactly when nobody is watching. This
  also settles the issue's TENET-10 note: nothing goes into the Deacon patrol.
- **D-2 Push kind: reuse `kind: 'failed'`, `category: 'failed'`.** A new kind
  would be dropped by every operator who lists `push.events` explicitly, and a
  new phone category is a key of the phone app's closed `CATEGORY_LABEL` record,
  so it needs a phone-app change and release. Consequence: a phone with the
  **Failures** type muted, or paused, gets no disk push. The Needs-you item
  still shows.
- **D-3 "Louder" critical alert.** The critical crossing sends its own push with
  the title `Disk critical · <x> GiB free` and puts the Needs-you item in the
  blocking group (sorted first). Web Push and the Overdeck app already send
  `failed` at `high` urgency, and ntfy at priority 4. Raising ntfy to priority 5
  is out of scope.
- **D-4 Thresholds are config; poll interval and margin are constants.**
  `resources.disk_warn_gb` (default 5) and `resources.disk_critical_gb` (default
  2), in GiB, matching the existing `memory_warn_gb` naming. The poll interval
  (`DISK_ALERT_POLL_MS = 30_000`) and the recovery margin
  (`DISK_ALERT_RECOVERY_MARGIN_BYTES = 0.5 GiB`) are documented constants. A
  critical value that is not lower than the warning value falls back to both
  defaults with one console warning per distinct pair (the `merge-cpu.ts`
  inverted-threshold pattern). Values must be finite numbers > 0 and ≤ 1024;
  anything else is ignored (the previous layer's value stays).
- **D-5 Config changes apply without a restart, read asynchronously.** Each
  poll reads thresholds with the async `loadGlobalConfigNoMigration()`
  (`src/lib/config-yaml/load.ts`, the machine-wide global-config reader used for
  `resources.quality_gate_slots`), never `loadConfigSync()`, which calls
  `existsSync`/`statSync`/`readFileSync` (NFR-1). A rejected read keeps the
  last good thresholds (the defaults before the first success). The holder
  collector reads `conversationSearch.dbPath` the same way.
- **D-6 First sample already low ⇒ push.** The service starts at level `ok`, so
  a dashboard that starts while the disk is low pushes once. Fail loud is the
  point of this issue. A restart while the disk stays low pushes again; that is
  accepted.
- **D-7 Push first, holders after.** Measuring holders runs `du` over trees as
  large as 53 GiB and can take minutes on a nearly full disk. The push and the
  Needs-you item go out at once; holders attach to the item when ready
  (`measuring: true` until then). Holders are measured once per crossing, never
  per poll, with a 120 s timeout per path, at most 4 `du` processes at a time.
  A timed-out path is left out and the result is marked `incomplete: true`.
- **D-8 Holders are read-only.** Nothing is deleted, pruned or moved.
- **D-9 Conversation search index.** The holder list always includes the
  configured `conversationSearch.dbPath` file and, when it differs and exists,
  the default-path file `~/.overdeck/conversations/embeddings.db`, labeled "not
  in use". Cleaning up or migrating the stale copy is a NonGoal of this issue
  (the issue scopes the hints as read-only); the label tells the operator it is
  safe to judge.
- **D-10 Rate limit stays.** Disk pushes go through the dispatcher's normal
  path (`enabled`, `events`, rate limit, phone mute/pause). In a burst of more
  than 6 notifications a minute, a disk push can be folded into the
  `N more items need you` summary; the Needs-you item still shows the details.
- **D-11 Activity feed entries.** Each crossing and each recovery to `ok` writes
  one activity entry (`source: 'dashboard'`, `link: '/resources'`), `warn` for
  warning, `error` for critical, `info` for recovery. Critical entries set
  `desktop: true`.
- **D-12 Needs-you item shape.** One item with id `disk-alert`; `kinds:
  ['diskLow']` at warning, `['diskCritical']` at critical; `diskCritical` is a
  blocking kind, `diskLow` is not. It renders its own card on the desktop
  (never the generic row, whose **Answer** button calls `requestReopen(id)` on
  a subject id) and a read-only line on the phone. The `source` field is
  `'agent'`, following the `mcpSignInDecisions` precedent; the card ignores it.
- **D-13 Peers.** A peer dashboard does not run the service. Its
  `GET /api/disk-alert` answers `level: 'ok'` with `checkedAt: null`, so a peer
  shows no item (the primary shows it).
- **D-14 Snapshot type lives in `@overdeck/contracts`.** Server and frontend
  share `DiskAlertSnapshot` from `packages/contracts/src/disk-alert.ts`.

## Requirements

### Functional

- **FR-1** When free bytes on the Overdeck home's filesystem drop below the
  warning threshold (default 5 GiB), the dashboard raises one Needs-you item and
  sends one phone push whose body names the free space ("Disk low: 4.1 GiB
  free …").
- **FR-2** When free bytes drop below the critical threshold (default 2 GiB),
  a second push goes out with the title `Disk critical · <x> GiB free`, and the
  Needs-you item becomes blocking.
- **FR-3** Each crossing pushes once. Staying at a level pushes nothing more;
  moving down a level (critical → warning) pushes nothing; a new crossing after
  a recovery to `ok` pushes again, even within 24 h.
- **FR-4** The Needs-you item clears when free bytes reach the warning threshold
  plus the 0.5 GiB margin; critical lowers to warning at the critical threshold
  plus the margin.
- **FR-5** Thresholds come from `resources.disk_warn_gb` and
  `resources.disk_critical_gb`, with documented defaults 5 and 2; an inverted
  pair falls back to the defaults with a warning.
- **FR-6** The Needs-you item lists the top space holders on the same
  filesystem — each child of the Overdeck home, `~/.claude/projects`,
  `~/.local/share/opencode/opencode.db`, the conversation search index (in-use
  and stale copies), the known caches (`~/.local/share/pnpm/store`,
  `~/.cache/huggingface`, `~/.cache/ms-playwright`, `~/.npm/_cacache`,
  `~/.bun/install/cache`, `~/.cache/uv`) — plus Docker's reclaimable bytes.
- **FR-7** `GET /api/disk-alert` returns the current `DiskAlertSnapshot`; paired
  phones read it with the `read:state` scope.
- **FR-8** Each crossing and each recovery writes one activity entry linking to
  `/resources`.

### Non-functional

- **NFR-1** No `execSync`, `statfsSync` or other blocking call in the service or
  anything it calls (dashboard server rule).
- **NFR-2** Tests use `vi.useFakeTimers()` for the poll interval and inject
  `readAvailableBytes`, the holder collector, the clock and the push sink; no
  test calls real `statfs`, `du` or `docker`.
- **NFR-3** `src/dashboard/server/main.ts` grows by at most 7 lines;
  `schema.ts` stays ≤ 1114 and `merge.ts` ≤ 1045 lines.
- **NFR-4** A failed `statfs` read skips that poll (level unchanged, no push);
  a failed holder measurement never throws into the poll loop.
- **NFR-5** One poll costs one `statfs` call; `du`/`docker` run only on a
  crossing.

## Snapshot contract (D-14)

```ts
// packages/contracts/src/disk-alert.ts
export type DiskAlertLevel = "ok" | "warning" | "critical"

export interface DiskSpaceHolder {
  readonly label: string   // e.g. "~/.overdeck/transcript-preservation", "Docker reclaimable"
  readonly path: string | null  // null for Docker
  readonly bytes: number
}

export interface DiskAlertHolders {
  readonly measuredAt: string     // ISO
  readonly incomplete: boolean    // at least one path timed out or failed
  readonly holders: readonly DiskSpaceHolder[]
}

export interface DiskAlertSnapshot {
  readonly level: DiskAlertLevel
  readonly path: string                 // the watched directory (Overdeck home)
  readonly availableBytes: number | null
  readonly totalBytes: number | null
  readonly warningBytes: number
  readonly criticalBytes: number
  readonly since: string | null         // ISO time the current non-ok level began
  readonly checkedAt: string | null     // ISO time of the last successful statfs; null on a peer
  readonly measuring: boolean           // holders measurement in flight
  readonly holders: DiskAlertHolders | null
}
```

     not `ok` now (a new crossing happened), call `ensureHolderScan()` again so

## Critique response

Answers to `.pan/drafts/PAN-5093-critique.md` (round 1). All four findings were
accepted and the design changed.

### A failed refresh clears an active alert

Accepted. WI-6 step 1 now makes `fetchDiskAlert` throw on a non-ok response or
network error instead of returning `null`, and the query sets `retry: false`.
React Query keeps `data` at the last successful snapshot when a refetch
rejects, so the card stays until the server reports `ok`. WI-6 tests add a
warning response followed by a rejected refetch, which must still produce the
`diskLow` decision.

### Recovery does not invalidate a running holder scan

Accepted. WI-4 now keeps an `alertGeneration` counter that increments on every
recovery to `ok`. A scan records the generation it started under and publishes
only when that generation is still current and the level is not `ok`. If a
stale scan settles after a new crossing, the service starts a fresh scan. Tests
cover recovery during a scan (holders stay `null`) and recovery then
re-crossing during a scan (the collector runs a second time).

### Two crossings can exceed the four-process disk limit

Accepted. WI-4 now allows one holder scan at a time for the whole service
(`scanInFlight`). A warning → critical crossing during a running scan reuses
it, so at most `HOLDER_DU_CONCURRENCY` (4) `du` processes ever run. A shared
`createPromiseConcurrencyLimiter` was not needed: with one scan at a time the
per-call limit in WI-3 is the service-wide limit. A test with an unresolved
collector across a warning and a critical poll asserts the collector was called
once.

### The scheduled poll uses synchronous filesystem reads

Accepted. D-5 and WI-4 now read thresholds with the async
`loadGlobalConfigNoMigration()` (global config merged over defaults; disk
thresholds are machine-wide, like `resources.quality_gate_slots`).
`readThresholds` is `() => Promise<DiskAlertThresholds>`; a rejection keeps the
last good thresholds, and a test covers it. The holder collector's
`conversationSearch.dbPath` comes from the same async read. No `loadConfigSync`
call remains in the service path.

### The critical card inherits an inaccurate group hint

Accepted (framing). WI-6 step 6 renders the disk item in its own `System` group
above "Blocking work", with the hint "Overdeck's machine needs attention", so
the panel never claims an agent is waiting. `blocking: true` at critical keeps
it sorted first on every other surface.

### Unresolved after two critic rounds

- A config read error can clear an active disk alert
- Sending a disk push still blocks the dashboard event loop
