# PAN-4201 — Command Deck issue tree: real state badge, one resource cluster, labelled progress, clearer hierarchy

**Issue:** [PAN-4201](https://github.com/eltmon/overdeck/issues/4201)
**Planned:** 2026-09-25 (auto planning mode — every open question is decided in this document; see "Planning Q&A / auto decisions").

## 1. Glossary

- **Command Deck issue tree** — the left-sidebar "Issues" section of the Command Deck. `ProjectNode` renders one `FeatureItem` per issue; `FeatureItem` renders the issue row plus, when expanded, its session rows, conversation rows, UAT stack group and resources group. Files live in `src/dashboard/frontend/src/components/CommandDeck/ProjectTree/`.
- **Feature / feature row** — one issue row in the tree (`FeatureItem`). "Feature" is the legacy name for an issue in this directory.
- **Collapsed / expanded row** — the row's caret toggles `expanded` (persisted in `localStorage` key `mc-feature-expanded:<issueId>`). Expanded rows also render `IssueView` at `density="cockpit"`.
- **Derived issue state (`IssueState`)** — the nine pipeline states computed at read time (PAN-3917 FR-6), defined in `packages/contracts/src/derived-issue-state.ts`: `backlog`, `parked`, `planned`, `working`, `in-review`, `changes-requested`, `ready`, `merged`, `closed`. Never stored.
- **`stateLabel`** — a server-built display string from `deriveStateLabel()` in `src/dashboard/server/services/resource-discovery.ts` (line ~207). It is the source of the "Allocated" text (line 229: `if (issue.resourceSources.has('workspace') || issue.resourceSources.has('branch')) return 'Allocated';`). This issue stops *rendering* it on the row; it does not change the server.
- **`feature.state`** — the `state: IssueState | null` field the server already sends on every `/api/issues/resource-allocated` row (`ResourceAllocatedIssue.state`, resource-discovery.ts line ~112). It is `null` whenever `shouldDeriveIssueState()` is false (no live resource, no active tracker state).
- **Store derived state** — `useDerivedIssueState(issueId)` (`src/dashboard/frontend/src/lib/store.ts` line 313) reads `derivedIssueStateByIssueId`, fed by the `/ws/rpc` snapshot and `issue_state.changed` events (`packages/contracts/src/event-reducers.ts` lines 298, 635). Same derivation as `feature.state`, pushed live, but only present for issues the server has emitted.
- **Pipeline bucket** — `feature.pipelineBucket` (`PipelineBucket` in `packages/contracts/src/types.ts` line 10): `in_flight | zombie_pr | post_merge_limbo | planned_backlog | clean_terminal`.
- **State badge** — the new colored badge on the row's meta line that names the derived state. Replaces the `stateLabel` pill.
- **Activity dot** — the existing `StatusDot` primitive (`components/CommandDeck/StatusDot.tsx`) rendered on the row when an agent session is live. `dominantStatus` is already computed in `FeatureItem` (line 970) but currently only feeds the flash key.
- **Resource cluster** — the single compact icon-only group of resource facts (workspace, branch, tmux, fly.io, xBRIEF, PRD, tasks, PR, docker) that replaces today's text chip strip (`ResourceStrip`, `featureResourceChip`).
- **Pipeline pips** — the five-segment mini progress strip (`data-section="Pipeline pips"`, `data-testid="feature-pipe"`, FeatureItem.tsx line 1165), computed by `derivePipeline()` (line 851).
- **Signal tokens** — the semantic CSS custom properties in `src/dashboard/frontend/src/index.css` `:root` (lines ~191–203) and `.dark` (lines ~269–280): `--info` (machine working), `--warning` (human must act), `--success` (outcome), `--destructive` (broken), `--signal-review` (specialist verb, incl. planning), `--muted-foreground` (rest). Each has a `-foreground` text-safe variant.
- **Badge formula** — style guide: tint `8%` background / `32%` border, text in the `-foreground` variant, radius `var(--badge-radius, var(--radius-sm))`, never a pill (`999px`).

## 2. Problem

The operator's screenshot of the ISSUES section shows seven problems (issue body, verbatim intent):

1. Every row carries an **"Allocated"** pill. It is `stateLabel`'s fallback for any issue with a workspace or branch, so it says nothing.
2. **Resource chips duplicate each other**: `workspace` and `branch local 1` text chips sit on a separate line under every row (`ResourceStrip`, FeatureItem.tsx line 1176), and the expanded `ResourcesGroup` (line 1269) repeats branches and PRs.
3. The **five-segment progress bar is unexplained** — its only tooltip is the static string `"plan · work · review · test · ship"`.
4. The **expand chevron** is vertically centered on a 2–3 line row (`.featureItemRow { align-items: center }`, command-deck.module.css line 703), so it does not line up with the ID/title.
5. The **selected/expanded row** is a flat lavender block (`.featureItemWrapperSelected` and `.featureItemSelected` = `--primary` 8%, lines 388 and 699); child session rows read at the same weight as the parent, with no visible nesting.
6. **Typography**: the mono ID and a wrapped 2-line title (`.featureLabel` 2-line clamp, line 401) do not read as one unit.
7. The **flat light-gray palette** gives no hierarchy. Existing state pills also break the style guide: `999px` pill radius (`.featureState`, line 575) and hardcoded hex (`.featureState_context` `#14b8a6`/`#0f766e`, `.featureState_planning` `#8b5cf6`/`#7c3aed`, lines 604–614).

Goal: a compact, scannable list where each row answers *what is this, what state is it in, is something live on it right now, does it need me?*

## 3. Requirements

### Functional

- **FR-1** No feature row renders the text "Allocated" (or any other `stateLabel` string) as its state badge. The badge text comes only from the derived issue state.
- **FR-2** The state badge label and tone are produced by one pure function, `resolveFeatureStateBadge()`, following the table in §5.1. Source precedence: store derived state → `feature.state` → bucket/tracker fallback → no badge.
- **FR-3** A live planning session on an issue whose derived state is `planned`, `backlog` or unknown shows the badge "Planning".
- **FR-4** When the derived state is `ready`, the state badge reads "Ready" and the separate "Ready · awaiting merge" badge is gone; the `MergeButton` still renders.
- **FR-5** A row with a live agent session shows the `StatusDot` activity dot before the state badge; a row with no live session shows no dot.
- **FR-6** Resource facts appear once per row, as the icon-only resource cluster on the meta line (collapsed and expanded). The separate chip line under the row and the separate "tasks N/M" line are removed. The cluster keeps: hover popover with identifiers, click-to-open for xBRIEF / tasks / PRD, and the orphan "Cleanup" buttons.
- **FR-7** The expanded `ResourcesGroup` lists only docker containers (with live CPU/memory), headed "Containers". It no longer lists branches or PRs. `BranchNode.tsx` and `PrNode.tsx` are deleted.
- **FR-8** The pipeline pips carry a computed label naming the current step: the strip's `title` and `aria-label` read `Step <n> of 5: <step> (<status>) — plan <s> · work <s> · review <s> · test <s> · merge <s>`, and each segment has its own `title`.
- **FR-9** The caret aligns with the ID/title line; the ID and title sit on one line; the title is truncated to one line with an ellipsis and its full text in `title`.
- **FR-10** The selected row uses a neutral surface (no `--primary` lavender tint); expanded child rows are visibly nested (indent plus a hairline guide) and read quieter than the parent row.

### Non-functional

- **NFR-1** No new color palette and no hardcoded hex in the changed CSS. Every color resolves to an existing signal/neutral token. No new tokens are required (§5.2); if the implementer finds one genuinely missing, it goes into the `:root` / `.dark` blocks of `index.css` *and* the PAN-3706 four-scope region, and the PR body names it for [PAN-4197](https://github.com/eltmon/overdeck/issues/4197).
- **NFR-2** Style guide: badges use the 8%/32% formula and `var(--badge-radius, var(--radius-sm))`; no `999px` radius on the new/changed status badges; no `font-weight` above 500 on the row; maximum one *colored* status signal per row, except the style guide's permitted actionable exceptions (`! INPUT` amber, `✕ review` red).
- **NFR-3** `FeatureItem.tsx` must end at or below its `origin/main` line count (1309 at planning time). The extractions in WI-1, WI-5 and WI-6 make this hold; `scripts/lint-file-size.sh` enforces it.
- **NFR-4** Every `data-section` listed for `FeatureItem.tsx` / `ResourcesGroup.tsx` in `components/issue-view/inventory.ts` (lines 109–130) still renders, so `IssueView.test.tsx` line 72 stays green. No inventory entry is removed.
- **NFR-5** Tests: Vitest for pure helpers and component behavior; one Playwright spec for screenshots. Any test that waits on time uses `vi.useFakeTimers()` (repo rule), though none is expected here. Run only touched test files locally (`npx vitest run <files>`), never the full suite.

## 5. Design decisions

### 5.1 State badge table (FR-2, FR-3)

`resolveFeatureStateBadge(input)` in a new file `ProjectTree/featureStateBadge.ts`:

```ts
import type { IssueState, PipelineBucket, SessionNode } from '@overdeck/contracts';

export type FeatureStateTone = 'rest' | 'machine' | 'specialist' | 'human' | 'outcome';

export interface FeatureStateBadge {
  /** Stable key: an IssueState, or 'planning' / 'merged-closeout' / 'closed-tracker'. */
  key: string;
  label: string;
  tone: FeatureStateTone;
  /** Full-sentence tooltip. */
  title: string;
}

export interface FeatureStateBadgeInput {
  storeState?: IssueState | null;   // useDerivedIssueState(id)?.state
  restState?: IssueState | null;    // feature.state
  sessions?: readonly SessionNode[];
  pipelineBucket?: PipelineBucket;
  rawTrackerState?: string;
}

export function resolveFeatureStateBadge(input: FeatureStateBadgeInput): FeatureStateBadge | null;
```

Resolution order:

1. `state = input.storeState ?? input.restState ?? null`.
2. If `state` is `planned`, `backlog` or `null`, **and** any session has `type === 'planning'` with `presence === 'active' || presence === 'idle'` → `{ key: 'planning', label: 'Planning', tone: 'specialist', title: 'A planning agent is writing the plan for this issue.' }`.
3. If `state` is non-null → the row of this table:

| `IssueState` | label | tone | CSS token | title |
| --- | --- | --- | --- | --- |
| `backlog` | Backlog | rest | `--muted-foreground` | Open issue with no plan yet. |
| `parked` | Parked | rest | `--muted-foreground` | Parked by the operator; the pipeline will not pick it up. |
| `planned` | Planned | rest | `--muted-foreground` | Planned and waiting for a work agent. |
| `working` | Working | machine | `--info` | A work agent owns this issue. |
| `in-review` | In review | human | `--warning` | The pull request is in review. |
| `changes-requested` | Changes requested | human | `--warning` | Review asked for changes. |
| `ready` | Ready | human | `--warning` | Approved, green and mergeable — awaiting your merge. |
| `merged` | Merged | outcome | `--success` | The pull request is merged. |
| `closed` | Closed | rest | `--muted-foreground` | The tracker issue is closed. |

4. If `state` is `null` (and step 2 did not match):
   - `pipelineBucket === 'post_merge_limbo'` → `{ key: 'merged-closeout', label: 'Merged', tone: 'outcome', title: 'Merged; close-out has not run yet.' }`
   - `rawTrackerState` (lower-cased) contains `closed`, `done` or `canceled` → `{ key: 'closed-tracker', label: 'Closed', tone: 'rest', title: 'The tracker issue is closed.' }`
   - otherwise → `null` (the row renders **no** state badge; it never falls back to `stateLabel`).

Tone → CSS class (in `command-deck.module.css`): `featureStateBadge` base + `featureStateBadge_rest|machine|specialist|human|outcome`. Tokens: rest → `--muted-foreground`, machine → `--info` / `--info-foreground`, specialist → `--signal-review` / `--signal-review-foreground`, human → `--warning` / `--warning-foreground`, outcome → `--success` / `--success-foreground`.

The `title` for `working` appends the existing activity summary when sessions exist (reuse `buildActivitySummary`, FeatureItem.tsx line ~411): `A work agent owns this issue. <summary>.` That concatenation happens in `FeatureItem`, not in the pure helper, so the helper does not import FeatureItem.

### 5.2 Tokens (NFR-1)

Every tone maps to an existing token, so **no new tokens** are added. The PR body states: "PAN-4201 added no color tokens; it consumes `--info`, `--warning`, `--success`, `--signal-review`, `--muted-foreground` (+ `-foreground` variants) so PAN-4197 can retune them in one place." The hardcoded-hex `.featureState_context` / `.featureState_planning` classes are deleted with the rest of `.featureState_*`.

### 5.3 One colored signal per row (NFR-2, FR-5)

After this change a row's colored signals are:

- **State badge** — the one colored status signal.
- **Activity dot** — `<StatusDot status={dominantStatus} />` rendered only when `dominantStatus` is `active`, `thinking` or `waiting`. It is the "something is live right now" pulse the issue asks for. It uses the default variant (blue/amber pulse per `StatusDot`).
- **Exceptions allowed by the style guide:** `! INPUT` (amber) and `✕ review` (red) aggregate badges keep their color because they are immediately actionable.

To get there:

- Aggregate badges `▸ work` and `●●● N` render with the neutral `featureBadge_stopped` class regardless of running state (the dot now carries liveness). Their `title` text is unchanged.
- The left edge bar keeps only the error variant (`featureItemWrapperError`, red = broken). The `Working`, `Ready` and `Merged` edge variants are removed from `edgeClass` and from the CSS (they repeated the badge color). `featureItemWrapperNeedsAttention` (amber row tint) stays.
- The separate "Ready · awaiting merge" badge (`data-testid="feature-ready"`) is removed; the state badge carries `data-testid="feature-state"` and `data-state="<key>"` so tests keep a stable hook. `isReady` is recomputed as `resolvedState === 'ready'` from the same resolved state the badge uses, so the Merge button and the badge can never disagree.

### 5.4 Pipeline pips: label, don't remove (FR-8)

Decision: keep the pips (they are a no-loss inventory section) and label them. Move `PipeSegState`, `PIPE_ORDER`, `derivePipeline` and `PIPE_CLASS` out of `FeatureItem.tsx` into a new `ProjectTree/pipelineStrip.ts`, and add:

```ts
export const PIPE_STEP_LABELS = ['plan', 'work', 'review', 'test', 'merge'] as const;

/** Human label for a segment state. */
export function describePipeSegment(seg: PipeSegState): string;
// none → 'pending', done → 'done', working → 'running', paused → 'paused',
// error → 'failed', merged → 'merged'

/** Strip label: names the current step (the last non-'none' segment). */
export function describePipeline(segments: readonly PipeSegState[]): string;
```

`describePipeline` output:
- All `none` → `Not started — plan pending · work pending · review pending · test pending · merge pending`.
- Otherwise, with `i` = index of the last segment that is not `none`: `Step ${i+1} of 5: ${PIPE_STEP_LABELS[i]} (${describePipeSegment(seg[i])}) — plan <s> · work <s> · review <s> · test <s> · merge <s>`.

Example: `['done','done','working','none','none']` → `Step 3 of 5: review (running) — plan done · work done · review running · test pending · merge pending`.

JSX (FeatureItem.tsx line 1165) before:

```tsx
<span data-section="Pipeline pips" className={styles.featurePipe} data-testid="feature-pipe" title="plan · work · review · test · ship">
  {pipeline.map((seg, i) => (
    <i key={PIPE_ORDER[i]} className={...} />
  ))}
</span>
```

after:

```tsx
<span data-section="Pipeline pips" className={styles.featurePipe} data-testid="feature-pipe"
  role="img" title={pipelineLabel} aria-label={pipelineLabel}>
  {pipeline.map((seg, i) => (
    <i key={PIPE_ORDER[i]} className={...} title={`${PIPE_STEP_LABELS[i]}: ${describePipeSegment(seg)}`} />
  ))}
</span>
```

with `const pipelineLabel = useMemo(() => describePipeline(pipeline), [pipeline]);`. The segment keys stay the session types (`planning … ship`); only the human labels say `plan … merge`.

Delete the old `<div data-section="ResourceStrip">` line (1176) and the `Tasks summary` button (1177–1180).

When the expanded Containers group renders, the cluster omits its docker icon: `ResourceCluster` takes `omit?: readonly ResourceSource[]` and FeatureItem passes `['docker']` exactly when it renders `ResourcesGroup`. So each fact appears once per render.
- Delete `ProjectTree/BranchNode.tsx` and `ProjectTree/PrNode.tsx`, and their CSS (`.branchNode`, `.branchBadge`, `.prNode`, `.prNode:hover` and any `.prNode*` / `.branchNode*` descendants in `command-deck.module.css` ~6322–6360). ## 8. Intersecting repo rules (restated)

- Quality gates before `pan done`: `npm run typecheck`, `npm run lint`, `npx vitest run <touched test files>`. Never run the full `npm test` on the host.
- Style guide (`pan-style-guide`): amber = human, blue = machine, emerald = outcome, red = broken, purple = specialist verb, neutral = rest; no pill radius on status badges; no hardcoded hex; no bold (≤500 on the row); one colored signal per row.
- File-size ratchet: `scripts/lint-file-size.sh` compares with `origin/main`; `FeatureItem.tsx` has an allowlist row (1351, PAN-3231) but must not grow — the extractions shrink it.
- Worktree discipline: stay on `feature/pan-4201`; never `git checkout` or `git stash`.
- Browser verification uses its own isolated Playwright context; never attach to another agent's browser.
- `.claude/skills/*` are sync targets — edit sources under `sync-sources/` or `skills/`, never the synced copy.

1. **Badge source precedence** — store derived state, then REST `feature.state`, then bucket/tracker fallback, then no badge. Both sources come from the same FR-6 derivation; the store is live and already drives `isReady`, so one resolved value feeds both the badge and the Merge button.
