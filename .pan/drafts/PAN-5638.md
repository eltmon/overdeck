# PAN-5638 — Polyrepo review verdicts and the ready set read GitHub member PRs

**Issue:** [PAN-5638](https://github.com/eltmon/overdeck/issues/5638)
**Sibling (out of scope here):** [PAN-5641](https://github.com/eltmon/overdeck/issues/5641) — polyrepo UAT promote eligibility and the merge-train board read one PR from the non-git project root.

## Glossary

- **Polyrepo project.** A project whose `workspace.type` is `polyrepo` in `~/.overdeck/projects.yaml`. Its root (for Mind Your Now, `/home/eltmon/Projects/myn`) is not a git repository. Each entry in `workspace.repos` is a **member repo** with its own forge.
- **Writable member.** A member repo without `readonly: true` (`required === true` in `resolveConfiguredRepos`). Only writable members carry issue branches, PRs and MRs.
- **GitHub member PR.** A pull request on a writable member repo whose forge is GitHub (MYN: `mindyournow/myn-skills`, `mindyournow/openclaw-plugin`, `mindyournow/hermes-mind-your-now`, configured with `remote: github`).
- **Verdict write.** `pan admin specialists done review <issue> --status <passed|failed|blocked>` (`src/cli/commands/specialists/done.ts`, `doneCommand`). It posts the review verdict on the forge.
- **Verdict marker.** A PR comment whose first line is `<!-- overdeck-verdict: APPROVED|CHANGES_REQUESTED [sha=<sha>] -->` (`formatVerdictMarker`, `parseVerdictMarkerWithSha` in `src/lib/cloister/pr-facts.ts`). `postReviewVerdict` posts it when GitHub refuses a review on your own PR.
- **Trust rules.** The checks `pr-facts.ts` applies before a marker counts: the comment author must be `OWNER`/`MEMBER`/`COLLABORATOR` or an Overdeck identity (`isTrustedComment`), and where the GitHub App covers the repo only the App's bot may approve by marker (`markerApproversFor`). The three MYN member repos are **public**, so without these rules anyone could approve a PR by commenting.
- **Dated marker approval (`facts.approved`).** `gitHubFacts` sets `approved: true` when the forge reports `APPROVED`, or, when the forge reports no decision, when the newest trusted marker is `APPROVED` and was posted no earlier than the PR head commit (`markerVerdictFromComments`). A push after the marker cancels it.
- **Sha-proven approval (`facts.approvedAtHead`).** A trusted `APPROVED` marker whose `sha=` names the head (`approvalMarkerAtHead`). The single-repo merge gate requires it.
- **Standing review at head.** A trusted reviewer's latest GitHub review is `APPROVED` on the exact head commit (`forgeApprovalAtHead` in `pr-facts.ts`). This covers a real review posted by the GitHub App on an unprotected branch, where GitHub leaves `reviewDecision` empty and no marker exists.
- **Ready set.** `listReadyIssuesForProject(projectPath)` in `src/lib/overdeck/ready-set.ts`: the issues whose PRs/MRs are approved, green and mergeable. The UAT train assembles batches from it (`src/dashboard/server/services/uat-train.ts`, lines 182, 286, 331).
- **`ReadySetUnavailableError`.** Thrown when a forge read the ready set depends on fails. The reconciler then skips the tick. An empty ready set would instead invalidate a live batch.

## Problem

A polyrepo issue that changes a GitHub member repo can neither record its review verdict nor enter the ready set.

1. **Verdict write refuses.** `postPolyrepoReviewVerdict` (`src/cli/commands/specialists/done.ts`, lines 123–160) returns early when any discovered artifact is not on GitLab:

   ```ts
   const github = found.find((entry) => entry.target.forge !== 'gitlab');
   if (github) {
     return {
       ok: false,
       url: github.artifact.url,
       reason: `${github.target.repoKey} is a GitHub member of a polyrepo project; record its verdict there by hand`,
     };
   }
   ```

   This was the PAN-5614 (#5620) stopgap.

2. **The ready set reads only `reviewDecision`.** `githubRows` (`src/lib/overdeck/ready-set.ts`, lines 134–147) judges a GitHub member row from the listing alone:

   ```ts
   const ready = !row.isDraft && pr.reviewState === 'approved' && pr.checks === 'green' && pr.mergeable === true;
   ```

   GitHub reports `reviewDecision` only when a branch rule requires reviews. The MYN member repos leave `main` unprotected, and their PRs are authored by the operator account, so `gh pr review --approve` is refused and the verdict lands as a marker comment. `pr-facts` reads markers; the ready set does not.

3. **A rejection on GitHub members never reaches the work agent.** After a `blocked`/`failed` verdict, `doneCommand` re-reads `getPrFacts(normalizedIssueId)` (`done.ts`, around line 499) and drives the work agent only when that read shows the rejection. For a MIN issue, `getPrFacts` cannot see GitHub member PRs: `resolveGitHubPullRequestRepo` (`src/lib/tracker-utils.ts`, line 137) returns `null` for a Linear-tracked project without `github_repo`, so `readPrFacts` falls through to the GitLab members only. An issue whose PRs are all on GitHub members reads `exists: false`, and the rejection is never delivered.

### Evidence (verified 2026-11-23)

- MIN-1142 has open PRs `mindyournow/myn-skills#4`, `mindyournow/openclaw-plugin#9` and `mindyournow/hermes-mind-your-now#6`. Each one: `state: OPEN`, `isDraft: false`, `reviewDecision: ""`, `mergeable: MERGEABLE`, checks `SUCCESS`/`SKIPPED`, author `eltmon`, zero comments. All three repos are public.
- `gh api orgs/mindyournow/installations` lists only `mintlify` and `indent`. The Overdeck GitHub App is not installed there, so `appTokenEnv` returns no token, `gh pr review` runs as the operator and is refused ("Can not approve your own pull request"), and `postReviewVerdict` falls back to the marker comment (`src/lib/cloister/pr-review-verdict.ts`, lines 195–215).
- Polyrepo review run ids hash a composite anchor, not a commit (`src/lib/cloister/review-agent.ts`, line 471: "polyrepos hash the full composite anchor so any sub-repo move changes it"). `reviewedHeadFromRunId` therefore never matches a member head, `reviewedHeadSha` returns `null`, and every polyrepo member marker is posted **without** `sha=`. A sha-proven rule can never hold for a polyrepo member.

## Decisions

- **D1 — One trusted reader on both sides.** Both the verdict write and the ready set read a GitHub member PR through one new function, `readGitHubMemberPrFacts`, which reuses `pr-facts`' trust rules by calling a newly exported `gitHubPrFacts`. The ready set must never parse markers itself: the repos are public.
- **D2 — The ready set uses the dated rule, plus a standing review.** A GitHub member PR counts as approved when (a) the listing's `reviewDecision` is `APPROVED`, or (b) `facts.approved` from `readGitHubMemberPrFacts` is true (forge decision or dated trusted marker), or (c) `forgeApprovalAtHead(facts)` returns `true`. Rule (b) is what the issue calls "the latest verdict marker is APPROVED at the PR head". We do not require `sha=` because polyrepo markers never carry one (Evidence, third bullet). This matches the GitLab member rule, which uses `facts.approved` (a named approver) and is not head-pinned either. Rule (c) covers a member repo the GitHub App does cover.
- **D3 — The per-PR read lives in the lazy `ready` thunk.** It runs only for rows that are open, not drafts, green, mergeable, and have no forge decision. It is cached per `<repoPath>|<number>|<headRefOid>` for 60 s, and a failed read is not kept (same shape as `gitlabMrFactsCache`). A failed read throws `ReadySetUnavailableError`, never "not ready".
- **D4 — The listing decides checks and mergeability; the read decides approval.** The listing already proved checks green and mergeable for this head. The read answers only `open`, `draft`, `approved`, `changesRequested`, and its `headSha`. If the read's `headSha` differs from the listing's `headRefOid` (a push landed between the two reads), the row is not ready this tick.
- **D5 — Keep the name `readMemberMrFacts`.** It gains GitHub dispatch on the artifact URL's forge (`parseArtifactRef`). Renaming would touch three test files' mocks for no behavior. Its doc comment says it reads "a member PR or MR".
- **D6 — The new reader goes in a new module.** `src/lib/cloister/pr-facts.ts` is 996 lines against the 1000-line ceiling (`scripts/lint-file-size.sh`, `CEILING=1000`). It changes only by one extracted, exported function (net +2 lines, see WI-1). The fetch and composition live in `src/lib/cloister/github-member-pr-facts.ts`.
- **D7 — Promote eligibility and the merge-train board are out of scope.** `postUatGenerationPromotePayload` (`uat-train.ts`, `memberStates` loop) and `boardProject` (`merge-train-board.ts`) read one PR per issue from the non-git polyrepo root, which breaks every polyrepo issue, not only GitHub members. No MYN batch has been created since 2026-08-14 (`~/.overdeck/overdeck.db`, `uat_generations`), so that path has never run since PAN-3917 or PAN-5320. Filed as [PAN-5641](https://github.com/eltmon/overdeck/issues/5641).
- **D8 — The GitHub monorepo path does not change.** `githubRows` is only called for polyrepo members (`readySetRepos` returns `null` for a GitHub monorepo, and `listReadyIssuesForProject` keeps its own loop). That loop and its comment (#4066 review) stay as they are.

## Requirements

### Functional

- **FR-1.** `pan admin specialists done review` on a polyrepo issue posts the verdict on every open member PR/MR, GitHub members included. It never prints "is a GitHub member of a polyrepo project".
- **FR-2.** Before posting anything, the verdict write reads every member's facts (GitLab: `readGitLabMrFacts`; GitHub: `readGitHubMemberPrFacts`). If any read has `error`, nothing is posted and the command exits 1 naming that member's URL.
- **FR-3.** On a pass, a member whose facts already show `approved` is skipped, and the skip result carries that member's forge (`github` or `gitlab`), not a hard-coded `gitlab`.
- **FR-4.** On `blocked`/`failed` for a polyrepo issue (not a strike), the "rejection visible" check re-reads each member's facts and is true when any member reports `changesRequested`, or is an open GitLab MR that is not approved.
- **FR-5.** `readGitHubMemberPrFacts(issueId, url)` reads one GitHub PR by owner/repo/number with `gh pr view <n> --repo <owner>/<repo> --json <GH_PR_VIEW_FIELDS>` and returns `PrFacts` built by `gitHubPrFacts` (the same trust rules as `getPrFacts`). An unparseable URL or failed read returns `emptyPrFacts(issueId, <reason>)` with `error` set.
- **FR-6.** In the ready set, a GitHub member row with no forge decision is approved when its read facts are open, not a draft, not `changesRequested`, at the listing's head, and either `approved` or approved by a standing review at head (`forgeApprovalAtHead` returns `true`).
- **FR-7.** A failed GitHub member read in the ready set throws `ReadySetUnavailableError` with the member repo path.
- **FR-8.** The GitHub member read runs only for rows that are not drafts, green, mergeable, and not `changes-requested`/`approved` on the listing; it is cached per repo path, PR number and head sha for 60 s; a failed read is not cached.
- **FR-9.** The GitHub monorepo ready-set path and `mergedIssueIdsForProject` make no per-PR reads.
- **FR-10.** `docs/REVIEW-AGENT-ARCHITECTURE.md`, `docs/MERGE-TRAIN.md` and `changelog.d/pan-5638.md` describe the new behavior.

### Non-functional

- **NFR-1.** `src/lib/cloister/pr-facts.ts` stays at or under 1000 lines; no file passes its file-size cap (`bash scripts/lint-file-size.sh` exits 0).
- **NFR-2.** No test runs `gh` or `glab`. Every forge read is injected or mocked.
- **NFR-3.** Delay and TTL tests use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()` (repo rule: fake timers for retry and delay tests); none waits on real time.

   ```ts
   import { fetchPullRequestByNumber } from '../overdeck/pull-requests.js';
   import { emptyPrFacts, forgeApprovalAtHead, gitHubPrFacts, type PrFacts, type PrFactsDeps } from './pr-facts.js';

   const GITHUB_PR_URL = /github\.com\/([^/]+)\/([^/]+)\/pull\/(\d+)/;

   export interface GitHubMemberPrFactsDeps extends PrFactsDeps {
     fetchPr?: typeof fetchPullRequestByNumber;
     /** A trusted standing review of the head (`forgeApprovalAtHead`); used by the ready-set read only. */
     standingApproval?: (facts: PrFacts) => Promise<boolean | undefined>;
   }

   /** One GitHub member PR's facts, read from its URL under the marker trust rules. Never throws. */
   export async function readGitHubMemberPrFacts(issueId: string, url: string, deps: GitHubMemberPrFactsDeps = {}): Promise<PrFacts> {
     const match = url.match(GITHUB_PR_URL);
     if (!match) return emptyPrFacts(issueId, `unrecognized GitHub PR URL ${url}`);
     const { fetchPr = fetchPullRequestByNumber, standingApproval: _unused, ...factsDeps } = deps;
     try {
       const read = await fetchPr(issueId, `${match[1]}/${match[2]}`, Number(match[3]));
       if (!read.pr) return emptyPrFacts(issueId, read.error ?? `GitHub PR ${url} could not be read`);
       return await gitHubPrFacts(issueId, read.pr, factsDeps);
     } catch (cause) {
       return emptyPrFacts(issueId, `GitHub PR lookup failed for ${url}: ${cause instanceof Error ? cause.message : String(cause)}`);
     }
   }

   /**
    * The ready set's read: the member PR's facts, with a trusted standing review
    * of the head folded into `approved`. A real review by the GitHub App on an
    * unprotected branch sets no `reviewDecision` and posts no marker.
    */
   export async function readGitHubMemberReadyFacts(issueId: string, url: string, deps: GitHubMemberPrFactsDeps = {}): Promise<PrFacts> {
     const facts = await readGitHubMemberPrFacts(issueId, url, deps);
     if (facts.error || facts.approved || facts.changesRequested || !facts.open || facts.draft) return facts;
     return (await (deps.standingApproval ?? forgeApprovalAtHead)(facts)) === true ? { ...facts, approved: true } : facts;
   }
   ```

   If the `_unused` destructure trips lint, destructure `standingApproval` out under any name lint accepts; the point is that `factsDeps` passed to `gitHubPrFacts` is a `PrFactsDeps`.
