# PAN-5369 — Stop the /clear-orphan scan from re-querying SQLite for every transcript on every poll tick

**Issue:** [PAN-5369](https://github.com/eltmon/overdeck/issues/5369)
**Status:** draft (planning, `pan plan --auto`)
**Planned at:** `feature/pan-5369` @ `934a4559e6b`, 2026-11-15

## Glossary

- **Lifecycle poll / tick** — `pollConversations()` in `src/dashboard/server/services/conversation-lifecycle.ts`. It runs every 10 s (`POLL_INTERVAL_MS = 10_000`) on the dashboard server's main thread.
- **/clear orphan** — a Claude Code transcript (`~/.claude/projects/<encoded-cwd>/<sessionId>.jsonl`) that Claude Code created when the user ran `/clear`. Its first 5 lines carry the sentinel `<command-name>/clear</command-name>`. It has no conversation row until the scan adopts it.
- **/clear-orphan scan** — `detectOrphanedClaudeCodeSessions(activeConvs)` in `conversation-lifecycle.ts` (starts at line 519). It runs once per tick, after `adoptForkedClaudeSessions`.
- **Locator** — `conversation_files.locator`, the harness session id a conversation owns. For Claude Code it is the transcript's file name without `.jsonl`. One conversation can own many locators (`sequencer-runner` owns 3059 on the live DB).
- **Owned transcript** — a transcript whose session id is a locator of some conversation row. The scan must never adopt it.
- **Definitive verdict** — `readFirstClearTimestamp()` (`src/lib/overdeck/conversation-fork-adoption.ts:159`) returns `{ clearTs: null, definitive: true }` only after it saw a 6th line, so the 5-line window is complete and the "not an orphan" answer can never change.
- **Provisional verdict** — `{ clearTs: null, definitive: false }`: the file has 5 lines or fewer, so the answer may change if the file grows.
- **Settled set** — the existing per-boot `notOrphanJsonlPaths` (`conversation-lifecycle.ts:80`): paths with a definitive "not an orphan" verdict.
- **Full select** — `LEGACY_CONVERSATION_SELECT` (`src/lib/overdeck/conversations.ts:358`). Every row it returns runs a correlated subquery (`claude_session_id`) that sorts all of that row's locators.

## Problem (verified 2026-11-15 against the live `~/.overdeck/overdeck.db`, read-only)

The issue's CPU profile puts 41.9 % of the dashboard main thread in `detectOrphanedClaudeCodeSessions → getConversationByClaudeSessionId`. Planning reproduced the cost directly:

| Measurement (live data, read-only, `node:sqlite`) | Value |
| --- | --- |
| `.jsonl` files in `~/.claude/projects/-home-eltmon-Projects-overdeck/` | 4089 |
| … owned by a conversation (lookup hits) | 3103 |
| … not owned (lookup misses) | 986 (721 have ≤ 5 lines, 265 have more) |
| `conversations` rows / `conversation_files` rows | 3930 / 8245 |
| Time for one `getConversationByClaudeSessionId` per file, today's SQL | **11.6 s** (synchronous) |
| Time to load every locator into a `Set` once (`SELECT cf.locator … JOIN conversations`) | **9.9 ms** |
| Existence check per file with a locator index (`SELECT 1 … LIMIT 1`), all 4090 files | 8.5 ms |

The poll runs every 10 s, so an 11.6 s synchronous burst per tick pins the main thread. Three defects combine:

1. **Owned transcripts are re-checked every tick.** In the loop at `conversation-lifecycle.ts:546-563`, an owned transcript hits `if (getConversationByClaudeSessionId(sessionId)) continue;` (line 557) and is never added to any skip set. 3103 lookups repeat every tick.
2. **The lookup scans every conversation.** `getConversationByClaudeSessionId` (`conversations.ts:617-626`) is `… WHERE EXISTS (SELECT 1 FROM conversation_files cf WHERE cf.conversation_id = c.id AND cf.locator = ?)`. `conversation_files` has only `conv_files_conv_idx (conversation_id)` (`drizzle/overdeck/0000_overdeck_init.sql:67`). `EXPLAIN QUERY PLAN` is `SCAN c` plus one index search per row, so a miss reads all 3930 rows. A hit also pays the full select's `claude_session_id` subquery, which sorts every locator of the row (about 0.7 ms for `sequencer-runner`).
3. **Short transcripts are re-read every tick.** A transcript with ≤ 5 lines gets a provisional verdict, which is never cached. The live dir has 721 such files; each tick opens and parses each one again.

The same full-select ownership check runs in fork adoption: `defaultForkAdoptionDeps.isLocatorOwned` (`conversation-fork-adoption.ts:70`) is `getConversationByClaudeSessionId(sessionId) !== null`. `adoptFromBackgroundingMarker` (line ~322) calls it for **every** `.jsonl` in the project dir before its mtime filter, so whenever its dir-mtime gate opens it repeats the same multi-second burst.

`hooks.ts` (lines 577, 627, 678, 764, 793) calls `getConversationByClaudeSessionId` on every Claude Code hook event. Its misses (agent sessions with no row) pay the same full scan. The index in WI-1 and the query rewrite in WI-2 fix that path too.

## Requirements

### Functional

- **FR-1** — On a tick, the /clear-orphan scan resolves transcript ownership from one bulk locator query, not from one query per transcript. It never calls `getConversationByClaudeSessionId`.
- **FR-2** — The scan still adopts a /clear orphan exactly as today (same sibling row, same `setClearedToConvId`, same `markConversationEnded` on the parent). Just before it creates the sibling row, it re-checks ownership with one point query, so a locator written during the tick's awaits is never adopted twice.
- **FR-3** — After the scan adopts an orphan, it adds the orphan's session id to the tick's owned set, so a second cwd group that encodes to the same project dir does not adopt it again in the same tick.
- **FR-4** — A transcript with a provisional verdict is re-read only when its size or mtime has changed since the last read.
- **FR-5** — `conversation_files(locator)` has an index named `conv_files_locator_idx` on fresh and existing databases.
- **FR-6** — `getConversationByClaudeSessionId` drives its query from the locator index and returns the same row as today when several conversations share a locator: the one with the lowest `rowid`.
- **FR-7** — Fork adoption's default ownership check uses the existence-only point query instead of the full select.
- **FR-8** — `docs/DASHBOARD-ARCHITECTURE.md`, `.overdeck/context/codebase/concerns.md` and `changelog.d/pan-5369.md` describe the new behavior.

### Non-functional

- **NFR-1** — With 4000 owned transcripts in one project dir, one tick issues exactly one bulk locator query and zero per-transcript SQLite queries.
- **NFR-2** — No new synchronous filesystem call (`*Sync`) in server-reachable code (repo rule: no `execSync`/sync I/O on the server poll path). New filesystem work in the scan uses `fs/promises`.
- **NFR-3** — No file under `src/` grows past its file-size limit (`scripts/lint-file-size.sh`: non-test files over 1000 lines may not grow past their `origin/main` count or allowlist cap). `src/lib/overdeck/infra.ts` is 982 lines; it may gain at most 18. New query helpers go in `src/lib/overdeck/conversation-batch-lookup.ts` (63 lines), not `conversations.ts`.
- **NFR-4** — No new import cycle (`npm run lint` runs the circular check). `conversation-batch-lookup.ts` imports only `./infra.js`.

## Decisions

- **D1 — A per-tick locator `Set`, not a per-boot "linked" memo.** The issue's fix direction 1 suggests remembering owned transcripts for the life of the process. Planning rejected that: loading every locator costs about 10 ms per tick, and a per-boot memo would go stale when a locator row is deleted (`vacateConversationName` in `src/lib/overdeck/conversation-replace.ts:26`, `removeVaultBrowseRow` in `src/lib/overdeck/conversation-vault-rows.ts:124`). The `Set` gives today's exact answer every tick at bulk cost.
- **D2 — The `Set` matches every harness's locators**, not only `claude-code`. Today's lookup matches any `conversation_files` row, so the `Set` keeps that behavior. The bulk query joins `conversations` so it, like today's `EXISTS`, only counts locators whose conversation row exists.
- **D3 — Load the `Set` inside `detectOrphanedClaudeCodeSessions`, after the cwd grouping, and only when at least one cwd group exists.** `adoptForkedClaudeSessions` runs before the scan and may write a locator, so loading inside the scan sees that write. A tick with nothing to scan issues no query.
- **D4 — Keep a point re-check before `createConversation`.** The scan awaits file reads and stats between loading the `Set` and creating the sibling. A hook can register the session in that window. One existence query per adoption (rare) closes it.
- **D5 — Provisional verdicts are memoized by `size:mtimeMs`.** Take the stat **before** reading the file and store that stat key. If the file grows during the read, the next tick sees a new key and reads it again. Drop the memo entry when a verdict becomes definitive or a sentinel is found.
- **D6 — Index plus query rewrite, with pinned order.** `ORDER BY c.rowid LIMIT 1` reproduces today's result. Planning checked all 8215 distinct live locators: zero differences against today's query. Without the pin, 2 of the 7 shared locators returned a different row, and `hooks.ts` routes hook events on that row.
- **D7 — Index placement mirrors PAN-5233.** Add the index to the init migration (fresh databases) and as a `runSchemaTopUp` in `ensureRuntimeIndexesSync` (existing databases). There is no schema-audit implementation to update (the "schema audit" in the `infra.ts` header comment has no code); leave that comment alone.
- **D8 — The other profile hot paths are out of scope.** `findProjectByPath → canonicalPath → realpathSync` (10.8 %) is a cross-cutting helper with about 40 callers. Caching it needs its own invalidation design. `runPullRequestSyncOnce` (7.8 %) and `loadIssueStatesForProject` (6.4 %) are separate subsystems. Planning filed [PAN-5381](https://github.com/eltmon/overdeck/issues/5381) for them, with the `findProjectByPath` cause verified in code.
- **D9 — The live `:3011` acceptance checks are post-deploy steps, not item ACs.** The work agent cannot run its branch as the production dashboard before merge. Item ACs use pre-merge proxies (call counts in unit tests, query plans). `continue.json` records the post-deploy check.

```ts
/**
 * Every locator any conversation owns, any harness (PAN-5369). One query; the
 * /clear-orphan scan checks transcript ownership against this set each tick.
 */
export function listConversationLocators(): Set<string> {
  const rows = getOverdeckDatabase()
    .prepare('SELECT cf.locator AS locator FROM conversation_files cf JOIN conversations c ON c.id = cf.conversation_id')
    .all() as Array<{ locator: string }>;
  return new Set(rows.map((row) => row.locator));
}

/** True when some conversation owns this locator. Existence only: never runs the full conversation select. */
export function isConversationLocatorOwned(locator: string): boolean {
  return getOverdeckDatabase()
    .prepare('SELECT 1 FROM conversation_files cf JOIN conversations c ON c.id = cf.conversation_id WHERE cf.locator = ? LIMIT 1')
    .get(locator) !== undefined;
}
```
