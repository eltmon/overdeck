# PAN-5486: Bot integrations: stamp the core version pins at release, and make the Grok Bot docs agree with the live result

**Issue:** [PAN-5486](https://github.com/eltmon/overdeck/issues/5486)
**Related:** [PAN-5242](https://github.com/eltmon/overdeck/issues/5242) (the failed Grok Bot connector run), [PAN-5058](https://github.com/eltmon/overdeck/issues/5058) (the live Public MCP run and the later Grok Bot docs, its work item W-5), [PAN-5072](https://github.com/eltmon/overdeck/issues/5072) (Grok Bot `mcp.json` became a stdio connector config).

The issue has two parts. Part 1 adds one script that writes every `@overdeck/core` version pin under `integrations/` from the root `package.json` version, checks it in CI and runs it during `pan release`. Part 2 makes the four Grok Bot surfaces say the same thing: the connector route fails from Grok Bot's sandbox, Public MCP is the route to use, and Public MCP with Grok Bot is not verified live yet.

## Glossary

- **Core pin**: a concrete `@overdeck/core@<digits>` string (for example `@overdeck/core@0.90.1`) or the `OVERDECK_CORE_VERSION:-<digits>}` default in `integrations/grok-build/scripts/run-mcp.sh`. A plugin passes it to `npx` to run the connector.
- **Placeholder**: `@overdeck/core@<version>` or `@overdeck/core@<pin>` in a README. It is text for a human to fill in. It is never a core pin, and the sync script never changes it.
- **Root version**: the `version` field of the repository's root `package.json` (`"version": "0.90.1"` on 2026-11-23). `pan release stable` and `pan release canary` write it.
- **Pin sync script**: the new `integrations/shared/sync-core-pins.mjs`. It follows `integrations/shared/sync-skill.mjs`.
- **Connector**: the local process (`mcp connector serve --stdio`) that a bot runs to reach one Overdeck machine over WebRTC.
- **Public MCP**: Overdeck's `/mcp` endpoint published on a public HTTPS address (today only through Tailscale Funnel), with OAuth sign-in.
- **Grok Bot**: xAI's hosted bot. It runs on xAI's servers, not on the user's computer.
- **Reach**: the route a bot uses in the Connect a bot dialog. `BOT_PLATFORMS[].reaches` in `botSnippets.ts` lists the reaches for each platform; the first entry is the default the dialog selects.
- **Live run**: a dated, recorded attempt with the real bot or API. A unit test is not a live run.

## Decisions

- **D-1 One script owns every pin.** `integrations/shared/sync-core-pins.mjs` reads the root version and rewrites every core pin it finds under `integrations/`. It finds pins by pattern, not from a file list, so a pin someone adds later is covered at once. The patterns match only digits after the `@`, so placeholders are never touched.
- **D-2 Pins stay exact.** No `@latest`, no ranges. An exact pin keeps a plugin install reproducible.
- **D-3 Both release channels stamp.** CI compares each pin with the root version, and canary also writes the root version. So `releaseCreateCommand` runs the sync for stable and canary. The script and the tests accept a prerelease suffix (`-canary.1`).
- **D-4 The tests derive pins, they do not repeat them.** The tests that assert a pin compare it with the root version from `package.json`. No test holds a concrete version literal for a pin.
- **D-5 CI runs the check twice, like the skill check.** A `ci.yml` step runs `--check` in the `integrations` job, and a repository-level unit test runs `--check` in the root shards. The unit test alone satisfies FR-2, and through `release.yml`'s full-suite gate it also blocks a stale tag.
- **D-6 The dialog defaults Grok Bot to Public MCP.** `reaches` becomes `['public', 'connector']`. The connector reach stays available for a Grok Bot environment that has WebRTC egress, but the dialog warns when it is picked. PAN-5058's `reaches` anchor stops matching; continue.json and this PRD record that.
- **D-7 `mcp.json` stays the stdio connector config.** The issue does not ask to change it, PAN-5072 chose it on purpose, and the Public MCP steps already tell the user to replace it. It keeps its pin under the sync.
- **D-8 The Grok Bot README leads with Public MCP.** The connector material moves under a heading that says it fails from Grok Bot's sandbox. The README test asserts the new order.
- **D-9 Verification records only what was run.** The 2026-11-04 rows stay unchanged. A new dated section lists what changed since, each row "Not run" unless a dated live run exists. The PAN-5242 run is a dated live run, so its row says "Failed 2026-11-14".
- **D-10 No `release.yml` edit.** Its full-suite gate already runs the repository-level pin test.

## Requirements

- **FR-1** One command, `node integrations/shared/sync-core-pins.mjs`, rewrites every core pin under `integrations/` to the root version.
- **FR-2** CI fails when any core pin differs from the root version.
- **FR-3** `pan release stable` and `pan release canary` run the pin sync and commit the updated pins in the release commit.
- **FR-4** `configuration/bots.mdx`, `configuration/mcp.mdx`, `integrations/grok-bot/README.md` and the Connect a bot dialog state the same Grok Bot route (Public MCP) and the same verification status (connector route failed live 2026-11-14 in PAN-5242; Public MCP not yet verified live).
- **FR-5** Each `integrations/*/docs/verification.md` keeps its 2026-11-04 rows and gains a dated section for what changed since.
- **FR-6** All pins under `integrations/` equal the root version on the merged branch.
- **NFR-1** No doc marks a connection as verified without a dated live run.
- **NFR-2** The sync never changes a placeholder (`@<version>`, `@<pin>`) and never changes any byte outside the version digits.
- **NFR-3** The sync and check use only Node built-ins, so they run in the `integrations` CI job without `bun install`.

     // PAN-5486: the plugins under integrations/ pin @overdeck/core; stamp them from the bumped root version.
     export function stampCorePins(repoRoot: string): void {
       const script = join(repoRoot, 'integrations', 'shared', 'sync-core-pins.mjs');
