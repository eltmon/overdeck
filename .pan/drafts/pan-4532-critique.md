## blocks-the-design: Consumption precedes dispatch

[verification-worker-supervisor.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4532/src/lib/cloister/verification-worker-supervisor.ts), lines 199–204 and 259–265, marks a result consumed as soon as the waiter reads it. [request-review-pipeline.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4532/src/lib/cloister/request-review-pipeline.ts), lines 30–46, still has to push the branch and dispatch review. If the dashboard restarts between those steps, boot adoption skips the consumed result (supervisor lines 142 and 259) and the next request runs every gate again. There is a worse second-restart case: boot adoption appends `review.requested` before resuming ([review-pipeline.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4532/src/dashboard/server/routes/workspaces/review-pipeline.ts), lines 261–280), so [recoverUndispatchedReviews](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4532/src/lib/cloister/undispatched-review-recovery.ts), lines 84–85, also ignores that journal tail. The review can remain undispatched indefinitely. Keep a durable dispatch-owed state until dispatch succeeds, or extend recovery to resume this exact result and request state; test a restart after result consumption and a second restart during boot adoption.

## blocks-the-design: Boot reattachment can be refused as dirty

[verification-boot-adoption.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4532/src/lib/cloister/verification-boot-adoption.ts), lines 21–28, re-enters the normal review starter. That starter rejects a dirty tree *before* attaching to the worker ([review-pipeline.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4532/src/dashboard/server/routes/workspaces/review-pipeline.ts), lines 163–176 and 233–245). The worker itself runs `npm install` or `bun install` and configurable build commands while alive ([verification-runner.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4532/src/lib/cloister/verification-runner.ts), lines 493–515); these can modify tracked files during the boot check. Thus FR-4's live-worker case can lose its continuation even when its result later passes. Define a resume path for an already-accepted request that survives this preflight, with a head and workspace safety check at dispatch, and test boot while the worker has temporarily modified a tracked file.

## blocks-the-design: Existing workers lack adoption metadata

I checked the prior state layout with `git show main:src/lib/cloister/verification-worker-supervisor.ts`: `WorkerState` at lines 10–23 has neither `logPrefix` nor `options`. The proposed boot scan requires `state.logPrefix === 'request-review'` ([verification-worker-supervisor.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4532/src/lib/cloister/verification-worker-supervisor.ts), lines 120–145), and finished-result adoption rejects missing options (lines 259–260). Therefore a worker already running when this change is deployed is skipped on the very restart that deploys it; a later re-request repeats the gates. Add a legacy-state recovery rule using the existing `verification.started` journal source ([verification-runner.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4532/src/lib/cloister/verification-runner.ts), lines 340–346) and the known request-review defaults, or explicitly narrow FR-4 and document the upgrade behavior. Test a state file in the prior format.

## blocks-the-design: Consumption write failures permit reuse

[verification-worker-supervisor.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4532/src/lib/cloister/verification-worker-supervisor.ts), lines 183–188, swallows a failed `resultConsumedAt` write, yet both the live waiter and adoption return that result (lines 199–204 and 259–265). A transient state-file write failure lets the first continuation dispatch review; after restart, the same result still appears unconsumed and can dispatch again. That contradicts FR-3's at-most-once rule. Make a failed consumption write observable to the caller and prevent dispatch until durable ownership is recorded; test a failed state write followed by restart.
