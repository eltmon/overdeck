# PAN-5058 — Hosted-bot access without Tailscale: a TLS passthrough relay at `<name>.mcp.overdeck.ai`

**Status:** planned (auto planning, 2026-11-17) · **Author:** planning agent, Claude Opus 5.5
**Issue:** [PAN-5058](https://github.com/eltmon/overdeck/issues/5058) · **Amends:** `.pan/drafts/pan-4927.md` (line 9, NFR-7 line 156, D-3 lines 171-172, D-16 line 206, FR-12 line 142) · **Prices:** `.pan/drafts/pan-2350.md` OD-3, lines 380-404 (relay add-on, $13/mo or $126/yr)
**Ships as:** this issue plus seven sibling issues, [#5490](https://github.com/eltmon/overdeck/issues/5490) to [#5496](https://github.com/eltmon/overdeck/issues/5496) (D-1). This PRD is the design for all eight. Each sibling's planner lowers its own "Sibling S-x" section after this issue merges and this file is on `main`.

**Why this exists.** A hosted bot (Grok Bot, the xAI API, Meta's Muse agent) runs on someone else's servers. It cannot run the Overdeck connector, so it needs a public HTTPS URL for `/mcp`. Today the only such URL is Tailscale Funnel (`configuration/mcp.mdx`, "Public MCP for hosted bots"), which needs Tailscale installed, `sudo tailscale set --operator`, HTTPS certificates and the `funnel` node attribute. Most users will not do that. In PAN-5242 (2026-11-14) Grok Bot failed the connector route three times because its sandbox has no WebRTC egress, so for Grok Bot a public HTTPS address is the only candidate route. This PRD adds a second public route that needs no Tailscale: an Overdeck-run relay that forwards TLS **without decrypting it**, so TLS still ends on the user's machine and overdeck.ai never sees MCP plaintext.

## Glossary

- **MCP:** Model Context Protocol, JSON-RPC over HTTP that an AI client uses to list and call tools. Overdeck serves it at `POST /mcp` (`src/dashboard/server/routes/mcp.ts`).
- **Public MCP:** the opt-in public `/mcp` plus the eight OAuth surfaces (`PUBLIC_MCP_SURFACES`, `src/lib/mcp/public-mcp.ts:21-31`). Switch: `mcp.public.enabled` in `~/.overdeck/config.yaml` (PAN-4947).
- **Public ingress:** the path a public request took to reach the dashboard. Today only **Funnel**; this PRD adds **relay**.
- **Tailscale Funnel:** Tailscale's public HTTPS proxy. tailscaled terminates TLS on the user's machine and forwards to `http://127.0.0.1:<port>` with the header `Tailscale-Funnel-Request` (it deletes any client-sent copy).
- **SNI:** Server Name Indication, the hostname a TLS client sends in clear text in its first message (the ClientHello).
- **TLS passthrough relay ("the relay"):** a public TCP service that reads only the SNI from the ClientHello and forwards the still-encrypted byte stream to the machine that owns that hostname. It never holds a certificate or key for a user hostname. Same model as Tailscale Funnel's relays and boringproxy.
- **Relay hostname:** `<label>.mcp.overdeck.ai`, one per machine, where `<label>` is a random 12-character server-allocated label (D-2).
- **Control host:** `mcp-relay.overdeck.ai`, the relay's own hostname for tunnel sockets. It is outside the `*.mcp.overdeck.ai` user wildcard, and it is the only TLS the relay terminates (D-6).
- **Tunnel:** the machine's outbound connection to the relay: one **control socket** (WebSocket, JSON frames) and one **data socket** (WebSocket, binary) per inbound public TCP connection (D-5).
- **Stream:** one inbound public TCP connection, carried over one data socket.
- **Relay ticket:** a short-lived, HMAC-signed statement from the account service: "device D of user U owns hostname H until time T" (D-4). The machine presents it to the relay; device tokens never reach the relay.
- **Relay socket:** a decrypted `tls.TLSSocket` on the machine that came through the relay. The dashboard tags it so the request gate treats its requests as public (D-8).
- **ACME:** the protocol a CA uses to issue certificates. **TLS-ALPN-01** is the ACME challenge answered on port 443 with a special certificate during a TLS handshake that offers ALPN protocol `acme-tls/1`. It reaches the machine through the passthrough relay.
- **CT logs:** Certificate Transparency logs, public append-only logs of every certificate a public CA issues. crt.sh is a public search over them.
- **Relay add-on:** the paid Anywhere + relay plan. In code, `Entitlement.relay === true` (`services/account/src/entitlement.ts:35`); `tester` accounts also have it (`entitlement.ts:51`).
- **Device token:** the machine's `odd_<64 hex>` account-service credential (`services/account/src/devices.ts:18`). It can call every `/v1/*` route, including device revoke and account deletion (`services/account/src/routes.ts`), so it must never be sent to the relay.
- **Grok Bot:** xAI's hosted bot. Its custom-MCP OAuth runs on Cursor's agent infrastructure (forum threads at forum.cursor.com, "Grok Bot custom MCP").
- **Muse (Meta):** Meta's consumer agent. Not to be confused with the `muse` **harness** that Overdeck launches as an agent (`RuntimeName`, `src/lib/runtimes/types.ts`). In this PRD "Muse" means the Meta consumer agent unless it says "the `muse` harness".
- **Checkpoint (CP):** a live verification step with a stated fallback. A CP row is never marked passed without a dated live run.

- `isTailscaleFunnelRequest(headers)` is defined at `src/dashboard/server/routes/dashboard-auth.ts:501-503`. Its eight callers: `remote-request-gate.ts:130`, `public-mcp-funnel.ts:52`, `ws-auth.ts:49`, `routes/mcp.ts:124` and `:128`, `routes/mcp-oauth.ts:55`, `routes/knowledge-viewer.ts:301`, `routes/account.ts:113`, `routes/dashboard-auth.ts:483` (inside `isTrustedLocalCaller`).

- Secure channels already hand a non-TCP socket to the HTTP server: `installChannelListener` captures Node's `connection` listeners and calls them with a `ChannelSocket` (`src/dashboard/server/channel-listener.ts:133-137`, `toHttp`). `channelOfRequest` finds the marker from `request.source.socket` (`src/dashboard/server/channel-peer.ts:25-29`).
- Dynamic client registration rejects the **whole** registration when any redirect URI is not `https:` or loopback `http:` (`src/lib/mcp/oauth-flow.ts:78-86`, `redirectUriProblem`; `validateRegistration` loops at lines 99-102).
- Forum reports for Grok Bot custom MCP: "redirect_uri not allowed" before sign-in when the authorization server refused a `cursor://anysphere.cursor-mcp/oauth/callback` entry in dynamic registration; the other listed callback is `https://www.cursor.com/agents/mcp/oauth/callback` (forum.cursor.com thread 171877, reply 16). What Grok Bot sends to Overdeck is unverified: that is CP-1.
- No dashboard code logs a refused registration: the register route (`routes/mcp-oauth.ts:93-108`) returns the 400 body and nothing else, and the audit layer never reads bodies (`public-mcp-funnel.ts:14-16`).
- This build host has no `tailscale` CLI and no tailscaled (`tailscale: command not found`). `~/.overdeck/config.yaml` already has `mcp.public.enabled: true`.
- `integrations/grok-bot/docs/verification.md` (dated 2026-11-04) marks CP-8a to CP-8d "Not run".
- Meta Muse custom connectors (third-party guides, 2026-09: parallel.ai "How to create custom integrations with Meta Muse", CData Connect AI KB): no form; the user describes the server in chat, Muse writes an MCP SDK client on its cloud VM, connects over streamable HTTP to a **public** URL, and takes credentials through a secure prompt. So Muse is not directory-only; it is in scope as CP-2.
- `Entitlement.relay` already exists and is `PRODUCTS[productKey].relay` for paid plans (`services/account/src/entitlement.ts:59-69`).
- Account D1 migrations end at `services/account/migrations/0004_billing.sql`; the next is `0005`.
- `acme-client` 5.4.0 (npm, 2024-07, MIT) has `crypto.createAlpnCertificate(authz, keyAuthorization, keyPem?)` and External Account Binding (`externalAccountBinding: { kid, hmacKey }`). It has no ARI (renewal information) support.
- Let's Encrypt limits (letsencrypt.org/docs/rate-limits, read 2026-11-17): 50 new certificates per registered domain per 7 days (override by form, weeks to process); 5 per exact set of identifiers per 7 days (no override); 5 authorization failures per identifier per account per hour (no override). An order with exactly the same identifiers as an earlier certificate is a renewal and is exempt from the per-domain limit.
- Fly.io (docs.fly.io/networking/services): a service with no TLS/HTTP handler forwards TCP as-is and needs a dedicated IPv4 for raw TCP; the `proxy_proto` handler prepends a PROXY protocol header (v1 default, v2 via `proxy_proto_options`).
- `PROJECTED_SURFACE_MAX_FILES = 25` and `PROJECTED_SURFACE_MAX_SUBSYSTEMS = 6` (`src/lib/xbrief/quality-lint.ts:38-39`).

## Requirements

### Functional

- **FR-1 Grok Bot live run (CP-1).** Grok Bot is run against Public MCP over Tailscale Funnel on the operator's machine before any relay code is written, and the result is recorded with the date, Grok Bot version, and these facts: whether dynamic client registration succeeded, the redirect URI schemes and hosts it registered, whether PKCE S256 was used, whether the token arrives bare or as `Bearer`, and whether "redirect_uri not allowed" appeared.
- **FR-2 Refused registrations are visible.** A refused dynamic client registration writes one activity entry naming the error code and the `scheme://host` of each redirect URI, never a path, query, token or code.
- **FR-3 Custom-scheme redirect URIs (conditional).** If CP-1 shows a registration refused because of a custom-scheme redirect URI, registration accepts private-use schemes (D-15) and the authorize page names the scheme and host. If CP-1 shows no such refusal, FR-3 is retired with that reason.
- **FR-4 Muse live run (CP-2).** Muse is run against Public MCP over Funnel and the result is recorded. If Muse accepts a custom public MCP URL, `configuration/bots.mdx` gains a Muse section; if it does not, Muse is recorded out of scope with the reason.
- **FR-5 Docs follow the live result.** The Grok Bot sections named in #5486 say what CP-1 found.
- **FR-6 PAN-4927 amendment.** `.pan/drafts/pan-4927.md` line 9, NFR-7, D-3 items 3-4, D-16 and FR-12 describe the relay as a second public route that forwards ciphertext only.
- **FR-7 Hostname registry (S-A).** A machine with the relay add-on can claim one sticky relay hostname; without the add-on the claim is refused with a plain message.
- **FR-8 Relay tickets (S-A).** The account service issues 10-minute relay tickets only for an active hostname of the calling device on an entitled account.
- **FR-9 Passthrough relay (S-B).** The relay forwards each public TLS connection for a registered hostname to that hostname's tunnel without decrypting it.
- **FR-10 Machine tunnel and TLS listener (S-C).** With the relay switch on, the dashboard keeps a tunnel open, terminates TLS locally and serves exactly the nine Public MCP surfaces on the relay hostname, with the Funnel rules (OAuth tokens only, rate limits, audit).
- **FR-11 Certificates (S-D).** The machine obtains and renews its own certificate for its relay hostname with TLS-ALPN-01; the private key never leaves the machine.
- **FR-12 Settings switch (S-E).** Settings → Anywhere has a "Public MCP through overdeck.ai" panel that turns the relay on and off per machine and shows the URL and status.
- **FR-13 Fallback CA (S-F).** When Let's Encrypt refuses for rate limits, the machine can get a certificate from Google Trust Services.
- **FR-14 CT watch (S-G).** The machine warns when a CT log shows a certificate for its hostname that it did not obtain.

### Non-functional

- **NFR-1 No plaintext through overdeck.ai.** The relay never decrypts traffic for a user hostname and holds no key for one. It terminates TLS only for the control host.
- **NFR-2 Device tokens stay on the machine.** Only relay tickets reach the relay.
- **NFR-3 Public means public.** A relay request is never a trusted local caller and reaches only `PUBLIC_MCP_SURFACES` while the relay switch is on. It never reaches `/hooks/*`, `/api/*`, `/events/*`, sockets or the SPA.
- **NFR-4 Async only.** No `execSync`, `spawnSync`, `execFileSync` or new `*Sync` function in server-reachable code (repo rules `no-execsync-server`, `prefer-async`).
- **NFR-5 Fake timers.** Tests of ticket expiry, refresh, back-off, idle timeouts and retries use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`, never real waits (repo rule `fake-timers-for-retry-tests`). Tests that run under happy-dom use an `AbortController` plus `setTimeout`, never `AbortSignal.timeout`.
- **NFR-6 File size.** New modules stay under 400 lines. No allowlist raise: `scripts/lint-file-size.sh` compares against `origin/main`, and an agent may not raise a cap. Extract a module instead.
- **NFR-7 Every new dashboard HTTP route** is in a top-level file of `src/dashboard/server/routes/`, has a row in `tests/unit/lib/overdeck/no-loss-matrix.ts`, and is `admin` in the remote gate (no `route-scopes.ts` row) with a root-only handler check, like `routes/mcp-public.ts`.
- **NFR-8 Secrets.** Keys, certificates and tickets live in 0600 files in 0700 directories under `~/.overdeck/mcp-relay/` and never in logs, argv, env exports or URLs. The relay logs hostname, stream id, byte counts, duration and outcome only.
- **NFR-9 Operator-only deploys.** No agent deploys the relay, changes DNS, runs `wrangler deploy` or files the Let's Encrypt override. Agents prepare the config, commands and checklist (same rule as `services/` Workers).
- **NFR-10 No source-grep tests.** Tests exercise behavior; tests that read source files fail lint.

  S-E and S-G ship in the same release, because the privacy wording in S-E depends on the CT watch.
- **D-2 Hostnames.** One per machine (per account device), allocated by the server: `<label>.mcp.overdeck.ai` with `<label>` matching `^[a-z][a-z2-7]{11}$` (60 bits of randomness from `crypto.getRandomValues`). Why random: every certificate is public in CT logs, so a GitHub login or machine name in the hostname would publish it; a random label reveals nothing and leaves nothing to dispute or squat. Sticky: turning the relay off and on keeps the same hostname, so the bot's saved URL and the certificate stay valid. A released label is never reassigned (its row stays with `released_at`). Reserved labels (never allocated even though the pattern makes a clash unlikely): `relay`, `mcp`, `www`, `api`, `admin`, `status`. At most **5 active hostnames per account** (bounds Let's Encrypt use). The control host is `mcp-relay.overdeck.ai`, outside the wildcard.
- **D-3 Registry home: the account service (D1), not the connect directory.** Hostnames need one global uniqueness index and the entitlement check; the account service has both. The connect directory keeps one Durable Object per account and has no global index.
- **D-4 Relay tickets.** `POST /v1/mcp-relay/ticket` (device token) returns `{ ticket, hostname, expiresAt }`. The ticket is `<base64url(payloadJson)>.<base64url(hmacSha256(key, payloadJsonBytes))>` with payload `{ "v": 1, "hostname": "<label>.mcp.overdeck.ai", "userId": "...", "deviceId": "...", "iat": <ms>, "exp": <ms> }`, `exp = iat + 600_000`. Key: Worker secret `MCP_RELAY_TICKET_KEY` (32 random bytes, base64), the same value as the relay's Fly secret. Sign and verify use Web Crypto (`crypto.subtle`), available in Workers and Node 22, in the shared `packages/contracts/src/mcp-relay.ts`. The machine refreshes every 5 minutes over the control socket (`refresh` frame). The relay closes a tunnel 30 s after its ticket's `exp` without a refresh. So a revoked device, a released hostname or a lapsed add-on loses the relay within 10.5 minutes, with no callback from the relay to the account service. Why not the device token: it can delete the account (`DELETE /v1/account`); the relay must never hold it.
- **D-5 Wire protocol: control socket plus one data socket per stream.**
  - Control: `wss://mcp-relay.overdeck.ai/v1/tunnel`. Machine → relay: `{ "type": "hello", "v": 1, "ticket": "..." }`, then `{ "type": "refresh", "ticket": "..." }`. Relay → machine: `{ "type": "ready", "hostname": "..." }`, `{ "type": "open", "streamId": "<32 hex>", "clientIp": "<ip>", "clientPort": <n> }`, `{ "type": "error", "code": "bad_ticket" | "expired" | "replaced" | "bad_frame" | "busy" }`. Frames are JSON text, at most 4 KiB, decoded with known keys only.
  - Data: for each `open`, the machine dials `wss://mcp-relay.overdeck.ai/v1/stream/<streamId>` within 10 s. The relay splices that socket's binary frames with the public TCP connection, starting with the bytes it already read (the ClientHello). A stream id is 128 random bits, single use, sent only over the authenticated control socket, and expires after 10 s.
  - One tunnel per hostname: a newer `hello` for the same hostname closes the older control socket with code 4011 (`replaced`), as the connect directory does for machines.
  - Why not a multiplexer on one socket: WebSocket already frames bytes, so per-stream sockets need no custom framing, flow control or head-of-line handling. The cost is one extra round trip per public TCP connection, which is small for MCP's few keep-alive connections.
  - The types and decoder live in `packages/contracts/src/mcp-relay.ts`, imported by the relay, the account Worker (ticket only) and the dashboard.
- **D-6 The relay.** A Node 22 TypeScript app in `services/mcp-relay/` (own Bun workspace, FSL-1.1-MIT like the other services), deployed to Fly.io with a dedicated IPv4.
  - Port 443, raw TCP, Fly `proxy_proto` handler with v2. Per connection: parse the PROXY v2 header (client IP and port), read the ClientHello (at most 16 KiB, within 10 s), take the SNI.
  - SNI = control host: terminate TLS locally with the relay's own certificate and serve the two WebSocket paths. The relay gets that certificate itself with ACME TLS-ALPN-01 (`acme-client` 5.4.0), stored on a Fly volume.
  - SNI matches `^[a-z][a-z2-7]{11}\.mcp\.overdeck\.ai$` and has a live tunnel: send `open`, wait up to 10 s for the data socket, splice. No tunnel, data socket timeout or no SNI: close the TCP connection. The relay never sends a TLS alert for a user hostname, because it cannot.
  - Bounds: 32 concurrent streams per hostname (`busy` beyond), a stream idle for 5 minutes is closed, 1,000 tunnels per process.
  - `GET /healthz` on the control host answers `{ ok, tunnels }`.
- **D-7 Machine side.** Only a primary dashboard runs the tunnel client (the same rule as `installChannelListener`). For each `open`, it dials the data socket and wraps the WebSocket stream in `new tls.TLSSocket(duplex, { isServer: true, ALPNProtocols: ['acme-tls/1', 'http/1.1'], SNICallback })`. A handshake that negotiates `acme-tls/1` gets the pending challenge certificate and is closed after the handshake. Every other socket must present the relay hostname as SNI, gets this machine's certificate, is tagged as a relay socket with its `clientIp`, and is handed to the HTTP server's connection listeners. `channel-listener.ts` exports a `deliverHttpSocket(socket)` door for this, set when the listener is installed. It is never proxied over loopback: an untagged loopback request is the trusted operator, so a proxy that forgot a header would fail open, while a tagged socket fails closed.
- **D-8 One public-request predicate.** A leaf module `src/dashboard/server/public-ingress.ts` exports `publicIngressOf(request): 'funnel' | 'relay' | null`. It checks the socket tag **first**: a tagged relay socket (via `request.source.socket`) is always `'relay'`, whatever headers it carries, because a relay visitor controls every header inside its TLS connection and could send `Tailscale-Funnel-Request` to take the Funnel branch and reach `/hooks/*`. Only an untagged request with the Funnel header is `'funnel'` and `publicIngressOfIncoming(req)` for raw Node callers. All eight `isTailscaleFunnelRequest` call sites switch to it. The relay branch of the gate admits only `PUBLIC_MCP_SURFACES`, never `POST /hooks/*`: triggers keep their own Funnel route, and the relay is for MCP only. Rate limiting reads the relay client IP from the socket tag and ignores `x-forwarded-for`. `resolveIssuer` gains `relayBase`: a relay request's issuer is `https://<configured hostname>`, never the raw `Host`.
- **D-9 Config.** `mcp.public.relay: { enabled: boolean, hostname: string | null }` in the global `config.yaml` only (a project file can never turn it on), normalized in `src/lib/config-yaml/mcp-config.ts`. The gate admits a relay request only when `mcp.public.enabled` and `mcp.public.relay.enabled` are both true. Turning the relay on in Settings sets both; turning it off sets `relay.enabled: false`, stops the tunnel and keeps `hostname`.
- **D-10 Certificates.** `acme-client` pinned exactly to `5.4.0`. Let's Encrypt production directory by default; `OVERDECK_ACME_DIRECTORY` overrides it (staging in live checks). Files in `~/.overdeck/mcp-relay/` (0700): `acme-account.pem` (ECDSA P-256 account key), `cert-key.pem` (ECDSA P-256), `cert.pem` (chain), `issued.json` (serials and expiry of every certificate this machine obtained, read by S-G), all 0600. Order only when there is no valid certificate for the hostname or fewer than 30 days remain; renew with exactly the same identifier (exempt from the per-domain limit). Never more than one order in flight. After a failed order, wait 1 hour, then double up to 24 hours, so the 5-failures-per-hour limit is never reached. No ARI in this release: same-identifier renewals are already exempt, and `acme-client` has no ARI support. The ACME logic sits behind a `CertificateAuthority` port so tests use a local test CA, never a real one.
- **D-11 Metering.** Relay MCP bytes do not count against the relay add-on's 50 GB monthly allowance in this release. MCP traffic is small JSON, and metering would need the Fly app to report into the connect Durable Objects. The relay logs bytes per stream so real use can be measured. Revisit if a hostname moves more than 1 GB in a month.
- **D-12 CT watch.** Once every 24 hours (first run 10 minutes after the certificate is obtained), the machine fetches `https://crt.sh/?q=<hostname>&output=json` and compares each entry's `serial_number` with the serials in `issued.json`. An unknown serial writes an `error` activity entry and sets `ctAlert` in the relay status shown by Settings. A crt.sh failure changes nothing and is retried at the next run.
- **D-13 Fallback CA.** Google Trust Services (`https://dv.acme-v02.api.pki.goog/directory`) needs External Account Binding. The account service mints a one-time EAB key per request through the Google Public CA API with an operator-provided service account (secret `GTS_SERVICE_ACCOUNT_JSON`), following the RS256 service-account pattern of `services/connect/src/push/` FCM. The machine uses GTS only when Let's Encrypt answers `urn:ietf:params:acme:error:rateLimited` or fails three times in a row.
- **D-14 Entitlement.** Every hostname and ticket route requires `entitlement.relay === true`, else `403 { "error": "relay_addon_required", "message": "Public MCP through overdeck.ai needs the relay add-on. Add it on your account page, or publish Public MCP with Tailscale Funnel." }`. The dashboard shows the `message` as is.
- **D-15 Custom-scheme redirect URIs (applies only if CP-1 shows the refusal).** A redirect URI is also accepted when its scheme matches `^[a-z][a-z0-9+.-]*$`, it is not `http` or `https` (those keep today's rules), and it is not one of `javascript`, `data`, `file`, `blob`, `vbscript`, `about`, `ws`, `wss`, `ftp`. This is the private-use URI scheme rule of RFC 8252 §7.1 for native and agent clients. PKCE S256 is already mandatory and the operator approves every sign-in with the approval code on their own dashboard, so a custom scheme adds no way to use a stolen code. The authorize page and approval card show `scheme://host` (for example `cursor://anysphere.cursor-mcp`) instead of the bare host.
- **D-16 Checkpoints.**
  - **CP-1 Grok Bot over Funnel** (this issue, W-2): needs Tailscale on the operator's machine, which needs `sudo` and a Tailscale sign-in. Those two are operator steps; the agent does everything else, including the admin-console settings through the browser once the operator is signed in. Fallback: if the operator has not done them, the agent blocks the item with `pan task block` and sends `pan tell flywheel-orchestrator`; it never marks a row passed.
  - **CP-2 Muse over Funnel** (this issue, W-4): needs the operator's Meta account. Same fallback.
  - **CP-3 Fly raw TCP on 443** (S-B): confirm a dedicated IPv4 with a handler-less, `proxy_proto` v2 service on 443 works. Fallback: a small VPS with a public IPv4 runs the same container under systemd; the relay code does not change.
  - **CP-4 Live relay run** (S-E, operator checklist in `docs/MCP-RELAY.md`): after the operator deploys the relay and DNS, `https://<label>.mcp.overdeck.ai/mcp` answers an OAuth-authorized MCP call from Grok Bot with no Tailscale installed. It cannot gate `pan done`, because deploys are operator-only.
- **D-17 Deploy and DNS are operator steps.** The operator creates the Fly app and IPv4, sets `MCP_RELAY_TICKET_KEY` on the relay and the account Worker, adds the DNS records (`*.mcp.overdeck.ai` and `mcp-relay.overdeck.ai` → the relay IPv4, CAA allowing `letsencrypt.org` and `pki.goog`) and files the Let's Encrypt rate-limit override for `overdeck.ai` before launch. S-B writes the runbook.
