# PAN-4641 — Let the operator queue a message that sends when rate limits reset

**Issue:** https://github.com/eltmon/overdeck/issues/4641
**Planning mode:** `pan plan --auto` (no operator questions; every default is recorded under "Decisions" and in the xBRIEF `autoDecisions[]`).

## Glossary

- **Usage limit** — a subscription window limit (Claude Code "session limit" = 5-hour window, "weekly limit" = 7-day window) or any provider 429. In a Claude Code transcript it is an assistant record with `isApiErrorMessage: true` and either `error: "rate_limit"` or `apiErrorStatus: 429`.
- **`quotaLimits`** — a structured object Claude Code writes on a usage-limit error record. Verified on this machine (Claude Code 2.1.2xx transcripts under `~/.claude/projects/`):
  ```json
  "quotaLimits": {"status":"rejected","resetsAt":1788354000,"unifiedRateLimitFallbackAvailable":false,
                  "rateLimitType":"five_hour","overageStatus":"rejected", ...},
  "error":"rate_limit","isApiErrorMessage":true,"apiErrorStatus":429
  ```
  `resetsAt` is **unix seconds**. `rateLimitType` seen: `five_hour`, `seven_day`. The message text of the same record reads `You've hit your session limit · resets 9am (America/New_York)` or `You've hit your weekly limit · resets Oct 1, 3pm (America/New_York)`.
- **Proxied 429** — a 429 from a non-Anthropic provider routed through Claude Code, e.g. `API Error: Request rejected (429) · Provider returned error` with `error: "rate_limit"` and **no** `quotaLimits` and no reset text.
- **Reset time** — the instant the limit is expected to clear. Sources in precision order: (1) `quotaLimits.resetsAt`, (2) the `resets …` text, (3) none (fallback probe).
- **Scheduled message** — an operator message held on the server until its `not_before` instant, then delivered to the conversation. The issue calls these "pending messages"; code uses **scheduled** because "pending" already names composer optimistic bubbles (`deliveryState: 'pending'`) and `pendingInput`. The CLI verb stays `pan conv pending` as the issue specifies.
- **`not_before`** — epoch ms before which a scheduled message is never delivered.
- **Tick** — one run of `tickScheduledMessages` (every 60 s, the same cadence as `DEACON_LITE_INTERVAL_MS`).
- **Head row** — for one conversation, the scheduled row with the lowest `id` whose status is not `delivered`. Only the head row is ever acted on (this gives ordering).
- **Outcome check** — after a row is pasted into the conversation (status `sent`), later ticks read the transcript tail to decide whether it landed (`delivered`) or hit the limit again (re-arm).
- **Re-arm** — move a `sent` row back to `pending` with a later `not_before`, `attempts + 1`.
- **Delivery door** — `handleConversationMessage` in `src/lib/overdeck/conversation-message.ts` (line ~407), the function behind `POST /api/conversations/:name/message`.
- **Resume door** — `handleConversationResume` in `src/lib/overdeck/conversation-runtime.ts` (line ~1074), the function behind `POST /api/conversations/:name/resume`.
- **Patrol host** — a dashboard-process module that owns a `setInterval` and process-wide skips (peer dashboard, frozen Deacon, kill switch, overlapping tick). Precedent: `src/dashboard/server/services/blocker-wake-patrol.ts` (PAN-4451).

## Problem

When a conversation hits a usage limit the operator cannot do anything useful until the window resets, sometimes hours later. Today:

- `providerErrorFromTranscriptTail` (`src/lib/overdeck/conversation-provider-error.ts`, PAN-4222) detects that the last assistant record is an API error, and records `message`, `at`, `status`, `code` — **no reset time**.
- The composer's failed-send outbox and held messages (`src/dashboard/frontend/src/lib/composerStore.ts`, `releaseHeld` ~line 524) live in the browser tab; nothing on the server holds a message for later.
- Deacon `checkApiErrorAgents` (`src/lib/cloister/deacon-api-recovery.ts`) nudges pipeline agents only, never operator conversations.

## Proposal (summary)

1. Parse the reset time out of the Claude Code transcript (structured `quotaLimits.resetsAt` first, then the `resets …` text, else none).
2. Store scheduled messages in a new overdeck.db table `conversation_scheduled_messages` behind one door module.
3. A dashboard-process patrol runs `tickScheduledMessages` every 60 s. For each conversation it acts on the head row only: when due and not limited it resumes an ended session, refuses to paste into a blocking menu, then calls the delivery door; later ticks run the outcome check and re-arm on a second limit.
4. HTTP: `GET/POST /api/conversations/:name/scheduled-messages`, `PATCH/DELETE /api/conversations/:name/scheduled-messages/:id`.
5. Composer: a "When limits reset" delivery option and, when the conversation is limited, a notice with a "Send when limits reset" button. Scheduled rows render at the end of the timeline as dimmed user bubbles with the expected send time, Edit and Cancel.
6. CLI: `pan tell <conv> --when-limit-resets "<msg>"` and `pan conv pending <conv>`.

## Requirements

### Functional

- **FR-1** The transcript parser returns, for a usage-limit error record, a `usageLimit` object `{ resetsAt: string | null; window: string | null; source: 'quota-limits' | 'message-text' | null }`. `resetsAt` comes from `quotaLimits.resetsAt` (seconds → ISO) when present, else from the `resets …` text, else null. `window` is `quotaLimits.rateLimitType` when present, else `null`. Non-limit API errors keep `usageLimit: null`.
- **FR-2** `parseLimitResetText(text, at)` turns `resets 9am (America/New_York)`, `resets 12:30pm (America/New_York)`, `resets Oct 1, 3pm (America/New_York)`, and the same without the zone, into an ISO instant; returns null for text without a `resets <time>` phrase.
- **FR-3** `readConversationUsageLimit(conv)` answers the current limit state of a conversation: `null` when the last main-chain user/assistant record is not a usage-limit error; otherwise `{ limited, resetsAt, window, source, errorAt }` where `limited` is false once `resetsAt` is in the past.
- **FR-4** Scheduled messages persist in overdeck.db table `conversation_scheduled_messages` (schema in WI-4) and survive a dashboard restart.
- **FR-5** Scheduling is supported only for conversations whose harness `transcriptKind` is `'claude-jsonl'`; others are refused with code `limit-detection-unsupported`. Vault browse copies are refused with code `vault-browse-copy`. Text starting with `/pan` is refused with code `command-not-schedulable`. Empty text → 400; text over 50 000 chars → 400; more than 20 undelivered rows per conversation → 409 `queue-full`.
- **FR-6** `not_before` at schedule time: limited with a known future reset → `resetsAt + 60 000 ms` (grace); limited with unknown reset → `now + 15 min`; not limited → `now` (sent at the next tick).
- **FR-7** The tick never delivers a row before `not_before`. Once due, it delivers within one tick (≤ 60 s) if the conversation is no longer limited.
- **FR-8** When a due head row's conversation is still limited with a future reset, the tick re-arms the row to that reset (+ grace) without delivering and without counting an attempt.
- **FR-9** After a successful paste (delivery door answers 2xx), the row is `sent`; the outcome check moves it to `delivered` on a newer non-error assistant record (or after a 10-minute window without a newer limit error), or re-arms it (`attempts + 1`, new `not_before` per FR-6 rules) on a newer usage-limit error record.
- **FR-10** Messages of one conversation are delivered strictly in queue (`id`) order: only the head row is acted on; a `failed` or `unknown` head blocks the rows behind it until the operator cancels (dismisses) it.
- **FR-11** An ended conversation (or one whose harness is not alive) is resumed through the resume door before delivery. A pane showing a blocking choice menu (`paneHasBlockingChoiceMenu`) defers delivery to the next tick.
- **FR-12** Delivery-door response taxonomy: 2xx → `sent`; 409 → stay `pending`, retry next tick; any other 4xx → `failed` with `last_error`; 5xx or a thrown error → `unknown` (never retried automatically).
- **FR-13** Cancel deletes a `pending`, `failed` or `unknown` row; a `sending` or `sent` row cannot be cancelled (409 `already-sent`). Edit replaces the text of a `pending` row only (409 `not-editable` otherwise).
- **FR-14** Each paste emits an activity entry (`level: 'info'`, link `/conv/<rowid>`); each re-arm, failure and unknown outcome emits a `warn` entry.
- **FR-15** `GET /api/conversations/:name/scheduled-messages` returns `{ supported, limit, messages }`; POST/PATCH/DELETE as in WI-5.
- **FR-16** The composer offers "When limits reset" in the delivery selector when `supported`, and shows a limit notice with a "Send when limits reset" button when `limit.limited` is true. Choosing either stores the message on the server (POST) and clears the editor.
- **FR-17** Undelivered scheduled rows render at the end of the conversation timeline as dimmed user bubbles: `Sends at about 17:00 (when your 5-hour limit resets)` (or the variants in WI-11), with Edit and Cancel.
- **FR-18** `pan tell <conv> --when-limit-resets "<msg>"` creates the same row through the same door; `pan conv pending <conv>` lists undelivered rows.

### Non-functional

- **NFR-1** No `execSync` in any code reachable from the dashboard server; all transcript reads are async (`fs/promises`).
- **NFR-2** Every delay/interval test uses `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()`; the tick is tested with injected `now`, delivery, resume, pane and transcript seams and **no real I/O behind the timers** (the db tests use a temp `OVERDECK_HOME`, as `src/lib/overdeck/__tests__/conversation-bookmarks.test.ts` does).

- **NFR-4** The patrol skips a peer dashboard, a frozen Deacon (`isDeaconGloballyPaused()`), `OVERDECK_DISABLE_SCHEDULED_MESSAGES=1`, and an overlapping tick.
- **NFR-5** At-most-once delivery: a row whose outcome is unknown is never re-pasted automatically.

## Decisions (made here; mirrored in xBRIEF `autoDecisions[]`)

- **D1 Tick lives in the dashboard process, not in the deacon child.** The deacon-lite routines run in a forked child (`src/dashboard/server/deacon-main.ts`) that does not hold the dashboard's conversation delivery dependencies. PAN-4451 set the precedent of a "deacon-lite-style" patrol hosted in the dashboard (`blocker-wake-patrol.ts`): same 60 s cadence, honors the Deacon freeze. The issue's "within one deacon tick" is met by the 60 s interval.
- **D2 Claude Code only in this issue.** Only Claude Code transcripts carry a parsed reset time today. Codex records `rate_limits.primary.resets_at` in its rollout and "try again at 2:48 PM" text, but Overdeck has no Codex rollout tail reader for limits; that belongs with #2333/#2065. The UI and CLI refuse scheduling for other harnesses (FR-5) instead of delivering blindly.
- **D3 No `deliverAs` column.** A scheduled message is always a plain submit. Steer is meaningless once the turn has ended on a limit error, and `follow_up` is Pi-only. `pan tell --steer --when-limit-resets` is refused.
- **D4 Attachments ride in the text.** The composer already prefixes uploaded attachments as `@<serverPath>` lines and the delivery door extracts them from the text (`extractConversationAttachmentPaths`). Storing the composed text stores the attachments.
- **D5 Delivery calls the doors directly, not over HTTP and not through `withConversationMessageReceipt`.** The 24 h receipt cache would replay a 409 for the same id. Idempotency comes from the row's atomic `pending → sending` claim.
- **D6 Crash recovery:** at patrol start, rows left in `sending` become `unknown` (NFR-5). A crash between claim and paste loses at most that one message, which the timeline shows as "Delivery not confirmed" with Cancel.
- **D7 Inbox resurfacing (#4639) is not built here.** #4639 is open. Delivery writes a new user record, which already advances the conversation's `lastActivityAt` (`src/lib/overdeck/conversation-list.ts`, PAN-4515), so the row moves up in the recency-sorted list.
- **D8 Cross-conversation spacing is out of scope** (issue's open question 2). Each conversation's head row is delivered independently.
- **D9 Archived conversations are skipped by the tick** (rows stay `pending`); unarchiving resumes delivery.
- **D10 Bounded retries:** `MAX_SCHEDULED_ATTEMPTS = 24`. A re-arm that would exceed it marks the row `failed` with `last_error: 'gave up after 24 attempts'`.
- **D11 Size justification over a sibling split.** The issue's ACs span composer, server store, delivery tick and CLI over one table and one API. Every item below is a vertical slice; the DAG allows the lib parsers, the store, both CLI items and the frontend items to run in parallel lanes.

## Work items

### WI-1 Reset-time text parser (FR-2)

New file `src/lib/overdeck/limit-reset-text.ts`, pure, no I/O:

```ts
/** PAN-4641: the reset instant in a Claude Code limit message ("resets 9am (America/New_York)"). */
export function parseLimitResetText(text: string, at: Date): string | null
```

Algorithm:
1. Match `/resets\s+(?:([A-Z][a-z]{2})\s+(\d{1,2}),\s+)?(\d{1,2})(?::(\d{2}))?\s*(am|pm)(?:\s*\(([^)]+)\))?/i`. No match → `null`.
2. Hour: `h % 12 + (pm ? 12 : 0)`; minute default 0. Month (if present) from `Jan…Dec` (case-insensitive); unknown month → `null`.
3. Zone: the captured IANA name if `new Intl.DateTimeFormat('en-US', { timeZone })` does not throw; otherwise the process zone (`Intl.DateTimeFormat().resolvedOptions().timeZone`).
4. The wall date: with a month/day, that date in `at`'s year in the zone; without one, `at`'s calendar date in the zone.
5. Convert wall time in zone → UTC: `guess = Date.UTC(y, m, d, h, mi)`; `offset = zoneOffsetMs(guess, zone)` where `zoneOffsetMs` formats `guess` with `Intl.DateTimeFormat(…, { timeZone, hourCycle: 'h23', year…second })`, rebuilds it with `Date.UTC`, and subtracts `guess`; `result = guess - offset`; recompute the offset at `result` once and apply again (DST edge).
6. If the result is `<= at`: without a month/day add one day (re-run step 5 for the next date); with a month/day add one year. Return `new Date(result).toISOString()`.

Tests `src/lib/overdeck/__tests__/limit-reset-text.test.ts`:
- `resets 9am (America/New_York)` at `2026-08-31T20:00:00Z` → `2026-09-01T13:00:00.000Z` (next day, EDT).
- `resets 12:30pm (America/New_York)` at `2026-08-27T15:38:26Z` → `2026-08-27T16:30:00.000Z`.
- `resets Oct 1, 3pm (America/New_York)` at `2026-09-24T12:00:00Z` → `2026-10-01T19:00:00.000Z` (matches the recorded `resetsAt: 1790881200`).
- An invalid zone `(Mars/Base)` falls back to the process zone (assert by setting `process.env.TZ = 'UTC'` in the test → `9am` = `09:00Z`).
- `API Error: Request rejected (429) · Provider returned error` → `null`.

Per tick:
1. `pruneDeliveredScheduledMessages(now)`.
2. For each name in `listConversationsWithDueWork(now)` (sequentially; one conversation's failure is caught, logged, and does not stop the others):
   1. `head = headScheduledMessage(name)`; skip if none or `head.status` is `failed`/`unknown` (FR-10).
   2. `head.status === 'sent'` → `outcome = readOutcome(conv, Date.parse(head.sentAt))`:
      - `limited-again` → `rearmScheduledMessage(head.id, now, computeNotBefore({ limited: true, ...usageLimit }, now), { countAttempt: true })`; emit `warn` "Queued message for "<title>" hit the limit again; it will retry at about <HH:MM>" (or "gave up after 24 attempts" if it became `failed`).
      - `confirmed` → `markScheduledDelivered`.
      - `waiting` and `now - sentAt >= OUTCOME_WINDOW_MS` → `markScheduledDelivered(head.id, now, 'no transcript confirmation')`; otherwise leave it.
      - Then stop for this conversation (never deliver a second row in the same tick).
   3. `head.status === 'pending'` and `notBefore > now` → skip.
   4. `limit = readUsageLimit(conv)`; `limit?.limited && limit.resetsAt` (future) → `rearmScheduledMessage(…, { countAttempt: false })` to that reset; stop. (A limited conversation with unknown reset is probed: continue to delivery.)
   5. `claimScheduledMessage(head.id, now)`; false → stop.
   6. If `conv.status === 'ended'` or `!(await harnessAlive(conv.tmuxSession))` → `resume(name)`; non-2xx → `releaseScheduledToPending(head.id, now, 'resume failed: <error>', now + SCHEDULED_MESSAGES_INTERVAL_MS)`; stop.
   7. `paneBlocked(conv.tmuxSession)` → `releaseScheduledToPending(head.id, now, 'waiting: a choice menu is open in the conversation')`; stop.
   8. `deliver(name, head.text)` (a throw → treat as status 500):
      - 2xx → `markScheduledSent`; emit `info` "Sent your queued message to "<title>"" with `link: /conv/<conv.id>`. Every activity entry this tick emits uses `source: 'dashboard'` (the value the other dashboard-process patrols use), and `<title>` is `conv.title ?? conv.name`.
      - 409 → `releaseScheduledToPending(head.id, now, body.error ?? 'conflict')`.
      - other 4xx → `failScheduledMessage(head.id, now, 'failed', body.error)`; emit `warn`.
      - ≥ 500 → `failScheduledMessage(head.id, now, 'unknown', body.error ?? 'delivery not confirmed')`; emit `warn`.
   Archived conversations never appear (D9, filtered in `listConversationsWithDueWork`).
