# PAN-3835: Attach the native Codex terminal to an app-server conversation

Status: C1 passed on codex-cli 0.153.4 (2026-09-23); implemented on `feature/pan-3835` on top of the PAN-3974 companion-terminal seam.

## C1 result and implementation notes (2026-09-23)

The C1 experiment ran in isolation (throwaway `codex app-server --listen unix://…`, temporary
`CODEX_HOME`, `tmux -L pan3835-test`, an Overdeck-style `ws` client). The full results table is in
`docs/CODEX-APP-SERVER-PROTOCOL.md`, "Native Terminal Attachment". Summary:

- Pass: idle attach, active-turn attach (no interruption), attach with a pending approval,
  shared events, approval answered from either client with `serverRequest/resolved` to both,
  a stale second answer ignored, settings converging both ways through `thread/settings/updated`,
  TUI `/quit` or kill leaving the owner running, reconnect via `thread/resume` on a loaded thread,
  malformed connections dropped without harm.
- Constraints found: the handshake fails if the client offers permessage-deflate; the TUI cannot
  attach before the thread's first turn writes its rollout; `thread/started` for other threads
  (ephemeral title threads, `/new`) is broadcast to every client, so the manager must pin its own
  thread; the remote TUI keeps retrying when the app-server dies; without
  `check_for_update_on_startup=false` the TUI blocks on an update modal.
- Not exercised: user-input requests (no `request_user_input` in Default mode). Resolution uses the
  same method-agnostic `serverRequest/resolved`.
- Decision: proceed with simultaneous attachment. No handover, proxy, or second runtime.

Deviations from the plan below, all deliberate:

- Reused PAN-3974's seam instead of new routes: kind `codex-resume-remote`, adapter
  `src/lib/overdeck/companion-terminal/codex-adapter.ts` in `defaultAdapters()`, routes
  `POST /api/conversations/:name/companion-terminal/open|close`, companion session
  `companion-<ownerSession>`, UI `ConversationTerminalView.tsx` (Native CLI / Runtime log). No new
  routes, so the no-loss route matrix is unchanged.
- The socket lives in the per-conversation dir, `~/.overdeck/agents/<id>/codex-native/app.sock`
  (dir 0700, socket 0600), recorded in `codex-native-endpoint`; stdio fallback above 100 bytes.
- FR-5 revised: a thread with no turn cannot be attached (C1), so `prepare-terminal` never creates a
  thread. It strictly resumes a saved thread the host has not loaded, and otherwise answers
  `no-thread` ("send a first message").
- Version floor for attachment is 0.153.4 (the verified version), not 0.153.3.
- FR-8 partly: the host adopts acknowledged model/effort so the next dashboard turn keeps a TUI
  choice; projecting them into the conversation record (the dashboard's displayed effort) is left
  open.
- Native navigation is detected from foreign-thread traffic (`navigationEpoch`), and it changes the
  companion fingerprint, so the next open replaces a TUI that left the pinned thread.

Left open: projection of TUI settings into the conversation record; a Playwright screenshot pass
against a booted isolated dashboard; the opt-in slow protocol suite (`*.slow.test.ts`); a menu entry
separate from the Terminal toggle.

## Glossary

- **App server:** The persistent `codex app-server` process that owns Codex threads and executes their turns.
- **Host:** Overdeck's `CodexAppServerHost`, which owns the app-server child and exposes authenticated Overdeck control operations.
- **Manager:** `CodexAppServerManager`, the protocol client inside the host.
- **Thread:** Codex's conversation identity, returned as `thread.id` and stored with its saved transcript.
- **Turn:** One unit of agent execution within a thread, which may be active, waiting for input, or completed.
- **TUI:** The native Codex terminal user interface, launched here as a remote client of the existing app server.
- **Owner session:** The existing Overdeck tmux session containing the host. It remains the conversation's liveness and delivery target.
- **Companion session:** A separate tmux session containing only the attached TUI client. Its lifetime must not control the owner session.
- **Native endpoint:** A private Unix socket accepting Codex WebSocket protocol connections. This differs from Overdeck's existing HTTP control socket.
- **Generation:** A random identifier for one host process lifetime. A restart creates a new generation, preventing reuse of stale companion sessions.
- **Rollout:** Codex's saved JSONL transcript under the conversation's isolated `CODEX_HOME`.
- **Checkpoint:** A bounded implementation experiment with explicit pass criteria and a specified response to failure.

## Problem and outcome

Overdeck's structured app-server delivery avoids terminal paste and Enter timing failures. Its current terminal view provides a basic text bridge, so operators cannot use the native Codex interface there. The operator wants to open that interface during a conversation while retaining reliable dashboard control.

For an attachment-capable running conversation, choosing Terminal opens the native CLI on the same thread. Returning to Conversation preserves the thread and active turn. Reopening Terminal reconnects to the same companion. The dashboard continues to use structured messages; the terminal does not become its delivery path.

This is an additive conversation feature. It does not change provider/model/harness routing, introduce a transport picker, or switch all work agents to a different transport. It does not start implementation agents as part of authoring this PRD.

## Requirements

### Functional requirements

- **FR-1:** Open the native Codex TUI for a running, capable Codex conversation on its exact current thread, with no owner-process restart, new thread, or synthetic user turn.
- **FR-2:** Keep dashboard delivery on the structured host connection. TUI attachment never changes the conversation's `tmuxSession`, transport preference, harness, provider, or model.
- **FR-3:** Reuse one companion per owner generation across repeated clicks and browser tabs. Returning to chat or losing a browser connection does not terminate the owner or active turn.
- **FR-4:** Attach while idle or active when C1 proves it safe. If only active-turn attachment fails, disable attachment until the turn becomes idle; explain this in the UI without interrupting work.
- **FR-5:** For a running host with no loaded thread, initialize or resume the owner's exact thread through the host, using its normal instructions/settings. Do not send a user message to create it. Missing saved resume targets return an error, never a new thread.
- **FR-6:** Preserve the saved rollout, context, permissions, working directory, and cost attribution. Terminal-originated turns must appear in the same dashboard transcript without duplicate cost ingestion.
- **FR-7:** Reconcile approvals and user-input requests answered from either interface; resolved requests disappear from the other interface. Never answer a request twice or leave a stale dashboard card blocking progress.
- **FR-8:** Track model and effort changes accepted by Codex for the owned thread. Do not overwrite terminal choices on the next dashboard prompt with stale cached launch values. Preserve existing dashboard model-change restrictions.
- **FR-9:** Expose explicit capability/unavailable reasons from the running host. Old stdio hosts continue operating and show a restart-required explanation; opening Terminal never restarts them automatically.
- **FR-10:** Preserve the current owner text bridge as a separate “Runtime log” action for Codex app-server conversations, including its existing line input and y/n shortcuts. Other harnesses and legacy Codex TUI retain their existing Terminal behavior.
- **FR-11:** Explicitly closing the Codex terminal stops only the companion, including its other open browser views. Stopping, archiving, deleting, or restarting the owner also cleans up its companion.
- **FR-12:** Authentication, authorization, and origin validation apply to terminal status/open/close operations. Clients cannot supply arbitrary endpoint, thread ID, shell command, cwd, or tmux target.
- **FR-13:** Native thread navigation must not rebind the Overdeck conversation. The manager only adopts the owner thread from its own start/resume response; unrelated thread events cannot alter its pointer, activity, requests, settings, or costs.

### Non-functional requirements

- **NFR-1:** Use one app-server process and one canonical conversation state path. A TUI client is not a managed agent and must not appear in the agent registry or trigger independent recovery.
- **NFR-2:** Use a private Unix socket in a user-owned directory with mode 0700 and socket mode 0600. No TCP listener or network exposure is needed.
- **NFR-3:** All new server and tmux operations are asynchronous, bounded, and cleaned up on failure. No `execSync`, new sync tmux calls, or one-shot agent execution.
- **NFR-4:** Read/write canonical conversation data through existing domain doors. Attachment status is derived from the live host and tmux; do not add database tables or permanent attachment records.
- **NFR-5:** Use fake timers in delay/retry tests. Keep genuine protocol/PTY timing tests in a separate `@slow` suite excluded from default tests.
- **NFR-6:** A focused no-loss audit must cover every affected existing control and route before replacing the Terminal target.
- **NFR-7:** Unsupported versions and failed attachment must leave ordinary app-server operation usable. Do not relax permissions or pick a fallback model.
- **NFR-8:** Dashboard validation runs under Node 22. Build and boot-test an isolated instance before any deployment; follow the repository DoD for implementation close-out.

## Product behavior

Keep the existing Conversation/Terminal toggle. For a capable Codex app-server host, Terminal lazily opens the native client. Add “Open Codex terminal” to the conversation menu as another entry to the same operation and “Runtime log” for the existing host pane. | --- | --- |

| Host has a saved thread not yet loaded | Host strictly resumes that thread before attachment. |

| Legacy `codex.transport: tui` session or another harness | Existing Terminal flow remains intact. Determine actual live mode, not just current global preference. |
| Stopped/archived conversation | Existing Resume/Unarchive behavior remains; attachment does not auto-resume. |
| Browser disconnect or navigating away | Owner stays alive; companion can be reattached. |
| TUI exits or crashes | Owner stays alive; show Reopen terminal, no restart loop. |
| Owner restarts or dies | Old companion is no longer valid; new generation must not reuse it. |

Native `/new`, `/resume`, and `/fork` are native navigation, not Overdeck conversation creation. If used, they must never redirect dashboard delivery or transcript attribution away from the pinned owner thread. Reopening through Overdeck must return to that pinned thread; C1 must prove how to detect/recreate a companion that navigated elsewhere. If this cannot be established, report a checkpoint blocker rather than shipping silent misattribution.

## Technical design and decisions

### Ownership and connection

```text
Dashboard controls -> existing authenticated Overdeck HTTP socket -> host/manager
                                                               |
                                                               | WebSocket over private Unix socket
                                                               v
                                                   one codex app-server
                                                               ^
                                                               | same native endpoint + thread
Browser XTerminal -> existing terminal stream -> companion tmux -> codex resume --remote ... <threadId>

Owner tmux still contains the host. Runtime log still targets owner tmux.
```

For supported conversation launches, start the child with `app-server --listen unix://<absolute-socket>`. Connect the manager using the existing `ws` dependency over that socket. The TUI connects independently to the same native endpoint. Preserve stdio mode for work agents, older CLIs, and existing host callers that do not request this capability.

Use a new optional `codexTerminalAttach` launcher field, set only for app-server conversation launches. Pass `--terminal-attach` to the host; default the option to false for all other host invocations. The manager selects Unix transport only when the option is requested and CLI capability checks pass. Version 0.153.3 is the initial supported attachment floor, not a claim about the earliest upstream release. Check the required CLI flags and prove behavior at C1. Do not silently select another binary.

Keep socket path length bounded: derive a short directory component from owner ID plus generation beneath the managed sockets directory, and reject native attachment if the resulting UTF-8 path exceeds 100 bytes. Fall back to ordinary stdio before starting a thread, with a visible unavailable reason. Do not remove another generation's socket. Never retry a failed startup by launching a second child while the first remains alive.

The host reports its generation, transport, owned thread, accepted settings, and native attachment capability over its existing authenticated `status` operation. Endpoint paths remain server-side. A new host `prepare-terminal` operation calls a shared, serialized `ensureThread({ strictResume: true })` and returns the trusted connection descriptor. Both message initiation and preparation use that one thread-initialization lock. No GET handler starts threads.

A new `src/lib/overdeck/conversation-terminal.ts` owns status/open/close orchestration. Resolve conversations using existing domain readers. Fetch live host capability through a shared internal client; use deterministic companion names `codex-ui-<hash(ownerId,generation)>`, which do not use managed-agent or conversation prefixes. Serialize concurrent opens; recheck generation before returning. Create companions with async `createSession`, an exec launcher, the owner's cwd and isolated CODEX_HOME, and properly quoted arguments. Do not inject text into the owner pane.

### API contract

Define the three routes in **new** `src/dashboard/server/routes/conversation-terminal.ts` and compose its exported layer into the existing conversations route layer. Keep handlers thin so the existing large route file does not grow another implementation. All mutations use origin and dashboard-session guards. The server resolves `:name` to the canonical conversation.

| Route | Meaning and response |
| --- | --- |
| `GET /api/conversations/:name/codex-terminal` | Read-only capability/status. `{ supported, state, reason?, sessionName?, generation? }`; state is unavailable, idle, opening, or attached. Never creates a thread or terminal. |
| `POST /api/conversations/:name/codex-terminal` | Open/reuse current-generation companion. Accept no caller-selected runtime fields. Return `{ sessionName, generation }` after readiness; repeated calls reuse it. |
| `POST /api/conversations/:name/codex-terminal/close` | Idempotently stop only the resolved companion. Body carries the generation from open/status; stale generations return 409, never close a newer client. |

Use 404 for missing conversation, 409 for stopped/busy/stale-generation states, 422 for unavailable capability, and 503 for a failed runtime connection. Error bodies have stable `code` plus a human-readable `error`. Bound host and companion readiness to 10 seconds each, allow one explicit UI retry, and do not retry messages automatically after ambiguous delivery. Long-running active turns are not failures.

### Shared state and requests

Pin owner thread identity from the manager's own start/resume response. Filter thread-scoped notifications and server requests before they affect manager state or host bookkeeping. A second client's `thread/started` must not set the conversation thread or make an active turn appear idle. Use returned live thread status on reconnect; do not assume resume means idle.

Consume `serverRequest/resolved` for the owner and remove the matching pending request whether it was answered in the dashboard, runtime bridge, or TUI. Apply the same pending-membership guard to user-input and approval responses. Validate the user-input reply payload against the pinned schema, including the required answer-object nesting; correct the serializer if the current string-array mapping does not satisfy that schema. Verify request IDs are shared/consistent across clients at C1; do not invent cross-client request-ID mapping. Clear obsolete cards after reconnect from authoritative runtime evidence; do not replay old responses.

Consume `thread/settings/updated` for the owner. Treat acknowledged runtime model/effort as the current execution settings; keep launch defaults only until the first authoritative settings snapshot. Current `handleMessageOp` reapplies host effort on every message, and manager notifications do not track settings, so simply adding a TUI would let the next dashboard turn overwrite terminal changes. W3 must fix this.

Keep existing dashboard model-change restrictions. For the existing effort picker, prove that its accepted change is reflected in TUI runtime settings: use the verified live-thread settings mechanism from C1, without starting a synthetic turn or resetting instructions/permissions. There is no verified `thread/settings/update` request in the inspected schema; do not invent one. The experiment must validate whether updating through live `thread/resume` is safe. If settings cannot be synchronized, C1 is blocked.

Project acknowledged model/effort into the existing conversation read/write doors via `conversation-reads.ts` and `setConversationModel`/`setConversationEffort` only when changed. Ignore events for other threads. Do not rewrite stored permissions from a local TUI config; keep the app server authoritative and preserve its configured approval reviewer. Keep costs sourced from the existing rollout parser; a second interface is not a second charge stream.

### Before/after implementation sketches

These show the intended seams; new helper names are part of this PRD. Complete types and error handling in their owning modules.

**Manager launch and framing (R1/R2):**

Before:
```ts
const child = spawn(binary, ['app-server'], { cwd, env, stdio: ['pipe', 'pipe', 'pipe'] });
child.stdin.write(`${JSON.stringify(message)}\n`);
```
After:
```ts
const args = nativeEndpoint ? ['app-server', '--listen', nativeEndpoint] : ['app-server'];
```

**Thread initialization (R3):**

Before: `handleMessageOp` starts/resumes the thread itself, then starts a turn.

After:
```ts
await this.ensureThread({ strictResume: true }); // serialized, shared with prepare-terminal
await this.manager.startTurn(content, this.currentTurnOptions());
```
Use strict resume for the new attachment-enabled conversation path. Preserve unrelated legacy callers' existing behavior unless independently required.

**Externally resolved requests (R4):**

Before: requests are removed only in host reply handlers.

```ts
if (message.method === 'serverRequest/resolved') {
  const params = asRecord(message.params);
  const requestId = parseRequestId(params.requestId);
  if (requestId !== undefined) this.pendingRequests.delete(String(requestId));
}
```

Before:
```tsx

```
After:
```tsx
<CodexConversationTerminal
```

## Implementation checkpoint C1

W1 is a prerequisite for all implementation work. Run experiments against an isolated CODEX_HOME and throwaway tmux sessions, never the operator's live conversation. Do not mount the operator's full Overdeck home into a test dashboard. Minimal model turns may be used only for the explicitly named protocol tests; capture version, launch arguments, sanitized protocol traces, thread IDs, and assertions. Keep credentials out of evidence.

1. Start one Unix-listening server and connect an Overdeck-style client. Start a thread, then `codex resume --remote unix://<path> <exact-id>` as a second client. Confirm both use the same thread, app-server PID, rollout, and permissions.
2. Repeat with an active turn. Establish whether resume returns/reports the active turn without interruption, configuration reset, or duplicate thread creation.
3. Trigger an approval and a structured user question. Answer each in both directions in separate trials; establish server-request routing, IDs, external-resolution notifications, and disconnect behavior while a request is pending.
4. Change effort/model in the TUI and verify settings events reach the manager. Test the existing dashboard effort action using a verified runtime update and confirm the TUI observes it. Check no stale launch setting overwrites the next turn.
5. Disconnect/reconnect the TUI and manager separately. Verify a TUI exit cannot unload/stop a thread still owned by the manager. Record whether client reconnect requires `thread/resume` and how active state and pending requests are recovered.
6. Exercise native thread navigation and reopening. Establish a supported way to know the companion's selected thread or restore the pinned thread before reusing it. Confirm foreign-thread events cannot rebind dashboard ownership.
7. Verify socket framing and permissions, same-user attachment, and behavior of malformed/unauthorized connections. Confirm no alternate app-server child is spawned by remote TUI invocation.

**Decision rule:** If all baseline idle/shared-request/settings/identity tests pass, implement the chosen Unix multi-client design. If only initial active-turn attachment fails, implement the explicit idle-only attachment restriction in FR-4. If only initial pending-request attachment fails, defer attachment until requests resolve, while still requiring requests created after attachment to synchronize correctly. Any failure of baseline ownership, settings synchronization, request resolution, or navigation isolation blocks product enablement: retain ordinary operation, record the blocker in this PRD and issue, and require a revised design. Do not quietly ship a restart/resume handover, protocol proxy, second runtime, or global TUI switch.

## Scope boundaries and delivery notes

No general remote Codex service, new provider, global transport preference UI, terminal protocol proxy, or cross-machine attachment is included. No automatic upgrade/restart of running conversations. Do not claim existing stdio-only hosts can acquire a second native endpoint in place. Their next ordinary restart/resume loads the new host capability; subsequent terminal toggles do not restart it.

The PRD is ready for a planner to lower W1–W7 into tasks. W2–W7 depend on a passing C1 baseline; W5 additionally depends on W4's API contract. The only unresolved questions are the enumerated C1 protocol facts, each with a defined fallback or block condition. A failed checkpoint is evidence to revise the design, not permission to silently substitute another product behavior.
