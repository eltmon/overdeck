## blocks-the-design: Failed replay can hold the gate indefinitely

The PRD's D-9 (lines 97–105) leaves the gate held when the post-snapshot replay returns `failed`, and the proposed `bootstrap()` change only throws for `too-far-behind`. In [EventRouter.tsx](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5604/src/dashboard/frontend/src/components/EventRouter.tsx), lines 242–258, `bootstrapComplete` becomes true, the fallback poller stops, and bootstrap returns `true` after a `failed` replay. The retry wrapper schedules a reconnect only when bootstrap returns `false` (lines 136–139). The watchdog cannot reliably rescue this: `handleEvent` resets it before checking whether an event is sequenced (lines 358–373), and the code explicitly says heartbeats arrive every 15 seconds (lines 361–366). The coordinator then defers later events because `failRecovery()` sets `bootstrapped: false` ([recoveryCoordinator.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5604/src/dashboard/frontend/src/lib/recoveryCoordinator.ts), lines 85–89 and 151–158). A transient replay request error on an otherwise healthy stream can therefore leave a previously announced question visible, and suppress new questions, until a manual Retry or transport reconnect.

Smallest change: make a `failed` post-snapshot replay fail the bootstrap attempt and use the existing reconnect backoff. Add a test where replay rejects while heartbeats continue, then assert another snapshot is requested and the gate eventually settles.

## blocks-the-design: A router remount replays stale cache through a settled gate

The proposed gate is a module-level Zustand store whose `held` value becomes `null` after a successful bootstrap (PRD item 1, lines 194–225). [EventRouter.tsx](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5604/src/dashboard/frontend/src/components/EventRouter.tsx), lines 194–199, reads and applies the localStorage cache on every effect mount; its cleanup (lines 422–430) does not re-hold the gate. The PRD inserts `holdAgentPendingInput()` only after `getSnapshot` resolves (item 1, lines 236–263). If a live event clears Q1 after the last full snapshot, then EventRouter unmounts and remounts in the same page, the cached snapshot reinstates Q1 while `held` is still `null`. The announcement hook can show the stale toast and dialog again before the new bootstrap completes. The planned EventRouter tests mock `loadSnapshotCacheEntry` to always return `null` ([EventRouter.test.tsx](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5604/src/dashboard/frontend/src/components/EventRouter.test.tsx), lines 37–40), so they miss this path.

Smallest change: hold the current settled agent lists before applying a cached snapshot on each EventRouter mount, preserving the existing empty initial hold on a fresh page. Add a remount test with a cached Q1, a prior clearing event, and a delayed new snapshot; assert Q1 never reappears in the gate output or notifications.

PRD item 5, line 477, instructs the implementer to build `agentWithQ1` with `applyEvent(INITIAL_READ_MODEL_STATE, <agent.enrichment_changed ...>).agentsById['agent-pan-5058']`. [event-reducers.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5604/packages/contracts/src/event-reducers.ts), lines 396–398, ignores enrichment when the agent is absent, so that expression is `undefined`. The cited [AppLiveStoreHost.render-count.test.tsx](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5604/src/dashboard/frontend/src/App/AppLiveStoreHost.render-count.test.tsx), lines 45–52, first seeds the agent; its enrichment event succeeds for that reason.

Smallest change: seed the reducer with an `agent.created` event before applying enrichment, or construct the snapshot agent from a valid fixture. State this explicitly in the recovery-window test instructions.
