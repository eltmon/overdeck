# PAN-4754 — Operator decision dialog: render markdown, show context separately, tighten `pan ask` guidance

**Issue:** [PAN-4754](https://github.com/eltmon/overdeck/issues/4754)

## Glossary

- **Operator decision** — a blocking question a work agent raises with `pan ask <ISSUE> "<question>" --option <a> --option <b> [--context <text>]` (PAN-4383). It is stored as an `operator.decision-requested` entry in the issue's pipeline journal. `src/lib/cloister/operator-decision.ts` derives whether it is still open.
- **Pending question** — the `AskUserQuestion`-shaped payload the dashboard shows. It comes from two sources: a real `AskUserQuestion` tool call in an agent transcript, and an open operator decision mapped by `operatorDecisionAsPendingQuestion`. On the wire it is `pendingAskUserQuestion` on agent snapshots and conversation rows.
- **Decision dialog** — `src/dashboard/frontend/src/components/AskUserQuestionDialog.tsx`, the modal that shows a pending question with option buttons and a custom-answer box.
- **Context** — the `--context` text of a `pan ask` call. It holds the facts and findings behind the question.
- **`ChatMarkdown`** — `src/dashboard/frontend/src/components/chat/ChatMarkdown.tsx`, the dashboard's shared markdown renderer (react-markdown + remark-gfm, themed, code highlighting). The sibling modal `PlanApprovalDialog.tsx` already uses it.

## Problem

The decision dialog shows every decision as one run-on paragraph. Example: the PAN-4638 live-check decision held four numbered points, a "Which do you want?" question and a separate `--context` block. The dialog showed all of it as one paragraph, and the first option label was a full sentence.

There are two causes.

1. **The dialog drops structure.** `operatorDecisionAsPendingQuestion` joins question and context into one string:

   `src/lib/cloister/operator-decision.ts` (around line 181, grep `d.context ?`):
   ```ts
   question: d.context ? `${d.question}\n\n${d.context}` : d.question,
   ```

   The dialog renders that string in a plain paragraph, which collapses newlines and does not parse markdown:

   `src/dashboard/frontend/src/components/AskUserQuestionDialog.tsx` (around line 159):
   ```tsx
   <p className="text-sm font-medium text-foreground">{q.question}</p>
   ```

2. **The work-agent prompt encourages one run-on string.** `roles/work.md`, section `## Ask the operator with \`pan ask\`` (around line 106), shows:
   ```bash
   pan ask <ISSUE-ID> "<the question, with the facts the operator needs>" --option "<choice 1>" --option "<choice 2>" --context "<what you already tried>"
   ```
   This tells the agent to put every fact into one quoted shell argument. `--option` takes a label only, so agents also put the consequence of each choice into the label.

## Requirements

- **FR-1** The decision dialog renders each question's text as GitHub-flavored markdown: paragraphs, bullet and numbered lists, bold and inline code display as such.
- **FR-2** An operator decision's context travels as its own optional `context` field on the pending question. It is no longer concatenated into `question`.
- **FR-3** The decision dialog shows `context`, when present, as a separate block in muted styling, also rendered as markdown. Its position follows FR-13 (after the options).
- **FR-4** Surfaces split in two groups. **Answer surfaces** let the operator pick an option, so they show the context under the question: the decision dialog (FR-3), the simple issue page's question card (`SimpleQuestionCard.tsx`) and the phone Needs-you list (`MobileNeedsYou.tsx`) (FR-7). **Summary surfaces** show the question text only: the Needs-you strip (`NeedsYouStrip.tsx`, `line-clamp-2`), the decisions panel row (`DecisionsPanel.tsx`), the simple home sentence (`SimpleHomePage.tsx`), the session feed (`SessionFeedSidebar.tsx`), browser notifications (`usePendingInputDialogs.ts`), push previews (`src/lib/push/classify.ts`, truncated to 140 chars), the issue view prompt (`useIssueView.ts`) and the `awaitingInput` prompt in `agent-enrichment.ts`. Summary surfaces already clamped or truncated the old concatenated text, so the context rarely showed there; question-only is the intended summary. TTS does not read question text (no reference in `tts-playback.ts`, `tts-summarizer.ts` or `activity-logger.ts`), so it is unaffected.
- **FR-5** `roles/work.md` tells agents to write a short question, put facts in `--context` as a markdown bullet list with real newlines, keep option labels short, and explain each option's consequence in the context. It includes one worked example.
- **FR-6** `docs/PIPELINE-GATES.md` section `## Operator decisions (PAN-4383)` documents the formatting contract (markdown question, separate context block).
- **FR-7** `SimpleQuestionCard.tsx` and `MobileNeedsYou.tsx` show `context`, when present, as a muted block under the question, with line breaks preserved.
- **FR-8** The dialog is an accessible modal: `role="dialog"`, `aria-modal="true"`, `aria-labelledby` (the header `h2`), `aria-describedby` (the first question text). Focus moves into the dialog on open, Tab is trapped inside it, and focus returns to the previously focused element on close.
- **FR-9** Keyboard: Esc minimizes (same as the Minimize button; disabled while submitting). Cmd+Enter (macOS) or Ctrl+Enter sends when Send is enabled, from anywhere in the dialog, including the textarea. Keys `1`–`4` pick the matching option when the dialog has exactly one question and focus is not in the textarea. Keystrokes inside the dialog never reach the dashboard's global shortcuts (`g` chord, `/` search).
- **FR-10** Option semantics: single-choice questions render options as `role="radiogroup"` / `role="radio"` with `aria-checked`. `multiSelect: true` questions render `role="group"` / `role="checkbox"` with `aria-checked` and toggle selection. The selected state shows a check icon as well as color. Every button and the textarea have a visible `focus-visible` ring.
- **FR-11** Option plus note: the textarea becomes "Add a note (optional)". Choosing an option never clears the note, and typing never clears the choice. Send is enabled when every question has a choice, or when the note is non-empty (note-only answer, as today's custom answer).
- **FR-12** Consequence next to its option: when a context line has the form `- **<label>:** <text>` (also `*` bullets and `**<label>**:`), and `<label>` matches an option label (trimmed, case-insensitive), the dialog shows `<text>` under that option's label and removes the line from the context block. It applies only to options whose `description` is empty.
- **FR-13** Layout order puts the decision first: the header (one line of identity + blocked-for age), then the question text, then the options, then the remaining context, then the note box. The separate AGENT/ISSUE metadata grid is removed.
- **FR-14** "Needs you" color: the dialog's border and header icon use the warning/needs-you tone (`border-warning/40`, icon `text-warning` on `bg-warning/15`), matching `NeedsYouStrip.tsx` (`question: { label: 'Question', tone: 'border-warning/40' }`). Only the Send button keeps `bg-primary`. Section labels use the existing `.eyebrow` utility (`src/dashboard/frontend/src/index.css` around line 140) instead of ad-hoc `text-xs font-semibold uppercase tracking-wide` classes.
- **NFR-1** No change to the `pan ask` CLI flags or the pipeline journal entry format. Existing open decisions keep rendering.
- **NFR-2** No new dependencies. Reuse `ChatMarkdown`.

## Decisions

- **Reuse `ChatMarkdown`, not a bare `ReactMarkdown`.** `PlanApprovalDialog.tsx` (around line 115) renders `<ChatMarkdown text={pending.plan} cwd={undefined} />` inside a modal of the same design. Using it keeps theming, links and code styling consistent across dashboard modals. `UpdateDialog.tsx` uses a bare `ReactMarkdown` with `prose-invert`, which ignores the light theme, so do not copy that.
- **Add `context` to the shared wire schema** rather than a decision-only side channel. The field is optional, so transcript `AskUserQuestion` payloads (which never have it) are unaffected.
- **Do not add an option-description syntax to `--option`.** That would change the CLI contract (NFR-1). Consequences go in the context instead.
- **Option buttons change only through work items 9–11.** Work item 2 leaves option buttons as they are; the design-review items later add radio/checkbox semantics, a check icon, focus rings and lifted consequences. The existing `opt.description` text still wins over a lifted consequence.
- **Answer surfaces show context; summary surfaces do not.** See FR-4. This keeps the issue's rule ("other consumers must still get the context where they show it today") on every surface where the operator decides, without pushing multi-line context into clamped one-line previews.
- **`SimpleQuestionCard` and `MobileNeedsYou` render context as plain text with `whitespace-pre-line`, not `ChatMarkdown`.** A bullet list written one item per line stays readable as plain lines, and the change needs no new providers in those components' tests. The full markdown rendering lives in the dialog, which is the main answer surface.
- **The answer echo shortens.** `POST /api/agents/:id/answer-question` (`src/dashboard/server/routes/agents/permissions.ts` around line 172, grep `Operator answered your decision request`) echoes `Q: <question>` back to the agent. After FR-2 it echoes the question without the context. The agent wrote the context itself, so nothing is lost. The existing test `agent-answer-operator-decision.test.ts` asks without context, so its expected string does not change.
- **`pan ask` already preserves newlines.** `src/cli/commands/ask.ts` (around line 76, grep `question?.trim()`; around line 91, grep `options.context?.trim()`) only trims both strings. Multi-line questions and contexts reach the journal unchanged, so no CLI change is needed (NFR-1).


Design review decisions (operator-approved scope addition, 2026-11-01; source: an Impeccable design critique of `AskUserQuestionDialog.tsx`). Line numbers are for `AskUserQuestionDialog.tsx` on this branch before any edits, verified at planning time; grep anchors are given where they may drift.

- **Stop keyboard events at the dialog, not in `App.tsx`.** `App.tsx` registers its global shortcuts with `document.addEventListener('keydown', handleKeyDown)` (around line 681) in the bubble phase. React 18 dispatches from the root container, which sits below `document`, so calling `e.stopPropagation()` in the dialog panel's `onKeyDown` keeps keys from reaching that listener. The focus trap (FR-8) guarantees focus is inside the panel.
  **Implementation checkpoint:** verify with a test that pressing `g` then `p` inside the open dialog does not navigate. **Fallback** if propagation still leaks: in `App.tsx`'s `handleKeyDown`, return early when `document.querySelector('[role="dialog"][aria-modal="true"]')` is non-null.
- **No focus-trap library.** Implement the trap in the component: on Tab/Shift+Tab at the last/first focusable element inside the panel ref, wrap focus. Focusable = `button:not([disabled]), textarea:not([disabled]), [href], [tabindex]:not([tabindex="-1"])`. NFR-2 (no new dependencies) still holds.
- **Initial focus:** the first option of the first question (the selected option if one is already selected). For a Codex approval (`toolUseId` starts with `codex-approval:`), also the first option.
- **Answer format with a note.** `handleSubmitAskUserQuestion` (`App/hooks/usePendingInputDialogs.ts` around line 406) takes `answers: string[]`, one per question, and the server (`src/dashboard/server/routes/agents/permissions.ts`, grep `lines.push(\`Q: ${q}\nA: ${answers[i]}\`)`) echoes them as `Q:/A:` pairs. The dialog keeps that contract:
  - choices only → `answers[i]` = the chosen label (multiSelect: chosen labels joined with `", "`, in option order);
  - choices + note → same, and the **last** answer gets `"\n\nNote: " + note` appended;
  - note only → `[note]` (unchanged from today's custom answer).
  Codex approvals keep the note box hidden (`isCodexApproval`, around line 70) and send only the option.
- **Blocked-for age** uses the existing `formatRelativeTime(date, now)` from `src/dashboard/frontend/src/lib/formatRelativeTime.ts` on `pendingAskUserQuestion.askedAt`. Re-render once a minute with a `setInterval` cleared on unmount; tests use `vi.useFakeTimers()` (repo rule: fake timers for delay-based tests).
- **Header line:** `h2` = `formatIssueRef(issueId, issueTitle)` (unchanged); subtitle = `<agent id> · waiting <age>`. Footer helper text left of the buttons: "Send delivers your answer to the agent, which then continues." When Send is disabled, the helper reads "Choose an option or write a note."
- **Remove the duplicate Minimize button** in the footer (grep `title="Keeps the question in the activity feed`), keeping the header icon button and Esc. The footer keeps Send. Keep the backdrop-click minimize.
- **Context block styling must differ from option buttons.** Option buttons use `border-border bg-background/40`; render the context as a left rule (`border-l-2 border-border pl-3 text-muted-foreground`) under an `.eyebrow` label "Agent's notes", not a bordered box.
- **Long option labels:** `line-clamp-2` on the label span with `title={opt.label}`.
- **Consequence lifting is a pure function** in a new file `src/dashboard/frontend/src/lib/decisionContext.ts`:
  ```ts
  export function liftOptionConsequences(
    context: string | undefined,
    optionLabels: readonly string[],
  ): { consequences: Record<string, string>; remainingContext: string | undefined }
  ```
  It matches lines with `/^\s*[-*]\s+\*\*(.+?)(?::\*\*|\*\*:)\s*(.+)$/`, compares the captured label to option labels trimmed and case-insensitively, and keys `consequences` by the option's exact label. `remainingContext` is `undefined` when only blank lines remain.

### 3. Rewrite the `pan ask` guidance in `roles/work.md` (FR-5)

File: `roles/work.md`, section `## Ask the operator with \`pan ask\`` (around lines 106–114).

Replace the code block and add a formatting paragraph before the existing "`pan ask` writes the request…" paragraph. Keep that paragraph unchanged.

New content:

````markdown
When you need an operator decision before you can continue (a blocking question), raise it with:

```bash
pan ask <ISSUE-ID> "<one or two sentences: the decision you need>" \
  --option "<short label>" --option "<short label>" \
  --context $'- <fact the operator needs>\n- <what you already tried>\n- **<label>:** <what happens if they pick it>'
```

The dashboard renders the question and the context as markdown, in separate blocks. Write them so the operator can scan them:

- The question states the decision in one or two plain sentences. Do not put facts in it.
- `--context` carries the facts as a short bullet list, one fact per bullet. Use real newlines: `$'...\n...'` in bash, or build the text in a variable first.
- Option labels are a few words each. Explain each option's consequence in the context, under a bullet that starts with the label in bold.

Example:

```bash
pan ask PAN-4638 "The live check cannot run until this branch is merged and released. How should I close out?" \
  --option "Close out now, rig + Fly" --option "Close out now, rig only" --option "Hold until after merge" \
  --context $'- Both the rig and a Fly VM install the published npm version, so neither can run this branch.\n- The rig answers over SSH but has no Overdeck installed.\n- **Close out now, rig + Fly:** I cancel the two live-check criteria and run pan done; the check runs after release.\n- **Close out now, rig only:** same, but skip Fly.\n- **Hold until after merge:** the issue stays open and you run the check yourself.'
```
````

The commit that edits `roles/work.md` must carry a `Prompt-Change:` trailer (for example `Prompt-Change: pan ask guidance asks for a short question, bulleted markdown context and short option labels`). Without it, `lint:prompt-trailer` fails.

## Planning Q&A

This plan was made in `pan plan --auto` mode, so no questions were put to the operator. The defaults chosen in place of questions:

- **Q: Which surfaces must show the context after it moves out of `question`?** Options: (a) only the dialog; (b) every surface that reads the question; (c) answer surfaces show it, summary surfaces show the question only. **Chosen: (c).** The issue requires that consumers keep the context "where they show it today". The dialog, `SimpleQuestionCard` and `MobileNeedsYou` show the full text and let the operator answer, so they must keep it. Summary surfaces clamp or truncate the text (`line-clamp-2`, 140-char push preview), so the context rarely showed there, and multi-line context does not fit a one-line preview.
- **Q: How do `SimpleQuestionCard` and `MobileNeedsYou` render the context?** Options: `ChatMarkdown`, or plain text with `whitespace-pre-line`. **Chosen: plain text.** It is the smaller change and keeps those components' tests free of new providers; one bullet per line stays readable.
- **Q: How is the screenshot produced?** **Chosen:** a committed Playwright spec on the isolated-dashboard fixture, following `pan-2355-mobile.spec.ts`, so the check is repeatable and isolated from the operator's live dashboard.
- **Q: Scope change (operator, 2026-11-01).** The operator approved adding every finding of a design review of `AskUserQuestionDialog.tsx` to this issue: FR-8..FR-14, work items 7–12, the design-review decisions and acceptance criteria 8–13.
