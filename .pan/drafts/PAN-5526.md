# PAN-5526: pan plan finalize reads a removed consent field and promises a promotion recovery that does not exist

**Issue:** [PAN-5526](https://github.com/eltmon/overdeck/issues/5526)
**Found by:** PR #5524 (PAN-5498), left out of its scope.
**Related, open:** [PAN-5527](https://github.com/eltmon/overdeck/issues/5527) — finalize timeout plus a dashboard death during server-side promotion loses the auto-start handoff. PAN-5527 owns any consumer for the pending-promotion marker. Its fix step 1 ("read the v2 consent status in `readAutoSpawnOnFinalize`") is superseded by work item 2 here; whichever lands second drops the overlap.
**Kind:** small CLI bug fix plus docs. Verified against `main` at `0bd8281e03f` (2026-11-18).

## Glossary

- **Finalize**: `pan plan finalize`, implemented by `planFinalizeCommand` in `src/cli/commands/plan-finalize.ts`. It gates the plan, stamps it `proposed`, then POSTs to the dashboard's complete-planning route to promote it.
- **Plan done**: `pan plan done <id>`, implemented by `planDoneCommand` in `src/cli/commands/plan-done.ts`. It re-sends the same complete-planning POST. It is the manual retry for a promotion that did not complete.
- **`promotePlanning`**: the exported function in `plan-finalize.ts` that sends the complete-planning POST with retries (search `export async function promotePlanning`). Both commands call it.
- **Complete-planning route**: `POST /api/issues/:id/complete-planning`, handled by `completePlanningForIssue` in `src/lib/overdeck/planning-promotion.ts`. It promotes the PRD and spec to the feature branch, transitions the issue, requests a work agent when auto-start applies, and announces the outcome in the activity feed and TTS (search `planning complete — work-agent startup accepted`).
- **Auto-start consent record**: the JSON file `~/.overdeck/agents/planning-<issue-lower>/auto-spawn-on-finalize.json`, owned by `src/lib/planning/auto-spawn-consent.ts`. The current (v2) shape is `{ version: 2, generation, status: 'granted' | 'claimed' | 'spent', workModel?, workspaceLocation?, hostOverride?, updatedAt }`. A legacy v1 shape `{ autoSpawnOnFinalize: boolean }` is still parsed: `true` maps to `granted`, `false` to `spent`.
- **Generation**: one planning cycle's consent, identified by a UUID. A work start claims the generation, then spends it. Writing the record with `writeAutoSpawnOnFinalizeFlag` always starts a new generation.
- **Consent reader**: `readAutoSpawnOnFinalizeFlagAsync(issueId): Promise<boolean>` in `auto-spawn-consent.ts`. It returns `true` only when the record's status is `granted`. It never throws and never writes: a missing or unreadable file reads as `false`.
- **Server consent resolver**: `resolveAutoSpawnOnFinalize(requestedAutoSpawn, issueId)` in `src/lib/planning/spawn-planning-session.ts`. For an explicit `true` or `false` in the request body it **writes a new generation** with that value. For an omitted value it only reads, through the consent reader.
- **Legacy CLI reader**: `readAutoSpawnOnFinalize(issueId): boolean`, exported from `plan-finalize.ts`. It reads only the v1 field `autoSpawnOnFinalize`. This PRD deletes it.
- **Pending-promotion marker**: `<workspace>/.overdeck/pending-promotion.json`, written by `writePendingPromotionMarker` in `plan-finalize.ts` when promotion does not complete. The complete-planning route deletes it on success (`removePendingPromotionMarker`, `planning-promotion.ts`). Nothing else reads it. Its old reader, `src/lib/cloister/pending-promotion-reconciler.ts`, was deleted by the Cut (PAN-3917; `docs/THE-CUT.md` line 82).

## Problem

### 1. The CLI reads auto-start consent from a field that no longer exists

`src/cli/commands/plan-finalize.ts` lines 152–162 (search `export function readAutoSpawnOnFinalize`):

```ts
export function readAutoSpawnOnFinalize(issueId: string): boolean {
  const overdeckHome = process.env.OVERDECK_HOME ?? join(homedir(), '.overdeck');
  const flagFile = join(overdeckHome, 'agents', `planning-${issueId.toLowerCase()}`, 'auto-spawn-on-finalize.json');
  try {
    if (!existsSync(flagFile)) return false;
    const flag = JSON.parse(readFileSync(flagFile, 'utf-8')) as { autoSpawnOnFinalize?: unknown };
    return flag.autoSpawnOnFinalize === true;
  } catch {
    return false;
  }
}
```

Every record written today by `writeAutoSpawnOnFinalizeFlag` is v2 and has no `autoSpawnOnFinalize` field, so this returns `false` for every issue planned with consent. It has two callers: `plan-finalize.ts` line 376 and `plan-done.ts` lines 17 and 26.

**What actually goes wrong (verified; narrower than the issue text).** `promotePlanning` puts `autoSpawn: true` in the body only when its argument is true (line 566); for `false` it omits the key. The route then calls `resolveAutoSpawnOnFinalize(undefined, id)`, which reads the v2 record. So the server still auto-starts for a granted record. The CLI-side defects are:

1. The activity entry and TTS line (lines 387–403) say "planning finalized — awaiting your approval" for an auto-start plan.
2. The printed report branches at lines 495 (`autoSpawnOnFinalize && workAgentDeferred`) and 501 (`autoSpawnOnFinalize`) are unreachable. A deferred or skipped work start prints "Run `pan start <id>` or click Start Agent" instead of the deferral or skip explanation.
3. The pending-promotion marker records `autoSpawnRequested: false` (line 447).
4. `pan plan done` keeps a second copy of the broken read (`plan-done.ts` line 26).

**Why the fix must not send `autoSpawn: true` (from the plan critique).** An explicit boolean makes the server consent resolver write a new generation. The route does that at `planning-promotion.ts` lines 555–556, before its origin check and before its in-flight lease (line 573). If a work start claims the current generation between the CLI's read and that write, the write replaces the claimed generation; completing the old claim then cannot spend the new one (`resolve-auto-spawn-on-finalize.test.ts`, "keeps old claims from consuming a newer planning cycle"). A concurrent or repeated finalize could leave usable consent after work has started. The omitted-key path only reads. So the CLI stops sending `autoSpawn` entirely, and the server alone decides from the record.

A 90 s timeout (`complete-planning timed out after 90s`) is also not proof of failure: `promotePlanning` does not retry it because the server may still be working. And nothing in the activity feed or TTS reports a failed promotion today.

## Decisions

- **D1. The CLI never sends `autoSpawn`.** Remove the `autoSpawn` parameter from `promotePlanning`. The request body carries only `noPrd` and `critic`. The server consent resolver reads the record (read-only path). This keeps auto-start working, since it already works through that path, and removes the generation-renewal race.
- **D2. One consent reader, used for reporting only.** Delete `readAutoSpawnOnFinalize`. `plan-finalize.ts` awaits `readAutoSpawnOnFinalizeFlagAsync`, imported directly from `../../lib/planning/auto-spawn-consent.js`, to choose its messages and to fill the marker's `autoSpawnRequested`. `plan-done.ts` no longer reads consent at all; it needs no value to send.
- **D3. Fix the messages; add no marker consumer.** The issue names the message change as the smaller fix. A consumer must re-run promotion (PRD gates, git commit and push, tracker transition) and coordinate the auto-start handoff, so it is not trivial. PAN-5527 owns it.
- **D4. Keep writing the marker, unchanged in shape.** PAN-5527 may build a consumer. Keep `writePendingPromotionMarker`, `PendingPromotionMarker` and `PENDING_PROMOTION_FILENAME`.
- **D5. Keep the JSON output keys.** `pan plan finalize --json` keeps `promotionDeferred` and `promotionMarkerError`. Only human-readable text, activity entries and TTS change.
- **D6. The CLI never announces a confirmed start.** The pre-POST activity and TTS for a consent plan say promotion is under way with auto-start; they never say implementation is starting. The route announces the confirmed outcome (`planning complete — work-agent startup accepted` / `ready for work`). This matters because, when auto-start applies, the route closes the planning pane right after promotion (`completePlanningAutoSpawnAndKill`, `if (options.autoSpawn) { await runKill(); }`), so a finalize run inside that pane may not live to print anything after the POST.
- **D7. Failure is "not confirmed", and it is announced.** One wording covers HTTP failure, unreachable dashboard and timeout: promotion was not confirmed, nothing retries it, check whether the issue reached Planned, and if not run `pan plan done <id>`. On that path finalize also emits an error-level activity entry and a TTS line. The pre-POST "awaiting your approval" line for a non-consent plan stays as it is.

## Requirements

- **FR-1.** `readAutoSpawnOnFinalize` no longer exists in `src/` or `tests/`. `pan plan finalize` reads consent only through `readAutoSpawnOnFinalizeFlagAsync`; `pan plan done` does not read consent.
- **FR-2.** `pan plan finalize` and `pan plan done` POST a complete-planning body that never contains the key `autoSpawn`, whatever the consent record says.
- **FR-3.** With a granted v2 record or a legacy `{ "autoSpawnOnFinalize": true }` record, finalize treats the plan as auto-start: the pre-POST activity entry contains `promoting with auto-start`, a written marker records `autoSpawnRequested: true`, and a deferred work start prints the deferral line (`Work agent start deferred`).
- **FR-4.** With a spent or claimed record, or none, finalize treats the plan as manual: the activity entry contains `awaiting your approval` and a written marker records `autoSpawnRequested: false`.
- **FR-5.** No finalize activity entry or TTS line says `starting implementation`.
- **FR-6.** When promotion is not confirmed, finalize exits 1, prints a line naming `pan plan done <id>` that does not mention the deacon or automatic completion, and emits an error-level activity entry and a TTS line saying promotion was not confirmed.
- **FR-7.** The user docs and developer docs say that an unconfirmed promotion is not retried automatically, that `pan plan done <id>` finishes it, and that the server reads auto-start consent itself.
- **NFR-1.** Neither command writes the consent record. Claims and generation rewrites stay on the server.
- **NFR-2.** Tests never wait for real retry delays (see Repo rules).

## Critique response

### Explicit auto-start renews consent during promotion

Accepted.
