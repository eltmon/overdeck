# PAN-2528 — Harness picker offers ohmypi for Anthropic+subscription combos it will reject at spawn (ToS)

**Issue:** https://github.com/eltmon/overdeck/issues/2528

## Glossary
- **ohmypi** — the alternative (non-Anthropic) coding harness (`omp` binary). Harness id `ohmypi` in `RuntimeName`. The legacy id `pi` was renamed to `ohmypi` (`RuntimeName = 'claude-code' | 'ohmypi' | 'codex'`, `src/lib/runtimes/types.ts:44`).
- **ToS gate** — the Claude Code subscription Terms of Service rule that forbids running an Anthropic model on a non-Anthropic harness (ohmypi) when authenticated via the Claude Code subscription. Enforced by `canUseHarnessSync()` in `src/lib/harness-policy.ts`.
- **harness-policy API** — `GET /api/settings/harness-policy?models=…` (`src/dashboard/server/routes/settings.ts:1014`) returns per-model per-harness allow/deny decisions the pickers consume.
- **canUsePickerHarness** — frontend helper (`src/dashboard/frontend/src/components/shared/ModelPicker/ModelPicker.tsx:37`) that reads a decision out of the API response: `policyDecisions?.[modelId]?.[harness] ?? { allowed: true }`.

## Problem
Only the server-side spawn path enforces the ohmypi + Anthropic + subscription ToS block. No picker prevents the choice up front, and the client-side awareness that *is* wired is silently broken.

### Root cause (verified at code level, 2026-07-09)
`src/dashboard/server/routes/settings.ts:1043-1047` builds the decision map as:

```ts
decisions[model] = {
  'claude-code': canUseHarnessSync('claude-code', model, authMode),
  pi: canUseHarnessSync('pi', model, authMode),
  codex: canUseHarnessSync('codex', model, authMode),
};
```

Two defects compound:
1. **Wrong key.** The map is keyed `pi`, but every picker asks for `ohmypi` (`HARNESS_OPTIONS` uses id `ohmypi`; `canUsePickerHarness('ohmypi', …)` reads `decisions[model]['ohmypi']`). That key is **undefined**, so the helper falls through to `{ allowed: true }`.
2. **Wrong value.** Even if a picker asked for `pi`, `canUseHarnessSync('pi', …)` returns ALLOWED — the ToS block lives under `if (harness === 'ohmypi')` (`harness-policy.ts:86-92`); `'pi'` hits the bottom fall-through (`harness-policy.ts:94-95`).

Net: `canUsePickerHarness('ohmypi', anthropicModel, policy)` is **always `{allowed:true}`** today. No picker can ever disable ohmypi. The auto-flip / "ToS gated" badge branches described in the issue are effectively dead code because their `!decision.allowed` guard never fires. The only working enforcement is `spawn.ts` (which, for the start-agent route at `spawn.ts:668-673`, silently falls back to `claude-code` rather than telling the user why).

### Picker landscape (verified)
- **`shared/ModelPicker/ModelPicker.tsx` `HarnessSelect`** (~:299) — on a blocked pick it either auto-flips the model (if `onModelChange` given) or no-ops; reason only in a `title` tooltip, `ToS gated` badge only in the no-`onModelChange` branch. Currently only rendered by a render test — `ModelHarnessPicker` (the live wrapper) no longer renders a harness selector (PAN-1984). Kept in scope because it is exported surface and the issue names it ("any future picker").
- **`chat/ModelPicker.tsx` harness section** (~:471) — the live user-selectable harness picker, gated behind the experimental `showHarnessModelPermutations` setting. On a blocked pick it auto-flips the model and toasts. Its inline `harnessOptionNote` (`:533-535`) already renders `decision.reason` but never shows because the decision is never blocked (root cause above).
- **`PlanDialog.tsx`** (~:195-200, 855-876) — uses `ModelHarnessPicker` (renders **no** harness selector post-PAN-1984) and already shows an inline warning (`:874-876`) with `planningHarnessDecision.reason` and falls `effectivePlanningHarness` back to `claude-code`. Already satisfies "explain why, visibly." No code change needed; its message improves automatically when the reason copy is updated.

## Proposal
1. **Fix the data contract (foundation).** Change the harness-policy route to key the decision `ohmypi` and compute it with `canUseHarnessSync('ohmypi', …)`. Extract the decision-building into a pure, exported, testable helper so it can be unit-tested with a stubbed auth-mode resolver.
2. **Disable, don't auto-flip, in `chat/ModelPicker.tsx`.** When `!decision.allowed`, render the harness option `disabled` and keep the inline `harnessOptionNote` reason. Remove the silent auto-flip + toast path for the blocked harness.
3. **Disable + explain inline in `HarnessSelect`.** Render the blocked option `disabled` and show `decision.reason` as inline text (not only a `title` tooltip / badge). Remove the silent auto-flip / no-op branch for the blocked harness.
4. **Copy.** Reword the ToS block reason to plainly name it a *Claude Code subscription Terms of Service* restriction (not a bug/missing feature). The user-visible string is the backend `OHMYPI_ANTHROPIC_SUBSCRIPTION_BLOCK.reason` (surfaced through the API); keep the frontend `PI_TOS_BLOCK_REASON` constant in sync.
5. **Docs.** Update `configuration/harnesses.mdx` "## ToS rules" to state pickers now visibly disable + explain the blocked combo up front.
6. **Keep** the `spawn.ts` server-side check as defense-in-depth (CLI `--harness` has no inline UI). Do not weaken `canUseHarnessSync`.

## Requirements
- **FR-1** — `GET /api/settings/harness-policy` returns, for an Anthropic model under subscription auth, `decisions[model].ohmypi.allowed === false` with a reason.
- **FR-2** — In `chat/ModelPicker.tsx`'s harness section, a blocked `ohmypi` option is rendered disabled (non-clickable, no auto-flip, no toast) with a visible inline reason.
- **FR-3** — In `HarnessSelect`, a blocked `ohmypi` option is rendered disabled with a visible inline reason (not only a `title` tooltip).
- **FR-4** — The ToS block reason text plainly states it is a Claude Code subscription Terms of Service restriction.
- **FR-5** — `configuration/harnesses.mdx` documents the up-front picker behavior.
- **NFR-1** — Server-side `canUseHarnessSync` gate in `spawn.ts` is preserved (defense-in-depth); policy semantics unchanged.

## Decisions (auto)
- **D1** The root cause is the harness-policy API returning key `pi` (always-allowed) instead of `ohmypi`. Fix the data first; the UI changes are inert without it. This is bug-fixing the wiring the issue points to, not a new policy.
- **D2** Blocked harness options become **disabled with an inline reason**, replacing the prior auto-flip-the-model behavior (PAN-1067). The issue explicitly asks for "visibly disabled or hidden, not just a no-op click." Disabling (vs hiding) keeps the option discoverable so the user learns *why* it is unavailable.
- **D3** `PlanDialog.tsx` needs no code change — post-PAN-1984 it renders no harness selector and already shows an inline reason + falls back to claude-code. Recorded as a NonGoal.
- **D4** The user-visible reason is the backend string surfaced via the API; the frontend `PI_TOS_BLOCK_REASON` is test-only today but kept in sync.
