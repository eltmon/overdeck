# PAN-5665: Flywheel "Start fresh" shows the previous run's transcript until the new session is up

**Issue:** [PAN-5665](https://github.com/eltmon/overdeck/issues/5665)
**Follow-up filed during planning:** [PAN-5668](https://github.com/eltmon/overdeck/issues/5668) (server side, non-Claude harnesses; out of scope here)
**Verified against:** `main` at `f618fc739b2` (2026-11-25)

## Glossary

- **Flywheel pane** — `FlywheelConversationPane` (`src/dashboard/frontend/src/components/flywheel/FlywheelConversationPane.tsx`). The conversation column of the Flywheel page and of the `/popout/flywheel-conversation` window. It embeds `ConversationPanel` for the conversation named `conv-flywheel`.
- **Run** — one lifetime of the `conv-flywheel` conversation row, from `startFlywheel` creating it to the next `Start fresh` replacing it. Every run uses the same name, `conv-flywheel`.
- **Run identity** — the string `` `${conversation.id}:${conversation.createdAt}` `` of the row the pane shows. It changes on every `createConversation` and never during a run (see D2).
- **Messages cache** — the TanStack Query entry `['conversation-messages', <name>]` (`conversationMessagesQueryKey(name)`, `src/dashboard/frontend/src/components/chat/useConversationMessagesStream.ts`, line 13). The stream, the HTTP fallback and older-page loads all write it. Subagent transcripts live under the same prefix: `['conversation-messages', <name>, 'subagent', <agentId>]` (line 14).
- **About cache** — `['conversation-about', <name>]` (`ConversationPanel.tsx`, line 325).
- **Composer echoes** — optimistic copies of messages the operator sent, held in the composer store (`src/dashboard/frontend/src/lib/composerStore.ts`, in memory, not persisted) by conversation name until the transcript shows them. `clearOptimistic(name)` (line 589) drops them.
- **Run-bound composer state** — the parts of a conversation's composer slice (`ComposerSlice`, `composerStore.ts`, line 65) that belong to one run: `optimistic` echoes, `commandResults` (results of dashboard-intercepted `/pan` commands, which `ConversationPanel.tsx` line 628 appends to the visible message list), and `failed` entries with `heldOffline: true` (prompts held while the server was unreachable, which `useComposerDeliveryState.ts` lines 121-135 send automatically to the conversation *name* when the connection returns).
- **Cache owner** — the run identity whose transcript the name-keyed caches in one `QueryClient` currently hold. New in this change.
- **Start mutation** — the `useFlywheelAction('start')` mutation (`src/dashboard/frontend/src/lib/flywheelApi.ts`, line 84). `Start` posts `{}`; `Start fresh` posts `{ fresh: true }`.

## Problem

After **Start fresh** on a paused Flywheel, the pane keeps showing the previous run's transcript. The new run's messages appear only after the new harness writes its first transcript record, which is after `startFlywheel` has spawned the session, waited for it, and delivered `/pan-flywheel`. The operator saw this on 2026-11-25: the old run (transcript `c6a51768…`) stayed on screen while the new run (conversation 4106) was already working.

## Root cause (verified; corrects parts of the issue text)

1. **Every run shares one name, and the pane's caches are keyed by name.** `ConversationPanel` keys its messages cache by `conversation.name` (`ConversationPanel.tsx`, line 169: `const messagesQueryKey = useMemo(() => conversationMessagesQueryKey(conversation.name), [conversation.name]);`). The stream (`useConversationMessagesStream.ts`, line 184), the older-history loader (`ConversationPanel.tsx`, line 578) and the about query (line 325) are keyed by name too. The Flywheel pane renders the panel with no `key` (`FlywheelConversationPane.tsx`, line 237: `<ConversationPanel`), so a new run reuses the mounted panel and the old run's cache.
2. **The cache never drops the old rows by itself.**
   - Before the new run's transcript file exists, the stream opens on the new (missing) path and emits nothing: the new row's session id resolves to a path, so `ws-rpc.ts` (around line 838) calls `streamClaudeTranscript`, and its watcher retries a missing file without emitting (`src/dashboard/server/services/conversation/watch.ts`, line 156: `// Missing or unreadable file — the next tick retries.`). With no event, the cache keeps the old rows. (When no path resolves at all, the server sends `discovering` events instead, and `applyConversationMessagesEvent` also keeps `previous.messages` on those, `useConversationMessagesStream.ts`, line 74.)
   - A full snapshot that is shorter than the cache is merged, not replaced (`snapshotShrinks`, line 107), so a new run's first small snapshot can keep old rows.
   - On (re)subscribe the client sends a `resume` built from the old cache (`resumeField`, line 189).
3. **The pane does not only refresh on settle.** The issue says the pane re-reads the row only in `onSettled`. In fact the conversation query also polls every 5 s (`FlywheelConversationPane.tsx`, line 91: `refetchInterval: 5_000`). So the new row can reach the pane while the start is still pending. The new row then streams into the old cache, which keeps the old rows (cause 2).
4. **There are never two `conv-flywheel` rows, and the pane reads the row fresh.** The issue asks to confirm that `GET /api/conversations/conv-flywheel` returns the newest of two rows. `createConversation` (`src/lib/overdeck/conversations.ts`, line 762) first calls `vacateConversationName` (`src/lib/overdeck/conversation-replace.ts`, line 15). That function deletes the old row and its `conversation_files` in the same transaction, or renames and archives it as `conv-flywheel~<8 hex>` when other rows link to it. So `getConversationByName` (`conversations.ts`, line 603) can only return the new row. `GET /api/conversations/:id` (`src/dashboard/server/routes/conversations.ts`, line 274) calls `getConversationRead` (`src/lib/overdeck/conversation-reads.ts`, line 487). That reads the row through `resolveConversationKey` → `getConversationByName` (line 798) on every request and returns `{ ...conv, … }`, so the response carries the row's `id` and `createdAt`. No server change is needed.
5. **The row id alone cannot detect a new run.** `conversation.id` is the SQLite `rowid` (`conversations.ts`, line 360: `c.rowid AS legacy_id`). The `conversations` table has a text primary key and no `AUTOINCREMENT` (`drizzle/overdeck/0000_overdeck_init.sql`, line 131). So SQLite can reuse a deleted rowid when the old row had the largest one, for example on two fresh starts in a row. `createdAt` is set once at insert (`created_at` gets `now`, `conversations.ts` around line 780) and no `UPDATE conversations SET created_at` exists in `src/lib/overdeck/`. So `id:createdAt` identifies a run.
6. **The server reads only the new run's file (Claude Code).** The new row gets its new `claudeSessionId` in the same transaction (`conversations.ts`, around line 797: `INSERT OR IGNORE INTO conversation_files`). `conv-flywheel` is not an agent-prefixed name, so `resolveConversationClaudeSessionId` returns `conv.claudeSessionId` before the launcher pin (`src/lib/overdeck/conversation-claude-session.ts`). `resolveConversationTranscriptFile` (`src/dashboard/server/services/conversation-session-follow.ts`, line 44) and `resolveSessionFile` (`src/lib/overdeck/conversation-reads.ts`, line 148) therefore resolve the new path. Non-Claude harnesses resolve by tmux session name (`HARNESS_SESSION_FILE`, `conversation-reads.ts`, line 134). They can fall back to the old run's file, which [PAN-5668](https://github.com/eltmon/overdeck/issues/5668) tracks.

## Decisions

- **D1 — Fix in the Flywheel pane, not in `ConversationPanel`.** The issue scopes the fix to the pane. Re-keying `conversationMessagesQueryKey` by id changes five consumer files (`ConversationPanel.tsx`, `useConversationMessagesStream.ts`, `SubagentComposer.tsx`, `SimpleActivityFeed.tsx`, `DirectoryDetail.tsx`) and eight test files. That is a wider change than this bug needs, so it is out of scope. `ConversationPanel.tsx` is not edited.
- **D2 — Run identity is `` `${id}:${createdAt}` ``.** `id` alone can repeat (root cause 5). `claudeSessionId` can change within a run on fork adoption or `/clear`, which would remount the panel mid-run. `createdAt` is written once per row.
- **D3 — The clear runs before the panel first renders a new identity, and it does not depend on the start mutation.** A CLI `pan flywheel start --fresh` and the popout window have no mutation in this tab. So the pane renders the panel only after it has claimed the cache for the row's identity. If the claim changed owner, it first removed the name-keyed caches. The claim runs in a `useLayoutEffect` that calls `setState`, so React re-renders before paint and the old cache never reaches the screen.
- **D4 — The cache owner is stored per `QueryClient` in a module-level `WeakMap<QueryClient, string>` in `flywheelApi.ts`.** It lives as long as the cache it describes and survives navigating away from the Flywheel page and back. A fresh `QueryClient` (a page load, a test) has no owner, so the first claim clears the query caches. That costs one transcript re-read on first open.
- **D5 — What the reset removes.** The claim always removes every query under the `['conversation-messages', 'conv-flywheel']` prefix (main and subagent transcripts) and the `['conversation-about', 'conv-flywheel']` query. When it replaces a known, different owner, it also resets the run-bound composer state through a new store action, `resetForNewRun('conv-flywheel')`:
  - `optimistic` echoes are cleared;
  - `commandResults` are cleared, so the old run's `/pan` results no longer render;
  - every `failed` entry with `heldOffline: true` becomes a `cancelled` outbox entry (the existing `cancelledEntry()` helper, `composerStore.ts` line 144). It is no longer sent automatically to the new run, but the operator can still read it and resend it by hand.
  Other `failed` entries (rejected or unconfirmed sends) and attachments stay: retrying them is an explicit operator action.
  On a first claim the owner is unknown, so composer state is kept. The composer store lives in memory only, so after a page load it is empty. A non-empty slice at a first claim means the operator used `conv-flywheel` in another view (the Command Deck) in this tab before opening the Flywheel page. That state most likely belongs to the current run, for example a live "Sending…" bubble, and the Command Deck pane is out of scope.
- **D6 — Placeholder while any start is pending.** While the start mutation is pending, the pane body shows `Starting a fresh Flywheel…` when the posted body had `fresh: true`, or `Starting the Flywheel…` otherwise. This covers all three `start.run` call sites (lines 178, 182, 194), including an idle pane that still shows an archived row. TanStack Query 5.103.2 marks the mutation successful only after the `onSettled` invalidations finish (`query-core/build/modern/mutation.js`, lines 182-185). So the placeholder lasts until the new row has been read.
- **D7 — The panel gets `key={runIdentity}`.** Its local state (resume latch, model picker, subagent selection, first-payload flag, about drawer) resets on a new run.

## Requirements

- **FR-1** After a Start fresh, the Flywheel pane never renders a message of the previous run, whether the new row arrives by the start mutation's invalidation or by the 5 s poll.
- **FR-2** While a start (fresh or plain) is pending, the pane body shows a starting placeholder instead of any transcript, terminal or empty state.
- **FR-3** A new run detected without a mutation in this tab (a CLI `pan flywheel start --fresh`, or the popout window) also clears the old run's cached messages before the panel renders the new row.
- **FR-4** A new row whose `id` equals the old row's `id` but whose `createdAt` differs counts as a new run.
- **FR-5** Re-fetching the same row (same identity) does not clear the cache or remount the panel.
- **FR-6** The Flywheel docs describe the starting placeholder and that a fresh run's pane shows only the new run's messages.
- **NFR-1** `ConversationPanel.tsx` and the shared message-cache key are unchanged (D1).
- **NFR-2** No server code changes. The server-side read for non-Claude harnesses is [PAN-5668](https://github.com/eltmon/overdeck/issues/5668).

1. In `flywheelApi.ts`, below `FLYWHEEL_CONVERSATION_QUERY_KEY` (line 16), add:

   ```ts
   import type { QueryClient } from '@tanstack/react-query';
   import { conversationMessagesQueryKey } from '../components/chat/useConversationMessagesStream';
   import { useComposerStore } from './composerStore';

   /**
    * One run of `conv-flywheel` (PAN-5665). Every run reuses the name, and the
    * rowid can be reused after `vacateConversationName` deletes the old row, so
    * the row's `createdAt` is what tells two runs apart.
    */
   export function flywheelRunIdentity(conversation: { id: number; createdAt?: string | null }): string {
     return `${conversation.id}:${conversation.createdAt ?? ''}`;
   }

   /** Which run's transcript the name-keyed caches of each QueryClient hold. */
   const transcriptCacheOwner = new WeakMap<QueryClient, string>();

   /**
    * Make `identity` the owner of the `conv-flywheel` caches. When another run
    * (or nobody known) owned them, drop the messages, subagent transcripts and
    * about summary first; reset the run-bound composer state only when a known
    * other run owned it. Returns true when it cleared.
    */
   export function claimFlywheelTranscriptCache(queryClient: QueryClient, identity: string): boolean {
     const previous = transcriptCacheOwner.get(queryClient);
     if (previous === identity) return false;
     queryClient.removeQueries({ queryKey: conversationMessagesQueryKey(FLYWHEEL_CONVERSATION_NAME) });
     queryClient.removeQueries({ queryKey: ['conversation-about', FLYWHEEL_CONVERSATION_NAME] });
     if (previous !== undefined) useComposerStore.getState().resetForNewRun(FLYWHEEL_CONVERSATION_NAME);
     transcriptCacheOwner.set(queryClient, identity);
     return true;
   }
   ```

   `removeQueries` matches by prefix by default, so it also removes `['conversation-messages', 'conv-flywheel', 'subagent', …]`. `useComposerStore` is exported at `composerStore.ts`, line 463. `flywheelApi.ts` already imports from `../components/` (line 12). Run `npm run lint:circular`. If it reports a new cycle (it counts `import type` edges too), replace the `conversationMessagesQueryKey` import with the literal `['conversation-messages', FLYWHEEL_CONVERSATION_NAME]` and a comment naming `conversationMessagesQueryKey`.

## Critique response

The plan critic (round 1, `.pan/drafts/PAN-5665-critique.md`) raised two `blocks-the-design` findings.

### Composer state survives a fresh run

Accepted and fixed in the design. D5 now resets all run-bound composer state when a known, different run owned the cache: echoes, `/pan` command results, and held-offline prompts. Held prompts become `cancelled` outbox entries, so they never auto-send to the new run, and the operator can still resend them by hand. WI-1 adds the store action `resetForNewRun` for this, and its tests seed all four kinds of entry. Rejected and unconfirmed sends stay, because retrying them is an explicit operator action, as the critique allows. D5 also defines the unknown-first-owner case: composer state is kept, with the reason stated there.

### Run identity can repeat

The critique is right that `(rowid, created_at)` can repeat when one row is deleted and a new one inserted within the same millisecond. That repeat cannot leave the old run's messages on screen, so the design keeps `id:createdAt` and needs no server change:

1. A repeat needs run A and run B created in the same millisecond, so A existed for under 1 ms.
2. In `startFlywheel` (`src/lib/flywheel/actions.ts`, lines 216-233) the session is spawned only after `createConversation` returns. `defaultSpawnSession` and `waitReady` take seconds, so A's harness had not started and A had no transcript.
3. The pane's cache can only hold rows of a transcript the server read for a row. For a Claude Code row, the server reads the file of that row's own `claudeSessionId` (Root cause 6). A row that lived under 1 ms has no file, so the cache holds no messages of A.
4. Before A, the cache held the paused run P. P was created in an earlier start, seconds or days before, so its `createdAt` differs from B's, and the claim clears P's rows.

So whenever an identity repeats, nothing of the replaced row is cached. The pane test still gives A and B the same `id` (WI-2), which covers the realistic case of a reused rowid with a new millisecond.

- Late command results repopulate the new timeline
