# PAN-4532 — Verification survives a dashboard restart

**Issue:** [PAN-4532](https://github.com/eltmon/overdeck/issues/4532)
**PR:** [#4602](https://github.com/eltmon/overdeck/pull/4602), which builds on PAN-4527 ([#4599](https://github.com/eltmon/overdeck/pull/4599))
**Status:** delivered. This PRD records the work in PR #4602.

## Glossary

- **Verification worker**: the detached process that runs the verification gate for one issue. Its state is
  in `~/.overdeck/verification-workers/<issue>/state.json` and its result is in `result-<runId>.json`.
- **Waiter**: the in-process code in the dashboard that waits for a worker's result and then continues the
  request-review pipeline (push the verified branch, dispatch review). It lives only in memory
  (`activeSupervisorRuns`), so it dies with the dashboard process.
- **Unconsumed result**: a result file that no waiter has read. After this change, the worker state records
  consumption in `resultConsumedAt`.
- **Same-head rule**: the PAN-4527 rule in `src/lib/cloister/verification-head.ts`. A later head is the
  verified head when it is unchanged or is only the worker's own target-branch sync merge.
- **Boot adoption**: on dashboard boot, the server re-attaches a waiter to each review-verification worker that
  survived the restart.

## Root cause

`src/lib/cloister/verification-worker-supervisor.ts`, line 174 on main, in `runSupervisedVerificationInternal`:
`if (existing && existing.workspacePath === workspacePath && isProcessAlive(existing.pid) && !existsSync(existing.resultPath)) {`
A worker was joined only while it was alive and had no result. A finished worker whose waiter died in a restart
fell through to a fresh, full verification. Nothing on boot re-attached a waiter to a surviving worker. This
was seen on PAN-4515 on 2026-10-04.

## Requirements

- **FR-1**: When a finished worker's result is unconsumed, ran with the same options, is not an error, and the
  same-head rule says its verified head is the current head, the supervisor returns that result and starts no
  worker.
- **FR-2**: When the agent has committed since that result, a fresh worker starts.
- **FR-3**: A result is consumed at most once. The waiter marks it consumed. Adoption uses a result only after
  its consumption is written to the state file; when that write fails, a fresh worker runs.
- **FR-4**: On boot, the dashboard re-attaches the request-review continuation to each live or unconsumed
  `request-review` worker that a PAN-4532 dashboard started (its state has `logPrefix` and `options`). A worker
  alive at boot whose workspace passes the request preflight dispatches review when it writes `passed`, with no
  re-request. Every other case falls back to the deacon-lite recovery, which re-runs the gates as before.
- **FR-5**: `docs/PIPELINE-GATES.md` states that verification survives a dashboard restart and that results are
  adopted, not re-run.

## Non-goals

- No change to deacon-lite's `recoverUndispatchedReviews`. It stays as the backstop.
- No adoption of merge-verification workers.
- No new HTTP route, CLI verb or setting.

## Acceptance criteria

1. Given a worker state with a finished `passed` result for the current HEAD and no consumer, when review is
   re-requested, then no new worker starts and the result is returned.
2. Given the same state, when the agent has pushed a new commit since, then a fresh worker starts.
3. Given a result already consumed by its waiter or by adoption, or a result whose consumption write fails, when
   review is re-requested, then that result is not adopted and a fresh worker runs.
4. Given a live request-review worker at dashboard boot, when it later writes `passed`, then review dispatches
   with no re-request and no new worker.
5. `docs/PIPELINE-GATES.md` contains the "Verification survives a dashboard restart" subsection.

## Critique response

Round 1 critique: `.pan/drafts/pan-4532-critique.md`. The test for each finding is whether it leaves a review
worse off than before PAN-4532. Before this change, every restart during verification meant a deacon-lite
re-request and a full re-run of the gates.

### Consumption precedes dispatch

Accepted as residual cost, not a loss. The runner writes `verification.passed` to the journal from the worker
process (`verification-runner.ts`, the `type: 'verification.passed'` append near line 928). So a restart after
the waiter consumes the result leaves a `verification.passed` tail, and `recoverUndispatchedReviews`
(`undispatched-review-recovery.ts`, line 85) re-requests it. The second-restart case leaves a
`review.requested` tail. The critique says recovery ignores that tail, but `recoverStalledReviews` handles it
(`deacon-lite.ts`, `stalledReviewReason` near line 263). It treats a tail older than 15 minutes as "the review
was requested but the pipeline never dispatched reviewers", and re-enters the request-review starter when no
review parent state exists (near line 470). Both paths re-run the gates, which is the pre-PAN-4532 behavior, so
the review is never stranded. A durable dispatch-owed marker would remove the re-run. It is a design change,
tracked in [PAN-4622](https://github.com/eltmon/overdeck/issues/4622).

### Boot reattachment can be refused as dirty

Accepted and narrowed in FR-4. When the preflight refuses boot adoption, the worker still finishes and writes
`verification.passed`. `recoverUndispatchedReviews` then re-requests the review after its age threshold, when
the tree is clean again. So the cost is a delay and a re-run, which is the old behavior. Resuming an accepted
request past the preflight is tracked in [PAN-4622](https://github.com/eltmon/overdeck/issues/4622).

### Existing workers lack adoption metadata

Accepted and narrowed in FR-4. Only workers started by a PAN-4532 dashboard carry `logPrefix` and `options`.
A worker already running when this change deploys is skipped on that one restart and falls back to the old
recovery. The window lasts for one deploy and is no worse than today, so no legacy-state rule is added.
`docs/PIPELINE-GATES.md` states the upgrade behavior.

### Consumption write failures permit reuse

Fixed. `markResultConsumed` now returns whether the `resultConsumedAt` write landed, and `adoptUnconsumedResult`
returns the result only when it did. Otherwise a fresh worker runs. The waiter still returns its own result
when its write fails, because it is the result's first and only owner, and adoption refuses any result whose
consumption is not on disk. New test: "a result whose consumption cannot be recorded is not adopted: a fresh
worker runs" in `verification-worker-supervisor-join.test.ts`.

### Unresolved after two critic rounds

- The second restart can strand review
- A waiter can leave its result reusable
