# PAN-4862 — Relay route cannot connect when UDP is blocked

**Issue:** [PAN-4862](https://github.com/eltmon/overdeck/issues/4862) · found by the PAN-4774 release UAT
(`.pan/uat/pan-4774/ac-03-direct-relay.md` on `feature/pan-4774`).

## Glossary

- **Relay route** — the `rtc+turn://<environment id>` link route (kind `relay`). The initiator asks the
  overdeck.ai directory for TURN credentials (`ice-servers { relay: true }`) and opens a WebRTC peer
  connection with `iceTransportPolicy: 'relay'`. The responder asks for the same credentials and opens its
  peer connection with the default policy (`'all'`).
- **Direct route** — `rtc://<environment id>`; the directory answers `ice-servers { relay: false }` with STUN
  URLs only. Not changed by this issue.
- **TURN URL** — one ICE server URL with scheme `turn:` or `turns:`. `turn:` plus `?transport=udp` (or no
  `transport`) allocates over UDP; `turn:` plus `?transport=tcp` allocates over plain TCP; `turns:` allocates
  over TLS (werift maps `turns:` + `?transport=tcp` to `tls`).
- **Cloudflare ICE list** — the `iceServers` array Cloudflare Realtime returns. It is one entry whose `urls`
  hold STUN URLs, then UDP TURN URLs, then TCP TURN URLs, then TLS TURN URLs, under one `username` /
  `credential`. The connect service passes it through unchanged
  (`services/connect/src/turn.ts`, `parseIceServers`).
- **werift** — the WebRTC library the machine side uses (`werift` 0.25.1, bundled; `import { RTCPeerConnection } from 'werift'`).
- **Gathering** — werift's candidate collection. `setLocalDescription` awaits it, so the offer (initiator)
  or answer (responder) is sent only after every candidate source settles.
- **Open budget** — `RELAY_PROBE_TIMEOUT_MS` (10 000 ms) in
  `src/dashboard/server/services/link-supervisor.ts`: signalling, gathering on both ends, ICE checks, DTLS,
  SCTP, the data channel and the Noise handshake must all finish inside it.

## Problem

### What the UAT saw

With UDP blocked inside a Fly VM (UDP 53 allowed, all other UDP dropped, TCP untouched), every route stayed
`unreachable` for 3+ minutes: `rtc+turn://…: Secure channel … did not open within 10000 ms`. The VM logged on
every relay attempt:

```
werift:packages/webrtc/src/utils.ts iceOptions { turnServer: [ 'turn.cloudflare.com', 3478 ], turnTransport: 'udp', … }
```

### Root cause (verified in `node_modules/werift/lib/index.mjs`, the ESM bundle our code loads)

1. **werift keeps only one TURN URL.** `parseIceServers` (`index.mjs` ~line 11676; CJS
   `lib/webrtc/src/utils.js` line 96) takes the first `turn`-kind URL across all entries and ignores the rest:

   ```js
   if (!options.turnServer && parsed.kind === "turn") {
     options.turnServer = parsed.address;
     options.turnTransport = parsed.transport;
   ```

   Cloudflare's first TURN URL is `turn:turn.cloudflare.com:3478?transport=udp`, so werift allocates over UDP.

2. **werift's UDP→TCP fallback arrives too late.** `getCandidatePromises` (`index.mjs` ~line 9820–9850,
   grep `if (turnTransport === "udp")`) retries a failed UDP allocation over TCP on the same host and port.
   But the UDP ALLOCATE transaction gives up only after `RETRY_RTO` 50 ms doubled across `RETRY_MAX` 6
   retransmissions: 50+100+200+400+800+1600+3200 = **6 350 ms**. Then the TCP allocation starts.

3. **Gathering blocks the SDP.** `setLocalDescription` awaits `gatherCandidates()` (CJS
   `lib/webrtc/src/peerConnection.js` line 919), and `RtcTransport.create` / `accept`
   (`src/lib/anywhere/channel/rtc-transport.ts`) send the offer / answer only after it resolves. So the
   side whose UDP is blocked sends its SDP no earlier than ~6.4 s plus the TCP allocation.

4. **The responder also waits on STUN.** The responder is not `forceTurn`, so werift also gathers a
   server-reflexive candidate from the first `stun:` URL. With UDP blocked that waits the full
   `stunGatherTimeout` default of 5 s (`getCandidatePromises(addresses, timeout = 5)`). `stun.cloudflare.com`
   resolves to `162.159.207.0` / `2606:4700:49::`, a different address from `turn.cloudflare.com`
   (`141.101.90.1` / `2a06:98c1:3200::1`), so the issue's control run (UDP allowed only to the TURN address
   and `104.30.0.0/16`) also hit this 5 s wait.

Steps 2–4 together consume most or all of the 10 s open budget before ICE checks begin. When the
initiator's budget expires it closes its peer connection (`awaitOpen` → `closeEntry`), and the next probe
starts gathering from scratch, so the relay never connects.

**Why werift configuration cannot fix it.** `resolveTurnTransport` gives the URL's own transport
(`parsedTurnTransport`) precedence over `config.turnTransport` and `config.forceTurnTCP`, and every
Cloudflare TURN URL carries an explicit `?transport=`. Only the order and choice of URLs we pass changes
the transport werift uses.

### Observation not root-caused (issue section 2)

In the control run the VM's UDP TURN allocation succeeded and home's relay candidate arrived, but every
candidate pair failed and the link stayed offline for 90 s. Root cause 4 (the responder's 5 s STUN wait,
then the initiator closing at 10 s) is a plausible explanation, but it is not proven. This issue does not
root-cause it; the live check (WI-4) records whether it persists after the fix.

## Decisions

- **D1 — Fix on the machine side, not in the connect Worker.** Both `RtcTransport.create` (initiator) and
  `RtcTransport.accept` (responder) shape the relay-route ICE list before `new RTCPeerConnection`. The
  limitation is werift's, the responder needs it as much as the initiator, and the rule then does not depend
  on which Worker version is deployed. `services/connect/src/turn.ts` keeps passing Cloudflare's list
  verbatim.
- **D2 — Selection by rank, not a hard-coded URL.** Within each ICE server entry, TURN URLs are ordered
  by rank, and entries are ordered by their best rank, so werift's "first TURN URL" is the best one:
  1. rank 0 — `turns:` on port 443 (TLS on the HTTPS port; passes the most restrictive firewalls),
  2. rank 1 — any other `turns:` URL,
  3. rank 2 — `turn:` with `transport=tcp`,
  4. rank 3 — any other `turn:` URL (UDP).
  The sort is stable, so equal ranks keep Cloudflare's order. `username` and `credential` stay on the entry
  that carries the URL.
- **D3 — Drop STUN URLs from the relay-route list.** `stun:` / `stuns:` URLs are removed, and an entry left
  with no URLs is dropped. This removes the responder's 5 s STUN wait (root cause 4). Cost: the responder
  offers no server-reflexive candidate, so a session that could have used one TURN leg (initiator relay ↔
  responder server-reflexive) uses two (relay ↔ relay). The direct route, tried before the relay, already
  covers STUN-based paths.
- **D4 — No TURN URL ⇒ unchanged list.** If the list holds no `turn:` / `turns:` URL, the function
  returns its input unchanged (today's behaviour; the relay cannot work without TURN anyway).
- **D5 — `RELAY_PROBE_TIMEOUT_MS` stays 10 000 ms.** Budget after the fix, UDP blocked on one or both ends:
  directory credential request (1 RTT to the Durable Object) + TLS TURN allocation per side (TCP 1 RTT +
  TLS 1–2 RTT + ALLOCATE 401 + ALLOCATE = ~5 RTT to the nearest Cloudflare edge, ~0.1–0.5 s) + signalling
  (2 one-way trips through the directory) + ICE checks through two relays (~2–4 RTT) + DTLS (2 RTT) + SCTP
  (2 RTT) + data channel open (1 RTT) + Noise IK (1 RTT). At a 150 ms end-to-end RTT that is about 3–4 s,
  well inside 10 s. The live check (WI-4) records the measured time; if it exceeds 7 s, the follow-up
  issue proposes a larger relay budget.
- **D6 — Selection only, no per-attempt rotation.** Retrying the relay dial with another TURN URL after a
  failure would add another full 10 s attempt per URL for no gain over picking the most reachable URL
  first.
- **D7 — The helper is a separate pure module.** `src/lib/anywhere/channel/relay-ice-servers.ts` has no
  werift import in its implementation, so it is unit-testable without network I/O. Its test also runs
  werift's exported `parseIceServers` on the output to pin which URL werift actually uses (a werift bump
  that changes the selection then fails the test).
- **D8 — Issue section 2 is recorded, not root-caused here.** If the live check shows the TLS allocation
  succeeds but the data channel still does not open, the work agent files a follow-up issue with the
  `DEBUG=werift*` logs from both ends and links it from the evidence file. It must not describe the relay
  as working in the docs unless the live check showed the channel open.

## Requirements

- **FR-1** — For the relay route, the ICE list passed to `new RTCPeerConnection` puts a TLS TURN URL first
  when the credential response holds one, by the D2 ranking.
- **FR-2** — For the relay route, the ICE list holds no `stun:` / `stuns:` URL.
- **FR-3** — The shaping applies on both the initiator (`create`) and the responder (`accept`), and only
  when `relay === true`. The direct route's list is passed through unchanged.
- **FR-4** — `username` and `credential` stay with the TURN URLs they came with.
- **FR-5** — A list with no TURN URL is returned unchanged.
- **FR-6** — The docs describe the relay's TURN transport preference and why werift needs it.
- **NFR-1** — Unit tests use no real network I/O and no timers.
- **NFR-2** — No change to `services/connect`, the contracts package, or werift itself.

## Work items

### WI-1 — Pure relay ICE list helper (FR-1, FR-2, FR-4, FR-5, NFR-1)

**New file** `src/lib/anywhere/channel/relay-ice-servers.ts`:

```ts
/**
 * The relay route's ICE list (PAN-4862). werift 0.25.1 uses only the first TURN URL it finds, and a
 * blocked UDP allocation falls back to TCP only after ~6.35 s, so the order we pass decides whether a
 * relay can open inside RELAY_PROBE_TIMEOUT_MS. TLS first, then TCP, then UDP; STUN dropped, because the
 * responder would otherwise wait 5 s for a server-reflexive candidate on a UDP-blocked network.
 */
export interface RTCIceServerLike {
  urls: string | string[];
  username?: string;
  credential?: string;
}

/** 0 = turns: on 443, 1 = other turns:, 2 = turn: over TCP, 3 = other turn:, null = not a TURN URL. */
export function turnUrlRank(url: string): number | null { … }

export function relayIceServers(servers: readonly RTCIceServerLike[]): RTCIceServerLike[] { … }
```

Rules for `turnUrlRank` (case-insensitive scheme, as werift parses it):
- `^turns:` → port is the digits after the last `:` of the authority (the part before `?`); port `443` →
  0, otherwise (including no port, which werift treats as 5349) → 1.
- `^turn:` with query `transport=tcp` → 2; any other `^turn:` → 3.
- Anything else → `null`.

Rules for `relayIceServers`:
1. Normalise each entry's `urls` to an array.
2. Keep only URLs with a non-null rank; stable-sort them by rank.
3. Drop entries left with no URLs; stable-sort entries by their lowest rank.
4. Copy `username` / `credential` onto the output entry only when present on the input.
5. If no entry kept a URL, return the input unchanged (a shallow copy is fine).

Type move: the `RTCIceServerLike` interface moves from `rtc-transport.ts` into `relay-ice-servers.ts`
(shown above), and `rtc-transport.ts` re-exports it with
`export type { RTCIceServerLike } from './relay-ice-servers.js';` so `directory-rtc.ts`'s existing import
(`import { type RTCIceServerLike, … } from '../../../lib/anywhere/channel/rtc-transport.js'`) keeps
compiling. This keeps the dependency one-way (`rtc-transport.ts` → `relay-ice-servers.ts`), so
`npm run lint:circular` sees no cycle, and the helper has no runtime werift import.

**New test** `src/lib/anywhere/channel/__tests__/relay-ice-servers.test.ts` (plain Vitest, no timers, no
network). Fixture — the Cloudflare shape:

```ts
const CLOUDFLARE = [{
  urls: [
    'stun:stun.cloudflare.com:3478', 'stun:stun.cloudflare.com:53',
    'turn:turn.cloudflare.com:3478?transport=udp', 'turn:turn.cloudflare.com:53?transport=udp',
    'turn:turn.cloudflare.com:3478?transport=tcp', 'turn:turn.cloudflare.com:80?transport=tcp',
    'turns:turn.cloudflare.com:5349?transport=tcp', 'turns:turn.cloudflare.com:443?transport=tcp',
  ],
  username: 'u', credential: 'c',
}];
```

Named cases:
- `puts turns: on 443 first and drops STUN` → `urls` equal
  `['turns:…:443?transport=tcp', 'turns:…:5349?transport=tcp', 'turn:…:3478?transport=tcp', 'turn:…:80?transport=tcp', 'turn:…:3478?transport=udp', 'turn:…:53?transport=udp']`, `username` `'u'`, `credential` `'c'`.
- `werift picks TLS on 443` → `parseIceServers(relayIceServers(CLOUDFLARE))` (imported from `'werift'`)
  has `turnServer` `['turn.cloudflare.com', 443]`, `turnTransport` `'tls'`, `turnUsername` `'u'`,
  `stunServer` `undefined`.
- `prefers TCP when there is no turns: URL` → werift `turnTransport` `'tcp'`.
- `keeps a UDP-only list usable` → `['turn:h:3478?transport=udp']` stays, werift `turnTransport` `'udp'`.
- `orders entries by their best URL` → a UDP entry with credentials A before a TLS entry with credentials
  B comes out TLS entry first, still carrying B.
- `returns a list with no TURN URL unchanged` → `[{ urls: ['stun:s:3478'] }]` deep-equals the input.
- `accepts a string urls value` → `{ urls: 'turns:h:443?transport=tcp', … }` is handled.

New private method:
```ts
  /** The relay route's list is reordered for werift's one-TURN-URL rule (PAN-4862). */
  private async peerIceServers(relay: boolean): Promise<RTCIceServerLike[]> {
    const servers = await this.port.iceServers(relay);
    return relay ? relayIceServers(servers) : servers;
  }
```

### WI-4 — Live relay check (implementation checkpoint)

Run after WI-1 and WI-2 are merged into the branch and pushed. Write the evidence to

Procedure (from `.pan/uat/pan-4774/ac-03-direct-relay.md` on `feature/pan-4774`, condensed):
1. A Fly VM running a branch-built image with `pan serve --port 3011 --no-open`, signed in to the same
   relay-plan account as home (`pan account login`; the device code goes to the Flywheel with
   `pan tell flywheel-orchestrator "PAN-4862 device code …"`), joined with
   `pan machines join --to <home>`, approved on home, accepted on the VM. Home must run the branch build too.
2. Start the VM's server with `DEBUG=werift*`.
3. On the VM, for both `iptables` and `ip6tables`:
   `-A OUTPUT -p udp --dport 53 -j ACCEPT`, `-A INPUT -p udp --sport 53 -j ACCEPT`,
   `-A OUTPUT -p udp -j DROP`, `-A INPUT -p udp -j DROP`.
4. On home: `POST /api/machines/<link>/reconnect`, then poll `pan machines list --json` for 120 s.
5. Variant (TCP-only egress): also drop TCP except port 443 (`-A OUTPUT -p tcp --dport 443 -j ACCEPT`,
   `-A OUTPUT -p tcp -m state --state ESTABLISHED,RELATED -j ACCEPT`, `-A OUTPUT -p tcp -j DROP`, keeping
   the existing loopback and DNS rules), and repeat step 4.

Record two outcomes separately for each run:
- **Outcome A — TLS allocation:** the VM log shows `iceOptions { turnServer: [ 'turn.cloudflare.com', 443 ], turnTransport: 'tls', … }` and a `turn candidateAddress` line.
- **Outcome B — channel open:** `pan machines list --json` on home shows the link `online` with the
  `rtc+turn://…` route current, and the time from reconnect to online.

Decision rules:
- A and B pass → record both; the issue is done.
- A passes, B fails → collect `DEBUG=werift*` logs from both ends, file a follow-up issue titled
  "Relay data channel does not open over TLS TURN (PAN-4862 section 2)" with the logs, link it from the
  evidence file, and `pan tell flywheel-orchestrator` with the follow-up number. Do not edit the docs to
  claim the relay connects on UDP-blocked networks (WI-3 item 4 says only which transport it tries).
- A fails → the fix is wrong; return to WI-1/WI-2.
- The environment cannot be set up (no Fly access, or the device code is not approved within 30 min) →
  write the evidence file with `Status: not-run` and the reason, `pan tell flywheel-orchestrator`, and
  continue; the PAN-4774 AC-3 re-run is the backstop.
