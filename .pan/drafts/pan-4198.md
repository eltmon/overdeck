That fails the finalize size gate (`PROJECTED_SURFACE_MAX_FILES = 25`, `PROJECTED_SURFACE_MAX_SUBSYSTEMS = 6`, `src/lib/xbrief/quality-lint.ts:38-39`). Each part below can ship on its own:

## Glossary

- **Issue action registry.** `ISSUE_ACTIONS` in `src/dashboard/frontend/src/lib/issueActions.ts`. One entry per issue action: `key`, `label`, `description`, `kind`, `panVerb`, `endpoint`, `enabledWhen`, `phasePrimary`, `group`. Every issue-action surface renders from it.
- **Action key.** A member of the `IssueActionKey` union (`issueActions.ts:18-57`, 39 keys today).
- **Grouped menu body.** `IssueActionGroupedBody.tsx` (`src/dashboard/frontend/src/components/IssueActionMenu/`). It is the shared body of both the right-click menu (`IssueActionContextMenu`) and the overflow popover. The issue-row right-click in the project tree (`FeatureItem.tsx` → `FeatureContextMenu`) and the Kanban and Pipeline overflow menus all render it.
- **Dispatcher.** `useIssueActions` in `src/dashboard/frontend/src/components/IssueActionMenu/useIssueActions.ts`. `runAction` (line 432) decides for each action whether to open a dialog, ask for typed confirmation, or POST to the endpoint.
- **Dialog host.** `IssueActionDialogHost` in `IssueActionMenu.tsx:377-433`. It renders the dialog for `activeDialog.key`.
- **Derived state.** `DerivedIssueState.state` (`packages/contracts/src/derived-issue-state.ts:19-29`): `backlog | parked | planned | working | in-review | changes-requested | ready | merged | closed`. "Planning" is not a value. It is `planned` plus a live plan pane, which `derivePipelineState` (`src/dashboard/frontend/src/lib/issuePipelineState.ts:48-71`) maps to `planning_active`.
- **Phase.** `PipelinePhase` from `deriveIssueActionPhase` (`issueActions.ts:651`). Phase primaries (`PHASE_PRIMARY_KEYS`, `issueActions.ts:568`) are the "obvious next step" actions.
- **Placement (new).** A new registry field. `'menu'` means the action appears in menus. `'contextual'` means the action is kept in the registry and invoked by key from a card or button (for example `NeedsYouSlot`, `AgentsLane`), but never listed in a menu.
- **Menu actions (new).** `getMenuActions(state)` = the registry entries with `placement === 'menu'` whose `enabledWhen(state)` is true. This is exactly the set a menu renders.
- **Retired key.** A key removed from `IssueActionKey`. It is recorded in `RETIREMENT_AUDIT` (`src/dashboard/frontend/src/lib/__tests__/issueActions.parity.test.tsx:92-112`) with a successor key or a stated new home.

## The problem (verified)

- The grouped body renders **every** registry action, disabled ones included, with a reason. The header reads `{availableCount} available now · {actions.all.length - availableCount} gated` (`IssueActionGroupedBody.tsx:210`). Phase primaries appear twice: once in "For this phase" (`:213-223`) and again in their group (`:225-236`).
- Overlaps:
  - Seven ways to try again: restartAgent, restartFromPlan, completeWorkReset, resetSession, recoverAgent, resumeSession, rebuildAndStart.
  - Five teardown actions: resetIssue, wipe, destroyWorkspace, cancel, closeOut.
  - Five planning actions: plan, autoPlan, watchPlanning, donePlanning, startSkipPlanning.
- Broken or meaningless entries:
  - `watchPlanning` opens a placeholder frame, "This action opens from the shared issue action surface." (`IssueActionMenu.tsx:428-432`).
  - `autoPlan` names `/api/issues/:id/plan`, which is **not a registered route**. It only passes `issueActions.c-actions.test.ts:86` because that substring appears in a header comment at `src/dashboard/server/routes/issues.ts:8`. Both `plan` and `autoPlan` actually open `PlanDialog`, which POSTs `/api/issues/:id/start-planning` (`PlanDialog.tsx:213-216`).
  - `startSkipPlanning` opens `PlanDialog` with `autoStart`, which just clicks "Auto-plan" for the user (`PlanDialog.tsx:506-513`). It never sends the server's `autoStart` field, which maps to `autoSpawnOnFinalize` (`src/lib/overdeck/planning-sessions.ts:169,430`). So "start without planning" does not start anything.
  - `upload` is hard-disabled (`enabledWhen: () => false`).
- Semantics that decide the consolidation (read from `src/dashboard/server/routes/agents/lifecycle-restart.ts`):
  - `POST /api/agents/:id/restart` (line 255) stops and relaunches the agent with its context.
  - `POST /api/agents/:id/recover` (line 174) relaunches a crashed or stopped agent with context. It returns 409 `already-running` when the harness is live.
  - `POST /api/agents/:id/restart-fresh` (line 444) wipes agent state, keeps the workspace, plan, tasks and branch, and with `{spawn:true}` (the default) spawns a new work agent through the `/api/agents` flow. `{spawn:false}` is today's `completeWorkReset`.
  - `POST /api/agents/:id/reset-session` (line 724) discards session pointers.
  - `restartFromPlan` POSTs `/api/agents` on the same workspace, which is the same outcome as `restart-fresh {spawn:true}` without the stale-state wipe.
  - `deepWipeIssue` (`src/lib/overdeck/workspace-hygiene.ts:134`) is `runDestructiveIssueLifecycle(id, 'reset')` plus an archive-row flag. That is the same teardown as `resetIssue` (`/api/issues/:id/reset` → `resetIssueTransition`, `src/lib/overdeck/issue-transitions.ts:379`).

## Decisions

- **D1 — Menus show enabled actions only.** Gated actions are hidden on every surface that uses the grouped body. The "N available now · M gated" line and disabled rows go. *Why:* the ≤10 acceptance counts what the operator sees. One body serves both the popover and the context menu, so they stay identical.
- **D2 — Primaries are not repeated.** An enabled phase primary renders only in the top section, which is relabeled "Next step". It is left out of its group section, the Danger section included.
- **D3 — Four groups.** `IssueActionGroup = 'communicate' | 'lifecycle' | 'inspect' | 'danger'`, and `GROUP_ORDER = ['communicate', 'lifecycle', 'inspect', 'danger']`. Labels: Communicate / Actions / Inspect / Danger. `navigation` folds into `inspect`. `recover` folds into `lifecycle`.
- **D4 — Placement field instead of deleting live consumers.** `pause`, `recoverAgent`, `rebuildAndStart` and `createWorkspace` become `placement: 'contextual'`. Their card consumers keep working unchanged:
  - `recoverAgent`: `NeedsYouSlot.tsx:38-44`, `AgentActivityCards.tsx:140`, `spotlight.ts`.
  - `rebuildAndStart` and `createWorkspace`: `AgentsLane.tsx:145`, `WorkspaceCard.tsx:59`.
  - `pause`: the agent-scope menu `AGENT_SCOPE_ACTION_KEYS` (`IssueActionMenu.tsx:47-54`).
  All other kept keys are `placement: 'menu'`.
- **D5 — The agent-scope menu ignores placement.** When `agentScopeOnly` is set, the menu shows the `AGENT_SCOPE_ACTION_KEYS` allowlist filtered by `enabledWhen` only. So `FleetAgentsView` still offers Pause and Recover.
- **D6 — Twelve keys retired.** Each gets a `RETIREMENT_AUDIT` row. Server endpoints stay; this issue removes UI entries only.

  | Retired key | Successor / new home | Why |
  | --- | --- | --- |
  | `autoPlan` | `plan` | `PlanDialog` already offers interview and automatic. The phantom endpoint goes with the key. |
  | `startSkipPlanning` | `plan` | It becomes `PlanDialog`'s "Start work as soon as the plan is ready" checkbox (D8). |
  | `restartFromPlan` | `restartAgent` | Fresh-session restart gives the same outcome and also clears stale agent state. |
  | `completeWorkReset` | `restartAgent` | Fresh-session restart covers it. The wipe-without-spawn variant is dropped from the UI. `/restart-fresh {spawn:false}` stays on the server. |
  | `resetSession` | `restartAgent` | Discarding session memory is what the fresh-session option means. |
  | `wipe` | `resetIssue` | Deep wipe runs the same `runDestructiveIssueLifecycle(id,'reset')`. `pan wipe` stays in the CLI. |
  | `inference` | new home: `src/dashboard/frontend/src/components/Stage/panes/DocsPane.tsx` (INFERENCE tab) | Artifact viewer, not an action. |
  | `discussions` | new home: `src/dashboard/frontend/src/components/Stage/cockpit/IssueDigTabs.tsx` (Discussions tab) | Same. |
  | `transcripts` | new home: the issue drawer conversation tab, `src/dashboard/frontend/src/lib/store.ts` `openIssue(id,'conversation')` | Same. |
  | `upload` | dropped | It has been hard-disabled with no handler. |
  | `syncDiscussions` | dropped | Rare. `POST /api/command-deck/planning/:issueId/sync-discussions` (`src/dashboard/server/routes/command-deck.ts:1101`) stays for automation. |
  | `copySettings` | dropped | Rare. `POST /api/issues/:id/copy-settings` (`routes/issues.ts:527`) stays. |

- **D7 — The `RETIREMENT_AUDIT` row shape widens.** It becomes `{ retiredKey, consumer, successorKeys: readonly IssueActionKey[], newHome?: string, dropped?: string }`. The parity test accepts a row when `successorKeys` is non-empty and every successor is a live key, **or** `newHome` names an existing repo file, **or** `dropped` is a non-empty reason. This matches the "new home or dropped (why)" idiom of `docs/THE-CUT.md`.
- **D8 — One "Plan…" dialog.** `PlanDialog` keeps its two start buttons, relabeled **"Plan with me"** (interview; was "Start Planning") and **"Plan automatically"** (was "Auto-plan"). It adds a checkbox, **"Start work as soon as the plan is ready"**, which sends `autoStart: true` in the start-planning body. The `autoStart` prop and its auto-click effect (`PlanDialog.tsx:21,91,111,506-513`) are removed. The issue suggested putting this in a "Start dialog", but no Start dialog exists (`startAgent` POSTs `/api/agents` directly), and "start without planning" only applies to an unplanned issue, where the Plan dialog is the entry point.
- **D9 — "Open planning session".** `watchPlanning` is relabeled and dispatched as `openIssue(issueId, 'conversation')` (store action at `src/dashboard/frontend/src/lib/store.ts:213`). Its kind becomes `'safe'` and its endpoint stays `null`. **Implementation checkpoint:** confirm in the running dashboard that the drawer's conversation tab shows the planning agent while planning is live. *Fallback:* if the tab shows no planning agent, still dispatch `openIssue(issueId, 'conversation')` and add a hazard note to the PR. Do not invent a new route.
- **D10 — "Restart agent…" dialog with two options.** A new `RestartAgentDialog`:
  - **Keep its memory** (default). A live agent (`hasLiveAgent`) goes to `POST /api/agents/:agentId/restart` with `{ graceful: true }`. A stopped or crashed agent goes to `POST /api/agents/:agentId/recover` with `{}`.
  - **Fresh session** goes to `POST /api/agents/:agentId/restart-fresh` with `{ spawn: true }`. The copy says: "The workspace, branch, plan and tasks stay. The agent's saved conversation is discarded."
  - No "from plan" option (see D6). Rebuild-containers stays the contextual `rebuildAndStart` card action.
  - `restartAgent.kind` becomes `'dialog'` (the dialog's own confirm button replaces the typed confirmation). The registry endpoint stays `/api/agents/:agentId/restart`.
- **D11 — Submit with an endpoint override.** `PostActionInput` and `submitDialogAction` in `useIssueActions.ts` gain an optional `endpoint?: string` override (interpolated with `interpolateEndpoint`). `RestartAgentDialog` uses it to reach `/recover` and `/restart-fresh` through the same mutation, so the 409 recovery handling, error `alert()` and dashboard refresh stay shared.
- **D12 — Plain-language labels and one-sentence descriptions** exactly as in the target table below. No label contains "Done planning" or "Watch planning".
- **D13 — FeatureItem "This session" extras go under "Debug".** Open State Dir and View JSONL render inside a collapsed **Debug** disclosure, built the same way as the Danger disclosure, instead of the always-open "This session" section. The Zone B session strip is untouched (non-goal).
- **D14 — Reset to Todo is a relabel only here.** Its description must not claim archiving. #4203 adds archive-first behavior.

New and changed predicates (`issueActions.ts`, near today's predicates at lines 504-564):

```ts
const derivedState = (state: IssueActionState) => state.derived?.state;
const reviewOrLater = (state: IssueActionState) => ['in-review', 'ready'].includes(derivedState(state) ?? '');
const canResumeWork = (state: IssueActionState) =>
  hasResumableSession(state) && !isMerged(state) && !isDoneOrCanceled(state) && !reviewOrLater(state);
const canRestartAgent = (state: IssueActionState) =>
  hasAgent(state) && state.agent?.role !== 'plan' && !isMerged(state) && !isDoneOrCanceled(state) && !reviewOrLater(state);
const canSyncMain = (state: IssueActionState) =>
  hasWorkspace(state) && hasStoppedAgent(state) && !isMerged(state) && !isDoneOrCanceled(state)
  && deriveIssueActionPhase(state) !== 'PLANNING';
const canResetIssue = (state: IssueActionState) =>
  (hasWorkspace(state) || hasAgent(state) || state.hasPlan || hasPrTarget(state)) && !isMerged(state) && !isDoneOrCanceled(state);
const canDestroyWorkspace = (state: IssueActionState) => hasWorkspace(state) && isDoneOrCanceled(state);
// Tightened: order books queue work that has not started.
const canAddToOrderBook = (state: IssueActionState) =>
  state.orderBooksLoaded === true && !state.isInActiveOrderBook && !isMerged(state) && !isDoneOrCanceled(state)
  && !hasLiveAgent(state) && ['backlog', 'parked', 'planned', undefined].includes(derivedState(state));
// requestReview gains: && derivedState(state) === 'working'
```

`canDestroyWorkspace` matches the server rule. `cleanupWorkspaceForIssue` (`src/lib/overdeck/workspace-hygiene.ts:61`) returns 409 unless `isOrphanedIssue` (`src/lib/overdeck/issue-transitions.ts:138`) sees a tracker status or state containing closed, done, or completed. A merged issue whose tracker issue is still open would get a 409, so merged-but-open issues do not offer Delete workspace. Close out tidies them instead.

Also delete the orphaned "Complete review reset" comment at `issueActions.ts:554-557`, and `canStartWithoutPlanning` (`:537`, no longer used).
