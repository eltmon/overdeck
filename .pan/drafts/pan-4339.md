# PAN-4339: `pan task claim` refuses a live competing claim and overlapping scope

**Issue:** [PAN-4339](https://github.com/eltmon/overdeck/issues/4339)
**Parent PRD:** [.pan/drafts/deft-adoption.md](deft-adoption.md), "Issue 5" (item 5 of 16, approved by the operator 2026-09-28).
**Related:** #4340 (item worktree for every mutating worker), #4350 (re-dispatch budget per item).
**Planned against:** `feature/pan-4339` at `6ac017656b2` (same tree as `origin/main` at planning time).

## Glossary

- **Continue file** — `<planHome>/.pan/continues/<ISSUE>.xbrief.json`. The only home for xBRIEF item status and item claims (`src/lib/xbrief/continue-state.ts`, module header). `pan task` writes it and commits it on the feature branch.
- **Plan home** — the checkout whose `.pan/` holds the issue's artifacts. `resolveTaskContext` (`src/cli/commands/task.ts`, lines 50-59) derives it from the *issue workspace path*, never the caller's cwd, so a worker in `<workspace>/.swarm/<item>/` still writes the issue workspace's continue file.
- **Claim** — the `claimedBy` / `claimedAt` pair on a continue-file item entry (`ContinueItemState`, `continue-state.ts` lines 157-166).
- **Active claim** — a continue-file item entry whose `claimedBy` is set AND whose `status` is neither `completed` nor `cancelled`. `blocked` and `pending` entries with a holder are active (the holder still owns the files).
- **Holder** — the agent id stored in `claimedBy`.
- **Claimant** — the id the current `pan task claim` process claims under (see FR-6).
- **Liveness** — the answer of `isAlive(agentId)` in `src/lib/agents/liveness.ts` (line 173). It returns a `LivenessVerdict`: `{ alive: true, … }`, or `{ alive: false, reason }`. `isConfirmedDead(verdict)` (line 101) is true only for a *confirmed* death; `reason: 'runtime-indeterminate'` means the probe itself failed.
- **Holder liveness** — the three-way classification this issue uses: `alive` (`verdict.alive`), `dead` (`isConfirmedDead(verdict)`), `indeterminate` (everything else).
- **files_scope / files_scope_confidence** — xBRIEF item metadata (`src/lib/xbrief/types.ts` lines 66-67): the files an item expects to touch and how sure the planner was (`high | medium | low`).
- **Overlap** — `hasFileOverlap(runningItems, candidate)` in `src/lib/xbrief/dag.ts` (line 303) returns true when either item's glob patterns match a path in the other's `files_scope`. An item with no `files_scope` never overlaps.
- **Steal** — the new `--steal` flag: the foreman's or operator's explicit override of a refusal.
- **Task-state lock** — the new per-worktree lock file that serializes every `pan task` write and its commit.
- **`pan spawn` worker** — the foreman's pane-only item worker (`src/cli/commands/spawn.ts`). Its backend agent name is `${issueId.toLowerCase()}-${item.id}` (spawn.ts line 127, `name:`).

## Problem

1. **Claims never refuse.** `claimItem` (`continue-state.ts` lines 289-310) writes `claimedBy: agentId` over whatever was there:

   ```ts
   [itemId]: {
     ...(state.items?.[itemId] ?? {}),
     status: state.items?.[itemId]?.status ?? 'in_progress',
     claimedBy: agentId,
     claimedAt,
   },
   ```

   `docs/XBRIEF.md` line 9 says "Two agents may race to claim an item; exactly one claim succeeds". That is false in code: both succeed and the last writer wins.

2. **Nothing stops overlapping parallel work.** Two workers can claim items whose `files_scope` overlap in the same wave. The only protection is prose in the foreman's dispatch prompt (`sync-sources/skills/pan-foreman/SKILL.md`: "concurrent workers in one worktree WILL clobber shared files").

3. **The write is an unguarded read-modify-write.** `updateContinueState` (`continue-state.ts` lines 235-246) reads, mutates, and `writeFileSync`s (line 232) with no lock. `runTaskClaim`, `runTaskDone`, and `runTaskStatus` then call `commitContinue` (`task.ts` lines 79-90), which runs `git add` + `git commit --only` in the plan home. Concurrent workers race on the file (lost updates: a claim written between `markItemDone`'s read and its write is erased) and on the git index.

4. **`pan spawn` workers claim under an id nobody can probe.** `runTaskClaim` (`task.ts` line 111) uses `process.env.OVERDECK_AGENT_ID ?? \`cli-${process.pid}\``. `pan spawn` sets only `OVERDECK_ISSUE_ID` and `OVERDECK_ITEM_ID` (spawn.ts line 125), and neither backend's `startAgent` adds `OVERDECK_AGENT_ID` (`src/lib/terminal-backends/herdr.ts` line 591 passes `spec.env` only; `tmux.ts` line 119 likewise). So a `pan spawn` worker claims as `cli-<pid>`, where the pid is the already-exited `pan` CLI process. A liveness check on that id always answers "no session", so without a fix the new holder check would never fire for exactly the workers this issue is about.

## Requirements

### Functional

- **FR-1** — `pan task claim <issue> <item>` exits non-zero and writes nothing when the item has an active claim by a different holder whose liveness is `alive`. The message names the holder.
- **FR-2** — The same refusal applies when the holder's liveness is `indeterminate`. The message says liveness could not be determined.
- **FR-3** — When the item's holder is `dead`, or the holder is the claimant itself, the claim succeeds and records the claimant as the new holder.
- **FR-4** — `pan task claim` exits non-zero and writes nothing when the item's `files_scope` overlaps (via `hasFileOverlap`) any *other* item with an active claim whose holder is `alive` or `indeterminate` — including other items held by the claimant itself. The message names the conflicting item, its holder, and the shared paths.
- **FR-5** — When the target item or a conflicting active item has `files_scope_confidence: "low"`, the two are treated as overlapping, and the refusal says a low-confidence scope is the reason.
- **FR-6** — The claimant id is `OVERDECK_CLAIM_ID`, else `OVERDECK_AGENT_ID`, else `cli-<pid>` (first non-empty wins).
- **FR-7** — `pan spawn` sets `OVERDECK_CLAIM_ID` in the worker pane's environment to the pane's backend agent name (`${issueId.toLowerCase()}-${item.id}`).
- **FR-8** — A holder id starting with `cli-` is classified `dead` without probing.
- **FR-9** — `pan task claim --steal` overrides every refusal from FR-1, FR-2, FR-4, and FR-5. It writes the claim and prints one stderr line per overridden refusal.
- **FR-10** — Every `pan task` writing verb (`claim`, `done`, `block`, `unblock`, `reopen`, `cancel`) holds the task-state lock across its continue-file read-modify-write AND its `commitContinue`. Of two concurrent `pan task claim` processes on the same item held by live claimants, exactly one succeeds.
- **FR-11** — The docs state the new behavior: `docs/XBRIEF.md`, `docs/FOREMAN.md`, `sync-sources/skills/pan-task/SKILL.md`, `sync-sources/skills/pan-foreman/SKILL.md`, `sync-sources/agents/pan-work-agent.md`, `src/lib/cloister/prompts/work.md`.

### Non-functional

- **NFR-1** — No lease, TTL, heartbeat, or stored liveness. Liveness is derived at claim time from `isAlive` and never written (the issue's "State rule").
- **NFR-2** — The lock is async (`node:fs/promises`), with no `*Sync` twin, and no `execSync` anywhere (`prefer-async`, `no-execsync-server` rules).
- **NFR-3** — The lock file never appears in `git status` of any checkout.
- **NFR-4** — Lock wait / stale-break unit tests use `vi.useFakeTimers()`; only the two-process contention test uses real time, bounded to a few seconds (`fake-timers-for-retry-tests` rule).
- **NFR-5** — The contention test is a regular `*.test.ts` (not `*.slow.test.ts`), because `VITEST_INCLUDE_SLOW` is set nowhere in `.github/` and slow tests never gate.
- **NFR-6** — Refusal messages are complete sentences: they name the holder, say nothing was written, and name both exits (`pan task next` and `--steal`) (`explain-fully-no-jargon` rule).

## Decisions (made here; auto mode)

- **D1 — Active claim** = `claimedBy` set and `status ∉ {completed, cancelled}`.
- **D2 — Same-holder re-claim is idempotent** (no FR-1 refusal), but the overlap set (FR-4) includes other items held by the claimant. Why: Claude Code in-harness subagents inherit the foreman's `OVERDECK_AGENT_ID`, so parallel subagents share one holder id; excluding same-holder items would give them no protection.
- **D3 — `indeterminate` counts as live** for both the holder check and the overlap set. A holder id missing from the liveness map is `indeterminate`.
- **D4 — `cli-*` holders are `dead`** (FR-8). The pid is a CLI process that has exited; probing would turn a Herdr socket outage into "indeterminate" and let one operator's manual claim block every worker.
- **D5 — `--steal` overrides both refusal kinds.** Otherwise a live-but-stuck overlapping holder has no escape except `pan task cancel`. There is no role check on `--steal`: this is cheap-path prevention, not a security boundary (parent PRD, threat model).
- **D6 — Raw `hasFileOverlap`,** not swarm-readiness's hotspot-stripped variant. Missing scope on either side = no overlap. Low confidence on either side = overlap (matches `analyzePairOverlap`, `src/lib/xbrief/swarm-readiness.ts` lines 121-136). An item id not found in the plan (for example a sub-item key) contributes no scope.
- **D7 — Lock location: the plan home's per-worktree git dir,** `git rev-parse --git-path overdeck-task-state.lock` run in the plan home, resolved against the plan home. NOT `<workspace>/.overdeck/` as the issue suggests "for example": the overdeck repo's `.gitignore` lists specific `.overdeck/` files, not the directory, so a lock there shows as `??` while held (and forever after a crash). The git dir is also exactly the index the lock protects.
- **D8 — Lock scope = every `pan task` writing verb** (FR-10). Other continue-file writers (`src/lib/cloister/deacon-swarm.ts:140`, `src/lib/xbrief/io.ts:394` and `:423`, `src/lib/xbrief/lifecycle-io.ts:319/335/347`, `src/cli/commands/done.ts:260`, `src/lib/pan-dir/migrate-plan-home.ts:392`) stay unlocked — a NonGoal.
- **D9 — New module `src/lib/xbrief/claim-check.ts`** holds the pure check and the async orchestrator, rather than growing `continue-state.ts` (410 lines). No import cycle: `claim-check → continue-state, dag, agents/liveness`; neither `continue-state` nor `dag` imports `claim-check`.
- **D10 — Dedicated env var `OVERDECK_CLAIM_ID`,** not `OVERDECK_AGENT_ID`, on `pan spawn` panes. `OVERDECK_AGENT_ID` drives the stop hook, auto-approve hook, cost recording, and the pre-rebase git guard (`src/lib/workspace-manager/worktree-ops.ts` line 73); setting it on spawn panes would change behavior far outside this issue.
- **D11 — `claimItem` keeps its status-preserving behavior** (a re-claimed `pending` item stays `pending`). Changing it is out of scope.
- **D12 — Lock parameters:** poll every 100 ms, give up after 60 000 ms with an error naming the holder pid; a lock is stale when its recorded pid is not running (`process.kill(pid, 0)` throws `ESRCH`), or when its content is unreadable and its mtime is older than 5 000 ms.

### W1 — Pure claim check + async orchestrator (`src/lib/xbrief/claim-check.ts`) — FR-1..FR-6, FR-8, FR-9, NFR-1

New file `src/lib/xbrief/claim-check.ts`. Exports:

```ts
import { isAlive, isConfirmedDead } from '../agents/liveness.js';
import { hasFileOverlap } from './dag.js';
import { claimItem, readContinueState, type ContinueItemsMap, type ContinueItemState } from './continue-state.js';
import type { XBriefItem } from './types.js';

export type HolderLiveness = 'alive' | 'dead' | 'indeterminate';

export type ClaimRefusal =
  | { kind: 'held'; holder: string; liveness: 'alive' | 'indeterminate' }
  | {
      kind: 'overlap';
      holder: string;
      liveness: 'alive' | 'indeterminate';
      conflictingItemId: string;
      sharedPaths: string[];
      lowConfidence: boolean;
    };

export type ClaimCheckResult =
  | { ok: true; overridden: ClaimRefusal[] }
  | { ok: false; refusal: ClaimRefusal };

export interface ClaimCheckInput {
  items: readonly XBriefItem[];
  claims: ContinueItemsMap;
  itemId: string;
  claimant: string;
  /** Liveness of every holder other than the claimant. A missing holder is 'indeterminate'. */
  liveness: ReadonlyMap<string, HolderLiveness>;
  steal?: boolean;
}

/** FR-6. */
export function resolveClaimantId(env: NodeJS.ProcessEnv = process.env, pid = process.pid): string;
/** Holders of active claims (D1) other than the claimant — the ids to probe. Sorted, unique. */
export function holdersToProbe(claims: ContinueItemsMap, claimant: string): string[];
/** FR-8 + liveness classification. `isAliveFn` defaults to `isAlive`. */
export async function probeHolder(holder: string, isAliveFn?: typeof isAlive): Promise<HolderLiveness>;
/** Pure. FR-1..FR-5, FR-9. */
export function checkClaim(input: ClaimCheckInput): ClaimCheckResult;
/** One sentence-complete message per refusal (NFR-6). */
export function formatClaimRefusal(itemId: string, refusal: ClaimRefusal): string;
export class ClaimRefused extends Error { constructor(readonly itemId: string, readonly refusal: ClaimRefusal); }
/** Read → probe (parallel) → check → claimItem. Throws ClaimRefused. Caller holds the task-state lock. */
export async function claimItemChecked(
  planHome: string,
  issueId: string,
  itemId: string,
  claimant: string,
  options: { items: readonly XBriefItem[]; probe?: (holder: string) => Promise<HolderLiveness>; steal?: boolean },
): Promise<{ state: ContinueItemState; overridden: ClaimRefusal[] }>;
```

`checkClaim` steps, in this order:

1. `claims[itemId]` is active (D1), its holder ≠ claimant, and the holder's liveness is `alive` or `indeterminate` ⇒ refusal `held`.
2. Target item = `items.find(i => i.id === itemId)`. For each *other* active claim key `k` (sorted ascending), with holder `h` whose liveness is `alive`/`indeterminate` (the claimant's own holdings count as `alive`, D2): find item `o = items.find(i => i.id === k)`; skip when either item is missing (D6). If either has `files_scope_confidence === 'low'` ⇒ refusal `overlap` with `lowConfidence: true`. Else if `hasFileOverlap([o], target)` ⇒ refusal `overlap` with `sharedPaths` = every path `p` from either scope for which `hasFileOverlap([other side], { ...side, metadata: { files_scope: [p] } })` holds, sorted. First refusal wins.
3. `steal: true` ⇒ collect every refusal the steps above would raise, return `{ ok: true, overridden }`. Otherwise `{ ok: true, overridden: [] }` when none.

`probeHolder(holder)`: `holder.startsWith('cli-')` ⇒ `'dead'`; otherwise `v = await isAliveFn(holder)`; `v.alive` ⇒ `'alive'`; `isConfirmedDead(v)` ⇒ `'dead'`; else `'indeterminate'`. A thrown probe ⇒ `'indeterminate'`.

`formatClaimRefusal` wording (exact shape):

- held/alive: `PAN-1-a is claimed by agent-x, which is still running. Nothing was written. Run "pan task next" to pick another item, or pass --steal if agent-x is stuck.`
- held/indeterminate: `PAN-1-a is claimed by agent-x, and Overdeck could not tell whether agent-x is still running (the terminal backend did not answer). Nothing was written. Run "pan task next" to pick another item, or pass --steal if you know agent-x is gone.`
- overlap: `PAN-1-b shares files with PAN-1-a, which agent-x has claimed and is still running: src/a/x.ts. Two workers editing the same files overwrite each other, so nothing was written. Wait for PAN-1-a to finish, run "pan task next" to pick another item, or pass --steal to claim it anyway.`
- overlap/lowConfidence: `PAN-1-b cannot run beside PAN-1-a (claimed by agent-x, still running): one of them has a low-confidence files_scope, so Overdeck cannot prove they touch different files. Nothing was written. …` (same two exits).

**Tests** — new `src/lib/xbrief/__tests__/claim-check.test.ts` (pure, no mocks except an injected `isAliveFn`):

- low confidence on either side ⇒ `overlap` with `lowConfidence: true`;
- completed/cancelled claims ignored; missing liveness entry ⇒ treated as indeterminate;

### W2 — Task-state lock (`src/lib/xbrief/task-state-lock.ts`) — FR-10, NFR-2, NFR-3, NFR-4

New file. Exports:

```ts
/** `git rev-parse --git-path overdeck-task-state.lock` in planHome (execFile, async), resolved against planHome. Throws a plain-English Error when planHome is not a git checkout. */
export async function taskStateLockPath(planHome: string): Promise<string>;

export interface TaskStateLockOptions {
  timeoutMs?: number; // default 60_000
  pollMs?: number;    // default 100
  isPidAlive?: (pid: number) => boolean; // default: process.kill(pid, 0), ESRCH ⇒ false, EPERM ⇒ true
}

export class TaskStateLockTimeout extends Error {}

/** Acquire (open 'wx', write {"pid","acquiredAt"}), run fn, release (unlink only if the file still names our pid). */
export async function withTaskStateLock<T>(lockPath: string, fn: () => Promise<T>, options?: TaskStateLockOptions): Promise<T>;
```

Acquire loop: `open(lockPath, 'wx')`; on `EEXIST` read the holder JSON. Stale (D12) ⇒ `unlink` and retry immediately. Otherwise wait `pollMs` (`await new Promise(r => setTimeout(r, pollMs))`) until `timeoutMs`, then throw `TaskStateLockTimeout`: `Another pan task command (pid 1234) has held the task-state lock for PAN-… for 60s. If that process is hung, stop it and run this again.` Release in `finally`.

**Tests** — new `src/lib/xbrief/__tests__/task-state-lock.test.ts`, temp dir lock path, `vi.useFakeTimers()` for every wait:
- runs fn and removes the lock file afterwards (also when fn throws);
- a lock held by a live pid (inject `isPidAlive: () => true`) makes a second acquire wait; advancing timers past `timeoutMs` rejects with `TaskStateLockTimeout` naming the pid;
- a lock naming a dead pid (`isPidAlive: () => false`) is broken immediately and fn runs;
- `taskStateLockPath` in a `git init` temp repo returns a path under `.git/` and that path does not appear in `git status --porcelain` after the lock file is created.

## Hazards

- **H1** — tmux host + a `pan spawn` worker on a non-Claude harness: `isAliveOnTmux` reads the harness from `state.json`, which spawn panes do not have, and defaults to `claude-code`; the runtime-pid probe then misses a codex process and answers `runtime-missing` (confirmed dead). Such a claim is treated as dead and overwritable — today's behavior, not a regression. Herdr hosts (the default) probe by agent name and are unaffected.
- **H2** — Holding the lock across `git commit --only` runs the repo's pre-commit hooks under the lock; the 60 s timeout covers that. If a hook hangs, the waiting process's timeout message names the holder pid.
- **H3** — `plan-finalize.ts` `readPrdDraftText` (line 154) reads `<ISSUE-UPPER>.md`, so the trace-coverage lint does not see this lowercase draft. Every FR/NFR is still traced on a plan item.
