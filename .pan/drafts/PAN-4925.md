# PAN-4925: CI test-shard 3/4 intermittently fails with "Worker exited unexpectedly" while every test passes

**Issue:** https://github.com/eltmon/overdeck/issues/4925
**Follow-up (out of scope here):** https://github.com/eltmon/overdeck/issues/4926 — the production `stopSmeeProcess()` PID-reuse bug.

## Glossary

- **Fork worker** — a child process that Vitest's `forks` pool (`vitest.config.ts`, `pool: 'forks'`, `maxWorkers: 4`) starts to run one test file. Its `process.pid` is a normal host PID, and its `process.ppid` is the main Vitest process.
- **"Worker exited unexpectedly"** — the error Vitest's main process raises from `ChildProcess.emitUnexpectedExit` when a fork worker exits before it reports its file's results. Vitest prints it as one "Unhandled Error" and fails the run even when every reported test passed.
- **Unreported file** — the test file whose fork worker died. Its tests never print a `✓  root  <file>` line, so the run reports one file fewer than its total (`579 passed | 1 skipped (581)`).
- **Fixture PID** — a made-up PID that a test feeds to the code under test, here `'12345'` returned by a mocked `readFileSync` for `~/.overdeck/github-app/smee.pid`.
- **Signal 0** — `process.kill(pid, 0)` sends no signal. It only probes whether `pid` exists. Any other signal (`'SIGTERM'`, `'SIGKILL'`, `15`) acts on the process.
- **PID namespace repro** — `unshare -rpf --mount-proc` starts a shell in a new user and PID namespace where an unprivileged user may write `/proc/sys/kernel/ns_last_pid`, so the next process gets a chosen PID (12345). This makes the CI coincidence deterministic.
- **Test guard** — a Vitest `setupFiles` module under `tests/setup/` that wraps a dangerous Node API for every root-project test file and throws an error whose message starts with `[test-guard]`. `tests/setup/no-real-home-writes.ts` is the existing example.

## Root cause (verified)

**File:** `tests/unit/lib/smee-process.test.ts`, the test `stopSmeeProcess > stops running process and removes pidfile` (line 235).

**Cause:** the test mocks `node:fs` so every `readFileSync` returns `'12345'`, then calls the real `stopSmeeProcess()` without mocking `process.kill`. `stopSmeeProcess()` (`src/lib/smee.ts`, line 219) reads PID 12345 from the mocked pidfile, probes it with the real `process.kill(12345, 0)` (`isProcessAlive`, line 51), and, if the probe succeeds, sends the real `process.kill(12345, 'SIGTERM')` (`terminateProcess`, line 115). Whatever process holds PID 12345 on the host dies.

Current test (lines 234–247):

```ts
describe('stopSmeeProcess', () => {
  it('stops running process and removes pidfile', () => {
    mockReadFileSync.mockReturnValue('12345');
    const logSpy = vi.spyOn(console, 'log').mockImplementation(() => {});

    stopSmeeProcess();

    expect(mockUnlinkSync).toHaveBeenCalledWith(
      expect.stringContaining('smee.pid'),
    );
    expect(logSpy).toHaveBeenCalledWith('[smee] Process stopped');
    logSpy.mockRestore();
  });
```

Code under test (`src/lib/smee.ts`, lines 219–232):

```ts
export function stopSmeeProcess(): void {
  const smeeUrl = getSmeeUrl();
  const target = smeeUrl ? getWebhookTarget() : null;
  const matchingPids = smeeUrl && target ? findMatchingSmeeProcesses(smeeUrl, target) : [];
  const pid = readSmeePid();
  const pidsToStop = new Set<number>(matchingPids);
  if (pid) pidsToStop.add(pid);

  for (const pidToStop of pidsToStop) {
    if (isProcessAlive(pidToStop)) terminateProcess(pidToStop);
  }
```

**Why the worker that dies is the smee worker itself.** In both failed runs the unreported file is `tests/unit/lib/smee-process.test.ts`. If the SIGTERM had hit a sibling fork, the sibling's file would be the unreported one, and it would differ between runs. So on both runs the process at PID 12345 was the fork running the smee test, and it signalled itself. SIGTERM's default action ends Node with exit status 143 and prints nothing, so the log has no `heap out of memory`, `FATAL ERROR`, `SIGKILL`, `SIGSEGV`, or `process.exit unexpectedly called`. Vitest only sees the child's `onexit`.

**Prior art.** Commit `cbedd4bf4d7` ("mock process.kill in smee-process spawn tests to kill flakiness") added `process.kill` spies to the `startSmeeProcess` tests for the same reason. The comment it added (line 84) states the hazard: "without mocking process.kill, isProcessAlive() probes the real host process table". The `stopSmeeProcess` tests were left unmocked.

### Why it is intermittent

The test only kills something when PID 12345 is alive at that moment. On a fresh GitHub runner, the PID counter reaches 12345 during the shard-3 run, at a point that depends on how many processes the build and earlier test files spawned. When the counter lands on the smee fork itself, shard 3 fails. Two of the last eight main runs hit it.

## Requirements

- **FR-1** — `tests/unit/lib/smee-process.test.ts` sends no real signal to any host process. Every `stopSmeeProcess()` test spies `process.kill`.
- **FR-2** — The `stops running process and removes pidfile` test asserts that `stopSmeeProcess()` probes PID 12345 with signal 0 and then sends it `'SIGTERM'`, through the spy.
- **FR-3** — A root-project test guard (`tests/setup/worker-signal-guard.ts`, installed by `tests/setup/no-worker-signals.ts`) refuses any non-zero signal that a test sends through `process.kill` to the worker itself (`process.pid`), the main Vitest process (`process.ppid`), PID `0` (the caller's process group), or PID `-1` (every process the user may signal). The refused call throws an `Error` whose message starts with `[test-guard]` and names the PID and signal.
- **FR-4** — When the code under test swallows the guard's error (as `terminateProcess` does with `try { … } catch {}`), the guard still fails the running test: it records the refusal, and the `afterEach` hook the installer registers throws a `[test-guard]` error that names each refused call.
- **FR-5** — The guard passes through signal 0 for any PID, and any signal for any other PID, by calling the original `process.kill` unchanged.
- **FR-6** — `docs/TESTING.md` states the fixture-PID rule, names the `[test-guard]` refusal, and gives the recipe for finding the unreported file after "Worker exited unexpectedly".
- **NFR-1** — No quarantine, no `.skip`/`.skipIf`/`.only`, no change to `maxWorkers`, `pool`, `retry`, `--max-old-space-size`, or the CI workflow.
- **NFR-2** — No change to `src/lib/smee.ts`. The production PID-reuse fix is #4926.
- **NFR-3** — The guard adds no measurable cost to a test run: it does no file I/O and no child-process work, only integer comparisons.

## Decisions

- **D1 — Fix the test, not the code under test, in this issue.** The test's job is to verify `stopSmeeProcess()`'s pidfile path with a fixture PID, so the test must own `process.kill`. The production code has a related bug (it signals a stale pidfile PID without checking its command line). That bug is real but separate, and fixing it would change `pan down` behavior. It is filed as #4926.
- **D2 — Add a self-signal guard (FR-3, FR-4).** The fix in FR-1 stops this one file. The guard turns the next test that signals its own worker into a named test failure instead of an unattributed worker exit. It follows the existing `tests/setup/no-real-home-writes.ts` pattern. A repo grep (`rg -n "process\.kill\(\s*process\.(pid|ppid)" tests src packages`) finds one self-signal, `src/cli/commands/__tests__/skills-pack-browser.test.ts:225`, and it uses signal 0, so the guard breaks no current test.
- **D3 — The guard does not protect sibling workers.** Detecting a sibling needs a `/proc/<pid>/stat` read per call and is Linux-only. Both CI failures were self-signals. A sibling check is a non-goal.
- **D4 — No CI-only per-worker reporter.** Diffing the `✓ root <file>` lines between a failed and a passing attempt already names the unreported file. The docs item records that recipe instead.
- **D5 — No sweep of the 39 test files that carry literal PIDs without a `process.kill` spy.** Most use the PID only as data (state rows, mocked command output). The guard covers the self-signal case for all of them. The landmine is recorded in `.overdeck/context/codebase/concerns.md`.
- **D6 — The 5-rerun acceptance criterion is kept, but it is not the proof.** At the observed ~25% failure rate, 5 green runs have about a 24% chance (0.75⁵) of happening with the bug still present. The PID namespace repro (before: `victim DEAD exit=143`; after: `victim ALIVE`) is the proof and goes in the PR description.

### WI-2 — Add the self-signal test guard (FR-3, FR-4, FR-5, NFR-3)

**Files:** new `tests/setup/worker-signal-guard.ts` (pure logic, no side effects); new `tests/setup/no-worker-signals.ts` (installs it); `vitest.config.ts` (the `setupFiles` line, line 69); new `tests/meta/no-worker-signals.test.ts`.

The refusal logic lives in a pure module so the meta test can exercise every refusal with a fake `kill` function and synthetic PIDs. No test ever sends a non-zero signal to a real protected PID, so a broken or missing guard cannot kill the Vitest worker, its parent, or the process group (see "Critique response").

Steps:

1. Create `tests/setup/worker-signal-guard.ts`. It imports nothing from `vitest` and touches no global state. It exports:
   - `type KillFn = (pid: number, signal?: string | number) => boolean;`
   - `function createWorkerSignalGuard(options: { kill: KillFn; protectedPids: readonly number[] }): { kill: KillFn; drainRefusals(): string[]; assertNoPendingRefusals(): void }`.
     - `kill(pid, signal)`: a signal is non-zero unless it is exactly `0`. An omitted signal means `'SIGTERM'` and counts as non-zero. When the signal is non-zero and `pid` is in `protectedPids`, build the message `` `[test-guard] refused process.kill(${pid}, ${String(signal ?? 'SIGTERM')}): that PID is this Vitest worker, the Vitest main process, or a process group — spy process.kill in the test (PAN-4925)` ``, push it onto the guard's own `refusals` array, write it with `console.error`, and `throw new Error(message)`. It must not call `options.kill` for a refused call. Otherwise return `options.kill(pid, signal)`.
     - `drainRefusals()`: returns the pending refusals and clears them.
     - `assertNoPendingRefusals()`: if refusals are pending, drains them and throws one `Error` whose message joins them with `\n`; otherwise returns.
   - `function installWorkerSignalGuard(target: { pid: number; ppid: number; kill: KillFn }, registerAfterEach: (hook: () => void) => void): ReturnType<typeof createWorkerSignalGuard>`.
     - Install once per target: keep the installed guard on `target[Symbol.for('overdeck.test.noWorkerSignals')]`. If it is already there, return it and do not wrap `target.kill` again or register a second hook. A reused fork can load `setupFiles` more than once, and a second wrap would split the refusals between two guards.
     - Otherwise: `const original = target.kill.bind(target);` create the guard with `protectedPids: [target.pid, target.ppid, 0, -1, -target.pid, -target.ppid]`, set `target.kill = guard.kill`, store the guard on the symbol key, call `registerAfterEach(() => guard.assertNoPendingRefusals())`, and return the guard.
   - Header comment: one paragraph naming PAN-4925 and the failure it prevents.
2. Create `tests/setup/no-worker-signals.ts`: `import { afterEach } from 'vitest';` and `installWorkerSignalGuard(process as unknown as Parameters<typeof installWorkerSignalGuard>[0], afterEach);`. Nothing else.
3. In `vitest.config.ts`, add `'tests/setup/no-worker-signals.ts'` to `setupFiles` directly after `'tests/setup/no-real-home-writes.ts'`.
4. Create `tests/meta/no-worker-signals.test.ts` (runtime behavior only; do not read source files, and add no `.skip`/`.skipIf`/`.only`). Unit checks use `createWorkerSignalGuard({ kill: fakeKill, protectedPids: [1001, 1000, 0, -1, -1001, -1000] })` with `const fakeKill = vi.fn(() => true)`:
   - `guard.kill(1001, 'SIGTERM')`, `guard.kill(1000, 'SIGKILL')`, `guard.kill(0, 'SIGTERM')`, `guard.kill(-1, 'SIGTERM')`, and `guard.kill(1001)` each throw an error containing `[test-guard]` and the PID, and `fakeKill` is never called.
   - `guard.kill(1001, 0)` and `guard.kill(4242, 'SIGTERM')` return `true` and call `fakeKill` with the same arguments; `guard.drainRefusals()` then returns `[]`.
   - Swallowed refusal fails the hook: `try { guard.kill(1001, 'SIGTERM'); } catch {}`, then `expect(() => guard.assertNoPendingRefusals()).toThrow('[test-guard]')`, and a second `assertNoPendingRefusals()` call does not throw.
   - Installer wiring with a fake target: `const target = { pid: 1001, ppid: 1000, kill: fakeKill }` and `const hooks: Array<() => void> = []`. Call `installWorkerSignalGuard(target, (h) => hooks.push(h))` twice. Assert both calls return the same guard, `hooks.length === 1`, and `try { target.kill(1001, 'SIGTERM'); } catch {}` followed by `expect(() => hooks[0]()).toThrow('[test-guard]')` (exactly one refusal named). This proves install-once and that the registered hook fails the test on a swallowed refusal.
   - Live install, safe calls only: `process[Symbol.for('overdeck.test.noWorkerSignals')]` is defined and `process.kill === thatGuard.kill`; `process.kill(process.pid, 0)` returns `true`; and a real child — spawn `process.execPath` with `['-e', 'setInterval(() => {}, 1000)']`, call `process.kill(child.pid!, 'SIGTERM')`, await its `exit` event, and assert `signal === 'SIGTERM'`. No live call sends a non-zero signal to `process.pid`, `process.ppid`, `0`, or `-1`.

## Critique response

### Guard test can kill the test runner

Accepted, and WI-2 changed. The earlier meta test sent `SIGTERM`/`SIGKILL` to `process.pid`, `process.ppid`, `0`, and `-1` in the live worker, so a missing setup entry or a broken wrapper would have killed the worker, Vitest's main process, or the process group, which is the failure this issue fixes. The refusal logic now lives in a pure factory, `createWorkerSignalGuard` in `tests/setup/worker-signal-guard.ts`, and every refusal is tested with a fake `kill` function and synthetic PIDs (1001 worker, 1000 parent). The installer, `installWorkerSignalGuard`, is tested with a fake process-like target. In the live worker the meta test only checks that the guard is installed (`process.kill` is the stored guard's `kill`), sends signal 0 to `process.pid`, and sends `SIGTERM` to a child it spawned.

### Swallowed-error test does not verify afterEach

Accepted. The meta test now calls `assertNoPendingRefusals()` after a swallowed refusal and expects it to throw `[test-guard]`. It also captures the hook that `installWorkerSignalGuard` registers through a fake `registerAfterEach`, swallows a refusal through the fake target, and asserts the captured hook throws. That proves the hook fails the test without a nested Vitest run. The one line that passes Vitest's real `afterEach` to the installer (`tests/setup/no-worker-signals.ts`) is visible in the diff.

### Unresolved after two critic rounds

- Install-once loses the afterEach hook
