# PAN-4717 — Conversation issue links: handle issues the dashboard snapshot does not hold

**Issue:** https://github.com/eltmon/overdeck/issues/4717
**Follows:** PAN-4714 (PR #4716, merged as `cb89792fca2`)
**CodeRabbit finding:** PR #4716 review comment `4435754182` on
`src/dashboard/frontend/src/components/chat/TranscriptIssueLink.tsx` —
"Do not intercept links for issues absent from the dashboard snapshot."

## Glossary

- **Dashboard snapshot / `issuesRaw`** — the issue list the frontend store holds
  (`useDashboardStore((s) => s.issuesRaw)`, `selectIssues` in
  `src/dashboard/frontend/src/lib/store.ts`). The server read model fills it from
  `IssueDataService.getIssues()` with **default options** (cycle `current`).
- **Cycle filter** — `computeIssues` in
  `src/dashboard/server/services/issue-data-service.ts` (search
  `if (cycle === 'current')`). For `current` it drops rows whose canonical status
  is `backlog` or `canceled`.
- **Aged-out closed issue** — a closed issue last updated before
  `issues.closedWindowDays` (default 14). The GitHub poll does not fetch it, so it
  is absent from the snapshot. Example on 2026-11-01: PAN-3659.
- **Cycle-filtered issue** — an issue the tracker poll holds but the cycle filter
  drops (Linear Backlog/Triage/Canceled; GitHub `backlog`/`icebox` labels or a
  closed issue with a `canceled`/`duplicate`/`wontfix` label). Example on
  2026-11-01: MIN-658 (Linear Backlog).
- **Backfill (PAN-3659)** — `IssueDataService.backfillIssue(issueId)`, fired by
  the server's `subscribeIssueEvents` handler (`src/dashboard/server/ws-rpc.ts`,
  search `getSharedIssueService().backfillIssue`). It resolves an absent issue
  through the tracker door (`resolveMissingIssue`), adds it to the snapshot, and
  the change reaches every client as an `issues.delta` event on the **global**
  domain-event stream. It returns early (no-op) when the poll already holds the
  row, even if the cycle filter drops it.
- **On-demand load** — the drawer showing an issue that was not in the snapshot
  when the drawer opened. The drawer's existing path is: `useIssueData`
  (`components/drawer/useDrawerData.ts`) subscribes `subscribeIssueEvents` for
  the id → server backfill → `issues.delta` → store → drawer re-renders.
- **Tracker button** — the "Issue" link in the drawer header
  (`components/drawer/IssueDrawer.tsx`, search `trackerIssueUrl(drawer.issueId`).
  Its URL is `trackerIssueUrl(drawer.issueId, issue?.url)`; with no issue row it
  falls back to a hardcoded GitHub prefix table (`lib/issueLinks.ts`:
  `PAN` → `eltmon/overdeck`, `KRUX` → `eltmon/krux`). Any other prefix (MIN,
  LEX, …) gets **no** tracker button when the row is absent.

## Problem

`TranscriptIssueLink` (PAN-4714) resolves a tracker URL in a conversation to an
issue ID and, on a plain left click, calls `openIssue(issueId, 'overview')`. It
never checks the snapshot. CodeRabbit flagged that a valid link to an issue the
snapshot lacks opens a drawer with the generic `Issue details` title and no
issue record, and that the drawer's GitHub tracker fallback does not cover every
registered repository.

## Investigation (done at planning time, 2026-11-01)

Live dashboard (`http://localhost:3011`), Playwright, isolated browser:

| Issue | In `GET /api/issues`? | Class | Drawer after 8 s |
| --- | --- | --- | --- |
| PAN-4299 (the issue's example) | **yes** (closed recently) | in snapshot | normal — not a repro |
| PAN-3659 | no | aged-out closed | **title loaded** via backfill, tracker button present, phase dates present |
| MIN-658 | no (present in `?cycle=all`) | cycle-filtered (Linear Backlog) | header `Issue details`, **no tracker button**, no title, ever |

`GET /api/issues` returned 1258 rows; `?cycle=all` returned 1269, so the
cycle-filtered class is small (11 rows today). Aged-out closed issues are the
common case, because conversations link old issues constantly.

So the drawer **already has an issue-fetch path** (the PAN-3659 backfill) and it
works for the dominant absent class. It fails for cycle-filtered issues and for
issues the tracker door cannot resolve (deleted, private, transient error —
`resolveMissingIssue` memoizes failures for the process lifetime). For those, the
drawer is a dead end when the prefix is not `PAN`/`KRUX`: no title and no way
to reach the tracker from the drawer.

## Decision

The issue's own rule: *"Pick the on-demand load if the drawer already has an
issue-fetch path; otherwise fall through."* The drawer has one, so:

1. **Keep intercepting** plain clicks for resolvable issues whether or not the
   snapshot holds them. The PAN-3659 backfill loads aged-out closed issues.
   CodeRabbit's literal suggestion (gate on snapshot presence) is **not**
   adopted: it would send every aged-out closed issue — the common case — back
   to a new tab, which the verified on-demand path already serves.
2. **Close the dead end** for issues the on-demand path cannot load: the link
   passes its own `href` into the drawer state, and the drawer's tracker button
   falls back to it when the issue row is absent. Every drawer opened from a
   conversation link then has a working tracker exit, for every registered
   repository and tracker. This answers CodeRabbit's second point (the fallback
   "does not cover every registered repository").
3. **No server change and no snapshot widening.** About 14 frontend views read
   `issuesRaw` (kanban, Command Deck, God View, Needs-You strip, …); pushing
   backlog/canceled rows into it to serve one drawer would change those views.

The decision must be synchronous: a click that falls through to a new tab must
not wait on a network call, or the browser treats the `window.open` as a popup.
That rules out "probe the server, then decide".

## Requirements

- **FR-1** A plain left click on a resolvable issue link in a conversation opens
  the issue drawer even when `issuesRaw` does not contain that issue.
- **FR-2** `openIssue` accepts an optional third argument `trackerUrl`; the
  drawer slice keeps it while the same issue stays open (including tab
  switches) and drops it on close, on a different `openIssue` call without it,
  and on URL sync.
- **FR-3** When the drawer's issue row is absent, the header tracker button uses
  `drawer.trackerUrl`. When the row is present, `issue.url` wins.
- **FR-4** `TranscriptIssueLink` passes the anchor's `href` as `trackerUrl`.
- **FR-5** When an `issues.delta` adds the drawer's issue to the store after the
  drawer opened, the drawer header shows the issue title (on-demand load,
  client half).
- **FR-6** Docs describe the absent-issue behaviour (backfill, tracker fallback).

  conversation, and the CodeRabbit thread on #4716 gets a reply linking this fix.
