# PAN-4970: One merge path per feature — stop the UAT batch reconciler racing the per-PR auto-merge train

**Issue:** [PAN-4970](https://github.com/eltmon/overdeck/issues/4970)
**Mode:** `pan plan --auto` (no operator Q&A; defaults recorded under "Decisions").

## Glossary

- **Per-PR auto-merge train** (also "the scheduler"): `scheduleReadyAutoMerges` in
  `src/dashboard/server/services/auto-merge-scheduler.ts`. Each tick it writes a
  `pending_auto_merges` row for every ready, gate-approved PR it may merge; the
  auto-merge executor merges that row after a 5-minute cooldown (`AUTO_MERGE_COOLDOWN_MS`).
- **`pending_auto_merges` row**: one scheduled auto-merge. Statuses: `pending`, `merging`,
  `merged`, `blocked`, `failed`, `cancelled`. Read the newest row for an issue with
  `getLatestAutoMerge(issueId)` (`src/lib/overdeck/merge-sync.ts`).
- **UAT batch reconciler** (also "the reconciler"): `reconcileUatGenerations` in
  `src/lib/cloister/uat-reconciler.ts`. Each tick it reads the project's ready set,
  invalidates stale generations, and assembles a new one.
- **Generation** / **batch**: one `uat/<codename>-<n>` branch that merges 2+ ready features
  (or one held feature) for testing. Statuses: `assembling`, `ready`, `superseded`,
  `invalidated`, `promoted`, `failed`.
- **Promote** / **Merge batch to main**: `POST /api/merge-train/generations/:name/promote`,
  which lands a `ready` or `superseded` generation on main (`promoteUatGeneration`,
  `src/lib/cloister/uat-promote.ts`; `PROMOTABLE = ['ready', 'superseded']`).
- **Held for UAT**: the three-tier policy in `shouldHoldForUat`
  (`src/lib/cloister/auto-merge-policy.ts`): the issue's `auto-merge` / `hold-for-uat` label,
  else the project's `auto_merge_default`, else the global
  `flywheel.require_uat_before_merge`. A held feature is never auto-merged.
- **Policy refusal**: `autoMergePolicyRefusal(issueId)` in
  `src/dashboard/server/routes/merge-train.ts` — the scheduler's forge-free first check
  (closed issue, held for UAT, global merge train off). It reads labels from the cached
  tracker row (`cachedIssueLabels`), never from `gh`.
- **Kill switch**: env `OVERDECK_DISABLE_AUTO_MERGE=1`; the scheduler returns `[]` at once.
- **Merge path owner**: the new rule this issue introduces. Every ready feature has exactly
  one owner: `per-pr` (the scheduler merges it) or `batch` (the reconciler may batch it).
- **Ready set**: `listReadyIssuesForProject(projectPath)`
  (`src/lib/overdeck/derived-issue-state.ts`, line ~856): open, non-draft PRs on a
  `feature/<id>` branch that the forge reports approved, green and mergeable.

## Problem (verified)

Both paths run on the same tick (`startUatTrainReconciler` in
`src/dashboard/server/services/uat-train.ts` fires `runUatTrainReconcileAllProjects()` and the
`onTick` scheduler hook, neither awaited) and both read the same ready PRs.

- The scheduler refuses held features (`autoMergePolicyRefusal` → 412 "UAT is still required
  before merge"), so it already leaves held features alone.
- The reconciler does **not** partition. `listReadyIssuesForProject` keeps every approved,
  green, mergeable PR (its own comment says "this is the UAT train's candidate set, which is
  mostly issues held for UAT"), and `reconcileUatGenerations` batches all of them.

For the Overdeck project, the live settings are `flywheel.require_uat_before_merge = false`,
`flywheel.merge_train_enabled = true`, and no `auto_merge_default` in `projects.yaml`
(`panopticon-cli` entry). So no Overdeck issue is held, the scheduler owns every ready PR, and
the reconciler still batches them. Every scheduler merge removes a member from the ready set,
`isStale` reports `"<id> left the ready queue"`, and the batch is invalidated. The dashboard log
for 2026-11-03 shows the cycle (`uat/pan-perch-1103-25` .. `-30`: assemble → schedule →
`invalidating …: PAN-4838 left the ready queue` → reassemble).

The **Merge batch to main** click on an invalidated generation returned 409 `wrong-status`.
The server first runs `evaluateIssueMergeGate` + `getDerivedIssueState` for every member
(forge reads, `uat-train.ts` `postUatGenerationPromotePayload`, the `memberStates` loop at line
~829) **before** `promoteUatGeneration` checks the status, so the refusal is slow. The
frontend `promoteMutation.onError` (`MergeTrainView.tsx` line ~360) calls `toast.error` and
`invalidate()`. That code path looks correct, but no test exercises a non-2xx promote, and the
operator reported seeing no message on the first click. That report is not reproduced; the
plan makes the refusal fast, the message explicit, and the card disappear at once, and proves
it with a test.

## Decisions

1. **Partition by policy first, `pending_auto_merges` state second.** A state-only exclusion
   ("skip members with a pending row") still assembles on tick N and invalidates on tick N+1,
   because the two passes are unordered. The policy rule is deterministic. The pending-row
   check stays as a second guard: it covers a feature that was scheduled and then labelled
   `hold-for-uat`, and a project where the policy guess is wrong.
2. **The owner rule** (decision order, first match wins; revised after the plan critique):
   1. Kill switch `OVERDECK_DISABLE_AUTO_MERGE=1` ⇒ `batch`. The auto-merge executor does not
      start under the kill switch (`startAutoMergeExecutor`), so even a `pending` row cannot merge.
   2. `autoMergePolicyRefusal(issueId)` returns a refusal ⇒ `batch` (held for UAT, closed, or
      global merge train off). The scheduler skips these, and the executor blocks (held, closed)
      or pauses (train off) any row that already exists.
   3. `deftAutoMergeHold(issueId)` returns a reason ⇒ `batch` (scheduler skips; executor blocks).
   4. Newest `pending_auto_merges` row is `pending` or `merging` ⇒ `per-pr`. It runs before the
      project rules, so a row an operator scheduled in a GitLab or polyrepo project still counts.
   5. Project forge is GitLab (`forgeForProject(projectPath) === 'gitlab'`) ⇒ `batch` (the
      scheduler skips GitLab projects).
   6. Project `workspace.type === 'polyrepo'` ⇒ `batch` (the scheduler lists PRs with `gh` in
      the project path; a polyrepo wrapper path yields no PRs, so it never schedules them).
   7. Newest row is `cancelled` ⇒ `batch` (the scheduler never re-schedules a cancel).
   8. Newest row is `failed` or `blocked` ⇒ `per-pr` only when
      `latestAutoMergeAllowsSchedule(row, pr)` (exported from `auto-merge-scheduler.ts`) is true
      for the feature's current PR (`{ url, headSha }`), else `batch`. A failed merge at the same
      head is never re-armed by the scheduler, so it must stay batchable; a new head re-arms it.
      The current PR comes from the cached `listRepoPullRequests(projectPath)` listing (the open
      row whose `headRefName` is `feature/<id>`: `url`, `headRefOid`), so this costs no new
      forge read.
   9. Otherwise (no row, or `merged`) ⇒ `per-pr`.
   Rules 1, 5 and 6 together are "the per-PR train is active for the project"
   (`perPrTrainActiveForProject`). The order mirrors the scheduler's and the executor's own
   skips, so the two paths cannot both claim one feature, and no ready feature is left with no
   path.

   **Handoff of an existing row (no row writes).** The reconciler never cancels, suspends or
   otherwise writes `pending_auto_merges`; only the schedule and cancel doors do. Ownership is
   recomputed every tick from current state, so the transitions are:
   - kill switch turned on with a `pending` row ⇒ `batch` at once (the executor is stopped); when
     the switch is turned off again the row fires, and the next reconcile invalidates the one
     batch holding that member (`… merges through the per-PR auto-merge train`). One
     invalidation per operator toggle, not a loop.
   - a `pending` row whose issue becomes held ⇒ `batch` at once; the executor blocks that row on
     its next tick (`isAutoMergeEligible` → "held for UAT"), so the row can no longer merge the
     member out from under the batch.
3. **Labels come from the cached tracker row**, through `autoMergePolicyRefusal`, not from
   `gh issue view`. Running `issueHoldsForUat` (one `gh` call per issue) for every ready
   feature every 60 s would cost N forge reads per project per tick, and a fresh read could
   disagree with the scheduler's cached read inside one tick.
4. **The reconciler takes ownership as an injected dep** (`mergesPerPr`), so the lib module
   stays pure and the unit test needs no database.
5. **Force does not override ownership.** `POST /api/merge-train/assemble` (forced rebuild)
   still drops per-PR features: force bypasses backoff and the live-match check, not policy.
6. **Keep the Merge batch button for `superseded`.** The issue asks that the button render only
   for `ready`, but `PROMOTABLE` deliberately includes `superseded` ("older subset still
   testable and promotable"). The button already never renders for `invalidated`, `failed` or
   `assembling` (`visibleGenerationsOf` filters them). The real defect is a stale card, which
   item 7 fixes.
7. **Fast refusal on the server.** The promote payload checks the generation's status before
   any forge read, through one exported helper shared with `promoteUatGeneration`.
8. **The scheduler is not changed.** It already refuses every feature the owner rule assigns to
   `batch` (the rules mirror its own skips and the executor's blocks). A feature in a live batch that gains the `auto-merge`
   label is scheduled (operator's explicit choice) and its batch is invalidated once; that is
   accepted.
9. **One-time invalidation after deploy.** The first tick after the fix invalidates any live
   Overdeck generation whose members are now `per-pr`. That is expected.
10. **Page copy must not promise a batch that will never come.** The queues payload carries a
    per-item `mergesPerPr` flag, and the section line says those features merge one at a time.

## Requirements

- **FR-1** — A shared owner function decides `per-pr` vs `batch` for one ready feature using
  exactly the rule in Decision 2.
- **FR-2** — The reconciler removes every `per-pr` feature from its ready set before stale
  checks and assembly, on normal and forced ticks.
- **FR-3** — A live generation whose member became `per-pr` is invalidated with the reason
  `"<ID> merges through the per-PR auto-merge train"`.
- **FR-4** — When every ready feature of a project is `per-pr`, no generation is assembled
  (`action: 'idle'`).
- **FR-5** — Both reconciler wirings in `uat-train.ts` (monorepo and polyrepo) pass the owner
  function.
- **FR-6** — Promoting a generation that is not `ready`/`superseded` returns 409
  `wrong-status` (404 `not-found` for an unknown name) without any merge-gate or forge read.
- **FR-7** — A failed promote shows a toast that names the batch and the server reason, removes
  that card from the page at once when the reason is `wrong-status` or `not-found`, and
  refetches.
- **FR-8** — `GET /api/merge-train/queues` marks each queue item with `mergesPerPr: boolean`.
- **FR-9** — When every ready feature is `per-pr` and no batch is live, the section line says
  they merge one at a time through auto-merge and no **Retry batch assembly** button renders.
- **FR-10** — Docs describe the one-owner rule in the three pages named in item 9.
- **NFR-1** — No new forge read per ready feature per tick (labels from the cached tracker row).
- **NFR-2** — `src/dashboard/frontend/src/components/merge-train/MergeTrainView.tsx` stays at or
  under 1000 lines (`scripts/lint-file-size.sh` `CEILING=1000`; it is exactly 1000 on main).

### Item 1 — `owner-rule`: the merge path owner function (FR-1, NFR-1)

**New file:** `src/dashboard/server/services/merge-path-owner.ts`.

```ts
/**
 * One owner per ready feature (PAN-4970). The per-PR auto-merge train
 * (auto-merge-scheduler.ts) and the UAT batch reconciler (uat-reconciler.ts)
 * both read the same ready PRs; a feature both of them claim is batched, then
 * merged on its own, which invalidates the batch. This module answers which
 * path owns a feature, mirroring the scheduler's own skip order.
 */
import type { ProjectConfig } from '../../../lib/projects.js';
import type { PendingAutoMerge } from '../../../lib/overdeck/merge-sync.js';

export type MergePathOwner = 'per-pr' | 'batch';

export interface MergePathOwnerDeps {
  env?: NodeJS.ProcessEnv;
  forgeOf?: (projectPath: string) => 'github' | 'gitlab';
  latestAutoMerge?: (issueId: string) => PendingAutoMerge | null;
  policyRefusal?: (issueId: string) => { status: number; body: { error: string } } | null;
  deftHold?: (issueId: string) => Promise<string | null>;
}

/** Rules 1, 5, 6: whether the per-PR train runs for this project at all. mergePathOwner calls it. */
export async function perPrTrainActiveForProject(
  projectPath: string,
  config: Pick<ProjectConfig, 'workspace'> | null | undefined,
  deps: Pick<MergePathOwnerDeps, 'env' | 'forgeOf'> = {},
): Promise<boolean>;

/** Rules 1–9 for one feature. */
export async function mergePathOwner(
  issueId: string,
  projectPath: string,
  config: Pick<ProjectConfig, 'workspace'> | null | undefined,
  deps: MergePathOwnerDeps = {},
): Promise<MergePathOwner>;
```

Defaults (dynamic imports, matching `auto-merge-scheduler.ts`):
- `env` → `process.env`; kill switch is `env.OVERDECK_DISABLE_AUTO_MERGE === '1'`.
- `forgeOf` → `forgeForProject` from `./derived-issue-state.js`.
- `latestAutoMerge` → `getLatestAutoMerge` from `../../../lib/overdeck/merge-sync.js`
  (upper-case the issue id before the call).
- `policyRefusal` → `autoMergePolicyRefusal` from `../routes/merge-train.js` (dynamic import).
- `deftHold` → `deftAutoMergeHold` from `../../../lib/deft/policy.js`.

Order is exactly Decision 2 (rules 1–9). Polyrepo is `config?.workspace?.type === 'polyrepo'`.
Add one more injected dep, `prOf?: (projectPath: string, issueId: string) => Promise<{ url?: string; headSha?: string | null } | null>`,
defaulting to a lookup in the cached `listRepoPullRequests(projectPath)` (from
`./derived-issue-state.js`): the open row whose `headRefName` equals `feature/<issue id lower-cased>`,
returning `{ url: row.url, headSha: row.headRefOid }`; `null` when absent. Rule 8 passes
`{ url: pr?.url, headSha: pr?.headSha ?? undefined }` to `latestAutoMergeAllowsSchedule`
(static import from `./auto-merge-scheduler.js`; it imports nothing back).

**Tests:** new `src/dashboard/server/services/__tests__/merge-path-owner.test.ts`, all deps
injected, no database:
- `pending` / `merging` row, GitHub monorepo, not held ⇒ `per-pr`; the same row in a GitLab or
  polyrepo project ⇒ `per-pr`.
- transition: `pending` row with the kill switch on ⇒ `batch`; the same row with the switch
  off ⇒ `per-pr`.
- transition: `pending` row, `policyRefusal` returns 412 (newly held) ⇒ `batch`; `deftHold`

- no row: kill switch on ⇒ `batch`; `gitlab` ⇒ `batch`; polyrepo ⇒ `batch`.
- newest row `cancelled` ⇒ `batch`; `merged` or none ⇒ `per-pr`.
- `failed` row: same head as `prOf` ⇒ `batch`; changed head ⇒ `per-pr`; row without `headSha`
  ⇒ `batch`. `blocked` row at the same head ⇒ `per-pr` (the scheduler re-arms it).
- `perPrTrainActiveForProject` is true for a GitHub monorepo with the kill switch off and false
  for each of the three exceptions.

## Critique response

### A pending row can have no running per-PR path

Accepted. Decision 2 is reordered: the kill switch (rule 1), the policy refusal (rule 2, which
includes the UAT hold) and the Deft hold (rule 3) now win over a `pending`/`merging` row (rule
4). Under the kill switch the executor is not running, so the feature is batch-owned at once;
a newly held feature is batch-owned at once and the executor blocks its row on the next tick.
The reconciler never writes `pending_auto_merges` (scheduling stays behind the schedule and
cancel doors, a TENET-10 boundary); the "Handoff of an existing row" paragraph under Decision 2
states the two transitions and their bounded cost (one batch invalidation per operator toggle).
Item 1's tests cover both transitions.

### Failed auto-merge at the same head is assigned to a path that cannot schedule it

Accepted. Rule 8 assigns a `failed` or `blocked` row to `per-pr` only when
`latestAutoMergeAllowsSchedule(row, currentPr)` — the scheduler's exact re-arm decision — is
true. The current PR's URL and head come from the cached `gh pr list` listing through a new
`prOf` dep, so no forge read is added. Item 1 tests same-head `failed` (batch), changed-head
`failed` (per-pr), headless legacy `failed` (batch) and same-head `blocked` (per-pr).

### The specified rejection handler misses synchronous throws

Accepted. Item 2 now prescribes `try { … await deps.mergesPerPr?.(feature) … } catch { false }`
and tests both a synchronous throw and a rejected promise; the tick completes and the feature is
batch-owned.

### The documentation says only held features batch while auto-merge is on (sharpens-framing)

Accepted. Item 9's text for `configuration/auto-merge.mdx`, `docs/MERGE-WORKFLOW.md` and
`features/merge-batches.mdx` now lists every batch-owned case in the owner rule.

### Unresolved after two critic rounds

- Mixed queues still offer an assembly that cannot happen
- One owner lookup failure hides the whole project queue
