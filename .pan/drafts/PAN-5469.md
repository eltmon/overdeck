## Glossary

- **Planning**: the step before work on an issue. A planning agent reads the issue and the code, writes a PRD, lowers it into an xBRIEF plan, and finalizes it. Nothing is implemented during planning.
- **Planning agent**: the agent that runs the `plan` role. Its session is named `planning-<issue-lowercase>` (for example `planning-pan-5469`).
- **PRD**: product requirements document, a markdown brief at `.pan/drafts/<issue>.md` in the project repo. In Overdeck the PRD carries the implementation detail (files, before/after code, work items), because a model executes it.
- **xBRIEF**: the JSON plan format Overdeck uses (spec: https://github.com/deftai/xBRIEF, current version 0.8). The old name is vBRIEF.
- **Spec**: the canonical xBRIEF file for an issue, `.pan/specs/<YYYY-MM-DD>-<ISSUE>-<slug>.xbrief.json`.
- **Item**: one task in the xBRIEF checklist (`plan.items[]`). An item has nested **acceptance criteria** (ACs), child items with `metadata.kind: "acceptance_criterion"` and ids like `<item>.ac1`.
- **Edge**: a dependency between two items (`plan.edges[]`). Only `blocks` edges order the work.
- **Continue file**: `.pan/continues/<issue-lowercase>.xbrief.json`, where `pan task` records item status. The spec itself does not change during work.
- **Finalize**: `pan plan finalize`, the command that checks the plan and hands it to the pipeline.
- **Plan critic**: an optional read-only worker on a model from a different family that critiques a flagged plan before it can finalize.
- **Plan integrity**: the required `plan-integrity` verification check that fails a branch whose plan items or ACs changed after finalize.
- **Mintlify**: the docs site generator. Pages are `.mdx` files at the repo root (`features/`, `configuration/`, `cli/`, `reference/`); navigation lives in `docs.json`.

## Fact sheet (verified 2026-11-17 against v0.88.0 source)

Use these facts. Each one names its source so a reviewer can check it.

### Starting planning

- F-1. `pan plan <id>` starts a planning session through the dashboard (`POST /api/issues/<id>/start-planning`, `src/cli/commands/plan.ts`). The dashboard must be running. Options (`pan plan --help`): `--auto` (non-interactive; inferred choices are recorded in `plan.autoDecisions[]`), `--probe` (adds an adversarial pre-finalize probe pass to the prompt), `--model <model>`, `--harness <harness>`, `--effort <level>` (`low | medium | high | xhigh | max`), `--remote` / `--local` (Fly.io or local planning workspace). `--auto-start` is deprecated: use `pan start <id>`.
- F-2. In `--auto` mode the planning agent asks no questions. It picks the most defensible default, records each one in `plan.autoDecisions[]` as `{ summary, rationale }`, and stops only for a real contradiction between the issue and a linked PRD (`src/lib/planning/spawn-planning-session.ts`, search `## Auto Planning Mode`).
- F-3. The probe pass is added when `--probe` is passed or when the planning effort is `high` or above (`spawn-planning-session.ts`, search `const deepEffort`). Probe findings go in `continue.json` `decisions[]` with the prefix `PROBE:`.
- F-4. `pan start <id>` plans first if the issue has no plan. `--plan <mode>` picks the depth: `interactive`, `auto` or `skip`. Precedence: `--plan` flag, then the deprecated `--auto` flag (means `skip`), then `planning.default_mode` in `~/.overdeck/config.yaml`, then the shipped default `auto` (`src/cli/commands/planning-mode.ts`, `resolvePlanningMode`). An invalid value fails with an error naming the three valid values. `--plan-model <model>` overrides the planning model for that start; `--model` stays the work model.
- F-5. `--plan skip` (and the deprecated `pan start --auto`) skips the planning agent and synthesizes a minimal one-item spec from the issue title and body into the issue workspace's `.pan/specs/` (docs/XBRIEF.md, PRD → Spec Lifecycle step 4; `src/lib/xbrief/auto-synthesize.ts`).
- F-6. Planning effort resolves with role `plan`: `roles.plan.effort`, then the project, then `high` (configuration/effort.mdx, "Planning" bullet). The Plan dialog defaults to `high` and offers all five levels (changelog v0.65.0, #4518).
- F-7. Starting a planning session adds the GitHub label `planning`; completing planning adds `planned` (docs/XBRIEF.md step 3, PAN-3953).

### Artifacts and where they live

- F-15. Planning artifacts live under `.pan/` in the project repo (or the plan-home repo for polyrepo projects that set `pan_records.repo`), committed on the issue's feature branch: `.pan/drafts/<issue>.md` (PRD), `.pan/specs/<YYYY-MM-DD>-<ISSUE>-<slug>.xbrief.json` (spec), `.pan/continues/<issue>.xbrief.json` (item status) (docs/XBRIEF.md, "Canonical plan state").
- F-16. The planning agent writes its working copy in the workspace: `.overdeck/spec.vbrief.json` (spec draft) and `.overdeck/continue.json` (decisions, hazards, git state). Workspace `.overdeck/` files are local and gitignored (docs/XBRIEF.md, "Workspace runtime state"; `roles/plan.md`).
- F-17. Spec filenames never change after creation: date (UTC creation date), issue id, slug from the plan title (docs/XBRIEF.md, "Issue-Keyed Filenames").
- F-18. Status is a JSON field; files never move between directories. The lifecycle is `draft → proposed → active → completed`, with `cancelled` reachable from `proposed` and `active` (docs/XBRIEF.md, "Status Transitions"). `pan start` sets the spec's top-level `status` to `active` and `plan.status` to `running` (`src/cli/commands/start-status.ts`).
- F-19. Legacy `vBRIEFInfo` envelopes and `*.vbrief.json` files stay readable; new writers emit `xBRIEFInfo` and `.xbrief.json`. Readers accept xBRIEF 0.5 through 0.8 (docs/XBRIEF.md, "Migration from vBRIEF"; docs/VBRIEF.md is only a redirect).

### The xBRIEF checklist

- F-20. A spec has exactly two top-level keys, `xBRIEFInfo` and `plan`. `plan.id` is the lowercase issue id. `plan.items[]` is the checklist; each item has `id`, `title`, `status`, optional `narrative.Action`, `metadata`, and nested AC items. `plan.edges[]` holds `{ from, to, type }` with type `blocks`, `informs`, `invalidates` or `suggests`; only `blocks` orders the work (docs/XBRIEF.md, "Required Format", "Edges").
- F-21. `plan.narratives` holds `Problem`, `Proposal` and `NonGoals`. Review treats NonGoals as must-not constraints (docs/XBRIEF.md, Field Reference).
- F-22. Overdeck item metadata (docs/XBRIEF.md, "Overdeck Extensions"): `difficulty`, `kind` (`docs | api | backend | frontend | infra | test | refactor | design | spike`), `files_scope`, `files_scope_confidence`, `verify_commands`, `expected_outputs`, `readiness` (`ready | sequential | needs_refinement`), `traces` (PRD requirement ids), `requiresInspection`, `inspectionDepth`, `foundationFor`.
- F-23. The verification gate requires every AC (child item with `metadata.kind: "acceptance_criterion"`) to be `completed` before review (docs/XBRIEF.md, "How Overdeck Uses xBRIEF" step 6).
- F-24. The dashboard shows a plan in the xBRIEF viewer. Entry points: the `xBRIEF` button on a Kanban card (opens "xBRIEF Plan: <ISSUE>"), the issue's `Plan` tab (sub-views `Map` and `PRD`; Map shows the dependency graph), the `xBRIEF` resource icon on a project-tree issue row, and the `⛶` "Expand xBRIEF full screen" button. Views: `List`, `DAG` and a raw JSON view, labeled `Raw JSON` in the tabbed viewer and `Raw` in the full-screen viewer (`components/xbrief/XBriefViewer.tsx`, `XBriefFullscreen.tsx`). The page should say "List, DAG and raw JSON views" and not quote a single raw label.

### `pan task`

- F-25. `pan task` reads and updates item state for one issue (`pan task --help`). Verbs: `next <issue>`, `show <issue> <item>`, `claim <issue> <item>`, `done <issue> <items...>`, `block <issue> <item>`, `unblock`, `reopen`, `cancel`. Every verb takes `--json`.
- F-26. The loop: `pan task next`, `pan task claim <item>`, implement and push, `pan task done <item>`. `pan task done` checks that a pushed commit carries the trailer `Item: <id>` for every id; if any id lacks one, nothing is written. It takes several ids at once and records them in one continue commit, for example `pan task done PAN-123 my-item my-item.ac1 my-item.ac2` (docs/XBRIEF.md, "Task state and concurrency"; `pan task done --help`).
- F-27. `pan task claim` refuses (exit 1, nothing written) when a running agent holds the item, or holds another item whose `files_scope` overlaps it. A low-confidence `files_scope` on either side counts as overlap. `--steal` overrides both refusals; it is a foreman or operator override, and a worker should never pass it (docs/XBRIEF.md; changelog v0.64.0 #4357).
- F-28. `pan task block <issue> <item> --on <refs...>` records which issues or PRs must merge first (an issue id, `#N`, `owner/repo#N` or a PR URL). Within about two minutes of the last one merging, the dashboard sends the work agent one `BLOCKERS MERGED` message, or raises Needs you once if the agent cannot be reached. `OVERDECK_DISABLE_BLOCKER_WAKE=1` turns it off (changelog v0.65.0 #4452).

### `pan scope`

- F-29. `pan scope list`, `show <issueId>`, `propose`, `approve`, `complete`, `cancel`, `restore` are manual lifecycle overrides. They rewrite the status fields of the spec in place (`src/lib/xbrief/lifecycle-io.ts`, `transitionIssueXBrief` and `updateSpecStatusSync`): `propose` → `proposed`; `approve` → lifecycle `active`, `plan.status` `approved`; `complete` → `completed`; `cancel` → `cancelled`; `restore` → `active`/`approved`, only from completed or cancelled. They write the workspace spec while the workspace exists, and commit and push on `main` only once it is gone (docs/XBRIEF.md, "Status Transitions"; changelog v0.64.0 #4377). `restore` refuses for a merged issue.
- F-30. Note for the writer: `pan scope --help` still says "Move xBRIEF to proposed/" and similar. That text is stale; the code rewrites fields and never moves files. Document the code's behavior. A follow-up issue fixes the help text (see Non-goals).

### `pan plan finalize`

- F-31. `pan plan finalize` runs from the workspace (`-w, --workspace <path>` to override). In order: PRD-first gate, xBRIEF quality lint, plan critique (flagged plans only), then it sets `plan.status: "proposed"` and calls the dashboard's complete-planning endpoint, which promotes the spec into `.pan/specs/` on the feature branch, transitions the issue to Planned and ends the planning session (`src/cli/commands/plan-finalize.ts`; `roles/plan.md`).
- F-32. PRD-first gate: finalize refuses without a PRD draft at `.pan/drafts/<ISSUE>.md` of at least 20 lines (`MIN_PRD_LINES = 20`, `src/lib/pan-dir/drafts.ts`). Exit code 4. `--no-prd` bypasses it for a genuinely trivial issue and prints `⚠ PRD gate SKIPPED (--no-prd)`. Finalize never overwrites an existing canonical draft.
- F-33. Quality lint: finalize lints the plan and exits 3 on any error (`lintPlanQuality`, `src/lib/xbrief/quality-lint.ts`). Checks include: each AC must name observable behavior; required item metadata; plans over 25 distinct `files_scope` files or 6 subsystems fail unless `plan.metadata.sizeJustification` is set (`projected-surface`); at least one docs item (`kind: "docs"` or a `.md`/`.mdx`/`docs/` path in `files_scope`) unless `plan.metadata.docsJustification` is set (`docs-item-missing`). `--no-quality-lint` is a one-run emergency bypass.
- F-34. With the Jev acceptance-criteria toggle on, finalize also prints advisory warnings (`ac-semantic-not-observable`, `ac-semantic-compound`). They never change the exit code (docs/XBRIEF.md, "Advisory semantic AC review"; configuration/jev.mdx).
- F-35. `--no-promote` stops after marking the spec `proposed`. Promote it later with `pan plan done <id>` or the dashboard Done button. `pan plan done <id>` takes `--no-prd`.
- F-36. If the dashboard cannot complete promotion, finalize writes a pending-promotion marker and the deacon completes promotion once the dashboard is healthy; the manual fallback is `pan plan done <id>` (`plan-finalize.ts`, search `Promotion deferred`).
- F-37. After promotion, whether a work agent starts depends on how planning began. By default the issue waits in Planned, and the dashboard shows "The plan is ready" with a `Start work` action (`src/dashboard/frontend/src/lib/simple/userFacingState.ts`, `planning_done_awaiting_work`); start it with `pan start <id>` or the dashboard. Work starts automatically when planning was started with the Plan dialog's `Start work as soon as the plan is ready` checkbox, or with `pan start <id>` on an unplanned issue (which plans, then starts work). `pan plan --auto-start` does the same but is deprecated (`roles/plan.md`, "Process" step 7; `plan-finalize.ts` messages).
- F-38. The finalize commit carries a `Plan-Finalized: <sha256>` trailer, the SHA-256 of the spec's bytes (docs/PIPELINE-GATES.md, "Plan-integrity gate").

### Plan critic

- F-39. A plan is flagged for critique when its issue has the label `architecture`, `substrate-improvement` or `security` (`CRITIC_LABELS`, `src/lib/planning/plan-critique.ts`), or when you run `pan plan finalize --critic`. If labels cannot be read, finalize warns and treats the plan as unflagged (`isPlanFlagged`, `plan-critique-io.ts`).
- F-40. The critic model comes only from `roles.plan.sub.critic.model` in `~/.overdeck/config.yaml`. It has no default. It must be from a different model family than the planner; a same-family or missing setting refuses finalize with a message naming the setting (`src/lib/planning/plan-critic-model.ts`).
- F-41. Finalize dispatches one read-only worker (`plan-critic-r<N>`) with `roles/plan-critic.md` and waits up to 9 minutes. It writes `.pan/drafts/<stem>-critique.md` (round 2: `<stem>-critique-2.md`). Findings are headings `## blocks-the-design: <title>`, `## sharpens-framing: <title>` or `## footnote: <title>` (docs/XBRIEF.md step 2).
- F-42. Each `blocks-the-design` finding needs an answer: a `### <title>` heading under `## Critique response` in the PRD. A refusal exits 5. Changing the draft makes the critique stale and starts the next round. After two rounds finalize proceeds and lists unanswered titles under `### Unresolved after two critic rounds` in the PRD. Never edit the critique file to pass. The Done button and `pan plan done` return 422 when a required critique is missing or unanswered and never start a critic (docs/XBRIEF.md step 2; changelog v0.64.0 #4382).

### Plan integrity and plan freshness

- F-43. A finalized plan cannot be changed by the work agent. The required `plan-integrity` verification check compares the spec at HEAD with the finalized reference and fails on any added, removed or changed item or AC, or a changed narrative or edge. Status fields (`status`, `plan.status`, `plan.updated`, `plan.sequence`, `xBRIEFInfo.updated`) may change. The failure message gives the exact `git restore --source=<sha> ...` fix (docs/PIPELINE-GATES.md, "Plan-integrity gate"; changelog v0.64.0 #4355).
- F-44. To change a plan, return the issue to planning and re-finalize: keep stable item ids, fix the draft, re-run finalize; it rewrites the same canonical filename and existing continue-file state still applies (docs/XBRIEF.md step 5, "Active plan repair").
- F-45. Plan-freshness preflight: before spawning, `pan start` refuses when an item's `files_scope` names a file that a commit on HEAD deleted after the plan was written. `--skip-freshness` bypasses it (`src/lib/xbrief/freshness.ts`; `pan start --help`).

### When to skip planning

- F-46. Skip planning (`pan start <id> --plan skip`) only for small, obvious changes: the synthesized one-item spec has no PRD, no checklist detail, and no critic. Use `--plan auto` when the issue is clear but not trivial, and `--plan interactive` when the scope needs your decisions. Set the default with `planning.default_mode`. This is guidance, not code; keep it short.
