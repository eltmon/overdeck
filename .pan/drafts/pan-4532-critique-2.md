## blocks-the-design: The second restart can strand review

The PRD says a second restart after consumption leaves a `review.requested` tail that `recoverStalledReviews` re-requests. Boot adoption appends `review.requested` before verification resumes (`src/dashboard/server/routes/workspaces/review-pipeline.ts:261-280`), and the supervisor marks the finished result consumed before push and dispatch (`src/lib/cloister/verification-worker-supervisor.ts:206-214`). If the dashboard restarts in that interval, boot adoption excludes the consumed result (`verification-worker-supervisor.ts:142`), while `recoverUndispatchedReviews` ignores the `review.requested` tail (`undispatched-review-recovery.ts:85`). `recoverStalledReviews` recognizes that tail, but with no review parent it asks `getRequestReviewStarter()` and skips when it is null (`deacon-lite.ts:470-479`). That registry is populated only by the dashboard review route (`routes/workspaces/review-pipeline.ts:348`); the patrol runs in a separate child (`dashboard/server/services/deacon-supervisor.ts:117-120`, `dashboard/server/deacon-main.ts:5-10`), and its entry does not register the route. The PRD's claimed fallback therefore cannot run in production for this case. Use the existing `requestReviewThroughRoute` HTTP path for the missing-parent fallback, as `recoverUndispatchedReviews` already does (`undispatched-review-recovery.ts:131-135`), and test recovery from a `review.requested` tail in the child-process arrangement.

## blocks-the-design: A waiter can leave its result reusable

FR-3 requires one consumer, but `waitForResult` ignores a failed `markResultConsumed` write and still returns the result (`src/lib/cloister/verification-worker-supervisor.ts:206-214`). The request-review pipeline then pushes and dispatches on a passed result (`src/lib/cloister/request-review-pipeline.ts:29-47`). After a transient write failure, `resultConsumedAt` is still absent, so a later boot lists the finished worker (`verification-worker-supervisor.ts:142-145`) and a successful write in `adoptUnconsumedResult` returns the same result again (`verification-worker-supervisor.ts:268-274`). The new test covers only a write failure in the adoption path (`verification-worker-supervisor-join.test.ts:284-290`), not this waiter path. Make the waiter fail closed when its consumption write fails, and add a test where that write fails once, recovers, and a later request or boot cannot use a result already handed to a continuation.
