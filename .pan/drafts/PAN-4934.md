# PAN-4934 — ACP harnesses (`acp`, `opencode`): inject the `overdeck` MCP server (W-INJ3)

**Status:** planned (`pan plan --auto`) · **Revision:** 1 (2026-11-04) · **Author:** Claude Opus 5.5 (planning agent)
**Issue:** [PAN-4934](https://github.com/eltmon/overdeck/issues/4934) · **Epic:** [PAN-4927](https://github.com/eltmon/overdeck/issues/4927), PRD `.pan/drafts/pan-4927.md`, work item **W-INJ3**
**Depends on (merged on `main`):** W-INJ1 = [PAN-4932](https://github.com/eltmon/overdeck/issues/4932) (`b4b96c624b0`), which builds on W-TOK1 = PAN-4930 (`99f28c3e222`) and W-MCP1 = PAN-4931 (`8bdce46e72a`).
**Sibling in flight:** W-INJ2 = [PAN-4933](https://github.com/eltmon/overdeck/issues/4933) (Codex), not yet planned. It edits some of the same lines (see H-1).

Every agent Overdeck launches on the two ACP harnesses — `acp` (Kimi Code CLI over ACP) and `opencode` (OpenCode over ACP) — starts with the MCP server named `overdeck`, exactly as Claude Code agents do since PAN-4932. The ACP host already sends an `mcpServers` field in `session/new` and `session/load`, but the field is always empty. This issue fills it from the same `overdeck-mcp.json` file W-INJ1 writes.

## Glossary

- **ACP (Agent Client Protocol):** the JSON-RPC protocol between Overdeck's ACP host and an ACP agent process (`kimi acp`, `opencode acp`). `session/new` starts a session; `session/load` resumes one. Both carry `mcpServers: McpServer[]`.
- **ACP host:** `src/lib/acp/host.ts`, bundled as `dist/acp-host.js` (`tsdown.config.ts:18`). The launcher runs it as `node <root>/dist/acp-host.js --agent … --provider … --workspace … --binary-path …`. It spawns the ACP agent and drives the session.
- **ACP provider:** the `--provider` value: `kimi`, `opencode` or `opencode-go` (`ACP_PROVIDER_SUPPORT`, `src/lib/acp/providers.ts:22-31`). `opencode` and `opencode-go` share one support object and one binary.
- **ACP harness:** the `RuntimeName` of an ACP launch: `acp` (provider `kimi`) or `opencode` (providers `opencode`, `opencode-go`). Both have `launchCommandKind === 'acp-host'`. `getAcpLauncherFields` derives the harness from the model prefix (`src/lib/agents/runtime-command.ts:140`).
- **ACP stdio server entry:** the `McpServerStdio` member of the ACP `McpServer` union: `{ name, command, args: string[], env: { name, value }[] }` with **no** `type` field (`packages/effect-acp/src/_generated/schema.gen.ts:1004-1010`, `:7112-7118`).
- **Overdeck MCP config:** `<dir>/overdeck-mcp.json` (mode 0600), written by `writeClaudeOverdeckMcpConfig` (`src/lib/mcp/agent-injection.ts:55-69`). Claude Code's `--mcp-config` format: `{ "mcpServers": { "overdeck": { "type": "stdio", "command", "args", "env": { KEY: value } } } }`. It names the token file, never the token. "Claude" in the helper names refers to this file format.
- **Token file:** `<dir>/mcp-token` (mode 0600), the agent token minted by `ensureAgentMcpToken` (W-TOK1).
- **Launch kind:** `getHarnessBehavior(harness).launchCommandKind`, the adapter selector the launcher switches on. Comparing it is not a harness-name comparison.
- **`overdeckMcp` capability:** `HarnessCapabilities.overdeckMcp` (`packages/contracts/src/harness-capabilities.ts:69-70`). `harnessGetsOverdeckMcp` reads it (`agent-injection.ts:28-31`).
- **CP-3:** epic implementation checkpoint "ACP providers accept stdio `mcpServers`" (epic PRD, "Implementation checkpoints").

## Requirements

### Functional

- **FR-1** The ACP host accepts `--mcp-config <path>`. It reads that file and sends every stdio server in it, converted to the ACP stdio shape, in `session/new` and in `session/load`.
- **FR-2** `buildAcpCommand` emits `--mcp-config <quoted path>` when `overdeckMcpConfig` is set, and nothing when it is not.
- **FR-3** `prepareClaudeOverdeckMcp` writes the Overdeck MCP config for `acp-host` launches as it does for `claude-code` launches. `ACP_CAPABILITIES` and `OPENCODE_CAPABILITIES` declare `overdeckMcp: true`. Result: every work agent, role run, planning session, recovered agent and conversation on `acp` or `opencode` starts with the `overdeck` server (traces epic FR-1, AC-5).
- **FR-4** CP-3 is run end to end and its result is recorded. A harness whose agent cannot list the `overdeck` tools is set back to `overdeckMcp: false` (C-4).
- **FR-5** The docs name `acp` and `opencode` as injected harnesses and record the CP-3 result (traces epic FR-16).

### Non-functional

- **NFR-1 No token outside the token file.** The launcher, the host argv, the MCP config and the ACP `session/new` / `session/load` payloads carry only paths and the loopback URL. Stdio only: the ACP `http` transport would put the token in a header inside the ACP payload, which protocol capture (`OVERDECK_PROTOCOL_CAPTURE_DIR`) and the agents' own logs record (epic NFR-2).
- **NFR-2 Async only.** The host reads the file with `readFile` from `node:fs/promises`. No `*Sync` call, no new `*Sync` function (repo rules `no-execsync-server`, `prefer-async`).
- **NFR-3 File size.** `launcher-generator.ts` stays ≤ 1,000 lines (994 today); `host.ts` grows by ≤ 6 lines; `agent-injection.ts` by ≤ 4; the new module stays under 80 lines. `npm run lint:file-size` passes.
- **NFR-4 Never block a start.** A missing, unreadable or malformed config file makes the host write one `[acp-host] overdeck MCP config skipped: <reason>` line to stderr and start with no MCP servers. It never throws (matches W-INJ1's degrade rule).
- **NFR-5 No Effect façade.** The new module exports a plain `async` function, not an Effect wrapper; `npm run lint:effect-facades` does not rise (`docs/EFFECT-BRIDGING.md`).
- **NFR-6 No new harness-name branch.** The guard compares `launchCommandKind`, not harness names; `npm run lint:harness-branches` does not rise.

## Decisions

- **D-1 Keep the helper names.** `prepareClaudeOverdeckMcp` and `writeClaudeOverdeckMcpConfig` keep their names; the header comment says the file is Claude Code's `--mcp-config` format and the ACP host reads the same file. Why: a rename touches 8 call sites in 7 files that W-INJ2 is about to edit, for no behavior change. A rename is a possible follow-up, not this issue.
- **D-2 The guard becomes a closed set of launch kinds.** `const OVERDECK_MCP_JSON_LAUNCH_KINDS: ReadonlySet<string> = new Set(['claude-code', 'acp-host']);` — the launch kinds whose command builders read `overdeckMcpConfig`. Codex is not in it; W-INJ2 decides its own shape.
- **D-3 One config file per owner.** The ACP launch reads the same `<dir>/overdeck-mcp.json` W-INJ1 writes. No ACP-specific file.
- **D-4 Stdio only** (NFR-1), even though both agents advertise `http` and `sse`.
- **D-5 Conversion rules** (`readAcpMcpServers`): each `mcpServers` entry whose `type` is `'stdio'` or absent, with a non-empty string `command`, becomes `{ name: <key>, command, args: <string[] or []>, env: Object.entries(<env or {}>).map(([name, value]) => ({ name, value: String(value) })) }`. An entry with any other `type` (`http`, `sse`) or without a `command` is skipped with one stderr line naming it. Entry order follows the file.
- **D-6 Degrade, never throw** (NFR-4). `readAcpMcpServers` returns `[]` and writes one stderr line on a read error, invalid JSON, or a top level without an `mcpServers` object.
- **D-7 Flag placement.** `buildAcpCommand` pushes `'--mcp-config', shellQuote(path)` right after the `--context-file` block and before the Kimi effort block. Space form: the host's own parser reads the next argv item, and no positional prompt follows the host command (the Claude Code equals-form rule, PAN-4932 C-1, does not apply here).
- **D-8 No `OPENCODE_PERMISSION` change by default.** OpenCode's defaults allow MCP tools, and widening the pre-allowed keys also overrides an operator's own `deny` (concerns.md, PAN-3937 entry). CP-3 checks it (W-6 step 5); only a hang found there adds a key.
- **D-9 No committed probe.** CP-3's probe script lives under `.tmp/` (gitignored) or the agent's scratch directory. Its result goes into `configuration/harnesses.mdx` and the PR description.
