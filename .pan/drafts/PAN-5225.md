# PAN-5225 — `pan close` ran the previous build after PAN-5209 shipped; harden the merged check and finish the MYN close-out path

**Issue:** [PAN-5225](https://github.com/eltmon/overdeck/issues/5225)
**Related:** [PAN-5209](https://github.com/eltmon/overdeck/issues/5209) (compare against `origin/<target>`, forge landing evidence for rows 1/2; PRD `.pan/drafts/PAN-5209.md`), [PAN-3538](https://github.com/eltmon/overdeck/issues/3538) (reload repoints the npm-global `pan` link), [PAN-2630](https://github.com/eltmon/overdeck/issues/2630) (the `~/.overdeck/cli-bin` exec shim).

## Glossary

- **Close-out** — `pan close <id>` and `POST /api/issues/:id/close-out`. Both call `closeOut()` in `src/lib/lifecycle/workflows.ts`, which runs the Definition-of-Done gate before any cleanup.
- **DoD gate / rows** — `evaluateDodGate()` in `src/lib/lifecycle/dod-gate.ts`. Rows: 1 review, 2 tests, 3 verification, 4 merged, 5 post-merge, 6 main-verify, 7 ship, 8 deploy. A row is `pass`, `skip` or `miss`. An unaccepted `miss` blocks close-out. The gate only reads; nothing is torn down before it passes.
- **Comparison ref** — the ref row 4's ancestry, diff and log checks compare against. Resolved by `resolveTargetComparison()` in `src/lib/lifecycle/verify-merged.ts`.
- **Remote-tracking ref** — `refs/remotes/origin/<target>` (written `origin/<target>`): the target branch as of the last successful fetch.
- **Repo landing evidence** — PAN-5209's per-repo verdict in `src/lib/lifecycle/dod-forge-merge.ts` (`merged`, `no-branch-work`, `unlanded`, `unverifiable`). "Complete" = no `unlanded`/`unverifiable` repo and at least one `merged` repo. Rows 1/2 of a non-GitHub-tracked issue (`ctx.github` unset) read it through the memoized `landing.forgeMerge`.
- **Generation** — a dashboard deployment directory, `~/.overdeck/deployments/dashboard/.pan-reload-generation-a` or `-b`. `pan reload` builds `origin/main` into the inactive one and activates it.
- **cli-bin shim** — `~/.overdeck/cli-bin/pan` (and `overdeck`), a two-line `#!/bin/sh` exec script rendered by `src/lib/pan-cli-shim.ts`. It execs `<generation>/dist/cli/index.js`. It is **first on PATH** (`which -a pan` → `~/.overdeck/cli-bin/pan`, then the npm-global `…/node/v22.22.0/bin/pan`).
- **npm-global link** — `<node>/lib/node_modules/@overdeck/core`, repointed to the new generation by `pan reload` (`repointGlobalCliToDeployment`, PAN-3538). It is second on PATH, so the cli-bin shim shadows it.
- **DoD probe** — a read-only script (WI-7) that calls `evaluateDodGate()` from source and prints each row. It never runs close-out teardown.

## Problem and verified root cause

The issue reports that after PAN-5209 shipped (`99517e495ab`), `pan close MIN-1140 --force` and `pan close MIN-1139 --force` still failed rows 1, 2, 4 and 5 with the **pre-PAN-5209** texts, and it hypothesises that `git fetch` fails inside `pan close`. That hypothesis is wrong. Verified on 2026-11-13:

1. **The failing run executed the previous generation.** Generation-b's checkout is at `70816bc8790` (PAN-5195, one commit before PAN-5209) and its `dist/cli/index.js` was built at 21:30:34 EST; PAN-5209 was committed at 21:36. `grep -rlaF "Checked against local"` and `grep -rlaF "forge merge incomplete"` find nothing in generation-b's `dist/`, and find `dist/lifecycle-D8atcbKq.js` in generation-a (`99517e495ab`, built 21:45:46).
2. **The shim pointed at generation-b when the issue was filed.** The issue was created at 02:50:08Z (21:50:08 EST). `~/.overdeck/cli-bin/pan` was rewritten at 21:50:43 to point at generation-a — by the launcher of the PAN-5225 planning agent (its session context is stamped 02:50:42Z). Until then the shell's `pan` ran generation-b.
3. **The reported text matches the old code exactly.** Row 4 said `10 unmerged commit(s) on feature/min-1140. Merge before closing out.` with no `(Checked against local main …)` suffix. Current code appends that suffix on every fallback failure (`withComparisonNote`, `verify-merged.ts` line 45). Row 1 said only `no pull request found on the forge for this issue`, with none of PAN-5209's `; forge merge …` text.
4. **Why the shim lagged.** `pan reload` repoints the npm-global link (`src/cli/commands/reload.ts` line 54, `reportCliRepoint` → `repointGlobalCliToDeployment`) but never the cli-bin shim. Only three things write the shim (`git grep writePanCliShims panCliShimLauncherLines src` → `pan-cli-shim.ts`, `launcher-generator.ts`, `install.ts`, `sync.ts`): agent launchers (`src/lib/launcher-generator.ts` line 395, `panCliShimLauncherLines()`, rendering the *spawning* process's own generation), `pan install`, and `pan sync` (`sync.ts` line 559; the dashboard's auto-sync runs `pan sync --if-changed`, which can return at line 144 before reaching it). So the shell `pan` runs whichever generation last launched an agent or ran a full sync. Nothing ties it to the reload that just activated a new generation, and the observed timestamps show it lagging generation-a by about five minutes. `docs/BUILD.md` line 21 documents the writers.

**What the current build does** (read-only DoD probe from `99517e495ab` source, 2026-11-13, in the planning agent's shell — fetch succeeded, no comparison note):

```
MIN-1140: review skip, tests skip (forge merge complete: fe merged (!121), infra merged (!16), others no branch work)
          verification pass, merged pass, post-merge MISS (canonical state unavailable; PR mergedAt: not merged; no running work/planning agents)
          main-verify skip, ship skip, deploy skip → passed false
MIN-1139: review MISS, tests MISS (forge merge incomplete: openclaw-plugin: feature/min-1139 is not on origin/main and has no merged review artifact)
          verification MISS (verification artifact: failed at 2026-11-11T08:16:11.273Z (frontend-lint))
          merged pass, post-merge MISS (same text as MIN-1140) → passed false
```

So three real gaps remain after PAN-5209, plus the hardening the issue asks for:

- **Row 5 has no pass path for a non-GitHub-tracked issue that landed through merged MRs.** `checkPostMergeRow()` (`dod-gate.ts` line 625) passes on `canonicalState === 'verifying_on_main' || Boolean(mergedAt)`. For a Linear issue `getAutoCloseOutCanonicalState()` (`src/lib/lifecycle/auto-close-out-canonical-state.ts` line 24, `if (!ghResolved.isGitHub)`) always returns `null`, and `readPullRequestMergedAt()` reads only the GitHub issue PR, so both are always empty. The branch-containment escape (`merged?.evidence === 'branch-containment'`) is not reachable either: `checkMergedRow()` reads containment only when row 4 misses, and `gatherIssueBranchContainment()` itself compares against the stale local `main` (probe: it lists `myn-skills` and `openclaw-plugin` as `unmergedRefs` for both issues). Every MYN close-out therefore needs `--accept-post-merge`.
- **Rows 1/2 call a branch "unlanded" even when its tree equals the target's.** `openclaw-plugin` `feature/min-1139` (tip `4642475`) carries a checkpoint commit `f679495` and a merge commit that drops it again. It is not an ancestor of `origin/main`, but `git rev-parse origin/main^{tree} feature/min-1139^{tree}` returns the same tree (`27e43655…`). There is nothing on it to land. Row 4 already accepts it (empty three-dot diff).
- **Row 3 for MIN-1139 is a genuine miss.** Its workspace verification artifact says `failed … (frontend-lint)`. This plan does not change row 3 (see Decisions).
- **Hardening (issue requirement 2).** When the fetch fails, `resolveTargetComparison()` falls back to the bare local `<target>` even when a remote-tracking `origin/<target>` exists. Local `main` in primary checkouts is weeks stale, so the last-fetched remote-tracking ref is always the better comparison.

## Requirements

### Functional

- **FR-1** — Every `pan reload` activation that repoints the npm-global link also rewrites the cli-bin shim (`pan` and `overdeck`) to exec `<deployRoot>/dist/cli/index.js`, through `writePanCliShims({ root: deployRoot })`. On success it prints `  pan CLI shim → <deployRoot>` (dim). - **FR-2** — `resolveTargetComparison(dir, target)`: when `git fetch origin +refs/heads/<target>:refs/remotes/origin/<target>` fails, the fallback order is (1) `origin/<target>` when `git rev-parse --verify --quiet refs/remotes/origin/<target>^{commit}` resolves, (2) the bare local `<target>` when `refs/heads/<target>^{commit}` resolves, (3) no ref. A stale local branch is never chosen while a remote-tracking ref exists. A successful fetch still returns `{ ref: 'origin/<target>' }` with no note.
- **FR-3** — Fallback notes (appended to `details` on pass/skip and to `error` in parentheses on failure, unchanged mechanism `withComparisonNote`):
  - remote-tracking fallback: `Checked against the last-fetched origin/<target> because git fetch origin <target> failed: <reason>`
  - local fallback (unchanged): `Checked against local <target> because git fetch origin <target> failed: <reason>`
  - no ref: error `Cannot verify merge: git fetch origin <target> failed (<reason>) and neither origin/<target> nor a local <target> branch exists`.
  `<reason>` is unchanged (`fetchFailureReason`: first non-empty stderr line, else message, cut to 200 chars).
- **FR-4** — In `assessRepoLanding()` (`dod-forge-merge.ts`), when `git merge-base --is-ancestor <tip> <ref>` fails, the repo is `no-branch-work` with reason `<repoKey>: <source> adds no changes over <ref>` if `git diff --quiet <ref>...<tip>` (three dots: the branch's net change since its merge-base with `<ref>`) exits 0. Exit 1 keeps today's `unlanded` result and reason. Any other exit is a git read failure and yields `unverifiable` (`<repoKey>: git read failed: <message>`) through the existing outer `catch`.
- **FR-5** — Row 5 for a non-GitHub-tracked issue: when the lifecycle is not otherwise observed (no `verifying_on_main` canonical state, no `mergedAt`), the strike and branch-containment branches do not apply, and `landing.forgeMerge` is present, the row reads `readForgeMergeVerdict(landing.forgeMerge)`. ## Decisions (made here)

- **D1 — Root cause is the stale shim, not a failing fetch.** No "why does fetch fail" spike. The fetch fix in FR-2 is hardening the issue asked for, not the fix for the reported run.
- **D2 — Fix the shim at reload (FR-1), not in `pan close`.** Every CLI verb is affected, not only close-out, and reload is the one place that knows a new generation went live. Doctor's "CLI Generation" check (`src/cli/commands/doctor-cli-generation.ts`) still inspects only the npm-global link; extending it to the shim is a follow-up, not this issue.
- **D3 — Rows 1/2 still refuse to judge on an unrefreshed target.** `assessRepoLanding()` keeps treating any `comparison.note` as `unverifiable` (PAN-5209 FR-6: "rows 1/2 never judge landing against an unrefreshed target"). FR-2's new fallback therefore changes only row 4.
- **D4 — An empty three-dot diff, with no path exclusions, for FR-4.** `git diff --quiet <ref>...<tip>` compares the tip with its merge-base, so it stays empty when `<ref>` advances later (verified: `openclaw-plugin` merge-base of `origin/main` and `feature/min-1139` is `db67f5a`, and the three-dot diff exits 0). Two-tree equality (`<ref> <tip>`) was rejected: one new commit on `main` would flip MIN-1139 back to `unlanded`. A squash-merged branch with no merged artifact still reads `unlanded`, because its merge-base is the old fork point and the diff shows its work. No `:!.planning`-style exclusions (row 4 has them): rows 1/2 stay strict. `no-branch-work` never counts as `merged`, so completeness still needs at least one merged artifact.
- **D3a — Why FR-2's remote-tracking fallback is safe, and the assumption it rests on.** The fetch refspec has a leading `+`, so `origin/<target>` can move backward on a later successful fetch, but only if upstream `<target>` itself was rewritten. **Assumption (stated, not enforced in code): a project's merge target is a protected branch that is never force-pushed or rewound.** GitHub and GitLab protect `main` for every registered project, and Overdeck itself only ever adds commits to it. Under that assumption a stale `origin/<target>` can only *under*-report merged work (a miss, never a false pass). Local `<target>` can be both weeks behind (MYN primary checkouts) and ahead with unpushed commits that never reached the forge, which could read as merged. So the remote-tracking ref is always the more conservative comparison, and the note still tells the reader the fetch failed. This differs from PAN-5209's critique about cached `origin/<source>` refs: that ref decided whether a *branch* exists; here the target ref only bounds what counts as landed.
- **D5 — Row 5 reuses the memoized forge verdict, not branch containment.** Containment compares against stale local `main` (`pipeline-membership-gather.ts resolveRepositoryDefaultBranch`, already listed as unfixed in `.overdeck/context/codebase/concerns.md`), so it would still list `myn-skills`/`openclaw-plugin` as unmerged. A complete forge verdict is the non-GitHub analogue of the GitHub PR's `mergedAt`, which row 5 already accepts on its own. Result is `pass` (same as the `mergedAt` path), and blocking agents still turn it into `miss`.
- **D6 — Row 3 is not touched.** MIN-1139's failed `frontend-lint` verification artifact is real evidence. Close-out for MIN-1139 needs an operator decision (`--accept-verification`, or a fresh verification run). The issue's "both close with no `--accept-*`" requirement is met for MIN-1140 and for MIN-1139 rows 1, 2, 4 and 5 only.
- **D7 — Extract row 5 before changing it.** `dod-gate.ts` has 8 lines of headroom; FR-5 needs about 10. WI-4 moves row 5 into `src/lib/lifecycle/dod-post-merge-row.ts` with no behavior change, and moves `rowDefinition`/`result` into `dod.ts` so both modules share them without a cycle.
- **D8 — The live check is a read-only probe, not a real close.** The deployed `pan` will not carry this fix before merge, and a passing close-out irreversibly removes the MYN workspaces and closes the Linear issues. The work agent pastes probe output into the PR (FR-6). The real `pan close MIN-1140 --force` runs after merge and `pan reload` (flywheel/operator), and its output goes on the PR as a comment.
