# PAN-4618 — Bookkeeping commits skip CI, superseded CI runs are cancelled, and main-CI readers use the newest decisive run

**Issue:** [PAN-4618](https://github.com/eltmon/overdeck/issues/4618)
**Status:** planned (auto mode, 2026-10-24). Revision 2: operator scope addition
(concurrency group, issue comment 2026-10-24T11:49Z) and the plan critique
(`.pan/drafts/PAN-4618-critique.md`) are folded in; see "Critique response".

## Glossary

- **Bookkeeping commit** — a commit on `main` whose changed files all sit under
  `.pan/` or `.overdeck/memory/`. Examples: the backlog sequencer's
  `chore(workspace): backlog sequence` commits (`.pan/backlog/sequence.md`),
  Flywheel state/report commits (`.pan/flywheel/…`), and `pan memory add`
  commits (`.overdeck/memory/<id>.md`). On 2026-10-23/24, 107 of 111 commits on
  `origin/main` were `chore(workspace)` commits; 93 of them touched only
  `.pan/backlog`.
- **CI** — the GitHub Actions workflow named `CI`, file `.github/workflows/ci.yml`
  (jobs `build (22)`, `lint-group (*)`, `lint`, `Prompt change trailer gate`,
  `test-shard (N/4)`, `test-e2e`, `test`, `Non-blocking flake lane`,
  `Clean install + server smoke test`). About 13 runner jobs per run. The
  workflow-runs API reports this workflow with `path: ".github/workflows/ci.yml"`
  (checked live during planning: `gh api 'repos/eltmon/overdeck/actions/runs?branch=main&event=push&per_page=6' --jq '.workflow_runs[].path'`).
- **Guard workflow** — `.github/workflows/no-planning-on-main.yml` (workflow
  `no-planning-on-main`, job `reject-planning-paths`). It runs on every push to
  `main` and stays unchanged.
- **Skipped push** — a push to `main` for which GitHub starts no `CI` run because
  of `paths-ignore`. GitHub compares the branch before and after the **whole
  push**: the run is skipped only when every file changed by the push matches a
  pattern. When it runs, it runs **at the pushed tip**. So one push holding code
  commit C followed by bookkeeping commit B runs CI on B, and C has no run.
- **Superseded run** — a CI run whose concurrency group received a newer run.
  With `cancel-in-progress: true`, GitHub cancels it; its jobs conclude
  `cancelled`.
- **Decisive conclusion** — a completed check whose conclusion is a verdict on the
  code: `success`, `failure`, `timed_out` (and `neutral`/`skipped` where the
  existing code already treats them). `cancelled`, `stale`, `startup_failure`,
  `action_required` are **indecisive** (`INDECISIVE_CONCLUSIONS`,
  `src/lib/cloister/ci-default-branch-tests.ts` line 23).
- **CI-bearing commit** — a default-branch commit that carries a CI run. Readers
  identify it by the CI evidence on the commit, never by its changed files
  (see Critique response): the test-verdict reader by the presence of test
  checks, DoD row 6 by the presence of every required check name, the Command
  Deck chip by a `CI` workflow run on that sha.
- **CI head** — the `head_sha` of the newest `push` run of the `CI` workflow on
  the default branch. It is the newest commit CI was started for. When the
  project has no `.github/workflows/ci.yml` workflow (the runs endpoint answers
  404) or no push run of it yet, the CI head falls back to the branch head
  (today's behaviour).
- **Check run / check suite / commit status** — a check suite is one workflow run
  on one commit (`check_suite` webhook); a check run is one job
  (`commits/<sha>/check-runs`); a commit status is the legacy status API
  (`commits/<sha>/status`, used by Dagger Cloud, PAN-4589).
- **Main-CI reader** — any code or agent instruction that reads CI results for
  the default branch (not for a PR head).

## Problem

`.github/workflows/ci.yml` lines 3–7:

```yaml
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
```

There is no path filter and no `concurrency` key.

1. Each bookkeeping commit runs the full ~13-job suite. On 2026-10-24, 95 CI runs
   on `main` came from bookkeeping commits and 4 from code merges; at 11:28 four
   approved PRs (#4601, #4607, #4611, #4615) waited with 13 checks `pending`.
2. Every push to a PR branch or to `main` queues a full run while runs for
   superseded heads keep their runners. At 11:50 there were 48 unfinished CI
   runs (24 on `main`, 12 on `feature/pan-4598` alone); the Flywheel cancelled 34
   superseded runs by hand (operator comment on the issue).

Nothing under `.pan/` or `.overdeck/memory/` feeds the build or the test suite
(verified during planning):

- `scripts/lint-permissions.sh` line 43 already excludes `':!.pan/*'`.
- The only tests that read `.pan/` paths build them in a temp directory
  (`src/lib/backlog/__tests__/write-sequence.test.ts` line 38;
  `tests/unit/lib/pan-dir/migrate-plan-home.test.ts` line 170).
- `scripts/check-prompt-change-trailer.sh` diffs `git merge-base origin/main HEAD`
  against `HEAD`; on a push to `main` that range is empty. No script reads
  `github.event.before`, `GITHUB_EVENT_*` or `HEAD~1`, so skipped or cancelled
  pushes change no push-range computation.
- `.overdeck/context/codebase/**` is not a bookkeeping path: it lands only inside
  code PR squash-merges.

## Requirements

### Functional

- **FR-1** — A push to `main` whose changed files all match `.pan/**` or
  `.overdeck/memory/**` starts no `CI` workflow run. A push that changes any
  other file still starts one. The `pull_request` trigger has no path filter and
  `no-planning-on-main.yml` is unchanged.
- **FR-2** — *Retired in revision 2.* (Was: a TypeScript bookkeeping-path module
  with a ci.yml drift test. No reader classifies commits by changed files any
  more, so nothing in code needs the path list.)
- **FR-3** — `pan reload` (`buildDashboardFromOriginMain`) builds `origin/main`
  HEAD when HEAD is a bookkeeping commit, and the built tree holds the parent
  code commit's files. A test proves it.
- **FR-4** — `readDefaultBranchFailingTestChecks` finds the newest decisive test
  verdict even when up to 99 newer commits carry no test checks or only
  cancelled ones. It never reports "no failing tests" because it only looked at
  commits without a decisive run.
- **FR-5** — DoD row 6's later-green fallback skips candidates that carry no full
  CI run (missing any required check name) without using up its 5-candidate
  budget. It keeps every first-parent candidate, including promote merges and
  bookkeeping tips of mixed pushes, and decides only from the checks each one
  carries.
- **FR-6** — The Command Deck CI chip shows the suites of the **CI head**. The
  REST fill and the `check_suite` webhook use the same resolver, and the event
  contract comments say `headSha`/`authoritativeHead` refer to the verified CI
  head.
- **FR-7** — The Flywheel, recap and consolidation skills and the Flywheel role
  prompt state two rules. **Red-main rule:** main's verdict is the newest `CI` run
  on `main` whose conclusion is `success` or `failure`; queued, in-progress and
  cancelled runs are not a verdict; its `headSha` is usually older than
  `origin/main` HEAD. **Deploy rule:** `pan reload` runs only when the newest `CI`
  run on `main` (no filter) is `completed` with conclusion `success`; queued or
  in-progress → wait; a cancelled newest run (only an operator can cancel the
  newest run) → ask, do not deploy.
- **FR-8** — `docs/PIPELINE-GATES.md`, `docs/MERGE-WORKFLOW.md` and
  `docs/EXTERNAL-EVENT-STREAM.md` state that bookkeeping commits skip CI, that
  superseded runs are cancelled, and how each reader finds the newest decisive
  run.
- **FR-9** — `ci.yml` declares a workflow-level concurrency group
  `ci-${{ github.event.pull_request.number || github.ref }}` with
  `cancel-in-progress: true`. A second push to a PR branch cancels the first
  push's still-running CI run; a newer push to `main` cancels the older
  in-progress `main` run.

### Non-functional

- **NFR-1** — No new synchronous child-process calls in server-reachable code
  (`no-execsync-server` rule). The CI-head resolver goes through the existing
  async `projectCiGhApi` (metered GitHub quota caller `ci-repair`).
- **NFR-2** — The CI-head resolver costs one GitHub call per resolution
  (`actions/workflows/ci.yml/runs?branch=…&event=push&per_page=1`, a one-run
  response); it replaces the `branches/<branch>` call, so the call count only
  grows (by one) when it falls back to the branch head.
- **NFR-3** — `src/lib/lifecycle/dod-gate.ts` is 993 lines; `scripts/lint-file-size.sh`
  (`CEILING=1000`) fails at 1001. Work item 4 has an extraction rule.
- **NFR-4** — Tests that need delays use fake timers (`fake-timers-for-retry-tests`
  rule). None of the planned tests need delays.

## Decisions

- **D1 — Path list.** `paths-ignore: ['.pan/**', '.overdeck/memory/**']` on
  `on.push` only, exactly as the issue names.
- **D2 — Guard workflow unchanged** (issue instruction). DoD row 6 requires its
  check name (`DEFAULT_MAIN_VERIFY_REQUIRED_CHECKS`, `dod-gate.ts` line 144).
- **D3 — `pan reload` needs no code change.** It always builds `origin/main`
  HEAD. Deliverable: a regression test plus the Flywheel wording.
- **D4 — Test-verdict window.** One page of 100 commits; a budget of 10 commits
  whose test checks are **running or decisive**. Commits with no test checks, or
  whose test checks all completed with an indecisive conclusion (cancelled
  superseded runs), are skipped without using the budget. When no commit in the
  page carried test checks: `new Set()` if the page held fewer than 100 commits,
  else `null` (unknown → `ci-failure-feedback.ts` line 180 spends no attempt).
- **D5 — DoD candidates are classified by their checks, not their files**
  (critique finding 1). Keep `readContainingDefaultBranchCommits` unchanged
  (unfiltered `git rev-list --first-parent`). In `findLaterGreenDefaultBranchRun`,
  scan up to `LATER_GREEN_SCAN_LIMIT = 50` candidates; a candidate whose
  `checks.names` lacks any required check is skipped and not counted; at most
  `LATER_GREEN_CANDIDATE_LIMIT = 5` CI-bearing candidates are probed. A
  CI-bearing candidate whose required checks are all present but some are not
  successful (failed, pending or cancelled) is counted and probing continues.
- **D6 — CI head from CI runs** (critique finding 2). `resolveCiHead` reads
  `repos/<repo>/actions/workflows/ci.yml/runs?branch=<branch>&event=push&per_page=1`
  (constant `MAIN_CI_WORKFLOW_FILE = 'ci.yml'` in
  `src/lib/ci/project-ci-github.ts`) and returns that run's `head_sha`. The
  workflow-specific endpoint is used because ~24 bookkeeping pushes (each with a
  guard run) can sit above the newest CI run, which would push it out of any
  page of the all-workflows runs list. A 404 (no such workflow) or an empty list
  → fall back to `resolveDefaultBranchHead`; any other error propagates. A mixed push's bookkeeping tip carries the run, so
  it becomes the CI head; a skipped push never does. Payload field names do not
  change.
- **D7 — The CI workflow path is a constant, not per-project config.** Projects
  without `.github/workflows/ci.yml` runs keep today's branch-head behaviour.
- **D8 — Concurrency (revised by the operator).** Revision 1 rejected
  `cancel-in-progress`; the operator's issue comment reverses that. Add, at
  workflow level (after `on:`, before `env:`):
  ```yaml
  concurrency:
    group: ci-${{ github.event.pull_request.number || github.ref }}
    cancel-in-progress: true
  ```
  Readers already skip indecisive conclusions or are made to (D4, D5, FR-7).
- **D9 — Pushing the workflow change.** `.github/workflows/` edits must be pushed
  over the SSH remote; the gh OAuth token lacks the `workflow` scope. Recent
  `ci.yml` changes (#3990, #3994) landed through normal PR squash-merges. If the
  push is refused, stop and report.
- **D10 — Retired in revision 2.** (Was: a `--jq` projection for
  `commits/<sha>` lookups. The resolver no longer reads commits.)
- **D11 — No bookkeeping-path module.** No reader classifies commits by their
  changed files, so FR-2's module and drift test are dropped. The ci.yml comment
  is the single statement of the path list.
- **D12 — Two Flywheel rules.** Red-main uses the newest decisive run; deploy
  uses the newest run and requires `completed`/`success` (see work item 8 for why
  they differ under cancel-in-progress).

### 5. CI-head resolver (FR-6, foundation for 6a/6b)

```ts
/** PAN-4618: the workflow whose newest push run marks the commit CI describes. */
export const MAIN_CI_WORKFLOW_FILE = 'ci.yml';

/**
 * PAN-4618: the newest default-branch commit CI was started for — the head_sha
 * of the newest push run of the CI workflow. Bookkeeping pushes start no CI
 * run, so this is usually older than the branch head. Falls back to the branch
 * head when the project has no such workflow (404) or no push run of it yet.
 */
export async function resolveCiHead(
  repo: string,
  branch: string,
  ghApi: ProjectCiGhApi = projectCiGhApi,
): Promise<string | null> {
  let response: { workflow_runs?: Array<{ head_sha?: string }> };
  try {
    response = await ghApi(
      `repos/${repo}/actions/workflows/${MAIN_CI_WORKFLOW_FILE}/runs?branch=${encodeURIComponent(branch)}&event=push&per_page=1`,
    ) as typeof response;
  } catch (error) {
    // runGh rethrows the execFile error: the gh text `gh: Not Found (HTTP 404)` is on `stderr` and in `message`.
    const failure = error as { message?: unknown; stderr?: unknown };
    if (!/HTTP 404/.test(`${String(failure?.stderr ?? '')} ${String(failure?.message ?? error)}`)) throw error;
    response = {};
  }
  return response.workflow_runs?.[0]?.head_sha ?? resolveDefaultBranchHead(repo, branch, ghApi);
}
```

### 8. Skills and role prompt say how to read main's CI (FR-7)

Two rules. With `cancel-in-progress` on `main`, a burst of merges cancels every
run but the last, so the newest *decisive* run can be green while HEAD's own run
was cancelled and its successor is still running: the red-main rule must not
approve a deploy. Use each rule verbatim.

**Red-main rule** (for "Keep `main` green"):

> Main's CI verdict is the newest `CI` run on `main` that concluded `success` or
> `failure`: `gh run list --branch main --workflow CI --limit 20 --json headSha,status,conclusion --jq '[.[] | select(.conclusion == "success" or .conclusion == "failure")][0]'`.
> Queued, in-progress and `cancelled` runs are no verdict (a newer push cancels a
> superseded run), and bookkeeping commits (only `.pan/**` or
> `.overdeck/memory/**`) run no CI (PAN-4618), so the verdict's `headSha` is
> usually older than `origin/main` HEAD. That is expected, not "unknown".

**Deploy rule** (for `pan reload`):

> Deploy with `pan reload` only when the newest `CI` run on `main` succeeded:
> `gh run list --branch main --workflow CI --limit 1 --json status,conclusion,headSha`
> must show `status: completed` and `conclusion: success`. Queued or in progress:
> wait for it. Cancelled: only an operator cancels the newest run, so ask; do not
> deploy. Bookkeeping commits run no CI (PAN-4618), so this run's `headSha` may be
> older than HEAD; the build is the same code.
