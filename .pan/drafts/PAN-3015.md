# PAN-3015 — `pan monitor`: pull-based background inbox transport for Claude Code sessions

Issue: https://github.com/eltmon/overdeck/issues/3015

## Glossary

- **Keystroke injection** — delivering a message by simulating typing into a TUI composer: PTY supervisor write + echo-confirm + `\r`, or tmux `load-buffer`/`paste-buffer` + `send-keys C-m`.
- **Mail dir** — `~/.overdeck/agents/<id>/mail/`, the durable per-agent message store. Today written by `queueAgentMail` (`src/lib/agents/messaging.ts:62-70`) as `<timestamp>.md` / `<timestamp>.pending.md` files; nothing drains the plain `.md` files (PAN-2668).
- **Monitor** — a long-running `pan monitor` process started as a background task *inside* the agent's Claude Code session. Claude Code surfaces background-command stdout to the model at the next turn boundary and wakes an idle session, so anything the monitor prints becomes model-visible context without touching the composer.
- **Presence file** — `~/.overdeck/agents/<id>/monitor.json`, heartbeat written by the running monitor; senders use it to decide the monitor tier is live.
- **Read archive** — `~/.overdeck/agents/<id>/mail/read/`, where the monitor moves a mail file after printing it (ack = move, not delete), so `pan inbox` can re-read full bodies after the background-output surface truncates.
- **Monitor tier** — the new delivery decision in `messageAgent`: when the target is a Claude Code agent with fresh presence, write the mail file and stop; no keystroke transport runs.

## Background / verified current behavior

- `messageAgent` (`src/lib/agents/messaging.ts:106`) is the liveness-gating door for mid-session tells; `deliverAgentMessage` (`src/lib/agents/delivery.ts:204`) is the transport cascade (app-server → ACP → PTY supervisor → channels → tmux).
- `queueAgentMail(agentId, message, pendingTurnEndDelivery)` (`messaging.ts:62-70`) writes `# Message\n\n<body>\n` to the mail dir. `.pending.md` files are drained only by the codex notify hook; plain `.md` files are a write-only backup today.
- `DeliveryResult.path` union: `'app-server' | 'acp' | 'supervisor' | 'channels' | 'tmux' | 'pi' | 'codex'` (`delivery.ts:33`).
- Kickoff/initial-prompt delivery goes through `deliverAgentMessage`/`deliverInitialPromptWithRetry` from `spawn.ts` (`src/lib/agents/spawn.ts:409,438,827`) — the monitor cannot exist yet at kickoff time, so the monitor tier must live in `messageAgent` (mid-session only), NOT in `deliverAgentMessage`.
- Work-agent role prompt: `roles/work.md`; strike: `roles/strike.md`. Agent id is available to the session as `$OVERDECK_AGENT_ID`.
- CLI commands live in `src/cli/commands/*.ts`, registered in `src/cli/index.ts` (e.g. `tell` at `src/cli/index.ts:452-455`).

## Requirements

### Functional

- **FR-1** `pan monitor [id]` runs until killed: on start it drains the backlog of plain `*.md` mail files (oldest first), then watches the mail dir and prints each new plain `.md` file to stdout as a structured block; after printing, it moves the file to the read archive. `.pending.md` and `*.json` (FPP) files are ignored.
- **FR-2** The printed block format is:
  `[overdeck:agent-message] source: <source> at: <iso-ts>` newline `<body>` newline `[overdeck:agent-message] end`. Bodies longer than 4000 chars are truncated with a trailing line telling the agent to run `pan inbox` for the full body.
- **FR-3** The monitor maintains `monitor.json` presence: `{pid, startedAt, heartbeatAt}` refreshed every 15s (fake-timer-testable), removed on SIGINT/SIGTERM/normal exit. All diagnostics go to stderr; stdout carries message blocks only.
- **FR-4** `pan inbox [id] [--limit <n>]` prints full bodies of the most recent messages (unread first, then read archive), default limit 10, no truncation, and does not move/ack anything.
- **FR-5** `queueAgentMail` records provenance: new optional `source` argument; file content becomes `# Message\n\nsource: <source>\ndate: <iso>\n\n<body>\n`. The monitor parses this header when present and falls back to printing the raw file body when absent (backward compatible with pre-existing mail).
- **FR-6** Monitor tier in `messageAgent`: for a target whose `state.harness === 'claude-code'` and whose presence file shows `heartbeatAt` within 45s AND a live pid, `messageAgent` writes the mail file (with source) and returns `{delivered: true, queuedToMail: true, reason: 'monitor'}` without calling `deliverAgentMessage`. It logs the winning path via `appendChannelDeliveryLog(id, {path: 'monitor', caller})`.
- **FR-7** Stale presence (old heartbeat or dead pid) falls through to the existing cascade unchanged. Kickoff, resume redelivery, and non-claude harnesses are untouched.
- **FR-8** Work and strike role prompts instruct Claude Code sessions to start `pan monitor` as a background task at session start (one short section each in `roles/work.md`, `roles/strike.md`).

### Non-functional

- **NFR-1** No `execSync` anywhere (dashboard-reachable rule); the monitor uses async fs watch + interval polling, `setInterval` for heartbeat.
- **NFR-2** All delay/interval tests use `vi.useFakeTimers()` + advance helpers — never real waits.
- **NFR-3** The monitor must not corrupt or double-print under concurrent writes: files are claimed by rename into the read archive before printing is considered final; a rename failure (already moved) skips the file.
- **NFR-4** Surgical changes: no refactor of the existing cascade; `deliverAgentMessage` is not modified except for the `'monitor'` member joining the `DeliveryResult.path` union used by the log call.

## Acceptance criteria

- AC-1 (↔WI-1,2): starting `pan monitor` for an agent with 2 queued mail files prints both blocks oldest-first, moves both into `mail/read/`, and writes `monitor.json`; killing it removes `monitor.json`.
- AC-2 (↔WI-4): with a fresh `monitor.json` and live pid, `messageAgent` returns `reason:'monitor'`, a new mail file exists with the `source:` header, and no PTY/tmux delivery is attempted; with a stale heartbeat it falls through to the existing cascade.
- AC-3 (↔WI-3): `pan inbox` prints full untruncated bodies including already-read messages, and changes nothing on disk.
- AC-4 (↔WI-1): a >4000-char body is truncated in the monitor block with the `pan inbox` pointer line; `pan inbox` shows it in full.
- AC-5 (↔WI-5,6): role prompts and `docs/MONITOR-TRANSPORT.md` land in the same change; typecheck, lint, and the test suite pass with no new failures.

## Decisions made

- Monitor tier lives in `messageAgent`, not `deliverAgentMessage` — kickoff/resume must keep using injection because no monitor exists before the session's first turn.
- Ack is move-to-archive, never delete — preserves `pan inbox` re-read and the durable-mail crash-safety property.
- Presence freshness window is 45s against a 15s heartbeat (3 missed beats) plus pid liveness; a dead monitor window at worst leaves the message durable-but-unread until the next monitor start — accepted for v1.
- `.pending.md` stays codex-notify-hook territory; the monitor never touches it.
