# PAN-5061 — Per-project MCP servers and credentials for agents

**Issue:** https://github.com/eltmon/overdeck/issues/5061
**Split out:** opt-in credential isolation → [#5065](https://github.com/eltmon/overdeck/issues/5065) (PAN-5065)
**Planned:** 2026-11-05, `pan plan --auto`, high effort

## Glossary

- **Project** — an entry under `projects:` in `~/.overdeck/projects.yaml`, typed `ProjectConfig` in `src/lib/projects.ts`.
- **Launch** — one start of a harness process for an agent or conversation: a fresh spawn, a role run, a planning session, a resume, a recovery relaunch, or a conversation start. Every launch writes a `launcher.sh` and opens a pane through `launchAgentPane` (`src/lib/terminal-backends/launch.ts`).
- **Launch project** — the project a launch belongs to. Resolved by issue prefix first (`resolveProjectFromIssueSync`), then by cwd containment (`findContainingProjectAsync`). A launch whose issue and cwd match no project has no launch project.
- **Role MCP servers** — servers declared in a role file's `mcpServers:` frontmatter (`roles/test.md` declares `playwright`), parsed by `parseRoleMcpServers()` in `src/lib/agents/runtime-command.ts`.
- **Project MCP servers** — the new `projects.<key>.mcp_servers` list. Same shape as role `mcpServers:`.
- **Launch MCP file** — the per-launch Claude Code `--mcp-config` file `<dir>/overdeck-mcp.json` (constant `CLAUDE_OVERDECK_MCP_CONFIG_FILE`), today written only for the `overdeck` server by `writeClaudeOverdeckMcpConfig` in `src/lib/mcp/agent-injection.ts`. `<dir>` is the agent dir (`~/.overdeck/agents/<id>/`) or the conversation state dir. The ACP host reads the same file.
- **Codex server map** — the `[mcp_servers.<name>]` tables `initCodexHome` (`src/lib/runtimes/codex.ts`) writes into the agent's `codex-home-v2/config.toml` on every launch.
- **Project secrets** — the `KEY=VALUE` pairs in the file named by `projects.<key>.workspace.env.secrets_file`.
- **Reserved keys** — env keys a secrets file may not set: every `OVERDECK_*` key and every key of `BLANKED_PROVIDER_ENV` (`src/lib/child-env.ts`).
- **`${NAME}` reference** — the literal text `${NAME}` (NAME matching `[A-Z_][A-Z0-9_]*`) inside a project MCP server's `args`, `env` values, `url`, or `headers` values.
- **Strict MCP mode** — Claude Code's `--strict-mcp-config` flag: only servers from `--mcp-config` files load.
- **Gate** — a project quality gate run by `runQualityGates` in `src/lib/cloister/validation.ts`.

## Problem

Every agent in every project gets the same credentials and the same MCP servers:

- Credentials come from the machine-wide `~/.overdeck.env`. The dashboard and every `pan` process load it (`src/lib/env-loader.ts`, `src/cli/index.ts` lines 12-35). Gates inherit the dashboard's whole `process.env` (`buildQualityGateEnv`).
- MCP servers come from role frontmatter and from the operator's own harness config. There is no per-project MCP setting.
- `workspace.env.secrets_file` is declared (`src/lib/projects.ts` line 115, `src/lib/workspace-config.ts` lines 74-79) but nothing reads it.
- Two accounts on one service (MYN and Auricle both on Linear; Sentry orgs; Fly apps) cannot be told apart, because each agent sees one `LINEAR_API_KEY` and the operator's one OAuth login per MCP server.
- Every user-scope MCP server's tools load into every Claude session (the probe below lists ten servers plus the claude.ai connector), whether or not the project uses them.

### F-2. A repo `.mcp.json` does not load in a spawned Claude session

`preTrustDirectory` writes `enabledMcpjsonServers: []` for each workspace (`src/lib/workspace-manager/worktree-ops.ts` lines 497-507) and nothing sets `enableAllProjectMcpServers`. Probe: in a directory with `.mcp.json` declaring `probe`, `claude mcp list` (Claude Code 2.1.293) reports `probe: cat - ⏸ Pending approval (run \`claude\` to approve)`. Overdeck never approves it, so repo `.mcp.json` servers do not reach agents. The launcher comments that say "project-level .mcp.json continues to load — so we MUST NOT also pass --strict-mcp-config" (`launcher-generator.ts` lines 240-241 and 270-271) describe behavior that does not happen.

### F-3. `--strict-mcp-config` keeps every `--mcp-config` file and drops user servers

Probe with `claude --print --output-format=stream-json --verbose`, reading the `system/init` event's `mcp_servers`:

- Without strict, with `--mcp-config=a.json --mcp-config=b.json`: sentry, linear, tldraw, mind-your-now, playwright, chrome-devtools, tldr, cloudflare, obs, stitch, alpha, beta, lin, claude.ai Claude Docs (14 servers).
- With `--strict-mcp-config` and the same two files: alpha, beta, lin only. Both equals-form files load.

### F-4. An HTTP server's OAuth login is per server name and URL

- `{"lin": {"type": "http", "url": "https://mcp.linear.app/mcp"}}` → status `needs-auth`.
- `{"linear": {"type": "http", "url": "https://mcp.linear.app/mcp"}}` (the operator's own name and URL) → `connected`, reusing the operator's stored login.

So a project HTTP server either reuses the operator's single login (same name and URL) or needs a token header. A spawned agent cannot complete an interactive OAuth flow. Per-project accounts therefore use a `headers` entry fed by project secrets.

### F-5. Where `~/.overdeck.env` keys reach agents today

Probed by key name only (no values read), on this host (Herdr backend under `overdeck-herdr.service`):

- The dashboard process environ holds all 11 keys of `~/.overdeck.env`.
- The Herdr server (pid of `herdr --session overdeck server`) and the `tmux -L overdeck` server hold **none** of them; a planning agent's shell holds none of them.
- Every `pan` subprocess an agent runs loads the file itself (`src/cli/index.ts` lines 12-35). Several modules read it directly (`close.ts:134`, `done.ts:92`, `lifecycle/types.ts:162`, `tracker-utils.ts:43`, `shadow-utils.ts:20`).
- Gates spread the dashboard's `process.env` (`validation.ts` lines 56-78), so gates see every key.
- A Herdr server started without systemd (`defaultSpawnDetached`, `src/lib/herdr-setup/service.ts` lines 122-139, no `env` option) and a tmux server founded by a process that loaded the file inherit the keys.

These leak paths are the subject of PAN-5065 (opt-in isolation). This issue adds credentials; it removes none.

### F-6. Skill packs that ship `.mcp.json`

`src/lib/skill-packs/adapters.ts` line 397 records `capabilities.mcpServers` and `notAppliedLabels` reports it as "Not applied". Project `mcp_servers` is the right mechanism to apply a pack's servers later (a pack's `.mcp.json` would be copied into the project's list). Wiring the adapter is out of scope for this issue.

### F-7. Should gates see project secrets?

Yes. Gates already see every `~/.overdeck.env` key; a project that moves a key into its secrets file must not break its own gates. Host-run gates get the project secrets; `gate.env` still wins.

## Requirements

### Functional

- **FR-1** `projects.<key>.mcp_servers` is a YAML list of single-key maps (the role `mcpServers:` shape). Each entry is `stdio` (default; `command` required, optional `args: string[]`, `env: map`) or `http` (`url` required, optional `headers: map`). Names match `^[A-Za-z0-9_-]+$`. The name `overdeck` is rejected. An invalid entry is skipped with one warning naming the project, the server and the reason; valid entries still apply.
- **FR-2** A launch's project is resolved by issue prefix first (`resolveProjectFromIssueSync(issueId)`), then by cwd containment. A launch with neither match gets no project servers and no project secrets.
- **FR-3** Each `${NAME}` reference in a project server's `args`, `env` values, `url` and `headers` values is replaced at launch time: project secrets first, then the launching process's `process.env`. A server with an unresolved reference is skipped with a warning naming the server and `NAME`, never a value. `$NAME` without braces is left as is.
- **FR-4** Claude Code and ACP launches write the project servers into the launch MCP file together with the `overdeck` server. The file is written when there is at least one server, including when `mcp.agents` is false or the token mint failed. A project server whose name equals a role MCP server of the launching role is dropped with a warning (the role's server wins).
- **FR-5** When the Claude Code command has no `--allowedTools`, the launcher emits `--allowedTools=mcp__<name>` for every server in the launch MCP file (comma-joined, `overdeck` first when present).
- **FR-6** `projects.<key>.mcp_strict: true` adds `--strict-mcp-config` to Claude Code launches of that project. Default `false`. It has no effect on other harnesses.
- **FR-7** Codex launches get the project servers in the Codex server map, each with `default_tools_approval_mode = "approve"`. `http` servers render `url` plus an `http_headers` inline table. Existing role and `overdeck` entries are unchanged.
- **FR-8** ohmypi, kimi-code, muse and prime-agent launches whose project declares servers log one warning per launch naming the harness and the server names. ACP launches drop `http` project servers through the existing `readAcpMcpServers` warning.
- **FR-9** `projects.<key>.workspace.env.secrets_file` (absolute or `~/` path, dotenv format) is read at every launch of that project and merged into the pane env under Overdeck's own launch env (Overdeck's keys win). Reserved keys are dropped with a warning naming the key. A relative path, a path inside the project's `path`, or a missing file yields no secrets and one warning.
- **FR-10** Host-run gates of that project get the project secrets in their env, under `gate.env` (`gate.env` wins). Remote (`isRemote`) gates do not resolve them.
- **FR-11** A launch or gate of a different project never receives another project's secrets or servers.
- **FR-12** The docs listed in WI-10 and WI-11 describe the fields, the per-harness support table, the `${NAME}` rule, strict mode, the OAuth finding (F-4) and the secrets file rules.

### Non-functional

- **NFR-1** A launch whose project declares neither `mcp_servers` nor `secrets_file` (or that has no project) produces the same launcher script, the same launch MCP file (or none) and the same pane env as before this change. The existing launcher golden tests (`tests/unit/lib/agents/codex-agent-home-golden.test.ts`, `tests/unit/lib/launcher-generator-overdeck-mcp.test.ts`) pass unchanged.
- **NFR-2** No secret value appears in any log line, warning, thrown error message or test snapshot. Warnings name projects, servers and keys only.
- **NFR-3** Files that hold resolved values are mode `0600` in a `0700` directory: the launch MCP file (already `0600`) and Codex `config.toml` (already `0600`).
- **NFR-4** New code on launch and gate paths uses `node:fs/promises`; no `execSync`, no new sync child processes. Reading `projects.yaml` goes through the existing cached loaders.
- **NFR-5** No god file grows: `src/lib/projects.ts` (1217 lines on `origin/main`), `src/lib/agents/spawn.ts` (1088) and `src/lib/overdeck/conversation-runtime.ts` (1190) stay at or under their `origin/main` count; `bash scripts/lint-file-size.sh` passes. Other touched files stay ≤ 1000 lines.

## Decisions

- **D-1 Isolation is split out.** Opt-in credential isolation moved to PAN-5065 (#5065). F-5 shows the pane env is not the main leak path on the default backend, so isolation is a different design (the `pan` CLI loader, direct file readers, non-systemd servers, gates) and gets its own PRD.
- **D-2 One launch MCP file.** Project servers go into the same `<dir>/overdeck-mcp.json` as the `overdeck` server, not a second `--mcp-config` file. The ACP host already reads exactly one file, so ACP gets project stdio servers with no ACP change. The constant name and file name stay (`CLAUDE_OVERDECK_MCP_CONFIG_FILE`) to avoid churn; the module header documents the wider content.
- **D-3 Writing the file is decoupled from the token mint.** `mcp.agents: false` or a failed mint drops only the `overdeck` entry.
- **D-4 Role wins on a name clash.** Roles declare the tools their job needs (`roles/test.md` → `playwright`). A project server with the same name is dropped with a warning. `overdeck` is always reserved.
- **D-5 Overdeck resolves `${NAME}` itself** and writes literal values into the `0600` files. Claude, Codex and ACP each expand (or don't) differently; one Overdeck rule gives one behavior for all three. The values never go in `projects.yaml` or the repo.
- **D-6 Project resolution order is issue first, cwd second.** The issue prefix is exact; cwd containment covers conversations and runs with no issue. Handoff worktrees under unregistered directories (for example `~/Projects/hoff-*`) get nothing. That is the safe default.
- **D-7 Secrets go in through the one pane chokepoint.** `launchAgentPane` merges them, so every launch path (spawn, role run, planning, the planning route, resume, recovery, messaging fallback, conversations, runtime panes) gets them with no per-site edit. On Herdr the values travel over the socket API; on tmux they travel as `-e` arguments, the same way provider keys already do.
- **D-8 Gates resolve their own project.** `runQualityGates` resolves the project secrets from `projectPath` when `opts.projectEnv` is undefined, so the two production callers (`verification-runner.ts` line 501, `merge-ops.ts` line 682, a 1759-line god file) stay untouched. Tests pass `opts.projectEnv` explicitly.
- **D-9 Strict mode is opt-in per project** (`mcp_strict`). It is the only way to stop user-scope servers loading (F-3), which the issue's context-cost motivation needs. It stays off by default because operators rely on their user servers today.
- **D-10 `mcp_servers` accepts only the role shape** (list of single-key maps), as the issue specifies. A plain map is rejected with a warning that shows the expected shape.
- **D-11 HTTP support per harness:** Claude renders `type: http` with `url` and `headers`; Codex renders `url` and `http_headers` (F-1 probe); ACP drops HTTP (existing PAN-4934 D-4 rule).
- **D-12 Remote (Fly) workspaces and container gates are out of scope.** A container gate's env reaches only the `docker exec` client, not the container. This is documented.

- No `execSync` in dashboard-reachable code; use `node:fs/promises` (NFR-4).
- Any delay-based test uses `vi.useFakeTimers()` (none are expected here).
- Quality gates before `pan done`: `npm run typecheck`, `npm run lint`, and `npx vitest run <touched test files>`. Never run the full `npm test` on the host.
- File-size ratchet: god files must not grow (NFR-5). Never raise `scripts/file-size-allowlist.txt`.
- Tests that need projects write `projects.yaml` under the test `OVERDECK_HOME` set by `tests/setup/overdeck-home.ts`, then call `invalidateProjectsConfigCache()`. Never write to the real home (`tests/setup/no-real-home-writes.ts` throws).
