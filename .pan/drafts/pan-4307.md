## Glossary

| Term | Meaning |
| --- | --- |
| **Vault engine** | `src/lib/vault/**`, shipped by PAN-2609. Standalone: it imports only Node built-ins and sibling modules (`tests/unit/lib/vault/import-graph.test.ts` fails otherwise). The dashboard may import it; it may never import the dashboard. |
| **Settlement** | One `settle()` call (`src/lib/vault/settle.ts` line 205): moves the lines a native transcript gained into the vault. First settlement of a file mints its record. Returns a `SettleResult` verdict: `noop`, `append`, `diverged`, `blocked`, `excluded`, `offline`. |
| **Sync cycle** | One `syncOnce()` call (`src/lib/vault/sync.ts` line 89): settles every owned transcript that grew, upserts this machine's `m/` ref, pulls every record into the list cache, and returns a `SyncReport` (including `machines: MachineRecord[]`). |
| **Owned transcript** | A native path present in the local index `${OVERDECK_HOME}/vault/index.json` (`listOwned()`, `src/lib/vault/local-index.ts` line 95). |
| **Managed conversation** | A row in the `conversations` table of `overdeck.db`, as returned by `listConversations()` (`src/lib/overdeck/conversations.ts` line 606). |
| **Active managed conversation** | A managed conversation with `status === 'active'` and harness `claude-code` or `codex`. |
| **Debounced settle** | A settlement run `debounceSec` (default 30, `VAULT_CONFIG_DEFAULTS` in `src/lib/vault/config.ts` line 39) after the last observed size change of a transcript. |
| **Forced settle** | `settle({ …, wip: 'force' })`: captures a WIP code snapshot even when the transcript did not grow (PAN-4329 D-1, §6). Used on session end and dashboard shutdown. |
| **Pending-deletion batch** | `${OVERDECK_HOME}/vault/eviction-batch.json`, owned by `src/lib/vault/evict.ts`. Entries are added by `scanEligible` and deleted only by `confirmEviction` (FR-20, FR-21). |
| **Fingerprint** | `batchFingerprint(batch)` (`evict.ts` line 116): a hash over every entry's `vaultId`, native path, size, settlement chunk. A confirmation must quote the current fingerprint. |
| **Deletion door** | `src/lib/cloister/transcript-deletion-door.ts` `removeTranscriptFile` (line 13). `confirmEviction` is its only caller in the vault. |
| **Vault service** | The new dashboard module `src/dashboard/server/services/vault-service.ts`: owns the sync loop, the settle queue, the status snapshot, and the eviction operations routes call. |
| **Settle poller** | The new module `src/dashboard/server/services/vault-settle-poller.ts`: detects transcript growth of active managed conversations and schedules debounced and forced settles. |
| **Peer dashboard** | A second dashboard process (workspace containers, UAT fixtures with `OVERDECK_DISABLE_DEACON=1`); `isPeerDashboardProcess()` (`src/lib/boot-gates.ts`, used at `src/dashboard/server/main.ts` line 223). Peers never run background writers. |
| **Snapshot** | `VaultServiceSnapshot`, the in-memory status the service exposes to `GET /api/vault/status`. |

## Problem

PAN-2609 shipped the vault as a standalone CLI. In Overdeck mode nothing saves conversations unless the
operator runs `pan vault save`/`sync` by hand or installs the Stop hook, nothing pulls records on a timer,
and the pending-deletion batch can be reviewed only in a terminal. The dashboard is the place an Overdeck
user looks; FR-3(a) and FR-22 put automatic settlement and the batch review there. Two facts verified during
planning shape the design:

1. **The conversation transcript watch cannot drive settlement.** `watchConversation`
   (`src/dashboard/server/services/conversation/watch.ts` line 38, re-exported by
   `services/conversation-service.ts` line 12) is started only per WebSocket subscriber inside
   `streamClaudeTranscript` (`src/dashboard/server/ws-rpc.ts` line 208, wrapped in `Effect.acquireRelease`).
   A conversation nobody is viewing has no watch. The PRD's "using the transcript watch in
   conversation-service.ts" is therefore replaced by a dedicated poller (decision D-2).
2. **`confirmEviction` can delete an entry the panel showed as failed.** It re-checks every entry of the
   batch and deletes those that now pass (`evict.ts` lines 314-352). FR-22 says entries whose copy is not
   `verified` "cannot be selected for deletion" and the button deletes "exactly the displayed entries". The
   dashboard therefore needs a `skipFailed` option (decision D-6).

## Goal

- Conversations started from the dashboard are saved to the vault automatically, 30 s after they stop
  growing, and again with a code snapshot when they end or when the dashboard shuts down.
- A sync cycle runs at dashboard boot and every `syncIntervalSec` (300 s), backs off while offline, and
  refreshes the pending-deletion batch when `evict` is on, asking Overdeck liveness before listing a
  transcript.
- Settings → Session Vault shows the vault's state, the machines that sync to it with their last-synced
  time, and the pending-deletion batch, with "Yes, delete these", decline, clear and re-offer.
- No timer, poll, sync cycle or boot step reaches the deletion door (NFR-10).

## Requirements

IDs are new to this PRD. `traces` in the xBRIEF map items to them; PAN-2609 ids are cited where they apply.

### Functional

- **FR-1** (PAN-2609 FR-3a) The dashboard settles each active managed conversation's transcript
  `debounceSec` after its last observed growth, with `wip: 'auto'`.
- **FR-2** (PAN-4329 §6) When a managed conversation the poller tracked changes from `active` to not active
  (ended, archived, or gone from the list), the dashboard settles its transcript once with `wip: 'force'`.
- **FR-3** (PAN-4329 §6) On dashboard shutdown, every transcript with a pending debounced settle, and every
  transcript of an active managed conversation, is settled once with `wip: 'force'`, bounded by a 10 s total
  budget; anything left when the budget expires is skipped and logged.
- **FR-4** (PAN-2609 FR-3) A sync cycle runs 5 s after boot, then every `syncIntervalSec`, with the engine's
  offline backoff (`createSyncLoop`, `sync.ts` line 209). The interval is re-read from config each cycle.
- **FR-5** (PAN-2609 FR-20, P-10) When `evict` is `true`, each sync cycle refreshes the batch through
  `scanEligible` with an `isLive` check that asks Overdeck: a transcript whose managed conversation's
  harness is alive, or whose agent (path under `${OVERDECK_HOME}/agents/<agentId>/`) is alive, is not
  eligible.
- **FR-6** Every vault operation the dashboard performs (debounced settle, forced settle, sync cycle,
  eviction confirm/decline/clear/re-offer) runs through one in-process promise queue, one at a time.
- **FR-7** The vault config (`readVaultConfig()`) and the vault handle (`openVaultContext()`) are resolved
  per operation, so `pan vault setup`, `join`, `rotate-key` or an `evict` change made in a terminal takes
  effect without a dashboard restart. When the vault is off, every operation is a no-op and nothing logs.
- **FR-8** `GET /api/vault/status` returns the snapshot: vault state, backend, `evict`, last sync (time,
  offline flag, counts, per-transcript errors, secret-scan blocks), and the machine list (label, whether it
  is this machine, last-synced time from `MachineRecord.updatedAt`).
- **FR-9** (PAN-2609 FR-22) `GET /api/vault/eviction-batch` returns the batch entries (title, harness,
  native path, size, verification, reason, checkedAt), the declined list, the fingerprint, the total size,
  and the count and size of `verified` entries.
- **FR-10** (PAN-2609 FR-22) `POST /api/vault/eviction-batch/confirm` with `{ fingerprint }` calls
  `confirmEviction` with `skipFailed: true` and the Overdeck `isLive`. A stale fingerprint returns 409 with
  the current fingerprint and deletes nothing.
- **FR-11** (PAN-2609 FR-23) `POST /api/vault/eviction-batch/decline` `{ vaultId }`,
  `POST /api/vault/eviction-batch/clear`, `POST /api/vault/eviction-batch/reoffer` `{ vaultId }` delegate
  to `declineEntry`, `clearBatch`, `reofferEntry`. None deletes a file.
- **FR-12** Settings → Session Vault renders FR-8 and FR-9 and offers "Yes, delete these (N files, X)",
  per-entry "Decline", "Clear batch", and per-declined-entry "Re-offer". Failed entries are shown with their
  reason and are never part of the deletion.
- **FR-13** The vault service exports a sync-report subscription (`onVaultSyncReport`) and
  `getVaultServiceSnapshot()`, so PAN-4436 can refresh browse copies after each cycle without editing the
  loop.

### Non-functional

- **NFR-1** (PAN-2609 NFR-3) All vault I/O is async; no `execSync` anywhere reachable from the dashboard;
  nothing runs on the HTTP request path except the six routes' own calls.
- **NFR-2** (PAN-2609 NFR-5) Every debounce, poll interval, sync interval, backoff and shutdown-budget test
  uses `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync` / `vi.runOnlyPendingTimersAsync`. Never real
  `setTimeout` waits.
- **NFR-3** (PAN-2609 NFR-10, AC-15) No timer, poller, sync cycle, boot step or shutdown step calls the
  deletion door. The only dashboard path to `removeTranscriptFile` is `POST /api/vault/eviction-batch/confirm`.
- **NFR-4** Background vault work runs only in the primary dashboard (`!isPeerDashboard`). The routes run
  in any dashboard.
- **NFR-5** The poller stats at most one file per active managed conversation per poll (15 s), and resolves
  a conversation's transcript path once, re-resolving only while the cached path is `null`.
- **NFR-6** A failing settle or sync logs one `console.warn('[vault] …')` line per distinct failure message
  per transcript and never throws out of a timer.
- **NFR-7** Routes follow the dashboard auth conventions: GETs call `rejectUnauthorizedDashboardRequest`
  (`src/dashboard/server/routes/dashboard-auth.ts` line 353); POSTs call
  `rejectUnsafeDashboardMutationRequest` (line 187). Native paths and titles never leave the machine except
  to the browser of an authorized dashboard session.

## Decisions (made in this document)

- **D-1 Split.** See "Scope split". Browse copies → PAN-4436; "Continue here" and the round-trip states →
  PAN-4437; first-run card → PAN-4330.
- **D-2 Growth detection is a dedicated poller, not `watchConversation`.** Reason in Problem 1. The poller
  covers active managed conversations only. Ended conversations do not grow, and owned transcripts of any
  origin (CLI `save --all`, Stop hook) are already settled by `syncOnce` step 2, which stats every owned
  path each cycle. Poll period `VAULT_POLL_MS = 15_000`, matching `ConversationDirectoryWatcher`'s default
  (`services/conversation-directory-watcher.ts` line 42). The directory watcher itself is not reused: it
  walks every `.jsonl` under the Claude projects root, which is the whole-tree cost this avoids.
- **D-3 What "live" means in Overdeck mode.** `src/lib/overdeck/conversation-liveness.ts` calls itself "the
  one liveness door for conversations" and handles Herdr and tmux; `src/lib/agents/liveness.ts` answers for
  agents. The issue named only `liveness.ts`. The dashboard `isLive(nativePath)` uses both:
  1. Claude transcript (`*.jsonl` whose basename is a UUID): `getConversationByClaudeSessionId(basename)`
     (`conversations.ts` line 640) → `conversationHarnessAlive(row.tmuxSession)` (`conversation-liveness.ts`
     line 93).
  2. Any path under `AGENTS_DIR` (`src/lib/paths.ts` line 32): the first path segment after it is the
     agent id → `isAlive(agentId)` (`liveness.ts` line 173) → `verdict.alive`.
  3. Otherwise `false`. The engine's mtime rule (`liveQuietMinutes`) still applies to every entry.
  A liveness probe that throws counts as live (never delete on uncertainty).
- **D-4 `evict.ts` gains injectable options, and stays standalone.** `ScanOptions` and `ConfirmOptions` get
  `isLive?: (nativePath: string) => Promise<boolean>`; `ConfirmOptions` gets `skipFailed?: boolean`.
  `checkEligibility` gets `isLive` as a new optional last parameter. The CLI passes neither, so its behavior
  is unchanged. `evict.ts` never imports dashboard or terminal-backend code (import-graph test).
- **D-5 The vault handle moves to the engine.** `openVault` in `src/cli/commands/vault/shared.ts` (line 85)
  mixes resolution with CLI output. Its resolution half moves to a new `src/lib/vault/open.ts`
  `openVaultContext()`, which returns a tagged result and prints nothing. The CLI `openVault` keeps its exact
  messages and exit codes and calls it. `storeForBackend`, `DIR_BACKEND_PREFIX` and the `OpenVault` type
  move too and are re-exported from `shared.ts`, so no other CLI file changes.
- **D-6 `skipFailed`.** With `skipFailed: true`, `confirmEviction` keeps every entry whose stored
  `verification` is `failed` exactly as it is (not re-checked, not deleted). The fingerprint check is
  unchanged. The next `scanEligible` re-verifies those files and turns them back into `verified` entries
  when they pass, and the operator sees them as deletable only after that. "Cannot be selected" in FR-22 is
  read as "is excluded from the button"; there are no per-entry checkboxes, since decline already removes a
  single entry.
- **D-7 One click deletes.** "Yes, delete these (N files, X)" is the confirmation. There is no second modal:
  the batch, paths, sizes and statuses are on screen, and a 409 on a changed batch prevents deleting
  something not displayed.
- **D-8 Sync cadence.** First cycle 5 s after start (`VAULT_BOOT_DELAY_MS = 5_000`), so boot-critical
  services start first; then `createSyncLoop` with the configured interval. Because `createSyncLoop` fixes
  its interval at creation, the service recreates the loop when a cycle reads a different
  `syncIntervalSec`.
- **D-9 Serialization is in-process only.** The service queue serializes dashboard operations. A terminal
  `pan vault save` can still race the dashboard: `casRef` keeps records correct, and the local index is
  last-writer-wins (hazard H-3).
- **D-10 Settle scope is by harness.** The poller settles `claude-code` and `codex` conversations only; the
  engine's materialization and turn filters support only those two (`turns.ts` `TurnHarness`).
- **D-11 Transcript path resolution.** The poller uses `resolveSessionFile` from
  `src/lib/overdeck/conversation-reads.ts` (line 120), the same resolver the messages route uses, injected
  as a dependency for tests.
- **D-12 No setup or join in the dashboard.** When the vault is off, the panel says
  `Session Vault is off. Run: pan vault setup <git-url>` (`VAULT_OFF_MESSAGE`, `config.ts` line 18) and
  links the docs. Setup and join with secrets are CLI-only until PAN-4330.
- **D-13 Routes live in one top-level file** `src/dashboard/server/routes/vault.ts`, because the no-loss
  test scans only top-level `routes/*.ts` (`tests/unit/lib/overdeck/no-loss-matrix.test.ts` lines 32-53).

### Wire contract (routes ↔ panel)

```ts
// GET /api/vault/status  → 200
interface VaultStatusResponse {
  state: 'off' | 'rotation-pending' | 'key-missing' | 'key-mismatch' | 'ready';
  running: boolean;               // false in a peer dashboard or before start
  backend: string | null;
  evict: boolean;
  lastSync: null | {
    at: string;                   // ISO
    offline: boolean;
    records: number;
    appended: number;             // settled entries with verdict 'append'
    errors: Array<{ nativePath: string; message: string }>;
    blocked: Array<{ nativePath: string; vaultId: string; hits: Array<{ line: number; pattern: string }> }>;
  };
  machines: Array<{ label: string; isThisMachine: boolean; lastSyncedAt: string }>;
}

// GET /api/vault/eviction-batch → 200
interface EvictionBatchResponse {
  evict: boolean;
  fingerprint: string;
  entries: Array<{ vaultId: string; title: string; harness: string; nativePath: string; sizeBytes: number;
                   verification: 'verified' | 'failed'; reason?: string; checkedAt: string }>;
  declined: Array<{ vaultId: string; nativePath: string; declinedAt: string }>;
  totalBytes: number;
  deletableCount: number;         // entries with verification 'verified'
  deletableBytes: number;
}

// POST /api/vault/eviction-batch/confirm { fingerprint } →
//   200 { deleted: string[]; skipped: Array<{ nativePath: string; reason: string }>; bytesFreed: number; fingerprint: string }
//   409 { error: 'The pending-deletion batch changed since it was displayed.', code: 'batch-changed', fingerprint: string }
//   400 { error: 'fingerprint is required' }
//   409 { error: <VAULT_OFF_MESSAGE or key message>, code: 'vault-unavailable' } when openVaultContext is not 'open'
// POST /api/vault/eviction-batch/decline { vaultId }  → 200 EvictionBatchResponse | 400
// POST /api/vault/eviction-batch/clear                → 200 EvictionBatchResponse
// POST /api/vault/eviction-batch/reoffer { vaultId }  → 200 EvictionBatchResponse | 400
```

`state` comes from `openVaultContext()` status (`open` → `ready`). Machine `lastSyncedAt` is
`MachineRecord.updatedAt` from the last `SyncReport.machines`; `isThisMachine` compares
`environmentId` with `ensureEnvironmentIdentity()`. The response never carries `environmentId`.

## Hazards

- **H-1** `resolveSessionFile` can search every Claude project directory on a miss. The poller caches
  non-null paths (NFR-5); a conversation whose path stays null is re-resolved each poll, so keep the list to
  active rows only.
