## Glossary

- **Machine, environment id, label:** one Overdeck server and its UUID identity (`src/lib/environment-identity.ts`). The UI says "machine"; the code says "environment".
- **Link, linking machine, linked machine:** from PAN-4645. The laptop holds a link to the desk; the laptop is the *linking* machine, the desk the *linked* machine. Links live in `${OVERDECK_HOME}/machine-links.json` (`src/lib/anywhere/link-store.ts`).
- **Owner machine:** the one machine whose harness runs a conversation and whose disk holds its live transcript. It is `conversations.environment_id` (PAN-4645 D-4645-19).
- **Viewing machine:** the machine whose dashboard the operator is using. In the examples it is the laptop.
- **Linked conversation:** a conversation whose owner is another machine, listed on the viewing machine from the cache.
- **Linked name:** the viewing machine's name for a linked conversation, `@<environmentId>/<ownerName>`, for example `@6f1c…-…/conv-20261101-1234`. It is unique across machines. The CLI also accepts `@<label>/<ownerName>`.
- **`linked_conversations`:** the new cache table on the viewing machine (D-5). The owner's answer is the only writer.
- **Shared list:** the owner's answer to `GET /api/machines/conversations`: the metadata of every local, unarchived conversation, or nothing when sharing is off.
- **Conversations hash:** first 16 hex of SHA-256 over the shared list's canonical JSON. It rides in the 15 s heartbeat, so the viewer refetches only when something changed.
- **Saved copy:** the Session Vault browse row (`origin = 'vault'`, name `vault-<id>`) of a conversation.
- **Release:** the owner's half of a pull. It sets `conversations.released_to`, settles the conversation (with uncommitted code) into a transfer store, and stops the harness. From then on the owner refuses new turns with 409 `conversation-released`.
- **Transfer store:** a temporary Session Vault `dir:` store with a fresh one-time vault key, made only for one pull. Its bytes travel inside the secure channel. No vault backend is needed when both machines are online.
- **Adopt:** the viewing machine's half of a pull. It runs the existing Continue here code (`continueHere`, `src/dashboard/server/services/vault-continue.ts:264`) against the transfer store.
- **Actor:** who a forwarded link request acts for: `operator` or `agent:<id>`, stamped in `x-overdeck-link-actor` (`src/lib/anywhere/link-actor.ts:12`).
- **Port forward:** a TCP port of the owner made reachable on the viewing machine's `127.0.0.1` through the secure channel (FR-24, D-22).
- **God file:** a `.ts`/`.tsx` file under `src/` over 1000 lines. `scripts/lint-file-size.sh` refuses any growth past its `origin/main` line count (CSS is not covered).

## Requirements

### Functional (from pan-2350, scoped to this issue)

- **FR-1 (pan-2350 FR-5) Shared list.** Once linked, the viewing machine lists every local, unarchived conversation of each linked machine with: owner name, title, native session id, harness, model, status, `sessionAlive`, `isWorking`, last activity, project key, git origin, cwd, issue id, terminal session name, `released_to`, created time and owner environment id. Sharing is on by default (D-4). The owner's **Share my conversations** switch (Settings → Anywhere → Machines) turns it off; the viewer prunes that owner's rows on the next sync. Transcript content is fetched only when a conversation is opened.
- **FR-2 (pan-2350 FR-6) One row per conversation.** The merged `GET /api/conversations` never shows two rows for one native session id. Precedence: a local row (including a released one) beats a linked row, which beats a vault copy. A linked row that has a matching vault copy carries `savedCopyName`.
- **FR-3 (pan-2350 FR-7) Remote control.** Opening a linked conversation streams its transcript live through the viewer's server. The operator can send, answer AskUserQuestion prompts, approve permissions, stop, abort, switch model, compact, and open its terminal. Images load from the owner. URLs are `/conv/@<environmentId>/<ownerName>`; local `/conv/<rowid>` URLs keep working.
- **FR-4 (pan-2350 FR-8) Pull here.** **Pull here** (and `pan conv pull <conv>`) makes this machine the owner, in five steps: ask to release (with **Wait for this turn** or **Stop it now** when a turn runs), release (settle with WIP, stop the harness, set `released_to`), transfer (through the secure channel), adopt (Continue here against the transfer store), finish (the old owner shows "Continued on <label>", read-only). If adoption fails, the release is undone and the old owner resumes. When the owner is offline, the vault saved copy is adopted through the existing compare-and-swap. Pushing back is a Pull here from the other side.
- **FR-5 (pan-2350 FR-9) Machine-aware UI.** Linked rows carry a machine chip. The title bar has the five D-6 states. An offline owner shows a banner "<label> is offline (last seen <time>)" with **Reconnect**, **Read saved copy** and **Continue here**, each only when it applies. **Hide this machine** removes a machine's rows without unlinking.
- **FR-6 (pan-2350 FR-28) Tell across machines.** `pan tell @<label>/<conv> "<message>"` delivers to the owner's conversation through the link, exactly once per message id.
- **FR-7 (pan-2350 FR-24) Preview.** **Open preview** and `pan machines forward <label> <port>` forward a TCP port of the owner to `127.0.0.1:<free port>` here, within the D-22 limits.
- **FR-8 (pan-2350 FR-30) Open in editor.** On a linked conversation, **Open in editor** launches the local editor in remote-SSH mode at the owner's checkout: `code --remote ssh-remote+<host> <cwd>`.

### Non-functional

- **NFR-1 (pan-2350 NFR-3) Owner is authority.** The viewer keeps only the `linked_conversations` read cache and never writes status for another machine's conversation. Only the owner's own answer writes cache rows.
- **NFR-2 (pan-2350 NFR-4) One runner.** At most one machine runs a conversation's harness: release-before-adopt online, vault compare-and-swap offline. No automatic undo of a release ever runs on a timer.
- **NFR-3 (pan-2350 NFR-9) Small reads.** Opening a linked conversation moves at most 1 MiB + 64 KiB over the link; returning within 10 minutes moves only rows newer than the cached sequence (the existing `resume` field, unchanged).
- **NFR-4 (pan-2350 NFR-5) Bounded idle traffic.** The shared list is fetched in full on connect and afterwards only when the heartbeat's conversations hash changes. No timer polls the list.
- **NFR-5 (pan-2350 NFR-7) Async only.** No `execSync`, no new `*Sync` tmux calls in server-reachable code.
- **NFR-6 No god-file growth.** Every god file listed above ends with a net line change ≤ 0.

## Decisions (made here; the executor does not revisit them)

- **D-4650-1 Cache, not `conversations` (pan-2350 D-5).** New table `linked_conversations` keyed `(environment_id, name)`; the merge happens at read time in the list route. `replaceLinkedConversations(environmentId, rows, hash)` runs in one transaction: upsert every row in the answer, delete that environment's rows absent from it. Rows of an environment with no active link in `linksSnapshot()` are excluded from the merge and deleted by the sync service on its next reconcile.
- **D-4650-2 Change detection by hash, not deltas.** The heartbeat gains optional `conversationsHash` (old peers omit it ⇒ the viewer fetches once per connect only). The viewer fetches `GET /api/machines/conversations` on every connect (`onDescriptor` hook) and whenever a heartbeat hash differs from the cached one. Rows are trimmed to the FR-1 fields (≈300 bytes each), so a full refetch of 500 rows is ≈150 KB.
- **D-4650-3 Linked names and row ids.** A linked row's `name` is `@<environmentId>/<ownerName>`, its `id` is the negative of its `linked_conversations` rowid (never collides with positive local rowids), `origin` is `'linked'`, and it carries `environmentId`, `remoteName`, `machineLabel`, `machineState` (`LinkState`), `machineLastSeenAt`, `savedCopyName` and `releasedTo`. Contracts export `linkedConversationName(environmentId, name)` and `parseLinkedConversationName(value)` (also accepting `@<label>/<name>` for the CLI).
- **D-4650-4 HTTP remote control by path prefix.** A global middleware on the viewing server catches `/api/conversations/@<envOrLabel>/<ownerName>[/<rest>]` (matched on the decoded pathname, so `%40…%2F…` and raw forms both work), resolves the link with `getLink`, and forwards `METHOD /api/conversations/<ownerName><rest>?<query>` through that link's `LinkAgent` with the link token and actor headers. It streams nothing; it buffers request and response bodies up to 32 MiB (413 above). Status, `content-type` and body pass back unchanged. Link errors map to 503 `{ error, code: <LinkUnavailableCode> }`. The middleware runs only for credentials the local gate already accepted; because unlisted routes default to `admin`, a machine credential arriving over a channel cannot use it (no chained hops). The owner's own scope table decides what is allowed. So every existing frontend call that builds `/api/conversations/${name}/…` works unchanged for linked rows.
- **D-4650-5 WebSocket remote control by byte pipe.** The viewing server handles upgrades on `/ws/linked/<environmentId>/rpc` and `/ws/linked/<environmentId>/terminal` itself (the `setupTerminalWebSocket` pattern, `server.ts:148`). It authorizes the browser locally with `authorizeDashboardUpgrade(headers, 'GET', 'admin', channelOfIncoming(req))`, refuses channel callers (no chained hops), opens a channel with `openLinkSocket`, writes the upgrade request for `/ws/rpc` or `/ws/terminal?<query>` with `Authorization: Bearer <link token>`, `x-overdeck-link-actor: operator`, no `Origin`, waits for the owner's `101`, relays that response head to the browser, then pipes bytes both ways and closes both sides together. The frontend uses a second RPC transport for linked conversations; the owner's restricted RPC group (PAN-4645 D-4645-14) enforces scopes.
- **D-4650-6 Actor mapping.** Browser requests are `operator`. CLI requests send `x-overdeck-sender: <senderFromEnv().id>`; the viewer maps a missing header, `conv-operator-<pid>`, or a sender that `isOperatorConversation` accepts to `operator`, and every other sender to `{ agentId: sender }` (D-6 of the local prompt guard, applied unchanged).
- **D-4650-7 Agent fence on the owner.** No conversation is started through a link in this issue (#4651 adds that), so on the owner a `machine` credential whose actor is an agent is refused with 403 `{ code: 'agent-fenced' }` on every non-GET `/api/conversations/*` route, on `/ws/terminal` and on `/ws/forward`. Reads stay allowed. One helper, `linkActorFence(credential, method, pathname)` in `src/dashboard/server/link-fence.ts`, is called from `remote-request-gate.ts` and from the two upgrade handlers. #4651 widens it for link-started conversations.
- **D-4650-8 Released guard is one helper in each lib door (pan-2350 D-8).** `conversationWriteRefusal(conv)` in `src/lib/overdeck/conversation-release.ts` returns the existing vault-browse 409 or `409 { error: 'Continued on <label>; this copy is read-only', code: 'conversation-released', releasedTo }` when `conv.releasedTo` is set, else `null`. It replaces the vault check at `conversation-runtime.ts:1082` (same line count) and is added as the first statement after the lookup in `handleConversationMessage`, `handleConversationSwitchModel`, the compact and plan-action doors in `conversation-delivery.ts`, and the kickoff door. In-process callers (scheduler, triggers, flywheel) are therefore covered. `/resume` refuses unless the release was undone (undo clears the column).
- **D-4650-9 Transfer store for online pulls.** The owner settles into a fresh `dir:` store under `${OVERDECK_HOME}/pull-transfers/<transferId>/store` with a fresh `createVaultKey()`, `wip: 'force'`. It packs the store directory into one buffer (`src/lib/vault/transfer-pack.ts`: repeated `uint32be pathLength, path (UTF-8, relative), uint32be dataLength, data`; paths with `..` or absolute paths are rejected on unpack). The release response returns `{ transferId, vaultId, keyHex, ownerEnvironmentId, harness, nativeSessionId, bytes }`; the key travels only inside the secure channel. The viewer downloads the pack, unpacks it under its own `${OVERDECK_HOME}/pull-transfers/<transferId>/store`, and calls `continueHere(vaultId, { expectedOwnerToken: ownerToken(ownerEnvironmentId), onDrift: 'note' }, { openVaultContext: async () => ({ status: 'open', vault: { config, keys: deriveSubkeys(key), store, rotatedAt: null } }), removeVaultBrowseRow: async () => {} })`. Both sides delete their transfer directory on completion, undo, or 15 minutes after creation. Pulls support the harnesses `continueHere` resumes (`claude-code`, `codex`, decided by its existing `isResumable` (`vault-continue.ts:143`), which WI-2 moves unchanged into `src/lib/vault/resumable.ts` as `isResumableHarness` so `src/lib` can use it without importing server code and `lint:harness-branches` does not grow); others get 400 `not-pullable`. Shared rows carry `pullable`, and the UI hides **Pull here** when it is false.
- **D-4650-10 Release never times out into a second runner.** Undo happens only when the viewer reports failure (`POST …/release/undo`) or the operator runs `pan conv reclaim <conv>` on the old owner. `reclaim` asks the target machine (if online) whether it lists a live, unreleased conversation with the same native session id; if yes it refuses with `still-running-there`; if the target is offline it refuses with `target-offline` unless `--force`.
- **D-4650-11 Wait for a turn.** "Turn running" means the owner's enrichment reports `isWorking` (`conversation-list.ts:227-252`). With `whenTurnRunning: 'stop'` the owner calls `handleConversationAbort(name)` first. With `'wait'` it polls every 2 s up to 30 minutes, then answers 409 `turn-still-running`. The viewer's link request for release uses a 31-minute timeout. Tests use fake timers.
- **D-4650-12 Pull is a job.** `POST /api/linked-conversations/pull { conversation: '@env/name', whenTurnRunning }` answers 202 `{ pullId }`; `GET /api/linked-conversations/pull/:pullId` answers `{ step: 'release' | 'transfer' | 'adopt' | 'finish', state: 'running' | 'done' | 'failed', error?, conversation?: { id, name } }`. Jobs live in memory for 1 hour. The UI polls every 1 s; `pan conv pull` polls and prints each step.
- **D-4650-13 Offline pull = vault Continue here.** When the owner's link is not `online`, Pull here uses the matching vault copy (`savedCopyName`): it calls the existing `previewContinue` + `continueHere` for that vault id. ## Intersecting repo rules (restated)

- Dashboard runs Node 22 from `dist/` only; run `npm run build` before restarting it. Never Bun or tsx.
- No `execSync` in server-reachable code; async tmux primitives only.
- Every retry, wait, back-off, idle-timeout or poll test uses `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`.
- A new HTTP route needs a row in `tests/unit/lib/overdeck/no-loss-matrix.ts` and, unless it is admin-only, in `src/dashboard/server/route-scopes.ts`.
- Changing a `pan` verb's flags or help needs the matching `sync-sources/skills/pan-<verb>/SKILL.md` edit in the same commit (`scripts/lint-skills.sh`).
- God files must not grow (`scripts/lint-file-size.sh`); extract a module instead; never raise an allowlist cap.
- New must-run frontend tests go into `scripts/frontend-test-subset.txt` in sorted position.
- JSONL transcripts are never deleted or truncated; a pull copies and never removes the old owner's file. Never send a destructive HTTP request speculatively.
- Agent state rows only after the terminal-backend session exists (no placeholder rows).
- `src/lib/vault/**` stays importable without the dashboard, Effect or terminal backends.
- Quality gates before `pan done`: `npm run typecheck`, `npm run lint`, `npx vitest run <touched tests>`; never the full `npm test` on the host.
- Browser verification uses an isolated Playwright context; never another agent's session.
