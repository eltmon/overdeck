# PAN-4528: New-conversation Skills field — skill descriptions and collapsible groups

**Issue:** [PAN-4528](https://github.com/eltmon/overdeck/issues/4528)
**Planned:** 2026-10-04, `pan plan --auto` (no operator questions; every inferred choice is listed under "Decisions").

## Glossary

- **New-conversation dialog** — the "New conversation with options…" dialog (caret beside the Command Deck `+`, or the command palette; PAN-4486). Component: `src/dashboard/frontend/src/components/newConversation/NewConversationDialog.tsx`.
- **Skills field** — the dialog's per-conversation skill choices. Component: `src/dashboard/frontend/src/components/newConversation/ConversationSkillsField.tsx`. Each row offers **Inherit / On / Off**; only On/Off choices reach the dialog's `skillOverrides` value.
- **Row choice** — an explicit On or Off the operator set in this dialog for one row (a key present in the field's `value` prop). Inherit removes the key.
- **Skill catalog** — `listSkillCatalog()` in `src/lib/skill-overrides/catalog.ts`: every directory holding a `SKILL.md` under the skill roots, deduped by name, first root wins.
- **Skill root** — one of the four directories the catalog reads, in this order: `~/.overdeck/skills`, `~/.claude/skills`, `~/.agents/skills`, `<projectRoot>/.pan/skills` (the last only when a project is in context).
- **Origin** (new) — which kind of root a catalog entry came from: `overdeck` (`~/.overdeck/skills`), `personal` (`~/.claude/skills` or `~/.agents/skills`), `project` (`<projectRoot>/.pan/skills`). Because the first root wins, a name present in several roots takes the origin of the first.
- **Source** (existing, NOT the same as origin) — the override level that decided a skill's resolved on/off state: `core`, `global`, `project`, `issue`, `conversation`, `default` (and `*-pack` for pack skills). A skill can have `source: 'project'` (a project-level override) while its `origin` is `overdeck`. **Never group by `source`.**
- **Pack skill** — a skill from a registered skill pack (PAN-4334), id `pack/skill` (e.g. `mattpocock/tdd`), returned under `packs[].skills[]`.
- **Group** — one collapsible section of the Skills field: "Project skills", "Overdeck", "Personal", then one per pack (header = the pack id, e.g. "mattpocock").
- **Description** — the first line of the SKILL.md frontmatter `description` (`parseSkillDescription`, `catalog.ts:29-31`); `''` when absent.

## Problem

The Skills field lists ~237 skills as one flat list of bare names. The operator cannot tell what `mattpocock/wayfinder` or `hyperframes-core` does without leaving the dialog, and the filter matches names only. The descriptions are already in `GET /api/skills/overrides`; the field drops them. The catalog also loses which root a skill came from, so there is nothing to group by.

## Requirements

- **FR-1** Every `SkillCatalogEntry` carries `origin: 'overdeck' | 'personal' | 'project'`: `~/.overdeck/skills` → `overdeck`; `~/.claude/skills` and `~/.agents/skills` → `personal`; `<projectRoot>/.pan/skills` → `project`. First root wins, as today. `projectSkill` stays, unchanged in meaning.
- **FR-2** `GET /api/skills/overrides` returns `origin` on every `skills[]` entry (via `SkillState.origin`).
- **FR-3** Each Skills-field row shows its description as one truncated muted line under the name; the description element's `title` attribute holds the full description text. Rows with an empty description show no description line. Applies to native and pack skills.
- **FR-4** The Skills-field filter matches a row when its id **or** its description contains the filter text (case-insensitive, trimmed). Placeholder: `Filter skills by name or description`. The `aria-label` stays `Filter skills`.
- **FR-5** Rows are grouped into sections in this order: **Project skills** (origin `project`), **Overdeck** (origin `overdeck`), **Personal** (origin `personal`), then one section per pack in the response's `packs[]` order, labelled with the pack id. Rows inside a group are sorted by id. A group with no rows is never rendered.
- **FR-6** Each group header is a button with `aria-expanded`, a chevron, the label, and a count `<on> on · <total>`, where `<total>` is the number of rows in the group and `<on>` is the number of those rows whose effective state is on (the row choice if set, else the inherited `enabled`). Counts always cover the whole group, also while filtering.
- **FR-7** With an empty filter, a group starts collapsed unless it holds a row choice, in which case it starts expanded. Clicking a header toggles that group. Setting any row choice in a group (including back to Inherit) pins that group open, so it does not collapse under the operator's cursor.
- **FR-8** With a non-empty filter, only groups with at least one matching row render; each renders expanded, showing only its matching rows; headers are disabled (no toggle) while filtering. Clearing the filter restores each group's previous open/closed state. When no row matches at all, the field shows `No skills match.` (as today).
- **FR-9** `docs/CONTEXT-LAYERS.md` documents the Skills field: row contents, description tooltip, filter scope, the group order with each group's root directories, first-root-wins, the collapse rules, and the header count.
- **NFR-1** No group-level Inherit/On/Off control; per-row choices, the emitted `value`, the issue-fallback fetch (D8), and the "drop choices for unlisted skills" effect behave exactly as today.
- **NFR-2** No new HTTP route, no request-shape change; the response change is additive. `SkillOverridesPanel.tsx` (Settings) is not modified.
- **NFR-3** Styling follows `pan-style-guide`: muted text for descriptions and counts, no pill badges, no decorative color; CSS-module classes only in `ConversationSkillsField.module.css`.

## Decisions (made here; auto mode)

1. **`origin` is a required field** on `SkillCatalogEntry` and `SkillState`. The only producer is `readRoot`; required typing makes every producer set it. Test fixtures that build entries by hand add it.
2. **Missing `origin` in a response falls back to `personal`** in the frontend. The dashboard frontend and server ship together, but a fixture or a mid-reload server can omit the field; without a fallback the row would silently fall into no group and disappear. One expression, no other defensive code.
3. **Header count = effective on-count over the whole group** (FR-6), not the filtered subset — a stable number that does not jump while typing.
4. **Open state model:** `const [opened, setOpened] = useState<Record<string, boolean>>({})`; a group is open when `filtering || (opened[key] ?? groupHasChoice)`. Header click sets `opened[key] = !currentlyOpen`. A row choice sets `opened[groupKey] = true`. This satisfies FR-7 and FR-8 and keeps a group from collapsing when its last choice returns to Inherit.
5. **Headers are disabled while filtering** (FR-8): the filter owns expansion then; this avoids a toggle with no visible effect.
6. **Pack rows keep displaying their full id** (`mattpocock/tdd`) and keep `aria-label={row.id}` on the radiogroup, so existing tests and accessibility names stay stable.
7. **`.list` max-height stays 220px.** Collapsed groups make the list short by default; resizing the dialog is out of scope.
8. **No new module or test file.** Grouping logic lives in `ConversationSkillsField.tsx`; tests extend `ConversationSkillsField.test.tsx`. This avoids editing the CI frontend subset list.
9. **Docs go in `docs/CONTEXT-LAYERS.md`** as a new section directly after "Bare conversations", because no page covers the field and that section is where the dialog is introduced (the issue's stated fallback).
