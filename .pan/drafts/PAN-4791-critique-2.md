## blocks-the-design: Create failure can leave only a volume

The PRD itself notes that a durable volume survives when `createMachine` fails ([.pan/drafts/PAN-4791.md](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4791/.pan/drafts/PAN-4791.md), line 18), but FR-2 and AC-2 say every create-step failure leaves a machine discoverable with `fly machines list` (lines 43 and 134). WI-1 step 2 would put that false claim in the quick-start text. In [fly-provider.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4791/src/lib/remote/fly-provider.ts), lines 221–235 create or reuse the volume before `api.createMachine` at line 255. If that call rejects before creating a machine, `createRemoteWorkspace` never enters its rollback block ([remote-workspace.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-4791/src/lib/remote-workspace.ts), lines 164–169), so the volume remains and the proposed machine-list/destroy path finds nothing. The existing provider already reuses an unattached named volume on retry (fly-provider.ts, lines 222–235); no new recovery mechanism is needed. Change FR-2, WI-1 step 2, and AC-2 to say a machine **may** remain, require checking `fly volumes list -a <app>` for a durable volume even when no machine is listed, and make manual machine destruction conditional on finding one.
