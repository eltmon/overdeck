# PAN-4446: Overdeck Anywhere — set up, join, unlock and sync the Session Vault from the dashboard

**Issue:** [PAN-4446](https://github.com/eltmon/overdeck/issues/4446) · **Epic:** [PAN-2350](https://github.com/eltmon/overdeck/issues/2350) · **Split from:** [PAN-4445](https://github.com/eltmon/overdeck/issues/4445) (design input: `.pan/drafts/PAN-4445.md`, section "Sibling scope: Session Vault from the dashboard") · **Blocked by:** [PAN-4307](https://github.com/eltmon/overdeck/issues/4307) — **merged** as `5d500fb0d53` (#4444), so the blocker is gone · **Planned:** 2026-10-01 (auto mode) against `8a82dad552b`

## Summary

An operator can set up a Session Vault on a git remote, join it from a second machine with the passphrase or the recovery phrase, unlock a machine whose key is missing or retired, and run "Sync now" — all from Settings → Session Vault, with no terminal step. The CLI verbs `pan vault setup` and `pan vault join` keep their exact output and exit codes. Both callers run the same new core functions in `src/lib/vault/setup-core.ts` and `src/lib/vault/join-core.ts`, which print nothing and return typed results.

## Glossary

- **Session Vault** — Overdeck's encrypted cross-machine conversation backup (`src/lib/vault/`, `docs/SESSION-VAULT.md`). A *backend* is a git remote URL or a `dir:<path>` local directory.
- **Vault key** — the 32-byte secret in `${OVERDECK_HOME}/vault/key`. **Recovery phrase** — the same key as 24 BIP-39 words (`keyToPhrase()` / `phraseToKey()` in `src/lib/vault/identity.ts`). It is shown once, at setup.
- **Passphrase** / **keywrap** — PAN-4328: the key wrapped under a passphrase with scrypt and stored on the backend as the object `keywrap/v1` (`KEYWRAP_OBJECT_NAME`). A new machine can join with the passphrase instead of the 24 words. `generatePassphrase()` returns 6 EFF words; `checkPassphraseStrength()` requires 16+ characters and rejects common/repetitive ones (`src/lib/vault/keywrap.ts`).
- **Vault state** — `openVaultContext()` (`src/lib/vault/open.ts`, line 58) returns `off` (no backend configured), `rotation-pending` (`key.next` exists), `key-missing`, `key-mismatch` (the key does not open the header; it was retired by a rotation elsewhere), or `open`. `GET /api/vault/status` reports `open` as `ready`.
- **Unlock** — joining an existing vault on a machine whose backend is configured but whose state is `key-missing` or `key-mismatch`. It is the same operation as join, with the URL taken from the configured backend. There is no lock action and no `pan vault unlock` verb.
- **Core** — a function under `src/lib/vault/` that performs a vault operation, prints nothing, never exits the process, and returns a tagged result. `openVaultContext()` (PAN-4307 D-5) is the precedent.
- **Prompt callback** — a function parameter a core calls at the exact point where the CLI prompts the user today. The CLI passes a callback that prints and prompts; the dashboard passes a plain value instead.
- **Vault service** — `src/dashboard/server/services/vault-service.ts`: one in-process promise queue (`enqueueVaultOperation`, line 131) for every vault operation the dashboard performs, the background sync loop, and the status snapshot.
- **Primary / peer dashboard** — only the primary dashboard calls `startVaultService()` (`src/dashboard/server/main.ts`, line 571–574). A peer (isolated test dashboards) does not, unless `OVERDECK_VAULT_IN_PEER=1` is set.
- **Credential kind** — what `resolveDashboardCredential()` (`src/dashboard/server/routes/dashboard-auth.ts`, line 162) returns: `internal-token` (CLI and pipeline agents), `root-session` (the operator's browser on this machine), `device` (a paired device, `odk_` token), `token` (a scoped API token, Bearer only).
- **No-loss matrix** — `tests/unit/lib/overdeck/no-loss-matrix.ts`; every HTTP route needs a row or CI fails.

## Decisions (made in this document)

- **D-1 Cores take prompt callbacks.** Both verbs prompt mid-flow (setup after printing the phrase; join after learning whether a keywrap exists). So each core takes either a resolved value (dashboard) or a callback the core calls at exactly that point (CLI). This keeps every CLI line in its current order. Plain input→result signatures would force the CLI to reorder its output.
- **D-2 Cores own the state changes and their cleanups.** Opening/cloning the store, saving or forgetting the key, removing a clone the operation created, the header check, `discardUnpublished`, `clearNextKey`, `writeVaultConfig` and `syncOnce` all move into the cores. CLI-only behavior stays in the wrappers: flag-conflict checks, reading `--passphrase-file`/`--phrase-file`, `--passphrase-file` strength validation, TTY prompts, `--hooks`, and every `io.out`/`io.err`/`io.exit`.
- **D-3 Core error messages are the CLI's exact strings.** The CLI wrapper prints `result.message` to stderr and exits 1. The dashboard UI rewrites only the codes whose CLI text says "Run: pan vault …" (D-9).
- **D-4 Join keeps its check order.** Today join checks "other backend" before the flag conflict. The wrapper keeps that order by reading `readVaultConfig()` and printing the other-backend message itself before the flag check; the core repeats the other-backend check (cheap, and the dashboard needs it).
- **D-5 "Suggested passphrase" means the server generates it.** The setup body sends `{ mode: 'generate' }`; the server generates the passphrase, wraps the key, and returns it once in the setup response next to the recovery phrase. There is no `GET /api/vault/passphrase-suggestion` route (dropped from the PAN-4445 sibling sketch): the passphrase crosses the wire once instead of twice.
- **D-6 Sync now needs the running vault service.** `POST /api/vault/sync` returns 409 `{ code: 'sync-not-running' }` when `startVaultService()` has not run (a peer dashboard), and the UI shows "Sync now" only when `status.running` is true. This keeps PAN-4307 NFR-4 (a peer never advances the vault). The Playwright fixture sets `OVERDECK_VAULT_IN_PEER=1`, the existing precedent.
- **D-7 Setup and join run through the vault-service queue** (`enqueueVaultOperation('setup' | 'join', …)`), so they never race a sync cycle, a settle or an eviction confirm. They run whether or not the service is started.
- **D-8 Who may call the new routes.** Credential kinds `root-session` and `device` only. `internal-token` and `token` get 403 with no side effect. The kind check runs after `rejectUnsafeDashboardMutationRequest`, so a device cookie still faces the Origin and CSRF checks. Devices also need the `admin` scope, which `route-scopes.ts` already requires by default for unlisted routes; no row is added there.
- **D-9 UI copy for error codes.** `foreign-vault` and `race-lost` (setup) render "This remote already holds a vault. Use “Join an existing vault” below." `not-a-vault` (join) renders "This remote is not a Session Vault yet. Use “Set up a new vault” above." Every other error renders the server's `message`.
- **D-10 Auto-sync settings link to the docs.** No dashboard control exists, so the section shows one line: "Sync runs automatically every few minutes in the primary dashboard. Change the interval in the docs: Session Vault configuration." linking `https://overdeck.ai/configuration/session-vault#save-and-sync`.
- **D-11 Secrets never persist outside the response.** The recovery phrase and a generated passphrase are returned once with `Cache-Control: no-store`, never written to an activity entry, log line or error message, and held in React component state only (never the react-query cache, a toast, `localStorage` or the URL).
- **D-12 `dir:` backends are accepted from the dashboard.** They are a documented backend; a caller that may set up a vault already has `admin`. URL input is validated: a non-empty string of at most 2048 characters, no control characters, not starting with `-`.
- **D-13 Two new component files.** `SessionVaultSetupForm.tsx` (setup form plus the shown-once dialog) and `SessionVaultJoinForm.tsx` (join and unlock). `SessionVaultSection.tsx` only mounts them and adds "Sync now".
- **D-14 HTTP status for refused operations.** Body validation errors → 400. A core `{ status: 'error' }` → 422 with `{ code, message }`. Sync-not-running → 409. An unexpected throw → 500 `{ error: message }` (message only, never a secret).

### WI-1 `setupVault()` core (FR-1, D-1, D-2, D-3)

Create `src/lib/vault/setup-core.ts`. Move `openOrInitStore` (setup.ts 41–56) and the state-changing body of `setupCommand` (75–132 plus the passphrase wrap at 184–190) into it. Move `KEY_LOSS_WARNING` here too and re-export it from `setup.ts`.

```ts
export type SetupPassphrase = { mode: 'generate' } | { mode: 'custom'; value: string } | { mode: 'none' };

export interface SetupCreated { recoveryPhrase: string; machine: { label: string; environmentId: string }; backend: string }

export interface SetupVaultInput {
  url: string;
  /**
   * A value (dashboard), or a callback (CLI) called once, only when a new key was
   * created, after the vault is live and before the keywrap is stored.
   * A direct `custom` value is strength-checked before anything is created;
   * a callback's `custom` value is trusted (the CLI validated it).
   */
  passphrase: SetupPassphrase | ((created: SetupCreated) => Promise<SetupPassphrase>);
}

export type SetupVaultResult =
  | {
      status: 'created';
      backend: string;
      machine: { label: string; environmentId: string };
      /** Null when an existing key file was reused (no phrase is shown, no passphrase offered). */
      recoveryPhrase: string | null;
      passphrase: { stored: true; generated: string | null } | { stored: false; error: string | null };
    }
  | { status: 'already-set-up'; backend: string }
  | { status: 'error'; code: SetupErrorCode; message: string };

export type SetupErrorCode = 'weak-passphrase' | 'other-backend' | 'unreachable' | 'store-error' | 'foreign-vault' | 'race-lost';
```

Steps, in this order:
1. If `passphrase` is a direct `{ mode: 'custom' }`, run `checkPassphraseStrength(value)`; on failure return `weak-passphrase` with `strength.message`. Nothing is created.
2. `readVaultConfig()`. `config.backend && config.backend !== url` → `other-backend`, message exactly `Session Vault is already enabled with backend ${config.backend}. Run pan vault status, or remove that backend from vault/config.json first.`
3. `loadVaultKey()`. `config.backend === url && existingKey` → `{ status: 'already-set-up', backend: url }`. Do not call `ensureEnvironmentIdentity()` here: setup.ts line 82 never reads the identity on this path, so a corrupt `environment-id.json` must not start failing it.
4. `openOrInitStore(url)`: `VaultOfflineError` → `unreachable`, message `Could not reach ${url}: ${error.message}`; any other error → `store-error`, message `error.message`.
5. Save a new key before the header write; header check and CAS exactly as setup.ts 103–127, with the same cleanups. Messages: `foreign-vault` → `${url} is already a vault protected by another key. Run: pan vault join ${url}`; `race-lost` → `Another machine initialized ${url} first. Run: pan vault join ${url}`.
6. `ensureEnvironmentIdentity()`, `writeVaultConfig({ backend: url })`, `syncOnce({ store, keys })`.
7. Existing key reused → return `created` with `recoveryPhrase: null`, `passphrase: { stored: false, error: null }`. Do not call the callback.
8. New key: resolve the passphrase (call the callback with `{ recoveryPhrase: keyToPhrase(key), machine, backend: url }` if it is a function). `generate` → `generatePassphrase()`. `none` → `{ stored: false, error: null }`. Otherwise `store.putSlot(KEYWRAP_OBJECT_NAME, await wrapVaultKey(key, chosen))`; a `VaultOfflineError` → `{ stored: false, error: error.message }` (any other error rethrows, as today). Success → `{ stored: true, generated: <the generated value, or null for custom> }`.

Tests — new `tests/unit/lib/vault/setup-core.test.ts`, using the `Fixture`/`git` helpers in `tests/unit/cli/vault/helpers.ts` and a bare git remote:
- `created` on an empty bare remote returns a 24-word `recoveryPhrase` and writes `vault/key` and `vault/config.json`.
- `{ mode: 'generate' }` returns a 6-word `generated` value and the remote holds `objects/keywrap/v1`.
- A direct 12-character `custom` value returns `weak-passphrase` and creates no `vault/key` and no commit on the remote.
- A remote that is already a vault for another key returns `foreign-vault` and leaves no `vault/key` and no clone directory.
- The callback receives the same phrase the result returns, and is not called when a key file existed.

### WI-2 `joinVault()` core (FR-2, D-1, D-2, D-3)

Create `src/lib/vault/join-core.ts`. Move `PHRASE_MISMATCH_MESSAGE` and `PASSPHRASE_KEY_RETIRED_MESSAGE` here and re-export both from `join.ts` (tests import them from `join.ts`).

```ts
export type JoinSecret = { kind: 'passphrase'; value: string } | { kind: 'phrase'; value: string };
export type KeywrapState = 'present' | 'absent' | 'unreadable';

export interface JoinVaultInput {
  url: string;
  /**
   * A value (dashboard; a phrase is parsed before any backend access), or a callback
   * (CLI) called after the store is open, with the keywrap state. The callback may
   * return `{ kind: 'fail', message }` to stop; the core then removes a clone it created.
   */
  secret: JoinSecret | ((keywrap: KeywrapState) => Promise<JoinSecret | { kind: 'fail'; message: string }>);
}

export type JoinVaultResult =
  | { status: 'joined'; backend: string; machine: { label: string; environmentId: string }; records: number; offline: boolean; via: 'passphrase' | 'phrase' }
  | { status: 'error'; code: JoinErrorCode; message: string };

export type JoinErrorCode =
  | 'other-backend' | 'bad-phrase' | 'unreachable' | 'store-error' | 'no-passphrase' | 'keywrap-unreadable'
  | 'wrong-passphrase' | 'not-a-vault' | 'key-retired' | 'phrase-mismatch' | 'aborted';
```

Steps, in this order (mirroring join.ts 77–165):
1. `readVaultConfig()`; other backend → `other-backend`, message `Session Vault is already enabled with backend ${config.backend}.`
2. A direct `phrase` secret: `phraseToKey(value)`; a throw → `bad-phrase` with the thrown message, before any backend access.
3. Open or clone the store exactly as join.ts 97–113 (`unreachable` / `store-error` with the same messages). Track `createdClone`. Every later error path removes a clone this call created.
4. Refresh an existing git clone, ignoring `VaultOfflineError` (join.ts 120–125).
5. Unless step 2 produced a key: read the keywrap object. Classify it as `absent` (no object), `unreadable` (`parseKeywrap` throws `KeywrapFormatError`) or `present`.
   - Callback: call it with that state. `{ kind: 'fail' }` → `aborted` with its message. A `phrase` → `phraseToKey` (`bad-phrase` on throw). A `passphrase` → `unwrapVaultKey(wrapped, value)`; null → `wrong-passphrase` (`PASSPHRASE_MISMATCH_MESSAGE`).
   - Direct `passphrase`: `absent` → `no-passphrase`, message `This vault has no passphrase set. Use the recovery phrase.`; `unreadable` → `keywrap-unreadable` (`KEYWRAP_UNREADABLE_MESSAGE`); `present` → unwrap as above.
   - A wrong passphrase returns before any read other than the keywrap (tested invariant).
6. Header check (join.ts 142–154): no header → `not-a-vault`, message `${url} is not a Session Vault yet. Run: pan vault setup ${url}`; mismatch → `key-retired` (`PASSPHRASE_KEY_RETIRED_MESSAGE`) when the key came from a passphrase, else `phrase-mismatch` (`PHRASE_MISMATCH_MESSAGE`).
7. `discardUnpublished()`, `saveVaultKey(key)`, `clearNextKey()`, `writeVaultConfig({ backend: url })`, `ensureEnvironmentIdentity()`, `syncOnce({ store, keys })` → `joined` with `records: report.records`, `offline: report.offline`.

Tests — new `tests/unit/lib/vault/join-core.test.ts` (bare git remote set up through `setupVault`):
- A direct passphrase joins: `status: 'joined'`, `via: 'passphrase'`, `vault/key` written.
- A direct wrong passphrase returns `wrong-passphrase`, writes no `vault/key`, and leaves no clone directory.
- A direct passphrase against a vault with no keywrap returns `no-passphrase`.
- A direct malformed phrase returns `bad-phrase` and creates no clone directory.
- A callback returning `{ kind: 'fail', message: 'x' }` returns `aborted` with message `x` and removes the clone it created.
