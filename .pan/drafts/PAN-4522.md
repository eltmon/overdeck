# PAN-4522 — Dashboard restart wipes every agent's live activity stamp

**Issue:** [PAN-4522](https://github.com/eltmon/overdeck/issues/4522)
**Planned:** 2026-10-04 (auto mode, `pan plan --auto`)

## Glossary

- **Read model** — the server's in-memory projection of dashboard state,
  `ReadModelServiceLive` in `src/dashboard/server/read-model.ts`. It is built once
  at boot and then kept current by applying every appended domain event through the
  shared reducer `applyEvent` (`packages/contracts/src/event-reducers.ts`).
- **Runtime map** — `agentRuntimeById: Record<agentId, AgentRuntimeSnapshot>` in the
  read model. Each entry holds the event-driven state of one agent: `activity`,
  `currentTool`, `thinking`, `waiting`, `model`, `claudeSessionId`, and
  `lastActivity` (the timestamp of the last runtime event that touched it) plus
  `updatedAtSequence`.
- **Runtime event** — any domain event whose reducer case writes `agentRuntimeById`.
  The full set (verified against `event-reducers.ts` on 2026-10-04):
  `agent.activity_changed`, `agent.thinking_started`, `agent.thinking_stopped`,
  `agent.waiting_started`, `agent.waiting_cleared`, `agent.message_received`,
  `agent.channel_reply`, `agent.model_set`, `agent.current_issue_set`,
  `agent.context_saturation_changed`, `agent.resolution_changed`,
  `agent.state_restored`, `agent.stopped`, `agent.heartbeat_dead`.
- **Event store** — the append-only SQLite `events` table in `~/.overdeck/overdeck.db`
  (`src/dashboard/server/event-store.ts`). `sequence` is `INTEGER PRIMARY KEY
  AUTOINCREMENT`, so it is monotonic across dashboard restarts. Rows older than 7
  days are compacted at startup.
- **Snapshot** — the `DashboardSnapshot` a client receives on connect/reconnect via
  the `getSnapshot` RPC. The browser applies it with `syncSnapshot`
  (`packages/contracts/src/event-reducers.ts`, wrapped by
  `src/dashboard/frontend/src/lib/store.ts`).
- **Effective stamp** — `effectiveStamp()` in
  `src/dashboard/frontend/src/components/GodView/confluence/useConfluenceData.ts`:
  the fresher of the runtime entry's `lastActivity` and the agent row's
  `lastActivity ?? startedAt`. The God View classifies an orb `stale` when the
  issue's newest effective stamp is at least `STALE_AFTER_MS` (30 min,
  `GodView/confluence/model.ts` line 164) old.
- **Boot seed** — the new step this issue adds: at read-model boot, replay every
  retained runtime event of each agent in `agentsById`, per agent, through the shared
  reducer into `agentRuntimeById`.

## Problem

On 2026-10-04 at ~03:34 UTC, about 20 s after `pan reload` put a new build live,
PAN-4256, PAN-4260 and PAN-4508 were drawn `❄ 1h idle` in the God View doldrums while
each work agent was writing its transcript every minute. They thawed at each agent's
next `agent.activity_changed`.

Root cause, verified in code on 2026-10-04:

1. **The read model boots with an empty runtime map.** `read-model.ts` lines
   501-507 (search for `...INITIAL_READ_MODEL_STATE,` inside the bootstrap
   `Effect.gen`):

   ```ts
   state = {
     ...INITIAL_READ_MODEL_STATE,
     sequence,
     agentsById,
     issuesRaw: [],
     recentActivity,
   };
   ```

   `INITIAL_READ_MODEL_STATE.agentRuntimeById` is `{}` (`event-reducers.ts` line
   150). No runtime event is replayed, so the first snapshot serves `{}`.
2. **The client replaces its runtime map wholesale on snapshot.**
   `event-reducers.ts` line 337 (search `agentRuntimeById: snapshot.agentRuntimeById ?? state.agentRuntimeById`).
   A `{}` from the freshly booted server wipes every live stamp the browser held.
3. **The fallback stamp is old.** With no runtime entry, `effectiveStamp` falls back
   to `agent.lastActivity ?? agent.startedAt`. For a claude-code agent that is the
   `state.json` `lastActivity`, which `markAgentRunning` (`src/lib/agents/agent-state.ts`
   line 834) writes once at spawn. `agent-pan-4256`'s `state.json` had
   `"lastActivity": "2026-10-04T02:22:58.009Z"` → 71 min ≥ 30 min → `stale`.

The `AgentStateService` (`src/dashboard/server/services/agent-state-service.ts`)
keeps its own runtime map seeded from the pane inventory; the read model does not
read it, and its seed stamps `lastActivity` with `pane.stateSince`, not the last
event. It is not part of this fix.

## Requirements

- **FR-1** At read-model boot, `agentRuntimeById` is seeded for every agent in
  `agentsById` that has at least one retained runtime event. Each seeded entry
  equals the result of replaying ALL of that agent's retained runtime events through
  the shared reducer in ascending `sequence` order (identical to a full replay of the
  runtime map for that agent).
- **FR-2** The boot seed changes only `agentRuntimeById`. It never changes
  `agentsById` (status, `lastActivity`, liveness flags), `agentIdBySessionId`,
  `turnDiffSummariesByAgentId`, or permission maps.
- **FR-3** The event store exposes `queryRuntimeHistory(types, agentIds)`: every row
  whose `type` is in `types` and whose `payload.agentId` is in `agentIds`, ordered by
  `sequence` ascending. Empty `types` or empty `agentIds` returns `[]`.
- **FR-4** `syncSnapshot` merges the snapshot's runtime map per agent. For an agent
  in both maps, the client entry is kept when its `lastActivity` is strictly newer
  than the snapshot entry's, or when both `lastActivity` values are equal and the
  client's `updatedAtSequence` is strictly greater (both finite). Otherwise the
  snapshot entry wins. An agent present only in the client map keeps its client
  entry. An agent present only in the snapshot takes the snapshot entry.
- **FR-5** `syncSnapshot` rebuilds `agentIdBySessionId` from the merged runtime map
  (not only from the snapshot's map).
- **FR-6** The God View keeps an orb `active` across a snapshot from a freshly
  restarted server when the client already held a recent runtime stamp for the
  agent.
- **FR-7** `docs/DASHBOARD-ARCHITECTURE.md` states the boot seed and the per-agent
  snapshot merge.
- **NFR-1** The boot seed is synchronous and inline in the bootstrap (not forked),
  so the first `getSnapshot` already carries it. Measured on the live 500 MB
  `overdeck.db` on 2026-10-04: 199,106 retained runtime rows (7 days, 33 MB of
  payload; 136k of them belong to `agent-`/`planning-`/`strike-` ids). SQL read
  0.3 s; JSON parse plus per-agent fold of all rows 0.6 s in a Node benchmark. The
  seed logs `[ReadModel] Seeded <n> runtime entries from <m> events in <ms> ms`.
- **NFR-2** A failure of the seed query or fold is caught and logged
  (`[ReadModel] Failed to seed the runtime map:`); boot continues with `{}` and keeps
  `sequence` and `recentActivity`.
- **NFR-3** `packages/contracts/src/event-reducers.ts` is 1,670 lines, above the
  1,000-line ceiling of `scripts/lint-file-size.sh`, and has no allowlist row, so it
  must not grow past its `origin/main` line count. Never raise an allowlist cap.

## Decisions

- **D1 — Seed source is the event store, not `AgentStateService`.** The pane-inventory
  seed stamps `lastActivity` with `pane.stateSince`, which for a pane that has been
  `working` for an hour is an hour old — the same bug. The event store holds each
  agent's real last runtime event (7-day retention).
- **D2 — Replay each agent's full retained runtime history, not the latest event per
  type.** Several reducer cases are not last-writer-wins: `agent.model_set` keeps the
  previous `sessionModel`/`sessionHarness`/`claudeSessionId` when the event omits
  them; `agent.message_received` and `agent.activity_changed` keep or clear
  `channelReply` depending on direction/activity; `agent.channel_reply` keeps the
  previous `resolution` for other reply kinds. Dropping intermediate events changes
  the result (see Critique response). Full replay is exact and its measured cost is
  under one second (NFR-1). The SQL filters by agent id so rows of conversations and
  other ids not in `agentsById` are never parsed.
- **D3 — Fold each agent against its own scratch state.** For each agent, the fold
  runs on `{ ...INITIAL_READ_MODEL_STATE, agentsById: { [id]: agentsById[id] },
  agentRuntimeById: {} }` and only `.agentRuntimeById[id]` is kept. Reasons:
  `agent.stopped` and `agent.heartbeat_dead` also rewrite `agentsById` (status
  `stopped` / `error`), and the later `agent.status_changed` from a resume is not a
  runtime event. Applying them to the real boot state would serve a resumed agent as
  `error` (`deriveServedAgentStatuses` passes stored `stopped`/`error` through). The
  agent's own row must be in the scratch `agentsById` because `agent.heartbeat_dead`
  returns early when `agentsById[agentId]` is absent. Every runtime reducer case
  reads only `agentRuntimeById[agentId]` and `agentsById[agentId]` of its own agent,
  so a per-agent scratch state gives the same entry as one shared replay, while each
  step copies a one-entry map instead of a map of hundreds of agents.
- **D4 — Only agents in `agentsById` are seeded.** Events for unknown agent ids are
  dropped, so the snapshot does not grow with history.
- **D5 — Merge rule: newer `lastActivity` keeps the client entry; equal stamps fall
  to `updatedAtSequence`.** The issue states "keeping the newer `lastActivity`".
  `agent.context_saturation_changed` advances `updatedAtSequence` without moving
  `lastActivity`, so on equal stamps the higher `updatedAtSequence` wins (the event
  store's `AUTOINCREMENT` sequence is monotonic across restarts). The whole entry is
  kept or replaced (entries are coherent units). Remaining ties, a missing sequence,
  and unparseable timestamps go to the snapshot (server is authoritative).
- **D6 — `effectiveStamp` is not changed (deviation from issue fix #3, which is
  phrased "If a fallback is needed").** After boot, the agent row's `lastActivity`
  carries no live signal for any harness: the enrichment poller emits `agent.created`
  once per agent per server lifetime (`seenAgentIds` in
  `agent-enrichment-service.ts`), so the row stamp is frozen at first sight. For
  claude-code it is the spawn stamp (`markAgentRunning`, `agent-state.ts` line 834);
  for codex it is whatever `recordAgentActivity` (line 182, every 5 s from
  `src/lib/codex/app-server-host.ts` line 647) last wrote before first sight. Codex
  posts no `agent.activity_changed` (`sync-sources/hooks/codex-notify-hook` writes
  heartbeat files only), so codex orbs already go stale 30 min after a restart; that
  is a separate codex-liveness gap, not fixed by changing the fallback. Swapping the
  fallback to `startedAt` would change the operator-directed "goes stale on evidence"
  semantics for every harness (that test uses `startedAt: NOW`) without fixing codex.
  After FR-1 and FR-4, every agent with a runtime event in the 7-day window has a
  runtime entry, so the fallback runs only for agents with no runtime events. Issue
  AC3 is met by FR-6 (W5).
- **D7 — The `RUNTIME_EVENT_TYPES` drift in `agent-state-service.ts` is not fixed here.**
  That list lacks `agent.channel_reply` and `agent.heartbeat_dead` despite its "keep
  in sync" comment. The boot seed uses its own complete list
  (`RUNTIME_SEED_EVENT_TYPES`). Changing `AgentStateService` is out of scope.

### W2 — Pure runtime fold module

**Files (new):** `src/dashboard/server/services/runtime-seed.ts`,

```ts
/**
 * Boot seed for the read model's runtime map (PAN-4522).
 *
 * The read model used to boot with `agentRuntimeById: {}`, so every client that
 * connected after a restart saw each agent's spawn-time stamp until its next tool
 * beat. This replays each agent's retained runtime events through the shared
 * reducer so a live agent comes back with its real last-activity stamp.
 */
import { applyEvent, INITIAL_READ_MODEL_STATE } from '@overdeck/contracts';
import type { AgentRuntimeSnapshot, AgentSnapshot, DomainEvent, ReadModelState } from '@overdeck/contracts';
import type { StoredEvent } from '../event-store.js';

/** Every event type whose reducer case writes `agentRuntimeById`. */
export const RUNTIME_SEED_EVENT_TYPES: readonly string[] = [
  'agent.activity_changed', 'agent.thinking_started', 'agent.thinking_stopped',
  'agent.waiting_started', 'agent.waiting_cleared', 'agent.message_received',
  'agent.channel_reply', 'agent.model_set', 'agent.current_issue_set',
  'agent.context_saturation_changed', 'agent.resolution_changed',
  'agent.state_restored', 'agent.stopped', 'agent.heartbeat_dead',
];

/**
 * Replay stored runtime events into a runtime map for the agents in `agentsById`.
 * Each agent folds against its own scratch state and only its runtime entry is
 * kept: `agent.stopped` and `agent.heartbeat_dead` also rewrite agent rows, and a
 * later resume's `agent.status_changed` is not a runtime event, so their row
 * changes must not leak into the served agents.
 */
export function foldRuntimeSeed(
  events: readonly StoredEvent[],
  agentsById: Readonly<Record<string, AgentSnapshot>>,
): Record<string, AgentRuntimeSnapshot> {
  const byAgent = new Map<string, StoredEvent[]>();
  for (const event of events) {
    const agentId = (event.payload as { agentId?: unknown } | null)?.agentId;
    if (typeof agentId !== 'string' || !(agentId in agentsById)) continue;
    const list = byAgent.get(agentId) ?? [];
    list.push(event);
    byAgent.set(agentId, list);
  }
  const seeded: Record<string, AgentRuntimeSnapshot> = {};
  for (const [agentId, list] of byAgent) {
    let scratch: ReadModelState = {
      ...INITIAL_READ_MODEL_STATE,
      agentsById: { [agentId]: agentsById[agentId] },
      agentRuntimeById: {},
    };
    for (const event of [...list].sort((a, b) => a.sequence - b.sequence)) {
      scratch = applyEvent(scratch, event as unknown as DomainEvent);
    }
    const entry = scratch.agentRuntimeById[agentId];
    if (entry) seeded[agentId] = entry;
  }
  return seeded;
}
```

from `@overdeck/contracts` (`agent-state-service.ts` lines 32-36 and `read-model.ts`
lines 14-22 import them this way).

New module:

```ts
/**
 * Runtime-map helpers shared by the reducers (PAN-4522).
 */
import type { AgentRuntimeSnapshot } from './types'

export function defaultRuntimeSnapshot(agentId: string, timestamp: string, sequence: number): AgentRuntimeSnapshot {
  return { id: agentId, activity: 'idle', lastActivity: timestamp, updatedAtSequence: sequence }
}

/**
 * Merge a snapshot's runtime map into the client's, per agent. A freshly booted
 * server may serve an older or missing entry; a client entry with a strictly
 * newer `lastActivity` (or an equal stamp with a higher `updatedAtSequence`)
 * survives, and an agent the snapshot omits keeps its entry.
 */
export function mergeSnapshotRuntimeById(
  current: Readonly<Record<string, AgentRuntimeSnapshot>>,
  incoming: Readonly<Record<string, AgentRuntimeSnapshot>> | undefined,
): Record<string, AgentRuntimeSnapshot> {
  if (!incoming) return { ...current }
  const merged: Record<string, AgentRuntimeSnapshot> = { ...current }
  for (const [agentId, next] of Object.entries(incoming)) {
    const held = current[agentId]
    merged[agentId] = held && heldIsNewer(held, next) ? held : next
  }
  return merged
}

/** Newer `lastActivity` wins; equal stamps fall to the higher `updatedAtSequence`. */
function heldIsNewer(held: AgentRuntimeSnapshot, next: AgentRuntimeSnapshot): boolean {
  const heldAt = Date.parse(held.lastActivity)
  const nextAt = Date.parse(next.lastActivity)
  if (heldAt > nextAt) return true
  if (heldAt !== nextAt) return false
  return Number.isFinite(held.updatedAtSequence) && Number.isFinite(next.updatedAtSequence)
    && held.updatedAtSequence > next.updatedAtSequence
}
```

## Critique response

Plan critic round 1 (`.pan/drafts/PAN-4522-critique.md`) raised two
blocks-the-design findings and one sharpening note. All three changed the plan.

### Latest per type loses runtime fields

Accepted. The critic is right: `agent.model_set` keeps `sessionModel`,
`sessionHarness` and `claudeSessionId` when a later event omits them, and
`channelReply`/`resolution` are kept or cleared conditionally by
`agent.message_received`, `agent.activity_changed` and `agent.channel_reply`. The
latest-per-type fold is dropped. D2, FR-1 and FR-3 now require a full replay of each
agent's retained runtime events. W1 replaces `queryLatestPerAgentByType` with
`queryRuntimeHistory(types, agentIds)`, which filters by agent id in SQL so rows for
ids outside `agentsById` (55k `conv-*` rows, 7k `sequencer-runner` rows in the live
store) are never parsed. `queryByTypesSince(types, 0)` was evaluated and rejected: it
would parse all 199k rows, including ids the seed discards. W2 folds per agent
(D3), so each reducer step copies a one-entry runtime map. The measured cost of a
full replay of all 199k rows is 0.3 s SQL plus 0.6 s parse and fold (NFR-1); the
agent-id filter lowers it. W2 adds the critic's two-event `agent.model_set`
counterexample and a `channelReply` clear case as tests.

### Equal activity stamps can discard newer state

Accepted. `agent.context_saturation_changed` advances `updatedAtSequence` without
moving `lastActivity`. FR-4 and D5 now break equal-stamp ties on the higher
`updatedAtSequence` (the `AUTOINCREMENT` sequence is monotonic across restarts).
W4's `heldIsNewer` implements it, and W4 adds the critic's sequence-10/11
counterexample plus the reverse case as tests.

### The boot test bypasses boot

Accepted. W3's test now drives the real `ReadModelServiceLive` with a mocked
`../event-store.js`, mocked backend inventory and issue service, and a stub
`AgentsResolver`, following `read-model-served-agent-status.test.ts`. It asserts the
first snapshot's runtime stamp and the failure fallback (`{}`, `sequence` kept, error
logged). The direct query and fold tests stay under W1 and W2.

- Current agent row changes historical heartbeat replay
