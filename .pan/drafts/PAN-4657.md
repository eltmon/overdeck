## Glossary

- **Conversation** — a row in the `conversations` table of `overdeck.db`. It has a unique `name` (for example `conv-20261101-1234`); every route and door in this PRD keys on `name`.
- **Schedule** — a row in `conversation_schedules` (PAN-4640): one prompt, a 5-field cron, an IANA `time_zone`, `enabled`, `next_run_at` (epoch ms), the last run's time, status and error. The only reader and writer is the **schedule door** `src/lib/overdeck/conversation-schedules.ts`.
- **Enabled schedule** — `enabled = 1`. A paused schedule has `enabled = 0`.
- **Preset** — a named recurrence (hourly, daily at HH:MM, weekdays at HH:MM, weekly on a day at HH:MM) that compiles to a 5-field cron. Only the cron is stored.
- **Sweep** — `src/dashboard/server/services/conversation-schedule-service.ts`: boot +30 s, then every 60 s, primary dashboard only. It **claims** a due schedule (compare-and-set that advances `next_run_at`), then **fires** it (resume if needed, then deliver the prompt).
- **Delivered** — a fire whose message delivery returned 2xx; the sweep records `last_run_status = 'delivered'`.
- **Chain head** — when a conversation was `/clear`ed, the sweep delivers to the continuation row returned by `resolveClearChainHead(conv)` (`src/lib/overdeck/conversation-clear-chain.ts`), not to the scheduled row.
- **Triage state** (PAN-4639) — `conversations.settled_at`, `settle_reason`, `snoozed_until`. Read and written only through `src/lib/overdeck/conversation-triage-store.ts`.
- **Inbox** — the conversation-list section for a top-level group that is not waiting on the operator, not snoozed (`snoozedUntil` null or past) and not settled (`settledAt` null). Section assignment is client-side in `src/dashboard/frontend/src/components/CommandDeck/conversation-triage.ts`.
- **Resurface** — clear all three triage columns of a conversation, so it renders in Inbox (or Needs you) again.
- **List enrichment** — `enrichConversationList` in `src/lib/overdeck/conversation-list.ts`, the per-page builder behind `GET /api/conversations`. Its result is cached for 2 s (`LIST_ENRICHMENT_TTL_MS`); writers call `invalidateConversationListEnrichmentCache()`.
- **In-memory event** — a `DomainEvent` sent with `getEventStore().emitOnly(...)`: pushed over `/ws/rpc`, never persisted.
- **List revision** — `conversationsListRevision` in the shared read model (`packages/contracts/src/event-reducers.ts`). `ConversationList.tsx` invalidates the `['conversations']` query whenever it changes.
- **Dialog host pattern** — a zustand store plus a host component mounted once in `src/dashboard/frontend/src/main.tsx`, so a dialog opened from a menu outlives the menu (`LinkPullRequestDialogHost`).

## Problem

PAN-4640 shipped scheduled conversations as a backend and a CLI. The dashboard has no way to create, see, pause or delete a schedule, the conversation row does not show that a conversation is scheduled, a schedule change does not refresh the list, and a settled or snoozed conversation stays hidden in its collapsed section after its schedule fires, so the operator never sees the scheduled run's output.

## Decisions (auto mode)

- **D1 — Share the preset compiler through `@overdeck/contracts`.** Move `SchedulePreset` and `presetToCron` (with `parseTime`, `TIME_PATTERN`, `DAY_NUMBERS`) verbatim into a new `packages/contracts/src/conversation-schedule-presets.ts`, export it from `packages/contracts/src/index.ts`, and make the recurrence module re-export it. The dialog and the CLI then compile presets with one function. Error messages stay byte-identical.
- **D2 — The badge counts enabled schedules only.** One grouped query per page returns, per conversation name, `MIN(next_run_at)` and `COUNT(*)` over `enabled = 1`. A conversation with only paused schedules gets `nextScheduledRunAt: null, scheduleCount: 0` and renders no badge.
- **D3 — Event name and payload.** `conversation.schedules_changed`, payload `{ conversationName: string }`, in-memory only. The reducer bumps `conversationsListRevision` and changes nothing else.
- **D4 — Emitter lives in the schedule door; cache invalidation does not.** `emitConversationSchedulesChanged(name)` goes in `conversation-schedules.ts` (same try/catch shape as the PR emitter). `conversation-list.ts` will import the door (D2), so the door must never import `conversation-list.ts` (import cycle, `npm run lint:circular`). The routes and the sweep call `invalidateConversationListEnrichmentCache()` themselves, then the emitter.
- **D5 — Routes notify on every successful write.** POST 201, PATCH 200 and DELETE 200 invalidate the enrichment cache and emit. Refusals (400/403/404/409) do neither. CLI writes made with the dashboard down go straight to the door and emit nothing; the 10 s list poll picks them up.
- **D6 — "Each sweep run" means once per changed conversation per sweep pass.** The sweep collects the name of every schedule it claimed (fired, failed or skipped) plus every chain head it delivered to into a `Set`, and after the loop calls `onChanged(name)` once per entry. A pass that claims nothing emits nothing (no event every 60 s).
- **D7 — Resurface on delivery only.** When a fire is delivered, the sweep clears the triage state of the conversation it delivered to (the chain head, reported by `fireScheduledPrompt` as `conversationName`). A `failed` or `skipped` run does not resurface: the operator would see a conversation that received nothing. A paused schedule never fires, so it never resurfaces.
- **D8 — One statement clears all three triage columns.** New `clearConversationTriage(name)` in the triage store: `UPDATE conversations SET settled_at = NULL, settle_reason = NULL, snoozed_until = NULL WHERE name = ?`. A clear failure is logged (`console.warn`) and never turns a delivered run into a failed one.
- **D9 — Resurfacing beats PAN-4639 D8 for this one cause.** PAN-4639 D8 says new activity never changes stored triage state. A scheduled delivery is an operator-authored instruction arriving on the operator's timetable, and the issue requires the conversation back in Inbox; this is the one write path that clears triage without the operator clicking. Ordinary agent activity still never changes it.
- **D10 — Dialog form shape.** One form serves create and edit. Fields: `Prompt` textarea; `Repeat` select with options `Hourly`, `Daily`, `Weekdays`, `Weekly`, `Custom cron`; `Time` (`<input type="time">`, default `09:00`, shown for Daily/Weekdays/Weekly); `Day` select `mon`…`sun` (default `mon`, shown for Weekly); `Cron expression` text input (shown for Custom cron); `Time zone` text input, default `Intl.DateTimeFormat().resolvedOptions().timeZone`. Create mode defaults to `Repeat = Daily`. The request always sends `timeZone` explicitly.
- **D11 — Edit pre-fills the raw cron.** Edit sets `Repeat = Custom cron`, the cron field to the stored cron, the prompt and the zone to the stored values. Choosing a preset overwrites the cron. There is no cron-to-preset decoding.
- **D12 — The dialog list shows raw values.** Each schedule row shows the prompt (one line, truncated, full text in `title`), `<cron> · <timeZone>`, `next <when>` (or `paused`), and, when present, `last <status>` with the error in `title`. `<when>` is `formatLocalWhen` (D15).
- **D13 — Pause, resume, delete.** Pause sends `PATCH { enabled: false }`; Resume sends `PATCH { enabled: true }`; Delete sends `DELETE` with no confirmation step (the Pull requests dialog's Unlink is the precedent). Errors from the API show in a `role="alert"` line with the server's `error` text.
- **D14 — Dialog freshness.** After every successful write the dialog invalidates its own query `['conversation-schedules', name]` and `['conversations']`. While open it also invalidates its own query whenever `conversationsListRevision` changes, so a sweep run updates `next`/`last` in place.
- **D15 — Badge format.** Extract `formatLocalWhen(iso, now)` from `formatSnoozeWake` in `conversation-triage.ts`; it returns `today HH:MM`, `tomorrow HH:MM`, `<Ddd> HH:MM` within 7 days, else `<Mmm> <D> HH:MM`. `formatSnoozeWake` becomes `` `back ${formatLocalWhen(untilIso, now)}` `` (output unchanged). The badge is a `conversationBranchChip` span with a lucide `CalendarClock` icon (size 10) and the text `formatLocalWhen(nextScheduledRunAt, now)`. Its `title` and `aria-label` are `` `${scheduleCount} active ${scheduleCount === 1 ? 'schedule' : 'schedules'} · next run ${new Date(nextScheduledRunAt).toLocaleString()}` ``. It renders in both row variants, right after `pullRequestBadge`, only when `nextScheduledRunAt` is a non-null string. No color beyond the chip's muted style (style guide: no decorative color, no pill badges).
- **D16 — Menu placement and eligibility.** A `Schedule…` item (lucide `CalendarClock`, size 14) goes right after `PullRequestMenuItems` in both menus, through one exported component `ScheduleMenuItem` in the dialog module. It returns `null` for `origin === 'vault'` (the API refuses vault copies with 409) and `origin === 'linked'` (another machine's conversation). It renders on nested rows too: lanes and successors are ordinary conversations the API accepts.
- **D17 — Dialog file.** Store, host, dialog and `ScheduleMenuItem` live in one new file `src/dashboard/frontend/src/components/chat/ConversationScheduleDialog.tsx` (next to `LinkPullRequestDialog.tsx`), kept under 450 lines. The wire type for a schedule is a local `interface ConversationScheduleView` in that file mirroring the JSON in "What the code does today" item 1.
- **D18 — Size.** The plan touches 28 files across 6 subsystems (11 are tests, the CI list and docs). This issue is already the dashboard slice split from PAN-4640; each work item touches 8 files or fewer. `plan.metadata.sizeJustification` records this.

## Requirements

### Functional

- **FR-1** — `presetToCron` and `SchedulePreset` are exported from `@overdeck/contracts` with the PAN-4640 FR-3 mapping (hourly → `0 * * * *`; daily `HH:MM` → `M H * * *`; weekdays → `M H * * 1-5`; weekly `<day> HH:MM` → `M H * * <0-6>`, sun=0), and `src/lib/overdeck/conversation-schedule-recurrence.ts` re-exports them, so the CLI behaves exactly as before.
- **FR-2** — `GET /api/conversations` returns `nextScheduledRunAt` (ISO string or null: the earliest `next_run_at` among the conversation's enabled schedules) and `scheduleCount` (number of enabled schedules) on every row; vault browse copies always carry `null` and `0`. The values come from one query per page.
- **FR-3** — `packages/contracts` defines the in-memory `conversation.schedules_changed` event (payload `{ conversationName }`), includes it in `DomainEvent`, and its reducer case increments `conversationsListRevision` by 1.
- **FR-4** — `emitConversationSchedulesChanged(name)` in the schedule door emits that event and never throws when the event store is uninitialized.
- **FR-5** — Successful `POST`, `PATCH` and `DELETE` schedule routes invalidate the list enrichment cache and emit `conversation.schedules_changed` for the route's conversation name; refused requests emit nothing.
- **FR-6** — The sweep calls `onChanged(name)` once per sweep pass for every conversation whose schedule it claimed and every chain head it delivered to; a pass that claims nothing calls it zero times.
- **FR-7** — When a scheduled prompt is delivered, the sweep clears `settled_at`, `settle_reason` and `snoozed_until` of the conversation it delivered to; failed and skipped runs leave triage state untouched.
- **FR-8** — A `Schedule…` item in the row overflow menu and in the tab menu opens one schedule dialog for that conversation; it is absent for vault browse copies and linked rows.
- **FR-9** — The dialog lists the conversation's schedules and creates (`POST`), edits (`PATCH` with `prompt`, `cron`, `timeZone`), pauses (`PATCH { enabled: false }`), resumes (`PATCH { enabled: true }`) and deletes (`DELETE`) them; presets compile through `presetToCron`; the zone defaults to the browser zone; API errors show as text.
- **FR-10** — A row whose `nextScheduledRunAt` is set renders a schedule badge with `formatLocalWhen` text and a tooltip naming the active schedule count; a row with `nextScheduledRunAt: null` renders none.
- **FR-11** — `features/conversations.mdx` and `docs/DASHBOARD-ARCHITECTURE.md` describe the dialog, the badge, the event and the resurfacing rule.
