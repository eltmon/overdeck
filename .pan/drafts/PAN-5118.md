# PAN-5118: `pan task done` closes many items in one call and one commit

**Issue:** [PAN-5118](https://github.com/eltmon/overdeck/issues/5118)
**Status:** draft (planning, `pan plan --auto`)
**Verified against:** `feature/pan-5118` at `5b16f5b133e` (2026-11-10)

## Glossary

- **Item.** A top-level entry in `plan.items[]` of an issue's xBRIEF, for example `cli-variadic-done`.
- **AC sub-item.** A child of an item whose `metadata.kind` is `acceptance_criterion`. Its id is `<item-id>.acN`, for example `cli-variadic-done.ac2`. `pan done` refuses while any AC sub-item is not `completed` or `cancelled` (`src/lib/work/done-preflight.ts`, `evaluateIncompletePlanItems`).
- **Continue file.** `<planHome>/.pan/continues/<ISSUE>.xbrief.json`. It holds item state. `pan task` writes it and commits it on the feature branch.
- **Continue commit.** The commit `commitContinue()` makes after each write, message `chore(workspace): plan artifacts for <ISSUE>`.
- **Trailer line / evidence.** A commit body line `Item: <id>`. `pan task done` accepts an id only when some commit in an issue repo carries that exact line (line-anchored `git log --grep`, so `Item: a` never matches `Item: a.ac1`) and that repo's branch is not ahead of its upstream.
- **Corroborating repo.** The first repo root (of the workspace repos plus the plan home) whose history carries the id's trailer line.
- **Batch.** One `pan task done` call with more than one id.

## Problem

On 2026-11-10 two work agents spent 20 to 40 minutes closing AC sub-items before they opened PRs. PAN-5100 had 48 sub-items and took about 25 minutes. PAN-5078 had 85 and was still looping 25 minutes in. The loop was `pan task done <issue> <id>; git push` once per id.

The cause has two parts, both verified in code:

1. `runTaskDone` takes one id and calls `commitContinue` on success, so N ids make N continue commits. Source: [task.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5118/src/cli/commands/task.ts), lines 169 to 193, anchor `export async function runTaskDone(issue: string, itemId: string`.
2. `markItemDone` refuses while the corroborating repo is ahead of its upstream. In a single-repo project the plan home is that repo, so the continue commit from call K makes call K+1 refuse with "1 commit(s) ahead of its upstream". That is why agents push between calls, and each push runs the pre-push hooks (commitlint, ratchet audit, `scripts/lint-file-size.sh`). Source: [continue-state.ts](/home/eltmon/Projects/overdeck/workspaces/feature-pan-5118/src/lib/xbrief/continue-state.ts), lines 439 to 446, anchor `if (options.requirePushed) {`.

No work prompt mentions AC sub-items today. Agents learn about them only from the `pan done` refusal list, then close them one id at a time.

## Goal

Closing an item and all of its AC sub-items takes one `pan task done` call, one continue commit, and no extra push. For 85 ids: one call, one continue commit, one push (the next item's push or `pan done` carries the continue commit).

## Requirements

### Functional

- **FR-1.** `pan task done <issue> <item...>` accepts one or more ids.
- **FR-2.** Every id must have its own evidence: a commit carrying the exact line `Item: <id>` in a corroborating repo whose branch is not ahead of its upstream. An AC sub-item does not inherit its parent's evidence.
- **FR-3.** The command verifies every id before it writes anything. If any id fails, it writes nothing, makes no commit, exits 1, and names every failing id with its reason. Verification does not stop at the first failure.
- **FR-4.** When every id passes, all ids are recorded in one continue-file write and committed with exactly one continue commit.
- **FR-5.** The single-id form keeps today's stdout (`<id>\tcompleted`, or the JSON object `{ itemId, status, doneAt, ... }` with `--json`) and today's refusal text (`<id> is not done yet: <reason>.` then `Nothing was written. Commit the work with a body line "Item: <id>", push the branch, then run this again.`).
- **FR-6.** With more than one id, text output is one `<id>\tcompleted` line per id, and `--json` output is a JSON array of `{ itemId, status, doneAt, ... }` objects. Both follow argument order after duplicates are removed.
- **FR-7.** A repeated id is processed once.
- **FR-8.** `POST /api/self/tasks/done` accepts either `itemId` (a string, unchanged) or `itemIds` (an array of 1 to 500 strings). Both together is a 400. Neither keeps today's 400 text. Each id still passes through a `{ ref }` job argument.
- **FR-9.** The MCP `task_done` tool accepts `itemIds` (array) or `itemId` (string) and posts the matching body.
- **FR-10.** The work prompts tell the agent to put `Item: <item-id>` plus one `Item: <item-id>.acN` line per AC in the item's commit body, and to close the item and its ACs with one `pan task done` call after the push. The rule "never batch multiple tasks into one commit" stays; AC sub-items of one item share that item's commit.
- **FR-11.** The `pan task` reference text, the MCP tool table, and the changelog describe the multi-id form.
- **FR-12.** A `task-done` self job keeps its whole stdout (up to the existing 4 MiB child buffer), so a 500-id `--json` result reaches the `task_done` caller as valid JSON. Every other verb keeps the 16 KiB tail.
- **FR-13.** The foreman protocol (`docs/FOREMAN.md`, `sync-sources/skills/pan-foreman/SKILL.md`) tells workers to put the AC `Item:` lines on the item commit and tells the foreman to close the item and its ACs with one call.
- **FR-14.** The verification feedback for `incomplete-plan-items` gives one copy-ready `pan task done <issue> <id> <id> ...` command that lists every incomplete id.

### Non-functional

- **NFR-1.** The upstream-ahead check runs at most once per corroborating repo per call, not once per id.
- **NFR-2.** Added lines in the doc files of work item 6 contain no em dash (U+2014).
- **NFR-3.** No new HTTP route and no new `pan` verb. A new route would need a `no-loss-matrix.ts` row; extending the existing route does not.
- **NFR-4.** One variant per operation (CLAUDE.md "Key Invariants"): `markItemDone` is replaced by `markItemsDone`, not kept beside it.

```ts
export interface MarkItemsDoneOptions {
  /** When true, each corroborating repository's branch must not be ahead of its upstream. */
  requirePushed: boolean;
  /** Repository roots to search for each id's `Item: <id>` commit; the plan home alone by default. */
  repoRoots?: readonly string[];
}

/** One reason a set of ids cannot be completed: a missing trailer (one id) or an unpushed repository (every id it corroborates). */
export interface ItemVerificationFailure {
  readonly kind: 'missing-trailer' | 'unpushed';
  readonly itemIds: readonly string[];
  readonly reason: string;
}

export class ItemNotVerifiable extends Error {
  constructor(message: string, readonly failures: readonly ItemVerificationFailure[] = []) {
    super(message);
  }
}

/**
 * Record every id as done, but only once git corroborates each one: a commit in
 * one of the issue's repositories carries the exact line `Item: <id>`, and (when
 * required) that repository's branch is not ahead of its upstream. Every id is
 * checked before anything is written; any failure throws one ItemNotVerifiable
 * listing all of them, and nothing is written. On success all ids land in one
 * continue-file write with a shared doneAt.
 */
export async function markItemsDone(
  planHome: string,
  issueId: string,
  itemIds: readonly string[],
  options: MarkItemsDoneOptions,
): Promise<Record<string, ContinueItemState>> {
  const ids = [...new Set(itemIds)];
  if (ids.length === 0) throw new Error('markItemsDone needs at least one item id');
  const repoRoots = options.repoRoots?.length ? [...new Set(options.repoRoots)] : [planHome];
  const failures: ItemVerificationFailure[] = [];
  const idsByRoot = new Map<string, string[]>();
  for (const id of ids) {
    let corroborating: string | null = null;
    for (const root of repoRoots) {
      if (await hasTrailerCommit(root, `Item: ${id}`)) { corroborating = root; break; }
    }
    if (!corroborating) {
      failures.push({ kind: 'missing-trailer', itemIds: [id], reason: `no commit in ${repoRoots.join(', ')} carries the trailer "Item: ${id}" — commit the work for ${id} first` });
      continue;
    }
    idsByRoot.set(corroborating, [...(idsByRoot.get(corroborating) ?? []), id]);
  }
  if (options.requirePushed) {
    for (const [root, rootIds] of idsByRoot) {
      try {
        const ahead = await unpushedCommitCount(root);   // runs once per root (NFR-1)
        if (ahead > 0) failures.push({ kind: 'unpushed', itemIds: rootIds, reason: `the branch in ${root} is ${ahead} commit(s) ahead of its upstream — push before completing ${rootIds.join(', ')}` });
      } catch (error) {
        if (!(error instanceof ItemNotVerifiable)) throw error;
        failures.push({ kind: 'unpushed', itemIds: rootIds, reason: error.message });   // the no-upstream case
      }
    }
  }
  if (failures.length > 0) throw new ItemNotVerifiable(failures.map((failure) => failure.reason).join('\n'), failures);
  const doneAt = new Date().toISOString();
  const next = updateContinueState(planHome, issueId, (state) => {
    const items = { ...(state.items ?? {}) };
    for (const id of ids) items[id] = { ...(items[id] ?? {}), status: 'completed', doneAt };
    return { ...state, items };
  });
  return Object.fromEntries(ids.map((id) => [id, next.items![id]]));
}
```

```ts
function notDoneMessage(itemIds: readonly string[], repoRoots: readonly string[], error: ItemNotVerifiable): string {
  if (itemIds.length === 1) {
```

```ts
/** PAN-5118: the most ids one task_done call may close (PAN-4223 had 117 AC sub-items). */
export const MAX_TASK_DONE_ITEMS = 500;

/** `body.itemIds` → 1..MAX_TASK_DONE_ITEMS non-empty strings of at most 200 characters, else the refusal. */
function parseItemIds(body: Record<string, unknown>): { ok: true; value: readonly string[] } | { ok: false; result: SelfRouteResult } {
  const ids = body['itemIds'];
  const bad = { ok: false, result: badRequest(`itemIds must be a list of 1 to ${MAX_TASK_DONE_ITEMS} item ids of at most 200 characters`) } as const;
  if (!Array.isArray(ids) || ids.length === 0 || ids.length > MAX_TASK_DONE_ITEMS) return bad;
  for (const id of ids) if (typeof id !== 'string' || !id.trim() || id.length > 200) return bad;
  return { ok: true, value: ids as readonly string[] };
}

export async function handleSelfTaskDone(...) {
  const prepared = prelude(credential, text, deps);
  if (!prepared.ok) return prepared.result;
  const { caller, body, jobs } = prepared;
  let ids: readonly string[];
  if (body['itemIds'] !== undefined) {
    if (body['itemId'] !== undefined) return badRequest('pass itemId or itemIds, not both');
    const parsed = parseItemIds(body);
    if (!parsed.ok) return parsed.result;
    ids = parsed.value;
```
