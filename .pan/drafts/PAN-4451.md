# PAN-4451 — Conflict repair for conflicting PRs without CI, and waking agents whose blockers merged

**Issue:** [PAN-4451](https://github.com/eltmon/overdeck/issues/4451)
**Planned:** 2026-10-01 (auto planning, base `c98f934d1c3`)

## Glossary

- **Conflict-repair patrol** — the PAN-4384 dashboard patrol. `tickConflictRepair`
  (`src/lib/cloister/conflict-repair.ts`) runs every 60 s from
  `startConflictRepairPatrol` (`src/dashboard/server/services/conflict-repair-patrol.ts`).
  It finds an approved PR that conflicts with `main` and sends its work agent one
  `pan sync-main` repair per PR head.
- **Conflict-repair gate** — `evaluateConflictRepairGate` in
  `src/lib/cloister/merge-gate.ts`. It answers "is this PR merge-ready in every
  respect except `mergeable: false`?". The patrol acts only when it answers
  `conflicting: true`.
- **PR facts** — `PrFacts` from `getPrFacts` (`src/lib/cloister/pr-facts.ts`): the
  forge's view of one issue's PR. Relevant fields: `mergeable` (`false` = GitHub says
  CONFLICTING), `checks` (`'green' | 'pending' | 'red' | 'none'` over the head commit's
  checks; SKIPPED counts as green), `testJobSucceeded` (a CI `test` job concluded
  SUCCESS on the head), `approvedAtHead`.
- **`verification.tests: ci`** — project mode where tests run only on CI, so the merge
  gate requires `testJobSucceeded` (#4021). Overdeck itself runs in this mode.
- **Merge ref** — the synthetic `refs/pull/<n>/merge` commit GitHub builds for a PR.
  GitHub cannot build it for a CONFLICTING PR, so `pull_request` workflows do not run on
  that PR, and the head never gets a CI test result.
- **Pipeline journal** — `<workspace>/.overdeck/pipeline.jsonl`, the append-only log of
  what Overdeck did (`src/lib/cloister/pipeline-journal.ts`). Not authority; entries are
  never rewritten.
- **Continue file** — `<planHome>/.pan/continues/<ISSUE>.xbrief.json`, which holds xBRIEF
  item status (`pending | blocked | completed | …`). `pan task block` writes `blocked`
  there (`src/cli/commands/task.ts` `runTaskStatus`).
- **Blocker declaration** — new in this issue: `pan task block <issue> <item> --on <ref>...`.
  It marks the item blocked (as today) and journals which issues/PRs it waits on.
- **Blocker ref** — one thing an item waits on: an issue ID of any registered project
  (`PAN-4307`), a PR of the blocked issue's GitHub repo (`#4444`), `owner/repo#N`, or a
  GitHub PR URL. Stored in canonical form: `PAN-4307` or `eltmon/overdeck#4444`.
- **Blocker-wake patrol** — new in this issue: a dashboard patrol that sends the work
  agent one wake message when every blocker of a live declaration has merged.
- **Live declaration** — the newest `blocked.declared` entry for an item, while the
  continue file still says that item is `blocked` and no `blocked.woken` entry names it.

## Problem

### Part 1: approved + CONFLICTING PRs never get repaired

PR #4440 (PAN-4433) was approved at head `13c97089`
(journal: `review.verdict APPROVED` at 2026-09-30T18:42Z), then `main` moved and it
became CONFLICTING. It sat idle about 19 hours. Verified with
`gh pr view 4440 --json mergeable,statusCheckRollup` on 2026-10-01: `mergeable:
CONFLICTING`, rollup = `Mintlify Deployment` SKIPPED + `CodeRabbit` SUCCESS, and **no
`test` check**. So `checks` computes `'green'` but `testJobSucceeded` is `false`.

`evaluateConflictRepairGate` (`src/lib/cloister/merge-gate.ts`, lines 136–163) requires
everything the merge gate requires except mergeability:

```ts
// merge-gate.ts:144
if (facts.draft || facts.changesRequested || facts.checks !== 'green') {
  return { conflicting: false, reason: 'PR is not otherwise merge-ready', facts };
}
...
// merge-gate.ts:151-161
const asMergeable: PrFacts = { ...facts, mergeable: true, ...(approvedAtHead ? { approvedAtHead: true } : {}) };
const ciTestsRequired = facts.forge === 'github' && (deps.ciTestsRequired ?? issueRunsTestsOnCi)(issueId);
...
const readiness = evaluateMergeReadiness(asMergeable, { ciTestsRequired, uatRequired, requireApprovalAtHead: true });
```

`evaluateMergeReadiness` (`pr-facts.ts` ~line 936) then rejects with
`no CI test job reported on PR HEAD … (verification.tests: ci)` (line ~964), and also
rejects `checks: 'pending'` (line 959) and `'none'` (line 960). GitHub does not run
`pull_request` CI on a conflicting PR, so these conditions can never become true while
the PR conflicts. The repair that would fix the conflict is gated on CI that the
conflict prevents. Deadlock.

During the whole idle window (2026-09-30T18:42Z to 2026-10-01T13:17Z) the PR head was
`13c97089`, the approved head (`gh pr view 4440 --json commits`), so approval at head held
and the journal pre-filter passed (last `review.verdict` = `APPROVED`, no
`merge.completed`). The CI condition was the only reason the patrol did nothing; WI-1
alone would have sent the repair. (After the operator's manual nudge the agent pushed
`f89c00e3`/`e05f77e6`; a head that moved past its approval is out of scope here — the
agent's own `pan review request` covers it.)

### Part 2: an agent blocked on sibling issues is never re-woken

PAN-4437's work agent finished 5 of 9 items, then parked: the other 4 needed code from
PAN-4307 (PR #4444) and PAN-4436 (PR #4448). It said so only in an issue comment. It
did not run `pan task block` (its continue file on `feature/pan-4437` shows only
completed items). Both PRs merged; nothing woke the agent for hours. Overdeck has no
structured way for an agent to say "I wait on X", so nothing can act when X merges.

## Decisions (made here; the executor does not re-decide)

- **D1 — Waive CI at a conflicting head; keep red disqualifying.** When the forge says
  `mergeable: false`, the conflict-repair gate ignores `checks: 'pending'`,
  `checks: 'none'` and a missing/skipped CI test job. `checks: 'red'` still answers
  `conflicting: false` (reason `CI checks failing on PR HEAD <sha>`): a red head belongs
  to the CI-failure feedback path (`cloister/ci-failure-feedback.ts`). Why this is safe:
  the merge gate (`evaluateIssueMergeGate`) is unchanged, so the repaired head still
  needs green CI and a CI test job pass before anything merges. Why no second forge read
  for "the last green result on an earlier head": the issue accepts "no result at all
  when the PR is conflicting", which covers that case, and the extra read adds quota
  cost with no safety gain.
- **D2 — Approval at head, draft, change requests and failed required UAT still apply.**
  Only the CI conditions change.
- **D3 — Declaration door is `pan task block --on`.** No new top-level verb (so no new
  skill, no slash-command manifest change, and `src/cli/index.ts`, at 1267 lines, is
  untouched). An item-level declaration fits the existing checklist model:
  `--on` takes one or more refs (variadic, and each value may be comma-separated).
- **D4 — Refs are validated at declaration time.** An issue ID must resolve to a
  registered project (`resolveProjectFromIssueSync` non-null) and must not be the
  blocked issue itself. `#N` resolves against the blocked issue's GitHub repo
  (`resolveGitHubIssue(blockedIssueId)` in `src/lib/tracker-utils.ts`); when the blocked
  issue is not on GitHub, `#N` is rejected. A GitLab MR URL is rejected. Anything else is
  rejected. A rejected ref exits 1 and writes nothing (neither continue file nor journal).
- **D5 — Two new journal types:** `blocked.declared` (`data: { item, blockers: string[] }`,
  source `pan-task-block`) and `blocked.woken` (`data: { item, declaredAt, blockers,
  outcome: 'delivered' | 'unreachable', agentId? }`, source `blocker-wake`). A wake is
  keyed by the declaration's `at` timestamp, the same way conflict repair keys by
  `data.head`. No third "cleared" type: liveness comes from the continue file (D6).
- **D6 — Live declaration rule.** For each item, only the newest `blocked.declared`
  counts. It is live while (a) the continue file says the item's status is `blocked`
  and (b) no `blocked.woken` entry has `data.declaredAt` equal to its `at`. So
  `pan task unblock`, `reopen`, `cancel` and `done` end a declaration with no extra write.
- **D7 — "Merged" means:** for an issue ref, `getPrFacts(id, {}, { preferBranch:
  'feature/<id-lowercase>' }).merged === true` (a branch read bypasses the PR-tab cache,
  the `readApprovalStandsAtHead` precedent). For a PR ref,
  `runGh(['pr', 'view', String(n), '--repo', repo, '--json', 'state'])` returns
  `state === 'MERGED'`. A read error counts as "not merged yet" and is logged. A ref seen
  merged is memoized in-process (merged is permanent).
- **D8 — One wake per declaration, batched per issue per tick.** When one or more live
  declarations of an issue resolve in the same tick, the agent gets one message that
  lists every resolved item, and each declaration gets its own `blocked.woken` entry.
- **D9 — Delivery reuses the conflict-repair ladder.** `resolveIssueFeedbackTarget`
  (wake the live agent, else resume or start one) + `messageAgent(..., 'blocker-wake',
  { owesRework: true, feedbackRedelivery: true, dedupKey })` with the same
  "cannot enforce a dedup key" unkeyed retry as `conflict-repair.ts` `defaultDeliver`.
  `dedupKey = blocker-wake:<issue-lowercase>:<declaredAt values joined with ','>`.
  Unreachable (needs-you target, thrown error, or not delivered and not queued to mail)
  → raise Needs-you once via `surfaceIssueFeedbackNeedsYou` and journal `blocked.woken`
  with `outcome: 'unreachable'`, so the next tick never retries.
- **D10 — Blocker-wake patrol interval is 120 s** (`BLOCKER_WAKE_INTERVAL_MS = 120_000`).
  A wake a minute later than a merge costs nothing; half the forge reads of a 60 s tick.
- **D11 — Host skips** mirror conflict repair: `OVERDECK_DISABLE_BLOCKER_WAKE=1`, a peer
  dashboard (`isPeerDashboardProcess`), a frozen Deacon (`isDeaconGloballyPaused`), an
  overlapping tick, a paused issue (`getIssuePause(issueId).status !== 'unpaused'`), a
  workspace directory that no longer exists.
- **D12 — The work role prompt tells agents to declare.** `roles/work.md` gets one
  paragraph in "Signal the flywheel before you stall". This needs a `Prompt-Change:`
  trailer on the commit, or `npm run lint` (`lint:prompt-trailer`) fails.

## Requirements

### Functional

- **FR-1** — `evaluateConflictRepairGate` returns `conflicting: true` for an open,
  non-draft PR with no change request, approval proven at the head, `mergeable: false`
  and `checks` in `{'green', 'pending', 'none'}`, whatever `testChecks` /
  `testJobSucceeded` say, in a `verification.tests: ci` project.
- **FR-2** — `evaluateConflictRepairGate` still returns `conflicting: false` when
  `checks === 'red'`, when approval is not proven at the head, when changes are
  requested, for a draft, and for a failed required UAT at the head.
- **FR-3** — The conflict-repair prompt no longer claims the PR is green; it says GitHub
  runs no CI on a conflicting PR and that CI runs again after the push.
- **FR-4** — `pan task block <issue> <item> --on <ref>...` sets the item to `blocked`
  and appends one `blocked.declared` journal entry with canonical blocker strings.
- **FR-5** — Invalid refs (unknown project prefix, the blocked issue itself, `#N` for a
  non-GitHub issue, a GitLab URL, garbage) make the command exit 1 with a message naming
  the bad ref, and write nothing.
- **FR-6** — `pan task block` without `--on` behaves exactly as today and journals nothing.
- **FR-7** — The blocker-wake tick sends the issue's work agent one message when every
  blocker of a live declaration has merged, and journals `blocked.woken` with
  `outcome: 'delivered'`.
- **FR-8** — A declaration whose item is no longer `blocked` in the continue file, or
  that already has a `blocked.woken` entry, never produces a message.
- **FR-9** — When some but not all blockers merged, no message is sent.
- **FR-10** — An unreachable agent produces one Needs-you and a `blocked.woken` entry with
  `outcome: 'unreachable'`; the next tick does nothing for that declaration.
- **FR-11** — The dashboard starts the blocker-wake patrol at boot, every 120 s, and
  honors the D11 host skips.
- **FR-12** — `pan show <id>` prints a one-line summary for `blocked.declared` and
  `blocked.woken` entries.
- **FR-13** — Docs: `docs/PIPELINE-GATES.md` describes the waived-CI predicate, a new
  "Blocker wake (PAN-4451)" section, and the two journal types;
  `docs/MERGE-WORKFLOW.md` "After another feature merges" mentions both behaviors;
  `sync-sources/skills/pan-task/SKILL.md` documents `--on`; `roles/work.md` tells agents
  to declare blockers.

   ```ts
     | { kind: 'issue'; id: string }                    // 'PAN-4307'
     | { kind: 'pr'; repo: string; number: number };    // repo = 'eltmon/overdeck'

   export class BlockerRefError extends Error {}

   export interface BlockerRefContext {
     blockedIssueId: string;
     /** True when the issue ID belongs to a registered project. */
     isKnownIssue: (issueId: string) => boolean;
     /** The blocked issue's GitHub repo as 'owner/repo', or null when it is not on GitHub. */
     blockedIssueRepo: () => string | null;
   }

   /** Canonical string: 'PAN-4307' or 'eltmon/overdeck#4444'. */
   export function formatBlockerRef(ref: BlockerRef): string;

   /** Inverse of formatBlockerRef, for journal data; null for anything else. */
   export function parseStoredBlockerRef(value: string): BlockerRef | null;

   /**
    * Parse CLI values. Each value may hold comma-separated refs. Returns
    * de-duplicated refs in input order. Throws BlockerRefError naming the first
    * bad ref.
    */
   export function parseBlockerRefs(values: readonly string[], ctx: BlockerRefContext): BlockerRef[];
   ```

   Accepted forms (trim each; empty pieces are skipped; zero refs total → error
   `--on needs at least one issue or PR`):
   - `^[A-Za-z][A-Za-z0-9]*-\d+$` → issue, uppercased. Error if `!ctx.isKnownIssue(id)`

### WI-5 — The blocker-wake tick (FR-7, FR-8, FR-9, FR-10, NFR-2, NFR-3)

New file `src/lib/cloister/blocker-wake.ts`, shaped like `conflict-repair.ts`:

```ts
export const BLOCKER_WAKE_INTERVAL_MS = 120_000;
const SOURCE = 'blocker-wake';

export interface BlockerWakeDeps {
  listWorkspaces?: () => Pick<WorkspaceRow, 'issueId' | 'path'>[];
  readJournal?: (workspacePath: string) => PipelineJournalEntry[];
  appendEntry?: (workspacePath: string, entry: Omit<PipelineJournalEntry, 'at'>) => unknown;
  getIssuePause?: (issueId: string) => IssuePause;
  /** Item statuses from the continue file (readItemStatusesAsync(resolvePlanHome(path), issueId)). */
  readItemStatuses?: (issueId: string, workspacePath: string) => Promise<Record<string, string>>;
  isMerged?: (ref: BlockerRef) => Promise<boolean>;
  resolveTarget?: (issueId: string) => Promise<IssueFeedbackTarget>;
  deliver?: (agentId: string, prompt: string, dedupKey: string) => Promise<MessageDeliveryOutcome>;
  surfaceNeedsYou?: (issueId: string, reason: string, details: Record<string, unknown>) => Promise<void>;
  log?: (message: string) => void;
}

export function __resetBlockerWakeStateForTests(): void; // clears inFlight + mergedRefs

/** D6 without the continue file: newest declared per item with no woken entry naming its `at`. */
export function pendingDeclarations(entries: readonly PipelineJournalEntry[]): PipelineJournalEntry[];

export function buildBlockerWakePrompt(input: { issueId: string; items: readonly string[]; blockers: readonly string[] }): string;

export async function tickBlockerWake(deps?: BlockerWakeDeps): Promise<string[]>;
```

Per issue (`tickIssue`), in order:
1. `pending = pendingDeclarations(readJournal(path))`; none → return null (no other read).
2. Paused issue → null.
3. `statuses = await readItemStatuses(issueId, path)`; keep declarations whose
   `statuses[data.item] === 'blocked'` (D6). None → null.
4. For each kept declaration, parse `data.blockers` with `parseStoredBlockerRef`
   (skip unparsable strings; a declaration with zero parsable refs is skipped) and
   check each ref with the memoized `isMerged` (module `mergedRefs: Set<string>` keyed by
   the canonical string; only `true` is memoized). Evaluate refs one at a time and stop at
   the first unmerged ref of a declaration.
5. `resolved` = declarations whose every ref merged. None → null.
6. `target = await resolveTarget(issueId)`. `'needsYou' in target` → unreachable path.
7. Build the prompt; `deliver(target.agentId, prompt, dedupKey)` (D9). Throw, or
   `!delivered && !queuedToMail` → unreachable path.
8. Success: for each resolved declaration append `blocked.woken`
   `{ item, declaredAt: decl.at, blockers, outcome: 'delivered', agentId }`; return
   `woke <agentId> for <items>`.
9. Unreachable path: `surfaceNeedsYou(issueId, 'Blockers of <items> merged but the work agent could not be reached', { items, blockers, reason })`
   (catch + log its error), then append `blocked.woken` with `outcome: 'unreachable'`
   for each resolved declaration; return `escalated`.

Default deps: `listWorkspaces()` from `../workspaces/resolver.js`; `readPipelineJournal`;
`appendPipelineEntry`; `getIssuePause` from `../agents/agent-state.js`;

## Repo rules that apply here

- Fake timers for any delay-based test (`vi.useFakeTimers`, `advanceTimersByTimeAsync`);
  never real `setTimeout` waits; never drop `maxForks`.
- No `execSync` in server-reachable code; use `runGh` / `getPrFacts` (async).
- Agents never `git stash`; never `git checkout` another branch in the workspace.
- Quality gates before `pan done`: `npm run typecheck`, `npm run lint`,
  `npx vitest run <touched test files>`. Do not run the full `npm test` locally.
- File-size ratchet: `src/lib/cloister/pr-facts.ts` is 993/1000 — do not touch it.
  `src/dashboard/server/main.ts` is 895 lines; the WI-6 addition (~12 lines) stays under 1000.
- A `roles/*.md` edit needs a `Prompt-Change:` trailer in the same commit.
- New lib modules that need agent state import from the leaf (`agent-state.js`
  `getIssuePause` is what conflict-repair uses — reuse that import) to avoid
  `lint:circular` failures.

## Non-goals

- A blocker that closes without a merge (cancelled, not planned) never wakes the agent.
- No escalation timer for a declaration whose blockers never merge.
- GitLab MR refs (`#N` on a GitLab project, MR URLs) are not accepted; issue IDs of
  GitLab projects work through `getPrFacts`.
- Conflicting PRs with red checks at the head stay on the CI-failure feedback path.
- Conflicting PRs whose approval does not stand at the head are not repaired.
- No change to the merge gate, the auto-merge scheduler, or the review pipeline.
- No dashboard UI for blocker declarations.
- No "cleared" journal type; `unblock` writes no journal entry.
