## Glossary

- **A / B** — the two local dashboards a two-machine test starts on one host, each with its own `OVERDECK_HOME` and port. A is "the laptop" (the linking machine), B is "the desktop" (the owner of the conversation).
- **Home dashboard** — the operator's live dashboard on this host (`http://localhost:3011`, deployed main). Live Fly checks link Fly machines to it.
- **Peer test dashboard** — a second dashboard on this host with its own `OVERDECK_HOME` and port, started from this workspace's `dist/`. Never the operator's home.
- **Two-machine smoke** — `scripts/anywhere/two-machine-smoke.mjs` (1023 lines). Starts A (port 3041) and B (port 3042), links them through a byte-logging TCP proxy, and runs named steps. Documented in `docs/ANYWHERE-ARCHITECTURE.md` "Running the two-machine smoke" (line 13).
- **Fake claude** — a shell script named `claude` on a fake `PATH` that imitates Claude Code enough for Overdeck: prints a version, prints a `❯` prompt, writes a Claude-format JSONL transcript, and answers each input line deterministically.
- **Evidence file** — a markdown file under `.pan/uat/pan-4774/` that records, for one criterion, the exact commands run, the relevant output, the status, and any issue filed. Precedent: `.pan/uat/pan-4743/` (screenshots) and `.pan/notes/pan-4320-live-verification.md`.
- **Status** — one of `passed` (with evidence), `failed` (with the issue filed for it), `approximated` (with what was not covered). These are the only three values the closing comment may use.
- **Fix-or-file rule** — see D-4.
- **Device flow** — `pan account login` prints a user code and a verification URL. Per the operator's comment on the issue (2026-11-02T20:31Z), the agent sends both to the Flywheel conversation with `pan tell conv-flywheel "<code> <url>"`, and the Flywheel approves it in the browser.
- **NFR-9 open budget** — opening a linked conversation transfers at most the bounded open window (75 rows or 1 MiB) plus 64 KiB = **1,114,112 bytes** (`OPEN_BUDGET_BYTES`, two-machine-smoke.mjs line 117).

## Problem

Every Anywhere work item merged, but each issue verified only its own slice. Nobody has run AC-1 to AC-15 end to end on integrated `main`. The release needs one run that gives every criterion a status with evidence, one CI test that keeps AC-1 from regressing, and a checklist that lets the run be repeated.

### How the CI test can run AC-1 without a real model (traced 2026-11-02)

- **Message delivery** (`src/lib/overdeck/conversation-message.ts` line 408, `handleConversationMessage`) needs the row, not released, not ended, and a live pane for Claude Code (`paneInputGuard: true`, `packages/contracts/src/harness-capabilities.ts` line 103). No pane ⇒ 409 `input-target-not-main`. A pane with no Claude selector parses as `no-selector`, which is accepted (`src/lib/agents/input-target.ts` line 238). Success is 200 `{ ok: true, inputTarget: 'main' }`. Setting `POST /api/conversations/:name/delivery-method { deliveryMethod: 'tmux' }` sends straight through tmux paste-buffer and avoids a double delivery when the PTY supervisor's submit check fails. Bracketed paste may wrap input in `\e[200~ … \e[201~`, so tests match substrings.
- **Conversation create** (`src/lib/overdeck/conversation-runtime.ts` line 994, `handleConversationCreate`) on the tmux backend starts `bash launcher.sh`, which wraps the harness in `node dist/pty-supervisor.js claude …`. The fake receives `--session-id <uuid>` on create and `--resume <uuid>` on resume, plus permission flags, optional `--model`, `--effort`, and `--append-system-prompt-file <f>` (`src/lib/overdeck/launcher-generator.ts` lines 668-702). `waitForClaudeReady` (`src/lib/overdeck/claude-readiness.ts` lines 117-150) waits up to 30 s for `❯`.
- **Socket path limit:** `${OVERDECK_HOME}/sockets/pty-conv-<name>.sock` must stay under about 107 bytes or the supervisor exits and the fake dies. In this workspace a repo-relative home gives about 109 bytes. Use homes under `os.tmpdir()` with short names (for example `/tmp/odk-a-XXXXXX`).
- **Transcript location:** `$HOME/.claude/projects/<cwd with every char except [a-zA-Z0-9-] replaced by '-'>/<session-id>.jsonl` (`src/lib/runtimes/storage/claude-code.ts` line 55). Lines need `type`, `uuid`, `sessionId`, `cwd`, `timestamp`, `message` (the smoke's `seedTranscript` shape, lines 381-390). Omit `model` so the resume preflight on A never compares against the fake's version.
- **Pull** (`src/dashboard/server/services/conversation-pull.ts` lines 132-210): `release` on B settles the transcript and a forced WIP snapshot (a git bundle of `git add -A`, `src/lib/vault/wip-capture.ts`) into a fresh `dir:` vault store with a fresh key, packs it and stops the harness; `transfer` unpacks it under A's home; `adopt` runs `continueHere` (`src/dashboard/server/services/vault-continue.ts` line 261); `finish` completes. A real JSONL with at least one complete line and a `cwd` field is required.
- **Single-host tautology:** `resolveTarget` (`vault-continue.ts` lines 153-167) uses the record's saved `cwd` when that directory exists. On one host B's checkout exists for A too, so A adopts into B's checkout, `isWipPresent` is true and nothing is applied. The transferred store is encrypted with a per-transfer key held only in memory (`conversation-pull.ts` lines 168-176), so the test cannot read the bundle back. D-2 fixes this with one test-only environment variable.
- **Bind address:** the dashboard binds `HOST ?? '0.0.0.0'` (`src/dashboard/server/config.ts` line 128). B's reverse link to A uses A's advertised RFC1918 addresses (`src/lib/anywhere/endpoints.ts`), so `HOST` must stay unset. GitHub runners have a private 10.x interface.
- **tmux in CI:** `.github/workflows/ci.yml` installs only ripgrep and Playwright Chromium. Nothing installs tmux.
- **Slow tests:** `vitest.config.ts` lines 54-57 exclude `**/*.slow.test.ts` unless `VITEST_INCLUDE_SLOW=1`. No CI step sets it today.

## Requirements

### Functional

- **FR-1** A Node test under `tests/` starts two dashboards from `dist/` with separate `OVERDECK_HOME`s and, in order: links them both ways (each lists the other `online`); shows each side's seeded conversation on the other side within 15 s; sends a message from A to a live conversation on B and sees B's deterministic reply through A; pulls that conversation to A with an uncommitted file, which then exists in A's own, distinct checkout; and gets 409 `conversation-released` from B for a new turn.
- **FR-2** The same test asserts AC-14 (opening the linked conversation moves at most 1,114,112 bytes from B to A, counted at the proxy) and the local half of AC-2 (the proxy capture starts with the channel preamble byte `0x00` and contains no `HTTP/1.1`).
- **FR-3** `resolveTarget` skips the saved-cwd branch when `OVERDECK_TEST_ADOPT_SKIP_SAVED_CWD=1`, so a single-host test adopts into the project that matches the git origin.
- **FR-4** CI runs the FR-1 test in the `test-e2e` job, with tmux installed, and a failure fails `test-all-passed`.
- **FR-5** The two-machine smoke gains a `needs-docker` step: B reports no `docker` capability, and placement with `needs: ['docker']` and `pan lane start --machine auto --needs docker` both pick A.
- **FR-6** The two-machine smoke gains `--hold`: after the last check it keeps both servers running, prints their URLs, and stops them on SIGINT/SIGTERM. Servers start through a symlink whose path does not contain `dist/dashboard/server.js`.
- **FR-7** Every AC from AC-1 to AC-15 has a status and evidence. Evidence lives in `.pan/uat/pan-4774/`, one file per item below.
- **FR-8** Every failure found is either fixed in this issue or filed as a new issue, following D-4.
- **FR-9** Every Fly machine and Fly volume this run creates is destroyed when its test ends.
- **FR-10** `docs/ANYWHERE-RELEASE-CHECKLIST.md` lists the exact steps for every criterion, `CLAUDE.md`'s topic index links it, and `docs/ANYWHERE-ARCHITECTURE.md` describes the CI test, `needs-docker` and `--hold`.
- **FR-11** A comment on PAN-4774 gives AC-1 to AC-15 each one status from {passed, failed, approximated} with its evidence, issue, or uncovered part.

### Non-functional

- **NFR-1** The run never edits the operator's home configuration (`~/.overdeck/config.yaml`, `~/.ssh/config`) and never stops or restarts the home dashboard. The only home `projects.yaml` change allowed is the temporary throwaway project of D-15, removed when its items end. No pull, worker or lane may target a registered primary checkout (every registered project path on this host is one). The run never deletes anything outside `.tmp/`, the test's own temp homes, the D-15 clone at `/home/eltmon/Projects/pan4774-anywhere-smoke`, and the Fly resources it created.
- **NFR-2** No secret reaches an evidence file, a commit or the issue comment: account access tokens, device tokens, webhook secrets, Fly tokens and `odk_` tokens are replaced with `<redacted>`.
- **NFR-3** The CI test uses no `skipIf`, no `.only`, and no source-file grep. It fails (never skips) when `dist/` or tmux is missing, with a message naming the fix (`npm run build`, install tmux).
- **NFR-4** The CI test binds free ports chosen at run time (never 3011, 3041 or 3042), kills its own tmux servers, and removes its temp homes in `afterAll`, even after a failure.
- **NFR-5** Fly machines use the smallest size that runs the check (`shared-cpu-1x`, 1 GB unless the item says otherwise); at the end, `fly machines list` and `fly volumes list` for every app used show nothing created by this run.

## Decisions

- **D-1 The CI test is a vitest `.slow.test.ts` run by its own step in the `test-e2e` job.** File: `tests/integration/anywhere/two-machine-ac1.slow.test.ts`. The `test-e2e` job already runs `npm run build`; the new step runs after "Resource discovery benchmark" and before "Install Playwright browsers": `sudo apt-get install -y tmux && tmux -V && VITEST_INCLUDE_SLOW=1 npx vitest run tests/integration/anywhere/two-machine-ac1.slow.test.ts`. A plain `.test.ts` would run inside a 4-way shard at 5 s default timeouts, and the memory fact "gate rejects source-grep + skipIf" rules out a skip when tmux is missing. Why Node and not Playwright: every AC-1 step is an HTTP or CLI assertion; no step needs a browser.
- **D-2 One test-only environment variable, not a mount namespace.** `OVERDECK_TEST_ADOPT_SKIP_SAVED_CWD=1` makes `resolveTarget` ignore the record's `cwd`. The test registers on A a project with the same git origin (`https://github.com/smoke/repo.git`) at A's own clone, so adoption applies the WIP bundle there. Precedent: `OVERDECK_TEST_FORCE_CPU_SATURATED` in `src/dashboard/server/services/machine-load.ts` line 52. A mount namespace needs privileges the runner and this host do not grant without `sudo`; reading the bundle back needs the in-memory transfer key. The honest AC-1 claim this supports: "the transcript and WIP bundle cross the link and the uncommitted file is applied in a distinct checkout on A"; the live Fly run (AC-5) covers the same across two real filesystems.
- **D-3 AC-14 is measured at the proxy.** The proxy counts every byte B sends to A, including channel framing, so it bounds the channel's own counters from above. No new route exposes `ChannelSocket.bytesIn/bytesOut`.
- **D-4 Fix-or-file rule.** A failure is fixed in this issue when the fix touches at most two source files, adds fewer than 60 lines, stays in one subsystem, and comes with a unit test that fails before the fix. Otherwise the agent files a new GitHub issue with: the AC, the failing step, the exact command, its output (trimmed to the relevant 40 lines), and the commit tested. The evidence file links the fix commit or the issue. A failed AC with a filed issue still counts as a completed run item.
- **D-5 AC-2 has two halves.** The local half uses the smoke's proxy capture (the "channel's frame dump" the issue allows) because tcpdump needs root here. The relay half runs `tcpdump -i any -w /tmp/relay.pcap` as root inside the AC-3 Fly VM while the relay route carries a conversation open, then scans the pcap for the plaintext marker and `HTTP/1.1`.
- **D-6 Live Fly checks link to the home dashboard.** The home dashboard runs deployed integrated main, and the issue says "confirm it shows online here". If a Fly VM's `pan` lacks code from integrated main (provisioning pins the VM's pan to home's version), the agent switches that item to the peer-test-dashboard recipe in `docs/fly-provider.md` "Live verification" and the memory fact `live-fly-check-test-home` (branch-built image, separate HOME with symlinks, server started through a symlink path). It never edits the home `config.yaml` to change `[remote.fly] image`.
- **D-7 AC-10 uses a systemd image with a volume, and the packed main tarball.** The pan-workspace image has no systemd and the Fly rootfs resets on restart. The agent builds a throwaway "VPS" image: `ubuntu:24.04` + `systemd` as PID 1 (`/sbin/init`) + `openssh-server` + Node 22 + a user `vps`, with a Fly volume mounted at `/home` and `/var/lib/systemd/linger` symlinked to `/home/.linger` so lingering survives the rootfs reset. It copies `npm pack` output of integrated main to the VM and runs `npx ./overdeck-core-<version>.tgz connect` as `vps`. **Implementation checkpoint:** if systemd does not reach `running` or `degraded` as PID 1 on Fly after two attempts, AC-10 is `approximated`, the evidence records how far `connect` got, and the agent files an issue "Run AC-10 on a real VPS". The Dockerfile text goes into the checklist, not into the repo.
- **D-8 Directory registrations are serialized.** The account's plan tier is not known and a free account allows 3 machines. The items that register a machine with the directory (AC-3 direct/relay VM, AC-10 VPS, AC-11 peer dashboard) run one after another and each ends with `pan machines forget <label>` (and `pan machines unlink`) for what it registered. Each new machine signs in with its own device flow; the agent never copies `account.json` between machines.
- **D-9 AC-6 reaches the Fly sshd through `fly proxy`.** `fly proxy 10022:22 -a <app> -s` on this host, then the SSH host is `ssh://root@127.0.0.1:10022` (`src/lib/anywhere/ssh/target.ts` line 40 accepts `ssh://user@host:port`). No `~/.ssh/config` edit. The VM's authorized key is a throwaway key generated for the run under `.tmp/pan-4774/ssh/`, passed with the SSH host's identity setting if the add flow offers one; otherwise the agent adds the throwaway public key to the VM and loads the private key with `ssh-add` for the run only, then `ssh-add -d` it.
- **D-10 AC-7 runs on a peer test dashboard with headed Chrome.** Subscribing the home dashboard would leave a stray push target. The agent starts a peer dashboard, opens it in `google-chrome` through Playwright `channel: 'chrome'` with an isolated `userDataDir` under `.tmp/pan-4774/chrome`, `DISPLAY=:1`, notification permission granted, subscribes from Settings, and measures `POST /api/push/test` to the service worker's `push` event. The "unreadable at the push service" half registers a second subscription whose endpoint is a local capture server and asserts the captured request has `Content-Encoding: aes128gcm` and its body does not contain the notification title. Status is always "approximated: desktop Chrome, no phone".
- **D-11 AC-11 targets a peer test dashboard.** Stopping the home dashboard is not allowed (NFR-1). The production half sends a signed GitHub event to the directory inbox while the peer dashboard is stopped; the storage half reuses `directory-smoke.mjs` step `inbox`, which scans Miniflare storage of the same Worker code for the body marker. The evidence states that production Durable Object storage cannot be inspected and names the Miniflare run as the storage evidence.
- **D-12 AC-3 Tailscale is recorded, not run.** The orchestrator conversation runs **Set up Tailscale** on this host because sign-in needs the operator's browser. The agent asks with `pan tell conv-flywheel` and records the reply. The direct-route check (Tailscale off on both) runs before that request, because installing Tailscale on this host changes the "off on both" precondition.
- **D-13 AC-15's W-LINK7 harness half is the smoke's `update-all` step.** It already updates fake `claude` and `codex` on both machines; no separate run.
- **D-15 Fly items use a throwaway project, never a primary checkout.** Every project registered on this host points at a primary checkout (`panopticon-cli` is `/home/eltmon/Projects/overdeck`), and pulling into a clean target checks the branch out at the snapshot's base (`src/lib/vault/wip-apply.ts` header), which would move a primary checkout off its branch. So before AC-5 the agent picks a small public repository of the operator that no registered project names in `github_repo` (`gh repo list eltmon --visibility public --limit 200 --json nameWithOwner,diskUsage`, smallest unregistered one), clones it to `/home/eltmon/Projects/pan4774-anywhere-smoke`, registers it as project `pan4774-anywhere-smoke`, and uses `--project pan4774-anywhere-smoke` for AC-5 and AC-4. After AC-4 it unregisters the project and deletes that clone. AC-5 and AC-4 run one after the other because they share this registration.
- **D-14 AC-4 "three machines including Fly" is the home dashboard plus two Fly VMs** created with `pan machines add-fly`, because a peer dashboard on the same host is not a separate machine in the operator's sense.

### WI-2 `ac1-fake-claude` — the fake harness for the CI test (FR-1)

New file `tests/helpers/anywhere/fake-claude.ts` exporting `installFakeClaude(home: string, nodePath: string): { binDir: string; inputLog: string }`. It writes into `<home>/bin/`:

- `claude` (`#!/bin/sh`, mode 0755): on `--version|-v|version` prints `2.1.0 (Claude Code)` and exits 0. Otherwise it parses `--session-id <id>` or `--resume <id>`, runs `"$NODE" "$dir/fake-claude-writer.mjs" init "$id" "$PWD"` (only for `--session-id`), prints `❯ `, then loops `while IFS= read -r line; do … done`: strips `\e[200~` / `\e[201~`, appends the line to `$HOME/fake-claude-input.log`, runs the writer with `turn "$id" "$PWD" "$line"`, prints `❯ ` again. It never exits on its own. The script name stays `claude`, so the liveness oracle sees a `claude` process.
- `fake-claude-writer.mjs`: `init` creates `$HOME/.claude/projects/<encoded cwd>/<id>.jsonl` with one user and one assistant line; `turn` appends a user line with the text and an assistant line `fake-reply:<text>`. Every line has `type`, `uuid`, `sessionId`, `cwd`, `timestamp`, `message`; no `model`. Encoding rule: every character outside `[a-zA-Z0-9-]` becomes `-`.

Test: `tests/helpers/anywhere/__tests__/fake-claude.test.ts` spawns the fake with `--session-id <uuid>` in a temp cwd, writes `hello\n` to stdin, and asserts the JSONL has 4 lines, the last is an assistant line containing `fake-reply:hello`, and the input log contains `hello`.

### WI-4 `ac1-ci-test` — the AC-1 test (FR-1, FR-2, NFR-3, NFR-4)
