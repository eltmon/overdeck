# PAN-1728: plan-integrity verification gate — work agents cannot rewrite their own spec

**Issue:** [PAN-1728](https://github.com/eltmon/overdeck/issues/1728)
**Source design:** issue comment of 2026-09-29 (rescope from `.pan/drafts/deft-adoption.md`, "Issue 2: Work agents cannot rewrite their own plan"), approved by the operator on 2026-09-28.
**Related:** #4345 (gate-integrity rule names "your own spec"), #4348 (scope-drift evidence reads the same reference spec — it reuses the resolver this issue exports).

## Glossary

- **Spec** — the canonical xBRIEF plan for an issue: `.pan/specs/<YYYY-MM-DD>-<ISSUE>-<slug>.xbrief.json` (legacy suffix `.vbrief.json` still readable). It lives in the **plan home** and is committed on the issue's feature branch.
- **Plan home** — the git checkout that holds `.pan/`. For a monorepo it is the workspace itself. For a polyrepo project with `pan_records.repo` in `projects.yaml` it is that nested sub-repo inside the workspace. Resolved by `resolvePlanHome(path)` in `src/lib/pan-dir/paths.ts` (grep: `export function resolvePlanHome`).
- **Continue file** — `.pan/continues/<issue>.xbrief.json`; the only place item and AC completion is recorded (`pan task done`). Never the spec.
- **Allowed fields** — the five spec fields lifecycle writers legitimately change after planning: top-level `status`, `plan.status`, `plan.updated`, `plan.sequence`, `xBRIEFInfo.updated`. Written by `updateSpecStatus` (`src/lib/pan-dir/specs.ts`) and `updatePlanStatus` (`src/lib/xbrief/lifecycle-io.ts`, grep `doc.plan.sequence = (doc.plan.sequence ?? 0) + 1`).
- **Finalize commit** — the commit planning completion makes after it writes the spec: `commitCompletePlanningWorkspaceGit` in `src/lib/overdeck/planning-promotion.ts` (grep: ``chore(plan): complete planning for ${issueId}``).
- **`Plan-Finalized` trailer** — a new git trailer, `Plan-Finalized: <sha256-hex>`, on the finalize commit. The value is the SHA-256 of the spec file's bytes exactly as written at that commit.
- **Reference spec** — the copy of the spec the gate compares HEAD against. Resolved by the reference chain (FR-3).
- **Merge base** — `git merge-base HEAD origin/<targetBranch>` in the plan home.
- **plan-integrity** — the new required verification check this issue adds, beside `test-skip`.

## Problem

Specs are committed on the feature branch (`docs/XBRIEF.md`, "Canonical plan state"). A work agent can therefore edit its own acceptance criteria or item statuses, and the edit rides the merge to main. PAN-1700's agent did exactly this: commit `d897ca1f4` "chore: mark PAN-1700 acceptance criteria complete" edited `.pan/specs/2026-06-10-PAN-1700-*.vbrief.json`. The invariant is documented (`docs/XBRIEF.md`: "The canonical spec is immutable after planning except for lifecycle status changes and explicit re-planning") but nothing enforces it. `roles/work.md` also never tells the work agent not to edit `.pan/specs/` (verified: its Per-Task Workflow section mentions only `pan task` and `.overdeck/continue.json`).

Legitimate writes to the same file exist and must keep passing:

1. **Finalize** writes the whole spec (first planning, and active-plan repair re-finalizes at the same filename — `docs/XBRIEF.md` lifecycle step 4).
2. **`pan start`** changes status fields only, through `transitionStartedXBrief` → `transitionXBriefOnMain` → `updateSpecStatusSync` + `updatePlanStatus` (`src/cli/commands/start-status.ts`), and `updateWorkspaceDraftPlanStatus` → `updatePlanStatus`.
3. **`pan start --auto`** synthesizes a minimal spec with `writeAutoStartXBrief` (`src/lib/xbrief/auto-synthesize.ts`, called at `src/cli/commands/start.ts` grep `writeAutoStartXBrief(projectRoot, workspace, issue)`) and never makes a finalize commit.

Close-out's `completed` transition and `pan scope` transitions happen on main after merge and are not seen by verification.

## Decisions (made here; recorded as autoDecisions in the plan)

- **D1 — Reference chain.** Newest valid finalize commit on the branch → merge-base copy → first commit on the branch that added a spec file for the issue. "Valid finalize commit" = a commit in `mergeBase..HEAD` carrying a `Plan-Finalized` trailer whose value equals the SHA-256 of the issue's spec blob at that commit, OR (legacy, pre-this-change) a commit whose subject matches `chore(plan): complete planning for <ISSUE>` case-insensitively and that touches the issue's spec. The third fallback and the legacy subject are additions to the approved design: without them every in-flight branch and every `pan start --auto` spec has no reference, and a re-planned in-flight branch would fail a check its agent cannot fix by editing code.
- **D2 — Hash.** SHA-256 hex over the spec file's exact bytes as committed. The gate verifies the blob at the trailer commit hashes to the trailer value; a mismatched trailer is not a reference and is reported as evidence.
- **D3 — Threat model.** This gate catches misguided edits (the observed `chore: mark … acceptance criteria complete`). It does not stop deliberate forgery: an agent can compute a hash and write the trailer itself. `roles/work.md` forbids both editing `.pan/specs/` and writing the trailer.
- **D4 — Polyrepo in scope.** Finalize makes its trailer commit in the repo that actually holds the spec (`git rev-parse --show-toplevel` run in the spec's directory). When that repo is the wrapper (`gitRoot`), the existing commit carries the trailer. When it differs, the wrapper commit stays as today and a second commit in the spec repo stages `.pan/` with the trailer. The gate runs in `resolvePlanHome(workspacePath)`.
- **D5 — Conflict markers.** When the HEAD spec contains conflict markers (`<<<<<<<`, `=======`, `>>>>>>>` all present), plan-integrity passes with evidence "spec has merge-conflict markers; vbrief-conflicts owns this" so the existing `vbrief-conflicts` check and its instructions still fire.
- **D6 — Fail-closed boundary.** Mirror test-skip (PR #3872 finding 4): a git command that fails inside a valid plan-home work tree fails the gate with the diagnostic. Pass-with-evidence exceptions: the plan home is not a git work tree; no spec for the issue at HEAD and none at the reference; HEAD spec has conflict markers (D5).
- **D7 — Remediation in the evidence.** The generic failure feedback says "fix the code". The gate's evidence therefore ends with the exact fix: `git restore --source=<refSha> -- <specPath>`, commit, record completion with `pan task done`; if the plan itself is wrong, stop and ask for re-planning (`pan plan <ISSUE>`). Never `git checkout` (worktree-discipline rule).
- **D8 — Filename set.** The gate compares the set of spec filenames for the issue at the reference and at HEAD. An added, removed, or renamed spec file fails. Same-named pairs are diffed field by field.
- **D9 — Order in the runner.** test-skip runs first (unchanged). If it passes, plan-integrity runs. If plan-integrity fails, the quality gates do not run and the gate results are one `plan-integrity` failure row, exactly like test-skip.
- **D10 — No one-off branch audit.** The issue's old check #3 ("audit in-flight branches") is replaced by the gate itself: every branch is checked at its next verification.

## Requirements

- **FR-1** A pure function diffs a reference spec document against a HEAD spec document, ignoring only the five allowed fields, and returns one violation per changed item id (added, removed, or changed, recursing into nested `items`) plus one per changed non-item path (e.g. `plan.narratives`, `plan.edges`, `plan.title`).
- **FR-2** Planning finalize writes `Plan-Finalized: <sha256>` on the commit that contains the finalized spec, in the repo that holds the spec (monorepo and polyrepo).
- **FR-3** A resolver returns the reference spec for an issue in a plan home by the D1 chain, and is a named export reusable by #4348.
- **FR-4** Verification runs a required `plan-integrity` check after test-skip and before the quality gates; a failure emits `verification.failed { failedCheck: 'plan-integrity' }` and its evidence names each violating item id and the remediation (D7).
- **FR-5** A branch whose only spec changes are the allowed fields passes; a branch with no spec change passes; a branch with a later valid finalize commit that changes items passes against that commit.
- **FR-6** `roles/work.md` forbids editing `.pan/specs/` and writing a `Plan-Finalized` trailer, and names the plan-integrity gate.
- **FR-7** `docs/PIPELINE-GATES.md` and `docs/XBRIEF.md` describe the gate, the trailer, and the reference chain; XBRIEF.md lifecycle step 3 is corrected to match the code.
- **NFR-1** Async git only (`execFile` promisified) — the runner is server-reachable; no `execSync`.
- **NFR-2** Nothing is stored: the reference is derived from git on every run.
- **NFR-3** Growth of `verification-runner.ts` and `planning-promotion.ts` carries a `# PAN-1728` allowlist row in the same commit; runner growth is limited to wiring.

### WI-1 Trailer helper (foundation) — FR-2, FR-3

New file `src/lib/xbrief/plan-finalized.ts`:

```ts
import { createHash } from 'node:crypto';

/** Git trailer key planning finalize writes on the commit holding the finalized spec (PAN-1728). */
export const PLAN_FINALIZED_TRAILER = 'Plan-Finalized';

/** SHA-256 hex over the spec file's exact bytes. */
export function planFinalizedHash(bytes: string | Buffer): string {
  return createHash('sha256').update(bytes).digest('hex');
}

/** `Plan-Finalized: <hash>` — the last paragraph of a commit message. */
export function formatPlanFinalizedTrailer(hash: string): string {
  return `${PLAN_FINALIZED_TRAILER}: ${hash}`;
}

/** Legacy finalize subject, written before the trailer existed. */
export function isLegacyFinalizeSubject(subject: string, issueId: string): boolean {
  return subject.trim().toLowerCase() === `chore(plan): complete planning for ${issueId.toLowerCase()}`;
}
```

### WI-2 Pure spec diff — FR-1

```ts
export interface PlanIntegrityViolation {
  /** Item id for item changes; dotted JSON path otherwise (e.g. `plan.narratives`). */
  subject: string;
  kind: 'item-added' | 'item-removed' | 'item-changed' | 'field-changed';
  /** Changed item keys for item-changed (e.g. ['title', 'status']). */
  keys?: string[];
}

export function diffPlanDocuments(reference: unknown, head: unknown): PlanIntegrityViolation[];
```

Steps: (1) `normalizeXBriefEnvelope` both; (2) deep-clone and delete the five allowed fields; (3) walk `plan.items` recursively, keyed by `id`, comparing each item minus its nested `items` with a stable deep-equal (key order must not matter — serialize with sorted keys); (4) compare every other top-level `plan.*` key and every non-`plan` top-level key; report `field-changed` with the dotted path. Items without an `id` are compared by array position under subject `plan.items[<n>]`.

Test `tests/unit/lib/cloister/plan-integrity-gate.test.ts`:
- changed item `title` → `[{ subject: '<id>', kind: 'item-changed', keys: ['title'] }]`;
- changed nested AC status (`x.ac1` `pending`→`completed`) → violation subject `x.ac1`;
- only `status: proposed→active`, `plan.status→running`, `plan.updated`, `plan.sequence`, `xBRIEFInfo.updated` changed → `[]`;
- identical docs → `[]`; reordered object keys → `[]`;
- `plan.narratives.Problem` changed → `field-changed` `plan.narratives`;
- item added / removed → `item-added` / `item-removed`;
- a legacy `vBRIEFInfo` reference vs `xBRIEFInfo` head with equal content → `[]`.

### WI-3 Reference resolver and gate run — FR-3, FR-4, FR-5 (depends on WI-1, WI-2)

New file `src/lib/cloister/plan-integrity-run.ts`, mirroring `test-skip-run.ts`. Async `execFile` only.

```ts
export interface PlanReference {
  kind: 'trailer' | 'legacy-finalize' | 'merge-base' | 'first-add';
  sha: string;
  /** Spec paths (relative to the plan home) for the issue at `sha`. */
  specPaths: string[];
  /** Evidence lines, e.g. an ignored mismatched trailer. */
  notes: string[];
}

export async function resolvePlanReference(planHome: string, issueId: string, baseRef: string): Promise<PlanReference | null>;

export interface PlanIntegrityEvaluation { failed: boolean; evidence: string; error?: string }

export async function evaluatePlanIntegrityGate(
  issueId: string,
  workspacePath: string,
  roots: readonly { repoKey: string; dir: string; targetBranch: string }[],
): Promise<PlanIntegrityEvaluation>;
```

Steps for `evaluatePlanIntegrityGate`:
1. `planHome = resolvePlanHome(workspacePath)`. If `git rev-parse --is-inside-work-tree` fails there → `{ failed: false, evidence: 'plan home <path> is not a git work tree; plan-integrity skipped' }`.
2. `targetBranch` = the root whose `realpath(dir) === realpath(planHome)`, else `roots[0]?.targetBranch ?? 'main'`. `baseRef = origin/<targetBranch>`; `mergeBase = git merge-base HEAD <baseRef>` (failure → fail closed with the message).
3. Spec files for the issue at a commit: `git ls-tree --name-only <sha> .pan/specs/` filtered by `parseXBriefFilename(name)?.issueId.toUpperCase() === issueId.toUpperCase()`.
4. `resolvePlanReference`: `git log --format=%H%x1f%s%x1f%(trailers:key=Plan-Finalized,valueonly,separator=%x2c)%x1e <mergeBase>..HEAD`, newest first. First commit with a trailer whose value equals `planFinalizedHash(git show <sha>:<specPath>)` for a spec path at that commit → `trailer`; a trailer that does not match → note `ignored Plan-Finalized trailer on <sha8>: hash mismatch` and continue. Else first commit with `isLegacyFinalizeSubject` that touches the issue's spec (`git diff-tree --no-commit-id --name-only -r <sha> -- .pan/specs/`) → `legacy-finalize`. Else if the merge base has spec files for the issue → `merge-base`. Else `git log --diff-filter=A --reverse --format=%H <mergeBase>..HEAD -- .pan/specs/` first commit that added an issue spec → `first-add`. Else `null`.
5. HEAD spec files = step 3 on `HEAD`. If none and reference is `null` → pass, evidence `no spec for <ISSUE>`. If any HEAD spec bytes contain all three conflict markers → pass with D5 evidence.
6. Filename sets differ → violation lines `spec file added: <path>` / `spec file removed: <path>`.
7. For each same-named pair: equal bytes → no violation; else `JSON.parse` both (HEAD parse error → violation `spec does not parse at HEAD: <msg>`) and `diffPlanDocuments`.
8. Evidence: first line `reference: <kind> <sha8>`, then notes, then one line per violation: `item <id>: changed <keys>` / `item <id>: added` / `item <id>: removed` / `<path>: changed`. When failed, append the D7 remediation using the reference sha and spec path(s).

Tests `tests/unit/lib/cloister/plan-integrity-run.test.ts` — real temp git repos (`git init`, a bare `origin`, `main` pushed, feature branch; `-c user.name=t -c user.email=t@t`), with `resolvePlanHome` mocked to return the temp repo:
- spec added in a trailer commit, then a later commit changes an AC status → `failed: true`, evidence names the AC id and contains `git restore --source=`;
- later commit changes only allowed fields → `failed: false`;
- no spec change after the trailer commit → `failed: false`;
- a second trailer commit (valid hash) that changes an item → `failed: false`, evidence `reference: trailer <second sha8>`;
- trailer with a wrong hash is ignored → reference falls back and evidence contains `hash mismatch`;
- legacy subject commit then an item edit → `failed: true` with `reference: legacy-finalize`;
- spec on main (merge base) edited on branch → `failed: true`, `reference: merge-base`;
- no finalize commit, spec added by a plain commit then edited → `failed: true`, `reference: first-add`;
- conflict markers at HEAD → `failed: false`, evidence mentions `vbrief-conflicts`;
- non-git directory → `failed: false`;
- unknown `origin/<target>` inside a git repo → `failed: true` (fail closed).
