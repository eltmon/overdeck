# Conversation open: why the skeleton lingers (2026-09-28)

Scope, narrowed mid-investigation by the operator: opens take about a second now, so this is low priority. The report covers only simple, clearly wasteful work on the path that opens a conversation. It proposes no redesign. Code was read from `origin/main` @ `66712fd5f60`. All measurements ran against the live dashboard (PID 2719601, generation-b, up about 1h35m) at load average 17–24 on 24 cores. **Nothing was measured at idle.**

## Verdict

1. **The conversation lookup at the start of every live stream waits behind 13-second search-stats queries on the same worker thread.** `subscribeConversationMessages` resolves the conversation row with `runDashboardDbJob('getConversationByName')`, which uses the `read` worker lane. That lane runs one job at a time, and it also runs the polling aggregates:
   - `getConversationSearchStats`: `count(*)` and `max(indexed_at)` over 277,857 chunks in a 3.07 GB embeddings DB. It refreshes every 60 s. This boot it ran for more than 1 s **44 times, median 13.4 s, max 34.3 s**.
   - `getCostsByIssueSnapshot`: about 1.2 s every 15 s.

   The lookup itself takes 0–1 ms. This boot it still **waited more than 1 s 9 times, median 11.5 s, max 17.6 s** (`[db-jobs] slow: op=getConversationByName lane=read waitMs=…`). While it waits, the skeleton stays up, unless the redundant HTTP fetch in item 3 lands first. `docs/DASHBOARD-ARCHITECTURE.md` says the read lane is for "interactive lookups". The polling aggregates were put on it on 2026-09-09 (`e5ad47170b5`). This is the "sometimes it takes forever" case, and host CPU load makes it worse (see the CPU-contention section).
2. **Size-proportional work runs synchronously on the main thread.** `computeContextUsage` reads everything since the last compact boundary, which is the whole file when there is no boundary. It JSON-parses every line on the event loop, even though the parse result it sits next to already carries `latestAssistantUsage` and `contextActiveBytes`. It costs 30 ms for 2972 (7 MB), 61 ms for 2884 (15 MB active) and 297 ms for 2832 (76 MB, plus a 364 ms first boundary scan). A hard-load deep link runs it twice: once in `GET /api/conversations/:id` and once in `GET …/messages`.
3. **Every live conversation is loaded twice.** `ConversationPanel` fires `GET /api/conversations/<name>/messages` in the same millisecond as the WebSocket subscribe. Its `cancelQueries` calls run *before* the query starts, so they cancel nothing. The HTTP response carries the same payload as the WebSocket frame: 811 KB vs 814 KB for 2973, and 2.69 MB vs 2.71 MB for 2884. That means a second parse, a second `computeContextUsage` and a second JSON encode on the main thread. Today this duplicate is the accidental hedge against item 1, so it has to be fixed *after* item 1.

Typical numbers at load 17–24:
- **In-app open** (pushState to `/conv/<id>`): skeleton to first rendered row takes **0.5–0.8 s** for transcripts under 10 MB and **1.7 s** for 2884 (34 MB file, 2.7 MB payload).
- **Browser render** after the frame arrives takes 40–90 ms. The rest is server time.
- **Hard load** of `/conv/2972`: first row at **3.0–6.3 s**. Most of that time passes *before* the skeleton appears (see "Not quick wins").

On conv 2972 (`20260928-7563`, the operator's screenshot): the "29.5M tokens" figure is cumulative token usage. The transcript file is 6.9 MB, has 0 compact boundaries and produces a 484 KB payload. In-app it opened in about 0.5 s. When 2972 sat on the skeleton, the likeliest cause is the read-lane stall in item 1, not transcript size. Transcript size shows up in 2884 and 2832.

## Why CPU contention makes it worse

Nothing here was measured at idle, so this section rests on mechanism plus the loaded-state evidence above.

- **Fixed-cadence jobs grow longer on a shared single-slot queue.** The read lane runs one job at a time. The search-stats refresh (every 60 s) and the cost snapshot (every 15 s) take longer when the host is saturated: runMs goes up to 34 s, and the slow log shows `depth=2..5` queues behind them. Any `getConversationByName` that arrives during one waits for the rest of it. At this boot's rates the read lane is busy with aggregates about 14 % of the time (44×13.4 s plus 173×1.2 s over about 95 min). So roughly 1 in 7 live opens can stall, for about half a job (around 6 s) on average.
- **Main-thread synchronous work.** `computeContextUsage` (sync JSON.parse of up to 76 MB), `getCachedMessages` (main-thread parser), JSON encoding of 0.5–2.7 MB responses and frames, and the 5.35 MB `getSnapshot` encode all run on the one event loop. That loop already runs at a p99 of 250–600 ms with nobody opening anything. When cores are oversubscribed, each of these slices gets less CPU, so the queue of pending requests drains more slowly.
- **Subprocess fan-out.** `/diffs` for 2973 spawns 84+ serial `git diff` processes per 5 s tick, taking 2–7 s per call. Every spawn competes for the same saturated cores, and each call burns event-loop turns on subprocess I/O.

## Not quick wins (explicitly out of scope)

- **The hard-load burst.** On a cold `/conv/<id>` load, DOMContentLoaded to skeleton takes 1.9–5.1 s. About 60 parallel REST calls, the per-issue deck fan-out and a 5.35 MB `getSnapshot` frame saturate the event loop before the conversation row resolves. Fixing it means prioritizing or deferring deck loads, which is a design change.
- **Windowing the initial payload.** For example, sending the tail N messages first for 2884's 2.7 MB. Payload size is what makes 2884 take 1.7 s, but the virtualized timeline, subagent rail and message locator all assume the full history.
- **Background main-thread load.** About 40–60 % of a core, with a p99 event-loop lag of 250–600 ms at rest. Finding its source needs a CPU profile of the live server, which was not taken because this investigation was read-only.

## Ready-to-file issue

**Title:** Conversation open stalls behind polling aggregates on the `read` worker lane; duplicate transcript loads on open

**Body:**

### Problem
Opening a conversation sometimes holds the transcript skeleton for seconds. Two things cause it:
- The WebSocket stream cannot send its first payload until `getConversationByName` has run as a worker job. That job shares the single-slot `read` lane with polling aggregates that take up to 34 s.
- Every open also repeats transcript work: a duplicate HTTP `/messages` load for live conversations, synchronous context-usage re-parses on the main thread, and `/diffs` spawning git per turn every 5 s.

The waits get longer as host CPU load rises.

### Findings
Measured 2026-09-28, load 17–24. Details in `.tmp/conversation-load-perf-2026-09-28.md`.
- In the current boot, `getConversationByName` (0–1 ms of runtime) waited more than 1 s 9 times, p50 11.5 s, max 17.6 s. It was queued behind `getConversationSearchStats` (44 runs over 1 s, p50 13.4 s, max 34.3 s; `count(*)` over 277k chunks in a 3 GB DB) and `getCostsByIssueSnapshot` (about 1.2 s every 15 s). Cause: `dashboard-db-task.ts:workerLane` routes `isPollingSnapshot` ops to `read` (`e5ad47170b5`, 2026-09-09). The docs say `read` is for interactive lookups.
- `computeContextUsage` JSON-parses the whole active window synchronously on the main thread: 30 ms (7 MB), 61 ms (15 MB) and 297 ms (76 MB) per call. It runs in `getConversationRead` and in `getConversationMessagesRead`, even though `parsed` already carries `latestAssistantUsage` and `contextActiveBytes`.
- `ConversationPanel` issues `GET …/messages` alongside the WebSocket subscribe for every live conversation. The `cancelQueries` effects run before the query starts, so the request is never cancelled. It returns the same 0.5–2.7 MB payload.
- The Claude initial snapshot (`parseTranscriptSnapshot` with `claude-initial`) is an uncached full-file parse on the single-slot `parse` lane. It takes 2–3.2 s for 76–120 MB transcripts.
- `/diffs` runs 2 serial `git diff`s per edited turn, every 5 s, including for ended conversations. That is 84+ spawns and 2–7 s per call for a 42-edit-turn conversation.

### Fix
1. Add a `poll` worker lane. Route `getCostsByIssueSnapshot`, `getConversationSearchStats`, `getAgentCostStats` and `getConversationLedgerCosts` to it, so `read` serves only point lookups.
2. `getConversationMessagesRead`: derive context usage with `contextUsageFromParseResult(parsed, conv.model)`. `getConversationRead`: memoize `computeContextUsage` by `(path, size, mtimeMs)`.
3. After (1): make the HTTP `/messages` query for streaming conversations a fallback that starts only when no stream payload has arrived after about 1.5 s. Remove the dead `cancelQueries` effects.
4. Memoize and coalesce the `claude-initial` snapshot by `(dev, ino, size, mtime)`, as `sharedTranscriptParser` does.
5. `/diffs`: poll only while `sessionAlive`. Run one git diff pair per repo, not per turn. Cache by transcript size and repo HEAD.
6. `getConversationSearchStats` / `getStats()` in `conversation-embeddings-db.ts`: stop scanning `chunks` and reopening the 3 GB DB with sqlite-vec on each refresh. Profile both, then maintain counts or index `indexed_at`.

### Acceptance criteria
- [ ] With conversation search enabled, zero `[db-jobs] slow: op=getConversationByName` lines appear in a 30-minute dashboard.log window after deploy (the slow log fires at more than 1 s; today there are 9 in about 95 min).
- [ ] `workerLane('getConversationSearchStats')` (and the other three polling ops) returns `'poll'`, and `workerLane('getConversationByName')` returns `'read'`.
- [ ] `GET /api/conversations/20260919-9189/messages` (76 MB, no compact boundary) completes in under 150 ms warm (today: 281–458 ms), and `getConversationMessagesRead` never calls `computeContextUsage` when a parse result is present (unit test).
- [ ] Opening a live conversation in-app issues zero `GET …/messages` requests when the first WebSocket payload arrives within 1.5 s. Verify with a Playwright network log.
- [ ] Opening an ended conversation issues zero `GET …/diffs` requests after the first, and the server spawns no `git` for it.
- [ ] `/diffs` for a conversation with N edited turns in one repo spawns at most 2 `git diff` processes per call (today 2·N).
- [ ] In-app open of a 10 MB live transcript, skeleton to first row: p90 under 1 s across 10 opens at load 20 or higher (today, stalls reach 17 s).

### Tests
- `src/dashboard/server/services/__tests__/dashboard-poll-worker.test.ts`: update the `it.each` lane assertion to `'poll'`, and add a case for `getConversationByName` staying on `read`.
- New `src/lib/overdeck/__tests__/conversation-messages-read-context-usage.test.ts`: `getConversationMessagesRead` returns the context usage derived from the parse result and does not call `computeContextUsage`. `getConversationRead` reuses the memoized result when size and mtime are unchanged.
- `src/dashboard/frontend/src/components/chat/__tests__/useConversationMessagesStream.test.ts` (or a new `ConversationPanel` messages-query test): with streaming enabled, the HTTP query does not fire before the fallback delay, and does fire when no payload arrives.
- New `src/lib/overdeck/__tests__/conversation-diffs.test.ts`: N turns in one repo produce one git diff pair. The results are split per turn correctly.
- `src/dashboard/server/services/__tests__/` (shared-transcript-parser): a `claude-initial` snapshot is reused for an unchanged signature and coalesced for concurrent subscribers.

### Docs
- `docs/DASHBOARD-ARCHITECTURE.md`, section "DB job worker lanes": add the `poll` lane, state that `read` is for point lookups only, and add a rule that aggregates never share a lane with lookups on an interactive path.
- `docs/DASHBOARD-ARCHITECTURE.md` (conversation streaming section): the open sequence (WebSocket first payload, HTTP fallback timer) and where context usage comes from.
- `../overdeck-knowledge/frontend/conversation-ui.md` and `../overdeck-knowledge/frontend/data-flow.md`, via `/okf author`: the conversation-open critical path and the fallback rule.
