# PAN-4312 — Conversation open: take polling aggregates off the read lane and stop duplicate transcript work

**Issue:** [PAN-4312](https://github.com/eltmon/overdeck/issues/4312). **Status:** planned 2026-09-28 (auto mode). Code references were verified against `feature/pan-4312` @ `4b6ad0f0d97` (same tree as `origin/main` at planning time). The original investigation report (measurements at load 17–24, regressions, critical-path table) is kept unchanged as the appendix at the end of this document.

The investigation found that the conversation stream's first payload waits for a 0–1 ms row lookup that sits in a one-slot worker queue behind 13-second polling aggregates, and that every open repeats size-proportional transcript work. This PRD turns the investigation's six quick wins into nine executable work items plus one documentation item. It proposes no redesign.

## Glossary

- **Worker lane.** One `node:worker_threads` Worker in `src/dashboard/server/services/dashboard-db-task.ts`. Each lane runs one job at a time (`MAX_CONCURRENT_JOBS_PER_LANE = 1` in `dashboard-db-worker.ts`). Today there are four: `read`, `long`, `semantic`, `parse` (`export type WorkerLane = 'read' | 'long' | 'semantic' | 'parse';`, line 64).
- **Polling aggregate / polling snapshot.** One of the four operations `isPollingSnapshot()` recognises (line 381): `getAgentCostStats`, `getCostsByIssueSnapshot`, `getConversationSearchStats`, `getConversationLedgerCosts`. Each is wrapped by `createRefreshingSnapshot` in `src/dashboard/server/services/dashboard-poll-snapshots.ts` (15 s TTL for costs, 60 s for search stats, 5 min max age).
- **Point lookup.** A worker job that reads one row or a few rows by key, such as `getConversationByName`. It runs in milliseconds.
- **Open path.** Everything between the operator selecting a conversation and the first transcript row rendering: route → conversation row → `ConversationPanel` mount → `TranscriptLoadingSkeleton` → first WebSocket payload (live) or HTTP `/messages` (ended).
- **First payload.** The first `ConversationEvent` that `useConversationMessagesStream` receives for the current stream identity. It flips `receivedFirstPayload` to true (`useConversationMessagesStream.ts`, `setFirstPayloadIdentity(streamIdentity)`).
- **Streaming conversation.** A conversation for which `shouldStreamConversationMessages()` returns true: a real row (`id >= 0`), no `endedAt`, and a harness that supports streaming. Ended conversations use HTTP only.
- **HTTP fallback.** The new rule for streaming conversations: the HTTP `GET /api/conversations/:name/messages` query starts only if no first payload has arrived within `MESSAGES_HTTP_FALLBACK_MS` (1500 ms).
- **`claude-initial` snapshot.** The full-file parse `streamClaudeTranscript` requests with `runDashboardDbJob('parseTranscriptSnapshot', { sessionFile, parser: 'claude-initial' })` before it starts the incremental watcher.
- **Snapshot signature.** `${dev}:${ino}:${size}:${mtimeMs}` from `fs.stat`, the key `sharedTranscriptParser` uses to reuse an unchanged parse (`src/dashboard/server/services/shared-transcript-parser.ts`).
- **Parse state containers.** The `Map`/`Set` fields the incremental parser mutates in place when it receives them through `priorState`: `pendingToolUse`, `unresolvedResults`, `planToolUseIds`, `countedUsageIds` (`src/dashboard/server/services/conversation/parser.ts`, lines 149–175, mutations at 258, 268, 323, 371, 424, 434).
- **Context usage.** The `ContextUsage` object the composer meter shows. `computeContextUsage(sessionFile, model)` derives it by reading and JSON-parsing the active window of the file. `contextUsageFromParseResult(result, model)` derives the same object from fields a parse already produced (`latestAssistantUsage`, `contextActiveBytes`). Both live in `src/dashboard/server/services/conversation/context-usage.ts`.
- **Diff pair.** The two `git diff` invocations (`--numstat` and `--name-status`) that `diffFilesSinceBase` or `diffFilesAgainstHead` runs for one set of paths.
- **File-size ratchet.** `scripts/lint-file-size.sh` fails when a file above 1000 lines grows past its allowed count: its last row in `scripts/file-size-allowlist.txt` (`<lines> <path> # <ISSUE>`) when one exists, otherwise its `origin/main` line count. The last row for a path wins.

## Requirements

### Functional

- **FR-1.** The four polling aggregates run on a new `poll` worker lane. `workerLane()` returns `'poll'` for them and still returns `'read'` for `getConversationByName`.
- **FR-2.** `getConversationSearchStats` no longer scans the `chunks` table for `max(indexed_at)`. `lastIndexedAt` comes from `max(updated_at)` over `file_cursors` rows with `byte_offset > 0`.
- **FR-3.** `getConversationMessagesRead` derives `contextUsage` from its parse result with `contextUsageFromParseResult(parsed, conv.model)` and never calls `computeContextUsage`.
- **FR-4.** `computeContextUsage` returns a memoized result when it is called again for the same `(sessionFile, model)` and the file's `size` and `mtimeMs` are unchanged. `getConversationRead` gets this for free.
- **FR-5.** For a streaming conversation, `ConversationPanel` does not issue `GET …/messages` until 1500 ms pass without a first payload. The query is disabled again once a first payload arrives. Non-streaming conversations and panels with an `agentId` keep today's behavior.
- **FR-6.** Resume, switch-model and fork completion still re-read `/messages` over HTTP once, even while the messages query is disabled.
- **FR-7.** The dead `cancelQueries` calls on the messages key are removed from `ConversationPanel.tsx` and `useConversationMessagesStream.ts`.
- **FR-8.** `streamClaudeTranscript` reuses an unchanged `claude-initial` snapshot through `sharedTranscriptParser('claude-initial')`, and each subscriber receives its own copies of the parse state containers.
- **FR-9.** `getConversationDiffs` runs at most one diff pair per repo per call. It splits the per-repo result back into per-turn summaries.
- **FR-10.** `getConversationDiffs` returns a cached result for 30 s when the transcript's `size` and `mtimeMs` are unchanged.
- **FR-11.** The `/diffs` query in `ConversationPanel` polls every 5 s only while `conversation.sessionAlive` is true. Otherwise it fetches once.
- **FR-12.** `docs/DASHBOARD-ARCHITECTURE.md` and the OKF pages `frontend/conversation-ui.md` and `frontend/data-flow.md` describe the `poll` lane, the lane rule, the open sequence with the HTTP fallback, and where context usage comes from.

### Non-functional

- **NFR-1.** No new synchronous work on the dashboard main thread. No `execSync` (dashboard server rule).
- **NFR-2.** Tests that exercise the 1500 ms fallback or the 30 s diffs TTL use `vi.useFakeTimers()` and `vi.advanceTimersByTime*()`. Never wait on real timers (repo rule: fake timers for delay-based tests).
- **NFR-3.** The file-size ratchet stays green. `src/dashboard/server/ws-rpc.ts` is at exactly its last allowlist row (1219 lines, `# PAN-3668`) and must not grow. `ConversationPanel.tsx` is at 1524 lines with a last row of 1531 (`# PAN-3773`); it must stay at or under 1531.
- **NFR-4.** Quality gates before `pan done`: `npm run typecheck`, `npm run lint`, and `npx vitest run <touched test files>`. Never run the full `npm test` on the host.

## Decisions

These were made in auto-planning mode. Each is also recorded in the xBRIEF `plan.autoDecisions[]`.

1. **One new `poll` lane, not the existing `long` lane.** `long` runs `costReconcileSweep`, `scanConversations`, `enrichSessions` and `embedSessions`, which can run for minutes. A 15 s cost snapshot queued behind one of them would outlive its 5-minute `maxAgeMs` and the route would start returning errors. A fifth worker thread costs one extra V8 isolate; that is accepted.
2. **All four aggregates share the one `poll` lane**, as the issue specifies. The conversation list's cold read (`conversation-list.ts` line 161 awaits `getConversationLedgerCostsSnapshot()`) can wait behind a search-stats run right after boot. That is no worse than today, and FR-2 cuts search stats from about 9 s to under 300 ms.
3. **Search stats: read `lastIndexedAt` from `file_cursors`, keep `count(*)`, keep the per-refresh open.** Measured read-only against the live 3.07 GB `~/.panopticon/conversations/embeddings.db` at load 16.6 (2026-09-28): open plus sqlite-vec load 3.0 ms; `SELECT count(*) FROM chunks` 290 ms (it uses the covering index `sqlite_autoindex_chunks_1`); `SELECT max(indexed_at) FROM chunks` **9005 ms** (no index, full scan through overflow pages); `SELECT max(updated_at) FROM file_cursors` 0.4 ms; the existing `file_cursors` count 8 ms. Rejected alternatives: an index on `chunks(indexed_at)` needs a one-time full scan inside `migrateSchema` at open (about 9 s, blocking the first opener) and adds write cost to every upsert; a `db_config` counter row changes the indexer write path. Semantics: `setCursor` stamps `updated_at` each time the indexer advances a file's cursor, so the value means "last time the indexer advanced a cursor". The indexer's reset call `db.setCursor(filePath, 0)` (`src/lib/conversation-search/indexer.ts` line 129) is excluded by the `byte_offset > 0` filter.
4. **Memoize inside `computeContextUsage`**, not in `getConversationRead`. The key is `${sessionFile}\0${model ?? ''}`, validated by `size` and `mtimeMs`, in a module-level `Map` capped at 16 entries (evict the oldest insertion). This covers `getConversationRead` without touching it.
5. **HTTP fallback delay is 1500 ms**, as the issue proposes, in a new hook file so `ConversationPanel.tsx` does not grow (NFR-3).
6. **Resume, switch-model and fork completion use `queryClient.fetchQuery`.** `invalidateQueries` does not refetch a disabled query, and these three events are exactly when the stream may still be watching the old session file. `fetchQuery` runs whether or not the query is enabled and writes the result into the same cache key. The query function keeps its existing "prefer the streamed cache if it is at least as complete" merge (PAN-1642).
7. **The `claude-initial` snapshot shares `sharedTranscriptParser`'s existing cache and budget** (8 entries, 32 MB of transcript bytes, one oversized entry kept). Concurrent identical requests already coalesce today through `COALESCED_OPERATIONS` plus `sharedJobs` in `dashboard-db-task.ts`, so this item adds cross-time reuse only. A 76 MB Claude transcript can evict the other cached parses; they are re-parsed on the next new subscriber, which is today's behavior anyway.
8. **Diffs cache key is `(conversation name, sessionFile, size, mtimeMs)` with a 30 s TTL. Repo HEAD is not in the key.** `git diff <base> -- <paths>` compares the base commit against the working tree, so HEAD does not decide the result. The TTL bounds staleness from working-tree changes made outside the conversation.
9. **Live measurements are post-deploy verification, not item acceptance criteria.** The 30-minute `dashboard.log` window, the p90 open latency at load 20 and the 150 ms warm `/messages` target need the deployed dashboard. They are listed under "Post-deploy verification" below. Item acceptance criteria are named unit tests plus one Playwright check the test role can run.
10. **The OKF pages are committed in the separate `overdeck-knowledge` repo** (`/home/eltmon/Projects/overdeck-knowledge`, remote `eltmon/overdeck-knowledge`) through `/okf author`, inside the documentation item. The item's `Item:` trailer commit is the `docs/DASHBOARD-ARCHITECTURE.md` change on the feature branch.
11. **Accepted consequences, not fixed here.** (a) `getConversationMessagesRead` calls `updateConversationCost` (a DB write on a GET). Streaming conversations no longer hit that route on open, so opening one no longer refreshes `conversations.total_cost`. The conversation list already prefers the ledger cost (`conversation-list.ts` line 265: `totalCost: ledger ? ledger.cost : row.totalCost`). (b) For non-Claude transcripts, HTTP `contextUsage` now comes from the parser's own usage fields rather than from a Claude-shaped scan that found nothing. That matches what the WebSocket path already sends.

```ts
// after (sketch; match the file's style)
const CONTEXT_USAGE_CACHE_MAX = 16;
const contextUsageCache = new Map<string, { size: number; mtimeMs: number; usage: ContextUsage | null }>();

export async function computeContextUsage(sessionFile: string, model: string | null): Promise<ContextUsage | null> {
  const capability = resolveContextCapability(model);
  if (!capability) return null;

  const fileStats = await stat(sessionFile);
  const key = `${sessionFile}\0${model ?? ''}`;
  const cached = contextUsageCache.get(key);
  if (cached && cached.size === fileStats.size && cached.mtimeMs === fileStats.mtimeMs) return cached.usage;

  const boundaryOffset = await findLastCompactBoundary(sessionFile);
  const activeBytes = Math.max(0, fileStats.size - boundaryOffset);
  const usageSummary = await readLatestAssistantUsage(sessionFile, boundaryOffset, activeBytes);
  const usage = buildContextUsage(capability, activeBytes, usageSummary);
  contextUsageCache.delete(key);
  contextUsageCache.set(key, { size: fileStats.size, mtimeMs: fileStats.mtimeMs, usage });
  if (contextUsageCache.size > CONTEXT_USAGE_CACHE_MAX) contextUsageCache.delete(contextUsageCache.keys().next().value!);
  return usage;
}
```

   ```ts
   import { useEffect, useState } from 'react';

   export const MESSAGES_HTTP_FALLBACK_MS = 1500;

   /** True once `delayMs` pass for this identity without a first stream payload; false again after one arrives. */
   export function useMessagesHttpFallback(
     streamEnabled: boolean,
     receivedFirstPayload: boolean,
     identity: string,
     delayMs = MESSAGES_HTTP_FALLBACK_MS,
   ): boolean {
     const [dueIdentity, setDueIdentity] = useState<string | null>(null);

     return streamEnabled && !receivedFirstPayload && dueIdentity === identity;
   ```

## Why CPU contention makes it worse

Nothing here was measured at idle, so this section rests on mechanism plus the loaded-state evidence above.

- **Fixed-cadence jobs grow longer on a shared single-slot queue.** The read lane runs one job at a time. The search-stats refresh (every 60 s) and the cost snapshot (every 15 s) take longer when the host is saturated: runMs goes up to 34 s, and the slow log shows `depth=2..5` queues behind them. Any `getConversationByName` that arrives during one waits for the rest of it. At this boot's rates the read lane is busy with aggregates about 14 % of the time (44×13.4 s plus 173×1.2 s over about 95 min). So roughly 1 in 7 live opens can stall, for about half a job (around 6 s) on average.
- **Main-thread synchronous work.** `computeContextUsage` (sync JSON.parse of up to 76 MB), `getCachedMessages` (main-thread parser), JSON encoding of 0.5–2.7 MB responses and frames, and the 5.35 MB `getSnapshot` encode all run on the one event loop. That loop already runs at a p99 of 250–600 ms with nobody opening anything. When cores are oversubscribed, each of these slices gets less CPU, so the queue of pending requests drains more slowly.
- **Subprocess fan-out.** `/diffs` for 2973 spawns 84+ serial `git diff` processes per 5 s tick, taking 2–7 s per call. Every spawn competes for the same saturated cores, and each call burns event-loop turns on subprocess I/O.

## Not quick wins (explicitly out of scope)

- **The hard-load burst.** On a cold `/conv/<id>` load, DOMContentLoaded to skeleton takes 1.9–5.1 s. About 60 parallel REST calls, the per-issue deck fan-out and a 5.35 MB `getSnapshot` frame saturate the event loop before the conversation row resolves. Fixing it means prioritizing or deferring deck loads, which is a design change.
- **Windowing the initial payload.** For example, sending the tail N messages first for 2884's 2.7 MB. Payload size is what makes 2884 take 1.7 s, but the virtualized timeline, subagent rail and message locator all assume the full history.
- **Background main-thread load.** About 40–60 % of a core, with a p99 event-loop lag of 250–600 ms at rest. Finding its source needs a CPU profile of the live server, which was not taken because this investigation was read-only.
