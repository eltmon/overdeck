## Glossary

| Term | Meaning |
| --- | --- |
| **State plane** | The git-mirrored durable pipeline state: per-issue records, continue states, vBRIEF specs, PRD drafts, review/test/feedback artifacts, backlog sequence, and the beads database exports. Enumerated today by `STATE_PLANE_PATHS` in `src/lib/state-plane.ts:6`. |
| **Code branch** | `main` and `feature/*` branches — the branches that carry product source and go through CI/review/merge. |
| **State branch** | `overdeck-state` — a same-repo **orphan branch** (no common ancestor with `main`) whose tree contains *only* state-plane content. |
| **Orphan branch** | A branch created with `git checkout --orphan <name>`: it starts with an empty tree and shares no history with any other branch. |
| **State worktree** | A second checkout of the same repository, pinned to `overdeck-state`, living at `${OVERDECK_HOME}/state/<projectKey>`. Created with `git worktree add`. The **only** place state commits happen. |
| **Write door** | The single code path allowed to commit/push state: `queueAutoCommit` / `flushAutoCommits` in `src/lib/pan-dir/auto-commit.ts` (exports at lines 189 and 241; search for `export function queueAutoCommit`). |
| **Read door** | The per-domain canonical resolvers in `src/lib/pan-dir/` (`specs.ts`, `records.ts`, `continue.ts`, `drafts.ts`, `feedback.ts`) and `src/lib/backlog/sequence-io.ts`. |
| **Context layer** | Human-authored project configuration at `.pan/context/` (e.g. `project.md`, `codebase/*.md`) that renders into harness context files (CLAUDE.md / AGENTS.md). **Not** machine state. |
| **Workspace-local runtime files** | Gitignored, per-workspace operational files (`continue.json`, `kickoff.md`, `agent-mcp.json`, `events/`, `convoy/`, `prompts/`, `pid/`) — see `.gitignore:142-151`. Never committed anywhere; not part of the state branch. |
| **bd / beads** | The external issue tracker CLI. Its discovery is hardcoded to a `.beads/` directory found in the working directory or its ancestors (verified: `bd --help` — "default: auto-discover .beads/*.db"; `bd init` "creat[es] a .beads/ directory"). |
| **Beads redirect** | bd v1.0.4+ mechanism already used by Overdeck workspaces: a gitignored `.beads/redirect` file inside the workspace containing a path to the shared canonical `.beads/` directory. Written by `initializeWorkspaceBeads` in `src/cli/commands/workspace-beads.ts` (search for `writeFileSync(redirectPath`) — today it writes `../../.beads`, pointing at the project root. |

## Background & motivation

Today the deacon and pipeline mirror the state plane into git by committing to **the same branch and the same worktree as the code**. Three incident classes on 2026-07-09 alone share this root:

1. **Review-reset loop ([PAN-2468](https://github.com/eltmon/overdeck/issues/2468)).** High-frequency state commits on `main` force feature branches to rebase constantly; each rebase rewrites every commit SHA; the deacon's post-review guard read a byte-identical branch as "new code" and reset a passed review in a loop. Patched at the guard layer (commit `9887913c73`, patch-id contribution comparison) — but the *trigger* (state churn on main) remains.
2. **Writer race on the shared worktree.** The deacon's auto-commit (`chore(state): batch update …`) runs in the primary worktree concurrently with human/conversation commits. Two agents were bitten the same day by `git commit --amend` silently absorbing a concurrent deacon state commit.
3. **History and pipeline pollution.** `git log main` interleaves state noise; state pushes trigger CI; `src/lib/pipeline-state-paths.ts` and `src/lib/state-plane.ts` exist largely to discriminate state commits from code commits *after the fact*.

Moving the state plane to an orphan branch written through a dedicated worktree removes the trigger conditions structurally. Prior art: `gh-pages`, CI benchmark-data branches, Gerrit `refs/meta/config`; Overdeck already uses same-repo custom refs (`refs/pan/turn/*`) for checkpoints.

## Decisions (made in this document — do not re-litigate downstream)

| # | Decision | Rationale |
| --- | --- | --- |
| D1 | The state branch is named **`overdeck-state`**. | Self-describing post-rebrand name. Not `pan-state` (legacy name). Not `overdeck/state` (a branch named `overdeck` could never coexist — git ref namespace collision). |
| D2 | The state branch tree is **flat**: `records/`, `continues/`, `specs/`, `drafts/`, `review/`, `test/`, `feedback/`, `backlog/`, `notes/`, `.beads/` at its root. **No `.pan/` wrapper.** | The dot-directory existed only to hide state inside the code checkout. On a dedicated branch the branch *is* the namespace. This is also the clean break from the `pan` legacy name: the new home never contains it. |
| D3 | **No symlinks anywhere** in this design. | Operator decision (2026-07-09): symlinks cause more confusion than they solve, and D2+D4 make them unnecessary. |
| D4 | `.beads/` lives at the **state worktree root**, keeping its literal name so bd's hardcoded discovery works natively (bd runs with `-C <state worktree>` or with cwd inside it). It is removed from code `main`. Workspaces keep reaching the shared DB through their existing redirect, retargeted per **D13**. | Avoids both the symlink and any bd fork. Verified: bd supports `-C` (global flag) and `--db` explicit path. |
| D5 | The context layer moves **out of the state directory entirely**: `.pan/context/` → **`.overdeck/context/`** on `main`, tracked and code-reviewable. `main`'s `.overdeck/` directory holds *only* human-authored, code-owned config. | Operator decision: no carve-out/negation patterns. One directory = one owner. Context governs the code, so it travels and reviews with the code. |
| D6 | Workspace-local runtime files rename `.pan/` → `.overdeck/` (they are gitignored; rename = code constants + a read-compat fallback for `.pan/`). | Completes the clean break at the only other place the `.pan` name would survive. |
| D7 | **No internal module rename** in this PRD: `src/lib/pan-dir/` keeps its name; the CLI stays `pan`. | Surgical-changes rule. The `pan-dir` module name is internal; renaming it is churn with no behavioral value. May be a follow-up. |
| D8 | `main` and `overdeck-state` **never merge**. Reconciliation is referential (records carry issue IDs / PR numbers / commit SHAs) plus a release-time snapshot: `pan release stable` records the current `overdeck-state` SHA in `.release/<tag>.md`. | The trees are disjoint; a merge is meaningless and would import thousands of state commits into code history. |
| D9 | Legacy `.pan/` **read fallbacks** are kept during the migration window (same pattern as the existing `vbrief/` legacy fallback, `findLegacyVBriefByIssue`). Writes go only to the new home. | Non-destructive migration; old checkouts keep working read-only. |
| D10 | Multi-machine writer semantics: before each push the writer runs `git fetch` + `git rebase origin/overdeck-state`; on conflict it aborts the rebase, re-reads the canonical value through the read door, re-applies the queued write, and retries (bounded, 3 attempts). Per-issue record files make conflicts rare; last-writer-wins per file is acceptable for this plane. | Records are per-issue JSON files with a single writer per machine. |
| D11 | The existing benign-HEAD-move guards in `checkPostReviewCommits` (tree-identical + the folded effective-code/patch-id check — `src/lib/cloister/deacon.ts:1620-1631`, search for `Benign post-review HEAD move`) are **kept as backstops**, not removed. | No-loss principle. Feature branches may still rebase for genuine code conflicts. Removal is a separate, later cleanup once telemetry shows they no longer fire. |
| D12 | **Migration detection is repo-derived, never machine-local:** a project counts as migrated iff the `overdeck-state` branch exists on `origin` (checked via `git ls-remote --heads origin overdeck-state` or a local ref after fetch, cached per process). No `projects.yaml` stamping. | A machine-local config flag would break every *other* machine: it would still read the legacy `.pan/` paths on `main`, which are empty after migration. Branch existence propagates with the repo itself — any clone anywhere resolves correctly with zero per-machine setup. |
| D13 | **Workspace beads keep working via the existing redirect, retargeted.** Workspaces already resolve beads through a gitignored `.beads/redirect` file (see Glossary). Post-migration the redirect target becomes the state worktree's `.beads/` (absolute path `${OVERDECK_HOME}/state/<projectKey>/.beads`), and the redirect-creation code's project-root existence check repoints there. Workspace-committed `issues.jsonl` inheritance is retired — feature branches carry no beads content at all. | Verified: the redirect mechanism exists today (`workspace-beads.ts`, bd ≥ 1.0.4 path). Retargeting one path string preserves every workspace flow; committing beads to feature branches is what FR-2's guard forbids, so it must stop at the source. |
| D14 | **Fly remote workspaces are blocked at spawn on migrated projects** until remote state sync is redesigned (follow-up issue, filed during implementation; see PAN-1676 for the existing remote-gap list). The spawn path fails fast with an error naming this decision. Unmigrated projects keep the current remote behavior. | The retargeted redirect (D13) points at a host-local absolute path (`${OVERDECK_HOME}/state/<key>/.beads`) that cannot resolve on a Fly machine, and the old remote write-back path — committing `.beads/` to the feature branch (`fly-provider.ts:694`) — is exactly what FR-11 removes. Fly remote is experimental and work-phase-only today; failing loudly is honest, silently losing remote beads writes is not. |

## Alternatives considered (and why not)

| Alternative | Why it loses to the orphan branch |
| --- | --- |
| **Separate state repo** (the existing `pan_records.repo` polyrepo path) | Operationally cleaner isolation and lighter clones of the code repo — this is the strongest competitor, not a strawman. It loses on setup weight (a second repo to create, authenticate, and clone per project) and discoverability. **Crucially, this design keeps it reachable:** everything resolves through `resolveStateHome()`, so moving to a separate repo later is a config change plus one history transplant — not a rewrite. If state-branch history growth ever becomes a real clone-weight problem, that is the escape hatch. |
| **Custom refs** (`refs/overdeck/state/*`, like the existing `refs/pan/turn/*` checkpoints) | Invisible on the GitHub UI — records/specs would not be browsable at github.com at all, and every clone needs explicit refspec configuration to even fetch them. Auditability in the browser is a feature, not an accident. |
| **Keep state on `main`, add more guards** | The status quo. Each incident class (review-reset loops, `--amend` races, CI churn) gets its own patch forever; the root — two writers and two kinds of history on one branch — remains. |
| **Stop mirroring state to git entirely** (SQLite only) | Violates the standing cache-derivability tenet: the DB is a disposable cache, git is the durable, machine-portable record. Not relitigated here. |
| **Git submodule for state** | Submodules pin SHAs in the superproject, so every state commit would require a bump commit on `main` — reintroducing exactly the churn this design removes. |

One honest cost of the same-repo choice, stated plainly: the state branch's history (especially `.beads/issues.jsonl` churn) lives in the same object store, so full clones of the repository carry it. Today that history already lives on `main`, so the migration makes nothing worse — it reorganizes existing weight — but the weight keeps growing on `overdeck-state` over time. Mitigations if it ever matters: `git clone --filter=blob:none` for contributors, or the separate-repo escape hatch above.

## Requirements

### Functional

- **FR-1** All state-plane writes for a project land as commits on the `overdeck-state` branch, made **only** from the state worktree at `${OVERDECK_HOME}/state/<projectKey>`, serialized by the existing write-door lock.
- **FR-2** No new commit on `main` or any `feature/*` branch may contain state-plane paths. Enforced mechanically (gitignore + CI guard), not by convention.
- **FR-3** The `overdeck-state` tree contains only state-plane content (D2 layout). Enforced by a CI guard on pushes to `overdeck-state`.
- **FR-4** All read doors resolve state from the state worktree; when it is absent (not yet migrated), they fall back to the legacy `<projectRoot>/.pan/` locations read-only (D9).
- **FR-5** The context layer is served from `<projectRoot>/.overdeck/context/` on `main`, with read fallback to `.pan/context/` (D9).
- **FR-6** `pan install` / `pan doctor` create or self-heal the state worktree (correct branch, correct path, clean status).
- **FR-7** A migration command (`pan admin state migrate <project>`) performs the one-time cutover per project (see WI-2) and is idempotent — re-running after success is a no-op.
- **FR-8** The canonical `.beads/` database and JSONL exports live at the state worktree root; project-scope bd invocations in Overdeck source pass `-C <state worktree>`. Workspaces reach the same DB through their existing redirect, retargeted per D13 — every workspace bd command keeps working; only the redirect's target path changes.
- **FR-9** `pan release stable` records the `overdeck-state` HEAD SHA of every registered project in `.release/<tag>.md`.
- **FR-10** The PAN-1124 invariant survives verbatim: specs are immutable after planning except `plan.status` flips via `updateSpecStatus()`; the single writer is the write door. Only the storage location changes.
- **FR-11** After migration, **no pipeline flow commits state-plane paths to a feature branch or to `main`**: the agent-spawn planning-artifact commit, `pan done`'s artifact sync (both sites), beads compaction, the Fly remote beads push, and the complete-planning promotion commit are all removed, rerouted through the write door, or made migration-aware (see WI-11 for the verified site list; `roles/*.md` verified to contain no commit-state instructions — a regression lint keeps it that way). The WI-7 CI guard is the backstop, not the mechanism.
- **FR-12** After migration, no Overdeck code **writes** under `<projectRoot>/.pan/` state paths or `<projectRoot>/.beads/`. WI-10 audits that every legacy *read* surface survives; FR-12 is its write-side twin — a stray writer that recreates `.pan/records/` in the project checkout would silently fork state (the D9 fallback is read-only by policy, but only a guard makes that mechanical). Enforced two ways: (a) a source-level lint failing any code outside the doors (`src/lib/pan-dir/`, `src/lib/state-home.ts`) that constructs a write path under a state-plane location, and (b) a `pan doctor` / deacon-patrol tripwire flagging a migrated project whose checkout has any state-plane directory present on disk — evidence a stray writer recreated it.

### Non-functional

- **NFR-1** Migration is non-destructive: no history rewrite on `main`; legacy `.pan/**` blobs remain reachable in old commits. The migration makes ordinary commits only (recoverable-actions principle).
- **NFR-2** State pushes trigger **zero** CI workflows (branch filter), and stop appearing in `git log main`.
- **NFR-3** Every new test that exercises delay/retry logic (the writer's rebase-retry, D10) uses `vi.useFakeTimers()` — never real timers (repo rule, restated below).
- **NFR-4** No `execSync` in any server-reachable code added by this work; async `execFile`/`spawn` only (repo rule).
- **NFR-5** The whole feature ships as one issue — no partial delivery. Phases below are organizational, not separate deliverables.

## Design

### Target layout — what you see on GitHub

A visitor to `github.com/eltmon/overdeck` sees `main` by default: source code, docs, `.overdeck/context/` — and **no state files anywhere**. Switching the branch dropdown to `overdeck-state` shows the state tree **at the root of that branch** — the file listing starts directly with `records/`, `continues/`, `specs/`, … There is **no wrapper directory** (no `/overdeck/records`, no `/.pan/records`): "flat" means the branch root *is* the container, exactly like `gh-pages` branches whose root is directly `index.html`. A spec is browsable at `github.com/eltmon/overdeck/blob/overdeck-state/specs/<file>`.

```
Branch: main ▾                          Branch: overdeck-state ▾
├── src/ …                              ├── records/      pan-2541.json …
├── docs/ …                             ├── continues/    pan-2541.vbrief.json …
├── .overdeck/                          ├── specs/        2026-…-PAN-2541-….vbrief.json …
│   └── context/                        ├── drafts/       pan-2541.md …
│       ├── project.md                  ├── review/  test/  feedback/
│       └── codebase/*.md               ├── backlog/      sequence.md …
├── .gitignore (ignores state paths)    ├── notes/
└── (NO .pan/, NO .beads/)              └── .beads/       issues.jsonl, *.db …

state worktree: ${OVERDECK_HOME}/state/<projectKey>  ⟶ checked out on overdeck-state
(so on disk, records/ etc. appear inside that worktree directory)
```

**Where the files are, precisely.** After migration the project checkout (e.g. `~/Projects/overdeck`) contains **no state files at all** — its `.overdeck/` holds only `context/`. The state files exist on disk **only inside the state worktree** (e.g. `~/.overdeck/state/overdeck/records/…`). A worktree is a checkout of a branch, so the branch root maps to the worktree directory root: the same file is `records/pan-2541.json` at the branch root on GitHub and `${OVERDECK_HOME}/state/overdeck/records/pan-2541.json` locally. Note the two different `.overdeck`s: **`~/.overdeck/`** is the machine-level Overdeck home (agents, sockets, config — and now `state/<project>/` worktrees under it), while **`.overdeck/` inside a repo** is the code-owned config directory holding only the context layer. Same name, two scopes — the standard project-vs-home tool convention (`.cargo/` vs `~/.cargo/`).

### Resolution chokepoint

`resolveInfraRepo()` in `src/lib/projects.ts:353` already returns `{ repoPath, recordsPath }` with `recordsPath = project.pan_records?.path ?? '.pan'` (line 357). It grows a successor, `resolveStateHome(project)`, that returns the state worktree path with `recordsPath: '.'` once the project is migrated — migration detected per **D12** (the `overdeck-state` branch exists), never from machine-local config — and the legacy values otherwise. Every read/write door resolves through it. Verified: no project in the live `~/.overdeck/projects.yaml` sets `pan_records`, so there are no existing overrides to preserve (the polyrepo code path in lines 358-373 is kept working).

**Before (`src/lib/projects.ts:357`):**
```ts
const recordsPath = project.pan_records?.path ?? '.pan';
```
**After (sketch — exact shape to match file style):**
```ts
// PAN-2541: migrated projects resolve to the dedicated state worktree on
// branch 'overdeck-state'; recordsPath collapses to '.' (flat tree, D2).
const home = resolveStateHome(project);
if (home.migrated) return { repoPath: home.worktreePath, recordsPath: '.' };
const recordsPath = project.pan_records?.path ?? '.pan';
```

### Write door

`queueAutoCommit` / `flushAutoCommits` (`src/lib/pan-dir/auto-commit.ts`, exports at lines 189/241) currently derive a repo root from the changed path and commit there. After this change they (a) refuse to commit state paths anywhere except the state worktree, (b) assert `git branch --show-current` = `overdeck-state` before every commit (worktree-discipline rule applied to the machine), and (c) push after flush using the D10 fetch/rebase/retry loop.

### Guards

1. **CI guard on code branches** (new script wired into the existing lint/CI): fail if `git diff --name-only origin/main...HEAD` (or the tracked tree on main) contains any state-plane path.
2. **CI/hook guard on `overdeck-state`**: fail if the tree contains any path *outside* the D2 layout.
3. **Writer self-check**: unit-tested branch assertion in the write door (WI-4's named test).
4. **Stray-write tripwires (FR-12)**: source-level lint against direct state-path writes outside the doors, plus a doctor/patrol check that no state-plane directory reappears in a migrated project's checkout. The CI guard (1) catches *committed* strays; these catch strays before they ever commit.

### Multi-project rollout

Every registered project gets the same treatment, independently, with **zero new repos or remote setup** — that is the payoff of the same-repo decision:

- `pan admin state migrate <project>` runs once per project; each project's repo gets its own `overdeck-state` branch and its own state worktree at `${OVERDECK_HOME}/state/<projectKey>`. Records, specs, drafts, and `.beads/` for that project's issues (`MIN-*`, `LEX-*`, `KRUX-*`, …) live on *that repo's* state branch.
- **Remote-host agnostic.** Every mechanism here is plain git — orphan branch, `git worktree`, `git ls-remote` (D12 detection), gitignore. Mind Your Now's GitLab remote behaves identically to GitHub, including branch-switcher browsing of `records/` on gitlab.com. Nothing depends on `gh`.
- **Multi-repo projects** (e.g. MYN's frontend + backend repos): the state branch lives in the project's **primary repo** (`project.path`), exactly where `.pan/` lives today. The `pan_records.repo` polyrepo override remains available for projects that want state in a different member repo.
- **Portable vs per-repo mechanisms.** The writer-side branch assertion, the redirect retarget, the remediated pipeline flows (WI-11), and the migration-written gitignore all live in Overdeck's own code or are written by the migration command — they protect every project automatically. The WI-7 *CI* guards are per-repo hardening: required in the overdeck repo (this PRD), and the guard script is written so other projects can adopt it in their own CI as a follow-on (GitLab CI for MYN); the portable mechanisms do not depend on it.
- **Rollout order:** overdeck first (dogfood, this PRD's acceptance), then the other registered projects one at a time via the same command. Unmigrated projects keep working unchanged the whole time — `isStateMigrated()` (D12) gates every behavior change per project.
