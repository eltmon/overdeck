# PAN-2167 — Pipeline-written `.pan/records` + `.pan/test/result.json` dirty the worktree and block the review clean-tree gate

**Issue:** [PAN-2167](https://github.com/eltmon/overdeck/issues/2167)
**Governing policy:** [`docs/STATE-PLANE-COMMIT-POLICY.md`](../../docs/STATE-PLANE-COMMIT-POLICY.md) (adopted 2026-07-06, operator-directed)
**Planning model:** agent:claude-opus-4-8 · **Mode:** `pan plan --auto`

## Glossary

- **State-plane path** — a `.pan/`/`.beads/` path the pipeline owns and writes on the
  agent's behalf. The canonical list lives in `STATE_PLANE_PATHS` in
  [`src/lib/state-plane.ts:6`](../../src/lib/state-plane.ts): `.pan/records/`,
  `.pan/continues/`, `.pan/continue.json`, `.pan/specs/`, `.beads/`, `.pan/test/`,
  `.pan/review/`, `.pan/feedback/`. Everything else is **source**.
- **Clean-tree gate** — a pipeline check that runs `git status --porcelain` in the
  feature workspace and refuses to proceed if the tree is dirty. Three exist on the
  review→merge path (see Work Items).
- **State-plane-only dirt** — a working tree whose *entire* `git status` consists of
  state-plane paths (e.g. `MM .pan/records/pan-1982.json`, `?? .pan/test/result.json`).
- **`isStatePlanePath` / `isStatePlaneOnlyDiff`** — the single shared predicate/path-list
  in `src/lib/state-plane.ts` that rule 3/6 of the policy mandates every gate consume.
  `isStatePlaneOnlyDiff(baseSha, tipSha, root)` operates on a **committed diff**; the
  clean-tree gates operate on the **working tree**, so this issue adds a working-tree
  companion that reuses the same `isStatePlanePath` list.

## Problem

The pipeline writes `.pan/records/<id>.json` (per-issue record writer,
[`src/lib/pan-dir/record.ts`](../../src/lib/pan-dir/record.ts)) and
`.pan/test/result.json` into the **feature workspace**, but the record auto-committer is
**main-only** ([`src/lib/pan-dir/auto-commit.ts`](../../src/lib/pan-dir/auto-commit.ts)).
So on a feature branch these state-plane files sit **dirty and are never committed**,
tripping every clean-tree gate on the review→merge path:

- `pan review request` aborts with "Workspace has uncommitted changes" even when the
  ONLY dirty files are pipeline bookkeeping (the title symptom — 4 recorded manifestations,
  RUN-37/38/58).
- `pan done` preflight refuses completion for the same reason (a work agent that fixed
  review feedback cannot re-enter review).
- The approve/merge pre-push gate refuses the same way one step later.

The result: an issue that is genuinely ready cannot move through the pipeline; the operator
or flywheel must `pan review restart` repeatedly. Unattended work agents stall indefinitely.

## Root cause (verified)

- `.pan/records/*` is git-tracked **on purpose** — it is the durable, portable per-issue
  plane for cross-machine handoff ([`docs/AGENT-STATE-PLANES.md:18`](../../docs/AGENT-STATE-PLANES.md)).
  Gitignoring it is explicitly forbidden (policy rule 1; PAN-2386 tried this and was wrong).
- The three clean-tree gates each run a raw `git status --porcelain` and treat *any*
  non-empty result as "agent has uncommitted work", with no awareness that state-plane
  paths are pipeline-owned. This is a **plane violation at the gate** — the fix the policy
  prescribes (rule 3): the gate must consume the shared state-plane predicate.

## Proposal

Add a **working-tree companion** to the existing shared predicate in `src/lib/state-plane.ts`
that reuses the single `isStatePlanePath` list (policy rule 6 — no new path list), then wire
it into all three feature-workspace clean-tree gates so that a tree dirty with **only**
state-plane paths is treated as clean. Any non-state-plane dirt still fails the gate exactly
as today (policy rule 4 — this loosens nothing about code review).

We do **not** make records commit-on-write on feature branches. Manifestations 3 and 4 on
this issue demonstrate that committing pipeline bookkeeping onto a feature branch is itself
harmful — it re-triggers PR CI and can deadlock a readyForMerge branch. Gate-side tolerance
(rule 3) is the correct fix here; commit-on-write (rule 2) is contraindicated for feature
branches by this issue's own evidence.

## Requirements

- **FR-1** — A feature workspace whose entire `git status` is state-plane paths passes the
  `pan review request` clean-tree gate (`getDirtyWorkspaceErrorForReviewRequest` returns null).
- **FR-2** — The same workspace passes the `pan done` preflight uncommitted-changes check;
  the preflight still fails and lists any **non**-state-plane dirty paths.
- **FR-3** — The approve/merge pre-push clean-tree gate tolerates state-plane-only dirt and
  still rejects any non-state-plane dirt.
- **FR-4** — All three gates derive their decision from the single `STATE_PLANE_PATHS` /
  `isStatePlanePath` source (policy rule 6); no gate re-implements the path list.
- **NFR-1** — The new predicate is a **pure** function over `git status --porcelain` output
  (a string), so it applies to both local (`execAsync` cwd) and remote (fly-exec) status
  without issuing a second git call.
- **NFR-2** — Untracked new state files (`?? .pan/records/<id>.json`), staged+unstaged
  (`MM …`), and renames (`R  old -> new`) are all classified correctly.

## Work Items

### WI-1 — Add working-tree state-plane predicate to `src/lib/state-plane.ts` (foundation)

Add two pure exports beside `isStatePlaneOnlyDiff`, reusing `isStatePlanePath`:

```ts
/** Parse `git status --porcelain[ -uno]` output into changed paths.
 *  Strips the 2-char XY status, resolves rename `orig -> new` to `new`,
 *  and unquotes git's C-quoted paths. */
export function parsePorcelainStatusPaths(porcelain: string): string[] { … }

/** True iff the porcelain status contains no non-state-plane paths.
 *  Vacuously true for a clean tree (empty input). Reuses isStatePlanePath —
 *  the single path source (policy rule 6). */
export function isStatePlaneOnlyStatus(porcelain: string): boolean {
  return parsePorcelainStatusPaths(porcelain).every(isStatePlanePath);
}
```

Unit tests in `src/lib/__tests__/state-plane.test.ts`: clean → true; only `.pan/records/`
+ `.pan/test/` (incl. `MM` and `??`) → true; mixed source+state → false; source-only → false;
rename of a state path → true; rename of a source path → false.

## Planning Q&A (`--auto` — decisions recorded, no operator prompts)

**Q: Gate-side predicate (rule 3) vs. commit-on-write for records (rule 2)?**
Chose **gate-side predicate**. The policy allows either, but this issue's own manifestations 3/4
show committing bookkeeping onto a feature branch re-triggers CI and deadlocks readyForMerge —
so commit-on-write is actively harmful here. Gate tolerance is the least-surprising, safe fix.

**Q: How many gates are in scope?**
Chose **all three feature-workspace clean-tree gates on the review→merge path** (review request,
`pan done` preflight, approve/merge pre-push). They are mechanically identical; fixing only the
first leaves the same bug one step later. The auto-start guard, verify-merged, and verdict-reset
are explicitly other cluster issues (see NonGoals).

**Q: Worktree predicate shape?**
Chose a **pure function over the porcelain string** (not a git-invoking async helper) so the
remote (fly-exec) gate reuses it without a second git call, and it reuses the single
`isStatePlanePath` list (rule 6) rather than adding a parallel path list.

**Q: Manifestations 2/3/4 — in scope?**
**No.** They share the root family but are distinct mechanisms (conflict resolution, CI
re-trigger, rebase latch). Bundling them would violate tracer-bullet slicing. Recorded as
NonGoals with a note to file separate issues.
