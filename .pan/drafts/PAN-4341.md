# PRD: An independent, different-family plan critic before finalize for flagged plans (PAN-4341)

**Issue:** [PAN-4341](https://github.com/eltmon/overdeck/issues/4341)
**Parent PRD:** `.pan/drafts/deft-adoption.md`, "Issue 7" (lines 339-362) and Verdict item 3 (line 24).
**Related:** PAN-4342 (fresh re-review lane; same critic method for code review). Out of scope here.
**Planning mode:** `pan plan --auto`. Every choice the issue left open is recorded under "Decisions" and in the xBRIEF `plan.autoDecisions[]`.

## Glossary

- **Planner.** The `plan`-role agent (`planning-<issue-lower>`) that writes the PRD and the draft xBRIEF, then runs `pan plan finalize`.
- **Draft xBRIEF.** The workspace plan file `<workspace>/.overdeck/spec.vbrief.json` that finalize promotes.
- **Critic.** One read-only `worker`-role agent started by finalize. It reads the PRD, the draft xBRIEF and the repository, and returns findings. It never sees the planner's reasoning (transcript, `.overdeck/continue.json`).
- **Flagged plan.** A plan whose issue carries the label `architecture`, `substrate-improvement` or `security`, or a finalize run with `--critic`. Only flagged plans need a critique.
- **Model family.** The vendor lineage of a model, computed by `familyOf(model)` (WI-3). The critic's family must differ from the planner's.
- **Plan digest.** SHA-256 hex of the draft xBRIEF after lifecycle and finalize-stamp fields are removed and keys are sorted (WI-1). The digest does not change when finalize stamps the plan.
- **Critique file.** `.pan/drafts/<PRD-stem>-critique.md` (round 1) or `<PRD-stem>-critique-2.md` (round 2), next to the PRD. Line 1 is `plan-digest: <64 hex>`. The dispatcher writes this file, not the critic.
- **Finding.** A level-2 heading in a critique file of the form `## <classification>: <title>`. Classification is one of three tokens: `blocks-the-design`, `sharpens-framing`, `footnote`.
- **Critique response.** The PRD section `## Critique response`. Each answered `blocks-the-design` finding has a level-3 heading `### <title>` there.
- **Round.** One critic run. A round counts as used when its critique file exists in the working tree or has ever been committed on the branch (`git log -- <path>` is non-empty). At most two rounds per plan.
- **Critique gate.** The pure decision function `evaluateCritiqueGate` (WI-2). It returns pass or refuse, plus a reason. The CLI and the complete-planning server both call it.

## Problem

The only pre-code critique today is `pan plan --probe`, which is the planner attacking its own plan (`sync-sources/skills/pan-plan/SKILL.md` line 62, "`--probe` adds an adversarial self-review section"). Correlated review is not verification: a critic on the same model, with the same context, tends to repeat the planner's blind spots. Deft's design-critique contract names four cheap principles (decorrelation, method-reconciliation, non-self-arbitration, "a reviewer would catch it" is a failed finding) and a three-token finding classification. This issue adopts those principles for one critic, on flagged plans only, before finalize.

## Requirements

### Functional

- **FR-1.** A plan is flagged when `pan plan finalize --critic` is passed, or when the issue carries at least one of the labels `architecture`, `substrate-improvement`, `security` (exact, case-insensitive match). The complete-planning server computes the same flag from labels and from `body.critic === true`.
- **FR-2.** The plan digest is `sha256(stableStringify(strip(doc)))`, where `strip` removes the five plan-integrity lifecycle fields plus `plan.metadata.canonicalFilename` and `plan.metadata.promotionIntent`. The digest before and after `stampPlanForFinalization` is identical.
- **FR-3.** Critique files are named from the PRD stem: `<dir>/<stem>-critique.md` for round 1 and `<dir>/<stem>-critique-2.md` for round 2, where `<dir>/<stem>.md` is the workspace PRD resolved as `<workspace>/.pan/drafts/<ISSUE-UPPER>.md`, then `<issue-lower>.md`.
- **FR-4.** Line 1 of a critique file is exactly `plan-digest: <64 lowercase hex>`. The dispatcher writes this line with the digest computed at dispatch time, then a blank line, then the critic's report body.
- **FR-5.** Findings are parsed from level-2 headings matching `/^## (blocks-the-design|sharpens-framing|footnote):\s*(.+?)\s*$/`. Any other heading is ignored.
- **FR-6.** A `blocks-the-design` finding is answered when the PRD's `## Critique response` section (from that heading to the next level-2 heading or end of file) contains a level-3 heading whose text equals the finding title after trimming and lower-casing.
- **FR-7.** The gate decision, in this order: (a) not flagged → pass `not-required`; (b) rounds used ≥ 2 → pass `cap-reached`, with `unresolved` = the latest critique's unanswered `blocks-the-design` titles; (c) no critique file for the latest used round, or no rounds used → refuse `missing` with `nextRound = roundsUsed + 1`; (d) the latest critique's digest differs from the current digest → refuse `stale` with `nextRound = roundsUsed + 1`; (e) one or more unanswered `blocks-the-design` findings → refuse `unanswered` with their titles; (f) otherwise pass `answered`. The latest critique is round 2's file when it exists in the tree, else round 1's.
- **FR-8.** On `missing` or `stale`, `pan plan finalize` dispatches one critic for `nextRound`, waits up to 540 s for its report, writes the critique file, and evaluates the gate again in the same run. When the second evaluation passes, finalize continues to stamping and promotion.
- **FR-9.** The critic's model comes only from `roles.plan.sub.critic.model` in config (workhorse refs allowed). When it is unset, or `familyOf(critic) === familyOf(planner)`, finalize refuses with a message that names the setting and both families. There is no fallback model.
- **FR-10.** The critic's harness is `resolveHarness({ model: criticModel })`. After the worker starts, the dispatcher reads the worker's `state.json` and refuses (stopping the worker) when `state.harness` differs from the resolved critic harness or `familyOf(state.model)` equals the planner's family.
- **FR-11.** The critic brief contains the text of `roles/plan-critic.md`, the issue id, the round number, the workspace-relative PRD path, and the draft xBRIEF JSON inlined. It contains nothing from the planner's transcript or `.overdeck/continue.json`.
- **FR-12.** Re-running finalize while a critic for round N is still running (a worker for the issue named `plan-critic-r<N>` that has no report yet and is alive) waits on that worker instead of starting another one. A worker named `plan-critic-r<N>` that already has a `done` report is used without waiting.
- **FR-13.** `completePlanningForIssue` evaluates the same gate after its quality-lint pre-check and returns HTTP 422 `{ error: 'Plan critique gate: <reason>', critiqueGate }` on refusal. It never dispatches a critic.
- **FR-14.** On `cap-reached` with a non-empty `unresolved` list, complete-planning writes (or replaces) a `### Unresolved after two critic rounds` subsection under `## Critique response` in the workspace PRD, listing each title as `- <title>`, before the promotion commit. It creates the `## Critique response` heading when absent.
- **FR-15.** When labels cannot be read (tracker error or timeout), both the CLI and the server print or emit a warning and treat the plan as not flagged unless `--critic`/`body.critic` forces it.
- **FR-16.** The CLI exits 5 on any critique-gate refusal. With `--json` it prints `{ success: false, error: 'Plan critique gate failed', message, critiqueGate }`.

### Non-functional

- **NFR-1.** No stored "critiqued" flag. Readiness is derived each run from the critique file, the current draft and git history.
- **NFR-2.** No `execSync` in server-reachable code. Git reads in `plan-critique-io.ts` use promisified `execFile`.
- **NFR-3.** `src/lib/overdeck/planning-promotion.ts` stays at or under 1000 lines; no `scripts/file-size-allowlist.txt` change.
- **NFR-4.** Tests use injected dependencies and temp directories, never a live worker, tracker or dashboard. Any test that waits on time uses `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`.
- **NFR-5.** Unflagged plans see no behavior change and no extra tracker call beyond one label read.

## Decisions

1. **Dispatch in the CLI, verification in both.** The CLI can wait up to 540 s (inside Claude Code's 10-minute foreground maximum; the Bash tool's default timeout is 120 s, so the planner must pass a 600 s timeout or run finalize in the background); the server POST has a 90 s timeout, so the server only verifies. The Done button and `pan plan done` therefore cannot bypass a required critique; they return 422 and tell the operator to run `pan plan finalize` in the workspace.
2. **Model family, not harness, is the decorrelation axis.** `familyOf(model)` = `toTelemetryModelFamily(model)`; when that returns `other`, the family is `provider:<getProviderForModel(model).name>`; when the model is unknown, `unknown:<model>`. Two `other` models from different providers therefore count as different. A same-harness critic on a different family is allowed (the operator deliberately routes some GPT models through claude-code). The dispatch test still asserts the launched harness equals the resolved critic harness, so a dropped `--harness` is caught.
3. **Explicit config, no default.** `roles.plan.sub.critic.model` is new and unset by default. Default workhorses are all Claude, so any default would be same-family. Finalize refuses loudly when it is unset (repo rule: never hardcode a model fallback).
4. **Unreadable labels warn and continue.** The threat model is cheap-path prevention, not a security boundary (`deft-adoption.md` line 12). Blocking every finalize on a tracker outage costs more than missing a critique on one run.
5. **The dispatcher writes the critique file and does not commit it.** The planner pane's git shim interferes with `pan` git writes, and promotion already runs `git add .pan/`. Rounds count from the tree or history, so an uncommitted round still counts on re-run and a committed one still counts after deletion.
6. **Critic isolation is prompt-level.** The read-only worker runs in the planner's workspace, where `.overdeck/continue.json` exists. The draft xBRIEF is inlined into the brief and the role prompt forbids reading `.overdeck/`. This is not enforced; it is stated here so nobody assumes otherwise.
7. **At the cap, finalize always proceeds.** After two rounds, unanswered `blocks-the-design` findings are listed in the PRD for the operator instead of blocking.
8. **No bypass flag.** There is no `--no-critic`. The operator's bypass is removing the label; `--critic` can only add a requirement.
9. **Exit code 5** is new and means "critique gate refused". Codes 1, 3 and 4 keep their meaning.
10. **Worker name `plan-critic-r<N>`** makes re-runs idempotent (FR-12).

```ts
/**
 * Plan digest for the plan critic (PAN-4341): SHA-256 over the draft xBRIEF
 * without lifecycle fields or the finalize stamp, so the value a critique
 * records still matches after `stampPlanForFinalization` runs.
 */
import { createHash } from 'node:crypto';

import { stableStringify, stripAllowedFields } from '../cloister/plan-integrity-gate.js';

export function planDigest(doc: unknown): string {
  const stripped = stripAllowedFields(doc);
  const plan = stripped.plan as Record<string, unknown> | undefined;
  const metadata = plan?.metadata as Record<string, unknown> | undefined;
  if (metadata) {
    delete metadata.canonicalFilename;
    delete metadata.promotionIntent;
    if (Object.keys(metadata).length === 0) delete plan!.metadata;
  }
  return createHash('sha256').update(stableStringify(stripped)).digest('hex');
}
```

### WI-5. Critic role prompt (FR-11)

Files: new `roles/plan-critic.md`. Commit with a `Prompt-Change:` trailer.

Content (plain Markdown, no frontmatter, no template variables; the dispatcher appends the issue-specific parts):

- You are an independent plan critic. You did not write this plan and must not coordinate with its author.
- Inputs: the PRD at the path given, the draft xBRIEF JSON in the brief, and the repository. Do not read `.overdeck/` or any transcript; they hold the author's reasoning, and reading them correlates you with it.
- Method, four principles: **Decorrelation** (your agreement with the author is not evidence; re-derive each claim). **Method-reconciliation** (before calling a number, line reference or behavior wrong, re-run the author's check: open the cited file and line, run the grep, count again). **Non-self-arbitration** (you do not decide whether the author's answer resolves your finding; the operator does). **"A reviewer would catch it" is a failed finding** (if the plan would let a defect reach review, report it now).
- Inventory existing mechanisms before proposing a new one; cite the file and line.
- Output format: one level-2 heading per finding, `## <classification>: <short title>`, where classification is exactly one of `blocks-the-design`, `sharpens-framing`, `footnote`, then evidence (file:line, command and output) and the smallest change that resolves it. Use `blocks-the-design` only when the plan as written would produce a wrong or unsafe result. No other level-2 headings. If you find nothing, write `## footnote: no blocking findings` with one line of evidence of what you checked.
- Do not edit files. Your report is the whole deliverable.
