# PAN-2359 — bug(deacon): `reapMergedStrikeWorkspaces` reaps FRESH strike workspaces

**Issue:** https://github.com/eltmon/overdeck/issues/2359
**File under repair:** [`src/lib/cloister/strike-workspace-reaper.ts`](../../src/lib/cloister/strike-workspace-reaper.ts)
**Discovered:** RUN-55 (2026-07-04) — `strike-pan-2357` reaped seconds after spawn.

## Glossary

- **Strike agent** — an out-of-pipeline fast-fix agent (`pan strike <id>`). Runs in a
  git worktree at `workspaces/feature-<id>-strike/` on a `strike/<id>` branch. Its merge
  flow (per `roles/strike.md` and `buildStrikePrompt` in `src/cli/commands/strike.ts:139`)
  is: commit on the strike branch → rebase onto `origin/main` → **fast-forward merge into
  `main`** → push. It never opens a review PR.
- **Reaper** — `reapMergedStrikeWorkspaces()` in `src/lib/cloister/strike-workspace-reaper.ts:48`,
  run every deacon patrol (`src/lib/cloister/deacon.ts:2790`). It removes a `strike/<id>`
  worktree + branch once the strike has merged, because strikes bypass close-out teardown
  and their worktrees otherwise pile up (PAN-1882).
- **"ahead"** — `git rev-list --count origin/main..<branch>` = the number of commits on
  `<branch>` that are NOT in `origin/main`. `ahead == 0` means every commit on the branch
  is already contained in `origin/main`.
- **Worktree-drift** — when an agent's git worktree loses its feature branch and HEAD
  lands on `main`, so the agent (correctly) refuses to edit and escalates. Here it is
  caused by the reaper removing the worktree out from under a live/spawning strike.

## Problem

The reaper reaps a strike worktree when its branch is `ahead == 0`
(`strike-workspace-reaper.ts:79`). The stated safety rationale in the module header is
"0 commits ahead — nothing unmerged is ever lost."

But **a just-created strike branch is also `ahead == 0`.** `ensureStrikeWorktree`
creates it with `git worktree add -b strike/<id> <workspace> origin/main`
(`src/cli/commands/strike.ts:116`), so before the agent commits anything the branch sits
exactly at `origin/main`'s HEAD — zero commits ahead, identical by ancestry to a merged
branch.

Two facts make this actively harmful:

1. **The spawn race.** `runOne` creates the worktree (`strike.ts:180`) *before* it spawns
   the agent's tmux session (`strike.ts:187`). During that window the reaper's liveness
   guard `sessionExistsSync('strike-<id>')` (`strike-workspace-reaper.ts:65`) returns
   false, so a deacon patrol landing in the gap sees `ahead == 0` + no session → reaps.
2. **The harm is not lost commits (there are none) — it is yanking an in-use worktree.**
   The removal dumps the spawning agent onto `main` (worktree-drift). Observed 2026-07-04:
   `strike-pan-2357` reaped seconds after spawn, agent landed on branch `main`, refused to
   edit, escalated, produced nothing.

### Root cause

The reap predicate treats "branch is an ancestor of `origin/main`" as "branch was
merged." Those are not the same: a branch that **never authored a commit** is trivially
an ancestor of `origin/main`. The predicate must instead require positive evidence the
strike actually did work that reached main — i.e. **the branch authored ≥1 commit AND all
of them are now in `origin/main`** — never merely "`ahead == 0`."

## Chosen discriminator (empirically verified)

Ancestry alone cannot distinguish the two `ahead == 0` cases (a fresh branch and a
fast-forward-merged branch both have their tip contained in `origin/main`). The
difference is whether the branch ever **authored** a commit. The git reflog records this
and never shrinks on merge:

| Strike state | `origin/main..branch` (ahead) | `git rev-list --walk-reflogs --count branch` |
| --- | --- | --- |
| **Fresh** (created from `origin/main`, no commits) | `0` | `1` (only `branch: Created from origin/main`) |
| **Merged** (authored a commit, ff-merged to main) | `0` | `2` (adds `commit: …`) |

Verified in a throwaway repo (init → clone → `worktree add -b … origin/main` → commit →
ff-merge → push → refetch): fresh gives `ahead=0 walkReflogs=1`; merged gives
`ahead=0 walkReflogs=2`.

**Fix:** reap only when `ahead == 0` **AND** `walk-reflogs count > 1` (branch authored at
least one commit). A never-committed branch (`walkReflogs == 1`) is never a reap
candidate, which fixes the exact observed incident: `strike-pan-2357` had authored 0
commits when it was reaped.

**Failure-mode safety:** the guard errs toward *not* reaping. If the reflog is
unavailable / expired / disabled, the count reads `1` (or the command errors → existing
`catch → continue`), so a genuinely-merged branch would merely leak (not be cleaned up)
rather than a fresh one being wrongly reaped. The dangerous direction (wrongful reap) is
structurally excluded.

## Proposal

In `reapMergedStrikeWorkspaces`, after the existing `ahead !== '0'` guard, add an
authored-commits guard using `git rev-list --walk-reflogs --count <branch>`; skip
(`continue`) when the count is `<= 1`. Update the module header comment so the safety
invariant reads "authored commits, all now in origin/main" rather than "0 commits ahead."
Extend the unit test's exec mock to answer the new command and add regression tests for
the fresh-branch case.

## Requirements

- **FR-1** — The reaper MUST NOT reap a `strike/<id>` worktree whose branch has authored
  zero commits (`walk-reflogs count == 1`), even when `ahead == 0` and no live session.
- **FR-2** — The reaper MUST still reap a `strike/<id>` worktree whose branch authored ≥1
  commit that is now fully in `origin/main` (`ahead == 0` AND `walk-reflogs count > 1`)
  and has no live session (no behavioral regression of PAN-1882 cleanup).
- **FR-3** — When merge/authored state cannot be determined (git command error), the
  reaper MUST leave the worktree untouched for a future patrol.
- **NFR-1** — The module-header safety comment MUST describe the corrected invariant.

## NonGoals

- Not adding a worktree-age grace window / timer. The reflog guard fixes the reported
  root cause (fresh, never-committed branch) directly and non-speculatively.
- Not changing the strike spawn ordering (`ensureStrikeWorktree` before `spawnAgent`).
- Not adding GitHub PR merged-state lookups — strikes ff-merge directly and open no PR,
  so PR state is not a usable signal for this reaper.
- Not closing the narrow reused-stale-branch corner (a prior merged `strike/<id>` branch
  whose `git branch -D` was skipped, re-checked-out for a new strike during the spawn
  window). Pre-existing, out of scope for this bug; recorded as a hazard.
- Not touching `feature/*` worktrees or any non-strike branch.

Single tracer-bullet slice: the predicate change, its module-header comment, and its
regression tests are one indivisible unit (the tests prove the guard). See vBRIEF item
`guard-authored-commits`.
