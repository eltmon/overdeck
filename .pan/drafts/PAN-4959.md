# PAN-4959: overdeck.ai account page (phase 1, read-only)

**Issue:** [PAN-4959](https://github.com/eltmon/overdeck/issues/4959). Part of PAN-2350. Sibling: [PAN-4960](https://github.com/eltmon/overdeck/issues/4960) (dashboard Account card + PKCE sign-in, split out during planning).
**Status:** plan for phase 1 only (operator decision 2026-11-03: ship read-only for invite-allowlisted testers, do not wait for billing PAN-4294).

## Glossary

- **Account service** — the Cloudflare Worker `overdeck-account` in `services/account/` at `https://account.overdeck.ai`. D1 database `overdeck-account`. Server-rendered HTML, no JavaScript, CSP `default-src 'none'` (`services/account/src/http.ts`, `HTML_CSP`).
- **Connect service** — the Cloudflare Worker `overdeck-connect` in `services/connect/` at `https://connect.overdeck.ai`. Holds one Durable Object per account.
- **Directory DO** — the `AccountDirectory` Durable Object (class in `services/connect/src/index.ts`, logic in `DirectoryHost`, `services/connect/src/directory.ts`). Named `DIRECTORY.idFromName(userId)`. Its SQLite tables hold the account's machines, phones (`clients`), approvals, `relay_usage`, `meta` (`plan`, `push_window`) and inbox tables (`inboxes`, `inbox_events`).
- **Machine** — a row of the Directory DO `machines` table, keyed by `environment_id`, carrying the `device_id` of the device token that last said `hello`. Not the same as an account-service **device** (a row of D1 `devices`, one per signed-in install).
- **Internal DO path** — a path served by `DirectoryHost.fetch` that only a Durable Object stub can reach (today `INTERNAL.socket = '/socket'`, `INTERNAL.inbox = '/inbox'`, `services/connect/src/env.ts`). The DO trusts every request on these paths.
- **Cross-script DO binding** — a `durable_objects.bindings[]` entry with `script_name` naming another Worker. The account Worker gets a stub to the Directory DO with it; the code still runs inside `overdeck-connect`.
- **Web session** — new in this issue: a signed-in browser session for an ordinary allowlisted user on `account.overdeck.ai`, cookie `__Host-od_account`, stored hashed in the new D1 table `user_sessions`. Distinct from the owner-only admin session (`__Host-od_admin`, `admin_sessions`).
- **Entitlement** — `entitlementFor(grant)` in `services/account/src/entitlement.ts`: `{ plan: 'free' | 'tester', storageBytesCap, maxDevices }`. `free` → 3 machines and no relay; `tester` (every other grant, and the owner) → unlimited machines and the relay.
- **Data holder** — a bound Worker that deletes a user's hosted data on account deletion (`AccountDataHolder.deleteAccountData(userId)`, `services/account/src/env.ts`). Today only the optional `VAULT` (unbuilt, PAN-4297).
- **Relay month** — UTC calendar month `YYYY-MM` (`monthOf`, `services/connect/src/relay-meter.ts`). Reset date = 00:00 UTC on the first day of the next month.

## Requirements

- **FR-1** `GET /account` on the account service renders a sign-in page ("Sign in with GitHub" button posting to `/account/login`) when the request has no valid web session, and the account page when it has one.
- **FR-2** Signing in through `/account/login` runs the shared GitHub leg with purpose `account`. An allowlisted GitHub id (owner or active grant) gets a web session; a user whose grant has expired but whose `users` row and `grants` row still exist gets a web session with access status "expired"; an account being deleted gets the page "This account is being deleted."; anyone else gets the existing invite-only page and **no** pending-attempt row.
- **FR-3** The account page shows the signed-in GitHub login and GitHub id, and a **Sign out** button that deletes the web session.
- **FR-4** The page shows the plan: `free` → "Free account", `tester` → "Tester", computed from `entitlementFor(getGrant(...))` — the grant row whether or not it expired, so an expired `free` grant still shows "Free account" (owner with no row → "Tester") — never from the Directory DO's `meta.plan`. `getGrant` is new in `services/account/src/grants.ts` (WI-4): the `getActiveGrant` query without the expiry clause. It shows access expiry ("No expiry", the date, or "Expired on <date>") and the sentence "Paid plans are invite-only for now." No price appears anywhere on the page.
- **FR-5** The page shows relay use: for `tester`, "<used> of <cap> GB relay traffic this month" (decimal GB, one decimal for used, same as `relayTrafficText` in `src/dashboard/frontend/src/components/Settings/anywhere/AnywhereStatusCard.tsx`) and "Resets on <YYYY-MM-01 of next month> (UTC).", plus "Relay allowance used; it resets on <date>." when `stopped`; for `free`, "The relay is not included in the free account." Extra traffic: "Paid plans are invite-only for now." (no Add 50 GB button).
- **FR-6** The page lists the account's directory machines (label, Online/Offline, last seen, Overdeck version) oldest first, with a count line: `free` → "<n> of 3 machines", `tester` → "<n> machines".
- **FR-7** Each machine row has a **Remove** button. Remove revokes that machine's device token (`revokeDevice(rc, userId, deviceId, 'user')`) and removes the machine from the Directory DO: its open socket closes with 4012, every other machine and phone of the account receives the updated `directory` frame, its approvals and inbox rows are deleted, and on a free account a new machine can then register in the freed slot.
- **FR-8** A **Billing** section says "Billing is not available yet. Paid plans are invite-only for now."
- **FR-9** A **Delete account** section states "Deleting your account signs out every device, removes your machines from the directory and deletes all of your hosted data within 24 hours." Delete is two-step: `POST /account/delete` shows a confirm page that asks for the GitHub login; `POST /account/delete/confirm` with the matching login (case-insensitive) runs `requestDeletion`, deletes every web session of the user, clears the cookie and shows "Your account is being deleted." A mismatch re-renders the confirm page with "Type your GitHub login to confirm." and status 400.
- **FR-10** The Directory DO answers three new internal DO paths: `GET /account-view` (machines + relay status), `POST /remove-machine` (JSON `{ "environmentId" }`), `POST /delete-account` (empties every table, closes every socket with 4001).
- **FR-11** When the `DIRECTORY` binding is present, account deletion lists `directory` as a data holder whose `deleteAccountData(userId)` calls `POST /delete-account`, so the deletion job completes only after the Directory DO is empty.
- **FR-12** When `DIRECTORY` is unbound, or the DO call throws or answers non-200, the page still renders; the machines and relay sections read "Machines and relay use are unavailable right now." and Remove is not shown. Remove answers the page with that message and status 503 instead of a 500.
- **NFR-1** Every mutation POST (`/account/logout`, `/account/machines/:environmentId/remove`, `/account/delete`, `/account/delete/confirm`) requires the session's `csrf` form field and `Origin` equal to `PUBLIC_BASE_URL`'s origin, else 403 "Request rejected."; `/account/login` requires the Origin (no session yet).
- **NFR-2** The page stays server-rendered with no JavaScript, every value through `escapeHtml()`, responses through `html()` (CSP and headers unchanged).
- **NFR-3** Web-session cookies and csrf tokens are stored hashed (session) / random (csrf) exactly like `admin_sessions`; the cookie is `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=43200` (12 h).
- **NFR-4** New POSTs are rate limited: bucket `account-login` (10 per 10 min) on `POST /account/login`; bucket `account-action` (30 per 15 min) on the four mutation POSTs.
- **NFR-5** No new runtime dependency, Web APIs only, `src/index.ts` stays the only `cloudflare:workers` importer in both Workers. Tests never wait on real time (injected `deps.now`).
- **NFR-6** Agents never deploy. Deploy order for this change: `overdeck-connect` first (new internal paths), then `overdeck-account` (binding + migration 0002).

## Decisions (made here)

- **D-1 Split.** The dashboard Account card and PKCE Sign in button moved to PAN-4960. Reason: the two halves share no code (the card only needs the URL `<baseUrl>/account`), and together they exceed one plan's size (6 subsystems, ~35 files).
- **D-2 Cross-script DO binding, not a service binding.** Account `wrangler.jsonc` gets `"durable_objects": { "bindings": [{ "name": "DIRECTORY", "class_name": "AccountDirectory", "script_name": "overdeck-connect" }] }`. No `migrations` entry (the class is not defined in this Worker). Connect already binds account, so a service binding back would be a cycle that Cloudflare documentation does not confirm is deployable.
- **D-3 Remove = revoke + forget.** Forgetting alone lets an offline machine re-register (Current state 7). The page revokes the machine's `device_id` first (D1), then calls `POST /remove-machine`. Page copy under the table: "Remove signs that machine out of overdeck.ai and frees its place. Sign in on it again to add it back."
- **D-4 Directory is a data holder.** `HOLDER_NAMES = ['vault', 'directory']`; `boundHolders(env)` returns, in this order, `'vault'` if `env.VAULT` and `'directory'` if `env.DIRECTORY`. This makes the page's deletion statement true for directory data.
- **D-5 New reducer event, not a null-socket `forget`.** Add `{ kind: 'remove-machine'; environmentId: string }` to `DirectoryEvent`. It never sends to `'self'`. `DirectoryHost` gets `self: WebSocket | null` in `apply`, `context`, `execute` and `resolve`; `resolve(null, 'self')` returns `[]`, `resolve(null, 'all' | 'others')` returns every registered machine socket.
- **D-6 Delete-account empties tables, it does not `deleteAll()`.** The DO keeps its schema (created once in the constructor), so `POST /delete-account` runs `DELETE FROM` on `machines`, `meta`, `approvals`, `relay_usage`, `clients`, `inboxes`, `inbox_events`, calls `storage.deleteAlarm()`, resets in-memory state to `EMPTY_DIRECTORY`, and closes every socket (machines and phones) with `4001` reason `account deleted`. Idempotent: a second call answers 200 with nothing to do.
- **D-7 Web session sign-in records no pending attempt.** `resolveSignIn`'s `flow` parameter becomes `SignInFlow | null`; `null` skips `recordPendingAttempt`. The page is for existing allowlisted users; invitations keep coming from device and PKCE sign-ins.
- **D-8 Migration 0002 rebuilds `auth_requests`.** Rows live 10 minutes, so dropping in-flight rows at deploy is acceptable; the migration copies them anyway (`INSERT ... SELECT`).
- **D-9 Expired-grant access.** Mirrors `GET /v1/me`: a user with an expired grant may sign in to the page, see it and delete the account; the plan line shows the grant's entitlement and "Expired on <date>". Access is revoked when the user is not the owner and `getGrant` returns null (operator revoked); such a user is refused at sign-in with the invite-only page, and an existing web session for them renders the sign-in page with "Access to this account was removed."
- **D-10 No phones list.** Phones (`clients`) are out of phase 1; the page lists machines only. Phones keep being removed from the phone app or a machine.
- **D-11 Structural types across Workers.** The account Worker does not import connect code. It declares the `/account-view` response shape structurally in `services/account/src/directory-view.ts`, the way `services/connect/src/account.ts` types `AccountRpc`.
