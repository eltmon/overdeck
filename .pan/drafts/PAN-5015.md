# PAN-5015: Classify GitHub's GraphQL "Something went wrong" and gh's "non-200 OK status code: 50x" as transient forge errors

**Issue:** [PAN-5015](https://github.com/eltmon/overdeck/issues/5015)

## Glossary

- **Transient forge error** — a failure talking to GitHub/GitLab that can succeed on retry (rate limit, network blip, 502/503/504). Decided by `isTransientForgeError()` in `src/lib/forge-transient.ts`, which tests one regex, `TRANSIENT_FORGE_ERROR`, against an error's `message` and `stderr`.
- **Verdict deferral** (PAN-4263) — when `pan admin specialists done review` fails to find the PR or post the review for a transient reason, it journals a `review.verdict-deferred` entry instead of dropping the verdict. deacon-lite replays it later (`src/lib/cloister/deferred-verdict-replay.ts`).
- **GraphQL 5xx message** — GitHub's GraphQL answer when it fails server-side. gh prints it as `GraphQL: Something went wrong while executing your query on 2026-11-04T10:15:14Z. Please include \`<request id>\` when reporting this issue.`
- **gh raw-5xx message** — gh's wording when the GraphQL endpoint returns a raw HTTP 5xx: `non-200 OK status code: 502 Bad Gateway body: "<html>..."` (Go `resp.Status` is `502 Bad Gateway`).
- **Anchoring** — the status-code alternative in the regex only matches after a known client prefix (`failed: `, `HTTP `), so a PR number like `/pull/504` inside a message never reads as a 5xx.

## Problem

On 2026-11-04 (about 10:15–11:20Z) GitHub's API was degraded. Three approvals were lost: for PAN-4956 (#4996) and PAN-4960 (#5010), `pan admin specialists done review --status passed` failed on `gh pr review --approve` with the GraphQL 5xx message. `deferIfTransient` (`src/cli/commands/specialists/done.ts`, line 221) called `isTransientForgeError(reason)`, which returned `false`, so no deferral was journaled and nothing replayed the verdict. The same hour, `gh pr update-branch` and `gh pr merge` failed with the gh raw-5xx message, which the regex also misses.

The regex today (`src/lib/forge-transient.ts`, line 14–15, grep anchor `const TRANSIENT_FORGE_ERROR =`):

```ts
const TRANSIENT_FORGE_ERROR =
  /rate limit|secondary rate|abuse detection|ECONNRESET|ETIMEDOUT|ENOTFOUND|EAI_AGAIN|ECONNREFUSED|socket hang up|timed out|(?:failed: |HTTP )50[234]\b/i;
```

It knows `HTTP 502` and `failed: 502`. It knows neither `Something went wrong while executing your query` nor `non-200 OK status code: 502`.

### Verified call paths (both reach the regex with the gh text intact)

1. **Post path.** `postReviewVerdict` (`src/lib/cloister/pr-review-verdict.ts`, line 202, grep `gh pr review failed: ${message}`) returns `reason: "gh pr review failed: <message>\n<stderr>"`; `errorText()` (line 105–110) appends gh's stderr. `done.ts` line 333 passes `result.reason` to `deferIfTransient`.
2. **Lookup path.** `getExistingGitHubArtifact` (`src/lib/forge.ts`, line 189, grep `` `gh pr view ${branchName} failed: ``) throws `new Error("gh pr view <branch> failed: <stderr>")`, so stderr is inside `message`. `done.ts` line 240 builds `reason` from `err.message` and line 242 passes it to `deferIfTransient`. Note the lookup message reads `failed: non-200 OK status code: 502 …`, which the existing `failed: 50[234]` alternative does not match.
3. **Lookup retry.** `discoverArtifact` wraps the lookup in `retryTransientForgeOp` (`forge.ts` lines 501 and 576). After this fix, that 2 s / 8 s retry also fires on the two new shapes. That is intended.

## Requirements

- **FR-1** `isTransientForgeError` returns `true` for the GraphQL 5xx message, given as an `Error`, a string, or an exec-shaped `{ message, stderr }` object.
- **FR-2** `isTransientForgeError` returns `true` for the gh raw-5xx message with status 502, 503, or 504.
- **FR-3** `isTransientForgeError` still returns `false` for `non-200 OK status code: 404 Not Found`, `non-200 OK status code: 500 Internal Server Error`, and a message containing a PR URL `/pull/502` with no 5xx text.
- **FR-4** A review verdict whose post fails with the GraphQL 5xx message is journaled as `review.verdict-deferred` and the command prints `The verdict is saved and deacon-lite will retry recording it.`
- **FR-5** A review verdict whose PR lookup fails with the gh raw-5xx message is journaled as `review.verdict-deferred`.
- **FR-6** `docs/PIPELINE-GATES.md` names both GitHub shapes as transient in the "Recording retries transient forge failures (PAN-4263)" paragraph.
- **NFR-1** The change is regex-only in production code: no new retry loop, no change to the 2 s / 8 s delays, no change to the deferral cap or cooldown.
- **NFR-2** The anchoring guarantee stays: no new bare `50[234]` alternative; every status-code match follows a client prefix.
- **NFR-3** No test uses real timers for delays (repo rule: fake timers for retry/backoff tests). The new tests here are synchronous classification tests and mocked-forge command tests, so they need no timers at all.

## Decisions

- **D1 — Extend the anchored alternation, do not add a bare `502`.** New status alternative: `(?:failed: |HTTP |non-200 OK status code: )50[234]\b`. Keeps `/pull/504` non-transient (NFR-2).
- **D2 — Match the GraphQL message by its fixed phrase** `something went wrong while executing your query` (case-insensitive via the existing `/i` flag). Do not match bare `Something went wrong`: that phrase is too generic and would catch unrelated failures.
- **D3 — 500 stays non-transient.** The current regex excludes 500 and the issue's fix names `50[234]`. A raw 500 is not added. (GitHub's GraphQL 5xx surfaces as the "Something went wrong" phrase, which D2 covers.)
- **D4 — Merge and update-branch paths are out of scope.** `gh pr merge` and `gh pr update-branch` do not call `isTransientForgeError` (only `src/lib/forge.ts` and `src/cli/commands/specialists/done.ts` import it). The issue cites their 502s as context only. This change gives them no retry.
- **D5 — `src/lib/cloister/deacon-api-recovery.ts` is unrelated.** Its `'502 Bad Gateway'` pattern classifies Claude API errors in agent panes, not forge errors. Do not touch it.
