## Glossary

- **Permission mode**: how a Claude Code or Codex session that Overdeck launches is gated before a tool call runs.
- **Auto**: Overdeck's name for the Claude Code mode `claude.permissionMode: auto`. It is not a Claude Code flag value;
  it emits `--permission-mode default`.
- **Bypass**: `claude.permissionMode: bypass`; emits `--permission-mode bypassPermissions`.
- **Auto-approve hook**: the `PreToolUse` hook script `~/.overdeck/bin/auto-approve-hook`, registered in
  `~/.claude/settings.json` by `pan sync`. Source: `sync-sources/hooks/auto-approve-hook`.
- **Agent id**: the `OVERDECK_AGENT_ID` environment value Overdeck sets when it launches a session.
- **Shim**: a small `git` or `gh` wrapper script that the launcher puts first on an agent's `PATH`. Source:
  `src/lib/launcher-git-guard.ts`.
- **Primary checkout**: a project's main clone (the registered project path), as opposed to a worktree under
  `workspaces/`.
- **Operator grant labels**: the tracker labels `released`, `auto-merge`, `hold-for-uat` and `vetoed`.
- **Mint check**: `npx -y mint@4.3.49 validate` and `npx -y mint@4.3.49 broken-links`, run from the workspace root.
  Always pin `mint@4.3.49`. Never run `mint validate --fix`: it rewrites many files that sibling docs issues edit.
- **Dash rule**: no em dash (U+2014) or en dash (U+2013) in any line this issue adds or edits, and none in the
  frontmatter `title` or `description` of any touched page.

`FE/` below means `src/dashboard/frontend/src/`.

## Background: verified facts

### Claude Code permission modes

- F-1. Two modes, `auto` and `bypass` (`src/lib/config.ts`, `export type ClaudePermissionMode = 'bypass' | 'auto';`).
  Auto emits `--permission-mode default`; bypass emits `--permission-mode bypassPermissions`
  (`src/lib/claude-permissions.ts` line 88, `return ['--permission-mode', 'default'];`, and
  `BYPASS_PERMISSION_MODE = 'bypassPermissions'`). Every Claude Code launch site uses this resolver: work agents,
  resumes, planning, conversations, smart compaction and remote agents (`grep -rn getClaudePermissionFlags src`).
- F-2. Default: `auto` for a new installation (`src/lib/config-yaml/defaults.ts` line 290, `permissionMode: 'auto',`).
  An installation that existed before v0.80.0 was pinned once to `bypass`: on first run of that version, if
  `~/.overdeck/config.yaml`, `config.toml` or `overdeck.db` already existed and `claude.permissionMode` was absent or
  invalid, Overdeck wrote `claude.permissionMode: bypass` into `~/.overdeck/config.yaml` and printed a notice
  (`src/lib/claude-permission-mode-pin.ts` line 105, `doc.setIn(['claude', 'permissionMode'], 'bypass');`). The
  decision is recorded in `~/.overdeck/.claude-permission-mode-pin.json` (line 38) and never repeats. An existing
  install moves to Auto by choosing Auto in Settings.
- F-3. **Where to set it:** Settings → **Permissions** → **Claude Code** has two options, **Auto (recommended)** and
  **Bypass (yolo)** (`FE/components/Settings/sections/PermissionsSection.tsx`, `title: 'Auto (recommended)'`,
  `title: 'Bypass (yolo)'`). It saves `claude.permissionMode` in `~/.overdeck/config.yaml`. The YAML form:

  ```yaml
  claude:
    permissionMode: auto   # or bypass
  ```

  An unrecognized value prints a `[config]` warning naming the valid values (`src/lib/config-yaml/merge.ts`,
  `is not a valid value`).
- F-4. **What the auto-approve hook does** (`sync-sources/hooks/auto-approve-hook`, read in full, 96 lines). For a
  session whose agent id starts with `agent-`, `planning-`, `flywheel-`, `strike-`, `inspect-`, `sequencer-` or
  `conv-` (line 73, `agent-*|planning-*|flywheel-*|strike-*|inspect-*|sequencer-*|conv-*) : ;;`), it returns
  `permissionDecision: "allow"` for every tool except `AskUserQuestion` (line 78). It inspects nothing else: no command
  filter, no path check. Any other session (agent id unset, such as a `claude` you start yourself) is left alone and
  keeps Claude Code's normal prompts. It logs each call to `~/.overdeck/logs/auto-approve.log`. On any error it exits
  silently, which falls back to Claude Code's normal prompt.
  **Do not write that Auto "blocks destructive" commands, uses a "classifier", or filters force pushes or `rm -rf`.**
  The Settings description and `pan --help` say so; that text is wrong and tracked in #5566 (D-3).
  Which sessions those prefixes cover (verified id formats): issue agents `agent-<issue>` including review
  (`src/lib/cloister/review-convoy.ts`, `` `agent-${issueId.toLowerCase()}-review-${subRole}` ``), test, and workers
  (`src/lib/agents/worker/ids.ts`, `` `agent-${issueId.toLowerCase()}-worker-` ``); planning agents; conversations; the
  Flywheel; strike and inspect agents; the backlog sequencer. Write that list in plain words; do not claim it covers
  "every" session.
- F-5. **So, in practice:** under either mode a session Overdeck launches runs without stopping for routine approval.
  Bypass gets there by turning Claude Code's own gating off (the `pan doctor` row reads that tool calls are not gated
  and the hook is not needed, `src/cli/commands/doctor-permission-mode.ts`, `bypass`). Auto keeps Claude Code's
  default mode and relies on the hook, which approves only sessions with an Overdeck agent id. Neither mode is a
  sandbox. The guardrails in F-20 to F-36 are what stop specific mistakes.
- F-6. **Launch guard under Auto** (`src/lib/agents/hook-readiness.ts`, `ensureAutoApproveHookReady`): before a Claude
  Code launch, if the hook is not registered, Overdeck tries to register it; if it still cannot (registration needs
  `jq`), the launch is refused with an error that names `pan sync` and the Bypass option (line 69,
  `Claude Code permission mode is auto, but`). It never launches an agent that would prompt on every tool call. Under
  bypass the guard does nothing.
- F-7. **`pan doctor`** shows a **Claude Permission Mode** row (`doctor-permission-mode.ts` line 31). Under Auto it is
  an error when the hook is not registered in `~/.claude/settings.json`; the fix it prints is to run `pan sync` (needs
  `jq`) or set bypass. The messages contain em dashes: paraphrase them, never quote them.
- F-8. **Remote Fly agents need bypass.** A Fly VM has no Overdeck hooks, so a remote launch under Auto is refused with
  an error that says to choose Bypass in Settings → Permissions or start with `PAN_YOLO=true`
  (`src/lib/remote/remote-agents.ts` line 612, `Remote Fly agents need claude.permissionMode: bypass`).
- F-9. **A change applies to new launches only.** A running Claude Code process keeps the flags it started with
  (`claude-permissions.ts`, AUDIT TRAP comment, `a running \`claude\` process keeps the flags it was launched with`).
  After a change, agents and conversations already running keep their old mode until they are restarted or resumed.

### Override the mode for one command

- F-10. `pan --help` lists a global `--yolo [value]` option (`src/cli/index.ts` line 134). Forms: `--yolo`,
  `--yolo=true`, `--yolo true` (bypass); `--yolo=false`, `--no-yolo` (auto). It works in any argv position
  (`pan --yolo start PAN-12` and `pan start PAN-12 --yolo` are the same). The CLI only sets `PAN_YOLO` on its own
  process (line 84, `process.env.PAN_YOLO = value.trim().toLowerCase();`).
- F-11. `PAN_YOLO` values (`claude-permissions.ts` line 25, `YOLO_TRUE` / `YOLO_FALSE`): `1`, `true`, `yes`, `y`, `on`
  mean bypass; `0`, `false`, `no`, `n`, `off` mean auto; anything else is ignored.
- F-12. Precedence (`resolvePermissionMode`, line 66): `PAN_YOLO` (so also `--yolo`) first, then
  `claude.permissionMode` from config, then `auto`. If the config cannot be read, the result is `auto`.
- F-13. **Reach.** `PAN_YOLO` affects the `pan` process you run and the processes it starts. `pan start <id> --yolo`
  launches that work agent from your shell, so the agent gets bypass. `pan up --yolo` starts the dashboard server with
  your environment (`src/cli/index.ts` line 860, `const dashboardBootEnv = applyBootGateEnv({ ...process.env }, options);`),
  so agents and conversations that dashboard launches use bypass for as long as that dashboard process runs. Agents
  already running are unchanged (F-9). For a lasting change, use Settings → Permissions. Do not claim more than this
  (for example, do not claim `pan reload` keeps or drops the override).

  Auto-review description in the UI contains an em dash: paraphrase it (a Codex sub-agent reviews approval requests and

- F-15a. **Default transport caveat (#5567).** `codex.transport` defaults to `app-server` (`defaults.ts`,

### Operator-only labels

- F-20. Meanings (link, do not restate in depth): `released` lets the Flywheel pick an issue up
  (`/features/flywheel`); `vetoed` stops the Flywheel from ever picking it up, planning it or striking it
  (`/features/flywheel`); `auto-merge` and `hold-for-uat` override the merge policy for one issue
  (`/configuration/auto-merge`).
- F-21. The agent `gh` shim refuses any `gh issue|pr edit|create` label flag or non-GET `gh api` label write that names
  one of the four labels, in any case or list form, and tells the agent to ask the operator
  (`src/lib/launcher-git-guard.ts` line 381, `is an operator grant label (released, auto-merge, hold-for-uat, vetoed)`).
  A refused call exits 1. Work agents, conversations and the Flywheel get this shim (changelog v0.64.0 #4379, v0.87.0
  #5325; conversations get a `gh` shim, line 50, `beside their \`gh\``).
- F-22. The dashboard routes that write these labels (the merge policy toggle and the backlog veto) need the `admin`
  access level, which no agent token holds (`src/dashboard/server/route-scopes.ts` line 260,
  `PAN-5321: POST /api/merge-train/policy/:issueId has no row on purpose.`; the backlog gate route has no row either,
  and unlisted routes need `admin`, header line 4).
- F-23. It is a `PATH` shim that stops accidents, not a sandbox: an absolute `/usr/bin/gh` bypasses it (line 31,
  `An absolute \`/usr/bin/gh\` bypasses it too.`). Say so in one sentence.

### The agent git shim

- F-24. Agents' `git` refuses `git rebase` (suggesting `pan sync-main` or `pan done`), state-moving `git stash`
  (`git stash list` and `git stash show` stay allowed), and `git reset --hard` (lines 561, 584, 592).
- F-25. It refuses `commit`, `push`, `merge` and `cherry-pick` in an issue worktree that is not on its expected branch
  or is on a detached HEAD (line 275, `must be on branch`). Expected branches: `workspaces/feature-<name>` must be on
  `feature/<name>`; slot and swarm item worktrees have their own branch rules (header lines 33 to 41). The message tells
  the agent to stop and report through `pan tell`.
- F-26. It only acts on the agent's own worktree; a `git rebase` inside a test fixture repository passes through
  (header, scoping rule 1).
- F-27. `pan worker run --read-only` workers get a stricter shim: any git write in the workspace's repository is
  refused; reads such as `status`, `diff`, `log` and `show` are allowed (line 205). `pan worker run --help` shows
  `--read-only  Run in the issue workspace with git writes blocked`.
- F-28. Each agent commit gets an `Overdeck-Agent: <agentId>` trailer; conversations get a trailer-only shim that adds
  `Overdeck-Conversation: <id>` and refuses nothing (line 50). Not a sandbox: an absolute `/usr/bin/git` bypasses it,
  and file-system and network writes are not restricted (line 24).

### Primary checkout refusals

- F-29. `pan fork` and `pan handoff` take `--cwd <path>`. The path must be absolute, contain no `..`, exist as a
  directory, and resolve inside your home directory (`src/lib/overdeck/cwd-containment.ts` line 23); otherwise the
  dashboard answers `Invalid cwd`.
- F-30. A `--cwd` inside a project's primary checkout is refused with `Invalid cwd: <path> is the primary checkout of
  <project>; use a worktree` (`src/lib/overdeck/conversation-forks.ts` line 795). `--allow-primary` overrides it only
  when the caller is the operator; agent sessions are refused even with the flag (`pan fork --help` and
  `pan handoff --help`: `Operator only: allow --cwd to be a project's primary checkout (refused for agent sessions)`).
- F-31. `pan worker run --cwd <path>` must stay inside the issue workspace; a read-write worker whose `--cwd` resolves to
  a primary checkout is refused (`src/lib/agents/worker/start.ts` line 148). `--read-only` workers are not checked.
- F-32. The file explorer never writes a project's main checkout; edits go to an edit workspace. One sentence and a
  link to `/features/file-explorer#edit-workspaces`.

### Other guardrails

- F-33. `pan task claim <issue> <item>` refuses an item another live agent holds, or one whose `files_scope` overlaps
  an item another live agent holds; a low-confidence scope counts as overlapping. `--steal` claims anyway and reports
  what it overrode (`src/lib/xbrief/claim-check.ts` line 145; `pan task claim --help`: `Claim even when a running
  agent holds this item or an overlapping one (foreman/operator override)`). Link `/cli/pipeline-commands`.
- F-34. Before an issue agent starts, Overdeck adds deny rules to the workspace's `.claude/settings.local.json`
  (`src/lib/agents/spawn-prep.ts` line 698; patterns at `src/lib/claude-settings-overlay.ts` line 46): no edits or
  writes to `.claude/agents/` and `.claude/hooks/`, no `rm` of those folders, of `~/.overdeck/` or of
  `~/.claude/projects/`, and no `tmux send-keys` or `tmux paste-buffer`. The code calls them best effort: they match
  the start of a command, so `cd .claude && rm -rf agents/` is not caught.
- F-35. A work agent (agent id `agent-<prefix>-<number>`) cannot type into another session: the `tmux-send-keys-guard`
  hook rewrites a `tmux send-keys` or `tmux paste-buffer` aimed at another session into a failing command
  (`sync-sources/hooks/tmux-send-keys-guard` line 24). Agents message each other with `pan tell`.
- F-36. Screenshots: `images/` has no Settings, permission dialog or Needs you screenshot. Use none (issue rule).
