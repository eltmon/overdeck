# PAN-5068: Account sign-in retries the device-code request on a network error and shows fetch's real cause

**Issue:** [PAN-5068](https://github.com/eltmon/overdeck/issues/5068)
**Status:** planned (auto mode, 2026-11-05)

## Glossary

- **Device flow** — the RFC 8628 sign-in that `pan account login` and `pan mcp connector login` run against the overdeck.ai account service (`https://account.overdeck.ai` by default). Step 1 is `POST /oauth/device/code` (the **device-code request**); step 2 is a polling loop on `POST /oauth/token`.
- **Account client** — `src/lib/account/client.ts`. It holds every HTTP call to the account service. Both login commands call the same `requestDeviceCode` and `pollForToken` functions in it.
- **Network error / thrown error** — `fetch` rejects (throws) instead of returning a `Response`. Node's fetch (undici) always throws `TypeError: fetch failed` and puts the real reason in `error.cause` (an object such as `{ code: 'ECONNRESET', message: 'socket hang up' }`).
- **HTTP error response** — `fetch` resolves with a `Response` whose status is not 2xx (for example 400, 429 or 503). This is not a network error.
- **Cause suffix** — the text that `describeError` appends after the error message, in parentheses, built from `error.cause.code` and `error.cause.message`.
- **Backoff** — the wait between two attempts of the device-code request: 1 000 ms after the first failure, 2 000 ms after the second.

## Problem

On a fresh cloud VM (Node 24.22.1, Debian 13) the first `pan mcp connector login` failed with `Cannot reach https://account.overdeck.ai: fetch failed`. An immediate retry worked, and curl reached the service a few minutes earlier. Two defects in the account client caused this:

1. `requestDeviceCode` (`src/lib/account/client.ts`, line 103, grep anchor `export async function requestDeviceCode(`) calls `postForm` once. Any thrown error ends the login. A single transient failure (cold DNS, a reset first TLS connection, a Happy Eyeballs miss) is enough. `pollForToken` in the same file already tolerates two consecutive failures (line 172, `if (consecutiveFailures >= 3)`); the first request has no tolerance.
2. `describeError` (`src/lib/account/client.ts`, line 90, grep anchor `function describeError(error: unknown): string {`) returns only `error.message`. For an undici failure that is always `fetch failed`, so the user cannot tell DNS from TLS from a timeout.

## Requirements

- **FR-1** — When `describeError` receives an `Error` whose `cause` is an object with a string `code` and/or a non-empty string `message`, it returns `<error.message> (<suffix>)`, where `<suffix>` is `code: message` when both exist, `code` when only the code exists, and `message` when only the message exists.
- **FR-2** — When the error has no `cause`, or the `cause` is not an object, or the object has neither a string `code` nor a non-empty string `message`, `describeError` returns exactly what it returns today (`error.message` for an `Error`, `String(error)` otherwise).
- **FR-3** — `requestDeviceCode` makes up to 3 attempts of `POST /oauth/device/code`. After a thrown error on attempt 1 it waits 1 000 ms; after a thrown error on attempt 2 it waits 2 000 ms. The waits use the existing `sleep` helper.
- **FR-4** — `requestDeviceCode` never retries when `fetch` returns a `Response`, whatever its status (400, 429, 503 …). A non-2xx response still throws `Cannot start sign-in at <baseUrl>: HTTP <status>` after exactly one fetch call.
- **FR-5** — After the third thrown error, `requestDeviceCode` throws `AccountClientError` with the message `Cannot reach <baseUrl>: <describeError(last error)>`. The last error wins, not the first.
- **FR-6** — A single transient network failure of the device-code request no longer fails `pan mcp connector login` (exit code 0, account stored) or `pan account login` (same client function).
- **FR-7** — `cli/account.mdx` and `docs/ACCOUNT-SERVICE.md` state that the device-code request is retried on a network error and that the `Cannot reach` reason names the underlying cause code.
- **NFR-1** — Every retry/backoff test uses `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`; no test waits real wall-clock time (repo rule "Fake timers for retry / backoff / delay-based tests").
- **NFR-2** — No error message or `detail` string includes the device token, the device code, the authorization code, or the PKCE verifier (module header invariant of `client.ts`). Undici's cause normally carries only connection information, but an injected or future `fetch` may put anything in `cause.message`, so `describeError` takes the calling request's secret values and replaces every occurrence of each in its whole result (message and suffix) with `[redacted]`.
- **NFR-3** — `client.ts` keeps importing only Node built-ins (module header: the standalone `pan account` CLI loads it without the dashboard or Effect runtime).

## Decisions

- **D-1 Retry any thrown value.** The retry fires on any value `doFetch` throws, not only on `TypeError`. Reason: the only code inside the `try` is the fetch call, and a test-injected fetch or a future runtime may throw other types. HTTP responses are never retried (FR-4), as the issue requires.
- **D-2 5xx is not retried.** The issue says "do not retry an HTTP error response". A 503 is an HTTP error response, so it is not retried. This differs from `pollForToken`, which counts 5xx as a failure; that difference is deliberate and out of scope.
- **D-3 Last error wins** in the final message (FR-5), because the last failure is the most current diagnosis.
- **D-4 One level of cause.** `describeError` reads `error.cause` only, never `error.cause.cause`. Undici puts the useful reason at one level.
- **D-5 Shared helper, shared benefit.** `describeError` is also used by `pollForToken`, `exchangeAuthorizationCode`, `getMe` and `revokeDevice`, so their `detail` strings (and the dashboard's `account-sign-in.ts` detail, which consumes `exchangeAuthorizationCode`) gain the cause suffix too. This is intended. Existing tests pass plain `new Error('network down')`, `new Error('ECONNREFUSED')` and `new Error('offline')` with no cause, so their expected strings do not change.
- **D-6 Silent retry.** No progress line is printed during the backoff. The worst-case added delay is 3 s plus fetch's own timeouts.
- **D-7 Docs are touched.** The issue says "no documented surface changes", but `cli/account.mdx` line 69 documents `Cannot reach <baseUrl>: <reason>` only for the polling phase. The work item updates that sentence and the `login` bullet in `docs/ACCOUNT-SERVICE.md`. This is a one-sentence touch per file, more accurate than a justification.
- **D-9 Redact, do not confine.** The cause suffix applies to every call in `client.ts` (the poll's `unreachable` detail is the most common place a user sees a network error), and each secret-bearing call passes its secrets to `describeError`: `pollForToken` passes `[code.deviceCode]`, `exchangeAuthorizationCode` passes `[input.code, input.codeVerifier]`, `getMe` and `revokeDevice` pass `[token]`. `requestDeviceCode` sends no secret (`platform`, `environment_id`) and passes none. Empty strings are skipped so they never match everything. Adopted from the plan critique (see Critique response).
- **D-8 Duplicated text is acceptable.** For `getaddrinfo ENOTFOUND account.overdeck.ai` with code `ENOTFOUND`, the suffix reads `(ENOTFOUND: getaddrinfo ENOTFOUND account.overdeck.ai)`. No de-duplication logic.

```ts
/** Node's fetch reports every network failure as `fetch failed` and puts the reason in `cause`. */
function describeCause(cause: unknown): string | null {
  if (typeof cause !== 'object' || cause === null) return null;
  const { code, message } = cause as { code?: unknown; message?: unknown };
  const parts = [typeof code === 'string' ? code : '', typeof message === 'string' ? message : ''].filter((part) => part !== '');
  return parts.length > 0 ? parts.join(': ') : null;
}

/** `secrets` are the request's sensitive values; each is replaced in the whole result, cause included. */
function describeError(error: unknown, secrets: readonly string[] = []): string {
  let text = String(error);
  if (error instanceof Error) {
    const cause = describeCause(error.cause);
    text = cause === null ? error.message : `${error.message} (${cause})`;
  }
  for (const secret of secrets) {
    if (secret !== '') text = text.replaceAll(secret, '[redacted]');
  }
  return text;
}
```

### W-2 `requestDeviceCode` retries a thrown error (FR-3, FR-4, FR-5, NFR-1)

**Files:** `src/lib/account/client.ts`, `tests/unit/lib/account/client.test.ts`. Depends on W-1 (same files; the final-message test reads W-1's suffix).

Before (`client.ts` lines 108–114):

```ts
  const doFetch = opts.fetch ?? fetch;
  let res: Response;
  try {
    res = await postForm(baseUrl, '/oauth/device/code', new URLSearchParams({ platform: input.platform, environment_id: input.environmentId }), doFetch);
```

```ts
/** Waits between device-code attempts after a thrown (network) error: 3 attempts in all. */
const DEVICE_CODE_RETRY_DELAYS_MS = [1_000, 2_000];

  const doFetch = opts.fetch ?? fetch;
  const form = new URLSearchParams({ platform: input.platform, environment_id: input.environmentId });
  let res: Response;
  for (let attempt = 0; ; attempt += 1) {
    try {
      res = await postForm(baseUrl, '/oauth/device/code', form, doFetch);
      break;
    } catch (error) {
      const delayMs = DEVICE_CODE_RETRY_DELAYS_MS[attempt];
      if (delayMs === undefined) throw new AccountClientError(`Cannot reach ${baseUrl}: ${describeError(error)}`);
      await sleep(delayMs);
    }
  }
```

## Critique response

### shared cause text can expose sign-in secrets

Accepted. The cause suffix stays shared (the poll's `unreachable` detail is where most users meet a network error), and `describeError` now takes the calling request's secrets and replaces each one with `[redacted]` in its whole result, message and suffix alike (D-9, NFR-2, W-1). `pollForToken` passes the device code, `exchangeAuthorizationCode` the authorization code and PKCE verifier, `getMe` and `revokeDevice` the device token; `requestDeviceCode` sends no secret. W-1 adds tests where the cause message contains the authorization code, verifier and device token, and asserts the `detail` contains `[redacted]` and none of them. This also hardens the existing `error.message` path, which had the same theoretical exposure.
