# PAN-4560 — Profile dashboard re-renders under live event load and fix the top offenders

**Issue:** [PAN-4560](https://github.com/eltmon/overdeck/issues/4560) · **Related:** [PAN-4561](https://github.com/eltmon/overdeck/issues/4561) (React 19 + React Compiler, runs after this one)

## Glossary

- **Store** — the main Zustand store `useDashboardStore` in `src/dashboard/frontend/src/lib/store.ts`. Its state extends the shared `ReadModelState` from `packages/contracts/src/event-reducers.ts`. Zustand is **4.5.7**: a `useDashboardStore(selector)` call re-renders its component whenever `Object.is(prevResult, nextResult)` is false after any `set()`.
- **Slice** — one top-level map of the store, for example `agentsById`, `agentRuntimeById`, `issuesRaw`, `backendPanesById`, `derivedIssueStateByIssueId`, `recentActivity`.
- **Entry** — one value inside a slice, for example `agentsById['agent-pan-1']`.
- **Identity** — object reference. "Keeps identity" means the reducer or selector returns the very same object (`===`) when nothing the reader uses changed.
- **Fresh-value selector** — a selector that builds a new array or object on every call (`Object.values(...).filter(...)`, `?? []`). It re-renders its component on every store `set()`, including sets for unrelated events.
- **Whole-slice subscriber** — a component that subscribes to an entire slice (for example `useDashboardStore(selectAgents)`) when it needs one entry. It re-renders whenever any entry in that slice changes.
- **Domain event** — a sequenced event from `/ws/rpc` `subscribeDomainEvents`. `EventRouter.tsx` batches them every 16 ms and applies each batch with one `applyEvents` call.
- **Runtime event** — the high-frequency agent events (`agent.activity_changed`, `agent.thinking_started`, …) that the reducers write into `agentRuntimeById`. A Claude Code agent produces at least two per tool call: one from the PreToolUse hook and one from the PostToolUse hook.
- **Streamed delta** — one `subscribeConversationMessages` event for the open conversation. `useConversationMessagesStream.ts` writes it into the TanStack Query cache key `['conversation-messages', name]` with `setQueryData`.
- **Command Deck route** — the `command-deck` tab: `App` shell (`App.tsx`, `AppChrome`), `CommandDeck` (`components/CommandDeck/index.tsx`), its project tree (`ProjectNode` → `FeatureItem` rows), the conversation list (`ConversationList` → `ConversationRow`), and the Stage (`Stage` → `AgentPane` → `ConversationPanel`, or the issue cockpit `IssueMissionControl`).
- **Render-count test** — a Vitest test that mounts a component or hook, applies one representative event, and asserts how many times named subtrees re-rendered. It fails if the count goes up.
- **Profiling build** — a production Vite build where `react-dom` resolves to `react-dom/profiling`, so React records per-fiber timings (`fiber.selfBaseDuration`) in production mode.
- **bippy** — the MIT library by the author of react-scan that installs the React DevTools global hook and walks the fibers that rendered in a commit (`instrument`, `traverseRenderedFibers`, `isCompositeFiber`, `getDisplayName`, all present in **bippy@0.7.3**, released 2026-08-22).

## Problem

Nobody has measured how much the dashboard re-renders when domain events or conversation stream events arrive. A static census for this plan found these structural causes. Every reference below was checked against the tree at `6f80870ebfc`.

1. **Runtime events rewrite `agentsById` to bump a field nothing reads.** `packages/contracts/src/event-reducers.ts:276-284`:
   ```ts
   function bumpRuntimeSnapshotSequence(
     agentsById: Record<string, AgentSnapshot>,
     agentId: string,
     sequence: number,
   ): Record<string, AgentSnapshot> {
     const agent = agentsById[agentId]
     if (!agent) return agentsById
     return { ...agentsById, [agentId]: { ...agent, runtimeSnapshotSequence: sequence } }
   }
   ```
   It is called from every runtime case (search `bumpRuntimeSnapshotSequence(state.agentsById` — 12 call sites, the first in `case 'agent.activity_changed'` near line 1087). `git grep runtimeSnapshotSequence` finds only this function, the schema field `packages/contracts/src/types.ts:392` (`runtimeSnapshotSequence: Schema.optional(SequenceNumber),`) and the unit test `tests/contracts/agent-runtime-reducers.test.ts:375-390`. It contradicts the `ReadModelState` comment at `event-reducers.ts:81-85`: *"Kept separate from agentsById because it updates on every tool call; merging would cause the whole AgentSnapshot to re-diff on the frontend."* Every `selectAgents` subscriber (including `App.tsx:633` and `CommandDeck/index.tsx:446`) therefore re-renders at least twice per tool call per agent.
2. **`selectBackendPanes` is a fresh-value selector used in every issue row.** `src/dashboard/frontend/src/lib/store.ts:332-337`:
   ```ts
   export const selectBackendPanes =
     (issueId: string) =>
     (s: DashboardState): BackendPane[] =>
       Object.values(s.backendPanesById).filter(
         (pane) => pane.issue?.toUpperCase() === issueId.toUpperCase(),
       )
   ```
   `useIssueActions` calls it (`components/IssueActionMenu/useIssueActions.ts:212`). Every Command Deck `FeatureItem` row mounts `useIssueActions` through `FeatureContextMenu` (`ProjectTree/FeatureItem.tsx:937`, hook at `:411`). So **every issue row re-renders on every store `set()`**, whatever the event. The same selector is used by `KanbanCards.tsx:566`, `drawer/useDrawerData.ts:306` and `issue-detail/IssuePeek.tsx:39`.
3. **`useIssueActions` subscribes to whole slices.** `useIssueActions.ts:209-210` — `useDashboardStore(selectIssues)` and `useDashboardStore(selectAgents)` — then finds one issue and one agent (`:218-219`). Every row re-renders when any issue or agent changes.
4. **`App` subscribes to whole slices, so any change re-renders the entire tree.** `App.tsx:230` (`recentActivity`), `App.tsx:633` (`selectAgents`), `App.tsx:640` (`selectIssues`), `usePendingInputDialogs({ agents, issues })` at `App.tsx:661` (which also subscribes to `selectAgentsWithPendingAskUserQuestion` and `selectAgentsWithPendingProposedPlan`, `App/hooks/usePendingInputDialogs.ts:44-45`), and `useDesktopActivityNotifications()` (`App/hooks/useDesktopActivityNotifications.ts:21`, `recentActivity`). Nothing below `App` on the Command Deck route is wrapped in `React.memo`, so each of these changes re-renders `AppChrome`, `AppRoutes`, `CommandDeck`, the tree, the list, the Stage and the open conversation.
5. **`CommandDeck` subscribes to whole slices.** `CommandDeck/index.tsx:446` (`useDashboardStore(selectAgents)`), `lib/useAgentSetInvalidation.ts:25` (`selectAgents`, called from `CommandDeck/index.tsx:288`), and the `issues` prop that `App` passes through `AppRoutes` (`App/AppRoutes.tsx:126`).
6. **The open issue cockpit subscribes to every agent.** `Stage/cockpit/IssueMissionControl.tsx:404` — `useDashboardStore(selectAgents)`, then filters to the issue.
7. **A streamed delta re-renders the composer.** `chat/ConversationPanel.tsx`: `handleMessageSent` depends on `serverMessages` (`:1285-1289`, a new array per delta), `contextWindowUsage` is rebuilt every render (`:1271`), and `ComposerFooter` (`chat/ComposerFooter.tsx:957`) is not memoized. So the whole composer toolbar (model picker, effort picker, context meter, attachments) re-renders on every delta.
8. **A conversation-list poll re-renders every row.** `CommandDeck/ConversationList.tsx:420-465` passes an inline `onSelect={(name) => onSelectConversation(name)}` and the `mutations` object (rebuilt on every call, `CommandDeck/useConversationMutations.ts:308-331`) to unmemoized `ConversationRow`s, each inside a `<motion.div layout>`. TanStack Query structural sharing already keeps unchanged conversation objects identical, so only the streaming conversation's object changes on a poll, but every row still re-renders.

## Goals

- Measure the four scenarios from the issue with a repeatable tool and post the table.
- Fix the offenders above so that, on the Command Deck route, one streaming conversation re-renders only the open timeline and its own conversation-list row, and a domain event for one issue or agent re-renders only the rows that show it.
- Guard each fixed path with a render-count test.
- Document the selector and identity rules the fixes depend on.

## Requirements

### Functional

- **FR-1** A repeatable profiling tool records, per scenario, which components commit, how often, and their self render time, against a production profiling build.
- **FR-2** The profiling table for all four scenarios (streaming conversation, domain-event burst with no conversation open, composer typing, idle tickers) is posted on [PAN-4560](https://github.com/eltmon/overdeck/issues/4560) before the fixes land ("baseline") and after ("after").
- **FR-3** Runtime events (`agent.activity_changed`, `agent.thinking_started`/`_stopped`, `agent.message_received`, `agent.waiting_*`, and the other cases that call `bumpRuntimeSnapshotSequence`) no longer change `agentsById` identity.
- **FR-4** `selectBackendPanes(issueId)` returns the same array instance while that issue's panes are unchanged.
- **FR-5** `useIssueActions(issueId)` re-renders only when that issue's row, that issue's active agent, that issue's derived state or that issue's panes change.
- **FR-6** `App` holds no subscription to `agentsById`, `issuesRaw` or `recentActivity`. A domain event for one agent or issue does not re-render `App`.
- **FR-7** `CommandDeck` holds no whole-slice subscription to `agentsById` or `issuesRaw`. It re-renders only when the set of agent ids, the issue→agent mapping, or an issue title or creation date changes.
- **FR-8** `IssueMissionControl` for issue A does not re-render when an agent of a different issue changes.
- **FR-9** A streamed delta for the open conversation does not re-render `ComposerFooter`.
- **FR-10** A conversation-list poll in which only conversation A changed re-renders only A's list item.
- **FR-11** `docs/DASHBOARD-ARCHITECTURE.md` documents the selector and identity rules, the render-count harness and the profiling commands.
- **FR-12** Offenders found but not fixed here are filed as one follow-up issue with their file references and after-profile numbers.

### Non-functional

- **NFR-1** No user-visible behavior changes: same labels, same counts, same dialogs, same menu actions.
- **NFR-2** Render-count tests are deterministic: no real timers for delays (fake-timers rule), no reading of source files (the `lint:source-introspection` gate rejects new source-reading tests), no `skipIf`/`.only` (the test-skip gate rejects them).
- **NFR-3** No file under `src/` grows past its `origin/main` line count when that count is over 1000 (`scripts/lint-file-size.sh`). This applies to `App.tsx` (1017), `CommandDeck/index.tsx` (1598) and `chat/ConversationPanel.tsx` (1525). New code goes into new files instead.
- **NFR-4** Per-row selectors do O(number of issues or agents) work per store `set()` at most. No per-row selector sorts.
- **NFR-5** The profiling tool never sends a mutating request to the dashboard server. Synthetic events and synthetic stream deltas are applied only inside the browser page.

## Decisions (made here, not left to the implementer)

1. **Scope of the outcome guarantees is the Command Deck route.** The Kanban page, Pipeline page, GodView, Live Agents and Home have their own whole-slice aggregators (census below). They are profiled only if they appear in the scenarios, and they go to the follow-up issue (FR-12).
2. **Aggregate chrome is exempt from "only the rows that show it".** `RunningAgentsPill`, `StoppedAgentsBanner`, `SystemHealthPill`, `DecisionsIndicator`, `NeedsYouIndicator`, the nav `Sidebar` and `ConversationDock` show cross-issue totals. They may re-render when an agent or issue entry changes. After FR-3 they no longer re-render on runtime events, because those no longer touch `agentsById`. The render-count tests assert on this explicit set of non-aggregate surfaces: `App`, `CommandDeck`, `FeatureItem` rows of other issues, `IssueMissionControl` of another issue, `ConversationList` items of other conversations, and `ComposerFooter`.
3. **Leave `App`'s 5 s `backend-health` poll alone.** `App.tsx:286` destructures `dataUpdatedAt`, so `App` re-renders the whole tree every 5 s. Many relative-time labels currently advance only because of that re-render: `SessionFeedSidebar.tsx:72` (`now = new Date()` default), `RunningAgentsPill.tsx:80` (`Date.now()` in render), `HomePage.tsx:127` and others. Removing it without moving those labels onto a shared clock would freeze them, which violates NFR-1. The shared-clock work goes to the follow-up issue. It is not a domain event, so it does not affect FR-6.
4. **Keep the schema field removal surgical.** Removing `bumpRuntimeSnapshotSequence` orphans `runtimeSnapshotSequence`. Remove the schema line at `types.ts:392` too, because nothing writes or reads it after the change. `Schema.optional` fields absent from a cached snapshot decode identically.
5. **Manual memoization is allowed where a render-count test proves the need.** [PAN-4561](https://github.com/eltmon/overdeck/issues/4561) will adopt the React Compiler and remove hand-written `useMemo`/`useCallback`. The render-count tests from this issue are the safety net for that removal, so they assert behavior (render counts), never implementation (that a `memo` exists). Prefer structural fixes (narrow selectors, identity-keeping reducers, reading the store at call time in handlers) over `memo`. Use `memo` only for `ComposerFooter` (item `streaming-composer-isolation`) and the new `ConversationListItem` (item `conversation-list-item-isolation`).
6. **Event handlers read the store at call time.** Where a component subscribes to a slice only to look something up inside a click handler, replace the subscription with `useDashboardStore.getState()` inside the handler.
7. **Profiling runs against the live dashboard, read-only.** The profiling build is served by `vite preview` on port **3010**. The server already trusts the `http://localhost:3010` origin (`src/dashboard/server/routes/origin-validation.ts`, `getTrustedOrigins`). Preview inherits `server.proxy`, which targets `VITE_PROXY_TARGET` or `http://127.0.0.1:3011`. That gives the real snapshot (hundreds of issues, running agents) and real live events. Deterministic load comes from synthetic events applied in-page through `window.useDashboardStore` (already exposed at `store.ts:695-697`) and synthetic stream deltas applied through a profile-only `window.__overdeckQueryClient`.
8. **Synthetic events never advance the sequence.** Each synthetic event carries `sequence: useDashboardStore.getState().sequence`, the current value. The reducers take `Math.max(state.sequence, event.sequence)`, so the store's sequence and the recovery coordinator's replay logic are unaffected.
9. **Docs target is `docs/DASHBOARD-ARCHITECTURE.md`, not the OKF bundle.** The OKF bundle lives in a separate repository (`../overdeck-knowledge`) outside this PR's review. The issue allows either.
10. **Size justification.** This plan touches about 37 files across 6 subsystems, over the 25-file guideline. Eight of those files are the new render-count harness and its seven tests, which the issue's AC #4 requires per fixed path; six more are existing tests that must keep passing. The issue's ACs #1–#3 are measured by one harness in one baseline/after profiling run, so splitting the streaming path into a sibling issue would duplicate the profiling runs and split one operator-written acceptance list across issues. Every item is still a separate commit with its own `Item:` trailer and its own test.

### WI-1 `render-counter` — the render-count test harness (FR-5…FR-10 foundation)

**What/why.** Every render-count test needs the same three things: count the re-renders of a named subtree, apply store events inside `act`, and reset the store singleton between tests. Build them once.

**Files.** New `src/dashboard/frontend/src/test-utils/renderCounter.tsx`.

**Steps.**
1. Export `createRenderCounter()`, which returns `{ Probe, count, counts, reset }`. `Probe({ id, children })` renders `<Profiler id={id} onRender={...}>`. `onRender(profilerId, phase)` increments `updates[profilerId]` only when `phase !== 'mount'`, so mounts are excluded. `count(id)` returns the number or 0. `counts()` returns a plain object. `reset()` clears.
2. Export `applyStoreEvents(events: DomainEvent[])`, which runs `act(() => { useDashboardStore.getState().applyEvents(events) })`.
3. Export `resetDashboardStore()`. At module load, capture `const initial = useDashboardStore.getState()`; `resetDashboardStore` calls `useDashboardStore.setState(initial, true)`. This keeps the action functions, because they are part of `initial`.
4. Export `seedDashboardStore(partial: Partial<DashboardState>)`, which calls `useDashboardStore.setState(partial)`.
5. Header comment: what the helper counts (React `Profiler` commits of the subtree, mounts excluded), and that tests assert counts, never `memo` usage (Decision 5).

```tsx
export function createRenderCounter() {
  const updates = new Map<string, number>()
  function Probe({ id, children }: { id: string; children: ReactNode }) {
    return (
      <Profiler id={id} onRender={(profilerId, phase) => {
        if (phase === 'mount') return
        updates.set(profilerId, (updates.get(profilerId) ?? 0) + 1)
      }}>{children}</Profiler>
    )
  }
  return { Probe, count: (id: string) => updates.get(id) ?? 0, counts: () => Object.fromEntries(updates), reset: () => updates.clear() }
}
```

**Tests.** Exercised by every later render-count test. A self-test is not required.
