**Issue:** [PAN-5623](https://github.com/eltmon/overdeck/issues/5623) (FR-2 of [PAN-5621](https://github.com/eltmon/overdeck/issues/5621))
**Depends on:** PAN-5621 (starvation detection). Its files exist only on `origin/feature/pan-5621` at planning time (verified 2026-11-23). See "Precondition".
**Related:** [PAN-5250](https://github.com/eltmon/overdeck/issues/5250) (idle frontend/dev stop; not started, so this issue owns the restart path), [PAN-3050](https://github.com/eltmon/overdeck/issues/3050) (idle-stack reaper coverage).

## Glossary

- **Workspace stack.** The Docker Compose containers of one issue workspace, all carrying the label `com.docker.compose.project=<compose project>`. The compose project comes only from `tryComposeProjectNameForWorkspace(workspacePath, issueId)` (`src/lib/workspace/stack-health.ts:180`).
- **Service.** A container's `com.docker.compose.service` label. Verified on this host 2026-11-23: `api`, `fe`, `frontend`, `server`, `dev`, `postgres`, `redis`.
- **Reclaimable service.** One of exactly `api`, `fe`, `frontend`, `server` (`RECLAIMABLE_STACK_SERVICES`). `dev` (the VS Code attach target), databases and caches are never reclaimable.
- **Starvation record / episode.** PAN-5621's `~/.overdeck/verification-workers/admission/starvation.json`, read with `readGateStarvationRecord()` (`src/lib/cloister/gate-starvation.ts`, PAN-5621). An episode is **open** when the record exists, has no `closing` field, a fresh `readQualityGateQueue()` snapshot has no `readError`, and `starvationEpisodeCloseReason(snapshot, record.openedAtMs)` returns `null`.
- **Head.** `snapshot.waiters[0]`, the oldest queued gate.
- **Head still blocked.** The head has a `footprintKey`, and `fitsAloneAboveHardReserve({ memAvailableBytes, memTotalBytes, hardReserveBytes, estimateBytes })` (`src/lib/cloister/quality-gate-memory.ts`, PAN-5621) returns `ok: false`.
- **Reclaim.** Overdeck stops the running reclaimable containers of one parked issue's stack and journals it.
- **Restore.** Overdeck runs `docker start` on exactly the containers the last reclaim named, then journals it.
- **Open reclaim.** In an issue's pipeline journal, the newest entry whose type starts with `stack.` is `stack.reclaimed`. `openStackReclaim(entries)` returns it; otherwise `null`.
- **Housekeeping entry.** A pipeline-journal entry whose type starts with `stack.`. It records what Overdeck did to an issue's containers, not a pipeline step, so every reader of the journal *tail* skips it.
- **Pipeline journal.** `<workspace>/.overdeck/pipeline.jsonl`, append-only (`src/lib/cloister/pipeline-journal.ts`).
- **Issue pane.** A live pane from the terminal backend inventory whose `issue` token equals the issue id (case-insensitive), or whose `agentId` satisfies `hasIssueToken(agentId, issueId)` (`stack-health.ts:301`), or whose `workspace` (cwd) equals the workspace path or lies inside it.
- **Turn state.** For an agent id: `unknown` when the runtime mirror has no snapshot (`getRuntimeSnapshot`, `src/lib/agent-runtime-mirror.ts:40`); `boundary` when `isSessionAtTurnBoundary(agentId)` is true (`src/lib/agents/liveness.ts:108`); otherwise `in-turn`. The mirror exists only in the primary dashboard process.
- **Parked position.** One of exactly two: (a) the issue has an unresolved blocker declaration, `pendingDeclarations(readPipelineJournal(ws)).length > 0` (`src/lib/cloister/blocker-wake.ts:73`); or (b) the merge gate says the PR is ready to merge, `(await evaluateIssueMergeGate(issueId)).ready === true` (`src/lib/cloister/merge-gate.ts:136`).
- **Primary dashboard.** The dashboard process with `!isPeerDashboard` in `src/dashboard/server/main.ts`.
- **Stack lock.** The per-workspace cross-process lock file `<workspace>/.overdeck/stack-reclaim.lock`, taken with `withFileLock` (`src/lib/vault/file-lock.ts:63`) with `staleMs: 300_000` and `retryMs: 250`. Every reclaim (re-check, journal write, stops) and every restore (journal read, listing, starts, journal write) runs inside it, so a restore can never interleave with a stop sequence.

## Problem

On 2026-11-23 the gate admission queue ran no gate for at least 7 minutes. MemAvailable stayed between 8.5 and 10.4 GB, below the hard reserve (8 GB) plus the head's 2.86 GB footprint, so the PAN-5285 alone-admission could never fire. The MIN-1144 and MIN-1146 MYN stacks (an `api` and an `fe` container each) held memory while their agents only waited. The Flywheel stopped those four containers by hand; MemAvailable rose to 11.5 GB and the head ran. PAN-5621 now detects and reports such a stall. Nothing frees memory automatically, and nothing would start a stopped stack again when its issue needs it.

## Requirements

### Functional

- **FR-1 Trigger.** The primary dashboard checks every 30 s. It reclaims only while the starvation episode is open and the head is still blocked. A missing record, a `closing` record, an unreadable queue, a close reason, a head without `footprintKey`, unreadable memory, or a head that fits alone each mean: do nothing this poll.
- **FR-2 Candidate rule (deny by default, closed list).** An issue is a candidate only when every one of these holds:
  1. Its workspace row is not `kind: 'main'`, has an `issueId`, and its path exists.
  2. The issue resolves to a registered project (`resolveProjectFromIssueSync(issueId) !== null`).
  3. `tryComposeProjectNameForWorkspace(path, issueId)` returns a name, and at least one **running** container has that exact compose project label and a reclaimable service.
  4. No gate-queue owner or waiter belongs to the issue: no entry with `issueId` equal (case-insensitive), and no entry whose `workspacePath` equals the workspace path or lies inside it.
  5. No verification worker is active (`isVerificationWorkerActive(issueId)` is false) and no verification dispatch is owed (`readVerificationDispatchOwed(issueId) === null`), both in `src/lib/cloister/verification-worker-supervisor.ts`.
  6. The issue was not already reclaimed in this episode (no `stack.reclaimed` entry with `data.episodeSince === record.since`).
  7. Issue panes with role `review` are ignored (review reads only the committed diff and never needs the stack; the spawn gate exempts it the same way, PAN-4690). Every other issue pane has role `work`, has an `agentId`, has backend state other than `working`, and has turn state `boundary`. Zero such panes satisfies this rule. Verified 2026-11-23: MIN-1144 and MIN-1146 each have a live `work` pane and a finished, still-alive `review` pane, and both are merge-gate `ready` (`evaluateIssueMergeGate` returned `ready: true`, forge `gitlab`), so this rule admits the incident's issues.
  8. The issue is in a parked position (glossary). The blocker check runs first; the merge gate runs last and only for the top 3 candidates by memory.
  An unreadable docker listing, pane inventory or container memory read skips the whole poll. Because the merge gate can take seconds, FR-3's re-check runs from fresh reads inside the stack lock immediately before the journal append; any failure there skips the stop this poll.
- **FR-3 Stop.** At most one issue per poll: the candidate with the largest summed container memory (ties: issue id ascending). Inside the stack lock, Overdeck re-checks the episode, the head, rules 4, 5 and 7, and each target container's id, running state, compose project and service from fresh reads; appends a `stack.reclaimed` entry naming the exact containers and their ids; reads the journal back and stops nothing unless that exact entry is the newest `stack.*` entry; then runs `docker stop <id>` on each verified id; then emits one activity entry. It never stops a container outside the issue's compose project, never a non-reclaimable service.
- **FR-4 Journal.** Two new entry types, `stack.reclaimed` and `stack.restored`, with the data shapes in D4. `lastPipelineEntry(ws)` without a prefix, and every reader of the journal tail (`stale-approval-rereview.ts`, `deacon-lite.ts` `failedDispatchRetryReason`, `derive-status.ts` journal tail), skip housekeeping entries. `JOURNAL_ACTIVITY_LABELS` gains both types.
- **FR-5 Restore.** An open reclaim is restored (exactly its journaled containers are started) when the issue next needs its stack:
  - **turn:** any non-`review` issue pane has backend state `working` or turn state `in-turn` (primary dashboard, checked every 5 s);
  - **spawn:** the spawn gate runs for a role that checks stack health (before its health check), and the dashboard spawn route runs (before its first health read, so its disk-floor hold applies only when a rebuild is still needed);
  - **verification:** a verification run starts (right after `verification.started` is journaled).
  A container that no longer exists counts as resolved, and so does one already running. A journaled name whose container is not in the issue's current compose project, or whose service is not reclaimable, is refused (never started) and also counts as resolved. A real `docker start` failure writes no `stack.restored`; the turn trigger retries no sooner than 60 s later.
- **FR-6 Reclaimed reads as stopped on purpose, on display surfaces only.** `getWorkspaceStackHealth(..., { reclaimAware: true })` ignores exited containers named by the open reclaim and reports them in `health.reclaimed`. `pan status` and the two workspace-data route reads opt in. Every gating read (spawn gate, spawn route, handoff source check) keeps the strict default.
- **FR-7 Reclaims survive a dashboard restart.** The restore poll rebuilds its set of open reclaims from the journals of all workspaces on its first tick after start.
- **FR-8 Documentation and changelog.** `docs/PIPELINE-GATES.md` and `changelog.d/pan-5623.md` (WI-15).

### Non-functional

- **NFR-1 Fake timers.** Every poll, interval and retry clock test uses `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()`. No test waits on a real 5 s, 30 s or 60 s delay (repo rule `fake-timers-for-retry-tests`).
- **NFR-2 No synchronous child processes** in dashboard-reachable code: no `execSync`, no `*Sync` tmux helper (repo rules `no-execsync-server`, `prefer-async`). Docker calls use promisified `execFile` with an argument array, never a shell string.
- **NFR-3 Never throws out of a timer, never blocks a spawn or verification on failure.** The service catches and logs every poll error. `restoreReclaimedStack` never throws; on failure it returns `{ kind: 'failed' }` and the caller continues on its existing path.
- **NFR-4 Primary dashboard only.** The service starts only when `!isPeerDashboard`. The runtime mirror it reads exists only there.
- **NFR-5 File-size ratchet** (`scripts/lint-file-size.sh`, ceiling 1000 lines for files not on the allowlist). `src/dashboard/server/main.ts` is 993 lines on main and PAN-5621 adds 3; this issue adds exactly 1 (WI-14), so it must stay ≤ 1000. `src/lib/cloister/verification-runner.ts` is 911 lines. `src/lib/cloister/deacon-lite.ts` is 758. `src/dashboard/server/routes/agents/spawn-issue.ts` is 950 and gains 2 lines. Never raise an allowlist cap.
- **NFR-6 Container names are validated** against `^[A-Za-z0-9][A-Za-z0-9_.-]*$` before they reach `docker`. A journal entry is a workspace file and must not inject arguments.
- **NFR-7 Import hygiene.** New `src/lib` modules import nothing from `src/dashboard/`. `stack-health.ts` may import `pipeline-journal.ts` (it imports only `pipeline-notifier.ts`); `stack-restore.ts` may import `stack-health.ts`; `stack-health.ts` must never import `stack-restore.ts` or `stack-reclaim*.ts`. `npm run lint:circular` passes.

## Design decisions

- **D1. Where it runs.** A new primary-dashboard service, `src/dashboard/server/services/stack-reclaim-service.ts`, with two timers: the reclaim poll (`STACK_RECLAIM_POLL_MS = 30_000`) and the restore poll (`STACK_RESTORE_POLL_MS = 5_000`). Each timer has its own in-flight guard and `unref()`. It is not part of the deacon child's hygiene scheduler, because the runtime mirror exists only in the main process. The restore *door* (`restoreReclaimedStack`) is plain `src/lib` code, because the spawn gate runs in CLI processes and verification runs in a detached worker process.
- **D2. Ownership is the compose label.** A container belongs to an issue only when its `com.docker.compose.project` label equals `tryComposeProjectNameForWorkspace(path, issueId)` for a non-main workspace of a registered project with an existing directory. `open-design` and `overdeck-traefik` (projects `open-design`, `traefik`) can never match. Name patterns are never used for the stop side.
- **D3. Docker reads.** A new module `src/lib/workspace/stack-reclaim-docker.ts`. Listing uses
  `docker ps [-a] --format '{{.ID}}\t{{.Names}}\t{{.State}}\t{{.Label "com.docker.compose.project"}}\t{{.Label "com.docker.compose.service"}}'`
  (verified on this host 2026-11-23). Rows with an empty project label are dropped. Memory uses `docker stats --no-stream --format '{{.Name}}\t{{.MemUsage}}' <names...>`, parsed with `parseMemUsage` (exported from `docker-stats.ts`). The service does not read `DockerStatsCollector`, which starts only when some route first asks for it.
- **D4. Journal entries.**
  - `stack.reclaimed`, source `stack-reclaim`, data: `{ containers: string[], containerIds: string[], services: string[], composeProject: string, memoryBytes: number, reason: 'gate-starvation', episodeSince: string, head: { gateName: string, issueId?: string } }`. `containers[i]` is the name of the container whose verified id `containerIds[i]` is passed to `docker stop`.
  - `stack.restored`, source `stack-restore:<trigger>`, data: `{ containers: string[], started: string[], alreadyRunning: string[], missing: string[], refused: string[], trigger: 'turn' | 'spawn' | 'verification', reclaimedAt: string }`.
- **D5. Journal before stop, confirmed, under the lock.** The reclaim appends `stack.reclaimed` *before* it runs `docker stop`. A crash between the two leaves a journal that names running containers; the next restore finds them running and records them as `alreadyRunning`. The reverse order could leave stopped containers with no record, which nothing would ever restart. `appendPipelineEntry` swallows write errors, so the reclaim reads the journal back with `openStackReclaim(readPipelineJournal(ws))` and stops nothing unless it returns an entry with the same `at` and the same `containers`; otherwise the poll ends idle `journal-unwritable`. The whole sequence runs inside the stack lock, so a spawn or verification restore waits for the stops to finish and then sees them exited. A failed `docker stop` is logged and named in the activity entry; the journal is not rewritten (append-only).
- **D6. Housekeeping entries never become the tail.** `isHousekeepingEntry(entry)` is `entry.type.startsWith('stack.')`. `lastPipelineEntry(ws)` without a prefix skips them; with a prefix it behaves as before, so `lastPipelineEntry(ws, 'stack.')` still finds them. `lastPipelineStep(entries)` returns the last non-housekeeping entry for readers that already hold the array. Without this, a reclaim would hide a `blocked.declared` tail from the board's blocker text (`board.ts:390`) and from the recoveries that act on the tail.
- **D7. Position rule.** Parked means an unresolved blocker declaration, or the merge gate's own `ready` answer. "Approved" alone is not enough: `evaluateIssueMergeGate` also requires green checks, mergeability, the CI test job and the UAT policy. A test or UAT role that still runs after approval has a live pane with role `test`/`uat`, which FR-2 rule 7 rejects; a test role that spawns later passes the spawn gate, which restores first.
- **D8. Anti-flap.** An issue is reclaimed at most once per episode (FR-2 rule 6). A woken agent's stack is restored and stays up for the rest of that episode.
- **D9. Restore door.** `restoreReclaimedStack({ issueId, workspacePath, trigger }, deps?)` in `src/lib/workspace/stack-restore.ts`:
  1. Resolve the workspace path: the given one, else `defaultWorkspacePath(issueId, getProjectSync(resolveProjectFromIssueSync(issueId)?.projectKey))`. No path, or a path that does not exist, returns `{ kind: 'none' }`.
  2. A cheap unlocked `openStackReclaim(readPipelineJournal(path))`; `null` returns `{ kind: 'none' }` without taking the lock (the common case costs one file read).
  3. Take the stack lock (`timeoutMs: 300_000`; a lock timeout returns `{ kind: 'failed' }`). Inside it, re-read `openStackReclaim`; `null` returns `{ kind: 'none' }`.
  4. Recompute `composeProject = tryComposeProjectNameForWorkspace(path, issueId)`. List containers with `-a`; a listing failure returns `{ kind: 'failed' }`.
  5. Classify each journaled name: `refused` when it fails the NFR-6 pattern, when `composeProject` is `null`, or when its listed container's project label is not `composeProject` or its service is not in `RECLAIMABLE_STACK_SERVICES`; `missing` when absent; `alreadyRunning` when state `running`; else start it with `docker start <name>`.
  6. Any start failure returns `{ kind: 'failed', failed, error }` and writes nothing.
  7. Otherwise append `stack.restored` (D4), emit an `info` activity entry when `started` is non-empty, log a warning naming any `refused` names, and return `{ kind: 'restored', started, alreadyRunning, missing, refused }`.
  It never throws (NFR-3). `restoreReclaimedStackForSpawn(issueId, workspacePath)` in the same module wraps it with trigger `spawn`: when `started` is non-empty it takes a fresh `collectDockerContainerLifecycleSnapshot()`, records it with `recordDockerContainerLifecycleSnapshot()`, and returns that listing; otherwise it returns `undefined`.
- **D10. Spawn paths.** Two call sites use `restoreReclaimedStackForSpawn` and pass its listing as `containers` to their next `getWorkspaceStackHealth` read:
  - the spawn gate, after `if (role === 'review') return;` and before its health read;
  - the dashboard spawn route (`spawn-issue.ts:507-508`), before its first health read, so a reclaimed stack is started before the route's disk-floor hold (which runs only while health is still unhealthy) can refuse the spawn.
  The cached snapshot has no TTL, so without the fresh, recorded listing both would read the stale exited state and fall through to the disk hold or to `up -d --build`; recording it also refreshes the cache the route re-reads at `spawn-issue.ts:524`.
- **D11. Verification.** In `runVerificationForIssueInProcess`, right after the `verification.started` append, `await restoreReclaimedStack({ issueId, workspacePath, trigger: 'verification' })`. The result is ignored: a failure falls through to the existing `infraUnavailable` path.
- **D12. Health leniency is opt-in.** `WorkspaceStackHealthOptions.reclaimAware?: boolean` (default `false`). `evaluateWorkspaceStackHealth` gains `expectedStopped?: ReadonlySet<string>`: an exited, non-one-shot container whose name is in the set adds no reason and is listed in `health.reclaimed`. `getWorkspaceStackHealth` builds the set from `openStackReclaim(readPipelineJournal(workspacePath))` only when `reclaimAware` is true. Opt-in sites: `status.ts:195`, `workspace-data.ts:438` and `:604`. Gating sites (`workspace-stack-spawn-gate.ts`, `spawn-issue.ts`, `src/lib/conversations/summary-fork.ts`) never pass `reclaimAware`; the spawn gate's only health change is the fresh `containers` listing of D10.
- **D13. `pan status` line.** When an agent's `stackHealth.reclaimed` is non-empty, `pan status` prints under that agent `  Stack:    stopped to free memory: <names joined by ", ">; starts again when the issue needs it`, with the phrase in yellow. A reclaimed stack with no agent reads healthy, so it no longer appears under "Broken Workspace Stacks"; that is intended.
- **D14. Activity entries.** Reclaim: `emitActivityEntry({ source: 'cloister', level: 'info', issueId, message: 'stack-reclaimed: <ISSUE>', details: 'Stopped <names> (<X.X> GiB) to free memory for the starved gate queue (<gateName>[ for <head issue>] is waiting). They start again when <ISSUE> next needs them; to start them by hand: docker start <names>.' })`. Restore with started containers: `{ source: 'cloister', level: 'info', issueId, message: 'stack-restored: <ISSUE>', details: 'Started <names> (<trigger>).' }`.
- **D15. Restore poll index.** The service keeps `Map<issueIdUpper, workspacePath>` of open reclaims. The first restore tick after start seeds it from `listWorkspaces()` (every non-archived workspace with an existing path whose journal has an open reclaim). A reclaim adds its issue. Each tick, for each indexed issue: drop it when the path is gone or `openStackReclaim` is now `null` (another process restored it); skip it while its retry time is in the future; restore with trigger `turn` when a non-`review` issue pane has backend state `working` or turn state `in-turn`; on `failed`, set the retry time to now + `STACK_RESTORE_RETRY_MS = 60_000`. The tick reads the pane inventory only when the index is non-empty; an unreadable inventory skips the tick.

## Critique response

### A failed journal write can strand stopped containers

Accepted. D5 and WI-12 step 9 now read the journal back after `appendPipelineEntry` and stop nothing unless `openStackReclaim` returns the entry just written (same `at`, same `containers`); otherwise the poll ends idle `journal-unwritable`. WI-12 tests the write-failure path.

### Restore accepts foreign containers named in the journal

Accepted. D9 step 4–5 recompute the compose project with `tryComposeProjectNameForWorkspace` and start a journaled name only when its listed container carries that project label and a service in `RECLAIMABLE_STACK_SERVICES`; anything else is `refused`, never started, and logged. WI-5 tests a journaled `postgres` container and a container from another project.

### Restore can close the journal before stop finishes

Accepted. A per-workspace cross-process stack lock (`withFileLock`, `<workspace>/.overdeck/stack-reclaim.lock`, `staleMs: 300_000`, which exceeds the bounded stop sequence of at most four 60 s stops) now covers the whole reclaim (re-check, journal write, read-back, stops) and the whole restore (journal re-read, listing, starts, journal write). A restore that arrives during a stop sequence waits, then sees the containers exited and starts them. WI-5 tests that every restore step runs inside the lock callback; WI-12 tests the lock-busy path.

### Dashboard spawn can reject before reaching restore

Accepted. D10 and WI-6 now also call `restoreReclaimedStackForSpawn` in `spawn-issue.ts` before the route's first health read, so the disk-floor hold (which sits inside `if (!stackHealth.healthy && !allowHost)`) runs only when the stack is still unhealthy after the restore. The route has no test harness, so the ordering is checked in the diff; the helper's fresh, recorded listing is unit-tested in WI-5.

### The pre-stop check omits starvation and container ownership

Accepted. WI-12 step 8 re-checks, inside the stack lock and from fresh reads, the open episode, the close reason, the blocked head (memory, reserve and estimate re-read), rules 4, 5 and 7, and every target container's id, running state, compose project and service. Step 9 stops by verified container id, so a name reused by another container cannot redirect the stop. WI-12 tests an admitted queue and a changed container id during the merge-gate wait.

### Unresolved after two critic rounds

- Restore can miss an in-progress reclaim
- Top-three search can permanently skip a parked issue
- The lock directory is not guaranteed to exist
- A failed stop consumes the only attempt
