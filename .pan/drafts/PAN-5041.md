# PAN-5041: Phone app light mode (System / Light / Dark appearance setting)

**Issue:** [PAN-5041](https://github.com/eltmon/overdeck/issues/5041)
**Related:** PAN-4837 (the phone app), PAN-4835 H-4 (admin routes the phone cannot call), PAN-4839 (Live Activity), PAN-4842 (phone docs page), PAN-4841 (TestFlight testing).
**Planned at:** `5225c28ec27` on `feature/pan-5041`, 2026-11-04.

## Glossary

- **Phone app / the app:** `apps/mobile`, the Capacitor 8 iOS and Android app (`ai.overdeck.app`). A Vite web build that runs inside a native WebView.
- **Shell screens:** the app's own React screens in `apps/mobile/src/shell/` (sign-in, machine list, pair, removed, Settings).
- **Machine screens:** the dashboard frontend's `MobileApp` (`src/dashboard/frontend/src/components/mobile/MobileApp.tsx`) that `apps/mobile/src/shell/MachineView.tsx` renders for the current machine.
- **Appearance:** the new phone-only setting. One of `system`, `light`, `dark`. Default `system`.
- **Resolved theme:** `light` or `dark`. For `light`/`dark` it is the appearance itself; for `system` it is what `matchMedia('(prefers-color-scheme: dark)')` reports.
- **`.dark` class:** the class on `<html>` that switches the frontend's CSS tokens. `src/dashboard/frontend/tailwind.config.js` line 3: `darkMode: 'class'`. `src/dashboard/frontend/src/index.css` defines light tokens on `:root` (line 159, `--background: #ffffff`) and dark tokens on `.dark` (line 250, `--background: #080b10`).
- **`useTheme`:** the frontend's zustand theme store, `src/dashboard/frontend/src/hooks/useTheme.ts`. Its state `resolvedTheme` drives code highlighting (`ChatMarkdown.tsx:185`, `MarkdownFileLink.tsx:221`), `ConversationPanel.tsx:317`, and `useColorTheme`'s UI token re-apply (`useColorTheme.ts:188`, `useTheme.subscribe`).
- **Native shell flag:** `globalThis.__OVERDECK_NATIVE__`, set first thing in `apps/mobile/src/main.tsx`; read by `isNativeShell()` in `src/dashboard/frontend/src/lib/nativeShell.ts` (a leaf module).
- **SystemBars:** Capacitor 8's built-in core plugin (`SystemBars`, `SystemBarsStyle` exported from `@capacitor/core`). `setStyle({ style })` sets status-bar content color on iOS (`bridge.statusBarStyle`) and Android (`WindowInsetsControllerCompat.setAppearanceLightStatusBars`). `SystemBarsStyle.Dark` = light content on a dark background; `SystemBarsStyle.Light` = dark content on a light background.
- **`OverdeckAppearance`:** the new app-local native plugin this issue adds (iOS Swift + Android Java). It persists the appearance natively and applies it to native chrome.
- **Mac rig:** the Mac build machine for iOS Simulator runs (see `apps/mobile/README.md`, "Run in the iOS Simulator").

## Problem

The app is dark only. Three facts make that so today:

1. `apps/mobile/src/shell/MachineView.tsx` lines 1-6 (grep: `The frontend's boot-time settings and theme reconciles and telemetry are not run`) deliberately skips the frontend's boot reconciles, because they read admin routes the phone token cannot call (PAN-4835 H-4).
2. `useTheme.ts` evaluates when `ShellApp` is dynamically imported (ShellApp → MachineView → MobileApp → MobileConversations → ConversationPanel → ChatMarkdown → useTheme). At module load (lines 42-49) it reads `localStorage['overdeck.ui.theme']`, defaults to `dark`, toggles `.dark` on `<html>`, and, when the key exists, `PUT /api/settings/ui-theme` — an admin route. In the phone the key never exists, so the app is always dark and never makes that request.
3. The native chrome has no notion of the setting. iOS: `CAPBridgeViewController` sets the WKWebView background to `UIColor.systemBackground` (Capacitor 8.6 `CAPBridgeViewController.swift:313`) and the status bar style to `.default` (line 14); both follow the phone's system appearance. Android: `AppTheme.NoActionBar` extends `Theme.AppCompat.DayNight.NoActionBar` (`android/app/src/main/res/values/styles.xml`), the WebView background is unset (Capacitor `Bridge.java:608-615` only sets it when `backgroundColor` is configured).

The operator wants to use the phone app in light mode (found while testing TestFlight 1.0 (3), PAN-4841).

## Proposal

The phone owns a three-way **appearance** setting in its own `localStorage` key `overdeck.appearance`. It never writes a machine or admin route.

- **Early paint:** an inline classic script in `apps/mobile/index.html` `<head>` resolves the appearance, toggles `.dark` on `<html>`, and writes the resolved theme to the frontend's own key `overdeck.ui.theme` **before** any CSS paints or module runs. `useTheme`'s module-load code then reads the right value and does not revert it.
- **Frontend seam (one file):** `useTheme.ts` gains a `setTheme(theme)` action and skips both server syncs when `isNativeShell()` is true. Its `Theme` type stays `'light' | 'dark'`; the desktop dashboard behaves exactly as before.
- **Live controller:** `apps/mobile/src/shell/appearance.ts` holds the store (read/write/subscribe, same pattern as `notificationPrefs.ts`), the resolver, and `installAppearance(deps)`. The controller applies the resolved theme through `useTheme.getState().setTheme`, sets `SystemBars` style, mirrors the appearance to the native plugin, and listens to `matchMedia` `change` events so **System** follows the phone without a restart.
- **Settings row:** an **Appearance** section in `SettingsScreen.tsx` with three choices.
- **Native chrome:** `OverdeckAppearance` persists the appearance (iOS `UserDefaults`, Android `SharedPreferences`) and applies it. At cold launch, iOS `SceneDelegate` sets `window.overrideUserInterfaceStyle` before the WebView is created, so `systemBackground` and the `.default` status bar resolve to the chosen appearance. Android `MainActivity` calls `AppCompatDelegate.setDefaultNightMode` before `super.onCreate` and sets the WebView background to the token color.

## Requirements

### Functional

- **FR-1** Settings shows an **Appearance** section with three choices — **System**, **Light**, **Dark** — and marks the current one. The default is **System**.
- **FR-2** The appearance is stored on the phone only, in `localStorage['overdeck.appearance']`. Choosing one sends no HTTP request through the channel shims. The value survives an app restart and the page reload that a machine switch performs (C-7).
- **FR-3** With **System**, the app follows the phone's light/dark appearance and changes live, without a restart or reload.
- **FR-4** The resolved theme applies at once to every shell screen and every machine screen through the frontend's existing `.dark` class and `useTheme.resolvedTheme` (no second palette). Code highlighting in conversations follows it.
- **FR-5** The status bar content color follows the resolved theme on iOS and Android.
- **FR-6** The native background behind the WebView follows the appearance from the app's first window (iOS window override, Android night mode plus WebView background), so a Light appearance shows no dark frame between the launch screen and the first web paint, and vice versa.
- **FR-7** The Live Activity and notifications are unchanged; iOS keeps drawing them in the phone's system appearance.
- **FR-8** The phone never sends `PUT /api/settings/ui-theme` (or any other theme route) to a machine.

### Non-functional

- **NFR-1** Storage failures (blocked or full `localStorage`) read as **System** and never throw; native persistence failures are logged and ignored.
- **NFR-2** The desktop dashboard's theme behavior is unchanged: same storage key, same default (dark), same server sync, same toggle.
- **NFR-3** The appearance code adds no new npm dependency (SystemBars is in `@capacitor/core` 8).
- **NFR-4** Tests follow repo rules: no `it.skip`/`skipIf`/`.only`; no fake-timer-sensitive real delays (none are needed here); frontend tests stay in the frontend Vitest project, phone tests in `apps/mobile/vitest.config.ts`.

## Decisions

- **D-1 Storage key and values.** `localStorage['overdeck.appearance']` holds exactly `system`, `light` or `dark`. Anything else (missing, invalid, storage error) reads as `system`.
- **D-2 The phone pre-seeds the frontend key.** The index.html boot script and every controller apply write the *resolved* theme into `localStorage['overdeck.ui.theme']`. This is the phone WebView's own storage; it never reaches a machine because D-3 removes the server sync in the native shell.
- **D-3 `useTheme` native guard.** In `useTheme.ts`, both the module-load sync (line 47) and every sync from an action are skipped when `isNativeShell()` is true. Import `isNativeShell` from `../lib/nativeShell` (a leaf; no import cycle).
- **D-4 `setTheme` is additive.** `setTheme(theme: 'light' | 'dark')` applies the class with transitions suppressed, writes `overdeck.ui.theme`, syncs to the server only outside the native shell, and sets `{ theme, resolvedTheme }`. `toggleTheme` keeps its behavior. Do not widen `Theme` to include `system`.
- **D-5 Status bar from JS.** The controller calls `SystemBars.setStyle({ style: resolved === 'dark' ? SystemBarsStyle.Dark : SystemBarsStyle.Light })`. Never pass `SystemBarsStyle.Default`: it reads the OS night mode and ignores a Light/Dark choice.
- **D-6 Native background colors.** The phone renders no `data-theme` attribute (`useDesignLanguage` is not in the phone's import graph — its only importers are the frontend `main.tsx` and Settings components), so the page background is `:root` `#ffffff` (light) or `.dark` `#080b10` (dark). Android sets the WebView background to exactly those. iOS uses `systemBackground` under the window override (white / black), which never shows the opposite brightness.
- **D-7 Native persistence key.** iOS `UserDefaults.standard` key `overdeck.appearance`; Android `SharedPreferences` file `overdeck_appearance`, key `appearance`. Values as D-1. Missing or invalid ⇒ system.
- **D-8 localStorage is the source of truth.** The native copy exists only so native code can apply the appearance before the WebView runs. The controller pushes the stored appearance to native on every install (each page load) and on every change, so the native copy self-heals.
- **D-9 Sign-out resets the appearance to System.** `signOut` calls `localStorage.clear()` (`ShellApp.tsx`, `clearStorage: () => localStorage.clear()`), which removes the key. After the sign-out reload, the controller pushes `system` to native. No change to `signOut.ts`.
- **D-10 iOS launch screen stays OS-drawn.** `LaunchScreen.storyboard` uses `systemBackgroundColor` and iOS draws it before app code runs. Only the static `UIUserInterfaceStyle` plist key could force it, which would break System. FR-6 applies from the app's first window onward.
- **D-11 One controller per page.** `ShellApp` installs the controller once in a mount effect and uninstalls on unmount. `ShellApp` is the root for both shell and machine screens, so one install covers both.
- **D-12 Selection UI.** Three `role="radio"` buttons inside a `role="radiogroup"` labeled "Appearance", each `min-h-11`, styled like the existing rows (`border-b border-border text-sm text-foreground`), the selected one marked with `aria-checked="true"` and a trailing "✓" in `text-muted-foreground`.
- **D-13 matchMedia reflects the native override.** On iOS the WKWebView's `prefers-color-scheme` follows `overrideUserInterfaceStyle`; on Android it follows the AppCompat night mode. So the controller resolves again on every `change` event, and switching from Light/Dark to System corrects itself when the override clears and the media query fires.

```swift
/// The `OverdeckAppearance` plugin on iOS (PAN-5041): stores the phone app's appearance and applies it to the
/// window, so `systemBackground` behind the WebView and the default status bar follow it.
@objc(OverdeckAppearancePlugin)
public class OverdeckAppearancePlugin: CAPPlugin, CAPBridgedPlugin {
    public let identifier = "OverdeckAppearancePlugin"
    public let jsName = "OverdeckAppearance"
    public let pluginMethods: [CAPPluginMethod] = [CAPPluginMethod(name: "set", returnType: CAPPluginReturnPromise)]

    static let defaultsKey = "overdeck.appearance"

    /// `system` (or anything unknown) ⇒ `.unspecified`.
    static func style(for appearance: String?) -> UIUserInterfaceStyle {
        switch appearance { case "light": return .light; case "dark": return .dark; default: return .unspecified }

        DispatchQueue.main.async {
            self.bridge?.viewController?.view.window?.overrideUserInterfaceStyle = Self.style(for: appearance)
            self.bridge?.viewController?.setNeedsStatusBarAppearanceUpdate()
            call.resolve()
        }
    }
}
```

`OverdeckAppearancePlugin.java`:

```java
/** The `OverdeckAppearance` plugin on Android (PAN-5041): stores the phone app's appearance and applies it. */
@CapacitorPlugin(name = "OverdeckAppearance")
public class OverdeckAppearancePlugin extends Plugin {
    static final String PREFS = "overdeck_appearance";
    static final String KEY = "appearance";
    static final int LIGHT_BACKGROUND = 0xFFFFFFFF; // :root --background
    static final int DARK_BACKGROUND = 0xFF080B10;  // .dark --background

    static int nightMode(String appearance) {
        if ("light".equals(appearance)) return AppCompatDelegate.MODE_NIGHT_NO;
        if ("dark".equals(appearance)) return AppCompatDelegate.MODE_NIGHT_YES;
        return AppCompatDelegate.MODE_NIGHT_FOLLOW_SYSTEM;
    }

    static String stored(Context context) {
        return context.getSharedPreferences(PREFS, Context.MODE_PRIVATE).getString(KEY, "system");
    }

    /** Sets the WebView background to the page's background color for the current night mode. */
    static void applyBackground(Activity activity, WebView webView) {
        int uiMode = activity.getResources().getConfiguration().uiMode & Configuration.UI_MODE_NIGHT_MASK;
        webView.setBackgroundColor(uiMode == Configuration.UI_MODE_NIGHT_YES ? DARK_BACKGROUND : LIGHT_BACKGROUND);
    }

    @PluginMethod
    public void set(PluginCall call) {
        String appearance = call.getString("appearance", "system");
        getContext().getSharedPreferences(PREFS, Context.MODE_PRIVATE).edit().putString(KEY, appearance).apply();
        getActivity().runOnUiThread(() -> {
            AppCompatDelegate.setDefaultNightMode(nightMode(appearance));
            applyBackground(getActivity(), getBridge().getWebView());
            call.resolve();
        });
    }
}
```

```java
    if (getBridge() != null) OverdeckAppearancePlugin.applyBackground(this, getBridge().getWebView());
}
```

## Planning Q&A (auto mode)

Planning ran with `--auto`; no questions were asked. Defaults chosen:

- **Where to store the setting?** Options: phone `localStorage`; native storage only; the machine's config. Chosen: `localStorage` as the source of truth plus a native mirror for launch (D-1, D-8). The issue requires phone-only storage, and only `localStorage` is readable synchronously before first paint.
- **How to drive the frontend's theme?** Options: pre-seed `overdeck.ui.theme` plus a `setTheme` action; widen `Theme` with `system`; a phone-only CSS override. Chosen: pre-seed plus `setTheme` with a native-shell server-sync guard (D-2–D-4). It is the smallest change that keeps the desktop identical and blocks the admin-route PUT.
- **Status bar?** Options: built-in `SystemBars`; add `@capacitor/status-bar`; native only. Chosen: built-in `SystemBars` with explicit styles (D-5, NFR-3).
- **Sign-out?** Options: reset to System; preserve. Chosen: reset (D-9), because sign-out already clears all of the phone's local storage and the native copy self-heals.
- **iOS launch screen?** Chosen: leave it OS-drawn (D-10); forcing it needs a static plist key that breaks System.
