# PAN-4739: Fly machine — conversation-lifecycle marks a live conversation ended on every tick

**Issue:** [PAN-4739](https://github.com/eltmon/overdeck/issues/4739) · found in the PAN-4652 live check (Run 1, Fly machine `862102ae249718`, 2026-11-01; recorded in `docs/fly-provider.md` "Live verification (PAN-4652)").

## Glossary

- **Lifecycle patrol** — `pollConversations()` in `src/dashboard/server/services/conversation-lifecycle.ts`. Runs every 10 s (`POLL_INTERVAL_MS = 10_000`) inside the dashboard server (`pan serve` on a Fly machine). It marks a conversation row `ended` when its terminal session is gone ("session gone") or the session is left with no harness process ("keep-alive corpse"), and resurrects an `ended` row whose session and harness are alive.
- **Runtime census** — `src/lib/runtime-census.ts`. One cached snapshot (TTL 3 s) of every tmux pane (`tmux list-panes -a -F '#{session_name}\t#{pane_pid}\t#{pane_dead}\t#{pane_dead_status}'`, via `listAllPaneRecords` in `src/lib/tmux.ts`) plus the process table (`ps -eo pid=,ppid=,pcpu=,rss=,comm=,args=`). The patrol's `tmuxView` reads `census.sessionNames` for "session gone" and `runtimeCensusHasHarnessProcess` for "harness gone".
- **Conversation-liveness door** — `src/lib/overdeck/conversation-liveness.ts` (PAN-3921 FR-7). `conversationHarnessAlive(name)` on a tmux host is `isHarnessProcessAlive(name)` (`tmux list-panes -t =<name> -F '#{pane_pid}'` plus a `ps -eo pid=,ppid=,comm=` tree walk) OR a Herdr `alive`. `listLiveConversationSessions()` on a tmux host is `tmux list-sessions -F '#{session_name}'` plus Herdr `conv-*` agents.
- **List-route repair** — `enrichConversationList()` in `src/lib/overdeck/conversation-list.ts` (lines 214–226). For an `ended` row whose session `list-sessions` names and whose harness `conversationHarnessAlive` reports alive, it calls `markConversationRunning(row.name)`.
- **Shared-conversations sync** — home's viewer sync calls the VM's `GET /api/machines/conversations` (`src/dashboard/server/routes/machines-peer.ts`), which `buildSharedConversations` (`src/lib/anywhere/shared-conversations.ts`) answers from `getEnrichedConversationList` → `enrichConversationList`. So every home sync runs the list-route repair on the VM.
- **Idle sweep** — `sweepFlyMachines` in `src/lib/remote/fly-machine-loops.ts` (home side). A machine stays alive only while a linked row has `status === 'active'` or a recent `lastActivityAt`; otherwise it is destroyed after `remote.fly.machine_idle_minutes` (default 30).
- **Flap** — a row that alternates `active` → `ended` → `active` because two writers read two different liveness oracles.

## Problem

On the Fly VM, `fly-serve.log` prints, on every patrol tick:

```
[conversation-lifecycle] marked 1 conversation(s) ended (1 session(s) gone, 0 keep-alive corpses)
```

while `tmux -L overdeck ls` shows the conversation's session alive and Claude Code answers turns.

### The mechanism (verified in code)

1. The patrol never re-marks an `ended` row whose session is gone — `conversation-lifecycle.ts` line 304: `if (conv.status === 'ended') continue;` (PAN-2215). So a line that prints on *every* tick proves something flips the row back to `active` between ticks.
2. Exactly two code paths set `status = 'active'` on an existing row: `markConversationRunning` (`src/lib/overdeck/conversations.ts` line 798), called only by the patrol's own resurrect (`conversation-lifecycle.ts` line 296) and by the list-route repair (`conversation-list.ts` line 222). (`createConversation` inserts new rows only.)
3. The patrol's resurrect runs only when the census says the session exists, so it cannot be the resurrector of a row the census calls "gone". The list-route repair can: it reads `list-sessions` and `conversationHarnessAlive`, not the census.
4. Home's shared-conversations sync calls `GET /api/machines/conversations` on the VM, which runs the list-route repair. So the row flaps: the patrol ends it from the census (`list-panes -a` omits the session), the next home sync resurrects it from `list-sessions` (which names the session).
5. Home reads whichever state the VM held at sync time. When it reads `ended` with an old `lastActivityAt`, the idle sweep can destroy a working machine.

### What is not yet known

Why `list-panes -a` omitted the session on that VM while `list-sessions` named it. A local probe on this host (tmux 3.4, the same version Ubuntu 24.04 ships; the census code run through `tsx` against an isolated socket) returned the session from both. The VM image (`docker/pan-workspace/Dockerfile`, `FROM ubuntu:24.04`) has `ps` (`procps 2:4.0.4` is in the base image, checked with `docker run --rm ubuntu:24.04`), so a missing process table is ruled out. Fly-specific conditions (`HOME=/`, `IS_SANDBOX=1`, no systemd so the tmux server is founded with `setsid`, PAN-1798 warning in the log) remain candidates. WI-3 is a time-boxed reproduction checkpoint for this question.

## Decisions

- **D-1 One door decides the end.** The patrol keeps the census for its per-tick sweep (cheap, one `list-panes -a` per tick, PAN-3921 FR-8), but before it calls `markConversationEnded` it asks the conversation-liveness door: `await conversationHarnessAlive(conv.tmuxSession)`. If the door reports the harness alive, the patrol does **not** end the row. Rationale: the list-route repair resurrects only when the same door reports the harness alive, so a row the patrol ends can no longer be resurrected by the list route, and a row the list route keeps alive can no longer be ended by the patrol. The flap cannot happen whichever oracle is wrong.
- **D-2 A disagreement is loud, once.** When the census says "gone" (or "corpse") and the door says alive, the patrol logs one `console.warn` line naming both answers and the census health (see WI-1 for the exact text). It warns once per session until the census and the door agree again, so a VM log is not flooded every 10 s, and a recurrence after agreement warns again. This line makes the next occurrence on a Fly machine diagnosable from `fly-serve.log` alone.
- **D-3 No change to the census, the list route, or the idle sweep** unless WI-3 finds the cause and the fix fits the WI-3 decision rule.
- **D-4 The confirmation runs only for rows about to be ended.** It sits right after the existing re-validation (`readLivenessView(true)`, line 330, and its verdict check at line 334), so a normal tick with no dead conversation makes zero extra subprocess calls.
- **D-5 The door's own "unknown" answers keep the row alive.** `isHarnessProcessAlive` returns `true` when `ps` fails, and the Herdr probe's `indeterminate` reads alive. That matches the census rule (`runtimeCensusHasHarnessProcess` returns `true` when the process table is unavailable), so no corpse that the patrol ends today is newly kept alive on a host where `ps` works.
- **D-7 The VM's server used the default socket.** The PAN-1798 warning in `fly-serve.log` prints only when `useManagedUnit` is true (`src/lib/tmux.ts` line 354: `const useManagedUnit = getManagedTmuxSocketName() === DEFAULT_MANAGED_TMUX_SOCKET;`), so the server resolved the `overdeck` socket, the same one the operator's `tmux -L overdeck ls` read. A socket-name mismatch is not the cause.
- **D-6 Reproduction is local Docker, not a paid Fly machine.** In `--auto` planning no operator approved Fly spend for this issue. WI-3 reproduces the Fly serve conditions in a local `ubuntu:24.04` container; a live Fly run happens only if the operator asks for it.

## Requirements

- **FR-1** The lifecycle patrol does not mark a conversation `ended` while `conversationHarnessAlive(conv.tmuxSession)` resolves `true` at mark time, for both the "session gone" and the "keep-alive corpse" verdicts, on tmux and Herdr hosts.
- **FR-2** When the census verdict and the door disagree, the patrol logs exactly one warning per session per disagreement episode, containing the session name, the census verdict, and the census `available`, `stale`, `error`, pane count, and up to 20 census session names.
- **FR-3** When the census verdict and the door agree that the harness is dead, the patrol ends the row exactly as before (companion terminal closed, `markConversationEnded`, attachment cleanup, the summary log line with its counts).
- **FR-4** The reproduction checkpoint's outcome (cause found and fixed, cause found and filed, or not reproduced) is recorded in `docs/fly-provider.md`.
- **FR-5** `docs/fly-provider.md` and `docs/TERMINAL-BACKENDS.md` describe the mark-time confirmation and the warning line; the "Recorded, not fixed here" bullet for #4739 no longer says the patrol marks the live conversation ended on every tick.
- **NFR-1** A patrol tick with no row about to be ended runs no subprocess beyond today's (no added `tmux` or `ps` calls).
- **NFR-2** `conversation-lifecycle.ts` stays under the 1000-line file-size ceiling (`scripts/lint-file-size.sh`, `CEILING=1000`; the file is 716 lines at planning time).
- **NFR-3** No test uses real timers for delays; `pollConversations()` is called directly, so no fake timers are needed.

    * list route resurrects a row only when conversationHarnessAlive says alive,

   }
