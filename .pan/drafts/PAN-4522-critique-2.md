## blocks-the-design: Newer event loses when its timestamp is older

The proposed `heldIsNewer` chooses the client entry whenever its `lastActivity` is later, even if the snapshot entry has a higher `updatedAtSequence`. These orders can disagree: `src/dashboard/server/routes/agents/runtime-events.ts`, line 117 accepts the heartbeat body's timestamp, while `src/dashboard/server/event-store.ts`, lines 373-393 assigns sequence at append time and preserves that timestamp. `packages/contracts/src/event-reducers.ts`, lines 1071-1091 applies a later `agent.activity_changed` even when its timestamp is earlier. For example, a client holds seq 100, working at 03:35; a delayed idle heartbeat is appended as seq 101 with timestamp 03:34; the server snapshot correctly holds idle at seq 101, but W4 keeps working at seq 100 indefinitely after `syncSnapshot`. The same issue arises from `agent.state_restored`: lines 1395-1407 replace the whole runtime entry and assign the new sequence while retaining the snapshot's older `lastActivity`. Make `updatedAtSequence` the primary order when both entries have valid sequences; use timestamps only when sequence cannot decide. Add a W4 case with a higher snapshot sequence and earlier timestamp.

## blocks-the-design: Current agent row changes historical heartbeat replay

W2 starts every scratch reducer state with the *current* `agentsById[agentId]`. `packages/contracts/src/event-reducers.ts`, lines 596-600 ignores `agent.heartbeat_dead` when the row is absent, and lines 1071-1091 allow an activity event to create a runtime entry before a row exists. The comment at lines 279-287 explicitly accounts for runtime events before `agent.created`. In the sequence activity_changed, heartbeat_dead, agent.created, a long-lived reducer leaves the runtime entry working because heartbeat_dead returned early. W2 replays the first two events with the current agent row already present and produces stopped. That violates FR-1's claim that the seed equals full replay. Preserve historical row existence for this conditional reducer case, or specify and test a different recovery rule; add this sequence to W2's tests.

## sharpens-framing: Retained clearing events may produce no entry

FR-1 says every agent with at least one retained runtime event gets a seeded entry. After the seven-day compaction in `src/dashboard/server/event-store.ts`, lines 420-428, the first retained event could be `agent.thinking_stopped` or `agent.waiting_cleared`. `packages/contracts/src/event-reducers.ts`, lines 1118-1122 and 1164-1168 return without creating a runtime entry when the prior entry is absent. W2's fold then omits that agent. Change FR-1 to cover agents whose retained events actually produce an entry, or define a bootstrap value for clearing events and test it.
