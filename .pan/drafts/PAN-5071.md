# PAN-5071 — overdeck.ai activate link: one Authorize click that names the bot and the machine

**Issue:** https://github.com/eltmon/overdeck/issues/5071
**Parent design:** `.pan/drafts/pan-5069.md`, section "Part C — account page (PAN-5071)" (FR-18, FR-19, FR-20)
**Planned:** 2026-11-11, auto mode, high effort. Code verified at `1d276ecc4bc`.

This PRD refines Part C of the PAN-5069 design into an executable brief. Part A (PAN-5069, the
bot side) has already landed: `requestDeviceCode` in `src/lib/account/client.ts` (lines 125–138)
sends `client_name` and `target_name`, and `pan mcp connector connect` tells the bot "ask them to
open it and click Authorize" (`cli/mcp.mdx` line 234). The account service still ignores the two
fields and still shows a typed-code form behind the link. This issue closes that gap. It touches
only `services/account`, its tests and `docs/ACCOUNT-SERVICE.md`.

## Glossary

- **Account service** — the overdeck.ai Cloudflare Worker at `services/account/` (D1 database
  `overdeck-account`). It runs GitHub sign-in and mints device tokens. Deploy is operator-only.
- **Device flow** — RFC 8628 sign-in in `services/account/src/device-flow.ts`. A client calls
  `POST /oauth/device/code`; a human opens the **activate link** and approves; the client polls
  `POST /oauth/token`.
- **Device grant** — one row of the D1 table `device_grants` (created in
  `services/account/migrations/0001_init.sql` lines 65–76): the hashed device code, the hashed
  user code, `platform`, `environment_id`, `status` (`pending | approved | denied`), timestamps.
- **User code** — the 8-letter code (`BCDF-GHJK`, letters from `BCDFGHJKLMNPQRSTVWXZ`) the
  human enters or receives in the link. **Normalized** = uppercase with dashes and spaces removed
  (`normalizeUserCode`).
- **Activate link** — `verification_uri_complete`, `https://account.overdeck.ai/activate?user_code=<8 letters>`.
  The bot shows it to the operator.
- **Confirm step** — the page that names the device and holds the one button that posts to
  `POST /activate/confirm`, which starts the GitHub leg (`startGitHubLeg`). Today only
  `POST /activate` renders it.
- **GitHub leg** — the redirect to GitHub and back to `/auth/github/callback`; it approves the
  grant (`onGitHubIdentity`). Unchanged by this issue.
- **Names** — `client_name` (the bot's name, for example `grok-bot`) and `target_name` (the
  machine's name, for example `eltmon-desktop`). They are **claims**: whoever requested the device
  code chose them. The page shows them as claims and never trusts them.
- **`activate-fail` bucket** — the per-IP rate-limit window for wrong user codes
  (`services/account/src/rate-limit.ts` `LIMITS['activate-fail']`: 10 per 15 minutes). `peek`
  reads it without counting; `hit` counts one.
- **Link previewer** — a chat or mail client that fetches a URL to draw a preview. It will fetch
  the activate link with GET before the human clicks it.

## Problem

The operator clicks the bot's activate link and sees "Enter the code shown in your terminal" with
the code prefilled and a **Continue** button. Continue shows "Connect a **Linux device** to your
Overdeck account?" with **Continue with GitHub**. That is two clicks, and the page never says
which bot asked or which machine it wants. The PAN-5069 operator decision 3 requires one
**Authorize** click on a page that names the bot and the machine.

## Requirements

FR-18, FR-19 and FR-20 keep the numbers the parent PRD gave them. New ids start at FR-25 so they
do not collide with Parts B and D.

- **FR-18** `GET /activate?user_code=<code of a pending, unexpired grant>` returns 200 with the
  confirm step: the names (when present), the device type, the formatted code, and one
  **Authorize** button whose form posts the normalized code to `/activate/confirm`.
- **FR-19** `POST /oauth/device/code` stores optional `client_name` and `target_name` in two new
  nullable `device_grants` columns added by migration `0003_device_grant_names.sql`. Each value is
  cleaned by `deviceName` (FR-25); a missing, empty or whitespace-only value stores NULL. The
  response body does not change.
- **FR-20** `GET /activate?user_code=<anything that does not resolve>` renders the typed-code form
  with the invalid-code notice, status 400, and counts one `hit` against `activate-fail`. When
  the `activate-fail` window is already exhausted, any GET with a non-empty code returns the 429
  rate-limited page before any lookup. When the window fills on this request, it returns 429.
- **FR-25** `deviceName(value)` removes C0/C1 control characters and the bidi controls
  U+200E, U+200F, U+202A–U+202E and U+2066–U+2069, trims, keeps at most 64 code points, trims
  again, and returns null when nothing is left. A value over 64 is cut, never refused.
- **FR-26** One renderer, `confirmStep(grant, normalized)`, draws the confirm step for both
  `GET /activate` and `POST /activate`. Its button reads `Authorize`. The string
  `Continue with GitHub` no longer appears in `services/account/src/`.
- **FR-27** Wording, by which names are present (`<device>` = `defaultLabel(grant.platform)`):
  - both: `<strong>{client}</strong> ({device}) wants to connect to your Overdeck account to reach <strong>{target}</strong>.`
  - client only: `<strong>{client}</strong> ({device}) wants to connect to your Overdeck account.`
  - target only: `This <strong>{device}</strong> wants to connect to your Overdeck account to reach <strong>{target}</strong>.`
  - neither: `Connect a <strong>{device}</strong> to your Overdeck account?` (today's sentence, unchanged).
  When either name is present, a muted line follows: `NAMES_ARE_CLAIMS_MESSAGE` =
  `These names come from the device that asked for this code. Overdeck does not verify them.`
  The existing muted line `Code XXXX-XXXX. If you did not start this sign-in, close this tab.`
  stays on every confirm step.
- **FR-28** `GET /activate` with no `user_code`, or one that is empty after trim, renders the
  bare form with status 200 and reads or writes no `rate_limits` row.
- **FR-29** `GET /activate` never writes `device_grants`: a GET (valid or not) leaves every
  grant's `status`, `user_id` and `last_polled_at` as they were. A link previewer's fetch
  therefore approves nothing.
- **FR-30** The names appear only on the confirm step. `devices.label` keeps
  `defaultLabel(platform)`; the token response and `GET /v1/devices` are unchanged.

- **NFR-2** Migration `0003` is additive (two `ALTER TABLE … ADD COLUMN`), contains no semicolon

- **NFR-3** `services/account` stays Web-APIs only (no `node:` imports in `src/`).

## Decisions (made here; recorded in the xBRIEF `autoDecisions`)

1. **Wrong code on GET shows the notice.** Status 400, form prefilled with the formatted code
   when it normalizes to 8 letters (else the raw text), plus `INVALID_CODE_MESSAGE`. A silent
   prefilled form would make the human submit it and burn a second `activate-fail` hit.
2. **GET mirrors POST's rate-limit order.** `peek` before the lookup, `hit` on a miss. Only a
   non-empty code is gated (FR-28), so opening the bare `/activate` page costs nothing.
3. **No route bucket on GET.** Wrong-code guessing is already capped by `activate-fail`; adding
   the `activate` bucket to GET would also cap valid reloads and is not needed for safety.
4. **One renderer for both paths** (FR-26). Otherwise the typed-code path keeps two clicks and
   two different confirm pages exist.
5. **Cut, don't refuse, long names** (FR-25), matching the client (`.slice(0, 64)` in
   `src/lib/account/client.ts`). Code points, not UTF-16 units, so a cut never splits a
   surrogate pair. Control and bidi characters are dropped because a name is shown to a human
   deciding whether to approve; this costs one regex.
6. **Absent client name falls back to the device type** (FR-27); the page never says "unknown".
7. **Names stay off the device record** (FR-30). The device label is a privacy decision (D-17:
   "never the hostname"); changing it is out of scope.
8. **Deploy order: migrate, then deploy.** The new `issueCode` INSERT names the two new columns,
   so a Worker deployed before `0003` is applied answers 500 to every device-code request. The
   old Worker on the migrated schema works (the columns are nullable). Rollback with
   `npx wrangler rollback` is safe; the columns stay.

/**
 * GET /activate[?user_code=…]: a code of a pending grant renders the confirm step directly (PAN-5071 FR-18), so the
 * device-flow link is one Authorize click. A code that does not resolve counts against `activate-fail` like POST /activate

export const activatePage: Handler = async (req, rc) => {
  const raw = (new URL(req.url).searchParams.get('user_code') ?? '').trim();
  if (raw === '') return html(activateForm('', null));
  const exhausted = await peek(rc, 'activate-fail');
  if (!exhausted.ok) return rateLimitedPage(exhausted.retryAfterS, TOO_MANY_WRONG_CODES_MESSAGE);

   `target_name`; `schema.test.ts` lists three migrations and reads NULL for both on a row
   inserted without them (W-1).
2. `POST /oauth/device/code` with names stores the cleaned values (trim, ≤64 code points,
   controls and bidi removed, blank → NULL) and returns the same six fields (W-1).
3. The confirm step from `POST /activate` names the bot and machine per FR-27, shows
   `NAMES_ARE_CLAIMS_MESSAGE` only when a name is present, escapes names, and has one
   `Authorize` button; `grep -rn "Continue with GitHub" services/account/src` finds nothing (W-2).
4. `GET /activate?user_code=<valid>` returns 200 with the confirm step and changes no
   `device_grants` row; a wrong code returns 400 with the error and counts one `activate-fail`;
   the 11th wrong code in a window returns 429; no code returns the form and counts nothing (W-3).
5. Following the link (GET → confirm POST → GitHub callback) yields a token on the next poll
   with no `POST /activate` (W-3), and the Miniflare test shows the named confirm step on real
   workerd (W-4).
6. `docs/ACCOUNT-SERVICE.md` describes the name fields, the GET confirm step and its claims
   line, the GET `activate-fail` counting, and the migrate-before-deploy order (W-5).

Operator check after deploy (not a pipeline gate): `npx wrangler d1 migrations apply
overdeck-account --remote`, then `npx wrangler deploy`; `pan mcp connector connect` from a bot
prints a link whose page names the bot and the machine and needs one Authorize click.

## Non-goals

- Deploying the Worker or applying the migration remotely (operator-only).
- Any change to `POST /activate/confirm`, its Origin check, `startGitHubLeg` or the GitHub leg.
- Showing the names on the "Device connected" page, in `devices.label`, in the token response or
  in `GET /v1/devices`.
- Adding a route-level rate-limit bucket to `GET /activate`.
- Verifying the names against the directory or the machine (they are claims by design; the
  machine-minted pairing code is the authority, PAN-5069 "Security model").
- Changing the client (`src/lib/account/client.ts`) or `pan mcp connector connect`; Part A shipped.
- Defending the per-IP `activate-fail` window against cross-site GETs that burn it (see Risks).

## Risks

- **Cross-site GETs can fill a victim's `activate-fail` window.** A page that loads
  `https://account.overdeck.ai/activate?user_code=WRONG` ten times (for example as images) makes
  the victim's IP wait up to 15 minutes before activating. `POST /activate` refuses cross-site
  posts before counting, so GET is the only cross-site path into the window. The issue requires
  GET to count wrong codes (otherwise GET becomes an unmetered code-guessing oracle), and the
  effect is a delay of at most 15 minutes with no data exposure. Accepted; not fixed here.
- **Deploy order** (Decision 8): the docs item states it; the operator runs the migration first.
- **Link previewers** fetch the link with GET; FR-29 and its W-3 test make that harmless.
- **Expired codes from a stale bot message** land on the 400 form with the error; the bot's next
  `connect` run prints a fresh link (Part A FR-3).

## Probe pass (findings acted on)

- The parent PRD's migration snippet (`ALTER TABLE … ADD COLUMN client_name TEXT; ADD COLUMN
  target_name TEXT;`) is not valid SQLite; W-1 uses two `ALTER TABLE` statements.
- `device-flow.test.ts` lines 98–100 assert the old GET prefill; W-3 replaces them rather than
  leaving a failing assertion.
- `schema.test.ts` line 40 pins the migration list; W-1 updates it.
- A whitespace-only `user_code` would otherwise hit the lookup path and count as a wrong code;
  FR-28 treats it as no code.
- Without the claims line a malicious requester could name itself "Overdeck Official"; FR-27's
  muted line says the names are unverified, and the existing "If you did not start this
  sign-in, close this tab" stays.
- The issue says "at most 64 characters"; the client cuts UTF-16 units, the server cuts code
  points (Decision 5). A client-cut value is at most 64 units, so it is at most 64 code points and
  passes through the server cut unchanged.
