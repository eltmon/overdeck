## Glossary

- **Home** — the operator's machine: the Overdeck dashboard that holds the link and starts the Fly VM.
- **Fly machine** (new term) — a Fly.io Machine started by this issue's service that runs `pan serve` and is linked from home. It is a *machine* in the Anywhere sense (`pan-2350.md` glossary). It is different from a **remote work agent** VM (`pan start --remote`, `src/lib/remote/remote-agents.ts`), which runs Claude Code in raw tmux and no Overdeck server.
- **Machines exec API** — `POST /apps/{app}/machines/{id}/exec` (`FlyApiClient.execCommand`, `src/lib/remote/fly-api.ts:258`). It runs one command on the VM and returns `{ stdout, stderr, exit_code }`. `FlyProvider.sshImpl` (`src/lib/remote/fly-provider.ts:372-401`) calls it with a 60 s timeout, so anything longer must run detached (`setsid nohup … &`) and be polled. This pattern already exists as `cloneDetached` in `src/lib/remote-workspace.ts:35-64`.
- **Fly proxy** — Fly's edge. With a machine `services` entry `{ internal_port: 3011, ports: [{ port: 443, handlers: ['tls','http'] }] }`, `https://<app>.fly.dev` reaches port 3011 on a machine of the app. Every machine in an app shares that hostname. The request header `fly-force-instance-id: <machineId>` pins a request to one machine.
- **Public route** — a link route of kind `public` (`ROUTE_KINDS`, `packages/contracts/src/machines.ts:23`). For a Fly machine it is the URL `wss://<app>.fly.dev/ws/link?fly-instance=<machineId>`.
- **`fly-instance` route parameter** (new) — a reserved query parameter on a `wss://` route URL. The channel client removes it from the URL it dials and sends its value as the `fly-force-instance-id` header.
- **Pairing code** — the one-time `odp_` credential from `issuePairingCredential()` (`src/dashboard/server/pairing-credentials.ts:65-75`). It is held in memory by the server that issued it, and only that server can complete a pairing with it (Noise `XXpsk0`, `src/lib/anywhere/channel/noise.ts:162-172`).
- **Public-link-only mode** (new) — env `OVERDECK_PUBLIC_LINK_ONLY=1` on the VM's server. A request that is neither inside a secure channel nor from a local loopback caller gets 404 on every path. The `/ws/link` upgrade is handled before the HTTP gate (`src/dashboard/server/channel-listener.ts:190-205`) and keeps working.
- **Host heartbeat / ephemeral watchdog** — PAN-4295's VM-side Node script (`generateEphemeralWatchdogScript`, `remote-agents.ts:185`) stops the machine with `kill 1` when `/workspace/.pan/host-heartbeat` is more than 300 s old. Home writes that file every 60 s (`refreshHostHeartbeatForEphemeralVms`, `remote-agents.ts:353`, registered in `src/lib/cloister/hygiene-scheduler.ts:77`).
- **Fly machine record** (new) — one row in `${OVERDECK_HOME}/fly-machines.json` (0600, atomic writes): which Fly machine backs which link. It is the Fly counterpart of `ssh-machines.json` (`src/lib/anywhere/ssh/machine-store.ts:24-38`). It is kept outside `machine-links.json` because `upsertLink` rebuilds link records field by field (that file's header gives the same reason).

## Problem

FR-18 and D-12 say a Fly VM is an ordinary linked machine. Today nothing in the Anywhere code knows about Fly (`grep -i fly src/lib/anywhere` finds nothing), and:

1. **The image has no `pan`.** `docker/pan-workspace/Dockerfile` installs Node 22, pnpm, Bun, gh, Claude Code and flyctl, then runs `CMD ["sleep", "infinity"]`. There is no Overdeck server to link to and no Docker (OD-4).
2. **Nothing is reachable from outside.** `createVm` passes no `services` (`fly-provider.ts:243-253`), `FlyMachineConfig` has no `services` field (`fly-api.ts:134-164`), and `exposePort()` always fails (`fly-provider.ts:456-465`).
3. **The channel client cannot pin a Fly machine.** `connectTransport` dials `new WsClient(target.url)` with no headers (`src/lib/anywhere/channel/open.ts`, the `const ws = new WsClient(target.url);` line). Several machines share `<app>.fly.dev`, so without `fly-force-instance-id` the upgrade can land on the wrong VM. The handshake then sees the wrong key and the supervisor backs off for 300 s.
4. **The label would be the machine id.** A new server labels itself `hostname()` once (`src/lib/environment-identity.ts:91-96`). On Fly that is the bare machine id, but the chip must read `fly-<id>`. The label is fixed at link time (`machine-link-service.ts:283`; `link-supervisor.ts` `applyDescriptor` merges routes only).
5. **The loops that keep VMs safe skip VMs without `remote-state.json`.** Heartbeat, credential refresh and the spend cap (`checkRemoteSpendCap`, `remote-agents.ts:411`) all iterate `listActiveRemoteAgentStates()`. A VM that only runs conversations would never be heartbeated (its watchdog would never arm), never get fresh Claude credentials (401 mid-conversation), and never count toward `remote.max_concurrent_agents`.
6. **Home cannot start a conversation on a linked machine.** `link-fence.ts:4` says so ("#4651 adds that"). The owner side already accepts it: `POST /api/conversations` needs scope `operate` (`route-scopes.ts:61`), machine tokens carry `operate` (`src/lib/access-tokens.ts:93-97`), and `validateOrigin` admits an Origin-less `Bearer odk_` request (`origin-validation.ts:140-144`).

## Goals

- `pan machines add-fly --project <key> --message "<text>"` starts a Fly VM, links it, puts the project on it, and starts a Claude Code conversation there. The conversation streams live in the home dashboard as a linked row with a `fly-<machineId>` chip.
- **Pull here** on that row (or `pan conv pull @fly-<machineId>/<name>`) brings it home, through the existing PAN-4650 path.
- The same service function is the door that #4651 (**Fly (new VM)** in the Machine field, `--machine fly`) and #4638 (lanes on Fly) call.
- VM spend is bounded: the cap counts Fly machines, a VM stops itself when home goes away, and home destroys stopped or idle Fly machines.
- OD-4 is settled by a live check: Docker runs inside the image, or the fallback is recorded.

## Non-goals

- `pan start --remote` work agents as linked conversations, and session rows for them (closing PAN-1775) — [PAN-4734](https://github.com/eltmon/overdeck/issues/4734).
- The **Machine** field, **Fly (new VM)** in the new-conversation dialog, and `--machine fly` on `pan start`, `pan worker run` and `pan lane start` — #4651 (W-WORK1). Its issue body says those wait for this issue's door.
- Workers and gauntlet lanes placed on a Fly machine, and `gauntlet.fly.max_vms` — #4651 and #4638.
- Capability tags in the descriptor (`docker`, `gpu`, OS) and `--needs` placement — #4651 (W-WORK6, FR-23). See D-8 for the OD-4 fallback.
- Codex or any harness other than Claude Code on Fly — #4296 (W-FLY3).
- Joining Fly VMs to the tailnet with an ephemeral key — #1254 (W-TS1).
- A dashboard UI button for adding a Fly machine. The CLI and the route are the door; the dialog entry is #4651.
- Restarting a stopped Fly machine. The rootfs resets on every start (`.overdeck/context/codebase/concerns.md`, "Fly Machine rootfs resets on every start"), so a stopped Fly machine has lost its server state and conversations. It is destroyed, never restarted.
- Durable-tier volumes for Fly machines. They always use the ephemeral layout.
- GitLab-hosted projects on a Fly machine (the image has no `glab`; PAN-4295 non-goal).
- Allocating the Fly app's public IPs automatically. This is a one-time documented setup step (D-10).

## Requirements

### Functional

- **FR-1** The `pan-workspace` image installs `@overdeck/core` globally (build argument `OVERDECK_VERSION`, default `latest`), so `pan --version` runs on the VM.
- **FR-2** `pan serve` accepts `--no-open` and then never tries to open a browser.
- **FR-3** `FlyApiClient.createMachine` passes `config.services` and `config.env` to the Machines API unchanged when given.
- **FR-4** A `wss://` route URL with the query parameter `fly-instance=<id>` is dialled without that parameter and with the header `fly-force-instance-id: <id>`. Every other URL is dialled exactly as today.
- **FR-5** With `OVERDECK_PUBLIC_LINK_ONLY=1`, the remote request gate returns 404 to every HTTP request that is neither inside a secure channel nor a local loopback caller, including static SPA paths. Unset, the gate behaves exactly as today.
- **FR-6** `fly-machines.json` stores Fly machine records with mode 0600 and atomic writes, and supports upsert, get by link id, list and remove.
- **FR-7** `provisionFlyMachine()` creates a Fly machine and returns once `pan serve` answers on the VM and a pairing code is issued. It:
  1. creates the machine with the `services` of D-3;
  2. waits for `started`;
  3. makes the VM's `pan --version` equal home's version;
  4. writes the `fly-<machineId>` identity;
  5. syncs Claude and GitHub credentials and configures Claude Code;
  6. starts `pan serve` detached with the env of D-4;
  7. installs the ephemeral watchdog and writes the first heartbeat;
  8. starts `dockerd` when the image has Docker;
  9. reads a pairing code from `pan pair --json`.
- **FR-8** `addFlyMachine()` enforces the cap (FR-12), provisions, links one way (home → VM) over the public route with `access: 'operator'`, and writes the record. A failure after the machine exists destroys the machine, removes any link it made and deletes the record.
- **FR-9** With `projectKey`, `addFlyMachine()` clones that project on the VM over HTTPS into `/workspace/<projectKey>` and registers it there with `pan project clone`, so the VM's `projects.yaml` carries its `github_repo`.
- **FR-10** With `message` (which needs `projectKey`), `addFlyMachine()` starts a conversation on the VM through the link (`POST /api/conversations` with `{ message, projectKey, harness: 'claude-code', model?, effort? }`, actor `operator`). It returns `{ environmentId, name, path: '/conv/@<environmentId>/<name>' }`. A `harness` other than `claude-code` is refused with `harness-unsupported` before any VM is created.
- **FR-11** `POST /api/machines/fly` and `pan machines add-fly [--project <key>] [--message <text>] [--model <id>] [--effort <level>] [--region <code>] [--image <ref>] [--json]` expose FR-8 to FR-10. The route refuses callers that arrive over a secure channel, like `POST /api/machines/ssh`.
- **FR-12** `checkRemoteSpendCap` counts active remote agents plus Fly machine records against `remote.max_concurrent_agents` (0 or unset stays unlimited). `addFlyMachine` refuses with `cap-reached` before creating a machine.
- **FR-13** Unlinking a Fly machine (`pan machines unlink`, `DELETE /api/machines/:id`) destroys its Fly machine and deletes its record. With `--keep-server` (`keepServer=1`) the machine is left running and only the record is deleted.
- **FR-14** Every 60 s the deacon child writes the host heartbeat to every Fly machine record, whether or not the deacon freeze is set.
- **FR-15** The credential refresh covers Fly machine records the same way it covers active remote agents (fingerprint change or 15 min, per-VM watermark).
- **FR-16** Every 60 s the deacon child removes a Fly machine record, its link and its machine when either of these holds:
  - the Fly API reports the machine `stopped`, `destroyed` or absent (404). This is positive evidence; an API error is indeterminate and does nothing;
  - for at least `remote.fly.machine_idle_minutes` (default 30, 0 disables), home's `linked_conversations` cache has no **active** row for that machine's environment id. A row is active when its `releasedTo` is null and either its `status` is `active` or its `lastActivityAt` falls inside the idle window (`SharedConversationRow`, `packages/contracts/src/linked-conversations.ts:18-21`). A conversation that ended but was never pulled therefore does not keep its VM alive forever (the shared list keeps every non-archived row, `shared-conversations.ts:105`).

### Non-functional

- **NFR-1** With zero Fly machine records, the FR-14 to FR-16 loops construct no Fly provider and make no Fly API call.
- **NFR-2** Tests of polling, intervals, idle windows and heartbeats use `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()`; no test waits on a real `setTimeout` (repo rule: fake timers for retry and delay tests).
- **NFR-3** No `execSync` in code reachable from the dashboard server or the deacon child. Remote commands go through the Machines exec API; local processes through async `spawn`/`exec` (repo rule).
- **NFR-4** No file passes the file-size guard (`scripts/lint-file-size.sh`, compared with its `origin/main` line count). New logic goes in new modules. `remote-agents.ts` (851 lines) takes only the FR-12 change, at most +10 lines.
- **NFR-5** Every new export has a production caller, or carries the test-seam comment `/** Test seam: no production caller; … */` (dead-export scan).
- **NFR-6** No operator SSH private key reaches the VM (PAN-4295 FR-10 still holds). Credentials go only through `syncAllCredentials` (Claude OAuth file and `gh auth token`).
- **NFR-7** Bytes between home and the VM travel only inside the secure channel (PRD NFR-1). Fly's proxy terminates TLS but sees only Noise ciphertext inside the WebSocket.

## Decisions (made here)

- **D-1 Pairing direction: the VM issues the code; home links.** D-12 says "home creates a pairing code and passes it to the VM". The code only supports codes issued by the server that holds them (`issuePairingCredential`; no import path exists). So home runs `pan pair --json` on the VM through the Machines exec API and reads `credential` from stdout. This is exactly what SSH machines do (`ssh/helper.ts:342-362`), and it has the same security property: the code travels only over the Fly-authenticated exec channel, never over the network route being paired.
- **D-2 One-way link.** Home links to the VM (`bothWays: false`). The VM cannot reach home's LAN or tailnet addresses, and home's dashboard needs no access from the VM.
- **D-3 Public route = WSS on 443 with instance pinning.** The machine config carries `services: [{ protocol: 'tcp', internal_port: 3011, ports: [{ port: 443, handlers: ['tls', 'http'] }] }]`. The route is `wss://<app>.fly.dev/ws/link?fly-instance=<machineId>`, kind `public`, source `pairing`. Raw TCP is not used: Fly cannot pin a raw TCP connection to one machine, and raw ports need a dedicated IPv4. `/ws/link` already exists for TLS-terminating proxies (`channel-listener.ts:12-14`), and `upgradePath()` compares only the pathname (`channel-listener.ts:220-224`).
- **D-4 The VM server's environment.** The detached `pan serve` runs with `OVERDECK_TERMINAL_BACKEND=tmux` (Herdr is absent and there is no fallback, `src/lib/terminal-backends/select.ts:7-16`), `IS_SANDBOX=1` (Claude Code refuses bypass mode as root otherwise; PAN-4295 live run), `OVERDECK_PUBLIC_LINK_ONLY=1` (FR-5), and `PORT=3011`. It never sets `OVERDECK_DISABLE_DEACON`, which would make it a peer that hosts no machine links (`src/lib/boot-gates.ts:47-48`). These go on the command line of the detached process, not in the image, so remote work-agent VMs are unchanged.
- **D-5 The image keeps `CMD ["sleep", "infinity"]`.** The server is started by exec after the identity file is written, because the label needs the machine id, which exists only after `createMachine` returns. Remote work-agent VMs (same image) do not start a server.
- **D-6 Label `fly-<machineId>`.** Before the server first starts, home writes `/root/.overdeck/environment-id.json` with `{ "v": 1, "environmentId": <randomUUID()>, "label": "fly-<machineId>", "createdAt": <ISO> }`, the exact shape `ensureEnvironmentIdentity()` writes (`environment-identity.ts:91-96`). `pan-4437-continue-here.spec.ts:65` already pre-writes identity this way.
- **D-7 Version equality by install, not by image tag.** The image installs the newest published `@overdeck/core` at build time. At provisioning, when the VM's `pan --version` differs from home's `getOverdeckVersion()`, home runs `npm install -g @overdeck/core@<home version>` detached and polls (at most 5 min). A failed install fails provisioning with `version-mismatch`, naming both versions. SSH machines require the same equality (`ssh-machine-service.ts:268-269`). Home's version is its `package.json` version, which is always a published release. A workspace build carries the last release's number, so it matches.
- **D-8 OD-4 Docker: try it, and fall back without a new descriptor field.** The image installs Docker (`docker.io` and `iptables` from Ubuntu). Provisioning starts `dockerd` detached and records `docker: true` when `docker info` succeeds within 60 s. The live checkpoint (WI-13) proves it with `docker run --rm hello-world`. **Fallback, if Docker cannot run on a Fly machine:** remove the Docker install and the `dockerd` start, record `docker: false`, and say in the docs that Fly machines have no Docker. No capability field is added here: FR-23's `docker` tag ("`docker info` succeeds") and its `--needs docker` placement belong to #4651 (W-WORK6), and that detection reports a Docker-less Fly machine correctly. The work agent comments the outcome on #4651.
- **D-9 Lifecycle is destroy, never stop.** Removal, idle and the stopped-machine sweep all destroy the machine (`destroyMachine`, `force=true`). A Fly machine's conversations live on its rootfs. The operator keeps them with **Pull here** before removal, or with a vault the VM shares with home (not configured by this issue).
- **D-10 Public IPs are a one-time setup.** `https://<app>.fly.dev` needs the app to hold a shared IPv4 and an IPv6. The Machines REST API cannot allocate them. The docs give `fly ips allocate-v4 --shared -a <app>` and `fly ips allocate-v6 -a <app>`. When the link step fails with `unreachable`, `addFlyMachine`'s error names those two commands.
- **D-11 The Fly API client is used directly for create and destroy.** `FlyProvider.createVm` hard-codes its machine config (`fly-provider.ts:243-253`), so the new code calls `createFlyApiClient()` (`fly-api.ts:341`) for `ensureApp`, `createMachine`, `waitForState`, `getMachine`, `execCommand` and `destroyMachine`. It reuses `createFlyProviderFromConfig((await loadConfig()).remote, 'ephemeral')` (`src/lib/remote/index.ts:77-105`; `loadConfig` is async, `src/lib/config.ts:368`) only for `syncAllCredentials`, `configureClaudeCode` and `writeRemoteFile` (`remote-agents.ts:514`). Those take the machine *name* and resolve it through `resolveVm`'s API fallback (`fly-provider.ts:143-166`), so machine names must be unique within the app: `overdeck-machine-<8 hex>`.
- **D-12 Memory.** Fly machines use `max(remote.fly.vm_memory ?? 1024, 2048)` MB. The dashboard server plus Claude Code do not fit in 1 GB.
- **D-13 Synchronous route.** `POST /api/machines/fly` runs the whole flow in one request (3–10 min with a clone), as `POST /api/machines/ssh` does. The CLI waits with no client timeout and prints the result.
- **D-14 Who may add.** The route needs the `admin` scope (unlisted routes default to `admin`, `route-scopes.ts`). Like `POST /api/machines/ssh` (`routes/machines-ssh.ts:102-123`), it refuses channel callers, so no linked machine can start Fly VMs on this machine's account.
- **D-15 Split.** Moving work agents onto this path is [PAN-4734](https://github.com/eltmon/overdeck/issues/4734). It rewrites the reap, tell and kill contract that PAN-4295 restored and live-tested on 2026-11-01, and would double this PR's surface.

## Hazards

- **Wrong-instance landing.** If `fly-force-instance-id` is not honored, the handshake sees another machine's key, and the supervisor backs off 300 s. WI-14 detects this; the fallback is to stop and escalate.
- **Fly proxy idle timeout.** Link heartbeats every 15 s keep the WebSocket busy. If Fly still drops it, the supervisor reconnects (state `connecting`).
- **`/workspace` at home.** `vault-continue.ts` `resolveTarget` prefers `record.cwd` when that directory exists at home. A Fly conversation's cwd is `/workspace/<projectKey>`. A home machine with that exact path would adopt into it. This is rare; it is noted in the docs, not fixed.
- **Pull size.** A WIP bundle larger than 32 MiB (`LINK_FORWARD_MAX_BYTES`, `link-client.ts:243`) fails the transfer with `transfer-too-large`. A WIP with secret hits is recorded as `skipped`, so the transcript moves without the code (`wip-capture.ts:292`, `:298`).
- **Home project must carry `github_repo`.** Pull here matches by `findProjectForGitOrigin` (`src/lib/projects/origin-match.ts:13-25`).
- **Exec payload limit (~16 KB).** `writeRemoteFile` already chunks (8 KB base64, 350 ms apart). Use it for every file write.
- **The test image tag.** The live checkpoint must pass `--image registry.fly.io/pan-workspace:pan-4652`, because `:latest` has no `pan` until the merge rebuilds it. An operator config may still name `registry.fly.io/pan-workspaces:latest` (#4682), which is the work-agent image without `pan`.
- **The deacon child removes links.** `sweepFlyMachines` writes `machine-links.json` from the deacon process; the dashboard's link store refresh (5 s, `link-store.ts:31`) and `reconcile()` pick it up.
