## Glossary

- **Stack reclaim.** PAN-5623's feature: while the quality-gate admission queue is starved on memory,
  the primary dashboard stops the `api`/`fe`/`frontend`/`server` containers of one parked issue's
  workspace stack, journals `stack.reclaimed`, and starts them again later (`stack.restored`).
- **Open reclaim.** The newest `stack.*` journal entry of a workspace is a `stack.reclaimed` with at
  least one container name. Read by `openStackReclaim(entries)` in `src/lib/cloister/pipeline-journal.ts`.
- **Episode.** A gate-starvation episode (PAN-5621), identified by `GateStarvationRecord.since`.
- **Housekeeping entry.** A journal entry whose type starts with `stack.` (`isHousekeepingEntry`).
- **Restore door.** `restoreReclaimedStack` in `src/lib/workspace/stack-restore.ts`. Callers: the
  dashboard restore poll (trigger `turn`), the verification runner (`verification`), and through the
  spawn wrapper `restoreReclaimedStackForSpawn` the spawn gate and the dashboard spawn route (`spawn`).
- **Lifecycle snapshot cache.** The module-level `cachedContainerLifecycleSnapshot` in
  `src/lib/docker-stats.ts` (per process, no TTL). `getWorkspaceStackHealth` reads it when the caller
  passes no `containers`. Written by `recordDockerContainerLifecycleSnapshot`.
- **Stack lock.** `<workspace>/.overdeck/stack-reclaim.lock`, taken by `withStackLock` on top of the
  shared `withFileLock` (`src/lib/vault/file-lock.ts`), stale after `STACK_LOCK_STALE_MS = 300_000`.
- **Restore index.** `StackReclaimState.restoreIndex` in the reclaim service: open reclaims the 5 s
  restore poll watches, seeded once from every workspace journal (`seeded` flag).
- **Fail closed.** When a fact cannot be read, the decision that changes nothing is taken.

## Requirements

### Functional

- **FR-1** A journal that exists but cannot be read is reported as `null` by `tryReadPipelineJournal`;
  a missing journal is `[]`. Every reclaim-service decision that reads a journal fails closed on `null`.
- **FR-2** A restore-index entry whose journal read returns `null` stays in the index; seeding is
  marked complete only after every workspace journal was read.
- **FR-3** An issue whose open reclaim (from any episode) names a container that is not running now is not a reclaim candidate.
- **FR-4** The blocker-declaration check runs for every ranked candidate. The merge gate is asked for at
  most `MERGE_GATE_CANDIDATES = 3` candidates per poll: the largest ones without a declaration.
- **FR-5** After a failed restore, the restore poll waits `STACK_RESTORE_RETRY_MS` measured from the
  moment the failure returned, not from the tick start.
- **FR-6** The stack lock's mtime is renewed every `STACK_LOCK_RENEW_MS = 60_000` while its holder runs.
- **FR-7** `withFileLock` removes the lock file at release only when the file still holds the content
  this acquisition wrote.
- **FR-8** The restore door refreshes the process's lifecycle snapshot cache after any successful
  `docker start`, partial failures included, before it journals `stack.restored`.
- **FR-9** `restoreReclaimedStackForSpawn` returns a fresh recorded listing whenever the restore result
  is not `none`, and when it is `none` but the workspace's newest `stack.*` entry is `stack.restored`.
  It returns `undefined` only when no reclaim history applies or the fresh listing fails or is empty.
- **FR-10** The Flywheel row's default journal tail is the last 50 non-housekeeping entries.
- **FR-11** `pan status` lists reclaimed stacks of issues without an agent record in their own section
  and does not print "No running agents." when such a stack exists.
- **FR-12** `panesAllowReclaim` refuses a non-review pane whose backend state is not `idle`, `done` or
  `exited`.

### Non-functional

- **NFR-1** No new `execSync`, no sync tmux calls, no new timers that hold the process open (`unref`).
- **NFR-2** Tests that depend on delays use fake timers or an injected clock; no real waits.
- **NFR-3** The restore door and the reclaim polls still never throw out of a timer or to a caller.
- **NFR-4** No file grows past its `origin/main` line count plus ceiling rules (`scripts/lint-file-size.sh`,
  `CEILING=1000`). `tests/unit/lib/flywheel/derive-status.test.ts` is at 931 lines, so WI-5 uses a new file.

## Design decisions

- **D1 (finding 5). Failure-aware read, not a periodic rescan.** A rescan would leave the turn trigger
  off for up to the rescan interval and still let the candidate path fail open (`[]` means "not
  reclaimed" and "no open reclaim"). A `null` result lets every caller fail closed. The service dep
  `readJournal` becomes `(workspacePath: string) => PipelineJournalEntry[] | null`, defaulting to
  `tryReadPipelineJournal`. `readPipelineJournal` keeps its signature (`tryReadPipelineJournal(...) ?? []`).
  Null handling: `buildCandidates` skips the workspace; the parked check treats it as not parked; the
  read-back after the `stack.reclaimed` append returns idle `journal-unwritable`; seeding leaves `seeded`
  false (readable workspaces are still indexed, so the next tick re-seeds); the restore poll keeps the
  index entry and its retry time and moves on.
- **D2 (finding 2).** `buildCandidates` reads the journal once and skips the issue when
  `reclaimedInEpisode(journal, record.since)`, or when an open reclaim names any container that is not
  running now (`open.containers.some((name) => !runningNames.has(name))`, where `runningNames` is the set of
  names in the `running` listing). That is the case CodeRabbit describes: a new reclaim would replace the
  record of a still-stopped container. An open reclaim whose containers are all running again (every
  `docker stop` failed, the read-back failed after the append, or an operator started them all) loses
  nothing when superseded, so it does not exclude the issue; otherwise such an issue could be excluded for
  good, because nothing closes a reclaim whose containers never stopped. After a restore closes the reclaim,
  the issue is eligible again in a later episode (PAN-5623 D8 unchanged).
- **D3 (finding 3). Budget definition.** Iterate every ranked candidate in rank order. Read its journal
  (null: skip). A pending declaration selects it. Otherwise, while fewer than 3 merge-gate calls were
  made this poll, call `mergeReady` (a throw counts as not ready); `true` selects it. The first selected
  candidate is the target. So the merge gate is asked for the three largest candidates without a
  declaration, and never more than three times per poll.
- **D4 (finding 4). Two fixes.** (a) `withStackLock` renews the lock mtime every 60 s with
  `fs.promises.utimes` while `fn` runs, so a live holder never looks stale; this covers both the stop
  loop and the restore start loop. (b) `withFileLock` writes a per-acquisition token
  (`${process.pid} ${randomUUID()}\n`) and at release removes the file only when its content still
  equals that token. The reclaim and restore polls share one pid, so the pid alone is not an owner. The
  release change touches a primitive with ~15 callers; it changes behavior only when a lock was taken
  over as stale, which is exactly the case where removing it is wrong. A small read-then-remove window
  remains; it is accepted (renewal makes the takeover itself near impossible for the stack lock).
- **D5 (finding 6).** `state.restoreRetryAt.set(issueId, deps.now() + STACK_RESTORE_RETRY_MS)`. The tick's
  captured `now` still drives the skip comparison.
- **D6 (finding 9). Allowlist `idle`, `done`, `exited`, not only `idle`.** Herdr reports a finished turn
  with a live pane as `done` (`toAgentState`, contract comment in `packages/contracts/src/backend-pane.ts`).
  A parked, merge-ready work agent is usually `done`; requiring `idle` would stop reclaim on the default
  backend. `exited` means no harness runs. `unknown` and `blocked` are refused with the new reason
  `pane-not-idle`; `working` keeps `pane-working`. The turn-state checks stay after it.
- **D7 (findings 7 and 10). One mechanism in `stack-restore.ts`.** The dashboard spawn route runs in the
  same process as the restore poll, and the cache has no TTL (`DockerStatsCollector` starts only when a
  resources route is hit). So: (a) the door refreshes the cache after any successful start, before the
  failed return and before journaling `stack.restored`; (b) the wrapper also refreshes when the door
  returned `restored`/`failed` without a snapshot (all already running, or listing failure), and when the
  door returned `none` but the newest `stack.*` entry is `stack.restored` (another process, such as the
  verification worker, already restored). An empty or failed listing is never recorded or returned.
  `collect` and `record` move into `StackRestoreDeps` so the door and the wrapper share them; test call
  shapes `{ ...w.deps, collect, record }` keep working. `workspace-stack-spawn-gate.ts` and
  `spawn-issue.ts` need no change.
- **D8 (finding 8).** Apply CodeRabbit's suggested diff and export the function as
  `readFlywheelJournalTail` so it can be tested. Keep the row filter at line 628: injected `journalTail`
  and `lastJournal` deps still need it.
- **D9 (finding 1).** A new `reclaimedStacksWithoutAgent` list (issues without an agent whose
  `stackHealth.reclaimed` is non-empty, healthy or not). A stack both broken and reclaimed appears in
  both sections, matching the agent loop, which prints both lines. JSON output is unchanged.
- **D10. No changelog file.** `changelog.d/pan-5623.md` is still unfolded (unreleased) and its text stays
  accurate; these are fixes to the same unreleased feature, so they ship under that entry.
- **D11. Settlement record.** The table above plus commit messages that name the thread id
  (`CodeRabbit discussion_r<id>`) settle the findings. No comments are posted on merged PR #5647.
