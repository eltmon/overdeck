## Glossary

- **Share service.** The Cloudflare Worker in `services/share/`. It runs the lobby and relays WebRTC signaling (SDP and ICE) between the host server and each viewer server. It never sees content.
- **Host socket.** The WebSocket the host's dashboard server holds to `GET /v1/rooms/:code/host?v=1`, owned by `ShareManager` (`src/dashboard/server/services/share-host.ts`). Slice 2 ignores its `signal` and `ice-servers` frames; this slice consumes them.
- **Host frame / service frame.** `HostFrame` (host → service) and `ServiceToHostFrame` (service → host) in `packages/contracts/src/sharing.ts`. This slice sends `signal` and `ice-servers` host frames and consumes `signal`, `ice-servers` and `error turn_unavailable` service frames.
- **Peer hub.** The new `PeerHub` class (`src/dashboard/server/sharing/peer-hub.ts`). One per live share. It holds one `RTCPeerConnection` per eligible viewer.
- **Viewer peer.** The far end of one peer connection. In production it is the viewer's browser (slice 4). In this slice's tests it is a second werift `RTCPeerConnection` (the **loopback viewer**).
- **Host-admitted set.** The peer hub's own `Set<number>` of GitHub ids that **this host process** admitted by sending an `admit` frame. It is the NFR-4 content gate. A room snapshot never adds to it.
- **Eligible viewer.** A GitHub id that is in the host-admitted set **and** appears in the latest room snapshot with `state: 'admitted'` and `connected: true`. Only eligible viewers get a peer connection.
- **Data channel labels.** The five labels `control`, `conversation`, `drafts`, `terminal`, `presence`. Every peer connection carries all five, ordered and reliable, created by the host before its offer.
- **Wire format.** The types that cross a data channel. They are defined for sharing and are never the internal `ChatMessage` / `PanRpcGroup` types.
- **Envelope.** `SharedEnvelope`: `{ v, ch, streamId, seq, t, payload }`. Every data-channel message is either one encoded envelope or one **fragment** of an encoded envelope.
- **Fragment.** `SharedChunk`: `{ v, chunk: { id, index, count }, data }`. An encoded envelope longer than `SHARE_MAX_MESSAGE_CHARS` is sent as `count` fragments in order on the same channel.
- **Stream.** One agent session inside a share. A v0 conversation share has exactly one stream, and its `streamId` is the conversation name (`ShareScope.conversationId`).
- **seq.** A per-peer-connection, per-channel, per-stream counter. The first envelope on a channel for a stream has `seq: 1`; each next one adds 1. Fragments do not consume a `seq`.
- **Hello.** `SharedHello`: `{ v, scopeKinds, scope }`. The first envelope each side sends on `control`, wrapped in an envelope with `payload: { kind: 'hello', hello }`.
- **Negotiated peer.** A peer whose viewer hello passed `negotiateHello`. The hub sends conversation and presence content only to negotiated peers.
- **Conversation bridge.** The new `ConversationBridge` class (`src/dashboard/server/sharing/conversation-bridge.ts`). One per peer hub. It parses the shared conversation's Claude JSONL once, watches it with `watchConversation`, and feeds every attached sink: a `history` payload on attach, then `append` and `update` payloads.
- **Sink.** One subscriber of the bridge: `{ send(payload: ConversationPayload): void }`. The hub attaches one sink per negotiated peer.
- **Channel writer.** The new `ChannelWriter` class (`src/dashboard/server/sharing/channel-writer.ts`). It sends one channel's envelopes in order, fragments long ones, and waits while the channel's `bufferedAmount` is high.
- **Spike.** The WebRTC dependency check that the parent PRD's decision rule asks for (*WebRTC dependency*).

## Problem

Slice 2 lets a host create a share and admit viewers, but nothing flows after admission. The host ignores the `signal` and `ice-servers` frames the share service relays, no peer connection exists, and there is no wire format for content. A viewer that is admitted receives `status admitted` and then nothing. Slice 4 (the viewer surface) cannot start until the host side can open data channels, speak a defined wire format, and stream the shared conversation.

## Scope

This issue is slice 3 of Shared Sessions v0. It delivers, on the host side only:

1. The content wire format types in `packages/contracts/src/sharing.ts` (type-only).
2. The wire format runtime in a new `packages/contracts/src/sharing-wire.ts` (mapping, envelope decode, fragments, `seq` gap detection, hello negotiation), so slice 4's browser viewer reuses the same code.

## Requirements

- **FR-1** `packages/contracts/src/sharing.ts` exports the wire format types `SharedChannel`, `SharedEnvelope`, `SharedChunk`, `SharedHello`, `SharedHelloError`, `ControlPayload`, `SharedMessage`, `ConversationPayload`, `SharedStream`, `PresenceParticipant`, `PresencePayload`, `DraftPayload`, and stays type-only and import-free.
- **FR-2** `toSharedMessage(message)` copies exactly the allow-listed fields (`id`, `role`, `text`, `createdAt`, and `turnId`, `completedAt`, `streaming`, `sequence` when present) and nothing else. It never sets `author`.
- **FR-3** `packages/contracts/src/sharing-wire.ts` provides envelope decoding, fragment encoding and reassembly, per-channel per-stream `seq` gap detection, and hello negotiation.
- **FR-4** The peer hub opens exactly one `RTCPeerConnection` per eligible viewer, creates the five labeled data channels (ordered, reliable) before its offer, and sends the offer and its ICE candidates as `signal` host frames.
- **FR-5** The peer hub opens no peer connection, sends no `signal` frame and sends no content for a GitHub id that is not in its host-admitted set, whatever the room snapshot says (NFR-4 of the parent PRD).
- **FR-6** ICE servers come from the share service (`ice-servers` host frame). `error turn_unavailable`, or no answer within 5 s, falls back to an empty list (host candidates only).
- **FR-7** Each side's first envelope on `control` is a hello. The hub sends conversation and presence content to a peer only after that peer's hello negotiates successfully; a failed negotiation answers with a `control` error payload and sends no content.
- **FR-8** On a negotiated peer, the conversation channel carries one `history` payload (the full message list), then `append` payloads for new message ids and `update` payloads for changed messages, in transcript order. Every envelope carries `streamId` equal to the conversation name.
- **FR-9** On a negotiated peer, the presence channel carries a `PresencePayload` when it opens and again after every room snapshot that changes the roster or the controller.
- **FR-10** `ShareManager` routes `signal`, `ice-servers` and `error turn_unavailable` service frames to the share's peer hub, tells the hub when it sends `admit`, `kick` or `revoke`, and closes the hub when the share ends or the host entry is dropped.
- **FR-11** Kick and revoke close that viewer's peer connection immediately. A viewer who disconnects from the share service loses its peer connection; when it reconnects (still admitted) the hub offers a new one with a fresh history.
- **FR-12** The spike result (werift kept or replaced, measured throughput, ordering result, browser interop result) is written into `.pan/drafts/pan-658.md` under *WebRTC dependency*.
- **NFR-1** `packages/contracts/src/sharing.ts` stays type-only with no `import` (D-R3-8 of the parent PRD): the share Worker imports it by relative path, and `npm run typecheck` (which runs `typecheck:share`) must stay green.
- **NFR-2** Delay-based tests (the 5 s ICE timeout) use `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()`. Real-UDP tests (loopback, Miniflare) use real timers and resolve every wait on an event or `vi.waitFor`; nothing sleeps a fixed time.
- **NFR-3** New modules are plain async TypeScript with injected seams (slice 2's D-8); no `execSync`; nothing logs signaling data, ICE credentials or content.
- **NFR-4** The `drafts` and `terminal` channels exist but carry nothing in this slice. The hub subscribes to inbound messages on `control` only; `terminal` has no inbound handler at all.
- **NFR-5** Outbound content is bounded: a channel writer waits while `bufferedAmount` is above 1 MiB, and a peer whose queued content passes 64 Mi characters is closed.
- **NFR-6** No file grows past its file-size ratchet: `share-host.ts` (416 lines now) and every new non-test file stay at or under 1000 lines.

## Decisions

Auto mode asked the operator nothing. Each decision below is final for this issue and is mirrored in the xBRIEF `plan.autoDecisions[]`.

- **D-1 werift stays the WebRTC stack; the spike measures, it does not choose.** `werift` 0.25.1 is already a production dependency (`package.json` line 204, `"werift": "0.25.1"`) used by Overdeck Anywhere's data-channel transport (`src/lib/anywhere/channel/rtc-transport.ts`), including relayed (TURN) routes. The spike (WI-3) runs the parent PRD's two checks (≥ 5 MB/s, 1000 ordered messages) on werift ↔ werift loopback, plus the one thing Anywhere never exercises: werift ↔ a real Chromium `RTCPeerConnection`. **Implementation checkpoint:** if werift ↔ werift is below 5 MB/s, keep werift anyway and record the number (a shared conversation is a few KB/s, so 5 MB/s is a ~1000× margin, and `@roamhq/wrtc` is a native addon that breaks `bun run` dev mode, against NFR-5 of the parent PRD). If the Chromium interop fails, record the failure and the error in `pan-658.md`, run `pan tell flywheel-orchestrator "PAN-4474: werift↔Chromium interop failed (<reason>); slice 4 (PAN-4475) is blocked on a WebRTC stack decision"`, and finish this slice on werift: the hub reaches werift only through `PeerHubDeps.createPeerConnection`, so a later swap is local.
- **D-2 Forced-TURN is not re-verified here.** The parent PRD's spike names "loopback + forced-TURN". A forced-TURN run needs real Cloudflare TURN credentials, which agents do not hold (deploy and secrets are operator-only). werift's TURN client already runs Anywhere's relay route in production (PAN-2356, PAN-4862), and forced-TURN verification for sharing is slice 11 ([PAN-4482](https://github.com/eltmon/overdeck/issues/4482)). The spike records this.
- **D-3 Runtime wire code lives in contracts, in its own file.** `sharing.ts` must stay import-free and type-only (parent D-R3-8). Slice 4's browser needs the same decoder, so the runtime goes in `packages/contracts/src/sharing-wire.ts`, exported from `packages/contracts/src/index.ts`. The share Worker never imports it. The server and the frontend both resolve `@overdeck/contracts` from source (`vitest.config.ts` line 24 alias, `tsdown.config.ts` line 36 alias).
- **D-4 The hello is wrapped in an envelope.** One decoder handles every message. The hello envelope has `ch: 'control'`, `streamId` = the conversation name, and the normal `seq` (1 for the host's first control envelope).
- **D-5 The viewer echoes the scope.** The PRD's `SharedHello` carries `scope` in both directions. A viewer does not know the scope before the host's hello (the share service sends viewers only `status`), so the viewer sends its hello after it receives the host's, with `scope` copied from it. `negotiateHello` checks that the two scopes are equal.
- **D-6 Content waits for the viewer's hello.** The host sends its hello when `control` opens and sends no conversation or presence envelope until the viewer's hello negotiates. There is no timeout: a peer that never sends a hello stays idle until it disconnects. This gives a later host the viewer's version before it chooses a format.
- **D-7 Version rule.** `negotiateHello(local, remote)` agrees on `min(local.v, remote.v)`. A remote `v` that is not a positive integer, or a remote that is not a hello shape, is `invalid_hello`. In this version every positive integer agrees on 1. Scope kinds must be supported on both sides, else `scope_kind_unsupported`. `version_unsupported` is reserved for a future minimum version; it is part of the type now so the error union does not change later.
- **D-8 Generic fragmentation, one history envelope.** History is one `history` envelope (the full list), as the parent PRD says ("progressive lazy-load is a future optimization"). Any encoded envelope longer than `SHARE_MAX_MESSAGE_CHARS = 32_768` characters is split into fragments; 32,768 UTF-16 code units are at most 96 KiB of UTF-8, below the 256 KiB `max-message-size` browsers advertise. This also covers one huge message in an `append`. An encoded envelope longer than `SHARE_MAX_ENVELOPE_CHARS = 32 * 1024 * 1024` is never sent: the hub sends `{ kind: 'unavailable', reason: 'history_too_large' }` instead.
- **D-9 History replaces, and it is the full transcript.** The initial parse is the `'claude-initial'` worker job, `parseEntireConversation(sessionFile, { flushPendingToolUse: false })` (`src/dashboard/server/services/dashboard-db-worker.ts` line 75; `parser.ts` line 703), which loops over 10 MB chunks to EOF. So `history` carries every message, not a window. A `history` payload always means "replace this stream's whole message list". The bridge sends it on attach and again after a genuine transcript reset (`gateSnapshotEmission` returns `snapshot: true`). A suppressed shrink is merged like a normal delta.
- **D-10 Append versus update.** The bridge keeps `Map<id, SharedMessage>` in transcript order. A delta message with a new id is `append`. A message whose id is known and whose mapped JSON changed is `update` (streaming assistant text). An unchanged known message sends nothing.
- **D-11 Claude JSONL transcripts only, no harness branch.** The bridge resolves the conversation's Claude session file the same way `ws-rpc.ts` does (lines 827–846: launcher-pinned session id, else `claudeSessionId`, `sessionFilePath(cwd, id)`, not a Pi session file). It does **not** require the file to exist: a conversation shared before its first prompt has a pinned id but no JSONL yet, and `parseEntireConversation` returns an empty result for a missing file while `watchConversation` polls until it appears, exactly as the dashboard's own conversation view does. Unknown conversation, no session id, or a Pi file → `{ kind: 'unavailable', reason: 'transcript_not_found' }`. A conversation on another harness whose `claudeSessionId` is empty gets `unavailable`; one whose `claudeSessionId` holds a foreign id resolves to a Claude path that never appears, so its viewers get an empty `history` that never grows (hazard, non-goal). The bridge does **not** compare `transcriptKind` or a harness name: `scripts/lint-harness-branches.sh` counts every such comparison against `scripts/harness-branches-baseline.txt` and fails a file with no row. For the same reason this slice neither extracts the resolver out of `ws-rpc.ts` nor adds a harness check to `POST /api/shares`.
- **D-12 The host-admitted set is fed only by the host's own commands.** `ShareManager.command` calls `hub.admit(id)` after it sends an `admit` frame and `hub.remove(id)` after `kick` or `revoke`. A snapshot can only remove ids: when a snapshot lists no participant with that id at all, the id leaves the set (the viewer left, was kicked or revoked). A snapshot showing an id in `lobby` does not remove it, because a snapshot sent before the service processed the `admit` can still be in flight. Re-park after a restart, which must seed the set from the snapshot, is slice 8.
- **D-13 Peer lifetime follows eligibility.** On every snapshot the hub reconciles: an eligible viewer with no peer gets one; a peer whose viewer is no longer eligible (disconnected, kicked, revoked, left) is closed. A peer whose `connectionState` becomes `failed` or `closed` is removed, and the next snapshot that still shows the viewer eligible creates a new one. A viewer that needs a fresh offer (slice 4 browser reload) closes its join socket, waits until it observes that socket's `close` event, and only then opens a new one; the snapshot flips `connected` false then true. Opening the new socket first does not work: the share service replaces the old socket with close 4008 and never marks the viewer disconnected, so no flip happens.
- **D-14 The host always offers.** An inbound `signal` with `sdp.type: 'offer'` is ignored. Inbound signals from a GitHub id with no peer are ignored.
- **D-15 Host-socket loss keeps established peers.** Slice 2 never reconnects the host socket (its D-1). When it drops (`disconnect`), established peer connections stay up: content is peer-to-peer, and the host-admitted set is still valid. Consequence: if the host never returns, the service ends the room after 5 minutes, but the host keeps streaming to peers it already has. Each viewer's join socket closes 4004 at that point, and slice 4 must tear down its peer connection on that close; slice 8 reconciles the host side. The hub closes only when the host entry is dropped: `end`, close 4004, a 404/401 upgrade, a stale record replaced by `create`, or `stop()`.
- **D-16 ICE servers.** The hub sends `{ type: 'ice-servers' }` once and shares the in-flight request across peers. A successful list is cached for 50 minutes (credentials live 3600 s). `error turn_unavailable` or 5 s without an answer resolves to `[]` and is not cached. The list is passed to werift unchanged (no TURN URL reordering; see hazard H-4).
- **D-17 Presence follows the parent PRD's type, with numeric ids.** `PresencePayload` lists the data owner first (`isHost: true`, `state: 'admitted'`, `contributor: false`), then every snapshot participant (lobby and admitted, `isHost: false`), and one `streams` entry. GitHub ids are `number` (the parent PRD sketched `string`; `RoomSnapshot` uses `number`, and one type avoids conversion bugs). The block list is never sent.
- **D-18 Stream label.** `streams[0].label` is the conversation title, else the conversation name, resolved once per hub through `PeerHubDeps.streamLabel()`. A failed lookup uses the name.
- **D-19 Plain async, no new error tags.** Slice 2's D-8 and D-9 apply: plain classes with injected seams, string error codes, no `src/lib/errors.ts` tags (the parent PRD's `WebRtcError` is not added because nothing runs in an Effect error channel).
- **D-20 Module location.** New modules go under `src/dashboard/server/sharing/`, the path the issue names. `share-host.ts` stays in `services/` (slice 2).
- **D-21 Work log is not shared.** The allow-list is `SharedMessage` only. Tool calls, thinking, plans, cost and context usage never cross the wire in v0.

## Design

### Wire format types (`packages/contracts/src/sharing.ts`, appended; still type-only, no `import`)

Replace the header sentence "The content wire format (SharedEnvelope and friends) is not here: the share service never carries content. Slice 3 (PAN-4474) adds it." with "The content wire format (PAN-4474, slice 3) is at the end of this file; the share service never carries it. Its runtime helpers are in `sharing-wire.ts`, which the Worker never imports." Then append:

```ts
// ── Content wire format (PAN-4474, slice 3): host server ⇄ viewer over WebRTC data channels. ──
// The share service never carries these. Runtime helpers live in ./sharing-wire.ts.

/** The five data channel labels. Every peer connection carries all five, ordered and reliable. */
export type SharedChannel = 'control' | 'conversation' | 'drafts' | 'terminal' | 'presence';

/** One data-channel message. `v` is 1 in this version; a later host may send more. */
export interface SharedEnvelope<P = unknown> {
  readonly v: number;
  readonly ch: SharedChannel;
  /** The member session; v0: always the shared conversation's name. */
  readonly streamId: string;
  /** Per peer connection, per channel, per stream: 1, 2, 3, … Fragments do not consume one. */
  readonly seq: number;
  /** Host epoch ms. */
  readonly t: number;
  readonly payload: P;
}

/** One piece of an encoded envelope longer than SHARE_MAX_MESSAGE_CHARS, sent in order on the same channel. */
export interface SharedChunk {
  readonly v: number;
  readonly chunk: { readonly id: number; readonly index: number; readonly count: number };
  readonly data: string;
}
```

```ts
export const SHARED_WIRE_VERSION = 1;
export const SHARED_SCOPE_KINDS: readonly ShareScope['kind'][] = ['conversation'];
export const SHARED_CHANNELS: readonly SharedChannel[] = ['control', 'conversation', 'drafts', 'terminal', 'presence'];
export const SHARE_MAX_MESSAGE_CHARS = 32_768;
export const SHARE_MAX_ENVELOPE_CHARS = 32 * 1024 * 1024;

export function toSharedMessage(message: ChatMessage): SharedMessage;
export function decodeEnvelope(value: unknown): SharedEnvelope | null;
export function encodeSharedMessage(envelope: SharedEnvelope, chunkId: number): string[];
export class SharedChannelReader { read(text: string): SharedReadResult }
export type SharedReadResult =
  | { readonly kind: 'envelope'; readonly envelope: SharedEnvelope }
  | { readonly kind: 'pending' }
  | { readonly kind: 'invalid'; readonly reason: 'not_json' | 'not_envelope' | 'chunk_out_of_order' | 'too_large' };
export class SeqTracker {
  observe(ch: SharedChannel, streamId: string, seq: number): { readonly ok: true } | { readonly ok: false; readonly expected: number; readonly got: number };
}
export function negotiateHello(local: SharedHello, remote: unknown):
  | { readonly ok: true; readonly v: number }
  | { readonly ok: false; readonly code: SharedHelloError };
```

Rules:

- `toSharedMessage`: build a new object field by field. Always copy `id`, `role`, `text`, `createdAt`. Copy `turnId` and `completedAt` only when `typeof … === 'string'`, `streaming` only when boolean, `sequence` only when a finite number. Never spread the input. Never set `author`.
- `decodeEnvelope(value)`: `null` unless `value` is an object with `v` a positive safe integer, `ch` one of `SHARED_CHANNELS`, `streamId` a non-empty string, `seq` a positive safe integer, `t` a finite number, and an own `payload` key. Returns a new object with exactly those six keys.
- `encodeSharedMessage(envelope, chunkId)`: `text = JSON.stringify(envelope)`. `text.length > SHARE_MAX_ENVELOPE_CHARS` → throw `RangeError('shared envelope too large')`. `text.length <= SHARE_MAX_MESSAGE_CHARS` → `[text]`. Otherwise `count = Math.ceil(text.length / SHARE_MAX_MESSAGE_CHARS)` and return `count` strings `JSON.stringify({ v: SHARED_WIRE_VERSION, chunk: { id: chunkId, index: i, count }, data: text.slice(i * MAX, (i + 1) * MAX) })`. (Slicing can split a UTF-16 surrogate pair across fragments; the receiver joins the slices before `JSON.parse`, so the pair is whole again.)
- `SharedChannelReader.read(text)`: `JSON.parse` failure → `invalid not_json`. An object with a `chunk` key is a fragment: `index`/`count` non-negative safe integers with `index < count`, `count * SHARE_MAX_MESSAGE_CHARS <= SHARE_MAX_ENVELOPE_CHARS + SHARE_MAX_MESSAGE_CHARS` (else `too_large`), `data` a string. The first fragment of a new `id` must have `index: 0`; each next fragment must have the same `id` and `count` and `index` = previous + 1, else `chunk_out_of_order` and the partial buffer is dropped. A non-final fragment → `pending`. The final fragment → join, `JSON.parse`, `decodeEnvelope`. A non-fragment object → `decodeEnvelope`. A `null` decode → `invalid not_envelope`.
- `SeqTracker.observe`: keyed by `ch + '\n' + streamId`; the expected value starts at 1; `seq === expected` → `ok` and expected becomes `seq + 1`; otherwise `{ ok: false, expected, got: seq }` and expected becomes `seq + 1` (so one gap is reported once).
- `negotiateHello(local, remote)`, in this order: `remote` is not an object, or `v` is not a positive safe integer, or `scopeKinds` is not an array of strings, or `scope` is not `{ kind: string, conversationId: string }` → `invalid_hello`. `v = Math.min(local.v, remote.v)`; `v < 1` → `version_unsupported`. `remote.scopeKinds` lacks `local.scope.kind`, or `local.scopeKinds` lacks `remote.scope.kind` → `scope_kind_unsupported`. `remote.scope.kind !== local.scope.kind` or `remote.scope.conversationId !== local.scope.conversationId` → `invalid_hello`. Else `{ ok: true, v }`.

### Channel writer (`src/dashboard/server/sharing/channel-writer.ts`, new)

```ts
export const WRITER_HIGH_WATER_BYTES = 1024 * 1024;
export const WRITER_LOW_WATER_BYTES = 256 * 1024;
export const WRITER_MAX_QUEUED_CHARS = 64 * 1024 * 1024;

/** The part of a werift RTCDataChannel the writer uses; tests supply a fake. */
export interface WritableDataChannel {
  readonly readyState: string;
  readonly bufferedAmount: number;
  bufferedAmountLowThreshold: number;
  send(data: string): void;
  readonly bufferedAmountLow: { subscribe(listener: () => void): { unSubscribe(): void } };
}

export class ChannelWriter {
  constructor(channel: WritableDataChannel, onOverflow: () => void);
  /** Encodes and queues one envelope; throws RangeError when it is over SHARE_MAX_ENVELOPE_CHARS. */
  send(envelope: SharedEnvelope): void;
  close(): void;
}
```

- The constructor sets `channel.bufferedAmountLowThreshold = WRITER_LOW_WATER_BYTES`.
- `send` calls `encodeSharedMessage(envelope, ++this.chunkId)` (a `RangeError` propagates and nothing is queued), appends the parts to a FIFO queue, adds their lengths to `queuedChars`, and calls `flush()`. If `queuedChars > WRITER_MAX_QUEUED_CHARS` after appending, the writer closes itself and calls `onOverflow()` once.
- `flush()`: while the queue is not empty, the channel is `open`, and `bufferedAmount <= WRITER_HIGH_WATER_BYTES`, shift one part and `channel.send(part)`. If it stops because of the high-water mark, subscribe once to `bufferedAmountLow` and flush again when it fires. A `send` that throws closes the writer.
- `close()`: drop the queue, unsubscribe, ignore later `send` calls.

Behavior:

- **Lazy start, shared.** The first `attach` starts the bridge (`resolveSessionFile`, then `parseInitial`), stored as one promise; concurrent `attach` calls await the same promise. A start that resolves to no file, or whose `parseInitial` throws, sends `{ kind: 'unavailable', reason: 'transcript_not_found' }` to each waiting sink, returns a no-op detach, and clears the stored start so the next `attach` tries again.

- **Attach.** After the start resolves: add the sink, then synchronously `sink.send({ kind: 'history', messages: [...messages.values()] })`. Both happen in the same turn, so no live payload can arrive between them.
- **Watch.** Started once per successful start: `deps.watch(file, onResult, { byteOffset: initial.byteOffset, priorState: parseStateFromSnapshot(initial) })`.

- **Errors.** A sink whose `send` throws is removed; the others continue. Nothing logs.
