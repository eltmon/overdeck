# PAN-5587 — Antigravity harness: run Gemini models through `agy acp` (API key and Agent Platform auth only)

**Issue:** [PAN-5587](https://github.com/eltmon/overdeck/issues/5587)
**Status:** planned 2026-11-21 (auto planning, high effort). Base commit `83bda8904e4`.
**Precedent:** Grok Build harness ([PAN-5078](https://github.com/eltmon/overdeck/issues/5078), commit `7fb68257448`, PRD `.pan/drafts/PAN-5078.md`). This PRD follows that PRD's structure and reuses its patterns; where Antigravity differs, the decision below says why.
**Related:** [PAN-5586](https://github.com/eltmon/overdeck/issues/5586) (registers `gemini-4-carbon`, `gemini-4-neon`, `gemini-4-hydrogen`; open at planning time), [#752](https://github.com/eltmon/overdeck/issues/752) (OAuth question; left to the operator).

## Glossary

- **Antigravity CLI / `agy`** — Google's closed-source agent CLI. Installed on the reference host during planning: `agy 1.5.14` at `/home/eltmon/.local/bin/agy` (273 MB native binary). Install: `curl -fsSL https://antigravity.google/cli/install.sh | bash` (downloads a manifest, checks SHA512, copies to `~/.local/bin/agy`, then runs `agy install`, which appends `export PATH="$HOME/.local/bin:$PATH"` to `~/.bashrc`). Update: `agy update`. It also self-updates in the background.
- **Antigravity desktop app** — a separate VS Code-based app at `/usr/bin/antigravity` (version 1.107.0 here). It is **not** the CLI. Overdeck resolves only the `agy` binary.
- **`agy acp`** — the persistent ACP stdio server mode of `agy` (`agentInfo.name: "Antigravity ACP Server"`).
- **ACP** — Agent Client Protocol, JSON-RPC 2.0 over stdio (`initialize`, `authenticate`, `session/new`, `session/load`, `session/prompt`, `session/set_config_option`, `session/request_permission`, `session/update`). Overdeck's client: `packages/effect-acp` plus `src/lib/acp/session-runtime.ts`.
- **ACP host** — `dist/acp-host.js` built from `src/lib/acp/host.ts`: the per-agent Node process Overdeck runs in a terminal pane. It spawns the ACP agent binary, owns the ACP session, listens on a Unix socket, and writes the Overdeck transcript `~/.overdeck/agents/<id>/acp-session.jsonl`.
- **ACP provider** — the key into `ACP_PROVIDER_SUPPORT` (`src/lib/acp/providers.ts`). Today: `opencode`, `opencode-go`, `kimi`, `grok`. This issue adds **`antigravity`**. The launcher passes it to the host as `--provider`.
- **Harness** — the `Harness` union in `packages/contracts/src/types.ts` line 92. This issue adds the literal **`antigravity`** (display name "Antigravity").
- **Google provider** — the existing Overdeck model provider `google` (`src/lib/providers.ts` line 156, `defaultHarness: 'pi'`, API key `api_keys.google`, exported as `GEMINI_API_KEY`). **Antigravity adds no model provider.** It is a second harness for some existing Google model ids.
- **Antigravity model** — an Overdeck Google model id that `agy` also serves, listed in `ANTIGRAVITY_MODEL_IDS` (WI-2) with the value `agy` accepts for `session/set_config_option configId=model`.
- **Thought level** — `agy`'s ACP config option `thought_level` (category `thought_level`), which holds the reasoning effort. Its allowed values depend on the model.
- **Gemini dir** — the directory `agy` uses instead of `~/.gemini`, set with `agy acp --gemini-dir <abs path>`. Overdeck uses `<OVERDECK_HOME>/antigravity` (default `~/.overdeck/antigravity`). `agy` then keeps its conversations at `<gemini dir>/antigravity-cli/conversations/<sessionId>.db` and logs at `<gemini dir>/antigravity-cli/log/acp-server-*.log`.
- **Antigravity credential** — what Overdeck hands `agy` for one launch: the auth method id (`gemini-api-key` or `agent-platform`) plus the env vars that method needs (WI-4).
- **OAuth methods** — `oauth-personal`, `oauth-business` and `terminal-login`. Overdeck never selects them (D3).
- **Turn usage** — the ACP-standard `usage` object on the `session/prompt` result (`inputTokens`, `outputTokens`, `cachedReadTokens`, `cachedWriteTokens`, `thoughtTokens`, `totalTokens`).
- **No-loss audit** — `tests/unit/lib/prime-agent-no-loss-audit.test.ts`: checks that every harness in `KNOWN_HARNESSES` reaches every harness surface.
- **File-size ratchet** — `scripts/lint-file-size.sh`: a `src/**/*.ts(x)` file over 1000 lines may not exceed its `origin/main` line count (or its `scripts/file-size-allowlist.txt` row). A file at or under 1000 may grow to 1000.
- **Effort lint** — `scripts/lint-effort.sh` (`npm run lint:effort`): a shrink-only ratchet that fails when a non-excluded source file adds an effort-level list literal (patterns such as `['low', 'medium'` or `'low' | 'medium'`). `packages/contracts/src/harness-behavior.ts`, `src/lib/model-capabilities.ts` and `src/lib/model-capability-additions.ts` are excluded.

## Problem

Overdeck runs Gemini models only through `pi` (the Google provider default) or other API-key harnesses. Google's own agent CLI is Antigravity: Gemini CLI handed its consumer users to Antigravity on 2026-06-18 (https://github.com/google-gemini/gemini-cli/discussions/27274). An operator cannot run an Overdeck conversation or agent on Gemini inside Google's own agent loop, the way `grok` and `codex` run on their vendors' CLIs.

Antigravity's terms, clause 6 (https://antigravity.google/terms/), say that "Using third party software, tools, or services to access the Service" with Antigravity OAuth "is a breach of this Agreement", and that it may lead to suspension of Antigravity and Gemini CLI accounts. Users report bans. So Overdeck must run `agy` only with a Gemini API key or Agent Platform (formerly Vertex AI) credentials.

## Empirical findings (probed 2026-11-21 against `agy 1.5.14`)

All probes used a hand-written ACP client (`node probe.mjs`) in the planning session scratchpad, a throwaway cwd, and the Gemini API key from `~/.overdeck/config.yaml` `api_keys.google`. The key was never printed. Findings the plan relies on:

1. **`agy acp --help`** lists: `--add-dir`, `--agent`, `--app-data-dir`, `--dangerously-skip-permissions`, `--disable-telemetry`, `--gemini-dir` ("Path where Gemini files are stored (default .gemini)"), `--include-default-customizations`, `--log-file`, `--login` ("Log in with Google interactively, then exit"), `--process-per-session`, `--sandbox`, `--stdio` (default), `--worker`.
2. **`initialize`** returns `protocolVersion: 1`, `agentInfo { name: "Antigravity ACP Server", version: "1.5.14" }`, `agentCapabilities.loadSession: true`, `sessionCapabilities { resume, close, load, list, additionalDirectories }`, `promptCapabilities { image: true, audio: false, embeddedContext: true }`, `_meta.antigravity { tier: true, systemPrompt: { append: true } }`, and no `mcpCapabilities` (stdio MCP only). `authMethods` ids: `oauth-personal`, `oauth-business`, `gemini-api-key` ("Use an API key with Gemini Developer API"), `agent-platform` ("Use Gemini Enterprise Agent Platform (formerly Vertex AI) with Application Default Credentials"). `terminal-login` is not advertised to a client without terminal capability.
3. **`authenticate { methodId: "gemini-api-key" }`** with `GEMINI_API_KEY` in the child env returns `{}`. No `modelProvider` setting was needed (the install docs claim one is; the live run shows otherwise). `authenticate` does **not** validate the key: with a bogus key it still returns `{}`, and the first prompt then streams one `agent_message_chunk` with text `⚠ agent executor error: generating and executing: Error 400, Message: API key not valid. …` and ends `stopReason: "end_turn"` with **no** `usage`.
4. **`session/new`** returns `sessionId`, `models.availableModels` (effort-suffixed ids such as `gemini-4-argon-high`), `modes`, and `configOptions`:
   - `{ id: "model", category: "model", type: "select", currentValue: "gemini-3.1-pro", options: gemini-4-neon | gemini-4-carbon | gemini-4-hydrogen | gemini-4-argon | gemini-3.8-flash | gemini-3.7-flash | gemini-3.6-flash | gemini-3.1-pro }`
   - `{ id: "thought_level", category: "thought_level", type: "select" }` whose values depend on the model: `gemini-3.1-pro` low/high; `gemini-4-argon`, `gemini-4-carbon`, `gemini-3.8-flash`, `gemini-3.7-flash`, `gemini-3.6-flash` low/medium/high; `gemini-4-neon`, `gemini-4-hydrogen` low/medium/high/xhigh. No model offers `max`.
   - `{ id: "mode", options: default | accept-edits | plan }` (`default`: "Ask before edits and commands, per your permission settings.").
   - Overdeck's `setModel` sends `session/set_config_option { configId: "model", value }` (`session-runtime.ts` line 795, `setConfigOption(started.modelConfigId ?? "model", model)`) and refreshes its cached `configOptions` from the response, so the `thought_level` values the host reads after `setModel` are the new model's.
5. **Turn usage** is the ACP-standard `usage` on the `session/prompt` result, per turn, summed over the turn's model calls. `inputTokens` **excludes** cache reads; `outputTokens` **includes** thought tokens. Evidence: a tool-using turn returned `{ inputTokens: 12101, outputTokens: 117, cachedReadTokens: 7739, cachedWriteTokens: 0, thoughtTokens: 0, totalTokens: 19957 }` (12101 + 7739 + 117 = 19957; its two `usage_update.used` values were 9867 and 10090, summing to 19957). A thinking turn returned `{ inputTokens: 9700, outputTokens: 123, thoughtTokens: 122, totalTokens: 9823 }`. Two prompts in one process returned 9301 then 2116 uncached + 7257 cached input (not cumulative). No cost and no model id are reported.
6. **Resume:** a fresh `agy acp` process accepted `session/load { sessionId, cwd, mcpServers: [] }`, replayed the history as `user_message_chunk` / `agent_message_chunk` updates, and answered a follow-up that depended on the earlier turn. **After `session/load` the model resets to the default `gemini-3.1-pro`** (unlike Grok, which kept the session's model).
7. **Permissions:** tool calls arrive as `session/request_permission` with options `[{ optionId: "allow", kind: "allow_once" }, { optionId: "deny", kind: "reject_once" }]`, for both an MCP tool and `run_command`. The host's existing `selectAutoPermissionOutcome` (`src/lib/acp/permissions.ts`) picks `allow_once`. No skip-permissions flag is needed.
8. **MCP via ACP:** a stdio MCP server passed in `session/new.mcpServers` (`{ name, command: "node", args, env: [] }`) worked: the agent called it as tool `mcp_probe_ping` and returned its output. So the existing PAN-4934 path (`readAcpMcpServers`, `src/lib/acp/mcp-config.ts`) delivers the managed `overdeck` MCP server.
9. **Isolation:** with `--gemini-dir <scratch>/iso`, a valid key answered normally, and `agy` wrote only under that directory (`iso/antigravity-cli/…`, `iso/config/…`). A bogus key failed the turn as in finding 3. The operator's `~/.gemini/` holds Gemini CLI's `oauth_creds.json` and a `settings.json` with `security.auth.selectedType: "oauth-personal"`. Before isolation was tested, five valid-key probe turns (findings 3–8) ran against the **default** `~/.gemini` directory, with Gemini CLI's `oauth_creds.json` present. Each selected `gemini-api-key` explicitly and returned API-key-style usage, but nothing in the output proves which credential served them. Those probes left conversations under `~/.gemini/antigravity-cli/` (session ids `afd75d7c-…`, `550d3c05-…`, `e6a12879-…`). The planner deliberately did **not** run a missing-key or bogus-key probe against the default directory, because a silent fallback there would itself be a third-party OAuth use on the operator's account.
10. **No GCP setup on the reference host:** no `gcloud`, no `~/.config/gcloud/application_default_credentials.json`. `agent-platform` could not be probed live.

## Decisions

- **D1 — New harness literal `antigravity` on the ACP host** (the OpenCode/Grok pattern), display name **"Antigravity"**, executable `agy`, ACP provider key `antigravity`. Same reasons as PAN-5078 D1: per-harness binary, capabilities, policy and picker entries.
- **D2 — No new model provider; bare Google ids.** The harness runs existing Google provider ids (`gemini-4-argon`, …). Rejected alternative: a Grok-style `antigravity/<id>` provider. Reason: with `gemini-api-key` auth, `agy` bills the same Gemini API key the `google` provider already uses, so the same id, the same pricing row and the same key are correct; the issue's acceptance text also names bare ids (`gemini-4-argon`, `gemini-4-carbon`) and asks for Antigravity "as a harness for Google models". Consequence: the harness cannot be derived from the model id, so the resolved harness must be passed into `getAcpLauncherFields` (WI-7).
- **D3 — Auth allowlist: `gemini-api-key` and `agent-platform` only.** `resolveAntigravityAuthMethodId` returns only one of those two ids, and only when `initialize.authMethods` advertises it. It never returns `oauth-personal`, `oauth-business` or `terminal-login`, and Overdeck never passes `--login`. If no credential resolves, the launch fails with `ANTIGRAVITY_AUTH_REQUIRED` (WI-4), which names both supported setups and the ToS reason.
- **D4 — Credential resolution order** (first match wins; values are never logged or put in messages):
  1. Overdeck `config.apiKeys.google` → `gemini-api-key`. `src/lib/config-yaml/merge.ts` lines 367–373 set `apiKeys.google` **only when the Google provider is enabled** (`models.providers.google: true` or `{ enabled: true, api_key }`; the legacy `api_keys.google` is the fallback key). So the operator enables the Google provider and gives it a key in Settings. On the reference host `models.providers.google` is `false`, so this source is empty there until it is enabled.
  2. A value that is still an unresolved env reference (matches `/\$\{?[A-Z_][A-Z0-9_]*\}?/`) is **not** a key: `resolveEnvVar` (`merge.ts` line 83) keeps `$NAME` when the variable is unset, and agent panes blank provider variables (`PROVIDER_ENV_KEYS`, `src/lib/child-env.ts` line 24, includes `GEMINI_API_KEY`). The resolver throws `` `The Google API key in Overdeck config is an environment reference (${value}) that agent panes do not receive. Put the literal key in Settings → Google.` `` (the reference text is a variable name, not a secret).
  3. Agent Platform: project = env `GOOGLE_CLOUD_PROJECT` else `gcp.project` in `<gemini dir>/antigravity-cli/settings.json`; location = env `GOOGLE_CLOUD_LOCATION` else `gcp.location` there; ADC = the file named by env `GOOGLE_APPLICATION_CREDENTIALS`, else `~/.config/gcloud/application_default_credentials.json`. All three present → `agent-platform`. `GOOGLE_CLOUD_*` are not in `PROVIDER_ENV_KEYS`, so a pane sees them only if the terminal backend's environment has them; the settings file is the reliable path. Whether `agy` reads `settings.json` from the isolated gemini dir is **unverified** (D18).
  4. Otherwise → throw `AntigravityCredentialError(ANTIGRAVITY_AUTH_REQUIRED)`.
  An API key wins over Agent Platform when both exist. There is deliberately **no** env `GEMINI_API_KEY` source: the dashboard process might have one while every agent pane has it blanked, so the picker and doctor would say "ready" for a launch that cannot see the key. The picker and doctor (`readAntigravityAuthStatus`) and the host (`resolveAntigravityCredential`) call the same rules.
- **D5 — The ACP host resolves the credential, not the launcher.** The host's `main()` awaits `support.resolveCredential()` (plain `await`, before `support.makeRuntime`) and passes the result as `input.credential`; `makeAntigravityAcpRuntime` puts its env vars only in the `agy` child env. Because the failure is a plain rejected promise in `main()`, its message reaches `acp-launch-error` unwrapped. `acp-host` is a tsdown entry (`tsdown.config.ts` line 18, `'acp-host': 'src/lib/acp/host.ts'`); `src/lib/prime-agent/provider-map.ts` already imports `loadConfigNoMigration` from `../config-yaml.js` in launch code, and `npm run lint` (`lint:circular`) must stay green after WI-4/WI-5. Rejected alternative: Prime Agent's `paneEnv` + `preserveProviderEnv` (`src/lib/prime-agent/launcher-fields.ts`). Reasons: the host is Overdeck code and can read the config itself; the key never enters a pane env or launcher script; and the alternative edits five launch sites, two of them over the file-size ceiling (`src/lib/agents/spawn.ts` 1088 lines, `src/lib/overdeck/conversation-runtime.ts` 1224). A credential failure before the host constructs `AcpHost` must still reach the operator: WI-6 writes `acp-launch-error` from `main()`, which `waitForHostReady` (`src/lib/agents/runtime-command.ts` line 502) already reads.
- **D6 — Isolated Gemini dir.** Every launch passes `--gemini-dir <OVERDECK_HOME>/antigravity` (absolute). `agy` then never reads `~/.gemini/oauth_creds.json`, `~/.gemini/settings.json` (`selectedType: oauth-personal`), the operator's `agy` MCP servers, hooks or skills. This is a structural guard for D3 (finding 9). Sessions persist in that directory, so resume works across processes. Operator `agy` customizations do not apply to Overdeck agents (documented).
- **D7 — Spawn input:** command = resolved `agy` path (else `agy`), args `["acp", "--gemini-dir", <gemini dir>]`, env = caller env with `GOOGLE_API_KEY`, `GEMINI_API_KEY`, `GOOGLE_CLOUD_PROJECT` and `GOOGLE_CLOUD_LOCATION` deleted, then the credential's env vars added. No `--dangerously-skip-permissions` (finding 7). No `--disable-telemetry`, `--sandbox`, `--process-per-session` or `--login`.
- **D8 — Models:** `ANTIGRAVITY_MODEL_IDS: Readonly<Partial<Record<GoogleModel, string>>>` maps an Overdeck id to the `agy` model value. At planning time: `gemini-4-argon` → `gemini-4-argon`, `gemini-3.8-flash` → `gemini-3.8-flash`, `gemini-3.6-flash` → `gemini-3.6-flash`, `gemini-3.1-pro-preview` → `gemini-3.1-pro` (`agy` lists it as "Gemini 3.1 Pro"; Overdeck's id for that model is the API id). Rule for the implementer: if `git grep -n "'gemini-4-carbon'" src/lib/settings.ts` finds the id (PAN-5586 landed), also add `gemini-4-neon`, `gemini-4-carbon` and `gemini-4-hydrogen` with identical values. Otherwise post one comment on PAN-5586 asking its implementer to add those three rows to `ANTIGRAVITY_MODEL_IDS` in `src/lib/antigravity-models.ts`. `gemini-3.7-flash` is not an Overdeck id and stays out. Other Google ids (`gemini-3.5-flash-lite`, `gemini-3-flash-preview`, `gemini-3.1-flash-lite`, …) are not served by `agy` and stay out.
- **D9 — Policy:** `canUseHarness('antigravity', m)` allows exactly the `ANTIGRAVITY_MODEL_IDS` keys; any other model is denied with `ANTIGRAVITY_MODEL_BLOCK_REASON` = `` `Antigravity runs only the Gemini models its CLI serves: ${ids.join(', ')}. Select one of them, or another harness for this model.` ``. Google models on other harnesses are unchanged; `acp` stays Kimi-only.
- **D10 — No hardcoded model fallback.** A launch without a model throws `Antigravity requires an explicit model` (mirrors `Grok Build requires an explicit model`, `src/lib/runtimes/acp.ts` line 179). The default `gemini-3.1-pro` of `agy` is never relied on; the host always sets the model, including after `session/load` (finding 6).
- **D11 — Effort:** `ANTIGRAVITY_BEHAVIOR.effortLevels = ["low", "medium", "high", "xhigh"]`, so `clampEffort` maps `max` → `xhigh`, and `resolveEffort` clamps to model ∩ harness levels (`src/lib/agents/resolve-effort.ts`). Default stays `high` (effort-high-default rule). After `setModel`, the host reads the `thought_level` option's live values and sends `clampAntigravityThoughtLevel(effort, values)`: the requested level if offered; else the highest offered level ranked below it in `EFFORT_LEVELS`; else the lowest offered level. Example: `medium` on `gemini-3.1-pro` → `low`; `xhigh` on `gemini-4-argon` → `high`. The ranking imports `EFFORT_LEVELS` from `@overdeck/contracts`; no new effort-level list literal appears outside the effort-lint exclusions.
- **D12 — Cost:** the host copies Antigravity turn usage onto the `turn_completed` transcript entry with `model` = the Overdeck model id the host launched with and `source: "antigravity"`. Mapping: `inputTokens` → `inputTokens` (already uncached), `cachedReadTokens` → `cacheReadTokens`, `cachedWriteTokens` → `cacheWriteTokens`, `outputTokens` → `outputTokens` (includes thought tokens, which Gemini bills as output), `thoughtTokens` → `reasoningTokens`. No `costUsd`. A new `antigravity` reconcile source imports one cost event per turn, priced with `getPricing('google', model)` from `src/lib/cost.ts` (the `google` rows, lines 165–173). The numbers are estimates at Gemini API list prices: free-tier usage and Agent Platform contract pricing are not modeled. The docs and the PR say so. Turns without `usage` (finding 3) produce no cost event.
- **D13 — Picker:** the settings model catalog appends, to the `google` group, one extra row per Google row whose id is an Antigravity model: label `` `${baseName} — Antigravity` ``, `harness: 'antigravity'`, `effortLevels` = the row's capability levels filtered to `ANTIGRAVITY_BEHAVIOR.effortLevels`. It does this only when `resolveHarnessBinary('antigravity')` finds `agy` **and** `readAntigravityAuthStatus().ready` is true; otherwise it adds nothing. The plain Google rows are unchanged. The shared harness picker (`HARNESS_OPTIONS`) lists Antigravity; its policy decision enables it only for Antigravity models.
- **D14 — Transcripts:** Overdeck records the transcript from the ACP stream into `acp-session.jsonl`, the same as every ACP harness, and renders it with the ACP transcript adapter. It never reads `agy`'s private `<gemini dir>/antigravity-cli/conversations/*.db`.
- **D15 — Session index harness:** the host records `harness: "antigravity"` for provider `antigravity` (via the provider support entry's `harness` field, `src/lib/acp/host.ts` line 206, `harness: support.harness ?? "acp"`).
- **D16 — Harness-name branch ratchet:** `scripts/lint-harness-branches.sh` pattern `N` does not list `antigravity`, and this issue does not add it. New behavior prefers the provider support table and capability fields; `=== 'antigravity'` comparisons are allowed only in harness lists/allowlists that already enumerate `'grok'`, in `canUseHarness`, and in the two launcher-field lines of WI-7.
- **D17 — Scope stays one issue** (`plan.metadata.sizeJustification`), following PAN-5078 D15 and PAN-3668: a `Harness` literal forces coordinated edits across contracts, `src/lib`, CLI, server and frontend, and a selectable-but-unlaunchable harness delivers zero value. The work is decomposed into 23 small items with real dependency edges.
- **D18 — `agent-platform` is implemented and unit-tested but not live-verified** on the reference host (finding 10). The docs say "not verified live"; WI-23 records an implementation checkpoint.

## Requirements

### Functional

- **FR-1** `antigravity` is a member of `Harness`, `RuntimeName` and `KNOWN_HARNESSES`, with `ANTIGRAVITY_BEHAVIOR` (display name "Antigravity", executable `agy`) and `ANTIGRAVITY_CAPABILITIES`.
- **FR-2** `canUseHarness('antigravity', m)` allows exactly the `ANTIGRAVITY_MODEL_IDS` keys and denies every other model with the D9 reason. Other harnesses' decisions for Google models are unchanged.
- **FR-3** The ACP host launches `agy acp --gemini-dir <OVERDECK_HOME>/antigravity` for provider `antigravity`, authenticates with `gemini-api-key` or `agent-platform` per D4, and never with an OAuth method.
- **FR-4** The host sets `model` to the translated `agy` value and `thought_level` to the D11-clamped effort, on fresh starts and after `session/load`.
- **FR-5** `pan start <issue> --harness antigravity --model gemini-4-argon`, a dashboard/REST conversation create with harness `antigravity`, and a planning session with `harness: antigravity` all launch the ACP host with `--provider antigravity`.
- **FR-6** A restart or resume of an Antigravity agent or conversation passes the recorded `acp-session-id` as `--resume`, and the host issues `session/load` with it.
- **FR-7** The managed `overdeck` MCP server reaches Antigravity sessions through `session/new` / `session/load` `mcpServers` (`ANTIGRAVITY_CAPABILITIES.overdeckMcp = true`).
- **FR-8** Antigravity transcripts render in the conversation view through the ACP transcript adapter.
- **FR-9** Every Antigravity turn with usage produces exactly one cost event (model = the Overdeck Google id, priced per D12) after an `antigravity` reconcile; a second reconcile imports zero duplicates.
- **FR-10** The settings catalog adds "— Antigravity" rows to the Google group only when `agy` is installed and a credential is ready (D13). Harness pickers list "Antigravity".
- **FR-11** `pan doctor` reports the Antigravity CLI as: warn "Not installed (optional ACP harness)" with the install command; warn "No API key or Agent Platform credentials" with the setup steps; or ok `<version>, auth <method>`. Every Antigravity result's message or fix text says why Google sign-in (OAuth) is not used.
- **FR-12** `harness:antigravity` context-layer blocks apply to Antigravity agents (own `contextLayerKind: "antigravity"`).
- **FR-13** A credential failure writes `acp-launch-error` with `ANTIGRAVITY_AUTH_REQUIRED`, so the spawn reports it instead of timing out.
- **FR-14** Docs describe setup, both auth methods, the OAuth/ToS reason, models, effort, cost estimates, resume, MCP, isolation and known behavior.

### Non-functional

- **NFR-1** Persistent sessions only: no `agy -p`, `--print`, `--prompt` or any one-turn invocation anywhere (no-oneshot-agents rule).
- **NFR-2** No hardcoded model fallback (D10).

## Hazards

- **HZ-1** OAuth leakage. The isolated gemini dir (D6) is the structural guard; the OS keyring is the one channel it cannot rule out. `agy` was never signed in interactively on the reference host. Five planning probe turns ran with the default `~/.gemini` before isolation (finding 9); which credential served them is not proven. Never run any probe, test or recording against the default `~/.gemini` directory: always pass `--gemini-dir`.
- **HZ-2** `authenticate` does not validate the key (finding 3). An invalid key surfaces only as assistant text; the docs say so, and doctor checks only presence.
- **HZ-3** `session/load` resets the model to `gemini-3.1-pro` (finding 6). A regression that skips `setModel` on resume would silently run the wrong model; WI-6 and WI-21 test it.
- **HZ-4** `agy` self-updates in the background, so its ACP shapes can drift under Overdeck. The replay fixtures pin the 1.5.14 shapes; doctor reports the version.
- **HZ-5** The `agy` installer appended `export PATH="/home/eltmon/.local/bin:$PATH"` to the operator's `~/.bashrc` during planning (installed 2026-11-21). `~/.local/bin` was already searched by `resolveHarnessBinary`.
- **HZ-6** Over-ceiling files: one added line fails the file-size ratchet; edit in place (NFR-3).
- **HZ-7** PAN-5586 ordering: if it lands after this issue, its implementer must add the three Gemini 4 ids to `ANTIGRAVITY_MODEL_IDS` (D8 comment step).
- **HZ-8** Effort lint: a literal level list in a non-excluded file fails `npm run lint:effort` (NFR-8).
