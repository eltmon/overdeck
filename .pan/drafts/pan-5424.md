# PAN-5424: desktop npm publish failed on a 515 MB tarball (onnxruntime staged into `server/node_modules`)

**Issue:** [PAN-5424](https://github.com/eltmon/overdeck/issues/5424) · **Failed run:** release run 43809356998 (v0.87.0) · **Caused by:** PAN-5358 (#5389, `3b415ad03f2`)

## Glossary

- **Desktop npm package** — `@overdeck/desktop`, published from `apps/desktop/` by the `npm` job of `.github/workflows/release.yml`. Its `files` list (`apps/desktop/package.json`) is `bin`, `dist-electron`, `server`, `resources`, `drizzle`, `sync-sources`. `cli/` is NOT in it.
- **Staged server** — `apps/desktop/server/` (gitignored), built by `apps/desktop/scripts/prepare-server-resources.mjs`: the dashboard chunk graph copied from `dist/dashboard/*.js` plus `server/node_modules/` holding the externals.
- **Externals** — bare package specifiers found in the server's reachable chunk graph by `scanImportClosure` (`apps/desktop/scripts/import-closure.mjs`). Each one present at the repo root's `node_modules/<name>` is pinned to the root version and `npm install`ed into `server/node_modules`. Its transitive dependencies come along.
- **`SKIP_PACKAGES`** — the set passed to `scanImportClosure` that the scanner ignores. Today it lives inline at `apps/desktop/scripts/prepare-server-resources.mjs` line 279 (`const SKIP_PACKAGES = new Set([`).
- **Transformers chunk** — `dist/dashboard/transformers.node-<hash>.js`, a ~1.46 MB rolldown chunk where the dashboard server build has *bundled* `@huggingface/transformers` (the server tsdown build bundles everything not listed in `neverBundle`, `src/dashboard/server/tsdown.config.ts` line 177).
- **Tarball size** — the gzip'd package size npm prints as `npm notice package size:` and returns as `size` from `npm pack --dry-run --json`. npm's display uses decimal MB (1 MB = 1,000,000 bytes).
- **Half-release** — a release where some packages reach npm and others do not, and the GitHub Release is skipped. v0.87.0 is one: `@overdeck/core` and `@overdeck/contracts` published, `@overdeck/desktop` stuck at 0.86.0, no GitHub Release.

## Problem

The v0.87.0 `npm` job died at "Publish desktop to npm":

```
npm notice package size: 515.2 MB
npm notice unpacked size: 1.2 GB
npm notice total files: 19812
npm error code ERR_STRING_TOO_LONG
npm error Cannot create a string longer than 0x1fffffe8 characters
```

npm base64-encodes the tarball into one JSON string for the publish `PUT`. V8's maximum string is `0x1fffffe8` chars (≈536.9 M), so any tarball above ≈402 MB raw can never publish. v0.86.0's desktop package was 133.3 MB packed / 457.8 MB unpacked / 17,046 files (`npm view @overdeck/desktop@0.86.0 dist`, and run 43660874786's log).

The new weight is `server/node_modules/onnxruntime-node` (574 MB), `onnxruntime-web` (145 MB) and `@huggingface` (10 MB).

## Root cause (steps 1 and 3-5 verified during planning; step 2 inferred)

The planning session verified each step against `dist/` built from current main and against the v0.86.0/v0.87.0 release logs:

1. `src/lib/memory/facts/vectors.ts` lines 24-25 (`return import('../../docs/index-builder.js');`) dynamically imports the **whole** index-builder module namespace. The dashboard server reaches `vectors.ts` through `src/lib/memory/injection.ts` line 23 (`import { readFactVectorsForFacts } from './facts/vectors.js';`).
2. *(Inferred from the v0.86.0/v0.87.0 diffs and logs, not reproduced on a v0.86.0 build.)* Before PAN-5358 the server reached index-builder only through `src/lib/docs/query.ts` line 6 (`import { bufferToFloat32Array, validateDocsIndex } from './index-builder.js';`), so rolldown tree-shook the local-embedding code away. A namespace dynamic import keeps every export, including `embedText` → `getLocalEmbeddingPipeline` → `import('@huggingface/transformers')` (`src/lib/docs/index-builder.ts` line 412). Rolldown bundles transformers into the transformers chunk, and `dist/dashboard/index-builder-<hash>.js` now ends in `import("./transformers.node-<hash>.js")`.
3. `scanImportClosure` regex-scans chunk text. The transformers chunk contains a JSDoc example `import { AutoTokenizer } from "@huggingface/transformers";`, and the `from\s*["']…["']` pattern matches it. So `@huggingface/transformers` lands in the externals list. The v0.87.0 log shows `Externalized deps (627 reachable chunks): … @huggingface/transformers@4.3.0 …`, but v0.86.0's list (595 chunks) does not have it.
4. `npm install` of `@huggingface/transformers@4.3.0` in `server/` pulls `onnxruntime-node`, `onnxruntime-web` and `sharp` transitively. The chunk's real runtime load, `requireFromHere("onnxruntime-node")`, does not match the scanner's `require(` pattern, so the scanner never saw onnxruntime directly.
5. The other bare names only the transformers chunk references (`sharp`, `int32`) are already dropped: they are not hoisted at the repo root under Bun's linker, so `pinnedDependencies` logs `Skipping 'sharp' — … not installed at the repo root` (confirmed in the v0.87.0 log). Planning probed `scanImportClosure` over `dist/dashboard`. Adding `@huggingface/transformers` to the skip set drops exactly one package, `@huggingface/transformers`, and nothing else.

### Why skipping it is safe (degradation path)

- The dashboard server only **reads** fact vectors: `src/lib/memory/injection.ts` lines 386-391 call `readFactVectorsForFacts` inside `try { … } catch { /* FR-7 */ }`. `readFactVectors` loads index-builder only for `bufferToFloat32Array`. The index-builder chunk's static imports are `config-yaml`, `driver`, `path` and `fs/promises`. It loads the transformers chunk only via the dynamic `import()` inside `getLocalEmbeddingPipeline`. So the server never loads the transformers chunk on this path.
- `src/lib/docs/query.ts` never embeds. It ranks against a centroid of stored vectors (line 161).
- Planning probed the server's reachable chunk graph in `dist/dashboard` (built from current main). No reachable chunk contains `refreshFactVectors` or the `fact vector refresh timed out` message. `embedText(` and `createDocsEmbeddingFunction(` appear only as definitions inside the index-builder chunk, so nothing in the server calls them.
- Embedding happens only from CLI commands: `refreshStoreVectorsBestEffort` (`src/lib/memory/facts/vectors.ts` line 181, used by `memory-facts.ts` and `memory-sync.ts`) returns `{ ok: false, reason }` on any failure, and `memory-reindex.ts` calls `refreshFactVectors`. These run from the **CLI** runtime, whose staging (`cli/`) is untouched by this issue and keeps `@huggingface/transformers`. The v0.86.0 log already lists it in `Staged pan CLI (…): … @huggingface/transformers@4.3.0`.
- If anything ever did load the transformers chunk inside a packaged server, `requireFromHere("onnxruntime-node")` would throw inside a dynamic import. That rejects the caller's promise, which every caller above catches.
- `@overdeck/core` (the npm CLI package) keeps `@huggingface/transformers` as a root dependency (`package.json` line 181). It is unaffected.

## Decisions

- **D1 — Skip by package name, as the issue proposes.** Add `@huggingface/transformers` to the server skip set. Rejected alternatives: (a) teaching the scanner to ignore comments, which is a regex-scanner rewrite with wide blast radius; (b) changing `vectors.ts` to import only `bufferToFloat32Array`, which would restore tree-shaking but still needs a refactor of `refreshFactVectors`'s embed path, and does not stop the next accidental reachability; (c) adding `@huggingface/transformers` to the server `neverBundle`, which would make the server import it for real and require installing it. Not doing (a)–(c).
- **D2 — Do not add `sharp`, `int32` or `onnxruntime-*` to the skip set.** The probe shows they are already dropped by `pinnedDependencies`, and onnxruntime is never a scanned external. The forbidden-package guard (D4) catches them if they ever arrive transitively.
- **D3 — Move the skip set into an importable module** `apps/desktop/scripts/package-policy.mjs` so tests can import the real set instead of reading script text. `prepare-server-resources.mjs` has top-level side effects and cannot be imported by a test. The new tests must be behavioral: import functions and run them on fixture directories. Never `readFileSync` a source file and `toContain` on it (repo rule: `lint:source-introspection` rejects new source-reading tests under `tests/`).
- **D4 — Guard 1, forbidden packages, in `prepare-server-resources.mjs`.** Right after `installDependencies(serverDir);` (search `installDependencies(serverDir);`), walk `server/node_modules` recursively, including nested `node_modules`. If any of `@huggingface/transformers`, `onnxruntime-node`, `onnxruntime-web` or `onnxruntime-common` is present, print every hit and `process.exit(1)`. This runs on every desktop packaging path: npm publish (`build-for-publish.mjs`) and `dist:linux|mac|win`. Scope: `server/node_modules` only. `cli/node_modules` intentionally ships transformers.
- **D5 — Guard 2, tarball size, in `build-for-publish.mjs`.** After the electron promotion, run `npm pack --dry-run --json --ignore-scripts` in `apps/desktop` with `execFileSync` and `maxBuffer: 512 * 1024 * 1024`. The 17k-file `files` array overflows the 1 MB default. Read `[0].size` and fail with exit 1 when it exceeds **300,000,000 bytes** (300 MB decimal, matching npm's display). Print `size`, `unpackedSize` and `entryCount` either way. The threshold is 2.25× v0.86.0's 133.3 MB and well under the ≈402 MB hard limit.
  - **Verified shape:** `npm pack --dry-run --json --ignore-scripts` returns a JSON array whose `[0].size` is a number. Planning checked this on `packages/contracts` with npm 10.9.4 (host) and npm 11.21.2. The release job installs `npm@11` onto `PATH` before this step.
  - **Shipped fallback (code, not a one-time choice):** `build-for-publish.mjs` must handle any unexpected dry-run output: JSON parse failure, not an array, no `[0]`, or a non-numeric `size`. In each case it falls back to a real `npm pack --ignore-scripts --pack-destination <mkdtempSync dir>`, sets `size` from `statSync(<tgz>).size`, then removes the temp dir. The guard fails closed (exit 1) only if the fallback also cannot measure a size.
- **D6 — Build the desktop package before the first publish.** In `release.yml`, split `node scripts/build-for-publish.mjs` out of "Publish desktop to npm" into a new step, "Build desktop package", placed after "Build contracts" and before "Publish CLI to npm". A failure of the desktop npm packaging guards then stops the `npm` job before **any** package reaches npm. This closes the v0.87.0 failure mode. It does not cover the separate `desktop` installer matrix job (`release.yml` job `desktop`), which runs independently of `npm`: an installer build failure can still leave npm published and the GitHub Release skipped. Changing that job graph is a non-goal (see Critique response). This is what the existing PAN-5176 comment in that job ("every build step runs before the first publish") already claims. `build-for-publish.mjs` promotes electron in `apps/desktop/package.json`. The later publish step in the same job reads that file, so the ordering stays correct. Publishing uses `--ignore-scripts`, so `prepublishOnly` does not rebuild.
- **D7 — Correct the stale "npm pack strips nested node_modules" statements.** They are wrong: the v0.87.0 tarball contained `server/node_modules/onnxruntime-node`. Correct them only where this issue edits text anyway: the `build-for-publish.mjs` header, the `prepare-server-resources.mjs` header (search `npm pack strips nested`), and `docs/DESKTOP-APP.md` (around line 322). Leave the PTY-supervisor `vendor/` comment alone. It is a different, still-valid precaution.

## Requirements

- **FR-1** `prepare-server-resources.mjs` stages no `@huggingface/transformers` in `server/node_modules`, and `@huggingface/transformers` is absent from its "Externalized deps" log line.
- **FR-2** The server skip set is exported from `apps/desktop/scripts/package-policy.mjs` as `SERVER_SKIP_PACKAGES` and contains `@effect/platform-bun`, `playwright`, `playwright-core` and `@huggingface/transformers`.
- **FR-3** `prepare-server-resources.mjs` exits 1 when `server/node_modules` (at any depth) contains `@huggingface/transformers`, `onnxruntime-node`, `onnxruntime-web` or `onnxruntime-common`, and names each offending path.
- **FR-4** `build-for-publish.mjs` exits 1 when the packed desktop tarball exceeds 300,000,000 bytes, and prints the measured size in both the pass and fail cases.
- **FR-5** The release `npm` job builds and size-checks the desktop package before publishing any package. (Scope: the `npm` job only; the `desktop` installer matrix is unchanged.)
- **FR-6** The docs describe the skip, both guards, the threshold, and what to do when a guard fails.
- **NFR-1** The new tests are behavioral (fixtures plus imported functions), live under root `tests/unit/scripts/` so root Vitest and CI run them, and use no fake or real timers.
- **NFR-2** CLI staging (`cli/`, `scanImportClosure(distRoot, ["cli/index.js"])`) is byte-for-byte unchanged in behavior.
