# PAN-4540 — A merge-gate refusal inside triggerMerge must not strand an approved green PR

**Issue:** [PAN-4540](https://github.com/eltmon/overdeck/issues/4540)
**PR:** [#4612](https://github.com/eltmon/overdeck/pull/4612)
**Status:** delivered. This PRD records the work in PR #4612.

## Glossary

- **Auto-merge row**: a row in `pending_auto_merges`, written by the scheduler and run by the executor
  (`src/dashboard/server/services/auto-merge-executor.ts`).
- **failed row**: a row whose merge command ran and failed. It is never re-armed at the same head (#3983).
- **blocked row**: a row that was refused before any merge ran. `latestAutoMergeAllowsSchedule`
  (`auto-merge-scheduler.ts`) re-arms it once the gate passes again.
- **Merge gate**: `evaluateIssueMergeGate` (`src/lib/cloister/merge-gate.ts`), which reads PR facts
  (`getPrFacts`, `src/lib/cloister/pr-facts.ts`) and asks `evaluateMergeReadiness`. Both the executor and
  `triggerMerge` run it.
- **Mergeability not computed**: GitHub returns `mergeable: null` (UNKNOWN) for a short time after the base
  branch moves, while it recomputes.
- **PR-facts cache**: `getPrFacts` caches an answer for 60 seconds. With `fresh: true` it skips the cached answer.

## Root cause

1. `triggerMerge` re-ran the gate and refused with a plain failure
   (`src/dashboard/server/routes/workspaces/merge-strike.ts`, `error: \`Cannot merge: ${gate.reason ?? 'the merge gate refused'}\``).
   The executor treated it as terminal and called `markFailed`, so the row was never re-armed at that head.
2. `evaluateMergeReadiness` reported a missing approval proof ("not approved at PR HEAD") before mergeability.
   The approval lookup (`withForgeApprovalAtHead`) runs only when checks are green and `mergeable === true`, so a
   transient `mergeable: null` read looked like a missing approval.
3. Nothing re-read an unknown mergeability.

This was seen on PAN-4515 / PR #4525 on 2026-10-04: row 191 ended `failed` with "not approved at PR HEAD" right
after `main` moved.

## Requirements

- **FR-1**: A refusal inside `triggerMerge` that comes before any merge command, and that the merge gate checks
  again before re-arming, is returned as `refused: true`. That covers the merge gate itself, failing required
  checks and a CONFLICTING PR. The executor marks the row `blocked` (`markMergeRefused`), never `failed`, and the
  scheduler re-arms it when the gate passes again. Refusals that only the operator can clear stay `failed`: a
  closed PR, a PR other than the one the gate judged, a polyrepo merge set, and `.planning/` files. Re-arming those
  would refuse again on every cycle.
- **FR-2**: `evaluateMergeReadiness` reports red checks and an unknown mergeability before an unproven approval.
  The GitHub approval-at-head refusal applies only to a green, mergeable PR.
- **FR-3**: When the gate sees an open, non-draft, green PR whose `mergeable` is null, it re-reads the facts once,
  after `MERGEABILITY_REREAD_MS` (3 s) and with `fresh: true`, before deciding.
- **FR-4**: `docs/MERGE-WORKFLOW.md` states what `failed` and `blocked` mean for auto-merge rows, and
  `configuration/auto-merge.mdx` matches.

## Non-goals

- No change to the #3983 rule that a `failed` row stays failed at its head.
- No retry loop beyond the one mergeability re-read.
- No new HTTP route, CLI verb or setting.

## Acceptance criteria

1. Given the executor's gate passes but `triggerMerge`'s gate refuses, then the row ends `blocked`, not `failed`, and
   the scheduler re-arms it at the same head once the gate passes.
2. Given an approving review at head, green checks and `mergeable: null`, then `evaluateMergeReadiness` returns a
   mergeability reason, not "not approved at PR HEAD".
3. Given `mergeable` is null on the first read and `true` on the re-read, then the gate passes. If the re-read is
   still null, it reports mergeability (fake timers).
4. `docs/MERGE-WORKFLOW.md` states the `failed` vs `blocked` meaning, and `configuration/auto-merge.mdx` matches.

## Critique response

Round 1 critique: `.pan/drafts/pan-4540-critique.md`.

### Later pre-merge refusals still strand the same head

Accepted, and fixed for the refusals the merge gate re-checks. In the pre-merge PR-state check in `triggerMerge`
(`merge-ops.ts`), the failing-required-checks return and the CONFLICTING return now carry `refused: true`. So a
check rerun that turns green, or a conflict cleared from the base side, re-arms the row at the same head. The other
pre-merge refusals stay `failed`, deliberately. `mergeTargetRefusal` (the gate passed a different PR than the one the
merge would land), a closed PR, a polyrepo merge set and `.planning/` files are all structural. The gate would pass
again on the next cycle and the merge call would refuse again, so re-arming them would loop. A non-retryable
`automaticMergeStartRefusal` means the PR moved off the approved head, and the new head gets its own row. The
`failed`/`blocked` wording in `docs/MERGE-WORKFLOW.md` and `configuration/auto-merge.mdx` now states this split. New
test: "refuses a CONFLICTING PR before any merge command, as a refusal (PAN-4540)". The failing-CI test now expects
`refused: true`.

### Unresolved after two critic rounds

- Fresh mergeability read can return the same cached answer
- Concurrent merge still strands an auto-merge row
