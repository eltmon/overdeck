## Glossary

- **Review run dir** — `.pan/review/<runId>/` inside the issue workspace, where `<runId>` looks like `agent-pan-3111-review-168a05aa`. Holds `context.json`, sub-role reports, and the verdict file. The physical dir is `.pan/` (hardcoded `PAN_DIRNAME`, `src/lib/pan-dir/types.ts:10`); the `.overdeck/review/…` strings in `roles/review.md` are stale.
- **Verdict file / verdict report** — the markdown file the review role writes before signaling: `synthesis.md` in convoy mode, `review.md` in self-review (PAN-1981) mode (`src/lib/cloister/review-agent.ts:82-83`).
- **Verdict vocabulary** — the documented `## Verdict:` line (`roles/review.md:158`): `## Verdict: APPROVED` or `## Verdict: CHANGES REQUESTED — <one-line top blocker>`. Legacy tokens `PASSED` / `FAILED` also occur.
- **Signal** — the review agent running `pan admin specialists done review <issue> --status … --run-id …`, the canonical path that writes `review_status` and delivers feedback (`src/cli/commands/specialists/done.ts:235-271`).
- **review_status** — the durable per-issue pipeline status row; canonical write door is `setReviewStatusSync()` (`src/lib/review-status.ts:151`).
- **Deacon sweep** — an async function called from `runPatrol()` (`src/lib/cloister/deacon.ts:2559`, default 60 s cycle) that returns `string[]` action log lines. Recent example: `reconcileBranchInvalidation()` (PAN-3154), registered at `deacon.ts:2970`.
- **`feedback_delivery_needs_you`** — stuck flag (`FEEDBACK_DELIVERY_STUCK_REASON`, `src/lib/review-status.ts:886`) set by `surfaceIssueFeedbackNeedsYou()` (`src/lib/cloister/feedback-target.ts:190-205`) when feedback for the work agent could not be delivered.

## Problem

A completed review verdict can sit fully synthesized on disk for hours while `review_status` stays `pending`, the work agent is never told, and the issue is flagged `feedback_delivery_needs_you`. Incident (PAN-3111, 2026-07-27): cycle-4 review verdict written to `.pan/review/agent-pan-3111-review-168a05aa/review.md` at 08:02Z, all review agents stopped by 08:34Z, and at 10:26Z `review_status` was still `review=pending, review_spawned_at=08:03Z`. The operator pasted the verdict into the agent by hand. PAN-3191 flagged the same class the same hour.

## Root cause (verified against this tree)

Three compounding defects, each verified in code:

1. **Status-gate blind spot.** Both deacon verdict-recovery sweeps only fire when `reviewStatus === 'reviewing'`:
   - `checkCompletedButUnsignaledReviews` — `src/lib/cloister/deacon-review-unsignaled.ts:161`: `if (status.reviewStatus !== 'reviewing') continue;`
   - `nudgeSynthesisForCompleteReviewerReports` — same gate in `src/lib/cloister/deacon-review-signals.ts`.
   But `reviewStatus` is reset to `pending` by ~15 paths while run dirs stay on disk (verification failure `verification-runner.ts:441,663,860,929`; review trigger reset `review-pipeline.ts:215-229`; reset/abort `review-control.ts:134-159,520-524`; post-review-commit detection `deacon-post-review-commits.ts:128-151`; startup orphan reset `service.ts:445,453`; `checkStuckReviewing` itself `deacon-review-unsignaled.ts:77`). A written verdict with status `pending` has **no** reconciliation path. PAN-3111 sat exactly here.

2. **Filename and parser mismatch.** Every deacon reader looks only for `synthesis.md` (`deacon-review-unsignaled.ts:177`, `deacon-review-signals.ts:191`, `review-verdict-feedback.ts:56`), but self-review mode instructs `review.md` (`roles/review.md:47`, `review-agent.ts:83,300`) — the incident file was `review.md`. Worse, the inline verdict parser (`deacon-review-unsignaled.ts:208-214`) accepts only exact `PASSED` / `CHANGES REQUESTED` / `FAILED`, while the role prompt's documented vocabulary is `APPROVED` and `CHANGES REQUESTED — <blocker>` (`roles/review.md:158`) — a prompt-conformant synthesis fails to parse (`"APPROVED"` matches nothing; `"CHANGES REQUESTED — foo" !== "CHANGES REQUESTED"`). Note `synthesizeReviewFromReports` itself emits `## Verdict: APPROVED` (`deacon-review-signals.ts:45-105`), so even deacon-written syntheses can't be re-parsed by the sweep.

3. **`feedback_delivery_needs_you` fires without any delivery attempt.** `resolveIssueFeedbackTarget` (`src/lib/cloister/feedback-target.ts:65-132`) is tmux-name-bound: it checks `agent-<issue>` and swarm slot sessions only, never the agents table. A live work agent registered under another session id (the shape `pan tell` resolves fine via `resolveAgentTargetSync` → `listOverdeckAgentStatesSync`, `src/lib/agents/identity.ts:47-66`) is declared "no live target" → `review-verdict-feedback.ts:232` surfaces `needs_you` with zero delivery attempts.

## Requirements

- **FR-1** — The deacon detects a completed on-disk verdict whose `reviewStatus` is `pending` and applies it within one patrol cycle: `setReviewStatusSync` write, and for `blocked` verdicts feedback delivery via `deliverReviewVerdictFeedback`.
- **FR-2** — Verdict discovery accepts both `synthesis.md` and `review.md`, and one shared parser accepts the documented vocabulary (`APPROVED`, `PASSED`, `CHANGES REQUESTED` with optional `— <blocker>` suffix, `FAILED`).
- **FR-3** — The new sweep never applies a stale verdict: it skips when the workspace HEAD has moved past the reviewed commit, when a newer `reviewRequestedAt` postdates the verdict, or when the active-run guards (`isSynthesisForActiveReviewRun`) fail.
- **FR-4** — `feedback_delivery_needs_you` is surfaced only after an agents-table-backed resolution also finds no live work-capable agent for the issue; a live agent whose delivery was never attempted does not trip it.
- **FR-5** — Every fallback application emits an operator-visible activity event naming the deacon sweep as the applier, and the `reviewNotes` record the attribution.
- **NFR-1** — New patrol code runs inside the dashboard server: no `execSync` (repo rule); the HEAD read uses the async `snapshotWorkspaceHeadsPromise` (`src/lib/git-utils.ts`, same as `deacon-review-signals.ts:241-242`).
- **NFR-2** — The incident shape is pinned by a regression test: on-disk verdict + `pending` status → applied by the sweep, with an event naming the applier.

## Decisions (auto mode — recorded, not asked)

- **D1: New dedicated sweep, not a wider gate on the existing one.** `reconcileUnappliedReviewVerdicts()` is added alongside `checkCompletedButUnsignaledReviews()` in `deacon-review-unsignaled.ts` instead of changing its `reviewing` gate. The `pending` case needs stronger anti-stale guards (HEAD anchor, newer-request check) that don't belong on the `reviewing` path, and the existing behavior stays untouched. *Alternative rejected:* flipping line 161 to also accept `pending` — an old verdict from a prior run passes `isSynthesisForActiveReviewRun` when `reviewSpawnedAt`/`lastVerifiedCommit` are stale, so a stale verdict could be applied to new code.
- **D2: Fail-closed on HEAD mismatch.** If the workspace HEAD ≠ the `context.json` `headSha` the verdict reviewed, the sweep skips. A moved HEAD means `deacon-post-review-commits` has already queued re-review; applying the old verdict would lie about the current tree.
- **D3: Nudge-first when the review session is alive.** A live `agent-<issue>-review` session gets one nudge with the exact `pan admin specialists done review …` command (the canonical CLI path also posts the PR comment and does keyed feedback delivery); the sweep applies directly only when the session is dead, or when a prior nudge went unhealed for a 30-minute grace period.
- **D4: Fix `needs_you` at the target-resolution layer.** A new agents-table-backed tier goes inside `resolveIssueFeedbackTarget` (before the resurrection ladder), not at each `surfaceIssueFeedbackNeedsYou` call site — this fixes review feedback, verification-runner, and strike-landing callers at once.
- **D5: One shared verdict-report module.** `src/lib/cloister/review-verdict-report.ts` owns `findVerdictReport()` (synthesis.md preferred, review.md fallback) and `parseVerdictReport()` (full vocabulary); the three existing readers adopt it, replacing the divergent inline regexes.
- **D6: Fix the stale `.overdeck/review/` references in `roles/review.md`.** Runtime uses `.pan/review/<runId>/`; the role file's four stale references (lines 47, 86, 153, 195) are a trap for agents that read them literally.

```ts
import { existsSync } from 'fs';
import { join } from 'path';

export const VERDICT_REPORT_FILENAMES = ['synthesis.md', 'review.md'] as const;
export type ReviewVerdictValue = 'passed' | 'blocked' | 'failed';
export interface VerdictReport { path: string; filename: string; }
export interface ParsedVerdict { verdict: ReviewVerdictValue; topBlocker: string; }

/** synthesis.md (convoy) wins when both exist; review.md is self-review (PAN-1981). */
export function findVerdictReport(dirPath: string): VerdictReport | null {
  for (const filename of VERDICT_REPORT_FILENAMES) {
    const path = join(dirPath, filename);
    if (existsSync(path)) return { path, filename };
  }
  return null;
}

/** Parse the `## Verdict:` line per roles/review.md: `APPROVED` or
 *  `CHANGES REQUESTED — <top blocker>`, plus legacy PASSED / FAILED. */
export function parseVerdictReport(content: string): ParsedVerdict | null {
  const verdictLine = content.match(/^##\s*Verdict:\s*(.+)$/im);
  if (!verdictLine) return null;
  const raw = verdictLine[1]!.trim();
  const head = raw.toUpperCase();
  let verdict: ReviewVerdictValue;
  if (head.startsWith('APPROVED') || head.startsWith('PASSED')) verdict = 'passed';
  else if (head.startsWith('CHANGES REQUESTED')) verdict = 'blocked';
  else if (head.startsWith('FAILED')) verdict = 'failed';
  else return null;
  let topBlocker = '';
  if (verdict === 'blocked') {
    const inline = raw.match(/^CHANGES REQUESTED\s*[—–:-]\s*(.+)$/i);
    if (inline) topBlocker = inline[1]!.trim().slice(0, 120);
    if (!topBlocker) {
      const blockerMatch = content.match(/## Blocking Findings\s*\n\s*###\s*\[[^\]]+\]\s*(.+)/);
      if (blockerMatch) topBlocker = blockerMatch[1]!.slice(0, 120);
    }
  }
  return { verdict, topBlocker };
}
```
