# PAN-3406 — Show issue titles in the order-book lane editor

## Glossary

- **Order book** — an operator-curated Flywheel campaign: a named set of issues split between Lane A (parallel) and Lane B (serial), persisted on `overdeck-state`. See `docs/ORDER-BOOKS.md`.
- **Lane editor** — the dashboard UI at `/orders` that renders a book's items as draggable rows. Components live in `src/dashboard/frontend/src/components/orders/`.
- **`OrderBookItem`** — the persisted shape of one lane entry (`packages/contracts`). Carries `issue` (the bare ID string, e.g. `PAN-3295`), `lane`, `order`, `prereqs`, `reVerify`, `planAtPickup`, `addedAt`, `addedBy`. It has **no title field** and must not gain one.
- **Issues read model** — the dashboard Zustand store slice fed by `/ws/rpc`, read via `useDashboardStore(selectIssues)` (`src/dashboard/frontend/src/lib/store.ts:604`). Elements are `Issue` (`src/dashboard/frontend/src/types.ts`) with `identifier` and `title` fields. This is the same store `AddIssuesRail` and `BacklogCandidatesRail` already draw titles from.
- **Render-time join** — resolving each row's title in the React tree from the read model, never writing it into the stored book.

## Problem

The lane editor renders each item as `A1 · book PAN-3295 · [no PRD] released` — the bare issue ID only (operator screenshot, 2026-08-01). With 8+ items per lane the operator cannot tell what any item is without opening the tracker, which defeats the point of curating a book.

`LaneItem.tsx:76` renders `{item.issue}` as the row label and nothing else; `OrderBookItem` carries no title; titles live only in the dashboard issues read model.

## Requirements

- **FR-1** — Every lane row whose issue exists in the issues read model renders the issue title next to the mono ID: ID first (unchanged, mono), then the title truncated with a muted style on the same row.
- **FR-2** — The full title is reachable via tooltip (HTML `title` attribute) on the title element.
- **FR-3** — Items whose issue is not in the read model (cross-project, tracker miss, store not yet loaded) render exactly as today: bare ID, no crash, no blank row, no layout shift beyond the empty title slot.
- **FR-4** — The title lookup is case-insensitive on the issue ID (book items and read-model identifiers may differ in case).
- **NFR-1** — Titles are never persisted into the order-book store. No `OrderBookItem` schema change, no write path carries a title. Resolution happens at render time only, so a renamed issue shows its fresh title on the next store update.
- **NFR-2** — The change adds no new data fetching; it reads the already-populated issues read model.

## Approach (decided)

Resolve titles in `LaneEditor` and pass them down — do **not** subscribe inside `LaneItem`:

1. **`LaneEditor.tsx`** gains an optional `issues?: Issue[]` prop, mirroring `AddIssuesRail.tsx:42-44` exactly (`const storeIssues = useDashboardStore(selectIssues) as Issue[]; const availableIssues = issues ?? storeIssues;`). A `useMemo` builds `Map<string, string>` keyed by `identifier.toUpperCase()` → `title`. Each `<LaneItem>` receives `title={titles.get(item.issue.toUpperCase())}`.
   - *Why here and not in `LaneItem`:* one store subscription per editor instead of one per row, and the `issues` prop override keeps component tests free of store seeding — the established pattern in the sibling rail (`AddIssuesRail.test.tsx` passes `issues` directly and never mocks the store).
2. **`LaneItem.tsx`** gains an optional `title?: string` prop. The current empty flex spacer (`LaneItem.tsx:77`, `<span className="min-w-0 flex-1" aria-hidden="true" />`) is replaced by a title span when a title is known:
   ```tsx
   // before
   <span className="w-20 shrink-0 font-mono text-[11px] text-foreground">{item.issue}</span>
   <span className="min-w-0 flex-1" aria-hidden="true" />

   // after
   <span className="w-20 shrink-0 font-mono text-[11px] text-foreground">{item.issue}</span>
   {title
     ? <span className="min-w-0 flex-1 truncate text-muted-foreground" title={title}>{title}</span>
     : <span className="min-w-0 flex-1" aria-hidden="true" />}
   ```
   When `title` is undefined the rendered output is byte-identical to today (FR-3).
3. **Test** — extend `src/dashboard/frontend/src/components/orders/__tests__/LaneEditor.test.tsx` with a case that renders `LaneEditor` with an `issues` prop: a known issue's row shows its title (and the `title` attribute carries the full string), an unknown issue's row shows ID-only. The existing `book` fixture uses `PAN-1..PAN-3`; add an `Issue` fixture helper shaped like the one in `AddIssuesRail.test.tsx:12-24`.
4. **Docs** — one sentence in `docs/ORDER-BOOKS.md` (UI/Progress-view paragraph near line 131) stating that the lane editor renders each item's issue title resolved at render time from the dashboard issues read model, and that titles are not persisted in the book.

## Decisions

- **Render-time join over denormalization** (per the issue's fix direction): the stored book stays canonical-ID-only; renamed issues show fresh titles automatically; no migration of existing books.
- **`LaneEditor` subscribes, `LaneItem` stays presentational:** matches the `AddIssuesRail` precedent and keeps `LaneItem` testable without a store.
- **Optional `issues` prop override on `LaneEditor`:** not speculative flexibility — it is the existing test seam used by every sibling component test in this directory.
- **Fallback = today's exact DOM:** the unknown-issue path renders the same spacer element as before, so the degradation is a no-op visually, not a new "unknown" label.

## NonGoals

- No `title` field on `OrderBookItem`, no API/schema change, no persistence of titles.
- No titles in other order-book surfaces (BookStrip, ProgressPanel, LifecycleStrip) unless they already show them — this issue covers the lane editor rows only.
- No fetching of titles for issues absent from the read model (no tracker lookups, no new endpoints).
- No redesign of the row layout, chips, or state tones.
