# PAN-3025 — Durable pipeline journal omits verificationStatus; DoD row 3 false-MISSes after live status is cleared

**Issue:** https://github.com/eltmon/overdeck/issues/3025
**Branch:** `feature/pan-3025` (workspace `workspaces/feature-pan-3025/`, based on `8bc91b51aa`)
**Mode:** `--auto` planning; all decisions recorded in `autoDecisions[]` / continue.json.

## Glossary

- **DoD gate** — the mechanical Definition-of-Done check (`evaluateDodGate()` in `src/lib/lifecycle/dod-gate.ts`) that `pan close` runs before any cleanup. Rows 1–3 are the verdict rows (review, tests, verification); row 5 is post-merge.
- **Live status** — the per-issue `ReviewStatus` row in SQLite (`~/.overdeck/overdeck.db`), read via `getReviewStatus()` (`src/lib/review-status.ts`). Doctrinally a disposable cache.
- **Pipeline journal / durable record** — the per-issue JSON record at `${OVERDECK_HOME}/state/<project>/records/<issue>.json` on `overdeck-state`; its `pipeline` block (`PanIssuePipelineRecord`, `src/lib/pan-dir/record.ts:149`) is the durable verdict store.
- **Journal fallback** — `loadStatus()` (`src/lib/lifecycle/dod-gate.ts:205`) reads live status first, then the record's `pipeline` block via `defaultDeps.getJournalStatus` (`dod-gate.ts:188-191`).
- **Close-out ceremony** — `closeOut()` in `src/lib/lifecycle/workflows.ts:166`; step "mark pipeline terminal" calls `markRecordPipelineClosedOutSync()` (`workflows.ts:319-335`), then "clear review status" deletes the live row (`workflows.ts:306-308`).
- **`markRecordPipelineClosedOutSync`** — the terminal journal write (`src/lib/pan-dir/record.ts:856-870`).

## Problem

Re-running `pan close` on an already-closed-out issue false-MISSes DoD row 3
(`verificationStatus: missing … from pipeline journal`) even though verification
verifiably passed — reproduced cleanly on MIN-896 (pass, then MISS four minutes
later, issue comment 2026-07-28) and observed on PAN-3018.

Root cause, verified against code and the on-disk record:

1. The mirror chain already carries `verificationStatus` end-to-end:
   `projectPipeline()` (`src/lib/pan-dir/records.ts:97`), `durableSubset()`
   (`src/lib/overdeck/review-status-record-sync.ts:127`), and
   `pipelineToDurableUpdate()` (`src/lib/pan-dir/verdict-restore.ts:56`) all map it.
2. But the terminal close-out write deletes it: `markRecordPipelineClosedOutSync`
   sets `record.pipeline.verificationStatus = undefined` (`record.ts:865`), and
   `JSON.stringify` drops the key. This line has existed since the function was
   introduced (`600d83c55a`) with no documented rationale.
3. Confirmed on disk: `records/pan-3018.json` `.pipeline` has
   `reviewStatus: passed`, `testStatus: passed`, `mergeStatus: merged`,
   `lastVerifiedCommit`, `closedOut: true` — and **no** `verificationStatus` key.
   Its `closeOut.dodGate` audit (persisted at close time) shows
   `verification | pass | verificationStatus: passed at 59692f68…`, proving the
   verdict existed and was destroyed by step 8, not never written.
4. After close-out step 9 clears the live row, `checkVerificationRow`
   (`dod-gate.ts:317`) can only observe the journal — which now lacks the verdict.
   A DB rebuild has the same shape: `restoreReviewStatusFromRecords` can only
   restore what the journal kept.

Adjacent defects surfaced by the same reproduction (in scope — the issue's fix
item 2 and the MIN-896 comment's row-5 observation):

5. Row 5 (`checkPostMergeRow`) reads merge status through
   `defaultPostMergeRowDeps.readMergeStatus` (`dod-gate.ts:105`), which reads
   **live status only** — no journal fallback. Post-close-out it reports
   `mergeStatus: missing` while the journal holds `mergeStatus: merged`.
6. `pan close` on a fully closed-out issue re-runs the entire gate and ceremony
   against post-close state. The server route has an idempotency check, but it
   keys on the dashboard's cached `closed-out` label
   (`src/lib/overdeck/issue-close-out.ts:87-113`) — a cache heuristic, not the
   durable record — and the CLI has no short-circuit at all.

## Proposal

Four small, independent fixes, each with named tests:

1. **Stop destroying the verdict (FR-1).** Delete the
   `record.pipeline.verificationStatus = undefined;` line from
   `markRecordPipelineClosedOutSync`. The journal then carries the full verdict
   triple (review/tests/verification) plus `lastVerifiedCommit` through close-out
   and across DB rebuilds.
2. **Reset the verdict explicitly on reopen (FR-4).** `reopenWorkspaceState`
   (`src/lib/reopen.ts:62-79`) resets review/test/merge to `'pending'` but not
   verification. With FR-1 the journalled `passed` verdict now survives close-out,
   so reopen must reset it deterministically: add `verificationStatus: 'pending'`
   to the same `setReviewStatusSync` call. (Without this, correctness still holds
   — the next mirror write projects `undefined` over the stale verdict — but an
   explicit `'pending'` keeps the live row truthful and matches its siblings.)
3. **Row 5 journal fallback (FR-2).** Repoint the default `readMergeStatus`
   through the existing `loadStatus()` live→journal fallback. Signature
   (`(issueId) => Awaitable<string | undefined>`) unchanged; the 8 existing
   `checkPostMergeRow` test call sites that inject this dep are untouched.
4. **Idempotent re-close (FR-3).** At the top of the `closeOut()` workflow,
   before the UAT-evidence step and the DoD gate: if the record's
   `pipeline.closedOut === true` **and** no live review-status row exists, return
   success immediately with one skipped step `close-out:idempotent` whose details
   name `closedOutAt` — same shape as the server route's existing
   `closeOutAlreadyCompletedResult` (`issue-close-out.ts:92-100`). Implementing in
   the workflow covers the CLI, the dashboard single close-out, and bulk
   close-out uniformly. The two-condition guard is deliberate: a ceremony that
   aborted between "mark pipeline terminal" and "clear review status" (the
   `recordDodGate` failure path, `workflows.ts:295-298`) leaves `closedOut: true`
   with live status still present, and that issue MUST fall through and complete
   its ceremony (NFR-1).

The guard lives in a new exported helper in `dod-gate.ts` (which already imports
both `getReviewStatus` and `readIssueRecord`, and has headroom under the 1000-line
ceiling at 664 lines), so `workflows.ts` gains only the call + early return.
`workflows.ts` is at its allowlisted 1006 lines, so the item includes the
audited `scripts/file-size-allowlist.txt` bump per the ratchet rule
(`<lines> <path> # PAN-3025`).

## Decisions (made here, not left to the implementer)

- **D1 — Fix the delete, not the readers.** The defect is the destructive
  terminal write, not a missing projection. No changes to `projectPipeline`,
  `durableSubset`, or `pipelineToDurableUpdate` — they are already correct.
- **D2 — Short-circuit in the workflow, not the CLI.** One guard covers every
  caller (CLI, dashboard, bulk). Without `--force` the CLI still prompts before
  reaching it; acceptable — the flywheel runs `pan close --force`, and the
  idempotent result prints as an ordinary skipped step.
- **D3 — Guard requires live status absent.** `closedOut: true` alone is
  ambiguous (completed ceremony vs. mid-ceremony abort). Live-row absence is the
  completion witness because "clear review status" is the ceremony's final
  mutating step; everything after it (`resetPostMergeStateForIssue`,
  `recordFeatureRegistryLifecycle`, telemetry) is non-fatal.
- **D4 — No backfill of historical records.** PAN-3018/MIN-896-era records
  permanently lost `verificationStatus`, but FR-3 makes re-running `pan close`
  on them a no-op, and the verdict remains recoverable from each record's
  `closeOut.dodGate` audit if ever needed. A repair sweep is scope creep.
- **D5 — Dep signature for row 5 unchanged.** Keep
  `readMergeStatus: (issueId) => Awaitable<string | undefined>`; only the default
  implementation changes. A `(from pipeline journal)` source annotation on row
  5's observed string would require a signature change rippling to 8 test sites —
  not worth it.

## Requirements

- **FR-1** — `markRecordPipelineClosedOutSync` preserves `pipeline.verificationStatus`
  (and `lastVerifiedCommit`, `verificationNotes`) when marking the journal closed-out.
- **FR-2** — `checkPostMergeRow`'s default `readMergeStatus` resolves merge status
  from live status first and the pipeline journal second, exactly like rows 1–3.
- **FR-3** — Re-running close-out on a fully closed-out issue returns success
  without evaluating the DoD gate or running any ceremony step, and names the
  original `closedOutAt` timestamp.
- **FR-4** — `reopenWorkspaceState` resets `verificationStatus` to `'pending'`
  alongside the other verdict fields.
- **NFR-1** — A close-out that aborted after "mark pipeline terminal" but before
  "clear review status" (`closedOut: true` + live status present) still re-runs
  the full ceremony to completion.
- **NFR-2** — No behavioral change for in-pipeline issues (live status present,
  `closedOut` unset): gate evaluation, ceremony order, and journal projection
  are byte-identical.

New helper in `dod-gate.ts` (imports already present there):

```ts
/**
 * PAN-3025: completion witness for the close-out ceremony. Returns closedOutAt
 * only when the journal is terminal AND the live row is gone (the ceremony's
 * final mutating step). closedOut with live status present means a prior run
 * aborted mid-ceremony and must fall through to complete it.
 */
export async function readCompletedCloseOut(issueId: string, projectPath: string): Promise<string | null> {
  const project = resolveProjectForIssue(issueId) ?? getProjectConfigFromWorkspacePath(projectPath);
  const record = await readIssueRecord(project, issueId.toUpperCase());
  if (!record?.pipeline.closedOut) return null;
  const live = await Effect.runPromise(getReviewStatus(issueId)).catch(() => null);
  return live ? null : (record.pipeline.closedOutAt ?? 'unknown');
}
```

Guard at the top of `closeOut()` in `workflows.ts` (first statement inside
`Effect.gen`, before the UAT-evidence step):

```ts
const closedOutAt = yield* Effect.promise(() => readCompletedCloseOut(ctx.issueId, ctx.projectPath));

}
```
