# PAN-3752 — Move conversation transcript parsing off the dashboard main thread

**Issue:** https://github.com/eltmon/overdeck/issues/3752
**Status:** draft PRD
**Author:** conversation conv-20260816-9367, 2026-08-16

## Glossary

- **Transcript** — a session JSONL file (Claude: `~/.claude/projects/<slug>/<session>.jsonl`;
  pi/codex: under `${OVERDECK_HOME}/agents/<id>/…/sessions/**/*.jsonl`). Active-project files
  reach 15–27 MB.
- **Full-parse snapshot stream** — `streamFullParseSnapshots` (`src/dashboard/server/ws-rpc.ts:114`)
  and its wrapper `streamHarnessFullParseSnapshots` (`ws-rpc.ts:346`): parse the ENTIRE file on
  first subscribe and on every debounced (300 ms) fs.watch change, emitting `snapshot: true`
  events (PAN-1908 design — clients adopt snapshots idempotently and never shrink a populated
  view).
- **Incremental watcher** — the Claude-only path (`ws-rpc.ts:938` onward) that tails from a
  `byteOffset` after an initial full parse establishes `initial.byteOffset` and `priorState`.
- **DB job worker** — `runDashboardDbJob()` / `runInline` in
  `src/dashboard/server/services/dashboard-db-task.ts` (PAN-3743 added lanes + the
  `[db-jobs] slow:` instrumentation at line 111).
- **Staleness watchdog** — the frontend reconnects (with a "Reconnecting to the dashboard…"
  overlay) when no domain event arrives for 35 s (`EventRouter.tsx`,
  `STREAM_STALENESS_TIMEOUT_MS`); server heartbeats tick every 15 s (`ws-rpc.ts:779`).

## Problem (verified 2026-08-16, build f33a226f0a)

Parsing runs in the server process. `parse(sessionFile)` (`ws-rpc.ts:128`) executes the harness
parser on the main thread; a 27 MB JSONL means seconds of JSON parsing that blocks the event
loop. Observed: event-loop p99 spikes to 200–307 ms while `[db-jobs] slow:` stays silent (the
worker queue is clean — the stall is main-thread). Consequences:

1. Conversation opens sit on the loading skeleton until the full parse completes.
2. The blocked loop gaps heartbeats for every other subscriber past the 35 s staleness timeout —
   opening one large conversation triggers "Reconnecting…" overlays in other tabs.
3. `getConversationByName` is called directly on the main thread (`ws-rpc.ts:890`) although the
   same operation exists as a DB-job op (`runInline` case `'getConversationByName'`,
   `dashboard-db-task.ts:239–240`) — the door exists and is bypassed.

Intersecting repo rules (restated): **no blocking work in dashboard-server-reachable code**
(PAN-70 class — applies to CPU-bound JSON parsing, not just `execSync`); **fake timers** for any
debounce/interval test; **two-doors** — reads go through the canonical resolver/job op, never a
bypass.

## Requirements

- **FR-1** Transcript parsing (pi, codex, AND the Claude initial full parse) executes off the
  main thread. The fs.watch + debounce + queue shell stays on the main thread; only
  `parse(sessionFile)` moves.
- **FR-2** PAN-1908 snapshot semantics are unchanged on the wire: same event shape
  (`kind: 'messages'`, `snapshot: true`, workLog, compactBoundaries, contextUsage), same
  idempotent-adopt client behavior. Venue changes; contract does not.
- **FR-3** `subscribeConversationMessages` resolves the conversation row through the existing
  `getConversationByName` job op instead of the direct main-thread call.
- **FR-4** Parse jobs are observable: they run under the PAN-3743 instrumentation (or equivalent)
  so a parse whose wait or run exceeds 1 s emits a `slow:`-class log line with the file size.
- **FR-5** Concurrent subscriptions to the same file share one in-flight parse (the current
  `parsing`/`pendingReparse` coalescing at `ws-rpc.ts:122–152` must survive the move, per file,
  not per subscription).
- **NFR-1** Opening a 25 MB-transcript conversation produces no event-loop-monitor warning
  attributable to the parse and triggers no staleness reconnect in other connected tabs.
- **NFR-2** First-payload latency for large transcripts is no worse than today (the parse itself
  may take the same time; it just must not block the loop).

## Work items

### 1. Parse worker op (FR-1, FR-2, FR-5)

Files: `src/dashboard/server/services/dashboard-db-task.ts`, `src/dashboard/server/ws-rpc.ts`,
the harness parser modules (follow the `parse` callbacks passed to
`streamHarnessFullParseSnapshots` at `ws-rpc.ts:346` to their definitions).

Add operation `parseTranscriptSnapshot` with payload `{ sessionFile, harness, model }` returning
the `ParseResult`. Route it to a lane that never blocks interactive ops (reuse the PAN-3743 lane
split; parsing is interactive-adjacent — decide: dedicated `parse` lane so bulk sweeps cannot
starve it, and assert the lane mapping in the existing lane unit test from PAN-3743).

In `streamFullParseSnapshots`, replace the direct call:

Before (`ws-rpc.ts:128`):
```ts
const result = await parse(sessionFile);
```
After (shape):
```ts
const result = await runDashboardDbJob<ParseResult>('parseTranscriptSnapshot', { sessionFile, harness, model });
```
The `parse` callback parameter becomes a harness discriminator (or the callsites pass harness
through) — keep the change surgical; do not redesign the wrapper signature beyond what routing
needs. Keep per-file coalescing: move the `parsing`/`pendingReparse` latch so it keys on
`sessionFile` (module-level map), satisfying FR-5 when two clients watch the same agent.

Worker side: `runInline` gains the case; the parsers must be importable in the worker context —
verify they pull no server-singleton dependencies (event bus, Effect layers). If a parser does,
split the pure parse out of it first (that split is in-scope; it is the "proper refactor" this
issue exists for).

### 2. Claude incremental initial parse (FR-1)

File: `ws-rpc.ts:938` onward (the incremental watcher acquire block).

The initial full parse that computes `initial.byteOffset`/`priorState` moves to the same worker
op (a `mode: 'initial'` variant returning `{ parseResult, byteOffset, priorState }` — priorState
must be structured-clone-safe; if it is not, return the minimal serializable state the watcher
needs and reconstruct). Subsequent incremental appends are small; they stay on the main thread.

### 3. Conversation row via the job door (FR-3)

File: `ws-rpc.ts:890`.

Before:
```ts
const conv = getConversationByName(input.conversationName);
```
After:
```ts
const conv = yield* Effect.promise(() =>
  runDashboardDbJob<Conversation | null>('getConversationByName', input.conversationName));
```
Remove the now-unused direct import if nothing else in the file uses it.

### 4. Instrumentation (FR-4)

Ensure `parseTranscriptSnapshot` flows through the `[db-jobs] slow:` path
(`dashboard-db-task.ts:110–111`); extend the log line with `bytes=<file size>` for this op only.

## Implementation checkpoint

If a harness parser cannot run in the worker without dragging in server singletons AND the pure
split balloons past this issue's scope, the fallback is chunked cooperative parsing on the main
thread (yield to the event loop every N lines via `setImmediate`, bounded chunk size) for that
harness only — it satisfies NFR-1's no-stall requirement at some cost to total parse time. State
in the PR which harnesses (if any) took the fallback and file the split as a follow-up.
