# PAN-3110 — Merge-ready recovery trap: agent-liveness merge executor + session-keyed verdict reset

## Glossary

- **review_status / review-status row** — the per-issue pipeline verdict record (SQLite
  `review_status` table, mirrored to the per-issue permanent record on `overdeck-state`).
  Holds `reviewStatus`, `testStatus`, `verificationStatus`, `mergeStatus`,
  `readyForMerge`, and the verdict anchors `reviewedAtCommit` / `lastVerifiedCommit`.
- **Verdict anchor** — the commit SHA (monorepo) or composite `repo@sha …` string
  (polyrepo) recorded when a verdict was earned. Type `HeadAnchor`; produced by
  `snapshotWorkspaceHeadsPromise()` (`src/lib/git-utils.ts:394-409`); persisted as
  `reviewedAtCommit` (review verdict) and `lastVerifiedCommit` (verification verdict).
- **Anchor drift verdict** — the result of `evaluateWorkspaceAnchorDrift()`
  (`src/lib/workspace-anchor-drift.ts:73-146`): `current` (HEAD identical to anchor),
  `benign` (HEAD moved but same tree / same effective code), `drifted` (real code
  change), `unreadable` (workspace/git unavailable).
- **triggerMerge** — the single merge executor
  (`src/dashboard/server/routes/workspaces/merge-ops.ts:325`), used by the human MERGE
  button, the flywheel auto-merge executor, and strike merges.
- **Auto-merge executor** — `tickAutoMergeExecutor`
  (`src/dashboard/server/services/auto-merge-executor.ts:68-136`), a 30-second interval
  that drains due `pending_auto_merges` rows and calls `triggerMerge`.
- **Server-side rebase** — `rebaseFeatureBranch()`
  (`src/lib/cloister/merge-rebase.ts:28-124`): deterministic in-process
  fetch → rebase → push with no agent involvement. Already used as the `/approve`
  fallback (`merge-ops.ts:1710-1717`).
- **mergeableState** — GitHub REST `pull.mergeable_state` (lowercase: `clean`,
  `behind`, `dirty`, `unstable`, `blocked`, `unknown`), exposed as
  `GitHubPullRequestState.mergeableState` (`src/lib/github-app.ts:63,542`). `clean`
  means GitHub will accept the merge as-is (no conflicts, required checks green,
  branch-protection satisfied). A `clean` PR may still be behind `main` in commits —
  GitHub only reports `behind` when branch protection requires up-to-date branches.
- **Retryable merge failure** — a merge failure caused by transient infrastructure
  (work agent stopped or unstartable, workspace missing, git transport error), as
  opposed to a content failure (failing CI, merge conflicts, closed/draft PR).

## Problem

Observed RUN-71 tick 2 (2026-07-26), PAN-3097 / PR #3102: review=passed, test=passed,
verification=passed, CI green, GitHub `mergeStateStatus: CLEAN`. The scheduled
auto-merge (`pending_auto_merges` id 38) failed with:

> Work agent agent-pan-3097 stopped before completing the rebase onto main

The natural recovery — `pan start PAN-3097 --fresh` — then reset the review_status row
from all-passed to all-pending with zero new commits on the branch, and
`POST /api/flywheel/auto-merge/schedule` now refuses with `review status is not
readyForMerge` (`src/lib/cloister/auto-merge-eligibility.ts:193-194`). The issue must
re-earn every verdict for an unchanged HEAD.

Two root causes, each independently a defect:

**RC-1 — the merge executor requires a live work agent even when no agent work is
needed.** In `triggerMerge`'s rebase step (`merge-ops.ts:908-991`), unless
`isBranchAlreadyRebased()` returns true, the server messages/spawns the work agent and
polls up to 30 minutes for a push. Three compounding problems:

1. `isBranchAlreadyRebased()` (`merge-ops.ts:53-77`) wraps everything in a bare
   `catch { return { alreadyRebased: false } }` — any fetch failure, missing
   workspace, or git error is indistinguishable from "genuinely behind".
2. A GitHub-`clean` PR does not need a rebase at all: the actual merge is always
   server-side (`mergeReviewArtifact` → `gh pr merge --squash`,
   `merge-ops.ts:1144-1157`, `src/lib/forge.ts:285-358`). The rebase-first step is
   Overdeck policy, not a GitHub requirement, and for a `clean` PR it is pure risk.
3. When a rebase genuinely is needed (`mergeableState: behind`), the deterministic
   server-side `rebaseFeatureBranch()` already exists but is never tried — the flow
   goes straight to agent recovery (`ensureAgentReadyForMerge`,
   `src/dashboard/server/routes/workspaces/merge-strike.ts:122-140`).

The failure is then made permanent twice over: the executor marks the row `failed`
(terminal — `auto-merge-executor.ts:127-133`, `markFailed` in
`src/lib/overdeck/merge-sync.ts`), and `triggerMerge` writes
`mergeStatus: 'failed', readyForMerge: false` (`merge-ops.ts:994-997`). Because
`reviewGatesPassedSync` (`src/lib/review-status-reconcile.ts:89-105`) requires
`mergeStatus ∈ {pending, queued, undefined, null}`, the `failed` value blocks both
restoration paths: the 60-second deacon patrol `reconcileStuckReadyForMerge`
(`src/lib/cloister/deacon-merge.ts:492-508`) and the boot repair
`fixStuckReadyForMerge` (`src/lib/review-status.ts:771-790`, which deliberately skips
`failed`). Only the 30-minute-cooldown `checkFailedMergeRetry` patrol
(`deacon-merge.ts:703-731`) would eventually restore it — far too slow for a scheduled
auto-merge the operator is watching.

**RC-2 — the verdict reset is keyed to agent-session lifecycle, not to branch HEAD.**
`spawnAgent` calls `resetPipelineVerdictsForWorkStartSync`
(`src/lib/review-status.ts:604-649`) on **every** work-role spawn
(`src/lib/agents/spawn.ts:571-580`). That function clears `reviewStatus`,
`testStatus`, `verificationStatus`, `readyForMerge` AND both anchors
(`reviewedAtCommit`, `lastVerifiedCommit`) without ever comparing HEAD. It fires on
`pan start` (fresh or not), on dashboard start-agent, and — critically — on
`ensureAgentReadyForMerge`'s fresh-spawn recovery (`merge-strike.ts:138`), so even the
merge executor's own recovery path destroys the verdicts that made the issue
merge-eligible. Every existing HEAD-comparison guard (`pan done`'s skip-re-review,
`src/cli/commands/done.ts:781-803`; the deacon's `checkPostReviewCommits`,
`src/lib/cloister/deacon.ts:1569-1638`; `canSkipTests`,
`src/lib/review-status.ts:441-459`) operates on the preserved anchors, so once the
reset deletes them the circular trap is complete: merge fails because agent stopped →
restarting the agent wipes merge-readiness → merge can never be scheduled without a
full re-review of identical code.

## Proposal

**Defect 1 — make the merge path agent-independent for the happy cases, and
retryable for the rest.**

1. **Direct merge for `clean` PRs.** In `triggerMerge`, after the existing pre-merge
   PR-state check, when GitHub reports the PR mergeable with
   `mergeableState === 'clean'` and no failing/pending checks, skip the entire rebase
   section (no `isBranchAlreadyRebased`, no `ensureAgentReadyForMerge`, no polling)
   and proceed straight to the verification/merge steps with `newHead =
   prState.headSha`. The existing PAN-2487 skip (CI green on tip → skip redundant
   local verification, `merge-ops.ts:1049-1070`) already covers verification for this
   case.
2. **Server-side rebase before any agent.** When a rebase is needed
   (`mergeableState` not `clean`, or PR state unavailable) and the branch is not
   already rebased, try `rebaseFeatureBranch()` first (the `/approve` precedent at
   `merge-ops.ts:1710-1717`). Only a conflict result engages the existing agent path
   (an LLM can resolve conflicts; git cannot).
3. **Retryable failure classification.** Add `retryable?: boolean` to
   `TriggerMergeResult` (`merge-strike.ts:44-58`). Agent stopped/unstartable,
   workspace missing, and non-conflict server-side rebase errors are retryable: the
   result carries `retryable: true`, and the status write uses `mergeStatus:
   'queued'` with an explanatory `mergeNotes` — never `mergeStatus: 'failed'` —
   leaving `readyForMerge` and the component verdicts intact (`queued` passes
   `reviewGatesPassedSync`, so the normal derivation keeps the issue merge-eligible).
4. **Executor requeue.** In `tickAutoMergeExecutor`, a `retryable` result requeues
   the row via the existing `requeueToPending` with the standard 60s backoff
   (`REQUEUE_BACKOFF_MS`, `auto-merge-executor.ts:39`) instead of `markFailed`, and
   increments `mergeRetryCount`. When the shared circuit breaker is saturated
   (`mergeRetryCount >= FAILED_MERGE_MAX_RETRIES`, the same counter the deacon's
   `checkFailedMergeRetry` uses), the row is marked `blocked` with a stand-alone
   operator-facing reason. "Never fail permanently on agent stopped" — but never spin
   forever either.

**Defect 2 — key the verdict reset to HEAD movement.**

5. **Anchor guard at work-agent spawn.** In `spawnAgent`'s work-role branch
   (`spawn.ts:571-580`), before calling `resetPipelineVerdictsForWorkStartSync`,
   evaluate the stored `reviewedAtCommit` anchor with the same machinery the deacon
   already trusts (`evaluateWorkspaceAnchorDrift` + `rehydrateHeadAnchor`):
   - `current` → skip the reset entirely (and skip `resetPostMergeState`, which is
     currently coupled to the reset having fired); log the preservation.
   - `benign` → skip the reset and update the stored anchor to the current one,
     mirroring the deacon's benign path (`deacon.ts:1596-1601`).
   - `drifted`, `unreadable`, or no anchor/verdicts to preserve → reset exactly as
     today (conservative fallback; NFR-2).

   This protects every spawn path at once: `pan start`, `pan start --fresh`,
   dashboard start-agent, and `ensureAgentReadyForMerge`'s conflict-recovery spawn.

Deliberate operator resets stay unconditional: `pan reset-to-planned`
(`src/cli/commands/reset-to-planned.ts:66`, `force: true`), dashboard
reset/purge/abort (`src/dashboard/server/routes/workspaces/review-control.ts:114-159`),
`pan reopen` (`src/lib/reopen.ts:62-79`), and all `clearReviewStatus` callers are
explicit "throw the verdicts away" commands and are out of scope.

## Decisions (made in this doc — do not re-litigate during implementation)

- **D1: `clean` PRs merge without any rebase.** A squash merge of a `clean` PR is
  accepted by GitHub by definition of the state; rebasing first adds agent-liveness
  risk and a new SHA whose CI cannot be green yet, defeating the PAN-2487
  verification skip. Linear history is unaffected — every merge is a squash merge.
- **D2: server-side rebase runs BEFORE the agent path, not after.** Deterministic
  mechanical work should never wait on an LLM session (`rebaseFeatureBranch` is the
  retired ship-role's replacement for exactly this reason — see
  `src/lib/cloister/merge-agent.ts:1106-1109`). The agent is reserved for the one
  thing git cannot do: conflict resolution.
- **D3: retryable failures write `mergeStatus: 'queued'`, not `'failed'`.** This is
  what keeps `readyForMerge` derivable (`reviewGatesPassedSync` accepts `queued`) and
  lets the executor's 60s requeue — rather than the deacon's 30-minute patrol — drive
  recovery. The human MERGE button shows the issue back in the merge queue with the
  transient reason in `mergeNotes`.
- **D4: the retry cap reuses `mergeRetryCount` / `FAILED_MERGE_MAX_RETRIES`.** No
  schema migration. The counter already means "merge infrastructure retries
  consumed" and already has a circuit-breaker convention
  (`deacon-merge.ts:703-708`). The executor increments it per requeue; both retry
  mechanisms share the ceiling. An operator who fixes the underlying cause and
  re-schedules gets a fresh counter only via the existing reset paths
  (`deacon.ts:1627` resets it on real HEAD drift).
- **D5: the spawn-time preservation guard lives at the `spawn.ts` call site, not
  inside `resetPipelineVerdictsForWorkStartSync`.** The reset function is
  synchronous; anchor evaluation is async git I/O, and server-reachable code must not
  gain sync git calls (no-execSync rule). The guard is an async pre-check at the one
  call site that must be conditional; the other call site (`reset-to-planned.ts:66`)
  is a deliberate operator reset and stays unconditional by passing `force: true`.
- **D6: `unreadable` anchor state falls back to resetting.** If the workspace is
  gone or git fails, we cannot prove HEAD is unchanged, so we keep today's behavior
  (reset). A future follow-up could compare against `origin/<branch>` from the
  primary checkout; out of scope here (NFR-2 conservatism wins).
- **D7: `testStatus` needs no new anchor.** Test verdicts ride the review anchor:
  preservation keeps `testStatus: 'passed'` only when `reviewedAtCommit` matches, the
  same coupling `canSkipTests` (`review-status.ts:441-459`) already uses.

## Requirements

### Functional

- **FR-1** — When any work agent is spawned (any entry point) and the stored
  `reviewedAtCommit` anchor evaluates as `current` against the workspace, the
  pipeline MUST NOT reset `reviewStatus`, `testStatus`, `verificationStatus`,
  `readyForMerge`, or the anchors.
- **FR-2** — When the anchor evaluates as `benign`, the spawn path MUST preserve the
  verdicts and update the stored `reviewedAtCommit` to the current anchor.
- **FR-3** — When the anchor evaluates as `drifted` or `unreadable`, or no anchor or
  no passed verdicts exist, the spawn path MUST reset verdicts exactly as today.
- **FR-4** — When the pre-merge PR-state check reports a mergeable PR with
  `mergeableState === 'clean'` and `checksFailed`/`checksPending` both false,
  `triggerMerge` MUST reach the merge step without calling
  `ensureAgentReadyForMerge` and without polling for an agent push.
- **FR-5** — When a rebase is needed and the branch is not already rebased,
  `triggerMerge` MUST attempt `rebaseFeatureBranch()` before engaging any agent, and
  MUST engage the agent path only when the server-side rebase reports conflicts.
- **FR-6** — When the merge fails for a transient infrastructure reason (agent
  stopped or unstartable, workspace missing, non-conflict server-side rebase error),
  `triggerMerge` MUST return `success: false` with `retryable: true` and write
  `mergeStatus: 'queued'` with the reason in `mergeNotes`, leaving `readyForMerge`
  and the component verdicts untouched.
- **FR-7** — On a `retryable` result, the auto-merge executor MUST requeue the
  `pending_auto_merges` row with the standard backoff and increment
  `mergeRetryCount`, and MUST mark the row `blocked` (not `failed`) with an
  operator-facing reason once `mergeRetryCount >= FAILED_MERGE_MAX_RETRIES`.
- **FR-8** — Documentation: `docs/MERGE-WORKFLOW.md` describes the
  clean-direct → server-side-rebase → agent-conflict escalation and the
  retryable/requeue contract; the flywheel auto-merge docs
  (`docs/FLYWHEEL.md`) describe requeue-vs-failed-vs-blocked.

### Non-functional

- **NFR-1** — No new synchronous process/git calls in server-reachable code
  (no-execSync rule). All new git I/O uses `execAsync`/`execFileAsync`.
- **NFR-2** — The preservation guard is conservative: any doubt (unreadable anchor,
  missing workspace, missing `reviewedAtCommit`, verdicts not all-passed) falls back
  to today's reset behavior. It must never preserve verdicts across a real code
  change.
- **NFR-3** — The retryable requeue is loop-safe: bounded by the shared
  `mergeRetryCount` circuit breaker; steady state makes zero writes.
- **NFR-4** — Existing deliberate-reset commands (`reset-to-planned`, review
  purge/abort, `reopen`, close-out) keep their unconditional semantics.

**Change:** add an async guard evaluated before the sync reset:

```ts
// src/lib/cloister/verdict-preservation.ts
export async function shouldPreservePipelineVerdicts(
  issueId: string,
  workspacePath: string,
): Promise<{ preserve: boolean; refreshedAnchor?: string; reason: string }> {
  const status = getReviewStatusSync(issueId);
  if (!status?.reviewedAtCommit) return { preserve: false, reason: 'no review anchor recorded' };
  if (status.reviewStatus !== 'passed' && status.reviewStatus !== 'skipped') {
    return { preserve: false, reason: `reviewStatus=${status.reviewStatus}` };
  }
  const verdict = await evaluateWorkspaceAnchorDrift(
    issueId, workspacePath, rehydrateHeadAnchor(status.reviewedAtCommit),
  );
  if (verdict.kind === 'current') return { preserve: true, reason: 'HEAD unchanged since verdicts' };
  if (verdict.kind === 'benign') {
    return { preserve: true, refreshedAnchor: verdict.currentAnchor, reason: 'benign post-verdict HEAD move' };
  }
  return { preserve: false, reason: `anchor ${verdict.kind}` };
}
```

In `spawn.ts`, the work branch becomes: evaluate the guard; on `preserve`, skip both
`resetPipelineVerdictsForWorkStartSync` and `resetPostMergeState`, apply
`refreshedAnchor` via `setReviewStatusSync(issueId, { reviewedAtCommit:
refreshedAnchor })` when present, and log one line
(`[spawn] Preserved pipeline verdicts for <issue> — <reason>`). On `!preserve`,
behave exactly as today.

**Tests** (mock `getReviewStatusSync` + `evaluateWorkspaceAnchorDrift`; no real git):
1. `current` anchor + passed verdicts → reset NOT called, `resetPostMergeState` NOT
   called, verdicts + `readyForMerge` intact.
2. `benign` → reset NOT called; anchor updated to `currentAnchor`.
3. `drifted` → reset called (today's behavior).
4. `unreadable` / no `reviewedAtCommit` / `reviewStatus !== 'passed'` → reset called.
5. Non-work roles never evaluate the guard.

**Acceptance criteria:** AC1 = test 1 passes; AC2 = test 2 passes; AC3 = tests 3+4
pass; AC4 = test 5 passes; AC5 = `npm run typecheck` clean.

## NonGoals

- Changing the eligibility predicate in `auto-merge-eligibility.ts` (the
  `readyForMerge` requirement stays; the fix makes it reachable again, not looser).
- Changing deliberate operator resets (`reset-to-planned`, review purge/abort,
  `reopen`, close-out `clearReviewStatus`) — they stay unconditional (NFR-4).
- Origin-branch anchor comparison when the workspace is unreadable (D6 follow-up).
- Adding a SHA anchor for `testStatus` (D7).
- Reworking the deacon's 30-minute `checkFailedMergeRetry` patrol — the executor's
  60s requeue makes it the fast path; the patrol remains the backstop.
- GitLab forge auto-merge (eligibility exists, but the incident and the executor
  changes are GitHub-scoped; the retryable contract is forge-agnostic).
