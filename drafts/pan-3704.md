# PRD: PAN-3704 — Ctrl-K search: add a toggle for newest-first conversation ordering

Issue: https://github.com/eltmon/overdeck/issues/3704
Depends on / relates to: https://github.com/eltmon/overdeck/issues/3703 (Ctrl-K search: show conversations newest first — still in planning at authoring time, 2026-08-14)

## Glossary

- **Command palette / Ctrl-K palette** — the `cmdk`-based modal in the dashboard opened with Cmd+K / Ctrl+K, implemented in `src/dashboard/frontend/src/components/CommandPalette.tsx`.
- **Conversation hit** — one search result in the palette's *Conversations* group, produced by the server route `src/dashboard/server/routes/palette.ts` via `src/dashboard/server/services/conversation-search-service.ts` and the ranker `src/lib/conversation-search/ranker.ts`. Client-side type: `PaletteConversationHit` (CommandPalette.tsx:130-142). It already carries `ts: string | null` (the canonical conversation timestamp) and `rank: number`.
- **PaletteAction** — the client-side row model every palette result is lowered into (CommandPalette.tsx:51-80). Rendered groups sort rows by `rank` ascending (CommandPalette.tsx:970-972).
- **Rank order / existing order** — the current conversation ordering: the server's `rank`, assigned by `rankConversationSearch` (ranker.ts:81 sorts by score descending, then `rowid` ascending) and preserved by the palette's within-group rank sort.
- **Newest-first order** — the ordering requested by PAN-3703: conversations sorted by `ts` descending, with a deterministic fallback for equal or missing timestamps.
- **Established settings pattern** — the dashboard's client-side preference persistence convention: an exported `overdeck.ui.*` localStorage key constant, a lazy `useState(() => localStorage.getItem(KEY) ...)` initializer, and a setter that writes through `try { localStorage.setItem(...) } catch { /* ignore */ }`. Precedent: `SIDEBAR_STORAGE_KEY` / `WORKSPACES_GROUPED_KEY` / `WORKSPACES_PIPELINE_EXPANDED_KEY` in `src/dashboard/frontend/src/components/Sidebar.tsx` (lines 60, 176, 182; usage at 292-307).

## Problem

PAN-3703 makes Ctrl-K conversation results appear newest first. Once that lands, the ordering is unconditional: an operator who preferred the relevance-ranked order has no way back. PAN-3704 makes the newest-first ordering optional through a visible, persistent, accessible toggle inside the palette.

## Proposal

Implement the toggle entirely client-side in `CommandPalette.tsx`. The server response is unchanged: it already sends `ts` and `rank` per conversation hit, which is everything the client needs to render either ordering.

1. **Preference state** following the established settings pattern: exported key constant `PALETTE_CONVERSATIONS_NEWEST_FIRST_KEY = 'overdeck.ui.paletteConversationsNewestFirst'`, lazy `useState` initializer, try/catch write-through. **Default is ON** (newest-first), because PAN-3703 establishes newest-first as the requested default; the toggle is the opt-out that restores rank order. Scope: per-browser localStorage, same as every other `overdeck.ui.*` preference.
2. **Carry the timestamp onto the row model**: add `sortTs?: string | null` to `PaletteAction` and set `sortTs: hit.ts` when building conversation actions (the loop at CommandPalette.tsx:764-807).
3. **Exported comparator** `compareConversationActionsNewestFirst(a, b)` in CommandPalette.tsx: `ts` descending; invalid/missing `ts` sorts after valid ones; remaining ties fall back to `rank` ascending (rank is itself deterministic: score desc, rowid asc). Exported so tests can exercise it directly.
4. **Conditional sort at render**: the within-group `.sort((a, b) => (a.rank ?? 0) - (b.rank ?? 0))` at CommandPalette.tsx:970-972 becomes: if `group === 'Conversations'` and the preference is ON, use the comparator; otherwise rank ascending. All other groups (Actions, Commands, Workspaces, Issues, Running Agents, Memory, Observations, Summaries) keep the rank sort untouched.
5. **Footer toggle control**: a real `<button type="button">` added to the palette footer (CommandPalette.tsx:1035-1048), right-aligned with `ml-auto`, labeled "Newest first", with `aria-pressed={conversationsNewestFirst}` and the same active/inactive chip styling as the scope chips (CommandPalette.tsx:937-941: active = `bg-primary/15 border-primary/40 text-primary font-medium`, inactive = `bg-card border-border text-muted-foreground`). The scope chips already demonstrate that plain buttons inside `<Command>` but outside `<Command.List>` are keyboard-focusable and clickable without disturbing cmdk's list selection. Clicking the button toggles the preference, persists it, and reorders the already-loaded results immediately (no refetch).

## Coordination with PAN-3703

PAN-3703 is still in planning (planning session observed running 2026-08-14; no spec or commits on `feature/pan-3703`). Two landing orders are possible, and this plan is written so either works:

- **PAN-3703 lands first.** Its newest-first ordering is already in the tree; the work agent rebases and gates that ordering behind the preference. If PAN-3703 implemented the ordering client-side as a comparator, wrap it; if it implemented ordering server-side, the work agent must still add this client-side comparator so the OFF mode can restore rank order without a server round-trip — and should flag the now-redundant server-side ordering in review.
- **PAN-3704 lands first.** The work agent implements the comparator specified here (which is exactly the ordering PAN-3703 specifies: canonical timestamp desc, deterministic fallback). PAN-3703 then reduces to flipping the default / removing any duplicate ordering code.

Decision (auto): implement the comparator client-side regardless of PAN-3703's landing state, and keep the server response untouched. Rationale: the client already has `ts` and `rank`; a client-side comparator makes both orderings available with zero API change, which is the only design that satisfies "disabled mode restores the existing order" without a refetch or a new query parameter.

## Requirements

### Functional

- FR-1: The palette footer renders a control labeled "Newest first" whenever the palette is open, regardless of query or result contents.
- FR-2: When the preference is ON, conversation results render newest-first: valid `ts` descending; hits with missing/invalid `ts` after all valid ones; ties (equal or both-missing `ts`) ordered by `rank` ascending.
- FR-3: When the preference is OFF, conversation results render in `rank` ascending order (the pre-PAN-3703 behavior).
- FR-4: Activating the control flips the ordering of the currently displayed conversation results immediately, without closing the palette and without a new search request.
- FR-5: The preference persists in localStorage under `overdeck.ui.paletteConversationsNewestFirst` and is honored on the next palette mount (new dashboard load reads the stored value).
- FR-6: The toggle changes only the Conversations group. Actions, Commands, Workspaces, Issues, Running Agents, Memory, Observations, and Summaries keep rank order in both modes.

### Non-functional

- NFR-1: The control is a native `<button type="button">` with `aria-pressed` reflecting current state, focusable by keyboard (Tab) and activatable with Enter/Space, so screen readers announce it as a pressed/not-pressed toggle button.
- NFR-2: The control's active/inactive styling reuses the scope-chip class formula (no new color tokens), per the dashboard style system's color-restraint rules.
- NFR-3: No server, route, or API-contract change; `PaletteSearchResponse` is untouched.

### WI-2: Newest-first comparator

Files: `src/dashboard/frontend/src/components/CommandPalette.tsx`

Add and export, next to the other display helpers (after `formatHitDate`, line 203):

```ts
/**
 * PAN-3704: newest-first ordering for conversation results (the PAN-3703 order).
 * Valid timestamps sort newest first; missing/invalid timestamps sort last;
 * remaining ties fall back to server rank (score desc, rowid asc) so the order
 * is deterministic.
 */
export function compareConversationActionsNewestFirst(a: PaletteAction, b: PaletteAction): number {
  const aTs = a.sortTs ? Date.parse(a.sortTs) : Number.NaN;
  const bTs = b.sortTs ? Date.parse(b.sortTs) : Number.NaN;
  const aValid = Number.isFinite(aTs);
  const bValid = Number.isFinite(bTs);
  if (aValid && bValid && aTs !== bTs) return bTs - aTs;
  if (aValid !== bValid) return aValid ? -1 : 1;
  return (a.rank ?? 0) - (b.rank ?? 0);
}
```

(`PaletteAction` is currently module-private; export it or type the comparator parameters structurally — pick whichever the lint rules prefer; exporting the interface is the smaller diff.)

## Acceptance criteria

- AC-1 (FR-1, NFR-1): With the palette open, a keyboard-focusable button with accessible name "Newest first" and `aria-pressed` state renders in the footer.
- AC-2 (FR-2): Given conversation hits whose rank order differs from recency order, when the preference is ON, then the Conversations group renders newest first.
- AC-3 (FR-3): When the preference is OFF, the Conversations group renders in rank ascending order.
- AC-4 (FR-4): Clicking the toggle reorders the visible conversation results immediately; the palette stays open and no new `/api/palette/search` request fires.
- AC-5 (FR-5): The choice persists in localStorage and a remounted palette renders the stored ordering.
- AC-6 (FR-2): Given equal timestamps, results order by rank ascending; given a missing timestamp, that result sorts after all timestamped results.
- AC-7 (FR-6): Issue, action, workspace, and memory result order is identical in both toggle states.
- AC-8 (WI-5): `docs/DESKTOP-APP.md`'s palette section names the "Newest first" toggle, its default, and its persistence scope.

## NonGoals

- No server-side ordering change, new query parameter, or API-contract change.
- No reordering of non-conversation groups, and no per-group toggles.
- No cross-device/account sync of the preference (localStorage only, matching all other `overdeck.ui.*` prefs).
- No change to which conversations are searched or matched — only display order.
- No change to the ⌘J entry point beyond what sharing the component gives it for free.
- Not a fix for PAN-3703 itself; this issue assumes/specifies the same comparator but owns only the toggle.

## Planning Q&A

Planning ran in `--auto` mode; no interactive questions were asked. Decisions are recorded in `plan.autoDecisions[]` of the xBRIEF and in continue.json:

1. **Default ON (opt-out).** The issue says newest-first "should be optional," and PAN-3703 requests newest-first as the behavior; making the toggle default-on preserves PAN-3703's intent while restoring choice.
2. **Client-side comparator, no API change.** The client already receives `ts` and `rank`; only a client-side design can restore rank order without a refetch.
3. **localStorage persistence, `overdeck.ui.*` key.** The established Command-Palette-adjacent pattern (Sidebar.tsx keys); the issue explicitly asks for "the established settings pattern," and this is it.
4. **Footer placement with `aria-pressed`.** The footer is the palette's persistent-affordance area; `aria-pressed` on a native button is the existing dashboard idiom for toggles (PipelineView.tsx) and satisfies the keyboard + screen-reader requirement with no new component.
5. **PAN-3703 not yet landed.** The comparator is specified in full here so PAN-3704 is executable regardless of PAN-3703's landing order; coordination rules are in the Coordination section.
