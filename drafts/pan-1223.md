## Glossary

- **Browser dashboard**: the React dashboard served by `pan up`, `overdeck up`, or `npx @overdeck/core`; it is not running inside Electron.
- **Desktop app**: the packaged Electron application under `apps/desktop/`, which embeds the same dashboard and can replace its own signed application binary through `electron-updater`.
- **Version control**: the small `vX.Y.Z` technical identifier beside the Overdeck wordmark in the expanded primary sidebar.
- **Update manager**: the one canonical read/write door for checking, installing, and reporting Overdeck update state. Routes, the CLI command, and the Electron bridge delegate to it rather than independently reading registries or spawning installers.
- **Update manifest**: the `electron-builder` YAML file (`latest.yml`, `latest-mac.yml`, `latest-linux.yml`, or the corresponding `beta*` file) that names an update payload and carries its checksum.
- **Stable channel**: normal releases and npm's `latest` dist-tag. Stable builds never select a GitHub prerelease.
- **Canary channel**: prereleases whose Overdeck version contains `-canary.N`; npm publishes them under the `canary` dist-tag and desktop metadata uses Electron's `beta` channel filename.
- **Release notes**: the Markdown body committed at `.release/vX.Y.Z.md` and published as the matching GitHub Release body. The dialog renders the target release's notes and links to the release page.
- **Ready**: the update payload has been installed (npm path) or downloaded and verified (desktop path), but the dashboard/application has not restarted into it yet.
- **No-loss audit**: a focused test that enumerates every pre-existing updater/version affordance and fails until each still has a home after the refactor.

## Problem

Overdeck has three disconnected pieces that create the appearance of an updater without a working end-to-end field experience:

1. The dashboard shows the running version beside the Overdeck wordmark, but the entire wordmark/version group is one Home navigation button. The version cannot check or install an update (`src/dashboard/frontend/src/components/Sidebar.tsx`, search for `v{versionData.version}`, currently lines 357-373).
2. The Electron main process already owns updater state and IPC handlers (`apps/desktop/src/updater.ts`, lines 17-249; `apps/desktop/src/main.ts`, search for `GET_UPDATE_STATUS`), but `apps/desktop/src/preload.ts` does not expose any updater channel or method to React. The dashboard cannot observe, download, or apply a desktop update.
3. The release workflow uploads only `.AppImage`, `.dmg`, and `.exe` (`.github/workflows/release.yml`, lines 216-233 and 300-337). The live v0.45.16 GitHub Release was verified to contain exactly those three assets and no updater YAML, macOS ZIP, or blockmap. `electron-updater` therefore has no manifest/checksum path, and macOS has no ZIP update payload.

The existing `pan update` command also uses `execSync` for both registry lookup and installation (`src/cli/commands/update.ts`, lines 5, 27-37, and 96-103). That implementation cannot be called from dashboard server code because synchronous child processes freeze the Node event loop. Its `--force` flag is parsed but does not bypass the early “latest” return at lines 79-84.

## Product decision

The version control beside the wordmark becomes the single dashboard entry point for updates.

- Hover and keyboard focus display: **“Click to update Overdeck to the latest version.”**
- The Overdeck mark and title remain a Home button. The version becomes a separate button, so the existing Home affordance is preserved.
- Clicking the version always performs a fresh check and opens the updater dialog.
- If no release is newer, the dialog says **“You’re up to date”**, shows the installed version and “Checked just now,” and offers Done.
- If a release is newer, the dialog shows Installed → Available versions, stable/canary channel, “What’s new,” the target release notes, a full-release link, restart impact, Later, and Update Overdeck.
- Download/install progress replaces the release-note body in the same dialog. It is not a toast-only workflow.
- Desktop updates download, verify, then wait for **Restart Overdeck**. There is no surprise restart.
- Browser/npm updates install the exact version asynchronously, run `pan sync`, then wait for **Restart dashboard**. Running tmux agent sessions are not killed; the dashboard reconnects.
- Development checkouts are check-only. The dialog identifies the development build and does not mutate the source worktree.
- Background checks may mark the version control as update-available, but never open the dialog and never start a download without a user click.

The standalone HTML at `docs/design/mockups/pan-1223-overdeck-updater.html` is the visual contract (published preview: https://overdeck.localhost/s/DZchcC8g). Its “Prototype state” control demonstrates update-available, up-to-date, and error paths; the primary action also demonstrates download progress and restart-ready state.

## Requirements

### Functional requirements

- **FR-1**: The expanded sidebar renders the Overdeck mark/title as Home navigation and the version as a separate keyboard-operable button.
- **FR-2**: Hovering or focusing the version displays “Click to update Overdeck to the latest version.” through a visible tooltip and accessible description.
- **FR-3**: Clicking the version forces a new channel-appropriate update check and opens one dialog covering checking, current, available, downloading/installing, ready, complete, and error states.
- **FR-4**: The available state displays installed version, target version, channel, release notes, release URL, restart consequence, Later, and Update Overdeck.
- **FR-5**: The current state explicitly says no update is available and reports the installed version and last-check time.
- **FR-6**: Desktop renderer code can read update state, request a check, start a download, observe progress/status, and request restart/install only through the typed preload bridge.
- **FR-7**: Desktop resolution selects the first qualifying non-draft GitHub release: stable excludes prereleases; canary includes only prereleases carrying the beta/canary update manifest. It then uses the release's exact asset base URL with the generic provider.
- **FR-8**: Desktop update metadata includes release notes, release URL, release date, byte progress, and error detail without exposing arbitrary IPC.
- **FR-9**: Browser/npm mode checks the appropriate npm dist-tag and GitHub Release, installs the exact resolved package version asynchronously, runs `pan sync`, and exposes ready/error status without blocking the dashboard event loop.
- **FR-10**: Development mode is check-only and never runs npm installation, `pan sync`, restart, git, or source mutation.
- **FR-11**: Desktop release CI publishes the installer/update payload and matching update manifest/checksum assets from the same build; macOS includes ZIP as well as DMG.
- **FR-12**: Stable and canary releases cannot cross-select a manifest from the wrong release class.
- **FR-13**: No update path restarts the app/dashboard without an explicit Restart action during the current interaction. A downloaded desktop update may still install on a later normal application quit, preserving existing behavior.
- **FR-14**: Help menu update actions and the CLI command delegate to the same state/action semantics as the dashboard.
- **FR-15**: A background check may decorate the version button when an update is available but must not open UI or start installation.
- **FR-16**: Retry logic performs at most three download attempts with 2s then 4s backoff and exposes Retry after exhaustion.
- **FR-17**: Release notes Markdown is rendered with the existing safe Markdown stack; raw HTML is not enabled and external links use safe targets.
- **FR-18**: Existing updater/version surfaces pass the explicit no-loss audit.

### Non-functional requirements

- **NFR-1**: Dashboard-server code uses `execFile`, `spawn`, or Effect async primitives only; no new `execSync`, `spawnSync`, or shell-string installer execution is allowed.
- **NFR-2**: Delay/retry tests use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`; no real backoff delay is allowed in the default suite.
- **NFR-3**: Update state has one read door and one write door. React, routes, CLI, menu, and IPC do not read registries or mutate status independently.
- **NFR-4**: The dialog meets WCAG 2.1 AA, traps/restores focus, closes on Escape when safe, names progress, and never relies on color alone.
- **NFR-5**: Motion is 150-250ms and honors `prefers-reduced-motion`.
- **NFR-6**: Registry/release checks use a 10s timeout, an identifying User-Agent, and a 24-hour background cache; manual clicks bypass the cache.
- **NFR-7**: Installer arguments are arrays and target an exact validated semver returned by the update check, never interpolated shell text and never an unbounded `latest` at install time.
- **NFR-8**: The release gate verifies the published manifest refers to an asset in the same release and its checksum matches the uploaded payload before the release is made non-draft.
- **NFR-9**: Dashboard boot-path changes receive a throwaway runtime boot test before any live restart. This PR must not be hot-patched onto the live server.
- **NFR-10**: No telemetry is added in this issue. Version-in-field telemetry remains out of scope until a separate privacy decision exists.

### Typed update snapshot

Add `packages/contracts/src/update.ts` and export it from `packages/contracts/src/index.ts`:

```ts
export type UpdatePhase =
  | 'idle' | 'checking' | 'current' | 'available'
  | 'downloading' | 'installing' | 'ready' | 'error';

export interface UpdateSnapshot {
  phase: UpdatePhase;
  installMode: 'desktop' | 'npm' | 'development';
  channel: 'stable' | 'canary';
  currentVersion: string;
  targetVersion: string | null;
  releaseNotes: string | null;
  releaseUrl: string | null;
  releaseDate: string | null;
  progress: { percent: number; transferred: number; total: number } | null;
  lastCheckedAt: string | null;
  error: { code: string; message: string; retryable: boolean } | null;
}
```

### Desktop bridge

Before: main registers `pan:get-update-status`, `pan:check-for-updates`, `pan:download-update`, and `pan:quit-and-install`, while preload defines none of them.

After, `OverdeckBridge` adds only fixed methods/channels:

```ts
getUpdateStatus(): Promise<UpdateSnapshot>;
checkForUpdates(): Promise<UpdateSnapshot>;
downloadUpdate(): Promise<UpdateSnapshot>;
restartAndInstallUpdate(): void;
onUpdateStatus(listener: (status: UpdateSnapshot) => void): () => void;
```

The subscription listens only to `pan:update-status`; progress is folded into the snapshot rather than exposed through a second loosely typed channel.

### Browser HTTP surface

```text
GET  /api/update/status   -> cached UpdateSnapshot
POST /api/update/check    -> fresh check, returns UpdateSnapshot
POST /api/update/install  -> 202, starts exact-version async install
```

The existing `POST /api/system/restart-dashboard` remains the restart action after npm mode reaches ready. New routes must be added to `tests/unit/lib/overdeck/no-loss-matrix.ts` with their update-manager door classification.

## Out of scope

- Rollback command or automatic binary backup.
- Forced restarts or unattended installation.
- User-selectable stable/canary settings; this issue preserves build-derived channel selection.
- Update telemetry or a field-version analytics service.
- Delta-update optimization beyond what the generated manifest/payload supports by default.
- Updating active agent/harness processes in place; existing sessions continue with their launch-time code until restarted normally.
