# PAN-2989 — Bound the state-branch push under the per-issue record lock; fix deploy-patrol lock-owner attribution

## Glossary

- **Per-issue record lock** — an fs lock at `${OVERDECK_HOME}/locks/records/<project>/<ISSUE>.lock` serializing read-modify-write of one issue's permanent record. Acquired via `withRecordFsLock` in `src/lib/pan-dir/fs-lock.ts:115`.
- **Record write door** — `updateIssueRecord(project, issueId, mutator, options)` in `src/lib/pan-dir/record-update.ts:198`; the only legal way to mutate a permanent issue record.
- **State push / flush** — `flushAutoCommits(commitRoot)`: commits and pushes the `overdeck-state` worktree after a record write, with remote-ref-race reconciliation retries (`reconcileStatePush`, up to `MAX_STATE_PUSH_RECONCILIATIONS`).
- **Fallback verdict file** — `<workspace>/.overdeck/pipeline-verdict.json` (PAN-2583); verdict writers fall back to it when the journal write throws.
- **deploy-patrol** — `src/lib/cloister/deploy-patrol.ts`; deacon patrol that auto-deploys the dashboard by spawning `pan reload` detached.

## Background (verified 2026-07-21)

Two review-verdict journal writes for PAN-806 failed with "record lock held by deploy-patrol pid=464147", the second hold stretching 18:30:27 → after 18:38:10 (8+ minutes). Both writes fell back to `pipeline-verdict.json`.

Code-level findings (this reframing is on the issue as a comment; the original title blamed the patrol module, which never touches the lock):

1. **The push runs under the lock.** `updateIssueRecord` (`record-update.ts:208`) wraps the whole mutation AND the `flushAutoCommits` await in `withRecordFsLock`:

   ```ts
   return withRecordFsLock(project, normalizedIssueId, { writerId, recordPath }, async () => {
     ...
     const commitRoot = queueIssueRecordCommit(project, normalizedIssueId, path);
     // Start and await the explicit flush while the issue lock is held. ...
     const flushed = await Effect.runPromise(flushAutoCommits(commitRoot));
     ...
   });
   ```

   The under-lock flush is deliberate (see the code comment: no second writer may observe terminal state before its durability outcome is known), but nothing bounds it. A slow `git push` — network stall, GitHub slowness, repeated remote-ref races — holds the per-issue lock for minutes.

2. **The `deploy-patrol` owner string is an attribution artifact.** Deploy-patrol spawns the reload child with `OVERDECK_AGENT_ID=deploy-patrol` (`deploy-patrol.ts:15`, `:76`, `:336–341`). The restarted dashboard server inherits that env var, and `updateIssueRecord` defaults `writerId` to `process.env.OVERDECK_AGENT_ID` (`record-update.ts:207`). pid 464147 was the dashboard server itself; every record write it performs is attributed to "deploy-patrol".

3. **The retry budget is ~1s.** `RECORD_LOCK_RETRY_DELAYS_MS = [5, 10, 20, 40, 80, 160, 320, 360]` (`fs-lock.ts:8`) sums to ~1005ms, so any lock hold over ~1s spills a verdict write to the fallback file. Fallback keeps reads truthful (reconcile-on-read) but widens the drift window (see PAN-2988).

4. Timeline fit: the lock was acquired at 18:30:27.562Z, 13ms after the test-passed verdict write — that write's own push stalled ~8 minutes and starved the 18:38 review-passed write.

## Requirements

### Functional

- **FR-1** — The `flushAutoCommits` await inside `updateIssueRecord` MUST be bounded by a constant `RECORD_PUSH_TIMEOUT_MS = 60_000`. On timeout the lock MUST be released and the call MUST throw a distinguishable error (e.g. `RecordPushTimeoutError`) so verdict writers take their existing fallback path.
- **FR-2** — A timed-out flush MUST NOT corrupt the record: the flush promise may still settle later, so the restore path must not race it. On timeout: detach a background continuation that waits for the abandoned flush to settle, THEN runs the existing `restoreRetryableRecord(project, issueId, original, path)` if the flush failed (if the flush eventually succeeded, the record is durable — no restore). The foreground call throws immediately at timeout.
- **FR-3** — The dashboard server MUST NOT inherit `OVERDECK_AGENT_ID` from a deploy-patrol reload (or any spawner). Scrub it at server boot in `src/dashboard/server/main.ts` (capture-then-delete before any record write can occur). After the scrub, `writerId` falls back to `process-<pid>@<hostname>` — honest attribution.
- **FR-4** — `RECORD_LOCK_RETRY_DELAYS_MS` MUST be extended so the total budget is ~5s (e.g. append `500, 750, 1000, 1500` → total ~5.7s), so ordinary multi-second pushes under FR-1's bound no longer force verdict writes to the fallback.

### Non-functional

- **NFR-1** — The timeout uses fake timers in tests (`vi.useFakeTimers()` + `advanceTimersByTimeAsync`); no real 60s waits.
- **NFR-2** — The durability-ordering guarantee the under-lock flush provides is weakened ONLY on the timeout path (accepted trade-off; the fallback file preserves verdict truth and reconcile-on-read heals).
- **NFR-3** — No `execSync`; no new sync primitives.

## Work items

### 1. Bound the flush under the lock (`src/lib/pan-dir/record-update.ts`)

Traces: FR-1, FR-2.

Add near `MAX_STATE_PUSH_RECONCILIATIONS`:

```ts
export const RECORD_PUSH_TIMEOUT_MS = 60_000;

export class RecordPushTimeoutError extends Error {
  constructor(issueId: string) {
    super(`State push for ${issueId} exceeded ${RECORD_PUSH_TIMEOUT_MS}ms under the record lock; releasing the lock. The verdict writer's fallback path preserves the write.`);
    this.name = 'RecordPushTimeoutError';
  }
}
```

In `updateIssueRecord`, replace the direct `await Effect.runPromise(flushAutoCommits(commitRoot))` with a raced timeout:

```ts
const flushPromise = Effect.runPromise(flushAutoCommits(commitRoot));
let timeout: ReturnType<typeof setTimeout>;
const timeoutPromise = new Promise<never>((_, reject) => {
  timeout = setTimeout(() => reject(new RecordPushTimeoutError(normalizedIssueId)), RECORD_PUSH_TIMEOUT_MS);
});
let flushed;
try {
  flushed = await Promise.race([flushPromise, timeoutPromise]);
} catch (err) {
  if (err instanceof RecordPushTimeoutError) {
    // FR-2: the abandoned flush may still settle — restore only after it does,
    // and only if it failed. Runs lock-free in the background.
    void flushPromise
      .catch(() => undefined)
      .then((late) => { if (!late || late.pushed === false) return restoreRetryableRecord(project, normalizedIssueId, original, path); })
      .catch(() => undefined);
    throw err; // lock releases via withRecordFsLock finally; writers fall back (PAN-2583)
  }
  throw err;
} finally {
  clearTimeout(timeout!);
}
```

(Adjust to the file's existing style; the key semantics are race + settle-then-restore + immediate throw.)
