# PAN-3568 — Adopt Effect diagnostics (@effect/language-service) as a mechanical CI gate and agent feedback loop

**Issue:** https://github.com/eltmon/overdeck/issues/3568
**Companion bug issue (lands first):** https://github.com/eltmon/overdeck/issues/3567
**Author:** conversation, 2026-08-05. All file/line references verified against the tree at `main` (dfbbb45a66) on 2026-08-05.

## 1. Glossary

- **Effect diagnostics** — extra compiler diagnostics specific to Effect code (e.g. an Effect value constructed but never run), produced by the `@effect/language-service` TypeScript plugin, not by stock `tsc`.
- **`@effect/language-service`** — a TypeScript language-service plugin (installed version 0.84.2, bin name `effect-language-service`) providing ~40 Effect-aware diagnostic rules, quickfixes, and completions. Configured per-tsconfig via a `compilerOptions.plugins` entry.
- **Patch mode** — `effect-language-service patch` modifies the local `node_modules/typescript` install so that plugin diagnostics are also emitted by CLI `tsc` runs (stock `tsc` ignores language-service plugins). Without the patch, diagnostics appear only in editors.
- **`floatingEffect`** — the flagship correctness rule: an `Effect` value that is neither `yield*`ed, run, nor assigned — i.e. constructed and dropped. Six shipping instances exist today (PAN-3567).
- **Diagnostic lane** — this PRD's architecture: a set of `tsconfig.effect-diag.json` variants that `extends` the real project tsconfigs and add the plugin, consumed ONLY by the new ratchet script. The real tsconfigs stay plugin-free, so every existing gate is provably untouched.
- **Ratchet** — a shrink-only baseline gate: current findings are recorded in a baseline file; new findings fail the build; the baseline may be lowered (`--update`) but never raised. Existing examples: `scripts/lint-dashboard-types.sh` (count ratchet, baseline 54), `scripts/lint-frontend-types.sh` (line-level ratchet, baseline 0, PAN-3192).
- **Ratchet audit** — `scripts/lint-ratchet-audit.sh`: commits that grow an audited baseline/allowlist must carry an issue reference (`[A-Z]+-[0-9]+` or `#[0-9]+`) in the message.
- **Verification gate** — Cloister runs `quality_gates` from `projects.yaml` after a work agent signals done; for this project `typecheck` and `lint` are both `required: true`, so anything wired into `npm run lint` reaches work agents mechanically.

## 2. Background and verified evidence (measured 2026-08-05)

- ~982 files import `effect`/`@effect/*` (480 in `src/lib`, 212 in `src/dashboard/server`). `Effect.gen` appears 1,135 times; there are 1,217 non-test `Effect.runPromise` call sites across 322 files, plus 904 `Effect.promise` and 458 `Effect.tryPromise` bridges. Every bridge is an opportunity for the floating-Effect mistake.
- The mistake has shipped: 6 baselined `TS2741: Property 'then' is missing in type 'Effect<...>'` errors plus ~12 cascading `TS18046` in `scripts/dashboard-types-baseline.txt` (count 54) are Effects that never run — including a bypassed workspace-deletion guard. PAN-3567 fixes those six; this PRD builds the gate that refuses the class.
- `@effect/language-service@0.84.2` is already exact-pinned in the Bun workspace catalog (`package.json:52`) and declared in `packages/contracts/package.json:36` (`"catalog:"`, devDependencies) — but no tsconfig anywhere has a `plugins` entry, no `prepare` step patches tsc, and the package is not resolvable from the repo root. It is currently dead weight.
- Everything is on `effect@4.0.0-beta.73` (single-version discipline enforced by `scripts/check-effect-versions.mjs`, PAN-1562) and TypeScript 5.9.3. The successor tool `@effect/tsgo` requires TypeScript ≥ 7 — out of scope (see Non-goals).
- Blind spot: `packages/effect-acp` (14 of 16 files Effect-heavy) is typechecked by no gate — it has a local `typecheck` script (`packages/effect-acp/package.json:36`) that nothing invokes.

Key facts from the installed plugin's README (`node_modules/@effect/language-service/README.md` under `packages/contracts` today; repo-root after WI-1):

- Rule severities are configurable per rule: allowed values `off`, `error`, `warning`, `message`, `suggestion` (README ~line 187). Defaults vary per rule (`floatingEffect`, `missingEffectError`, `classSelfMismatch` default to error; `duplicatePackage` to warning; `anyUnknownInErrorContext` off).
- Exit-code knobs: `ignoreEffectErrorsInTscExitCode`, `ignoreEffectWarningsInTscExitCode` (both default false), `ignoreEffectSuggestionsInTscExitCode` (default true) — README ~lines 192–194.
- Inline per-site overrides: `// @effect-diagnostics effect/floatingEffect:off` comments (README ~line 352).

## 3. Requirements

### Functional

- **FR-1** — `@effect/language-service` is resolvable from the repo root as a devDependency, pinned via the existing catalog entry.
- **FR-2** — Four diagnostic-lane tsconfigs exist (`tsconfig.effect-diag.json` at root; `src/dashboard/server/tsconfig.effect-diag.json`; `packages/contracts/tsconfig.effect-diag.json`; `packages/effect-acp/tsconfig.effect-diag.json`), each `extends` its project tsconfig and adds the plugin. The real project tsconfigs remain plugin-free.
- **FR-3** — CLI `tsc` runs against the diag tsconfigs emit Effect diagnostics, and this survives a fresh `bun install` in a new worktree (patch persistence).
- **FR-4** — `scripts/lint-effect-diagnostics.sh` enforces a line-level shrink-only baseline (`scripts/effect-diagnostics-baseline.txt`) over the four lanes, is wired into `npm run lint`, is covered by `lint-ratchet-audit.sh`, and has a unit test mirroring `tests/unit/scripts/lint-frontend-types.test.ts`.
- **FR-5** — `packages/effect-acp` is typechecked by the root `npm run typecheck` chain.
- **FR-6** — `roles/review-correctness.md` instructs the correctness reviewer to treat NEW effect-diagnostic findings as blocking.
- **FR-7** — Documentation: new `docs/EFFECT-DIAGNOSTICS.md`; a pointer paragraph in `CLAUDE.md`. No Mintlify page (this is dev-repo tooling, not a product surface — stated deliberately per the docs-work-item rule).

### Non-functional

- **NFR-1** — Existing gates are behaviorally unchanged: `npm run typecheck` output/exit unchanged; `scripts/lint-dashboard-types.sh` still passes at baseline 54 (or lower after PAN-3567); `scripts/lint-frontend-types.sh` still passes at 0. Mechanically checkable by running all three before/after.
- **NFR-2** — Added wall-clock: the new lint step adds four `tsc --noEmit` runs; total `npm run lint` growth must stay under ~90s on the dev machine. If it exceeds that, drop the contracts lane (lowest Effect-bug density of the four) and note it in the docs.
- **NFR-3** — The plugin version stays exact-pinned via the catalog; upgrades are deliberate commits that re-verify the baseline (a version bump that changes emitted findings must adjust the baseline in the same commit, with the issue reference the ratchet audit requires).

## 4. Decisions made in this document (no judgment calls left to the executor)

- **D-1: Isolation via extends-variant tsconfigs, not plugin entries in project tsconfigs.** Only the ratchet script consumes the diag tsconfigs, so existing gates cannot see plugin output regardless of rule severities. Editor wiring is deferred (Non-goals) — the primary consumer of diagnostics in this repo is agents running CLI gates, not editors.
- **D-2: Keep the plugin's default per-rule severities in v1.** No severity map, no per-file `overrides` array. Both `ignoreEffectErrorsInTscExitCode` and `ignoreEffectWarningsInTscExitCode` are set `true` in the diag tsconfigs so the diag lane's tsc exit code reflects only real TS errors (which the base gates already own).
- **D-3: Findings are identified by the plugin's diagnostic codes, not by severity labels.** WI-4 determines the code range from a fixture at implementation time and pins it as a commented regex constant in the script; the unit test locks it. Rationale: real TS errors and effect findings share the same output stream in a diag-lane run and must be separated deterministically.
- **D-4: Enforcement lives solely in the ratchet.** Promotion of any individual rule to a hard error gate is a separate future issue, taken only after that rule's slice of the baseline reaches zero.
- **D-5: PAN-3567 lands before the baseline is seeded**, so the six known bugs are fixed rather than baselined. If sequencing slips, seeding with them present is acceptable — they then burn down via the ratchet.
- **D-6: The frontend is excluded.** 9 of 963 frontend files import Effect; the lane would be near-empty and the frontend tsconfig churn isn't worth it.
- **D-7: `scripts/check-effect-versions.mjs` keeps its `EXCLUDED` entry** (`scripts/check-effect-versions.mjs:33`): the plugin is a devtool, not a runtime dep; the catalog pin plus NFR-3 govern it.
- **D-8: Inline `// @effect-diagnostics effect/<rule>:off` comments are the sanctioned per-site escape hatch**, and each one must carry a trailing comment with an issue reference — enforced by review convention, documented in WI-7 (not mechanically in v1).

## 8. Non-goals

- `@effect/tsgo` adoption (needs TypeScript ≥ 7; we are on 5.9.3). It is the successor with ~80 rules and a structured-output `diagnostics` CLI; revisit alongside any TS 7 upgrade.
- Editor/LSP wiring of the plugin (D-1 defers it; agents are the consumer that matters here).
- Enabling style / effect-native rule categories, per-file `overrides` arrays, or severity promotion to hard errors (D-4's later step).
- Typechecking test files; burning down the seeded baseline (follow-up work through the ratchet).
- Any change to `quality_gates` in `projects.yaml` — `lint` is already required, which is the whole point of wiring into the lint chain.

## 9. Repo rules restated for the executor

- **Commit often on main / feature branch per pipeline** — each WI is a coherent commit; push before `pan task done` on each xBRIEF item.
- **Never weaken a ratchet** — `--update` lowers only; a red guard test means the protection was reopened, not that the test is stale.
- **No `execSync` in server-reachable code** — not applicable here (shell scripts only), but do not add Node wrappers around the lane that import into server code.
- **Fake timers for any delay-based tests** — the WI-4 tests shell out synchronously; if any polling/retry is added to the script tests, use `vi.useFakeTimers()`.
- **Husky/commitlint** — commits touching `roles/*.md` need the `Prompt-Change:` trailer (WI-6); never `--no-verify`.
- **`bun install`, never symlinked node_modules** in worktrees (CP-3 verification).

## 10. Hazards for the implementing agent

- Do not put the `plugins` entry into the real project tsconfigs "while you're there" — D-1's isolation is the load-bearing design; AC-2 checks it.
- Do not filter findings by `warning TS`/`error TS` severity prefixes — severity is configurable and version-dependent; D-3's code-range filter is the contract.
- The patch touches `node_modules/typescript`, which is shared with tsdown dts builds — CP-2 exists because contamination there would corrupt published contracts types. Take the checkpoint seriously; the fallback is fully specified.
- `Effect.promise(() => import('...'))` sites are correct (dynamic import returns a Promise) — if the plugin flags any, that's a finding to investigate against the plugin, not a site to "fix".
