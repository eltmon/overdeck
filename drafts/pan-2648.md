# PAN-2648 — Remove Beads and execute the vBRIEF checklist directly

**Status:** Draft  
**Tracking issue:** [PAN-2648](https://github.com/eltmon/overdeck/issues/2648)  
**Supersedes:** [PAN-2641](https://github.com/eltmon/overdeck/issues/2641)

**Audience:** Implementation, review, test, and documentation agents

## Glossary

- **Checklist:** `plan.items[]` in one issue's immutable vBRIEF specification. Each item already has an ID, title, status, acceptance-criteria children, metadata, and dependency edges.
- **Merged vBRIEF view:** The immutable canonical spec with the per-issue record's `statusOverrides` applied by `readWorkspacePlanSync()` / `readWorkspacePlan()`. This is the runtime checklist presented to agents and the dashboard.
- **Status override:** A durable `Record<string, string>` on the issue record under `overdeck-state`. Keys are item IDs or `itemId.subItemId`; values are vBRIEF statuses. It records runtime progress without rewriting the canonical spec.
- **Task operation:** One existing vBRIEF operation: `claim`, `done`, `block`, `unblock`, or `cancel`. Read operations are `next` and `show`.
- **Actionable item:** A checklist item not `completed`, `cancelled`, `running`, or explicitly `blocked`, whose incoming `blocks` edges are resolved.
- **Active slice:** The existing bounded prompt projection for one vBRIEF item, including its acceptance criteria, resolved blockers, unlocks, constraints, and synthesis context.
- **Beads integration:** Every Overdeck-owned adapter around the external `bd` process: Dolt home/layout, locks, redirects, bootstrap, sync, export, reconciliation, telemetry, materialization, queries, CLI, prompts, dashboard rollups, skills, and docs.
- **No-loss audit:** A focused, mechanically enforced inventory that gives every old Beads-backed command, route, action, status, view, prompt behavior, and pipeline gate either a vBRIEF-task home or an explicit deletion disposition.

## Problem

Overdeck's actual managed-work requirement is a checklist: choose the next unblocked plan item, mark it active, implement it, commit and push it, mark it done, and continue. The vBRIEF already contains that checklist and its dependency graph.

Overdeck nevertheless materializes the checklist into Beads and then owns a second operational system around it: an external binary, embedded Dolt startup, a cross-process lock, canonical-home redirects, state-branch exports, remote bootstrap/push/pull, recovery, reconciliation, compaction, orphan sweeping, health telemetry, dashboard snapshots, installation, skills, and prompt rules. [PAN-2641](https://github.com/eltmon/overdeck/issues/2641) proposed adding a persistent Dolt server, lifecycle management, fallback, boot tests, recovery, and observability to improve the performance of that duplicate task store. The operator rejected that complexity; the issue is closed as not planned.

The replacement is not a new task system. [PAN-977](https://github.com/eltmon/overdeck/issues/977) already shipped the replacement engine. PR [#1054](https://github.com/eltmon/overdeck/pull/1054) explicitly accepted:

- vBRIEF-native dispatchable items, waves, critical path, and overlap checks;
- `next`, `show`, `claim`, `done`, `block`, `unblock`, and `cancel` operations;
- sequence conflict detection and atomic writes;
- durable runtime status in the per-issue record;
- a vBRIEF-first task graph “for migration away from Beads precedence.”

This PRD finishes that cutover and deletes the compatibility mirror.

## Goals

1. Make managed work one vBRIEF checklist with one runtime status overlay.
2. Remove `bd`, Dolt, and `.beads/` from every Overdeck runtime path.
3. Preserve item-by-item execution, dependency ordering, conditional inspection, one pushed commit per item, completion gating, recovery, and dashboard visibility.
4. Delete substantially more code than is added.
5. Leave existing `.beads/` data untouched but unused; no data migration and no automatic deletion.

## Non-goals

- Build a task database, daemon, server, cache, event log, sync protocol, or replacement tracker.
- Import Beads history into `statusOverrides` or another store.
- Create new checklist items during execution. Missing scope returns to planning for a vBRIEF revision.
- Change GitHub/Linear issue authority, PR/review/test/UAT/merge state, agent runtime state, or workspace ownership.
- Rewrite old historical documents merely because they mention Beads. Only live docs, generated context, and operator guidance are updated.
- Automatically delete any project or state-worktree `.beads/` directory. The system simply stops reading and writing it.

## Product decisions

### D-1 — One checklist, not four task authorities

The immutable vBRIEF defines checklist content and edges. The per-issue record's `statusOverrides` defines runtime item status. The merged vBRIEF view is the only task read model. There is no Beads mirror, task table, task cache, JSONL export, or task-event database.

### D-2 — Status writes do not rewrite the canonical spec

`src/lib/vbrief/io.ts` states that the canonical spec is immutable after planning. The current DAG mutation helpers also write a workspace/canonical plan file and mirror to the record, a transitional contradiction introduced during [PAN-977](https://github.com/eltmon/overdeck/issues/977). Resolve it in favor of the documented PAN-1124 model:

- `next` and `show` read the merged view;
- `claim/done/block/unblock/cancel` validate the transition against the merged view;
- the mutation writes only the affected item/sub-item statuses to the per-issue record through the existing record writer;
- no runtime task command rewrites `spec.vbrief.json`.

The issue record writer is already serialized and durable on `overdeck-state`; do not add a second lock or event log.

### D-3 — Minimal CLI

Expose exactly:

```text
pan task next <issue>
pan task show <issue> <item>
pan task claim <issue> <item>
pan task done <issue> <item> [--reason <text>]
pan task block <issue> <item> --reason <text>
pan task unblock <issue> <item> [--reason <text>]
pan task cancel <issue> <item> --reason <text>
```

No `create`, `delete`, `dep`, `compact`, `sweep`, `stats`, `doctor`, `upgrade`, or generic update command is added. Planning authors checklist structure; execution only changes status.

### D-4 — Item IDs replace bead IDs everywhere

Work prompts, commits, inspection, active slices, dashboard rows, nudge text, logs, and API payloads use the existing vBRIEF item ID. Rename `pan inspect --bead <id>` to `pan inspect --item <id>` and remove the `bd show` fallback. Do not preserve a runtime Beads-ID resolver.

### D-5 — Preserve user data by abandonment, not migration

Upgrade stops touching `.beads/`. It does not remove old directories, export them, validate them, or migrate their contents. Documentation may say they are unused legacy data and may be removed manually at the operator's discretion, but must not provide a destructive “acceptance test.”

### D-6 — Compatibility is source-level, not a second runtime

No deprecated `pan beads` forwarding shim is kept. Generated agent instructions and live docs change atomically in the same release. Historical transcripts and old commits can retain the word “bead.” Existing API clients inside this repo move from `/beads` to `/tasks` in the same change.

## Requirements

### Functional requirements

- **FR-1:** `pan task next/show/claim/done/block/unblock/cancel` operates on vBRIEF item IDs and never invokes `bd`.
- **FR-2:** Task reads use `readWorkspacePlanSync()` / `readWorkspacePlan()` so canonical spec content and per-issue `statusOverrides` are always merged.
- **FR-3:** Task mutations validate the target item and allowed transition, then write only item/sub-item status overrides through the per-issue record writer.
- **FR-4:** Dependency readiness, waves, critical path, file-overlap, active-slice, and swarm behavior continue to use the existing vBRIEF DAG.
- **FR-5:** Planning completion promotes the vBRIEF and marks planning complete without materializing Beads or requiring a Beads warning/recovery path.
- **FR-6:** Agent start requires a readable, implementation-ready vBRIEF, not Beads presence or `bd` availability.
- **FR-7:** The work prompt loops one item at a time: next, claim, implement, commit, push, done, optional inspect, next.
- **FR-8:** `pan done` fails when any checklist item or acceptance-criteria child remains non-terminal; it does not query or synchronize Beads.
- **FR-9:** Idle nudging, stuck remediation, orphaned completion recovery, flywheel readiness, backlog readiness, and swarm advance derive remaining/ready work from the merged vBRIEF.
- **FR-10:** Inspection accepts `--item`, reads the item's vBRIEF active slice/metadata, and preserves `requiresInspection`/inspection-depth/no-inspection behavior without `bd show`.
- **FR-11:** Dashboard task list, counts, progress, task rail/tab/dialog/kanban, resource activity signals, and issue detail read the merged vBRIEF and use task terminology.
- **FR-12:** `/api/issues/:id/tasks` returns vBRIEF task rows; `/api/issues/:id/tasks/:itemId/inspect` inspects the item. Beads freshness/Dolt health fields and events are removed.
- **FR-13:** Install, sync, doctor, workspace creation, state migration, teardown, close-out, dashboard boot, and Deacon boot neither require nor invoke `bd`, Dolt, redirects, or `.beads/`.
- **FR-14:** All Beads-only commands, services, source modules, lifecycle jobs, exports, locks, prerequisites, telemetry, skills, rules, templates, docs, and tests are deleted after their retained behavior has a verified vBRIEF home.
- **FR-15:** Existing `.beads/` data is left unchanged and ignored.
- **FR-16:** The PR includes a mechanically checked no-loss matrix covering every operator-facing and pipeline surface listed below.
- **FR-17:** The PR reports exact added/deleted line counts and is net-negative by at least 8,000 lines overall. If it is not, implementation stops for operator review rather than adding abstractions to meet the feature.

### Non-functional requirements

- **NFR-1:** No new canonical task store, cache, database table, daemon, server, background poller, sync loop, or recovery protocol.
- **NFR-2:** No synchronous process or filesystem calls are added to dashboard server paths. No `execSync` is introduced.
- **NFR-3:** Runtime task reads are local file/record reads and must not spawn a process.
- **NFR-4:** Delay/retry tests use fake timers. Do not retain real-delay tests from the Beads process-lock implementation.
- **NFR-5:** The dashboard continues to boot under Node 22. Because dashboard boot imports change, run a throwaway runtime boot test before any live restart.
- **NFR-6:** No-inspection policy remains mechanically enforced: items with `requiresInspection: false` never trigger inspection.
- **NFR-7:** State-branch writes continue through the per-issue record writer; no direct state-worktree writes are added.
- **NFR-8:** Existing unrelated dirty files in the primary worktree and state worktree are not modified, committed, or cleaned up.

## Implementation detail

### Canonical task mutation

Before (`src/lib/vbrief/dag-cli.ts`, search `Mutations write to the canonical spec on main`):

```ts
const planPath = findPlanSync(options.workspacePath)
return applyTaskOperationToPlanFile(planPath, operation, options.workspacePath)
```

After:

```ts
const doc = readWorkspacePlanSync(options.workspacePath)
const result = applyTaskOperation(doc, operation)
writeStatusOverridesSync(project, options.issueId, statusesFrom(result, operation))
return result
```

`statusesFrom()` is a small pure helper returning the parent item override and affected sub-item overrides. It must not write a spec file, create a lock directory, or add another persistence format.

### Completion gate

Before (`src/lib/work/done-preflight.ts`, search `Check 1: Open beads`):

```ts
const beadFailures = await Effect.runPromise(checkOpenBeads(workspacePath, issueId))
// fetch closed beads and sync each back into vBRIEF
const acFailures = checkVBriefACStatusSync(workspacePath)
```

After:

```ts
const doc = readWorkspacePlanSync(workspacePath)
const taskFailures = checkIncompletePlanItems(doc)
const acFailures = checkVBriefACStatusSync(workspacePath)
```

`checkIncompletePlanItems()` reports item IDs/titles for every status other than `completed` or `cancelled`. A blocked item is incomplete and prevents `pan done`.

### Task API row

`GET /api/issues/:id/tasks` maps each merged `VBriefItem` to the existing task presentation fields. Use `plan.edges` to derive `blockedBy`; use item `created/completed/metadata.statusUpdatedAt` when present. Remove `source`, Dolt freshness, last-pull, and sync-error fields rather than fabricating replacements.
