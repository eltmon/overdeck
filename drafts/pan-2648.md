# PAN-2648 — Remove Beads and execute the vBRIEF checklist directly

**Status:** Draft v2 (2026-07-14 revision: adds the verified engine audit and the mandatory concurrency/durability model; supersedes the 2026-07-13 draft in place)
**Tracking issue:** [PAN-2648](https://github.com/eltmon/overdeck/issues/2648)
**Supersedes:** [PAN-2641](https://github.com/eltmon/overdeck/issues/2641) (closed, not planned)

## Revision note (v2)

The v1 draft claimed "The issue record writer is already serialized and durable on `overdeck-state`; do not add a second lock." **That claim is false and is retired.** `withIssueRecordLock` (`src/lib/pan-dir/record-lock.ts:10`) is an in-process promise chain; it provides zero cross-process protection, and `writeStatusOverridesSync` (`src/lib/pan-dir/record.ts:598`) performs an unlocked read-modify-write. Concurrent processes (work-agent CLI, dashboard server, Deacon patrols, swarm slots) can silently lose updates today. This revision adds the concurrency model (D-7), the engine-audit defect list (E-1…E-9), FR-18…FR-26, NFR-9…NFR-13, and splits WI-2 into WI-2A/WI-2B. No existing FR/NFR/WI/AC id is renumbered.

## Glossary

- **Checklist:** `plan.items[]` in one issue's immutable vBRIEF specification. Each item has an ID, title, status, acceptance-criteria children, metadata, and dependency edges.
- **Merged vBRIEF view:** The immutable canonical spec with the per-issue record's `statusOverrides` applied by `readWorkspacePlanSync()` / `readWorkspacePlan()` (`src/lib/vbrief/io.ts`). This is the only runtime checklist read model.
- **Per-issue record (the record):** `records/<issue>.json` on the `overdeck-state` branch, on disk at `${OVERDECK_HOME}/state/<project>/records/<issue>.json`. Read and written only through `src/lib/pan-dir/record.ts` (the record door). Auto-committed to git by `queueIssueRecordCommit()`.
- **Status override:** `record.statusOverrides`, a `Record<string, string>`; keys are item IDs or `itemId.subItemId`, values are vBRIEF statuses. Records runtime progress without rewriting the canonical spec.
- **Task operation:** One of `claim`, `done`, `block`, `unblock`, `cancel`. Read operations are `next` and `show`.
- **Task claim:** A new record field recording *which agent* owns a `running` item: `record.tasks.claims[itemId] = { writerId, agentId, pid, host, claimedAt }`.
- **Writer id:** The stable identity of the mutating process: `process.env.OVERDECK_AGENT_ID` when set (every pan-spawned agent and conversation has one), else `cli-<pid>@<hostname>`.
- **Record fs-lock:** A cross-process mutual-exclusion lock for one issue's record: an atomically created lock *directory* (`mkdir` fails with `EEXIST` if it exists) containing `owner.json` (writerId, pid, acquiredAt), with dead-PID reclaim and bounded async retry. Lives under `${OVERDECK_HOME}/locks/`, never inside a git worktree.
- **Stale claim:** A claim whose owning process is provably dead (`process.kill(pid, 0)` throws `ESRCH` and the agent's runtime state is not `running`).
- **Task sequence:** `record.tasks.sequence`, a monotonically increasing integer bumped by every task mutation; supports optional compare-and-set (`--expected-sequence`).
- **Actionable item:** A checklist item not `completed`, `cancelled`, `running`, or `blocked`, whose incoming `blocks` edges are all resolved.
- **Active slice:** The existing bounded prompt projection for one vBRIEF item (`createActiveSlice`, `src/lib/vbrief/dag.ts:449`).
- **Beads integration:** Every Overdeck-owned adapter around the external `bd` process: Dolt home/layout, locks, redirects, bootstrap, sync, export, reconciliation, telemetry, materialization, queries, CLI, prompts, dashboard rollups, skills, and docs.
- **No-loss audit:** A focused, mechanically enforced inventory that gives every old Beads-backed command, route, action, status, view, prompt behavior, and pipeline gate either a vBRIEF-task home or an explicit deletion disposition.

## Problem

Overdeck's managed-work requirement is a checklist: choose the next unblocked plan item, claim it, implement it, commit and push it, mark it done, and continue. The vBRIEF already contains that checklist and its dependency graph.

Overdeck nevertheless materializes the checklist into Beads and owns a second operational system around it: an external ~137 MB binary, embedded Dolt startup (~2s per invocation, [PAN-2640](https://github.com/eltmon/overdeck/issues/2640)), a cross-process lock, canonical-home redirects, state-branch exports, remote bootstrap/push/pull ([PAN-2613](https://github.com/eltmon/overdeck/issues/2613)), recovery, reconciliation, compaction, orphan sweeping, health telemetry, dashboard snapshots, installation, skills, and prompt rules. [PAN-2641](https://github.com/eltmon/overdeck/issues/2641) proposed a persistent Dolt server on top; the operator rejected that complexity and it is closed as not planned.

[PAN-977](https://github.com/eltmon/overdeck/issues/977) shipped a vBRIEF-native task engine, but its mutation side was **never wired into production** (`runTaskCommand` has zero non-test callers) and carries the concurrency defects audited below. This PRD finishes the cutover correctly: harden the engine's write path for concurrent multi-agent use, expose it as `pan task`, migrate every Beads consumer, and delete the Beads stack.

## Goals

1. Make managed work one vBRIEF checklist with one runtime status overlay.
2. Make concurrent task mutation safe: multiple agents, the dashboard server, and Deacon patrols operating on the same issue must never lose an update, double-claim an item, or corrupt a record — including across process crashes.
3. Remove `bd`, Dolt, and `.beads/` from every Overdeck runtime path.
4. Preserve item-by-item execution, dependency ordering, conditional inspection, one pushed commit per item, completion gating, recovery, and dashboard visibility.
5. Delete substantially more code than is added.
6. Leave existing `.beads/` data untouched but unused; no data migration and no automatic deletion.

## Non-goals

- Build a task database, daemon, server, cache, event log, sync protocol, or replacement tracker.
- Import Beads history into `statusOverrides` or another store.
- Create new checklist items during execution. Missing scope returns to planning for a vBRIEF revision.
- Change GitHub/Linear issue authority, PR/review/test/UAT/merge state, agent runtime state, or workspace ownership.
- Add cross-machine coordination beyond the existing per-issue owner lease (`claimIssueOwner`, `src/lib/pan-dir/record.ts:484`, PAN-1908). One machine owns one in-flight issue; the fs-lock serializes processes on that machine.
- Rewrite historical documents merely because they mention Beads. Only live docs, generated context, and operator guidance are updated.
- Automatically delete any project or state-worktree `.beads/` directory.

## Engine audit — verified defects in the PAN-977 engine (2026-07-14)

The implementer MUST treat these as bugs to fix, not behavior to preserve. Each was verified against `main` on 2026-07-14; line numbers may drift — the quoted search strings will not.

- **E-1 — Mutations rewrite the canonical spec.** `runTaskCommand` (`src/lib/vbrief/dag-cli.ts:196`, search `Mutations write to the canonical spec on main`) resolves `findPlanSync()` — post-PAN-1124 that is the canonical spec on `overdeck-state` — and `applyTaskOperationToPlanFile` rewrites it (status change + sequence bump). This violates the PAN-1124 invariant that the spec is immutable after planning and that only `plan.status` may change via `updateSpecStatus()`. Fix: mutations write ONLY the record (D-7/CD-1); the spec stays byte-identical.
- **E-2 — No status-transition guard.** `applyTaskOperation` (`src/lib/vbrief/dag.ts:586`) sets `item.status = statusForOperation(type)` unconditionally. Claiming an item that is already `running` (claimed by another agent) or `completed` silently succeeds. This is the direct cause of the double-claim hazard the operator flagged. Fix: CD-3 transition matrix.
- **E-3 — No claim ownership.** Nothing records which agent claimed an item, so there is no way to reject a competing claim, attribute work, or recover a claim held by a crashed agent. Fix: CD-4 claims + CD-5 stale-claim release.
- **E-4 — The record write path has no cross-process lock.** `withIssueRecordLock` (`src/lib/pan-dir/record-lock.ts:10`) is an in-process promise chain keyed by issue id. `writeStatusOverridesSync` (`src/lib/pan-dir/record.ts:598`) does read-modify-write with no lock at all. Roughly 20 production files write the record via `writeIssueRecordSync`/`writeStatusOverridesSync`/`writeIssueRecordForWorkspaceSync` (`git grep -l` on those names), each a whole-record write: a concurrent task claim and pipeline-verdict write can silently drop one another. Fix: CD-2 record fs-lock on every record RMW.
- **E-5 — The sync CLI lock cannot wait.** `assertSingleWriter` in `dag-cli.ts:35` makes 2 attempts with no delay (a sync function cannot sleep), so concurrent same-issue claims fail outright instead of waiting ~1s like the async path (`WRITER_LOCK_RETRY_DELAYS_MS`, `dag.ts:767`). Fix: CD-7 single async implementation; delete the sync duplicate.
- **E-6 — Duplicated concurrency-critical code.** `dag.ts` (async) and `dag-cli.ts` (sync) implement lock/atomic-write/mirror twice and have already drifted (retry budgets differ). Fix: CD-7.
- **E-7 — Issue id derived from a path regex, failing silently.** `mirrorTaskOperationToRecord` (`dag-cli.ts:115`, `dag.ts:876`) extracts the issue id via `workspacePath.match(/feature-([a-z]+-\d+)$/i)` and **silently skips the record write** when it does not match. Fix: CD-6 — `issueId` is an explicit required parameter; a missing id is an error.
- **E-8 — Lock directories and tmp files are created next to the plan file.** `lockPathForPlan` (`dag.ts:709`) is `<planPath>.writer.lock`; when the plan path is the canonical spec, locks and `.tmp` transaction files land inside the shared `overdeck-state` worktree, polluting `git status` (this dirt blocked a `pan start` on 2026-07-14). Fix: CD-2 lock root under `${OVERDECK_HOME}/locks/`.
- **E-9 — Atomic writes do not fsync.** `writePlanFileAtomically` (`dag.ts:853`) and `writeRecordFileAtomicSync` (`src/lib/pan-dir/record.ts:353`) do write-tmp + rename with no `fsync` of file or directory. This machine has verifiably zeroed mid-write files on crash reboot (PAN-2623 lineage). The record writer at least does a read-back parse; the plan writer does not. Fix: CD-8 fsync; plan writes disappear anyway under CD-1.

Good parts to keep: the pure graph functions (`getDispatchableItems`, `groupItemsByWave`, `criticalPath`, `hasFileOverlap`, `createActiveSlice`), the pure `applyTaskOperation` shape (after adding the transition guard), the mkdir-lock + owner.json + dead-PID-reclaim + bounded-retry pattern in `dag.ts:769-822` (relocated, not next to the plan), and `writeRecordFileAtomicSync`'s read-back verification plus `preserveCorruptRecordSync`.

## Product decisions

### D-1 — One checklist, not four task authorities

The immutable vBRIEF defines checklist content and edges. The per-issue record defines runtime status (`statusOverrides`) and ownership (`tasks.claims`). The merged vBRIEF view is the only task read model. There is no Beads mirror, task table, task cache, JSONL export, or task-event database.

### D-2 — Status writes never rewrite the canonical spec

`claim/done/block/unblock/cancel` validate against the merged view, then write only the affected item/sub-item overrides plus the claim/sequence fields to the record, under the record fs-lock. No runtime task command writes any `spec.vbrief.json`, anywhere. (Replaces v1 D-2, which wrongly asserted the record writer was already serialized.)

### D-3 — Minimal, per-issue-scoped CLI

Task commands are always scoped to one issue — there is no global queue. Concurrency across issues needs no coordination at all (different record files); concurrency within one issue (swarm slots) is handled by the fs-lock, the transition matrix, and claims.

```text
pan task next <issue>                          # dispatchable items for THIS issue (read-only)
pan task show <issue> <item>                   # one merged item (read-only)
pan task claim <issue> <item>                  # pending → running, records the claim
pan task done <issue> <item> [--reason <text>] # running → completed, claim-owner only
pan task block <issue> <item> --reason <text>
pan task unblock <issue> <item> [--reason <text>]
pan task cancel <issue> <item> --reason <text>
```

All mutating verbs accept `--expected-sequence <n>` (CAS) and `--force` (override the owner/transition guard; requires `--reason`; logged into item metadata). No `create`, `delete`, `dep`, `compact`, `sweep`, `stats`, `doctor`, `upgrade`, or generic update verb. Planning owns checklist structure; execution only changes status.

### D-4 — Item IDs replace bead IDs everywhere

Work prompts, commits, inspection, active slices, dashboard rows, nudge text, logs, and API payloads use the vBRIEF item ID. Rename `pan inspect --bead <id>` to `pan inspect --item <id>` and remove the `bd show` fallback. No runtime Beads-ID resolver is preserved.

### D-5 — Preserve user data by abandonment, not migration

Upgrade stops touching `.beads/`. It does not remove, export, validate, or migrate old directories. Docs may say they are unused legacy data removable at the operator's discretion, but must not provide a destructive "acceptance test" (bundled rule: no destructive recovery tests).

### D-6 — Compatibility is source-level, not a second runtime

No deprecated `pan beads` forwarding shim. Generated agent instructions and live docs change atomically in the same release. In-repo API clients move from `/beads` to `/tasks` in the same change.

### D-7 — Concurrency and durability model (normative)

The concurrent actors on one issue's task state, all on the machine holding the issue's owner lease: N swarm work-agent CLI processes, the dashboard server, Deacon patrols, the verification runner, the flywheel, and operator CLI invocations. The following rules are requirements, not suggestions.

- **CD-1 — Single write door.** Exactly one function performs task mutations: `applyTaskStatusChange(project, issueId, operation)` in `src/lib/pan-dir/record.ts` (or a sibling module in `pan-dir/`). CLI, server routes, Deacon, and swarm all call it. It is `async`. Nothing else writes `statusOverrides` or `tasks.*`.
- **CD-2 — Record fs-lock.** Extract the proven mkdir-lock pattern from `dag.ts:769-822` (owner.json with `{writerId, pid, acquiredAt}`, `EEXIST` loop, dead-PID reclaim via `isPidDead`, bounded retry delays `[5,10,20,40,80,160,320,360]` ms, cleanup-on-partial-failure, `finally`-release) into a new shared module `src/lib/pan-dir/fs-lock.ts`. Lock path: `${OVERDECK_HOME}/locks/records/<project-key>/<ISSUE-ID>.lock/`. **Never inside any git worktree** (fixes E-8). Every read-modify-write of a per-issue record — task or otherwise — acquires this lock: provide `updateIssueRecord(project, issueId, mutator)` that locks → reads → mutates → atomically writes → queues the git commit → releases. Convert every production caller of `writeIssueRecordSync`/`writeStatusOverridesSync`/`writeIssueRecordForWorkspaceSync` to it (WI-2A step 5 lists them). The in-process `withIssueRecordLock` promise chain may remain as a fast path *inside* the fs-lock, or be deleted; it must not be the only guard.
- **CD-3 — Transition matrix.** `applyTaskStatusChange` enforces, against the merged current status:

  | Operation | Allowed from | Result | Notes |
  | --- | --- | --- | --- |
  | claim | `pending` | `running` | Re-claim by the SAME writerId while `running` is an idempotent success (crash-resume). Claim while `running` under a DIFFERENT writerId is rejected with the owner's identity in the error. |
  | done | `running` | `completed` | Claim-owner only (writerId matches the stored claim). |
  | block | `pending`, `running` | `blocked` | From `running`, claim-owner only. `--reason` required. |
  | unblock | `blocked` | `pending` | |
  | cancel | `pending`, `running`, `blocked` | `cancelled` | `--reason` required. |

  Any other transition is rejected with a structured error naming the issue, item, current status, requested operation, claim owner (if any), and the recovery command. `completed` and `cancelled` are terminal: reopening is a planning-side vBRIEF revision, never a runtime task op. `--force` (with mandatory `--reason`) bypasses the owner check and the from-status check but never resurrects a terminal item; every forced transition is recorded in `item metadata.statusReason` and the claim history.
- **CD-4 — Claims.** `claim` writes `record.tasks.claims[itemId] = { writerId, agentId: process.env.OVERDECK_AGENT_ID ?? null, pid: process.pid, host: hostname(), claimedAt }`. `done`/`cancel`/`block` move the claim to `record.tasks.claimHistory[]` (bounded to the last 50 entries). `pan task next` excludes items with a live claim and lists stale-claimed items with a `staleClaim: true` marker — read operations never write (no auto-release on read).
- **CD-5 — Stale-claim release.** A Deacon patrol step (`releaseStaleTaskClaims`, added to the existing patrol cadence in `src/lib/cloister/deacon.ts`) finds `running` items whose claim PID is dead on this host AND whose `agentId` is not a running agent in the agents table, then — under the fs-lock — reverts them to `pending`, records `statusReason: "stale claim released (<writerId> dead)"`, and archives the claim. This is the only automatic release path.
- **CD-6 — Explicit identity, no path parsing.** `issueId` is a required parameter end-to-end (it already exists on `TaskCommandOptions`). Delete the `feature-([a-z]+-\d+)$` regex derivations (E-7). A missing/mismatched issue id is a thrown error, never a silent skip. `validatePlanIssue` (`dag.ts:845`) still cross-checks the doc against the issue id.
- **CD-7 — One implementation.** The async door is the only lock/persistence implementation. Delete the sync duplicates in `dag-cli.ts` (lock, atomic write, mirror) and the plan-file mutation path in `dag.ts` (`applyTaskOperationToPlanFile`, `writePipelineMirrorToPlanFile`'s plan write — the pipeline mirror moves to `record.pipeline`, where it already canonically lives). CLI command handlers are async (commander supports async actions); "sync because CLI" is not a reason to duplicate concurrency code.
- **CD-8 — Durable atomic writes.** `writeRecordFileAtomicSync` (and its async successor) gains: `fsync` the tmp file before `rename`, `fsync` the containing directory after `rename` (crash-truncation history, PAN-2623). Keep the read-back parse verification and `preserveCorruptRecordSync`. Tmp files stay siblings of the record (rename atomicity requires same filesystem); the fs-lock acquire path sweeps orphaned `<record>.*.tmp` files, mirroring `removeStaleLockFromDisk` (`dag.ts:740`).
- **CD-9 — Sequence and CAS.** Every task mutation bumps `record.tasks.sequence` (integer, starts 0). If the caller passed `expectedSequence` and it mismatches the current value (checked under the lock), the mutation fails with a structured conflict error carrying the current sequence. Orchestrators that read-then-act (swarm dispatch) pass it; interactive CLI use may omit it.

### D-8 — The parked `feature/pan-2648` branch is superseded

A prior session left three local commits on `feature/pan-2648` (`b35719c8ad`, `e5c6c70b30`, `e62069dbbc`). They predate this concurrency model (their `pan task` had no transition guard, no claims, no fs-lock, and a global-feeling UX the operator rejected). **Do not build on or merge that branch.** Start from `main` in a fresh workspace. ## Requirements

### Functional requirements

- **FR-1:** `pan task next/show/claim/done/block/unblock/cancel` operates on vBRIEF item IDs and never invokes `bd`.
- **FR-2:** Task reads use `readWorkspacePlanSync()` / `readWorkspacePlan()` so canonical spec content and per-issue `statusOverrides` are always merged.
- **FR-3:** Task mutations validate the target item and allowed transition, then write only record fields (`statusOverrides`, `tasks.*`) through the single write door (CD-1).
- **FR-4:** Dependency readiness, waves, critical path, file-overlap, active-slice, and swarm behavior continue to use the existing vBRIEF DAG.
- **FR-5:** Planning completion promotes the vBRIEF and marks planning complete without materializing Beads or requiring a Beads warning/recovery path.
- **FR-6:** Agent start requires a readable, implementation-ready vBRIEF, not Beads presence or `bd` availability.
- **FR-7:** The work prompt loops one item at a time: next, claim, implement, commit, push, done, optional inspect, next.
- **FR-8:** `pan done` fails when any checklist item or acceptance-criteria child remains non-terminal; it does not query or synchronize Beads.
- **FR-9:** Idle nudging, stuck remediation, orphaned completion recovery, flywheel readiness, backlog readiness, and swarm advance derive remaining/ready work from the merged vBRIEF.
- **FR-10:** Inspection accepts `--item`, reads the item's vBRIEF active slice/metadata, and preserves `requiresInspection`/inspection-depth/no-inspection behavior without `bd show`.
- **FR-11:** Dashboard task list, counts, progress, task rail/tab/dialog/kanban, resource activity signals, and issue detail read the merged vBRIEF and use task terminology.
- **FR-12:** `/api/issues/:id/tasks` returns vBRIEF task rows; `/api/issues/:id/tasks/:itemId/inspect` inspects the item. Beads freshness/Dolt health fields and events are removed.
- **FR-13:** Install, sync, doctor, workspace creation, state migration, teardown, close-out, dashboard boot, and Deacon boot neither require nor invoke `bd`, Dolt, redirects, or `.beads/`.
- **FR-14:** All Beads-only commands, services, source modules, lifecycle jobs, exports, locks, prerequisites, telemetry, skills, rules, templates, docs, and tests are deleted after their retained behavior has a verified vBRIEF home.
- **FR-15:** Existing `.beads/` data is left unchanged and ignored.
- **FR-16:** The PR includes a mechanically checked no-loss matrix covering every operator-facing and pipeline surface listed below.
- **FR-17:** The PR reports exact added/deleted line counts and is net-negative by at least 8,000 lines overall. If it is not, implementation stops for operator review rather than adding abstractions to meet the number.
- **FR-18:** A claim on an item already `running` under a different writer id fails with a structured error naming the current owner; a re-claim by the same writer id succeeds idempotently (CD-3).
- **FR-19:** Every task mutation executes under the record fs-lock (CD-2); with 8 concurrent processes claiming the same item, exactly one succeeds and seven receive the structured rejection.
- **FR-20:** Concurrent mutations of *different* items on the same issue all survive — no lost updates (CD-2 serializes the read-modify-write).
- **FR-21:** Claims record writer id, agent id, pid, host, and timestamp; `done` is claim-owner-only absent `--force` (CD-4).
- **FR-22:** A Deacon patrol releases stale claims (dead PID + non-running agent) back to `pending` under the lock, with an audit trail; no read path auto-releases (CD-5).
- **FR-23:** `record.tasks.sequence` increases by exactly 1 per successful mutation; `--expected-sequence` mismatch fails with the current sequence in the error (CD-9).
- **FR-24:** Task mutations never modify any `spec.vbrief.json`; a byte-comparison test proves the canonical spec is unchanged across a full claim→done lifecycle (fixes E-1).
- **FR-25:** Lock directories and their owner files live only under `${OVERDECK_HOME}/locks/`; no task operation creates any file inside a git worktree other than the record itself and its transient sibling `.tmp` (fixes E-8).
- **FR-26:** All production whole-record writers (the `writeIssueRecordSync`/`writeStatusOverridesSync`/`writeIssueRecordForWorkspaceSync` call sites enumerated in WI-2A step 5) are converted to the locked `updateIssueRecord` door, and a lint/test guard rejects new unlocked record writes (fixes E-4).

### Non-functional requirements

- **NFR-1:** No new canonical task store, cache, database table, daemon, server, background poller, sync loop, or recovery protocol.
- **NFR-2:** No synchronous process or filesystem calls are added to dashboard server request paths. No `execSync` anywhere (repo rule).
- **NFR-3:** Runtime task reads are local file/record reads and must not spawn a process.
- **NFR-4:** Delay/retry tests use `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()` (repo rule). The fs-lock retry unit tests mock timers; only the real-multi-process contention test uses wall-clock, lives in its own file tagged `@slow`, and is excluded from the default run.
- **NFR-5:** The dashboard continues to boot under Node 22. Because dashboard boot imports change, run a throwaway runtime boot test before any live restart (repo rule: never hot-patch a boot path).
- **NFR-6:** No-inspection policy remains mechanically enforced: items with `requiresInspection: false` never trigger inspection.
- **NFR-7:** State-branch writes continue through the record door; no direct state-worktree writes are added.
- **NFR-8:** Existing unrelated dirty files in the primary worktree and state worktree are not modified, committed, or cleaned up.
- **NFR-9:** Exactly one lock implementation and one atomic-write implementation exist after this change (CD-7); a duplicate sync variant is a review blocker.
- **NFR-10:** The fs-lock's total retry budget stays ~1s (the existing delay ladder); a held lock past the budget fails fast with the owner identity — no unbounded waits, no busy-wait loops.
- **NFR-11:** Task mutation adds no network calls and no dependence on the dashboard server being up; a work agent on a machine with only the CLI must be able to claim and complete items.
- **NFR-12:** Record schema changes are additive (`tasks` block, optional); readers tolerate records without it (`schemaVersion` handling follows the existing pattern in `record.ts`).

export async function applyTaskStatusChange(
  project: ProjectConfig,
  issueId: string,
  op: TaskStatusChange, // { type, itemId, subItemIds?, reason?, expectedSequence?, force?, writerId }
): Promise<TaskStatusChangeResult> {

    assertLegalTransition(mergedDoc, record, op);      // CD-3 matrix + CD-4 owner check
    assertSequence(record, op.expectedSequence);        // CD-9

}
