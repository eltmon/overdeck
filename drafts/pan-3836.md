## 1. Glossary

| Term | Meaning |
| --- | --- |
| Project | A registered repository or directory with its own identity, tracker configuration, and primary path. |
| Workspace | A checkout of a registered project. A second checkout is a workspace, not another project. |
| Main workspace | The singleton primary-checkout workspace returned by the workspace resolver. |
| Registration | Creating a project configuration through `registerProjectFromPath` and the project writer. |
| Intent | User-selected creation mode, source, destination, and optional overrides before writes. |
| Resolve | Read-only validation and derivation of defaults, final path, repository metadata, and field findings. |
| Perform | Clone or initialize if needed, register, finish project setup, and ensure the main workspace. |
| Finding | Structured validation result attached to a field; distinct from an unexpected server failure. |
| Mode | `clone`, `existing`, or `new`. These continue to share one core. |
| Transport URL | Exact Git source passed to `git`; its protocol, username, port, and path affect authentication. |
| Display URL | A credential-redacted representation safe for UI, logs, and API responses. |
| Repo slug | Provider identity such as `owner/repo` or GitLab `group/subgroup/repo`; not a replacement transport URL. |
| Proposal / override | A derived default / a value explicitly edited by the user. Proposals must not overwrite overrides. |
| Operation ID | Client-generated opaque identifier used to correlate and deduplicate one submission. It is not an authorization token. |
| Job | Runtime owner of a clone process and its progress, cancellation, settlement, and short-lived result. |
| Unknown outcome | The client lost contact or the server lost the job; neither success nor failure has been proved. |
| Finish setup | Idempotent repair of context/hooks/exclusions/main-workspace setup for a verified, already registered project. It does not clone again. |
| Two doors | Canonical resolver for reads and canonical writer for mutations in each state domain. |
| No-loss audit | Executable inventory proving every previous action, route, callback, and useful affordance remains reachable. |

## 2. Problem, evidence, and reference

The original feature correctly recognized that project creation needs cloning, remote-derived configuration, a main workspace, and shared CLI/dashboard behavior. Those foundations remain. The first implementation does not yet provide a dependable user interaction.

### 2.1 Verified observations

1. `NewProjectPage.tsx` exposes URL, parent directory, name, and issue prefix together. Defaults are placeholders in empty inputs. Existing paths must be typed; the original FolderPicker was lost despite the old PRD requiring it.
2. The preview is a dense chain of internal facts (`will clone`, `main workspace will be created`, etc.). It does not prioritize the destination and action. Unknown providers can incorrectly display `no remote`.
3. The Clone action is labeled `Create project`. Cancel is disabled while cloning, mode buttons remain enabled, and progress is text only.
4. An isolated Playwright check used the real page and hook with mocked API responses. A job reported 42% progress; a subsequent HTTP 503 poll re-enabled Create, retained stale 42% progress, and displayed an error. The operation had no confirmed terminal result. The same check found no initial input focus and zero input/label associations.
5. Preflight returns error detail but the page only renders the generic finding message. Editing name/prefix re-resolves; the route sets `refreshRemote: true` even for preview, bypassing the intended 60-second memo.
6. The URL parser rejects dotted shorthand repo names, rewrites GitHub/GitLab SSH URLs to HTTPS, and parses an SSH port as a path segment. These break otherwise usable inputs and authentication.
7. Registration precedes main-workspace setup. A later setup error leaves a registered project; retrying ordinary create hits the duplicate guard. The earlier injected failure check exercised the actual perform module with inert dependencies, not live project writes.
8. Jobs have a terminal-result TTL but no running-operation deadline or cancellation endpoint. The UI's 404 fallback treats a matching project key as success without verifying its path or main workspace.
9. HEAD `ba0c3b5c360` adds return navigation from workspace creation. Preserve and verify that change rather than treating it as missing.

Browser evidence at review time: `/tmp/pan3836-ux-review/ready.png` and `/tmp/pan3836-ux-review/poll-error.png`. These are local review artifacts, not durable acceptance evidence for the revised implementation. Orca was reviewed in source; its desktop UI was not launched for this comparison.

### 2.2 What to adopt from Orca

- `AddRepoStartSteps.tsx` and `add-repo-local-start-actions.ts`: understandable entry actions, descriptions, focus, and keyboard navigation.
- `AddRepoCloneStep.tsx`: a focused URL + destination form, folder browsing, action-specific button text, and progress below the action so it does not move unexpectedly.
- `AddRepoCreateStep.tsx`: name first; a readable location summary opens uncommon settings. Defaults are visible without making every option a mandatory decision.
- `useAddRepoCloneFlow.ts` and `clone-defaults.ts`: location defaults, stale-callback guards, consistent completion handling.
- `AddRepoDialog.tsx`: backing out closes the operation through `cloneAbort`; it does not silently abandon a live clone.
- `repo-clone-lifecycle.ts` and `repo-clone-path.ts`: preserve the supplied transport URL, serialize same-path operations, claim directories, guard cleanup ownership, cap stderr retained, and settle abort before retry.
- `git-clone-failure-message.ts`: useful auth/destination explanations with credentials removed.

Adopt the behavior, not Orca's Electron IPC, store, branding, or whole component tree. Keep Overdeck's full-page route, existing FolderPicker, current style tokens, shared resolve/perform core, and canonical state doors. Orca is prior art, not proof that every one of its edge cases is correct.

## 3. Goals and scope

### Goals

- Let someone add an existing folder, clone a remote, or start a new Git project without understanding internal registration details.
- Make defaults visible and editable while minimizing initial choices.
- Show exactly where files will be created and which server owns that path.
- Keep progress, cancellation, transient disconnection, and partial completion truthful and recoverable.
- Preserve CLI parity, project/workspace distinction, remote-derived identity, existing integration flags, and no-loss navigation.

### Non-goals

No Fly/SSH execution-host selector, remote-machine clone execution, central-worktree relocation, checked-in setup-command system, issue-id smart workspace field, or automatic test/quality-gate discovery. An SSH **Git URL** is in scope; executing the clone on a separate SSH **machine** is not. No mass redesign of `/workspaces/new`, project settings, or other pickers. No new model routing or agent behavior. No live dashboard restart, agent restart, or merge is authorized by this document update.

## 4. Decisions

- **D-1 (retained):** Clone is a project mode. Another checkout of an existing project belongs in the workspace flow.
- **D-2 (corrected):** Preview debounces 300 ms and uses a remote-result cache for 60 seconds. Key by exact trimmed transport URL, including protocol/user/port, not only provider slug. Coalesce concurrent probes of the same key; maximum 128 settled entries, evict expired/oldest entries. Preview passes `refreshRemote: false`; submit revalidates with `true`. Valid unchanged URLs are not re-probed when name/location/prefix changes. Each probe has a 15,000 ms timeout, prompt guards, and sanitized errors. Do not add background retries to validation.
- **D-3 (retained with explicit failure handling):** Proposed prefix is uppercase normalized key with hyphens removed, truncated to ten characters. Validate `/^[A-Z][A-Z0-9]{0,9}$/` and uniqueness. A proposal beginning with a digit or colliding with another prefix opens Options and asks for an override; do not silently select another prefix or claim every derived prefix is valid. Explicit lower-case input is not silently rewritten while typing.
- **D-4 (clarified):** Default parent is the server's `<home>/Projects`. Resolve returns actual absolute `parentDir` and `homeDir` metadata for display/picker initialization; no browser-home inference. Display an actual value, not only `~/Projects` as placeholder. Typed `~` and `~/...` expand against server home; `~otheruser` is rejected with guidance. Relative paths stay invalid in dashboard; CLI retains its existing cwd-relative behavior.
- **D-5 (strengthened):** Claim the target with non-recursive mkdir; capture directory identity with lstat. Only remove a directory created by this operation, after clone failure/cancellation is confirmed, if its identity still matches and no successor owns the path. Never remove a pre-existing target, parent, successful clone, or registered project. Serialize same-path operations and wait for cleanup before admitting a retry.
- **D-6 (replaced):** Clone is a cancellable runtime job with operation correlation, a 30-minute pre-registration clone deadline, and 10-minute retention after terminal settlement. Client transport errors mean unknown outcome, not job failure. A missing job is reconciled through the project-creation resolver against expected key, canonical path, mode/remote identity, and main workspace; key alone never proves completion. See §6.3 and WI-2. No new independent persistent job database is needed for this feature.
- **D-7 (retained):** `existing` and `new` retain `200 { key, name, path }`; additive `mainWorkspaceId` and metadata are allowed. Clone keeps `202 { jobId }` with additive operation information. Client submission guarding applies to all modes.
- **D-8 (retained):** Add the configured workspaces directory to `.git/info/exclude` idempotently, not tracked `.gitignore`. Do not modify tracked repository files. Skip exclusion edits for a `.git` file unless an existing supported helper correctly resolves its gitdir; do not improvise a second implementation.
- **D-9 (strengthened):** Use existing workspace resolve/perform and read doors. Success requires the main workspace to exist at the registered primary path. Split the post-registration setup into an idempotent `finishProjectSetup` in the shared core so partial completion can be repaired without registering or cloning again.
- **D-10 (retained/typed):** Registration extras remain a typed Pick of ProjectConfig. Preserve `seededContextLayer` and `hooksInstalled` results for existing CLI reporting. No broad `Record<string, object>` cast around configuration writes.
- **D-11 (corrected):** Dashboard remains home-bounded, CLI does not gain that restriction. Canonicalize home and nearest existing ancestor with realpath and use path.relative/sep containment. Check again under the operation lock before writes. Symlink escapes, files used as directories, and unreadable ancestors get field findings.
- **D-12 (replaced):** Preserve explicit HTTP(S), SSH URL, and SCP-style sources as transport URLs, trimming surrounding whitespace only. Use URL parsing for scheme URLs; parse SCP separately; only owner/repo shorthand synthesizes an HTTPS URL. Hostname determines provider metadata; protocol/user/port/path remain intact. Dots and subgroup paths are accepted. Unsupported schemes/local-file sources and values beginning with `-` are rejected for dashboard cloning. Folder name derives separately, including for unknown hosts. Do not rewrite SSH to HTTPS or append `.git` to explicit URLs. See the exact matrix in WI-1.
- **D-13 (clarified):** Progress has phase-local percentages, not a fictitious overall percent. Show Preparing, Git's known phases, Setting up project, then terminal state. Unknown progress is indeterminate. A phase transition may reset its percent. Error/cancelled states cannot retain a live-looking progress bar.
- **D-14 (refined):** Keep `/projects/new`, `project-new`, all existing entry points, and `?mode=` presets. Without a preset, show three short entry actions: Open existing folder, Clone repository, Create new project. Existing is first/focused; this selection view replaces the automatic clone default. Inside a selected mode show a compact mode switch/Back control, not an additional wizard. Options are a disclosure, not a separate step. Keep full-page route semantics.
- **D-15 (corrected):** Detect existing Git roots/worktrees using async Git (`rev-parse --show-toplevel`/`--git-dir` as needed), not `.git.isDirectory()` alone. Respect the chosen directory's identity; a subdirectory of a repo must not silently register a second project rooted there. Return a finding offering the discovered root unless it is already the selected canonical path. Keep origin/default-branch detection and non-Git existing-folder support.
- **D-16 (retained):** Do not refactor unrelated `resolveWorkspaceRemote` callers to satisfy this issue.
- **D-17 (clarified):** Store overrides separately from proposals. Effective field values are proposal-unless-edited. Auto values update when source changes; edited values do not. Offer Reset to detected value. Changing source must not overwrite typed values or trigger resolve loops.
- **D-18 (new):** A fixed-width readable form uses at most 42rem of content width, responsive gutters, and existing style tokens. Clone initially exposes URL and parent folder; New exposes name and a location summary; Existing exposes selected folder and Browse. Display name/prefix and uncommon location edits live under Options. Expand Options automatically for a finding inside it.
- **D-19 (new):** While an operation is submitting/running/cancelling/unknown, freeze mode/source/destination/Options edits and prevent a second submit synchronously. Cancel becomes Cancel clone during clone preparation/process execution. Once registration begins, cancellation is no longer accepted; show Finishing setup and retain a truthful disabled finishing control. Pre-submit Cancel leaves normally. Client navigation away does not pretend to cancel a server job; retained operation metadata resumes observation on return.
- **D-20 (new):** Keep the user's input on errors. Provide a concise explanation plus next action and expandable sanitized details. Separate validation, auth, destination, transient observation, clone terminal failure, and partial setup. No raw command-line dumps or secrets.
- **D-21 (new):** Reuse FolderPicker and `/api/fs/list-dirs`. Label it as server folders. Harden its existing button types and selection/loading behavior because it will be nested in a form. Do not invent a native client picker that returns paths on another machine.
- **D-22 (new):** Preserve normal completion into the selected project's command deck. Preserve the workspace-origin return path with the new project selected. Allow only the exact `/workspaces/new` pathname as a return target; retain allowed query parameters deliberately, never arbitrary URLs or prefix matches. Do not replace successful return behavior with an extra success page.

## 6. UX and API contracts

### 6.1 Screen states and exact interaction

**Entry:** Heading `Add a project`. Guide: `A project is a repository or folder. To make another checkout of a project you already use, create a workspace.` Link `create a workspace` to `/workspaces/new`. Three described actions: `Open existing folder` / `Use a folder already on this server`; `Clone repository` / `Download a Git repository`; `Create new project` / `Start an empty Git repository`. Focus first action; arrow keys are optional only if a complete semantic radio/tab pattern is used, otherwise normal buttons and Tab suffice.

**Clone:** Focus `Repository URL`; placeholder `https://github.com/owner/repo or owner/repo`. `Parent folder` is populated from resolved defaults and has Browse. Show `Will clone to <absolute path>` once derivable. Options reveals `Project name` and `Issue prefix`, both populated. Brief prefix help: `Used in issue IDs, for example APP-123.` CTA `Clone repository`.

**Existing:** Focus Browse or Directory input. Support typed absolute path and `Browse server folders`. Selected path is visible and copyable. Show `Will add <absolute path>` and detected repository/non-Git-folder state in plain language. Options reveals name/prefix. CTA `Add project`. Selecting a file or an inaccessible path produces a field finding, never a false preview.

**New:** Focus `Project name`, with placeholder `my-project`. Summary `Git repository in <parent>` and complete target path. Expand Options to change parent using input/Browse and issue prefix. CTA `Create project`. Name is the only user input required when defaults are usable.

**Defaults and details:** A placeholder is an example only. Return actual server-resolved defaults even before enough input exists for full validation; missing required fields are not rendered as red errors on first load. Render findings for touched fields, after submit, or when a returned conflict requires action. Transport/server errors are shown immediately. A Details disclosure can show repository key, provider slug, branch or `Default branch not available`, and automatic main-workspace setup; these must not dominate the form or falsely say `no remote` for an unknown provider.

**Preparing/Cloning:** Keep fields visible, frozen. Status above/below a stable action area: `Preparing clone…`, then phase and phase-local percentage/progressbar. Cancel clone is operable and announces `Cancelling clone…` until confirmed. No new submission while cancelling. If registration has started, show `Finishing project setup…` and explain that this short step must finish; do not offer a fake abort.

**Lost contact:** Text `Connection interrupted. The clone may still be running.` Show `Checking status…` during retries, then `Check again` after retry exhaustion. Preserve job/operation ID and input. Freeze Create and mode changes. Last progress may appear only as `Last update: Receiving objects 42%`; no active progress animation. Keep a cancel request possible when connectivity returns. Do not replace operation state with `creating = false`.

**Terminal failure:** Clear active progress, focus the error summary, preserve fields, show categorized next action. Clone retry is enabled only when the server confirms the prior process ended and cleanup settled. A target conflict offers `Use existing folder` (switches to existing with the exact path for review) and `Choose another folder`; neither deletes anything.

**Partial setup:** `The repository is available at <path>, but project setup did not finish.` Show `Finish setup` and a sanitized reason. Do not offer Clone again. If path/identity changed, show a conflict and require reviewing the existing project instead of silently adopting it.

**Success:** Call existing completion handler once, refresh project queries, select the new project, navigate to command deck or the allowlisted workspace return route. Emit `project_created` once for actual completion. A completed recovery should not emit an additional creation event if that operation was already reported.

### 6.2 Client state and persistence

Use a discriminated state instead of independent booleans that permit contradictory states:

```ts
type ProjectSubmissionState =
  | { kind: 'editing' }
  | { kind: 'submitting'; operationId: string }
  | { kind: 'running'; operationId: string; jobId: string; progress: ProjectCreateProgress }
  | { kind: 'cancelling'; operationId: string; jobId: string }
  | { kind: 'connection-lost'; operationId: string; jobId?: string; lastProgress?: ProjectCreateProgress }
  | { kind: 'needs-setup'; operationId: string; key: string; path: string; error: ProjectCreateFailure }
  | { kind: 'failed'; error: ProjectCreateFailure; retrySafe: boolean }
  | { kind: 'cancelled' }
  | { kind: 'done'; result: ProjectCreateResult };
```

Keep a synchronous ref guard in addition to React state; acquire before any await. Generate one operationId on the first accepted submit. Reuse it after a lost POST response; a new attempt after confirmed failure/cancellation gets a new ID. Correlate every callback with operationId and generation, ignore stale callbacks, and invoke onCreated at most once per operation.

Store only a versioned observation record in sessionStorage under `overdeck:project-create:v1`: operationId/jobId, mode, expected key/path, and safe remote identity. Never store raw credential-bearing URL or diagnostic text. This is a client convenience, not canonical project/job state. Restore observation on returning to the page/reload; clear only on known terminal completion or explicit acknowledgement of an unresolved state. Merely navigating away never sets the server job to cancelled. If storage is unavailable, normal same-page operation still works and explain that observation cannot survive reload when relevant.

### 6.3 Server contracts and ownership

`ResolvedProjectIntent` keeps existing members, adds `parentDir: string | null` and `homeDir: string`, and uses sanitized public representations. The core may hold private transport input for perform; the route must project a safe public DTO so embedded credentials cannot be reflected. Add typed error/recovery metadata instead of parsing error strings. `ProjectCreateResult` retains key/name/path/mainWorkspaceId and may include registration metadata used by CLI.

```ts
interface ProjectCreateFailure {
  code: 'authentication-required' | 'host-key-untrusted' | 'remote-unreachable'
    | 'destination-conflict' | 'cancelled' | 'timed-out'
    | 'setup-incomplete' | 'operation-unknown' | 'internal-error';
  message: string;
  detail?: string; // sanitized and bounded; rendered only on disclosure
  retrySafe: boolean;
  recovery?: { action: 'finish-setup'; key: string; path: string }
    | { action: 'use-existing'; path: string };
}
```

Keep `error: string` in failure responses where old callers expect it; add `failure` for structured clients. Do not leak raw Error.stack or command args.

| Surface | Required behavior |
| --- | --- |
| `POST /api/projects/resolve` | Mutation-auth guard despite read-only semantics; validate body; force `homeBoundary: true`, preview refresh false; 200 safe intent including findings/defaults. |
| `POST /api/projects` | Existing fields plus optional operationId for backward compatibility. For all modes, reserve operation ID before async fresh validation; attach same-ID/same-input retries to the same submission; changed-input reuse returns 409. Fresh findings: 422. Clone: 202 with jobId/operationId. Existing/new: 200 result. Unexpected failures: 500; real conflicts: 409. |
| `GET /api/projects/create-jobs/:jobId` | Authenticated dashboard read; returns safe status/progress/result/failure; 404 means unknown to this runtime, not confirmed failure. |
| `POST /api/projects/create-jobs/:jobId/cancel` (new) | Mutation-auth guard. Running/preparing clone: request abort, return 202 cancelling; poll confirms cancelled after close/cleanup. Repeated requests are idempotent. Done/failed/cancelled returns current terminal result. During registration returns 409 `cannot-cancel-setup` with current state; client continues observing. |
| `POST /api/projects/create-jobs/reconcile` (new) | Authenticated read-style POST with operationId, optional jobId, expected key/path/mode/safe remote identity. Return known job if present; otherwise inspect canonical project/workspace and read-only filesystem/Git facts via the shared core. Return completed, needs-setup, conflict, or unknown with precise actions. Never create, delete, register, or infer success from a key alone. |
| `POST /api/projects/:key/finish-setup` (new) | Mutation-auth guard; body expectedPath and operationId. Canonical key/path must match. Hold same-path lock; complete idempotent setup through existing writers. 200 verified result; 409 identity mismatch; typed setup failure with retry action otherwise. No clone, config overwrite, or registration of a new project. |

The job implementation belongs in the existing `project-create-jobs.ts` owner (or move it once behind an equivalent single domain entry point if lint layering requires). Routes call that owner; no parallel route-local stores. Shared resolver/perform/finish-setup owns project logic. Inputs including raw URLs stay private inside the runtime operation; logs and status DTOs are redacted.

The operation table maps client ID to normalized request fingerprint, preparation promise, job, and terminal result. The fingerprint must include mode/canonical destination/name/prefix and exact transport; store it only in runtime memory, do not log it. For synchronous existing/new requests, retain the same operation correlation and terminal response so a repeated POST can return that result instead of registering twice. Coalesce same-ID preparations before the first await and reject conflicting same-target operations under the target lock, even with different IDs. Auth remains required regardless of operation ID. Legacy callers without an operation ID get one server-generated ID and still receive same-target exclusion.

**Job lifecycle:** preparing → cloning → registering → done; preparing/cloning → cancelling → cancelled; failures become failed with retrySafe/recovery metadata. Start 30-minute deadline at accepted preparation; use the probe's separate 15-second limit. Pass the AbortController signal to Git. After abort, request SIGTERM and, if the child has not closed after 5 seconds, SIGKILL; do not settle before close. If cancellation races successful clone before registration, retain the complete repo, do not register, and offer Add existing. If registration has already begun, finish or report needs-setup instead of claiming cancellation. When entering registering, clear the clone deadline and detach the clone abort path; a deadline must not label a still-writing registration as cancelled or retry-safe. Preserve observation of setup until it returns success or typed failure. Clear every timer/listener/lock in finally and prune terminal entries after ten minutes. Active jobs are never evicted as a substitute for cancellation.

**Polling:** one request at a time, normal 750 ms delay after response. On network/5xx timeout retain operation and use retries at 1s, 2s, 4s, 8s, 8s. After five failed retries expose Check again; never silently enable Create. A successful poll resets the retry budget. Auth failures show session guidance and suspend automatic retries. Abort pending fetches on unmount, retaining the operation observation. A 404 triggers reconciliation once, not blind repeated creates.

**Restart/missing-job limit:** in-memory jobs cannot prove a pre-registration clone died across a server restart. Reconciliation may prove a complete registered result or partial registered setup by exact identity. If no such proof exists, return unknown, leave Create disabled for the retained operation, show the target and `Review existing folder`/`Check again`, and never delete or retry automatically. A registered-but-incomplete result permits Finish setup only after ruling out a currently owned runtime operation; setup itself remains serialized and idempotent. Do not add a misleading automatic “fresh retry” after 404. This limitation is documented and tested.
