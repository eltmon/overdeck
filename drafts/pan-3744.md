# PAN-3744 — Conversation panel renders the "How can I help you?" greeting while the transcript is still loading

**Issue:** https://github.com/eltmon/overdeck/issues/3744
**Status:** draft PRD
**Author:** conversation conv-20260816-9367, 2026-08-16

## Glossary

- **Conversation panel** — `src/dashboard/frontend/src/components/chat/ConversationPanel.tsx`, the
  transcript view for a conversation or agent session.
- **Fetch path** — the react-query `/messages` fetch used when streaming is off
  (`enabled: !streamMessagesEnabled`, ConversationPanel.tsx:251). Its in-flight state is
  `isLoading`.
- **Stream path** — live claude-code conversations are pushed over WS by
  `useConversationMessagesStream` (`src/dashboard/frontend/src/components/chat/useConversationMessagesStream.ts`,
  wired at ConversationPanel.tsx:188). It writes into the query cache; the panel reads `data`
  from the cache.
- **Greeting / first-message state** — the `How can I help you?` empty state rendered at
  ConversationPanel.tsx:1432 when `isFirstMessage` is true.
- **Skeleton** — a placeholder layout indicating content is loading (the panel already has a
  minimal precedent: the `conversationConnecting` block at ConversationPanel.tsx:1345–1348).

## Problem (verified 2026-08-16)

State derivation at ConversationPanel.tsx:1290–1317:

```ts
const isDiscovering = streamMessagesEnabled && data?.discovering === true && messages.length === 0;
…
const isFirstMessage = !isLoading && !isDiscovering && !hasTimelineActivity && conversation.sessionAlive;
```

On the stream path, before the first WS payload arrives, `data` is `undefined`: `isLoading` is
false (the fetch query is disabled), `isDiscovering` is false (`data?.discovering` is not `true`),
and `hasTimelineActivity` is false. For a live conversation (`sessionAlive`), `isFirstMessage`
therefore evaluates true and the panel renders the greeting **as an assertion the conversation is
empty**, when the truth is "transcript not delivered yet". Under server load (see PAN-3743) that
window stretches to many seconds. Two earlier patches (comments at lines 243 and 1291–1297)
narrowed adjacent variants of this bug but left the pre-first-payload window uncovered.

## Requirements

- **FR-1** The panel must distinguish three states on the stream path: (a) awaiting first payload,
  (b) payload received and conversation genuinely empty, (c) payload received with content.
- **FR-2** State (a) renders a loading skeleton. The greeting renders only in state (b) (plus the
  existing fetch-path conditions).
- **FR-3** The skeleton must appear immediately on conversation switch — no flash of greeting or of
  the previous conversation's emptiness state.
- **NFR-1** No regression of the states guarded by existing tests: PAN-3544 (work-agent workLog
  timelines must not show the greeting), the spawn window ("Starting…"), orphaned, and
  fetch-failed states (lines 1298–1317).

## Work items

### 1. Surface "first payload received" from the stream hook (FR-1)

File: `src/dashboard/frontend/src/components/chat/useConversationMessagesStream.ts`.

The hook currently returns only the enabled boolean (`streamMessagesEnabled`,
ConversationPanel.tsx:188). Extend it to also expose whether the current conversation's
subscription has delivered at least one payload (snapshot or delta) since (re)subscribing — e.g.
return `{ enabled, receivedFirstPayload }`, resetting `receivedFirstPayload` on conversation
identity change. Implementation detail is the hook's own state (a `useState` flipped in the message
handler), NOT a query-cache sentinel — cache entries survive conversation switches and would
reintroduce the stale-flash bug (FR-3).

### 2. Gate the empty states on it (FR-1, FR-2)

File: `src/dashboard/frontend/src/components/chat/ConversationPanel.tsx` (lines 1290–1317, 1345).

Before:
```ts
const isDiscovering = streamMessagesEnabled && data?.discovering === true && messages.length === 0;
```
After (shape, adjust to the hook's actual return):
```ts
const awaitingFirstPayload = streamMessagesEnabled && !receivedFirstPayload && messages.length === 0;
const isDiscovering = streamMessagesEnabled && data?.discovering === true && messages.length === 0;
```
Then include `!awaitingFirstPayload` in `isFirstMessage`, `messagesFetchFailed`, and `isOrphaned`
(all three currently treat "no data yet" as a settled fact), and render the skeleton when
`awaitingFirstPayload` is true, in the same branch position as the `isLoading || isDiscovering`
block at line 1345.

### 3. Skeleton component (FR-2, FR-3)

Files: `ConversationPanel.tsx`, its CSS module (`styles.conversation*`).

Replace the bare `Loading…` text branch with a lightweight skeleton: 3–4 message-shaped shimmer
blocks matching the panel's message layout. Use it for both `isLoading` (fetch path) and
`awaitingFirstPayload` (stream path) so the two paths look identical. Follow the dashboard style
guide (`pan-style-guide` skill): no decorative color, respect both themes.

### 4. Tests (NFR-1)

File: `src/dashboard/frontend/src/components/chat/__tests__/ConversationPanel.test.tsx` (the
greeting suite starts at line 627).

- Stream path, no payload yet, sessionAlive → skeleton, no greeting.
- Stream path, first payload arrives empty → greeting.
- Conversation switch resets to skeleton (FR-3).
- Existing PAN-3544 workLog test and spawn/orphan/fetch-failed tests stay green.

Run with the frontend runner: `cd src/dashboard/frontend && bun run vitest run --configLoader runner`.

### 5. Documentation

`docs/ISSUE-VIEW.md` — the conversation-view section gains a paragraph enumerating the panel's
loading/empty states (awaiting-payload skeleton, greeting, Starting…, orphaned, fetch-failed) and
what each asserts. Update the module-header comment block in `ConversationPanel.tsx` where the
prior incident comments (lines 243, 1291–1297, 1299–1305) already document state semantics.

## Acceptance criteria

- **AC-1 (↔FR-1/FR-2, WI-1–3)** With a throttled transcript delivery (dev-tools WS throttle or a
  delayed mock), opening a live conversation shows the skeleton and never the greeting until the
  first payload; an actually-empty conversation shows the greeting only after its first payload.
- **AC-2 (↔FR-3)** Rapidly switching between two conversations never flashes the greeting or the
  other conversation's content.
- **AC-3 (↔NFR-1, WI-4)** All pre-existing ConversationPanel tests pass unmodified except where a
  test asserted the buggy behavior.
- **AC-4 (↔WI-5)** Named docs updated in the same PR.
