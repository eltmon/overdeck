# PAN-2713 — Deploy joins the Definition of Done: staleness signal + guarded mechanical deploy

**Issue:** https://github.com/eltmon/overdeck/issues/2713
**Author:** planning agent (claude-fable-5), 2026-07-15
**Status:** draft → proposed via `pan plan finalize`

## Glossary

- **Live server** — the production dashboard process: Node 22 running `dist/dashboard/server.js` from the primary repo root (`/home/eltmon/Projects/overdeck`), port 3011. Never Bun, never tsx.
- **Build commit** — the git SHA of the checkout that produced the currently running `dist/` bundle. Does NOT exist today; this issue introduces it.
- **Build inputs** — repo paths whose changes affect the built bundle: `src`, `packages`, `package.json`, `bun.lock`, `tsdown.config.ts`.
- **Staleness** — the running build commit is behind `origin/main` by ≥1 commit touching build inputs. "Behind by N" = `git rev-list --count <buildCommit>..origin/main -- <build inputs>`.
- **Deploy** — rebuild `dist/` from a pristine `origin/main` worktree, swap it in, restart the dashboard, health-gated. Two existing implementations: `scripts/post-merge-deploy.sh` (bash, spawned by Step 0) and `pan reload` (`src/cli/commands/reload.ts`).
- **Step 0** — the deploy block at the top of `postMergeLifecycle()` (`src/lib/cloister/merge-agent.ts:378-426`): writes `~/.overdeck/pending-post-merge.json`, spawns `scripts/post-merge-deploy.sh` detached, returns; the fresh server finishes the lifecycle via `processPendingLifecycle()` (`src/dashboard/server/pending-lifecycle.ts`).
- **Deacon / patrol** — the Cloister supervisor child process (`dist/dashboard/deacon.js`, spawned by `startDeaconChild`). `runPatrol()` (`src/lib/cloister/deacon.ts:2715`) runs every `patrolIntervalMs` (60s, `deacon.ts:220`); sub-cadence throttling via `shouldRunRecoveryJanitor` (`src/lib/cloister/patrol-cadence.ts`).
- **Restart lock** — `acquireRestartLock(caller)` (`src/lib/restart-lock.ts:162`); serializes all dashboard restarts (`pan reload`, `pan restart`, flywheel deploys).
- **Verification in flight** — any review-status row with `verificationStatus === 'running'` (set at `src/lib/cloister/verification-runner.ts:373`).
- **Merge in flight** — the `specialist-merge-agent` tmux session exists (`isMergeAgentRunning()`, `src/lib/cloister/merge-agent.ts:1119-1121`) or `~/.overdeck/pending-post-merge.json` exists.

## Root cause (verified 2026-07-15)

A per-merge deploy mechanism ALREADY EXISTS and works (`/tmp/overdeck-deploy.log` shows a successful deploy for PAN-1232 at 02:27 local). The incident (PAN-2684/2690/2701 merged 13:04–13:16Z, server stayed on an older build) happened because the mechanism is **event-driven with no reconciliation backstop**:

1. Step 0 only runs inside `postMergeLifecycle`. It is skipped by:
   - **Guard 2 (close-out is terminal)** — `merge-agent.ts:347-357`: spec `completed`/`cancelled` skips the whole lifecycle. The live server's log shows exactly this for the incident: `[merge-agent] PAN-2684 is closed out (spec completed) — skipping post-merge lifecycle`. Operator-bypass merges that close out before the lifecycle runs on the current server never deploy.
   - **Every reconciliation caller passes `skipDeploy: true`** — `deacon.ts:2136`, `deacon-merge.ts:254`, `done.ts:518` (strike), `pending-lifecycle.ts:49`.
   - A merge whose lifecycle ran on a **previous server process** that died before Step 0.
2. **Nothing detects staleness.** No build commit is stamped anywhere (verified: no `define`/build stamp in either tsdown config; `/api/health` returns only `{status, repoRoot, mode}` from `getDashboardIdentity()`, `src/dashboard/server/identity.ts:16-21`). A missed deploy is invisible until an operator asks.
3. Step 0 also has no safety window: it kills the server regardless of in-flight verifications (the PAN-2687 wedge class) and fires per merge (a merge train = several restarts), and it fires even for merges of OTHER projects (repoRoot is derived from `__dirname`, not `projectPath` — `merge-agent.ts:387-397`), restarting the dashboard onto an unchanged build.

Fix shape: keep the event-driven fast path (Step 0) but gate it on staleness + a safety window, and add a **state-based reconciliation backstop** (deacon patrol) that detects staleness and deploys with debounce, covering every miss path above.

## Requirements

### Functional
- **FR-1** The server bundle carries its build commit; `GET /api/health` returns `buildCommit` (and `builtAt`) alongside the existing identity fields.
- **FR-2** A shared staleness module computes `{behindTotal, behindBuildInputs, originMainSha, originMainLastCommitAt}` for the running build vs `origin/main`, usable from both the server process and the deacon child, with throttled fetches.
- **FR-3** `GET /api/system/health` includes the staleness result; the dashboard header renders a stale-build chip when `behindBuildInputs ≥ 1` and renders nothing otherwise.
- **FR-4** A deacon patrol emits an activity observation when the running build is stale (throttled — not every 60s cycle).
- **FR-5** The patrol mechanically deploys when stale: guarded, debounced, by spawning the bundled `pan reload` detached. A dashboard-touching merge results in the live server running that commit within one patrol + debounce interval.
- **FR-6** Deploys (patrol AND Step 0) defer while verification or a merge is in flight, while the restart lock is held, or while a `pan dev` supervisor owns the dashboard; a deferred deploy is retried by the patrol on later cycles.
- **FR-7** Step 0 becomes staleness-gated and safety-gated: when the running build already contains `origin/main`'s build-input state, or the window is unsafe, it skips the restart and falls through to the existing in-process lifecycle path instead.
- **FR-8** Config: cloister config gains `deploy: { auto_deploy: boolean (default true), debounce_minutes: number (default 5) }`. `auto_deploy: false` disables patrol deploys but keeps detection + chip + observations.
- **FR-9** `docs/DEFINITION-OF-DONE.md` row 7 names the new mechanical owner; `docs/OVERDECK_DEV_SOP.md` documents auto-deploy behavior and config.

### Non-functional
- **NFR-1** No `execSync` in any server-reachable code (PAN-70). Build-time-only files (tsdown configs, build scripts) may use sync exec — they never run in the server.
- **NFR-2** All debounce/throttle tests use `vi.useFakeTimers()` + `advanceTimersByTimeAsync` — never real delays.
- **NFR-3** Patrol-spawned reloads pass `--health-timeout 120000` (the ≥120s rule).
- **NFR-4** Peer-mode servers (`OVERDECK_DISABLE_DEACON=1`, workspace containers) never deploy — they run no deacon, and the identity `mode` guard is belt-and-suspenders.
- **NFR-5** Deploys stay serialized: the existing restart lock + the deploy script's flock make concurrent attempts no-ops; a missed deploy is always recovered by a later patrol cycle (no one-shot state).

## Decisions (made here; mirrored in `plan.autoDecisions`)

- **D1 — Reconciliation over more event hooks.** The backstop is a state-based deacon patrol, not additional `firePostMergeLifecycle` call sites. Event hooks provably miss paths (root cause above); a patrol that compares "running build vs origin/main" catches all of them by construction.
- **D2 — Build stamp via tsdown `define`, fallback build-info file.** Add `define: { __OVERDECK_BUILD_COMMIT__, __OVERDECK_BUILD_TIME__ }` to BOTH `src/dashboard/server/tsdown.config.ts` and the root `tsdown.config.ts` (the deacon child and CLI must self-identify too), computed at config-eval time via sync git call (build-time only — NFR-1 does not apply). Accessor uses a `typeof` guard so unstamped bundles (tests, tsx) resolve to `null`. **Implementation checkpoint:** if tsdown/rolldown `define` does not replace the identifier as expected, fall back to a build script step writing `dist/build-info.json` read once (sync, at module init) by the accessor.
- **D3 — Patrol deploys via the bundled `pan reload`, not a generalized `post-merge-deploy.sh`.** `pan reload` already owns: restart lock, `pan dev` SIGUSR2 hot path, pristine origin/main worktree build, dist swap, identity-checked health-gated restart, restart-status recording (`reload.ts:182-271`). Spawn `node <repoRoot>/dist/cli/index.js reload --health-timeout 120000` detached (`detached: true`, stdio to `~/.overdeck/logs/auto-deploy.log`, `unref()`). The reload process survives the server/deacon restart it causes. **Checkpoint:** `pan reload` does not write the `dashboard-restarting.json` restart marker (`pending-lifecycle.ts:20`) — verify boot treats the restart as planned (restart-status.json is written); if boot reconciliation complains about an unplanned restart, write the RESTART_MARKER with `reason: "auto-deploy"` before spawning.
- **D4 — Step 0 changes are gating-only.** Do not restructure the pending-file/fresh-server mechanism, the PAN-328 guards, or `processPendingLifecycle`. Only insert: (a) staleness check — skip deploy when `behindBuildInputs === 0` after fetch; (b) safety check — skip deploy when `getDeployBlockReason()` is non-null. Both skips log and fall through to the existing in-process lifecycle code path (the same one all `skipDeploy: true` callers exercise daily). Side effect (deliberate): merges of non-overdeck projects no longer restart the dashboard when overdeck didn't change.
- **D5 — Debounce = quiet period on origin/main.** Deploy only when the newest `origin/main` commit is older than `debounce_minutes` (via `git log -1 --format=%ct origin/main`). A merge train keeps resetting the clock → exactly one deploy after the train settles. Default 5 minutes.
- **D6 — Staleness scope is the self repo only.** The patrol and Step 0 evaluate the server's own repo root (identity `repoRoot`); other projects' merges are irrelevant to the dashboard build (their deploys belong to `triggerPostMergeReleaseIfConfigured`).
- **D7 — Default ON.** `deploy.auto_deploy` defaults `true`: the issue's purpose is covering flywheel-down periods mechanically. The flywheel keeps override authority; collisions are harmless (restart lock + staleness re-check make the second attempt a no-op).
- **D8 — Guard blocks, never queues.** `getDeployBlockReason()` returns a reason string or null; callers defer and rely on the next patrol cycle. No persistent deploy queue (NFR-5 makes it unnecessary).

## Restated repo rules that intersect this work

- **No `execSync` in server-reachable code** (PAN-70). tsdown configs/build scripts are exempt (build-time only). Everything in `src/lib/deploy/**` and patrol code: promisified `exec`/`spawn` only.
- **Fake timers** for every debounce/throttle test — `vi.useFakeTimers()` + `advanceTimersByTimeAsync`; never real waits, never `maxForks: 1` masking.
- **Node-22 dist boot, never Bun**; `pan reload --health-timeout 120000` satisfies the ≥120s restart rule.
- **Boot-path discipline:** this issue does not change server boot paths; the reload it spawns deploys already-reviewed merges — it is not a bypass of the runtime-boot-test rule for boot-path changes.
- **Style guide** for the chip: color = signal only, no pill badges, monospace-leaning.
- **Additive refactor / no-loss:** Step 0's existing safe-window behavior is a superset change — every current deploy path still deploys (unless provably unnecessary or unsafe), plus the patrol backstop. The `unknown` staleness case preserves today's behavior exactly.
- **postMergeLifecycle idempotency:** `in-flight-guard.test.ts` green is a hard gate.

## Acceptance criteria (issue-level)

1. A dashboard-touching merge to main results in the live server running that commit within one patrol + debounce interval (default ≤ ~10 min after the merge train quiets), with the safety guard observed. (FR-5, FR-6)
2. `GET /api/health` exposes the build commit; the dashboard header shows a stale-by-N chip when the running build is behind origin/main on build inputs, and nothing otherwise. (FR-1, FR-3)
3. A merge landing while verification or a merge is in flight defers the deploy (logged, observable in the activity feed) rather than interrupting, and the deploy happens on a later patrol cycle. (FR-6, FR-7)
4. `deploy.auto_deploy: false` yields detection + chip + observations with zero mechanical restarts. (FR-8)
5. DoD row 7 names its live mechanical owner. (FR-9)

## Non-goals

- No external/CI deployment or release-engine changes (`triggerPostMergeReleaseIfConfigured` untouched).
- No auto-deploy for projects other than the overdeck repo the server runs from.
- No removal or restructuring of Step 0 / `pending-post-merge.json` / `processPendingLifecycle` machinery.
- No change to flywheel doctrine or authority (it remains the deployer when running).
- No auto-close-out or other DoD-row automation beyond deploy (PAN-2715 owns the gate).
- No fix for pre-existing dual live servers / orphaned peers (PAN-2318 territory).
