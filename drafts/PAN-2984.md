# PAN-2984 — Assisted Node-24 install for the open-knowledge viewer

**Issue:** https://github.com/eltmon/overdeck/issues/2984 · Refs #2066, #2983
**Status:** draft (planning session 2026-07-21, auto mode)

## Glossary

- **open-knowledge / OpenKnowledge** — `@inkeep/open-knowledge`, the GPL-licensed npm package providing the `ok` CLI and the local knowledge-viewer web UI. Kept at arm's length (spawned executable, HTTP access; never imported). Declares `engines.node >=24`.
- **`ok`** — the open-knowledge CLI binary. Every Overdeck invocation today spawns the literal string `'ok'` and relies on `PATH` resolution.
- **Viewer** — the open-knowledge server+UI pair started by `ok start`, embedded by the dashboard Knowledge page and opened by `pan knowledge open`.
- **Ambient / default Node** — whatever `node` resolves to on the user's `PATH`. Overdeck itself requires >=22.16 and the dashboard is pinned to Node 22 (node-pty, circular ESM). The viewer must NOT require changing this.
- **Version manager** — a per-user Node multiplexer: nvm, fnm, volta, mise, or asdf. Each keeps complete Node runtimes in its own directory tree, so a Node 24 runtime can exist without being the default.
- **Runtime** — one installed Node version directory containing `bin/node` (e.g. `~/.config/nvm/versions/node/v24.17.0`).
- **Shim** — a 2-line `#!/bin/sh` script written to `~/.local/bin/ok` that `exec`s a pinned Node 24 binary against the installed open-knowledge entry script, bypassing the package's `#!/usr/bin/env node` shebang (which would resolve the wrong node).
- **Detection ladder / rung** — the ordered resolution strategy in `ensureOpenKnowledge()`: (1) working `ok`, (2) `OVERDECK_OPEN_KNOWLEDGE_NODE` override, (3) version manager that already has a 24+ runtime, (4) version manager without one, (5) no version manager.
- **Setup plan** — a structured, plain-English description of what the ladder is about to do, shown before any action (CLI prompt / dashboard panel). Shared between CLI and dashboard.

## Problem

`pan knowledge open` and the dashboard Knowledge page hard-fail on machines whose ambient Node is <24 with `open-knowledge requires Node 24+; found v22.22.0` ([`src/lib/installers/open-knowledge.ts:336-340`](src/lib/installers/open-knowledge.ts)). "Upgrade your Node" is the wrong ask twice over: Overdeck's own dashboard is pinned to Node 22, and on the operator machine a Node 24 runtime already existed under nvm — the installer just never looked. The viewer needs a Node 24 runtime *for the `ok` subprocess only*.

A hand-verified reference of rung 3 exists on the operator machine at `~/.local/bin/ok`:

```sh
#!/bin/sh
# Pin open-knowledge to Node 24 (package declares engines.node >=24);
# the ambient default node is v22 for the Overdeck dashboard.
exec /home/eltmon/.config/nvm/versions/node/v24.17.0/bin/node /home/eltmon/.config/nvm/versions/node/v24.17.0/lib/node_modules/@inkeep/open-knowledge/dist/cli.mjs "$@"
```

`pan knowledge open` succeeds with it.

## Requirements

- **FR-1** — Never modify the user's default/ambient Node or their shell rc files. Version-manager install commands must be the non-default-changing variants (see the manager table; e.g. `volta fetch`, never `volta install`).
- **FR-2** — The shim must survive default-node changes and be detectably broken (and re-resolvable) if its pinned runtime is later removed. Rung 1's health probe is the detector; a broken Overdeck-owned shim is rewritten by re-walking the ladder.
- **FR-3** — The dashboard Knowledge page error state becomes an assisted flow: a "Set up the viewer" button that shows what it will do before doing it, sharing the ladder with the CLI path.
- **FR-4** — `pan install` mention stays informational only; nothing eager. (No changes to `pan install` code paths; the docs sentence in `configuration/knowledge.mdx:31` about "no unattended install" stays true.)
- **FR-5** — The resolved `ok` command (absolute shim path when applicable) is threaded through every `ok` invocation (status/start/stop) instead of relying on the invoking process's `PATH` containing `~/.local/bin`. The dashboard server's `PATH` cannot be assumed to include it.
- **FR-6** — CLI and dashboard consume one shared setup-plan resolver; neither reimplements ladder logic.
- **NFR-1** — Keep the injectable-command test seams (`CommandRunner`, `dependencies` objects); add tests for each ladder rung with fake runtimes; fake timers (`vi.useFakeTimers`) for any retry/backoff per the repo rule.

## The detection ladder (specification)

`ensureOpenKnowledge()` walks the rungs in order. `--no-install` (`autoInstall: false`) keeps today's strict behavior: rung 1 or throw with the manual command — rungs 2–5 are skipped entirely.

1. **Existing working `ok`.** Probe `ok --version` on `PATH`; if that fails, additionally probe `~/.local/bin/ok` by absolute path (the dashboard server's `PATH` may lack `~/.local/bin`). Success returns `{ status: 'already-installed', command: <the command that worked> }`. If an Overdeck-owned shim exists but its probe fails (pinned runtime deleted), continue down the ladder and rewrite it (FR-2).
2. **Explicit override.** `OVERDECK_OPEN_KNOWLEDGE_NODE=/path/to/node24`: validate it is an executable Node >=24 (`<path> --version`), then install/shim under it exactly as rung 3. An invalid override is a hard error naming the env var — never silently fall through (advanced-dev escape hatch; misconfiguration must be loud).
3. **Version manager with an existing 24+ runtime.** Enumerate installed runtimes (table below), pick the highest >=24, install `@inkeep/open-knowledge` under it, write the shim. Zero downloads of Node itself.
4. **Version manager without a 24+ runtime.** Offer (CLI prompt / dashboard plan + button) to install Node 24 through *their* manager with the non-default-changing command, then proceed as rung 3.
5. **No version manager.** Offer to install nvm (official install script) and continue via rung 4→3, or print the manual one-liner and exit.

### Version-manager table (detection roots, runtime layout, safe install command)

| Manager | Detection roots (first hit wins) | Runtime node binaries | Rung-4 install command (never changes default) |
| --- | --- | --- | --- |
| nvm | `$NVM_DIR`, `~/.nvm`, `~/.config/nvm` | `<root>/versions/node/v*/bin/node` | `bash -c '. "<root>/nvm.sh" && nvm install --no-progress 24'` (shell-local; does not touch the `default` alias) |
| fnm | `$FNM_DIR`, `~/.local/share/fnm`, `~/Library/Application Support/fnm` | `<root>/node-versions/v*/installation/bin/node` | `fnm install 24` |
| volta | `$VOLTA_HOME`, `~/.volta` | `<root>/tools/image/node/*/bin/node` | `volta fetch node@24` — **not** `volta install`, which changes the default (FR-1) |
| mise | `$MISE_DATA_DIR`, `~/.local/share/mise` | `<root>/installs/node/*/bin/node` | `mise install node@24` |
| asdf | `$ASDF_DATA_DIR`, `~/.asdf` | `<root>/installs/nodejs/*/bin/node` | `asdf install nodejs latest:24` |

Manager detection = detection root directory exists (env var respected first). "Has a 24+ runtime" = at least one runtime glob match whose version-directory name parses to major >=24 (parse the path segment; do not execute every binary). The chosen binary is validated once with `<node> --version` before use. After a rung-4 install completes, re-run rung-3 enumeration rather than guessing the resulting path.

### Installing the package under a pinned runtime (rung 2/3 mechanics)

Run `<runtimeBin>/npm install -g @inkeep/open-knowledge` with `env.PATH = <runtimeBin> + path.delimiter + process.env.PATH`, where `<runtimeBin>` = directory of the pinned node binary. Prepending `PATH` makes npm's `#!/usr/bin/env node` shebang and any package lifecycle scripts resolve the pinned Node 24, and npm's global prefix resolves to the runtime's own tree — nothing outside the runtime directory is written (FR-1). Then resolve the entry script as `realpath(<runtimePrefix>/bin/ok)` (the bin symlink target — robust against `dist/cli.mjs` moving) and write the shim.

### Shim contract

Written to `~/.local/bin/ok` (create the directory if needed), mode `0755`:

```sh
#!/bin/sh
# overdeck-managed shim (PAN-2984): pins open-knowledge to a Node 24 runtime.
# Regenerate with `pan knowledge open`; safe to delete.
exec "<nodePath>" "<entryScriptRealpath>" "$@"
```

- The `overdeck-managed shim` marker line is the ownership test. If `~/.local/bin/ok` exists **without** the marker (user's own file, like today's hand-written one — which predates the marker), never overwrite it: if it works, rung 1 already used it; if it is broken, fail with a message naming the file and asking the user to delete or fix it. An Overdeck-owned shim may always be rewritten.
- `ensureOpenKnowledge` returns the **absolute shim path** as `command` after writing it; callers must use that value rather than assuming `ok` is on `PATH` (FR-5). The shim still serves human shells that do have `~/.local/bin` on `PATH`.

### Setup plan (shared CLI/dashboard structure)

New pure resolver in the installer layer:

```ts
export type OpenKnowledgeSetupPlan =
  | { kind: 'ready'; command: string }                                                   // rung 1
  | { kind: 'install-under-runtime'; source: 'override' | ManagerName; nodePath: string; steps: string[] }  // rungs 2-3
  | { kind: 'install-node-via-manager'; manager: ManagerName; installCommand: string; steps: string[] }     // rung 4
  | { kind: 'install-nvm'; steps: string[]; manualCommand: string };                     // rung 5
```

`steps` are complete plain-English sentences (per the operator-messages rule) — e.g. "Install Node 24 with fnm by running `fnm install 24`. Your default Node and shell configuration will not change." `resolveOpenKnowledgeSetupPlan()` only inspects; `executeOpenKnowledgeSetupPlan(plan)` performs it. `ensureOpenKnowledge` composes the two; CLI/dashboard use the resolver to *show* the plan before executing.

**Consent boundaries:** rungs 1–3 (zero Node downloads) run under the existing auto-install consent — CLI default (opt out with `--no-install`) and the dashboard's explicit button click. Rungs 4–5 (download Node / install nvm) additionally require: CLI — a `readline/promises` y/N prompt showing `steps` (non-TTY stdin: throw an error containing the steps and manual command instead of hanging); dashboard — the panel renders `steps` and the button click is the consent.

## Design decisions (made here, not by the executor)

- **D1** — Thread the resolved command; don't rely on `PATH`. `EnsureOpenKnowledgeResult.command` widens from `'ok'` to `string`. `getOpenKnowledgeStatus`, `startOpenKnowledgeServer`, `startReadOnlyOpenKnowledgeServer`, and the service's stop path accept `okCommand?: string` (default `'ok'`, preserving every existing caller and test).
- **D2** — New sibling module `src/lib/installers/node-runtime.ts` owns manager detection, runtime enumeration, override validation, and shim writing, with injectable seams (`env`, `homedir`, directory listing, `CommandRunner`). `open-knowledge.ts` owns the ladder orchestration and setup-plan types.
- **D3** — `volta fetch node@24` (rung 4) because `volta install` changes the user's default toolchain — an FR-1 violation.
- **D4** — Package install under the pinned runtime happens with `PATH` prepended (see mechanics above); no `--prefix` flags, no writes outside the runtime tree.
- **D5** — Shim ownership via marker comment; foreign files at `~/.local/bin/ok` are never overwritten.
- **D6** — Rung-5 nvm install uses the official install script one-liner as the offered command; declining prints the manual path (`install nvm or Node 24 yourself, then re-run`). The nvm installer does append to shell rc files by design — the plan text must say so explicitly before consent, satisfying FR-1's spirit ("never *silently* touch rc files"); users who refuse get the manual instructions. `PROFILE=/dev/null` is NOT used because the user genuinely needs nvm on their own PATH later.
- **D7** — Dashboard `install` endpoint executes the full ladder (the click after the rendered plan is the consent); the status endpoint gains a `setupPlan` field so the frontend can render steps before any click.
- **D8** — Windows is out of scope (POSIX `sh` shim; Overdeck targets Linux/macOS).
- **D9** — Keep the `installationError` Node-24 message as the terminal fallback for genuinely unresolvable failures, but it can only be reached after the ladder found no path — no longer a first-line dead end.

## Acceptance criteria (mechanically checkable, mapped 1:1 to work items)

- **W1**: given a fake nvm tree with v22 and v24 runtimes, `resolveNode24Runtime` returns the v24 `bin/node` path; given only v22, returns `manager-without-24`; given no manager roots, returns `none`; given `OVERDECK_OPEN_KNOWLEDGE_NODE` pointing at a fake node whose `--version` reports v24, returns it with `source: 'override'`; given an override whose validation fails, rejects naming the env var.
- **W2**: `writeOkShim` produces an executable file containing the marker and the exec line; called against a foreign `ok` file it rejects without modifying the file; called against an Overdeck-owned shim it rewrites it.
- **W3**: with a fake runtime available, `ensureOpenKnowledge({ autoInstall: true })` invokes npm with `PATH` prepended by the runtime bin dir, writes the shim, and resolves `{ command: <shim path> }`; with only a manager-without-24, it rejects with `OpenKnowledgeSetupRequiredError` carrying an `install-node-via-manager` plan; with `autoInstall: false` it preserves today's manual-command error; the post-install health loop advances via fake timers.
- **W4**: `getOpenKnowledgeStatus` and `startOpenKnowledgeServer` invoke the injected `okCommand` string instead of `'ok'` when provided, and default to `'ok'` when omitted (existing tests pass unmodified).
- **W5**: on a TTY, the CLI prints the plan steps and a `y/N` prompt; answering `y` executes the plan and retries ensure; answering `n` exits printing the manual command; with non-TTY stdin it throws an error containing the steps without prompting; `--no-install` never reaches the prompt.
- **W6**: `GET /api/knowledge-viewer/status` returns `setupPlan.steps` when the viewer is not installed; `POST /api/knowledge-viewer/install` with a resolvable rung-4 plan executes it and returns an installed status.
- **W7**: the not-installed panel renders each `setupPlan.steps` sentence and a button labeled "Set up the viewer"; clicking it fires the install mutation; a failing install surfaces the error message in the existing error region.
- **W8**: `configuration/knowledge.mdx` contains the string `OVERDECK_OPEN_KNOWLEDGE_NODE`, a ladder description, and the shim path `~/.local/bin/ok`; `sync-sources/skills/okf/references/overdeck.md` mentions the assisted Node-24 resolution.

## Out of scope (NonGoals)

- Windows support for the shim or detection ladder (POSIX `sh` only).
- Changing the dashboard's own Node 22 pin, Overdeck's `engines` range, or anything about ambient Node.
- Eager installation from `pan install`, dashboard boot, or any unattended path (FR-4).
- Bundling, importing, or linking open-knowledge code (GPL boundary stays).
- Auto-updating an already-working `ok` installation to newer versions.
- Homebrew/apt/system package managers as Node sources (version managers + nvm bootstrap only).
