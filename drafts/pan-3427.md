# PAN-3427 — Order books are unreachable for every project except the dashboard server's own cwd project

## Glossary

- **Order book** — an operator-curated Flywheel campaign: a durable JSON entity (`orders/<id>.json` on a project's `overdeck-state` branch) naming issues in two lanes, with status `draft → ready → running → drained → complete`. Full model: `docs/ORDER-BOOKS.md`.
- **State root** — the on-disk root of a project's state plane. Resolved per project by `resolveStateReadHomeSync(project, projectKey?)` in `src/lib/state-read-home.ts:22`, which returns `{ root, migrated }`. For migrated projects `root` is `${OVERDECK_HOME}/state/<projectKey>/`.
- **Projects registry** — `projects.yaml` under `OVERDECK_HOME`, read through `src/lib/projects.ts`. Relevant functions: `listProjectsSync()` (`src/lib/projects.ts:546`), `getProjectSync(key)` (`src/lib/projects.ts:883`), `findProjectByPathSync(path)` (`src/lib/projects.ts:738`), `resolveProjectPath(project)` (`src/lib/projects.ts:790`).
- **Project key** — the registry key for a project (e.g. `panopticon-cli`, `myn`). `projectKey(project, explicit?)` in `src/lib/project-key.ts:20` resolves the registered key from a `ProjectConfig`.
- **Flywheel singleton** — one Flywheel run per machine; `spawnFlywheel` throws while any run is active. A run is bound to a book via `launch.json` → `orders.bookId`, written by `writeFlywheelLaunchMetadata`.
- **Read door / write door** — `src/lib/orders/resolver.ts` is the only order-book read door; `src/lib/orders/writer.ts` the only write door. All new reads/writes extend these; nothing else touches `orders/*.json` (`scripts/lint-state-writes.sh` enforces).
- **Server project** — the project containing the dashboard server process's own cwd (`findProjectByPathSync(process.cwd())`). Today this is the only project whose books the dashboard can see.

## Problem

Order books are per-project state, but every supported surface resolves "the" state root from a single ambient cwd, so books belonging to any project other than the dashboard server's own are unreachable:

1. **Dashboard HTTP routes are cwd-pinned.** `stateRootFor` in `src/dashboard/server/routes/orders.ts:61` resolves `findProjectByPathSync(process.cwd())` — the server process's cwd. `PATCH /api/orders/:id {status: ready}` for another project's book returns `Order book not found`. The `/orders` UI (`src/dashboard/frontend/src/pages/OrderBookPage.tsx`) has the same blindness because it fetches bare `/api/orders*`.
2. **The draft→ready transition only exists on that HTTP route.** The CLI (`src/cli/commands/orders.ts`) has create/list/show/add/remove/move/start but no `queue` verb, so a non-server project's book is stuck in `draft` (`start` refuses: must be `ready`). Reproduced 2026-08-01 with `2026-08-01-myn-hermes-smoke-test-remediation`; the workaround was calling `setStatus(stateRoot, id, 'ready')` directly via tsx.
3. **Continuation never crosses projects.** `completeFlywheelRun` in `src/cli/commands/flywheel-complete.ts:92` only advances the queue within `stateRootFor(launch.workspace)` (line 105) and only when the completing run was itself orders-bound (line 102). Combined with the machine-level singleton, a READY book in another project's state root starves indefinitely: it can't start now (singleton) and nothing will ever start it later (continuation can't see it).

Two coherence defects follow from the same root cause and must be fixed with it, or the new paths fail immediately:

4. **The dashboard start route would launch the Flywheel in the wrong project.** `defaultStartOrderBook` in `src/dashboard/server/routes/orders.ts:273` calls `startFlywheelRun({ cwd: process.cwd(), orders: book.id })`. For a non-server project's book, `resolveFlywheelOrderStart(cwd, …)` (`src/cli/commands/flywheel-orders.ts:40`) would look for the book in the wrong state root and fail.
5. **The Flywheel-page widget 404s on a cross-project active book.** `OrderBookModule.tsx:27` fetches `GET /api/orders/:id`; once continuation can start another project's book, the active run's book is no longer guaranteed to live in the server project's state root.

## Requirements

### Functional

- **FR-1** — Every `/api/orders*` route accepts an optional `project` query parameter naming a projects-registry key. The state root is resolved as `resolveStateReadHomeSync(getProjectSync(key), key).root`. When the parameter is absent, behavior is exactly as today (server cwd project).
- **FR-2** — An unknown `project` key produces HTTP 400 with a message naming the key (`Unknown project: <key>`), not a 404 for the book.
- **FR-3** — `GET /api/orders/:id` without a `project` parameter, when the book is absent from the default state root, scans the other registered projects' state roots in registry order and returns the first match. The book projection (and the `GET /api/orders` list envelope) carries a `project` field naming the resolved key.
- **FR-4** — `POST /api/orders/:id/start` launches the Flywheel with `cwd` set to the book's project root (`resolveProjectPath(project)`), so the run, the brief, and the launch metadata all belong to the book's project.
- **FR-5** — Every `pan orders` subcommand accepts `--project <key>`, resolved through the same registry path as FR-1; omitted means cwd resolution as today.
- **FR-6** — `pan orders queue <id>` transitions a `draft` book to `ready` through the orders write door, refusing with a clear message when the book is not `draft` (same guard as the HTTP PATCH route: "Order book <id> must be draft before it can be queued").
- **FR-7** — The "first ready book in queue order" read lives in the orders read door (`src/lib/orders/resolver.ts`) as `firstReadyBookInQueue(stateRoot)`, and `writer.advanceQueue` (`src/lib/orders/writer.ts:206`) reuses it instead of its inline `readOrderBookIndex` loop, so queue-order knowledge stays in one door.
- **FR-8** — When `completeFlywheelRun` advances the queue and finds no ready book in the completing run's own state root, it scans the other registered projects' state roots in registry order and starts the first ready book found, with `cwd` set to that project's root and the brief resolved to that project's default brief (no `brief` option passed). The completion result and console output name the project when the continuation crosses projects.
- **FR-9** — The `/orders` page has a project picker listing all registered projects (from the existing `GET /api/registered-projects`), defaults to the server project (from the new `project` field on the list envelope), threads `?project=<key>` through every orders fetch, and honors a `?project=` URL search param so a selection is deep-linkable. The Flywheel-page widget links back to `/orders?project=<key>` using the projection's `project` field.
- **FR-10** — Documentation names the new surface: `docs/ORDER-BOOKS.md` (HTTP surface, lifecycle continuation, CLI verbs) and `configuration/order-books.mdx` (operator guide: picker, `queue`, `--project`, cross-project continuation). The `pan-orders` wrapper skill is updated in the same commits as the CLI changes (lint-enforced by `scripts/lint-skills.sh`).

### Non-functional

- **NFR-1** — Backward compatibility: every existing caller that passes no `project` parameter observes identical behavior to today (server-cwd project for routes, cwd for CLI).
- **NFR-2** — Single-door discipline: new reads go through `src/lib/orders/resolver.ts`, writes through `src/lib/orders/writer.ts`; no route, CLI command, or UI reads `orders/*.json` directly.
- **NFR-3** — No `execSync` in server-reachable code; all new code uses the existing sync registry readers (`getProjectSync`, `listProjectsSync`, `resolveStateReadHomeSync` are already synchronous and filesystem-only) or async primitives.

## Decisions (made in this document — do not re-litigate during implementation)

- **D1 — Query param, not path segment.** `?project=<key>` follows the existing precedent (`/api/workspace-registry/project-targets?project=`, `/api/orders/backlog-candidates?limit=`) and is purely additive: old URLs keep working. A path segment would fork the route table.
- **D2 — Continuation scans all tracked projects, not the run's scope.** A `ready` order book is an explicit operator release (`docs/ORDER-BOOKS.md`: "Book membership counts as operator release for the pickup gate"); Flywheel `scope` governs backlog pickup, not curated queues. Gating continuation on scope would re-create the starvation this issue fixes for `pan-only` runs.
- **D3 — Cross-project continuation uses the target project's default brief.** `requireFlywheelBrief(cwd, requestedPath?)` (`src/lib/flywheel-start.ts:33`) enforces that the brief lives inside the project root; carrying the completing run's `briefPath` across projects would either violate containment or silently run the old project's brief against the new project. Passing no `brief` resolves `docs/flywheel-brief.md` in the target project — the same default `pan flywheel start` uses there.
- **D4 — No new "orders projects" endpoint.** The picker gets its option list from the existing `GET /api/registered-projects` (`src/dashboard/server/routes/misc/meta.ts:128`, already cached in the frontend under queryKey `registered-projects`) and the default selection from the new `project` field on the `GET /api/orders` envelope. Per-project book counts in the picker are a NonGoal.
- **D5 — Single-book GET scans on miss rather than 404.** This keeps `OrderBookModule` (Flywheel page) and any deep link correct when the active run's book lives in another project, without requiring every consumer to know the book's project up front. Scan order is deterministic: server project first, then `listProjectsSync()` registry order.
- **D6 — `--project` on every CLI verb, not just `queue`.** The issue title is that books are unreachable; a flag only on `queue` would leave `add`/`show`/`move` cwd-bound. One shared resolution helper keeps this mechanical.
- **D7 — Issue-state lookup needs no change.** `liveOrderIssueLookup` (`src/lib/orders/resolver.ts:41`) reads the server's shared issue service across all registered projects, so enrichment and validation are already project-agnostic once the correct state root is supplied. PRD lookup (`hasOrderIssuePrd`) is state-root-relative and becomes correct for the same reason.

## NonGoals

- No aggregate cross-project book list view; the list route and UI stay single-project, switched by the picker.
- No deacon patrol that auto-starts ready books while the Flywheel is idle; cross-project start happens at completion-continuation time or by explicit operator action only.
- [PAN-3426](https://github.com/eltmon/overdeck/issues/3426) (CLI `orders start` validates against an unstarted issue service) is a separate issue and stays open.
- No change to the machine-level Flywheel singleton or per-project concurrency.
- No per-project book counts or status badges in the picker.
- No changes to `dispatch-gate.ts`/`eligibility.ts`: they resolve the book via `launch.workspace`, which is already the book's project root once FR-4 lands.
- No tracker/PRD changes to how books reference issues from other projects; a book's items remain issues of its own project.

## Acceptance criteria (mechanically checkable)

1. `curl 'https://overdeck.localhost/api/orders?project=<other-key>'` returns that project's books and `project: <other-key>`; the same request without the parameter returns the server project's books.
2. `PATCH /api/orders/:id?project=<other-key> {status: ready}` queues a draft book in that project; an unknown key returns HTTP 400 naming the key.
3. `GET /api/orders/<id>` for a book that exists only in another project's state root returns 200 with `project` naming that project.
4. `pan orders queue <id> --project <key>` from any cwd moves a draft book in that project to `ready`; a non-draft book exits non-zero with the guard message.
5. `pan flywheel complete` with no ready book in the completing project and a ready book in a second project starts a new run whose launch metadata `workspace` is the second project's root.
6. `npm run typecheck`, `npm run lint`, and `npm test` pass with the new tests in: `src/dashboard/server/routes/__tests__/orders.test.ts`, `tests/unit/cli/orders.test.ts`, `tests/unit/lib/orders/orders-resolver.test.ts`, `tests/unit/cli/flywheel-complete.test.ts`, `src/dashboard/frontend/src/pages/__tests__/OrderBookPage.test.tsx`.
7. `docs/ORDER-BOOKS.md` and `configuration/order-books.mdx` document every behavior above; `scripts/lint-skills.sh` passes with the updated `pan-orders` skill.
