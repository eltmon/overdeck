# PRD: PAN-3184 — Boot reconciliation latches hold_all over an empty candidate set

**Issue:** https://github.com/eltmon/overdeck/issues/3184
**Companion issue (owns the rogue writer, out of scope here):** https://github.com/eltmon/overdeck/issues/3183

## Glossary

- **Boot reconciliation** — the dashboard-boot flow that decides what to do with agents that were running before the previous shutdown. Stamps a `bootId` + grace deadline, holds resumable candidates during the grace window, then commits a durable decision (`resume_all` / `hold_all` / `per_agent`). Core: `src/lib/cloister/boot-reconciliation.ts`.
- **Candidate** — a stopped agent eligible for boot-resume, decided by `isBootReconciliationCandidate()` (`src/lib/cloister/boot-reconciliation.ts:101`). Recomputed **live** on every read/apply; there is no persisted stamp-time set.
- **Grace window** — `startup.reconciliation_grace_secs` (default 120s, `DEFAULT_BOOT_RECONCILIATION_GRACE_SECS` at `src/lib/cloister/boot-reconciliation.ts:20`). On expiry the timer callback in `armBootReconciliationGraceTimer` (`src/lib/cloister/boot-reconciliation.ts:214`) currently commits `hold_all` unconditionally.
- **Boot window / recency** — a stopped agent is "recent" when its newest timestamp (`lastActivity`/`stoppedAt`/`startedAt`) is ≥ `bootStartedAt − reconciliation_max_candidate_age_secs` (default 240s; `isRecentBootCandidate`, `src/lib/cloister/boot-reconciliation.ts:77`).
- **Held set** — agents whose resume is suppressed by the current decision. Two mechanisms: `getBootReconciliationHeldResumeSet()` (candidate-based) gates the batch path, and an event-path hold in `handleAgentStoppedEvent` (`src/lib/cloister/deacon-auto-resume.ts:657-661`) parks **every** stopped work agent while the decision is `pending`/`hold_all`.
- **Vacuous hold** — a `hold_all` decision latched while the live candidate set is empty. Suppresses event-path resumes yet acts on nothing; the banner self-hides; `resume_all` resumes nothing.
- **Clean boot / crash boot** — classification of this dashboard start by whether the previous dashboard shutdown was signal-handled (SIGTERM/SIGINT/SIGHUP → clean) or not (OOM, SIGKILL, power loss → crash).
- **stoppedByUser** — agent-table flag meaning "deliberately stopped by the operator." Auto-resume refuses these. PAN-3183 documents a rogue boot-path writer that batch-stamped this flag on the whole fleet 39s before the incident boot.
- **Strike agent** — `pan strike` fast-fix agent; `role: 'strike'` (`src/lib/agents/spawn.ts:493`). Currently refused by every auto-resume role gate.

## Problem

Verified incident chain (2026-07-27 reboot; issue body has the log lines):

1. A pre-deacon writer (PAN-3183's subject) batch-stopped the fleet at 02:52:14Z, stamping `stoppedByUser: true`. At the 02:52:53Z stamp, `isBootReconciliationCandidate` excluded the entire cohort — strikes by the `role !== 'work'` gate (`boot-reconciliation.ts:102`), the work agent by the `stoppedByUser` exclusion (`boot-reconciliation.ts:104`) — despite all stops being 39s old, well inside the 240s recency window.
2. The grace timer expired over the empty set and latched `hold_all` unconditionally (`boot-reconciliation.ts:217`).
3. The event-path hold (`deacon-auto-resume.ts:658`) then parked every subsequent stopped-agent event — a broader set than the candidates the UI and `resume_all` can see.
4. `GET /api/boot-reconciliation` returned `{decision: "hold_all", set: []}`.
5. `BootReconciliationModal.tsx:338` (`if (heldAgents.length === 0) return null`) hid the banner because it derives held agents from the empty candidate `set`.
6. `POST /api/boot-reconciliation/decision` with `resume_all` applied to the empty live candidate list → `{resumed: [], count: 0}`. Even with a non-empty list it would have refused the cohort: `handleAgentStoppedEvent` refuses `stoppedByUser` agents (`deacon-auto-resume.ts:742`) and non-`work` roles (`deacon-auto-resume.ts:639`).

Net effect: a clean operator reboot parked a 7-agent fleet with no popup, no banner, and a resume-all that resumes nothing.

## Proposal

Make the candidate set reflect the recently-stopped cohort, make a vacuous `hold_all` impossible, classify the boot clean-vs-crash and default toward resume only after a clean shutdown, and drive the banner and `resume_all` from one live server-computed held set.

This **amends a resolved decision** in `docs/FAILSAFE-CONTROL-ARCHITECTURE.md:85` ("the expiry action is **Hold**… locked by test"). The amendment: expiry action is Hold **only on crash/unknown boots with a non-empty candidate set**; clean boots default to Resume; an empty candidate set always auto-releases. The PAN-3052 constraint stands: no surface may promise "auto-resuming" for a crash boot.

### Decision rules (made here, not left to the implementer)

- **D1 — In-window stops are presumed boot-caused.** The `stoppedByUser` candidacy exclusion is deleted, not relaxed: recency (`isRecentBootCandidate`) is the sole discriminator. A stop older than the boot window is already excluded by recency; a stop inside the window is treated as boot fallout and shown to the operator. Rationale: after PAN-3183, `stoppedByUser` attribution near boot is untrustworthy, and the dialog exists precisely to let the operator disposition the cohort.
- **D2 — Strikes are boot-resumable.** Candidacy and `handleAgentStoppedEvent`'s role gate admit `work` and `strike` via one shared helper `isAutoResumableRole(role)`. `resumeAgent()` is role-agnostic; kickoff delivery already treats the two roles alike (`src/lib/agents/spawn.ts:667`, `src/lib/agents/delivery.ts:732`). The steady-state patrol query (`autoResumeStoppedWorkAgents`, `deacon-auto-resume.ts:866-867`) is **not** widened (NonGoal) — boot reconciliation and the reactive event path only.
- **D3 — The automatic expiry default never resumes `stoppedByUser` agents; an explicit operator `resume_all` does.** Auto expiry (FR-3) filters `stoppedByUser === true` out of the apply batch. The operator clicking **Resume all** is an explicit override and resumes the full held cohort — `handleAgentStoppedEvent` gains `overrideStoppedByUser` for exactly this path. This keeps `pan stop-all-agents` + reboot safe while making the banner button actually work in the incident scenario.
- **D4 — Clean-vs-crash classification, not zero-client hold-open.** The issue offers "and/or stays open while zero dashboard clients are connected." There is no server-side dashboard-client gauge (ws-rpc keeps no global connection count), so we classify the shutdown instead: `handleShutdownSignal` (`src/dashboard/server/main.ts:627`) already runs on SIGTERM/SIGINT/SIGHUP; it persists `dashboard.last_clean_shutdown_at` **synchronously at entry**, before any `await`. A crash, OOM kill, or power cut never writes the marker.
- **D5 — One live held set, three consumers.** Candidacy (FR-1), the route's `set` + new `heldCount`, the banner guard, and the apply batch all derive from `listBootReconciliationCandidates()`. No second definition of "held" anywhere.

## Requirements

### Functional

- **FR-1 — Candidacy includes the recently-stopped cohort.** `isBootReconciliationCandidate` admits `role: 'work' | 'strike'` and no longer excludes `stoppedByUser` agents; recency, paused/troubled, skip-reason, workspace-exists, and non-terminal-issue checks unchanged. `handleAgentStoppedEvent`'s role gate (`deacon-auto-resume.ts:639`) uses the same `isAutoResumableRole` helper.
- **FR-2 — Vacuous hold never latches.** The grace-expiry callback recomputes live candidates; if the set is empty it commits `resume_all` (a no-op apply) and logs `vacuous hold auto-released — 0 candidates at expiry`, never `hold_all`.
- **FR-3 — Shutdown-classified expiry default.** New `dashboard.last_clean_shutdown_at` setting written synchronously at `handleShutdownSignal` entry. New `isCleanShutdownBoot()` in `boot-reconciliation.ts`: marker parseable and within `CLEAN_SHUTDOWN_FRESHNESS_MS = 30 * 60 * 1000` of `bootStartedAt`. Expiry over a non-empty candidate set: clean → `resume_all`; crash/unknown → `hold_all` (unchanged safe default).
- **FR-4 — Origin-aware apply.** `applyBootReconciliationDecision(deps, opts?: { origin?: 'operator' | 'auto' })`: `auto` (default; the grace-expiry hook) drops `stoppedByUser` candidates from the batch; `operator` (the decision route) keeps them and passes `overrideStoppedByUser: true` into `handleAgentStoppedEvent`, which then skips its deliberate-stop refusal for those calls only.
- **FR-5 — Live held count drives the banner.** `GET /api/boot-reconciliation` adds `heldCount` (hold_all → live candidate count; per_agent → candidates whose issue is not marked `resume`; else 0) and a `stoppedByUser` boolean on each `set` row. The modal renders the held banner whenever `heldCount > 0` under `hold_all`/`per_agent`, initializes stoppedByUser rows to `hold` in the per-agent map, and labels them `stopped by operator` via `whyStopped` regardless of candidacy.
- **FR-6 — Regression tests** per the Tests table below, using `vi.useFakeTimers()` for every grace-timer case (repo rule: no real `setTimeout` in delay tests).
- **FR-7 — Docs** per WI-8.

### Non-functional

- **NFR-1 — No new config surface.** Classification constants are exported code constants with tests; no new `projects.yaml`/cloister-config keys.
- **NFR-2 — Two-door discipline.** The new setting goes through `control-settings.ts` (`getSetting`/`setSetting` helpers), the existing settings write path — no new store access.
- **NFR-3 — Boot-path safety.** `handleShutdownSignal` and `startBootReconciliation` are boot-path code: the change must not add `await`s before the marker write, and must keep `startBootReconciliation` synchronous.

## Hazards

- **H1 — Operator stops an agent, then reboots within the window.** That agent is now a candidate (D1) and a clean-boot auto-expiry would resume it. Mitigated by D3: the **automatic** default filters `stoppedByUser`; only an explicit operator `resume_all` resumes it. Residual risk: explicit click resumes more than intended — accepted, the button says "all".
- **H2 — Marker written, then crash before boot.** A handled SIGTERM followed by a crash-looping dashboard leaves a fresh marker; the next boot classifies "clean" and auto-resumes. Bounded by the 30-min freshness window and by the concurrency/load/memory gates inside the apply loop. Accepted.
- **H3 — Ancient stopped strikes on the reactive event path.** Widening the `handleAgentStoppedEvent` role gate means a strike that crashes mid-run now auto-resumes (previously refused). Completed strikes carry completion markers and deliberately-stopped ones carry `stoppedByUser`; both are still refused. The steady-state patrol is unchanged (NonGoal), so no herd of historical strikes.
- **H4 — PAN-3183 lands first and fixes the rogue writer.** All fixes here remain correct; D1 simply stops being load-bearing for that failure class. No coordination required.
- **H5 — `per_agent` + `heldCount`.** `heldCount` must subtract issues marked `resume` so the banner disappears once the operator has resumed everything they chose to.

## NonGoals

- Identifying or fixing the 02:52:14Z batch-stop writer — that is PAN-3183, explicitly.
- Widening the steady-state patrol (`autoResumeStoppedWorkAgents`) to strikes.
- A server-side dashboard-client gauge and "hold the window while zero clients connected" (D4 explains why classification was chosen instead).
- Read-model vs agents-table drift (phantom running agents) — PAN-3183.
- CLI parity (`pan boot status`) — PAN-2078.
- Any change to `OVERDECK_NO_RESUME` handling or the Freeze control.
