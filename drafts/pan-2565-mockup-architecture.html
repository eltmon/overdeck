Agent-to-Agent Messaging for Overdeck

Flow mockup — how Overdeck could replicate Traycer's "agents with walkie-talkies" using the machinery it already has. Based on a code review of traycerai/traycer (cloned at ~/Projects/traycer).

Verdict: Traycer's A2A is a brokered mailbox with reply-thread tracking, not magic. Overdeck already owns the two hardest pieces — a push-delivery door (deliverAgentMessage: PTY supervisor → channels → tmux) and a live agent registry — so the replication is mostly one new broker module + one new CLI verb family, not a new transport. We can also skip their heaviest machinery (background monitor processes, versioned RPC bridges) because our push model and single-repo contracts make them unnecessary.

What the repo actually contains

traycerai/traycer is the protocol + clients package only — wire contracts (zod schemas), the CLI (traycer agent send|list|inbox|transcript, traycer monitor), and message formatting. The host broker itself (queues, sweep timers, MCP server, hook installation) is closed-source. But the contracts alone carry the whole design:

  1. Five unary RPCs are the entire A2A surface. agent.create (spawn a child agent), agent.list (discovery with per-agent capabilities), agent.sendMessage (fire-and-forget hand-off), agent.getTranscript (read a peer's conversation, flattened to XML tags), agent.stop (halt, optional cascade down the delegation tree). That's it — everything else is delivery plumbing.
  2. Messages are brokered, never peer-to-peer. agent.sendMessage enqueues a MailboxEnvelope on a RAM-only per-receiver inbox queue in the host. The sender returns immediately; a reply is a separate agent.sendMessage traveling the other way.
  3. Reply threading is explicit, not conversational. expectReply: true makes the broker mint a responseId that names the thread, not the message — follow-ups may share it, and one reply carrying it closes the whole thread. The receiver echoes it back with expectReply: false.
  4. TUI agents receive via a background monitor, not injection. A traycer monitor process spawned inside the Claude Code session subscribes to agent.inbox.subscribe (versioned streaming RPC) and prints each frame to stdout; Claude Code's background-output notification then surfaces it into the agent's context. GUI chat agents skip the inbox entirely — messages arrive as ordinary chat turns with sender: {type: "agent", …}.
  5. Stalled-receiver notices close the loop. If a receiver on an expectReply thread goes silent, the broker fires an inactivity notice to the sender with one of seven reasons: turn-ended (Claude Code Stop hook → agent.tui.turnEnded — the primary signal), exited, quiet (PTY watchdog), user-stopped, errored, awaiting-input, receiver-cancelled.
  6. Every message teaches the receiver how to reply. The injected text is prefixed [traycer:agent-message] with the exact reply command and the responseId inline — the receiving model never has to guess the protocol.
  7. Capability gating is honest. canParticipateInA2A = every GUI agent, plus only Claude Code among TUI harnesses. agent.list exposes per-row {readTranscript, sendMessage} booleans (sendMessage = sameUser ∧ isLocal ∧ canParticipate), so senders can see who is reachable before trying. Cross-host sends are rejected outright (RECEIVER_NOT_LOCAL).
  8. Roles are a side-channel. Agents claim durable (role, scope) tuples inside an epic; claim/release broadcasts a role-awareness frame to currently connected monitors only (never queued — a reconnecting monitor reads roles fresh from its prompt).

The design discipline worth stealing

Traycer freezes every shipped schema version and writes explicit upgrade/downgrade bridge functions between them (contracts.ts is 700 lines of this). An old CLI talking to a new host gets its responses projected down; unrepresentable requests fail with a typed DOWNGRADE_UNSUPPORTED, never a silent semantic change. Overdeck ships all its clients from one repo, so we don't need the bridges — but the attitude (the wire shape is a contract; the receiver's negotiated version is authoritative) is worth keeping for the dashboard RPC surface.

What lands where (if built)

New code

  • src/dashboard/server/services/a2a-broker.ts — mailbox, thread registry, stall sweep
  • agent_messages + a2a_threads tables (rebuildable-cache DB, mirrored like other runtime state)
  • pan msg send|list|inbox|transcript CLI verbs (+ /pan-msg skill per the skills convention)
  • pan agent turn-ended-from-hook + Stop-hook entry in the agent-session settings the launcher writes
  • Message envelope formatter ([overdeck:agent-message]) — the Traycer format, our nouns
  • Dashboard Messages panel (threads, stalls, replay) fed by a domain event over /ws/rpc

Touched, not new

  • deliverAgentMessage — gains an a2a caller kind; transport logic unchanged
  • Deacon patrol — broker sweep registers as one more patrol tick consumer
  • Launcher — exports one extra env (OVERDECK_A2A=1) and the Stop hook
  • Role prompts (roles/*.md) — one section teaching agents the verbs and when to use them

Explicitly not built

  • No background monitor processes (push model covers it)
  • No schema-version bridge machinery
  • No role-claim registry in v1

The verbs an agent learns

# who can I talk to? (live agents + deliverability probe)
pan msg list

# ask a peer, want an answer (opens a thread)
pan msg send --to agent-pan-3011-review \
  --expect-reply \
  --message "Does clearStuck still hold after the review-pipeline change?"
# → { "responseId": "thr_01JXYZ…" }

# fire-and-forget hand-off (no thread)
pan msg send --to agent-pan-2988 \
  --message "Heads up: I touched feedback-target.ts, rebase before you push"

# answer a thread (closes it)
pan msg send --to agent-pan-3011 \
  --response-id thr_01JXYZ… \
  --message "Yes — it only touches review_status rows where …"
# recover a message that arrived truncated
pan msg inbox

# read a peer's transcript (flattened)
pan msg transcript agent-pan-2988

# Stop-hook (wired by the launcher, not typed by agents)
pan agent turn-ended-from-hook

The envelope the receiver sees

Delivered through deliverAgentMessage (PTY supervisor first). Same rule as Traycer: the prefix teaches the protocol so the receiving model never guesses.

[overdeck:agent-message] from work agent PAN-3011 (agent-pan-3011) [claude-code]
[overdeck:agent-message] A reply is expected. Reply with:
  pan msg send --to agent-pan-3011 --response-id thr_01JXYZ --message "<your reply>"
[overdeck:agent-message] The response-id names this thread, not this single message —
  follow-ups may arrive with the same id, and one reply with it answers them all.

Does clearStuck still hold after the review-pipeline change? I'm seeing
a row that …

[overdeck:agent-message] ─── end of message ───
[overdeck:agent-message] If this looks truncated, read it in full with: pan msg inbox

And the stalled-receiver notice, when a thread goes quiet:

[overdeck:a2a-notice] kind=inactivity reason=turn-ended thread=thr_01JXYZ
[overdeck:a2a-notice] agent-pan-3011-review ended its turn without replying to your
  message on thread thr_01JXYZ. Options: wait (it may be mid-work), nudge with
  another pan msg send on the same thread, or escalate to the operator.
