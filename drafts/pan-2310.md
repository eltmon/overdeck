# PAN-2310 — read-door done→merged reconciliation

**Issue:** [PAN-2310](https://github.com/eltmon/overdeck/issues/2310)
**Type:** bug (read-model)
**Difficulty:** simple (single-file, obvious change + regression test)

## Glossary

- **Read door / read-model** — the single canonical resolver that serves issue data to the dashboard. Here it is `IssueDataService.getIssues()` in `src/dashboard/server/services/issue-data-service.ts`. No route reads issue state directly; it goes through this resolver.
- **`mergeStatus`** — a per-issue field describing where the issue sits in the merge lifecycle (`pending`, `merged`, etc.). On a served issue it originates from the per-issue record's planning-time `pipeline` block and is optionally overwritten from the live `review_status` cache.
- **`reviewStatusesCache`** — an in-memory `Record<string, ReviewStatus>` on `IssueDataService`, backed by the `review_status` SQLite table. Currently empty (0 rows) in the running instance, which is what exposes the bug.
- **canonical status** — the normalized dashboard status computed by `getCanonicalStatus(status, stateType)` at `issue-data-service.ts:42`. Maps `done`/`completed`/`closed` → `'done'`, and `canceled`/`cancelled`/`duplicate`/`won't do` → `'canceled'`.
- **forward reconciliation** — the existing rule (lines 455–464): when `mergeStatus === 'merged'` but canonical status is not yet `done`/`canceled`, surface the issue as `Verifying`/`verifying_on_main`.
- **inverse reconciliation** — the NEW rule this issue adds: when canonical status IS `done`, never surface a non-terminal `mergeStatus`; resolve it to `merged`.

## Problem

Closed/`done` issues render **"Done" in the project issue tree** but **"pending" in the issue detail/slide-out**. A scan found 18 issues in this state (`state=done` but `mergeStatus=pending`, one `failed`): PAN-1762, 1832, 1847, 1919, 1935, 1989, 2044, 2076, 2148, 2150, 2155, 2173, 2174, 2181, 2214, 2222, 2248, 2258.

Sampled issues (2258, 2248, 2150, 1919, 1935) were code-verified as genuinely merged on main — so the tree's "Done" is correct and the display's "pending" is stale.

## Root cause (verified against the code)

`src/dashboard/server/services/issue-data-service.ts:449-469` augments `mergeStatus` from `reviewStatusesCache`. Verified current shape:

```ts
// Augment with mergeStatus from the asynchronous review-status cache.
allIssues = allIssues.map(issue => {
  const key = issue.identifier?.toUpperCase();
  const rs = key ? this.reviewStatusesCache[key] : null;
  if (rs?.mergeStatus) {
    const issueWithMerge = { ...issue, mergeStatus: rs.mergeStatus };
    if (rs.mergeStatus === 'merged') {
      const canonical = getCanonicalStatus(issue.state ?? issue.canonicalStatus ?? issue.status, issue.stateType);
      if (canonical !== 'done' && canonical !== 'canceled') {
        return {
          ...issueWithMerge,
          status: 'Verifying',
          canonicalStatus: 'verifying_on_main',
          state: 'verifying_on_main',
        };
      }
    }
    return issueWithMerge;
  }
  return issue;   // <-- BUG PATH: cache empty → stale mergeStatus=pending passes through unchanged
});
```

When the `review_status` cache is empty (0 rows), `rs` is `null`, the `if` block is skipped, and the issue is returned unchanged carrying its stale `mergeStatus=pending`. Only the forward direction (merged-but-not-done → Verifying) is reconciled; there is no inverse (done-but-not-merged → merged).

- The **tree** renders canonical `state` → `Done` (fresh from the tracker).
- The **issue display** renders `mergeStatus` → `pending` (stale).

## Proposal

Add inverse reconciliation to the SAME `.map()`, applied regardless of cache state so it also fixes the empty-cache path. Compute the canonical status once at the top of the callback and, when it is `'done'`, coerce any non-`merged` `mergeStatus` to `merged` before returning — in both the cache-hit `return issueWithMerge` path and the cache-miss `return issue` path.

**Before → after** (the `.map()` callback at line 450):

```ts
allIssues = allIssues.map(issue => {
  const key = issue.identifier?.toUpperCase();
  const rs = key ? this.reviewStatusesCache[key] : null;
  const canonical = getCanonicalStatus(issue.state ?? issue.canonicalStatus ?? issue.status, issue.stateType);
  if (rs?.mergeStatus) {
    const issueWithMerge = { ...issue, mergeStatus: rs.mergeStatus };
    if (rs.mergeStatus === 'merged') {
      if (canonical !== 'done' && canonical !== 'canceled') {
        return {
          ...issueWithMerge,
          status: 'Verifying',
          canonicalStatus: 'verifying_on_main',
          state: 'verifying_on_main',
        };
      }
    }
    // Inverse reconciliation: a done issue's work has landed — never show a non-terminal mergeStatus.
    if (canonical === 'done' && issueWithMerge.mergeStatus !== 'merged') {
      return { ...issueWithMerge, mergeStatus: 'merged' };
    }
    return issueWithMerge;
  }
  // Cache miss: reconcile a stale done issue the same way.
  if (canonical === 'done' && issue.mergeStatus && issue.mergeStatus !== 'merged') {
    return { ...issue, mergeStatus: 'merged' };
  }
  return issue;
});
```

**Design decisions (auto-mode defaults):**

- **Gate strictly on `'done'`.** A `'canceled'` issue may legitimately be unmerged and must NOT be shown as `merged`. `getCanonicalStatus` already maps cancel-family statuses to `'canceled'`, distinct from `'done'`, so the strict equality check is sufficient.
- **Only coerce when a `mergeStatus` is actually present and non-terminal.** In the cache-miss path we guard on `issue.mergeStatus && issue.mergeStatus !== 'merged'` so we never invent a `mergeStatus` on an issue that never had one, and never rewrite one that is already `merged`.
- **Reuse the existing `getCanonicalStatus(issue.state ?? issue.canonicalStatus ?? issue.status, issue.stateType)` precedence** already used by the forward branch — do not introduce a different status source, to keep both directions consistent.
- **Keep the change inside the existing `.map()`** — no new pass over `allIssues`, no new helper module. Defense-in-depth living next to the forward rule it mirrors.

This is defense-in-depth: even when the runtime cache is empty or a per-issue record is stale, a closed/`done` issue never displays `mergeStatus=pending`.

## Requirements

- **FR-1** — When an issue's canonical status is `'done'`, `getIssues()` never returns it with a non-`merged` `mergeStatus`; it resolves such a `mergeStatus` to `'merged'`. Holds whether or not the `review_status` cache has an entry for the issue.
- **FR-2** — Issues whose canonical status is `'canceled'` are never coerced to `mergeStatus=merged`; an unmerged canceled issue keeps its original `mergeStatus`.
- **FR-3** — The inverse rule only rewrites an existing non-terminal `mergeStatus`; it never adds a `mergeStatus` to an issue that had none, and never alters an already-`merged` value.
- **NFR-1** — No new pass over the issue array and no new module; the change lives inside the existing `.map()` at `issue-data-service.ts:449` and reuses `getCanonicalStatus`.

## Out of scope (NonGoals)

- Fixing the upstream cause of the stale per-issue record (why `review_status` is empty / why the record froze at `pending`). Filed separately as the record-reconciliation bug; this issue is the read-door defense-in-depth layer only.
- Backfilling or repairing the `review_status` SQLite table or the 18 already-affected records at rest.
- Any change to the tree renderer or the issue-display frontend components — the fix is entirely in the read-door resolver.
- Changing forward reconciliation (merged-but-not-done → Verifying) behavior.
- Touching `'canceled'` issue display.

## Acceptance criteria

1. A `done`/closed issue with an empty `reviewStatusesCache` and a base `mergeStatus=pending` resolves to `mergeStatus=merged` in `getIssues()` output — tree and issue-display agree.
2. A `canceled` issue with a base `mergeStatus=pending` is unaffected (still `pending`, not `merged`).
3. Unit test in `tests/dashboard/issue-data-service.test.ts` covers criteria 1 and 2 using the existing `injectIssues` + `service.reviewStatusesCache` harness.
