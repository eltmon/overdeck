# PAN-2596 — Generic file attachment in conversation composer (+ button and drag-and-drop)

**Issue:** https://github.com/eltmon/overdeck/issues/2596
**Author:** planning agent (claude-fable-5), 2026-07-13
**Status:** draft

## Glossary

- **Composer** — the message-composition area at the bottom of the dashboard ConversationPanel: `src/dashboard/frontend/src/components/chat/ComposerFooter.tsx` (Lexical editor + toolbar).
- **composerStore** — module-level Zustand store at `src/dashboard/frontend/src/lib/composerStore.ts` holding per-conversation ephemeral composer state (pending uploads, sending flag, optimistic messages) so it survives pane unmounts (PAN-1591).
- **Attachment** — a file the user queues in the composer for upload. Today only images qualify; this issue generalizes to a curated set of text/code files plus PDF.
- **Upload route** — `POST /api/conversations/:name/upload-image` (`src/dashboard/server/routes/conversations.ts:493`, `postConversationUploadImageRoute`), a rate-limited multipart endpoint delegating to `handleConversationImageUploadFile` in `src/lib/overdeck/conversation-message.ts`.
- **`@path` token convention** — on send, each uploaded attachment's server path is spliced into the plain-text message body as `@<serverPath>` (`ComposerFooter.tsx:384-387`). Harnesses consume a text stream; `extractConversationAttachmentPaths` (`src/dashboard/server/services/conversation-attachments.ts`) re-parses these tokens server-side.
- **Vision gate** — two independent checks that block image input for models without vision: frontend `modelSupportsImages()` (`ComposerFooter.tsx:130-140`, from `Settings/modelCatalog.ts:148`) and server `modelSupportsImagesSync()` (`src/lib/overdeck/conversation-message.ts:298`, from `src/lib/model-capabilities.ts:1268`).
- **Kind** — new attachment classification: `'image'` (existing four image MIME types) vs `'file'` (everything else on the allowlist).

## Problem

The composer supports image attachment via two undiscoverable paths (paste, drag-and-drop) with no visible affordance and no support for non-image files. Dropping a `.txt`/`.log`/`.pdf` on the composer is silently ignored at three layers:

1. `handleDrop` filters to `file.type.startsWith('image/')` — `ComposerFooter.tsx:304`.
2. `composerStore.enqueueImages` filters again to `image/*` — `composerStore.ts:288`.
3. Server `ALLOWED_UPLOAD_MIME_TYPES` hard-locks to 4 image MIME types — `src/lib/overdeck/conversation-message.ts:66-71` — returning 400 for anything else.

There is no `<input type="file">` anywhere in the composer.

## Decisions

- **D1 — Extension-driven allowlist.** Browsers report empty or wrong MIME types for many text files (`.log`, `.md`, `.toml`; `.ts` reports `video/mp2t`). Therefore non-image validation keys on the **file extension**, not the client-declared MIME. The client MIME is never trusted for non-image types.
- **D2 — Allowlisted extensions (curated set + PDF):**
  - Text/code (validated as UTF-8, see D3): `.txt .md .markdown .json .jsonl .log .csv .tsv .yaml .yml .toml .xml .html .css .js .jsx .ts .tsx .py .sh .bash .sql .diff .patch .ini .conf .cfg`
  - Binary: `.pdf` (magic-byte validated, see D3)
  - Images unchanged: `image/png .png`, `image/jpeg .jpg`, `image/gif .gif`, `image/webp .webp` (MIME + magic bytes, exactly as today).
- **D3 — Content validation per kind.** Text extensions: bytes must decode as UTF-8 (`new TextDecoder('utf-8', { fatal: true })`) and contain no NUL (0x00) bytes. `.pdf`: bytes must start with `%PDF-` (0x25 0x50 0x44 0x46 0x2D). Images: existing `validateImageMagicBytes` untouched.
- **D4 — Uniform 5 MiB cap** for every type. `MAX_UPLOAD_BYTES` and the route's `Multipart.limitsServices` values are unchanged.
- **D5 — Attachment terminology rename.** `PendingImage`→`PendingAttachment` (+ `kind: 'image' | 'file'` field), `enqueueImages`→`enqueueAttachments`, `removeImage`→`removeAttachment`, `updateImage`→`updateAttachment`, `consumeImages`→`consumeAttachments`, `useConversationImages`→`useConversationAttachments`, `getConversationImages`→`getConversationAttachments`, CSS classes `composerImageStrip`→`composerAttachmentStrip` etc. Scope: `composerStore.ts`, `ComposerFooter.tsx`, their two test files, `command-deck.module.css`. Behavior-preserving for images (no-loss: every existing affordance — queue, preview, remove, retry-on-error, orphan-delete, send-splice — must survive the rename).
- **D6 — Paperclip button** (`lucide-react` `Paperclip`) in the composer toolbar, placed in the right cluster before the voice toggle, using the `styles.voiceToolbarButton` pattern. It clicks a hidden `<input type="file" multiple accept="...">` whose `accept` string is derived from the frontend allowlist. Input value is reset after each selection so re-picking the same file works.
- **D7 — Send-time representation unchanged.** `@<serverPath>` text tokens; **no** `attachments` field on the `ChatMessage` contract (`packages/contracts/src/rpc.ts:145-155`).
- **D8 — Endpoints keep their paths.** `/upload-image` and `/delete-image` are generic multipart/JSON endpoints already; renaming them buys nothing and churns the no-loss route audit. The frontend is their only caller.
- **D9 — Vision gating becomes image-only at both layers.** Frontend: the gate in the `enqueueAttachments` wrapper blocks only `kind: 'image'` files when `!modelSupportsImages(model)` (files still enqueue; the existing warning toast fires for the dropped images). Server (`conversation-message.ts:296-311`): strip only attachment paths whose extension is an image extension; text/PDF paths always pass through. Classification helper: `isImageAttachmentPath(path)` by extension (`.png .jpg .jpeg .gif .webp`).
- **D10 — Harness transform wording generalized.** `transformMessageForHarness` says "attached files" instead of "attached image files".
- **D11 — No silent drops.** Rejected files (disallowed extension) produce a `toast.error` naming each rejected filename, from all three entry points (picker, drop, paste). The store's `enqueueAttachments` returns the rejected `File[]` so callers can toast.
- **D12 — Stored filename keeps a sanitized original basename for non-image files** — `<uuid>-<sanitized-basename><ext>` where the basename is lowercased, restricted to `[a-z0-9._-]`, and capped at 48 chars — so the agent reading `@/…/3f2a…-error.log` retains the semantic filename. Images keep the existing `<uuid><ext>` naming (parity, avoids churn). (autoDecision — defensible default, not operator-confirmed.)
- **D13 — Frontend mirror module.** New `src/dashboard/frontend/src/lib/attachmentTypes.ts` mirrors the server allowlist (extension set, extension→MIME inference, kind classification, `accept` string). Mirroring precedent: `modelSupportsImages` mirrors `modelSupportsImagesSync`. Each side carries a comment naming its mirror.

## Non-goals (must NOT be introduced)

- No structured `attachments` field on `ChatMessage` or any contract change in `packages/contracts/`.
- No renaming or addition of HTTP endpoints (`/upload-image`, `/delete-image` keep their paths).
- No per-type size caps; no change to `MAX_UPLOAD_BYTES` or the multipart route limits.
- No change to paste semantics beyond the mechanical renames: paste remains image-focused (file-manager paste is `text/uri-list` and stays unsupported with the existing toast).
- No support for extension-less files or dotfiles (`.env`, `Makefile`) — `extname()` yields `''` and they are rejected like any disallowed type.
- No binary formats beyond PDF (no docx/xlsx/zip/audio/video).
- No timeline-rendering changes for sent attachments (the `@path` stays plain text in the transcript view).
- No reload durability for pending attachments (tracked separately in #1592).
- No change to the rate limiter, path-containment checks, or attachment cleanup/reaper logic (already type-agnostic).

## Requirements

- **FR-1** — A visible Paperclip button in the composer toolbar opens a native multi-select file picker; selected files enqueue into the same attachment queue used by pasted/dropped images.
- **FR-2** — Dragging any allowlisted file type onto the composer box queues it; disallowed types produce a rejection toast naming the file, never a silent drop.
- **FR-3** — The server accepts allowlisted non-image uploads (extension-driven, UTF-8-validated text, magic-byte-validated PDF) with the uniform 5 MiB cap, reusing the existing rate-limited multipart route; disallowed/oversized/content-mismatched uploads get a clear 400.
- **FR-4** — The attachment preview strip renders a file chip (icon, filename, human-readable size, status, remove button) for `kind: 'file'` attachments and keeps thumbnails for images; remove deletes the server upload exactly as images do today.
- **FR-5** — Sent messages reference uploads via `@<serverPath>` tokens; non-image stored filenames embed a sanitized original basename (D12).
- **FR-6** — Vision gating applies to images only, at both the frontend enqueue gate and the server send-path strip; text/PDF attachments deliver to any model.
- **FR-7** — The Pi/Codex harness transform (`transformMessageForHarness`) uses type-neutral wording for attachment instructions.
- **NFR-1** — All existing image behaviors survive unchanged (magic bytes, upload pump concurrency, orphan-delete on remove-during-flight, consume-on-send, vision warnings). The rename is a no-loss refactor.
- **NFR-2** — Server-side validation gains dedicated unit tests (none exist today).
- **NFR-3** — Docs: `features/conversations.mdx` documents the attachment feature (button, drag-drop, paste, allowed types, size cap); stale image-only module headers updated.
