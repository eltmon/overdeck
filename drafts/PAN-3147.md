# PAN-3147 — Flywheel doctrine: require reading the review verdict for blocked issues

## Glossary

- **Flywheel** — the singleton orchestrator conversation that drives the fix-all pipeline
  in ~20-minute "ticks". Its standing instructions are the prompt file `roles/flywheel.md`.
- **Observe step** — the first step of each flywheel tick in `roles/flywheel.md` (section
  beginning "Each revolution is a tick"), where the orchestrator reads agent panes and
  status snapshots before classifying issues.
- **Liveness metrics** — signals that answer "is the agent working?": cost rising, pane
  output advancing, sibling agents running, fresh-session cost drops.
- **Review verdict / synthesis** — the review role's output at
  `<workspace>/.pan/review/<runId>/synthesis.md` (newest `runId`), containing a
  `## Verdict` line and a `## Blocking Findings` list. Confirmed convention at
  `docs/REVIEW-AGENT-ARCHITECTURE.md:339`.
- **`review_status`** — the per-issue review verdict column (`blocked` / `failed` /
  approved / clean), surfaced in the flywheel's status snapshots as `rev=<state>`.
- **Prompt-Change trailer** — a `Prompt-Change: <explanation>` git-commit trailer
  enforced by `scripts/check-prompt-change-trailer.sh` for any commit touching
  `roles/*.md` or `docs/flywheel-brief.md`.

## Problem

On 2026-07-26 the flywheel orchestrator reported PAN-3093 as "advancing healthily" for
four consecutive ticks on the strength of rising cost and output alone. It never opened
the review. PAN-3093 sat at CHANGES REQUESTED the entire time with five blocking
findings — including a correctness bug where `fetchFeatureBranch()`
(`src/lib/flywheel-merge-order.ts:362`) fetches without a leading `+`, swallows the
non-fast-forward failure, and lets a UAT generation be assembled and promoted from
obsolete feature code. The pointer (`rev=blocked`) was in the orchestrator's own status
snapshots the whole time.

Root cause: the orchestrator's iteratively sharpened *stall test* answers "is the agent
working?" but was used to answer "is the work good?" — different questions with different
evidence. An agent burning tokens on its third rework cycle is indistinguishable, by
liveness metrics, from one making progress. Compounding it: a cost *drop* (a fresh
session started because review blocked it) was explained away as benign instead of
triggering a review read.

## Proposal

Add one doctrine clause to the Observe step of `roles/flywheel.md`, immediately after the
"Then verify agents are ACTUALLY progressing" paragraph (currently at
`roles/flywheel.md:284-287`, anchor text: `same question, or churn).` followed by
`Run skill \`pan-agent-activity\``). The clause is additive — it splits the existing
paragraph and inserts the doctrine text between the anchor sentence and
`Run skill \`pan-agent-activity\``. No other content changes.

The exact text to insert (from the issue body, applied verbatim):

```
**LIVENESS IS NOT CORRECTNESS — for every issue whose `review_status` is `blocked` or
`failed`, READ THE REVIEW VERDICT before you describe it in any report.** Cost and output
metrics answer *"is the agent working?"*; they can NEVER answer *"is the work good?"* An
agent burning tokens on its third rework cycle looks identical to one making progress.
Open `<workspace>/.pan/review/<runId>/synthesis.md` (newest runId) and read the
`## Verdict` line and the `## Blocking Findings` list; count blocking findings across
review cycles to get the trend. Say **"blocked, N findings, converging/not"** — never
"healthy" — for any issue that is not review-clean. A cost DROP on such an issue is a
*fresh session started because review blocked it*, so treat it as a prompt to read the
verdict, not as a benign explanation. (Why: on 2026-07-26 the orchestrator called
PAN-3093 "advancing healthily" for four consecutive ticks on rising spend alone while
it sat at CHANGES REQUESTED with five blocking findings — including a correctness bug
letting a UAT generation promote obsolete feature code. The pointer, `rev=blocked`, was
in its own status snapshots the whole time.)
```

Formatting: match the file's existing 3-space-indented, hard-wrapped paragraph style
(the surrounding lines are indented three spaces and wrapped at ~100 columns).
