Multi-agent UX for Overdeck

Interactive UX mockup for PAN-2565 — a conversation with N member sessions (the "room"), plus the "ask the room" council flow: one question fanned out to five agents, rolled up by a synthesizer. Companion to the architecture flow mockup.

The point of this page: everything you see here runs on the broker from the architecture mockup — no new machinery per feature. A "room" is a read model over a2a_messages; a "council" is five expect-reply threads plus one synthesis send. The UX is the product; the plumbing is already designed.
What you're looking at: one conversation with six member sessions — not a new surface. It lives in the project's CONVERSATIONS list in the Command Deck, at /conv/1042, like every other conversation; the "6 members" chip is the only list-level difference. The operator asked a design question; five agents answered on their own threads and are now discussing the disagreements with each other. The Room tab (default when a conversation has >1 member) merges everything the broker sees into one timeline; member tabs drill into each session's own transcript (where A2A mail lands as [overdeck inbox] user turns). Presence dots come from existing run-state signals.

The council flow: one question, fanned out. The operator picks members and hits Ask the room — the broker opens one expect-reply thread per member, answers stream back as they land, and when the last thread closes (or you click Synthesize now) a synthesizer member gets the question plus every reply and rolls up consensus, disagreements, and a recommendation.       How each UX element maps to the broker (nothing here is new machinery):
      
    
        
  • Room timeline — a read model: union of a2a_messages rows for the task plus each member's public turns, ordered by time. The broker already sees every message; the room is a query, not a transport.
    • 
        
  • Member tabs — the existing ConversationPanel, reused per member session (PRD WI-5). A2A mail renders as [overdeck inbox] user turns because that's literally what was injected into the transcript — the JSONL stays the single source of truth (NFR-2).
    • 
        
  • Presence dots — existing run-state events; awaiting-input reuses the AUQ / needs-you detection (FR-8).
    • 
        
  • Council fan-out — N sends with expectReply: true; the broker mints N thread ids. No "council" concept exists in the broker — the pattern lives in the composer.
    • 
        
  • Synthesis — one more member session whose kickoff brief is the question + the N reply bodies (read from a2a_messages, not scraped from panes). Its answer is an ordinary send back to the operator's room.
    • 
        
  • Liveness notices in-room — a stalled answerer doesn't silently hang the council: the sender (here the room itself) surfaces the broker's typed notice, and "Synthesize now" lets the operator proceed with whoever answered.
    • 
        
  • Standards alignment — thread states open|closed|stalled deliberately mirror A2A's task states (submitted|working|input-required|completed), and pan msg list rows mirror Agent Card capability fields. If an A2A facade ever ships, the mapping is mechanical.
