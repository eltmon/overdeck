# PAN-2702 — Deacon-owned strike merge handoff

## Glossary

- **Strike agent:** The persistent `strike-<issue>` session working in `workspaces/feature-<issue>-strike` on `strike/<issue>`. It may push only its strike branch.
- **Strike-ready marker:** Durable pipeline state identifying the exact pushed remote strike HEAD that is eligible for landing.
- **Merge door:** `triggerMerge()` in `src/dashboard/server/routes/workspaces/merge-ops.ts`, which serializes merge work, rebases, verifies, merges through the forge adapter, and calls `postMergeLifecycle()`.
- **Deacon patrol:** The always-running Cloister loop in `src/lib/cloister/deacon.ts`.
- **Recovery cycle:** One failed landing attempt followed by feedback to the warm strike session and a fresh pushed HEAD/readiness signal.
- **Needs-you:** A durable operator-attention state used only when recovery is impossible or its bounded budget is exhausted.

## Problem

`src/cli/commands/strike.ts` and `roles/strike.md` currently end a successful strike with:

```text
pan tell flywheel-orchestrator "strike <id>: fix ready on strike/<id>, gates green — review and land"
```

That message is ephemeral and has only one optional consumer. The strike cannot push `main` because `scripts/guard-agent-main-push.sh` correctly blocks agent identities, so a stopped Flywheel leaves a verified emergency branch unmerged.

## Requirements

- **FR-1:** A strike agent must persist the exact pushed `origin/strike/<issue>` HEAD as ready without messaging Flywheel.
- **FR-2:** Strike landing must reuse the canonical server merge door, persistent merge queue, post-rebase quality gates, forge adapter, and `postMergeLifecycle()`.
- **FR-3:** The strike lane must resolve `workspaces/feature-<issue>-strike`, `strike/<issue>`, and `strike-<issue>` explicitly; it must not derive or address the normal feature lane.
- **FR-4:** Deacon must claim a ready strike and start landing it within one patrol interval when Flywheel is absent.
- **FR-5:** An agent-actionable landing failure must be delivered to the warm strike session with the current main SHA and concrete conflict/gate evidence.
- **FR-6:** Recovery must allow three cycles, require a fresh remote strike HEAD before another landing attempt, and never spend budget twice on the same HEAD.
- **FR-7:** Needs-you must occur immediately for non-agent-actionable failures, failed recovery delivery, or after three failed cycles, and must include ordered attempt history.
- **NFR-1:** Normal review/test/UAT merge eligibility and forge history semantics must remain unchanged.
- **NFR-2:** Strike readiness and recovery state must survive SQLite cache rebuilds through the canonical issue record.
- **NFR-3:** `agent-*` and `strike-*` processes must remain unable to push `main`; the guard is untouched or strengthened.
- **NFR-4:** Concurrent Deacon/Flywheel observation must not start duplicate merges or duplicate post-merge lifecycle work.

## Chosen design

Add `pan strike-ready <issueId>`. It verifies that the caller is in the registered strike worktree on `strike/<issue>`, fetches the remote branch, requires local committed HEAD to equal the pushed remote HEAD, and writes readiness through `setReviewStatusSync()`. Do not parse human messages and do not overload `pan done --strike`, whose existing meaning is post-merge completion.

Extend the durable review/issue pipeline model with the signaled HEAD, ready timestamp, landing state (`ready`, `landing`, `recovering`, `landed`, `needs_you`), recovery count, and attempt history. Cover the SQLite schema/sync mapping and `PanIssuePipelineRecord` projection so the record is the durable source and the DB remains a rebuildable cache.

Refactor `triggerMerge(issueId)` to accept an optional discriminated strike request. The default call retains every existing gate. The strike request is allowed only for a matching durable ready marker and remote HEAD, but then reuses the existing queue, verification, forge merge, and lifecycle. Preserve the existing `method: 'squash'` forge request; “revertible merge commit” means the merge door produces a revertible main commit, not that this issue changes repository-wide merge policy.

Add a focused Deacon strike patrol. It atomically changes the matching HEAD from `ready` to `landing` before external work and invokes the strike merge door. The landing state plus the existing persistent merge queue and `_serverManagedMerges` guard make concurrent observers idempotent.

On actionable failure, append attempt evidence and deliver a recovery request to `strike-<issue>` using async/resurrection-first messaging without overriding operator pauses. The strike fetches/rebases current main, resolves, reruns configured gates, pushes only its strike branch, and calls `pan strike-ready` again. No retry occurs until a new remote HEAD arrives.

## Before/after anchors

### Strike completion prompt

Before, in `buildStrikePrompt()` and `roles/strike.md`:

```text
pan tell flywheel-orchestrator "strike ${plan.issueId}: fix ready on ${plan.branch}, gates green — review and land"
```

After:

```text
pan strike-ready ${plan.issueId}
```

### Merge branch resolution

Before, `triggerMerge()` derives every `feature-*` directory as a feature branch:

```ts
const branchName = workspaceDirName.startsWith('feature-')
  ? `feature/${workspaceDirName.slice('feature-'.length)}`
  : `feature/${issueLower}`;
```

After, the default keeps this behavior and a validated strike request supplies:

```ts
{ workspacePath, branchName: `strike/${issueLower}`, agentId: `strike-${issueLower}` }
```

The implementation may choose the exact discriminated type name, but it must not infer a strike lane from an arbitrary suffix without validating the durable marker.

## Verification rules

- Retry, cooldown, patrol cadence, and polling tests must use `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()` or `vi.runAllTimersAsync()`; do not use real delays or lower worker concurrency.
- Dashboard-reachable delivery and child-process work must remain async; do not introduce `execSync` or sync tmux calls.
- Run focused Vitest suites for each item, then `npm run typecheck` and `npm run lint`.
- Because merge routing is dashboard boot-path code, run `npm run build:dashboard:server` and boot a throwaway Node 22 `dist/dashboard/server.js` instance with isolated state. Verify health without restarting the live server.

## Acceptance criteria

1. A matching pushed strike HEAD produces durable `ready` state, while wrong workspace/branch, dirty/unpushed work, or mismatched HEAD rejects without mutation.
2. A valid marker runs through post-rebase gates, forge merge, and `postMergeLifecycle()` with `strike/<issue>`; no agent pushes main.
3. With Flywheel absent, the next patrol claims the strike and starts landing; concurrent observation produces only one merge/lifecycle execution.
4. A main-movement conflict produces `recovering`, sends current main SHA/conflict files to `strike-<issue>`, and lands after a fresh resolved HEAD without operator involvement.
5. Re-signaling the same HEAD does not consume budget or rerun work; three failed fresh-HEAD cycles produce one needs-you containing every attempt.
6. The no-loss audit proves every normal `triggerMerge()` command, gate, queue outcome, and lifecycle affordance still has the same behavior.
7. Documentation and CLI help describe `pan strike-ready`, Deacon ownership, three recovery cycles, and terminal needs-you escalation.

## Non-goals

- Changing the normal pipeline lane or its human/UAT consent.
- Exempting agents from the main-push guard.
- Adding a second merge implementation or direct local-main push.
- Requiring Flywheel or an operator conversation to remain alive.
- Changing global forge merge/history policy.
- Restarting the live dashboard during implementation.
