# PAN-3183 — Boot-path writer batch-stops agents directly in the agents table, bypassing the event door

**Issue:** https://github.com/eltmon/overdeck/issues/3183
**Mode:** `pan plan --auto` (no operator Q&A; defaults recorded in xBRIEF `autoDecisions[]`)

## Glossary

- **agents table** — the `agents` table in the runtime-plane SQLite DB `~/.overdeck/overdeck.db`. The authoritative runtime registry of agents (docs/AGENT-STATE-PLANES.md, plane 2).
- **event door** — the rule that every agent lifecycle status change must be persisted as a domain event (`agent.stopped`, `agent.status_changed`, …) in the event store, in the same transaction as the agents-row write, so event-sourced projections can never diverge from the table. Implemented today by `saveAgentStateAndEmitEvent()` in `src/dashboard/server/services/agent-projection.ts` ("write-through projection", PAN-1908) and by `AgentWriterService` verbs in `src/lib/overdeck/agents.ts` which `bus.emit` after each DB write.
- **backfill / boot reconcile** — `backfillAgentsSync()` (`src/lib/overdeck/agents.ts:881`) and its legacy twin `backfillAgentsFromStateJsonSync()` (`src/lib/database/agent-backfill.ts:178`). Both enumerate `~/.overdeck/agents/*/state.json`, and inside a single SQLite transaction `INSERT OR REPLACE` every row, flipping `running`/`starting` agents to `stopped` when no live tmux session matches.
- **read model** — the dashboard server's in-memory projection (`src/dashboard/server/read-model.ts`), bootstrapped from `AgentsResolver.list({})`, plus `AgentStateService`'s event-folded `agentRuntimeById` map (`src/dashboard/server/services/agent-state-service.ts`).
- **write door** — the single sanctioned write surface for a domain's canonical state (single-source-of-truth tenet). For agent lifecycle rows: `agent-projection.ts` and `AgentWriterService`.

## Problem

After the 2026-07-27 02:50Z reboot, 8 ancient agents rendered as RUNNING on the Agents page and in `RunningAgentsPill` with 339–720h runtimes. The agents table correctly said `stopped`/`error`; REST `/api/agents` agreed; the WebSocket-snapshot read model disagreed — a two-door drift.

Verified evidence from the issue:

1. The agents were batch-marked `stopped` at 2026-07-27T02:52:14Z — `stopped_at` values within 3ms of each other (a single transaction), `consecutive_failures=0`, no resume gates.
2. That write emitted **zero domain events** and **zero lifecycle log lines**.
3. It was not the deacon, not the supervisor, not the (surviving) dashboard process, not the memory census. It ran ~16s before the supervisor started.

Because no `agent.stopped`/`agent.status_changed` event ever reached the event log, event-derived projections (server `agentRuntimeById`, frontend replay) keep the pre-reboot `agent.created` + `agent.status_changed → running` events as the last word — the phantom "8 running agents".

## Root cause (code-level)

`backfillAgentsSync()` (`src/lib/overdeck/agents.ts:881-966`) matches the evidence signature exactly:

- One `db.transaction(...)` wrapping `INSERT OR REPLACE INTO agents` per agent (`src/lib/overdeck/agents.ts:907-964`) — produces the ≤3ms `stopped_at` spread (`state.stoppedAt = state.stoppedAt ?? new Date().toISOString()` at `src/lib/overdeck/agents.ts:939`).
- It emits **no domain events** and writes **no lifecycle log lines** — the only status-flip path in the codebase with that property.
- It runs on the dashboard boot path: `reconstructCacheAuto()` (`src/lib/reconstruct/reconstruct-cache.ts:278`, calls `backfillAgentsSync` at line 285) is invoked by the read-model bootstrap (`src/dashboard/server/read-model.ts:546-553`) and by the `AgentStateService` seed (`src/dashboard/server/services/agent-state-service.ts:109-125`).

The 20s-before-dashboard-start timing is consistent with an earlier dashboard instance spawned at login (desktop autostart, user session ~02:51:50Z) that ran the boot reconstruct at 02:52:14Z and then lost the port to the supervisor-managed instance (02:52:34Z). Confirming which process invoked it is a bounded live-forensics step (work item 1); **the fix is identical regardless of which process called the backfill**, because the defect is in the backfill itself.

The legacy twin `backfillAgentsFromStateJsonSync()` (`src/lib/database/agent-backfill.ts:178-257`) has the same no-event defect; its only live caller is the one-time v54→v55 schema migration (`src/lib/database/schema.ts:1611`), so it is a latent rather than active hole.

Secondary defect (projection precedence): `mergeRuntimeBySequence()` (`src/dashboard/server/services/agent-state-service.ts:160-178`) merges the source-reconstructed runtime map with the event-folded current map by sequence number alone — an event-folded `running` entry always beats a source-reconstructed `stopped` entry whenever it carries any sequence. Per docs/AGENT-STATE-PLANES.md the agents table is the authoritative runtime registry, so a table-backed `stopped` with no live tmux session must win.

## Requirements

- **FR-1** — `backfillAgentsSync()` reports every agent it flips to stopped (id + previous status) in its result, so callers can emit the lifecycle events the write skipped.
- **FR-2** — Each backfill-reconciled stop appends a lifecycle log line via `logAgentLifecycleSync`, matching every other stop path (e.g. `markAgentStopped` in `src/lib/agents/agent-state.ts:859`).
- **FR-3** — Both dashboard boot callers of `reconstructCacheAuto()` (read-model bootstrap and AgentStateService seed) emit `agent.status_changed` (`status: 'stopped'`, `hasLiveTmuxSession: false`) through the event store for each id reported by FR-1, durable before boot continues.
- **FR-4** — `mergeRuntimeBySequence()` gives a source-reconstructed `stopped` (no live tmux session) precedence over an event-folded `running`/`starting` entry regardless of sequence number, per "the table wins" in docs/AGENT-STATE-PLANES.md.
- **FR-5** — A CI lint guard (extending `scripts/lint-state-writes.sh`, already wired into `npm run lint`) fails the build on any direct agents-table status mutation (`INSERT OR REPLACE INTO agents`, `UPDATE agents ... status`, `DELETE FROM agents`) outside the allowlisted door modules.
- **FR-6** — `docs/AGENT-STATE-PLANES.md` documents the invariant: boot-path status writes go through the event door too; the lint guard and its allowlist are named.
- **NFR-1** — `backfillAgentsSync` stays synchronous and dependency-free (it runs in CLI processes with no event store); event emission lives in the dashboard-side callers, not inside the backfill.
- **NFR-2** — No behavior change to `pan admin db rebuild-agents` CLI output beyond the added result field.
- **NFR-3** — `backfillAgentsFromStateJsonSync()` (legacy layer) gets the same reporting/logging parity so the latent hole is closed, with no change to its one-time migration caller's behavior.

## NonGoals

- No redesign of the event store, the read model, or the two-door architecture.
- No frontend changes (`RunningAgentsPill`, Agents page read the store correctly once events exist).
- No healing of historical phantom state — the read model is in-memory and corrects on the next dashboard boot once bootstrap precedence and event emission are fixed.
- No changes to deacon stop paths — they already emit through `setAgentStoppedNotifier`/`setAgentStatusChangedNotifier` (`src/lib/cloister/deacon.ts:1553-1580`).
- No change to the one-time v54→v55 schema migration semantics.
- No removal of the legacy `src/lib/database/agent-backfill.ts` module.

## Planning Q&A

Auto mode — no operator questions were asked. Defaults chosen (also in xBRIEF `autoDecisions[]`):

- **Emit from dashboard callers, not inside the backfill.** The backfill runs in CLI processes (`pan admin db rebuild-agents`) where no event store exists; making it emit would either crash CLI usage or silently no-op. The dashboard boot callers own emission; the backfill's job is to *report* what it flipped. Rationale: NFR-1 keeps the sync/dependency-free contract that its header comment already promises.
- **Fix the legacy twin rather than delete it.** Deletion would need its own no-loss audit and migrationCaller verification; parity reporting is a ~15-line change that closes the latent hole without touching the v54→v55 migration path.
- **`agent.status_changed` rather than `agent.stopped` for the boot-reconcile event.** The reducer for `agent.status_changed` already strips pending-input fields on stop (PAN-1591 logic) and carries `previousStatus` + `hasLiveTmuxSession`, which is exactly the boot-reconcile fact pattern; `agent.stopped` payloads (`{id, suspend}`) carry user-stop semantics (`stoppedByUser`) that a boot reconcile must NOT set.
