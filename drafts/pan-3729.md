# PAN-3729 — Restart Gate: operator-approval banner for voluntary dashboard restarts

**Issue:** https://github.com/eltmon/overdeck/issues/3729
**Mode:** operator-directed bypass (direct Opus agents, orchestrated by conversation)
**Split:** Agent A = server gate domain + read model + frontend banner + docs. Agent B = CLI blocking + deploy script client. Disjoint file sets; both build against the pinned wire contract in §4. Agent B MUST NOT touch server, frontend, or docs files; Agent A MUST NOT touch `src/cli/commands/*` or `scripts/post-merge-deploy.sh`.

## 1. Glossary

- **Voluntary restart** — a dashboard restart requested by a deploy script, `pan reload`, or `pan restart`. Only these are gated.
- **Involuntary restart** — crash recovery, watchdog respawn, supervisor restart-on-death. Never gated.
- **Gate** — server-held queue of pending restart requests plus an approval state machine.
- **Requester** — a process that wants a restart: the post-merge deploy script, `pan reload`, or bare `pan restart`.
- **Epoch** — one approval cycle: the snapshot of pending request ids captured when the operator approves. One epoch = at most one restart.
- **Claim** — the exclusive right, granted to exactly one requester per epoch, to actually perform the restart. All other requesters in the epoch are *satisfied* by that restart.
- **Runtime plane** — non-canonical operational state (precedent: `~/.overdeck/dashboard-restarting.json`). The gate file is runtime-plane: it does NOT mirror to git or the state branch.

## 2. Behavior (operator's requirements)

1. A voluntary restart never happens while the operator is mid-work: the requester registers a request and **blocks indefinitely** until the operator approves. No auto-timeout on approval.
2. The dashboard shows a **banner at the top of every view** whenever ≥1 request is pending: requesters + reasons + a single **Restart now** button.
3. **Coalescing:** one approval → one restart → every request pending at approval is satisfied. Requests arriving after approval wait for the next cycle.
4. `pan restart --now` is the explicit operator bypass. The dashboard's own UI restart button is implicit approval.

## 3. State machine (Agent A implements; Agent B consumes)

Request lifecycle: `pending → (approve) approved → (claim) claimed → (new server boots) satisfied`. Expiry: a pending request not refreshed for **20s** expires and leaves the banner (poll = refresh, see §4). A claim not completed within **5 minutes** lapses; the gate returns to `approved` and the next poller may claim (covers a claimant that died after claiming).

Approve when every request has already expired → clear the gate, restart nothing.

Persistence: single JSON file `~/.overdeck/restart-gate.json`, owned by ONE writer module in the dashboard server (one read door / one write door — state it in code comments; this is runtime-plane, not canonical, so no git mirror, but the two-doors structure still applies). On boot the server reads the file: if it holds an epoch in `claimed` state, the boot IS the restart completing — mark that epoch's requester ids **satisfied**, persist, clear pending. Satisfied ids are served to polls for 10 minutes after boot, then pruned.

## 4. Wire contract (PINNED — neither agent may change shapes or paths)

All endpoints on the dashboard server (`:3011`).

**POST `/api/restart-gate/requests`** — upsert + poll + TTL-refresh, all in one. Requesters call this every **5s** while waiting.
Body: `{ "requesterId": string, "kind": "deploy"|"reload"|"restart", "reason": string, "builtSha"?: string }`
`requesterId` is stable for one requester invocation (e.g. `deploy:PAN-3724:<pid>`; `reload:<pid>`; `restart:<pid>`).
Response 200: `{ "status": "pending"|"approved"|"claimed"|"satisfied", "mayClaim": boolean, "pendingCount": number }`
- `satisfied` → this requester's restart already happened; skip your own restart step and exit success.
- `approved` + `mayClaim:true` → you may try to claim.

**POST `/api/restart-gate/claim`** — body `{ "requesterId": string }` → 200 `{ "granted": boolean, "status": ... }`. Atomic: exactly one granted per epoch (unless a claim lapses per §3).

**POST `/api/restart-gate/approve`** — no body → 200 `{ "approved": true, "pendingCount": number }`. Operator-only surface (banner button, `pan restart approve`).

**GET `/api/restart-gate`** — read door → 200 `{ "status": "idle"|"pending"|"approved"|"claimed", "pending": [{ "requesterId", "kind", "reason", "builtSha", "requestedAt" }] }`.

**Compat rule (lets this feature deploy through today's ungated server):** if a gate endpoint returns 404, or the dashboard health endpoint fails continuously for 60s, the requester proceeds **ungated** with its normal restart. A dead dashboard has nothing to interrupt.

## 5. Agent A — server + read model + banner + docs

6. **Supervisor `POST /restart-dashboard` (src/supervisor/server.ts) stays ungated** — it is the mechanism an approved restart uses; gating it would deadlock. Do not modify the supervisor.

6. **Tests:** client unit tests with fake timers — pending→approved→claim-granted flow, claim-denied→satisfied flow, 404-compat fallback, unhealthy-60s fallback. Mock fetch; no real HTTP, no real delays.
