## 1. Glossary

Define-before-use. Every term of art in this document:

- **OKF (Open Knowledge Format)** — Google Cloud's vendor-neutral spec (v0.1 Draft, announced 2026-06-12) for representing knowledge as a directory of Markdown files with YAML frontmatter. Spec: https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md (Apache-2.0).
- **Bundle** — an OKF directory tree, distributable as a git repo or subdirectory. The unit of knowledge.
- **Concept** — one non-reserved `.md` file in a bundle; exactly one idea per file. Its **concept ID** is the file path minus `.md` (e.g. `tables/orders`).
- **Frontmatter** — the YAML block at the top of a concept. OKF requires exactly one field (`type`); recommends `title`, `description`, `resource`, `tags`, `timestamp`. **Extensions clause (§4.1):** "Producers MAY include any additional keys. Consumers SHOULD preserve unknown keys when round-tripping and SHOULD NOT reject documents with unrecognized fields."
- **`tags`** — recommended OKF frontmatter field: a flat YAML list of short strings for cross-cutting categorization. No controlled vocabulary; tag-browsing views are consumer-synthesized.
- **Reserved files** — `index.md` (directory listing for progressive disclosure; no frontmatter except bundle-root `okf_version`) and `log.md` (per-directory change history, `## YYYY-MM-DD` headings, newest first). Never concept documents.
- **Karpathy llm-wiki** — Andrej Karpathy's "LLM Knowledge Bases" pattern (gist 2026-04-04: https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f). Three layers: immutable sources, an LLM-owned wiki of interlinked Markdown, and a prose schema file that "makes the LLM a disciplined wiki maintainer." Three operations: ingest, query, lint. Anti-RAG: synthesis compounds at write time.
- **Knowledge repo** — this skill's default bundle host: a companion git repo named `<project>-knowledge`, created as a **peer directory** of the code repo (e.g. `~/Projects/acme-pay` → `~/Projects/acme-pay-knowledge`), PR-gated, carrying its own CI conformance gate.
- **Pointer file (`.okf.yml`)** — a tiny file in the *code* repo recording where the project's bundle lives. All skill commands resolve the bundle through it.
- **Conformance gate** — deterministic Python validation (`validate.py --strict` + `diff_lint.py`) run locally and as a required CI check on knowledge-repo PRs. Never an LLM.
- **Diff-lint** — the "was-clean-now-broken" check: compares validation between a PR's base and head so pre-existing warnings don't block, but new breakage does.
- **`okf-embeddings`** — the extension standard this PRD defines (v0.1, ours): committed `okf-embeddings.yaml` manifest + committed per-profile vector shards + a gitignored derived SQLite index. See §5.3.
- **Profile** — one named embedding configuration in the manifest (provider + model + dimensions + endpoint). The **default profile is Ollama** so the skill works with no API key.
- **Vector shard** — a committed JSONL file (`embeddings/<profile>.okfe.jsonl`), one line per chunk: concept ID, content hash, vector. Shareable so consumers don't recompute.
- **Content hash** — SHA-256 of a concept's normalized content; staleness is detected per-concept, re-embedding is incremental.
- **BM25** — keyword relevance ranking (SQLite FTS5 built-in). The zero-dependency search floor.
- **RRF (Reciprocal Rank Fusion)** — rank-fusion `score = Σ 1/(K + rank)`, K=60, merging BM25 and vector lists. Already used in three Overdeck subsystems.
- **Observations** — Overdeck's LLM-extracted, append-only JSONL memory records captured from agent transcripts (`~/.overdeck/memory/<project>/<issue>/observations/`), FTS-indexed. **Prompt-time injection is LIVE** at agent spawn (`src/lib/agents/spawn-prep.ts:600`), user-prompt delivery (`src/lib/agents/runtime-command.ts:334`), and the hooks route (`src/dashboard/server/routes/hooks.ts:243`), gated by config `prompt_time_injection`.
- **Ollama** — local model server (localhost:11434) serving embedding models such as `nomic-embed-text` (768-dim). Free, keyless. Not currently installed by Overdeck (`src/lib/ollama.ts` does not exist; PAN-1641 plans the sidecar for the Pi harness).
- **mnemos** — https://github.com/arhuman/mnemos: a cgo-free Go binary that indexes Markdown/OKF bundles into SQLite FTS5 and serves **cited** search (`file#section` + line range) over MCP and CLI (`mnemos init/ingest/search/serve`, `mnemos eval` retrieval metrics). Overdeck will auto-install it on demand (WI-20); the skill leverages it when present.
- **claude-mega-brain** — https://github.com/guhcostan/claude-mega-brain: a Claude Code plugin whose SessionStart hook scans the project for OKF-frontmattered files and injects a compact concept index (benchmarked: 100% accuracy, 0 tool calls, −66% tokens vs Obsidian+MCP). **We replicate this behavior inside Overdeck** (WI-22) rather than installing the plugin, integrating it with the existing Observations injection.
- **kcmd** — Google's "Metadata as Code" CLI/library/MCP server (knowledge-catalog `toolbox/mdcode`): git-style `init/pull/status/push` sync between local YAML/Markdown and the cloud Knowledge Catalog service. Not a dependency; §5.6 states the compatibility posture.
- **Bridge skill / harness bridge** — a skill/plugin that lets one coding agent delegate a task to another vendor's model via that vendor's local CLI. Canonical example: `openai/codex-plugin-cc` (official OpenAI plugin driving the local `codex` CLI with `--model`/`--effort`); simplest pattern: direct shell-out `codex exec -m <model> …`. Gemini equivalents exist (`abiswas97/gemini-plugin-cc`, ACP-based); MCP multi-bridges too (`jarrodwatts/claude-delegator`, `mkXultra/ai-cli-mcp`).
- **Knowledge role** — the new first-class Overdeck agent role added by Track B: a spawnable, model-routable, Command-Deck-visible agent whose job is running the skill's knowledge passes (study/retro/sync).

## 2. Vision & motivation

Every project accumulates knowledge that lives only in heads and transcripts: why an architecture was rejected, how overtime calculations actually work, which invariant a subsystem protects. Agents re-derive this context every session — slowly, expensively, sometimes wrongly.

The skill maintains a **wiki-style OKF bundle per project** — interlinked Markdown concepts, one idea per file — kept current by the same agents that do the development work:

- **Before a feature**: a topic-focused *study* pass documents what exists today (e.g. "overtime calculations") so planning starts from written truth.
- **After a feature**: a *retro* pass asks "what did this session have to rediscover that the wiki should have known?" and files it.
- **At any time**: an *extract* pass pulls the few relevant concepts into a prompt — hybrid semantic + keyword search when embeddings exist, keyword-only otherwise, index-guided reading at the floor.

Correctness is enforced by the bundle itself (CI conformance gate), not by any agent's discipline. Delivery is two tracks in one workspace:

- **Track A — the portable skill.** Works with zero Overdeck: git + gh + Python 3 + PyYAML (+ Ollama or an API key for embeddings). Model requests are honored best-effort via harness bridges, and **error out** when unservable.
- **Track B — Overdeck integration.** A first-class `knowledge` agent role (Command Deck tree, model routing, `pan knowledge <id>`), on-demand mnemos + Ollama installation, mega-brain-style session-start concept injection wired into the live Observations injection path, and post-merge auto-retro.

The strategy in one line: **OKF on disk, Karpathy in behavior, embeddings as a conformant extension, Overdeck as the amplifier.**

## 3. Research grounding (verified 2026-07-07)

- Vector-search convention emerging and it is NOT frontmatter: derived sidecar indexes (hdean-ssp/okf-tools, travisjakel/okf-ingest, OKFgraph, mnemos), hybrid BM25+vector, local models favored. Nobody standardizes embedding *metadata* — `okf-embeddings` fills that gap.

## 4. Requirements

### Functional — Track A (portable skill)

- **FR-1** `/okf init` scaffolds the knowledge bundle. **Default target: a peer directory of the code repo** — for code repo `~/Projects/<name>`, create `~/Projects/<name>-knowledge` (new git repo + `gh repo create`). Overrides: `--dir <path>` (any filesystem location) and `--local <subdir>` (in-repo bundle, no companion repo). Init writes the pointer file `.okf.yml`, seeds `index.md`/`log.md` + starter concepts (Overview + first Decision), installs the CI conformance gate, writes the default `okf-embeddings.yaml` (Ollama profile), and adds one discovery line to the code repo's `CLAUDE.md`/`AGENTS.md`.
- **FR-2** `/okf author "<topic>"` writes/updates one concept: infer-and-confirm `type`, frontmatter handled by the skill, relative cross-links, index/log regeneration, local validation.
- **FR-3** `/okf convert <path>` onboards existing docs non-destructively: dry-run plan, frontmatter-first edits, confirmed renames, never deletes a README.
- **FR-4** `/okf sync [--topic "<focus>"]` maps code changes since the last log entry (or PR base) to concepts, updates them, appends `log.md`, regenerates `index.md`, validates, opens a PR. `--topic` restricts the pass (tag match + search).
- **FR-5** `/okf study "<focus>"` researches the **current codebase** for a topic (e.g. "overtime calculations") and creates/refreshes the concepts describing today's behavior, via PR.
- **FR-6** `/okf retro` reviews the change (diff + available session context) and answers: *what would have made this work easier if documented?* Files answers as concepts via PR. With Overdeck: mines the issue's Observations (`pan memory search --issue`); without: `git diff` + current transcript.
- **FR-7** `/okf extract "<query>" [--budget <tokens>]` returns ranked, token-budgeted, **cited** concepts for prompt inclusion. Ranking tiers: hybrid RRF → BM25-only → index-guided reading. When `mnemos` is on PATH with the bundle ingested, extract MAY use `mnemos search` as the retrieval backend (its citations map to concept IDs); the skill's own `search.py` remains the guaranteed path.
- **FR-8** `/okf validate [--strict]` runs the deterministic gate locally — identical code to CI. Exit 0/1/2.
- **FR-9** `/okf lint` — advisory LLM semantic patrol (contradictions, staleness, orphans, oversized concepts). Never the merge gate.
- **FR-10** `/okf embed [--profile <name>]` — hash-gated incremental embedding per the manifest; updates the shard; rebuilds the local index.
- **FR-11** `okf-embeddings` v0.1 (§5.3) implemented exactly as specified. **The default profile init writes is `ollama`/`nomic-embed-text`** — keyless out of the box; `openai`/`voyage`/`custom` are opt-in profile additions.
- **FR-12** All bundle writes PR-gated by default; CI gate installed by init as a required check.
- **FR-13** Every command works with zero Overdeck (git, gh, Python 3 + PyYAML; embeddings need Ollama or a key).
- **FR-14** Overdeck detection lights up Track B behaviors; core never *imports* Overdeck.
- **FR-15** Reading rules in SKILL.md: read `index.md` first, load only relevant concepts, answer only from loaded concepts, cite concept IDs, never invent.
- **FR-16** **Model selection (`--model <model>`)** on `study`, `retro`, `sync`, and `author`: the pass runs on the requested model, best-effort. Resolution ladder (§5.4): native harness support → underlying vendor CLI on PATH (`codex exec -m`, `gemini -p -m`) → installed bridge plugin commands → MCP bridge tools → **hard ERROR** naming the model, the bridge that would serve it, its install command, and the auth step. The skill never silently substitutes a different model.

### Functional — Track B (Overdeck integration)

- **FR-17** A first-class **`knowledge` role**: in the `Role` union, model-routable via `roles.knowledge.model` (default mirrors the `plan` role's ref; unset+unresolvable must error loudly per repo rule), spawnable via `pan knowledge <id> [--focus "<topic>"] [--retro] [--model <m>]`, running as a live TUI tmux session (never one-shot), discovered and nested under its issue in the Command Deck tree with a role label. It opens PRs against the *knowledge* repo only; it never enters the code-repo review/merge pipeline, never runs `pan done`, and skips the beads gate (plan-style).
- **FR-18** **mnemos auto-install**: Overdeck installs mnemos on demand (release binary download, like other on-demand installations) the first time a knowledge feature needs it; the skill uses it when present (FR-7).
- **FR-19** **Ollama on-demand**: when an embedding operation needs the default Ollama profile and no server answers on localhost:11434, Overdeck offers/performs on-demand install + `nomic-embed-text` pull + health check. Shares substrate with PAN-1641 (Pi-harness sidecar) — one `src/lib/ollama.ts`, two consumers.
- **FR-20** **Session-start knowledge injection (mega-brain replicated)**: at agent spawn and session start, Overdeck injects a compact concept index (ID + type + one-line description, recent log entries) for the project's bundle — implemented inside the existing prompt-time injection path (`injectPromptTimeMemory` surfaces `spawn`/`user-prompt`), budgeted alongside observation context, gated by config. Reconcile PAN-1115 (close or re-scope to the doc-retrieval remainder; PAN-1117 stays separate).
- **FR-21** **Post-merge auto-retro**: `postMergeLifecycle` gains an opt-in hook that spawns `pan knowledge <id> --retro` after an issue merges, so the wiki learns from every shipped feature. Idempotent; must keep `tests/unit/lib/cloister/in-flight-guard.test.ts` green.

### Non-functional

- **NFR-1** Conformance verdicts deterministic — no LLM in the gate.
- **NFR-2** Graceful degradation for *retrieval* (hybrid → BM25 → guided reading). **Model requests are the exception: unservable `--model` is a hard error (FR-16), not a degradation.**
- **NFR-3** Bundles remain conformant OKF v0.1 for vanilla consumers; also readable by kcmd-style consumers (no reliance on non-spec directory semantics; extension keys tolerated per §4.1).
- **NFR-4** Vector shards incremental: unchanged concept never re-embedded.
- **NFR-5** Local index rebuildable from Markdown + shards (`--rebuild`), and from Markdown alone (re-embed).
- **NFR-6** embed/search scripts run under plain CPython (stdlib + PyYAML; `sqlite-vec` optional with BLOB-cosine fallback).
- **NFR-7** Track B additions follow the two-door rule (reads via resolvers, writes via the writer), `sendKeysAsync` only, no `execSync` in server-reachable code.

### 5.3 The `okf-embeddings` extension standard, v0.1

Markdown is the source of truth; vectors are derived — but derived data that costs money/time is worth sharing:

| Artifact | Location | Committed? | Why |
| --- | --- | --- | --- |
| **Manifest** | `okf-embeddings.yaml` (bundle root) | yes | Human-readable contract: profiles, chunking, hash rules. PR-reviewable. |
| **Vector shards** | `embeddings/<profile>.okfe.jsonl` | yes when profile `share: true` (default profile defaults to true) | Consumers reuse instead of recompute. Line-per-concept → clean diffs; content hashes make stale lines safe (re-embed only those). |
| **Local index** | `.okf-index/` (SQLite: FTS5 + sqlite-vec or BLOB) | no (gitignored by init) | Binary machine-local cache, rebuilt in seconds. The only gitignored piece. |

**Manifest (init default — keyless):**

```yaml
# okf-embeddings.yaml — okf-embeddings extension, v0.1
okf_embeddings_version: "0.1"
default_profile: local

profiles:
  local:
    provider: ollama                 # openai | voyage | ollama | custom
    model: nomic-embed-text
    dim: 768
    endpoint: http://localhost:11434 # ollama is localhost-only; custom REQUIRES an
                                     #   OpenAI-compatible /v1/embeddings endpoint
    share: true                      # commit this profile's shard
  # cloud:                           # opt-in example
  #   provider: openai
  #   model: text-embedding-3-small
  #   dim: 1536
  #   share: false

chunking:
  strategy: concept                  # v0.1: whole-concept only ("section" reserved for v0.2)
  max_tokens: 512                    # longer concepts truncated for embedding; lint flags as split candidates

hash: sha256                         # over normalized content: frontmatter minus timestamp, plus body,
                                     #   LF-normalized, trailing whitespace stripped
vectors_dir: embeddings
```

**Shard format** — `embeddings/<profile>.okfe.jsonl`, one line per chunk:

```json
{"id":"tables/orders#0","concept":"tables/orders","hash":"sha256:9f2c…","dim":768,"v":[0.0123,-0.0456,…]}
```

Rules: lines sorted by `id` (stable diffs); vectors L2-normalized, 6-decimal precision (cosine = dot product); readers MUST ignore hash-mismatched lines and SHOULD re-embed them; writers replace lines in place. Size: ~6–19 KB/concept/profile → 500 concepts ≈ 3–10 MB per shared profile.

**Frontmatter footprint:** exactly one optional key, `x_embed: exclude`. **No vectors in frontmatter, ever.** The `x_` prefix avoids collision with future blessed fields.

**Provider contract:** `embed(texts: list[str]) -> list[list[float]]`, batched, L2-normalized. Built-ins: `ollama` (default, localhost-only), `openai`, `voyage`, `custom` (OpenAI-compatible endpoint + env-var key). New provider = one adapter in `embed.py`.

**Succession:** if the ecosystem/spec standardizes embedding metadata, migrate and mark with `okf_embeddings_version` (D-4: we also *propose* this upstream after it proves out).

### 5.4 Model selection & harness bridges (FR-16)

`--model` resolution ladder, executed by SKILL.md instructions (documented in `references/model-bridges.md`):

1. **Native**: the current harness serves the model directly (e.g. Claude Code + `claude-*`) → proceed.
2. **Vendor CLI on PATH**: `command -v codex` → `codex exec -m <model> --sandbox workspace-write --output-last-message <f> "<pass prompt>"`; `command -v gemini` → `gemini -p "<pass prompt>" -m <model>`. Verify auth first (`codex login status` / ADC or `GOOGLE_API_KEY`).
3. **Bridge plugin**: official plugin commands present (e.g. `/codex:rescue` from `openai/codex-plugin-cc`, `/gemini:task`) → delegate through them with the model flag.
4. **MCP bridge**: `mcp__codex__*` / `mcp__gemini__*` / ai-cli-mcp `doctor` tools available → route through them.
5. **ERROR** (hard stop, per ecosystem convention and operator decision): message names (a) the requested model, (b) the bridge that would serve it, (c) the install command (e.g. `/plugin marketplace add openai/codex-plugin-cc` + `npm i -g @openai/codex`), (d) the auth step (`codex login`). Never substitute a different vendor's model silently.

Under Overdeck (Track B), `pan knowledge <id> --model <m>` bypasses this ladder entirely — Overdeck's own model routing and harness selection (provider-default routing; never force `--harness` for CLIProxy-routed models) spawns the right agent natively.

### 5.6 kcmd compatibility posture

No dependency, no sync. Compatibility means: bundles are pure conformant OKF (NFR-3), extension keys are round-trip-preservable (kcmd's own requirement for unknown keys), and nothing in our layout collides with kcmd's `catalog/` conventions. A team that wants their bundle in Google's Knowledge Catalog points kcmd at it; we change nothing.
