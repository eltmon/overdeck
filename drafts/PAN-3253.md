# PAN-3253 — Bound `review.status_changed` payloads at every door (residual hardening)

**Issue:** https://github.com/eltmon/overdeck/issues/3253
**Status of prior work:** The primary fix landed on main in `4b9b740129` (2026-07-28, operator-directed): `REVIEW_STATUS_HISTORY_LIMIT = 20` enforced at DB hydration (single + bulk) and on status writes, plus a boot-time trim of oversized historical payloads followed by `VACUUM`. It deployed and ran: the DB dropped from 1.30 GB to 362 MB and the historical MIN-90x giants are gone. **This plan covers only the measured residual gaps.**

## Glossary

- **Review status object** — the per-issue pipeline state (`ReviewStatus` in `src/lib/review-status-reconcile.ts`), including a `history: StatusHistoryEntry[]` timeline of status transitions.
- **`status_history` table** — SQLite table in `~/.overdeck/overdeck.db` holding the *full, uncapped* transition record per issue. Deliberately unbounded (forensics). Nothing in this plan changes what is written to it.
- **Hydration** — reading DB rows into an in-memory `ReviewStatus`; since `4b9b740129` hydration slices history to the newest `REVIEW_STATUS_HISTORY_LIMIT` (20) entries.
- **Event store / append door** — `createEventStore()` in `src/dashboard/server/event-store.ts`; its `append()` (line ~346) and `appendOnce()` (line ~449) persist domain events into the `events` table verbatim.
- **Boot trim** — `trimReviewStatusHistoryPayloads()` (`src/dashboard/server/event-store.ts:176`), run at boot: rewrites `review.status_changed` payloads longer than `OVERSIZED_REVIEW_PAYLOAD_CHARS` (16 KB) whose history exceeds 20 entries, keeping the newest tail; triggers `VACUUM` when the trim frees > 64 MB, `PRAGMA incremental_vacuum` otherwise.
- **Stale-build emitter** — any process (short-lived `pan` CLI, agent-side status writers, a not-yet-restarted daemon) running a dist built before `4b9b740129`. Its old `getHistoryFromDb` has no `LIMIT`, so it hydrates the full `status_history` table and emits/persists uncapped history.

## Measured residual problem (2026-07-29, live `~/.overdeck/overdeck.db`, read-only)

After the deploy and migration:

- `review.status_changed` is **still the largest single account**: 110.6 MB across 19,596 rows vs `cost_events` at 72.3 MB — the issue's third acceptance criterion ("no longer the largest object in dbstat") is not yet met.
- **The 20-entry cap is not holding on live emissions.** 191 of the newest 500 payloads exceed 20 history entries (max 259; newest over-cap at 2026-07-29T05:38Z, hours after the deploy). Proof of mechanism: the largest fresh payload (seq 935098, PAN-3260, 25 entries) matches PAN-3260's `status_history` row count *exactly* (25) — a full-table hydration by a stale-build emitter. New code caps its own reads, but the append door persists whatever it is handed.
- **Per-entry `notes` are unbounded.** In seq 935098, one 3,697-char `testNotes` string is embedded 8× across history entries; across the newest 200 payloads (2.05 MB total), history is 1.47 MB and notes-inside-history are 0.82 MB. The payload bound is "independent of transition count" but its constant is dominated by note size.

## Decisions (made here, not left to the executor)

- **D1 — keep the bounded-full-status event shape.** The issue's "proposed fix #1" (emit only a delta and let consumers hit the resolver) is rejected for this issue: it changes the event contract consumed by the shared reducers in `@overdeck/contracts` and every replay consumer. The landed, operator-chosen approach (full status with bounded history) stays. NonGoal.
- **D2 — enforce the bound at the append door.** `append()` and `appendOnce()` must bound `review.status_changed` payloads before persisting, so no emitter — current or stale-build — can reinsert unbounded blobs. This turns the one-shot migration into a standing invariant.
- **D3 — cap history-entry notes at 500 characters** (`REVIEW_STATUS_NOTE_LIMIT = 500`, truncated with a trailing `…`). Applied where history entries are *composed*: the push sites in `updateReviewStatus` and the hydration row-mapping in `review-status-db.ts`. Full notes remain untouched in the status object's own `reviewNotes`/`testNotes`/… fields and in the `status_history` table. Worst-case payload becomes ≈ 20 × ~0.7 KB + a few KB of scalar fields — under the existing 16 KB oversized threshold.
- **D4 — constants live in `src/lib/review-status-reconcile.ts`** next to `REVIEW_STATUS_HISTORY_LIMIT` (line 30), and `event-store.ts` imports them, retiring its duplicated local `REVIEW_HISTORY_TRIM_LIMIT = 20` (line 166). **Implementation checkpoint:** the dashboard server rejects circular ESM imports under Node strict ESM (see CLAUDE.md "Dashboard Server: Node 22 Only"). If `npm run build` reports a cycle after adding this import, fall back to moving *both* constants into a new leaf module `src/lib/review-status-limits.ts` (no imports of its own) and import it from both `review-status-reconcile.ts` (re-export to preserve the existing import surface) and `event-store.ts`.
- **D5 — boot trim gate stays at 16 KB.** With notes capped, any payload above 16 KB is by definition over-cap; rows under 16 KB that still carry slightly-fat history are bounded and age out under the existing 7-day retention. No threshold change.

## Requirements

- **FR-1:** Every `review.status_changed` payload persisted through `append()` or `appendOnce()` carries at most `REVIEW_STATUS_HISTORY_LIMIT` history entries and note strings of at most `REVIEW_STATUS_NOTE_LIMIT` chars, regardless of what the caller passed. Non-`review.status_changed` events and unparseable payloads are persisted byte-identically.
- **FR-2:** History entries composed by `updateReviewStatus` (push sites, `src/lib/review-status.ts:252-268`) and by hydration (`getHistoryFromDb` and both bulk paths in `src/lib/database/review-status-db.ts`) carry notes truncated to `REVIEW_STATUS_NOTE_LIMIT`.
- **FR-3:** `trimReviewStatusHistoryPayloads` also truncates over-limit entry notes when rewriting an oversized payload, and remains idempotent (a second run over trimmed rows rewrites nothing).
- **FR-4:** `docs/AGENT-STATE-PLANES.md` documents the bounded review-status history invariant: the two limits and their values, the four enforcement points (write, hydration, append door, boot trim + VACUUM), and the fact that the `status_history` table intentionally keeps the full record.
- **NFR-1:** No change to what is written into the `status_history` table (full forensic record preserved).
- **NFR-2:** No sync additions to server-reachable code; no `execSync`; changes stay on the existing prepared-statement paths.

**Files:** `src/lib/review-status-reconcile.ts`, `src/lib/review-status.ts`, `src/lib/database/review-status-db.ts`, `tests/unit/lib/database/review-status-history-cap.test.ts`

1. In `src/lib/review-status-reconcile.ts`, next to `export const REVIEW_STATUS_HISTORY_LIMIT = 20;` (line 30), add:
   ```ts
   /** PAN-3253: per-entry note bound inside the bounded history tail. Full notes
    *  stay in the status object's own fields and in the status_history table. */
   export const REVIEW_STATUS_NOTE_LIMIT = 500;
   export function truncateHistoryNote(notes: string | undefined): string | undefined {
     if (notes === undefined || notes.length <= REVIEW_STATUS_NOTE_LIMIT) return notes;
     return notes.slice(0, REVIEW_STATUS_NOTE_LIMIT - 1) + '…';
   }
   ```

## Acceptance criteria (map 1:1 to work items)

- **AC-W1:** Hydration and status updates produce history entries whose `notes` never exceed 500 chars (tests in `review-status-history-cap.test.ts` assert truncation with `…` and full-note preservation on the status's own fields).
- **AC-W2:** The event store persists a bounded payload for `review.status_changed` regardless of input size (test: 259-entry input → 20 entries stored), and persists other event types byte-identically.
- **AC-W3:** The boot trim rewrites oversized rows to the bounded form and converges (second run trims 0 rows).
- **AC-W4:** `docs/AGENT-STATE-PLANES.md` names both limits, all four enforcement points, and the full-record `status_history` exception.
