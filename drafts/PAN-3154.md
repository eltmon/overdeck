# PRD: PAN-3154 — Notify agents when a merge to main invalidates their branch

## Glossary

- **Conflict gate** — the machinery in `src/lib/cloister/conflict-gate.ts` that
  non-destructively probes whether a feature branch merges cleanly into
  `origin/main` (`git merge-tree --write-tree`), keeps `merge_conflict` /
  `not_mergeable` blocker reasons fresh, and dispatches conflict-resolver
  prompts. Today it runs on review dispatch and on a deacon patrol for issues
  *already carrying* a merge blocker.
- **Merge blocker** — a `BlockerReason` of type `merge_conflict` or
  `not_mergeable` on a `ReviewStatus` record. Presence of any blocker forces
  `readyForMerge = false` on every `setReviewStatusSync` write
  (`src/lib/review-status.ts:265-289`).
- **Review status** — the per-issue runtime record (`ReviewStatus`,
  `src/lib/review-status-reconcile.ts:22-70`), persisted in the SQLite
  `review_status` table and mirrored to the durable per-issue record
  (`records/<issue>.json` on `overdeck-state`). Read door:
  `getReviewStatusSync` / `loadReviewStatuses`; write door:
  `setReviewStatusSync` (both `src/lib/review-status.ts`).
- **Deacon patrol** — the 60-second server tick `runPatrol()` in
  `src/lib/cloister/deacon.ts:2686`. Reconciler functions (e.g.
  `reconcileStaleMergeBlockers`, `src/lib/cloister/deacon-merge.ts:430`) hook
  into it and return action strings.
- **In-pipeline issue** — an issue with a `review_status` row whose
  `mergeStatus !== 'merged'`. This is the same population
  `reconcileStaleMergeBlockers` iterates.
- **`conflictsSince`** — the NEW review-status field this PRD adds:
  `{ sha: string; detectedAt: string; paths: string[] }` recording the
  `origin/main` head SHA that first made the branch conflict, when that was
  detected, and which paths conflict.
- **Main-head watcher** — the NEW per-project check this PRD adds: remember
  the last-seen `refs/heads/main` SHA; when it changes, fan out a conflict
  probe to every in-pipeline issue of that project.

## Problem

When a merge lands on `main`, every open branch that touches the same files
can silently stop applying. On 2026-07-26 at 18:58, merge `6ac4a3dc11`
(PAN-3116) deleted `scripts/file-size-baseline.txt` and instantly invalidated
three live branches (`strike/pan-3150`, `feature/pan-3111`,
`feature/pan-3138`). Twelve minutes later none had rebased — their agents were
alive and healthy-looking; nothing had told them `main` moved underneath them.

Today conflicts are discovered only at the merge gate (too late — the conflict
has grown) or via GitHub webhooks (lazy, PR-only, and never delivered to the
agent). One merge can silently create N stalled branches, each discovered only
when someone happens to look.

## Proposal

Add a **branch-invalidation sweep** to the deacon patrol:

1. **Watch main heads.** Per project, poll `git ls-remote origin
   refs/heads/main` on a short cooldown (120s), persisting the last-seen SHA
   in `app_settings` (`branch_invalidation.main_head.<projectKey>`).
2. **On change, probe every in-pipeline branch.** Reuse the existing
   merge-tree probe, extended to return the conflicting paths. Enumerate
   in-pipeline issues from `loadReviewStatuses()`, resolve each issue's
   workspace (agent workspace column first, then
   `workspaces/feature-<issue>*` prefix scan so `-strike` / `-slot-N`
   variants are covered), fetch `origin main` in the workspace, and run
   `git merge-tree --write-tree --name-only HEAD origin/main`.
3. **Mark newly-conflicting branches.** Write `conflictsSince` plus a
   `merge_conflict` blocker reason (replacing any prior merge blocker, the
   same replace pattern as `src/lib/webhook-handlers.ts:482-498`) through
   `setReviewStatusSync`. The blocker flips `readyForMerge` false and lights
   up the *existing* conflict-gate machinery (review-dispatch gate, resolver
   dispatch, dashboard `stuckReason`) with no further work.
4. **Notify the owning agent.** Resolve the live agent with
   `resolveIssueFeedbackTarget` (precedent:
   `src/lib/cloister/verification-runner.ts:218-224`) and deliver a message
   naming the causing commit and the conflicting paths, with rebase guidance.
   Dedup per SHA: if `conflictsSince.sha` already equals the current main
   head, do not re-notify. No live agent → skip the message (the blocker +
   existing resolver machinery covers stopped agents).
5. **Report to the orchestrator.** Emit one summary activity entry per sweep
   ("main `6ac4a3dc1` invalidated 3 branches: …") plus a per-issue warn entry,
   so the flywheel/operator sees the fallout of a merge in the activity feed.
6. **Clear on recovery.** When the conflict gate's probe goes clean again
   (existing clean path in `resolveConflictGate`,
   `src/lib/cloister/conflict-gate.ts:167-176`), clear `conflictsSince` in the
   same write that clears the blockers.

Detection is keyed on "main moved", not on Overdeck's own merge route, so
flywheel merges, webhook admin merges, and out-of-band pushes are all caught
by one mechanism.

### `git merge-tree` output format (verified experimentally, git 2.x)

```
# conflict case: exit code 1
$ git merge-tree --write-tree --name-only feature main
372a91d087defa345fe76a0b369984fcf527c796      <- line 1: tree OID
a.txt                                          <- lines 2..blank: conflicting paths

Auto-merging a.txt                             <- after blank line: messages
CONFLICT (content): Merge conflict in a.txt

# clean case: exit code 0
$ git merge-tree --write-tree --name-only clean main
cae77a980c249d3659de60a47ca6d238132e3015      <- tree OID only
```

Parse rule: exit 0 → `clean`, paths `[]`. Exit 1 → `conflicts`, paths =
stdout lines after the first, up to (not including) the first blank line.
Any other failure (non-zero with `fatal`/`usage:` in output, fetch failure)
→ `unknown`, paths `[]`. This matches the existing
`mergeTreeFailureIndicatesConflict` semantics
(`src/lib/cloister/conflict-gate.ts:330-340`).

## Requirements

- **FR-1** — When a project's `origin/main` head SHA changes, every
  in-pipeline issue of that project with an existing local workspace is
  probed for merge conflicts against the new head within one patrol cycle.
- **FR-2** — A newly-conflicting issue's review status records
  `conflictsSince: { sha, detectedAt, paths }` (the new main head SHA,
  detection time, conflicting paths), persisted in the `review_status` table
  and mirrored to the durable per-issue record.
- **FR-3** — A newly-conflicting issue's review status gains a
  `merge_conflict` blocker reason (replacing any prior merge blocker), which
  forces `readyForMerge = false` through the existing deriver.
- **FR-4** — The issue's live agent receives a message naming the causing
  main head SHA and the conflicting paths, delivered via
  `resolveIssueFeedbackTarget` + `messageAgent`, at most once per main head
  SHA per issue.
- **FR-5** — Each sweep that finds newly-conflicting branches emits one
  summary activity entry naming the main head SHA and all invalidated issue
  IDs, plus one warn-level entry per invalidated issue naming its paths.
- **FR-6** — When a branch becomes mergeable again, the existing
  conflict-gate clean path clears `conflictsSince` in the same write that
  clears the merge blockers.
- **NFR-1** — Steady state (main unchanged) costs at most one `git
  ls-remote` per project per 120s cooldown window; workspace probes run only
  after a detected main-head change.
- **NFR-2** — Probe failures (`unknown`) change no state and send no
  messages; `ls-remote` failures keep the last-seen SHA and skip the cycle.
- **NFR-3** — All git I/O is async (`execAsync`-style, 30s timeout). No
  `execSync` anywhere reachable from the dashboard server.
- **NFR-4** — Detection is merge-path-agnostic: it reacts to the remote
  ref moving, so route merges, webhook admin merges, and external pushes are
  all covered by the same mechanism.

## NonGoals

- No automatic rebase of agents' branches. The agent (or the existing
  conflict-resolver machinery) decides; this PRD only detects, marks, and
  notifies.
- No change to merge-train eligibility (`readyForMerge`-only siblings) or to
  the `merge_train.enabled` default. The sweep covers ALL in-pipeline
  branches regardless of the train flag.
- No polyrepo fan-out: the sweep probes the workspace's primary repo only
  (the repo `checkBranchMergeability` would probe). Multi-repo workspaces are
  a follow-up.
- No dedicated dashboard badge for `conflictsSince`. The field lands in the
  API DTO and the durable record; the existing `blockerReasons` →
  `stuckReason` path already renders the conflict in the cockpit.
- No backfill for merges that landed before this ships.
- No change to webhook blocker handling (`src/lib/webhook-handlers.ts`) —
  it keeps working; the sweep is additive and dedupes via `conflictsSince.sha`.

## Decisions (auto mode)

- **D1 — Patrol watcher, not a merge-route hook.** Hooking
  `firePostMergeLifecycle` would miss webhook admin merges (which call
  `postMergeLifecycle` directly, `src/lib/webhook-handlers.ts:423`) and any
  out-of-band push. Keying on the remote ref moving covers every merge path
  with one mechanism. Cost: up to ~2 minutes of detection latency
  (120s cooldown) instead of instant — irrelevant against the 12-minute
  silence in the issue.
- **D2 — Reuse the merge-blocker machinery instead of inventing a parallel
  marker.** Writing a `merge_conflict` blocker flips `readyForMerge` and
  routes the issue into the existing conflict gate, review-dispatch defer,
  resolver dispatch, and cockpit `stuckReason` display for free.
  `conflictsSince` carries only what blockers can't: the causing SHA and the
  paths.
- **D3 — Notify via the feedback-target resolver, not raw session names.**
  `resolveIssueFeedbackTarget` handles swarm slots and unregistered slots;
  `needsYou` means no live agent, and stopped agents are already handled by
  the existing resolver dispatch — no duplicate nudge channel needed.
- **D4 — Workspace resolution is sweep-local.** `getWorkspaceInfoForIssue`
  misses `-strike`/`-slot-N` dirs and lives in a route module (layering).
  The sweep resolves via the agents table first, then a
  `feature-<issue>*` prefix scan.
- **D5 — No auto-rebase.** The issue asks for detection + notification; the
  owning agent rebases with full context. Automatic rebases of mid-work
  branches would race the agent's uncommitted state.

## Acceptance criteria

1. AC-1 (FR-1, NFR-1): with main unchanged, a patrol cycle performs no
   workspace probes; after `origin/main` moves, every in-pipeline issue of
   that project with a workspace is probed within one cycle.
2. AC-2 (FR-2, FR-3): a newly-conflicting issue's review status shows
   `conflictsSince.sha` equal to the new main head, `paths` matching
   `git merge-tree` output, a `merge_conflict` blocker, and
   `readyForMerge === false`; the durable record mirrors `conflictsSince`.
3. AC-3 (FR-4): a live agent receives exactly one message per main head

5. AC-5 (FR-6): after the branch is rebased, the conflict gate's clean path
   clears both the merge blocker and `conflictsSince`.
6. AC-6 (NFR-2): a simulated `ls-remote` failure and a simulated probe
   `unknown` produce zero state writes and zero messages.
7. AC-7 (WI-5): `docs/MERGE-WORKFLOW.md` contains a

   `reconcileBranchInvalidation`.
