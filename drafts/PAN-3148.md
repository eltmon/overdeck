# PAN-3148 — Pushed rework commit does not trigger re-review

**Issue:** https://github.com/eltmon/overdeck/issues/3148
**Status:** Draft (auto-planning, 2026-07-26)

## Glossary

- **Review run / runId** — one execution of the review convoy, named
  `agent-<issue>-review-<head8-or-digest>` (e.g. `agent-pan-3093-review-cd81b757`). Minted in
  `src/lib/cloister/review-agent.ts` (~line 561-568) from the workspace HEAD at dispatch time.
- **`reviewedAtCommit`** — a `HeadAnchor` (branded string; composite `repo=sha` snapshot for
  polyrepo workspaces, PAN-2948) recorded on the review status when a review verdict is anchored
  to a HEAD. Defined in `src/lib/review-status-reconcile.ts:48`; durable via `durableSubset()` in
  `src/lib/overdeck/review-status-record-sync.ts:106`.
- **Anchor drift** — the comparison between a stored `HeadAnchor` and a fresh
  `snapshotWorkspaceHeadsPromise()` snapshot, evaluated by
  `evaluateWorkspaceAnchorDrift()` in `src/lib/workspace-anchor-drift.ts:73`. Verdicts:
  `current` | `benign` (same tree/effective code — anchor is advanced, no re-review) |
  `drifted` (real code change) | `unreadable`.
- **`checkPostReviewCommits()`** — deacon patrol in `src/lib/cloister/deacon.ts:1569` that
  detects HEAD drift after a review and resets + re-dispatches review. Registered in the patrol
  loop at `src/lib/cloister/deacon.ts:2952`.
- **Review-verdict feedback** — the `SPECIALIST FEEDBACK: review-agent reported BLOCKED …`
  message + `.pan/feedback/NNN-*.md` file + continue-record `feedback[]` entry produced by
  `deliverReviewVerdictFeedbackPromise()` in `src/lib/cloister/review-verdict-feedback.ts:97`.
- **Keyed delivery / `dedupKey`** — the existing exactly-once message-delivery infrastructure:
  `deliverKeyedAgentMessage()` in `src/lib/agents/delivery.ts:480`, two-phase tmux markers in
  `src/lib/tmux-dedup.ts`, PTY-supervisor key store (`src/lib/channels/pty-supervisor.ts:429`),
  and deterministic keyed mail filenames (`src/lib/agents/messaging.ts:78`).
- **needs-you** — the operator-visible escalation surface
  (`surfaceIssueFeedbackNeedsYou()` in `src/lib/cloister/feedback-target.ts`), already used when
  feedback delivery fails (PAN-2228).

## Problem

Observed on PAN-3093 (2026-07-26): a review convoy blocked at HEAD `cd81b757`. The work agent
fixed the findings, committed, and pushed (`a0bd351134`). Nothing noticed. `review_status` stayed
`blocked` against the stale SHA, the pipeline re-delivered the already-satisfied BLOCKED feedback
to the agent three times, and the agent — reasoning "waiting for a new run ID" — idled while its
context filled to 81% ($60 → $85). `pan review restart PAN-3093` fixed it in one command, proving
the agent and the branch were fine; the missing piece is the **edge from "rework pushed" to
"re-review dispatched"**.

Root cause, verified in code:

1. `checkPostReviewCommits()` (deacon.ts:1580) skips every issue that is not `passed`/
   `readyForMerge`: `if (status.reviewStatus !== 'passed' && !status.readyForMerge) continue;`.
   A `blocked` issue with drift is never examined.
2. `reviewedAtCommit` is only snapshotted on **passed** verdicts
   (`src/dashboard/server/routes/specialists/legacy-routes.ts:316`,
   `src/cli/commands/specialists/done.ts:159` — `if (workspaceHead && options.status === 'passed')`).
   A blocked verdict records no anchor, so even a blocked-aware patrol would have nothing to
   compare against. (Exception: the deacon fallback synthesis computes `fallbackHead` at
   `deacon-review-signals.ts:~240` but only uses it for per-reviewer `atCommit`, not
   `reviewedAtCommit`.)
3. `deliverReviewVerdictFeedbackPromise()` calls
   `messageAgent(target.agentId, message, 'internal', { owesRework: true })`
   (review-verdict-feedback.ts:146) **without a `dedupKey`**, bypassing the exactly-once
   delivery infrastructure that already exists, so every re-trigger (reconcile transition,
   fallback synthesis, operator action) re-pastes the identical message into the agent's context.

## Proposal

Four changes, each mapped to one ask in the issue:

1. **Anchor blocked verdicts** (enabler). Snapshot `reviewedAtCommit` on `blocked` review
   verdicts at all three verdict sites, best-effort and *after* the durable verdict write +
   feedback kickoff, preserving PAN-2524's synchronous-write property.
2. **Extend `checkPostReviewCommits()` to blocked reviews** (primary fix). When review status is
   `blocked` and the anchor drifts (real code change), reset review to `pending` and re-dispatch
   the convoy — the automatic form of `pan review restart`. A two-patrol-tick HEAD-stability
   debounce prevents dispatching against an agent that is still mid-rework (see D2).
   For legacy blocked rows with no `reviewedAtCommit`, derive the anchor from
   `reviewerVerdicts[*].atCommit` when they all agree (covers issues blocked before this ships).
3. **Keyed feedback delivery** (defence in depth). Compute
   `dedupKey = review-feedback:<issueLower>:<sha256(verdict|runId|anchor)[:16]>` and pass it
   through `messageAgent`'s existing `opts.dedupKey`, making the agent message exactly-once per
   (issue, verdict, run/anchor) across live tmux, PTY supervisor, and the mail queue. Fall back
   to unkeyed delivery for ACP/Channels targets, which cannot enforce keys
   (`delivery.ts:485-492` throws) — delivery beats dedup.
4. **Escalate repeated suppression** (bound the damage). Thread the existing
   `DeliveryResult.deduplicated` flag into `MessageDeliveryOutcome`; in
   `deliverReviewVerdictFeedbackPromise`, count suppressed repeats per key in a module-level map
   and on the 2nd suppressed repeat surface one needs-you ("feedback for this verdict was
   delivered; repeated re-triggers detected — possible stuck loop") via the existing
   `surfaceIssueFeedbackNeedsYou`.

## Decisions

- **D1 — Reset-and-redispatch, not `pan review restart` reuse.** The patrol mirrors the passed
  path's reset (`reviewStatus: 'pending'` + `spawnReviewRoleForIssue({ force: true })`) rather
  than shelling to the restart route. Same code path as the proven passed-case drift handling;
  no HTTP self-call from the deacon.
- **D2 — Two-tick HEAD-stability debounce before auto-dispatch.** Auto-dispatching on the *first*
  observed drift could fire while the work agent is still mid-rework (agents commit and push
  per item), buying a convoy run against an incomplete rework. Requiring the same drifted anchor
  on two consecutive patrol ticks (~1-2 min of HEAD stability) means a finished-and-waiting
  agent is rescued within ~2 minutes, while a still-pushing agent keeps resetting the clock.
  In-memory map keyed by issueId; a dashboard restart costs at most one extra tick.
- **D3 — Message-level dedup, not file-level.** The context damage is the repeated agent
  *message*; the append-only feedback file/`feedback[]` history is by design (cleared per cycle
  by `clearFeedbackFiles`). The dedupKey covers live delivery, supervisor, and mail-replay
  (keyed mail filenames overwrite instead of stacking). No new persisted fields, no DB
  migration: the tmux/session markers and mail filenames already provide the durability the
  incident needs (the observed loop was within one host/session lifetime).
- **D4 — Escalation counter is in-memory.** Counting suppressed repeats per key in the
  long-lived dashboard host is sufficient for the observed failure class (a same-process
  redelivery loop over four ticks). Persisting attempts to the journal would require a
  `ReviewStatus` field + SQLite column; rejected as disproportionate for a defence-in-depth
  signal. Rationale recorded per auto-mode rules.
- **D5 — Blocked verdicts only; `failed` is out of scope.** `reviewStatus: 'failed'` is the
  infra-failure path with its own recovery (`reviewRetryCount`, `recoveryStartedAt`,
  PAN-794). Extending drift detection there is a separate design; see NonGoals.
- **D6 — The "waiting for a new run ID" sentence is agent-derived, not a logger** (confirmed:
  no match in `src/`). Ask #2 is therefore satisfied by (a) the primary fix removing the
  condition, and (b) a work-prompt update telling agents that pushed rework while blocked
  auto-triggers re-review and that waiting for a run ID is never correct. No new status
  surface is built.

## Requirements

### Functional

- **FR-1** — When a review verdict of `blocked` is recorded through any of the three verdict
  sites (CLI `pan specialists done`, HTTP `/api/specialists/done`, deacon fallback synthesis),
  `reviewedAtCommit` is snapshotted from the workspace HEAD, best-effort, after the durable
  verdict write.
- **FR-2** — When `reviewStatus` is `blocked`, `reviewedAtCommit` (or an anchor derived from
  agreeing `reviewerVerdicts[*].atCommit`) is set, and `evaluateWorkspaceAnchorDrift` returns
  `drifted`, the deacon resets review to `pending` and re-dispatches the review convoy at the
  new HEAD, subject to the two-tick stability debounce and the existing advancing-slot
  concurrency gate.
- **FR-3** — A `benign` drift verdict for a blocked issue advances `reviewedAtCommit` without
  resetting review (same as the passed path).
- **FR-4** — Review-verdict feedback messages are delivered with a `dedupKey`; a second
  delivery attempt for the same (issue, verdict, anchor/runId) submits nothing to the agent's
  terminal and stacks no second mail file.
- **FR-5** — When a keyed delivery target cannot enforce dedup (ACP or Channels), feedback is
  delivered unkeyed rather than failing.
- **FR-6** — The 2nd suppressed (deduplicated) re-delivery for the same key surfaces exactly one
  needs-you escalation naming the issue and the repeated verdict.

### Non-functional

- **NFR-1** — No new persisted schema: no `ReviewStatus` fields, no SQLite columns, no journal
  format changes. (`reviewedAtCommit` is already durable.)
- **NFR-2** — PAN-2524 preserved: the durable blocked-verdict write stays synchronous and ahead
  of feedback delivery; the anchor snapshot is a second, later write.
- **NFR-3** — The patrol addition reuses `evaluateWorkspaceAnchorDrift` unchanged; polyrepo
  composite anchors work without new code.
- **NFR-4** — No `execSync` in server-reachable code; patrol git probes stay async
  (`snapshotWorkspaceHeadsPromise`).

## Acceptance Criteria

1. Given a `blocked` review verdict recorded through any of the three verdict sites, when the
   write completes, then `getReviewStatusSync(issueId).reviewedAtCommit` returns the workspace
   HEAD anchor, and the feedback file exists (anchor write ordered after feedback).
2. Given an issue with `reviewStatus: 'blocked'` and an anchor, when the workspace HEAD advances
   with a real tree change and stays there for two patrol ticks, then review status resets to
   `pending` and a new review convoy is spawned at the new HEAD.
3. Given the same setup but a same-tree (benign) HEAD move, when the patrol runs, then
   `reviewedAtCommit` advances and review stays `blocked` — no dispatch.
4. Given a blocked issue with no `reviewedAtCommit` but uniform `reviewerVerdicts[*].atCommit`,
   when the patrol runs, then the derived anchor is used for drift detection.
5. Given feedback already delivered for (issue, verdict, anchor), when the same delivery is
   triggered again, then the agent's terminal receives no new message and the mail directory
   holds at most one file for that key.
6. Given an ACP-target work agent, when review feedback is delivered, then delivery succeeds
   unkeyed (no "cannot enforce a dedup key" rejection reaches the caller).
7. Given two consecutive suppressed re-deliveries for one key, when the second suppression is
   counted, then exactly one needs-you escalation is surfaced for the issue.
8. `npm run typecheck`, `npm run lint`, and `npm test` pass with the new/extended test files
   green.

## NonGoals

- Extending drift detection to `reviewStatus: 'failed'` (infra-failure recovery is PAN-794's
  design space).
- Persisting feedback-delivery attempt counts to the journal or SQLite (D4).
- Deduplicating the append-only feedback file/`feedback[]` history (D3).
- Changing `pan review restart`, the review convoy prompts, or the reviewer sub-role fan-out.
- Any dashboard frontend change.
- Fixing PAN-3147 (orchestrator liveness-vs-verdict read) — related, separately filed.
