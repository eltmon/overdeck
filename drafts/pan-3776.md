## Glossary

- **t3code** — Ping.gg's open-source (MIT) web/desktop/mobile chat UI for AI coding
  agents. Effect-based Node server, React web app, Electron desktop, Expo mobile.
  Repo: `github.com/pingdotgg/t3code`; local clone `~/Projects/t3code`.
- **Upstream** — the t3code project/maintainers. Not accepting contributions
  (CONTRIBUTING.md verified 2026-08-25); feature input goes through their GitHub Ideas
  discussions only.
- **Plugin runtime** — t3code's in-process Effect-based plugin engine
  (`packages/plugin-runtime/src/runtime.ts`, 809 lines on the plugin branches). Unmerged
  to their `main` as of 2026-08-25.
- **Plugin package** — a directory in t3code's plugins directory containing a
  `t3-plugin.json` manifest, a server entrypoint module, and (per the manifest schema,
  not yet implemented) optional web/desktop entrypoints.
- **Contribution catalog** — the manifest's `contributes` block declaring what a plugin
  adds. Four categories in the schema (`packages/plugin-runtime/src/manifest.ts` lines
  22–25 on `feat/plugin-management-ui`): `commands`, `settings`, `views`, `mobileCards`.
  Only `commands` is implemented.
- **Capability** — a named service a plugin `requires` or `provides`, resolved by the
  runtime at activation. The host provides exactly one today: `t3.commands@1`
  (`apps/server/src/plugins/PluginPackageManager.ts:31` on
  `feat/plugin-package-lifecycle`).
- **`overdeckd`** — (proposed, this PRD) Overdeck's engine extracted as a headless
  daemon: Cloister/Deacon, event store, webhook ingestion, merge execution, patrol
  loops, state-branch write door, tmux agent substrate. No UI of its own.
- **Bridge plugin** — (proposed, this PRD) the t3code plugin package whose server
  entrypoint connects to `overdeckd` and whose web bundle contributes Overdeck's
  orchestration views.
- **Seams-only fork** — the bounded fallback: carrying t3code's own plugin branches plus
  a diff that implements ONLY missing extension machinery (views catalog, web-bundle
  loading), mirroring upstream's manifest schema, deleted seam-by-seam as upstream ships
  equivalents. Never contains Overdeck features.

## Problem

Overdeck is maintained by one person and carries an entire platform surface that is not
its differentiator: chat UX, in-browser terminals, diff rendering, desktop packaging,
auth, remote access, provider drivers. t3code maintains a better-funded, fast-moving
version of exactly that surface (multiple nightlies per day). Overdeck's differentiator —
the issue-to-merge pipeline, orchestration, flywheel — is ~98% original code with no
t3code counterpart (feasibility doc, "What Overdeck would have to re-home").

Goal: shed the platform surface by shipping Overdeck as a plugin on stock t3code, so
upstream maintains the app shell and Overdeck maintains only the engine and its views.

Forking t3code outright is explicitly rejected (operator-confirmed 2026-08-25): a fork is
the highest-maintenance option, not the lowest. The only acceptable fork is the
seams-only fork, and only if upstream's plugin system never supports what we need.

## Target architecture (three tiers)

```
┌───────────────────────────────────────────────────────────┐
│ t3code (stock, upstream-maintained)                        │
│  chat threads · terminals · diffs · desktop/mobile · auth  │
│  ┌───────────────────────────────────────────────┐        │
│  │ Overdeck bridge plugin                         │        │
│  │  server entrypoint: connects to overdeckd,     │        │
│  │    registers commands, relays read-model       │        │
│  │  web bundle: Command Deck, kanban, pipeline    │        │
│  │    board, God view … as t3code views           │        │
│  └───────────────┬───────────────────────────────┘        │
└──────────────────┼────────────────────────────────────────┘
                   │ HTTP/WS (existing dashboard API surface)
┌──────────────────▼────────────────────────────────────────┐
│ overdeckd (ours, headless)                                 │
│  Cloister/Deacon · event store · webhooks · merge exec ·   │
│  patrols · state write door · pan CLI server side          │
└──────────────────┬────────────────────────────────────────┘
                   │ tmux -L overdeck
        work / plan / review / test / merge agents
```

Tier boundaries and their rationale:

1. **Engine stays a sibling daemon, never a plugin.** The orchestrator (Cloister/Deacon
   is the dashboard server — `src/dashboard/server/`, ~100 Cloister files), the tmux
   substrate, and pipeline agents cannot run inside a web-app plugin runtime under any
   architecture (feasibility doc, "Sibling processes" + "Host-internals"). Extracting
   `overdeckd` is valuable under every future, including the one where t3code pivots
   and Overdeck keeps its own dashboard.
2. **Plugin server entrypoint is a connector, not the engine.** It holds no canonical
   state; it speaks to `overdeckd` over the existing HTTP/WS API. Both systems
   independently converged on append-only events + projections + client-side reducers
   over WS (t3code: `packages/client-runtime/src/state/threadReducer.ts`; Overdeck:
   `packages/contracts/src/event-reducers.ts`), so the relay is a translation between
   two dialects of the same model.
3. **Web bundle = Overdeck's orchestration UI as contributed views.** ~590 of 664
   frontend files (~89%) are orchestration surfaces with no t3code counterpart; chat is
   ~11% and is the part being retired (feasibility doc inventory).

| Plugin management UI | **EXISTS** — `PluginsSettings.tsx` (299 lines) + `routes/settings.plugins.tsx` on `feat/plugin-management-ui` | Unmerged |

## Requirements

Functional:

- **FR-1** Overdeck's engine runs as a headless daemon (`overdeckd`) with no UI process,
  exposing its existing HTTP/WS API; the current dashboard frontend and any t3code
  bridge plugin are interchangeable clients of it.
- **FR-2** A t3code plugin package (manifest + server entrypoint) connects to
  `overdeckd` and contributes pipeline commands to t3code's command palette (status,
  start-work, approvals) using only upstream's shipped plugin surface.
- **FR-3** When upstream ships views + web entrypoints: Overdeck's orchestration
  surfaces (pipeline board first, then Command Deck, kanban, God view, issue views)
  render as contributed t3code views, fed live by the read-model relay.
- **FR-4** Exactly one owner per collision domain (see Decisions): agent sessions,
  transcripts, terminals, worktrees, event stores, cost tracking, model resolution.
- **FR-5** The legacy Overdeck dashboard remains fully functional until every migrated
  view has a no-loss audit pass; surfaces retire view-by-view, never big-bang.

Non-functional:

- **NFR-1** The bridge plugin holds no canonical state (two-doors tenet: reads via
  `overdeckd` resolvers, writes via its write surfaces only).
- **NFR-2** Any seams-only fork diff contains extension machinery only — never Overdeck
  features — mirrors upstream's manifest schema, and shrinks monotonically as upstream
  ships equivalents.
- **NFR-3** Version pinning: the plugin declares `engines`/`apiVersion` per upstream's
  manifest; a t3code upgrade that breaks the plugin API must fail loudly at activation
  (runtime already rolls back failed activations), never corrupt `overdeckd` state.

## Decisions (made here so executors don't re-derive)

- **D1 — Session ownership:** Overdeck agents stay tmux subprocesses owned by
  `overdeckd`. t3code's provider sessions (Codex/Claude in-process) are used only for
  *chat threads a human opens*; pipeline agents never migrate to t3code providers.
- **D2 — Transcripts:** JSONL transcripts remain owned by Overdeck harnesses;
  t3code's SQLite projections never write them. Bridge exposes read-only transcript
  views if needed. (Concurrent writers would corrupt — feasibility doc collision list.)
- **D3 — Terminals:** t3code's PTY/terminal stack is for its own threads; attaching to
  Overdeck agent tmux sessions goes through a contributed view backed by `overdeckd`'s
  existing attach hub, not t3code's PTY manager.
- **D4 — Event stores:** two stores remain (theirs for chat threads, ours for
  orchestration); the bridge translates read-only. No shared writes, no merge.
- **D5 — Cost tracking:** `overdeckd` remains the single cost ledger; bridge relays
  display data. t3code-native chat costs stay t3code's.
- **D6 — Worktrees:** `overdeckd` owns pipeline workspaces; t3code's worktree feature
  is for human chat threads only. The bridge must not let both create worktrees for the
  same issue branch.
- **D7 — Fork posture:** hard fork rejected. Seams-only fork is the only fork variant,
  and only under Phase 4 conditions.
