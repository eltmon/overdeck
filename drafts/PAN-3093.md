# PAN-3093 — Polyrepo UAT assembly: per-repo generation branches, per-repo base SHAs, all-or-nothing promote

**Issue:** https://github.com/eltmon/overdeck/issues/3093
**Status:** draft (planning, `--auto` mode)
**Date:** 2026-07-26

## Glossary

- **UAT batch train / generation** — a deterministic-per-day `uat/<label>-<codename>-<MMDD>` branch assembled off current main containing as many merge-ready features as possible, promoted ("merge what you tested") as one batch. State lives in the `uat_generations`, `uat_generation_members`, `uat_generation_resolutions` SQLite tables.
- **Polyrepo project** — a project whose `projects.yaml` config sets `workspace.type: 'polyrepo'` with `workspace.repos[]`. Its project path (e.g. `/home/eltmon/Projects/myn`) is a **wrapper**: not a git repo; each member repo is a real git repo at `<projectPath>/<repo.path>`. Polyrepo *workspaces* mirror this: `<workspace>/<repoKey>` sub-repo worktrees.
- **Monorepo project** — the default; one git repo at the project path. The canonical repo resolver (`src/lib/project-repos.ts`) collapses it to a single synthetic `ResolvedProjectRepo`.
- **Repo anchor / composite anchor** — the per-repo head-SHA tuple format already used by the review pipeline (PAN-2948), e.g. `fe@abc1234 api@def5678`. This plan reuses it as the polyrepo `base_sha` encoding.
- **Ready set** — the merge-queue-ordered list of `ReadyFeature`s the reconciler wants bundled into the next generation.
- **Hold-out** — a feature whose merge conflicts and cannot be auto-resolved is excluded from the generation with a recorded reason; assembly continues.
- **Promote** — merging a generation's uat branch into main (no-ff, throwaway worktree) and firing each member's post-merge lifecycle.
- **Generation folder** — `uat-<label>-<codename>-<mmdd>` (slashes collapsed), the worktree directory under `<projectRoot>/workspaces/`; doubles as the docker compose project suffix and Traefik host.
- **`tryIdempotentDdl`** — the schema-ladder helper in `src/lib/database/schema.ts` that applies additive DDL once, keyed by `user_version`.

## Problem

The UAT assembly engine is single-repo by construction. `assembleUatGeneration` (`src/lib/cloister/uat-generation-engine.ts:122`) drives one `GenerationGitDeps` against one `projectRoot`: `fetchMain()`, one worktree, one `baseSha`, one push. A polyrepo project (MYN: six member repos, wrapper has no `.git`) violates every assumption, so PAN-1696 (PR #3095, merged 2026-07-26) shipped a guard in `runUatTrainReconcileForProject` (`src/dashboard/server/services/uat-train.ts:126-131`) that skips polyrepo projects with a logged reason. Until this issue lands, `mind-your-now` gets no UAT train.

Single-repo assumptions to remove, all verified in the tree at branch `feature/pan-3093` (synced with `origin/main` at 2026-07-26):

1. **Schema** — `uat_generations.base_sha` is one TEXT column (`src/lib/database/schema.ts:354-373`); `uat_generation_members` has one `branch`/`head_sha` per issue (`src/lib/overdeck/merge-sync.ts:471`). `UatGeneration` (`src/lib/overdeck/merge-types.ts:69-86`) has one `worktreePath`, one `baseSha`.
2. **Ready set** — `computeMergeQueueFromCandidates` (`src/lib/flywheel-merge-order.ts:279`) derives `feature/<issue>` branch names (line 325) and runs `branchExists`/`changedFilesVsMain` against the project root — git ops that fail on a wrapper.
3. **Assembly** — `GenerationGitDeps` (`uat-generation-engine.ts:55-74`) is one repo's worth of git.
4. **Reconciler** — `desiredSignature`/`liveSignatureMatches` (`src/lib/cloister/uat-reconciler.ts:84-122`) compare one main SHA and one head SHA per branch.
5. **Promote** — `promoteUatGeneration` (`src/lib/cloister/uat-promote.ts:105`) does one stale-base check and one `mergeIntoMain`.
6. **Teardown** — `cleanupUatGenerations` (`uat-generation-engine.ts:283`) removes one worktree + one branch per generation.

## Proposal

Extend the subsystem **additively** along the existing seam: the canonical repo resolver already collapses monorepo to a one-element repo list, so the polyrepo model (N repos) generalizes the monorepo model (1 repo) rather than forking it. The existing single-repo engine, its deps contract, and its unit tests (`tests/unit/lib/cloister/uat-generation-engine.test.ts`, 299 lines) stay **byte-identical**; polyrepo gets a sibling engine module, sibling ready-set computation, and extended schema/store/reconciler/promote/cleanup paths that treat monorepo as the N=1 case only where the code already routes through the extended surface (store reads, reconciler signatures, promote, cleanup).

### Design decisions (made in this doc — no judgment calls left to the implementer)

- **D1 — Schema is additive: two child tables, no ALTER of existing semantics.**
  - New `uat_generation_repos`: `(uat_name, repo_key, repo_path, branch, base_sha, worktree_path, merge_order, PRIMARY KEY(uat_name, repo_key))`. One row per repo the generation touched. Monorepo generations ALSO get one row (repoKey = project key) on write, so every reader can loop uniformly; existing pre-migration rows are backfilled lazily at read time (row mapping synthesizes the single repo entry from `base_sha`/`worktree_path` when no child rows exist).
  - New `uat_generation_member_repos`: `(uat_name, issue_id, repo_key, branch, head_sha, merge_order_in_repo, PRIMARY KEY(uat_name, issue_id, repo_key))`. One row per (member, repo) contribution.
  - `uat_generations.base_sha` stays NOT NULL. Polyrepo rows store the **composite anchor** (`<repoKey>@<shortSha>` space-separated, merge_order order) — the same format PAN-2948 already records for review anchors (MIN-901 precedent cited in the issue). This keeps `baseSha` meaningful for staleness comparison without a second encoding.
  - Types: `UatGeneration` gains `repos: UatGenerationRepo[]`; `UatGenerationMember` gains optional `repos?: UatGenerationMemberRepo[]`.
- **D2 — Polyrepo assembly is a new engine module, not an `if (polyrepo)` fork.** New `src/lib/cloister/uat-polyrepo-engine.ts` exports `assemblePolyrepoUatGeneration(input, deps)` where `deps.repos: Array<{ repo: ResolvedProjectRepo; git: GenerationGitDeps }>` reuses the existing per-repo `GenerationGitDeps` contract verbatim. The real wiring builds one `buildUatGenerationGitDeps(repo.repoPath)` per repo — the existing factory already takes a root argument and needs no change. Worktrees land at `<projectPath>/workspaces/<generationFolder>/<repoKey>` (mirrors the polyrepo workspace layout from `src/lib/workspace-manager/create.ts`); the generation's `worktreePath` is the wrapper folder, keeping the stack contract (`uatStackFolderName`, compose discovery, Traefik host) unchanged.
- **D3 — Global hold-out by fixpoint re-assembly.** A feature that cannot be merged+resolved in ANY contributing repo is removed from ALL repos' merge lists, and every repo branch that had already merged it is rebuilt from base (force-reset worktree to the repo's target branch, replay the remaining features). Loop until no new hold-outs occur; bounded by the feature count. Rationale: excising a merged commit from the middle of a branch is fragile; replay is deterministic, reuses the existing per-repo merge loop, and the conflict hook simply isn't consulted for pairs that no longer co-occur.
- **D4 — Promote is two-phase; all-or-nothing is decided in phase A.**
  - Phase A (validate, pushes nothing): for every repo in `merge_order`, fetch the target branch, run the per-repo stale-base overlap check (same disjoint-movement rule as `uat-promote.ts:133-156`, per repo), then trial-merge the repo's uat branch into the target in a throwaway worktree WITHOUT pushing, producing the merge commit locally. Any failure in any repo → discard all throwaway worktrees, return failure, generation stays `ready`. **Nothing has been pushed.**
  - Phase B (publish): push each prepared merge to its repo's target branch in `merge_order`. If a push fails partway, the promote is **resumable, not rolled back**: per-repo success is recorded in `uat_generation_repos` (add `promoted_at INTEGER` column), a retry skips repos whose target branch already contains the merge commit, and the failure result names the repos that did and did not land. Force-pushing/rewinding a member repo's main is a one-way door and is NOT done (restated from repo rules).
  - Post-merge lifecycle (`firePostMerge`) fires per member issue only after ALL repos publish, exactly as today.
- **D5 — Reconciler generalizes via optional anchor deps, existing tests untouched.** `UatReconcilerDeps` gains optional `getBaseAnchor(): Promise<string>` and `getFeatureAnchor(feature: ReadyFeature): Promise<string>`; when absent, behavior is exactly today's (`getMainHeadSha` / `getBranchHeadSha`). The polyrepo service wiring passes composite anchors (per-repo target heads; per-issue per-repo branch heads joined as anchors). Signatures stay strings — `desiredSignature`, `generationSignature`, `liveSignatureMatches` need no structural change beyond routing through the anchor accessors, and `gen.baseSha` (composite for polyrepo) compares correctly.
- **D6 — Polyrepo ready set is computed per repo, aggregated for ordering.** Candidates still come from `listEligibleCandidatesByProject` (git-free, review-status based). For each candidate, `resolveProjectReposFromResolvedIssueSync` yields the configured repos; a per-repo branch-existence check (origin-first, same convention as `branchHeadSha`) determines **contributions** — repos with no feature branch for the issue are skipped, per the issue. Conflict prediction unions each candidate's changed-file sets across its contributing repos (`changedFilesVsMain` per repo against that repo's target branch) and feeds the existing `orderMergeCandidates`. A candidate with zero contributing repos is excluded with a logged reason.
- **D7 — The conflict hook is scoped, not changed.** `ConflictContext` gains optional `repoKey`; `buildConflictResolutionPrompt` mentions the repo when present. The hook already operates purely on the worktree path it is given — per-repo worktrees make it per-repo automatically.
- **D8 — Guard removal rides with the routing change.** Deleting the guard at `uat-train.ts:126-131` (plus the dead `PolyrepoAssemblyUnsupported` class at lines 87-92 and the stale comment at line 215) happens in the same item that wires polyrepo routing, so the tree never has routing-without-support or support-without-routing.

### What a polyrepo generation looks like after this lands

- One generation row `uat/min-<codename>-0727`, `base_sha = "fe@… api@…"`, `worktree_path = /home/eltmon/Projects/myn/workspaces/uat-min-<codename>-0727`.

## Requirements

### Functional

- **FR-1 (schema):** Generations record per-repo base SHAs, branch names, worktree paths, and per-(member,repo) contributions in new child tables; the migration is additive (`tryIdempotentDdl`), idempotent, and leaves every existing row readable (monorepo read path synthesizes N=1 repo data when child rows are absent).
- **FR-2 (ready set):** For a polyrepo project, the ready set resolves each candidate's contributing repos via `resolveProjectReposFromResolvedIssueSync`, excludes candidates with zero contributing branches (logged), and orders via the existing conflict-prediction ordering over per-repo changed-file unions.
- **FR-3 (assembly):** Assembly creates one `uat/<label>-<codename>-<MMDD>` branch per contributing member repo, each off that repo's current target-branch head, merging features in queue order; repos with no contributing feature branch get no branch, no worktree.
- **FR-4 (conflict/hold-out):** The conflict hook runs per repo with `repoKey` in its context; a feature that fails merge+resolution in any repo is held out of the WHOLE generation (all repos), recorded once in `heldOut` with the repo that blocked it named in the reason.
- **FR-5 (promote):** Promote validates and trial-merges every repo before publishing anything (all-or-nothing decision); publishes per repo in merge order; records per-repo publish state; is safely resumable after a partial publish; fires per-member post-merge lifecycles only after every repo publishes.
- **FR-6 (teardown):** Cleanup removes every per-repo worktree and branch (local + remote), tears down the generation's stack (including its docker network), and removes the wrapper folder; promoted/invalidated/failed rows are never deleted.
- **FR-7 (guard):** The PAN-1696 polyrepo-exclusion guard, the dead `PolyrepoAssemblyUnsupported` class, and the stale comment in `uat-train.ts` are deleted; polyrepo projects route through the new path in `runUatTrainReconcileForProject`.
- **FR-8 (monorepo parity):** Monorepo behavior is byte-identical — `tests/unit/lib/cloister/uat-generation-engine.test.ts` passes UNMODIFIED, and the monorepo assembly call path (`assembleFromReadySetForProject` → `assembleUatGeneration`) is unchanged.
- **FR-9 (docs):** `docs/UAT-BATCH-TRAINS.md`, `docs/MERGE-TRAIN.md`, and `features/merge-batches.mdx` describe polyrepo generations (per-repo branches, composite base anchor, two-phase promote); `docs/ORDER-BOOKS.md` is updated if it still references the single-repo limitation (verify at implementation; if no reference exists, say so in the commit).

### Non-functional

- **NFR-1:** All git/docker I/O in server-reachable code is async (`execAsync`/`spawn`); no `execSync`; the pure-orchestrator-with-injected-deps pattern is preserved (new engine logic is unit-tested with fake per-repo git deps — no live git in tests).
- **NFR-2:** Branch names and worktree paths pass through the existing `safeBranchName`/`safeGenerationWorktreePath` validators per repo.
- **NFR-3:** New unit tests use `vi.useFakeTimers()` wherever retry/backoff/timeouts are exercised (repo rule).

## NonGoals

- Changing monorepo assembly logic, its deps contract, or its unit tests.
- Automatic rollback (force-push / revert) of a member repo's main after a partial publish — recovery is idempotent resume only.
- Cross-repo semantic conflict detection beyond per-repo changed-file overlap.
- Dashboard/frontend rendering changes for per-repo generation detail (payload gains the `repos` field additively; presentation is a follow-up).
- Changing per-issue polyrepo merge (`merge-ops.ts`) or merge-set semantics.
- Making the live UAT stack render polyrepo-specific devcontainer templates beyond what `ensureDevcontainerSync` already renders into the wrapper folder (verified at WI-7; gaps become a follow-up issue, not scope creep here).
