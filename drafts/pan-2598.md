# PAN-2598 — Issue view misreports an in-flight planning session

**Issue:** https://github.com/eltmon/overdeck/issues/2598
**Authored:** 2026-07-12 (planning agent, `pan plan --auto`), verified against main @ `5698a7d546`.

## Glossary

- **Issue view / cockpit** — the per-issue dashboard page (`IssueMissionControl`) with the phase banner, "What just happened" feed, and AGENTS & STEPS tree.
- **HappenedFeed** — the "What just happened" timeline component (`src/dashboard/frontend/src/components/Stage/cockpit/HappenedFeed.tsx`), which renders lines like "fable-5 finished the plan".
- **Phase banner** — the `StatusNarrative` headline ("The crew is writing code", "Planning what to build", …) rendered by `src/dashboard/frontend/src/components/Stage/cockpit/StatusNarrative.tsx`.
- **AGENTS & STEPS tree** — the `AgentsLane` component (`.../cockpit/AgentsLane.tsx`) listing Plan/Work/Verification/Test rows for the issue.
- **Activity sections** — per-issue agent session summaries returned by `GET /api/command-deck/activity/:issueId` (`src/dashboard/server/routes/command-deck.ts:186-385`). Each section has `type` (planning/work/…), `startedAt`, `duration`, `status`, `presence`, `awaitingInput`.
- **Session-trees** — `GET /api/session-trees` (`src/dashboard/server/routes/projects.ts:490-561`), the primary per-issue session list, built by `collectSessionTreeNodes` (`projects.ts:197-407`).
- **Planning agent** — the `plan`-role session. Route/CLI spawn names it `planning-<issue>` (`src/lib/overdeck/planning-sessions.ts:266`); Cloister `spawnRun(issueId, 'plan')` names it `agent-<issue>-plan` (`src/lib/agents/spawn-prep.ts:621-625`).
- **AUQ** — AskUserQuestion. A PreToolUse deny hook (`sync-sources/hooks/ask-user-question-hook`) blocks the tool and tells the agent to restate; the dashboard detects the hook-denied tool_result in the session JSONL and surfaces a pending question (modal + needs-you).
- **Deny marker** — the literal string `PAN-1520` that `isAskUserQuestionHookDenyToolResult` (`src/lib/agent-enrichment.ts:253-270`) requires inside the deny tool_result to classify it as a hook deny rather than a real answer.
- **needs-you** — `isNeedsYouFeature` (`src/dashboard/frontend/src/components/CommandDeck/pipeline-helpers.ts:65-68`); trips for a planning session when `session.awaitingInput` is true, which the server derives solely from enrichment `hasPendingQuestion` (`command-deck.ts:222`, `projects.ts:84`).
- **PLANNING_FINISHED_STATUSES** — the set of `plan.status` values that mean planning genuinely completed (`src/lib/vbrief/io.ts:353-379`).

## Incident (ground truth, verified 2026-07-12)

While `planning-pan-2597` was alive on the `overdeck` tmux socket and blocked on an operator question (~12:29–13:05 local):

1. HappenedFeed said "fable-5 finished the plan" — no spec, no beads, no continue file existed.
2. Phase banner said "The crew is writing code — Up next: the reviewer checks the finished work" — no work agent existed.
3. AGENTS & STEPS showed only synthetic Verification/Test steps — no planning row.
4. No AUQ modal and no needs-you trip fired for the blocked question.

Filesystem timestamps confirm: workspace `.overdeck/` created 12:30; workspace `.pan/` first artifact 13:05:51; `agent-pan-2597` (work agent) state.json 13:22. `planning-pan-2597/state.json` existed from 12:29 with `role: "plan"`.

## Root causes (all verified at file:line)

### RC-1 — "finished the plan" fires on mere elapsed time
`command-deck.ts:340-343` computes section `duration` as `Date.now() - startedAt` — non-null for any agent that ever started, alive or not. `HappenedFeed.tsx:66-74` renders the "done" verb (`finished the plan`) whenever `duration !== null` and the status doesn't regex-match `/fail|blocked|error/`. An idle-but-alive planning agent has `status: 'running'` (`command-deck.ts:344-350`), so the "done" line always renders. No layer consults planning artifacts (`plan.status`, spec existence, finalize). The same defect class applies to work/review sections. `collectSessionTreeNodes` (`projects.ts:265-271`) has the identical elapsed-as-duration computation and always emits `endedAt: undefined`.

### RC-2 — phase banner conflates "no review row" with "work agent running"
`IssueMissionControl.tsx:910` passes `workRunning={phase === 'pending'}` to StatusNarrative. `phaseStatus()` (`IssueMissionControl.tsx:135-145`) returns `'pending'` whenever the review-status query has no data — which is exactly the planning phase. `StatusNarrative.tsx:81-83` then hits the "The crew is writing code" branch before the `!hasPlan` → "Planning what to build" branch at `:84-86`. A genuine live-work-session signal exists in the same file (`sections.some(s => s.type==='work' && s.status==='running')`, used by NowPanel ~`:727`) but is not used here.

### RC-3 — live planning agent invisible in the tree (incident chain, two compounding halves)
**(a) Backend pre-filter drops the whole feature.** `projects.ts:533-539` includes a feature in session-trees only if `~/.overdeck/agents/agent-<issue>/` (work agent) exists OR `<workspace>/.pan/` exists (`PAN_DIRNAME = '.pan'`, `src/lib/pan-dir/types.ts:10`). During planning neither existed: the work agent hadn't started and the modern workspace runtime dir is `.overdeck/`, not `.pan/`. A live `planning-<issue>` agent dir is not a qualifying condition.
**(b) Frontend shadowing.** `fetchCockpitProjectFeature` (`IssueMissionControl.tsx:340-381`) returns `{...feature, sessions: treeFeature?.sessions ?? feature.sessions}` from `/api/issues/resource-allocated` — a non-null object with empty/undefined sessions — so `projectFeature.data ?? fallbackFeature` (`IssueMissionControl.tsx:462`) never falls back to the activity-derived sessions, which WOULD have included the live planning section (the activity builder at `command-deck.ts:277-283` enumerates `planning-<issue>` directly with no pre-filter).
**Additional latent gaps (not the incident, still real):** the candidate sets in `projects.ts:214` and `command-deck.ts:283` do not include `agent-<issue>-plan` (Cloister spawnRun naming); a tmux-alive planning session with a missing/invalid `state.json` yields no node (`projects.ts:230-234`).

### RC-4 — AUQ deny misclassified as answered (marker contract broken)
Commit `3d77214f55` (PAN-2530) deleted the `(PAN-1520)` substring from the hook's deny `REASON` (`sync-sources/hooks/ask-user-question-hook:52`). `isAskUserQuestionHookDenyToolResult` (`agent-enrichment.ts:253-270`) requires that literal, so `scanPendingInputsPromise` (`agent-enrichment.ts:311-393`) now takes the else-branch at `:365-368` and marks the AUQ **answered**. Consequences: `hasPendingQuestion=false` → no AUQ modal (`usePendingInputDialogs.ts`) and no `awaitingInput` → the planning needs-you condition at `pipeline-helpers.ts:68` (which DOES cover planning sessions) never trips. The existing tests (`tests/lib/agent-enrichment-pending-inputs.test.ts:87-113`) hardcode `PAN-1520` into fake deny reasons, so they pass while the real hook no longer emits it — the hook↔detector contract is unguarded.

## Requirements

- **FR-1** — The HappenedFeed "done" line for a section renders only when the session actually ended (terminal signal present), never from elapsed time; for planning sections it additionally requires real planning completion (`plan.status ∈ PLANNING_FINISHED_STATUSES`, resolved via `findSpecByIssue`). A live idle/blocked planning agent renders as in-progress (and "waiting on you" when `awaitingInput`).
- **FR-2** — Activity sections and session-tree nodes carry an explicit terminal-end signal (`endedAt` populated only on true session end, derived from presence/runtime/`state.stoppedAt`) plus `planningComplete: boolean` on planning sections. `duration` semantics are unchanged (additive change; no-loss for existing consumers).
- **FR-3** — The phase banner derives "writing code" from an actual live work session (activity sections `type==='work' && status==='running'`) or in-progress beads — never from `phase === 'pending'`. An issue whose only live agent is a planning session shows the planning headline.
- **FR-4** — The session-trees feature pre-filter qualifies a feature when a planning agent dir (`planning-<issue>` or `agent-<issue>-plan`) exists, or the workspace runtime dir exists under either name (`.pan` or `.overdeck`), or a live tmux session for the issue exists — in addition to the current conditions.
- **FR-5** — Both session builders enumerate `agent-<issue>-plan` as a planning candidate and classify it by `state.role === 'plan'` (not only by the `planning-` name prefix).
- **FR-6** — A tmux-alive `planning-<issue>` session with no readable agent state still yields a planning node (synthesized, presence from tmux).
- **FR-7** — When session-trees yields no sessions for the issue, the cockpit uses the activity-derived sessions instead of rendering an empty tree.
- **FR-8** — The AUQ deny hook again emits the deny marker (`PAN-1520`) in its `permissionDecisionReason`, and the detector additionally recognizes the hook's stable phrase (`surfaced to the operator`) so a future copy-edit cannot silently break classification. Backward compat: old transcripts containing `PAN-1520` keep working.
- **FR-9** — A contract test executes the real hook script and asserts `isAskUserQuestionHookDenyToolResult` returns true on its actual emitted reason; the existing pending-input tests derive their deny fixture from the hook source instead of a hardcoded copy.
- **FR-10** — Docs updated: `docs/ASKUSERQUESTION-DASHBOARD.md` (marker contract, this incident) and `docs/MISSION-CONTROL.md` (what feeds the tree/banner/feed and the completion-gating rules).
- **NFR-1** — All fixes are additive per the no-loss rule: no existing field is removed or repurposed; existing tests keep passing.
- **NFR-2** — Any delay/retry tests use fake timers (`vi.useFakeTimers()`), per repo rule.

## Auto decisions (pan plan --auto)

- **AD-1** Additive fields (`endedAt`, `planningComplete`) instead of changing `duration` semantics — other consumers may render elapsed time; no-loss rule.
- **AD-2** Detector robustness = restore marker AND accept the stable phrase "surfaced to the operator" as a secondary signal — NOT "any is_error tool_result counts as deny" (a genuine AUQ error would then wedge as forever-pending).
- **AD-3** The `agent-pan-2597` tmux session naming quirk (Cloister spawnRun) is covered by FR-5 even though the incident's planner used `planning-<issue>` naming — the gap is real and cheap to close in the same files.
- **AD-4** No backend read-model phase rewrite: `derive-phase.ts` (`src/lib/reconstruct/derive-phase.ts`) is out of scope; the banner fix stays in the frontend derivation it actually uses.

- **H-2** `agent-<issue>-plan` starts with `agent-`, so prefix-based `isPlanning` checks misclassify it as work; classification must consult `state.role`.
- **H-3** The hook is installed into `~/.claude/settings.json` via `pan sync`/install; source changes take effect only after re-provisioning — the contract test must run against the repo source, not the installed copy.
- **H-4** `tests/lib/agent-enrichment-pending-inputs.test.ts` currently gives false confidence (hardcoded marker); refit it as part of item 9, don't just add a new test beside it.
- **H-5** Frontend `fetchCockpitProjectFeature` merge must not regress the deep-link (no projectName) path — `feature` can be null there.
