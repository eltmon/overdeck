# PAN-3138 — Merge-time Docker cleanup leaves workspace devnet behind

## Glossary

- **`_devnet`** — the per-workspace Docker bridge network named
  `<composeProject>-feature-<issue>_devnet` (e.g. `overdeck-feature-pan-3093_default`/
  `..._devnet`). Each one consumes one subnet from Docker's default address pools
  (~31 usable). Exhaustion makes every new workspace spawn fail with
  `all predefined address pools have been fully subnetted`.
- **Teardown primitive** — `teardownWorkspaceDockerByNamePromise(issueIdLower)` in
  `src/lib/workspace-manager/docker.ts:156`. Name-based (does not need the workspace
  directory): `docker compose -p <name> down -v --remove-orphans`, force-removes the
  workspace's own containers, **disconnects** foreign containers (shared infra like
  `overdeck-traefik`) instead of removing them, removes the network, and verifies it
  is gone. Idempotent: an absent network resolves as `networkRemoved: true`
  (test: `src/lib/workspace-manager/__tests__/docker.test.ts:71`).
- **`postMergeLifecycle()`** — merge handoff in `src/lib/cloister/merge-agent.ts:295`.
  Runs once per merge (guarded by `createInFlightGuard`), pauses agents, preserves
  the workspace/state/branches, and currently only **stops** Docker containers.
- **Closed-issue reaper** — deacon patrol `reconcileClosedIssueAgents()` in
  `src/lib/cloister/closed-issue-reaper.ts:168`. Enumerates candidate issues from
  running agents, tmux sessions, workspace dirs, agent state dirs, and leaked
  `_devnet` networks (`listFeatureDevnetIssueIds`, line 39), but gates every action
  on `isIssueClosed` (tracker-closed only).
- **`reapIssueResidue()`** — `src/lib/cloister/reap-issue-residue.ts:19`. Full
  residue teardown (tmux kills, Docker teardown, worktree + branch deletion). The
  Docker step already runs unconditionally inside it; the destructive disk/branch
  steps are gated on the branch being merged.
- **mergeStatus** — review-status field (`getReviewStatusSync(issueId)?.mergeStatus`),
  set to `'merged'` by the merge agent (`src/lib/cloister/merge-agent.ts:347`) after
  the branch/PR is verified landed. Local read door; no tracker call.
- **Verify-on-main** — the window between merge and close-out where the issue is
  `verifying_on_main`. The workspace directory is preserved; nothing in this window
  needs the workspace Docker stack.

## Problem

Verified at code level in the issue body and re-verified during planning:

`teardownWorkspaceDockerByNamePromise()` has exactly two callers —
`src/lib/close-out.ts:365` and `src/lib/cloister/reap-issue-residue.ts:50` (the
latter reachable only for tracker-closed issues via the reaper's `isIssueClosed`
gates). The merge-time path never calls it: `postMergeLifecycle()` step 4
(`src/lib/cloister/merge-agent.ts:533-550`) calls only
`stopWorkspaceDocker(workspacePath, issueLower)`, which stops containers via the
workspace's compose files but never removes the `_devnet` network.

So every merged issue leaks its `_devnet` — with `overdeck-traefik` still attached,
which also defeats a naive `docker network rm` — until close-out runs, which can lag
merge by hours or days. On 2026-07-26 this exhausted the pool: 5 merged-but-not-closed
issues (PAN-1696, PAN-2997, PAN-3037, PAN-3114, PAN-3115) held devnets and blocked
PAN-3093 workspace prep.

Two secondary gaps compound the leak:

1. The reaper's devnet loop (`closed-issue-reaper.ts:224-227`) discovers leaked
   `_devnet` networks every patrol but skips merged-but-not-closed issues, so
   stragglers are never reaped even though the teardown primitive is safe for them.
2. `rebuildWorkspaceStack()` (`src/lib/workspace/rebuild-stack.ts:167`) gates on
   `isIssueClosed` (tracker-closed) only — a merged-but-not-closed issue's stack can
   still be rebuilt by patrols, recreating the network between merge and close-out.
   CLAUDE.md ("postMergeLifecycle Verify Handoff and Docker Cleanup") already claims
   the chokepoint "no-ops for closed/merged issues"; the code only honors "closed".

## Proposal

Three surgical changes, all built on the existing verified teardown primitive:

1. **Merge-time teardown (root fix).** In `postMergeLifecycle()` step 4, after the
   existing `stopWorkspaceDocker` block, call
   `teardownWorkspaceDockerByNamePromise(issueLower)` — unconditionally (not gated
   on `findWorkspacePath` returning a path; the primitive is name-based precisely
   for the case where the workspace dir is already gone), non-fatally (try/catch +
   `console.warn`, matching the surrounding style). Log/activity-log the result.
2. **Reaper backstop for merged issues.** In `reconcileClosedIssueAgents()`'s
   devnet loop, when an issue is not tracker-closed, check
   `getReviewStatusSync(issueId)?.mergeStatus === 'merged'` (via dynamic
   `await import('../review-status.js')` to avoid any import-cycle risk) and, if so,
   run **Docker-network teardown only**: call `teardownWorkspaceDockerByNamePromise`
   directly — never `reapIssueResidue`, no tmux/agent kills, no disk/branch reap.
   The workspace must survive until close-out.
3. **Rebuild gate honors merged.** In `rebuildWorkspaceStack()`, treat
   `mergeStatus === 'merged'` as terminal alongside the existing `isIssueClosed`
   check so patrols cannot recreate a torn-down network before close-out. This
   aligns the code with the invariant CLAUDE.md already documents. Reopen clears
   mergeStatus, so a reopened issue rebuilds normally.

```ts
    try {
      const { findWorkspacePath } = await import('../lifecycle/archive-planning.js');
      const { stopWorkspaceDocker } = await import('../workspace-manager.js');
      const { teardownWorkspaceDockerByNamePromise } = await import('../workspace-manager/docker.js');
      const issueLower = issueId.toLowerCase();
      const workspacePath = findWorkspacePath(projectPath, issueLower);
      if (workspacePath) {
        const dockerResult = await Effect.runPromise(stopWorkspaceDocker(workspacePath, issueLower));
        if (dockerResult.containersFound) { /* existing log */ }
      }
      // PAN-3138: remove the network too — stopping containers alone leaks the
      // _devnet subnet until close-out. Name-based: runs even when the workspace
      // dir is gone. Idempotent; disconnects shared sidecars, never removes them.
      const teardown = await teardownWorkspaceDockerByNamePromise(issueLower);
      if (teardown.networkRemoved) {
        console.log(`[merge-agent] ✓ Removed Docker network for ${issueId}: ${teardown.steps.join('; ')}`);
        logActivity('docker_cleanup', `Removed Docker stack for ${issueId}: ${teardown.steps.join('; ')}`);
      }
    } catch (err) {
      console.warn(`[merge-agent] Docker cleanup failed (non-fatal): ${err}`);
    }
```

## Requirements

### Functional

- FR-1: `postMergeLifecycle()` removes the workspace `_devnet` network (and any
  remaining workspace containers) at merge time by calling
  `teardownWorkspaceDockerByNamePromise(issueLower)`, even when the workspace
  directory no longer exists.
- FR-2: A failure of the merge-time teardown is non-fatal — it logs a warning and
  never blocks or fails the merge handoff (`_completedPostMerge` still marks).
- FR-3: The deacon's `reconcileClosedIssueAgents()` patrol tears down the
  `_devnet` of a merged-but-not-closed issue (Docker-network step only) within one
  patrol cycle of discovery, without stopping agents, killing tmux sessions, or
  touching the workspace dir or branch.
- FR-4: The shared `overdeck-traefik` container is disconnected from the removed
  network, never removed, and remains running throughout (existing primitive
  behavior — locked by `docker.test.ts:174`; the new call sites must not weaken it).
- FR-5: `rebuildWorkspaceStack()` refuses to rebuild the stack of an issue whose
  `mergeStatus === 'merged'`, returning the existing terminal-error shape.

### Non-functional

- NFR-1: No new sync exec in server-reachable code; all new calls go through the
  existing async primitive.
- NFR-2: No new tracker API calls per patrol cycle — merged eligibility is read
  from the local review-status door (`getReviewStatusSync`).
- NFR-3: Documentation updated in the same change (see work item 4).

## Decisions (auto mode)

- D1: Implement BOTH proposed fixes from the issue (merge-time call + reaper
  backstop) rather than either/or. The issue says "alternatively/additionally";
  the merge-time call is the root fix and the reaper extension is the backstop for
  already-leaked networks and non-fatal merge-time failures, matching the repo's
  reaper-as-backstop doctrine.
- D2: Issue AC3 ("demonstrated by a regression test or scripted repro that fills
  the pool") is satisfied by unit-level regression tests with a mocked Docker CLI,
  not a live pool-fill repro. Filling the host's real address pool is destructive
  to concurrent workspaces and not CI-safe; the leak mechanism was already
  demonstrated live in the issue, and the regression surface is "both call sites
  invoke the verified teardown primitive."
- D3: The reaper reads merged eligibility from `getReviewStatusSync` (local door)
  via dynamic import — no tracker calls per patrol, no static import-cycle risk.
- D4: Add the rebuild-gate hardening (work item 3) even though the issue didn't
  ask for it: CLAUDE.md already claims the chokepoint no-ops for merged issues,
  and without it a patrol can recreate a network the merge-time teardown just
  removed. Small, same-file, same-guard change.

## Hazards

- H1: The teardown primitive runs `docker compose down -v` — workspace container
  **volumes** are destroyed at merge time rather than at close-out. Acceptable:
  postMergeLifecycle already stops the containers, nothing post-merge reads
  workspace volumes (verify-on-main runs on main), and close-out would do the
  same `down -v` later anyway.
- H2: `closed-issue-reaper.ts` statically importing `review-status.js` risks an
  import cycle (review-status is a large module with many imports). Mitigation:
  use dynamic `await import('../review-status.js')` inside the loop, as shown.
- H3: `listFeatureDevnetIssueIds` extracts issue ids from any project prefix
  (`myn-feature-min-729_devnet` etc.). `getReviewStatusSync` returns null for
  issues with no local review-status row → no teardown. Correct: we only reap
  merged issues this host knows about.
- H4: The new merge-time teardown must stay OUTSIDE the `if (workspacePath)` gate
  — the leaked-network case is exactly the one where the workspace dir may be
  gone.
- H5: A merged issue whose close-out is legitimately pending verify-on-main loses
  its workspace stack — intended. If the merge is reverted / issue reopened,
  `pan reopen` resets mergeStatus and the stack rebuilds on demand.
