## Glossary

Define these before use; the executor must not infer them.

| Term | Meaning |
| --- | --- |
| **Harness** | The coding-agent CLI Overdeck drives to do work. The writable union today is `'claude-code' \| 'ohmypi' \| 'codex' \| 'acp'` (`packages/contracts/src/types.ts:87`). This PRD adds `'kimi-code'`. |
| **Kimi Code CLI** | Moonshot AI's own terminal coding agent. Binary **`kimi`** (npm `@kimi-code/cli`, Node ≥ 22.19, or install script). MIT-licensed, TypeScript, interactive TUI with a headless `--print` mode. Home dir `~/.kimi-code` (relocatable via `KIMI_CODE_HOME`). |
| **`acp` harness (existing)** | The in-tree harness that drives the **same `kimi` binary** through its Agent Client Protocol host (`kimi acp`). Its binary is already `kimi` (`src/lib/harness-binary.ts:18`), it is Kimi-only gated in policy, and its `processNames` already include `'kimi'`. This is the "Kimi through ACP" path the operator scoped **out** of this issue. |
| **`kimi-code` harness (this PRD)** | A new, coexisting harness that drives Kimi Code's **native** interface directly — launch `kimi` in a tmux session, deliver via tmux paste, read the native transcript at `~/.kimi-code/sessions/<workDirKey>/<sessionId>/agents/main/wire.jsonl`. No ACP, no JSON-RPC host. |
| **RuntimeName** | Runtime-side alias of `Harness` (`src/lib/runtimes/types.ts:44`; re-derived as `type RuntimeName = Harness` in `packages/contracts/src/harness-behavior.ts:3`). |
| **Behavior matrix** | `packages/contracts/src/harness-behavior.ts`. A `HarnessBehavior` record per harness carrying discriminant fields (`launchCommandKind`, `deliveryKind`, `readinessKind`, `transcriptKind`, `sessionIdSource`, `contextLayerKind`, `feedKind`, `executableName`, `processNames`, …). **Almost nothing in the codebase switches on the raw harness string; consumers switch on these `*Kind` discriminants.** Adding a harness = add a union member + a behavior entry + an adapter + register it, then handle each `*Kind` branch. |
| **Adapter** | An `AgentRuntimeSync` implementation under `src/lib/runtimes/` (`claude-code.ts`, `codex.ts`, `pi.ts`/`ohmypi.ts`, `acp.ts`). Owns spawn, delivery, readiness, session/transcript resolution, health, cost, kill. |
| **`workDirKey`** | Kimi Code's per-working-directory session bucket name: `wd_<slug>_<first-12-chars-of-sha256(workDir)>` (from Kimi's data-locations doc). We avoid reproducing this algorithm by resolving the transcript with a glob on the known `<sessionId>` (see WI-8). |
| **Deterministic session id** | Kimi's `kimi --session <ID>` "resumes that session, **creates new if not found**." We pass Overdeck's own `agentId` as `<ID>`, so the on-disk session directory name is known up front — the same model as `claude-code`'s `launcher-session-id`. |

## Vision

Moonshot ships Kimi Code, its own Claude-Code-class terminal agent. Today Overdeck can only run
Kimi models either through `claude-code` pointed at Kimi's Anthropic-compatible endpoint
(`src/lib/providers.ts:74-90`) or through the `acp` harness (ACP bridge). Neither runs Kimi's
**native** agent loop. `kimi-code` closes that gap: Kimi models run on Moonshot's own harness,
end-to-end, as a first-class Overdeck harness selectable anywhere `codex`/`ohmypi`/`acp` are —
work agents, plan/review/test roles, and the conversation panel — with correct branding, policy
gating, transcript resolution, and cost.

This is a complete feature, not a stub. Per the project no-partial-implementations rule, "done"
means Kimi Code runs a work agent to completion **and** every cross-cutting surface (pickers,
branding, policy decisions, prerequisites, context layers, skills, transcript, cost, health)
knows about `kimi-code`. See Acceptance Criteria.

## Coexistence: `kimi-code` (direct) vs `acp` (ACP) — the central design decision

**Both harnesses target the `kimi` binary and coexist. They are not the same harness.**

- `acp` drives `kimi acp` (the Agent Client Protocol JSON-RPC host). Delivery `acp-host-rpc`,
  readiness `acp-host-ready`, transcript `acp-jsonl` (a normalized transcript the ACP host writes
  to `~/.overdeck/agents/<id>/acp-session.jsonl`). Policy: Kimi-provider-only
  (`ACP_KIMI_ONLY_BLOCK`, `src/lib/harness-policy.ts:47-52,96-98`).
- `kimi-code` (this PRD) drives the **native** `kimi` TUI. Delivery `tmux-paste`, readiness
  `kimi-session-signal` (native session dir appears), transcript `kimi-wire-jsonl` (Kimi's own
  `~/.kimi-code/sessions/.../agents/main/wire.jsonl`).

**Do not delete, merge, or repurpose `acp`.** It stays exactly as-is; "Kimi through ACP" is
tracked by its own issue. This PRD only *adds* `kimi-code`. Where a decision must distinguish the
two (policy, prerequisites, env), the rules below name each explicitly.

**Caching — both `acp` and `kimi-code` capture it; `claude-code` does not (fully). This is the
motivation for the whole issue.** Moonshot's context caching is server-side ($0.30/M cached vs
$3/M miss, ~90% hit in coding). Realizing it needs *cache discipline* in the agent core — stable
prefixes, preserved thinking across turns, and no mid-session model switch (K3's Kimi Delta
Attention makes prefix caching fragile). `acp` drives the real `kimi acp` binary (verified:
`src/lib/acp/kimi.ts:35-36` spawns `command:'kimi', args:['acp']`) against Moonshot's endpoint via
`kimi login`, one persistent session per agent — so Kimi's own discipline applies and caching
works today. Native `kimi-code` is identical on caching (same binary/agent core) and additionally
speaks Kimi's *native* endpoint/protocol instead of the Anthropic-compatibility shim, so it can
reach Kimi-specific levers the shim can't. The prior `claude-code`→`api.kimi.com/coding` path
speaks Anthropic's Messages surface through a compatibility translation and does not replicate the
discipline — it is the one path that leaves cache hits on the table.

**Which is the default? Two-phase (see WI-7.1).** `acp` is the pragmatic default *now* via the
operator override `providerHarnesses.kimi: 'acp'` — caching today, no code change. `kimi-code`
becomes the shipped default once proven, because native is a *capability* layer (reaches
Kimi-specific/future features) while ACP is a generic *portability* layer (lowest-common-
denominator across editors). The two are at parity on caching; native wins on capability headroom.

## Kimi Code CLI — verified facts the adapter depends on

Researched from Moonshot's official docs (`kimi.com/code/docs`, `moonshotai.github.io/kimi-cli`)
and the `MoonshotAI/kimi-code` repo on 2026-07-27. Restated here so the executor needs no
re-research. Anything marked **[checkpoint]** must be confirmed live against the installed binary
before/while building (fallback stated inline).

- **Binary / install:** `kimi`. npm `@kimi-code/cli` (Node ≥ 22.19), or
  `curl -fsSL https://code.kimi.com/kimi-code/install.sh | bash`. Already registered as a
  prerequisite (`src/lib/system-prerequisites.ts:169-180`, id `kimi`, name "Kimi Code CLI").
- **Auth:** `kimi login` (browser OAuth device-code) or a Moonshot API key in
  `~/.kimi-code/config.toml`; credentials stored under `~/.kimi-code/credentials/`. **Auth is
  host-owned** — the operator runs `kimi login` once on the host, exactly like `codex login`.
  Overdeck does not mint or inject a Kimi token for this harness (contrast the `claude-code`+kimi
  path, which injects `ANTHROPIC_BASE_URL`/`KIMI_API_KEY` — that shim must NOT be applied to
  `kimi-code`; see WI-7).
- **Headless (verified 0.29.2):** `kimi -p/--prompt "<text>" --output-format text|stream-json`
  (the docs' `--print` name was ahead of the binary). Cannot be combined with `--auto`. Not used
  for interactive work agents in v1; reserved for future one-shot roles.
- **Interactive launch flags (verified 0.29.2):** `-m/--model <name>`, `--add-dir <path>`,
  `-S/--session [id]` (resumes an EXISTING session or opens a picker — does NOT create for an
  arbitrary id; `-S probe1` errors `Session "probe1" not found`), `-c/--continue` (resume the
  previous session for the cwd), `-y/--yolo` (auto-approve tool calls), `--auto` (fully
  autonomous). **There is no `--work-dir`/`-w`** — the working directory is the process cwd, so
  the launcher must `cd` into the workspace.
- **Binary is at `~/.kimi-code/bin/kimi`** (install-script default) and is NOT on PATH nor in the
  resolver's fixed-candidate dirs — configure `acp.kimi.binaryPath` / a new `kimiCode.binaryPath`,
  or add `~/.kimi-code/bin` to PATH.
- **Session/transcript layout** (`$KIMI_CODE_HOME` default `~/.kimi-code`):
  ```
  ~/.kimi-code/
  ├── config.toml
  ├── credentials/<name>.json
  ├── session_index.jsonl                      # index of all sessions
  └── sessions/<workDirKey>/<sessionId>/
      ├── state.json                           # title, timestamps, forkedFrom
      ├── agents/main/wire.jsonl               # ← the main-agent transcript (event stream)
      ├── agents/main/plans/
      ├── agents/agent-0/…/wire.jsonl          # sub-agents
      └── logs/kimi-code.log
  ```
  `workDirKey = wd_<slug>_<sha256(workDir)[:12]>`. `kimi export <id>` zips a session dir.
- **[RESOLVED — verified 0.29.2] Session id is NOT presettable.** `-S <id>` errors
  `Session "<id>" not found` when the id doesn't exist — Overdeck cannot hand Kimi a chosen id.
  Kimi generates its own `session_<uuid>` under `sessions/<workDirKey>/<sessionId>/`, where
  `workDirKey = wd_<basename>_<sha256(workDir)[:12]>` (confirmed: a probe in `.../kimi-cache-probe2`
  produced `wd_kimi-cache-probe2_a54219d88647`). **So the launcher passes no session id**; the
  adapter captures Kimi's generated id **after** launch by taking the newest session dir under the
  workspace's `workDirKey` by mtime (the pattern `codex.ts` uses for its thread-id), then persists
  it per-agent for stable transcript resolution.
- **[verified 0.29.2] `wire.jsonl` usage fields:** token/cache accounting is present as
  `inputCacheRead`, `inputCacheCreation`, and `maxTokens` — a two-turn probe showed cache reads of
  17,920 then 26,112, proving caching. Pin a real `wire.jsonl` fixture and map the full per-line
  record shape (roles, tool calls) before finalizing the parser (WI-8).

## Requirements

**Functional**

- **FR-1** `'kimi-code'` is a member of the canonical `Harness` union and passes `getHarness()`
  normalization (not silently coerced to `claude-code`).
- **FR-2** A `KIMI_CODE_BEHAVIOR` entry exists in the behavior matrix with correct discriminants,
  and `getHarnessBehavior`/`getRuntimeBehavior` return it.
- **FR-3** `harnessBinaryName('kimi-code') === 'kimi'`; `requireHarnessBinary` names it
  "Kimi Code CLI" on failure; a configured binary path is honored.
- **FR-4** The policy gate allows `kimi-code` only for the Kimi provider (mirroring `acp`), and
  the policy-decisions map served to pickers includes a `kimi-code` key for every model.
- **FR-5** A `kimi-code` adapter implements the full `AgentRuntimeSync` contract and is registered;
  `getRuntimeForAgent` dispatches `harness === 'kimi-code'` to it.
- **FR-6** The launcher generates a correct native `kimi` invocation for work and role spawns.
- **FR-7** The transcript resolver returns the native `wire.jsonl` for a `kimi-code` agent, and a
  parser normalizes it into Overdeck's transcript/cost model.
- **FR-8** `kimi-code` appears in every harness picker (composer + Settings), with a brand entry
  (label, color, icon).
- **FR-9** Context-layer templating and `pan sync` skill fan-out recognize `kimi-code`.
- **FR-10** Selecting `kimi-code` with a Kimi model runs a work agent to `pan done`, with a live
  transcript, cost, and health, without falling back to another harness.

**Non-functional**

- **NFR-1** Zero regression to `claude-code`, `codex`, `ohmypi`, and especially `acp` — verified
  by the existing runtime/registry/policy suites staying green.
- **NFR-2** No hardcoded model fallback and no silent harness fallback: an unsupported
  `{kimi-code, non-Kimi model}` selection is blocked with a clear reason, never coerced.
- **NFR-3** All new tmux delivery uses async primitives only (`sendKeysAsync`, `load-buffer` +
  `paste-buffer`); no `sendKeys`/`execSync` (async-tmux + no-execSync rules).
- **NFR-4** The `kimi` binary is resolved through the existing resolver (PATH + `~/.local/bin` +
  npm/bun prefixes + login shell), never assumed on `$PATH`.

## Launch & delivery model (the design the work items implement)

A `kimi-code` **work agent**:

1. **Launch** an interactive `kimi` in the agent's tmux session (socket `-L overdeck`), **cd'd into
   the workspace** (there is no `--work-dir`): `cd <workspace> && kimi -m <kimiModel> --yolo` — no
   preset session id (Kimi generates its own). `--yolo` gives the unattended autonomy a work agent
   needs; configurable. Binary resolved via `prepareHarnessLaunch('kimi-code')` or the configured
   `kimiCode.binaryPath` (it installs to `~/.kimi-code/bin`, not on PATH).
2. **Readiness** (`kimi-session-signal`): poll for a new
   `sessions/<workDirKey>/<sessionId>/agents/main/wire.jsonl` under the workspace's `workDirKey`
   bucket, bounded by `readyTimeoutSeconds`.
3. **Kickoff + follow-up delivery** (`deliveryKind: 'pty-supervisor'`) — mirror `claude-code`.
   Launch `kimi` under the PTY supervisor (`node <projectRoot>/dist/pty-supervisor.js kimi
   --session <agentId> …`). The supervisor owns Kimi's PTY master fd; the kickoff prompt and every
   `adapter.sendMessage` are written as text + newline into Kimi's stdin, and echo into the tmux
   transcript. Kimi Code is a stdin-driven TUI with the same "Enter submits, Ctrl-J for newline"
   model as Claude, so this is the exact path `claude-code` uses — no new delivery machinery.
   **[checkpoint]** confirm Kimi's TUI accepts supervisor-written stdin; **fallback** =
   `deliveryKind: 'tmux-paste'` via `sendKeysAsync` (`load-buffer` → `paste-buffer` → 300ms →
   `send-keys C-m`). H1 lifecycle applies: if the supervisor exits, `kimi` exits with it and the
   session resumes through the normal Deacon/dashboard flow (same as claude-code).
5. **Transcript** (`kimi-wire-jsonl`): `sessions/<workDirKey>/<capturedSessionId>/agents/main/wire.jsonl`;
   a parser normalizes it for the feed and cost (usage via `inputCacheRead`/`inputCacheCreation`).
6. **Session id source** (post-launch capture): Kimi's generated `session_<uuid>`, captured by
   resolving the newest session dir under the workspace's `workDirKey` after ready, then persisted
   per-agent (like codex's thread-id) so transcript resolution stays stable.

Conversation-panel (interactive chat) sessions reuse the same adapter and transcript path; the
feed renders from the normalized `wire.jsonl` (WI-8).

## Architecture — what a new harness must touch

Two classes of edit. **Compiler-enforced** (a `Record<RuntimeName|Harness, …>` won't compile
without the new key): `HARNESS_BINARY_BY_RUNTIME`, `BEHAVIORS`, `HARNESS_MARKERS`,
`HARNESS_LABELS`, `HARNESS_BRANDS`. **Not compiler-caught** (must be found by hand — enumerated in
the work items): the `KNOWN_HARNESSES` set + `getHarness`, the `getRuntimeForAgent` switch, the
registry `register()` calls, `getHarnessBehavior` switch, the `harness-policy.ts` `if` ladder,
`harness-policy-decisions.ts` hardcoded keys, every inline `=== 'ohmypi' || === 'codex' || …`
membership check, the launcher `buildCommand` dispatch, `SKILL_SYNC_HARNESSES`, the frontend
`HARNESS_OPTIONS`/`HARNESSES` arrays, `system-prerequisites`, and the `sync.ts` context-layer
render blocks.

## Hazards & intersecting rules

- **`acp` is not `kimi-code`.** Same binary, different harness. Never merge, delete, or re-point
  `acp`. Its Kimi-only policy, `acp-jsonl` transcript, and RPC delivery are untouched.
- **Silent coercion (`getHarness`).** The single most likely bug: a missed hand-maintained
  validator (WI-1 list) makes a kimi-code agent run as Claude with no error. The
  membership-check enumeration in WI-1 is exhaustive against the tree at authoring time; re-grep
  `=== 'acp'` before finalizing to catch any drift.
- **No hardcoded/silent fallback (NFR-2).** `harness-resolve.ts` fail-loud logic (100-135) refuses
  to silently drop non-`claude-code` built-ins to claude-code; ensure `kimi-code` inherits that
  refusal, not a fallback.
- **Delivery = PTY supervisor (NFR-3).** Primary delivery mirrors `claude-code` (the supervisor
  owns Kimi's PTY master fd; H1 lifecycle applies). The tmux-paste fallback, if it's needed, must
  use async primitives only (`sendKeysAsync` + `load-buffer`/`paste-buffer`, 300ms-before-Enter);
  never `sendKeys` or `execSync`.
- **Auth-env leakage (WI-7).** The Kimi Anthropic-compat shim (`ANTHROPIC_BASE_URL`,
  `KIMI_API_KEY`) is correct for `claude-code`+kimi and *wrong* for native `kimi-code`. Gate it.
- **Two live [checkpoint]s** (both with fallbacks stated inline): (a) does `kimi --session <id>`
  accept our chosen id verbatim; (b) the `wire.jsonl` record schema for the parser. Pin a real
  session fixture before writing the resolver/parser.
- **Behavior-matrix completeness.** Any consumer that switches on a `*Kind` you did not extend will
  hit its `else`/default branch and mis-handle kimi-code. WI-2 adds the discriminants; WI-6/WI-8
  add the branches that read them.
