# PAN-3344 — CPU-saturation admission: close the agent-shell test-run gap and add a CPU dimension to the governor

**Issue:** https://github.com/eltmon/overdeck/issues/3344
**Status:** draft
**Author:** conversation (Fable), 2026-07-31
**Landed mitigation already on main:** `d9656e37bf` capped the frontend vitest threads pool at 4 local / 2 CI workers (was defaulting to CPU count ≈ 24 threads per run).

---

## Glossary

Define once, used throughout:

- **Governor** — the deacon's autonomous admission controller in `src/lib/cloister/memory-governor.ts`. It runs a three-mode hysteresis state machine (`admitting` → `holding` → `shedding`) over memory signals and publishes a cached **verdict** consumed by dispatch/resume paths.
- **Verdict** — the `MemoryVerdict` object (`src/lib/cloister/memory-verdict-cache.ts:21`) published by `assessMemoryPressure()`: a `band` (`'ok' | 'soft' | 'hard'`) plus the raw signals. `band !== 'ok'` means "defer new admissions".
- **Runway** — the governor's secondary signals beyond MemAvailable: swap-free percent and memory PSI, evaluated in `nextGovernorModeWithRunway()` (`src/lib/cloister/memory-governor.ts:124`). This PRD adds CPU saturation as a third runway signal.
- **Quality-gate admission** — the existing cross-process FIFO + single-owner lease in `src/lib/cloister/quality-gate-admission.ts` that serializes verification-runner quality gates machine-wide and admits the queue head only when sampled CPU utilization < 75% **and** 1-minute load < 1.0 per core. State lives in `${OVERDECK_HOME}/verification-workers/admission/`.
- **Agent-shell test run** — a `vitest run` / `npm test` invocation an agent (work/strike/conversation) executes directly from its own Bash tool in a workspace. These do **not** go through `runQualityGates()` and therefore bypass quality-gate admission today.
- **load-per-core** — `os.loadavg()[0] / os.cpus().length`. 1.0 means the run queue exactly fills the cores; 2.0 means the box is 2× oversubscribed.
- **Fail-open** — when a throttling mechanism cannot decide in time, it lets the work proceed (with a warning) rather than blocking it forever. Admission is an optimizer, not a correctness gate.

## Background — the 2026-07-30 incident, corrected diagnosis

Load average hit ~48 on 24 cores while memory stayed healthy (~8 GB free; the memory governor never engaged). ~76 node processes consumed ~15 cores. The original issue text claimed "nothing considers CPU" — research shows that is **wrong in three places and right in two**:

**CPU gating that already exists (do not rebuild):**

1. **Quality-gate admission** (`src/lib/cloister/quality-gate-admission.ts`, wired in `runQualityGates()` at `src/lib/cloister/validation.ts:576`): every local verification gate queues in a FIFO and runs one-at-a-time machine-wide, admitted only under `QUALITY_GATE_CPU_START_THRESHOLD = 0.75` utilization and `QUALITY_GATE_LOAD_PER_CORE_START_THRESHOLD = 1` (`quality-gate-admission.ts:7-8`).
2. **Resume load gates**: `RESUME_LOAD_FACTOR = 1.5` (`src/lib/cloister/deacon-auto-resume.ts:600`) blocks deacon auto-resume when `load1 > cores × 1.5`, at `deacon-auto-resume.ts:773-783` (reactive resume), `deacon-auto-resume.ts:889-897` (patrol resume), and `boot-reconciliation-apply.ts:97-112` (boot recovery).

**CPU gaps that let the storm happen (this PRD's scope):**

3. **Agent-shell test runs bypass admission entirely.** The July 30 load came from strike agents running `vitest run … && npm --prefix ./src/dashboard/frontend run test …` from their own shells (observed live: 3+ concurrent full-suite runs across `feature-pan-3339-strike`, `feature-pan-3327-strike`, and a `pan-3328-strike` scratchpad checkout). Nothing queues or throttles these.
4. **The governor verdict has no CPU dimension**, so every cached-verdict consumer is CPU-blind: `canDispatchAdvancing()` (`src/lib/cloister/concurrency.ts:234-241`, gates review/test dispatch), `resumeYieldedAgents()` (`src/lib/cloister/preemption.ts:253`), and `memoryDrivenWorkSlots()` (`concurrency.ts:198`). Review/test specialists dispatch freely into a CPU-saturated box.
5. (Fixed) The frontend vitest pool was unbounded — landed as `d9656e37bf`.

## Decisions (made here, not left to the implementer)

- **D-1: CPU saturation maps to `holding` only, never `shedding`.** CPU overload self-heals as suites finish; killing or pausing running work wastes completed compute. Only memory signals may shed.
- **D-2: Signal is load-per-core from `os.loadavg()`, not CPU PSI.** Three existing sites already use loadavg (consistency), it works on Linux and darwin (`readProcMemoryDarwin()` returns `psiFullAvg10: null` — PSI is Linux-only), and `/proc/pressure/cpu` `full` is always 0 for CPU by kernel design, so PSI would need a new `some`-line parser for one platform. Not worth it.
- **D-3: Governor CPU thresholds sit above the quality-gate admission threshold.** Admission throttles test runs at 1.0 load-per-core; the governor defers *agent* admissions only under sustained saturation: soft = 1.5, recovery = 1.0. Note the inverted sense vs. memory reserves: for CPU, *lower* is healthier, so recovery (1.0) < soft (1.5). Config validation must enforce `recovery < soft`.
- **D-4: The `RESUME_LOAD_FACTOR` checks stay unchanged.** They are stateless point-in-time checks at the moment of resume with the same 1.5 factor; the governor adds hysteresis (no flapping) and covers the dispatch paths the point checks miss. Removing them would be churn with no benefit; keep both as defense in depth.
- **D-5: Agent-shell runs are brought under the existing admission door at the vitest layer** via `globalSetup`, not via Bash hooks or agent prompts. A config-level mechanism covers every invoker (agent shell, verification worker, human, CI-local) on every rebased branch with zero prompt compliance required.
- **D-6: Reentrancy via environment variable.** `runQualityGates()` already holds the admission lease when its gate command spawns vitest; without a marker the child would queue behind its own parent forever (deadlock until the 25-minute stale reclaim). The lease holder exports `OVERDECK_GATE_ADMITTED=1`; the vitest client skips acquisition when it is set.
- **D-7: The vitest client fails open after 30 minutes** and on any admission-protocol error. Tests must always be able to run; a wedged admission dir must never brick every suite on the machine. Escape hatch for humans: `OVERDECK_GATE_ADMISSION=0` skips the client entirely. CI (`process.env.CI`) also skips — runners have no cross-process contention and no `~/.overdeck`.
- **D-8: eslint/tsc agent-shell runs are out of scope.** They are single-process (no worker fan-out); vitest is the multiplier (4 forks root + 4 threads frontend per run). If they show up in a future storm, they can adopt the same client.
- **D-9: No `nice`/`renice` work item.** With suite runs serialized through one lease, at most one suite's ~8 workers run at a time on a 24-core box; scheduler-priority tuning adds cross-platform complexity for negligible residual benefit. (This drops the `nice -n 10` idea from the original issue text.)

## Requirements

### Functional

- **FR-1:** `assessMemoryPressure()` evaluates CPU saturation (load-per-core) as a runway signal: when `previousMode === 'admitting'`, load-per-core ≥ soft threshold forces at least `holding`; when previously `holding`/`shedding`, the mode cannot return to `admitting` until load-per-core < recovery threshold (hysteresis, mirroring the swap-runway shape).
- **FR-2:** CPU saturation never produces `shedding`; only memory/PSI signals may. (D-1)
- **FR-3:** The runway restructure removes the `swapTotalBytes <= 0` early return (`memory-governor.ts:132`) so CPU is evaluated on swapless boxes; swap logic itself remains gated on `swapTotalBytes > 0` with unchanged behavior.
- **FR-4:** New config keys with defaults, snake_case user keys and camelCase resolved keys, following the existing governor key pattern (`schema.ts:402-419`, `schema.ts:897-908`, `defaults.ts:205-215`): `governor_cpu_soft_load_per_core` (default **1.5**) and `governor_cpu_recovery_load_per_core` (default **1.0**); config validation rejects `recovery >= soft`.
- **FR-5:** The verdict carries the sampled `loadPerCore` (nullable), and the three governor-defer log sites that print `availMB` (`deacon-auto-resume.ts:781`, `deacon-auto-resume.ts:894` block, `boot-reconciliation-apply.ts:106` block, `preemption.ts:255` block) include `loadPerCore` so a CPU-caused hold is distinguishable from a memory hold in `deacon.log`.
- **FR-6:** While `runQualityGates()` holds an admission lease, the gate subprocess environment contains `OVERDECK_GATE_ADMITTED=1`.
- **FR-7:** `acquireQualityGateAdmission()` accepts an optional `maxWaitMs`; on expiry it removes its own waiter ticket and throws a typed `QualityGateAdmissionTimeoutError`. Callers that pass nothing keep today's wait-forever behavior.
- **FR-8:** Every root-suite and frontend-suite vitest invocation acquires quality-gate admission in `globalSetup` and releases it in teardown, except when `OVERDECK_GATE_ADMITTED=1`, `OVERDECK_GATE_ADMISSION=0`, or `CI` is set. On timeout (30 min) or protocol error it proceeds with a one-line warning to stderr. (D-5/D-6/D-7)

### Non-functional

- **NFR-1:** No new synchronous child-process or blocking I/O on any server-reachable path (repo rule: no `execSync` in dashboard-reachable code). `os.loadavg()`/`os.cpus()` are in-memory syscalls and fine.
- **NFR-2:** All new delay/poll/timeout tests use `vi.useFakeTimers()` + `advanceTimersByTimeAsync` or the module's injectable `sleep`/`now` deps (repo rule: fake timers for retry/backoff/delay tests). `quality-gate-admission.ts` already exposes `deps.now/sleep/pollMs` for exactly this; `tests/unit/lib/cloister/quality-gate-admission.test.ts` shows the pattern.
- **NFR-3:** darwin keeps working: `loadavg()` is available; no `/proc` reads added outside the existing Linux branch.
- **NFR-4:** No import cycles: `memory-verdict-cache.ts` must keep zero imports (its header explains the `concurrency.ts` cycle it prevents); the vitest client must not pull dashboard-server modules into vitest setup (it imports only `quality-gate-admission.ts`, whose only project import is `../paths.js` — `node:os`/`node:fs`/`node:path` otherwise).
- **NFR-5:** Behavior of `evaluateSpawnGuardrails`' HTTP-path predicate `classifyMemoryPressure()` (`memory-governor.ts:40`) is untouched — its header explicitly pins it.

     swapTotalBytes: number;

2. Restructure `nextGovernorModeWithRunway` (`memory-governor.ts:124-146`). Before (current, search for `swapTotalBytes <= 0`):

   ```ts
   const memoryMode = nextGovernorMode(availableBytes, reserves, previousMode);
   if (runway.swapTotalBytes <= 0) return memoryMode;

   const swapSoftBytes = ...;
   ...
   if (memoryMode === 'shedding' || psiShed) return 'shedding';
   if (swapLow) return 'holding';
   return memoryMode;
   ```

   After:

   ```ts
   const memoryMode = nextGovernorMode(availableBytes, reserves, previousMode);

   const swapEnabled = runway.swapTotalBytes > 0;
   const swapSoftBytes = runway.swapTotalBytes * runwayThresholds.swapSoftFreePercent / 100;
   const swapRecoveryBytes = runway.swapTotalBytes * runwayThresholds.swapRecoveryFreePercent / 100;
   const swapLow = swapEnabled && (previousMode === 'admitting'
     ? runway.swapFreeBytes < swapSoftBytes
     : runway.swapFreeBytes < swapRecoveryBytes);
   const psiShed = swapLow
     && runway.psiFullAvg10 != null
     && runway.psiFullAvg10 >= runwayThresholds.psiFullShedAvg10;

   // CPU saturation holds admissions but never sheds (PAN-3344): suites and
   // agent turns self-heal as they finish; killing running work wastes it.
   const cpuSaturated = runway.loadPerCore != null && (previousMode === 'admitting'
     ? runway.loadPerCore >= runwayThresholds.cpuSoftLoadPerCore
     : runway.loadPerCore >= runwayThresholds.cpuRecoveryLoadPerCore);

   if (memoryMode === 'shedding' || psiShed) return 'shedding';
   if (swapLow || cpuSaturated) return 'holding';
   return memoryMode;
   ```
