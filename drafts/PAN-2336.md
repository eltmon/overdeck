## Glossary

- **`create-beads.test.ts`** — the test file at `src/lib/vbrief/__tests__/create-beads.test.ts`. Tests `createBeadsFromVBrief()` and related functions from `src/lib/vbrief/beads.ts`. Runs 38 test cases (38/38 pass locally, fails in CI with beads DB errors).
- **`beads.ts`** — `src/lib/vbrief/beads.ts`. At line 9: `import { execFile } from 'child_process';`. At line 10: `import { promisify } from 'util';`. At line 22: `const execFileAsync = promisify(execFile);` — **module-scope capture**: `execFileAsync` is assigned once at module load time and never reassigned.
- **`execFileAsync`** — the module-scope variable in `beads.ts` that all `bd` CLI calls flow through. Every `bd ping`, `bd list`, `bd create`, `bd delete`, `bd init`, `bd doctor`, `bd dep` call uses `await execFileAsync(...)`.
- **`mockExecAsync`** — the `vi.fn()` defined via `vi.hoisted()` at the top of the test file. All test expectations are set on this mock.
- **Module-scope capture problem** — when `beads.ts` is already in vitest's module registry (loaded by a previous test file in the same worker or by a `setupFiles` entry), `execFileAsync` holds `realPromisify(realExecFile)`. The test file's `vi.mock('util', ...)` replaces `promisify` in the registry but cannot retroactively change the already-captured `execFileAsync` variable. As a result, real `bd` binary calls are made.
- **`vi.hoisted()`** — vitest's mechanism for defining variables that are available at `vi.mock()` factory time (before top-level imports). Used in the test to define `mockExecAsync`.
- **`vi.mock('util', ...)` approach** — the current mock strategy: intercept `util.promisify` to return `mockExecAsync` for any call. Works when `beads.ts` is freshly loaded; fails when `beads.ts` was pre-loaded with a real `promisify`.
- **Callback-level mock** — the alternative strategy: mock `child_process.execFile` at the callback-invocation level so that even the real `promisify(execFile)` (which is already captured) calls the mocked `execFile`, which routes to `mockExecAsync`. Works regardless of module load order.
- **`pool: 'forks'` + `setupFiles`** — vitest's config (`vitest.config.ts:20`) uses `pool: 'forks'`. The `setupFiles` (`tests/setup/overdeck-home.ts`, `tests/setup/no-real-home-writes.ts`, `tests/setup.ts`) run inside each fork before test files. If any setup file transitively imports `beads.ts`, `execFileAsync` is captured with the real `execFile` before the test file's mocks apply.

## Problem (verified 2026-07-04)

`src/lib/vbrief/__tests__/create-beads.test.ts` fails in GitHub Actions CI with:
```
[beads] bd ping failed (Error 1146 (HY000): table not found: issues); running bd doctor --fix before retry
[beads] beads probe failed after recovery (Error 1146 (HY000): table not found: issues)
```

These are real `bd` binary errors — the actual `bd ping --json` subprocess ran in CI and hit a missing `issues` table because the CI environment has no initialized beads DB.

**Root cause (verified by code inspection):**

`beads.ts` line 22: `const execFileAsync = promisify(execFile);`

This is a module-scope assignment. If `beads.ts` is in vitest's module registry before the test file's `vi.mock('util', ...)` is processed, `execFileAsync` holds `realPromisify(realExecFile)`. The mock cannot retroactively change it.

The current test mock:
```ts
vi.mock('util', async (importOriginal) => {
  const actual = await importOriginal<typeof import('util')>();
  return { ...actual, promisify: () => mockExecAsync };
});
```

This replaces `util.promisify` in the module registry. But `beads.ts`'s `execFileAsync` was set by calling `promisify(execFile)` at module load time. If `beads.ts` was loaded before the mock, the captured `execFileAsync` is the real function. Calls to `await execFileAsync('bd', ...)` then run the real `bd` binary.

**Why it passes locally and fails in CI:** in local dev, vitest's module cache is warm and the fork's test sequence happens to load `beads.ts` fresh with mocks in place. In CI, the module evaluation order differs (likely due to `setupFiles` transitively importing a module that loads `beads.ts`), or the fork reuses a cached `beads.ts` loaded by a concurrent worker test.

**Impact:** reddened main across 3 consecutive commits (b340db626, add5c0563e, e1f6a0e137) — all docs/skill-only changes that don't touch beads.

## Work items

### W1 — Replace `util.promisify` mock with `child_process.execFile` callback-level mock (FR-1, FR-2)

The key insight: `execFileAsync = promisify(execFile)`. When `execFileAsync('bd', args, opts)` is called, it calls `execFile('bd', args, opts, callback)` and waits for `callback`. If `child_process.execFile` is mocked at the callback level — so that calling `execFile(..., callback)` invokes `mockExecAsync(...)` and then calls `callback` with the result — then even the already-captured `execFileAsync` (which holds `realPromisify(realExecFile)`) routes through the mock. This is because the real `promisify` wraps its argument function (`execFile`), not the already-resolved return value.

**Step 1: Remove the `vi.mock('util', ...)` block.**

Grep anchor (unique block to remove):
```ts
vi.mock('util', async (importOriginal) => {
  const actual = await importOriginal<typeof import('util')>();
  return {
    ...actual,
    promisify: () => mockExecAsync,
  };
});
```

Delete this entire block.

**Step 2: Replace `vi.mock('child_process', ...)` with a callback-level mock.**

Grep anchor (current mock, to be replaced):
```ts
vi.mock('child_process', () => ({
  exec: vi.fn(),
  execFile: vi.fn(),
}));
```

Replace with:
```ts
vi.mock('child_process', () => ({
  exec: vi.fn(),
  // Route execFile calls through mockExecAsync at the callback level.
  // This works even if beads.ts was loaded before this mock applied:
  //   execFileAsync = realPromisify(execFile)
  //   execFileAsync('bd', args, opts) → execFile('bd', args, opts, cb) → mockExecAsync
  execFile: vi.fn((...callArgs: unknown[]) => {
    // execFile signature: (file, args?, options?, callback)
    // The callback is always the last argument.
    const cb = callArgs[callArgs.length - 1] as (
      err: Error | null, stdout: string, stderr: string
    ) => void;
    const file = callArgs[0] as string;
    const args = Array.isArray(callArgs[1]) ? (callArgs[1] as string[]) : [];
    void mockExecAsync(file, args).then(
      (r: { stdout: string; stderr: string }) => cb(null, r.stdout, r.stderr),
      (err: Error) => cb(err, '', ''),
    );
  }),
}));
```

**Step 3: Verify `mockExecAsync` signature compatibility.**

The `mockExecAsync` is a `vi.fn()` with `mockResolvedValue({ stdout: '', stderr: '' })` as default. Individual tests call `mockExecAsync.mockRejectedValueOnce(...)` or `mockExecAsync.mockResolvedValueOnce(...)`. The new callback-level mock calls `mockExecAsync(file, args)` — passing two arguments. The existing test setup calls `mockExecAsync.mockResolvedValueOnce({ stdout: '...', stderr: '' })` without caring about call args. This is compatible — `vi.fn()` match is by call order, not by argument value, unless `mockResolvedValueOnce` is combined with `expect(...).toHaveBeenCalledWith(...)`.

**Step 4: Verify the `mockExecAsync.mock.calls` assertions in the test.**

Grep anchor (assertions that check call args):
```ts
    const initCall = mockExecAsync.mock.calls.find(
```

These assertions check `mockExecAsync.mock.calls` for specific `file`/`args` combinations. With the new mock, `mockExecAsync(file, args)` is called with the `file` string as first arg and `args` array as second. But the EXISTING mock via `vi.mock('util', promisify: () => mockExecAsync)` called `mockExecAsync` with the same args that `execFileAsync` received. The signature is identical — `mockExecAsync(file, argsArray, opts?)` becomes `mockExecAsync(file, argsArray)` (opts stripped, since the callback-level mock only passes `file` and `args`). 

Check every assertion of the form `mockExecAsync.mock.calls.find(([file, args]) => ...)` — verify the args destructuring still works when called as `mockExecAsync(file, args)` (two positional args). If any assertion accesses `opts` (third element), note that opts is now absent; adjust if needed.
