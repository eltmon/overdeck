# PAN-3217 — Make `tracker_unconfigured` reachable for tracker-less projects

## Glossary

- **Membership read door** — `resolvePipelineMembership()` and its gather stage; the only path by which pipeline membership is computed. See `docs/PIPELINE-MEMBERSHIP.md`.
- **Gather** — `gatherProjectLensSignals()` in `src/lib/pipeline-membership-gather.ts`; collects tracker/forge/branch/spec lens signals for one project. Throws `PipelineMembershipUnavailableError` with a typed `reason` when a lens cannot run.
- **Typed reason** — one of `MEMBERSHIP_UNAVAILABLE_REASONS` (`packages/contracts/src/types.ts:15`): `missing_issue_prefix`, `repo_unavailable`, `default_branch_unresolved`, `forge_unavailable`, `tracker_unconfigured`, `gather_failed`. Surfaced verbatim through `GET /api/pipeline/membership?project=<key>` as `{ status: 'unavailable', reason, message }`.
- **Path-only project** — a `projects.yaml` entry carrying `name` and `path` and nothing else: no `issue_prefix`, `linear_team`, `github_repo`, `gitlab_repo`, `rally_project`, or `tracker`. Currently `papers-please` and `puzzdom` on the operator's machine.
- **Prefix check** — the guard `const issuePrefix = getIssuePrefix(project)?.toUpperCase(); if (!issuePrefix) throw … 'missing_issue_prefix'`. `getIssuePrefix` (`src/lib/projects.ts:217-219`) is just `config.issue_prefix`.
- **Tracker resolution** — `resolveProjectTrackerType()` (`src/lib/pipeline-membership-gather.ts:187-197`); infers the tracker from project fields and throws `tracker_unconfigured` when none is present.

## Problem

For a path-only project, `gatherProjectLensSignals()` reports `missing_issue_prefix`. That reason is wrong: the project is not missing *only* a prefix — it has no tracker at all, so there is nothing to query. The accurate, already-declared reason `tracker_unconfigured` exists in the contract and is thrown by `resolveProjectTrackerType()` at `src/lib/pipeline-membership-gather.ts:193-196`, but it is unreachable for these projects because the prefix check runs **before** tracker resolution at both gates:

1. `gatherProjectLensSignals()` entry guard — `src/lib/pipeline-membership-gather.ts:503-509`:

```ts
const issuePrefix = getIssuePrefix(project)?.toUpperCase();
if (!issuePrefix) {
  throw new PipelineMembershipUnavailableError(
    'missing_issue_prefix',
    `Missing issue_prefix for project ${project.name}`,
  );
}
```

2. `listProjectTrackerIssues()` inner guard — `src/lib/pipeline-membership-gather.ts:200-208`: same prefix-first ordering; `resolveProjectTrackerType(project)` is only called at line 208, after the throw.

The cost is misdirection, permanently: the Flywheel must report every `status: unavailable` project as an `investigate` suggestion naming its reason, so every tick these projects generate an item whose stated fix ("add an issue_prefix") would not make them queryable. A permanently-wrong reason string also trains readers to stop reading the reason field.

## Requirements

### Functional

- **FR-1** — A project with no resolvable tracker (path-only) produces `reason: 'tracker_unconfigured'` from `gatherProjectLensSignals()`, with a message naming the project.
- **FR-2** — A project with a resolvable tracker but no `issue_prefix` (e.g. `github_repo` set, prefix absent) still produces `reason: 'missing_issue_prefix'`. The reorder must not mask this case.
- **FR-3** — Fully configured projects (prefix + tracker) gather exactly as before; no behavior change on the happy path.

### Non-functional

- **NFR-1** — `docs/PIPELINE-MEMBERSHIP.md` documents the precedence: no tracker ⇒ `tracker_unconfigured`; tracker present but no prefix ⇒ `missing_issue_prefix`.

## Decision

**Reorder, option 1 of the issue.** Resolve the tracker type before requiring the prefix at both gates. Chosen over option 2 (return empty membership for tracker-less projects) because:

- Option 2 changes `unavailable` → `available-but-empty` semantics and would silently hide a genuine misconfiguration (an operator who *meant* to give the project a tracker and forgot). `tracker_unconfigured` keeps the blind spot visible with an accurate label; the operator can then either configure a tracker or unregister the project.
- Whether registering a path-only project is legitimate at all is an operator policy decision this issue should not bake into the read door.

Option 2, and deleting the two path-only `projects.yaml` entries, are config-hygiene follow-ups outside this issue's scope (see NonGoals).

The reorder is safe because `resolveProjectTrackerType()` already treats "prefix present" as evidence of a tracker (`if (getIssuePrefix(project)) return 'linear'` at `src/lib/pipeline-membership-gather.ts:191`), so for every project where the prefix check currently passes, tracker resolution also succeeds — no currently-working project changes behavior. For a project where the prefix check currently throws, exactly two cases exist: a tracker field is set (resolution succeeds, prefix check still throws `missing_issue_prefix` — FR-2 preserved) or no tracker field is set (resolution throws `tracker_unconfigured` first — FR-1 achieved).

## Work items

### WI-1 — Reorder tracker resolution before the prefix check at both gates

**Files:** `src/lib/pipeline-membership-gather.ts`, `tests/unit/lib/pipeline-membership-gather.test.ts`

In `gatherProjectLensSignals()` (`src/lib/pipeline-membership-gather.ts:499`), call `resolveProjectTrackerType(project)` before the prefix guard:

```ts
// BEFORE (lines 503-509)
const issuePrefix = getIssuePrefix(project)?.toUpperCase();
if (!issuePrefix) {
  throw new PipelineMembershipUnavailableError(
    'missing_issue_prefix',
    `Missing issue_prefix for project ${project.name}`,
  );
}

// AFTER
resolveProjectTrackerType(project); // throws tracker_unconfigured when no tracker exists
const issuePrefix = getIssuePrefix(project)?.toUpperCase();
if (!issuePrefix) {
  throw new PipelineMembershipUnavailableError(
    'missing_issue_prefix',
    `Missing issue_prefix for project ${project.name}`,
  );
}
```

In `listProjectTrackerIssues()` (`src/lib/pipeline-membership-gather.ts:199`), hoist the existing `resolveProjectTrackerType(project)` call above the prefix guard:

```ts
// BEFORE (lines 200-208)
const issuePrefix = getIssuePrefix(project)?.toUpperCase();
if (!issuePrefix) {
  throw new PipelineMembershipUnavailableError(
    'missing_issue_prefix',
    `Missing issue_prefix for project ${project.name}`,
  );
}

const trackerType = resolveProjectTrackerType(project);

// AFTER
const trackerType = resolveProjectTrackerType(project);
const issuePrefix = getIssuePrefix(project)?.toUpperCase();
if (!issuePrefix) {
  throw new PipelineMembershipUnavailableError(
    'missing_issue_prefix',
    `Missing issue_prefix for project ${project.name}`,
  );
}
```

**Tests** — add to `tests/unit/lib/pipeline-membership-gather.test.ts`, next to the existing `'classifies a missing GitHub issue prefix'` test at line 584 (which must keep passing unchanged — it is the FR-2 regression guard):

1. Path-only project ⇒ `gatherProjectLensSignals({ name, path }, deps())` rejects with `{ reason: 'tracker_unconfigured', message: expect.stringContaining(project.name) }`.
2. Tracker-without-prefix project (e.g. `{ name, path, gitlab_repo: 'group/repo' }`, no prefix) ⇒ rejects with `reason: 'missing_issue_prefix'`. This pins FR-2 independently of the GitHub variant so the ordering can't silently swap which reason masks which.

Use the existing `deps()` fixture pattern from the surrounding tests; do not add new mocks.
