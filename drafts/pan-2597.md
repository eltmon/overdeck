# PAN-2597 — Adopt `codex app-server` as the Codex transport

**Issue:** https://github.com/eltmon/overdeck/issues/2597
**Status:** draft
**Author context:** conv-795 incident (2026-07-12) — a large composer paste hard-wedged a Codex conversation's PTY supervisor (~90% kernel-time CPU spin, zero throughput, SIGKILL-only recovery). Root cause is structural: Overdeck delivers messages to Codex by emulating keystrokes into a TUI and screen-scraping for confirmation.

## Glossary

| Term | Meaning |
| --- | --- |
| **Codex TUI** | The interactive terminal UI launched by plain `codex` — what Overdeck runs in a tmux pane today. |
| **`codex app-server`** | Codex CLI subcommand (verified present in `codex-cli 0.144.1`, `[experimental]`) that runs the same agent core as a headless JSON-RPC server: newline-delimited JSON (`{id,method,params}` / `{id,result\|error}` / notifications without `id`) over stdio. No `jsonrpc:"2.0"` field. |
| **thread** | app-server's conversation unit. `thread/start` creates one; `thread/resume {threadId}` reattaches. Thread state persists in `CODEX_HOME` (same store the TUI uses). |

| **server request** | JSON-RPC request FROM app-server TO us (has `method` + `id`): approval prompts (`item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, `item/fileRead/requestApproval`) and `item/tool/requestUserInput`. We reply `{id, result:{decision}}` / `{id, result:{answers}}`. |

| **PTY supervisor** | Today's `dist/pty-supervisor.js` (`src/lib/channels/pty-supervisor.ts`) — node-pty wrapper that types injected messages into the harness TUI and confirms by screen echo. Stays for Claude Code; retired for Codex. |
| **delivery door** | `deliverAgentMessage()` in `src/lib/agents/delivery.ts:177` — the single message-delivery primitive (supervisor socket → channels → tmux paste tiers). |
| **rollout JSONL** | Codex's transcript files: `<CODEX_HOME>/sessions/YYYY/MM/DD/rollout-<uuid>-<threadId>.jsonl`. Overdeck's transcript/cost readers (`src/lib/cost-parsers/codex-parser.ts`, `conversation-reads.ts`) parse these today. |
| **t3code** | Reference implementation at `/home/eltmon/Projects/t3code` — production `codex app-server` integration (`apps/server/src/codexAppServerManager.ts`, 1593 lines). File:line citations below were verified 2026-07-12. |

## Repo rules restated (binding on the executor)

- **Fake timers** (`vi.useFakeTimers()` + `advanceTimersByTimeAsync`) for every timeout/retry test (request timeouts, readiness polls). Never real `setTimeout` waits; never `maxForks: 1`.
- **No `execSync`** in anything reachable from the dashboard server; use `execAsync`/`spawn`.
- **Async tmux primitives only** (`sendKeysAsync`); the load-buffer+paste-buffer+300ms+C-m pattern for any tmux delivery code.
- **Node 22 only** for the host binary (it is spawned by launcher.sh like the PTY supervisor today; the dashboard is untouched at boot).
- **Never hardcode a model fallback** — model always flows from the existing resolution (`spawn.ts` / conversation settings) into `turn/start`; absence is an error, not a default.
- **No-loss audit** gates the TUI-path removal (work item 9): every old affordance must have a named new home before deletion.
- Commit each work item separately on `main` (or land via the pipeline as directed).

## 1. Problem

Codex sessions run the interactive TUI in a tmux pane, wrapped by the PTY supervisor. Every Overdeck→Codex interaction is keystroke emulation + screen scraping:

- **Delivery** (`injectPtyMessage`, `src/lib/channels/pty-supervisor.ts:271-329`): type content into the PTY, wait for the composer to *render* it, confirm via a regex that only knows **Claude Code's** `[Pasted text #N]` placeholder (`:227`). For Codex the confirmation can never match on large pastes → backspace-purge → full rewrite ×2 → throw → tmux paste-buffer fallback stacks a third copy. conv-795: supervisor pegged at ~90% CPU (all system time), 0 bytes written over 10s, only ~157KB of the paste ever reached Codex, SIGKILL required (which kills the session — the supervisor owns the PTY).
- **Approvals** (`conversation-delivery.ts:124-165`): screen-scrape the pane (`parseCodexApprovalPrompt`, `src/lib/agent-input-detection.ts:348-377`), answer by typing a digit.
- **Readiness** (`waitForCodexTuiReady`, `src/lib/agents/runtime-command.ts:270-298`): poll `capturePane` for `›` + status line.
- **Idle/awaiting-input** (`detectAwaitingInputForAgent`, `src/lib/agent-input-detection.ts:277`): 90-line pane capture.

All four are render-speed-coupled and per-harness-format-fragile. `codex app-server` eliminates the class: a message of any size is one field in one `turn/start` request; approvals, readiness, completion, and interruption are structured protocol events.

This is NOT a return to one-shot `codex exec`: app-server is a persistent session with resumable threads — *stronger* lifecycle than the TUI (which cannot survive its supervisor). The bundled rule `sync-sources/rules/no-oneshot-agents.md` was amended accordingly (commit `dfc75a3f44`).

## 2. Architecture decision

**Decision: keep tmux as the process plane; put an Overdeck "app-server host" in the pane instead of the TUI.**

```
BEFORE (codex):  tmux pane → launcher.sh → pty-supervisor.js → codex (TUI)
AFTER  (codex):  tmux pane → launcher.sh → codex-app-server-host.js → codex app-server (JSON-RPC stdio)
```

The host:
1. spawns `codex app-server` with per-agent `CODEX_HOME` (unchanged from today),
2. speaks JSON-RPC on the child's stdio (t3code manager pattern),
3. exposes `${OVERDECK_HOME}/sockets/appserver-<agentId>.sock` (0600, token-authenticated like `pty-token`) with ops: `message` (→ `turn/start`), `interrupt`, `approval`, `user-input`, `status`,
4. renders a human-readable event feed to its stdout — which IS the tmux pane, so the dashboard terminal panel, `tmux attach`, and pane captures keep working with **zero frontend changes**,
5. reads its own stdin line-by-line: a line typed into the pane (or tmux-pasted by the delivery fallback) becomes a `turn/start` — the operator can still talk to the agent from the terminal,
6. appends every protocol event to `${OVERDECK_HOME}/agents/<id>/appserver-events.jsonl` (durable event log),
7. persists `threadId` via the existing `writeThreadId` (`src/lib/runtimes/codex.ts:67-91`).

Why this shape (vs. dashboard-owned children, t3code-style): agents must survive dashboard restarts; the tmux session **is** Overdeck's liveness oracle (`docs/AGENT-STATE-PLANES.md`) and the deacon's patrol unit. Keeping one-host-per-tmux-session preserves the entire lifecycle plane — spawn, deacon recovery, `pan kill`, `/ws/terminal` — while swapping only the harness substrate.

**Scope decision:** conversations AND work agents move together (both currently use `codexMode: 'tui'`/`'work-tui'`). A config escape hatch `codex.transport: "tui"` keeps the old path selectable for one release; default is `"app-server"`.

## 3. Requirements

### Functional
- **FR-1** Codex conversations spawn via the app-server host when `codex.transport` is unset or `"app-server"`.
- **FR-2** Codex work agents spawn via the app-server host under the same setting.
- **FR-3** The delivery door delivers to Codex sessions via the host socket as one `turn/start`; a 1MB message is delivered whole, with no echo confirmation, purge, or rewrite. Tier order for codex: host socket → tmux paste (which the host's stdin line-reader converts to `turn/start`).
- **FR-4** Approval and user-input server requests surface as structured pending-input state (existing awaiting-input surfaces) and are answered via the host socket; the digit-keystroke path is not used for app-server sessions.
- **FR-5** Resume: a stopped Codex agent/conversation resumes via `thread/resume {threadId}`; on the recoverable not-found error class it falls back to `thread/start` and logs the fallback.
- **FR-6** Interrupt: stopping a running turn issues `turn/interrupt` before any process kill.
- **FR-7** The tmux pane shows a readable event feed (user turns, assistant text, tool/command items, approvals, errors) and accepts typed line input.
- **FR-8** Liveness, deacon patrols, pause/troubled/yield gates, and `pan kill` work unchanged (tmux session per agent remains the unit).
- **FR-9** Transcript rendering and cost parsing keep working for app-server sessions (rollout JSONL if written — see Checkpoint C1 — else the host event log).
- **FR-10** `codex.transport: "tui"` restores the previous behavior end-to-end.

### Non-functional
- **NFR-1** Host + manager code contains no `execSync` and no sync tmux primitives.
- **NFR-2** Host runs under Node 22 (launcher uses the same node resolution as the PTY supervisor).
- **NFR-3** All timeout/retry tests use fake timers.
- **NFR-4** No hardcoded model IDs anywhere in the new code; missing model = loud error.
- **NFR-5** Version gate: refuse to start with codex CLI < 0.144.0 with an actionable upgrade message (0.144.1 is the verified baseline; t3code's floor is 0.37.0 but we test against what's installed).

- message classification (server-request vs notification vs response) — t3code `:1352-1382`; invalid JSON → warn, never crash — `:996-1035`.
- methods: `thread/start` (params `{model, cwd, approvalPolicy, sandbox, experimentalRawEvents:false}`), `thread/resume {…, threadId}`, `turn/start {threadId, input:[{type:"text",text,text_elements:[]}], model?, effort?}`, `turn/interrupt {threadId, turnId}`, `thread/read`, `account/read` — t3code `:526-736`.

### WI-3 — `src/lib/codex/app-server-host.ts` → `dist/codex-app-server-host.js` (traces: FR-3, FR-4, FR-7, NFR-1, NFR-2)
New tsdown entry (add alongside `pty-supervisor` in the root `tsdown.config.ts`). Composition: manager (WI-2) + a unix-socket server + pane feed + stdin reader.
- Socket `${OVERDECK_HOME}/sockets/appserver-<agentId>.sock`, mode 0600, token file `${OVERDECK_HOME}/agents/<id>/appserver-token` — clone the `pty-token` scheme (`src/lib/pty-token.ts`, socket-bind pattern `pty-supervisor.ts:381-398`).
- Ops (HTTP-on-unix POST, JSON body): `{op:"message", content, model?, effort?}` → `turn/start`; `{op:"interrupt"}`; `{op:"approval", requestId, decision}`; `{op:"user-input", requestId, answers}`; `{op:"status"}` → `{state: starting|ready|running|awaiting-approval|error|closed, threadId, activeTurnId, pendingRequests:[…]}`.
- Pane feed: compact single-writer rendering of user turns, streamed assistant text, item started/completed lines, approval prompts (`[approval #3] command: git push … — reply via dashboard or type 'y'/'n'`), errors. Plain text; no cursor addressing (the pane is a log, not a UI).
- stdin: `readline` per line — `y`/`n`/digit while an approval is pending → decision; anything else → `turn/start`. This is what makes the tmux-paste delivery fallback and operator typing work (FR-3, FR-7).
- Event log: append every ProviderEvent-equivalent to `${OVERDECK_HOME}/agents/<id>/appserver-events.jsonl`.
- Lifecycle: child exit → render reason, close socket, exit with child's code (launcher/tmux semantics identical to the PTY supervisor today: pane shows "session ended"). SIGTERM → `turn/interrupt` if running (FR-6), child SIGTERM, 5s grace, exit — mirror `pty-supervisor.ts:455-474`.
- `threadId` persistence via `writeThreadId` (`src/lib/runtimes/codex.ts:67-91`) as soon as `thread/started` arrives — replaces the 120s rollout poll in `spawn.ts:808-821` for app-server sessions (keep the poll as fallback only under `transport: tui`).
**Tests:** socket auth (reject bad/missing token), op round-trips against the fake child, stdin line → turn/start, approval via stdin, SIGTERM interrupt flow (fake timers).
