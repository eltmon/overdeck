# PAN-3668: Add Prime Agent as a managed harness

## Status

Draft PRD. This document covers the first production integration of Prime Agent into Overdeck's managed harness surface.

## Glossary

- **Prime Agent**: Prime Intellect's MIT-licensed coding and research agent, invoked by the `prime-agent` executable.
- **RPC mode**: Prime Agent's persistent JSON Lines protocol over stdin and stdout, started with `prime-agent --mode rpc`.
- **Prime session**: The durable root agent session identified by Prime Agent's session ID and JSONL session file.
- **Prime child**: An RLM subagent created inside a Prime session by `rlm(...)`.
- **Cloister**: Overdeck's lifecycle supervisor. It owns agent registration, recovery, messaging, pipeline dispatch, and observability.
- **Managed work**: Plan, work, review, test, ship, strike, and other issue-bound execution controlled by Overdeck.
- **Harness behavior**: The canonical contract in `packages/contracts/src/harness-behavior.ts` that defines launch, delivery, readiness, transcript, session, context, and feed behavior.
- **No-loss audit**: A mechanical test that enumerates every existing harness-facing surface and proves the new harness is represented without removing any existing behavior.
- **State write door**: The single canonical Overdeck writer for durable pipeline state. Prime Agent must not create a parallel writer.

## Problem

Overdeck supports Claude Code, OhMyPi, Codex, ACP, and Kimi Code, but it cannot route work through Prime Agent. Prime Agent offers a different execution model: a persistent IPython control environment, programmatic recursive subagents, durable supplemental harness state, and daemon-backed sessions for long-running work.

Prime Agent publishes the integration primitives Overdeck needs. Its RPC mode accepts correlated JSONL commands for prompt, steer, follow-up, abort, model selection, state, messages, compaction, and session statistics. It streams agent, turn, message, and tool-execution events. The protocol exposes session IDs, session paths, token totals, costs, and context use.

A shallow integration would make Prime Agent selectable but leave gaps in delivery, recovery, costs, transcripts, context, and dashboard status. This PRD requires full managed-harness parity and a no-loss audit.

## Goals

1. Let operators select `prime-agent` through the same provider-owned harness routing used by existing runtimes.
2. Support Prime Agent for managed work and supervised conversations through a persistent, resumable RPC session.
3. Keep Cloister as the lifecycle authority and preserve Overdeck's issue, workspace, message, cost, transcript, and recovery contracts.
4. Make installation, authentication, configuration, and failures visible and actionable.
5. Add Prime Agent without removing or weakening any existing harness surface.

## Non-goals

- Training or evaluating models through Prime Intellect Lab or `verifiers`.
- Installing or managing Prime Intellect GPU compute.
- Importing Prime Agent's continual-harness refinements into bundled, machine, project, or workspace context layers.
- Exposing Prime schedules, autonomous mode, or heartbeat scheduling as Overdeck pipeline controls in the first release.
- Treating Prime's worker and kernel processes as a security sandbox.
- Registering arbitrary Prime RLM children as first-class Overdeck work agents in the first release.
- Adding a hardcoded default model or changing existing provider-to-harness defaults.

## Research findings and decisions

### Prime Agent integration contract

Prime Agent starts RPC mode with:

```bash
prime-agent --mode rpc --provider <provider> --model <model> --session-dir <path>
```

Commands and responses are JSON objects separated by LF. Events stream asynchronously on stdout. Prime Agent explicitly warns that Node's `readline` is not protocol-compliant because it also splits on Unicode U+2028 and U+2029. The adapter must buffer bytes and split only on `\n`, stripping one trailing `\r` before JSON parsing.

The minimum command mapping is:

| Overdeck operation | Prime RPC command |
| --- | --- |
| Initial or idle delivery | `prompt` |
| Running delivery | `steer`, or `prompt` with `streamingBehavior: "steer"` |
| Deferred delivery | `follow_up` |
| Stop current generation | `abort` |
| Readiness and session pointer | `get_state` |
| Transcript projection | `get_messages` plus the durable session JSONL |
| Usage and cost | `get_session_stats` |
| Reasoning effort | `set_thinking_level` after startup when supported |

### Lifecycle ownership

Prime Agent normally routes headless clients through its daemon, supervisor, worker, and kernel processes. Overdeck must treat that process tree as one managed root session. Cloister owns whether the root is running, stopped, resumed, or replaced.

Prime schedules, Prime heartbeats, autonomous continuation, direct cross-agent messaging, and retained RLM children can continue after a client detaches. For managed work, the first release must disable those capabilities through a supplemental system instruction and reject their RPC management commands in Overdeck's adapter. If upstream lacks a reliable disable switch, implementation must add a checkpoint: run Prime in an isolated workspace, prove that the policy prevents invisible descendants, and otherwise limit the first release to supervised conversations with a clear error for managed work.

Prime RLM children created within one root session may be used as internal tool execution only when their activity and cost remain attributable to that root. They are not independent Overdeck agents and must not call `pan done`, alter pipeline records, or claim issue ownership.

### Security boundary

Prime Agent executes model-generated Python and project commands with the user's operating-system permissions. Its worker and kernel isolation is not a sandbox. Overdeck must launch it only inside the same isolated local workspace or remote container assigned to other work harnesses. Documentation and doctor output must state this boundary.

### Provider and model routing

Prime Agent supports subscription OAuth and API-key providers. Its documented credentials live in `~/.prime/agent/auth.json` or provider environment variables such as `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `PRIME_API_KEY`, `GEMINI_API_KEY`, `OPENROUTER_API_KEY`, and others.

Overdeck remains the source of the selected model and provider. The launcher derives the Prime provider argument from Overdeck's provider registry and maps the model ID explicitly. It must fail when no mapping exists. It must never choose a fallback model.

The first release supports only providers with a verified, unambiguous mapping and valid credentials. At minimum, verify OpenAI API key, Anthropic API key, Prime Inference API key, and one subscription-auth path. Add further providers only through table-driven mappings and tests.

Subscription semantics need a policy gate. Prime Agent documents that Claude Pro/Max third-party harness use is billed as extra usage, not plan quota. The UI and error text must not imply Claude Code subscription parity.

### Context and continual harness state

Prime Agent loads user and project state from `~/.prime/agent` and `./.prime/agent`. Overdeck must not overwrite those user-owned directories. Add an Overdeck-owned rendered artifact at `~/.overdeck/context/prime-agent-global.md`, then inject its contents at session creation through the supported Prime prompt/system extension mechanism selected during implementation.

The injected policy must define Overdeck message provenance, workspace boundaries, `pan` lifecycle rules, no hidden work agents, and the state write door. Prime's `/refine` feature may change only session-local supplemental state. It must not edit Overdeck context sources or rendered artifacts.

## Requirements

### Functional requirements

- **FR-1**: `prime-agent` is a canonical harness literal in contracts, runtime types, persisted state, configuration validation, telemetry, artifacts, flywheel records, context previews, dashboard filters, and API schemas.
- **FR-2**: The behavior registry defines Prime-specific launch, delivery, readiness, transcript, session-ID, context-layer, feed, streaming, and timeout semantics without falling back to Claude Code.
- **FR-3**: Overdeck resolves an executable named `prime-agent`, supports an optional absolute configured path, and reports missing or non-executable binaries without creating a terminal session.
- **FR-4**: Doctor verifies a supported Prime Agent version and RPC capability. The compatible version range is a named constant tied to protocol tests, not `latest`.
- **FR-5**: Work and conversation launchers start a persistent Prime RPC client in the assigned working directory with explicit provider, model, session directory, and environment.
- **FR-6**: The RPC client implements strict LF JSONL framing, request IDs, response correlation, asynchronous event streaming, bounded pending requests, startup timeout, malformed-record handling, backpressure, stderr capture, and child-process exit handling.
- **FR-7**: Overdeck records the Prime session ID and session file path through the existing agent/conversation state write surface and resumes the same session after a recover or restart.
- **FR-8**: `pan tell`, dashboard messaging, and conversation steering map to `prompt`, `steer`, or `follow_up` based on `get_state.isStreaming`; delivery receipts report accepted versus rejected commands accurately.
- **FR-9**: Kill and pause abort active generation and stop the managed process tree. Recovery detects the durable session before starting a replacement client.
- **FR-10**: Heartbeat and health use RPC events while live, durable transcript modification time while detached, and git activity only as the existing low-confidence fallback.
- **FR-11**: Transcript ingestion renders user, assistant, thinking, tool-call, tool-result, compaction, and error events through the conversation viewer without reading Prime's internal store outside the transcript adapter.
- **FR-12**: `get_session_stats` data maps input, output, cache-read, cache-write, total tokens, cost, context window, and percent into Overdeck's cost and activity schemas. Missing upstream fields remain absent; the adapter does not invent values.
- **FR-13**: Provider and model mapping is explicit, table-driven, validated, and covered by success and unsupported-model tests. No hardcoded fallback model is allowed.
- **FR-14**: Provider credentials use the existing provider environment resolver or Prime's user-owned auth file. Errors identify the missing credential and the command or file the operator must configure.
- **FR-15**: Overdeck renders and previews `prime-agent-global.md`, injects it at spawn, and supports `harness:prime-agent` context blocks without modifying `~/.prime/agent`.
- **FR-16**: Managed Prime sessions receive a policy that keeps Cloister authoritative, forbids direct canonical-state writes, and prevents child agents from claiming pipeline lifecycle actions.
- **FR-17**: Prime schedules, heartbeats, autonomous continuation, and direct daemon agent messaging are unavailable for managed work in the first release. Attempts return a standalone explanation.
- **FR-18**: The dashboard can select, display, filter, stream, stop, resume, and inspect Prime Agent wherever it supports another harness.
- **FR-19**: A mechanical no-loss audit enumerates every old harness-facing CLI option, route, schema, setting, status, badge, filter, view, context preview, transcript adapter, cost source, recovery path, and lifecycle action, and gives each existing item and Prime Agent a valid home.
- **FR-20**: Installation and configuration docs cover binary installation, version pinning, authentication, provider mapping, context, lifecycle ownership, security, recovery, limitations, and uninstall behavior.

### Non-functional requirements

- **NFR-1**: Dashboard-reachable code uses asynchronous process and filesystem primitives. It must not add `execSync`.
- **NFR-2**: RPC parsing is incremental and bounded so one large tool result cannot block the dashboard event loop or grow memory without limit.
- **NFR-3**: Credentials, full prompts, Python source, and tool outputs never enter routine logs. Diagnostics may log event types, request IDs, byte counts, paths, exit codes, and redacted errors.
- **NFR-4**: Prime Agent failures cannot corrupt or bypass the issue, agent, conversation, or state write doors.
- **NFR-5**: Existing harness tests remain green, and the no-loss audit fails when any canonical harness enumeration omits Prime Agent.
- **NFR-6**: Delay, retry, and startup-timeout tests use Vitest fake timers. They must not use real waits or lower worker concurrency to hide leaks.
- **NFR-7**: Runtime boot-path changes are tested in a throwaway dashboard instance before deployment to the live server.
- **NFR-8**: The integration is supported on macOS and Linux, matching Prime Agent's documented release platforms.

## Rollout

Ship behind availability detection: `prime-agent` appears selectable only when configuration permits it and doctor can resolve a compatible binary. Do not change any provider's existing default harness. Operators opt in by setting the resolved harness to `prime-agent` for a provider or role.

If production evidence shows RPC protocol drift, mark Prime Agent unavailable with the version mismatch explanation. Do not fall back silently to Claude Code or another harness.
