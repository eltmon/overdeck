# PAN-2378 — Tiered-execution configuration UI (editable Settings surface)

**Issue:** [PAN-2378](https://github.com/eltmon/overdeck/issues/2378)
**Depends on:** [PAN-2283](https://github.com/eltmon/overdeck/issues/2283) (config loading + dispatch wiring + read-only panel) — **merged** into this branch.
**Operator priority:** must land with PAN-2283 before the special-orders run (RUN-56) begins.

---

## Glossary

- **Tiered execution** — routing each vBRIEF bead to the cheapest warm agent tier that can do the work, with a durable supervisor. Off by default. Full contract: `docs/TIERED-EXECUTION.md`.
- **Tier table** — the `tiered_execution.tiers` map: each named tier (`cheap`/`standard`/`frontier`, operator-chosen) declares `model`, `harness`, and the list of `difficulties` it owns. Every one of the five difficulties (`trivial`, `simple`, `medium`, `complex`, `expert`) must map to exactly one tier.
- **The config door** — the single canonical read/write path for global settings: `GET /api/settings` → `loadSettingsApi()` and `PUT /api/settings` → `saveSettingsApiPromise()` in `src/lib/settings-api.ts`, persisted to `~/.overdeck/config.yaml`. Single-source-of-truth rule: no direct file writes outside this door.
- **Effective / resolved state** — the on/off value dispatch actually uses. `resolveTieredExecutionEnabled(config, planMetadata)` (`src/lib/agents/tier-table.ts:124`): a per-issue `plan.metadata.tiered_execution: 'on'|'off'` override wins over the global `tiered_execution.enabled` flag; unset inherits the global flag.
- **Per-issue override** — an issue's vBRIEF `plan.metadata.tiered_execution` set to `'on'` or `'off'`, overriding the global flag for that one issue.
- **Validation door** — `validateTieredExecutionConfig(rawConfig, { providerAuth })` (`src/lib/agents/tier-table.ts:268`): fail-loud validator that throws `TieredExecutionConfigError` on any invalid table. Also enforces the ToS gate (`canUseHarnessSync`) on tier/supervisor model+harness pairs.
- **Autosave pipeline** — the Settings page has no Save button; `useAutosavePipeline` (`src/dashboard/frontend/src/components/Settings/hooks/useAutosavePipeline.ts`) serializes latest-wins `PUT /api/settings` calls. Sections mutate global `formData` via an `onSettingsChange` prop (`applySettings`, `SettingsPage.tsx:408`).

## Problem

PAN-2283 shipped the tiered-execution *read* half end-to-end: config loading (`config-yaml/merge.ts`), dispatch wiring (`agents/spawn-prep.ts`), and a **read-only** Settings panel (`Settings/sections/TieredExecutionSection.tsx`). There is no way to *configure* tiered execution from the UI:

1. The panel has no inputs — it takes `{ formData }` only, no `onSettingsChange`.
2. The write door silently drops `tiered_execution`: `saveSettingsApiPromise` (`settings-api.ts:844`) never adds it to `yamlConfig`, and `writeYamlConfigPreservingComments` (`settings-api.ts:750`, `topLevelSections` list `~785`) does not write it. A `PUT /api/settings` carrying edited tiered config is discarded.
3. `validateSettingsApi` (`settings-api.ts:1080`) has no tiered branch, so nothing validates a tiered edit at save time.
4. A per-issue `plan.metadata.tiered_execution` override is invisible to the operator.

The operator expected an editing surface in v0.42. This issue delivers it.

## Proposal

Upgrade the existing read-only global Settings panel into an **editable** one, persisting through the existing config door with fail-loud save-time validation, plus a **read-only** per-issue override chip on the issue view.

- **Config is global.** `tiered_execution` is a top-level block in `config.yaml` (`schema.ts:499`); projects override it via per-project `.pan.yaml` additive merge, but the Settings surface is global (no project selector) and no per-project write path exists. "Per project" in the issue maps to this global door. Per-project override *editing* is a NonGoal (gap noted).
- **Edit inputs, not derived fields.** The editor mutates raw input fields (`tiers`, `by_kind`, `supervisor`, `feed`, `escalation`, `enabled`, `replay_threshold`). The server derives `difficultyToTier`/`byKind` during `validateTieredExecutionConfig` on save; the frontend never computes them.
- **Fail-loud validation, server-side.** Save-time validation reuses `validateTieredExecutionConfig` (passing `providerAuth` context as `merge.ts:428` does). Invalid edits → `400` with the `TieredExecutionConfigError` message. Because the validator throws when `enabled: true` has an incomplete table (unmapped difficulty `tier-table.ts:320`, missing supervisor `:340`), "saving is blocked while invalid" is enforced by the existing validator. The frontend surfaces the 400 message inline and shows a not-saved state.
- **Per-issue override is read-only.** `updateSpecStatus` (`pan-dir/specs.ts:287`) mutates only `plan.status` (PAN-1124 spec immutability). No spec-status write door for `plan.metadata` exists. Per the issue's own fallback, the chip is read-only + doc link; editing the override is a NonGoal.

## Requirements

**Functional**
- **FR-1** — `tiered_execution` edits persist through the config door to `config.yaml`, preserving surrounding comments.
- **FR-2** — Save-time validation rejects an invalid `tiered_execution` block with `400` + the human-readable `TieredExecutionConfigError` message; a valid block is accepted and round-trips.
- **FR-3** — The enable/disable toggle (`tiered_execution.enabled`) is editable in Settings and persists.
- **FR-4** — The panel shows the resolved effective state (global `enabled` combined with validation status), reusing `resolveTieredExecutionEnabled` semantics.
- **FR-5** — The tier table is editable: add / edit / remove a tier (name, model, harness, difficulties), with inline validation errors and no persisted save while invalid.
- **FR-6** — The supervisor, `by_kind`, `feed`, and `escalation` blocks are editable and persist.
- **FR-7** — Where an issue's `plan.metadata.tiered_execution` override exists, the issue view surfaces a read-only chip showing effective state and override source ("tiered: on (issue override)" / "off (global)").
- **FR-8** — `docs/TIERED-EXECUTION.md` documents the Settings edit UI and notes the per-issue-override-editing gap.

**Non-functional**
- **NFR-1** — Single-source-of-truth: reuse the existing `/api/settings` door; no new direct file writes for `tiered_execution`.
- **NFR-2** — Follow `pan-style-guide`: no decorative color; validation errors are the only red.
- **NFR-3** — Fail-loud: invalid config is never silently persisted nor silently dropped.

## NonGoals

- Per-project `tiered_execution` editing / a per-project Settings surface or project selector (config is global; per-project `.pan.yaml` override is an existing additive-merge mechanism, not surfaced for editing).
- Editing the per-issue `plan.metadata.tiered_execution` override from the UI (no `plan.metadata` write door; PAN-1124 spec immutability) — chip is read-only.
- Changing the `tiered_execution` schema, validation rules, or dispatch behavior (owned by PAN-1791 / PAN-2222 / PAN-2283).
- A design mockup — this converts a self-contained existing Settings section in place following existing section patterns (not a redesign of hard-won layout).
