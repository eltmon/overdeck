## 1. Glossary

- **Floating Effect** — an `Effect` value that is constructed but never executed: neither `yield*`ed inside an `Effect.gen`, nor passed to `Effect.runPromise`/`runSync`, nor returned into a chain that runs it.
- **Bridge combinator** — `Effect.promise(thunk)` / `Effect.tryPromise({ try, catch })`. Both exist to lift a **Promise-returning** thunk into an Effect. Handing them an Effect-returning thunk is the bug this issue fixes.
- **Effect-returning callee** — a function whose return type is `Effect.Effect<A, E, R>`. It performs no work when called; it returns a description that must be run.
- **Typed error channel** — the `E` parameter of `Effect.Effect<A, E, R>`. A `yield*` of an Effect whose `E` is non-`never` propagates that error through the enclosing Effect, **not** through JavaScript exception flow.
- **Defect** — an unexpected, untyped failure (`Effect.die`). A rejected promise inside `Effect.promise` becomes a defect, as does a `TypeError` thrown inside Effect's own runtime.
- **`httpHandler`** — `src/dashboard/server/routes/http-handler.ts:58`. Wraps a route body `Effect.Effect<HttpServerResponse, E, R>` and returns `Effect.Effect<HttpServerResponse, never, R>`. It `catchTag`s ten known typed errors to specific statuses, then `catchCause`s everything else — typed failures *and* defects — into `jsonResponse({ error: message }, { status: 500 })`. Because it is generic over `E`, a route body may `yield*` an Effect with any typed error channel and still typecheck.
- **Dashboard-types ratchet** — `scripts/lint-dashboard-types.sh`, baseline `scripts/dashboard-types-baseline.txt` (a single integer, currently **47**). Counts `error TS` lines from `npx tsc --noEmit -p src/dashboard/server/tsconfig.json`. It never raises; `--update` lowers it.

## 2. Problem

Five call sites in the dashboard server hand an **Effect-returning** callee to a **Promise** bridge combinator. The inner Effect is never executed, and the route dies.

These are exactly the `TS2741: Property 'then' is missing in type 'Effect<...>'` errors plus their cascading `TS18046: '<x>' is of type 'unknown'` in the dashboard-types baseline — **17 of the 47 baselined errors**.

### 2.1 Correction to the issue body: this is a 500, not a silent no-op

The issue text says the sites are "silently inert" and that `await`ing an Effect "resolves immediately to the Effect object itself", so callers receive a truthy Effect object typed `unknown`. **That is not what `effect@4.0.0-beta.73` does**, and the difference changes what each fix must restore.

Measured in this workspace on 2026-08-06 with a throwaway script against the installed `effect@4.0.0-beta.73`:

```
Effect.promise(() => <Effect>)     → FAILURE
  cause: TypeError: internalCall(...).then is not a function
         at .../effect/dist/internal/effect.js:691:40
Effect.tryPromise({ try: () => <Effect>, catch })  → FAILURE (catch maps the same TypeError)
```

Effect's `promise` implementation calls `.then()` on whatever the thunk returns. An Effect has no `.then`, so the runtime throws a `TypeError` **inside the fiber**. That becomes a defect (or, for `tryPromise`, a mapped typed failure), which propagates out of the enclosing `Effect.gen`, reaches `httpHandler`'s `catchCause`, and the route returns:

```
HTTP 500  { "error": "internalCall(...).then is not a function" }
```

So the real production behavior at all five sites is: **the endpoint is dead — every call returns 500 and no code after the bad `yield*` runs.** The inner Effect still never executes, exactly as the issue says; but nothing downstream sees a garbage success payload, because there is no success payload.

Two consequences for scope:

- **Site 6 (`stash-clean.ts`) is not currently dangerous.** The issue predicted `orphanedContainers.length` would be `undefined`, `undefined > 0` false, and the removal would proceed unguarded past a bypassed safety check. It does not: the route dies at the guard, several statements *before* the `rm -rf`. The corrupted-workspace removal endpoint is simply broken (always 500). The fix restores the feature **and** makes the enumeration-failure path explicitly fail-closed, so the guard is correct once it starts running again.
- **Sites 2 and 3 kill the whole `POST /api/workspaces/:issueId/review-status` request** whenever review status is `blocked`/`failed` with `reviewNotes`, or test status is `failed` with `testNotes`. `setReviewStatus()` has already run and persisted by then (`src/dashboard/server/routes/workspaces.ts:1488`), so the status sticks, but the caller gets a 500 and every statement after the feedback block — including the `pipeline.review-completed` / `pipeline.test-completed` event appends — never runs.

### 2.2 Second, independent defect in the same code: JS `try/catch` cannot catch Effect failures

Sites 2 and 3 sit inside JavaScript `try { … } catch (err) { console.error(…) }` blocks whose stated intent is "a feedback-write failure must not fail the whole request". Measured against `effect@4.0.0-beta.73`:

```
try { yield* Effect.fail(new Error('x')) } catch { … }                → catch NEVER runs; failure escapes to catchCause
try { yield* Effect.promise(() => Promise.reject(…)) } catch { … }    → catch NEVER runs; defect escapes to catchCause
```

Effect's generator runtime short-circuits the fiber; it does not call `iterator.throw()`. So those `try/catch` blocks are inert today and will stay inert after the `yield*` fix unless they are rewritten as Effect-level handling. The issue calls this out and this PRD implements it.

The identical dead-`try/catch` pattern also guards the destructive `rm -rf` fallback at `src/dashboard/server/routes/workspaces/stash-clean.ts:375-387`: when the plain `rm -rf` fails on root-owned files, the `catch` is supposed to fall back to an Alpine container cleanup. It never runs. Fixing it is a six-line change in a file this issue already opens, on a path whose failure mode is "workspace cannot be cleaned at all", so it is **in scope** (see D-4).

## 3. Requirements

### Functional

- **FR-1** — No call site in `src/dashboard/server` passes an Effect-returning callee to `Effect.promise` or `Effect.tryPromise`. Mechanically: `npx tsc --noEmit -p src/dashboard/server/tsconfig.json` reports zero `TS2741: Property 'then' is missing in type 'Effect<`.
- **FR-2** — `POST /api/specialists/:project/:type/context/regenerate` runs `regenerateContextDigest` and returns the real digest string, or `{ error: 'Failed to generate context digest' }` with status 500 when the digest is `null`.
- **FR-3** — `POST /api/workspaces/:issueId/refresh-token` runs `refreshWorkspaceToken`. On success it returns `{ success: true, message: … }`; on a typed failure it returns `{ success: false, error: <message> }` with status 500 — never `success: true` for a refresh that did not happen.
- **FR-4** — The review-feedback block (`workspaces.ts` ~1508–1536) writes the review feedback file, and a failure anywhere in that block logs `[review-status] Failed to send feedback to <agentId>` and lets the request continue to its normal `jsonResponse(status)` — it does not 500 the route.
- **FR-5** — The test-feedback block (`workspaces.ts` ~1574–1601) behaves the same way for the test-agent feedback file, logging `[review-status] Failed to send test feedback to <agentId>`.
- **FR-6** — `POST /api/workspaces/:issueId/clean` enumerates containers before deleting a workspace, and **fails closed**: if enumeration succeeds and finds containers it returns 409; if enumeration itself fails it returns 500 and performs no deletion.
- **FR-7** — The `rm -rf` fallback in `POST /api/workspaces/:issueId/clean` actually runs when the plain `rm -rf` fails, using Effect-level error handling rather than a JS `try/catch`.
- **FR-8** — A regression test locks FR-6's three outcomes (clear / blocked / enumeration-failed).
- **FR-9** — `scripts/dashboard-types-baseline.txt` is lowered to the post-fix count via `bash scripts/lint-dashboard-types.sh --update`.
- **FR-10** — Documentation: a new `docs/EFFECT-BRIDGING.md` states the bridging rule and the two measured runtime facts; `CLAUDE.md` gains a short pointer paragraph.

### Non-functional

- **NFR-1** — No behavior change to any `Effect.promise(() => import('…'))` line. Dynamic `import()` genuinely returns a Promise; those bridges are correct.
- **NFR-2** — `npm run typecheck`, `npm run lint`, and `npm test` stay green with no new failures relative to the pre-change run on the same tree.
- **NFR-3** — The ratchet is only ever lowered. If the post-fix count exceeds 47, the change introduced new errors and must be fixed rather than baselined.

## 4. Decisions made in this document

- **D-1: `httpHandler` absorbs unhandled typed errors, so an explicit handler is only added where the current code demonstrably intends to swallow or reshape the failure.** `httpHandler<R, E>` is generic over `E` and ends in `catchCause`, so a bare `yield* someEffect()` typechecks and degrades to a 500 JSON body. Sites 5 (empty error channel) therefore needs nothing; sites 2, 3, 4, and 6 each get explicit handling because each has a specific observable behavior to preserve or establish.
- **D-2: Sites 2 and 3 keep "log and continue", implemented with `Effect.catchCause`.** `catchCause` (not `Effect.catch`) is required because the block must swallow both typed `FeedbackWriteError` failures and the defects that `Effect.promise(() => deliverQueuedFeedback(…))` produces on rejection — which is what the dead `try/catch` was trying to do. This preserves today's *intended* behavior exactly and does not introduce a new 500 path.
- **D-3: Site 6's guard is extracted into an exported Effect helper, `checkWorkspaceRemovalGuard`.** The route handler at `stash-clean.ts:323` is a module-private `HttpRouter.add(…)` with no exported seam, so its behavior cannot be unit-tested. Extracting the guard gives FR-8 a real seam without inventing a dependency-injection framework. The helper returns a verdict value rather than throwing, so the test asserts the refusal directly.
- **D-4: The dead `try/catch` around the `rm -rf` fallback (`stash-clean.ts:375-387`) is fixed in this issue.** It is the same bug class the issue is about, in a function this issue already edits, six lines long, and its failure mode is a destructive operation silently losing its recovery path. Leaving it would be knowingly walking past the trash.
- **D-5: Site 1 (`costs.ts:328`) is out of scope**, per §2.4. It is already correct; making it idiomatic would change an error channel with no bug to justify it.
- **D-6: Documentation lands as a new `docs/EFFECT-BRIDGING.md`, not folded into PAN-3568's `docs/EFFECT-DIAGNOSTICS.md`.** This issue lands first, and the two documents cover different things: the authoring convention (here) versus the mechanical gate that enforces it (3568). 3568's doc links back to this one.
- **D-7: Status code for enumeration failure is 500, not 409.** 409 means "containers exist, stop them first" — an actionable operator state. "We could not determine whether containers exist" is a server-side failure and gets 500 with an explicit message naming the workspace path.

```ts
 * Verdict for the "never delete a workspace while containers still reference
 * its compose path" guard (PAN-3567).
 *
 * The guard fails closed: if Docker cannot be enumerated we refuse the removal
 * rather than assume there is nothing to protect.
 */
export type WorkspaceRemovalGuard =
  | { readonly allow: true }
  | { readonly allow: false; readonly status: 409 | 500; readonly error: string };

export const checkWorkspaceRemovalGuard = (
  workspacePath: string,
): Effect.Effect<WorkspaceRemovalGuard> =>
  getContainersReferencingWorkspacePath(workspacePath).pipe(
    Effect.map((containers): WorkspaceRemovalGuard =>
      containers.length > 0
        ? {
            allow: false,
            status: 409,
            error: `Cannot remove workspace: ${containers.length} Docker container(s) still reference compose paths in ${DEVCONTAINER_DIRNAME}/. Stop the containers first.`,
          }
        : { allow: true }),
    Effect.catch((err: ProcessSpawnError): Effect.Effect<WorkspaceRemovalGuard> =>
      Effect.succeed({
        allow: false,
        status: 500,
        error: `Cannot remove workspace: failed to enumerate Docker containers referencing ${workspacePath}: ${err.message}`,
      })),
  );
```

### WI-9 — Documentation

**What/why:** the convention that prevents this bug class must be written down where an agent will find it. Satisfies FR-10.

**Files:**

1. **`docs/EFFECT-BRIDGING.md`** (new, ≤80 lines). Contents:
   - The rule: `Effect.promise` / `Effect.tryPromise` bridge **Promise**-returning thunks. An Effect-returning callee is `yield*`ed directly; its typed error channel then becomes live and must be discharged (or deliberately allowed to reach `httpHandler`, which maps anything unhandled to a 500).
   - Measured fact 1: on `effect@4.0.0-beta.73`, `Effect.promise(() => <Effect>)` throws `TypeError: internalCall(...).then is not a function` inside the fiber. The endpoint returns 500; it does not silently succeed. Include the reproduction snippet from §2.1.

Use `Effect.catch` for typed failures and `Effect.catchCause` when defects (e.g. a rejected `Effect.promise`) must also be swallowed.
   - The legitimate uses that must not be "fixed": `Effect.promise(() => import('…'))` and any genuinely Promise-returning callee.
