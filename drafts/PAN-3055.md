# PAN-3055 — A pending AskUserQuestion outlives its agent: reap zombie pending input at the liveness boundary

**Issue:** https://github.com/eltmon/overdeck/issues/3055

## Glossary

- **AUQ** — AskUserQuestion: the tool an agent calls to ask the operator a multiple-choice question. Detected from the agent's Claude JSONL transcript via the PAN-1520 hook-deny marker (see `docs/ASKUSERQUESTION-DASHBOARD.md`).
- **Enrichment poller** — `src/dashboard/server/services/agent-enrichment-service.ts`. Every 10s (`POLL_INTERVAL_MS`, line 291) it scans each agent's transcript and emits `agent.enrichment_changed` domain events carrying pending-input fields (`pendingAskUserQuestion`, `pendingInputCount`, `pendingInputKinds`, …).
- **Pending input** — the derived "this agent is waiting on the operator" state. Kinds include `askUserQuestion`, `exitPlanMode`, `rateLimit`, `agentTurnEnded` (built in `src/lib/agent-enrichment.ts:589-624`).
- **Runtime census** — `src/lib/runtime-census.ts`. A 3s-TTL cached snapshot of tmux panes (`overdeck` socket) + process table. `census.tmuxAvailable` is `panesResult.status === 'fulfilled'` (line 135): it is **false** whenever `tmux -L overdeck list-panes -a` fails — including the common boot case where the tmux server has no sessions yet ("no server running"), because `listAllPaneRecords` (`src/lib/tmux.ts:999`) rejects on non-zero exit.
- **Fail-open liveness** — `listRunningAgents()` (`src/lib/agents/queries.ts:49-74`) computes `tmuxActive: !runtimeCensus.tmuxAvailable || tmuxNames.has(id)` (line 71). When the census cannot see tmux, **every registered agent reads `tmuxActive: true`**, deliberately, so one-off CLI processes that can't reach the socket don't declare agents dead (recovery/kill paths depend on this).
- **Rising edge** — `isAwaitingInputRisingEdge` (`agent-enrichment-service.ts:68-74`): pendingInputCount transitions 0 → >0 (with `undefined` previous treated as 0). Fires one `activity.entry` + one `activity.tts` utterance (lines 229-234).
- **Decisions door** — `src/dashboard/frontend/src/lib/useDecisions.ts` (`useDecisions` / `usePendingInputSubjects`), the only enumeration of what waits on the operator (PAN-2765).
- **Read model** — server-side event-sourced snapshot (`src/dashboard/server/read-model.ts`); reducers live in `packages/contracts/src/event-reducers.ts`.
- **Idle-alive agent (PAN-2633)** — an agent whose DB status is stop-shaped but whose tmux pane is live and awaiting operator input. Must keep surfacing pending input; `shouldForceReemitPendingInput` (`agent-enrichment-service.ts:82-92`) bypasses dedup for it.

## Problem — verified root cause

`agent-pan-1865-plan` asked an AUQ on 2026-06-29, was stopped unanswered (~50 min later, `status='stopped'`, `stopped_by_user=1`), and has no tmux session. Yet on every dashboard boot after a host restart it re-emits `agent.enrichment_changed` (observed 2026-07-25 at 11:12:09.845Z / :18.944Z / :28.651Z — exactly the 10s poll cadence) plus a TTS announcement, and then sits in the Decisions list as an unanswerable question.

The verified causal chain, all at the code level:

1. **Boot fail-open.** At dashboard boot after a host restart the `overdeck` tmux server has no sessions yet, so `tmux list-panes -a` exits non-zero → `listAllPaneRecords` rejects → `census.tmuxAvailable = false` (`runtime-census.ts:135`) → `listRunningAgents` marks **every** registered agent `tmuxActive: true` (`queries.ts:71`).
2. **The poller scans the dead agent.** `pollOnce` filters `runningAgents.filter(a => a.tmuxActive)` (`agent-enrichment-service.ts:119`) — under fail-open that is everyone, including agents stopped weeks ago.
3. **The zombie is promoted to running.** The `agent.created` seed maps `agent.tmuxActive && agent.status === 'stopped' ? 'running' : agent.status` (line 142), and the stale-status reconciliation branch (line 169) emits `agent.status_changed` stopped→running. The read model now holds a *running* row for a dead agent, which defeats both prior fixes: the PAN-1591 bootstrap strip (`read-model.ts:266-279` — only strips non-running rows) and the PAN-1520/2633 stop-event wipe (`event-reducers.ts:489-507` — needs a stop event that never arrives again).
4. **TTS fires.** `state.lastEnrichment` is empty on a fresh boot, so the rising edge fires (lines 229-234): *"agent-pan-1865-plan on pan 1865 is waiting for askUserQuestion"*.
5. **Dedup is bypassed every poll.** `shouldForceReemitPendingInput('stopped', enrichment-with-AUQ)` returns true (lines 82-92), so the event re-emits each 10s cycle until the tmux server comes up and the census recovers — hence the three observed emissions.
6. **Nothing ever clears it.** Once the census recovers, the agent drops out of `activeAgents`; the cleanup loop (lines 276-283) deletes the private cache entries but **emits nothing**, so the read model keeps a running+pending row. The Decisions door correctly reports what the read model says — the poison entered upstream.

Prior art: PAN-1520 (stop-event wipe), PAN-1591 (bootstrap strip), PAN-2633 (idle-alive force re-emit) each patched one surface of this; the remaining hole is the census fail-open feeding the poller, and the poller's silent falling edge.

## Proposal

Fix pendingness at its single write door — the enrichment poller — following the issue's principles: liveness is part of pendingness; no evidence means no claims; reap on the transition.

1. **Census gate (FR-1).** `pollOnce` obtains the runtime census and returns immediately when `census.tmuxAvailable === false`, before any event emission, activity, TTS, or cache mutation. Rationale: when tmux is unobservable the poller cannot distinguish live from dead, so it must assert nothing. A skipped cycle costs ≤10s of enrichment latency; the fail-open in `listRunningAgents` itself is **kept unchanged** for CLI/recovery callers (changing it would risk orphan-recovery declaring live agents dead).
2. **Falling-edge reap (FR-2, FR-3).** After the (census-gated) scan, for each agent tracked in `state.lastEnrichment` with pending input that is no longer tmux-active, emit one `agent.enrichment_changed` event with all pending fields cleared, plus one **info-level** activity entry recording that the agent stopped with its question unanswered — and **no TTS**. This resolves the pending state at the moment the asker dies, so the Decisions list converges within one poll and boot re-hydration has nothing to resurrect even if a stale row was somehow planted.
3. **History stays intact (auto-decision).** The question and its options remain verbatim in the agent's JSONL transcript (never touched) and viewable in the existing transcript/conversation history surfaces; the agent's terminal status is on its row; the new expiry activity entry is the durable feed record. No new "expired questions" UI panel is added, and the Decisions list must NOT grow an expired section (AC1 requires expired questions out of Decisions).
4. **No read-side parallel check (FR-5).** `useDecisions` / `usePendingInputSubjects` / `selectPendingInputSubjects` are not modified — per the single-source-of-truth tenet, liveness is enforced where pendingness is derived, not re-checked per surface.

### Decision rules (made here, not by the work agent)

- Census unavailable ⇒ skip the **entire** poll cycle (including the cleanup loop and the reap). Treating "census unavailable" as "all agents dead" would mass-reap live agents' pending questions; treating it as "all alive" is the current bug. Only a fulfilled census carries evidence.
- Reap trigger ⇒ previous enrichment had `pendingInputCount > 0` OR a non-null `pendingAskUserQuestion` OR `pendingProposedPlan`, AND the agent is absent from the current census-verified active set. Registry status is NOT consulted (an idle-alive agent has a live pane and stays active; PAN-2633 preserved).
- Reap emits enrichment clearing only — it must NOT emit `agent.status_changed` (status is owned by other doors: stop routes, deacon orphan recovery).
- A reaped agent that later resumes re-enters cleanly: its `lastEnrichment` entry was deleted, so the next scan re-emits and the rising edge re-fires — correct, because a live pane makes the question answerable again.

## Requirements

- **FR-1** `pollOnce` returns without emitting any domain event, activity entry, or TTS utterance, and without mutating poller state, when the runtime census reports `tmuxAvailable === false`.
- **FR-2** When the census is available and an agent tracked with pending input is no longer in the tmux-active set, `pollOnce` emits, in that same cycle, an `agent.enrichment_changed` event for it with `hasPendingQuestion: false`, `pendingQuestionCount: 0`, `pendingInputCount: 0`, `pendingInputKinds: []`, and `pendingAskUserQuestion`/`pendingProposedPlan`/`pendingQuestionPrompt`/`pendingQuestionReason` undefined.
- **FR-3** The reap emits exactly one info-level `activity.entry` naming the agent, its issue (when known), and that its pending question expired unanswered; it emits no `activity.tts` event.
- **FR-4** No awaiting-input rising-edge activity or TTS fires for an agent that has no live tmux session (guaranteed by FR-1's gate; asserted by test).
- **FR-5** No frontend/decisions-door source file changes; expired questions disappear from Decisions solely via the cleared read model.
- **NFR-1** PAN-2633 behavior is preserved: an agent with stop-shaped registry status but a live tmux pane keeps its pending payload and the force re-emit path.
- **NFR-2** `listRunningAgents` / `listRunningAgentsSync` fail-open semantics are unchanged.
- **NFR-3** All new code is async-only (no `execSync` — server-reachable code); any delay-based test uses fake timers per repo rule (expected: none needed — the new helpers are pure).
