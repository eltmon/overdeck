# PAN-3187 — Review-status auto-dispatch floods on wedged closed issues

**Issue:** https://github.com/eltmon/overdeck/issues/3187
**Author:** planning agent (auto mode), 2026-07-27
**Scope note:** expanded by operator direction during planning (2026-07-27): the same
defect's ledger half — 22 close-out backlog issues (the 11 wedged PAN issues below +
11 more tracker-closed residue issues) blocked only on DoD rows 1/2/3 — is in scope.
Rows 5/7 were mechanically fixed the same night (PAN-3188); this plan decides and
implements the rule for rows 1/2/3.

## Glossary

- **Review request intent** — the durable `reviewRequestedAt` timestamp written into the
  per-issue record's `pipeline` block (on `overdeck-state`) by `pan done`. It is the
  PAN-1988 auto-heal: if the reactive review-dispatch trigger is dropped, the host
  re-dispatches review from this intent on the next status read.
- **Serviced request** — a `reviewRequestedAt` that is older than (or equal to) the
  `reviewSpawnedAt` stamped when the review role actually spawned. An **unserviced
  request** has no `reviewSpawnedAt` or a `reviewRequestedAt` newer than it.
- **Journal** — the durable per-issue record (`records/<issue>.json` on
  `overdeck-state`, on disk at `${OVERDECK_HOME}/state/<project>/records/`). The
  SQLite `review_status` table is a disposable cache reconciled FROM the journal on
  read. `reviewRequestedAt` is journal-only — it is NOT a DB column
  (`src/lib/overdeck/review-status-record-sync.ts:86-89`).
- **Reconcile-on-read** — every `getReviewStatusSync()` read overlays the journal
  onto the DB row and fires side-effect hooks (`maybeAutoDispatchReviewHostSide`)
  (`src/lib/review-status-read.ts:12-38`, `src/lib/review-status-reconcile.ts:108-165`).
- **Host-side dispatch** — `dispatchReviewHostSide()` in `src/lib/review-status.ts:538`,
  which re-enters the dashboard-owned durable review pipeline via
  `startDurableReviewPipelineHostSide()`.
- **Durable review pipeline handler** — a process-global callback registered ONLY by
  the dashboard server (`src/dashboard/server/services/durable-review-pipeline.ts:129`).
  In CLI processes the handler is `null` and `startDurableReviewPipelineHostSide()`
  returns `false` (`src/lib/cloister/durable-review-pipeline.ts:32-45`).
- **Closed-issue reaper** — deacon patrol (`reconcileClosedIssueAgents`,
  `src/lib/cloister/closed-issue-reaper.ts:169`, called from
  `src/lib/cloister/deacon.ts:2641`) that stops agents/sessions and reaps workspace
  residue for tracker-closed issues.
- **Close-out** — `pan close <id>`; the mechanical DoD gate (`evaluateDodGate`,
  `src/lib/lifecycle/dod-gate.ts:533`) that marks a record `closeOut.closedOut: true`,
  after which the read path deletes the review_status row and returns null
  (`src/lib/review-status-read.ts:20-27`).
- **DoD rows 1/2/3** — the verdict rows of the close-out gate: `review`
  (`reviewStatus: passed`), `tests` (`testStatus: passed`), `verification`
  (`verificationStatus: passed`), checked by `checkVerdict`/`checkVerificationRow`
  (`src/lib/lifecycle/dod-gate.ts:238-292`). A row resolves `pass`, `skip`
  (deliberately not run — never blocks), or `miss` (blocks close-out unless an
  operator records `--accept-<row>`).
- **Terminal-closed with landed work** — an issue that is closed/completed/cancelled
  on its tracker AND whose DoD row 4 (`merged`) passes, i.e. its work verifiably
  reached main (merged PR, durable merge record, or branch-containment evidence).
- **Never-requested verdict** — rows 1/2/3 read `pending`/missing because the
  specialist was never (successfully) dispatched or its intent died unserviced.
  Distinct from a **negative verdict** (`failed`/`blocked`/`dispatch_failed`): a
  specialist ran and said no.

## Problem (verified against live state, 2026-07-27)

Eleven tracker-closed issues (PAN-2510, PAN-2230, PAN-2420, PAN-2375, PAN-2167,
PAN-2407, PAN-2257, PAN-2258, PAN-2248, PAN-1935, PAN-2150) carry an unserviced
review request from 2026-06-29 → 2026-07-09 in their journal `pipeline` block
(`reviewRequestedAt` set, `reviewSpawnedAt` never set, `reviewStatus: pending`,
`mergeStatus: pending`, no `closeOut` — verified by reading all eleven record files).
Every reconcile-on-read of any of these issues calls
`maybeAutoDispatchReviewHostSide` → `dispatchReviewHostSide` →
`startDurableReviewPipelineHostSide`, which returns `false` in any process without
the registered handler (every CLI process), printing one line per wedged issue:

```
[review-status] durable review pipeline unavailable or already in flight for PAN-2510 (host-side)
```

The flood repeats on every CLI invocation and dashboard boot. Three structural gaps
sustain it:

1. **No age-out.** `needsReviewDispatch()` (`src/lib/review-dispatch-decision.ts:22-35`)
   treats "requested, never spawned" as a live dispatch need forever.
2. **No handler gate.** `dispatchReviewHostSide()` attempts the durable pipeline even
   when no handler is registered in the process, and logs at info level on every
   failure (`src/lib/review-status.ts:550-552`).
3. **No reaper coverage.** `reconcileClosedIssueAgents` discovers closed issues only
   via residue signals — running agents, tmux sessions, workspace dirs, agent dirs,
   devnet networks (`src/lib/cloister/closed-issue-reaper.ts:169-264`) — and
   `reapIssueResidue` (`src/lib/cloister/reap-issue-residue.ts:18-109`) cleans tmux /
   Docker / workspace / branches / agent dirs but never touches the review_status row
   or the journal `pipeline` block. The eleven wedged issues have none of the residue
   signals left, so the reaper never looks at them. (No stuck/swarm flag gate was
   found in the reaper; the "swarming off (global)" flag on PAN-2257 is incidental —
   the structural gap is the missing review-status sweep.)

**The ledger half (operator-added scope).** The same wedge blocks close-out: those
records sit at `pending/pending/pending`, so DoD rows 1/2/3 `miss` and `pan close`
refuses without `--accept-*` overrides. Tonight 22 issues (these 11 + 11 more
tracker-closed residue issues) sit in exactly that state. PAN-3188 just established
the precedent that DoD rows resolve MECHANICALLY for terminal landing classes (row 5
terminal states, row 7 keyed to row 6's skip); PAN-3180 established the verdict-row
waiver pattern for strike-landed issues (rows 1/2 `skip` when no specialist was ever
dispatched, but never for a negative verdict). Rows 1/2/3 have no equivalent
terminal-closed rule, so every one of the 22 needs an individual operator judgment
call — which does not scale.

## Requirements

### Functional

- **FR-1** — A review request older than a bounded age is dead: `needsReviewDispatch`
  returns `false` for it, and a new pure `isReviewRequestStale()` predicate identifies
  it. Bound: `REVIEW_REQUEST_MAX_AGE_MS = 7 days` (see D1).
- **FR-2** — When the reconcile-on-read path encounters a stale (dead) request, it
  clears `reviewRequestedAt` from the journal and DB through the status write door
  (`setReviewStatusSync`), best-effort, instead of re-attempting dispatch — and emits
  one warn-level log + activity entry per issue per process.
- **FR-3** — `dispatchReviewHostSide` never attempts the durable pipeline when no
  handler is registered in the process (new `hasDurableReviewPipelineHandler()`);
  it logs at most one debug-level line per process in that case.
- **FR-4** — The closed-issue reaper sweep clears unserviced review-request intent
  (`reviewRequestedAt`/`reviewSpawnedAt`) for tracker-closed issues through the status
  write door, regardless of how much other residue the issue has, and logs each
  clearing as a deacon action.
- **FR-5** — DoD rows 1/2/3 resolve mechanically for **terminal-closed with landed
  work** issues, per the rule in D7/D8: never-requested verdicts resolve `skip` with
  the real (absent) verdict and the reason preserved in the observed string; negative
  test/verification verdicts resolve `skip` only when row 6 proves the landed state
  green (superseded); negative review verdicts and unprovable supersession stay
  `miss` (operator `--accept-*` territory). Issues that are closed WITHOUT landed
  work (row 4 miss) get no settling — rows 1/2/3 stay `miss`.
- **FR-6** — Documentation: `docs/REVIEW-AGENT-ARCHITECTURE.md` documents the
  extended intent lifecycle (request → serviced → consumed → **dies at 7 days /
  tracker-close**) and the handler gate; `docs/DEFINITION-OF-DONE.md` documents the
  rows 1/2/3 terminal-settling rule including the never-requested vs
  stale/superseded distinction.
- **FR-7** — A one-time repair closes out the close-out backlog through
  `pan close <id>`: the 11 named PAN issues plus the remaining tracker-closed,
  not-closed-out residue discovered at execution time (target: the operator's count
  of 22 total), verifying tree-merged status via close-out's own DoD audit and using
  NO `--accept-*` overrides. Any issue that still refuses (e.g. a negative verdict
  that stays `miss` under D8) is surfaced with its blocking row, not forced. The
  repair runs as an auditable checked-in script.

### Non-functional

- **NFR-1** — No new configuration knobs. The age bound is a named exported constant.
- **NFR-2** — Read-path clearing (FR-2) never throws and never re-enters the
  reconcile: it must pass the already-reconciled status as the `existing` merge base
  to `setReviewStatusSync` (third parameter), because `setReviewStatusSync` otherwise
  calls `getReviewStatusSync` internally (`src/lib/review-status.ts:183`) which would
  re-run the reconcile → hook → clear chain.
- **NFR-3** — Server behavior with a registered handler is unchanged for live
  (non-stale, tracker-open) issues: fresh unserviced requests still auto-dispatch on
  read with the existing 30 s throttle.
- **NFR-4** — Tests touching the throttle/clear maps or age boundaries use
  `vi.useFakeTimers()` / explicit injected `now` — never real wall-clock delays
  (repo rule: fake timers for retry/backoff/delay-based tests).
- **NFR-5** — The DoD settling (FR-5) never converts a verdict to `pass` the
  pipeline did not earn: terminal settling is `skip` (deliberately resolved without
  a verdict), never `pass` (ran and succeeded), exactly the PAN-3180 strike-waiver
  semantics. The observed string always carries the original verdict value so the
  close-out record stays honest.

## Decisions (made in this document — do not re-litigate at implementation time)

- **D1 — the age bound is 7 days, not 24 hours.** The auto-heal's real value is
  long-outage recovery: an issue whose `pan done` fired while the dashboard was down
  for a weekend MUST still dispatch on Monday. 24 h would silently clear those.
  7 days is orders of magnitude beyond any planned downtime, while a request
  unserviced for a week is wedged by any measure. The eleven live wedges are 18–28
  days old, so 7 days kills all of them immediately. Clearing is visible (warn log +
  activity entry), and an operator can always re-request via `pan done` or
  force-review.
- **D2 — clearing happens on the read path in ANY process, best-effort.** The flood
  originates in CLI boots, so a deacon-only sweep cannot be the only clear mechanism.
  Writing-through-the-door on read is the established pattern here: the reconcile
  already upserts the DB and emits events on read
  (`src/lib/review-status-reconcile.ts:134-141`), and the `closedOut` journal branch
  already deletes rows on read (`src/lib/review-status-read.ts:20-27`). A sandboxed
  read-only reader's clear attempt fails silently (try/catch) — the age-out alone
  still suppresses the flood for that process.
- **D3 — the tracker-closed check lives in the async deacon sweep, not the sync read
  path.** `isIssueClosed()` is async (`src/lib/cloister/issue-closed.ts:102-111`);
  `needsReviewDispatch` is deliberately pure and sync. The issue's "(or its callers)"
  wording permits caller-side placement; the reaper sweep is that caller.
- **D4 — the sweep clears intent fields only; it does NOT delete review_status rows
  or mark `closedOut`.** Deleting the DB row is pointless churn (the next read
  reconciles the journal back into an inert row), and stamping `closedOut` would fake
  the close-out ceremony and corrupt `pan close`'s audit. Verdict history in the
  journal is untouched. Full row deletion for the backlog remains close-out's job and
  happens via FR-7.
- **D5 — the handler gate lives in `dispatchReviewHostSide`, not in
  `startDurableReviewPipelineHostSide`.** The latter's `false` return conflates
  "no handler" with "already in flight"; changing its contract would touch the
  server's registered path. A separate `hasDurableReviewPipelineHandler()` predicate
  keeps the server path byte-identical.
- **D6 — the repair is a checked-in script, run once, no overrides.** It produces an
  auditable artifact of exactly what was closed and what refused, and satisfies the
  xBRIEF files_scope gate. It runs AFTER the code items so the flood can be observed
  before and after on a live CLI boot.
- **D7 — rows 1/2/3 settle mechanically ONLY for terminal-closed WITH landed work.**
  The settling gate is: tracker-terminal (closed/completed/cancelled) AND row 4
  (`merged`) `pass`. The landed-work condition is the protective asymmetry: for a
  closed-as-won't-fix issue with no landed work, rows 1/2/3 stay `miss` and close-out
  keeps demanding an explanation. For landed work the verdict gate's purpose —
  keeping unverified code OFF main — is already moot: the code IS main and the
  tracker issue is closed, so nobody will act on a late blocked verdict. This mirrors
  PAN-3188's row 6→7 skip chain (compute the dependency row, pass its status
  through) applied to rows 1/2/3.
- **D8 — the never-requested / stale-superseded / negative distinction.**
  - **Never requested** (verdict `pending`/missing — the MIN-305 class): resolve
    `skip`. A specialist that was never dispatched is a different fact from one that
    said no (PAN-3180's exact logic); for terminal-closed landed work the absent
    verdict is settled, not waived.
  - **Negative review verdict** (`failed`/`blocked`/`dispatch_failed` on row 1):
    stays `miss`, always. A blocked review is a human design judgment about landed
    code; green CI does not supersede it.
  - **Negative test/verification verdict** (rows 2/3 — the PAN-1919 class,
    `test: failed` on code whose modern main is green): resolve `skip` ONLY when row
    6 (`main-verify`) `pass` on the landed merge commit — green CI on the landed
    state mechanically supersedes a specialist failure recorded against an older
    snapshot. If row 6 does not pass (skip or miss), supersession is unprovable and
    the verdict stays `miss` — operator judgment.
  - In every `skip` the observed string preserves the original verdict value and
    anchor, so the close-out ledger shows what actually happened (NFR-5).
- **D9 — settle, never recover.** We do NOT re-run or reconstruct review/test/
  verification verdicts for terminal-closed issues (no re-dispatching specialists
  against ancient commits, no fabricating `passed` from tree state). The only
  mechanical resolutions are `pass` (a real verdict exists) and `skip` (D8 rule).
  Anything else is an operator `--accept-*` decision, recorded in the close-out
  record as today.

```ts
export const REVIEW_REQUEST_MAX_AGE_MS = 7 * 24 * 60 * 60 * 1000;

export function isReviewRequestStale(params: {
  reviewRequestedAt?: string;
  now?: number;
  maxAgeMs?: number;
}): boolean {
  if (!params.reviewRequestedAt) return false;
  const now = params.now ?? Date.now();

  return now - Date.parse(params.reviewRequestedAt) > maxAge;
}
```

```ts
const staleReviewRequestClearAttemptedAt = new Map<string, number>();

function maybeAutoDispatchReviewHostSide(issueId: string, status: ReviewStatus): void {
  if (!needsReviewDispatch({
    reviewRequestedAt: status.reviewRequestedAt,
    reviewSpawnedAt: status.reviewSpawnedAt,
    reviewStatus: status.reviewStatus,
    mergeStatus: status.mergeStatus,
    readyForMerge: status.readyForMerge,
  })) {
    clearStaleReviewRequestHostSide(issueId, status);
    return;
  }
  const last = reviewDispatchAttemptAt.get(issueId) ?? 0;
  if (Date.now() - last < REVIEW_AUTO_DISPATCH_THROTTLE_MS) return;
  reviewDispatchAttemptAt.set(issueId, Date.now());
  void dispatchReviewHostSide(issueId, status.prUrl);
}

function clearStaleReviewRequestHostSide(issueId: string, status: ReviewStatus): void {
  if (!isReviewRequestStale({ reviewRequestedAt: status.reviewRequestedAt })) return;
  if (staleReviewRequestClearAttemptedAt.has(issueId)) return;
  staleReviewRequestClearAttemptedAt.set(issueId, Date.now());
  try {
    // NFR-2: pass the reconciled status as the merge base — setReviewStatusSync would
    // otherwise re-enter getReviewStatusSync → reconcile → this hook (recursion).
    setReviewStatusSync(issueId, { reviewRequestedAt: undefined }, status);
    const message =
      `cleared stale review request for ${issueId} — unserviced request older than ` +
      `${REVIEW_REQUEST_MAX_AGE_MS / (24 * 3_600_000)}d will not be re-dispatched`;
    console.warn(`[review-status] ${message} (host-side)`);
    emitActivityEntrySync({ source: 'cloister', level: 'warn', issueId, message });
  } catch {
    // Sandboxed read-only reader — the host's next writable read clears it. The
    // age-out alone still suppresses the dispatch flood in this process.
  }
}
```

```ts
export async function dispatchReviewHostSide(issueId: string, prUrl?: string): Promise<void> {
  try {
    const [{ startDurableReviewPipelineHostSide, hasDurableReviewPipelineHandler }, { spawnReviewRoleForIssue }] =
      await Promise.all([
        import('./cloister/durable-review-pipeline.js'),
        import('./cloister/review-agent.js'),
      ]);

      // CLI / one-shot process: only the dashboard server registers the handler
      // (src/dashboard/server/services/durable-review-pipeline.ts:129), so a
      // host-side dispatch can never succeed here. One debug line per process.
      if (!loggedMissingPipelineHandler) {
        loggedMissingPipelineHandler = true;
        console.debug(
          '[review-status] no durable review pipeline handler registered in this process — skipping host-side review dispatch',
        );
      }
      return;
    }
    const started = await startDurableReviewPipelineHostSide({
      issueId,
      ...(prUrl ? { prUrl } : {}),
      setReviewPending: (update) => setReviewStatusSync(issueId, update),
      dispatchReview: (context) => Effect.runPromise(spawnReviewRoleForIssue(context)),
    });
    if (!started) {
      console.log(`[review-status] durable review pipeline unavailable or already in flight for ${issueId} (host-side)`);
    }
  } catch (err) {
    console.warn(`[review-status] host-side review auto-dispatch for ${issueId} did not complete (non-fatal): ${err instanceof Error ? err.message : String(err)}`);
  }
}
```

```ts
export async function reapClosedIssueReviewRequests(
  closedChecks: Map<string, Promise<boolean>>,
): Promise<string[]> {
  const actions: string[] = [];
  const { getAllReviewStatusesFromDb } = await import('../overdeck/review-status-sync.js');
  const { readJournalStatusSync } = await import('../overdeck/review-status-record-sync.js');
  const { setReviewStatusSync } = await import('../review-status.js');
  const rows = getAllReviewStatusesFromDb();
  for (const [issueId, row] of Object.entries(rows)) {
    if (row.reviewStatus !== 'pending') continue;
    const journal = readJournalStatusSync(issueId);
    const requestedAt = journal?.durable?.reviewRequestedAt;
    if (!requestedAt) continue;
    const spawnedAt = journal?.durable?.reviewSpawnedAt;
    if (spawnedAt && Date.parse(requestedAt) <= new Date(spawnedAt).getTime()) continue;
    if (!await isClosedIssue(issueId, closedChecks)) continue;
    // NFR-2: build the merge base ourselves (DB row + journal durable overlay, the
    // same merge reconcileJournalIntoCacheSync performs) and pass it as `existing` —
    // otherwise setReviewStatusSync's internal getReviewStatusSync would re-run the
    // reconcile and, in the server, dispatch a review for this closed issue.
    const existing = { ...row };
    for (const [key, value] of Object.entries(journal.durable)) {
      if (value !== undefined) (existing as Record<string, unknown>)[key] = value;
    }
    setReviewStatusSync(issueId, { reviewRequestedAt: undefined, reviewSpawnedAt: undefined }, existing);
    const action = `cleared unserviced review request for tracker-closed ${issueId}`;
    actions.push(action);
    console.log(`[deacon] ${action}`);
    emitActivityEntrySync({ source: 'cloister', level: 'info', issueId, message: `[deacon] ${action}` });
  }
  return actions;
}
```

  cleared).

  `--accept-*` territory by design).
- Extending terminal settling to issues that are closed WITHOUT landed work (D7 —
  those keep their `miss` and their demand for an explanation).

## Hazards

- **H1 — re-entrant reconcile.** Any clearing that calls `setReviewStatusSync`
  WITHOUT the `existing` merge base re-enters `getReviewStatusSync` → reconcile →
  hooks; in the server that can dispatch a review for the very issue being cleared.
  Both WI-2 and WI-4 must pass `existing`. Mitigated by NFR-2 and named tests.
- **H2 — time-bomb existing tests.** `src/lib/__tests__/review-dispatch-decision.test.ts`
  uses fixed 2026-06-20 dates that are already older than the 7-day bound; WI-1
  explicitly updates them to inject `now`.
- **H3 — long-outage false positive.** A genuinely open issue whose dashboard was
  down >7 days loses its pending review dispatch (logged, activity-entered,
  recoverable via `pan done` / force-review). Accepted in D1.
- **H4 — journal-only wedges.** The sweep enumerates DB rows, so a wedge whose DB
  row was deleted is only caught after some read reconciles it back. Acceptable: the
  read-path clear (WI-2) fires on exactly that read.
- **H5 — module-global handler in tests.** WI-3's predicate reads a module-global
  with no unregister; tests must not let a registration leak across files. Follow the
  repo's existing isolation pattern.
- **H6 — settling weakens the gate.** WI-5 widens what close-out accepts
  mechanically; a bug in the landed-work gate (row 4 false pass) would settle
  verdicts for work that never landed. Mitigation: settling requires row 4 `pass`
  computed by the same multi-evidence `checkMergedRow` used today, and the
  tracker-open case is covered by a named test.
- **H7 — repair-before-merge sequencing.** WI-7 needs a `pan` binary containing
  WI-5; running the installed CLI (built from main) would refuse rows 1/2/3 and
  produce 22 refusals. The item explicitly builds the workspace CLI first.
