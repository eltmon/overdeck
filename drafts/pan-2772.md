# PAN-2772 — Restart blast radius: patient terminal reconnect, restart broadcast, agent restart gating

**Issue:** https://github.com/eltmon/overdeck/issues/2772
**Author:** planning agent (claude-fable-5), 2026-07-16, auto mode

## Glossary

- **Terminal panel** — the xterm.js host component `src/dashboard/frontend/src/components/XTerminal.tsx`, connected to `/ws/terminal?session=<name>` (raw WebSocket, server side `src/dashboard/server/ws-terminal.ts`).
- **RPC channel** — the Effect RPC WebSocket at `/ws/rpc` consumed by `src/dashboard/frontend/src/components/EventRouter.tsx`. It already reconnects indefinitely and re-bootstraps the snapshot on reconnect.
- **Reconnect budget** — XTerminal's current retry policy: `maxReconnectAttempts = 5` (XTerminal.tsx:141) with exponential backoff 1/2/4/8/16s (`getReconnectDelay`, XTerminal.tsx:198) ≈ 31s total, ending in a dead-end message (XTerminal.tsx:716).
- **Restart blast radius** — every `pan restart` (~18–21s down) / `pan reload` (~46–62s down) severs all `/ws/terminal` and `/ws/rpc` sockets; the tmux + Claude sessions underneath survive.
- **Deploy-window block reasons** — `getDeployBlockReason()` in `src/lib/deploy/deploy-window.ts:41`: verification in flight, an active flywheel run owns deployment, merge specialist active, pending post-merge, restart lock held, dev supervisor running. The deploy patrol (`src/lib/cloister/deploy-patrol.ts:165`) already defers on these; agent-issued `pan restart`/`pan reload` currently ignore them entirely.
- **Initiator** — `process.env.OVERDECK_AGENT_ID`, already recorded into restart-status by both commands (`src/cli/commands/restart.ts:184`, `src/cli/commands/reload.ts:177`). Conversations are `conv-*`, pipeline agents `agent-*`, the flywheel is `flywheel-orchestrator`. Unset = human operator shell.
- **Close code 4404** — existing "session not found" fatal close (`ws-terminal.ts:272`); the client treats it as terminal-session-gone and does not retry (XTerminal.tsx:697).
- **Close code 4503** — NEW close code this plan introduces: "server restarting", sent to all terminal clients during graceful shutdown.

## Problem

On 2026-07-15 the dashboard server was restarted 8 times in ~3 hours by conversations and the flywheel deploying fixes. Each restart severed every live conversation's WebSockets mid-typing. The terminal reconnect budget (5 tries ≈ 31s, failing fast while Traefik answers instantly) dies before a `pan reload` (46–62s) finishes, leaving a permanently dead panel with no retry affordance — operators abandoned live sessions that were actually still running.

Three compounding defects:
1. The terminal reconnect budget is attempt-counted, smaller than a reload, and ends in a dead end.
2. Clients get no signal that the disconnect is a planned restart, so they show scary connection-lost errors.
3. Agent-issued `pan restart`/`pan reload` bypass the deploy patrol's ownership/deferral gates that the automated deploy path respects.

## Requirements

### Functional

- **FR-1 (patient reconnect):** The terminal panel retries for a time-based window of at least 5 minutes after an unexpected close — exponential 1/2/4/8/16s, then flat 5s — instead of giving up after 5 attempts. 4404 stays fatal. A successful reattach (snapshot received) resets the window.
- **FR-2 (no dead end):** While reconnecting, the panel shows a non-alarming status; when the window finally exhausts, the panel offers a clickable "Reconnect" action that restarts the retry cycle. The red "Could not reconnect after N attempts" dead end is gone.
- **FR-3 (restart broadcast):** On graceful shutdown (SIGTERM/SIGINT/SIGHUP), the server closes every `/ws/terminal` client with close code 4503 reason `server-restarting` before tearing down services.
- **FR-4 (restart-aware client):** The terminal panel treats close code 4503 as a planned restart: it shows "Dashboard restarting — reconnecting automatically…" (calm styling, no red error) and enters the patient retry cycle.
- **FR-5 (agent restart gate):** When `OVERDECK_AGENT_ID` is set and the restart scope includes the dashboard, `pan restart` and `pan reload` consult the deploy-window block reasons and refuse with the block reason (exit code 1) unless `--force` is passed. The flywheel-ownership reason does not block the flywheel itself (`OVERDECK_AGENT_ID === 'flywheel-orchestrator'`). Human operators (no `OVERDECK_AGENT_ID`) are never gated. When an agent restart proceeds, the command prints a notice that live conversations/terminals will be disconnected.
- **FR-6 (docs):** `sync-sources/skills/pan-restart/SKILL.md` and `sync-sources/skills/pan-reload/SKILL.md` document the agent gate and `--force` bypass (`scripts/lint-skills.sh` enforces flag parity in the same commit). The "Terminal architecture" bullets in the repo `CLAUDE.md` describe patient reconnect and the 4503 restart close code.

### Non-functional

- **NFR-1 (fake timers):** Any test exercising retry delays uses `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()` — never real waits (repo rule).
- **NFR-2 (async server):** No `execSync` or sync tmux primitives in any server-reachable code (repo rule).
- **NFR-3 (layering):** The restart broadcast is best-effort UX polish; patient reconnect must work without it (SIGKILL paths never broadcast).

## Design

### Patient reconnect (FR-1, FR-2, FR-4)

Extract a pure policy module `src/dashboard/frontend/src/lib/terminalReconnectPolicy.ts`:

```ts
export interface ReconnectPolicyState { attempt: number; windowStartedAt: number }
export const PATIENT_WINDOW_MS = 5 * 60_000;
export const FLAT_DELAY_MS = 5_000;
/** Returns the next delay in ms, or null when the window is exhausted. */
export function nextReconnectDelay(state: ReconnectPolicyState, now: number): number | null
```

Delays: `min(1000 * 2**attempt, FLAT_DELAY_MS)` → 1s, 2s, 4s, then flat 5s. Exhausted when `now - windowStartedAt >= PATIENT_WINDOW_MS`. Pure arithmetic — unit-testable without timers.

XTerminal replaces `maxReconnectAttempts`/`getReconnectDelay` with this policy. The per-attempt ANSI `writeln` spam (up to ~60 lines over 5 min) is replaced by a React connection-status overlay rendered above the terminal: `'connected' | 'reconnecting' | 'restarting' | 'failed'`. `'failed'` renders a Reconnect button that resets `ReconnectPolicyState` and calls `connect()`. Close code 4503 sets `'restarting'` with the calm message; any other unexpected close sets `'reconnecting'`. 4404 keeps today's session-ended behavior. The snapshot handler (XTerminal.tsx:645) resets the policy state and sets `'connected'`.

Hazard: the connect effect's dependency array (XTerminal.tsx:764) and the `onDisconnect` ref pattern (XTerminal.tsx:175) exist to prevent reconnect loops — keep policy state in refs, not React state, except the coarse overlay status.

### Restart broadcast (FR-3)

`ws-terminal.ts` exports `broadcastServerRestarting(): number` — iterate every PTY hub's clients, `ws.close(4503, 'server-restarting')`, return count closed. `handleShutdownSignal` in `src/dashboard/server/main.ts:544` calls it first thing after the `shuttingDown` guard. The hub map is module-local today; the new export reads it in place.

### Agent restart gate (FR-5)

New module `src/lib/deploy/agent-restart-gate.ts`:

```ts
export interface AgentRestartGateInput { initiator: string | undefined; force: boolean }
/** Returns a refusal message, or null when the restart may proceed. */
export async function agentRestartBlockReason(input: AgentRestartGateInput, deps?: Partial<DeployWindowDependencies>): Promise<string | null>
```

Behavior: `initiator` unset or `force` → null. Otherwise call `getDeployBlockReason`, injecting `getFlywheelActiveRunId: () => null` when `initiator === 'flywheel-orchestrator'`. Returned message must state the block reason AND how to proceed (`--force`) in complete sentences (operator-facing rule).

Wire into `restartCommand` (after the dev-supervisor refusal, before the restart lock, only for scope `dashboard`/`full`) and `reloadCommand` (before acquiring the lock). `pan restart` reuses its existing `--force` flag (help text extended); `pan reload` gains `--force` (registered at `src/cli/index.ts:1283`ff).

## Auto decisions

1. **RPC channel gets no restart control frame.** EventRouter already reconnects indefinitely, re-bootstraps, and offers a Retry overlay; the reported dead-end pain is the terminal panel. Adding a restart frame to the Effect RPC protocol is invasive for a cosmetic message change. Out of scope (NonGoals).
2. **Patient window = 5 minutes, flat 5s cadence.** Worst observed reload downtime is 62s; 5 minutes covers slow builds with wide margin without retrying forever against a dead server.
3. **Reconnect button only on window exhaustion, not on 4404.** After the server's respawn-pending wait (`ws-terminal.ts:269`), 4404 means the tmux session truly no longer exists — reconnecting cannot help.
4. **Reuse `--force` for the gate bypass** (extend help text; add `--force` to reload) rather than a new flag — fewer flags, wrapper skills updated in the same commit.
5. **Gate = hard refusal on deploy-window block reasons, not a live-attachment warning system.** The block reasons are the mechanically owned gates the deploy patrol already respects; counting live attachments would need the (dying) server's API and adds a race for little value. The unconditional disconnect notice covers awareness.
