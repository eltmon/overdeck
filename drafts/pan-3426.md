# PRD: PAN-3426 — `pan orders start` validates against an unstarted issue service

**Issue:** https://github.com/eltmon/overdeck/issues/3426
**Date:** 2026-08-01
**Mode:** `--auto` planning (decisions recorded in xBRIEF `autoDecisions[]`)

## Glossary

- **Order book** — an operator-curated Flywheel campaign stored on `overdeck-state`; a named list of issues with lanes, prereqs, and settings. Read door: `src/lib/orders/resolver.ts`. Write door: `src/lib/orders/writer.ts`.
- **`validateBookForStart()`** — the synchronous validator in `src/lib/orders/validate.ts:102` that returns `{ blocks, warns }` before a book may start. Any block refuses the start.
- **`liveOrderIssueLookup`** — the default issue-state lookup (`src/lib/orders/resolver.ts:41`) used by the validator and the dispatch gate. Reads the shared issue service via a lazy `require`.
- **Shared issue service** — the `IssueDataService` singleton in `src/dashboard/server/services/issue-service-singleton.ts`. Serves tracker issues from the shared SQLite cache. `getSharedIssueService()` constructs it lazily; `startSharedIssueService({ skipPolling: true })` loads the cache read-only with zero tracker API calls (PAN-1817).
- **Store-empty / store-unavailable** — the failure mode at the heart of this issue: the singleton exists but `start()` was never called in this process (CLI), or the cache genuinely contains zero issues (fresh machine).
- **CLI start path** — `pan orders start <id>` (`src/cli/commands/orders.ts:263`) and `pan flywheel start --orders <id>`, both funneling into `startFlywheelRun()` → `resolveFlywheelOrderStart()`.

## Problem

`pan orders start <book>` fails with `[issue-not-open] <ID>: <ID> could not be resolved as an open issue` for **every** issue in the book, including issues that are plainly open and cached (reproduced 2026-08-01 with book `2026-08-01-myn-hermes-smoke-test-remediation`, MIN-930…934).

Root cause, verified in this workspace:

1. `resolveFlywheelOrderStart()` (`src/cli/commands/flywheel-orders.ts:40`) calls `validateBookForStart(stateRoot, book)`.
2. The validator's default lookup is `liveOrderIssueLookup` (`src/lib/orders/validate.ts:120`), which lazy-requires the singleton and calls `getSharedIssueService().getIssues({ cycle: 'all', includeCompleted: true })` (`src/lib/orders/resolver.ts:47-48`).
3. `getSharedIssueService()` **constructs** the service on first call (`issue-service-singleton.ts:11-16`) without throwing — so the `try/catch` in the lookup (`resolver.ts:60-62`) swallows nothing because nothing throws.
4. In a CLI process nothing ever calls `startSharedIssueService()`, so `IssueDataService.start()` never runs `loadCachedData()` (`issue-data-service.ts:329`) and `getIssues()` returns `[]`.
5. Every wanted ID is therefore missing from the result map, and the validator emits `issue-not-open` with the "could not be resolved" message (`validate.ts:131-137`) for all of them.

Net effect: CLI `pan orders start` can never pass validation for any book in any project. The reporter verified that calling `startSharedIssueService({ skipPolling: true })` first in the same process returns 1258 cached issues and resolves the same IDs fine.

## Proposal

Two coordinated changes, both additive:

1. **Prime the store in the CLI start path.** `resolveFlywheelOrderStart()` becomes async and awaits a new injectable `prepareIssueStore` dep — default `ensureOrderIssueStore()` in `src/lib/orders/resolver.ts`, which calls `startSharedIssueService({ skipPolling: true })` through the same lazy-require pattern the lookup already uses. The singleton memoizes its start promise (`issue-service-singleton.ts:19-23`), so this is idempotent and free on the server, where boot already started it (`src/dashboard/server/main.ts:172-175`).
2. **Distinguish store-unavailable from issue-missing.** The validator gains a store probe, `orderIssueStoreStatus()` in `resolver.ts`, reporting `{ started, issueCount }`. When the **default** lookup is in use and the store is unstarted or empty, validation emits a single `issue-store-unavailable` block with an actionable message and skips the store-dependent `issue-not-open` / `unresolved-prerequisite` checks (they would be noise). Store-independent checks (empty-book, duplicate-membership, prerequisite-cycle, missing-prd) still run.

This is the issue's first suggested fix direction plus its suggested error-quality improvement, both implemented at the single chokepoints so every present and future caller (CLI, dashboard route, dispatch gate) benefits.

### Decision: prime the service vs. a separate CLI-safe cache reader

Chosen: prime the shared service. The issue offered both. A separate reader would duplicate `IssueDataService`'s cache-loading logic and create a second read path for the same domain — against the two-door tenet. `skipPolling` mode exists precisely for read-only cached consumers (PAN-1817, `issue-data-service.ts:311-338`), and `src/cli/commands/doctor.ts:339-361` already uses `CacheService` in a CLI process with no process-lifetime problems.

### Decision: block vs. warn for store-unavailable

Chosen: block. When the store cannot be read, validation has verified nothing; starting a Flywheel run against unverifiable issue state is unsafe. This matches the existing fail-closed comment in the lookup ("A non-server caller receives missing issue state and validation blocks safely", `resolver.ts:61`).

### Decision: make `resolveFlywheelOrderStart` async rather than hoisting the prime into `startFlywheelRun`

The store dependency travels with resolution. Hoisting it to the caller (`flywheel.ts:335`) would let the next caller of `resolveFlywheelOrderStart` repeat the bug. The function's only caller is already in an async context.

### Decision: store check only applies to the default lookup

When a caller injects `options.issueLookup` (tests, the dashboard route's `deps.issueLookup`), that injection defines its own truth; probing the singleton would be wrong. The check runs only when `options.issueLookup` is undefined.

## Requirements

- **FR-1** — `pan orders start <id>` and `pan flywheel start --orders <id>` validate against the populated shared issue cache, so open cached issues pass validation from a CLI process.
- **FR-2** — When the issue store is unstarted or empty, validation emits exactly one `issue-store-unavailable` block naming an actionable remedy, and does not emit per-issue `issue-not-open` or `unresolved-prerequisite` findings.
- **FR-3** — When the store is populated, genuinely missing or closed issues still produce `issue-not-open` blocks exactly as today (existing behavior preserved).
- **NFR-1** — The CLI start path makes zero tracker API calls: the service starts with `skipPolling: true` only (PAN-1817).
- **NFR-2** — The dashboard route `POST /api/orders/:id/start` and the order dispatch gate (`src/lib/orders/dispatch-gate.ts:82`) behave as before; the singleton's memoized start makes the extra prime a no-op on the server.
- **NFR-3** — Validation stays synchronous; no new sync I/O is introduced in server-reachable code beyond the existing lazy-require pattern.

```ts
/** Prime the shared issue store read-only (cached, zero tracker calls — PAN-1817). Idempotent. */
export async function ensureOrderIssueStore(): Promise<void> {
  // eslint-disable-next-line @typescript-eslint/no-require-imports
  const { startSharedIssueService } = require('../../dashboard/server/services/issue-service-singleton.js') as typeof import('../../dashboard/server/services/issue-service-singleton.js');
  await startSharedIssueService({ skipPolling: true });
}

/** Store health for validation: distinguishes "store unavailable" from "issue genuinely missing". */
export function orderIssueStoreStatus(): { started: boolean; issueCount: number } {
  try {
    // eslint-disable-next-line @typescript-eslint/no-require-imports
    const { getSharedIssueService, isSharedIssueServiceStarted } = require('../../dashboard/server/services/issue-service-singleton.js') as typeof import('../../dashboard/server/services/issue-service-singleton.js');
    const issueCount = (getSharedIssueService().getIssues({ cycle: 'all', includeCompleted: true }) as unknown[]).length;
    return { started: isSharedIssueServiceStarted(), issueCount };
  } catch {
    return { started: false, issueCount: 0 };
  }
}
```
