# PAN-3260 — Markdown file chips open the internal markdown editor in a tab by default

**Issue:** https://github.com/eltmon/overdeck/issues/3260
**Mode:** auto planning (no operator Q&A; defaults recorded in `plan.autoDecisions[]`)

## Glossary

- **File chip** — the inline pill rendered for a path-like token in chat markdown, implemented by `MarkdownFileLink` (`src/dashboard/frontend/src/components/chat/MarkdownFileLink.tsx`). Rendered only after `resolveFilePathExists` confirms the path exists.
- **Markdown chip** — a file chip whose target has a markdown extension: `.md`, `.mdx`, or `.markdown`.
- **External editor** — one of the 23 `EDITORS` entries in `packages/contracts/src/editor.ts:3-26` (Cursor, VS Code, Zed, …, file-manager), launched as a detached OS process by the server (`src/dashboard/server/services/open.ts`).
- **Internal editor / editor pane** — the new Stage pane (paneType `'editor'`) built by this issue: loads a markdown file's content, offers Edit and Preview sub-views, and saves back to disk.
- **Stage / deck** — the project-scoped tabbed pane surface (`src/dashboard/frontend/src/components/Stage/index.tsx`). Pane state lives in `usePanesStore` (`src/dashboard/frontend/src/lib/panesStore.ts`), keyed by `deckKey` (the project key). Conversations render inside the Stage as `agent` panes (`AgentPane` → `ConversationPanel`), so the reported flywheel-conversation chip lives inside a Stage.
- **Deck context** — the new React context (`StageDeckContext`) this issue adds so a deeply nested chip can open a pane in the deck it renders inside, without prop-threading through the markdown component tree.
- **File door** — the new server read/write RPC pair for markdown files addressed by absolute path (`pan.readFileAtPath` / `pan.writeFileAtPath`), independent of any issue/workspace.
- **Markdown open target** — the persisted preference for what a left click on a markdown chip does: `'internal'` or an external `EditorId`. Stored in localStorage, separate from the existing `overdeck:last-editor` key.

## Problem

Left-clicking any file chip calls `handleOpen()` (`MarkdownFileLink.tsx:174-188`, wired at `:288-292`), which resolves a preferred **external** editor and dispatches `pan.shellOpenInEditor`. Right-click (`:293-305`) offers exactly one open action — the same external path. There is no internal editor; `MarkdownTab` (`src/dashboard/frontend/src/components/CommandDeck/ZoneCOverviewTabs/MarkdownTab.tsx`) is a read-only renderer fed by planning queries, and the only file-content RPC, `pan.readWorkspaceFile` (`src/dashboard/server/services/read-workspace-file.ts`), requires an `issueId` and resolves paths relative to that issue's workspace. The reported case — the Flywheel brief chip `docs/flywheel-brief.md` inside the `flywheel-orchestrator` conversation — has **no issue and no workspace**, so any issue-scoped door cannot serve it (Quickview already fails there, `MarkdownFileLink.tsx:196-203`).

## Decisions already made in the issue (not re-litigated)

1. The internal editor **edits and saves** — not a viewer. Requires a write door; only reads exist today.
2. **Non-markdown chips keep today's external-editor behavior** unchanged.
3. **Internal is the default for markdown; external stays one right-click away.** The external path is not removed or degraded.
4. The editor must resolve **repo-root paths with no issue/workspace context** and be openable from a conversation view.

## Approach

Four layers, each small:

1. **Contracts** — add `pan.readFileAtPath` and `pan.writeFileAtPath` RPCs addressed by absolute path.
2. **Server file door** — one service implementing both, with realpath containment in an allowlist (registered project roots + `OVERDECK_HOME`), markdown-only extensions, a 1 MiB hard cap (error, never truncate — truncated content must never be savable), and mtime-based conflict detection on write.
3. **Editor pane** — new `paneType: 'editor'` + `EditorPane` component (Edit textarea / Preview via `MarkdownTab`'s `ChatMarkdown` rendering, Save button + Ctrl/Cmd+S, dirty indicator, conflict and too-large states).
4. **Chip behavior** — `StageDeckContext` lets `MarkdownFileLink` open/focus an editor pane in its deck. Left click on a markdown chip resolves the markdown open target (default `'internal'`); right click lists the internal editor plus every *available* external editor and persists the choice.

Where no deck context exists (popout conversation windows `/popout/conversation/<id>`, the `ConversationDock`, issue-drawer transcripts), a markdown chip falls back to today's external behavior. This is additive — no surface loses an affordance (no-loss audit: the existing menu items and external flow survive verbatim for every chip).

## Requirements

### Functional

- **FR-1** Contracts export `ReadFileAtPathInput/Result`, `WriteFileAtPathInput/Result` schemas, `WS_METHODS.readFileAtPath` / `WS_METHODS.writeFileAtPath`, and register both Rpcs in `PanRpcGroup`.
- **FR-2** `pan.readFileAtPath` returns `{ text, lang, mtimeMs, totalLines }` for an allowlisted markdown file; rejects paths outside the allowlist (`PATH_NOT_ALLOWED`), non-markdown extensions (`UNSUPPORTED_FILE_TYPE`), missing files (`FILE_NOT_FOUND`), and files over 1 MiB (`FILE_TOO_LARGE`).
- **FR-3** `pan.writeFileAtPath` writes UTF-8 content under the same validation, honors optional `expectedMtimeMs` (mismatch → `WRITE_CONFLICT`, nothing written), and returns the new `mtimeMs`.
- **FR-4** A new Stage pane type `'editor'` renders `EditorPane`: loads via the read door, Edit/Preview sub-tabs, Save (button and Ctrl/Cmd+S) via the write door, dirty indicator, conflict state offering Reload / Overwrite, too-large state offering "Open externally".
- **FR-5** `Stage` provides `StageDeckContext` (deck key + `openOrFocusEditorPane(filePath, label)` with focus-if-open semantics) around everything it renders, including the `renderHome`/`renderIssue` render props.
- **FR-6** Left click on a markdown chip with markdown open target `'internal'` (or unset) opens/focuses the editor pane in the current deck; no external editor launches. With an external target, it opens that editor. Without deck context and target `'internal'`, it falls back to the existing external flow.
- **FR-7** Right click on a markdown chip shows: "Open in internal editor", one "Open in <label>" item per available external editor, "Copy relative path", "Copy full path". Choosing any open item opens it there and persists the markdown open target. Non-markdown chips keep today's exact menu.
- **FR-8** The markdown open target persists in localStorage (`overdeck:markdown-open-target`) and survives reload; the existing `overdeck:last-editor` key and non-markdown behavior are untouched.

### Non-functional

- **NFR-1** No `execSync` anywhere server-reachable; all fs via `node:fs/promises`.
- **NFR-2** No new npm dependencies (plain `<textarea>`; no CodeMirror/Monaco).
- **NFR-3** Additive only: every existing chip affordance (external open, copy items, Quickview) still works; existing `MarkdownFileLink` tests keep passing (extended, not rewritten).
- **NFR-4** The write door never persists truncated content: oversize files are rejected at read time, so the editor can never hold a truncated buffer.
- **NFR-5** Frontend styling follows the dashboard style guide (reuse `stage.module.css` subTab patterns; no new fonts/colors).

### W2 — Server file door service + wiring (FR-2, FR-3)

**Files:** new `src/dashboard/server/services/file-at-path.ts`, new `src/dashboard/server/services/__tests__/file-at-path.test.ts`, `src/dashboard/server/ws-rpc.ts` (handlers block at `:1040-1053`).

Model the service on `read-workspace-file.ts` (capped read, `PanRpcError` codes, `Effect.tryPromise` wrapper, symlink-safe `realpath` + `isInsidePath` containment — reuse its shape, `read-workspace-file.ts:48-50,120-133`). Validation, shared by read and write:

1. `path` must be absolute (`isAbsolute`), ≤ 4096 chars.
2. Extension must be `.md`, `.mdx`, or `.markdown` → else `UNSUPPORTED_FILE_TYPE`.
3. Allowlist roots = `realpath` of every registered project path (`listProjectsSync()` from `src/lib/projects.ts:307`, each `config.path`) plus `realpath(OVERDECK_HOME)` (`src/lib/paths.ts:6`) — covers repo-root files, workspaces (they live under the project root), and state-worktree drafts. `realpath(resolvedPath)` must be inside one root → else `PATH_NOT_ALLOWED`.
4. Must be a regular file (write: or not exist yet is still an error — the editor only edits existing chip targets; `FILE_NOT_FOUND`).

Read: full UTF-8 read; `stat.size > 1 MiB` → `FILE_TOO_LARGE` (never truncate); return `{ text, lang: languageForPath(path), mtimeMs: stat.mtimeMs, totalLines }`. Write: when `expectedMtimeMs` present and `stat().mtimeMs !== expectedMtimeMs` → `WRITE_CONFLICT` without writing; else `writeFile`, re-`stat`, return `{ mtimeMs }`. Wire both into `ws-rpc.ts` next to `readWorkspaceFile`.

Tests (Vitest, temp dirs, no fake timers needed — no delays): containment accept/reject (project root, OVERDECK_HOME, `/etc/passwd`-style reject, symlink escaping the root rejected), extension gate, too-large, conflict, happy-path read/write round-trip.

## Acceptance criteria (issue-level)

1. Left-clicking a markdown file chip in a deck conversation opens the internal markdown editor as a tab; `shellOpenInEditor` is not called.
2. The Flywheel-brief case — a repo-root markdown chip in a conversation with no workspace/issue — opens and renders in the editor pane; covered by a named test in `MarkdownFileLink.test.tsx`.
3. Right-clicking a markdown chip lists the internal editor and the available external editors; choosing either opens it there and the choice survives a reload (localStorage).
4. Edits saved in the internal editor persist to disk and reappear after closing and reopening the tab.
5. Non-markdown chips behave exactly as before (left click external, three-item menu).
6. All pre-existing `MarkdownFileLink` tests pass unmodified in intent (mock additions allowed).

## Out of scope (NonGoals)

- No internal editing for non-markdown files; `EDITORS` in contracts stays external-only.
- No internal-editor entry in surfaces without a deck (popout conversation windows, ConversationDock, issue-drawer/session transcripts) — they keep the external fallback; follow-up material.
- No rich markdown editing (CodeMirror/Monaco/WYSIWYG), no autosave, no multi-file tabs within one pane.
- No changes to Quickview, `readWorkspaceFile`, or the `overdeck:last-editor` preference semantics.
- No file creation or deletion through the file door — existing files only.

## Hazards

- **H1** Stage self-heal (`ISSUE_SCOPED`, `Stage/index.tsx:156`) closes panes without `issueId` — `'editor'` must not join that set or persisted editor tabs get deleted on load.
- **H2** Truncated-save data loss: the door must reject >1 MiB reads outright rather than truncating, or a save would silently drop the file tail.
- **H3** Concurrent modification by agents is routine here — the `expectedMtimeMs` conflict gate is load-bearing, not speculative.
- **H4** `getAvailableEditors` is async but `showContextMenu` is sync — capture coordinates before awaiting; cache module-level; degrade to internal+copy items on fetch failure.
- **H5** Persisted panes hydrate from localStorage (`isValidPane`, `panesStore.ts:111-120`) — new optional fields pass, but verify an `editor` pane without `editorFilePath` renders an error state, not a crash.
- **H6** Symlink escape: containment must check `realpath` of the target, as `read-workspace-file.ts:128-133` does.
