# PRD: PAN-3419 — `pan handoff --project` and explicit conversation→project association

**Issue:** [PAN-3419](https://github.com/eltmon/overdeck/issues/3419)
**Status:** Draft (planning `--auto`, 2026-08-01)
**Related:** [PAN-1577](https://github.com/eltmon/overdeck/issues/1577) (move-conversation UX — builds on the column this issue creates), [PAN-2590](https://github.com/eltmon/overdeck/issues/2590) (deck identifies projects by display name), [PAN-1990](https://github.com/eltmon/overdeck/issues/1990) (projects/workspaces domain; the `workspace_id` schema-top-up pattern this issue follows).

## Glossary

- **Registered project** — an entry in `~/.overdeck/projects.yaml`. It has a yaml **key** (the map slug, e.g. `mind-your-now`), a **display name** (`name:`, may differ from the key), and a **path** on disk. Surfaced to the frontend by `GET /api/registered-projects` (`src/dashboard/server/routes/misc/meta.ts:128-153`) as `{key, name, path, ...}`.
- **Conversation row** — a row in the `conversations` table of `~/.overdeck/overdeck.db`, read/written only through the door module `src/lib/overdeck/conversations.ts`. Its TypeScript DTO is `LegacyConversation` (`conversations.ts:642-673`).
- **Explicit project association** — the new nullable `project_key` TEXT column on the conversation row holding a registered project's **yaml key**. NULL means "no explicit association; derive from cwd".
- **cwd containment** — today's grouping rule: a conversation belongs to project P when `conv.cwd === P.path || conv.cwd.startsWith(P.path + '/')`.
- **No-project bucket** — the dashboard group (`NO_PROJECT_KEY = '__no-project__'`, `projectsData.ts:13`) for conversations matching no registered project.
- **Effective project (of a conversation)** — `project_key` if set and matching a registered project, else the cwd-containment match, else none.
- **Fork/handoff** — `POST /api/conversations/:name/summary-fork` creates a successor conversation row and spawns its session. `pan handoff` and `pan fork` both reach this route through `src/cli/commands/fork-client.ts`; the dashboard ForkModal reaches it via `useConversationMutations.summaryForkConversation`.
- **Write door** — `src/lib/overdeck/conversations.ts`, the only module allowed to write conversation rows.
- **Deck identifier** — the string the frontend uses to select a project deck: `name ?? key` of the registered project (see `resolveConversationProjectName`, `CommandDeck/index.tsx:502-512`, and the palette's `p.config.name ?? p.key` at `palette.ts:238`).

## Problem

`pan handoff` has no way to say which project the successor conversation belongs to. Project membership is inferred purely from cwd containment, and the standing universal rule that spawned agents must run in an **isolated `--cwd`** (`sync-sources/rules/handoff-isolate-cwd.md`) guarantees that cwd is outside every registered project path. Every correctly-isolated handoff therefore lands in the No-project bucket by construction — invisible in the project tree the operator actually works from. Live repro 2026-08-01: conv 1827 (`20260801-2fc7`, cwd `/home/eltmon/Projects/hoff-agent-surface`) does entirely MYN work but groups under No project because `/home/eltmon/Projects/hoff-agent-surface` is not under `/home/eltmon/Projects/myn`.

The fork/handoff route handler (`handleConversationSummaryFork`, `src/lib/overdeck/conversation-forks.ts:652-818`) accepts `model`, `cwd`, `issueId`, `focus`, etc. — no project field. `POST /api/conversations` accepts `projectKey` (`conversation-runtime.ts:889-898`) but only converts it to a cwd; the key itself is never stored.

## Proposal

Introduce **one** explicit association primitive — a nullable `project_key` column on the conversation row — and thread it through every surface that creates or groups conversations:

1. **Store** the association on the row (schema top-up + door support + a `setConversationProjectKey` writer that PAN-1577's move UX will reuse).
2. **Fork/handoff inherits**: the summary-fork route accepts an optional `projectKey` (yaml key or display name, validated loudly) and, when omitted, stores the **source conversation's effective project** on the successor — never re-deriving from the successor's own cwd.
3. **CLI**: `pan handoff --project <key>` (and `pan fork --project <key>`, same route, same defect class) forward the value; unknown projects fail non-zero with the server's error.
4. **Group explicit-first**: every grouping surface (sidebar/deck bucketing, deck selection routing, command-palette routing) resolves the explicit association before falling back to cwd containment, so existing rows (NULL) keep working unchanged.
5. **Modal**: the Fork/Handoff modal gains a Project select defaulted to "Same as source".
6. **Backfill conv 1827** to `mind-your-now` through the write door.

### Decision: one mechanism shared with PAN-1577

PAN-1577 (still open) proposes an explicit `projectKey` override column for its move-conversation UX, "so the JSONL on disk is never relocated". This issue lands exactly that column and its writer; PAN-1577 then only adds the move endpoint/CLI/drag-drop UX on top. One column, one writer, one read-side resolution order — no second mechanism.

### Decision: `project_key` (yaml key), not reuse of `workspace_id`

The row already has `workspace_id` (`infra.ts:277`), derived from `resolveWorkspaceForCwd(cwd)` at creation (`conversations.ts:1209-1217`). It was rejected as the association vehicle because (a) it is cwd-derived state, not an explicit choice — overloading it would silently change memory-home attribution (memory is keyed by workspace UUID); (b) project grouping would need a workspace→project join the frontend cannot do today; (c) PAN-1577's leaning is a `projectKey` override column. A plain nullable TEXT column of the yaml key is the smallest mechanism that satisfies both issues.

### Decision: no fork-blob field

The issue notes the persisted fork request blob (`ForkRequest`, `conversations.ts:627-640`) carries no project field. The blob exists so `recoverStuckForks` can re-run the pipeline for a row that already exists (`conversation-forks.ts:583-638`); the association is written to the row at `createConversation` time before the pipeline starts, so recovery never needs it in the blob. Adding it would be dead weight.

### Decision: `resolveRegisteredProjectKey` does NOT require the path to exist

`resolveProjectCwd` (`conversation-runtime.ts:867-876`) rejects a registered project whose path is missing, because it must return a usable cwd. The new `resolveRegisteredProjectKey` validates association only — a successor's cwd is independent of the project path — so it accepts a key-or-name match regardless of path existence. Unknown identifiers still fail loudly. `POST /api/conversations` keeps its existing `resolveProjectCwd` behavior and additionally stores the canonical key.

## Requirements

### Functional

- **FR-1** — `POST /api/conversations/:name/summary-fork` accepts an optional `projectKey` body field, resolving either a projects.yaml key or a display name to the canonical yaml key (same acceptance rule as `resolveProjectCwd`). An unknown value returns HTTP 400 naming the unknown project; no conversation is created.
- **FR-2** — When `projectKey` is omitted from the fork body, the successor row stores the source conversation's effective project (source's `project_key`, else cwd-containment match of the **source's** cwd). When the source has none, nothing is stored.
- **FR-3** — `pan handoff --project <key>` and `pan fork --project <key>` forward `projectKey` to the fork route. A server rejection surfaces as the server's message with a non-zero exit.
- **FR-4** — The conversations table gains a nullable `project_key` column via an idempotent schema top-up; `createConversation` persists an optional `projectKey`; conversation reads expose it as `projectKey` on the DTO; `setConversationProjectKey(name, key|null)` updates it through the write door.
- **FR-5** — `POST /api/conversations` stores the canonical project key on rows it creates when `projectKey` is given (it already validates and cwd-resolves the value).
- **FR-6** — Dashboard grouping (sidebar No-project bucketing, CommandDeck `projectConversations` partition, `resolveConversationProjectName`) resolves the explicit association first — matching on yaml key, then display name — and falls back to cwd containment when the association is absent or matches nothing.
- **FR-7** — The Fork/Handoff modal renders a Project select (all registered projects, all three fork intents) defaulted to "Same as source (<name>)". The default sends no `projectKey`; an explicit choice sends the project's yaml key.
- **FR-8** — Command-palette conversation hits route by the row's explicit association first, falling back to the cwd-encoded `projectId` derivation.
- **FR-9** — The live row for conv 1827 (`20260801-2fc7`) is set to `project_key = 'mind-your-now'` through `setConversationProjectKey` — never raw SQL.

### Non-functional

- **NFR-1** — Backward compatibility: rows with NULL `project_key` (everything existing) group exactly as before.
- **NFR-2** — Docs: `features/conversations.mdx` and `sync-sources/skills/pan-handoff/SKILL.md` document `--project`, the inherit default, and the `--cwd` interaction; `sync-sources/rules/handoff-isolate-cwd.md` mentions `--project` alongside `--cwd` (and `pan sync` is run).
- **NFR-3** — Regression tests cover: isolated-cwd handoff inherits the source project; explicit `--project` wins over inheritance; unknown `--project` fails loudly.

  ```ts
  /** PAN-3419: yaml key of the registered project whose path contains `cwd`,
   *  longest prefix wins; null when under no registered project. */
  export function resolveProjectKeyForCwd(cwd: string): string | null {
    const normalized = cwd.replace(/\/+$/, '');
    let best: { key: string; pathLen: number } | null = null;
    for (const { key, config } of listProjectsSync()) {
      const projectPath = (config.path ?? '').replace(/\/+$/, '');
      if (!projectPath) continue;
      if (normalized === projectPath || normalized.startsWith(projectPath + '/')) {
        if (!best || projectPath.length > best.pathLen) best = { key, pathLen: projectPath.length };
      }
    }
    return best?.key ?? null;
  }
  ```

  ```ts
  /** PAN-3419: normalize a project identifier (yaml key or display name) to
   *  the canonical yaml key. Association-only: unlike resolveProjectCwd this
   *  does NOT require the project path to exist on disk. */
  export function resolveRegisteredProjectKey(input: string): { key: string } | { error: string } {

    if (!match) return { error: `Unknown project: ${input}` };
    return { key: match.key };
  }
  ```

2. Extract an exported pure resolver (testable without the server):
   ```ts
   /** PAN-3419: the project the successor conversation should be explicitly
    *  associated with. An explicit request wins (validated to the canonical
    *  yaml key); otherwise the successor inherits the SOURCE conversation's
    *  effective project — never derived from the successor's own cwd. */
   export function resolveForkProjectKey(
     requested: string | undefined,
     source: Pick<Conversation, 'projectKey' | 'cwd'>,
   ): { projectKey?: string } | { error: string } {
     if (requested) {
       const result = resolveRegisteredProjectKey(requested);
       if ('error' in result) return { error: result.error };
       return { projectKey: result.key };
     }
     const inherited = source.projectKey ?? (source.cwd ? resolveProjectKeyForCwd(source.cwd) : null);
     return inherited ? { projectKey: inherited } : {};
   }
   ```

## NonGoals

- **No move-conversation UX** (endpoint, `pan conv move`, drag-and-drop, menu action, clearing an association from the UI) — that is PAN-1577, which reuses this issue's column and `setConversationProjectKey` writer.
- **No "No project" option in the modal select** — deliberate un-scoping is a move/clear operation; PAN-1577 territory.
- **No fork-blob (`ForkRequest`) field** — the row carries the association; recovery re-runs the pipeline against the existing row.
- **No backfill beyond conv 1827** — existing rows keep NULL and cwd-derived grouping by design (NFR-1).
- **No change to memory-home attribution** — `workspace_id` and workspace-keyed memory are untouched.
- **No frontend longest-prefix change** — the frontend's first-match cwd containment order is unchanged; only the explicit-first step is added.
