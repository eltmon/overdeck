## Glossary (read first)

- **Issue view**: any UI that renders one issue's live pipeline state (agents, verification, ship, beads, activity). There are three today.
- **Console** = **View 1** = `components/drawer/IssueDrawer.tsx` (+ its `Drawer*` children). A closable drawer/panel. Has operator pickup/park gates, a dated lifecycle band, the ★ Active-Agent panel, verification gate cards, and a Live-Activity rail.
- **Cockpit** = **View 2** = `components/Stage/cockpit/IssueMissionControl.tsx` (+ `AgentsLane.tsx`, `CrewStage.tsx`, `HappenedFeed.tsx`, `StatusNarrative.tsx`, `ShipTab.tsx`, `IssueBlockerSpotlight.tsx`, `PlanMapCard`, `BeadsRail`). Opens as a Command Deck tab. Has the Agents & Steps lane, the Overview tab (crew + what-just-happened + plan-map + blocker), and detail tabs.
- **Rail** = **View 3** = `components/CommandDeck/ProjectTree/FeatureItem.tsx` (+ `SessionNode.tsx`, `ProjectNode.tsx`, `ResourcesGroup.tsx`, `UatStackTreeGroup.tsx`, `ShipDoorTreeRow`, `ReviewGroup`, `TroubledBadges.tsx`). The always-on sidebar tree under the conversation list. Compact; the operator's most-used surface.
- **Density**: the size/detail at which the unified view renders — `rail` (compact, always-on), `cockpit` (medium, tabbed), `console` (large, operator control room). Same data, same components, different arrangement.
- **`IssueViewModel`**: the single normalized object describing one issue, produced by `useIssueView(issueId)` — the "one data model."
- **Shared kit**: the component family under `components/issue-view/` that every density composes — the "one component family."
- **Agent/step row**: one row rendering a single agent or pipeline step (icon tile, status, spinner, model, cost, verdict). Today implemented **twice**: `AgentsLane.tsx` `Row` (cockpit) and `SessionNode.tsx` (rail).
- **★ Active-Agent panel**: the live agent output stream + "Tell this agent…" input + Resume button. Today only in Console (`DrawerActiveAgent`). The operator explicitly wants this at every density.
- **no-loss inventory**: the section list in the mockup (three columns: Console 14 panels, Cockpit ~16, Rail ~13). It is the **surface-lock** — see FR-0.

## Requirements

### Functional
- **FR-0 (no-loss surface-lock).** A test `tests/unit/dashboard/frontend/issue-view-no-loss.test.ts` enumerates every section name from the mockup inventory and asserts each is rendered (by `data-section="<name>"` attribute) by at least one density of `<IssueView>`. The build fails if a section from the inventory has no home. This gate exists **from Phase 1** and every phase keeps it green.
- **FR-1.** `useIssueView(issueId)` returns one `IssueViewModel` composed from the existing hooks + store (FR references above). No view may fetch issue state except through this hook after its phase migrates.
- **FR-2.** `<AgentStepRow>` renders one agent/step identically for cockpit and rail densities (icon tile, status label, spinner when active, model, cost, duration, reviewer verdict tick), driven by one `AgentRowModel`. Replaces `AgentsLane` `Row` and the row portion of `SessionNode`.
- **FR-3.** `<ShipProgress>` renders the server-side merge-door progress (rebase→verify→merge→cleanup steps + live ship-log lines) at any density. Replaces `ShipTab` body and `ShipDoorTreeRow`.
- **FR-4.** `<VerificationGates>` renders the typecheck/lint/test/uat gate results at any density. Replaces `DrawerVerificationGates` (console) and the cockpit Verification node.
- **FR-5.** `<BeadsPanel>` renders bead plan-progress + list at any density. Replaces `DrawerBeadsList`, `BeadsRail`/`BeadsTab`, and the rail beads chip.
- **FR-6.** `<ActiveAgentPanel>` renders the live agent output stream + "Tell this agent…" input + Resume (from `DrawerActiveAgent`) and is available at **all** densities (operator requirement). Rail shows it on session-node expand; cockpit shows it in the Conversation tab and the Overview crew section.
- **FR-7.** `<IssueView density="rail|cockpit|console">` composes the kit. The three existing shells become thin adapters that render `<IssueView>` at their density (or are replaced outright in Phase 5).
- **FR-8 (interaction).** In the Rail, clicking an issue's expand affordance grows the **same** `<IssueView>` from `rail` to `cockpit` density **in place** (no separate tab), and a "full screen" control promotes to `console`. The old "open in a new Command Deck tab" path is preserved during migration and removed in Phase 5.
- **FR-9 (needs-you recovery CTA).** When an issue's work agent is in an operator-blocked state — `troubled` (stuck-remediation exhausted), paused with a needs-you reason, or stopped with no live session while the issue is still in progress — `<IssueView>` shows a **prominent primary call-to-action button ("Restart work agent")** at **every** density, in the status-narrative / needs-you band. Clicking it performs the full one-click recovery server-side: clear the operator-facing gates that block start (the CLI equivalents are `pan untroubled <id>` and `pan unpause <id>` — explicit operator click IS the operator authorization those gates wait for), then invoke the same start door the cockpit button already uses (`POST /api/agents`, see `components/Stage/cockpit/AgentActivityCards.tsx` `startMutation`, ~line 116), and surface the spawn outcome (success → live agent row appears; failure → the error inline, never a silent no-op). Motivating incident: PAN-2229 (2026-07-13) sat `troubled` with "stuck remediation exhausted — needs-you" and the operator had **no button anywhere** — recovery required knowing two CLI verbs. Cross-ref PAN-2037 (Start-agent CTA when an agent is merely stopped): FR-9 extends the same shared CTA component to gated states with gate-clearing semantics; build ONE `<StartAgentCta>` in the shared kit that covers both (plain start vs. clear-gates-and-start, label and confirm copy varying by state). The gate-clearing variant must state what it will clear in the confirm copy (e.g. "This agent was marked troubled after repeated failed resumes. Clear the flag and start a fresh work agent?") per the operator-facing-messages rule.

### Non-functional
- **NFR-1.** No behavior regressions: every action available today (per the no-loss inventory — e.g. SessionNode's 9-item context menu: Stop/Pause/Unpause/Resume/Restart/Deep-wipe/Open-state-dir/View-JSONL/View-terminal) remains reachable at the density that had it. The context menu moves to the shared `<AgentStepRow>`.
- **NFR-2.** Data fetching is not multiplied: `useIssueView` shares React Query cache keys with the existing hooks (same `queryKey`s) so opening a view does not double the polling. Reuse `refetchInterval` values already set.
- **NFR-3.** The dashboard uses the pan-style-guide (see `/pan-style-guide` skill): DM Sans / Space Grotesk / DM Mono fonts, no Inter/bold, no pill badges misuse, color-signal semantics (never green for "running" — running is blue/info), StatusDot semantics. All new components follow it. **Restated inline so the executor doesn't need to recall it:** running/active = blue/info (not green); green = success/passed only; a spinner marks active work; chips are square-ish, not candy pills.
- **NFR-4.** File-size ratchet: new shared components are new files (each < 400 lines); the three shells must **shrink** as logic moves out (they are god-file offenders — FeatureItem 1373, IssueMissionControl 994). Update `scripts/file-size-baseline.txt` downward as they shrink; never upward for these three.
- **NFR-5.** Every extracted component ships with a colocated `*.test.tsx` (Vitest + React Testing Library, matching the existing tests under `components/**/__tests__/` and `*.test.tsx`).

## Decisions (made here — do not re-litigate)

- **D1 — Extract, then adopt, one cluster at a time.** Each shared component is (a) created with tests, (b) adopted in the cockpit, (c) adopted in the rail/console, (d) old duplicate deleted — all in one PR per cluster. Never leave two implementations of the same cluster on main across PRs.
- **D2 — `IssueViewModel` is a view-model, not a new store.** It is derived read-only from the existing hooks + Zustand selectors inside `useIssueView`. It introduces **no** new API endpoint and **no** new server state (two-door rule: reads go through existing read paths). If a datum needs a new endpoint, that is a separate issue, not this one.
- **D3 — Density is a prop, not three code paths.** `<IssueView density>` branches layout only. A section either renders or is hidden per density via a declarative `DENSITY_SECTIONS` map, not via forked component trees.
- **D4 — Rail-first interaction (option B) is the target, but gated behind the extraction (option A).** Do the extraction (Phases 1–4) before the in-place-expand interaction (Phase 4's second half). Do not change navigation before the components are shared, or you will have re-created the drift you are removing.
- **D5 — Keep the three entry points working the entire time.** Users keep the Console drawer, the Cockpit tab, and the Rail throughout Phases 1–4. Phase 5 (retire shells) is the ONLY phase that removes an entry point, and it is optional / can be deferred.
