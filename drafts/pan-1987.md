# PAN-1987 — Allow renaming a registered project

**Issue:** https://github.com/eltmon/overdeck/issues/1987
**Planned:** 2026-07-10 (auto mode — no interactive Q&A; decisions recorded in autoDecisions)

## Glossary

- **Registration key** — the map key under `projects:` in `~/.overdeck/projects.yaml` (e.g. `panopticon-cli`). Derived from the name at registration (`name.toLowerCase().replace(/[^a-z0-9-]/g, '-')`, `src/lib/project-registration.ts:90`). Used in agent state, API paths, and internal routing. **Immutable in this issue.**
- **Display name** — the `name:` field inside a project's config entry. Human-facing label shown in the Command Deck tree, project page hero, sidebar, kanban filter. **This is what rename changes.**
- **Write door** — the single sanctioned mutation path for a piece of state. For projects.yaml it is `saveProjectsConfigSync` in `src/lib/projects.ts:236`, reached through purpose-built helpers (`registerProjectSync:261`, `setProjectAutoMergeDefaultSync:272`).

## Problem

A project's display name is fixed at registration and there is no rename affordance — CLI, API, or UI. The only path is hand-editing `~/.overdeck/projects.yaml`. Concrete case: the project registered as `panopticon-cli` still displays that name even though the repo is now `overdeck`.

## Requirements

- **FR-1** A `renameProjectSync(key, newName)` helper in `src/lib/projects.ts` renames a project's display name through the existing write door. Validation: unknown key → throw; trimmed empty name → throw; case-insensitive collision with any OTHER project's key or name → throw; rename to the project's own current name → idempotent success (no error).
- **FR-2** `POST /api/projects/:projectKey/rename` with body `{name}` performs the rename. The `:projectKey` param resolves against key first, then current display name (same tolerance as `fetchProjectSessionTree`). Responses: 200 `{key, name}`; 404 unknown project; 400 invalid name; 409 duplicate. Mutation-guarded via `rejectUnsafeDashboardMutationRequest`.
- **FR-3** `pan project rename <key> <newName>` (and the `pan projects` alias) renames from the CLI with clear success/error output. The `pan-projects` wrapper skill documents it in the same commit.
- **FR-4** The project page hero (HeroBillboard in ProjectOverview) shows a pencil next to the project name; clicking opens an in-place input pre-filled with the current name; Enter commits (POST FR-2), Escape cancels; 409/400 shows the server error without losing the draft. On success all project-name surfaces refresh without a page reload (react-query invalidation of `command-deck-projects`, `registered-projects`, and `session-trees` prefixed keys).
- **FR-5** The Command Deck tree project row offers "Rename project" in its context menu, switching the row's name span to the same in-place editor with identical commit/cancel/error behavior.
- **FR-6** `configuration/projects.mdx` documents the rename command and the display-name-vs-registration-key distinction (key is immutable; name is the human label).
- **NFR-1** No `execSync` in server-reachable code (repo rule).
- **NFR-2** All writes go through `renameProjectSync` — no route or CLI writes projects.yaml directly (single-write-door tenet).
- **NFR-3** Any delay/retry logic in tests uses fake timers (repo rule) — not expected to be needed here.

## Design decisions (auto mode)

1. **Display-name-only rename; key immutable.** The issue comment offers "keep the registration key stable (or offer a separate, explicitly-warned re-key)" — the stated default is kept; re-key is a NonGoal.
2. **Uniqueness across names AND keys, case-insensitive.** Because name doubles as identity in the tree flow (routes/projects.ts:496), a new name equal to another project's key would misroute.
3. **Route param accepts key or current name.** Matches `fetchProjectSessionTree` semantics and spares the frontend a name→key mapping step in ProjectNode (which only holds the display name).
4. **Stale URLs after rename are acceptable.** Another open tab at `/command-deck/<oldName>` will 404 its tree fetch until re-navigation; not worth a redirect layer for a rename affordance.
5. **YAML comment loss on write is accepted** — pre-existing `saveProjectsConfigSync` behavior, not a regression introduced here.
