**Operator direction (2026-07-13, verbatim intent):** the order book page must be *the*

---

## Glossary

- **Order book** — an operator-assembled, ordered plan of issues for one flywheel run:
  items grouped into **Lane A** (parallel-safe, overlap freely) and **Lane B** (strictly
  serial, exactly one in flight), with per-item prereqs and re-verify flags. Today this
  exists only as prose (`docs/master-plan-cicd-and-refactoring.md`); this PRD makes it a
  first-class entity.
- **Run** — one flywheel orchestrator lifetime, `RUN-NN`, tracked by the active-run gate
  (SQLite `app-settings`) and a run dir `~/.overdeck/flywheel/runs/RUN-NN/`.
- **Drain / drained** — every item in the book is terminal: `closed-out`, or explicitly
  `parked` with a needs-you. **Drained defines the end of the run.**
- **Retrospective** — a post-drain flywheel step that identifies potential improvements
  to the flywheel itself (doctrine, substrate bugs, brief templates) for future runs.
  Emitted **only when it recognizes some** — no ceremony otherwise.
- **Pickup gate** — the predicate the flywheel applies before dispatching an issue
  (`roles/flywheel.md:135` "## The pickup gate", mirrored by `isAutoPickable()` in
  `src/lib/backlog/pickup.ts`).
- **Pre-released semantics** — membership in the *active* order book counts as operator
  release for the pickup gate; `auto_pickup_backlog` stays OFF for everything else.
- **Sequenced backlog** — the ranked `sequence.md` produced by `pan backlog
  write-sequence` (`src/lib/backlog/sequence-io.ts`), served at
  `GET /api/backlog/sequence` (`src/dashboard/server/routes/backlog.ts:70`).
- **State worktree / state door** — the `overdeck-state` orphan branch checked out at
  `${OVERDECK_HOME}/state/<project>/`; permanent planning state lives there and is
  written only through domain writers that auto-commit (two-door tenet).

## Why (from the issue, still true)

The pattern was proven manually across RUN-56…RUN-62: the operator handed the flywheel
an ordered two-lane plan via prose briefs, and it drained 21 of 26 items — but every
constraint (one Lane B in flight, prereqs, re-verify, membership-as-release) was prompt
discipline, not mechanics. A separate drip-orchestrator would duplicate the flywheel's
shepherding loop and split pipeline authority. Special orders makes the flywheel's
existing loop operator-programmable.

## Requirements

### Functional

- **FR-1 — Order-book entity + storage.** An order book is a JSON document on
  `overdeck-state` (`orders/<book-id>.json` + `orders/index.json` queue), with exactly
  one resolver and one writer (two-door tenet). Books have status
  `draft | ready | running | drained | complete`, a settings block, and ordered lane
  items `{ issue, lane, order, prereqs[], reVerify, addedAt, addedBy }`.
- **FR-2 — Order Book page.** New dashboard route `/orders` rendering the mockup: book
  switcher strip (active + queued + drained books, "+ New book"), lane editors with
  drag-reorder, lane swap, remove, prereq + re-verify + PRD-presence chips, lifecycle
  strip, run-settings panel, validation panel, Setup ⇄ Progress view toggle, Preview
  brief, and Start run.
- **FR-3 — Search-and-add on the page.** A search box on the page queries open issues
  (id/title/label) across the project's trackers; each result has a one-click add.
  Adding never dispatches anything — a book is a plan until its run starts.
- **FR-4 — Backlog top-10 rail.** The page shows the top 10 sequenced-backlog items
  **not already in any book**, in rank order, each one-click addable. Served by a new
  `GET /api/orders/backlog-candidates?limit=10` that joins the sequence with book
  membership.
- **FR-5 — Add from other surfaces.** "Add to order book ▸ <book | + New book…>"
  appears on: the kanban card action menu, the issue drawer action bar (both via the
  shared `ISSUE_ACTIONS` registry, so one entry covers both), a hover action on backlog
  sequencer rows, and the CLI (`pan orders add <book> <issue…>`).
- **FR-6 — Start run from the book.** "Start run" (page) and `pan flywheel start
  --orders <book-id>` (CLI) start a flywheel run **bound to the book**: doctrine + the
  standard brief still load; the book defines scope; an optional per-run brief overlay
  path may be attached. Starting requires validation clean (FR-7) and flips the book to
  `running` with the `runId` stamped. Exactly one book may be `running` (matches the
  single active-run gate).
- **FR-7 — Validation gate.** Before arming Start run: every item's issue is OPEN; no
  item is in another non-complete book; prereq references resolve and are acyclic;
  items with no PRD are either flagged `blocks` (default for Lane B) or downgraded to
  `warn` ("plan at pickup") per item. Blocks disable the button and the CLI errors.
- **FR-8 — Mechanical lane semantics.** While an orders-bound run is active, the
  dispatch path **refuses** a second concurrent Lane B item and enforces prereq order
  and the book's Lane A concurrency — server-side, the same way swarm slot bounds are
  enforced, not by prompt discipline.
- **FR-9 — Pre-released pickup.** `isAutoPickable()` (and the doctrine gate) treat
  membership in the active book as `released`. Off-book issues stay gated by
  `auto_pickup_backlog` exactly as today.
- **FR-10 — Progress surface.** `FlywheelStatus` gains an `orders` block
  (`bookId, bookName, landed, total, laneAInFlight[], laneBInFlight?, drained`); the
  Order Book page Progress view and the Flywheel page render the book as a live
  checklist (statuses: queued / planning / working / review / merged / closed).
- **FR-11 — Drain ends the run.** When every item is terminal the status computation
  marks the book+run `drained`; the flywheel then finalizes via `pan flywheel complete`
  (writes retro + report, clears the active-run gate, flips book to `complete`).
  Drained is computed mechanically; the flywheel cannot "forget" to end the run.
- **FR-12 — Retrospective.** After drain, before continuation, the flywheel authors a
  retrospective: potential improvements to the flywheel for future runs (doctrine
  deltas, substrate bugs to file, brief-template fixes). Written to
  `<run-dir>/retro.md` and summarized in `report.md`. **If it recognizes none, it
  writes none** — a single "no findings" line in report.md, no retro.md.
- **FR-13 — Continuation.** `pan flywheel complete` then: (a) if another book is
  `ready` in queue order → start a new run bound to it; (b) else if
  `flywheel.auto_pickup_backlog` is true → start a new backlog-mode run (today's
  behavior); (c) else → stay stopped, emit a needs-you ("pipeline idle — no order book
  queued and auto-pickup is off").
- **FR-14 — Documentation** (work item 12; required).

## Design decisions (made here — do not re-litigate downstream)

- **D-1 Storage.** `orders/` on `overdeck-state`, one JSON file per book +
  `index.json` holding queue order and status snapshots. Rationale: order books are
  permanent planning state (like `specs/`, `drafts/`), must travel cross-machine, and
  must survive DB rebuilds. SQLite gets a read-through cache only if profiling demands
  it (not in v1).
- **D-2 Book id** = `<yyyy-mm-dd>-<kebab-name>` stamped at creation; display name
  free-form and renamable; id immutable.
- **D-3 One running book at a time.** Enforced by the existing single active-run gate;
  `ready` books queue in `index.json` order.
- **D-4 Lane enforcement location.** The chokepoint is the server-side dispatch path
  the flywheel already calls (`pan start` → start-agent route). When the active run is
  orders-bound, the route consults the resolver: reject Lane B dispatch if another
  Lane B item is non-terminal; reject any item whose prereqs are non-terminal; reject
  off-book work-agent dispatch **with an override flag** (`--off-book`, logged) so
  emergency blocks-main strikes stay possible per doctrine.
- **D-5 Drain detection** lives in the run-status computation
  (`flywheel-run-state.ts` + the emit-status path), derived from issue terminal state
  via the issues resolver — not from the flywheel's self-report.
- **D-6 `pan flywheel complete`** is the single finalizer verb (report + retro + gate
  clear + queue advance). `pan flywheel stop` keeps today's semantics (manual stop, no
  continuation). `report` keeps refusing while the session is alive.
- **D-7 Item terminal states** are `closed` (issue closed-out) and `parked` (flywheel
  parked it with a needs-you). Parked items count toward drain — a book never wedges a
  run open forever.
- **D-8 The brief stays.** Doctrine (`roles/flywheel.md`) + standard brief
  (`docs/flywheel-brief.md`) always load; `--orders` replaces the *scope* prose. The
  old `--brief` path remains for bookless runs (backlog mode, bespoke runs like
  RUN-63).
