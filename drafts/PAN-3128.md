# PAN-3128 PRD — Deploys must build from a clean canonical source, never the mutable primary worktree

Issue: https://github.com/eltmon/overdeck/issues/3128
Status: draft (planning, `--auto` mode)
Author: planning agent (k3[1m]), 2026-07-26

## Glossary

- **Primary worktree** — the main checkout of the overdeck repo (`/home/eltmon/Projects/overdeck`), where operator conversations legitimately work. Expected to carry uncommitted WIP and occasional local-only commits.
- **Deploy** — replacing the running production dashboard's `dist/` bundle and restarting the server. The sanctioned deploy verb is `pan reload`; the flywheel is the standing deployer (`roles/flywheel.md` Mission #5).
- **`pan reload`** — CLI command (`src/cli/commands/reload.ts`) that builds the bundle and restarts the dashboard only if the build succeeds.
- **Build worktree** — a temporary detached `git worktree` checked out at `origin/main`, used purely as build input and removed afterwards.
- **`buildCommit`** — the SHA stamped into the server bundle at build time (`src/dashboard/server/tsdown.config.ts`), exposed by `/api/health`.
- **DoD row 7 (`deploy`)** — the Definition-of-Done row (`src/lib/lifecycle/dod-gate.ts`, `checkDeployRow`) that proves the live dashboard runs a build containing a given merge commit.
- **Deploy window / gate** — `getDeployBlockReason()` in `src/lib/deploy/deploy-window.ts`; defers deploys while verification, merges, post-merge, flywheel runs, restarts, or `pan dev` ownership are active.
- **Deploy patrol** — `src/lib/cloister/deploy-patrol.ts`; Deacon patrol that auto-deploys when the running build falls behind `origin/main`. It already spawns `pan reload`.

## Problem

The deploy path builds from whatever the primary worktree happens to contain. Two
concrete failures resulted (issue body + comments, RUN-71 ticks 10/11/14/15):

1. **Unreviewed code reached the live server.** The flywheel deployed a build of a
   working tree carrying uncommitted edits to `merge-ops.ts`, `merge-strike.ts`,
   `agent-state.ts` plus a local-only commit (`124eb2e108`, not on the forge).
   `/api/health` reported `buildCommit: 124eb2e108`.
2. **DoD row 7 became unsatisfiable.** With `buildCommit` a local-only SHA,
   `git merge-base --is-ancestor <merge> <buildCommit>` is false for every merged
   issue, blocking close-out (PAN-3119, PAN-3037 stuck).
3. **Stray working-tree state blocked deploys.** A two-line uncommitted test edit
   prevented `git merge --ff-only origin/main`, so a clear deploy window could not
   be used to ship merges the operator was waiting on.

The recurrence pattern (three independent instances in ~5 hours, from different
conversations) shows this is the steady state, not a one-off: people work in the
primary worktree continuously, and the window between "canonical" and
"non-canonical" is smaller than a deploy cycle.

## Root cause (verified against code)

`buildFromOriginMain()` in `src/cli/commands/reload.ts:173-199` fetches
`origin/main`, then checks `git merge-base --is-ancestor origin/main HEAD`
(reload.ts:176). When `origin/main` **is** an ancestor of `HEAD` — i.e. `HEAD ==
origin/main` (possibly with a dirty tree) or `HEAD` is *ahead* with local-only
commits — it builds **in place in the primary worktree** (reload.ts:177-179,
`runInstallAndBuild(repoRoot)`). Only when the local HEAD is behind or diverged
does it fall back to a detached `origin/main` worktree build (reload.ts:186-198).

So the in-place fast path triggers in exactly the two dangerous states:

- `HEAD == origin/main` + dirty tree → uncommitted changes ship, `buildCommit`
  looks canonical but the code is not.
- `HEAD` ahead with local-only commits → unreviewed commits ship and
  `buildCommit` is a SHA that exists nowhere on the forge.

Compounding it, the flywheel's documented deploy procedure
(`roles/flywheel.md:124-126`) is `npm run build` then `pan restart --dashboard`
in the primary worktree — a fully unguarded in-place build that bypasses even
`pan reload`. And the build stamp (`src/dashboard/server/tsdown.config.ts:82-87`)
records only `git rev-parse HEAD` and a timestamp, so `/api/health` cannot
distinguish "live runs main" from "live runs someone's desk".

## Proposal

Adopt the issue's fix direction 2 as the mechanism, with direction 3 as the
detection surface. (Direction 1, preflight-refuse, is subsumed: if the deploy
never reads the primary tree, its state can neither contaminate nor block a
deploy. The issue comments confirm preflight alone is insufficient — the tree
was canonical at build time and non-canonical minutes later.)

1. **`pan reload` always builds from a dedicated clean worktree.** Remove the
   in-place fast path. Every production build runs `bun install` + `npm run
   build` in a temporary detached worktree checked out at `origin/main`, then
   swaps the resulting `dist/` into the primary checkout. When the primary tree
   is dirty or `HEAD` differs from `origin/main`, reload prints a note that
   those changes are excluded from the deploy (a note, not a refusal — the whole
   point is that the primary tree's state no longer gates the deploy).
2. **Stamp build provenance.** The server bundle stamps `buildDirty`
   (`git status --porcelain` non-empty at build time) and `buildBranch`
   (`git rev-parse --abbrev-ref HEAD`, `null` when detached) alongside
   `buildCommit`. `getBuildInfo()` exposes them; they flow onto `/api/health`
   via `getDashboardIdentity()` (identity.ts:17-23 spreads `getBuildInfo()`;
   server.ts:131-135 serves `{ status: 'ok', ...getDashboardIdentity() }`).
3. **DoD row 7 consumes provenance.** `checkDeployRow` misses with an explicit
   reason when `/api/health` reports `buildDirty: true`, and when `buildCommit`
   is not an ancestor of `origin/main` — so a bypass-built server fails
   close-out loudly with a message that names the remedy (`pan reload`), instead
   of the current ambiguous "does not contain merge" for every issue.
4. **Point the flywheel and the docs at the clean path.** `roles/flywheel.md`
   Mission #5 instructs `pan reload` as the deploy verb; the reload skill, dev
   SOP, and DoD doc describe the clean-worktree guarantee and the new provenance
   fields.

The deploy patrol (`src/lib/cloister/deploy-patrol.ts:335-342`) already spawns
`pan reload`, so auto-deploy inherits the fix with no patrol changes.

## Decisions (made in `--auto` mode; recorded in `plan.autoDecisions`)

- **D1 — Clean worktree build over preflight-refuse.** The issue lists both;
  the comments elevate the worktree build as "the only variant that is immune"
  because a preflight can pass and be stale by the next build. With the worktree
  build there is nothing left for a preflight to refuse.
- **D2 — Remove the in-place fast path entirely, no `--build-in-place` flag.**
  The fast path only ever triggered in the two dangerous states; a clean tree at
  `origin/main` produces an identical bundle either way, at the cost of one
  `bun install` (~2s, hardlinked from the global cache) plus a `dist/` copy. One
  code path beats a faster dangerous one. Deploying uncommitted code to
  production was never legitimate — `pan dev` is the iteration surface.
- **D3 — Stamp raw facts, not a canonical verdict.** `buildDirty` and
  `buildBranch` are build-time facts; "canonical" is a time-sensitive judgment
  (it depends on where `origin/main` is *now*) and belongs in consumers
  (DoD row 7, operators), not baked into an immutable artifact.
- **D4 — Row 7 misses (not warns) on non-canonical builds.** A dirty or
  local-only live build is exactly the state close-out must not certify. Once
  reload is fixed, only a deliberate bypass can produce it, and the miss message
  names the remedy.
- **D5 — `pan dev` hot-reload is out of scope.** When a `pan dev` supervisor
  owns the dashboard, `pan reload` signals it (SIGUSR2) to rebuild in place —
  intentionally, because a dev-owned dashboard exists to run uncommitted code.
  Provenance stamping makes such builds visible (`buildDirty: true`), and row 7
  will miss on them, which is the intended pressure.

## Requirements

### Functional

- **FR-1** — `pan reload` builds the dashboard bundle in a temporary detached
  worktree checked out at `origin/main`, for every state of the primary
  worktree (clean, dirty, ahead, behind, diverged). It never runs the build in
  the primary worktree.
- **FR-2** — When the primary worktree is dirty or its `HEAD` differs from
  `origin/main`, reload prints a note stating that those changes/commits are
  excluded from the deploy. The note does not block the deploy.
- **FR-3** — The built server bundle records `buildDirty` (boolean) and
  `buildBranch` (string, `null` when detached) at build time;
  `GET /api/health` exposes both fields; bundles built before this change
  report `null` for both (no crash, no fabricated values).
- **FR-4** — DoD row 7 (`checkDeployRow`) returns `miss` with an explicit
  provenance reason when the live health payload reports `buildDirty: true`,
  and when the live `buildCommit` is not an ancestor of `origin/main`.
- **FR-5** — `roles/flywheel.md` Mission #5 names `pan reload` as the deploy
  command and no longer instructs `npm run build` + `pan restart --dashboard`
  as the deploy path.

### Non-functional

- **NFR-1** — A failed build leaves the old dashboard running, removes the
  temporary build worktree, and removes `dist.incoming`.
- **NFR-2** — No loss of existing `pan reload` behavior: `--skip-build`,
  `--force`, `--health-timeout`, `--no-deacon`, the restart lock, the
  non-primary-cwd refusal, and the `pan dev` SIGUSR2 path all keep working.
- **NFR-3** — A stale build-worktree directory from a crashed previous reload
  cannot fail the next reload.

### WI-1 — `pan reload` always builds from a detached `origin/main` worktree

**Files:**
- `src/lib/deploy/build-from-origin.ts` — **new.** Home for the moved logic.
- `src/cli/commands/reload.ts` — rewire to the lib module; delete moved code.
- `tests/unit/lib/deploy/build-from-origin.test.ts` — **new.**

**Design.** Move `buildFromOriginMain`, `swapBuiltDist`, `runInstallAndBuild`,
`runBunInstall`, `resolveBunBinary`, `runBuild`, `runCommand`, `runGitAsync`,
and `shellQuote` out of `src/cli/commands/reload.ts` (reload.ts:47-199) into
`src/lib/deploy/build-from-origin.ts`. Give the exported entry point an
injectable deps object, following the `DeployWindowDependencies` pattern in
`src/lib/deploy/deploy-window.ts:16-39`:

```ts
export interface BuildFromOriginDeps {
  fetchOriginMain(repoRoot: string): Promise<void>;        // git fetch origin main
  workingTreeClean(repoRoot: string): Promise<boolean>;    // git status --porcelain
  headMatchesOriginMain(repoRoot: string): Promise<boolean>; // rev-parse HEAD vs origin/main
  addBuildWorktree(repoRoot: string, path: string): Promise<void>;
  removeBuildWorktree(repoRoot: string, path: string): Promise<void>;
  installAndBuild(cwd: string): Promise<void>;             // bun install + npm run build
  swapDist(repoRoot: string, buildWorktree: string): Promise<void>;
  note(message: string): void;                             // operator-facing note lines
}

export async function buildDashboardFromOriginMain(
  repoRoot: string,
  deps: BuildFromOriginDeps = defaultDeps,
): Promise<void>;
```

**Behavior** (in order):

1. `fetchOriginMain(repoRoot)`.
2. If `!(await workingTreeClean(repoRoot))`, `note(...)` that the primary
   worktree has uncommitted changes and they are **not** part of this deploy.
3. If `!(await headMatchesOriginMain(repoRoot))`, `note(...)` that local
   HEAD differs from `origin/main` and only `origin/main` is being deployed.
   (This covers behind, ahead-with-local-commits, and diverged in one check;
   the deploy no longer cares which.)
4. Compute `buildWorktree = join(dirname(repoRoot), '.pan-reload-build-' + process.pid)`.
   Before adding it, `git worktree prune` and `fs.rm(buildWorktree, {recursive,
   force})` so a stale directory from a crashed reload cannot fail the add
   (NFR-3). Then `git worktree add --detach <path> origin/main`.
5. `try { installAndBuild(buildWorktree); swapDist(repoRoot, buildWorktree); }
   finally { removeBuildWorktree(...); fs.rm(buildWorktree); fs.rm(join(repoRoot,
   'dist.incoming')); }` — preserving today's cleanup and error semantics
   (reload.ts:189-198).

**In `reload.ts`:** `reloadCommand` calls `buildDashboardFromOriginMain(repoRoot)`
where it currently calls `buildFromOriginMain(repoRoot)` (reload.ts:295). Delete
the moved helpers, including `runGitExit` (orphaned once the ancestor check is
gone). Everything else in reload.ts stays byte-identical: the dev-supervisor
SIGUSR2 block, the restart lock, `agentRestartBlockReason`, mtime freshness
check, `restartDashboard` call. This is a deliberate behavior **removal** (the
in-place fast path is the defect), not a surface loss — no reload flags or
operator affordances change.

**Tests** (`tests/unit/lib/deploy/build-from-origin.test.ts`, all with injected
deps, no real git):

- **Never builds in the primary worktree:** with `workingTreeClean() → true`
  and `headMatchesOriginMain() → true`, asserts `installAndBuild` is called
  with the build-worktree path (never `repoRoot`), `addBuildWorktree` and
  `swapDist` are called, and the worktree is removed afterwards. This is the
  regression test for the deleted fast path.
- **Notes on dirty tree:** `workingTreeClean() → false` produces a note whose
  text says uncommitted changes are excluded; build still proceeds.
- **Notes on differing HEAD:** `headMatchesOriginMain() → false` produces a
  note naming `origin/main` as the deployed ref; build still proceeds.
- **Failure leaves old dashboard running:** `installAndBuild` rejects → the
  error propagates, `swapDist` is never called, `removeBuildWorktree` is
  called, and `dist.incoming` cleanup is attempted (NFR-1).
- **swapDist happy path** (real `fs` in `os.tmpdir()`): fake `dist/` trees;
  assert the incoming tree lands at `<repoRoot>/dist` and no `dist.incoming`
  or `dist.old.*` remains.

**Acceptance criteria:**

- AC-1: Given any primary-worktree state (clean, dirty, ahead, behind), when
  `pan reload` builds, then `bun install` and `npm run build` execute only in
  the detached `origin/main` worktree — proven by the injected-deps test
  asserting `installAndBuild` never receives `repoRoot`.
- AC-2: When the primary tree is dirty or HEAD ≠ `origin/main`, reload prints
  a note stating those changes are excluded and continues the deploy (does not
  exit non-zero for that reason).
- AC-3: When the build fails, the command exits non-zero with a message ending
  in `old dashboard left running`, and the build worktree plus `dist.incoming`
  are removed.
- AC-4: `grep "merge-base" src/cli/commands/reload.ts` returns no matches —
  the in-place fast path is gone.
- AC-5: `npm run typecheck` passes and the new test file passes under
  `npx vitest run tests/unit/lib/deploy/build-from-origin.test.ts`.

declare const __OVERDECK_BUILD_COMMIT__: string;
declare const __OVERDECK_BUILD_TIME__: string;
declare const __OVERDECK_BUILD_DIRTY__: boolean;
declare const __OVERDECK_BUILD_BRANCH__: string | null;

export interface BuildInfo {
  readonly buildCommit: string | null;
  readonly builtAt: string | null;
  readonly buildDirty: boolean | null;
  readonly buildBranch: string | null;
}

export function getBuildInfo(): BuildInfo {
  return {
    buildCommit: typeof __OVERDECK_BUILD_COMMIT__ === 'string' ? __OVERDECK_BUILD_COMMIT__ : null,
    builtAt: typeof __OVERDECK_BUILD_TIME__ === 'string' ? __OVERDECK_BUILD_TIME__ : null,
    buildDirty: typeof __OVERDECK_BUILD_DIRTY__ === 'boolean' ? __OVERDECK_BUILD_DIRTY__ : null,
    buildBranch: typeof __OVERDECK_BUILD_BRANCH__ === 'string' ? __OVERDECK_BUILD_BRANCH__ : null,

## NonGoals

- **Changing the `pan dev` hot-reload (SIGUSR2) path.** A dev-owned dashboard
  intentionally runs uncommitted code; provenance stamping makes that visible
  and row 7 will miss on it — intended.
- **A refuse-on-dirty preflight in `pan restart` / `pan up`.** Operator dev
  restarts of edited code are legitimate; detection flows through provenance +
  row 7 instead of refusal.
- **Frontend provenance display** (e.g. StaleBuildChip). The health JSON
  exposure is the contract; UI surfacing can follow separately.
- **Generalizing beyond `origin/main`.** The repo's deploy tooling already
  hardcodes `main` (`buildFromOriginMain`, deploy patrol staleness); other
  default branches are out of scope.
- **An operator escape hatch to deploy uncommitted code to the production
  dashboard.** That was the defect. `pan dev` covers iteration.
- **Changing `npm run build` itself.** Local dev builds in the primary worktree
  stay exactly as they are; only the deploy path changes what it builds from.

## Acceptance criteria (issue-level)

1. `pan reload` never executes a build in the primary worktree; every deploy
   build runs in a detached `origin/main` worktree (WI-1).
2. A dirty primary tree or local-only commits produce a printed note and are
   excluded from the deploy — they cannot contaminate it or block it (WI-1).
3. `/api/health` reports `buildCommit`, `buildDirty`, and `buildBranch`;
   pre-change builds report `null` for the new fields (WI-2).
4. DoD row 7 misses with explicit, distinct reasons for dirty builds and for
   non-canonical build commits, naming `pan reload` as the remedy (WI-3).
5. The flywheel deploy mission and all deploy docs point at `pan reload` and
   describe the clean-worktree guarantee and provenance fields (WI-4).
6. A failed deploy build leaves the old dashboard running and cleans up its
   temporary worktree (WI-1).
