## 1. Glossary (defined before use)

- **beads / `bd`** — the issue-tracker CLI (repo **`github.com/gastownhall/beads`**, moved from `steveyegge/beads`), installed at `/home/eltmon/.local/bin/bd`, **version 1.1.0** (upgraded from 1.0.4 on 2026-07-12). Overdeck's per-issue tasks ("beads") live here.
- **Dolt** — a version-controlled SQL database ("Git for data"). As of `bd 1.0.4+` it is the **only** supported beads storage backend (the legacy SQLite backend was removed).
- **Dolt schema version** — Dolt's internal migration counter, distinct from beads' logical `schema_version`. `bd 1.1.0` targets **v53**; Overdeck's live DBs were created at **v32**. Upgrading `bd` does not auto-migrate a remote-backed DB (see *migration-fork guard*).
- **migration-fork guard (`bd 1.1.0`, GH#4259)** — when a DB has a configured Dolt remote, `bd 1.1.0` **refuses to auto-apply** pending schema migrations, printing: *"refusing to auto-apply N pending schema migrations to a remote-backed database (v32 → v53): migrating clones independently forks the schema."* Read-only commands continue on the old schema; write/vc commands refuse until migrated. This is a *coordination decision*, not an auto-fix.
- **designated migrator** — the single machine authorized to apply schema migrations, via `BD_ALLOW_REMOTE_MIGRATE=1 bd migrate` followed by `bd dolt push`. Every other clone adopts the migrated schema with `bd bootstrap` (re-clone from the remote). Only one machine may migrate; any second independent migration forks irrecoverably.
- **embedded mode** — default `bd` mode: an **in-process Dolt engine**, data under `.beads/embeddeddolt/`, **no external server**. `bd context --json` reports `"dolt_mode": "embedded"`. `bd sql` (raw SQL) is **not supported** in embedded mode. Local Dolt HEAD is read via `bd vc status` (prints `Branch:` / `Commit:`).
- **server mode** — `bd init --server`: an external `dolt sql-server`; data under `.beads/dolt/`; `bd sql` works. Overdeck does **not** use server mode today; per-worktree embedded engines are the root of the PAN-1158/939 contention.
- **`refs/dolt/data`** — the git ref where Dolt stores its data when a git remote is configured as a Dolt remote. **Separate from `refs/heads/*`**; travels over the *same* git remote as the code but is not a branch and never merges into one. Confirmed present on `origin` for panopticon-cli at authoring (`a299698f…`).
- **Dolt remote** — a push/pull target for Dolt history, configured via `bd dolt remote add <name> <url>`; for Overdeck the URL is the project's own git remote (`git+ssh://…`), so Dolt history publishes to `refs/dolt/data` there. Stored as `sync.remote` in `.beads/config.yaml`.
- **`bd bootstrap`** — non-destructive setup/recovery. Detection order (from `bd bootstrap --help`): `sync.remote` configured → clone from remote; git origin has `refs/dolt/data` → clone from git; `.beads/backup/*.jsonl` → restore; `.beads/issues.jsonl` → import; no DB → create fresh; DB exists → validate. Flags: `--dry-run`, `--yes`/`--non-interactive`, `--json`.
- **`bd dolt pull` merge behavior (`bd 1.1.0`)** — per the v1.1.0 release notes, "pull merges that previously failed now **cascade-repair or auto-resolve** constraint violations and mixed schema conflicts," with **timestamp-based conflict resolution favoring local rows**, plus content-hash **schema-drift detection**. This is the divergent-writer merge primitive this PRD relies on (see D6).
- **auto-export** — `bd` exports the issues table to `.beads/issues.jsonl` when enabled via the `export.auto` config key. **Verified on the panopticon-cli state DB (2026-07-12): `bd config get export.auto` → `false`.** So Overdeck does NOT currently rely on auto-export; the write door produces the export explicitly. (Do not describe auto-export as an always-on default; cite `bd config get export.auto` for the live value.)
- **`issues.jsonl`** — a **derived export of the issues table only**. It does not capture Dolt branches, full commit history, working-set state, or non-issue tables. Not authoritative.
- **record universe** — the set of record types an export/list/count covers. `bd export` defaults to **regular issues**; `bd export --all` additionally includes infrastructure/template/gate/memory records. Every count/verify comparison in this PRD MUST use **one explicitly named universe** on both sides (see WI-6).
- **`no-db: true`** — a *removed* legacy beads mode (JSONL as source of truth, no DB). `bd 1.1.0` exposes no such flag; it survives only as a stale string in some `.beads/config.yaml`. **Not a supported configuration.**
- **`.beads/redirect`** — a file whose contents are the path to another repo's `.beads/`; makes a worktree share one Dolt DB. Gitignored. Resolved by `resolveSharedBeadsDir` in `src/lib/bd-process-lock.ts`.
- **canonical local Dolt home** — the ONE physical `.beads/embeddeddolt/` per project that every checkout/worktree/route/agent resolves to (decided in D-HOME / FR-10). For panopticon-cli: `${OVERDECK_HOME}/state/<project>/.beads/`.
- **read door / write door** — Overdeck's single-source-of-truth tenet: each domain has exactly one canonical resolver (read) and one canonical writer (write). Beads must have exactly one of each — and, because agents mutate beads from shell, the write door needs an **agent-facing surface** (FR-9), not only a TypeScript module.
- **`overdeck-state`** — the orphan git branch (checked out at `${OVERDECK_HOME}/state/<project>/`) holding pipeline state (records, specs, drafts, continues). It carries `issues.jsonl` today; after this change it carries only the *derived* export, never the Dolt DB.
- **Machine A/B/C scenario** — A creates beads; B implements and closes some; C opens the issue view and must see B's closures. The driving requirement.

## 2. Problem

Beads made **Dolt the only backend** and demoted `.beads/issues.jsonl` to an export-only artifact. Overdeck's beads integration grew up in the JSONL era and is now **mixed-authority and split-brained**:

- `bd` reads/writes a local Dolt DB under `.beads/embeddeddolt/` (per machine, per checkout, gitignored).
- Multiple runtime paths still parse `.beads/issues.jsonl` **directly** as if authoritative.
- Work agents mutate beads with **raw `bd update`/`bd close`** shell commands from their sessions (the shipped work prompt tells them to). A TypeScript-only write door cannot intercept these.
- The only thing Overdeck transports cross-machine is `issues.jsonl` committed to `overdeck-state`; the Dolt DB never travels. There is **no `bd dolt push/pull` anywhere in Overdeck** (grep confirms zero).
- The issue view's beads panel reads the *dashboard machine's local* Dolt DB; refreshing does not sync from another machine.

**Live split-brain (measured 2026-07-12).** This machine has **two separate 1.1G Dolt databases for the same project** (`project_id 8403b792-11dd-4e86-b04c-ce7a6effd31b`):
- `${OVERDECK_HOME}/state/panopticon-cli/.beads/embeddeddolt` — the state worktree DB (canonical per PAN-2541);
- `/home/eltmon/Projects/overdeck/.beads/embeddeddolt` — the code-checkout DB, **no `redirect`**, so it is an independent clone.

The dashboard/deacon run with cwd = the code checkout, so their `bd` reads hit the code-checkout DB, while the write door commits from the state worktree. A resolver rooted by `cwd` reads a *different database* depending on where it runs. This is the concrete failure mode the read/write doors must eliminate: **a door can faithfully sync the wrong local store.**

**Schema divergence (`bd 1.1.0`).** Upgrading to `bd 1.1.0` revealed both DBs sit at Dolt schema **v32** while `bd 1.1.0` wants **v53**, and its migration-fork guard refuses to auto-migrate a remote-backed DB. As designated migrator on this box, we migrated the **state-worktree DB to v53** (802 open issues intact, verified) and **held** the `bd dolt push` (leaving `refs/dolt/data` at v32) because the remote push is a cross-machine cutover. The code-checkout DB remains at v32 and must be **redirected**, not independently migrated. This is not incidental to PAN-2564 — it is the same cross-machine coordination problem, and `bd 1.1.0` ships the exact primitives to solve it (designated migrator, bootstrap, cascade-repair pull).

**Export divergence (evidence, requires audit — not proof of loss).** A live Dolt `bd export --all` held **3,291** records vs **3,214** lines in the `overdeck-state` `issues.jsonl`. Part of this delta may be the `--all` universe versus an older issue-only export, and part may be the split-brain above. This is **evidence of divergence that FR-7 must audit at full fidelity before any winner is chosen** — it is not a license to declare JSONL "lossy" and overwrite a side.

Root-cause history (verified): `bd` switched to Dolt in [PAN-386](https://github.com/eltmon/overdeck/issues/386); Dolt failures followed — [PAN-1158](https://github.com/eltmon/overdeck/issues/1158) (workspace Dolt DB silently empties → `bd export` writes empty → tracked `issues.jsonl` deleted), [PAN-939](https://github.com/eltmon/overdeck/issues/939)/[PAN-2261](https://github.com/eltmon/overdeck/issues/2261) (lock contention), [PAN-506](https://github.com/eltmon/overdeck/issues/506). `no-db: true` drifted in incidentally (commit `6ab6f1309a`, side effect of a bundled `bd init`); its *effect* masked those failures but it was never a deliberate design and is now unsupported.

## 3. Decisions (made in this document)

- **D1 — Dolt is canonical; the canonical copy travels on git as `refs/dolt/data`.** Each machine keeps a **gitignored local Dolt working copy** (disposable cache, rebuildable via `bd bootstrap`). Source of truth = Dolt refs on the git remote.
- **D2 — `refs/dolt/data` lives on the project's own git remote** (same remote as code / `overdeck-state`), via `bd dolt remote add origin git+ssh://…` (stored as `sync.remote`). No external DoltHub/S3.
- **D3 — `issues.jsonl` is a derived, validated recovery/interoperability export only.** Never a live write surface, never a canonical read source in production paths. It stays committed to `overdeck-state` for human/diff/disaster-recovery use, produced by the write door with integrity checks (refuse-empty, source-head record, count/ID verify over one named universe), never by line-union merge.
- **D4 — One beads read door and one beads write door — enforced at BOTH the TypeScript layer AND the agent shell layer.** Live reads go through the resolver; all mutations go through the writer; **agents mutate only through `pan beads …` (FR-9)**, and raw mutating `bd` is mechanically rejected in agent environments. No route/agent/hook/prompt/skill touches `issues.jsonl` or raw `bd` mutation for canonical state.
- **D-HOME — One physical local Dolt home per project** (FR-10). For a migrated project it is `${OVERDECK_HOME}/state/<project>/.beads/`. The code checkout, every feature worktree, and workspaces resolve to it via `.beads/redirect`; no other directory initializes its own DB. A doctor check blocks when two populated DBs with the same `project_id` are found.
- **D5 — The state migration must never copy a live Dolt layout to `overdeck-state`.** `.beads/dolt/`, `.beads/embeddeddolt/`, and Dolt runtime files (pid/lock/port/log/backup) are gitignored on all branches and on `overdeck-state`.
- **D6 — Divergent-writer policy: distributed writers over `bd 1.1.0` native merge + per-machine serialization.** The writer pulls before mutating and pushes after; cross-machine divergence is resolved by `bd 1.1.0`'s **cascade-repair / timestamp-based (local-favoring) pull merge**, not by a bespoke coordinator. `bd dolt push --force` and unattended `dolt.auto-push` are never used. When `bd`'s auto-resolve reports an *unresolved* conflict, the writer returns a **typed conflict result** (no side silently chosen). Per-machine, all `bd` ops serialize through `src/lib/bd-process-lock.ts`. This replaces revision-1's contradictory "single-writer fallback." The exact observed merge outcome is pinned by the WI-12 two-clone divergent-write test (C1).
- **D7 — Reconcile before cutover, at full fidelity, in isolation.** For every project, clone `refs/dolt/data` into an **isolated temporary DB** (never pull into the live DB), inventory the exact Dolt tables/columns, and produce a deterministic no-loss report across {live local Dolt, isolated `refs/dolt/data` clone, `overdeck-state` `issues.jsonl`} before any import/push/winner-selection. The reviewed report is the artifact that unlocks the cutover marker (D-MARKER).
- **D-MARKER — Cutover is a recorded state machine, not a directory shape** (FR-1). A project is "cut over" only when a durable marker records: remote URL, remote Dolt head, local reconciled head, reconciliation-report path+hash, and completion time. The migration gate validates this marker + the remote ref, not the mere presence/absence of `embeddeddolt/`.
- **D8 (reframed) — All *code* ships in one delivery; per-project *operational cutover* is separately gated.** Per the operator's "nothing carved out, implement it all now," every FR/NFR and all machinery (safety gate, doors, agent surface, sync, tooling, this machine's own cutover proof) land in **this issue, one delivery** — no code phase is deferred to a follow-up. But the **risky per-project data cutover** (reconcile → review → wire remote → publish `refs/dolt/data` → flip the project) is an operator-reviewed rollout with its own recorded gate and rollback per project; it is **not** a precondition of code completion. AC-12 therefore requires the *machinery* + *this machine's cutover* to pass, and lists remaining projects (krux, lexerra, myn, …) as tracked operator rollouts, not code-blocking ACs.

## 4. Requirements (normative)

Functional:
- **FR-1 Safe migration gate (cutover-marker state machine).** `pan admin state migrate` (a) before cutover: detects any live Dolt data/runtime layout and refuses to copy it, mutating nothing; (b) after a valid cutover marker (D-MARKER) exists: migrates only allowed derived/config files, explicitly excluding DB/runtime dirs. The gate validates the marker + remote `refs/dolt/data`, not `issues.jsonl` presence/absence. Both the pre-cutover refusal and the post-cutover success path are tested.
- **FR-2 Canonical beads resolver.** All live beads reads use one resolver backed by `bd … --json` against the synchronized **canonical local Dolt home** (FR-10). Remove direct runtime parsing of `issues.jsonl`; JSONL may be read only by explicit recovery/import/export-verification/diagnostic paths on an allowlist (WI-15).
- **FR-3 Canonical beads writer (unit-of-work).** All mutations pass through one writer exposing a **`runMutationBatch`** transaction boundary that, per batch: acquires the project lock once, `bd bootstrap`s if needed, pulls once, performs+validates all operations, commits once, exports once (FR-6), and pushes once at a defined safe checkpoint; returns a typed `{ ok } | { conflict, localHead, remoteHead }`. Single claim/close is a one-operation batch. Closing a bead is not "durably complete" until its batch push succeeds; `pan done` cannot report durable completion with unpushed closes. Failure atomicity is specified (WI-3): a failed batch reverts or blocks the working set for operator recovery — never pushes a partial plan.
- **FR-4 Cross-machine bootstrap.** A fresh clone / newly-registered machine detects `refs/dolt/data` and hydrates via `bd bootstrap`. A plain git checkout is never treated as proof beads are current; the resolver bootstraps first if the local canonical DB is absent/empty while `refs/dolt/data` exists.
- **FR-5 Dashboard freshness.** The dashboard obtains beads progress from the resolver. A single-owner background synchronizer (WI-5) pulls remote Dolt changes off the UI path (never `execSync`), and on a head-advancing pull emits a domain event that the frontend consumes to invalidate its beads query (WI-5 transport). The 10s UI poll issues no network pull. The beads rail exposes `lastSyncedAt`, freshness age, and a stale/error badge.
- **FR-6 JSONL recovery export (one universe, exact commands).** After successful canonical mutations/sync, produce a validated `issues.jsonl` export that: uses one named record universe on both export and verify sides; refuses to replace a non-empty known-good snapshot with an unexpectedly-empty export; records the source Dolt head (via `bd vc status`) into `export-state.json`; verifies count + ID set (same universe) before publishing; never line-union-merges; distinguishes a genuinely-empty new project from corruption by checking the Dolt head/commit exists rather than a vague sentinel; is documented as derived.
- **FR-7 Reconcile existing divergence (isolated, full-fidelity).** Before enabling the new flow for a project: take independent safety exports first; clone `refs/dolt/data` into an isolated temp DB (never pull into the live DB); inventory exact Dolt tables/columns; compare normalized issue rows + labels + dependencies + comments + non-issue/config records + relevant Dolt heads; distinguish "absent" from "outside export scope"; verify counts + sample-resolve; produce a deterministic no-loss report and a review/approval artifact. Import/push/delete/winner-selection happen only after review.
- **FR-8 Standardize configuration.** Remove unsupported `no-db` keys; validate `sync.remote`; define the supported `bd` version as a **policy** (min compatible version, single resolver — WI-16), not a second drifting literal; never commit `dolt/`, `embeddeddolt/`, backups, or pid/port/lock/log files to any code branch or `overdeck-state`.
- **FR-9 Agent-facing mutation door (mechanically enforced).** Beads mutations available to agents are exposed as `pan beads claim|update|close|create|dep|delete` backed by the writer (FR-3). All prompts, skills, hooks, lifecycle code, and operator docs use these. Supervised agent environments **mechanically reject raw mutating `bd` verbs** (a scoped `bd` wrapper/PATH shim permits read verbs, rejects mutation verbs, and redirects to `pan beads …`; the writer invokes the real binary by resolved absolute path). A no-loss audit enumerates every supported mutating bead action and proves each has a home in the new surface.
- **FR-10 One physical local Dolt home + resolution map.** Name the one canonical local Dolt home per project (D-HOME) and define how main, every worktree, `overdeck-state`, remote workspaces, dashboard routes, CLI commands, and spawned agents resolve to it (redirect files + `resolveSharedBeadsDir`). No non-canonical directory initializes its own DB. Startup/doctor checks detect multiple populated same-`project_id` DBs and block rather than silently choose.

Non-functional:
- **NFR-1 Concurrency safety.** Serialize local `bd` ops through `src/lib/bd-process-lock.ts` keyed by `resolveSharedBeadsDir`. Divergent Dolt histories are handled by D6 (bd native merge + typed conflict). `dolt.auto-push` stays OFF. Network pulls must NOT run inside a globally-contended lock in a way that recreates the documented lock-starvation (see NFR-4 budgets).
- **NFR-2 Availability.** Remote-Dolt failure may leave the UI in a clearly-marked stale/read-only state but must not fabricate zero progress, silently fall back to an unverified JSONL snapshot, or destroy local work.
- **NFR-3 Observability.** Log/expose local Dolt head, last pulled remote head, last successful pull/push, freshness age, and sync/conflict errors, in standalone operator-facing sentences.
- **NFR-4 Performance budgets.** Define and test: local resolver read latency; dashboard beads-poll latency (no network); background head-check/pull interval + jitter + backoff; per-bead close durability (batch push) budget; batch plan-finalization budget. Freshness must not reintroduce bd lock starvation — head checks/pulls run under the project lock with a bounded hold and off the request path.

### WI-1 — Migration gate as cutover-marker state machine (FR-1, D5, D-MARKER)
**Files:** `src/cli/commands/admin/state-migrate.ts`; new `src/lib/beads/dolt-layout.ts`; new `src/lib/beads/cutover-marker.ts`.
**Change:** `detectLiveDoltLayout(beadsDir)` → true if any of `dolt/`, `embeddeddolt/`, `dolt-server.pid|lock|port|log`, `*.dolt` exist. `cutover-marker.ts` reads/writes `${OVERDECK_HOME}/state/<project>/beads-cutover.json` `{ remoteUrl, remoteDoltHead, localReconciledHead, reconcileReport: {path, sha256}, completedAt }`.
