## Glossary

- **Advancing ceiling (PAN-1665)** — `totalCeiling = max_work_agents (6) + reserved_advancing_slots (3) = 9` (`src/lib/cloister/concurrency.ts:29-30,70`). The gate every review/test/ship dispatch consults is `canDispatchAdvancing()`/`tryReserveAdvancingSlot()` (concurrency.ts:160,193).
- **How the ceiling is counted (CORRECTED)** — `canDispatchAdvancing()` reads `countRunningAgents()` (concurrency.ts:130-143), which derives counts from **`countAgentsByStatus('running')` — the SQLite `agents` table**, grouped by role (advancing roles = review/test/ship). It is **NOT** tmux-based. Consequence: **killing a tmux session does NOT free a ceiling slot** until the agent's `agents`-table row is flipped to `status='stopped'`. (The prior draft's glossary claimed `countRunningAgents` counts tmux-alive sessions — that was wrong and is the reason a naive reaper does not free the slot. `describeRunningAgents()` at concurrency.ts:92 is tmux-based, but it is only a log helper, not the gate.)
- **Advancing zombie** — an `agent-<id>-<role>` tmux session still alive and idle after its verdict is recorded (or after its issue merged); its `agents`-table row stays `running`, so it keeps holding a ceiling slot.
- **`KEEP_SPECIALIST_SESSIONS_ALIVE`** — boolean in `src/lib/cloister/reap-terminal-sessions.ts:33`, currently `true` (PAN-2007 operator request). When true, `checkTerminalAdvancingSessions()` (deacon.ts:2481) returns early without reaping, and the completion path (`specialists/legacy-routes.ts:245`) skips the session kill. **This plan leaves it `true`.**
- **Test verdict artifact** — `<workspace>/.pan/test/result.json`, written by the test agent BEFORE its POST (test-agent-queue.ts:44). Read by `readTestVerdictArtifact()` (test-verdict.ts:54).
- **Per-issue journal** — `<workspace>/.pan/records/<issue-lower>.json` (the `pipeline` block); the durable verdict store (PAN-1908). Written by `updateIssueRecordForReviewStatusSync` inside `setReviewStatusSync` (review-status.ts:408). Read by `readJournalStatusSync` (overdeck/review-status-record-sync.ts:58).
- **Journal reconcile-on-read (PAN-1988)** — `getReviewStatusSync(issueId)` (review-status.ts:757) merges a newer journal into the DB (`dbUpsert`), re-emits handoff lifecycle events (`review.approved`, `test.passed`), delivers blocked/failed feedback host-side, and recovers a written test artifact. `loadReviewStatuses()` (review-status.ts:182) is a **pure DB read and does NOT reconcile** — so the patrol readers never see a journaled-but-unposted verdict.
- **`isRoleTerminal(role, status)`** — reap-terminal-sessions.ts:77: review terminal when reviewStatus ∈ {passed,failed,blocked}; test terminal when testStatus ∈ {passed,failed}; ship terminal when readyForMerge=true or mergeStatus ∈ {merged,failed}.
- **`sessionsToReapForRole(issueId, role, alive)`** — reap-terminal-sessions.ts:55: the alive sessions belonging to an issue's advancing role (`agent-<id>-review`, `agent-<id>-review-*`, `agent-<id>-<role>`, legacy `specialist-*`). Already exported.
- **Advancing agent id == tmux session name == `agent-<issue-lower>-<role>`** — verified review-agent.ts:412,630.
- **Boot reconciliation (PAN-2076)** — `applyBootReconciliationDecision()` (deacon-auto-resume.ts:885) resumes work agents; it does NOT reconcile advancing verdicts nor reap advancing sessions. `startDeacon()` (deacon.ts ~:3371) runs `reconcileAgentLiveness()` then `runScheduledPatrol('startup')`.

## Problem (verified 2026-07-07)

### 2026-07-03 incident

9 of 9 advancing slots were held by sessions whose verdicts were already done — **two merged, seven non-merged-but-terminal** (verdict recorded, issue not yet merged). `checkPendingTestDispatch` (deacon.ts:1148) and every re-dispatch deferred on `tryReserveAdvancingSlot()`. The pipeline froze for hours until a redeploy + manual `tmux kill-session`.

### Root causes (verified in source)

1. **The reaper is disabled.** `KEEP_SPECIALIST_SESSIONS_ALIVE = true` (reap-terminal-sessions.ts:33) no-ops `checkTerminalAdvancingSessions()` (deacon.ts:2481) and the completion-path kill (specialists/legacy-routes.ts:245). Completed advancing sessions are never reaped.
2. **No advancing-session reaper for merged issues.** `checkMergedWorkSessions()` (deacon.ts:2514) reaps only the WORK session `agent-<id>`. Both merged sessions in the incident were advancing sessions.
3. **Journal verdicts are not reconciled systematically.** The patrol/boot readers use `loadReviewStatuses()` (raw DB). A verdict that only reached the journal (POST failed: `Effect.catchAll is not a function`, `SQLITE_READONLY`) leaves the DB at `reviewing`/`testing`, so `isRoleTerminal` is false and nothing reaps it. `getReviewStatusSync` would reconcile, but nothing calls it for every in-flight issue.
4. **Reaping does not free the slot (count is DB-based).** Even a working reaper only `killSession`s; the `agents` row stays `running` and `countRunningAgents()` keeps counting it until the next `reconcileAgentLiveness()` — a cycle later, in `runPatrol` it runs BEFORE the reaper (deacon.ts:2683 vs 2763).
5. **Orphaned in-progress stage, no live specialist (operator comment, 2026-07-04, PAN-2145/PAN-2318).** When a review/test agent dies/reaped mid-stage with the verdict never recorded, `review_status` sits at `reviewing`/`testing` with no live agent. The existing recovery patrols read raw DB — so a journaled verdict is not reconciled (they'd wastefully re-dispatch), and with no verdict recovery required a manual `pan review restart`.

**Combined effect:** a transient POST failure → verdict in journal only → sessions alive → DB shows no terminal verdict → ceiling reads full → ALL advancing dispatch frozen, permanently, until manual intervention.

## Requirements

- **FR-1** — On boot (inside `startDeacon()`) AND on each periodic patrol, call `getReviewStatusSync(issueId)` for every in-flight issue so a journaled verdict is reconciled into `review_status` before the reapers run.
- **FR-2** — A new `checkMergedAdvancingSessions()` reaps advancing sessions (`agent-<id>-review`, `agent-<id>-review-*`, `agent-<id>-test`, `agent-<id>-ship`) for issues whose `mergeStatus === 'merged'`, bypassing `KEEP_SPECIALIST_SESSIONS_ALIVE` (merged issues have no diagnostic value).
- **FR-3** — `checkMergedAdvancingSessions()` runs both at boot (in `startDeacon()`) and in the periodic patrol.
- **FR-4** — This plan does NOT flip `KEEP_SPECIALIST_SESSIONS_ALIVE`; the PAN-2007 keep-alive is preserved (operator decision 2026-07-07).
- **FR-5** — Regression: with 9 advancing sessions held by merged issues at ceiling 9, after `checkMergedAdvancingSessions()` + the stopped-mark run, all 9 are reaped, their `agents` rows are `stopped`, and `canDispatchAdvancing()` returns true.
- **FR-6** — Idempotency: reconcile and both reapers may run repeatedly (boot + patrol) with the same result as one run (no duplicate state writes, no throw on an already-dead session, no-op stopped-mark when already stopped).
- **NFR-1** — No new explicit `any`; async only (no `execSync`); no new files ≥1,000 lines.
- **NFR-2** — The reconcile fan-out is bounded to in-flight issues: skip `mergeStatus === 'merged'`/closed/completed; reconcile only issues in pending/reviewing/passed/failed/blocked/testing/dispatch_failed.
- **FR-7** — A new `checkIdleTerminalAdvancingSessions()` reaps NON-merged advancing sessions whose verdict is terminal (`isRoleTerminal`) AND whose pane has been idle ≥ `TERMINAL_ADVANCING_IDLE_REAP_MS` (default 10 min, mirroring PAN-1730's `AWAITING_TEST_IDLE_REAP_MS`). It bypasses `KEEP_SPECIALIST_SESSIONS_ALIVE` only via the idle gate, so operator inspection is preserved for the idle window. Runs on boot and patrol.
- **FR-8** — Every reap in this plan (`checkMergedAdvancingSessions`, `checkIdleTerminalAdvancingSessions`) flips the reaped `agent-<id>-<role>` row to `status='stopped'` via the write door (`getAgentStateSync` → `markAgentStoppedState` → `saveAgentStateSync`) right after `killSession`, so the DB-based `countRunningAgents()` frees the slot in the same cycle (fixes root cause 4).
- **FR-9** — Orphaned-stage self-heal: `recoverStalledReviewConvoys` and the test-orphan path (`reconcileReviewStatusOrphan`) reconcile the journal (`getReviewStatusSync`) before deciding; if the verdict is now terminal they skip re-dispatch (the reaper frees the slot); they re-dispatch only a stage that is in-progress with no live specialist AND no journaled verdict — no manual `pan review restart`.
