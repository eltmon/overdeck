## 1. Glossary

- **Deacon** — the lifecycle watchdog inside the dashboard server (`src/lib/cloister/deacon.ts`). `startDeacon()` (line 3350) installs a `setInterval` at `config.patrolIntervalMs` (60 000 ms, `DEFAULT_CONFIG` line 221) that calls `runPatrol()` (line 2529), plus a separate 15 s resource-pressure timer (`MEMORY_PATROL_INTERVAL_MS`, line 316).
- **Patrol / step** — one function invocation inside `runPatrol()`. A **budgeted** step is wrapped in `runBudgetedPatrol('<name>', fn)` (`src/lib/cloister/patrol-budget.ts:186`). The five **alarm** steps (`runStallSweeperPatrol`, `checkApiErrorAgents`, `recreatedStateWarnings`, `recordMainDivergenceHealth`, `checkMassDeath`) are called directly, never budgeted (Appendix C #3, #64, #70, #71, #77).
- **Tick** — one `runPatrol()` pass. `state.patrolCycle` (persisted in `~/.overdeck/deacon/state.json` via `loadState()`/`saveState()`) counts ticks across restarts; today several steps gate on `patrolCycle % N === 0`.
- **Chore** — a Keep/Rewire patrol that is housekeeping (cleanup, retention, resource hygiene, projection, retry policy) rather than stuck detection. This PRD moves 29 of them off the tick.
- **Cadence** — how often a patrol runs: `tick` (every pass), `fast` (5 min), `hourly`, `daily`.
- **Housekeeping scheduler** — new module `src/lib/cloister/housekeeping-scheduler.ts`: its own 60 s timer that runs each chore when `now - lastRunAt >= cadenceMs`, with `lastRunAt` persisted to `~/.overdeck/deacon/housekeeping.json` so cadences survive `pan reload`.
- **Patrol registry** — new module `src/lib/cloister/patrol-registry.ts`: the single declarative list of every surviving patrol with its cadence. `pan doctor` and the no-loss audit read it.
- **No-loss audit** — `tests/unit/lib/cloister/patrol-no-loss-audit.test.ts`. Regex-parses `runBudgetedPatrol('<name>'` out of `deacon.ts` and holds the set against Appendix C (`KEEP_REWIRE` 42 names, `PENDING_SOAK_DELETION` 30 names, `PHASE_5_ADDITIONS` 1 name, `DELETED_PATROLS` map to covering fixtures).
- **Would-fire counter** — `recordWouldFire(patrol, issueId)` (`src/lib/cloister/patrol-would-fire.ts:110`) appends `{ts, patrol, issueId, shadow}` to `~/.overdeck/deacon/would-fire.jsonl`. `runShadowablePatrol(name, fn)` (line 202) passes `shadow = (OVERDECK_PATROL_SHADOW === '1')` so the patrol can count without acting. `pan doctor` prints the 7-day table (`printPatrolWouldFireTable`, `src/cli/commands/doctor.ts:386`). The recorder marks itself unhealthy at `~/.overdeck/deacon/would-fire.unhealthy.json` on a failed append.
- **Patrol budget** — per-UTC-day action tally in `~/.overdeck/deacon/patrol-budget.json` (default 50, `cloister.patrolBudgets`); crossing it suspends the patrol for the day and emits one needs-you.
- **W29/W36/W41 protocol** — from the epic PRD (`drafts/pan-3845.md` on `overdeck-state`): per patrol, (1) counter + soak with zero for 7 days, (2) audit test proving the repaired state unreachable, (3) delete registration + function + tests, one commit per patrol naming the audit test and the counter value.
- **F15** — reliability-review finding: `reconcileInFlightJournals` compares an enriched read against the raw row and therefore "fires forever" (Appendix C row #4; epic W27).

## 3. Decisions

- **D1 — Split Part A's deletions into PAN-3895.** The 30 deletions are gated on 7 clean days of counters. On 2026-09-18 that window is ≥7 days away for the 22 Phase 3 patrols (clock started 2026-09-17T23:32Z), does not exist for the 7 Phase 4 patrols (no counters), and is invalid for `reconcileInFlightJournals` (F15 noise). A work agent starting now would land everything else and then hold an open `deacon.ts` PR for a week. PAN-3894 therefore delivers Part B plus every Part A prerequisite that is not time-gated (W6, W7, W8); PAN-3895 carries the deletions, the decision rule, and the per-patrol map (its body is the executable brief). The "<15 steps" acceptance moves to PAN-3895 with a precise definition of "step" (see §8).
- **D2 — Tick set is 14 steps.** 5 alarms + `runInvariantChecker` (every 10 ticks, unchanged) + 8 pipeline-progress or stuck-recovery steps that are tick-dependent or time-critical: `swarmJanitorPass`, `checkPostReviewCommits` (2-tick debounce), `patrolStrikeLandings`, `monitorReviewConvoySignals`, `checkDeadEndAgents`, `nudgeIdleWorkAgentsWithOpenBeads`, `checkThinkingSignatureCorruption` (must run before idle-suspend; corrupted sessions cannot resume), `refreshHostHeartbeatForEphemeralVms` (5-min VM watchdog). Everything else in Keep/Rewire (29 chores) moves to the housekeeping scheduler.
- **D3 — Durable due-times, not bare `setInterval`s.** `patrolCycle` is persisted, so today's `% 60` gates survive `pan reload`; a bare hourly/daily `setInterval` resets on every restart and daily chores would rarely fire on a machine that reloads several times a day. The scheduler ticks every 60 s and runs a chore when `now - lastRunAt >= cadenceMs`, persisting `lastRunAt` after each run. A chore with no recorded `lastRunAt` is due on the first scheduler tick after boot.
- **D4 — Three cadence classes only: `fast` = 5 min, `hourly`, `daily`.** No per-chore config; constants live in the registry. The event-driven option from the issue is already the primary path for `reconcileClosedIssueAgents`, `reconcileOrphanProposedSpecs`, and `reconcileIdleWorkspaceStacks` (reactive handlers in `service-reactive.ts`); their polled runs become the slow backstop. No new Docker-events subscriber: `checkWorkspaceContainerHealth` polls at `fast` (its restart backoff floor is already 60 s). Strike-workspace reaping cannot key on the merge event (the strike session is still alive when its merge lands; the reaper requires no live session), so it polls at `hourly`.
- **D5 — Cadence assignment (29 chores).**

  | Cadence | Chores (in scheduler order) | Why |
  | --- | --- | --- |
  | `fast` (5 min) | `patrolStaleTaskClaims`, `processPendingLifecycleForPatrol`, `runScheduledDeployPatrol`, `reconcilePendingPromotions`, `checkAndSuspendIdleAgents`, `checkMergedWorkSessions`, `checkMergedAdvancingSessions`, `refreshClaudeCredentialsForActiveRemoteAgents`, `reapCompletedRemoteAgents`, `checkInspectAgentTimeouts`, `checkWorkspaceContainerHealth`, `checkFailedMergeRetry`, `autoCloseOut`, `reconcileAutoMergeRows`, `reconcileTraefikNetworks`, `reconcileIdleWorkspaceStacks`, `patrolDockerBridgePool`, `reapOrphanedDashboardServers`, `reapLeftoverPlaywrightBrowsers`, `perProjectSpecialistPatrol` | pipeline-progress retries, resource hygiene, and dead-specialist detection; every internal grace or cooldown is ≥ 2 min, so a 5-min cadence adds at most 5 min of latency |
  | `hourly` | `reconcileOrphanProposedSpecs`, `reconcileClosedIssueAgents`, `reapMergedStrikeWorkspaces`, `reconcilePipelineLabelsPatrol`, `reconcileProjectStatePlanes`, `reconcileTerminalIssueResidue`, `cleanupStaleAgentState` | reactive primaries or projections; three already ran hourly |
  | `daily` | `sweepTranscriptRetention`, then `pruneTerminalStoppedAgents` | retention must see the registry row before GC removes it (comment at `deacon.ts:3037-3038`); both stay in one class, in this order |

  Latency changes worth knowing: inspect sessions are bounded at 12 + ≤5 min instead of 12 + ≤1; a crashed UAT container restarts within ≤5 min instead of ≤1; a failed `complete-planning` promotion retries every 5 min instead of every 60 s (after its 120 s grace).
- **D6 — `containerRestarts` bookkeeping leaves `DeaconState`.** Off-tick, `checkWorkspaceContainerHealth` cannot share `runPatrol`'s in-memory state and a separate `saveState()` clobbers it (comment at `:2419`). The restart-backoff map becomes module-level in-memory state (`Map<string, ContainerRestartRecord>`). Losing it across a dashboard restart resets a container's attempt count, which is acceptable: a restart loop gets at most five more attempts per process lifetime.
- **D7 — The registry never imports `deacon.ts`, statically or dynamically.** `scripts/lint-circular-deps.sh` runs madge, and madge counts `await import(...)` as a graph edge (verified 2026-09-18 with a two-file fixture: `a` static-imports `b`, `b` dynamic-imports `a` → reported as a cycle). `deacon.ts` will statically import the scheduler, which imports the registry, so any registry → `deacon.js` edge is a new cycle and fails `npm run lint`. The four chores whose functions live in `deacon.ts` (`checkAndSuspendIdleAgents`, `checkMergedWorkSessions`, `checkWorkspaceContainerHealth`, `cleanupStaleAgentState`) are therefore **injected**: `run` receives a `ChoreContext` whose `deacon` field carries those four functions, and `startDeacon` supplies them. Every other chore's `run` uses a dynamic `await import('./<module>.js')` of its own module; reachability over the madge graph (2026-09-18) shows none of those 25 modules, nor `patrol-budget.ts`, `control-settings.ts`, `in-flight-guard.ts`, `merge-agent.ts`, `specialists.ts`, reaches `deacon.ts` or `service.ts`, so no other cycle can form. `pan doctor` imports the registry and the scheduler for listing only and never runs a chore.
- **D8 — Counters for the six Phase 4 patrols use the existing recorder unchanged.** Same call, same file, same `pan doctor` table; `checkStuckWorkAgents` is deleted instead (W8) because a `return []` stub repairs nothing and needs no soak.
- **D9 — The `reconcileInFlightJournals` counter records a real fold only.** A would-fire and an action string are recorded only when `readJournalStatusSync(issueId)` returns a journal whose `updatedAt` is newer than the DB row's `updatedAt` before the read. This also stops the patrol from crossing its 50/day budget every day (145 firings in 5 h on 2026-09-18) and paging the operator.
- **D10 — Effort and models:** nothing here changes model routing or effort; no `--model`/effort flags anywhere.

### 5.2 `src/lib/cloister/housekeeping-scheduler.ts` (new)

```ts
export const HOUSEKEEPING_SCHEDULER_TICK_MS = 60_000;
export function housekeepingStatePath(): string; // join(getOverdeckHome(), 'deacon', 'housekeeping.json')
export interface HousekeepingState { version: 1; lastRunAt: Record<string, string> } // ISO per chore
export function readHousekeepingState(path?: string): HousekeepingState;  // tolerant: missing/torn → { version: 1, lastRunAt: {} }
export function isChoreDue(chore: HousekeepingChore, state: HousekeepingState, nowMs: number): boolean;
export interface HousekeepingDeps {
  context: ChoreContext;                             // startDeacon passes its four deacon-resident functions
  chores?: readonly HousekeepingChore[];            // default HOUSEKEEPING_CHORES
  now?: () => number;
  isPaused?: () => Promise<boolean>;                 // default: lazily `(await import('../overdeck/control-settings.js')).isDeaconGloballyPaused()` so pan doctor's static import graph stays free of SQLite app_settings
  log: (level: 'info' | 'warn' | 'action' | 'error', message: string) => void; // deacon's appendDeaconLog
  runBudgeted?: typeof runBudgetedPatrol;
  statePath?: string;
}
export async function runHousekeepingTick(deps: HousekeepingDeps): Promise<string[]>; // one pass; exported for tests only. Decision: the manual trigger POST /api/deacon/patrol runs the 60 s tick only; chores are not manually triggerable.
export function startHousekeepingScheduler(deps: HousekeepingDeps): void; // setInterval(tick).unref(); single-flight via createInFlightGuard() key 'housekeeping'
export function stopHousekeepingScheduler(): void;
export interface HousekeepingRow { name: string; cadence: PatrolCadence; trigger?: string; lastRunAt: string | null; nextDueAt: string | null }
export function listHousekeepingRows(nowMs?: number, statePath?: string): HousekeepingRow[]; // for pan doctor
```

`runHousekeepingTick`: if `await isPaused()` → log once per pause span (mirror `hasLoggedGlobalPauseSkip`) and return `[]`. Otherwise read state once, iterate chores in order; for each due chore: `const actions = await runBudgeted(chore.name, chore.run)` inside try/catch (`warn` on throw: `Housekeeping chore ${name} failed: ${message}`), log every action at `action`, then `state.lastRunAt[name] = new Date(now()).toISOString()` and write the file atomically (tmp + `renameSync`, the `patrol-budget.ts:73-84` pattern). A chore that throws still gets `lastRunAt` stamped so a broken chore retries at its cadence, not every minute.

### 5.3 `deacon.ts` after wiring (W4)

`runPatrol()` keeps, in this order: `runStallSweeperPatrol` (direct), `monitorReviewConvoySignals`, `checkPostReviewCommits`, `patrolStrikeLandings`, `swarmJanitorPass`, `nudgeIdleWorkAgentsWithOpenBeads`, `checkThinkingSignatureCorruption`, `checkDeadEndAgents`, `refreshHostHeartbeatForEphemeralVms`, `checkApiErrorAgents` (direct), `runInvariantChecker` (`% 10`), `recreatedStateWarnings` (direct), `recordMainDivergenceHealth` (direct), `checkMassDeath` (direct) — interleaved with the 30 pending steps exactly where they are today (their relative order is untouched; PAN-3895 removes them). `deacon.ts` statically imports `./housekeeping-scheduler.js` (safe: nothing under the scheduler reaches `deacon.ts`, see D7). `startDeacon()` calls `startHousekeepingScheduler({ log: appendDeaconLog, context: { deacon: { checkAndSuspendIdleAgents, checkMergedWorkSessions, checkWorkspaceContainerHealth, cleanupStaleAgentState } } })` after installing `deaconInterval`; `stopDeacon()` calls `stopHousekeepingScheduler()`. Chore actions reach the deacon log (`GET /api/deacon/logs`, the log file) through `appendDeaconLog`; they are not part of `PatrolResult.actionsToken` (`GET /api/deacon/status` shows tick actions only). `addLog` is exported as `appendDeaconLog(level, message)` (cycle omitted).
