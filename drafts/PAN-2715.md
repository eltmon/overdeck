# PAN-2715 — `pan close` becomes the Definition-of-Done gate

**Issue:** https://github.com/eltmon/overdeck/issues/2715
**Related:** PAN-2713 (deploy step / build-commit exposure — NOT implemented here)

## Glossary

- **DoD** — Definition of Done: the 8-row table in `docs/DEFINITION-OF-DONE.md`. An issue is done only when every row is green.
- **Gate** — the pre-flight audit `pan close` runs before any cleanup: evaluate each DoD row mechanically, report a table, refuse completion on any unaccepted MISS.
- **Row id** — kebab-case key for a DoD row: `review`, `tests`, `verification`, `merged`, `post-merge`, `main-verify`, `deploy`, `teardown` (rows 1–8).
- **Accept flag** — `--accept-<row-id>` on `pan close`; an explicit, recorded override for one missed row. Never silent.
- **Read door** — the canonical resolver for a domain (two-doors tenet): `getReviewStatusSync` (review status), `readIssueRecordSync` (durable record/journal), `gh` CLI (forge), agents resolver, dashboard HTTP API.
- **Close-out record** — `closeOut` block of the per-issue record on `overdeck-state` (`PanIssueCloseOutRecord`, `src/lib/pan-dir/record.ts:57`).
- **verifying_on_main** — canonical issue state after `postMergeLifecycle()`; the label `verifying-on-main` maps to it.

## Problem

Close-out (`closeOut()` in `src/lib/lifecycle/workflows.ts:152`) verifies only branch-merge + its own teardown. Nothing audits the full DoD, so on 2026-07-15 PAN-2684/2690/2701 were fully closed-out while the live dashboard ran a build from before their merges (DoD row 7) — every fix inert until an operator asked.

## Requirements

- **FR-1** `pan close <id>` and the dashboard Close Out action evaluate every DoD row before any cleanup step and print/return a table: row, expected, observed, PASS/MISS/SKIP.
- **FR-2** Any MISS blocks close-out by default; completion requires the per-row `--accept-<row>` override (CLI) or `acceptedRows` (route body). `--force` never bypasses the gate.
- **FR-3** The gate result — all rows plus accepted misses with who/when — is written into the issue's close-out record on `overdeck-state` on a completed close-out.
- **FR-4** The gate enumerates rows from one shared definition module (`src/lib/lifecycle/dod.ts`); `docs/DEFINITION-OF-DONE.md` references it and a drift test locks the two together.
- **FR-5** Every fact is read through existing read doors only (two-doors tenet); no new direct store access.
- **FR-6** Row 7 (deploy) is best-effort until PAN-2713 lands: compare live dashboard process start time and `dist/dashboard/server.js` mtime against PR `mergedAt`; prefer a `buildCommit` field from `/api/version` when present.
- **NFR-1** Row checkers never throw and never hang: `execFile` with 10s timeouts, HTTP probes 3s; failures degrade to MISS with the error in `observed`.
- **NFR-2** Operator-facing gate output defines terms inline (operator-messages rule).
- **NFR-3** Tests use mocked doors only — never a live close-out against a real issue, never speculative destructive HTTP.

## Design decisions (made here, not by the executor)

1. **Gate location:** inside `closeOut()` in `src/lib/lifecycle/workflows.ts`, as the first step block, so CLI (`src/cli/commands/close.ts`) and dashboard route (`src/lib/overdeck/issue-close-out.ts:101` → `src/dashboard/server/routes/issues.ts:563`) share one implementation. `approve()`, `close()`, `deepWipe()`, reset/cancel are untouched.
2. **Row 4 reuses `verifyBranchMergedImpl`** (export it from `workflows.ts:410`, logic unchanged — no-loss). The old standalone verify-merged step is replaced by gate row 4.
3. **Rows 1–3 source:** `getReviewStatusSync(issueId)`; when null (status cleared by a prior close-out attempt — PAN-2611 re-run), fall back to the durable journal `readIssueRecordSync(project, issueId)?.pipeline`. `skipped` counts as PASS with a note (same semantics as `reviewGatesPassedSync`, `src/lib/review-status.ts:149`).
4. **Row 5 evidence:** canonical state `verifying_on_main` (gh state+labels door, `mapGitHubStateToCanonical`) or `mergeStatus: merged`, AND no running work/planning agent for the issue via the agents resolver.
5. **Row 6 definition:** CI check-runs on the merge commit concluded successfully (`gh api repos/…/commits/<sha>/check-runs`). No durable "verified on main" marker exists in code; forge CI is the only mechanical evidence. SKIP when no merge SHA or zero check-runs.
6. **Row 7 scope:** applies only when `/api/health`.repoRoot equals the issue's project root; other projects SKIP ("deploy semantics undefined"); unreachable dashboard = MISS. PASS best-effort requires BOTH server process start time AND dist mtime after `mergedAt`, or `buildCommit` ancestry (`git merge-base --is-ancestor`) when exposed (PAN-2713 forward-compat).
7. **Row 8** is performed by close-out itself (existing teardown + `_devnet` verification retained); it has no accept flag and its row result is synthesized from the teardown step results when writing the record.
8. **Overrides:** all rows 1–7 overridable, including `merged` (explicit + recorded beats the operator closing on GitHub directly). `acceptedBy` = `OVERDECK_AGENT_ID` ?? `os.userInfo().username`, `at` = ISO timestamp, plus the flag string.
9. **Persistence:** completed close-outs write `closeOut.dodGate { evaluatedAt, rows[], accepted[] }` via a new write-door function beside `markRecordPipelineClosedOutSync`; the PAN-2466 empty-closeOut preservation guard is extended to keep a populated `dodGate`. Blocked runs write nothing durable.
10. **Deacon auto close-out** (`src/lib/cloister/deacon-merge.ts:794` area) passes no accepts; a gate miss fails that auto close-out and is recorded via `recordAutoCloseOutFailure` — intended "refuse silent completion" behavior.

## Acceptance criteria (issue-level)

- **AC-1** (FR-1) `pan close` on an all-green issue completes and the close-out record contains the gate table. → items 8, 9.
- **AC-2** (FR-2, FR-6) `pan close` on an issue whose merge is not deployed reports row 7 MISS and does not complete without `--accept-deploy`. → items 7, 8, 10.
- **AC-3** (FR-3) Overrides appear in the close-out record with who/when. → item 9.
- **AC-4** (FR-4) Gate rows and the doc table cannot drift silently: shared module + drift test. → items 1, 2.

## Intersecting repo rules (restated for the executor)

- Two-doors tenet: extend resolvers/writers, never add direct store access.
- Never run a live close-out or send destructive HTTP in tests — mock the doors (pattern: `tests/unit/lib/lifecycle/workflows.test.ts`).
- `scripts/lint-skills.sh` fails CI if `pan close --help` flags and the skill drift — update `SKILL.md` in the same PR as the flags.
- No `execSync` anywhere server-reachable; use `execFile`/`execAsync` with timeouts.
- If any checker ever needs retry/delay logic, tests must use `vi.useFakeTimers()` — prefer no delays at all.
- Commit one vBRIEF item at a time and push before `pan task done`.
