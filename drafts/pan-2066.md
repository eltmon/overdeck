## Glossary

- **OKF (Open Knowledge Format):** markdown-bundle knowledge spec (Google Cloud, v0.1 draft) — a directory of concept `.md` files with YAML frontmatter plus reserved `index.md`/`log.md`. Spec: https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md
- **Bundle:** the OKF directory for a project. Resolved from `.okf.yml` at the code-repo root (keys `bundle:` relative path, `remote:` git URL). Overdeck's bundle: `../overdeck-knowledge`.
- **`/okf` skill:** Overdeck-shipped Claude Code skill at `sync-sources/skills/okf/` (verbs: init/author/convert/sync/study/retro/extract/validate/lint/embed). Shipped in PAN-2468.
- **open-knowledge (`ok`):** `@inkeep/open-knowledge` (https://github.com/inkeep/open-knowledge), GPL-3.0 — a WYSIWYG markdown editor + graph wiki-link viewer + MCP server over any folder of markdown with frontmatter. CLI binary is `ok`; `ok start` serves a local web UI. Requires Node 24+.
- **Mere aggregation:** the GPL boundary we rely on — installing open-knowledge as a separate global binary and invoking it as a subprocess/iframe keeps `@overdeck/*` MIT. Never `import`, link, or bundle it.
- **Progressive installation:** Overdeck's install-on-first-use pattern. Precedent: `ensureOllama()` in `src/lib/ollama.ts` (PAN-1641 note at the top of the file) — health-check, then optionally auto-install + start, with injectable `runCommand`/`installOllama`/`startServer` for tests.
- **Knowledge-index injection:** `src/lib/memory/injection.ts` builds a "Knowledge bundle concept index" block (concept id + type + description per line, plus recent `log.md` entries), budgeted at 1500 tokens (`knowledgeIndex: 1500`, line ~17), and folds it into agent prompts at spawn (`src/lib/agents/spawn-prep.ts`, `surface: 'spawn'`, line ~602) and per-prompt via the hooks route (`src/dashboard/server/routes/hooks.ts` imports `injectPromptTimeMemory`). Gated by `memory.features.knowledge_index` (default true, `src/lib/memory/settings.ts` `booleanOrDefault(features.knowledge_index, true)`).

## Requirements

### Functional

- **FR-1** `ensureOpenKnowledge()`: a progressive installer that (a) detects a working `ok` binary, (b) if missing and `autoInstall` is enabled, runs `npm install -g @inkeep/open-knowledge`, (c) verifies the installed binary launches, (d) fails loudly with actionable text when Node < 24 is the cause. Never a hardcoded silent fallback.
- **FR-2** `/okf open` skill verb and `pan knowledge open` CLI: resolve the bundle from `.okf.yml`, ensure open-knowledge (FR-1), start/reuse a local `ok start` server for the bundle, and print/open its URL. `--no-install` skips the auto-install and errors if the binary is absent.
- **FR-3** Dashboard **Knowledge page**: a new tab that hosts the open-knowledge viewer for the current project's bundle inside the dashboard (embedded UI), with graceful states for: no bundle configured, open-knowledge not installed (offer one-click progressive install), viewer starting, and embed-blocked (fallback link that opens the viewer in a new tab).
- **FR-4** Server-side viewer lifecycle: the dashboard server owns starting/stopping the `ok` subprocess per project (spawn on first open, health-check, reuse across page visits, kill on dashboard shutdown). All process handling async (`spawn`), no `execSync`.
- **FR-5** Same-origin access: the dashboard proxies the viewer (HTTP + WebSocket) under a dashboard path so the embedded UI works from `https://overdeck.localhost` without mixed-content or cross-origin breakage.
- **FR-6** Round-trip safety gate: before recommending edit-in-viewer, verify open-knowledge preserves YAML frontmatter losslessly on save and never touches `index.md`/`log.md`. If lossy: the Knowledge page still ships, labeled read-only ("view and search; edit via `/okf author`"), and the finding is recorded on the issue.
- **FR-7** MCP wiring documented: how to let `ok init` register its MCP so harness agents get agentic search over the bundle; opt-in, never run automatically by Overdeck.

### Non-functional

- **NFR-1** GPL isolation: no `import`/`require` of `@inkeep/open-knowledge` anywhere in `@overdeck/*`; subprocess + HTTP only. A grep-able CI guard is acceptable but optional.
- **NFR-2** Dashboard remains Node 22; `ok` runs as its own binary under whatever Node the user's PATH provides. Node 24 is `ok`'s requirement, not ours — detect and report, never auto-upgrade Node.
- **NFR-3** No new blocking calls on the server event loop (`execSync` ban); retry/delay tests use fake timers (`vi.useFakeTimers()`), per repo rules.
- **NFR-4** The viewer is optional at every layer: absent binary, absent bundle, or user opt-out must never degrade any existing dashboard surface.

## Design decisions (made here, not left to the executor)

1. **Embed via dashboard proxy, not direct localhost iframe.** The dashboard is served at `https://overdeck.localhost` (Traefik); an iframe to `http://localhost:<port>` is mixed content and will be blocked. The server proxies `/knowledge-viewer/*` → the `ok` server (HTTP and WS). **Implementation checkpoint:** if `ok`'s UI sets `X-Frame-Options`/CSP `frame-ancestors` that block framing even same-origin-via-proxy, fall back to FR-3's "open in new tab" state as the primary affordance and note it on the issue.
2. **One `ok` process per project, lazy.** Started on first Knowledge-page visit or `/okf open`, tracked in a server-side map keyed by project, port chosen by the OS (pass `--port 0` if supported, else probe a free port). **Implementation checkpoint:** confirm `ok start`'s actual flags (`ok start --open <bundle>` was the June analysis; verify `--port`/`--no-open` equivalents from `ok --help`) — adjust the launcher accordingly; the process contract (spawn/health/reuse/kill) is fixed regardless of flag spelling.
3. **Progressive install mirrors `ensureOllama`.** Same options shape (injectable `runCommand`, `installOpenKnowledge`, health attempts, retry delay) so tests are pure and fast. Auto-install default: **on** for the interactive `/okf open` and dashboard button (both are explicit user gestures), **off** for anything unattended.
4. **`pan install` mention only.** `pan install` gains a one-line pointer in its summary output ("knowledge viewer installs on first use — `pan knowledge open`"); it does NOT eagerly install open-knowledge. Progressive install replaces the earlier "pan install optionally installs it" idea from the June issue body.
5. **Read path stays canonical.** All bundle resolution goes through `resolveKnowledgeBundleRoot()` (exported if not already) — the CLI verb and the viewer service both call it.
