## Glossary

- **`pan done`** — the CLI command in `src/cli/commands/done.ts` that a work agent runs to signal work completion; it runs a sequential multi-step submission flow (rebase → tracker update → PR creation → state writes → review dispatch).
- **`doneCommand`** — the entry-point function (`doneCommand(id, options)`) at `done.ts:470`.
- **`reviewRequestedAt`** — the ISO-8601 timestamp written into both `review_status` (SQLite cache) and the per-issue record's `pipeline` block (durable journal) by `setReviewStatusSync`; `needsReviewDispatch` uses it to decide whether a review dispatch is owed. Defined in `PanIssuePipelineRecord` (record.ts:104).
- **`needsReviewDispatch`** — pure function in `src/lib/review-dispatch-decision.ts` that returns true when `reviewRequestedAt` is set, newer than `reviewSpawnedAt`, and `reviewStatus !== 'reviewing'`.
- **Deacon patrol** — the periodic watchdog loop in `src/lib/cloister/deacon.ts` that runs every ~60–144 s; each pass is a numbered `patrolCycle`; patrols call registered async functions (e.g. `checkPendingTestDispatch` at deacon.ts:2881).
- **Completed marker** — the file `${AGENTS_DIR}/<agentId>/completed` (written at done.ts:780), existence of which triggers `checkCompletionMarkers()` in `service.ts` to fire the review pipeline.
- **`panDoneRecoveredAt`** — new durable tombstone field to be added to `PanIssuePipelineRecord` in `record.ts`; guards the deacon patrol from re-firing an already-recovered stuck issue.
- **Per-issue record** — the durable JSON at `<workspace>/.pan/records/<issueId-lower>.json` (permanent plane), typed as `PanIssueRecord` in `src/lib/pan-dir/record.ts`; its `pipeline` block (`PanIssuePipelineRecord`) is the source of truth for verdicts.
- **Review status** — the per-issue row managed by `src/lib/review-status.ts` (`getReviewStatusSync` / `setReviewStatusSync` / `clearReviewStatus`); the SQLite row is a rebuildable cache; the per-issue record journal is the source of truth.
- **Forge adapter** — `src/lib/forge.ts`; `getExistingGitHubArtifact` (forge.ts:133) checks for an open GitHub PR via GitHub App (GraphQL) then falls back to `gh pr view` (REST CLI).

## Problem (verified 2026-07-04)

### PAN-2203 incident (2026-07-01)

`agent-pan-2203` completed all 14 beads, ran `pan done`, hit a GitHub GraphQL rate limit during PR creation, manually created the PR via REST (`gh pr create` REST path), pushed a final record commit, but **never re-ran `pan done`**. The pipeline's completion chain never fired:

- `reviewStatus = 'pending'`
- `reviewRequestedAt` empty
- Completed marker (`~/.overdeck/agents/agent-pan-2203/completed`) never written
- PR #2206 open and mergeable; all beads closed

Recovery: operator ran `pan done PAN-2203` manually →review + test dispatched.

### Root cause: step-sequence in `doneCommand`

Reading `doneCommand` (done.ts:470) end-to-end, the steps run sequentially inside a single try-block ending at catch (done.ts:988):

| Step | Lines | Description | Idempotent? |
|------|-------|-------------|-------------|
| Pre-flight | 577–636 | uncommitted changes, lint, typecheck, tests | — |
| Step 0 | 641–691 | rebase+push via `rebaseAndPushRepos` | Yes (skip if already current) |
| Step 1 | 697–727 | tracker label update (`updateGitHubToInReview`) | Low-harm re-add |
| **Step 2** | 739–753 | `createReviewArtifactsForIssue` (PR creation) | **Yes** for GitHub via `getExistingGitHubArtifact` — but **throws** if the existing-PR lookup also rate-limits |
| Step 3 | 755–768 | Agent state → stopped | Yes |
| **Step 4** | 770–784 | Write completed marker | Yes (overwrites) |
| Step 5 | 798–832 | Already-merged / already-reviewed guards | — |
| **Step 6** | 834–850 | `setReviewStatusSync` with `reviewRequestedAt` | Yes |
| Step 7 | 886–982 | HTTP auto-trigger to dashboard | Retried |

**When Step 2 throws**, execution falls into the catch block at done.ts:988 (`spinner.fail(error.message); process.exit(1)`). Steps 4 and 6 never run: the completed marker is not written, `reviewRequestedAt` is not set, the HTTP trigger never fires. The PR exists on GitHub but nothing ever dispatches review.

**Step 2's idempotency caveat:** `createReviewArtifactsForIssue` calls `getExistingGitHubArtifact` (forge.ts:207) before creating a new PR. When GitHub App is configured, `getExistingGitHubArtifact` uses `listPullRequestsForHead` (GraphQL at forge.ts:142); under a GraphQL rate limit this also throws — so even the idempotency guard fails. The `gh pr view` REST fallback (forge.ts:154) is only reached when GitHub App is NOT configured.

**Gap in deacon coverage:** the existing `needsReviewDispatch` mechanism (review-dispatch-decision.ts) only fires when `reviewRequestedAt` IS set. No patrol detects "PR open on GitHub + `reviewStatus=pending` + `reviewRequestedAt` empty" and writes the missing intent.

## Requirements

- **FR-1** — When `createReviewArtifactsForIssue` throws AND the feature branch already has an open PR on GitHub (detectable via `gh pr list --head <branch> --state open`), `pan done` MUST NOT exit; it MUST record the PR URL, proceed to write the completed marker and `reviewRequestedAt`, and attempt the review dispatch.
- **FR-2** — A deacon patrol MUST detect "PR open on GitHub + `reviewStatus === 'pending'` + `reviewRequestedAt` empty" and set `reviewRequestedAt` to trigger the existing `needsReviewDispatch` auto-dispatch path.
- **FR-3** — The patrol's durable tombstone (`panDoneRecoveredAt`) MUST live in the per-issue record's `pipeline` block (via `writeIssueRecordSync`/`updateIssueRecordForReviewStatusSync`), NOT in review_status fields (which `clearReviewStatus` can clear from SQLite, and which `setReviewStatusSync` can overwrite). Once written, subsequent patrol cycles skip the issue. This is the PAN-2367 lesson: per-issue record fields survive `clearReviewStatus`, which only deletes the SQLite row.
- **FR-4** — `pan done` re-runs (after feedback) MUST clear `panDoneRecoveredAt` from the per-issue record so the patrol can re-fire if the new run also fails mid-flight.
- **FR-5** — Regression test: simulate a `createReviewArtifactsForIssue` failure (mock throws) + an open PR found by the fallback check → `pan done` still writes `reviewRequestedAt` and the completed marker. And: patrol detects `reviewStatus=pending + reviewRequestedAt empty + open PR` → writes `reviewRequestedAt` and tombstone; second patrol cycle skips (tombstone honored).
- **NFR-1** — No new explicit `any`; async only (no `execSync`); no new files ≥1,000 lines.
- **NFR-2** — The patrol's GitHub PR check MUST use the REST CLI (`gh pr list`) not GraphQL, to remain functional under GraphQL rate limits. One API call per stuck issue per cycle is acceptable.

### W3 — Deacon: `checkOrphanedCompletions` patrol (FR-2, FR-3)

**File:** `src/lib/cloister/deacon.ts`

**New function** (add alongside `checkMissingReviewStatuses`, which is a comparable patrol):
```ts
/**
 * PAN-2207: detect issues where a PR exists on GitHub but the review pipeline
 * was never dispatched (pan done failed mid-flight after PR creation). Writes
 * reviewRequestedAt to trigger the existing needsReviewDispatch auto-dispatch.
 * Tombstone (`panDoneRecoveredAt` in per-issue record) prevents re-firing.
 */
export async function checkOrphanedCompletions(): Promise<string[]> {
  const actions: string[] = [];
  try {
    const { loadReviewStatuses, setReviewStatusSync } = await import('../review-status.js');
    const { needsReviewDispatch } = await import('../review-dispatch-decision.js');
    const statuses = loadReviewStatuses();
    for (const [issueId, status] of Object.entries(statuses)) {
      // Only issues that are pending + have never had a review request
      if (status.reviewStatus !== 'pending') continue;
      if (status.mergeStatus === 'merged') continue;
      if (needsReviewDispatch(status)) continue; // reviewRequestedAt already set
      // Tombstone check — per-issue record (durable, survives clearReviewStatus)
      const { resolveProjectFromIssueSync } = await import('../projects.js');
      const { readIssueRecordSync } = await import('../pan-dir/record.js');
      const resolved = resolveProjectFromIssueSync(issueId);
      if (!resolved) continue;
      const record = readIssueRecordSync(resolved, issueId);
      if (record?.pipeline?.panDoneRecoveredAt) continue;
      // REST-only check: does the feature branch have an open PR?
      const issueLower = issueId.toLowerCase();
      const branchName = `feature/${issueLower}`;
      let prUrl: string | null = null;
      try {
        const { execAsync: execA } = await import('../exec-async.js');
        const { stdout } = await execA(
          `gh pr list --head ${branchName} --state open --json url --jq '.[0].url' 2>/dev/null || true`,
          { encoding: 'utf-8', timeout: 15000 }
        );
        prUrl = stdout.trim() || null;
      } catch { continue; /* non-fatal — skip this issue this cycle */ }
      if (!prUrl) continue;
      // Recovery: write reviewRequestedAt (triggers needsReviewDispatch on next read)
      // and the durable tombstone (prevents loop).
      const now = new Date().toISOString();
      setReviewStatusSync(issueId, { reviewRequestedAt: now, prUrl });
      const { writeIssueRecordSync } = await import('../pan-dir/record.js');
      const freshRecord = readIssueRecordSync(resolved, issueId) ?? buildDefaultRecord(issueId);
      writeIssueRecordSync(resolved, issueId, {
        ...freshRecord,
        pipeline: { ...freshRecord.pipeline, panDoneRecoveredAt: now },
      });
      const msg = `checkOrphanedCompletions: recovered ${issueId} — PR ${prUrl} was open but reviewRequestedAt was missing; set now, tombstone written`;
      actions.push(msg);
      logDeaconEventSync(msg);
      console.log(`[deacon] ${msg}`);
    }
  } catch (err: any) {
    console.warn('[deacon] checkOrphanedCompletions error:', err.message);
  }
  return actions;
}
```
