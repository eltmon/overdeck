## Glossary

- **Panel** — the Settings → Tiered Execution section: `src/dashboard/frontend/src/components/Settings/sections/TieredExecutionSection.tsx` (851 lines today), mounted at `src/dashboard/frontend/src/components/Settings/SettingsPage.tsx:549`, saving through the `useAutosavePipeline` hook (`SettingsPage.tsx:41,254`) like every other section.
- **Config shape** — `TieredExecutionConfig` in `src/dashboard/frontend/src/components/Settings/types.ts:162-194`: `enabled`, `tiers` (record keyed by tier name → `{ model, harness, difficulties, distribution? }`), `supervisor`, `by_kind`, `feed`, `escalation`, `compaction_reroute`, `replay_threshold`. Server-side validation is `validateTieredExecutionSettings` and save-shaping is `tieredExecutionConfigForSave`, both in `src/lib/settings-api-tiered-execution.ts` (wired at `src/lib/settings-api.ts:950,1242-1244`). **Neither changes in this issue.**
- **Crew** — the new UI-only concept: one staffing definition (a single model, or a weighted **mix**) plus the set of difficulties assigned to it. A crew serializes as exactly one entry in `tiers`. Crews are never named by the operator; they are **labeled** by composition ("Kimi K2.7 Code", "4-model mix").
- **Board** — the five-column difficulty surface (trivial → expert) where each difficulty selects its crew. Assignment is a total function, so difficulty-coverage errors are unrepresentable in the UI.
- **Derived tier name** — the auto-generated `tiers` key on save: the crew's owned difficulties in ladder order joined with `-` (see D-3).
- **Representative entry** — existing PAN-2391 rule: when a tier has a `distribution`, its top-level `model`/`harness` mirror the max-weight entry so save/load round-trips are idempotent (today's `representativeOf`, `TieredExecutionSection.tsx:279-283`). Preserved as-is.
- **Disclosure** — a collapsed row with a one-line plain-language summary of its current resolution that expands to the full controls (Supervisor, Commit feed, Escalation, Session replay, YAML preview).
- **Never-frontier default** — `DEFAULT_MODEL = 'claude-haiku-4-5'` and `DEFAULT_SUPERVISOR_MODEL = 'claude-sonnet-5'` exported from the component (`TieredExecutionSection.tsx:27-33`), locked by `__tests__/TieredExecutionSection.test.tsx:379-383` (2026-07-05 incident rule). Both exports and the test must survive.

## Decisions (made here, not by the executor)

- **D-1 — Crews are presentation-only.** The stored schema, the loader (`src/lib/agents/tier-table.ts`), server validation, and runtime resolution are untouched. This is a rebuild of one React component plus a pure mapping module.
- **D-2 — Import groups identical staffing into one crew.** On load, tiers whose staffing is identical (single: same `model` + `harness`; mix: same entries after sorting by model id — compare `{model, harness, weight}` triples) become ONE crew owning the union of their difficulties. Operator-approved consequence, demonstrated in the mockup: this project's `tier-2`/`tier-3` (identical mixes) import as one crew; the next save writes the merged form. Runtime behavior is identical.
- **D-3 — Tier names on save are always derived.** Name = the crew's owned difficulties in ladder order (`trivial, simple, medium, complex, expert`) joined with `-`: `trivial-simple`, `medium`, `medium-complex-expert`. Unambiguous for non-contiguous ownership too (`trivial-expert` can only mean {trivial, expert} because a span would include the middle difficulties by name). `by_kind` values are rewritten to the same derived names in the same save so the file stays internally consistent — tier names are referenced nowhere outside the `tiered_execution` block (verified: `flounder_budget_minutes` is difficulty-keyed; `tierOverrides` in continue state stores effective difficulties; per-bead overrides use `metadata.model`). Hand-authored tier names in a hand-edited YAML are honored on read and replaced by derived names on the next UI save — documented, not silently.
- **D-4 — Harness stays concrete in the file; "auto" is a form state.** Every stored `harness` remains an explicit `Harness` value (type unchanged; validator unchanged). The form shows "auto (<provider default>)" when the stored harness equals the model's provider default, and the explicit harness otherwise. Picking "auto" writes the provider default at save time. A stored harness that contradicts the provider default renders the amber chip `⚠ harness overrides provider default — PAN-1865`. Provider-default resolution: use the `provider_harnesses` field if present on the loaded settings (**implementation checkpoint:** confirm the exact field name on `SettingsConfig` in `types.ts` at implementation time; **fallback** if absent from the settings payload: a local constant table mirroring `getBuiltInDefaultHarness` in `src/lib/providers.ts` — anthropic→claude-code, openai→codex, everything else→ohmypi — with a comment naming the source).
- **D-5 — Cost chips come from the catalog.** `costPer1MTokens` on `MODELS_BY_PROVIDER` entries (`src/dashboard/frontend/src/components/Settings/modelCatalog.ts:14`). Single-model crew: that model's cost. Mix: weight-blended average over entries that have a cost; if no entry has one, render `—` (never `$0`).
- **D-6 — Validation split.** Difficulty coverage errors disappear from the client (unrepresentable). Remaining client checks render inline at the offending control AND flip the header state chip red: mix weights ≠ 100 ("Invalid — a mix doesn't total 100%"), and the existing server `saveErrorMessage` routing (today's `serverTieredError` derivation, `TieredExecutionSection.tsx:182-195`) is kept for everything the server rejects. The server validator remains the backstop for hand-edited YAML.
- **D-7 — `compaction_reroute` gets its control** in the Session replay disclosure. The type already exists (`types.ts:192`); the options render as plain-language sentences (mockup copy binding: "bring back the same session as before" / "re-plan remaining work; retire crews no longer needed") with a "new — in config, missing from today's UI" tag removed at implementation (that tag is mockup annotation only).
- **D-8 — Two crews may be identical while editing.** No live dedup during editing; identical crews owning different difficulties serialize as two tiers and merge on next load per D-2. Acceptable; do not add merge-on-save logic.
- **D-9 — Copy is binding.** Section names ("The crews", "Kind overrides", "Advanced", "Standing reviewer"), summaries, helper sentences, difficulty subtitles ("typo-level fixes" … "judgment calls"), and error phrasing come from the mockup verbatim. The "Preview a state" scenario buttons are mockup-only pedagogy — do NOT ship them.
- **D-10 — The YAML preview ships.** The "What this writes to config.yaml" disclosure renders the exact `tiered_execution` object the next save would send, formatted by a small local serializer in the crews module (~30 lines; no YAML dependency). Its summary line lists the derived tier names.

## Requirements

### Functional

- **FR-1** A pure module maps `TieredExecutionConfig` ⇄ crews: `importCrews(config)` → `{ crews, assign, rest }` (grouping per D-2) and `serializeCrews(crews, assign, rest)` → `TieredExecutionConfig` (derived names per D-3, representative entries preserved, `by_kind` rewritten). Round-trip is semantics-preserving.
- **FR-2** The board renders five difficulty columns, each with a crew select (existing crews by label + "+ new crew…"), staffing summary, cost, and a crew-colored top border; changing a select reassigns instantly. "+ new crew" creates a Haiku 4.5 single-model crew (never-frontier default) and opens its editor.
- **FR-3** The crews list renders one expandable row per crew: color dot, composition label, mix summary, PAN-1865 warning chip when applicable (D-4), owned difficulties ("handles trivial · simple" / "handles nothing — assign it on the board or remove it"), cost chip. Expanded: single-model editor (model + harness-with-auto) or mix editor (weighted bar, per-entry model/harness/weight/remove, running total with red ≠100 state, Add model), plus "Use one model"/"Use a weighted mix" toggle (representative rule on collapse) and "Remove crew" (blocked with an explanatory message while the crew owns difficulties).
- **FR-4** Supervisor renders as a disclosure whose collapsed summary is a sentence ("reviews every commit · Claude Sonnet 5 · owns inspection"); expanded controls: model, harness, subscribe (plain-language option labels per mockup), owns-inspection switch. Existing requirement semantics unchanged (supervisor required when tiers exist — server-enforced).
- **FR-5** Kind overrides are overrides-only: a default line ("All kinds follow difficulty routing." / "N kinds overridden; …"), chips only for actual overrides with an ✕ to clear, and kind + crew pickers with "Add override". Serialization writes `by_kind` with derived tier names.
- **FR-6** Commit feed, Escalation, and Session replay render as disclosures with resolution summaries (mockup copy) and all existing fields; Session replay adds the `compaction_reroute` select (D-7).
- **FR-7** The "What this writes to config.yaml" disclosure renders the outgoing config per D-10.
- **FR-8** Header row: title, plain-language explainer (including the per-issue override chain sentence), state chip (Off / On · valid / Invalid — <reason>), enable switch. Chip red states cover client mix-total errors and server save errors (D-6).
- **FR-9** A no-loss test gates the swap: every control in the inventory below must be present and functional in the new panel before the old render is deleted.
- **FR-10** Docs updated (work item 6).

### Non-functional

- **NFR-1** No runtime/schema/server changes: `settings-api-tiered-execution.ts`, `tier-table.ts`, and all resolution paths byte-identical.
- **NFR-2** Component contract preserved: same props (`formData`, `saveErrorMessage`, `saveStatus`, `onSettingsChange` — `TieredExecutionSection.tsx:7-12`), same `DEFAULT_MODEL`/`DEFAULT_SUPERVISOR_MODEL` exports, mounted unchanged from `SettingsPage.tsx:549`.
- **NFR-3** Style guide conformance: DM Sans / `font-medium` only, semantic tokens (no hex, no `slate-*`, no pills), amber strictly = human decision (the PAN-1865 chip), cyan strictly = money (cost chips), crew colors are structural identity only.
- **NFR-4** No new dependencies (no YAML lib — D-10).
- **NFR-5** Disclosure and crew-row headers are keyboard-operable (Enter/Space toggle, visible focus state).
