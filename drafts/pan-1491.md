# PAN-1491 — Metric-aware flywheel prioritization

**Issue:** [PAN-1491](https://github.com/eltmon/overdeck/issues/1491) —
feat(flywheel): metric-aware prioritization — weight substrate-bug suggestions by which v1.0 criterion they affect

**Depends on:** #1487 (substrate-bug provenance + telemetry) — **MERGED** (PR #1505, 2026-05-25). Data foundation exists.

## Glossary

- **v1.0 readiness criteria** — the seven metrics (`c1_bugRate` … `c7_flake`) that gate declaring Overdeck v1.0-ready. Defined in `vision.mdx:142-157`; typed as `FlywheelStatsCriteria` in `packages/contracts/src/flywheel-stats.ts`. Each is AND-gated and equally weighted (no per-criterion weight constants exist).
- **Substrate bug** — a Overdeck-infrastructure bug the flywheel files during a run (GitHub issue, `label:substrate`), tracked in the `flywheel_substrate_bugs` SQLite table.
- **Metric drift** — how far a criterion's current value is from its target (e.g. bug-rate 3% vs target <2%).
- **Weight** — a deterministic per-substrate-bug number derived from which criteria the bug affects and how far those criteria are drifting. Used to break ties among P1 substrate suggestions.
- **Suggestion** — a `FlywheelSuggestion` (`packages/contracts/src/flywheel.ts:178`) the flywheel orchestrator emits each tick via `POST /api/flywheel/status`. Suggestions are **authored by the LLM orchestrator**, not computed server-side.
- **Affected-criterion declaration** — a `Flywheel-Affects-Criterion: 1,5` trailer in the bug's issue body (extends #1487's trailer convention) declaring which criteria the bug counts against.

## Problem

The flywheel ranks suggestions by P-level + age only (`roles/flywheel.md:225-233`). All substrate bugs bucket the same; there is no signal about which bug is closest to a v1.0 criterion threshold. #1487 shipped the telemetry that knows exactly which criterion is under threat; nothing consumes it for ranking. Commit `74403b36a6` landed substrate-first *bucketing* and explicitly left *"deterministic label-weighting in code"* to this issue.

## Proposal

Add a deterministic **metric-drift weight** for substrate bugs, consumed as a ranking signal by the LLM orchestrator and surfaced in the UI:

1. Substrate bugs declare affected criteria via a `Flywheel-Affects-Criterion: N,M` body trailer (primary) or `affects-criterion-N` labels (fallback, parse-only — no label infrastructure created).
2. A pure lib computes `weight` + human `weightReason` from the affected criteria and the live 30-day stats snapshot (`computeFlywheelStats`).
3. A shared lib service joins substrate bugs + stats + weights into a sorted table. Both a new `GET /api/flywheel/substrate-bug-weights` route (dashboard) and a new sandbox-safe `pan flywheel weights` CLI (orchestrator) call it.
4. The flywheel orchestrator calls `pan flywheel weights --json` each tick and writes `weight`/`weightReason` onto the substrate suggestions it emits (contract extended with two optional fields).
5. The dashboard renders a weight badge + reason and applies weight as a **secondary sort within an equal priority tier**.

### Weight formula (decided)

For each affected criterion `c` of a bug, with live stats `stats.criteria[c]`:

```
STATUS_MULT   = { red: 3, yellow: 2, green: 1, insufficient_data: 0 }
STATUS_FLOOR  = { red: 1, yellow: 0.5, green: 0, insufficient_data: 0 }
normalizedDistance(c):
  direction 'lower'  (value should be below target): max(0, (value - target) / target)
  direction 'higher' (value should be above target): max(0, (target - value) / target)
  direction 'zero'   (target is 0, e.g. c2 P0 count):  value                    // raw count
  compound value/target (objects): read the numeric sub-field named in CRITERION_META
                                   (c4 → medianMs, c6 → ratio); if absent/non-numeric ⇒ 0
contribution(c) = STATUS_MULT[status] * (STATUS_FLOOR[status] + normalizedDistance(c))
weight          = Σ contribution(c) over affected criteria
```

`STATUS_FLOOR` guarantees a red criterion outranks a yellow/green even when a compound value can't be cleanly normalized (the drift term still differentiates within a status). `insufficient_data` criteria contribute 0 — never penalize a bug before telemetry has signal (≥3 completed runs).

`weightReason` describes the highest-contributing criterion, e.g. `criterion 1 (substrate-bug discovery rate) red at 3.2% vs target <2%`.

### CRITERION_META (decided)

| # | stats key | direction | compound sub-field |
|---|-----------|-----------|--------------------|
| 1 | c1_bugRate | lower | — |
| 2 | c2_p0Bugs | zero | — |
| 3 | c3_passRate | higher | — |
| 4 | c4_mttr | lower | medianMs |
| 5 | c5_intervention | lower | — |
| 6 | c6_timeConsistency | lower | ratio |
| 7 | c7_flake | lower | — |

**Implementation checkpoint:** the exact numeric sub-field names for c4/c6 must be confirmed by reading `computeMttrCriterion` / `computeCriterion6Bucket` in `src/dashboard/server/services/flywheel-telemetry.ts` (verified at planning time: c4 `value:{medianMs,p95Ms}`, c6 bucket `{medianMs,p95Ms,ratio}`). Fallback if a field is absent or bucketed such that no scalar is extractable: that criterion's `normalizedDistance` is 0 (status floor still applies).

## Requirements

- **FR-1** `FlywheelSuggestion` carries optional `weight: number` and `weightReason: string` (contract + Effect Schema); contracts rebuilt.
- **FR-2** `parseAffectedCriteria(body, labels) → number[]` extracts declared criteria from a `Flywheel-Affects-Criterion:` trailer and/or `affects-criterion-N` labels; dedups, sorts, keeps only 1–7.
- **FR-3** `computeSubstrateBugWeight(criteria, stats) → { weight, reason }` implements the formula above, including compound and `insufficient_data` handling.
- **FR-4** A lib service `listSubstrateBugWeights(window) → WeightedSubstrateBug[]` joins in-window substrate bugs + stats + weights, sorted by weight desc.
- **FR-5** `GET /api/flywheel/substrate-bug-weights?window=30d` returns the weighted table (dashboard-facing).
- **FR-6** `pan flywheel weights [--issue <id>] [--window <dur>] [--json]` prints the weighted table, reading the lib service **directly (no HTTP — sandbox-safe)**.
- **FR-7** `roles/flywheel.md` + `docs/flywheel-brief.md` instruct the orchestrator to call `pan flywheel weights --json` each tick and set `weight`/`weightReason` on emitted substrate suggestions, with a worked example.
- **FR-8** Substrate-bug filing guidance teaches agents to add `Flywheel-Affects-Criterion:` when the affected criterion is known.
- **FR-9** `FlywheelStatusDetails.tsx` renders a weight badge + reason and sorts by weight desc within an equal priority tier.
- **FR-10** `docs/FLYWHEEL.md` + `vision.mdx` describe metric-aware weighting.
- **NFR-1** Weighting is a **default sort only**, never a hard filter — operators can still inject any issue manually; operator-filed issues keep their always-on-top behavior.
- **NFR-2** The parser and weight fn are pure and unit-tested; no network or DB access inside them.
- **NFR-3** The CLI path performs no HTTP (works inside the flywheel sandbox), matching the `flywheel merge-blockers` direct-SQLite pattern.

## Planning Q&A

Auto mode (`pan plan --auto`) — no interactive questions. All decisions recorded in `plan.autoDecisions[]`:

1. **Mapping mechanism** → `Flywheel-Affects-Criterion: N,M` trailer (primary) + `affects-criterion-N` labels (parse-only fallback). Reuses #1487's trailer convention and `substrate-bug-poller.ts` parsing style; no GitHub label infrastructure required.
2. **Weight formula** → status-multiplier × (status-floor + normalized drift), summed over affected criteria; robust to compound/un-normalizable criteria. Improves on the earlier raw-distance formula by guaranteeing red > yellow > green ordering.
3. **Criterion weights** → uniform (all seven equally weighted), because no per-criterion weight constants exist in telemetry and the vision defines them as an equal AND-gate.
4. **Tier interaction** → priority tier is primary sort; weight is a secondary sort *within* an equal tier. Never overrides P0/urgent; never a filter.
5. **CLI transport** → direct lib call, no HTTP, for sandbox safety (matches `flywheel merge-blockers`).
6. **insufficient_data** → contributes 0 (telemetry needs ≥3 completed runs).

## NonGoals

- Non-substrate (user-pipeline) bug prioritization — those keep normal P-level ranking.
- Operator-filed / operator-injected issues always-on-top — preserved; weighting is a default sort, not a filter.
- Changing how the seven criteria are computed or their targets — #1487 owns that.
- Introducing per-criterion weight constants or altering the v1.0 AND-gate definition.
- Historical backfill of `Flywheel-Affects-Criterion` on pre-existing substrate bugs.
- Creating `affects-criterion-N` GitHub labels as infrastructure — labels are parse-only if present; the trailer is the primary path.
