# PAN-2045 — perf(test): frontend vitest (jsdom) is the test-gate bottleneck — move to happy-dom / tune pool

**Issue:** https://github.com/eltmon/overdeck/issues/2045
**Related:** PAN-1918 (full frontend suite runs in no CI path; IssueMissionControl open-handle hang), PAN-1989 (where the timings were measured)
**Author:** planning agent (claude-fable-5), 2026-07-16, auto mode

## Glossary

- **Frontend suite** — the vitest project rooted at `src/dashboard/frontend/` (214 `*.test.ts(x)` files at planning time), configured by `src/dashboard/frontend/vitest.config.ts`, currently `environment: 'jsdom'`.
- **Root suite** — the repo-root vitest project (~715 files, ~72 s).
- **Test gate** — the verification `quality_gates.test` command in `~/.overdeck/projects.yaml`, which runs root and frontend `vitest run --changed {{CHANGED_BASE}}` in parallel; gate wall-clock is `max(root, frontend)`.
- **happy-dom** — an alternative DOM implementation for vitest, typically 2–3× faster than jsdom for React component tests; behavior diverges from jsdom in known ways.
- **Isolation (`isolate`)** — vitest's per-test-file environment isolation. `isolate: false` shares module registry/state across files within a worker. Default is `true`.
- **Pool** — vitest's worker strategy. Vitest 4 defaults to `'forks'` (child processes); `'threads'` uses worker threads, which spawn faster.
- **Open-handle hang** — a test file whose assertions pass but which leaves a live timer/socket, so the worker never exits and the suite never completes.
- **Divergence class** — a category of test failure caused by happy-dom behaving differently from jsdom (not by a product bug).

## Problem

The frontend suite takes ~5 min per full run vs ~72 s for the root suite (measured in PAN-1989), so it dominates the test gate and every work agent's `pan done`/verify cycle. Root cause: jsdom instantiates a fresh DOM per test file × ~200+ files. (The canvas `getContext` error-spam was noise, already silenced by the stub in `src/dashboard/frontend/src/canvas-setup.ts`.)

Two prior facts constrain the approach:

1. **The 2026-06-25 strike self-aborted.** A one-shot flip surfaced multiple happy-dom divergence classes — style-serialization differences, accessible-name differences, missing `window.prompt`, config/render mismatches — and `isolate: false` under jsdom caused *widespread cross-test state bleed*. The operator's comment routes this through the normal pipeline as a staged migration with focused fixes and full-suite verification.
2. **No full-suite run currently completes** (PAN-1918): `src/dashboard/frontend/src/components/Stage/cockpit/IssueMissionControl.test.tsx` creates `new QueryClient({...})` (line 118) inside its render helper with no teardown; react-query GC timers keep the worker alive. Until that is fixed, neither a baseline measurement nor suite-wide green can be demonstrated.

## Decisions (made in this document)

- **D1 — happy-dom is the primary lever**, executed as a staged migration with one plan item per divergence class. Not a one-shot flip.
- **D2 — `isolate: false` is rejected** for this issue (NonGoal). Empirically caused widespread state bleed. Isolation stays on in every committed config.
- **D3 — the IssueMissionControl open-handle fix is in scope** (prerequisite for measurement and verification); CI wiring of the full suite stays with PAN-1918.
- **D4 — `pool: 'threads'` is trialed unconditionally** after the suite is green under happy-dom, with a mechanical revert rule: any failure that appears only under threads → revert to default forks and record why in `docs/TESTING.md`.
- **D5 — measure before switching**: the jsdom baseline wall-clock is recorded in `docs/TESTING.md` before the environment changes.
- **D6 — target is <120 s** full-suite wall-clock on this hardware ("under ~2 min" from the issue). If both levers miss it, the tuning item is marked blocked and the shortfall surfaced with the measured number — never isolation-weakening or test deletion to close the gap.

## Intersecting repo rules (restated for the executor)

- **Fake timers rule:** any retry/backoff/delay test uses `vi.useFakeTimers()` + `advanceTimersByTimeAsync`; never real `setTimeout` waits; never mask leaks with `maxForks: 1` or heap-size bumps.
- **No bandaids:** in-suite-only failures are fixed at the leaking test's cleanup, not dodged with isolation or ordering tricks; failing behavior is understood before it's changed.
- **Per-item durability:** commit exactly one vBRIEF item at a time and push the feature branch before `pan task done`.
- **Workspace `bun install`, never symlink node_modules by hand** — the config's `ensureFrontendNodeModules()` shim does the frontend-level linking, driven by the frontend `package.json`.
