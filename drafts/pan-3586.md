## Glossary

Define these before use; the executing agent should not have to infer them.

| Term | Meaning |
| --- | --- |
| **Push-event run** | A GitHub Actions workflow run whose `event` is `push`. Created by GitHub when a `push` webhook is processed for a ref matching a workflow's `on.push.branches`. |
| **Run creation** | GitHub's act of materializing a workflow run from a received event. Distinct from *job execution*: a run can exist with delayed or failing jobs, and an event can exist with **no** run created at all. |
| **Check-run** | A per-job status object attached to a commit SHA, readable at `GET /repos/{owner}/{repo}/commits/{sha}/check-runs`. Row 6 of the Definition of Done reads these. |
| **DoD row 6 (`main-verify`)** | The Definition-of-Done row asserting a merged commit was exercised by CI on `main`. Implemented in `src/lib/lifecycle/dod-gate.ts` as `checkMainVerifyRow()`. |
| **Required checks** | The named check-runs row 6 demands. Resolved from branch protection, else `DEFAULT_MAIN_VERIFY_REQUIRED_CHECKS` = `['test', 'lint', 'build (22)', 'guard']` (`src/lib/lifecycle/dod-gate.ts:138`). |
| **Promote door** | `promoteGeneration()` in `src/lib/cloister/uat-promote.ts`, which merges a UAT batch branch into `main` and pushes with `git push origin HEAD:main` from a throwaway worktree. |
| **Merge door** | The dashboard/Deacon PR-merge path in `src/dashboard/server/routes/workspaces/merge-ops.ts`, which lands a reviewed PR through `getForgeAdapter(...).mergeReviewArtifact(...)`. |
| **Landing verification** | New behavior added by this issue: after a commit lands on `main`, confirm GitHub actually created at least one workflow run for that SHA, and escalate durably when it did not. |
| **Needs-you trip** | Overdeck's durable operator escalation. `recordDeadEndNeedsYou()` (`src/lib/cloister/dead-end-trip.ts:4`) writes a `recoveryTrips` entry into the per-issue permanent record through the record write door and emits the needs-you signal on the first trip (threshold 1). |
| **File-size ratchet** | `scripts/lint-file-size.sh`. Compares each working-tree file against its line count on `origin/main`; growth requires an audited row in `scripts/file-size-allowlist.txt` shaped `<lines> <path> # <ISSUE-REF>`. Ceiling for **new** files is 1000 lines. |

## Problem

### What was observed

Between 2026-08-06T14:58:51Z and the time of writing, **zero `push`-event workflow runs were created for `eltmon/overdeck`**, across all three push-triggered workflows (`CI`, `state-plane-branches`, `no-planning-on-main`). Six commits landed on `main` in that window and none carries CI evidence. `origin/main`'s tip `cc366a3a97` has exactly one check-run: `Mintlify Deployment = skipped`.

Meanwhile `pull_request`-event runs were still being created, intermittently — a pair completed on `86ac1506` at 20:36:28Z.

### Root cause — established, not assumed

The issue body hypothesized that the UAT promote path pushed with an unusual credential and that GitHub therefore suppressed the `push` event. **That hypothesis is disproven by direct evidence**, and so is the follow-up billing hypothesis. The investigation performed during this planning session found:

1. **The pusher identity is identical across working and non-working pushes.** The repository events feed reports `actor=overdeck-agent[bot]` for the push of `d921b8cec5` (21:02:48Z, no run created) and `cc366a3a97` (21:30:44Z, no run created) — the same actor as the push of `e18aa3f16a` at 14:58:51Z, which *did* create three runs. Command used:

   ```bash
   gh api "repos/eltmon/overdeck/events?per_page=100" \
     --jq '.[] | select(.type=="PushEvent") | select(.payload.ref=="refs/heads/main") |
           "\(.created_at)  actor=\(.actor.login)  head=\(.payload.head[0:10])"'
   ```

2. **The workflow definitions are byte-identical** between the last triggering commit and the current tip: `git diff --stat e18aa3f16a origin/main -- .github/` is empty, and all seven workflow files are present at the tip.

3. **The repository is public**, so Actions minutes are free and unmetered — `gh api repos/eltmon/overdeck --jq .visibility` returns `"public"`. A spending limit cannot be the cause. Actions permissions read `{"enabled":true,"allowed_actions":"all"}`.

4. **Run volume is unremarkable** — 84 runs created today, 93 yesterday. No anti-abuse throttle is plausible at that scale.

5. **GitHub is running a Critical Actions incident that describes exactly this symptom.** Incident `qcvjkzcs7j74` ("Incident with Actions"), opened 2026-08-06T15:22:49Z, still `investigating`. Its 20:34:17Z update states: *"Webhook triggers throttled to 15% processing; approximately 65% of queued jobs succeeding."* Permalink: <https://stspg.io/rcz3fcm83sff>.

**Conclusion: the cause is a GitHub platform incident, not Overdeck code, not the promote path's credential, and not repository configuration.** Webhook triggers are throttled to 15%, so most `push` and `pull_request` events never become runs. The 14:58:51Z cutoff sits just before the incident was publicly posted; the intermittent `pull_request` successes are the ~15% that got through.

This is why the "what to fix" item 1 in the issue body ("determine why the push raised no workflow event") produces **no code change** in this plan. It is answered, and the answer is recorded here, in `continue.json`, and in `plan.autoDecisions[]`.

### Why this still needs work

Three consequences survive the incident and are what this issue actually delivers:

**There is no way to verify an un-CI'd `main` tip.** Every push-triggered workflow has `on: push` as its only non-PR trigger. No run exists on `cc366a3a97` to re-run, and the only way to produce one is a fresh push — an artificial commit. That is the acute blocker: DoD row 6 now correctly reports `missing required checks on <sha>: test, lint, build (22), guard` (PAN-3589 landed as `d921b8cec5`), so **every close-out is blocked** until CI evidence exists on `main`.

**Both landing doors report success while leaving `main` unverified.** `promoteGeneration()` returns success the moment `git push origin HEAD:main` exits 0, and the merge door returns success the moment `mergeReviewArtifact` resolves. Neither asks whether GitHub did anything with the event. A promotion that silently leaves `main` unverified is reported as a clean promotion, and the operator learns about it hours later from a blocked close-out.

**The failure mode is cause-agnostic and will recur.** A platform incident today, a credential regression tomorrow, a workflow-file mistake next month — all present identically as "the commit landed and no run was created". Landing verification catches all of them; a root-cause fix for the incident catches none of them, because there is no repo-side root cause to fix.

## Proposal

Three changes, in the order they matter:

1. **A recovery door.** Add `workflow_dispatch` to the two workflows that own row 6's required checks, so an unverified `main` tip can be verified on demand with `gh workflow run`. This unblocks close-out today and every future occurrence.
2. **Landing verification at both doors.** After a commit lands on `main`, poll GitHub for a workflow run on that SHA within a bounded window. When none appears, record a durable needs-you trip naming the condition, the SHA, the recovery commands, and githubstatus.com. Never roll back — the merge already landed.
3. **A runbook.** Document the unverified-`main` condition and its recovery in the two docs that own the surfaces.

### Decisions made in this document

The executing agent makes none of these calls; they are decided here.

**D1 — `workflow_dispatch` goes on `ci.yml` *and* `state-plane-branches.yml`, not `ci.yml` alone.** Row 6's required set is `test, lint, build (22), guard`. Verified job ownership:

| Required check | Workflow | Line |
| --- | --- | --- |
| `build (22)` | `.github/workflows/ci.yml` | `build:` at :25, matrix `node-version: [22]` at :34 |
| `lint` | `.github/workflows/ci.yml` | `lint:` at :74 |
| `test` | `.github/workflows/ci.yml` | `test:` at :123 |
| `guard` | `.github/workflows/state-plane-branches.yml` | `guard:` at :13 |

Dispatching `ci.yml` alone yields three of four required checks and row 6 stays MISS on `guard` forever. Both workflows get the trigger.

**D2 — `state-plane-branches.yml` needs an explicit range under dispatch; the naive addition is a silent no-op.** Its guard step branches on `github.event_name`, and the non-`pull_request` branch reads `before="${{ github.event.before }}"` (`.github/workflows/state-plane-branches.yml:26`). Under `workflow_dispatch` that context is absent, so `before` is empty and `range` becomes `"..${GITHUB_SHA}"`. Git resolves a leading-empty range as `HEAD..<sha>`, and since the checkout *is* at that SHA, `git diff --name-only "$range"` (`scripts/guard-state-plane-branches.sh:31`) returns nothing — **the guard passes having inspected zero files**. A green `guard` check that inspected nothing is worse than no check, because row 6 would accept it.

The fix: add a `since` input defaulting to empty, and resolve `before` under dispatch as `inputs.since` when set, else `${GITHUB_SHA}~1`. That makes a bare dispatch verify the tip commit (matching single-commit push semantics), while letting an operator pass the last CI-verified SHA to cover a whole unverified window.

**D3 — `ci.yml` needs no context fix.** Its only event-context read is `sha="${{ github.event.pull_request.head.sha || github.sha }}"` (`.github/workflows/ci.yml:147`), which falls back to `github.sha` when `pull_request` context is absent. That is already the dispatch-correct value.

**D4 — the durable marker is a needs-you trip, not a new store or column.** Overdeck's single-source-of-truth rule forbids adding a parallel store. `recordDeadEndNeedsYou(issueId, recoveryPath, generation, message)` already writes through the record write door (`updateIssueRecordForWorkspace`) into the per-issue permanent record's `recoveryTrips`, and its threshold of 1 means the first trip emits the operator signal immediately. Use `recoveryPath: 'main-ci-run-missing'` and `generation: <landed sha>`, so re-running the same door for the same SHA de-duplicates instead of nagging.

**D5 — landing verification never fails the operation.** The push or merge has already landed and `main` is never rewound (the codebase states this explicitly at `src/lib/cloister/uat-promote.ts:261-278`). Verification observes and escalates; it must not turn a successful promotion into `success: false`, and any error inside verification is swallowed and logged rather than propagated.

**D6 — poll `actions/runs?head_sha=<full-sha>`, not check-runs.** Empirically verified this session: `GET /repos/eltmon/overdeck/actions/runs?head_sha=<40-char sha>` returns `total_count: 3` for the last triggering commit and `total_count: 0` for the current unverified tip. It detects **run creation**, which is the thing that failed, and it does so before any job starts — check-runs would not appear until jobs begin, conflating "no run created" with "jobs still queued". The filter requires the **full 40-character SHA**; an abbreviated SHA returns 0.

**D7 — bounded window: 120 seconds, 6 attempts, fixed 20-second interval.** GitHub normally creates runs within seconds. Two minutes is generous enough to avoid false alarms and short enough that it does not stall the promote flow; six API calls per landing is negligible against the 5000/hr installation budget.

## Requirements

### Functional

- **FR-1** — `.github/workflows/ci.yml` accepts `workflow_dispatch`, so `gh workflow run ci.yml --ref main` creates a run producing the `test`, `lint`, and `build (22)` check-runs on `main`'s tip.
- **FR-2** — `.github/workflows/state-plane-branches.yml` accepts `workflow_dispatch` with an optional `since` input, producing the `guard` check-run.
- **FR-3** — Under `workflow_dispatch`, `state-plane-branches.yml` computes a non-empty commit range: `inputs.since` when provided, otherwise the dispatched SHA's parent. It never passes a range whose left side is empty.
- **FR-4** — A landing-verification helper reports whether GitHub created at least one workflow run for a given 40-character SHA within a bounded polling window, and reports the elapsed attempts when it did not.
- **FR-5** — The promote door runs landing verification after `git push origin HEAD:main` succeeds and, when no run appears, records a `main-ci-run-missing` needs-you trip for each batch member issue.
- **FR-6** — The merge door runs landing verification after a successful PR merge and, when no run appears, records a `main-ci-run-missing` needs-you trip for the merged issue.
- **FR-7** — The escalation message names the condition in plain language, the landed SHA, the `gh workflow run` recovery commands for both workflows, and <https://www.githubstatus.com>.
- **FR-8** — `docs/DEFINITION-OF-DONE.md` and `docs/UAT-BATCH-TRAINS.md` describe the unverified-`main` condition and the dispatch recovery procedure.

### Non-functional

- **NFR-1** — Landing verification never changes the success/failure outcome of a promotion or merge that already landed, and never throws out of the calling path.
- **NFR-2** — Polling is bounded: at most 6 requests per landed SHA, at most 120 seconds elapsed.
- **NFR-3** — Every test exercising the polling interval uses `vi.useFakeTimers()` with `vi.advanceTimersByTimeAsync()`. No test may rely on real `setTimeout` wall-clock delay. (Repo rule, restated here deliberately: real retry delays in tests keep fetch mocks and abort controllers alive across workers and cause OOM under parallelization.)
- **NFR-4** — Any file whose line count grows past its `origin/main` count carries a matching `scripts/file-size-allowlist.txt` row `<lines> <path> # PAN-3586` **in the same commit**.

### Item 2 — `workflow_dispatch` on `state-plane-branches.yml` with a dispatch-safe range

**What/why.** `guard` is the fourth required check and lives here. Adding the trigger naively makes the guard inspect zero files (see D2), so the range computation changes in the same item. Satisfies FR-2 and FR-3.

**Files:** `.github/workflows/state-plane-branches.yml`

**Change — `on:` block:**

```yaml
# after
on:
  push:
    branches: [main, overdeck-state]
  pull_request:
    branches: [main]
  # PAN-3586: recovery door — see ci.yml. `guard` is one of the four checks
  # DoD row 6 requires, so CI's dispatch alone cannot unblock close-out.
  workflow_dispatch:
    inputs:
      since:
        description: 'Base SHA to diff from (default: the dispatched commit''s parent)'
        required: false
        default: ''
```

**Change — the guard step's range computation.** The current `else` branch (`.github/workflows/state-plane-branches.yml:24-31`) assumes push context:

```bash
# before
          else
            branch="${GITHUB_REF_NAME}"
            before="${{ github.event.before }}"
            if [[ "$before" == 0000000000000000000000000000000000000000 ]]; then
              before=$(git hash-object -t tree /dev/null)
            fi
            range="$before..${{ github.sha }}"
          fi

# after
          elif [[ "${{ github.event_name }}" == workflow_dispatch ]]; then
            # PAN-3586: workflow_dispatch has no `before` context. Leaving it
            # empty yields the range "..$GITHUB_SHA", which git reads as
            # HEAD..$GITHUB_SHA — and the checkout IS $GITHUB_SHA, so the guard
            # would diff nothing and report green having inspected zero files.
            branch="${GITHUB_REF_NAME}"
            before="${{ inputs.since }}"
            if [[ -z "$before" ]]; then
              before="${{ github.sha }}~1"
            fi
            range="$before..${{ github.sha }}"
          else
            branch="${GITHUB_REF_NAME}"
            before="${{ github.event.before }}"
            if [[ "$before" == 0000000000000000000000000000000000000000 ]]; then
              before=$(git hash-object -t tree /dev/null)
            fi
            range="$before..${{ github.sha }}"
          fi
```

**Implementation checkpoint.** The `since` input arrives as an empty string when omitted; the `-z` test covers that. If `inputs.since` names a SHA not present in the fetched history, `git diff` fails loudly — that is the intended behavior (a wrong base must not silently pass), and `actions/checkout@v4` already runs with `fetch-depth: 0` (`:16-18`), so any ancestor SHA resolves.

### Item 3 — Landing-verification helper (foundation)

**What/why.** One place that answers "did GitHub create a workflow run for this SHA?", with bounded polling and injectable dependencies so both doors share it and both can be tested without network or wall-clock. Satisfies FR-4 and NFR-2.

**Files:**
- `src/lib/github-app.ts` — add the API read.
- `src/lib/cloister/main-landing-verification.ts` — **new module**, the poller and the escalation message.
- `tests/unit/lib/cloister/main-landing-verification.test.ts` — **new test**.
- `scripts/file-size-allowlist.txt` — `github-app.ts` is at exactly 1000 lines on `origin/main`, which is also the new-file ceiling; any growth needs a row (NFR-4).

**Change — `src/lib/github-app.ts`.** Add an exported Promise-returning read next to `getCiCheckRunsStatePromise` (`:481`), using the existing module-private `githubApi` helper (`:358`) so it inherits the installation token:

```ts
/**
 * PAN-3586: how many workflow runs GitHub created for a SHA.
 *
 * This asks about *run creation*, which is the thing that fails when GitHub
 * drops push events (platform incident, credential regression). Check-runs
 * cannot answer it: they do not appear until jobs start, so "no run created"
 * and "jobs still queued" look identical. The filter needs the full 40-char
 * SHA — an abbreviated one silently returns zero.
 */
export async function countWorkflowRunsForShaPromise(
  owner: string,
  repo: string,
  sha: string,
): Promise<number> {
  const data = await githubApi<{ total_count?: number }>(
    `/repos/${owner}/${repo}/actions/runs?head_sha=${encodeURIComponent(sha)}&per_page=1`,
  );
  return data.total_count ?? 0;
}
```

**Change — new module `src/lib/cloister/main-landing-verification.ts`.** Shape:

```ts
export interface MainLandingVerificationDeps {
  countRuns: (owner: string, repo: string, sha: string) => Promise<number>;
  sleep: (ms: number) => Promise<void>;
  log?: (msg: string) => void;
}

export interface MainLandingVerdict {
  runCreated: boolean;
  attempts: number;
  sha: string;
}

/** PAN-3586: D7 — 6 attempts × 20s = a 120s bounded window. */
export const LANDING_VERIFY_ATTEMPTS = 6;
export const LANDING_VERIFY_INTERVAL_MS = 20_000;

export async function verifyMainLanding(
  owner: string, repo: string, sha: string,
  deps: MainLandingVerificationDeps,
): Promise<MainLandingVerdict>;

/** Operator-facing escalation text — names the condition, the SHA, and both recovery commands. */
export function buildUnverifiedMainMessage(sha: string, attempts: number): string;
```

`verifyMainLanding` polls `countRuns`; it returns `{ runCreated: true }` on the first non-zero count, sleeps `LANDING_VERIFY_INTERVAL_MS` between attempts, and returns `{ runCreated: false }` after `LANDING_VERIFY_ATTEMPTS`. A thrown `countRuns` is caught per attempt, logged, and treated as "not yet seen" so a transient API error does not masquerade as a missing run.

`buildUnverifiedMainMessage` produces text along these lines (exact wording is the agent's, but every element below is required by FR-7):

> `<sha>` landed on `main` but GitHub created no workflow run for it within 120s, so `main` has no CI evidence and DoD row 6 (`main-verify`) will block close-out for every issue merged at or before this commit. Nothing was rolled back — a landed merge is never rewound. Check <https://www.githubstatus.com> for an Actions incident, then produce the evidence on demand:
> `gh workflow run ci.yml --ref main`
> `gh workflow run state-plane-branches.yml --ref main`

**Tests — `tests/unit/lib/cloister/main-landing-verification.test.ts`.** Uses `vi.useFakeTimers()` in `beforeEach` and `vi.useRealTimers()` in `afterEach` (NFR-3), driving the poll loop with `vi.advanceTimersByTimeAsync()`:
- a run present on the first attempt returns `{ runCreated: true, attempts: 1 }` and makes exactly one `countRuns` call;
- a run appearing on the third attempt returns `{ runCreated: true, attempts: 3 }`;
- no run across the whole window returns `{ runCreated: false, attempts: 6 }` and makes exactly 6 calls;
- a `countRuns` that rejects on every attempt returns `{ runCreated: false }` rather than propagating the rejection;
- `buildUnverifiedMainMessage` output contains the SHA, `gh workflow run ci.yml`, `gh workflow run state-plane-branches.yml`, and `githubstatus.com`.

### Item 4 — Wire landing verification into the promote door

**What/why.** `promoteGeneration()` reports a clean promotion the moment the push exits 0. Satisfies FR-5.

**Files:** `src/lib/cloister/uat-promote.ts`, `tests/unit/lib/cloister/uat-promote-verification.test.ts`, `scripts/file-size-allowlist.txt`

**Change.** After the successful merge log at `src/lib/cloister/uat-promote.ts:242` and before `finishPromote(...)` at `:246`, verify the landing and escalate per member issue. Add `verifyLanding` and `recordUnverifiedMain` to the injectable deps interface (alongside `markRepoPromoted` at `:105`) so the existing tests can assert without network:

```ts
// after the existing:  log(`[uat-promote] ${name}: merged to main at ${mergeSha.slice(0, 9)} …`);

// PAN-3586: the push landed, but GitHub may not have created a workflow run
// for it. A promotion that silently leaves main unverified must not read as a
// clean promotion — row 6 will block close-out for every member. Observe and
// escalate only: never fail a merge that is already live on main (D5).
try {
  const verdict = await deps.verifyLanding?.(mergeSha);
  if (verdict && !verdict.runCreated) {
    const message = buildUnverifiedMainMessage(mergeSha, verdict.attempts);
    log(`[uat-promote] ${name}: ${message}`);
    // gen.members elements are objects carrying `issueId` (see :157, :715).
    for (const member of gen.members) {
      await deps.recordUnverifiedMain?.(member.issueId, mergeSha, message);
    }
  }
} catch (err) {
  log(`[uat-promote] ${name}: landing verification failed (non-fatal): ${err instanceof Error ? err.message : String(err)}`);
}

return finishPromote(gen, projectRoot, deps, mergeSha, log, false, options.shipVersion);
```

The production wiring binds `recordUnverifiedMain` to `recordDeadEndNeedsYou(issueId, 'main-ci-run-missing', mergeSha, message)` (D4).

**Note.** `gen.members` elements are objects, not bare strings — the codebase reads `gen.members.map((m) => m.issueId)` at `src/lib/cloister/uat-promote.ts:157` and `:715`. Use `member.issueId`, verified this session.

## Acceptance Criteria

## Non-Goals

- **Fixing GitHub's incident.** Nothing in this repository can make GitHub create runs for dropped webhook events. The plan delivers a recovery door and detection, not a cure.
- **A standing githubstatus.com poller or incident-aware pipeline mode.** The escalation message points at the status page; a background poller is a larger surface than this issue asks for.
- **Re-hardening DoD row 6.** PAN-3589 already landed that as `d921b8cec5` (`DEFAULT_MAIN_VERIFY_REQUIRED_CHECKS`). Row 6 is behaving correctly; do not change `checkMainVerifyRow`.
- **Rolling back or re-pushing a landed promotion.** `main` is never rewound. "Fail loudly" means a durable trip plus an operator signal, never unlanding.
- **`workflow_dispatch` on `no-planning-on-main.yml`.** Its `reject-planning-paths` check is not in row 6's required set, so it does not gate close-out. Left alone to keep the change minimal.
- **Auto-dispatching the recovery run.** Detection escalates to the operator; it does not fire `gh workflow run` on its own. Self-dispatch during a degraded-Actions window would queue runs that cannot execute.
- **Changing the promote path's credential or push mechanism.** The credential was proven identical across working and non-working pushes; there is nothing to change.
- **Using `--accept-main-verify` to override blocked close-outs.** The gate is correct and the evidence genuinely does not exist; an override would record a verification that never happened.
