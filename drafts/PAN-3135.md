# PAN-3135 PRD: Deploy queue with verification-admission pause and deadline escalation

## Glossary

- **Deploy gate / deploy window** — `getDeployBlockReason()` in `src/lib/deploy/deploy-window.ts:41`. Returns a human-readable string when a dashboard restart/deploy is unsafe, `null` when the window is clear. First (and starvation-relevant) condition: any issue whose review-status row has `verificationStatus === 'running'` and `mergeStatus !== 'merged'`.
- **Agent restart gate** — `agentRestartBlockReason()` in `src/lib/deploy/agent-restart-gate.ts:11`. Wraps the deploy gate for agent-issued `pan restart` / `pan reload` (initiator = `OVERDECK_AGENT_ID`). Operator-issued restarts (no `OVERDECK_AGENT_ID`) are never gated. `--force` bypasses.
- **Deploy patrol** — `runDeployPatrol()` in `src/lib/cloister/deploy-patrol.ts:267`, invoked every 5th deacon patrol cycle (`src/lib/cloister/deacon.ts:2765`). When the running build is stale, debounce has passed, CI is green, and the gate is clear, it spawns a detached `pan reload` (`spawnDetachedReload`, initiator `deploy-patrol`).
- **Verification runner** — `runVerificationForIssue()` in `src/lib/cloister/verification-runner.ts:936`. Default path spawns a detached supervised worker (`runSupervisedVerification` in `src/lib/cloister/verification-worker-supervisor.ts:126`); the worker itself calls `runVerificationForIssueInProcess` → `runVerificationForIssuePromise` (`verification-runner.ts:377`). The single status mutation that makes a run visible to the deploy gate is `setReviewStatusSync(issueId, { verificationStatus: 'running' })` at `verification-runner.ts:398`.
- **Verification outcome** — discriminated union `VerificationRunnerOutcome` in `src/lib/cloister/verification-types.ts:2`: `passed | skipped | failed | error`. This PRD adds a fifth variant, `deferred`.
- **Request-review pipeline** — `createRequestReviewPipeline()` in `src/lib/cloister/request-review-pipeline.ts:24`. Runs `verify()`; on anything other than `failed`/`error` it proceeds to `pushBranch()` + `dispatchReview()`. Used by the request-review route (`src/dashboard/server/routes/workspaces/review-pipeline.ts:716`); a second inline flow in the same file (line ~294) and the merge specialist's post-rebase verification (`src/dashboard/server/routes/workspaces/merge-ops.ts:1084`) call the runner directly.
- **Reactive review re-dispatch** — `maybeAutoDispatchReviewHostSide()` in `src/lib/review-status.ts:518`. Any review-status write re-evaluates `needsReviewDispatch()` (`src/lib/review-dispatch-decision.ts:22`): `reviewRequestedAt` set, `reviewSpawnedAt` unset/older, `reviewStatus === 'pending'`. Throttled 30 s per issue. This is the existing machinery that re-drives an issue whose verification never produced a review dispatch — the deploy-deferral design leans on it instead of inventing a new re-drive.
- **Deploy intent queue** (new) — a runtime-plane record at `${OVERDECK_HOME}/pending-deploy.json` (sibling of the existing `pending-post-merge.json`). Written whenever any deploy intent is deferred; read by the verification admission check and the patrol. Disposable cache state, never committed, not permanent-plane state.
- **DoD row 7** — the deploy row of the Definition-of-Done table (`docs/DEFINITION-OF-DONE.md:19`): an issue cannot close out until the live dashboard runs a build containing its merge.

## Problem

The deploy gate refuses any agent-issued restart while any verification is in flight, and the deploy patrol defers on the same condition. Neither path has a queue or a deadline: the deployer polls and the block clears only in an accidental window when the whole fleet is simultaneously idle. On 2026-07-26 (RUN-71) the blocker handed off from PAN-1696 to PAN-2997 across consecutive watch cycles — each verification individually healthy — and the wait was unbounded. Consequence: the live server drifted behind main and DoD row 7 blocked the close-out of three fully-merged issues (PAN-3119, PAN-3037, PAN-3114). With 21 in-flight issues eligible to enter verification, the probability of a simultaneously-clear window shrinks as the fleet grows.

This is starvation with an unbounded wait, not a deadlock. The defect is the missing queue: nothing registers the deploy intent, nothing stops new verification admissions while a deploy waits, and nothing escalates when the wait gets long.

## Proposal (chosen approach)

Implement the issue's **option 2 (queue the deploy, pause admissions, drain, fire automatically)**, plus **option 3 (deadline with escalation)** and the **minimum-viable reporting** (refusals report queue age and distinct blockers). Option 1 (resumable verification) is a deliberate NonGoal — it is a much larger change and the queue removes the acute pain.

The mechanism has five parts:

1. **Deploy intent queue** — a new module `src/lib/deploy/deploy-queue.ts` owns `${OVERDECK_HOME}/pending-deploy.json`. Three producers register intent: the agent restart gate (when it refuses), the deploy patrol (when it defers on the gate), and merge step 0 (when it defers a post-merge deploy to the patrol). Registration is idempotent: first `requestedAt` wins, `requestedBy` and `blockedBy` are unioned, `deferralCount` increments per registration.
2. **Verification admission pause** — while a queue record exists, no *new* verification run is admitted. Chokepoint: the top of `runVerificationForIssuePromise` (`verification-runner.ts:377`), before the `verificationStatus: 'running'` write at line 398. In-flight runs (`verificationStatus === 'running'` already) are untouched and drain naturally. A deferred admission consumes no verification cycle, sets `verificationStatus: 'pending'` with a marker `verificationNotes`, and returns a new `{ outcome: 'deferred', reason }` variant. Callers treat `deferred` as "leave everything pending, dispatch nothing, send no feedback" — the issue keeps its durable `reviewRequestedAt` intent, so the existing reactive re-dispatch retries automatically (each retry is a cheap file read until the queue clears).
3. **Queue-aware firing** — the deploy patrol fires a queued deploy at the first clear boundary: staleness behind + debounce passed + CI green + gate clear. Queued entries fire even when `auto_deploy` is false (an explicit agent request is not an unsolicited auto-deploy); patrol self-registration still respects `auto_deploy`. The record is cleared only when staleness is `fresh` — which happens exactly when a deploy (ours or anyone's) has landed — so the admission pause stays latched through the reload/restart window and a failed reload leaves the queue intact for the next patrol cycle.
4. **Deadline escalation** — new config `deploy.queue_deadline_minutes` (default 30) in `src/lib/cloister/config.ts` (`DeployConfig`, line ~328). When queue age exceeds the deadline and the gate is still blocked, the patrol emits an error-level activity entry + TTS and records one needs-you trip (`recordDeadEndNeedsYou` in `src/lib/cloister/dead-end-trip.ts:4`, anchored to the first currently-blocking issue, `recoveryPath: 'deploy-queue'`), once per queue lifetime (`escalated` flag on the record).
5. **Rich reporting** — the restart-gate refusal and the patrol deferral messages state: that the deploy is now queued, how long it has been deferred, and how many distinct issues have held it (with ids), plus explicit "fires automatically at the next verification boundary; do not retry or --force" guidance.

### Why this is safe

- The gate's block conditions are unchanged; with no queue file present, behavior is byte-for-byte today's behavior (the admission check is one file read that returns null).
- In-flight verifications are never interrupted by the pause; the deploy still waits for them. The only change is that the wait is bounded by the longest single in-flight run (hard-capped at 65 min by `MAX_RUN_MS` in `verification-worker-supervisor.ts:24`) instead of by fleet-wide activity.
- The reactive re-dispatch (`maybeAutoDispatchReviewHostSide`) already owns "verification pending + reviewRequestedAt set → retry"; deferred issues need no new re-drive machinery and cannot bypass verification on their way to review (review dispatch only happens after a passing/skipped verify in `request-review-pipeline.ts`).

## Requirements

### Functional

- **FR-1 — Queue record module.** `src/lib/deploy/deploy-queue.ts` provides `readPendingDeploy()`, `recordDeployIntent({ requestedBy, reason, blockedBy })`, and `clearPendingDeploy()`. Record shape: `{ requestedAt: string, requestedBy: string[], lastReason: string, blockedBy: string[], deferralCount: number, escalated: boolean }`. Writes are atomic (temp file + rename, matching `writeJsonAtomic` in `verification-worker-supervisor.ts:84`). `recordDeployIntent` on an existing record preserves the original `requestedAt`, unions `requestedBy`/`blockedBy`, updates `lastReason`, increments `deferralCount`. A corrupt or unreadable file is treated as absent (and quarantined by overwrite on next write) — it must never throw into a caller.
- **FR-2 — Restart-gate registration + enriched refusal.** When `agentRestartBlockReason` returns a refusal, it first calls `recordDeployIntent` with the initiator and the gate's current verifying-issue list. The refusal message states the deploy is queued, the queue age, the distinct blocker count and ids, and that it will fire automatically at the next verification boundary without retry or `--force`. Exit behavior (exit code 1, no restart) is unchanged.
- **FR-3 — Verification admission pause.** `runVerificationForIssuePromise` checks `readPendingDeploy()` before any status mutation; when a record exists and the issue's `verificationStatus` is not already `'running'`, it sets `verificationStatus: 'pending'` with `verificationNotes: 'Verification deferred: a dashboard deploy is queued (requested <requestedAt> by <requestedBy>). It re-runs automatically after the deploy.'`, consumes no cycle, and returns `{ outcome: 'deferred', reason }`. `runSupervisedVerification` performs the same check after the join-live-worker branch and before spawning a new worker, returning the same deferred outcome without a spawn. A run already in flight (`verificationStatus === 'running'`) is never deferred.
- **FR-4 — `deferred` outcome handling at every caller.** `VerificationRunnerOutcome` gains `{ outcome: 'deferred'; reason: string }` (`verification-types.ts`). `createRequestReviewPipeline` treats `deferred` like a stop: it calls a new optional `onVerificationDeferred` dep and returns without `pushBranch`/`dispatchReview`. The inline flow in `review-pipeline.ts` (~line 294) completes the pending operation with the deferral reason and returns without flipping `reviewStatus`. The merge specialist's post-rebase verification (`merge-ops.ts:1078-1096`) appends a ship-log line and aborts the merge attempt retriably — `mergeStatus` is not set to `failed`, no merge retry budget is consumed, and the issue remains mergeable so the normal merge re-drive retries after the deploy. No caller may treat `deferred` as `passed`/`skipped` (review would dispatch without verification) or as `failed`/`error` (agents would receive bogus failure feedback).
- **FR-5 — Patrol queue firing and clearing.** In `runDeployPatrol`: after computing staleness, if `fresh` → `clearPendingDeploy()` and return. Queue firing is evaluated before the `auto_deploy` early return (deploy-patrol.ts:308): if a queue record exists, debounce has passed, CI is green, and `getDeployBlockReason()` returns null → fire the reload exactly as today. The record is NOT cleared at fire time (it stays latched through the restart so admissions remain paused); it is cleared by the next patrol that observes `fresh` staleness. Patrol self-registration (`recordDeployIntent` with `requestedBy: 'deploy-patrol'`) happens only when `auto_deploy` is on and the gate blocks an otherwise-eligible deploy.
- **FR-6 — Deadline escalation.** When a queue record is older than `deploy.queue_deadline_minutes` (default 30) and the gate is still blocked, the patrol emits an error-level activity entry and TTS announcing the queued deploy's age and current blockers, and records one needs-you trip via `recordDeadEndNeedsYou(blockerIssueId, 'deploy-queue', requestedAt, message)` where `blockerIssueId` is the first currently-verifying issue. The `escalated` flag on the record makes this fire once per queue lifetime.
- **FR-7 — Merge step-0 registration.** `shouldRestartForPostMerge` (`src/lib/cloister/merge-agent-step0.ts:8`) calls `recordDeployIntent({ requestedBy: 'merge-step0', reason, blockedBy })` when it defers a post-merge deploy because the gate is blocked.

### Non-functional

- **NFR-1 — Async only.** No `execSync` anywhere reachable from the dashboard server; queue I/O uses `node:fs/promises` or existing sync-safe helpers only in CLI/sync contexts that already permit them (the verification runner and patrol already use sync fs helpers — match each file's existing convention).
- **NFR-2 — Tests use fake timers for anything time-based** (queue age, deadline, cooldowns): `vi.useFakeTimers()` + `advanceTimersByTimeAsync`, per repo rule.
- **NFR-3 — Runtime-plane state.** `pending-deploy.json` is disposable cache state under `OVERDECK_HOME`; nothing is written to `overdeck-state`, the SQLite DB, or review-status rows beyond the marker note in FR-3.
- **NFR-4 — Backward compatible.** Absent queue file → identical behavior to today in every path (gate, patrol, verification, restart).

## Decisions (made in this doc)

- **D1: Option 2 + 3, not option 1.** Resumable verification (option 1) is a NonGoal. The queue bounds the wait by the longest single run; resume-across-restart is a much larger change for marginal additional benefit. The issue's own comment thread endorses option 2.
- **D2: Chokepoint is the runner, not the dispatch sites.** The admission pause lives in `runVerificationForIssuePromise` (+ early exit in `runSupervisedVerification`) so every dispatch path — request-review, inline route, merge-ops, worker — is covered by one check. Gating each dispatch site instead would leave merge-ops and future call sites unguarded.
- **D3: New `deferred` outcome instead of reusing `skipped`/`failed`.** `skipped` would proceed to review dispatch without verification (request-review-pipeline.ts:40-41); `failed` would send bogus failure feedback to work agents and consume recovery budget. A distinct variant forces TypeScript to enumerate every handler.
- **D4: Re-drive leans on the existing reactive dispatch.** Deferral leaves `reviewRequestedAt` set and `reviewSpawnedAt` unset, so `maybeAutoDispatchReviewHostSide` retries on existing cadence. No new patrol, no boot hook. Each retry while queued is a no-op defer.
- **D5: Record survives the reload; cleared only on `fresh` staleness.** Clearing at fire time would reopen admissions during the build/restart window and let a new verification start just as the server dies. Clearing on boot would lose the queue when an operator restarts without deploying (`pan restart` does not rebuild). `fresh` staleness is the only signal that a deploy actually landed.
- **D6: Queued entries fire even when `auto_deploy` is false.** The queue only exists because someone explicitly asked for a deploy; `auto_deploy` gates *unsolicited* patrol-initiated deploys (and patrol self-registration), not explicit requests. Otherwise a queued deploy would never fire and admissions would pause forever — inverted starvation.
- **D7: Debounce and CI-green still apply to queued fires.** A queued deploy must not fire onto a red or still-settling main.
- **D8: Needs-you trip anchored to the first currently-blocking issue.** `recordDeadEndNeedsYou` is issue-scoped; the anchor is the first id in the gate's current verifying list. If no issue is currently verifying (blocked by a non-verification condition), escalate with the activity entry + TTS only.

## Intersecting repo rules (restated)

- Fake timers for any retry/backoff/deadline test (`vi.useFakeTimers()`); never real `setTimeout` waits.
- No `execSync` in server-reachable code.
- The queue file is runtime-plane disposable state; do not write it through the permanent-state door and do not commit it.
- Operator-facing messages must stand alone: the enriched refusal text must define "queued deploy" and state the consequence in complete sentences.
- xBRIEF items commit one at a time with an immediate push before `pan task done`.

## Acceptance criteria (plan-level)

1. With a verification in flight, an agent-issued `pan restart --dashboard` exits 1, writes `pending-deploy.json`, and its message reports queue age, distinct blockers, and auto-fire guidance.
2. While `pending-deploy.json` exists, a new verification admission returns `deferred`, consumes no cycle, leaves `reviewStatus`/`verificationStatus` pending, and dispatches no review and no agent feedback; in-flight verifications run to completion untouched.
3. When the last in-flight verification completes, the next deploy patrol fires the reload without any agent retrying; after the restart the build is fresh and the queue file is cleared on the following patrol.
4. A deferred issue enters review after the deploy through the normal verification-first path (reactive re-dispatch), with verification actually executed.
5. With the gate blocked past `queue_deadline_minutes`, exactly one escalation (activity entry + TTS + needs-you trip) fires per queue lifetime.
6. With no queue file present, gate, patrol, verification, and restart behavior is identical to before this change.
7. `npm run typecheck`, `npm run lint`, and `npm test` pass with the new tests green.
