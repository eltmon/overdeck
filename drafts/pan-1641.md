## Glossary

- **omp / ohmypi** — the Pi harness (`@earendil-works/pi-coding-agent`); Overdeck
  harness name `ohmypi`. Resolves `--model <id>` against its bundled provider
  catalog plus a user registry at `~/.omp/agent/models.json`.
- **Provisioning** — Overdeck's merge-write of a provider entry (baseUrl, apiKey
  env-var name, model defs) into `~/.omp/agent/models.json` before an ohmypi
  spawn, so omp can resolve models absent from its bundled catalog (DashScope,
  Ollama). Implemented in `src/lib/ohmypi-models.ts`.
- **Launcher generation** — `generateLauncherScriptSync()` in
  `src/lib/launcher-generator.ts:244`; builds the bash launcher script for every
  agent/conversation spawn. Runs inside the long-lived dashboard Node process on
  dashboard-initiated launches.
- **Preflight** — the Ollama endpoint + model-present health check in
  `getProviderEnvForModel()` (`src/lib/agents/provider-env.ts:45`) that runs
  before spawn and throws a clear error instead of falling back to cloud.
- **AC 19 / AC 28 / AC 29** — acceptance criteria from the 2026-08-13 review's
  requirements matrix. AC 19: preflight before every spawn. AC 28: an
  Overdeck-spawned Pi work agent completes a trivial Ollama task. AC 29: proof
  of localhost-only traffic and zero cloud calls for that spawned agent.
- **PAN-3684** — sibling acceptance issue ("PAN-1641 acceptance: local Ollama
  work-agent spawn"), open, created 2026-08-13 as the vehicle for the AC 28/29
  evidence: an Overdeck Pi work agent with `ollama:gemma4:12b` must create
  `LOCAL_OLLAMA_OK.txt` containing `LOCAL_OK`, commit, push, and `pan task done`.

## Blocking findings this PRD resolves

### B1 (performance) — Ollama launcher provisioning blocks the dashboard event loop

`provisionOhmypiProviderForModel()` (`src/lib/ohmypi-models.ts:97`) uses
synchronous fs (`existsSync`, `readFileSync`, `mkdirSync`, `writeFileSync`,
`renameSync` — imports at line 17) against `~/.omp/agent/models.json`. Ollama was
added to `PROVISIONED_PROVIDERS` (line 87), so `generateLauncherScriptSync()`
calls it at `src/lib/launcher-generator.ts:252`. Dashboard launch/relaunch
routes reach that path in the long-lived Node server; a slow home filesystem
blocks every HTTP request, WebSocket, and terminal stream. Cost also grows with
registry size because the whole document is read/parsed/rewritten even when the
entry is unchanged. This also violates the repo's no-sync-I/O-in-server rule.

**Reviewer-prescribed fix (adopted verbatim as the design):**
1. Make provisioning asynchronous with `node:fs/promises`.
2. Call it before the synchronous string-generation phase (i.e. hoist it out of
   `generateLauncherScriptSync` into the async call sites).
3. Skip the write when the existing provider definition already matches.
4. Serialize concurrent updates through a per-registry-path mutex/write queue.

### B2 (requirements) — E2E evidence bypasses the Overdeck work-agent spawn path

AC 28/29 require an **Overdeck-spawned** Pi work agent. The audit
(`docs/audits/pan-1641-local-ollama-verification.md:25`) invoked `omp --model
ollama/gemma4:12b` directly, so launcher generation, registry provisioning,
preflight integration, and Overdeck's spawn path are unverified end-to-end.
PAN-3684 already exists as the acceptance vehicle; the evidence must be
produced through it and recorded in the audit doc.

## Non-blocking findings folded into this delta

- **N1 (correctness)** — `checkOllamaHealth()` awaits `response.json()`
  (`src/lib/ollama.ts`, in the `try` after the `response.ok` check, ~line 119)
  with no timeout: `fetchOllamaTags()` clears its AbortController timeout once
  headers arrive, so a stalled response body pends preflight forever.
- **N2 (performance)** — a stalled local endpoint stretches a failed startup to
  ~189 s: preflight probes once (`checkOllamaHealth`, 5 s), then
  `ensureOllamaServeRunning()` probes again (5 s), then up to 30 attempts at
  5 s probe + 1 s gap (`waitForOllamaHealth`, `src/lib/ollama.ts:222`). Fix per
  review: pass the known-unhealthy result in so the ensure path does not probe
  twice, and enforce one overall startup deadline with per-attempt budget
  derived from the remaining time; keep fast retries for connection-refused.
- **N3 (requirements, demoted pre-existing)** — AC 19: the stopped-agent
  fresh-launch fallback in `messageAgent()` (`src/lib/agents/messaging.ts`,
  fallback starting ~line 330) must provably run the Ollama preflight before
  recreating the tmux/session. Code reading shows
  `await getProviderExportsForModel(...)` at `messaging.ts:331` already precedes
  `generateLauncherScriptSync` (line 360) and `createSession` (~line 377), and
  `getProviderExportsForModel` → `getProviderEnvForModel` → Ollama preflight
  (`provider-env.ts:184-185`, `provider-env.ts:45-56`), so the ordering appears
  correct; what is missing is the regression test pinning it.

## Decisions (made here, not left to the executor)

- **D1 — Delta scope.** This plan covers only the two blocking findings plus
  N1/N2/N3 above. The 9 completed items are not re-planned.
- **D2 — Fix shape follows the reviewer.** Async provisioning hoisted to call
  sites, per B1's prescribed fix. A cheaper sync fast-path was considered and
  rejected: the review gate owns this shape, and sync I/O in server-reachable
  code is independently banned.
- **D3 — No dual provisioning path.** The sync
  `provisionOhmypiProviderForModel` is replaced by
  `provisionOhmypiProviderForModelAsync`; `generateLauncherScriptSync` stops
  provisioning entirely. Every current call site is inside an async function,
  so no sync caller needs the old path. One door, no drift.
- **D4 — E2E runs through PAN-3684.** The acceptance issue already exists with
  its own xBRIEF on `overdeck-state`; do not invent a parallel flow. The
  deliverable in THIS issue is the updated audit doc plus PAN-3684's closure.
- **D5 — N1/N2/N3 are in this delta.** They are small, precisely specified, and
  would otherwise resurface as next cycle's blocking findings.
- **D6 — Mutex granularity.** The serialization queue is keyed by registry
  path, not global, so remote agents with a distinct `agentDir` never serialize
  against local launches.

## Requirements

- **FR-1** (B1): Provisioning performs no synchronous filesystem I/O. All
  registry reads/writes use `node:fs/promises` and run before
  `generateLauncherScriptSync` is called.
- **FR-2** (B1): When the existing registry entry deep-equals the entry to be
  written, provisioning performs no write (no tmp file, no rename).
- **FR-3** (B1): Concurrent provisioning calls for the same registry path
  serialize; no update is lost. Calls for different paths proceed in parallel.
- **FR-4** (N1): `checkOllamaHealth` bounds the total probe — headers AND body —
  by the 5 s probe timeout; on body timeout it treats the endpoint as
  unreachable and cancels the body.
- **FR-5** (N2): `ensureOllamaServeRunning` accepts a known-unhealthy hint that
  skips the duplicate pre-start probe, and bounds the whole startup wait by one
  overall deadline (default 30 s); per-attempt probe budget derives from the
  remaining deadline. Connection-refused failures still retry fast.
- **FR-6** (N3/AC 19): A regression test proves the stopped-agent fresh-launch
  fallback in `messageAgent()` completes the Ollama preflight before session
  recreation. If the test exposes wrong ordering, hoist the preflight call
  above the session-recreation block in `messaging.ts` (decision rule: fix the
  ordering, never weaken the test).
- **FR-7** (B2/AC 28/29): The audit doc records an Overdeck-spawned Pi work
  agent (via PAN-3684) completing its trivial Ollama task: agent identity,
  launch path, successful result (`LOCAL_OLLAMA_OK.txt` committed and pushed),
  localhost-only request evidence, and proof that cloud credentials and cloud
  endpoints were absent from the spawned agent's environment. PAN-3684 is
  closed after the evidence lands.
- **NFR-1**: No new synchronous fs in server-reachable code (repo rule).
- **NFR-2**: Delay/retry/deadline tests use `vi.useFakeTimers()` +
  `advanceTimersByTime` — never real waits (repo rule).
- **NFR-3**: The zero-cloud-call invariant is preserved: the Ollama provider
  env contains only `OPENAI_BASE_URL` (localhost `/v1`) and `OPENAI_API_KEY`;
  no `ANTHROPIC_*` variables, no cloud endpoints.
