## 0. Glossary (define-before-use)

- **Slot** — one parallel work agent inside a single issue's swarm: `agent-<issue>-slot-N`, on branch `feature/<issue>-slot-N`, in worktree `<featureWorkspace>-slot-N`. The naming convention is defined in exactly one place: `resolveRegisteredSlotSpawn` (`src/lib/agents/spawn-prep.ts:181-205`).
- **Foreman** — the persistent parent Work agent for the issue, `agent-<issue>` (bare id, no slot suffix). It owns swarm orchestration cognition: wave dispatch, slot supervision, integration verification, corrective messaging, freeze/resume, recovery decisions, and the normal work-agent lifecycle through `pan done` → review → merge → close-out. The name already exists in code: `src/lib/agents/tier-metrics.ts:100` labels the bare id `'foreman'`.
- **Wave** — a set of xBRIEF items with no unresolved `blocks` edges on un-merged items (`groupItemsByWave`, Kahn's algorithm). Waves run sequentially; slots within a wave run in parallel.
- **Gate / gated command** — a `pan swarm` subcommand whose internals enforce mechanical invariants the caller cannot override (blocker-done at claim, duplicate-spawn refusal, overlap serialization, capacity, claim-release-on-throw). The foreman *drives* gates; it cannot *bypass* them.
- **Deacon** — the Cloister patrol daemon (`runPatrol`, `src/lib/cloister/deacon.ts:2625`). After this PRD it performs **no swarm dispatch, merge, or recovery decisions**. It keeps three swarm duties: foreman liveness, stall/event detection, and janitorial GC.
- **Hold** — a durable per-issue swarm freeze. Today `pan swarm freeze` overloads the generic `ReviewStatus.deaconIgnored` flag (`src/lib/review-status.ts:1058`); this PRD gives swarm its own `swarm.hold` record field (D-8).
- **Completion marker** — `record.swarm.slotCompletions[String(slotIndex)]`, written by the slot's `pan done` via `persistAndVerifySwarmSlotCompletion` (`src/lib/cloister/deacon-swarm-record.ts:124`). Survives unchanged.
- **Inferred completion** — `classifyDoneWithoutSignal` (`src/lib/cloister/deacon-swarm-completion.ts:25`): branch ahead ≥1 + state-plane-clean worktree, two stable observations. Survives as a fallback (D-11).
- **Derive-don't-store** — no persisted swarm *runtime* state; each read re-derives from git + tmux + xBRIEF. Kept. The short list of durable exceptions is enumerated in NFR-1.
- **Dual stop** — the bounded-repair rule adopted from deft directive (#2442/#3152): every multi-iteration supervision loop needs a success stop AND a failure/budget stop, then an operator-visible halt report.

## 1. Problem

PAN-2203 built `coordinateSwarmSlots()` (`src/lib/cloister/deacon-swarm.ts:303`) — a deterministic Deacon-owned loop that dispatches, merges, and advances swarm slots with **no agent cognition anywhere**. Verified fact: `pan swarm <id>` never spawns a parent work agent at all — `swarmCommand` (`src/cli/commands/swarm.ts:115-175`) only ensures the workspace and runs a coordination pass; the only `spawnRun` in the whole path produces slot ids (`deacon-swarm.ts:980` → `spawn-prep.ts:200`). The "foreman" role label in `tier-metrics.ts:100` names a process that never exists. (The `~/.overdeck/agents/agent-min-888/` directory containing only `health.json` is an artifact of an ungated health probe — `saveAgentHealth` `src/lib/health.ts:85` mkdirs for never-spawned agents — not a crashed parent.)

### 1a. Fresh evidence — MIN-888 / MIN-889 (2026-08-13)

1. Slot reconciliation classified **live** slot branches as merged (sparse polyrepo root ancestry misread — PAN-3679), and the Deacon dispatched `sync-entities` while its declared blocker `sync-schema-foundation` was still running. Two dependent tasks ran concurrently against a schema that did not exist.
2. A slot agent edited the **shared primary `api` checkout** because its sparse slot workspace lacked that repo. No mechanical check noticed.
3. Recovery required a human-supervised conversation reading slot transcripts, freezing both swarms, stopping the dependent, relocating the stray diff, and messaging each slot corrective constraints. Every step was a judgment call `coordinateSwarmSlots` cannot make.

### 1b. Chronic evidence — the flywheel log

`docs/FLYWHEEL-STATE.md`: the global `swarm.mode off` orphan (`:920`, PAN-3459); readiness-contract stall with "no work-agent handoff and no needs-you" (`:965`, PAN-3468); a merged slot auto-resumed forever (`:1016`, PAN-3477); and the operator's own verdict at `:1017` — "the swarm path is the least-exercised part of the pipeline and it shows."

### 1c. Structural defects in the current loop (from the code audit)

- **Four unserialized entry points** call `coordinateSwarmSlots`: the patrol (`deacon.ts:3006`), the reactive `agent.stopped` fast-path (`src/lib/cloister/service-reactive.ts:467`), the slot-done fast path (`deacon.ts:2190`), and the CLI (`swarm.ts:156`, `:206`). The only serialization is 5s process-local cooldown maps (`deacon-swarm.ts:75-83`) — module-global, lost on restart, invisible across processes.
- **Freeze is overloaded onto `deaconIgnored`** (`review-status.ts:1058`) — `pan swarm freeze` and a generic operator deacon-ignore are indistinguishable downstream (`deacon-swarm.ts:313-317`).
- **The repo documents two contradictory ownership models.** `docs/SWARM.md` ("coordinated by Deacon… It does not stay resident", `:3`, `:98`) vs `roles/work.md:85-136` (the PAN-1762 foreman protocol: "You remain the durable work agent for the issue" — never mentions Deacon, `pan swarm`, or any CLI). They contradict each other on synthesis outright (SWARM.md:181 Deacon-dispatched synthesis slots vs work.md:122-126 in-context digest, no `SynthesisOutput`).

### 1d. Decision history

PAN-1762 shipped primitives + the prose foreman (cognition, no mechanics). PAN-1195 (operator feedback 2026-05-18) asked for the parent to stay and orchestrate; closed superseded. PAN-2203 built the autonomous Deacon loop (mechanics, no cognition), §9 of its PRD explicitly diverging from deft directive's persistent-monitor model. 2203 fixed 1762's fragility and reintroduced 1195's blindness. This PRD is the synthesis: **foreman drives, gates enforce, Deacon backstops.**

## 2. Locked design decisions

- **D-1 — Ownership inversion, no dual mode.** The foreman owns orchestration. The Deacon's autonomous swarm dispatch/merge/recovery is **removed**, not config-flagged. Rationale: two coordinators = races (the MIN-888 dispatch fired mid-intervention); four entry points already proved unserializable. One cognitive owner.
- **D-2 — Gates are commands.** Every PAN-2203 primitive survives as the internals of a gated `pan swarm` subcommand (§4.2). Invariants hold regardless of caller: blocker-done at claim, polyrepo-aware merged reconciliation (PAN-3679), duplicate-spawn refusal, claim-release-on-throw, overlap serialization, capacity ceilings.
- **D-3 — Deacon = watchdog + janitor.** Keeps: foreman liveness (§4.4), stall detection **as events to the foreman** (never actions), merged/orphan slot GC. Loses: `dispatchNextWave`, `mergeReadySlots`, recovery execution, finalization.
- **D-4 — The foreman is a registered pan work agent.** Spawned by `pan swarm <id>` via `spawnRun(issueId, 'work', …)` with a foreman marker — dashboard identity, pause/resume, `pan tell`, recovery all work. Never an Agent-tool subagent. Cloister routes its model; no hardcoded fallback. Slots keep tier routing (PAN-1791 axis untouched).
- **D-5 — Finalization is `pan done`.** When all items are merged and integration is green, the foreman runs `pan done <issue>` like any work agent — entering the normal review pipeline. `finalizeSwarmIssueIfComplete` (`src/lib/cloister/deacon-swarm-finalization.ts:36`) and its direct review-request are deleted. The Deacon's contribution to finalization is keeping the foreman alive to do it.
- **D-6 — Monitor-never-implements.** The foreman does not implement an item in its own context while that item's slot is live (deft directive closed this exact "monitor-as-implementer" false-DONE hole, deftai/directive#2843). Take-back requires `pan swarm recover --action reclaim` (§4.2), which closes the slot through the gate first.
- **D-7 — Bounded repair (dual stop).** Cognitive rule: max **3** corrective interventions per slot per failure class, then freeze + halt report. Mechanical backstop: the recover gate counts interventions in the per-issue record and refuses the 4th without `--operator` (FR-14).
- **D-8 — Dedicated `swarm.hold`.** New per-issue record field `{reason, setBy, at}` written by freeze/stop/reset, checked by every mutating gate. `deaconIgnored` reverts to meaning only the generic operator hold. Fixes the overload flagged in §1c.
- **D-9 — Policy semantics re-based on the foreman.** `SwarmMode = 'off'|'auto'|'always'` (`src/lib/swarm-policy.ts:5`; defaults `mode: off, maxSlots: 3, autoAdvance: true`, `src/lib/config-yaml/defaults.ts:39`). New meaning: `off` = no foreman wave loop (serial work only); `auto` = the Deacon may auto-spawn a **foreman** (never slots) for a swarm-eligible issue; `always` = require swarm readiness rather than silently falling back. `autoAdvance` is **redefined**: `true` = foreman advances waves without per-wave operator confirmation; `false` = foreman pauses for operator ack between waves. The field survives; the poller it used to gate does not.
- **D-10 — Synthesis is a foreman digest.** Resolve the documented contradiction in favor of `roles/work.md:122-126`: at DAG convergence points the foreman composes an in-context digest from merged parents' `expected_outputs` + verification evidence, inlined into the convergent item's slot prompt. Deacon-dispatched synthesis slots (`docs/SWARM.md:179-183`, `dispatchPhaseForItem`/`itemRequiresSynthesis`, `deacon-swarm.ts:1071-1114`) are removed. No `SynthesisOutput` object, ever.
- **D-11 — Completion marker + inference survive as the safety net.** The slot `pan done` marker write is unchanged. Mechanical inference (`classifyDoneWithoutSignal`) survives for the window where the foreman is dead/degraded, with its observation state moved from the process-local map (`deacon-swarm-completion.ts:10`) to the per-issue record (NFR-1). The *nudge* ("run `pan done`") becomes a foreman duty in the role protocol; the Deacon no longer messages slots.
- **D-12 — Existing CLI verbs survive, re-attributed.** `status`/`recover`/`freeze`/`resume`/`stop`/`reset` keep their names and operator semantics. `pan swarm <id>` changes from "dispatch wave-0 and exit" to "spawn/attach the foreman." New verbs: `dispatch`, `merge`, `wait` (§4.2).
- **D-13 — `pan start` inversion.** `docs/SWARM.md:5-9`'s "`pan start` refuses to launch a primary work agent while any slot is live" is removed. On a swarm-active issue, `pan start` attaches/respawns the **foreman**. The parent is now required, not forbidden.
- **D-14 — Nuclear-family messaging.** Foreman↔slot only (via the delivery door). Slots never message each other; cross-slot context flows through the foreman or the plan file. (deft directive ADR-003, deftai/directive#3155.) Enforced in role prompts; the delivery door is not modified in v1.
- **D-15 — Process-local safety maps become derive-or-durable.** The four module-global maps (`deacon-swarm.ts:80-83`) assumed one long-lived driver process. With gates running in short-lived CLI processes: merge-refire protection derives from git merge state + single-writer foreman serialization; advance backoff becomes foreman pacing + the durable intervention counter (D-7); stall observations stay in the Deacon process (its detector remains resident); completion observations move to the record (D-11).

## 3. Architecture

### 3.1 The ownership diagram

```
operator / flywheel
      │  pan swarm <id>            (spawn/attach foreman)
      ▼
FOREMAN  agent-<issue>  (persistent registered work agent; Cloister-routed model)
      │  drives gates, reads transcripts, judges, messages, freezes, finalizes
      ├── pan swarm dispatch <id>      ─┐
      ├── pan swarm merge <id> <slot>   │ gated commands — hard invariants,
      ├── pan swarm status --json       │ single mutator: the foreman
      ├── pan swarm wait <id>           │ (operator may also invoke any gate)
      ├── pan swarm recover …          ─┘
      ├── pan tell agent-<issue>-slot-N "<correction>"
      └── pan done <issue>             (normal pipeline entry when integration green)

SLOTS  agent-<issue>-slot-N   (unchanged: claim → implement → verify → pan done marker)

DEACON (patrol)                (no dispatch, no merge, no recovery)
      ├── foreman liveness: swarm-active issue + no live agent-<issue> → respawn foreman
      ├── stall/event detection → messageAgent(foreman, "[swarm-event] …")
      └── janitor: gcMergedSlots / gcOrphanedSlots (idempotent, merged-only)
```

### 3.2 Command surface (the gates)

All handlers live in `src/cli/commands/swarm.ts` (registration `registerSwarmCommands`, `:704`); shared internals stay in `src/lib/cloister/deacon-swarm.ts` (renamed exports acceptable; module rename to `swarm-gates.ts` optional but recommended — it no longer belongs to the deacon).

| Command | Semantics after this PRD |
|---|---|
| `pan swarm <id>` | Eligibility gate (`analyzeSwarmReadiness`) → `ensureFeatureWorkspace` (`swarm.ts:767`) → persist issue-level mode as today (`writeSwarmPolicyMode`, `deacon-swarm-record.ts:54`) → **spawn or attach the foreman** (`spawnRun(issueId, 'work', { workspace, foreman: true, startedBy })`). Prints foreman id + `pan swarm status` pointer. Idempotent: live foreman → message it instead of spawning (duplicate-agent doctrine). |
| `pan swarm dispatch <id> [--json]` | One dispatch pass: reconcile → classify → `dispatchNextWave` (`deacon-swarm.ts:863`) with every existing guard (occupancy `:889-906`, duplicate-spawn `slotIndexConflictReason` `:1041`, overlap `:915-919`, capacity `:921-924` + `tryReserveSwarmSlot` `concurrency.ts:303`, claim-before-spawn `:955`, rollback `:990-1000`). **New hard invariant (FR-6):** an item whose `blocks` parents are not all done/merged is never claimable — enforced inside the gate, not by the caller. Structured output: dispatched / deferred-with-reason / blocked. Refuses under `swarm.hold`. |
| `pan swarm merge <id> <slot> [--json]` | Single-slot verify+merge: marker/classification check → `verifyAndMergeSlot` (`src/lib/agents/slot-merge.ts:36`) → item `done` via the task door → `clearSwarmSlotCompletion` → reap agent (`deacon-swarm-gc.ts:10`) → `fireTieredCommitHooks` (`swarm-tiered-hooks.ts:97`). Conflict → durable `failedMergeBlock` (`deacon-swarm.ts:698`), exit non-zero with recovery hint. Refuses a live-session slot without a completion signal (FR-7, the PAN-3679 invariant). |
| `pan swarm status <id> [--json]` | Today's read-only reconcile+classify (`swarm.ts:590`) plus `--json` and three additions: foreman identity/liveness, `swarm.hold`, intervention counters. |
| `pan swarm wait <id> [--timeout <sec>]` | **New.** Blocks until a slot lifecycle transition (completion marker write, session exit, stall event, failed-merge block) or timeout; prints the status delta (`--json`). Implementation: poll the derive surface at a coarse interval in-process; no daemon dependency. This is the foreman's token-cheap quiescent loop. |
| `pan swarm recover <id> <slot> --action retry\|drop\|handoff\|reclaim` | Existing three actions keep semantics (`recoverFailedMergeSlot`, `deacon-swarm.ts:714`). **New `reclaim`** (D-6): archive the slot attempt (`archiveFailedSwarmSlot`, `swarm-failed-slot.ts:47`), `unblock` the item, record foreman take-over; the foreman then implements serially. Every action increments the per-slot intervention counter; the 4th in one failure class refuses without `--operator` (FR-14). |
| `pan swarm freeze/resume/stop/reset` | Same operator semantics, rewired to `swarm.hold` (D-8). `stop`'s hold-first ordering survives (it now beats the *foreman*, not the Deacon, to the respawn race). `reset` keeps `clearAllSlotAssignments` (`deacon-swarm.ts:1017`) + block clearing. |

Slot completion signaling is unchanged: slot `pan done <issue>` → `persistAndVerifySwarmSlotCompletion` (`deacon-swarm-record.ts:124`, write-then-reread, refuse on false).

### 3.3 Before/after — the two load-bearing call sites

**Patrol (`src/lib/cloister/deacon.ts:3006`), before:**
```ts

    actions.push(...swarmActions);
```
**After:**
```ts

    // detects stalls (events to the foreman), GCs merged/orphaned slots,

    const swarmActions = await swarmJanitorPass();
    actions.push(...swarmActions);
```

**CLI (`src/cli/commands/swarm.ts:156`), before (inside `swarmCommand`):**
```ts

```
**After:**
```ts
  const foreman = await ensureSwarmForeman(issueId, workspacePath, { startedBy: 'cli:swarm' });

```

**Reactive fast-path (`src/lib/cloister/service-reactive.ts:463-467`), before:** slot `agent.stopped` → `coordinateSwarmSlots({ issueId })`. **After:** slot `agent.stopped` → `messageAgent('agent-<issue>', '[swarm-event] slot N stopped (exit=…)', 'deacon:swarm-event')`. Same replacement at the slot-done fast path (`deacon.ts:2190`).

### 3.4 The janitor pass and foreman liveness

New `swarmJanitorPass()` in `deacon-swarm.ts` (or successor module), run each patrol tick:

1. **Enumerate swarm-active issues** — live slot sessions, unmerged slot branches, or slot assignments present (reuse `listFeatureWorkspaces` + `reconcileSlotState`, `src/lib/agents/slot-reconcile.ts:67`).
2. **Foreman liveness (FR-11).** Swarm-active + no live `agent-<issue>` session + no `swarm.hold` → respawn the foreman via `spawnRun` with a resume prompt ("read `.pan/continue.json`, run `pan swarm status <id> --json`, reconcile, continue the wave loop"). Respect the resource governor (swarm respawns already count under `holding`, `docs/RESOURCE-GOVERNOR.md:326`) and the generic liveness net (`reconcileAgentLiveness`, `src/lib/cloister/deacon-auto-resume.ts:955`, patrol call `deacon.ts:2711`). ≥3 consecutive respawn failures → freeze + operator halt report — never a silent thrash loop (cf. the PAN-821 dueling-deacon metronome).
3. **Stall detection (FR-12).** Keep `classifyInFlightSlots`' progress fingerprinting (`deacon-swarm.ts:465-508`; threshold `swarmStallThresholdMs` `:531`, default 30 min, `PAN_SWARM_STALL_THRESHOLD_MS`). On stall: emit `[swarm-event] slot N stalled (no progress 34m)` to the foreman. **Do not** write recovery blocks (`recordStalledSlotRecovery`, `:814`, is deleted) — classification is the Deacon's; the decision is the foreman's.
4. **GC.** `gcMergedSlots` (`deacon-swarm-gc.ts:24`) + `gcOrphanedSlots` (`deacon-swarm-orphan-gc.ts:14`) unchanged — idempotent, touch only merged/orphaned slots.

### 3.5 The foreman protocol (role surface, `roles/work.md` §Foreman rewrite)

The wave loop keeps the shape of `roles/work.md:91-99` but every mechanical step becomes a gate invocation:

1. On start/restart: `pan swarm status <id> --json` (replaces hand-run reconcile, work.md:95).
2. Dispatch: `pan swarm dispatch <id> --json`; read dispatched/deferred/blocked; judge the deferrals (semantic readiness beyond the DAG — the MIN-888 lesson).
3. Wait: loop `pan swarm wait <id> --timeout 540`; on each wake read the delta, spot-read slot transcripts (`tmux capture-pane` / activity), verify claims against worktree state.
4. Per completed slot: `pan swarm merge <id> <slot>`; then integration check on the feature branch (lint/typecheck/smoke per project verify commands) before advancing the wave (`autoAdvance: false` additionally requires operator ack).
5. Corrections: `pan tell agent-<issue>-slot-N` with the constraint; polyrepo isolation check — a slot's diff must stay inside its slot worktree (the MIN-888 escape).
6. Failure handling: retry-once-with-feedback (work.md:132), then `recover --action reclaim` and do it serially — never implement while the slot lives (D-6). Dual-stop envelope (D-7).
7. Convergence: compose the synthesis digest in-context (D-10).
8. Endgame: all items merged + integration green → `pan done <issue>`. The foreman continues through review/test/merge/deploy/verify-on-main/close-out as the issue's durable agent.
9. Context discipline: offload heavy subtasks (conflict archaeology, log spelunking) to ephemeral in-context subagents; if degraded, `pan handoff` to a fresh session with a state summary (directive's ~message-158 lesson).

In-context dispatch tier (`chooseDispatchTier`, work.md:96-97) survives for cheap slices; `sync-sources/rules/work-agents-via-pan.md` gains the explicit carve-out (§11 item 41).

## 4. Requirements

### Functional

- **FR-1** `pan swarm <id>` spawns (or attaches to) the foreman `agent-<issue>` as a registered work agent; it never directly dispatches slots. Live-foreman idempotency: message, don't double-spawn.
- **FR-2** `pan swarm dispatch` performs exactly one gated dispatch pass with all existing guards (occupancy, duplicate-spawn, overlap, capacity, claim-before-spawn with rollback) and structured `--json` output.
- **FR-3** `pan swarm merge` performs single-slot verify+merge with marker precedence, task-door `done`, marker clear, agent reap, tiered hooks; conflicts produce a durable `failedMergeBlock` and a non-zero exit.
- **FR-4** `pan swarm wait` blocks until a slot lifecycle transition or timeout and reports the delta.
- **FR-5** `pan swarm status` gains `--json`, foreman identity/liveness, `swarm.hold`, and intervention counters.
- **FR-6** **Blocker gate:** the dispatch gate refuses to claim an item whose `blocks` parents are not all done/merged — even when invoked with explicit arguments. (PAN-3679 invariant #1.)
- **FR-7** **Live-slot gate:** merge/reconcile never classifies a slot merged while its task is live; polyrepo-aware: merged status derives from the slot's concrete repo branches through the merge door, never root-branch ancestry of a sparse workspace. (PAN-3679 invariant #2 — coordinate with that issue's fix; whichever lands first, the invariant and its test live here.)
- **FR-8** All Deacon autonomous coordination is removed: patrol call (`deacon.ts:3006`), reactive fast-path (`service-reactive.ts:467`), slot-done fast path (`deacon.ts:2190`), and CLI pass-through (`swarm.ts:156`, `:206`). The reactive/slot-done paths deliver `[swarm-event]` messages to the foreman instead.
- **FR-9** `finalizeSwarmIssueIfComplete` and the Deacon's direct review-request are deleted; the foreman finalizes via `pan done <issue>`.
- **FR-10** `swarm.hold` is a dedicated record field written by freeze/stop/reset and checked by every mutating gate; `deaconIgnored` is no longer written by swarm commands.
- **FR-11** Foreman liveness: the janitor respawns a dead foreman on a swarm-active, un-held issue; ≥3 consecutive failures → freeze + halt report.
- **FR-12** Stall detection emits events to the foreman; `recordStalledSlotRecovery` (auto recovery-block writing) is removed.
- **FR-13** `pan swarm recover` gains `--action reclaim` (archive attempt → unblock → foreman-serial take-over); `retry`/`drop`/`handoff` keep current semantics through the gate.
- **FR-14** Intervention cap: the recover gate counts per-slot-per-failure-class interventions durably; the 4th refuses without `--operator`.
- **FR-15** Synthesis slots are removed; convergence items receive a foreman-composed in-context digest.
- **FR-16** `pan start` on a swarm-active issue attaches/respawns the foreman instead of refusing.
- **FR-17** Auto mode: with `swarm.mode` `auto`/`always` and readiness eligible, the janitor may auto-spawn a **foreman** (never slots). `resolveAutomaticSwarmPolicy` (`src/lib/swarm-policy.ts:36`) gates foreman auto-spawn, not patrol coordination. `autoAdvance` semantics per D-9.
- **FR-18** Completion inference observation state moves to the per-issue record; the Deacon-side completion nudge (`defaultSendCompletionNudge`, `deacon-swarm-completion.ts:143`) is removed; nudging is a foreman duty.
- **FR-19** Docs, skills, rules, and diagrams updated per the §11 no-loss audit; the audit is the merge gate for the doc work item.

### Non-functional

- **NFR-1** Derive-don't-store, with an explicit durable allowlist (all per-issue record fields through the record door): `swarm.slotCompletions`, `swarm.slotAssignments`, `swarm.failedMergeBlock(s)`, `swarm.supersededAttempts`, `swarm.finalizedAt` (existing; `docs/AGENT-STATE-PLANES.md:21-28`), plus new `swarm.hold`, `swarm.interventions`, `swarm.completionObservations`. Nothing else persists.
- **NFR-2** Single mutator: only gated commands mutate swarm state. The four-entry-point race is structurally gone; gates additionally take a coarse per-issue advisory file lock so an operator-invoked gate and a foreman-invoked gate cannot interleave one issue's mutation.
- **NFR-3** Server-reachable code stays async-only: `sendKeysAsync`, `execAsync`/`spawn`; no `execSync` (PAN-70); delays via `await new Promise(r => setTimeout(r, ms))`.
- **NFR-4** Every retry/backoff/stall/wait test uses `vi.useFakeTimers()` + `advanceTimersByTimeAsync`; never real timers; never `maxForks: 1` masking (configs keep `maxForks: 4`).
- **NFR-5** Single write door: item status only via the task door (`applyTaskStatusChange`, `src/lib/pan-dir/task-door.ts:105`); records only via the record door; no direct store access.
- **NFR-6** Worktree discipline: slot worktrees only via `ensureRegisteredSlotWorktree`; no `git checkout` inside workspaces; the foreman verifies `git branch --show-current` before feature-branch edits.
- **NFR-7** Node 22 only for the dashboard/deacon bundle; `npm run build` before restart; **the patrol change is a boot-path change** — runtime-boot-test on a throwaway instance and restart with `pan restart --health-timeout 120`; never hot-patch the live server.
- **NFR-8** Foreman model routing via Cloister; no `--model` in any spawn call unless operator-passed; no hardcoded model fallback anywhere in the foreman path.
