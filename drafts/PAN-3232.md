# PAN-3232 — Pending-input rendering drops the data the store already has

**Issue:** https://github.com/eltmon/overdeck/issues/3232
**Planning mode:** `--auto` (non-interactive; defaults recorded in autoDecisions)
**Verified against:** `feature/pan-3232` @ `2a487b4fb3` (2026-07-28). Every file/line
reference below was re-verified against this tree, not cited from the issue body.

## Glossary

- **Enrichment poller** — `src/dashboard/server/services/agent-enrichment-service.ts`; polls
  every ~3s and emits `agent.enrichment_changed` domain events carrying
  `hasPendingQuestion`, `pendingQuestionPrompt`, `pendingQuestionReason`,
  `pendingInputKinds`, etc. The event reducer copies these onto the store's
  `agentsById` snapshots (`packages/contracts/src/event-reducers.ts:385`).
- **Pending-input kinds** — the unified vocabulary (PAN-1520) for blocking surfaces:
  `askUserQuestion`, `permissionRequest`, `exitPlanMode`, … Labelled by
  `PENDING_INPUT_KIND_LABEL` in `src/dashboard/frontend/src/lib/pendingInput.ts:23`
  (`permissionRequest` → "Permission pending", `askUserQuestion` → "Question waiting").
- **Session tree** — the per-project sidebar tree served by
  `src/dashboard/server/routes/projects.ts` (`ProjectSessionTree` of `SessionNode`s),
  cached in React Query under key `['session-trees', …]` and live-patched by
  `SessionTreeDelta`s streamed over `/ws/rpc` (`subscribeProjectSessionTree`).
- **Activity route** — `GET /api/command-deck/activity` in
  `src/dashboard/server/routes/command-deck.ts`; feeds the issue view via
  `useActivityQuery` → `toSessionNode` (`src/dashboard/frontend/src/components/issue-view/useIssueView.ts:81`).
- **Decisions rail** — the pending-decision list built by `useDecisions()`
  (`src/dashboard/frontend/src/lib/useDecisions.ts`) and rendered by
  `src/dashboard/frontend/src/components/DecisionsPanel.tsx`.
- **Channels map** — `channelPermissionRequestsById`, populated only by the legacy
  Claude Code Channels MCP bridge. Permanently empty under the PTY supervisor
  (the default transport), so any surface deriving permission state solely from it
  never fires.
- **awaitingInputFromProjection** — helper duplicated in both routes
  (`routes/projects.ts:91`, `routes/command-deck.ts:217`) that converts an
  `AgentSnapshot`'s `hasPendingQuestion`/`pendingQuestionReason`/`pendingQuestionPrompt`
  into an `AwaitingInputDetection | null`.

## Problem

PAN-3068/3070/3051 made detection and classification work: for a live blocked agent the
store's `agentsById` snapshot carries `hasPendingQuestion: true`,
`pendingQuestionReason: 'tool_permission'`, `pendingInputKinds: ['permissionRequest']`,
and the full prompt text in `pendingQuestionPrompt`. Every defect below is the render
layer dropping data that is already present client-side (or already computed server-side).

All five issue claims were re-verified against this tree; two corrections:

1. **SessionPanel path** — the file is
   `src/dashboard/frontend/src/components/CommandDeck/SessionView/SessionPanel.tsx`
   (not `components/SessionPanel.tsx`). The cited line numbers hold (`hasPendingPermission`
   at :227, hardcoded `kinds` ternary at :338).
2. **AgentCard is already fixed** — `GodView/AgentCard.tsx:222-233` gates on
   `isAwaitingInput(agent, pendingPermissionAgentIds)` (fires from enrichment's
   `hasPendingQuestion`) and its tooltip merges `agent.pendingInputKinds` with the
   Channels-derived kind. No Channels-only defect remains there; defect 3 is scoped to
   SessionPanel only (recorded as AD-4).

## Requirements

### Functional

- **FR-1** — The issue view renders the pending-input triangle, the `waiting` dot state,
  and the "Awaiting user input: <prompt>" tooltip for any session the activity route
  reports as awaiting input.
- **FR-2** — A Decisions card for an agent parked on a prompt renders the actual prompt
  text (first non-empty line at minimum) instead of the constant kind label.
- **FR-3** — A permission prompt surfaced through enrichment is labelled
  "Permission pending" (not "Question waiting") in SessionPanel's indicator.
- **FR-4** — The sidebar session tree's pending-input badge updates from the live
  `agent.enrichment_changed` event (within one enrichment cycle, ~3s), not the 60s poll.
- **FR-5** — Review-orchestrator, reviewer, test, and ship nodes carry
  `awaitingInput`/`awaitingInputPrompt`/`awaitingInputReason`/`pendingInputKinds` in BOTH
  the session tree (`routes/projects.ts`) and the activity route (`routes/command-deck.ts`).
- **FR-6** — `projectPendingInput` (`src/dashboard/server/read-model.ts:267`) is removed
  along with its orphan test (zero production call sites; see AD-1).
- **FR-7** — `NeedsYouStrip.tsx`, `SimpleHomePage.tsx`, and `ConversationDock.tsx` read
  `usePendingInputSubjects()` instead of `selectPendingInputSubjects` (PAN-2765 rule:
  the raw selector is blind to conversations).
- **FR-8** — `docs/ASKUSERQUESTION-DASHBOARD.md` documents the prompt-threading chain,
  the new `pending_input_changed` tree delta, and specialist-node coverage.

### Non-functional

- **NFR-1** — No new polling loops; FR-4 is push-based (delta merge in place, never an
  invalidate-refetch, because the enrichment poller fires every ~3s per agent).
- **NFR-2** — Event-store replay compatibility: any new field on
  `AgentEnrichmentChangedEvent.payload` MUST be `Schema.optional` (append-only store;
  required fields break decode of older persisted events — see events.ts:184-186 comment).
- **NFR-3** — `npm run typecheck`, `npm run lint`, `npm test` all pass; frontend
  type-ratchet scripts stay green.

## Decisions (made here, not left to the executor)

- **AD-1: Remove `projectPendingInput`, don't wire it.** Its doc comment targets the
  bootstrap projection of already-stopped agents, but `agentSnapshotFromOverdeck`
  (`read-model.ts:403-422`) never populates any pending-input field, so there is nothing
  to strip at bootstrap — the invariant is structural. Delete the function, its
  `PendingInputFields` type alias (`read-model.ts:246`), and
  `src/dashboard/server/__tests__/read-model-pending-input.test.ts`.
- **AD-2: Carry `issueId` in the enrichment event payload** (as `Schema.optional(IssueId)`),
  rather than looking up agent→issue in `ws-rpc.ts`. `mapEventToDelta`
  (`ws-rpc.ts:577-580`) early-returns without `payload.issueId` and must stay a pure
  synchronous function; the poller already holds `agent.issueId` when it emits
  (`agent-enrichment-service.ts:301`).
- **AD-3: New delta kind `pending_input_changed`, merged in place client-side.** Do NOT
  reuse the `session_added` invalidate path — that triggers a full refetch and the poller
  re-emits for idle-alive waiting agents (`shouldForceReemitPendingInput`), which would
  refetch-storm. The client merge must be idempotent.
- **AD-4: AgentCard needs no change** (verified above); defect 3 touches SessionPanel only.
- **AD-5: DecisionRow prompt precedence:** AUQ first question → proposed-plan copy →
  enrichment prompt formatted by `getPendingQuestionTitle` (revives the dead code at
  `lib/pipeline-state.ts:35`) → `describePendingInput(kinds)` fallback.
- **AD-6: Specialist fix covers both duplicated route implementations** (session tree and
  activity route), plus `buildReviewerNodes` (`routes/reviewer-tree.ts:314`), which gains
  an optional `agentSnapshotsById` in `BuildReviewerNodesOptions`.

### WI-2 — Decisions rail: thread the prompt into subject → decision → card (FR-2)

   const prompt =
     decision.pendingAskUserQuestion?.questions?.[0]?.question ??

### WI-3 — SessionPanel label: derive kinds from enrichment, not the Channels map (FR-3)

`SessionPanel.tsx:338` hardcodes `kinds={hasPendingPermission ? ['permissionRequest'] :
['askUserQuestion']}` where `hasPendingPermission` (:227) reads the Channels-only
selector — permanently false under the PTY supervisor, so permission prompts are
labelled "Question waiting".

Change: prefer the enrichment-owned kinds already flowing on the tree node
(`session.pendingInputKinds`, set by `routes/projects.ts:321`), then the Channels-derived
kind, then the historical fallback:

```tsx
kinds={session.pendingInputKinds?.length
  ? session.pendingInputKinds
  : hasPendingPermission ? ['permissionRequest'] : ['askUserQuestion']}
```

Keep the `(session.awaitingInput || hasPendingPermission)` mount gate (:333) unchanged —
Channels-sourced permission requests must still light the indicator when enrichment
hasn't caught up.

Tests: `SessionPanel.test.tsx` — a session with `awaitingInput: true,
pendingInputKinds: ['permissionRequest']` and an empty Channels map renders the indicator
with the "Permission pending" label; a session with `awaitingInput: true` and no kinds
still renders "Question waiting".

### WI-4 — Live tree delta for enrichment changes (FR-4, NFR-1, NFR-2)

`mapEventToDelta` (`ws-rpc.ts:577-648`) has no case for `agent.enrichment_changed`, and
the session-tree query (`CommandDeck/index.tsx:278-282`) has no `refetchInterval`, so the
tree's pending-input badge lags up to ~70s (60s global staleness + enrichment cycle).

Changes (one vertical slice, producer to consumer):
1. `packages/contracts/src/events.ts` — add `issueId: Schema.optional(IssueId)` to
   `AgentEnrichmentChangedEvent.payload` (optional per NFR-2).
2. `agent-enrichment-service.ts` — emit `issueId: agent.issueId` in the poller's event
   (:301-310) and thread `issueId` into `buildPendingReapEvent` (:120-135; add a
   parameter, update its callers). If a caller genuinely lacks an issueId, omit the field
   — the tree then converges on the next poll, which is the status quo.
3. `packages/contracts/src/rpc.ts` — extend `SessionTreeDelta` (:226-234): add
   `'pending_input_changed'` to the `kind` literals and optional fields
   `awaitingInput: Schema.optional(Schema.Boolean)`,
   `awaitingInputPrompt: Schema.optional(Schema.String)`,
   `awaitingInputReason: Schema.optional(Schema.String)`,
   `pendingInputKinds: Schema.optional(Schema.Array(Schema.String))`.
4. `ws-rpc.ts` `mapEventToDelta` — add a case:

   ```ts
   case 'agent.enrichment_changed': {
     const agentId = p['agentId'] as string | undefined;
     if (!agentId) return null;
     const kinds = p['pendingInputKinds'] as string[] | undefined;
     return {
       kind: 'pending_input_changed',
       issueId,               // from the payload (step 1); the shared `if (!issueId) return null` guard stands
       sessionId: agentId,
       awaitingInput: p['hasPendingQuestion'] === true,
       awaitingInputPrompt: p['pendingQuestionPrompt'] as string | undefined,
       awaitingInputReason: p['pendingQuestionReason'] as string | undefined,
       pendingInputKinds: kinds,
       timestamp: event.timestamp,
     };
   }
   ```

5. `CommandDeck/index.tsx` `applySessionTreeDelta` (:78-116) — handle
   `pending_input_changed` by merging the four fields onto the matched session (same
   shape as the `status_changed` branch; an absent optional field on the delta must
   still OVERWRITE the session field — a cleared prompt must clear, so spread
   explicit values rather than `!== undefined` guards for this branch). Export
   `applySessionTreeDelta` (add `export`) so it is unit-testable.

Tests: `ws-rpc.test.ts` — `agent.enrichment_changed` with issueId+fields maps to a
`pending_input_changed` delta; without issueId maps to null. A new (or colocated)
frontend test for `applySessionTreeDelta` — applying the delta sets/clears
`awaitingInput` and `pendingInputKinds` on the right session and returns a new object;
a second identical apply is a no-op-safe merge (idempotent, AD-3).

show the triangle + `waiting` state in the issue view with the real prompt in the
tooltip (WI-1); render the actual prompt first line on its Decisions card (WI-2); be

(WI-4). A blocked review/test specialist surfaces pending input through the same fields
