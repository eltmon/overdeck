# PAN-1897 — `pan start` workspace-prep hangs/times out (>120s) on re-entry

**Issue:** https://github.com/eltmon/overdeck/issues/1897
**Mode:** auto planning (no interactive Q&A; decisions recorded in `autoDecisions`)
**Date:** 2026-07-16

## Glossary

- **Prep phase** — everything `pan start` does between printing `Preparing workspace for <id>...` and `Agent spawned:` — state reconcile, workspace resolution, sync-main, validation, prompt build, and `spawnAgent`.
- **sync-main** — `syncMainIntoWorkspace()` in `src/lib/cloister/merge-agent.ts:1259`: auto-commit dirty changes, clean stale git locks, `git fetch origin main`, `git merge origin/main`, conflict handling.
- **Heartbeat** — a periodic plain-text progress line (`[prep] ...`) written to stdout so a non-interactive caller can see which step is running and for how long.
- **Non-TTY caller** — any supervisor running `pan start` without a terminal (the flywheel via Bash, CI, `execAsync`). ora spinners are disabled in this mode.
- **Step budget** — a per-step timeout in milliseconds; exceeding it either fails fast (naming the step) or degrades (warn + continue), depending on the step.
- **Degrade** — the existing sync-failure semantics at `src/cli/commands/start.ts:1054-1064`: `spinner.warn(...)` and continue to spawn so the work agent can resolve the problem itself.

## Root cause (verified 2026-07-16)

Three compounding factors, no hard deadlock (confirmed by the RUN-35 refinement comment: the same start succeeded with a 300s budget under lighter load):

1. **Progress is invisible to non-TTY callers.** All prep progress is communicated via `spinner.text = ...` mutations on an ora spinner created at `src/cli/commands/start.ts:838` (`const spinner = ora(\`Preparing workspace for ${id}...\`).start();`). ora 8 disables rendering when the stream is not interactive (`node_modules/ora/index.js:54` sets `#isEnabled` from `isInteractive({stream})`; `index.js:249` skips rendering when `!this.#isEnabled || !this.#stream.isTTY`). Only `.succeed/.fail/.warn/.info` print lines. So the flywheel saw only the initial `Preparing workspace for PAN-1711...` line while prep was (slowly) progressing — indistinguishable from a hang.
2. **Several prep steps are unbounded.** In `syncMainIntoWorkspace` the git operations have **no `timeout` option**: `git fetch origin main` (`merge-agent.ts:1325`), `git merge origin/main` (`merge-agent.ts:1334`), and the pre-sync auto-commit's `git commit` (`merge-agent.ts:160`) which runs husky hooks (commitlint) under full host load. `getTrackerContext` (`src/lib/cloister/work-agent-prompt.ts:211`) makes tracker API calls with no explicit timeout. `spawnAgent` → `assertWorkspaceStackHealthyForSpawn` (`src/lib/agents/spawn-prep.ts:649`) can run a full inline docker `rebuildWorkspaceStack` (`spawn-prep.ts:780-785`) for work agents — minutes under load.
3. **Outer kill budgets were shorter than honest prep time under load.** RUN-35 ran ~10 agents + devcontainers; 120s/200s outer timeouts killed genuinely progressing preps.

## Requirements

- **FR-1** Every bounded prep phase emits a step-start line observable by non-TTY callers (plain stdout `[prep] <phase>...`), while still updating the ora spinner for interactive users.
- **FR-2** A step running longer than 15s emits periodic still-running heartbeat lines (`[prep] still running: <phase> (Ns elapsed)`) at most every 15s, in non-TTY mode.
- **FR-3** Each bounded prep phase has a step budget. On exceeding it: `state-reconcile` and `spawn` fail fast with an error naming the phase and elapsed time (exit non-zero); `sync-main` and `tracker-context` degrade (warn naming the phase, continue to spawn).
- **FR-4** The git operations inside `syncMainIntoWorkspace`/`autoCommitWorkspaceChangesBeforeSync` carry explicit `execAsync` timeouts, and a timeout produces `success:false` with a reason naming the specific git operation and its budget — never an indefinite wait. A timed-out merge attempts `git merge --abort` best-effort.
- **FR-5** `sync-sources/skills/pan-start/SKILL.md` documents the heartbeat lines, the per-phase budgets, the fail-fast vs degrade split, and advises outer supervisors to budget ≥300s for `pan start` under load.
- **NFR-1** All timeout/heartbeat tests use `vi.useFakeTimers()` + `advanceTimersByTimeAsync` — no real waits (repo fake-timers rule).
- **NFR-2** No new `execSync` in server-reachable code; `merge-agent.ts` stays async-only.
- **NFR-3** `SyncMainResult` return shape is unchanged (the function is shared with `src/dashboard/server/routes/workspaces/merge-ops.ts:273`).

## Decisions (auto mode)

- **D1 — Heartbeat + bounded steps, not prep parallelization.** The issue comment names two fix directions and calls the heartbeat/timeout direction the likely one ("rather than unstick a deadlock"). Parallelizing/speeding prep (bun caching, concurrent fetch) is deferred as a NonGoal — it's an optimization on top of, not a substitute for, bounded observable prep.
- **D2 — Budgets are constants, no new CLI flags.** `--prep-timeout` style configurability wasn't requested; constants in one module keep the skill/help surface unchanged (no `lint-skills.sh` churn). Values: state-reconcile 60s, sync-main outer 240s (inner: fetch 60s, merge 120s, auto-commit 60s, other git status ops 30s), tracker-context 60s, spawn 600s (docker rebuild is legitimately slow), heartbeat interval 15s.
- **D3 — Timeout ≠ always fatal.** sync-main already degrades on failure (start.ts:1054-1064 warns and continues so the agent resolves conflicts, PAN-1872); a sync-main *timeout* takes the same degrade path. Tracker-context timeout degrades to an empty tracker section (getTrackerContext already returns fallback strings on other errors). state-reconcile and spawn timeouts fail fast: proceeding without state reconcile violates the migration gate, and a spawn that exceeded 600s has no degraded mode.
- **D4 — Wrapper module lives in the CLI layer** (`src/cli/commands/start-prep-progress.ts`) because it owns ora/non-TTY presentation. The bounded-git-ops change lives in `merge-agent.ts` because it must protect *all* callers of sync-main, including the dashboard route.

## Work items

### W1 — Prep progress module (`start-prep-progress.ts`) — traces FR-1, FR-2, FR-3, NFR-1

New file `src/cli/commands/start-prep-progress.ts` exporting:

```ts
export interface PrepProgress {
  update(text: string): void;            // spinner.text + non-TTY "[prep] <text>" line
  step<T>(name: string, budgetMs: number, fn: () => Promise<T>): Promise<T>;
}
export function createPrepProgress(spinner: Ora, opts?: { stream?: NodeJS.WriteStream; heartbeatMs?: number }): PrepProgress;
export class PrepStepTimeoutError extends Error { constructor(readonly stepName: string, readonly budgetMs: number, readonly elapsedMs: number) { ... } }
```

Behavior: `update` always sets `spinner.text`; when the stream is not a TTY it also writes `[prep] <text>\n`. `step` emits a start line, starts a 15s `setInterval` heartbeat (`[prep] still running: <name> (Ns elapsed)`, non-TTY only), races `fn()` against a `setTimeout(budgetMs)`, clears both on settle, emits a completion line with elapsed seconds, and rejects with `PrepStepTimeoutError` on budget exhaustion (the message must name the step and budget: `Prep step 'sync-main' exceeded its 240s budget`). Note the raced `fn()` keeps running after a timeout — callers decide whether to exit (fail-fast) or continue degraded; that is acceptable because the fail-fast paths exit the process and the degraded paths tolerate late completion.

Tests: new `tests/unit/cli/start-prep-progress.test.ts` with fake timers covering: non-TTY line emission, TTY suppression of `[prep]` lines, heartbeat cadence, timeout rejection naming step+budget, in-budget resolution.

## NonGoals

- No parallelization or caching of prep steps (bun install, concurrent fetch) — follow-up optimization.
- No new CLI flags or config keys for budgets.
- No changes to the remote/fly.io workspace path or the planning-session (start-planning) streaming path.
- No global whole-command watchdog; bounds are per-step.
- No changes to the flywheel's own outer command budgets (guidance only, in docs).

## Hazards

- **H1** A timed-out raced promise keeps running; degraded paths must tolerate late completion (sync-main writing after we moved on). Mitigation: degrade paths mirror the existing sync-failure semantics which already tolerate a dirty-but-recoverable workspace; fail-fast paths exit the process.
- **H2** exec timeout kills git mid-op and can leave `.git` locks or `MERGE_HEAD`. `cleanupStaleLocks` (called at the top of sync-main) reaps stale locks on the next run; the merge-timeout path runs `git merge --abort` best-effort.
- **H3** `syncMainIntoWorkspace` is shared with the dashboard route `merge-ops.ts:273` — keep `SyncMainResult` shape unchanged; only reasons get more specific.
- **H4** ora TTY mode: `[prep]` lines must not double-print for interactive users (gate on `stream.isTTY`).
- **H5** Fake-timers rule: any test touching the heartbeat interval or budgets must use `vi.useFakeTimers()`; never real waits (repo-wide OOM history).
- **H6** RTK output compression may garble heartbeat lines when agents read them — trust exit codes, not line-diffing, in verification.
