## Glossary

- **Pipeline membership** — the boolean fact "is this issue in the pipeline," plus a classification bucket. Defined by the exception-queue model: an issue is in the pipeline iff its all-up state is not provably a clean terminal state.
- **Resolver** — `resolvePipelineMembership(signals)` in `src/lib/pipeline-membership.ts:85`. A pure function from durable lens signals to a `PipelineMembership` verdict. Already shipped with 8/8 unit tests (`src/lib/__tests__/pipeline-membership.test.ts`).
- **Lens signals (`IssueLensSignals`)** — the durable inputs (`src/lib/pipeline-membership.ts:29`): `issueOpen` (L3), `hasOpenPr` (L1), `hasMergedPr` (L1-merged, the squash-merge oracle), `hasConventionBranch`, `branchUnmerged` (L2), `phaseLabel` (L4). This PRD adds `hasVbriefSpec` (L6-spec).
- **L5** — the disposable runtime plane: SQLite `overdeck.db` (`review_status`, `agents` tables), `state.json`, tmux liveness. L5 may annotate; it must NEVER decide membership (FR-2).
- **Buckets** — `in_flight | zombie_pr | post_merge_limbo | planned_backlog | clean_terminal` (`PipelineBucket`, `src/lib/pipeline-membership.ts:49`). Only `clean_terminal` is out of the pipeline.
- **Read door** — the single sanctioned read path for a domain (single-source-of-truth tenet). For pipeline membership: the lib pair `gatherProjectLensSignals` + `resolvePipelineMembership`, surfaced over HTTP as `GET /api/pipeline/membership` and on the issue DTO as `pipelineMembership`.
- **Gatherer** — new module `src/lib/pipeline-membership-gather.ts` that batch-collects `IssueLensSignals` for a whole project from durable sources only.
- **No-loss audit** — the bundled refactor rule: enumerate everything each old surface exposes and prove the new surface covers it, gated by a focused test, never by memory.

## Requirements

- **FR-1** — One resolver returns the authoritative pipeline set with per-issue bucket. Planned issues (a vBRIEF spec exists) are members (operator comment 2026-07-16: plans encode code paths that age).
- **FR-2** — Membership derives only from durable signals (git + GitHub + specs-on-git). L5 annotates, never decides.
- **FR-3** — L2 (`branchUnmerged`) is always paired with the merged-PR oracle so squash-merges are never mis-flagged unmerged. (Already in the shipped resolver, `src/lib/pipeline-membership.ts:88`; the gatherer must feed both signals.)
- **FR-4** — Label drift detected in both directions: stale-present (pipeline phase label on a terminal/closed issue) and stale-absent (open PR with no phase label). Shipped as an additive `labelDrift` annotation, not new buckets.
- **FR-5** — All 6 sites delegate to the resolver; none computes membership independently. Enforced by a no-loss audit test AND an import-boundary lint guard.
- **NFR-1** — Cutover-safe: the gatherer+resolver path reads nothing from `overdeck.db`/`state.json`/tmux, verified mechanically by an import-graph assertion — NEVER a destructive "delete `~/.overdeck` and observe" test (bundled rule: no-destructive-acceptance-tests).

## Decisions (made here — do not re-litigate downstream)

1. **Planned lens = spec presence, not the label.** `hasVbriefSpec` is filled via `findSpecByIssue` (`src/lib/pan-dir/specs.ts:224`; sync variant `src/lib/vbrief/lifecycle-io.ts:110`). The GitHub `planned` label is applied on a swallowed-failure path (`src/lib/overdeck/planning-promotion.ts:645–646`, wrapped in `Effect.catch(() => Effect.void)`) and is stripped by `label-reconciler.ts` / `close-issue.ts:36` — hint only. Specs live on the `overdeck-state` git branch (durable, re-creatable from origin), which satisfies FR-2 even though the local checkout path is under `${OVERDECK_HOME}`.
2. **No `orphan_branch` bucket.** Shipped PAN-1980 §2d stands: closed issue ⇒ `clean_terminal` regardless of leftover branch/label/agent state, except an open PR (`zombie_pr`). The issue body's original bucket list predates the shipped resolver.
3. **Read door transports:** out-of-process consumers (pipeline-status skill, flywheel orchestrator) use `GET /api/pipeline/membership`; `pan pending` calls the lib directly so the CLI works with the dashboard down. Same single module computes either way.
4. **Merged-PR gathering is batched:** one `gh pr list --state merged --json headRefName,mergedAt --limit 500` per project; never per-issue calls. `isBranchMerged` (`src/lib/close-out.ts:97`, squash-aware) is the per-branch fallback pattern.
5. **Resource-discovery no-loss:** an issue with live resources but a `clean_terminal` verdict is still emitted, flagged as orphan-resource drift — the Command Deck tree loses nothing silently.
6. **Frontend gate moves, lanes stay:** the server computes membership onto the issue DTO; `getPipelineIssuePhase` lane assignment for in-pipeline issues is unchanged.

## Intersecting repo rules (restated for the executor)

- No `execSync` in server-reachable code — async exec only (`execAsync`/`spawn`), PAN-70. The gatherer and endpoint are server-reachable.
- After editing `packages/contracts/`, rebuild: `cd packages/contracts && npm run build` before frontend typecheck.
- Skill edits: `sync-sources/skills/.../SKILL.md` is the source of truth; keep `scripts/lint-skills.sh` (in `npm run lint`) green.
- Delay/retry tests use fake timers (`vi.useFakeTimers()`); the TTL-cache test in the endpoint item must not sleep real time.
- Quality gates before `pan done`: `npm run typecheck`, `npm run lint`, `npm test`.
- Never write a destructive recovery acceptance test.

## Acceptance criteria (issue-level, mechanically checkable)

- `git grep -l resolvePipelineMembership` includes all six sites (or their DTO/endpoint delegation), and the audit test proves no independent membership math remains.
- Drift cases classify per the table: closed+openPR→`zombie_pr`; open+mergedPR→`post_merge_limbo`; open+spec-only→`planned_backlog`; squash-merged→`post_merge_limbo`; closed+branch-only→`clean_terminal`.
- The gatherer's import graph contains no DB/review-status/agent-state/tmux modules (test + lint guard) — the mechanical form of "deleting the runtime plane does not change the result."
- `npm run lint` runs the FR-5 boundary guard and passes.
