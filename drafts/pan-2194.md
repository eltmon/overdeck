# PAN-2194 — Mechanically prevent the Flywheel orchestrator from authoring/committing artifacts

**Issue:** [PAN-2194](https://github.com/eltmon/overdeck/issues/2194)
**Planning agent:** claude-opus-4-8 (auto mode)
**Date:** 2026-07-03

## Glossary

- **Flywheel orchestrator** — the singleton "Fix-All Flywheel" agent (`OVERDECK_AGENT_ID=flywheel-orchestrator`, role `flywheel`, prompt `roles/flywheel.md`). It *dispatches* pipeline agents (`pan plan`/`start`/`strike`/`review`) and emits status. It must **never author content itself**.
- **Implementer harness** — a coding harness built to edit files and run git (codex/gpt-5.5, claude-code work agents). The orchestrator runs on whatever harness its configured model routes to (`resolveHarness({ model })`, `src/cli/commands/flywheel.ts:228`).
- **PreToolUse hook** — a Claude Code settings.json hook that runs before a tool call and may return `permissionDecision: "allow" | "deny"`. **Claude-code only** — codex/pi do not honor Claude Code hooks.
- **Git-level hook** — a `.husky/pre-commit` / `.husky/pre-push` hook. Runs on **any** `git commit`/`git push` in the repo regardless of which harness invoked git (`core.hooksPath=.husky`). **Harness-agnostic.**
- **Allowlist** — the exact set of repo paths the orchestrator's *own shell* is permitted to commit/write. Everything else is refused.
- **FLYWHEEL-STATE.md** — `docs/FLYWHEEL-STATE.md`, the orchestrator's durable cumulative memory. It commits this file to `main` every tick (e.g. `af4e8eec54`, `9dbf84d47c`). This is the one file it legitimately authors.

## Problem

The flywheel orchestrator (RUN-45, running on **codex**/gpt-5.5) edited `.pan/drafts/PAN-1791.md`, authored a 437-line vBRIEF spec, and **committed + pushed both to `main`** (`862eebfc9c`), bypassing the entire pipeline (no plan agent, no review). An orchestrator must only *dispatch*; it must never produce artifacts itself.

The role prompt was hardened (`2616a4c083`) so it now forbids editing/committing **any** file except `docs/FLYWHEEL-STATE.md` + the status snapshot. But **the prompt is the only lever today**, and two mechanical gaps remain:

1. **The pre-push guard doesn't cover artifact paths.** `scripts/guard-agent-main-push.sh:51` only refuses agent pushes touching `^(src|packages|roles|skills|scripts)/`. The incident staged `.pan/drafts/*` and `.pan/specs/*.vbrief.json` — neither matches, so the push to `main` was allowed. (Verified: `git show --stat 862eebfc9c` → `.pan/drafts/PAN-1791.md`, `.pan/specs/…foreman-independent…vbrief.json`.)
2. **There is no commit-time guard at all**, and on codex there is no PreToolUse interception (Claude Code hooks don't govern codex's own file/git tools). On **claude-code**, `sync-sources/hooks/auto-approve-hook:63-64` actually *auto-approves every* `flywheel-*` tool call (it's headless), so there is no gate there either.

## Key discovery — a harness-agnostic guard IS possible

The issue framed this as "mechanical guard **or** non-implementer harness", worrying that codex can't be governed. That worry is specific to *Claude Code PreToolUse hooks*. **Git hooks are harness-agnostic**, and crucially `OVERDECK_AGENT_ID=flywheel-orchestrator` reaches the codex agent's shell environment:

- `src/lib/runtimes/codex.ts:567` sets `OVERDECK_AGENT_ID: agentId` in the codex spawn env.
- `src/lib/launcher-generator.ts:273` exports `OVERDECK_AGENT_ID` in every launcher.
- `FLYWHEEL_ORCHESTRATOR_AGENT_ID = 'flywheel-orchestrator'` (`src/lib/cloister/flywheel.ts:25`).

Therefore a `.husky/pre-commit` guard keyed on `OVERDECK_AGENT_ID=flywheel-orchestrator` that inspects staged paths against an allowlist **mechanically blocks the exact incident on codex, claude-code, and pi alike** — no harness change, no codex sandbox restriction, no violation of the "let Cloister route models / never hardcode a model fallback / never force `--harness claude-code` for CLIProxy models" rules.

### The allowlist boundary (verified)

- The orchestrator's own shell **legitimately commits only** `docs/FLYWHEEL-STATE.md` (its memory). The status snapshot is emitted over HTTP via `pan flywheel emit-status`, never committed.
- The `chore(beads): sync beads state` / `chore(state): batch update` commits are **server-side**, produced by the deacon patrol via `queueAutoCommit` (`src/lib/pan-dir/auto-commit.ts:194`, debounced `setTimeout` flusher `:162,214`). They run in the dashboard-server process, which does **not** set `OVERDECK_AGENT_ID=flywheel-orchestrator`, so the guard never evaluates them.
- The incident paths (`.pan/drafts/**`, `.pan/specs/**`) and all code paths are **not** in the allowlist → refused.

**Allowlist (shared by all three guards):** a staged/written repo path is permitted for the orchestrator only if it is `docs/FLYWHEEL-STATE.md` or under one of the state directories `.pan/records/`, `.pan/continues/`, `.pan/backlog/`, `.beads/`. Everything else is refused. The state directories are included as a **safe superset**: they hold pipeline state, never authored content, so allowing them cannot reproduce the incident, while ensuring the guard never false-positives if an orchestrator-run CLI command (e.g. `pan close`) commits state in-process.

## Proposal

Three complementary guards + a docs update. Guard 1 is load-bearing; Guards 2–3 are defense-in-depth.

1. **Git pre-commit guard (load-bearing, harness-agnostic).** New `scripts/guard-flywheel-orchestrator-commit.sh`, wired into `.husky/pre-commit` (currently empty). When `OVERDECK_AGENT_ID=flywheel-orchestrator`, it reads `git diff --cached --name-only` and refuses the commit if any staged path is outside the allowlist.
2. **Git pre-push backstop.** Broaden `scripts/guard-agent-main-push.sh` so that, for the orchestrator specifically, a pushed range touching any path outside the allowlist is refused (closes gap #1 — vBRIEF/PRD pushed to `main`).
3. **Claude-code PreToolUse Write/Edit deny (defense-in-depth).** Extend `sync-sources/hooks/auto-approve-hook` so that for `flywheel-*` a `Write`/`Edit`/`MultiEdit` whose target is inside the repo and outside the write-allowlist is `deny`ed *before* the file is authored. (Commit/push policing stays with the git hooks, which inspect staged paths precisely and work on codex too.)
4. **Document the guard** in `roles/flywheel.md` and `docs/FLYWHEEL.md`: the write/commit ban is now mechanically enforced and harness-agnostic.

### Why not the alternatives the issue floated

- **Codex read-only sandbox** (`sandbox_mode=read-only`, `toCodexSandboxValue`, `src/lib/runtimes/codex.ts:255`) would block the orchestrator's *legitimate* `docs/FLYWHEEL-STATE.md` write and could break `pan` dispatch that writes under `~/.overdeck`. Rejected.
- **Forcing a non-implementer harness/model** would violate `never force --harness claude-code for a CLIProxy model`, `let Cloister route models`, and `never hardcode a model fallback`. The harness-agnostic git guard makes a harness restriction unnecessary. Rejected.

## Requirements

- **FR-1** — When `OVERDECK_AGENT_ID=flywheel-orchestrator`, a `git commit` staging any path outside the allowlist is refused with a non-zero exit and a message naming the offending paths.
- **FR-2** — When `OVERDECK_AGENT_ID=flywheel-orchestrator`, a `git commit` staging only allowlisted paths (e.g. `docs/FLYWHEEL-STATE.md`) succeeds.
- **FR-3** — When `OVERDECK_AGENT_ID` is unset or any non-orchestrator value, the pre-commit guard is a no-op (exit 0) — it never affects work agents, humans, or server-side commits.
- **FR-4** — The pre-push guard refuses an orchestrator push whose range touches any path outside the allowlist (including `.pan/drafts/**` and `.pan/specs/**`), while still allowing an allowlisted-only range.
- **FR-5** — On claude-code, a `flywheel-*` `Write`/`Edit`/`MultiEdit` to a repo path outside the write-allowlist returns `permissionDecision: "deny"`; a write to `docs/FLYWHEEL-STATE.md` (or outside the repo) is still auto-approved; non-flywheel agents are unaffected.
- **NFR-1** — All guards are keyed on `OVERDECK_AGENT_ID=flywheel-orchestrator`, so they are harness-agnostic (codex/claude-code/pi) and never touch server-side or human commits.
- **NFR-2** — Guards fail closed on refusal but never crash the git operation on internal error paths for non-orchestrator sessions (mirror `guard-agent-main-push.sh` style: precise, exit-0 for out-of-scope).

## Non-Goals

- Restricting or changing the orchestrator's harness/model, or adding a codex sandbox restriction. The guard is harness-agnostic; routing stays config-driven.
- Fixing `pan flywheel stop` reporting success without killing the session (the "gate-drift/headless" bug named in the issue) — **file separately**.
- The codex sandbox `/api` limitation / sandbox-safe CLI surfaces (sibling issue).
- Defending against a deliberate `git commit --no-verify` bypass — out of scope; branch protection / CI on `origin/main` is the ultimate backstop. Recorded as a hazard.
- Blocking working-tree edits on codex (no PreToolUse there); the git-commit guard prevents the durable artifact, and dirty primary-worktree files are discarded by the deacon.
