## Glossary

- **Flaky test** — a test that fails non-deterministically for environmental/timing reasons, not code regressions. See the PAN-2373 flake-policy PRD for the quarantine mechanism this issue depends on.
- **`conversation-supervisor-uat.test.ts`** — the file at `tests/playwright/conversation-supervisor-uat.test.ts`. Contains two tests: `'resumes Codex conversations through the real route with codex resume'` and `'delivers through real conversation routes and keeps plain forks off Channels MCP'`. The flake is in the second test.
- **`#create` button** — a `<button id="create">New conversation</button>` element in the static test HTML served by the embedded HTTP server (`pageHtml()` function in the test). Its `onclick` calls `POST /api/conversations`.
- **Playwright locator** — `page.locator('#create')` returns a Playwright locator. `.click()` implicitly waits up to the action timeout (default 30s in this test's 45s test timeout) for the element to be visible and enabled before clicking. The flake manifests as this implicit wait exhausting the 30s budget.
- **`startRealConversationRoutes()`** — the `beforeEach` helper (defined in the test file) that: (1) dynamically imports `conversationsRouteLayer` and `setupTerminalWebSocket`, (2) creates a Node `http.Server`, (3) calls `setupTerminalWebSocket(httpServer)`, and (4) awaits `httpServer.listen(0, '127.0.0.1', callback)`. The resolved `baseUrl` is available to tests after this completes.
- **Chromium cold-start** — `browser = await chromium.launch()` in `beforeEach` launches a headless Chromium instance. In CI, this can take 3–8 seconds. After launch, `context.newPage()` creates a new page before any navigation.
- **Quarantine** — the mechanism from PAN-2373 (`scripts/flaky-quarantine.txt`) that excludes this test from the blocking verification gate while it remains flaky. This fix removes the need for quarantine; the quarantine entry is removed when the test is green 20× in CI.

## Problem (verified 2026-07-04)

The second test `'delivers through real conversation routes and keeps plain forks off Channels MCP'` timed out in the Cloister verification gate, blocking [PAN-2231](https://github.com/eltmon/overdeck/issues/2231) (a lint-rule change, provably orthogonal) through 3/3 verification cycles, pushing it to `verification_stuck`. GitHub CI shows the test green, confirming it is an environmental/timing flake — not a code regression.

**Verified failure location** (read from the test file at line ~340 in `tests/playwright/conversation-supervisor-uat.test.ts`):

```ts
await page.goto(baseUrl);
await page.locator('#create').click();   // ← timeout here (30s exhausted)
```

**Root cause analysis:** The `#create` button is statically present in the HTML served by the embedded HTTP server — it cannot be absent from a successfully loaded page. The 30s Playwright action timeout (the default for `locator.click()`) should be more than sufficient for a static element. The failure occurs when `page.goto(baseUrl)` does not result in a properly loaded page.

The mechanics: `startRealConversationRoutes()` performs two dynamic `await import(...)` calls (for `conversationsRouteLayer` and `ws-terminal`) inside `beforeEach`. These dynamic imports may re-evaluate a large module graph on each test run (because `vi.resetModules()` is called at the top of `beforeEach`). In CI on slow machines, module re-evaluation + Chromium cold-start + `page.goto()` exhausts enough wall-clock time that Playwright's connection to the embedded server may fail or return an error document — which contains no `#create` element. The `page.locator('#create').click()` then burns its 30s budget waiting for an element that is absent from the error document.

**Evidence:** GitHub Actions CI passes (no Chromium cold-start overhead, pre-warmed module cache); the verification gate (which runs inside the dashboard server process with different module caching behavior and CPU contention from the running server) fails.

## Requirements

- **FR-1** — The second test must add an explicit `waitFor({ state: 'visible' })` on `#create` BEFORE calling `.click()`, so the wait semantics are clear and the timeout surfaces a specific cause.
- **FR-2** — The test must also verify that `page.goto(baseUrl)` produced a valid page (not an error document) by checking that `page.url()` matches `baseUrl` after navigation.
- **FR-3** — The `#create` click interaction must use a reduced explicit timeout (15s) for the `waitFor`, not the default 30s, so a genuine failure is reported faster with a clear locator message.
- **FR-4** — The quarantine entry for this file in `scripts/flaky-quarantine.txt` must be REMOVED once the test passes 20 consecutive times in CI without a retry. The quarantine file is created by PAN-2373; see the Re-verify section below.
- **NFR-1** — No new test logic, mocks, or assertions beyond the readiness wait and URL check. The fix is surgical.
- **NFR-2** — No new explicit `any`. No `execSync`. No real-timer sleeps; this test does not use fake timers (it exercises Playwright/HTTP I/O — fake timers would break WebSocket and `fetch` timing).

## Work items

### W1 — Add explicit readiness wait before `#create` click (FR-1, FR-2, FR-3)

**File:** `tests/playwright/conversation-supervisor-uat.test.ts`

Locate the second `it(...)` block. Grep anchor (unique string in the file):
```ts
  it('delivers through real conversation routes and keeps plain forks off Channels MCP', async () => {
    await page.goto(baseUrl);
    await page.locator('#create').click();
```

**Before:**
```ts
    await page.goto(baseUrl);
    await page.locator('#create').click();
```

**After:**
```ts
    await page.goto(baseUrl);
    // Verify the page loaded correctly — if the HTTP server returned an error
    // document (timing race during module init), the URL would differ.
    if (page.url() !== baseUrl) {
      throw new Error(`page.goto did not reach baseUrl — got: ${page.url()}`);
    }
    // Wait explicitly for #create to be visible before clicking.
    // The button is always present in the static HTML; this makes the wait
    // semantics clear and surfaces failures faster with a locator-level message.
    await page.locator('#create').waitFor({ state: 'visible', timeout: 15_000 });
    await page.locator('#create').click();
```

**Rationale:** `page.locator('#create').waitFor({ state: 'visible', timeout: 15_000 })` is semantically identical to the implicit wait in `.click()`, but it: (1) surfaces failures with a `locator.waitFor` error that names the missing element, (2) uses a 15s budget so failures are reported sooner, and (3) makes the test's timing contract explicit. This pattern is recommended by Playwright docs for tests where element visibility timing is known to vary by environment.

### AD-1 — Approach: harden the test in place (adopt W1), not "move it out of the suite"
The issue lists three acceptable fixes (stabilize the locator wait / gate behind a
readiness check / move out of the blocking suite). The existing PRD (W1) and the
issue's option 1 both endorse the readiness-wait approach. Verified this session:
the on-host verification gate runs its `test` quality-gate command from
**machine-local `~/.overdeck/projects.yaml`** (loaded via `OVERDECK_HOME` in
`src/lib/projects.ts:18`), NOT the repo's `.overdeck/projects.yaml`. Therefore a
repo PR **cannot** change the gate command to exclude this test — the only
repo-controllable levers are the test file itself or the root `vitest.config.ts`
include/exclude topology. Single-file test hardening is the lowest-risk,
repo-PR-able fix and matches the authoritative draft. Chosen.

### AD-2 — Drop W2 (quarantine removal); it depends on a mechanism absent from this repo
Verified this session: `scripts/flaky-quarantine.txt` **does not exist** and there

### AD-3 — Strengthen the navigation guard: assert `goto` response is OK, not just URL equality
The draft's own Re-verify note flags that `page.url() !== baseUrl` is fragile
(trailing-slash normalization). The draft's root-cause hypothesis is that
`page.goto` lands on an **error document** during heavy `beforeEach` init. The
direct, robust check for that is to capture the `Response` returned by
`page.goto(...)` and assert `response?.ok()` — this fails fast with the HTTP status
when the embedded server returned a 500, instead of burning the click budget on a
missing `#create`. The explicit `#create` visibility wait (15s) is kept as the
second guard. Both `it(...)` cases get the guard (both navigate).

### AD-4 — Flake elimination is verified over time, not in one run (hazard, not an AC)
Because GitHub CI is green on a dedicated runner while the saturated on-host gate
flakes, the underlying trigger is plausibly **browser-process resource starvation**,
which a readiness wait improves diagnostically but may not fully eliminate. This is
recorded as hazard H1 with a documented follow-up (move browser UATs out of the
on-host `vitest --changed` gate) rather than expanding this issue's scope.
