# PAN-3191 — Auto-merge rows strand forever: reconcile failed/blocked rows against real merge state

**Issue:** https://github.com/eltmon/overdeck/issues/3191
**Dependency:** PAN-3190 (`pan merge cancel` CLI fix) — already merged to `main` at 4eae74dee9. No ordering constraint remains.

## Glossary

- **`pending_auto_merges`** — table in `overdeck.db` (snake_case columns, integer-ms timestamps) holding Flywheel scheduled auto-merge cooldown rows. Drizzle definition: `src/lib/overdeck/merge.ts:52`; raw-SQL access layer: `src/lib/overdeck/merge-sync.ts`.
- **Row status lifecycle** — `pending` → `merging` → (`merged` | `failed` | requeue to `pending` | circuit-breaker `blocked`); `pending` → `blocked` on eligibility failure; any of `pending`/`blocked`/`failed` → `cancelled` via `cancelPending`. Type: `PendingAutoMergeStatus` in `src/lib/overdeck/merge-types.ts:7`.
- **Problems list** — `GET /api/flywheel/auto-merge/problems`, served by `getAutoMergeProblemPayload()` (`src/dashboard/server/routes/flywheel.ts:356`), which returns `listProblemAutoMerges()` (`src/lib/overdeck/merge-sync.ts:229`): rows with `status IN ('blocked','failed')`. Operator-facing queue of auto-merges needing attention.
- **Deacon patrol** — the periodic server-side loop in `src/lib/cloister/deacon.ts` that runs reconciler functions (e.g. `reconcileClosedPrReadyForMerge`, `reconcileStuckMergingStates`) and collects their action strings.
- **Closed-out** — an issue that completed `pan close`. Recorded durably as `closedOut: true` in the per-issue review-status journal, readable via `readJournalStatusSync(issueId)` from `src/lib/overdeck/review-status-record-sync.ts:464` (`(journal.durable as { closedOut?: boolean }).closedOut === true`; same read pattern as `src/lib/review-status.ts:98`).
- **`findMergedArtifact`** — forge-agnostic "is there a merged PR/MR for this branch/artifact?" query on `ForgeAdapter` (`src/lib/forge.ts:110`). With a GitHub PR URL carrying the PR number it costs one `getPullRequestState` API call (or one `gh pr view` when the GitHub App is not configured).
- **Auto-merge executor** — `src/dashboard/server/services/auto-merge-executor.ts`; the interval service that transitions due rows and calls `markMerged`/`markFailed`/`markBlocked`. It is the only current caller of `markMerged`.

## Problem

A `pending_auto_merges` row that reaches `failed` or `blocked` is stranded permanently. The only writer of `merged` is `markMerged` (`src/lib/overdeck/merge-sync.ts:193-199`):

```ts
export function markMerged(id: number): boolean {
  const db = getOverdeckDatabaseSync();
  const result = db.prepare(
    "UPDATE pending_auto_merges SET status = 'merged', merged_at = ? WHERE id = ? AND status = 'merging'",
  ).run(nowMillis(), id);
  return result.changes === 1;
}
```

The `AND status = 'merging'` precondition can never be met again once an attempt lands in `failed` or `blocked`, because nothing moves a row back to `merging`. No patrol reconciles these rows against what actually happened to the issue's PR, so the problems list accumulates permanent residue: 15 rows across 13 issues as of 2026-07-27, every one of them closed, closed-out, and with its merge commit an ancestor of `origin/main`. The list is the operator's stuck-merge signal, and residue makes a genuinely stuck merge indistinguishable from shipped work.

`pan merge cancel` (fixed by PAN-3190) is the manual exit, but it clears only ONE row per invocation — `deleteAutoMergePayload` (`src/dashboard/server/routes/flywheel.ts:360`) resolves `getActionableAutoMerge(issueId)`, which returns the newest actionable row only (`src/lib/overdeck/merge-sync.ts:211-217`). Two of the thirteen issues (PAN-2297, PAN-1644) hold two stale rows each, so one `pan merge cancel` per issue silently leaves residue behind and reports success anyway.

## Proposal

Three changes, plus docs.

### 1. Widen the `markMerged` precondition (issue expectation #2)

Change the `WHERE` clause to accept `status IN ('pending','blocked','failed','merging')` so a late-landing merge can close its own row from any non-terminal state. This is strictly additive: the only existing caller (`auto-merge-executor.ts:125`) always calls it from `merging`, and the partial unique index `idx_pending_auto_merges_active_issue` covers only `('pending','merging')`, so moving `blocked`/`failed` rows to `merged` cannot violate it. Rows already `merged` or `cancelled` still return `false`.

### 2. New deacon reconciler: `reconcileAutoMergeRows`

New module `src/lib/cloister/deacon-auto-merge-reconcile.ts`, wired into the deacon patrol in `src/lib/cloister/deacon.ts` immediately after the `reconcileClosedPrReadyForMerge()` block (~line 2950), and re-exported through `src/lib/cloister/deacon-merge.ts` exactly the way `reconcileStuckMergingStates` is re-exported at `deacon-merge.ts:21` (with the mirror re-export in `deacon.ts:142`).

Per patrol run:

1. Collect candidate rows: `listProblemAutoMerges()` (`blocked`/`failed`) plus the `pending` rows from `listActiveAutoMerges()` (filter out `merging` — in-flight merges are the executor's; reconciling stuck `merging` rows is a NonGoal).
2. Group rows by `issueId`. **Every actionable row for an issue is processed, not just the newest** — duplicate rows exist in the wild (PAN-2297, PAN-1644).
3. Skip issues still inside a per-issue 10-minute in-memory cooldown (`Map<string, number>`, same pattern as `closedPrReadyReconcileCooldowns` at `src/lib/cloister/deacon-merge.ts:334`; module-local, resets on restart — a rate limiter, not state).
4. **Tier 1 — closed-out age-out (cheap, local, no forge call).** If `readJournalStatusSync(issueId)?.durable.closedOut === true`, cancel every `pending`/`blocked`/`failed` row for the issue via `cancelPending(id, 'auto-merge-reconciler')`. Rationale: `pan close` is the mechanical DoD gate — an issue can only reach closed-out after its merge was verified — so re-proving the merge via the forge buys nothing, and the issue explicitly authorizes age-out "regardless of merge evidence". The row's `cancelledBy` records why it left the queue.
5. **Tier 2 — positive merge evidence (one forge call, only for issues with `blocked`/`failed` rows that are NOT closed-out).** Resolve the project path via `resolveProjectFromIssueSync(issueId)` (used the same way in `src/lib/cloister/deacon-stuck-merging.ts`), then call:

   ```ts
   await getForgeAdapter(row.forge).findMergedArtifact({
     sourceBranch: `feature/${issueId.toLowerCase()}`,
     artifactUrl: row.prUrl,
     cwd: projectPath,
   })
   ```

   If it returns non-null, call `markMerged(id)` for **each** `blocked`/`failed` row of the issue and log an action. If it returns null, the row is genuinely stuck — leave it (that is the signal the list exists for) and set the cooldown. On error, leave the row, set the cooldown, `console.warn`, and continue with the next issue; the reconciler must never throw past the patrol (same wrapper shape as `reconcileClosedPrReadyForMerge`).
6. Return the action strings for the patrol log.

After reconciliation the rows' new terminal statuses (`merged`/`cancelled`) remove them from `listProblemAutoMerges()`'s `status IN ('blocked','failed')` filter, so the problems endpoint needs no change — it stays a pure DB read with no forge calls in the request path (NFR-1).

The 15 current rows all belong to closed-out issues, so tier 1 cancels them on the first patrol after deploy; no one-off migration or manual SQL.

### 3. `pan merge cancel` reports remaining rows (flywheel design note, adopted)

Single-row cancel semantics are deliberate (race handling in `deleteAutoMergePayload` reasons about one entry); we keep them but stop hiding the duplicates.

- New helper in `src/lib/overdeck/merge-sync.ts`:

  ```ts
  export function countActionableAutoMerges(issueId: string): number {
    const db = getOverdeckDatabaseSync();
    const row = db.prepare(
      "SELECT COUNT(*) AS n FROM pending_auto_merges WHERE issue_id = ? AND status IN ('pending','merging','blocked','failed')",
    ).get(issueId) as { n: number };
    return row.n;
  }
  ```

- `deleteAutoMergePayload` (`src/dashboard/server/routes/flywheel.ts:381-389`): after a successful cancel, include `remainingActionable: countActionableAutoMerges(issueId)` in the 200 body.
- `mergeCancelCommand` (`src/cli/commands/merge.ts:35-38`): parse the JSON body; when `remainingActionable > 0` print `Cancelled auto-merge for <ID> (<N> actionable row(s) remain — re-run \`pan merge cancel <id>\` to clear the next one)`; otherwise keep the current message.
- Update `sync-sources/skills/pan-merge/SKILL.md` in the same commit (skills-convention rule): document that cancel clears one row per invocation, that duplicate rows exist, and what the remaining-rows output means. The wrapper skill's command/flag surface is unchanged, so `scripts/lint-skills.sh` is unaffected.

### 4. Docs

Extend the "Scheduled auto-merge recovery" section of `docs/FLYWHEEL.md` (starts at line 159) with a short "Reconciliation" subsection: `failed`/`blocked` are not terminal-residue states — a deacon reconciler flips rows to `merged` when the forge shows the PR merged, and cancels actionable rows whose issue is closed-out; `pan merge cancel` clears one row per invocation and now reports how many actionable rows remain.

## Decisions (made in `--auto` mode)

- **D1 — Reconcile on patrol, not on read.** The issue allows either. On-read reconciliation would put forge/git calls in an HTTP handler (latency, failure modes, rate limits in a request path); the patrol pattern (`reconcileClosedPrReadyForMerge`, `reconcileStuckMergingStates`) is the established home for exactly this drift class. The endpoint stays a pure DB read and rows leave it via status transitions.
- **D2 — Closed-out ⇒ `cancelled`, not `merged`, without a forge call.** Close-out already verified the merge through the DoD gate, so the distinction is cosmetic for those rows; skipping the forge call keeps the common residue sweep at zero network cost. Positive-evidence `merged` transitions are reserved for rows whose issue is still open (the AC "a row in `failed` whose PR subsequently merges transitions to `merged`").
- **D3 — Tier-2 evidence via `findMergedArtifact`, not `observeForgeMergeState`.** `observeForgeMergeState` (`src/lib/cloister/merge-completeness.ts:211`) does a `git fetch` plus merge-base per repo and patches merge-set rows — heavier than needed and it mutates unrelated state. `findMergedArtifact` with the row's `prUrl` is one PR-state API call and is forge-agnostic (GitLab adapter implements it too, `src/lib/forge.ts:534`).
- **D4 — Cancel keeps single-row semantics; only reporting is added.** Cancel-all flags/loops change the operator-facing contract and the race handling; a remaining-row count in the response fixes the silent-residue UX the flywheel hit, at a fraction of the surface.
- **D5 — Stuck `merging` rows are out of scope.** A row orphaned in `merging` by a mid-merge crash is a distinct failure class (it also wedges the unique active-issue index). Noted as a hazard for a follow-up issue; this plan does not touch it.

## Hazards

- **H1 — Stuck `merging` rows remain un-reconciled.** A crash between `transitionToMerging` and the outcome write strands a row in `merging`, which also blocks new rows for that issue via `idx_pending_auto_merges_active_issue`. Out of scope here; file a follow-up if observed.
- **H2 — Forge observation failure must not clear rows.** A `findMergedArtifact` error (network, auth, rate limit) leaves the row in place and sets the cooldown; rows only leave the problems list on positive evidence (merged) or positive closed-out state (cancelled). Never on absence of evidence.
- **H3 — Cooldown resets on dashboard restart.** Acceptable: worst case is one extra forge call per genuinely-stuck issue per restart.
- **H4 — `markMerged` widening is a behavior change for any future caller.** The function now succeeds from `pending` too. The executor's call site is unaffected; the precondition list matches the issue's expectation #2 verbatim.
- **H5 — `prUrl` is NOT NULL in the schema but may be unparseable for non-PR URLs.** `findMergedArtifact` tolerates an unparseable `artifactUrl` (falls back to branch discovery); a null result just leaves the row for the next cooldown cycle.

## Requirements

### Functional

- **FR-1** — `markMerged(id)` transitions a row to `merged` (setting `merged_at`) from any of `pending`, `blocked`, `failed`, `merging`; it returns `false` for rows already `merged` or `cancelled`.
- **FR-2** — A deacon patrol reconciler transitions every `blocked`/`failed` row of an issue to `merged` when `findMergedArtifact` returns positive evidence for that issue's PR, without operator action.
- **FR-3** — The reconciler cancels every `pending`/`blocked`/`failed` row of an issue whose review-status journal records `closedOut: true`, regardless of merge evidence.
- **FR-4** — The reconciler processes ALL actionable rows of an issue per run (duplicate rows are transitioned together), and throttles forge observations to at most one per issue per 10 minutes of process uptime.
- **FR-5** — `DELETE /api/flywheel/auto-merge/:id` includes `remainingActionable: <n>` in its 200 response, and `pan merge cancel <id>` prints the remaining count and re-run guidance when n > 0.

### Non-functional

- **NFR-1** — `GET /api/flywheel/auto-merge/problems` remains a pure database read: no forge, git, or tracker calls in the request path.
- **NFR-2** — Reconciler errors (forge, DB, journal) are caught per issue, logged, and never propagate past the patrol; a failing issue does not block reconciliation of the others.

## NonGoals

- Reconciling rows stuck in `merging` (H1) — separate failure class, follow-up issue if observed.
- Cancel-all semantics or a `--all` flag for `pan merge cancel` — single-row contract preserved; reporting only.
- On-read filtering or forge checks inside the problems endpoint (NFR-1 forbids it).
- One-off SQL/migration to clear the current 15 rows — the reconciler clears them after deploy (AC-5).
- Changes to the auto-merge executor's retry/requeue/circuit-breaker policy.
