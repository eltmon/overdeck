# PAN-3114 — Record verification verdicts for UAT-promoted merges

## Glossary

- **DoD row 3 (`verification`)** — the Definition-of-Done gate row (`src/lib/lifecycle/dod.ts:24-30`)
  that requires `verificationStatus: passed` (or `skipped`) before `pan close` will complete
  close-out. Evaluated by `checkVerificationRow` in `src/lib/lifecycle/dod-gate.ts:222-245`;
  the verdict alone decides the row (`passed`/`skipped` → pass, anything else → miss).
- **Verification gate / runner** — the pre-merge, branch-scoped supervised worker
  (`src/lib/cloister/verification-runner.ts`) that runs typecheck/lint/tests/build on a feature
  branch and records `verificationStatus` through `setReviewStatusSync`. It can only run while
  the branch and workspace still exist.
- **UAT generation / batch** — a `uat/<name>` branch assembling several approved feature
  branches into one tested tree (`src/lib/overdeck/merge-types.ts:69-87`). The operator
  exercises the batch stack, then promotes it.
- **Promotion** — `promoteUatGeneration()` (`src/lib/cloister/uat-promote.ts:99-206`) merges the
  `uat/*` branch into main with one no-ff merge, marks the generation `promoted`, and fires the
  standard per-issue post-merge lifecycle for each member.
- **Review-status write door** — `setReviewStatusSync(issueId, update)`
  (`src/lib/review-status.ts:147`), the single write path for pipeline verdicts
  (`verificationStatus`, `verificationNotes`, `lastVerifiedCommit`, …).
- **Terminal verdict** — `verificationStatus` of `passed` or `skipped`. A terminal verdict is
  never overwritten by this change (PAN-3067 precedent).
- **`pan close` DoD gate** — `closeOut()` in `src/lib/lifecycle/workflows.ts:165-...` evaluates
  `evaluateDodGate(ctx, …)` (line 175) before any teardown; a miss on any non-accepted row
  blocks close-out.

## Problem

When the operator promotes a UAT generation to main, member issues whose branch never got a
verification-runner run before promotion are left with `verificationStatus: pending` forever.
The runner is pre-merge and branch-scoped; once the batch merges and branches are gone, nothing
can ever run it. DoD row 3 then reads `pending` (a miss) and close-out is permanently blocked
except by an operator `--accept-verification` override — on an issue that is merged, deployed,
and green. Observed 2026-07-26 on PAN-3037 (batch `uat/pan-cedar-0726`, promote commit
546d05b989); PAN-3097 and PAN-3109 passed row 3 only because verification happened to run on
their branches in time — timing luck, not a confidence distinction.

This is the same shape as the PAN-3067 strike gap: a legitimate landing path discards evidence
the system already has. With `require_uat_before_merge`, operator UAT *is* the verification
step — a human exercised the batch and promoted it, which is stronger evidence than the
automated gate.

## Proposal

Record the evidence at the moment it exists, exactly as PAN-3067 does for strikes:

1. **Promote-time recording (FR-1..FR-3).** After `promoteUatGeneration` successfully merges
   the batch and marks the generation `promoted`, stamp each member's
   `verificationStatus: 'passed'` through the review-status write door, with
   `verificationNotes` carrying source `uat-promotion`, the generation name, and the promote
   merge SHA, and `lastVerifiedCommit` anchored to the member's assembly `headSha`. Terminal
   verdicts are never overwritten. A recording failure logs and never fails the promote.
2. **Close-out heal for past promotions (FR-4).** `closeOut()` gains a pre-gate
   evidence-reconciliation step: if the issue is a member of an already-`promoted` generation
   and its verification verdict is not terminal, the same verdict is recorded before
   `evaluateDodGate` runs, so row 3 passes on recorded evidence instead of an override. This
   gives PAN-3037 a mechanical path: `pan close PAN-3037` just works.
3. **Docs (FR-5).** `docs/DEFINITION-OF-DONE.md` row 3 names `uat-promotion` as a verdict
   source; `docs/UAT-BATCH-TRAINS.md` documents that promotion records per-member verdicts.

## Requirements

- **FR-1** — A successful `promoteUatGeneration` records `verificationStatus: 'passed'` for
  every member whose current verdict is not terminal, via `setReviewStatusSync`, with
  `verificationNotes` naming source `uat-promotion`, the generation name (e.g.
  `uat/pan-cedar-0726`), and the promote merge SHA.
- **FR-2** — Members already carrying a terminal verdict (`passed`/`skipped`) are left
  untouched; their existing notes and anchors are preserved.
- **FR-3** — A failure while recording never fails or rolls back a successful promote; the
  error is logged and the promote result is returned unchanged.
- **FR-4** — `closeOut()` heals past promotions: before `evaluateDodGate` runs, an issue that
  is a member of a `promoted` generation and lacks a terminal verification verdict gets the
  FR-1 verdict recorded (merge SHA recovered from git history, best-effort), appearing as a
  visible ceremony step. Row 3 then passes on the recorded verdict.
- **FR-5** — `docs/DEFINITION-OF-DONE.md` and `docs/UAT-BATCH-TRAINS.md` state that UAT
  promotion records per-member verification verdicts.
- **NFR-1** — `promoteUatGeneration` stays pure orchestration over injected deps; the
  recorder is an injected dep (real implementation wired in
  `src/dashboard/server/services/uat-train.ts`).
- **NFR-2** — The recording/stamp logic lives in a new module
  `src/lib/cloister/uat-promote-verification.ts` (PAN-3067 ratchet pattern: keeps
  `uat-promote.ts` and `workflows.ts` near their file-size baselines).

## Decisions (made in this doc; auto-mode)

- **D1: verdict is `passed`, not `skipped`.** The operator exercised the batch stack and
  promoted it — real human verification, stronger than the automated gate. `skipped` would
  understate the evidence. (DoD row 3 accepts both; we record the honest one.)
- **D2: never overwrite terminal verdicts.** Mirrors `buildStrikeBypassStamp`
  (`src/cli/commands/strike-merge-verification.ts:14-38`). Members like PAN-3097/PAN-3109 that
  already passed keep their original runner verdict and notes.
- **D3: heal lives in `closeOut`, not in resync or the DoD checks.**
  `processResyncReviewStatus` is deliberately non-mutating
  (`src/dashboard/server/routes/workspaces/review-control.ts:78-92`) and the dod-gate row
  checks are read-only. A visible pre-gate step in `closeOut()` heals past promotions at the
  single chokepoint all close-out paths (CLI, dashboard, flywheel auto-close-out) share.
- **D4: recorder is an optional injected dep on `UatPromoteDeps`.** Guarantees every promote
  path records, keeps `promoteUatGeneration` pure/testable, and existing tests keep compiling
  (the dep is optional; new tests pass a spy).
- **D5: `lastVerifiedCommit` = member `headSha`.** That is the commit review anchored
  (`reviewedAtCommit`) and the commit the operator exercised, so drift comparisons stay
  consistent. The promote merge SHA goes in `verificationNotes` for main-side traceability.
  Anchor crosses a storage boundary via `rehydrateHeadAnchor`
  (`src/lib/git-utils.ts:355-357`).

## NonGoals

- No change to `memberEligibility` — promotion does not start requiring a passed verification
  gate.
- No change to the verification runner itself; it stays pre-merge and branch-scoped.
- No heal for `testStatus` (row 2) — UAT members already pass tests before promotion; only the
  verification row has the gap.
- No change to `processResyncReviewStatus`'s non-mutating contract.
- No retroactive stamping of historical records outside the close-out heal path.
