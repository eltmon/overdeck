# PAN-3233 — Fix enrichment classification defects that hide genuinely frozen agents

**Issue:** https://github.com/eltmon/overdeck/issues/3233
**Related:** PAN-3228 (recovery gate on needs_input), PAN-2882 (frozen agent incident), PAN-1834 (specialist suppression origin), PAN-1591 (actionable-kinds rule), PAN-3070 (blocking-reason predicate).

## Glossary

- **Enrichment** — the per-agent derived state computed by `computeAgentEnrichmentPromise` in [`src/lib/agent-enrichment.ts`](../../src/lib/agent-enrichment.ts) (JSONL scan + runtime state + tmux pane detection), emitted as `agent.enrichment_changed` events by the enrichment poller (`src/dashboard/server/services/agent-enrichment-service.ts`, 10s interval).
- **Detection** — an `AwaitingInputDetection { reason, prompt }` (`src/lib/agent-input-detection.ts:5-10`). Reasons: `tool_permission | user_question | disambiguation | confirmation | planning_done | session_resume | rate_limit | other`.
- **Detection sources**, in precedence order (`agent-enrichment.ts:625`): `questionDetection` (JSONL AskUserQuestion entries, reason `user_question`), `runtimeDetection` (stop-hook runtime state `waiting-on-human`, reason from `waitingReason`), `paneDetection` (live tmux pane scan — only computed when the first two are null, `:593-595`), `fallbackDetection` (runtime `resolution: needs_input`, reason `other`), `turnEndedDetection` (interactive roles, reason `other`).
- **Blocking reasons** — `BLOCKING_AWAITING_INPUT_REASONS` (`agent-enrichment.ts:129-137`): every reason except `other`. `isBlockedOnPendingInput` (`:144-150`) is the shared "agent is parked" predicate.
- **Specialist suppression** — PAN-1834: while a review/test/merge specialist is active on the issue (`hasActiveSpecialist`), the parked work/plan agent's pending-input surfaces are hidden (`shouldSuppressPendingInput`, `:626`).
- **Kinds** — `pendingInputKinds: PendingInputKind[]` (`agent-enrichment.ts:46-60`; frontend copy `src/dashboard/frontend/src/lib/pendingInput.ts:12-20`). The actionable-signal vocabulary: PAN-1591 established that surfaces trust `kinds.length > 0`, never the fuzzy `hasPendingQuestion` bool.
- **Decisions surface** — `selectPendingInputSubjects` (`src/dashboard/frontend/src/lib/store.ts:426-489`) requires `kinds.length > 0` (`:467`).
- **Reaping** — when an enriched agent leaves the active set, the poller emits a clearing event if `hasReapablePendingInput` (`src/dashboard/server/services/agent-enrichment-service.ts:112-118`) — which requires `pendingInputCount > 0` or a structured payload.

## The three defects (verified against this branch)

**D1 — suppression hides a frozen work agent's live permission prompt.** `agent-enrichment.ts:626-627`:

```ts
const shouldSuppressPendingInput = hasActiveSpecialist === true && !isOwnActiveSpecialist(role)
const hasPendingQuestion = !shouldSuppressPendingInput && detection !== null
```

A live pane `tool_permission` detection is zeroed whenever a specialist is active, so a work agent frozen on a permission menu during review is invisible everywhere at once (extended the PAN-2882 incident). Meanwhile `pendingQuestionPrompt`/`pendingQuestionReason` (`:665-666`) and `pendingQuestionCount` (`:664`) are NOT gated by suppression, producing the contradictory fingerprint `{hasPendingQuestion: false, pendingQuestionReason: "tool_permission", pendingInputKinds: []}`.

**D2 — question-family detections yield empty kinds → invisible AND unreapable.** `appendPaneDetectionKind` (`:103-118`) promotes only `session_resume`, `rate_limit`, `tool_permission`. A `user_question` / `confirmation` / `disambiguation` / `planning_done` detection (typically from `runtimeDetection` when the JSONL has no AskUserQuestion) produces `pendingInputKinds: []` and `pendingInputCount: 0`, so the Decisions surface drops the agent (`store.ts:467`) and the reaper never clears it (`agent-enrichment-service.ts:112-118`). 35 live agents observed in this state.

**D3 — `pendingQuestionCount` structurally excludes pane prompts.** `:664` counts only JSONL AskUserQuestion entries (`:561`), so every pane/runtime prompt reports `hasPendingQuestion: true, pendingQuestionCount: 0`. Consumer audit (this branch): `hasActualPendingQuestion` (`src/dashboard/frontend/src/lib/pipeline-state.ts:31-33`) requires `count > 0 || prompt` — pane prompts pass only via the prompt fallback; `getPendingQuestionTitle` (`:48`) uses `count || 1`; `listing.ts:254` and `event-reducers.ts:381` pass it through. No consumer breaks if the count starts including blocking detections; the count-vs-flag contradiction disappears.

## Decisions (made here, not by the executor)

1. **Suppression exemption is keyed on blocking pane detections.** `shouldSuppressPendingInput` becomes false when `paneDetection !== null && BLOCKING_AWAITING_INPUT_REASONS.has(paneDetection.reason)`. Rationale: pane detections are live tmux evidence (10s cache TTL) and are only computed when JSONL/runtime detections are absent (`:593-595`) — they are never the stale parked-agent surfaces PAN-1834 suppression was built for. JSONL-derived surfaces (`askUserQuestion`, plan-mode kinds), runtime detections, fallback and turn-end detections **remain suppressed** while a specialist is active.
2. **The existing test that locks the defect is inverted, not preserved.** `src/lib/__tests__/compute-agent-enrichment.test.ts:56-72` ("suppresses pendingInputKinds for a work-role agent when hasActiveSpecialist is true") asserts a `rate_limit` pane detection is hidden — under decision 1 it must now surface. Rewrite it to assert suppression using a non-blocking surface (e.g. a JSONL AskUserQuestion in the scan with the pane detection mock returning null).
3. **New kind `paneQuestion`.** Question-family reasons (`user_question`, `confirmation`, `disambiguation`, `planning_done`) promote to a new `PendingInputKind` `'paneQuestion'`, guarded by `!kinds.includes('askUserQuestion')` so a JSONL-backed question is not double-represented. Named for symmetry with `paneChoice`; it covers pane- **and** runtime-detected prose/modal questions that carry no structured payload. Contracts type kinds as plain strings (`packages/contracts/src/events.ts:193`, `types.ts:345,659`) — no schema change. Frontend renders unknown kinds via label-map fallback, and we add the label anyway.
4. **D3 is resolved by folding, not renaming.** `pendingQuestionCount` = JSONL question count when > 0, else 1 when the (unsuppressed) detection has a blocking reason, else 0. Renaming (`pendingAskUserQuestionCount`) would touch contracts, events, reducers, and every frontend consumer for the same observable result.
5. **No new reconciliation machinery for the 35 stuck agents.** Active agents reclassify within one 10s poll after deploy (kinds change → `enrichmentChanged` → event). Stopped agents already have pending fields cleared at projection time by `projectPendingInput` (`src/dashboard/server/read-model.ts:267-280`, PAN-1591) and the status_changed reducer. Verify live during verify-on-main.
6. **`other`-reason detections stay kind-less and count-less** (PAN-1591: they carry no answerable prompt; promoting them would resurrect phantom "Waiting on your input" rows).

## Requirements

- **FR-1** — A `tool_permission` (or any blocking-reason) pane detection surfaces `hasPendingQuestion: true`, its kind, and `resolution: needs_input` even while a specialist is active on the issue.
- **FR-2** — When suppression applies, the entire fingerprint is suppressed: `pendingQuestionCount: 0`, `pendingQuestionPrompt: undefined`, `pendingQuestionReason: undefined` alongside `hasPendingQuestion: false`.
- **FR-3** — A `user_question` / `confirmation` / `disambiguation` / `planning_done` detection yields `pendingInputKinds: ['paneQuestion']` (when no JSONL AskUserQuestion is pending) and `pendingInputCount ≥ 1`.
- **FR-4** — `pendingQuestionCount ≥ 1` whenever `hasPendingQuestion` is true with a blocking reason; still equals the JSONL question count when JSONL questions exist.
- **FR-5** — The frontend kind vocabulary includes `paneQuestion` with a human label, so Decisions/tooltips/notifications render it.
- **FR-6** — An enrichment carrying only a `paneQuestion` kind is eligible for `selectPendingInputSubjects` and for reaping (`hasReapablePendingInput` returns true).
- **FR-7** — `docs/PENDING-INPUT.md` documents the new kind, the suppression exemption, and the count semantics.
- **NFR-1** — No `other`-reason detection produces kinds, count, or Decisions rows (PAN-1591 preserved).
- **NFR-2** — The 35 live stuck agents reclassify without manual action after deploy (poller re-enrichment); note this in the PR body for verify-on-main.

### W3 — `paneQuestion` kind for question-family detections (FR-3)

- Extend `appendPaneDetectionKind` (`:103-118`):
```ts
  // PAN-3233 — question-family detections previously yielded NO kind, making
  // the agent invisible to Decisions (kinds.length > 0 gate) and unreapable
```

Tests: unit tests on `appendPaneDetectionKind` for each of the four reasons, the `askUserQuestion` guard, and `other` yielding nothing (NFR-1); compute-level test — runtime state `{ state: 'waiting-on-human', waitingReason: 'user_question' }`, empty scan → `hasPendingQuestion: true`, `pendingInputKinds: ['paneQuestion']`, `pendingInputCount: 1` (issue's second acceptance bullet, server half). Note: `appendPaneDetectionKind` is also called from `src/lib/overdeck/conversation-list.ts` and `conversation-reads.ts` — conversations gain the kind too; no changes needed there.
