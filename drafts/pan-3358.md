# PAN-3358 PRD — Ship step: propagate version strings across a project's repos when a batch merges

**Issue:** [PAN-3358](https://github.com/eltmon/overdeck/issues/3358)
**Status:** Draft (planning)
**Author:** planning agent (auto mode)

## Glossary

- **UAT batch / generation** — a throwaway `uat/<label>-<codename>-<MMDD>` branch off main containing as many ready features as possible, assembled by the UAT train reconciler. Stored as a `UatGeneration` row (schema v51 `uat_generations`, `src/lib/database/uat-generations-db.ts`; type in `src/lib/overdeck/merge-types.ts:128-165`). See `docs/UAT-BATCH-TRAINS.md`.
- **Promote** — merging a generation's exact tested tree into main via `promoteUatGeneration()` (`src/lib/cloister/uat-promote.ts:160`). One no-ff merge per repo, in a throwaway detached worktree, then per-member post-merge fan-out in `finishPromote()` (`src/lib/cloister/uat-promote.ts:590`).
- **Ship (this issue's definition)** — the act of making the project's version strings reflect a merged batch: set the canonical version, run the project's version-sync command, verify every declared version path, commit, push. **Not** `npm publish`, **not** store submission, **not** a prod deploy, **not** tag creation.
- **version_sync** — the per-project declaration in `projects.yaml` that makes ship data-driven: which file(s) receive the canonical version, which command propagates it, which paths must report the version afterwards, which repos to push.
- **DoD row** — one row of the Definition-of-Done table (`docs/DEFINITION-OF-DONE.md`), defined in `src/lib/lifecycle/dod.ts` (`DOD_ROWS`) and checked mechanically by `evaluateDodGate()` in `src/lib/lifecycle/dod-gate.ts` during `pan close <id>`.
- **Ship record** — the durable per-issue verdict written into the per-issue permanent record's `pipeline` block on `overdeck-state` (same durability channel as the `uat-promotion` verification verdicts written by `recordUatPromotionVerdicts`), so the DoD row survives DB rebuilds.
- **Main checkout** — the project's primary worktree on its default branch (e.g. `/home/eltmon/Projects/myn/frontend`). The ship runner operates here, exactly as today's manual flow does — never in an issue workspace.
- **Polyrepo project** — a project whose `workspace.type: 'polyrepo'` declares several sibling repos (`workspace.repos[]` in `projects.yaml`; resolved by `resolveConfiguredReposSync()` in `src/lib/project-repos.ts:61-93`). mind-your-now is the driving example.

## Problem

Every merged batch already gets a version bump — by hand, invisible to the pipeline, with nothing asserting it happened. Two live consequences (from the issue):

1. **MIN-908** merged to the backend on 2026-07-27 21:53 and shipped in 47.3.0 at 23:08 that night. Four days later it still sat in `post_merge_limbo` in the pipeline-membership read door because nothing recorded that the issue was finished. The pipeline cannot tell "merged, shipped and done" from "merged and forgotten".
2. **PAN-3341** was filed for the visible symptom of the same gap: the board showed MIN-852, MIN-861 and MIN-882 as "Planning" while all three were merged in both repos and Done in Linear for over a week.

Overdeck already asserts the analogous claim one step later — DoD row 7 (`deploy`): "live server build includes the merged commit". That row exists because merged ≠ in force. Ship is the same idea one hop earlier: **merged ≠ versioned**.

The silent-partial hazard is real and specific. mind-your-now's `pnpm vsync` (`frontend/sync-versions.js`) edits four files across two repos using regex `String.replace` calls that **succeed silently when the pattern does not match** — it prints `✓ Updated Java Version.java` even when it wrote nothing. A half-applied bump (frontend says 48.7.0, `Version.java` still says 48.6.0) is invisible today.

## Proposal

Add a **ship step** to batch promotion that does exactly one thing — propagate version strings — plus a **DoD row** that asserts it happened, plus a **dashboard settings surface** to configure it.

1. **A per-project `version_sync` block in `projects.yaml`** declares the mechanism: `set` targets that receive the canonical version, an optional propagation `command`, `expect` paths with patterns that must report the version, and the repos to push. A project with no `version_sync` skips ship entirely.
2. **A ship runner** (`src/lib/cloister/version-ship.ts`) — pure orchestrator with injected deps, unit-tested like the other uat-* modules. It sets the version, runs the command, verifies every `expect` pattern (this is what catches silent partial propagation), commits any dirty declared paths per repo, and pushes.
3. **A promote hook**: `finishPromote()` gains a `runShip` dep, invoked once per batch after the merge lands. The version is **operator-supplied at promote time** (the issue's recommended option): the promote route accepts an optional `shipVersion`, and the dashboard batch card asks for it when the project declares `version_sync`. Ship failure never blocks or rolls back the merge — the verdict is recorded and surfaced.
4. **A durable ship record** per member issue (`pipeline.ship` in the per-issue record), so `pan close` can assert it and the dashboard can surface it.
5. **A new DoD row `ship`** between `main-verify` and `deploy`: passes when the batch the issue merged in has a `passed` ship record; misses loudly on `pending` or `partial` (naming the failing paths); skips with an explicit reason for projects without `version_sync` and for issues merged outside a batch.
6. **A dashboard settings surface** editing `version_sync` through a **lossless YAML write door** — the UI and hand-editing share `projects.yaml` as the single store; the writer preserves comments, formatting, and unrelated projects byte-for-byte. Unset renders explicitly as "this project skips ship". The same surface shows the last ship outcome, including partial-propagation failures.
7. **A deferred-ship path** — a **Ship version** action on a promoted-but-unshipped batch card (`POST /api/merge-train/generations/:name/ship`) that runs the same runner later and rewrites the members' ship records, so the DoD row stays satisfiable when the operator promoted without supplying a version.

### The `version_sync` config shape

```yaml
# ~/.overdeck/projects.yaml
mind-your-now:
  version_sync:
    set:
      - path: frontend/package.json
        json_field: version
    command: pnpm vsync
    command_cwd: frontend
    expect:
      - path: frontend/package.json
        pattern: '"version": "{version}"'
      - path: api/src/main/java/com/myn/config/Version.java
        pattern: 'String version = "{version}\.git "'
      - path: frontend/ios/App/App/Info.plist
        pattern: 'CFBundleShortVersionString</key>\s*<string>{majorMinor}</string>'
      - path: frontend/android/app/build.gradle
        pattern: 'versionName "{majorMinor}"'
    push:
      - frontend
      - api
```

```yaml
panopticon-cli:
  version_sync:
    set:
      - path: package.json
        json_field: version
      - path: apps/desktop/package.json
        json_field: version
      - path: packages/contracts/package.json
        json_field: version
    expect:
      - path: package.json
        pattern: '"version": "{version}"'
      - path: apps/desktop/package.json
        pattern: '"version": "{version}"'
      - path: packages/contracts/package.json
        pattern: '"version": "{version}"'
    commit_message: "chore: bump version to {version}"
    push:
      - .
```

Semantics:

- `set[].path` / `set[].json_field` — before the command runs, the runner writes the chosen version into each listed JSON field. This is the entire mechanism for projects (like overdeck) whose "sync" is just keeping several `package.json` files in lockstep.
- `command` / `command_cwd` — optional; run after `set`, cwd relative to the project root. For myn this is `pnpm vsync` in `frontend/`, which propagates into `api/` via the `mind-your-now-api` symlink and commits in both repos itself.
- `expect[].path` / `expect[].pattern` — after `set` + `command`, every listed file (path relative to the project root) must match its pattern. Placeholders: `{version}` (full, e.g. `48.7.0`) and `{majorMinor}` (e.g. `48.7`). **This assertion is the heart of the feature** — it converts silent regex-miss partial propagation into a loud `partial` verdict naming the exact paths.
- `commit_message` — template for the runner's own commit, default `chore: bump version to {version}`. After the command, the runner stages only the declared `set` + `expect` paths per repo and commits whatever is dirty; a command that already committed (vsync does) leaves nothing, which is success, matching vsync's own "already up to date" semantics.
- `push[]` — repo paths (relative to project root; `.` for a monorepo) the runner pushes to their tracked upstream after committing.

### Where ship hooks into promote

`finishPromote()` (`src/lib/cloister/uat-promote.ts:590-676`) is the one place a generation becomes terminal. Ship slots in **after** the generation is stamped `promoted` and `recordVerification` has run, **before** the per-member `firePostMerge` fan-out — keeping main's history "batch merge → version bump" adjacent, matching today's manual shape (`014c2f96d chore: bump version to 48.7.0` directly after the batch merge). It is wrapped exactly like `recordVerification` (`uat-promote.ts:619-623`): a failure is logged and recorded, never thrown — the merge is already live and member post-merge lifecycles must not be held hostage by a version-sync failure.

The version flows: dashboard card / route body `shipVersion` → `postUatGenerationPromotePayload()` (`src/dashboard/server/services/uat-train.ts:713`) → `promoteUatGeneration(name, root, deps, options)` → `finishPromote` → `deps.runShip(gen, { version, config })`.

If the project declares `version_sync` but no `shipVersion` was supplied at promote: the merge still proceeds, and every member gets a ship record of `pending` with reason "no version supplied at promote time". The batch card shows a **Ship version** action for promoted-but-unshipped batches, and `pan ship <batch> --version X.Y.Z` runs the same runner later. `pending` fails the DoD row until ship completes.

### The DoD row

New row inserted between `main-verify` (row 6) and `deploy` (renumbered 7→8; `teardown` 8→9):

| # | Gate ID | Step | Mechanical owner | Visible at |
| --- | --- | --- | --- | --- |
| 7 | `ship` | Version strings propagated for the batch this issue merged in: every declared `version_sync.expect` path reported the batch's version | ship runner (`version-ship.ts`) via `finishPromote` / the batch-card Ship version action; terminal settlement in `evaluateDodGate()` | `pipeline.ship.status: passed`, or `skip` naming the no-`version_sync` / non-batch-merge reason; `partial` names the failing paths |

Row semantics (checked by a new `checkShipRow()` in `src/lib/lifecycle/dod-gate.ts`, reading the durable per-issue `pipeline.ship` record):

- Project declares no `version_sync` → **skip**, observed: "project declares no version_sync; ship step not applicable".
- Issue merged outside a UAT batch (no ship record, direct merge) → **skip**, observed: "merged outside a batch; ship is batch-scoped".
- `pipeline.ship.status: passed` → **pass**, observed names version + batch + paths verified.
- `pending` → **miss**: "batch <name> merged but no version was shipped — use the Ship version action on the batch card for <name>".
- `partial` → **miss**, naming every failing path: "version propagation partial: api/.../Version.java still reports 48.6.0".

The row is overridable (`--accept-ship`), consistent with rows 1–7. Adding the row means editing `src/lib/lifecycle/dod.ts` (`DodRowId` + `DOD_ROWS`) and `docs/DEFINITION-OF-DONE.md` in the same commit — `tests/unit/lib/lifecycle/dod-doc-drift.test.ts` enforces the pair.

### Dashboard surfaces

1. **Batch card (`src/dashboard/frontend/src/components/flywheel/MergeQueueCard.tsx`)** — when the project declares `version_sync`, the "Merge batch (N) to main" action asks for the version (validated `X.Y.Z`) before promoting; a promoted batch with a `pending` ship record shows a **Ship version** action that runs the same runner. The card learns whether the project declares `version_sync` from the `/api/registered-projects` DTO (`src/dashboard/server/routes/misc/meta.ts:126-154`), which gains a `versionSync` field.
2. **Project settings — Version ship section** in the existing per-project settings surface, `src/dashboard/frontend/src/components/CommandDeck/ProjectSettingsDisclosure.tsx` (today: auto-merge default, swarm policy, merge-train toggles posting to `/api/projects/:projectKey/*`). It edits the `version_sync` block through new `GET`/`PUT /api/projects/:projectKey/version-sync` routes (modeled on the three existing routes at `src/dashboard/server/routes/projects.ts:785-821` and `src/dashboard/server/routes/projects-merge-train.ts:15-49`). Unset renders explicitly as **"this project skips ship"** (not an empty form). The same section shows the most recent ship outcome for the project — `passed` (version, batch, timestamp) or `partial` with the failing paths named — so partial propagation is visible where the mechanism is configured, not only inside `pan close`.

Both the UI and hand-editing share `~/.overdeck/projects.yaml` as the single store. The write door is a new `setProjectVersionSyncSync()` that follows the established lossless pattern — `writeYamlConfigPreservingComments` for `config.yaml` (`src/lib/settings-api.ts:771-850`) and `updateConversationsConfig` (`src/lib/config-yaml/load.ts:609-647`): read with `parseDocument`, mutate with `doc.setIn(['projects', key, 'version_sync'], …)` / `doc.deleteIn(...)`, write with `doc.toString()`. Comments, quoting, key order, and every unrelated project survive byte-for-byte — `yaml@^2.8.2` is already a dependency (`package.json:175`). No second store, no DTO-only shadow.

**Pre-existing hazard (not fixed here):** the three legacy per-project setters (`setProjectAutoMergeDefaultSync` `src/lib/projects.ts:329-336`, `setProjectSwarmPolicySync` `:390-398`, `setProjectMergeTrainSync` `:404-411`) and the `pan projects` CLI writes all go through `saveProjectsConfigSync` (`src/lib/projects.ts:293-302`), which re-serializes the **entire** file with `stringifyYaml` — lossy, drops comments. The new version_sync door is lossless, but one click on an old toggle still reformats the file. Migrating those writers onto the Document API is a deliberate follow-up issue, not part of this plan.

## Requirements

### Functional

- **FR-1** — A project MAY declare `version_sync` in `projects.yaml` with `set`, optional `command`/`command_cwd`, `expect`, optional `commit_message`, and `push` fields; the loader exposes it on `ProjectConfig` as a typed `version_sync?: VersionSyncConfig`.
- **FR-2** — Promoting a UAT batch with a supplied version runs the ship step once per batch after the merge lands: set targets written, command run, every `expect` pattern asserted, declared paths committed per repo, repos pushed.
- **FR-3** — A failed `expect` assertion produces a `partial` verdict naming every non-matching path and the version each file still reports where determinable; a command non-zero exit produces `failed` with the command's stderr tail. Neither aborts the promote result.
- **FR-4** — Ship verdicts are recorded durably per member issue (`pipeline.ship` in the per-issue record on `overdeck-state`) with status `passed | partial | failed | pending`, the version, the batch name, per-path results, and timestamp.
- **FR-5** — `pan close` evaluates a new `ship` DoD row per the semantics above; the row appears in the gate table and in `--accept-ship` overrides; `docs/DEFINITION-OF-DONE.md` and the doc-drift test are updated in the same commit.
- **FR-6** — The promote route (`POST /api/merge-train/generations/:name/promote`) accepts an optional `shipVersion` (semver `X.Y.Z`, 400 on malformed); when the project declares `version_sync` and none is supplied, members' ship records are written as `pending` and the merge proceeds.
- **FR-7** — A promoted-but-unshipped batch can be shipped after the fact from the batch card: `POST /api/merge-train/generations/:name/ship` with `{ version }` runs the ship step and rewrites the members' ship records; it refuses batches that are not `promoted` (409) and projects without `version_sync` (422).
- **FR-8** — The dashboard batch card asks for the version at promote time when the project declares `version_sync`, and offers Ship version for promoted-but-unshipped batches.
- **FR-9** — A dashboard project-settings section edits `version_sync` through the lossless YAML write door: saving never reformats or drops unrelated `projects.yaml` content (verified by a round-trip test with comments and multiple projects); unset renders as an explicit "this project skips ship" state; the section displays the project's latest ship outcome including partial-path detail.
- **FR-10** — The `.husky/commit-msg` version guard accepts the ship commit subject `chore: bump version to X.Y.Z` in addition to `chore: release X.Y.Z`, so enabling `version_sync` for the overdeck repo itself is not blocked by the guard.

### Non-functional

- **NFR-1** — Ship never blocks, rolls back, or fails a batch merge: the merge is live before ship runs, and ship failures are recorded verdicts, not promote failures.
- **NFR-2** — The ship runner is a pure orchestrator with injected deps (unit-tested without real git/network), matching the uat-* module pattern; all process exec is async `execFile` argv arrays — never `execSync`, never shell-string interpolation of paths or versions.
- **NFR-3** — The runner stages and commits only the declared `set` + `expect` paths, so unrelated dirty state in a main checkout is never committed.
- **NFR-4** — The YAML write door is byte-lossless for everything outside the edited key: comments, formatting, and unrelated projects survive a save round-trip.

## Decisions (auto mode — recorded in `plan.autoDecisions`)

- **D1 — Operator supplies the version at promote time; ship only propagates.** The issue's own recommended option ("propagation is the part that is mechanical and error-prone; choosing the number is judgement"). No auto-derivation (patch-vs-minor heuristics) in v1.
- **D2 — Ship runs in the project's main checkouts, not a throwaway worktree.** Today's manual flow and `pan release stable` both operate on the main checkout; commands like vsync resolve sibling repos via relative paths (`../mind-your-now-api`, a symlink to `api/`) that only exist in the real layout. Commits use explicit pathspecs (NFR-3) so this is safe against unrelated dirty state.
- **D3 — The runner owns commit+push uniformly; commands that self-commit are fine.** After `command`, the runner commits any still-dirty declared paths per repo (no-op when vsync already committed) and pushes each `push[]` entry. One code path covers both myn (command commits) and overdeck (no command).
- **D4 — Two placeholders: `{version}` and `{majorMinor}`.** myn's `versionCode` (major*10+minor) is deliberately not a placeholder — its formula is project-specific, and every myn target also carries a `{version}` or `{majorMinor}` string the assertion can key on. A project needing exotic derived values can extend the placeholder set later.
- **D5 — Ship is batch-scoped; direct (non-batch) merges skip the DoD row.** The issue is explicit: "Per batch, not per issue… Attaching ship to individual issues would fight this." The row's skip reason states this plainly.
- **D6 — The DoD row reads the durable ship record; it does not re-verify the filesystem.** Same model as rows 1–3 reading recorded verdicts: the runner is the verifier, the gate is the reader. (The observed string names the recorded failing paths, so no information is lost.)
- **D7 — New row inserted at position 7, renumbering deploy→8 and teardown→9.** Ship is asserted before deploy because version propagation is a precondition for any meaningful "the right build is live" claim downstream.
- **D8 — The `commit-msg` guard gains the ship subject rather than reusing `chore: release X.Y.Z`.** Reusing the release subject would pollute release-notes generation (`git log <prev-tag>..HEAD` would list fake "release" commits) and mislabel a non-release act.
- **D9 — Unset `version_sync` renders as an explicit "this project skips ship" state in the UI** (operator requirement, issue comment 2026-07-31), not a blank form — absence of config is a deliberate, visible posture.
- **D10 — The settings UI writes through a lossless YAML Document-API door, never a parse→mutate→restringify cycle** (operator requirement, issue comment 2026-07-31), so hand-edited comments and formatting survive UI saves.
- **D11 — Ship verdicts persist only to the per-issue record's `pipeline.ship` block via the record write door** — no `review_status` columns, no SQLite schema migration. Ship is batch-terminal state and the DoD row reads the durable record only, so the ephemeral live-status plane adds nothing.
- **D12 — Deferred ship is dashboard-only (batch-card Ship version action), no `pan ship` CLI.** One remediation surface keeps the story simple; the finalize projected-surface lint counts each top-level `docs/*.md` and `src/cli` as separate "subsystems" (first-two-segment heuristic), and a CLI plus its skills-convention edit pushed the plan past the 6-subsystem cap. The route (`POST /api/merge-train/generations/:name/ship`) remains callable by hand for terminal-only operators.

## Out of scope (NonGoals)

- `npm publish`, App Store / Play submission, prod deploys, tag creation — all stay operator-initiated (`pan release stable` keeps its five atomic steps untouched).
- Choosing the version number automatically (patch/minor derivation heuristics).
- Per-issue ship triggers on direct (non-batch) merges.
- A `{versionCode}`-style placeholder or configurable version-code formulas.
- Release notes / changelog generation (myn's `changelog:` splash-site entries remain manual).
- Migrating MIN-908-style already-limp issues: the row helps future closes; existing limbo issues keep their current settlement paths.

## Acceptance criteria (plan-level)

- AC-1: Given a project with the myn-style `version_sync` declared, when a batch is promoted with `shipVersion: 48.8.0`, then the runner writes the version, runs the command, asserts every `expect` path, commits and pushes, and every member's durable record shows `pipeline.ship.status: passed` with version `48.8.0`. (unit-tested with injected deps)
- AC-2: Given an `expect` path whose content does not match after the command, when ship runs, then the verdict is `partial` naming that path, and `pan close` on a member misses the `ship` row with the path in the observed string.
- AC-3: Given a project with no `version_sync`, when a member issue of a promoted batch is closed, then the `ship` row skips with the "not applicable" reason; given a direct (non-batch) merge in a `version_sync` project, the row skips with the "batch-scoped" reason.
- AC-4: Given a projects.yaml containing comments and several projects, when the dashboard saves one project's `version_sync`, then every byte outside that project's `version_sync` key is unchanged (round-trip test).
- AC-5: Given a promoted batch whose members have `pending` ship records, when the operator ships a version from the batch card's Ship version action, then the records flip to `passed` and the DoD row passes.
- AC-6: Given the project settings UI with no `version_sync` configured, when the section renders, then it displays an explicit "this project skips ship" state; with a `partial` latest outcome, it names the failing paths.
- AC-7: `npm run typecheck`, `npm run lint`, and `npm test` pass with the new row and modules; the doc-drift test stays green with the renumbered table.
