# PAN-3293 — `pan restart` must verify the port's listener is its own spawn before reporting success

**Issue:** https://github.com/eltmon/overdeck/issues/3293
**Author:** planning agent (claude-fable-5), 2026-07-30, auto mode
**Verified against:** branch `feature/pan-3293` @ `a584bc6cb2`

## Glossary

- **Dashboard server** — `dist/dashboard/server.js`, the Node 22 process serving the
  API port (default 3011) and frontend port (default 3010).
- **Health probe** — `GET http://127.0.0.1:<apiPort>/api/health`, which returns
  `{ status: 'ok', repoRoot, mode }` (route: `src/dashboard/server/server.ts:134-138`,
  payload: `getDashboardIdentity()` in `src/dashboard/server/identity.ts:17-22`).
- **Lifecycle primitives** — `stopDashboard` / `waitForDashboardHealth` /
  `restartDashboard` in `src/lib/platform-lifecycle.ts`, shared by `pan restart`
  (`src/cli/commands/restart.ts:459-462`), `pan up` (`src/cli/commands/up.ts:216-222`),
  and (transitively) the supervisor sidecar.
- **Spawn handle** — `DashboardSpawnHandle` (`src/lib/platform-lifecycle.ts:345-347`),
  currently `{ stop: () => Promise<void> | void }`, returned by
  `spawnDashboardDetached()` (`src/cli/commands/restart.ts:240`).
- **systemd spawn path** — `spawnDashboardSystemdUnit()` (`src/cli/commands/restart.ts:304`)
  launches the server via `systemd-run --user --unit overdeck-dashboard-<ts> --collect`;
  the CLI never sees the server's pid directly.
- **Supervisor sidecar** — `src/supervisor/server.ts` (port 3012). Its
  `POST /restart-dashboard` spawns `pan restart --dashboard` via
  `createSupervisorRestartSpawner` (`src/supervisor/restart-spawn.ts`); the spawner's
  `done` promise **already rejects on non-zero child exit** (restart-spawn.ts:127-139),
  so a truthfully-failing `pan restart` propagates to the watchdog.
- **Squatter** — a process (typically the previous dashboard server) that still owns
  the port's LISTEN socket when a new server is spawned.
- **#3099 rule** — never kill the freshly spawned server on a health-gate failure
  (comment at `src/lib/platform-lifecycle.ts:365-378`); it is left running with
  `recovery: 'dashboard-left-running'`.

## Problem

`pan restart` declares `✓ Dashboard restarted and healthy` when *any* process returns
200 on `/api/health`. On 2026-07-29 the old server (pid 56538) survived teardown, kept
port 3011, answered the probe, and the fresh spawn crash-looped on EADDRINUSE for ~25
minutes while the CLI, the supervisor (`202 {ok:true}`), and the operator all believed
the restart succeeded. Two concrete code gaps:

1. **The health gate cannot tell servers apart.** `waitForDashboardHealthPromise`
   (`src/lib/platform-lifecycle.ts:247-284`) supports `expectedIdentity`
   (`repoRoot` + `mode`), but the old and new server report identical identity —
   same cwd, same mode. Nothing ties the 200 to the process just spawned.
2. **Teardown detection can lie silently.** `pidsOnPort()`
   (`src/lib/platform-lifecycle.ts:145-155`) shells `fuser <port>/tcp` with every
   failure swallowed to `[]`. On macOS that syntax matches nothing at all, and any
   fuser miss (address-family blind spots, tool failure) makes `stopDashboardPromise`
   (`:188-247`) see "no pids", kill nothing, and `waitForPortFree` (`:171-179`) report
   the port free immediately — the exact preconditions of the incident.

## Proposal (decisions made)

**D1 — pid-echo is the primary ownership gate.** `/api/health` gains a `pid` field
(`process.pid`). The spawn paths report the new server's pid to the CLI, and
`waitForDashboardHealth` accepts `expectedPid`: a 200 whose payload pid differs from
(or omits) the expected pid is *not* healthy. Chosen over lsof-parsing as the primary
gate because it is cross-platform, race-free, and identifies the actual responder;
port probes remain for teardown verification and for naming the squatter in errors.
A pre-fix old server that answers without a `pid` field correctly fails the gate —
that is the incident scenario.

**D2 — port probing becomes multi-tool and dual-stack.** `pidsOnPort()` tries
`lsof -nP -iTCP:<port> -sTCP:LISTEN -t` first (works on Linux and macOS, covers IPv4
and IPv6), then falls back to `fuser <port>/tcp`, then to parsing `ss -ltnp`. If every
probe tool is unavailable, teardown logs a warning and proceeds — the D1 pid gate
still guarantees a truthful success/failure verdict.

**D3 — EADDRINUSE in the child's early output is a hard failure.** The restart flow
records the byte offset of `DASHBOARD_LOG_FILE` (`src/lib/platform-lifecycle.ts:75`)
before spawning; while polling health it scans bytes appended after that offset. An
`EADDRINUSE` match fails the restart immediately, naming the port's owning pid and
command via the probe + `describePid()` (`:181-188`).

**D4 — failures leave processes alone and name pids.** Per the #3099 rule the fresh
spawn is never reaped, and the squatter is not auto-killed at health time either
(teardown already had its chance; auto-killing here could loop). The `StageError`
names the owning pid + command and exits non-zero, so `recordRestartStatus` records
failure and the supervisor's `done` rejection marks the watchdog restart failed.

**D5 — supervisor reconciliation is transitive.** Because every supervisor/watchdog/
browser restart path shells out to `pan restart --dashboard` and the spawner already
rejects on non-zero exit, no separate supervisor-side port-reconciliation loop is
added. The hardened `stopDashboardPromise` is what detects and kills an orphaned
predecessor on every restart, regardless of who initiates it.

**D6 — the operator comment's generation-deleter hunt and CLI-symlink integrity guard
are out of scope.** They concern the `pan reload` deployment plane, are independently
shippable, and would push this plan past the subsystem lint. They are recorded in
NonGoals; a sibling issue should be filed (references PAN-3264).

## Requirements

- **FR-1** `GET /api/health` returns `pid` (the serving process's `process.pid`)
  alongside `status`, `repoRoot`, `mode`.
- **FR-2** Both dashboard spawn paths expose the new server's pid to the caller:
  plain spawn via `child.pid`; systemd path by resolving the unit's `MainPID`
  (polling until non-zero, bounded).
- **FR-3** `waitForDashboardHealth` accepts `expectedPid`; with it set, success
  requires an OK response whose payload pid equals `expectedPid`. On timeout the
  `StageError` names the pid (and command, when resolvable) that actually answered
  or owns the port. Without `expectedPid`, behavior is unchanged (watchdog/peer
  callers keep working).
- **FR-4** `restartDashboard` fails fast (before the health timeout) when
  `EADDRINUSE` appears in the dashboard log after the spawn offset, and the failure
  message names the owning pid; `pan restart` exits non-zero.
- **FR-5** `pidsOnPort()` detects LISTEN owners on both IPv4 and IPv6 via
  lsof-first multi-probe with fuser and ss fallbacks, on Linux and macOS.
- **FR-6** `stopDashboardPromise` verifies the pids it targeted are dead
  (`process.kill(pid, 0)` → ESRCH) after escalation, and its failure names
  surviving pids; old-server teardown is never inferred from an HTTP 200.
- **NFR-1** No `execSync` in `src/lib/**` or any server-reachable code; all new
  probing/polling there is async. (`src/cli/commands/restart.ts` may keep its
  existing `execFileSync` style for systemd calls.)
- **NFR-2** All tests exercising polling/delays use `vi.useFakeTimers()` +
  `advanceTimersByTimeAsync`; no real-clock waits.
- **NFR-3** `waitForDashboardHealth`'s options remain backward compatible; no
  existing caller signature breaks (`up.ts`, watchdog, tests).

### 3. `pids-on-port-multiprobe` — reliable dual-stack listener detection (FR-5)

**Files:** `src/lib/platform-lifecycle.ts`,
`tests/unit/lib/platform-lifecycle.test.ts`.

Before (`platform-lifecycle.ts:145-155`): single `fuser ${port}/tcp` with `|| true`
and a catch returning `[]`. After: try in order, returning the first probe that
*executes successfully* (an empty result from a working probe means "port free"):
1. `lsof -nP -iTCP:${port} -sTCP:LISTEN -t` (exit 1 with empty stdout = no listeners);
2. `fuser ${port}/tcp`;
3. `ss -ltnp` parsed for `:${port} ` and `pid=(\d+)`.
If every tool fails to execute, log one warning (`console.warn`) and return `[]` —
the FR-3 pid gate remains the correctness backstop. All probes via `execAsync`
(NFR-1). Unit-test the fallback order and the ss parser with injected exec fakes.

## Acceptance criteria (mechanically checkable, map 1:1 to items)

1. `curl /api/health` on a running dashboard returns a `pid` equal to the server
   process's pid (item 1).
2. `spawnDashboardDetached(...).pid()` resolves to the live server pid on both spawn
   paths, and `null` when the unit died (item 2).
3. With a squatter answering health, `restartDashboard` rejects at the health
   deadline with a message naming the responder pid; with a matching pid it resolves
   (items 4, 7).
4. An `EADDRINUSE` line appended to the watched log after spawn causes rejection
   before the health deadline, naming the port owner (item 5).
5. `pidsOnPort` returns the listener pid when lsof is available, falls back to
   fuser/ss when not, and returns `[]` with a single warning when no tool executes
   (item 3).
6. After `stopDashboard`, every targeted pid is ESRCH-dead or the call rejects
   naming survivors (item 6).
7. `npm run typecheck`, `npm run lint`, `npm test` pass; new tests use fake timers
   exclusively for delays (all items).
8. The two named docs describe the pid-verified success contract (item 8).
