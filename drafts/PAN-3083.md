# PAN-3083 — Passed+ready issues get re-dispatched for review, knocking them out of the ready queue and invalidating UAT generations

**Issue:** https://github.com/eltmon/overdeck/issues/3083
**Planning mode:** `pan plan --auto` (non-interactive; decisions recorded in `plan.autoDecisions[]`)

## Glossary

- **Review dispatch** — spawning the review role (convoy) for an issue, via `spawnReviewRoleForIssue()` in `src/lib/cloister/review-agent.ts`.
- **Durable review-request intent (`reviewRequestedAt`)** — an ISO timestamp written by `pan done` (`src/cli/commands/done.ts:802-807`) into the per-issue journal record *before* any HTTP progression, so a dropped reactive trigger survives. The host "auto-heals" by reconciling on read: `getReviewStatusSync()` calls `maybeAutoDispatchReviewHostSide()` (`src/lib/review-status.ts:714`, and via the journal reconcile at `src/lib/review-status.ts:706`).
- **`reviewSpawnedAt`** — ISO timestamp stamped when a review is actually dispatched (`src/lib/cloister/review-agent.ts:514`, and `:325` for review-mode `none`). An intent is *serviced* when `reviewRequestedAt <= reviewSpawnedAt`.
- **`needsReviewDispatch()`** — the PURE dispatch-decision predicate in `src/lib/review-dispatch-decision.ts:19`. Returns true when an un-serviced request exists, review is not `reviewing`, and the issue is not `merged`. **It does not check `passed` or `readyForMerge` — that is the defect.**
- **`readyForMerge`** — event-driven derived flag (PAN-1650): true when review+test+verification gates pass (`src/lib/review-status.ts:256-274`).
- **Journal record** — the per-issue permanent record on `overdeck-state` (`records/<issue>.json`); the SQLite row is a rebuildable cache. `enrichReviewNotesFromRecordSync()` (`src/lib/overdeck/review-status-record-sync.ts:88`) overlays the journal's `reviewRequestedAt` onto **every read**, so a stale journal intent resurrects even if the DB row is cleared.
- **Workspace verdict fallback** — sandbox-writable verdict drop at `<workspace>/.overdeck/pipeline-verdict.json` (PAN-2583). Its drain preserves absent keys unless they are listed in `clearedFields`, which is limited to `FALLBACK_CLEARABLE_FIELDS` (`src/lib/overdeck/review-status-record-sync.ts:94-98`).
- **UAT generation** — an assembled batch of ready issues. The reconciler (`src/lib/cloister/uat-reconciler.ts:134-149`, `isStale()`) invalidates a live generation when a bundled member "left the ready queue".
- **Regression guard** — `setReviewStatusSync` rejects `passed → reviewing` writes that don't reset `mergeStatus` (`src/lib/review-status.ts:190-194`). It blocks the *status* write, not the *dispatch* — and rejecting the spawn's write also discards the `reviewSpawnedAt` stamp that would have marked the intent serviced, which is why the loop never converges.

## Problem

`needsReviewDispatch` re-dispatches review for issues that already **passed review and are queued to merge**. Live evidence (PAN-3037, 2026-07-25): `reviewed_at_commit`, `last_verified_commit`, and workspace HEAD all `93ad317654`, yet the host repeatedly auto-dispatched review from the durable journal intent, the issue flipped `review=passed test=passed ready=1` → `review=reviewing ready=0`, and the UAT reconciler invalidated `uat/pan-reef-0725` because the member left the ready queue. `review_retry_count=0` and `auto_requeue_count=0` — retry accounting never registers it. Each cycle burns a full review convoy.

**The loop mechanism** (verified in code):

1. A stale `reviewRequestedAt` newer than `reviewSpawnedAt` sits in the journal. (Provenance for PAN-3037 not fully root-caused; see Hazards H7. The fix closes the loop regardless of provenance.)
2. Every status read runs `maybeAutoDispatchReviewHostSide()`; `needsReviewDispatch` returns true because neither `passed` nor `readyForMerge` is checked (`src/lib/review-dispatch-decision.ts:25-28`). The 30s throttle (`src/lib/review-status.ts:507`) bounds the rate, not the loop.
3. The spawn's `{ reviewStatus: 'reviewing', reviewSpawnedAt }` write is rejected by the regression guard (passed→reviewing without mergeStatus reset), so the intent is never marked serviced — the predicate stays true forever.
4. Whenever a `reviewing` write does land (e.g. via a path the guard does not cover — `src/lib/review-status-json.ts:61` has a sibling copy), the issue leaves the ready set and the UAT generation is torn down.

The sibling recovery path gets it right: `maybeRecoverTestVerdictHostSide` returns early on `status.mergeStatus === 'merged' || status.readyForMerge` (`src/lib/review-status.ts:564`).

**Why genuine re-review still works with the new guards:** both legitimate re-review paths reset `reviewStatus` to `'pending'` before (or along with) writing a fresh intent:

- New commit after a pass: `pan done` detects HEAD ≠ `reviewedAtCommit`, persists a fresh `reviewRequestedAt`, and resets `reviewStatus/testStatus/mergeStatus` to pending (`src/cli/commands/done.ts:780-855`).
- Explicit operator re-request: `POST /api/review/:issueId/request` rejects `passed` unless `force`/`nudge`; `force` performs a full reset to pending before dispatch (`src/dashboard/server/routes/workspaces/review-pipeline.ts:441-504`).

So while `reviewStatus` is still `'passed'`, any pending intent is stale by construction.

## Requirements

- **FR-1:** `needsReviewDispatch` returns `false` when `reviewStatus` is `'passed'` or `'skipped'`, regardless of `reviewRequestedAt`/`reviewSpawnedAt` values.
- **FR-2:** `needsReviewDispatch` accepts a `readyForMerge?: boolean` param and returns `false` when it is `true`, matching `maybeRecoverTestVerdictHostSide`.
- **FR-3:** `maybeAutoDispatchReviewHostSide` passes `readyForMerge` from the status into the predicate. (The deacon call site `src/lib/cloister/deacon.ts:1174` passes the whole status object, so it picks up the new field structurally — verify, don't change.)
- **FR-4:** When a terminal review verdict lands via `setReviewStatusSync` (`update.reviewStatus` transitions to `passed`, `blocked`, `failed`, or `skipped`), a **serviced** `reviewRequestedAt` (requestedAt ≤ spawnedAt, or `reviewSpawnedAt` absent) is cleared from the merged status, so it is removed from the DB row AND the journal record's pipeline block (JSON.stringify drops `undefined` keys; `projectPipeline` at `src/lib/pan-dir/records.ts:126` writes `status.reviewRequestedAt` directly with no `?? existing` resurrect).
- **FR-5:** An **unserviced newer** request (`reviewRequestedAt > reviewSpawnedAt`, both present) survives a terminal verdict write unchanged.
- **FR-6:** `'reviewRequestedAt'` is added to `FALLBACK_CLEARABLE_FIELDS` (`src/lib/overdeck/review-status-record-sync.ts:94`) so a sandboxed verdict write that cleared the intent propagates the clear through the workspace fallback drain instead of resurrecting it from the record.
- **FR-7:** Regression coverage proves genuine dispatch still fires: predicate returns `true` for `reviewStatus: 'pending'` with an un-serviced request (the post-`pan done` and post-operator-force shapes).
- **FR-8:** A test asserts a UAT generation whose member has `review=passed, test=passed, ready=1` and a stale `reviewRequestedAt` is NOT invalidated: the predicate returns false → the member never leaves the ready set → `reconcileUatGenerations` does not invalidate.
- **FR-9:** `docs/REVIEW-AGENT-ARCHITECTURE.md` documents the full intent lifecycle: written by `pan done`, serviced at spawn (`reviewSpawnedAt`), consumed at terminal verdict, and the passed/ready dispatch guards.
- **NFR-1:** `needsReviewDispatch` stays a pure function — no I/O, no imports beyond types.
- **NFR-2:** No test may rely on real wall-clock delays; any throttle/backoff interaction uses `vi.useFakeTimers()` (repo rule).

## Design decisions (made here, not by the work agent)

- **D1 — Guard both `passed` and `skipped`.** `skipped` is the review-mode-`none` success verdict (`src/lib/cloister/review-agent.ts:321-331`) and advances the lifecycle exactly like `passed`; a resurrected newer intent would loop identically on it.
- **D2 — Consume conditionally, not unconditionally.** Clearing on verdict only when the intent is serviced (requestedAt ≤ spawnedAt) preserves a genuinely newer mid-review request (new commit + `pan done` while the convoy runs). When `reviewSpawnedAt` is absent, clear anyway — the verdict itself is proof the request was serviced.
- **D3 — No verdict-timestamp param in the predicate.** The AC's "unless a newer review request postdates the passing verdict" is satisfied structurally: genuine re-requests reset `reviewStatus` to `'pending'`, so the `passed` guard never sees them. Keeping the predicate's input surface small keeps it pure and testable.
- **D4 — Consume on ALL terminal verdicts** (`passed`/`blocked`/`failed`/`skipped`), not just `passed`. Any terminal verdict services the request that produced its cycle; after `blocked`/`failed` the work agent's next `pan done` writes a fresh intent.
- **D5 — Do not weaken the regression guards** (`src/lib/review-status.ts:190-214`, `src/lib/review-status-json.ts:61`). They are the last line of defense; the fix is upstream in the predicate + intent consumption.
- **D6 — Implementation point for FR-4** is inside `setReviewStatusSync` after `merged` is computed (`src/lib/review-status.ts:227`) and before `updateIssueRecordForReviewStatusSync(issueId, updated)` (`:321`), by deleting the key or assigning `undefined` explicitly on the object passed to `normalizeReviewStatusSync`. Note the `{...status, ...update}` spread: a key explicitly present with value `undefined` DOES override, so clearing must be an explicit assignment/delete on `merged`, not an omitted key in `update`.

### Before/after — `src/lib/review-dispatch-decision.ts`

Before (`:19-29`):

```ts
export function needsReviewDispatch(params: {
  reviewRequestedAt?: string;
  reviewSpawnedAt?: string | number;
  reviewStatus?: string;
  mergeStatus?: string;
}): boolean {
  if (!params.reviewRequestedAt) return false;
  if (params.reviewStatus === 'reviewing') return false;
  if (params.mergeStatus === 'merged') return false;
  return !params.reviewSpawnedAt || Date.parse(params.reviewRequestedAt) > new Date(params.reviewSpawnedAt).getTime();
}
```

After (shape — keep the existing doc comment, extend it):

```ts
export function needsReviewDispatch(params: {
  reviewRequestedAt?: string;
  reviewSpawnedAt?: string | number;
  reviewStatus?: string;
  mergeStatus?: string;
  readyForMerge?: boolean;
}): boolean {
  if (!params.reviewRequestedAt) return false;
  if (params.reviewStatus === 'reviewing') return false;
  // PAN-3083: a passed/skipped verdict or a merge-queued issue must never be re-dispatched
  // from a stale durable intent — genuine re-review paths reset reviewStatus to 'pending'
  // (pan done on a new commit; operator force re-request) before writing a fresh intent.
  if (params.reviewStatus === 'passed' || params.reviewStatus === 'skipped') return false;
  if (params.readyForMerge === true) return false;
  if (params.mergeStatus === 'merged') return false;
  return !params.reviewSpawnedAt || Date.parse(params.reviewRequestedAt) > new Date(params.reviewSpawnedAt).getTime();
}
```

Caller update (`src/lib/review-status.ts:510-515`): add `readyForMerge: status.readyForMerge` to the params object.

### Before/after — intent consumption in `setReviewStatusSync`

Insert after the `merged` computation (`src/lib/review-status.ts:227`, after the `reviewerVerdicts` merge at `:232-234`):

```ts
// PAN-3083: a terminal review verdict CONSUMES the durable request intent that produced
// this cycle. A serviced intent left in place outlives the verdict and re-fires dispatch
// on every status read (the predicate guards are belt; this is suspenders). An unserviced
// NEWER request (arrived mid-review via pan done on a new commit) is preserved.
const isTerminalReviewVerdict =
  update.reviewStatus !== undefined &&
  ['passed', 'blocked', 'failed', 'skipped'].includes(update.reviewStatus) &&
  update.reviewStatus !== status.reviewStatus;
if (isTerminalReviewVerdict && merged.reviewRequestedAt) {
  const spawnedMs = merged.reviewSpawnedAt !== undefined
    ? new Date(merged.reviewSpawnedAt).getTime()
    : undefined;
  const serviced = spawnedMs === undefined || Date.parse(merged.reviewRequestedAt) <= spawnedMs;
  if (serviced) merged.reviewRequestedAt = undefined;
}
```

The cleared value flows into `updated` → `updateIssueRecordForReviewStatusSync` → `projectPipeline` (which writes the field verbatim, and `JSON.stringify` drops the `undefined` key) → journal record no longer carries the intent → `enrichReviewNotesFromRecordSync`'s overlay (`pipeline.reviewRequestedAt ?? status.reviewRequestedAt`) stops resurrecting it. A test MUST verify the journal-side clear, not just the in-memory result (Hazard H1).

```ts
const FALLBACK_CLEARABLE_FIELDS = [
  'strikeTransportRetryCount',
```

becomes:

```ts
const FALLBACK_CLEARABLE_FIELDS = [
```

`writeWorkspaceVerdictFallbackSync` already lists any of these fields that are `undefined` on the written status into `clearedFields` (`:180-182`), and the drain honors `clearedFields` on merge (`:356` comment). No other change needed; the risk surface is that every fallback write with an absent `reviewRequestedAt` now clears it — safe, because the fallback is always written from the full merged status (`updated`), where absence means genuinely cleared or never set.

## Acceptance criteria (map 1:1 to work items)

- AC-1 (item 1): `needsReviewDispatch` returns false for `{reviewStatus:'passed', readyForMerge:true, reviewRequestedAt: newer, reviewSpawnedAt: older}` and for `{readyForMerge:true}` with any request timestamps; returns true for `{reviewStatus:'pending', reviewRequestedAt: newer}`. `npx vitest run tests/unit/lib/review-dispatch-decision.test.ts` passes.
- AC-2 (item 2): after `setReviewStatusSync(issue, {reviewStatus:'passed'})` on a status whose `reviewRequestedAt <= reviewSpawnedAt`, the returned status and the journal pipeline record both lack `reviewRequestedAt`; with `reviewRequestedAt > reviewSpawnedAt` the field survives. `npx vitest run tests/unit/lib/review-status.test.ts` passes.
- AC-3 (item 3): a workspace verdict fallback written from a cleared status carries `clearedFields: ['reviewRequestedAt']` (possibly among others) and its drain removes the field from the record. `npx vitest run tests/unit/lib/overdeck/review-status-record-sync-fallback.test.ts` passes.
- AC-4 (item 4): the new reconciler test shows no invalidation for the passed+ready+stale-intent member and invalidation for a genuinely departed member. `npx vitest run tests/unit/lib/cloister/uat-reconciler.test.ts` passes.
- AC-5 (item 5): `docs/REVIEW-AGENT-ARCHITECTURE.md` states the four lifecycle stages of `reviewRequestedAt` (written / serviced / consumed / guarded) and references PAN-3083.

## Hazards

- **H1:** The journal overlay (`enrichReviewNotesFromRecordSync:88`) resurrects `reviewRequestedAt` from the record on every read. Clearing ONLY the DB row does nothing; the clear must reach the journal record (it does via `projectPipeline` writing the field verbatim — but the test must assert the record-side clear).
- **H2:** In `{...status, ...update}`, an `update` key explicitly set to `undefined` overrides — but the FR-4 clear happens on `merged` after the spread (per D6), not by adding keys to callers' `update` objects.
- **H3:** The fallback drain preserves absent keys unless listed in `clearedFields` — item 3 is required or a sandboxed verdict write silently resurrects the intent.
- **H4:** Do not weaken the `passed→reviewing` regression guard to "fix" the loop; the guard rejecting the spawn's write (and its `reviewSpawnedAt` stamp) is why the intent never counted as serviced, but the correct fix is refusing the dispatch upstream.
- **H5:** Pre-existing race, OUT of scope: `pan done` on a new commit resets status to `pending` while a convoy is mid-flight; the late verdict write flips it back to terminal. Merge-time reviewed-commit gates cover the safety; do not attempt to fix here.
- **H6:** Any test touching the 30s dispatch throttle or drain retry timers MUST use `vi.useFakeTimers()` (repo rule; OOM history).
- **H7:** Provenance of PAN-3037's stale intent (how `reviewRequestedAt` became newer than `reviewSpawnedAt` after a pass) is not fully root-caused; candidate writers are the deacon orphaned-completions recovery (`src/lib/cloister/deacon.ts:1199`) and polyrepo wrapper-blind stamp sites (PAN-3076 territory). The guards + consumption close the loop for ALL provenances; if the work agent finds the writer, note it on the issue rather than expanding scope.

## NonGoals

- No change to the 30s dispatch throttle or `dispatchReviewHostSide`.
- No weakening or modification of the reviewStatus regression guards (`review-status.ts:190-214`, `review-status-json.ts:61`).
- No root-cause repair of how the stale intent's timestamp was produced for PAN-3037 (tracked via PAN-3076 / polyrepo anchor work).
- No changes to UAT reconciler invalidation semantics (`isStale` stays as-is; it is correct given a stable ready set).
- No polyrepo/composite-anchor changes (PAN-3076, PAN-2948).
