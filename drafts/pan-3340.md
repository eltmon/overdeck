# PAN-3340 — Dashboard: Review action opens a submenu to pick review mode (Full / Quick / None)

**Issue:** https://github.com/eltmon/overdeck/issues/3340
**Status:** Draft (auto-planned 2026-07-30)

## Glossary

- **Review action** — the `requestReview` entry in the dashboard issue-action
  registry (`src/dashboard/frontend/src/lib/issueActions.ts:610`), labeled
  "Request review". Rendered on every issue-action surface (kanban card strip,
  cockpit overflow, right-click context menu, pipeline view).
- **Review mode** — per-issue override `reviewMode?: 'quick' | 'full' | 'none'`
  on the durable issue record (`src/lib/pan-dir/record.ts:216`; type at
  `src/lib/config-yaml/schema.ts:361`). `quick` = single reviewer (default),
  `full` = four convoy reviewers + synthesis, `none` = skip AI review
  (verification floor still runs).
- **Record write door** — `updateIssueRecord(project, issueId, mutator)` in
  `src/lib/pan-dir/record-update.ts:471`. The only legal writer of
  `record.reviewMode`; used today by `pan review mode`
  (`src/cli/commands/review-mode.ts:24`) and `POST /api/review/:issueId/config`
  (`src/dashboard/server/routes/workspaces/review-control.ts:713-731`).
- **Trigger route** — `POST /api/review/:issueId/trigger`
  (`src/dashboard/server/routes/workspaces/review-pipeline.ts:121-405`).
  Validates, then responds 200 and dispatches in a background IIFE
  (`review-pipeline.ts:254`).
- **Dispatch** — `spawnReviewRoleForIssue`
  (`src/lib/cloister/review-agent.ts:320-760`). Reads the mode via
  `resolveReviewMode(issueId)` (`review-agent.ts:935-946`): record override →
  `roles.review.mode` config → default `quick`.
- **Submenu** — the `submenu?: { key, label, invoke }[]` field on
  `IssueActionView` (`useIssueActions.ts:35-42`), rendered as an expandable
  sub-list by `IssueActionGroupedBody.tsx:118-141`. Existing example:
  `addToOrderBook` (`useIssueActions.ts:506-515`).
- **Primary strip** — the inline phase-primary buttons rendered by
  `ActionButton` in `IssueActionMenu.tsx:62-77` (kanban cards, pipeline rows).
  `ActionButton` currently invokes directly and does not render submenus.
- **Policies strip** — `IssuePolicyStrip.tsx`; per-issue overrides panel whose
  Mode segmented control POSTs `/api/review/:id/config`
  (`IssuePolicyStrip.tsx:376-380`).

## Problem

Requesting a review and choosing its mode are two disjoint interactions: the
**Review** action dispatches with whatever mode is already resolved, and the
mode is set separately under **Policies**. Both interactions are silent —
`postActionMutation.onSuccess` has no `requestReview` toast
(`useIssueActions.ts:372`), and `IssuePolicyStrip.save()` swallows non-OK
responses (`IssuePolicyStrip.tsx:206-218`). On 2026-07-30 the operator clicked
Review and FULL on MIN-908; neither visibly took effect and the review had to
be dispatched from the CLI.

## Proposal

One interaction: **Review → Full / Quick / None**. The `requestReview` action
gains a submenu of the three modes on every surface, including the primary
strip. Selecting a mode POSTs `{ reviewMode }` to the existing trigger route,
which persists the mode through the record write door **synchronously, before
responding**, then dispatches. Dispatch keeps reading the mode through
`resolveReviewMode` — no new plumbing. A success toast names the chosen mode;
mode-persist failures fail the HTTP response and surface through the existing
error alert. Separately, `IssuePolicyStrip.save()` gains an error toast so the
Policies chip can never fail silently again.

### Decisions (auto mode — recorded in `plan.autoDecisions`)

1. **Single POST**: the trigger route accepts `reviewMode`, rather than the
   frontend POSTing `/config` then `/trigger`. Atomic ordering is guaranteed
   server-side, and a mode-persist failure becomes a synchronous non-200 the
   frontend can surface. A two-POST dance has a partial-failure window.
2. **The strip button becomes a popover**, not "click dispatches with current
   mode". The issue asks for the Review action itself to be a submenu; a
   phase-primary strip button that still dispatches silently on click would
   preserve the exact interaction that bit the operator.
3. **No current-mode checkmark in the submenu.** It would need a
   `GET /api/review/:id/config` per rendered row on kanban/board surfaces.
   The Policies strip remains the mode display.
4. **Background dispatch failures stay on the existing surface**
   (`reviewStatus.reviewNotes` + the pending-operation machinery). In scope is
   making the *click* verifiably take effect: validation and mode persistence
   move before the 200; spawn health is already visible via the spawned agent
   row and review status.
5. **Plain `invoke()` still dispatches with the resolved mode** (no body).
   Programmatic/test paths keep working; the mode body is only sent by submenu
   options. The registry key `requestReview`, its testid, and its gating are
   unchanged — no-loss tests keep passing unmodified.
6. **Submenu labels carry a one-line hint**: "Full — 4-reviewer convoy",
   "Quick — single pass (default)", "None — skip AI review". The pick must be
   self-explanatory without opening docs.

## Requirements

### Functional

- **FR-1** — The Review action exposes exactly three submenu options — Full,
  Quick, None — on every issue-action surface that renders `requestReview`:
  grouped overflow, right-click context menu, and the primary strip.
- **FR-2** — Selecting a mode persists it as the issue's `record.reviewMode`
  through the record write door and dispatches the review in the same POST
  `POST /api/review/:issueId/trigger` with body `{ "reviewMode": "<mode>" }`.
  The dispatched review runs in the chosen mode (convoy for `full`, single
  pass for `quick`, `reviewStatus: 'skipped'` for `none`).
- **FR-3** — The trigger route rejects an invalid `reviewMode` value with a
  400 `{ error }` response and persists nothing. If mode persistence throws,
  the route returns a non-200 response and does not dispatch.
- **FR-4** — A successful mode-selected dispatch shows a `toast.success`
  naming the issue and mode; a failed POST shows the existing error alert
  with the server's error message.
- **FR-5** — A failed save from the Policies strip (`IssuePolicyStrip.save`)
  shows a `toast.error` instead of failing silently.

### Non-functional

- **NFR-1** — No new npm dependencies; reuse `sonner`, the existing submenu
  mechanism, and the existing record write door.
- **NFR-2** — No issue-action registry keys are added, renamed, or removed;
  the no-loss parity tests (`issueActions.no-actions-lost.test.ts`,
  `issue-actions-surface-parity.test.tsx`, `KanbanBoard.test.tsx` snapshot)
  pass without weakening their assertions.
- **NFR-3** — The strip popover is keyboard/screen-reader sane:
  `aria-haspopup="menu"`, `aria-expanded`, and items reachable as buttons;
  it closes on outside click and on selection.
- **NFR-4** — CLI behavior is unchanged: `pan review mode` and
  `pan review restart/request` work exactly as before (the trigger route's
  new body field is optional).

**Steps:**

1. In `review-pipeline.ts`, add an exported pure helper near the other
   module-level helpers (the dirty-gate helper
   `getDirtyWorkspaceErrorForReviewRequestStatus` is the style precedent):

   ```ts
   export type RequestedReviewMode = 'quick' | 'full' | 'none';

   export function parseRequestedReviewMode(body: unknown):
     | { ok: true; mode?: RequestedReviewMode }
     | { ok: false; error: string } {
     const raw = (body as { reviewMode?: unknown } | null)?.reviewMode;
     if (raw === undefined || raw === null) return { ok: true };
     if (raw === 'quick' || raw === 'full' || raw === 'none') return { ok: true, mode: raw };
     return { ok: false, error: `reviewMode must be quick, full, or none, got '${String(raw)}'` };
   }
   ```

2. In the trigger route handler, immediately after `const body = yield*
   readJsonBody;` (`review-pipeline.ts:131`), add:

   ```ts
   const requestedMode = parseRequestedReviewMode(body);
   if (!requestedMode.ok) {
     return jsonResponse({ error: requestedMode.error }, { status: 400 });
   }
   ```

3. After the existing guards and **before** the background IIFE (insert just
   before the `// Respond immediately` comment at `review-pipeline.ts:252`),
   persist the mode synchronously, mirroring the dynamic-import pattern at
   `review-control.ts:713-718`:

   ```ts
   if (requestedMode.mode) {
     const persisted = yield* Effect.promise(async () => {
       try {
         const { resolveProjectForIssue } = await import('../../../../lib/pan-dir/record.js');
         const { updateIssueRecord } = await import('../../../../lib/pan-dir/record-update.js');
         const project = resolveProjectForIssue(issueId);
         await updateIssueRecord(project, issueId, (current) => {
           current.reviewMode = requestedMode.mode;
         });
         return null as string | null;
       } catch (error) {
         return error instanceof Error ? error.message : String(error);
       }
     });
     if (persisted) {
       return jsonResponse({
         error: `Failed to persist review mode for ${issueId}: ${persisted}`,
       }, { status: 500 });
     }
   }
   ```

   Placement note: persist **after** the early-exit guards (invalid issue,
   remote 409, already-reviewed, already-merged, missing workspace, conflict
   gate) so a refused dispatch never writes the mode. Do not persist when the
   route is about to return a guard response.

4. New test file `review-pipeline-review-mode.test.ts` in the same `__tests__`
   directory as `review-pipeline-dirty-gate.test.ts`, testing only the pure

   `quick`/`full`/`none` → `{ ok: true, mode }`; `"FULL"`, `""`, `123`,

   function ActionButton({ view, inline = false, onInvoked }: { view: IssueActionView; inline?: boolean; onInvoked?: () => void }) {
     const [submenuOpen, setSubmenuOpen] = useState(false);
     const hasSubmenu = !!view.submenu?.length;
     return (
       <span className="relative inline-flex">
         <button
           type="button"
           data-testid={`issue-action-${view.action.key}`}

           disabled={!view.enabled || view.isPending}

## Acceptance criteria (1:1 with work items)

- **AC-1 (WI-1):** Given a stopped work agent and no review status, when
  `POST /api/review/PAN-X/trigger` is sent with `{ "reviewMode": "full" }`,
  then the issue record's `reviewMode` is `"full"` before the response
  returns, and the dispatched review runs the convoy path; an invalid mode
  returns 400 and leaves the record untouched.
- **AC-2 (WI-2):** Given the grouped/context action menu on an issue eligible
  for review, when the operator expands Request review, then three options —
  Full, Quick, None — render, and selecting Full POSTs `{ reviewMode: 'full' }`
  to the trigger endpoint and shows a success toast containing the issue id
  and "full".
- **AC-3 (WI-3):** Given a kanban card whose primary strip shows Request
  review, when the operator clicks it, then a popover with the three modes
  opens and no request fires until a mode is picked; picking Quick POSTs
  `{ reviewMode: 'quick' }`; the no-loss parity tests pass unmodified.
- **AC-4 (WI-4):** Given the Policies panel, when the mode save responds
  non-OK, then an error toast appears with the server's message.
- **AC-5 (WI-5):** `docs/ISSUE-VIEW.md` and
  `docs/REVIEW-AGENT-ARCHITECTURE.md` describe the submenu and the trigger
  route's `reviewMode` body as specified.
