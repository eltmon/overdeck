# PAN-3842 — Warn when a tiered-execution tier is configured with a model unsuited to that tier

**Issue:** https://github.com/eltmon/overdeck/issues/3842
**Planned:** 2026-09-16 (auto mode, `pan plan --auto`) against `c7e4ba6d78b` on `feature/pan-3842`.
**Related:** PAN-3836 (the incident), PAN-1791 / PAN-2397 (tiered execution + Always Tiered), PAN-2391 (distribution tiers), PAN-1865 (harness-override badge).

## 0. Glossary

| Term | Meaning in this document |
| --- | --- |
| **Tier** | One entry of `tiered_execution.tiers.<name>` in `~/.overdeck/config.yaml`: a `model`, a `harness`, and the list of `difficulties` it owns. Validated by `validateTieredExecutionConfig` in `src/lib/agents/tier-table.ts:356`. |
| **Crew** | The Settings-page presentation of a tier (`src/dashboard/frontend/src/components/Settings/sections/tiered-crews.ts:19`). One crew serializes to one tier on save. |
| **Distribution tier** | A tier that declares `distribution: [{model, harness, weight}]` instead of a single model (PAN-2391). `TierDefinition.distribution` at `src/lib/agents/tier-table.ts:29`. |
| **Supervisor** | `tiered_execution.supervisor` — the standing model that reviews every tier's commits and, by default, owns inspection (`TieredExecutionSupervisorConfig`, `src/lib/agents/tier-table.ts:44`). |
| **Difficulty** | `XBriefDifficulty = 'trivial' \| 'simple' \| 'medium' \| 'complex' \| 'expert'` (`src/lib/xbrief/types.ts:30`). Each plan item carries `metadata.difficulty`. |
| **Capability class** | NEW. A three-value classification of a model id: `frontier` (best-in-class reasoning, premium price), `workhorse` (balanced, the default implementation class), `small` (fast/cheap, for trivial and simple edits). Defined once in `src/lib/model-capability-class.ts` (new). |
| **Difficulty band** | NEW. For each difficulty, the minimum and maximum capability class that is *appropriate*. Below the minimum is an "underpowered" warning; above the maximum for every difficulty a tier owns is an "overpowered" (cost) warning. |
| **Fitness warning** | NEW. One structured warning object produced by the checker (`checkTierFitness` in `src/lib/agents/tier-fitness.ts`, new). Never an error; the operator may configure a cheap model deliberately. |
| **Model catalog** | The union of `PROVIDERS[*].models` (`src/lib/providers.ts:70`) and the keys of `MODEL_CAPABILITIES` (`src/lib/model-capabilities.ts:69`). The Settings page uses its own mirror, `MODELS_BY_PROVIDER` (`src/dashboard/frontend/src/components/Settings/modelCatalog.ts`). |
| **Enabled provider** | A provider present in `config.enabledProviders` (`Set<ModelProvider>`, `src/lib/config-yaml/schema.ts:784`, default `new Set(['anthropic'])` at `src/lib/config-yaml/defaults.ts:44`). The Settings GET payload exposes it as `models.providers.<name>: boolean` (`src/lib/settings-api.ts:690`). This is the single canonical "this provider is usable" signal. |
| **Implicit tier** | When tiered execution is off, every item is staffed from `roles.work` through `resolveImplicitStaffing` (`src/lib/agents/staffing.ts:79`). The "role model that feeds a tier" in the issue text. |
| **Single-work path** | A non-swarm issue runs ONE foreground work agent. `resolveSingleWorkTierSpawnParams` (`src/lib/agents/spawn-prep.ts:299`) staffs it from the tier of the **first dispatchable item** — the whole issue then runs on that model. This is exactly how PAN-3836 landed on haiku. |
| **Slot path** | A swarm dispatches one registered slot per item; `resolveSlotTierSpawnParams` (`src/lib/agents/spawn-prep.ts:242`) staffs each slot from that item's tier. |
| **`pan doctor`** | `doctorCommand` in `src/cli/commands/doctor.ts:705`. Pushes `CheckResult { name, status: 'ok'\|'warn'\|'error', message, fix? }` (`src/cli/commands/doctor.ts:205`) rows; each check lives in its own `doctor-<topic>.ts` module with a sibling test. |

## 1. Problem

On 2026-09-16 PAN-3836 (14 items: routes, a page, a hook, CLI) ran end-to-end on `claude-haiku-4-5` because its first xBRIEF item was `simple` and the `trivial-simple` tier mapped to haiku. Six review cycles and a UAT rejection followed. Nothing in the product warned the operator that the mapping was risky, and nothing at spawn time said "this agent is about to run a plan whose hardest item is `complex` on a small-class model".

Today:

- `validateTieredExecutionConfig` (`src/lib/agents/tier-table.ts:356`) rejects unknown models, unknown harnesses, and ToS-policy violations as hard errors, but has no notion of *capability*.
- `pan doctor` never loads or validates `tiered_execution` at all.
- The Settings crew row shows exactly one advisory badge, `⚠ harness overrides provider default — PAN-1865` (`src/dashboard/frontend/src/components/Settings/sections/CrewRow.tsx:54`).
- The spawn paths log `[DEBUG] Selected model: …` (`src/lib/agents/spawn.ts:633`) and nothing about fit.

## 2. Proposal (summary)

1. Add a **capability-class table** beside the model catalog, with a completeness test so every catalog model has a class.
2. Add one **pure checker** (`checkTierFitness`) that turns a tier table + context into fitness warnings. It has no I/O and no node imports so the Settings page can call it on the *unsaved draft* and `pan doctor` / spawn can call it on the loaded config.
3. Surface warnings in three places: a `pan doctor` row, a badge on each affected crew row and the supervisor block in Settings, and one `[spawn]` log line per work-agent spawn (slot path and single-work path).
4. The single-work spawn check compares the staffed model against the **maximum difficulty across all dispatchable plan items**, which is the check that would have caught PAN-3836.

## 3. Decisions (made here, not by the executor)

- **D1 — Class table is its own module.** `src/lib/model-capability-class.ts` exports the table and `capabilityClassOf`. It does NOT import `model-capabilities.ts` (that file imports `effect` and the context-window module and would break the frontend import). It imports only `MODEL_DEPRECATIONS` from `src/lib/model-deprecations.ts:4` (a plain table, `import type` only from settings) so a retired id with no row of its own resolves to its replacement's class. **Revised 2026-09-16 (R1):** `capabilityClassOf` reads the literal id FIRST and hops `MODEL_DEPRECATIONS` only as a fallback. The original wording said replacement-first unconditionally, which contradicted the §5.1 table — that table lists `glm-4.7` and `glm-4.7-flash` with their own classes. Replacement-first made both report `frontier` (via `glm-5.1`). An explicit `--model` override is launched verbatim (`normalizeModelOverrideSync` validates but never rewrites the id), so the check was rating a model that was not executing and silently passed `glm-4.7-flash` on an expert plan. See Revisions.
- **D2 — Class assignments are the table in §5.1.** The work agent copies it verbatim. No re-derivation from benchmark scores.
- **D3 — Difficulty bands are the table in §5.2.** `expert` requires `frontier`; `medium`/`complex` require at least `workhorse`; `trivial`/`simple` accept `small` and treat `frontier` as overpowered.
- **D4 — "Overpowered" fires only when every difficulty the tier owns has `max` below the model's class.** A `trivial-simple-medium` tier on Opus is not overpowered because `medium` allows `frontier`.
- **D5 — Unclassified model ids skip the band checks silently.** Dynamic OpenCode/OpenRouter ids (contain `/` and are discovered at runtime) have no class. They still get the `unknown-model` check when they are not in `knownModelIds`.
- **D6 — Credential check = enabled-provider check.** The checker's context carries `enabledProviders` (from `config.enabledProviders` on the server, from `formData.models.providers` on the frontend). A tier whose model's provider is not enabled produces `provider-not-enabled`. No per-provider API-key probing (three fragmented sources today: `getApiKeysFromEnv`, `config.apiKeys`, Claude/OpenAI auth status). `getProviderAuthMode` (`src/lib/agents/runtime-command.ts:684`) returns `undefined` for most providers regardless of credentials and is NOT used.
- **D7 — No harness-subagent check.** `HarnessBehavior` (`packages/contracts/src/harness-behavior.ts:33`) has no subagent-support field and nothing in the codebase records which harness/model routes can spawn Claude Code subagents. Inventing that table would be guessing (facts-not-guessing rule). The verifiable subset is already enforced: `canUseHarnessSync` rejections are hard errors in the loader, and harness ≠ provider default is the existing PAN-1865 badge. The code enum reserves `'harness-unverified'` for a follow-up; no check ships for it.
- **D8 — Warnings are never errors.** The loader keeps throwing for the existing hard cases; fitness warnings never throw and never block save or spawn.
- **D9 — Warning messages start with the config path** (`tiered_execution.tiers.<name>` or `tiered_execution.supervisor`), matching the loader's error-message convention so the Settings section's existing substring routing (`serverTieredError?.includes('tiered_execution.supervisor')`) keeps working.
- **D10 — Supervisor rule.** A `small`-class supervisor produces `supervisor-underpowered`. No overpowered rule for the supervisor.
- **D11 — Implicit tier.** When `tiered_execution.enabled` is false, `pan doctor` runs the same band check against `roles.work` resolved through `requireModelOverrideSync(resolveModel('work', undefined, config))` — the same pair `resolveImplicitStaffing` uses at `src/lib/agents/staffing.ts:82` — as a pseudo-tier named `default` owning all five difficulties. Path prefix for its messages: `roles.work.model`. When `roles.work.model` is a percent-distribution array, `resolveModel` without a `spawnKey` returns the representative (max-weight) entry (`src/lib/config-yaml/roles.ts:133-136`); the doctor checks that representative only. If resolution throws (unset or unresolvable `roles.work`), the doctor row reports that error and stops — never a hardcoded fallback.
- **D12 — Frontend keeps its own `tier: premium|balanced|fast`** in `modelCatalog.ts`. Reconciling it with the class table is a NonGoal (hazard H3). The Settings badge uses `capabilityClassOf` from the shared module, never the frontend `tier`.

## 4. Requirements

### Functional

- **FR-1** A capability-class table exists in `src/lib/model-capability-class.ts` mapping every static catalog model id to `frontier | workhorse | small`, and a test fails when any id in `PROVIDERS[*].models` or any non-deprecated `MODEL_CAPABILITIES` key lacks a class.
- **FR-2** `checkTierFitness(config, ctx)` returns a `TierFitnessWarning[]` covering: `underpowered`, `overpowered`, `unknown-model`, `provider-not-enabled`, `supervisor-underpowered`. It is pure (no I/O, no node built-ins) and accepts both the lib config shape and the frontend config shape structurally.
- **FR-3** `pan doctor` prints a `Tiered execution` row: `error` when the loader throws `TieredExecutionConfigError`, `warn` listing every fitness warning message, `ok` otherwise. When tiered execution is disabled, the row checks the implicit `roles.work` tier (D11).
- **FR-4** The Settings crew row renders a `⚠` badge per fitness warning affecting that crew (any of its entries), computed from the unsaved draft; the supervisor block renders its own badge for `supervisor-underpowered`.
- **FR-5** The slot spawn path logs one `[spawn] tier fitness:` line when the staffed model's class is below the band minimum for the slot item's difficulty.
- **FR-6** The single-work spawn path logs one `[spawn] tier fitness:` line when the staffed model's class is below the band minimum for the **maximum difficulty across all dispatchable items** of the plan, naming the item(s) that exceed the staffed class.
- **FR-7** No fitness warning throws, blocks a settings save, or aborts a spawn.
- **FR-8** `docs/TIERED-EXECUTION.md` documents the class table, the bands, the three surfaces, and the never-blocking rule; `docs/MODEL_ROUTING.md` documents the class concept; `reference/troubleshooting.mdx` lists the doctor row.

### Non-functional

- **NFR-1** The class module and the checker module have zero imports from node built-ins or from modules that import them (`fs`, `path`, `effect`, `child_process`, `pan-dir`, `projects`, `config-yaml`), so `TieredExecutionSection.tsx` can import them directly like `ProgressPanel.tsx:5` imports `lib/orders/eligibility.js`.
- **NFR-2** Checker cost is O(tiers × entries); it is called on every Settings keystroke through the autosave pipeline and must not fetch.
- **NFR-3** No hardcoded model id appears in the checker or in doctor/spawn/Settings call sites; only the class table names models (rule: no-hardcoded-model-fallbacks).
- **NFR-4** New tests use vitest with no real timers or I/O; spawn tests follow the `vi.mock('../../config-yaml.js')` + `vi.mock('../../xbrief/io.js')` pattern from `src/lib/agents/__tests__/dispatch-tier.test.ts:11-18`.

### 5.3 Warning shape

```ts
export type TierFitnessCode =
  | 'underpowered'          // class rank < band.min for at least one owned difficulty
  | 'overpowered'           // class rank > band.max for EVERY owned difficulty (cost)
  | 'unknown-model'         // model id not in ctx.knownModelIds
  | 'provider-not-enabled'  // ctx.enabledProviders is set and lacks providerOf(model)
  | 'supervisor-underpowered' // supervisor class === 'small'
  | 'harness-unverified';   // reserved (D7) — never emitted in this issue

export interface TierFitnessWarning {
  code: TierFitnessCode;
  /** 'tiered_execution.tiers.<name>' | 'tiered_execution.supervisor' | 'roles.work.model' */
  path: string;
  tierName: string;             // '<name>' | 'supervisor' | 'default'
  model: string;
  harness?: string;
  difficulties: XBriefDifficulty[];
  /** Full operator-facing sentence, starts with `path`. */
  message: string;
}

export interface TierFitnessContext {
  knownModelIds: ReadonlySet<string>;
  classOf: (model: string) => ModelCapabilityClass | undefined;
  providerOf: (model: string) => string | undefined;
  /** undefined ⇒ skip the provider check (frontend without provider info). */
  enabledProviders?: ReadonlySet<string>;
}
```

Message templates (exact strings, `${}` interpolated):

- underpowered: `` `${path}: ${model} is a ${cls}-class model but this tier owns ${bad.join(', ')} — ${detail}` ``
  - **Revised 2026-09-16 (R2).** `${detail}` is `items at that difficulty need at least ${needed}-class` when every failing difficulty shares one requirement (byte-identical to the original template). When they differ, it groups them by requirement, strongest first, joined with `'; '`: e.g. `expert needs at least frontier-class; medium, complex need at least workhorse-class`. The original single-`${needed}` form stated the maximum requirement across a mixed list, so `medium, complex, expert` on a small model read as though `medium` required `frontier`. Classification is unchanged — the maximum still decides whether the warning fires; only the sentence is corrected.
- overpowered: `` `${path}: ${model} is a frontier-class model but this tier only owns ${difficulties.join(', ')} — a ${maxAllowed}-class model would cost less` ``
- unknown-model: `` `${path}: ${model} is not in the model catalog` ``
- provider-not-enabled: `` `${path}: ${model} belongs to provider '${provider}', which is not enabled in Settings › Providers` ``
- supervisor-underpowered: `` `tiered_execution.supervisor: ${model} is a small-class model; the supervisor reviews every tier's commits and should be workhorse-class or better` ``

### WI-2 — Pure fitness checker (FR-2, FR-7, NFR-1, NFR-2, NFR-3)

**Files:** `src/lib/agents/tier-fitness.ts` (new), `src/lib/agents/__tests__/tier-fitness.test.ts` (new).

`import type { TierDefinition, TieredExecutionSupervisorConfig } from './tier-table.js'` only (that module's runtime imports reach `fs`). `import type { XBriefDifficulty } from '../xbrief/types.js'`. `import { capabilityClassOf, type ModelCapabilityClass } from '../model-capability-class.js'` is allowed but the checker still takes `ctx.classOf` so tests inject.

Exports:

```ts
export const CAPABILITY_CLASS_RANK, DIFFICULTY_CLASS_BANDS;         // §5.2
export type TierFitnessCode, TierFitnessWarning, TierFitnessContext; // §5.3

/** Structural input so both lib and frontend config shapes fit. */
export interface TierFitnessConfig {
  tiers: Record<string, { model: string; harness?: string; difficulties: XBriefDifficulty[]; distribution?: Array<{ model: string; harness?: string; weight: number }> }>;
  supervisor?: { model: string; harness?: string };
}

export function checkTierFitness(config: TierFitnessConfig, ctx: TierFitnessContext): TierFitnessWarning[];

/** One staffed (model, harness) against a set of difficulties — the spawn-time check. */
export function checkStaffingFitness(
  staffing: { tierName: string; model: string; harness?: string; path?: string },
  difficulties: XBriefDifficulty[],
  ctx: TierFitnessContext,
): TierFitnessWarning[];   // only 'underpowered' | 'unknown-model' | 'provider-not-enabled'
```

Algorithm for each tier (entries = `distribution ?? [{model, harness, weight: 100}]`), for each entry:
1. `unknown-model` if `!ctx.knownModelIds.has(entry.model)`; continue to next entry (no band checks).
2. `provider-not-enabled` if `ctx.enabledProviders` is defined and `providerOf(model)` is defined and not in the set.
3. `cls = ctx.classOf(model)`; if undefined ⇒ stop (D5).
4. `bad = difficulties.filter(d => rank(cls) < rank(band[d].min))`; if non-empty ⇒ `underpowered` with `difficulties: bad`.
5. If `bad` is empty and `difficulties.every(d => rank(cls) > rank(band[d].max))` ⇒ `overpowered`.
Supervisor: run steps 1–3; then `supervisor-underpowered` if `cls === 'small'`.
Output order: tiers in `Object.entries` order, then supervisor. Deterministic.

Test cases (build ctx from a literal `Map`/`Set`, never from the real catalog): expert tier on small ⇒ underpowered naming `expert`; trivial-simple tier on frontier ⇒ overpowered; trivial-simple-medium on frontier ⇒ no warning (D4); medium on small ⇒ underpowered; distribution tier with one small entry among frontier entries owning `complex` ⇒ one underpowered for that entry only; unknown model ⇒ only `unknown-model`, no band warning; provider not enabled ⇒ `provider-not-enabled`; `enabledProviders` undefined ⇒ no provider warning; supervisor small ⇒ `supervisor-underpowered`; unclassified model in `knownModelIds` ⇒ no warning; every message starts with its `path`; `checkStaffingFitness` with `['simple','complex']` on small ⇒ underpowered with `difficulties: ['complex']`.

### WI-3 — Server-side context builder (FR-3, FR-5, FR-6 share it)

```ts
import { PROVIDERS, getProviderForModelSync } from '../providers.js';
import { MODEL_CAPABILITIES } from '../model-capabilities.js';
import { capabilityClassOf } from '../model-capability-class.js';
import type { NormalizedConfig } from '../config-yaml/schema.js';
import type { TierFitnessContext } from './tier-fitness.js';

export function buildTierFitnessContextSync(config: Pick<NormalizedConfig, 'enabledProviders'>): TierFitnessContext {
  const knownModelIds = new Set<string>(Object.keys(MODEL_CAPABILITIES));
  for (const provider of Object.values(PROVIDERS)) for (const id of provider.models) knownModelIds.add(id);
  return {
    knownModelIds,
    classOf: capabilityClassOf,
    providerOf: (model) => getProviderForModelSync(model).name,
    enabledProviders: new Set(config.enabledProviders),
  };
}
```

### WI-4 — `pan doctor` row (FR-3, FR-7)

**Files:** `src/cli/commands/doctor-tier-fitness.ts` (new), `src/cli/commands/__tests__/doctor-tier-fitness.test.ts` (new), `src/cli/commands/doctor.ts` (edit: one import + one `checks.push`).

export interface TierFitnessDoctorDeps { loadConfig: () => ReturnType<typeof loadConfigSync>; }

const FIX = 'Adjust the tier model in Settings › Tiered Execution (warning only — a cheap model may be deliberate). With tiered execution off, enable it to route expert items to a frontier tier.';

export function checkTierFitnessConfig(deps: TierFitnessDoctorDeps = { loadConfig: loadConfigSync }): CheckResult {
  const { config } = deps.loadConfig();
  // PAN-2395: an invalid tiered_execution block never throws at load; it is
  // degraded to disabled and the reason is surfaced here. That is the error row.
  if (config.tieredExecutionInvalid) {
    return { name: 'Tiered execution', status: 'error', message: `tiered_execution is invalid and has been disabled: ${config.tieredExecutionInvalid.reason}`, fix: 'Fix ~/.overdeck/config.yaml tiered_execution and re-run pan doctor' };
  }
  const tiered = config.tieredExecution;
  const ctx = buildTierFitnessContextSync(config);
  let warnings: TierFitnessWarning[];
  if (tiered.enabled) {
    warnings = checkTierFitness(tiered, ctx);
  } else {
    // D11: implicit roles.work tier owns every difficulty. Same resolution pair
    // as resolveImplicitStaffing (staffing.ts:82) — fails loudly, never falls back.
    let model: string;
    try {
      model = requireModelOverrideSync(resolveModel('work', undefined, config));
    } catch (error) {
      return { name: 'Tiered execution', status: 'error', message: `roles.work.model could not be resolved: ${error instanceof Error ? error.message : String(error)}`, fix: 'Set roles.work.model in ~/.overdeck/config.yaml' };
    }
    warnings = checkTierFitness({ tiers: { default: { model, difficulties: [...TIERED_EXECUTION_DIFFICULTIES] } } }, ctx)
      .map((w) => ({ ...w, path: 'roles.work.model', message: w.message.replace('tiered_execution.tiers.default', 'roles.work.model') }));
  }
  if (warnings.length === 0) {
    return { name: 'Tiered execution', status: 'ok', message: tiered.enabled ? `${Object.keys(tiered.tiers).length} tiers fit their difficulties` : 'disabled; roles.work fits every difficulty' };
  }
  return { name: 'Tiered execution', status: 'warn', message: warnings.map((w) => w.message).join('\n    '), fix: FIX };
}

### R1 — Classification must follow the model that actually runs

**Defect.** D1 mandated replacement-based classification while §5.1 supplied rows for
`glm-4.7` and `glm-4.7-flash`, which are themselves keys of `MODEL_DEPRECATIONS`. The
implementation followed D1, so both ids hopped to `glm-5.1` and reported `frontier`.
Reproduced before the fix:

```json
{"id":"glm-4.7-flash","spawnModel":"glm-4.7-flash","declaredClass":"small","checkedClass":"frontier","expertWarnings":[]}
```

`spawnModel` is the literal id: an explicit override reaches the harness unrewritten.
The feature's whole purpose — warning on an underpowered selection — was defeated for
exactly the case an operator is most likely to hit by hand.

**Correction.** `capabilityClassOf` reads the literal id first, hopping only for ids with
no row. Deleting the two deprecated rows would NOT have fixed this: it would have made
both ids classify as `frontier` via the hop, which is the same false negative. After the
fix:

```json
{"id":"glm-4.7-flash","spawnModel":"glm-4.7-flash","declaredClass":"small","checkedClass":"small","expertWarnings":["underpowered"]}
```

**Scope.** Explicit overrides only in effect. The configured-tier path already normalizes
deprecated ids upstream, so a tier reaching `capabilityClassOf` presents an already-live id
and is unaffected.

### R2 — Mixed-difficulty wording named one requirement for every difficulty

**Defect.** The §5.3 `underpowered` template interpolated a single `${needed}` — the
maximum requirement across the failing difficulties — after listing them all. For
`medium, complex, expert` on a `small` model it read as though `medium` needed
`frontier`-class. `medium` needs `workhorse`.

**Correction.** Group the failing difficulties by requirement and state each group's own
requirement. The single-requirement case keeps the original sentence verbatim. Band
comparison and the decision to warn are untouched; this is a copy fix.

### Explicitly NOT revised

- **D11 representative-only check of a weighted `roles.work`** and **the untiered default
  producing a fitness warning** were both reported as defects by raw reviewers. Both are
  deliberate decisions in this document; they stand. The doctor checks the max-weight
  representative, and the default model is checked against all five difficulties, by design.
- Speculative hardening from the raw reports (invalid-difficulty guards, prototype-key
  handling, malformed-plan robustness) is out of scope — the adjudication established no
  reachable product path for any of it.
