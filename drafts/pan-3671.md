# PRD: PAN-3671 — Test-home OVERDECK_HOME poisoned shared tmux global env; false 'Spawn failed' on every conversation spawn

**Issue:** https://github.com/eltmon/overdeck/issues/3671
**Status:** Draft for planning (auto mode)
**Author:** planning agent (claude)
**Date:** 2026-08-13

## Glossary

- **Managed tmux server / shared socket** — the long-lived tmux server on socket `-L overdeck`, founded by `ensureOverdeckTmuxServerSync()` under a dedicated systemd user unit. Every conversation and agent session on the host is a tmux session on this server.
- **tmux global environment** — per-server environment (`tmux set-environment -g KEY VALUE`) that every *new* session on that server inherits. Shared mutable state across every process that talks to the socket.
- **Sanitizer** — `sanitizeManagedServerGlobalEnvSync()` in `src/lib/tmux.ts` (PAN-1798). Runs before every `new-session`; pins `HOME`/`OVERDECK_HOME` into the server's global env and strips test-only keys.
- **Canonical home** — `join(os.homedir(), '.overdeck')`, i.e. what `getOverdeckHome()` returns when `process.env.OVERDECK_HOME` is unset. The home the shared managed socket belongs to.
- **PTY supervisor** — `dist/pty-supervisor.js` wrapper process that owns message delivery for a conversation and listens on `${OVERDECK_HOME}/sockets/pty-<agentId>.sock` (mode 0600).
- **fork_status / fork_error / spawn_error** — `conversations` table columns. `fork_status='failed'` + `fork_error` records fork-pipeline failure; `spawn_error` records spawn failure and drives the dashboard's "Failed to start" screen (`ConversationPanel.tsx:629`, `isSpawnFailed = !!conversation.spawnError`).
- **Lifecycle heal** — the PAN-1972 resurrect path in `pollConversations()` (`src/dashboard/server/services/conversation-lifecycle.ts:170-173`): when tmux session AND harness process are alive but the row reads `ended`, it calls `markConversationRunning()`.
- **Launcher script** — the bash script `generateLauncherScriptSync()` (`src/lib/launcher-generator.ts:244`) writes per spawn; the tmux session runs it.

## Background and root cause (verified live by the operator, 2026-08-12/13)

A PAN-3668 throwaway test dashboard ran with `OVERDECK_HOME=/tmp/pan-3668-dashboard-home-20260812` **on the shared managed socket**. Its spawn preflight called the sanitizer, which pins `HOME`/`OVERDECK_HOME` from the **caller's raw env** (`src/lib/tmux.ts:236-244`) into the shared server's global env. The /tmp test home was stamped globally. Chain from there:

1. Conversation launcher scripts export `OVERDECK_AGENT_ID` but **not** `OVERDECK_HOME` (`src/lib/launcher-generator.ts:306-319`), so every `pty-supervisor` resolved `getOverdeckHome()` (`src/lib/paths.ts:9-11`) from the inherited, polluted tmux global env.
2. Supervisors bound their sockets under the /tmp test home (verified live via `ss -xlp`).
3. The real dashboard polls `~/.overdeck/sockets/pty-<id>.sock` in `waitForPtySupervisorSocket()` (`src/lib/overdeck/conversation-runtime.ts:424-440`), timed out after 30s (`PTY_SUPERVISOR_SOCKET_WAIT_MS = 30_000`, line 77), and the fork/spawn pipeline recorded `fork_status='failed'` + `markConversationEnded()` (`handleForkPipelineFailure`, `src/lib/overdeck/conversation-forks.ts:400-405`) or `spawn_error` (`handleConversationCreate` catch, `conversation-runtime.ts:945-954`) — while the tmux session and harness were demonstrably alive.
4. The pollution **self-perpetuated**: the sanitizer skips pinning when the caller's env lacks the var (`if (!value) continue`, `src/lib/tmux.ts:238`), so the clean real dashboard could never repair the global env.
5. `extractSupervisorFailure()` (`conversation-runtime.ts:416-422`) found no error lines in the pane and fell back to quoting the last 3 lines — the harness's healthy statusline — as the "failure output" in the operator-facing error.
6. The lifecycle heal resurrected `status` but never cleared `fork_status`, and `sessionAlive` requires `!forkStatus` (`conversationSessionAliveFromState`, `conversation-runtime.ts:269-274`), so healed rows stayed latched "failed". A third field, `spawn_error`, independently keeps the "Failed to start" screen up. No operator door existed to clear any of this (the operator fixed rows with raw SQL).

Remediation already applied live by the operator (2026-08-12 ~23:40): manual `tmux -L overdeck set-environment -g OVERDECK_HOME /home/eltmon/.overdeck`, plus SQL clears of `fork_status`/`fork_error`/`spawn_error` on the affected rows. This issue is the permanent fix.

## Requirements

### Functional

- **FR-1** — On the **default managed socket** (`OVERDECK_TMUX_SOCKET_NAME` unset), the sanitizer pins `HOME` and `OVERDECK_HOME` to the **canonical** values derived from `os.homedir()`, never the caller's env, and pins them **always** (no skip-on-unset), so a clean-env dashboard repairs pollution and a test-home process cannot stamp its home into the shared server.
- **FR-2** — When a process whose resolved `getOverdeckHome()` differs from canonical runs the sanitizer against the default managed socket, it logs a warning naming the non-canonical home and advising `OVERDECK_TMUX_SOCKET_NAME` isolation; it still pins canonical values (never the caller's).
- **FR-3** — Every launcher script generated by `generateLauncherScriptSync()` for a **non-remote** spawn exports `OVERDECK_HOME=<resolved home of the spawning process>`, so the PTY supervisor and in-session `pan` calls never resolve home from tmux global env. Remote (`spawnMode: 'remote'`) launchers are unchanged — a local home path must not leak onto a Fly VM.
- **FR-4** — When `waitForPtySupervisorSocket()` times out but the tmux session exists, `spawnConversationSession()` logs a warning and continues (delivery proceeds via the existing channels → tmux-paste fallback). It does **not** write `spawn_error`, does **not** set `fork_status='failed'`, and does **not** call `markConversationEnded()`. When the tmux session is gone, the error propagates exactly as today.
- **FR-5** — The liveness heal clears stale failure state: `markConversationRunning()` additionally sets `spawn_error = NULL` always, and `fork_status = NULL` + `fork_error = NULL` when `fork_status = 'failed'` (in-flight fork states `'spawning'`/`'injecting'` are preserved for stuck-fork recovery).
- **FR-6** — New operator door: `POST /api/conversations/:name/clear-fork-state` clears `fork_status`, `fork_error`, and `spawn_error` for a conversation whose tmux session is alive. Returns 404 when the conversation does not exist, 409 when the tmux session is not alive (the stored failure state is then truthful).
- **FR-7** — New CLI verb `pan conversations heal <name>` that POSTs to the FR-6 endpoint (same thin-client pattern as `pan conversations move`).
- **FR-8** — `extractSupervisorFailure()` returns `null` when the pane contains no error-shaped lines, and the socket-timeout error message then states that the supervisor pane shows no error output (a healthy harness statusline) instead of quoting the statusline as failure output.

### Non-functional

- **NFR-1** — On a non-default socket (`OVERDECK_TMUX_SOCKET_NAME` set), the sanitizer keeps pinning the caller's resolved home: per-test/per-instance socket isolation behavior is unchanged.
- **NFR-2** — Delay/poll-based tests use `vi.useFakeTimers()` + `advanceTimersByTimeAsync()` per the bundled fake-timers rule. No new sync tmux primitives; server-reachable code stays async (`execFileSync` already present in the sanitizer is pre-existing CLI-side usage, not new server code).
- **NFR-3** — No behavior change to remote (Fly) launcher generation.
- **NFR-4** — Single write door preserved: all failure-state clearing goes through writers in `src/lib/overdeck/conversations.ts`; the route handler and CLI never touch the DB directly (the CLI is an HTTP client of the FR-6 endpoint).

## Decisions (made in --auto mode; recorded in plan.autoDecisions)

- **D1 — Sanitizer refusal, not forced socket derivation.** The issue offers "refuse to stamp the shared socket" OR "force test dashboards onto their own socket". There is no mechanical test-dashboard launch path in the repo to force (the PAN-3668 dashboard was launched ad hoc), and pinning canonical values on the shared socket is always safe. Chosen: canonical pinning + refuse-caller-home + warning (FR-1/FR-2).
- **D2 — Heal inside `markConversationRunning`.** Both heal sites (`conversation-lifecycle.ts:172`, `conversation-list.ts:111`) call this one writer; extending it fixes both with one change and keeps the write door single.
- **D3 — Heal clears `fork_status` only when `'failed'`.** Clearing in-flight `'spawning'`/`'injecting'` would orphan `getStuckForks()` recovery (`src/lib/overdeck/conversations.ts:1417-1422`).
- **D4 — Degrade keeps `delivery_method='auto'`.** `deliverAgentMessage` already falls back supervisor → channels → tmux-paste at delivery time; no stored state change is needed for delivery to work. The degrade is a warn-log + continue.
- **D5 — Operator door is REST endpoint + thin CLI.** Matches `pan conversations move` (resolve locally, POST to dashboard). No direct-DB CLI path (NFR-4).
- **D6 — Stale-socket janitor sweep is out of scope.** The issue itself calls it "a separate concern" (619 stale `pty-conv-*.sock` files in `~/.overdeck/sockets/`).

## NonGoals

- Janitor sweep of stale `pty-conv-*.sock` files (separate concern per the issue; file a sibling issue).
- Mechanically forcing test/throwaway dashboards onto their own tmux socket (the FR-2 warning advises it; no launch path exists to enforce it).
- Frontend changes: the "Failed to start" screen renders from `spawn_error`; FR-5/FR-6 clearing makes it correct without touching `ConversationPanel.tsx`.
- Changing the delivery fallback ordering (supervisor → channels → tmux-paste).
- Healing rows whose tmux session is genuinely dead (their failure state is truthful).
- Retroactive repair of rows already stuck tonight beyond what FR-5's heal and the FR-6 door provide (the operator already cleared them by hand).

// liveness oracle — when session + harness are alive, a stored

## Risks / hazards

- **H1 — Legitimate non-canonical homes on the default socket.** If any real flow intentionally runs with a custom `OVERDECK_HOME` against the shared socket (none found in the repo; workspace devcontainers run their own tmux server and set `OVERDECK_DISABLE_DEACON=1`), FR-1 would pin the canonical home for its future sessions. Mitigation: the FR-2 warning names exactly this case and points at `OVERDECK_TMUX_SOCKET_NAME`.
- **H2 — Heal clearing a `failed` fork whose summary never landed.** After FR-5, a resurrected conversation whose fork genuinely failed mid-injection loses its `failed` marker. Mitigation: the conversation is alive and usable; the fork_request recovery only handles non-failed states today, so no recovery path is regressed (D3).
