# PAN-2633 — pending-question payload wiped when an idle-alive asking agent flaps to 'stopped'

**Issue:** https://github.com/eltmon/overdeck/issues/2633
**Author:** planning agent (claude-fable-5), 2026-07-13, `pan plan --auto`

## Glossary

- **Pending-input payload** — the enrichment-owned fields on an `AgentSnapshot` that drive the needs-you surface and modals: `hasPendingQuestion`, `pendingQuestionCount`, `pendingQuestionPrompt`, `pendingQuestionReason`, `pendingInputCount`, `pendingInputKinds`, `pendingAskUserQuestion`, `pendingProposedPlan`. See `docs/PENDING-INPUT.md`.
- **Idle-alive** — an agent whose registry status is `stopped` (or otherwise non-running) while its tmux session on the `overdeck` socket is still alive. This is a designed, legitimate state (`src/lib/work-agent-lifecycle.ts:83` models `hasLiveTmuxSession && isStopped`); an agent waiting at its prompt on an operator answer is the archetypal case.
- **The wipe** — the PAN-1520 rule in the `agent.status_changed` fold (`packages/contracts/src/event-reducers.ts:489-503`) that deletes every pending-input field when the new status is not `running`/`starting`.
- **Enrichment poller** — `src/dashboard/server/services/agent-enrichment-service.ts`: every 10s scans each tmux-alive agent's JSONL and emits `agent.enrichment_changed` when its computed enrichment differs from its private `lastEnrichment` cache.
- **Needs-you surface** — `NeedsYouSection` + the AUQ/plan modals, all fed from the read model's `agentsById` via `selectAgentsWithPendingAskUserQuestion` etc. (`src/dashboard/frontend/src/App/hooks/usePendingInputDialogs.ts`). Purely a consumer — the fix is server/contracts-side.

## Problem

Operator report (2026-07-13): `agent-pan-2568-slot-3` asked an AskUserQuestion; the dialog appeared once, but after it was dismissed there was **no needs-you entry to get back to it** — recovery required a page refresh. The agent's registry status was `stopped` while its tmux session was alive and showing the question.

### Verified mechanism (all references checked 2026-07-13 on this branch)

1. **The wipe is liveness-blind.** `packages/contracts/src/event-reducers.ts:494` — `if (event.payload.status !== 'running' && event.payload.status !== 'starting')` deletes all eight pending-input fields. The payload schema *already* carries an optional `hasLiveTmuxSession` boolean (`packages/contracts/src/events.ts:123`) and the fold already copies it into the snapshot via `optionalFields` (`event-reducers.ts:469`), but the wipe condition ignores it. So a status flap to `stopped` while the pane is alive erases the payload.
2. **Nothing restores it.** The poller keeps scanning idle-alive agents — `listRunningAgents()` returns *all* agents with a `tmuxActive` flag and the poller filters on `tmuxActive`, not status (`agent-enrichment-service.ts:95`, `src/lib/agents/queries.ts:45-73`). But its dedup compares the fresh enrichment against its **private `lastEnrichment` cache** (`agent-enrichment-service.ts:207`), which still holds the pending question. The enrichment genuinely didn't change, so no event is re-emitted and the read model stays wiped. (This is the "write-only field / dedup-vs-read-model drift" pattern.)
3. **Partial mitigations exist but don't cover the flap.** The poller's stopped→running reconcile (`agent-enrichment-service.ts:145`) fires once per agent per server lifetime and emits only a *status* event, which carries no pending fields. The deacon's `handleAgentStoppedEvent` reconcile (`src/lib/cloister/deacon-auto-resume.ts:672-679`) flips work agents back to running with `hasLiveTmuxSession: true` — again status only; the wiped payload stays wiped.

### Why the wipe exists (must be preserved for dead sessions)

- PAN-1520 (`event-reducers.ts:489` comment): a paused/stopped agent whose session is gone would otherwise show INPUT/AskUserQuestion forever, because the poller stops emitting for it.
- PAN-1591 (`ac20ac6021`): the same rule was applied at bootstrap projection via `projectPendingInput` (`src/dashboard/server/read-model.ts:260`). **Note:** that function is now dead in the wire path — the post-remodel bootstrap builds snapshots from the two-door `Agent` with pending fields starting `undefined` (`read-model.ts:376-380`), so only the reducer wipe is live today. Boot self-heals: `lastEnrichment` starts empty, so the first poll re-emits payloads for tmux-alive agents.

## Chosen approach

Three independent, individually-mergeable slices — gate the wipe on liveness, make the liveness signal accurate at every emitter, and give the poller a convergence path that restores the payload no matter which emitter caused a wipe.

**Decision rule for the gate:** wipe **unless the event explicitly asserts `hasLiveTmuxSession === true`**. Events with `false` or an **absent** field still wipe. This preserves PAN-1520 semantics for every emitter that doesn't know liveness (fail-safe toward clearing, never toward phantom needs-you rows), and fixes the flap once emitters assert liveness truthfully.

**Decision rule for the poller:** bypass the `enrichmentChanged` dedup and re-emit when (a) the agent's registry status is not `running`/`starting`, and (b) the computed enrichment carries a pending payload (`pendingInputCount > 0`, or a `pendingAskUserQuestion`/`pendingProposedPlan` object). Do **not** clear `lastEnrichment` to force this — `previousEnrichment` must stay intact so the PAN-1834 awaiting-input rising edge (`isAwaitingInputRisingEdge`, `agent-enrichment-service.ts:200`) does not re-fire activity/TTS every poll. Cost: one redundant `agent.enrichment_changed` per 10s poll per idle-alive *waiting* agent — bounded to exactly the agents where needs-you freshness matters, and reducers are idempotent.

## Requirements

- **FR-1** — On `agent.status_changed` to a non-running/starting status, the reducer preserves all pending-input fields when `event.payload.hasLiveTmuxSession === true`, and deletes them when the field is `false` or absent.
- **FR-2** — Every `agent.status_changed` emitter that can emit a non-running/starting status includes an accurate `hasLiveTmuxSession` in its payload (computed via `sessionExists`/`sessionExistsSync` at emit time when not already known).
- **FR-3** — The enrichment poller re-emits `agent.enrichment_changed` for a tmux-alive agent whose registry status is not running/starting while its enrichment carries a pending payload, so the read model converges within one poll (≤10s) after any wipe.
- **FR-4** — `docs/PENDING-INPUT.md` documents the liveness-gated wipe invariant (and `docs/ASKUSERQUESTION-DASHBOARD.md` where it describes payload clearing).
- **NFR-1** — The PAN-1834 awaiting-input activity entry + TTS still fire exactly once per rising edge; FR-3's re-emission must not re-trigger them.
- **NFR-2** — PAN-1520/PAN-1591 behavior is preserved for dead sessions: an agent without a live tmux session never retains pending-input fields after a stop-shaped status event.

### W3 — Enrichment poller convergence re-emit (traces FR-3, NFR-1)

**File:** `src/dashboard/server/services/agent-enrichment-service.ts`.

Add an exported pure helper (testable like the existing `isAwaitingInputRisingEdge`):
```ts
// PAN-2633 — an idle-alive agent's pending payload can be wiped from the read
// model by a stop-shaped status event; the dedup cache can't see that. While
// such an agent still owes the operator an answer, re-emit every poll so the
// read model converges. previousEnrichment stays set, so the PAN-1834 rising
// edge does not re-fire.
export function shouldForceReemitPendingInput(
  agentStatus: string,
  enrichment: AgentEnrichment,
): boolean {
  if (agentStatus === 'running' || agentStatus === 'starting') return false
  return (
    enrichment.pendingInputCount > 0 ||
    enrichment.pendingAskUserQuestion != null ||
    enrichment.pendingProposedPlan != null
  )
}
```
In `pollOnce`, change the dedup return (currently line 207):
```ts
      if (!enrichmentChanged(previousEnrichment, enrichment) && !shouldForceReemitPendingInput(agent.status, enrichment)) {
        return
      }
```
Do NOT touch `state.lastEnrichment` handling, the `reconciledAgentIds` once-guard, or the rising-edge block.

**Tests** (extend `src/dashboard/server/services/__tests__/agent-enrichment-service.test.ts`): `shouldForceReemitPendingInput` returns true for `stopped` + pending AUQ payload / pending input count; false for `running` + pending payload; false for `stopped` + empty enrichment. ## Hazards

- **H1** — The exact emitter that flapped `agent-pan-2568-slot-3` was not pinned; several paths write `status: 'stopped'` without killing the pane. W3 guarantees convergence regardless of source; W2's audit covers all current emitters.
- **H2** — `projectPendingInput` is dead in the wire path but still exported/tested; if anyone rewires it, it must adopt the same liveness gate. Do not delete it in this issue (surgical-changes rule).
- **H3** — Forcing re-emission by clearing `lastEnrichment` would make `previousEnrichment` undefined and re-fire the PAN-1834 activity/TTS every 10s (TTS metronome). The chosen design (dedup bypass, cache intact) avoids this — do not "simplify" to a cache clear.
- **H4** — Server code: use async `sessionExists`, never `sessionExistsSync`, in route handlers (no-execsync/async-tmux rules).
- **H5** — After editing `packages/contracts`, rebuild it (`cd packages/contracts && npm run build`) before running dependent suites; run `bun install` from the workspace root first.
- **H6** — Any new test touching poll timing must use fake timers (`vi.useFakeTimers()`); the planned tests avoid timers by testing pure helpers.
