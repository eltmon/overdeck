# PAN-3550 — Memory pressure must warn in the activity feed before anything dies

**Issue:** https://github.com/eltmon/overdeck/issues/3550
**Status:** DRAFT (planning in progress)

## Planning Q&A

### Q1 (2026-08-05) — What to do with the dormant eviction ladder?

**Situation presented to the operator:** `shed()` in
`src/lib/cloister/memory-governor.ts:342` (stops merged Docker stacks, then pauses
idle work agents) has **zero callers anywhere in `src/`**. Verified at HEAD
`f69486a9c6` with an exhaustive grep across `src/` and `tests/`: the only
references are its own definition, its unit tests
(`tests/unit/lib/cloister/memory-governor.test.ts:428`), and prose comments. It
was introduced by commit `e743ec52bf` ("feat(cloister): tiered eviction under
HARD memory pressure", 2026-07-08) *without* a caller, and none was ever added.
`docs/RESOURCE-GOVERNOR.md:172-211` describes the ladder as live behavior — that
is documentation drift.

Consequence: the issue body's premise ("The memory governor sheds under HARD
pressure ... with only console.log output") is **not** what happens today. No
automatic shedding runs. What is actually silent is (a) the memory gate deferring
autonomous resumes/dispatches with only a deacon-log line, and (b) kernel OOM
kills.

**Options offered:**
1. Leave `shed()` dormant, fix `docs/RESOURCE-GOVERNOR.md` to say plainly it is
   unwired. This issue then ships warnings only. *(Recommended)*
2. Delete `shed()` and its tests as dead code.
3. Wire `shed()` behind an off-by-default config flag.

**Operator chose: option 1 — leave dormant, fix the docs.**

Rationale carried forward: the operator directive is "instead of it killing
processes, it should just give a warning in the Awareness Activity log." Shipping
warnings without wiring any evictor is exactly that. The doc must stop claiming a
behavior the code does not have.
