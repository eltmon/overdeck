## Glossary

- **Composer** — `ComposerPromptEditor` plus `ComposerFooter`, the dashboard text-input surface used to send input to a conversation or work agent.
- **Overdeck operator command** — a command in the reserved `/pan` namespace, such as `/pan start PAN-1987`. Overdeck parses and executes it; the active model never receives it.
- **Harness-native command** — a control command interpreted by Claude Code, Codex, or ohmypi rather than by Overdeck. Availability and syntax may differ by harness.
- **Agent prompt** — ordinary user text delivered to the active harness and model.
- **Command manifest** — the serializable description of CLI command paths, arguments, options, descriptions, visibility, composer execution mode, and safety class.
- **CLI tree** — the Commander.js `Command` hierarchy currently constructed in `src/cli/index.ts`.
- **Execution mode** — one of `captured` (await a short operation), `detached` (start tracked background work), `ui` (return a typed dashboard action), or `terminal-only` (discoverable but not executable from the composer).
- **Safety class** — `safe`, `dialog`, or `destructive`. `dialog` requires ordinary confirmation; `destructive` requires typed confirmation.
- **Structured command result** — the response and timeline item describing command acceptance, running/completed/failed status, activity identifier, and actionable consequence without presenting it as an agent message.
- **No-loss audit** — a test-owned inventory proving that every legacy composer entry and alias maps to the new manifest, a harness-native entry, or an explicit documented exclusion.
- **Isolated Codex home** — `${OVERDECK_HOME}/agents/<conversation-or-agent>/codex-home`, containing per-session Codex config/auth/session state.

## Problem and root cause

The dashboard currently conflates three different concepts in one slash menu: Overdeck lifecycle commands, harness-native controls, and harness skills. The static list suggests commands that the receiving harness may not recognize, while the server forwards almost all submitted text directly to that harness.

The concrete regression is `/pan start PAN-1987` in a Codex-backed conversation. Codex recognizes the leading `/` as its own command namespace, rejects `/pan`, and never gives Overdeck or the model a chance to act. This is not a `pan start` failure; it is a command-ownership failure.

## Decisions

### D1 — Overdeck owns `/pan`

`/pan <verb> [args]` is the canonical portable operator syntax. It is intercepted on the server before harness transformation or delivery. Its behavior cannot depend on model compliance, shell-tool access, skill installation, or whether the harness is currently accepting input.

Unprefixed `pan …` remains an ordinary agent prompt for backward compatibility. This lets an operator intentionally ask the agent to reason about or execute a CLI command. Only the leading `/pan` selects deterministic control-plane routing.

### D2 — Discovery and execution share one manifest

Commander remains the source of truth for command names, positional arguments, options, aliases, descriptions, hidden state, and deprecation text. Composer-only policy lives in a small overlay keyed by canonical command path.

The overlay must not repeat arguments or flags. It contains only:

```ts
type ComposerExecutionMode = 'captured' | 'detached' | 'ui' | 'terminal-only';
type ComposerSafety = 'safe' | 'dialog' | 'destructive';

interface ComposerCommandPolicy {
  mode: ComposerExecutionMode;
  safety: ComposerSafety;
  confirmationText?: string;
  typedConfirmation?: string;
  uiAction?: 'handoff' | 'fork';
}
```

An unlisted command defaults to `{ mode: 'terminal-only', safety: 'safe' }`. This fail-closed default makes every CLI command discoverable without making every administrative command remotely executable.

### D3 — Build the CLI tree without running it

Move program construction into an import-safe function. `src/cli/index.ts` retains environment bootstrapping and becomes the thin executable entrypoint:

```ts
const program = createOverdeckProgram();
if (process.argv.length === 2) process.argv.push('serve');
await program.parseAsync();
```

The builder must not parse argv, mutate argv, start services, load user state for side effects, or call `process.exit`. Registration functions may remain where they are, but construction must be callable by tests and the dashboard command-manifest endpoint.

### D4 — Server is the enforcement boundary

React may recognize `/pan` early to render optimistic UI, but the server owns parsing, safety, confirmation, and dispatch. Retry outbox sends and future clients call the same boundary. A frontend-only rewrite is rejected because it would remain harness-dependent and would not enforce destructive-command policy.

### D5 — Use argv arrays, never command strings

The router tokenizes a restricted command line, validates it against the manifest, and dispatches an argv array. It must not build `exec("pan " + userInput)`. Server-reachable code uses async `spawn`/`execFile` primitives only; never `execSync`.

### D6 — First executable set is deliberately bounded

The first release registers:

| Command | Mode | Safety | Result |
| --- | --- | --- | --- |
| `pan start` | detached | safe | tracked activity plus issue id |
| `pan plan` | detached | safe | tracked planning activity |
| `pan show` | captured | safe | formatted captured output |
| `pan status` | captured | safe | formatted captured output |
| `pan tell` | captured | safe | delivery result |
| `pan handoff` and aliases | ui | dialog | open existing handoff dialog |
| `pan fork` | ui | dialog | open existing fork dialog |

All other commands appear in discovery as `terminal-only` until an explicit policy and handler are added. Destructive commands must not be silently omitted; their manifest row explains that they require terminal/dashboard action until typed confirmation support is registered.

### D7 — Skill parity is separate from control routing

The `/pan` router must work with zero skills installed. Nevertheless, isolated Codex homes must inherit the synced Codex skills so other reusable workflows remain available. Copy only the managed skill directory entries into `<codexHome>/skills` at initialization; do not symlink the whole global Codex home and do not share `auth.json`, `config.toml`, or `sessions/`.

Use the same source selected by `pan sync` for Codex (`~/.codex/skills`) and copy/update directories idempotently. Do not delete per-agent skill directories that are not in the source; this change is additive and must not erase user/session additions.

### D8 — Native commands are harness capabilities

Add optional native-command metadata to `HarnessBehavior` (or a sibling pure registry if behavior should stay runtime-only). The frontend shows active-harness commands in a separate labeled group. It must not advertise a Claude-only command to Codex or ohmypi.

No attempt is made to normalize the native command implementations. `/pan` is the portable namespace; native commands remain native.

## Requirements

### Functional

- **FR-1** `/pan start PAN-X` is intercepted and parsed before Claude Code, Codex, or ohmypi delivery.
- **FR-2** The same valid `/pan` input yields the same canonical argv, command policy, and structured acceptance result for all three harnesses.
- **FR-3** A `/pan` command consumes no model turn and is absent from the harness transcript.
- **FR-4** Every non-hidden Commander command, positional argument, option, alias, description, and deprecation marker appears in `GET /api/commands`.
- **FR-5** Adding or changing a CLI command/option does not require editing `ComposerPromptEditor.tsx`.
- **FR-6** The composer groups Overdeck commands and active-harness commands separately and inserts exact executable syntax.
- **FR-7** `/handoff`, `/pan-handoff`, and `/pan handoff` continue opening the existing handoff UI with focus text preserved.
- **FR-8** `captured`, `detached`, `ui`, and `terminal-only` commands return distinct typed results that the frontend renders in plain operator-facing language.
- **FR-9** Unknown commands, missing required arguments, invalid flags, and terminal-only execution attempts return actionable 4xx responses without harness delivery.
- **FR-10** Dialog commands require a server-issued confirmation nonce; destructive commands require both a nonce and exact typed confirmation.
- **FR-11** Ordinary messages, attachments, image transformation, retry outbox behavior, and unprefixed `pan …` prompts retain their existing delivery behavior.
- **FR-12** Each isolated Codex home contains the synced Codex skill directories while keeping its config, credentials, and sessions isolated.
- **FR-13** The no-loss audit accounts for every legacy `SLASH_COMMANDS` entry and handoff alias.

### Non-functional

- **NFR-1** No server-reachable `execSync` and no shell-string interpolation.
- **NFR-2** Execution extends the canonical CLI/domain write path and adds no direct SQLite, state-worktree, `state.json`, or tracker writes.
- **NFR-3** The command builder and manifest walker are import-safe and do not introduce a circular ESM dependency into the Node 22 dashboard bundle.
- **NFR-4** Operator-facing messages define `accepted`, `running`, `completed`, and `failed` consequences in complete sentences.
- **NFR-5** No new runtime dependency.
- **NFR-6** Refactoring the CLI entrypoint preserves every existing command and option; a mechanical parity test blocks command loss.

## Acceptance criteria

- **AC-1 / WI-1:** `createOverdeckProgram()` constructs the complete current CLI tree without parsing argv; the parity snapshot includes all existing top-level and nested commands/options.
- **AC-2 / WI-2:** `GET /api/commands` data derives command syntax from Commander and composer policy from the overlay; an unregistered command is terminal-only.
- **AC-3 / WI-3:** The command endpoint returns Overdeck plus active-harness sections and does not rebuild the manifest per request.
- **AC-4 / WI-4:** `/pan start PAN-X` is intercepted before attachments, prompt-memory injection, or harness delivery on both conversation and agent endpoints.
- **AC-5 / WI-5:** `start`, `plan`, `show`, `status`, and `tell` return the declared structured result types; handoff/fork return UI actions; no executor uses a shell string or sync child process.
- **AC-6 / WI-6:** The composer has no hardcoded Overdeck command catalog, preserves keyboard/draft behavior, and renders command results separately from agent messages.
- **AC-7 / WI-7:** confirmation nonces are single-use and command-bound; destructive typed confirmation is mechanically enforced before any request executes.
- **AC-8 / WI-8:** Each harness advertises only verified native commands and the UI labels them by harness.
- **AC-9 / WI-9:** a fresh isolated Codex home receives global synced skill directories without losing a pre-existing per-agent-only skill or sharing sessions/config.
- **AC-10 / WI-10:** the no-loss audit accounts for every legacy command/alias; the three-harness `/pan start` matrix passes and ordinary-message negative controls pass.
- **AC-11 / WI-11:** both named docs explain the portable `/pan` contract, native commands, prompts, and confirmation behavior.
- **AC-12 / all:** `npm run typecheck`, `npm run lint`, targeted Vitest suites, and the Command Deck Playwright composer spec pass.

## Explicit non-goals

- Execute every administrative/destructive CLI command from the composer in this issue.
- Replace the terminal CLI or dashboard action menus.
- Force native Claude, Codex, and ohmypi commands into one syntax.
- Route `/pan` through the model as a prompt.
- Copy the user’s whole `~/.codex` directory into isolated homes.
- Add live external-value autocomplete for arbitrary issue/model/conversation catalogs beyond existing local data.

## Repo rules restated for the executor

- Investigate unexpected behavior before fixing it; do not mask harness differences with frontend string rewriting.
- Server code uses async child-process primitives only; never `execSync`.
- Never interpolate command text into a shell; validate manifest-derived argv.
- Canonical state reads/writes go through their domain resolver/writer or existing CLI write door.
- Destructive HTTP requests are never sent before confirmation.
- Refactors require the no-loss audit; no old command, alias, route, or affordance may disappear silently.
- Dashboard boot-path changes require a throwaway runtime boot test before any live restart; the dashboard runs the built bundle under Node 22, never Bun.
- Delay/expiry tests use Vitest fake timers, never real waits.
- Changes must remain surgical: command ownership, discovery, routing, skill parity, tests, and named docs only.
