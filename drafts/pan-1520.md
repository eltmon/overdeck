## Glossary

- **Pending input** — any state where an agent/conversation is blocked waiting on the operator. Kinds: `askUserQuestion`, `permissionRequest`, `exitPlanMode`, `enterPlanMode`, `sessionResume`, `rateLimit` (`src/dashboard/frontend/src/lib/pendingInput.ts`).
- **AUQ** — AskUserQuestion. A PreToolUse deny hook (`sync-sources/hooks/ask-user-question-hook`) converts it into a detectable JSONL state; the deny reason carries the literal marker `(PAN-1520)` that detection keys on. See `docs/ASKUSERQUESTION-DASHBOARD.md`.
- **Enrichment** — per-agent JSONL scan (`src/lib/agent-enrichment.ts`, polled by `src/dashboard/server/services/agent-enrichment-service.ts`) producing `pendingInputKinds`, `pendingAskUserQuestion`, etc., flowed to the frontend read model via events.
- **Pending-input feed** — `GET /api/conversations/pending-input` (`src/dashboard/server/routes/conversations.ts:236`), the lightweight per-4s poll that feeds conversation rows into the needs-you/dialog machinery.
- **Needs-you** — pinned recovery list of pending inputs in the activity feeds; clicking re-opens the corresponding dialog.
- **Plan-action** — `POST /api/conversations/:name/plan-action` (`src/dashboard/server/routes/conversations.ts:830`): injects native plan-menu keystrokes (`approve-manual`→`2`, `reject-feedback`→`4`+text) via `sendRawKeystroke` (`src/lib/tmux.ts`).
- **ProposedPlan** — a pending `ExitPlanMode` tool_use with no matching tool_result, tracked by `src/dashboard/server/services/conversation/parser.ts:153` (conversations) and as boolean `exitPlanModePending` in `src/lib/agent-enrichment.ts:282` (agents).

## Remaining gaps (this plan's scope)

1. **Plan-approval popup modal ([#1671](https://github.com/eltmon/overdeck/issues/1671)).** A pending `ExitPlanMode` never promotes to a modal — only `pendingAskUserQuestion` does (`App.tsx:748-755`). The plan appears inline in the transcript only; operators approve in the terminal after the fact. Missing plumbing: (a) agents' enrichment carries only a boolean, not the plan text; (b) the pending-input feed doesn't carry the conversation's `proposedPlan`; (c) no modal component/wiring; (d) no agent-scoped plan-action route (existing one is conversation-scoped); (e) no notification/needs-you-reopen for plan subjects.
2. **Card-level permission indicator.** Cards use `isAwaitingInput(agent)` on the agent snapshot; `permissionRequest` lives only in the separate channel-permission event stream, merged read-time in `selectPendingInputSubjects`. A permission-only agent shows in needs-you but its card shows no indicator (known residual, issue comment 2026-06-01).
3. **Docs.** `docs/ASKUSERQUESTION-DASHBOARD.md` covers AUQ only; the unified subsystem (kinds table, plan modal, permission merge) is undocumented.

**No new code needed for [#1102](https://github.com/eltmon/overdeck/issues/1102):** notification, interactive prompts, and the delivery-confirmation loop (optimistic mark → unmark on delivery error → reconcile against live JSONL toolUseIds) are all verified in code. Close #1102 and #1671 at close-out as delivered by this issue.

## Requirements

- **FR-1** Agent enrichment exposes the pending plan payload `pendingProposedPlan { toolUseId, plan }` (parsed from the `ExitPlanMode` tool_use `input.plan`) and it reaches `agentsById` in the frontend store.
- **FR-2** `GET /api/conversations/pending-input` rows include `pendingProposedPlan` for tmux-alive conversations with a pending plan.
- **FR-3** A `PlanApprovalDialog` modal renders the pending plan markdown with Approve / Request-Changes(feedback) / Minimize; minimize never strands the plan (needs-you keeps it recoverable); it never auto-approves.
- **FR-4** Approve/reject from the dialog delivers native plan-menu keystrokes: conversations via existing `/plan-action`; agent sessions via a new `POST /api/agents/:id/plan-action` mirroring it.
- **FR-5** Pending plan subjects fire the same desktop/toast notification as AUQ, and clicking their needs-you entry re-opens the plan dialog.
- **FR-6** Card-level surfaces (AgentCard, FleetAgentsView, DrawerActiveAgent, SessionPanel) light the uniform indicator when a channel permission request is pending for that agent, using one shared accessor (no per-component drift).
- **FR-7** The plan modal and its needs-you entry clear when the plan is resolved out-of-band (terminal approval → matching tool_result in JSONL) or the session stops.
- **FR-8** Docs: unified pending-input subsystem documented (kinds, surfaces, responders, plan modal), superseding the AUQ-only framing.
- **NFR-1** No pending input is ever answered by synthesis/auto-default, under any condition.
- **NFR-2** The pending-input feed stays lightweight (scans only tmux-alive conversations; no full enrichment per row).
- **NFR-3** Server code stays async (no execSync; tmux via async primitives only).
