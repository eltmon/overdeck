# PRD: PAN-3705 — Ctrl-K search: add Conversations to the type list

**Issue:** https://github.com/eltmon/overdeck/issues/3705
**Planning mode:** `pan plan --auto` (no interactive Q&A; all decisions recorded in
`## Decisions` and mirrored into the xBRIEF `autoDecisions[]`).
**Code references verified against:** workspace `workspaces/feature-pan-3705`, branch
`feature/pan-3705`, 2026-08-14.

## Glossary

- **Command palette / Ctrl-K palette** — the modal search UI in the dashboard,
  implemented in `src/dashboard/frontend/src/components/CommandPalette.tsx`, opened
  with Cmd/Ctrl+K (or Cmd/Ctrl+J, see below).
- **Scope** — a result-type filter. Type union `PaletteScope`
  (`CommandPalette.tsx:207`): `'all' | 'actions' | 'commands' | 'issues' |
  'workspaces' | 'conversations' | 'memory'`.
- **Scope chip / type list entry** — one `<button>` per scope in the chip row under
  the search input (`CommandPalette.tsx:929-947`). The issue calls this the "type
  list".
- **`availableScopes`** — the `useMemo` at `CommandPalette.tsx:865-873` that computes
  which chips render. This is the function this issue changes.
- **`initialScope`** — prop passed to `CommandPalette`. Cmd/Ctrl+J sets it to
  `'conversations'` (`src/dashboard/frontend/src/App.tsx:712-717`, PAN-2908).
- **`PaletteAction`** — the unified result-row type; each action carries a `group`
  heading string, mapped to a scope by `groupScope()` (`CommandPalette.tsx:220-229`).
- **Conversation hit** — a semantic-search result from `GET /api/palette/search`,
  rendered under the `Conversations` group (`CommandPalette.tsx:764-807`).
- **`EMPTY_SEARCH`** — the zero-result constant `fetchPaletteSearch` returns on
  non-OK responses, aborts, and exceptions (`CommandPalette.tsx:277-292`).

## Problem

The palette's scope-chip row only offers a chip for a type when results of that type
are currently on screen. Conversation hits exist only after a ≥2-character query
returns them from the server (`CommandPalette.tsx:405-419`), so the **Conversations
chip is invisible until conversation results already exist** — the operator cannot
narrow the palette to conversations first.

Worse, the scope-reset effect at `CommandPalette.tsx:876-878` actively fights the one
existing entry point: Cmd/Ctrl+J opens the palette with `initialScope =
'conversations'` (`App.tsx:712-717`), but with no conversation results present
`availableScopes` does not contain `'conversations'`, so the effect fires
`setScope('all')` and the conversations scope is silently discarded on open.

Note the scope *machinery* is already complete: `'conversations'` is in the
`PaletteScope` union (line 207), has a label (`SCOPE_LABEL`, lines 209-217), a group
mapping (`groupScope`, lines 220-229), and an accent color (`accentForGroup`,
lines 233-242). The only missing piece is that the chip's *availability* is
result-derived instead of first-class.

## Proposal

Pin `'conversations'` as a persistent scope so the chip renders whenever the chip row
renders, independent of current results, and make the empty/loading copy scope-aware.
Three small changes, all client-side, all in
`src/dashboard/frontend/src/components/CommandPalette.tsx` (plus its test file and one
docs page):

1. **Pin the chip.** In `availableScopes` (lines 865-873), always add
   `'conversations'` to the `present` set before ordering. Because the reset effect
   (lines 876-878) only resets scopes missing from `availableScopes`, pinning also
   fixes the Cmd/Ctrl+J reset bug with no change to the effect itself.
2. **Scope-aware empty and loading copy.** When `scope === 'conversations'`:
   - the empty-query hint (lines 957-962) renders `Type to search conversations…`
     instead of `Start typing…`;
   - the loading row (lines 951-956) renders `Searching conversations…` instead of
     `Searching conversations & memory…`.
3. **Document the chip row** in `docs/DESKTOP-APP.md` (section "Cmd+K Command
   Palette", lines 103-118), which currently never mentions scope chips at all.

No server changes. No new endpoints. No changes to result ordering (owned by
[PAN-3703](https://github.com/eltmon/overdeck/issues/3703)) and no ordering toggle
(owned by [PAN-3704](https://github.com/eltmon/overdeck/issues/3704)); scope filtering
already preserves the rank order produced upstream (`CommandPalette.tsx:970-972`
sorts by `rank`), so both sibling issues compose on top of this change unmodified.

### Before / after: `availableScopes` (CommandPalette.tsx:865-873)

Before:

```ts
const availableScopes = useMemo<PaletteScope[]>(() => {
  const present = new Set<PaletteScope>();
  for (const g of groupOrder) present.add(groupScope(g));
  // An action may answer to a chip its group does not imply, so the chip has
  // to be offered even when nothing else of that type is listed.
  for (const action of filtered) for (const s of action.alsoScopes ?? []) present.add(s);
  const ordered = (['actions', 'commands', 'workspaces', 'issues', 'conversations', 'memory'] as const).filter((s) => present.has(s));
  return ordered.length > 1 ? ['all', ...ordered] : [];
}, [groupOrder, filtered]);
```

After (one constant added near `SCOPE_LABEL`, two lines changed in the memo):

```ts
/** Scopes offered whether or not results of that type are currently present.
 * PAN-3705: Conversations is a first-class type-list entry; pinning it here also
 * stops the reset effect below from discarding the ⌘J conversations scope. */
const PINNED_SCOPES: ReadonlyArray<Exclude<PaletteScope, 'all'>> = ['conversations'];

const availableScopes = useMemo<PaletteScope[]>(() => {
  const present = new Set<PaletteScope>();
  for (const g of groupOrder) present.add(groupScope(g));
  // An action may answer to a chip its group does not imply, so the chip has
  // to be offered even when nothing else of that type is listed.
  for (const action of filtered) for (const s of action.alsoScopes ?? []) present.add(s);
  for (const s of PINNED_SCOPES) present.add(s);
  const ordered = (['actions', 'commands', 'workspaces', 'issues', 'conversations', 'memory'] as const).filter((s) => present.has(s));
  return ordered.length > 1 ? ['all', ...ordered] : [];
}, [groupOrder, filtered]);
```

The chip lands between **Issues** and **Memory**, matching the existing ordering
array. Selection, active-state styling, keyboard focus, and clear/reset behavior come
free — the chip renders through the same `<button>` path as every other chip
(`CommandPalette.tsx:932-945`).

## Requirements

Functional:

- **FR-1** — Whenever the scope-chip row renders, it includes a **Conversations**
  chip alongside Actions/Workspaces/Issues, even with an empty query and zero
  conversation results.
- **FR-2** — Activating the Conversations chip renders only conversation-group
  result rows (and rows declaring `alsoScopes: ['conversations']`, none exist
  today), in the same rank order the unfiltered list would show.
- **FR-3** — The Conversations chip uses the identical interaction path as the
  existing chips: pointer click and keyboard activation (focusable `<button>`,
  Enter/Space), the same active-state styling, and clearing via the **All** chip.
- **FR-4** — Opening the palette with `initialScope = 'conversations'` (Cmd/Ctrl+J)
  keeps the Conversations scope active; the reset effect does not flip it to All.
- **FR-5** — With the Conversations scope active: the empty-query hint reads `Type
  to search conversations…`; the in-flight search row reads `Searching
  conversations…`; a failed `/api/palette/search` request renders the same
  no-results empty state as zero hits (the existing `EMPTY_SEARCH` convention) with
  the chip row and active Conversations chip intact.
- **FR-6** — The change does not reorder any results. Conversation rows under the
  Conversations scope appear in ascending `rank` order exactly as delivered, so
  newest-first ordering (#3703) and the ordering toggle (#3704) compose on top.

Non-functional:

- **NFR-1** — No server-side changes: `/api/palette/search`, `palette.ts`, and the
  conversation-search service are untouched.
- **NFR-2** — No new colors, badge styles, or fonts; the existing chip class list
  (`CommandPalette.tsx:937-941`) and accent map are reused as-is.
- **NFR-3** — Tests use the repo's established patterns: vitest +
  `@testing-library/react` in `CommandPalette.test.tsx`, `vi.useFakeTimers()` for the
  120 ms search debounce, `installStrictFetchMock` for API stubs, `getByRole('button',
  { name })` for chips (the literal text "Conversations" also appears as a cmdk group
  heading — see the disambiguation pattern at `CommandPalette.test.tsx:206-214`).

## Decisions

- **D1 — Pin unconditionally, don't derive from capability.** The chip renders
  whenever the chip row renders; there is no client-side feature probe for semantic
  search (the server already returns an empty `conversations` array when search is
  unavailable). This matches the issue's "first-class entry" language.
- **D2 — Scope-aware copy.** The AC "empty, loading, and error states are correct
  when the Conversations type is selected" is read as: copy must not claim the
  palette is searching memory when only conversations are in scope. The generic
  strings stay for every other scope.
- **D3 — Error convention preserved.** `fetchPaletteSearch`
  (`CommandPalette.tsx:288-291`) swallows failures into `EMPTY_SEARCH` for every
  type today; under the Conversations scope that yields the standard no-results
  empty state. No new error UI is introduced — consistency with the other types
  outranks a one-off error affordance.
- **D4 — Memory chip is NOT pinned.** Symmetric treatment of Memory is unrequested
  and would change behavior operators did not ask about.
- **D5 — No ordering work here.** #3703 (newest-first) and #3704 (toggle) own
  ordering. This change only guarantees the scope filter preserves upstream rank
  order, and WI-1's order-preservation test is the composition guard.

## NonGoals

- Changing conversation result ordering (owned by #3703).
- Adding an ordering toggle or any persistence (owned by #3704).
- Pinning a Memory chip or altering Memory scope behavior.
- Any server change, including `/api/palette/search` parameters.
- Restyling the chip row, or adding ARIA pressed-state to the pre-existing chips
  (parity with existing chips is the requirement, not an accessibility retrofit).
