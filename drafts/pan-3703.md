# PRD: PAN-3703 — Ctrl-K search: show conversations newest first

**Issue:** https://github.com/eltmon/overdeck/issues/3703
**Status:** Draft for planning finalize
**Author:** planning agent (auto mode)

## Glossary

- **Command palette / Ctrl-K search** — the global search overlay in the dashboard,
  opened with Cmd-K / Ctrl-K. Implemented in
  `src/dashboard/frontend/src/components/CommandPalette.tsx`.
- **Conversation hit** — one row in the palette's *Conversations* group. A hit is a
  matched transcript **chunk** (not a whole conversation): it carries `sessionId`,
  `byteOffset` (where to open the transcript), `rank` (relevance), and `ts`
  (the matched chunk's message timestamp).
- **`ts`** — the canonical conversation timestamp at the palette layer: the ISO-8601
  message timestamp extracted from the transcript JSONL line by the chunker
  (`extractTimestamp` in `src/lib/conversation-search/chunker.ts:102`), stored on the
  chunk row in the embeddings DB, and returned by `/api/palette/search` as
  `PaletteConversationHit.ts` (`string | null`). This is the same value the row
  already displays as its Clock chip (`formatHitDate(hit.ts)`).
- **RRF / rank** — Reciprocal Rank Fusion over BM25 + vector results
  (`fuseRankedRows` in `src/lib/conversation-search/ranker.ts:66`). Produces `rank`
  1..N in relevance order. Rank decides *which* hits are returned (limit 15); this
  change does not alter it.

## Problem

When Ctrl-K search returns conversation results, they render in relevance (`rank`)
order. The render path sorts **every** palette group by ascending rank:

`src/dashboard/frontend/src/components/CommandPalette.tsx:970-972`:

```tsx
                  {filtered
                    .filter((a) => a.group === group && inScope(a))
                    .sort((a, b) => (a.rank ?? 0) - (b.rank ?? 0))
```

`ts` is present on every conversation hit but is used only as a display chip
(`CommandPalette.tsx:772`: `const date = formatHitDate(hit.ts);`). The conversation
the operator is most likely to resume — the most recently active one — is not
prioritized.

## Requirements

### Functional

- **FR-1** — Conversation results in the Conversations group render newest-first by
  the hit's `ts` (descending).
- **FR-2** — Ordering uses the canonical timestamp field (`ts` from the server
  response), never display order or client arrival (array) order.
- **FR-3** — Hits with equal `ts` values, unparseable `ts` strings, or `ts: null`
  order deterministically: timestamped hits before missing-timestamp hits; remaining
  ties break by ascending `rank`, then by action `id`.
- **FR-4** — Search filtering and scope-chip filtering do not change the
  newest-first ordering within the Conversations group (ordering is applied after
  filtering, at render).
- **FR-5** — Actions, commands, workspaces, issues, running agents, memory,
  observations, and summaries groups keep their current rank-ascending ordering.

### Non-functional

- **NFR-1** — No server changes: `/api/palette/search` already returns `ts`; the
  response's relevance ranking and limit behavior are unchanged.
- **NFR-2** — Tests use the existing `CommandPalette.test.tsx` fetch-mock harness
  with `vi.useFakeTimers()` (repo rule: no real timer waits in tests).

## Decisions (made in this document)

- **D1 — Sort key is the hit-level `ts`, not a per-conversation MAX(ts) join.**
  Each palette row represents a matched chunk and displays that chunk's `ts` as its
  date chip; sorting by the displayed value keeps the UI self-consistent. A
  per-session recency join (`MAX(ts) GROUP BY session_id` on the embeddings DB)
  would sort rows by a value that is not displayed — an old chunk of a recently
  active conversation would jump to the top while showing an old date — and would
  add a DB query per search. Rejected.
- **D2 — The sort lives in the frontend render path, not the server.** Presentation
  ordering is already frontend-owned (group ordering and the rank sort both live in
  `CommandPalette.tsx`), the server response order stays meaningful as pure
  relevance for any future consumer, and FR-2 is satisfied because the comparator
  reads the server's canonical `ts`, not array position.
- **D3 — Missing/unparseable `ts` sorts last.** A hit with no recency information
  is the least-likely resume target; last placement plus the rank/id tiebreak makes
  ordering fully deterministic (`rank` is unique within one response; `id` is
  `conv-<sessionId>-<byteOffset>` and unique per row).
- **D4 — Relevance still selects the result set; recency only reorders it.** RRF
  fusion and the limit of 15 are untouched. This matches the issue's third
  acceptance criterion (filtering does not change ordering) by keeping ordering a
  pure function of the returned set.

## Work items

### WI-1 — Sort the Conversations group newest-first by `ts` (with tests)

**Files:**
- `src/dashboard/frontend/src/components/CommandPalette.tsx` (implementation)
- `src/dashboard/frontend/src/components/CommandPalette.test.tsx` (tests)

**Steps:**

1. Add an optional `ts` field to the `PaletteAction` interface. Before
   (`CommandPalette.tsx:64-65`):

   ```ts
   // Sort hint within group: lower = earlier.
   rank?: number;
   ```

   After:

   ```ts
   // Sort hint within group: lower = earlier.
   rank?: number;
   // Conversation hit timestamp (chunk message ts); the Conversations group
   // sorts newest-first by this (PAN-3703).
   ts?: string | null;
   ```

2. In `memoryActions`, set the field when building conversation actions. The
   `out.push({...})` for conversations is at `CommandPalette.tsx:779-806`; add one
   property alongside `rank: hit.rank,` (line 785):

   ```ts
        rank: hit.rank,
        ts: hit.ts,
   ```

3. Add two module-level comparators near the other display helpers (after
   `formatHitDate`, around `CommandPalette.tsx:189-200`):

   ```ts
   /** Within-group ordering for non-conversation groups: relevance rank ascending. */
   const compareByRank = (a: PaletteAction, b: PaletteAction) => (a.rank ?? 0) - (b.rank ?? 0);

   /**
    * Conversations group ordering (PAN-3703): newest activity first by the hit's
    * canonical transcript timestamp. Hits with no parseable ts sort last; ties
    * fall back to relevance rank, then action id, so ordering is deterministic.
    */
   function compareConversationHits(a: PaletteAction, b: PaletteAction): number {
     const ta = a.ts ? Date.parse(a.ts) : Number.NaN;
     const tb = b.ts ? Date.parse(b.ts) : Number.NaN;
     const aHas = !Number.isNaN(ta);
     const bHas = !Number.isNaN(tb);
     if (aHas && bHas && ta !== tb) return tb - ta;
     if (aHas !== bHas) return aHas ? -1 : 1;
     return compareByRank(a, b) || a.id.localeCompare(b.id);
   }
   ```

4. Make the render sort group-aware. Before (`CommandPalette.tsx:970-972`):

   ```tsx
                    .filter((a) => a.group === group && inScope(a))
                    .sort((a, b) => (a.rank ?? 0) - (b.rank ?? 0))
   ```

   After:

   ```tsx
                    .filter((a) => a.group === group && inScope(a))
                    .sort(group === 'Conversations' ? compareConversationHits : compareByRank)
   ```

5. Add tests in `src/dashboard/frontend/src/components/CommandPalette.test.tsx`
   under a new `describe('CommandPalette conversation ordering (PAN-3703)')` block,
   using the same harness as the existing `describe('CommandPalette conversation
   results')` block (`installStrictFetchMock`, `vi.useFakeTimers()`,
   `renderCommandPalette`, advancing 120 ms for the debounce). Override the
   `/api/palette/search` mock per test with the fixtures below, and assert DOM order
   pairwise with the existing pattern:

   ```ts
   expect(earlier.compareDocumentPosition(later) & Node.DOCUMENT_POSITION_FOLLOWING).toBeTruthy();
   ```

   Row elements are looked up with the existing `getOptionByValue` helper; row
   values are `conv-<sessionId>-<byteOffset>`.

   - **T1 (multiple timestamps, FR-1/FR-2):** mock returns three hits in rank order
     1,2,3 whose `ts` values are NOT in rank order (e.g. rank 1 →
     `2026-06-01T01:00:00.000Z`, rank 2 → `2026-06-03T01:00:00.000Z`, rank 3 →
     `2026-06-02T01:00:00.000Z`). Assert rendered order is rank-2's row, then
     rank-3's, then rank-1's (newest first, not rank order).
   - **T2 (equal timestamps, FR-3):** two hits with identical `ts` and ranks 2 and
     1. Assert the rank-1 row renders before the rank-2 row.
   - **T3 (missing timestamp, FR-3):** one hit with `ts: null`, rank 1, and one hit
     with a real `ts`, rank 2. Assert the timestamped row renders first and the
     null-`ts` row last.
   - **T4 (other groups unchanged, FR-5):** in the same mock as T1, include two
     memory hits with ranks 2 and 1. Assert the memory group still renders
     rank-ascending. (Conversation ordering must not leak into other groups.)

**Tests that prove it:** T1–T4 above, run with

## Acceptance criteria (map 1:1 to work items)

- **AC-1 (WI-1, FR-1/FR-2):** T1 passes — conversation rows render newest-first by
  `ts` when the mock's rank order disagrees with timestamp order.
- **AC-2 (WI-1, FR-3):** T2 passes — equal `ts` hits render in ascending rank order.
- **AC-3 (WI-1, FR-3):** T3 passes — a `ts: null` hit renders after timestamped hits.
- **AC-4 (WI-1, FR-5):** T4 passes — memory rows keep rank-ascending order.
- **AC-5 (WI-1, FR-4):** the comparator is applied to the post-filter list at render
  (the `.filter(...)` / `.sort(...)` chain at `CommandPalette.tsx:970-972`), so
  scope-chip filtering cannot reorder conversation rows; T1's assertions hold with
  the Conversations scope chip active.
- **AC-6 (WI-2):** the plan carries a `docsJustification` entry stating no
  documented surface changes.

## Non-goals

- Changing RRF relevance ranking, the candidate limit, or the result limit.
- Per-conversation (session-level) recency joins against the embeddings DB or the
  transcripts resolver.
- Reordering any group other than Conversations.
- Server-side (`/api/palette/search`) response-order changes.
- Debounce, scope-chip, or keyboard-navigation behavior changes.
