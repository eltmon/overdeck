## 1. Glossary

Define every term before use. The executor is a model that cannot re-derive
these from tribal knowledge.

| Term | Meaning in this document |
| --- | --- |
| **Command Deck** | The three-column sidebar control surface. The project rows live in `src/dashboard/frontend/src/components/CommandDeck/ProjectTree/ProjectNode.tsx`. |
| **Project row / project header** | The clickable `<button className={styles.projectHeader}>` at `ProjectNode.tsx:305-366`. It contains the chevron, the project name, and the feature count. The CI chip goes here. |
| **Default branch** | `ProjectConfig.workspace?.default_branch` (`src/lib/projects.ts:54`), falling back to the literal `'main'` when unset. |
| **Check suite** | GitHub's grouping of check runs produced by one app for one commit. GitHub Actions creates **one check suite per workflow run**. Delivered as the `check_suite` webhook event. |
| **Suite app slug** | `check_suite.app.slug` in the webhook payload — e.g. `github-actions`, `vercel`, `posthog`. Used to filter (see §4.2). |
| **Observation** | One `project.ci_suite_observed` domain event: "at time T, suite S for project P at commit SHA had status X / conclusion Y". |
| **Record** | The per-project aggregate the read model keeps: `ProjectCiSnapshot`. One per project key. |
| **Read model** | `ReadModelState` in `packages/contracts/src/event-reducers.ts:72-117`, projected server-side by `src/dashboard/server/read-model.ts` and mirrored into the frontend Zustand store by `src/dashboard/frontend/src/lib/store.ts:38`. |
| **Domain event** | A member of the `DomainEvent` union at `packages/contracts/src/events.ts:1349-1451`. Appending one to the event store both updates the server read model and streams it to every browser over `/ws/rpc`. |
| **REST fill** | A one-shot `gh api` read of `repos/{repo}/actions/runs?branch=<default>` that seeds the record before any webhook arrives. |
| **Chip** | The compact CI indicator rendered in the project header. Not a badge, not a pill — see §7.3. |

## 2. Problem

The Command Deck shows agents, features, and conversations per project, but says
nothing about whether that project's `main` branch is currently green. To learn
that, the operator leaves the dashboard and opens GitHub. Overdeck already
receives `check_suite` webhooks for every tracked repository — it just throws
away everything that is not attached to a pull request
(`src/lib/webhook-handlers.ts:319`: `if (!suite.pull_requests || suite.pull_requests.length === 0) return;`).
A push to `main` produces check suites with an **empty** `pull_requests` array,
so today those events are dropped on the floor.

## 3. Proposal (one paragraph)

Stop dropping default-branch `check_suite` events. Map the event's repository to
a registered project, emit one new domain event
(`project.ci_suite_observed`) per observed GitHub Actions suite, and let a new
shared reducer aggregate those observations into a per-project record inside the
existing read model. A boot-time REST fill emits the same event type so the
record is correct before the first webhook. The frontend reads the record with a
Zustand selector and renders a chip in the project header that links to that
commit's checks on GitHub. No new store, no frontend polling, no new WebSocket
channel.

```
check_suite webhook ─┐
                     ├─► project.ci_suite_observed ─► event store ─► read model ─┬─► /ws/rpc ─► store ─► ProjectCiChip
REST fill (boot) ────┘                                                            └─► DashboardSnapshot (fresh page load)
```

## 4. Verified findings that shape the design

Every claim below was checked against the working tree and the live GitHub API
on 2026-08-04. Do not re-derive them; do not "fix" them back.

### 4.1 The GitHub App is **not** subscribed to `workflow_run`, and cannot read the Actions API

Queried live with an App JWT minted from `~/.overdeck/github-app/private-key.pem`:

```
slug:   overdeck-agent
events: ["check_run","check_suite","pull_request","pull_request_review",
         "pull_request_review_thread","status"]
perms:  {"checks":"read","contents":"write","metadata":"read",
         "pull_requests":"write","statuses":"write"}
```

Two consequences, both binding:

1. **No `workflow_run` events.** Live state must come from `check_suite`. The
   issue's decision block already anticipated this and forbids changing the App
   subscription in this issue.
2. **No `actions` permission.** An App installation token cannot call
   `GET /repos/{repo}/actions/runs` — it returns 403. The REST fill therefore
   **must not** use `src/lib/github-app.ts`. It uses `gh api` (the operator's
   user token), which is the same mechanism `src/lib/overdeck/project-pipelines.ts:99-106`
   already uses for the release panel and which was verified working:

   ```
   $ gh api "repos/eltmon/overdeck/actions/runs?branch=main&per_page=2"
   → 200, workflow_runs[] with id, name, head_branch, head_sha, status,
     conclusion, html_url, check_suite_id, created_at, updated_at
   ```

   The issue text names `src/lib/github-app.ts` as the fill client. That is the
   one anchor in the issue that does not survive verification. Use `gh api`.

### 4.2 A single commit on `main` has **7 check suites**, and 4 of them never conclude

```
$ gh api repos/eltmon/overdeck/commits/7fe22a07.../check-suites
total_count: 7
  vercel         queued      (conclusion null)
  mintlify       completed   skipped
  github-pages   queued      (conclusion null)
  posthog        queued      (conclusion null)
  github-actions completed   success
  github-actions in_progress (conclusion null)
  github-actions completed   success
```

If the chip aggregated all seven suites it would read "in progress" forever,
because the Vercel/PostHog/Pages suites sit in `queued` indefinitely for this
repo. **The reduction must keep only suites whose `app.slug === 'github-actions'`.**
This mirrors the existing advisory-filter precedent in
`src/lib/advisory-checks.ts`, which excludes CodeRabbit from merge gates.

The REST fill needs no equivalent filter: `actions/runs` returns GitHub Actions
runs only, and each run carries its own `check_suite_id`, so the two paths
produce the same suite identities.

### 4.3 One push produces several workflow runs, so "the latest run" is ambiguous

The same push produced `no-planning-on-main` (success) and `CI` (in_progress),
each its own workflow run with its own check suite. Reporting whichever row the
API returned first would let a trivial guard workflow paint the chip green while
CI is still running or failing. The record is therefore keyed by **head SHA**
and aggregates every GitHub Actions suite for that SHA.

### 4.4 The `check_suite` webhook payload carries no `html_url` for the run

`check_suite` gives `head_branch`, `head_sha`, `status`, `conclusion`, `id`,
`app`, and API URLs — never the human Actions URL. The issue's decision block
says to "build the link via the REST fill's `html_url` for that head SHA". That
works when a fill has run for the current SHA, and not otherwise. Both cases are
covered by the derivation rule in §6.4; the webhook-only fallback,
`https://github.com/<repo>/commit/<sha>/checks`, was verified to return HTTP 200
and shows every workflow run for that commit.

### 4.5 The event → read-model → browser path already exists end to end

- `src/dashboard/server/services/domain-services.ts:170-178` subscribes the read
  model to the event store, so **every** appended event runs through
  `applyEvent` in `packages/contracts/src/event-reducers.ts:332`.
- `src/dashboard/server/read-model.ts:410-447` (`buildSnapshot`) is what a fresh
  browser load receives; a field must be added there or a page reload shows an
  empty chip until the next webhook.
- There is no persistence allowlist — `src/dashboard/server/event-store.ts` writes
  and broadcasts whatever it is given.
- `src/dashboard/frontend/src/lib/store.ts:38` declares
  `DashboardState extends ReadModelState`, so adding a field to `ReadModelState`
  automatically makes it available to a selector.

### 4.6 `src/lib` code emits domain events through the activity-logger provider

`src/dashboard/server/event-store.ts:697` calls
`setActivityEventStoreProvider(() => store)`, and the deacon child does the same
with its HTTP client at `src/dashboard/server/deacon-main.ts:72`. The provider's
interface (`src/lib/activity-logger.ts:73-86`) already accepts any
`Omit<DomainEvent, 'sequence'>`; only its accessor is module-private. That is the
one wired emit door available to `src/lib/webhook-handlers.ts`, which runs
in-process in the dashboard server via `src/dashboard/server/routes/webhooks.ts:81-86`.

### 4.7 The project header is a `<button>`

`ProjectNode.tsx:305` renders `<button className={styles.projectHeader}>`.
Nesting an `<a href>` inside a `<button>` is invalid HTML and React will not
stop you. The existing "new conversation" affordance at `ProjectNode.tsx:353-366`
solves this with `<span role="button" tabIndex={0}>` plus `e.stopPropagation()`.
The chip follows that exact pattern.

## 5. Requirements

Functional:

- **FR-1** — Each Command Deck project header renders a compact CI chip for that
  project's default branch showing one of `queued`, `in progress`, `success`,
  `failure`, plus a `completed/total` suite count while not concluded. The chip
  is absent when the read model holds no record for that project key (a project
  with no GitHub repo, or one the App/`gh` cannot see, therefore shows nothing —
  no dead chrome).
- **FR-2** — Activating the chip opens that commit's GitHub checks in a new tab:
  the single run's `html_url` when exactly one GitHub Actions suite is known and
  its URL was supplied by the REST fill, otherwise
  `https://github.com/<repo>/commit/<headSha>/checks`.
- **FR-3** — State updates arrive over the existing webhook → domain event →
  `/ws/rpc` path. The frontend adds no polling loop, no `setInterval`, and no
  `useQuery` refetch for CI state.
- **FR-4** — A REST fill runs once at dashboard boot, per project with a
  `github_repo`, so the chip is correct before the first webhook arrives. A page
  reload also renders correctly, because the record ships in `DashboardSnapshot`.
- **FR-5** — An in-progress run shows progression: a suite transitioning
  `queued → in_progress → completed` moves the chip's state and count without a
  reload.
- **FR-6** — The record is derived only from GitHub Actions check suites for the
  project's default branch. Suites from other apps and events for other branches
  never change it.
- **FR-7** — Out-of-order and stale events do not corrupt the record: a
  same-SHA observation merges by suite id, a newer-SHA observation replaces the
  record, and an observation older than the record's `updatedAt` for a different
  SHA is ignored.
- **FR-8** — A low-frequency server-side refill (every 15 minutes) repairs the
  record if a webhook delivery is lost, so a long-running dashboard cannot show
  an indefinitely stale CI state.

Non-functional:

- **NFR-1** — The chip follows the dashboard style guide: no pill
  (`rounded-full`) badge, no `font-bold`/`font-semibold`, no hardcoded hex, no
  `slate-*`, SF Mono only for the count. Signal color appears only for
  `in progress` (`--info`, machine working) and `failure` (`--destructive`,
  broken); `success` and `queued` render `--muted-foreground`.
- **NFR-2** — Unit tests cover the webhook→observation mapping (branch filter,
  app-slug filter, untracked repo) and the reducer (merge, new-SHA replace,
  stale-drop, state derivation), plus a frontend render test for every chip
  state.
- **NFR-3** — No `execSync` anywhere on this path (`src/dashboard/server` and
  everything it reaches). The REST fill uses `promisify(execFile)`, matching
  `src/lib/overdeck/project-pipelines.ts:29`.
- **NFR-4** — No new durable store. The record is disposable cache state in the
  read model, rebuilt from REST + webhooks on every boot.

## 6. Design

### 6.1 The new domain event — `project.ci_suite_observed`

One event type, not two. A REST fill emits the same shape as a webhook, so the
reducer has exactly one case and one staleness rule to reason about.

Added to `packages/contracts/src/events.ts` (place it next to
`BeadsFreshnessChangedEvent` at line 38, the existing project-scoped event) and
registered in the `DomainEvent` union at line 1349:

```ts
/**
 * One GitHub Actions check suite observed on a project's default branch
 * (PAN-3537).
 *
 * Emitted from two places, deliberately with the same shape:
 *   1. the `check_suite` webhook handler, for live updates; and
 *   2. the boot/periodic REST fill, which seeds and repairs the record.
 *
 * `suiteId` is the check suite id — for GitHub Actions that is one suite per
 * workflow run, so the per-SHA suite set is the set of workflow runs for that
 * commit. `htmlUrl` is present only on REST-sourced observations; the webhook
 * payload does not carry one.
 *
 * The aggregate this feeds is `ReadModelState.ciByProjectKey`, a disposable
 * cache rebuilt from REST on every boot — there is no durable CI store.
 */
export const ProjectCiSuiteObservedEvent = Schema.Struct({
  type: Schema.Literal("project.ci_suite_observed"),
  sequence: SequenceNumber,
  timestamp: Schema.String,
  payload: Schema.Struct({
    projectKey: Schema.String,
    repo: Schema.String,          // "owner/repo"
    branch: Schema.String,        // the project's default branch
    headSha: Schema.String,
    suiteId: Schema.String,       // stringified check suite id
    status: Schema.String,        // queued | in_progress | completed | ...
    conclusion: Schema.NullOr(Schema.String),
    htmlUrl: Schema.optional(Schema.String),
    observedAt: Schema.String,    // ISO 8601
  }),
})
export type ProjectCiSuiteObservedEvent = typeof ProjectCiSuiteObservedEvent.Type
```

### 6.2 The record shape

Added to `packages/contracts/src/types.ts` next to the other snapshot schemas
(before `DashboardSnapshot` at line 525), because `DashboardSnapshot` must carry
it:

```ts
export const ProjectCiSuite = Schema.Struct({
  status: Schema.String,
  conclusion: Schema.NullOr(Schema.String),
  htmlUrl: Schema.optional(Schema.String),
})
export type ProjectCiSuite = typeof ProjectCiSuite.Type

export const ProjectCiSnapshot = Schema.Struct({
  projectKey: Schema.String,
  repo: Schema.String,
  branch: Schema.String,
  headSha: Schema.String,
  /** suiteId → suite. Only GitHub Actions suites ever appear here. */
  suites: Schema.Record(Schema.String, ProjectCiSuite),
  /** Newest `observedAt` folded into this record. */
  updatedAt: Schema.String,
})
export type ProjectCiSnapshot = typeof ProjectCiSnapshot.Type
```

State (`derived`, never stored) and the link are computed by a shared exported
helper so the server and the browser cannot disagree — see §6.4.

- Add to `syncSnapshot` (line 274-330): `ciByProjectKey: snapshot.ciByProjectKey ?? state.ciByProjectKey,`
- Add the case to `applyEvent`:

```ts
case 'project.ci_suite_observed': {
  const p = event.payload
  const existing = state.ciByProjectKey[p.projectKey]
  const suite = { status: p.status, conclusion: p.conclusion, htmlUrl: p.htmlUrl }

  let next: ProjectCiSnapshot
  if (!existing) {
    next = {
      projectKey: p.projectKey, repo: p.repo, branch: p.branch, headSha: p.headSha,
      suites: { [p.suiteId]: suite }, updatedAt: p.observedAt,
    }
  } else if (existing.headSha === p.headSha) {
    // Same commit: merge the suite in, advance updatedAt monotonically.
    next = {
      ...existing,
      suites: { ...existing.suites, [p.suiteId]: suite },
      updatedAt: p.observedAt > existing.updatedAt ? p.observedAt : existing.updatedAt,
    }
  } else if (p.observedAt >= existing.updatedAt) {
    // Newer commit wins and resets the suite set — commit ordering is not
    // available from the payload, so observation recency is the tiebreak.
    next = {
      projectKey: p.projectKey, repo: p.repo, branch: p.branch, headSha: p.headSha,
      suites: { [p.suiteId]: suite }, updatedAt: p.observedAt,
    }
  } else {
    // A late event for an older commit. Drop it.
    return { ...state, sequence: Math.max(state.sequence, event.sequence) }
  }

  return {
    ...state,
    sequence: Math.max(state.sequence, event.sequence),
    ciByProjectKey: { ...state.ciByProjectKey, [p.projectKey]: next },
  }
}
```

### 6.4 Derivation helper (shared, pure, exported from contracts)

New file `packages/contracts/src/project-ci.ts`, re-exported from
`packages/contracts/src/index.ts`:

```ts
export type ProjectCiState = 'queued' | 'in_progress' | 'success' | 'failure'

export interface DerivedProjectCi {
  state: ProjectCiState
  completed: number
  total: number
  /** Where the chip navigates. Always an absolute github.com URL. */
  href: string
}

/** Conclusions that mean the suite failed. Mirrors FAILING_CHECK_CONCLUSIONS
 *  in src/lib/webhook-handlers.ts:196. */
const FAILED = new Set(['failure', 'timed_out', 'cancelled', 'action_required', 'startup_failure', 'stale'])

export function deriveProjectCi(record: ProjectCiSnapshot): DerivedProjectCi {
  const suites = Object.values(record.suites)
  const total = suites.length
  const completed = suites.filter((s) => s.status === 'completed').length

  const state: ProjectCiState =
    suites.some((s) => s.conclusion != null && FAILED.has(s.conclusion.toLowerCase())) ? 'failure'
    : suites.some((s) => s.status === 'in_progress') ? 'in_progress'
    : completed < total || total === 0 ? 'queued'
    : 'success'

  const only = total === 1 ? suites[0] : undefined
  const href = only?.htmlUrl
    ?? `https://github.com/${record.repo}/commit/${record.headSha}/checks`

  return { state, completed, total, href }
}
```

Precedence note: `failure` outranks `in_progress`. A red CI run stays red on the
chip even while another workflow is still running — the operator needs to see
"broken" the moment it is known, not after everything settles.

### 6.6 The emit door

`src/lib/activity-logger.ts` gains one export next to

/**
 * Append an arbitrary domain event through the process-local event store.
 *
 * The provider is shared with activity emission (it is set by
 * src/dashboard/server/event-store.ts in the server and by deacon-main.ts in

export async function appendDomainEventAsync(
  event: Omit<DomainEvent, 'sequence'>,
): Promise<boolean> {
  const store = getActivityEventStore();
  if (!store) return false;
  try {
    await store.appendAsync(event);
    return true;
  } catch {
    return false;
  }
}

### 6.8 REST fill

New `src/lib/overdeck/project-ci-fill.ts`, modelled directly on
`src/lib/overdeck/project-pipelines.ts` (same `GhApi` injection point at line
97-106, same `promisify(execFile)` at line 29):

```ts
type GhApi = (path: string) => Promise<unknown>

/** Fetch the newest default-branch commit's GitHub Actions runs for one
 *  project and return one observation per run. Returns [] on any failure —
 *  no repo, no gh auth, no Actions — so the chip simply does not render. */
export async function fillProjectCiObservations(
  project: { key: string; config: ProjectConfig },
  deps?: { ghApi?: GhApi; now?: () => string },
): Promise<ProjectCiSuiteObservedEvent['payload'][]>

/** Fill every project with a github_repo and append the observations. */
export async function fillAllProjectCi(
  deps?: { ghApi?: GhApi; append?: typeof appendDomainEventAsync },
): Promise<number>
```

`fillProjectCiObservations` logic:

1. `repo = project.config.github_repo`; return `[]` when unset.
2. `branch = project.config.workspace?.default_branch ?? 'main'`.
3. `ghApi('repos/' + repo + '/actions/runs?branch=' + encodeURIComponent(branch) + '&per_page=20')`.
4. Take `workflow_runs[0].head_sha` as the current SHA; keep only runs with that
   `head_sha` (`per_page=20` is a generous window for one commit's workflows).
5. Emit one observation per kept run:
   `suiteId: String(run.check_suite_id)`, `status: run.status`,
   `conclusion: run.conclusion`, `htmlUrl: run.html_url`,
   `observedAt: run.updated_at`.

Using `run.updated_at` as `observedAt` — not wall-clock — is deliberate: it
makes the fill lose to a fresher webhook under the §6.3 staleness rule instead
of stomping it.

**Component** — new `src/dashboard/frontend/src/components/CommandDeck/ProjectCiChip.tsx`:

```tsx
const STATE_COLOR: Record<ProjectCiState, string> = {
  // Style guide v1.2 signal law: blue = a machine is working, red = broken,
  // neutral = rest state. Emerald is deliberately NOT used for success — a
  // green chip on every project row all day is decoration, and the
  // colour-restraint rule caps a data-dense row at one colored signal.
  queued: 'var(--muted-foreground)',
  in_progress: 'var(--info)',
  success: 'var(--muted-foreground)',
  failure: 'var(--destructive)',
};

export function ProjectCiChip({ projectKey }: { projectKey: string }) {
  const record = useDashboardStore(selectProjectCi(projectKey));
  if (!record) return null;
  const { state, completed, total, href } = deriveProjectCi(record);
  const label = state === 'success' ? 'CI' : state === 'failure' ? 'CI ✗' : `CI ${completed}/${total}`;
  const open = (e: React.SyntheticEvent) => {
    e.stopPropagation();
    window.open(href, '_blank', 'noopener,noreferrer');
  };
  return (
    <span
      role="link" tabIndex={0}
      data-testid="project-ci-chip"
      data-ci-state={state}
      className={styles.projectCiChip}
      style={{ color: STATE_COLOR[state] }}
      title={`${record.branch} @ ${record.headSha.slice(0, 7)} — ${state} (${completed}/${total} workflows)`}
      onClick={open}
      onKeyDown={(e) => { if (e.key === 'Enter' || e.key === ' ') open(e); }}
    >{label}</span>
  );
}
```

`role="link"` + `window.open` rather than an `<a>` because the parent is a
`<button>` (§4.7). `data-ci-state` is the test hook.

## 7. Decisions made in this document

These are the `--auto` decisions. Do not re-open them during implementation.

| # | Decision | Rationale |
| --- | --- | --- |
| D1 | REST fill uses `gh api`, not the GitHub App client | The App has no `actions` permission (§4.1); an App token 403s on `actions/runs`. `gh api` is the verified-working precedent in `project-pipelines.ts`. |
| D2 | Only `app.slug === 'github-actions'` suites count | 4 of the 7 suites on a real `main` commit are third-party apps stuck in `queued` forever; including them pins the chip at "in progress" (§4.2). |
| D3 | The record is keyed by head SHA and aggregates all Actions suites for it | One push creates several workflow runs; picking one would let a guard workflow paint the chip green while CI fails (§4.3). |
| D4 | One event type for both webhook and REST fill | Same semantics ("a suite was observed"), so one reducer case and one staleness rule. Two types would mean two merge policies to keep consistent. |
| D5 | Newer `observedAt` wins when the SHA changes | Commit ordering is not derivable from the payload; observation recency is the only tiebreak available without an extra API call. |
| D6 | `failure` outranks `in_progress` in state derivation | A known-red run should show red immediately, not after unrelated workflows finish. |
| D7 | `success` renders neutral, not emerald | Style-guide colour restraint: one colored signal per data-dense row. A permanently green chip on every project is decoration. |
| D8 | Chip is absent when no record exists | Satisfies "no dead chrome" without plumbing extra project config to the frontend — the fill only creates records for projects it can actually read. |
| D9 | 15-minute server-side refill, boot fill alone is not enough | Smee-relayed webhooks can drop; without a repair path a long-running dashboard shows stale CI indefinitely. It is server-side, so FR-3's no-frontend-polling rule is untouched. |
| D10 | `check_run` (per-job) granularity is out of scope | Suite-level `completed/total` already exceeds FR-5's minimum, and check suites map 1:1 to workflow runs, which is the more meaningful unit. |
| D11 | The event is promoted to the public external-stream catalog | "Is main green" is exactly the signal a third-party sidecar wants, and `docs/EXTERNAL-EVENT-STREAM.md:107` requires the promoting PR to add the row. |

## 8. Non-goals

- Feature-branch or PR CI state. Already surfaced per-PR elsewhere; this issue is
  default branch only.
- Changing the GitHub App's event subscription or permissions (explicitly
  forbidden by the issue).
- Per-job (`check_run`) counts in the chip.
- A CI panel, history, or run list anywhere else in the dashboard (God View, the
  Stage, the release panel). The chip is the only new surface.
- Any durable persistence of CI state. The record is disposable cache.
- Any frontend polling, refetch interval, or new WebSocket channel.
- Re-running or cancelling workflows from the dashboard.
- GitLab CI (MYN's backend). Only `github_repo` projects get a chip.

## 11. Acceptance criteria (mapped to work items)
