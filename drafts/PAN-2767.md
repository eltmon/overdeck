# PAN-2767 — Expose Codex app-server conversation controls in the dashboard

**Status:** Draft  
**Issue:** https://github.com/eltmon/overdeck/issues/2767  
**Mockup:** `docs/design/mockups/codex-app-server-controls.html`  
**Depends on:** PAN-2597, which established Codex app-server as the structured conversation transport.

## Glossary

- **App-server:** The persistent `codex app-server` child process that owns a Codex thread and exchanges JSON-RPC requests, responses, notifications, and approval prompts with Overdeck.
- **Thread:** Codex's durable conversation history. A thread contains zero or more turns and can be resumed or forked.
- **Turn:** One unit of agent work begun by `turn/start`. A turn has an ID, lifecycle state, model configuration, streamed items, token usage, plan, and aggregate diff.
- **Steer:** Add user input to the currently active turn with `turn/steer`. It is distinct from starting the next turn and requires the caller's expected active turn ID.
- **Capability:** A model or control value reported by the running app-server, such as supported models and reasoning-effort levels. The UI must not infer Codex capabilities from the Anthropic-only static table.
- **Control projection:** The small, typed, UI-safe view of app-server state exposed by Overdeck. It is not a raw JSON-RPC passthrough.
- **Terminal bridge:** A text composer that presents familiar command-like shortcuts but translates only explicitly supported commands into typed app-server operations.
- **No-loss audit:** A focused compatibility test proving every existing conversation action still has a working home after this surface is extended.

## Problem

PAN-2597 moved Codex conversations from terminal keystroke delivery to a persistent app-server. That fixed structured delivery and approvals, but the dashboard still treats live model and effort controls as if Codex were a TUI: the model picker is locked after launch, OpenAI models report no effort levels, compact is Pi-only, and ordinary messages carry neither effort nor service tier. Operators consequently lose controls that the Codex app-server already exposes.

The backend has the necessary foundation but only a narrow surface. `src/lib/codex/app-server-host.ts` handles `status`, `message`, `interrupt`, `approval`, and `user-input`; `src/lib/codex/app-server-manager.ts` sends `turn/start` with optional `model` and `effort`; and `src/lib/agents/delivery.ts` currently forwards only the stored model:

```ts
const body: Record<string, unknown> = {
  op: 'message',
  content: message,
  meta: { caller },
};
if (state.model) body['model'] = state.model;
```

The frontend similarly sends only the message and Pi's `deliverAs` from `src/dashboard/frontend/src/lib/composerStore.ts`:

```ts
body: JSON.stringify(deliverAs ? { message, deliverAs } : { message }),
```

Codex 0.144.4's generated protocol fixture at `src/lib/codex/__fixtures__/app-server-schema.json` exposes `model/list`, `turn/steer`, `turn/interrupt`, `thread/compact/start`, `review/start`, `thread/fork`, lifecycle notifications, token usage, plans, diffs, and approval requests. This change should expose that useful subset as first-class Overdeck controls without attempting to recreate the entire Codex TUI.

## Goals

1. Let operators choose the Codex model, reasoning effort, and supported service tier for an explicit turn and see the effective values.
2. Distinguish steering the active turn from sending the next turn.
3. Expose interrupt, compact, review, and fork through typed controls.
4. Show authoritative turn state, token usage, plan, diff, and pending approvals in the conversation UI.
5. Preserve tmux as the process host and liveness surface while app-server remains the sole owner of Codex conversation state.
6. Preserve every existing Claude, Pi, attachment, retry, approval, and fallback behavior.

## Non-goals

- Running the real Codex TUI and app-server against the same thread concurrently.
- Passing arbitrary JSON-RPC methods or parameters from the browser.
- Exposing `shellCommand`, filesystem APIs, plugin installation, account mutation, configuration writes, or other full-access protocol methods.
- Reimplementing every Codex slash command.
- Adding a new rollback control. `thread/rollback` is deprecated in the checked-in protocol fixture and only rewrites conversation history, not the filesystem. Forking from a selected completed turn is the supported recovery action for this issue.
- Changing model defaults. An unset model or effort continues to resolve from explicit configuration; `high` remains the default effort and `xhigh`/`max` appear only when the operator explicitly selects a model-reported value.

## Decisions

### One process owns a thread

The app-server remains the only protocol client for its Codex thread. The dashboard talks to the existing host socket; tmux owns the persistent host process and supplies liveness/fallback only. No second TUI process may resume and mutate that thread concurrently.

### Selection is explicit and response-backed

Changing a picker updates a local draft. The chosen model, effort, or service tier is sent only when the operator starts or steers a turn. The UI updates its “effective” badges from the successful app-server response or subsequent notification, never merely from the click. This preserves the PAN-1847 invariant documented in `ComposerFooter.tsx`: a plain message must not silently switch models while the picker lies about the running model.

### Steer and next turn are different actions

When a turn is active, the primary send action is **Steer current turn** and includes `expectedTurnId`. **Send next turn** is a separately labeled action that waits until the current turn completes; Overdeck must not silently translate one into the other. A stale expected turn returns HTTP 409 with refreshed control state.

### Typed façade, not generic passthrough

`CodexAppServerHost` gains individually validated operations. Browser payloads never choose arbitrary app-server method names. This bounds the security surface and lets protocol drift fail clearly at one adapter.

### Capability source and fallback

The host obtains Codex models and effort levels from `model/list` and caches them for the life of the app-server process. If capability discovery fails, the response reports `capabilitiesAvailable: false`; the UI keeps current effective values visible but disables unsupported pickers. It must not substitute `MODEL_EFFORT_SUPPORT`, whose current entries in `ModelPicker.tsx` are Anthropic-only.

### Protocol-version checkpoint

Implementation must regenerate or validate the fixture against the packaged Codex version before wiring a method. If a named method changed, adapt at `CodexAppServerManager`; do not leak version branches into React. If compact, review, or fork is absent, disable that action with an explicit “unsupported by Codex <version>” reason and continue shipping the remaining controls.

## Requirements

### Functional requirements

- **FR-1:** A Codex app-server conversation exposes a control projection containing host state, thread ID, active turn ID, effective model, effective effort, effective service tier, supported models and their effort levels, pending request count/types, token usage, plan, diff availability, and per-action capability flags.
- **FR-2:** Starting a turn accepts optional model, effort, and service tier values only after validating them against the live capability projection. Omitting a value preserves the app-server/configured default; no hardcoded fallback is introduced.
- **FR-3:** Steering an active turn calls `turn/steer` with `threadId`, `expectedTurnId`, and input. A mismatched or completed turn returns a conflict response and current state rather than starting a new turn.
- **FR-4:** The existing interrupt action remains available and clearly reflects idle, interrupting, and stopped states.
- **FR-5:** Compact calls the supported thread compact method, disables while incompatible work is active, and reports completion or failure in the timeline.
- **FR-6:** Review starts a Codex review for an explicit target and supports inline or detached delivery when the installed protocol advertises those values.
- **FR-7:** Fork creates a new Overdeck conversation from a selected completed turn via `thread/fork`; it never repoints the existing conversation at a different thread.
- **FR-8:** App-server lifecycle notifications update the control projection and conversation timeline for turn started/completed, token usage, plan, aggregate diff, and approval/user-input requests.
- **FR-9:** The terminal bridge translates only `/model`, `/effort`, `/compact`, `/review`, `/status`, and `/help` into typed operations. Unsupported slash-prefixed text remains ordinary prompt text after a visible confirmation; it is never executed as a shell command.
- **FR-10:** The dashboard explains when draft settings apply, distinguishes draft from effective settings, and identifies controls unavailable in the running app-server version.
- **FR-11:** Existing `message`, `interrupt`, `approval`, and `user-input` host operations retain their request/response behavior.
- **FR-12:** Non-Codex conversation payloads and control-channel behavior remain byte-for-byte compatible, including Pi `deliverAs`, thinking-level changes, and compact.
- **FR-13:** Image validation, harness transformation, optimistic timeline behavior, eaten-message retry protection for Claude, title generation, and app-server-to-tmux fallback remain intact.

### Non-functional requirements

- **NFR-1:** Dashboard-server and host code use async process/network primitives only; no `execSync` or synchronous tmux delivery is added.
- **NFR-2:** The browser cannot invoke arbitrary app-server methods or supply unvalidated model/effort/service-tier values.
- **NFR-3:** Retry, timeout, debounce, or delayed notification tests use Vitest fake timers.
- **NFR-4:** The UI is keyboard navigable, has visible focus states, announces turn/control status changes, and remains usable at 375px width.
- **NFR-5:** Cached capabilities are scoped to one running app-server process and invalidated when that process restarts.
- **NFR-6:** Boot-path changes are validated on a throwaway dashboard instance before any live restart.

## Design and implementation

### Work item 1 — Extend the typed Codex manager adapter

**Traces:** FR-1, FR-3, FR-5, FR-6, FR-7, FR-8; NFR-1, NFR-5.

Update `src/lib/codex/app-server-manager.ts` near `ThreadOptions`, `TurnOptions`, `startTurn`, `interruptTurn`, and `handleServerMessage`.

1. Add typed parameter/result interfaces for model listing, steer, compact, review, and fork. Keep the generic `request()` private to the adapter boundary.
2. Extend `TurnOptions` with the exact service-tier field supported by the validated schema.
3. Add `steerTurn(input, expectedTurnId)`, `compactThread()`, `startReview(target, delivery)`, `forkThread(lastTurnId)`, and `listModels()` methods.
4. Project `thread/tokenUsage/updated`, `turn/plan/updated`, and `turn/diff/updated` notifications into manager state. Store bounded summaries, not unbounded raw notification history.
5. Clear cached capabilities and volatile turn projection when the child process stops.

Before:

```ts
async startTurn(input: string, options: TurnOptions = {}): Promise<unknown> {
  return this.request('turn/start', {
    threadId: this.threadId,
    input: [{ type: 'text', text: input }],
    model: options.model,
    effort: options.effort,
  });
}
```

After, structurally:

```ts
async steerTurn(input: string, expectedTurnId: string): Promise<TurnSteerResult> {
  return this.request('turn/steer', {
    threadId: this.requireThreadId(),
    expectedTurnId,
    input: [{ type: 'text', text: input }],
  });
}
```

Tests: extend `src/lib/codex/__tests__/app-server-manager.test.ts` and `src/lib/codex/__tests__/fake-app-server.ts` to assert exact method names/params, state transitions, cache invalidation, notification projection, and protocol errors.

## Risks and mitigations

- **Protocol drift:** App-server APIs evolve with Codex. Isolate all translation in the manager, validate the packaged schema, and advertise unavailable actions rather than guessing.
- **False UI state:** Picker state can get ahead of the process. Separate draft from effective values and acknowledge mutations from host state.
- **Dual ownership:** A TUI and app-server can race on one thread. Keep a single app-server owner and use tmux only for host lifecycle.
- **Regression breadth:** The composer serves several harnesses. Gate with the explicit no-loss matrix and keep Codex-only request fields out of other harness branches.
- **Unbounded streaming state:** Plan/diff/token notifications can be frequent. Store bounded latest projections and coalesce frontend updates.
- **Unsafe protocol expansion:** The schema includes full-access methods. Expose a fixed allowlist and keep shell/filesystem/config/plugin operations out of scope.
