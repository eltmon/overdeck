## Glossary

- **Needs-you event** — a state change that blocks on the operator. Primary source:
  `agent.enrichment_changed` events emitted by the enrichment poller
  (`src/dashboard/server/services/agent-enrichment-service.ts:213-231`) with payload fields
  `hasPendingQuestion`, `pendingQuestionCount`, `pendingQuestionPrompt`, `pendingAskUserQuestion`,
  `pendingInputKinds`. Edge-triggered: emitted only on change (dedup at `:47-48`).
- **Event store subscription** — in-process API: `getEventStore()` (`src/dashboard/server/event-store.ts:403`),
  `store.subscribe(fn): Unsubscribe` (`:303-306`), sees ALL events including internal ones. This matters:
  `agent.enrichment_changed` is NOT in the SSE `PUBLIC_CATALOG` (`routes/events.ts:27-42`), so the bridge
  must be an in-server subscriber, not an SSE client.
- **ntfy** — self-hostable pub/sub push service; publishing is a plain HTTP POST to `https://<server>/<topic>`
  with title/body/click headers. iOS caveat: self-hosted ntfy still routes notification wake-ups through
  ntfy.sh upstream (APNs constraint) — acceptable for v1, payload can be kept minimal.
- **Config YAML layer** — dashboard-editable config at `~/.overdeck/config.yaml`, schema in
  `src/lib/config-yaml/schema.ts` (main config is TOML; YAML overrides — the `tts` block at `:269-289`,
  wired at `:487-490` with normalizer `:776-780`, is the pattern to copy).

## Problem

When an agent asks a question or the pipeline blocks, nothing reaches the operator away from the screen.
TTS (`activity.tts`) covers in-room presence only. Zero push infrastructure exists (verified:
`grep -rniE "ntfy|web-push|webpush|vapid" src/` → no matches). The UX rule (Omnara's lesson, adopted in the
epic): notify on needs-you, never the activity firehose.

## Decisions

- **D-1 In-server subscriber, not a separate daemon and not an SSE client** — because needs-you events are
  internal-only (see Glossary) and a daemon adds lifecycle surface for no benefit. Exact template exists:
  the memory-poller subscriber block in `src/dashboard/server/main.ts:459-478`
  (`initEventStore()` → `store.subscribe(...)` with typed filtering), started alongside services like
  `startAgentEnrichmentService()` (`main.ts:151-165`), torn down with the shutdown cleanup (`main.ts:498+`).
- **D-2 Provider interface from day one, ntfy as the only v1 implementation.**
  `PushProvider = { send(n: PushNotification): Promise<void> }`; `PushNotification = {title, body, link?,
  priority?}`. PAN-2355 adds `webpush`, PAN-2356 adds `relay`. No speculative providers beyond the interface.
- **D-3 Notify set (v1, closed list):** (1) `agent.enrichment_changed` where `payload.hasPendingQuestion
  === true` — title from role+issue, body from `pendingQuestionPrompt` (truncated 140 chars); (2)
  `issue.status_changed` into operator-gated phases (awaiting-merge / needs review decision) — exact phase
  list resolved at implementation from the event's payload values, recorded in the vBRIEF; (3)
  `dashboard.lifecycle_failed`. Everything else: out, including agent.started/stopped.
- **D-4 Debounce + burst-collapse:** per-subject cooldown 90s; ≥3 notifications within 10s collapse into
  one "N agents need you" summary. Timers via `setTimeout` in the service — tests use fake timers.
- **D-5 Deep links** use `push.link_base_url` (falls back to `http://localhost:3011`); links target the
  existing tab paths (`/command-deck`, `/awaiting-merge` — `FE/src/App/routes.ts:4`) and, after PAN-2355,
  the mobile surface.

## Requirements

- **FR-1** Config block `push` in the YAML layer: `{enabled: boolean, provider: 'ntfy', ntfy: {url, topic,
  auth_token?}, link_base_url?: string, quiet_hours?: {start, end}}`. Defaults: disabled. Schema + defaults
  + normalizer following the `tts` pattern (`config-yaml/schema.ts:269-289`, `:487-490`, `:776-780`).
  No hardcoded topic/server fallbacks — disabled means silent, absent field means loud config error at boot
  validation, not a guessed default.
- **FR-2** Bridge service `src/dashboard/server/services/push-bridge.ts`: `startPushBridge()` /
  `stopPushBridge()`; subscribes per D-1, filters per D-3, debounces per D-4, calls the provider. Failures:
  log-and-drop with a counter; NEVER retry-storm (single retry after 5s, then drop — fake-timer tested);
  a dead ntfy server must not affect the dashboard (fire-and-forget promise, error boundary).
- **FR-3** ntfy provider: POST with `Title`, `Click` (deep link), `Priority` headers; `Authorization:
  Bearer` when `auth_token` set; 5s request timeout via `AbortController`.
- **FR-4** Quiet hours (if configured): suppress non-critical (D-3 class 2) notifications; class 1 and 3
  always deliver.
- **FR-5** Observability: bridge emits `activity.entry` events on start/stop/config-reload and keeps
  sent/dropped counters exposed on `GET /api/health`-adjacent debug logging (no new route).
- **NFR-1** No `execSync`; no event-loop blocking; all delays fake-timer-testable.
- **NFR-2** Zero behavior when `push.enabled` is false or absent (byte-identical event handling path:
  subscriber not registered at all).

## Intersecting repo rules (restated)

Fake timers for ALL delay/debounce/retry tests (`vi.useFakeTimers()` + `advanceTimersByTimeAsync` — never
real 5s waits, never `maxForks: 1` masking); no `execSync` server-side; no hardcoded fallbacks (D-1 of the
model rule applies to servers/topics too); boot-path adjacency: `main.ts` startup wiring is a boot-path
change — runtime-boot-test on a throwaway instance before live restart, `pan restart --health-timeout 120`;
two doors — the bridge only consumes the event store's subscribe API, never reads SQLite directly.

## Out of scope

Web Push/VAPID (PAN-2355); APNs/FCM and relay-origin push (PAN-2356); per-user routing (single operator
topic in v1); notification actions/replies from the notification itself.
