**Status:** Draft implementation PRD

**Audience:** Implementation, review, test, and documentation agents
**Codebase snapshot reviewed:** `main` at `02809858e2a8cbe629d3783929d199a32f97eff9` on 2026-07-14

## Glossary

- **Accepted assessment:** One internally consistent health result whose severity, structured reasons, metrics, and timestamp all come from the same sample accepted by the hysteresis state machine.
- **Admission headroom:** Available RAM remaining after accounting for configured reserves and the estimated footprint of a new agent. It controls whether Overdeck may start work; it is not synonymous with host failure.
- **Agent runtime health:** State-aware classification of an agent using canonical persisted agent state, live tmux presence, and canonical runtime state. Intentional idle/warm/waiting states are not failures.
- **Current pressure:** Evidence that the operating system is presently reclaiming, stalling, swapping, or otherwise struggling for memory. Historical swap occupancy and virtual commitment are not current pressure.
- **Health domain:** One independently reported area: host pressure, spawn admission, agent runtime, or service availability. A domain retains its own status and reasons instead of being flattened into an unexplained color.
- **Historical swap occupancy:** `SwapTotal - SwapFree`; pages may remain swapped out after pressure ends. It is diagnostic context only.
- **Hysteresis:** Requiring three consecutive samples in a new severity band before publishing a transition. The accepted reasons and severity transition atomically.
- **Measuring:** Initial state before enough valid samples exist to calculate deltas and accept a health assessment. Measuring is neutral, not healthy or failed.
- **Optional service:** A feature such as TLDR or an unconfigured webhook relay whose absence is expected. `not_configured` is neutral and distinct from `stopped`, `degraded`, and `unavailable`.
- **Orphaned advancing session:** A live review/test/ship session classified as reclaimable by the canonical advancing-session lifecycle logic. A terminal-verdict warm session is not orphaned.
- **PSI:** Linux Pressure Stall Information from `/proc/pressure/*`; it measures time tasks are stalled by resource pressure.
- **Structured reason:** A stable code plus severity, domain, message, and metric metadata. React never parses English reason strings to decide which metric to display.
- **Warm session:** An intentionally retained review/test/ship session with a durable terminal verdict, kept for fast reuse. It is idle capacity and the memory governor may shed it under hard pressure.
- **No-loss audit:** A focused inventory test proving every old route field, metric, status, event, guardrail, cleanup action, and UI affordance is preserved, deliberately renamed, or explicitly retired.

## Problem

Overdeck currently has multiple incompatible health models. The header pill uses `SystemHealthSnapshot`; the Health page independently scans agent directories; the Resources view builds a second host-vitals snapshot; the spawn gate derives another state from the system snapshot; and the memory governor owns separate hysteresis and reserve thresholds. The models disagree about what is healthy, what is current pressure, and which agents are active.

The first-user failure is reproducible. On the reviewed Linux host, `/proc/meminfo` reported about 41 GiB available on a 62 GiB machine while 49.9% of configured swap remained occupied. `evaluateSeverity()` marks 20% swap warning and 50% critical (`src/dashboard/server/services/system-health-service.ts:472-475`), even though occupancy alone does not show current pressure. The same service divides `Committed_AS` by physical RAM at line 648 and labels it overcommit pressure, although Linux safely permits virtual commitment above RAM.

The agent surface has an independent false-positive path. `determineHealthStatus()` reads runtime timestamps but not runtime state, then marks every live session inactive for 30 minutes `stuck` (`src/dashboard/lib/health-filtering.ts:115-123`). This treats intentional idle, suspended, waiting-on-human, and warm advancing sessions as unhealthy. It also returns `wedged` at lines 97-102, while `AgentHealth` omits that value (`src/dashboard/frontend/src/types.ts:172-180`) and `HealthDashboard` has no rendering configuration (`src/dashboard/frontend/src/components/HealthDashboard.tsx:32-38`), so a valid response can crash the page.

The result is worse than noisy telemetry: operators learn to ignore red, first-time users believe a healthy machine is failing, and stale/error agent counts can force unnecessary spawn acknowledgements or block work.

## Goals

1. Make health trustworthy on Linux and macOS by separating current pressure, admission headroom, agent runtime, and optional services.
2. Publish one accepted, runtime-validated snapshot consumed consistently by the header, Health page, Resources view, spawn gate, and health events.
3. Make cold start neutral and honest: measuring or unavailable data never masquerades as healthy zeroes or critical failure.
4. Make agent health lifecycle-aware and align capacity counts with agents that are actually admitted/live.
5. Preserve every useful existing metric and cleanup affordance through an explicit no-loss audit.
6. Cover the original first-run, swap, warm-idle, wedged, unavailable, and narrow-viewport failures with focused tests.

## Non-goals

- Redesign the entire Resources page or Command Deck.
- Change the memory governor's configured soft/hard/recovery reserves or its shedding policy.
- Add destructive automatic cleanup from the health UI.
- Promise Windows-native support; unsupported platforms return explicit unavailable signals instead of attempting Linux `/proc` reads.
- Treat cost, disk capacity, Docker stack health, model-provider health, or tracker availability as host memory pressure.
- Remove `pan doctor`; this issue documents how diagnostic checks differ from live dashboard health.
- Restart or hot-patch the live dashboard during implementation. Server changes receive a throwaway Node 22 boot test first.

## Product and architecture decisions

### 1. One snapshot, distinct domains

Add a runtime-validated `SystemHealthSnapshot` contract under `packages/contracts/src/system-health.ts`. It is the one read shape for dashboard health. It contains separate `host`, `admission`, `agents`, and `services` domains plus diagnostic metrics and top consumers.

The overall state is derived only for the compact header:

1. `unavailable` if the snapshot cannot be produced.
2. `measuring` while host deltas/hysteresis are warming.
3. `critical` if host current pressure is critical or a required core service is down.
4. `warning` if host current pressure is elevated or a required domain is degraded.
5. `healthy` otherwise.

Admission `soft` or `blocked` is shown separately as capacity/headroom. It does not turn a healthy host red. The spawn gate continues to enforce admission decisions.

### 2. Host signals

Use these platform adapters behind one collector interface:

```ts
interface HostHealthCollector {
  readonly platform: 'linux' | 'darwin' | 'unsupported'
  sample(previous?: HostMetricSample): Promise<HostMetricSample>
}
```

Linux:

- RAM: `/proc/meminfo` `MemAvailable` and total.
- CPU utilization: delta of aggregate `/proc/stat` counters.
- Current memory pressure: `/proc/pressure/memory` `some.avg10` and `full.avg10` when present.
- Swap activity: delta/time of `/proc/vmstat` `pswpin` + `pswpout`; occupancy remains diagnostic.
- Load averages remain diagnostic and never masquerade as CPU percent.
- `Committed_AS` and `CommitLimit` remain diagnostic fields but never independently alter severity or admission.

macOS:

- RAM/current pressure: parse `memory_pressure -Q`; retain `vm_stat` totals as diagnostics/fallback.
- CPU utilization: use deltas from `os.cpus()[].times`, the same counter method as Linux, not load average.
- Swap activity: use deltas of `Swapins`/`Swapouts` from `vm_stat` when available; `vm.swapusage` remains occupancy only.
- If `memory_pressure -Q` or a delta signal is unavailable, mark that signal unavailable and fall back to available-memory admission only. Do not substitute zero.

Default current-pressure bands:

- Linux `warning`: `memory.some.avg10 >= 5` or swap activity >= 64 MiB/min for three consecutive samples while `MemAvailable` is below the configured warning reserve.
- Linux `critical`: `memory.full.avg10 >= 1` or swap activity >= 256 MiB/min for three consecutive samples while `MemAvailable` is below the configured critical reserve.
- macOS `warning`: `memory_pressure -Q` free percentage <= 10% for three consecutive samples.
- macOS `critical`: free percentage <= 5% for three consecutive samples.
- Available-memory reserve crossings always control the `admission` domain. They affect overall host health only when corroborated by a current-pressure signal; on a platform without a current-pressure signal, report `host: unavailable` and the admission band honestly.

All defaults are named constants in the platform collector module. Environment overrides, if retained, are parsed through one finite-number validator and surfaced in the snapshot. Invalid values log once and use defaults.

### 3. Sampling and hysteresis

On first request, return a valid `measuring` snapshot and start a singleton sampler. Take three warm-up samples one second apart, then use the configured poll interval. While the snapshot is measuring, React refetches every second; afterward it uses the snapshot's `nextPollMs`.

The pure transition function receives a complete raw assessment and returns a complete accepted assessment. Severity, structured reasons, and the accepted metrics change together. Three consecutive samples are required for escalation and recovery. Missing/invalid samples do not count and cannot clear a previous accepted state.

All sampler/backoff/delay tests must use `vi.useFakeTimers()` and `vi.advanceTimersByTimeAsync()`; real waits are forbidden.

### 4. Agent health and capacity

Retire the direct directory scan in `/api/health/agents`. Build agent health from the canonical agent resolver plus canonical runtime state and one live tmux-session set.

Classification order:

1. Persisted corrupt/unreadable through the resolver: `unavailable` with structured reason.
2. Context saturated: `wedged`.
3. Running/starting state without tmux after the existing five-minute startup grace: `dead`.
4. Work agent with `kickoffDelivered === false` past grace: `stalled`.
5. Runtime `waiting-on-human`: `waiting` regardless of inactivity.
6. Runtime `idle` or `suspended`, including terminal-verdict advancing sessions: `idle`; add lifecycle `warm` when the canonical review-status classifier says warm.
7. Runtime `active`: `warning` after 15 minutes without effective activity and `stalled` after 30 minutes.
8. Otherwise: `healthy` while live, or `idle` when persisted but intentionally inactive.

Expose the actual `lastActivityAt`; remove fabricated `lastPing`. Preserve `consecutiveFailures`, `killCount`, and `contextPercent`, including `0`.

`admittedWorkAgentCount` includes only:

- role `work` with a live tmux session; or
- role `work`, status `starting`, started less than five minutes ago.

It excludes `error`, dead/stale starting, stopped, warm advancing, plan, conversation, and specialist roles. The spawn gate uses this field; no UI-derived count controls admission.

### 5. Specialist lifecycle

Replace dead `leakedSpecialists` derivation with lifecycle annotations sourced from canonical agent + review status:

- `active`
- `warm`
- `orphaned`
- `unknown`

Reuse the canonical warm/orphan classifiers used by advancing-session lifecycle code. Do not introduce a second definition. Top-consumer Kill/Remove actions remain available with confirmation. The special leaked-only filter becomes **Reclaimable sessions** and includes only canonically orphaned sessions; warm sessions are labeled **Warm · reusable** and are never described as leaks.

### 6. Backward compatibility

The contract adds structured domains while retaining the existing `summary`, raw diagnostic metrics, `topConsumers`, and routes for one compatibility cycle. Deprecated `swapUsedWarningPercent`, `swapUsedCriticalPercent`, and overcommit thresholds may remain readable but do not affect severity. Add comments and tests pinning this behavior.

`GET /api/system/health`, `GET /api/godview/system-health`, `GET /api/health/agents`, Resources host vitals, spawn gate, and `system.health_severity_changed` remain available. They delegate to the canonical snapshot/projectors rather than collecting independently.

## Requirements

### Functional requirements

- **FR-1:** Define a runtime-validated shared system-health contract with overall state `measuring | healthy | warning | critical | unavailable` and separate host, admission, agent, and service domains.
- **FR-2:** Collect Linux current pressure from MemAvailable, PSI, CPU deltas, and swap-activity deltas; keep load, swap occupancy, and commitment as diagnostics.
- **FR-3:** Collect macOS current pressure from `memory_pressure -Q`, `vm_stat`, real CPU-time deltas, and swap deltas; unavailable signals remain explicitly unavailable.
- **FR-4:** Unsupported platforms return a valid unavailable host domain and continue rendering other domains.
- **FR-5:** Historical swap occupancy and committed virtual memory never independently produce warning/critical severity or spawn blocking.
- **FR-6:** Cold start returns measuring until three valid samples exist. Hysteresis accepts severity, reasons, and metrics atomically after three consecutive samples in the new band.
- **FR-7:** Read all resource settings through the canonical resolved YAML configuration loader. Invalid or reversed thresholds normalize once and are surfaced; no raw regex parsing of `config.yaml` remains.
- **FR-8:** Admission headroom preserves configured memory and agent ceilings but is presented separately from host current pressure.
- **FR-9:** Agent health is built through the canonical resolver and distinguishes healthy, idle, waiting, warning, stalled, wedged, dead, and unavailable.
- **FR-10:** Intentional idle, suspended, waiting-on-human, and warm sessions are never classified as stuck/stalled from inactivity alone.
- **FR-11:** Only live work agents plus fresh starting work agents count toward admission capacity.
- **FR-12:** Replace fabricated `lastPing` with actual `lastActivityAt`; preserve a valid context percentage of zero.
- **FR-13:** Route/read failures return explicit unavailable data and an appropriate non-2xx response where the entire request failed; they never become HTTP 200 empty healthy results.
- **FR-14:** Replace dead leaked-specialist detection with canonical active/warm/orphaned lifecycle annotations and preserve confirmed cleanup actions.
- **FR-15:** The header pill, Health page, Resources host vitals, God View, spawn gate, and health transition events project from the same accepted snapshot.
- **FR-16:** React selects labels by stable structured reason codes, never by matching English reason text.
- **FR-17:** Every server agent status has an exhaustive frontend renderer and runtime contract; unknown future values render unavailable instead of throwing.
- **FR-18:** The Health page renders host and service domains when there are zero agents and distinguishes optional not-configured services from failures.
- **FR-19:** Normal health uses a neutral/positive icon; measuring, warning, critical, unavailable, and optional states have distinct text and icon semantics.
- **FR-20:** The system-health popover supports Escape/outside dismissal, focus restoration, `aria-expanded`/`aria-controls`, accessible names, reduced motion, and narrow viewport containment.
- **FR-21:** Existing routes, metrics, status counts, event history, top consumers, and Kill/Remove actions pass the no-loss audit.
- **FR-22:** First-run, healthy-with-swap, actual pressure, recovery, warm-idle, waiting, wedged, unavailable, zero-agent, optional-service, and narrow-viewport scenarios have automated coverage.

### Non-functional requirements

- **NFR-1:** Dashboard-server code uses async filesystem/process primitives only. Do not introduce `execSync`, `spawnSync`, or synchronous tmux calls.
- **NFR-2:** Delay and hysteresis tests use Vitest fake timers; no real sleep/backoff occurs in the default suite.
- **NFR-3:** Each canonical domain has one read door and one write/event door. Routes and React do not access stores, state files, `/proc`, or config directly.
- **NFR-4:** Sampling is single-flight and bounded. One browser with multiple consumers cannot start duplicate collectors or subprocesses.
- **NFR-5:** Process-tree attribution is no worse than `O(processes + descendants)` per refresh; build a parent-to-children index once rather than scanning the process table for every descendant.
- **NFR-6:** Snapshot serialization is backward-compatible for one cycle and validated before crossing HTTP/WebSocket boundaries.
- **NFR-7:** UI meets WCAG 2.1 AA, never relies on color alone, and honors `prefers-reduced-motion`.
- **NFR-8:** Dashboard boot-path changes are built and booted under Node 22 in a throwaway instance before any live restart.
- **NFR-9:** Logs contain stable reason codes and transition summaries but never dump environment values or unrelated process command lines.
- **NFR-10:** No destructive cleanup is automatic. Existing Kill/Remove actions retain confirmation.

## Shared contract

Add `packages/contracts/src/system-health.ts` and export it from `packages/contracts/src/index.ts`:

```ts
export const HealthState = Schema.Literal(
  'measuring', 'healthy', 'warning', 'critical', 'unavailable',
)

export const HealthReason = Schema.Struct({
  code: Schema.String,
  domain: Schema.Literal('host', 'admission', 'agent', 'service'),
  severity: Schema.Literal('info', 'warning', 'critical'),
  message: Schema.String,
  metric: Schema.optional(Schema.String),
  observed: Schema.optional(Schema.Number),
  threshold: Schema.optional(Schema.Number),
})

export const SystemHealthSnapshot = Schema.Struct({
  version: Schema.Literal(2),
  state: HealthState,
  updatedAt: Schema.String,
  nextPollMs: Schema.Number,
  host: Schema.Struct({
    state: HealthState,
    platform: Schema.Literal('linux', 'darwin', 'unsupported'),
    reasons: Schema.Array(HealthReason),
    metrics: HostHealthMetrics,
  }),
  admission: Schema.Struct({
    state: Schema.Literal('open', 'soft', 'blocked', 'unavailable'),
    availableMemoryBytes: Schema.Number,
    admittedWorkAgentCount: Schema.Number,
    reasons: Schema.Array(HealthReason),
  }),
  agents: Schema.Array(AgentHealthSnapshot),
  services: Schema.Array(ServiceHealthSnapshot),
  topConsumers: Schema.Array(SystemHealthConsumer),
  // Compatibility projection retained for one release cycle.
  summary: LegacySystemHealthSummary,
})
```

Use schema decoding at the route boundary and `Schema.decodeUnknown` in the frontend fetcher. Do not maintain a hand-written duplicate in `src/dashboard/frontend/src/types.ts`.

## Before/after behavior

### Host evaluation

Before (`evaluateSeverity`, search `Swap usage is high`):

```ts
if (data.swapUsedPercent >= thresholds.swapUsedCriticalPercent) {
  criticalReasons.push(`Swap usage is high (${data.swapUsedPercent}%).`)
}
```

After:

```ts
const raw = evaluateHostPressure(sample, resolvedThresholds)
const accepted = transitionAcceptedAssessment(previous, raw)

// swapUsedBytes is still displayed, but only swap activity + corroborating
// pressure can contribute a structured reason.
```

### Hysteresis

Before:

```ts
return {
  severity: effectiveSeverity,
  reasons: evaluation.reasons, // can describe a different severity
}
```

After:

```ts
return {
  state: accepted.state,
  reasons: accepted.reasons,
  metrics: accepted.metrics,
  acceptedAt: accepted.acceptedAt,
}
```

### Agent health

Before (`health-filtering.ts`):

```ts
if (ageMinutes > 30) return { status: 'stuck' }
```

After:

```ts
switch (runtime.state) {
  case 'waiting-on-human': return waitingSnapshot(agent, runtime)
  case 'idle':
  case 'suspended': return idleSnapshot(agent, runtime, lifecycle)
  case 'active': return classifyActiveProgress(agent, runtime, now)
  default: return classifyLiveness(agent, runtime, sessions, now)
}
```

### UI copy

Use domain-specific copy:

- Healthy: **Healthy · 41 GB available**
- Measuring: **Measuring system health…**
- Admission soft with healthy host: **Healthy · spawn headroom tight**
- Optional TLDR absent: **TLDR · Not configured (optional)**
- Warm reviewer: **Idle · Warm for reuse**
- Unavailable: **Health unavailable · Retry**

Never show `normal` with an alert icon or call historical swap occupancy “high pressure.”

## Risks and mitigations

- **Risk:** PSI is absent in some kernels/containers. **Mitigation:** per-signal unavailable state and admission-only fallback.
- **Risk:** macOS command output varies. **Mitigation:** verified fixtures and fail-closed parsing to unavailable, not fabricated zero.
- **Risk:** Three-sample warm-up feels slow. **Mitigation:** one-second warm-up sampling and explicit measuring UI.
- **Risk:** Changing health affects spawn admission. **Mitigation:** separate host and admission domains, preserve reserve predicate tests, and use admitted work-agent count only.
- **Risk:** Warm sessions are misidentified as leaks. **Mitigation:** canonical lifecycle classifier and explicit warm/orphan tests.
- **Risk:** Existing consumers depend on legacy fields. **Mitigation:** compatibility projector plus no-loss matrix for one release cycle.
- **Risk:** Collector subprocesses increase server load. **Mitigation:** singleton sampler, single-flight reads, bounded timeouts, async primitives, and cached accepted snapshots.
