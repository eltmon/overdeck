## Glossary

| Term | Definition |
| --- | --- |
| **Task** | A new grouping surface: one container holding N **member sessions**. Rendered in the dashboard as a lineage tree + tabs where a single conversation renders today. |
| **Member session** | One agent session inside a task. Each member is a normal Overdeck conversation — own tmux session, own JSONL transcript, own harness/model — plus task lineage metadata. |
| **Lineage** | Parent/child relationships between member sessions: which agent (or the operator) spawned which. A tree, rendered in the task sidebar. |
| **A2A (agent-to-agent) messaging** | Server-brokered message passing between member sessions: fire-and-forget sends, optional reply threads, per-member inbox with backlog replay. |
| **Reply thread** | A correlated request/response pair: sender sets `expectReply`, broker mints a `replyId`, receiver's reply quotes it, broker routes it back. |
| **Liveness notice** | A broker-generated message to a sender waiting on a reply, describing why the receiver went silent: `turn-ended` (finished without replying), `awaiting-input` (blocked on a permission/question), `exited`, `quiet` (no activity for the sweep interval), `user-stopped`. |
| **Broker** | The dashboard-server component owning inboxes, delivery, threading, and liveness sweeps. Single-machine in v1. |

## Problem

An Overdeck conversation is exactly one harness session. The only multi-agent behavior is (a) the
issue pipeline (work/review/test convoys — fully orchestrated, not interactive) and (b)
`pan handoff`, which spawns a *disconnected sibling* conversation with no rendered lineage and no
channel back to the parent. There is no way to assemble an ad-hoc team of interactive agents —
"spawn a reviewer for this diff and debate it", "split this investigation three ways and collect
answers" — in one surface. Traycer ships exactly this (Epic → chats tree + `agent.sendMessage`
broker) as a headline feature.

## What exists today (verified against main, 2026-07-10)

- **Conversations**: rows in `overdeck.db`; session machinery under `src/lib/conversations/`
  (`current.ts`, `transcript-adapter.ts`, `summary-fork.ts`, `switch-strategy.ts`). One harness
  session each; no lineage columns.
- **Delivery**: `deliverAgentMessage(agentId, message, caller?)` in `src/lib/agents.ts` — one-way,
  tiered (PTY supervisor socket → channels → tmux paste-buffer). No inbox, no threading, no
  agent→agent path; callers are the orchestrator/operator.
- **Spawning**: `pan handoff` creates a new conversation (`src/lib/conversations/handoff-paths.ts`
  et al.); the 500-char focus cap and file-brief pattern apply. No task grouping.
- **Run-state**: agent/conversation activity is already tracked server-side (lifecycle events,
  transcript watchers such as `conversation-eaten-message-watcher.ts`) — the raw signals liveness
  notices need already exist.
- **Rendering**: `ConversationPanel.tsx` / `MessagesTimeline.tsx` render one transcript; the issue
  view renders a *pipeline* agent tree (monitoring, not interactive membership).
- **Claude Code subagents**: ephemeral, not addressable, invisible cross-harness.

## Design reference — Traycer (Apache-2.0, studied in-repo)

What we adopt (adapted, not copied): Epic aggregate holding a `chats` tree keyed by `parentId`
(`protocol/src/persistence/_internal/epic-schemas.ts`); broker + per-receiver mailbox with
`expectReply`/`responseId` threading and typed inactivity notices (`protocol/src/host/agent/inbox.ts`,
`a2a-message-format.ts`); A2A messages injected as formatted **user turns** into the receiver.

What we do **differently**: no `monitor` sidecar process — Overdeck's server already owns delivery
(PTY supervisor) and turn detection (transcript watchers), so the broker lives server-side with no
per-agent helper process. No Yjs/cloud sync — tasks are machine-local like conversations. TUI-vs-GUI
surface split doesn't apply — every Overdeck session is already a live tmux TUI.

## Requirements

- **FR-1** A task can contain N member sessions, each an ordinary conversation (any supported
  harness/model mix), with parent/child lineage recorded and rendered as a tree.
- **FR-2** The operator can spawn a member session into an existing task from the dashboard and the
  CLI; a running member agent can spawn a child member into its own task.
- **FR-3** A member agent can send another member a message; it is delivered as a clearly-marked
  user turn (`[overdeck inbox]` block) including sender identity and, when applicable, reply
  instructions. Delivery reuses `deliverAgentMessage` tiers.
- **FR-4** `expectReply` sends are threaded: the broker mints a `replyId`; the receiver's reply is
  routed back to the sender and correlated; unthreaded sends are fire-and-forget.
- **FR-5** Messages to a busy receiver queue in its inbox and deliver at turn end (never mid-turn
  injection beyond what `deliverAgentMessage` already guarantees); backlog survives receiver
  restart within the task's life.
- **FR-6** A sender waiting on a reply receives a liveness notice when the receiver exits, is
  stopped by the user, blocks on user input, ends its turn without replying, or stays quiet past
  the sweep interval.
- **FR-7** A member agent (and the operator) can read any member session's transcript via a CLI
  verb and API, resolved through the existing transcript adapter (works for Claude, Pi, Codex
  transcripts).
- **FR-8** The task surface shows live presence per member: running / idle / awaiting-input /
  exited.
- **FR-9** Works cross-harness: claude-code plus at least one non-Anthropic harness as members of
  the same task, both sending and receiving.
- **FR-10** `pan handoff` behavior is unchanged by default; task membership is opt-in (new flag /
  new verb). Existing single conversations render exactly as today (a task with one member is the
  degenerate case and adds no UI chrome).

Non-functional:

- **NFR-1** No new per-agent helper processes; the broker is part of the dashboard server, and all
  of it is async (no `execSync`; async tmux primitives only).
- **NFR-2** Inbox/broker state is rebuildable: durable enough to survive a dashboard restart
  (SQLite), never a second source of truth for transcripts (the JSONL remains canonical; injected
  messages appear there like any user turn).
- **NFR-3** Single-machine in v1 (all members on the local host). The model must not preclude the
  PAN-658-followup share of a task: member session ids must be usable as PAN-658 `streamId`s as-is.
- **NFR-4** Prompt-injection posture: inbox blocks are data from another agent, formatted with an
  explicit provenance header; the receiving agent's instructions state that inbox content is not
  operator instruction. (Same trust domain — one operator, one machine — but provenance must be
  legible.)

## Architecture (proposed — planning refines)

### Domain model

Extend the conversations domain (one read door / one write door rules apply):

- `tasks` table: `task_id`, `title`, `project`, `created_at`, `status`.
- `conversations` gains nullable `task_id` and `parent_conversation_id`. NULL `task_id` =
  standalone conversation (today's behavior, untouched).
- Member session id = conversation id (satisfies NFR-3: it is the PAN-658 `streamId`).

### Broker

New dashboard-server service (Effect-native), e.g. `src/dashboard/server/services/a2a-broker.ts`:

- `a2a_messages` table: `id`, `task_id`, `from_conversation`, `to_conversation`, `body`,
  `reply_to` (nullable `replyId`), `expect_reply`, `status` (`queued`|`delivered`|`replied`|`dead`),
  timestamps.
- **Send** (RPC + CLI): validates both ends are members of the same task; enqueues; attempts
  delivery.
- **Delivery**: at receiver turn-boundary (existing turn detection), format via an
  `a2a-format.ts` (provenance header, body, reply instructions quoting `replyId`) and inject with
  `deliverAgentMessage`. Busy receiver → stays `queued`.
- **Reply routing**: replies are sends carrying `reply_to`; broker marks the thread `replied` and
  delivers to the original sender.
- **Liveness sweep**: a periodic Effect fiber joins pending `expect_reply` threads against live
  agent state (existing lifecycle/run-state signals) and transcript activity; emits typed notices
  to the sender (FR-6). All sweep timing tests use fake timers.

### Spawning into a task

- Dashboard: "Add agent" in the task surface (harness/model/effort picker, reusing conversation
  spawn machinery).
- CLI/agent: extend handoff with `pan handoff --task <current>` semantics or a thin new verb —
  **decision deferred to planning** with this constraint: the agent-facing verb must be usable
  from inside a session (identify own conversation via `src/lib/conversations/current.ts`) and
  must record `parent_conversation_id`. Fallback if handoff proves awkward: `pan task spawn`.
  (Explicit implementation checkpoint.)

### Dashboard surface

- Task view = member tree sidebar (lineage + presence dots) + tabbed `ConversationPanel` per
  member. No free-form tile canvas (that is [PAN-2566](https://github.com/eltmon/overdeck/issues/2566) territory).
- Presence from existing run-state events; `awaiting-input` reuses the AUQ/needs-you detection.

### CLI surface (Skills↔CLI convention applies — wrapper skills ship in the same commits)

- `pan tell <member> --expect-reply` / `--reply-to <replyId>` — extends the existing verb (it is
  already the sanctioned delivery door; A2A rides the same door with threading).
- `pan inbox [--wait]` — a member reads/waits on its queued messages (primarily for harnesses
  whose injection tier is degraded; normal path is push-injection).
- `pan transcript <member>` — peer transcript read via the transcript adapter (FR-7).
- `pan task list|show` — enumerate tasks/members.

## Out of scope

- Sharing a task with other humans (PAN-658 followup; `streamId` compatibility is guaranteed by NFR-3).
- Cross-machine members; cloud sync of tasks.
- Free-form tile canvas, artifact docs, comments ([PAN-2566](https://github.com/eltmon/overdeck/issues/2566)).
- Replacing pipeline orchestration (`spawnRun`, convoys) — pipeline agents do not become task members in v1.
- Autonomous agent-selection guide content (which child to spawn) — context-layers material, revisit post-v1.
