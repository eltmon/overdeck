# PAN-3049: Duplicate Docker stacks per workspace (myn-feature-* beside overdeck-feature-*) — single compose-project-name resolver

## Glossary

- **Compose project name** — the `docker compose -p <name>` project identifier. It prefixes every container (`<name>-<service>-1`) and derives the stack's bridge network (`<name>_devnet`). Two different names over the same compose file = two complete stacks.
- **Declared name** — the name a workspace asks for, either via `COMPOSE_PROJECT_NAME="…"` in its `.devcontainer/dev` script or the top-level `name:` field of its rendered compose file. MYN workspaces declare `myn-feature-<issue>`; Overdeck workspaces declare `overdeck-feature-<issue>` (dev script only — the Overdeck compose template has no `name:` field).
- **Canonical resolver** — `composeProjectNameForWorkspace(workspacePath, issueId)` in `src/lib/workspace/stack-health.ts:38`. The single function every Overdeck code path must use to learn a workspace's compose project name.
- **Fallback name** — `overdeck-feature-<issue>`, returned by the resolver when no declared name is found. Before this change, the fallback was silent; that is the bug's enabler.
- **Strict resolver** — new variant introduced by this plan: fails loudly when a compose file exists but no declared name can be resolved, instead of silently guessing the fallback.
- **Pipeline producer** — an Overdeck code path that runs `docker compose up` for a workspace (spawn-time rebuild, workspace create, containerize, UAT).
- **Workspace producer** — the workspace's own `dev` script, run by the agent inside the workspace, which exports its declared `COMPOSE_PROJECT_NAME`.

## Problem

MYN workspaces ran two complete stacks at once — one under the declared `myn-feature-<issue>` project and one under the fallback `overdeck-feature-<issue>` — doubling a ~2 GB stack to ~4 GB per workspace and exhausting the host (MemAvailable 3.1 GB, swap 8191/8191, load 235). Container labels proved both halves are the same compose file brought up twice, differing only in `-p`.

Root cause, verified in code during planning:

1. **Three independent derivations of one name.** `composeProjectNameForWorkspace` (`src/lib/workspace/stack-health.ts:38-57`) prefers the declared name and silently falls back to `overdeck-feature-<issue>`. `stopWorkspaceDockerPromise` (`src/lib/workspace-manager/docker.ts:71-91`) re-implements the same parse but hardcodes `overdeck-` and *throws* when the dev script declares anything else.
2. **The pipeline producer resolves the name before the declaration exists.** `rebuildWorkspaceStack` (`src/lib/workspace/rebuild-stack.ts:187`) resolves the compose project name *before* `ensureDevcontainerSync` (re)renders `.devcontainer/` (line 203). On a workspace whose `.devcontainer/dev` is absent at that moment, the resolver takes the silent fallback and `docker compose -p overdeck-feature-<issue> up` (line 225) **overrides the compose file's `name: myn-…`**. This path is invoked at agent spawn (`src/lib/agents/spawn-prep.ts:818`, via the unhealthy-stack gate), from `deacon-review-status.ts:170`, and from `verification-runner.ts:634`. Minutes later the agent's own `dev` script brings the stack up under the declared `myn-` name — the duplicate. This matches the incident's creation-order evidence exactly (`overdeck-` stack first, `myn-` stack minutes later, MIN-898 observed transitioning).
3. **Cleanup machinery only reaps one naming scheme.** Hardcoded `overdeck-feature-` filters blind the reapers to `myn-` stacks: `src/lib/cloister/idle-stack-reaper.ts:53` (`UI_CONTAINER_RE`), `src/lib/cloister/deacon.ts:2317` and `:2336` (crashed-container sweep), `src/lib/close-out.ts:377` (warning names only `overdeck-feature-<issue>_devnet`), `src/cli/commands/workspace-reap.ts:12` (`WORKSPACE_PROJECT_PREFIX`). Exited `myn-feature-*` corpses sat unreaped for 2–3 days on the host.

## Proposal

One resolver, strict at bring-up, prefix-agnostic everywhere:

1. Extend the canonical resolver to also read the top-level `name:` field of the rendered devcontainer compose file, and add a strict variant that throws when a compose file exists but no declared name resolves. The lenient variant keeps the `overdeck-` fallback only when the workspace has no compose file at all (non-docker workspaces — callers gate on `stackExpected`/`hasDockerWorkspace` separately).
2. `rebuildWorkspaceStack` resolves the name **after** rendering `.devcontainer/`, via the strict resolver, and brings the stack up under the declared name. When the pre-render best-effort name differs from the post-render name, it tears down under both names so a fallback-named stack cannot leak.
3. `stopWorkspaceDockerPromise` routes through the canonical resolver and drops its hardcoded name and its throw-on-mismatch (the throw currently makes MYN teardown fail outright).
4. Every consumer that filters containers/networks by the literal `overdeck-feature-` becomes prefix-agnostic (deacon crash sweep, idle-stack-reaper UI regex, close-out warning, workspace-reap).
5. Add `name: overdeck-{{FEATURE_FOLDER}}` to the Overdeck compose template so Overdeck workspaces are self-describing the way MYN's already are.
6. Add a read-only `pan doctor` check that reports any issue with two or more distinct live compose projects, labels canonical vs. foreign, and prints safe remediation guidance. Reconciliation of existing duplicates (issue ask #3) remains an operator action — code never stops a running foreign stack (the MIN-891 lesson: a foreign-named stack may be the workspace's *only* stack, serving a live agent).

## Decisions

- **D1 — The compose file's `name:` field joins the dev script as a declaration source.** MYN's template already declares `name: myn-{{FEATURE_FOLDER}}`; Overdeck's does not. Reading both sources makes the resolver correct even when the dev script is missing, and item 9 makes the Overdeck template self-describing. Precedence: dev-script declaration first (existing behavior), then compose `name:`, then (lenient only) fallback.
- **D2 — Strictness applies to bring-up paths, leniency to read-only paths.** Health checks and name-token matching must keep working for non-docker workspaces and half-provisioned ones, so the throwing variant is opt-in and used only where a wrong name creates a stack (`rebuildWorkspaceStack`, future producers).
- **D3 — The crash sweep and UI-idle regex keep their existing service sets.** Only the prefix anchor is removed. Extending crash-restart or idle-reap coverage to MYN's service names (`api`, `dev`, `postgres`, `redis`) changes reaping behavior for another project and is deliberately out of scope.
- **D4 — No automated killing of foreign stacks.** `removeStaleIssueContainers` (`rebuild-stack.ts:103-121`) already removes *non-running* foreign corpses after a rebuild; that is preserved. Running foreign stacks are surfaced (doctor check, existing activity logs), never stopped by code.
- **D5 — `teardownWorkspaceDockerByNamePromise` (`docker.ts:156-308`) is already correct** (discovers project names from live networks/containers, prefix-agnostic) and is the model for the other consumers; it is not modified except for the small `remainingNetworks` addition the close-out warning needs.

## Requirements

- **FR-1** — `composeProjectNameForWorkspace` resolves the declared name from (a) the dev script, then (b) the devcontainer compose file's top-level `name:` field, validating that the result ends with `feature-<issue>` exactly as the dev-script path does today.
- **FR-2** — A strict variant `requireComposeProjectNameForWorkspace` throws a descriptive error when a devcontainer compose file exists but no declared name resolves; it never silently returns the fallback in that case.
- **FR-3** — `rebuildWorkspaceStack` resolves the compose project name after `ensureDevcontainerSync` renders `.devcontainer/`, using the strict resolver, and runs `up -p` with that name. If the pre-render best-effort name differs, the stack is torn down under both names.
- **FR-4** — `stopWorkspaceDockerPromise` uses the canonical resolver (lenient — teardown must proceed for odd states) and no longer throws when the dev script declares a non-`overdeck-` name.
- **FR-5** — The deacon crashed-container sweep (`deacon.ts:2317`, `:2336`) enumerates and parses containers of any compose-project prefix, keeping the existing `(frontend|server)` service set and exit-code-0 skip.
- **FR-6** — `UI_CONTAINER_RE` in `idle-stack-reaper.ts:53` matches any project prefix, keeping the `(server|frontend)` service set.
- **FR-7** — The close-out warning enumerates the actual remaining `*-feature-<issue>_devnet` networks instead of naming `overdeck-feature-<issue>_devnet`.
- **FR-8** — `pan workspace reap` discovers candidate projects of any prefix ending in `feature-<issue>`, not only `overdeck-feature-`.
- **FR-9** — `pan doctor` reports issues that have ≥2 distinct compose projects with at least one running container each, naming the canonical project (via the resolver) and the foreign one(s), with remediation guidance.
- **FR-10** — The Overdeck devcontainer compose template declares `name: overdeck-{{FEATURE_FOLDER}}`.
- **NFR-1** — After this lands, no `src/` file outside tests/docs may filter Docker containers or networks by the literal `overdeck-feature-` prefix; each consumer item carries a "no literal remains" acceptance criterion.
- **NFR-2** — No code path stops or removes a *running* container whose compose project is not the canonical one (existing `removeStaleIssueContainers` guarantee, preserved).
- **NFR-3** — Non-docker workspaces are unaffected: the lenient resolver still returns the fallback when no compose file exists, and bring-up paths that previously rendered-then-resolved continue to work.

## Acceptance criteria

1. Given a workspace whose dev script declares `COMPOSE_PROJECT_NAME="myn-${FEATURE_FOLDER}"`, when any Overdeck path brings its stack up, then the compose project is `myn-feature-<issue>` — never `overdeck-feature-<issue>` while a declaration exists and is readable.
2. Given a workspace with a compose file but no resolvable declared name, when a bring-up path resolves the project name, then it throws a descriptive error instead of starting a stack under a guessed name.
3. Given a stack exists under the fallback name and the workspace declares a different name, when `rebuildWorkspaceStack` runs, then the fallback-named stack is torn down and the new stack comes up under the declared name.
4. Given exited `myn-feature-*` containers, when the deacon crash sweep, idle-stack reaper, close-out, or workspace-reap enumerate containers/networks, then `myn-` projects are included exactly as `overdeck-` projects are.
5. Given two live compose projects for one issue, when `pan doctor` runs, then it reports the pair with canonical vs. foreign labeling and safe remediation guidance, and stops nothing itself.
6. `npm run typecheck`, `npm run lint`, and `npm test` pass with the new unit tests green.
