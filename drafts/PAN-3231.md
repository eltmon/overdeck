## Glossary

- **Chip strip / `ResourceStrip`** — the row of small resource indicators (`workspace` / `branch` / `tmux` / `xBRIEF` / `tasks` / `pr` / `docker`) rendered under each issue row in the project tree. Implemented as `ResourceStrip` in `src/dashboard/frontend/src/components/CommandDeck/ProjectTree/FeatureItem.tsx:133-268`. Chips are currently non-interactive `<span>`s (`ResourceIcon`, lines 113-131).
- **`vbrief` source token** — the legacy `ResourceSource` string for the xBRIEF chip. - **`XBriefViewer`** — presentational xBRIEF component with List / DAG / Raw JSON tabs (`src/dashboard/frontend/src/components/xbrief/XBriefViewer.tsx`). Does NOT fetch; the parent owns the query and passes `doc`.

## Problem

The chip strip advertises that artifacts exist (xBRIEF, tasks, PRD-adjacent planning output) but none of the chips open anything. Operators must navigate to kanban (xBRIEF button) or the drawer's Plan tab to see the plan, there is no tasks click-through at all from the tree, and the PRD has no affordance anywhere in the issue row.

## Current state (verified)

1. **Chips are display-only.** `ResourceIcon` (`FeatureItem.tsx:113-131`) renders `<span className={styles.featureResourceChip}>` — no `onClick`, no `role`, no `tabIndex`. The only interactive element in the strip is the orphan-cleanup button inside the hover popover.
2. **`XBriefDialog` exists but is not full-screen** and is reachable only from kanban cards. It owns its own query under yet another key (`['xbrief-plan', id]`).
3. **Query-key fragmentation:** four distinct React Query keys hit the same plan endpoint — `['workspace-plan', id]` (canonical hook `useWorkspacePlanQuery`, `CommandDeck/ZoneCOverviewTabs/queries.ts:163-178`), `['xbrief-plan', id]` (`XBriefDialog.tsx:17`), `['plan', id]` (`PlanMapViewer.tsx:70`, `TasksPanel.tsx:59`, `StatusNarrative.tsx:138`, `HappenedFeed.tsx:47`), `['drawer-xbrief-plan', id]` (`DrawerSecondaryPanels.tsx:19`).
4. **`XBriefViewer` DAG tab hardcodes `calc(100vh - 280px)`** (`XBriefViewer.tsx:88`) — sized for the current dialog chrome; wrong inside any other shell.
5. **The embedded viewer** is `DrawerPlanPanel` (console density, Plan tab): section id `DrawerPlanPanel / XBriefViewer` (`IssueDetail.tsx:363-364`, inventory `inventory.ts:42`, density `densitySections.ts:4`), component `drawer/DrawerSecondaryPanels.tsx:18-23` rendering `<XBriefViewer doc={…} initialTab="dag" />`. Cockpit has a DAG-only `PlanMapCard` (`Stage/cockpit/PlanMapCard.tsx:8-18`, section `PlanMapCard`).
6. **The beads viewer already survives as `TasksPanel`** with xBRIEF data. What's missing is only the chip → viewer wiring. Note: the older `components/TasksDialog.tsx` (self-fetching, used once from `CommandDeck/index.tsx:15` + `~1565`) still keys its status styles on the dead beads vocabulary (`open`/`in_progress`/`closed`, `TasksDialog.tsx:142-152`) while the endpoint serves xBRIEF statuses (`pending`/`running`/`completed`/…) — its status colors/icons silently miss for most items.
7. **PRD read path:** `GET /api/command-deck/planning/:issueId` (`command-deck.ts:703-717`, `fetchPlanningData` 719-897) serves the PRD but **falls back to continue.json content when no PRD exists** (`command-deck.ts:829`: `if (!result.prd && result.state) result.prd = result.state;`) and bundles transcripts/discussions/notes. There is no lightweight, honest PRD endpoint. `readPrdContent` (handles `flat`/`pan-draft`/`subdir` formats) is a local helper at `command-deck.ts:746-763`.
8. **Resource discovery has no canonical PRD signal.** `scanWorkspace` (`resource-discovery.ts:388-424`) sets `hasPrd` from the legacy workspace path `.pan/prd.md` (line 417) and that field never reaches `resourceDetails`/`resourceSources`; the frontend has no `prd` source.
9. **No markdown-file viewer dialog exists.** `MarkdownModal` (`CommandDeck/FeatureMetadata/MarkdownModal.tsx`) renders in-memory metadata with raw ReactMarkdown (no file links, no highlighting); `MarkdownFileLink` opens files in an external editor.

## Requirements

- **FR-1** Clicking the xBRIEF chip in the issue row opens a **full-screen** xBRIEF viewer that preserves the List / DAG / Raw JSON toggle.
- **FR-2** The embedded xBRIEF surfaces — `DrawerPlanPanel` (console Plan tab) and cockpit `PlanMapCard` — carry an expand affordance that opens the same full-screen viewer.
- **FR-3** Clicking the tasks chip opens the tasks viewer (resurrected beads-panel UX = `TasksPanel`) showing xBRIEF items/sub-items with their merged statuses.
- **FR-4** A PRD affordance renders in the chip strip (sibling of xBRIEF/tasks chips) when a PRD draft exists, and clicking it opens the PRD in a markdown viewer built on `ChatMarkdown`.
- **FR-5** Before the full-screen xBRIEF viewer is built, creative interactive mockups (full-screen List view, full-screen DAG view, the toggle, status/checks/lane legibility) are produced per the style guide and **approved by the operator** via AskUserQuestion.
- **FR-6** A dedicated endpoint serves the PRD markdown through the drafts read door, with **no continue.json fallback** (404/`hasPrd:false` when absent).
- **FR-7** Resource discovery exposes canonical PRD-draft presence as a `prd` resource source + `hasPrd` detail (state-plane drafts, not the legacy workspace `.pan/prd.md`).
- **FR-8** All existing entry points keep working unchanged: kanban xBRIEF button, drawer Plan tab, cockpit PlanMapCard, CommandDeck tasks dialog (no-loss).
- **NFR-1** All reads go through existing doors: plan endpoint for xBRIEF/tasks, `prd-locations`/`drafts` read door for the PRD. No new direct store access (single-source-of-truth tenet).
- **NFR-2** Issue-view kit compliance: any new/moved section follows `docs/ISSUE-VIEW.md` (inventory + `DENSITY_SECTIONS` + real `data-section` marker) and the no-loss tests stay green.
- **NFR-3** Style-guide conformance for all new UI (DM Sans, `font-medium` max, one color signal per row, no pill badges).
- **NFR-4** New frontend code uses the canonical `useWorkspacePlanQuery` hook (`['workspace-plan', id]`); no fifth query key for the plan endpoint.
- **NFR-5** New overlays are accessible: `role="dialog"`, `aria-modal="true"`, Escape closes, scrim click closes, focus lands inside the dialog on open.

## Decisions

- **D1 — Full-screen shell is store-driven and globally mounted**, mirroring the `IssueDrawer` precedent: a `xbriefViewerIssueId: string | null` field + `openXbriefViewer(issueId)` / `closeXbriefViewer()` actions in the dashboard store (`src/dashboard/frontend/src/lib/store.ts`), host component mounted once in `App.tsx` next to `<IssueDrawer />` (`App.tsx:870`). Rationale: the two openers (tree chip, drawer Plan tab) live in different component trees; store-driven is the codebase's canonical mechanism. **No URL sync in this issue** (NonGoal).
- **D2 — Chips call store actions directly** (via `useDashboardStore`) instead of prop-drilling new callbacks through `CommandDeck/index.tsx → ProjectNode → FeatureItem → ResourceStrip`. `FeatureItem` already consumes the store (`openIssue`, line 1032). The existing `onOpenPlanDialog` prop is NOT reused — it opens the planning-terminal `PlanDialog`, a different feature.
- **D3 — Reuse `XBriefViewer` unchanged in API**; fix its DAG pane sizing from `calc(100vh - 280px)` to flex-fill (`flex-1 min-h-0`) so it fills whatever shell hosts it. Every existing mount gives the viewer a bounded flex column, so flex-fill is correct in all of them; each mount is verified by AC.
- **D4 — Tasks viewer = `TasksPanel` in a store-driven dialog.** New `openTasksViewer(issueId)` / `closeTasksViewer()` store actions + a dialog host mounted in `App.tsx`. The legacy self-fetching body of `components/TasksDialog.tsx` is replaced by `TasksPanel` (keeping the `{ issueId, isOpen, onClose }` contract for its one CommandDeck caller), which also fixes its dead beads status vocabulary. This is an upgrade-in-place, not a deletion — the dialog affordance and its caller survive (no-loss).
- **D5 — PRD endpoint is `GET /api/issues/:id/prd`**, implemented as `getIssuePrd` in `src/lib/overdeck/issue-reads.ts` (pattern: `getIssueTasks`), resolving via `findPrdAnywhereSync(projectPath, issueId)` and a `readPrdContent` helper **extracted from `command-deck.ts:746-763` into `src/lib/prd-locations.ts`** (command-deck imports the shared version; behavior there unchanged, including its fallback). The new endpoint returns `{ hasPrd: true, content, path, status, format }` or `404 { hasPrd: false, error }` — never continue.json content.
- **D6 — PRD chip presence** comes from resource discovery: add `'prd'` to `ResourceSource` (server `resource-discovery.ts:43` + frontend `ProjectNode.tsx:9`), `hasPrd` to `ProjectFeatureResourceDetails` (`ProjectNode.tsx:11-36`), populated where `vbrief`/`tasks` sources are added (`resource-discovery.ts:~600-610`) using the async `findDraftPrd` (`prd-locations.ts:138`). The stale workspace-`.pan/prd.md` check in `scanWorkspace` is left untouched (pre-existing, unused downstream).
- **D7 — PRD viewer dialog** composes `ChatMarkdown` (with `issueId` for file-link chips) inside a large overlay following the same shell idioms as the xBRIEF full-screen (D1) for visual consistency; store-driven `openPrdViewer(issueId)`.
- **D8 — Mockups are work item 1 with an explicit operator gate.** The work agent produces interactive HTML mockups and asks operator approval via AskUserQuestion (which surfaces in the dashboard Decisions queue) before starting the xBRIEF full-screen items. The mockup gate blocks only the xBRIEF-viewer chain (items 2-4); tasks/PRD items (5-8) may proceed in parallel — the issue's design requirement is scoped to the full-screen xBRIEF viewer.

## NonGoals (must-not constraints for review)

- No consolidation of the four pre-existing plan query keys beyond files this issue already touches; do not rename keys used by untouched components.
- No behavior change to the kanban `XBriefDialog` entry point (it keeps its centered dialog).
- No PRD editing — view only.
- No new markdown renderer and no Streamdown imports outside `ChatMarkdown.tsx`.
- No changes to `pan task` semantics, the task write door, or xBRIEF statuses.
- No per-mount persistence redesign of the viewer tab localStorage key (`xbrief-viewer-tab` stays a single global key).
- No shared generic Dialog primitive refactor across the ~37 hand-rolled overlays.
