# PAN-2558 — Polyrepo state-branch migration support

**Issue:** [PAN-2558](https://github.com/eltmon/overdeck/issues/2558)
**Status:** draft
**Author:** conversation (Opus 4.8), 2026-07-10

Enable `pan admin state migrate` to migrate **polyrepo** projects (whose root is
not a git repo) onto the `overdeck-state` branch of a designated sub-repo, using
the existing `pan_records` mechanism. Concretely: migrate **mind-your-now (MyN)**,
whose pipeline state is currently tracked in *no git repo at all*.

---

## Glossary

- **State-branch migration (PAN-2541):** moves a project's pipeline state (`.pan/{records,specs,drafts,continues,backlog,notes,review,test,feedback}`, `.beads/`) off the code branch onto an orphan branch `overdeck-state`, checked out at a **state worktree** `~/.overdeck/state/<project>/`. A `migration-complete.json` **marker** at the branch tip signals migration.
- **State-host repo:** the git repository whose `overdeck-state` branch physically stores the state. For a monorepo this is the project root; for a polyrepo it must be a designated sub-repo.
- **`pan_records`:** existing per-project config (`projects.yaml`) declaring which sub-repo + subdir holds records. Type `PanRecordsConfig` at `src/lib/projects.ts:33`; field at `:175`.
- **`resolveInfraRepo(project)`** (`src/lib/projects.ts:353`, PAN-1908): returns `{ repoPath, recordsPath }` — resolves the state-host repo from `pan_records` (monorepo → `project.path`; polyrepo → `project.path/<workspace.repos[name].path>`).
- **Polyrepo project:** `workspace.type: polyrepo` — the project root is a directory of independent git repos (`workspace.repos[]`), not itself a git repo. MyN's repos: `fe, api, infra, docs, myn-skills, openclaw-plugin`.
- **Legacy state source:** where `.pan`/`.beads` physically live *before* migration.

---

## Problem (validated 2026-07-10)

1. **The migration command ignores `pan_records`.** `src/cli/commands/admin/state-migrate.ts:105` hardcodes `const repo = project.path;` and runs every git op (`status`, `rev-parse main`, orphan-commit, push) against it. For MyN, `project.path = /home/eltmon/Projects/myn` is **not a git repo** → migration cannot run.

2. **MyN has no `pan_records`.** So `resolveInfraRepo()` returns the default `repoPath = project.path`, and `.pan`/`.beads` were created at the **non-git root**. Result: **MyN's pipeline state is committed to no git repo** — it exists only on local disk (a standing data-loss risk). A pre-migration backup is at `~/Backups/state-premigration-20260710/mind-your-now-state.tgz`.

3. **The read-door is half-migrated-aware.** `resolveStateHome()` (`src/lib/state-home.ts`, async) *already* routes through `resolveInfraRepo(project)` for the legacy path. But two sync/legacy surfaces still hardcode `project.path`:
   - `src/lib/state-read-home.ts:31` → `return { root: project.path, migrated: false }`
   - `src/lib/state-home.ts:167-168` (`findRecreatedLegacyStatePaths` tripwire) → `join(project.path, '.beads')` / `join(project.path, '.pan', …)`
   These disagree with the async resolver for polyrepo projects.

4. **First GitLab cutover.** MyN's repos are GitLab (`infra` = `git@gitlab.com:eltmon/myn-infra.git`). The migration has only run on GitHub (eltmon/overdeck).

### Design nuance — source vs. host repo

`resolveInfraRepo` assumes state lives *inside* the designated repo at `<repoPath>/<recordsPath>` (e.g. `infra/.pan`). But MyN's state currently sits at the **root** (`/home/eltmon/Projects/myn/.pan`), because `pan_records` was never set. So the **legacy state source (root)** and the **future state-host repo (infra)** differ. The migration must read the current-location state and publish it to the host repo's `overdeck-state` branch.

---

## Decisions made in this document

- **D1 — Designate `infra` as MyN's state-host** via `pan_records: { repo: infra }`. Rationale: `infra` (`myn-infra`) already owns MyN's cross-cutting infra (`.devcontainer-template`, `.agent-template`, traefik, seed). It is the meta/infra repo by role.
- **D2 — The migration resolves the host repo via `resolveInfraRepo`, and the legacy state source explicitly.** The command gets **two** paths: `hostRepo = resolveInfraRepo(project).repoPath` (git ops target) and `legacyStateSource` (where `.pan`/`.beads` are read from). For monorepo both equal `project.path`. For a polyrepo whose state is at the **root** (MyN today), `legacyStateSource = project.path` while `hostRepo = <root>/infra`. Reading from root and hosting on infra is correct and needs no pre-relocation step.
- **D3 — Do NOT relocate MyN's on-disk `.pan` into `infra/.pan` as a separate commit first.** The migration removes legacy state from the source anyway; a relocation commit into `infra` on `main` would be immediately superseded and would pollute the infra code branch with state. Read-in-place from the root, write to the orphan branch.
- **D4 — GitLab is validated as an implementation checkpoint, not assumed.** See WI-5.

---

## Requirements

- **FR-1** `pan admin state migrate <polyrepo-project>` resolves the state-host git repo via `resolveInfraRepo(project).repoPath` and performs all git operations there.
- **FR-2** The migration reads legacy `.pan`/`.beads` from their actual current location (`project.path` root for MyN) regardless of the host repo.
- **FR-3** All sync/legacy read surfaces (`state-read-home.ts`, `findRecreatedLegacyStatePaths`) resolve the repo consistently with the async `resolveStateHome` — via `resolveInfraRepo`, never bare `project.path`.
- **FR-4** MyN is configured with `pan_records: { repo: infra }` and migrates cleanly; post-migration, `pan doctor` reports MyN migrated and its state worktree resolves to `~/.overdeck/state/mind-your-now/`.
- **FR-5** The state-branch guards (`scripts/guard-state-plane-branches.sh`) and no-loss test cover the polyrepo/GitLab case.
- **NFR-1** No behavior change for existing monorepo projects (overdeck) — `resolveInfraRepo` returns `project.path` when `pan_records` is unset, so their resolution is byte-identical.
- **NFR-2** GitLab remotes behave identically to GitHub for orphan-branch push + marker round-trip.

### WI-1 — Route the migration through the state-host repo (FR-1, FR-2)
**File:** `src/cli/commands/admin/state-migrate.ts`
**Change:** replace the hardcoded root with the resolved host repo, and track the legacy source separately.

Before (`:105`):
```ts
const repo = project.path;
```
After:
```ts
import { resolveInfraRepo } from '../../../lib/projects.js';
// ...
const { repoPath: repo } = resolveInfraRepo(project); // state-host git repo (monorepo → project.path)
const legacyStateSource = project.path;                // where .pan/.beads physically live pre-migration
```
Then audit every use of `repo` in `migrateProjectState`: git operations (`git(repo, …)`, `stateWorktreePath`, orphan-commit, push, dirty check, `main`/`origin/main` rev-parse) must target `repo` (host). The **source-copy** steps that read `.pan`/`.beads` (the manifest build + file copy into the orphan tree) must read from `legacyStateSource`, and the legacy-removal + `.gitignore` rewrite + `.pan/context → .overdeck/context` move must operate on `legacyStateSource`. Where `repo === legacyStateSource` (monorepo) behavior is unchanged.
**Tests:** extend `tests/integration/state-branch-no-loss.test.ts` with a polyrepo fixture: a root dir containing a sub-repo `infra/` (its own `git init`), `.pan`/`.beads` at the root, and `pan_records: { repo: infra }`. Assert: orphan `overdeck-state` created on the **infra** repo, `.beads/issues.jsonl` + `records/*.json` tracked there, marker at tip, root `.pan`/`.beads` removed, and `infra/main` unchanged (no state committed to the code branch).

### WI-5 — GitLab cutover **implementation checkpoint** (D4, NFR-2)
**Not a code change — a live-verification gate with a fallback.**
Before the MyN production cutover:
1. `pan admin state migrate mind-your-now --dry-run` — confirm the plan targets `infra` (`myn-infra`) and reads state from the root.
2. Verify the deacon is frozen for the cutover window (MyN has ~34 stopped agents; an unfrozen patrol writing MyN state races the migration). Re-freeze if needed.
3. Run the migration; confirm the orphan `overdeck-state` pushes to `gitlab.com:eltmon/myn-infra` and the marker round-trips (`git show origin/overdeck-state:migration-complete.json`).
4. Confirm MyN's Vercel-on-`main` deploy did **not** fire (state branch ≠ `main`).
**Fallback if GitLab push/marker misbehaves:** abort (the migration is atomic pre-push and refuses dirty/divergent state), restore from `~/Backups/state-premigration-20260710/mind-your-now-state.tgz`, and file a GitLab-specific follow-up. Do not force.
