## Glossary

| Term | Definition |
| --- | --- |
| **Sync plane** | A user-scoped git repository that carries durable conversation/task state between one user's machines. Local clone at `${OVERDECK_HOME}/sync/`; remote is a **user-owned** private repo. Distinct from the per-project `overdeck-state` branch (project-scoped, shared with collaborators) — conversations span projects and must never land in project repos. |
| **Owner machine** | The single machine whose harness session a conversation currently belongs to. Only the owner writes that conversation's synced record. |
| **Machine identity** | A stable per-machine id (`machineId` UUID + human label, generated once at `${OVERDECK_HOME}/machine-id.json`). Identifies owners in synced records. |
| **Browse copy** | A non-owner machine's read-only rendering of a synced conversation, badged with its owning machine. |
| **Adoption** | The explicit "continue here" action: a non-owner machine builds a live local session from the synced transcript and takes ownership. Clone-not-migrate: the origin machine's original session is untouched; ownership of the *synced identity* moves. |
| **Sync record** | The per-conversation directory in the sync plane: `meta.json` (metadata + ownership) + `transcript.jsonl` (raw harness transcript snapshot). |
| **CAS ownership transfer** | Compare-and-swap via git push: adoption commits an ownership change and pushes; a rejected push forces pull → re-check ownership unchanged → retry or abort. Serializes concurrent adoptions without a coordination server. |

## Problem

Overdeck is single-machine. Conversation transcripts (harness JSONL under `~/.claude/projects/`
and harness-equivalent paths), conversation metadata (the `conversations` table in `overdeck.db`),
and live tmux sessions all live on the machine that created them. A user with a desktop and a
laptop has two disjoint Overdecks: work started at the desk is invisible on the couch. Traycer
syncs durable task state across devices through cloud CRDT rooms; the demand is real, but their
mechanism (content in vendor cloud) violates the privacy stance
[PAN-658](https://github.com/eltmon/overdeck/issues/658) locks in.

## Goal

Durable conversation state syncs between one user's machines through **storage the user owns**:

1. A **sync plane** — user-scoped git repo, user-chosen private remote — carrying per-conversation
   sync records.
2. **Browse anywhere:** every machine renders all synced conversations; non-owned ones read-only,
   badged with the owning machine.
3. **Adopt explicitly:** "Continue here" builds a live local session from the synced transcript
   (existing fork machinery) and transfers ownership via git CAS.
4. **CLI + dashboard** surfaces: `pan devices setup|sync|list` and dashboard equivalents.

Explicit non-goal: concurrent multi-machine editing of one live session (CRDT). Single owner,
explicit adoption — matching Traycer's own clone-not-migrate host model rather than their cloud
room model.

## Requirements

- **FR-1** A user can enable sync by pointing Overdeck at a git remote they own (`pan devices
  setup <remote-url>` or dashboard settings). Overdeck clones/initializes `${OVERDECK_HOME}/sync/`.
  Overdeck never provides or defaults a remote — an unset remote means sync is off (echoes the
  no-hardcoded-fallback rule).
- **FR-2** Each machine has a stable identity (`machineId` + label) created on first sync use and
  recorded in the sync plane under `machines/<machineId>.json`.
- **FR-3** Owned conversations are exported to sync records automatically: metadata on
  create/rename/end/archive; transcript snapshots at turn boundaries, debounced. Sync commits are
  batched and pushed in the background; a push/pull cycle also runs at dashboard boot and on a
  periodic timer.
- **FR-4** Non-owned synced conversations appear in the dashboard conversation list as browse
  copies: full transcript rendering through the existing conversation UI, read-only composer,
  owner-machine badge. They are excluded from cost totals and agent/runtime views.
- **FR-5** "Continue here" (dashboard action + `pan devices adopt <conversation>`) on a browse
  copy: performs the CAS ownership transfer, then builds a live local session seeded from the
  synced transcript via the existing fork pipeline; the new local conversation links back to the
  synced identity. The origin machine, on its next pull, shows its local copy as "continued on
  <machine>" (its local session file is never touched).
- **FR-6** Adoption works fully for claude-code conversations in v1 (plain-fork resume path);
  conversations from harnesses without a wired resume path still sync and browse, and adoption
  falls back to a summary-seeded fresh session (explicitly labeled as such).
- **FR-7** Exclusions: per-project and per-conversation opt-out (config list + a "never sync"
  toggle on a conversation). Excluded conversations never enter the sync plane; excluding an
  already-synced conversation tombstones its record.
- **FR-8** Conflicts never lose data: the sync engine only fast-forwards or rebases its own
  unpushed commits; a genuinely conflicting record (should be structurally impossible under
  single-owner writes) is surfaced to the operator, never auto-resolved by discarding.
- **FR-9** Once [PAN-2565](https://github.com/eltmon/overdeck/issues/2565) lands, task metadata
  (task record + member lineage) syncs as an additional record type; member conversations follow
  the same per-conversation ownership rules. (Schema reserved now; implementation gated on
  PAN-2565 shipping.)

Non-functional:

- **NFR-1** No conversation content ever transits an Overdeck-operated service. The sync plane's
  remote is user-configured; docs state plainly that the repo contains sensitive conversation
  content and must be private.
- **NFR-2** `overdeck.db` stays a rebuildable cache: synced-conversation rows on any machine are
  derivable from the sync plane. Reads/writes go through the conversations domain doors — no new
  direct store access (two-doors tenet).
- **NFR-3** All sync I/O is async (no `execSync`; `execFileAsync`/`spawn`), runs off the request
  path, and degrades silently to local-only when the remote is unreachable (offline laptop must
  not error-spam).
- **NFR-4** Sync-plane git operations never touch project repos, `overdeck-state`, or harness
  session directories of other machines' conversations. The only writes to `~/.claude/projects/`
  are the adoption fork's own new session file (created by existing fork machinery).
- **NFR-5** Timers (debounce, periodic sync) are testable with fake timers; every retry/backoff
  test uses `vi.useFakeTimers()` per the repo rule.
- **NFR-6** Sync must tolerate large transcripts: records are append-mostly JSONL (git delta-packs
  these well); a per-conversation size guard (default 100 MB, configurable) skips transcript
  snapshots above the cap with a visible "too large to sync" state rather than failing the whole
  cycle.

## Architecture

### Sync plane layout

```
${OVERDECK_HOME}/sync/            # git clone of the user's private remote, branch: main
  machines/<machineId>.json       # { machineId, label, lastSeenAt }
  conversations/<syncId>/
    meta.json                     # see below
    transcript.jsonl              # raw harness transcript snapshot (owner's export)
  tasks/<taskId>.json             # FR-9, reserved — written only after PAN-2565
```

`syncId` is a new UUID minted when a conversation first syncs (decoupled from any machine-local
conversation id or harness session id; local rows map to it).

```jsonc
// meta.json
{
  "v": 1,
  "syncId": "…",
  "owner": { "machineId": "…", "label": "desktop" },
  "harness": "claude-code",            // conversations.harness
  "claudeSessionId": "…",              // owner-side session UUID (harness-specific field, nullable)
  "title": "…", "model": "…", "effort": "high",
  "project": "overdeck",               // resolved project key; used for exclusion rules
  "cwd": "/home/…",                    // owner-side; informational only on other machines
  "createdAt": "…", "updatedAt": "…", "endedAt": null,
  "lineage": [ { "machineId": "…", "adoptedAt": "…" } ],   // adoption history
  "tombstone": false                   // FR-7 exclusion after the fact
}
```

### Sync engine (dashboard server, Effect-native)

New service `src/dashboard/server/services/device-sync.ts` + lib module
`src/lib/device-sync/` (plane git ops, record read/write, machine identity):

- **Export path (owner):** subscribes to conversation lifecycle + transcript-watcher events the
  server already emits; debounced per conversation (default 30 s after last activity), writes
  `meta.json` + copies the transcript (resolved via the existing transcript path resolution in
  `src/lib/conversations/transcript-adapter.ts` / `src/lib/paths.ts`), commits.
- **Transport loop:** batched `git add/commit` + `push`; `pull --rebase` (of its *own* unpushed
  commits only) at boot, on a periodic timer (default 5 min), and before any adoption. Push
  rejection → pull → retry. Unreachable remote → mark `sync: offline`, retry with backoff.
- **Import path (all machines):** after each pull, upsert browse rows through the conversations
  write door (new `origin: 'synced'` discriminator on the row; the read door filters them out of
  runtime/agent/cost queries — FR-4).
- **Adoption (FR-5):** `adopt(syncId)` = pull → assert `owner.machineId ≠ self` and record not
  tombstoned → commit ownership change (owner→self, lineage append) → push (CAS; on rejection
  re-pull and re-check) → invoke the fork pipeline (`createSummaryFork()` /
  `runForkPipeline()` — plain-fork mode for claude-code per FR-6, summary-seed otherwise) seeded
  from the synced `transcript.jsonl` → link the new local conversation to `syncId`.

### Why git (decision, made here)

- Matches the existing state-plane pattern (`overdeck-state`, `src/lib/state-plane.ts`) — same
  operational skills, same auditability, same "user-controlled remote" trust model.
- Single-owner writes make merge conflicts structurally rare; CAS-via-push gives ownership
  transfer without any coordination service.
- Rejected alternatives: E2E-encrypted relay (new always-on Overdeck infrastructure holding
  ciphertext — cost + key management for marginal benefit) and self-hosted room server (heavy
  ask for a single-user feature). Both remain open for a future *real-time* tier; this PRD is
  durable-state sync only.

### DB changes

Schema bump in `src/lib/database/schema.ts` (v59 at writing; use current at implementation):
`conversations` gains `sync_id TEXT` (nullable, unique) and `sync_origin TEXT`
(`'local'` default | `'synced'`); new `sync_state` table (remote url hash, last push/pull, per-
conversation export watermarks). All access via the conversations domain doors + a new
`device-sync-db.ts` accessor.

### CLI (Skills↔CLI convention — wrapper skills ship in the same commits)

`pan devices` verb group (avoids collision with the existing `pan sync` context/skills verb —
**do not overload `pan sync`**): `setup <remote>`, `status`, `list` (machines + owned/browse
counts), `sync` (force a cycle), `adopt <conversation>`, `exclude <conversation|project>`.

## Test Plan

**Unit** — record schema round-trip; machine identity; debounce/backoff (fake timers); exclusion
rules; size guard. **Integration** — two clones against a bare-repo fixture: export→import,
CAS adoption race, rejected-push retry, tombstone propagation, offline/backoff cycle (fake
timers). **E2E/Playwright** — browse rendering, read-only composer, adopt flow on claude-code,
"continued on" state.

## Out of Scope

- Real-time / live co-presence across machines (PAN-658 is the live-sharing surface; a future
  encrypted-relay tier could revisit).
- Sharing with other people (PAN-658), durable multi-user authorization ([PAN-2608](https://github.com/eltmon/overdeck/issues/2608)).
- Syncing agent runtime state, workspaces, Docker stacks, tmux sessions.
- Cost-history sync (cost stays per-machine; revisit with the cost archive).
- Automatic conflict-free multi-owner editing (CRDT) — rejected for v1 by design.
