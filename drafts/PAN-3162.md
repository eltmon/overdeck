# PRD: Observe GitLab-side merges and reconcile Overdeck merge state (PAN-3162)

## Glossary

- **Forge** — the git hosting service that owns merge state for a repo: GitHub or GitLab.
  Abstracted by `ForgeAdapter` in `src/lib/forge.ts` (`getForgeAdapter(forge)`).
- **Review artifact** — a GitHub PR or GitLab MR. The forge adapter calls both
  "review artifacts" so merge logic is forge-neutral.
- **Merge set** — the per-issue, per-repo merge coordination record
  (`merge_sets` + `merge_set_repos` SQLite tables, written only through
  `src/lib/merge-set.ts`: `upsertMergeSetSync`, `withRepoStateSync`). Polyrepo
  issues (MYN) have one row per member repo, each with its own `merge_status`,
  `artifact_url`, `forge`, `required` flag.
- **Review status** — the per-issue pipeline row (`review_status` table, written
  only through `src/lib/review-status.ts` doors). Holds the scalar
  `merge_status` (`pending` / `queued` / `merging` / `verifying` / `merged` /
  `failed`), `ready_for_merge`, `merge_step`, `merge_notes`, and a `history`
  array of `{type, status, timestamp}` transition entries.
- **Merge completeness** — the per-repo forge verdict computed by
  `assessMergeCompleteness(issueId)` in `src/lib/cloister/merge-completeness.ts`.
  Per repo: `merged` (merged review artifact found on the forge), `no-changes`
  (source branch gone or zero commits ahead), `unmerged` (commits ahead, no
  merged artifact), `unverifiable` (forge/git error). The issue is `complete`
  when every repo is `merged` or `no-changes`.
- **Deacon patrol** — a periodic reconciler run from the deacon tick in
  `src/lib/cloister/deacon.ts` (~60s cadence). Merge-related patrols live in
  `src/lib/cloister/deacon-merge.ts`.
- **UAT generation / merge train** — the batch mechanism that assembles
  ready features onto a `uat/<name>` branch per repo, tests them together, and
  promotes (merges) the batch. Ready set comes from
  `listEligibleCandidatesByProject()` in `src/lib/flywheel-merge-order.ts`;
  staleness is decided by `isStale()` in `src/lib/cloister/uat-reconciler.ts`.
- **`unmerged_sibling_repo` blocker** — the existing dashboard-surfaced signal
  that one required repo of a polyrepo issue has not merged while others have.

## Problem

Nothing in Overdeck observes forge-side merge state for non-GitHub projects.
Every merge observation point is GitHub-only:

1. `verifyMergedBeforeLifecycle()` (`src/lib/cloister/merge-verification.ts:210-213`)
   hard-refuses non-GitHub issues: `Non-GitHub project for ${issueId}; merge
   state cannot be auto-verified`. This makes `shouldSkipDispatchAsMerged()`
   (`merge-verification.ts:297`) blind for MYN — review dispatch
   (`review-agent.ts:332`), `deacon-review-status.ts:674`, and
   `service-reactive.ts:240` all consult it.
2. The deacon's stale-merge reconciler `reconcileStaleMergeStatus()`
   (`src/lib/cloister/deacon-merge.ts:145-264`) gates its only authoritative
   check on `resolveGitHubIssueSync(issueId).isGitHub` (`deacon-merge.ts:212`).
   For Linear-tracked, GitLab-forged MYN issues the check never runs.
3. `reconcileClosedPrReadyForMerge()` (`deacon-merge.ts:346-403`) parses only
   `github.com/.../pull/N` URLs.
4. The boot-time `clearStuckMergeStatuses()` (`src/lib/review-status.ts:696-718`)
   resets `merging`/`verifying` to `pending`, but only at server start. While
   the server runs, nothing time-bounds those states.
5. The polyrepo merge-click path in
   `src/dashboard/server/routes/workspaces/merge-ops.ts:533-535` builds its
   `activeRepos` list as `mergeStatus !== 'skipped' && !!artifactUrl` — a repo
   already recorded `merged` is merged *again* on the next click, and
   `glab mr merge` on an already-merged MR errors, failing the whole issue
   merge. There is no forge re-check of `pending`/`failed` repo rows before
   the attempt.

A merge that completes on GitLab — by the pipeline's own per-repo step, by
another Overdeck actor, or by a human clicking merge in the GitLab UI — is
invisible unless the exact code path that performed it writes the result back.

### Consequences (from the issue)

1. Already-merged work stays on Awaiting Merge, inviting duplicate clicks.
2. Clicking Merge on it hangs in `merging` indefinitely (or, per live state,
   fails opaquely at rebase).
3. UAT generations can include already-merged members, so a batch may carry
   no-op work or conflict against a base that already contains it.

Same defect family as #3148 (pushed rework commit not observed): an event that
should advance the pipeline is observed by nobody.

## Proposal

Make the forge the merge oracle for every forge type, through the existing
completeness door, in four surgical moves plus docs.

**D1 — one observation door.** Extend
`src/lib/cloister/merge-completeness.ts` — already forge-aware
(`findMergedGitLabArtifact` / `findMergedGitHubArtifact` in
`src/lib/forge.ts:224-246` / `:191-222`), already polyrepo-aware, already used
by `requireCompletePolyrepoMerge` (`merge-verification.ts:151-171`) — into the
single read door for "what does the forge say about this issue's merge state".
No new forge adapter methods; no second mechanism. Polling via the deacon
tick, not webhooks — GitHub merge observation works partly through the
`pull_request` webhook handler (`src/lib/webhook-handlers.ts:407-438`), but
there is no GitLab webhook ingress at all, and every other drift
reconciliation in this family is a deacon patrol, so polling closes the gap
with no new ingress surface.

**D2 — per-repo writeback, issue-level positive evidence.** Observation writes
per-repo truth into the merge set (`withRepoStateSync` + `upsertMergeSetSync`
— the existing write door) whenever the forge shows a merged artifact the row
doesn't know about. The *issue* terminalizes
(`merge_status: 'merged'`, `merge_step: 'post-merge-cleanup'`,
`ready_for_merge: false`, `enqueuePostMergeLifecycle`) only when
`assessMergeCompleteness` returns `complete` **and at least one repo verdict
is `merged`** (artifact-backed positive evidence). An all-`no-changes` result
(e.g. branches deleted after a manual merge) never terminalizes — branch
absence is not proof of merge, mirroring the guard comment at
`deacon-merge.ts:185-189`. `unverifiable` repos skip the issue for that tick;
the reconciler fails open, never closed.

**D3 — bound `merging`/`verifying` at 30 minutes.** A merge state that has sat
in `merging` or `verifying` for more than 30 minutes (from the latest
`{type: 'merge'}` entry in `review_status.history`, falling back to
`updated_at`) reconciles against the forge first (D1/D2), and if the forge
shows no complete merge, resets to `pending` with an explanatory
`merge_notes` — restoring the Merge button exactly as the boot-time
`clearStuckMergeStatuses()` does, including its `readyForMerge` preservation
rule (`review-status.ts:708-712`). 30 minutes (not the issue's "a few
minutes") because polyrepo verification gates legitimately run docker builds
for 10–20 minutes inside the `verifying` window.

**D4 — the merge-click path heals itself.** In `triggerMerge`'s polyrepo
branch (`merge-ops.ts:502-551`): (a) refresh merge-set rows from the forge
before building `activeRepos` (extend `reconcileStrandedRepos` in
`merge-completeness.ts:175` — today it only fills missing `artifactUrl`; it
will also flip `pending`/`failed`/`merging` repo rows to `merged` when
`findMergedArtifact` proves it); (b) exclude `merge_status === 'merged'` repos
from `activeRepos`. A fully-merged issue then falls into the existing "No
changed repos remain" success path (`merge-ops.ts:537-551`) — terminalized,
post-merge lifecycle enqueued, no re-merge attempted.

**D5 — non-GitHub `verifyMergedBeforeLifecycle`.** Replace the refusal at
`merge-verification.ts:210-213` with the D1 door: non-GitHub issues verify via
`assessMergeCompleteness` under the same positive-evidence rule as D2. This
unblinds `shouldSkipDispatchAsMerged` for MYN.

**Propagation (no new mechanism).** Once terminalized, an issue is ineligible
(`mergeGateEligibility`: `mergeStatus === 'merged'` → not eligible,
`review-status.ts:60`), so it leaves `listEligibleCandidatesByProject()`
(`flywheel-merge-order.ts:248-273`); `isStale()` in the UAT reconciler
(`uat-reconciler.ts:149-164`) then invalidates any live generation containing
it ("left the ready queue") and the next tick assembles a generation without
it. Awaiting Merge empties for the same reason. Fix direction 2 of the issue
is satisfied by propagation, verified by an acceptance criterion, not by new
code in the train.

**Scope guard for the reconciler patrol.** The forge sweep runs only for
issues in merge-relevant states: `ready_for_merge` true, or `merge_status` in
`merging` / `verifying` / `queued` / `failed`, or merge-set status
`merging` / `failed`. Mid-pipeline issues (review running, work in progress)
are not polled — this bounds git-fetch and forge-API cost per tick and
matches where drift actually hurts. (The existing GitHub path polls every
non-merged issue every tick; the GitLab sweep deliberately does not replicate
that cost profile across 6 repos × N issues.)

## Requirements

### Functional

- **FR-1** — A deacon-tick reconciler observes forge merge state for
  non-GitHub (GitLab) and polyrepo issues and writes per-repo merged truth
  into `merge_set_repos` through the merge-set write door.
- **FR-2** — The issue-level reconciler terminalizes an issue
  (`merge_status: 'merged'`, `merge_step: 'post-merge-cleanup'`,
  `ready_for_merge: false`, post-merge lifecycle enqueued) only when merge
  completeness is `complete` with at least one artifact-backed `merged` repo
  verdict; partial merges write per-repo truth but leave the issue un-merged;
  `unverifiable` skips the tick.
- **FR-3** — Re-planning deferral (active planning agent or spec at
  `draft`/`proposed`, PAN-1994) and the closed-out spec guard
  (`completed`/`cancelled`, PAN-1190) apply to the forge reconciler exactly as
  they do to the GitHub path in `reconcileStaleMergeStatus`.
- **FR-4** — `merging`/`verifying` states older than 30 minutes reconcile
  against the forge and resolve: complete → terminalize per FR-2; not
  complete → reset to `pending` with explanatory `merge_notes`, preserving
  `readyForMerge` when review+test+verification gates passed (mirroring
  `clearStuckMergeStatuses`).
- **FR-5** — `triggerMerge`'s polyrepo path refreshes merge-set rows from the
  forge before merging, excludes repos already `merged` from `activeRepos`,
  and routes a fully-merged issue through the existing "No changed repos
  remain" success path (post-merge lifecycle included).
- **FR-6** — `verifyMergedBeforeLifecycle` (and therefore
  `shouldSkipDispatchAsMerged`) verifies non-GitHub issues through the merge
  completeness door under the FR-2 positive-evidence rule instead of refusing
  them.
- **FR-7** — A forge-merged issue leaves the train ready set on the next
  deacon tick, and a live generation containing it is invalidated by the
  existing `isStale()` "left the ready queue" path (propagation verified by
  test, no new train code).
- **FR-8** — Documentation updated: `docs/MERGE-WORKFLOW.md` "Single Merge
  Oracle" section re-specified for forge-neutral verification;
  `docs/RECOVERY-NET.md` gains the new patrol.

### Non-functional

- **NFR-1** — No new synchronous primitives in server-reachable code
  (`execAsync`/`execFileAsync` only — repo rule, PAN-70).
- **NFR-2** — The reconciler fails open: any forge/git error for an issue
  skips that issue for the tick and logs a warning; it never terminalizes or
  resets on `unverifiable`.
- **NFR-3** — Forge polling is bounded to merge-relevant issues (scope guard
  above) and parallelized across repos (`Promise.all`, as
  `assessMergeCompleteness` already does).
- **NFR-4** — New patrol code is dependency-injectable for tests (completeness
  assessor, status door, clock), matching the existing deacon-merge test
  style; delay/timeout tests use `vi.useFakeTimers()`.

## Acceptance criteria (issue level)

1. `npm run typecheck`, `npm run lint`, and `npm test` pass with the new and
   extended suites green.
2. A GitLab-merged MR for a non-GitHub-tracked issue is reflected in
   `merge_set_repos` and, when all required repos are complete with positive
   evidence, terminalizes the review row within one deacon tick — covered by
   the WI-2 tests with an injected assessor and by the WI-6 live checkpoint.
3. A `merging` state older than 30 minutes never survives the next patrol
   unresolved: it either terminalizes (forge-complete) or resets to `pending`
   with merge notes — covered by WI-3 tests.
4. Clicking Merge on a fully-merged polyrepo issue returns the "No changed
   repos remain" success path without calling `mergeReviewArtifact` for any
   repo — covered by WI-5 tests.
5. `shouldSkipDispatchAsMerged` returns `skip: true` for a forge-merged
   non-GitHub issue — covered by WI-4 tests.
6. No GitHub-path behavior changes: existing deacon-merge, merge-verification,
   merge-ops, and merge-completeness suites stay green unmodified except where
   a test names the new behavior.

## NonGoals

- GitLab webhook ingress of any kind.
- GitLab closed-without-merge MR reconciliation (the GitHub-only
  `reconcileClosedPrReadyForMerge` keeps its current scope; parity is a
  follow-up).
- Changes to how merges execute (per-repo MR flow, quality gates, rebase) —
  only observation, bounding, and the skip-merged filter change.
- Auto-retry of failed repo merges (MIN-898/MIN-858 api/docs retries are
  operator/strike-driven through the normal Merge path, now self-healing).
- Any change to GitHub-project behavior.
- Manual DB/record backfill for MIN-898/MIN-858 — recovery flows through the
  deployed reconciler and the normal merge path, not one-off writes.

## Repo rules restated for the executor

- **No `execSync`** anywhere reachable from the dashboard server (PAN-70).
- **Fake timers** (`vi.useFakeTimers()` + `advanceTimersByTime`) for the
  30-minute-bound tests; never real `setTimeout` waits.
- **Single source of truth:** review-status writes only through
  `setReviewStatusSync`; merge-set writes only through
  `withRepoStateSync`/`upsertMergeSetSync`; no direct SQLite access.
- **Surgical changes:** the GitHub branches of every touched function stay
  byte-identical unless a named test says otherwise.
- Commit one xBRIEF item at a time and push before `pan task done`.
