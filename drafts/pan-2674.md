## Glossary

- **Issue record** — the durable per-issue JSON at `records/<issue>.json` on `overdeck-state`, typed `PanIssueRecord` in `src/lib/pan-dir/record.ts`. All writes go through `updateIssueRecord` in `src/lib/pan-dir/record-update.ts` (the write door).
- **Override field** — a flat optional field on the issue record that beats project/global config for one knob. Existing examples on `PanIssueRecord` (`src/lib/pan-dir/record.ts:202-207`): `reviewMode`, `reReviewScope`, `tieredExecutionOverride`.
- **Staffing** — the `{ tierName, model, harness, implicit }` answer to "who runs this work item", produced by `resolveStaffing()` in `src/lib/agents/staffing.ts:84` (PAN-2397: EVERY work dispatch resolves through it).
- **Implicit tier** — `resolveImplicitStaffing()` (`src/lib/agents/staffing.ts:66`): the degenerate one-tier world whose model is the `roles.work` resolution. Used when no explicit tier table is enabled and as the fallthrough.
- **Explicit tier table** — `config.tieredExecution` with per-difficulty tiers/distributions; enablement is issue-aware via `resolveTieredExecutionEnabledForIssue()` (`src/lib/agents/tier-table.ts:168`), which already reads a record override.
- **Swarm policy layers** — `resolveSwarmPolicyLayers()` in `src/lib/swarm-policy.ts:14`: precedence `cli > issue > project > global > built-in`. The issue layer is `record.swarm.policy` (`src/lib/pan-dir/record.ts:104-110`), already served by `GET/POST /api/issues/:issueId/swarm-policy` (`src/dashboard/server/routes/projects.ts:708-719`).
- **Policy strip** — the compact select group in the issue header. Today it is `ReviewPolicyControl` (`src/dashboard/frontend/src/components/ReviewPolicyControl.tsx`), mounted at `src/dashboard/frontend/src/components/Stage/cockpit/IssueMissionControl.tsx:768` and `src/dashboard/frontend/src/components/CommandDeck/SessionView/IssueHeader.tsx:324`.
- **Resolved default label** — the pattern where the empty option of an override select shows what the merged config resolves to, e.g. `review: default (full)`.

## Decisions (made here, not by the executor)

- **D-1 — Flat field, not a nested block.** The work-model override is `workModel?: string` directly on `PanIssueRecord`, matching the sibling flat overrides `reviewMode` / `reReviewScope` / `tieredExecutionOverride`. No `staffing: {...}` sub-object.
- **D-2 — Model only.** No per-issue harness or effort override in this issue. Harness is always derived from the model's provider via `providerDefaultHarnessSync()` (`src/lib/agents/staffing.ts:57`). Never force `claude-code` for a CLIProxy-routed model (PAN-1865). Effort stays role-config (`high` default — never default `xhigh`/`max`).
- **D-3 — Precedence.** `explicit spawn model (CLI --model / API model param) > issue workModel > explicit tier table > implicit roles.work`. The issue override is stronger than the tier table: an operator pinning a model on one issue means THIS issue, regardless of per-bead difficulty routing.
- **D-4 — `pan start` treats the override as an implicit `--model`.** In `issueCommand` (`src/cli/commands/start.ts:727`), the override slots in as `options.model ?? record.workModel` before `resolveSpawnModel()` (`src/cli/commands/start.ts:719-725`). Because `resolveSpawnModel` lets an explicit model beat the recorded session model, setting an override and restarting applies it without `--fresh` being mandatory (though a model switch still gets a fresh session downstream, per existing behavior).
- **D-5 — Swarm needs no new backend.** The swarm select reuses `GET/POST /api/issues/:issueId/swarm-policy` verbatim. The only new swarm surface is the CLI verb (FR-4) and the header select (FR-5).
- **D-6 — Resolved label semantics.** The `work:` select's default label shows the implicit roles.work resolution; when an explicit tier table is active for the issue, it shows `work: default (tiered)` instead — per-bead models vary, so naming one would lie.
- **D-7 — This issue does NOT touch the rail or the drawer.** `DrawerSwarmPolicy` (`src/dashboard/frontend/src/components/drawer/IssueDrawer.tsx:70`, mounted at `:297`) stays; PAN-2499's no-loss audit retires it when the strip reaches console density. Rail chips (mockup section C) are PAN-2499 work.
- **D-8 — New CLI verb `pan staffing`,** added to the wrapper-skill exclusion list in `docs/SKILLS-CONVENTION.md` (its `--help` is self-sufficient; `scripts/lint-skills.sh` must stay green).

## Requirements

### Functional

- **FR-1** `PanIssueRecord` gains `workModel?: string` — per-issue work-model override, written only through `updateIssueRecord`.
- **FR-2** Every staffing path honors the override: swarm-slot spawn (`resolveSlotTierSpawnParams`, `src/lib/agents/spawn-prep.ts:256`), single-work spawn (`resolveSingleWorkTierSpawnParams`, `src/lib/agents/spawn-prep.ts:301`), agent restart (`src/dashboard/server/routes/agents/lifecycle-restart.ts:787`), and `pan start` (D-4). Precedence per D-3.
- **FR-3** `GET/POST /api/issues/:issueId/staffing` — returns `{ override: { workModel }, resolved: { model, tiered, source } }`; POST accepts `{ workModel: string | null }` (null clears). Model values validated with `normalizeModelOverrideSync` (`src/lib/model-validation.ts`); invalid → 400.
- **FR-4** `pan staffing <id> [--model <m>|default] [--swarm <off|auto|always|default>]` — sets/clears both overrides; bare `pan staffing <id>` prints resolved values with their source layer.
- **FR-5** `ReviewPolicyControl` is extended into `IssuePolicyStrip` with `work:` and `swarm:` selects (resolved-default labels, blue `--primary` border when overridden), replacing the component at both existing mounts. Model options come from `GET /api/settings/available-models` (`src/dashboard/server/routes/settings.ts:171` — same source as `RolesPanel.tsx:174`).
- **FR-6** Restart affordance: when `workModel` is set and differs from `record.model` (the recorded agent model, `src/lib/pan-dir/record.ts:201`), the strip's host shows an amber bar: override applies to the NEXT spawn; button restarts the agent fresh. Never auto-restart on select change.
- **FR-7** Docs updated (work item 8).

### Non-functional

- **NFR-1** No hardcoded model fallback: an unresolvable model fails loudly (`requireModelOverrideSync`), never a literal.
- **NFR-2** All record writes via `updateIssueRecord` (single write door); no direct file/DB writes.
- **NFR-3** UI follows the style guide: DM Sans, `font-medium`, amber = human must act, one colored signal per control, no pills.
- **NFR-4** No behavior change for issues with no override: `resolveStaffing` output is byte-identical when `workModel` is unset (existing `staffing.test.ts` suites stay green unmodified).

## Intersecting repo rules (restated for the executor)

- Write the issue record ONLY via `updateIssueRecord` — never edit `records/*.json` or the DB directly (two-door rule).
- No `execSync` anywhere server-reachable; async only.
- Fake timers (`vi.useFakeTimers`) for any delay/retry test.
- Quality gates before `pan done`: `npm run typecheck`, `npm run lint`, `npm test`.
- Frontend styling: DM Sans / `font-medium`, semantic tokens only (no hex, no `slate-*`, no pills), amber strictly = human action required.
- Never introduce a hardcoded model fallback; unresolvable ⇒ loud error.
- CLI changes ship with their skills-lint consequences handled in the same commit (`scripts/lint-skills.sh` is in `npm run lint`).
