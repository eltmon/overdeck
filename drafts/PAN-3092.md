# PAN-3092 — Verdict writes must survive record-lock contention: verdict-aware merge, bounded backoff, contention surfacing, and frozen-agent escalation

Issue: https://github.com/eltmon/overdeck/issues/3092

## Glossary

- **Verdict** — a terminal specialist outcome for one pipeline gate: review passed/blocked/failed, test passed/failed, uat passed/blocked/failed, verification passed/failed/skipped, inspect passed/blocked/failed, merge merged/failed.
- **Write door** — `setReviewStatusSync()` (`src/lib/review-status.ts:152`), the single path every verdict signal (CLI `pan admin specialists done`, server `POST /api/review/:issueId/status`, deacon recoveries) flows through. It writes the SQLite cache (best-effort) and the journal record (source of truth).
- **Journal / record** — the per-issue permanent record at `records/<issue>.json` on `overdeck-state`, written under a per-issue file lock by `updateIssueRecord()` (`src/lib/pan-dir/record-update.ts:318`).
- **Record lock** — `~/.overdeck/locks/records/<projectKey>/<ISSUE>.lock`, a mkdir lock with owner.json (`src/lib/pan-dir/fs-lock.ts`). Internal retries total ~1s (`RECORD_LOCK_RETRY_DELAYS_MS`, fs-lock.ts:8); each writer may hold it up to the 30s durability budget (`DEFAULT_RECORD_DURABILITY_BUDGET_MS`, record-update.ts:25).
- **Workspace verdict fallback** — `<workspace>/.overdeck/pipeline-verdict.json`, written when the journal write fails (PAN-2583), folded back by `drainWorkspaceVerdictFallback()` (`src/lib/overdeck/review-status-record-sync.ts:391`, PAN-2989).
- **Verdict artifact** — the test role's deterministic `.pan/test/result.json` (PAN-1681) and the review role's `.pan/review/<runId>/{synthesis,review}.md` verdict report, both read back by deacon patrols when the agent never signaled.
- **Gate group** — a verdict status field plus its companion fields that must move as a unit (e.g. `reviewStatus` + `reviewNotes` + `reviewedAtCommit` + `reviewerVerdicts`).
- **Needs-you** — the operator-attention surface (recovery trips in the per-issue record via `recordRecoveryFailure()`, `src/lib/cloister/recovery-trip.ts`, plus activity-log entries via `emitActivityEntrySync()`).

## Problem

A completed specialist verdict can fail to reach any persisted plane even though every mechanism reports success, and the failure is invisible to operators. Observed 2026-07-26 on MIN-902 (review verdict, spinning agent, ~$5/hr of LLM retries for ~1h until it landed) and MIN-858 (test verdict, frozen agent, 6h silent, verdict held only in the agent's pane).

The causal chain, verified against the code at planning time:

1. `projectPipeline()` stamps `pipeline.updatedAt` on **every** status write, verdict or not (`src/lib/pan-dir/records.ts:109`). Every newer-wins comparison treats a newer timestamp as newer truth:
   - `pickNewerPipeline()` (`src/lib/pan-dir/records.ts:316-322`) — used inside the locked record write (`updateIssueRecordForIssue`, records.ts:357) to protect against PAN-2587 clobbering. A verdict fold whose `updatedAt` is older than any subsequent verdict-free write is silently discarded while `updateIssueRecordForIssue` returns `true`.
   - The drain's supersede check (`review-status-record-sync.ts:404`): `if (journal?.updatedAt && !(journal.updatedAt < fallback.updatedAt))` deletes the fallback **without folding** whenever any newer write landed — even if the journal never carried the verdict.
2. Under sustained lock contention (writers serialized behind an unhealthy state push, each holding the lock up to its 30s budget), verdict-free writes with newer timestamps land while the verdict write fails. The drain then consumes the fallback unlanded, and the verdict exists nowhere: DB says pending/reviewing, journal says pending/reviewing, fallback file gone. This is exactly MIN-902's observed state at 00:09Z.
3. When the CLI reports the journal write failed, nothing tells the agent to stop. The agent retries the signal at LLM-turn cost — MIN-902 burned ~$5/hr with no backoff, no decay, no cap, no termination condition.
4. Frozen mode (MIN-858): the agent never executed the write contract (no artifact POST landed; verdict only in the pane). `decideUnsignaledTestAction()` (`src/lib/cloister/test-verdict.ts:99-134`) nudges a live idle session once, then returns `'none'` forever. No escalation fires; the dashboard reports `healthy`/`working` for 6 hours.

**Operator constraint (issue comment 4, authoritative):** do NOT break or bypass the record lock — contention resolves on its own (MIN-902 eventually landed). Fix the unbounded flat-rate retry with backoff, surface long contention instead of failing it, and make the frozen mode recoverable from outside the agent.

**Refuted hypothesis:** the issue title's "self-deadlock by construction" (the reviewer holding its own lock across its completion signal) is not the mechanism — a single writer holds the lock ≤ ~30s by design (PAN-2989), and MIN-902's verdict did eventually land. The defect is timestamp-conflated verdict loss plus unbounded retry, not lock semantics.

## Requirements

### Functional

- **FR-1 — Verdict-aware pipeline merge.** A whole-record rebuild must never drop a terminal verdict from the incoming pipeline when the newer on-disk pipeline belongs to the same review cycle and carries no verdict for that gate. Newer cycles (newer `reviewSpawnedAt`) and newer terminal verdicts still win, preserving PAN-2587's protection.
- **FR-2 — Content-aware drain supersede.** The fallback drain deletes a fallback as superseded only when the journal actually carries the fallback's terminal verdicts (per-gate content equality) or belongs to a strictly newer review cycle. A newer-but-verdict-free journal no longer consumes an unlanded verdict.
- **FR-3 — Bounded in-process backoff for verdict writes.** A journal write that introduces a NEW terminal verdict retries `updateIssueRecordForIssue` with exponential backoff (~2.6 min total, env-tunable) inside the process before falling back to the workspace file. `pan admin specialists done` awaits this via the existing `flushReviewStatusJournalWrites()`, so the agent's Bash call waits in-process instead of burning LLM turns. Non-verdict bookkeeping writes keep today's single-shot behavior.
- **FR-4 — Contention surfacing.** When a fallback remains undrained past a threshold (10 min), the host emits one activity-log warning and one needs-you recovery trip per contention episode, naming the issue, the verdict age, and the current lock owner. No nag loops.
- **FR-5 — Stranded-fallback sweep patrol.** A deacon patrol sweeps every in-pipeline issue's workspace for fallback files (live path + stranded drain claims) each patrol cycle and drains them — the external retry the short-lived CLI's unref'd timers can never provide.
- **FR-6 — Frozen-agent escalation (test side).** A live, idle test session with an unsettled verdict and no verdict artifact escalates to needs-you after the nudge grace instead of the patrol returning `'none'` forever. Never fabricates a verdict (D6 preserved): the operator is told to read the pane and apply or re-dispatch.
- **FR-7 — Stop-signal contract in role prompts.** Review and test prompts (and the test spawn prompt builder) state plainly: once the verdict is in the fallback file or the artifact, it is durable — do not re-run the signal; the host folds it automatically.
- **FR-8 — Documentation.** `docs/AGENT-STATE-PLANES.md`'s verdict-fallback paragraph is updated to the new merge/supersede/backoff/sweep semantics.

### Non-functional

- **NFR-1 — Lock protocol unchanged.** No lock-exempt writes, no changes to `RECORD_LOCK_RETRY_DELAYS_MS` or the 30s durability budget, no `specialists/done` exemption (operator directive).
- **NFR-2 — Fake timers.** Every test exercising backoff/delays uses `vi.useFakeTimers()` + `advanceTimersByTimeAsync` (repo rule).
- **NFR-3 — No verdict fabrication.** Recovery applies verdicts only from written evidence (fallback file, verdict artifact, verdict report). Escalation, never guessing.
- **NFR-4 — Async-only in server-reachable code.** The sweep patrol uses the async fallback/drain readers; no `execSync`, no blocking calls on the dashboard event loop.
- **NFR-5 — Single trip per episode.** Contention surfacing and frozen-agent escalation each emit at most one needs-you per issue per episode (deduped by the fallback's `updatedAt` / the test dispatch generation).

## Design

### FR-1 — `mergePipelineVerdictAware()` (new module)

New file `src/lib/pan-dir/pipeline-verdict-merge.ts`. No runtime imports (type-only imports from `records.ts` — avoids cycles). Exports:

```ts
// Terminal verdict values per gate. Non-terminal: pending, reviewing, testing,
// merging, dispatch_failed, queued, undefined.
const TERMINAL_GATE_VALUES = {
  reviewStatus: ['passed', 'blocked', 'failed', 'skipped'],
  testStatus: ['passed', 'failed'],
  uatStatus: ['passed', 'blocked', 'failed'],
  verificationStatus: ['passed', 'failed', 'skipped'],
  inspectStatus: ['passed', 'blocked', 'failed'],
  mergeStatus: ['merged', 'failed'],
} as const;

// Companion fields that move with their gate's status as one unit.
const GATE_COMPANIONS = {
  reviewStatus: ['reviewNotes', 'reviewedAtCommit', 'reviewerVerdicts'],
  testStatus: ['testNotes'],
  uatStatus: ['uatNotes'],
  verificationStatus: ['verificationNotes', 'lastVerifiedCommit'],
  inspectStatus: ['inspectNotes'],
  mergeStatus: ['mergeNotes', 'mergeStep'],
} as const;

export function mergePipelineVerdictAware(
  rebuilt: PanIssuePipelineRecord,
  fresh: PanIssuePipelineRecord | undefined,
): PanIssuePipelineRecord
```

Rules, in order:

1. `!fresh?.updatedAt || !rebuilt?.updatedAt` → return `rebuilt` (existing PAN-2587 guard).
2. `rebuilt.updatedAt >= fresh.updatedAt` → return `rebuilt` (existing behavior).
3. Base = `structuredClone(fresh)`.
4. **New-cycle override:** if both `fresh.reviewSpawnedAt` and `rebuilt.reviewSpawnedAt` parse and `fresh.reviewSpawnedAt > rebuilt.reviewSpawnedAt` → return base unchanged (a new review cycle legitimately resets verdicts).
5. For each gate: if `rebuilt[gate]` is terminal and `base[gate]` is not terminal → copy the gate's status + companion fields from `rebuilt` onto base.
6. Return base.

`pickNewerPipeline()` (`records.ts:316-322`) becomes a thin wrapper delegating to `mergePipelineVerdictAware` (keep the export name — `updateIssueRecordForIssue` at records.ts:357 and tests/unit/lib/pan-dir/pipeline-monotonic.test.ts reference it).

Before (records.ts:316-322):

```ts
export function pickNewerPipeline(rebuilt, fresh) {
  if (!fresh?.updatedAt || !rebuilt?.updatedAt) return rebuilt;
  return rebuilt.updatedAt < fresh.updatedAt ? fresh : rebuilt;
}
```

After:

```ts
export function pickNewerPipeline(rebuilt, fresh) {
  return mergePipelineVerdictAware(rebuilt, fresh);
}
```

### FR-2 — content-aware supersede in the drain

`drainWorkspaceVerdictFallback()` (review-status-record-sync.ts:403-407).

Before:

```ts
const journal = readPipelineSync(issueId);
if (journal?.updatedAt && !(journal.updatedAt < fallback.updatedAt)) {
  for (const claim of claims) rmSync(claim.claimPath, { force: true });
  return true;
}
```

After:

```ts
const journal = readPipelineSync(issueId);
if (journal?.updatedAt && !(journal.updatedAt < fallback.updatedAt) &&
    pipelineCoversFallbackVerdicts(journal, fallback)) {
  for (const claim of claims) rmSync(claim.claimPath, { force: true });
  return true;
}
```

`pipelineCoversFallbackVerdicts(journal, fallback)` (same new module, FR-1):

1. Newer cycle: `journal.reviewSpawnedAt` parses and is `> fallback.updatedAt` → `true`.
2. For every gate where `fallback.pipeline[gate]` is terminal: `journal[gate]` must equal it. Any mismatch → `false`.
3. Fallback carries no terminal gates → `true` (pure bookkeeping; timestamp rule stands).

The existing drain test "deletes the fallback without a record write when the journal is already newer" (tests/unit/lib/overdeck/review-status-record-sync-drain.test.ts:88) must be split: journal newer **and** verdict-covering → delete; journal newer but **verdict-free** → fold.

### FR-3 — terminal-verdict backoff in the write path

`setReviewStatusSync` computes whether the update introduces a NEW terminal verdict (it already computes `terminalReviewVerdict` at review-status.ts:243-248; extend to test/uat/verification/inspect/merge transitions) and passes it down: `updateIssueRecordForReviewStatusSync(issueId, updated, { verdictWrite: true })`.

`updateIssueRecordForReviewStatusSync()` (review-status-record-sync.ts:15-41) gains a retry loop around `updateIssueRecordForIssue` when `verdictWrite` is set:

```ts
const DEFAULT_VERDICT_BACKOFF_DELAYS_MS = [2_000, 5_000, 10_000, 20_000, 40_000, 80_000] as const; // ≈2.6 min
// env override: OVERDECK_VERDICT_BACKOFF_DELAYS_MS="2000,5000,..." (same pattern as recordDurabilityBudgetMs)

for (let attempt = 0; ; attempt += 1) {
  let landed: boolean | undefined;
  try { landed = await updateIssueRecordForIssue(issueId, status); } catch { landed = false; }
  if (landed !== false) {
    if (landed === true) trackVerdictFallbackDrain(issueId);
    return;
  }
  const delay = backoff ? delays[attempt] : undefined;
  if (delay === undefined) break;
  await new Promise<void>((resolve) => setTimeout(resolve, delay));
}
writeWorkspaceVerdictFallbackSync(issueId, status);
scheduleVerdictFallbackDrain(issueId);
```

The promise stays in `pendingJournalWrites`, so `flushReviewStatusJournalWrites()` (called by `doneAndExitCommand`, src/cli/commands/specialists/done.ts:343-344) waits out the backoff in-process. Server-side calls are fire-and-forget as today (no event-loop blocking — the loop is fully async).

CLI messaging in `doneAndExitCommand`: after the flush, if `readWorkspaceVerdictFallbackSync(issueId)` (already exported, review-status-record-sync.ts:325) returns a fallback, print:

```
⚠ Journal write is contended — the verdict is durable at <path>.
  The host folds it automatically (drain + deacon sweep). Do NOT re-run this
  signal: repeated signals add lock pressure and burn tokens for nothing.
```

### FR-4 + FR-5 — sweep patrol `sweepStrandedVerdictFallbacks()`

New file `src/lib/cloister/deacon-verdict-fallback-sweep.ts`:

```ts
const VERDICT_CONTENTION_SURFACE_MS = 10 * 60 * 1000;

export async function sweepStrandedVerdictFallbacks(now = Date.now()): Promise<string[]> {
  const actions: string[] = [];
  for (const [issueId, status] of Object.entries(loadReviewStatuses())) {
    if (status.mergeStatus === 'merged' || status.closedOut) continue;
    const fallback = await readWorkspaceVerdictFallback(issueId); // newest across live path + claims
    if (!fallback) continue;
    const drained = await drainWorkspaceVerdictFallback(issueId);
    if (drained) { actions.push(`Drained stranded verdict fallback for ${issueId}`); continue; }
    const ageMs = now - Date.parse(fallback.updatedAt);
    if (ageMs < VERDICT_CONTENTION_SURFACE_MS) continue;
    if (status.stuck || status.deaconIgnored) continue;
    // One trip per contention episode — obligationGeneration = fallback.updatedAt.
    // Activity entry is immediate (no record lock); the recovery trip is best-effort.
    emitActivityEntrySync({ source: 'cloister', level: 'warn', issueId,
      message: `${issueId} — verdict fallback undrained for ${Math.round(ageMs / 60000)}min; record lock contended (${lockOwnerDescription})` });
    const { emitNeedsYou } = await recordRecoveryFailure(workspacePath, issueId,
      'verdict-fallback-contention', fallback.updatedAt, 1);
    if (emitNeedsYou) actions.push(`needs-you ${issueId}: verdict contended ${Math.round(ageMs / 60000)}min`);
  }
  return actions;
}
```

`lockOwnerDescription` comes from `readOwner(recordLockPath(project, issueId))` — needs `readOwner` exported from `src/lib/pan-dir/fs-lock.ts` (currently module-private, fs-lock.ts:65).

Registration: wire into the deacon patrol cycle alongside `reconcileUnappliedReviewVerdicts` — import in `src/lib/cloister/deacon.ts` (see the patrol list at deacon.ts:1136-1140 and invocation near deacon.ts:2861). Async readers only (NFR-4).

## Decisions (auto mode — recorded in plan.autoDecisions)

- **D1: Content-aware merge over re-architecting timestamps.** Stamping a separate `verdictUpdatedAt` per gate would touch every writer and reader; the merge-rule change is contained to one new module and two call sites, and preserves PAN-2587's newer-wins default for all non-verdict fields.
- **D2: ~2.6 min in-process backoff, not longer.** MIN-902's hour-long contention was the outlier; the sweep patrol (FR-5) owns the long tail, so the agent-facing budget stays short and the CLI never blocks for more than a few minutes.
- **D3: Surfacing threshold is duration-based (10 min), not spend-based.** With FR-3 the retry no longer burns LLM turns, so the residual risk is elapsed time, not cost; a duration threshold in the long-lived server is the honest signal.
- **D4: Frozen mode escalates; it never fabricates.** D6 (never guess a verdict) outranks automation — a live session holding a pane-only verdict is an operator decision.
- **D5: No new review-side verdict artifact.** The review role already has the fallback file plus the `.pan/review/<runId>/` verdict report and two deacon patrols that read it (`checkCompletedButUnsignaledReviews`, `reconcileUnappliedReviewVerdicts`); the consumption fix and the sweep close the hole without a third contract.
- **D6: New-cycle identity is `reviewSpawnedAt`.** It is the existing cycle marker the status guards already use (review-status.ts:201-219).

## Hazards

- **H1 — PAN-2587 regression.** The merge change alters the single write door's clobber protection. Mitigation: the existing pipeline-monotonic tests must stay green untouched except where the new verdict-preservation semantics deliberately change an expectation; new tests pin the MIN-902 repro and the new-cycle reset.
- **H2 — Deadlock-of-load.** Longer in-process retry means more processes waiting on a contended lock. Mitigation: backoff is exponential, bounded at ~2.6 min, and applies only to new terminal verdicts — bookkeeping writes stay single-shot.
- **H3 — False needs-you during a genuinely long state-push outage.** A 10-min contention during a GitHub outage trips one needs-you per issue. Mitigation: one trip per episode (deduped by `fallback.updatedAt`), warn-level activity entry, auto-resolves when the drain lands.
- **H4 — `readOwner` export widens fs-lock's surface.** It is read-only; no new mutation path.
- **H5 — Shared-file conflicts.** FR-2 and FR-3 both touch `review-status-record-sync.ts` (disjoint functions); land them in separate commits and rebase between items.
