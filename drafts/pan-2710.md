# PAN-2710 — Auto re-trigger stale failed PR checks after main goes red→green

**Issue:** https://github.com/eltmon/overdeck/issues/2710
**Status:** draft (auto planning, 2026-07-15)
**Prior art:** PAN-2712 (`2b8971f9b5`) fixed the *reconciler* half — `failing_checks` blockers now get a 10-minute recheck cadence. This issue is the *trigger* half: nothing re-runs a PR check that failed while main was red, so the reconciler keeps re-reading the stale `fail` and re-latching the blocker.

## Glossary

- **Red window** — a per-workflow time interval on `main` during which that workflow's latest completed run was failing: it opens at the `createdAt` of a failing completed run on `main` and closes at the `createdAt` of the next successful completed run of the *same workflow* on `main`. An unclosed window means main is still red for that workflow.
- **Poisoned run** — a failing workflow run on an open feature PR's current head whose `createdAt` falls inside a *closed* red window of the same workflow: its failure is presumed inherited from red main, not caused by the PR's own diff.
- **`failing_checks` blocker** — the `blocker_reasons` entry in `review_status` that forces `ready_for_merge = 0` (`src/lib/review-status.ts:401-407`, PAN-905 absolute override).
- **Reconciler** — `src/dashboard/server/services/merge-blocker-reconcile-service.ts`, which polls `refreshMergeStateFromGitHub` to rebuild GitHub-native blockers from the live PR `statusCheckRollup`.
- **Run attempt** — GitHub's per-run re-run counter, exposed by `gh run list --json attempt`. `attempt: 1` means the run has never been re-run (verified live against `eltmon/overdeck` on 2026-07-15).

## Problem

When `main` goes red, every open feature PR inherits the failing check. When main recovers, nothing re-runs those PR checks. The stale `test: fail` stays on the rollup, the reconciler faithfully re-observes it and re-latches the `failing_checks` blocker, and the issue is held out of the merge gate indefinitely (proof: PAN-2683 / PR #2693 — all gates passed, `ready_for_merge=0` until a manual `gh run rerun 29414663205 --failed`). The manual re-run is exactly and entirely what needs automating.

## Proposal — level-triggered stale-check re-trigger service

A new dashboard server service (`stale-check-retrigger-service.ts`, mirroring the reconcile-service pattern) that on a poll cadence:

1. Selects Overdeck-managed candidates: `review_status` rows carrying a `failing_checks` blocker with a parseable `prUrl` (reuse `getMergeBlockerReconcileCandidates()` from `src/lib/overdeck/review-status-sync.ts:458`). Zero GitHub calls when there are no candidates.
2. Probes main run history per repo (`gh run list --branch main --limit 50 --json databaseId,workflowName,createdAt,conclusion,status,attempt,headSha`, throttled per repo) and computes per-workflow **red windows** with a pure, unit-tested classifier.
3. For each candidate PR, lists failing runs at the PR's current head and selects **poisoned runs**: `status == completed`, conclusion in `FAILING_CHECK_CONCLUSIONS`, `attempt === 1`, `createdAt` inside a *closed* red window of the same workflow.
4. Re-triggers each selected run once via `gh run rerun <id> --failed` and logs issue, PR, run id, workflow, and the red window that justified it, plus a per-tick summary count.

The re-run merges against the now-green main; when it passes, the PAN-2712 reconciler observes the changed rollup within its 10-minute cadence and clears the blocker — the loop breaks with no further coupling.

### Why level-triggered instead of a durable red→green transition event

The strike analysis asked for a "durable main red→green transition owner". Persisting a transition *event* requires new durable state and misses transitions that happen while the server is down. Instead the service re-derives the condition from GitHub on every tick: red windows come from main's run history, and idempotency comes from GitHub's own `attempt` counter. The owner is durable because its inputs are — a restart loses nothing.

### Why `attempt === 1` is the idempotency guard

After our re-run, the run's attempt becomes ≥ 2 permanently. A genuinely broken PR whose run was poisoned-by-coincidence gets exactly one re-run; when attempt 2 fails against green main, it is never touched again. This is "once per PR per transition" enforced by GitHub state, with no local ledger to corrupt or lose. Belt-and-suspenders: an in-memory attempted-run set prevents duplicate `gh run rerun` calls within one process lifetime before GitHub reflects the new attempt.

### Why red-window membership is the inherited-vs-broken guard

The issue suggests "failing run started before the fixing commit landed, and/or failure signature matches main's". Red-window membership is the first predicate made precise and per-workflow: a run that failed while main was *green* for that workflow is never touched (it is independently broken), and a run that failed while main is *still* red is not re-run yet (the window is open). Signature matching is weaker (check names vary across workflows) and is a NonGoal.

## Requirements

- **FR-1** Compute per-workflow red windows on `main` from `gh run list` history as a pure function.
- **FR-2** Select poisoned runs on candidate PRs' current heads: completed + failing conclusion + `attempt === 1` + created inside a closed red window of the same workflow.
- **FR-3** Re-trigger each selected run at most once via `gh run rerun <id> --failed`; a rerun failure (run in progress, expired, API error) is logged and skipped, never retried in a loop.
- **FR-4** Never re-run when main is still red for that workflow; never re-run a run that failed outside a red window (independently broken) or whose createdAt predates available main history.
- **FR-5** Log every re-trigger with issue, PR number, run id, workflow, and red window; log a per-tick summary `N candidates, M re-triggered, K skipped`; skip reasons logged once per run id (no per-tick spam).
- **FR-6** Service starts from `src/dashboard/server/main.ts` alongside `startMergeBlockerReconcileService()` and stops cleanly on shutdown.
- **FR-7** Troubleshooting doc describes the automation and the manual fallback (`gh run rerun <id> --failed`).
- **NFR-1** No `execSync` anywhere on the path — async `execFile` only (dashboard server rule).
- **NFR-2** Zero GitHub calls on ticks with no `failing_checks` candidates.
- **NFR-3** Bounded GitHub usage: per-repo main-probe throttle (≥3 min), per-issue evaluation throttle (≥10 min), global cap of 5 re-runs per tick.
- **NFR-4** All timer/delay tests use `vi.useFakeTimers()` (repo rule); `gh` interactions mocked via `execFile` mocks.

## NonGoals

- No failure-signature matching between PR check names and main's failing set (red-window membership is the guard).
- No new durable transition state, DB table, or state-branch record — idempotency is GitHub-derived.
- No new UI/dashboard surface for poisoned-PR visibility — structured server logs only.
- No re-run of PRs outside Overdeck management (rows without `review_status` `failing_checks` blockers).
- No changes to the PAN-2712 reconciler cadence or blocker semantics.
- No webhook (`workflow_run`) ingestion — polling only, consistent with the reconcile-service's webhook-gap rationale.
