# PAN-2988 — Make `review.status_changed` emission durable; add self-healing reconcile and a never-gated re-sync action

## Glossary

- **review_status cache** — the `review_status` table in `~/.overdeck/overdeck.db`. A rebuildable cache of the verdict.
- **Journal record** — the per-issue permanent record at `${OVERDECK_HOME}/state/<project>/records/<issue>.json`; the source of truth for the pipeline verdict.
- **Fallback verdict file** — `<workspace>/.overdeck/pipeline-verdict.json` (PAN-2583); written when the journal write fails (e.g. record-lock contention).
- **Domain event / event plane** — rows in the `events` table, appended via `getEventStore().append(...)`; the frontend Zustand store is fed by the boot snapshot plus these events only.
- **Enrichment** — `enrichReviewStatus(issueId, status)` in `src/lib/review-status-enrichment.ts`; adds tmux session names for TerminalTabs UI. Async because it shells out to tmux.
- **Read door / reconcile-on-read** — `getReviewStatusSync(issueId)` in `src/lib/review-status.ts:807`; when the journal is newer than the DB cache it overlays the journal onto the cache ("journalNewer branch").

## Background (verified 2026-07-21)

PAN-806 passed review+tests at 18:38:10 UTC. The backend was correct (`GET /api/review/PAN-806/status` showed `readyForMerge: true`), but the issue never appeared on Awaiting Merge and every gated action stayed gated. Root cause: the `review.status_changed` domain event for the transition was silently lost.

Verified evidence:

- Event log gap: last `review.status_changed` before the loss is seq 668822 (18:30:27); the next is seq 669154 (19:37:39, a manual re-POST through the write door).
- Natural experiment isolating the mechanism: during those 67 minutes, 327 events of other types appended fine — including `pipeline.test-completed`, which takes the synchronous no-enrichment branch. Only the event type routed through fire-and-forget enrichment was lost.
- `notifyPipelineSync` did fire at 18:38 (the activity entry from the same call landed, seq 668846).

The loss path, `src/dashboard/server/main.ts` (~L245–L267, search `setPipelineHandlerSync`):

```ts
case 'status_changed': {
  // Enrich async — fire-and-forget so the notifier stays sync.
  void (async () => {
    try {
      const enriched = await Effect.runPromise(enrichReviewStatus(event.issueId, event.status));
      const es = getEventStore();
      es.append({ type: 'review.status_changed', ... });
    } catch (err) {
      console.error('[pipeline] Failed to append status_changed event:', err);
    }
  })();
  return;
}
```

Three independent ways the append is lost, all silent:

1. **Enrichment hangs.** `enrichReviewStatus` → `listSessionNames()` (`src/lib/tmux.ts:970`) → `tmuxExecAsync(['list-sessions', ...])` with no timeout. A wedged tmux server leaves the promise pending forever; the `catch` never runs (a hang is not a rejection).
2. **Process exit.** A server restart between notify and enrichment completion kills the pending promise; the `catch` never runs.
3. **No reconcile.** The frontend store (`reviewStatusByIssueId`) is boot-snapshot + events only. One lost event means Awaiting Merge (`selectAwaitingMerge`), the kanban, and action gating (`useIssueActions` → `selectReviewStatus`) disagree with the canonical record until server restart.

The same fire-and-forget pattern exists in the merge-ready notifier, `main.ts` (~L478–L494, search `setMergeReadyNotifier`).

The read door already re-emits `review.approved` / `test.passed` lifecycle events on reconcile (`src/lib/review-status.ts` journalNewer branch, ~L869–L884) but does NOT call `notifyPipelineSync({ type: 'status_changed' })`, so the frontend never learns about reconciled status.

## Requirements

### Functional

- **FR-1** — A `review.status_changed` event carrying the unenriched status MUST be appended synchronously (same tick as `notifyPipelineSync`) before any enrichment is attempted. Enrichment may only produce a follow-up patch event; it must never be load-bearing for the status itself.
- **FR-2** — The enrichment path MUST be bounded: an `Effect.timeout` (constant `ENRICHMENT_TIMEOUT_MS = 5000`) around `enrichReviewStatus`, falling back to skipping the patch event on timeout. No pending promise may outlive the timeout. Applies to both `setPipelineHandlerSync` and `setMergeReadyNotifier` sites.
- **FR-3** — When `getReviewStatusSync`'s journalNewer reconcile changes the effective status, it MUST call `notifyPipelineSync({ type: 'status_changed', issueId, status: reconciled })` after the `dbUpsert(reconciled)` so server processes re-emit the drift. (In CLI/sandboxed processes the notifier has no handler and is a no-op — harmless.)
- **FR-4** — A deacon patrol sweep MUST periodically (piggyback an existing patrol tick) compare, for every issue with a journal pipeline block, the journal-derived status against the `review_status` cache row; on drift it MUST reconcile the cache and emit `review.status_changed`. This heals unread issues; FR-3 alone only heals issues someone reads.
- **FR-5** — The issue action menu RECOVER section MUST gain a "Re-sync pipeline state from canonical record" action that is never gated by pipeline state. It calls a new `POST /api/issues/:id/resync-pipeline` endpoint which: reads the canonical journal status, upserts the cache, appends `review.status_changed`, and returns the effective status. Frontend store updates via the normal event flow.

### Non-functional

- **NFR-1** — No new sync tmux calls; all tmux interaction stays on the async primitives.
- **NFR-2** — No `execSync` in server-reachable code.
- **NFR-3** — Retry/delay tests use `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()` (repo rule).

## Work items

### 1. Durable append reorder + enrichment timeout (`src/dashboard/server/main.ts`)

Traces: FR-1, FR-2.

Before (both the `status_changed` case and the `setMergeReadyNotifier` body):

```ts
void (async () => {
  try {
    const enriched = await Effect.runPromise(enrichReviewStatus(event.issueId, event.status));
    const es = getEventStore();
    es.append({ type: 'review.status_changed', timestamp: ..., payload: { issueId: event.issueId, status: enriched } } as any);
  } catch (err) { console.error(...); }
})();
```

After:

```ts
// FR-1: the unenriched status IS the event — append it synchronously so a wedged
// tmux or a restart can never lose the transition. Enrichment only patches after.
try {
  getEventStore().append({
    type: 'review.status_changed',
    timestamp: new Date().toISOString(),
    payload: { issueId: event.issueId, status: event.status },
  } as any);
} catch (err) {
  console.error('[pipeline] Failed to append status_changed event:', err);
}
void (async () => {
  try {
    const enriched = await Effect.runPromise(
      Effect.timeout(ENRICHMENT_TIMEOUT_MS)(enrichReviewStatus(event.issueId, event.status)),
    );
    getEventStore().append({ type: 'review.status_changed', ..., payload: { issueId: event.issueId, status: enriched } } as any);
  } catch {
    // Timeout or tmux failure: the unenriched event already landed; TerminalTabs
    // simply lacks session names until the next status change. Nothing to repair.
  }
})();
```

Verify the frontend reducer tolerates a second `review.status_changed` for the same issue (it does — the event log shows many repeated appends per issue; the reducer is last-write-wins). `Effect.timeout` returns a `TimeoutException` failure; the exact combinator form may be `enrichReviewStatus(...).pipe(Effect.timeout(ENRICHMENT_TIMEOUT_MS))` — match the Effect version's idiom used elsewhere in the codebase.

### 2. Read-door emission on reconcile (`src/lib/review-status.ts`)

Traces: FR-3.

In `getReviewStatusSync`, journalNewer branch, immediately after the `dbUpsert(reconciled)` try/catch (~L853), add:

```ts
// PAN-2988 FR-3: the reconcile changed the effective status — re-emit so the
// server's event plane (and every UI fed by it) converges with the journal.
notifyPipelineSync({ type: 'status_changed', issueId, status: reconciled });
```

`notifyPipelineSync` is already imported at `src/lib/review-status.ts:4`. Guard against redundant emission: only fire when the reconciled status differs from the pre-reconcile `dbStatus` in any gate field (review/test/verification/merge status or readyForMerge) — the journalNewer check alone is too loose because `updatedAt` ties can recur on every read until the DB catches up in read-only processes. Simplest correct predicate: `JSON.stringify({r: dbStatus?.reviewStatus, t: dbStatus?.testStatus, v: dbStatus?.verificationStatus, m: dbStatus?.mergeStatus, ready: dbStatus?.readyForMerge})` vs the same tuple from `reconciled`.

### 3. Periodic reconcile sweep (deacon)

Traces: FR-4.

Add `reconcileReviewStatusPlaneSweep()` in a new module `src/lib/cloister/review-status-plane-sweep.ts`: enumerate issues that have a journal pipeline block (via the record read door — `records/` on `overdeck-state`), derive the journal-side status with the same logic `getReviewStatusSync` uses (reuse `readJournalStatusSync` + the overlay), compare against `getReviewStatusFromDbSync(issueId)`, and on drift call `getReviewStatusSync(issueId)` (which reconciles and — via FR-3 — emits). Wire it into an existing deacon patrol cadence in `src/lib/cloister/deacon.ts` (e.g. every 5th cycle like deploy-patrol at `deacon.ts:2794`, or the existing stuck-verdict patrol if one exists). Keep it read-mostly: issues with no drift cost one record read each. Log one line per drift healed: `[review-status-plane] healed drift for <issue>: <field> <old> -> <new>`.

### 4. Never-gated re-sync action (server route + frontend)

Traces: FR-5.

- Route: add `POST /api/issues/:id/resync-pipeline` in `src/dashboard/server/routes/issues.ts` next to the other issue routes. Handler: `const status = getReviewStatusSync(id)` (journal-reconciled read door); if null → 404 `{ error: 'No pipeline record for <id>' }`; else `notifyPipelineSync({ type: 'status_changed', issueId: id, status })` and `jsonResponse({ status })`. The notify drives the normal `review.status_changed` append (post-FR-1, synchronous and durable).
- Frontend: in `src/dashboard/frontend/src/components/IssueActionMenu/useIssueActions.ts`, add a RECOVER-section action "Re-sync pipeline state from canonical record" that POSTs the route. It MUST NOT gate on `selectReviewStatus` or any pipeline-state selector — that is the whole point (the store may be lying). Follow the existing RECOVER-section action pattern in that file.

## Acceptance criteria

- **AC-1 (FR-1/FR-2):** With tmux made unresponsive (test double), a `status_changed` notify produces a `review.status_changed` event in the same tick, carrying the unenriched status; no promise remains pending after 5s (fake timers).
- **AC-2 (FR-3):** A verdict that lands only in the journal (fallback-file path) produces a `review.status_changed` event the next time any server code path reads that issue's status.
- **AC-3 (FR-4):** With the frontend store deliberately stale (event row deleted in test), the sweep heals the cache and emits without any read traffic.
- **AC-4 (FR-5):** The action menu shows "Re-sync pipeline state from canonical record" for an issue whose store status is stale/absent, and clicking it makes Awaiting Merge reflect the canonical record without a server restart.
- **AC-5:** `npm run typecheck`, `npm run lint`, and the new + existing unit tests pass.

## Intersecting repo rules (restated)

- Fake timers for any timeout/delay test. No real `setTimeout` waits.
- No `execSync` server-reachable. Async tmux primitives only (`sendKeysAsync` family); this change adds no tmux calls.
- Frontend store is boot-snapshot + events: do not add a polling fetch as a substitute for durable events.
