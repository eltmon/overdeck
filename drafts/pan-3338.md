# PAN-3338 — Finished plan agent reads as "still planning" once its idle signal is cleared

**Issue:** https://github.com/eltmon/overdeck/issues/3338
**Mode:** `pan plan --auto` (no interactive Q&A; decisions recorded as autoDecisions in the xBRIEF)

## Glossary

- **Read model** — the dashboard server's in-memory projection (`agentsById`, `agentRuntimeById`) built by folding domain events; what the frontend renders. Rebuilt from sources at boot by `reconstructCacheAuto()`.
- **Agents table / DB** — the `agents` table in `~/.overdeck/overdeck.db`, the authoritative runtime registry, written by `saveAgentStateSync` / `saveOverdeckAgentStateSync`.
- **state.json** — per-agent rollback file at `~/.overdeck/agents/<id>/state.json`; boot backfill source.
- **Runtime snapshot** — `AgentRuntimeSnapshot` (`activity: working|thinking|idle|stopped|waiting`), folded from `agent.*` runtime events; the Stop hook's `idle` lives here and nowhere else durable.
- **Simple mode** — the PAN-2908 plain-English projection (`src/dashboard/frontend/src/lib/simple/`): five user-facing states (`working`, `needs-you`, `ready`, `done`, `not-started`).
- **`planning_active` / `planning_done_awaiting_work`** — `PipelineState` values from `derivePipelineState` (`src/dashboard/frontend/src/lib/issuePipelineState.ts`).
- **Interactive role** — `plan` role agents and `conv-*` conversation sessions, whose steady state is sitting idle at a live prompt (agent-enrichment.ts:673).
- **Stop hook** — `sync-sources/hooks/stop-hook`; fires on every Claude Code turn end, emits `activity: idle`, and for `planning-*` agents calls `complete-planning` with `skipKill: true`.
- **complete-planning** — `completePlanningForIssue()` in `src/lib/overdeck/planning-promotion.ts:478`; the single finalize chokepoint (`pan plan finalize`, dashboard Done, Stop-hook auto-complete).
- **The flip** — the enrichment poller's reconcile that rewrites a stopped-but-tmux-alive agent to `running` in the read model (`agent-enrichment-service.ts:221-242`, plus the `agent.created` projection at :196).
- **skipKill** — finalize path that deliberately leaves the planning tmux session alive after completion so the operator can inspect it.

## Problem

A plan agent that finalized hours ago, with its tmux session still alive, renders in simple mode as **"Planning — The agent is breaking this down into tasks"** with no Start work button. Three signals disagree about the same agent, and the two process-derived ones drown the honest durable one:

1. **The finalize-time stop-marking never reaches the read model.** `completePlanningForIssue` marks the planning agent `status: 'stopped'` via `saveAgentStateSync` (planning-promotion.ts:566-575). `saveAgentStateSync` (src/lib/agents/agent-state.ts:360-384) writes the DB + state.json but emits **no** `agent.status_changed` event, so the read model keeps the spawn-time `'running'` forever. This is the DB-says-stopped / read-model-says-live disagreement the issue names.
2. **The poller flip entrenches the lie.** The enrichment poller (`agent-enrichment-service.ts:221-242`) sees DB `stopped` + live tmux and emits `agent.status_changed('running', hasLiveTmuxSession: true)` once per server lifetime; its `agent.created` projection (:196) applies the same forced `'running'`. For interactive roles, stopped-but-alive is the deliberate post-finalize steady state (skipKill), not staleness.
3. **`derivePipelineState` keys `planning_active` on the (lied-about) agent status** (`issuePipelineState.ts:65`: `if (agentRunning && agent?.role === 'plan') return 'planning_active'`) — never on whether a plan exists.
4. **The one correct display path is ephemeral.** Commit `64e8ce75bc` made simple mode project "The plan is ready" from `hasPlan` + an `agentTurnEnded` pending-input kind — but that kind is only emitted while `runtimeState?.state === 'idle'` (agent-enrichment.ts:674), and the idle activity is held only in the runtime snapshot. Boot reconstruction (`reconstruct-cache.ts:107-112`) derives activity from status (`running→working`, `stopped→stopped`), discarding the Stop-hook idle; a finished plan agent never fires another Stop hook, so after any dashboard restart the `agentTurnEnded` signal is gone for good and the page reverts to raw `planning_active`.

Verified live behavior chain: finalize → DB `stopped` (no event) → poller flip → read model `running` → `planning_active` → "breaking this down into tasks". Correct only in the window between finalize and the next dashboard restart.

## Decisions (made in this doc — no judgment calls left to the implementer)

- **D1 — The durable turn-end signal is the finalize-time stopped status; route it into the read model.** The issue offers two options: make the idle/turn-end signal durable, or stop deriving `planning_active` from process liveness once a plan exists. We take the first, interpreted precisely: the Stop-hook `idle` *activity* stays ephemeral, but the finalize-time **`stopped` status** — already written durably by complete-planning — must (a) be emitted as an event so the read model converges, and (b) stop being overwritten by the poller flip. This fixes AC1 and AC3 at the root with no new durable state. Making the ephemeral idle activity durable (event-log folding at boot, sidecar files) would not fix AC3, adds machinery, and is unnecessary once the status is honest.
- **D2 — Scope the flip removal to interactive roles** (`role === 'plan'` or id prefix `conv-`), the exact predicate already used at agent-enrichment.ts:673. Work/review/test/strike agents keep the PAN-1419 reconcile: their stopped-but-alive state is transitional (crash recovery) rather than a deliberate steady state, and changing it is a separate audit. The suspected related victim (standby work agents reading as `running`) is a follow-up, recorded in NonGoals.
- **D3 — Do NOT gate `planning_active` on `!hasPlan`.** Replanning is a real flow: a plan agent runs while a spec already exists (deacon-merge.ts:244-248 defers merges while a planning agent runs). Keying plan-ready purely on `hasPlan` would mislabel an actively replanning agent as "The plan is ready — Start work", the same class of lie this issue fixes. The durable-status fix preserves replanning correctness: a replan agent's status is legitimately `running`.
- **D4 — Move the stop-marking after the finalize gates.** Today the stop-marking runs *before* the PRD gate and spec promotion (planning-promotion.ts:566-575 vs :589+). A gate failure (422) leaves the agent durably stopped while it is actually still mid-planning — pre-existing, but once the read model honors the stopped status (this PRD) that premature stop becomes user-visible as a false "The plan is ready". The stop-marking must happen only after promotion succeeds, next to the existing `planning.sync` event (planning-promotion.ts:763-774).
- **D5 — Accept canonical `'planned'` in the awaiting-work gate.** `derivePipelineState` line 66 gates on `todo|backlog`. The overdeck stage machine has a real `planned` stage (src/lib/overdeck/issues.ts:31-44, transitions at :96-108); the GitHub label mapping never emits it (src/core/state-mapping.ts:296-349), so this is cheap insurance for the stage-machine/Linear paths, not a behavior change on the GitHub path.

## Requirements

### Functional

- **FR-1** — When complete-planning successfully finalizes, it marks the planning agent stopped AND appends `agent.status_changed` with `status: 'stopped'`, the true `previousStatus`, and an honestly computed `hasLiveTmuxSession` (live on the skipKill path), so the read model converges to the durable truth and the reducer's PAN-2633 gate preserves the pending-input payload (event-reducers.ts, `agent.status_changed` case, sessionAlive gate).
- **FR-2** — The enrichment poller never rewrites an interactive-role agent (plan, `conv-*`) from `stopped` to `running` — neither in the reconcile block nor in the `agent.created` projection. Non-interactive roles keep the existing reconcile.
- **FR-3** — A failed finalize (PRD gate 422, quality-lint rejection, promotion failure) leaves the planning agent `running` and emits no stopped event.
- **FR-4** — `derivePipelineState` returns `planning_done_awaiting_work` when no agent is running, a plan exists, and the canonical state is `todo`, `backlog`, or `planned`; it returns `planning_active` for a running plan agent regardless of `hasPlan` (replan preserved, per D3).
- **FR-5** — Simple mode renders a finalized issue whose plan agent is stopped and carries no pending-input kinds as `needs-you` / "The plan is ready" with primary action "Start work", and buckets it into simple-home needs-you.
- **FR-6** — Simple mode keeps rendering a running plan agent with no written plan as `working` / "Planning" ("The agent is breaking this down into tasks.").

### Non-functional

- **NFR-1** — No new durable state, no DB schema change, no new event types. The fix routes existing durable facts through the existing event door.
- **NFR-2** — The stopped→running reconcile behavior for work/review/test/strike agents is byte-for-byte unchanged.
- **NFR-3** — The stopped-but-session-alive contract is documented in `docs/AGENT-STATE-PLANES.md`: `status` is the durable record, `hasLiveTmuxSession` is liveness, and interactive roles are never auto-flipped (resolver named: `shouldResurrectStoppedAgent` in `agent-enrichment-service.ts`).

### WI-2 — `poller-stops-resurrecting-interactive-agents`: honor the durable stopped status for interactive roles + document the contract

**Files:** `src/dashboard/server/services/agent-enrichment-service.ts`, `src/lib/agent-enrichment.ts`, `src/dashboard/server/services/__tests__/agent-enrichment-service.test.ts`, `docs/AGENT-STATE-PLANES.md`

```ts
/**
 * Interactive roles idle at a live prompt as their steady state — plan agents
 * after finalize (skipKill) and conversation sessions. For these,
 * stopped-but-session-alive is deliberate, never stale (PAN-3338).
 */
export function isInteractiveRoleAgent(agentId: string, role?: string): boolean {
  return role === 'plan' || agentId.startsWith('conv-')
}
```

Rewrite agent-enrichment.ts:673 to use it: `const isInteractiveRole = isInteractiveRoleAgent(agentId, role)`.

2. In `agent-enrichment-service.ts`, add one exported pure decision and use it at BOTH flip sites:

```ts
/**
 * PAN-3338 — should the poller rewrite this stopped agent to 'running' on tmux
 * liveness alone? For interactive roles the durable stopped status is the
 * deliberate post-completion state, so it must stand; other roles keep the
 * PAN-1419 crash-recovery reconcile.
 */
export function shouldResurrectStoppedAgent(
  agentId: string,
  role: string | undefined,
  status: string,
  tmuxActive: boolean,
): boolean {
  if (!tmuxActive || status !== 'stopped') return false
  return !isInteractiveRoleAgent(agentId, role)
}
```
