# PAN-3341 — Pipeline board shows stale phase for merged-but-never-closed-out issues

## Glossary

- **Pipeline membership / bucket** — the canonical per-issue verdict from
  `resolvePipelineMembership()` (`src/lib/pipeline-membership.ts:99`), computed
  from durable lenses (tracker open/closed, open PR, merged PR, branch
  containment in main, phase label, xBRIEF spec). Buckets: `in_flight`,
  `post_merge_limbo`, `planned_backlog`, `zombie_pr`, `clean_terminal`.
- **`post_merge_limbo`** — "merged but never closed out; run close-out"
  (`src/lib/pipeline-membership.ts:144,154`). An open issue with a merged PR,
  or whose convention branch's unique commits are contained in main.
- **`clean_terminal`** — not in the pipeline. Two sub-cases, distinguished by
  `membership.lenses.L3_issueOpen`: tracker-closed (issue done/canceled) vs.
  open backlog never started (`src/lib/pipeline-membership.ts:127-137,173`).
- **Membership snapshot** — the server-side per-project cache of membership
  verdicts, refreshed at most every 5 min
  (`src/dashboard/server/services/pipeline-membership.ts:12-13`,
  `PIPELINE_MEMBERSHIP_SNAPSHOT_TTL_MS`). Read without scheduling work via
  `readPipelineMembershipSnapshotsForProjects()`
  (`src/dashboard/server/services/pipeline-membership.ts:114`).
- **Resource discovery / `stateLabel`** — the Command Deck project-tree feed
  (`GET /api/issues/resource-allocated`,
  `src/lib/overdeck/issue-reads.ts:321`). Each row carries a human-readable
  `stateLabel` derived by `deriveStateLabel()`
  (`src/dashboard/server/services/resource-discovery.ts:205`) — values today:
  `In Review`, `In Progress`, `Done`, `Closed`, `Suspended`, `Planning`,
  `Has Context`, `Allocated`, `Idle`.
- **`getPipelineIssuePhase`** — the frontend lane classifier
  (`src/dashboard/frontend/src/lib/pipeline-state.ts:127`) used by both the
  main Pipeline board (`PipelineView.tsx:335`) and the Command Deck pipeline
  section (`ProjectOverview.tsx:95` via `bucketFeaturePhase`).
- **Issue action registry** — `src/dashboard/frontend/src/lib/issueActions.ts`;
  the single registry mapping every issue action to a `pan` verb + REST
  endpoint. `closeOut` → `POST /api/issues/:id/close-out`
  (`issueActions.ts:626`).

## Problem

A merged, tracker-Done issue that never went through `pan close` renders on
the dashboard as a pre-work phase. Observed 2026-07-30 on the MYN Command
Deck: MIN-852, MIN-861, MIN-882 all showed **Planning** despite being merged
to main and Done in Linear for a week-plus.

Root cause, verified against the code:

1. `deriveStateLabel()` (`resource-discovery.ts:205-219`) derives the tree's
   phase chip from the tracker-row cache and local resource artifacts only.
   When the tracker row has aged out of the issue-service sync window (the
   exact case the PAN-3337 title-fallback comment at
   `resource-discovery.ts:719-722` describes), `trackerState` is `null`, so
   the function falls through to artifact heuristics:
   `hasPrd && !hasState` → `'Planning'` (line 215), workspace/branch →
   `'Allocated'` (line 217). It never consults git merge state or the
   canonical membership verdict — even though the caller already has that
   verdict in hand (`resource-discovery.ts:746`).
2. `getPipelineIssuePhase()` (`pipeline-state.ts:127`) deliberately ignores
   the server membership verdict for lane assignment — a contract locked in
   by two tests: `pipeline-state.test.ts:38-53` ("does not use server
   membership as a lane-assignment signal") and
   `PipelineView.test.tsx:135-150` (an issue with
   `pipelineMembership.bucket: 'post_merge_limbo'` and `state: 'in_review'`
   is asserted to render in the **review** lane). Those tests encode the bug:
   the stale record outranks tracker + git truth.

## Proposal

Apply the single-source-of-truth tenet to the read door: reconcile the
displayed phase against the canonical membership verdict (tracker + forge +
git lenses) at the two derivation points, and light up the existing
close-out action on limbo rows. No new gather machinery — the membership
snapshot is already computed, already attached to both feeds
(`pipelineBucket` on resource-allocated rows, `resource-discovery.ts:779`;
`pipelineMembership` on `/api/issues` DTOs, `routes/issues.ts:246-264`).

### Decision D1 — membership reconciles the tree state label

`deriveStateLabel()` gains an optional `membership?: PipelineMembership`
parameter (the caller at `resource-discovery.ts:746-749` already holds it).
Two new checks at the **top** of the function, before the `readyForMerge`
check (a stale `readyForMerge` must not outrank a merged PR):

```ts
function deriveStateLabel(
  issue: MutableResourceIssue,
  hasTmux: boolean,
  hasFreshHeartbeat: boolean,
  membership?: PipelineMembership,   // NEW
): string {
  // PAN-3341: the canonical membership verdict (tracker + forge + git lenses)
  // outranks local resource artifacts, so a landed issue can never render as
  // a pre-work phase when its tracker row has aged out of the sync window.
  if (membership?.bucket === 'post_merge_limbo') return 'Merged — Needs Close-Out';
  if (membership?.bucket === 'clean_terminal' && membership.lenses.L3_issueOpen === false) {
    return hasTmux ? 'Closed' : 'Done';
  }
  // …existing checks unchanged…
}
```

The `L3_issueOpen === false` guard is required: `clean_terminal` also covers
"open issue, no branch, no PR — backlog, never started"
(`pipeline-membership.ts:173`), which must NOT render as Done (e.g. a backlog
issue with a live planning tmux session).

When membership is unavailable (`membership` undefined for the issue), the
function falls through to today's artifact heuristics — never guess "merged"
without the canonical verdict.

### Decision D2 — limbo maps to the existing ship lane, no new lane

`getPipelineIssuePhase()` returns `'ship'` when
`issue.pipelineMembership?.available === true` and the bucket is
`post_merge_limbo`, checked after the terminal-state check and before the
`mergeStatus` block. The `available === true` guard matters: the unavailable
sentinel (`unavailablePipelineMembership()`,
`services/pipeline-membership.ts:222-224`) reports `bucket: 'clean_terminal'`
and must not influence lanes.

No new lane is added. The issue body allows "done (or explicitly merged —
needs close-out)"; the ship lane is where landed work already lives, and a
new lane would mean new glyphs, URL filter params, and PhaseHeader styles
for zero additional information — the row label carries the close-out
signal.

The two tests that lock the old contract are updated to the narrowed
contract: membership is ignored for lane assignment **except**
`post_merge_limbo`, which forces the ship lane.

### Decision D3 — close-out affordance via the existing action registry

`useIssueActions.ts:330` extends `isMerged`:

```ts
// before
isMerged: reviewStatus?.mergeStatus === 'merged' || issue?.mergeStatus === 'merged',
// after
isMerged: reviewStatus?.mergeStatus === 'merged' || issue?.mergeStatus === 'merged'
  || issue?.pipelineMembership?.bucket === 'post_merge_limbo',
```

That single change: (a) enables the existing `closeOut` registry action
(`canCloseOut`, `issueActions.ts:563-566`) on limbo rows, and (b) routes the
row to the `MERGED` phase (`derivePipelineState` returns `'merged'` when
`input.isMerged === true`, `issuePipelineState.ts:48-55`;
`deriveIssueActionPhase` maps `merged` → `MERGED`, `issueActions.ts:660-710`),
making **Close out** the phase-primary action in the existing context menu
(`FeatureItem.tsx:733`). No new button, endpoint, or dialog — the registry
stays the single action source.

### Decision D4 — out of scope

`zombie_pr` (closed issue, open PR) rendering is unchanged. Membership
unavailable → today's behavior. No change to the tree inclusion filter
(`resource-discovery.ts:737-744`): tracker-Done merged issues with no live
resources correctly drop out of the tree.

## Requirements

- **FR-1** — A resource-allocated issue whose membership bucket is
  `post_merge_limbo` renders `stateLabel: 'Merged — Needs Close-Out'` from
  `GET /api/issues/resource-allocated`, regardless of stale PRD/workspace/
  state artifacts.
- **FR-2** — A resource-allocated issue whose membership bucket is
  `clean_terminal` with `lenses.L3_issueOpen === false` renders `'Done'` (or
  `'Closed'` when a tmux session survives), never `'Planning'`/`'Allocated'`.
- **FR-3** — An open backlog issue with no branch/PR (`clean_terminal`,
  `L3_issueOpen === true`) keeps its current label (no false "Done").
- **FR-4** — `getPipelineIssuePhase` returns `'ship'` for an issue whose
  attached membership is available and `post_merge_limbo`, even when the
  stored state says `in_review`/`in_progress` or a plan exists.
- **FR-5** — Membership buckets other than `post_merge_limbo` do not change
  lane assignment; unavailable membership does not change lane assignment.
- **FR-6** — The Close out action is enabled and phase-primary (MERGED) on
  issue rows whose store issue carries `pipelineMembership.bucket ===
  'post_merge_limbo'`, via the existing registry entry and
  `POST /api/issues/:id/close-out`.
- **FR-7** — The Command Deck tree row and ProjectOverview pipeline section
  present `'Merged — Needs Close-Out'` as done-work-needing-ceremony (not
  with the planning tone, not bucketed into the plan lane).
- **NFR-1** — No new tracker/git gather work is introduced on any request
  path; all reconciliation reads the existing membership snapshot.
- **NFR-2** — Docs name the new label and the reconciliation contract
  (docs/PIPELINE-MEMBERSHIP.md).
