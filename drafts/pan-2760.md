# PAN-2760 — Make crew create and delete discoverable in Tiered Execution settings

- **Issue:** https://github.com/eltmon/overdeck/issues/2760
- **Status:** planned (interactive planning session, 2026-07-16; operator approved the interactive mockup)
- **Approved interaction spec:** `drafts/pan-2760-mockup.html` on `overdeck-state` (disk: `${OVERDECK_HOME}/state/panopticon-cli/drafts/pan-2760-mockup.html`). Also published during planning at https://claude.ai/code/artifact/e0cfb789-2be7-4144-bed4-65d335552519. Work item W3 commits it into the repo at `docs/design/mockups/crew-create-delete-pan-2760.html`.

## Glossary

- **Board** — the "Who handles each difficulty?" five-column grid in `TieredExecutionSection.tsx` (one `<select>` per difficulty). Each select ends with the `+ new crew…` option, today the only create entry point.
- **Roster** — the "The crews" list of `CrewRow` components under the board.
- **Crew** — form-only editing shape over the YAML tier table (`tiered-crews.ts`). Crew `id` is transient; tier names are derived from owned difficulties on save.
- **Create-and-assign invariant** — `serializeCrews` (`src/dashboard/frontend/src/components/Settings/sections/tiered-crews.ts:112-114`) silently drops any crew owning zero difficulties, and the section re-derives all crews from config on every render (`importCrews`, called at `TieredExecutionSection.tsx:116`). Therefore a crew that owns nothing cannot persist; creation must assign a difficulty in the same gesture.
- **Final-difficulty guard** — reassigning the last difficulty of a crew that holds kind overrides is blocked (`TieredExecutionSection.tsx:170-177`; serializer throw at `tiered-crews.ts:113`).
- **Hand-off remove** — the approved delete flow: removing a crew asks which other crew inherits its difficulties, then reassigns and removes in one `writeCrews` call.

## Problem (from the issue, verified in code)

Create, update, and delete all exist but are unfindable:

- Create is only `+ new crew…` at the bottom of each board dropdown (`TieredExecutionSection.tsx:349`, handled at `:179-189`). Nothing near the roster suggests crews can be made; the empty state teaches the trick in prose (`:382`).
- Delete is the `Remove crew` button inside the **expanded** `CrewRow` body (`CrewRow.tsx:75-79`), so it exists only after discovering rows expand. Worse — verified during planning — that button can never succeed on a saved crew: every persisted crew owns ≥1 difficulty (zero-difficulty crews are dropped on save), and the button refuses while any difficulty is owned. Its only reachable outputs are its two error messages. The real delete gesture today is reassigning difficulties on the board until the crew evaporates.
- This is inherited from the approved PAN-2684 mockup (`docs/design/mockups/tiered-execution-redesign-pan-2684.html`), which encodes the same pattern. The mockup is the spec, so it must be updated/superseded (issue AC 7).

## Planning Q&A

**Q1 (AskUserQuestion): Which create affordance should the "Add crew" button use?**
Options offered: (1, recommended) create + pick difficulty — inline prompt preserving the create-and-assign invariant; (2) unassigned draft crew — requires a new local draft-state layer since config cannot represent ownerless crews, draft vanishes on navigation; (3) signpost only — button that highlights the board dropdowns.
**Operator answer:** asked for an interactive mockup of option 1 before deciding ("use claude artifacts to make me a mockup of what you have in mind").

**Q2 (mockup review):** Mockup published showing option 1 create plus a hand-off remove flow (× remove on the collapsed row opens "give its difficulties to: <other crew>"), with the finding that the existing Remove button is a dead end on every saved crew.
**Operator answer:** "yes I like all of this, lets go with this." — full approval of both flows as mocked.

## Decisions

- **D1 — Create = option 1 (create + pick difficulty).** "+ Add crew" beside the roster header opens an inline prompt: "The new crew starts on Haiku 4.5. Which difficulty does it take over?" with five difficulty buttons, each labeled with the current owner. Picking one runs the exact create path the board uses today. No draft-crew state, no new validation path; the create-and-assign invariant holds by construction. (Resolves the issue's "design decision this needs".)
- **D2 — Delete = hand-off remove.** "× remove" on every collapsed row. On a crew owning difficulties it opens an inline heir prompt listing every other crew (label + blended $/1M); choosing one reassigns the owned difficulties to the heir and removes the crew in one `writeCrews` call. The expanded body's `Remove crew` button routes through the same flow. This supersedes the always-refusing behavior; the old "Assign these difficulties to another crew before removing it." dead-end message disappears (the hand-off prompt IS that reassignment).
- **D3 — Guards preserved verbatim.** Kind-override removal block keeps the existing message ("Move or remove these kind overrides before removing this crew."); the final-difficulty reassignment guard keeps its message; the serializer throw at `tiered-crews.ts:113` is untouched. New guard: the last remaining crew cannot be removed (message: "This is the only crew, and every difficulty needs one. Add another crew first — or turn tiered execution off.").
- **D4 — Remove-flow state lives in the parent.** `TieredExecutionSection` owns `removePromptCrewId` and the per-crew remove error; `CrewRow` gains an `onRequestRemove` callback and loses its local `removeError` state. The hand-off prompt and error render as siblings directly beneath the owning row.
- **D5 — Board `+ new crew…` stays** (issue's no-loss requirement). First-crew-owns-all behavior stays: from zero crews, create takes all five difficulties with no prompt (matches `TieredExecutionSection.tsx:185-187`).
- **D6 — Mockup supersession, not rewrite.** The approved PAN-2760 mockup is committed as `docs/design/mockups/crew-create-delete-pan-2760.html`; the PAN-2684 mockup gets a one-line note that its roster create/delete affordances are superseded by it. The PAN-2684 interactive JS is NOT reworked.
- **D7 — Expandability cue.** Collapsed rows get a hover/focus background highlight and a small "edit" cue next to the caret (visible on hover/focus only), so the disclosure reads as interactive.

## Requirements

- **FR-1** — A new crew can be created from the roster without opening any board dropdown, via "+ Add crew" and an inline difficulty prompt; the created crew starts on `DEFAULT_MODEL` (Haiku 4.5), is assigned the chosen difficulty, and renders expanded.
- **FR-2** — With zero crews, the empty state carries its own "+ Add crew" button; the first crew owns all five difficulties (no prompt), and the prose "Choose '+ new crew…' on the board" empty state is replaced.
- **FR-3** — A crew can be removed from its collapsed row: "× remove" opens a hand-off prompt; picking an heir reassigns the crew's difficulties and removes it in a single settings write. The expanded-body Remove button uses the same flow.
- **FR-4** — Guards: kind-override crews can't be removed (existing message); the sole remaining crew can't be removed (new message); the difficulty prompt disables a difficulty whose owner would be stranded by the final-difficulty guard, with the existing message.
- **FR-5** — The board's `+ new crew…` continues to create and assign in one gesture (no-loss).
- **FR-6** — Collapsed rows visibly read as expandable (hover/focus highlight + "edit" cue).
- **FR-7** — `docs/TIERED-EXECUTION.md` Settings UI section (currently lines 64-74) describes the create and delete affordances and names the mockup files as the interaction reference.
- **FR-8** — The PAN-2760 mockup is committed to `docs/design/mockups/` and the PAN-2684 mockup carries a supersession note (issue AC 7).
- **NFR-1** — New crews and defaults are never a frontier model; `DEFAULT_MODEL` stays `claude-haiku-4-5` (guarded by the existing frontier-default test).
- **NFR-2** — No schema or persistence change: `serializeCrews`/`importCrews` in `tiered-crews.ts` are not modified; all changes are presentation-layer in `TieredExecutionSection.tsx`/`CrewRow.tsx`.
- **NFR-3** — Existing behavior tests keep passing except the one that locks the superseded dead-end remove behavior (`__tests__/TieredExecutionSection.test.tsx:162` "blocks removal while a crew owns difficulties…"), which is rewritten to lock the hand-off flow.

### W2 — Collapsed-row hand-off remove + expandability cue (frontend) — traces FR-3, FR-4, FR-6, NFR-3

**Files:** `src/dashboard/frontend/src/components/Settings/sections/CrewRow.tsx`, `src/dashboard/frontend/src/components/Settings/sections/TieredExecutionSection.tsx`, `__tests__/TieredExecutionSection.test.tsx`.

Steps:

1. `TieredExecutionSection` owns the flow: add `const [removePromptCrewId, setRemovePromptCrewId] = useState<string | null>(null);` and `const [removeError, setRemoveError] = useState<{ crewId: string; message: string } | null>(null);`

   ```tsx
   const handleRequestRemove = (crewId: string) => {
     setRemoveError(null);
     setRemovePromptCrewId(null);
     const kinds = Object.entries(byKind).filter(([, id]) => id === crewId).map(([kind]) => kind);
     const owned = DIFFICULTIES.filter((difficulty) => assign[difficulty] === crewId);
     if (kinds.length > 0) { setRemoveError({ crewId, message: 'Move or remove these kind overrides before removing this crew.' }); return; }
     if (crews.length === 1) { setRemoveError({ crewId, message: 'This is the only crew, and every difficulty needs one. Add another crew first — or turn tiered execution off.' }); return; }
     if (owned.length === 0) { writeCrews(crews.filter((entry) => entry.id !== crewId), assign); return; }
     setRemovePromptCrewId(crewId);
   };
   const handleRemoveWithHeir = (crewId: string, heirId: string) => {
     const nextAssign = { ...assign };
     for (const difficulty of DIFFICULTIES) if (nextAssign[difficulty] === crewId) nextAssign[difficulty] = heirId;
     setRemovePromptCrewId(null);
     writeCrews(crews.filter((entry) => entry.id !== crewId), nextAssign);
   };
   ```
