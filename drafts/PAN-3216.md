# PRD: PAN-3216 — Briefing "Troubled agents" line must count the troubled gate, not accumulated failure history

**Issue:** https://github.com/eltmon/overdeck/issues/3216 (filed by Flywheel RUN-73)

## Glossary

- **Briefing** — the "Working Inside Overdeck" markdown injected at the top of every agent session and printed by `pan briefing`. Assembled by `assembleLiveBriefingMarkdown()` in `src/lib/briefing-assembler.ts`.
- **Fleet-health lines** — the five `- <label>: <count>` bullets rendered under `## Current Workspace` by `renderDashboardWorkspaceSection()` (`src/lib/briefing-assembler.ts:148-188`) when a dashboard snapshot is available.
- **Troubled gate** — the per-agent `troubled: true` flag (`AgentSnapshot.troubled`, `packages/contracts/src/types.ts:328`). A precise lifecycle gate: it quarantines the agent from auto-resume (`src/lib/agents/resume.ts:133-153`) and is cleared only by `pan untroubled` (`src/cli/commands/untroubled.ts`) after the crash cause is investigated.
- **`consecutiveFailures`** — an accumulated failure counter on the agent record (`packages/contracts/src/types.ts:330`). Incremented on any recorded failure, including routine `orphaned: tmux session missing (reconcile)` events from `reconcileAgentLiveness` — the patrol working correctly, not distress. Cleared alongside the gate by `pan untroubled`.
- **DashboardSnapshot** — the read-model snapshot type (`packages/contracts/src/types.ts:525-542`) passed into the briefing by `src/dashboard/server/services/session-context-writer.ts:57`.

## Problem

The fleet-health line labelled `Troubled agents` does not count troubled agents. At `src/lib/briefing-assembler.ts:151`:

```ts
const troubledAgents = snapshot.agents.filter((agent) => agent.troubled || (agent.consecutiveFailures ?? 0) > 0);
```

rendered at `src/lib/briefing-assembler.ts:165` as:

```ts
`- Troubled agents: ${troubledAgents.length}`,
```

The label says "troubled" (a gate with exact semantics); the filter says "troubled **or** has ever recorded a consecutive failure". At filing time the gate held **1** agent while the line reported **60** — 57 of them routine `orphaned: tmux session missing (reconcile)` records on stopped agents, i.e. normal end-of-life reconciliation.

The briefing is the first situational-awareness surface every session and terminal-only operator reads. A permanently-inflated crisis number invites investigation of a non-problem and teaches readers to discount the whole panel, including the lines that are accurate. Flywheel RUN-73 carried `Troubled agents: 60` as a standing anomaly across four briefings before checking it; there was never anything to act on.

## Proposal (chosen approach)

**Count what the label says.** Narrow the filter to `agent.troubled` alone, matching the precise meaning the term already has everywhere else in the system (the resume gate, `pan untroubled`, the dashboard quarantine). This is option 1 of the issue's two suggested fixes, and the one the issue recommends.

The broader "agents with recorded failures" set is deliberately **not** surfaced as a second line: 57/60 of that population is reconciliation noise on stopped agents with no operator action attached, and reintroducing a non-actionable count defeats the purpose of the fix. The dashboard's per-agent failure displays (`ResourceCard.tsx`, `HealthDashboard.tsx`, `DeaconActivityView.tsx`) already show `consecutiveFailures` in context where an operator can act on it.

### Before / after

`src/lib/briefing-assembler.ts:151` — before:

```ts
const troubledAgents = snapshot.agents.filter((agent) => agent.troubled || (agent.consecutiveFailures ?? 0) > 0);
```

after:

```ts
const troubledAgents = snapshot.agents.filter((agent) => agent.troubled === true);
```

No other code changes. The variable name, the render line at :165, and the other four fleet-health lines are untouched.

### Regression test

New file `tests/unit/lib/briefing-assembler.test.ts`. The snapshot code path of `assembleLiveBriefingMarkdown({ snapshot })` is pure — with a snapshot supplied it performs no filesystem access (`src/lib/briefing-assembler.ts:36-37` skips workspace detection; `readStatusByIssue` reads `snapshot.memory` only), so the test needs no fs mocking. Build a minimal `DashboardSnapshot`-shaped object (fields required by the type: `sequence`, `agents`, `specialists`, `reviewStatuses`, `issues`, `timestamp`; each agent needs at minimum `id`, `issueId`, `status`) and cast `as DashboardSnapshot`. `AgentStatus` literals are `["starting", "running", "stopped", "error", "unknown"]` (`packages/contracts/src/types.ts:50`).

Test cases:

1. **Given** a snapshot with 1 agent `troubled: true` and 3 agents with `consecutiveFailures: 1..3` but `troubled` unset (status `stopped`, mirroring the reconciliation population), **when** the briefing is assembled, **then** the output contains exactly `- Troubled agents: 1`.
2. **Given** a snapshot with no troubled agents and several agents with `consecutiveFailures > 0`, **then** the output contains `- Troubled agents: 0`.

## Requirements

- **FR-1** — The briefing fleet-health line labelled `Troubled agents` MUST count only agents whose `troubled` flag is `true`, so the number equals the population `pan untroubled` can clear.
- **FR-2** — A regression test MUST pin FR-1: agents with `consecutiveFailures > 0` but no `troubled` flag MUST NOT be counted in the `Troubled agents` line.
- **NFR-1** — No other fleet-health line (`Running agents`, `Active issues with agents`, `Paused gates`, `Failed verification/review states`) may change behavior.
- **NFR-2** — No behavioral change to any gate, untroubled-clear path, or per-agent failure display that intentionally uses the broader `troubled || consecutiveFailures > 0` set (`src/lib/cloister/feedback-target.ts:182`, `src/dashboard/server/routes/agents/spawn.ts:170`, `src/dashboard/server/routes/agents/lifecycle-stop.ts:347`, `src/cli/commands/untroubled.ts:26`). Those sites use the broad set to *clear* failure state, which is correct and out of scope.

## Non-goals

- Renaming the `Troubled agents` label or adding a second "agents with recorded failures" line (option 2 from the issue — rejected, see Proposal).
- Changing any other surface that consumes `consecutiveFailures` (frontend warning highlights, health endpoints, gate/untroubled logic).
- Cleaning up the 59 stale `consecutiveFailures` rows in the agents table — they are historical records on stopped agents and harmless once nothing presents them as distress.
- Bootstrapping `.pan/context/codebase/` (absent at planning time) — out of proportion for a one-line filter fix; recorded as an auto decision.
