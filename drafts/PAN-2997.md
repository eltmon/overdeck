# PAN-2997 — Surface Linear MCP OAuth as a global intervention and wake blocked agents after re-auth

**Issue:** https://github.com/eltmon/overdeck/issues/2997
**Mode:** `pan plan --auto` (all decisions recorded in §Decisions; no interactive Q&A)

## Glossary

- **Linear MCP** — the agent-facing MCP server `https://mcp.linear.app/mcp` configured in `~/.claude/mcp.json` and copied into each workspace (`src/lib/workspace-manager/migration.ts:93-108`). Tools are named `mcp__linear__*`. This is NOT the Overdeck tracker client (`src/lib/tracker/linear.ts`, API-key `@linear/sdk`), which is out of scope.
- **`mcp__linear__authenticate` / `mcp__linear__complete_authentication`** — Claude Code harness meta-tools exposed when an MCP server requires OAuth. `authenticate` returns an authorization URL; after the operator authorizes in a browser, `complete_authentication` takes the localhost callback URL and finishes the flow. On remote sessions the callback page fails to load but its URL is still valid (the "localhost callback fallback").
- **Heartbeat ingestion (PAN-800)** — the token-gated route `POST /api/agents/:id/heartbeat` (`src/dashboard/server/routes/agents/runtime-events.ts:90`). Hook scripts POST typed bodies (`{kind: ...}`); `bodyToEvent` (`src/dashboard/server/services/agent-event-utils.ts:17`) maps them to DomainEvents, Schema-validates them, and `AgentStateService.emit` durably appends them via the EventStore (`src/dashboard/server/event-store.ts`).
- **`pan_emit_event`** — bash helper in `sync-sources/hooks/pan-hook-lib.sh` that POSTs a heartbeat body with the internal token and buffers to `pending-events.jsonl` on network failure. Every Overdeck hook uses it; the new hook must too.
- **Event store / read door / write door** — canonical state discipline: one resolver (read door) and one writer (write door) per domain; the SQLite events table is the durable runtime-plane store.
- **`messageAgent`** — `src/lib/agents/messaging.ts:100`. Sanctioned message-delivery wrapper over `deliverAgentMessage` (`src/lib/agents/delivery.ts:204`). For stopped agents it auto-resumes via `decideResumeGate` or queues mail in `<agentDir>/mail/` when a resume gate (paused/troubled/stoppedByUser) blocks. The wake path must use this, never raw tmux.
- **Intervention lifecycle** — the fold concept introduced here: the span from the first `linear_mcp_auth.required` event to the next `linear_mcp_auth.healthy` event. There is at most one open lifecycle; that is the dedup mechanism.
- **Codex auth banner** — the existing pattern this issue reuses: `src/lib/codex-auth.ts` + `src/dashboard/server/routes/codex-auth.ts` + `src/dashboard/frontend/src/components/CodexAuthBanner.tsx` (mounted at `src/dashboard/frontend/src/App/AppChrome.tsx:88`).

## Problem

When a work/plan agent needs the Linear MCP server but its OAuth session is missing or expired, the agent can only emit an authorization URL into its own transcript and block. The operator may not have that conversation open, so the request is missed and stuck-agent checks repeatedly report inactivity without exposing the action needed (observed on MIN-852, which sat blocked on interactive Linear MCP OAuth across repeated status checks — `docs/FLYWHEEL-STATE.md:5901`). Overdeck already solved the equivalent problem for GPT/Codex OAuth (#913, #1067): surface one prominent top-of-dashboard intervention instead of burying it in a transcript. Linear MCP OAuth gets the same treatment, plus the piece the Codex flow never had: after re-auth, every blocked agent is woken through the delivery door and told to re-check and resume.

## Proposal

Five cooperating pieces, all additive:

1. **Structured detection (hook).** A new PostToolUse hook `linear-mcp-auth-hook` (matcher `mcp__linear__.*`) inspects the tool result of every Linear MCP call. On `authenticate` it extracts the authorization URL from the tool response; on auth-error results it flags the requirement without a URL; on `complete_authentication` success — or on any successful Linear call after the agent had flagged — it flags healthy. It reports through `pan_emit_event` (heartbeat ingestion, with its existing offline buffering), maintains a hook-local marker file so healthy is only emitted after a prior required (no event spam), and always exits 0 so it can never break an agent session.
2. **Durable events.** Four additive DomainEvent types in `packages/contracts/src/events.ts`: `linear_mcp_auth.required`, `linear_mcp_auth.healthy`, `linear_mcp_auth.notified`, `linear_mcp_auth.callback_relayed`. Two new heartbeat kinds in `bodyToEvent` map hook posts to the first two. Durability across dashboard restart is free — the events table is SQLite.
3. **Read/write door + fold.** `src/lib/linear-mcp-auth.ts` owns the intervention projection: it folds the events into at most one open lifecycle (the deduped global intervention), tracks the blocked-agent set, the latest authorization URL and *the agent that produced it*, per-agent expiry, and per-agent notified bookkeeping. Operator-facing routes (`GET /api/linear-mcp-auth`, `POST /api/linear-mcp-auth/callback`, `POST /api/linear-mcp-auth/complete`) live in `src/dashboard/server/routes/linear-mcp-auth.ts` and go through this door.
4. **Global banner.** `LinearMcpAuthBanner.tsx` mounted beside `CodexAuthBanner` in `AppChrome.tsx`, polled via React Query. Shows "Linear authentication required", the blocked agents with links to their issues, the open-authorization action, a paste-callback-URL field (localhost fallback), an operator "mark completed" action, and expired/waiting-for-URL states. Copy states the action and consequence in plain sentences.
5. **Wake.** When a `healthy` event lands (hook-observed or operator-marked), the reactive domain-event handler (`src/lib/cloister/service-reactive.ts`) runs the wake processor: for every agent in the just-ended lifecycle that has no `notified` event, call `messageAgent(agentId, <resume/recheck copy>, 'linear-mcp-auth-wake')` and append a `notified` event with the outcome (`delivered`/`queued`/`failed`). `messageAgent` covers the stopped-agent case (auto-resume or mail queue). The processor also runs once at server boot to recover a crash between `healthy` and `notified`.

The completing agent is also in the blocked set and is notified like any other — uniform semantics, harmless if it is mid-turn.

## Requirements

### Functional

- **FR-1** Detection is structured: PostToolUse hook reading the MCP tool result. No transcript/pane prose matching anywhere in the design.
- **FR-2** Hook signals are durable DomainEvents (`required`, `healthy`) ingested through the token-gated heartbeat route; two additive kinds in `bodyToEvent`.
- **FR-3** The projection dedups all agents into one global intervention lifecycle, keeps the latest authorization URL and its owning agent, per-agent blocked records, and per-agent expiry (default TTL 30 min when the tool response carries no expiry). Expired requests show an expired state; a fresh `required` refreshes the same intervention — no competing OAuth flows.
- **FR-4** A persistent top-of-dashboard banner shows while an intervention is open: message, blocked-agent identities with issue links, open-authorization action, paste-callback field, mark-completed action, and active/expired/waiting-for-URL states. Copy defines the action and consequence without external docs.
- **FR-5** The operator can complete OAuth from the banner two ways: (a) paste the localhost callback URL → server relays it via `messageAgent` to the URL-owning agent with exact `complete_authentication` instructions (this is the remote-session fallback); (b) "Mark completed" after running `claude mcp login linear` or authorizing directly → server appends an operator-source `healthy` event.
- **FR-6** On `healthy`, the wake processor sends the resume/re-check message via `messageAgent` to every blocked agent, at most once per agent per lifecycle (`notified` events are the ledger). Stopped agents are auto-resumed or mail-queued by `messageAgent`; agents whose records are gone get outcome `failed`.
- **FR-7** Intervention state survives dashboard refresh/restart (event store). The wake processor also runs once at server boot so a crash between `healthy` and `notified` cannot strand blocked agents.
- **FR-8** `roles/work.md` and `roles/plan.md` document the agent-side contract: call `mcp__linear__authenticate` once, state the URL in one sentence, stop and wait; do not retry-loop; on the wake message, re-check with a lightweight read and resume.

### Non-functional

- **NFR-1** No `execSync` in any dashboard-server-reachable code; async only.
- **NFR-2** Expiry/wake tests use `vi.useFakeTimers()` + `advanceTimersByTimeAsync`; no real `setTimeout` delays.
- **NFR-3** The heartbeat kinds ride the existing `validateAgentRuntimeEventAuth` gate; the operator POST routes use the same origin validation as `src/dashboard/server/routes/codex-auth.ts`.
- **NFR-4** Agent notification uses only `messageAgent`/`deliverAgentMessage`. Never raw `tmux send-keys`/`paste-buffer` from new code.
- **NFR-5** Contracts change is purely additive (new union members); no existing event type, field, or consumer is altered (no-loss audit).
- **NFR-6** The hook never breaks a session: any internal error exits 0 silently (same contract as `sync-sources/hooks/ask-user-question-hook`).

## NonGoals

- No spawn guardrail (HTTP 429 like the Codex spawn path) — Linear MCP auth failure is discovered at tool-call time, not at spawn.
- No settings/provider-page surface — banner only.
- No probing of Claude Code's internal MCP OAuth token store (`~/.claude.json`) — fragile, harness-internal.
- No transcript/pane prose matching.
- No auto-start of an OAuth flow before any agent has declared a requirement — the intervention exists only once an agent declares.
- No changes to the Codex auth flow.
- No Linear MCP auth signal for non-claude-code harnesses (pi/codex/acp) — the hook is claude-code-only; other harnesses simply never emit the events and the banner stays hidden.
- The Overdeck Linear tracker client (`LINEAR_API_KEY`) is untouched.

## Design details

### Event payloads (contracts item)

```ts
// packages/contracts/src/events.ts — additive, mirroring OperatorInterventionEvent (:585-595)
export const LinearMcpAuthRequiredEvent = Schema.Struct({
  type: Schema.Literal("linear_mcp_auth.required"),
  sequence: SequenceNumber,
  timestamp: Schema.String,
  payload: Schema.Struct({
    agentId: Schema.String,
    issueId: Schema.NullOr(Schema.String),
    authUrl: Schema.NullOr(Schema.String),
    expiresAt: Schema.NullOr(Schema.String),
  }),
})
// linear_mcp_auth.healthy:     { agentId, issueId: string|null, source: "hook"|"operator" }
// linear_mcp_auth.notified:    { agentId, issueId: string|null, outcome: "delivered"|"queued"|"failed" }
// linear_mcp_auth.callback_relayed: { agentId, issueId: string|null }
```

All four are appended to the `DomainEvent` union at `packages/contracts/src/events.ts:1182`. Nothing existing is touched (NFR-5). After editing contracts, rebuild: `cd packages/contracts && npm run build` (workspace rule).

### Heartbeat kinds (ingestion item)

Two new `bodyToEvent` cases in `src/dashboard/server/services/agent-event-utils.ts`:

```ts
case 'linear_mcp_auth_required':
  return { type: 'linear_mcp_auth.required', timestamp, payload: {
    agentId, issueId: body.issueId ?? null,
    authUrl: body.authUrl ?? null, expiresAt: body.expiresAt ?? null } }
case 'linear_mcp_auth_healthy':
  return { type: 'linear_mcp_auth.healthy', timestamp, payload: {
    agentId, issueId: body.issueId ?? null, source: 'hook' } }
```

The heartbeat handler in `runtime-events.ts` enriches the body with the agent's `issueId` (resolved from agent state) before `bodyToEvent` for these kinds, so payloads carry issue attribution even though the hook only knows its agent id. The route's kind documentation comment (`runtime-events.ts:44-54`) is extended. Tests extend `tests/contracts/heartbeat-ingestion.test.ts`.

### Fold / projection (`src/lib/linear-mcp-auth.ts`)

Read door: `resolveLinearMcpAuthIntervention(nowIso?)` →

```ts
{ status: 'none' | 'active' | 'expired',
  authUrl: string | null, authUrlAgentId: string | null, authUrlExpiresAt: string | null,
  declaredAt: string | null,
  blockedAgents: Array<{ agentId, issueId: string|null, declaredAt, expiresAt, notifiedAt: string|null }> }
```

Write door: `appendLinearMcpAuthEvent(...)` helpers mirroring `src/lib/operator-interventions.ts:25`.

Fold semantics (walk `queryByType` results merged in sequence order):

- `required`: open a lifecycle if none is open. Record/refresh `agents[agentId] = { issueId, declaredAt, expiresAt = payload.expiresAt ?? declaredAt + TTL }`. If `authUrl` non-null, set `authUrl`, `authUrlAgentId = agentId`, `authUrlExpiresAt = expiresAt`.
- `healthy`: close the open lifecycle (it becomes `lastCompleted`); record `source`.
- `notified`: apply to the open lifecycle if present, else to `lastCompleted`: set `agents[agentId].notifiedAt`. (Wake appends `notified` *after* the closing `healthy`, so this ordering matters.)
- `callback_relayed`: informational only.
- Projection status: `none` when no open lifecycle; `expired` when open and `authUrlExpiresAt < now`; else `active`.
- Wake set: agents of `lastCompleted` with `notifiedAt == null`.

`LINEAR_MCP_AUTH_URL_TTL_MS = 30 * 60 * 1000` (named constant in the lib). Repeated `required` events — same agent or many — refresh the same open lifecycle; nothing ever creates a second intervention (FR-3).

### Wake processor

`processLinearMcpAuthWake()` in the same lib (or `src/lib/linear-mcp-auth-wake.ts` if the lib grows past ~300 lines):

1. Fold; take the wake set. If empty, no-op (this makes a second `healthy` from a just-woken agent a no-op → idempotent).
2. For each agent: `await messageAgent(agentId, WAKE_COPY, 'linear-mcp-auth-wake')`. On success append `notified` with outcome `delivered` (or `queued` when `messageAgent` reports mail-queued); on throw append outcome `failed`.
3. Serialize concurrent runs with the in-flight-guard pattern (`src/lib/cloister/in-flight-guard.ts`).

`WAKE_COPY` (agent-facing, verbatim in code): "Linear MCP authentication has been restored — the operator completed OAuth. Re-check access now with one lightweight read (e.g. mcp__linear__list_issues). If it succeeds, resume your canonical task. If it still returns an authentication error, call mcp__linear__authenticate once and wait; do not retry in a loop."

Trigger points: a `linear_mcp_auth.healthy` case in `handleCloisterDomainEventPromise` (`src/lib/cloister/service-reactive.ts:393`), and once at server boot (wire next to the other boot reconciliation in the server startup path).

### Operator routes (`src/dashboard/server/routes/linear-mcp-auth.ts`)

- `GET /api/linear-mcp-auth` → projection JSON (shape above). No side effects.
- `POST /api/linear-mcp-auth/callback` — origin-validated like the codex routes; body `{ callbackUrl }`. 400 when the URL fails validation (must be an `http://localhost`/`http://127.0.0.1` URL carrying `code=` and `state=`). 409 when the projection has no `authUrlAgentId`. Otherwise `messageAgent(authUrlAgentId, CALLBACK_COPY(callbackUrl), 'linear-mcp-auth-callback')`, append `callback_relayed`, return `{ success: true, relayedTo }`.
- `POST /api/linear-mcp-auth/complete` — origin-validated; appends `healthy` with `source: 'operator'` (agentId `'operator'`, issueId null). The wake rides the normal reactive path. Return `{ success: true }`.

`CALLBACK_COPY` (verbatim in code): "The operator completed the Linear OAuth authorization in their browser. Finish the flow now: call mcp__linear__complete_authentication with callback_url set to exactly this URL: <URL> — then re-check Linear access and resume your canonical task."

Register the layer in `src/dashboard/server/server.ts` beside `codexAuthRouteLayer` (`:69`).

### Hook (`sync-sources/hooks/linear-mcp-auth-hook`)

Bash + jq, mirroring `ask-user-question-hook` structure. Sources `pan-hook-lib.sh`; resolves `AGENT_ID`; marker file `${OVERDECK_HOME:-$HOME/.overdeck}/agents/$AGENT_ID/linear-mcp-auth-pending`. Logic:

- `mcp__linear__authenticate` → extract first `https://linear\.app/oauth/authorize[^"\s]*` from the tool response; emit `{kind:'linear_mcp_auth_required', authUrl}` (null when extraction fails); touch marker.
- `mcp__linear__complete_authentication` → response contains an auth error marker → emit `required` (no URL); otherwise emit `{kind:'linear_mcp_auth_healthy'}` and delete marker.
- any other `mcp__linear__*` → response contains an auth error marker (`requires authentication|not authenticated|unauthorized|401`) → emit `required` (no URL), touch marker; response is clean AND marker exists → emit `healthy`, delete marker; clean and no marker → nothing (no event spam, NFR-6-adjacent).
- Always `exit 0`, `set +e`, silence on any internal error.

Registration: add to `HOOK_SCRIPT_NAMES` and `OVERDECK_HOOK_REGISTRATIONS` (`{ hookType: 'PostToolUse', scriptName: 'linear-mcp-auth-hook', matcher: 'mcp__linear__.*' }`) in `src/lib/claude-hooks-registration.ts`. Agents pick it up on next `pan sync` / new sessions — existing sessions simply lack the hook until restarted, which is acceptable (NonGoal: no retroactive wiring).

Contract test `tests/scripts/linear-mcp-auth-hook.test.ts` mirrors the AUQ test: stub `pan-hook-lib.sh` (recording `pan_emit_event` bodies to a log), run the real hook via `spawn` with fixture stdin, assert: URL extraction, auth-error → required, success-with-marker → healthy + marker deleted, success-without-marker → silence, garbage stdin → exit 0. This pins the bash↔TS string contract (concerns.md: string-marker contracts break silently without contract tests).

### Banner (frontend)

- `src/dashboard/frontend/src/hooks/useLinearMcpAuthStatus.ts` — React Query, `['linear-mcp-auth']`, polls `GET /api/linear-mcp-auth`: `refetchInterval` 5s while `status !== 'none'`, 30s otherwise (mirrors the codex 3s-active/120s-idle shape).

- Tests `LinearMcpAuthBanner.test.tsx` mirror `CodexAuthBanner.test.tsx`: hidden when none, renders agents + links when active, expired copy, callback submit posts the URL, mark-complete posts and shows its copy.

## Decisions (auto mode — each recorded in the xBRIEF `autoDecisions`)

- **D1** Detection via PostToolUse hook on `mcp__linear__.*` reading the tool result — the only structured signal available on the default harness; probing Claude Code's internal OAuth store is fragile and transcript/pane matching is banned by the issue.
- **D2** Durability via additive DomainEvents in the existing event store — restart persistence with no migration, consistent with the two-door tenet and the `operator-interventions.ts` precedent.
- **D3** Ingestion through the existing heartbeat route (`bodyToEvent` kinds) rather than a new agent-facing POST — reuses token auth, Schema validation, and the offline `pending-events.jsonl` buffering in `pan_emit_event`.
- **D4** Wake via `messageAgent`, not raw `deliverAgentMessage` — it handles the stopped-agent acceptance case (auto-resume or mail queue).
- **D5** Notify every blocked agent including the completing one — uniform semantics; the completer may itself be parked waiting.
- **D6** One global intervention by construction (fold of one open lifecycle); latest `authUrl` wins and callbacks relay to the URL-owning agent — the dedup the issue demands.
- **D7** Banner mounted beside `CodexAuthBanner`, polled via React Query REST — exactly the #913/#1067 pattern the issue says to reuse; no read-model/Zustand projection needed.
- **D8** Two completion paths: callback relay (remote fallback) and operator mark-completed (covers `claude mcp login linear`, the actual MIN-852 resolution path, which produces no hook signal on its own).
- **D9** Default URL TTL 30 min when the tool response carries no expiry — Linear authorize URLs are short-lived; a fresh `required` refreshes, and the expired state is explicit in the banner.
- **D10** No spawn guardrail and no settings-page surface — out of scope per the issue's acceptance criteria.
