# PAN-3111 — Planning-finalize auto-starts work agents past the pickup gate; spawn provenance missing

## Glossary

- **Pickup gate / pickup predicate** — the flywheel's eligibility rule for automatically starting work on an issue, implemented as `isAutoPickable()` in `src/lib/backlog/pickup.ts:107`: `ready && planned && (released || auto_pickup_backlog || activeBookMember) && !parked && !vetoed && !objection && !inPipeline && !epic`. Also documented in `roles/flywheel.md:159`.
- **`ready` label** — Definition-of-Ready entry label (`READY_LABEL`, `src/lib/backlog/pickup.ts:25`).
- **`released` label** — the operator's explicit "go" after reviewing a plan (`RELEASED_LABEL`, PAN-2059). A planned issue is NOT auto-startable until released, unless `auto_pickup_backlog` is on or the issue is in the active order book.
- **`auto_pickup_backlog`** — global control setting (`isFlywheelAutoPickupBacklog()`, `src/lib/overdeck/control-settings.ts:554`); when on, it satisfies the release gate for the whole backlog.
- **Active order book / `activeBookMember`** — issue membership in the flywheel run's active order book (`activeOrderBookIssues()`, `src/lib/cloister/flywheel.ts:46`); membership counts as operator release.
- **Orphan-proposed reconciler** — `src/lib/cloister/orphan-proposed-reconciler.ts`. PAN-1908/PAN-2520 recovery mechanism: when a spec sits at `plan.status === 'proposed'` with no active work agent, it spawns one via `POST /api/agents`. Fires reactively on `issue.statusChanged(todo|planned)` and from a deacon patrol sweep.
- **Reactive lifecycle scheduler** — `src/lib/cloister/service-reactive.ts`. Maps issue lifecycle states to role spawns (`ROLE_RUN_STATES`, line 75): `in_progress` → work, `in_planning` → plan, `in_review` → review, `testing` → test.
- **`decideAutonomousPlanDispatch`** — `src/lib/cloister/autonomous-plan-dispatch.ts:85`. The existing label-gate precedent: autonomous *planning* spawns fail closed unless the issue is released (or auto-pickup is on) and not parked/vetoed/objected. The work-side mirror of this function does not exist yet — that absence is this issue.
- **Auto-spawn-on-finalize flag** — `~/.overdeck/agents/planning-<issue>/auto-spawn-on-finalize.json`, written at planning-spawn time only when the session was launched with `--auto-start` (`src/lib/planning/spawn-planning-session.ts:749`). Read by `readAutoSpawnOnFinalizeFlag()` (same file, line 65).
- **`startedBy`** — the provenance field this issue adds: who/what caused an agent spawn (operator CLI, dashboard, planning auto-handoff, reconciler, reactive lifecycle, deacon, flywheel run).
- **`flywheelRunId`** — existing provenance field (`AgentState.flywheelRunId`, `src/lib/agents/agent-state.ts:116`), threaded through spawn options but — verified defect — never assigned to the state object at spawn.

## Problem

Observed 5 times on 2026-07-26 (PAN-3109, PAN-3116, PAN-3114, PAN-3115, MIN-904), zero counter-examples: an issue filed and planned by the flywheel via `pan plan <id> --auto` (no `--auto-start`, never `ready`, never `released`, run configured `auto_pickup_backlog: false`) acquired a running work agent within minutes of its planning finalizing. `roles/flywheel.md` documents the contract that `pan plan <id> --auto` "produces xBRIEF + beads and stops at planned". The correlation is deterministic: every finalized plan started work; the one issue still planning did not.

### Root cause (verified against the tree)

1. The flywheel runs `pan plan PAN-X --auto` → `POST /api/issues/:id/start-planning` with `autoStart: false` (`src/cli/commands/plan.ts:40`), so no auto-spawn-on-finalize flag file is written.
2. The planning agent finishes and runs `pan plan finalize` → `POST /api/issues/:id/complete-planning` with `autoSpawn: false` (`src/cli/commands/plan-finalize.ts:251,286`; flag absent → false). `completePlanningAutoSpawn` correctly does NOT spawn.
3. `completePlanningForIssue` (`src/lib/overdeck/planning-promotion.ts:740-745`) flips labels to `planned` and appends `issue.statusChanged { canonicalStatus: 'todo' }` to the event store.
4. Cloister's domain-event subscription (`src/lib/cloister/service.ts:520,538`) invokes `handleCloisterDomainEventPromise` (`src/lib/cloister/service-reactive.ts:388`), which on `canonicalStatus === 'todo' || status === 'planned'` calls `handleOrphanProposedSpec(issueId)` (line 456-458).
5. `handleOrphanProposedSpec` (`src/lib/cloister/orphan-proposed-reconciler.ts:370`) finds the just-promoted spec at status `proposed`, no active work agent, and spawns one via `POST /api/agents` (line 486). Its existing gates are: cooldown, project resolved, spec proposed, agent not active, not paused/troubled, no issue-scoped tmux session, no review-pipeline presence, not closed, non-empty plan, no open PR (lines 385-481). **There is no pickup-predicate check — `ready`, `released`, `auto_pickup_backlog`, parked/vetoed/objection are never consulted.**
6. The deacon patrol sweep `reconcileOrphanProposedSpecs` (`src/lib/cloister/deacon.ts:2782`) delegates to the same handler as a dropped-event backstop — same missing gate.
7. `spawnAgent` then transitions the tracker to in-progress (`src/lib/agents/spawn.ts:568`), which is why the observed issues wore the `in-progress` label *after* the fact.

Secondary ungated path (same defect family): the reactive lifecycle scheduler's **work**-role dispatch (`service-reactive.ts:331`) spawns `spawnRun(issueId, 'work', …)` on any `in_progress` issue-state event with no gate. The sibling **plan**-role dispatch was gated by `decideAutonomousPlanDispatch` at `service-reactive.ts:306`; the work role never got the same treatment. Boot reconciliation replays issue-state-change events, so any issue sitting at in-progress with no live agent is an auto-start candidate.

Provenance defects (why the incidents were unattributable):

- `startedBy` does not exist anywhere in the codebase (verified by `git grep startedBy src/ packages/` — only an unrelated tmux systemd check).
- `flywheelRunId` is declared on `AgentState` (`agent-state.ts:116`) and `SpawnOptions` (`spawn-prep.ts:98`) and threaded into `spawnAgent` (`spawn.ts:121`), but **neither state literal assigns it** (`spawn.ts:549-562` for `spawnAgent`, `spawn.ts:189-204` for the `spawnRun` role path). Every agent therefore records `flywheelRunId: null`, which also silently defeats PAN-1812's operator-started exemption in `src/lib/cloister/concurrency.ts:341` and the memory-governor shed filter in `src/lib/cloister/memory-governor.ts:253` — both treat flywheel-spawned agents as operator-started today.

## Proposal

Two coordinated fixes.

### A. One pickup predicate for every autonomous work-agent spawn

Add `src/lib/cloister/autonomous-work-dispatch.ts` mirroring the existing `autonomous-plan-dispatch.ts` shape (gather + pure decide, fail-closed):

```ts
export interface AutonomousWorkDispatchInput {
  labels: readonly string[] | null;          // null = tracker labels unavailable
  autoPickupBacklog: boolean;
  activeBookMember: boolean;
  autoSpawnOnFinalizeConsent: boolean;       // launch-time --auto-start flag file
}

export type AutonomousWorkDispatchDecision =
  | { allow: true }
  | { allow: false; code: 'not-ready' | 'not-released' | 'parked' | 'vetoed'
      | 'objection' | 'epic' | 'labels-unavailable'; reason: string };
```

Decision logic (exact `isAutoPickable` semantics, `src/lib/backlog/pickup.ts:107-116`, with the consent flag as a release-equivalent):

- labels unavailable → refuse `labels-unavailable` (fail closed — same posture as `decideAutonomousPlanDispatch`, `autonomous-plan-dispatch.ts:88-95`).
- parked / vetoed / objection / epic label → refuse with the matching code.
- `ready` label absent → refuse `not-ready`.
- release satisfied iff `released` label OR `autoPickupBacklog` OR `activeBookMember` OR `autoSpawnOnFinalizeConsent` → else refuse `not-released`.

**The consent exception is deliberate no-loss preservation.** The reconciler's only legitimate role today is retrying the planning→work auto-handoff for sessions launched with `--auto-start` whose direct spawn failed (e.g. stack-unhealthy). Those sessions carry the operator's explicit launch-time consent in the flag file; treating that consent as release-equivalent keeps the retry alive without weakening the gate for anything else. `pan start` (paved road) launches planning with `autoStart: true` (`src/cli/commands/start.ts:891-897`), so it flows through the direct `completePlanningAutoSpawn` path and is unaffected either way.

`gatherAutonomousWorkDispatchInput(issueId)` sources:

- labels: lazy `require` of the dashboard issue-service singleton, exactly as `autonomous-plan-dispatch.ts:50` does (static import would create a lib→dashboard layering edge); unavailable → `null` → fail closed.
- `autoPickupBacklog`: `isFlywheelAutoPickupBacklog()` (`control-settings.ts:554`).
- `activeBookMember`: `activeOrderBookIssues(projectRoot)` (`flywheel.ts:46`) — returns an empty set when no run/book is active.
- consent: `readAutoSpawnOnFinalizeFlag(issueId)` (`spawn-planning-session.ts:65`).

Do NOT reuse `buildClassifyLookups` wholesale: its `isInPipeline` counts workspace-directory existence (`src/lib/backlog/lookups.ts:54-58`), which every reconciler candidate has — it would make the gate permanently false. Construct the decision inputs directly.

### B. Wire the predicate into both autonomous spawn paths

1. **Orphan-proposed reconciler** — in `handleOrphanProposedSpec` (`orphan-proposed-reconciler.ts:370`), immediately after the `plan.status !== 'proposed'` check (line 424-427), evaluate the predicate. On refusal: `logReconcilerDiagnostic('spawn-skipped', { reason: \`pickup-gate:\${code}\` })`, one durable needs-you trip via `recordDeadEndNeedsYou(issueId, 'orphan-proposed-pickup-gate', …)` (`src/lib/cloister/dead-end-trip.ts:4`), and return the skip string. No per-attempt activity-feed warning (PAN-1626 anti-spam: diagnostic logs + the durable trip only). Inject the predicate as an optional dep (`evaluatePickupGate?`) so tests can stub it; default is the real gather+decide.
2. **Reactive work-role dispatch** — in `service-reactive.ts` before the `spawnRun(normalizedIssueId, role, …)` call at line 331, when `role === 'work'` evaluate the same predicate; on refusal mirror the plan-role refusal at lines 309-319 (warn activity entry + `recordDeadEndNeedsYou` + return).

Operator-initiated paths are NOT gated: `pan start`, the dashboard Start Agent button, and `completePlanningAutoSpawn` (launch-time consent) are themselves the release. Out of scope: gating the `/api/agents` route itself — internal recovery paths (rebuild-and-start for an operator-started but unreleased issue) legitimately pass through it.

### C. Spawn provenance

1. **Persist `flywheelRunId`** in both state literals (`spawn.ts:549-562` and `spawn.ts:189-204`) using the same resolved run id that `resolveFlywheelSpawnEnv` already computes (`spawn-prep.ts:55`), so state and launcher env agree.
2. **Add `startedBy?: string`** to `AgentState`, `SpawnOptions`, `SpawnRunOptions`; stamp in both literals as `options.startedBy ?? process.env.OVERDECK_AGENT_STARTED_BY ?? (flywheelRunId ? \`flywheel:\${flywheelRunId}\` : undefined)`. The env fallback exists because the `/api/agents` route launches the real spawn as a detached `pan start` child process (`spawnPanCommandDetached`, `src/dashboard/server/routes/agents/shared.ts:78`) — provenance must cross that process boundary, and env is the channel that already propagates there (same pattern as `OVERDECK_FLYWHEEL_RUN_ID`).
3. **Agents table `started_by TEXT` column** following the established pattern: `tryIdempotentDdl` migration in `src/lib/database/schema.ts` (pattern at line 819+), the `agents` CREATE TABLE (line ~455), `ALL_COLUMNS` + `Agent` interface + `agentToParams` + row mapper in `src/lib/database/agents-db.ts` (lines 103, 120-135), the backfill column map in `src/lib/database/agent-backfill.ts:72`, and both directions of `src/lib/overdeck/agent-state-sync.ts` (lines 172, 226). A round-trip test is mandatory — `docs/…/concerns.md` names this exact "write-only AgentState field" trap, and `flywheelRunId` is the living example of it.
4. **Stamp tokens at every spawn entry point** (sub-items in the xBRIEF):
   - `/api/agents` route: accept optional `startedBy` in the POST body; default `operator:dashboard`; propagate into the detached child env.
   - `pan start` CLI: default `operator:cli:pan-start` (set the env var when unset).
   - `completePlanningAutoSpawn` (`planning-promotion.ts:350`): body `startedBy: 'planning-auto-handoff'`.
   - `spawnWorkAgentThroughAgentsEndpoint` (`orphan-proposed-reconciler.ts:261`): body `startedBy: 'orphan-proposed-reconciler'`; `triggerRebuildAndStart` (line 306): `'workspace-rebuild-recovery'` (and the rebuild-and-start route forwards it).
   - Reactive lifecycle dispatch (`service-reactive.ts:321,331`): `'reactive-lifecycle'`.
   - Deacon resume/respawn paths (`deacon-auto-resume.ts`, `service-crash.ts:374`): `'deacon:auto-resume'` / `'deacon:crash-respawn'`.
   - `handoff.ts:137`: `'handoff'`; `merge-strike.ts:221`: `'merge-strike'`.
   - Planning sessions (`spawn-planning-session.ts:741` state write): `operator:cli:pan-plan` / `operator:dashboard` / flywheel-env derivation.

## Requirements

### Functional

- **FR-1** — The orphan-proposed reconciler (reactive handler and patrol sweep) refuses to spawn a work agent unless the issue passes the pickup predicate: `ready` label present, spec proposed (by construction), release satisfied by `released` label / `auto_pickup_backlog` / active order-book membership / auto-spawn-on-finalize consent flag, and no `parked` / `vetoed` / `objection` / `epic` label.
- **FR-2** — The reactive lifecycle work-role dispatch (`in_progress` → `spawnRun(work)`) applies the same predicate before spawning.
- **FR-3** — Both paths fail closed when tracker labels are unavailable, and every refusal produces a diagnostic log plus one durable needs-you trip — never a silent skip, never per-attempt feed spam.
- **FR-4** — `flywheelRunId` is persisted to `AgentState` (state.json) and the agents table at every spawn that carries one.
- **FR-5** — `startedBy` is stamped on every agent spawn (work, strike, plan, review, test roles), persisted to state.json and the agents table, with the entry-point tokens listed in Proposal C.4; spawns under a flywheel run derive `flywheel:<runId>` when no explicit token is given.

### Non-functional

- **NFR-1** — No regression to legitimate flows: `pan start` paved road, `--auto-start` handoff including its reconciler retry, operator Start Agent, flywheel dispatch, rebuild-and-start recovery. The existing reconciler test suite (`src/lib/cloister/__tests__/orphan-proposed-reconciler.test.ts`, 27 tests) stays green with the gate dep injected.
- **NFR-2** — Refusals respect the PAN-1626 anti-spam constraint: console diagnostics + durable needs-you, no repeated activity-feed entries per cooldown window.

## Decisions made in this doc (auto mode — recorded in xBRIEF autoDecisions)

1. **Consent flag is release-equivalent.** Strict `isAutoPickable` without the auto-spawn-on-finalize exception would silently kill the `--auto-start` handoff-retry recovery — a silent feature deletion. The flag file is launch-time operator consent, so it satisfies the release clause.
2. **Gate the reactive work dispatch too**, not just the reconciler. The observed incident used the reconciler, but `service-reactive.ts:331` is the same hole (boot reconciliation replays `in_progress` events); fixing only the observed path leaves the bypass one tracker-label away.
3. **Fail closed on unavailable labels**, mirroring `decideAutonomousPlanDispatch` — an autonomous spawner that cannot verify blocker labels must not spawn.
4. **Fix the latent `flywheelRunId` persistence bug in scope.** Ask #2 (attributable spawns) cannot be satisfied while the one existing provenance field is never written; the fix is two assignments plus tests.
5. **Refusals go to diagnostics + durable needs-you, not the activity feed** (PAN-1626 lesson: per-attempt reconciler chatter floods the feed).
6. **No route-level gate on `/api/agents`.** Internal recovery paths (rebuild-and-start after an operator's explicit start) legitimately spawn for unreleased issues; consent is established at the entry points, not the transport.
7. **Dashboard surfacing of `startedBy` is out of scope** — stamping and persistence only; a UI surface can follow once the data exists.

## Acceptance criteria (plan-level)

- Given a proposed spec for an issue with no `ready`/`released` labels and `auto_pickup_backlog=false`, when planning finalizes and `issue.statusChanged(todo)` fires, then no work agent is spawned and a durable needs-you trip exists naming the pickup-gate refusal.
- Given the same issue with the auto-spawn-on-finalize consent flag present, when the reconciler runs, then the work agent IS spawned (handoff retry preserved).
- Given labels unavailable (issue service not ready), when either gated path evaluates, then it refuses with `labels-unavailable` and records a needs-you trip.
- Given an agent spawned with `flywheelRunId` set or `startedBy` provided, when the spawn completes, then state.json and the agents table row carry the values (round-trip test).
- `npm run typecheck`, `npm run lint`, and `npm test` pass with no new failures; the reconciler and reactive-scheduler suites are green.

## NonGoals

- Dashboard/UI surfacing of `startedBy` (data layer only).
- Rank-ordered pickup — the reconciler remains a per-issue recovery mechanism, not a sequencer; within the pickable set it may start out of rank order (pre-existing, strictly narrowed by the gate).
- Gating operator-initiated spawns (`pan start`, Start Agent button) — operator action is the release.
- Route-level (`/api/agents`) pickup gating.
- Changing what `complete-planning` emits (`issue.statusChanged(todo)` stays).
- Migrating the patrol sweep's legacy `.pan/specs` discovery to `findSpecByIssue`.
