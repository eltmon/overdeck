## Glossary

- **Workspace registry** — the PAN-1990 tables (`projects`, `workspaces`, `project_targets`, `pinned_docs`) reached only through `src/lib/workspaces/resolver.ts` (reads) and `src/lib/workspaces/writer.ts` (writes); `scripts/guard-workspace-doors.sh` enforces this in lint.
- **User workspace** — a `kind='main'` or `kind='scratch'` registry row: created by operator intent, not by the issue pipeline. `kind='issue'` rows are pipeline-owned and out of scope here.
- **Creation intent** — the operator's declared inputs: name, project, target directory, mode (shared/isolated), optional parent branch. Distinct from the **resolved intent**: the concrete outcome computed from it — final `path`, `branchName`, `parentBranch(+Guessed)`, `isGitRepository`, `wouldCreateWorktree` — the exact JSON shape `pan workspace new --dry-run` already prints (`src/cli/commands/workspace-scratch.ts:128-147`).
- **Resolve-before-create** — the flow's signature: the dialog continuously displays the resolved intent from a server-side dry-run of the *same* resolution code the real create executes, so confirming never produces a surprise.
- **Shared mode** — the workspace targets an existing directory it does not own (no branch created; default). **Isolated mode** — a dedicated git worktree at `<workspaces_dir>/scratch-<name>` on branch `scratch/<name>`.
- **Mutation guard** — `rejectUnsafeDashboardMutationRequest(request)` (`src/dashboard/server/routes/dashboard-auth.ts`), applied by every existing registry mutation route (`workspace-registry.ts:160,175,193,212`).
- **Registry query key** — the react-query key `['workspace-registry']` used by the sidebar (`Sidebar.tsx`, 10s refetch) and detail views.

## Motivation

PAN-3286 delivered workspace creation by intent in the CLI and workspace *presentation* in the dashboard, but the dashboard cannot create, relocate, or archive a user workspace: the registry API exposes no create/relocate route (verified — `workspace-registry.ts` imports neither `createWorkspace` nor `relocateWorkspace`), no endpoint serves a project's registered target paths, and the only "create workspace" button in the frontend is the unrelated issue-worktree affordance (`WorkspaceStatusOverview.tsx`). Workspaces are supposed to exist by operator intent; the intent must be expressible where the operator actually works.

## Decisions

- **D-1: One shared core, two callers.** Extract intent resolution + creation into `src/lib/workspaces/create.ts`: `resolveWorkspaceCreateIntent(input): Promise<ResolvedWorkspaceIntent>` (pure resolution + validation; no writes, no worktree) and `performWorkspaceCreate(intent): Promise<{id: string}>` (seeding, optional `git worktree add` via `execFileAsync`, `createWorkspace`). The CLI command and the new routes both call these; the CLI keeps only flag parsing and console output. Project resolution takes an explicit `cwd?: string` parameter instead of reading `process.cwd()` so the server can pass nothing and require an explicit project.
- **D-2: The dialog always shows resolved truth.** Field changes debounce (~300ms) into `POST /api/workspace-registry/resolve`; the preview panel renders resolved path (mono), branch to be created or observed, parent branch (with "inferred" tag when `parentBranchGuessed`), git-repository detection, and `wouldCreateWorktree`. Validation errors from the resolver render inline against their field; the Create button disables while the preview is stale or erroring. Resolve is a POST (it takes a JSON body) but MUST remain write-free — assert in tests.
- **D-3: Server-side creation requires an explicit project.** No cwd inference exists in a browser context. The project select defaults to the sole registered project when only one exists, else to the workspace rail's current project context when unambiguous, else forces a choice.
- **D-4: Target directory field = registered targets + free-form.** A new read endpoint (FR-3) supplies the project's `project_targets` rows plus the project's primary `config.path`, rendered as a dropdown with the primary preselected in shared mode; a "Browse…" option opens `FolderPicker` for any absolute path (matching CLI D-3 of PAN-3286: unregistered targets are allowed, noted informationally, never an error). Target-path selection is disabled in isolated mode (path is derived), mirroring the CLI's mutual exclusion.
- **D-5: Explicit cache invalidation.** The create/relocate/archive mutations call `queryClient.invalidateQueries({ queryKey: ['workspace-registry'] })` on success rather than waiting out the 10s poll — a deliberate break from the fire-and-forget precedent, so a just-created workspace appears in the rail immediately. The modal additionally receives `onCreated(workspaceId)` and the app activates + navigates to the new workspace (same post-create posture as palette activation).
- **D-6: Reuse the archive/favorite routes; add only what is missing.** New routes: `POST /api/workspace-registry` (create), `POST /api/workspace-registry/resolve` (dry-run), `POST /api/workspace-registry/:id/relocate`, `GET /api/workspace-registry/project-targets?project=<key>`. All mutations behind the standard guard; the GET is read-only and unguarded like its siblings. No changes to existing routes (no-loss).
- **D-7: Issue workspaces stay out.** The modal creates `scratch` only (plus main-bootstrap: when a project has no `main` row the dialog offers a one-click "register main workspace" variant using the same core the CLI `workspace main` verb uses). Relocate in the UI obeys writer rules: never offered on issue rows; on main it requires a typed confirmation and passes `force`.
- **D-8: Modal chrome clones `NewProjectModal`** (CSS-module overlay/dialog, `dashboardMutationJsonHeaders`, `fetchWithTimeout`), not a new dialog framework. Archive uses the existing `ConfirmationDialog` via `DialogProvider`.
- **D-9: Name validation is shared and immediate.** The dialog validates the name with the same `validateFeatureName` rule surfaced through the resolve endpoint (single source; no duplicated client regex — the client merely displays the resolver's finding).
- **D-10: No model calls anywhere in this feature.** Pure CRUD + git plumbing.

## Intersecting repo rules (restated for the executor)

- **Two doors:** routes call `src/lib/workspaces/{resolver,writer,create}.ts` only; never SQL or table access in route files (`scripts/guard-workspace-doors.sh` fails lint otherwise).
- **No `execSync`** server-reachable; `execFileAsync` argument vectors for git (no shell strings — names/paths must not be interpolatable).
- **Fake timers** for the debounce tests; never real `setTimeout` waits.
- **Mutation guard** on every new POST; GETs unguarded like existing registry GETs.
- **Style guide** per verified state item 10; run the style checks in `design/style-guide/STYLE-GUIDE.md` before UI screenshots.
- **Playwright verification** of the modal + rail button at narrow and wide widths is the implementer's job — never ask the operator to eyeball. Use an isolated browser instance/profile; never depend on another agent's Playwright session.
- **Worktree discipline / push-per-item / commit hygiene** as standard.
