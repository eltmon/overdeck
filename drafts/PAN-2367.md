## Glossary

- **Deacon patrol / cycle** — the lifecycle watchdog loop that runs every ~60s–2.4min inside the dashboard server process; each pass is a numbered `cycle` in `~/.overdeck/logs/deacon.log`.
- **Swarm finalization** — `finalizeSwarmIssueIfComplete()` in `src/lib/cloister/deacon-swarm-finalization.ts` (added 2026-07-04 by the PAN-2357 fix, commit `d10a604868`): when a feature workspace's plan items are all `completed`, it requests issue-level review (writes review status + spawns a review agent).
- **Review status** — the per-issue row managed by `src/lib/review-status.ts` (`getReviewStatusSync` / `setReviewStatusSync` / `clearReviewStatus`), holding `reviewStatus`, `mergeStatus`, `reviewRequestedAt`, etc.
- **Per-issue record** — the durable JSON at `.pan/<recordsPath>/<issue>.json` (permanent plane), typed in `src/lib/pan-dir/record.ts`; its `swarm` block (`PanIssueSwarmRecord`) already persists `slotAssignments` and `failedMergeBlock`.
- **Closed-issue reaper** — `src/lib/cloister/closed-issue-reaper.ts`; stops agents whose parent tracker issue is closed (log line: `Reaped <agentId> — parent issue <issue> is closed`).
- **Review-status pruner** — `pruneClosedIssueReviewStatuses()` in `src/dashboard/server/main.ts` (grep anchor: `Pruned ${removed} stale review-status`): deletes review-status rows for tracker-CLOSED issues.
- **Spec `plan.status`** — the lifecycle field on the main-side vBRIEF spec (`.pan/specs/…`), resolved by `findSpecByIssue()` in `src/lib/pan-dir/specs.ts`; close-out flips it to `completed`/`cancelled` via `updateSpecStatus()`.

## Problem (verified 2026-07-04 on the live deacon)

`finalizeSwarmIssueIfComplete` fires **every patrol cycle for ~20 already-merged, closed-out issues**, spawning a real review-agent harness session each time (272 firings logged). Loop for PAN-2311 (deacon.log, times UTC):

```
21:38:23 [swarm] finalized PAN-2311: issue-level review requested   (cycle 17177)
21:39:20 Reaped agent-pan-2311-review — parent issue PAN-2311 is closed (cycle 17178)
21:40:47 [swarm] finalized PAN-2311: issue-level review requested   (cycle 17178)
```

Mechanics — three subsystems with contradictory views of a closed issue:

1. 59 stale `workspaces/feature-*` worktrees linger for merged/closed issues. Each has a spec whose items are all `completed` — to finalization this looks like "a swarm just finished".
2. Finalization's only idempotency guard is the review status (`reviewRequestedAt` / `reviewing` / `passed`). But review-status rows for closed issues are **deleted by design** — by `pruneClosedIssueReviewStatuses()`, by `clearReviewStatus()` at close-out (`src/lib/close-out.ts`, grep anchor `clearReviewStatus(ctx.issueId`), and by other transition paths. Verified live: the `review_status` table has **no row** for PAN-2311 despite finalization having just written one.
3. The closed-issue reaper kills each spawned review agent one cycle later. Erased tombstone → finalize fires again. Repeat forever.

Root defect: **the fix for PAN-2357 used a clearable-by-design field as its idempotency tombstone, and never checks whether the issue is terminal.** (The pre-landing audit recommendation was a durable `swarm.finalizedAt` in the per-issue record.)

## Requirements

- **FR-1** — Swarm coordination MUST skip an issue whose main-side spec `plan.status` is `completed` or `cancelled`, before any reconcile/finalize work.
- **FR-2** — `finalizeSwarmIssueIfComplete` MUST NOT request review when the issue's review status shows `mergeStatus === 'merged'`.
- **FR-3** — Successful finalization MUST write a durable `finalizedAt` (ISO-8601 string) into the per-issue record's `swarm` block, and finalization MUST return early when it is already set. This tombstone is the idempotency source of truth; review-status fields remain advisory only.
- **FR-4** — A genuinely completing swarm (spec `plan.status` not terminal, items all completed via `statusOverrides`, no slot state) MUST still finalize exactly once — the PAN-2357 behavior is preserved.
- **FR-5** — The runaway scenario MUST be locked by a regression test: all-completed spec + terminal `plan.status` + absent review status ⇒ zero `requestIssueReview` calls; and repeated finalize calls interleaved with review-status clears ⇒ exactly one `requestIssueReview` call (tombstone honored).
- **NFR-1** — No new explicit `any`; async only (no `execSync`); no new files ≥1,000 lines.
- **NFR-2** — Retry/delay-free logic — no timers involved; if any test needs simulated time, use `vi.useFakeTimers()` per the fake-timers repo rule.

## Work items

### W1 — Terminal-spec guard at the coordination loop (FR-1)

**File:** `src/lib/cloister/deacon-swarm.ts`, inside `coordinateSwarmSlots`, immediately after the spec resolve. Grep anchor:

```ts
const spec = await Effect.runPromise(findSpecByIssue(workspace.projectPath, issueId));
if (!spec) continue;
```

**After:**

```ts
const spec = await Effect.runPromise(findSpecByIssue(workspace.projectPath, issueId));
if (!spec) continue;
const planStatus = spec.document.plan.status;
if (planStatus === 'completed' || planStatus === 'cancelled') continue;
```

Rationale: close-out flips `plan.status` via `updateSpecStatus()` (`src/lib/pan-dir/specs.ts`), so every closed-out issue is excluded here regardless of leftover workspaces — this removes the runaway's fuel and skips wasted reconcile work. Do NOT delete or modify the stale workspaces themselves (close-out owns workspace teardown; out of scope).

**Test:** extend `tests/unit/lib/cloister/deacon-swarm-doneness.test.ts` — a workspace whose spec has `plan.status: 'completed'` and all-completed items produces no actions and no `requestIssueReview` call.

### W2 — Durable `finalizedAt` tombstone (FR-3, FR-4)

**Files:** `src/lib/pan-dir/record.ts`, `src/lib/cloister/deacon-swarm-finalization.ts`, `src/lib/cloister/deacon-swarm.ts`.

1. In `record.ts`, extend the swarm record interface. Grep anchor:

   ```ts
   export interface PanIssueSwarmRecord {
     failedMergeBlock?: PanIssueSwarmFailedMergeBlock;
     slotAssignments?: PanIssueSwarmSlotAssignment[];
   ```

   Add `finalizedAt?: string;`. Add read/write helpers `getSwarmFinalizedAt(...)` / `setSwarmFinalizedAt(...)` following the existing `failedMergeBlock` helper pattern in the same file (same signature style, same `writeIssueRecordSync` persistence; find them by grepping `failedMergeBlock` in `record.ts` and its callers).

2. In `deacon-swarm-finalization.ts`, extend the deps of `finalizeSwarmIssueIfComplete` with injectable `getFinalizedAt` / `setFinalizedAt` (defaults = the new record helpers, resolved the same way `getFailedMergeBlock(issueId, workspacePath)` resolves the record in `deacon-swarm.ts` — grep anchor `export function getFailedMergeBlock`). Guard order inside the function:

   ```ts
   if (!doc.plan.items.every(item => item.status === 'completed')) return [];
   if (deps.getFinalizedAt?.(issueId, workspacePath)) return [];            // NEW — durable tombstone
   const currentStatus = getReviewStatusSync(issueId);
   if (currentStatus?.mergeStatus === 'merged') return [];                  // NEW — FR-2
   if (currentStatus?.reviewRequestedAt || currentStatus?.reviewStatus === 'reviewing' || currentStatus?.reviewStatus === 'passed') {
     return [];
   }
   ```

3. After a successful `requestIssueReview`, write the tombstone before returning the action string:

   ```ts
   if (result.success) {
     deps.setFinalizedAt?.(issueId, workspacePath, new Date().toISOString());
     return [`[swarm] finalized ${issueId}: issue-level review requested`];
   }
   ```

   On `result.success === false` do NOT write the tombstone (a gated/deferred finalization must retry next cycle — preserves the PAN-2357 `finalization deferred` path).

4. Wire the two new deps through `CoordinateSwarmSlotsDeps` in `deacon-swarm.ts` (grep anchor `requestIssueReview: (issueId: string, workspacePath: string)`), defaulting to the record helpers.

**Tests:** `tests/unit/lib/cloister/deacon-swarm-finalization.test.ts` (new file, or extend the suite added by d10a604868 in `deacon-swarm-completion.test.ts` if the reviewers prefer):
