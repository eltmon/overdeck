# PAN-2807 — SQLite schema drift: loud migrations + startup schema audit

**Issue:** https://github.com/eltmon/overdeck/issues/2807
**Planned:** 2026-07-16 (auto planning session, claude-fable-5)

## Glossary

- **overdeck.db** — the live runtime cache DB at `~/.overdeck/overdeck.db`, owned by the two-door remodel layer (`src/lib/overdeck/infra.ts`). Created by a one-shot **init migration** and patched by **top-ups**.
- **panopticon.db** — the legacy DB at `~/.overdeck/panopticon.db`, owned by `src/lib/database/schema.ts` (`runMigrations`, a `user_version` **ladder** with `SCHEMA_VERSION = 61`). Still opened by legacy `src/lib/database/*-db.ts` modules.
- **init migration** — `drizzle/overdeck/0000_overdeck_init.sql`. `runOverdeckMigrationSync` (`src/lib/overdeck/infra.ts:50`) executes it only when the `agents` table is absent, i.e. only on a fresh overdeck.db.
- **top-up** — an idempotent `ALTER TABLE`/`CREATE INDEX IF NOT EXISTS` in `ensureRuntimeIndexesSync` (`src/lib/overdeck/infra.ts:69`) that patches existing overdeck.db files the init migration will never touch again.
- **ladder** — the sequential `if (currentVersion < N)` migration steps in `runMigrations` (`src/lib/database/schema.ts:772`), stamped via `PRAGMA user_version`.
- **pragma shim** — `wrapDatabase().pragma()` in `src/lib/database/driver.ts:206`, which runs `PRAGMA <sql>` through `prepare().all()` for both `node:sqlite` and `bun:sqlite`.

## Root cause (verified 2026-07-16, re-framing the issue text)

The issue's forensics assumed the schema.ts ladder governs the live DB. Discovery
established a different picture, verified against the live machine:

1. **The live DB is overdeck.db, not panopticon.db.** Its `user_version = 0` is
   *expected*: `infra.ts` never writes `user_version` at all. It is not a failed stamp.
2. **The pragma shim works.** Empirically verified on this machine: under both
   `node:sqlite` (Node 22.22) and `bun:sqlite`, `pragma('user_version = 61')` via
   `prepare().all()` writes the value and reads it back. The issue's "verify the shim"
   bullet resolves to *lock it with a test*, not fix it.
3. **The missing indexes were never declared for overdeck.db.** The init migration
   creates `cost_events` with indexes on `issue_id`, `ts`, `session_id`, `request_id`
   only (`drizzle/overdeck/0000_overdeck_init.sql:123-126`). `idx_cost_agent_id` and
   `idx_cost_issue_upper` exist only in the *legacy* schema.ts world
   (`src/lib/database/schema.ts:193` and `:911`), which applies to panopticon.db. The
   hot queries (`src/lib/overdeck/cost-sync.ts:462` `WHERE agent_id = ? AND ts >= ?`;
   many `UPPER(issue_id)` filters in the same file) run against overdeck.db — hence the
   215k-row full scans of PAN-2805. The operator created both indexes manually on this
   machine (live DDL: `CREATE INDEX idx_cost_agent_id ON cost_events(agent_id, ts)`;
   `CREATE INDEX idx_cost_issue_upper ON cost_events(UPPER(issue_id))`); every other
   machine still has the hole.
4. **"v10/v12 present but v9 absent"** is because overdeck.db's `conversations`
   table is a *different schema by design* (Drizzle shape with `total_cost`,
   `archived_at`, no `title_seed`/`claude_session_id`) — not a partially applied ladder.
5. **The silent-failure hazards are nonetheless real, in both layers:**
   - `ensureRuntimeIndexesSync` wraps every top-up in bare `catch {}` — a SQLITE_BUSY,
     I/O error, or typo is swallowed identically to the intended "duplicate column".
   - `runMigrations` in schema.ts has ~60 bare `catch { /* already exists */ }` sites
     with the same problem; a swallowed real failure lets the final
     `user_version = SCHEMA_VERSION` stamp (`schema.ts:1741`) advance past a step that
     did not apply.
   - If the init migration ever fails partway *after* creating `agents`, the fresh-DB
     check (`infra.ts:52-54`) skips it forever — permanent silent partial schema.
6. panopticon.db on this machine reads `user_version = 60` with `SCHEMA_VERSION = 61`
   — the v61 step simply hasn't run since it shipped; the ladder will advance on next
   open. Not itself a defect.

## Requirements

- **FR-1**: overdeck.db carries `idx_cost_agent_id` on `cost_events(agent_id, ts)` and `idx_cost_issue_upper` on `cost_events(UPPER(issue_id))` — created by the init migration on fresh DBs and by an idempotent top-up on existing DBs, using exactly those names/definitions so the live machine's manual indexes are no-ops.
- **FR-2**: infra.ts top-ups swallow only expected errors (message matching duplicate column / already exists / no such table); any other error is logged via `console.error` naming the failing statement and SQLite message, and the remaining top-ups still run.
- **FR-3**: the schema.ts ladder swallows only duplicate column/index errors; any other step failure logs the target version and failing SQL, rethrows, and leaves `user_version` unstamped past the failed step.
- **FR-4**: a startup schema audit for overdeck.db derives expected tables/columns/indexes from the init migration plus the top-up expectations, compares against `sqlite_master` / `pragma_table_info`, and logs a `[schema-audit]` drift report. Report-only: expected ⊆ actual; extra tables/columns are never flagged (other modules create tables lazily in overdeck.db, e.g. `observation_index`, `transcripts` from `src/lib/overdeck/memory.ts`).
- **FR-5**: a driver test locks the pragma shim: `pragma('user_version = N')` then `pragma('user_version', { simple: true })` returns N under the runtime's active driver.
- **NFR-1**: the audit costs only `sqlite_master`/`pragma_table_info` reads at boot — no table scans, no writes.
- **NFR-2**: the audit never mutates the DB; top-ups remain the only healing path.

## Decisions made in this document

- **No `user_version` ladder is introduced for overdeck.db.** Its init+top-up model stays; loud failures (FR-2) plus the audit (FR-4) provide the safety the ladder would. A proper Drizzle migration journal is a larger refactor — out of scope, file separately if wanted.
- **Failure policy differs by layer, deliberately.** Top-ups log-and-continue (a missing index is degradation, and Overdeck has boot-brick history — one bad artifact must not stop the dashboard). The ladder rethrows (its steps are ordered and version-stamped; continuing past a failure corrupts the ladder's meaning).
- **Audit is report-only.** A flagged missing artifact means a top-up is missing — the fix is a code change, never a runtime mutation by the audit.
- **The partial-init skip-forever hole is detection-only in this issue.** The audit reports it; automated repair is a NonGoal.

## Intersecting repo rules restated

- Fake timers rule: not applicable (no retry/delay logic); tests use in-memory or temp-file DBs.

- Surgical changes: do not reorder or "fix" the out-of-order v61-before-v60 block at `schema.ts:1733` beyond the catch narrowing; do not touch the operator's live DB.
