# PAN-3037 — pan sync-main fails on polyrepo workspaces

**Issue:** https://github.com/eltmon/overdeck/issues/3037
**Planning mode:** `--auto` (2026-07-25)
**Campaign:** polyrepo substrate cluster — #2467 (merge train), #3040 (strike), #1696 (UAT train), #3076 (verdict anchors, filed during this planning session)

## Glossary

- **Polyrepo workspace** — a workspace directory `workspaces/feature-<issue>/` whose code lives in nested member-repo worktrees named by repo key (`<workspace>/fe`, `<workspace>/api`, …), each on its own feature branch. The workspace root is either a one-commit wrapper repo or (as observed on MIN-850) not a git repo at all. Any git operation that matters must run inside the member repos, never the root.
- **Monorepo workspace** — the ordinary case: the workspace root itself is the git worktree on `feature/<issue>`.
- **The resolver door** — `src/lib/project-repos.ts`. `resolveWorkspaceRepoRootsSync(issueId, workspacePath)` returns `WorkspaceRepoRoot[]` (`{ repoKey, dir, sourceBranch, targetBranch, isPolyrepo }`). For monorepo it returns exactly one root whose `dir` is the workspace path, so call sites loop unconditionally with **no polyrepo conditionals**. `resolveConfiguredReposSync` (src/lib/project-repos.ts:61) supplies per-repo `branch_prefix`, `default_branch`/`pr_target` fallback, forge, `mergeOrder`, and `required` (`required = repo.readonly !== true`).
- **Required repo** — a member repo with `readonly !== true`. Readonly repos carry no feature branch, so they are excluded from workspace repo roots and from sync.
- **Verdict anchor** — a stored SHA (`reviewedAtCommit`, `lastVerifiedCommit`, `roleRunHead`) compared against a live HEAD to decide re-review/staleness. The polyrepo-composite redesign of these is **out of scope here** — see [#3076](https://github.com/eltmon/overdeck/issues/3076).
- **`syncMainIntoWorkspace`** — `src/lib/cloister/merge-agent.ts:1238`. The engine behind `pan sync-main`, the dashboard "Sync with Main" button (`POST /api/issues/:issueId/sync-main`, `src/dashboard/server/routes/workspaces/merge-ops.ts:235`), and `pan start`'s prep sync (`src/cli/commands/start.ts:1038`). Those are its only two live callers.

## Problem

`syncMainIntoWorkspace(workspacePath, issueId)` runs its entire flow — `autoCommitWorkspaceChangesBeforeSync` (which calls `probeGitOperationHeads`), stale-lock cleanup, `git fetch origin main`, `git merge origin/main`, conflict handling — with `cwd` = the workspace root. On a polyrepo workspace the root is not the code repo, so the very first probe dies:

```
✖ Sync failed: MERGE_HEAD probe failed: Command failed: git rev-parse -q --verify MERGE_HEAD
fatal: not a git repository (or any of the parent directories): .git
```

The operator's comment extends scope: `pan review restart MIN-850` fails the same way (the route's branch probe at `src/dashboard/server/routes/specialists/project-routes.ts:603` runs `git branch --show-current` at the workspace root), and the fix should cover the other workspace-root `git branch --show-current` / `rev-parse` probes found by grep.

## Requirements

- **FR-1** `syncMainIntoWorkspace` iterates the workspace's repo roots from `resolveWorkspaceRepoRootsSync(issueId, workspacePath)` in resolver order, running the existing single-repo sync flow (auto-commit, lock cleanup, fetch, merge, conflict handling) with `cwd` = each root's `dir` and merge source `origin/<root.targetBranch>`.
- **FR-2** The aggregated `SyncMainResult` carries an additive per-repo breakdown (`repos: SyncMainRepoResult[]`), and the CLI + HTTP route surface per-repo outcomes (repo key, commit count / already-up-to-date / conflict files / skipped).
- **FR-3** On the first root whose sync fails (conflicts or blocked), iteration stops; that repo's merge is aborted clean (existing `ensureSyncGitQuiescent` behavior), and unattempted roots are reported as skipped.
- **FR-4** Monorepo behavior is unchanged: single root at the workspace path, top-level result fields identical to today (`changedFiles`/`conflictFiles` unprefixed), except the merge source is the configured `targetBranch` (which defaults to `main`).
- **FR-5** The review-restart route detects the branch from the primary repo root, falling back to the root's `sourceBranch` (never `'unknown'`) when the probe fails.
- **FR-6** `dispatchReviewHostSide` detects the branch from the primary repo root, falling back to the root's `sourceBranch`.
- **FR-7** The agents-listing git status (`getGitStatusAsync`) resolves the primary repo root so polyrepo agents show branch/uncommitted/latest-commit instead of `null`.
- **FR-8** `pan start`'s branch verification iterates resolver roots (each root must not be on `main`/`master`) instead of probing the workspace root and hand-scanning subdirectories.
- **FR-9** `sync-sources/skills/pan-sync-main/SKILL.md` and `docs/SPECIALIST_WORKFLOW.md` (Sync with Main section) describe the per-repo polyrepo behavior; the skill's stale "All-or-nothing for polyrepo — not implemented yet" note is replaced.
- **NFR-1** All repo discovery goes through `src/lib/project-repos.ts`. No new `workspaceConfig.type === 'polyrepo'` conditionals, no hand-rolled `.git` directory scans, no parallel resolver.
- **NFR-2** All result-shape and API changes are additive; existing consumers of `SyncMainResult` and the sync-main JSON response keep working unchanged.

## Design decisions (made here, not by the work agent)

- **D1 — iteration lives inside `syncMainIntoWorkspace`.** Both callers (route + `pan start` prep) pass `(workspacePath, issueId)` already; internal iteration fixes both with zero call-site changes.
- **D2 — stop at first failed repo** (FR-3). The issue body says "stopping on conflicts". Roots after the failed one get `skipped: true`. Roots before it keep their successful merges (no cross-repo rollback — merges are local, un-pushed, and individually recoverable with `git reset --hard ORIG_HEAD` if the operator chooses).
- **D3 — sync only required (non-readonly) repos.** `computeWorkspaceRepoRootsSync` already filters to required roots with an existing `.git`; readonly repos have no feature branch to merge into.
- **D4 — polyrepo paths are `repoKey/`-prefixed** in aggregated `changedFiles`/`conflictFiles`, matching the PAN-2948 manifest convention. Monorepo paths stay unprefixed (NFR-2).
- **D5 — primary-repo helper.** Add `resolvePrimaryWorkspaceRepoDirSync(issueId, workspacePath): string` to project-repos.ts returning `roots[0].dir` (`computeWorkspaceRepoRootsSync` always returns ≥1 root). The pattern `resolveWorkspaceRepoRootsSync(...)[0]?.dir ?? workspace` already appears at review-agent.ts:366, :549 and review-convoy.ts:301 — refactor those three to the helper.
- **D6 — dashboard git status shows primary-repo state** for polyrepo (branch/uncommitted/latest of `roots[0]`), not a per-repo aggregation. Per-repo status display is a UI feature this issue does not add.
- **D7 — merge source is `origin/<root.targetBranch>`**, not hardcoded `origin/main`. `getRepoTargetBranch` defaults to `main`, so behavior only changes for projects that configured a different default branch — where hardcoded `main` was a latent bug.

### WI-2: `syncMainIntoWorkspace` iterates repo roots (traces FR-1, FR-3, FR-4, NFR-1, NFR-2)

`src/lib/cloister/merge-agent.ts`:

1. Extract the current body of `syncMainIntoWorkspace` (lines ~1244–1360) into a module-private `async function syncMainIntoRepo(repoDir: string, issueId: string, targetBranch: string, signal?: AbortSignal): Promise<SyncMainResult>`. Inside it, replace the two hardcoded commands: `git fetch origin main` → `` `git fetch origin ${targetBranch}` `` and `git merge origin/main` → `` `git merge origin/${targetBranch}` `` (also the `ORIG_HEAD` stat collection is unchanged). All `projectPath` references become `repoDir`.
2. Extend the result types additively:

```ts
export interface SyncMainRepoResult extends SyncMainResult {
  repoKey: string;
  /** True when a prior repo's failure stopped iteration before this repo ran. */
  skipped?: boolean;
}
export interface SyncMainResult {
  success: boolean;
  alreadyUpToDate?: boolean;
  commitCount?: number;
  changedFiles?: string[];
  conflictFiles?: string[];
  reason?: string;
  repos?: SyncMainRepoResult[];   // NEW — present for every run
}
```

3. Rewrite `syncMainIntoWorkspace(projectPath, issueId, signal)`:
   - `const roots = resolveWorkspaceRepoRootsSync(issueId, projectPath);`
   - Sequentially `for (const root of roots)`: call `syncMainIntoRepo(root.dir, issueId, root.targetBranch, signal)`; push `{ repoKey: root.repoKey, ...result }`; on `success === false`, mark all remaining roots `{ repoKey, success: false, skipped: true, reason: 'skipped: earlier repo failed' }` and break.
   - Aggregate: `success` = every entry `success === true`; `alreadyUpToDate` = success && every entry `alreadyUpToDate`; `commitCount` = sum; `changedFiles`/`conflictFiles` = concatenation, `` `${repoKey}/${path}` ``-prefixed only when `roots[0].isPolyrepo`; `reason` = failing entries joined as `` `[${repoKey}] ${reason}` `` lines.
   - Preserve the existing log/`logActivity` calls, adding the repo key to messages when `isPolyrepo`.
4. `SyncGitCommandAbortError`/`SyncGitCommandTimeoutError` from a repo propagate exactly as today (the existing catch produces the cancellation result); remaining roots become skipped entries.

Tests: `src/lib/cloister/__tests__/sync-main-polyrepo.test.ts` with real temp git repos (init bare "origin" + two member worktrees on feature branches inside a wrapper directory; no fake timers needed — no retry/backoff paths are exercised, per the fake-timers rule that applies only to delay-based logic):
