# PAN-2822 — Issues pane: toggle to show/hide planned_backlog (spec-only) pipeline members

**Issue:** https://github.com/eltmon/overdeck/issues/2822 · **Planned:** 2026-07-17 (auto mode, agent:claude-fable-5)

## Glossary

- **Pipeline membership** — the single authoritative classification of an issue's pipeline state, computed by `resolvePipelineMembership()` in `src/lib/pipeline-membership.ts` from durable lenses (L1 PRs, L2 branch-vs-main, L3 issue open, L4 phase label, L6 spec).
- **Bucket** — the membership category: `in_flight`, `zombie_pr`, `post_merge_limbo`, `planned_backlog`, `clean_terminal` (`PipelineBucket` in `packages/contracts/src/types.ts:8`).
- **Spec lens (L6)** — the PAN-1966 rule: an open issue with a vBRIEF spec on `overdeck-state` and no branch/PR is `planned_backlog` (`src/lib/pipeline-membership.ts:145-150`).
- **Spec-only planned row** — an issue whose `planned_backlog` classification comes solely from the spec lens (reason string at line 147-148). `planned_backlog` can also arise from an unmerged branch with no PR (line 137) or the explicit `ready` label (line 152); those are NOT spec-only.
- **Resource-allocated tree** — `GET /api/issues/resource-allocated` (`src/dashboard/server/routes/issues.ts:897` → `src/dashboard/server/services/resource-discovery.ts`), the issue list feeding the dashboard's Issues pane, cockpit project overview, sidebar rail, and home page via the shared react-query key `command-deck-projects` (`src/dashboard/frontend/src/components/CommandDeck/projectsData.ts`).
- **Issues pane** — the "Issues" section of the CommandDeck left column (`src/dashboard/frontend/src/components/CommandDeck/index.tsx:1338-1400`), which renders the selected project's `ProjectNode` tree and an All/Alive/Failed filter row (`treeFilterRow`, ~line 1350).

## Problem

PAN-1966 (PR #2790) made any open issue with a durable vBRIEF spec `planned_backlog`, so months-old abandoned plans (PAN-532, PAN-538, PAN-608, PAN-783, PAN-804, …) now render as Idle rows in the Issues pane. By design they need disposition, but during a drain push the operator wants to see only work in motion. There is no way to hide them without corrupting membership semantics.

## Requirements

- **FR-1** — The Issues pane offers a toggle control to show/hide spec-only planned rows, defaulting to visible.
- **FR-2** — With the toggle off, exactly the rows whose only membership reason is the spec lens are hidden; all other buckets and non-spec `planned_backlog` rows render unchanged. Filtering is purely display-side.
- **FR-3** — The preference persists in localStorage (`overdeck.ui.*` convention) and survives reload.
- **FR-4** — The preference applies to every surface rendering lists/counts from the resource-allocated tree (Issues pane tree + badge, cockpit project swimlanes, sidebar rail counts, home page cards). Single-issue views are never filtered.
- **FR-5** — Membership semantics and API responses are byte-identical regardless of toggle state; `resolvePipelineMembership` classification behavior is unchanged.
- **NFR-1** — No brittle prose duplication: the spec-lens discriminator is single-sourced (an exported constant), locked by a unit test.

## Design decisions

1. **Reason-level, not bucket-level, hiding** (FR-2). AC1 of the issue says "whose only membership reason is the planned_backlog spec-lens bucket"; the title says "(spec-only)". Branch-backed and ready-label `planned_backlog` rows stay visible.
2. **Server annotates, client filters.** The frontend DTO (`ResourceAllocatedIssue`, `src/dashboard/server/services/resource-discovery.ts:80-104`) today carries only `pipelineBucket`, which cannot distinguish spec-only rows. Extract the spec-lens reason literal into `export const PLANNED_BACKLOG_SPEC_ONLY_REASON` (byte-identical output — this honors "do NOT change resolvePipelineMembership" because no classification or emitted string changes) and derive a constant `specOnlyPlanned?: boolean` in the resource-discovery mapping (~line 796: `pipelineBucket: membership.bucket`). The server never reads the toggle → FR-5 holds structurally.
3. **Preference store** mirrors `useTheme` (`src/dashboard/frontend/src/hooks/useTheme.ts`): zustand + localStorage key `overdeck.ui.showPlannedBacklog`, default `true` when missing/invalid, no server sync. Global, not per-project.
4. **Toggle placement:** the Issues pane's existing filter row (All/Alive/Failed). The issue said "near the existing Policies control", but no Policies control exists in that pane header — `IssuePolicyStrip` is a per-issue control (`IssueHeader.tsx:324`). The filter row is the pane's display-filter affordance.
5. **File-size ratchet:** `CommandDeck/index.tsx` is exactly at its 1537-line baseline (`scripts/file-size-baseline.txt:6`) and the ratchet forbids growth, so the filter row + toggle are extracted into a new `IssuesPaneFilterRow.tsx`; the baseline is not edited.
6. **Stale-cache safety:** the filter hides only `specOnlyPlanned === true`; an undefined field (old cache/server) degrades to today's behavior, never over-hiding.
7. **Known consequence:** an issue with both a spec and the `ready` label carries the spec-lens reason (resolver checks `hasVbriefSpec` first) and is hidden when the toggle is off. Accepted — it is planned work not in motion.
