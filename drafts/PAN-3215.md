# PAN-3215 — DoD gate verify-merged: GitLab + polyrepo merge evidence

## Glossary

- **DoD gate** — the Definition-of-Done audit that `pan close` runs before
  teardown. Row 4 (`merged`) must pass with accurate evidence.
- **verify-merged path** — `verifyBranchMergedImpl()` in
  `src/lib/lifecycle/workflows.ts`, the `verifyMerged` step the DoD gate's
  `checkMergedRow()` (`src/lib/lifecycle/dod-gate.ts`) calls first.
- **Convention branch** — `feature/<issue>` or `strike/<issue>` (lowercased
  issue id), the two branch names the verify-merged path probes.
- **Branch-containment fallback** — when `verifyMerged` returns the
  branch-absent sentinel, `checkMergedRow()` asks
  `gatherIssueBranchContainment()` (the membership L2-work lens,
  `src/lib/pipeline-membership-gather.ts:456`) whether the work is contained
  in the default branch anyway, and passes row 4 with evidence labeled
  `non-PR landing`.
- **Forge oracle** — a lookup that asks the forge (GitHub/GitLab) whether a
  merged review artifact (PR/MR) exists for a branch. Today only GitHub has
  one in this path (`verifySquashMergedPrByBranch`).
- **Repo root** — a `{ dir, sourceBranch, targetBranch, forge }` quadruple
  naming one git checkout the verification runs against. Monorepo: one root
  at `ctx.projectPath`. Polyrepo (e.g. mind-your-now): one root per
  configured sub-repo (`fe`, `api`, `infra`, `docs`, …).
- **Head-sha discipline** — matching a merged MR's `sha` against the branch
  tip (`git rev-parse <ref>`) before accepting it as evidence, the same
  check `assessRepoMergeCompleteness()`
  (`src/lib/cloister/merge-completeness.ts:147-160`) already applies for
  GitLab.

## Problem

`pan close MIN-908` (2026-07-28) passed DoD row 4 only through the
branch-containment fallback with evidence reading
`non-PR landing (membership L2-work lens)` — while MR !75 sat merged on
GitLab the whole time. Two stacked gaps:

1. **GitHub-only PR oracle.** `verifySquashMergedPrByBranch`
   (`src/lib/lifecycle/workflows.ts:710`) returns `null` immediately when
   `!ctx.github`, and its only query is
   `gh pr list --state merged --head <branch>`. No GitLab equivalent exists
   in this path, so a squash-merged GitLab branch always falls through.
2. **Monorepo-scoped git checks.** `verifyConventionBranchMerged`
   (`src/lib/lifecycle/workflows.ts:555`) runs `git branch --list`,
   `git merge-base --is-ancestor`, and `git diff main...<branch>` in
   `ctx.projectPath`. For polyrepo mind-your-now, `projectPath` is the
   wrapper dir; the convention branches live in the sub-repos
   (`fe`, `api`, …), so every probe comes back empty and the function
   returns the branch-absent sentinel. Same consumer-blindness family as
   PAN-2948 / PAN-2956.

Additionally `checkMergedRow()` (`src/lib/lifecycle/dod-gate.ts:372-390`)
only enriches row 4 with forge metadata `if (ctx.github)`, so even a
correctly detected GitLab MR would never be named in the observed evidence.

The row still passes, so this is mislabeled audit evidence plus dependence
on a fallback — but a gate whose purpose is accurate evidence must not call
an MR landing a "non-PR landing".

## Proposal

Three coordinated changes, all inside the existing verify-merged surface:

1. **Parameterize the convention-branch verification on a repo root.**
   `verifyConventionBranchMerged` and `verifyRemoteBranchIfPresent` take a
   root `{ dir, sourceBranch, targetBranch, forge }` instead of running in
   `ctx.projectPath` against hardcoded `main`. A single default root derived
   from `ctx.projectPath` + `main` reproduces today's commands byte-for-byte,
   so monorepo behavior and the existing mocked-command test suite are
   unchanged.

2. **Add a GitLab squash-merge oracle.** Reuse the existing forge adapter:
   `getForgeAdapter('gitlab').findMergedArtifact()`
   (`src/lib/forge.ts`, added by PAN-2882 as commit `1ac4841532`
   "feat(forge): find merged review artifacts" — the issue body's
   `src/lib/gitlab-merge-requests.ts` name is stale; this is its actual
   home). Following the head-sha discipline from
   `assessRepoMergeCompleteness`: `git rev-parse <branchRef>` in the repo
   root, then `findMergedArtifact({ sourceBranch, targetBranch, headSha, cwd })`,
   which requires the merged MR's `sha` to equal the branch tip via
   `matchesCurrentArtifact`. On a match, return `stepOk` naming the MR:
   `MR !75 is merged and <ref> matches the merged MR head (<url>)`.
   Placement: immediately after `merge-base --is-ancestor` fails (before
   the diff-empty heuristic) so a real merged MR is recorded as evidence
   instead of the anonymous "squash-merged" label; and alongside the GitHub
   check in the remote-branch path. GitHub ordering and logic are untouched.

3. **Loop resolved repos and record MR evidence in the DoD row.**
   `verifyBranchMergedImpl` resolves repos with
   `resolveProjectReposForIssueSync(ctx.issueId)`
   (`src/lib/project-repos.ts:95`), runs the per-root verification for every
   required repo, and aggregates: any per-root failure → `stepFailed` with
   repo-qualified detail; at least one pass and the rest branch-absent →
   `stepOk` with repo-prefixed evidence; all absent → the branch-absent
   sentinel (drives the existing durable-merge/containment machinery
   unchanged). In `checkMergedRow`, a new `readMergedForgeArtifacts` dep
   (default: resolve repos, `findMergedArtifact` per required repo, no
   headSha — the branch may already be deleted at close time) supplies
   merged-MR evidence for non-GitHub contexts: appended to `observed`, and
   accepted as forge evidence in the branch-absent path so a deleted-branch
   GitLab squash-merge passes naming its MR instead of
   "no merged forge artifact … found" + containment.

The `MergedDodRowResult.evidence` union is NOT extended: `evidence` stays
`'branch-containment' | undefined`, so `checkPostMergeRow`'s containment
special case fires only when containment genuinely supplied the evidence.

## Decision rules (made here, not at implementation time)

- **Oracle choice is per-repo `forge`, never project-level.** A GitLab
  project may contain GitHub repos (mind-your-now does). For a github-forge
  root, only the GitHub oracle runs (and only when `ctx.github` is set, as
  today); for a gitlab-forge root, only the GitLab oracle runs.
- **GitLab requires exact head-sha match in the verify-merged path.** No
  port of the GitHub post-PR-commit policy (post-PR commits on main,
  state-plane-only deltas). On mismatch the flow falls through to the
  existing heuristics and fallbacks.
- **Resolution failure falls back to the synthetic single root.** When
  `resolveProjectReposForIssueSync` returns `null` (unconfigured project,
  hermetic CI), behavior is byte-identical to today.
- **Readonly repos are excluded** (`repo.required === false`), matching
  `assessRepoMergeCompleteness`.
- **Strike branch probe is per-root:** candidates are
  `[root.sourceBranch, strike/<issue>]` per repo.

## Requirements

### Functional

- FR-1: For a gitlab-forge repo root whose convention branch tip equals a
  merged MR's `sha`, `verifyBranchMergedImpl` returns success with the MR
  iid and URL in `details`, without consulting the branch-containment
  fallback.
- FR-2: For a polyrepo project, every git probe in the verify-merged path
  executes in each required repo's `repoPath` against that repo's
  `targetBranch`; no probe runs only in the wrapper `projectPath`.
- FR-3: Polyrepo aggregation passes only when no required repo reports
  unmerged work and at least one repo produced positive merge evidence;
  per-repo evidence strings name their repo.
- FR-4: When the convention branch is absent everywhere but a merged MR
  exists for it, `checkMergedRow` passes row 4 with the MR iid/URL in
  `observed` (not "no merged forge artifact … found" and not
  "non-PR landing").
- FR-5: The branch-containment fallback remains as last resort and still
  sets `evidence: 'branch-containment'` only when it actually supplied the
  pass.

### Non-functional

- NFR-1: Monorepo GitHub behavior is byte-identical: existing
  `workflows.test.ts` and `dod-gate.test.ts` verify-merged suites pass
  unmodified.
- NFR-2: GitLab MR lookups run at most once per required repo per merged-row
  evaluation, in parallel (`Promise.all`).

## NonGoals

- No GitHub-path changes: `verifySquashMergedPrByBranch` logic and ordering
  are untouched.
- No port of the GitHub post-PR-commit policies (post-PR commits already on
  main, state-plane-only deltas) to GitLab; exact head-sha match only.
- No GitLab equivalent of the `gh issue view` closed-issue skip; tracker
  settlement is already handled by PAN-3187's terminal-verdict settlement.
- No changes to row 6 (main-verify) or row 7 (deploy), which have their own
  GitHub-only paths — separate issues.
- No changes to `assessMergeCompleteness` / `observeForgeMergeState`
  (merge-gate surface, already GitLab-aware via PAN-2882).
- No `MergedDodRowResult.evidence` union extension and no post-merge row
  changes.
