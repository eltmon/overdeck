## 1. Glossary

Terms of art this document uses. Every one is defined here before it appears in a work item.

| Term | Definition |
| --- | --- |
| **UAT** | User Acceptance Testing — the browser-driven acceptance check the `test` role runs with Playwright against the running app. Recorded as a *separate* verdict from the automated test gate: `uatStatus` / `uatNotes`, not `testStatus` / `testNotes`. |
| **UAT verdict** | A write of `uatStatus: 'passed' \| 'failed'` (plus optional `uatNotes`) into the review-status row. |
| **Review-status row** | The per-issue pipeline gate record (`ReviewStatus`, `src/lib/review-status-types.ts:20`). Holds `reviewStatus`, `testStatus`, `uatStatus`, `mergeStatus`, `readyForMerge`, and their notes. |
| **Write door** | The single function permitted to mutate a domain's canonical state. For review status this is `setReviewStatus()` in `src/lib/review-status.ts:~180`. Every caller — REST route, CLI, deacon patrol — goes through it. |
| **Feedback file** | A markdown file written into the work agent's workspace under `<workspace>/.overdeck/feedback/NNN-<specialist>-<outcome>.md` by `writeFeedbackFile()` (`src/lib/cloister/feedback-writer.ts:91`). Also appended to the per-issue continue state's `feedback[]`. |
| **Feedback target door** | `resolveIssueFeedbackTarget(issueId)` in `src/lib/cloister/feedback-target.ts:73`. Returns either `{ agentId }` (a live or successfully-resurrected work agent) or `{ needsYou: true, reason }`. It owns the whole resurrection ladder: live session → assigned swarm slot → unregistered live slot → registered work agent → unpause/untrouble/resume/start. |
| **needs-you trip** | `surfaceIssueFeedbackNeedsYou(issueId, reason, details)` in `src/lib/cloister/feedback-target.ts:260`. Marks the review-status row stuck with `FEEDBACK_DELIVERY_STUCK_REASON` so the operator sees an escalation instead of silence. |
| **Relay** | A module that turns a pipeline verdict into (a) a feedback file and (b) a delivery through the feedback-target door. Existing relays: `ci-failure-feedback.ts`, `review-verdict-feedback.ts`, and the inline `deliverTestFailureToWorkAgentHostSide()` in `review-status.ts:697`. |
| **Parked orbit** | One of the nine states in which an issue sits with no autonomous owner. Classified by the pure function `classifyParked()` in `src/lib/parked/resolver.ts:225`. `uat-failed` is orbit #5. |
| **Stall sweeper** | `src/lib/cloister/stall-sweeper.ts` — observability-only patrol that emits an operator recommendation per parked orbit. It never acts. |
| **Anchor** | A commit SHA identifying which code state a verdict was recorded against. `ReviewStatus.reviewedAtCommit` is snapshotted when review passes (`src/dashboard/server/routes/workspaces.ts:1466-1469`). Used here as the dedup key so one UAT failure produces one feedback file. |

## 2. Problem

A failed UAT verdict is durably recorded and then **nothing acts on it**.

`setReviewStatus()` counts a failed UAT as a merge blocker, so the merge gate correctly refuses:

```ts
// src/lib/review-status.ts:292
const hasBlockers = (merged.blockerReasons?.length ?? 0) > 0 || merged.uatStatus === 'failed';
```

But no code path writes a feedback file, messages the work agent, or escalates. The issue lands in the `uat-failed` parked orbit, whose own copy already names the defect:

```ts
// src/lib/parked/resolver.ts:312-321
if (!closed && r?.uatStatus === 'failed' && r.mergeStatus !== 'merged' && !r.readyForMerge) {
  push(
    'uat-failed',
    isoOr(r.updatedAt, s.now),
    'UAT failed after review and test passed — the merge gate will not take it and nothing routed the failure back to work',
    'route the UAT failure notes to the work agent as a rework kickoff through the existing work-resume door',
    { uatNotes: r.uatNotes ?? null },
  );
}
```

Compare the three verdicts that *do* route back:

| Verdict | Relay | Wired at |
| --- | --- | --- |
| `reviewStatus: blocked/failed` | `deliverReviewVerdictFeedback()` (`review-verdict-feedback.ts:126`) + an inline route relay | `workspaces.ts:1500-1531` and the registered write-door adapter (`review-pipeline.ts:68`) |
| `testStatus: failed` | `deliverTestFailureToWorkAgentHostSide()` (`review-status.ts:697`) | `review-status.ts:509-514`, fired on the transition inside the write door |
| CI checks failing | `relayCiFailureFeedback()` (`ci-failure-feedback.ts:289`) | GitHub webhook / status handler |
| **`uatStatus: failed`** | **none** | **nowhere** |

### 2.1 Why the route is the wrong wiring point

The issue body proposes wiring the relay into the `uatStatus` branch of the status route. That branch is real (`src/dashboard/server/routes/workspaces.ts:1475`), but it is **one of three** writers of `uatStatus: 'failed'`:

1. `POST /api/review/:issueId/status` — the test agent's `curl` (`workspaces.ts:1444-1483`). The prompt that generates this call is `src/lib/cloister/test-agent-queue.ts:52-56`.
2. `POST /api/specialists/done` → `case 'uat'` (`src/dashboard/server/routes/specialists/legacy-routes.ts:241-247`), reached by `pan admin specialists done uat --status failed`.
3. The deacon's unsignaled-verdict auto-complete, which replays `.pan/test/result.json` (`src/lib/cloister/deacon.ts:1452-1455`).

All three converge on `setReviewStatus()`. Wiring only the route would leave paths 2 and 3 silently unwired — the exact class of gap this issue exists to close. `deliverTestFailureToWorkAgentHostSide()` already establishes the correct pattern for this repo: fire the relay from the **transition inside the write door**, so every caller is covered by one wiring.

This is a deliberate deviation from the issue body's step 3, recorded as an auto-decision (§6, D1). The issue's acceptance criterion — "`uatStatus: 'failed'` with notes writes exactly one feedback file … and delivers it to a live work agent" — is satisfied transitively, because the route calls `setReviewStatus()` at `workspaces.ts:1483`.

## 3. Requirements

### Functional

- **FR-1** — A `uatStatus: 'failed'` write through `setReviewStatus()` writes exactly one feedback file for that verdict, with `specialist: 'uat-agent'` and `outcome: 'failed'`, containing the `uatNotes`.
- **FR-2** — The relay resolves its delivery target through `resolveIssueFeedbackTarget()` and, when the target is an agent, sends the standard `SPECIALIST FEEDBACK … MUST READ: <path>` message through `messageAgent()` with `owesRework: true`.
- **FR-3** — When `resolveIssueFeedbackTarget()` returns `{ needsYou }`, the relay calls `surfaceIssueFeedbackNeedsYou()` with the target's reason instead of returning silently.
- **FR-4** — When the resolved agent exists but the message throws, the relay surfaces a needs-you trip carrying the failure reason (mirrors `review-verdict-feedback.ts:275-288`).
- **FR-5** — Re-posting the same failed UAT verdict against the same anchor does not write a second feedback file; a UAT failure recorded against a *different* anchor does deliver again.
- **FR-6** — A `uatStatus` write of any non-`failed` value clears the dedup anchor for that issue, so the next genuine failure is delivered even when no anchor SHA is available.
- **FR-7** — The relay is fired from the `uatStatus` transition inside `setReviewStatus()`, so the REST status route, `pan admin specialists done uat`, and the deacon auto-complete are all covered by one wiring.
- **FR-8** — The `uat-failed` parked orbit is not emitted while a live work agent exists for that issue; with no live work agent it is emitted with copy naming the relay as the owner that failed to find a target.
- **FR-9** — The stall sweeper's `uat-failed` recommendation names the start path (`pan start <id>`) rather than claiming nothing routed the failure.

### Non-functional

- **NFR-1** — The relay module must not be statically imported by `src/lib/review-status.ts`. `feedback-target.ts:266` dynamically imports `../review-status.js`; a static edge in the other direction creates a circular ESM dependency that Node's strict ESM rejects at dashboard boot (see the CLAUDE.md "Dashboard Server: Node 22 Only" section). Use `await import()` at the fire site, exactly as `deliverTestFailureToWorkAgentHostSide()` does at `review-status.ts:713`.
- **NFR-2** — The relay must never throw into `setReviewStatus()`. It is fired fire-and-forget (`void`) and swallows every recoverable error with a `console.warn`, matching `review-status.ts:722-724`.
- **NFR-3** — No new patrol, timer, or nudge channel. Only `writeFeedbackFile()`, `resolveIssueFeedbackTarget()`, `surfaceIssueFeedbackNeedsYou()`, and `messageAgent()` may be used for delivery.
- **NFR-4** — No `execSync` anywhere in the new code (dashboard-reachable path).
- **NFR-5** — New tests must not rely on real wall-clock delays; there is no retry/backoff in this change, so no fake-timer setup is required, but any future delay must use `vi.useFakeTimers()`.

## 4. Design

### 4.1 New module — `src/lib/cloister/uat-failure-feedback.ts`

Modeled on `review-verdict-feedback.ts` (doors + needs-you) with the anchor dedup from `ci-failure-feedback.ts:60-66,214-219`.

```ts
/**
 * UAT failure feedback relay (PAN-3575).
 *
 * A failed UAT verdict blocks the merge gate (review-status.ts:292) but had no
 * autonomous owner: the issue sat in the `uat-failed` parked orbit until an
 * operator noticed. This relay routes the failure back to the work agent through
 * the same two doors review and test failures use — writeFeedbackFile() for the
 * durable artifact, resolveIssueFeedbackTarget() for delivery — and escalates
 * with surfaceIssueFeedbackNeedsYou() when no target can be resurrected.
 *
 * Dedup is anchored on the reviewed commit so one failed verdict produces one
 * feedback file even when the verdict is re-posted (route retry, deacon replay).
 */
import { join } from 'node:path';
import { Effect } from 'effect';

import { messageAgent } from '../agents/messaging.js';
import { resolveProjectFromIssueSync } from '../projects.js';
import { writeFeedbackFile } from './feedback-writer.js';
import { resolveIssueFeedbackTarget, surfaceIssueFeedbackNeedsYou } from './feedback-target.js';

export interface UatFailureFeedbackOptions {
  issueId: string;
  uatNotes?: string;
  /** Defaults to <project>/workspaces/feature-<issue>. */
  workspacePath?: string;
  /** Dedup anchor — normally ReviewStatus.reviewedAtCommit. */
  anchor?: string;
}

export interface UatFailureFeedbackResult {
  feedbackPath?: string;
  agentMessageSent: boolean;
  needsYouSurfaced: boolean;
  deduplicated: boolean;
}

/** Per-issue anchor the last UAT failure feedback was delivered for. */
const lastNotifiedAnchor = new Map<string, string>();

/** Clear the dedup anchor — called when uatStatus leaves 'failed'. */
export function clearUatFailureFeedbackAnchor(issueId: string): void {
  lastNotifiedAnchor.delete(issueId.toUpperCase());
}

/** Reset internal dedup state — for tests only. */
export function resetUatFailureFeedbackStateForTests(): void {
  lastNotifiedAnchor.clear();
}

function buildUatFeedbackBody(issueId: string, uatNotes?: string): string {
  const notes = uatNotes?.trim()
    || 'The UAT gate reported a failure but recorded no notes. Re-run the browser acceptance pass and inspect the UAT panel.';
  return `# UAT FAILED for ${issueId}\n\n`
    + `Browser acceptance verification did not prove the issue's acceptance criteria.\n\n`
    + `## Unmet criteria and evidence\n\n${notes}\n\n`
    + `## Required action\n\n`
    + `Fix the behavior each unmet criterion describes, commit the fixes, then invoke the `
    + `/rebase-and-submit skill for ${issueId}. Do NOT stop at the prompt.\n`;
}

export async function relayUatFailureFeedbackPromise(
  opts: UatFailureFeedbackOptions,
): Promise<UatFailureFeedbackResult> { /* … see work item 1 … */ }

export const relayUatFailureFeedback = (
  opts: UatFailureFeedbackOptions,
): Effect.Effect<UatFailureFeedbackResult> => Effect.promise(() => relayUatFailureFeedbackPromise(opts));
```

Body of `relayUatFailureFeedbackPromise`, step by step:

1. `const issueId = opts.issueId.toUpperCase()`.
2. `const anchor = opts.anchor ?? ''`. If `lastNotifiedAnchor.get(issueId) === anchor` **and** the map has an entry for `issueId`, return `{ agentMessageSent: false, needsYouSurfaced: false, deduplicated: true }` and log one `console.log`. (Using `Map.has` + equality means an empty anchor still dedups against a prior empty-anchor delivery, and FR-6's clear re-arms it.)
3. Resolve `workspacePath` from `opts.workspacePath` or `resolveProjectFromIssueSync(issueId)` → `join(resolved.projectPath, 'workspaces', 'feature-' + issueId.toLowerCase())`. Mirrors `ci-failure-feedback.ts:239-242`.
4. `writeFeedbackFile({ issueId, workspacePath, specialist: 'uat-agent', outcome: 'failed', summary: 'UAT FAILED: ' + (opts.uatNotes ?? '').slice(0, 80), markdownBody })` via `Effect.runPromise`. On `!success`, `console.error` and return `{ agentMessageSent: false, needsYouSurfaced: false, deduplicated: false }` **without** recording the anchor, so a later retry can still deliver.
5. Set `lastNotifiedAnchor.set(issueId, anchor)` immediately after a successful file write — the file is the thing FR-5 dedups on.
6. `const target = await resolveIssueFeedbackTarget(issueId)`.
7. If `'agentId' in target`: build the message
   `SPECIALIST FEEDBACK: uat-agent reported UAT FAILED for <ID>.\n\nMUST READ: <path>\n\nUse your Read tool to open this file, read every line, then fix every unmet acceptance criterion and re-submit. Do NOT stop at the prompt.`
   and `await messageAgent(target.agentId, message, 'internal', { owesRework: true })`. On success set `agentMessageSent = true`. On throw, `console.warn` then `await surfaceIssueFeedbackNeedsYou(issueId, 'UAT feedback delivery to <agentId> failed: <reason>', { specialist: 'uat-agent', feedbackPath })` and set `needsYouSurfaced = true`.
8. Else (`needsYou`): `await surfaceIssueFeedbackNeedsYou(issueId, target.reason, { specialist: 'uat-agent', feedbackPath })`, `needsYouSurfaced = true`.
9. Wrap steps 6-8 in a `try/catch` that `console.warn`s — NFR-2.

`specialist: 'uat-agent'` is already a legal value of the `WriteFeedbackOptions.specialist` union (`feedback-writer.ts:19`); no type change is needed.

**No keyed/dedup-key `messageAgent` delivery.** `review-verdict-feedback.ts` uses `dedupKey` plus an ambiguous-delivery retry ladder because a review cycle can re-fire many times per anchor. The UAT relay's own anchor map already guarantees one delivery per verdict, so the extra machinery is not warranted (§6, D3).


**After**:

```ts
  if (
    (update.testStatus === 'failed' || update.testStatus === 'dispatch_failed') &&
    status.testStatus !== 'failed' && status.testStatus !== 'dispatch_failed'
  ) {
    void deliverTestFailureToWorkAgentHostSide(issueId, updated);
  }

  // PAN-3575: UAT FAILED → hand it back to the work agent through the same doors
  // review and test failures use. Fired from the write door, not the status route,
  // because three callers write this verdict (the test agent's REST POST, `pan admin
  // specialists done uat`, and the deacon's unsignaled-verdict replay) and only the
  // door sees all three. Duplicate verdicts are absorbed by the relay's anchor dedup.
  if (update.uatStatus === 'failed') {
    void deliverUatFailureToWorkAgentHostSide(issueId, updated);
  } else if (update.uatStatus) {
    void clearUatFailureAnchorHostSide(issueId);
  }

  return updated;
```

And the two module-private helpers, placed next to `deliverTestFailureToWorkAgentHostSide` (`review-status.ts:697`):

```ts
async function deliverUatFailureToWorkAgentHostSide(issueId: string, status: ReviewStatus): Promise<void> {
  try {
    // Dynamic import — feedback-target.ts imports review-status.js, so a static
    // edge here would close a circular ESM cycle that Node strict ESM rejects at boot.
    const { relayUatFailureFeedbackPromise } = await import('./cloister/uat-failure-feedback.js');
    const result = await relayUatFailureFeedbackPromise({
      issueId,
      ...(status.uatNotes ? { uatNotes: status.uatNotes } : {}),
      ...(status.reviewedAtCommit ? { anchor: status.reviewedAtCommit } : {}),
    });
    if (result.agentMessageSent) {
      console.log(`[review-status] delivered UAT failure to the work agent for ${issueId} (host-side)`);
    }
  } catch (err) {
    console.warn(`[review-status] host-side UAT-failure delivery for ${issueId} did not complete (non-fatal): ${err instanceof Error ? err.message : String(err)}`);
  }
}

async function clearUatFailureAnchorHostSide(issueId: string): Promise<void> {
  try {
    const { clearUatFailureFeedbackAnchor } = await import('./cloister/uat-failure-feedback.js');
    clearUatFailureFeedbackAnchor(issueId);
  } catch { /* non-fatal — the anchor only affects dedup */ }
}
```

Note the fire condition is `update.uatStatus === 'failed'`, **not** a transition guard (`status.uatStatus !== 'failed'`). The anchor map is the dedup mechanism (FR-5), and it is strictly better than a transition guard: a second genuine failure on a *new* anchor still delivers, which a transition guard would swallow.

### 4.3 Parked orbit — `src/lib/parked/resolver.ts`

**Before** (`resolver.ts:312-321`) — quoted in §2.

**After**:

```ts
  // 5. uat-failed — passed review+test but UAT failed and no work agent owns the rework.
  //    PAN-3575 gave this orbit an owner: setReviewStatus fires the UAT-failure relay,
  //    which resurrects and messages the work agent. So the orbit only means "the relay
  //    could not put anyone on it" — a live work agent IS the rework owner, not a park.
  const hasLiveWorkAgent = s.liveAgents.some((agent) => agent.role === 'work');
  if (!closed && r?.uatStatus === 'failed' && r.mergeStatus !== 'merged' && !r.readyForMerge && !hasLiveWorkAgent) {
    push(
      'uat-failed',
      isoOr(r.updatedAt, s.now),
      'UAT failed and no work agent is live to rework it — the merge gate will not take the issue and the UAT-failure relay found no delivery target',
      'pan start <id> to put a work agent on the UAT feedback; the relay redelivers on the next failed verdict',
      { uatNotes: r.uatNotes ?? null },
    );
  }
```

`s.liveAgents` is already gathered (`resolver.ts:170-171`, used by the zombie-session and idle-running orbits) and `AgentState.role` is already read elsewhere in the same function (`IDLE_EXEMPT_ROLES` check at `resolver.ts:370`). No signal-gathering change is needed.

Interaction with `idle-running`: that orbit only fires when `rows.length === 0` *and* the agent has been idle ≥ 6h *and* `shouldSkipReviewStatus(r)` is false (`resolver.ts:361-383`). Suppressing `uat-failed` for a live work agent can therefore let `idle-running` fire for an agent that has genuinely done nothing for six hours — which is the correct signal, not a regression.

### 4.5 What is deliberately not built

- No new patrol, cron, timer, or second nudge channel (NFR-3, and the issue's step 4).
- No new `stuckReason` flavor — the relay reuses `FEEDBACK_DELIVERY_STUCK_REASON` through `surfaceIssueFeedbackNeedsYou()`, so `scripts/guard-park-exits.sh` needs no new copy entry.
- No UAT activity-log or TTS entry in `setReviewStatus()` (the `uatStatus` transition has no `emitActivityEntrySync` map today, unlike review/test/merge/verification). Adding one is a separate observability change.
- No PR comment on UAT failure. `review-verdict-feedback.ts` posts one for review verdicts; UAT gets the feedback file and the agent message only.
- No change to `readyForMerge`/blocker semantics — `review-status.ts:292` already blocks the merge gate correctly.

## 8. Intersecting repo rules restated for the executor

- **No `execSync`** anywhere in this change — it is dashboard-server-reachable code. Use async primitives only.
- **Fake timers** are mandatory for any test that exercises retry/backoff/delay. This change introduces none; do not add a real `setTimeout` to a test.
- **Async tmux only** — `sendKeysAsync`, never `sendKeys`. This change does not touch tmux directly; `messageAgent` owns delivery.
- **Single source of truth** — reach canonical state only through the resolver/writer doors. `setReviewStatus()` is the review-status write door; `resolveIssueFeedbackTarget()` and `writeFeedbackFile()` are the feedback doors. Do not add a parallel path.
- **Circular ESM** — `src/lib/review-status.ts` must reach the new relay through `await import()` only (NFR-1). A static import breaks dashboard boot under Node strict ESM, and typecheck will not catch it.
- **Push every item before completing it** — commit one xBRIEF item at a time and push the feature branch before `pan task done`.
