# PRD — PAN-3367: Code-level audit of 29 verdict-laundered issues

**Issue:** https://github.com/eltmon/overdeck/issues/3367
**Companion guard issue:** [PAN-3365](https://github.com/eltmon/overdeck/issues/3365) (prevents recurrence; this issue is the cleanup)
**Planning mode:** `--auto` (decisions recorded in `autoDecisions[]` of the xBRIEF)

## Glossary

- **Negative verdict** — a `review.status_changed` event whose status has `reviewStatus` or `testStatus` equal to `failed` or `blocked`.
- **Reset** — a subsequent `review.status_changed` event with state `pending/pending`.
- **Laundered pass** — a `passed/passed` state reached within 60 minutes of a negative verdict, after a reset, with zero commits on the feature branch in between. The pass replaced the verdict instead of being earned.
- **Worklist** — the set of issues this audit covers: the 25 named in the PAN-3367 body (mandatory) plus derived extras (see "Worklist derivation").
- **Evidence snapshot** — the committed JSON dump of raw `review.status_changed` events per worklist issue, taken before the 7-day event retention deletes more of it.
- **Audit verdict** — per issue, exactly one of: `satisfied` (the merged diff satisfies the failing acceptance criterion), `not satisfied` (it does not), `cannot determine` (the criterion is not verifiable from code alone, e.g. environment-blocked browser UAT).
- **Failing AC** — the specific acceptance criterion the recorded negative verdict was about. The audit question is always about this criterion, never about the change as a whole.

## Background

PAN-3365 established the mechanism: a negative verdict can be reset to `pending/pending` and replaced with `passed/passed` with no commits in between, so the pipeline records a pass that was never earned. The flywheel (RUN-75) queried the event log and found 29 issues matching the sharp signature (negative → reset → passed/passed within 60 minutes) spanning 2026-07-25 to 07-28; four spot-checked cases all had zero commits between failure and pass. PAN-3367 is the audit: for each affected issue, decide at the code level whether the merged diff actually satisfied the failing AC.

**This is a read-only audit producing a report.** It re-runs nothing, re-verdicts nothing, and fixes nothing. Gaps found are filed as follow-up issues.

2. **Retention hazard** — the events table has **7-day retention with startup compaction** (`src/dashboard/server/event-store.ts`: `compact()` declared at lines 124-125, `DELETE FROM events WHERE timestamp < ?` at line ~308-309, compaction log line ~512). At planning time the oldest surviving `review.status_changed` event is 2026-07-24. The `feedback` array may be empty (verified empty for PAN-3216) — do not rely on it as the failure-reason source. 4. **Acceptance criteria (PAN)** — `gh issue view <n> --repo eltmon/overdeck` (gh is authenticated; verified). Where present, also the xBRIEF spec's acceptance criteria: `~/.overdeck/state/panopticon-cli/specs/*<issue-id>*` and the PRD draft `~/.overdeck/state/panopticon-cli/drafts/<issue-id>.md`.
5. **Acceptance criteria (MIN)** — Linear GraphQL API. Key: `LINEAR_API_KEY` in `~/.overdeck.env` (verified present; **never print or commit the key**). Query: `curl -s https://api.linear.app/graphql -H "Authorization: $LINEAR_API_KEY" -H "Content-Type: application/json" -d '{"query":"{ issue(id: \"MIN-858\") { title description } }"}'` with the key loaded via `set -a; . ~/.overdeck.env; set +a`.
6. **Merged diffs (PAN)** — `gh pr diff <prNumber> --repo eltmon/overdeck`, PR number from the record's `pipeline.prUrl` (verified: PAN-3216 → PR #3219, PAN-3356 → PR #3360, PAN-1525 → PR #3033). Cross-check with the merge commit on `main` (`git log --oneline main --grep="<issue>"`).
7. **Merged diffs (MIN)** — the MYN product spans two repos: `~/Projects/myn` (frontend, GitHub) and `~/Projects/myn-cli` (backend, GitLab). `glab` is authenticated to gitlab.com as eltmon (verified). This is branch-independent, so it survives branch deletion at close-out. Fallback: `git ls-remote --heads origin feature/<id>` to verify the branch exists, then `git log --since=<negAt> --until=<passAt> --oneline feature/<id>`. **Reproduction script** (validated at planning time against the live DB — it reproduces every named issue whose events survive). Save as `docs/audits/pan-3367/evidence/reproduce-worklist.mjs` and run with Node 22 from the workspace:

```js
import { DatabaseSync } from 'node:sqlite';
import { writeFileSync, mkdirSync } from 'node:fs';
const HOME = process.env.HOME;
const db = new DatabaseSync(`${HOME}/.overdeck/overdeck.db`, { readOnly: true });
const rows = db.prepare(
  "SELECT sequence, timestamp, payload FROM events WHERE type='review.status_changed' ORDER BY sequence ASC",
).all();
const byIssue = new Map();
for (const r of rows) {
  let p; try { p = JSON.parse(r.payload); } catch { continue; }
  if (!p.issueId || !p.status) continue;
  const rs = p.status.reviewStatus, ts = p.status.testStatus;
  if (!rs || !ts) continue;
  const t = typeof r.timestamp === 'number' ? r.timestamp : Date.parse(r.timestamp);
  if (!byIssue.has(p.issueId)) byIssue.set(p.issueId, []);
  byIssue.get(p.issueId).push({ t, state: `${rs}/${ts}`, raw: r });
}
const HOUR = 3600e3;
const NEG = (s) => { const [a, b] = s.split('/'); return ['failed','blocked'].includes(a) || ['failed','blocked'].includes(b); };
const candidates = [];
mkdirSync('docs/audits/pan-3367/evidence', { recursive: true });
for (const [id, evs] of byIssue) {
  const seq = evs.filter((e, i) => i === 0 || e.state !== evs[i - 1].state); // collapse consecutive dupes
  let hit = null;
  for (let i = 0; i < seq.length && !hit; i++) {
    if (!NEG(seq[i].state)) continue;
    let sawPending = false;
    for (let j = i + 1; j < seq.length; j++) {
      if (seq[j].t - seq[i].t > HOUR) break;
      if (seq[j].state === 'pending/pending') { sawPending = true; continue; }
      if (seq[j].state === 'passed/passed' && sawPending) {
        hit = { issueId: id, negState: seq[i].state, negAt: new Date(seq[i].t).toISOString(),
                passAt: new Date(seq[j].t).toISOString(), minutes: Math.round((seq[j].t - seq[i].t) / 60e3),
                negNotes: JSON.parse(seq[i].raw.payload).status.reviewNotes ?? JSON.parse(seq[i].raw.payload).status.testNotes ?? null };
        break;
      }
    }
  }
  if (!hit) continue;
  candidates.push(hit);
  // Dump the issue's full raw event series verbatim — this is the forensic evidence.
  writeFileSync(`docs/audits/pan-3367/evidence/events-${id.toLowerCase()}.json`,
    JSON.stringify(evs.map((e) => e.raw), null, 1));
}
candidates.sort((a, b) => a.negAt.localeCompare(b.negAt));
writeFileSync('docs/audits/pan-3367/evidence/candidates.json', JSON.stringify(candidates, null, 1));
console.log(`candidates: ${candidates.length}`);
```

Then, per candidate, the commit count (PAN example):

```bash
negAt=2026-07-28T06:40:00Z; passAt=2026-07-28T07:26:00Z; pr=3219
gh pr view $pr --repo eltmon/overdeck --json commits \

```

## Method — per audited issue

1. **Failing AC.** Read the issue's acceptance criteria (source 4 or 5) and identify the criterion the negative verdict was about, using the recorded failure reason (snapshot `negNotes`, plus PR review comments via `gh pr view <n> --comments` when the notes are thin, plus the record's `pipeline.reviewNotes`/`testNotes`). Quote both in the report with their source.
2. **Merged diff.** Read the merged diff (source 6 or 7).
3. **Verdict.** Answer: does the diff satisfy *that criterion*? Not "does it look reasonable", and not "do tests pass now" — a green suite proves only that the suite passes. Record `satisfied` / `not satisfied` / `cannot determine`, each with the diff evidence (file:line) the verdict rests on. `cannot determine` is for criteria that are not code-checkable (e.g. the browser UAT that was environment-blocked in the first place); for those, record what would unblock verification (e.g. PAN-3362).
4. **Follow-ups.** For every `not satisfied`, file a follow-up issue with the gap — GitHub issue on `eltmon/overdeck` for PAN, Linear issue in team MIN for MIN — and record its URL in the per-issue report. Do not fix anything in place. `cannot determine` verdicts do **not** get defect issues; their re-verification dependency is recorded in the report and the synthesis.
5. **Classification.** Tag each issue's failure as `genuine-finding` (a real test/review defect claim) or `environment-blocked` (infra/UAT environment). Genuine findings rank above environment blocks in the synthesis, per the issue's triage order.

## Hazards

- **H1 — Evidence compaction.** 7-day retention deletes the oldest events at every dashboard startup; PAN-1525's are already gone. Snapshot first, before anything else, and never gate the snapshot on other work.
- **H2 — Deleted-ref false positives.** A deleted feature branch returns 0 commits; use the PR commit list (branch-independent) or verify `git ls-remote` first.
- **H3 — "Tests pass now" trap.** A green suite proves the suite passes, not that the failing AC is met; verdicts must tie diff evidence to the specific criterion.
- **H4 — Cross-tracker MIN evidence.** MIN ACs live in Linear and diffs in `~/Projects/myn` + `~/Projects/myn-cli`; if a source is unreachable, the item is blocked and surfaced — not silently downgraded to `cannot determine`.
- **H5 — Live DB.** `overdeck.db` is written by the running dashboard; read-only connections only.
- **H6 — Thin failure notes.** Some negative events carry infra-flavored notes (e.g. "Verification worker exited before writing a result") rather than a substantive finding; classify these `environment-blocked`/`unknown` and say so, rather than inventing a finding.
- **H7 — Extra overflow.** If more than 10 zero-commit extras qualify, cap at 10 and flag the overflow in `worklist.md` + synthesis for operator triage.
