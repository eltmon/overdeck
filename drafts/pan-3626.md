# PAN-3626 — Windows: CLIProxy auto-installs the pinned version

**Issue:** https://github.com/eltmon/overdeck/issues/3626
**Status:** draft (planning output, 2026-08-09)
**Verified against:** `feature/pan-3626` @ `64c24bc573` (identical to `origin/main` for all cited files)

## Glossary

- **CLIProxy / CLIProxyAPI** — the upstream `router-for-me/CLIProxyAPI` Go binary Overdeck runs as a local sidecar on port 8317 to bridge ChatGPT-subscription OAuth to an Anthropic-compatible endpoint. Overdeck pins release `v7.2.113` (`CLIPROXY_RELEASE_VERSION`, `src/lib/cliproxy.ts:55`).
- **Pinned version** — the exact upstream release Overdeck auto-installs; install is gated on the on-disk binary reporting this version.
- **Watchdog** — `startCliproxyWatchdog()` in `src/dashboard/server/routes/cliproxy.ts:41`: a 30s interval in the dashboard server that health-checks the sidecar and calls `restartCliproxy()` when it's down.
- **Sync path / task path** — `src/lib/cliproxy.ts` has parallel implementations of every lifecycle op: `*Sync` (execSync, used only by the CLI: `src/cli/up-sidecars.ts:16`, `src/cli/commands/restart.ts:514`, `src/cli/commands/dev.ts:174`) and `*Task` (execAsync, used by the dashboard server via the Effect wrappers). **Both paths must gain Windows support** — `npx @overdeck/core` boots through the sync path, the watchdog runs the task path.
- **bsdtar** — the `tar.exe` shipped in `C:\Windows\System32` on Windows 10 1803+/11. Unlike GNU tar it extracts `.zip` archives; `tar -xf` auto-detects both gzip tarballs and zip.
- **Exec-bit check** — `(st.mode & 0o111) !== 0` in `isCliproxyInstalled()` (`src/lib/cliproxy.ts:440`); meaningless on Windows where fs modes carry no execute bit.

## Problem

On win32, `detectPlatformAsset()` (`src/lib/cliproxy.ts:417`) returns `null` because it only maps `linux` and `darwin`, so `installCliproxyTask()` throws `CLIProxyAPI does not publish a prebuilt binary for win32/x64…`. The watchdog retries forever (install attempts gated to every 5 min by `INSTALL_RETRY_COOLDOWN_MS`, `routes/cliproxy.ts:37`), spamming `CliproxyError` for the life of the dashboard. The error's premise is false: release `v7.2.113` ships `CLIProxyAPI_7.2.113_windows_amd64.zip` and `CLIProxyAPI_7.2.113_windows_aarch64.zip`, containing `cli-proxy-api.exe` at the archive root, and the issue reporter verified the exe runs on Windows 11.

Beyond the asset mapping, four more platform assumptions block Windows, and one bug affects **all** platforms:

1. Extraction/installation shells out to Unix tools: `tar -xzf`, `install -m 0755`, `rm -rf` (`src/lib/cliproxy.ts:512-526` sync, `:550-562` task).
2. `getCliproxyBinary()` (`:61`) has no `.exe` suffix, so the spawned path and the installed file can never match Windows conventions.
3. The exec-bit check in `isCliproxyInstalled()` (`:440`) reports a correctly installed Windows binary as missing → eternal reinstall.
4. `isCliproxyRunningSync()` (`:585`) falls back to `bash -c 'echo >/dev/tcp/…'` — bash doesn't exist on stock Windows, so a listening proxy with a stale/missing pidfile is reported as down and the CLI spawns a duplicate.
5. **All platforms:** the version probe `"<bin>" --version` (`:469` sync, `:483` task) relies on exec success, but v7.2.113 does not define `-version`: it prints `CLIProxyAPI Version: 7.2.113, …` then `flag provided but not defined: -version` and **exits 2**. Verified locally on linux (`~/.overdeck/bin/cliproxy --version; echo $?` → banner + `exit=2`). `execSync`/`execAsync` throw on non-zero exit, the `catch` returns `false`, so `isCliproxyUpToDate*` can never be true → every cold start (`startCliproxy*` with the proxy not running) silently redownloads the ~65 MB archive even when the pinned version is already installed.

## Requirements

- **FR-1** `detectPlatformAsset('win32', 'x64')` returns `CLIProxyAPI_<ver>_windows_amd64.zip`; `('win32','arm64')` returns `CLIProxyAPI_<ver>_windows_aarch64.zip`; unsupported combos (e.g. `win32`/`ia32`) still return `null`.
- **FR-2** `getCliproxyBinary()` returns `<BIN_DIR>/cliproxy.exe` on win32, `<BIN_DIR>/cliproxy` elsewhere.
- **FR-3** `isCliproxyInstalled()` applies the exec-bit test only when `process.platform !== 'win32'`; on win32 a present regular file counts as installed.
- **FR-4** `installCliproxySync`/`installCliproxyTask` extract both `.tar.gz` and `.zip` via `tar -xf`, look for `cli-proxy-api.exe` on win32 (`cli-proxy-api` elsewhere), and install/cleanup via `fs` primitives (`rm` target → `copyFile` → `chmod 0o755`; `fs.rm(tmpDir, {recursive:true, force:true})`) instead of `install`/`rm -rf`. The unsupported-platform error message no longer claims "linux and darwin only".
- **FR-5** The version up-to-date checks parse the version banner from stdout **even when the probe command exits non-zero**, on all platforms; a genuinely absent/unparsable banner still yields false (reinstall).
- **FR-6** `isCliproxyRunningSync()` on win32 uses `netstat` output parsed in JS instead of the bash `/dev/tcp` probe; non-win32 behavior is unchanged.
- **NFR-1** No new npm dependencies (bsdtar + curl.exe ship with Windows 10 1803+/11; the repo has no zip library and doesn't need one).
- **NFR-2** No `execSync` added to any dashboard-server-reachable code path — the `*Task` variants stay on `execAsync` (existing repo rule; `fuser`/netstat fallbacks in task code use `execAsync`).
- **NFR-3** All new platform-dependent logic is parameterized (`platform: NodeJS.Platform = process.platform` style, matching `detectPlatformAsset`'s existing signature) so it is unit-testable on linux CI — there is no Windows runner.
- **NFR-4** `src/lib/cliproxy.ts` (881 lines on `origin/main`) stays under the 1000-line ceiling of `scripts/lint-file-size.sh`, or the work adds an audited `scripts/file-size-allowlist.txt` row `<lines> src/lib/cliproxy.ts # PAN-3626`.

## Decisions (made here, not left to the executor)

- **D1 — bsdtar over Expand-Archive or a Node unzip dependency.** The issue suggested `Expand-Archive`/Node unzip; we instead change `tar -xzf` → `tar -xf`: GNU tar auto-detects gzip on linux/darwin, and Windows' System32 `tar.exe` is bsdtar, which extracts zip. One command, zero new dependencies, no PowerShell.
- **D2 — keep `--version` as the probe flag deliberately.** Its being *undefined* is what guarantees the binary prints the banner and exits fast (exit 2) instead of starting a server. Fix the parsing, not the flag: on exec failure, read `err.stdout` (both `execSync` errors and promisified-`exec` rejections attach `.stdout`; the sync call's `stdio: ['ignore','pipe','ignore']` keeps stdout piped so it is present on the error object).
- **D3 — fix the probe for all platforms, not win32 only.** Verified locally that linux v7.2.113 also exits 2; the current code redownloads on every cold start on linux/darwin too.
- **D4 — install ordering is rm-then-copy.** GNU `install` unlinks before writing; naive `copyFile` over a *running* binary throws ETXTBSY on linux. Replacement sequence: `fs.rm(target, {force:true})` → `fs.copyFile(extracted, target)` → `fs.chmod(target, 0o755)` (chmod is harmless on win32).
- **D5 — win32 sync port probe parses netstat in JS.** Run `netstat -ano -p TCP` and decide in an exported pure helper (local address ending `:8317` in `LISTENING` state) rather than chaining `findstr` — findstr quoting is fragile and a bare `:8317` match would also hit foreign addresses.
- **D6 — out of scope:** the `fuser` port-kill fallback in `stopCliproxy*` stays Unix-only (already wrapped in silent catch; pid-based `process.kill` terminates the process on Windows). No CI Windows runner, no upstream changes, no watchdog skip/disable on Windows (explicitly rejected by the issue).

### W4 — version probe: parse stdout on non-zero exit  *(traces FR-5; all platforms)*

/** stdout captured on a failed exec — execSync errors and promisified-exec

export function execFailureStdout(err: unknown): string {

## Hazards for the executor

- **H1** Replacing a running binary: linux ETXTBSY / win32 EPERM-EBUSY. D4's rm-then-copy fixes linux; on win32 `rm` of a running exe also fails — but every force-reinstall path already stops the proxy first (`src/dashboard/server/routes/cliproxy.ts:118-124` stop→install(true)→start; `src/cli/commands/restart.ts:513-518` restart orchestrator with injected stop/install) and `startCliproxy*` only installs when the proxy is not running. No retry logic needed; do not add any.
- **H2** `src/lib/cliproxy.ts` is 881 lines vs. the 1000 ceiling — the changes above fit (~+40 net); if you somehow exceed 1000, add the audited allowlist row with a PAN-3626 ref rather than bypassing.
- **H3** Repo rule: no `execSync` in dashboard-server-reachable code. Only touch execSync in `*Sync` functions (CLI-only); `*Task` stays `execAsync`.
- **H4** Do not "fix" `stopCliproxy*`'s `fuser` fallback for Windows — out of scope (D6), the silent catch is the intended behavior there.
- **H5** Tests with delays/retries must use fake timers per repo rule — not expected to be needed here (all new tests are pure).
