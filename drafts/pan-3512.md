## 1. Glossary

- **Verdict** — the terminal outcome of one review cycle: `passed` | `blocked` | `failed` | `skipped`.
- **Verdict artifact** — the durable file a finished reviewer writes: `.pan/review/<runId>/synthesis.md` (convoy) or `.pan/review/<runId>/review.md` (quick/self review). **The verdict of record** (PAN-3511 clause 1, already landed).
- **Review row** — the `review_status` row (SQLite `overdeck.db`, mirrored to the journal record). Derived, lagging, never authoritative.
- **Head anchor** (`HeadAnchor`, `src/lib/git-utils.ts:352`) — a branded string. In a monorepo it is a bare 40-char SHA. In a polyrepo it is `repoKey@sha repoKey@sha …` (`snapshotWorkspaceHeadsPromise`, `src/lib/git-utils.ts:394-414`). **It is not always a SHA — every comparison must go through `parseCompositeSnapshot` (`src/lib/git-utils.ts:359`).**
- **Evidence head** — the anchor a review verdict was produced at: `update.reviewedAtCommit`, or the first `update.reviewerVerdicts[*].atCommit`.
- **Row head** — `status.lastVerifiedCommit`, the anchor the last verification gate ran at.
- **Verdict write door** — `recordReviewVerdict()`, the new single write path for terminal REVIEW verdicts, introduced by this issue.
- **Dispatch-not-drop** — the rule this issue installs: a verdict whose evidence head disagrees with the row head is never silently discarded. It is rejected loudly (with an event) when the evidence is provably stale, and landed plus re-gated otherwise.
- **Merge gate** — `reviewGatesPassedSync()` (`src/lib/review-status-reconcile.ts:126`), the predicate that derives `readyForMerge` on every write.
- **Test gate** — `status.testStatus`. One of the three inputs to the merge gate.

## 2. Problem statement

`rejectVerdictEvidenceHeadMismatch` (`src/lib/review-verdict-guards.ts:69`, invoked from
`src/lib/review-status.ts:196`) currently does this on a head disagreement:

```ts
// src/lib/review-status.ts:196-198  (current)
if (rejectVerdictEvidenceHeadMismatch(
  issueId, status, update, () => notifyPipelineSync({ type: 'status_changed', issueId, status }),
)) return status;
```

It prints one `console.warn`, re-emits the OLD status, and returns. The verdict is gone —
no event, no activity entry, no retry, no route to an honest next step. On 2026-08-02 that
destroyed five APPROVED verdicts on PAN-1577 in one evening, because the deacon fallback
(`src/lib/cloister/deacon-review-signals.ts:230`) synthesized APPROVED at a *fresher* head
than the row's stale `lastVerifiedCommit`, and then killed the convoy parent unconditionally
at `deacon-review-signals.ts:247` regardless of the rejected write.

Two independent defects:

1. **The guard destroys instead of routing.** Fresher evidence than the row's is not a
   reason to discard a verdict — it is a reason to re-run the gate the row is stale about.
2. **The fallback's teardown does not read the write's outcome.** `setReviewStatusSync`
   returns a `ReviewStatus`, never a landed/rejected signal, so no caller can condition on it.

Underneath both: there are **seven** terminal-review-verdict write sites and no shared
contract. §4 enumerates every one of them.

## 3. Merge-gate regression analysis (REQUIRED — the reason this issue was split out)

The issue requires proving that dispatch-not-drop cannot advance a verdict whose verification
later fails at the verdict's head. This section is that proof.

### 3.1 What `readyForMerge` is derived from

`readyForMerge` is not stored intent; it is re-derived on **every** write
(`src/lib/review-status.ts:295-300`):

```ts
const hasBlockers = (merged.blockerReasons?.length ?? 0) > 0 || merged.uatStatus === 'failed';
const readyForMerge = hasBlockers
  ? false
  : (update.readyForMerge !== undefined ? update.readyForMerge : reviewGatesPassedSync(merged));
```

and identically on the journal→cache reconcile path (`src/lib/review-status-reconcile.ts:169`).
The predicate (`src/lib/review-status-reconcile.ts:126-142`) requires **all** of:

- `reviewStatus` ∈ {`passed`, `skipped`}
- `testStatus` ∈ {`passed`, `skipped`}
- `verificationStatus !== 'failed'` (`verificationSatisfied`, :94)
- `uatStatus` undefined or `passed`
- `mergeStatus` ∈ {`pending`, `queued`, undefined, null}

### 3.2 The exact regression dispatch-not-drop could introduce

Landing a review verdict at evidence head **B** while the row's `testStatus` is `passed`
from an earlier cycle at head **A** makes `reviewGatesPassedSync` return true immediately.
`readyForMerge` flips to true for a tree **no gate has ever run against**. Today the guard
prevents this by discarding the verdict. Removing the guard without a replacement re-opens it.

This is the "could ADMIT verdicts that should not advance" risk named on the issue. It is real.

### 3.4 The merge gate DOES re-verify — cited

`triggerMerge()` Step 3, `src/dashboard/server/routes/workspaces/merge-ops.ts:994-1070`
("`Step 3: Post-rebase verification gate ensures the rebase remains valid before merging`"):
it rebases, sets `mergeStatus: 'verifying'`, then runs the full quality-gate suite at the
post-rebase HEAD via `runVerificationForIssue(...)` and on `outcome === 'failed'` sets
`mergeStatus: 'failed', readyForMerge: false` and returns HTTP 500 without merging
(`:1050-1069`). The only bypass is PAN-2487 (`:1002-1024`): local gates are skipped **only**
when GitHub CI reports green on the exact tip SHA being merged — stronger evidence on the
identical tree, not weaker.

**Conclusion (the requirement's first clause): no unverified tree can merge under
dispatch-not-drop.** The merge-time gate is a re-verification at the merge head, and it is
unconditional apart from a green-CI-on-the-same-SHA equivalence.

### 3.5 …but citing it is not enough, so this issue also adds the block

`triggerMerge`'s gate protects the *merge*. It does not protect the *state*: between a
fresh-evidence land and the merge attempt, the issue would advertise `readyForMerge: true`,
sit on the Awaiting Merge page, enter the merge train, and be auto-merge eligible — all on a
head only the reviewer ever saw. Correct-but-late is not the standard for a write door.

**Decision D-3 (made here, do not re-litigate): when the door lands a verdict whose evidence
head differs from the row head, it resets the test gate in the SAME update.** Concretely, if
`status.testStatus` is `passed` or `skipped`, the door adds
`testStatus: 'pending'` + an explanatory `testNotes` to the update. Consequences, all verified
in the tree:

1. `reviewGatesPassedSync` returns false (testStatus is `pending`) → `readyForMerge` stays
   false. The regression in §3.2 becomes structurally impossible, not merely late-caught.
2. The reactive review→test handoff at `src/lib/review-status.ts:479-502` fires, because its
   condition is `(update.reviewStatus === 'passed' || 'skipped') && status.reviewStatus` was
   neither && `updated.testStatus === 'pending'`. Its `canSkipTests` shortcut (`:484-487`)
   requires `updated.reviewedAtCommit === updated.lastVerifiedCommit`, which is false by
   construction in this branch — so it takes the `else` and emits `review.approved`
   (`:500`), which dispatches the test role. **That dispatch is the "verification re-run at
   the evidence head" the issue asks for**; the test role runs the gates against the current
   workspace tree, and `runVerificationForIssue` re-anchors `lastVerifiedCommit` from a live
   snapshot when it passes (`src/lib/cloister/verification-runner.ts:899-911`).
3. The deacon backstop at `src/lib/cloister/deacon.ts:1336` already covers the case where the
   reactive handoff does not fire ("`review=passed + test=pending, but the reactive
   review→test handoff … never fired — the deacon had to dispatch test`"). No new backstop needed.
4. `testStatus: passed → pending` is legal: the only testStatus regression guard
   (`src/lib/review-status.ts:229-238`, PAN-424) rejects `passed → failed | dispatch_failed`
   and nothing else.

**Decision D-4:** the door does NOT call `runVerificationForIssue` itself. Verification is a
full quality-gate suite; invoking it inline from a deacon patrol callback would block a patrol
tick for minutes. Resetting the test gate hands the work to the role that already owns it.

### 3.6 Residual risk, stated

If a `blocked`/`failed` verdict lands at a fresh head the test gate is also reset. That is
harmless: a blocked review cannot satisfy the merge gate anyway, and the row moves to
`pending` tests, which the next cycle re-runs. Accepted.

## 5. Requirements

**Functional**

- **FR-1** `src/lib/cloister/review-verdict-writer.ts` exports `recordReviewVerdict(issueId, input): Promise<VerdictOutcome>` with the exact shape in §6.1, returning `{ landed: true }` or `{ landed: false; reason }`.
- **FR-2** Provably-stale evidence (evidence head is an ancestor-or-equal of the row head in every repo, and strictly behind in at least one) → `{ landed: false, reason: 'stale-evidence-head' }`, a `review.verdict_rejected` domain event, and an activity entry. The row is not written.
- **FR-3** Any other head disagreement (fresher, divergent, or shape-indeterminate) → the verdict LANDS with `reviewedAtCommit` set to the evidence head, the test gate is reset per D-3, and a `review.verdict_dispatched` domain event plus activity entry are emitted.
- **FR-4** `rejectVerdictEvidenceHeadMismatch` loses its REVIEW arm; its TEST arm (`src/lib/review-verdict-guards.ts:56-63`) is unchanged and still rejects mismatched test-verdict writes.
- **FR-5** All nine call sites in §4 marked "yes" write terminal review verdicts through the door.
- **FR-6** `killSession` in the deacon fallback (`deacon-review-signals.ts:247`) and the blocked-feedback delivery immediately above it (`:236-245`) run only when the door returned `{ landed: true }`.
- **FR-7** `pan admin specialists done review` reports a rejected write to the caller: it prints the reason and exits non-zero, so a review agent does not believe it signalled.
- **FR-8** Docs: `docs/REVIEW-AGENT-ARCHITECTURE.md` gains a "The verdict write door" section stating the writer table, the dispatch-not-drop rule, the test-gate reset, and the kill-conditional.

**Non-functional**

- **NFR-1** No silent verdict loss: every rejected verdict emits a domain event AND an activity entry naming the writer, both heads, and the reason.
- **NFR-2** Both review modes are covered — fixtures exercise `synthesis.md` and `review.md` artifact shapes and both writer families.
- **NFR-3** Polyrepo-safe: every head comparison parses composite anchors; a bare-vs-composite shape disagreement is never treated as "stale" (PAN-3254's false-drift lesson).
- **NFR-4** No behavior change when no evidence head is present — writers 1, 4a, 5a, 5b keep landing exactly as today.
- **NFR-5** No `execSync` anywhere; the ancestor probe uses `execFileAsync` with a timeout.
- **NFR-6** `readyForMerge` cannot be true on the write that lands a fresh-evidence verdict. Proven by a dedicated regression test, not by inspection.

## 6. Design

### 6.1 The door — `src/lib/cloister/review-verdict-writer.ts` (new)

```ts
import type { HeadAnchor } from '../git-utils.js';
import type { ReviewStatus } from '../review-status.js';

export type VerdictWriter =
  | 'coordinator' | 'fallback' | 'quick-signal'
  | 'orphan-restore' | 'sweeper-restore'
  | 'unsignaled-recovery' | 'infra-bypass';

export interface VerdictInput {
  verdict: 'passed' | 'blocked' | 'failed' | 'skipped';
  notes?: string;
  runId?: string;
  /** Anchor the review ran at. Omit when the writer has no evidence. */
  evidenceHead?: HeadAnchor;
  reviewerVerdicts?: ReviewStatus['reviewerVerdicts'];
  /** Extra row fields the writer needs in the same atomic update
   *  (e.g. the orphan restore's stuck-clearing fields). */
  extra?: Record<string, unknown>;
  writer: VerdictWriter;
}

export type VerdictOutcome =
  | { landed: true; classification: 'no-evidence' | 'anchor-match' | 'dispatched' }
  | { landed: false; reason: 'stale-evidence-head' };

export async function recordReviewVerdict(
  issueId: string,
  input: VerdictInput,
): Promise<VerdictOutcome>;
```

Behavior, in order:

1. `const status = getReviewStatusSync(issueId)`.
2. No `evidenceHead`, or no `status.lastVerifiedCommit`, or the two anchors are equal →
   build the update, `setReviewStatusSync`, emit nothing extra, return
   `{ landed: true, classification: 'no-evidence' | 'anchor-match' }`. This is FR-4/NFR-4:
   today's behavior byte for byte.
3. Anchors differ → `classifyEvidenceAgainstAnchor(issueId, evidenceHead, status.lastVerifiedCommit)`:
   - `'stale'` → emit `review.verdict_rejected` + activity entry, return `{ landed: false, reason: 'stale-evidence-head' }`. No row write.
   - anything else → land: `setReviewStatusSync(issueId, { reviewStatus, reviewNotes, reviewerVerdicts, reviewedAtCommit: evidenceHead, ...testGateReset, ...extra })`, then emit `review.verdict_dispatched` + activity entry, return `{ landed: true, classification: 'dispatched' }`.

`testGateReset` is `{}` unless `status.testStatus` is `'passed'` or `'skipped'`, in which case
it is:

```ts
{
  testStatus: 'pending',
  testNotes: `Re-queued by the verdict write door: review evidence ${formatAnchorShort(evidenceHead)} `
    + `is not the verified head ${formatAnchorShort(status.lastVerifiedCommit)} (writer: ${input.writer}).`,
}
```

### 6.2 The staleness classifier (same module, not exported beyond the door + its test)

```ts
type EvidenceClassification = 'stale' | 'fresh' | 'indeterminate';

async function classifyEvidenceAgainstAnchor(
  issueId: string,
  evidenceHead: string,
  rowHead: string,
): Promise<EvidenceClassification>;
```

Rules, all polyrepo-aware via `parseCompositeSnapshot` (`src/lib/git-utils.ts:359`):

1. Resolve repo roots with `resolveWorkspaceRepoRootsSync(issueId, workspacePath)`
   (`src/lib/project-repos.ts`), workspace path resolved the same way
   `readLatestSynthesisVerdict` does (`src/lib/cloister/synthesis-verdict.ts:60-66`). Unresolvable → `'indeterminate'`.
2. Composite-vs-bare shape disagreement between the two anchors → `'indeterminate'`. Never
   `'stale'` — PAN-3254 (`src/lib/workspace-anchor-drift.ts:88-96`) is the precedent: a shape
   disagreement is a producer disagreement, not evidence about code.
3. Composite on both sides with different repo key sets → `'indeterminate'`.
4. Otherwise, per repo, run
   `execFileAsync('git', ['merge-base', '--is-ancestor', evidenceSha, rowSha], { cwd: root.dir, timeout: 10_000 })`.
   Exit 0 = evidence is an ancestor-or-equal of the row head. Any throw that is not a clean
   non-zero exit (unreadable repo, missing object) → `'indeterminate'` for the whole comparison.
5. `'stale'` iff every repo answered ancestor-or-equal AND at least one repo's shas differ.
   Otherwise `'fresh'`.

Only `'stale'` rejects. `'fresh'` and `'indeterminate'` both land — landing is the conservative
action once the test gate is reset, because an unlanded verdict is invisible while a landed
one is re-gated.

### 6.5 Call-site migrations — before/after

**Fallback + kill-conditional** (`src/lib/cloister/deacon-review-signals.ts:230-251`):

```ts
// before
setReviewStatusSync(state.issueId, {
  reviewStatus: synthesis.verdict,
  reviewNotes: synthesis.topBlocker || 'Review approved by Deacon fallback from completed reviewer reports',
  reviewerVerdicts: anchoredVerdicts,
  ...(synthesis.verdict === 'blocked' && fallbackHead ? { reviewedAtCommit: fallbackHead } : {}),
});
if (synthesis.verdict === 'blocked') { await …deliverReviewVerdictFeedback(…); }
if (sessionAlive) { await Effect.runPromise(killSession(state.id))… }

// after
const outcome = await recordReviewVerdict(state.issueId, {
  verdict: synthesis.verdict,
  notes: synthesis.topBlocker || 'Review approved by Deacon fallback from completed reviewer reports',
  reviewerVerdicts: anchoredVerdicts,
  ...(fallbackHead ? { evidenceHead: fallbackHead } : {}),
  runId: state.reviewRunId,
  writer: 'fallback',
});
if (!outcome.landed) {
  const action = `Deacon fallback verdict for ${state.issueId} was not recorded (${outcome.reason}) — convoy parent left alive`;
  actions.push(action);
  logDeaconEventSync(`monitorReviewConvoySignals: ${action}`);
  continue;
}
if (synthesis.verdict === 'blocked') { await …deliverReviewVerdictFeedback(…); }
if (sessionAlive) { await Effect.runPromise(killSession(state.id))… }
```

Note the after-shape passes `evidenceHead` for **every** verdict, not only `blocked`. The
`reviewedAtCommit` anchor is what makes the reactive `canSkipTests` comparison meaningful, and
the fallback's `anchoredVerdicts` already carried the head into the guard's view anyway.
The synthesis artifact is written to disk before this call and stays there on rejection —
correct under the verdict-of-record contract: the artifact IS the verdict, and PAN-3511's
read-side recovery paths honor it.

**Quick signal** (`src/cli/commands/specialists/done.ts:244`): the `case 'review'` branch keeps
building its update, but the terminal fields route through the door while the non-review
specialists keep `setReviewStatusSync`. On `{ landed: false }` print the reason with
`chalk.red` and `process.exitCode = 1` before returning, so the review agent sees the failure
(FR-7). The CLI's existing `flushReviewStatusJournalWrites()` drain (PAN-2689) still applies.

**Coordinator** (`src/dashboard/server/routes/specialists/legacy-routes.ts:198,232`): the
`case 'review'` update fields move into a `recordReviewVerdict(… writer: 'coordinator')` call;
every other specialist keeps `setReviewStatusBase`. The second, anchor-only write at `:330`
is untouched — it carries no terminal `reviewStatus`, so it never reached the guard.

**Orphan restores** (`src/lib/cloister/deacon-review-status.ts:565`, `:592`): both become
`await recordReviewVerdict(issueId, { …, writer: 'orphan-restore', extra: { reviewRetryCount: 0, recoveryStartedAt: undefined, …stuckClearingFields } })`.
The `:592` site passes `evidenceHead: artifact.headSha`.

**Unsignaled recovery** (`src/lib/cloister/deacon-review-unsignaled.ts:316`, `:423`, `:451`):
`writer: 'unsignaled-recovery'`; the `:316` site passes `evidenceHead: currentHead`.

**Infra bypass** (`src/lib/cloister/deacon.ts:1557`): `writer: 'infra-bypass'`,
`evidenceHead: reviewedAtCommit` when present, stuck-clearing fields via `extra`.
`deacon.ts` is allowlisted at 3569 lines — if this edit grows the file, bump
`scripts/file-size-allowlist.txt` in the same commit with `# PAN-3512`.

## 7. Decisions made (do not re-litigate)

- **D-1 Dispatch, not drop.** A verdict with fresher evidence is truth about what the reviewer
  saw. Discarding it is what caused PAN-1577.
- **D-2 The guard's review arm is deleted, not made conditional.** A marker field threaded
  through `setReviewStatusSync` would grow `src/lib/review-status.ts`, which is at its
  allowlist ceiling. Deleting the arm and owning the whole decision in the door is smaller
  and puts the rule in one place. Every evidence-carrying writer migrates in the same issue,
  so nothing loses protection.
- **D-3 The door resets the test gate on a head disagreement.** §3.5. This is the "add the
  block" branch of the issue's requirement, taken in addition to citing the merge-time gate.
- **D-4 The door does not run verification inline.** §3.5 item 2 — the reactive test dispatch
  already owns it.
- **D-5 `indeterminate` lands.** Once the test gate is reset, landing is the conservative
  option; a dropped verdict is invisible, a landed one is re-gated.
- **D-6 Scope is the nine call sites in §4.** Terminal-verdict writes that carry no evidence
  head and are pure reconciliation (mode-none skip, spawn failure, merged reconcile, PAN-869
  backfill, verification-failed, merge fulfillment) stay on `setReviewStatusSync`. They never
  reached the guard, so this issue changes nothing for them; folding them in would be an
  unrelated refactor.
- **D-7 `'sweeper-restore'` ships as a writer-union member with a unit fixture, but no call
  site.** The sweeper restore is created by PAN-3511 WI-6, which is a separate issue. Shipping
  the tag now means PAN-3511 wires a call, not a contract.
