# PAN-3229 — Pending-promotion marker + deacon recovery owner for finalized-but-unpromoted plans

**Issue:** https://github.com/eltmon/overdeck/issues/3229
**Author:** planning agent (claude-fable-5), auto mode, 2026-07-28

## Glossary

- **Finalize**: `pan plan finalize`, run by the planning agent from the workspace. Stamps the workspace xBRIEF (`.overdeck/spec.vbrief.json`, legacy `.pan/spec.vbrief.json`) to `plan.status: "proposed"` via `stampPlanForFinalization` (`src/cli/commands/plan-finalize.ts:458`), then attempts **promotion**.
- **Promotion**: `POST /api/issues/:id/complete-planning`, sent by `promotePlanning` (`src/cli/commands/plan-finalize.ts:382`). Handled server-side by `completePlanningForIssue` (`src/lib/overdeck/planning-promotion.ts:466`): promotes the spec to `specs/` on `overdeck-state`, transitions the issue to Planned, resolves the persisted auto-spawn stamp, kills the planning session.
- **Pending-promotion state**: workspace spec stamped `proposed`, but promotion never succeeded — no canonical spec on `overdeck-state`, issue not transitioned. This is the state PAN-3212 sat in for 9.5h.
- **Marker**: the new durable file `<workspace>/.overdeck/pending-promotion.json` recording that state.
- **Reconciler**: a function called from the deacon's `runPatrol()` (`src/lib/cloister/deacon.ts:2560`, ~60s cadence) that detects a condition and converges it through normal endpoints.
- **Needs-you trip**: `recordDeadEndNeedsYou(issueId, recoveryPath, generation, message)` (`src/lib/cloister/dead-end-trip.ts:4`) — durable operator escalation, deduped per generation.
- **Internal endpoint call**: `fetch` against `internalDashboardOrigin()` with `INTERNAL_TOKEN_HEADER: getInternalTokenSync()` — the reconciler→dashboard pattern (see `spawnWorkAgentThroughAgentsEndpoint`, `src/lib/cloister/orphan-proposed-reconciler.ts:278`).

## Problem

`promotePlanning` retries 5 attempts with 1s/2s/4s/8s backoff — 15 seconds total (`plan-finalize.ts:366-375`) — against dashboard outages that last minutes (deploy windows). When the budget is exhausted, the CLI prints "run `pan plan done` to retry" and exits; **no durable record of the pending-promotion state exists and no server-side owner ever scans for it**:

- `orphan-proposed-reconciler.ts` requires a spec **already promoted** with `plan.status: 'proposed'` — an artifact written by the very endpoint that failed (its scan reads the promoted specs dir, `orphan-proposed-reconciler.ts:216-225`).
- Boot reconciliation resumes work/strike agents only; `cleanupOrphanedPlanningSessions` requires the work agent to already be running; stuck remediation's idle-planning nudge requires `auto === true`.

PAN-3212 finalized at ~06:52Z during a deploy outage and stalled until a human ran `pan plan done` at 12:24Z, despite hours of healthy dashboard uptime in between.

## Approach (decided)

Keep the CLI's 15s budget (a bigger budget still loses to long outages) and make recovery server-owned:

1. **CLI writes a durable marker when promotion retries are exhausted**, and its output honestly says recovery is deferred to the deacon, not converged.
2. **A new deacon reconciler** scans workspaces for markers (and defensively for markerless finalized-unpromoted specs), re-drives promotion through the normal endpoint, and trips needs-you after bounded failures.
3. **The promotion service clears the marker on success**, whatever path triggered it (patrol, `pan plan done`, dashboard Done button).

The deacon runs only while the dashboard is up, so the patrol inherently waits out the outage and converges on the first cycle after recovery — exactly the regression scenario.

### Marker schema (contract — consumed by WI-2, WI-4, WI-5)

Path: `<workspace>/.overdeck/pending-promotion.json`. Written atomically (temp + rename). Gitignored.

```json
{
  "version": "1",
  "issueId": "PAN-3212",
  "canonicalFilename": "2026-07-28-PAN-3212-some-slug.xbrief.json",
  "noPrd": false,
  "autoSpawnRequested": false,
  "finalizedAt": "2026-07-28T06:52:11.000Z",
  "lastError": "Dashboard unreachable: fetch failed",
  "lastAttemptAt": "2026-07-28T06:52:26.000Z",
  "patrolAttempts": 0
}
```

- `noPrd` mirrors the finalize `--no-prd` flag; the reconciler must forward it or the PRD-first gate rejects the re-drive.
- `autoSpawnRequested` is observability only — the reconciler must NOT send `autoSpawn` in the body; `resolveAutoSpawnOnFinalize` (`planning-promotion.ts:482`) reads the persisted `auto-spawn-on-finalize.json` stamp, and an explicit `autoSpawn: true` body would also trigger the origin gate (`planning-promotion.ts:493-496`).
- `patrolAttempts` is incremented and persisted by the reconciler on each failed re-drive.

## Requirements

### Functional

- **FR-1**: When `promotePlanning` exhausts retries during `pan plan finalize` (and `--no-promote` was not passed), the CLI writes the marker file with the schema above before exiting.
- **FR-2**: The finalize failure output states that a durable marker was written and the deacon will complete promotion automatically once the dashboard is reachable; `--json` output carries `promotionDeferred: true` when the marker was written. Exit code stays 1 (unchanged consumer contract).
- **FR-3**: A deacon patrol reconciler scans every project's `workspaces/feature-*/` directories for markers and, for each candidate, re-drives promotion via an internal `POST /api/issues/:id/complete-planning` with `{ noPrd }` from the marker.
- **FR-4**: Defensively, the reconciler also detects markerless pending-promotion states: a workspace spec with `plan.status === 'proposed'` whose issue has no promoted counterpart (checked via `findSpecByIssue(projectRoot, issueId)`, `src/lib/pan-dir/specs.ts:213`) and whose spec file mtime is older than 5 minutes. These are treated as candidates as if a marker existed (with `noPrd: false`).
- **FR-5**: If the promoted counterpart already exists for a candidate (promotion actually landed — e.g. the 90s AbortError case), the reconciler deletes the marker and emits a diagnostic, without POSTing.
- **FR-6**: The reconciler skips candidates whose marker (or spec mtime, for markerless candidates) is younger than 120 seconds, and skips closed issues (`isIssueClosed`).
- **FR-7**: On re-drive failure the reconciler increments `patrolAttempts` in the marker; when `patrolAttempts` reaches 5 it calls `recordDeadEndNeedsYou(issueId, 'pending-promotion', <finalizedAt>, <plain-language message>)`. It keeps retrying once per patrol cycle after the trip (the trip itself is generation-deduped).
- **FR-8**: `completePlanningForIssue` deletes `<workspacePath>/.overdeck/pending-promotion.json` (ignoring ENOENT) after successful promotion, so every success path converges the marker.
- **FR-9**: Regression coverage: a test proves that a marker written with the dashboard down converges (POST issued, marker removed) in a single reconciler pass once the endpoint responds successfully.

### Non-functional

- **NFR-1**: No `execSync` and no sync tmux primitives anywhere in the new code (server-reachable).
- **NFR-2**: Every test exercising retry/backoff/delay uses `vi.useFakeTimers()` + `advanceTimersByTimeAsync` — no real waits.
- **NFR-3**: The reconciler treats HTTP 202 (in-flight lease) and the `skipped: 'pending-ask-user-question'` body as "not converged": no marker deletion, no attempt increment beyond one, retry next cycle.
- **NFR-4**: The reconciler uses injectable dependencies (fetch, project list, now/clock, marker IO) so tests run hermetically, following the `orphan-proposed-reconciler.ts` options pattern.

## Decisions made in this document

- **Keep the 15s CLI retry budget; the marker+patrol is the recovery owner.** Extending the budget still loses to multi-minute outages and keeps the planning session alive pointlessly.
- **Exit code of failed-promotion finalize stays 1.** Changing it to 0 would alter the contract for `emitAutoPromotePhase` consumers and orchestrators; honesty is delivered via wording + `promotionDeferred` JSON flag. The stall harm in PAN-3212 was silence, not the exit code.
- **The reconciler never sends `autoSpawn` in the body** — the persisted auto-spawn stamp decides via `resolveAutoSpawnOnFinalize`, and an explicit true would hit the origin gate.
- **90s AbortError stays non-retried in the CLI** (PAN-2243 rationale). FR-5's already-promoted check makes the marker safe for the partially-executed case.
- **Use `findSpecByIssue` (state-worktree aware) for promoted-counterpart checks** — do NOT copy the orphan-proposed-reconciler's legacy `.pan/specs` scan; that blindness is a separately filed issue and out of scope here.
- **Patrol-only recovery; no boot-reconciliation hook.** The 60s patrol cadence satisfies "within one patrol cycle"; a second trigger path would add a race for no latency win.
- **`pan plan done` failure does not write a marker.** It is the manual fallback typically run after finalize already wrote one; keeping marker authorship in finalize keeps one writer.

## Intersecting repo rules (restated for the executor)

- Fake timers for every retry/backoff test (`vi.useFakeTimers()`; never real `setTimeout` waits; never `maxForks: 1` workarounds).
- No `execSync` in server-reachable code; `execAsync`/`spawn` only.
- Reconcilers call endpoints (two-door rule); never write SQLite, `state.json`, or the state worktree directly.
