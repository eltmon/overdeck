## Glossary

- **PostHog** — hosted product-analytics platform. Our project: PostHog Cloud US, project id 514675, ingestion host `https://us.i.posthog.com`.
- **Project API key** (`phc_…`) — publishable client key, safe to embed; already committed in `src/dashboard/frontend/.env.production`. Used for event capture and flag evaluation.
- **Personal API key** (`phx_…`) — secret, per-user key for PostHog's private REST API and CLI (sourcemap upload, HogQL queries). NEVER committed; supplied via env only.
- **posthog-js** — browser SDK, already a dependency of the frontend (`posthog-js@^1.402.3`).
- **posthog-node** — Node SDK: batched capture, `shutdown()` flush, feature-flag evaluation, exception capture. New dependency added by this PRD (root `package.json`).
- **AnalyticsService** — the single server/CLI telemetry choke point this PRD introduces at `src/lib/telemetry/service.ts`. All backend capture goes through it (single-write-door tenet).
- **Install ID** — a random UUIDv4 persisted at `${OVERDECK_HOME}/telemetry-id`, used as PostHog `distinct_id` for server/CLI events and as a correlating `install_id` property on frontend events. Never derived from any other tool's credential files.
- **Opt-out** — `telemetry.enabled: false` in `~/.overdeck/config.yaml`, or env `OVERDECK_TELEMETRY=0` (env wins). Disabled means **zero PostHog network calls** from frontend, server, and CLI.
- **Telemetry event schema** — the typed catalog of event names + property shapes in `packages/contracts/src/telemetry.ts`, mirrored 1:1 in `docs/TELEMETRY.md` and enforced by a lint test.
- **Sourcemap upload** — `posthog-cli sourcemap inject` + `upload`, which lets PostHog error tracking symbolicate minified frontend stack traces.

## Decisions (made here, not deferred)

- **D1 — Opt-out is runtime, evaluated per session, on by default.** The key/host stay baked into the bundle; the *gate* is `telemetry.enabled` resolved server-side (config.yaml, env `OVERDECK_TELEMETRY=0` overriding to false) and delivered to the frontend via `GET /api/settings`. When disabled, `posthog.init` is **never called** — that (not `opt_out_capturing`) is what guarantees zero network calls, because posthog-js contacts `/flags` during init. Events fired before the settings fetch resolves are dropped by the wrapper (acceptable: lifecycle events only). Per the 2026-07-14 operator decision there is still **no first-run notice**; disable is documented.
- **D2 — Server/CLI transport is `posthog-node` wrapped in one AnalyticsService.** This supersedes v1's raw-HTTP-no-SDK preference, consistent with the operator's 2026-07-16 directive accepting the SDK on the frontend. Rationale: one dependency buys batched capture + `shutdown()` flush + exception capture + flag evaluation; hand-rolling `$exception` events is explicitly discouraged by PostHog. The Effect-style wrapper preserves what mattered about v1's design: single choke point, no-op test layer, bounded shutdown flush.
- **D3 — Identity.** Server/CLI `distinct_id` = random install UUID at `${OVERDECK_HOME}/telemetry-id` (created on first use, mode 0600). Server/CLI events carry `$process_person_profile: false`. The frontend keeps its SDK-generated anonymous id and `person_profiles: 'identified_only'` with **no `identify()` calls**; it additionally registers `install_id` as a super property (via `posthog.register`) so frontend and backend events from one install can be joined. No code path may read `~/.codex/`, `~/.claude*`, or any other tool's credential files (the t3code practice we rejected in v1 — still rejected).
- **D4 — LLM analytics is out of scope; owner is PAN-2443.** PostHog's AI-observability ingestion (`@posthog/ai` / OTel `gen_ai.*` exporter) overlaps the PAN-2443 OTel GenAI pipeline. Decision: PAN-2443 owns model/token/cost telemetry end-to-end; if it later wants a PostHog exporter, that is a PAN-2443 work item. This PRD ships nothing there.
- **D5 — Feature flags: minimal read door, config always wins.** One method `isFeatureEnabled(flag, fallback)` on AnalyticsService, evaluated via posthog-node against the public `/flags` endpoint with the project key (no secure/local-evaluation key — that key is secret and cannot ship in an OSS repo). Precedence: explicit config value (e.g. `experimental.*`) > PostHog flag > `fallback` argument. Offline or disabled telemetry ⇒ `fallback`. No flag is wired to a real feature in this issue; the door + docs ship, adoption is per-feature follow-up work.
- **D6 — Error tracking.** Frontend: enable posthog-js exception autocapture (init option) in the wrapper, keep the four existing manual `captureException` calls. Server: `enableExceptionAutocapture: true` on the posthog-node client (uncaught exceptions / unhandled rejections), gated by the same enabled check. Sourcemaps: build with `sourcemap: 'hidden'` and upload via `posthog-cli` during release, gated on `POSTHOG_CLI_API_KEY` presence (skip with a warning when absent — releases must not hard-require the key).
- **D7 — Agent-facing consumption ships as documentation, not code.** The hosted MCP server (`https://mcp.posthog.com/mcp`) and `posthog-cli api` already exist; we document how an operator/flywheel wires them (personal API key, tool scoping) rather than building a wrapper. Pulling HogQL aggregates into the dashboard metrics page stays out of scope (tracked by #750's local-data-first stance).
- **D8 — Event names are typed in `@overdeck/contracts`.** Both frontend wrapper and server service import event-name/property types from `packages/contracts/src/telemetry.ts`. `docs/TELEMETRY.md` is the human mirror; a lint test fails if they drift.

## Requirements

### Functional

- **FR-1** `telemetry.enabled` (default `true`) is typed in YamlConfig, seeded in defaults, readable via `loadConfigSync()`, and env `OVERDECK_TELEMETRY=0|false` forces it to `false` regardless of config.
- **FR-2** `GET /api/settings` returns the resolved telemetry state (`{ telemetry: { enabled, installId } }`); `PUT /api/settings` can persist `telemetry.enabled`.
- **FR-3** When resolved-disabled, the frontend never calls `posthog.init` and makes zero requests to `*.posthog.com`; server and CLI AnalyticsService no-op (no client constructed, no network).
- **FR-4** All frontend PostHog usage goes through one wrapper module (`src/dashboard/frontend/src/lib/telemetry.ts`); no component imports `posthog-js` directly.
- **FR-5** The Settings page has a Telemetry section with an on/off switch matching the mockup (`drafts/pan-2599-mockup.html`), showing what is/isn't collected and the config/env equivalents.
- **FR-6** Server/CLI AnalyticsService captures: `server_boot` (bucketed `projectCount`, `activeAgentCount`), `cli_command_run` (`verb`, `ok`, bucketed `durationMs`), `pipeline_stage_changed` (`stage` ∈ {work_done, review_passed, verification_passed, merged, closed_out}, `harness`, `model`), using the install UUID as `distinct_id` and `$process_person_profile: false`.
- **FR-7** CLI exit flushes the queue with a bounded wait (≤ 2s hard cap) and adds ≤ 10ms synchronous overhead per command when enabled; zero overhead when disabled.
- **FR-8** Frontend and server exception autocapture are enabled behind the same gate; production frontend builds emit hidden sourcemaps; release uploads them to PostHog when `POSTHOG_CLI_API_KEY` is set, else skips with a warning.
- **FR-9** `isFeatureEnabled(flag, fallback)` exists on AnalyticsService with precedence config > flag > fallback and offline ⇒ fallback.
- **FR-10** Event names + property shapes are typed in `packages/contracts/src/telemetry.ts`; `docs/TELEMETRY.md` enumerates them; a lint test fails on drift.
- **FR-11** User-facing docs cover: what is collected, how to opt out (all three surfaces), and how to operate PostHog from agents (MCP + posthog-cli).

### Non-functional

- **NFR-1** No event property may contain a file path, repo name, issue title, branch name, prompt, or code content — enforced by a unit test over the schema types (property values restricted to enums, booleans, and bucketed numbers).
- **NFR-2** Telemetry is structurally inert under test: the service exposes a no-op layer used by the vitest setup; frontend wrapper no-ops when `import.meta.env.MODE === 'test'`.
- **NFR-3** Delay/flush behavior is tested with fake timers (`vi.useFakeTimers()` + `advanceTimersByTimeAsync`) — never real sleeps.
- **NFR-4** No `execSync` anywhere in server-reachable code (existing rule; the release sourcemap step runs in the CLI via the existing `runStreaming` helper).

import posthog from 'posthog-js';
import type { TelemetryEventName } from '@overdeck/contracts';

let ready = false;
export async function initTelemetry(): Promise<void> {
  if (import.meta.env.MODE === 'test') return;
  const res = await fetch('/api/settings').then(r => r.json()).catch(() => null);
  if (!res || res.telemetry?.enabled === false) return; // no init ⇒ zero network
  posthog.init(import.meta.env.VITE_PUBLIC_POSTHOG_KEY as string, {

    person_profiles: 'identified_only',
    capture_exceptions: true,
  });

  ready = true;
}
export function capture(event: TelemetryEventName, props?: Record<string, unknown>): void {
  if (ready) posthog.capture(event, props);
}
export function captureException(err: unknown, props?: Record<string, unknown>): void {
  if (ready) posthog.captureException(err, props);
}
