# PAN-2616 — Closed-issue reaper is blind to Linear-tracked issues

**Issue:** https://github.com/eltmon/overdeck/issues/2616
**Planning mode:** `--auto` (non-interactive; decisions recorded in `plan.autoDecisions[]`)
**Authored:** 2026-07-13, against workspace `feature/pan-2616` at `1df0c8ec5b`.

## Glossary

- **Closed-issue reaper** — the Deacon patrol `reconcileClosedIssueAgents` (`src/lib/cloister/closed-issue-reaper.ts`) that finds residue (tmux sessions, workspaces, agent dirs, Docker `_devnet` networks) belonging to closed issues and tears it down via `reapIssueResidue`.
- **`isTrackerIssueClosed`** — the function in `src/lib/cloister/issue-closed.ts:22` that asks the *external tracker* whether an issue is closed. Today it only knows how to ask GitHub.
- **`isIssueClosed`** — the wrapper (`src/lib/cloister/issue-closed.ts:60`) that first consults shadow state, then falls back to `isTrackerIssueClosed`.
- **Shadow state** — Overdeck's locally recorded mirror of tracker status (`getShadowState`). Only populated when Overdeck's own flows write it; an issue closed directly in the Linear UI leaves shadow state stale.
- **Linear-tracked issue** — an issue whose prefix resolves to a project using the Linear tracker (e.g. `MIN-*`, `AUR-*`), per `resolveTrackerTypeSync` (`src/lib/tracker-utils.ts:129`).
- **`LinearTracker`** — the existing Linear adapter (`src/lib/tracker/linear.ts:52`) implementing `IssueTracker`. Its `STATE_MAP` (`linear.ts:23-29`) normalizes Linear state types `completed` and `canceled` to `'closed'`.
- **Normalized `Issue.ref`** — the Linear identifier string (e.g. `MIN-729`) on the normalized issue (`linear.ts:370`).

## Problem

`isTrackerIssueClosed` short-circuits to `false` for any issue that doesn't resolve to a GitHub repo (`src/lib/cloister/issue-closed.ts:27-31`):

```ts
const resolved = resolveGitHubIssueSync(issueId);
if (!resolved.isGitHub) {
  trackerClosedCache.set(issueId, { closed: false, checkedAt: now });
  return false;
}
```

Linear-tracked issues therefore never look closed to `isIssueClosed` unless shadow state happens to record `done`/`canceled`. The closed-issue reaper consequently never reaps their residue. Evidence (2026-07-12): MIN-729, MIN-861, MIN-862 were Done in Linear, yet their `myn-feature-min-*_devnet` Docker networks persisted for days while the same patrol reaped closed PAN-* residue correctly.

## Chosen approach

Extend `isTrackerIssueClosed` with a Linear branch that queries the Linear API through the existing `LinearTracker` adapter, mirroring the structure of the existing GitHub branch (App API → gh CLI). The alternative in the issue — writing terminal shadow state at merge/close time — was rejected: it only covers closes performed by Overdeck's own flows, and the evidence issues were closed directly in the Linear UI. The tracker check must observe external closes.

### Decision rules (all decided here; no judgment calls left)

1. **Gating.** The Linear lookup runs only when BOTH hold:
   - `resolveTrackerTypeSync(issueId) === 'linear'` (`src/lib/tracker-utils.ts:129`), AND
   - `resolveProjectFromIssueSync(issueId)` (`src/lib/projects.ts:440`) returns non-null.
   `resolveTrackerTypeSync` falls back to `'linear'` for *unknown* prefixes; requiring a configured project prevents Linear API searches for junk IDs. Issues resolving to `rally`/`gitlab`, or to no configured project, keep the current behavior: cache `false`, return `false`, no API call.
2. **API key / client construction.** Try `createTracker({ type: 'linear' })` (`src/lib/tracker/factory.ts:58` — resolves config.yaml `trackerKeys.linear` first, then `LINEAR_API_KEY` env, throws `TrackerAuthError` when absent). If it throws, fall back to `getLinearApiKey()` (`src/lib/shadow-utils.ts:19` — reads `~/.overdeck.env`, then env) and construct `new LinearTracker(key)` when non-null. If no key from either path: cache `false`, return `false`, make no API call.
3. **Closed mapping.** `closed = issue.state === 'closed' && issue.ref?.toUpperCase() === issueId.toUpperCase()`. The `ref` equality guard exists because `LinearTracker.getIssue` resolves identifier-form IDs via `searchIssues(id, { first: 1 })` (`src/lib/tracker/linear.ts:116-120`), which is a fuzzy search — a wrong-issue hit must NOT report closed (the reaper is destructive).
4. **Timeout.** Wrap the lookup in `Effect.timeout('10 seconds')` for parity with the gh CLI path's `timeout: 10_000`. The Deacon patrol must never hang on a slow Linear API.
5. **Failure posture.** Any error, timeout, `IssueNotFoundError`, or ref mismatch → `false`, cached for the full TTL. False negatives (residue lingers one more patrol) are acceptable; false positives (reaping a live issue) are not.
6. **Caching.** All outcomes — closed, open, no-key, error — are cached in the existing `trackerClosedCache` with `TRACKER_CLOSED_CACHE_TTL_MS` (5 min), same as the GitHub path.

### After sketch (`src/lib/cloister/issue-closed.ts`)

```ts
const resolved = resolveGitHubIssueSync(issueId);
if (!resolved.isGitHub) {
  const closed = await isLinearIssueClosed(issueId);
  trackerClosedCache.set(issueId, { closed, checkedAt: now });
  return closed;
}
```

```ts
async function isLinearIssueClosed(issueId: string): Promise<boolean> {
  if (resolveTrackerTypeSync(issueId) !== 'linear') return false;
  if (!resolveProjectFromIssueSync(issueId)) return false;

  let tracker: IssueTracker | null = null;
  try {
    tracker = createTracker({ type: 'linear' });
  } catch {
    const key = await Effect.runPromise(getLinearApiKey());
    tracker = key ? new LinearTracker(key) : null;
  }
  if (!tracker) return false;

  try {
    const issue = await Effect.runPromise(
      tracker.getIssue(issueId).pipe(Effect.timeout('10 seconds')),
    );
    return issue.state === 'closed'
      && issue.ref?.toUpperCase() === issueId.toUpperCase();
  } catch {
    return false;
  }
}
```

(Exact style to match the file's existing patterns; `Effect.timeout` emits a `TimeoutException` failure which the catch treats like any other error.)

## Requirements

- **FR-1** — For an issue whose project is Linear-tracked, `isTrackerIssueClosed` returns `true` when the Linear issue's normalized state is `'closed'` (Linear state types `completed`/`canceled`).
- **FR-2** — When no Linear API key is resolvable (config.yaml `trackerKeys.linear`, `LINEAR_API_KEY` env, `~/.overdeck.env`), `isTrackerIssueClosed` returns `false` without making a Linear API call.
- **FR-3** — Issues resolving to `rally`/`gitlab` tracker types, or to no configured project, preserve current behavior: `false`, no Linear API call.
- **FR-4** — Every outcome (closed/open/no-key/error) is cached in `trackerClosedCache` for `TRACKER_CLOSED_CACHE_TTL_MS`; a repeat call within the TTL performs no tracker call.
- **FR-5** — The Linear lookup is bounded by a 10-second timeout; timeout or API error yields `false`.
- **FR-6** — A lookup whose returned issue `ref` does not equal the requested issue ID (case-insensitive) yields `false` (fuzzy-search mismatch guard).
- **NFR-1** — No `execSync` / sync child-process additions; the code runs inside Deacon patrols on the dashboard server event loop.
- **NFR-2** — Tests exercising the cache TTL use `vi.useFakeTimers()` / `vi.setSystemTime()` — never real waits (repo fake-timers rule).
