# PAN-3155 — Strike-landed issues can never close out: DoD row 4 resolves 'merged' through the superseded feature branch, and row 7 cascades

**Issue:** https://github.com/eltmon/overdeck/issues/3155
**Mode:** `--auto` planning (decisions recorded in xBRIEF `autoDecisions[]`)

## Glossary

- **DoD gate / DoD row** — the eight-row Definition-of-Done audit run by `closeOut()`
  before any teardown. Row definitions live in `src/lib/lifecycle/dod.ts`
  (`DOD_ROWS`); evaluation lives in `src/lib/lifecycle/dod-gate.ts`
  (`evaluateDodGate`). A `miss` on any row blocks close-out unless an operator
  accepts it with a `--accept-<row>` flag.
- **Strike** — the urgent landing path (`pan strike <id>`): work is redone on a
  `strike/<id-lowercase>` branch and merged from there, because the original
  `feature/<id-lowercase>` branch became un-mergeable. The feature branch keeps
  its commits forever — they are superseded, not merged.
- **Convention branch / convention head** — `feature/<id>` or `strike/<id>`, the
  two branch names Overdeck associates with an issue
  (`src/lib/pipeline-membership.ts:40-44`).
- **`verifyBranchMergedImpl`** — the git-level merge verifier behind DoD row 4,
  in `src/lib/lifecycle/workflows.ts:511`. Produces the `StepResult` that
  `checkMergedRow` maps to pass/miss.
- **`resolveIssuePullRequestRef`** — PR resolver in
  `src/lib/overdeck/pull-requests.ts:127` that maps an issue to a forge PR by
  trying convention heads in order. Backs `fetchIssuePullRequest`,
  `fetchIssuePullRequestDiff`, `fetchIssuePullRequestDetails`.
- **Containment lens (L2-work)** — `gatherIssueBranchContainment()` in
  `src/lib/pipeline-membership-gather.ts:456`: pure-git ancestry classification
  of an issue's convention refs into `unmergedRefs` / `mergedWorkRefs` /
  `pointerRefs`. Blind to squash merges by construction (a squash-merged branch
  tip is never an ancestor of main).
- **`buildCommit`** — the commit the live dashboard was built from, reported by
  `GET /api/health`. DoD row 7 proves deployment by checking the merge commit is
  an ancestor of `buildCommit`.

## Problem

PAN-3116 was strike-landed (PR #3152, squash merge `6ac4a3dc11`, live and
verified on main) yet its close-out fails DoD rows 4 and 7:

```
4 merged        MISS  "7 unmerged commit(s) on feature/pan-3116. Merge before closing out.; PR #3127 CLOSED"
6 main-verify   SKIP  "no merge commit resolvable"
7 deploy        MISS  "cannot resolve merge commit; live deployment cannot be proven"
```

Three verified root causes, each a one-line summary of code read during
planning:

1. **Row 4's git verifier only knows the feature branch.**
   `verifyBranchMergedImpl` (`src/lib/lifecycle/workflows.ts:511-620`) hardcodes
   `branchName = \`feature/${issueLower}\`` (line 514) and runs its whole
   cascade — `merge-base --is-ancestor`, empty-code-diff, then
   `verifySquashMergedPrByBranch` (line 691, already fully branch-parametric) —
   against that one branch. A strike-landed issue fails all three on
   `feature/<id>` *by construction*, so the row misses before any other
   evidence is considered.
2. **The forge PR resolver lets a closed superseded PR shadow the landing PR.**
   `resolveIssuePullRequestRef` (`src/lib/overdeck/pull-requests.ts:137-155`)
   iterates `[feature/<id>, strike/<id>]` and returns the first head that has
   *any* PR (`lookupPullRequestNumberForBranch` uses `gh pr list --state all
   --limit 1`, `src/lib/github-pr-lookup.ts:22-26`). For PAN-3116 it returns the
   CLOSED, unmerged #3127 and never looks at `strike/pan-3116`, whose PR #3152
   is MERGED. Row 4's observed string therefore says "PR #3127 CLOSED", and
   `merged.mergeCommit` / `merged.mergedAt` are never populated — which is
   exactly what rows 6 and 7 consume
   (`src/lib/lifecycle/dod-gate.ts:460-461`).
3. **Row 7 cascades.** `checkDeployRow`
   (`src/lib/lifecycle/dod-gate.ts:418-420`) turns a missing `mergeCommit` into
   an unconditional `miss` ("live deployment cannot be proven") even when row 4
   already missed — a second miss carrying no information, because the deploy
   row never learns that its input was unresolvable upstream.

The existing containment-lens fallback (`dod-gate.ts:304-316`) cannot rescue a
strike landing: it requires `unmergedRefs.length === 0`, and a squash-merged
`strike/<id>` tip is not an ancestor of main, so both the feature and strike
refs classify as `unmerged` (verified against the live repo: `feature/pan-3116`
tip `113377f2`, `strike/pan-3116` tip `1f3cd2a7`, both still present locally and
on origin).

## Proposal

Three surgical changes plus docs, all inside the existing read doors — no new
state, no record-format changes, no parallel paths.

### 1. Teach the row-4 git verifier the strike cascade (FR-1)

In `src/lib/lifecycle/workflows.ts`, extract the per-branch cascade out of
`verifyBranchMergedImpl` into a helper
`verifyConventionBranchMerged(ctx, branchName): Promise<StepResult | null>`
(`null` = branch absent locally and remotely). `verifyBranchMergedImpl` then:

1. keeps the review-status shortcut exactly as-is (issue-level);
2. evaluates `feature/<id>` — pass/skip returns immediately (the common case;
   zero extra git or forge calls for non-strike issues, NFR-1);
3. **only when the feature check fails or the branch is absent**, evaluates
   `strike/<id>` through the identical cascade. A strike pass returns `stepOk`
   whose details name the strike branch and note that the superseded feature
   branch retains unmerged commits;
4. when the feature branch was absent everywhere and the strike check did not
   pass, returns the exact current `BRANCH_ABSENT_MERGE_ERROR`
   (`src/lib/lifecycle/dod.ts:70`) so `checkMergedRow`'s durable-merge fallback
   (`dod-gate.ts:263-302`) keeps working unchanged;
5. when the feature check failed and the strike check did not pass, returns the
   original feature failure — behavior for non-strike issues is byte-identical.

The strike cascade reuses `verifySquashMergedPrByBranch`
(`workflows.ts:691-800`) unchanged — it already takes `(ctx, branchName,
branchRef)` and already implements the merged-PR-head, post-PR-commit, and
state-plane policies.

**Decision (auto):** when the strike branch verifies merged, row 4 passes even
though the feature branch retains unmerged commits. Rationale: the strike
exists precisely to supersede those commits, and a strict "feature code-diff
must be empty" rule fails legitimate landings — PAN-3116's feature diff
differs from main by one line of rebase drift (+194/−660 on closed #3127 vs
+194/−659 on merged #3152). The residual risk (someone pushes genuinely new
work to the feature branch *after* the strike landed) is surfaced, not hidden:
the success details name the superseded-branch residual, and row 4 remains
operator-overridable. The alternative (record-gating on
`strikeLandingState === 'landed'`) was rejected — see Hazard H2.

### 2. Make the forge PR resolver prefer the landing PR (FR-2)

In `resolveIssuePullRequestRef` (`src/lib/overdeck/pull-requests.ts:127-159`),
collect PR candidates from **both** convention heads instead of stopping at the
first head with any PR, then rank:

1. `OPEN` first — an open PR represents active work and must keep winning for
   the dashboard PR tab mid-pipeline;
2. then `MERGED` (most recently merged wins) — the landing evidence;
3. then anything found (current behavior — first candidate).

Single-candidate resolution (the overwhelming common case) performs exactly the
same lookups as today; the ranking queries only fire when two heads both carry
PRs. The gh CLI path in `lookupPullRequestNumberForBranch`
(`src/lib/github-pr-lookup.ts:12-40`) gains `--json number,state,mergedAt` so
ranking needs no extra `gh pr view`; the GitHub App path
(`listPullRequestsForHeadPromise`, `src/lib/github-app.ts:574-596`) already
returns `state` / `merged` / `mergedAt`.

This is the fix at the shared layer: row 4's `readPullRequest`
(`dod-gate.ts:73-79`) then resolves the strike PR, populates
`merged.mergeCommit` / `merged.mergedAt` from the squash merge commit, and rows
6 and 7 receive a resolvable commit through the existing wiring
(`dod-gate.ts:460-461`). The dashboard PR tab (`fetchIssuePullRequest`,
`fetchIssuePullRequestDiff`, `fetchIssuePullRequestDetails`) improves
consistently — it shows the PR that landed the issue instead of the superseded
closed one. A CLOSED superseded PR is thereby treated as *evidence of
supersession*, not as the verdict: with change 1 passing row 4, the observed
string records the MERGED strike PR (number, mergedAt) instead of stopping at
"PR #3127 CLOSED".

### 3. Decouple row 7 from the row-4 cascade (FR-3)

In `evaluateDodGate` (`dod-gate.ts:451-461`), pass the merged row's status into
the deploy row: `deps.deploy(ctx, { mergedAt, mergeCommit, mergedRowStatus:
merged.status })`. In `checkDeployRow` (`dod-gate.ts:392-430`), when
`merge.mergeCommit` is missing:

- merged row **missed** → `skip` with an observed string naming the dependency,
  e.g. `no merge commit resolved because the merged row missed — deploy
  ancestry depends on row 4; build ancestry unchecked`. The row-4 miss already
  blocks the gate; a second miss is noise.
- merged row **passed** without a resolvable commit (durable-merge or
  branch-containment evidence) → keep `miss`, reworded to name the gap:
  `merged row passed without a resolvable merge commit; build ancestry cannot
  be checked`. This case is a genuine evidence hole and must keep blocking.

The `DeployRowDeps` interface and the `EvaluateDodGateDeps['deploy']` signature
gain the one field; `workflows.ts` passes the gate through unchanged.

### 4. Documentation (FR-4)

Update `docs/DEFINITION-OF-DONE.md` in the same commit as the behavior:

- Row 4 (`merged`) description gains the strike branch: merge evidence resolves
  through either convention head (`feature/<id>` or `strike/<id>`), forge
  squash-merge detection included.
- The "Branch absence is not merge evidence" rule gains one sentence: a
  strike-landed issue passes row 4 through the strike branch's own evidence,
  and the superseded feature branch's unmerged commits are reported in the
  observed string rather than treated as a miss.
- Row 7 (`deploy`) description notes the dependency behavior: when the merged
  row missed, deploy reports the unresolved dependency instead of a second
  miss.
- `src/lib/lifecycle/dod.ts` row-4 `expected` string is updated to match
  (`'PR merged on the forge (feature or strike head), or branch work contained
  in main (non-PR landing)'`). `tests/unit/lib/lifecycle/dod-doc-drift.test.ts`
  only couples row num/id, so no drift-test change is needed.

## Requirements

- **FR-1** — Row 4 evaluates `strike/<id>` through the same three-lens cascade
  (ancestor, empty code diff, merged forge PR) whenever the `feature/<id>`
  check does not pass, and passes with strike-branch attribution when the
  strike branch is merged.
- **FR-2** — Forge PR resolution across convention heads ranks OPEN > MERGED >
  other, so a closed superseded PR never shadows the PR that landed the issue;
  single-PR issues resolve exactly as today.
- **FR-3** — Row 7 reports `skip` with dependency wording when row 4 missed,
  and only reports `miss` for a missing merge commit when row 4 passed without
  one.
- **FR-4** — `docs/DEFINITION-OF-DONE.md` and the `DOD_ROWS` expected strings
  describe the strike-landing resolution in the same commit as the behavior.
- **NFR-1** — Issues with no strike branch take byte-identical code paths: the
  strike cascade and the PR ranking run only after the feature-first checks
  fail or find multiple PRs.
- **NFR-2** — Every new branch of logic is covered by unit tests in the
  existing dep-injection style: `tests/unit/lib/lifecycle/dod-gate.test.ts`,
  `tests/unit/lib/lifecycle/workflows.test.ts` (mocked `execAsync`,
  `__testInternals.verifyBranchMerged`), and
  `tests/unit/dashboard/server/routes/issue-pr.test.ts`.

## NonGoals

- **Healing PAN-3116's stale strike record.** Its durable record still says
  `strikeLandingState: "recovering"` although the strike landed; nothing in
  this issue writes strike-landing state. The fix deliberately resolves through
  branch + forge evidence so record staleness cannot block close-out.
- **Recording the strike merge commit durably at merge time** (e.g. in
  `closeOut.merges` or a new review-status field). A reasonable follow-up; not
  needed once the forge is the oracle.
- **`isBranchMerged` in `src/lib/close-out.ts`.** The legacy checker feeds only
  `reap-issue-residue.ts` (a safety probe before teardown). It has the same
  feature-only blindness, but tightening it is not required to unblock
  close-out and touching it widens blast radius.
- **Loosening the containment lens.** The `unmergedRefs.length === 0`
  requirement stays; the lens is for non-PR landings and cannot see squash
  merges by construction.
- **Durable-merge fallback hardening.** `checkMergedRow`'s branch-absent path
  counts `closeOut.merges` artifact URLs without checking they merged (for
  PAN-3116 that list contains the CLOSED #3127). Out of scope; flagged as
  hazard H3.

## Hazards (carried into continue.json)

- **H1 — Post-strike feature pushes become invisible to row 4.** Accepted per
  Proposal §1: success details must name the residual so it is visible in the
  gate output, and row 4 stays operator-overridable.
- **H2 — The durable strike record is not consulted** (the issue text suggested
  preferring it): verified during planning that `StrikeLandingStatus`
  (`src/lib/strike-landing.ts`) records `strikeReadyHead` and attempt outcomes
  but no merge commit, and PAN-3116's record is stale (`recovering`). The
  forge is the oracle.
- **H3 — The branch-absent durable-merge fallback counts unmerged PR URLs**
  (PAN-3116's `closeOut.merges` names the CLOSED #3127). Not changed here; if
  it ever false-passes, the fix belongs to that fallback's evidence check.
- **H4 — Behavior change beyond the gate:** `resolveIssuePullRequestRef` also
  backs the dashboard PR tab and PR diff endpoints; the OPEN > MERGED ranking
  keeps mid-pipeline display stable, but reviewers should sanity-check the PR
  tab on a strike-landed issue during UAT.
