## 0. Glossary (define-before-use)

- **ACP** — the Agent Client Protocol (https://agentclientprotocol.com): a JSON-RPC protocol over stdio between a **client** (an editor such as Zed, or any tool that embeds agents) and an **agent** (a process that answers prompts). The client spawns the agent process and owns its stdin/stdout.
- **ACP client role vs agent role** — a process speaks exactly one role per connection. Overdeck today implements only the client role (it hosts ACP-speaking harnesses like kimi-code). This PRD implements the agent role.
- **effect-acp** — the vendored Effect implementation of ACP at `packages/effect-acp/` (from t3code, see `packages/effect-acp/VENDORING.md`). Its `effect-acp/agent` entry point (`packages/effect-acp/src/agent.ts`) provides the `AcpAgent` service with `handleInitialize` / `handleCreateSession` / `handleLoadSession` / `handlePrompt` / `handleCancel` handler registration and `agent.client.sessionUpdate(...)` for streaming updates back to the client. `layerStdio()` (`packages/effect-acp/src/agent.ts:530`) wires it to stdio.
- **The mock peer** — `src/lib/acp/__tests__/fixtures/acp-mock-peer.ts`: a complete, working 111-line ACP agent built on `AcpAgent.layerStdio()`. It is the canonical in-repo example of the agent role and the template for the bridge's handler wiring.
- **Conversation** — Overdeck's supervised interactive session domain object: a row created by `createConversation` (`src/lib/overdeck/conversations.ts:1219`), a tmux session `conv-<name>` on the `overdeck` socket, and a harness process inside it. Conversations are persistent, dashboard-discoverable, resumable, and cost-tracked.
- **The bridge** — the new process this PRD builds: `pan acp serve`, an ACP agent over stdio whose handlers translate ACP requests into calls against the dashboard server's HTTP/WS doors.
- **Dashboard doors** — the canonical HTTP/WS surface of the dashboard server (Node 22, port 3011). The bridge uses ONLY these; it never touches the DB, state worktree, or tmux directly.
- **Turn** — one ACP `session/prompt` request/response cycle. ACP requires the agent to resolve the prompt request with a `stopReason` when the turn ends.
- **Working state (`isWorking`)** — the dashboard's canonical "conversation is mid-turn" signal: `summarizeConversationActivity` (`src/dashboard/server/services/conversation/activity-summary.ts:38-67`) computes `isWorking` from transcript recency, `lastTurnCompletedAt`, streaming/tool-wait heuristics; the enriched conversation list rows carry it (`src/lib/overdeck/conversation-list.ts:119-126`, served by `GET /api/conversations`, `routes/conversations.ts:205`). `isWorking === false` on a live session means the turn is over and the harness awaits input.
- **Pending-input feed** — `GET /api/conversations/pending-input` (`routes/conversations.ts:237`) lists conversations with a **blocking surface** (pending AskUserQuestion / approval menu — "rows that actually need attention", per the route comment). It is NOT an idle-at-prompt signal; a normally completed turn never appears here. The bridge uses it only to detect a blocked conversation (D-6).

## 1. Problem and value

Overdeck consumes only the client half of effect-acp. `src/lib/acp/session-runtime.ts:18` imports `effect-acp/client` to host ACP harnesses; the agent half is exercised nowhere outside the test fixture. Consequently no external ACP client — Zed, or any editor/tool speaking ACP — can drive Overdeck.

The value of closing that gap: an editor becomes an alternative front-end to Overdeck conversations. The conversation stays a first-class Overdeck object (dashboard-visible, persistent tmux session, resumable, cost-tracked, `pan tell`-reachable), while the editor gets structured streaming output instead of a terminal embed. Nothing about the pipeline changes; this is a new *presentation* surface over the existing conversation domain.

## 2. Locked design decisions

- **D-1 — The bridge is `pan acp serve`, a CLI subcommand speaking ACP over stdio.** ACP clients spawn `pan acp serve` as their agent command. It runs `AcpAgent.layerStdio()` exactly as the mock peer does (`acp-mock-peer.ts:109`), provided with `NodeServices.layer`.
- **D-2 — The bridge is a thin client of the dashboard server. Doors only.** Every read and write goes through the dashboard HTTP/WS surface. The bridge spawns no processes, opens no SQLite handle, touches no tmux socket, and runs no orchestrator (single-Deacon invariant). If the dashboard is unreachable, `initialize` fails with a descriptive `AcpError` — there is no fallback local-spawn path, deliberately.
- **D-3 — ACP `sessionId` IS the conversation name.** `session/new` → `POST /api/conversations` with **no `message` field** — `handleConversationCreate` (`src/lib/overdeck/conversation-runtime.ts:914`) generates the name server-side (`generateConversationName()`, `:939`), accepts an omitted message (delivery is guarded by `if (message)`, `:953`), and spawns the session. The returned conversation `name` becomes the ACP `sessionId`. `session/load` resolves the same name back through the doors. **No new persistence, no side files, no mapping table.**
- **D-4 — Prompt turns resolve on the working→idle transition.** After delivering a prompt via `POST /api/conversations/:name/message` (`routes/conversations.ts:584` → `handleConversationMessage` → the delivery door `deliverAgentMessage`, `src/lib/agents/delivery.ts:279`), the bridge polls the enriched conversation list (`GET /api/conversations`) and resolves the ACP prompt with `stopReason: "end_turn"` when its session's row reports `isWorking === false`. **Race guard:** an `isWorking === false` observation may resolve the turn only after the bridge has first observed the turn start — either an `isWorking === true` sample or a first streamed update for this turn — because immediately after delivery the row can still read idle before the harness picks up the prompt. A bounded turn-start grace window (default 15s) prevents a hang if the turn never visibly starts (resolve `end_turn` with whatever streamed, and log). Streaming updates flow independently of turn resolution (D-5).
- **D-5 — Streaming rides the same live message stream the dashboard UI uses.** The bridge connects to `/ws/rpc` (`src/dashboard/server/ws-rpc.ts:1321`) and calls `WS_METHODS.subscribeConversationMessages` (`ws-rpc.ts:887`, PAN-451) with the conversation name. Message deltas translate to ACP `session/update` notifications. Fallback when the WS is unavailable: poll `GET /api/conversations/:name/messages` (`routes/conversations.ts:466`) and diff. The fallback is a degraded mode, not the design.
- **D-6 — v1 permission scope: none.** Conversations run under their normal permission regime (dashboard AUQ pipeline). The bridge does NOT map AskUserQuestion / harness permission prompts to ACP `session/request_permission` in v1 — that mapping is a named follow-up (see §7). Until then, a conversation waiting on an operator answer simply keeps its ACP turn open (the pending-input feed is how the bridge can tell blocked-on-operator apart from still-working, and `isWorking` stays true while a blocking surface is up — verify that assumption when implementing WI-3 and, if a blocking surface reads idle, treat presence in the pending-input feed as "turn still open"); the operator can answer from the dashboard as today.
- **D-7 — Model/project selection is per-serve, not per-session, in v1.** `pan acp serve --project <key> --model <m>` applies to every session the bridge creates (`projectKey` and `model` are accepted by `handleConversationCreate`, `conversation-runtime.ts:920-935`). Do not pass `--model` defaults from code — omit the field entirely when the flag is absent so Cloister/config routing decides (never-hardcode-a-model rule).
- **D-8 — Cancellation maps to abort, not stop.** ACP `session/cancel` → `POST /api/conversations/:name/abort` (`routes/conversations.ts:444`), which interrupts the current turn but leaves the conversation alive. `session/stop`-like semantics (killing the conversation) are NOT exposed over ACP; conversations are never deleted by the bridge.

## 3. Requirements

### Functional

- **FR-1** `pan acp serve` starts an ACP agent over stdio that completes `initialize` (protocolVersion 1, `agentInfo.name: "overdeck"`, `loadSession: true` capability) when the dashboard server is healthy, and fails `initialize` with a descriptive error naming the dashboard URL when it is not.
- **FR-2** `session/new` creates a real Overdeck conversation through `POST /api/conversations` and returns its server-generated name as `sessionId`. The conversation appears in the dashboard conversation list like any other.
- **FR-3** `session/prompt` delivers the message through `POST /api/conversations/:name/message`, streams the assistant's output back as `session/update` notifications (`agent_message_chunk` for assistant text; `tool_call` / `tool_call_update` for tool activity where the parsed message stream distinguishes them), and resolves with `stopReason: "end_turn"` on the working→idle transition per D-4 (including its race guard).
- **FR-4** `session/load` accepts a previously issued `sessionId` (conversation name), replays the existing transcript as `session/update` notifications carrying `_meta: { isReplay: true }` (the pattern the mock peer demonstrates, `acp-mock-peer.ts:31-55`), and leaves the session live for further prompts. Loading a name that resolves to no conversation fails with a session-not-found `AcpError`.
- **FR-5** `session/cancel` calls the abort door and causes the in-flight prompt (if any) to resolve with `stopReason: "cancelled"`.
- **FR-6** A delivery failure (the message route's 504 `MessageDeliveryFailed` response, `routes/conversations.ts:604-609`) rejects the ACP prompt with an error that includes the server's `details` string.
- **FR-7** The bridge honors `OVERDECK_DASHBOARD_URL` with the same default as the rest of the CLI (`http://127.0.0.1:3011`, the convention at `src/lib/agent-runtime.ts:27`); resolution goes through the existing shared resolver used by CLI-side callers (`getDashboardApiUrlSync`, exported from the module that `src/lib/activity-logger.ts:234` imports it from) — do not invent a second resolver.
- **FR-8** `--project <key>` and `--model <m>` flags forward to conversation creation; both omitted fields are absent from the request body, never empty strings or hardcoded defaults.

### Non-functional

- **NFR-1** The bridge performs zero direct store access: no `overdeckDb()`/SQLite import, no state-worktree reads, no `tmux` invocation, no direct JSONL transcript reads. Mechanical check: the new bridge modules import nothing from `src/lib/database/`, `src/lib/tmux.ts`, or `src/lib/conversations/jsonl-async.ts`.
- **NFR-2** The bridge is a persistent process for the lifetime of the ACP connection but owns no durable state; killing and restarting it loses nothing (sessions resolve by name through the doors — D-3).
- **NFR-3** All bridge I/O is async (async-tmux/no-execSync rules do not bite here because the bridge shells out to nothing — keep it that way).
- **NFR-4** Turn-resolution polling (D-4) uses a bounded interval (default 1000ms) and stops when the turn resolves or cancels; the poll must not keep the process alive after the ACP connection closes (tie it to the connection scope).

## 4. Architecture

```
Zed (ACP client)
  │ spawns, owns stdio
  ▼
pan acp serve                      ← the bridge (new)
  ├─ AcpAgent.layerStdio()          effect-acp/agent, as in acp-mock-peer.ts
  ├─ handleInitialize  ──► GET  /api/... health probe (any cheap authenticated-origin door)
  ├─ handleCreateSession ─► POST /api/conversations            {model?, projectKey?}   → name = sessionId
  ├─ handlePrompt ────────► POST /api/conversations/:name/message
  │      └─ resolves on isWorking false via GET /api/conversations (D-4 race guard)
  ├─ handleLoadSession ───► GET  /api/conversations/:name/messages  → replay w/ _meta.isReplay
  ├─ handleCancel ────────► POST /api/conversations/:name/abort
  └─ streaming task ──────► WS /ws/rpc  subscribeConversationMessages(name)
                                └─ translate → agent.client.sessionUpdate(...)
  ▼
Dashboard server (Node 22 dist, :3011) — existing doors, unchanged
  ▼
Conversation: conv-<name> tmux session, harness process, JSONL transcript
```

The dashboard server needs **no changes** for v1 except the implementation checkpoint in WI-2 (origin validation). Everything else composes existing doors.

### WI-3 — Prompt turn lifecycle (traces: FR-3, FR-5; NFR-4)

- In `agent-bridge.ts`: `handlePrompt` delivers via POST `/api/conversations/:name/message`, then races: (a) turn-state poll loop (1000ms interval against `GET /api/conversations`, tracking the session row's `isWorking` — resolve `end_turn` only on a working→idle transition per the D-4 race guard, with the 15s turn-start grace window), (b) cancellation signal from `handleCancel` (resolve `cancelled` after POST abort), (c) connection close (interrupt via Effect scope).
- Use Effect primitives (`Effect.race`, `Effect.repeat` with `Schedule.spaced`) — the bridge is Effect-native end to end; do not hand-roll `setInterval`.
- **Repo rule restated for the executor:** any test exercising the poll interval MUST use `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync(...)` — never real timers (fake-timers rule; see the global CLAUDE.md section "Fake timers for retry / backoff / delay-based tests").
- **Test:** extend `agent-bridge.test.ts` (fake timers throughout) — turn resolves on working→idle transition; an idle sample BEFORE any working sample does NOT resolve the turn (the race-guard case); the 15s turn-start grace window resolves a never-started turn; cancel mid-turn resolves `cancelled` and fires the abort door exactly once; connection close stops the poller (no timer leaks — assert `vi.getTimerCount() === 0` after scope close).

### WI-4 — Streaming translator (traces: FR-3)

- **New file** `src/lib/acp/agent-bridge-stream.ts`. Connects to `ws://<dashboard>/ws/rpc`, issues `subscribeConversationMessages` for the session's conversation name (`ws-rpc.ts:887` — read the frontend's client usage of `WS_METHODS.subscribeConversationMessages` to copy the exact frame shape rather than reverse-engineering it), and translates the emitted message events into `agent.client.sessionUpdate` calls:
  - assistant text delta/snapshot → `{ sessionUpdate: "agent_message_chunk", content: { type: "text", text } }` — the stream emits snapshots for some harnesses (`ws-rpc.ts:103-132` documents full-parse snapshot semantics); dedupe by message id and emit only the appended suffix of a grown message.
  - tool activity (messages the parser marks as tool use/result) → `tool_call` / `tool_call_update` with `status` mapped from the parsed state.
  - anything unmappable → skip silently (v1 is lossy-but-correct; never crash the stream on an unknown message kind).
- Fallback (D-5): when the WS connect or subscribe fails, poll `GET /api/conversations/:name/messages` on the same fake-timer-friendly schedule and diff by message id.
- **Test:** `src/lib/acp/__tests__/agent-bridge-stream.test.ts` — snapshot-growth dedupe (two snapshots, second emits only the suffix), tool mapping, unknown-kind skip, WS-fail → poll fallback engages.

### WI-5 — Session load / replay (traces: FR-4)

## 7. Non-goals / named follow-ups

- **Permission bridging** (AUQ / harness permission prompts → ACP `session/request_permission`) — follow-up issue; v1 keeps operator answers on the dashboard (D-6).
- **Per-session model/mode selection over ACP** — follow-up; v1 is per-serve flags (D-7).
- **Terminal embedding** (`effect-acp/terminal`) and file-system methods (`fs/read_text_file` etc.) — the bridge advertises no such capabilities in v1; ACP capability flags must say so explicitly in `handleInitialize`.
- **Exposing pipeline work agents over ACP** — conversations only. Work/plan/review agents stay pan-pipeline-only.

## 8. Intersecting repo rules restated (executor must follow)

- **Persistent sessions only** — the bridge attaches to persistent conversations; never add a one-shot/headless execution path (`claude -p`, `codex exec`) as a "simpler" alternative.
- **Doors only / no direct store access** — NFR-1 is the single-source-of-truth tenet applied to this feature; a direct DB or tmux read in the bridge is a defect even if convenient.
- **No execSync anywhere server-reachable; fake timers for all delay tests; never hardcode a model fallback** (D-7).
- **Dashboard changes** (if the WI-2 checkpoint forces any server-side origin change): build with `npm run build` before restart; never hot-patch a boot path; `pan restart --health-timeout 120000` (milliseconds).
- **Commit per work item and push before `pan task done`** (managed-work push rule).
