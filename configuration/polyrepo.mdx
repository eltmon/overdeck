Overdeck supports projects with multiple git repositories (like separate frontend/backend repos). Configure workspace settings directly in `projects.yaml` to manage polyrepo workspaces.

## Overview

Polyrepo workspaces create git worktrees in each repository, allowing agents to work across multiple codebases simultaneously while maintaining proper git isolation.

## Recommended: Separate Infra Repository

For polyrepo projects, we strongly recommend maintaining a **dedicated infrastructure repository** alongside your code repos:

```
myproject/
├── infra/                    # Infrastructure repo (git)
│   ├── .devcontainer-template/   # Templates for workspace creation
│   │   ├── dev.template          # Dev script template
│   │   ├── compose.infra.yml.template
│   │   └── docker-compose.devcontainer.yml.template
│   ├── new-feature              # Script to create workspaces
│   ├── remove-feature           # Script to clean up workspaces
│   ├── certs/                   # SSL certificates
│   └── traefik/                 # Traefik config
├── frontend/                 # Frontend repo (git)
├── backend/                  # Backend repo (git)
└── workspaces/               # Feature workspaces (git worktrees)
    └── feature-xxx/
        ├── fe/               # Worktree of frontend
        ├── api/              # Worktree of backend
        └── .devcontainer/    # Generated from templates
```

**Benefits of a separate infra repo:**

1. **Version-controlled templates** - Dev script changes are tracked and shared
2. **Centralized configuration** - DNS, ports, Traefik rules in one place
3. **Workspace consistency** - All workspaces use the same templates
4. **Team collaboration** - Infra changes go through normal PR review
5. **Easy updates** - Fix a template once, regenerate affected workspaces

**Key files in the infra repo:**

| File | Purpose |
|------|---------|
| `dev.template` | Template for `./dev` script (container management) |
| `new-feature` | Creates workspace with git worktrees + devcontainer |
| `remove-feature` | Cleans up workspace and worktrees |
| `.devcontainer-template/` | Docker Compose and devcontainer templates |

## Configuration in projects.yaml

```yaml
projects:
  myapp:
    name: "My App"
    path: /home/user/projects/myapp
    issue_prefix: APP

    workspace:
      type: polyrepo
      workspaces_dir: workspaces
      # Default branch for all repos (optional, defaults to 'main')
      default_branch: main

      # Git repositories to include in each workspace
      # Each repo is a SEPARATE git repository with its own .git
      repos:
        - name: fe
          path: frontend           # Relative to project root
          branch_prefix: "feature/"
          # default_branch: main   # Can override workspace default per-repo
          # package_manager: pnpm   # Optional: host-side install in this repo at workspace creation
        - name: api
          path: backend
          branch_prefix: "feature/"
          # default_branch: develop  # Example: API uses 'develop' as default
          ci: none  # this repo runs no CI

      # DNS entries for local development
      dns:
        domain: myapp.test
        entries:
          - "{{FEATURE_FOLDER}}.{{DOMAIN}}"
          - "api-{{FEATURE_FOLDER}}.{{DOMAIN}}"
        sync_method: wsl2hosts  # default wsl2hosts; use hosts_file or dnsmasq on Linux and macOS

      # Port assignments for services
      ports:
        redis:
          range: [6380, 6499]

      # Service definitions: the commands and ports Overdeck shows for each service (it does not start them)
      services:
        - name: api
          path: api
          start_command: ./mvnw spring-boot:run
          docker_command: ./mvnw spring-boot:run
          health_url: "https://api-{{FEATURE_FOLDER}}.{{DOMAIN}}/actuator/health"
          port: 8080
        - name: frontend
          path: fe
          start_command: pnpm start
          docker_command: pnpm start
          health_url: "https://{{FEATURE_FOLDER}}.{{DOMAIN}}"
          port: 3000

      # Docker configuration
      docker:
        # Any value starts Overdeck's own Traefik from ~/.overdeck/traefik/docker-compose.yml
        # (installed by pan install). Overdeck never reads a project compose file here.
        traefik: ~/.overdeck/traefik/docker-compose.yml
        compose_template: infra/.devcontainer-template

      # Agent configuration templates
      agent:
        template_dir: infra/.agent-template
        templates:
          - source: .mcp.json.template
            target: .mcp.json
        copy_dirs:             # directories are copied into the workspace, not linked
          - .claude/commands
          - .claude/skills

      # Environment template
      env:
        template: |
          COMPOSE_PROJECT_NAME={{COMPOSE_PROJECT}}
          FRONTEND_URL=https://{{FEATURE_FOLDER}}.{{DOMAIN}}
        load: false  # true also exports this .env into agent shells and host quality gates
```

A few notes on these keys:

- **Repos:** each repo can also set `forge` (`github` or `gitlab`), `remote` (a legacy alias for `forge`) and `pr_target` (the branch its PR targets). The Add-project dialog's **Add this folder as one project** writes this `workspace` block for you. Set `ci: none` on a repo that runs no CI. The merge train then counts a GitLab merge request in that repo with no pipeline as passing; a failing or pending pipeline still blocks the merge, and a repo without the field still needs a green pipeline. It has no effect on GitHub member repos. Remove it as soon as the repo gains CI.
- **Services:** each service needs its own `start_command`, and optionally `docker_command`, `health_url` and `port`.
- **Docker:** setting `docker.traefik` makes Overdeck start its own Traefik from `~/.overdeck/traefik/docker-compose.yml` (installed by `pan install`) when a workspace starts its containers. It never reads a project compose file. See [Docker & HTTPS Setup](/guides/docker-setup).
- **Agent templates:** templates that target `CLAUDE.md`, `AGENTS.md` or another harness-native instruction file are dropped. Put project instructions in `.overdeck/context/project.md` instead (see [Context Layers](/configuration/context-layers)). `symlinks:` is a deprecated alias for `copy_dirs:`.

## Dependency installs in polyrepo workspaces

A polyrepo workspace root is a plain container directory with no `package.json`, so Overdeck skips the root install there. Per-repo installs run only for repos that set `package_manager` (`bun`, `npm`, or `pnpm`) and have a `package.json` in their directory.

Leave `package_manager` unset on a repo when a devcontainer installs that repo's dependencies (for example a pnpm init service): a host install can conflict with the container's pnpm store. A failed per-repo install fails workspace creation; re-running the command resumes setup.

## The workspace root repository

The workspace root becomes a small local repository (no remote) when planning completes. It holds the sub-repo worktrees alongside Overdeck's own files: the synced skills and agent template (`.claude/`, `.mcp.json`), Hume config (`.hume-config`), and env (`.env`). Overdeck lists these in the root `.gitignore` so they never count as uncommitted work.

If a workspace was created before Overdeck started writing these entries, the next agent start from the dashboard repairs it automatically; no manual step is needed. Anything else left uncommitted at the workspace root still stops a start, exactly as before.

## Template Placeholders

| Placeholder | Example | Description |
|------------|---------|-------------|
| `{{FEATURE_NAME}}` | `min-123` | Normalized issue ID |
| `{{FEATURE_IDENT}}` | `min_123` | FEATURE_NAME as an unquoted SQL identifier |
| `{{FEATURE_FOLDER}}` | `feature-min-123` | Workspace folder name |
| `{{BRANCH_NAME}}` | `feature/min-123` | Git branch name |
| `{{COMPOSE_PROJECT}}` | `myapp-feature-min-123` | Docker Compose project |
| `{{DOMAIN}}` | `myapp.test` | DNS domain |
| `{{PROJECT_NAME}}` | `myapp` | Project directory name |
| `{{PROJECT_PATH}}` | `/home/user/projects/myapp` | Project root |
| `{{PROJECTS_DIR}}` | `/home/user/projects` | Parent directory of the project root |
| `{{WORKSPACE_PATH}}` | `/home/user/projects/myapp/workspaces/feature-min-123` | Workspace directory |
| `{{HOME}}` | `/home/user` | Home directory |
| `{{CHANGED_BASE}}` | `origin/main` | Git ref quality gates diff against (set only when quality gates run) |

## What Your Project Needs to Provide

Overdeck is an orchestration layer: it manages workspaces, agents, and workflows, but **your project repository provides the actual templates and configuration**.

Projects can be as simple as just a git repo (for worktree-only workspaces) or as complex as a full polyrepo with Docker, Traefik, and database seeding.

### Required: Workspace Templates

Your project needs a `.devcontainer/` or template directory with:

```
your-project/
├── infra/
│   └── .devcontainer-template/      # Template for workspace containers
│       ├── docker-compose.devcontainer.yml.template
│       ├── compose.infra.yml.template   # Optional: separate infra services
│       ├── Dockerfile
│       └── devcontainer.json.template
└── ...
```

**Docker Compose templates** should use placeholders that Overdeck will replace:

```yaml
# docker-compose.devcontainer.yml.template
services:
  api:
    build: ./api
    user: vscode  # Run as non-root to avoid permission issues
    labels:
      - "traefik.http.routers.{{FEATURE_FOLDER}}-api.rule=Host(`api-{{FEATURE_FOLDER}}.{{DOMAIN}}`)"
    environment:
      - DATABASE_URL=postgres://app:app@postgres:5432/mydb

  frontend:
    build: ./fe
    user: vscode  # Run as non-root to avoid permission issues
    labels:
      - "traefik.http.routers.{{FEATURE_FOLDER}}.rule=Host(`{{FEATURE_FOLDER}}.{{DOMAIN}}`)"
```

> **⚠️ Important: File Permissions**
>
> Always run containers as a non-root user (e.g., `user: vscode`) to avoid permission issues.
> Files created by root-owned containers cannot be removed by `pan workspace destroy` without sudo.
> The Microsoft devcontainers base image includes a `vscode` user (UID 1000) that matches most host users.

### Required for HTTPS: Traefik Configuration

You do not provide a Traefik compose file. Setting `docker.traefik` makes Overdeck start its own Traefik from `~/.overdeck/traefik/docker-compose.yml` (installed by `pan install`); it never reads a project compose file. Your compose templates only need the Traefik router labels shown above. See [Docker & HTTPS Setup](/guides/docker-setup).

### Required for Database Seeding: Seed Directory

For projects with databases:

```
your-project/
├── infra/
│   └── seed/
│       └── seed.sql              # Sanitized production data
└── ...
```

Your compose template should mount this:
```yaml
services:
  postgres:
    image: postgres:16
    volumes:
      - /path/to/project/infra/seed:/docker-entrypoint-initdb.d:ro
```

### Optional: Agent Templates

For customizing how agents work in your project:

```
your-project/
├── infra/
│   └── .agent-template/
│       ├── .mcp.json.template    # MCP server configuration
│       └── .claude/commands/     # Copied into each workspace (copy_dirs)
└── .claude/
    └── skills/                   # Project-specific skills
        └── my-project-standards/
            └── SKILL.md
```

Templates that target `CLAUDE.md`, `AGENTS.md` or another harness-native instruction file are dropped. Project instructions belong in `.overdeck/context/project.md`; see [Context Layers](/configuration/context-layers).

## Quick Checklist

| Component | Required? | Location | Purpose |
|-----------|-----------|----------|---------|
| Docker Compose template | Yes (for Docker workspaces) | `infra/.devcontainer-template/` | Container configuration |
| Traefik | Only for HTTPS | `~/.overdeck/traefik/` (installed by `pan install`) | Reverse proxy |
| Seed file | Only if database needed | `infra/seed/seed.sql` | Pre-populate database |
| Agent template | Recommended | `infra/.agent-template/` | MCP config and copied directories |
| Project skills | Optional | `.claude/skills/` | Project-specific workflows |

## Example: Minimal Setup

For a simple monorepo with no Docker:

```yaml
# ~/.overdeck/projects.yaml
projects:
  simple-app:
    name: "Simple App"
    path: /home/user/projects/simple-app
    issue_prefix: APP
    # No workspace config needed - uses git worktrees
```

Overdeck creates workspaces as git worktrees. Docker, HTTPS, and seeding are opt-in.

## Container Configuration Tips

When setting up Docker containers for workspaces, avoid these common pitfalls:

**Maven projects:**
- DO NOT set `MAVEN_CONFIG=/some/path` as an environment variable
- Maven interprets `MAVEN_CONFIG` as additional CLI arguments, not a directory path
- This causes "Unknown lifecycle phase" errors (e.g., "Unknown lifecycle phase /maven-cache")
- Instead, use `-Dmaven.repo.local=/path/to/cache` in the Maven command

```yaml
# WRONG - causes Maven startup failure
environment:
  - MAVEN_CONFIG=/maven-cache

# CORRECT - use command line argument
command: ./mvnw spring-boot:run -Dmaven.repo.local=/maven-cache/repository
volumes:
  - ~/.m2:/maven-cache:cached
```

**pnpm projects:**
- Set `PNPM_HOME=/path` to configure the pnpm store location
- Mount a named volume for the store to share across containers

## Polyrepo Merge Considerations

A polyrepo issue has one PR or MR per repo. **Merge** handles them together as one merge set, and verifies every repo. Automatic merging skips polyrepo issues, so merge them from the dashboard.

| Feature | Status | Notes |
|---------|--------|-------|
| Workspace creation | ✅ Supported | Creates worktrees in each repo |
| Branch management | ✅ Supported | Each repo gets its own feature branch |
| Agent work | ✅ Supported | Agents can work across repos |
| Merge | ✅ Supported | **Merge** lands every repo's PR as one merge set |
| Automatic merging | ⏭️ Skipped | Merge polyrepo issues from the dashboard |

## Quality Gates in Polyrepo Projects

Set a gate's `path` to the repo's workspace directory (its `name`, for example `fe`). The gate runs in that directory.

### How it works

Verification runs every gate. At merge time only gates whose `path` names the repo being merged run again; gates without a `path` are skipped.

| Gate config | Repo being merged | Result at merge time |
|-------------|-------------------|--------|
| `path: fe` | `fe` | ✅ Runs |
| `path: api` | `fe` | ⏭️ Skipped |
| no `path` field | `fe` | ⏭️ Skipped |

### Configuration example

```yaml
projects:
  myapp:
    name: "My App"
    path: /home/user/projects/myapp

    quality_gates:
      # Runs in the fe worktree; runs again when merging the fe repo
      fe-lint:
        command: pnpm lint
        path: fe
        required: true

      # Runs in the api worktree; runs again when merging the api repo
      api-checkstyle:
        command: ./mvnw checkstyle:check
        path: api
        required: true

      # No path: runs at the workspace root during verification, skipped at merge time
      integration-tests:
        command: make integration-test
        required: false

    workspace:
      type: polyrepo
      repos:
        - name: fe
          path: frontend       # gate.path uses the name (fe), not this path
          branch_prefix: "feature/"
        - name: api
          path: backend        # gate.path uses the name (api), not this path
          branch_prefix: "feature/"
```

> **Important:** A gate's `path` is relative to the workspace, so use the repo's `name` from the
> `workspace.repos` list, not its `path` in the project root.

## Large-Scale Projects: Progressive Polyrepo

For projects with **10 or more repositories**, consider using progressive polyrepo mode instead of the standard all-at-once approach.

| Approach | Use When | Workspace Creation | Repo Addition |
|----------|----------|-------------------|---------------|
| Standard polyrepo | 2-9 repos | All repos at once | N/A (all included) |
| Progressive polyrepo | 10+ repos | Only essential repos | On demand via CLI or skill |

**Benefits of progressive mode:**
- **Faster workspace creation:** only meta/docs repos initially
- **Less disk usage:** agents only check out repos they need
- **Flexible scope:** agents add repos as they discover what's needed
- **Cleaner meta repos:** symlinked and marked readonly for agents, with no feature branches

See [Progressive Polyrepo Workspaces](/configuration/progressive-polyrepo) for full documentation.
