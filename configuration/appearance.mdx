# Appearance

Overdeck ships two complete, named design languages for the dashboard, and the choice between them is a single setting rather than a migration you have to absorb all at once.

## The two themes

- **Ledger** — the classic dense monitoring style: DM Sans for prose, SF Mono for technical identifiers (code, IDs, hashes — same as Broadsheet), a flat medium-weight cap on everything else, panel-first layout. The one exception is the "Overdeck" sidebar wordmark, set in Space Grotesk. Ledger is now the **frozen legacy theme** — it keeps working exactly as it does today and continues to receive bug fixes, but it does not gain new visual patterns going forward.
- **Broadsheet** — the **default** theme. Geist and Geist Mono typefaces, a real type hierarchy (body text through page-level display headings), chips, soft cards, hero placeholders, and dot-metadata lines. New Overdeck UI patterns land here first, and only here.

Both themes are fully self-hosted — the dashboard makes zero external font requests in either theme, so switching (or working offline) never depends on a CDN.

## Choosing a theme

Go to **Settings → Appearance**. The **Overdeck Theme** picker shows both themes as selectable cards, each with a one-line description and a live mini-specimen rendered in that theme's own fonts, so you can compare them side by side before choosing.

Selecting a card applies the theme immediately — no page reload, no rebuild, no restart. Your choice is saved to `~/.overdeck/config.yaml` and mirrored to the browser so it survives a reload.

## Configuration

The setting is `ui.theme` in `~/.overdeck/config.yaml`:

```yaml
ui:
  theme: broadsheet # or: ledger
```

- Accepted values are `ledger` and `broadsheet`.
- Leaving it unset resolves to `broadsheet`.
- Any other value fails loudly with a clear error naming the field and the two allowed values — Overdeck never silently falls back to a default when a config value is invalid.

## What stays the same either way

The Overdeck Theme picker above is a typography, texture, and scale change. The meaning of each status color (amber = a human needs to act, blue = a machine is working, and so on) and the badge tint formula are identical under both themes, and color themes (below) never touch them either. The one small visual difference outside typography is that badges use a slightly larger corner radius under Broadsheet for texture consistency with its softer vocabulary; Ledger's badge radius is unchanged.

## Color themes

A color theme is a separate, named set of colors — terminal palette, chat code-block syntax colors, and a small UI token subset — layered on top of the Overdeck Theme and mode choices above. Two built-ins ship in the box, `overdeck-dark` and `overdeck-light`; they carry today's terminal palette and change nothing else.

**Settings → Appearance** shows a light-mode picker and a dark-mode picker under the Overdeck Theme cards. Each lists only themes of its own type (a light-mode picker never offers a dark theme). Switching the dashboard's light/dark mode swaps between the two selections immediately, with no reload.

### Configuration

The selection is `ui.color_theme` in `~/.overdeck/config.yaml`:

```yaml
ui:
  color_theme:
    light: ayu-light
    dark: ayu-dark
```

- Each mode's id is independent; either or both may be unset.
- An id that names no file, or names a theme of the wrong type for that mode (a light theme under `dark`), falls back to the built-in for that mode and logs a warning — config loading never fails on these keys.
- A general dashboard settings save never removes `ui.color_theme`.

### User themes

A theme other than the two built-ins lives as a file at `~/.overdeck/themes/<id>.json` — the file name is the id. Hand-editing or dropping in a new file there is picked up on the next reload; no restart beyond that is needed. The on-disk shape:

```jsonc
{
  "name": "Ayu Dark",
  "type": "dark", // light | dark
  "terminal": { "background": "#0d1017", "red": "#f06b73" /* ...21 keys, each optional */ },
  "syntax": { "colors": { "editor.background": "#10141c" }, "tokenColors": [ /* VS Code-style scopes */ ] },
  "ui": { "background": "#10141c", "accent": "#e6b450" /* ...6 keys, each optional */ }
}
```

Any color the theme omits falls back to the matching built-in of the same `type` — a theme that sets only `terminal.background` still gets a complete, usable terminal palette.

### Importing a VS Code theme

Choose **Import VS Code theme** next to the pickers and pick a `.json` theme file (JSON-with-comments is fine — VS Code theme files commonly carry comments). Overdeck maps it onto the shape above and shows a preview — name, swatches, and a highlighted code sample — before anything is saved:

| VS Code key | Theme field |
| --- | --- |
| `terminal.background` / `terminal.foreground` | `terminal.background` / `terminal.foreground` |
| `terminalCursor.foreground` / `terminalCursor.background` | `terminal.cursor` / `terminal.cursorAccent` |
| `terminal.selectionBackground` | `terminal.selectionBackground` |
| `terminal.ansiBlack` … `terminal.ansiBrightWhite` (16 keys) | `terminal.black` … `terminal.brightWhite` |
| `tokenColors` | `syntax.tokenColors` |
| `editor.background`, `editor.foreground` | `syntax.colors` |
| `editor.background` | `ui.background` |
| `sideBar.background` | `ui.surface` |
| `panel.border` | `ui.border` |
| `editor.foreground`, else `foreground` | `ui.foreground` |
| `descriptionForeground` | `ui.muted` |
| `focusBorder` | `ui.accent` |

A theme with no `type` field is classified by the luminance of `editor.background`; a theme with neither a `type` field nor an `editor.background` color defaults to `dark`, with a warning. Importing a `.vsix` extension package is tracked separately (#4659); a duplicate-and-edit color-picker editor for themes already in the store is tracked separately too (#4660) — until then, edit the JSON file by hand.

### What color themes never change

Signal and state colors — `--destructive*`, `--info*`, `--success*`, `--warning*`, and every `--signal-*`/`--state-*` token — are fixed by the pan-style-guide color law and are never set by a color theme's `ui` group, built-in or imported. A color theme changes terminal colors, chat syntax highlighting, and a small background/surface/border/foreground/muted/accent subset of the UI — never what a status color means.

## Creation flows are pages, not modals

Independent of which theme you use, Overdeck is moving major creation and composition flows — new project, new workspace, and future editors — out of modal dialogs and into full routed pages. Modals remain for what they're good at: confirmations and short forms of four fields or fewer. You'll see this rolled out incrementally, starting with the New Workspace flow; existing modal-based flows are migrated one at a time rather than all at once.

## For developers: why this is safe to adopt gradually

New dashboard surfaces are written against the Broadsheet vocabulary directly — no per-component "if the theme is X" logic. The display-scale utilities (page and section headings) and the eyebrow label resolve to a matching, already-shipped Ledger style when Broadsheet isn't active, so a surface built only from those renders correctly under either theme without extra work: it just looks a little denser and smaller under Ledger. The newer component vocabulary — chips, soft cards, hero placeholders, the large CTA + keycap pattern, and dot-metadata lines — has no Ledger equivalent at all; a surface built with those is a Broadsheet-only surface by design (Ledger is frozen legacy and doesn't receive new patterns). See `design/style-guide/STYLE-GUIDE.md` for the full component-level specification, including which utilities fall into each category.
