# Workspaces

A workspace is one git worktree Overdeck knows about for a registered
project — the checkout a planning, work, review, or scratch session actually
runs in. Every workspace has a `kind`: `main` (the project's primary
checkout, exactly one per project), `issue` (one per tracked issue), or
`scratch` (ad-hoc, not tied to an issue).

## Overview

Workspaces are reachable from three places in the dashboard:

- **Sidebar → Workspaces** — favorites first, then most-recently-accessed. The
  workspaces you created are listed directly; worktrees Overdeck created for
  issues collapse into a **N pipeline worktrees** count row, as do archived
  workspaces. A flat/grouped-by-project toggle persists across sessions.
- **Cmd-K / Ctrl-K** — the command palette's "Workspaces" section lists the same
  set, filterable by name, with the same **N pipeline worktrees** row to reveal
  the rest; selecting a workspace activates it and opens its view. Expanding in
  either place expands both.
- **`/workspace/:id`** — a dedicated view with a terminal (issue-kind
  workspaces, when an agent is running), workspace-filtered conversations,
  and the workspace's memory surface (status headline, phase, and observation
  timeline). Issue-kind workspaces additionally show the xBRIEF plan and
  verification gates.

## Creating a workspace from the dashboard

Click the **+** in the sidebar's **Workspaces** header, run **New workspace…**
from Cmd-K / Ctrl-K, or use **New workspace** on a project's overview (which
preselects that project). All three open the same dialog.

The dialog asks for a name, a project, a mode, and a target directory:

- **Shared directory** (the default) points the workspace at a directory it
  does not own — the project's primary path, another registered target from the
  dropdown, or anything you pick with **Browse…**.
- **Isolated worktree** creates a dedicated git worktree at
  `workspaces/scratch-<name>` on a `scratch/<name>` branch. It derives its own
  path, so the target-directory field is disabled in this mode.
- **Advanced** reveals a parent-branch override; leave it alone and Overdeck
  infers the project's current branch, shown in the field's placeholder.

<Note>
  **The preview is the point.** As you type, the panel below the fields shows
  the resolved outcome — the final path, the branch that will be created or the
  one already there, the parent branch (marked `inferred` when Overdeck guessed
  it), whether the target is a git repository, and whether a worktree gets
  made. That preview comes from the server running the *same* resolution the
  real create runs, so confirming never produces a surprise.
</Note>

Names are validated by that same resolution, not by a separate rule in the
browser: an invalid name, a missing directory, or an ambiguous project appears
as a message beside the offending field, and **Create** stays disabled until
the preview is clean. On success the new workspace appears in the rail
immediately and opens.

This is the dashboard equivalent of `pan workspace new` below — both call the
same code, so a workspace created either way is identical.

### The routes behind the dialog

The dashboard drives these; they are listed so you can reach them directly or
recognize them in logs.

| Route | What it does |
| --- | --- |
| `POST /api/workspace-registry/resolve` | Dry-runs the intent and returns the resolved outcome plus any validation findings. Writes nothing — this is what the live preview calls. |
| `POST /api/workspace-registry` | Creates the workspace. Returns `422` with the findings when the intent is invalid, otherwise `201 {id}`. |
| `POST /api/workspace-registry/:id/relocate` | Body `{path, force?}`. Re-points a workspace; `409` carries the refusal message when the rules below say no. |
| `GET /api/workspace-registry/project-targets?project=<key>` | The project's primary path plus its registered targets — the target-directory dropdown. |

The three `POST` routes require the dashboard's mutation token; the `GET` is a
plain read like the rest of the registry's reads.

## Managing a workspace

Open a workspace's view (`/workspace/:id`) and its header carries:

- **Favorite** — pins it to the top of the rail.
- **Relocate** — pick a new directory, confirm the resolved path. Relocating
  the **main** workspace additionally asks you to type its name, because that
  diverges the row from `projects.yaml`.
- **Archive** — removes it from the rail. Files, branch, and memory are left
  untouched, and it is reversible.

Issue workspaces show none of these: Overdeck's pipeline owns their worktree.
Deleting a workspace and purging its memory stay CLI-only
(`pan workspace destroy`), behind their typed confirmations.

## CLI

```bash
# Create a scratch workspace (shares the project directory by default)
pan workspace new my-scratch-notes

# --isolated creates a separate git worktree instead
pan workspace new my-experiment --isolated --parent-branch main

# --target-path points the workspace at any existing directory
pan workspace new vendor-lens --target-path ~/code/some-vendored-repo

# --dry-run prints the resolved intent as JSON and creates nothing
pan workspace new my-scratch-notes --dry-run

# Re-point an existing workspace at a new directory
pan workspace relocate vendor-lens --path ~/code/moved-vendored-repo

# Resolve (or lazily create) the project's singleton main workspace
pan workspace main

# Inspect, activate, or archive a workspace by id
pan workspace get <id>
pan workspace activate <id>
pan workspace archive <id>

# List, filtered through the same door the dashboard reads
pan workspace list --kind scratch --archived
```

<Note>
  `pan workspace` also carries an older set of subcommands (`create`,
  `migrate`, `ssh`, `destroy`, …) for the separate issue/git-worktree
  lifecycle that predates this domain.
  `new`/`main`/`get`/`activate`/`archive`/`relocate` are the ones documented
  here.
</Note>

### Targeting and relocating

A workspace is a lens that *targets* a directory, so more than one workspace can
target the same repo and a workspace can be re-pointed later. Two rules to know:

- `--target-path` and `--isolated` are mutually exclusive. An isolated worktree
  already defines its own path, so accepting both would leave two sources for
  one field.
- `pan workspace relocate` refuses issue workspaces (the pipeline owns their
  worktree path) and requires `--force` for the `main` workspace, since moving
  it diverges the row from `projects.yaml`.

Relocating never moves memory on disk — memory homes are keyed by workspace id,
not by path or name.

### What the sidebar shows

The dashboard's **Workspaces** rail lists the workspaces you created — `main`,
scratch workspaces, and any issue workspace you favorited — and collapses the
worktrees Overdeck created for issues into an expandable **N pipeline
worktrees** row. Nothing is hidden permanently: expand the row to see them all,
and issues remain reachable from the Pipeline and Board views. Main and scratch
rows also show the phase Overdeck's memory synthesized for them (`exploring`,
`building`, `shipping`, …).

### The quick-action band

Open a workspace and a band of three cards sits between the title bar and the
panels.

**Git** shows the branch, how many files are uncommitted, and how far ahead or
behind the remote you are — measured against *your branch's own upstream*, not
the repo's default branch. The count is honest because the dashboard actually
fetches when you open the view and when you press **Refresh** (at most once
every 30 seconds per checkout); the background poll only re-reads what that
fetch left behind. **Incoming (n)** expands the list of commits waiting for you.

When something can't be determined the card says so instead of guessing in your
favour: a working tree git can't read reads **status unknown**, never "clean";
a comparison that couldn't run reads **sync state unknown**, never "up to date";
and a fetch that can't reach the remote keeps saying so — through the background
polls, until a fetch actually succeeds — rather than letting stale counts look
freshly confirmed after one refresh.

**Pull** is fast-forward only, and it tells you plainly when it will not run:
an uncommitted file, a merge or rebase already in progress, a branch that has
diverged, no upstream, or a detached HEAD each come back as that specific
reason rather than a generic failure. Nothing is merged or stashed on your
behalf. On an issue workspace the button reads **Sync main** and goes through
the existing sync-main flow instead — that behavior is unchanged.

**Run** launches the workspace's run command in a tmux session rooted in the
workspace directory, and its terminal appears in the panel below. The command
defaults to the first `services[].start_command` in your project config; press
**Edit** to override it for this workspace (saving an empty command restores the
default). Once a session is live the button becomes **Restart**, which stops the
process and starts a fresh one — it does not silently re-attach to the old one —
and **Stop** ends it. If the process already exited on its own (a crashed dev
server, say), Restart still works: stopping something that is already stopped is
treated as done rather than an error. `Cmd-K → "Run workspace command"` does the same thing from
the keyboard for the workspace you used last.

Your run command is treated as sensitive: it is served only over authenticated
requests and never appears in the workspace list, since operators sometimes
embed tokens in a start command.

**Open** reveals the workspace in your file manager. To get an **Editor** button
beside it, set a command template in `~/.overdeck/config.yaml`:

```yaml
ui:
  open_in_editor_command: cursor {path}   # or: code {path}, subl {path}
```

`{path}` is replaced with the workspace directory and passed as a single
argument, so paths with spaces are safe — and because of that, quoting the
template is unnecessary and is rejected. Without this setting the Editor button
is not shown at all.

## Memory scopes

Memory is keyed by workspace, not by issue: observations, status, and
summaries for a workspace live under
`~/.overdeck/memory/{project}/{workspaceId}/`. This means a scratch or main
workspace — one with no spawned agent — still accumulates memory from
whatever conversations run in it.

```bash
# Search within one workspace, one project, or across every registered project
pan memory search "auth refactor" --workspace <id>
pan memory search "auth refactor" --project myproject
pan memory search "auth refactor" --global

# Pin a doc into every prompt for a workspace or a whole project
pan memory pin docs/ARCHITECTURE.md --workspace <id>
pan memory pin docs/ARCHITECTURE.md --project myproject
pan memory pins --workspace <id>
pan memory unpin docs/ARCHITECTURE.md --workspace <id>

# Search every workspace that targets a directory (bare flag = current directory)
pan memory search "auth refactor" --target
pan memory search "auth refactor" --target ~/code/some-repo

# Backfill historical Claude Code sessions into memory, matched by cwd
pan memory backfill --dry-run
pan memory backfill --workspace <id>
```

### Reading a workspace's memory back

`status` and `summary` take an issue, a workspace, or neither — with neither they
use the workspace that owns your current directory:

```bash
# Current status, by issue, by workspace, or from inside the workspace
pan memory status PAN-123
pan memory status --workspace my-scratch-notes
pan memory status

# Plus the archived statuses that came before it, newest first
pan memory status --workspace my-scratch-notes --history 3

# Observations in order — last 7 days and 50 rows by default
pan memory timeline --workspace my-scratch-notes
pan memory timeline --days 2 --limit 20 --json

# Print a file from the workspace's memory home, or a slice of one
pan memory read summaries/2026-07-30.md
pan memory read summaries/2026-07-30.md --from 10 --lines 20
```

`pan memory read` only reaches inside that workspace's own memory home:
absolute paths, `../` traversal, and symlinks pointing outside it are all
refused, so your Claude Code session transcripts stay out of reach.

<Note>
  `--history` is capped at 50, but Overdeck keeps only the three most recent
  archived statuses on disk, so asking for more returns what is retained.
</Note>

A pin's scope determines its lifetime: a project-scoped pin survives every
workspace under that project, while a workspace-scoped pin is deleted when
its workspace is.
