# MCP server

Overdeck serves a Model Context Protocol (MCP) server, so another tool (Claude
Desktop, another agent harness, a chat bot) can list conversations, read one,
send a message, start a conversation or a worker, and answer prompts that wait
on you. It reaches this machine's Overdeck only.

This is separate from the Channels bridge (`overdeck-bridge`), which delivers
messages into one running agent. The MCP server is a control surface for
outside tools.

Every tool calls an existing dashboard route with the token the client
presents, so a tool can do only what that token's scopes allow on that route.
There is no second path to any operation.

## Tools

| Tool | What it does | Scope the token needs |
| --- | --- | --- |
| `list_machines` | Lists this machine and its linked machines with their state, load and capability tags. | `read:state` |
| `list_conversations` | Lists recent conversations with status, harness, model and pending input. `limit` 1–200, default 50. | `read:conversations` |
| `search_conversations` | Searches conversations by title and content. `query`, `limit` 1–50, default 20. | `read:conversations` |
| `read_conversation` | Reads one conversation's messages. Pass a page cursor as `before` for older messages. | `read:conversations` |
| `send_message` | Sends a message to a running conversation. | `tell` (`operate` includes it) |
| `start_conversation` | Starts a conversation with a first message. Optional `projectKey`, `model`, `harness`, `effort`, `issueId`, `machine` (a label, environment id or `auto`), `needs`. | `operate` |
| `start_worker` | Starts a registered worker on an issue that has a workspace on the chosen machine. `issueId`, `prompt`, optional `model`, `harness`, `effort`, `readOnly`, `name`, `machine`, `needs`. | `operate` |
| `list_pending_input` | Lists conversations waiting on input: questions, permission prompts, plan approvals and menus. | `read:conversations` |
| `answer_question` | Answers a Claude Code conversation's pending question. | `tell` and `approve` |
| `answer_permission` | Answers a Claude Code permission prompt with `allow-once`, `allow-always` or `deny`. | `approve` |

No tool pairs devices, creates or revokes tokens, reads or writes settings, or
touches the session vault.

`tools/list` shows only the tools whose scope the token holds, so a
`read:state` token sees only `list_machines`. Calling a tool the token cannot
see answers `Unknown tool <name>`. Tools for managed agents are listed only to
agent tokens.

A tool the token's scopes hide answers `Unknown tool <name>`. A route can
still refuse a listed tool, for example a linked machine's ceiling, with
`HTTP 403: insufficient_scope (missingScope: approve)`.

## Over HTTP

Open **Settings → Anywhere** on this machine and choose **Copy MCP URL**. The
dialog:

1. Asks for a name, the address the client will use, and whether to allow
   answering questions and approving permissions.
2. Creates an MCP access token and copies the URL, `<address>/mcp`, to the
   clipboard.
3. Shows the URL, the `Authorization: Bearer odk_…` header and a ready client
   config, each with a Copy button. The token is shown once.

The address list holds the machine's trusted addresses that other devices can
reach, with the first `https://` one selected. When there is none, the dialog
offers this browser's address, which works only on this machine. Add a
reachable address (for example a Tailscale address) under Settings → Anywhere
first.

The token is never part of the URL. Proxy and access logs record URLs, so the
token travels only in the `Authorization` header. Every common MCP client
accepts a header. With Claude Code:

```bash
claude mcp add --transport http overdeck https://desk.tailnet.ts.net/mcp \
  --header "Authorization: Bearer odk_…"
```

Or in an `mcp.json`-style config:

```json
{
  "mcpServers": {
    "overdeck": {
      "type": "http",
      "url": "https://desk.tailnet.ts.net/mcp",
      "headers": { "Authorization": "Bearer odk_…" }
    }
  }
}
```

The endpoint is stateless. Each `POST /mcp` gets its own server and one JSON
answer; there is no session and no event stream. `GET /mcp` and `DELETE /mcp`
answer 405. Only a browser on this machine can create the token; a paired
device's browser sees "Only a browser on this machine can create MCP tokens."

`/mcp` is served by the production dashboard (`pan up`) and its reachable
addresses. The Vite dev server (`pan dev`) does not proxy it.

## Over stdio

`pan mcp serve` serves the same tools over stdin and stdout. It reads the token
from the `OVERDECK_MCP_TOKEN` environment variable, or, when that is unset,
from the file named by `OVERDECK_MCP_TOKEN_FILE`; a command-line flag would
show in `ps`. Create a token first:

```bash
pan token create mcp --scopes read:state,read:conversations,operate
OVERDECK_MCP_TOKEN=odk_… pan mcp serve
```

Or from a file, which must be mode 0600:

```bash
chmod 600 ~/.overdeck/mcp-token
OVERDECK_MCP_TOKEN_FILE=~/.overdeck/mcp-token pan mcp serve
```

The command checks the token before it serves. It exits 1 when neither is set,
when the token is unknown, revoked, a paired-device credential, or carries
`admin`, or when the file is unreadable, empty, or readable by group or
others. Its stdout carries only JSON-RPC; every message goes to stderr.

A Claude Desktop config:

```json
{
  "mcpServers": {
    "overdeck": {
      "command": "pan",
      "args": ["mcp", "serve"],
      "env": { "OVERDECK_MCP_TOKEN": "odk_…" }
    }
  }
}
```

The dashboard must be running: each tool calls it.

## Sign in with OAuth

A hosted MCP client (a Claude Desktop connector, a chat bot) cannot be handed a
token file. It signs in through the MCP authorization flow instead: point it at
`<dashboard URL>/mcp` and it finds the sign-in server by itself. The discovery
document is at `<dashboard URL>/.well-known/oauth-protected-resource/mcp`, and
an unauthenticated `POST /mcp` answers 401 with a `WWW-Authenticate` header that
names it.

1. Your app opens a sign-in page in your browser. The page shows the app's
   name, where it will send you back, and an approval code such as `KQZT-MWRB`.
2. You open the Overdeck dashboard on this machine, or run `pan mcp oauth pending`.
3. You check that the dashboard shows the same code, and pick an access level.
4. The page sends you back to your app, and your app is signed in.

The page itself can never approve anything, because anyone who can reach the
port can open it. Approve only a sign-in whose code matches the page you opened.

| Level | Label | Scopes |
| --- | --- | --- |
| `read` | Read only | `read:state`, `read:conversations` |
| `message` | Can message | `read:state`, `read:conversations`, `tell` |
| `operate` | Can operate | `read:state`, `read:conversations`, `tell`, `operate` |
| `approve` | Can approve | `read:state`, `read:conversations`, `tell`, `operate`, `approve` |

An OAuth sign-in never gets `admin`, `forward`, `read:settings`, `read:costs` or
`read:events`. The level the app asks for is only a suggestion: a stock MCP
client asks for every level, so Overdeck offers the lowest one it named, and you
choose the real level when you approve.

Each sign-in gets an access token that lasts 30 days and a refresh token that
lasts 90 days. Each refresh replaces both. A refresh token is single use: if an
old one is presented again, Overdeck treats it as stolen and ends the sign-in.
After 90 days the app must sign in again. A sign-in waiting for approval expires
after 10 minutes, and every waiting sign-in is lost when the dashboard restarts;
start it again from the app.

Manage sign-ins from the terminal:

```bash
pan mcp oauth pending                            # sign-ins waiting for you
pan mcp oauth approve KQZT-MWRB --level operate  # approve the one showing that code
pan mcp oauth deny KQZT-MWRB                     # refuse it
pan mcp oauth list                               # active sign-ins
pan mcp oauth revoke <sign-in id>                # end one
pan mcp oauth issue --name xAI --level message   # tokens for a client that cannot open a browser
```

`issue` creates a sign-in at once and prints its access and refresh tokens. They
are shown once; store them in the client. Use it for an API caller such as the
xAI API, which takes a token but cannot show you a browser page. The approval
code is case-insensitive and the dash is optional.

The sign-in endpoints answer on this machine, the LAN, the tailnet (Tailscale
Serve) and the dashboard's other trusted addresses. The discovery documents are
built from the address the client used, so a request for an address Overdeck
does not trust gets 400. A Tailscale Funnel request gets 404.

## Scopes and the approve scope

An MCP token is an ordinary access token. Copy MCP URL gives it `read:state`,
`read:conversations` and `operate` by default. `operate` covers `tell` and the
two start tools.

The box **Allow answering questions and approving permissions** adds
`approve`. It is off by default, and only `approve` or `admin` satisfies it.
`approve` lets the token answer blocking prompts: the `answer_question` and
`answer_permission` tools, and the dashboard routes for pane-choice menus, pi
asks, Codex approvals and plan approvals. See [Remote access](/configuration/remote-access)
for the full scope table.

<Warning>
`approve` does not stop text from reaching a conversation that waits on a
question. A token with `tell` can still send any message with `send_message`.
What `approve` gates is the keystroke-driven answers and the two answer tools.
</Warning>

MCP never accepts an `admin` token, the machine's internal token or the
dashboard's own session. Both transports refuse them.

## Revoking

Revoke an MCP token under **Settings → Anywhere → Access tokens**, under
**Settings → Access Tokens**, or with `pan token revoke <id>`. A token revoked
through the dashboard fails its next request at once. A token revoked by
another process (for example `pan token revoke` while the dashboard is
unreachable) fails within 5 seconds, when the dashboard rereads its token list.

End an OAuth sign-in with `pan mcp oauth revoke <sign-in id>` (ids from
`pan mcp oauth list`); its access and refresh tokens stop working at once.
Revoking an OAuth access token under **Settings → Access Tokens** or with
`pan token revoke` stops that access token at once and ends its sign-in at its
next refresh.

## Fleet reach

One MCP URL reaches every machine this one is linked to (see
[Linked machines](/configuration/linked-machines)).

- `list_machines` lists this machine and each linked machine with its state, load and tags.
- `list_conversations` and `search_conversations` include linked machines' conversations.
  A conversation on another machine is named `@<label|environment-id>/<name>`; pass that
  name to `read_conversation`, `send_message` and the `answer_*` tools.
- `start_conversation` and `start_worker` take `machine`: omit it for this machine, give a
  linked machine's label or environment id, or `auto` to place the work by load. With
  `auto`, `needs` (a list of capability tags such as `docker`) limits the choice.

**The token's scopes are the fence on every machine.** A call that reaches another machine
is forwarded as the operator with a ceiling equal to the token's own scopes, so the other
machine applies exactly what you granted: a token without `approve` gets 403 on a linked
conversation's permission prompt, and one without `tell` cannot message it. Settings are
never reachable: `PUT /api/settings` answers 403 because an MCP token never carries `admin`,
and linked machines never forward it. A linked machine cannot use this one to reach a third
machine (no chained hops), so the URL reaches only the machines linked to this dashboard.
