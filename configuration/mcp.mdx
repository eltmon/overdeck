# MCP server

Overdeck serves a Model Context Protocol (MCP) server, so another tool (Claude
Desktop, another agent harness, a chat bot) can list conversations, read one,
send a message, start a conversation or a worker, and answer prompts that wait
on you. It reaches this machine and the machines it is linked to (see Fleet reach).

This is separate from the Channels bridge (`overdeck-bridge`), which delivers
messages into one running agent. The MCP server is a control surface for
outside tools.

Every tool calls an existing dashboard route with the token the client
presents, so a tool can do only what that token's scopes allow on that route.
There is no second path to any operation.

## Tools

| Tool | What it does | Scope the token needs |
| --- | --- | --- |
| `list_machines` | Lists this machine and its linked machines with their state, load and capability tags. | `read:state` |
| `list_conversations` | Lists recent conversations with status, harness, model and pending input. `limit` 1–200, default 50. | `read:conversations` |
| `search_conversations` | Searches conversations by title and content. `query`, `limit` 1–50, default 20. | `read:conversations` |
| `read_conversation` | Reads one conversation's messages. Pass a page cursor as `before` for older messages. | `read:conversations` |
| `send_message` | Sends a message to a running conversation. | `tell` (`operate` includes it) |
| `start_conversation` | Starts a conversation with a first message. Optional `projectKey`, `model`, `harness`, `effort`, `issueId`, `machine` (a label, environment id or `auto`), `needs`. | `operate` |
| `start_worker` | Starts a registered worker on an issue that has a workspace on the chosen machine. `issueId`, `prompt`, optional `model`, `harness`, `effort`, `readOnly`, `name`, `machine`, `needs`. | `operate` |
| `schedule_message` | Queues a message for a Claude Code conversation that Overdeck sends after its usage limit resets, or at once if it is not limited. At most 20 queued; `/pan` commands are refused. | `tell` |
| `schedule_recurring` | Creates a recurring schedule: `prompt`, a 5-field `cron` (runs at least 15 minutes apart), optional `timeZone` (default: the Overdeck machine's zone) and `enabled`. Not for agent conversations. | `tell` |
| `list_scheduled` | Lists a conversation's pending one-shot messages (`once`) and its schedules (`recurring`). | `read:conversations` |
| `update_scheduled` | `kind: once` replaces a pending message's text; `kind: recurring` changes `prompt`, `cron`, `timeZone` or `enabled` (pause or resume). | `tell` |
| `delete_scheduled` | `kind: once` cancels an unsent message; `kind: recurring` deletes a schedule. | `tell` |
| `list_pending_input` | Lists what waits on input on this machine and every online linked machine, conversations and agents, grouped by machine. | `read:conversations` |
| `answer_question` | Answers a pending question of a Claude Code conversation (`conversation`) or of an agent on this machine (`agentId`, optional `toolUseId`). | `tell` and `approve` |
| `answer_permission` | Answers a Claude Code permission prompt with `allow-once`, `allow-always` or `deny`. | `approve` |
| `answer_pane_choice` | Chooses an option (`selectedIndex` 0-8) in a numbered menu shown in a Claude Code conversation, with its `signature`. | `approve` |
| `answer_codex_approval` | Answers a Codex conversation's approval prompt with the 1-based `optionNumber`, and `toolUseId` when the app-server transport needs it. | `approve` |
| `answer_pi_ask` | Answers a Pi conversation's ask prompt: `toolUseId` and exactly one `answers` entry. | `approve` |
| `answer_plan` | Approves or rejects a conversation's proposed plan: `action` (`approve-auto`, `approve-manual`, `reject-ultraplan`, `reject-feedback`) and optional `feedback`. | `approve` |
| `answer_agent_plan` | Approves or rejects a plan an agent on this machine is waiting on: `agentId`, `action`, optional `feedback`. | `approve` |
| `answer_agent_permission` | Allows or denies a tool-permission request from an agent on this machine: `agentId`, `requestId`, `behavior` (`allow`/`deny`). | `approve` |

No tool pairs devices, creates or revokes tokens, reads or writes settings, or
touches the session vault.

`tools/list` shows only the tools whose scope the token holds, so a
`read:state` token sees only `list_machines`. Calling a tool the token cannot
see answers `Unknown tool <name>`. Tools for managed agents are listed only to
agent tokens.

### Agent-only tools

| Tool | What it does | Scope the token needs |
| --- | --- | --- |
| `wait_job` | Waits up to 50 s for a job another tool started. Answers `done` with the exit code and output, or `running` with `next`, the call to make again. Never poll or sleep; jobs are forgotten when the dashboard restarts. | `read:state` (agent tokens only) |
| `task_claim` | Claims a checklist item of the agent's issue (`pan task claim`). | `tell` (agent tokens only) |
| `task_done` | Marks a checklist item done once its `Item:` commit is pushed (`pan task done`). | `tell` (agent tokens only) |
| `task_block` | Marks a checklist item blocked, optionally on issues or PRs (`on`), and wakes the agent when they merge (`pan task block`). | `tell` (agent tokens only) |
| `done` | Signals the issue's work is complete: push, PR, tracker In Review, review started (`pan done`). | `operate` (agent tokens only) |
| `handoff` | Hands the conversation off to a new one with a `focus` and optional `title` (`pan handoff self`). Not for work agents, which have no conversation. | `tell` (agent tokens only) |
| `worker_report` | Records a worker's report with `status` `done`, `blocked` or `failed` (`pan worker report`). Workers only. | `tell` (agent tokens only) |
| `request_secret` | Asks the operator for a secret, such as an API key, by an environment-variable-style `name` and a short `prompt`; answers a `requestId` and `next`, the `secret_wait` call to make. | `tell` (agent tokens only) |
| `secret_wait` | Waits up to 50 s for the operator's answer. Answers `pending` with `next`, `delivered` with `file` (the path of the secret, never the value), `declined` or `expired`. | `read:state` (agent tokens only) |

Each workflow tool runs the `pan` command for the calling agent, on that
agent's issue, and waits up to 50 s. It answers `done` with the exit code and
output, or `running` with `next`, a `wait_job` call to make again. A non-zero
exit code means `pan` refused; stderr says why. Review, test and ship agents
lack `operate`, so `done` is hidden from them.

Agent-only tools call routes under `/api/self/`, which refuse any token that
is not an agent token.

### Secrets

An agent that needs an API key or a password calls `request_secret` instead
of asking in chat, so the value never enters its transcript.

- The request appears as a **Secret requested** card in the Decisions panel.
  Only this machine's own dashboard, opened in a browser on this machine, can
  answer it. A phone, a paired device or another machine's browser shows
  "Answer this on <machine>'s own dashboard".
- The operator types the value into the masked input and chooses **Send**, or
  chooses **Decline**.
- The value lands in a file: `~/.overdeck/agents/<agentId>/secrets/<NAME>` for
  an agent, or `~/.overdeck/conversations/<tmux session>/secrets/<NAME>` for a
  conversation. The file has mode 0600 in a directory with mode 0700.
- The `secrets/` directory is deleted when the agent stops, is killed, exits
  or is closed out.
- A request expires after 10 minutes by default (`timeoutMs` allows 1 to 60
  minutes). A dashboard restart forgets every pending request, and the agent
  must call `request_secret` again.
- The value never appears in a tool result, the transcript, the activity feed
  or the dashboard log. The agent reads the file straight into the program
  that needs it, for example `KEY="$(cat <file>)" some-command`, and never
  prints it.

A tool the token's scopes hide answers `Unknown tool <name>`. A route can
still refuse a listed tool, for example a linked machine's ceiling, with
`HTTP 403: insufficient_scope (missingScope: approve)`.

## Over HTTP

Open **Settings → Anywhere** on this machine and choose **Copy MCP URL**. The
dialog:

1. Asks for a name, the address the client will use, and whether to allow
   answering questions and approving permissions.
2. Creates an MCP access token and copies the URL, `<address>/mcp`, to the
   clipboard.
3. Shows the URL, the `Authorization: Bearer odk_…` header and a ready client
   config, each with a Copy button. The token is shown once.

The address list holds the machine's trusted addresses that other devices can
reach, with the first `https://` one selected. When there is none, the dialog
offers this browser's address, which works only on this machine. Add a
reachable address (for example a Tailscale address) under Settings → Anywhere
first.

The token is never part of the URL. Proxy and access logs record URLs, so the
token travels only in the `Authorization` header. Every common MCP client
accepts a header. With Claude Code:

```bash
claude mcp add --transport http overdeck https://desk.tailnet.ts.net/mcp \
  --header "Authorization: Bearer odk_…"
```

Or in an `mcp.json`-style config:

```json
{
  "mcpServers": {
    "overdeck": {
      "type": "http",
      "url": "https://desk.tailnet.ts.net/mcp",
      "headers": { "Authorization": "Bearer odk_…" }
    }
  }
}
```

The endpoint is stateless. Each `POST /mcp` gets its own server and one JSON
answer; there is no session and no event stream. `GET /mcp` and `DELETE /mcp`
answer 405. Only a browser on this machine can create the token; a paired
device's browser sees "Only a browser on this machine can create MCP tokens."

`/mcp` is served by the production dashboard (`pan up`) and its reachable
addresses. The Vite dev server (`pan dev`) does not proxy it.

## Over stdio

`pan mcp serve` serves the same tools over stdin and stdout. It reads the token
from the `OVERDECK_MCP_TOKEN` environment variable, or, when that is unset,
from the file named by `OVERDECK_MCP_TOKEN_FILE`; a command-line flag would
show in `ps`. Create a token first:

```bash
pan token create mcp --scopes read:state,read:conversations,operate
OVERDECK_MCP_TOKEN=odk_… pan mcp serve
```

Or from a file, which must be mode 0600:

```bash
chmod 600 ~/.overdeck/mcp-token
OVERDECK_MCP_TOKEN_FILE=~/.overdeck/mcp-token pan mcp serve
```

The command checks the token before it serves. It exits 1 when neither is set,
when the token is unknown, revoked, a paired-device credential, or carries
`admin`, or when the file is unreadable, empty, or readable by group or
others. Its stdout carries only JSON-RPC; every message goes to stderr.

A Claude Desktop config:

```json
{
  "mcpServers": {
    "overdeck": {
      "command": "pan",
      "args": ["mcp", "serve"],
      "env": { "OVERDECK_MCP_TOKEN": "odk_…" }
    }
  }
}
```

The dashboard must be running: each tool calls it.

## Agents get these tools

Every Claude Code, Kimi Code ACP (`acp`) and OpenCode (`opencode`) agent that
Overdeck launches on this machine starts with the `overdeck` server: work agents, role runs (plan, review, test, ship, worker and
the others), planning sessions and conversations. You do not create a token for
them.

Each agent holds its own agent token. It sits in `mcp-token` (mode 0600), next
to `overdeck-mcp.json`, in `~/.overdeck/agents/<id>/` for an agent or
`~/.overdeck/conversations/conv-<name>/` for a conversation. `overdeck-mcp.json`
runs `pan mcp serve` and names only the token file, so neither it nor the
launcher script holds the token. The launcher passes
`--mcp-config=<file>` and, when the role has no tool allow-list,
`--allowedTools=mcp__overdeck`, so a tool call does not stop at a permission
prompt. Roles with a `tools:` list (review, test) get `mcp__overdeck` in that
list instead.

An ACP agent gets the same `overdeck-mcp.json`. The launcher passes
`--mcp-config <file>` to the ACP host, which sends the server to the agent in
`session/new` and `session/load`. The ACP host approves the agent's permission
requests itself, so no allow-list is needed.

The token's scopes follow the agent's role:

| Agent | Scopes |
| --- | --- |
| work, worker, plan, strike, sequencer, knowledge, flywheel | `read:events`, `read:state`, `read:conversations`, `tell`, `operate` |
| review, test, ship | `read:events`, `read:state`, `read:conversations`, `tell` |
| an operator conversation | the work scopes plus `approve` |
| a lane conversation (`pan lane start`) | the `worker` scopes |
| the Flywheel conversation | the `flywheel` scopes |

A resumed, recovered or relaunched agent keeps the same server and reuses its
live token. Stopping the agent revokes the token.

To turn injection off, set this in `config.yaml`:

```yaml
mcp:
  agents: false
```

These launches get no server: Docker workspaces (`OVERDECK_DOCKER_WORKSPACE=1`
or `PAN_DOCKER=1`), bare conversations, Fly machines, and harnesses other than
Claude Code, `acp` and `opencode` (Codex follows). When the token cannot be
minted or the config cannot be written, the agent starts without the server and
the log shows one `[agent-injection] overdeck MCP skipped for <id>: <reason>`
warning. The agent can still reach Overdeck through `pan`.

## Scopes and the approve scope

An MCP token is an ordinary access token. Copy MCP URL gives it `read:state`,
`read:conversations` and `operate` by default. `operate` covers `tell` and the
two start tools.

The box **Allow answering questions and approving permissions** adds
`approve`. It is off by default, and only `approve` or `admin` satisfies it.
`approve` lets the token answer blocking prompts with any of the eight answer
tools: `answer_question`, `answer_permission`, `answer_pane_choice`,
`answer_codex_approval`, `answer_pi_ask`, `answer_plan`, `answer_agent_plan`
and `answer_agent_permission`. See [Remote access](/configuration/remote-access)
for the full scope table.

<Warning>
`approve` does not stop text from reaching a conversation that waits on a
question. A token with `tell` can still send any message with `send_message`.
What `approve` gates is the keystroke-driven answers and the two answer tools.
</Warning>

MCP never accepts an `admin` token, the machine's internal token or the
dashboard's own session. Both transports refuse them.

## Revoking

Revoke an MCP token under **Settings → Anywhere → Access tokens**, under
**Settings → Access Tokens**, or with `pan token revoke <id>`. A token revoked
through the dashboard fails its next request at once. A token revoked by
another process (for example `pan token revoke` while the dashboard is
unreachable) fails within 5 seconds, when the dashboard rereads its token list.

## Fleet reach

One MCP URL reaches every machine this one is linked to (see
[Linked machines](/configuration/linked-machines)).

- `list_machines` lists this machine and each linked machine with its state, load and tags.
- `list_conversations` and `search_conversations` include linked machines' conversations.
  A conversation on another machine is named `@<label|environment-id>/<name>`; pass that
  name to `read_conversation`, `send_message`, the `answer_*` tools, and `schedule_message`,
  `schedule_recurring`, `list_scheduled`, `update_scheduled` and `delete_scheduled`.
- `start_conversation` and `start_worker` take `machine`: omit it for this machine, give a
  linked machine's label or environment id, or `auto` to place the work by load. With
  `auto`, `needs` (a list of capability tags such as `docker`) limits the choice.

**The token's scopes are the fence on every machine.** A call that reaches another machine
is forwarded as the operator with a ceiling equal to the token's own scopes, so the other
machine applies exactly what you granted: a token without `approve` gets 403 on a linked
conversation's permission prompt, and one without `tell` cannot message it. Settings are
never reachable: `PUT /api/settings` answers 403 because an MCP token never carries `admin`,
and linked machines never forward it. A linked machine cannot use this one to reach a third
machine (no chained hops), so the URL reaches only the machines linked to this dashboard.

Agent answers (`answer_agent_plan`, `answer_agent_permission`, `answer_question` with
`agentId`) reach agents on this machine only; `list_pending_input` marks a linked machine's
agents `remote: true`.

The linked machine must run a version with the schedule scopes (PAN-4939); an older one
answers `403 insufficient_scope` for recurring schedules.
