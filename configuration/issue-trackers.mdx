# Issue Tracker Integration

Overdeck integrates with popular issue tracking systems to provide unified project management.

## Supported Trackers

| Tracker | Configuration |
|---------|---------------|
| **GitHub Issues** | `GITHUB_TOKEN` or `gh auth login` |
| **Linear** | `LINEAR_API_KEY` in `.overdeck.env` |
| **GitLab Issues** | `GITLAB_TOKEN` or `glab auth login` |
| **Rally** | `RALLY_API_KEY` in `.overdeck.env` |
| **Jira** (Cloud and Data Center) | `JIRA_API_TOKEN`, `JIRA_EMAIL`, `JIRA_BASE_URL` in `.overdeck.env`, or Settings → Tracker Keys |

All trackers are equal — configure whichever your projects use. The dashboard displays issues from all configured trackers in a unified Kanban board.

## Configuration

Create `~/.overdeck.env`:

```bash
GITHUB_TOKEN=ghp_xxxxx     # For GitHub-tracked projects
LINEAR_API_KEY=lin_api_xxxxx  # For Linear-tracked projects
GITLAB_TOKEN=glpat-xxxxx  # For GitLab-tracked projects
RALLY_API_KEY=_xxxxx       # For Rally-tracked projects
JIRA_API_TOKEN=xxxxx       # For Jira-tracked projects (API token or personal access token)
JIRA_EMAIL=you@acme.com    # Jira Cloud only: the account that owns the token
JIRA_BASE_URL=https://acme.atlassian.net  # Default Jira site
```

## Unified Issue ID Parser

Overdeck uses a unified issue ID parser that handles multiple formats through configurable project patterns. This eliminates the hardcoded `PREFIX-NUMBER` assumption that doesn't work for Rally-style IDs.

### Supported Formats

| Format | Example | Parser Behavior |
|--------|---------|----------------|
| **Standard** | `MIN-123`, `PAN-456` | Prefix and number separated by dash |
| **Rally** | `F29698`, `US12345` | Type prefix directly concatenated with number |
| **Custom** | `PROJ12345` | Per-project regex pattern via `issue_pattern` |
| **Jira** | `PROJ-123` | Standard format; `issue_prefix` is the Jira project key |

### Configuration Fields

| Field | Description |
|-------|-------------|
| `tracker` | Tracker type: `linear`, `github`, `gitlab`, `rally`, `jira` |
| `issue_prefix` | Single prefix (e.g., `"MIN"`) |
| `issue_prefixes` | Array of prefixes mapping to one project (e.g., `[F, US, DE, TA]`) |
| `issue_pattern` | Custom regex with two capture groups: `^(PREFIX)-(\d+)$` |

### Custom ID Patterns

For non-standard trackers, define a custom regex pattern:

```yaml
projects:
  myproject:
    tracker: custom
    issue_pattern: "^(PROJ)-(\\d+)$"  # Matches PROJ-123
```

## GitHub Issues

GitHub Issues provides full integration with PRs, status updates, and automated merging.

### Setup

```bash
# Authenticate with GitHub CLI (recommended)
gh auth login

# Or set a token in .overdeck.env
GITHUB_TOKEN=ghp_xxxxx
```

### GitHub organizations and identities

A project's GitHub **owner** is the first part of its `github_repo` (`mindyournow` in `mindyournow/myn-cli`). Overdeck decides per repository who acts there:

- **The GitHub App's bot** (for example `overdeck-agent[bot]`) acts on every repository where the App is installed. Agents push, open and merge pull requests, and post review verdicts as the bot.
- **Your `gh` account** acts everywhere else. Agents keep the remote and credentials the clone came with, and verdicts post as your account.

Overdeck finds the installation that covers each repository by itself (`GET /repos/{owner}/{repo}/installation`) and remembers the answer for six hours.

**To cover an organization with the bot**, make the App public in its GitHub settings, install it on the organization, then run `pan doctor` so Overdeck asks GitHub again. Until then, a review verdict there posts as your `gh` account, and an approving verdict marker counts from any trusted author on that repository. Installing the App restores bot-only approval.

**If the organization enforces SAML single sign-on**, authorize your `gh` token for it: run `gh auth refresh -h github.com` and authorize the organization in the browser.

**Where to see the identity:** the sidebar groups projects by owner when they span more than one; the Command Deck project header shows `<owner> · <identity>`; **Settings → GitHub Identities** lists every project; and `pan doctor` prints one `GitHub identity: <owner>` row per owner, with a fix when the identity cannot push.

A separate work GitHub account and GitHub Enterprise Server hosts are not supported yet ([#5154](https://github.com/eltmon/overdeck/issues/5154)).

### Issue Prefix

GitHub Issues use an uppercase project key as prefix, derived from the project name in `projects.yaml`:

```
PAN-45       # GitHub issue #45 on the overdeck project
KRUX-3       # GitHub issue #3 on the krux project
```

The prefix is the project key uppercased. Configure via `projects.yaml`:

```yaml
projects:
  overdeck:
    name: "Overdeck CLI"
    path: /home/user/projects/overdeck
    github_repo: eltmon/overdeck
```

### Creating Issues

```bash
# Via CLI
gh issue create --title "New feature" --body "Description"

# Or via dashboard - select GitHub project
```

## Linear Integration

Linear provides full integration with cycles, labels, and status updates.

### Setup

1. Generate an API key at https://linear.app/settings/api
2. Add to `~/.overdeck.env`:
   ```bash
   LINEAR_API_KEY=lin_api_xxxxx
   ```

### Team Mapping

Map Linear teams to local projects in `~/.overdeck/projects.yaml`:

```yaml
projects:
  myapp:
    name: "My Application"
    path: /home/user/projects/myapp
    issue_prefix: APP  # Linear team prefix
```

### Issue States

Overdeck tracks and updates Linear issue states:

| State | Description |
|-------|-------------|
| **Backlog** | Not started |
| **Planning** | Planning session active |
| **In Progress** | Agent working on issue |
| **In Review** | Awaiting code review |
| **Done** | Work completed |

myproject!23  # GitLab issue/MR

## Rally Integration

Rally (CA Agile Central) is supported for enterprises using Rally for project management.

### Setup

1. Generate a Rally API key from your Rally workspace settings
2. Add to `~/.overdeck.env`:
   ```bash
   RALLY_API_KEY=_xxxxx
   ```

### Configuration

Configure Rally workspace mapping:

```yaml
# ~/.overdeck/projects.yaml
projects:
  enterprise-app:
    name: "Enterprise Application"
    path: /home/user/projects/enterprise
    tracker: rally
    issue_prefixes: [F, US, DE, TA, TC]  # All Rally artifact types → this project
    rally_workspace: YOUR_WORKSPACE_OID
    rally_project: YOUR_PROJECT_OID
```

### Rally ID Formats

Rally uses a different ID format than most trackers. Instead of `PREFIX-NUMBER`, Rally uses **type prefixes concatenated with numbers**:

| Prefix | Artifact Type | Example |
|--------|--------------|---------|
| `F` | Feature | `F29698` |
| `US` | User Story | `US12345` |
| `DE` | Defect | `DE118304` |
| `TA` | Task | `TA4567` |
| `TC` | Test Case | `TC78901` |

Overdeck's unified issue ID parser handles these formats automatically. Configure `issue_prefixes` to map all Rally artifact types to your project:

```yaml
issue_prefixes: [F, US, DE, TA, TC]
```

With this configuration:
- `pan workspace create F29698` → resolves to your project
- `pan workspace create US12345` → resolves to your project
- `pan workspace create DE118304` → resolves to your project

### Shadow Mode

Rally integration supports **shadow mode** — tracking Rally issues locally without modifying the tracker. This is useful for teams transitioning to Overdeck or evaluating the workflow.

```yaml
projects:
  enterprise-app:
    shadow:
      enabled: true
      trackers:
        rally: true
```

In shadow mode:
- Issue states are tracked locally in Overdeck
- No updates are sent to Rally
- Agents can read Rally data but changes stay local

### Rally Troubleshooting

#### WSAPI Query Parse Errors

If you see errors like `Could not parse: Error parsing expression`, check:

1. **Workspace and Project Configuration**
   ```bash
   # In ~/.overdeck.env
   RALLY_WORKSPACE=/workspace/12345
   RALLY_PROJECT=/project/67890
   ```

2. **API Key Permissions**
   - Ensure API key has read access to the workspace
   - Verify key is not expired

3. **Debug Logging**
   ```bash
   DEBUG=rally pan up
   ```
   This will log the actual WSAPI queries being sent to Rally, which helps diagnose parse errors.

4. **Test Configuration**
   Use the Settings page "Test Connection" button to validate Rally setup, or call the API directly:
   ```bash
   curl -X POST http://localhost:3011/api/rally/validate \
     -H 'Content-Type: application/json' \
     -d '{"apiKey": "YOUR_KEY", "workspace": "/workspace/12345", "project": "/project/67890"}'
   ```

#### Finding Workspace and Project IDs

Rally workspace and project IDs are numeric strings prefixed with `/workspace/` or `/project/`:

1. Log into Rally web UI
2. Navigate to desired workspace/project
3. Check URL: `https://rally1.rallydev.com/#/workspace/12345/project/67890`
4. Use: `RALLY_WORKSPACE=/workspace/12345` and `RALLY_PROJECT=/project/67890`

## Jira Integration

Jira Cloud and Jira Data Center are supported. A project selects Jira with `tracker: jira`; its code can still live on GitHub or GitLab, and Overdeck finds its pull requests there.

### Setup (Jira Cloud)

1. Create an API token at [id.atlassian.com/manage-profile/security/api-tokens](https://id.atlassian.com/manage-profile/security/api-tokens).
2. Add the token, the email of the account that owns it, and your site to `~/.overdeck.env`:
   ```bash
   JIRA_API_TOKEN=xxxxx
   JIRA_EMAIL=you@acme.com
   JIRA_BASE_URL=https://acme.atlassian.net
   ```
   Or fill the three Jira rows under **Settings → Tracker Keys**. Settings values win over the environment.
3. Run `pan doctor` to check the credentials.

Jira Cloud uses REST API v3 and HTTP Basic authentication with `email:token`.

### Setup (Jira Data Center)

1. Create a personal access token in your Jira profile (**Profile → Personal Access Tokens**).
2. Set `JIRA_API_TOKEN` to that token and `JIRA_BASE_URL` to your site, for example `https://jira.acme.com`. The email is not needed.

Overdeck sends the personal access token as a `Bearer` token and uses REST API v2. It detects the deployment once per site: a host ending in `.atlassian.net` is Cloud; any other site is asked `GET /rest/api/2/serverInfo`. Set `jira.deployment` to skip the probe.

### Configuration

```yaml
# ~/.overdeck/projects.yaml
projects:
  acme-app:
    name: "Acme App"
    path: /home/user/projects/acme-app
    tracker: jira
    issue_prefix: ACME             # The Jira project key (letters only)
    github_repo: acme/app          # Where the code and pull requests live
    jira:
      site: https://acme.atlassian.net   # Optional; defaults to JIRA_BASE_URL
      deployment: cloud                  # Optional: cloud | datacenter
      status_map:                        # Optional: your workflow's status names
        in_review: Code Review
        in_planning: Refinement          # Only written when set
```

You can also register a Jira project with `pan project add <path> --tracker jira --jira-site https://acme.atlassian.net`, or choose **Issue tracker → Jira** under Options in the dashboard's Add-project dialog.

### Status mapping

Overdeck maps a Jira status to its own state by status name first, then by status category. `jira.status_map` entries replace the defaults below.

| Overdeck state | Default Jira status |
|----------------|---------------------|
| `backlog` | Backlog |
| `todo` | To Do |
| `in_progress` | In Progress |
| `in_review` | In Review |
| `verifying_on_main` | In Review |
| `done` | Done |
| `canceled` | Canceled |

A name match is case-insensitive, and the first state in this table wins, so `In Review` reads as `in_review`. A status with no name match uses its category: To Do → `todo`, In Progress → `in_progress`, Done → `done`. Overdeck writes no workflow labels to Jira.

### Lifecycle writes

Jira does not let a client set a status directly, so Overdeck posts the workflow transition that reaches the wanted status.

| Action | Target status |
|--------|---------------|
| `pan start` (work begins) | In Progress |
| Planning starts | `status_map.in_planning`, only when set |
| `pan done` | In Review |
| Merge handoff | Verifying on main (default: In Review) |
| Close-out | Done |
| Reopen, reset, aborted planning | To Do (a reopen after a merge goes to Verifying on main) |
| Cancel | Canceled |

Overdeck picks the transition whose target status has the wanted name. For To Do, In Progress and Done it also accepts the single transition into the matching category. When no transition fits, it changes nothing and logs the choices, for example:

```text
[jira] Jira ACME-12: no transition reaches "Canceled" (available: Start → In Progress, Finish → Done); status left unchanged.
```

A Jira write never blocks a merge, a close-out or `pan done`: network, authentication and missing-transition failures are logged and the pipeline continues.

### Pull request links

`pan done` attaches each pull request to the Jira issue as a remote link and moves the issue to In Review. With `--comment`, it also posts the same agent-completed comment Linear gets. Close-out links the merged pull request again (the link is keyed by its URL, so it is not duplicated), moves the issue to Done, and comments `Closed by Overdeck after merge of <PR URL>.`

### Atlassian Rovo MCP for agents

The same Jira email and API token that authenticate the tracker also sign agents into the [`atlassian` skill pack](/features/skill-packs#atlassian)'s Rovo MCP server. Run `pan skills pack add atlassian` and confirm the preview that lists the MCP server, then `pan skills set --pack atlassian on` (or `--project`/`--issue`) to turn it on; Jira and Confluence tools then reach Claude Code and Codex agents. See [Pack MCP servers](/configuration/mcp#pack-mcp-servers).

### Limits

- Jira issues are polled every 120 seconds, on the same cadence as Rally. There are no Jira webhooks yet.
- Jira Service Management, sprints and boards are not supported.
- Authentication is an API token (Cloud) or a personal access token (Data Center); OAuth is not supported.
- Project keys must be 1 to 10 letters; keys with digits or underscores (`AB2`, `MY_PROJ`) are not supported.
- Shadow mode does not apply to Jira.
- The automatic closed-issue workspace cleanup does not read Jira; Jira workspaces are cleaned up by close-out.

### Troubleshooting

- `pan doctor` shows one `Jira (<site>)` row per site. `Authenticated as <name>` means the credentials work.
- HTTP 401 or 403 means Jira rejected the credentials. On Cloud, check that `JIRA_EMAIL` is the account that owns the token.
- HTTP 429 (rate limited) is retried after the `Retry-After` delay, up to three times.
- Search the dashboard log for `[jira]` (lifecycle writes) and `[jira-poll]` (polling) lines.

## Multi-Tracker Workflows

### Tracker and Code Host Can Differ

The issue tracker and code host are independent project settings. The `tracker` field selects where issues and workflow states live, while `github_repo` or `gitlab_repo` selects where Overdeck reads pull requests or merge requests.

Set `tracker` explicitly when one project uses different systems. This example tracks `APP-*` issues in Linear while hosting source code and pull requests on GitHub:

```yaml
projects:
  myapp:
    name: "My Application"
    path: /home/user/projects/myapp
    issue_prefix: APP
    tracker: linear
    linear_project: My Application
    github_repo: myorg/myapp
```

This setup requires both Linear credentials and authenticated GitHub access. Overdeck queries Linear for issue state and labels, then queries GitHub for pull-request evidence. Keep `github_repo`; removing it would hide GitHub pull requests from pipeline membership.

If a Linear-tracked, GitHub-hosted project reports a GitHub Issues request such as `/repos/myorg/myapp/issues?...labels=planning` instead, check for a missing `tracker: linear`. Without that explicit setting, tracker inference may select GitHub Issues from `github_repo`. A GitHub 404 can be misleading here because private repositories also return 404 when the selected GitHub credential lacks access.

Pipeline membership is refreshed in the background and cached per project. If a GitHub GraphQL call fails without returning a response (a network error, a `gh` crash, or a 30-second timeout), Overdeck retries it once after one second. If the refresh still fails, the last successful membership snapshot keeps serving the dashboard and the server log records `[pipeline-membership] refresh failed for <project>; keeping last-good snapshot:` followed by `gh`'s own error output (exit code or timeout, attempt number, and stderr), so the cause is visible without re-running the query by hand. A GraphQL response that carries only `errors` is not retried.

### Different Trackers Across Projects

A separate pattern is using different trackers for different projects:

```yaml
projects:
  myapp:
    name: "My Application"
    issue_prefix: APP
    tracker: linear

  myapp-oss:
    name: "My App OSS Components"
    issue_prefix: OSS
    tracker: github
    github_repo: myorg/myapp-oss
```

### Syncing Between Trackers

Overdeck doesn't sync issues between trackers — each issue lives in its source system. However, agents can reference issues from multiple trackers:

```markdown
<!-- In an agent's STATE.md -->
Related issues:
- MIN-123 (Linear) - Parent feature
- PAN-45 (GitHub) - Dependency fix needed
```
